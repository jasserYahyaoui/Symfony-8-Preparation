Objectif

L'import du blog reçoit un état d'article sous forme de texte. Une faute comme publised ne doit pas devenir un nouvel état accepté par accident. Une enum, disponible depuis PHP 8.1, définit un ensemble fermé de cas nommés. Nous allons choisir entre choix interne et code scalaire, convertir l'entrée puis décider explicitement quoi faire lorsqu'aucun cas ne correspond.

L'essentiel

À comprendre

À retenir en priorité
  1. Les cases sont des singletons comparables par ===.
  2. Une enum peut porter du comportement, pas un état d'instance.

Un cas d'enum est un object représentant un choix connu, pas une string déguisée. Une enum pure suffit pour un choix interne sans code scalaire. Une enum adossée, ou backed enum, associe à chaque cas une valeur int ou string, utile pour échanger ce choix avec l'extérieur.

Toutes exposent les cas par cases() et leur nom par ->name. Les adossées ajoutent ->value, from() et tryFrom(). Pour une valeur du type approprié sans cas correspondant, from() lève ValueError et tryFrom() rend null ; un type incompatible peut encore produire TypeError. L'import devra donc séparer type de l'entrée, appartenance aux choix permis et politique métier.

Une enum peut porter du comportement lié à ses cas, mais pas les données variables de chaque article. Le titre et l'auteur restent dans les objets de l'application ; le cas indique seulement le choix d'état.

Le schéma

Avant de convertir l'état d'un article, isolons le mécanisme avec les codes courts d'une couleur de carte : H correspond à Hearts, X ne correspond à rien. Le diagramme compare deux politiques face à cette absence. Ce détour reste un exemple PHP, pas une étape du GET.

Bleu : entrée ; losange orange : recherche ; capsules vertes : retour ; rouge : exception. Les branches comparent deux méthodes, pas deux appels successifs. tryFrom() tolère une valeur sans cas, pas tous les types : valider le type attendu d'une entrée de formulaire reste nécessaire. Nous gardons ce petit exemple pour observer aussi un comportement attaché au cas, puis nous reviendrons à Draft et Published.

L'exemple

Exemple concret

À retenir en priorité
  1. Une backed enum utilise int ou string.
  2. Chaque case possède une valeur unique.

Nous déclarons deux cas de Suit, leur code et la méthode color() promise par l'interface locale Colorful. L'entrée inconnue X choisit ici volontairement une valeur de repli :

interface Colorful { public function color(): string; }

enum Suit: string implements Colorful
{
    case Hearts = 'H';
    case Spades = 'S';

    const Default = self::Spades;          // alias

    public function color(): string
    {
        return match ($this) {
            self::Hearts => 'Red',
            self::Spades => 'Black',
        };
    }
}

$input = 'X';
$suit = Suit::tryFrom($input) ?? Suit::Default; // Suit::Spades

Le bloc n'affiche rien : $suit contient le cas Suit::Spades, et $suit->color() retournerait Black. Default est une constante désignant ce même cas, pas un troisième cas. Le repli vient de ??, opérateur qui choisit la valeur de droite quand celle de gauche est null, pas d'une règle implicite des enums.

Cette politique peut convenir à une préférence d'affichage. Elle ne doit pas convertir silencieusement un état d'article invalide en « publié » : reconnaître l'absence de cas et décider de son traitement sont deux étapes.

Pure ou adossée

Pour un déplacement interne gauche/droite, nous n'avons pas besoin de code à échanger. Pour l'état importé d'un article, une string stable comme draft est utile. Comparons ces deux besoins :

enum Direction
{
    case Left;
    case Right;
}

enum Status: string
{
    case Draft = 'draft';
    case Published = 'published';
}

echo Direction::Left->name, "\n";
echo Status::Draft->name, ' ', Status::Draft->value, "\n";
var_dump(Direction::Left instanceof UnitEnum);
var_dump(Status::Draft instanceof BackedEnum);

La sortie est Left, Draft draft, puis deux bool(true). Draft est le nom PHP, draft la valeur scalaire adossée, et Status::Draft l'object représentant le cas. Ces trois notions ne sont pas interchangeables.

Une enum adossée utilise un seul type d'adossement, int ou string, pour tous ses cas ; leurs valeurs sont uniques et constantes. Elle ne mélange pas cas purs et cas adossés. Toute enum implémente automatiquement UnitEnum, et une enum adossée implémente aussi BackedEnum. Une enum pure n'acquiert pas de value implicite à partir de son nom.

🌍 In Real Life

La situation : un sélecteur possède des positions nommées ; certaines ont aussi un code utilisé sur les formulaires externes.

L’équivalent dans Symfony : position reconnue → cas d'enum ; nom PHP → name ; code d'échange d'une enum adossée → value.

Retour à la réalité technique : un cas est un objet, pas sa string. Une enum pure n'a pas de value implicite ; une adossée utilise un seul type int ou string avec des valeurs uniques. Ce sont des garanties PHP utilisables dans Symfony.

🧠 Comment le mémoriser : « Position, nom, code. » Image mentale : sélecteur étiqueté avec un code distinct. Question-réflexe : attend-on le cas lui-même ou sa représentation scalaire ?

⚠️ À ne pas confondre : nom Draft, valeur draft et objet Status::Draft.

Une case d'enum ressemble à un statut unique sur un tableau de suivi. Une backed enum lui ajoute un code de lecture : le nom identifie la case dans le programme, la value fournit son code scalaire.

L'API

À retenir en priorité
  1. Pour une valeur du type attendu sans cas correspondant, from() lève ValueError ; tryFrom() renvoie null.
  2. tryFrom() permet de traiter explicitement l'absence de case.

L'import possède désormais une liste de choix connus. cases() retourne les objects des cas, dans l'ordre de déclaration, et non leurs codes. Pour obtenir les codes, on peut lire value sur chacun : array_column(Suit::cases(), 'value') donne ['H', 'S']. Le nom name et, pour une enum adossée, value sont en lecture seule.

L'exemple autonome suivant reprend Status pour distinguer énumération des choix et conversion. Exécute-le séparément du précédent, puisqu'il redéclare la même enum :

enum Status: string
{
    case Draft = 'draft';
    case Published = 'published';
}

var_export(array_column(Status::cases(), 'value'));
echo "\n";
echo Status::from('draft')->name, "\n";
$status = Status::tryFrom('missing');
if (null === $status) {
    echo "unknown status\n";
}

try {
    Status::from('missing');
} catch (ValueError) {
    echo "conversion failed\n";
}

Il affiche l'array ['draft', 'published'], puis Draft, unknown status et conversion failed. La même string inconnue donne soit une absence explicite, soit une ValueError : choisis selon le contrat d'entrée, pas selon l'idée que l'une des méthodes serait toujours plus sûre. Les deux retournent le même cas quand la valeur correspond.

Un array reçu à la place d'une string est un autre problème : tryFrom() ne le transforme pas en simple absence. Les règles de type PHP s'appliquent, et une TypeError reste possible. Si une conversion lève ValueError, elle appartient à la branche Error, pas Exception, comme l'explique le cours sur les erreurs.

Ce qu'une enum peut faire

Après conversion, l'écran de préparation de l'article veut un libellé lisible. Une méthode de l'enum peut centraliser ce choix au lieu de répéter un match chez chaque appelant. Les enums acceptent méthodes, méthodes statiques, constantes, interfaces et attributes PHP. Une constante qui désigne un cas reste un alias.

Cette troisième variante indépendante de Status ajoute le contrat local Labeled et son libellé :

interface Labeled
{
    public function label(): string;
}

enum Status: string implements Labeled
{
    case Draft = 'draft';
    case Published = 'published';

    public const Default = self::Draft;

    public function label(): string
    {
        return match ($this) {
            self::Draft => 'Brouillon',
            self::Published => 'Publié',
        };
    }
}

echo Status::Default->label(), "\n";
var_dump(Status::Default === Status::Draft);
echo count(Status::cases()), "\n";

La sortie est Brouillon, bool(true), puis 2. Chaque cas est un singleton : un seul object représente ce cas, et === vérifie cette identité. L'alias n'a ajouté aucune possibilité à cases().

Cette stabilité interdit d'y stocker l'état propre de chaque article : une enum ne déclare ni property d'instance ni property statique, ni constructor, et n'utilise pas extends. new Status() lève une Error « Cannot instantiate enum ». Ses propriétés natives name et value restent en lecture seule ; tenter de les modifier directement ou par référence lève aussi une Error. Pour changer l'état d'un article, l'application lui associe un autre cas ; elle ne modifie pas le cas partagé.

🌍 In Real Life

La situation : tous les dossiers peuvent désigner le même état « brouillon » ; modifier l'état d'un dossier ne doit pas modifier la définition de « brouillon » pour les autres.

L’équivalent dans Symfony : choix commun → singleton du cas ; état du dossier → référence au cas dans l'objet article ; libellé commun → méthode de l'enum.

Retour à la réalité technique : une enum ne porte pas les propriétés variables de chaque article. Un alias ne crée aucun cas supplémentaire ; changer d'état associe un autre cas, sans muter le cas partagé.

🧠 Comment le mémoriser : « Changer le choix, pas le cas. » Image mentale : dossiers pointant vers des étiquettes fixes. Question-réflexe : cette donnée appartient-elle au choix commun ou à cet article ?

⚠️ À ne pas confondre : identité d'un cas et service partagé dans un container.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Sans cas correspondant, from() lève, tryFrom() renvoie null.

    Sans cas correspondant, from() lève, tryFrom() renvoie null. Une valeur valide produit le cas avec les deux méthodes. Un type incompatible peut lever TypeError : tryFrom() n'est pas une validation universelle de toute donnée reçue. Dans l'import, missing est bien une string mais ne fait pas partie des choix. Un tableau à sa place n'a même pas le type attendu : le message de rejet et le point de validation peuvent donc différer.

  • Voir l’explication : Redéfinir from() ou tryFrom() sur une enum adossée est une erreur fatale.

    Redéfinir from() ou tryFrom() sur une enum adossée est une erreur fatale. Ces methods sont fournies par l'engine. Pour une règle de normalisation propre à l'import, prépare l'entrée dans un code distinct ou choisis une autre méthode ; ne tente pas de remplacer cette API native.

  • Voir l’explication : cases() sur une enum adossée renvoie les cas, pas les valeurs.

    cases() sur une enum adossée renvoie les cas, pas les valeurs. Pour les valeurs : array_column(Suit::cases(), 'value'). Une liste de choix pour l'éditeur et les codes transportés par son formulaire sont donc deux représentations à distinguer.

  • Voir l’explication : Une enum pure n'a pas de ->value.

    Une enum pure n'a pas de ->value. Y accéder ne lève rien : PHP émet un avertissement « Undefined property » et rend null dans le comportement PHP ordinaire. Un gestionnaire d'erreurs configuré peut modifier le traitement de ce warning ; cela ne crée toujours pas de valeur adossée.

Choisir une politique de conversion pour l'état d'article

  • Valeur externe, repli métier et invariant interne

    Pour un état reçu dans un formulaire ou un import, valide d'abord le type attendu, puis utilise tryFrom() si l'absence de cas est un résultat à présenter proprement. Une valeur de repli doit être une décision métier explicite ; elle n'est pas obligatoire. Pour une donnée interne dont le contrat garantit une valeur connue, par exemple un code conservé dans votre propre stockage, from() permet de faire apparaître une violation de cet invariant plutôt que de la masquer.

  • Voir l’explication : HttpKernel appelle ArgumentResolver, qui consulte les value resolvers

    Dans une branche HTTP adaptée, un argument de controller typé par une backed enum peut être résolu à partir d'un paramètre de route : HttpKernel appelle ArgumentResolver, qui consulte les value resolvers, dont BackedEnumValueResolver. Ce lecteur utilise les valeurs de Request::attributes et les cas déjà déclarés ; il ne crée pas un nouveau cas à partir d'une string inconnue. Ce mécanisme ne signifie pas que tout champ JSON ou query parameter est automatiquement converti.

  • Identifiant d’article contre état applicatif

    Le parcours principal garde id=42 pour choisir l'article dans ArticleCatalog. Son éventuel état Published est une autre valeur applicative : ni l'enum ni son libellé n'effectuent la lecture du catalogue, la publication ou le contrôle d'accès.

🌍 In Real Life

La situation : un code reçu doit désigner une position existante du sélecteur ; un code inconnu ne fabrique pas une position supplémentaire.

L’équivalent dans Symfony : recherche du code → from/tryFrom ; absence → ValueError ou null ; choix de rejeter ou de replier → politique applicative.

Retour à la réalité technique : le type doit aussi convenir, sinon TypeError reste possible. Dans la branche de route configurée, HttpKernel appelle ArgumentResolver et ses value resolvers ; BackedEnumValueResolver lit les attributs de Request, pas automatiquement tout JSON ou query.

🧠 Comment le mémoriser : « Reconnaître, puis décider. » Image mentale : code inconnu arrêté devant le sélecteur. Question-réflexe : une absence est-elle attendue ou viole-t-elle un invariant ?

⚠️ À ne pas confondre : conversion d'argument, publication de l'article et autorisation.

Application

À retenir en priorité
  1. Pour une valeur du type attendu sans cas correspondant, from() lève ValueError ; tryFrom() renvoie null.
  2. tryFrom() permet de traiter explicitement l'absence de case.
  3. Une backed enum utilise int ou string.
  4. Chaque case possède une valeur unique.

Fiche express

À mémoriser

De la string importée au choix utilisé par l'article, retiens six repères :

  • Pure : des cas ; adossée : int ou string, unique et constante.
  • cases() → les cas ; name en lecture seule, et value également pour les seules enums adossées.
  • Valeur sans cas : from() lève \ValueError, tryFrom() rend null ; valeur correspondante : les deux rendent le cas.
  • Methods, constantes (alias), interfaces : oui.
  • État, constructor, extends, new : non.
  • UnitEnum pour toutes, BackedEnum en plus pour les adossées.

Moyen mnémotechnique : « Un code reconnu retrouve un cas ; un code inconnu exige une décision. » tryFrom() tolère l'absence de cas, pas un type d'entrée arbitraire.
