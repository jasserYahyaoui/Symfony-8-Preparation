Objectif

Savoir quelles commands sont déjà là, et laquelle sert à quoi. Aucune liste à apprendre : list la donne.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La liste est le point d'entrée de découverte.
  2. help détaille ensuite une command.

Aucune liste à apprendre : bin/console sans argument exécute list, et help détaille une command. À l'examen, il faut reconnaître les familles — debug:* inspecte, cache:* vide, lint:* valide —, savoir abréger un nom, et se rappeler qu'une command vise dev par défaut.

Le schéma

À retenir en priorité
  1. Le préfixe décrit une famille d'usage.
  2. Choisir la famille selon le diagnostic.

L'exemple : vider le cache de production

▣ Exemple concret

À retenir en priorité
  1. L'environment doit être explicite.
  2. Le cache de dev n'est pas celui de prod.
php bin/console cache:clear              # vide le cache de dev
php bin/console cache:clear --env=prod   # celui de prod
php bin/console d:r                      # debug:router, abrégé

Les familles

○ À comprendre

À retenir en priorité
  1. La liste dépend de l'application.
  2. Toutes les commands ne sont pas universelles.

C'est quoi ?

Les commandes intégrées exposent les outils disponibles dans l'application. Le préfixe avant : indique une famille d'usage, pas la garantie que tous ses membres sont installés.

À quoi ça sert ?

Choisir une famille à partir du problème évite des commandes mutantes inutiles : une route introuvable se diagnostique avant de vider tous les caches.

Où dans Symfony ?

  • debug:* inspecte routes, services, événements ou configuration résolue.
  • lint:* vérifie la validité de fichiers ou définitions ; ce n'est pas une preuve du comportement métier.
  • cache:* vide, préchauffe ou gère des caches selon la commande.
  • secrets:* gère le coffre de secrets ; ne pas exposer ses données dans un exemple ou un journal.
  • make:* génère du code si MakerBundle est installé ; ce n'est pas une famille universelle de Console seul.

Comment, étape par étape ?

  1. Appeler list pour voir ce que l'application offre réellement.
  2. Lire l'aide de la commande pertinente.
  3. Choisir explicitement l'environment pour un diagnostic ou une opération qui en dépend.
  4. Lire le résultat et le code de sortie. Une syntaxe valide ne prouve ni bon ordre de règles ni bonne autorisation.

Exemple concret en shell

php bin/console list debug
php bin/console help debug:router
php bin/console debug:router --env=prod

Dans une application dotée du routage, la dernière ligne inspecte les routes de production. Elle ne modifie pas leur définition. Les noms peuvent être abrégés segment par segment seulement tant qu'ils restent non ambigus. Contre-exemple : figer deb:c dans un script ; ce préfixe peut désigner debug:config ou debug:container. Correction : écrire le nom complet dans les automatisations. Même une abréviation aujourd'hui unique peut devenir ambiguë quand un package ajoute une commande.

Les familles

Famille Ce qu'elle fait
debug:* inspecter : container, routes, events, Twig, configuration
cache:* vider, préchauffer, gérer les pools
lint:* valider une syntaxe — YAML, Twig, XLIFF, container
secrets:* gérer le coffre de secrets
make:* générer du code, si MakerBundle est installé
  • La liste dépend des components installés : sans le component Translation, pas de lint:xliff.
  • Commands sans namespace : about, completion, help, list, _complete.
  • Les debug:* répondent à « qu'est-ce que Symfony a réellement compris de ma configuration ? » : elles lisent le container compilé.

L'abréviation

À retenir en priorité
  1. Chaque segment peut être abrégé.
  2. L'unicité reste obligatoire.

Un nom s'abrège segment par segment tant qu'il reste non ambigu :

Saisie Résultat
c:c cache:clear
d:r debug:router
l:y lint:yaml
deb:c « Command "deb:c" is ambiguous. » — debug:config, debug:container

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Vérifier APP_ENV ou --env.
  2. Ne pas déduire la cible du serveur utilisé.
  • Voir l’explication : Une command vise dev sans APP_ENV ni --env.

    Une command vise dev sans APP_ENV ni --env. Un cache:clear lancé sans rien ne vide pas le cache de prod.

  • Voir l’explication : debug:* lit le container compilé, pas les files de configuration.

    debug:* lit le container compilé, pas les files de configuration. C'est précisément son intérêt : il montre ce que Symfony a retenu, pas ce qu'on croit avoir écrit.

  • Commande Console par défaut

    bin/console sans argument exécute list.

  • Voir l’explication : Le préfixe n'indique pas le bundle d'origine

    Le préfixe n'indique pas le bundle d'origine : il nomme le domain.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Les imports et defaults sont pris en compte.
  2. Le résultat révèle la configuration réellement retenue.

Si tu dois retenir seulement 5 choses :

  • bin/console seul → list ; help détaille une command.
  • debug:* inspecte, cache:* vide, lint:* valide.
  • La liste dépend des components installés.
  • Abréviation par segment, si non ambiguë.
  • dev par défaut ; --env / -e, --no-debug.

Moyen mnémotechnique : « Lister, inspecter, vider, valider ».
