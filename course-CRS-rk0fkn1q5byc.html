Objectif

La commande d'import a une interface, mais avant d'ajouter un outil de diagnostic, regardons ceux déjà enregistrés. Si GET /blog/42 ne trouve plus sa route après un déploiement, devons-nous inspecter les routes, valider un fichier ou vider un cache ? Ce cours apprend à choisir l'action et son environnement, plutôt qu'à lancer une commande connue au hasard.

L'essentiel

À comprendre

À retenir en priorité
  1. La liste est le point d'entrée de découverte.
  2. help détaille ensuite une command.

Le catalogue est l'ensemble des commandes accessibles dans l'application installée ; ce n'est pas une liste universelle fournie par PHP. Commencer par list permet de voir ce qui existe ; help explique ensuite les arguments et options d'une commande précise. Les préfixes regroupent des usages : debug:* inspecte, cache:* gère les caches et lint:* valide.

Il faut aussi identifier l'environnement visé. Dans l'entrée Symfony habituelle, sans configuration contraire, APP_ENV vaut dev par défaut ; --env=prod sélectionne explicitement la production. Le nom de la commande ne choisit pas cet environnement à votre place.

L'environnement et le mode debug sont deux réglages distincts : --env=prod choisit l'environnement, --no-debug désactive le debug. Cette seconde option, seule, ne transforme pas dev en prod. Les options d'environnement appartiennent à l'intégration Symfony, pas à l'obligation d'utiliser le composant Console autonome.

Le schéma

À retenir en priorité
  1. Le préfixe décrit une famille d'usage.
  2. Choisir la famille selon le diagnostic.

Commencer par la découverte évite de confondre « outil absent » et « outil mal appelé ». list debug filtre les commandes d'inspection ; demander l'aide d'une commande présente permet d'en lire le contrat sans exécuter son traitement :

Le nom choisi passe ensuite par Application::find(). Un nom ou alias exact enregistré est reconnu avant la recherche d'abréviation. Pour un préfixe abrégé, le catalogue détermine les candidats :

Bleu : opérations ; cylindre : catalogue ; losange ambre : décision ; formes vertes : résultats. L'abréviation dépend des commandes et alias installés. L'ajout d'une commande peut rendre une ancienne abréviation ambiguë : préférer les noms complets dans les scripts automatisés.

L'exemple : vider le cache de production

Exemple concret

À retenir en priorité
  1. L'environment doit être explicite.
  2. Le cache de dev n'est pas celui de prod.

Le déploiement nécessite ici un renouvellement du cache applicatif de production. Cette opération modifie l'état de l'application : ne pas la confondre avec une inspection en lecture seule. Les variantes suivantes illustrent les cibles ; il n'est pas nécessaire de les exécuter toutes :

php bin/console cache:clear              # dev si APP_ENV n'est pas redéfini
php bin/console cache:clear --env=prod --no-debug
php bin/console d:r                      # debug:router si cette abréviation est unique

Pour la deuxième commande, si elle réussit, le message final indique :

Cache for the "prod" environment (debug=false) was successfully cleared.

Le bloc de style ajoute sa présentation autour de ce texte. La première commande annoncerait dev dans les conditions indiquées ; la troisième affiche les routes et leurs chemins, dont blog_show si elle est enregistrée.

En interne, CacheClearCommand obtient du kernel l'environnement, le mode debug et les répertoires concernés, puis appelle les cache clearers et organise le préchauffage selon les options. Elle ne purge pas magiquement toutes les copies HTTP de /blog/42 dans les navigateurs ou les caches intermédiaires. Le cache HTTP et les pools de cache applicatif ont leurs propres règles d'invalidation.

Les familles

À retenir en priorité
  1. La liste dépend de l'application.
  2. Toutes les commands ne sont pas universelles.

🌍 In Real Life

La situation : pour diagnostiquer le blog, l'équipe ouvre une mallette contenant une loupe, un vérificateur de formulaires et des outils d'entretien.

L’équivalent dans Symfony : loupe → debug:* ; vérification ciblée → lint:* ; entretien des caches → cache:*.

Retour à la réalité technique : les commandes disponibles dépendent des composants et de l'intégration. Inspecter une route n'est pas modifier le cache ; réussir un lint ne prouve pas le comportement métier de /blog/42.

🧠 Comment le mémoriser : « Inspecter avant d'intervenir. » Image mentale : la loupe sortie avant la clé. Question-réflexe : cette commande observe-t-elle ou modifie-t-elle l'état ?

⚠️ À ne pas confondre : catalogue installé et liste universelle d'outils Symfony.

Le préfixe exprime une intention. Pour notre incident, nous inspectons d'abord la route et les services ; nous validons ensuite les fichiers suspects. Gérer les caches est une action différente :

Famille Ce qu'elle fait
debug:* inspecter : container, routes, events, Twig, configuration
cache:* vider, préchauffer, gérer les pools
lint:* valider des fichiers ou la configuration du conteneur, selon la commande
secrets:* gérer le coffre de secrets
make:* générer du code, si MakerBundle est installé
  • La liste dépend des components installés : sans le component Translation, pas de lint:xliff.
  • Commands sans namespace : about, completion, help, list, _complete.
  • Les debug:* répondent à « qu'est-ce que l'application a réellement enregistré ? » : services pour debug:container, routes pour debug:router, listeners pour debug:event-dispatcher, selon la commande.

Console seul fournit notamment help, list, completion et _complete ; about et les outils du framework proviennent de son intégration. make:* reste une possibilité conditionnelle, pas une dépendance ajoutée à ce parcours. De même, FrameworkBundle retire sa définition lint:xliff si la classe du composant Translation nécessaire n'est pas disponible.

Une route listée prouve son enregistrement, pas l'existence de l'article 42. Cette dernière reste la responsabilité du catalogue métier appelé par le contrôleur. Un diagnostic de configuration ne remplace pas un test de la requête.

L'abréviation

À retenir en priorité
  1. Chaque segment peut être abrégé.
  2. L'unicité reste obligatoire.

🌍 In Real Life

La situation : au bureau du blog, « appeler Mar… » suffit avec une seule Marie ; l'arrivée de Marc rend la consigne ambiguë.

L’équivalent dans Symfony : début de nom → abréviation de segment ; annuaire actuel → catalogue Console ; deux candidats → ambiguïté.

Retour à la réalité technique : Console résout les abréviations selon les noms et alias présents. Elles ne sont pas des alias permanents. Les scripts gagnent à employer le nom complet.

🧠 Comment le mémoriser : « Court seulement si unique. » Image mentale : deux fiches sous « Mar ». Question-réflexe : une nouvelle commande peut-elle rendre ma saisie ambiguë ?

⚠️ À ne pas confondre : abréviation déduite et alias explicitement déclaré.

Pour une exploration manuelle, un nom s'abrège segment par segment tant qu'il désigne une commande sans ambiguïté. Le tableau suppose un catalogue où les trois premières abréviations sont uniques et où les deux candidats indiqués pour deb:c existent :

Saisie Résultat
c:c cache:clear
d:r debug:router
l:y lint:yaml
deb:c « Command "deb:c" is ambiguous. » — debug:config, debug:container

d:r ne signifie donc pas « alias permanent de debug:router ». Une nouvelle commande ou un nouvel alias peut changer la résolution sans modifier notre script. Dans un script de déploiement, écrire le nom complet rend l'intention stable et évite cette dépendance au catalogue.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Vérifier APP_ENV ou --env.
  2. Ne pas déduire la cible du serveur utilisé.
  • Voir l’explication : L'entrée Symfony habituelle utilise dev par défaut.

    L'entrée Symfony habituelle utilise dev par défaut. Il faut aussi exclure une valeur chargée depuis la configuration d'environnement ou un Runtime personnalisé avant de conclure que rien ne la redéfinit. Le nom de la machine « production » ne sélectionne aucun environnement.

  • Voir l’explication : Les commandes debug:* inspectent l'état effectif propre à leur domaine.

    Les commandes debug:* inspectent l'état effectif propre à leur domaine. Elles évitent de déduire une configuration active de la seule lecture d'un fichier qui pourrait être surchargé ailleurs.

  • Voir l’explication : bin/console sans argument exécute normalement list.

    bin/console sans argument exécute normalement list. C'est la commande par défaut de Application, configurable par une application personnalisée.

  • Voir l’explication : Le préfixe n'indique pas le bundle d'origine

    Le préfixe n'indique pas le bundle d'origine : il nomme le domain.

  • Voir l’explication : --no-debug ne signifie pas --env=prod.

    --no-debug ne signifie pas --env=prod. Le premier règle le debug, le second sélectionne l'environnement.

Fiche express

À mémoriser

À retenir en priorité
  1. Les imports et defaults sont pris en compte.
  2. Le résultat révèle la configuration réellement retenue.

Notre incident est désormais formulé : quel état inspecter, dans quel environnement, avant quelle action ? Cette démarche compte davantage que la mémorisation d'une longue liste :

Si tu dois retenir seulement 5 choses :

  • bin/console seul → list ; help détaille une command.
  • debug:* inspecte, cache:* gère les caches, lint:* valide.
  • La liste dépend des components installés.
  • Abréviation par segment, si non ambiguë.
  • dev par défaut dans l'entrée habituelle sans surcharge ; --env / -e sélectionne l'environnement, --no-debug le mode debug.

Moyen mnémotechnique : « Lister, inspecter, vider, valider ».

Les outils intégrés répondent au diagnostic, pas à l'import métier. Poursuivre avec Custom commands pour enregistrer app:blog:import et lui fournir ses dépendances.
