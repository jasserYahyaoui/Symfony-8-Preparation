Objectif

Rendre un form dans un template, du plus court au plus contrôlé, sans perdre de field en route — ni le token CSRF.

L'essentiel

À comprendre

À retenir en priorité
  1. form_widget() ne constitue pas toute la ligne.
  2. form_row() préserve les éléments associés au field.

Twig rend un form à trois grains : tout (form()), ligne par ligne (form_row()), ou pièce par pièce (form_label(), form_widget()…). Quel que soit le grain, form_end() rend les fields oubliés — le token CSRF compris —, sauf render_rest: false. Pour une même FormView, les rendus row et widget ne peuvent pas être répétés après leur achèvement ; cette restriction ne vise pas label, help ou errors.

Le schéma

À retenir en priorité
  1. Les fields cachés ne doivent pas être oubliés.
  2. render_rest: false exige de les rendre explicitement.

Bleu = étapes de rendu, ambre = décision. Les flèches représentent l'ordre dans le template, pas un appel de form_start() vers form_row().

L'exemple : `task_form`

Exemple concret

À retenir en priorité
  1. Choisir le niveau de contrôle nécessaire.
  2. Ne pas réécrire tous les éléments d'accessibilité sans besoin.

Après un GET d'inscription ou un POST refusé, le contrôleur prépare une FormView adaptée à l'état courant. Le petit formulaire de tâche ci-dessous isole son rendu ; il ne soumet ni ne valide les données depuis Twig. Créer la vue après le traitement permet d'y retrouver les valeurs et les erreurs issues de la soumission.

Un form avec un field texte task (doté d'une aide) et un field caché secret, qui illustre un enfant oublié. Ce champ arbitraire n'assure pas la protection CSRF ; le véritable champ CSRF est ajouté par l'extension dédiée :

{{ form_start(form) }}
    {{ form_row(form.task) }}
{{ form_end(form) }}

secret est rendu par form_end(), alors que le template ne le nomme jamais.

Les functions

Pour l'email d'inscription, la vue enfant porte nom HTML, valeur, libellé et erreurs. Le renderer transforme cette description avec un thème. form_errors(form) n'est donc pas un rapport récursif automatique : une erreur attachée à l'email doit être rendue à cet emplacement, sous réserve des règles de mapping et de remontée des erreurs configurées.

Function Ce qu'elle produit
form(form) le form entier
form_start(form) / form_end(form) le tag ouvrant / le tag fermant et les fields non rendus
form_row(form.champ) libellé + widget + aide + erreurs, dans son container
form_label(), form_widget(), form_help(), form_errors() une pièce seule
form_rest(form) tous les fields non encore rendus
  • form_row() relie la saisie à l'aide par aria-describedby ; form_widget() seul ne rend pas l'aide.
  • form_label(form.task, 'Titre') remplace le libellé.
  • form_errors(form) ne rend que les erreurs du form lui-même : une erreur sur task sort avec form_errors(form.task).
  • Les functions prennent la vue du field : form_row('task') lève une TypeError.
  • Pour écrire son propre HTML, les helpers field_* rendent des valeurs : field_name(form.task) donne task_form[task] ; field_value(), field_label(), field_help(), field_errors().

🌍 In Real Life

La situation : l'imprimeur reçoit une fiche préparée avec les cases, libellés, aides et annotations d'erreur. Il peut composer la fiche entière ou seulement une partie ; une note attachée à la case email ne devient pas automatiquement une note générale.

L’équivalent dans Symfony : les helpers form_* utilisent une FormView et les blocs du thème pour produire du HTML. form_errors() rend les erreurs attachées à la vue ciblée ; les helpers field_* exposent des valeurs pour un balisage personnalisé.

Retour à la réalité technique : passer le nom 'email' n'équivaut pas à passer form.email. Le rendu ne déclenche pas la validation ; crée la vue après le traitement afin d'y retrouver son état. Mapping et remontée des erreurs déterminent où celles-ci sont attachées. Le thème précise la composition HTML effective.

🧠 Comment le mémoriser : « Imprimer la fiche préparée, pas deviner son nom. » Image mentale : fiche email avec sa propre annotation d'erreur. Question-réflexe : quelle FormView et quelle partie ai-je réellement demandées ?

⚠️ À ne pas confondre : Form, FormView, nom du champ, valeurs field_* et HTML form_*.

Trois niveaux de contrôle

Commence par form_row() pour conserver libellé, aide et erreurs tout en organisant la page. Descendre au widget donne davantage de contrôle mais transfère au template la responsabilité de rendre les autres parties et leurs relations accessibles. Le choix graphique ne modifie pas les contraintes serveur du champ.

Besoin Rendu
un form standard, page d'administration {{ form(form) }}
une page publique : choisir l'ordre, grouper des lignes form_start(), des form_row(), form_end()
un balisage sur mesure autour d'un field form_label(), form_errors(), form_widget(…, {'attr': {…}})

🌍 In Real Life

La situation : on peut acheter une fiche entièrement composée, disposer des lignes préassemblées ou assembler soi-même chaque libellé et chaque case. Plus on descend dans le détail, plus on doit vérifier les pièces oubliées et leurs liens.

L’équivalent dans Symfony : form() compose l'ensemble ; form_row() permet d'ordonner des lignes complètes ; label, widget, help et errors permettent une composition fine. Cette dernière impose de maintenir les relations accessibles entre saisie, libellé, aide et erreurs.

Retour à la réalité technique : un widget seul n'apporte pas automatiquement toute la ligne. Les détails d'ARIA et de balisage dépendent aussi du thème utilisé ; vérifie le HTML réel. Ces choix de présentation ne modifient pas les contraintes Validator côté serveur.

🧠 Comment le mémoriser : « Plus de pièces libres, plus de liens à vérifier. » Image mentale : ligne assemblée face à quatre pièces séparées. Question-réflexe : mon contrôle fin conserve-t-il libellé, aide, erreurs et associations accessibles ?

⚠️ À ne pas confondre : personnalisation graphique, accessibilité et validation métier.

Le détail qui compte

Une mise en page manuelle peut omettre le champ CSRF sans modifier le formulaire côté serveur. Le POST suivant sera alors refusé dans le cas stateful standard. Le suivi rendered évite les doublons, mais marquer artificiellement le token comme rendu ne signifie pas que son HTML a été envoyé : vérifie la sortie réelle avant de masquer un enfant.

  • form_end() appelle form_rest(form), sauf si render_rest vaut false : un token non rendu manuellement est alors omis. Dans le cas stateful standard avec protection active, son absence invalide le form.
  • FormRenderer retient ce qui a été rendu : form_rest(form) puis form_end(form) ne rendent le field caché qu'une fois.
  • {% do form.secret.setRendered() %} écarte volontairement un field.
  • form_row(form.task) puis form_widget(form.task) : BadMethodCallException, « Field "task" has already been rendered… ». Pour réafficher un rendu, le stocker dans une variable.

🌍 In Real Life

La situation : avant de fermer une enveloppe, l'agent ajoute les pièces non encore cochées sur sa liste. Cocher une pièce sans l'avoir mise dedans trompe seulement la liste ; cela ne complète pas l'enveloppe.

L’équivalent dans Symfony : form_end() complète normalement les enfants non rendus via form_rest(). Le suivi de FormView évite de répéter row/widget ; setRendered() modifie ce suivi sans produire le HTML correspondant.

Retour à la réalité technique : render_rest: false transfère la responsabilité des omissions au template. Le champ CSRF n'existe que si la protection correspondante est configurée ; dans le cas stateful standard décrit, son absence compromet la soumission attendue. Un champ caché nommé secret n'est ni confidentiel ni une protection CSRF. Réutiliser une chaîne de HTML évite un second appel renderer, mais peut dupliquer des IDs et noms de saisie.

🧠 Comment le mémoriser : « Coché sur la liste ne veut pas dire présent dans l'enveloppe. » Image mentale : case cochée face à une pièce encore sur le bureau. Question-réflexe : ai-je vérifié le HTML réellement produit, notamment les champs cachés nécessaires ?

⚠️ À ne pas confondre : état rendered, sortie effectivement envoyée, absence visuelle et protection CSRF.

L'imprimeur vérifie les petites lignes oubliées avant de fermer le document. form_rest(), appelé par défaut par form_end(), joue ce rôle pour les fields non rendus, notamment cachés.

Action, method, attributes

À retenir en priorité
  1. Le HTML utilise POST pour ce cas.
  2. Le serveur doit activer l'interprétation du parameter _method.

Les variables de rendu changent le HTML que le navigateur soumettra, pas rétroactivement les options du Form qui attend cette soumission. Garde cohérents route cible, méthode configurée et méthode effective. novalidate permet de tester les erreurs serveur sans contrôle HTML5 ; il ne désactive ni Validator ni la protection CSRF.

{{ form_start(form, {'action': path('cible'), 'method': 'GET'}) }}
{{ form_start(form, {'attr': {'novalidate': 'novalidate'}}) }}
  • form() accepte les mêmes variables : son block appelle form_start().
  • Une method PUT : le tag porte method="post" et un field caché _method valant PUT, lu seulement si framework.http_method_override vaut true — false par défaut en 8.0.
  • novalidate désactive la validation HTML5 du navigateur.

🌍 In Real Life

La situation : l'enveloppe indique une destination et un mode de dépôt. Changer cette inscription ne reconfigure pas le guichet qui attend le dossier ; joindre une instruction « traiter comme PUT » n'a d'effet que si le guichet accepte cette convention.

L’équivalent dans Symfony : les variables de form_start() modifient le HTML action/method/attr. Pour PUT dans un formulaire HTML, le navigateur envoie POST avec _method, que Request peut interpréter selon la configuration d'override autorisée.

Retour à la réalité technique : garde cohérents route, méthode du Form et méthode effective. L'activation de l'override de champ n'annule pas une éventuelle liste de méthodes autorisées ; la méthode réelle reste POST. novalidate coupe le contrôle HTML5 du navigateur, pas Validator ni CSRF. Ces attributs HTML ne sont ni les attributs de Request ni les attributs PHP.

🧠 Comment le mémoriser : « Inscription sur l'enveloppe et règles du guichet doivent s'accorder. » Image mentale : enveloppe POST avec consigne PUT devant un guichet configuré. Question-réflexe : qu'envoie le navigateur et qu'attendent réellement route et Form ?

⚠️ À ne pas confondre : méthode transportée, méthode effective, options Form et attributs de rendu.

Pièges d'examen

Piège à éviter

  • Voir l’explication : form_end() rend aussi ce qui n'a pas été rendu

    form_end() rend aussi ce qui n'a pas été rendu, token CSRF compris.

  • Voir l’explication : Répéter row ou widget sur une vue déjà rendue

    Répéter row ou widget sur une vue déjà rendue lève une exception ; relire son libellé ou ses erreurs est possible.

  • Voir l’explication : form() règle aussi action et method

    form() règle aussi action et method, par le form_start() de son block.

  • Passer le champ aux fonctions de rendu

    Les functions de rendu prennent le field, pas son nom.

  • Voir l’explication : Une method PUT n'est pas envoyée en PUT

    Une method PUT n'est pas envoyée en PUT : le tag porte method="post" et un field caché _method, ignoré tant que http_method_override vaut false.

Application

À retenir en priorité
  1. Le HTML utilise POST pour ce cas.
  2. Le serveur doit activer l'interprétation du parameter _method.
  3. Les fields cachés ne doivent pas être oubliés.
  4. render_rest: false exige de les rendre explicitement.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • form() tout ; form_row() un field complet ; form_widget() la saisie seule.
  • form_end() rend les fields oubliés, token compris — sauf render_rest: false.
  • row / widget : une fois par vue ; sinon BadMethodCallException.
  • Les functions prennent form.champ, jamais 'champ'.
  • form_start() / form() : action, method, attr.
  • PUT : method="post" + _method, lu avec http_method_override.
  • form_errors(form) : erreurs du form seul ; field_* : des valeurs sans HTML.

Moyen mnémotechnique : « Ouvrir, ranger, fermer — la closure ramasse le reste ».
