Objectif

Rendre un form dans un template, du plus court au plus contrôlé, sans perdre de field en route — ni le token CSRF.

L'essentiel

À comprendre

À retenir en priorité
  1. form_widget() ne constitue pas toute la ligne.
  2. form_row() préserve les éléments associés au field.

Twig rend un form à trois grains : tout (form()), ligne par ligne (form_row()), ou pièce par pièce (form_label(), form_widget()…). Quel que soit le grain, form_end() rend les fields oubliés — le token CSRF compris —, et un field ne se rend qu'une fois.

Le schéma

À retenir en priorité
  1. Les fields cachés ne doivent pas être oubliés.
  2. render_rest: false exige de les rendre explicitement.

L'exemple : `task_form`

Exemple concret

À retenir en priorité
  1. Choisir le niveau de contrôle nécessaire.
  2. Ne pas réécrire tous les éléments d'accessibilité sans besoin.

Un form avec un field texte task (doté d'une aide) et un field caché secret, qui joue le rôle du token :

{{ form_start(form) }}
    {{ form_row(form.task) }}
{{ form_end(form) }}

secret est rendu par form_end(), alors que le template ne le nomme jamais.

Les functions

À comprendre

C'est quoi ?

Les fonctions Twig de formulaire rendent une FormView entière ou l'une de ses parties. Le widget est le contrôle de saisie ; la row est une ligne qui assemble le contrôle, son libellé, son aide et ses erreurs selon le theme. Une chaîne contenant le nom d'un champ n'est pas sa FormView.

À quoi ça sert ?

Choisir la bonne granularité évite de refaire manuellement les noms HTTP, identifiants, erreurs et liens d'accessibilité. form_widget seul est utile pour un agencement précis, mais ne rend pas automatiquement toutes les pièces que form_row aurait assemblées.

Où dans Symfony ?

form_start produit l'ouverture adaptée, notamment pour l'envoi de fichiers ; form_end ferme et rend normalement le reste. form_rest rend les champs pas encore affichés. form_errors(form) vise les erreurs du formulaire racine, pas toutes les erreurs de ses enfants regroupées automatiquement.

Comment, étape par étape ?

  1. Fournir une FormView au template, directement ou via la conversion effectuée par le raccourci de rendu du controller.
  2. Ouvrir le formulaire avec form_start.
  3. Rendre les erreurs racines puis les champs choisis avec form_row.
  4. Fermer avec form_end en conservant les champs techniques non encore rendus, sauf gestion manuelle consciente de ces champs.

Exemple concret Twig

Le contexte contient la vue form, avec un champ email :

{{ form_start(form) }}
    {{ form_errors(form) }}
    {{ form_row(form.email) }}
    <button type="submit">Enregistrer</button>
{{ form_end(form) }}

La ligne email reçoit ses erreurs propres ; les erreurs globales sont rendues séparément. Contre-exemple : écrire form_row('email') ou seulement form_errors(form) puis croire que les erreurs du champ sont affichées. Correction : passer form.email et rendre sa ligne ou ses pièces.

Les helpers field_name, field_value et apparentés fournissent des valeurs pour du HTML manuel ; ils ne sont pas un remplacement automatique de tous les attributs et associations accessibles produits par les widgets. Modifier la méthode affichée sans aligner la configuration de traitement peut empêcher la reconnaissance de la soumission.

Passage canonique conservé
Function Ce qu'elle produit
form(form) le form entier
form_start(form) / form_end(form) le tag ouvrant / le tag fermant et les fields non rendus
form_row(form.champ) libellé + widget + aide + erreurs, dans son container
form_label(), form_widget(), form_help(), form_errors() une pièce seule
form_rest(form) tous les fields non toujours rendus
  • form_row() relie la saisie à l'aide par aria-describedby ; form_widget() seul ne rend pas l'aide.
  • form_label(form.task, 'Titre') remplace le libellé.
  • form_errors(form) ne rend que les erreurs du form lui-même : une erreur sur task sort avec form_errors(form.task).
  • Les functions prennent la vue du field : form_row('task') lève une TypeError.
  • Pour écrire son propre HTML, les helpers field_* rendent des valeurs : field_name(form.task) donne task_form[task] ; field_value(), field_label(), field_help(), field_errors().

Trois niveaux de contrôle

Besoin Rendu
un form standard, page d'administration {{ form(form) }}
une page publique : choisir l'ordre, grouper des lignes form_start(), des form_row(), form_end()
un balisage sur mesure autour d'un field form_label(), form_errors(), form_widget(…, {'attr': {…}})

Le détail qui compte

Piège à éviter

C'est quoi ?

Le rendu de formulaire transforme une FormView, description destinée à la présentation, en HTML. Le renderer mémorise quels champs ont été rendus. form_rest(form) rend les champs restants ; form_end(form) le fait également par défaut avant de fermer le formulaire.

À quoi ça sert ?

Cela permet de choisir l'ordre de quelques champs sans oublier les champs cachés. Le token CSRF, valeur de protection contre une soumission forgée lorsque cette protection est activée, fait partie de ces champs. La fonction de fermeture ne peut toutefois pas compenser un token déjà marqué rendu sans avoir été réellement affiché.

Où dans Symfony ?

Les fonctions proviennent de l'intégration Form/Twig, pas du moteur Twig seul. form(form) rend l'ensemble ; form_row() rend une ligne avec libellé, widget, aide et erreurs selon le thème ; form_widget() rend seulement la saisie. form_errors(form) vise les erreurs du formulaire racine, pas toutes les erreurs de chaque enfant.

Comment, étape par étape ?

  1. Traiter le formulaire côté PHP avant d'en créer la vue ou de le transmettre à AbstractController::render().
  2. Ouvrir avec form_start() ; cette fonction gère aussi l'encodage requis pour les fichiers.
  3. Rendre chaque champ visible une seule fois, en préférant form_row() si aucune présentation particulière n'est nécessaire.
  4. Fermer avec form_end() et son comportement par défaut, ou prendre explicitement en charge tous les champs restants.

Exemple concret Twig

Le contexte contient la vue form avec un champ name. Le formulaire est configuré côté serveur ; cet extrait ne définit pas ses contraintes.

{{ form_start(form) }}
    {{ form_errors(form) }}
    {{ form_row(form.name) }}
    <button type="submit">Enregistrer</button>
{{ form_end(form) }}

Le champ name n'est pas rendu une deuxième fois par form_end. Les enfants non encore affichés le sont, notamment le token s'il existe. Contre-exemple : mettre render_rest: false pour cacher un champ indésirable et oublier _token. Correction : corriger la construction ou le rendu du champ concerné, et conserver les champs cachés nécessaires. render_rest: false est utilisable seulement lorsque le rendu complet est réellement maîtrisé. novalidate désactive les contrôles du navigateur, jamais les contraintes serveur.

Passage canonique conservé
  • form_end() appelle form_rest(form), sauf si render_rest vaut false : les fields non rendus ne sont plus ajoutés automatiquement ; rendre explicitement le token CSRF s'il n'a pas déjà été rendu.
  • FormRenderer retient ce qui a été rendu : form_rest(form) puis form_end(form) ne rendent le field caché qu'une fois.
  • {% do form.secret.setRendered() %} écarte volontairement un field.
  • form_row(form.task) puis form_widget(form.task) : BadMethodCallException, « Field "task" has already been rendered… ». Pour réafficher un rendu, le stocker dans une variable.

L'imprimeur vérifie les petites lignes oubliées avant de fermer le document. form_rest(), appelé par défaut par form_end(), joue ce rôle pour les fields non rendus, notamment cachés.

Action, method, attributes

À comprendre

À retenir en priorité
  1. Le HTML utilise POST pour ce cas.
  2. Le serveur doit activer l'interprétation du parameter _method.

C'est quoi ?

Les variables action, method et attr de form_start configurent l'ouverture HTML rendue. action choisit la destination, method la méthode annoncée et attr les attributs du tag form. Modifier ce HTML ne reconfigure pas automatiquement le Form PHP qui reconnaîtra la soumission.

À quoi ça sert ?

Un formulaire de recherche peut envoyer un GET à une route précise ; une page peut également ajouter une classe CSS ou désactiver les contrôles HTML5 pour tester les erreurs serveur. Il faut conserver l'accord entre le rendu et le traitement.

Où dans Symfony ?

form_start gère les particularités HTTP du balisage. Pour PUT, PATCH ou DELETE, le navigateur envoie un POST accompagné du champ _method ; son interprétation dépend de http_method_override, désactivé par défaut en Symfony 8.0. novalidate concerne seulement le navigateur.

Comment, étape par étape ?

  1. Configurer côté PHP la méthode et la destination attendues.
  2. Rendre les valeurs correspondantes dans form_start, ou conserver celles de la vue.
  3. Ajouter uniquement les attributs HTML utiles.
  4. Pour une méthode substituée, vérifier aussi la configuration de Request et les routes.

Exemple concret Twig

La route search accepte GET et le Form PHP a été créé avec method GET ; la vue possède un champ query :

{{ form_start(form, {action: path('search'), method: 'GET', attr: {novalidate: 'novalidate'}}) }}
{{ form_row(form.query) }}
<button type="submit">Rechercher</button>
{{ form_end(form) }}

La saisie part vers la route search en GET. Contre-exemple : changer uniquement method dans Twig alors que le Form PHP attend POST ; handleRequest peut ne reconnaître aucune soumission. Correction : aligner les deux configurations. novalidate n'autorise jamais à ignorer isValid ni les contraintes serveur.

Passage canonique conservé

Action, method, attributes

{{ form_start(form, {'action': path('cible'), 'method': 'GET'}) }}
{{ form_start(form, {'attr': {'novalidate': 'novalidate'}}) }}
  • form() accepte les mêmes variables : son block appelle form_start().
  • Une method PUT : le tag porte method="post" et un field caché _method valant PUT, lu seulement si framework.http_method_override vaut true — false par défaut en 8.0.
  • novalidate désactive la validation HTML5 du navigateur.

Pièges d'examen

Piège à éviter

  • Voir l’explication : form_end() rend aussi ce qui n'a pas été rendu

    form_end() rend aussi ce qui n'a pas été rendu, token CSRF compris.

  • Voir l’explication : Un field déjà rendu ne se rend pas une seconde fois

    Un field déjà rendu ne se rend pas une seconde fois : exception.

  • Voir l’explication : form() règle aussi action et method

    form() règle aussi action et method, par le form_start() de son block.

  • Passer le champ aux fonctions de rendu

    Les functions de rendu prennent le field, pas son nom.

  • Voir l’explication : Une method PUT n'est pas envoyée en PUT

    Une method PUT n'est pas envoyée en PUT : le tag porte method="post" et un field caché _method, ignoré tant que http_method_override vaut false.

Application

À retenir en priorité
  1. Le HTML utilise POST pour ce cas.
  2. Le serveur doit activer l'interprétation du parameter _method.
  3. Les fields cachés ne doivent pas être oubliés.
  4. render_rest: false exige de les rendre explicitement.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • form() tout ; form_row() un field complet ; form_widget() la saisie seule.
  • form_end() rend les fields oubliés, token compris — sauf render_rest: false.
  • Un field se rend une fois ; sinon BadMethodCallException.
  • Les functions prennent form.champ, jamais 'champ'.
  • form_start() / form() : action, method, attr.
  • PUT : method="post" + _method, lu avec http_method_override.
  • form_errors(form) : erreurs du form seul ; field_* : des valeurs sans HTML.

Moyen mnémotechnique : « Ouvrir, ranger, fermer — la closure ramasse le reste ».
