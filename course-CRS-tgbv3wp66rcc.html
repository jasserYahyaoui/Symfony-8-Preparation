Objectif

Connaître les redirects que le routage déclenche de lui-même. Les redirects émis par un controller — redirect(), redirectToRoute() — et les options de RedirectController appartiennent au Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. UrlMatcher peut échouer sans rediriger.
  2. Le matcher du framework cible RedirectController.

Le routage redirige de lui-même dans deux cas : la barre oblique finale et le schéma exigé par schemes. Toujours en 301, toujours seulement en GET et HEAD — un POST sur la mauvaise forme reçoit un 404. Ce n'est pas le component seul qui redirige, mais le matcher de FrameworkBundle, qui route la Request vers RedirectController.

En un coup d'œil

À retenir en priorité
  1. Le redirect canonique n'est pas universel pour toutes les methods.
  2. La correction du slash ne doit pas être confondue avec un redirect applicatif explicite.

Bleu = coordination serveur ; vert = réponse construite. Le matcher ne fabrique pas lui-même la réponse et n'appelle pas le contrôleur. Les 404 décrits supposent qu'aucune autre route ne correspond. Un matching réussi ne garantit pas un 200 : le contrôleur décide ensuite du statut.

L'exemple

Exemple concret

À retenir en priorité
  1. schemes intervient dans les deux sens.
  2. La génération doit exprimer le changement de schéma.
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LoginController
{
    #[Route('/login/', name: 'login', schemes: ['https'])]
    public function login(): Response
    {
        return new Response('Connexion');
    }
}
// GET http://example.com/login  → un seul 301 vers https://example.com/login/
// POST http://example.com/login/ → 404

Ces résultats supposent le matcher redirectable du framework et aucune autre route correspondante ; une instance autonome de UrlMatcher ne promet pas ces redirections.

Qui redirige, et comment

Le UrlMatcher du component lève ResourceNotFoundException, qui devient un 404. Le redirect n'existe que si le matcher implémente RedirectableUrlMatcherInterface ; le component n'en fournit qu'une abstract class, l'implémentation concrète est RedirectableCompiledUrlMatcher, de FrameworkBundle. Sa method redirect() ne construit pas de Response : elle rend des attributes qui désignent RedirectController, avec permanent à true. D'où un 301, la query string recopiée sur la cible, et _route qui porte le nom de la route trouvée.

La barre oblique finale

À retenir en priorité
  1. La forme déclarée est la cible du redirect.
  2. Un POST ne doit pas perdre son body par cette correction automatique.
Path de la route /foo demandé /foo/ demandé
/foo route trouvée 301 vers /foo
/foo/ 301 vers /foo/ route trouvée

Le redirect va vers la forme déclarée : la Request doit être en GET ou HEAD, la route candidate doit être compatible avec cette method, et la racine / n'est pas concernée. Une route limitée à HEAD peut donc canonicaliser une Request HEAD, dans les deux sens /foo ↔ /foo/ ; accepter GET n'est pas une condition universelle. Un POST vers /foo pour une route /foo/ reçoit un 404 : RFC 9110 (15.4.2) permet de rejouer en GET un POST redirigé en 301, et le body serait perdu.

Le redirect passe avant une route générique : avec /foo/ puis /{name}, GET /foo est redirigé vers /foo/ (test testFallbackPage).

Un avis de réexpédition corrige la forme d'adresse pour GET ou HEAD, mais ne doit pas changer silencieusement le traitement d'un POST. Dans le cas du slash non correspondant décrit ici, retenir 404, pas le 405 proposé par l'analogie source2.

Repère — En un coup d'œil : No. This canonicalisation is restricted to GET and HEAD under the matching conditions. Le redirect canonique n'est pas universel pour toutes les methods. La correction du slash ne doit pas être confondue avec un redirect applicatif explicite.

Le schéma

schemes: ['https'] agit dans les deux sens.

À la génération, l'URL utilise HTTPS : path('login') produit le path absolu /login/ si la Request est déjà en HTTPS, mais https://example.com/login/ si elle est en HTTP.

À l'appariement, un GET en HTTP est redirigé en 301 vers HTTPS — pas un POST, qui reçoit un 404 ; la documentation omet cette restriction. Avec plusieurs schémas, aucun redirect si l'un correspond, sinon vers le premier. Barre finale et schéma faux sont corrigés par un seul redirect. schemes s'impose aussi à un import ; derrière un proxy TLS mal configuré, il produit une loop de redirect.

Complément sur les schémas HTTP et HTTPS

C'est quoi ?

schemes restreint les schémas admis par une route, généralement HTTP ou HTTPS. Cette restriction participe à l'appariement entrant et à la génération sortante. Demander un path ne garantit donc pas toujours une chaîne sans schéma ni hôte.

À quoi ça sert ?

Une adresse qui doit être utilisée en HTTPS doit aussi être générée ainsi depuis une page en HTTP. Côté entrée, l'intégration de routage redirigeable peut corriger certaines requêtes, mais ce mécanisme ne doit pas servir de garantie de réémission d'une opération POST.

Où dans Symfony ?

Le component Routing porte la restriction. Dans le matching redirigeable utilisé par FrameworkBundle, une requête GET ou HEAD sur un mauvais schéma peut recevoir une redirection 301 ; un POST sur ce seul candidat ne bénéficie pas de cette correction et aboutit à l'absence de correspondance, normalement une 404. Un UrlMatcher autonome ordinaire ne doit pas être présenté comme produisant cette redirection HTTP lui-même.

Comment, étape par étape ?

  1. Déclarer les schémas autorisés sur la route ou l'import concerné.
  2. Fournir au router le schéma extérieur réellement utilisé ; derrière un proxy terminant TLS, une mauvaise information peut produire une boucle.
  3. Générer les liens et destinations de soumission dans le bon schéma dès le départ.
  4. Tester génération et requêtes entrantes séparément, avec GET et POST. Avec plusieurs schémas, une correspondance existante ne redirige pas ; sinon la correction choisit le premier schéma prévu. La correction de barre finale et de schéma peut être combinée en une redirection.

Depuis une route

À comprendre

À retenir en priorité
  1. Les defaults configurent la destination.
  2. Une action applicative n'est pas nécessaire pour ce déplacement.

C'est quoi ?

Une route peut choisir RedirectController comme traitement. Le matching reconnaît l'ancienne adresse ; le controller construit ensuite une Response de redirection à partir des defaults. Ce n'est pas le mécanisme de correction automatique d'une barre finale.

À quoi ça sert ?

Une migration simple d'URL peut être déclarée sans classe applicative. La configuration reste explicite et testable : adresse d'entrée, destination et caractère temporaire ou permanent.

Où dans Symfony ?

RedirectController appartient à FrameworkBundle. Le mode route génère une destination nommée ; le mode path vise une adresse définie. Les modes sont exclusifs. Une logique métier, une autorisation ou une destination calculée complexe justifie un traitement applicatif plutôt qu'une multiplication de defaults.

Comment, étape par étape ?

  1. Déclarer l'ancien path.
  2. Désigner le controller interne.
  3. Fournir la destination de confiance et le statut souhaité via ses options.
  4. Vérifier Location et le statut sans confondre réponse de redirection et exécution de la cible.

Exemple concret YAML

old_guide:
    path: /old-guide
    methods: [GET]
    controller: Symfony\Bundle\FrameworkBundle\Controller\RedirectController
    defaults:
        path: /guide
        permanent: true

GET /old-guide reçoit une redirection 301 vers /guide. Le navigateur doit ensuite la suivre pour consulter le contenu. Contre-exemple : choisir permanent true pour une destination expérimentale puis supposer que tous les clients oublieront immédiatement cette décision. Correction : employer une redirection temporaire pendant la période où la destination peut changer. Ne pas prendre path librement dans une donnée utilisateur : la configuration doit conserver une destination maîtrisée.

Passage canonique conservé

Une route peut déléguer à RedirectController pour un simple déplacement d'URL, sans écrire de controller.

Repère — Qui redirige, et comment : No. FrameworkBundle's redirectable matcher supplies that behaviour. UrlMatcher peut échouer sans rediriger. Le matcher du framework cible RedirectController.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Ni barre finale ni schéma ne redirigent un POST.

    Ni barre finale ni schéma ne redirigent un POST. Les deux mécanismes sont réservés à GET et HEAD ; un POST qui ne correspond qu'à une autre forme d'URL reçoit un 404.

  • Voir l’explication : Le schéma agit à l'appariement et à la génération.

    Le schéma agit à l'appariement et à la génération. Une Request dans le mauvais schéma est redirigée ; et l'URL générée devient absolue dès que le schéma courant diffère, alors qu'elle serait restée un path sans host (ABSOLUTE_PATH, pas RELATIVE_PATH).

  • Voir l’explication : Le matcher non redirigeable ne redirige pas.

    Le matcher non redirigeable ne redirige pas. Son UrlMatcher lève une exception de routage, traduite en 404 par l'intégration HTTP ; c'est le matcher de FrameworkBundle qui sait rediriger.

  • Voir l’explication : Aucun controller applicatif n'intervient.

    Aucun controller applicatif n'intervient. Le matcher route la Request vers RedirectController ; le 301 conserve la query string.

Application

  3. schemes intervient dans les deux sens.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Le component ne redirige pas ; RedirectableCompiledUrlMatcher si.
  • Redirect de routage = 301, query string recopiée.
  • Barre finale : vers la forme déclarée, route compatible avec la Request GET ou HEAD ; une route HEAD-only convient à une Request HEAD.
  • Barre ou schéma : GET et HEAD seulement ; POST → 404.
  • schemes : URL absolue générée si le schéma change ; 1er schéma listé.
  • Barre et schéma faux → un seul redirect.

Moyen mnémotechnique : « Le routage ne redirige que ce qui se relit ».
