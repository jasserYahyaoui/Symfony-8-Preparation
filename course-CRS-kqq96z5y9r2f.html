Objectif

Déclarer une route en YAML et en attribute PHP, savoir choisir entre les deux, et maîtriser la conséquence la plus piégeuse de ce choix : l'ordre d'évaluation.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La première correspondance gagne.
  2. En YAML, réordonner les routes ; en attributes, utiliser priority.

Une route se déclare en attribute #[Route] ou en YAML : les deux formes sont équivalentes, mais pas leurs options. priority n'existe qu'en attribute ; une key YAML inconnue fait échouer le chargement. Et la règle qui pilote tout : les routes sont essayées dans l'ordre, et la première qui correspond gagne — jamais la plus spécifique.

Le schéma

À retenir en priorité
  1. Importer Route depuis Attribute.
  2. L'ancien namespace Annotation n'est plus disponible.

L'exemple : les deux formes

▣ Exemple concret

use Symfony\Component\Routing\Attribute\Route;

class BlogController
{
    #[Route('/blog/{page}', name: 'blog_list', requirements: ['page' => '[0-9]+'], methods: ['GET', 'HEAD'])]
    public function list(int $page = 1): Response {}
}
blog_list:
    path: /blog/{page}
    controller: App\Controller\BlogController::list
    requirements:
        page: '[0-9]+'
    defaults:
        page: 1
    methods: [GET, HEAD]

Les deux formes

○ À comprendre

À retenir en priorité
  1. La key YAML nomme la route.
  2. L'attribute utilise name et la method qui le porte.

C'est quoi ?

Une route peut être décrite près de l'action par un attribute PHP ou séparément dans un fichier YAML. Les deux déclarations peuvent produire le même nom, path, controller et restriction de méthode ; leurs syntaxes et options de chargement ne sont pas identiques.

À quoi ça sert ?

Les attributes rapprochent traitement et adresse. YAML permet de centraliser le routage ou de désigner un controller fourni ailleurs. Choisir un format ne change pas le besoin de charger la déclaration dans la collection.

Où dans Symfony ?

L'attribute est Symfony\Component\Routing\Attribute\Route, pas l'ancien namespace Annotation. En YAML, la clé est le nom de route et controller est explicite. En attribute, name donne le nom et la méthode porteuse détermine le controller. priority est une option d'attribute, pas une clé de route YAML.

Comment, étape par étape ?

  1. Fixer le nom, le chemin, la méthode HTTP et l'action voulus.
  2. Les écrire dans le format choisi.
  3. Vérifier la découverte de la ressource par les loaders.
  4. Ne charger qu'une des deux déclarations équivalentes ci-dessous, puis contrôler debug:router.

Exemple concret PHP et YAML

Méthode de App\Controller\StatusController, déjà enregistré :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[\Symfony\Component\Routing\Attribute\Route('/status', name: 'status', methods: ['GET'])]
public function show(): \Symfony\Component\HttpFoundation\Response
{
    return new \Symfony\Component\HttpFoundation\Response('ok');
}

Alternative dans config/routes.yaml, pour la même méthode sans l'attribute :

status:
    path: /status
    controller: App\Controller\StatusController::show
    methods: [GET]

Contre-exemple : conserver les deux définitions sous le même nom et attendre deux routes indépendantes. Correction : choisir une source de déclaration ou des noms réellement distincts. Copier Annotation\Route d'un ancien exemple ne fournit pas l'attribute Symfony 8.0 : employer le namespace exact ci-dessus.

Passage canonique conservé

Les deux formes

Le nom de la route est la key YAML, ou l'argument name: de l'attribute. Le controller est explicite en YAML ; en attribute, il est déduit de la method qui porte l'attribute. path accepte un array indexé par locale : l'attribute produit alors une route par locale, blog_list.fr, blog_list.en…

Les jeux d'options diffèrent. L'attribute accepte seize arguments ; le loader YAML a sa propre liste, AVAILABLE_KEYS :

Besoin Attribute YAML
réordonner priority absent — on déplace la route dans le file
restreindre à un environment env un block when@prod: au premier niveau
déclarer un alias alias une entrée qui ne porte que alias (et deprecated)
désigner le controller déduit de la method controller

Une key hors liste lève une InvalidArgumentException qui énumère les keys admises ; controller avec defaults._controller, ou stateless avec defaults._stateless, lèvent aussi.

Le namespace de l'attribute

Symfony\Component\Routing\Attribute\Route est le seul correct. Symfony\Component\Routing\Annotation\Route, hérité des annotations, a été supprimé : l'importer échoue en Symfony 8.0.

Le piège : l'ordre d'évaluation

△ Piège à éviter

C'est quoi ?

L'ordre de routage est l'ordre dans lequel les candidats sont considérés. Lorsqu'une route générale et une route spécifique acceptent la même requête, la première correspondance l'emporte ; le matcher ne choisit pas automatiquement le chemin qui semble le plus précis à un humain.

À quoi ça sert ?

Une route /blog/{slug} accepte notamment le texte new. Sans ordre ou requirement approprié, elle peut intercepter /blog/new destiné à un formulaire de création. Le problème est un chevauchement de règles, pas une erreur dans la méthode du controller cible.

Où dans Symfony ?

En YAML, déplacer les déclarations règle l'ordre. L'attribute PHP Symfony\Component\Routing\Attribute\Route propose priority, les valeurs les plus élevées passant d'abord. Cette option n'est pas une clé de route YAML équivalente. Le namespace Annotation de l'ancien attribute n'est pas celui de Symfony 8.0.

Comment, étape par étape ?

  1. Lister les routes qui pourraient correspondre au même chemin.
  2. Placer les cas spécifiques avant le cas général, ou rendre les ensembles de valeurs disjoints.
  3. Pour les attributes, exprimer explicitement la priorité voulue lorsque l'ordre de découverte ne suffit pas.
  4. Contrôler l'ordre effectif avec debug:router, puis tester le chemin avec router:match.

Exemple concret YAML

Avec les deux méthodes de BlogController réellement enregistrées :

blog_new:
    path: /blog/new
    controller: App\Controller\BlogController::new

blog_show:
    path: /blog/{slug}
    controller: App\Controller\BlogController::show

/blog/new correspond à blog_new ; /blog/introduction à blog_show. Contre-exemple : inverser les deux routes sans restreindre slug. La route générale accepte new avant la route dédiée. Correction : conserver cet ordre, ou introduire une règle qui exclut réellement new du domaine de slug. En attributes, priority: 2 sur la route spécifique peut exprimer la précédence ; ce nombre ne change ni le nom de la route ni son URL.

Le piège : l'ordre d'évaluation

Symfony essaie les routes dans l'ordre, et la première qui correspond gagne. En YAML, cet ordre est celui du file : on déplace la route. En attributes, il dépend de la découverte des classes et des methods, qu'on ne contrôle pas : d'où priority.

class Example03cc6c71
{
    #[Route('/blog/list', name: 'blog_list', priority: 2)]
    public function list(): Response {}

    #[Route('/blog/{slug}', name: 'blog_show')]   // priority 0
    public function show(string $slug): Response {}
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

La priority la plus élevée passe en premier ; à égalité, l'ordre de déclaration départage. L'argument vaut null par défaut : la route hérite alors de la priority d'un #[Route] posé sur la class, à défaut de 0.

Le cahier de tri s'arrête au premier motif qui convient. Une règle générale placée avant une adresse précise peut absorber son courrier : le nom plus précis ne lui donne aucune priorité automatique.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : La première route qui correspond gagne, et les suivantes ne sont jamais essayées.

    La première route qui correspond gagne, et les suivantes ne sont jamais essayées. Une route générale placée avant une route spécifique masque définitivement la seconde.

  • Voir l’explication : La priority est une option d'attribute, pas de YAML.

    La priority est une option d'attribute, pas de YAML. En YAML on déplace une ligne ; écrire la key fait échouer le chargement.

  • Voir l’explication : Les deux formats n'ont pas le même jeu d'options.

    Les deux formats n'ont pas le même jeu d'options. L'environment et l'alias existent des deux côtés, mais sous deux formes différentes.

  • Voir l’explication : L'ancien namespace d'annotation n'existe plus.

    L'ancien namespace d'annotation n'existe plus. Un import hérité de l'ancien système d'annotations échoue en Symfony 8.0 — l'attribute vit désormais dans Attribute.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Import : Routing\Attribute\Route ; Annotation est supprimé.
  • Première route qui correspond gagne, jamais la plus spécifique.
  • priority : attribute seulement ; plus haute d'abord, égalité → ordre.
  • priority null → celle de la class, sinon 0.
  • YAML : when@prod: pour l'environment, entrée alias seul pour un alias.
  • Key YAML inconnue ou doublon de controller → InvalidArgumentException.

Moyen mnémotechnique : « Premier arrivé, premier servi ».
