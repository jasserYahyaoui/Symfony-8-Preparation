Objectif

Suivre le trajet complet d'une Request HTTP dans une application Symfony, depuis le front controller jusqu'à l'envoi de la Response, et savoir qui fait quoi à chaque étape.

L'essentiel

À comprendre

À retenir en priorité
  1. kernel.view tente de convertir un résultat non-Response.
  2. kernel.response intervient sur la Response obtenue.

Une Request entre, une Response sort : tout le cycle tient dans HttpKernelInterface::handle() pour la transformation, puis l'envoi séparé. Le kernel orchestre les events, appelle les resolvers et exécute le controller ; les listeners ajoutent notamment routage et conversion. Trois points tombent à l'examen : kernel.view est conditionnel, un court-circuit ne saute pas la fin du cycle, et kernel.finish_request a lieu même quand une exception remonte — à une condition.

Le cycle en schéma

À retenir en priorité
  1. Le cycle prend une branche différente selon le type du retour controller.
  2. kernel.response travaille ensuite sur la Response obtenue.

Bleu : étapes d'orchestration ; orange : conversion conditionnelle ; vert : émission et terminaison ; rouge : échec. Vue d'une requête principale dans le runner Runtime, sans exception des listeners. handle() ne fait pas lui-même l'envoi et une sous-requête n'entraîne pas automatiquement terminate().

L'exemple : une page de maintenance qui court-circuite

Exemple concret

À retenir en priorité
  1. Une Response posée sur RequestEvent court-circuite la résolution et l'exécution du controller.
  2. Le cycle traite la Response ; terminate relève ensuite du runner après émission.
#[AsEventListener(priority: 100)]
final class MaintenanceListener
{
    public function __invoke(RequestEvent $event): void
    {
        $event->setResponse(new Response('Maintenance', 503));
        // controller sauté ; response et finish_request restent traités
        // le runner appelle terminate après l'émission de la Response
    }
}

Le contrat

À comprendre

À retenir en priorité
  1. Le contrat relie Request à Response.
  2. MAIN_REQUEST vaut 1 et SUB_REQUEST vaut 2.

C'est quoi ?

HttpKernelInterface::handle() transforme une Request en Response. Ses arguments sont la demande, son type — principale ou sous-requête — et le choix de laisser le kernel prendre en charge les exceptions. Retourner une Response n'est pas l'envoyer sur le réseau.

À quoi ça sert ?

Le contrat permet de traiter une demande sans connaître tous les détails du kernel. Le type permet aux listeners de distinguer demande principale et traitement imbriqué. $catch permet notamment à un appelant de conserver la responsabilité des erreurs au lieu de demander leur conversion en réponse.

Où dans Symfony ?

MAIN_REQUEST vaut 1, SUB_REQUEST vaut 2. Les valeurs par défaut sont la demande principale et $catch = true. Une sous-requête utilise le même mécanisme de traitement ; les listeners doivent décider explicitement s'ils ne concernent que la principale.

Comment, étape par étape ?

  1. Passer l'objet Request au kernel.
  2. Indiquer principale ou sous-requête selon le contexte réel.
  3. Choisir la politique de capture.
  4. Recevoir une Response si le traitement aboutit, ou l'exception si elle n'a pas été prise en charge.

Exemple concret PHP

Cette fonction reçoit un kernel déjà assemblé et n'émet pas la réponse :

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\HttpKernelInterface;
function handleWithoutErrorPage(HttpKernelInterface $kernel, Request $request): Response
{
    return $kernel->handle($request, HttpKernelInterface::MAIN_REQUEST, false);
}

Une exception concernée par ce choix remonte à l'appelant au lieu de passer par kernel.exception. Contre-exemple : croire que $catch = true garantit toujours une page d'erreur : sans listener produisant une réponse, l'échec peut remonter. De plus, le HttpKernel autonome distingue les Error selon handleAllThrowables, désactivé par défaut dans son constructeur, contrairement à la configuration habituelle du framework. Correction : distinguer contrat, configuration concrète et listeners disponibles.

Passage canonique conservé
interface ExampleKernelContract
{
    public const MAIN_REQUEST = 1;
    public function handle(Request $request, int $type = self::MAIN_REQUEST, bool $catch = true): Response;
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

$type vaut MAIN_REQUEST (1) ou SUB_REQUEST (2) : même code, aux listeners de distinguer. $catch décide si une exception devient une Response ou remonte.

Repère — La pile de Requests, poussée et dépilée par handle() : handle() pops the RequestStack in a finally block. handle() empile la Request à l'entrée. Le finally restaure la pile même en cas d'exception.

Repère — La branche que le trajet nominal ne montre pas : No. The exception propagates instead; covered exception paths still finish the request. catch=false désactive la conversion par kernel.exception. Distinguer cette option du traitement des Error par handleAllThrowables.

Le trajet

  1. public/index.php, seul front controller, rend une function ; le component Runtime crée la Request, appelle handle(), envoie, puis terminate().
  2. Kernel::boot() enregistre les bundles et charge le container compilé.
  3. kernel.request, avant que le controller soit connu : le router y pose _controller dans les attributes. setResponse() y saute le controller, pas la suite.
  4. Le ControllerResolver rend un callable ; puis kernel.controller, qui peut le remplacer.
  5. Arguments résolus, puis kernel.controller_arguments, qui relit le controller et les arguments.
  6. Appel. kernel.view n'a lieu que si le retour n'est pas une Response.
  7. kernel.response lorsqu'une Response est obtenue, puis kernel.finish_request, qui restaure l'état global.
  8. Envoi, puis kernel.terminate dans le runner : le processus PHP reste occupé. La libération anticipée du client dépend du serveur ; ce hook n'est pas un substitut à une tâche asynchrone persistante.

Le cycle ressemble à un colis passant des points de contrôle : kernel.view emballe seulement un résultat qui n'est pas déjà une Response ; kernel.response inspecte la Response obtenue. Ce ne sont pas deux emballages systématiques.

Repère — Trois façons d'échouer, trois exceptions : After a non-Response controller result remains unconverted by kernel.view. Le retour est contrôlé après kernel.view. Un listener peut produire la Response manquante.

Repère — Le cycle en schéma : No. A Response skips kernel.view; a different result must be converted to a Response. Le cycle prend une branche différente selon le type du retour controller. kernel.response travaille ensuite sur la Response obtenue.

Repère de l’exemple : It short-circuits controller execution; response and finish-request processing still take place. Une Response posée sur RequestEvent court-circuite la résolution et l'exécution du controller. Le cycle traite la Response ; terminate relève ensuite du runner après émission.

La pile de Requests, poussée et dépilée par `handle()`

À retenir en priorité
  1. handle() empile la Request à l'entrée.
  2. Le finally restaure la pile même en cas d'exception.

handle() empile la Request dans le RequestStack à l'entrée et la dépile dans un finally, exception comprise : c'est ce qui fait marcher getCurrentRequest(). Pour une StreamedResponse, le callback est réenveloppé pour réempiler la Request le temps du flux — sans quoi il trouverait une pile vide, handle() étant terminé.

La branche que le trajet nominal ne montre pas

À retenir en priorité
  1. catch=false désactive la conversion par kernel.exception.
  2. Distinguer cette option du traitement des Error par handleAllThrowables.

Losanges orange : décisions ; bleu : events ; rouge : throwable entrant ou relancé. Ce second schéma suppose que les listeners de traitement d'erreur ne lèvent pas eux-mêmes une nouvelle exception. Le finally dépile la Request même sur la branche « relancée sans event ».

Avec $catch à true, kernel.exception est dispatché ; si un listener pose une Response, kernel.response puis kernel.finish_request ont lieu, sinon kernel.finish_request puis l'exception remonte. Avec $catch à false, pas de kernel.exception, mais kernel.finish_request avant de remonter. Il a donc lieu sur les trois paths — à une condition : une \Error n'entre dans ces branches que si handleAllThrowables est vrai. framework.handle_all_throwables le fait par défaut, le constructor d'HttpKernel non. Une TypeError levée dans le controller arrive après kernel.request, kernel.controller et kernel.controller_arguments ; ces notifications déjà faites ne sont pas annulées.

Trois façons d'échouer, trois exceptions

À retenir en priorité
  1. Le retour est contrôlé après kernel.view.
  2. Un listener peut produire la Response manquante.
Ce qui manque Ce qui est levé
Le resolver ne trouve aucun controller NotFoundHttpException — « the route is wrongly configured »
Le controller ne rend pas une Response, et aucun listener de kernel.view n'en pose une ControllerDoesNotReturnResponseException
La Request elle-même est malformée (RequestExceptionInterface) convertie en BadRequestHttpException avant la branche d'exception

La deuxième — « Did you forget to add a return statement somewhere in your controller? » — n'est levée qu'après kernel.view.

Pièges d'examen

Piège à éviter

Voir l’explication : conditionnel
  • kernel.view est conditionnel ; kernel.response suit une Response obtenue, pas une exception qui remonte sans Response.
  • kernel.terminate est après l'envoi, pas avant.
  • kernel.finish_request vient après kernel.response, pas avant.
  • kernel.request précède la résolution du controller : à ce moment, _controller peut être toujours absent.
  • Un court-circuit sur kernel.request saute le controller, pas kernel.response, kernel.finish_request ni kernel.terminate.
  • Un seul front controller, public/index.php — quelle que soit l'URL demandée.
  • kernel.finish_request a lieu même quand l'exception remonte, et même quand $catch vaut false — mais une \Error hors handle_all_throwables le saute.
  • kernel.controller_arguments peut remplacer le controller, pas seulement ses arguments.
  • MAIN_REQUEST vaut 1 et SUB_REQUEST 2 — pas 0 et 1.

Application

À retenir en priorité
  1. Le retour est contrôlé après kernel.view.
  2. Un listener peut produire la Response manquante.
  3. Le contrat relie Request à Response.
  4. MAIN_REQUEST vaut 1 et SUB_REQUEST vaut 2.

Fiche express

À mémoriser

Si tu dois retenir seulement 8 choses :

  • handle(Request, $type, $catch): Response ; MAIN_REQUEST = 1, SUB_REQUEST = 2.
  • Ordre : request → controller → controller_arguments → (appel) → [view] → response → finish_request → (envoi) → terminate.
  • kernel.view n'est dispatché que si le controller ne rend pas une Response.
  • Court-circuit sur kernel.request : response, finish_request, terminate ont lieu.
  • controller_arguments peut toujours remplacer le controller.
  • Pile : empilée à l'entrée, dépilée dans un finally.
  • finish_request sur les trois paths — sauf \Error hors handle_all_throwables.
  • Aucun controller → 404 ; pas de Response → ControllerDoesNotReturnResponseException.

Moyen mnémotechnique : « Une Request entre, une Response sort ».
