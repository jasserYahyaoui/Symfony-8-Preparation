Objectif

Le navigateur demande GET /blog/42. Notre application possède une route blog_show, un BlogController::show enregistré et un service ArticleCatalog qui fournit en mémoire l'article 42 sous forme d'ArticleView. Il reste à relier cette demande à une réponse : qui prépare l'application, choisit la méthode, fournit ses arguments et envoie le résultat ?

Suivons une requête principale dans Symfony 8.0, exécuté avec PHP 8.4. Nous partons de l'entrée Runtime HTTP standard, sans cache HTTP réutilisable ni interruption. Nous raccorderons ensuite maintenance, sous-requête et erreur à l'endroit où chacune change réellement le trajet.

L'essentiel

À comprendre

À retenir en priorité
  1. kernel.view tente de convertir un résultat non-Response.
  2. kernel.response intervient sur la Response obtenue.

Une Request représente la demande ; une Response contient le contenu, le statut et les headers à retourner. HttpFoundation fournit ces objects. HttpKernelInterface::handle() décrit leur transformation, pas l'envoi. App\Kernel prépare l'application et son conteneur ; le service concret HttpKernel orchestre ensuite le traitement HTTP.

Pour notre article, HttpKernel notifie des events, points d'extension auxquels des listeners enregistrés réagissent. Il demande séparément un callable au ControllerResolver, puis ses arguments à l'ArgumentResolver, avant de l'appeler. Le routage, la sélection du callable et la préparation des valeurs ne sont donc pas une seule opération.

Si l'action retourne directement une Response, kernel.view ne se produit pas. Si la maintenance répond avant l'action, celle-ci est sautée, mais la réponse doit encore être traitée puis envoyée. Une erreur peut au contraire remonter sans réponse : nous distinguerons ce chemin de la fin normale.

🌍 In Real Life

La situation : au restaurant, le client remet un bon ; le responsable coordonne sa préparation, puis un résultat prêt à servir lui revient.

L’équivalent dans Symfony : - Bon décrivant la demande → Request pour GET /blog/42. - Préparation de l'établissement → Kernel et son conteneur. - Coordination de cette commande → HttpKernel. - Résultat avec contenu et indications de service → Response, avec statut et headers.

Retour à la réalité technique : HttpFoundation fournit les objets HTTP ; HttpKernel coordonne leur traitement. Le conteneur ne reconstruit pas systématiquement tous les services pour chaque requête. Une Response retournée n'est pas encore un envoi réseau.

🧠 Comment le mémoriser : « Le bon décrit, le responsable coordonne. » Image mentale : le bon posé devant le responsable. Question-réflexe : est-ce un objet HTTP, la préparation de l'application ou son orchestration ?

⚠️ À ne pas confondre : Kernel prépare l'application ; HttpKernel traite la requête ; leurs interfaces fixent des contrats, elles ne sont pas des acteurs exécutables.

Le cycle en schéma

À retenir en priorité
  1. Le cycle prend une branche différente selon le type du retour controller.
  2. kernel.response travaille ensuite sur la Response obtenue.

Lisons ce schéma à partir de kernel.request, donc après la préparation de l'application. Sur le trajet de l'article 42, l'action produit une Response et rejoint directement kernel.response. La branche orange n'existe que pour un autre type de retour ; elle n'est pas une étape obligatoire du rendu HTML.

Bleu : étapes d'orchestration ; orange : conversion conditionnelle ; vert : émission et terminaison ; rouge : échec. Vue d'une requête principale dans le runner Runtime, sans exception des listeners. handle() ne fait pas lui-même l'envoi et une sous-requête n'entraîne pas automatiquement terminate().

L'exemple : une page de maintenance qui court-circuite

Exemple concret

À retenir en priorité
  1. Une Response posée sur RequestEvent court-circuite la résolution et l'exécution du controller.
  2. Le cycle traite la Response ; terminate relève ensuite du runner après émission.

Supposons maintenant que le blog soit fermé pour maintenance. Nous voulons répondre 503 à GET /blog/42 sans appeler ArticleCatalog. Un listener sur kernel.request peut fournir cette réponse avant la résolution du controller. Dans cet extrait, la class doit être enregistrée comme service avec l'autoconfiguration des listeners activée ; les imports rendent explicites les trois API utilisées.

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Event\RequestEvent;

#[AsEventListener(priority: 100)]
final class MaintenanceListener
{
    public function __invoke(RequestEvent $event): void
    {
        $event->setResponse(new Response('Maintenance', 503));
        // Le controller est sauté ; HttpKernel traite encore cette Response.
    }
}

Le RequestEvent reçu porte la demande courante. setResponse() y place le contenu Maintenance, statut 503, et arrête la propagation de cet event. Avec la priorité 100, ce listener précède notamment le RouterListener standard de priorité 32 s'ils sont tous deux enregistrés. Le callable de l'article n'est pas résolu.

Cet exemple répond toujours et concerne aussi les sous-requêtes : il faudrait une condition de maintenance et, si nécessaire, un contrôle isMainRequest() pour un autre périmètre. Sans nouvelle erreur, kernel.response et kernel.finish_request ont encore lieu. L'envoi et terminate() restent à la charge du runner ; setResponse() ne les exécute pas. Voyons le contrat que cette sortie anticipée respecte.

🌍 In Real Life

La situation : l'accueil remet une réponse « fermé pour maintenance » avant de transmettre le bon en cuisine.

L’équivalent dans Symfony : accueil prioritaire → listener de kernel.request ; avis de fermeture → Response 503 ; bon non transmis → résolution et appel du contrôleur sautés.

Retour à la réalité technique : RequestEvent::setResponse() arrête la propagation de cet événement. Ici, la priorité 100 précède le RouterListener standard à 32 : même le routage peut être évité. Sans nouvelle erreur, le filtrage de réponse et finish restent nécessaires ; l'envoi appartient au runner.

🧠 Comment le mémoriser : « Répondre tôt n'est pas envoyer tout de suite. » Image mentale : un avis encore sur le comptoir. Question-réflexe : quelles étapes cette Response évite-t-elle, et qui l'envoie ?

⚠️ À ne pas confondre : arrêter cet événement ne supprime pas tous les événements ultérieurs du traitement.

Le contrat

À retenir en priorité
  1. Le contrat relie Request à Response.
  2. MAIN_REQUEST vaut 1 et SUB_REQUEST vaut 2.

Que la réponse contienne l'article ou la maintenance, l'appelant attend le même résultat. Voici la signature de HttpKernelInterface, à lire dans son interface, et non comme une fonction autonome :

public function handle(Request $request, int $type = self::MAIN_REQUEST, bool $catch = true): Response;

Pour GET /blog/42, $request contient la demande et $type vaut par défaut MAIN_REQUEST (1). Un traitement HTTP imbriqué emploie SUB_REQUEST (2) ; il suit le même mécanisme, et les listeners doivent décider s'ils concernent aussi cette sous-requête.

$catch = true autorise la prise en charge des exceptions concernées ; il ne garantit pas qu'un listener fabriquera une page d'erreur. Avec false, l'appelant conserve la responsabilité de l'échec. Le traitement des Error dépend aussi de handleAllThrowables, détaillé plus bas. En cas de succès, le résultat est un object Response encore distinct de son émission réseau. Le contrat fixe cette frontière ; parcourons maintenant ses acteurs dans l'ordre réel.

Pour observer cette frontière, l'exemple suivant reçoit un kernel déjà assemblé et une Request de l'appelant. Avec une Request visant /blog/42, il retourne la Response obtenue ; avec une exception concernée par $catch, il la laisse remonter au lieu de demander sa conversion.

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\HttpKernelInterface;

function handleWithoutErrorPage(HttpKernelInterface $kernel, Request $request): Response
{
    return $kernel->handle($request, HttpKernelInterface::MAIN_REQUEST, false);
}

Cette fonction ne construit pas le kernel, ne configure pas les routes et n'émet aucun octet. Son résultat dépend donc de l'assemblage fourni. Elle rend visible le choix de l'appelant ; elle n'est pas un deuxième front controller à exécuter en plus du runner.

🌍 In Real Life

La situation : une fiche de poste promet de prendre un bon et de remettre un résultat ; elle ne prépare elle-même aucun plat.

L’équivalent dans Symfony : fiche de poste → HttpKernelInterface ; employé remplissant ce rôle → objet qui implémente le contrat ; résultat remis au responsable → valeur Response retournée par handle().

Retour à la réalité technique : une interface décrit une signature. L'implémentation peut échouer au lieu de retourner normalement. $catch = true autorise le traitement des exceptions concernées, sans garantir leur conversion en Response ; ce contrat ne couvre pas l'émission.

🧠 Comment le mémoriser : « La promesse n'est pas l'employé. » Image mentale : la fiche à côté de la personne. Question-réflexe : décrit-on un contrat ou le code qui l'exécute ?

⚠️ À ne pas confondre : MAIN_REQUEST et SUB_REQUEST qualifient le traitement ; ce ne sont pas deux signatures ni deux navigateurs.

Repère — La pile de Requests, poussée et dépilée par handle() :

Question: How is the current request restored after a sub-request finishes?

Answer: handle() pops the RequestStack in a finally block.

handle() empile la Request à l'entrée. Le finally restaure la pile même en cas d'exception.

Repère — La branche que le trajet nominal ne montre pas :

Question: Does catch=false dispatch kernel.exception?

Answer: No. The exception propagates instead; covered exception paths still finish the request.

catch=false désactive la conversion par kernel.exception. Distinguer cette option du traitement des Error par handleAllThrowables.

Le trajet

Reprenons le blog ouvert, route importée et controller enregistré. Voici le chemin de notre entrée Runtime HTTP standard, sans cache HTTP réutilisable ni réponse anticipée ; les listeners terminent sans erreur.

  1. Le serveur web transmet GET /blog/42 à public/index.php, notre front controller, point d'entrée HTTP. Le script charge vendor/autoload_runtime.php et retourne un callable construisant App\Kernel. L'amorçage l'appelle : nous avons un object Kernel, pas encore une application démarrée.
  2. SymfonyRuntime::getRunner() choisit le runner, chargé d'exécuter l'application. Dans ce chemin standard, il crée la Request depuis les superglobales après construction du Kernel. Le runner appelle ensuite handle() ; il n'a encore rien envoyé.
  3. Kernel::handle() prépare l'application : son chemin comporte preBoot(), le cache HTTP optionnel, puis boot() avant délégation au service http_kernel. Le conteneur compilé est chargé s'il est utilisable, construit si nécessaire. Nous ne recompilons pas toute la configuration pour chaque lecture d'article et ne construisons pas tous les services.
  4. Le concret HttpKernel empile la Request et dispatche kernel.request. Si le routage est atteint, RouterListener fait correspondre l'URL à blog_show et ajoute ici les attributes _route = blog_show, _controller = App\Controller\BlogController::show et id = '42'. Ce sont des attributes de Request, pas les paramètres de query ni les attributes PHP #[...]. Le matching ne prouve pas l'existence de l'article. Un listener peut encore répondre à ce stade, comme pour la maintenance.
  5. Sans réponse anticipée, HttpKernel appelle ControllerResolver. À partir de _controller, celui-ci fournit le callable, ici l'object controller et sa method show. L'intégration au conteneur peut fournir ce controller-service avec ses dépendances. kernel.controller peut remplacer le callable ; l'action n'a pas encore été exécutée.
  6. HttpKernel appelle ArgumentResolver, qui consulte les value resolvers, collaborateurs chargés de fournir les valeurs adaptées à la signature finale. L'attribute id peut ainsi fournir la valeur de l'argument correspondant. Ce travail est distinct de l'injection au constructeur. kernel.controller_arguments peut encore modifier les arguments et le callable ; HttpKernel récupère ces valeurs finales.
  7. HttpKernel appelle enfin le controller. BlogController::show peut consulter notre ArticleCatalog en mémoire : 42 existe, 999 non. Pour 42, l'action prépare le contenu de l'article et retourne une Response. Aucun chargement de base de données, Validator ou Serializer n'est imposé par ce GET. Pour 999, l'action doit choisir explicitement une réponse ou exception 404. Si une variante retourne autre chose qu'une Response, kernel.view donne aux listeners une occasion d'en produire une ; un tableau ne devient pas automatiquement du JSON.
  8. Une Response obtenue passe par kernel.response, puis kernel.finish_request si ce filtrage réussit. Les listeners de finish peuvent restaurer un contexte parent. HttpKernel dépile la Request dans son finally et rend la Response à l'appelant.
  9. Le runner envoie ensuite la Response et appelle terminate() si le noyau implémente TerminableInterface, ce qui permet kernel.terminate. Le processus PHP reste occupé pendant ces traitements. La libération anticipée du client dépend du serveur : ce hook n'est pas une tâche asynchrone persistante.

Variante manuelle, à ne pas superposer à cette séquence. Sans Runtime, le point d'entrée prend explicitement en charge l'autoload et l'amorçage, la création de Request, handle(), l'envoi, puis la terminaison si disponible. Il n'y a pas une seconde Request ou un second envoi à ajouter au chemin Runtime. Un runner personnalisé peut aussi suivre un autre mode d'exécution.

🌍 In Real Life

La situation : le responsable fait annoter le bon, choisit la personne chargée de la commande, puis lui prépare les informations nécessaires avant de lui demander d'agir.

L’équivalent dans Symfony : - Destination inscrite sur le bon → matching du routeur via RouterListener, pendant kernel.request. - Personne et geste identifiés → callable obtenu par ControllerResolver, à la demande de HttpKernel. - Informations adaptées à ce geste → arguments obtenus par ArgumentResolver et ses value resolvers, à la demande de HttpKernel. - Ordre de commencer → invocation finale du callable par HttpKernel.

Retour à la réalité technique : après le callable vient kernel.controller, puis la résolution des arguments, puis kernel.controller_arguments, puis l'appel. Les resolvers ne s'appellent pas entre eux. _route, _controller et id sont trois attributes de Request distincts. L'injection du constructeur n'est pas la résolution des paramètres de l'action ; lire l'article en mémoire dans l'action est ici un choix explicite.

🧠 Comment le mémoriser : « Destination, qui, avec quoi ; le responsable appelle. » Image mentale : trois réponses revenant au même bureau. Question-réflexe : qui appelle ce collaborateur et que reçoit-il en retour ?

⚠️ À ne pas confondre : les annotations de ce bon ne sont ni la query string ni les attributes PHP #[...]. Le matching ne prouve pas l'existence de l'article.

🌍 In Real Life

La situation : désigner un responsable sur le planning n'ouvre pas encore l'établissement ; il faut ensuite préparer le service.

L’équivalent dans Symfony : désignation → construction de App\Kernel ; préparation effective → amorçage de l'application ; bon pris en charge → Request fournie au traitement.

Retour à la réalité technique : dans l'entrée Runtime standard décrite, le callable construit Kernel avant que SymfonyRuntime::getRunner() crée la Request. Le runner appelle ensuite handle(), qui prépare l'application. Cette image distingue les responsabilités, sans faire de cet ordre une règle pour tous les runners. L'entrée manuelle est une alternative complète, pas un second passage.

🧠 Comment le mémoriser : « Nommé n'est pas démarré. » Image mentale : un nom sur le planning devant une salle encore fermée. Question-réflexe : parle-t-on de construction, de boot ou de traitement ?

⚠️ À ne pas confondre : charger un conteneur compilé utilisable et recompiler sa configuration.

Le cycle ressemble à un colis passant des points de contrôle : kernel.view emballe seulement un résultat qui n'est pas déjà une Response ; kernel.response inspecte la Response obtenue. Ce ne sont pas deux emballages systématiques.

Repère — Trois façons d'échouer, trois exceptions :

Question: When is ControllerDoesNotReturnResponseException raised?

Answer: After a non-Response controller result remains unconverted by kernel.view.

Le retour est contrôlé après kernel.view. Un listener peut produire la Response manquante.

Repère — Le cycle en schéma :

Question: Does a controller result always need kernel.view conversion?

Answer: No. A Response skips kernel.view; a different result must be converted to a Response.

Le cycle prend une branche différente selon le type du retour controller. kernel.response travaille ensuite sur la Response obtenue.

Repère de l’exemple :

Question: What does setting a Response during kernel.request do to controller execution?

Answer: It short-circuits controller execution; response and finish-request processing still take place.

Une Response posée sur RequestEvent court-circuite la résolution et l'exécution du controller. Le cycle traite la Response ; terminate relève ensuite du runner après émission.

La pile de Requests, poussée et dépilée par `handle()`

À retenir en priorité
  1. handle() empile la Request à l'entrée.
  2. Le finally restaure la pile même en cas d'exception.

Pendant la préparation de la page, un fragment peut déclencher une sous-requête. Le code de ce fragment doit alors voir sa propre Request, puis le traitement de l'article doit retrouver la sienne. RequestStack est la pile qui conserve cet ordre : HttpKernel::handle() empile à l'entrée et dépile dans un finally, exception comprise. getCurrentRequest() retourne le sommet ; après le fragment, la Request de l'article redevient courante. kernel.finish_request est une notification, pas ce dépilement.

Une StreamedResponse déplace une partie du travail au moment de l'envoi : son callback, fonction appelée pour produire le flux, s'exécute après le retour de handle(). HttpKernel le réenveloppe pour réempiler sa Request pendant le flux, puis la retirer. Un export lié au blog peut donc retrouver la demande qui l'a produit. Sans cette enveloppe, la pile d'une requête principale isolée serait déjà vide ; cela ne signifie pas que tout traitement différé conserve automatiquement son contexte HTTP.

🌍 In Real Life

La situation : pour traiter un complément, le responsable pose un petit bon sur le bon principal, puis le retire pour reprendre la commande initiale.

L’équivalent dans Symfony : bon supérieur → Request courante ; bon dessous → Request parente ; ajout/retrait → opérations de RequestStack encadrées par HttpKernel::handle().

Retour à la réalité technique : le dépilement se fait dans finally, même si une exception remonte. kernel.finish_request est une notification distincte. Pour le flux décrit ici, HttpKernel enveloppe le callback de StreamedResponse afin de réempiler temporairement sa Request pendant l'émission ; ce n'est pas une conservation universelle du contexte.

⚠️ À ne pas confondre : la pile représente des traitements imbriqués, pas une file de commandes à exécuter plus tard.

La branche que le trajet nominal ne montre pas

À retenir en priorité
  1. catch=false désactive la conversion par kernel.exception.
  2. Distinguer cette option du traitement des Error par handleAllThrowables.

Remplaçons 42 par 999. La route peut correspondre, mais notre catalogue ne contient pas cet article. Si l'action lève une exception HTTP 404, le trajet quitte l'appel du controller et rejoint la gestion d'erreur. Une panne inattendue suit aussi une branche d'erreur, mais ne doit pas être maquillée en absence d'article. Le diagramme distingue conversion en Response et remontée vers l'appelant.

Losanges orange : décisions ; bleu : events ; rouge : throwable entrant ou relancé. Ce second schéma suppose que les listeners de traitement d'erreur ne lèvent pas eux-mêmes une nouvelle exception. Le finally dépile la Request même sur la branche « relancée sans event ».

Pour l'exception 404 concernée, $catch = true ouvre kernel.exception. Un listener peut produire la page d'erreur : si son filtrage réussit, kernel.response puis kernel.finish_request ont lieu. Sans Response, kernel.finish_request précède la remontée de l'exception. Avec $catch = false, HttpKernel saute kernel.exception, notifie finish puis laisse remonter l'échec. Ces chemins supposent que les listeners de gestion d'erreur ne provoquent pas eux-mêmes une nouvelle panne.

Changeons maintenant la cause : le code de l'article déclenche une \TypeError, qui est une \Error. Elle n'entre dans ces branches que si handleAllThrowables est vrai. framework.handle_all_throwables l'active par défaut, contrairement au constructor d'HttpKernel autonome. Sans cette option, cette Error remonte directement sans ces notifications d'erreur ou de finish ; le finally dépile quand même. Les events déjà exécutés avant l'appel fautif — request, controller, controller_arguments — ne sont pas annulés. Pour diagnostiquer une panne, cherche donc son point d'apparition et la configuration concrète, pas seulement son statut final.

🌍 In Real Life

La situation : un incident en cuisine est signalé au responsable ; celui-ci peut préparer une explication pour le client, ou transmettre l'incident sans réponse prête.

L’équivalent dans Symfony : incident → exception ; possibilité de préparer une explication → listeners de kernel.exception ; explication prête → Response ; incident transmis → exception relancée.

Retour à la réalité technique : cette conversion dépend de $catch, du throwable concerné et des listeners. Sans Response, le chemin nominal de réponse n'est pas garanti. Une Error hors handleAllThrowables contourne les notifications décrites ; le finally dépile néanmoins la Request. Les événements déjà exécutés ne sont pas annulés.

🧠 Comment le mémoriser : « Signaler n'est pas résoudre. » Image mentale : un signalement à côté d'une réponse encore absente. Question-réflexe : une Response a-t-elle réellement été produite ?

⚠️ À ne pas confondre : article absent et panne technique ; l'une ne justifie pas de masquer l'autre sous une 404.

Trois façons d'échouer, trois exceptions

À retenir en priorité
  1. Le retour est contrôlé après kernel.view.
  2. Un listener peut produire la Response manquante.

Nous savons maintenant comment une erreur peut être traitée. Encore faut-il identifier ce qui a échoué. Un article absent dans ArticleCatalog n'est pas un controller introuvable : dans le premier cas, l'action a été appelée ; dans le second, elle ne l'a jamais été. Ce tableau repère trois frontières techniques à examiner avant de conclure à une panne du catalogue.

Ce qui manque Ce qui est levé
Le resolver ne trouve aucun controller NotFoundHttpException — « the route is wrongly configured »
Le controller ne rend pas une Response, et aucun listener de kernel.view n'en pose une ControllerDoesNotReturnResponseException
La Request elle-même est malformée (RequestExceptionInterface) convertie en BadRequestHttpException avant la branche d'exception

La deuxième — « Did you forget to add a return statement somewhere in your controller? » — n'est levée qu'après kernel.view. Si une variante de show retourne un tableau sans listener de conversion, le problème est donc le résultat de l'action, pas le matching de /blog/42. À l'inverse, un callable existant mais invalide ne doit pas être assimilé sans examen au cas précis où le resolver ne trouve aucun controller.

🌍 In Real Life

La situation : personne n'est affecté à la commande, le résultat n'est pas prêt à servir, ou le bon est malformé : ce sont trois incidents différents.

L’équivalent dans Symfony : aucune cible trouvée par le resolver → NotFoundHttpException ; aucun résultat Response après kernel.view → ControllerDoesNotReturnResponseException ; erreur de Request concernée → conversion en BadRequestHttpException.

Retour à la réalité technique : ces correspondances repèrent les cas précis du tableau, pas toutes les erreurs possibles. Un callable invalide n'est pas nécessairement une cible absente. Un tableau retourné ne devient pas automatiquement du JSON : il faut une conversion configurée ou une Response explicite.

Pièges d'examen

Piège à éviter

  • Conserver les conditions du trajet nominal

    Pour relire une trace de GET /blog/42, garde les conditions avec l'ordre :

  • Voir l’explication : saute kernel.view
    • Une Response directement retournée par show saute kernel.view. kernel.response exige une Response obtenue, pas une exception remontée sans conversion.
    • Sur notre chemin géré avec Response, kernel.finish_request vient après kernel.response. Mais pour une exception concernée qui remonte sans Response, finish peut avoir lieu sans response. Une \Error hors handle_all_throwables contourne ces notifications.
    • Le runner appelle la terminaison après l'envoi ; ni le retour de handle() ni kernel.finish_request ne signifient « le client a reçu tous les octets ».
    • La maintenance saute le controller mais rejoint le traitement de la Response. Response et finish restent attendus sans nouvelle erreur ; terminate dépend toujours du runner ou de l'appelant.
    • Sur kernel.request, _controller peut encore manquer. RouterListener intervient dans cet event, pas avant lui. Plus tard, kernel.controller_arguments peut remplacer le callable aussi.
    • public/index.php est le front controller conventionnel de notre application ; ce n'est pas une obligation pour tous les assemblages Symfony, ni le chemin nécessaire de chaque fichier statique.
    • Une sous-requête vaut SUB_REQUEST (2), la principale MAIN_REQUEST (1) ; changer ce type ne crée pas un nouveau navigateur.

Choisir le hook sans confondre retour, émission et traitement durable

  • Terminaison locale contre traitement durable

    Après émission de la page 42, un traitement bref peut utiliser kernel.terminate dans le runner décrit. Si le besoin devient « importer un long fichier même après la fin de ce processus », ce hook ne suffit pas : il faut un mécanisme durable distinct, avec traitement asynchrone configuré. Il ne faut pas transformer le GET en import obligatoire.

  • Restaurer le contexte parent après une sous-requête

    À l'intérieur de la page, si un fragment a modifié la locale, un listener de kernel.finish_request peut restaurer le contexte parent. Ce travail répond au retour d'une sous-requête, pas à l'envoi réseau. Le cours sur les events du kernel précise comment enregistrer ces réactions ; celui sur les exceptions reprend la bifurcation 404/500.

🌍 In Real Life

La situation : une commande prête revient au comptoir ; le service la remet ensuite au client, puis range son poste.

L’équivalent dans Symfony : retour au comptoir → retour de handle() ; remise → émission par le runner ; rangement local → appel séparé à terminate() lorsque disponible.

Retour à la réalité technique : sur le chemin réussi, kernel.response puis kernel.finish_request précèdent le retour ; finally dépile avant que l'appelant reprenne. Le runner envoie ensuite et peut terminer. Contrairement à la remise physique imaginée, cela ne garantit pas la réception de tous les octets par le client. Le processus reste occupé pendant la terminaison.

🧠 Comment le mémoriser : « Prêt, envoyé, puis terminé. » Image mentale : trois emplacements distincts sur le comptoir. Question-réflexe : suis-je encore dans handle(), dans l'envoi ou dans la terminaison ?

⚠️ À ne pas confondre : rangement local et tâche durable confiée à un autre processus ; kernel.terminate n'est pas une file asynchrone persistante.

Fiche express

À mémoriser

Pour reconstruire la trace de l'article sans imposer toutes les branches :

  • handle(Request, $type, $catch): Response ; MAIN_REQUEST = 1, SUB_REQUEST = 2.
  • Chemin avec controller, Response obtenue et listeners sans erreur : request → controller → controller_arguments → (appel) → [view si nécessaire] → response → finish_request → (retour, puis envoi par le runner) → terminate si appelé sur un noyau terminable.
  • kernel.view n'est dispatché que si le controller ne rend pas une Response.
  • Maintenance sur kernel.request : response, finish_request sans nouvelle erreur ; terminate reste séparé, à la charge du runner.
  • controller_arguments peut encore remplacer le controller.
  • Pile : empilée à l'entrée, dépilée dans un finally.
  • finish_request sur les trois paths — sauf \Error hors handle_all_throwables.
  • Aucun controller → 404 ; pas de Response → ControllerDoesNotReturnResponseException.

Moyen mnémotechnique : « Traiter retourne ; envoyer émet ; terminer suit. » Si aucune Response n'a été produite, reviens à la branche d'exception au lieu de réciter la fin nominale.
