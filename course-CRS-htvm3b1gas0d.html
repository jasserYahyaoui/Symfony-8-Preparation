Objectif

Comprendre ce que la dependency injection résout, distinguer recevoir un service et le demander au container, choisir la forme d'injection adaptée à une dependency, et savoir utiliser le component seul jusqu'à la compilation. Le container dans une application — definitions, visibilité, configuration — a sa propre page, Service container.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La signature expose les dependencies.
  2. La récupération masque les besoins réels.

Une class reçoit ses dependencies au lieu de les fabriquer ou de les demander au container. Elle les reçoit par l'une des quatre formes d'injection, selon que la dependency est obligatoire ou facultative. Le component, autonome, décrit les services, puis les compile : un container figé, d'où l'on ne fait qu'un get(), à l'entry point.

Le schéma

À retenir en priorité
  1. Le kernel assemble l'application.
  2. Les services reçoivent leurs collaborators.

Le fil rouge : un `NewsletterManager` et son `Mailer`

À retenir en priorité
  1. Une string reste une valeur.
  2. Reference désigne un service.
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;

$container = new ContainerBuilder();
$container->setParameter('mailer.transport', 'sendmail');
$container->register('mailer', Mailer::class)
    ->addArgument('%mailer.transport%');                 // un parameter : une valeur
$container->register('newsletter_manager', NewsletterManager::class)
    ->addArgument(new Reference('mailer'))               // un service
    ->setPublic(true);                                   // privé par défaut
$container->compile();
$manager = $container->get('newsletter_manager');

addArgument('mailer') passerait la string 'mailer' : seul new Reference('mailer') désigne un service.

Injecter ou récupérer : la distinction de fond

À retenir en priorité
  1. Le container ne décrit pas les besoins précis.
  2. Préférer des arguments typés par collaborator.

Une class qui reçoit ContainerInterface et appelle get('mailer') ne fait pas de dependency injection : elle récupère. Le critère est ce qu'elle reçoit — un object qui fournit n'importe quoi —, pas le moyen.

Injection Container entier Service locator
La signature dit ce qu'elle utilise oui non une liste déclarée

« As few times as possible at the entry point » : dans une application, cet entry point est le kernel.

Les quatre formes d'injection

À retenir en priorité
  1. Le constructor garantit l'état initial.
  2. Un setter convient aux dependencies facultatives.
La dependency est… Forme Écriture avec le component
obligatoire constructor ->addArgument(new Reference('mailer'))
facultative, service immuable immutable-setter (withMailer() renvoie un clone) ->addMethodCall('withMailer', [...], true)
facultative setter ->addMethodCall('setMailer', [...])
imposée par du code tiers property publique — « mainly only disadvantages » ->setProperty('mailer', ...)
  • Le constructor garantit la présence et la stabilité ; le setter ne garantit ni l'appel ni la stabilité.
  • #[Required] (Symfony\Contracts\Service\Attribute) n'agit que sur un service autowiré ; l'autowiring n'appelle pas un setter qui ne le porte pas. Un immutable-setter autowiré doit renvoyer static, sinon son résultat est jeté.
  • Deux constructors qui se reçoivent mutuellement : compile() lève ServiceCircularReferenceException. Un setter d'un côté casse le cycle ; un immutable-setter, non.

Le component seul, ligne par ligne

À retenir en priorité
  1. La compilation fige la configuration.
  2. Les services restent ensuite accessibles selon leur visibilité.

symfony/dependency-injection s'installe seul et fournit un container PSR-11. Après compile() :

Appel Résultat
get() d'un service public l'object ; deux get() donnent la même instance, sauf setShared(false)
get() ou has() d'un service privé ServiceNotFoundException « …has been removed or inlined… » ; false
register() BadMethodCallException : « Adding definition to a compiled container is not allowed. »
setParameter() LogicException : « Impossible to call set() on a frozen ParameterBag. »
getParameter() fonctionne : figé, pas illisible
  • Une référence vers un service jamais déclaré fait échouer la compilation (« …has a dependency on a non-existent service "mailer" ») : c'est EXCEPTION_ON_INVALID_REFERENCE, le défaut.
  • new Reference('mailer', ContainerInterface::IGNORE_ON_INVALID_REFERENCE) dans un addMethodCall() : l'appel est omis si le service manque. NULL_ON_INVALID_REFERENCE passerait null.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Required dépend de l'autowiring.
  2. L'attribute seul ne déclenche pas l'appel.

« Le container est injecté, donc c'est de la dependency injection. » Faux. Le critère est ce que la class reçoit, pas la façon dont elle le reçoit. Une class qui reçoit le container et appelle get() fait de la récupération de services, et ses dependencies réelles ont disparu de sa signature.

« Il existe trois formes d'injection. » La documentation 8.0 en décrit quatre : constructor, immutable-setter, setter et property. Un énoncé qui présente l'immutable-setter (une method withX() qui renvoie un clone) comme une invention ou une mauvaise pratique se trompe.

Constructor et setter inversés. Le constructor est la voie normale, pour la dependency obligatoire ; le setter est réservé à la dependency facultative (ou à un cycle). Un choix qui met une dependency indispensable dans un setter crée un object qui peut exister sans elle.

#[Required] sans autowiring. L'attribute seul ne fait rien : sur un service non autowiré, le setter n'est jamais appelé et la property reste null. À l'inverse, l'autowiring n'appelle pas un setter qui n'a pas #[Required].

Un service privé n'est pas « non injectable ». Privé interdit seulement le get() après compilation ; le service reste injectable dans les autres. Et c'est le défaut : un register() sans setPublic(true) donne un service privé.

compile() fige. Après compilation, ni nouvelle definition ni nouveau parameter : register() lève une BadMethodCallException, setParameter() une LogicException. Lire un parameter reste possible.

Une référence absente casse compile(), pas get(). Par défaut, un service qui référence un service inexistant fait échouer la compilation, même si personne ne demande jamais ce service.

Un cycle entre deux constructors aussi. Deux services qui se reçoivent mutuellement par leur constructor lèvent ServiceCircularReferenceException dès compile(), pas au premier appel. Un setter d'un côté suffit à le casser.

addArgument('mailer') n'injecte pas le service mailer. C'est la string 'mailer' qui part dans le constructor. Pour un service, il faut new Reference('mailer').

Fiche express

◆ À mémoriser

À retenir en priorité
  1. L'immutable setter rend un nouvel object.
  2. Ne pas le confondre avec un setter mutable.

Si tu dois retenir seulement 7 choses :

  • Recevoir le container n'est pas de l'injection : un seul get(), à l'entry point.
  • Quatre formes : constructor, immutable-setter, setter, property.
  • Obligatoire → constructor. Facultative → setter. Un cycle se casse par un setter.
  • #[Required] n'agit que sur un service autowiré.
  • Reference = un service ; %x% = un parameter ; sinon une string.
  • Service privé par défaut ; compile() fige (ni register() ni setParameter()).
  • Référence absente ou cycle : compile() échoue, pas get().

Moyen mnémotechnique : « C-I-S-P : Constructor, Immuable, Setter, Public », de la plus sûre à la moins sûre.

composer require symfony/dependency-injection
