Objectif

Pour afficher /blog/42, BlogController a besoin d'un ArticleCatalog. Pour traiter l'inscription, un autre service peut avoir besoin d'un moyen de notification. Si chacun construit ses collaborateurs ou les recherche dans un container global, leur remplacement en test devient difficile et leurs besoins réels se cachent dans le corps du code.

La dependency injection, ou injection de dépendances, consiste à fournir ces collaborateurs depuis l'extérieur. Nous allons distinguer ce principe du composant Symfony 8.0 qui peut organiser leur construction. Les laboratoires PHP 8.4 fonctionnent sans Request ; le cours suivant relie leurs définitions au container complet de l'application.

L'essentiel

À comprendre

À retenir en priorité
  1. La signature expose les dependencies.
  2. La récupération masque les besoins réels.

Une dépendance est un collaborateur dont l'objet a besoin pour travailler. Recevoir ArticleCatalog au constructeur rend ce besoin visible et permet de fournir un catalogue adapté au scénario testé, par exemple article 42 présent ou 999 absent. L'injection existe déjà avec un simple appel PHP à new : elle ne nécessite pas un container.

Le composant DependencyInjection ajoute un outil d'assemblage. Une définition décrit comment obtenir un service ; une Reference désigne une autre définition ; un paramètre fournit une valeur de configuration. La compilation vérifie et transforme cet ensemble avant les demandes d'objets. Elle n'est pas une nouvelle étape métier de chaque GET du blog.

La documentation distingue quatre formes d'injection. Le choix dépend de l'état dans lequel l'objet peut réellement être utilisé, pas d'une obligation d'employer les quatre. Les accès au container entier restent concentrés au point d'assemblage ; les services métier travaillent ensuite avec leurs collaborateurs. Après compilation, la lecture de paramètres et l'accès aux services autorisés restent possibles : « figé » ne signifie ni « seul get() existe » ni « tous les objets sont immuables ».

🌍 In Real Life

La situation : on remet au cuisinier l'ustensile dont il a besoin, au lieu de lui demander de construire lui-même tous ses outils.

L’équivalent dans Symfony : ustensile fourni de l'extérieur → dépendance injectée ; cuisinier → service consommateur ; organisation de l'équipement → conteneur, lorsqu'on en utilise un.

Retour à la réalité technique : l'injection est un principe d'assemblage, déjà présent dans new NewsletterManager($mailer). DependencyInjection 8.0 automatise l'assemblage à partir de définitions ; il n'est pas nécessaire pour que l'injection existe.

🧠 Comment le mémoriser : « Recevoir plutôt que fabriquer. » Image mentale : l'outil posé dans la main. Question-réflexe : l'objet reçoit-il son collaborateur ou décide-t-il lui-même comment le construire ?

⚠️ À ne pas confondre : le service qui travaille et le conteneur qui sait le fournir.

Le schéma

À retenir en priorité
  1. Le kernel assemble l'application.
  2. Les services reçoivent leurs collaborators.

Nous conservons le laboratoire NewsletterManager/Mailer pour la branche d'inscription. Il illustre la même question que le catalogue du controller : comment fournir le collaborateur sans obliger le consommateur à savoir comment on le construit ?

Les pointillés orange représentent les instructions, pas un mailer déjà créé. La compilation prépare leur utilisation. Lors du premier accès montré, les services ordinaires ne sont ni déjà construits ni configurés comme lazy, c'est-à-dire à initialisation différée : le container obtient d'abord le mailer, puis le passe au constructeur du manager.

Les flèches pleines représentent cette construction effective. Le manager ne reçoit pas une Reference ni une chaîne d'identification, mais l'objet attendu. Il peut ensuite travailler sans connaître le container. Un test peut l'assembler directement ; choisir une interface pour sa dépendance permet en outre de varier les implémentations, sujet repris avec les aliases.

Le fil rouge : un `NewsletterManager` et son `Mailer`

À retenir en priorité
  1. Une string reste une valeur.
  2. Reference désigne un service.

Voici les classes minimales qui rendent le laboratoire complet. Ce Mailer local ne désigne pas le composant Mailer : il mémorise seulement un nom de transport. Aucune commande système ni aucun email ne sera envoyé. Le script suppose l'autoload de DependencyInjection 8.0 chargé :

use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;

final class Mailer
{
    public function __construct(public readonly string $transport) {}
}

final class NewsletterManager
{
    public function __construct(private Mailer $mailer) {}

    public function transport(): string
    {
        return $this->mailer->transport;
    }
}

$container = new ContainerBuilder();
$container->setParameter('mailer.transport', 'sendmail');
$container->register('mailer', Mailer::class)
    ->addArgument('%mailer.transport%');                 // un parameter : une valeur
$container->register('newsletter_manager', NewsletterManager::class)
    ->addArgument(new Reference('mailer'))               // un service
    ->setPublic(true);                                   // privé par défaut
$container->compile();
$manager = $container->get('newsletter_manager');
echo $manager->transport(), "\n";

L'entrée de configuration mailer.transport vaut 'sendmail'. %mailer.transport% demande sa valeur ; new Reference('mailer') demande l'objet du service. Résultat attendu : sendmail. Le manager est public uniquement parce que ce programme le récupère directement à son point d'entrée ; le mailer reste privé et injectable.

addArgument('mailer') transmettrait la string 'mailer', incompatible ici avec le type Mailer du constructeur. La chaîne Mailer::class serait également une valeur, pas une demande d'instance. Ce contraste explique la nécessité de Reference. Changer la valeur de transport de ce laboratoire ne configure pas un vrai système d'envoi : nous observons seulement l'assemblage.

🌍 In Real Life

La situation : une fiche d'équipement peut indiquer un réglage, écrire le mot « fouet », ou demander de fournir le véritable fouet.

L’équivalent dans Symfony : réglage nommé → %mailer.transport% ; mot seul → string 'mailer' ; demande de l'objet → new Reference('mailer').

Retour à la réalité technique : la Reference décrit un lien entre services avant leur obtention. Le constructeur reçoit ensuite l'objet résolu, pas la Reference. Ni le nom de classe ni l'identifiant écrit comme simple string ne deviennent automatiquement une instance.

🧠 Comment le mémoriser : « Le nom de l'outil n'est pas l'outil. » Image mentale : une étiquette à côté du fouet. Question-réflexe : cet argument représente-t-il une valeur, un paramètre ou une référence de service ?

⚠️ À ne pas confondre : le Mailer de ce laboratoire et un vrai composant d'envoi ; afficher sendmail n'envoie aucun message.

Injecter ou récupérer : la distinction de fond

À retenir en priorité
  1. Le container ne décrit pas les besoins précis.
  2. Préférer des arguments typés par collaborator.

Le manager connaît maintenant son besoin par sa signature. Si nous lui fournissions plutôt ContainerInterface, ce container serait bien injecté, mais un appel interne get('mailer') servirait ensuite à localiser son vrai collaborateur. La signature ne dirait plus quel mailer préparer pour le tester.

Recevoir directement la dépendance réduit ce couplage. Un service locator est un cas plus ciblé : il donne accès à un ensemble déclaré de collaborateurs, utile lorsque le choix doit être différé. Il n'est pas une raison de cacher une dépendance unique déjà connue.

Injection Container entier Service locator
La signature dit ce qu'elle utilise oui non une liste déclarée
Identifier demandé inexistant référence obligatoire vérifiée sur le graphe conservé recherche dynamique à l'exécution recherche dynamique à l'exécution ; références déclarées vérifiables à la compilation
Statut la voie normale à éviter cas particulier légitime

Dans la colonne DI, une référence obligatoire manquante provoque une erreur si son consommateur reste dans le graphe compilé. Une définition privée inutilisée peut être retirée avant ce contrôle. Un identifiant inventé dynamiquement dans un get() ne bénéficie pas du même contrôle préalable. Pour un locator, distinguons aussi la validation de ses références déclarées de la key que le code décidera de demander plus tard.

Dans une application Symfony, le kernel et l'intégration du framework organisent le container ; cela n'oblige pas le controller ou l'importeur à répéter des recherches dans le container entier. Le principe « aussi peu d'accès que possible au point d'entrée » décrit une frontière d'assemblage, pas une interdiction de toute API de container dans les outils qui ont précisément cette responsabilité.

🌍 In Real Life

La situation : remettre un outil précis, donner accès à un petit casier identifié, et ouvrir tout le magasin ne révèlent pas les mêmes besoins.

L’équivalent dans Symfony : outil reçu → injection directe ; petit casier → service locator à liste déclarée ; magasin entier → conteneur global consulté par le consommateur.

Retour à la réalité technique : injecter le conteneur reste une injection de cet objet, mais ses recherches internes cachent les dépendances métier. Un locator permet un choix différé borné. Les références déclarées du graphe conservé sont vérifiables à la compilation ; une clé calculée à l'exécution peut encore être inconnue.

🧠 Comment le mémoriser : « Montrer le besoin, pas seulement la clé du magasin. » Image mentale : une main avec un outil face à une main avec une clé. Question-réflexe : la signature révèle-t-elle le collaborateur réellement utilisé ?

⚠️ À ne pas confondre : accès limité par conception et autorisation de sécurité ; un locator n'est pas un contrôle d'accès utilisateur.

Les quatre formes d'injection

À retenir en priorité
  1. Le constructor garantit l'état initial.
  2. Un setter convient aux dependencies facultatives.

Demandons d'abord si un objet utilisable peut exister sans le collaborateur. Notre manager ne peut pas annoncer son transport sans mailer : le constructeur est donc le choix naturel. Un suivi d'activité réellement facultatif peut, lui, posséder un comportement défini lorsqu'il est absent. La table propose les formes à examiner :

La dependency est… Forme Écriture avec le component
obligatoire constructor ->addArgument(new Reference('mailer'))
facultative, service immuable immutable-setter (withMailer() renvoie un clone) ->addMethodCall('withMailer', [...], true)
facultative setter ->addMethodCall('setMailer', [...])
imposée par du code tiers property publique — « mainly only disadvantages » ->setProperty('mailer', ...)

Le constructeur impose la présence d'un argument requis et typé lors de la construction. Cela ne rend pas automatiquement la propriété qui le conserve immuable : le code de la class pourrait encore la réaffecter s'il l'autorise. PHP permet aussi des arguments optionnels au constructeur ; la table exprime une recommandation de conception, pas une restriction du langage.

Le setter ordinaire modifie l'objet existant. Il peut ne jamais être appelé ou l'être plusieurs fois. Une dépendance facultative doit donc avoir un état initial valide et être vérifiée avant usage ; laisser une propriété typée non initialisée ne constitue pas un comportement facultatif correct.

L'immutable-setter, ou wither, renvoie une autre instance portant le changement. Ce laboratoire utilise un préfixe de diagnostic d'import pour rendre visible la différence, sans ajouter de dépendance externe :

final class Label
{
    public function __construct(private string $prefix = '') {}

    public function withPrefix(string $prefix): static
    {
        $copy = clone $this;
        $copy->prefix = $prefix;
        return $copy;
    }

    public function render(string $text): string
    {
        return $this->prefix.$text;
    }
}
$plain = new Label();
$marked = $plain->withPrefix('[INFO] ');
echo $plain->render('Prêt'), "\n";
echo $marked->render('Prêt'), "\n";

Les résultats attendus sont Prêt, puis [INFO] Prêt. Ignorer le retour de withPrefix() ne configure pas $plain. Le préfixe est ici une valeur ; avec une dépendance objet, il faudrait pareillement conserver l'instance retournée. Le container peut le faire avec le troisième argument de addMethodCall() :

// Même class Label, autoload DI et imports du laboratoire précédent.
$labels = new ContainerBuilder();
$labels->register('label', Label::class)
    ->addMethodCall('withPrefix', ['[INFO] '], true)
    ->setPublic(true);
$labels->compile();
echo $labels->get('label')->render('Prêt'), "\n";

Résultat attendu : [INFO] Prêt. Avec false au troisième argument dans ce cas, le retour serait ignoré et l'objet initial garderait son préfixe vide. Ce booléen ne transforme pas un setter mutable en méthode immuable : la méthode doit réellement respecter ce contrat.

La propriété publique peut recevoir une valeur avec setProperty(), mais autorise aussi d'autres écritures sans passer par un setter contrôlé. Elle sert notamment à intégrer du code tiers qui impose ce modèle ; ce n'est pas le premier choix pour notre propre manager.

L'attribute #[Required], du namespace Symfony\Contracts\Service\Attribute, demande le traitement automatique des méthodes d'un service autowiré. L'autowiring est le câblage des dépendances à partir de leurs types. Sans lui, cet attribute seul ne programme pas l'appel ; un addMethodCall() explicite peut néanmoins appeler la méthode, avec ou sans attribute.

Pour reconnaître un wither automatiquement, Symfony 8.0 accepte le type de retour static ou un PHPDoc @return static. Le résultat est alors conservé ; le seul nom with... ne suffit pas. La forme PHPDoc @return $this désigne au contraire le cas non-clonant dans cette détection.

Enfin, deux dépendances de constructeur réciproques ordinaires et non lazy forment un cycle détecté par compile() avec ServiceCircularReferenceException. Un setter peut différer un lien et permettre l'assemblage, mais ne résout pas tous les cycles d'utilisation : il faut vérifier l'ordre et ne pas utiliser l'autre objet avant la fin de son initialisation. Un wither n'est pas un remplacement équivalent pour casser ce cycle ; les services lazy constituent un cas distinct.

🌍 In Real Life

La situation : un poste doit être équipé avant ouverture ; un accessoire optionnel peut arriver plus tard. Pour modifier une fiche sans toucher à l'original, on utilise une copie.

L’équivalent dans Symfony : équipement indispensable à l'ouverture → argument de constructeur requis ; ajout sur le poste existant → setter ; nouvelle fiche à conserver → objet retourné par un wither ; emplacement accessible directement → propriété publique.

Retour à la réalité technique : ces formes décrivent comment la dépendance arrive, pas quatre étapes obligatoires. Un setter facultatif exige un état initial utilisable. Le booléen de addMethodCall(..., true) conserve le retour, sans rendre la méthode immuable par magie. Un clone PHP ne clone pas récursivement tous les objets qu'il référence.

🧠 Comment le mémoriser : « Le setter change ici ; le wither rend ailleurs. » Image mentale : original et copie côte à côte. Question-réflexe : quel objet dois-je utiliser après cet appel ?

⚠️ À ne pas confondre : recevoir une dépendance au constructeur et rendre tout l'objet immuable ; un setter ne résout pas non plus tous les cycles d'utilisation.

Le component seul, ligne par ligne

À retenir en priorité
  1. La compilation fige la configuration.
  2. Les services restent ensuite accessibles selon leur visibilité.

Nous savons maintenant ce que le consommateur reçoit. Revenons au programme qui l'assemble : ContainerBuilder reçoit les instructions de construction, et compile() résout, vérifie et optimise leur graphe. Le flux normal ne consiste pas à demander tous les objets applicatifs. Cela n'interdit pas à du code de compilation personnalisé de créer ses propres objets.

Dans le framework, le kernel organise cette préparation et son cache. Avec le composant seul, notre programme charge l'autoload, enregistre les définitions et compile lui-même. Le laboratoire indépendant suivant garde Prefix et Greeting pour observer un résultat sans email ni Request. L'autoload de DependencyInjection 8.0 est supposé déjà chargé :

<?php
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;
final class Prefix { public function __construct(public string $value) {} }
final class Greeting
{
    public function __construct(private Prefix $prefix) {}
    public function text(): string { return $this->prefix->value.' Léa'; }
}
$container = new ContainerBuilder();
$container->register('prefix', Prefix::class)->addArgument('Bonjour');
$container->register('greeting', Greeting::class)
    ->addArgument(new Reference('prefix'))->setPublic(true);
$container->compile();
echo $container->get('greeting')->text(), "\n";

L'entrée 'Bonjour' devient la valeur de Prefix, puis Greeting reçoit cet objet ; la sortie attendue est Bonjour Léa. L'enregistrement ne déclenche pas l'affichage, et compile() n'appelle pas text(). Le résultat vient de la dernière ligne.

prefix reste privé mais injectable ; greeting est public parce que ce programme le récupère directement. addArgument('prefix') transmettrait une chaîne au lieu du Prefix requis. La définition décrit donc à la fois le bon type de donnée et le lien entre les services, sans demander à Greeting de consulter le container.

L'inlining incorpore, lorsque les optimisations le permettent, la définition privée dans celle du consommateur. L'objet reste fourni, même si son ancien identifiant n'est plus accessible directement. « Privé » ne veut donc pas dire « absent du comportement de l'application ».

Le kernel peut ensuite réutiliser une forme compilée et générée en PHP, mise en cache pour son environment. La présence et la fraîcheur du cache, notamment selon le mode debug, gouvernent la reconstruction. Un simple ContainerBuilder::compile() autonome ne crée pas à lui seul toute cette politique de fichiers et de démarrage.

Le composant s'utilise indépendamment du framework et fournit un container compatible PSR-11, le contrat de consultation des services. Dans nos laboratoires de services ordinaires, après compile() :

Appel Résultat
get() d'un service public l'object ; deux get() donnent la même instance, sauf setShared(false)
get() ou has() d'un service privé ServiceNotFoundException « …has been removed or inlined… » ; false
register() BadMethodCallException : « Adding definition to a compiled container is not allowed. »
setParameter() LogicException : « Impossible to call set() on a frozen ParameterBag. »
getParameter() fonctionne : figé, pas illisible

Le partage concerne les demandes au même container : répéter get('greeting') réutilise normalement l'instance. Il ne rend pas Greeting globalement unique dans tous les processus. Les exceptions de la table concernent l'ajout de définitions et la modification des paramètres figés ; lire getParameter() reste autorisé.

Si une référence obligatoire vise un service jamais déclaré, EXCEPTION_ON_INVALID_REFERENCE, comportement par défaut, fait échouer la compilation lorsque le consommateur est conservé. Un consommateur privé inutilisé peut être supprimé avant ce contrôle ; il ne suffit pas qu'une mauvaise référence ait figuré dans la configuration initiale.

Pour une variante ayant réellement un setter facultatif, la référence new Reference('mailer', ContainerInterface::IGNORE_ON_INVALID_REFERENCE) dans un addMethodCall() permet d'omettre cet appel si le service manque. Ici, ContainerInterface désigne celui de Symfony\Component\DependencyInjection, qui définit ces constantes, pas la seule interface PSR-11. NULL_ON_INVALID_REFERENCE transmettrait plutôt null : la signature et le comportement de la méthode doivent alors l'accepter. Ni l'un ni l'autre ne doit masquer l'absence du mailer indispensable de notre premier manager.

🌍 In Real Life

La situation : l'équipe vérifie le plan d'équipement avant le service ; ce contrôle n'exécute pas les gestes de cuisine.

L’équivalent dans Symfony : plan → définitions ; liens d'équipement → Reference ; vérification et optimisation du plan → compile() ; matériel effectivement fourni → obtention des services.

Retour à la réalité technique : compiler résout et transforme le graphe, sans appeler les méthodes métier ni construire systématiquement tous les services. Le programme autonome ne reçoit pas automatiquement la génération et le cache organisés par Kernel. Une référence obligatoire absente est jugée sur le graphe conservé ; ignorer un appel facultatif n'est pas lui passer null.

🧠 Comment le mémoriser : « Vérifier le plan n'exécute pas le travail. » Image mentale : un plan coché devant un poste encore inactif. Question-réflexe : suis-je dans la définition, la compilation ou l'utilisation ?

⚠️ À ne pas confondre : paramètres figés et illisibles ; getParameter() reste utilisable après compilation.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Required dépend de l'autowiring.
  2. L'attribute seul ne déclenche pas l'appel.
  • Voir l’explication : Recevoir le container ne révèle pas le besoin de mailer.

    Recevoir le container ne révèle pas le besoin de mailer. Sa réception est bien une injection ; les recherches qu'il permet cachent encore les collaborateurs métier. Le manager peut recevoir son mailer directement.

  • Voir l’explication : Le retour d'un wither compte.

    Le retour d'un wither compte. Les quatre formes incluent l'immutable-setter. Dans le laboratoire Label, utiliser l'original après withPrefix() ignore la configuration portée par le clone.

  • Voir l’explication : L'état utilisable gouverne le choix.

    L'état utilisable gouverne le choix. Mettre une dépendance indispensable dans un setter permet de construire un objet sans elle. À l'inverse, un constructeur peut accepter une option explicite : la recommandation n'est pas une interdiction PHP.

  • Voir l’explication : Required n'est pas un appel PHP automatique.

    Required n'est pas un appel PHP automatique. Son traitement dépend de l'autowiring. Un appel de méthode configuré explicitement reste possible sans lui ; une propriété non initialisée ne devient pas magiquement null. Pour un wither automatique, le type static ou le PHPDoc @return static indique de garder le retour.

  • Voir l’explication : Privé ne signifie pas non injectable.

    Privé ne signifie pas non injectable. Le mailer et le préfixe sont fournis à leurs consommateurs sans être publics. L'accès direct au container compilé est une autre question.

  • Voir l’explication : Figé ne signifie pas illisible ou objet métier immuable.

    Figé ne signifie pas illisible ou objet métier immuable. register() après compilation échoue avec BadMethodCallException, setParameter() avec LogicException. Le paramètre peut toujours être lu, et la mutabilité des services dépend de leur propre code.

  • Voir l’explication : Une erreur de référence se juge sur le graphe conservé.

    Une erreur de référence se juge sur le graphe conservé. Le consommateur public qui requiert un service inexistant échoue à la compilation. Un consommateur privé supprimé avant ce contrôle ne constitue pas le même scénario.

  • Voir l’explication : Un setter peut différer un lien, pas corriger toute architecture cyclique.

    Un setter peut différer un lien, pas corriger toute architecture cyclique. Le cycle de constructeurs ordinaires non lazy est détecté à la compilation. Après passage par un setter, l'ordre d'assemblage et les usages trop précoces doivent encore être vérifiés ; un wither n'a pas le même effet.

  • Voir l’explication : Une chaîne de caractères n'est pas une Reference.

    Une chaîne de caractères n'est pas une Reference. 'mailer' reste une valeur ; %mailer.transport% lit un paramètre ; new Reference('mailer') demande l'objet du service. Le type attendu par le consommateur permet d'expliquer le résultat.

Fiche express

À mémoriser

À retenir en priorité
  1. L'immutable setter rend un nouvel object.
  2. Ne pas le confondre avec un setter mutable.

Pour assembler les collaborateurs du blog :

  1. Rendre leurs besoins visibles, plutôt que leur fournir le container entier.
  2. Choisir parmi constructeur, immuable-setter, setter et propriété publique selon l'état dans lequel l'objet peut fonctionner.
  3. Conserver le retour d'un wither ; ne pas supposer qu'un setter sera toujours appelé ou qu'il résoudra tous les cycles.
  4. Distinguer Required traité par autowiring et appel explicitement configuré ; la détection du wither accepte static ou @return static.
  5. Séparer valeur, paramètre %x% et service Reference, puis respecter le type attendu par le constructeur ou la méthode.
  6. Garder les services privés sauf besoin d'accès direct ; la compilation interdit ensuite register() et setParameter(), pas la lecture.
  7. Interpréter les erreurs selon le graphe : référence obligatoire conservée, suppression des privés inutilisés, cycle non lazy et politique d'absence facultative ne sont pas un seul cas.

La commande Composer 2 historique illustre l'installation du composant dans un projet de laboratoire, pas une étape d'une Request :

composer require symfony/dependency-injection

Résultat attendu si la résolution réussit : la dépendance et son autoload sont disponibles. Cette commande sans contrainte explicite ne garantit pas Symfony 8.0 ; les contraintes du projet doivent préserver cette cible et PHP 8.4. Elle n'est pas exécutée ici. L'étape suivante est d'observer comment le container de l'application charge ces définitions, expose ses points d'entrée et réutilise son cache.
