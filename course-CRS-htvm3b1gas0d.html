Objectif

Comprendre ce que la dependency injection résout, distinguer recevoir un service et le demander au container, choisir la forme d'injection adaptée à une dependency, et savoir utiliser le component seul jusqu'à la compilation. Le container dans une application — definitions, visibilité, configuration — a sa propre page, Service container.

L'essentiel

À comprendre

À retenir en priorité
  1. La signature expose les dependencies.
  2. La récupération masque les besoins réels.

Une class reçoit ses dependencies au lieu de les fabriquer ou de les demander au container. Elle les reçoit par l'une des quatre formes d'injection, selon que la dependency est obligatoire ou facultative. Le component, autonome, décrit les services, puis les compile : un container figé, d'où l'on ne fait qu'un get(), à l'entry point.

Le schéma

À retenir en priorité
  1. Le kernel assemble l'application.
  2. Les services reçoivent leurs collaborators.

Le fil rouge : un `NewsletterManager` et son `Mailer`

À retenir en priorité
  1. Une string reste une valeur.
  2. Reference désigne un service.
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;

$container = new ContainerBuilder();
$container->setParameter('mailer.transport', 'sendmail');
$container->register('mailer', Mailer::class)
    ->addArgument('%mailer.transport%');                 // un parameter : une valeur
$container->register('newsletter_manager', NewsletterManager::class)
    ->addArgument(new Reference('mailer'))               // un service
    ->setPublic(true);                                   // privé par défaut
$container->compile();
$manager = $container->get('newsletter_manager');

addArgument('mailer') passerait la string 'mailer' : seul new Reference('mailer') désigne un service.

Injecter ou récupérer : la distinction de fond

À comprendre

À retenir en priorité
  1. Le container ne décrit pas les besoins précis.
  2. Préférer des arguments typés par collaborator.

C'est quoi ?

Une dépendance est un objet dont une classe a besoin pour travailler. L'injection consiste à fournir cet objet depuis l'extérieur. La récupération consiste à demander cet objet à un registre avec get(). Si l'on injecte le container, on injecte bien cet objet-là, mais les dépendances métier restent récupérées à l'intérieur : la signature ne les décrit plus.

À quoi ça sert ?

Recevoir directement Formatter permet de connaître le besoin de Receipt sans lire ses méthodes. Un test peut construire Receipt sans démarrer Symfony. À l'inverse, recevoir un container entier masque les services réellement nécessaires et reporte les erreurs de noms au chemin d'exécution qui les utilise.

Où dans Symfony ?

Le component DependencyInjection assemble les objets. Le code métier reçoit normalement les services, pas le container. Un point d'entrée de l'application peut récupérer l'objet principal ; un service locator, registre limité à une liste déclarée, est une solution distincte pour choisir une dépendance parmi plusieurs à l'exécution.

Comment, étape par étape ?

  1. Déclarer le besoin dans le constructeur.
  2. Construire la dépendance au point d'assemblage.
  3. La transmettre à l'objet consommateur.
  4. Utiliser la dépendance reçue sans connaître son identifiant dans le container.

Exemple concret PHP

Cet exemple est du PHP autonome, sans Symfony : il montre que l'injection est un principe, pas une méthode du framework.

<?php
final class Formatter
{
    public function format(int $cents): string
    {
        return number_format($cents / 100, 2, ',', ' ').' EUR';
    }
}
final class Receipt
{
    public function __construct(private Formatter $formatter) {}
    public function total(int $cents): string
    {
        return $this->formatter->format($cents);
    }
}
$receipt = new Receipt(new Formatter());
echo $receipt->total(1250), "\n";

La sortie est 12,50 EUR. Le constructeur rend la dépendance obligatoire ; il n'exécute pas le formatage. Contre-exemple : dans total(), appeler $this->container->get('formatter') cache le besoin et peut échouer seulement au premier reçu. Correction : recevoir Formatter, comme ici. L'injection ne dispense toutefois pas de choisir une interface lorsque plusieurs implémentations doivent être substituables.

Une class qui reçoit ContainerInterface et appelle get('mailer') ne fait pas de dependency injection : elle récupère. Le critère est ce qu'elle reçoit — un object qui fournit n'importe quoi —, pas le moyen.

Les quatre formes d'injection

À comprendre

À retenir en priorité
  1. Le constructor garantit l'état initial.
  2. Un setter convient aux dependencies facultatives.

C'est quoi ?

Le point d'injection est l'endroit où l'objet reçoit une dépendance :

  • Le constructeur la reçoit à la création : sans argument obligatoire, l'objet ne peut pas être construit.
  • Un setter est une méthode qui modifie l'objet après sa création. L'appel doit être prévu séparément.
  • Un immutable-setter, méthode de configuration immuable, retourne un nouvel objet ; ignorer le retour perd la modification.
  • Une propriété publique autorise l'affectation directe, mais expose aussi la dépendance aux remplacements arbitraires.

À quoi ça sert ?

Le constructeur convient à une dépendance indispensable. Un setter convient à une option lorsque le comportement sans cette option est réellement défini. « Facultatif » ne signifie pas « propriété typée laissée non initialisée puis utilisée sans contrôle ».

Où dans Symfony ?

Une définition DI peut fournir des arguments de constructeur, programmer des appels de méthodes ou affecter des propriétés. Pour un appel immuable, elle doit conserver l'objet retourné : addMethodCall() possède un troisième argument prévu à cet effet. #[Required] concerne le câblage d'un service autowiré ; PHP seul n'appelle pas une méthode parce qu'elle porte cet attribut.

Comment, étape par étape ?

  1. Décider si un objet utilisable peut exister sans la dépendance.
  2. Si non, choisir le constructeur et éviter un état partiellement initialisé.
  3. Si oui, définir explicitement le comportement par défaut.
  4. Avec une méthode immuable, réaffecter le résultat avant l'utilisation.

Exemple concret PHP

Le préfixe est ici une option simple pour isoler la différence entre mutation et copie ; le même contrat de retour s'applique à une dépendance objet.

<?php
final class Label
{
    public function __construct(private string $prefix = '') {}
    public function withPrefix(string $prefix): static
    {
        $copy = clone $this;
        $copy->prefix = $prefix;
        return $copy;
    }
    public function render(string $text): string
    {
        return $this->prefix.$text;
    }
}
$plain = new Label();
$marked = $plain->withPrefix('[INFO] ');
echo $plain->render('Prêt'), "\n";
echo $marked->render('Prêt'), "\n";

Les sorties sont Prêt, puis [INFO] Prêt. Contre-exemple : appeler $plain->withPrefix('[INFO] ') sans conserver le résultat ne configure pas $plain. Correction : utiliser l'objet retourné. Un setter peut différer une liaison circulaire, mais cela ne justifie pas automatiquement le cycle : il faut vérifier qu'aucune méthode n'utilise l'autre objet avant la fin de l'assemblage.

Les quatre formes d'injection

La dependency est… Forme Écriture avec le component
obligatoire constructor ->addArgument(new Reference('mailer'))
facultative, service immuable immutable-setter (withMailer() renvoie un clone) ->addMethodCall('withMailer', [...], true)
facultative setter ->addMethodCall('setMailer', [...])
imposée par du code tiers property publique — « mainly only disadvantages » ->setProperty('mailer', ...)
  • Le constructor garantit la présence et la stabilité ; le setter ne garantit ni l'appel ni la stabilité.
  • #[Required] (Symfony\Contracts\Service\Attribute) n'agit que sur un service autowiré ; l'autowiring n'appelle pas un setter qui ne le porte pas. Un immutable-setter autowiré doit renvoyer static, sinon son résultat est jeté.
  • Deux constructors qui se reçoivent mutuellement : compile() lève ServiceCircularReferenceException. Un setter d'un côté casse le cycle ; un immutable-setter, non.

Le component seul, ligne par ligne

À comprendre

À retenir en priorité
  1. La compilation fige la configuration.
  2. Les services restent ensuite accessibles selon leur visibilité.

C'est quoi ?

DependencyInjection est une bibliothèque autonome : elle peut construire des services sans application HTTP, bundle ou controller. ContainerBuilder reçoit des définitions, c'est-à-dire des instructions de construction. compile() vérifie et transforme ce graphe de dépendances avant son utilisation.

À quoi ça sert ?

La compilation détecte notamment une référence obligatoire vers un service absent. Elle permet aussi de retirer ou d'intégrer dans leurs consommateurs les services privés inutilisés comme points d'accès. Compiler n'est pas demander tous les objets : la construction ordinaire reste déclenchée par leur utilisation.

Où dans Symfony ?

Dans le framework, le kernel organise cette préparation et la mise en cache du container. Avec le component seul, le programme doit enregistrer les définitions et appeler compile() lui-même. Il doit également charger l'autoload Composer ; l'extrait suppose cet autoload déjà chargé pour DependencyInjection 8.0.

Comment, étape par étape ?

  1. Enregistrer une classe sous un identifiant.
  2. Donner des valeurs scalaires ou des Reference vers d'autres services.
  3. Exposer uniquement le point d'entrée nécessaire avec setPublic(true).
  4. Compiler, puis récupérer ce point d'entrée.
  5. Ne plus modifier les définitions ni les paramètres figés après compilation.

Exemple concret PHP

<?php
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;
final class Prefix { public function __construct(public string $value) {} }
final class Greeting
{
    public function __construct(private Prefix $prefix) {}
    public function text(): string { return $this->prefix->value.' Léa'; }
}
$container = new ContainerBuilder();
$container->register('prefix', Prefix::class)->addArgument('Bonjour');
$container->register('greeting', Greeting::class)
    ->addArgument(new Reference('prefix'))->setPublic(true);
$container->compile();
echo $container->get('greeting')->text(), "\n";

La sortie attendue est Bonjour Léa. prefix reste privé mais est injectable ; seul greeting doit être récupéré directement. Contre-exemple : addArgument('prefix') transmet une chaîne, pas le service ; le constructeur attend pourtant Prefix. Correction : utiliser new Reference('prefix'). Une référence facultative doit être décidée explicitement : ignorer un appel de setter si le service manque n'est pas la même chose que lui passer null.

Passage canonique conservé

Le component seul, ligne par ligne

symfony/dependency-injection s'installe seul et fournit un container PSR-11. Après compile() :

Appel Résultat
get() d'un service public l'object ; deux get() donnent la même instance, sauf setShared(false)
get() ou has() d'un service privé ServiceNotFoundException « …has been removed or inlined… » ; false
register() BadMethodCallException : « Adding definition to a compiled container is not allowed. »
setParameter() LogicException : « Impossible to call set() on a frozen ParameterBag. »
getParameter() fonctionne : figé, pas illisible
  • Une référence vers un service jamais déclaré fait échouer la compilation (« …has a dependency on a non-existent service "mailer" ») : c'est EXCEPTION_ON_INVALID_REFERENCE, le défaut.
  • new Reference('mailer', ContainerInterface::IGNORE_ON_INVALID_REFERENCE) dans un addMethodCall() : l'appel est omis si le service manque. NULL_ON_INVALID_REFERENCE passerait null.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Required dépend de l'autowiring.
  2. L'attribute seul ne déclenche pas l'appel.
  • Distinguer injection de dépendances et recherche de services

    « Le container est injecté, donc c'est de la dependency injection. » Faux. Le critère est ce que la class reçoit, pas la façon dont elle le reçoit. Une class qui reçoit le container et appelle get() fait de la récupération de services, et ses dependencies réelles ont disparu de sa signature.

  • Reconnaître les quatre formes d’injection

    « Il existe trois formes d'injection. » La documentation 8.0 en décrit quatre : constructor, immutable-setter, setter et property. Un énoncé qui présente l'immutable-setter (une method withX() qui renvoie un clone) comme une invention ou une mauvaise pratique se trompe.

  • Voir l’explication : Constructor et setter inversés.

    Constructor et setter inversés. Le constructor est la voie normale, pour la dependency obligatoire ; le setter est réservé à la dependency facultative (ou à un cycle). Un choix qui met une dependency indispensable dans un setter crée un object qui peut exister sans elle.

  • Voir l’explication : #[Required] sans autowiring.

    #[Required] sans autowiring. L'attribute seul ne fait rien : sur un service non autowiré, le setter n'est jamais appelé et la property reste null. À l'inverse, l'autowiring n'appelle pas un setter qui n'a pas #[Required].

  • Voir l’explication : Un service privé n'est pas « non injectable ».

    Un service privé n'est pas « non injectable ». Privé interdit seulement le get() après compilation ; le service reste injectable dans les autres. Et c'est le défaut : un register() sans setPublic(true) donne un service privé.

  • Voir l’explication : compile() fige.

    compile() fige. Après compilation, ni nouvelle definition ni nouveau parameter : register() lève une BadMethodCallException, setParameter() une LogicException. Lire un parameter reste possible.

  • Voir l’explication : Une référence absente casse compile(), pas get().

    Une référence absente casse compile(), pas get(). Par défaut, un service qui référence un service inexistant fait échouer la compilation, même si personne ne demande jamais ce service.

  • Voir l’explication : Un cycle entre deux constructors aussi.

    Un cycle entre deux constructors aussi. Deux services qui se reçoivent mutuellement par leur constructor lèvent ServiceCircularReferenceException dès compile(), pas au premier appel. Un setter d'un côté suffit à le casser.

  • Voir l’explication : addArgument('mailer') n'injecte pas le service mailer.

    addArgument('mailer') n'injecte pas le service mailer. C'est la string 'mailer' qui part dans le constructor. Pour un service, il faut new Reference('mailer').

Fiche express

À mémoriser

À retenir en priorité
  1. L'immutable setter rend un nouvel object.
  2. Ne pas le confondre avec un setter mutable.

Si tu dois retenir seulement 7 choses :

  • Recevoir le container n'est pas de l'injection : un seul get(), à l'entry point.
  • Quatre formes : constructor, immutable-setter, setter, property.
  • Obligatoire → constructor. Facultative → setter. Un cycle se casse par un setter.
  • #[Required] n'agit que sur un service autowiré.
  • Reference = un service ; %x% = un parameter ; sinon une string.
  • Service privé par défaut ; compile() fige (ni register() ni setParameter()).
  • Référence absente ou cycle : compile() échoue, pas get().

Moyen mnémotechnique : « C-I-S-P : Constructor, Immuable, Setter, Public », de la plus sûre à la moins sûre.
