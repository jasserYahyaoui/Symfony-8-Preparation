Objectif

Intervenir autour de l'exécution d'une command sans la modifier : journaliser, mesurer, empêcher, rattraper une erreur.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le component autonome ne l'ajoute pas implicitement.
  2. FrameworkBundle fournit cette intégration.

La Console dispatche des events autour de chaque command — avant (COMMAND), en cas d'erreur (ERROR), après (TERMINATE), à un signal (SIGNAL) — mais seulement si l'Application a un dispatcher. TERMINATE est toujours atteint, et l'exit code final est celui qu'il porte.

Le schéma

À retenir en priorité
  1. L'erreur possède son event.
  2. La fin du cycle peut ajuster l'exit code.

L'exemple : journaliser chaque command

▣ Exemple concret

À retenir en priorité
  1. La mesure se termine après le traitement.
  2. Le listener peut aussi lire l'exit code.
class CommandLogger implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [ConsoleEvents::TERMINATE => 'onTerminate'];
    }

    public function onTerminate(ConsoleTerminateEvent $event): void
    {
        $this->logger->info($event->getCommand()?->getName().' → '.$event->getExitCode());
    }
}

Quatre constantes, cinq events

À retenir en priorité
  1. Les constantes usuelles ne couvrent pas tous les events.
  2. L'alarme possède sa class.
Constante Valeur Quand
COMMAND console.command avant l'exécution
SIGNAL console.signal à la réception d'un signal POSIX
ERROR console.error une exception ou une erreur est remontée
TERMINATE console.terminate après l'exécution, quoi qu'il arrive

ConsoleEvents déclare aussi une cinquième constante, ALIASES, qui associe chaque class d'event à son nom. Un cinquième event, ConsoleAlarmEvent, n'a pas de constante. FrameworkBundle donne un dispatcher à l'Application ; construite à la main, elle ne dispatche rien sans setDispatcher().

L'ordre réel

À retenir en priorité
  1. Désactivé n'est ni succès ni échec ordinaire.
  2. L'exécution de la command est sautée.
Cas Events Code
succès COMMAND, exécution, TERMINATE:0 0
disableCommand() sur COMMAND COMMAND, TERMINATE:113 — pas d'exécution 113
exception COMMAND, exécution, ERROR, TERMINATE:1 1
exception, setExitCode(0) sur ERROR … ERROR, TERMINATE:0 0
succès, setExitCode(1) sur TERMINATE … TERMINATE:0 1
exception, sans dispatcher exécution seule 1
  • ConsoleCommandEvent::RETURN_CODE_DISABLED vaut 113 : « refusée », pas « échouée ».
  • TERMINATE est le seul endroit fiable pour libérer une ressource ou mesurer une durée.

`ERROR` — rattraper

À retenir en priorité
  1. Le listener peut transformer le résultat.
  2. Ce choix ne doit pas masquer un échec involontairement.

ConsoleErrorEvent : getError(), setError(), setExitCode(). setExitCode(0) fait abandonner l'erreur : l'exception n'est pas propagée. ERROR couvre tout Throwable : une TypeError déclenche ERROR puis TERMINATE, et n'est relancée qu'ensuite.

`SIGNAL` — pendant

À retenir en priorité
  1. Le signal peut être intercepté.
  2. L'absence de sortie doit être demandée explicitement.

Avec un dispatcher, l'Application intercepte SIGINT, SIGQUIT, SIGTERM, SIGUSR1, SIGUSR2 et SIGALRM. Ordre : SIGNAL, puis handleSignal() d'une SignalableCommandInterface, puis TERMINATE et exit().

Situation Résultat
aucun listener ne change le code sortie en code 0, getInterruptingSignal() = 2
abortExit() sur SIGNAL, ou handleSignal() rend false la command continue
setExitCode(3) sur SIGNAL sortie en code 3
ni dispatcher ni command signalable PHP meurt du signal

L'alarme

À retenir en priorité
  1. Les alarmes reposent sur les signaux POSIX.
  2. Le comportement dépend de la plateforme disponible.

Application::setAlarmInterval(10) programme un SIGALRM toutes les 10 s, qui dispatche SIGNAL puis ConsoleAlarmEvent sous son nom de class. Sans abortExit() dans un listener, la première alarme termine la command. Il faut l'extension pcntl.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le test direct contourne le cycle Application.
  2. Adapter le test à la frontière vérifiée.
  • Voir l’explication : Quatre constantes, cinq events.

    Quatre constantes, cinq events. ConsoleAlarmEvent n'a pas de constante ; il n'existe pas d'event « après configure() ».

  • Voir l’explication : Un signal intercepté sort en code 0

    Un signal intercepté sort en code 0 si personne ne le change.

  • Voir l’explication : TERMINATE est dispatché même après une erreur

    TERMINATE est dispatché même après une erreur — c'est sa raison d'être.

  • Voir l’explication : disableCommand() produit le code 113

    disableCommand() produit le code 113, pas 0 ni 1 — et TERMINATE est quand même dispatché.

  • Voir l’explication : setExitCode(0) sur ERROR avale l'exception

    setExitCode(0) sur ERROR avale l'exception au lieu de la laisser remonter.

  • Voir l’explication : Pas de dispatcher, pas d'events

    Pas de dispatcher, pas d'events : une Application autonome est muette.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. La command ne fixe pas toujours seule le code final.
  2. Les listeners peuvent le modifier.

Si tu dois retenir seulement 7 choses :

  • Quatre constantes (COMMAND, SIGNAL, ERROR, TERMINATE), cinq events avec ConsoleAlarmEvent.
  • Pas de dispatcher, pas d'events.
  • TERMINATE est toujours dispatché ; son code est le code final.
  • disableCommand() → 113.
  • setExitCode(0) sur ERROR avale l'exception.
  • Un signal intercepté sort en 0, sauf abortExit() ou un autre code.
  • setAlarmInterval() : la première alarme termine, sans abortExit().

Moyen mnémotechnique : « Avant, erreur, après — et toujours après ».
