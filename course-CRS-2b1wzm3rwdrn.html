Objectif

Choisir une route selon l'hôte demandé, par exemple séparer le site principal du site mobile tout en gardant le même chemin /. Le nom d'hôte est un critère de routage, pas une autorisation d'accès.

L'essentiel

À comprendre

À retenir en priorité
  1. Sans option host, une route accepte tous les hosts.
  2. Une route générale peut masquer une route restreinte.

L'option host fait dépendre une route du nom de host ; sans elle, tout host correspond. Le host prend des parameters, avec defaults et requirements ordinaires — mais une default value de host ne rend rien facultatif : elle ne sert qu'à la génération. La comparaison ignore la casse. À schéma inchangé, path() vers un autre host produit //hôte/… ; si la route impose un autre schéma, le générateur doit produire une URL absolue.

Le schéma

À retenir en priorité
  1. Le changement de host exige une autorité dans le lien.
  2. url() produit une URL absolue complète.

Dans ces vues, bleu = entrée, ambre = choix, vert = résultat ; les flèches décrivent les effets de configuration. L'hôte doit aussi être accepté par la configuration de confiance de l'application. Les exemples de génération supposent la vérification stricte des requirements et aucun changement de schéma.

L'exemple : un site mobile

Exemple concret

Le blog peut avoir une entrée mobile et une entrée principale au même chemin. Les signatures ci-dessous isolent leur sélection, sans corps d'action exécutable. Le sous-domaine différencie la destination ; il n'authentifie pas le lecteur et ne lui accorde aucun droit sur l'article.

#[Route(
    '/',
    name: 'mobile_homepage',
    host: '{subdomain}.example.com',
    defaults: ['subdomain' => 'm'],
    requirements: ['subdomain' => 'm|mobile'],
)]
public function mobileHomepage(): Response {}

#[Route('/', name: 'homepage')]   // après : sans host, elle capte tout
public function homepage(): Response {}

L'option `host`

Pour deux visites de /blog/42 sur des hôtes différents, le chemin seul ne suffit plus à choisir la route. Le matcher vérifie aussi le host configuré, à l'intérieur des hôtes que l'application accepte comme fiables. Une route sans cette restriction reste une candidate générale : son ordre peut donc masquer la route spécialisée.

Elle exige que le host de la Request corresponde. Deux routes peuvent ainsi partager le même path et ne différer que par le host ; sans host, une route accepte n'importe quel host. La comparaison ignore la casse : le matcher met le host en minuscules, et l'expression compilée porte le drapeau i. Un requirement EN|FR accepte en.example.com, et l'attribute vaut en (test testHostIsCaseInsensitive).

🌍 In Real Life

La situation : deux restaurants possèdent chacun une table 42. Pour orienter la réservation, il faut connaître l'établissement, pas seulement le numéro de table.

L’équivalent dans Symfony : host ajoute un critère au matching du chemin. Deux routes peuvent viser le même path sur des hôtes différents ; une route sans restriction de host peut aussi correspondre et masquer une route spécialisée placée après elle.

Retour à la réalité technique : toutes les autres conditions de route restent applicables. La comparaison d'hôte ignore la casse. Cette sélection ne configure ni le DNS ni le serveur web et n'accorde aucun droit ; la confiance dans l'hôte reçu relève également de la configuration de l'application.

🧠 Comment le mémoriser : « Même table, pas forcément même restaurant. » Image mentale : deux façades portant chacune une table 42. Question-réflexe : ai-je vérifié l'hôte, le chemin et l'ordre des routes candidates ?

⚠️ À ne pas confondre : host de routage, hôte de confiance et autorisation d'accès.

Deux bâtiments peuvent avoir chacun une salle 101. Vers l'autre bâtiment, le lien doit nommer le host ; avec path(), cela peut être //autre.example/101, sans forcer une URL avec schéma explicite.

Question: What can path() return when the route has a different host?

Answer: A scheme-relative network path such as //m.example.com/.

Le host accepte des parameters

À retenir en priorité
  1. Les placeholders de host utilisent defaults et requirements.
  2. Ils rejoignent les mêmes attributes que ceux du path.

Avec {subdomain}.example.com, le matcher capture par exemple m et RouterListener le dépose dans les attributs, comme id='42' pour le chemin. L'ArgumentResolver peut ensuite fournir un argument homonyme. Cette capture ne désigne pas automatiquement un service, un compte ou un tenant autorisé.

Comme un path : defaults et requirements sont les mêmes options, sans key séparée pour le host. Le parameter apparié est disponible en attribute de Request et en argument de controller.

🌍 In Real Life

La situation : une adresse comporte une case variable « établissement ». Lire cette case fournit un nom ; cela ne vérifie pas que le visiteur appartient à cet établissement.

L’équivalent dans Symfony : {subdomain} capture une partie du host selon ses requirements. Le résultat rejoint les attributes de Request via l'intégration de routage ; la résolution des arguments peut ensuite fournir cette valeur au contrôleur.

Retour à la réalité technique : defaults et requirements utilisent les mêmes options que les variables de chemin. La capture n'est ni un service, ni une entité chargée, ni un tenant autorisé. Toute sélection métier ou vérification d'appartenance reste explicite.

🧠 Comment le mémoriser : « Lire le nom sur la porte ne délivre pas une clé. » Image mentale : nom d'établissement relevé sur une fiche, clé encore absente. Question-réflexe : ai-je seulement capturé une chaîne ou réellement vérifié le contexte métier ?

⚠️ À ne pas confondre : capture du host, valeur d'argument et contrôle d'accès au tenant.

Repère — Une default value de host ne rend rien facultatif :

Question: Does a host placeholder default make its subdomain optional when matching?

Answer: No. It supplies a generation default, not an optional host segment.

Un host parameter reste obligatoire au matching. Le défaut évite de le répéter lors de la génération.

Une default value de host ne rend rien facultatif

À retenir en priorité
  1. Un host parameter reste obligatoire au matching.
  2. Le défaut évite de le répéter lors de la génération.

Le lien vers le mobile peut omettre subdomain grâce au défaut m, mais une requête reçue sur example.com ne contient aucun sous-domaine à capturer. Le compilateur ne rend pas cette partie facultative comme un suffixe de path : la même configuration a donc des effets différents en lecture et en génération.

Dans RouteCompiler, le calcul du premier parameter facultatif n'est fait que pour le path : un parameter de host est toujours exigé à l'appariement. Avec l'exemple, une Request vers example.com ne correspond pas à mobile_homepage, malgré la default value m. Celle-ci sert à la génération, pour ne pas fournir subdomain à chaque URL.

🌍 In Real Life

La situation : l'imprimeur connaît l'établissement habituel et complète son nom sur les invitations. Cela ne transforme pas une enveloppe reçue sans ce nom en courrier adressé à cet établissement.

L’équivalent dans Symfony : le défaut subdomain=m peut compléter l'URL générée pour {subdomain}.example.com. Il ne permet pas à example.com de correspondre au motif qui exige le sous-domaine.

Retour à la réalité technique : le compilateur ne rend pas les variables de host facultatives comme certains suffixes de chemin. Le défaut facilite la génération ; le matching reste lié à la structure réellement reçue. Une autre route peut cependant accepter l'hôte sans sous-domaine.

🧠 Comment le mémoriser : « Compléter à l'impression n'est pas compléter à la réception. » Image mentale : nom ajouté sur l'invitation, case manquante sur le courrier entrant. Question-réflexe : suis-je en train de générer un lien ou de reconnaître une requête ?

⚠️ À ne pas confondre : défaut de host pour la génération et paramètre de chemin facultatif.

Générer vers un autre host

Depuis la page principale, / ne pourrait pas désigner l'accueil mobile : le navigateur resterait sur son hôte actuel. Le générateur élargit donc la référence à //m.example.com/ lorsque le schéma peut rester inchangé. Pour l'email du blog, demande une URL complète, indépendante du document où elle sera ouverte.

Quand le host de la route diffère de celui de la Request courante, UrlGenerator bascule de ABSOLUTE_PATH vers NETWORK_PATH :

Request courante path('mobile_homepage')
m.example.com /
www.example.com //m.example.com/

Le résultat est relatif au schéma ; url() demande l'URL absolue complète. Si schemes impose un autre schéma que le contexte, même path() produit une URL absolue pour pouvoir l'indiquer. Le requirement du host est vérifié à la génération lorsque cette vérification est activée ; en mode strict (cas des exemples), sa violation lève InvalidParameterException.

🌍 In Real Life

La situation : « allez à l'accueil » suffit à l'intérieur du restaurant actuel. Pour aller dans un autre établissement, il faut préciser lequel ; pour une invitation extérieure, il faut une adresse complète.

L’équivalent dans Symfony : à schéma inchangé, une génération demandant un chemin vers un autre host doit inclure cet hôte sous forme //hôte/…. url() demande une URL absolue ; un changement de schéma imposé exige également de l'indiquer explicitement.

Retour à la réalité technique : la forme dépend du contexte de génération et des contraintes de route, pas seulement du nom path(). Les requirements sont contrôlés selon la politique active ; en mode strict, une valeur invalide lève. Générer ne crée pas de navigation ni de résolution DNS.

🧠 Comment le mémoriser : « Changer d'établissement exige de le nommer. » Image mentale : flèche locale remplacée par une adresse d'autre restaurant. Question-réflexe : la cible change-t-elle d'hôte, de schéma, ou des deux ?

⚠️ À ne pas confondre : référence réseau relative au schéma et URL absolue complète.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Sans requirement de host, une route accepte n'importe quel host.

    Sans requirement de host, une route accepte n'importe quel host. L'absence de l'option n'est pas une restriction implicite au domain principal.

  • Voir l’explication : Une default value de host ne sert qu'à la génération.

    Une default value de host ne sert qu'à la génération. Contrairement au path, elle ne rend pas le parameter facultatif à l'appariement.

  • Voir l’explication : path() vers un autre host donne //hôte/chemin si le schéma reste le même.

    path() vers un autre host donne //hôte/chemin si le schéma reste le même. Un changement de schéma imposé par la route exige une URL absolue.

  • Voir l’explication : Le host ignore la casse

    Le host ignore la casse, requirement compris.

  • Voir l’explication : Deux routes peuvent partager le même path

    Deux routes peuvent partager le même path et ne se distinguer que par le host : la route sans host doit donc venir après celle qui en a un, sinon elle capte toutes les Requests.

Application

À retenir en priorité
  1. Le changement de host exige une autorité dans le lien.
  2. url() produit une URL absolue complète.
  3. Les placeholders de host utilisent defaults et requirements.
  4. Ils rejoignent les mêmes attributes que ceux du path.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Sans host → n'importe quel host.
  • Host comparé sans casse ; valeur appariée en minuscules.
  • Parameters de host : defaults et requirements ordinaires.
  • Default value de host : génération seulement, jamais facultative au match.
  • path() vers un autre host → //hôte/… à schéma inchangé ; schéma imposé différent → absolue ; url() demande une URL absolue.
  • Route sans host après celle qui en a un.

Moyen mnémotechnique : « Le défaut du host ne sert qu'à écrire ».
