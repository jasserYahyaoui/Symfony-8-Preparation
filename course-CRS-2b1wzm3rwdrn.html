Objectifs d’apprentissage

  • Contraindre une route à un nom de host

Objectif

Choisir une route selon l'hôte demandé, par exemple séparer le site principal du site mobile tout en gardant le même chemin /. Le nom d'hôte est un critère de routage, pas une autorisation d'accès.

L'essentiel

À comprendre

À retenir en priorité
  1. Sans option host, une route accepte tous les hosts.
  2. Une route générale peut masquer une route restreinte.

L'option host fait dépendre une route du nom de host ; sans elle, tout host correspond. Le host prend des parameters, avec defaults et requirements ordinaires — mais une default value de host ne rend rien facultatif : elle ne sert qu'à la génération. La comparaison ignore la casse. À schéma inchangé, path() vers un autre host produit //hôte/… ; si la route impose un autre schéma, le générateur doit produire une URL absolue.

Le schéma

À retenir en priorité
  1. Le changement de host exige une autorité dans le lien.
  2. url() produit une URL absolue complète.

Dans ces vues, bleu = entrée, ambre = choix, vert = résultat ; les flèches décrivent les effets de configuration. L'hôte doit aussi être accepté par la configuration de confiance de l'application. Les exemples de génération supposent la vérification stricte des requirements et aucun changement de schéma.

L'exemple : un site mobile

Exemple concret

class Examplee20ca559
{
    #[Route(
        '/',
        name: 'mobile_homepage',
        host: '{subdomain}.example.com',
        defaults: ['subdomain' => 'm'],
        requirements: ['subdomain' => 'm|mobile'],
    )]
    public function mobileHomepage(): Response {}

    #[Route('/', name: 'homepage')]   // après : sans host, elle capte tout
    public function homepage(): Response {}
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

L'option `host`

Elle exige que le host de la Request corresponde. Deux routes peuvent ainsi partager le même path et ne différer que par le host ; sans host, une route accepte n'importe quel host. La comparaison ignore la casse : le matcher met le host en minuscules, et l'expression compilée porte le drapeau i. Un requirement EN|FR accepte en.example.com, et l'attribute vaut en (test testHostIsCaseInsensitive).

Deux bâtiments peuvent avoir chacun une salle 101. Vers l'autre bâtiment, le lien doit nommer le host ; avec path(), cela peut être //autre.example/101, sans forcer une URL avec schéma explicite.

Repère — Générer vers un autre host : A scheme-relative network path such as //m.example.com/. Le changement de host exige une autorité dans le lien. url() produit une URL absolue complète.

Le host accepte des parameters

À comprendre

À retenir en priorité
  1. Les placeholders de host utilisent defaults et requirements.
  2. Ils rejoignent les mêmes attributes que ceux du path.

C'est quoi ?

Le host, nom d'hôte, est la partie de l'adresse qui identifie le serveur, sans le schéma ni le chemin. L'option host d'une route peut contenir des paramètres, tout comme son path. Une valeur extraite du host devient un attribute de la Request et peut être fournie à l'action par son nom.

À quoi ça sert ?

Plusieurs sites peuvent partager le même chemin / tout en utilisant des routes différentes selon leur hôte. Un paramètre de sous-domaine peut sélectionner une variante linguistique ou une zone de l'application. Cette sélection n'est pas une autorisation d'accès à des données sensibles.

Où dans Symfony ?

Les mêmes options defaults et requirements servent aux paramètres du host : il n'existe pas un second dictionnaire indépendant à inventer. Sans option host, une route ne restreint pas l'hôte. Le matching du host est insensible à la casse ; les contraintes et la valeur observée doivent être comprises dans ce contexte normalisé.

Comment, étape par étape ?

  1. Définir le modèle d'hôte réellement desservi par l'infrastructure.
  2. Restreindre les paramètres aux variantes acceptées.
  3. Faire correspondre le nom du paramètre à celui utilisé par l'action.
  4. Pour tester, fournir aussi le host au matcher ou à la commande de diagnostic : tester seulement le path laisse de côté la condition essentielle.

Exemple concret YAML

localized_home:
    path: /
    host: '{language}.example.test'
    controller: App\Controller\HomeController::index
    requirements:
        language: 'fr|en'

La requête vers fr.example.test/ fournit language égal à fr ; de.example.test/ ne correspond pas à cette route. Contre-exemple : définir uniquement une route plus générale sur / avant celle-ci et s'attendre à ce que le host rende automatiquement la route localisée prioritaire. Correction : maîtriser aussi l'ordre et les restrictions de la route générale. Pour générer une URL de cette route, fournir language ou un défaut valide ; un host différent du contexte courant peut conduire à une URL complète plutôt qu'à un simple chemin.

Passage canonique conservé

Comme un path : defaults et requirements sont les mêmes options, sans key séparée pour le host. Le parameter apparié est disponible en attribute de Request et en argument de controller.

Repère — Une default value de host ne rend rien facultatif : No. It supplies a generation default, not an optional host segment. Un host parameter reste obligatoire au matching. Le défaut évite de le répéter lors de la génération.

Une default value de host ne rend rien facultatif

À retenir en priorité
  1. Un host parameter reste obligatoire au matching.
  2. Le défaut évite de le répéter lors de la génération.

Dans RouteCompiler, le calcul du premier parameter facultatif n'est fait que pour le path : un parameter de host est toujours exigé à l'appariement. Avec l'exemple, une Request vers example.com ne correspond pas à mobile_homepage, malgré la default value m. Celle-ci sert à la génération, pour ne pas fournir subdomain à chaque URL.

Générer vers un autre host

Quand le host de la route diffère de celui de la Request courante, UrlGenerator bascule de ABSOLUTE_PATH vers NETWORK_PATH :

Request courante path('mobile_homepage')
m.example.com /
www.example.com //m.example.com/

Le résultat est relatif au schéma ; url() demande l'URL absolue complète. Si schemes impose un autre schéma que le contexte, même path() produit une URL absolue pour pouvoir l'indiquer. Le requirement du host est vérifié à la génération lorsque cette vérification est activée ; en mode strict (cas des exemples), sa violation lève InvalidParameterException.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Sans requirement de host, une route accepte n'importe quel host.

    Sans requirement de host, une route accepte n'importe quel host. L'absence de l'option n'est pas une restriction implicite au domain principal.

  • Voir l’explication : Une default value de host ne sert qu'à la génération.

    Une default value de host ne sert qu'à la génération. Contrairement au path, elle ne rend pas le parameter facultatif à l'appariement.

  • Voir l’explication : path() vers un autre host donne //hôte/chemin si le schéma reste le même.

    path() vers un autre host donne //hôte/chemin si le schéma reste le même. Un changement de schéma imposé par la route exige une URL absolue.

  • Voir l’explication : Le host ignore la casse

    Le host ignore la casse, requirement compris.

  • Voir l’explication : Deux routes peuvent partager le même path

    Deux routes peuvent partager le même path et ne se distinguer que par le host : la route sans host doit donc venir après celle qui en a un, sinon elle capte toutes les Requests.

Application

À retenir en priorité
  1. Le changement de host exige une autorité dans le lien.
  2. url() produit une URL absolue complète.
  3. Les placeholders de host utilisent defaults et requirements.
  4. Ils rejoignent les mêmes attributes que ceux du path.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Sans host → n'importe quel host.
  • Host comparé sans casse ; valeur appariée en minuscules.
  • Parameters de host : defaults et requirements ordinaires.
  • Default value de host : génération seulement, jamais facultative au match.
  • path() vers un autre host → //hôte/… à schéma inchangé ; schéma imposé différent → absolue ; url() demande une URL absolue.
  • Route sans host après celle qui en a un.

Moyen mnémotechnique : « Le défaut du host ne sert qu'à écrire ».
