Objectif

Déclarer et contraindre les options d'un form type. Le component sert partout où une class accepte un array d'options, pas seulement dans les forms.

L'essentiel

À comprendre

À retenir en priorité
  1. Le type Options signale une dépendance aux options résolues.
  2. L'ordre de déclaration ne commande pas l'ordre de résolution.

OptionsResolver remplace un array d'options brut par une déclaration : quelles options existent, lesquelles sont requises, leurs défauts, leurs types et valeurs permis. Une faute de frappe lève une exception au lieu de passer en silence. C'est le mécanisme de configureOptions() dans un form type.

Le schéma

À retenir en priorité
  1. Une option définie peut rester absente du résultat.
  2. Une option requise avec défaut n'est plus manquante.

L'exemple : `PriceType`

Exemple concret

class Examplee27157ce
{
    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['decimals' => 2, 'currency' => 'EUR']);
        $resolver->setRequired('vat_rate');
        $resolver->setAllowedTypes('decimals', 'int');
        $resolver->setAllowedValues('currency', ['EUR', 'USD']);
        $resolver->setDefault('label', function (Options $options) {
            return 'Prix (' . $options['currency'] . ')';
        });
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Les options déclarées sont celles que ->add() accepte pour ce type ; elles arrivent dans $options de buildForm().

Le problème résolu

À retenir en priorité
  1. Les options admises sont déclarées explicitement.
  2. Une faute de nom ne doit pas être ignorée.

Une option inconnue lève UndefinedOptionsException, qui liste les options définies : « The option "b" does not exist. Defined options are: "a", "c". ».

Les methods

À comprendre

C'est quoi ?

Déclarer une option peut signifier trois choses distinctes : setDefaults lui donne une valeur de repli ; setDefined autorise son nom sans inventer de valeur ; setRequired exige une valeur résolue, fournie par l'appelant ou par un défaut.

À quoi ça sert ?

Une option facultative absente ne doit pas toujours devenir null. Le résultat peut volontairement ne pas contenir sa clé, alors qu'une option obligatoire doit signaler une configuration incomplète. Les noms inconnus sont refusés pour révéler les fautes plutôt que les ignorer.

Où dans Symfony ?

resolve réalise le contrôle. Une option non déclarée provoque UndefinedOptionsException ; une option requise sans valeur ni défaut provoque MissingOptionsException. Ajouter un défaut à une option requise la laisse requise au sens de la déclaration, mais elle n'est plus manquante.

Comment, étape par étape ?

  1. Distinguer défaut, permission et obligation.
  2. Déclarer les types et valeurs admis si nécessaire.
  3. Résoudre un tableau concret.
  4. Vérifier séparément option absente, obligatoire manquante et nom inconnu.

Exemple concret PHP

Avec OptionsResolver chargé :

<?php
use Symfony\Component\OptionsResolver\OptionsResolver;
$resolver = new OptionsResolver();
$resolver->setDefaults(['enabled' => true]);
$resolver->setDefined('note');
$resolver->setRequired('recipient');
$options = $resolver->resolve(['recipient' => 'Ada']);
var_export($options);
var_dump(array_key_exists('note', $options));

Le résultat contient enabled égal à true et recipient égal à Ada ; note est absente et le dernier résultat vaut false. Contre-exemple : résoudre un tableau vide en pensant que required crée une valeur : recipient manque et une exception est levée. Correction : fournir recipient ou choisir un défaut légitime. Une faute recipent est un nom inconnu, pas une autre manière de satisfaire recipient ; ne pas supprimer ce contrôle pour cacher l'erreur.

Passage canonique conservé

Les methods

Method Effet
setDefaults() déclare des options avec une default value
setDefined() l'option est acceptée, sans défaut : absente du résultat si non passée
setRequired() l'option doit être fournie, sauf si elle a un défaut
setAllowedTypes() 'string', 'int\|null', 'DateTime[]' (chaque élément contrôlé)
setAllowedValues() une liste, ou une function de test
setNormalizer() transforme la valeur après validation
setDeprecated() signale une option obsolète quand elle est passée
setOptions() déclare des options imbriquées

Requise et défaut se combinent : isRequired('a') reste vrai, isMissing('a') devient faux. Sans défaut ni valeur : MissingOptionsException, « The required option "a" is missing. ».

Repère — Options imbriquées : setOptions(), not an arbitrary setDefault() closure. Le resolver imbriqué déclare ses propres options. Une closure ordinaire peut rester une simple valeur.

Options lazy

À comprendre

C'est quoi ?

Un défaut lazy, calculé à la demande, est une valeur obtenue pendant resolve à partir d'autres options. Dans OptionsResolver, une closure dont le premier argument est typé Options exprime ce calcul. Une closure ordinaire peut au contraire être la valeur de l'option elle-même.

À quoi ça sert ?

Un défaut dépendant du contexte résolu ne doit pas être calculé trop tôt, avant de connaître les valeurs fournies par l'appelant. Le calcul lazy permet par exemple de déduire une taille standard du mode choisi tout en laissant l'appelant fournir explicitement la taille.

Où dans Symfony ?

OptionsResolver est un component réutilisable, également employé par les types Form. setDefaults ou setDefault définit une valeur ; setDefined accepte une option sans en créer une valeur absente ; setRequired impose une valeur à défaut d'un défaut disponible. resolve applique les valeurs fournies, les dépendances, les contrôles et les normalizers.

Comment, étape par étape ?

  1. Déclarer les options dont le calcul dépend et leurs types.
  2. Déclarer le défaut calculé avec un argument Options.
  3. Lire uniquement les options nécessaires dans la closure.
  4. Éviter les dépendances circulaires et distinguer un défaut calculé d'un normalizer, qui transforme une valeur après les contrôles prévus.

Exemple concret PHP

Avec OptionsResolver chargé :

<?php
use Symfony\Component\OptionsResolver\Options;
use Symfony\Component\OptionsResolver\OptionsResolver;

$resolver = new OptionsResolver();
$resolver->setDefault('compact', false)->setAllowedTypes('compact', 'bool');
$resolver->setDefault('rows', static fn (Options $options): int => $options['compact'] ? 2 : 5);
$resolver->setAllowedTypes('rows', 'int');
var_dump($resolver->resolve(['compact' => true])['rows']);
var_dump($resolver->resolve(['compact' => true, 'rows' => 8])['rows']);

On attend 2 puis 8 : un défaut ne remplace pas la valeur explicitement fournie. Contre-exemple : retirer le type Options puis attendre le même calcul. La closure peut être considérée comme la valeur, et le contrôle int la refuser. Correction : conserver la signature reconnue. L'ordre des déclarations n'est pas l'ordre d'évaluation des dépendances.

Passage canonique conservé

Options lazy

Une default value peut être une closure qui reçoit les options résolues, ce qui permet à une option de dépendre d'une autre.

  • Le parameter doit être typé Options ; sinon, la closure est elle-même la valeur.
  • L'ordre de déclaration n'a pas d'importance.
  • Un second parameter reçoit le défaut précédent, celui d'un type parent : fn (Options $o, $prev) => $prev . '+child'.

Validation, puis normalization

À comprendre

À retenir en priorité
  1. Les types et valeurs admis sont contrôlés d'abord.
  2. Le normalizer transforme seulement une valeur acceptée.

C'est quoi ?

OptionsResolver transforme un tableau d'options fourni par l'appelant en configuration connue et contrôlée. Une option possède éventuellement une valeur par défaut, un caractère obligatoire, un type autorisé, des valeurs autorisées et un normalizer, fonction qui produit sa forme finale.

À quoi ça sert ?

Il distingue une configuration incorrecte d'une donnée métier invalide. Une faute dans le nom d'une option doit échouer au lieu d'être ignorée. Un normalizer simplifie une valeur déjà acceptée ; ce n'est pas une étape préalable qui rendrait acceptable n'importe quelle entrée.

Où dans Symfony ?

Les types de formulaire utilisent configureOptions(OptionsResolver $resolver). Le component peut aussi servir seul : resolve() réalise effectivement le contrôle. setDefaults() déclare avec défaut ; setDefined() autorise sans fournir de valeur ; setRequired() exige une valeur, qui peut néanmoins être satisfaite par un défaut.

Comment, étape par étape ?

  1. Déclarer les noms admis et les valeurs par défaut nécessaires.
  2. Contrôler les types puis les valeurs acceptables.
  3. Normaliser seulement après ces contrôles.
  4. Pour un défaut dépendant d'une autre option, employer une closure dont le paramètre est typé Options. Sans cette signature, une closure peut être une simple valeur d'option plutôt qu'un calcul différé.

Exemple concret PHP

Avec OptionsResolver 8.0 installé, cet exemple accepte une chaîne puis la met en majuscules.

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\OptionsResolver\Options;
use Symfony\Component\OptionsResolver\OptionsResolver;

$resolver = new OptionsResolver();
$resolver->setDefaults(['label' => 'bonjour']);
$resolver->setAllowedTypes('label', 'string');
$resolver->setNormalizer('label', static fn (Options $options, string $value): string => strtoupper($value));
var_export($resolver->resolve(['label' => 'salut']));

On attend ['label' => 'SALUT']. Un tableau à la place de salut est refusé avant le normalizer. Contre-exemple : autoriser uniquement GET et POST, puis ajouter un normalizer strtoupper() en espérant accepter post. Le contrôle des valeurs précède la normalisation. Correction : définir explicitement les formes d'entrée acceptées, ou normaliser avant l'appel à resolve() si tel est le contrat de l'API ; ne pas cacher un mauvais contrat en supprimant le contrôle.

Passage canonique conservé

Validation, puis normalization

La validation passe avant le normalisateur, qui ne répare donc pas une valeur refusée : avec setAllowedValues('m', ['GET', 'POST']) et un normalisateur strtoupper(), 'post' est refusée par InvalidOptionsException.

Options imbriquées

À retenir en priorité
  1. Le resolver imbriqué déclare ses propres options.
  2. Une closure ordinaire peut rester une simple valeur.
$resolver->setOptions('display', function (OptionsResolver $display): void {
    $display->setDefaults(['width' => 80, 'height' => 24]);
});

Fournir ['display' => ['width' => 100]] conserve le défaut de height. setOptions() interprète le resolver imbriqué ; une closure arbitraire passée à setDefault() peut rester une valeur Closure.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Déclarer qu'une option existe n'est pas lui donner une default value

    Déclarer qu'une option existe n'est pas lui donner une default value : une option seulement définie est absente du résultat.

  • Voir l’explication : Une option requise peut avoir un défaut

    Une option requise peut avoir un défaut : elle reste requise, mais n'est plus manquante.

  • Voir l’explication : Une option lazy exige le type Options

    Une option lazy exige le type Options ; sans lui, la closure est la valeur.

  • Voir l’explication : Le normalisateur s'exécute après la validation

    Le normalisateur s'exécute après la validation : il ne rattrape pas une valeur refusée.

  • Voir l’explication : Les options imbriquées passent par setOptions()

    Les options imbriquées passent par setOptions(), pas par setDefault().

Application

À retenir en priorité
  1. Une option définie peut rester absente du résultat.
  2. Une option requise avec défaut n'est plus manquante.
  3. Le resolver imbriqué déclare ses propres options.
  4. Une closure ordinaire peut rester une simple valeur.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Option inconnue : UndefinedOptionsException, avec la liste.
  • setDefined() : acceptée, absente si non passée ; setDefaults() : une valeur.
  • Requise et défaut : requise, mais pas manquante.
  • Lazy : closure typée Options ; $prev reçoit l'ancien défaut.
  • Types et valeurs avant le normalisateur.
  • Imbriquées : setOptions(), pas setDefault().
  • setDeprecated() avertit quand l'option est passée.

Moyen mnémotechnique : « Connaître, exiger, compléter, vérifier, normaliser ».
