Objectif

Déclarer et contraindre les options d'un form type. Le component sert partout où une class accepte un array d'options, pas seulement dans les forms.

L'essentiel

À comprendre

À retenir en priorité
  1. Le type Options signale une dépendance aux options résolues.
  2. L'ordre de déclaration ne commande pas l'ordre de résolution.

OptionsResolver remplace un array d'options brut par une déclaration : quelles options existent, lesquelles sont requises, leurs défauts, leurs types et valeurs permis. Une faute de frappe lève une exception au lieu de passer en silence. C'est le mécanisme de configureOptions() dans un form type.

Le schéma

À retenir en priorité
  1. Une option définie peut rester absente du résultat.
  2. Une option requise avec défaut n'est plus manquante.

Ambre = contrôles, rouge = exceptions, bleu = données. Ce chemin suppose le comportement standard, sans setIgnoreUndefined(true). La résolution se fait par option, pas en grandes passes globales : lire currency depuis le défaut de label résout d'abord cette dépendance. Un cycle entre deux défauts lazy lève OptionDefinitionException.

L'exemple : `PriceType`

Exemple concret

Avant que le lecteur ne soumette une valeur, le développeur configure le champ. PriceType illustre ce contrat de construction : devise, décimales et taux doivent être résolus pour que buildForm() reçoive des options cohérentes. Ce contrôle n'est pas la validation du prix saisi plus tard.

public function configureOptions(OptionsResolver $resolver): void
{
    $resolver->setDefaults(['decimals' => 2, 'currency' => 'EUR']);
    $resolver->setRequired('vat_rate');
    $resolver->setAllowedTypes('decimals', 'int');
    $resolver->setAllowedValues('currency', ['EUR', 'USD']);
    $resolver->setDefault('label', function (Options $options) {
        return 'Prix (' . $options['currency'] . ')';
    });
}

Les options déclarées sont celles que ->add() accepte pour ce type ; elles arrivent dans $options de buildForm(). Avec vat_rate: 0.2 et currency: 'USD', le défaut de label devient Prix (USD) ; sans vat_rate, la construction échoue avant buildForm(). Les extraits emploient OptionsResolver et Options du namespace Symfony\Component\OptionsResolver.

Le problème résolu

À retenir en priorité
  1. Les options admises sont déclarées explicitement.
  2. Une faute de nom ne doit pas être ignorée.

Une faute help_ico dans SignupType ne doit pas être ignorée en laissant le thème sans sa donnée attendue. OptionsResolver refuse ce nom dès la construction concernée. L'erreur indique un défaut de configuration du développeur, pas une violation à afficher comme erreur de saisie du lecteur.

Une option inconnue lève UndefinedOptionsException, qui liste les options définies : « The option "b" does not exist. Defined options are: "a", "c". ».

🌍 In Real Life

La situation : l'imprimeur accepte un bon de fabrication avec des rubriques précises : devise, décimales, libellé. Une rubrique mal orthographiée est refusée avant fabrication ; ce n'est pas le futur utilisateur de la fiche qui a mal rempli son prix.

L’équivalent dans Symfony : OptionsResolver définit le contrat du tableau d'options utilisé pour construire le champ. En comportement standard, une clé inconnue déclenche UndefinedOptionsException avant que buildForm() reçoive les options résolues.

Retour à la réalité technique : ce composant est utilisable hors Form. Ici, il contrôle les paramètres du développeur, pas les données soumises du lecteur. setIgnoreUndefined(true) change le traitement des clés inconnues ; ignorer une faute ne la convertit pas en option correctement nommée.

🧠 Comment le mémoriser : « Vérifier le bon de fabrication avant la fiche remplie. » Image mentale : bon de configuration contrôlé devant l'imprimante. Question-réflexe : l'erreur porte-t-elle sur une option de construction ou sur une donnée soumise ?

⚠️ À ne pas confondre : OptionsResolver, Validator, ArgumentResolver et résolution de services.

Les methods

Pour une aide facultative, « option connue » et « option présente dans le résultat » ne sont pas équivalents. Le code qui lit une option seulement définie doit gérer son absence ; un défaut sert au contraire à garantir une valeur de repli. La table sépare ce contrat de présence des contrôles de type et de valeur.

Déclarer une option, lui donner un défaut et exiger sa présence sont des opérations distinctes. Avec l'autoload OptionsResolver chargé :

<?php
use Symfony\Component\OptionsResolver\OptionsResolver;
$resolver = new OptionsResolver();
$resolver->setDefaults(['enabled' => true]);
$resolver->setDefined('note');
$resolver->setRequired('recipient');
$options = $resolver->resolve(['recipient' => 'Ada']);
var_export($options);
var_dump(array_key_exists('note', $options));

Le résultat contient enabled=true et recipient='Ada', mais pas note ; le dernier résultat vaut false. Résoudre un tableau vide ne fabrique pas recipient : l'option obligatoire manque. Une faute recipent est un nom inconnu, pas une autre manière de satisfaire cette obligation.

Method Effet
setDefaults() déclare des options avec une default value
setDefined() l'option est acceptée, sans défaut : absente du résultat si non passée
setRequired() l'option doit être fournie, sauf si elle a un défaut
setAllowedTypes() 'string', ['int', 'null'], 'DateTime[]' (chaque élément contrôlé)
setAllowedValues() une liste, ou une function de test
setNormalizer() transforme la valeur après validation
setDeprecated() signale une option obsolète quand elle est passée
setOptions() déclare des options imbriquées

Requise et défaut se combinent : isRequired('a') reste vrai, isMissing('a') devient faux. Sans défaut ni valeur : MissingOptionsException, « The required option "a" is missing. ».

Pour autoriser un entier ou null, cette forme évite toute ambiguïté d'échappement dans une table Markdown. La string équivalente est 'int|null', sans backslash :

<?php
use Symfony\Component\OptionsResolver\OptionsResolver;
$resolver = new OptionsResolver();
$resolver->setDefined('value')->setAllowedTypes('value', ['int', 'null']);
foreach ([2, null] as $value) {
    var_export($resolver->resolve(['value' => $value])['value']);
    echo "\n";
}

Les sorties sont 2 et NULL. Une string non numérique telle que 'bad' n'appartient à aucun de ces deux types et déclenche InvalidOptionsException.

🌍 In Real Life

La situation : le bon accepte une note facultative, impose un destinataire et prévoit une valeur de repli pour une autre rubrique. Une case autorisée peut rester absente ; une rubrique exigée peut être remplie par la valeur de repli.

L’équivalent dans Symfony : setDefined() autorise une clé sans la fournir ; setDefaults() apporte une valeur ; setRequired() impose sa présence résolue. Les types et valeurs permis ajoutent un contrat distinct.

Retour à la réalité technique : required ne signifie pas non-null ou non-vide ; ces restrictions doivent être déclarées si voulues. ['int', 'null'] autorise ces types sans convertir automatiquement une string numérique en entier. Déprécier signale une migration à prévoir, sans supprimer automatiquement l'option ; normaliser et déclarer une structure imbriquée sont encore d'autres opérations.

🧠 Comment le mémoriser : « Connue, présente et correcte : trois questions. » Image mentale : note facultative absente, destinataire rempli et valeur cochée conforme. Question-réflexe : ai-je défini un nom, assuré une présence ou contraint une valeur ?

⚠️ À ne pas confondre : défini, requis, manquant, null, défaut et type autorisé.

Options lazy

Le libellé de prix dépend de la devise réellement retenue, pas seulement du défaut écrit dans le type. La closure reçoit donc les options pendant la résolution et demande sa dépendance à ce moment. Cette paresse concerne le calcul d'une option ; elle ne désigne ni un service lazy ni le démarrage différé de la session ou des données Form.

Une default value peut être une closure qui reçoit les options résolues, ce qui permet à une option de dépendre d'une autre.

  • Le parameter doit être typé Options ; sinon, la closure est elle-même la valeur.
  • L'ordre de déclaration n'a pas d'importance.
  • Un second parameter reçoit le défaut précédent, celui d'un type parent : fn (Options $o, $prev) => $prev . '+child'.

🌍 In Real Life

La situation : l'imprimeur attend de connaître la devise retenue avant de composer « Prix (USD) ». Il ne se contente pas de recopier la devise standard annoncée avant la commande.

L’équivalent dans Symfony : un défaut lazy déclaré avec un paramètre Options calcule sa valeur pendant la résolution et demande la valeur résolue de ses dépendances. Un second paramètre peut reprendre le défaut précédent.

Retour à la réalité technique : une valeur explicitement fournie remplace normalement ce défaut ; ce n'est pas un recalcul permanent lors de chaque rendu. La résolution suit les dépendances, pas l'ordre visuel des déclarations ; une dépendance circulaire échoue. Une closure non reconnue comme défaut lazy peut rester une valeur callable, sans être exécutée.

🧠 Comment le mémoriser : « Composer le libellé avec la devise retenue. » Image mentale : USD choisi avant l'impression de Prix (USD). Question-réflexe : est-ce un défaut à calculer, une valeur explicite ou une fonction à conserver ?

⚠️ À ne pas confondre : défaut lazy, callback stocké, service lazy et normalisateur.

Validation, puis normalization

À retenir en priorité
  1. Les types et valeurs admis sont contrôlés d'abord.
  2. Le normalizer transforme seulement une valeur acceptée.

Pour une option de méthode, accepter seulement GET et POST signifie que post est déjà refusé avant le normalisateur. Si ton contrat veut accepter une autre forme puis la convertir, les valeurs autorisées doivent accepter cette entrée. Ne compte pas sur une étape postérieure pour réparer une valeur que le resolver a déjà rejetée.

La validation passe avant le normalisateur, qui ne répare donc pas une valeur refusée : avec setAllowedValues('m', ['GET', 'POST']) et un normalisateur strtoupper(), 'post' est refusée par InvalidOptionsException.

🌍 In Real Life

La situation : un atelier vérifie le matériau avant de le polir. Un matériau refusé à l'entrée n'atteint jamais la machine qui lui donnerait son aspect final.

L’équivalent dans Symfony : pour chaque option résolue, les contrôles de types et valeurs précèdent son normalisateur. Si seules GET et POST sont acceptées, post échoue avant strtoupper().

Retour à la réalité technique : déclare les formes d'entrée réellement acceptables au lieu d'espérer leur réparation ultérieure. Le normalisateur est responsable de sa sortie ; ne suppose pas une seconde validation automatique identique après lui. Cette normalisation d'options n'est ni la norm data Form ni une opération du Serializer.

🧠 Comment le mémoriser : « Un refus à l'entrée n'arrive pas au polissage. » Image mentale : matériau bloqué avant la machine. Question-réflexe : ma valeur franchit-elle les contrôles avant la transformation prévue ?

⚠️ À ne pas confondre : contrôle d'options, normalisation d'options, transformation Form et validation métier.

Options imbriquées

À retenir en priorité
  1. Le resolver imbriqué déclare ses propres options.
  2. Une closure ordinaire peut rester une simple valeur.

L'exemple db démontre le composant générique, pas une dépendance base de données du formulaire d'inscription. Le sous-resolver contrôle ses propres clés et complète seulement les valeurs manquantes prévues. setOptions() déclare cette structure ; stocker une closure dans un défaut n'est pas demander son exécution comme sous-configuration.

$resolver->setOptions('db', function (OptionsResolver $db): void {
    $db->setDefaults(['host' => 'localhost', 'port' => 3306]);
});

['db' => ['port' => 5432]] donne host et port complétés. La même closure passée à setDefault() n'est pas interprétée : l'option vaut l'object Closure.

🌍 In Real Life

La situation : le bon de fabrication contient une sous-fiche avec ses propres rubriques et valeurs de repli. Joindre une notice de remplissage ne remplit cette sous-fiche que si le bureau sait qu'il doit l'appliquer.

L’équivalent dans Symfony : setOptions() déclare un sous-resolver ; ses défauts complètent les clés manquantes du tableau imbriqué, comme host lorsque port est fourni.

Retour à la réalité technique : en8.0, la closure typée OptionsResolver passée à setDefault() dans l'exemple reste une valeur, pas une déclaration de sous-options. Une valeur par défaut qui est elle-même un tableau reste possible, mais ne remplace pas un schéma imbriqué. Nommer la sous-option db ne crée aucune connexion ni dépendance ORM.

🧠 Comment le mémoriser : « Une sous-fiche a besoin de son propre contrat. » Image mentale : petit bon host/port à l'intérieur du grand bon. Question-réflexe : ai-je déclaré la structure interne ou seulement stocké une valeur ?

⚠️ À ne pas confondre : tableau par défaut, sous-resolver, closure conservée et connexion à une base.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Option inconnue : UndefinedOptionsException, avec la liste.
  • setDefined() : acceptée, absente si non passée ; setDefaults() : une valeur.
  • Requise et défaut : requise, mais pas manquante.
  • Lazy : closure typée Options ; $prev reçoit l'ancien défaut.
  • Types et valeurs avant le normalisateur.
  • Imbriquées : setOptions(), pas setDefault().
  • setDeprecated() avertit quand l'option est passée.

Moyen mnémotechnique : « Connaître, exiger, compléter, vérifier, normaliser ».
