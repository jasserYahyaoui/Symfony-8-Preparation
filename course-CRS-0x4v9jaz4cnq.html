Objectif

Le test de /blog/42 vérifie maintenant le statut et le contenu. Il peut pourtant rester vert après une régression du travail serveur. Pour un test ciblé sur une métrique, le profiler conserve les données recueillies pendant cette requête ; les en-têtes et le HTML ne suffisent pas à les déduire.

L'essentiel

À comprendre

À retenir en priorité
  1. Activer le service et collecter sont deux réglages.
  2. Le helper agit sur la collecte.

Le profiler enregistre des mesures pendant le traitement d'une requête. Le Profile est cet enregistrement ; un collector en expose une partie, par exemple la durée. Ce n'est pas le service applicatif vivant.

La configuration de test recommandée garde le profiler disponible, mais désactive la collecte systématique. enableProfiler() demande alors une collecte pour la requête suivante. getProfile() lit le profil associé à la réponse courante : il ne reconstitue pas les mesures d'une requête passée.

Il faut distinguer le service qui collecte, le profil enregistré et l'interface web qui permet de le consulter. Le test lit les données du profil, sans devoir afficher la barre de debug. Un token de profil sert à identifier cet enregistrement ; ce n'est ni une authentification ni une protection CSRF.

Le schéma

À retenir en priorité
  1. La collecte ciblée réduit le coût.
  2. Les tests peuvent activer seulement la Request utile.

La décision de mesurer précède l'appel HTTP. La présence du profil est ensuite une précondition de l'assertion de mesure, pas une option à ignorer si le service manque :

Bleu : opérations du test ; vert : résultat observable ; losange ambre : vérification. Ce parcours suppose un service profiler disponible, une réponse profilable et aucune restriction supplémentaire de collecte. Sans nouvelle activation, la requête suivante revient au réglage collect: false.

L'exemple

Exemple concret

À retenir en priorité
  1. La collecte ne se reconstruit pas après coup.
  2. Cibler explicitement la prochaine Request.

Dans une méthode de WebTestCase, avec Symfony 8.0, PHPUnit 11.5, la route blog_show, le catalogue de test et le collector time correctement instrumenté :

$client = static::createClient();
$client->enableProfiler();                    // la Request suivante seulement
$client->request('GET', '/blog/42');
self::assertResponseStatusCodeSame(200);
self::assertRouteSame('blog_show');

$profile = $client->getProfile();
$this->assertInstanceOf(
    \Symfony\Component\HttpKernel\Profiler\Profile::class,
    $profile,
    'Ce test exige un profil : vérifier la configuration de collecte.',
);
$this->assertLessThan(
    500,
    $profile->getCollector('time')->getDuration(),
    sprintf('Budget dépassé (token %s)', $profile->getToken()),
);

Dans une méthode de WebTestCase, avec le collector time disponible, ce test exige une durée inférieure à 500 ms. Un profil absent fait échouer le test au lieu de sauter silencieusement l'assertion. Ce seuil est un exemple de budget local, pas une garantie de performance Symfony ; sa stabilité dépend de l'environnement d'exécution.

Le statut et la route évitent notamment de déclarer rapide une réponse 404 reçue par erreur. Établir le budget avec un environnement, des données et un état de cache contrôlés : la charge de la CI et l'instrumentation peuvent faire varier la mesure. Ce test n'est pas un benchmark du réseau ni du temps d'affichage dans un navigateur.

Deux réglages, pas un

À retenir en priorité
  1. Le helper ne remplace pas la configuration.
  2. Un service absent reste absent.

🌍 In Real Life

La situation : le restaurant possède un chronomètre de contrôle, mais l'observateur ne déclenche la mesure que pour le service choisi.

L’équivalent dans Symfony : instrument disponible → service profiler configuré ; déclenchement ciblé → enableProfiler() avant la prochaine requête /blog/42.

Retour à la réalité technique : demander la collecte ne crée pas un profiler absent. L'activation ciblée concerne la requête suivante ; contrôler ensuite la présence du Profile évite de traiter l'absence de mesure comme une réussite.

🧠 Comment le mémoriser : « Installer l'instrument, puis déclencher. » Image mentale : chronomètre présent mais arrêté. Question-réflexe : le service existe-t-il et la collecte a-t-elle précédé cette requête ?

⚠️ À ne pas confondre : disponibilité du profiler et collecte systématique.

La configuration rend le service disponible lors de la préparation de l'application ; le test choisit ensuite la requête à observer :

when@test:
    framework:
        profiler: { enabled: true, collect: false }
  • enabled crée le service profiler ; collect décide si chaque Request est profilée. collect: false évite le coût d'une collecte systématique, sans promettre un surcoût global exactement nul.
  • enableProfiler() n'active pas le profiler : sans service profiler, l'appel ne fait rien. Elle active la collecte, pour la Request suivante.

Dans KernelBrowser, le helper pose un drapeau si le service existe. Avant le traitement suivant, le client consomme ce drapeau et active le profiler. Le cycle normal de reboot ou de reset rétablit ensuite la politique initiale. Il ne relance pas les extensions du conteneur pour installer à la volée un profiler absent.

Le tableau décrit ce parcours normal, sans restriction supplémentaire de collecte ni échec du stockage du profil :

Configuration Request getProfile()
service profiler absent (enabled: false) après enableProfiler() false
enabled: true, collect: false sans enableProfiler() null
idem juste après enableProfiler() un Profile
idem la Request suivante null
enabled: true, collect: true chacune un Profile
  • false = pas de profiler (ou pas encore de Response, juste après createClient()) ; null = aucun profil chargé pour cette Response, par exemple parce qu'elle n'a pas été collectée.
  • enableProfiler() appelée après la Request ne profile rien après coup : null, puis un Profile à la Request suivante.

Plus précisément, le chargement lit X-Debug-Token sur la réponse, puis utilise ce token pour lire le stockage. Sans ce header, le résultat est null ; un profil devenu introuvable peut aussi manquer à la lecture. null ne prouve donc pas universellement que la collecte n'a jamais eu lieu. Après une redirection suivie, la réponse courante peut être celle de destination : lire le profil au moment voulu plutôt que mesurer une autre page.

Lire un collector

À retenir en priorité
  1. Les collectors dépendent des fonctionnalités actives.
  2. Un nom inconnu peut lever une exception.

🌍 In Real Life

La situation : après le service, le contrôleur consulte la feuille des durées et celle des commandes ; il ne demande pas à la feuille de refaire le travail du serveur.

L’équivalent dans Symfony : dossier d'observation → Profile ; feuille spécialisée → collector nommé ; mesure inscrite → donnée de la requête enregistrée.

Retour à la réalité technique : le collector du profil expose l'observation conservée, pas le service applicatif vivant. Les noms disponibles dépendent de l'instrumentation ; une durée mesurée dépend aussi de l'environnement du test.

🧠 Comment le mémoriser : « Lire la trace, pas commander au service. » Image mentale : carnet daté après le repas. Question-réflexe : ce collector existe-t-il et quelle unité expose-t-il ?

⚠️ À ne pas confondre : nom de collector, identifiant de service et token d'authentification.

Après avoir exigé un Profile, choisir la métrique par le nom du collector enregistré. Ce nom n'est pas nécessairement l'identifiant d'un service applicatif dans le conteneur :

$profile->getCollector('time')->getDuration();   // un float, en millisecondes
$profile->getCollector('request')->getRoute();
$profile->getToken();                             // pour retrouver la Request dans le profiler web
  • La liste des collectors dépend des bundles installés (request, time, memory…).
  • Un nom inconnu : InvalidArgumentException, « Collector "nope" does not exist. » ; hasCollector('nope') rend false.
  • La documentation : un functional test teste d'abord la Response ; le profiler sert quand la métrique est le sujet du test.

Le profiler place des clones de collectors dans le profil lors de la collecte. Récupérer un service vivant par getContainer()->get(...) ne revient pas à relire cette observation. Pour un collector propre à l'application, par exemple app.hit, exiger sa présence avec hasCollector() si le test en dépend, puis employer son API de données.

Une absence de profil ou de collector n'est pas une mesure égale à zéro. Même time->getDuration() peut rendre 0 si son événement de section n'est pas disponible : vérifier l'instrumentation avant d'interpréter ce résultat comme une page instantanée. Le token placé dans le message d'échec aide à retrouver les données, dont l'accès doit rester protégé.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Tester la présence avant lecture.
  2. Absence de service et absence de collecte sont distinctes.
  • Voir l’explication : enableProfiler() n'active pas le profiler

    enableProfiler() n'active pas le profiler ; elle active la collecte.

  • Collecte du profiler pour la prochaine Request

    La collecte activée par enableProfiler() ne vaut que pour la Request suivante.

  • Voir l’explication : getProfile() peut rendre false ou null

    getProfile() peut rendre false ou null — le tester. false : pas de profiler ou de réponse ; null : aucun profil chargé pour cette réponse.

  • Voir l’explication : collect: true collecte à chaque Request

    collect: true collecte à chaque Request, sans enableProfiler().

Fiche express

À mémoriser

À retenir en priorité
  1. Le profiler sert aux métriques ciblées.
  2. Il ne remplace pas les assertions fonctionnelles.

Le test fonctionnel dit si l'article attendu a été rendu ; le test de profil dit ce que l'instrumentation a observé pendant cette requête. Ne pas transformer l'absence de mesure en réussite silencieuse.

Si tu dois retenir seulement 6 choses :

  • Test : enabled: true, collect: false.
  • enableProfiler() active la collecte, pas le profiler.
  • Pour la Request suivante seulement, donc avant request().
  • false : pas de profiler ou pas de Response ; null : aucun profil chargé.
  • collect: true : chaque Request profilée.
  • getCollector() pour la métrique, getToken() pour la retrouver.

Moyen mnémotechnique : « Activé par config, collecté sur demande ».

config : enabled: true, collect: false ; enableProfiler() AVANT la Request (une seule) ; getProfile() : false = pas de service ou de réponse, null = pas de profil chargé ;
collect: true = toutes ; getCollector('time')->getDuration() ; getToken() dans le message

Le cours accès aux objets du framework traite l'autre besoin : obtenir les services réels du test, plutôt que relire leurs données collectées.
