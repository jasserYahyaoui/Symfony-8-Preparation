Objectif

Lire les données du profiler depuis un test, pour vérifier une métrique que la Response ne montre pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Activer le service et collecter sont deux réglages.
  2. Le helper agit sur la collecte.

Le profiler enregistre des mesures pendant le traitement d'une requête. Le Profile est cet enregistrement ; un collector en expose une partie, par exemple la durée. Ce n'est pas le service applicatif vivant.

La configuration de test recommandée garde le profiler disponible, mais désactive la collecte systématique. enableProfiler() demande alors une collecte pour la requête suivante. getProfile() lit le profil associé à la réponse courante : il ne reconstitue pas les mesures d'une requête passée.

Le schéma

À retenir en priorité
  1. La collecte ciblée réduit le coût.
  2. Les tests peuvent activer seulement la Request utile.

Bleu : opérations du test ; vert : résultat observable ; losange ambre : vérification. Ce parcours suppose un service profiler disponible, une réponse profilable et aucune restriction supplémentaire de collecte. Sans nouvelle activation, la requête suivante revient au réglage collect: false.

L'exemple

Exemple concret

À retenir en priorité
  1. La collecte ne se reconstruit pas après coup.
  2. Cibler explicitement la prochaine Request.
$client = static::createClient();
$client->enableProfiler();                    // la Request suivante seulement
$client->request('GET', '/lucky/number');

$profile = $client->getProfile();
$this->assertInstanceOf(
    \Symfony\Component\HttpKernel\Profiler\Profile::class,
    $profile,
    'Ce test exige un profil : vérifier la configuration de collecte.',
);
$this->assertLessThan(
    500,
    $profile->getCollector('time')->getDuration(),
    sprintf('Budget dépassé (token %s)', $profile->getToken()),
);

Dans une méthode de WebTestCase, avec le collector time disponible, ce test exige une durée inférieure à 500 ms. Un profil absent fait échouer le test au lieu de sauter silencieusement l'assertion. Ce seuil est un exemple de budget local, pas une garantie de performance Symfony ; sa stabilité dépend de l'environnement d'exécution.

Deux réglages, pas un

À retenir en priorité
  1. Le helper ne remplace pas la configuration.
  2. Un service absent reste absent.
when@test:
    framework:
        profiler: { enabled: true, collect: false }
  • enabled crée le service profiler ; collect décide si chaque Request est profilée. collect: false garde le service sans ralentir la suite.
  • enableProfiler() n'active pas le profiler : sans service profiler, l'appel ne fait rien. Elle active la collecte, pour la Request suivante.
Configuration Request getProfile()
service profiler absent (enabled: false) après enableProfiler() false
enabled: true, collect: false sans enableProfiler() null
idem juste après enableProfiler() un Profile
idem la Request suivante null
enabled: true, collect: true chacune un Profile
  • false = pas de profiler (ou aucune Response, juste après createClient()) ; null = rien collecté pour cette Response.
  • enableProfiler() appelée après la Request ne profile rien après coup : null, puis un Profile à la Request suivante.

Lire un collector

À retenir en priorité
  1. Les collectors dépendent des fonctionnalités actives.
  2. Un nom inconnu peut lever une exception.
$profile->getCollector('time')->getDuration();   // un float, en millisecondes
$profile->getCollector('request')->getRoute();
$profile->getToken();                             // pour retrouver la Request dans le profiler web
  • La liste des collectors dépend des bundles installés (request, time, memory…).
  • Un nom inconnu : InvalidArgumentException, « Collector "nope" does not exist. » ; hasCollector('nope') rend false.
  • La documentation : un functional test teste d'abord la Response ; le profiler sert quand la métrique est le sujet du test.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Tester la présence avant lecture.
  2. Absence de service et absence de collecte sont distinctes.
  • Voir l’explication : enableProfiler() n'active pas le profiler

    enableProfiler() n'active pas le profiler ; elle active la collecte.

  • Collecte du profiler pour la prochaine Request

    La collecte activée par enableProfiler() ne vaut que pour la Request suivante.

  • Voir l’explication : getProfile() peut rendre false ou null

    getProfile() peut rendre false ou null — le tester. false : pas de profiler ; null : rien collecté.

  • Voir l’explication : collect: true collecte à chaque Request

    collect: true collecte à chaque Request, sans enableProfiler().

Fiche express

À mémoriser

À retenir en priorité
  1. Le profiler sert aux métriques ciblées.
  2. Il ne remplace pas les assertions fonctionnelles.

Si tu dois retenir seulement 6 choses :

  • Test : enabled: true, collect: false.
  • enableProfiler() active la collecte, pas le profiler.
  • Pour la Request suivante seulement, donc avant request().
  • false : pas de profiler ou pas de Response ; null : rien collecté.
  • collect: true : chaque Request profilée.
  • getCollector() pour la métrique, getToken() pour la retrouver.

Moyen mnémotechnique : « Activé par config, collecté sur demande ».

config : enabled: true, collect: false ; enableProfiler() AVANT la Request (une seule) ; getProfile() : false = rien à profiler, null = rien collecté ;
collect: true = toutes ; getCollector('time')->getDuration() ; getToken() dans le message
