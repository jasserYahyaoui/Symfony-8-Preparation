Objectif

Obtenir la session depuis un controller, connaître son API de base, et comprendre quand elle démarre réellement.

L'essentiel

À comprendre

À retenir en priorité
  1. La régénération d'identifier ne vide pas les données.
  2. invalidate() vide puis appelle migrate(true).

La session s'obtient par la Request, par un argument typé SessionInterface ou, dans un service, par RequestStack. Elle démarre paresseusement : pas parce que la configuration l'active, mais au premier accès — lire, écrire ou tester. migrate() change l'identifier en gardant les données ; invalidate() vide le stockage, puis appelle migrate(true).

Le schéma

Bleu = opérations ; vert = effet standard sans désactivation du cache automatique. Stockage, cookie d'identification et politique HTTP sont distincts.

L'exemple

Exemple concret

À retenir en priorité
  1. has() n'est pas une consultation neutre.
  2. La Response peut devenir private même sans cookie émis pour une session vide.
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpFoundation\Session\SessionInterface;

final class CartController extends AbstractController
{
    public function addToCart(SessionInterface $session, int $id): Response
    {
        $cart = $session->get('cart', []);   // [] par défaut
        $cart[] = $id;
        $session->set('cart', $cart);
        return $this->redirectToRoute('cart_show', [], 303);
    }
}

Le contrôleur est enregistré dans une application avec session et route cart_show configurées ; l'identifiant reçu a déjà été validé.

L'obtenir

À comprendre

À retenir en priorité
  1. Un controller peut recevoir SessionInterface.
  2. RequestStack retrouve la session liée à la Request courante.

C'est quoi ?

L'objet SessionInterface donne accès à un état de session configuré pour la Request. Il ne faut pas créer un stockage indépendant à chaque endroit où l'application souhaite lire cet état.

À quoi ça sert ?

Utiliser la session attachée au contexte conserve la cohérence entre les lectures et écritures de la même requête. Dans un service, RequestStack permet d'obtenir cette session au moment de l'opération, plutôt que figer prématurément le contexte HTTP.

Où dans Symfony ?

Dans une action, Request.getSession ou un argument SessionInterface sont possibles avec l'intégration correspondante. Dans un service, injecter RequestStack puis appeler getSession. Sans session disponible, cette dernière méthode lève SessionNotFoundException : elle ne retourne pas null ni une session vide de remplacement.

Comment, étape par étape ?

  1. Activer et configurer les sessions si le parcours en a besoin.
  2. Choisir l'accès adapté à l'action ou au service.
  3. Ne consulter la session qu'au moment utile.
  4. Si le service doit fonctionner hors HTTP, lui fournir les données nécessaires explicitement ou définir une opération séparée, plutôt que masquer l'absence de session.

Exemple concret PHP

Service dont l'opération dépend volontairement d'une session HTTP :

<?php
use Symfony\Component\HttpFoundation\RequestStack;

final class DisplayPreference
{
    public function __construct(private RequestStack $requests) {}
    public function chooseCompactMode(): void
    {
        $this->requests->getSession()->set('compact', true);
    }
}

La clé est écrite dans la session du contexte courant. Contre-exemple : appeler ce service dans une commande sans Request puis convertir toute exception en succès silencieux. Correction : respecter sa dépendance HTTP ou séparer le calcul de préférence de sa persistance en session. Obtenir l'objet et accéder à son sac n'ont pas nécessairement le même effet sur le démarrage du stockage.

Contexte Accès
controller, Request en main $request->getSession()
controller, argument typé SessionInterface $session, via SessionValueResolver
service RequestStack::getSession()

Le démarrage est lazy

La documentation écrit que la session démarre quand on la lit ou l'écrit. Le code va plus loin : sept methods de Session — has(), get(), set(), all(), replace(), remove(), clear() — passent par getAttributeBag(), qui démarre la session. Il n'y a donc aucune consultation neutre : has() la démarre comme get().

Sans usage de session, ce mécanisme n'impose pas de cookie ni de privatisation ; cela ne rend pas automatiquement la réponse publiquement cachable. Avec la configuration standard, l'usage du bag rend la réponse principale privée. Si les cookies sont activés, une session non vide reçoit un cookie lorsque son identifiant diffère de celui reçu ; il n'est pas renvoyé à chaque lecture. Une session devenue vide peut produire un cookie d'expiration. Un simple has() sur une session neuve vide donne « privée sans nouveau cookie ».

Le cookie de session est le ticket, les données restent dans le casier côté serveur. Attention à la limite de l'image du vestiaire : même demander si un objet est présent avec has() démarre l'accès à la session.

L'API

À comprendre

C'est quoi ?

migrate régénère l'identifiant de session en conservant les données. invalidate commence par vider le stockage puis appelle migrate avec destruction de l'ancienne session. Changer d'identifiant et supprimer les données sont donc deux décisions distinctes.

À quoi ça sert ?

Une régénération peut accompagner un changement de niveau de confiance sans perdre les données utiles. Une invalidation convient lorsqu'il faut abandonner l'ancien état. Le mécanisme d'authentification de l'application peut déjà gérer cette politique : il ne faut pas le doubler aveuglément.

Où dans Symfony ?

SessionInterface expose ces deux méthodes et leur résultat booléen. migrate a destroy égal à false par défaut : régénérer ne demande alors pas la destruction de l'ancien stockage. Le paramètre lifetime permet de préciser la durée de vie selon le stockage utilisé.

Comment, étape par étape ?

  1. Décider si les données doivent être conservées.
  2. Si oui, choisir migrate ; si non, invalidate.
  3. Décider explicitement du sort de l'ancienne session lors d'une migration.
  4. Traiter un résultat d'échec au lieu d'annoncer une transition accomplie.

Exemple concret PHP

Fonction recevant une session réelle configurée :

<?php
use Symfony\Component\HttpFoundation\Session\SessionInterface;

function rotateSession(SessionInterface $session): void
{
    $session->set('compact', true);
    if (!$session->migrate(true)) {
        throw new \RuntimeException('Impossible de régénérer la session.');
    }
    // La donnée compact reste présente après une migration réussie.
}

Contre-exemple : remplacer migrate par invalidate pour ne changer que l'identifiant : compact disparaît parce que le stockage est vidé. Correction : utiliser migrate pour conserver les données. À l'inverse, migrate(true) détruit l'ancien stockage sans effacer les données transférées dans la session courante ; ce n'est pas l'équivalent d'une déconnexion complète.

Passage canonique conservé

set(), get($name, $default), has(), remove(), all(), clear(). Pour la security, deux methods, l'une bâtie sur l'autre :

  • migrate($destroy = false, $lifetime = null) régénère l'identifier et garde les données ; avec destroy à false, l'ancienne session reste sur le serveur. On l'appelle après une authentication réussie, contre la fixation de session.
  • invalidate($lifetime = null) vide le stockage, puis appelle migrate(true, $lifetime). C'est le vidage qui supprime les données, pas la régénération. On l'appelle à la déconnexion.

Les deux rendent un bool.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Tester une valeur démarre la session, comme la lire.

    Tester une valeur démarre la session, comme la lire. Il n'existe pas de consultation neutre : has() passe par le même accès au sac que get(). La vérification suffit à rendre la page non cachable par un proxy partagé — sans nouveau cookie d'identification pour une session neuve vide. Une session vide avec cookie reçu peut au contraire produire son expiration.

  • Voir l’explication : Activer la session dans la configuration ne la démarre pas.

    Activer la session dans la configuration ne la démarre pas. Le démarrage est lazy ; sans autre intervention, une page qui n'y touche jamais ne déclenche pas de cookie par ce mécanisme.

  • Voir l’explication : invalidate() n'est pas l'opposé de migrate(), elle l'utilise.

    invalidate() n'est pas l'opposé de migrate(), elle l'utilise. Elle vide le stockage puis appelle migrate(true, …). La suppression des données vient du vidage, pas de la régénération.

  • Voir l’explication : migrate() seule ne détruit pas l'ancienne session.

    migrate() seule ne détruit pas l'ancienne session. Son argument $destroy vaut false par défaut : l'identifier change, mais la session précédente reste sur le serveur. C'est invalidate() qui passe true.

  • Voir l’explication : La documentation ne mentionne pas le test.

    La documentation ne mentionne pas le test. Elle parle de lire et d'écrire ; c'est le code qui montre que tester compte aussi. Sur ce point précis, se fier au texte seul donne une réponse fausse.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Accès : Request, SessionInterface typé, RequestStack en service.
  • Démarrage lazy : lire, écrire ou tester — has() compte.
  • Pas d'usage → aucune garantie de cache public : vérifier la politique HTTP.
  • Usage → private par défaut ; cookie selon contenu et identifiant reçu.
  • migrate() : nouvel id, données gardées, destroy à false.
  • invalidate() = vider puis migrate(true).

Moyen mnémotechnique : « Migrate garde, invalidate vide ».

Does Session::has() necessarily send a session cookie?

No. It starts session storage, but has() alone does not modify a Response. In the integrated HTTP cycle, SessionListener with auto cache control makes the response private after session use; an empty session need not send Set-Cookie.

Session::has() démarre le stockage mais ne modifie pas une Response isolée. Dans le cycle HTTP intégré, SessionListener applique la confidentialité si le contrôle automatique du cache est actif. Démarrage, confidentialité et émission effective du cookie restent trois effets distincts.
