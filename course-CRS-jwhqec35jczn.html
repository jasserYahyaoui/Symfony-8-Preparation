Objectif

L'import sait lire un fichier et publier son rapport. Il doit maintenant sélectionner un lot de fichiers sans mélanger entrées, archives et dossiers. Finder décrit cette recherche ; nous allons séparer ses critères, leur état mutable et le parcours réel des résultats.

L'essentiel

À comprendre

À retenir en priorité
  1. Les critères s'accumulent.
  2. Cloner une base avant deux recherches différentes.

Finder construit une recherche de fichiers ou de dossiers. Les appels chaînés règlent ses critères ; l'itération parcourt les résultats. in() fournit les dossiers de départ dans le cas habituel ; append() permet aussi de fournir une source de résultats.

L'objet est mutable : appeler name() change cette même recherche. Deux critères name() positifs se combinent avec OU, pas avec ET. Pour préparer deux recherches indépendantes sur une base commune, cloner la base avant d'ajouter le critère propre à chaque branche.

La recherche ne lit pas et ne valide pas automatiquement les articles contenus dans les fichiers retenus. Le service d'import doit encore ouvrir, parser et traiter chaque entrée. Finder ne fournit pas non plus une liste figée dès la construction : le système de fichiers peut changer ensuite.

Le schéma

À retenir en priorité
  1. Deux variables peuvent viser le même object.
  2. Le clone sépare les configurations.

Pour rendre le piège visible, conservons un petit dossier de templates du blog. Deux familles de noms partagent une racine ; elles doivent rester deux sélections indépendantes. La même technique servira aux lots d'import :

Bleu : objets de recherche distincts ; cylindres verts : résultats. Les noms sont ceux d'un dossier d'exemple contenant partial_menu, plugin_search et README. Les flèches décrivent une copie ou une itération, pas un héritage entre classes.

L'exemple : deux recherches sur une base commune

Exemple concret

À retenir en priorité
  1. L'object partagé conserve les modifications.
  2. La réutilisation exige une copie volontaire.

Avec Finder 8.0 chargé, lancer ce fragment depuis un répertoire où ./templates contient les trois fichiers du schéma :

use Symfony\Component\Finder\Finder;

$finder = new Finder();
$finder->files()->in('./templates');

foreach ((clone $finder)->name('partial_*') as $file) {
    $file->getRelativePathname();
}
foreach ((clone $finder)->name('plugin_*') as $file) {
    // Sans les deux clones : partial_* OU plugin_* sur la même instance.
}

La première boucle reçoit partial_menu, la seconde plugin_search ; README ne correspond à aucun des deux motifs. Le premier getter calcule le nom relatif, mais ne l'affiche pas : ces boucles illustrent la sélection, pas un rendu Twig ni l'exécution d'un import.

L'usage de base

À retenir en priorité
  1. Les résultats enrichissent SplFileInfo.
  2. Ils restent itérables sans conversion préalable.

Chaque résultat est un Symfony\Component\Finder\SplFileInfo, qui étend celui de PHP pour ajouter getRelativePath() et getRelativePathname(). Toutes les methods de critère se chaînent.

Pour les entrées de l'import, $root doit être un répertoire existant, choisi par la configuration de l'application :

use Symfony\Component\Finder\Finder;

$inputs = (new Finder())->files()->in($root)->name('*.csv');
foreach ($inputs as $file) {
    $relativeName = $file->getRelativePathname();
    // Le service d'import décide ensuite comment traiter ce fichier.
}

files() choisit le type, in() la racine, name() le motif. Par défaut, un archive/old.csv peut aussi être retenu car le parcours est récursif : exclure archive si cette branche ne doit pas être réimportée. getRelativePathname() inclut le nom du fichier ; getRelativePath() donne seulement son répertoire relatif.

L'object est à état — le piège central

À retenir en priorité
  1. L'affectation ne clone pas l'object.
  2. Les deux références voient le même état.
  3. Deux Finder créés indépendamment ne partagent pas leurs critères.

🌍 In Real Life

La situation : deux collègues du blog écrivent leurs critères de recherche sur la même fiche. Changer de personne ne donne pas une fiche neuve.

L’équivalent dans Symfony : fiche partagée → même instance Finder ; nouvelle variante indépendante → clone avant spécialisation ; rayonnages consultés → système de fichiers actuel.

Retour à la réalité technique : les appels modifient les critères de l'objet. Des motifs name() successifs s'accumulent ici en alternatives ; cloner les critères ne photographie pas les fichiers.

🧠 Comment le mémoriser : « Copier la fiche avant d'ajouter. » Image mentale : deux photocopies avant annotation. Question-réflexe : mes variables désignent-elles le même Finder ?

⚠️ À ne pas confondre : copie de configuration et instantané des résultats.

Le Finder est stateful : les critères restent sur l'instance modifiée. Deux variables qui désignent cette même instance voient les mêmes changements ; deux instances distinctes ne partagent pas automatiquement leurs critères.

Avec les trois fichiers de l'exemple, name('partial_*') retient partial_menu. Ajouter name('plugin_*') sur le même objet retient partial_menu et plugin_search, car l'un ou l'autre motif suffit. Le nombre dépend des fichiers présents ; ajouter un critère n'ajoute pas nécessairement exactement un résultat. Le clone isole les critères à venir, mais ne fige pas le contenu du système de fichiers.

$a = $finder ne copie donc pas une requête : les deux variables désignent le même objet. Cloner après avoir ajouté les deux motifs conserverait déjà les deux dans chaque clone. Le bon moment est avant la spécialisation. Dans un worker durable, ne pas laisser une recherche partagée accumuler les filtres de chaque message.

Quoi chercher

À retenir en priorité
  1. Le type de résultat doit être filtré.
  2. La recherche est récursive par défaut.

Le choix de la racine borne le parcours ; les filtres disent ensuite quelles entrées rendre. Une racine invalide n'est pas une recherche valide à zéro résultat :

  • in() : un ou plusieurs directories, joker * permis — chaque pattern doit résoudre vers un directory, sinon DirectoryNotFoundException ; exclude() prend des paths relatifs à ceux d'in() ; une URL ftp:// ou zlib:// est acceptée.
  • Par défaut, files et directories ; files() ou directories() restreignent. Sans in() ni append(), l'itération lève une LogicException.
  • Récursif par défaut ; depth('== 0'), depth(['> 2', '< 5']) bornent.
  • Métadonnées VCS ignorées par défaut ; ignoreVCS(false) désactive cette exclusion. Le filtre indépendant des entrées commençant par un point reste actif : pour inclure .git, il faut aussi ignoreDotFiles(false), sous réserve des autres critères de recherche. ignoreVCSIgnored(true) applique les .gitignore en partant du directory de recherche. Liens symboliques suivis seulement avec followLinks().

La vérification des répertoires se produit dans in() : un joker qui ne résout aucun dossier peut lever avant le foreach. La LogicException sans in() ni append() concerne, elle, le démarrage de l'itération. Ce sont deux erreurs de préparation différentes.

Ignorer les métadonnées VCS ne signifie pas appliquer les .gitignore. La seconde option part du dossier recherché, qui peut différer de la racine du dépôt. Les entrées commençant par un point sont aussi ignorées par défaut. followLinks() concerne notamment la descente dans les répertoires liés ; ne pas l'activer sans considérer ce qui se trouve hors de la racine logique.

Récupérer les résultats

À retenir en priorité
  1. Les keys peuvent se répéter.
  2. Désactiver leur préservation conserve chaque occurrence.

🌍 In Real Life

La situation : deux tournées d'archives du blog visitent la même boîte. Le carnet compte deux visites ; le registre indexé par adresse ne garde qu'une case.

L’équivalent dans Symfony : visites → occurrences itérées ; adresse → clé de chemin ; case remplacée → conservation des clés par iterator_to_array().

Retour à la réalité technique : des racines qui se recouvrent peuvent produire plusieurs occurrences d'un même chemin. Compter l'itération et compter le tableau avec clés peuvent donc donner des nombres différents ; sans conservation des clés, les occurrences restent.

🧠 Comment le mémoriser : « Visites ou adresses ? » Image mentale : deux coches devant une adresse unique. Question-réflexe : compte-t-on les occurrences ou les clés conservées ?

⚠️ À ne pas confondre : même nom de fichier et même chemin.

Finder implémente IteratorAggregate : foreach, iterator_to_array(), iterator_count(), hasResults(). La clé est le chemin du fichier : deux a.txt de répertoires distincts donnent deux clés différentes.

Supposons exactement quatre fichiers : imports/a.csv, imports/b.csv, imports/c.csv, imports/archive/d.csv. Une recherche files() sur imports puis imports/archive atteint d.csv deux fois. Sans changement du disque entre observations, iterator_count() compte cinq occurrences ; iterator_to_array() en conserve quatre car la même clé est écrasée ; iterator_to_array($finder, false) conserve les cinq.

Préserver les occurrences n'est pas dédupliquer le travail : l'import doit encore décider s'il traite d.csv une ou deux fois. hasResults() cherche une première entrée ; il ne valide pas tout le lot et ne réserve pas les fichiers contre une modification concurrente.

Un ordre déterministe

À retenir en priorité
  1. Le tri naturel interprète les séquences numériques.
  2. Le tri lexical donnerait f1, f10, f2.

L'ordre d'import ou de comparaison dans un test ne doit pas dépendre du parcours natif du disque. Le tableau suppose les mêmes entrées stables ; pour les exemples f1, f10, f2, elles sont dans le même répertoire :

Appel Ordre
aucun tri celui du filesystem : ni alphabétique, ni de création
sortByName() f1, f10, f2 — comparaison de strings
sortByName(true) f1, f2, f10 — ordre naturel
sortByType() directories d'abord, puis files
->reverseSorting() l'ordre inverse du tri

Le tri par nom compare les chemins réels, ou les chemins disponibles en repli : sur plusieurs racines, ce n'est pas seulement le nom de base. Le tri charge les résultats pour les comparer ; sur un grand arbre, cela coûte de la mémoire et retarde le premier résultat. Borner la racine et les filtres avant de trier. Un ordre déterministe ne rend pas les effets de l'import transactionnels.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le critère s'interprète depuis in().
  2. Un path mal relatif peut ne rien exclure.
  • Sources, critères, tri et clés du Finder

    Avant de compter, lire les sources et les critères de la même instance ; avant de comparer une liste, lire le tri et la conservation des clés :

  • Voir l’explication : Le Finder est à état

    Le Finder est à état : deux name() s'additionnent. Cloner pour réutiliser.

  • Types d’entrées retournés par Finder

    Sans files() ni directories(), les deux sont rendus.

  • Voir l’explication : Il faut une source de recherche

    Il faut une source de recherche : habituellement in(), ou append(). Sans les deux, l'itération lève une LogicException.

  • Voir l’explication : Racines recouvrantes : iterator_to_array($finder, false) conserve les occurrences.

    Racines recouvrantes : iterator_to_array($finder, false) conserve les occurrences. Cela ne supprime pas les doublons métier.

Fiche express

À mémoriser

À retenir en priorité
  1. L'ordre du filesystem n'est pas garanti.
  2. Un test stable doit trier.

Nous avons choisi un ensemble d'entrées, pas encore traité leurs articles. Conserver cette frontière évite de confondre « fichier trouvé », « fichier lu » et « import réussi » dans le rapport.

Si tu dois retenir seulement 6 choses :

  • Une source par in() ou append() ; joker in() sans correspondance → exception.
  • Par défaut files et directories, récursif, VCS ignorés, liens non suivis.
  • Object à état : clone pour réutiliser.
  • exclude() relatif à in().
  • Plusieurs in() : iterator_to_array($finder, false).
  • Trier pour un ordre stable : sortByName(true), sortByType(), reverseSorting().

Moyen mnémotechnique : « Où, quoi, dans quel ordre — et cloner ».

La commande Custom commands peut maintenant orchestrer cette sélection. Si un outil externe doit convertir les fichiers, le cours Process explique une autre frontière : le lancement et le résultat d'un processus distinct.
