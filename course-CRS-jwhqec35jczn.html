Objectif

Trouver des files et des directories par critères chaînés, et connaître le piège qui fait échouer une réutilisation d'object.

L'essentiel

À comprendre

À retenir en priorité
  1. Les critères s'accumulent.
  2. Cloner une base avant deux recherches différentes.

Finder construit une recherche de fichiers ou de dossiers. Les appels chaînés règlent ses critères ; l'itération parcourt les résultats. in() fournit les dossiers de départ dans le cas habituel ; append() permet aussi de fournir une source de résultats.

L'objet est mutable : appeler name() change cette même recherche. Deux critères name() positifs se combinent avec OU, pas avec ET. Pour préparer deux recherches indépendantes sur une base commune, cloner la base avant d'ajouter le critère propre à chaque branche.

Le schéma

À retenir en priorité
  1. Deux variables peuvent viser le même object.
  2. Le clone sépare les configurations.

Bleu : objets de recherche distincts ; cylindres verts : résultats. Les noms sont ceux d'un dossier d'exemple contenant partial_menu, plugin_search et README. Les flèches décrivent une copie ou une itération, pas un héritage entre classes.

L'exemple : deux recherches sur une base commune

Exemple concret

À retenir en priorité
  1. L'object partagé conserve les modifications.
  2. La réutilisation exige une copie volontaire.
$finder = new Finder();
$finder->files()->in('./templates');

foreach ((clone $finder)->name('partial_*') as $file) {
    $file->getRelativePathname();
}
foreach ((clone $finder)->name('plugin_*') as $file) {
    // Sans les deux clones : partial_* OU plugin_* sur la même instance.
}

L'usage de base

À retenir en priorité
  1. Les résultats enrichissent SplFileInfo.
  2. Ils restent itérables sans conversion préalable.

Chaque résultat est un Symfony\Component\Finder\SplFileInfo, qui étend celui de PHP pour ajouter getRelativePath() et getRelativePathname(). Toutes les methods de critère se chaînent.

L'object est à état — le piège central

À retenir en priorité
  1. L'affectation ne clone pas l'object.
  2. Les deux références voient le même état.
  3. Deux Finder créés indépendamment ne partagent pas leurs critères.

Le Finder est stateful : les critères restent sur l'instance modifiée. Deux variables qui désignent cette même instance voient les mêmes changements ; deux instances distinctes ne partagent pas automatiquement leurs critères.

Avec les trois fichiers de l'exemple, name('partial_*') retient partial_menu. Ajouter name('plugin_*') sur le même objet retient partial_menu et plugin_search, car l'un ou l'autre motif suffit. Le nombre dépend des fichiers présents ; ajouter un critère n'ajoute pas nécessairement exactement un résultat. Le clone isole les critères à venir, mais ne fige pas le contenu du système de fichiers.

Quoi chercher

À retenir en priorité
  1. Le type de résultat doit être filtré.
  2. La recherche est récursive par défaut.
  • in() : un ou plusieurs directories, joker * permis — chaque pattern doit résoudre vers un directory, sinon DirectoryNotFoundException ; exclude() prend des paths relatifs à ceux d'in() ; une URL ftp:// ou zlib:// est acceptée.
  • Par défaut, files et directories ; files() ou directories() restreignent. Sans in() ni append(), l'itération lève une LogicException.
  • Récursif par défaut ; depth('== 0'), depth(['> 2', '< 5']) bornent.
  • Métadonnées VCS ignorées par défaut (ignoreVCS(false)) ; ignoreVCSIgnored(true) applique les .gitignore en partant du directory de recherche. Liens symboliques suivis seulement avec followLinks().

Récupérer les résultats

À retenir en priorité
  1. Les keys peuvent se répéter.
  2. Désactiver leur préservation conserve chaque occurrence.

Finder implémente IteratorAggregate : foreach, iterator_to_array(), iterator_count(), hasResults(). La key est le path du file : deux a.txt de directories distincts donnent deux keys, sans collision. Deux in() qui se recouvrent atteignent le même file deux fois — iterator_count() rend 5, iterator_to_array() 4, avec false en second argument 5.

Un ordre déterministe

À retenir en priorité
  1. Le tri naturel interprète les séquences numériques.
  2. Le tri lexical donnerait f1, f10, f2.
Appel Ordre
aucun tri celui du filesystem : ni alphabétique, ni de création
sortByName() f1, f10, f2 — comparaison de strings
sortByName(true) f1, f2, f10 — ordre naturel
sortByType() directories d'abord, puis files
->reverseSorting() l'ordre inverse du tri

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le critère s'interprète depuis in().
  2. Un path mal relatif peut ne rien exclure.
  • Voir l’explication : Le Finder est à état

    Le Finder est à état : deux name() s'additionnent. Cloner pour réutiliser.

  • Types d’entrées retournés par Finder

    Sans files() ni directories(), les deux sont rendus.

  • Voir l’explication : Il faut une source de recherche

    Il faut une source de recherche : habituellement in(), ou append(). Sans les deux, l'itération lève une LogicException.

  • Préserver les résultats de plusieurs répertoires

    Plusieurs in() : iterator_to_array($finder, false).

Fiche express

À mémoriser

À retenir en priorité
  1. L'ordre du filesystem n'est pas garanti.
  2. Un test stable doit trier.

Si tu dois retenir seulement 6 choses :

  • Une source par in() ou append() ; joker in() sans correspondance → exception.
  • Par défaut files et directories, récursif, VCS ignorés, liens non suivis.
  • Object à état : clone pour réutiliser.
  • exclude() relatif à in().
  • Plusieurs in() : iterator_to_array($finder, false).
  • Trier pour un ordre stable : sortByName(true), sortByType(), reverseSorting().

Moyen mnémotechnique : « Où, quoi, dans quel ordre — et cloner ».
