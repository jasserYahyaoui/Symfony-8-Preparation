Objectif

Trouver des files et des directories par critères chaînés, et connaître le piège qui fait échouer une réutilisation d'object.

L'essentiel

À comprendre

À retenir en priorité
  1. Les critères s'accumulent.
  2. Cloner une base avant deux recherches différentes.

Le Finder cherche files et directories par critères chaînés, in() étant le seul obligatoire. Il rend les deux par défaut, récursivement, dans l'ordre du filesystem. Le piège central : l'object est à état — un second name() s'ajoute au premier ; pour réutiliser une configuration, on clone.

Le schéma

À retenir en priorité
  1. Deux variables peuvent viser le même object.
  2. Le clone sépare les configurations.

L'exemple : deux recherches sur une base commune

Exemple concret

À retenir en priorité
  1. L'object partagé conserve les modifications.
  2. La réutilisation exige une copie volontaire.
$finder = new Finder();
$finder->files()->in('./templates');

foreach ((clone $finder)->name('partial_*') as $file) {
    $file->getRelativePathname();
}
foreach ((clone $finder)->name('plugin_*') as $file) {
    // sans clone : partial_* ET plugin_*
}

L'usage de base

À retenir en priorité
  1. Les résultats enrichissent SplFileInfo.
  2. Ils restent itérables sans conversion préalable.

Chaque résultat est un Symfony\Component\Finder\SplFileInfo, qui étend celui de PHP pour ajouter getRelativePath() et getRelativePathname(). Toutes les methods de critère se chaînent.

L'object est à état — le piège central

Piège à éviter

À retenir en priorité
  1. L'affectation ne clone pas l'object.
  2. Les deux références voient le même état.
  3. Deux Finder créés indépendamment ne partagent pas leurs critères.

C'est quoi ?

Finder construit une recherche de fichiers ou répertoires par critères chaînés. Il conserve son état : les appels de configuration modifient cet objet. Deux variables désignant le même Finder partagent donc leurs critères ; deux objets créés indépendamment ne sont pas modifiés ensemble.

À quoi ça sert ?

Une recherche commune peut être spécialisée sans répéter toutes ses options, à condition de cloner la base avant chaque variante. Cela évite qu'un second filtrage soit influencé par le premier.

Où dans Symfony ?

in() définit les emplacements. Sans restriction, Finder parcourt récursivement fichiers et répertoires et ignore des métadonnées VCS. files(), directories(), depth(), name() et exclude() précisent la recherche. Les résultats sont des SplFileInfo enrichis, avec notamment le chemin relatif.

Comment, étape par étape ?

  1. Définir les racines et critères communs.
  2. Cloner avant deux recherches indépendantes.
  3. Choisir explicitement le tri si le résultat doit être reproductible : le filesystem ne promet pas l'ordre alphabétique.
  4. Lors d'une conversion en tableau, décider si les clés doivent être conservées. Des racines qui se recouvrent peuvent produire plusieurs occurrences d'un même chemin.

Exemple concret PHP

Fonction de recherche en lecture seule ; le directory doit exister et être autorisé à la lecture :

<?php
use Symfony\Component\Finder\Finder;

function findSourceFiles(string $directory): array
{
    $base = (new Finder())->files()->in($directory)->sortByName(true);
    $phpFiles = iterator_to_array((clone $base)->name('*.php'), false);
    $yamlFiles = iterator_to_array((clone $base)->name('*.yaml'), false);
    return ['php' => $phpFiles, 'yaml' => $yamlFiles];
}

Les deux résultats partent de la même base sans cumuler leurs filtres spécifiques. Le false conserve les occurrences sans réutiliser les clés de l'itérateur. Contre-exemple : $yaml = $base puis modifier $yaml, en pensant avoir copié la recherche. Correction : utiliser clone ou un nouveau Finder.

Le tri naturel place f2 avant f10 ; le tri lexical peut faire l'inverse. exclude() utilise des chemins relatifs aux racines. Un directory absent doit produire un diagnostic, pas être assimilé silencieusement à « aucun fichier ». Ce mécanisme de recherche ne garantit pas que les fichiers resteront inchangés entre leur découverte et leur lecture.

Finder 8.0.

Passage canonique conservé

L'object est à état — le piège central

Le Finder est stateful : les méthodes de configuration modifient l'instance appelée. Deux variables qui désignent cette même instance voient ses nouveaux critères ; deux Finder créés indépendamment ne partagent pas cet état. Cloner la base avant chaque spécialisation permet de séparer les recherches.

Un second name() s'ajoute : un file après le premier, deux après le second, sur le même object. clone donne une copie indépendante.

Quoi chercher

À retenir en priorité
  1. Le type de résultat doit être filtré.
  2. La recherche est récursive par défaut.
  • in() : un ou plusieurs directories, joker * permis — chaque pattern doit résoudre vers un directory, sinon DirectoryNotFoundException ; exclude() prend des paths relatifs à ceux d'in() ; une URL ftp:// ou zlib:// est acceptée.
  • Par défaut, files et directories ; files() ou directories() restreignent. Sans in() ni append(), l'itération lève une LogicException.
  • Récursif par défaut ; depth('== 0'), depth(['> 2', '< 5']) bornent.
  • Métadonnées VCS ignorées par défaut (ignoreVCS(false)) ; ignoreVCSIgnored(true) applique les .gitignore en partant du directory de recherche. Liens symboliques suivis seulement avec followLinks().

Récupérer les résultats

À retenir en priorité
  1. Les keys peuvent se répéter.
  2. Désactiver leur préservation conserve chaque occurrence.

Finder implémente IteratorAggregate : foreach, iterator_to_array(), iterator_count(), hasResults(). La key est le path du file : deux a.txt de directories distincts donnent deux keys, sans collision. Deux in() qui se recouvrent atteignent le même file deux fois — iterator_count() rend 5, iterator_to_array() 4, avec false en second argument 5.

Un ordre déterministe

À retenir en priorité
  1. Le tri naturel interprète les séquences numériques.
  2. Le tri lexical donnerait f1, f10, f2.
Appel Ordre
aucun tri celui du filesystem : ni alphabétique, ni de création
sortByName() f1, f10, f2 — comparaison de strings
sortByName(true) f1, f2, f10 — ordre naturel
sortByType() directories d'abord, puis files
->reverseSorting() l'ordre inverse du tri

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le critère s'interprète depuis in().
  2. Un path mal relatif peut ne rien exclure.
  • Voir l’explication : Le Finder est à état

    Le Finder est à état : deux name() s'additionnent. Cloner pour réutiliser.

  • Types d’entrées retournés par Finder

    Sans files() ni directories(), les deux sont rendus.

  • Critère indispensable à une recherche Finder

    in() est le seul critère obligatoire.

  • Préserver les résultats de plusieurs répertoires

    Plusieurs in() : iterator_to_array($finder, false).

Fiche express

À mémoriser

À retenir en priorité
  1. L'ordre du filesystem n'est pas garanti.
  2. Un test stable doit trier.

Si tu dois retenir seulement 6 choses :

  • in() obligatoire ; joker sans correspondance → exception.
  • Par défaut files et directories, récursif, VCS ignorés, liens non suivis.
  • Object à état : clone pour réutiliser.
  • exclude() relatif à in().
  • Plusieurs in() : iterator_to_array($finder, false).
  • Trier pour un ordre stable : sortByName(true), sortByType(), reverseSorting().

Moyen mnémotechnique : « Où, quoi, dans quel ordre — et cloner ».
