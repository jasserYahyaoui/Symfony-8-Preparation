Objectif

Maîtriser le component EventDispatcher — listeners, subscribers, priorities, propagation — et connaître le catalogue des events du kernel avec ce que chacun autorise. Le déroulé de la Request est traité dans Request handling ; on s'intéresse ici au mécanisme et aux pouvoirs de chaque event.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La propagation concerne un event précis.
  2. Les events suivants du kernel ne sont pas annulés.

Le component EventDispatcher appelle, pour un event, ses listeners par priority décroissante. Listener et subscriber ne diffèrent que par qui déclare l'abonnement. stopPropagation() n'arrête que les listeners restants du même event, et seulement sur un event arrêtable. Le kernel dispatche huit events, chacun avec son pouvoir propre.

Le schéma

À retenir en priorité
  1. Chaque event expose un pouvoir adapté à son étape.
  2. kernel.terminate intervient après l'émission de la Response.

L'exemple : un subscriber

▣ Exemple concret

À retenir en priorité
  1. Un listener est enregistré de l'extérieur.
  2. Un subscriber déclare lui-même ses subscriptions.
final class OrderSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [OrderPlacedEvent::class => [['notify', 10], ['log', -10]]];
    }
}

Listener ou subscriber

Un listener est un callable enregistré de l'extérieur (addListener($nom, $callable, $priority)) ; un subscriber déclare lui-même ses events par la method statique getSubscribedEvents() : un nom de method, un couple [méthode, priorité], ou une liste de couples. Dans le framework, un subscriber est autoconfiguré ; un listener se déclare par le tag kernel.event_listener ou #[AsEventListener] (event, method, priority, dispatcher). Sans parameter event, le nom se déduit du type de l'argument par KernelEvents::ALIASES ; retirer le type fait échouer la compilation du container. Un type union abonne le listener à chacun des events.

Priority

À retenir en priorité
  1. Une priority élevée passe d'abord.
  2. Les valeurs négatives sont valides.

Un int, positif ou négatif, 0 par défaut : plus il est grand, plus tôt le listener est appelé — l'ordre est établi par un krsort(). À priority égale, l'ordre d'ajout. getListenerPriority($nom, $listener) rend la priority réelle, ou null si le listener n'est pas enregistré ; debug:event-dispatcher montre l'ordre.

Propagation

stopPropagation() saute les listeners restants du même event ; ni la Request ni les autres events ne sont interrompus. callListeners() ne consulte isPropagationStopped() que si l'event implémente StoppableEventInterface (PSR-14) : un object maison sans elle voit tous ses listeners appelés. Symfony\Contracts\EventDispatcher\Event l'implémente, donc les events du kernel sont arrêtables.

Le dispatcher gère une file de passages sur une fréquence. stopPropagation() ferme cette file pour l'event courant, pas toutes les fréquences ni tout le cycle de Request.

Le catalogue du kernel

Tous étendent KernelEvent : getRequest(), getKernel(), getRequestType(), isMainRequest().

Nom Class d'event Pouvoir spécifique
kernel.request RequestEvent setResponse() — court-circuite
kernel.controller ControllerEvent setController()
kernel.controller_arguments ControllerArgumentsEvent setArguments()
kernel.view ViewEvent getControllerResult(), setResponse()
kernel.response ResponseEvent getResponse(), setResponse()
kernel.finish_request FinishRequestEvent aucun — restauration d'état
kernel.terminate TerminateEvent aucun — la Response est partie
kernel.exception ExceptionEvent setThrowable(), setResponse()

Les constants de KernelEvents sont REQUEST, CONTROLLER, CONTROLLER_ARGUMENTS, VIEW, RESPONSE, FINISH_REQUEST, TERMINATE et EXCEPTION ; leurs valeurs sont les noms kernel.* du tableau.

Pièges d'examen

△ Piège à éviter

Priorités, propagation et événements du kernel
  • Priority haute = tôt ; une priority négative est parfaitement valide.
  • stopPropagation() n'arrête qu'un event, pas la Request.
  • getSubscribedEvents() est statique.
  • kernel.terminate ne peut plus rien changer à la Response.
  • Les constants sont sur KernelEvents ; leurs valeurs sont les strings kernel.*.
  • dispatch() sans nom explicite utilise le nom de la class, pas une string pointée.
  • Un event qui n'implémente pas StoppableEventInterface ne peut pas être arrêté — stopPropagation() n'existe même pas dessus.
  • #[AsEventListener] sans event dépend du type de l'argument, via KernelEvents::ALIASES.

Application

À retenir en priorité
  1. Chaque event expose un pouvoir adapté à son étape.
  2. kernel.terminate intervient après l'émission de la Response.
  3. Un listener est enregistré de l'extérieur.
  4. Un subscriber déclare lui-même ses subscriptions.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • Listener / subscriber : qui déclare, pas ce qui change.
  • getSubscribedEvents() est statique.
  • Priority : haute = tôt, défaut 0, négative valide (krsort).
  • stopPropagation() : cet event seulement, et s'il est StoppableEventInterface.
  • dispatch() : nom par défaut = class ; l'event est rendu.
  • Huit events de kernel ; terminate ne change plus rien.
  • #[AsEventListener] sans event : le type décide (ALIASES).

Moyen mnémotechnique : « Grand nombre, premier servi ».
