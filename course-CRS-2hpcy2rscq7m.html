Objectif

Maîtriser le component EventDispatcher — listeners, subscribers, priorities, propagation — et connaître le catalogue des events du kernel avec ce que chacun autorise. Le déroulé de la Request est traité dans Request handling ; on s'intéresse ici au mécanisme et aux pouvoirs de chaque event.

L'essentiel

À comprendre

À retenir en priorité
  1. La propagation concerne un event précis.
  2. Les events suivants du kernel ne sont pas annulés.

Le component EventDispatcher appelle, pour un event, ses listeners par priority décroissante. Listener et subscriber ne diffèrent que par qui déclare l'abonnement. stopPropagation() n'arrête que les listeners restants du même event, et seulement sur un event arrêtable. Le kernel dispatche huit events, chacun avec son pouvoir propre.

Le schéma

À retenir en priorité
  1. Chaque event expose un pouvoir adapté à son étape.
  2. kernel.terminate intervient après l'émission de la Response.

Bleu : appels ; losange orange : vérification ; capsule verte : retour. Hypothèses : événement initialement non arrêté, deux listeners, aucune exception. Le dispatcher vérifie aussi l'arrêt avant le premier listener. Les nombres 10 et −10 sont des exemples, pas des bornes de priorité. Le catalogue ci-dessous décrit les événements du kernel ; il ne promet pas qu'ils surviennent tous.

Listener ou subscriber

À comprendre

C'est quoi ?

Un listener est un callable abonné à un événement. Un subscriber est un objet qui déclare lui-même ses abonnements par la méthode statique getSubscribedEvents(). Les deux conduisent à l'appel de méthodes par le dispatcher ; la différence porte surtout sur la déclaration de ces liens.

À quoi ça sert ?

Un listener permet de configurer l'abonnement de l'extérieur. Un subscriber regroupe dans une classe les événements et méthodes qui forment une responsabilité cohérente. Aucun n'est exécuté seulement parce que sa classe existe.

Où dans Symfony ?

Avec le component seul, on utilise addListener() ou addSubscriber(). Dans le framework, les services subscribers peuvent être autoconfigurés ; les listeners utilisent notamment kernel.event_listener ou #[AsEventListener]. Ces raccords de container ne sont pas présents par magie dans un dispatcher créé manuellement.

Comment, étape par étape ?

  1. Définir le nom de l'événement et les données de son objet.
  2. Déclarer les abonnements.
  3. Enregistrer listener ou subscriber dans le dispatcher concerné.
  4. Déclencher l'événement ; le dispatcher appelle les méthodes enregistrées.

Exemple concret PHP

Avec EventDispatcher 8.0 et son autoload :

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;
final class AuditSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return ['demo.completed' => 'record'];
    }
    public function record(object $event): void { echo "appel reçu\n"; }
}
$dispatcher = new EventDispatcher();
$dispatcher->addSubscriber(new AuditSubscriber());
$dispatcher->dispatch(new stdClass(), 'demo.completed');

La sortie attendue est appel reçu. Contre-exemple : omettre addSubscriber() dans ce programme autonome en se reposant sur l'autoconfiguration du framework. Correction : enregistrer explicitement l'objet, ou utiliser l'intégration complète qui réalise cet enregistrement.

Passage canonique conservé

Un listener est un callable enregistré de l'extérieur (addListener($nom, $callable, $priority)) ; un subscriber déclare lui-même ses events par la method statique getSubscribedEvents() : un nom de method, un couple [méthode, priorité], ou une liste de couples. Dans le framework, un subscriber est autoconfiguré ; un listener se déclare par le tag kernel.event_listener ou #[AsEventListener] (event, method, priority, dispatcher). Sans parameter event, le nom se déduit du type de l'argument par KernelEvents::ALIASES ; retirer le type fait échouer la compilation du container. Un type union abonne le listener à chacun des events.

Priority

À comprendre

À retenir en priorité
  1. Une priority élevée passe d'abord.
  2. Les valeurs négatives sont valides.

C'est quoi ?

La priorité d'un listener est un entier qui règle sa position parmi les listeners du même événement. La valeur par défaut est 0 ; une valeur plus haute est appelée plus tôt. Une valeur négative signifie donc « après zéro », pas « désactivé ».

À quoi ça sert ?

Un traitement peut préparer les données pour un autre, ou intervenir avant un traitement de secours. La priorité doit exprimer une dépendance d'ordre réelle. Mettre un grand nombre partout ne résout pas les conflits : cela les déplace.

Où dans Symfony ?

addListener() reçoit la priorité en troisième argument. Un subscriber peut la déclarer dans ses couples méthode/priorité. Dans l'application, debug:event-dispatcher permet d'inspecter l'ordre enregistré. À priorité égale, le dispatcher conserve l'ordre d'ajout.

Comment, étape par étape ?

  1. Regrouper les listeners par nom d'événement.
  2. Trier leurs priorités par ordre décroissant.
  3. À égalité, conserver l'ordre d'enregistrement.
  4. Avant chaque appel, tenir compte d'un éventuel arrêt de propagation : être dans la liste ne garantit pas être appelé.

Exemple concret PHP

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;
$dispatcher = new EventDispatcher();
$dispatcher->addListener('demo', static function (): void { echo "zéro\n"; });
$dispatcher->addListener('demo', static function (): void { echo "dix\n"; }, 10);
$dispatcher->addListener('demo', static function (): void { echo "moins dix\n"; }, -10);
$dispatcher->dispatch(new stdClass(), 'demo');

Avec le component chargé, l'ordre attendu est dix, zéro, moins dix, même si le listener à zéro a été ajouté en premier. Contre-exemple : trier les nombres en ordre croissant ou confondre priorité de listener et ordre d'assemblage des décorateurs. Correction : pour les événements, la plus haute priorité est appelée d'abord ; la décoration a une autre mécanique.

Passage canonique conservé

Un int, positif ou négatif, 0 par défaut : plus il est grand, plus tôt le listener est appelé — l'ordre est établi par un krsort(). À priority égale, l'ordre d'ajout. getListenerPriority($nom, $listener) rend la priority réelle, ou null si le listener n'est pas enregistré ; debug:event-dispatcher montre l'ordre.

Propagation

À comprendre

C'est quoi ?

La propagation est le parcours des listeners d'un événement. stopPropagation() demande de ne pas appeler ceux qui restent pour cet objet événement. Elle n'annule pas les effets des listeners déjà exécutés et n'arrête pas tout le programme.

À quoi ça sert ?

Un événement peut représenter une recherche de réponse : une fois le résultat fourni, les traitements de secours ne doivent plus l'écraser. Cet arrêt doit rester limité à ce contrat ; il n'est pas un remplacement de la gestion d'erreurs ou d'une transaction métier.

Où dans Symfony ?

Le dispatcher consulte l'arrêt pour les objets implémentant StoppableEventInterface. Symfony\Contracts\EventDispatcher\Event fournit ce mécanisme. Une classe possédant seulement une méthode de même nom, sans le contrat attendu, ne suffit pas à garantir l'arrêt par le dispatcher.

Comment, étape par étape ?

  1. Appeler les listeners dans leur ordre.
  2. Un listener modifie l'événement puis arrête sa propagation.
  3. Le dispatcher saute les listeners restants de cet événement.
  4. L'appelant reprend après dispatch() ; d'autres événements peuvent être déclenchés.

Exemple concret PHP

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Contracts\EventDispatcher\Event;
$dispatcher = new EventDispatcher();
$dispatcher->addListener('demo', static function (Event $event): void {
    echo "premier\n";
    $event->stopPropagation();
}, 10);
$dispatcher->addListener('demo', static function (): void { echo "second\n"; });
$dispatcher->dispatch(new Event(), 'demo');
echo "après dispatch\n";

On attend premier, puis après dispatch, sans second. Contre-exemple : conclure que l'arrêt de kernel.request supprime nécessairement kernel.response. Correction : l'arrêt concerne les listeners restants du premier événement ; le kernel peut poursuivre son cycle avec la réponse fournie et déclencher le second.

Passage canonique conservé

stopPropagation() saute les listeners restants du même event ; ni la Request ni les autres events ne sont interrompus. callListeners() ne consulte isPropagationStopped() que si l'event implémente StoppableEventInterface (PSR-14) : un object maison sans elle voit tous ses listeners appelés. Symfony\Contracts\EventDispatcher\Event l'implémente, donc les events du kernel sont arrêtables.

Le dispatcher gère une file de passages sur une fréquence. stopPropagation() ferme cette file pour l'event courant, pas toutes les fréquences ni tout le cycle de Request.

Le catalogue du kernel

À comprendre

C'est quoi ?

Les événements du kernel exposent des étapes précises du traitement HTTP. Leur classe indique quelles données sont disponibles et quelles modifications ont un sens. Tous donnent accès au kernel, à la Request et au type de demande via KernelEvent.

À quoi ça sert ?

Choisir l'événement adapté évite de modifier une réponse après son émission ou de chercher un résultat de controller avant son appel. Une sous-requête peut déclencher ces points ; isMainRequest() permet de limiter un traitement à la principale lorsque c'est nécessaire.

Où dans Symfony ?

  • KernelEvents::REQUEST, kernel.request, RequestEvent : fournir une réponse avant le controller.
  • CONTROLLER, kernel.controller, ControllerEvent : remplacer le callable choisi.
  • CONTROLLER_ARGUMENTS, kernel.controller_arguments, ControllerArgumentsEvent : modifier arguments et controller avant appel.
  • VIEW, kernel.view, ViewEvent : convertir un résultat qui n'est pas une Response.
  • RESPONSE, kernel.response, ResponseEvent : inspecter ou remplacer la réponse avant son retour au runner.
  • FINISH_REQUEST, kernel.finish_request, FinishRequestEvent : terminer le contexte et restaurer l'état nécessaire après un traitement imbriqué.
  • TERMINATE, kernel.terminate, TerminateEvent : intervenir après la phase d'envoi conduite par le runner, sans garantie universelle sur la réception déjà achevée côté client.
  • EXCEPTION, kernel.exception, ExceptionEvent : remplacer le throwable ou fournir une réponse d'erreur.

Comment, étape par étape ?

  1. Identifier la donnée à lire ou modifier.
  2. Choisir l'étape où elle existe.
  3. Vérifier si le traitement concerne aussi les sous-requêtes.
  4. Enregistrer le listener et respecter le pouvoir de sa classe d'événement ; kernel.view n'a pas lieu si une Response existe déjà.

Exemple concret PHP

Dans une application où ce service est découvert et autoconfiguré :

<?php
use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\ResponseEvent;
use Symfony\Component\HttpKernel\KernelEvents;
#[AsEventListener(event: KernelEvents::RESPONSE)]
final class CourseHeaderListener
{
    public function __invoke(ResponseEvent $event): void
    {
        if (!$event->isMainRequest()) {
            return;
        }
        $event->getResponse()->headers->set('X-Course', 'architecture');
    }
}

Le header est ajouté à la réponse principale avant son émission normale. Contre-exemple : déplacer cette modification dans kernel.terminate pour garantir sa présence chez le client. Correction : modifier l'objet pendant kernel.response, avant l'envoi.

Passage canonique conservé

Tous étendent KernelEvent : getRequest(), getKernel(), getRequestType(), isMainRequest().

Nom Class d'event Pouvoir spécifique
kernel.request RequestEvent setResponse() — court-circuite
kernel.controller ControllerEvent setController()
kernel.controller_arguments ControllerArgumentsEvent setArguments()
kernel.view ViewEvent getControllerResult(), setResponse()
kernel.response ResponseEvent getResponse(), setResponse()
kernel.finish_request FinishRequestEvent aucun — restauration d'état
kernel.terminate TerminateEvent aucun — la Response est partie
kernel.exception ExceptionEvent setThrowable(), setResponse()

Les constants de KernelEvents sont REQUEST, CONTROLLER, CONTROLLER_ARGUMENTS, VIEW, RESPONSE, FINISH_REQUEST, TERMINATE et EXCEPTION ; leurs valeurs sont les noms kernel.* du tableau.

Pièges d'examen

Piège à éviter

Priorités, propagation et événements du kernel
  • Priority haute = tôt ; une priority négative est parfaitement valide.
  • stopPropagation() n'arrête qu'un event, pas la Request.
  • getSubscribedEvents() est statique.
  • kernel.terminate ne peut plus rien changer à la Response.
  • Les constants sont sur KernelEvents ; leurs valeurs sont les strings kernel.*.
  • dispatch() sans nom explicite utilise le nom de la class, pas une string pointée.
  • Sans StoppableEventInterface, le dispatcher ne consulte pas l'état d'arrêt, même si l'objet possède une méthode nommée stopPropagation().
  • #[AsEventListener] sans event dépend du type de l'argument, via KernelEvents::ALIASES.

Application

À retenir en priorité
  1. Chaque event expose un pouvoir adapté à son étape.
  2. kernel.terminate intervient après l'émission de la Response.
  3. Un listener est enregistré de l'extérieur.
  4. Un subscriber déclare lui-même ses subscriptions.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Listener / subscriber : qui déclare, pas ce qui change.
  • getSubscribedEvents() est statique.
  • Priority : haute = tôt, défaut 0, négative valide (krsort).
  • stopPropagation() : cet event seulement, et s'il est StoppableEventInterface.
  • dispatch() : nom par défaut = class ; l'event est rendu.
  • Huit events de kernel ; terminate ne change plus rien.
  • #[AsEventListener] sans event : le type décide (ALIASES).

Moyen mnémotechnique : « Grand nombre, premier servi ».
