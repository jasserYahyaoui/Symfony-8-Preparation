Objectif

Traiter une submission dans le bon ordre, savoir ce que handleRequest() décide à ta place, et ce que submit($data, false) valide vraiment.

L'essentiel

À comprendre

À retenir en priorité
  1. Une action peut afficher et traiter le form.
  2. Après succès, un redirect sépare traitement et affichage.

Une seule action affiche et traite le form : handleRequest() soumet le form seulement si la Request lui est destinée, puis le garde isSubmitted() && isValid() décide entre le redirect et le rendu. Après une submission, l'object est déjà à jour. submit($data, false) garde les fields absents, sans les dispenser des constraints de la class.

Le schéma

À retenir en priorité
  1. isSubmitted() ne signifie pas valide.
  2. isValid() sur un form non soumis lève une LogicException.

L'exemple : une `Task`

Exemple concret

À retenir en priorité
  1. Tester d'abord si la Request a réellement soumis le form.
  2. isValid() vient ensuite ; le garde court-circuité évite l'appel prématuré.
class Example0b3ebc88
{
    #[Route('/task/new', name: 'task_new')]
    public function new(Request $request): Response
    {
        $task = new Task();                          // #[Assert\NotBlank] sur $title
        $form = $this->createForm(TaskType::class, $task);
        $form->handleRequest($request);

        if ($form->isSubmitted() && $form->isValid()) {
            // $task contient déjà les valeurs saisies
            return $this->redirectToRoute('task_success');
        }

        return $this->render('task/new.html.twig', ['form' => $form]);
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Le pattern recommandé

À comprendre

C'est quoi ?

Une action unique peut afficher le formulaire initial, traiter sa soumission puis afficher ses erreurs ou rediriger après succès. handleRequest distingue une requête qui soumet ce formulaire d'une simple consultation ; il ne sauvegarde aucune donnée métier par lui-même.

À quoi ça sert ?

La définition du formulaire reste identique entre affichage et traitement. Le parcours POST puis redirection vers GET évite qu'un rafraîchissement normal de la page de résultat renvoie le même POST.

Où dans Symfony ?

L'intégration HTTP de Form doit être disponible. On vérifie isSubmitted puis isValid avant l'opération ; une donnée liée peut déjà avoir changé en mémoire même si elle est invalide. AbstractController peut recevoir directement le Form dans render et préparer sa vue ; une soumission invalide reçoit le statut adapté par ce raccourci.

Comment, étape par étape ?

  1. Construire le formulaire avec les données initiales.
  2. Appeler handleRequest une fois.
  3. En cas de soumission valide, effectuer l'opération puis rediriger.
  4. Sinon, rendre le formulaire avec les erreurs et les champs techniques.

Exemple concret PHP et Twig

Méthode d'AbstractController dans une application avec Form, Validator, Twig, session et CSRF configurés :

#[\Symfony\Component\Routing\Attribute\Route('/preferences', name: 'preferences', methods: ['GET', 'POST'])]
public function preferences(\Symfony\Component\HttpFoundation\Request $request): \Symfony\Component\HttpFoundation\Response
{
    $form = $this->createFormBuilder(['name' => $request->getSession()->get('display_name', '')])
        ->add('name', \Symfony\Component\Form\Extension\Core\Type\TextType::class, [
            'constraints' => [new \Symfony\Component\Validator\Constraints\NotBlank()],
        ])->getForm();
    $form->handleRequest($request);
    if ($form->isSubmitted() && $form->isValid()) {
        $request->getSession()->set('display_name', $form->get('name')->getData());
        return $this->redirectToRoute('preferences', status: 303);
    }
    return $this->render('preferences.html.twig', ['form' => $form]);
}

GET affiche ; un POST valide met à jour la session puis redirige ; un POST invalide réaffiche les erreurs. Contre-exemple : sauvegarder immédiatement après handleRequest, avant les tests. Correction : réserver l'effet métier à la branche valide. Ne pas appeler submit ensuite sur la même instance déjà soumise.

Passage canonique conservé

Le pattern recommandé

handleRequest() est ce qui permet à une seule action de servir l'affichage et le traitement : sans submission pour ce form, il ne fait rien, et le code tombe sur le render(). Le redirect après succès évite qu'un rafraîchissement renvoie le POST.

Quand `handleRequest()` soumet-il ?

À retenir en priorité
  1. handleRequest() ignore une method différente.
  2. Le nom du form détermine aussi les données recherchées.

HttpFoundationRequestHandler (8.0) teste, dans l'ordre :

  1. La method de la Request = l'option method du form (POST par défaut).
  2. Le nom du form : lu dans la query string pour GET, HEAD et TRACE, dans le body et les files sinon.
  3. Puis submit($data, 'PATCH' !== $method).
Situation isSubmitted()
form POST, Request GET portant ses fields false
form 'method' => 'GET', ?task_form[title]=x true
form POST, Request POST sans key task_form false
form 'method' => 'PATCH', Request PATCH partielle true, absents conservés

L'ordre des deux tests

Piège à éviter

C'est quoi ?

isSubmitted indique que le Form a reçu une soumission ; isValid indique que le formulaire soumis ne porte pas d'erreur selon son traitement. Ces états ne se confondent pas : une soumission mal formée ou un token CSRF refusé peut produire un formulaire soumis mais invalide.

À quoi ça sert ?

Une action peut afficher le formulaire initial et traiter ses données sans enregistrer une valeur avant qu'elle ait été soumise et contrôlée. Tester dans le mauvais ordre ne revient pas simplement à obtenir false : isValid lève une LogicException sur un formulaire non soumis.

Où dans Symfony ?

handleRequest détermine si la Request correspond à la méthode et au nom du formulaire ; sans soumission pertinente il laisse son état initial. submit est une soumission explicite et ne s'appelle qu'une fois pour la même instance. La validation des contraintes suppose l'extension Validator ; les erreurs de transformation font aussi partie du traitement.

Comment, étape par étape ?

  1. Construire le formulaire avec ses données initiales.
  2. Appeler handleRequest, ou submit si l'on gère explicitement l'extraction.
  3. Tester isSubmitted avant isValid, en profitant du court-circuit de &&.
  4. Ne sauvegarder qu'après réussite ; sinon rendre le formulaire et ses erreurs. Une modification en mémoire du modèle ne constitue pas une validation ni une sauvegarde réussie.

Exemple concret PHP

Fonction recevant un formulaire configuré pour la Request ; le booléen retourné autorise seulement la suite du traitement :

<?php
use Symfony\Component\Form\FormInterface;
use Symfony\Component\HttpFoundation\Request;

function maySave(FormInterface $form, Request $request): bool
{
    $form->handleRequest($request);

    return $form->isSubmitted() && $form->isValid();
}

Sur l'affichage initial, le second test n'est pas exécuté. Contre-exemple : inverser les deux appels ou les combiner avec un opérateur qui évalue systématiquement les deux côtés. Correction : conserver cet ordre avec &&. Après sauvegarde, une redirection adaptée sépare la consultation du résultat de la soumission et limite son renvoi lors d'un rafraîchissement.

Passage canonique conservé

L'ordre des deux tests

isValid() sur un form non soumis lève une LogicException : « Cannot check if an unsubmitted form is valid… ». isSubmitted() vaut true même si les données sont invalides ; isValid() compte aussi les erreurs des fields enfants.

Le guichet distingue « le document a-t-il été remis ? » de « a-t-il passé les contrôles ? ». isSubmitted() et isValid() posent ces deux questions dans cet ordre, même lorsqu'une submission est invalide.

Repère de l’exemple : Calling isValid() on an unsubmitted form raises a LogicException. Tester d'abord si la Request a réellement soumis le form. isValid() vient ensuite ; le garde court-circuité évite l'appel prématuré.

L'object est déjà à jour

À comprendre

À retenir en priorité
  1. La submission met à jour le modèle mappé.
  2. Ne pas soumettre le même form une deuxième fois.

C'est quoi ?

Lorsqu'un formulaire est lié à un objet mutable avec le mapping habituel, la soumission peut écrire directement dans cet objet. getData peut alors retourner la même instance, déjà modifiée ; ce n'est pas systématiquement une copie à appliquer plus tard.

À quoi ça sert ?

Le mapping évite de recopier manuellement chaque champ. Il oblige aussi à séparer modification en mémoire, validité et sauvegarde durable : une validation en échec ne constitue pas un retour automatique à l'état initial.

Où dans Symfony ?

Le mapper écrit les enfants synchronisés et mappés selon la configuration. Les options de référence, de mapping, les données immuables et les transformers peuvent modifier ce comportement ; l'identité d'objet décrite ici concerne le cas mutable ordinaire. Une même instance de Form ne se soumet qu'une fois.

Comment, étape par étape ?

  1. Garder la référence de l'objet initial.
  2. Soumettre le Form une seule fois.
  3. Examiner sa donnée et sa validité sans supposer un rollback.
  4. N'effectuer la sauvegarde durable qu'après les contrôles requis ; prévoir une copie ou un objet d'entrée séparé si l'original doit rester intact avant acceptation.

Exemple concret PHP

Avec Form chargé ; le script illustre seulement le mapping en mémoire :

<?php
use Symfony\Component\Form\Forms;
use Symfony\Component\Form\Extension\Core\Type\FormType;
use Symfony\Component\Form\Extension\Core\Type\TextType;
final class EditableName { public string $name = 'Ada'; }
$value = new EditableName();
$form = Forms::createFormFactory()->createBuilder(FormType::class, $value)->add('name', TextType::class)->getForm();
$form->submit(['name' => 'Grace']);
var_dump($form->getData() === $value, $value->name);

On attend true puis Grace ; aucune base de données n'a été utilisée. Contre-exemple : réutiliser l'objet en pensant qu'isValid remettra automatiquement Ada si une contrainte échoue. Correction : concevoir explicitement l'isolation ou la restauration nécessaire et ne sauvegarder qu'après validation. Appeler submit une seconde fois ne recommence pas le cycle : il faut une nouvelle instance de formulaire.

Passage canonique conservé

L'object est déjà à jour

  • L'object passé à createForm() est modifié en place : $form->getData() === $task.
  • Un form ne se soumet qu'une fois : un second submit() lève une AlreadySubmittedException, « A form can only be submitted once. ».
  • AbstractController::render() passe la Response en 422 pour un form soumis et invalide, et convertit le form en vue sans createView(). renderView() rend une string : pas de 422.

`submit()`, pour le contrôle fin

À retenir en priorité
  1. clearMissing vaut true par défaut.
  2. Le false correspond au traitement partiel.
if ($request->isMethod('POST')) {
    $form->submit($request->getPayload()->all($form->getName()));
}
  • L'exemple de forms.rst écrit getPayload()->get(…) : pour un form composé, la valeur est un array, et InputBag::get() lève une BadRequestException. Il faut all().
  • $clearMissing vaut true par défaut : un field absent devient null ; false le garde — le choix de handleRequest() pour un form PATCH.

Repère — Quand handleRequest() soumet-il ? : No. The request method and expected form data must match. handleRequest() ignore une method différente. Le nom du form détermine aussi les données recherchées.

`clearMissing` et la validation

Piège à éviter

À retenir en priorité
  1. Distinguer constraints du field et du modèle.
  2. Préserver une valeur ne la dispense pas de validation d'object.

C'est quoi ?

submit($data, $clearMissing) applique une soumission au formulaire. Avec true, valeur par défaut, un champ omis est traité comme manquant et soumis avec une valeur nulle avant les conversions propres au type. Avec false, un enfant absent du tableau n'est pas soumis et conserve sa donnée.

Cela ne signifie pas « ignorer toute validation de cette propriété ». Une contrainte placée sur le champ absent et une contrainte placée sur l'objet parent n'empruntent pas le même chemin.

À quoi ça sert ?

Une mise à jour partielle doit distinguer « remplacer cette valeur » de « ne pas la modifier ». false convient à cette seconde sémantique. Il ne faut pas l'utiliser comme moyen de faire accepter un objet invalide : l'extension Validator peut encore valider l'objet entier, y compris ses contraintes sur une propriété omise.

Où dans Symfony ?

handleRequest() délègue à un gestionnaire de requête ; dans l'intégration HTTP, une soumission PATCH utilise cette logique partielle. Pour un appel explicite, le développeur choisit le second argument de submit() et fournit directement les données du formulaire, pas nécessairement toute l'enveloppe HTTP.

Comment, étape par étape ?

  1. Construire le formulaire avec les valeurs actuelles.
  2. Soumettre une seule fois les champs reçus ; distinguer clé absente et clé présente avec null.
  3. Tester isSubmitted() avant isValid() ; le second appel seul est interdit avant soumission.
  4. Après succès, effectuer l'opération métier. L'objet lié peut déjà avoir été modifié pendant la soumission ; isValid() n'est pas une transaction qui annule ces changements.

Exemple concret PHP

Ce script de component illustre la conservation, pas la validation métier ni le CSRF d'un formulaire HTTP.

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Form\Extension\Core\Type\FormType;
use Symfony\Component\Form\Extension\Core\Type\TextType;
use Symfony\Component\Form\Forms;

$form = Forms::createFormFactory()
    ->createBuilder(FormType::class, ['name' => 'Ada', 'city' => 'Paris'])
    ->add('name', TextType::class)
    ->add('city', TextType::class)
    ->getForm();
$form->submit(['name' => 'Grace'], false);
var_export($form->getData());

Le tableau attendu contient name => Grace et city => Paris. Contre-exemple : envoyer ['city' => null] en croyant préserver la ville parce que $clearMissing vaut false. La clé est présente : le champ est soumis. Correction : omettre la clé pour préserver, ou envoyer une valeur explicitement voulue pour remplacer. Pour vérifier une contrainte de champ sur une valeur omise, ajouter sa clé signifie aussi soumettre cette valeur : ce n'est pas un contrôle sans mutation.

Passage canonique conservé

clearMissing et la validation

La documentation (« Constraints At Field Level ») dit qu'avec false, seules les constraints des fields soumis sont évaluées. Le code 8.0 nuance :

Constraint de email, absent de submit(['nick' => 'z'], false) Résultat
option constraints du field sautée
attribute sur User::$email, valeur stockée invalide invalide : l'object entier est validé

Pour forcer la validation d'un field absent : ajouter sa key à null avant de soumettre — null remplace alors la valeur stockée.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Une action : handleRequest(), garde, redirect, render().
  • Soumis seulement si method = option method et nom du form présent.
  • isSubmitted() avant isValid(), sinon LogicException.
  • L'object est modifié en place ; un form ne se soumet qu'une fois.
  • render() : 422 pour un form soumis et invalide.
  • submit($data, false) garde les absents ; PATCH le fait seul.
  • false saute l'option constraints, pas les constraints de la class.

Moyen mnémotechnique : « Method, nom, submission ; soumis, puis valide ».
