Objectif

Brancher un téléversement sur un form sans corrompre l'entité. UploadedFile, move() et le caractère non fiable des métadonnées client sont traités dans le Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Séparer le file temporaire et sa référence persistante.
  2. Appliquer les constraints directement au field non mappé.

L'entité stocke le nom d'un file ; le form reçoit un file téléversé. Le field FileType est donc déclaré mapped: false, porte ses propres constraints, et le controller lit le file sur le form avant de le déplacer et d'écrire le nom sur l'entité.

Le schéma

L'exemple : la brochure

Exemple concret

À retenir en priorité
  1. FileType fournit un UploadedFile, pas le nom final du file.
  2. La property string reçoit le nom après traitement ; mapped: false évite ce mapping incompatible.
class Product
{
    public string $name = '';
    public string $brochure = '';   // le nom du fichier, pas le fichier
}

Le field

À comprendre

C'est quoi ?

FileType représente un fichier soumis, pas le nom final à stocker durablement. Dans un formulaire d'édition, le modèle peut conserver un nom de fichier existant tandis que le champ reçoit un nouvel UploadedFile temporaire : ces deux données ont des types et des durées de vie différents.

À quoi ça sert ?

Les séparer évite de remplacer un nom durable par un chemin temporaire. Un champ non mappé permet de traiter explicitement le remplacement, de conserver l'ancien fichier si aucun nouveau n'est envoyé et de ne modifier le modèle qu'après la réussite du stockage.

Où dans Symfony ?

mapped: false exclut le champ du mapping automatique ; required: false exprime qu'une nouvelle sélection n'est pas imposée par le rendu. La contrainte File valide la taille et les extensions autorisées ; cette validation nécessite Validator et, pour la vérification d'extension/type, Mime. required ne remplace pas une contrainte serveur de présence.

Comment, étape par étape ?

  1. Déclarer le FileType avec des contraintes propres au fichier reçu.
  2. Rendre le formulaire avec form_start pour le bon encodage multipart.
  3. Après soumission valide, lire get('brochure')->getData.
  4. Si cette valeur est absente dans un parcours de modification facultatif, conserver l'existant ; sinon déplacer le fichier et enregistrer seulement son identifiant durable après réussite.

Exemple concret PHP

Extrait de buildForm d'un type, dans une application équipée des extensions nécessaires :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function buildForm(\Symfony\Component\Form\FormBuilderInterface $builder, array $options): void
{
    $builder->add('brochure', \Symfony\Component\Form\Extension\Core\Type\FileType::class, [
        'mapped' => false,
        'required' => false,
        'constraints' => [new \Symfony\Component\Validator\Constraints\File(maxSize: '1024k', extensions: ['pdf'])],
    ]);
}

Contre-exemple : mapper ce champ directement sur une propriété qui contient une chaîne de nom durable et croire qu'il effectuera le stockage final. Selon les types et accessors, cela peut provoquer une erreur ou une donnée incorrecte. Correction : séparer le fichier reçu du nom enregistré. Un champ FileType peut être mappé lorsqu'un modèle adapté attend réellement un File ; mapped false n'est donc pas une interdiction universelle du mapping des fichiers.

Le field

$builder->add('brochure', FileType::class, [
    'label' => 'Brochure (PDF)',
    'mapped' => false,
    'required' => false,
    'constraints' => [
        new Assert\File(maxSize: '1024k', extensions: ['pdf']),

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Option Pourquoi
mapped: false dans cet exemple, le modèle conserve un nom durable, pas l'objet reçu par FileType
required: false téléversement facultatif : sur un form de modification, rien envoyé = garder l'existant
constraints un field non mappé ne profite pas des constraints de l'entité
  • Laisser ce champ mappé à une propriété contenant un nom durable string peut lever une LogicException dès la construction, ou conduire à un mapping incorrect ; l'échec n'est pas nécessairement silencieux. mapped: false convient ici : lire le File séparément puis affecter son nom durable au modèle. Un champ mappé reste possible si le modèle attend réellement un File.
  • Un b.txt échoue : « The extension of the file is invalid ("txt"). Allowed extensions are "pdf". ».
  • L'option extensions exige le component Mime : sans lui, FileValidator lève une LogicException.

Un CV agrafé à un dossier voyage avec le formulaire mais ne devient pas automatiquement le texte d'une case. mapped: false sépare l'attachment du modèle, sans supprimer les contraintes du field.

Récupérer le file

À comprendre

À retenir en priorité
  1. Tester la présence du file avant déplacement.
  2. Lire la donnée sur le field non mappé.

C'est quoi ?

FileType représente un fichier envoyé par le navigateur. Après une soumission réussie, sa donnée est un UploadedFile, objet qui décrit un fichier temporaire reçu. Une propriété qui stocke un nom de fichier durable ne représente pas la même chose : il faut organiser explicitement le passage de l'un à l'autre.

À quoi ça sert ?

Déclarer ce champ avec mapped: false évite d'écrire automatiquement l'objet temporaire dans une propriété destinée au nom stocké. Le champ existe toujours, reçoit la soumission et peut porter ses propres contraintes ; « non mappé » ne signifie pas « non traité » ou « non validé ».

Où dans Symfony ?

Le builder ajoute le champ. Le renderer produit l'encodage de formulaire adapté. Le gestionnaire HTTP transmet les fichiers au component Form. L'application lit ensuite $form->get('brochure')->getData(), puis déplace le fichier et conserve son nom selon sa politique de stockage.

Comment, étape par étape ?

  1. Ajouter FileType, mapped: false et les contraintes de fichier au champ.
  2. Pour une modification où l'absence de nouveau fichier conserve l'ancien, prévoir un champ facultatif ; required: false seul n'est pas une règle de validation complète.
  3. Traiter la soumission et ses erreurs avant d'écrire sur le stockage durable.
  4. Lire la donnée du champ. Si elle vaut null, ne pas effacer l'ancien nom par accident.
  5. Choisir un nom côté serveur, déplacer le fichier, puis mettre à jour le modèle. Gérer explicitement une erreur de déplacement.

Exemple concret PHP

Extrait à placer dans buildForm() d'un type ; $builder est le FormBuilderInterface reçu par cette méthode. L'extension Validator est nécessaire pour appliquer les contraintes.

$builder->add('brochure', \Symfony\Component\Form\Extension\Core\Type\FileType::class, [
    'mapped' => false,
    'required' => false,
    'constraints' => [
        new \Symfony\Component\Validator\Constraints\File(
            maxSize: '1024k',
            extensions: ['pdf'],
        ),
    ],
]);

L'extension et la taille sont vérifiées côté serveur ; le nom annoncé par le navigateur n'est pas utilisé comme chemin de destination. Contre-exemple : lire $product->brochure pour récupérer le nouvel upload alors que le champ est non mappé. Correction : lire le champ avec get('brochure')->getData(). Autre erreur : rendre le champ facultatif puis appeler move() sans tester null. L'absence de nouvel upload est un cas normal, pas un fichier vide à déplacer.

Passage canonique conservé

Récupérer le file

$file = $form->get('brochure')->getData();
if ($file) {
    // déplacer le fichier, puis stocker son nom sur l'entité
}

Un file envoyé : un UploadedFile, et $product->brochure reste vide. Rien envoyé, avec required: false : le form est valide et getData() vaut null — d'où le test.

Ce que `FileType` écarte

À retenir en priorité
  1. Le handler distingue les files des strings.
  2. multiple: true produit un array de files.
  • Un listener PRE_SUBMIT de FileType ne garde que de vrais files téléversés : une string postée à la place devient null, sans erreur.
  • multiple: true : la valeur est un array de files, et data_class vaut null.
  • Le handler compte : HttpFoundationRequestHandler, celui du framework, reconnaît un UploadedFile ; le handler natif attend l'array de $_FILES.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un field de file n'est presque jamais mappé

    Un field de file n'est presque jamais mappé — et le mapper par erreur n'échoue pas : l'entité reçoit le path temporaire.

  • Voir l’explication : Un field non mappé n'arrive pas dans l'object

    Un field non mappé n'arrive pas dans l'object, et vaut null quand rien n'a été envoyé.

  • Où déclarer les contraintes d’un champ non mappé

    Les constraints d'un field non mappé se déclarent sur le field.

  • Voir l’explication : extensions sans le component Mime

    extensions sans le component Mime : LogicException.

Application

À retenir en priorité

  2. Lire la donnée sur le field non mappé.
  3. Séparer le file temporaire et sa référence persistante.
  4. Appliquer les constraints directement au field non mappé.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • FileType : mapped: false — mappé, l'entité reçoit le path temporaire.
  • Lire le file sur le form, par son field : get(), puis getData().
  • Rien envoyé : null ; tester avant d'utiliser.
  • Constraints : sur le field, option constraints.
  • extensions sans Mime : LogicException.
  • Une string postée → null ; multiple: true → un array.

Moyen mnémotechnique : « Recevoir, valider, déplacer, nommer ».
