Objectif

Inspecter le contenu d'une variable dans un template, savoir où le résultat apparaît, et ce qui se passe hors du développement.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La disponibilité dépend des extensions et du mode debug.
  2. Retirer les dumps avant publication.

dump existe en function et en tag, qui n'écrivent pas au même endroit. Les deux viennent de DebugBundle, actif en dev et test : un dump() oublié en production fait échouer la compilation. Deux commands inspectent les templates sans les rendre.

Le schéma

À retenir en priorité
  1. La function modifie le contenu de la page.
  2. Le tag utilise l'intégration de debug.

Deux formes, deux destinations

Écriture Où va le résultat
{{ dump(article) }} dans la page, à l'endroit de l'appel
{% dump articles %} dans la debug toolbar, la page reste intacte
  • Sans argument, {{ dump() }} comme {% dump %} sortent tout le contexte du template, macros exclues.
  • Le tag nomme ce qu'il affiche : {% dump articles, user %}.
  • La function n'accepte que des arguments positionnels : l'exemple de la documentation {{ dump(blog_posts: articles, user: app.user) }} lève SyntaxError: Unknown arguments avec Twig 3.22.

La valise de diagnostic affiche les mêmes données soit sur le tableau de bord, soit sur une console d'atelier. De même, la function dump imprime dans la page, tandis que le tag utilise la destination de debug.

Hors du développement

DebugBundle enregistre l'extension (twig.extension.dump). Selon le cas :

DebugBundle kernel.debug {{ dump(x) }} {% dump x %}
oui oui dump HTML dans la page vers la toolbar
oui non rien rien
non oui var_dump brut de Twig tag inconnu
non non « Unknown function "dump" » tag inconnu

La production est la dernière ligne : un dump() oublié fait échouer la compilation du template — l'« erreur PHP » que décrit la documentation. C'est délibéré : un dump divulguerait l'état interne de l'application.

Les commands

○ À comprendre

À retenir en priorité
  1. Le lint n'exécute pas les branches du template.
  2. Un test de rendu reste nécessaire pour les données runtime.

C'est quoi ?

Déboguer un template demande de distinguer sa syntaxe, les extensions disponibles et les valeurs au moment du rendu. lint:twig contrôle la syntaxe ; debug:twig décrit l'environnement ; dump inspecte des données pendant un rendu. Aucun de ces outils ne remplace les deux autres.

À quoi ça sert ?

Une variable peut manquer alors que le template compile. Inversement, une fonction inconnue peut empêcher la compilation avant qu'on puisse inspecter une valeur. Choisir l'outil correspondant à la phase d'échec évite de chercher un problème de données dans le parseur, ou l'inverse.

Où dans Symfony ?

L'intégration de débogage dépend des extensions et de la configuration de l'environnement. Avec l'intégration de développement habituelle, la fonction dump affiche à l'endroit de l'appel ; le tag transmet ses données au dispositif de débogage, notamment la toolbar lorsqu'elle est disponible. Ne pas supposer ce comportement identique dans un Twig autonome ou en production.

Comment, étape par étape ?

  1. Vérifier la syntaxe du fichier.
  2. Vérifier que le filtre ou la fonction est réellement enregistré.
  3. Si la syntaxe est valide, reproduire le rendu avec les variables concernées.
  4. Retirer les sorties de débogage avant publication : elles peuvent révéler des données internes et échouer dans un environnement sans l'extension.

Exemple concret shell

Dans une application Symfony 8.0 équipée de TwigBundle :

php bin/console lint:twig templates/
php bin/console debug:twig --filter=date

La première commande ne rend pas les pages ; la seconde inspecte les éléments correspondant au filtre de recherche. Contre-exemple : conclure qu'un lint réussi prouve que {{ customer.address.city }} recevra toutes ses données. Correction : effectuer aussi un rendu avec le contexte attendu, sous la politique strict_variables choisie. Pour un diagnostic temporaire en développement, {{ dump(customer) }} inspecte la valeur ; ne pas lui attribuer la capacité de charger les données manquantes.

Passage canonique conservé

Les commands

  • php bin/console debug:twig — filters, functions, tests, globales et paths disponibles ; --filter=date restreint la liste.
  • php bin/console lint:twig templates/ — vérifie la syntaxe sans rendre : une variable indéfinie n'est pas détectée ; l'exit code vaut 1 en cas d'erreur. --show-deprecations traite les deprecations comme des erreurs.

Pièges d'examen

△ Piège à éviter

  • Destination de dump() et du tag dump

    La function et le tag n'écrivent pas au même endroit.

  • Voir l’explication : En production, la function n'existe pas

    En production, la function n'existe pas : erreur à la compilation, pas un avertissement.

  • Contenu d’un dump sans argument

    Sans argument, c'est tout le contexte qui sort.

  • Voir l’explication : Le tag indexe par nom de variable ; la function refuse les named arguments

    Le tag indexe par nom de variable ; la function refuse les named arguments avec Twig 3.22, malgré l'exemple de la documentation.

Application

À retenir en priorité
  1. La function modifie le contenu de la page.
  2. Le tag utilise l'intégration de debug.
  3. Le lint n'exécute pas les branches du template.
  4. Un test de rendu reste nécessaire pour les données runtime.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • Function : dans la page ; tag : vers la toolbar.
  • Sans argument : tout le contexte.
  • Function : arguments positionnels seulement ; tag : chaque variable nommée.
  • DebugBundle hors debug : rien.
  • Sans DebugBundle : debug → var_dump de Twig, tag inconnu ; sinon Unknown function.
  • debug:twig --filter=… : ce que Twig connaît.
  • lint:twig : syntaxe seulement, exit code 1 en cas d'erreur.

Moyen mnémotechnique : « accolades dans la page, tag dans la barre, prod sans bundle : erreur ».

{{ dump }} = page, {% dump %} = toolbar ; sans argument = tout le contexte ; function sans named arguments ;
DebugBundle + debug = actif, sans debug = muet ; sans bundle : debug = var_dump de Twig, prod = Unknown function ; lint = syntaxe
