L'essentiel

○ À comprendre

À retenir en priorité

Sans option methods, une route accepte tous les verbes ; avec methods: ['GET'], elle accepte aussi HEAD. L'option `methods`

À retenir en priorité
  1. L'absence de methods n'implique pas GET.
  2. HEAD est comparé comme GET au matching.

Par défaut une route accepte tous les verbes. methods restreint, et deux routes peuvent partager le même path en ne différant que par la method — le pattern REST. Écrire HEAD est superflu : le matcher compare une Request HEAD comme un GET.

Un guichet peut exister mais ne traiter que certaines opérations. Le path correspond et la method non : le 405 et son header Allow décrivent cette différence, contrairement à une absence de route.

Repère de l’exemple : Give the two routes different methods requirements; GET also accepts HEAD. Le path peut être identique si les methods distinguent les routes. La route GET accepte également HEAD ; PUT sélectionne l'autre action.

La limite des forms HTML

Revoir la règle : Le form HTML transmet GET ou POST.

Un form HTML envoie GET ou POST. Pour atteindre une route en PUT, PATCH ou DELETE, on ajoute un field caché _method :

<input type="hidden" name="_method" value="PUT">

Symfony ne le lit que si framework.http_method_override vaut true. Le theme de form Twig ajoute ce field dès que la method du form n'est ni GET ni POST, que l'option soit activée ou non.

Repère — Ce que fait Request::getMethod() (8.0) : No. It governs the parameter; allowed_http_method_override can also restrict the header. Le header est examiné sur un POST avant le parameter. Une liste allowed_http_method_override vide désactive les remplacements.

Ce que fait `Request::getMethod()` (8.0)

Revoir la règle : Le header est examiné sur un POST avant le parameter.

  • Rien n'est remplacé si la method réelle n'est pas POST.
  • Le header X-HTTP-METHOD-OVERRIDE est lu en premier, et il ne dépend pas de http_method_override, qui ne gouverne que _method.
  • _method est cherché dans le body, puis dans la query string.
  • Un remplacement vers GET, HEAD, CONNECT ou TRACE est ignoré.
  • Le nom est d'abord mis en majuscules : _method=put donne PUT. Un nom qui contient autre chose que des lettres — un chiffre, un tiret — lève une SuspiciousOperationException.

framework.allowed_http_method_override restreint les methods simulables : null, le défaut, les autorise toutes ; une liste les limite, une method hors liste laissant le POST ; un array vide désactive tout remplacement, header compris.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Le form HTML transmet GET ou POST.

Sans restriction de method, une route accepte tous les verbes. L'absence de l'option n'est pas un GET implicite.

Le field caché ne suffit pas. Simuler un verbe par _method exige http_method_override: true ; désactivée — ce qui est le cas par défaut — le field est ignoré et la Request reste un POST.

Le header, lui, n'attend pas cette option. Seul allowed_http_method_override: [] le neutralise.

methods: ['GET'] accepte HEAD.

Deux routes peuvent partager exactement le même path et ne différer que par la method : c'est le pattern REST, et il rend la lecture de la liste des routes indispensable.

Fiche express

◆ À mémoriser

Revoir la règle : Le header est examiné sur un POST avant le parameter.

Si tu dois retenir seulement 6 choses :

  • Sans methods → tous les verbes ; GET accepte HEAD.
  • _method lu seulement si http_method_override: true (false par défaut).
  • Remplacement depuis un POST seulement.
  • Header X-HTTP-METHOD-OVERRIDE lu en premier, même option désactivée.
  • Jamais vers GET, HEAD, CONNECT, TRACE ; nom non alphabétique → exception.
  • allowed_http_method_override: [] coupe tout, header compris.

Moyen mnémotechnique : « Le header passe avant le field ».
