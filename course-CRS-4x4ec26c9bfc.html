Objectif

Régler le client avant ou pendant la Request : headers, host, session, comportement face aux exceptions.

L'essentiel

○ À comprendre

À retenir en priorité
  1. L'environment appartient au premier array.
  2. Les headers simulés appartiennent au second.

Le client de test se règle à deux niveaux : createClient() pour tout le test, le 5ᵉ argument de request() pour une seule Request. Un header s'y écrit sous son nom CGI — HTTP_ + majuscules + soulignés. Et une valeur posée en session n'est vue qu'après save().

Le schéma

À retenir en priorité
  1. La surcharge locale ne modifie pas le défaut.
  2. Les Requests suivantes peuvent retrouver l'ancienne valeur.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le nom suit la convention CGI.
  2. Majuscules et underscores remplacent la forme HTTP.
$client = static::createClient([], [                 // 1ᵉʳ : kernel ; 2ᵉ : serveur
    'HTTP_HOST' => 'en.example.com',                  // toutes les Requests
]);

$client->request('GET', '/api/me', [], [], [
    'HTTP_X_SESSION_TOKEN' => 'abc',                  // X-Session-Token, une fois
]);

$session = $client->getSession();
$session->set('_csrf/form', 'fhr8d5sha3a69tpv24s5');
$session->save();                                     // sinon, invisible

Les deux arguments de `createClient()`

○ À comprendre

À retenir en priorité
  1. Ce sont des options du kernel.
  2. Ne pas les mélanger aux parameters serveur.

C'est quoi ?

Le client de test possède d'une part des options de démarrage du kernel et d'autre part des paramètres serveur simulant HTTP. createClient() sépare ces deux ensembles dans ses deux arguments.

À quoi ça sert ?

On peut tester une variante de configuration et un header sans confondre environment Symfony, corps du formulaire et métadonnées HTTP. Une entrée placée dans le mauvais tableau peut être ignorée au lieu de produire la Request voulue.

Où dans Symfony ?

Le premier tableau contient notamment environment et debug ; le second les paramètres serveur par défaut. Un header personnalisé suit la convention CGI : majuscules, tirets remplacés par _, préfixe HTTP_. Les exceptions courantes comprennent CONTENT_TYPE et CONTENT_LENGTH, sans ce préfixe.

Comment, étape par étape ?

  1. Choisir les options du kernel.
  2. Définir les headers communs avec leurs noms serveur.
  3. Pour une surcharge ponctuelle, employer le tableau serveur de request(), pas celui des paramètres de formulaire.
  4. Si le test prépare une session, y écrire les données, la sauvegarder et faire porter au client le cookie correspondant. Une session créée sans ce lien n'est pas forcément celle que l'application relira.

Exemple concret PHP

Dans un test WebTestCase :

$client = static::createClient(
    ['environment' => 'test'],
    ['HTTP_ACCEPT_LANGUAGE' => 'fr'],
);
$client->request('GET', '/');
self::assertSame('fr', $client->getRequest()->headers->get('Accept-Language'));

La route / doit exister dans l'application testée. L'assertion porte sur la Request reçue, pas sur une traduction automatique de la page : ce header ne choisit pas à lui seul toute politique de locale.

Contre-exemple : mettre Accept-Language directement dans le deuxième tableau ou passer ce header comme paramètre de formulaire. Correction : utiliser HTTP_ACCEPT_LANGUAGE à la bonne position. Pour un formulaire protégé, récupérer et soumettre le vrai formulaire avec son token CSRF et la même session ; ne pas inventer un token ni désactiver sa vérification. Pour Authorization, la clé serveur est HTTP_AUTHORIZATION, sans afficher de credential réel dans le test pédagogique.

Configurer le client 8.0.

Passage canonique conservé

Les deux arguments de createClient()

Le premier porte les options du kernel — environment, debug, celles de bootKernel(). Le second porte les parameters serveur, donc les headers, pour toutes les Requests du client.

La règle de nommage des headers

À retenir en priorité
  1. Certains headers CGI ont un nom spécial.
  2. Ne pas préfixer systématiquement sans vérifier.

Un header personnalisé suit la RFC 3875 : tirets → soulignés, majuscules, préfixe HTTP_. X-Session-Token devient HTTP_X_SESSION_TOKEN.

Key passée au client X-Session-Token côté serveur
HTTP_X_SESSION_TOKEN abc
X-Session-Token null
X_SESSION_TOKEN null
  • Les headers standards de CGI échappent au préfixe : CONTENT_TYPE, sans préfixe, arrive bien comme Content-Type.
  • HTTP_AUTHORIZATION arrive comme Authorization ; AUTHORIZATION donne null.
  • Sans réglage, le user agent vaut Symfony BrowserKit.

Par Request plutôt que par client

À retenir en priorité
  1. Les parameters de form sont ailleurs.
  2. La position évite de confondre body et headers.

L'array de la Request est fusionné par-dessus celui du client, pour cette Request seulement. Client créé avec HTTP_HOST a.example.com :

Request Host reçu
5ᵉ argument HTTP_HOST b.example.com b.example.com
la suivante, sans 5ᵉ argument a.example.com
après setServerParameter('HTTP_HOST', 'c.example.com') c.example.com

setServerParameter() modifie le client pour la suite du test.

Préparer la session

▣ Exemple concret

À retenir en priorité
  1. L'écriture doit être persistée.
  2. Le client doit retrouver la même session.

C'est quoi ?

Préparer une session de test consiste à enregistrer des données côté serveur puis à faire identifier cette même session par le client de test. Modifier un objet Session en mémoire et persister son contenu sont deux actions distinctes.

À quoi ça sert ?

Un test peut commencer avec une préférence déjà enregistrée, sans refaire toute l'interface qui l'a créée. Pour tester une protection CSRF, on préférera charger puis soumettre le vrai formulaire : cet exemple ne forge pas un token.

Où dans Symfony ?

En 8.0, KernelBrowser::getSession() crée ou retrouve la session et prépare le cookie correspondant dans le client. Il peut retourner null si l'application n'a pas de factory de session. Cette méthode évite de fabriquer une autre session et d'oublier son lien avec le client.

Comment, étape par étape ?

  1. Démarrer le client avec WebTestCase dans une application configurée pour les sessions de test.
  2. Obtenir sa session et vérifier qu'elle existe.
  3. Écrire la préférence puis appeler save() avant la Request qui doit la lire.
  4. Effectuer cette Request et affirmer la valeur réellement observée, pas seulement la présence de la clé dans l'objet préparé.

Exemple concret PHP

Dans une application de test, la route GET /test/preference doit utiliser le controller suivant. Déclarer la route dans la configuration de test seulement ; ce n'est pas une nouvelle route de production à publier.

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

final class PreferenceProbeController
{
    public function __invoke(Request $request): Response
    {
        return new Response($request->getSession()->get('preferred_locale', 'unset'));
    }
}

Test associé, une fois cette fixture enregistrée :

<?php
use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

final class PreferenceSessionTest extends WebTestCase
{
    public function testReadsPreparedSession(): void
    {
        $client = self::createClient();
        $session = $client->getSession();
        self::assertNotNull($session);
        $session->set('preferred_locale', 'fr');
        $session->save();

        $client->request('GET', '/test/preference');
        self::assertResponseIsSuccessful();
        self::assertSame('fr', $client->getResponse()->getContent());
    }
}

Le corps fr prouve que le controller a relu la donnée persistée. Sans préparation, la fixture retourne unset, pas une préférence inventée. Contre-exemple : créer une session indépendante sans cookie, ou omettre save() en comptant sur le prochain démarrage du kernel. Correction : employer la session liée au client et la sauvegarder. Conserver CSRF et validation sur les routes métier ; cette fixture ne les remplace pas. Ce test n'est pas exécuté ici : aucun kernel de fixture ni PHPUnit n'a été lancé.

Les cookies

À retenir en priorité
  1. Le cookie de test appartient à BrowserKit.
  2. Ne pas confondre avec le cookie HttpFoundation de Response.

$client->getCookieJar()->set(new Cookie('flavor', 'choco')) — le Cookie de BrowserKit — et la Request suivante porte le cookie flavor.

Voir les exceptions

À retenir en priorité
  1. La modification est locale au client.
  2. L'application garde son traitement normal.

$client->catchExceptions(false) : l'exception remonte à PHPUnit au lieu d'un 500 muet ; l'application, elle, ne change pas. Le client est le service test.client, en environment test ou avec framework.test.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. La modification concerne le client.
  2. Une surcharge de request() reste ponctuelle.
  • Ordre des arguments de createClient()

    createClient() prend d'abord les options du kernel, ensuite les headers.

  • Nommer les headers du client de test

    Un header personnalisé devient HTTP_ + majuscules + soulignés.

  • Voir l’explication : Les headers de Request sont le cinquième argument

    Les headers de Request sont le cinquième argument de request().

  • Voir l’explication : $session->save() est obligatoire

    $session->save() est obligatoire pour que la valeur soit visible.

  • Voir l’explication : catchExceptions(false) ne change pas l'application

    catchExceptions(false) ne change pas l'application, seulement ce que le client fait de l'exception.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le header suit la convention CGI du client.
  2. AUTHORIZATION seul n'est pas équivalent.

Si tu dois retenir seulement 7 choses :

  • createClient() : options du kernel, puis parameters serveur.
  • Header personnalisé : HTTP_ + MAJUSCULES + _.
  • CONTENT_TYPE échappe au préfixe.
  • 5ᵉ argument de request() : une Request, prioritaire.
  • setServerParameter() pour la suite du test.
  • save() après set() en session.
  • catchExceptions(false) : l'exception remonte, l'application ne change pas.

Moyen mnémotechnique : « Kernel, puis serveur ; HTTP_ en majuscules ; save ».

createClient(kernel, serveur) ; X-Foo-Bar → HTTP_X_FOO_BAR (CONTENT_TYPE à part) ; request(…, 5ᵉ) l'emporte une fois ;
setServerParameter() pour la suite ; session : set + save ; cookies : getCookieJar() ; catchExceptions(false)
