Objectif

Nous savons fournir un catalogue au controller plutôt que le fabriquer dans show(). Il reste à comprendre comment l'application prépare cet assemblage pour /blog/42, et pourquoi une configuration modifiée ne change pas forcément l'objet déjà utilisé par un processus.

Le service container gère les instructions de construction et les instances obtenues. Nous suivons définition, partage, visibilité, alias et cache avec Symfony 8.0. Le laboratoire de notification conserve ses noms PhpMailer et Newsletter, sans imposer un vrai transport d'email au blog.

L'essentiel

À comprendre

À retenir en priorité
  1. La definition décrit la construction.
  2. L'instance apparaît au premier usage.

Le ContainerBuilder manipule des définitions, plans décrivant les services. La compilation les résout et les optimise ; dans l'application Symfony, une étape de génération produit le code PHP réutilisable en cache. Un appel autonome à compile() ne signifie pas à lui seul qu'un fichier de container a été écrit.

Un service ordinaire non lazy est construit lorsqu'une demande le nécessite, directement ou comme dépendance d'un autre service. Il est partagé par défaut dans le container qui le gère. « Privé » interdit son accès direct normal par get() après compilation, mais pas son injection.

Un alias est un second identifiant dirigé vers un service existant. Il peut notamment associer le type d'une interface à l'implémentation choisie. Il ne rend pas compatible une class qui ne respecte pas cette interface. Enfin, la réutilisation du cache explique pourquoi la configuration et les objets déjà construits ne se mettent pas à jour spontanément.

Le schéma

À retenir en priorité
  1. Le partage est le comportement par défaut.
  2. shared: false demande de nouvelles instances.

La notification peut être demandée par plusieurs consommateurs. Avant de créer un second mailer, le container examine si la définition partagée a déjà produit son instance. Le schéma isole ce comportement :

Sur le chemin « non », le service ordinaire est construit puis mémorisé ; sur le chemin « oui », le consommateur reçoit l'instance déjà conservée. Bleu : opérations ; orange : test ; vert : instance partagée. Cette identité vaut pour les résolutions de la même définition dans le même container, pas pour tout objet de cette class dans tous les processus.

shared: false change la réutilisation lors d'une nouvelle résolution. lazy concerne le moment de l'initialisation : ce n'est pas un autre mot pour « non partagé ». Dans un processus persistant d'import, un service partagé peut vivre plus longtemps qu'un seul traitement ; le partage n'est donc pas une autorisation à y conserver sans précaution l'état d'un lecteur.

Le fil rouge : `PhpMailer`, `MailerInterface` et la `Newsletter`

À retenir en priorité
  1. L'interface exprime le contrat.
  2. L'alias choisit l'implémentation.

Ces déclarations locales illustrent seulement le choix d'une implémentation. L'interface vide n'est pas le contrat du composant Mailer et n'envoie rien. Dans un projet PSR-4, chaque déclaration serait placée dans son fichier correspondant sous src/Mail/ ; elles sont regroupées ici pour la lecture :

namespace App\Mail;

interface MailerInterface {}
class PhpMailer implements MailerInterface {}

class Newsletter
{
    public function __construct(private MailerInterface $mailer) {}

    public function mailer(): MailerInterface
    {
        return $this->mailer;
    }
}

La Newsletter demande un objet respectant MailerInterface. PhpMailer est une possibilité, mais le type seul ne décide pas quel service construire. L'accesseur mailer() est ajouté au laboratoire pour observer l'objet effectivement injecté, pas comme méthode Symfony.

L'assemblage manuel new Newsletter(new PhpMailer()) satisfait déjà ce contrat. Le container doit reproduire ce choix à partir de définitions et, pour le câblage automatique par types, d'un alias approprié. Ces classes ne créent ni inscription, ni email, ni service enregistré tant que leur configuration n'est pas chargée.

🌍 In Real Life

La situation : le poste exige un outil compatible, mais plusieurs modèles peuvent convenir ; il faut encore choisir lequel fournir.

L’équivalent dans Symfony : exigence commune → MailerInterface ; modèle compatible → PhpMailer ; choix d'équipement → assemblage manuel ou configuration du conteneur.

Retour à la réalité technique : le type de constructeur impose la compatibilité PHP, sans sélectionner à lui seul un service. L'alias d'interface guide l'autowiring lorsqu'il s'applique. L'interface vide du laboratoire ne promet aucun envoi d'email.

🧠 Comment le mémoriser : « Compatible ne veut pas dire choisi. » Image mentale : deux outils compatibles devant une seule place. Question-réflexe : quelle configuration désigne l'implémentation ?

⚠️ À ne pas confondre : déclarer une classe PHP et enregistrer un service dans le conteneur.

Ce que le container contient : des definitions

À retenir en priorité
  1. La definition est un plan.
  2. Elle n'est pas l'object exécuté.
  3. Lazy diffère l'initialisation après injection.
  4. Shared décide du partage, pas de l'instant d'initialisation.

Une définition décrit notamment une class ou une fabrique, les arguments à lui fournir, les appels de méthodes prévus, les tags et la visibilité. Enregistrer le plan du mailer n'exécute pas son constructeur. La compilation normale prépare l'assemblage sans instancier tous les services applicatifs ; du code de compilation personnalisé peut néanmoins créer ses propres objets.

La première demande qui nécessite le mailer déclenche son obtention. Demander Newsletter peut donc construire le mailer sans qu'aucun code applicatif n'ait appelé directement get() pour celui-ci. Si deux consommateurs résolvent la même définition partagée, ils reçoivent normalement le même objet.

Voici un laboratoire distinct avec une class existante et autoloadable App\Token, sans argument de constructeur requis. Les services sont publics uniquement pour comparer des appels directs :

services:
    app.shared_token:
        class: App\Token
        public: true
    app.fresh_token:
        class: App\Token
        public: true
        shared: false

Deux résolutions de app.shared_token dans ce container donnent le même objet ; deux résolutions de app.fresh_token produisent deux objets distincts. Ce sont deux définitions d'une même class, pas deux aliases d'une seule définition. Le résultat dépend ici de la construction ordinaire prévue par ces définitions.

Si un consommateur partagé reçoit une instance non partagée à sa construction, il garde cette instance. Appeler deux fois une méthode du consommateur ne redemande pas automatiquement la dépendance au container. Le non-partage ne corrige donc pas un état mutable mal placé.

Avec la découverte habituelle des classes dans src/, l'identifiant est le FQCN, nom de class complet avec son namespace. Cela fournit un repère au câblage automatique, ou autowiring. Un fichier présent dans src/ n'est toutefois pas forcément découvert : la ressource importée, les exclusions et la configuration décident des définitions réellement enregistrées.

🌍 In Real Life

La situation : une fiche explique comment fournir un équipement ; une fois obtenu, plusieurs postes peuvent utiliser le même équipement partagé.

L’équivalent dans Symfony : fiche d'assemblage → définition ; équipement réel → instance du service ; réutilisation prévue → partage de cette définition dans ce conteneur.

Retour à la réalité technique : enregistrer la définition ne construit pas l'objet. La demande peut être indirecte, via un consommateur. shared: false change les nouvelles résolutions, pas les appels de méthodes sur une dépendance déjà injectée. lazy concerne l'initialisation, pas le partage.

🧠 Comment le mémoriser : « La fiche décrit ; l'objet sert. » Image mentale : une fiche à côté d'un seul appareil relié à deux postes. Question-réflexe : parle-t-on du plan, d'une nouvelle résolution ou d'une instance déjà conservée ?

⚠️ À ne pas confondre : service partagé et singleton universel ; deux définitions d'une même classe peuvent fournir deux objets.

Un service partagé ordinaire est construit lorsqu'il est demandé, y compris comme dependency d'un autre service. lazy: true peut différer son initialisation après cette injection : le service consommateur peut être créé sans exécuter immédiatement le constructor coûteux de la dependency. Avec PHP 8.4, Symfony 8.0 exploite les lazy objects natifs ; cela ne change pas automatiquement le réglage shared.

Documentation Symfony 8.0.

Public ou privé : trois questions

À retenir en priorité
  1. Privé n'interdit pas l'injection.
  2. La compilation peut retirer les privés inutilisés.

Le mailer est utile à la newsletter sans devoir être accessible partout. La visibilité porte sur l'accès au container, pas sur les mots-clés public et private des méthodes PHP de sa class :

Question Privé (le défaut) Public
Injectable dans un autre service ? oui oui
Récupérable par get() une fois compilé ? non oui
Retirable ou inlinable par la compilation ? oui non

Dans le container applicatif compilé, demander directement un identifiant privé peut produire ServiceNotFoundException, avec l'indication qu'il a été retiré ou intégré ailleurs ; has() ne le présente pas comme un service directement accessible. Cela n'empêche pas qu'un consommateur reçoive l'objet.

L'inlining intègre une définition privée dans la recette du consommateur ; la suppression retire une définition inutilisée. Ces optimisations expliquent l'intérêt du privé par défaut. Les références obligatoires du graphe conservé sont aussi vérifiables à la compilation, contrairement à un identifiant inventé plus tard dans une recherche dynamique.

Pour l'observer sans système d'envoi, voici un autre petit assemblage. App\Formatter est une class autoloadable sans argument requis, et App\Report possède un constructeur __construct(Formatter $formatter) qui conserve cet objet :

services:
    App\Formatter: ~
    App\Report:
        public: true
        arguments:
            $formatter: '@App\Formatter'

Demander App\Report à ce container construit le report avec le formatter privé. La référence @App\Formatter suffit à exprimer la dépendance ; rendre aussi le formatter public n'est pas nécessaire. Ce fragment configure l'assemblage, pas le contenu métier d'un rapport.

Un véritable accès direct peut être exposé avec public: true, avec #[Autoconfigure(public: true)] lorsque son intégration lit l'attribute, ou avec un alias public. Une class doit toujours être enregistrée et l'attribute effectivement traité : écrire une métadonnée ne remplace pas toute la configuration.

Dans les tests Symfony configurés pour cela, static::getContainer() donne accès au container spécial qui atteint aussi des privés non retirés. Il ne ressuscite pas une définition supprimée. Pour conserver un service nécessaire seulement au test, on peut l'exposer dans la configuration chargée config/services_test.yaml, en préservant son câblage utile, plutôt que le rendre public dans tous les environments.

🌍 In Real Life

La situation : un ustensile réservé à l'assemblage interne reste disponible pour le poste qui en dépend, sans apparaître au guichet des demandes directes.

L’équivalent dans Symfony : fourniture interne → injection d'un service privé ; guichet direct → accès public par get() ; plan inutilisé supprimé → optimisation d'une définition privée.

Retour à la réalité technique : privé limite la récupération directe dans le conteneur compilé, pas l'injection. Une définition peut être intégrée à celle du consommateur ou retirée si inutile. Le conteneur de test atteint certains privés non retirés ; il ne recrée pas une définition supprimée.

🧠 Comment le mémoriser : « Interne n'est pas inutilisable. » Image mentale : un passage interne vers le poste et un guichet fermé. Question-réflexe : cherche-t-on à injecter le service ou à le récupérer directement ?

⚠️ À ne pas confondre : visibilité du service, visibilité PHP des méthodes et droits d'un utilisateur du blog.

L'alias : un second identifier

À retenir en priorité
  1. L'alias ajoute un nom.
  2. Le partage dépend du service cible.

Reprenons les classes App\Mail du fil rouge. Ce YAML rassemble les définitions, active l'autowiring et conserve deux aliases : un accès public app.mailer pour le laboratoire, et le type d'interface pour le constructeur. La newsletter est également publique ici uniquement afin d'observer son injection :

services:
    _defaults:
        autowire: true

    App\Mail\PhpMailer: ~
    App\Mail\Newsletter:
        public: true

    app.mailer: { alias: App\Mail\PhpMailer, public: true }
    App\Mail\MailerInterface: '@App\Mail\PhpMailer'      # rend l'interface injectable

Avec ces classes autoloadables, ce fichier chargé et $container désignant le container applicatif compilé de ce laboratoire :

use App\Mail\Newsletter;
use App\Mail\PhpMailer;

$newsletter = $container->get(Newsletter::class);
$mailer = $container->get('app.mailer');
var_dump($mailer instanceof PhpMailer);
var_dump($newsletter->mailer() === $mailer);

Les deux résultats attendus sont bool(true). L'alias n'a pas décrit un second objet : il pointe vers le même service partagé. Le demander peut bien déclencher la construction de la cible ; « un alias ne crée pas de service » ne signifie pas « aucun objet ne peut être construit quand on le consulte ».

Un alias est privé par défaut. La forme courte App\Mail\MailerInterface: '@App\Mail\PhpMailer' sert à résoudre le type, pas à autoriser un get() sous tous les noms. L'attribute #[AsAlias(id: 'app.mailer', public: true)] peut porter cette déclaration sur une class lorsque l'intégration correspondante la traite.

Lors de la découverte habituelle, Symfony peut créer automatiquement l'alias d'une interface lorsqu'une seule implémentation appropriée est découverte et qu'aucun choix n'est déjà déclaré. Deux implémentations ne conduisent pas à un choix alphabétique. Si un consommateur conservé doit être autowiré avec ce type et qu'aucun alias ou autre câblage explicite ne tranche, la compilation échoue.

Dans notre YAML, le choix est déjà explicite : ajouter SmtpMailer ne modifie pas l'injection de PhpMailer. Déclarer à la place une nouvelle définition avec class: App\Mail\PhpMailer sous le nom de l'interface serait une autre recette de service, pas cet alias. Et aucun alias ne peut corriger une incompatibilité PHP entre l'objet choisi et le type attendu.

🌍 In Real Life

La situation : deux étiquettes du registre désignent le même équipement ; ajouter une étiquette ne crée pas un second appareil.

L’équivalent dans Symfony : seconde étiquette → alias ; destination du registre → service cible ; étiquette d'exigence → identifiant d'interface utilisé par l'autowiring.

Retour à la réalité technique : l'alias redirige vers une définition, dont les règles de partage restent applicables. Consulter l'alias peut déclencher l'obtention de sa cible. Une seconde définition de la même classe n'est pas un alias ; un alias ne corrige jamais une incompatibilité de type PHP.

🧠 Comment le mémoriser : « Deux noms, une cible. » Image mentale : deux flèches d'étiquettes vers une seule fiche. Question-réflexe : ai-je déclaré une redirection ou une nouvelle recette de service ?

⚠️ À ne pas confondre : alias d'interface pour l'injection et alias public autorisant une récupération directe ; privé reste le défaut.

La compilation : pourquoi la configuration n'est pas relue

À retenir en priorité
  1. Le mode production ne surveille pas chaque source.
  2. Reconstruire le cache applique la configuration.

Nous changeons maintenant le câblage du mailer. Le fichier est modifié, mais un processus peut encore utiliser le container préparé précédemment. La compilation et la génération déplacent le travail de configuration avant les utilisations ordinaires, puis le kernel réutilise le résultat.

Avec App\Kernel, les méthodes et emplacements standards, ces noms de classe servent de repères ; les directories peuvent être personnalisés par le kernel :

Kernel Class compilée, dans var/cache/<env>/
App\Kernel, prod, sans debug App_KernelProdContainer
App\Kernel, test, debug App_KernelTestDebugContainer

En debug, la vérification de fraîcheur porte sur les ressources suivies du cache ; un changement détecté entraîne sa reconstruction. Sans debug, un cache utilisable est chargé sans cette vérification. Cela ne signifie pas qu'un cache absent pourrait être utilisé : le kernel doit alors le construire.

Le mode debug, et non le seul nom prod, détermine cette différence. Pour reconstruire explicitement le cache de production sans debug, la commande documentaire Symfony Console 8.0 est :

php bin/console cache:clear --env=prod --no-debug

Résultat attendu si elle réussit : le cache de l'environment prod est renouvelé et réchauffé selon la configuration de la commande. Vider seulement dev n'actualise pas prod. Un processus persistant qui conserve déjà l'ancien container doit également être renouvelé selon le mode de déploiement ; un objet construit ne se reconfigure pas par la seule modification du fichier. La commande n'est pas exécutée ici.

Dans la configuration habituelle du kernel, services_<env>.yaml est chargé après services.yaml. Il complète la configuration commune et peut redéfinir des entrées ciblées ; il ne remplace pas automatiquement tous ses services. Les détails d'une redéfinition doivent conserver le câblage souhaité.

Enfin, certaines références %env(...)% peuvent rester résolues à l'utilisation. Mettre le container en cache ne veut pas dire que toutes les valeurs d'environnement ont été copiées immédiatement dans des paramètres ordinaires. Cela ne transforme pas pour autant chaque variable en réglage mis à jour en continu dans les instances déjà créées.

🌍 In Real Life

La situation : l'équipe travaille avec une feuille de préparation déjà imprimée ; corriger le document source ne modifie ni cette feuille ni un équipement déjà assemblé.

L’équivalent dans Symfony : source modifiée → configuration ; feuille réutilisable → conteneur compilé et généré en cache ; équipement en place → service déjà instancié.

Retour à la réalité technique : Kernel contrôle les ressources suivies en debug ; sans debug, il peut charger un cache utilisable sans ce contrôle. Il faut traiter le bon environnement et les processus persistants concernés. Certaines valeurs %env(...)% peuvent rester résolues à l'utilisation : l'image de la feuille figée ne couvre pas toutes les valeurs.

🧠 Comment le mémoriser : « Corriger la source ne remplace pas l'exemplaire en main. » Image mentale : nouvelle feuille au bureau, ancienne feuille au poste. Question-réflexe : quel cache et quel processus utilisent encore l'ancien assemblage ?

⚠️ À ne pas confondre : cache de configuration du conteneur, cache applicatif d'un calcul et cache HTTP d'une réponse.

Inspecter le container

À retenir en priorité
  1. Distinguer types injectables et identifiers.
  2. Choisir la command selon la question.

Si la newsletter reçoit le mauvais objet, inspectons d'abord la configuration de l'environment concerné plutôt que rendre tous les services publics. Ces commandes Symfony Console 8.0 décrivent des services ou types ; elles ne constituent pas des appels métier :

php bin/console debug:container
php bin/console debug:container --show-hidden
php bin/console debug:autowiring Mailer
php bin/console debug:autowiring Mailer --all

La première liste les services ordinaires, privés compris ; --show-private n'existe pas en 8.0. La deuxième, dans cette liste textuelle, affiche seulement les identifiants internes commençant par un point, sous le titre Symfony Container Hidden Services. Elle n'ajoute pas les privés à une liste auparavant limitée aux publics.

La troisième recherche les types autowirables correspondant à Mailer. --all ajoute aussi les services sans alias dans cette recherche, pas une autorisation de les récupérer par get(). Les lignes exactes dépendent des services chargés et de l'environment ; les commandes ne sont pas exécutées ici. Un service visible dans l'outil d'inspection peut donc rester privé dans le container utilisé par l'application.

🌍 In Real Life

La situation : l'inventaire permet de voir les équipements internes ; les voir sur la liste ne donne pas accès à tous les guichets.

L’équivalent dans Symfony : inventaire des services → debug:container ; recherche des types câblables → debug:autowiring ; droit de récupération directe → visibilité dans le conteneur compilé.

Retour à la réalité technique : ces commandes inspectent la configuration, sans exécuter le métier. En Symfony 8.0, les privés figurent déjà dans la liste ordinaire ; la liste textuelle avec --show-hidden sélectionne les identifiants commençant par un point. Cela ne les rend pas publics.

🧠 Comment le mémoriser : « Voir n'est pas obtenir. » Image mentale : inventaire affiché devant un guichet fermé. Question-réflexe : l'outil décrit-il un service ou autorise-t-il son get() ?

⚠️ À ne pas confondre : identifiant interne caché de la liste ordinaire et service privé ; ce sont deux critères distincts.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une seule implémentation permet l'inférence.
  2. Plusieurs nécessitent un choix explicite.
  • Voir l’explication : L'injection et l'accès direct sont deux contrats.

    L'injection et l'accès direct sont deux contrats. Le formatter privé arrive dans le report, même si sa récupération directe par son identifiant privé est refusée après compilation.

  • Voir l’explication : Un échec de get() ne prouve pas une mauvaise déclaration.

    Un échec de get() ne prouve pas une mauvaise déclaration. Vérifions la visibilité, l'identifiant, l'environment et l'éventuelle suppression. Rendre tout public masquerait la distinction au lieu d'expliquer le résultat.

  • Voir l’explication : Compiler prépare ; demander peut construire.

    Compiler prépare ; demander peut construire. Le flux normal ne crée pas tous les services à la compilation, mais un service peut être construit indirectement comme dépendance. Les objets créés par du code de compilation personnalisé sont un autre cas.

  • Voir l’explication : Le partage concerne une définition et un container.

    Le partage concerne une définition et un container. Deux définitions de App\Token ne deviennent pas un singleton de class. Une dépendance non partagée déjà injectée n'est pas renouvelée à chaque appel de méthode du consommateur.

  • Voir l’explication : La deuxième implémentation ne casse pas un choix déjà explicite.

    La deuxième implémentation ne casse pas un choix déjà explicite. L'ambiguïté concerne un consommateur qui doit être autowiré sans alias ni autre instruction suffisante. Notre alias vers PhpMailer reste un choix même si SmtpMailer est ajouté.

  • Voir l’explication : Un alias n'est pas une seconde recette.

    Un alias n'est pas une seconde recette. Il est privé par défaut et peut exposer publiquement un accès choisi. Définir à nouveau la même class sous un autre identifiant crée au contraire un autre service, avec son propre partage.

  • Voir l’explication : Le cache et les instances ont des durées de vie distinctes.

    Le cache et les instances ont des durées de vie distinctes. Sans debug, ne comptons pas sur la détection d'un fichier changé. Il faut reconstruire le bon environment et renouveler les processus qui gardent l'ancien container ; le nom prod seul n'explique pas la règle.

  • Voir l’explication : Une liste d'inspection n'est pas une liste d'accès autorisés.

    Une liste d'inspection n'est pas une liste d'accès autorisés. Les privés apparaissent dans debug:container, sans --show-private. --show-hidden sélectionne les identifiants internes dans la liste textuelle ; cela ne change la visibilité d'aucun service.

Fiche express

À mémoriser

À retenir en priorité
  1. La visibilité ne règle pas le partage.
  2. shared décide de la réutilisation.

Pour vérifier l'assemblage avant de rejouer le blog :

  1. Distinguer définition, compilation, génération du cache et instance ; la construction peut être demandée indirectement par un consommateur.
  2. Identifier la définition réellement enregistrée, souvent par son FQCN avec la découverte habituelle, sans confondre fichier et service.
  3. Garder privé ce qui doit seulement être injecté ; l'optimisation peut retirer ou intégrer ses définitions sans supprimer son utilité métier.
  4. Interpréter le partage dans le même container, par définition, et non comme un singleton global ou un renouvellement à chaque méthode.
  5. Choisir l'implémentation d'interface par alias lorsque nécessaire ; l'alias automatique dépend de la découverte et de l'absence d'ambiguïté.
  6. Après un changement de configuration, traiter le cache du bon environment et les processus persistants ; debug gouverne le contrôle de fraîcheur.
  7. Utiliser les commandes d'inspection pour comprendre services et types, sans déduire leur visibilité d'une ligne affichée.

Le controller peut alors recevoir son catalogue, et la branche d'inscription ses collaborateurs, sans devoir savoir comment ces objets ont été assemblés.
