Objectif

Savoir ce que le container contient et quand il construit un object, ce que public et privé changent, à quoi sert un alias, et pourquoi une modification de configuration reste sans effet tant que le container n'est pas recompilé. La déclaration des services elle-même est traitée dans Services registration.

L'essentiel

À comprendre

À retenir en priorité
  1. La definition décrit la construction.
  2. L'instance apparaît au premier usage.

Le container garde des definitions, pas des objects : un service est construit au premier usage, puis partagé. Il est privé par défaut — injectable, mais pas récupérable par get(). Un alias rend une interface injectable. Et le container est compilé en une class PHP : sans debug, la configuration n'est pas relue.

Le schéma

À retenir en priorité
  1. Le partage est le comportement par défaut.
  2. shared: false demande de nouvelles instances.

Le fil rouge : `PhpMailer`, `MailerInterface` et la `Newsletter`

À retenir en priorité
  1. L'interface exprime le contrat.
  2. L'alias choisit l'implémentation.
namespace App\Mail;

interface MailerInterface {}
class PhpMailer implements MailerInterface {}

class Newsletter
{
    public function __construct(private MailerInterface $mailer) {}
}

La Newsletter demande une interface ; c'est PhpMailer qui doit arriver.

Ce que le container contient : des definitions

À comprendre

À retenir en priorité
  1. La definition est un plan.
  2. Elle n'est pas l'object exécuté.
  3. Lazy diffère l'initialisation après injection.
  4. Shared décide du partage, pas de l'instant d'initialisation.

C'est quoi ?

Une définition décrit comment obtenir un service : classe ou factory, arguments, appels supplémentaires, visibilité et partage. Ce n'est pas déjà l'objet. Le container utilise cette description pour construire le service lorsqu'il en a besoin, notamment pour l'injecter dans un autre service.

À quoi ça sert ?

Séparer définition et instance permet de vérifier l'assemblage avant de l'exécuter. Le partage évite de reconstruire le même service à chaque demande ; il ne signifie pas que l'objet est universellement unique dans tous les processus PHP.

Où dans Symfony ?

Les fichiers de services et la découverte de classes produisent des définitions. Avec la configuration habituelle, l'identifiant d'une classe découverte est son nom complet avec espace de noms, appelé FQCN. Les services sont partagés par défaut au sein du container qui les gère.

Comment, étape par étape ?

  1. Le chargement de configuration enregistre une définition.
  2. La compilation résout et optimise les références.
  3. La première demande qui nécessite le service provoque sa construction.
  4. Une demande ultérieure réutilise normalement cette instance ; shared: false demande une nouvelle instance à chaque résolution du service.

Exemple concret YAML

On suppose que App\Token existe et que son constructeur ne prend aucun argument. Les services sont publics ici uniquement pour permettre une comparaison par get() dans un laboratoire.

services:
    app.shared_token:
        class: App\Token
        public: true
    app.fresh_token:
        class: App\Token
        public: true
        shared: false

Deux récupérations de app.shared_token donnent le même objet ; deux récupérations de app.fresh_token donnent deux objets distincts. Contre-exemple : penser que shared: false renouvelle automatiquement une dépendance à chaque appel de méthode de son consommateur. Correction : si un consommateur partagé reçoit une instance au constructeur, il garde cette instance ; un appel de méthode ne redemande pas le service au container. Utiliser le non-partage pour une vraie exigence d'instances distinctes, pas pour masquer un état mutable mal placé.

Passage canonique conservé

Ce que le container contient : des definitions

  • Une definition est le plan d'un service : class, arguments, calls, tags, visibilité. Compiler ne construit rien ; « if you never ask for the service, it's never constructed ».
  • Partagé par défaut : deux services qui reçoivent PhpMailer reçoivent le même object. shared: false (setShared(false)) en donne un neuf à chaque fois.
  • L'identifier d'un service découvert dans src/ est son FQCN ; c'est ce qui rend l'autowiring possible.

Un service partagé ordinaire est construit lorsqu'il est demandé, y compris comme dependency d'un autre service. lazy: true peut différer son initialisation après cette injection : le service consommateur peut être créé sans exécuter immédiatement le constructor coûteux de la dependency. Avec PHP 8.4, Symfony 8.0 exploite les lazy objects natifs ; cela ne change pas automatiquement le réglage shared.

Documentation Symfony 8.0.

Public ou privé : trois questions

À comprendre

À retenir en priorité
  1. Privé n'interdit pas l'injection.
  2. La compilation peut retirer les privés inutilisés.

C'est quoi ?

La visibilité d'un service règle son accès depuis le container compilé, pas la visibilité PHP de ses méthodes. Un service privé peut être injecté dans un autre service. Il n'est pas un point d'accès public pour get() et la compilation peut le retirer s'il est inutilisé, ou intégrer sa construction dans celle d'un consommateur.

À quoi ça sert ?

Le privé permet l'optimisation et encourage des dépendances déclarées, vérifiables à la compilation. Rendre un service public est utile pour un véritable point d'entrée récupéré par un programme ; ce n'est pas une réparation générale des erreurs d'autowiring, le câblage automatique par types.

Où dans Symfony ?

Les définitions applicatives sont privées par défaut. public: true expose la définition ; un alias public peut aussi exposer un service sous un autre identifiant. Le container spécial des tests facilite l'accès à des privés non retirés, sans ressusciter magiquement les définitions supprimées.

Comment, étape par étape ?

  1. Le consommateur déclare sa dépendance.
  2. La configuration référence le service privé.
  3. La compilation constate cette utilisation et conserve un moyen de le construire.
  4. Le consommateur reçoit l'objet, sans effectuer de get() sur son identifiant privé.

Exemple concret YAML

Report possède un constructeur __construct(Formatter $formatter) ; les deux classes existent dans App.

services:
    App\Formatter: ~
    App\Report:
        public: true
        arguments:
            $formatter: '@App\Formatter'

Récupérer App\Report construit et injecte le formatter privé. Contre-exemple : conclure « privé donc non injectable » puis rendre tous les services publics. Correction : conserver Formatter privé et le référencer explicitement. Autre confusion : debug:container peut décrire un service privé ; une commande d'inspection n'est pas une promesse que get() permettra de le récupérer dans l'application compilée.

Passage canonique conservé

Public ou privé : trois questions

Question Privé (le défaut) Public
Injectable dans un autre service ? oui oui
Récupérable par get() une fois compilé ? non oui
Retirable ou inlinable par la compilation ? oui non
  • get() d'un service privé : ServiceNotFoundException, « …has been removed or inlined when the container was compiled » ; has() rend false.
  • Rendre public : public: true, #[Autoconfigure(public: true)], ou un alias public.
  • Privé par défaut : performance, et des erreurs tôt — un service obtenu par injection l'est par une référence que la compilation vérifie.
  • En test, static::getContainer() atteint les privés non retirés ; un privé retiré se rend public dans config/services_test.yaml.

L'alias : un second identifier

À comprendre

À retenir en priorité
  1. L'alias ajoute un nom.
  2. Le partage dépend du service cible.

C'est quoi ?

Un alias associe un identifiant à un service déjà défini. Il ne décrit pas une deuxième construction. Un alias dont l'identifiant est le nom complet d'une interface indique quelle implémentation injecter pour ce type.

À quoi ça sert ?

Le consommateur dépend d'un contrat stable, tandis que la configuration choisit l'implémentation. On peut ainsi changer le transport de courrier sans modifier tous les constructeurs qui demandent MailerInterface.

Où dans Symfony ?

En YAML, une chaîne commençant par @ sous un identifiant de service peut déclarer un alias. Sa visibilité est privée par défaut. La découverte peut créer automatiquement un alias lorsqu'une seule implémentation d'une interface est découverte ; l'arrivée d'une deuxième implémentation rend un choix explicite nécessaire en l'absence d'alias déjà défini.

Comment, étape par étape ?

  1. Enregistrer la classe concrète.
  2. Associer l'identifiant de l'interface à cette classe.
  3. Activer l'autowiring du consommateur.
  4. Le type demandé est résolu via l'alias ; le consommateur reçoit l'instance concrète.

Exemple concret YAML

Les classes du fil rouge sont supposées chargées ; Newsletter demande MailerInterface au constructeur.

services:
    _defaults:
        autowire: true
    App\Mail\PhpMailer: ~
    App\Mail\MailerInterface: '@App\Mail\PhpMailer'
    App\Mail\Newsletter: ~

Newsletter reçoit un PhpMailer. Ajouter une autre implémentation ne change pas ce choix explicite. Contre-exemple : déclarer une deuxième définition App\Mail\MailerInterface avec class: App\Mail\PhpMailer pour créer un « alias ». Cela décrit un autre service, avec son propre partage. Correction : utiliser la référence d'alias ci-dessus. Un alias ne rend pas compatible une classe qui n'implémente pas l'interface : le contrat PHP reste obligatoire.

Passage canonique conservé

L'alias : un second identifier

services:
    app.mailer: { alias: App\Mail\PhpMailer, public: true }
    App\Mail\MailerInterface: '@App\Mail\PhpMailer'      # rend l'interface injectable
  • Un alias ne crée aucun object, et il est privé par défaut ; #[AsAlias(id: 'app.mailer', public: true)] l'écrit sur la class.
  • Aucun service ne s'appelle MailerInterface : l'alias du même nom y remédie. Si une seule class de src/ implémente l'interface, Symfony le crée seul ; deux implémentations font échouer la compilation, « Cannot autowire service … You should maybe alias this interface ».

La compilation : pourquoi la configuration n'est pas relue

À comprendre

À retenir en priorité
  1. Le mode production ne surveille pas chaque source.
  2. Reconstruire le cache applique la configuration.

C'est quoi ?

Compiler le container consiste à transformer les définitions en un assemblage vérifié et optimisé. Dans l'application Symfony, cet assemblage est mis en cache sous forme de code PHP. Exécuter ce code évite de reparcourir toute la configuration YAML pour construire chaque service.

À quoi ça sert ?

La compilation déplace une partie des erreurs et du coût de configuration avant les requêtes. En contrepartie, changer un fichier de services ne suffit pas à modifier un container de production déjà compilé et réutilisé sans contrôle de fraîcheur.

Où dans Symfony ?

Le kernel utilise un cache propre à l'environnement et au mode debug. En debug, les ressources suivies permettent de détecter les changements ; sans debug, il ne faut pas attendre cette détection automatique. Les paramètres ordinaires sont figés, tandis que certaines valeurs %env(...)% peuvent rester résolues à l'utilisation : cache du container ne signifie donc pas copie immédiate de toutes les valeurs d'environnement.

Comment, étape par étape ?

  1. Charger la configuration commune puis les compléments de l'environnement.
  2. Résoudre, valider et optimiser les définitions.
  3. Générer le container mis en cache.
  4. Lors du déploiement d'une configuration changée, reconstruire le cache de l'environnement concerné.
  5. Redémarrer les processus persistants concernés : un objet déjà construit n'est pas reconfiguré par la seule modification d'un fichier.

Exemple concret shell

Commande à exécuter dans une application de démonstration, pas exécutée par ce paquet :

php bin/console cache:clear --env=prod --no-debug

Elle vise le cache prod sans debug, pas le cache dev. Contre-exemple : modifier services.yaml, vider uniquement le cache de développement, puis attendre un nouveau service dans un processus de production déjà actif. Correction : reconstruire le bon environnement et renouveler les processus qui réutilisent l'ancien container. Les fichiers d'environnement complètent la configuration commune ; ils ne constituent pas automatiquement une copie de remplacement de tous ses services.

Passage canonique conservé

La compilation : pourquoi la configuration n'est pas relue

Kernel Class compilée, dans var/cache/<env>/
App\Kernel, prod, sans debug App_KernelProdContainer
App\Kernel, test, debug App_KernelTestDebugContainer
  • Debug : le kernel vérifie la fraîcheur du cache et recompile si une source a changé.
  • Sans debug : il inclut le file sans vérifier ; une modification de services.yaml attend php bin/console cache:clear.
  • services_<env>.yaml s'ajoute à services.yaml, il ne le remplace pas.

Inspecter le container

À retenir en priorité
  1. Distinguer types injectables et identifiers.
  2. Choisir la command selon la question.
  • debug:container liste les services, privés compris : il n'existe pas de --show-private.
  • --show-hidden n'affiche que les services internes, dont l'identifier commence par un point ; le titre devient « Symfony Container Hidden Services ».
  • debug:autowiring Mailer liste les types autowirables ; --all ajoute les services concrets.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une seule implémentation permet l'inférence.
  2. Plusieurs nécessitent un choix explicite.
  • Voir l’explication : Un service privé est injectable.

    Un service privé est injectable. « Privé » ne restreint que $container->get() sur le container compilé. Un énoncé qui conclut qu'un service privé ne peut pas être passé en argument à un autre service se trompe.

  • Voir l’explication : Privé est le défaut.

    Privé est le défaut. Un get() qui échoue sur un service de src/ parfaitement enregistré et injecté ailleurs n'indique ni une erreur de déclaration ni un container non compilé : le service est simplement privé.

  • Voir l’explication : Le container ne construit rien à la compilation.

    Le container ne construit rien à la compilation. Les objects naissent au premier usage, puis sont réutilisés. Un énoncé qui affirme que tous les services sont instanciés au démarrage ou à compile() est faux.

  • Voir l’explication : Deux injections, une instance.

    Deux injections, une instance. Un service partagé (le défaut) est le même object pour tous ceux qui le reçoivent. Il faut shared: false pour obtenir des instances distinctes.

  • Voir l’explication : L'alias d'interface n'est automatique qu'avec une seule implémentation.

    L'alias d'interface n'est automatique qu'avec une seule implémentation. Ajouter une seconde class qui implémente l'interface fait échouer la compilation (« Cannot autowire service … You should maybe alias this interface ») : il faut déclarer l'alias.

  • Voir l’explication : Un alias est privé par défaut, lui aussi.

    Un alias est privé par défaut, lui aussi. Créer un alias ne donne pas accès à un service par get() : il faut que l'alias soit public.

  • Voir l’explication : La configuration n'est pas relue en production.

    La configuration n'est pas relue en production. Le container est une class PHP compilée dans var/cache/<env>/ ; sans debug, le kernel ne vérifie pas sa fraîcheur. Une modification de services.yaml reste sans effet tant que le cache n'est pas vidé.

  • Voir l’explication : --show-private n'existe pas, et --show-hidden ne fait pas ce que son nom suggère.

    --show-private n'existe pas, et --show-hidden ne fait pas ce que son nom suggère. Les services privés sont listés par défaut ; --show-hidden affiche uniquement les services internes, ceux dont l'identifier commence par un point.

Fiche express

À mémoriser

À retenir en priorité
  1. La visibilité ne règle pas le partage.
  2. shared décide de la réutilisation.

Si tu dois retenir seulement 7 choses :

  • Des definitions ; l'object au premier usage, puis partagé.
  • Identifier par défaut : le FQCN.
  • Privé par défaut : injectable, pas de get(), retirable.
  • Alias d'interface : automatique avec une seule implémentation.
  • Un alias est privé par défaut, lui aussi.
  • Compilé en App_Kernel + env + (Debug) + Container ; sans debug, cache:clear.
  • debug:container liste les privés ; --show-hidden = les internes seuls.

Moyen mnémotechnique : « I-G-R : Injectable, pas de Get, Retirable ».
