Objectif

Savoir ce que le component Form protège seul contre le CSRF, comment le régler, et ce qui change avec des tokens sans état. La vérification manuelle par isCsrfTokenValid() dans un controller appartient au Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Sans état signifie sans stockage de token en session.
  2. Les contrôles de provenance restent nécessaires.

Protection activée, un form Symfony pose un field caché _token, le rend par form_end() et le vérifie à la submission : sans token valide, le form est soumis mais invalide, sans une ligne de code. Les tokens avec état vivent en session ; les tokens sans état utilisent un contrôle d'origine et/ou un double envoi. L'absence d'Origin et de Referer ne suffit pas à conclure au refus : Sec-Fetch-Site et le double envoi peuvent fournir les preuves nécessaires. Une preuve explicitement invalide entraîne un refus ; une session existante peut aussi imposer de conserver la stratégie précédemment utilisée.

Le schéma

À retenir en priorité
  1. Le nom du field est distinct de l'identifier du token.
  2. csrf_token_id choisit le contexte du token.

L'exemple : le form `task`

Exemple concret

À retenir en priorité
  1. Le token ne détermine pas isSubmitted().
  2. L'erreur CSRF appartient au form racine.

Un form task avec un field title et un sous-form address :

vue de task      : title, address, _token
vue de address   : city
soumis sans token        → invalide, « The CSRF token is invalid. Please try to resubmit the form. »
soumis avec un token valide → contrôle CSRF satisfait ; autres contraintes toujours applicables
token de task sur other  → invalide

Ce qui est automatique

Piège à éviter

C'est quoi ?

La protection CSRF, contre la falsification de requête intersite, vérifie qu'une soumission satisfait le mécanisme de protection configuré, plutôt que se fier uniquement aux cookies envoyés automatiquement par le navigateur. Dans un formulaire protégé, un champ technique transporte le token nécessaire au mécanisme.

À quoi ça sert ?

Une opération de modification ne doit pas être acceptée seulement parce qu'un navigateur authentifié l'a envoyée. La protection CSRF ne remplace cependant ni l'authentification, ni l'autorisation sur la ressource, ni la validation du contenu métier.

Où dans Symfony ?

L'extension CSRF de Form ajoute le champ technique à la vue du formulaire racine. Elle ne crée pas un token séparé sur chaque sous-formulaire. Le nom par défaut du champ est _token ; l'identifiant de token est une autre notion. Avec la protection active, une erreur CSRF rend le formulaire soumis mais invalide et se rattache à la racine.

Comment, étape par étape ?

  1. Vérifier que la protection et ses dépendances sont activées pour ce formulaire.
  2. Rendre le champ technique, explicitement ou via les champs restants.
  3. Soumettre puis contrôler isSubmitted et isValid avant toute opération.
  4. Afficher les erreurs racines pour que l'utilisateur comprenne le refus.

Exemple concret Twig

Le contexte contient la vue d'un formulaire protégé avec un champ title :

{{ form_start(form) }}
{{ form_errors(form) }}
{{ form_row(form.title) }}
<button type="submit">Enregistrer</button>
{{ form_end(form) }}

form_end rend les champs restants, dont le token s'il n'a pas déjà été rendu. Contre-exemple : désactiver render_rest sans rendre le token ailleurs, puis ignorer les erreurs du form racine. Correction : conserver le rendu restant ou rendre explicitement le champ configuré, et contrôler la validité.

Désactiver csrf_protection supprime ce contrôle, pas les autres causes d'invalidité. Un mécanisme sans état n'utilise pas nécessairement la session, mais cela ne rend pas à lui seul toute réponse cacheable ; les conditions de validation et de cache doivent être considérées séparément.

Passage canonique conservé
  • Token absent ou altéré : le form est soumis (isSubmitted() vaut true) mais invalide ; l'erreur est portée par le form racine.
  • FormTypeCsrfExtension ajoute le field dans finishView(), sur le form racine seulement : un sous-form n'a pas de token propre.
  • Le token est rendu par form_end() : désactiver render_rest impose de le rendre explicitement s'il ne l'a pas déjà été.

Les options du form

Option Role Défaut
csrf_protection active ou désactive la protection pour ce form la configuration globale
csrf_field_name le nom du field caché _token
csrf_token_id la string qui génère le token voir ci-dessous
csrf_message le message d'erreur « The CSRF token is invalid… »

csrf_protection: false désactive le contrôle CSRF du form ; les autres règles de validité restent applicables. csrf_message: 'Jeton refusé.' remplace le message. Globalement : framework.csrf_protection ; les options de form par défaut sous framework.form.csrf_protection (token_id, field_name).

Un identifier par form

À comprendre

À retenir en priorité
  1. Le token id définit le contexte de validation.
  2. Un identifier distinct évite une réutilisation entre contexts différents.

C'est quoi ?

Une attaque CSRF, falsification de requête intersite, fait envoyer au navigateur une action non voulue vers une application où il possède déjà des moyens d'authentification. Un token CSRF permet de vérifier une condition supplémentaire à la présence du cookie. L'identifiant csrf_token_id nomme l'usage du token ; ce n'est pas sa valeur secrète.

À quoi ça sert ?

Avec des tokens à état, séparer les identifiants évite qu'un token émis pour un formulaire soit accepté pour un autre usage sensible. Cette séparation ne remplace ni l'autorisation de l'utilisateur ni la validation des données. Deux formulaires utilisant volontairement le même identifiant partagent ce contexte de validation.

Où dans Symfony ?

L'extension CSRF de Form ajoute le champ à la vue du formulaire racine et vérifie la soumission. csrf_protection active le mécanisme ; csrf_field_name nomme le champ, _token par défaut ; csrf_token_id choisit son contexte. Le gestionnaire de tokens et l'intégration Form doivent être configurés : un formulaire construit avec le component nu ne reçoit pas automatiquement cette protection.

Comment, étape par étape ?

  1. Activer la protection dans l'application et le formulaire concerné.
  2. Choisir un identifiant adapté à l'usage, puis laisser le renderer afficher le champ caché.
  3. À la soumission, laisser Form vérifier le token avant toute opération métier.
  4. Tester isSubmitted() puis isValid(). Un token absent ou altéré peut laisser le formulaire soumis tout en le rendant invalide.

Exemple concret PHP

Cette méthode appartient à un type étendant AbstractType, dans une application équipée de l'intégration CSRF. Elle configure le contexte, pas la valeur du token.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function configureOptions(\Symfony\Component\OptionsResolver\OptionsResolver $resolver): void
{
    $resolver->setDefaults([
        'csrf_protection' => true,
        'csrf_field_name' => '_token',
        'csrf_token_id' => 'profile_update',
    ]);
}

Contre-exemple : fabriquer soi-même la valeur _token avec la chaîne profile_update. C'est l'identifiant, pas un token valide. Correction : laisser le gestionnaire générer et vérifier le token, et conserver son champ au rendu.

Limite importante : les tokens sans état configurés par stateless_token_ids n'utilisent pas la comparaison avec une valeur conservée en session. Ils reposent sur les contrôles d'origine prévus par le gestionnaire. Il ne faut donc pas leur appliquer mécaniquement une explication fondée sur le stockage en session, ni conclure que CSRF rend toute la page non cachable dans tous les modes.

Passage canonique conservé

Un identifier par form

Sans csrf_token_id : le défaut configuré pour le type, sinon le nom du form, sinon la class du type. Un token du form task est refusé par le form other, accepté si other reçoit csrf_token_id: 'task'. Un identifier distinct par form sensible empêche de rejouer un token volé ailleurs.

Dans le modèle de token avec état, le badge appartient à un contexte nommé par csrf_token_id. Le nom visible du field n'est pas ce contexte ; changer csrf_field_name ne crée pas une nouvelle identité de token.

Tokens avec ou sans état

À comprendre

C'est quoi ?

Le mécanisme CSRF à état compare une valeur avec celle conservée en session pour un identifiant. Le mécanisme sans état n'exige pas ce stockage de valeur de token : il utilise les informations d'origine de la Request et, selon le parcours configuré, une vérification par double envoi de token, dans le formulaire et les données de cookie ou d'en-tête prévues.

À quoi ça sert ?

On peut protéger des formulaires sans démarrer une session uniquement pour stocker leur token. Cela facilite certains usages de cache, mais ne rend pas toute réponse automatiquement partageable : ses autres données et headers restent déterminants.

Où dans Symfony ?

stateless_token_ids choisit les identifiants concernés. Dans le code 8.0, Sec-Fetch-Site présent décide du contrôle d'origine avant Origin/Referer : seule la valeur same-origin le satisfait. Une origine explicitement refusée n'est pas réparée par un autre contrôle valide. Sans information d'origine ni double envoi valide, la vérification échoue ; l'absence des seuls Origin/Referer n'est donc pas une règle universelle suffisante. Le gestionnaire peut aussi tenir compte d'une stratégie précédemment utilisée dans une session existante.

Comment, étape par étape ?

  1. Choisir quels usages doivent être sans état, par identifiant de token.
  2. Laisser Form générer le champ et vérifier la soumission via le gestionnaire configuré.
  3. Vérifier les informations HTTP réellement disponibles, notamment derrière les intermédiaires.
  4. Tester les refus, sans transformer une origine étrangère ou une information absente en acceptation par commodité.

Exemple concret YAML

framework:
    csrf_protection:
        stateless_token_ids: ['profile_update']

Un formulaire avec csrf_token_id profile_update emprunte ce mécanisme ; ce nom n'est toujours pas la valeur à fabriquer manuellement dans _token. Contre-exemple : comparer son champ à une prétendue valeur en session comme pour tout token à état. Correction : déléguer au gestionnaire sélectionné. Ne pas supprimer la protection après un échec lié aux headers : diagnostiquer le parcours HTTP et le mécanisme prévu. Cette configuration seule ne réalise pas une intégration cliente de double envoi.

Passage canonique conservé

Tokens avec ou sans état

Avec état Sans état
stockage session (démarrée pour l'occasion) pas de valeur de token en session ; le cache de la page dépend aussi de son contenu et de ses headers
validation token = celui de la session contrôle d'origine et/ou double envoi ; absence des deux ou refus explicite : échec ; stratégie de session préexistante à respecter
déclaration le défaut sans configuration framework.csrf_protection.stateless_token_ids
  • L'absence d'Origin et de Referer ne suffit pas à conclure au refus. Sec-Fetch-Site: same-origin ou un double envoi valide peuvent fournir la preuve nécessaire. Si les deux preuves sont absentes, la vérification échoue.
  • Dans Symfony 8.0, Sec-Fetch-Site est prioritaire pour le contrôle d'origine : seule same-origin le satisfait. Une origine explicitement refusée n'est pas compensée par un double envoi valide. Une preuve de double envoi explicitement invalide entraîne aussi un refus. La stratégie précédemment utilisée dans une session existante ne doit pas être dégradée.
  • Dans une application Flex, la configuration fournie déclare stateless_token_ids: ['submit', 'authenticate', 'logout'].
  • Hors form : {{ csrf_token('delete-item') }} dans le template.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le token est rendu par form_end().

    Le token est rendu par form_end(). Désactiver son option render_rest impose un rendu explicite du token s'il manque.

  • Voir l’explication : Un form sans token valide est invalide

    Un form sans token valide est invalide ; c'est le component qui refuse.

  • Voir l’explication : Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form

    Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form — et dans une application Flex, la configuration fournie donne submit à tous les form types autoconfigurés : un identifier commun.

  • Voir l’explication : Sans état ne veut pas dire sans contrôle

    Sans état ne veut pas dire sans contrôle : contrôle d'origine et/ou double envoi, sans preuve explicitement invalide et sans dégradation de la stratégie d'une session existante. Origin et Referer ne sont pas les seules preuves possibles.

  • Voir l’explication : Un sous-form n'a pas son propre token

    Un sous-form n'a pas son propre token : seul le form racine en reçoit un.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Field caché _token, sur le form racine seulement, rendu par form_end().
  • Token absent ou faux : soumis, mais invalide.
  • Quatre options : csrf_protection, csrf_field_name, csrf_token_id, csrf_message.
  • Identifier par défaut : défaut du type, sinon nom du form ; submit avec Flex.
  • Avec état : token en session ; sans état : origine et/ou double envoi, avec refus explicites et protection contre la dégradation de stratégie.
  • Hors form : csrf_token('id') dans le template.

Moyen mnémotechnique : « Poser, rendre, vérifier ».
