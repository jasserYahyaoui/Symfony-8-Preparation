Objectif

Savoir ce que le component Form protège seul contre le CSRF, comment le régler, et ce qui change avec des tokens sans état. La vérification manuelle par isCsrfTokenValid() dans un controller appartient au Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Sans état signifie sans stockage de token en session.
  2. Les contrôles de provenance restent nécessaires.

La protection CSRF empêche de confondre une soumission autorisée avec une requête provoquée par un autre site utilisant les cookies du navigateur. Elle ne remplace ni l'autorisation ni la validation des données métier. L'extension CSRF de Form ajoute un champ caché au formulaire racine ; form_end() rend ce champ s'il reste à rendre. À la soumission, le gestionnaire vérifie le token : un refus rend le formulaire soumis mais invalide.

Avec état, le token est vérifié à l'aide de la session. Sans état, le gestionnaire utilise les preuves d'origine et/ou de double envoi. Une preuve invalide provoque un refus ; une session déjà utilisée peut imposer de conserver la stratégie précédente. « Sans état » ne veut donc pas dire « sans contrôle ».

Le schéma

À retenir en priorité
  1. Le nom du field est distinct de l'identifier du token.
  2. csrf_token_id choisit le contexte du token.

Bleu : transport du token ; losange ambre : décision ; sorties arrondies : résultat du contrôle. Les flèches représentent des opérations, pas de l'héritage. Le détail du contrôle sans état est expliqué dans « Tokens avec ou sans état ».

L'exemple : le form `task`

Exemple concret

À retenir en priorité
  1. Le token ne détermine pas isSubmitted().
  2. L'erreur CSRF appartient au form racine.

Un form task avec un field title et un sous-form address :

vue de task      : title, address, _token
vue de address   : city
soumis sans token        → invalide, « The CSRF token is invalid. Please try to resubmit the form. »
soumis avec un token valide → contrôle CSRF satisfait ; autres contraintes toujours applicables
option CSRF du sous-form seul → aucun token enfant indépendant
racine désactivée + enfant activé → la racine reste non protégée
token avec état de task sur other, identifiants distincts → refusé

Ce qui est automatique

  • Token absent ou altéré : le form est soumis (isSubmitted() vaut true) mais invalide ; l'erreur est portée par le form racine.
  • FormTypeCsrfExtension ajoute le field dans finishView(), sur le form racine seulement : un sous-form n'a pas de token propre.
  • form_end() rend le token parmi les champs restants. Avec render_rest: false, il faut l'avoir rendu explicitement, par exemple avec form_row(form._token) si le nom du champ n'a pas été personnalisé.

Les options du form

Option Role Défaut
csrf_protection active ou désactive la protection pour ce form la configuration globale
csrf_field_name le nom du field caché _token
csrf_token_id la string qui génère le token voir ci-dessous
csrf_message le message d'erreur « The CSRF token is invalid… »

csrf_protection: false supprime le contrôle CSRF, pas les autres causes d'invalidité. csrf_message: 'Jeton refusé.' remplace le message. Globalement : framework.csrf_protection ; les options de form par défaut sous framework.form.csrf_protection (token_id, field_name).

Un identifier par form

À retenir en priorité
  1. Le token id définit le contexte de validation.
  2. Un identifier distinct évite une réutilisation entre contexts différents.

Sans csrf_token_id : le défaut configuré pour le type, sinon le nom du form, sinon la class du type. Avec des tokens à état, un token du form task est refusé par le form other, accepté si other reçoit csrf_token_id: 'task'. Un identifier distinct par form sensible empêche de rejouer un token volé ailleurs.

Dans le modèle de token avec état, le badge appartient à un contexte nommé par csrf_token_id. Le nom visible du field n'est pas ce contexte ; changer csrf_field_name ne crée pas une nouvelle identité de token.

Tokens avec ou sans état

Avec état Sans état
stockage token conservé en session pas de token persistant côté serveur ; cela ne garantit pas à lui seul la mise en cache de la page
validation vérification à l'aide du token en session preuves d'origine et/ou de double envoi, sans refus explicite ni dégradation de stratégie
déclaration le défaut sans configuration framework.csrf_protection.stateless_token_ids
  • Pour la preuve d'origine, Sec-Fetch-Site, s'il existe, est prioritaire : seule la valeur same-origin convient. Sinon, le gestionnaire examine Origin et Referer.
  • Sans preuve d'origine, un double envoi valide peut suffire : la valeur est présentée dans la soumission et dans un cookie et/ou un header selon la configuration. Sans aucune preuve, le contrôle échoue. Une preuve explicitement invalide n'est pas compensée par l'autre.
  • Avec une session existante ayant mémorisé une stratégie, retirer une preuve précédemment utilisée peut faire échouer le contrôle. À l'examen, ne déduire ni acceptation ni refus de la seule absence de Origin.
  • Dans une application Flex, la configuration fournie déclare stateless_token_ids: ['submit', 'authenticate', 'logout'].
  • Hors form : {{ csrf_token('delete-item') }} dans le template.

Pièges d'examen

Piège à éviter

  • Voir l’explication : form_end() rend les champs restants.

    form_end() rend les champs restants. Désactiver render_rest ne supprime pas un token déjà rendu explicitement.

  • Voir l’explication : Un form sans token valide est invalide

    Un form sans token valide est invalide ; c'est le component qui refuse.

  • Voir l’explication : Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form

    Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form — et dans une application Flex, la configuration fournie donne submit à tous les form types autoconfigurés : un identifier commun.

  • Voir l’explication : Sans état ne veut pas dire sans contrôle

    Sans état ne veut pas dire sans contrôle : preuves d'origine, double envoi et stratégie antérieure doivent être considérés ensemble.

  • Voir l’explication : Un sous-form n'a pas son propre token

    Un sous-form n'a pas son propre token : seul le form racine en reçoit un.

Application

À retenir en priorité
  1. Le nom du field est distinct de l'identifier du token.
  2. csrf_token_id choisit le contexte du token.
  3. Le token id définit le contexte de validation.
  4. Un identifier distinct évite une réutilisation entre contexts différents.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Field caché _token, sur le form racine seulement, rendu par form_end().
  • Token absent ou faux : soumis, mais invalide.
  • Quatre options : csrf_protection, csrf_field_name, csrf_token_id, csrf_message.
  • Identifier par défaut : défaut du type, sinon nom du form ; submit avec Flex.
  • Avec état : session ; sans état : origine et/ou double envoi, sans preuve invalide ni dégradation d'une stratégie mémorisée.
  • Hors form : csrf_token('id') dans le template.

Moyen mnémotechnique : « Poser, rendre, vérifier ».

Does stateless CSRF mean no request validation?

No. Origin checks and/or double-submit evidence are required, subject to explicit failures and the previous session strategy.
