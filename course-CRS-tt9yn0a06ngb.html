Objectif

Situer le unit test parmi les trois types que la documentation Symfony distingue, et connaître la mise en place attendue d'un projet.

L'essentiel

À comprendre

À retenir en priorité
  1. Le test unitaire isole la logique.
  2. Le kernel appartient à une frontière d'intégration.

La documentation Symfony distingue trois types de tests : unitaire, intégration, application. Un unit test n'a rien de spécifique à Symfony : un test PHPUnit ordinaire, sans kernel ni container. Pour les tests unitaires de ce périmètre, PHPUnit peut être installé directement comme dependency de développement et lancé avec vendor/bin/phpunit. La convention tests/ reproduit src/.

Le schéma

À retenir en priorité
  1. Chaque base correspond à un scope.
  2. Choisir la plus légère adaptée au comportement.

L'exemple : un calcul

Exemple concret

À retenir en priorité
  1. La construction locale garde le test isolé.
  2. Aucune configuration du kernel n'est requise.
// tests/Util/CalculatorTest.php — reflète src/Util/Calculator.php
class CalculatorTest extends TestCase
{
    public function testAdd(): void
    {
        $this->assertSame(42, (new Calculator())->add(30, 12));
    }
}

Aucun kernel n'est démarré, aucun container n'est construit.

Trois types, trois périmètres

À comprendre

À retenir en priorité
  1. Le container assemble plusieurs services.
  2. La frontière du test s'élargit.
  3. Une ligne de provider produit une exécution du test.
  4. Le provider public static fournit des données, pas un kernel de test.

C'est quoi ?

Un test unitaire vérifie une unité de logique isolée. Un test d'intégration vérifie l'assemblage de plusieurs éléments. Un test d'application, aussi appelé functional test, traverse le comportement HTTP de l'application.

À quoi ça sert ?

Choisir la plus petite frontière suffisante rend les échecs plus faciles à expliquer. Un calcul pur n'a pas besoin de démarrer Symfony ; une erreur de câblage de services ne peut pas être détectée par ce seul calcul.

Où dans Symfony ?

Utiliser PHPUnit\Framework\TestCase pour l'unitaire, KernelTestCase pour le kernel et le container, WebTestCase pour le client d'application. Les tests vivent habituellement dans tests/, avec noms de classes et fichiers terminés par Test pour la découverte habituelle.

Comment, étape par étape ?

  1. Préparer une entrée représentative.
  2. Appeler le comportement à vérifier.
  3. Affirmer un résultat précis ; l'absence d'exception seule est rarement le contrat complet.
  4. Ajouter un cas limite distinct. Un data provider peut fournir plusieurs jeux d'arguments, sans démarrer le kernel dans ce fournisseur de données.

Exemple concret PHP

Test unitaire d'une petite règle de libellé, sans kernel ; PHPUnit reste nécessaire pour exécuter la classe de test :

<?php
use PHPUnit\Framework\TestCase;

final class Label
{
    public static function normalize(string $value): string
    {
        return trim($value);
    }
}

final class LabelTest extends TestCase
{
    public function testRemovesSurroundingSpaces(): void
    {
        self::assertSame('Bonjour', Label::normalize(' Bonjour '));
    }
    public function testAllowsEmptyLabel(): void
    {
        self::assertSame('', Label::normalize('   '));
    }
}

Le second test rend explicite le choix concernant une chaîne vide ; il faudrait une autre règle si le métier l'interdisait. Contre-exemple : démarrer le kernel pour ce calcul puis appeler ce test « unitaire ». Correction : garder le test isolé et réserver le kernel aux interactions qui le requièrent.

Dans une application préparée pour les tests, composer require --dev symfony/test-pack installe l'outillage et php bin/phpunit lance la suite. Ces commandes ne sont pas exécutées ici. Vérifier la configuration PHPUnit effective : un fichier local prioritaire peut changer la découverte et les options de la configuration partagée.

Tests Symfony 8.0.

Passage canonique conservé

Trois types, trois périmètres

Type Ce qu'il couvre Class de base
Unitaire une class, une method TestCase de PHPUnit
Intégration plusieurs classes ensemble, souvent via le container KernelTestCase
Application l'application complète, de la route à la vue WebTestCase

« Test d'application » et functional test sont synonymes. Dès qu'un test appelle bootKernel(), il est d'intégration ; sans kernel désigné, il échoue — « You must set the KERNEL_CLASS environment variable… » —, alors qu'un TestCase passe sans rien configurer.

Un data provider PHPUnit permet d'exécuter le même test unitaire sur plusieurs cas, sans démarrer le kernel. Dans le contrat PHPUnit 12.0 utilisé ici, #[DataProvider('cases')] désigne une method public static qui retourne un iterable d'arrays d'arguments ; chaque ligne devient une exécution distincte. Préparer les données dans ce provider ne remplace pas l'arrangement des services dans le test lui-même.

L'installation

À retenir en priorité
  1. La configuration locale est prioritaire.
  2. La version dist fournit le réglage partagé.
composer require --dev phpunit/phpunit
vendor/bin/phpunit

PHPUnit peut être installé directement pour les tests unitaires. Les packages d'intégration supplémentaires ne sont pas nécessaires à cette démonstration. La configuration du projet définit notamment le bootstrap et les suites de tests ; installer PHPUnit seul ne génère pas automatiquement la configuration d'une application Symfony.

Où vivent les tests

À retenir en priorité
  1. La découverte utilise un suffixe.
  2. Un nom proche mais différent peut être ignoré.

Dans tests/, dont l'arborescence reproduit celle de src/, chaque class se terminant par Test. Le suffixe compte : en parcourant un directory, PHPUnit n'exécute que CalcTest.php, pas CalcTests.php, qui ne tourne que désigné explicitement.

php bin/phpunit tests/Form                     # un répertoire
php bin/phpunit tests/Form/UserTypeTest.php    # un file

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le vocabulaire décrit le même scope.
  2. Ne pas compter deux niveaux distincts.
  • Voir l’explication : Un unit test ne démarre pas le kernel.

    Un unit test ne démarre pas le kernel. Dès qu'un test appelle bootKernel(), il est d'intégration.

  • Voir l’explication : « Functional test » et « test d'application » désignent la même chose

    « Functional test » et « test d'application » désignent la même chose dans le vocabulaire Symfony.

  • Voir l’explication : php bin/phpunit

    php bin/phpunit est la command que donne la documentation 8.0.

  • Voir l’explication : Un file …Tests.php est ignoré

    Un file …Tests.php est ignoré quand PHPUnit parcourt un directory.

  • Priorité des fichiers de configuration PHPUnit

    phpunit.xml passe avant phpunit.dist.xml.

  • Voir l’explication : tests/ reflète src/

    tests/ reflète src/, et les classes se terminent par Test.

Fiche express

À mémoriser

À retenir en priorité
  1. La structure facilite la navigation.
  2. Elle ne prouve pas à elle seule une couverture comportementale.

Si tu dois retenir seulement 6 choses :

  • Trois types : unitaire, intégration, application (= functional).
  • Un unit test : TestCase, sans kernel ni container.
  • bootKernel() → intégration ; KERNEL_CLASS identifie le kernel à charger.
  • PHPUnit installé directement : vendor/bin/phpunit.
  • phpunit.xml > phpunit.dist.xml > phpunit.xml.dist.
  • tests/ reflète src/, suffixe Test.

Moyen mnémotechnique : « Une class, un kernel, toute l'application ».
