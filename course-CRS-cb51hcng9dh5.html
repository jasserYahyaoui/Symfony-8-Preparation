Objectif

Les commandes intégrées inspectent l'application ; aucune ne connaît notre traitement d'import. Il faut donc exposer ce travail sous app:blog:import et lui fournir les services nécessaires. Nous allons séparer découverte, injection et appel, puis conserver une petite branche utile : créer un auteur par le terminal avant de lui attribuer des articles.

L'essentiel

À comprendre

À retenir en priorité
  1. La command invocable évite l'inheritance.
  2. Le contrat reste un exit code int.

Une commande expose un traitement applicatif au terminal, sans faire passer ce travail par BlogController::show. Avec Symfony 8.0, une classe ordinaire portant #[AsCommand] et une méthode __invoke(): int suffit dans une application qui l'enregistre comme service avec autoconfiguration. Elle n'a pas besoin d'hériter de Command.

Deux étapes sont distinctes : enregistrer la commande dans le catalogue, puis l'exécuter avec des entrées. L'attribute ne scanne pas les fichiers à lui seul. Étendre Command reste une autre forme valide, notamment pour personnaliser initialize().

Une classe invocable possède une méthode publique __invoke() : son objet peut être appelé comme une fonction. Cela décrit une capacité PHP, pas une inscription automatique dans Console. Le nom de commande, la définition du service et l'adaptation par Console donnent à cette capacité une entrée CLI.

Le schéma

À retenir en priorité
  1. La class doit être un service.
  2. L'autoconfiguration lit AsCommand.

Avant de recevoir articles.csv, la préparation du conteneur doit relier le nom de commande à un service. Une classe exclue des ressources de services ne franchit pas la première étape, même avec le bon attribut :

Les pointillés décrivent la configuration et la compilation ; le trait plein décrit le chargement à l'exécution. Les couleurs distinguent configuration (gris), décision (ambre), objets (bleu) et résultat (vert). Ce n'est pas un graphe d'héritage : le cas extends Command est un critère d'autoconfiguration, pas un appel à la classe parente.

Ce travail de préparation n'est pas rejoué pour chaque article importé ni pour chaque GET /blog/42. Une fois le conteneur utilisable, Console résout le nom demandé et obtient la commande ; le traitement métier vient ensuite.

L'exemple : créer un user

Exemple concret

À retenir en priorité
  1. La command est un service ordinaire.
  2. Les arguments CLI restent des entrées d'exécution.

🌍 In Real Life

La situation : l'équipe du blog équipe le bureau de création des auteurs, puis lui remet le dossier « Alice ».

L’équivalent dans Symfony : équipement du bureau → UserManager injecté au constructeur ; dossier courant → nom fourni par l'entrée Console.

Retour à la réalité technique : le conteneur fournit le service ; Console fournit les valeurs de la commande. Créer un compte n'authentifie pas une requête. En mode non interactif, une entrée requise manquante doit être traitée avant l'appel métier.

🧠 Comment le mémoriser : « L'outil reste, le dossier change. » Image mentale : un outil fixe et une pile de noms. Question-réflexe : cette valeur vient-elle du conteneur ou du terminal ?

⚠️ À ne pas confondre : injection de dépendances et résolution des entrées CLI.

Conservons cette branche d'administration : créer l'auteur Alice avant l'import de ses articles. Le mécanisme d'injection est le même que pour un service d'import ; créer l'auteur n'est pas authentifier une requête HTTP. La classe ci-dessous suppose un service applicatif App\Service\UserManager avec une méthode create(string $name) qui réalise ce travail :

<?php
namespace App\Command;

use App\Service\UserManager;
use Symfony\Component\Console\Attribute\Argument;
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Attribute\Ask;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Output\OutputInterface;

#[AsCommand(name: 'app:create-user', description: 'Creates a user')]
class CreateUserCommand
{
    public function __construct(private UserManager $userManager)
    {
    }

    public function __invoke(OutputInterface $output, #[Argument, Ask('Name?')] string $name): int
    {
        $this->userManager->create($name);
        $output->writeln('User successfully generated!');

        return Command::SUCCESS;
    }
}

Les dependencies arrivent par le constructor ; __invoke() reçoit l'output, l'entrée, et les arguments et options décrits par attributes.

UserManager est une dépendance à fournir, pas un service Symfony implicite. La création et la persistance de comptes ne sont pas implémentées par ce fragment. Une fois la classe et cette dépendance enregistrées :

php bin/console app:create-user Alice

Le service reçoit Alice. Si create() se termine normalement, la sortie est la suivante et le code de commande vaut 0 :

User successfully generated!

Avec -n sans nom, la validation échoue avant cet appel : le code ne crée pas un utilisateur vide. Les dépendances du constructeur restent différentes des valeurs de saisie : UserManager vient du conteneur, Alice vient de l'entrée Console.

La forme recommandée : la command invocable

À retenir en priorité
  1. Le nom permet d'appeler la command.
  2. Description et aide sont facultatives.

Pour isoler l'enregistrement de toute logique de compte, voici aussi la commande minimale app:greet, à placer dans src/Command/GreetCommand.php et à découvrir comme service. Elle conserve le petit test de contrat :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Output\OutputInterface;

#[AsCommand(name: 'app:greet', description: 'Affiche un accueil.')]
final class GreetCommand
{
    public function __invoke(OutputInterface $output): int
    {
        $output->writeln('Bonjour.');

        return Command::SUCCESS;
    }
}
php bin/console app:greet

Résultat attendu en verbosity normale, avec code 0 :

Bonjour.

Importer Command donne accès à la constante, sans imposer l'héritage. Utiliser OutputInterface ou SymfonyStyle permet à Console de maîtriser la sortie ; un echo métier contournerait notamment ce réglage.

  • La class n'étend pas Command ; la constant Command::SUCCESS reste utilisée pour la lisibilité.
  • #[AsCommand] n'exige que name ; description, aliases, hidden, help et usages sont facultatifs.
  • #[Ask] pose la question si l'argument manque ; #[Interact] sur une method publique couvre une interaction plus riche. Avec -n et sans argument : « Not enough arguments (missing: "name"). », code 1.

La question ne doit pas devenir un prérequis caché de l'automatisation. Pour app:blog:import, transmettre le chemin explicitement avec -n rend le contrat reproductible. Les noms et les valeurs acceptées seront détaillés dans Options et arguments.

Comment Symfony la trouve

À retenir en priorité
  1. Être invocable ne suffit pas.
  2. Le framework doit reconnaître la command.

🌍 In Real Life

La situation : une personne compétente pour importer les articles doit aussi figurer dans l'annuaire du blog.

L’équivalent dans Symfony : personne identifiée → définition de service ; rôle déclaré → tag console.command ; annuaire préparé → configuration du chargeur de commandes.

Retour à la réalité technique : avec l'autoconfiguration, #[AsCommand] apporte le rôle à un service découvert. Le compiler pass prépare son intégration ; l'attribut ne recherche pas seul toutes les classes du disque.

🧠 Comment le mémoriser : « Compétent ne veut pas dire enregistré. » Image mentale : une fiche à insérer dans l'annuaire. Question-réflexe : la définition existe-t-elle et porte-t-elle le bon tag ?

⚠️ À ne pas confondre : commande cachée de la liste et commande non enregistrée.

Une commande absente de list peut être non enregistrée ou simplement cachée. Pour trancher, suivre les responsabilités plutôt que modifier au hasard son constructeur :

  1. La configuration des services inclut une définition de la classe.
  2. FrameworkExtension enregistre les règles d'autoconfiguration : #[AsCommand] ou l'héritage de Command fait ajouter le tag console.command à une définition autoconfigurée.
  3. Le compiler pass AddConsoleCommandPass consomme les définitions taguées. Pour une classe ordinaire invocable, il prépare un objet Command adaptateur et lui associe le callable via setCode().
  4. Les noms connus alimentent le chargeur de commandes ; un nom fourni uniquement lors de la construction d'une commande classique suit la voie d'enregistrement correspondante. À l'exécution, Application peut alors demander la commande choisie.

L'autowiring résout les dépendances comme UserManager ; l'autoconfiguration attribue ici le tag ; l'extension enregistre ces règles et le compiler pass exploite les définitions. Ce sont des rôles distincts, pas quatre mots pour « créer la commande ».

Class Attribute Résultat
étend Command, nom posé dans configure() non enregistrée
invocable, n'étend rien non absente de l'application
invocable, hidden: true, alias app:h oui absente de list, exécutable par son nom et son alias

Une class de bibliothèque, hors de la ressource src/, se déclare comme service.

Ces résultats supposent l'autoconfiguration active et aucune déclaration manuelle de tag. Une définition explicitement marquée console.command constitue une autre voie d'enregistrement ; ne pas confondre « non découvert automatiquement » avec « impossible à enregistrer ».

Dans la voie manuelle, fournir aussi un nom de commande exploitable : un tag sur une invocable anonyme ne suffit pas à inventer le nom métier app:blog:import. Le nom de classe n'est pas une convention de commande automatique.

La syntaxe classique, toujours valide

À retenir en priorité
  1. Le style classique n'est pas supprimé.
  2. Il donne notamment accès à initialize().

Voici une alternative, et non une seconde classe à charger en même temps que l'exemple CreateUserCommand. Ce squelette montre uniquement la signature classique ; il n'appelle pas encore UserManager :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Input\InputInterface;
use Symfony\Component\Console\Output\OutputInterface;

#[AsCommand(name: 'app:create-user')]
class CreateUserCommand extends Command
{
    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        return Command::SUCCESS;
    }
}

La documentation la nomme legacy syntax. initialize() est une method de Command, sans équivalent par attribute : une command qui en a besoin étend Command, et peut alors définir __invoke() au lieu d'execute() — initialize() puis __invoke().

La condition compte : Command sélectionne l'adaptateur invocable si execute() reste celui de la classe de base. Avec une redéfinition d'execute(), ne pas supposer que Console exécute également __invoke(). Si un constructeur personnalisé est nécessaire dans la sous-classe, appeler le constructeur parent pour initialiser la définition et la configuration de la commande.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Masquer ne désactive pas.
  2. Un alias reste un accès valide.
  • Voir l’explication : Une command invocable n'a pas besoin d'étendre Command.

    Une command invocable n'a pas besoin d'étendre Command. L'invocation et l'héritage ne sont pas incompatibles : le cas hybride a été décrit ci-dessus.

  • Voir l’explication : __invoke() doit retourner un int.

    __invoke() doit retourner un int. C'est l'exit code du process.

  • Voir l’explication : #[AsCommand] exige un name.

    #[AsCommand] exige un name. C'est le seul parameter obligatoire ; description, aliases, hidden, help et usages sont facultatifs.

  • Voir l’explication : Sans attribute, une sous-classe de Command peut être enregistrée par autoconfiguration

    Sans attribute, une sous-classe de Command peut être enregistrée par autoconfiguration, avec un nom défini. Une invocable ordinaire sans attribut ni autre enregistrement ne reçoit pas automatiquement le tag.

  • Voir l’explication : hidden: true retire la command de list, pas de l'application.

    hidden: true retire la command de list, pas de l'application. Ce n'est pas une autorisation d'administration : le contrôle d'accès au process et les protections du traitement restent nécessaires.

  • Voir l’explication : Interagir ne suppose plus d'étendre Command

    Interagir ne suppose plus d'étendre Command : #[Ask] et #[Interact]. Seul initialize() reste propre à Command.

  • Voir l’explication : Le callable doit respecter le contrat de paramètres.

    Le callable doit respecter le contrat de paramètres. Même avec setCode(), une closure aux paramètres $input, $output non typés échoue à leur résolution en 8.0. Donner les types Console reconnus et retourner un entier ; le problème peut apparaître à l'exécution, loin de l'appel à setCode(). Un service métier arbitraire typé dans __invoke() ne devient pas pour autant une dépendance autowirée : le placer dans le constructeur.

Fiche express

À mémoriser

À retenir en priorité
  1. L'interaction ne nécessite pas toujours Command.
  2. Le mode non interactif peut la sauter.

Pour notre import, la bonne question de diagnostic dépend du moment : la commande est-elle enregistrée, ses dépendances sont-elles résolues, ou ses entrées d'exécution sont-elles invalides ?

Si tu dois retenir seulement 6 choses :

  • #[AsCommand(name: …)] + __invoke(): int, sans inheritance.
  • Tag console.command : l'attribute, ou une sous-classe de Command.
  • Invocable ordinaire sans attribute ni autre enregistrement : pas automatiquement une command.
  • Dependencies par le constructor : la command est un service.
  • hidden: true : hors de list, toujours exécutable.
  • extends Command : legacy, mais seul accès à initialize().

Moyen mnémotechnique : « Un attribute, un __invoke(), un int ».

L'interface existe ; il reste à nommer ses alias, rédiger son aide et choisir ce qui est visible. Continuer avec Console Configuration.
