Du navigateur à Request

Fixons les hypothèses : application conventionnelle, route blog_show importée, contrôleur enregistré, entrée Runtime HTTP standard, requête principale, aucun cache réutilisable ni interruption. Le navigateur demande GET /blog/42. Le serveur transmet au point d’entrée public/index.php.

Dans cette variante, vendor/autoload_runtime.php résout et appelle le callable qui construit App\Kernel. Construire cet objet n’est pas le booter. SymfonyRuntime::getRunner() crée ensuite la Request depuis les superglobales pour ce chemin standard. Le runner appelle handle() ; le Kernel prépare l’application et délègue au service http_kernel. Un conteneur compilé utilisable est chargé ; il n’est reconstruit que si nécessaire.

Une entrée manuelle assume explicitement création de Request, handle, envoi et terminaison éventuelle. Ce n’est pas une deuxième séquence à superposer au Runtime. Un runner personnalisé peut aussi changer l’entrée.

🌍 In Real Life

La situation : l’établissement se prépare, puis un responsable coordonne la commande ; le résultat prêt attend encore sa remise.

L’équivalent dans Symfony : préparation de l’établissement → Kernel ; coordination de la demande → HttpKernel ; bon reçu → Request ; résultat prêt → Response ; remise → émission par le runner.

Retour à la réalité technique : Runtime amorce l’application et choisit un runner. Dans cette variante standard, le Kernel est construit avant la Request, mais construire n’est pas booter. handle() retourne la Response ; l’envoi puis l’éventuel terminate() sont séparés. L’image ne garantit pas la réception réseau.

🧠 Comment le mémoriser : « Prêt n’est pas envoyé. » Image : plateau encore au comptoir. Réflexe : « Qui appelle handle, send et terminate dans cette entrée ? »

⚠️ À ne pas confondre : Kernel prépare l’application ; HttpKernel traite la requête ; une entrée manuelle remplace ce chemin Runtime, elle ne le double pas.

Choisir puis appeler le contrôleur

HttpKernel empile la Request et dispatche kernel.request. Si l’exécution atteint RouterListener, il peut effectuer le matching et écrire _route, _controller et id dans les attributes de Request. Dans notre exemple, id est la chaîne '42'. Un requirement numérique contraint le matching : il ne prouve pas l’existence de l’article et ne charge rien.

Le callable et ses arguments sont deux résultats différents. Après kernel.controller, ArgumentResolver interroge ses value resolvers pour la signature finale : Request courante, attribut de route, service d’un locator d’action, etc. Un resolver qui ne produit aucune valeur laisse essayer le suivant. kernel.controller_arguments peut encore modifier arguments et callable.

L’action consulte maintenant ArticleCatalog, notre service en mémoire. Le routeur n’a pas lu l’article. Une intégration Doctrine configurée peut résoudre une entité avant l’action ; ce comportement appartient au bridge, pas à HttpKernel seul, et l’ORM reste hors du programme étudié.

🌍 In Real Life

La situation : pour le bon 42, le responsable cherche la destination, le poste capable d’agir, puis les informations à lui remettre.

L’équivalent dans Symfony : destination annotée → matching et attributes via RouterListener ; poste choisi → callable du ControllerResolver ; fiche renseignée → arguments de l’ArgumentResolver ; consultation du catalogue → action appelant ArticleCatalog.

Retour à la réalité technique : HttpKernel orchestre ces collaborateurs ; ils ne s’appellent pas en chaîne. Résoudre prépare l’invocation, sans prouver l’existence de l’article. Dans la variante Doctrine, la résolution d’entité avant l’action repose sur le Doctrine Bridge et une intégration avec mapping configurés. Un value resolver personnalisé peut charger un objet sans Doctrine ; HttpKernel seul ne fournit pas ce chargement et l’ORM reste hors du programme étudié.

🧠 Comment le mémoriser : « Où, qui, avec quoi. » Image : destination, poste, fiche. Réflexe : « Ai-je obtenu des attributes, un callable ou des valeurs ? »

⚠️ À ne pas confondre : id = '42' n’est ni une entité chargée ni une conversion garantie par un requirement numérique.

Les événements changent le trajet

Un listener peut produire une réponse de maintenance sur kernel.request. HttpKernel n’a alors pas besoin du contrôleur. Autre bifurcation : si l’action ne retourne pas une Response, kernel.view permet à un listener d’en fournir une ; sans conversion, une exception est levée. Un tableau ne devient donc pas automatiquement du JSON.

Ce dessin ne promet pas tous ces événements à chaque requête. $catch=false, la prise en charge des Error, une exception non convertie ou une panne dans un listener changent la sortie. kernel.finish_request permet notamment de restaurer un contexte parent ; le dépilement se fait dans le finally. Il ne signifie pas que les octets sont déjà envoyés. Terminate n’est pas un worker durable. Approfondir événements et priorités.

🌍 In Real Life

La situation : une annonce « commande reçue » permet à l’accueil de répondre « maintenance » avant toute préparation.

L’équivalent dans Symfony : annonce → événement ; réaction enregistrée → listener ; intervenant déclarant les annonces auxquelles il réagit → subscriber ; réponse de maintenance → RequestEvent::setResponse().

Retour à la réalité technique : EventDispatcher appelle des callables selon priorité et propagation. Un subscriber est une classe déclarant ses abonnements, avec des méthodes de réaction, pas une simple procédure écrite. Une réponse anticipée saute le contrôleur ; kernel.view ne survient que pour un retour autre que Response.

🧠 Comment le mémoriser : « Une annonce ouvre une possibilité, pas une obligation. » Image : embranchement devant la cuisine. Réflexe : « Quelle condition rend cet événement atteignable ? »

⚠️ À ne pas confondre : fin du traitement, émission et terminaison ; une panne peut interrompre ce parcours.

HTML, JSON et sécurité : des choix configurés

Pour le navigateur, Twig peut rendre ArticleView en HTML avant que l’action retourne la Response. Pour GET /api/blog/42, Serializer peut normaliser l’objet puis encoder du JSON. Ce sont deux représentations possibles, pas deux étapes obligatoires de GET. Désérialiser n’est ni valider ni autoriser.

Avec Security installé et configuré, le firewall participe à kernel.request ; il n’attend pas une prétendue étape ORM obligatoire. Un contrôle d’autorisation dans l’action a lieu au point où vous l’appelez ; #[IsGranted] utilise un listener de kernel.controller_arguments. Ne placez donc pas toute la sécurité à une position universelle.

🌍 In Real Life

La situation : le restaurant présente une fiche au client, mais réserve les notes internes au personnel autorisé.

L’équivalent dans Symfony : fiche mise en page → rendu Twig/HTML ; données structurées exportées → normalisation puis encodage JSON ; identité vérifiée → authentification ; permission de consulter les notes → autorisation.

Retour à la réalité technique : Twig rend un contenu ; Serializer convertit des représentations ; Security établit le contexte et contrôle les droits selon configuration. Aucun format ne rend les données automatiquement accessibles. Les contrôles peuvent intervenir avant l’action, pas seulement après une lecture métier.

🧠 Comment le mémoriser : « Présenter n’est pas permettre. » Image : même fiche, deux lecteurs aux droits différents. Réflexe : « Qui peut voir quels champs, et où ce droit est-il contrôlé ? »

⚠️ À ne pas confondre : connaître l’identité n’accorde pas tous les droits ; produire du JSON ne valide pas les données.

Route absente, article absent, panne

Un chemin inconnu peut échouer au matching. /blog/999 peut matcher parfaitement mais ne trouver aucun article dans le catalogue : l’action décide alors d’une 404 explicite. Une panne inattendue n’est pas une troisième preuve d’absence ; elle relève du traitement d’erreur, souvent 500, sans exposer de détails sensibles.

🌍 In Real Life

La situation : l’accueil ne connaît pas la destination demandée ; ailleurs, le poste existe mais la référence manque ; ailleurs encore, le poste tombe en panne.

L’équivalent dans Symfony : destination inconnue → échec de matching ; référence 999 absente du catalogue → 404 décidée par l’action ; panne inattendue → traitement d’erreur, souvent 500.

Retour à la réalité technique : 404 signifie ressource non trouvée, pas nécessairement route inconnue. Une exception interceptée peut être convertie via kernel.exception ; sans Response fournie, elle remonte. L’analogie ne promet pas une réponse sur toute panne.

🧠 Comment le mémoriser : « Même 404, origines différentes. » Image : panneau absent ou fiche introuvable. Réflexe : « Le matching a-t-il réussi avant l’échec ? »

⚠️ À ne pas confondre : absence attendue et défaillance interne ; le client ne doit pas recevoir les détails sensibles de la panne.

Lisez les exceptions HTTP après les statuts.

Un cache navigateur/proxy peut répondre avant PHP. Le cache HTTP Symfony optionnel peut éviter le HttpKernel interne. Un cache applicatif réutilise un résultat de service : il ne supprime pas automatiquement le traitement HTTP.

🌍 In Real Life

La situation : l’accueil conserve une copie autorisée d’une fiche publique ; en cuisine, on conserve seulement un calcul utile à sa préparation.

L’équivalent dans Symfony : fiche complète réutilisée à l’accueil → cache HTTP ; résultat intermédiaire réutilisé au poste → cache applicatif.

Retour à la réalité technique : le cache HTTP réutilise une réponse selon fraîcheur, variantes et règles HTTP ; un proxy peut éviter PHP. Le cache applicatif évite un calcul ciblé, pas automatiquement le contrôleur. Une revalidation peut rappeler l’application. On copie des données, pas une assiette consommable.

🧠 Comment le mémoriser : « Réponse entière ou résultat interne ? » Image : copie à l’accueil, note en cuisine. Réflexe : « Quel code ce cache permet-il réellement d’éviter ? »

⚠️ À ne pas confondre : entrée présente et réponse réutilisable pour ce client.

Comparer cache HTTP et cache applicatif.

Vérifier puis bifurquer

Testez le catalogue seul, puis le câblage, puis le statut et le contenu du GET. KernelBrowser n’est pas un serveur web ni un navigateur JavaScript : ce test ne prouve pas l’exécution native de l’entrée Runtime.

🌍 In Real Life

La situation : avant l’ouverture, on vérifie séparément le catalogue, les raccordements et une commande simulée.

L’équivalent dans Symfony : catalogue isolé → test unitaire d’ArticleCatalog ; postes raccordés → test d’intégration avec KernelTestCase ; demande simulée → test fonctionnel avec WebTestCase/KernelBrowser.

Retour à la réalité technique : chaque test exerce un périmètre différent. KernelBrowser traite la demande dans l’application sans navigateur JavaScript ni véritable serveur web ; il ne démontre pas le démarrage par public/index.php et Runtime.

🧠 Comment le mémoriser : « Une répétition prouve ce qu’elle fait jouer. » Image : salle d’essai, porte extérieure non testée. Réflexe : « Quelle couche ce test traverse-t-il vraiment ? »

⚠️ À ne pas confondre : statut HTTP vérifié et parcours réseau/JavaScript vérifié.

Tests fonctionnels.

Quand le lecteur s’inscrit, Form transforme la saisie et Validator vérifie des contraintes selon l’intégration configurée ; aucune sauvegarde n’est implicite. Quand un rédacteur importe un fichier, Console utilise les services du même blog sans cycle HTTP obligatoire. Messenger peut ensuite différer le travail avec routage, transport et worker appropriés ; dispatch() ne signifie pas toujours « asynchrone ». Choisissez votre branche.

🌍 In Real Life

La situation : le même restaurant inscrit des clients et importe son catalogue ; ces tâches ne sont pas toutes des commandes à servir.

L’équivalent dans Symfony : fiche d’inscription transformée → Form ; règles vérifiées → Validator ; import lancé par le personnel → Console ; travail transmis maintenant ou différé → Messenger selon configuration.

Retour à la réalité technique : Form lie et transforme les données ; Validator produit des violations, sans sauvegarde implicite. Console exécute une commande sans cycle HTTP imposé. Messenger peut appeler un handler immédiatement ; un traitement différé exige transport approprié, routage et worker.

🧠 Comment le mémoriser : « Même établissement, plusieurs entrées. » Image : accueil, bureau d’import, bac de tâches. Réflexe : « Quelle entrée et quel mode d’exécution sont configurés ? »

⚠️ À ne pas confondre : message accepté et travail terminé ; sync:// reste synchrone.
