D'où viennent les services intégrés

À comprendre

À retenir en priorité
  1. La bibliothèque fournit la class.
  2. Le bundle fournit son intégration au service container.

C'est quoi ?

Un service intégré est un objet configuré par l'intégration Symfony d'une bibliothèque. Installer une bibliothèque rend ses classes chargeables ; cela ne signifie pas que chaque classe devient un service du container. Le bundle, module d'intégration au framework, fournit les définitions et leurs alias de type.

À quoi ça sert ?

Cette séparation explique pourquoi une classe peut exister en PHP tout en étant impossible à autowirer. Avant d'ajouter un new au milieu du code métier, il faut distinguer bibliothèque absente, bundle non activé, fonctionnalité désactivée et type sans alias.

Où dans Symfony ?

FrameworkBundle fournit notamment les intégrations du routage et de RequestStack. TwigBundle fournit l'intégration de Twig. Les fonctionnalités optionnelles dépendent des packages présents et de la configuration ; le nombre exact de services d'un projet n'est pas une constante de Symfony.

Comment, étape par étape ?

  1. Composer rend les classes de la bibliothèque disponibles.
  2. Le kernel active les bundles déclarés pour l'environnement.
  3. Leurs extensions chargent les définitions correspondant aux options activées.
  4. Le container résout les types demandés grâce aux identifiants et alias disponibles.

Exemple concret shell

Ces commandes d'observation supposent une application Symfony avec la console ; elles ne sont pas exécutées dans cette mission.

php bin/console debug:autowiring RequestStack
php bin/console debug:container request_stack

La première aide à trouver le type à écrire au constructeur ; la seconde décrit le service correspondant. Contre-exemple : installer twig/twig puis supposer que Twig\Environment est automatiquement câblé sans TwigBundle ni définition manuelle. Correction : activer l'intégration adaptée, ou déclarer explicitement l'objet si l'on utilise la bibliothèque seule. Une classe autoloadable et un service enregistré sont deux faits différents.

Passage canonique conservé

D'où viennent les services intégrés

  • Chaque bundle apporte les siens : FrameworkBundle (router, dispatcher, RequestStack, cache, filesystem, et serializer, validator, client HTTP quand leurs packages sont là), TwigBundle, SecurityBundle…
  • L'extension du bundle déclare le service et son type : ->alias(RequestStack::class, 'request_stack').
Situation Injectable ?
TwigBundle activé Twig\Environment : oui
twig/twig installé, sans TwigBundle non : « …but no such service exists »
symfony/serializer installé, section par défaut SerializerInterface : oui
framework.serializer.enabled: false non : 89 types au lieu de 98 dans debug:autowiring

C'est le bundle qui fournit le service, pas la bibliothèque ; et une section activable n'enregistre rien tant qu'elle est désactivée.

Trouver le bon type : `debug:autowiring`

À comprendre

À retenir en priorité
  1. La command expose les types configurés.
  2. Elle évite de deviner une class concrète.

C'est quoi ?

debug:autowiring présente les types utilisables pour le câblage automatique. debug:container inspecte les services par identifiant. Un identifiant tel que logger, une classe concrète et une interface PHP peuvent désigner des aspects différents du même service.

À quoi ça sert ?

Le choix de la commande dépend de la question : « quel type demander au constructeur ? » n'est pas « quelle définition est enregistrée ? ». Copier la classe interne affichée dans une inspection peut coupler l'application à une implémentation et ne garantit pas qu'un alias existe sous ce type.

Où dans Symfony ?

La console interroge le container de l'environnement choisi. Un résultat trouvé en développement ne prouve pas qu'un bundle activé seulement en développement sera présent en production. Une classe concrète peut aussi être le bon type public : RequestStack n'a pas besoin d'être remplacé arbitrairement par une interface inventée.

Comment, étape par étape ?

  1. Chercher le rôle voulu avec debug:autowiring.
  2. Lire le type complet et l'alias annoncé.
  3. Inspecter le service avec debug:container si ses arguments ou sa visibilité posent problème.
  4. Demander ce type au constructeur, puis vérifier la configuration de l'environnement réel.

Exemple concret shell

php bin/console debug:autowiring LoggerInterface
php bin/console debug:container logger

Dans une application qui expose un logger sous cette interface, le constructeur demande Psr\Log\LoggerInterface. Le nom de la classe concrète peut varier selon les bundles installés. Contre-exemple : typer le constructeur avec la classe interne d'un logger seulement parce qu'elle apparaît dans debug:container. Correction : utiliser le type aliasé annoncé par debug:autowiring, puis choisir un alias nommé si plusieurs usages sont proposés. Ces commandes sont des observations à effectuer dans le projet cible, pas des sorties universelles promises ici.

Passage canonique conservé

Trouver le bon type : debug:autowiring

Écriture Résultat
debug:autowiring les types utilisables comme type-hint
debug:autowiring log ceux qui contiennent « log » : Psr\Log\LoggerInterface - alias:logger
debug:autowiring zzzz « No autowirable classes or interfaces found », exit code 1
debug:autowiring RedirectController --all ajoute les services sans alias de type
  • debug:container répond à « quels services existent ? » (logger, twig…) ; debug:autowiring, à « quel type écrire ? ».
  • On injecte le type aliasé, pas la class du service : un argument typé Symfony\Component\HttpKernel\Log\Logger échoue, « Try changing the type-hint to "Psr\Log\LoggerInterface" instead ».
  • Souvent une interface, pas toujours : RequestStack, Filesystem et Twig\Environment sont des classes aliasées.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'alias peut viser une class.
  2. Le contrat n'est pas nécessairement une interface PHP.
  • Voir l’explication : debug:container et debug:autowiring ne répondent pas à la même question.

    debug:container et debug:autowiring ne répondent pas à la même question. Le premier liste tous les identifiers du container, le second les types utilisables comme type-hint. Apparaître dans debug:container ne rend pas un service injectable par son type : logger y figure, sa class concrète ne s'injecte pas.

  • Voir l’explication : On type-hinte le type aliasé, pas la class du service.

    On type-hinte le type aliasé, pas la class du service. Viser la class concrète de logger échoue ; LoggerInterface fonctionne.

  • Voir l’explication : « Toujours une interface » est faux

    « Toujours une interface » est faux : RequestStack ou Filesystem s'injectent par leur class, parce que c'est elle que le bundle a aliasée.

  • Voir l’explication : Un service intégré vient d'un bundle, pas du framework en bloc.

    Un service intégré vient d'un bundle, pas du framework en bloc. Retirer le bundle retire ses services : sans TwigBundle, pas d'Environment à injecter.

  • Voir l’explication : Une section désactivée n'enregistre aucun service.

    Une section désactivée n'enregistre aucun service. Avec framework.serializer.enabled: false, SerializerInterface n'est plus injectable, même si symfony/serializer est installé.

Fiche express

À mémoriser

À retenir en priorité
  1. Installation et activation sont distinctes.
  2. La configuration décide des services enregistrés.

Si tu dois retenir seulement 6 choses :

  • Un service intégré vient d'un bundle, activé par sa recipe.
  • Sans le bundle, ou section désactivée : pas de service.
  • debug:autowiring : quel type écrire ; debug:container : quels services existent.
  • On injecte le type aliasé, pas la class du service.
  • Interface le plus souvent ; RequestStack, Filesystem : des classes.
  • --all : les services sans alias de type.

Moyen mnémotechnique : « container = QUI existe, autowiring = QUOI écrire ».
