Objectif

Savoir d'où viennent les services que l'on n'a jamais déclarés, pourquoi l'un d'eux peut manquer, et trouver le type à écrire dans un constructor avec la bonne command, sans apprendre de liste par cœur.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Les bundles enregistrent les services.
  2. Une fonctionnalité désactivée peut retirer ses aliases.

Les services que tu n'as jamais déclarés viennent des bundles installés — FrameworkBundle d'abord —, chacun avec le type sous lequel il s'injecte. Pas de liste à apprendre : debug:autowiring dit quel type écrire. Un service manque si son bundle est absent ou sa section désactivée.

Le schéma

À retenir en priorité
  1. Le type doit correspondre à un service ou alias.
  2. La présence d'une bibliothèque seule ne suffit pas.

D'où viennent les services intégrés

À retenir en priorité
  1. La bibliothèque fournit la class.
  2. Le bundle fournit son intégration au service container.
  • Chaque bundle apporte les siens : FrameworkBundle (router, dispatcher, RequestStack, cache, filesystem, et serializer, validator, client HTTP quand leurs packages sont là), TwigBundle, SecurityBundle…
  • L'extension du bundle déclare le service et son type : ->alias(RequestStack::class, 'request_stack').
Situation Injectable ?
TwigBundle activé Twig\Environment : oui
twig/twig installé, sans TwigBundle non : « …but no such service exists »
symfony/serializer installé, section par défaut SerializerInterface : oui
framework.serializer.enabled: false non : 89 types au lieu de 98 dans debug:autowiring

C'est le bundle qui fournit le service, pas la bibliothèque ; et une section activable n'enregistre rien tant qu'elle est désactivée.

Trouver le bon type : `debug:autowiring`

À retenir en priorité
  1. La command expose les types configurés.
  2. Elle évite de deviner une class concrète.
Écriture Résultat
debug:autowiring les types utilisables comme type-hint
debug:autowiring log ceux qui contiennent « log » : Psr\Log\LoggerInterface - alias:logger
debug:autowiring zzzz « No autowirable classes or interfaces found », exit code 1
debug:autowiring RedirectController --all ajoute les services sans alias de type
  • debug:container répond à « quels services existent ? » (logger, twig…) ; debug:autowiring, à « quel type écrire ? ».
  • On injecte le type aliasé, pas la class du service : un argument typé Symfony\Component\HttpKernel\Log\Logger échoue, « Try changing the type-hint to "Psr\Log\LoggerInterface" instead ».
  • Souvent une interface, pas toujours : RequestStack, Filesystem et Twig\Environment sont des classes aliasées.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. L'alias peut viser une class.
  2. Le contrat n'est pas nécessairement une interface PHP.

debug:container et debug:autowiring ne répondent pas à la même question. Le premier liste tous les identifiers du container, le second les types utilisables comme type-hint. Apparaître dans debug:container ne rend pas un service injectable par son type : logger y figure, sa class concrète ne s'injecte pas.

On type-hinte le type aliasé, pas la class du service. Viser la class concrète de logger échoue ; LoggerInterface fonctionne.

« Toujours une interface » est faux : RequestStack ou Filesystem s'injectent par leur class, parce que c'est elle que le bundle a aliasée.

Un service intégré vient d'un bundle, pas du framework en bloc. Retirer le bundle retire ses services : sans TwigBundle, pas d'Environment à injecter.

Une section désactivée n'enregistre aucun service. Avec framework.serializer.enabled: false, SerializerInterface n'est plus injectable, même si symfony/serializer est installé.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Installation et activation sont distinctes.
  2. La configuration décide des services enregistrés.

Si tu dois retenir seulement 6 choses :

  • Un service intégré vient d'un bundle, activé par sa recipe.
  • Sans le bundle, ou section désactivée : pas de service.
  • debug:autowiring : quel type écrire ; debug:container : quels services existent.
  • On injecte le type aliasé, pas la class du service.
  • Interface le plus souvent ; RequestStack, Filesystem : des classes.
  • --all : les services sans alias de type.

Moyen mnémotechnique : « container = QUI existe, autowiring = QUOI écrire ».
