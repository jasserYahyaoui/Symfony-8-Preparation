Objectif

Savoir d'où viennent les services que l'on n'a jamais déclarés, pourquoi l'un d'eux peut manquer, et trouver le type à écrire dans un constructor avec la bonne command, sans apprendre de liste par cœur.

L'essentiel

À comprendre

À retenir en priorité
  1. Les bundles enregistrent les services.
  2. Une fonctionnalité désactivée peut retirer ses aliases.

Les services que tu n'as jamais déclarés viennent des bundles installés — FrameworkBundle d'abord —, chacun avec le type sous lequel il s'injecte. Pas de liste à apprendre : debug:autowiring dit quel type écrire. Un service peut manquer si son bundle est absent ou sa section désactivée : cela décrit l'enregistrement automatique, sans exclure des définitions ou alias applicatifs.

Le schéma

À retenir en priorité
  1. Le type doit correspondre à un service ou alias.
  2. La présence d'une bibliothèque seule ne suffit pas.

Orange : enregistrement et alias ; bleu : inspection ; vert : injection obtenue. La commande observe le container, elle ne crée pas l'alias. Sans TwigBundle, installer twig/twig apporte les classes mais pas cette configuration automatique ; une déclaration manuelle reste possible.

Le fil rouge : un `InvoiceMailer`

À retenir en priorité
  1. Le service configuré est injecté.
  2. Le consommateur n'assemble pas son infrastructure.
class InvoiceMailer

    public function __construct(
        private LoggerInterface $logger,              // Psr\Log\LoggerInterface
        private UrlGeneratorInterface $urls,          // Symfony\Component\Routing\Generator\…
        private Environment $twig,                    // Twig\Environment
    ) {
    }
}

D'où viennent les services intégrés

À retenir en priorité
  1. La bibliothèque fournit la class.
  2. Le bundle fournit son intégration au service container.
  • Chaque bundle apporte les siens : FrameworkBundle (router, dispatcher, RequestStack, cache, filesystem, et serializer, validator, client HTTP quand leurs packages sont là), TwigBundle, SecurityBundle…
  • L'extension du bundle déclare le service et son type : ->alias(RequestStack::class, 'request_stack').
Situation Injectable ?
TwigBundle activé Twig\Environment : oui
twig/twig installé, sans TwigBundle pas d'enregistrement automatique par ce bundle ; une définition applicative peut fournir Twig\Environment
symfony/serializer installé, section par défaut SerializerInterface : oui
framework.serializer.enabled: false pas d'alias fourni par cette section ; une déclaration applicative reste possible

Dans l'intégration automatique, c'est le bundle qui fournit le service, pas la simple installation de la bibliothèque. Une section désactivée ne fournit pas ses définitions ; cela n'interdit pas de déclarer les siennes.

Trouver le bon type : `debug:autowiring`

À retenir en priorité
  1. La command expose les types configurés.
  2. Elle évite de deviner une class concrète.

Un identifiant comme logger, une classe concrète et une interface PHP peuvent désigner des aspects différents du même service. Chercher le rôle avec debug:autowiring, puis inspecter sa définition si nécessaire :

php bin/console debug:autowiring LoggerInterface
php bin/console debug:container logger

Ces commandes observent le container de l'environnement choisi : un bundle activé seulement en développement ne promet rien en production. Copier une classe interne vue dans debug:container ne garantit pas sa disponibilité comme type injectable. Demander le type annoncé et vérifier la configuration ; si plusieurs usages existent, choisir l'alias approprié. Une classe publique comme RequestStack peut être le bon contrat, sans inventer une interface.

Écriture Résultat
debug:autowiring les types utilisables comme type-hint
debug:autowiring log ceux qui contiennent « log » : Psr\Log\LoggerInterface - alias:logger
debug:autowiring zzzz « No autowirable classes or interfaces found », exit code 1
debug:autowiring RedirectController --all ajoute les services sans alias de type
  • debug:container répond à « quels services existent ? » (logger, twig…) ; debug:autowiring, à « quel type écrire ? ».
  • Dans le câblage fourni par défaut, demander le type aliasé : Psr\Log\LoggerInterface. Demander Symfony\Component\HttpKernel\Log\Logger sans définition ni alias pour ce type peut échouer avec « Try changing the type-hint to "Psr\Log\LoggerInterface" instead ». Une définition applicative sous le nom de cette classe permet son injection.
  • Souvent une interface, pas toujours : RequestStack, Filesystem et Twig\Environment sont des classes aliasées.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'alias peut viser une class.
  2. Le contrat n'est pas nécessairement une interface PHP.
  • Voir l’explication : debug:container et debug:autowiring ne répondent pas à la même question.

    debug:container et debug:autowiring ne répondent pas à la même question. Le premier liste tous les identifiers du container, le second les types utilisables comme type-hint. Apparaître dans debug:container ne rend pas un service injectable par son type : logger y figure, sa class concrète n'est pas nécessairement enregistrée sous son nom de type.

  • Voir l’explication : Le câblage par défaut privilégie le type aliasé.

    Le câblage par défaut privilégie le type aliasé. Sans définition ou alias supplémentaire, viser la classe concrète de logger peut échouer ; LoggerInterface est le contrat fourni. Une configuration applicative peut enregistrer la classe concrète et permettre son autowiring.

  • Voir l’explication : « Toujours une interface » est faux

    « Toujours une interface » est faux : RequestStack ou Filesystem s'injectent par leur class, parce que c'est elle que le bundle a aliasée.

  • Voir l’explication : Un service intégré vient d'un bundle, pas du framework en bloc.

    Un service intégré vient d'un bundle, pas du framework en bloc. Retirer le bundle retire son enregistrement automatique : sans TwigBundle, une définition applicative peut néanmoins fournir Twig\Environment.

  • Voir l’explication : Une section désactivée n'enregistre aucun service.

    Une section désactivée n'enregistre aucun service. Avec framework.serializer.enabled: false, la section ne fournit plus son câblage de SerializerInterface. Une définition ou un alias applicatif distinct peut toutefois rendre ce contrat injectable.

Fiche express

À mémoriser

À retenir en priorité
  1. Installation et activation sont distinctes.
  2. La configuration décide des services enregistrés.

Si tu dois retenir seulement 6 choses :

  • Un service intégré vient d'un bundle, activé par sa recipe.
  • Sans intégration du bundle, ou section désactivée : pas d'enregistrement automatique correspondant ; ne pas confondre avec l'impossibilité de le déclarer.
  • debug:autowiring : quel type écrire ; debug:container : quels services existent.
  • On injecte le type aliasé, pas la class du service.
  • Interface le plus souvent ; RequestStack, Filesystem : des classes.
  • --all : les services sans alias de type.

Moyen mnémotechnique : « container = QUI existe, autowiring = QUOI écrire ».
