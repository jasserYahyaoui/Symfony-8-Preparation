Objectif

Générer une URL depuis une route, et maîtriser ce qui arrive aux parameters qui ne font pas partie de la route.

L'essentiel

À comprendre

À retenir en priorité
  1. Un service injecte UrlGeneratorInterface.
  2. Le controller dispose aussi de generateUrl().

Une URL se génère toujours depuis une route : generateUrl() dans un controller, generate() d'UrlGeneratorInterface dans un service, path() et url() en Twig. Le troisième argument choisit la forme — path absolu par défaut. Un parameter absent de la route part en query string, sans erreur ; un object y est converti, contrairement à ce que dit la documentation.

Le schéma

L'exemple

Exemple concret

$this->generateUrl('blog', ['page' => 2, 'category' => 'Symfony']);
// la route blog ne définit que page → /blog/2?category=Symfony

$this->generateUrl('blog', ['page' => 2], UrlGeneratorInterface::ABSOLUTE_URL);
// lien pour un email → https://example.com/blog/2

Où et comment

À comprendre

C'est quoi ?

Générer une URL signifie demander une adresse au router à partir d'un nom de route et de paramètres. Controller, service et template sont trois lieux d'appel d'un même contrat, pas trois catalogues d'URL indépendants.

À quoi ça sert ?

Les liens vers les routes de l'application suivent les modifications de leur path et les règles d'encodage. Une adresse externe fixe n'a pas forcément de route locale : la recommandation de génération concerne les destinations réellement routées.

Où dans Symfony ?

AbstractController fournit generateUrl. Un service injecte UrlGeneratorInterface et appelle generate. Twig utilise path pour demander un chemin et url pour une adresse complète, via son extension de routage.

Comment, étape par étape ?

  1. Identifier le nom exact de la route.
  2. Fournir les paramètres exigés avec leurs noms.
  3. Choisir le point d'accès adapté à l'appelant.
  4. Tester un changement de path sans changer les appels ; contrôler aussi le contexte hors HTTP.

Exemple concret PHP et Twig

Fonction utilisable depuis un service recevant le générateur ; la route article_show possède le path /articles/{slug} :

<?php
use Symfony\Component\Routing\Generator\UrlGeneratorInterface;
function articlePath(UrlGeneratorInterface $generator): string
{
    return $generator->generate('article_show', ['slug' => 'guide']);
}

Dans AbstractController, l'appel équivalent est $this->generateUrl('article_show', ['slug' => 'guide']). Dans un template équipé de l'extension :

<a href="{{ path('article_show', {slug: 'guide'}) }}">Lire le guide</a>

Contre-exemple : copier /articles/guide dans chaque appelant puis modifier le path en /guides/{slug}. Les copies restent anciennes. Correction : conserver le nom article_show et laisser le générateur produire le nouveau chemin. Un nom inconnu ou un paramètre obligatoire absent reste une erreur à traiter, pas une URL vide supposée valide.

Passage canonique conservé

Où et comment

Contexte Appel
controller (AbstractController) $this->generateUrl('nom', [...])
service injecter UrlGeneratorInterface, appeler generate()
template Twig path('nom', {...}) et url('nom', {...})

On ne construit jamais une URL à la main : changer le path d'une route met alors à jour tous les liens.

Le route name joue le rôle d'un contact téléphonique : changer son numéro une fois met à jour les appels futurs. Recopier le path partout revient à mémoriser des numéros qui deviendront périmés.

Les quatre types de référence

À comprendre

À retenir en priorité
  1. Le défaut produit un path absolu.
  2. Un lien complet pour un email exige ABSOLUTE_URL.

C'est quoi ?

Le type de référence décrit la forme de l'adresse générée : URL complète, chemin absolu dans le site, chemin relatif au contexte courant, ou référence réseau sans schéma explicite. Ce choix ne modifie pas le nom de la route.

À quoi ça sert ?

Un lien dans un courriel doit généralement être utilisable hors de la page actuelle ; un chemin relatif n'y décrit pas la même destination. À l'inverse, une navigation interne n'exige pas systématiquement de répéter le host et le schéma.

Où dans Symfony ?

UrlGeneratorInterface définit ABSOLUTE_URL, ABSOLUTE_PATH, RELATIVE_PATH et NETWORK_PATH. Le défaut de generate est ABSOLUTE_PATH, même si sa valeur numérique est 1 et celle d'ABSOLUTE_URL 0. Dans un service, injecter cette interface ; AbstractController et les fonctions Twig sont des accès pratiques au même mécanisme.

Comment, étape par étape ?

  1. Identifier le nom de route et fournir ses paramètres obligatoires.
  2. Choisir la forme d'adresse selon le consommateur.
  3. Fournir un contexte de host, schéma et chemin approprié, surtout hors d'une Request HTTP.
  4. Vérifier les contraintes propres à la route : un host ou un schéma différent peut obliger le générateur à produire une URL complète même lorsqu'un chemin a été demandé.

Exemple concret PHP

Fonction recevant un générateur configuré ; la route article_show attend slug :

<?php
use Symfony\Component\Routing\Generator\UrlGeneratorInterface;

function articleLink(UrlGeneratorInterface $generator, string $slug): string
{
    return $generator->generate('article_show', ['slug' => $slug], UrlGeneratorInterface::ABSOLUTE_URL);
}

Avec un contexte HTTPS example.test et le chemin /articles/{slug}, introduction produit https://example.test/articles/introduction. Contre-exemple : utiliser la constante 0 en croyant demander la forme par défaut. Correction : nommer la constante, qui exprime l'intention.

Les paramètres supplémentaires deviennent généralement une query string, sauf ceux égaux à un défaut ; le tableau réservé _query prend la priorité sur les paramètres supplémentaires homonymes. Pour une route éventuellement absente, traiter précisément RouteNotFoundException lors de generate plutôt que charger toute la collection dans chaque appel. Une URL générée n'est pas la preuve que toute condition de matching sera vraie lors de la visite.

Passage canonique conservé

Les quatre types de référence

Les constants sont sur UrlGeneratorInterface : ABSOLUTE_URL vaut 0, ABSOLUTE_PATH vaut 1 et c'est le défaut, RELATIVE_PATH vaut 2, NETWORK_PATH vaut 3. La constant qui vaut 0 n'est donc pas le défaut. NETWORK_PATH reprend le schéma courant ; RELATIVE_PATH est relatif au path courant.

Les parameters en trop

À comprendre

À retenir en priorité
  1. Une key inconnue du path peut devenir un parameter de query string.
  2. _query explicite prime sur les extras de même nom.

C'est quoi ?

Un paramètre supplémentaire n'est pas consommé par les variables de la route. Le générateur peut le placer dans la query string, après le point d'interrogation, plutôt que rejeter tout paramètre inconnu.

À quoi ça sert ?

On peut ajouter un tri ou un filtre sans modifier le path de la route. Ce comportement impose de transmettre seulement les données voulues : une faute de nom peut créer un paramètre query au lieu de remplir la variable attendue.

Où dans Symfony ?

Un paramètre supplémentaire égal au défaut homonyme peut être omis. _query fournit explicitement un tableau de query string et ses valeurs l'emportent sur les paramètres supplémentaires homonymes. _query doit être un tableau ; une chaîne n'est pas interprétée comme une query déjà encodée.

Comment, étape par étape ?

  1. Séparer paramètres du path et paramètres query.
  2. Vérifier les noms exigés par la route.
  3. Passer les paramètres supplémentaires, ou les regrouper sous _query.
  4. Lire l'URL produite pour détecter les clés involontaires et ne pas y placer de secret.

Exemple concret Twig

La route article_show est /articles/{slug} et n'a pas de défaut pour sort :

{{ path('article_show', {slug: 'guide', sort: 'date', _query: {sort: 'title'}}) }}

Le résultat est /articles/guide?sort=title : slug remplit le path et _query remplace la valeur supplémentaire sort. Contre-exemple : fournir _query: 'sort=title' ou remplacer slug par articleSlug. Correction : fournir un tableau pour _query et le nom slug attendu ; sinon le paramètre obligatoire manque, même si une clé ressemblante existe. La query générée n'effectue aucune validation métier du tri demandé.

Passage canonique conservé

Les parameters en trop

Un parameter absent de la definition de la route part en query string. Deux nuances : un parameter en trop égal à la default value de même nom est retiré ; la key réservée _query fournit un array de parameters qui l'emportent sur les parameters en trop de même nom — une valeur qui n'est pas un array lève une InvalidParameterException.

Repère — Les objects en parameter supplémentaire : Public properties are used first; otherwise a Stringable object can be converted to a string. Les properties publiques ont priorité. La conversion Stringable concerne les objects sans properties publiques.

Les objects en parameter supplémentaire

À retenir en priorité
  1. Les properties publiques ont priorité.
  2. La conversion Stringable concerne les objects sans properties publiques.

Pour un object supplémentaire, le generator utilise d'abord les properties publiques comme array ; à défaut, un object Stringable peut être converti en string. Une référence circulaire lève. Cette règle décrit la conversion générique, sans introduire de type d'identifier externe.

Route absente

À comprendre

À retenir en priorité
  1. Ne pas charger toute la RouteCollection pour ce simple test.
  2. Traiter explicitement RouteNotFoundException.

C'est quoi ?

RouteNotFoundException signale que le générateur ne connaît pas la route demandée. Ce cas diffère d'une route connue dont un paramètre manque ou ne satisfait pas un requirement.

À quoi ça sert ?

Un lien facultatif vers une fonctionnalité peut avoir un repli explicite lorsque sa route n'est pas installée. Une route obligatoire absente doit plutôt rester une erreur de configuration visible ; masquer toutes les erreurs de génération rendrait le diagnostic difficile.

Où dans Symfony ?

La recommandation est d'essayer generate et de traiter précisément RouteNotFoundException. Charger toute la collection avec getRouteCollection seulement pour tester un nom peut déclencher le chargement ou la reconstruction des données de routage ; ce n'est pas le chemin de diagnostic à répéter pour chaque lien.

Comment, étape par étape ?

  1. Décider si l'absence est réellement prévue.
  2. Tenter la génération avec les paramètres corrects.
  3. Capturer uniquement l'exception correspondant à cette absence.
  4. Fournir un repli défini ou laisser remonter l'erreur si le lien est obligatoire.

Exemple concret PHP

La route help est facultative ; homepage est obligatoire et ne demande aucun paramètre :

<?php
use Symfony\Component\Routing\Exception\RouteNotFoundException;
use Symfony\Component\Routing\Generator\UrlGeneratorInterface;
function helpOrHome(UrlGeneratorInterface $generator): string
{
    try {
        return $generator->generate('help');
    } catch (RouteNotFoundException) {
        return $generator->generate('homepage');
    }
}

Contre-exemple : capturer toute Throwable et retourner une chaîne vide, même en cas d'erreur de paramètre ou de configuration. Correction : limiter le repli au cas prévu ; l'échec du lien obligatoire de remplacement doit rester visible. Cette technique teste la génération, pas la disponibilité métier du contenu visé.

Passage canonique conservé

Route absente

Ne pas appeler getRouteCollection() pour tester l'existence d'une route : cela régénère le cache de routage. Tenter la génération et rattraper RouteNotFoundException.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un parameter absent de la route n'est pas ignoré : il part en query string.

    Un parameter absent de la route n'est pas ignoré : il part en query string. Une faute de frappe dans un nom de parameter ne produit donc aucune erreur — juste une URL avec un parameter en trop.

  • Voir l’explication : Un object en parameter supplémentaire est converti, selon le code 8.0.

    Un object en parameter supplémentaire est converti, selon le code 8.0. Les properties publiques d'abord, en array ; __toString() seulement s'il n'en a pas. La documentation dit toujours le contraire.

  • Valeurs par défaut et query string

    Un parameter en trop égal au défaut disparaît de la query string.

  • Voir l’explication : Le type de référence par défaut est le path absolu, pas l'URL absolue.

    Le type de référence par défaut est le path absolu, pas l'URL absolue. Générer un lien pour un email demande de le dire explicitement.

Application

À retenir en priorité

  2. Un lien complet pour un email exige ABSOLUTE_URL.

  4. Le controller dispose aussi de generateUrl().

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Jamais d'URL à la main : generateUrl(), generate(), path(), url().
  • Défaut : ABSOLUTE_PATH (1) ; ABSOLUTE_URL vaut 0.
  • Parameter hors route → query string, sans erreur.
  • Égal au défaut → retiré ; _query : un array, prioritaire.
  • Object en trop : properties publiques → array, sinon Stringable → string.
  • Route absente : rattraper RouteNotFoundException.

Moyen mnémotechnique : « Zéro, c'est tout : l'URL complète ».
