Objectif

Récupérer un file téléversé, le déplacer, et savoir quelles informations ne doivent jamais être crues.

L'essentiel

○ À comprendre

À retenir en priorité
  1. UploadedFile enveloppe le file temporaire.
  2. Le resolver utilise name ou le nom de l'argument.

Un file téléversé arrive en UploadedFile, par le sac files ou par #[MapUploadedFile]. Il vit dans un file temporaire que PHP supprime en fin de Request : seul move() le conserve. Et tout ce que le client annonce — nom, extension, path, type MIME — est une entrée, pas un fait : le nom stocké se génère, l'extension se devine du contenu.

Le schéma

L'exemple : un nom sûr

▣ Exemple concret

À retenir en priorité
  1. Le nom annoncé par le client n'est pas un path de stockage fiable.
  2. Générer le nom côté serveur et valider le file avant move() ; guessExtension() ne suffit pas à valider le contenu.
use Symfony\Component\HttpFoundation\File\UploadedFile;

function storeUpload(UploadedFile $upload, string $directory): string
{
    $extension = $upload->guessExtension();
    if (null === $extension) {
        throw new \RuntimeException('Cannot determine the file extension.');
    }
    $name = bin2hex(random_bytes(16)).'.'.$extension;
    $upload->move($directory, $name);

    return $name;
}

Après validation des contraintes du file, choisir un nom côté serveur et un directory non exécutable. Le nom annoncé par le client n'est pas utilisé comme path. La détection d'extension ne remplace pas la validation du contenu.

Le récupérer

○ À comprendre

C'est quoi ?

Le sac files contient les fichiers de la requête, sous forme d'UploadedFile ou de structures imbriquées. MapUploadedFile est un attribute d'argument qui demande au resolver de fournir le fichier correspondant. Le body texte et le sac de paramètres ordinaires ne sont pas ce sac de fichiers.

À quoi ça sert ?

La lecture directe convient lorsque l'action veut contrôler explicitement la structure reçue. L'attribute exprime le contrat dans la signature et peut porter des contraintes ; le caractère obligatoire ou facultatif doit être choisi volontairement.

Où dans Symfony ?

Le resolver lit la clé name de l'attribute, sinon le nom de l'argument. Sans fichier, un argument nullable ou doté d'un défaut peut recevoir null ou son défaut ; un argument array reçoit une liste vide. Un fichier obligatoire absent produit par défaut une réponse 422 via le traitement d'exception.

Comment, étape par étape ?

  1. Connaître le nom du champ multipart envoyé.
  2. Le faire correspondre à l'argument, ou préciser name.
  3. Gérer explicitement le cas absent si le contrat le permet.
  4. Valider le fichier avant stockage ; le simple fait de recevoir un UploadedFile ne prouve pas qu'il convient à l'application.

Exemple concret PHP

Action enregistrée avec les resolvers habituels de FrameworkBundle :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function inspect(#[\Symfony\Component\HttpKernel\Attribute\MapUploadedFile(name: 'brochure')] ?\Symfony\Component\HttpFoundation\File\UploadedFile $file = null): \Symfony\Component\HttpFoundation\JsonResponse
{
    return new \Symfony\Component\HttpFoundation\JsonResponse(['received' => null !== $file]);
}

L'exemple signale seulement la présence ; il ne stocke ni ne certifie le contenu. Contre-exemple : renommer l'argument sans name puis continuer à envoyer brochure. Le resolver cherche une autre clé. Correction : aligner les noms ou préciser name comme ci-dessus. Pour une lecture manuelle, $request->files->get('brochure') doit également être contrôlé avant utilisation.

Passage canonique conservé

Le récupérer

Deux paths, un même résultat : $request->files->get('brochure'), ou un argument portant #[MapUploadedFile]. On obtient un UploadedFile, sous-classe de File qui enveloppe le file temporaire.

Le resolver lit $request->files sous l'option name de l'attribute, à défaut sous le nom de l'argument. Quand rien n'est envoyé, un argument nullable ou doté d'une default value reçoit null ou ce défaut, un argument array un array vide, tout autre une HttpException 422. Ce 422 est la default value de validationFailedStatusCode, qui sert aussi quand les constraints de l'attribute échouent ; sur un array, elles s'appliquent à chaque file.

Le déplacer

À retenir en priorité
  1. move() vérifie l'upload avant déplacement.
  2. Le file temporaire ne doit pas être considéré comme persistant.

move($directory, $name) retourne un File à la nouvelle place. Elle vérifie d'abord isValid() — envoi sans erreur et file arrivé par HTTP —, sinon elle lève une exception par code d'erreur : IniSizeFileException pour la limite de php.ini, FormSizeFileException pour celle du form, PartialFileException, NoFileException, etc.

Ce qui vient du client n'est pas fiable

△ Piège à éviter

À retenir en priorité
  1. Les métadonnées annoncées par le client ne font pas autorité.
  2. guessClientExtension() diffère de guessExtension().

C'est quoi ?

UploadedFile représente un fichier temporaire reçu. Il expose à la fois des informations annoncées par le client et des mesures ou déductions effectuées côté serveur. Ces catégories n'ont pas la même valeur de preuve : un nom finissant par pdf ne démontre pas que le contenu est un PDF acceptable.

À quoi ça sert ?

Le serveur doit décider indépendamment du nom envoyé ce qu'il accepte et où il stocke le contenu. Une extension devinée à partir du type détecté est plus pertinente qu'une extension client, mais ne constitue pas un contrôle exhaustif d'innocuité du fichier.

Où dans Symfony ?

getClientOriginalName, getClientOriginalExtension, getClientOriginalPath, getClientMimeType et guessClientExtension partent des indications du client. getMimeType et guessExtension inspectent le contenu avec les outils de détection ; leur résultat peut être inconnu. getSize() mesure le fichier temporaire via SplFileInfo, pas une taille déclarée dans un champ client.

Comment, étape par étape ?

  1. Récupérer le fichier dans Request.files ou avec MapUploadedFile.
  2. Vérifier la réussite de l'envoi et appliquer les contraintes de taille et de type adaptées.
  3. Choisir un répertoire de confiance et un nom généré par le serveur.
  4. Déplacer le fichier avec move ; gérer explicitement les exceptions de stockage. Ne pas garder uniquement son chemin temporaire, dont la durée de vie est liée à la requête.

Exemple concret PHP

Cette fonction illustre uniquement le stockage d'un fichier déjà validé, dans un répertoire configuré non exécutable. Elle nécessite HttpFoundation et les dépendances de détection MIME :

<?php
use Symfony\Component\HttpFoundation\File\File;
use Symfony\Component\HttpFoundation\File\UploadedFile;

function storeValidatedPdf(UploadedFile $upload, string $directory): File
{
    if (!$upload->isValid() || 'pdf' !== $upload->guessExtension()) {
        throw new \InvalidArgumentException('Fichier PDF valide requis.');
    }

    return $upload->move($directory, bin2hex(random_bytes(16)).'.pdf');
}

Le nom ne dépend pas d'un chemin fourni par l'utilisateur ; move retourne le File situé au nouvel emplacement. Contre-exemple : choisir le nom de destination avec getClientOriginalPath, ou considérer guessExtension comme une validation métier complète. Correction : nom serveur, contraintes adaptées avant déplacement, stockage non exécutable et politique d'accès explicite. Une erreur disque ne doit pas être présentée comme une réussite.

Passage canonique conservé

Ce qui vient du client n'est pas fiable

Le code marque ces methods comme non sûres : getClientOriginalName(), getClientOriginalExtension(), getClientOriginalPath() — identique au nom sauf envoi d'un dossier —, getClientMimeType(), et guessClientExtension(), qui part du type annoncé bien que son nom ne commence pas par getClient.

Les methods fiables partent du contenu : getMimeType() et guessExtension().

getSize() : la documentation la range parmi les valeurs non sûres. Le code la mesure : elle vient de \SplFileInfo et rend la taille du file temporaire reçu, pas une valeur déclarée. Retenir les deux.

L'étiquette d'un colis décrit ce que l'expéditeur affirme ; inspecter son contenu est une autre opération. Le nom et le MIME annoncés ne remplacent ni validation du file ni nom choisi côté serveur.

Repère de l’exemple : The client filename is untrusted; a server-generated name avoids treating it as a storage path. Le nom annoncé par le client n'est pas un path de stockage fiable. Générer le nom côté serveur et valider le file avant move() ; guessExtension() ne suffit pas à valider le contenu.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Rien de ce que le client annonce sur le file n'est fiable.

    Rien de ce que le client annonce sur le file n'est fiable. Nom, extension, path, type MIME annoncé : tout vient du navigateur.

  • Voir l’explication : guessClientExtension() n'est pas guessExtension().

    guessClientExtension() n'est pas guessExtension(). La première part du type annoncé, la seconde du contenu.

  • Voir l’explication : Sans déplacement, il ne reste rien.

    Sans déplacement, il ne reste rien. Le file temporaire disparaît à la fin de la Request.

  • Voir l’explication : Un file manquant donne 422, pas 400.

    Un file manquant donne 422, pas 400. Sauf argument nullable, avec défaut, ou typé array.

  • Voir l’explication : move() lève une exception typée

    move() lève une exception typée selon l'erreur de téléversement.

Application

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • $request->files ou #[MapUploadedFile] (name, sinon nom d'argument).
  • Absent : null, défaut, [] pour un array, sinon 422.
  • Sans move(), rien ne reste ; elle rend un File.
  • move() lève une exception par code d'erreur (IniSizeFileException…).
  • Non fiables : les getClient… et guessClientExtension().
  • Fiables : getMimeType(), guessExtension() ; getSize() mesurée par le code.

Moyen mnémotechnique : « Client annonce, contenu prouve ».
