Objectif

Comprendre ce qu'un firewall délimite, et la règle d'ordre qui décide lequel s'applique.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Les firewalls ne s'empilent pas.
  2. L'ordre est déterminant.

Un firewall découpe les URL en zones qui s'authentifient chacune à sa façon : outils de développement, API sans session, site avec form. Un seul firewall traite une Request : le premier dont le matcher correspond.

Le schéma

À retenir en priorité
  1. La sélection s'arrête au premier match.
  2. L'API doit précéder le catch-all.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le contexte porte le token de session.
  2. Le partage doit être explicite.
security:
    firewalls:
        dev:                                  # outils : aucune security
            pattern: ^/(_profiler|_wdt|assets)/
            security: false
        api:                                  # tokens, sans session
            pattern: ^/api
            stateless: true
        main:                                 # tout le reste, en dernier
            lazy: true

Un seul firewall par Request

À retenir en priorité
  1. Le path est un critère possible.
  2. Le matcher définit la zone réelle.
  • Les firewalls sont essayés dans l'ordre de déclaration ; le premier qui correspond prend la Request, les autres ne sont jamais consultés.
  • Un firewall sans pattern correspond à tout : il se déclare en dernier. Placé en premier, il capte tout, sans erreur.
  • Un firewall peut aussi se choisir par host.
  • methods n'entre dans le matcher qu'avec un pattern ou un host : un firewall qui ne déclare que methods: [POST] attrape aussi les GET.
  • $security->getFirewallConfig($request)->getName() dit quel firewall a traité la Request.

Un firewall décide comment on s'authentifie ; access_control décide ce qu'il faut pour entrer, et c'est le firewall qui l'applique.

Ce qu'un firewall porte

À retenir en priorité
  1. Le firewall assemble l'authentication de sa zone.
  2. Les règles d'accès restent une décision distincte.
  3. switch_user appartient au firewall.
  4. _exit restaure l'identité d'origine ; IS_IMPERSONATOR décrit l'état.
  • ses authenticators, son provider, son entry point, son user checker ;
  • son caractère stateless ou non ;
  • l'AccessListener, qui applique access_control.

Chaque firewall a son propre contexte de session : se connecter sur main ne connecte pas sur admin. Avec context: shared sur les deux, alice connectée sur main est reconnue sur /admin/whoami. Dans un test, le second argument de loginUser() est ce contexte, pas le nom du firewall.

Sans état (stateless: true), aucun cookie n'est posé : la Request suivante sans credentials est anonyme.

L'impersonation se configure sur le firewall avec switch_user. Par défaut, l'autorisation ROLE_ALLOWED_TO_SWITCH permet de demander ?_switch_user=<identifier> ; ?_switch_user=_exit termine l'impersonation. IS_IMPERSONATOR vérifie cet état de connexion : ce n'est pas un role à ajouter au user ciblé.

Documentation Symfony 8.0.

`lazy`

À retenir en priorité
  1. Une page sans accès au user évite ce travail.
  2. Lire le user déclenche la restauration.

lazy: true diffère la lecture du token et le rechargement du user jusqu'à ce que quelque chose les demande : une page qui n'utilise pas le user n'appelle pas le provider ; une page qui le lit l'appelle, à la demande. La documentation ajoute que la session reste fermée, ce qui garde la Response cachable ; exécuté, Cache-Control restait le même dans les deux modes, et l'effet mesuré était l'appel au provider évité.

lazy est ignoré sur un firewall stateless : le contexte est un LazyFirewallContext avec état, un FirewallContext ordinaire sans état.

`security: false`

À retenir en priorité
  1. Ce réglage coupe l'authentication et l'accès.
  2. Il n'est pas équivalent à PUBLIC_ACCESS.

Ce firewall n'a aucun listener : ni authentication, ni AccessListener. Une règle access_control sur ses URL est morte. Réservé aux outils de développement et aux files statiques.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Chaque contexte reste indépendant.
  2. Un context commun est nécessaire pour partager.

Un seul firewall s'applique, le premier qui correspond ; les autres sont ignorés.

Un firewall sans pattern attrape tout et se déclare en dernier.

Deux firewalls n'échangent pas leur authentication sans context commun.

security: false désactive aussi access_control pour ses URL.

lazy épargne le rechargement du user sur les pages qui ne s'en servent pas — et n'a aucun effet sur un firewall stateless.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le token de test doit viser le bon contexte.
  2. Ce n'est pas toujours le nom du firewall.

Si tu dois retenir seulement 7 choses :

  • Un seul firewall par Request : le premier qui correspond.
  • Sans pattern : attrape tout, en dernier.
  • methods seul ne forme pas de matcher.
  • Chaque firewall a sa session ; context commun pour partager.
  • stateless: true : rien n'est gardé.
  • lazy diffère le rechargement du user ; ignoré si stateless.
  • security: false : aucun listener, access_control mort.

Moyen mnémotechnique : « Le premier prend tout, et garde sa session ».

firewalls dans l'ordre, 1er matcher gagne (sans pattern = tout, en dernier ; methods seul = pas de matcher) ;
contexte propre (context: shared) ; stateless = rien gardé ; lazy (ignoré si stateless) ; security: false = rien
