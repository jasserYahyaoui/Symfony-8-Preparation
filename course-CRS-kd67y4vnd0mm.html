Objectif

Savoir ce que Symfony fait d'une exception non rattrapée, et surtout comment il choisit le status code de la Response produite.

L'essentiel

À comprendre

À retenir en priorité
  1. Un statut 200 n'est pas conservé automatiquement lors d'une erreur.
  2. allowCustomResponseCode() autorise explicitement ce choix.

Une exception non rattrapée devient l'event kernel.exception. Un listener peut fournir une Response ou remplacer l'exception ; sinon ErrorListener construit la page d'erreur par une sub-Request. Le statut final suit une règle en trois temps, que l'examen interroge par des Responses 200 ou 204 qui ne sortent pas avec leur statut.

Le schéma

L'exemple : une exception qui porte son statut

Exemple concret

À retenir en priorité
  1. L'attribute associe un status code à cette exception précise.
  2. Ce choix explicite ne signifie pas que tout échec de validation doit produire 422.
use Symfony\Component\HttpKernel\Attribute\WithHttpStatus;

#[WithHttpStatus(422)]
final class InvalidQuantity extends \InvalidArgumentException {}
// levée dans un controller : la Response sort en 422, sans listener maison

Le mécanisme

À comprendre

À retenir en priorité
  1. setThrowable() remplace l'erreur traitée.
  2. setResponse() fournit la Response et arrête la propagation de cet event.

C'est quoi ?

Quand HttpKernel traite une exception dans sa branche de gestion d'erreur, il déclenche kernel.exception. Chaque listener, une fonction abonnée à cet événement, reçoit un ExceptionEvent. Cet objet contient le throwable, l'objet PHP représentant l'échec, et peut recevoir une Response, le résultat HTTP à retourner.

Deux opérations ont des effets différents :

  • setThrowable($exception) remplace l'échec transporté par l'événement. Les listeners suivants peuvent lire ce nouvel objet ; cet appel n'arrête pas la propagation à lui seul.
  • setResponse($response) fournit un résultat HTTP et arrête la propagation de cet événement. Les listeners restants sont sautés. Les effets des listeners déjà exécutés ne sont pas annulés.

À quoi ça sert ?

Remplacer le throwable sert à traduire un échec en un type mieux compris par les traitements suivants. Fournir une Response sert à prendre en charge la présentation HTTP de l'erreur. Il faut réserver cette prise en charge aux échecs que le listener sait réellement traiter : transformer toute erreur en 200 OK masquerait des pannes et annoncerait à tort un succès.

L'ordre détermine aussi si une journalisation a eu lieu. Une priorité plus élevée passe avant une priorité plus faible. L'affirmation « le log a toujours déjà eu lieu quand un listener répond » est donc fausse : elle dépend de la priorité de ce listener. Arrêter la propagation n'est ni annuler un log passé, ni garantir qu'un log futur sera écrit.

Où dans Symfony ?

ExceptionEvent hérite de RequestEvent, dont setResponse() appelle stopPropagation(). EventDispatcher, le component qui appelle les listeners, consulte cet arrêt avant chaque listener restant.

L'ErrorListener de HttpKernel déclare logKernelException à la priorité 0 et onKernelException, chargé de la page d'erreur, à -128. Il déclare aussi des interventions sur kernel.controller_arguments et kernel.response. Cela ne rend pas sa journalisation inconditionnelle : un listener à 100 peut fournir une réponse avant la priorité 0. À -64, il intervient après 0 mais avant -128, si aucun listener précédent n'a arrêté l'événement. L'exécution du callback de log ne prouve pas non plus qu'un journal externe a effectivement enregistré une ligne.

Comment, étape par étape ?

  1. Lire l'échec avec getThrowable() et décider si le listener connaît cette catégorie. Sinon, ne pas fournir de réponse : les autres traitements doivent pouvoir agir.
  2. Pour traduire l'échec sans choisir la réponse, employer setThrowable(). Les listeners suivants lisent alors le remplacement.
  3. Pour prendre en charge la réponse, construire une Response avec un statut d'erreur cohérent puis appeler setResponse().
  4. Arrêter le parcours des listeners restants de kernel.exception : c'est l'effet de cet appel, pas un arrêt de tous les événements du kernel.
  5. Après la propagation, HttpKernel relit le throwable et la réponse de l'événement. Sans réponse, il termine le contexte de la demande et relance l'échec ; avec une réponse, il applique les règles de statut puis le traitement de réponse. Une réponse 200 n'est donc pas automatiquement conservée : le statut suit les règles détaillées dans « Le choix du status code ».

Exemple concret PHP

L'autoload Composer doit déjà fournir EventDispatcher, HttpFoundation et HttpKernel 8.0. Cet exemple de laboratoire reproduit les positions 0 et -128 avec des callbacks de trace ; ce ne sont pas les méthodes du véritable ErrorListener et aucun fichier de log n'est écrit. Il sert à observer l'arrêt de propagation avec deux priorités du listener applicatif.

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Controller\ControllerResolver;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;
use Symfony\Component\HttpKernel\HttpKernel;
use Symfony\Component\HttpKernel\KernelEvents;

foreach ([100, -64] as $priority) {
    $trace = [];
    $dispatcher = new EventDispatcher();
    $dispatcher->addListener(KernelEvents::EXCEPTION,
        static function () use (&$trace): void {
            $trace[] = 'callback à 0';
        }, 0);
    $dispatcher->addListener(KernelEvents::EXCEPTION,
        static function (ExceptionEvent $event) use (&$trace): void {
            $trace[] = 'secours à -128';
            $event->setResponse(new Response('Erreur', 500));
        }, -128);
    $dispatcher->addListener(KernelEvents::EXCEPTION,
        static function (ExceptionEvent $event) use (&$trace): void {
            if (!$event->getThrowable() instanceof DomainException) {
                return;
            }
            $trace[] = 'application';
            $event->setResponse(new Response('Conflit de traitement', 409));
        }, $priority);

    $request = Request::create('/demo');
    $request->attributes->set('_controller', static function (): never {
        throw new DomainException('Etat incompatible');
    });
    $kernel = new HttpKernel($dispatcher, new ControllerResolver());
    $response = $kernel->handle($request);
    echo $priority, ': ', implode(' > ', $trace), ' / ', $response->getStatusCode(), "\n";
}

À priorité 100, la sortie attendue est 100: application / 409 : le callback à 0 n'a pas été appelé. À priorité -64, elle est -64: callback à 0 > application / 409 : l'effet précédent reste dans la trace. Dans les deux cas, le secours à -128 est sauté. Le code laisse une erreur d'un autre type poursuivre son traitement, au lieu de l'absorber silencieusement.

Contre-exemple : supposer qu'un listener à 100 peut appeler setResponse() tout en laissant nécessairement ErrorListener journaliser à 0. Correction : raisonner sur l'ordre réel et l'arrêt de propagation ; si la journalisation est indispensable, sa responsabilité et son ordre doivent être explicites. Une priorité choisie ne répare pas une garantie absente sans vérifier les autres listeners enregistrés.

Référence : gestion des exceptions dans HttpKernel Symfony 8.0.

Passage canonique conservé

Le mécanisme

ExceptionEvent offre deux leviers : setThrowable() remplace l'exception, setResponse() fournit une Response et met fin au traitement. Si aucun listener ne répond, l'ErrorListener intégré délègue à un controller d'erreur.

ErrorListener est branché sur quatre hooks, dont kernel.exception deux fois : logKernelException à 0, onKernelException à −128 ; s'y ajoutent onControllerArguments et removeCspHeader (kernel.response, −128). Le callback logKernelException à 0 ne s'exécute que si la propagation l'atteint. Un listener à 100 qui appelle setResponse() le précède et l'empêche ; un listener à -64 répond après le callback à 0 et avant celui à -128, sauf arrêt antérieur. Un callback exécuté ne prouve pas une écriture effective dans un journal externe.

Une alarme peut recevoir une intervention avant l'équipe de repli. De même, un listener qui fournit une Response arrête cet event ; ne pas en déduire que toute journalisation antérieure a été annulée.

Repère — La page d'erreur est une vraie sub-Request : No. The error sub-request uses catch=false. Le controller d'erreur s'exécute dans une sub-Request. Une nouvelle exception remonte avec l'erreur originale chaînée.

La page d'erreur est une vraie sub-Request

À retenir en priorité
  1. Le controller d'erreur s'exécute dans une sub-Request.
  2. Une nouvelle exception remonte avec l'erreur originale chaînée.

onKernelException duplique la Request vers le controller d'erreur et rappelle handle($request, SUB_REQUEST, false) : une exception levée dans le controller d'erreur n'est pas rattrapée, elle remonte avec l'originale en previous. En production, une exception pendant kernel.terminate ne produit pas de page : la Response est déjà partie.

Le choix du status code

À comprendre

C'est quoi ?

Après kernel.exception, HttpKernel examine la Response fournie et le throwable courant pour décider du statut final. Un listener qui construit une Response 200 ne garantit donc pas que cette réponse conservera 200.

À quoi ça sert ?

La règle évite qu'un échec non traité correctement soit annoncé comme un succès. Elle préserve toutefois les réponses d'erreur explicitement construites et permet une dérogation consciente lorsque l'application veut réellement un autre code.

Où dans Symfony ?

Sans autorisation de code personnalisé, HttpKernel applique ces tests :

  • Si la réponse est une erreur client, une erreur serveur ou satisfait Response::isRedirect(), son code est conservé.
  • Sinon, un throwable implémentant HttpExceptionInterface fournit son statut et ses headers.
  • Sinon, le statut devient 500.

Nuance exacte de 8.0 : isRedirect() reconnaît 201, 301, 302, 303, 307 et 308. Il ne faut donc pas remplacer ce test par « tous les 3xx », ni par une affirmation que tout 2xx serait forcément corrigé.

Comment, étape par étape ?

  1. Examiner la réponse et l'exception réellement présentes après les listeners.
  2. Appliquer les tests ci-dessus dans cet ordre.
  3. Si un statut de succès est intentionnel, appeler allowCustomResponseCode() avant de fournir la réponse.
  4. Réserver cette dérogation à un cas justifié : elle ne transforme pas une panne en succès métier.

Exemple concret PHP

Dans un listener déjà enregistré, cette fonction traite uniquement l'exception applicative précise AlreadyAccepted ; elle suppose que l'application a établi que la demande a déjà été acceptée.

<?php
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;
final class AlreadyAccepted extends RuntimeException {}
function handleAlreadyAccepted(ExceptionEvent $event): void
{
    if (!$event->getThrowable() instanceof AlreadyAccepted) {
        return;
    }
    $event->allowCustomResponseCode();
    $event->setResponse(new Response('', 202));
}

Le 202 est conservé grâce à l'autorisation explicite. Sans elle, cette exception ordinaire ferait corriger ce statut en 500. Contre-exemple : appliquer la même dérogation à toute exception pour éviter les erreurs HTTP. Correction : laisser les échecs inconnus suivre leur traitement et limiter la réponse personnalisée au cas métier défini.

Passage canonique conservé

Le choix du status code

  1. Response fournie en 4xx, 5xx ou redirect : son code est conservé.
  2. Sinon, exception HttpExceptionInterface : getStatusCode() de l'exception, et ses getHeaders() sont ajoutés à la Response.
  3. Sinon : 500.

Une Response 200 ou 204 construite dans un listener ne sort pas avec ce statut ; pour l'imposer, allowCustomResponseCode() avant setResponse().

Repère de l’exemple : It associates status 422 with that exception for the standard framework error handling. L'attribute associe un status code à cette exception précise. Ce choix explicite ne signifie pas que tout échec de validation doit produire 422.

HttpExceptionInterface

À comprendre

À retenir en priorité
  1. Le contrat HttpExceptionInterface porte statut et headers.
  2. WithHttpStatus peut transformer une exception avant cette décision.

C'est quoi ?

HttpExceptionInterface est le contrat d'une exception qui porte une intention HTTP : getStatusCode() donne le statut et getHeaders() les en-têtes associés. Le kernel se fonde sur cette interface, pas sur le seul nom de classe ni sur le code numérique général d'une exception PHP.

À quoi ça sert ?

Un échec peut transmettre les informations nécessaires à sa traduction HTTP sans fabriquer lui-même tout le contenu d'une page d'erreur. Un 404 indique une ressource introuvable ; un 429 peut être accompagné de Retry-After pour indiquer un délai avant nouvelle tentative.

Où dans Symfony ?

HttpException implémente ce contrat ; des classes spécialisées expriment des cas courants. Le framework peut aussi convertir une exception annotée avec #[WithHttpStatus] ou configurée dans sa table d'exceptions. Cette conversion dépend du listener qui la réalise : un traitement plus prioritaire qui arrête l'événement peut empêcher les listeners suivants d'agir.

Comment, étape par étape ?

  1. Déterminer le sens HTTP de l'échec à la frontière de l'application.
  2. Fournir le statut et les en-têtes nécessaires via le contrat.
  3. Laisser la gestion d'erreur produire une Response.
  4. Appliquer les règles de statut du kernel ; une réponse d'erreur déjà explicite n'est pas systématiquement remplacée par le statut de l'exception.

Exemple concret PHP

Avec HttpKernel 8.0 chargé, cet extrait inspecte l'exception sans la lancer ni envoyer une réponse :

<?php
use Symfony\Component\HttpKernel\Exception\HttpException;
$error = new HttpException(429, 'Limite temporaire', null, ['Retry-After' => '60']);
echo $error->getStatusCode(), "\n";
echo $error->getHeaders()['Retry-After'], "\n";

On attend 429 puis 60. Contre-exemple : créer new RuntimeException('Introuvable', 404) et supposer que getCode() devient le statut HTTP. Correction : utiliser une exception portant HttpExceptionInterface ou une traduction applicative explicite. Le code PHP d'une exception n'est pas son statut HTTP par convention universelle.

Passage canonique conservé

HttpExceptionInterface

Elle relie une exception à un statut : NotFoundHttpException (404), AccessDeniedHttpException (403), BadRequestHttpException (400), la class générique HttpException. Le critère est l'interface, jamais la class mère : HttpException étend \RuntimeException. Avant la règle du statut, logKernelException remplace par une HttpException toute exception annotée #[WithHttpStatus(…)] ou listée dans la table exceptions du framework — keys status_code, log_level, log_channel : la règle 2 s'applique alors sans un seul listener écrit à la main.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le statut de la Response fournie par un listener n'est pas toujours conservé.

    Le statut de la Response fournie par un listener n'est pas toujours conservé. Il ne l'est que si elle est 4xx, 5xx ou un redirect. Une Response 200 ou 204 prend le statut de l'exception — exécuté : 404 pour une NotFoundHttpException — et 500 dans le seul cas où l'exception n'implémente pas HttpExceptionInterface. Sauf allowCustomResponseCode() préalable.

  • Voir l’explication : \RuntimeException n'est pas le contre-exemple qu'on croit.

    \RuntimeException n'est pas le contre-exemple qu'on croit. HttpException extends \RuntimeException implements HttpExceptionInterface : la class mère ne dit rien du statut. Seule l'interface le dit.

  • Voir l’explication : setResponse() arrête la propagation de cet event.

    setResponse() arrête la propagation de cet event. Les callbacks restants, dont la page d'erreur à -128 si elle n'a pas déjà été appelée, ne sont pas exécutés. À priorité 100, cette réponse empêche aussi le callback de log à 0 ; à -64, elle vient après ce callback, sauf arrêt antérieur. Ne pas confondre callback atteint et journal externe écrit.

  • Voir l’explication : « Elle n'implémente pas l'interface, donc 500 » est trop rapide.

    « Elle n'implémente pas l'interface, donc 500 » est trop rapide. #[WithHttpStatus] et la table exceptions du framework font remplacer l'exception par une HttpException avant que la règle du statut ne s'applique.

  • Voir l’explication : Une exception dans le controller d'erreur n'est pas rattrapée.

    Une exception dans le controller d'erreur n'est pas rattrapée. La sub-Request est lancée avec $catch = false ; elle remonte, l'originale chaînée en previous.

Application

À retenir en priorité
  1. Un statut 200 n'est pas conservé automatiquement lors d'une erreur.
  2. allowCustomResponseCode() autorise explicitement ce choix.
  3. Le contrat HttpExceptionInterface porte statut et headers.
  4. WithHttpStatus peut transformer une exception avant cette décision.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • setResponse() termine ; setThrowable() remplace.
  • Statut : 4xx/5xx/redirect → le sien ; sinon HttpExceptionInterface ; sinon 500.
  • 200 ou 204 voulu : allowCustomResponseCode() d'abord.
  • Le critère est l'interface, pas \RuntimeException.
  • #[WithHttpStatus] et la table exceptions : statut sans listener.
  • Log à 0, page d'erreur à −128.
  • Page d'erreur = sub-Request, $catch = false.

Moyen mnémotechnique : « Logguer tôt, répondre tard ».
