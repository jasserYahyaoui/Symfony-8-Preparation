Objectif

Savoir ce que Symfony fait d'une exception non rattrapée, et surtout comment il choisit le status code de la Response produite.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Un statut 200 n'est pas conservé automatiquement lors d'une erreur.
  2. allowCustomResponseCode() autorise explicitement ce choix.

Une exception non rattrapée devient l'event kernel.exception. Un listener peut fournir une Response ou remplacer l'exception ; sinon ErrorListener construit la page d'erreur par une sub-Request. Le statut final suit une règle en trois temps, que l'examen interroge par des Responses 200 ou 204 qui ne sortent pas avec leur statut.

L'exemple : une exception qui porte son statut

▣ Exemple concret

À retenir en priorité
  1. L'attribute associe un status code à cette exception précise.
  2. Ce choix explicite ne signifie pas que tout échec de validation doit produire 422.
use Symfony\Component\HttpKernel\Attribute\WithHttpStatus;

#[WithHttpStatus(422)]
final class InvalidQuantity extends \InvalidArgumentException {}
// levée dans un controller : la Response sort en 422, sans listener maison

Le mécanisme

À retenir en priorité
  1. setThrowable() remplace l'erreur traitée.
  2. setResponse() fournit la Response et arrête la propagation de cet event.

ExceptionEvent offre deux leviers : setThrowable() remplace l'exception, setResponse() fournit une Response et met fin au traitement. Si aucun listener ne répond, l'ErrorListener intégré délègue à un controller d'erreur.

ErrorListener est branché sur quatre hooks, dont kernel.exception deux fois : logKernelException à 0, onKernelException à −128 ; s'y ajoutent onControllerArguments et removeCspHeader (kernel.response, −128). Le log passe donc toujours, même si un listener répond ensuite.

Une alarme peut recevoir une intervention avant l'équipe de repli. De même, un listener qui fournit une Response arrête cet event ; ne pas en déduire que toute journalisation antérieure a été annulée.

Repère — La page d'erreur est une vraie sub-Request : No. The error sub-request uses catch=false. Le controller d'erreur s'exécute dans une sub-Request. Une nouvelle exception remonte avec l'erreur originale chaînée.

La page d'erreur est une vraie sub-Request

À retenir en priorité
  1. Le controller d'erreur s'exécute dans une sub-Request.
  2. Une nouvelle exception remonte avec l'erreur originale chaînée.

onKernelException duplique la Request vers le controller d'erreur et rappelle handle($request, SUB_REQUEST, false) : une exception levée dans le controller d'erreur n'est pas rattrapée, elle remonte avec l'originale en previous. En production, une exception pendant kernel.terminate ne produit pas de page : la Response est déjà partie.

Le choix du status code

Revoir la règle : Un statut 200 n'est pas conservé automatiquement lors d'une erreur.

  1. Response fournie en 4xx, 5xx ou redirect : son code est conservé.
  2. Sinon, exception HttpExceptionInterface : getStatusCode() de l'exception, et ses getHeaders() sont ajoutés à la Response.
  3. Sinon : 500.

Une Response 200 ou 204 construite dans un listener ne sort pas avec ce statut ; pour l'imposer, allowCustomResponseCode() avant setResponse().

Repère de l’exemple : It associates status 422 with that exception for the standard framework error handling. L'attribute associe un status code à cette exception précise. Ce choix explicite ne signifie pas que tout échec de validation doit produire 422.

HttpExceptionInterface

À retenir en priorité
  1. Le contrat HttpExceptionInterface porte statut et headers.
  2. WithHttpStatus peut transformer une exception avant cette décision.

Elle relie une exception à un statut : NotFoundHttpException (404), AccessDeniedHttpException (403), BadRequestHttpException (400), la class générique HttpException. Le critère est l'interface, jamais la class mère : HttpException étend \RuntimeException. Avant la règle du statut, logKernelException remplace par une HttpException toute exception annotée #[WithHttpStatus(…)] ou listée dans la table exceptions du framework — keys status_code, log_level, log_channel : la règle 2 s'applique alors sans un seul listener écrit à la main.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Le controller d'erreur s'exécute dans une sub-Request.

Le statut de la Response fournie par un listener n'est pas toujours conservé. Il ne l'est que si elle est 4xx, 5xx ou un redirect. Une Response 200 ou 204 prend le statut de l'exception — exécuté : 404 pour une NotFoundHttpException — et 500 dans le seul cas où l'exception n'implémente pas HttpExceptionInterface. Sauf allowCustomResponseCode() préalable.

\RuntimeException n'est pas le contre-exemple qu'on croit. HttpException extends \RuntimeException implements HttpExceptionInterface : la class mère ne dit rien du statut. Seule l'interface le dit.

setResponse() met fin au traitement de l'erreur — l'ErrorListener intégré ne prend plus la main, et la page d'erreur n'est pas produite. Mais le log, lui, a déjà eu lieu : il passe à la priority 0, la page d'erreur à −128.

« Elle n'implémente pas l'interface, donc 500 » est trop rapide. #[WithHttpStatus] et la table exceptions du framework font remplacer l'exception par une HttpException avant que la règle du statut ne s'applique.

Une exception dans le controller d'erreur n'est pas rattrapée. La sub-Request est lancée avec $catch = false ; elle remonte, l'originale chaînée en previous.

Fiche express

◆ À mémoriser

Revoir la règle : Un statut 200 n'est pas conservé automatiquement lors d'une erreur.

Si tu dois retenir seulement 7 choses :

  • setResponse() termine ; setThrowable() remplace.
  • Statut : 4xx/5xx/redirect → le sien ; sinon HttpExceptionInterface ; sinon 500.
  • 200 ou 204 voulu : allowCustomResponseCode() d'abord.
  • Le critère est l'interface, pas \RuntimeException.
  • #[WithHttpStatus] et la table exceptions : statut sans listener.
  • Log à 0, page d'erreur à −128.
  • Page d'erreur = sub-Request, $catch = false.

Moyen mnémotechnique : « Logguer tôt, répondre tard ».
