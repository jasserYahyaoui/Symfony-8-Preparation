Objectif

Traduire depuis un template, gérer le plural et savoir ce que le filter et le tag font différemment. L'organisation des catalogues et la détection de la locale appartiennent aux Module 16 — Internationalisation et traduction et Module 05 — Routage.

L'essentiel

À comprendre

À retenir en priorité
  1. Le suffixe active l'interprétation MessageFormat.
  2. Les emplacements ICU utilisent des accolades.

Twig traduit avec un filter, |trans, un tag, {% trans %}, et une function, t(), qui crée un message traduit plus tard. Ils diffèrent par l'ordre des arguments, l'escaping et les emplacements. Le plural passe par ICU, dans un catalogue suffixé +intl-icu.

Le schéma

Le filter

À comprendre

À retenir en priorité
  1. Les parameters précèdent domain et locale.
  2. Les named arguments rendent l'appel moins ambigu.

C'est quoi ?

Le filtre trans demande la traduction d'un identifiant de message. Ses paramètres fournissent les substitutions, le domaine choisit un ensemble de messages et la locale choisit la langue. Ce sont trois décisions différentes.

À quoi ça sert ?

Un template utilise une clé stable alors que les formulations changent selon la langue. Les données variables restent des paramètres du message plutôt que des concaténations imposant le même ordre de mots partout.

Où dans Symfony ?

TranslationExtension relie Twig au translator. Pour une chaîne ordinaire, le premier argument après le filtre est le tableau de paramètres, suivi du domaine et de la locale. Le domaine usuel est messages, sauf contexte de domaine explicite ; la locale omise est celle du translator.

Comment, étape par étape ?

  1. Définir le message dans le catalogue voulu.
  2. Fournir des clés de substitution correspondant exactement au message.
  3. Choisir domaine et locale si leurs défauts ne conviennent pas.
  4. Vérifier le texte rendu avec les données réelles ; la traduction ne rend pas une donnée utilisateur sûre comme HTML.

Exemple concret YAML et Twig

Dans translations/store.fr.yaml :

user.greeting: 'Bonjour %name%'

Dans un template HTML avec l'intégration Translation :

<p>{{ 'user.greeting'|trans({'%name%': 'Ada'}, 'store', 'fr') }}</p>

Le texte est Bonjour Ada. Les arguments nommés permettent par exemple trans(domain: 'store') sans tableau vide si aucune substitution n'est nécessaire. Contre-exemple : écrire trans('store') sur une clé chaîne : store occupe la place du tableau de paramètres, pas celle du domaine. Correction : passer le tableau puis le domaine, ou utiliser l'argument nommé.

Passage canonique conservé

Le filter

<p>{{ 'user.greeting'|trans({'%name%': user.name}) }}</p>
<p>{{ 'checkout.total'|trans({}, 'store') }}</p>
<p>{{ 'legal.notice'|trans({}, 'messages', 'de') }}</p>
<p>{{ 'checkout.total'|trans(domain: 'store') }}</p>
  • Signature : trans(arguments = [], domain = null, locale = null, count = null). Domain omis : messages ; locale omise : la locale courante ; count renseigne %count%.
  • Les named arguments évitent l'array vide : trans(domain: 'store').
  • Le deuxième argument doit être un array. Une string n'y est admise que si le message est un object traduisible — elle désigne alors la locale. Sur une string ordinaire, |trans('store') lève une TypeError, que le template reçoit dans une RuntimeError.

Le catalogue est un guide de conversation : domain choisit l'onglet, locale l'édition, la key l'entrée stable. Changer la formulation n'exige donc pas de renommer la key dans tous les templates.

Repère — Échappé ou non : No. The filter output is escaped; the tag output is not automatically escaped. Le filter conserve l'auto-escaping. Le tag nécessite de maîtriser son contenu et ses parameters.

Les emplacements

À comprendre

À retenir en priorité
  1. Le remplacement doit viser la key exacte.
  2. name ne remplace pas proprement %name% si les délimiteurs restent dans le texte.

C'est quoi ?

Dans un message ordinaire, les paramètres sont des remplacements de chaînes : %name% est une convention de clé complète. Dans un message ICU, {name} appartient à la grammaire MessageFormat, qui peut aussi porter plural et select.

À quoi ça sert ?

Les paramètres permettent de varier la position d'une donnée selon la langue. Distinguer les deux formats évite d'attendre l'interprétation d'une expression ICU dans un catalogue ordinaire, ou de remplacer involontairement une partie de mot.

Où dans Symfony ?

Le suffixe +intl-icu du catalogue choisit MessageFormat. Dans un catalogue ordinaire, la clé de paramètre doit correspondre au texte à remplacer ; aucun ajout automatique de pourcents n'est promis. Pour ICU, Symfony accepte aussi des clés entourées de pourcents en retirant cet entourage.

Comment, étape par étape ?

  1. Identifier le format du catalogue.
  2. Écrire l'emplacement selon ce format.
  3. Fournir le nom de paramètre attendu.
  4. Tester une valeur et vérifier qu'aucun délimiteur involontaire ne subsiste.

Exemple concret YAML et Twig

Dans messages.fr.yaml :

greeting.normal: 'Bonjour %name%'

Dans messages+intl-icu.fr.yaml :

greeting.icu: 'Bonjour {name}'

Appels correspondants :

{{ 'greeting.normal'|trans({'%name%': 'Ada'}, 'messages', 'fr') }}
{{ 'greeting.icu'|trans({'name': 'Ada'}, 'messages', 'fr') }}

Les deux produisent Bonjour Ada par des mécanismes différents. Contre-exemple : passer la clé name sans pourcents au message ordinaire ci-dessus ; le remplacement de la sous-chaîne name laisse les pourcents autour d'Ada. Correction : utiliser la clé complète %name%. Les accolades seules ne font pas basculer un catalogue ordinaire vers ICU.

Passage canonique conservé

Les emplacements

Symfony remplace les emplacements par strtr(). Les pourcents de %name% sont une convention : #name# ou {name} marchent aussi, pourvu que la key corresponde exactement. Avec l'array {'name': 'Ada'} et le message Bonjour %name%, on obtient Bonjour %Ada%.

Le tag

À comprendre

À retenir en priorité
  1. Le domain par défaut a une portée locale.
  2. Un include conserve sa propre configuration de domain.

C'est quoi ?

Le tag trans traite son body comme du texte de message avec des emplacements. Il ne rend pas d'abord librement un sous-template Twig. trans_default_domain fixe le domaine implicite du template courant ; il ne modifie pas globalement tous les templates inclus.

À quoi ça sert ?

Le tag convient à un message écrit dans le template avec ses paramètres de traduction. Un domaine local évite de répéter son nom dans chaque filtre du fichier, tout en conservant un choix explicite possible par appel.

Où dans Symfony ?

Le tag vient de l'extension Translation du bridge. Ses clauses suivent l'ordre count, with, from, into. Les emplacements %name% peuvent venir de with ou, à défaut, du contexte ; une absence dans ce dernier peut échouer sous strict_variables.

Comment, étape par étape ?

  1. Écrire un body de texte simple avec ses emplacements.
  2. Passer les valeurs via with plutôt qu'insérer des doubles accolades dans le body.
  3. Choisir le domaine et la locale avec les clauses adaptées.
  4. Déclarer séparément le domaine d'un template inclus s'il en a besoin.

Exemple concret Twig

{% trans_default_domain 'store' %}
{% trans with {'%name%': 'Ada'} from 'store' into 'fr' %}Bonjour %name%{% endtrans %}

La traduction recherche le message Bonjour %name% dans store pour fr et substitue Ada ; en l'absence de traduction, ce texte reste le message utilisé. Contre-exemple : écrire {{ name }} dans le body du tag trans. Correction : employer %name% et with. Définir trans_default_domain dans le parent ne suffit pas à changer le domaine d'un fichier rendu par include : sa compilation conserve son propre contexte de domaine.

Passage canonique conservé

Le tag

{% trans with {'%name%': 'Fabien'} from 'app' into 'fr' %}Hello %name%{% endtrans %}
  • count, with, from, into, dans cet ordre ; un mot hors de place est une SyntaxError.
  • Le body est du texte simple : {{ name }} dans le body est une SyntaxError ; la notation %name% est obligatoire.
  • Un emplacement absent de with est lu dans le contexte (TransNode) : %name% vaut la variable name — erreur sous strict_variables si elle n'existe pas.
  • Un pourcent littéral se double : %percent%%%.

{% trans_default_domain 'app' %} fixe le domain du template courant seul : un template inclus garde messages.

Échappé ou non

À retenir en priorité
  1. Le filter conserve l'auto-escaping.
  2. Le tag nécessite de maîtriser son contenu et ses parameters.

L'output du filter est échappé, celui du tag ne l'est pas. Pour du HTML traduit par le filter : |trans|raw.

Le plural

À comprendre

C'est quoi ?

ICU MessageFormat est un format de messages qui sélectionne une variante selon un nombre ou une catégorie. plural utilise les règles de la locale ; select choisit une branche selon une valeur textuelle. Ce ne sont pas des expressions Twig placées dans le catalogue.

À quoi ça sert ?

Ajouter simplement un s quand le nombre dépasse un est insuffisant pour toutes les langues et tous les nombres. Le catalogue porte les variantes linguistiques ; le template fournit les données. Une branche exacte comme =0 exprime un cas métier particulier sans changer les règles de la locale.

Où dans Symfony ?

Le catalogue doit porter le suffixe +intl-icu, par exemple translations/messages+intl-icu.fr.yaml. Les arguments ICU utilisent des accolades, comme {name}, plutôt que la convention %name% des messages ordinaires. L'intégration Translation et le support ICU de la locale doivent être disponibles.

Comment, étape par étape ?

  1. Créer le message dans le catalogue ICU du domaine et de la locale voulus.
  2. Prévoir la branche other, y compris pour un select.
  3. Passer le nombre dans les paramètres du filtre trans.
  4. Tester zéro, un, plusieurs et les cas fractionnaires pertinents : les catégories dépendent de la locale, pas d'une comparaison PHP unique.

Exemple concret YAML et Twig

Catalogue messages+intl-icu.fr.yaml :

files.count: '{count, plural, =0 {Aucun fichier} one {# fichier} other {# fichiers}}'

Template, avec un nombre entier count dans le contexte :

<p>{{ 'files.count'|trans({'count': count}) }}</p>

Pour 0, 1 et 2, on attend Aucun fichier, 1 fichier, 2 fichiers. Contre-exemple : placer le même texte dans messages.fr.yaml sans suffixe puis attendre l'interprétation de plural. Correction : utiliser le catalogue ICU. Le domaine reste messages lors de l'appel.

Le filtre traduit une expression ; le tag trans traite son propre texte et ses emplacements. trans_default_domain ne configure que le template courant. Enfin t() construit un objet traduisible : en Symfony 8.0, l'afficher seul n'est pas une traduction ; employer |trans pour effectuer celle-ci.

Passage canonique conservé

Le plural

La documentation 8.0 traite plural, genre et formats par ICU MessageFormat : le file de catalogue porte le suffixe +intl-icu — messages+intl-icu.fr.yaml —, et les emplacements s'écrivent {name}. Sans le suffixe, les accolades ne sont pas interprétées.

La syntaxe à barres — '{0} Aucun|{1} Un|]1,Inf[ %count% résultats' — sélectionne d'après %count%. La documentation la dit legacy ; elle garde les intervalles personnalisés, qu'ICU n'a pas.

Plural et select, exécutés

À comprendre

À retenir en priorité
  1. other fournit le cas de repli obligatoire.
  2. Les catégories de plural dépendent de la locale.

C'est quoi ?

select choisit une branche par une valeur textuelle ; plural choisit une branche numérique exacte ou une catégorie grammaticale de la locale. On peut les imbriquer : la branche sélectionnée contient alors un second choix, pas une expression Twig à évaluer.

À quoi ça sert ?

Un type de contenu et une quantité peuvent modifier ensemble la formulation. Placer ces règles dans le message permet de changer l'ordre ou les mots selon la langue sans multiplier les conditions dans le template.

Où dans Symfony ?

Le message doit appartenir à un catalogue +intl-icu. Chaque select et chaque plural exige sa branche other. Dans un plural, une branche exacte =0 prime pour zéro ; # représente le nombre formaté dans la branche. Les catégories one et other dépendent de la locale, pas du nom du fichier d'affichage Twig.

Comment, étape par étape ?

  1. Choisir d'abord la dimension textuelle avec select.
  2. Prévoir un plural dans chaque branche qui dépend du nombre.
  3. Fermer soigneusement chaque niveau d'accolades.
  4. Tester branche connue, valeur textuelle inconnue, zéro et plusieurs.

Exemple concret YAML et Twig

Dans messages+intl-icu.fr.yaml :

media.count: '{kind, select, photo {{n, plural, =0 {Aucune photo} one {# photo} other {# photos}}} other {{n, plural, =0 {Aucun fichier} one {# fichier} other {# fichiers}}}}'
{{ 'media.count'|trans({'kind': 'photo', 'n': 2}, 'messages', 'fr') }}

Le résultat est 2 photos. Avec kind égal à document et n égal à 0, la branche other externe puis =0 interne donnent Aucun fichier. Contre-exemple : retirer other parce que toutes les valeurs actuelles semblent connues. Correction : conserver ce repli obligatoire à chaque niveau. Changer la locale change les catégories et le format des nombres, mais ne traduit pas automatiquement les noms écrits dans le message : un catalogue anglais doit aussi contenir les mots anglais.

Passage canonique conservé

Plural et select, exécutés

Message ICU Résultat
{n, plural, one {# fichier} other {# fichiers}}, locale fr 0 fichier, 1,5 fichier, 2 fichiers
le même message en anglais 0 files
=0 {aucun fichier} placé avant one =0 l'emporte pour 0
select ou plural sans other InvalidArgumentException à chaque trans()
select contenant un plural les deux s'imbriquent

Les catégories one, few… suivent la locale : en français, 0 et 1,5 sont one. Une key %name% remplit aussi {name} : Symfony retire les pourcents.

L'object traduisible

À comprendre

À retenir en priorité
  1. t() conserve message, parameters et domain.
  2. Le filter trans effectue la translation à l'affichage.

C'est quoi ?

t construit un TranslatableMessage : un objet qui conserve l'identifiant du message, ses paramètres et son domaine. La traduction est une opération ultérieure, effectuée notamment par le filtre trans dans Twig.

À quoi ça sert ?

On peut transmettre ensemble le message et son contexte de traduction sans choisir trop tôt le texte final. Transporter uniquement la clé perdrait les paramètres et le domaine nécessaires à un rendu correct.

Où dans Symfony ?

La fonction vient de TranslationExtension. En Symfony 8.0, TranslatableMessage n'offre plus de conversion implicite __toString ; l'affichage direct de l'objet ne produit pas automatiquement une traduction. Le translator doit être disponible au moment de trans.

Comment, étape par étape ?

  1. Construire l'objet avec sa clé, ses paramètres et son domaine.
  2. Le transmettre ou le conserver sans le convertir en chaîne.
  3. Appliquer trans à l'endroit du rendu.
  4. Vérifier la locale utilisée au moment de cette traduction différée.

Exemple concret YAML et Twig

Dans notifications.fr.yaml :

welcome: 'Bienvenue %name%'

Avec le translator configuré sur fr :

{% set message = t('welcome', {'%name%': 'Ada'}, 'notifications') %}
<p>{{ message|trans }}</p>

Le paragraphe affiche Bienvenue Ada. Contre-exemple : remplacer la dernière expression par l'affichage direct de message et attendre une traduction ou même une conversion en clé. Correction : conserver le filtre trans. La création par t ne prouve ni la présence du catalogue ni la disponibilité de la locale au moment où le message sera traduit.

Passage canonique conservé

L'object traduisible

t('notification.welcome', {…}, 'domaine') construit un TranslatableMessage qui garde ses parameters et son domain, et se traduit à l'affichage par |trans. Une enum qui retourne une key brute perd parameters et domain.

En 8.0, TranslatableMessage n'a plus de __toString() : {{ message }} seul fait échouer le rendu — une Error PHP, « could not be converted to string », sur Twig 3.22 —, là où 7.4 affichait la key. Seul {{ message|trans }} produit le texte.

Pièges d'examen

Piège à éviter

  • Voir l’explication : L'ordre des arguments du filter est parameters, puis domain, puis locale.

    L'ordre des arguments du filter est parameters, puis domain, puis locale. Les named arguments évitent de le deviner.

  • Voir l’explication : Une string en deuxième argument

    Une string en deuxième argument n'est une locale que pour un object traduisible ; ailleurs, c'est une erreur.

  • Échappement du filtre et du tag de traduction

    Le filter échappe, le tag non.

  • Portée du domaine de traduction dans un include

    trans_default_domain ne traverse pas un include.

  • Valeurs de remplacement issues du contexte Twig

    Dans le tag, un emplacement non fourni vient du contexte.

  • Voir l’explication : Accolades et pluriel

    Accolades et pluriel : sans le suffixe +intl-icu, {name} n'est qu'un emplacement ordinaire — rien n'est pluralisé.

Application

À retenir en priorité
  1. Le suffixe active l'interprétation MessageFormat.
  2. Les emplacements ICU utilisent des accolades.
  3. Le remplacement doit viser la key exacte.
  4. name ne remplace pas proprement %name% si les délimiteurs restent dans le texte.

Fiche express

À mémoriser

Si tu dois retenir seulement 8 choses :

  • |trans(paramètres, domaine, locale, count), named arguments admis.
  • String en 2ᵉ argument : locale pour t(), erreur pour une string.
  • strtr() : {'%name%': …}, pas {'name': …}.
  • Tag : count with from into, texte simple, %var% du contexte.
  • Filter échappé, tag non ; |raw pour le HTML du filter.
  • trans_default_domain : le template courant, pas les inclus.
  • ICU : +intl-icu, {name}, catégories de la locale, other obligatoire.
  • t() se traduit par |trans ; seul, il fait échouer le rendu.

Moyen mnémotechnique : « PDL : parameters, puis domain, puis locale — le filter échappe, le tag fait confiance ».

trans(params, domain, locale, count) ; string en 2e = locale pour t(), erreur sinon ; strtr exact ;
tag : count with from into, texte simple, non échappé ; default domain local ; ICU = +intl-icu + {name} ; t() via |trans
