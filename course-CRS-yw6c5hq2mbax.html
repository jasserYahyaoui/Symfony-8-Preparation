Objectif

Exécuter un controller depuis un template, et savoir ce que cela coûte et ce qui peut échouer. Le forward() d'un controller vers un autre appartient au Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Un fragment controller n'est pas un simple include Twig.
  2. Chaque sub-Request ajoute du traitement kernel.

render() exécute un controller depuis un template et insère sa Response — utile pour un élément qui a ses propres données sur toutes les pages, comme une barre latérale. Avec la stratégie inline, une sub-Request traverse le kernel : résolution du contrôleur, arguments, listeners concernés et rendu ont un coût. Les autres stratégies peuvent déléguer l'inclusion. Une simple réutilisation de HTML ne nécessite pas cette exécution de contrôleur.

Le schéma

Bleu = exécution inline ; ambre = contrôle de la réponse. Le chemin montre une réponse retournée normalement, pas une exception levée par le contrôleur : ce second cas suit les règles alt et ignore_errors détaillées ci-dessous. Une StreamedResponse réussie est diffusée immédiatement par le handler. Les stratégies déléguées ont un autre chemin de livraison : chaque fragment n'est pas nécessairement exécuté pendant le rendu PHP de la page principale.

Avec ou sans route

À retenir en priorité
  1. controller() construit la référence.
  2. render() déclenche son traitement.

La page de l'article peut proposer les trois publications récentes. Si show() possède déjà leurs données, un include suffit. Les appels ci-dessous conviennent lorsque cette zone possède réellement son propre traitement HTTP : l'un prépare une URI, l'autre une cible et ses attributs, puis render() demande leur traitement au système de fragments.

{{ render(path('latest_articles', {max: 3})) }}
{{ render(controller('App\\Controller\\BlogController::recentArticles', {max: 3})) }}
  • Un controller routé : render(path(…)) ou render(url(…)).
  • Un controller sans route : render(controller(…)). controller(nom, attributes, query) construit une ControllerReference et n'exécute rien ; c'est render() qui l'exécute. Affichée seule, {{ controller(…) }} fait échouer le rendu : la référence ne se convertit pas en string.
  • Les attributes de controller() deviennent des attributes de la sub-Request, objects compris en inline ; le troisième argument devient la query string.

🌍 In Real Life

La situation : pour ajouter un accompagnement, le serveur prépare soit une destination du circuit habituel, soit un bon désignant directement le poste compétent. Préparer ce bon ne cuisine encore rien.

L’équivalent dans Symfony : path() prépare une URI routée ; controller() prépare une ControllerReference avec cible, attributs et query. render() soumet cette entrée au système de fragments selon la stratégie choisie.

Retour à la réalité technique : une référence n'est ni du HTML ni une Response et ne s'affiche pas seule. Ses attributs sont des données de Request, pas des attributs PHP #[...]. Si les données des publications récentes sont déjà disponibles, un include Twig évite un traitement HTTP supplémentaire.

🧠 Comment le mémoriser : « Le bon désigne, le traitement prépare. » Image mentale : bon d'accompagnement encore posé devant le poste. Question-réflexe : ai-je préparé une référence, demandé son rendu, ou seulement besoin d'inclure un template ?

⚠️ À ne pas confondre : ControllerReference, callable résolu, données de fragment et HTML rendu.

Repère — Les strategies :

Question: Which fragment rendering strategy is the default?

Answer: inline.

Le rendu inline s'exécute dans le processus courant. Préférer un include lorsque le fragment ne requiert pas de controller.

Ce que cela déclenche

En inline, HttpKernel reçoit cette Request imbriquée et obtient le callable ; il appelle ensuite ArgumentResolver, qui consulte ses value resolvers, avant l'action. Les listeners peuvent distinguer main request et subrequest. Ce n'est donc ni un appel PHP gratuit ni une seconde navigation du lecteur, et les accès à la session restent partagés avec la page.

Avec la stratégie inline, chaque appel est une sub-Request GET traitée par le kernel (HttpKernelInterface::SUB_REQUEST). Elle reprend les cookies, les variables serveur et la session de la Request courante, sans If-Modified-Since ni If-None-Match, et transmet _format et la locale. Intégrer beaucoup de controllers pèse sur les performances.

🌍 In Real Life

La situation : le serveur fait préparer l'accompagnement pendant la commande principale. Il repasse par l'organisation interne ; le client ne sort pas pour passer une deuxième commande, mais le personnel travaille réellement une seconde fois.

L’équivalent dans Symfony : le renderer inline construit une sous-requête GET traitée par HttpKernel. ControllerResolver obtient le callable, ArgumentResolver fournit ses valeurs d'arguments, puis HttpKernel appelle l'action. Les listeners concernés participent selon leur traitement des sous-requêtes.

Retour à la réalité technique : ce n'est pas un nouveau démarrage complet du Kernel applicatif ni un simple include. Cookies et session sont repris selon le mécanisme décrit ; la session n'est pas une copie indépendante. La Request préparée n'est pas une duplication aveugle : certains en-têtes conditionnels sont retirés. Multiplier les fragments multiplie du travail, sans coût chiffré universel.

🧠 Comment le mémoriser : « Même visite, nouveau travail interne. » Image mentale : bon secondaire traversant les postes pendant que le client attend. Question-réflexe : ce fragment justifie-t-il une sous-requête avec résolution, listeners et rendu ?

⚠️ À ne pas confondre : Kernel applicatif, orchestration HttpKernel, résolution du callable et résolution des arguments.

Le journal envoie un reporter chercher un encadré prêt à imprimer : render(controller(...)) déclenche cette mission comme une vraie sub-Request. Un include, lui, réutilise un template sans cette mission kernel.

Repère — Quand le fragment échoue :

Question: Can a rendered fragment return a redirect as successful fragment content?

Answer: No. A non-2xx fragment response causes an error.

Un fragment doit fournir du contenu exploitable. Un redirect ne remplace pas ce contenu.

Les strategies

À retenir en priorité
  1. Le rendu inline s'exécute dans le processus courant.
  2. Préférer un include lorsque le fragment ne requiert pas de controller.

Pour compléter la page de l'article avec les publications récentes, render() utilise inline par défaut : le fragment est traité localement par une sous-requête. Son contenu rejoint le rendu de la page ; ce travail n'est ni une tâche parallèle ni une garantie de mise en cache.

L'option strategy sélectionne un renderer enregistré auprès de FragmentHandler. Un nom inconnu provoque une erreur, pas un repli automatique vers inline. Les raccourcis render_ssi() et render_hinclude() désignent d'autres stratégies lorsqu'elles sont configurées ; leur existence ne prouve pas qu'un renderer est disponible dans l'application. ESI reste hors de ce cours.

Avec le générateur d'URI de fragments configuré, fragment_uri() prépare au contraire l'URI d'une référence de contrôleur, signée par défaut, sans exécuter ce contrôleur. Obtenir cette adresse ne produit pas le contenu du fragment et ne garantit pas que son traitement réussira. La section suivante distingue cet adressage de l'appel inline interne.

🌍 In Real Life

La situation : pour compléter l'assiette, la cuisine prépare l'accompagnement sur place avant de l'y ajouter. Écrire sur un bon où demander cet accompagnement ne le prépare pas : le bon et le plat obtenu sont deux résultats différents.

L’équivalent dans Symfony : avec la stratégie inline, le fragment est traité localement par une sous-requête et son contenu rejoint le rendu de la page. Pour une référence de contrôleur, fragment_uri() prépare au contraire l'URI du fragment sans appeler ce contrôleur.

Retour à la réalité technique : inline est la stratégie par défaut ; le traitement du fragment reste du travail effectué pendant le rendu de la page, pas une tâche parallèle ni une garantie de cache. Préparer une URI ne produit pas le contenu du fragment et ne prouve pas que son exécution réussira. ESI reste hors de ce cours.

🧠 Comment le mémoriser : « Le bon indique où demander ; la cuisine produit le plat. » Image mentale : bon de commande à côté de l'accompagnement préparé. Question-réflexe : cet appel prépare-t-il une URI ou exécute-t-il le fragment pour en obtenir le contenu ?

⚠️ À ne pas confondre : URI de fragment, sous-requête locale, contenu rendu et mise en cache.

L'URL des fragments

À retenir en priorité
  1. framework.fragments expose un endpoint externe.
  2. Le rendu inline n'a pas besoin de cette exposition.

La référence interne peut transmettre des objets directement en inline. Une URI destinée à sortir du processus a d'autres contraintes : ses paramètres doivent pouvoir être transportés, et son accès doit être protégé. La signature de fragment contrôle cette entrée technique ; elle ne remplace pas les droits métier sur les données que l'action affiche.

controller() construit une référence, pas encore une URL. Pour cette référence, le générateur utilise le chemin /_fragment par défaut, configurable via framework.fragments.path. fragment_uri() prépare une URI signée par défaut, sans appeler le contrôleur ; ses attributs doivent être représentables dans l'URL, et non transportés comme objets PHP.

framework.fragments est désactivé par défaut. Son activation permet de traiter les requêtes extérieures vers cette entrée, par exemple pour une inclusion hinclude configurée. FragmentListener vérifie la signature et exige une méthode HTTP sûre avant de reconstruire les attributs de cette requête extérieure. La signature protège l'intégrité de l'URI, pas la confidentialité de ses paramètres ni l'autorisation métier. ESI reste hors de ce cours.

En inline, la sous-requête issue de la référence porte déjà son _controller et conserve les attributs en mémoire : cette exposition extérieure n'a pas besoin d'être activée. Pour le fragment « publications récentes », on peut donc rester dans le traitement local de la page.

🌍 In Real Life

La situation : un bon circulant entre postes peut transporter un dossier interne. Un bon envoyé par une entrée extérieure doit être transportable et porter un sceau vérifiable ; ce sceau ne donne pas tous les droits sur les dossiers.

L’équivalent dans Symfony : en inline, les attributs de la référence peuvent contenir des objets. Une URI de fragment doit transporter des paramètres représentables. L'exposition de /_fragment via framework.fragments permet l'entrée extérieure contrôlée par signature dans le dispositif décrit.

Retour à la réalité technique : l'appel inline porte déjà _controller et n'exige pas cette exposition extérieure. Une signature protège l'intégrité de l'URI ; elle ne chiffre pas les paramètres, n'identifie pas à elle seule l'utilisateur et ne remplace pas l'autorisation métier. Ne transforme pas arbitrairement un objet PHP en donnée publique d'URL.

🧠 Comment le mémoriser : « Bon interne, entrée signée, droits toujours vérifiés. » Image mentale : porte extérieure avec sceau devant des dossiers encore protégés. Question-réflexe : mon fragment reste-t-il interne ou devient-il accessible séparément ?

⚠️ À ne pas confondre : transport des paramètres, signature, authentification et autorisation.

Quand le fragment échoue

À retenir en priorité
  1. Un fragment doit fournir du contenu exploitable.
  2. Un redirect ne remplace pas ce contenu.

Un article42 peut être rendu correctement alors que la zone « publications récentes » échoue. Distingue l'exception pendant le renderer du refus, par FragmentHandler, d'une Response finalement non2xx. Les options de repli ne transforment pas une302 en navigation principale : le handler attend du contenu de fragment, pas une instruction de redirection.

Ici dev désigne la configuration habituelle avec kernel.debug = true, prod celle avec debug désactivé ; le nom de l'environnement ne décide pas du comportement. Le repli décrit concerne les Exception interceptées par InlineFragmentRenderer, pas toute erreur PHP possible.

  • Exception dans le controller : FragmentHandler fixe ignore_errors à !kernel.debug. En dev, l'exception remonte ; en prod, elle passe par kernel.exception — pour le log — et le fragment est vide.
  • alt désigne un fragment de repli, essayé avant de relancer : en dev, il masque l'erreur sans la loguer.
  • Response non 2xx, redirect compris : RuntimeException, quel que soit ignore_errors. Un fragment ne redirige pas.

🌍 In Real Life

La situation : le poste d'accompagnement peut signaler une panne pendant la préparation ; une solution de repli est alors envisageable. Mais un bon « allez ailleurs » remis à la livraison n'est toujours pas l'accompagnement attendu.

L’équivalent dans Symfony : alt et ignore_errors interviennent sur les exceptions interceptées pendant le rendu inline. FragmentHandler vérifie séparément que la Response à livrer a un statut2xx ; une302 retournée n'est pas une redirection de la page principale.

Retour à la réalité technique : le défaut de ignore_errors dépend de kernel.debug, pas du nom de l'environnement. Les options ne couvrent pas toute erreur PHP et n'annulent pas le contrôle non2xx du handler. Un repli réussi ne prouve pas l'absence de panne ; la journalisation dépend du chemin et des listeners configurés. Une StreamedResponse réussie a aussi une livraison particulière, pas simplement une chaîne conservée.

🧠 Comment le mémoriser : « Repli pendant la préparation, contrôle à la livraison. » Image mentale : deux contrôles distincts avant l'assiette finale. Question-réflexe : suis-je face à une exception du renderer ou à une Response refusée par le handler ?

⚠️ À ne pas confondre : exception interceptée, réponse non2xx, fragment vide et navigation principale.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le rendu inline déclenche une sub-Request

    Le rendu inline déclenche une sub-Request, pas un simple appel de function ; ne pas généraliser cette exécution locale aux stratégies déléguées.

  • Voir l’explication : controller() seul n'exécute rien

    controller() seul n'exécute rien : il construit une référence, et l'afficher sans render() fait échouer le rendu.

  • Erreurs de fragments selon l’environnement

    Une erreur de fragment ne se comporte pas pareil en dev et en prod.

  • Redirection dans un fragment

    Un redirect dans un fragment est une erreur.

  • Voir l’explication : framework.fragments n'est pas actif par défaut

    framework.fragments n'est pas actif par défaut ; il sert à exposer /_fragment à l'extérieur, pas à faire fonctionner inline.

Application

À retenir en priorité
  1. controller() construit la référence.
  2. render() déclenche son traitement.
  3. Le rendu inline s'exécute dans le processus courant.
  4. Préférer un include lorsque le fragment ne requiert pas de controller.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • render() exécute ; controller() désigne un controller sans route.
  • {{ controller(…) }} seul : le rendu échoue.
  • En inline, fragment = sub-Request GET ; cookies et session repris.
  • ignore_errors vaut !kernel.debug par défaut ; alt et le dispatcher d'exceptions interviennent selon les options.
  • alt est essayé avant de relancer.
  • Non 2xx → RuntimeException, toujours.
  • /_fragment n'exige framework.fragments que pour l'accès extérieur décrit ici, pas pour l'appel inline interne.

Moyen mnémotechnique : « controller désigne, inline exécute, 2xx livre ».

render avec stratégie inline = sub-Request GET ; controller() seul échoue ; ignore_errors = !debug ;
alt avant de relancer ; non 2xx = RuntimeException ; /_fragment pour l'extérieur
