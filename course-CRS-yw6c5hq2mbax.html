Objectif

Exécuter un controller depuis un template, et savoir ce que cela coûte et ce qui peut échouer. Le forward() d'un controller vers un autre appartient au Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Un fragment controller n'est pas un simple include Twig.
  2. Chaque sub-Request ajoute du traitement kernel.

render() exécute un controller depuis un template et insère sa Response — utile pour un élément qui a ses propres données sur toutes les pages, comme une barre latérale. Avec la stratégie inline, une sub-Request traverse le kernel : résolution du contrôleur, arguments, listeners concernés et rendu ont un coût. Les autres stratégies peuvent déléguer l'inclusion. Une simple réutilisation de HTML ne nécessite pas cette exécution de contrôleur.

Le schéma

Bleu = exécution inline ; ambre = contrôle de la réponse. Le chemin montre une réponse retournée normalement, pas une exception levée par le contrôleur : ce second cas suit les règles alt et ignore_errors détaillées ci-dessous. Une StreamedResponse réussie est diffusée immédiatement par le handler. Les stratégies déléguées ont un autre chemin de livraison : chaque fragment n'est pas nécessairement exécuté pendant le rendu PHP de la page principale.

Avec ou sans route

À retenir en priorité
  1. controller() construit la référence.
  2. render() déclenche son traitement.
{{ render(path('latest_articles', {max: 3})) }}
{{ render(controller('App\\Controller\\BlogController::recentArticles', {max: 3})) }}
  • Un controller routé : render(path(…)) ou render(url(…)).
  • Un controller sans route : render(controller(…)). controller(nom, attributes, query) construit une ControllerReference et n'exécute rien ; c'est render() qui l'exécute. Affichée seule, {{ controller(…) }} fait échouer le rendu : la référence ne se convertit pas en string.
  • Les attributes de controller() deviennent des attributes de la sub-Request, objects compris en inline ; le troisième argument devient la query string.

Repère — Les strategies : inline. Le rendu inline s'exécute dans le processus courant. Préférer un include lorsque le fragment ne requiert pas de controller.

Ce que cela déclenche

Avec la stratégie inline, chaque appel est une sub-Request GET traitée par le kernel (HttpKernelInterface::SUB_REQUEST). Elle reprend les cookies, les variables serveur et la session de la Request courante, sans If-Modified-Since ni If-None-Match, et transmet _format et la locale. Intégrer beaucoup de controllers pèse sur les performances.

Le journal envoie un reporter chercher un encadré prêt à imprimer : render(controller(...)) déclenche cette mission comme une vraie sub-Request. Un include, lui, réutilise un template sans cette mission kernel.

Repère — Quand le fragment échoue : No. A non-2xx fragment response causes an error. Un fragment doit fournir du contenu exploitable. Un redirect ne remplace pas ce contenu.

Les strategies

À retenir en priorité
  1. Le rendu inline s'exécute dans le processus courant.
  2. Préférer un include lorsque le fragment ne requiert pas de controller.

inline est la strategy de rendu admise ici. Elle fait traiter le fragment dans le processus courant. Si le besoin est seulement de réutiliser du balisage avec des données disponibles, préférer include() à un nouveau passage par le kernel.

L'URL des fragments

À comprendre

À retenir en priorité
  1. framework.fragments expose un endpoint externe.
  2. Le rendu inline n'a pas besoin de cette exposition.

C'est quoi ?

framework.fragments.path définit le chemin interne utilisé pour les références de controller, par défaut /_fragment. L'activation de framework.fragments permet au listener de traiter les requêtes externes destinées à cette entrée de fragments ; le rendu inline est un autre chemin d'exécution.

À quoi ça sert ?

Une stratégie de fragments faisant intervenir un client ou un intermédiaire HTTP a besoin d'une adresse atteignable. Un simple rendu inline possède déjà son _controller dans une sous-Request et n'exige pas d'exposer cette entrée publique.

Où dans Symfony ?

FrameworkBundle configure l'intégration des fragments HttpKernel. Les URL externes produites à partir de références de controller utilisent une signature ; le path n'est pas une permission d'appeler librement n'importe quelle action par des paramètres inventés.

Comment, étape par étape ?

  1. Identifier si le fragment est traité inline ou via une requête externe.
  2. Activer l'entrée seulement lorsque le mécanisme choisi en a besoin.
  3. Configurer son path de façon cohérente avec l'application.
  4. Laisser le générateur et les vérifications de signature assurer leur contrat ; ne pas construire manuellement les paramètres internes.

Exemple concret YAML

Dans config/packages/framework.yaml, pour une application ayant besoin de l'entrée externe :

framework:
    fragments:
        path: /_parts

L'adresse interne configurée devient /_parts. Contre-exemple : activer cette entrée uniquement parce que render(controller(...)) est utilisé en stratégie inline. Correction : distinguer la sous-Request déjà munie de son controller d'une requête externe vers une URL signée. Configurer ce path ne suffit pas à installer ni à rendre opérationnelle toute stratégie externe de cache ou de chargement.

Passage canonique conservé

Le path interne des fragments est /_fragment par défaut, configurable par framework.fragments.path. framework.fragments expose cet endpoint à l'extérieur et reste désactivé par défaut. En inline, une ControllerReference fournit déjà _controller à la sub-Request : l'activation externe n'est pas nécessaire.

Quand le fragment échoue

À retenir en priorité
  1. Un fragment doit fournir du contenu exploitable.
  2. Un redirect ne remplace pas ce contenu.

Ici dev désigne la configuration habituelle avec kernel.debug = true, prod celle avec debug désactivé ; le nom de l'environnement ne décide pas du comportement. Le repli décrit concerne les Exception interceptées par InlineFragmentRenderer, pas toute erreur PHP possible.

  • Exception dans le controller : FragmentHandler fixe ignore_errors à !kernel.debug. En dev, l'exception remonte ; en prod, elle passe par kernel.exception — pour le log — et le fragment est vide.
  • alt désigne un fragment de repli, essayé avant de relancer : en dev, il masque l'erreur sans la loguer.
  • Response non 2xx, redirect compris : RuntimeException, quel que soit ignore_errors. Un fragment ne redirige pas.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le rendu inline déclenche une sub-Request

    Le rendu inline déclenche une sub-Request, pas un simple appel de function ; ne pas généraliser cette exécution locale aux stratégies déléguées.

  • Voir l’explication : controller() seul n'exécute rien

    controller() seul n'exécute rien : il construit une référence, et l'afficher sans render() fait échouer le rendu.

  • Erreurs de fragments selon l’environnement

    Une erreur de fragment ne se comporte pas pareil en dev et en prod.

  • Redirection dans un fragment

    Un redirect dans un fragment est une erreur.

  • Voir l’explication : framework.fragments n'est pas actif par défaut

    framework.fragments n'est pas actif par défaut ; il sert à exposer /_fragment à l'extérieur, pas à faire fonctionner inline.

Application

À retenir en priorité
  1. controller() construit la référence.
  2. render() déclenche son traitement.
  3. Le rendu inline s'exécute dans le processus courant.
  4. Préférer un include lorsque le fragment ne requiert pas de controller.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • render() exécute ; controller() désigne un controller sans route.
  • {{ controller(…) }} seul : le rendu échoue.
  • En inline, fragment = sub-Request GET ; cookies et session repris.
  • ignore_errors vaut !kernel.debug par défaut ; alt et le dispatcher d'exceptions interviennent selon les options.
  • alt est essayé avant de relancer.
  • Non 2xx → RuntimeException, toujours.
  • /_fragment n'exige framework.fragments que pour l'accès extérieur décrit ici, pas pour l'appel inline interne.

Moyen mnémotechnique : « controller désigne, inline exécute, 2xx livre ».

render avec stratégie inline = sub-Request GET ; controller() seul échoue ; ignore_errors = !debug ;
alt avant de relancer ; non 2xx = RuntimeException ; /_fragment pour l'extérieur
