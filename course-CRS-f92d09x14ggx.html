Objectif

Conditionner l'appariement d'une route à une logique arbitraire, et connaître la limite de ce mécanisme.

L'essentiel

À comprendre

À retenir en priorité
  1. condition filtre l'entrée.
  2. L'expression peut être compilée dans le cache du matcher.

L'option condition prend une expression ExpressionLanguage, compilée une fois en PHP dans le cache du router, puis exécutée à chaque Request qui atteint la route. Elle voit context, request et params, et appelle env() ou service(). Fausse, elle efface la route : ni 405, ni redirect. Et elle est ignorée à la génération d'URL.

Le schéma

À retenir en priorité
  1. context expose le RequestContext.
  2. request donne la Request ; params les parameters déjà appariés.

Bleu = compilation ou exécution ; ambre = décision. Une condition ne remplace pas l'autorisation : le User-Agent de l'exemple est contrôlé par le client. Une condition fausse retire cette candidate, pas toutes les autres routes. Le coût du PHP compilé inclut les appels de services : éviter un accès réseau répété pour chaque candidate.

L'exemple

Exemple concret

La page de contact du blog sert ici de variante expérimentale selon le User-Agent. Cette donnée est contrôlée par le client : l'exemple montre une sélection de route, pas un mécanisme d'authentification. Un lecteur dont la condition échoue peut encore correspondre à une autre route.

#[Route(
    '/contact',
    name: 'contact',
    condition: "context.getMethod() in ['GET', 'HEAD'] and request.headers.get('User-Agent') matches '/firefox/i'",
)]

L'option `condition`

Une fonctionnalité de prévisualisation peut nécessiter un critère que le path ne représente pas. L'expression devient du PHP dans le matcher compilé ; à chaque candidate atteinte, ce PHP décide de poursuivre ou non. Cela évite de recompiler l'expression à chaque visite, pas d'exécuter les services qu'elle appelle.

L'expression est évaluée à l'appariement ; fausse, la route ne correspond pas. C'est la porte de sortie pour ce que methods, host et schemes ne savent pas exprimer.

CompiledUrlMatcherDumper la compile en PHP brut quand il écrit le matcher en cache, par ExpressionLanguage::compile() avec les noms context, request et params. Une condition ne coûte donc que l'exécution de ce PHP. Si le code compilé ne mentionne pas $request, le matcher ne construit pas d'object Request supplémentaire pour cette évaluation. Dans l'application HTTP, la Request de /blog/42 existe déjà : ce détail d'optimisation du matcher ne supprime pas l'objet reçu par HttpKernel.

🌍 In Real Life

La situation : l'accueil traduit une consigne en fiche de contrôle réutilisable. La fiche est préparée une fois, mais chaque visiteur doit encore passer le contrôle ; téléphoner à un service à chaque passage reste coûteux.

L’équivalent dans Symfony : le dumper compile l'expression de condition en PHP dans le matcher en cache. Ce PHP s'exécute lorsque la recherche atteint la candidate ; ses appels de services restent du travail à effectuer.

Retour à la réalité technique : compilation ne signifie pas résultat booléen mémorisé pour toutes les requêtes. Le cache peut être reconstruit. L'optimisation évitant une Request supplémentaire au matcher ne supprime pas la Request déjà reçue par HttpKernel.

🧠 Comment le mémoriser : « Préparer la grille une fois, contrôler chaque passage. » Image mentale : même fiche de contrôle devant plusieurs visiteurs. Question-réflexe : qu'ai-je mis en cache, la procédure ou son résultat ?

⚠️ À ne pas confondre : compilation, exécution et cache d'un résultat métier.

Les variables disponibles

params['id'] décrit ici la capture de route, pas un article déjà chargé. context suffit pour méthode et hôte ; request ouvre les données complètes de la requête. Si une règle appelle service(), son service doit figurer dans le locator prévu : compiler l'expression n'expose pas tout le conteneur.

Variable Contenu
context le RequestContext : method, host, schéma, port
request l'object Request complet
params les parameters de route déjà appariés : "params['id'] < 1000"

FrameworkBundle ajoute deux functions : env('NOM') lit une variable d'environment, avec ses processeurs ; service('alias') appelle un service marqué #[AsRoutingConditionService] ou tagué routing.condition_service — sans alias, par son identifier. service() passe par un locator de ces seuls services : une condition n'atteint pas le reste du container. Un parameter de configuration s'écrit entre pourcents.

🌍 In Real Life

La situation : l'agent dispose d'un résumé de visite, du dossier complet et des références déjà relevées. Son annuaire interne ne contient que les spécialistes autorisés à répondre à ce contrôle.

L’équivalent dans Symfony : context fournit le RequestContext ; request la Request ; params les valeurs de route disponibles. service() accède au locator des services déclarés pour les conditions, et env() est fourni par l'intégration FrameworkBundle.

Retour à la réalité technique : params['id'] n'est pas un article chargé. Le locator ne donne pas accès à tout le conteneur. Les données client, dont User-Agent, ne constituent pas une identité vérifiée ; les expressions restent une configuration de confiance, pas du code fourni par l'utilisateur.

🧠 Comment le mémoriser : « Résumé, dossier, captures ; annuaire limité. » Image mentale : trois sources sur le bureau et un petit annuaire dédié. Question-réflexe : quelle source contient ma donnée et quel service est réellement exposé ?

⚠️ À ne pas confondre : RequestContext, Request, captures et objets métier ; sélection de route et authentification.

Une condition fausse efface la route

À retenir en priorité
  1. Une condition fausse retire la route des candidates.
  2. Sans autre correspondance, le résultat est 404.

Si la prévisualisation est désactivée, cette candidate ne contribue plus aux méthodes autorisées ni à une correction de slash. Le matcher continue avec les autres routes ; 404 n'est le résultat que si elles échouent aussi. La route reste définie dans la collection : « effacer » décrit son exclusion pour cette tentative, pas une suppression durable de configuration.

Dans le matcher compilé, la condition est testée avant la barre finale, le schéma et la method. Une route dont la condition est fausse n'ajoute pas ses methods à la liste d'un 405, et ne déclenche aucun redirect de barre finale ou de schéma. Si rien d'autre ne correspond : 404.

🌍 In Real Life

La situation : une ligne du plan d'accueil ne convient pas à cette visite ; l'agent passe à la suivante sans déchirer le plan. Cette ligne écartée ne propose plus sa correction d'adresse ni ses modalités.

L’équivalent dans Symfony : une condition fausse exclut cette candidate de la tentative. Dans le matcher décrit, elle ne contribue alors ni aux méthodes d'un 405 ni aux corrections de slash ou de schéma ; les autres routes restent examinées.

Retour à la réalité technique : aucune route n'est supprimée durablement de la collection. Le résultat HTTP final dépend des autres candidates et de l'intégration. Une condition vraie permet seulement de poursuivre les contrôles, pas de garantir une réponse 200.

🧠 Comment le mémoriser : « Sauter une ligne n'efface pas le plan. » Image mentale : doigt passant une consigne inapplicable. Question-réflexe : cette candidate a-t-elle été écartée, et que peuvent encore produire les autres ?

⚠️ À ne pas confondre : condition fausse, méthode non autorisée, route supprimée et autorisation refusée.

La limite, et elle est importante

À retenir en priorité
  1. Le generator ne dispose pas du contexte de matching.
  2. Un lien généré peut viser une route qui ne correspondrait pas à la Request.

Un lien vers cette prévisualisation peut pourtant être généré et affiché. Le générateur n'évalue pas la condition du futur lecteur ; il écrit une URL à partir de la route. Contrôle donc séparément l'affichage du lien si nécessaire, et conserve l'autorisation dans Security plutôt que d'assimiler un lien générable à un accès accordé.

Les conditions ne sont pas prises en compte lors de la génération d'URL.

Le generator ne connaît ni la Request ni le user agent : une route protégée par une condition reste générable, y compris vers un contexte où elle ne correspondrait pas. Une condition filtre l'entrée ; un requirement, lui, vaut dans les deux sens.

🌍 In Real Life

La situation : imprimer l'adresse d'un guichet ne vérifie pas que sa règle d'accueil acceptera la prochaine visite. L'adresse peut être correcte alors que cette demande sera orientée ailleurs.

L’équivalent dans Symfony : le générateur écrit l'URL de la route sans évaluer sa condition. Le matching de la future Request reste indépendant ; l'affichage conditionnel du lien et l'autorisation nécessitent leurs propres décisions.

Retour à la réalité technique : cette limite n'enlève pas les autres contrôles de génération, notamment variables obligatoires et requirements selon la politique active. Masquer un lien ne protège pas la ressource et une URL générable ne prouve aucun droit d'accès.

🧠 Comment le mémoriser : « Adresse imprimable n'est pas visite admissible. » Image mentale : invitation prête devant un contrôle encore à passer. Question-réflexe : ai-je seulement généré le lien ou vérifié le contexte de sa future utilisation ?

⚠️ À ne pas confondre : condition de matching, requirement de paramètre et règle Security.

Une invitation peut imprimer une adresse même si une condition d'entrée refuserait son porteur. Le generator imprime le lien ; la condition reste une décision du matching, pas une règle d'authorization.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Une condition ne s'applique pas à la génération d'URL.

    Une condition ne s'applique pas à la génération d'URL. Une route protégée par une condition reste parfaitement générable, y compris vers un contexte où elle ne correspondrait pas.

  • Voir l’explication : Une condition filtre l'entrée ; elle ne documente pas l'output.

    Une condition filtre l'entrée ; elle ne documente pas l'output. C'est toute la différence avec un requirement de parameter, qui vaut dans les deux sens.

  • Voir l’explication : L'expression est compilée en PHP, pas interprétée à chaque Request.

    L'expression est compilée en PHP, pas interprétée à chaque Request. Elle est compilée une fois dans le cache du router ; seul le PHP qui en résulte s'exécute à chaque Request.

  • Voir l’explication : Condition fausse : pas de 405.

    Condition fausse : pas de 405. La route disparaît avant le contrôle de method.

Application

À retenir en priorité

  2. L'expression peut être compilée dans le cache du matcher.
  3. Une condition fausse retire la route des candidates.
  4. Sans autre correspondance, le résultat est 404.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • condition = ExpressionLanguage, compilée une fois en PHP.
  • Variables : context, request, params.
  • Functions : env(), service() (#[AsRoutingConditionService]).
  • Fausse → candidate ignorée ; 404 seulement si aucune autre ne correspond.
  • Vraie → les contrôles suivants (method, schéma) s'appliquent.
  • Ignorée à la génération d'URL.

Moyen mnémotechnique : « La condition filtre l'arrivée, jamais la génération ».
