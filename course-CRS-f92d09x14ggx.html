Objectifs d’apprentissage

  • Écrire une condition d'appariement de route

Précision, exception ou condition d’application d’une règle.

Objectif

Conditionner l'appariement d'une route à une logique arbitraire, et connaître la limite de ce mécanisme.

L'essentiel

○ À comprendre

À retenir en priorité
  1. condition filtre l'entrée.
  2. L'expression peut être compilée dans le cache du matcher.

L'option condition prend une expression ExpressionLanguage, compilée une fois en PHP dans le cache du router, puis exécutée à chaque Request qui atteint la route. Elle voit context, request et params, et appelle env() ou service(). Fausse, elle efface la route : ni 405, ni redirect. Et elle est ignorée à la génération d'URL.

Le schéma

À retenir en priorité
  1. context expose le RequestContext.
  2. request donne la Request ; params les parameters déjà appariés.

L'exemple

▣ Exemple concret

class ExampleController
{
    #[Route(
        '/contact',
        name: 'contact',
        condition: "context.getMethod() in ['GET', 'HEAD'] and request.headers.get('User-Agent') matches '/firefox/i'",
    )]
    public function __invoke(): \Symfony\Component\HttpFoundation\Response
    {
        return new \Symfony\Component\HttpFoundation\Response();
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

L'option `condition`

L'expression est évaluée à l'appariement ; fausse, la route ne correspond pas. C'est la porte de sortie pour ce que methods, host et schemes ne savent pas exprimer.

CompiledUrlMatcherDumper la compile en PHP brut quand il écrit le matcher en cache, par ExpressionLanguage::compile() avec les noms context, request et params. Une condition ne coûte donc que l'exécution de ce PHP. Si le code compilé ne mentionne pas $request, le matcher ne construit pas d'object Request.

Repère — Une condition fausse efface la route : No. It is rejected before that method decision. Une condition fausse retire la route des candidates. Sans autre correspondance, le résultat est 404.

Les variables disponibles

○ À comprendre

C'est quoi ?

Une condition dispose de context, le RequestContext ; request, la Request ; et params, les variables déjà extraites de la route. FrameworkBundle ajoute env et service : cette dernière fonction consulte uniquement les services exposés aux conditions, pas l'ensemble du container.

À quoi ça sert ?

Un prédicat réutilisé peut être placé dans un service pour éviter de répéter une expression complexe. Ce service décide de l'appariement ; il ne remplace pas l'autorisation métier et devrait éviter les effets de bord.

Où dans Symfony ?

AsRoutingConditionService, dans le namespace Routing\Attribute de FrameworkBundle, ajoute le tag prévu via l'autoconfiguration. Son alias devient le nom utilisé par service dans l'expression. L'instance doit également être enregistrée dans le container selon la configuration habituelle.

Comment, étape par étape ?

  1. Écrire un prédicat simple retournant bool.
  2. Exposer le service avec un alias explicite.
  3. Lui transmettre les données nécessaires depuis l'expression.
  4. Tester les cas vrai et faux ; un header client n'est pas une preuve d'identité.

Exemple concret PHP et YAML

Service applicatif autoconfiguré :

<?php
use Symfony\Bundle\FrameworkBundle\Routing\Attribute\AsRoutingConditionService;
use Symfony\Component\HttpFoundation\Request;

#[AsRoutingConditionService(alias: 'preview_selector')]
final class PreviewSelector
{
    public function matches(Request $request): bool
    {
        return '1' === $request->headers->get('X-Preview');
    }
}

Sur une route existante, la configuration de condition est :

condition: "service('preview_selector').matches(request)"

Contre-exemple : utiliser service avec n'importe quel identifiant du container, ou considérer X-Preview comme une permission. Correction : exposer explicitement le service et limiter cet exemple à une sélection de variante non sensible. Les contrôles d'accès restent séparés du matching.

Passage canonique conservé

Les variables disponibles

Variable Contenu
context le RequestContext : method, host, schéma, port
request l'object Request complet
params les parameters de route déjà appariés : "params['id'] < 1000"

FrameworkBundle ajoute deux functions : env('NOM') lit une variable d'environment, avec ses processeurs ; service('alias') appelle un service marqué #[AsRoutingConditionService] ou tagué routing.condition_service — sans alias, par son identifier. service() passe par un locator de ces seuls services : une condition n'atteint pas le reste du container. Un parameter de configuration s'écrit entre pourcents.

Une condition fausse efface la route

À retenir en priorité
  1. Une condition fausse retire la route des candidates.
  2. Sans autre correspondance, le résultat est 404.

Dans le matcher compilé, la condition est testée avant la barre finale, le schéma et la method. Une route dont la condition est fausse n'ajoute pas ses methods à la liste d'un 405, et ne déclenche aucun redirect de barre finale ou de schéma. Si rien d'autre ne correspond : 404.

La limite, et elle est importante

△ Piège à éviter

À retenir en priorité
  1. Le generator ne dispose pas du contexte de matching.
  2. Un lien généré peut viser une route qui ne correspondrait pas à la Request.

C'est quoi ?

Une condition de route est une expression évaluée pendant le matching. Si elle est fausse, cette route ne correspond pas. Elle n'est pas prise en compte par le générateur d'URL : une adresse peut donc être produite alors que la requête future échouera à cette condition.

À quoi ça sert ?

Une condition exprime un critère d'entrée que path, methods, host ou schemes ne couvrent pas directement. Elle ne doit pas devenir un substitut à l'autorisation métier : de nombreux critères de requête, tels que les headers envoyés par le client, sont contrôlables par celui-ci.

Où dans Symfony ?

L'expression dispose de context, le RequestContext ; request, la Request ; et params, les paramètres déjà extraits. Dans le matcher compilé, ExpressionLanguage produit du PHP qui sera exécuté lors de la recherche. Cela évite de reparcourir le texte de l'expression à chaque requête, mais n'annule pas le coût des fonctions ou services qu'elle appelle.

Comment, étape par étape ?

  1. Préférer une option native lorsqu'elle exprime directement le besoin.
  2. Écrire une condition courte et déterministe avec les données disponibles à ce stade.
  3. Tester le matching lorsque la condition est vraie puis fausse.
  4. Tester séparément la génération, sans conclure qu'une URL générée valide la condition.

Exemple concret YAML

Dans une application disposant du support ExpressionLanguage du routage :

small_report:
    path: /reports/{id}
    controller: App\Controller\ReportController::show
    requirements:
        id: '[0-9]+'
    condition: "params['id'] < 1000"

/reports/42 peut correspondre ; /reports/1000 échoue à cette condition. Pourtant la génération avec id égal à 1000 peut réussir, car son requirement numérique est satisfait. Contre-exemple : utiliser le lien généré comme preuve que la route acceptera toute visite. Correction : concevoir le parcours avec cette asymétrie explicite.

FrameworkBundle fournit aussi env et service dans cet environnement d'expression. service accède aux services de condition enregistrés pour cela, pas à tout le container. Éviter les effets de bord dans une condition : elle décide d'une correspondance et peut être évaluée avant qu'un controller soit choisi.

Passage canonique conservé

La limite, et elle est importante

Les conditions ne sont pas prises en compte lors de la génération d'URL.

Le generator ne connaît ni la Request ni le user agent : une route protégée par une condition reste générable, y compris vers un contexte où elle ne correspondrait pas. Une condition filtre l'entrée ; un requirement, lui, vaut dans les deux sens.

Une invitation peut imprimer une adresse même si une condition d'entrée refuserait son porteur. Le generator imprime le lien ; la condition reste une décision du matching, pas une règle d'authorization.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Une condition ne s'applique pas à la génération d'URL.

    Une condition ne s'applique pas à la génération d'URL. Une route protégée par une condition reste parfaitement générable, y compris vers un contexte où elle ne correspondrait pas.

  • Voir l’explication : Une condition filtre l'entrée ; elle ne documente pas l'output.

    Une condition filtre l'entrée ; elle ne documente pas l'output. C'est toute la différence avec un requirement de parameter, qui vaut dans les deux sens.

  • Voir l’explication : L'expression est compilée en PHP, pas interprétée à chaque Request.

    L'expression est compilée en PHP, pas interprétée à chaque Request. Elle est compilée une fois dans le cache du router ; seul le PHP qui en résulte s'exécute à chaque Request.

  • Voir l’explication : Condition fausse : pas de 405.

    Condition fausse : pas de 405. La route disparaît avant le contrôle de method.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • condition = ExpressionLanguage, compilée une fois en PHP.
  • Variables : context, request, params.
  • Functions : env(), service() (#[AsRoutingConditionService]).
  • Fausse → route effacée : pas de 405, pas de redirect, 404.
  • Vraie → les contrôles suivants (method, schéma) s'appliquent.
  • Ignorée à la génération d'URL.

Moyen mnémotechnique : « La condition filtre l'arrivée, jamais la génération ».
