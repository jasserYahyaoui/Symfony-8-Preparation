Objectif

Écrire une class user conforme à Symfony 8.0, et connaître le contrat minimal — plus court qu'on ne le croit.

L'essentiel

À comprendre

À retenir en priorité
  1. Le contrat user comporte deux methods.
  2. Le password relève d'une autre interface.

En 8.0, UserInterface n'a que deux methods. Le password vit dans une interface séparée. À chaque Request, le user rechargé est comparé à celui du token, et un compte suspendu se refuse dans un user checker, pas dans getRoles().

Le schéma

À retenir en priorité
  1. La relecture peut invalider le token.
  2. La comparaison détecte les changements importants.

Bleu : appels ; ambre : validations ; vert : issue. Le pointillé traverse deux requêtes via la session, pas via un appel direct. Vue du password et du refresh standard, hors pré-authentification ; le statut ou redirect d'échec dépend de l'authenticator. Un firewall lazy peut différer la restauration.

L'exemple

Exemple concret

À retenir en priorité
  1. ROLE_USER est une convention.
  2. Une identité sans role peut être authentifiée.
class User implements UserInterface, PasswordAuthenticatedUserInterface
{
    public function __construct(
        private string $email,
        private ?string $password,
        private array $roles = [],
    ) {}

    public function getUserIdentifier(): string { return $this->email; }        // pas l'id SQL
    public function getRoles(): array { return [...$this->roles, 'ROLE_USER']; } // convention
    public function getPassword(): ?string { return $this->password; }          // interface à part
}

Ce modèle stocke un hash, pas le mot de passe en clair. Il n'a pas de champ transitoire à exclure ; si le modèle en ajoute, définir une sérialisation qui l'omet et tester sa restauration. __serialize() contrôle les données persistées : il n'efface pas un secret déjà présent en mémoire.

`UserInterface`, en 8.0

À comprendre

À retenir en priorité
  1. Ne pas dépendre de l'ancien appel automatique.
  2. Écarter les données sensibles de la sérialisation.

C'est quoi ?

UserInterface décrit une identité utilisable par Security : son identifier et ses rôles. L'identifier sert à retrouver le user ; il n'est pas obligatoirement l'identifiant numérique d'une table.

À quoi ça sert ?

Le même contrat convient à une identité stockée en mémoire, dans un annuaire ou dans une base. Ne pas imposer de mot de passe dans ce contrat permet aussi les authentifications externes.

Où dans Symfony ?

En 8.0, les deux méthodes sont getUserIdentifier(): string et getRoles(): array. Le hash du mot de passe relève de PasswordAuthenticatedUserInterface::getPassword(): ?string. L'ancienne méthode eraseCredentials() a été retirée du contrat : ne pas dépendre de son appel automatique pour effacer une donnée sensible.

Comment, étape par étape ?

  1. Choisir un identifier stable pour la recherche d'authentication.
  2. Fournir les rôles directs ; ROLE_USER est une convention fréquente, pas une valeur ajoutée par l'interface.
  3. Implémenter séparément le contrat password si le mécanisme en utilise un. Ne pas conserver le mot de passe en clair sur le user sérialisé.
  4. Pour refuser un compte suspendu ou expiré, utiliser un user checker : checkPreAuth() vérifie avant les credentials, checkPostAuth() après leur vérification. Cela ne remplace pas l'autorisation sur chaque action ni le mécanisme de révocation des sessions existantes.

Exemple concret PHP

Identité minimale sans mot de passe ; dépend de Security Core 8.0 :

<?php
use Symfony\Component\Security\Core\User\UserInterface;

final class ReaderIdentity implements UserInterface
{
    public function __construct(private string $identifier) {}
    public function getUserIdentifier(): string { return $this->identifier; }
    public function getRoles(): array { return ['ROLE_READER']; }
}

Le provider peut retrouver cette identité par son identifier. L'exemple ne prétend pas l'authentifier : une preuve reste à vérifier par le mécanisme choisi. Contre-exemple : supprimer les rôles d'un compte suspendu en pensant empêcher sa connexion. Correction : refuser son état via un checker adapté ; les rôles concernent les droits. Lors d'une restauration de session, traiter aussi la fraîcheur de l'identité : un checker de connexion n'est pas une vérification automatique de chaque Request suivante.

Users et sécurité 8.0.

Passage canonique conservé
interface UserInterface
{
    public function getRoles(): array;
    public function getUserIdentifier(): string;
}
  • eraseCredentials() n'existe plus (dépréciée en 7.3, retirée en 8.0) ; le CHANGELOG renvoie à __serialize() pour écarter les données sensibles. Une class qui la déclare toujours ne casse rien, mais personne ne l'appelle.
  • getUserIdentifier() rend l'identifier de recherche — email, login —, celui que reçoit loadUserByIdentifier(), pas forcément la key primaire.

`getRoles()` : aucun minimum imposé

À retenir en priorité
  1. Le user fournit ses roles directs.
  2. La décision calcule les roles atteignables.

Ajouter ROLE_USER est une convention de la class, pas une exigence : un user dont getRoles() rend [] se connecte, IS_AUTHENTICATED_FULLY est vrai, mais isGranted('ROLE_USER') est faux.

Le password est une interface séparée

À retenir en priorité
  1. Un user peut exister sans password.
  2. Le contrat password reste séparé.

Un user peut ne pas avoir de password (token d'API, identité externe) : getPassword() vient de PasswordAuthenticatedUserInterface, l'interface que le hasher attend.

Comparer deux users

À retenir en priorité
  1. La comparaison personnalisée remplace la règle normale.
  2. Elle peut conserver un token malgré des données modifiées.

À chaque Request d'un firewall avec état, ContextListener::hasUserChanged() compare le user rechargé à celui du token : password, roles, identifier. Une différence abandonne le token. Une class EquatableInterface remplace cette règle par isEqualTo().

Class Changement Request suivante
ordinaire ROLE_EDITOR ajouté, ou password changé déconnectée
isEqualTo() ne comparant que l'identifier ROLE_EDITOR ajouté connectée, mais isGranted('ROLE_EDITOR') faux
la même password changé toujours connectée

Le token garde les roles de la connexion : c'est lui que les voters lisent.

Interdire un compte

À retenir en priorité
  1. Le statut du compte relève du user checker.
  2. Vider les roles n'empêche pas l'authentication.

Un compte suspendu ou expiré se refuse dans un user checker (UserCheckerInterface), déclaré par user_checker sur le firewall :

  • checkPreAuth() écoute CheckPassportEvent en priority 256, avant la vérification du password — il tourne même si le password est faux ;
  • checkPostAuth(UserInterface $user, ?TokenInterface $token = null) tourne après le succès ;
  • aucun des deux n'est appelé sur les Requests suivantes, portées par le cookie.

Piège à éviter

À retenir en priorité
  1. Le token garde les roles de la connexion.
  2. Une nouvelle authentication peut être nécessaire.

  • Voir l’explication : Un user sans role est authentifié

  • Voir l’explication : Les roles sont déjà comparés par défaut

Fiche express

À mémoriser

À retenir en priorité
  1. Le contrat porte sur la recherche d'identité.
  2. Un email ou login peut servir d'identifier.

Si tu dois retenir seulement 7 choses :

  • UserInterface : getRoles() et getUserIdentifier(), rien d'autre.
  • eraseCredentials() retirée ; __serialize() contrôle la persistance, mais n'efface pas un secret déjà présent en mémoire.
  • getPassword() : PasswordAuthenticatedUserInterface.
  • ROLE_USER : convention, pas obligation.
  • Comparaison par défaut : password, roles, identifier.
  • isEqualTo() remplace tout ; le token fige les roles.
  • User checker à la connexion : checkPreAuth() avant le password.

Moyen mnémotechnique : « Deux methods, trois comparaisons, un checker à la porte ».

UserInterface = getRoles + getUserIdentifier ; password = PasswordAuthenticatedUserInterface ;
hasUserChanged (password, roles, identifier) ou isEqualTo ; user checker : pre (CheckPassportEvent, 256), post
