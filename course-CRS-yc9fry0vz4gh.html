Objectif

Naviguer la hiérarchie Throwable et rattraper le bon type — sans rattraper trop.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Throwable couvre les deux branches.
  2. Placer les catch spécifiques avant le catch général.

Throwable est la racine, avec deux branches sœurs : Error, pour les problèmes de l'engine, et Exception, pour les conditions applicatives. Donc catch (Exception) laisse passer une Error ; seul Throwable attrape tout. Une class ne peut pas implémenter Throwable directement. Le premier catch compatible gagne, et finally s'exécute même après un return.

Le schéma

À retenir en priorité
  1. Error et Exception sont deux branches sœurs.
  2. ErrorException appartient à la branche Exception.

L'exemple

▣ Exemple concret

Revoir la règle : Error et Exception sont deux branches sœurs.

try {
    $result = intdiv(1, 0);
} catch (Exception $e) {
    // JAMAIS atteint : DivisionByZeroError est une Error, pas une Exception
} catch (DivisionByZeroError $e) {
    // atteint
} finally {
    // exécuté dans tous les cas, sauf exit()
}

La hiérarchie

○ À comprendre

Revoir la règle : Error et Exception sont deux branches sœurs.

C'est quoi ?

Throwable est l'interface commune aux objects que PHP peut lancer avec throw. Deux branches principales l'implémentent : Exception et Error. Error n'est pas une sous-class d'Exception. Depuis PHP 7, de nombreuses erreurs de l'engine sont des objects Error rattrapables, comme TypeError ou DivisionByZeroError.

ErrorException appartient malgré son nom à la branche Exception. Le nom d'une class ne suffit donc pas à trouver sa place dans la hiérarchie. Les warnings PHP ordinaires ne sont pas automatiquement des Throwable, et certaines erreurs de compilation empêchent le programme d'arriver jusqu'à son try.

À quoi ça sert ?

Deux circuits d'alarme rejoignent un même tableau central. Les circuits correspondent à Exception et Error, le tableau à Throwable. Surveiller un seul circuit ne surveille pas l'autre. Limite : un tableau ne capte pas une panne survenue avant son installation ; de même, un catch n'est pas une garantie de récupération de toutes les défaillances possibles du processus.

La distinction permet d'anticiper quel type de catch peut traiter un échec au lieu de choisir Exception par habitude pour tout problème.

Où dans Symfony ?

Le component HttpKernel expose le throwable d'un Symfony\Component\HttpKernel\Event\ExceptionEvent via getThrowable(). Ce nom reflète les deux branches PHP, même si l'événement s'appelle ExceptionEvent. L'ErrorHandler Symfony aide à présenter et traiter des erreurs, mais il ne change pas la parenté PHP entre Error et Exception.

Comment, étape par étape ?

  1. Identifier la class concrète de l'échec, par exemple DivisionByZeroError pour intdiv(1, 0).
  2. Remonter sa parenté : ici Error, puis le contrat Throwable, pas Exception.
  3. Choisir ensuite un traitement spécifique ou un traitement commun. L'ordre des blocs relève de la conséquence pratique.
  4. Ne pas étendre cette conclusion aux simples warnings ou à une syntaxe invalide dans le fichier qui doit installer le traitement.

Exemple concret PHP

Les trois booléens produits par la division sont true, true, false : l'object est un Throwable, une Error, mais pas une Exception. Le dernier booléen confirme qu'ErrorException est bien une Exception.

<?php
try {
    intdiv(1, 0);
} catch (Throwable $failure) {
    var_dump($failure instanceof Throwable);
    var_dump($failure instanceof Error);
    var_dump($failure instanceof Exception);
}

$convertedWarning = new ErrorException('Example warning');
var_dump($convertedWarning instanceof Exception);

Créer cet ErrorException est ici explicite ; aucun warning n'a été converti automatiquement. Référence : Throwable.

Passage canonique conservé

La hiérarchie

Depuis PHP 7, la plupart des erreurs fatales sont devenues des Error, donc rattrapables — mais elles ne descendent pas d'Exception. ErrorException, malgré son nom, est une Exception.

La conséquence pratique

△ Piège à éviter

Revoir la règle : Throwable couvre les deux branches.

C'est quoi ?

Quand un Throwable quitte un try, PHP examine les catch dans l'ordre et exécute le premier compatible. catch (Exception) ne traite pas la branche Error. catch (Throwable) accepte les deux branches, mais ne rend pas les blocs suivants exécutables pour le même object.

La hiérarchie définit la compatibilité ; l'ordre définit lequel des traitements compatibles est choisi. PHP ne cherche pas automatiquement le catch « le plus précis » parmi tous ceux écrits.

À quoi ça sert ?

À l'accueil d'un bâtiment, chaque visiteur entre dans la première file qui accepte son dossier. Une file « tous les dossiers » placée avant les guichets spécialisés détourne tout le monde. Les files correspondent aux catch, le dossier au throwable et les critères aux types. Limite : traiter un échec ne consiste pas nécessairement à le réparer ; le programme peut aussi le relancer pour un autre niveau.

On place les traitements spécifiques d'abord afin de conserver leur sens, puis un traitement général seulement à une frontière où l'on sait comment gérer l'échec.

Où dans Symfony ?

Un controller ou un service applicatif peut traiter une exception métier attendue et laisser remonter les problèmes inattendus. Le component HttpKernel dispose de sa propre gestion d'erreur autour de l'exécution. Ajouter partout un catch (Throwable) vide masquerait les défauts au lieu d'améliorer cette gestion.

Comment, étape par étape ?

  1. Lire le type lancé et sa hiérarchie.
  2. Parcourir les catch du haut vers le bas et s'arrêter au premier type compatible.
  3. Vérifier que ce bloc effectue une action utile : produire un résultat d'échec explicite, traduire ou relancer, plutôt que continuer avec une valeur fictive.
  4. Si aucun bloc ne convient, poursuivre le raisonnement dans l'appelant ; une Error n'est pas absorbée par un catch (Exception) inadapté.

Exemple concret PHP

Le premier essai affiche specific, car DivisionByZeroError est testé avant Throwable. Dans le second essai, le catch (Exception) intérieur ne convient pas ; l'échec atteint le catch (Throwable) extérieur, qui affiche outer. Aucun bloc silencieux n'est nécessaire.

<?php
try {
    intdiv(1, 0);
} catch (DivisionByZeroError) {
    echo "specific\n";
} catch (Throwable) {
    echo "general\n";
}

try {
    try {
        intdiv(1, 0);
    } catch (Exception) {
        echo "exception branch\n";
    }
} catch (Throwable) {
    echo "outer\n";
}

Référence : try et catch.

Passage canonique conservé

La conséquence pratique

catch (Exception $e) ne rattrape pas les Error. Pour tout attraper, il faut Throwable. Et l'ordre compte : le premier block compatible gagne, donc un catch (Throwable) placé en tête rend les suivants inatteignables.

Pensez à deux circuits d'alarme reliés au même panneau Throwable : surveiller uniquement Exception laisse passer Error. Le panneau commun ne rend pas les deux branches interchangeables.

Écrire ses propres exceptions

▣ Exemple concret

À retenir en priorité
  1. Une interface de marquage peut étendre Throwable.
  2. La class d'exception doit hériter d'Exception ou d'Error.

C'est quoi ?

Une exception applicative est une class qui donne un nom précis à une condition d'échec. Pour pouvoir la lancer, on hérite d'Exception ou d'une sous-class adaptée ; une class PHP ordinaire ne peut pas implémenter directement Throwable. Hériter d'Error est également possible, mais un échec métier est normalement modélisé dans la branche Exception.

Une interface de marquage peut, elle, étendre Throwable. Des classes d'exception issues de hiérarchies compatibles peuvent l'implémenter, et un catch sur cette interface les regroupe sans changer leur class parente.

À quoi ça sert ?

Des dossiers de services différents peuvent porter la même étiquette « incident de livraison ». Le dossier correspond à une exception concrète, le service d'origine à sa class parente, l'étiquette au marker interface. Limite : une étiquette seule ne transforme pas un object ordinaire en exception ; la class doit toujours hériter d'une base autorisée.

Un nom métier évite au client de reconnaître un échec en comparant des messages textuels fragiles. Le client peut traiter la catégorie annoncée et laisser les autres échecs remonter.

Où dans Symfony ?

Un service App\Service\Delivery peut lancer une exception applicative que son appelant traite. Le component HttpKernel n'a pas besoin d'une nouvelle hiérarchie PHP pour la voir comme Throwable. L'interface DeliveryFailure ci-dessous appartient à cet exemple : elle n'est pas présentée comme une interface Symfony existante.

Comment, étape par étape ?

  1. Nommer la condition d'échec, pas seulement la technique qui a échoué.
  2. Créer une class héritant d'Exception ; si plusieurs échecs doivent être groupés, déclarer d'abord un marker interface qui étend Throwable.
  3. Lancer l'exception avec un message utile, sans secret. Si elle traduit une autre exception, préserver cette cause dans previous.
  4. Traiter le type concret ou le marker interface à l'endroit où l'application sait décider de la suite. Relire les interfaces pour la distinction contrat et implémentation.

Exemple concret PHP

Deux classes différentes partagent le marker interface. catch (DeliveryFailure) reconnaît AddressUnavailable sans comparer son message. La sortie indique la class, le message et le fait qu'elle est aussi une Exception.

<?php
interface DeliveryFailure extends Throwable {}

final class AddressUnavailable extends Exception implements DeliveryFailure {}
final class ParcelRejected extends Exception implements DeliveryFailure {}

try {
    throw new AddressUnavailable('Destination unavailable');
} catch (DeliveryFailure $failure) {
    echo $failure::class, "\n";
    echo $failure->getMessage(), "\n";
    var_dump($failure instanceof Exception);
}

Référence : contrat Throwable.

Passage canonique conservé

Écrire ses propres exceptions

interface DomainFailure extends \Throwable {}
final class PaymentDeclined extends \RuntimeException implements DomainFailure {}

Une class ne peut pas implémenter Throwable directement : il faut étendre Exception ou Error. Une interface de marquage, elle, peut étendre Throwable, et catch (DomainFailure $e) rattrape alors toutes les exceptions qui l'implémentent, quelle que soit leur branche SPL.

Multi-catch et finally

△ Piège à éviter

À retenir en priorité
  1. finally s'exécute après return.
  2. exit() interrompt le script sans passer par finally.

C'est quoi ?

Un multi-catch comme catch (TypeError | ValueError $failure) partage le même traitement entre plusieurs types. Depuis PHP 8.0, on peut omettre la variable quand on n'a pas besoin de consulter l'object, par exemple catch (TypeError | ValueError).

Le bloc finally s'exécute quand on quitte le try ou un catch, y compris si un return a été demandé ou si une exception poursuit sa remontée. Un return dans finally remplace le retour précédent et peut même masquer une exception en cours : il faut donc éviter d'y décider du résultat métier. exit() termine le script sans exécuter ce finally.

À quoi ça sert ?

Après une réunion, on remet la salle en ordre, que la décision ait été positive ou négative. La réunion correspond au try, le traitement d'incident au catch, la remise en ordre au finally. Limite : une interruption du bâtiment ne permet pas de garantir cette remise en ordre ; exit() ou l'arrêt du processus ne suit pas le déroulement normal des blocs.

Le multi-catch évite de répéter un traitement identique. finally sépare ce traitement de la remise en état qui doit avoir lieu sur les différents chemins normaux de sortie.

Où dans Symfony ?

Une method de service peut employer finally pour remettre un indicateur temporaire dans son état initial, même si un appel échoue. Ce n'est pas un événement de fin de Request ni une API du kernel. La règle est appliquée par PHP à l'intérieur de cette method, avant que l'appelant Symfony reçoive le résultat ou l'exception.

Comment, étape par étape ?

  1. Regrouper dans un multi-catch seulement les types qui justifient le même traitement.
  2. Au moment d'un return, retenir la valeur calculée, puis exécuter le finally avant de quitter la function.
  3. Ne pas ajouter de return dans finally : il remplacerait la décision précédente au lieu de simplement nettoyer.
  4. Ne pas utiliser exit() comme équivalent de return ; il interrompt le script et saute ce nettoyage.

Exemple concret PHP

TypeError est traité par le multi-catch. Ensuite result() prépare le retour ready, mais affiche cleanup avant que l'appelant puisse afficher ce résultat. La sortie complète est invalid input, cleanup, puis ready.

<?php
try {
    strlen([]);
} catch (TypeError | ValueError) {
    echo "invalid input\n";
}

function result(): string
{
    try {
        return 'ready';
    } finally {
        echo "cleanup\n";
    }
}

echo result(), "\n";

Ce finally observe l'ordre d'exécution sans remplacer le retour. Référence : finally.

Passage canonique conservé

Multi-catch et finally

catch (TypeError | ValueError $e) unit des types ; depuis PHP 8.0, catch (\Throwable) s'écrit sans variable. Le block finally est exécuté après le try et les catch, y compris après un return — et un return dans le finally écrase celui du try. Il ne s'exécute pas après exit().

△ Piège à éviter

Revoir la règle : finally s'exécute après return.

Error n'étend pas Exception. Les deux implémentent Throwable, et c'est leur seul point commun dans la hiérarchie.

finally s'exécute même après un return dans le try — et un return dans le finally écrase celui du try. Pas après un exit(), en revanche : le script s'arrête sans passer par le finally.

L'ordre des catch compte : le premier block compatible gagne. Placer catch (Throwable) en premier rend les suivants inatteignables.
