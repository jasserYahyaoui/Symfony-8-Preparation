Objectif

Lire un security.yaml et savoir quelle section répond de quoi — et quelles erreurs d'ordre passent sans un message. Le détail de chaque section a son propre item.

L'essentiel

○ À comprendre

À retenir en priorité

  2. Leurs listes ne doivent pas être confondues.

security.yaml réunit cinq sections qui répondent chacune à une question. Deux d'entre elles, firewalls et access_control, appliquent la première entrée qui correspond — et une erreur d'ordre passe sans un message.

Le schéma

À retenir en priorité
  1. Un matcher général masque les suivants.
  2. Placer les cas précis en premier.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Les règles ne se cumulent pas.
  2. La règle générale peut rendre la restriction inaccessible.
security:
    password_hashers:                 # comment les passwords sont hachés
        App\Entity\User: { algorithm: auto }
    providers:                        # d'où viennent les users
        app_users:
            entity: { class: App\Entity\User, property: email }
    firewalls:                        # comment on s'authentifie
        dev:  { pattern: ^/(_profiler|_wdt)/, security: false }
        main: { lazy: true, provider: app_users, form_login: ~ }
    access_control:                   # ce qu'il faut pour entrer
        - { path: ^/admin, roles: ROLE_ADMIN }

Ce qui décide de quoi

○ À comprendre

À retenir en priorité
  1. Le provider charge l'identité.
  2. La hiérarchie définit des implications de roles.
  3. Le limiter combine username+IP et IP seule.
  4. L'intervalle d'exemple ne doit pas être confondu avec le défaut d'une minute.

C'est quoi ?

La configuration de sécurité assemble plusieurs décisions indépendantes. Une configuration YAML valide peut être incorrecte fonctionnellement : son ordre et ses associations de services comptent autant que sa syntaxe.

À quoi ça sert ?

Attribuer le symptôme au bon mécanisme évite de modifier un contrôle sans rapport avec le problème : un user introuvable relève du provider, pas d'une hiérarchie de rôles.

Où dans Symfony ?

  • password_hashers : calcul et vérification des hashes.
  • providers : chargement des users.
  • firewalls : mécanismes d'authentication pour une zone de Requests.
  • access_control : exigences pour une Request correspondante.
  • role_hierarchy : implications statiques entre rôles.

Comment, étape par étape ?

  1. Repérer le premier firewall correspondant : les suivants ne complètent pas sa configuration. Le cas général vient après les cas spécifiques.
  2. Vérifier son provider et ses authenticators.
  3. Repérer séparément la première règle access_control correspondante : les restrictions suivantes ne s'ajoutent pas.
  4. Examiner la configuration résolue, puis la réaction HTTP effective.

Cas dangereux à reconnaître, pas à reproduire : security: false désactive le traitement de sécurité du firewall sélectionné ; une règle d'accès située ailleurs ne le réactive pas. Ce n'est pas équivalent à rendre une seule URL publique avec PUBLIC_ACCESS. Ne pas utiliser cette désactivation pour résoudre un problème de connexion.

Exemple concret en shell

Commandes de diagnostic dans une application configurée, sans modifier ses règles :

php bin/console debug:config security
php bin/console debug:firewall main

La première montre les valeurs résolues, défauts compris ; la seconde examine le firewall nommé main. Contre-exemple : déplacer une règle restrictive après une règle générale puis penser qu'elle renforcera celle-ci. Correction : placer le cas spécifique avant le cas général et tester les deux chemins.

Enfin, expose_security_errors règle ce que le client apprend d'un échec : none par défaut, account_status pour les erreurs de statut du compte, y compris si checkPreAuth() les lève avant vérification des credentials, all pour davantage de détails. Distinguer protection contre l'énumération des comptes et diagnostic interne : ne pas exposer toutes les erreurs pour déboguer en production, ni supprimer les traces internes nécessaires. L'ancienne option hide_user_not_found n'est plus celle de Symfony 8.0.

Les deux règles d'ordre

À retenir en priorité
  1. Le firewall choisit l'authentication.
  2. La première règle d'accès impose ses exigences.
  • Dans firewalls, le premier pattern correspondant prend la Request.
  • Dans access_control, la première règle correspondante s'applique.

L'entrée la plus générale vient en dernier. Sinon, rien n'est signalé : main sans pattern déclaré avant api (^/api, stateless: true) prend /api/… et pose un cookie de session ; ^/rules en PUBLIC_ACCESS avant ^/rules/a en ROLE_ADMIN ouvre /rules/a à un anonyme.

`security: false` éteint tout

À retenir en priorité
  1. security: false coupe le traitement de sécurité.
  2. Une règle d'accès ne le réactive pas.

Un firewall security: false n'a aucun listener — ni authentication, ni AccessListener —, et SecurityExtension lui rend une liste vide. Une règle access_control sur ses URL est donc morte : avec un firewall free (^/free, security: false) et une règle ROLE_ADMIN sur ^/free, /free/page répond 200 à un anonyme. C'est l'usage du firewall dev.

Plusieurs providers

À retenir en priorité
  1. Plusieurs providers rendent le choix ambigu.
  2. Le firewall doit désigner son provider.

Dès qu'il y en a deux, chaque firewall doit nommer le sien, sinon InvalidConfigurationException : « … is ambiguous as there is more than one registered provider ».

Ce que l'échec révèle

À retenir en priorité
  1. Les erreurs sensibles sont masquées par défaut.
  2. La configuration contrôle leur exposition.

security.expose_security_errors — à la racine de security — règle ce que voit un client en échec ; hide_user_not_found n'existe plus en 8.0.

Valeur User inconnu Statut du compte (bloqué, expiré)
none (défaut) masqué masqué
account_status masqué non masqué, même si checkPreAuth() échoue avant vérification du password
all montré montré

Masqué veut dire remplacé par « Bad credentials. » : un user inconnu et un mauvais password donnent la même erreur. La default value, none, est lue dans MainConfiguration. Le tableau concerne les exceptions de statut ordinaires : CustomUserMessageAccountStatusException, explicitement destinée au user, n'est pas masquée même sous none. Le niveau d'exposition ne décale pas les contrôles : checkPreAuth() peut interrompre l'authentication avant le password. Pour réserver un contrôle de statut à une preuve déjà validée, le placer dans checkPostAuth(), après vérification effective des credentials. Le masquage du code Symfony 8.0 ne garantit pas à lui seul cette précondition.

  2. Vérifier le firewall effectivement choisi.

  • Voir l’explication : Un firewall security: false désactive aussi access_control

    Un firewall security: false désactive aussi access_control pour ses URL : aucun listener, aucune règle appliquée.

    Un firewall sans pattern déclaré en premier capte tout, sans erreur.

  • Provider explicite pour chaque firewall

    Plusieurs providers imposent de nommer celui de chaque firewall.

  • Voir l’explication : Par défaut, un user inconnu et un mauvais password donnent la même erreur

    Par défaut, un user inconnu et un mauvais password donnent la même erreur : expose_security_errors vaut none.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Employer l'option Symfony 8.0.
  2. Ne pas recopier une ancienne option supprimée.

Si tu dois retenir seulement 6 choses :

  • Cinq sections : hashers, providers, firewalls, access_control, role_hierarchy.
  • Firewalls : premier pattern ; access_control : première règle.
  • Le plus général en dernier ; une erreur d'ordre est silencieuse.
  • security: false : aucun listener, access_control mort.
  • Deux providers : nommer celui de chaque firewall.
  • expose_security_errors : none par défaut, « Bad credentials. ».

Moyen mnémotechnique : « Le premier qui correspond gagne, deux fois ».

hashers / providers / firewalls (1er pattern) / access_control (1re règle) / role_hierarchy ;
security: false = pas de listener ; 2 providers = provider explicite ; expose_security_errors: none
