Objectif

Le blog peut utiliser une intégration réutilisable dont les réglages doivent rester compréhensibles sans connaître tous les services internes. Le bundle fictif AcmeSocialBundle nous sert à suivre cette frontière : l'application choisit un délai et un identifiant ; le bundle contrôle ces options puis prépare les définitions. Nous n'ajoutons ici aucun protocole d'authentification sociale ni appel réseau.

L'essentiel

À comprendre

À retenir en priorité
  1. L'arbre valide la structure.
  2. L'extension configure les services.

La configuration sémantique décrit le sens des options, au-delà de leur syntaxe YAML : types, bornes, valeurs requises et défauts. Un arbre Config porte ces règles ; une extension exploite leur résultat pour préparer les définitions de services.

Dans une extension classique, load() reçoit des fragments et appelle leur traitement. Avec AbstractBundle, loadExtension() reçoit déjà le résultat traité. Ce travail appartient à la construction du container, pas à chaque utilisation de /blog/42. Le prepend ajoute des contributions avant la configuration applicative ; la fusion reste soumise aux règles de l'arbre cible.

Le schéma

À retenir en priorité
  1. La configuration est compilée.
  2. Elle ne dépend pas du user de la Request.

Partons de plusieurs fragments valides en YAML : ils ne constituent pas encore une configuration valide pour le bundle. Le diagramme distingue explicitement les deux APIs :

Orange : normalisation, fusion et validation ; rouge : refus ; vert : plan réutilisable. Si client_id est fourni et timeout omis, le résultat contient 30. Cette valeur sert ensuite à configurer un argument, sans instancier le client. Une extension peut effectuer des contrôles complémentaires : « l'arbre valide » ne signifie pas « l'extension ne peut jamais valider ». La réutilisation d'un container déjà construit ne rejoue pas ce traitement.

Le fil rouge : un `AcmeSocialBundle`

À retenir en priorité
  1. Une valeur par défaut rend l'omission possible.
  2. Une key requise doit être fournie.

Supposons le bundle enregistré dans l'application et son extension exposée sous acme_social. Son utilisateur écrit :

# config/packages/acme_social.yaml
acme_social:
    client_id: '%env(SOCIAL_CLIENT_ID)%'
    timeout: 10

Le délai choisi est 10, donc le défaut 30 ne doit pas l'écraser. SOCIAL_CLIENT_ID est une référence env, pas un secret inscrit dans ce document. Sa présence sous la clé requise satisfait la structure de configuration, mais ne prouve pas encore que la variable sera disponible au moment de sa résolution. Cette distinction évite de confondre validation de l'arbre et test de connexion à un fournisseur.

🌍 In Real Life

La situation : le restaurant commande un équipement avec un délai choisi et une référence de dossier à retrouver plus tard.

L’équivalent dans Symfony : délai demandé → timeout: 10 ; délai proposé faute de choix → défaut 30 ; référence de dossier → placeholder %env(SOCIAL_CLIENT_ID)%.

Retour à la réalité technique : la présence de la clé satisfait une exigence de structure, sans prouver que la variable sera disponible lors de sa résolution. La valeur explicite 10 n'est pas remplacée par le défaut. Aucun contrôle de connexion réseau n'est effectué par cette simple déclaration.

🧠 Comment le mémoriser : « Référence fournie, disponibilité à vérifier. » Image mentale : un numéro de dossier sans dossier encore ouvert. Question-réflexe : a-t-on validé la structure ou résolu et utilisé la valeur ?

⚠️ À ne pas confondre : référence env, secret écrit dans le document et authentification réussie.

Les deux moitiés : l'arbre et l'extension

À retenir en priorité
  1. Le traitement valide avant l'enregistrement.
  2. load() classique appelle processConfiguration() ; AbstractBundle::loadExtension() reçoit déjà le résultat traité.

Voici la méthode d'une classe Configuration implémentant Symfony\Component\Config\Definition\ConfigurationInterface, avec TreeBuilder importé depuis Symfony\Component\Config\Definition\Builder. Elle construit le contrat, pas un client :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function getConfigTreeBuilder(): TreeBuilder
{
    $tree = new TreeBuilder('acme_social');            // la key racine
    $tree->getRootNode()
        ->children()
            ->integerNode('timeout')->defaultValue(30)->min(1)->end()
            ->scalarNode('client_id')->isRequired()->end()
        ->end();

    return $tree;
}

timeout est entier, au moins égal à 1, et vaut 30 s'il manque. client_id doit être présent. Le scalarNode conservé ici n'impose pas à lui seul une string non vide : ce serait une règle supplémentaire, exprimable avec stringNode()->cannotBeEmpty().

Dans la méthode load(array $configs, ContainerBuilder $container) d'une extension classique dérivée d'Extension, l'étape essentielle est :

$config = $this->processConfiguration(new Configuration(), $configs);

Cette ligne suppose la classe Configuration précédente disponible. Avec les fragments [['client_id' => 'demo-client']], le résultat contient client_id = 'demo-client' et timeout = 30. Le Processor normalise les formes, fusionne selon l'arbre puis finalise et valide le résultat. load() ne reçoit donc pas automatiquement un array final déjà validé ; c'est la forme moderne suivante qui prend en charge cette étape avant loadExtension().

🌍 In Real Life

La situation : un formulaire précise les options autorisées ; après vérification, un préparateur en tire le plan d'équipement.

L’équivalent dans Symfony : règles du formulaire → arbre Config ; traitement des choix → normalisation, fusion et validation ; préparation du plan → extension enregistrant des définitions.

Retour à la réalité technique : l'arbre décrit types, bornes, défauts et présence. Dans l'extension classique, load() reçoit des fragments et appelle processConfiguration(). Avec AbstractBundle, loadExtension() reçoit déjà le résultat traité. Le scalarNode de cet exemple n'exige pas à lui seul une string non vide.

🧠 Comment le mémoriser : « Le formulaire fixe les règles, le préparateur exploite le résultat. » Image mentale : formulaire vérifié à côté du plan. Question-réflexe : ma méthode reçoit-elle des fragments ou une configuration déjà traitée ?

⚠️ À ne pas confondre : syntaxe YAML valide, configuration conforme et objet client instancié.

Une key inconnue est une erreur : ce que l'exécution montre

À retenir en priorité
  1. Une faute de key est une erreur.
  2. Le message peut proposer une correction.

Si l'application écrit timout, accepter silencieusement le fichier laisserait le délai réel à 30 alors que son auteur croit l'avoir réduit. Avec l'arbre présenté, le traitement refuse cette faute :

Configuration de l'application Résultat
timout: 5 InvalidConfigurationException : « Unrecognized option "timout" under "acme_social". Did you mean "timeout"? »
timeout: 0 « The value 0 is too small for path "acme_social.timeout"… »
aucune, client_id absent « The child config "client_id" under "acme_social" must be configured. »
client_id seul timeout vaut 30

Les quatre lignes représentent des essais indépendants. La suggestion du nom proche dépend des candidats trouvés ; le rejet de la clé inconnue ne promet pas toujours une suggestion. timeout: 0 est refusé, pas ramené à 1 ou remplacé par 30. Le défaut intervient quand la valeur manque, pas pour masquer une valeur invalide.

Pour le bundle actif dont l'extension est chargée, l'absence de fichier applicatif conduit encore au traitement d'une configuration vide : client_id requis manque alors. Un bundle non enregistré n'est pas magiquement chargé par son seul nom. Un arbre peut aussi choisir explicitement une politique différente, par exemple ignoreExtraKeys() ; ce n'est pas celle du laboratoire.

🌍 In Real Life

La situation : une fiche comporte une case inconnue ou un délai interdit ; le préparateur la renvoie au lieu de choisir silencieusement autre chose.

L’équivalent dans Symfony : case inconnue → timout ; valeur hors borne → timeout: 0 ; choix absent mais autorisé → application du défaut 30.

Retour à la réalité technique : avec cet arbre, une mauvaise clé ou valeur provoque InvalidConfigurationException. Le défaut comble une absence, pas une valeur invalide. Une suggestion orthographique n'est pas garantie. Un arbre configuré avec une autre politique peut traiter les clés supplémentaires autrement.

🧠 Comment le mémoriser : « Absent n'est pas invalide. » Image mentale : une case vide face à une case barrée. Question-réflexe : la valeur manque-t-elle ou viole-t-elle le contrat ?

⚠️ À ne pas confondre : validation et correction automatique ; min(1) ne transforme pas 0 en 1.

Requis ou par défaut, pas les deux

À retenir en priorité
  1. Requis et valeur par défaut se contredisent.
  2. L'arbre refuse cette définition.

L'auteur doit décider qui assume l'absence : l'application doit-elle fournir la valeur, ou le bundle propose-t-il un secours ? En Config 8.0, isRequired() et defaultValue() sur le même node se contredisent et lèvent InvalidDefinitionException dès la construction de l'arbre, quel que soit leur ordre. defaultNull() reste une valeur par défaut et ne contourne pas cette règle.

Pour comparer les responsabilités, avec l'autoload Config 8.0 chargé :

use Symfony\Component\Config\Definition\Builder\TreeBuilder;

$tree = new TreeBuilder('demo');
$tree->getRootNode()->children()
    ->stringNode('name')->isRequired()->cannotBeEmpty()->end()
    ->integerNode('timeout')->min(1)->defaultValue(30)->end()
->end();

name est à fournir et ne peut pas être vide ; timeout peut être omis. Cet extrait construit seulement l'arbre. Ajouter defaultValue('demo') à name produirait une erreur de définition, distincte d'une InvalidConfigurationException provoquée ensuite par une valeur applicative incorrecte. Inverser les appels ne change rien.

🌍 In Real Life

La situation : une case du formulaire dit à la fois « vous devez choisir » et « sans choix, nous déciderons » ; c'est le formulaire qui se contredit.

L’équivalent dans Symfony : obligation de choisir → isRequired() ; choix de secours → defaultValue() ; contradiction du formulaire → InvalidDefinitionException.

Retour à la réalité technique : Config 8.0 refuse ces deux règles sur le même node, quel que soit leur ordre. defaultNull() reste un défaut. Cette erreur de construction de l'arbre précède la validation des valeurs de l'application.

🧠 Comment le mémoriser : « Qui assume l'absence ? » Image mentale : deux consignes contradictoires sur une seule case. Question-réflexe : le problème vient-il du contrat ou d'une valeur qui le viole ?

⚠️ À ne pas confondre : InvalidDefinitionException et InvalidConfigurationException ; concevoir les règles et les respecter sont deux responsabilités.

La forme moderne : `AbstractBundle`, à la compilation

À retenir en priorité
  1. loadExtension() prépare le container.
  2. L'état utilisateur appartient à l'exécution.

La forme moderne regroupe ces points d'extension sur le bundle. Voici un laboratoire complet pour les deux hooks, avec un Client local qui ne fait que conserver ses arguments. Il renforce volontairement client_id en string non vide :

use Symfony\Component\Config\Definition\Configurator\DefinitionConfigurator;
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Loader\Configurator\ContainerConfigurator;
use Symfony\Component\HttpKernel\Bundle\AbstractBundle;

final class Client
{
    public function __construct(
        public readonly int $timeout,
        public readonly string $clientId,
    ) {}
}

class AcmeSocialBundle extends AbstractBundle
{
    public function configure(DefinitionConfigurator $definition): void
    {
        $definition->rootNode()->children()
            ->integerNode('timeout')->defaultValue(30)->min(1)->end()
            ->stringNode('client_id')->isRequired()->cannotBeEmpty()->end()
        ->end();
    }

    public function loadExtension(array $config, ContainerConfigurator $container, ContainerBuilder $builder): void
    {
        $container->services()->set('acme_social.client', Client::class)
            ->arg('$timeout', $config['timeout'])
            ->arg('$clientId', $config['client_id']);
    }
}

Avec les classes autoloadables, le bundle enregistré et client_id: 'demo-client', la définition préparée recevra 30 et 'demo-client' si timeout est omis. Un consommateur qui utilise ce service privé pourra obtenir l'objet ; aucun appel réseau n'est caché dans loadExtension().

Les hooks servent à construire le container. Ils ne constituent pas un emplacement pour choisir des services selon le lecteur courant : le résultat peut être réutilisé après cette exécution. Avec le nom et l'alias par défaut, AcmeSocialBundle expose acme_social. Un alias personnalisé est possible ; ne confondons pas cette racine de configuration avec un identifiant de service ou un namespace Twig.

🌍 In Real Life

La situation : un fournisseur propose un formulaire et le plan qui en découle dans le même dossier ; cela reste une préparation, pas un service à chaque table.

L’équivalent dans Symfony : formulaire → AbstractBundle::configure() ; plan issu des choix traités → loadExtension() ; équipement obtenu ensuite → service du conteneur.

Retour à la réalité technique : ces hooks participent à la construction du conteneur et enregistrent des définitions réutilisables. Ils ne doivent pas décider du câblage selon le lecteur courant. Ici, Client conserve simplement deux arguments ; son nom ne déclenche aucun réseau.

🧠 Comment le mémoriser : « Préparer le dossier n'exécute pas la commande. » Image mentale : un dossier de préparation fermé avant le service. Question-réflexe : suis-je en train de définir le service ou de l'utiliser ?

⚠️ À ne pas confondre : acme_social est une racine de configuration, pas l'identifiant acme_social.client.

Configurer un autre bundle : le prepend

À retenir en priorité
  1. Le prepend propose des réglages en amont.
  2. L'application conserve la surcharge finale.

Le bundle souhaite proposer un préfixe de cache sans l'imposer à l'application. Dans sa classe dérivée d'AbstractBundle, avec les imports précédents et FrameworkBundle disponible :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function prependExtension(ContainerConfigurator $container, ContainerBuilder $builder): void
{
    $container->extension('framework', ['cache' => ['prefix_seed' => 'foo/bar']], prepend: true);
}

Le résultat est une contribution framework.cache.prefix_seed = 'foo/bar' placée avant les réglages applicatifs. Ce hook n'écrit pas dans config/packages/ et ne crée pas une entrée de cache. Pour une même option scalaire remplaçable, l'ordre se lit ainsi :

Qui écrit la même key Qui gagne
un bundle (prepend) contre l'application l'application
deux bundles en prepend le premier enregistré : from-first

Si l'application fournit sa valeur, elle l'emporte sur ce secours. Si FirstBundle puis SecondBundle proposent respectivement from-first et from-second, les prepends successifs placent la contribution du premier plus tard dans la séquence à fusionner : from-first gagne en l'absence de choix applicatif. Les collections et les nodes aux règles de fusion particulières doivent être analysés selon leur arbre ; ce tableau n'est pas une loi universelle d'écrasement de tous les arrays.

Les templates sont une question distincte. Avec TwigBundle actif, les directories de templates reconnus pour AcmeSocialBundle sont enregistrés sous @AcmeSocial, sans ajouter ce prepend. Un template absent ne devient pas disponible grâce au seul namespace ; le dossier et le fichier doivent exister.

🌍 In Real Life

La situation : des fournisseurs glissent leurs propositions au début du dossier ; le choix final du restaurant reste inscrit plus loin.

L’équivalent dans Symfony : propositions antérieures → contributions prepend ; choix du restaurant → configuration applicative ; lecture du dossier → fusion selon l'arbre cible.

Retour à la réalité technique : pour le scalaire remplaçable illustré, l'application gagne. Deux prepends successifs placent la contribution du premier bundle plus tard dans la séquence à fusionner : elle gagne sans choix applicatif. Les collections peuvent obéir à d'autres règles. Le hook ne modifie aucun fichier et ne crée aucune entrée de cache.

🧠 Comment le mémoriser : « Reconstituer la pile avant de choisir le gagnant. » Image mentale : des feuillets ajoutés en tête, puis la décision applicative. Question-réflexe : quel est l'ordre de fusion et quelle règle applique ce node ?

⚠️ À ne pas confondre : proposer framework.cache.prefix_seed, stocker une donnée en cache et enregistrer le namespace Twig @AcmeSocial.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'absence de section ne supprime pas le contrat.
  2. Une key requise reste requise.
  • Voir l’explication : YAML valide ne signifie pas configuration conforme.

    YAML valide ne signifie pas configuration conforme. Notre arbre refuse timout ; la suggestion éventuelle aide à réparer le nom, sans désactiver la validation.

  • Voir l’explication : Le chargement prépare des définitions réutilisables.

    Le chargement prépare des définitions réutilisables. loadExtension() reçoit un résultat traité, contrairement au load() classique qui traite ses fragments. Aucun de ces hooks ne remplace une décision métier fondée sur la Request courante.

  • Voir l’explication : Le prepend propose un réglage avant celui de l'application.

    Le prepend propose un réglage avant celui de l'application. Pour notre scalaire remplaçable, l'application gagne, puis le premier bundle entre plusieurs prepends. Les règles de fusion du node restent actives.

  • Voir l’explication : Un bundle actif peut exiger une configuration même sans fichier dédié.

    Un bundle actif peut exiger une configuration même sans fichier dédié. Une configuration vide manque encore de client_id. La présence requise ne garantit ni une valeur non vide ni une variable env disponible.

  • Voir l’explication : Une erreur de définition précède les essais de configuration.

    Une erreur de définition précède les essais de configuration. Requis et défaut sur le même node sont incompatibles dans les deux ordres. Choisir un contrat cohérent vient avant tester les valeurs de l'application.

Fiche express

À mémoriser

À retenir en priorité
  1. Le nom du bundle détermine la racine.
  2. La forme snake_case sert dans la configuration.

Pour exposer un réglage stable au blog :

  1. Décrire types, bornes, présence et défauts dans un arbre cohérent.
  2. Distinguer erreurs de définition et valeurs applicatives invalides.
  3. Traiter les fragments dans l'extension classique, ou utiliser le résultat déjà traité de AbstractBundle::loadExtension().
  4. Enregistrer des définitions, sans confondre préparation et instanciation.
  5. Ne pas prendre la présence d'une référence env pour une connexion validée.
  6. Utiliser prepend comme contribution antérieure, selon les règles de fusion.
  7. Distinguer acme_social, acme_social.client et @AcmeSocial : racine de configuration, service et namespace de templates.

La configuration choisit ainsi le plan. Une factory peut maintenant prendre en charge une construction qui dépasse un simple appel de constructeur.
