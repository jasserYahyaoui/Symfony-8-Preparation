Objectif

Comprendre ce qui transforme framework: { … } en services : un arbre qui déclare et valide les keys, une extension qui les traduit en definitions. Savoir quand ce code s'exécute, pourquoi une key inconnue est une erreur, et comment un bundle configure un autre bundle sans priver l'application du dernier mot.

L'essentiel

À comprendre

À retenir en priorité
  1. L'arbre valide la structure.
  2. L'extension configure les services.

Un bundle a deux moitiés : un arbre qui déclare et valide ses keys, une extension qui traduit la configuration validée en services. Une key inconnue est une erreur. Le tout ne s'exécute qu'à la compilation. Et un bundle peut configurer un autre bundle par prepend, l'application gardant le dernier mot.

Le schéma

À retenir en priorité
  1. La configuration est compilée.
  2. Elle ne dépend pas du user de la Request.

Le fil rouge : un `AcmeSocialBundle`

À retenir en priorité
  1. Une valeur par défaut rend l'omission possible.
  2. Une key requise doit être fournie.
# config/packages/acme_social.yaml
acme_social:
    client_id: '%env(SOCIAL_CLIENT_ID)%'
    timeout: 10

Les deux moitiés : l'arbre et l'extension

À comprendre

À retenir en priorité
  1. Le traitement valide avant l'enregistrement.
  2. load() classique appelle processConfiguration() ; AbstractBundle::loadExtension() reçoit déjà le résultat traité.

C'est quoi ?

La configuration sémantique exprime des options de haut niveau, comme un délai, plutôt que les détails internes de chaque service. L'arbre de configuration définit les clés, types, contraintes et valeurs par défaut. L'extension utilise le résultat traité pour enregistrer ou configurer les services.

À quoi ça sert ?

Le bundle expose un contrat stable à son utilisateur et peut changer son assemblage interne sans lui demander de réécrire tous ses identifiants de services. Les fautes de configuration sont détectées avant le traitement des requêtes.

Où dans Symfony ?

ConfigurationInterface fournit un TreeBuilder. Dans la forme classique, l'extension appelle le traitement de la configuration avant d'utiliser son résultat : elle ne reçoit pas automatiquement un tableau déjà validé dans load(). Avec AbstractBundle::loadExtension(), le tableau reçu est déjà traité. Dans les deux formes, les règles de validation sont portées par l'arbre, pas par l'instanciation d'un client HTTP.

Comment, étape par étape ?

  1. Charger les fragments de configuration.
  2. Les normaliser pour rendre leurs formes cohérentes.
  3. Les fusionner selon les règles de l'arbre.
  4. Valider le résultat et appliquer les valeurs par défaut prévues.
  5. En déduire les définitions de services.

Exemple concret PHP

Ce fragment complet de classe nécessite Config 8.0 et son autoload ; il décrit un contrat sans construire de service.

<?php
use Symfony\Component\Config\Definition\Builder\TreeBuilder;
use Symfony\Component\Config\Definition\ConfigurationInterface;
final class Configuration implements ConfigurationInterface
{
    public function getConfigTreeBuilder(): TreeBuilder
    {
        $tree = new TreeBuilder('acme_social');
        $tree->getRootNode()->children()
            ->integerNode('timeout')->min(1)->defaultValue(30)->end()
            ->stringNode('client_id')->isRequired()->cannotBeEmpty()->end()
        ->end();
        return $tree;
    }
}

timeout peut être omis ; client_id doit être fourni et non vide. Contre-exemple : traiter directement le premier élément de $configs dans une extension classique. Les surcharges et valeurs par défaut peuvent être ignorées. Correction : faire traiter tous les fragments avec cet arbre, puis utiliser le résultat fusionné.

Les deux moitiés : l'arbre et l'extension

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function getConfigTreeBuilder(): TreeBuilder
{
    $tree = new TreeBuilder('acme_social');            // la key racine
    $tree->getRootNode()
        ->children()
            ->integerNode('timeout')->defaultValue(30)->min(1)->end()
            ->scalarNode('client_id')->isRequired()->end()
        ->end();

    return $tree;
}

L'arbre porté par ConfigurationInterface déclare types, contraintes et défauts. Dans une extension classique, load() reçoit les fragments et appelle processConfiguration() avant d'utiliser leur résultat : normalisation, fusion et validation, dont le défaut timeout=30. Dans AbstractBundle, loadExtension() reçoit déjà la configuration traitée. Les deux formes configurent ensuite les definitions de services.

Une key inconnue est une erreur : ce que l'exécution montre

À comprendre

À retenir en priorité
  1. Une faute de key est une erreur.
  2. Le message peut proposer une correction.

C'est quoi ?

Une clé inconnue est une option qui n'existe pas dans l'arbre déclaré. Par défaut, un arbre de clés définies la refuse. Ce contrôle est différent du contrôle de type, d'une borne numérique ou de la présence d'une option obligatoire.

À quoi ça sert ?

Refuser timout évite que l'utilisateur pense avoir réduit un délai alors que le bundle utilise silencieusement le défaut. Une configuration lisible par YAML peut rester invalide pour le bundle : la syntaxe du fichier et le sens des options sont deux validations distinctes.

Où dans Symfony ?

Le component Config signale une configuration invalide lors de son traitement. Un auteur peut explicitement autoriser des clés supplémentaires avec une règle comme ignoreExtraKeys() ; ce n'est pas le comportement à présumer pour l'arbre du fil rouge.

Comment, étape par étape ?

  1. Vérifier le nom de la racine attendue par le bundle.
  2. Comparer les clés aux enfants déclarés.
  3. Vérifier type et contraintes de chaque valeur.
  4. Ajouter les valeurs par défaut et vérifier les valeurs obligatoires absentes.

Exemple concret YAML

Pour l'arbre acme_social qui exige client_id non vide et timeout entier au moins égal à 1 :

acme_social:
    client_id: 'demo-client'
    timeout: 5

Cette configuration est conforme au contrat. Sans timeout, le défaut déclaré 30 est utilisé. Contre-exemples : timout: 5 est une clé inconnue ; timeout: 0 viole la borne ; retirer client_id viole l'obligation. Corrections : écrire timeout, choisir un entier positif et fournir l'identifiant. Ne pas supprimer la validation pour faire disparaître l'erreur : le message révèle précisément le contrat non respecté. Ces valeurs sont fictives et ne constituent aucun secret utilisable.

Passage canonique conservé

Une key inconnue est une erreur : ce que l'exécution montre

Configuration de l'application Résultat
timout: 5 InvalidConfigurationException : « Unrecognized option "timout" under "acme_social". Did you mean "timeout"? »
timeout: 0 « The value 0 is too small for path "acme_social.timeout"… »
aucune, client_id absent « The child config "client_id" under "acme_social" must be configured. »
client_id seul timeout vaut 30

L'extension traite une configuration vide même si l'application ne mentionne pas le bundle : un node isRequired() sans valeur fait échouer la compilation.

Requis ou par défaut, pas les deux

À comprendre

À retenir en priorité
  1. Requis et valeur par défaut se contredisent.
  2. L'arbre refuse cette définition.

C'est quoi ?

isRequired() impose que l'utilisateur fournisse une option. defaultValue() donne une valeur quand cette option manque. En Config 8.0, les deux intentions sont incompatibles sur le même nœud : la définition elle-même est invalide, avant de traiter la configuration d'une application.

À quoi ça sert ?

Cette séparation oblige l'auteur du bundle à décider qui assume le choix. Un identifiant propre à l'application peut être requis ; un délai raisonnable peut avoir un défaut. Une option obligatoire n'est pas nécessairement non vide : cannotBeEmpty() ajoute cette autre contrainte.

Où dans Symfony ?

NodeDefinition::defaultValue() et isRequired() vérifient chacun l'état opposé et lèvent InvalidDefinitionException. Inverser les appels ne contourne donc pas la règle. defaultNull() est aussi un défaut, pas une exception à cette incompatibilité.

Comment, étape par étape ?

  1. Décider si l'absence doit provoquer une erreur ou être compensée.
  2. Pour une erreur, utiliser isRequired() et les contraintes de valeur nécessaires.
  3. Pour une compensation, utiliser un défaut valide.
  4. Distinguer une mauvaise définition de l'arbre d'une mauvaise valeur fournie par l'utilisateur.

Exemple concret PHP

Avec l'autoload Config 8.0 chargé :

<?php
use Symfony\Component\Config\Definition\Builder\TreeBuilder;
$tree = new TreeBuilder('demo');
$tree->getRootNode()->children()
    ->stringNode('name')->isRequired()->cannotBeEmpty()->end()
    ->integerNode('timeout')->min(1)->defaultValue(30)->end()
->end();

name est à fournir ; timeout a un secours. Contre-exemple : ajouter ->defaultValue('demo') après ->isRequired() sur name. L'arbre devient contradictoire et lève une exception de définition. Correction : retirer soit le défaut, soit l'obligation selon le contrat voulu. Certains exemples documentaires historiques combinent les deux ; pour Symfony 8.0, le code taggé de Config tranche cette divergence.

Passage canonique conservé

Requis ou par défaut, pas les deux

En Config 8.0, isRequired() et defaultValue() (ou defaultNull()) sur un même node lèvent InvalidDefinitionException, « …cannot be required and have a default value », dans les deux ordres, dès la construction de l'arbre.

La forme moderne : `AbstractBundle`, à la compilation

À comprendre

À retenir en priorité
  1. loadExtension() prépare le container.
  2. L'état utilisateur appartient à l'exécution.

C'est quoi ?

AbstractBundle permet de regrouper la définition de configuration et le chargement des services dans la classe du bundle. configure() décrit l'arbre ; loadExtension() reçoit le tableau déjà normalisé, fusionné et validé.

À quoi ça sert ?

Cette forme réduit le nombre de classes nécessaires à un bundle simple sans confondre les responsabilités. Le bundle reste chargé de convertir une option publique en instructions de construction, pas d'exécuter le traitement métier pendant la compilation.

Où dans Symfony ?

Ces méthodes sont appelées lors de la compilation du container. Elles ne s'exécutent pas pour chaque requête. Elles ne doivent donc pas choisir un service en fonction de l'utilisateur HTTP courant : ce contexte n'est pas celui de la compilation.

Comment, étape par étape ?

  1. Activer le bundle dans l'application cible.
  2. Déclarer les options dans configure().
  3. Laisser Symfony traiter les fragments de configuration.
  4. Utiliser $config dans loadExtension() pour configurer les définitions.

Exemple concret PHP

Le service est ici un stdClass sans comportement ; sa propriété permet d'isoler le passage d'une option validée à une définition. L'exemple suppose HttpKernel, Config et DependencyInjection 8.0.

<?php
use Symfony\Component\Config\Definition\Configurator\DefinitionConfigurator;
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Loader\Configurator\ContainerConfigurator;
use Symfony\Component\HttpKernel\Bundle\AbstractBundle;
final class DemoBundle extends AbstractBundle
{
    public function configure(DefinitionConfigurator $definition): void
    {
        $definition->rootNode()->children()
            ->integerNode('timeout')->min(1)->defaultValue(30)->end()
        ->end();
    }
    public function loadExtension(array $config, ContainerConfigurator $container, ContainerBuilder $builder): void
    {
        $builder->register('demo.options', stdClass::class)
            ->setProperty('timeout', $config['timeout']);
    }
}

Sans surcharge, la définition reçoit 30. Aucun objet utilisateur n'est consulté. Contre-exemple : tenter de lire la requête courante pour choisir ce délai à la compilation. Correction : injecter un service qui prendra cette décision à l'exécution, ou utiliser une option de déploiement si le délai doit être fixe.

Passage canonique conservé

La forme moderne : AbstractBundle, à la compilation

class AcmeSocialBundle extends AbstractBundle
{
    public function configure(DefinitionConfigurator $definition): void { /* l'arbre */ }

    public function loadExtension(array $config, ContainerConfigurator $container, ContainerBuilder $builder): void
    {
        $container->services()->set('acme_social.client', Client::class)->arg('$timeout', $config['timeout']);
    }
}
  • configure() et loadExtension() ne tournent qu'à la compilation : ni Request, ni user.
  • La key racine découle du nom du bundle : AcmeSocialBundle → acme_social.

Configurer un autre bundle : le prepend

À comprendre

À retenir en priorité
  1. Le prepend propose des réglages en amont.
  2. L'application conserve la surcharge finale.

C'est quoi ?

Prepend signifie insérer une configuration avant celles déjà prévues pour une extension. Un bundle peut ainsi proposer des valeurs à un autre bundle sans imposer à chaque application de répéter ces réglages.

À quoi ça sert ?

Ce mécanisme convient aux valeurs d'intégration par défaut. Il ne doit pas servir à écraser arbitrairement la volonté de l'application : pour une même option scalaire surchargeable, sa configuration explicite est traitée après la proposition et peut l'emporter.

Où dans Symfony ?

Une extension classique implémente PrependExtensionInterface. Avec AbstractBundle, on utilise prependExtension(). ContainerBuilder::prependExtensionConfig() ajoute le fragment avant le chargement des extensions. La forme ContainerConfigurator::extension(..., prepend: true) exprime la même intention.

Comment, étape par étape ?

  1. Le bundle prépare un fragment conforme à l'arbre du bundle cible.
  2. Il l'insère avant les fragments applicatifs.
  3. Le bundle cible normalise, fusionne et valide l'ensemble.
  4. Le résultat final suit ses règles de fusion ; pour la clé scalaire montrée, l'application conserve le dernier choix explicite.

Exemple concret PHP

Dans une application qui active FrameworkBundle et ce bundle :

<?php
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Loader\Configurator\ContainerConfigurator;
use Symfony\Component\HttpKernel\Bundle\AbstractBundle;
final class DemoBundle extends AbstractBundle
{
    public function prependExtension(ContainerConfigurator $container, ContainerBuilder $builder): void
    {
        $builder->prependExtensionConfig('framework', [
            'cache' => ['prefix_seed' => 'demo/application'],
        ]);
    }
}

Le bundle propose un préfixe de cache ; une valeur applicative explicite peut le remplacer. Contre-exemple : annoncer que ce préfixe est imposé à toute application. Correction : le présenter comme un défaut d'intégration. Entre plusieurs bundles qui préfixent la même clé, le premier enregistré a la priorité ; ne pas déduire l'ordre final de l'ordre visuel des fichiers sans examiner leur chargement.

Passage canonique conservé

Configurer un autre bundle : le prepend

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function prependExtension(ContainerConfigurator $container, ContainerBuilder $builder): void
{
    $container->extension('framework', ['cache' => ['prefix_seed' => 'foo/bar']], prepend: true);
}
