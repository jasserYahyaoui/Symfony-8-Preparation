Objectifs d’apprentissage

Objectif

Situer HttpFoundation dans l'architecture : ce qu'il remplace, la place qu'il occupe sous le reste du framework, et ce qu'il fournit au-delà de Request et Response.

L'API de Request et de Response — les sacs, InputBag, les headers — est traitée dans le Module 02 — Fondamentaux HTTP ; leur emploi dans un controller, dans le Module 04 — Contrôleurs.

L'essentiel

○ À comprendre

À retenir en priorité
  1. HttpFoundation fonctionne sans le framework.
  2. Le kernel dépend de son vocabulaire Request et Response.

HttpFoundation remplace les superglobales PHP par des objects, Request et Response, qu'on peut fabriquer — d'où une pile HTTP testable. C'est un component autonome, et la brique la plus basse du framework : le kernel est écrit dans son vocabulaire. Il fournit aussi RequestStack, la seule façon pour un service de lire la Request en cours.

Le schéma

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.

L'exemple : un service qui lit la Request

▣ Exemple concret

final class LocaleReader
{
    public function __construct(private RequestStack $requestStack) {}

    public function locale(): ?string
    {
        return $this->requestStack->getCurrentRequest()?->getLocale();
    }
}

Ce qu'il remplace

À retenir en priorité
  1. Request représente les entrées HTTP.
  2. Response regroupe statut, headers et body.

En PHP nu, la Request est un ensemble de globales et la Response un effet de bord de header() et echo. Un object se fabrique : Request::create('/blog') produit une Request complète sans serveur web — impossible avec des superglobales. L'API des sacs et des headers relève du Module 02 — Fondamentaux HTTP.

Sa place

HttpFoundation s'installe dans n'importe quel projet PHP, sans le framework et sans dépendre d'un autre component Symfony. L'inverse n'est pas vrai : le contrat du kernel, handle(Request): Response, est écrit dans son vocabulaire.

Un service est construit une fois, la Request change à chaque appel : il reçoit RequestStack et appelle getCurrentRequest().

Les trois accessors, exactement

Accessor Résultat Pile vide
getCurrentRequest() dernière Request empilée null
getMainRequest() première Request null
getParentRequest() Request précédente null

Sur la main Request seule, getParentRequest() rend null. L'application laisse normalement le kernel gérer push() et pop(). Un service doit lire la Request courante plutôt que supposer qu'il traite toujours la principale. getSession() lève SessionNotFoundException si aucune session n'est disponible.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : On n'injecte jamais Request dans un service.

    On n'injecte jamais Request dans un service. Un service est construit une fois, la Request change à chaque appel : c'est RequestStack que l'on injecte, et getCurrentRequest() que l'on appelle.

  • Voir l’explication : La dependency va dans un seul sens.

    La dependency va dans un seul sens. HttpFoundation ne dépend d'aucun component Symfony ; c'est le framework qui dépend de lui, puisque le contrat du kernel est écrit dans son vocabulaire.

Application

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.
  3. HttpFoundation fonctionne sans le framework.
  4. Le kernel dépend de son vocabulaire Request et Response.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 5 choses :

  • Superglobales → objects fabricables : Request::create().
  • Component autonome ; le framework dépend de lui, pas l'inverse.
  • Service → RequestStack, jamais Request.
  • current = dernier, main = premier, parent = avant-dernier ; vide → null.
  • getSession() est le seul à lever.

Moyen mnémotechnique : « Pile, pas registre ».
