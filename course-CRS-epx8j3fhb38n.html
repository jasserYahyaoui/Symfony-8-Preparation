Objectif

Situer HttpFoundation dans l'architecture : ce qu'il remplace, la place qu'il occupe sous le reste du framework, et ce qu'il fournit au-delà de Request et Response.

L'API de Request et de Response — les sacs, InputBag, les headers — est traitée dans le Module 02 — Fondamentaux HTTP ; leur emploi dans un controller, dans le Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. HttpFoundation fonctionne sans le framework.
  2. Le kernel dépend de son vocabulaire Request et Response.

HttpFoundation remplace les superglobales PHP par des objects, Request et Response, qu'on peut fabriquer — d'où une pile HTTP testable. C'est un component autonome, et la brique la plus basse du framework : le kernel est écrit dans son vocabulaire. Il fournit aussi RequestStack, l'accès contextuel recommandé à la Request courante dans un service partagé.

Le schéma

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.

Rectangles bleus : états successifs de la pile ; capsules vertes : lectures. getMainRequest() rend main dans tous ces états. Le kernel gère push/pop : un service consulte la pile au moment utile, sans conserver la Request initiale dans son constructeur. Sur une pile vide, les accessors de requête rendent null.

L'exemple : un service qui lit la Request

Exemple concret

final class LocaleReader
{
    public function __construct(private RequestStack $requestStack) {}

    public function locale(): ?string
    {
        return $this->requestStack->getCurrentRequest()?->getLocale();
    }
}

Ce qu'il remplace

À comprendre

À retenir en priorité
  1. Request représente les entrées HTTP.
  2. Response regroupe statut, headers et body.

C'est quoi ?

HttpFoundation représente une demande HTTP par Request et son résultat par Response. Il fournit une couche objet à la place de lectures dispersées de superglobales et d'émissions directes avec header() ou echo.

À quoi ça sert ?

Un objet Request peut être construit pour un test sans serveur. Une Response peut être inspectée avant tout envoi. Les superglobales peuvent techniquement être modifiées dans un test, mais cela impose de gérer un état global partagé ; passer des objets explicites rend les entrées et sorties plus faciles à isoler.

Où dans Symfony ?

Le component ne choisit pas le controller et ne définit pas la logique métier. Il fournit le vocabulaire HTTP utilisé par HttpKernel et les controllers. Construire une Response n'émet ni headers ni contenu sur le réseau.

Comment, étape par étape ?

  1. Construire ou recevoir une Request.
  2. Lire l'origine précise de la donnée : query, body ou attributes.
  3. Produire une Response contenant statut, headers et contenu.
  4. Inspecter cet objet dans le test ; laisser le point d'entrée de l'application gérer l'émission réelle.

Exemple concret PHP

Avec l'autoload HttpFoundation 8.0 chargé, sans serveur :

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
$request = Request::create('/bonjour?name=Lea');
$response = new Response('Bonjour '.$request->query->get('name', 'visiteur'));
echo $response->getStatusCode(), ' ', $response->getContent(), "\n";

La sortie d'inspection attendue est 200 Bonjour Lea. Contre-exemple : dans une fonction censée retourner une réponse, écrire le contenu avec echo puis retourner une Response vide. Le contenu n'est plus représenté dans l'objet testé. Correction : placer le texte dans la Response. En rendu HTML réel, les données utilisateur doivent être échappées selon leur contexte ; cet exemple ne constitue pas un template HTML.

Passage canonique conservé

En PHP nu, la Request est un ensemble de globales et la Response un effet de bord de header() et echo. Un object se fabrique : Request::create('/blog') produit une Request complète sans serveur web, avec des entrées explicites. Les superglobales peuvent aussi être modifiées en test et lues par Request::createFromGlobals(), sans serveur ; il faut alors sauvegarder puis restaurer cet état global partagé pour isoler les tests. L'API des sacs et des headers relève du Module 02 — Fondamentaux HTTP.

Sa place

HttpFoundation s'installe dans n'importe quel projet PHP, sans le framework et sans dépendre d'un autre component Symfony. L'inverse n'est pas vrai : le contrat du kernel, handle(Request): Response, est écrit dans son vocabulaire.

Autonome signifie ici utilisable sans kernel ni bundles, pas sans dépendances Composer. Le paquet symfony/http-foundation 8.0 exige PHP 8.4 et déclare notamment le polyfill mbstring, une bibliothèque de compatibilité de fonctions. Avec son autoload chargé, ce programme construit un objet local, sans serveur ni accès réseau :

<?php
use Symfony\Component\HttpFoundation\Request;
$request = Request::create('https://example.test/catalogue?page=2');
echo $request->getPathInfo(), "\n";
echo $request->query->get('page'), "\n";

Il affiche /catalogue puis 2. Request::create() ne contacte pas cette adresse et ne lance pas le routage : un client HTTP émet une requête ; un kernel traite une Request. Charger le component, construire l'objet et inspecter ses entrées suffit ici ; ajouter l'orchestration est un choix séparé.

Un service partagé est réutilisé tant que son instance reste conservée dans ce container, tandis que la Request courante peut changer. Il reçoit donc RequestStack et appelle getCurrentRequest() au moment où il en a besoin ; un service non partagé n'a pas cette garantie de réutilisation.

Les trois accessors, exactement

À comprendre

C'est quoi ?

RequestStack représente les demandes actuellement imbriquées. getCurrentRequest() retourne la dernière empilée ; getMainRequest() la première ; getParentRequest() celle juste avant la courante. Une sous-requête peut donc être courante sans être principale.

À quoi ça sert ?

Un service partagé peut lire la Request du traitement en cours sans conserver celle qui existait à sa construction. Le parent sert à un besoin réellement lié à l'imbrication ; le consulter systématiquement rend un fragment dépendant de son appelant alors qu'il peut devoir fonctionner isolément.

Où dans Symfony ?

HttpKernel gère normalement les push() et pop(). En ligne de commande ou hors traitement HTTP, la pile peut être vide : les trois accesseurs retournent alors null. Avec une seule Request, le parent est également null. En revanche, getSession() peut lever une exception si aucune session n'est disponible ; tous les accesseurs n'ont pas la même politique d'absence.

Comment, étape par étape ?

  1. Empiler la demande principale.
  2. Pendant une sous-requête, empiler sa Request : elle devient courante.
  3. Lire séparément courante, principale et parent selon le besoin.
  4. Dépiler la sous-requête ; la principale redevient courante.

Exemple concret PHP

Ce laboratoire manipule explicitement la pile ; un service applicatif laisse normalement cette responsabilité au kernel.

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\RequestStack;
$stack = new RequestStack();
$stack->push(Request::create('/page'));
$stack->push(Request::create('/fragment'));
echo $stack->getCurrentRequest()?->getPathInfo(), "\n";
echo $stack->getMainRequest()?->getPathInfo(), "\n";
echo $stack->getParentRequest()?->getPathInfo(), "\n";
$stack->pop();
var_export($stack->getParentRequest());

On attend /fragment, /page, /page, puis NULL. Contre-exemple : utiliser sans contrôle le parent pour une demande principale. Correction : accepter son absence ou utiliser la courante si c'est réellement le contexte souhaité.

Passage canonique conservé
Accessor Résultat Pile vide
getCurrentRequest() dernière Request empilée null
getMainRequest() première Request null
getParentRequest() Request précédente null

Sur la main Request seule, getParentRequest() rend null. L'application laisse normalement le kernel gérer push() et pop(). Un service doit lire la Request courante plutôt que supposer qu'il traite toujours la principale. getSession() lève SessionNotFoundException si aucune session n'est disponible.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Ne pas figer la Request dans un service partagé.

    Ne pas figer la Request dans un service partagé. Injecter RequestStack, puis appeler getCurrentRequest() au moment utile suit les sous-requêtes et les changements de contexte. Passer explicitement une Request à une méthode reste valable ; ce n'est pas la même chose que l'autowirer au constructeur.

  • Voir l’explication : La dependency va dans un seul sens.

    La dependency va dans un seul sens. HttpFoundation ne dépend d'aucun component Symfony ; c'est le framework qui dépend de lui, puisque le contrat du kernel est écrit dans son vocabulaire.

Application

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.
  3. HttpFoundation fonctionne sans le framework.
  4. Le kernel dépend de son vocabulaire Request et Response.

Fiche express

À mémoriser

Si tu dois retenir seulement 5 choses :

  • Superglobales → objects fabricables : Request::create().
  • Component autonome ; le framework dépend de lui, pas l'inverse.
  • Service partagé : RequestStack pour lire le contexte courant ; passage explicite d'une Request à une méthode possible.
  • current = dernier, main = premier, parent = avant-dernier ; vide → null.
  • getSession() est le seul à lever.

Moyen mnémotechnique : « Pile, pas registre ».
