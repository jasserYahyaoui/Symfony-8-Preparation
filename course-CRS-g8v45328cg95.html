Objectif

Atteindre depuis un test les objects du framework — le container, un service, le kernel — et comprendre pourquoi le container de test n'est pas celui de production.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le TestContainer élargit l'accès pour les tests.
  2. Il ne recrée pas les services supprimés.

KernelTestCase démarre un kernel neuf à chaque test. static::getContainer() rend un container de test qui atteint aussi les services privés — sauf ceux supprimés à la compilation. Il permet de poser une doublure, à condition de le faire avant le premier get() du service qui en dépend.

Le schéma

À retenir en priorité
  1. La création du consommateur capture ses dependencies.
  2. Le remplacement doit précéder l'initialisation.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. La doublure contrôle le temps.
  2. Le service consommateur doit être construit ensuite.
class NewsletterGeneratorTest extends KernelTestCase
{
    public function testGenerate(): void
    {
        $container = static::getContainer();             // démarre le kernel
        $repository = $this->createMock(NewsRepositoryInterface::class);
        $container->set(NewsRepositoryInterface::class, $repository); // d'abord
        $generator = $container->get(NewsletterGenerator::class);     // ensuite
    }
}

Démarrer le kernel

À retenir en priorité
  1. Le test doit trouver la class du kernel.
  2. Une surcharge peut fournir cette décision.
  • Le kernel est désigné par la variable d'environment KERNEL_CLASS, posée dans .env.test ; une getKernelClass() ou createKernel() redéfinie l'emporte — la variable n'est alors plus lue.
  • bootKernel() rend le kernel démarré et accepte des options : self::bootKernel(['environment' => 'my_test_env', 'debug' => false]).
  • debug à false est recommandé en CI : plus de vidage automatique du cache, des tests nettement plus rapides — à charge de vider le cache soi-même.

Le container de test

○ À comprendre

À retenir en priorité
  1. Privé et supprimé ne sont pas synonymes.
  2. Un service supprimé n'est plus disponible.

C'est quoi ?

Le service container construit et relie les services. Le container spécial des tests donne accès aux services publics et aux services privés non supprimés lors de la compilation ; il ne recrée pas ce que cette compilation a éliminé.

À quoi ça sert ?

Un test d'intégration peut vérifier le service réellement câblé, ou remplacer une dependency externe par une doublure contrôlée. Cela teste une frontière différente de la simple construction manuelle d'un objet.

Où dans Symfony ?

KernelTestCase::bootKernel() démarre le kernel ; static::getContainer() fournit le container de test et peut démarrer le kernel si nécessaire. L'application doit désigner son kernel et activer framework.test. Depuis WebTestCase, créer le client démarre déjà le kernel.

Comment, étape par étape ?

  1. Démarrer l'environnement de test approprié.
  2. Récupérer le container spécial, pas seulement le container public du kernel.
  3. Installer une doublure avec set() avant que le service remplacé ou ses consommateurs soient initialisés.
  4. Récupérer ensuite le consommateur et vérifier le comportement. Les instances déjà construites ne changent pas rétroactivement leurs dependencies.

Exemple concret PHP

Dans une méthode d'un test KernelTestCase ; le paramètre du kernel est fourni par une application Symfony standard :

self::bootKernel();
$container = static::getContainer();
self::assertSame('test', $container->getParameter('kernel.environment'));

Le test confirme quel environment a réellement été démarré ; il ne mesure pas encore un comportement métier. Pour remplacer un service, l'ordre à respecter est set(dependency, double) puis get(consommateur), jamais l'inverse.

Contre-exemple : un service privé introuvable est rendu public dans toute l'application pour faire passer le test. Correction : vérifier d'abord s'il a été supprimé ou incorporé à un autre service ; si son exposition est nécessaire au test, la limiter à la configuration de test. Un service privé encore présent et un service supprimé ne sont pas le même cas. Une doublure doit respecter le contrat attendu ; elle ne doit pas désactiver la validation ou les autorisations que le test prétend vérifier.

Accès aux services en test 8.0.

Passage canonique conservé

Le container de test

static::getContainer() démarre le kernel s'il ne l'est pas, puis rend le service test.service_container, un TestContainer. Sans framework.test : LogicException, « Could not find service "test.service_container" ».

Trois services privés par défaut — Clock (utilisé par Greeter), son alias ClockInterface, et Unused (utilisé par personne) :

get() sur… Container de test Container du kernel
ClockInterface, Clock l'instance ServiceNotFoundException
Unused ServiceNotFoundException : « …has been removed or inlined when the container was compiled » idem

Le service privé ne devient pas public : c'est un autre container, branché sur le premier, qui y donne accès. Un service supprimé se rend public dans config/services_test.yaml.

Remplacer un service par une doublure

À retenir en priorité
  1. Le container conserve ses instances partagées.
  2. L'ordre d'installation de la doublure compte.

set() fonctionne sur ce container, y compris sur un alias privé, sans configuration. L'ordre compte :

Ordre Résultat
set(ClockInterface, double) puis get(Greeter) hello at fake
get(Greeter) puis set(ClockInterface, double) InvalidArgumentException : « …service is already initialized, you cannot replace it. »

Depuis un test d'application

À retenir en priorité
  1. Les deux accès visent l'intégration de test.
  2. La frontière de service reste commune.

$client->getContainer() rend test.service_container quand il existe — le même object que static::getContainer() — sinon le container du kernel. $client->getKernel() rend le kernel.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le helper gère l'initialisation nécessaire.
  2. Ne pas multiplier les boots sans raison.
  • Voir l’explication : static::getContainer() rend un container de test

    static::getContainer() rend un container de test, pas le container de production : les services privés y sont accessibles.

  • Voir l’explication : Un service privé supprimé reste inaccessible

    Un service privé supprimé reste inaccessible — il faut le rendre public dans config/services_test.yaml.

  • Voir l’explication : container->set() doit précéder get()

    container->set() doit précéder get() du service consommateur — après, c'est une exception.

  • Voir l’explication : getContainer() démarre le kernel

    getContainer() démarre le kernel s'il ne l'est pas.

  • Voir l’explication : KERNEL_CLASS désigne le kernel

    KERNEL_CLASS désigne le kernel ; getKernelClass() l'emporte sur elle.

  • Voir l’explication : Le kernel redémarre à chaque test

    Le kernel redémarre à chaque test, pas une fois par class — exécuté : deux tests, deux containers différents.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. L'état ne doit pas passer d'un test au suivant.
  2. Chaque test retrouve sa frontière d'isolation.

Si tu dois retenir seulement 7 choses :

  • KERNEL_CLASS désigne le kernel ; getKernelClass() l'emporte.
  • Le kernel redémarre à chaque test.
  • static::getContainer() démarre le kernel si besoin.
  • Il rend un TestContainer ; sans framework.test, LogicException.
  • Services privés accessibles, sauf supprimés à la compilation.
  • set() d'une doublure avant le get() du consommateur.
  • $client->getContainer() : le même container de test.

Moyen mnémotechnique : « Démarrer, atteindre, doubler avant ».

KERNEL_CLASS (getKernelClass() l'emporte) → kernel neuf par test ; getContainer() boote → TestContainer (framework.test) :
privés OK sauf supprimés (services_test.yaml) ; set() avant get(), sinon already initialized
