Objectif

Nommer un role correctement et connaître la seule règle que Symfony impose.

L'essentiel

À comprendre

À retenir en priorité
  1. Le voter natif reconnaît ce préfixe.
  2. Une autre convention demanderait un voter adapté.

Un rôle est une étiquette de permission portée par l'utilisateur, par exemple ROLE_EDITOR. Le voter de rôles standard reconnaît le préfixe ROLE_, sensible à la casse. D'autres attributes, comme EDIT sur un article, peuvent être traités par des voters applicatifs : ce ne sont pas des rôles standard mal nommés.

La hiérarchie évite de recopier les rôles hérités sur chaque compte. RoleHierarchyVoter calcule les rôles atteignables pour décider ; il ne réécrit pas le tableau retourné par $user->getRoles().

Le schéma

À retenir en priorité
  1. La hiérarchie est dirigée.
  2. La transitivité ne crée pas de relation inverse.

Bleu : voter ; gris et pointillés : configuration ; cylindres verts : données. Les flèches pleines décrivent le calcul de ce voter. La décision finale appartient à l'AccessDecisionManager, selon sa stratégie et les autres votes éventuels. Le graphe utilise exactement la hiérarchie de l'exemple, et non une relation spéciale attachée au mot ADMIN.

L'exemple

Exemple concret

À retenir en priorité
  1. Le user garde ses roles directs.
  2. Le voter applique la hiérarchie.
security:
    role_hierarchy:
        ROLE_EDITOR: ROLE_USER
        ROLE_ADMIN: [ROLE_EDITOR, ROLE_ALLOWED_TO_SWITCH]
$this->isGranted('ROLE_EDITOR');            // vrai pour un ROLE_ADMIN : hiérarchie
in_array('ROLE_EDITOR', $user->getRoles()); // faux pour le même user : la documentation dit BAD
$this->isGranted('IS_AUTHENTICATED_FULLY'); // un état de connexion, pas un role

La règle

À retenir en priorité
  1. La casse compte pour le voter natif.
  2. Les attributes métier suivent leurs propres voters.
  • Un role est une string libre qui commence par ROLE_ — « otherwise, things won't work as expected ».
  • RoleVoter reconnaît les attributes demandés qui commencent par ce préfixe. Pour isGranted('ROLE_ADMIN'), il refuse si le token ne contient que role_admin : les chaînes diffèrent. Pour isGranted('ADMIN'), il s'abstient car l'attribute n'est pas de son ressort. Un voter maison peut néanmoins traiter ADMIN ; toutes les abstentions donnent un refus avec la configuration par défaut.
  • Le code de la classe utilisateur peut ajouter ROLE_USER dans getRoles(). Le contrat UserInterface ne l'ajoute pas automatiquement.

La hiérarchie

À retenir en priorité
  1. Une recherche dans l'array ignore la hiérarchie.
  2. Le contrôle doit passer par les voters.
  • Un ROLE_ADMIN obtient ROLE_USER sans qu'on l'écrive sur le user ; la hiérarchie est transitive et ne remonte pas.
  • Elle est appliquée par le voter : isGranted('ROLE_USER') est vrai, in_array('ROLE_USER', $user->getRoles()) peut rester faux si le rôle n'y est pas explicitement retourné.
  • Avec role_hierarchy, le container remplace RoleVoter par RoleHierarchyVoter, qui l'étend et calcule les roles atteignables.
  • Les valeurs de role_hierarchy sont statiques ; pour une hiérarchie en base, la documentation recommande un voter — un service qui implémente RoleHierarchyInterface et décore security.role_hierarchy marche aussi.
  • php bin/console debug:security:role-hierarchy affiche la hiérarchie au format Mermaid (graph TB).

Les attributes qui ne sont pas des roles

À retenir en priorité
  1. L'attribute décrit l'état d'authentication.
  2. Il ne représente pas un role métier.

AuthenticatedVoter traite six attributes d'état de l'authentication :

Attribute Accordé quand
PUBLIC_ACCESS toujours, anonyme compris
IS_AUTHENTICATED un user est authentifié
IS_AUTHENTICATED_REMEMBERED authentifié, cookie « se souvenir de moi » compris
IS_AUTHENTICATED_FULLY authentifié dans cette session
IS_REMEMBERED authentifié par le cookie « se souvenir de moi »
IS_IMPERSONATOR le user en usurpe un autre

Ils s'emploient dans isGranted(), jamais dans getRoles().

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La configuration est statique.
  2. Une règle dynamique appartient au code d'autorisation.
  • Voir l’explication : Un attribute sans ROLE_ n'est pas traité comme un rôle par RoleVoter

    Un attribute sans ROLE_ n'est pas traité comme un rôle par RoleVoter ; ne pas confondre son abstention avec la décision de tous les autres voters.

  • Voir l’explication : in_array('ROLE_ADMIN', $user->getRoles()) ignore la hiérarchie.

    in_array('ROLE_ADMIN', $user->getRoles()) ignore la hiérarchie. La documentation marque cette ligne BAD et lui oppose isGranted('ROLE_ADMIN').

  • Voir l’explication : Les valeurs de role_hierarchy sont statiques

    Les valeurs de role_hierarchy sont statiques ; une hiérarchie en base demande du code — un voter, selon la documentation.

  • Voir l’explication : IS_AUTHENTICATED_FULLY n'est pas un role

    IS_AUTHENTICATED_FULLY n'est pas un role et n'a rien à faire dans getRoles().

Fiche express

À mémoriser

À retenir en priorité
  1. L'accès public n'exige pas d'identité.
  2. Il ne désactive pas le firewall entier.

Si tu dois retenir seulement 6 choses :

  • Un role commence par ROLE_, casse comprise.
  • Sans le préfixe : abstention du voter de rôles standard.
  • Hiérarchie transitive, appliquée par le voter (RoleHierarchyVoter).
  • in_array(…, getRoles()) ignore la hiérarchie : isGranted().
  • role_hierarchy statique ; en base : un voter.
  • IS_AUTHENTICATED_*, PUBLIC_ACCESS, IS_IMPERSONATOR : des états, pas des roles.

Moyen mnémotechnique : « ROLE_ devant, la hiérarchie dans le voter ».

role = ROLE_* (casse) ; RoleVoter → RoleHierarchyVoter si role_hierarchy (transitive, statique) ;
isGranted, pas in_array ; AuthenticatedVoter : PUBLIC_ACCESS, IS_AUTHENTICATED(_FULLY/_REMEMBERED), IS_REMEMBERED, IS_IMPERSONATOR
