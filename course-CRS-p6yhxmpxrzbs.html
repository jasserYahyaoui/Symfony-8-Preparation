Objectif

Mettre en cache une valeur coûteuse à calculer, et savoir pourquoi l'API de Symfony n'a pas de method pour écrire.

L'essentiel

À comprendre

À retenir en priorité
  1. La lecture et le calcul sont réunis.
  2. Le caller fournit la stratégie de reconstruction.

Le component Cache met des valeurs en cache dans le code. L'API recommandée, les Cache Contracts, n'a que get() et delete() : pas de set(), car get() reçoit un callable qui produit la valeur au manque. Le reste de la page répond à trois questions : quelle API, que fait get() au juste, et quel pool.

Le schéma

À retenir en priorité
  1. Le miss déclenche le calcul.
  2. La valeur retournée peut ensuite être réutilisée.

Bleu : opérations ; ambre : décisions ; vert : valeur retournée. Vue logique hors coordination du lock et pannes du stockage. Le callback doit supporter plusieurs exécutions : le cache n'est pas une garantie d'exécution métier unique.

L'exemple : un calcul coûteux

Exemple concret

À retenir en priorité
  1. Le pool applicatif contient les données métier mises en cache.
  2. Le pool système a une autre finalité.
  3. Les tags de cet exemple exigent TagAwareCacheInterface ; l'alias standard est cache.app.taggable, pas le pool cache.app non tag-aware.

Cet exemple reçoit explicitement un TagAwareCacheInterface. Le callable $compute représente le calcul métier fourni par l'appelant ; il doit retourner une string. La fonction conserve une valeur non vide pendant une heure et associe le tag reports. Une valeur vide est retournée mais non sauvegardée.

use Symfony\Contracts\Cache\ItemInterface;
use Symfony\Contracts\Cache\TagAwareCacheInterface;

function cachedReport(TagAwareCacheInterface $cache, callable $compute): string
{
    return $cache->get('my_cache_key', function (ItemInterface $item, bool &$save) use ($compute): string {
        $item->expiresAfter(3600);
        $item->tag(['reports']);
        $result = $compute();
        $save = '' !== $result;

        return $result;
    }, 0.0);
}

Avec un pool compatible, deux appels successifs réutilisent la valeur non vide ; $cache->invalidateTags(['reports']) impose un nouveau calcul au prochain appel. Le beta égal à zéro désactive ici le recalcul anticipé, pas la mémorisation. Dans la configuration standard de FrameworkBundle 8.0, l'autowiring de TagAwareCacheInterface fournit cache.app.taggable, qui enveloppe cache.app. L'alias de CacheInterface reste cache.app : son adapter filesystem standard n'est pas tag-aware. Appeler tag() sur cet item non taggable lève une LogicException. Une application peut remplacer ces alias : vérifier sa configuration effective plutôt que déduire la capacité des tags du nom du pool.

Trois API, une recommandée

À retenir en priorité
  1. Choisir l'API selon le contrat consommateur.
  2. Un stockage peut servir plusieurs abstractions.
  • les Cache Contracts — recommandés : moins de code, et protection contre la ruée par défaut ;
  • PSR-6 — pools et items, quand une bibliothèque tierce l'exige ;
  • PSR-16 — un cache « simple », sans object item.

Les adapters parlent à la fois les Cache Contracts et PSR-6 : on choisit l'API selon le contrat qu'attend le code consommateur.

Quatre mots

À retenir en priorité
  1. Le pool isole les keys.
  2. L'adapter choisit le mécanisme de stockage.
Terme Definition
Item une unité stockée : une key, une valeur
Pool un repository logique d'items ; toutes les opérations passent par lui
Adapter la class qui implémente le stockage réel — files, Redis…
Provider le service de connexion au stockage, notion propre au framework

Chaque pool du framework reçoit un namespace dérivé de son nom : deux pools ne se heurtent pas sur un stockage partagé.

L'API qui surprend

À comprendre

À retenir en priorité
  1. Un callback ne signifie pas toujours un miss.
  2. Le recalcul anticipé peut voir un hit.

C'est quoi ?

Un item associe une clé à une valeur ; un pool est leur espace logique ; l'adapter implémente le stockage ; le provider désigne notamment la connexion utilisée par certains stockages. Cache Contracts réunit lecture et reconstruction dans get().

À quoi ça sert ?

Le caller donne la clé et le calcul capable de reconstruire la valeur. Il n'a pas à dupliquer partout « lire, tester l'absence, calculer, sauvegarder ». Ce cache concerne des valeurs applicatives, pas directement des Responses HTTP.

Où dans Symfony ?

CacheInterface des Contracts est couramment relié à cache.app, destiné aux données applicatives. cache.system contient plutôt ce qui dérive du code et se prépare avec celui-ci. Leur finalité diffère ; changer d'adapter ne change pas cette distinction.

Comment, étape par étape ?

  1. Choisir une clé qui distingue les données nécessaires, notamment leurs variantes métier.
  2. Appeler get() avec le callback de calcul et fixer une expiration adaptée dans ce callback.
  3. Le callback s'exécute au manque, mais peut aussi participer à un recalcul anticipé : son exécution ne prouve pas toujours que l'item était absent.
  4. Pour invalider un ensemble logique, utiliser un pool tag-aware et ses tags ; toutes les implémentations PSR-6 ne possèdent pas cette capacité.

Exemple concret PHP

Exemple en mémoire, avec le component Cache installé ; aucun stockage externe :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;
use Symfony\Contracts\Cache\ItemInterface;

$cache = new ArrayAdapter();
$calls = 0;
$compute = static function (ItemInterface $item) use (&$calls): int {
    ++$calls;
    $item->expiresAfter(60);
    return 6 * 7;
};
$first = $cache->get('answer', $compute, 0.0);
$second = $cache->get('answer', $compute, 0.0);
var_dump($first, $second, $calls);

Les deux valeurs attendues sont 42 et le compteur vaut 1. Le paramètre beta égal à 0 désactive ici le recalcul anticipé, pas le cache ; il rend l'observation déterministe avant expiration. Contre-exemple : utiliser le callback pour envoyer un courriel en supposant qu'il ne s'exécutera qu'une seule fois. Correction : garder le calcul répétable ; expiration, invalidation ou recalcul peuvent le rappeler.

Pour des tags, appeler $item->tag() dans un pool compatible puis invalidateTags() avec le groupe concerné. Sans cette capacité, choisir une autre stratégie d'invalidation plutôt que supposer les tags universels. Si le callback emploie le paramètre $save pour empêcher une sauvegarde, celui-ci doit être reçu par référence.

Cache 8.0.

Passage canonique conservé
  • get() lit et écrit : la valeur et la façon de la produire sont déclarées au même endroit.
  • Le callable tourne au manque, et sur une key présente quand le recalcul anticipé l'élit ou que beta vaut INF ; $item->isHit() y rend alors true.
  • bool &$save, passé par référence : false empêche l'enregistrement.

La ruée sur le cache

À retenir en priorité
  1. Zéro ne désactive pas le cache.
  2. INF demande le calcul immédiatement.

Quand une key coûteuse expire, les Requests simultanées la recalculeraient toutes. Les Cache Contracts l'évitent sans configuration : un lock — un seul process par key et par machine — et une expiration anticipée probabiliste, où un user au hasard recalcule avant l'échéance pendant que les autres sont servis. Le beta, troisième parameter de get(), la règle : 1.0 par défaut, plus haut = plus tôt, 0 la désactive sans désactiver le cache, INF force le recalcul. Seul un item doté d'une échéance peut être élu en avance.

PSR-6 : écrire soi-même

À comprendre

À retenir en priorité
  1. L'item modifié reste local avant sauvegarde.
  2. save() réalise la persistance.

C'est quoi ?

PSR-6 sépare l'item de son pool : obtenir un item, modifier sa valeur et le sauvegarder sont des opérations distinctes. PSR-16 propose une interface plus directe à base de clés et valeurs. Ce sont des contrats d'accès, pas des types de stockage.

À quoi ça sert ?

Une bibliothèque peut demander un contrat particulier. Adapter l'interface évite de réécrire son code tout en gardant le même mécanisme de stockage lorsque l'adaptation convient.

Où dans Symfony ?

save() enregistre un item PSR-6. saveDeferred() permet une sauvegarde différée ; commit() demande de la réaliser. Le moment matériel exact peut dépendre de l'adapter : ne pas bâtir un test universel sur le seul fait qu'une écriture différée serait toujours invisible.

Comment, étape par étape ?

  1. Obtenir l'item et tester isHit() pour sa présence.
  2. Lire get() si présent ou calculer la valeur nécessaire.
  3. Employer set() puis save(), ou une sauvegarde différée suivie d'un commit explicite lorsque nécessaire.
  4. Choisir un bridge selon le consommateur : Psr16Cache expose PSR-16 à partir d'un pool PSR-6 ; Psr16Adapter expose un pool à partir d'un cache PSR-16.

Exemple concret PHP

Avec le component Cache, sans fichier ni serveur :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;

$pool = new ArrayAdapter();
$item = $pool->getItem('optional-result');
$item->set(null);
$pool->save($item);
$loaded = $pool->getItem('optional-result');
var_dump($loaded->isHit(), $loaded->get());

Le résultat est true, puis null. Contre-exemple : décider d'un manque avec $item->get() === null. Correction : utiliser isHit() ; null peut être une valeur volontairement stockée. De même, appeler seulement set() ne suffit pas à promettre une sauvegarde. En PSR-16, get($key, $default) donne le défaut en cas d'absence et has() distingue la présence ; cette vérification préalable ne constitue toutefois pas une transaction protégeant contre une modification concurrente.

API de cache 8.0.

Passage canonique conservé
Opération Effet
set('x') sans save() rien n'est stocké
set(null) puis save() isHit() vrai, get() rend null
saveDeferred() invisible d'un autre pool jusqu'au commit() ; le même pool le voit aussitôt
deleteItem('k') l'item disparaît

ArrayAdapter enregistre tout de suite : son saveDeferred() appelle save(). expiresAfter() et expiresAt() fixent l'échéance.

PSR-16 et les bridges

Exemple concret

À retenir en priorité
  1. null peut être une valeur valide.
  2. L'existence est une information distincte.

C'est quoi ?

Un bridge, ou adaptateur de contrat, présente une interface de cache à du code qui en attend une autre. Il ne transforme pas un stockage mémoire en stockage durable et ne donne pas automatiquement la capacité de gérer des tags.

À quoi ça sert ?

Une bibliothèque qui reçoit PSR-16 utilise get(), set() et des clés ; une autre peut attendre un pool PSR-6 et ses items. On choisit le sens de conversion d'après l'interface du consommateur, pas d'après la ressemblance du nom des classes.

Où dans Symfony ?

Psr16Cache reçoit un pool PSR-6 et expose PSR-16. Psr16Adapter reçoit un cache PSR-16 et expose un pool compatible PSR-6/Cache Contracts. Le défaut passé à get($key, $default) est réservé au manque ; une valeur null stockée est une valeur, pas ce défaut.

Comment, étape par étape ?

  1. Identifier le contrat déjà fourni et celui demandé par le code consommateur.
  2. Construire le bridge dans le bon sens, sans remplacer le stockage sous-jacent.
  3. Écrire une valeur puis vérifier présence et lecture ; distinguer un booléen de sauvegarde d'une valeur récupérée.
  4. Ne pas traiter une vérification has() puis get() comme une opération atomique face à d'autres processus.

Exemple concret PHP

Avec Cache 8.0, les interfaces PSR-6 et PSR-16 disponibles et l'autoload chargé ; seules des données en mémoire sont utilisées :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;
use Symfony\Component\Cache\Adapter\Psr16Adapter;
use Symfony\Component\Cache\Psr16Cache;

$pool = new ArrayAdapter();
$simple = new Psr16Cache($pool);
if (!$simple->set('optional', null, 60)) {
    throw new RuntimeException('Échec de sauvegarde.');
}
var_dump($simple->has('optional'));
var_dump($simple->get('optional', 'absent'));
var_dump($simple->get('missing', 'absent'));

$poolForAnotherConsumer = new Psr16Adapter($simple);
$item = $poolForAnotherConsumer->getItem('optional');
var_dump($item->isHit(), $item->get());

Les sorties attendues sont vrai, null, absent, puis vrai et null. Le dernier adaptateur est montré pour comparer les interfaces sur la même donnée ; empiler des bridges n'est pas nécessaire si le consommateur accepte déjà le pool initial.

Contre-exemple : passer un cache PSR-16 au constructeur Psr16Cache en pensant que son nom signifie « vers PSR-6 », ou tester seulement si get() est null pour détecter un manque. Correction : choisir Psr16Adapter dans ce sens et lire le contrat de présence approprié. Les interfaces PSR-16 sont un prérequis réel de ce snippet, pas une dependency installée par cette mission. Aucun backend externe ni support de tags n'est supposé.

Cache Symfony 8.0.

Passage canonique conservé

get('k', 'défaut') rend le défaut au manque ; has() distingue un null stocké d'une absence. Psr16Cache fait d'un pool PSR-6 un cache PSR-16 ; Psr16Adapter fait l'inverse, et parle aussi les Cache Contracts.

Les pools du framework

À retenir en priorité
  1. Le cache système suit le code déployé.
  2. Il n'est pas seulement un cache applicatif plus rapide.
  3. Le tag regroupe des items par préoccupation.
  4. L'invalidation par tag exige un pool tag-aware.
Pool Usage Adapter par défaut
cache.app données applicatives cache.adapter.filesystem
cache.system ce qui dérive du code source cache.adapter.system

cache.system se régénère au préchauffage et ne change qu'au deployment ; cache.adapter.system choisit le stockage : files PHP, chaînés derrière APCu quand il est là. Pour cache.app, Redis permet de survivre au deployment et de partager entre serveurs. Adapters : apcu, array, filesystem, memcached, psr6, redis, valkey.

Un pool compatible TagAwareCacheInterface associe des tags aux items dans le callback avec $item->tag(['products']). invalidateTags(['products']) invalide ensuite les items liés à cette préoccupation sans connaître chacune de leurs keys. Le pool doit être tag-aware ; les tags ne sont pas une propriété de toutes les implémentations PSR-6.

Piège à éviter

À retenir en priorité
  1. Le callback contrôle la sauvegarde.
  2. Le passage par référence est essentiel.
  • Voir l’explication : Il n'existe pas de set()

    Il n'existe pas de set() dans les Cache Contracts ; en PSR-6, set() sans save() n'écrit rien.

  • Voir l’explication : null n'est pas une absence

    null n'est pas une absence : isHit() en PSR-6, has() en PSR-16.

  • Voir l’explication : $save est passé par référence

    $save est passé par référence ; le mettre à false empêche l'enregistrement.

  • Voir l’explication : Le rappel ne tourne pas qu'au manque.

    Le rappel ne tourne pas qu'au manque. Exécuté : avec beta à INF, il tourne sur une key présente, et isHit() y rend true.

  • Voir l’explication : cache.system n'est pas un cache.app plus rapide

    cache.system n'est pas un cache.app plus rapide : il suppose des données dérivables du code source.

Fiche express

À mémoriser

À retenir en priorité
  1. La valeur et l'état de présence sont indépendants.
  2. Utiliser isHit() pour décider.

Si tu dois retenir seulement 7 choses :

  • Item, pool, adapter, provider ; un namespace par pool.
  • Cache Contracts : get() et delete(), pas de set().
  • Callable : au manque ou en avance ; &$save ; beta 0 = jamais en avance, INF = tout de suite.
  • PSR-6 : save() ; saveDeferred() + commit() pour les autres pools.
  • null n'est pas une absence : isHit(), has().
  • cache.app pour les données, cache.system pour le dérivé du code.
  • tag() + invalidateTags() (TagAwareCacheInterface).
