Objectif

Savoir comment un controller obtient la Request et où atterrissent les parameters de route. Le modèle des sacs appartient au Module 02 — Fondamentaux HTTP, le component lui-même au Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Le type déclenche le resolver.
  2. Dans un service durable, utiliser RequestStack.

Un controller obtient la Request en typant un argument ; un service, lui, reçoit RequestStack. Les parameters de route arrivent par $request->attributes, puis par le nom de l'argument. Pour le body, getPayload() est la method à connaître — et elle n'est pas symétrique : le form l'emporte sur le JSON.

Le schéma

L'exemple : une route à parameter

Exemple concret

class Example78ead211
{
    #[Route('/lucky/number/{max}')]
    public function number(Request $request, int $max): Response
    {
        $limit = $request->query->getInt('limit', 10);   // ?limit=5
        // ...
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

L'obtenir

À comprendre

C'est quoi ?

Request représente la requête traitée. RequestStack est la pile qui suit les requêtes actives, notamment lorsqu'une sous-Request est exécutée. Obtenir l'objet courant et conserver une référence prise lors de la construction d'un service sont deux opérations différentes.

À quoi ça sert ?

Dans une action, l'argument typé Request fournit directement le contexte HTTP. Dans un service partagé, consulter la pile au moment de l'appel évite de conserver une requête devenue obsolète ou d'exiger qu'une requête existe dès la construction du service.

Où dans Symfony ?

Importer Symfony\Component\HttpFoundation\Request. Le resolver utilise ce type, pas un nom imposé de variable. RequestStack.getCurrentRequest peut retourner null, par exemple hors HTTP ; getMainRequest vise la première requête, getParentRequest la précédente. Choisir la principale systématiquement ignorerait le contexte d'une sous-Request.

Comment, étape par étape ?

  1. Dans l'action, typer l'argument Request.
  2. Dans un service, injecter RequestStack.
  3. Lire la Request au moment du besoin.
  4. Définir explicitement le comportement sans requête : résultat facultatif si le besoin l'est, sinon erreur contextualisée.

Exemple concret PHP

Service dont le contrat exige une requête active :

<?php
use Symfony\Component\HttpFoundation\RequestStack;

final class CurrentPath
{
    public function __construct(private RequestStack $requests) {}
    public function get(): string
    {
        $request = $this->requests->getCurrentRequest();
        if (null === $request) {
            throw new \LogicException('Un contexte HTTP est requis pour lire le chemin.');
        }
        return $request->getPathInfo();
    }
}

Contre-exemple : mémoriser getCurrentRequest dans le constructeur puis l'utiliser pendant toutes les opérations. Correction : conserver la pile et la consulter à chaque appel ; le contexte peut changer entre deux traitements.

Passage canonique conservé

L'obtenir

Typer un argument avec Symfony\Component\HttpFoundation\Request suffit : le type déclenche l'injection, le nom est libre. Dans un service, construit une fois pour toutes, on injecte RequestStack : getCurrentRequest() rend la sub-Request si on est dedans, getMainRequest() celle du serveur, getParentRequest() null quand la courante est la principale, et getSession() lève une SessionNotFoundException au lieu de rendre null.

Les parameters de route

À comprendre

À retenir en priorité
  1. Réordonner les arguments ne change pas la correspondance.
  2. Renommer un argument impose de vérifier le parameter de route.

C'est quoi ?

Un paramètre extrait du chemin est ajouté aux attributes de Request. Le resolver d'arguments y cherche une clé portant le nom du paramètre de l'action. Cette correspondance par nom ne signifie pas que tous les sacs de Request sont fusionnés.

À quoi ça sert ?

L'action reçoit les données utiles sans analyser elle-même le chemin. Réordonner ses paramètres ne change pas cette correspondance ; renommer l'un d'eux change en revanche la clé recherchée.

Où dans Symfony ?

Les attributes contiennent aussi _route, nom de la route reconnue, et _controller, désignation du callable. Ce sont des informations de traitement ; query contient les données après le point d'interrogation. Le kernel prépare ensuite la liste d'arguments à appeler : il ne faut pas confondre cette résolution avec la syntaxe des arguments nommés écrite par un développeur PHP.

Comment, étape par étape ?

  1. Déclarer le nom du paramètre dans le path.
  2. Employer le même nom dans la signature.
  3. Lire les métadonnées internes dans attributes si nécessaire.
  4. Traiter séparément la query string, même si une clé y porte le même nom.

Exemple concret PHP

Dans un controller enregistré et découvert par le loader d'attributes :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[\Symfony\Component\Routing\Attribute\Route('/articles/{slug}', name: 'article_show')]
public function show(string $slug, \Symfony\Component\HttpFoundation\Request $http): \Symfony\Component\HttpFoundation\JsonResponse
{
    return new \Symfony\Component\HttpFoundation\JsonResponse([
        'slug' => $slug,
        'route' => $http->attributes->get('_route'),
    ]);
}

/articles/guide?slug=autre fournit guide à l'argument et article_show comme route. Contre-exemple : renommer seulement slug en title et attendre la même injection. Correction : aligner le nom de route et celui du paramètre, ou fournir une stratégie de résolution explicite.

Passage canonique conservé

Les parameters de route

Un parameter du path est déposé dans $request->attributes, puis passé au controller comme named argument : la correspondance se fait sur le nom, jamais sur la position. Réordonner les arguments ne change rien ; en renommer un casse tout. attributes porte aussi _route et _controller.

Les parameters de route sont des notes agrafées au dossier par le bureau de routing. Les chercher dans query revient à ouvrir le tiroir des informations de l'URL après le point d'interrogation : ce n'est pas la même origine.

Body et query string

À comprendre

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.

C'est quoi ?

Une Request sépare plusieurs sources de données. query contient la query string, partie après le point d'interrogation ; request les paramètres de formulaire analysés ; attributes les informations ajoutées au traitement, notamment par le routage ; files les fichiers téléversés. Le body est le contenu brut de la requête, qui peut être du JSON plutôt qu'un formulaire.

À quoi ça sert ?

Choisir le bon sac évite de lire une valeur homonyme provenant d'une autre source. Un paramètre de route n'est pas automatiquement une clé de query, et un body JSON n'alimente pas automatiquement le sac request comme un formulaire traditionnel.

Où dans Symfony ?

Dans une action, un argument typé Request peut être résolu quel que soit son nom. Dans un service, RequestStack permet de consulter la Request courante au moment de l'appel, qui peut être une sous-Request ; getMainRequest() vise la principale. Les arguments issus de la route sont résolus d'après leur nom, pas leur position dans la signature.

Comment, étape par étape ?

  1. Déterminer le contrat d'entrée : chemin, query string, formulaire ou JSON.
  2. Lire le sac correspondant.
  3. Pour getPayload(), retenir la priorité : sac request non vide, sinon body vide, sinon décodage JSON en tableau PHP.
  4. Traiter un JSON mal formé ou une valeur scalaire JSON comme une erreur, pas comme un formulaire vide. Cette méthode n'effectue pas la validation métier des champs.

Exemple concret PHP

Exemple isolable avec HttpFoundation chargé :

<?php
use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/search?q=Symfony', 'POST', content: '{"page":2}');
var_dump($request->query->get('q'));
var_dump($request->getPayload()->get('page'));

On attend la chaîne Symfony, puis l'entier 2. Contre-exemple : lire $request->request->get('page') en supposant que tout POST est un formulaire. Correction : utiliser le payload selon le contrat d'entrée. Si request contient déjà des paramètres, getPayload() en retourne un clone et ne fusionne pas le JSON avec eux ; modifier ce clone ne modifie pas le sac original.

Passage canonique conservé

Body et query string

$request->query porte la query string. getPayload() procède dans cet ordre : si $request->request n'est pas vide, elle rend un clone de ce sac — le form l'emporte, le JSON n'est pas lu ; sinon, un body vide donne un InputBag vide ; sinon le body est décodé en JSON. Un JSON mal formé lève une JsonException, comme un JSON valide qui ne décode pas en array.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Les parameters de route s'apparient par leur nom, jamais par leur position.

    Les parameters de route s'apparient par leur nom, jamais par leur position. Réordonner les arguments du controller ne casse rien ; en renommer un casse tout.

  • Voir l’explication : La Request ne s'injecte pas dans un service.

    La Request ne s'injecte pas dans un service. Typer un argument suffit dans un controller, mais un service est construit une fois pour toutes : il reçoit RequestStack.

  • Voir l’explication : getPayload() ne fusionne pas form et JSON.

    getPayload() ne fusionne pas form et JSON. Si le sac des parameters de form n'est pas vide, elle rend celui-là et ne regarde même pas le body brut.

  • Voir l’explication : Un body JSON invalide ne donne pas un sac vide

    Un body JSON invalide ne donne pas un sac vide : il lève une exception. Le sac vide est réservé au cas où le body est vide.

  • Voir l’explication : getPayload() rend un clone.

    getPayload() rend un clone. Écrire dans l'object retourné ne change rien à la Request.

Application

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.
  3. Le type déclenche le resolver.
  4. Dans un service durable, utiliser RequestStack.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Controller : typer Request ; service : RequestStack.
  • Parameters de route : attributes, puis le nom de l'argument.
  • _route et _controller sont dans attributes.
  • getPayload() : form d'abord, en clone ; body vide → sac vide.
  • JSON invalide ou pas un array → JsonException.
  • getSession() de RequestStack lève au lieu de rendre null.

Moyen mnémotechnique : « Le nom, pas la place ».
