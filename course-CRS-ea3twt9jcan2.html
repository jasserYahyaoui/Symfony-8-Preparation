Objectif

Sur GET /blog/42?limit=5, le routage a reconnu /blog/{id}. Le contrôleur va recevoir des valeurs provenant de lieux différents : l'identifiant du chemin, la limite de la query string et la Request elle-même. Les distinguer évite de chercher un paramètre dans le mauvais sac ou dans le conteneur.

Savoir comment un controller obtient la Request et où atterrissent les parameters de route. Le modèle des sacs appartient au Module 02 — Fondamentaux HTTP, le component lui-même au Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Le type déclenche le resolver.
  2. Dans un service durable, utiliser RequestStack.

Un controller obtient la Request en typant un argument ; un service, lui, reçoit RequestStack. Les parameters de route arrivent par $request->attributes, puis par le nom de l'argument. Pour le body, getPayload() est la method à connaître — et elle n'est pas symétrique : le form l'emporte sur le JSON.

Le schéma

Bleu = données retournées ; ambre = sélection ordonnée. Le JSON {} ou [] donne aussi un bag vide : « vide » ne signifie pas nécessairement « aucun body ». Dans un service, consulter la pile au moment de l'opération, plutôt que mémoriser la Request dans le constructeur ; hors HTTP, la pile peut être vide.

L'exemple : une route à parameter

Exemple concret

Le petit endpoint suivant isole ce mécanisme sans charger d'article. Pour /lucky/number/42?limit=5, le résultat attendu est max=42, limit=5 : $max vient des attributs de route, mais $limit est lu explicitement dans query. La route ne mappe pas automatiquement tous les paramètres de query string vers les arguments.

use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LuckyController
{
    #[Route('/lucky/number/{max}', requirements: ['max' => '\d+'])]
    public function number(Request $request, int $max): Response
    {
        $limit = $request->query->getInt('limit', 10);   // ?limit=5
        return new Response(sprintf('max=%d, limit=%d', $max, $limit));
    }
}

🌍 In Real Life

La situation : le bon porte le numéro demandé et une note complémentaire. Lire le numéro ne revient pas à lire toutes les notes.

L’équivalent dans Symfony : numéro extrait de la destination → {max} dans les attributes ; note après ? → limit dans query ; lecture explicite de la note → query->getInt('limit', 10).

Retour à la réalité technique : pour /lucky/number/42?limit=5, les deux valeurs viennent de sources distinctes. Le requirement \d+ contraint le matching du segment ; il ne mappe pas la query string, ne valide pas toutes les règles métier et ne charge aucune donnée du blog.

🧠 Comment le mémoriser : « Même URL, tiroirs différents. » Image mentale : numéro et note dans deux cases du bon. Question-réflexe : « Cette valeur vient-elle du chemin reconnu ou de la query string ? »

⚠️ À ne pas confondre : obtenir un entier ne garantit pas qu’il soit acceptable pour le métier.

L'obtenir

Dans le câblage standard, le RequestValueResolver reconnaît un argument typé Symfony\Component\HttpFoundation\Request et fournit la requête traitée : le nom est libre. C'est de la résolution d'argument, pas la construction d'un service Request par autowiring.

Un service qui doit consulter le contexte HTTP reçoit plutôt RequestStack. Les services sont partagés par défaut dans leur conteneur, mais leur durée de vie n'est pas universellement « une fois pour toutes » : elle dépend du conteneur et de la configuration. Consulter la pile au moment de l'opération évite de figer une ancienne requête. getCurrentRequest() rend la sub-Request si on est dedans, getMainRequest() celle du serveur, getParentRequest() null quand la courante est la principale, et getSession() lève une SessionNotFoundException au lieu de rendre null.

🌍 In Real Life

La situation : un poste reçoit le bon traité ; un autre consulte le porte-bons au moment utile. Garder la première fiche toute la journée risquerait de conserver une ancienne demande.

L’équivalent dans Symfony : bon remis à l’action → RequestValueResolver fournit la Request ; porte-bons consultable → service RequestStack ; fiche au sommet → requête courante, éventuellement une sous-requête.

Retour à la réalité technique : la pile décrit un contexte changeant, pas une file de tâches. Elle peut être vide ; la principale et la parente ne sont pas toujours la courante. Une Request d’action est résolue pour l’appel, non construite comme service applicatif par autowiring.

🧠 Comment le mémoriser : « Consulter maintenant, ne pas figer hier. » Image mentale : fiche du dessus qui change. Question-réflexe : « Ai-je besoin de la requête courante, principale ou parente ? »

⚠️ À ne pas confondre : service partagé dans son conteneur ne signifie pas contexte HTTP immuable.

Les parameters de route

À retenir en priorité
  1. Réordonner les arguments ne change pas la correspondance.
  2. Renommer un argument impose de vérifier le parameter de route.

Pour /blog/42, RouterListener ajoute le résultat du matcher à Request::attributes : id vaut la chaîne "42" avant les conversions éventuelles. Le resolver d'attributs cherche un attribut du même nom que l'argument. Il n'interroge pas la base de données. Le scénario principal consulte explicitement ArticleCatalog en mémoire dans l'action.

Une intégration Doctrine configurée peut résoudre une entité avant l’action ; ce comportement appartient au bridge, pas à HttpKernel seul, et l’ORM reste hors du programme étudié.

Un parameter du path est déposé dans $request->attributes, puis passé au controller via la résolution d'arguments : la correspondance se fait sur le nom, jamais sur la position. Réordonner les arguments ne change rien ; en renommer l'argument qui dépend de cet attribute casse cette correspondance, sauf autre resolver ou valeur par défaut. attributes porte aussi _route et _controller.

🌍 In Real Life

La situation : le responsable recopie « numéro : 42 » sur le bon ; le poste cherche la case « numéro », pas la première case disponible.

L’équivalent dans Symfony : case renseignée après orientation → RouterListener ajoute id: '42' aux attributes ; recherche par étiquette → resolver d’attributs associé au nom $id ; consultation ultérieure du catalogue → appel métier distinct.

Retour à la réalité technique : l’appariement repose sur le nom, non sur la position. Renommer $id rompt cette correspondance, sauf autre source de valeur. Une intégration d’entité exige son resolver et son mapping configurés ; le routeur ne réalise pas cette lecture.

🧠 Comment le mémoriser : « L’étiquette relie, la place ne décide pas. » Image mentale : cases réordonnées dont les étiquettes restent identiques. Question-réflexe : « Quel attribute porte exactement le nom de cet argument ? »

⚠️ À ne pas confondre : attributes de la Request = données d’exécution ; attribut PHP #[Route] = métadonnée de configuration.

La suite précise comment ces valeurs et les services sont préparés dans les argument value resolvers.

Les parameters de route sont des notes agrafées au dossier par le bureau de routing. Les chercher dans query revient à ouvrir le tiroir des informations de l'URL après le point d'interrogation : ce n'est pas la même origine.

Body et query string

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.

La consultation de l'article utilise ici query pour limit=5 et n'a pas besoin d'un body. Si le lecteur s'inscrit ensuite, le POST d'inscription ouvre une autre branche : formulaire encodé ou JSON selon le client. getPayload() choisit une représentation des données reçues ; il ne valide ni l'adresse e-mail ni les règles métier et ne soumet pas un Form Symfony.

$request->query porte la query string. getPayload() procède dans cet ordre : si $request->request n'est pas vide, elle rend un clone de ce sac — le form l'emporte, le JSON n'est pas lu ; sinon, un body vide donne un InputBag vide ; sinon le body est décodé en JSON. Un JSON mal formé lève une JsonException, comme un JSON valide qui ne décode pas en array.

🌍 In Real Life

La situation : après avoir lu le billet, le lecteur envoie son inscription. Le guichet dispose soit de champs déjà transcrits, soit d’un document à décoder ; lire le document ne certifie pas son contenu.

L’équivalent dans Symfony : champs disponibles → sac request non vide, cloné par getPayload() ; document absent → InputBag vide ; document restant → décodage du body JSON.

Retour à la réalité technique : la sélection est ordonnée, sans fusion avec la query string ni avec une seconde source JSON. Un JSON invalide ou non décodable en tableau déclenche une exception. Ce choix d’entrée ne soumet pas un Form Symfony et ne valide pas une adresse e-mail.

🧠 Comment le mémoriser : « Choisir, décoder, puis contrôler. » Image mentale : deux formats d’inscription, puis un contrôle séparé. Question-réflexe : « Ai-je seulement obtenu des données ou déjà évalué leurs contraintes ? »

⚠️ À ne pas confondre : paramètres de formulaire HTTP, composant Form, désérialisation et Validation sont des opérations distinctes.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Les parameters de route s'apparient par leur nom, jamais par leur position.

    Les parameters de route s'apparient par leur nom, jamais par leur position. Réordonner les arguments ne casse pas cette correspondance ; renommer celui qui dépend d'un attribut la rompt, sauf autre resolver ou valeur par défaut capable de fournir l'argument.

  • Voir l’explication : Dans le câblage standard, injecter RequestStack dans un service.

    Dans le câblage standard, injecter RequestStack dans un service. Typer un argument Request suffit dans un controller via son resolver ; un service qui consulte le contexte reçoit RequestStack et lit la requête courante au moment utile.

  • Voir l’explication : getPayload() ne fusionne pas form et JSON.

    getPayload() ne fusionne pas form et JSON. Si le sac des parameters de form n'est pas vide, elle rend celui-là et ne regarde même pas le body brut.

  • Voir l’explication : Un body JSON invalide ne donne pas un sac vide

    Un body JSON invalide ne donne pas un sac vide : il lève une exception. Le sac vide provient d'un body vide ou d'un JSON décodé en tableau vide.

  • Voir l’explication : getPayload() rend un clone.

    getPayload() rend un clone. Écrire dans l'object retourné ne change rien à la Request.

Application

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.
  3. Le type déclenche le resolver.
  4. Dans un service durable, utiliser RequestStack.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Controller : typer Request ; service : RequestStack.
  • Parameters de route : attributes, puis le nom de l'argument.
  • _route et _controller sont dans attributes.
  • getPayload() : form d'abord, en clone ; body vide → sac vide.
  • JSON invalide ou pas un array → JsonException.
  • getSession() de RequestStack lève au lieu de rendre null.

Moyen mnémotechnique : « Le nom, pas la place ».
