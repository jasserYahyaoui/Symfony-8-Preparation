Objectif

Hacher et vérifier un password, savoir quels anciens hashes restent lisibles après un changement d'algorithme, et faire migrer ceux qui ne le sont pas sans demander aux users de changer de password.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le user détermine le hasher.
  2. Le password seul ne permet pas ce choix.

On hache un password avec un hasher choisi par class de user. auto hache en bcrypt et sait toujours lire les hashes qui portent leur algorithme. Pour un ancien format qui ne le porte pas, migrate_from relit l'ancien hash et le rehache à la connexion, sans que le user ne voie rien.

Le schéma

À retenir en priorité
  1. La migration exige une vérification réussie.
  2. Le nouveau hash doit être enregistré.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le hash n'est pas une valeur à comparer directement.
  2. Le hasher connaît le format et sa vérification.
security:
    password_hashers:
        legacy:                          # l'ancien format, pour vérifier
            algorithm: sha256
            encode_as_base64: false
            iterations: 1
        App\Entity\User:
            algorithm: auto              # bcrypt pour hacher
            migrate_from: [legacy]       # relit les anciens hashes

Hacher

À retenir en priorité
  1. Un hash valide peut être ancien.
  2. La nécessité de migration est distincte de la validité.
$user->setPassword($hasher->hashPassword($user, $plainPassword));
  • hashPassword() prend le user, parce que l'algorithme dépend de sa class ; l'interface a aussi isPasswordValid() et needsRehash().
  • Un hasher déclaré sur PasswordAuthenticatedUserInterface couvre toutes les classes qui l'implémentent.
  • Un user qui implémente PasswordHasherAwareInterface choisit son hasher par getPasswordHasherName().
  • Aucun hasher pour la class : RuntimeException « No password hasher has been configured for account … ».
  • Un controller ne vérifie pas le password lui-même : le badge PasswordCredentials de l'authenticator s'en charge.

`auto` hache en bcrypt

À retenir en priorité
  1. Le choix est propre à la version étudiée.
  2. auto ne signifie pas sélection arbitraire par application.

auto choisit « the best available hasher (currently Bcrypt) ». Il construit une suite — native (bcrypt, coût 13), puis sodium s'il est disponible, puis pbkdf2 — dont le premier maillon hache et les suivants ne servent qu'à vérifier.

  • Un hash argon2id existant est accepté, et needsRehash() vaut true.
  • Un bcrypt d'un autre coût est accepté, et needsRehash() vaut true.
  • En test, on abaisse le coût : cost: 4, la valeur minimale de bcrypt.

Quels anciens hashes restent lisibles

À retenir en priorité
  1. Les formats auto-descriptifs facilitent la vérification.
  2. Un ancien format personnalisé nécessite sa règle.

Un hash bcrypt ou argon2 porte son algorithme ($2y$…, $argon2id$…) : auto le relit. Un condensat sha256 maison n'est qu'une suite hexadécimale : sans migrate_from, il n'est plus vérifié, et la connexion est refusée.

Migrer

À retenir en priorité
  1. La réussite de login ne garantit pas la persistance.
  2. L'upgrader doit enregistrer le nouveau hash.

migrate_from nomme les anciens hashers. À la connexion, le password est vérifié par l'ancien, puis PasswordMigratingListener le rehache. Il faut :

  • un PasswordUpgradeBadge sur le passport — form_login, json_login et http_basic l'ajoutent ;
  • un PasswordUpgraderInterface pour enregistrer le nouveau hash, en pratique le provider, dont upgradePassword() reçoit un $2y$13$….

Sans PasswordUpgraderInterface, la connexion réussit mais le hash reste inchangé, et rien ne le signale.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. L'ancien hash doit rester vérifiable.
  2. Le nouveau doit pouvoir être sauvegardé.
  • Voir l’explication : hashPassword() reçoit le user

    hashPassword() reçoit le user, pas seulement le password.

  • Voir l’explication : auto hache en bcrypt

    auto hache en bcrypt, même quand sodium est disponible.

  • Voir l’explication : Changer d'algorithme peut casser

    Changer d'algorithme peut casser : un condensat qui ne porte pas son algorithme n'est plus vérifié sans migrate_from.

  • Voir l’explication : La migration exige un PasswordUpgraderInterface

    La migration exige un PasswordUpgraderInterface, sinon le réencodage n'est jamais sauvegardé — et rien ne le signale.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le test peut utiliser un coût réduit.
  2. La configuration de production reste distincte.

Si tu dois retenir seulement 7 choses :

  • hashPassword($user, $plain) : le user, car l'algorithme dépend de sa class.
  • auto hache en bcrypt (coût 13) et vérifie argon2, pbkdf2.
  • needsRehash() vrai pour un autre algorithme ou un autre coût.
  • Un hash qui porte son algorithme reste lisible ; un sha256 maison non.
  • migrate_from + PasswordUpgradeBadge + PasswordUpgraderInterface.
  • Pas d'upgrader : migration silencieusement perdue.
  • En test : cost: 4.

Moyen mnémotechnique : « Hacher en bcrypt, lire l'ancien, rehacher en silence ».

hashPassword(user) ; auto = bcrypt (+ vérifie sodium/pbkdf2) ; needsRehash si algo/coût changent ;
sha256 maison = migrate_from ; rehachage = PasswordUpgradeBadge + PasswordUpgraderInterface
