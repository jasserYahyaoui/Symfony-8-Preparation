Objectif

Avant qu'Alice puisse administrer les articles, la branche /inscription doit transformer son mot de passe sans le conserver en clair. Plus tard, une évolution du hasher doit préserver la connexion des anciens comptes : vérifier une preuve et remplacer son hash sont deux opérations.

L'essentiel

À comprendre

À retenir en priorité
  1. Le user détermine le hasher.
  2. Le password seul ne permet pas ce choix.

On hache un password avec un hasher choisi par class de user. auto hache en bcrypt et sait encore lire les hashes qui portent leur algorithme. Pour un ancien format qui ne le porte pas, migrate_from relit l'ancien hash et le rehache à la connexion, sans que le user ne voie rien.

Le hachage n'est pas un chiffrement réversible : on ne déchiffre pas l'ancien hash pour récupérer le password. La migration utilise la preuve présentée et validée lors d'une connexion, sous les conditions détaillées plus bas. Lire publiquement /blog/42 ne doit pas déclencher ce travail.

Le schéma

À retenir en priorité
  1. La migration exige une vérification réussie.
  2. Le nouveau hash doit être enregistré.

Suivre Alice avec son ancien hash : la compatibilité du format permet une vérification, pas un succès automatique. Puis needsRehash() répond sur l'obsolescence du hash, pas sur la validité du password saisi.

Bleu : données/vérification ; ambre : décisions ; vert : résultat. Reconnaître le format du hash ne valide pas le password : cette étape manquait au raisonnement. Le statut d'échec dépend de l'authenticator, pas du hasher. Le rehachage ne convertit pas un ancien hash : il réutilise le password fourni et validé lors de la connexion.

L'exemple

Exemple concret

À retenir en priorité
  1. Le hash n'est pas une valeur à comparer directement.
  2. Le hasher connaît le format et sa vérification.

Ce scénario suppose un ancien format précisément connu : SHA-256 hexadécimal, une itération, avec ses éventuelles conventions de sel. La déclaration doit reproduire l'ancien calcul ; elle ne reconnaît pas n'importe quel condensat maison. Elle sert à migrer un existant, jamais à créer de nouveaux comptes avec un algorithme rapide.

security:
    password_hashers:
        legacy:                          # l'ancien format, pour vérifier
            algorithm: sha256
            encode_as_base64: false
            iterations: 1
        App\Entity\User:
            algorithm: auto              # bcrypt pour hacher
            migrate_from: [legacy]       # relit les anciens hashes

Hacher

À retenir en priorité
  1. Un hash valide peut être ancien.
  2. La nécessité de migration est distincte de la validité.

🌍 In Real Life

La situation : le bureau du blog conserve une empreinte de contrôle plutôt qu'une copie lisible du secret d'Alice. Une future présentation sera vérifiée contre cette empreinte.

L’équivalent dans Symfony : fabrication de l'empreinte → hashPassword() ; contrôle du secret présenté → vérification par le hasher ; archivage → sauvegarde applicative du hash.

Retour à la réalité technique : un hash de mot de passe n'est pas un chiffrement à déchiffrer. Le sel et les paramètres sont gérés par le format moderne ; deux hachages du même secret peuvent différer. Le résultat doit encore être affecté et sauvegardé.

🧠 Comment le mémoriser : « Vérifier sans relire le secret conservé. » Image mentale : empreinte de contrôle, pas coffre avec une copie. Question-réflexe : est-ce bien le hash que je persiste ?

⚠️ À ne pas confondre : hachage dédié aux mots de passe et simple condensat rapide.

Dans le traitement d'inscription, $user implémente PasswordAuthenticatedUserInterface, et sa méthode applicative setPassword() doit exister. Elle n'est pas fournie par cette interface. Le service injecté est Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface :

$user->setPassword($hasher->hashPassword($user, $plainPassword));

$hasher est un UserPasswordHasherInterface injecté ; sauvegarder ensuite le user via le stockage applicatif. Ne jamais journaliser $plainPassword. Le hasher legacy du YAML sert uniquement à relire un existant : ne pas choisir SHA-256 rapide pour de nouveaux passwords.

  • hashPassword() prend le user, parce que l'algorithme dépend de sa class ; l'interface a aussi isPasswordValid() et needsRehash().
  • Un hasher déclaré sur PasswordAuthenticatedUserInterface couvre toutes les classes qui l'implémentent.
  • Un user qui implémente PasswordHasherAwareInterface choisit son hasher par getPasswordHasherName().
  • Aucun hasher pour la class : RuntimeException « No password hasher has been configured for account … ».
  • Un controller ne vérifie pas le password lui-même : le badge PasswordCredentials de l'authenticator s'en charge.

Plus précisément, le parcours standard fait vérifier ces credentials par ses listeners ; le badge transporte la preuve. Pour une vérification explicite via le service, isPasswordValid($user, $candidate) rend un booléen mais ne crée pas une connexion. Ne pas comparer le plaintext au hash, ni comparer deux nouveaux hashes entre eux : le sel peut les rendre différents.

`auto` hache en bcrypt

À retenir en priorité
  1. Le choix est propre à la version étudiée.
  2. auto ne signifie pas sélection arbitraire par application.

Le comportement décrit vise Symfony 8.0 et ses réglages par défaut, pas une promesse pour toutes les versions futures ou des options surchargées.

auto choisit « the best available hasher (currently Bcrypt) ». Il construit une suite — native (bcrypt, coût 13), puis sodium s'il est disponible, puis pbkdf2 — dont le premier maillon hache et les suivants ne servent qu'à vérifier.

  • Un hash argon2id existant est accepté, et needsRehash() vaut true.
  • Un bcrypt d'un autre coût est accepté, et needsRehash() vaut true.
  • En test, on abaisse le coût : cost: 4, la valeur minimale de bcrypt.

« Accepté » suppose évidemment le bon password et un format pris en charge par la plateforme. Réserver le faible coût à la configuration de test : il accélère les scénarios d'authentification, pas une politique de production. Un coût plus élevé consomme davantage de calcul ; mesurer sur la plateforme cible plutôt qu'inventer un budget universel.

Quels anciens hashes restent lisibles

À retenir en priorité
  1. Les formats auto-descriptifs facilitent la vérification.
  2. Un ancien format personnalisé nécessite sa règle.

🌍 In Real Life

La situation : les fiches de contrôle du blog portent normalement la version du procédé utilisé. Une ancienne fiche sans étiquette exige de connaître exactement son mode de fabrication.

L’équivalent dans Symfony : étiquette de procédé → préfixe du hash moderne ; procédure historique déclarée → ancien hasher dans migrate_from.

Retour à la réalité technique : reconnaître le format permet d'essayer la vérification, pas de l'accepter d'avance. Les conventions historiques de sel, d'itération et d'encodage doivent correspondre ; le support effectif dépend aussi du runtime.

🧠 Comment le mémoriser : « Connaître le format pour contrôler la preuve. » Image mentale : fiche étiquetée à côté d'une notice historique. Question-réflexe : le format est-il supporté et le secret présenté est-il correct ?

⚠️ À ne pas confondre : compatibilité de lecture et conformité du hash à la politique actuelle.

Un hash bcrypt ou argon2 porte son algorithme ($2y$…, $argon2id$…) : auto le relit. Un condensat sha256 maison n'est qu'une suite hexadécimale : sans migrate_from, il n'est plus vérifié, et la connexion est refusée.

Pour Alice, distinguer trois observations : bon password/format supporté → vérification positive ; bon password/ancien format non déclaré → échec de compatibilité ; mauvais password → échec même avec un format reconnu. Le statut HTTP final appartient au mécanisme de connexion, pas au préfixe du hash.

Migrer

À retenir en priorité
  1. La réussite de login ne garantit pas la persistance.
  2. L'upgrader doit enregistrer le nouveau hash.

🌍 In Real Life

La situation : après un contrôle réussi, le bureau du blog refait la fiche selon la nouvelle norme et la remet au responsable des archives. Sans archivage, la prochaine visite retrouve l'ancienne.

L’équivalent dans Symfony : ancienne preuve vérifiée → connexion réussie ; besoin de modernisation → needsRehash() ; nouveau calcul → listener de migration ; archivage → PasswordUpgraderInterface.

Retour à la réalité technique : badge, listener et upgrader utilisable conditionnent ce parcours. L'ancien hash n'est pas déchiffré : le nouveau calcul utilise le secret présenté lors de la connexion. L'upgrader reçoit le nouveau hash, jamais un plaintext à stocker.

🧠 Comment le mémoriser : « Vérifier, refaire, enregistrer. » Image mentale : nouvelle fiche entrant dans les archives. Question-réflexe : ai-je constaté la sauvegarde, pas seulement la connexion ?

⚠️ À ne pas confondre : migration des hashes et migration de schéma de données.

migrate_from nomme les anciens hashers. À la connexion, le password est vérifié par l'ancien, puis PasswordMigratingListener le rehache. Il faut :

  • un PasswordUpgradeBadge sur le passport — form_login, json_login et http_basic l'ajoutent ;
  • un PasswordUpgraderInterface pour enregistrer le nouveau hash, en pratique le provider, dont upgradePassword() reçoit un $2y$13$….

Sans PasswordUpgraderInterface, la connexion réussit mais le hash reste inchangé, et rien ne le signale.

PasswordMigratingListener intervient sur LoginSuccessEvent. Il récupère et efface le plaintext du badge, vérifie que le user possède un hash et que needsRehash() est vrai, puis cherche un upgrader explicite ou celui lié au chargeur du UserBadge. Sans upgrader utilisable, il peut retourner sans calculer de nouveau hash. Avec lui, upgradePassword() reçoit le hash nouvellement calculé, jamais le plaintext à persister.

Tester séparément la connexion réussie et la valeur effectivement enregistrée. Un retour 200 ne prouve pas une migration ; une exception de stockage ne doit pas être présentée comme une migration silencieusement réussie.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'ancien hash doit rester vérifiable.
  2. Le nouveau doit pouvoir être sauvegardé.
  • Identifier l’étape de migration du password

    La question d'examen peut changer un seul maillon : class de user, ancien format, coût ou sauvegarde. Identifier celui-ci avant de conclure « le mot de passe est faux » ou « la migration est terminée ».

  • Voir l’explication : hashPassword() reçoit le user

    hashPassword() reçoit le user, pas seulement le password.

  • Voir l’explication : auto hache en bcrypt

    auto hache en bcrypt, même quand sodium est disponible.

  • Voir l’explication : Changer d'algorithme peut casser

    Changer d'algorithme peut casser : un condensat qui ne porte pas son algorithme n'est plus vérifié sans migrate_from.

  • Voir l’explication : La migration exige un PasswordUpgraderInterface

    La migration exige un PasswordUpgraderInterface, sinon le réencodage n'est jamais sauvegardé — et rien ne le signale.

Fiche express

À mémoriser

À retenir en priorité
  1. Le test peut utiliser un coût réduit.
  2. La configuration de production reste distincte.

Le mot de passe est maintenant vérifiable sans être conservé en clair. Les authenticators et passports montrent comment cette preuve rejoint les autres vérifications de connexion.

Si tu dois retenir seulement 7 choses :

  • hashPassword($user, $plain) : le user, car l'algorithme dépend de sa class.
  • auto hache en bcrypt (coût 13) et vérifie argon2, pbkdf2.
  • needsRehash() vrai pour un autre algorithme ou un autre coût.
  • Un hash qui porte son algorithme reste lisible ; un sha256 maison non.
  • migrate_from + PasswordUpgradeBadge + PasswordUpgraderInterface.
  • Pas d'upgrader : migration silencieusement perdue.
  • En test : cost: 4.

Moyen mnémotechnique : « Hacher en bcrypt, lire l'ancien, rehacher en silence ».

hashPassword(user) ; auto = bcrypt (+ vérifie sodium/pbkdf2) ; needsRehash si algo/coût changent ;
sha256 maison = migrate_from ; rehachage = PasswordUpgradeBadge + PasswordUpgraderInterface
