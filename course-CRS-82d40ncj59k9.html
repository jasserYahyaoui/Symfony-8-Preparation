Objectif

Composer un message électronique et savoir quelle structure MIME il produit.

L'essentiel

À comprendre

À retenir en priorité
  1. Mime définit le contenu et la structure.
  2. Le transport est une responsabilité séparée.

Le component Mime fabrique un message électronique ; il ne l'envoie pas. L'API Email, chaînable, couvre les besoins courants ; Message, bas niveau, se réserve aux cas rares. À l'examen : la structure MIME produite, les adresses, et MimeTypes, dont la devinette lit le contenu du file.

Le schéma

À retenir en priorité
  1. Chaque type exprime une relation.
  2. La structure MIME n'est pas arbitraire.

Bleu : conteneurs MIME ; vert : parties de contenu. Les flèches représentent la composition, pas une chronologie d'envoi. Le client choisit une version qu'il sait afficher dans alternative ; il ne concatène pas le texte et le HTML.

L'exemple : une notification

Exemple concret

À retenir en priorité
  1. Email couvre les usages courants.
  2. Message permet un contrôle plus bas niveau.
use Symfony\Component\Mime\Email;

$email = new Email()
    ->from('fabien@symfony.com')
    ->to('foo@example.com')
    ->addCc('bar@example.com')
    ->priority(Email::PRIORITY_HIGH)
    ->subject('Important Notification')
    ->text('Lorem ipsum...')
    ->html('<h1>Lorem ipsum</h1>')
    ->attachFromPath('/path/report.pdf');

Ce fragment suppose un PDF lisible au chemin indiqué. Il n'ajoute pas d'image intégrée : son arbre omet donc related et image/png, contrairement à la vue complète. Construire l'Email n'envoie aucun message.

Deux API pour un même message

À retenir en priorité
  1. Le bas niveau offre plus de contrôle.
  2. Il ajoute aussi de la complexité.
  3. Un objet Email restauré et sa représentation MIME brute sont deux types distincts.

Email est l'API haut niveau ; Message contrôle chaque partie à la main, et la documentation la déconseille pour un besoin ordinaire. Email et Message peuvent être sérialisés comme objets PHP ; un RawMessage, lui, peut être construit depuis le texte MIME produit par toString(). Ne pas confondre ces représentations ni appeler unserialize() sur des données provenant d'une source non fiable.

L'arborescence MIME

À comprendre

À retenir en priorité
  1. Les parties représentent le même contenu.
  2. L'ordre exprime la préférence.

C'est quoi ?

MIME décrit comment assembler des en-têtes et des contenus de types différents dans un courriel. Email est l'API de haut niveau ; Message permet de composer les parties manuellement. Mime construit le message, il ne réalise pas son transport.

À quoi ça sert ?

Un lecteur peut choisir entre une version texte et HTML du même contenu, afficher une image liée au HTML et présenter une pièce jointe séparée. Ces relations doivent être représentées correctement, pas seulement juxtaposées.

Où dans Symfony ?

  • multipart/alternative : plusieurs représentations du même contenu ; la préférée vient en dernier.
  • multipart/related : parties qui forment un même ensemble, comme HTML et image intégrée.
  • multipart/mixed : contenus distincts, notamment les pièces jointes.

L'API Email prépare cette structure à partir des corps et pièces fournis ; l'API Message demande d'en assumer l'assemblage.

Comment, étape par étape ?

  1. Construire des adresses valides ; Address sépare l'adresse et le nom affiché.
  2. Fournir des versions texte et HTML cohérentes, plutôt qu'un HTML seul supposé lisible partout.
  3. Ajouter les parties liées ou pièces jointes selon leur rôle.
  4. Confier ensuite le message au mécanisme d'envoi choisi. Pour conserver ou échanger des données externes, utiliser un format et une validation contrôlés ; ne pas reconstruire arbitrairement des objets PHP depuis des données non fiables.

Exemple concret PHP

Avec Mime et ses dependencies installés, ce code construit seulement un message :

<?php
use Symfony\Component\Mime\Address;
use Symfony\Component\Mime\Email;

$email = (new Email())
    ->from(new Address('reports@example.test', 'Rapports'))
    ->to('reader@example.test')
    ->subject('Rapport prêt')
    ->text('Votre rapport est prêt.')
    ->html('<p>Votre rapport est prêt.</p>');
echo $email->toString();

Les adresses sont fictives et aucun transport n'est appelé. Les deux corps représentent la même information : leur relation est alternative, pas deux pièces jointes indépendantes.

Contre-exemple : déclarer une image comme simple pièce jointe puis supposer qu'un HTML quelconque l'affichera automatiquement. Correction : choisir une relation et une référence adaptées. Ne pas interpoler de HTML utilisateur non échappé dans le corps.

Les correspondances extension/type MIME et les guessers ne répondent pas à la même question : une extension suggère un type, un guesser inspecte le fichier selon les capacités disponibles. Aucun résultat n'est une preuve générale d'innocuité d'un upload. Les adresses internationalisées demandent aussi de vérifier les contraintes du transport et de l'envelope, notamment pour l'expéditeur ; l'acceptation d'un objet Address ne promet pas toute capacité SMTP.

Mime 8.0.

Passage canonique conservé

L'arbre ci-dessus est exactement celui qu'Email produit pour texte, HTML, image intégrée et PDF joint. alternative réunit des versions du même contenu, related des parties qui forment un tout, mixed des contenus de natures différentes.

Les adresses

À retenir en priorité
  1. Le préfixe add conserve la liste.
  2. Un nouvel appel to remplace la destination.
  • Une string ou un object Address ; Address::create('Fabien Potencier <fabien@example.com>') analyse la forme Nom <adresse>.
  • to(), cc(), bcc() remplacent ; addTo(), addCc(), addBcc() ajoutent.
  • L'UTF-8 est admis dans la partie locale, sauf pour le sender : Envelope refuse jösé@… comme sender, l'accepte comme destinataire.

Les types MIME

À retenir en priorité
  1. Un nom .txt peut contenir une image.
  2. Le contenu détermine la détection.
Appel Code 8.0, exécuté
getExtensions('image/jpeg') jpg, jpeg, jpe, jfif
getMimeTypes('js') text/javascript d'abord

Les arrays sont classés par priority, le premier étant le préféré — la documentation 8.0 en montre un ordre que le code ne rend plus. guessMimeType() lit le contenu, pas le nom : un PNG nommé .txt est image/png. L'extension PHP fileinfo l'accélère ; un devineur maison implémente MimeTypeGuesserInterface, tag mime.mime_type_guesser.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le premier élément est préféré.
  2. Ne pas déduire une priorité de l'alphabet.
  • Ordre des variantes MIME

    Dans multipart/alternative, la version préférée est la dernière.

  • Voir l’explication : guessMimeType() ignore le nom du file

    guessMimeType() ignore le nom du file — il lit le contenu.

  • Voir l’explication : Les arrays de MimeTypes sont classés par priority, pas alphabétiquement

    Les arrays de MimeTypes sont classés par priority, pas alphabétiquement — et la priority réelle du code diffère de l'exemple de la documentation.

  • Adresse UTF-8 et restriction du sender

    L'UTF-8 dans la partie locale est refusé pour le sender seul.

Fiche express

À mémoriser

À retenir en priorité
  1. Le nom affiché est distinct de l'adresse.
  2. Address représente les deux.

Si tu dois retenir seulement 6 choses :

  • Mime fabrique, Mailer envoie.
  • Email haut niveau ; Message pour les besoins rares.
  • alternative = même contenu, préféré en dernier ; related = un tout ; mixed = natures différentes.
  • to() remplace, addTo() ajoute ; UTF-8 refusé pour le sender.
  • MimeTypes : arrays par priority ; jpg et text/javascript d'abord.
  • guessMimeType() lit le contenu ; fileinfo accélère.

Moyen mnémotechnique : « Même contenu, un tout, des natures ».
