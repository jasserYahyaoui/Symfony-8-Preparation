Objectif

Router un message vers un transport, savoir ce que change l'absence de routage, et ce qui est vérifié — ou non — au démarrage.

L'essentiel

À comprendre

À retenir en priorité
  1. L'absence de routage n'est pas une file implicite.
  2. Le bus appelle les handlers.

Un transport est le service qui envoie ou reçoit les Envelope ; son DSN configure sa connexion et sa fabrique. Le routage dit où part chaque message, par la configuration ou par #[AsMessage] — la configuration gagne. Un message routé nulle part n'est pas perdu : il est traité tout de suite. Une faute dans routing casse le build ; la même dans l'attribute ne casse qu'au dispatch.

Le schéma

À retenir en priorité
  1. La configuration adapte le routage à l'environment.
  2. Le stamp fournit un choix ponctuel.

Bleu : demande ; ambre : sélection ; vert : issue. Le dernier chemin suppose la pile par défaut et un handler enregistré. Il ne signifie pas qu'un message sans handler réussit : HandleMessageMiddleware peut lever NoHandlerForMessageException. La sélection d'un sender ne prouve pas non plus que sa connexion ou son envoi réussira.

Deux conséquences : la configuration l'emporte sur l'attribute, et une key en * n'est qu'un repli.

L'exemple

Exemple concret

À retenir en priorité
  1. Un message peut avoir plusieurs destinations.
  2. Ce choix ne signifie pas un seul traitement métier.
framework:
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
            audit: '%env(AUDIT_TRANSPORT_DSN)%'
            sync:  'sync://'
        routing:
            'App\Message\SendWelcomeEmail': async
            'App\Message\ChargeCard': sync
#[AsMessage(['async', 'audit'])]
final class SmsNotification {}
final class ResizeAvatar {}   // routé nulle part

SendWelcomeEmail part dans async ; ChargeCard est traité sur place par un vrai transport ; SmsNotification part dans deux transports ; ResizeAvatar est traité tout de suite, dans la Request.

Déclarer

À retenir en priorité
  1. sync est un vrai transport synchrone.
  2. in-memory sert à observer l'envoi en test.

sync:// est un transport intégré qui traite immédiatement dans le même process et ajoute des stamps de transport. in-memory:// conserve les messages envoyés pour les tests, sans les traiter automatiquement. Il ne sérialise pas par défaut ; in-memory://?serialize=true permet d'exercer cette frontière.

Un transport est sélectionné par son DSN et le routage. Pour un transport qui sérialise les messages, choisir des données sérialisables et un contrat compatible avec les messages déjà en attente. Les intégrations de transport externes restent exclues.

Router

À comprendre

À retenir en priorité
  1. Le joker sert de repli.
  2. Les routes précises ne reçoivent pas systématiquement sa destination.

C'est quoi ?

Un transport est le mécanisme d'envoi et de réception ; le routage associe des types de messages à ses noms. Déclarer une file ne signifie pas que tous les messages y seront envoyés.

À quoi ça sert ?

Le routage permet de changer le mode d'exécution par configuration et de séparer les travaux par destination. Plusieurs destinations signifient plusieurs envois, pas une unique exécution garantie du métier.

Où dans Symfony ?

framework.messenger.transports déclare les transports ; routing les sélectionne. sync:// utilise un transport mais traite immédiatement. in-memory:// conserve les messages en mémoire pour observer les envois en test ; il ne les traite pas automatiquement et ne constitue pas une file durable.

Comment, étape par étape ?

  1. Déclarer un transport pris en charge par les packages réellement installés.
  2. Router la classe, une interface ou un groupe de messages vers son nom.
  3. Au dispatch, un message non routé reste synchrone : le bus appelle ses handlers. L'absence de handler approprié n'est pas résolue par la seule déclaration d'un transport.
  4. Pour une file asynchrone, faire consommer les messages par un worker. Pour plusieurs transports, examiner aussi quels handlers s'exécutent à chaque réception et rendre leurs effets répétables.

Exemple concret YAML

Configuration de test pour une classe App\Message\GenerateReport déjà présente dans l'application :

framework:
    messenger:
        transports:
            test_queue: 'in-memory://?serialize=true'
        routing:
            'App\Message\GenerateReport': test_queue

Le test peut inspecter les messages envoyés sans lancer le traitement. serialize=true ajoute une frontière de sérialisation que le transport mémoire ordinaire ne teste pas. Contre-exemple : un message contenant une closure paraît acceptable en mémoire puis échoue sur une vraie file. Correction : transporter des données sérialisables et tester cette frontière, jamais désérialiser un contenu externe non fiable.

Une liste de noms de transports route vers plusieurs destinations. Les règles parent/interface peuvent aussi contribuer au routage ; le joker sert de repli, pas de destination systématique à ajouter. Un TransportNamesStamp impose un choix ponctuel : son emploi doit être intentionnel. Ni une file mémoire ni un routage multiple ne promettent une livraison exactement une fois.

Transports Messenger 8.0.

Passage canonique conservé
routing:
    'App\Message\SmsNotification': [async, audit]
    'App\Message\AsyncMessageInterface': async
    'App\Message\*': async
  • Une key peut être une class, une class parente, une interface, un namespace terminé par *, ou * seul ; un message peut viser plusieurs transports.
  • Attribute et configuration sur le même message : la configuration gagne, c'est elle qui change le routage par environment.
  • Parent et enfant s'additionnent ; un joker ne sert que si rien de plus précis n'a trouvé de transport — « the '*' acts as a fallback ».
routing Message Transports
SmsNotification: async, Notification: audit (parente) SmsNotification async et audit
Welcome: async, '*': audit Welcome async seulement
'*': audit SmsNotification, avec #[AsMessage(['async', 'audit'])] audit seulement

Au dispatch, TransportNamesStamp remplace tout : dispatch(new Welcome(), [new TransportNamesStamp(['sync'])]) ignore la key async.

Non routé : traité tout de suite

À retenir en priorité
  1. Déclarer un transport ne route pas les messages.
  2. Le routage décide pour chaque type.

Un message qui n'est routé nulle part est traité immédiatement, de façon synchrone. Ce n'est pas une erreur : une application sans routing fonctionne, entièrement synchrone.

Par exemple, ajouter seulement un transport nommé async ne change pas ResizeAvatar : sans règle applicable ni attribute, son handler reste appelé avant le retour de dispatch(). Ajouter la règle change ce moment d'exécution.

Ce qui est vérifié au démarrage

À retenir en priorité
  1. La configuration est contrôlée à la compilation.
  2. Une erreur d'attribute peut être différée.

FrameworkBundle contrôle chaque key de routing en construisant le container :

Key de routing Résultat
class mal orthographiée LogicException au build : « class or interface … not found »
transport inexistant (asyncc) LogicException : « This is not a valid transport or service id »
App\Other\* (namespace sans message) aucune erreur : traité en synchrone

L'attribute, lui, n'est vérifié qu'au dispatch : sans transport async déclaré, le container se construit, puis dispatch() lève une RuntimeException.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le mode synchrone peut passer par un transport.
  2. Les stamps révèlent ce trajet.
  • Voir l’explication : Sans routage, le message est traité tout de suite

    Sans routage, le message est traité tout de suite — pas mis en attente, pas perdu.

  • Voir l’explication : Une class mal orthographiée dans routing fait échouer le build

    Une class mal orthographiée dans routing fait échouer le build ; seul un namespace sans correspondance est silencieux.

  • Priorité de la configuration de routage Messenger

    La configuration l'emporte sur #[AsMessage].

  • Voir l’explication : sync:// n'est pas « pas de transport »

    sync:// n'est pas « pas de transport » : il traite sur place, et pose un SentStamp.

  • Voir l’explication : in-memory:// est réservé aux tests

    in-memory:// est réservé aux tests ; il ne traite jamais rien.

Fiche express

À mémoriser

À retenir en priorité
  1. Un test mémoire peut masquer une erreur de sérialisation.
  2. L'option permet de tester cette frontière.

Si tu dois retenir seulement 7 choses :

  • Le DSN configure un transport ; sync:// traite, in-memory:// garde.
  • routing ou #[AsMessage] ; la configuration gagne.
  • Parent et enfant s'additionnent ; un joker n'est qu'un repli.
  • Non routé : traitement immédiat, si un handler est disponible.
  • routing faux → build ; #[AsMessage] faux → dispatch.
  • TransportNamesStamp passe avant tout.
  • in-memory:// ne sérialise qu'avec ?serialize=true.

Moyen mnémotechnique : « le stamp, puis la configuration, puis l'attribute, sinon tout de suite ».

TransportNamesStamp > routing (class + parents + interfaces ; * en repli) > #[AsMessage] > rien = synchrone ;
routing vérifié au build, attribute au dispatch ; sync:// traite avec SentStamp ; in-memory:// sans serialize par défaut
