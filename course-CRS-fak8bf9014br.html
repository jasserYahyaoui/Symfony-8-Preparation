Objectif

Savoir ce que devient, à l'exécution, du code qui appelle une fonctionnalité dépréciée — et pourquoi rien ne casse.

L'essentiel

À comprendre

À retenir en priorité
  1. Une deprecation n'est pas une suppression immédiate.
  2. La visibilité dépend du traitement des erreurs.

Une deprecation émise par trigger_deprecation() est une notice E_USER_DEPRECATED silencée : elle ne fait pas échouer l'appel par elle-même. Elle est émise même sans affichage ; un handler d'erreurs peut la recueillir pour le journal configuré ou la debug toolbar en développement. On la corrige sur la dernière mineure, avant que la majeure ne supprime le code.

Le schéma

À retenir en priorité
  1. La mineure fournit les avertissements.
  2. La majeure peut retirer les APIs concernées.

Bleu : émission/collecte ; ambre : observateur ; vert : effet. Le choix du handler compte : un handler applicatif peut décider de lever, et PHPUnit peut rendre la suite non réussie selon ses options. Le chemin « continue » décrit le traitement standard, pas une garantie pour tout environnement.

L'exemple

Exemple concret

À retenir en priorité
  1. L'absence d'affichage n'est pas absence de notice.
  2. Consulter le dispositif de collecte.
// Exemple dans acme/pkg 1.2, avec le helper de dépréciation chargé.
final class DeprecatedService
{
    public function oldThing(): void
    {
        trigger_deprecation('acme/pkg', '1.2', 'Old thing is deprecated.');
        // … le code continue et fonctionne
    }
}

$service = new DeprecatedService();
$service->oldThing();   // l'appel réussit, en silence
// journal, si le handler de Symfony est actif :
// [info] User Deprecated: Since acme/pkg 1.2: Old thing is deprecated.

Rappel : reconnaître une deprecation

À comprendre

À retenir en priorité
  1. La documentation et le signal d'exécution sont distincts.
  2. Un marqueur PHPDoc ne déclenche pas seul une erreur.

C'est quoi ?

Une deprecation annonce qu'une API encore disponible doit être remplacée. Elle n'est ni une suppression immédiate ni la preuve que le résultat métier actuel est faux. Elle prépare une évolution incompatible d'une version majeure.

À quoi ça sert ?

L'avertissement donne le temps de migrer progressivement tout en gardant les tests du comportement attendu. Ignorer ces signaux reporte le problème au moment où l'ancienne API n'existera plus.

Où dans Symfony ?

Le marqueur PHPDoc @deprecated informe les lecteurs et outils. trigger_deprecation() produit le signal à l'exécution lorsqu'un chemin concerné est parcouru. Le premier ne déclenche pas automatiquement le second. Une suite de tests peut collecter les deprecations et décider séparément si un signal doit faire échouer la suite.

Comment, étape par étape ?

  1. Faire exécuter les chemins qui utilisent l'API et collecter les notices.
  2. Identifier leur origine : code applicatif, dependency appelée directement ou transitivement.
  3. Lire le remplacement annoncé puis modifier l'appel, en conservant une assertion du comportement.
  4. Relancer les tests et vérifier que la notice disparaît parce que l'ancien usage a disparu, pas parce que la collecte a été désactivée.

Exemple concret en shell

Dans une application dont PHPUnit et la collecte des deprecations sont déjà configurés :

php bin/phpunit

Un rapport sans notice ne prouve que les chemins exécutés avec ce dispositif. Contre-exemple : augmenter un seuil ou désactiver le handler pour faire disparaître un échec lié à une API retirée prochainement. Correction : vérifier d'abord le chemin appelé et la version de l'outil, puis migrer l'usage.

Dans les règles de contribution Symfony, une deprecation concerne une API existante et s'introduit dans une version mineure en conservant la compatibilité ; une suppression incompatible relève de la majeure appropriée. Ce contrat n'autorise pas à supposer que toute bibliothèque tierce suit exactement la même politique. Les paramètres du Bridge dépendent aussi de l'outillage installé : collecte et seuil d'échec ne sont pas la même chose.

Une deprecation n'entre que dans une mineure, jamais sur du code nouveau ; le code déprécié ne disparaît qu'à la majeure suivante.

Une notice, et elle est silencée

À retenir en priorité
  1. La deprecation conserve la compatibilité.
  2. Elle doit néanmoins être suivie et corrigée.

trigger_deprecation() appelle @trigger_error(…, \E_USER_DEPRECATED), avec un message qui commence par Since <paquet> <version>:. Sur PHP 8.4, display_errors actif :

Situation Ce qu'on voit
trigger_deprecation(), aucun handler rien ; le script continue
trigger_error(…, E_USER_DEPRECATED) sans @ Deprecated: … dans l'output
handler d'erreurs de Symfony + journal une entrée info : User Deprecated: Since acme/pkg 1.2: …

Le handler de Symfony ne lève jamais d'exception pour une deprecation, même réglé pour lever à tous les niveaux (throwAt(E_ALL, true)) : un E_USER_WARNING devient une ErrorException, une deprecation reste en info. L'option framework.php_errors.throw, active en dev, n'y change donc rien.

Les voir

À retenir en priorité
  1. Collecter et faire échouer sont deux réglages.
  2. Vérifier le comportement de la version PHPUnit utilisée.
  • En dev : la debug toolbar les montre, parce que le handler de Symfony les recueille.
  • Dans le journal : framework.php_errors.log vaut true, et accepte une table qui associe un niveau de journal à chaque niveau d'erreur PHP.
framework:
    php_errors:
        log:
            !php/const \E_USER_DEPRECATED: !php/const Psr\Log\LogLevel::ERROR
  • Dans les tests natifs PHPUnit 12.5.44, sur PHP 8.4 : la collecte d'une deprecation supprimée et le code de sortie de la suite sont distincts. Sans handler applicatif remplaçant celui de PHPUnit, créer tests/LegacyNoticeTest.php :
<?php

use PHPUnit\Framework\TestCase;

final class LegacyNoticeTest extends TestCase
{
    public function testLegacyNotice(): void
    {
        @trigger_error('Ancienne API : utiliser la nouvelle méthode.', E_USER_DEPRECATED);
        self::assertTrue(true);
    }
}

Le @ est essentiel : sans lui, ce test ne démontre pas la suppression. Configurer phpunit.xml :

<phpunit failOnDeprecation="true">
    <testsuites>
        <testsuite name="legacy"><file>tests/LegacyNoticeTest.php</file></testsuite>
    </testsuites>
    <source ignoreSuppressionOfDeprecations="true"/>
</phpunit>

Avec PHPUnit 12.5.44 installé et les extensions requises actives sur PHP 8.4 :

php8.4 vendor/bin/phpunit --configuration phpunit.xml --display-deprecations

Résultat observé avec PHPUnit 12.5.44 et PHP 8.4.27 dans un outil de test isolé : 1 test, 1 assertion, 1 deprecation, et code de sortie 1, même si l'assertion réussit. Les trois configurations ont été exécutées :

Configuration Résultat
failOnDeprecation="true" seul OK, exit code 0
<source ignoreSuppressionOfDeprecations="true"> la deprecation est listée ; code 0
les deux la deprecation est listée ; exit code 1

Contrôle supplémentaire : sans @, failOnDeprecation="true" seul détecte la notice et donne le code 1. La suppression et la politique d'échec sont donc bien deux réglages distincts.

Référence : gestion native des erreurs dans PHPUnit 12.5. Le manifeste officiel de 12.5.44 exige PHP >=8.3 ; le cas a été exécuté sur PHP 8.4, avec les extensions requises. Composer a installé l'outil et vérifié la plateforme et les avis de sécurité sans exception ni désactivation des contrôles.

L'ancien verrouillage 12.0.10 a été refusé par Composer à cause de GHSA-vvj3-c3rp-c85p (PKSA-z3gr-8qht-p93v, correction dans 12.5.8). Il n'a pas été forcé. Ce changement concerne seulement l'outil PHPUnit natif utilisé pour cette preuve ; les API Symfony étudiées restent celles de Symfony 8.0, sans Bridge.

Les corriger

À retenir en priorité
  1. Corriger progressivement réduit le risque.
  2. Ne pas attendre la suppression pour commencer.

Exemple de diagnostic : la route réussit mais le journal cite oldThing(). Repérer l'appelant, remplacer cet appel par l'API conseillée dans le message ou le guide UPGRADE, puis rejouer le même scénario. Zéro notice sur un seul test ne prouve pas l'absence de chemins dépréciés non couverts.

composer update "symfony/*", lire le file UPGRADE de la version atteinte, corriger progressivement. Pour une majeure : dernière mineure d'abord, zéro deprecation, puis la majeure.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un signal absent peut être un défaut de collecte.
  2. La preuve dépend aussi du chemin exécuté.
Visibilité des dépréciations et échéance de migration
  • Une deprecation ne fait échouer ni la Request ni le test par elle-même.
  • La notice est silencée : rien dans l'output, et sans handler d'erreurs, aucune trace.
  • En dev, la debug toolbar les montre — parce que le handler de Symfony les recueille, pas parce qu'elles s'affichent.
  • Le code déprécié fonctionne jusqu'à la majeure suivante.
  • On corrige avant la majeure, pas après.

Fiche express

À mémoriser

À retenir en priorité
  1. Le handler recueille les notices.
  2. La toolbar présente ce qui a été collecté.

Si tu dois retenir seulement 7 choses :

  • trigger_deprecation() = @trigger_error(E_USER_DEPRECATED).
  • Silencée : rien n'échoue, rien ne s'affiche.
  • Message Since <paquet> <version>:.
  • Handler de Symfony : info, jamais d'exception, même avec throw.
  • Debug toolbar si collecte dev active ; journal si configuré.
  • PHPUnit : ignorée par défaut, même avec failOnDeprecation.
  • Dernière mineure, zéro deprecation, puis majeure.

Moyen mnémotechnique : « Silencée, journalisée, corrigée avant la majeure ».

deprecation = @E_USER_DEPRECATED ("Since pkg x.y:") → rien ne casse ; visible via un handler : journal info (php_errors.log), toolbar en dev,
jamais d'exception ; PHPUnit : rien par défaut ; dernière mineure → corriger → majeure
