Objectif

Savoir ce que devient, à l'exécution, du code qui appelle une fonctionnalité dépréciée — et pourquoi rien ne casse.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Une deprecation n'est pas une suppression immédiate.
  2. La visibilité dépend du traitement des erreurs.

Une deprecation Symfony est une notice E_USER_DEPRECATED silencée : rien n'échoue, rien ne s'affiche. Elle n'existe que si un handler d'erreurs la recueille — la debug toolbar en dev, le journal partout. On la corrige sur la dernière mineure, avant que la majeure ne supprime le code.

Le schéma

À retenir en priorité
  1. La mineure fournit les avertissements.
  2. La majeure peut retirer les APIs concernées.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. L'absence d'affichage n'est pas absence de notice.
  2. Consulter le dispositif de collecte.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

// dans acme/pkg 1.2
public function oldThing(): void
{
    trigger_deprecation('acme/pkg', '1.2', 'Old thing is deprecated.');
    // … le code continue et fonctionne
}

$service->oldThing();   // l'appel réussit, en silence
// journal, si le handler de Symfony est actif :
// [info] User Deprecated: Since acme/pkg 1.2: Old thing is deprecated.

Rappel : reconnaître une deprecation

À retenir en priorité
  1. La documentation et le signal d'exécution sont distincts.
  2. Un marqueur PHPDoc ne déclenche pas seul une erreur.
Marqueur Pour qui
l'annotation PHPDoc @deprecated, avec la version le lecteur du code
l'appel trigger_deprecation() le code qui tourne

Une deprecation n'entre que dans une mineure, jamais sur du code nouveau ; le code déprécié ne disparaît qu'à la majeure suivante.

Une notice, et elle est silencée

À retenir en priorité
  1. La deprecation conserve la compatibilité.
  2. Elle doit néanmoins être suivie et corrigée.

trigger_deprecation() appelle @trigger_error(…, \E_USER_DEPRECATED), avec un message qui commence par Since <paquet> <version>:. Sur PHP 8.4, display_errors actif :

Situation Ce qu'on voit
trigger_deprecation(), aucun handler rien ; le script continue
trigger_error(…, E_USER_DEPRECATED) sans @ Deprecated: … dans l'output
handler d'erreurs de Symfony + journal une entrée info : User Deprecated: Since acme/pkg 1.2: …

Le handler de Symfony ne lève jamais d'exception pour une deprecation, même réglé pour lever à tous les niveaux (throwAt(E_ALL, true)) : un E_USER_WARNING devient une ErrorException, une deprecation reste en info. L'option framework.php_errors.throw, active en dev, n'y change donc rien.

Les voir

À retenir en priorité
  1. Collecter et faire échouer sont deux réglages.
  2. Vérifier le comportement de la version PHPUnit utilisée.
  • En dev : la debug toolbar les montre, parce que le handler de Symfony les recueille.
  • Dans le journal : framework.php_errors.log vaut true, et accepte une table qui associe un niveau de journal à chaque niveau d'erreur PHP.
framework:
    php_errors:
        log:
            !php/const \E_USER_DEPRECATED: !php/const Psr\Log\LogLevel::ERROR
  • Dans les tests : PHPUnit seul ne montre rien. Sur PHPUnit 11.5 :
Configuration Résultat
failOnDeprecation="true" seul OK, exit code 0
<source ignoreSuppressionOfDeprecations="true"> la deprecation est listée ; code 0
les deux la deprecation est listée ; exit code 1

Les corriger

À retenir en priorité
  1. Corriger progressivement réduit le risque.
  2. Ne pas attendre la suppression pour commencer.

composer update "symfony/*", lire le file UPGRADE de la version atteinte, corriger progressivement. Pour une majeure : dernière mineure d'abord, zéro deprecation, puis la majeure.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Un signal absent peut être un défaut de collecte.
  2. La preuve dépend aussi du chemin exécuté.
Visibilité des dépréciations et échéance de migration
  • Une deprecation ne fait échouer ni la Request ni le test par elle-même.
  • La notice est silencée : rien dans l'output, et sans handler d'erreurs, aucune trace.
  • En dev, la debug toolbar les montre — parce que le handler de Symfony les recueille, pas parce qu'elles s'affichent.
  • Le code déprécié fonctionne jusqu'à la majeure suivante.
  • On corrige avant la majeure, pas après.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le handler recueille les notices.
  2. La toolbar présente ce qui a été collecté.

Si tu dois retenir seulement 7 choses :

  • trigger_deprecation() = @trigger_error(E_USER_DEPRECATED).
  • Silencée : rien n'échoue, rien ne s'affiche.
  • Message Since <paquet> <version>:.
  • Handler de Symfony : info, jamais d'exception, même avec throw.
  • Debug toolbar en dev ; journal partout.
  • PHPUnit : ignorée par défaut, même avec failOnDeprecation.
  • Dernière mineure, zéro deprecation, puis majeure.

Moyen mnémotechnique : « Silencée, journalisée, corrigée avant la majeure ».

deprecation = @E_USER_DEPRECATED ("Since pkg x.y:") → rien ne casse ; visible via un handler : journal info (php_errors.log), toolbar en dev,
jamais d'exception ; PHPUnit : rien par défaut ; dernière mineure → corriger → majeure
