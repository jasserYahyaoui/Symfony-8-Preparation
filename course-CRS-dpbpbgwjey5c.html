Objectif

Générer une URL depuis un template. Le generator lui-même et ses quatre types de référence sont traités dans le Module 05 — Routage.

L'essentiel

○ À comprendre

À retenir en priorité
  1. path() et url() génèrent depuis une route.
  2. absolute_url() complète un path.

Deux functions prennent un route name — path() pour un path, url() pour une URL complète — et deux autres prennent un path — absolute_url() et relative_path(). Le generator peut élargir la référence demandée, et une URL ne s'écrit jamais à la main.

Le schéma

Deux functions

À retenir en priorité
  1. Les deux functions partagent nom et parameters.
  2. Leur troisième argument ne signifie pas la même chose.
<a href="{{ path('blog_show', {slug: post.slug}) }}">Lire</a>
<link rel="canonical" href="{{ url('blog_show', {slug: post.slug}) }}">
Appel Type de référence Depuis /products/hover-board
path(nom, params) ABSOLUTE_PATH /post/mon-article
path(nom, params, true) RELATIVE_PATH ../post/mon-article
url(nom, params) ABSOLUTE_URL http://example.com/post/mon-article
url(nom, params, true) NETWORK_PATH //example.com/post/mon-article

Les deux premiers arguments sont communs ; le troisième diffère : relative pour path(), schemeRelative pour url().

Un numéro de salle suffit souvent à quelqu'un déjà dans le bâtiment ; une adresse complète convient à un destinataire extérieur. Pour un lien d'email, url() exprime cette adresse complète plutôt qu'un simple path.

Repère — Ce que le generator décide seul : Yes. A different host or scheme can require a network-path or absolute URL. Le generator respecte host et schemes. Le nom path() n'interdit pas ces formes nécessaires.

Repère — Deux functions voisines, sans route : No. It accepts a path. path() et url() génèrent depuis une route. absolute_url() complète un path.

Repère — L'escaping : No. That is the correct HTML representation. Le contexte HTML impose son escaping. Ne pas utiliser raw pour corriger un ampersand correctement échappé.

Ce que le generator décide seul

À retenir en priorité
  1. Le generator respecte host et schemes.
  2. Le nom path() n'interdit pas ces formes nécessaires.
  • Une route qui exige un autre schéma que la Request rend une URL absolue, même par path() : https://example.com/sec.
  • Une route liée à un autre host rend une référence //api.example.com/o.
  • Un parameter absent de la route part en query string : /post/x?ref=nl.
  • Une route inconnue lève RouteNotFoundException, que le template reçoit dans une RuntimeError.
  • Sans Request — une command qui envoie un email —, url() prend le host du contexte du router, localhost par défaut : http://localhost/post/z. framework.router.default_uri le corrige.

Deux functions voisines, sans route

HttpFoundationExtension ajoute deux functions qui prennent un path :

  • absolute_url('/images/logo.png') → http://example.com/images/logo.png, souvent combinée à asset() ;
  • relative_path('/human.txt') → ../human.txt depuis /products/hover-board.

relative_path() rend inchangée une URL complète : avec 'http://example.com/human.txt', le résultat est l'URL elle-même — contrairement à l'exemple de la documentation de référence ; le code 8.0 tranche.

L'escaping

À retenir en priorité
  1. Le contexte HTML impose son escaping.
  2. Ne pas utiliser raw pour corriger un ampersand correctement échappé.

path() et url() déclarent un is_safe_callback : leur output n'échappe pas sans parameters, ou avec un seul parameter littéral. Sinon il est échappé : le & d'une query string devient &amp;, ce qui est correct dans un attribute HTML.

Jamais d'URL écrite à la main

À retenir en priorité
  1. Le route name constitue le point de référence.
  2. Le generator encode et applique les contraintes de destination.

Une URL ne s'écrit jamais à la main dans un template : changer le path d'une route mettrait alors les liens en défaut sans qu'aucun test ne le signale. Le generator applique aussi le schéma et le host exigés, retire un parameter égal à sa default value et encode les valeurs.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Le troisième argument n'a pas le même sens dans les deux functions

    Le troisième argument n'a pas le même sens dans les deux functions : path relatif pour l'une, URL sans schéma pour l'autre.

  • Voir l’explication : La function de path peut retourner une URL absolue

    La function de path peut retourner une URL absolue, quand la route exige un autre schéma — ou une référence //hôte/… quand elle est liée à un autre host.

  • Voir l’explication : Un parameter absent de la route part en query string

    Un parameter absent de la route part en query string — une faute de frappe ne produit aucune erreur.

  • Path attendu par absolute_url()

    absolute_url() prend un path, pas un route name.

  • Voir l’explication : relative_path() laisse une URL complète inchangée

    relative_path() laisse une URL complète inchangée : seul un path, /human.txt, devient relatif — contrairement à l'exemple de la documentation de référence.

Application

À retenir en priorité
  1. path() et url() génèrent depuis une route.
  2. absolute_url() complète un path.
  3. Les deux functions partagent nom et parameters.
  4. Leur troisième argument ne signifie pas la même chose.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • path() : path absolu ; url() : URL complète.
  • true en troisième argument : relatif pour path(), sans schéma pour url().
  • Autre schéma → URL absolue ; autre host → //host/….
  • Parameter en plus → query string, sans erreur.
  • Plus d'un parameter → output échappé (&amp;).
  • absolute_url() / relative_path() : un path ; une URL complète reste inchangée.
  • Hors Request, url() rend http://localhost/… sans default_uri.

Moyen mnémotechnique : « path pour la page, url pour l'extérieur, et jamais à la main ».

path = /x, url = http://host/x ; true = relatif / sans schéma ; schéma ≠ → absolue, host ≠ → //host ;
extra → query ; >1 param → &amp; ; absolute_url/relative_path sur un path, URL complète inchangée
