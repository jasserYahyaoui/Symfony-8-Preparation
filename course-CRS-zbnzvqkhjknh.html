Objectif

Parcourir une séquence, connaître la variable loop et sa limite, le scope d'une loop, et écrire une condition sans se tromper sur ce qui est « vide ».

L'essentiel

À comprendre

À retenir en priorité
  1. La branche else décrit une séquence vide.
  2. Elle ne signifie pas que la dernière condition interne était fausse.

Twig parcourt une séquence avec for, propose une clause else pour le cas vide et une variable loop qui connaît sa position — mais pas toujours sa taille. Pas de break ni de continue : on filtre la séquence avant. Et dans une condition, « faux » et « vide » sont deux questions différentes.

Le schéma

À retenir en priorité
  1. index et first restent utilisables.
  2. last et length exigent une taille connue.

Ambre = décision, bleu = exécution. Le body peut tourner zéro fois. ensureTraversable transforme une valeur non itérable en tableau vide. La restauration conserve les affectations aux variables déjà présentes, retire les nouvelles et restaure les variables d'itération.

L'exemple

Exemple concret

À retenir en priorité
  1. Initialiser total avant la loop lui donne une portée extérieure.
  2. Les affectations de la loop mettent alors à jour cette variable existante.

Le catalogue du blog peut fournir une séquence de cartes, et une sélection vide doit encore produire une page utile. L'équipe ci-dessous conserve un exemple d'accumulation indépendant : total existe avant la boucle, chaque membre actif y contribue, puis sa valeur est affichée après. Ce calcul de présentation ne modifie pas les objets du catalogue.

{% set total = 0 %}
{% for member in team.members|filter(m => m.active) %}
    {{ not loop.first ? ' — ' }}{{ loop.index }}. {{ member.name }}
    {% set total = total + member.points %}
{% else %}
    Aucun membre actif.
{% endfor %}
Total : {{ total }}

Le séparateur est placé avant chaque élément sauf le premier : cela fonctionne aussi quand le résultat de filter n'est pas Countable. Filtrer un tableau conserve un tableau ; filtrer un Traversable produit un CallbackFilterIterator, sans loop.last. Convertir une grande séquence en tableau juste pour connaître sa fin augmente la mémoire utilisée.

La loop

Avec une liste d'ArticleView, chaque itération rend une carte et else remplace la liste lorsqu'aucune carte n'a été parcourue. Une entrée null déclenche aussi cette branche : le résultat visuel ne prouve donc pas que le catalogue a correctement fourni une collection vide. Le contrat de données reste à vérifier côté appelant.

  • {% for user in users %}…{% else %}…{% endfor %} : else s'exécute quand aucune itération n'a eu lieu. Une valeur non itérable — null, une string — est traitée comme une séquence vide : else aussi.
  • {% for key, user in users %} donne la key et la valeur ; users|keys les keys seules.
  • 0..10 va de 0 à 10 inclus, 'a'..'z' marche aussi, 3..0 descend ; range(0, 10, 5) change le pas.

🌍 In Real Life

La situation : l'archiviste traite les fiches d'une corbeille une à une. S'il n'en prend aucune, il pose l'avis « aucun dossier traité » ; cet avis ne prouve pas que le fournisseur avait envoyé le bon type de contenant.

L’équivalent dans Symfony : for parcourt la séquence et son else intervient lorsqu'aucune itération n'a eu lieu. ensureTraversable traite aussi une valeur non itérable comme une séquence vide.

Retour à la réalité technique : null déjà obtenu n'est pas une variable absente évaluée en mode strict, laquelle peut échouer avant le parcours. Le else ne signifie pas « aucun HTML visible » si le corps a tourné sans rien afficher. Clés et valeurs restent distinctes ; les plages incluent leurs bornes.

🧠 Comment le mémoriser : « Aucun passage, alors le panneau vide. » Image mentale : corbeille non parcourue et avis d'absence. Question-réflexe : ai-je effectué zéro itération ou simplement masqué toutes les sorties ?

⚠️ À ne pas confondre : absence d'itération, absence de variable et absence de contenu affiché.

Repère de l’exemple :

Question: Why is total initialized before the Twig for loop?

Answer: An existing outer variable can be updated by the loop and read afterward; a variable first created inside the loop does not escape its scope.

Initialiser total avant la loop lui donne une portée extérieure. Les affectations de la loop mettent alors à jour cette variable existante.

La variable `loop`

Pour séparer les titres sans séparateur final, loop.last semble commode. Mais si la source devient un générateur, Twig ne connaît pas sa taille à l'avance. Mettre le séparateur avant chaque titre sauf le premier préserve le parcours sans charger toute la séquence juste pour compter.

Variable Contenu
loop.index / loop.index0 itération courante, à partir de 1 / de 0
loop.revindex / loop.revindex0 itérations restantes, à partir de 1 / de 0
loop.first / loop.last vrai à la première / à la dernière
loop.length taille de la séquence
loop.parent le contexte englobant

La limite : length, revindex, revindex0 et last n'existent que pour un array ou un object Countable — un ArrayIterator les a. Sur un generator ou un iterator non Countable, ils manquent : RuntimeError avec strict_variables, null sans. loop.index et loop.first fonctionnent toujours.

🌍 In Real Life

La situation : sur un tapis de fiches, l'agent connaît le numéro de celle qu'il tient et sait s'il vient de commencer. Sans inventaire total, il ne sait pas combien restent ni si cette fiche est la dernière.

L’équivalent dans Symfony : loop.index, index0 et first décrivent le parcours en cours. length, revindex, revindex0 et last exigent une séquence dont Twig connaît la taille, tableau ou itérable Countable.

Retour à la réalité technique : un générateur ordinaire ne fournit pas ces propriétés de fin ; leur accès absent dépend de strict_variables. Utiliser un séparateur avant chaque élément sauf le premier évite de matérialiser toute la séquence pour compter. loop.parent est le contexte englobant, pas directement le numéro de boucle extérieure.

🧠 Comment le mémoriser : « Je sais où j'en suis, pas toujours ce qu'il reste. » Image mentale : compteur croissant devant un tapis dont la fin est cachée. Question-réflexe : ma séquence est-elle comptable avant de demander last ?

⚠️ À ne pas confondre : itérable, Countable et tableau déjà matérialisé.

Le guide d'une visite connaît toujours l'arrêt courant, mais ne sait pas forcément combien d'arrêts un flux produira. Sur un generator non Countable, index existe alors que last et length peuvent manquer.

Repère — Le scope d'une loop :

Question: How can a total updated inside a loop remain available afterwards?

Answer: Declare it before the loop.

Une variable créée seulement dans la loop n'en sort pas. Une variable déjà déclarée conserve sa valeur mise à jour.

Le scope d'une loop

À retenir en priorité
  1. Une variable créée seulement dans la loop n'en sort pas.
  2. Une variable déjà déclarée conserve sa valeur mise à jour.

Un compteur préparé avant les cartes conserve ses mises à jour ; un libellé temporaire créé dans une carte disparaît à la sortie. La variable d'itération a encore un autre rôle : elle est restaurée, pas promue en « dernier article affiché ». Cette distinction explique le résultat après endfor sans supposer que toutes les affectations se comportent pareil.

  • Une variable créée par set dans la loop n'existe plus après endfor.
  • Une variable déclarée avant garde la dernière valeur reçue dedans : c'est ainsi qu'on cumule un total.
  • La variable de loop elle-même retrouve sa valeur d'avant : après {% set u = 'outer' %}{% for u in ['a', 'b'] %}{% endfor %}, u vaut outer.

🌍 In Real Life

La situation : pendant le traitement, l'archiviste met à jour un total préparé avant la séance, utilise des notes temporaires et emprunte une étiquette « fiche courante ». À la fin, le total reste, les notes disparaissent, l'étiquette retrouve son état initial.

L’équivalent dans Symfony : les variables ordinaires déjà présentes conservent leurs affectations dans la boucle ; celles créées à l'intérieur ne sortent pas. Les variables d'itération sont restaurées, et ne deviennent pas implicitement le dernier élément.

Retour à la réalité technique : ces règles concernent le contexte Twig, pas une transaction ni une restauration profonde des objets. Initialiser l'accumulateur avant for permet aussi de définir son résultat si aucune itération n'a lieu.

🧠 Comment le mémoriser : « Total conservé, brouillon retiré, étiquette restaurée. » Image mentale : trois objets rangés différemment après le travail. Question-réflexe : est-ce un accumulateur préexistant, une nouvelle variable ou la variable d'itération ?

⚠️ À ne pas confondre : portée des variables, restauration des variables d'itération et effets sur des objets partagés.

Filtrer et découper

À retenir en priorité
  1. filter sélectionne les éléments parcourus.
  2. La numérotation suit alors les éléments réellement retenus.

Pour numéroter seulement les articles retenus, filtre avant de parcourir. Un if intérieur masque le HTML mais l'itération a déjà eu lieu. Cette sélection de présentation ne doit pas servir de contrôle d'accès : les données non autorisées ne devraient pas être remises au template en espérant qu'un filtre les cachera.

Pas de break ni de continue, et ForTokenParser refuse une condition sur le tag for lui-même. On restreint la séquence :

{% for user in users|filter(u => u.isActive) %}{{ user.name }}{% endfor %}
{# Autre stratégie : afficher les dix premiers, sans filtrage. #}
{% for user in users|slice(0, 10) %}{{ user.name }}{% endfor %}

Avec un if dans le body, loop.index compte les éléments sautés et loop.last peut tomber sur un élément non affiché ; avec filter, la numérotation suit ce qui est affiché.

🌍 In Real Life

La situation : numéroter une pile puis masquer certaines fiches laisse des trous. Sélectionner d'abord les fiches à présenter permet ensuite une numérotation continue de cette sélection.

L’équivalent dans Symfony : filter construit le parcours pertinent ; un if dans le corps ne retire pas l'itération déjà comptée. slice limite une portion de la séquence ; Twig3.22 n'offre pas les tags break ou continue du modèle PHP.

Retour à la réalité technique : filtre et découpe ne sont pas un contrôle d'accès et ne garantissent pas la même stratégie mémoire selon l'itérable. Sur un Traversable filtré, loop.last peut rester indisponible. Masquer un résultat ne doit pas servir à remettre au template des données non autorisées.

🧠 Comment le mémoriser : « Sélectionner avant de numéroter. » Image mentale : fiches retenues alignées avant l'attribution des numéros. Question-réflexe : ma condition change-t-elle les éléments parcourus ou seulement leur affichage ?

⚠️ À ne pas confondre : sélection de présentation, interruption d'un parcours et autorisation métier.

Les conditions

À retenir en priorité
  1. Les tests utilisent is ou is not.
  2. same as compare strictement.

Avant d'afficher un titre facultatif, is defined vérifie sa présence ; is not null répond à une autre question. Pour comparer une valeur sans conversion de type, utilise same as. Ces tests de rendu ne remplacent pas les contraintes Validator qui décident si une saisie est acceptable.

{% if %}, {% elseif %}, {% else %}. Les tests s'écrivent avec is et se nient par is not : constant, defined, divisible by, empty, even, iterable, mapping, null (alias none), odd, same as, sequence. Pas d'operator === : la comparaison stricte est le test same as, et === ne compile pas.

🌍 In Real Life

La situation : un contrôleur de fiche peut demander « la case existe-t-elle ? », « contient-elle une valeur non nulle ? » ou « est-ce exactement cette valeur de ce type ? ». Une seule case à cocher ne répond pas à toutes ces questions.

L’équivalent dans Symfony : les tests Twig is defined, is not null et is same as portent sur des propriétés différentes. if et ses branches choisissent ensuite le contenu à rendre.

Retour à la réalité technique : en Twig3.22, same as fournit la comparaison stricte, pas l'opérateur PHP ===. Une vérification d'existence peut protéger un accès facultatif ; elle ne certifie ni la validité métier de la donnée ni le droit de l'afficher.

🧠 Comment le mémoriser : « Poser la bonne question avant de cocher. » Image mentale : trois questions distinctes devant la même case. Question-réflexe : existence, nullité, égalité stricte ou vérité sont-elles mon critère ?

⚠️ À ne pas confondre : test de rendu, validation de saisie et autorisation.

Question: Is numeric zero empty according to Twig's empty test?

Answer: No. It is false in a condition but not empty.

Truthiness et empty répondent à deux questions différentes. Une collection Countable vide peut être vraie mais empty.

Vrai, faux, vide : trois questions différentes

À retenir en priorité
  1. Truthiness et empty répondent à deux questions différentes.
  2. Une collection Countable vide peut être vraie mais empty.

Un compteur de zéro commentaire est une donnée valide, non une absence. Une collection objet vide peut au contraire être vraie dans if. Pour une séquence à usage unique, évite de la consommer une première fois avec is empty : le else du parcours peut produire l'état vide sans exiger ce parcours préalable.

Valeur Dans un if is empty
'', [], null faux vide
0, '0' faux pas vide
' ' vrai pas vide
collection Countable vide vrai (tout object est vrai) vide

is defined porte sur l'existence, pas sur la valeur. Sur un generator, is empty le parcourt pour compter : la loop qui suit lève « Cannot traverse an already closed generator ».

🌍 In Real Life

La situation : « zéro dossier » est une information renseignée ; une boîte existe même lorsqu'elle est vide. Pour savoir si un tapis à passage unique contient des fiches, les faire toutes défiler une première fois peut empêcher de les traiter ensuite.

L’équivalent dans Symfony : if, is empty et is defined n'évaluent pas la même propriété. Zéro est faux mais non vide pour le test Twig ; une collection objet usuelle peut être vraie et vide. Tester un générateur avec is empty peut le consommer.

Retour à la réalité technique : ne déduis pas la vacuité de la seule conversion booléenne, dont les objets PHP internes peuvent avoir des cas particuliers. Pour une séquence à usage unique, for … else traite le cas sans itération pendant le parcours utile, sans comptage préalable ; cela ne rend pas le générateur réutilisable.

🧠 Comment le mémoriser : « Zéro renseigné, boîte vide, tapis consommé : trois états. » Image mentale : compteur0, boîte vide et tapis déjà déroulé. Question-réflexe : quel test répond à mon besoin sans consommer ma source ?

⚠️ À ne pas confondre : vérité, vacuité, existence et possibilité de parcourir à nouveau.

Pièges d'examen

Piège à éviter

  • Voir l’explication : La moitié des properties de loop n'existent pas sur un generator ni sur un iterator non Countable

    La moitié des properties de loop n'existent pas sur un generator ni sur un iterator non Countable ; l'index et le test de première itération, si. Un ArrayIterator, qui est Countable, les a toutes.

  • Point de départ de loop.index

    L'index commence à 1.

  • Condition d’exécution du else d’une boucle

    La clause else d'une loop se déclenche sur une séquence vide.

  • Voir l’explication : Une variable créée dans une loop n'en sort pas

    Une variable créée dans une loop n'en sort pas ; déclarée avant, elle garde sa dernière valeur.

  • Distinguer les tests booléen et empty

    0 est faux mais n'est pas vide ; une collection vide est vraie mais vide.

Application

À retenir en priorité
  1. index et first restent utilisables.
  2. last et length exigent une taille connue.
  3. Les tests utilisent is ou is not.
  4. same as compare strictement.

Fiche express

À mémoriser

Si tu dois retenir seulement 8 choses :

  • else de loop : séquence vide ou non itérable.
  • loop.index part de 1.
  • last, length, revindex, revindex0 : array ou Countable.
  • Generator : RuntimeError sous strict_variables, null sans.
  • Variable créée dedans perdue, déclarée avant gardée.
  • Ni break ni continue : filter, slice, sort.
  • same as remplace ===, qui ne compile pas.
  • 0 faux mais pas vide ; collection vide vraie mais vide.

Moyen mnémotechnique : « else pour le vide, Countable pour la fin, avant pour garder ».

for…else (vide ou non itérable) ; loop.index dès 1 ; last/length/revindex = array ou Countable ;
scope : créé perdu, déclaré avant gardé ; filter au lieu de break ; same as pour === ; if ≠ empty
