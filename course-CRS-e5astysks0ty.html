Objectif

Consommer une file, comprendre pourquoi un worker doit s'arrêter tout seul, et ce qu'il garde — ou non — d'un message au suivant.

L'essentiel

À comprendre

À retenir en priorité
  1. Un process long ne recharge pas le code spontanément.
  2. Le redémarrage applique la nouvelle version.

Un worker est un processus PHP qui reste vivant pour recevoir plusieurs messages. Il demande des enveloppes aux receivers, puis les transmet au bus pour exécuter les handlers. Contrairement à une requête HTTP ordinaire, le prochain travail peut réutiliser les mêmes objets en mémoire.

Trois responsabilités doivent rester distinctes : le worker traite les messages ; les mécanismes d'arrêt lui demandent de terminer proprement ; le superviseur lance un nouveau processus. messenger:stop-workers ne recharge donc pas le code dans le processus existant.

Le schéma

À retenir en priorité
  1. L'arrêt respecte le message en cours.
  2. Le superviseur assure la reprise.

Bleu : opérations ; ambre : décisions ; vert : sortie. Le dessin simplifie l'itération des receivers : la recherche poursuit leur ordre jusqu'à trouver un lot ou constater qu'ils sont tous vides. Les événements et acquittements ne sont pas détaillés ici.

Les limites configurées et le signal de redémarrage permettent un arrêt gracieux aux points de contrôle de la boucle ; ils n'interrompent pas préemptivement le handler en cours. Un arrêt brutal du processus par le système n'offre pas cette garantie. Les receivers et les workers doivent aussi pouvoir accéder au signal partagé prévu par le déploiement.

L'exemple

Exemple concret

À retenir en priorité
  1. L'ordre des receivers définit la priorité.
  2. Ce n'est pas un tourniquet équitable : l'iterable d'un receiver est normalement parcouru avant de reprendre au premier receiver ; l'arrêt est vérifié après chaque message.
# lancé par Supervisor ou systemd, relancé dès qu'il s'arrête
php bin/console messenger:consume async_high async \
    --limit=100 --memory-limit=128M --time-limit=3600

# à chaque deployment, après la mise en place du nouveau code
php bin/console messenger:stop-workers

La command

À retenir en priorité
  1. Les limites évitent un process sans renouvellement.
  2. Prévoir la relance extérieure.
  • Plusieurs receivers sont consultés dans l'ordre donné. Le worker parcourt l'itérable renvoyé par get() avant de recommencer un tour de consultation. Si high-1 est disponible au premier polling, puis low fournit low-1 et low-2, l'ordre peut être high-1, low-1, low-2. Si high-2 arrive pendant ce module de low, cela ne garantit pas qu'il passe avant low-2. La priorité concerne la consultation des receivers, pas une interruption après chaque message.
  • Les options de messenger:consume en 8.0 : --limit, --failure-limit, --memory-limit, --time-limit, --sleep, --bus, --queues, --no-reset, --all, --exclude-receivers, --keepalive.
Appel Résultat
messenger:consume low --exclude-receivers=high exit 1 : l'option exige --all
sans récepteur, en mode interactif une question : quels récepteurs consommer ?
sans récepteur, non interactif exit 0 : « Consuming messages from transport "" » — le worker ne lit rien

Un worker est un process long

À retenir en priorité
  1. La limite porte sur les messages reçus.
  2. Un échec consomme aussi le budget.
  3. Renouveler les workers ne dispense ni du reset des services ni de corriger les fuites.

Un processus PHP durable peut accumuler de la mémoire ou garder des objets périmés. Le renouveler régulièrement borne sa durée de vie, mais ne dispense pas de corriger une fuite ni de nettoyer un état propre au message précédent.

--limit=10          # après 10 messages
--memory-limit=128M # au-delà de ce seuil
--time-limit=3600   # après une heure
--failure-limit=5   # après trop d'échecs
  • L'arrêt est gracieux : le message en cours est terminé.
  • --limit compte les messages reçus, pas les réussis : trois messages, le premier en échec, --limit=2 — l'échec et le deuxième, puis l'arrêt.

Le deployment

À retenir en priorité
  1. Le signal n'interrompt pas brutalement le handler.
  2. Les nouveaux workers ne doivent pas s'arrêter pour l'ancien signal.

Un worker démarré avant un deployment exécute l'ancien code. messenger:stop-workers ne tue rien : elle pose un signal — une date dans un cache — que chaque worker lit après le message en cours. Seul un worker démarré avant cette date s'arrête ; celui que le superviseur relance n'est pas visé.

L'état entre deux messages

À retenir en priorité
  1. Les instances peuvent survivre entre messages.
  2. reset() nettoie leur état temporaire.

Le worker garde les mêmes instances de services, mais entre deux messages ResetServicesListener appelle reset() sur chaque service qui implémente ResetInterface (ou porte le tag kernel.reset). Trois messages, deux services qui comptent ce qu'ils ont vu :

Worker Service ordinaire Service ResetInterface
par défaut 1, 2, 3 — l'état s'accumule 1, 1, 1
--no-reset 1, 2, 3 1, 2, 3

Le transport in-memory:// est lui-même réinitialisable : le reset vide sa file. Il sert aux tests, pas à un worker.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La mémoire logique peut alors s'accumuler.
  2. Utiliser cette option en connaissance de l'état conservé.
  • Voir l’explication : Un worker exécute le code chargé à son démarrage

    Un worker exécute le code chargé à son démarrage : sans redémarrage, un deployment ne l'atteint pas.

  • Voir l’explication : messenger:stop-workers ne tue pas

    messenger:stop-workers ne tue pas : elle demande un arrêt après le message courant.

  • Voir l’explication : Plusieurs receivers : ordre de priorité au polling

    Plusieurs receivers : ordre de priorité au polling, pas de tourniquet équitable ni de préemption du module courant.

  • Voir l’explication : Les instances de services restent partagées entre messages.

    Les instances de services restent partagées entre messages. Les services réinitialisables voient leur état nettoyé par reset() ; --no-reset désactive cette remise à zéro, pas le partage des instances.

  • Voir l’explication : Renouvellement, reset et correction des fuites sont complémentaires.

    Renouvellement, reset et correction des fuites sont complémentaires. Les limites organisent l'exploitation ; elles ne rendent pas acceptable une fuite identifiée ni un handler bloqué.

Fiche express

À mémoriser

À retenir en priorité
  1. Le transport mémoire sert aux tests.
  2. Il ne remplace pas une file durable.

Si tu dois retenir seulement 7 choses :

  • messenger:consume high low : ordre de polling ; un nouveau message prioritaire n'interrompt pas le lot en cours.
  • Un worker s'arrête de lui-même ; un superviseur le relance.
  • --limit compte les messages reçus, échecs compris.
  • messenger:stop-workers : après le message courant, workers plus anciens seulement.
  • ResetInterface : remis à zéro entre deux messages, sauf --no-reset.
  • Sans récepteur, non interactif : un worker qui ne lit rien.
  • --exclude-receivers exige --all.

Moyen mnémotechnique : « lire dans l'ordre, s'arrêter entre deux, repartir neuf ».

consume a b : priorité au polling, pas de préemption du lot ; arrêt gracieux aux points de contrôle, pas pendant le handler ;
stop-workers = date en cache, workers démarrés avant ; reset ResetInterface sauf --no-reset ; --exclude-receivers ⇒ --all

Revoir : L'exemple

What does messenger:consume high low prioritize?

It polls high before low. If a receiver yields messages, it normally consumes that returned iterable before polling again from high; low is considered when high yields none. Stop checks occur after each message.

L'ordre des receivers définit la priorité. Ce n'est pas un tourniquet équitable : l'iterable d'un receiver est normalement parcouru avant de reprendre au premier receiver ; l'arrêt est vérifié après chaque message.
