Objectif

Le dispatch de ImportBlogFile a confié un travail à un transport réellement différé. La page GET /blog/42 peut être terminée alors que ce travail attend encore. Il manque maintenant un process qui récupère le message et appelle le bus : le worker. Suivons plusieurs imports pour comprendre ses priorités, son état en mémoire et son renouvellement au déploiement.

L'essentiel

À comprendre

À retenir en priorité
  1. Un process long ne recharge pas le code spontanément.
  2. Le redémarrage applique la nouvelle version.

Un worker est un processus PHP qui reste vivant pour recevoir plusieurs messages. Il demande des enveloppes aux receivers, puis les transmet au bus pour exécuter les handlers. Contrairement à une requête HTTP ordinaire, le prochain travail peut réutiliser les mêmes objets en mémoire. Le worker n'hérite pas automatiquement de la Request ni de l'identité de son auteur : le message doit porter les références nécessaires à un traitement autonome.

Trois responsabilités doivent rester distinctes : le worker traite les messages ; les mécanismes d'arrêt lui demandent de terminer proprement ; le superviseur lance un nouveau processus. messenger:stop-workers ne recharge donc pas le code dans le processus existant. De même, le reset d'un service nettoie son état ; il ne recompile pas le service container et ne redémarre pas PHP.

Le schéma

À retenir en priorité
  1. L'arrêt respecte le message en cours.
  2. Le superviseur assure la reprise.

Supposons deux receivers configurés : async_high pour les notifications urgentes et async pour les imports. Le mot lot désigne ici l'iterable renvoyé par get(), pas nécessairement un handler utilisant l'API de traitement par lots de Messenger.

Bleu : opérations ; ambre : décisions ; vert : sortie. Le dessin simplifie l'itération des receivers : la recherche poursuit leur ordre jusqu'à trouver un lot ou constater qu'ils sont tous vides. Les événements et acquittements ne sont pas détaillés ici. Pour un handler ordinaire, le worker ajoute ReceivedStamp, ConsumedByWorkerStamp et un callback d'acquittement, puis dispatche sur le bus. Le premier stamp évite que le middleware d'envoi remette le message dans sa destination initiale.

Un retour sans échec mène normalement à l'acquittement du receiver : le message reçu a été traité. Une exception de dispatch est capturée et passe par le chemin d'échec, ses événements et le rejet. Cela ne garantit pas la survie du process à toute panne : une exception du receiver ou d'un listener peut encore interrompre la boucle. Les batch handlers peuvent différer leur acquittement ; le retour d'un seul dispatch ne suffit donc pas à conclure qu'un lot métier entier a réussi.

Un second problème arrive au déploiement : même si la boucle fonctionne, elle garde son code déjà chargé. Le schéma suivant montre qui demande l'arrêt et qui crée le process suivant.

Les limites configurées et le signal de redémarrage permettent un arrêt gracieux aux points de contrôle de la boucle ; ils n'interrompent pas préemptivement le handler en cours. Un arrêt brutal du processus par le système n'offre pas cette garantie. La command de signalement et les workers doivent accéder au même signal de cache prévu par le déploiement. Ce cache de coordination n'est pas le cache HTTP de la page article.

L'exemple

Exemple concret

À retenir en priorité
  1. L'ordre des receivers définit la priorité.
  2. Ce n'est pas un tourniquet équitable : l'iterable d'un receiver est normalement parcouru avant de reprendre au premier receiver ; l'arrêt est vérifié après chaque message.

Exemple d'exploitation pour Symfony 8.0 sous PHP 8.4 : les deux transports sont déjà installés, configurés et alimentés. Ces commands sont à lancer dans le projet concerné, pas des opérations effectuées pendant la lecture du cours. La politique du superviseur doit réellement prévoir leur relance.

# lancé par Supervisor ou systemd, relancé dès qu'il s'arrête
php bin/console messenger:consume async_high async \
    --limit=100 --memory-limit=128M --time-limit=3600

# à chaque deployment, après la mise en place du nouveau code
php bin/console messenger:stop-workers

Au lancement, la première command annonce les deux transports consommés. Le résultat attendu est une consultation de async_high avant async, puis un arrêt dès qu'une condition configurée est constatée aux points de contrôle. stop-workers, exécutée séparément au déploiement, demande cet arrêt ; elle ne prouve pas qu'un process de remplacement a déjà commencé.

La command

À retenir en priorité
  1. Les limites évitent un process sans renouvellement.
  2. Prévoir la relance extérieure.

🌍 In Real Life

La situation : le secrétariat du blog consulte d'abord le casier urgent, puis celui des imports ; il termine le lot déjà sorti d'un casier.

L’équivalent dans Symfony : ordre des casiers → ordre des receivers ; lot sorti → iterable de get() ; traitement des fiches → redispatch au bus par le worker.

Retour à la réalité technique : la préférence de consultation n'interrompt pas nécessairement un lot pour chaque nouvelle arrivée urgente. Un receiver toujours alimenté peut retarder les suivants.

🧠 Comment le mémoriser : « Priorité au casier, pas interruption du dossier. » Image mentale : une pile déjà posée sur le bureau. Question-réflexe : parle-t-on d'ordre de polling ou de priorité des handlers ?

⚠️ À ne pas confondre : ordre des receivers et tri des handlers d'un même message.

L'ordre des noms est une décision d'exploitation : des notifications constamment disponibles dans le premier receiver peuvent retarder les imports. Ce n'est pas la priorité d'un handler parmi plusieurs handlers d'un message.

  • Plusieurs receivers sont consultés dans l'ordre donné. Le worker parcourt l'itérable renvoyé par get() avant de recommencer un tour de consultation. Si high-1 est disponible au premier polling, puis low fournit low-1 et low-2, l'ordre peut être high-1, low-1, low-2. Si high-2 arrive pendant ce lot de low, cela ne garantit pas qu'il passe avant low-2. La priorité concerne la consultation des receivers, pas une interruption après chaque message.
  • Les options de messenger:consume en 8.0 : --limit, --failure-limit, --memory-limit, --time-limit, --sleep, --bus, --queues, --no-reset, --all, --exclude-receivers, --keepalive.

--queues exige des receivers capables de sélectionner ces queues ; --keepalive dépend du support correspondant et de son déclenchement dans l'environnement d'exécution. Une option ne crée pas une capacité du transport.

Avant de diagnostiquer une file vide, regarder aussi les valeurs par défaut : ConsumeMessagesCommand::configure() choisit automatiquement l'unique receiver déclaré lorsqu'il n'y en a qu'un. Les deux lignes « sans récepteur » ci-dessous concernent au contraire plusieurs receivers déclarés, sans argument explicite ni --all.

Appel Résultat
messenger:consume low --exclude-receivers=high exit 1 : l'option exige --all
sans récepteur, en mode interactif une question : quels récepteurs consommer ?
sans récepteur, non interactif, plusieurs receivers déclarés « Consuming messages from transport "" » — aucune lecture ; exit 0 après un arrêt normal

Un worker est un process long

À retenir en priorité
  1. La limite porte sur les messages reçus.
  2. Un échec consomme aussi le budget.
  3. Renouveler les workers ne dispense ni du reset des services ni de corriger les fuites.

Un processus PHP durable peut accumuler de la mémoire ou garder des objets périmés. Après plusieurs fichiers importés, un cache local du dernier auteur ou une collection qui grossit peut affecter le travail suivant. Renouveler le process limite cette accumulation aux points de contrôle, mais ne dispense pas de corriger une fuite ni de nettoyer l'état propre au message précédent.

Ces fragments sont des options à ajouter à messenger:consume, pas des commands autonomes :

--limit=10          # après 10 messages
--memory-limit=128M # au-delà de ce seuil
--time-limit=3600   # après une heure
--failure-limit=5   # après trop d'échecs
  • Les limites demandent un arrêt gracieux, lorsque la boucle reprend la main. --time-limit=3600 n'interrompt pas un handler bloqué à la seconde exacte ; une limite mémoire applicative n'empêche pas une panne brutale de PHP avant le prochain contrôle.
  • --limit compte les messages reçus, pas les réussis : trois messages, le premier en échec, --limit=2 — l'échec et le deuxième, puis l'arrêt. Le listener compte les WorkerRunningEvent non idle, pas les seuls WorkerMessageHandledEvent. Ce budget est distinct du nombre de retries autorisés pour un même message.

Le deployment

À retenir en priorité
  1. Le signal n'interrompt pas brutalement le handler.
  2. Les nouveaux workers ne doivent pas s'arrêter pour l'ancien signal.

🌍 In Real Life

La situation : une nouvelle procédure d'import du blog est publiée, mais le collègue en poste utilise encore son ancien manuel.

L’équivalent dans Symfony : ancien manuel en main → classes déjà chargées ; avis daté de relève → signal de messenger:stop-workers ; nouvelle équipe → processus relancé par le superviseur.

Retour à la réalité technique : le signal demande un arrêt aux points de contrôle des workers antérieurs à sa date. Il ne remplace pas leur code en mémoire et ne relance pas lui-même les processus.

🧠 Comment le mémoriser : « Nouveau code, nouveau poste. » Image mentale : un manuel échangé à la relève. Question-réflexe : qui détecte l'arrêt et qui assure le redémarrage ?

⚠️ À ne pas confondre : vider le cache et renouveler les classes d'un processus vivant.

Le nouvel importeur est déployé, mais les classes déjà chargées par un worker restent celles de l'ancienne version. Vider le cache du site ne les remplace pas dans ce process. messenger:stop-workers écrit une date dans le cache de coordination ; StopWorkerOnRestartSignalListener la compare à la date de démarrage du worker lors de WorkerRunningEvent.

Cette vérification arrive après un traitement, mais aussi lors d'un tour idle : il n'est pas nécessaire qu'un nouveau message arrive pour qu'un worker inactif constate le signal. Seul un worker démarré avant la date stockée demande son arrêt. Le superviseur lance ensuite un nouveau process sur le code déployé ; cet ancien signal ne l'arrête pas à son tour.

L'état entre deux messages

À retenir en priorité
  1. Les instances peuvent survivre entre messages.
  2. reset() nettoie leur état temporaire.

🌍 In Real Life

La situation : le même bureau traite plusieurs imports du blog ; les notes du précédent auteur doivent être effacées avant le dossier suivant.

L’équivalent dans Symfony : bureau conservé → service partagé ; notes temporaires → état mutable ; nettoyage prévu → méthode de reset enregistrée.

Retour à la réalité technique : l'intégration de reset appelle les méthodes configurées des services concernés. Elle ne reconstruit pas systématiquement le conteneur et ne devine pas quel état votre méthode devrait nettoyer.

🧠 Comment le mémoriser : « Même bureau, notes neuves. » Image mentale : un tableau effacé entre deux dossiers. Question-réflexe : quel état peut survivre au message précédent ?

⚠️ À ne pas confondre : reset d'un service, redémarrage du worker et compilation du conteneur.

Un service partagé peut conserver le dernier auteur traité entre deux ImportBlogFile. Le container ne reconstruit pas systématiquement ce service. Pour l'état temporaire, il faut une méthode de remise à zéro et son enregistrement dans le mécanisme de reset.

Avec l'intégration FrameworkBundle habituelle, l'autoconfiguration d'un service Symfony\Contracts\Service\ResetInterface permet son inscription via kernel.reset. Le tag explicite peut désigner une autre méthode de nettoyage. Ce travail de préparation n'est pas refait à chaque message.

À l'exécution, ResetServicesListener demande au resetter de nettoyer les services concernés sur WorkerRunningEvent non idle, ainsi qu'à l'arrêt. Le resetter appelle les méthodes configurées ; ce n'est pas une nouvelle instance pour chaque travail. Voici trois messages ordinaires et deux services qui incrémentent un compteur, celui réinitialisable le remettant effectivement à zéro :

Worker Service ordinaire Service ResetInterface
par défaut 1, 2, 3 — l'état s'accumule 1, 1, 1
--no-reset 1, 2, 3 1, 2, 3

Sans implémentation correcte du nettoyage, porter un tag ne suffit pas à isoler les auteurs. À l'inverse, ne vider que les données propres au message : un reset ne doit pas détruire arbitrairement l'état métier persistant.

Le transport in-memory:// est lui-même réinitialisable : le reset vide sa file interne. Un iterable déjà retourné par get() peut encore contenir ses Envelope ; cela ne le transforme pas en file durable pour les prochains tours ou un autre process. Il sert aux tests, pas au stockage des imports de production.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La mémoire logique peut alors s'accumuler.
  2. Utiliser cette option en connaissance de l'état conservé.
  • Voir l’explication : Le code déjà chargé reste dans le worker

    Le code déjà chargé reste dans le worker : déployer le nouvel importeur ne remplace pas ses classes en mémoire ; prévoir le renouvellement du process.

  • Voir l’explication : messenger:stop-workers ne tue pas

    messenger:stop-workers ne tue pas : le listener constate le signal à un point de contrôle, après le message courant ou pendant un tour idle. Le superviseur, pas cette command, assure la relance.

  • Voir l’explication : Plusieurs receivers : ordre de priorité au polling

    Plusieurs receivers : ordre de priorité au polling, pas de tourniquet équitable ni de préemption du lot courant. Un arrêt demandé peut interrompre la poursuite du lot après une Envelope ; une nouvelle arrivée prioritaire ne provoque pas à elle seule une interruption.

  • Voir l’explication : Les instances de services restent partagées entre messages.

    Les instances de services restent partagées entre messages. Les services réinitialisables voient leur état nettoyé par reset() ; --no-reset désactive cette remise à zéro, pas le partage des instances. Cela ne revient pas à compiler un nouveau container.

  • Voir l’explication : Renouvellement, reset et correction des fuites sont complémentaires.

    Renouvellement, reset et correction des fuites sont complémentaires. Les limites organisent l'exploitation ; elles ne rendent pas acceptable une fuite identifiée ni un handler bloqué. Et --limit n'est pas une limite de succès : un import échoué consomme aussi ce budget.

Fiche express

À mémoriser

À retenir en priorité
  1. Le transport mémoire sert aux tests.
  2. Il ne remplace pas une file durable.

Le worker donne une vie propre au travail différé : il reçoit, traite, nettoie et finit par sortir. La lecture de l'article et la consommation de l'import ne sont pas deux phases obligatoires d'une même Request.

Si tu dois retenir seulement 7 choses :

  • messenger:consume high low : ordre de polling ; un nouveau message prioritaire n'interrompt pas le lot en cours.
  • Un worker s'arrête de lui-même ; un superviseur le relance.
  • --limit compte les messages reçus, échecs compris.
  • messenger:stop-workers : aux points de contrôle, workers plus anciens seulement, y compris lorsqu'ils sont idle.
  • ResetInterface : remis à zéro entre deux messages, sauf --no-reset.
  • Sans argument receiver, non interactif : vérifier le défaut ; un seul receiver déclaré est choisi automatiquement, plusieurs ne le sont pas.
  • --exclude-receivers exige --all.

Moyen mnémotechnique : « lire dans l'ordre, s'arrêter entre deux, repartir neuf ».

consume a b : priorité au polling, pas de préemption du lot ; arrêt gracieux aux points de contrôle, pas pendant le handler ;
stop-workers = date en cache, workers démarrés avant ; reset ResetInterface sauf --no-reset ; --exclude-receivers ⇒ --all
