Objectif

Consommer une file, comprendre pourquoi un worker doit s'arrêter tout seul, et ce qu'il garde — ou non — d'un message au suivant.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Un process long ne recharge pas le code spontanément.
  2. Le redémarrage applique la nouvelle version.

Un worker est un process long : il lit ses files dans l'ordre donné, et s'arrête de lui-même sur une limite pour qu'un superviseur le relance. Après un deployment, messenger:stop-workers lui fait prendre le nouveau code. Entre deux messages, il garde ses services — sauf ceux qu'il remet à zéro.

Le schéma

À retenir en priorité
  1. L'arrêt respecte le message en cours.
  2. Le superviseur assure la reprise.

Tout ce qui arrête un worker passe par un listener, entre deux messages : aucune option ni command n'interrompt un traitement en cours.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. L'ordre des receivers définit la priorité.
  2. Ce n'est pas un tourniquet équitable.
# lancé par Supervisor ou systemd, relancé dès qu'il s'arrête
php bin/console messenger:consume async_high async \
    --limit=100 --memory-limit=128M --time-limit=3600

# à chaque deployment, après la mise en place du nouveau code
php bin/console messenger:stop-workers

La command

À retenir en priorité
  1. Les limites évitent un process sans renouvellement.
  2. Prévoir la relance extérieure.
  • Plusieurs transports sont consultés dans l'ordre donné : après chaque message, le worker repart du premier, et ne lit le second que si le premier est vide. Deux messages sur low, puis un sur high : messenger:consume high low --limit=3 traite high-1, low-1, low-2.
  • Les options de messenger:consume en 8.0 : --limit, --failure-limit, --memory-limit, --time-limit, --sleep, --bus, --queues, --no-reset, --all, --exclude-receivers, --keepalive.
Appel Résultat
messenger:consume low --exclude-receivers=high exit 1 : l'option exige --all
sans récepteur, en mode interactif une question : quels récepteurs consommer ?
sans récepteur, non interactif exit 0 : « Consuming messages from transport "" » — le worker ne lit rien

Un worker est un process long

À retenir en priorité
  1. La limite porte sur les messages reçus.
  2. Un échec consomme aussi le budget.

Un process PHP qui tourne des jours accumule de la mémoire et des objects périmés. La solution prévue n'est pas de corriger les fuites : c'est de s'arrêter régulièrement.

--limit=10          # après 10 messages
--memory-limit=128M # au-delà de ce seuil
--time-limit=3600   # après une heure
--failure-limit=5   # après trop d'échecs
  • L'arrêt est gracieux : le message en cours est terminé.
  • --limit compte les messages reçus, pas les réussis : trois messages, le premier en échec, --limit=2 — l'échec et le deuxième, puis l'arrêt.

Le deployment

À retenir en priorité
  1. Le signal n'interrompt pas brutalement le handler.
  2. Les nouveaux workers ne doivent pas s'arrêter pour l'ancien signal.

Un worker démarré avant un deployment exécute l'ancien code. messenger:stop-workers ne tue rien : elle pose un signal — une date dans un cache — que chaque worker lit après le message en cours. Seul un worker démarré avant cette date s'arrête ; celui que le superviseur relance n'est pas visé.

L'état entre deux messages

À retenir en priorité
  1. Les instances peuvent survivre entre messages.
  2. reset() nettoie leur état temporaire.

Le worker garde les mêmes instances de services, mais entre deux messages ResetServicesListener appelle reset() sur chaque service qui implémente ResetInterface (ou porte le tag kernel.reset). Trois messages, deux services qui comptent ce qu'ils ont vu :

Worker Service ordinaire Service ResetInterface
par défaut 1, 2, 3 — l'état s'accumule 1, 1, 1
--no-reset 1, 2, 3 1, 2, 3

Le transport in-memory:// est lui-même réinitialisable : le reset vide sa file. Il sert aux tests, pas à un worker.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. La mémoire logique peut alors s'accumuler.
  2. Utiliser cette option en connaissance de l'état conservé.

Un worker exécute le code chargé à son démarrage : sans redémarrage, un deployment ne l'atteint pas.

messenger:stop-workers ne tue pas : elle demande un arrêt après le message courant.

Plusieurs transports : priority stricte, pas de tourniquet.

Les services sont partagés entre messages, sauf ceux qui implémentent ResetInterface ; --no-reset supprime même cette remise à zéro.

Les limites ne sont pas un pansement : elles sont la façon prévue d'exploiter un worker.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le transport mémoire sert aux tests.
  2. Il ne remplace pas une file durable.

Si tu dois retenir seulement 7 choses :

  • messenger:consume high low : priority stricte, par l'ordre.
  • Un worker s'arrête de lui-même ; un superviseur le relance.
  • --limit compte les messages reçus, échecs compris.
  • messenger:stop-workers : après le message courant, workers plus anciens seulement.
  • ResetInterface : remis à zéro entre deux messages, sauf --no-reset.
  • Sans récepteur, non interactif : un worker qui ne lit rien.
  • --exclude-receivers exige --all.

Moyen mnémotechnique : « lire dans l'ordre, s'arrêter entre deux, repartir neuf ».

consume a b (ordre = priority, repart du premier) ; arrêt entre deux messages par listeners : limit (tout message), memory, time, failure ;
stop-workers = date en cache, workers démarrés avant ; reset ResetInterface sauf --no-reset ; --exclude-receivers ⇒ --all
