Objectif

Reconnaître ce qu'une interface peut et ne peut pas déclarer.

L'essentiel

À comprendre

À retenir en priorité
  1. Depuis PHP 8.1, une constant d'interface peut être redéfinie.
  2. final interdit cette redéfinition.

C'est quoi ?

Une interface définit un contrat que plusieurs classes peuvent respecter. Ses methods sont publiques et abstraites : elle annonce leur signature sans fournir leur body. Une class utilise implements puis fournit une implémentation compatible. On peut typer un parameter avec cette interface sans imposer une class concrète.

En PHP 8.4, une interface peut aussi déclarer des properties avec un contrat get, set ou les deux. Elle peut porter des constants ; depuis PHP 8.1 une constant non final peut être redéfinie. Ces possibilités ne lui donnent pas l'état partagé ni les bodies de methods d'une abstract class.

À quoi ça sert ?

Une prise normalisée impose une forme de connexion, sans imposer la construction de chaque appareil. La prise correspond à l'interface, chaque appareil à une class qui l'implémente, et l'utilisateur de la prise au code appelant. Limite : PHP vérifie la compatibilité des signatures et des accès, pas la qualité du comportement. Deux implémentations compatibles peuvent produire des résultats différents.

Le bénéfice est de remplacer une implémentation sans réécrire tous ses utilisateurs. Le contrat doit donc exprimer ce dont l'utilisateur a besoin, pas les détails internes d'un fournisseur particulier.

Où dans Symfony ?

Un service applicatif peut demander une interface dans son constructor. Le service container doit alors connaître l'implémentation à injecter, par exemple grâce à un alias explicite. PHP sait vérifier le type reçu ; il ne choisit pas lui-même l'implémentation. L'exemple utilise une construction manuelle pour isoler cette différence sans dépendance Symfony.

Comment, étape par étape ?

  1. Déclarer la capacité attendue dans une interface, ici produire une salutation à partir d'un nom.
  2. Implémenter sa method publiquement avec une signature compatible.
  3. Faire dépendre l'utilisateur de l'interface plutôt que de la class concrète.
  4. Choisir et fournir une implémentation lors de l'assemblage. Dans Symfony, cette responsabilité revient à la configuration du service container.
  5. Pour une property d'interface en PHP 8.4, vérifier séparément les accès get et set : readonly ne satisfait pas un contrat qui exige set.

Exemple concret PHP

Welcome ne connaît que Greeter. FrenchGreeter fournit le body de greet() ; remplacer cette implémentation ne change pas le type demandé par Welcome. La sortie est Bonjour Ada.

<?php
interface Greeter
{
    public function greet(string $name): string;
}

final class FrenchGreeter implements Greeter
{
    public function greet(string $name): string
    {
        return 'Bonjour ' . $name;
    }
}

final class Welcome
{
    public function __construct(private Greeter $greeter) {}

    public function message(): string
    {
        return $this->greeter->greet('Ada');
    }
}

echo new Welcome(new FrenchGreeter())->message(), "\n";
Passage canonique conservé

L'essentiel

Une interface déclare des methods implicitement publiques et abstraites, des constantes et, depuis PHP 8.4, des properties en get, set ou les deux. Deux réflexes anciens sont faux sur PHP 8.4 : une constant d'interface se surcharge depuis 8.1, sauf final ; et une property readonly ne satisfait pas une property d'interface set.

Le schéma

À retenir en priorité
  1. La property d'interface décrit un contrat d'accès.
  2. readonly et private(set) ne promettent pas une écriture publique.

L'exemple

Exemple concret

interface Cacheable
{
    const int DEFAULT_TTL = 3600;
    final const int VERSION = 2;

    public function getCacheKey(): string;
}

class Article implements Cacheable
{
    const int DEFAULT_TTL = 60;    // autorisé depuis 8.1
    // const int VERSION = 3;      // erreur fatale : la constante est final

    public function getCacheKey(): string { return 'article'; }
}

Ce qu'une interface contient

À comprendre

À retenir en priorité
  1. Une method d'interface reste publique dans l'implémentation.
  2. Une class peut implémenter plusieurs interfaces.

C'est quoi ?

Une interface est un contrat de type : elle décrit ce qu'un object doit exposer, sans fournir le corps des methods. Ses methods sont implicitement publiques et abstraites ; une implémentation ne peut pas les rendre privées ou protégées. Elle peut aussi déclarer des constantes publiques et, en PHP 8.4, des contrats d'accès à des properties, sans stocker d'état.

Une class peut implements A, B. Une interface peut extends A, B, ce qui rassemble les obligations des deux contrats. Ce n'est pas de l'inheritance multiple de code : aucun corps de method n'est copié depuis les interfaces.

À quoi ça sert ?

Une prise standard permet de brancher plusieurs appareils sans connaître leur fabrication. La forme de la prise correspond aux signatures de l'interface, l'appareil à la class concrète, le branchement au parameter typé par l'interface. Limite : PHP vérifie la compatibilité des signatures, pas que l'appareil accomplit correctement sa tâche métier.

Une signature compatible ne doit pas exiger davantage de l'appelant ni lui promettre moins. Un parameter peut accepter un type plus large, et un return type devenir plus précis : ce sont la contravariance et la covariance. Garder les noms des parameters évite aussi de casser des appels à named arguments.

Où dans Symfony ?

Symfony\Component\HttpKernel\HttpKernelInterface décrit un contrat ; HttpKernel en fournit une implémentation. Une application peut de même typer une dépendance avec sa propre interface. Ce type PHP ne choisit pas à lui seul quel service injecter : cette décision appartient à la configuration de DependencyInjection. L'exemple suivant définit un contrat local, pas une version abrégée d'une interface Symfony.

Comment, étape par étape ?

  1. Déclarer les opérations publiques nécessaires au client, avec leurs parameters et return types, puis terminer les signatures par ;.
  2. Si plusieurs interfaces sont étendues ou implémentées, vérifier toutes leurs obligations, notamment celles portant le même nom.
  3. Fournir des methods publiques compatibles dans la class concrète.
  4. À la lecture d'une variation de types, se placer du côté du client : accepter plus d'entrées est permis ; rendre un résultat plus précis l'est aussi. L'inverse casserait la promesse.

Exemple concret PHP

Le contrat promet de prendre un Dog et de rendre un Vehicle. L'implémentation accepte tout Animal et rend une Car, donc elle satisfait cette promesse. Les autres classes ne servent qu'à rendre les relations de types explicites. La sortie est Car.

<?php
class Animal {}
final class Dog extends Animal {}
class Vehicle {}
final class Car extends Vehicle {}

interface Transport
{
    public function carry(Dog $animal): Vehicle;
}

final class Shuttle implements Transport
{
    public function carry(Animal $animal): Car
    {
        return new Car();
    }
}

function travel(Transport $transport): Vehicle
{
    return $transport->carry(new Dog());
}

echo travel(new Shuttle())::class, "\n";

Références : interfaces et variance.

Passage canonique conservé

Ce qu'une interface contient

  • Des methods implicitement public et abstraites, sans corps ; une method private ou protected ne compile pas, et la class qui l'implémente doit la garder publique.
  • Des constants, forcément publiques.
  • Une class implémente plusieurs interfaces ; une interface étend plusieurs interfaces (extends A, B).

Elle ne contient aucune property porteuse d'état.

Un contrat qui accepte Dog et promet Vehicle reste respecté si l'implémentation accepte tout Animal et renvoie Car : parameter plus large, return type plus précis. Inverser ces directions impose davantage au client ou lui promet moins.

Les constants sont surchargeables — depuis PHP 8.1

À mémoriser

C'est quoi ?

Une constante d'interface est une valeur publique attachée au contrat, pas une property d'instance. Depuis PHP 8.1, une class qui implémente l'interface peut redéfinir cette constante, sauf si l'interface l'a déclarée final. La règle ancienne « toute constante d'interface est impossible à redéfinir » ne s'applique donc pas à PHP 8.4.

Le type d'une class constant peut être déclaré depuis PHP 8.3, par exemple const int LIMIT = 10. Le type, la valeur et le caractère final répondent à trois questions différentes : quelle catégorie de valeur, quelle valeur par défaut et quelle possibilité de redéfinition.

À quoi ça sert ?

Un règlement peut proposer un horaire local adaptable et imposer un numéro de protocole identique partout. L'horaire correspond à une constante redéfinissable ; le numéro imposé à une constante final. Limite : PHP ne juge pas la pertinence du nouveau choix ; sans final, il vérifie les contraintes du langage, pas la politique de l'organisation.

Redéfinir ne modifie pas rétroactivement la valeur du contrat : Contract::LIMIT et Implementation::LIMIT restent deux accès dont la class explicitement nommée compte.

Où dans Symfony ?

Ces règles valent pour les interfaces PHP utilisées dans les components comme pour celles d'une application Symfony. Elles ne constituent pas une configuration du service container. Le contrat local BatchPolicy de l'exemple n'appartient à aucun component ; il isole la règle sans inventer une constante Symfony.

Comment, étape par étape ?

  1. Lire la déclaration de l'interface et vérifier si la constante porte final.
  2. Vérifier le runtime : la redéfinition est disponible depuis 8.1 et les types de constantes depuis 8.3.
  3. Si la constante est redéfinissable, fournir une déclaration compatible dans la class.
  4. Dans un accès X::CONSTANT, identifier X au lieu de supposer que la valeur de l'interface a elle-même changé. Pour les accès indirects, revoir self et static.

Exemple concret PHP

La sortie est 100 20 1. L'interface conserve sa limite de 100, la class choisit 20 et hérite de la version finale 1. Redéclarer VERSION dans SmallBatch serait une erreur fatale ; ce code n'essaie pas de poursuivre après une déclaration invalide.

<?php
interface BatchPolicy
{
    public const int LIMIT = 100;
    final public const int VERSION = 1;
}

final class SmallBatch implements BatchPolicy
{
    public const int LIMIT = 20;
}

echo BatchPolicy::LIMIT, ' ', SmallBatch::LIMIT, ' ', SmallBatch::VERSION, "\n";

Référence : constantes d'interface.

Passage canonique conservé

Les constants sont surchargeables — depuis PHP 8.1

Avant PHP 8.1, une constant d'interface ne pouvait pas être redéfinie par la class qui l'implémente. Les constants d'interface sont surchargeables depuis 8.1, et Symfony 8.0 exige PHP 8.4. C'est final sur la constant de l'interface qui interdit la surcharge, pas l'interface elle-même.

Les properties d'interface — depuis PHP 8.4

À comprendre

C'est quoi ?

En PHP 8.4, une interface peut exiger qu'une property soit publiquement lisible avec { get; }, publiquement écrivable avec { set; }, ou les deux. Elle décrit des possibilités d'accès, sans stocker la valeur et sans fournir le corps d'un hook.

La class peut satisfaire l'exigence avec une property publique ordinaire ou des hooks appropriés, y compris une property virtuelle. Pour un get seul, une property publique readonly convient. Pour un set public, ni readonly ni public private(set) ne conviennent : ils ne permettent pas les écritures publiques promises.

À quoi ça sert ?

Une vitrine promet que le client peut lire un prix ; un tableau modifiable promet aussi qu'il peut écrire. La vitrine correspond à { get; }, le tableau à { get; set; }, l'objet exposé à la class concrète. Limite : l'interface ne dit pas si le prix est gardé en mémoire ou calculé à chaque lecture.

Le client peut ainsi utiliser $item->name sans connaître la façon dont la class produit ce nom. La promesse d'accès reste plus précise que « cette class possède quelque part une donnée privée nommée name ».

Où dans Symfony ?

Une class de modèle applicative peut employer ce mécanisme dans un projet Symfony 8.0, puisque PHP 8.4 est disponible. Cela ne signifie pas que les interfaces historiques des components déclarent toutes des properties. L'exemple Named est un contrat local ; son fonctionnement ne dépend d'aucun service.

Comment, étape par étape ?

  1. Identifier les accès dont le client a besoin : lire, écrire, ou les deux.
  2. Déclarer le type et les hooks sans corps dans l'interface.
  3. Dans chaque implémentation, vérifier chaque moitié du contrat séparément. Une property lisible publiquement n'est pas nécessairement écrivable publiquement.
  4. Choisir stockage ou calcul sans réduire les accès promis. Pour le mécanisme des hooks, consulter les ajouts PHP 8.4.

Exemple concret PHP

FixedName satisfait le contrat avec une property promue readonly. FullName le satisfait avec un calcul sans stockage name. Le même code lit les deux et affiche Ada, puis Ada Lovelace.

<?php
interface Named
{
    public string $name { get; }
}

final class FixedName implements Named
{
    public function __construct(public readonly string $name) {}
}

final class FullName implements Named
{
    public function __construct(private string $first, private string $last) {}

    public string $name {
        get => $this->first.' '.$this->last;
    }
}

function showName(Named $item): void
{
    echo $item->name, "\n";
}

showName(new FixedName('Ada'));
showName(new FullName('Ada', 'Lovelace'));

Ajouter set; au contrat ferait échouer ces implémentations : ni l'une ni l'autre ne fournit une écriture publique de name. Référence : interface properties.

Passage canonique conservé

Les properties d'interface — depuis PHP 8.4

Une interface peut déclarer une property, en disant si elle est lisible, écrivable, ou les deux :

interface Named
{
    public string $name { get; }        // lisible
    public string $slug { get; set; }   // lisible et écrivable
}

La déclaration ne porte que sur l'accès public. Une property publique ordinaire la satisfait, ou une property virtuelle qui implémente le hook correspondant.

Une property readonly ne peut pas satisfaire une property d'interface set : elle est implicitement protected(set) depuis PHP 8.4, et l'interface promet une écriture publique. Pour la même raison, public private(set) ne la satisfait pas non plus. PHP le dit : « Set access level of C::$name must be omitted (as in class I) ». readonly convient en revanche pour un get seul.

Pièges d'examen

Piège à éviter

  • Voir l’explication : La règle d'avant 8.1 est le réflexe à corriger.

    La règle d'avant 8.1 est le réflexe à corriger. « Une constant d'interface ne se surcharge pas » a été vrai pendant des années ; sur PHP 8.4 c'est faux, sauf final.

  • Voir l’explication : Déclarer une property n'est pas porter un état.

    Déclarer une property n'est pas porter un état. L'interface impose un contrat d'accès ; c'est la class qui décide s'il y a une valeur stockée derrière.

  • Voir l’explication : readonly ne satisfait pas un set.

    readonly ne satisfait pas un set. Le réflexe « readonly est une property publique, donc ça passe » échoue précisément sur la moitié écriture.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Methods publiques et abstraites, sans corps ; implémentation publique.
  • Constantes publiques, surchargeables depuis 8.1, sauf final.
  • implements A, B ; une interface extends A, B.
  • PHP 8.4 : properties { get; }, { get; set; } — un contrat, pas un état.

  • public private(set) ne satisfait pas set non plus.
