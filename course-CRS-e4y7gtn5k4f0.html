Objectif

Nous savons construire les objects du blog. Il faut maintenant permettre à un code appelant de demander une capacité sans imposer une class précise : lire une valeur, obtenir une clé ou appeler un service. Une interface décrit ce contrat ; la class qui l'implémente fournit le comportement. Nous allons lire ces promesses en PHP 8.4 sans les confondre avec le choix d'un service par Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Depuis PHP 8.1, une constant d'interface peut être redéfinie.
  2. final interdit cette redéfinition.

Le code qui prépare la page de l'article 42 peut dépendre d'un contrat de lecture plutôt que des détails du catalogue en mémoire. Un paramètre typé par une interface accepte un object qui l'implémente ; ce type ne construit pas l'object et ne décide pas quelle implémentation fournir.

L'interface annonce des methods implicitement publiques et abstraites : elle en donne les signatures, sans corps. Elle peut aussi déclarer des constantes et, depuis PHP 8.4, des properties en get, set ou les deux. Ces accès promis ne stockent aucune donnée. Pour comprendre la différence, partons d'un besoin voisin de l'article : lire le nom de son auteur sans imposer la façon dont ce nom est calculé.

Le schéma

À retenir en priorité
  1. La property d'interface décrit un contrat d'accès.
  2. readonly et private(set) ne promettent pas une écriture publique.

Le code de présentation a besoin d'une chaîne name. Une class pourrait la stocker directement ; une autre pourrait la calculer à partir de prénom et nom avec un hook, code exécuté lors de l'accès à une property. Dans les deux cas, le lecteur du contrat demande le résultat, pas le stockage.

Pointillés : conformité au contrat, pas appels ; flèche pleine : lecture. Exemple : un nom complet peut être mémorisé ou calculé depuis prénom et nom. Le client a besoin du résultat, pas du choix de stockage. get; set; ajouterait une promesse d'écriture publique que readonly ne remplit pas.

L'exemple

Exemple concret

Un autre besoin du blog est d'identifier une donnée réutilisable. Le contrat local Cacheable promet une clé et expose une durée par défaut, le TTL (time to live, durée de validité). Ce n'est pas une interface de Symfony Cache : nous isolons ici les règles PHP des methods et des constantes. La class d'exercice Article représente une donnée liée au billet, pas un remplacement imposé à notre modèle de lecture ArticleView.

interface Cacheable
{
    const int DEFAULT_TTL = 3600;
    final const int VERSION = 2;

    public function getCacheKey(): string;
}

class Article implements Cacheable
{
    const int DEFAULT_TTL = 60;    // autorisé depuis 8.1
    // const int VERSION = 3;      // erreur fatale : la constante est final

    public function getCacheKey(): string { return 'article'; }
}

Avec new Article(), appeler getCacheKey() retourne 'article' ; Article::DEFAULT_TTL vaut 60, tandis que Cacheable::DEFAULT_TTL reste 3600. Article::VERSION conserve 2. Décommenter la redéfinition de VERSION provoquerait une erreur fatale : elle est final.

L'extrait ne remplit aucun cache et ne gère pas son expiration. Sa clé constante sert à lire le contrat ; elle ne distingue pas les articles 42 et 999 et ne conviendrait donc pas telle quelle à un cache par article. Les constantes typées de cet exemple nécessitent PHP 8.3 ou ultérieur ; la possibilité de redéfinir une constante d'interface date, elle, de 8.1. Voyons maintenant ce que l'interface impose réellement à ses implémentations.

Ce qu'une interface contient

À retenir en priorité
  1. Une method d'interface reste publique dans l'implémentation.
  2. Une class peut implémenter plusieurs interfaces.

Dans Cacheable, l'appelant doit pouvoir invoquer getCacheKey() sans connaître la class concrète. Les methods d'interface sont donc implicitement public et abstraites, sans corps ; private ou protected ne compile pas dans ce contrat, et l'implémentation doit rester publique. Les constantes sont elles aussi publiques.

Une class peut satisfaire plusieurs contrats avec implements A, B. Une interface peut en réunir plusieurs avec extends A, B. Cela permettrait, par exemple, de décrire séparément une capacité de lecture et une capacité d'identification. Ce n'est pas un héritage multiple de code : aucun corps de method n'est copié, et les obligations de même nom doivent rester compatibles. L'interface ne porte aucune property porteuse d'état.

La compatibilité se lit du côté de l'appelant. Accepter un type de paramètre plus large, la contravariance, ne lui demande pas davantage ; retourner un type plus précis, la covariance, tient toujours la promesse. Les noms des paramètres méritent aussi d'être conservés pour ne pas casser les appels à arguments nommés. PHP contrôle les signatures, pas la pertinence métier de la clé retournée. Il reste à décider quelles constantes le contrat laisse spécialiser.

Pour vérifier le sens des variations de types, conservons cet exercice isolé. Ses noms Animal/Dog et Vehicle/Car rendent visibles les relations parent-enfant ; ce n'est pas un composant supplémentaire du blog. La règle est celle que nous appliquerions en faisant évoluer un contrat de service de lecture.

<?php
class Animal {}
final class Dog extends Animal {}
class Vehicle {}
final class Car extends Vehicle {}

interface Transport
{
    public function carry(Dog $animal): Vehicle;
}

final class Shuttle implements Transport
{
    public function carry(Animal $animal): Car
    {
        return new Car();
    }
}

function travel(Transport $transport): Vehicle
{
    return $transport->carry(new Dog());
}

echo travel(new Shuttle())::class, "\n";

travel() fournit un Dog et attend un Vehicle. Shuttle accepte tout Animal, donc aussi ce Dog, et retourne une Car, qui est bien un Vehicle. La sortie attendue est Car. Accepter plus d'entrées et fournir un résultat plus précis préserve le contrat ; inverser ces directions pourrait le rompre. Ce raisonnement ne choisit toujours pas l'implémentation à injecter.

🌍 In Real Life

La situation : un prestataire promet de transporter les chiens dans un véhicule. Accepter aussi les autres animaux et fournir précisément une voiture tient cette promesse ; n'accepter que certaines races pourrait la rompre.

L’équivalent dans Symfony : promesse → interface PHP ; entrées acceptées plus largement → contravariance ; résultat plus précis → covariance. Ces règles s'appliquent aussi aux contrats des services Symfony.

Retour à la réalité technique : carry(Animal): Car reste compatible avec carry(Dog): Vehicle dans l'exemple. PHP vérifie la signature, pas la qualité du transport ; conserver les noms de paramètres protège aussi les appels nommés. Plusieurs interfaces cumulent des obligations compatibles, pas des corps de méthodes.

🧠 Comment le mémoriser : « Accepter davantage, promettre plus précisément. » Image mentale : une porte d'entrée plus large et un résultat mieux défini. Question-réflexe : l'ancien appelant peut-il toujours fournir son argument et utiliser le résultat ?

⚠️ À ne pas confondre : compatibilité de type et sélection de l'implémentation par le conteneur.

Un contrat qui accepte Dog et promet Vehicle reste respecté si l'implémentation accepte tout Animal et renvoie Car : parameter plus large, return type plus précis. Inverser ces directions impose davantage au client ou lui promet moins.

Les constants sont surchargeables — depuis PHP 8.1

Notre exemple propose 3600 comme durée générale et 60 pour Article. Depuis PHP 8.1, la class qui implémente une interface peut redéfinir une constante non finale : ces deux valeurs coexistent, et le nom de type utilisé pour la lecture décide laquelle est visée. Avant 8.1, cette redéfinition était interdite.

Pour VERSION, nous voulons au contraire préserver la valeur du contrat : final interdit sa redéfinition. Ce n'est pas le fait d'être dans une interface qui la fige. Symfony 8.0 exige PHP 8.4 au minimum ; le rappel des versions antérieures sert à corriger un ancien réflexe, pas à annoncer une compatibilité de Symfony 8 avec PHP 8.1.

Dans la scène liée d'import des articles, une politique générale peut annoncer des lots de 100, tandis qu'une implémentation les réduit à 20. L'exemple suivant rend ce choix observable sans lancer une commande ni importer de fichier :

<?php
interface BatchPolicy
{
    public const int LIMIT = 100;
    final public const int VERSION = 1;
}

final class SmallBatch implements BatchPolicy
{
    public const int LIMIT = 20;
}

echo BatchPolicy::LIMIT, ' ', SmallBatch::LIMIT, ' ', SmallBatch::VERSION, "\n";

La sortie est 100 20 1. Lire BatchPolicy::LIMIT ne cherche pas automatiquement la constante d'une class qui l'implémente. Le code d'import doit encore décider quelle politique consulter ; ces constantes ne découpent aucun fichier à elles seules.

🌍 In Real Life

La situation : le guide général annonce des lots de cent dossiers ; une procédure spécialisée en prévoit vingt, tandis que le numéro de norme reste imposé.

L’équivalent dans Symfony : valeur générale → BatchPolicy::LIMIT ; valeur spécialisée → SmallBatch::LIMIT ; numéro imposé → constante final. Il s'agit de PHP utilisé par l'application, non d'une configuration de service.

Retour à la réalité technique : les constantes non finales peuvent être redéfinies depuis PHP 8.1. Lire le nom de l'interface vise toujours sa constante, pas automatiquement celle d'une implémentation. Ces déclarations n'effectuent aucun découpage de fichier ; Symfony 8.0 exige PHP ≥8.4 malgré ce repère historique.

🧠 Comment le mémoriser : « Lis le nom du document consulté. » Image mentale : guide général et fiche spécialisée ouverts côte à côte. Question-réflexe : quel type précède ::, et la constante est-elle finale ?

⚠️ À ne pas confondre : redéfinition autorisée d'une constante et modification de sa valeur à l'exécution.

Les properties d'interface — depuis PHP 8.4

Revenons au nom de l'auteur affiché à côté de l'article. Le consommateur veut le lire, mais un outil éditorial peut aussi avoir besoin de modifier son slug, nom court utilisé dans une URL. En PHP 8.4, une interface peut décrire ces besoins par une property lisible, écrivable, ou les deux :

interface Named
{
    public string $name { get; }        // lisible
    public string $slug { get; set; }   // lisible et écrivable
}

Avec une implémentation dont name vaut 'Ada' et slug vaut 'ada', le consommateur doit pouvoir lire ces deux chaînes et affecter $object->slug = 'ada-l'. Le contrat ne promet pas d'écriture sur name. Il n'effectue ni génération de slug ni validation de sa syntaxe.

La déclaration porte seulement sur l'accès public. Une property publique ordinaire peut satisfaire le contrat ; une property virtuelle peut fournir le hook correspondant sans valeur stockée. Une property initialisée public readonly convient pour name, puisqu'elle autorise sa lecture. Le code appelant n'a pas à connaître ces choix internes.

Une property readonly ne peut pas satisfaire une property d'interface set : elle est implicitement protected(set) depuis PHP 8.4, et l'interface promet une écriture publique. Pour la même raison, public private(set) ne la satisfait pas non plus. PHP le dit : « Set access level of C::$name must be omitted (as in class I) ». readonly convient en revanche pour un get seul. Pour slug, une lecture publique accompagnée de private(set) échouerait donc aussi : le contrat promet à l'appelant un droit d'écriture que l'implémentation lui retirerait.

Pour la seule lecture du nom d'auteur, exécutons une variante indépendante de Named, limitée à name. Ne la charge pas avec la déclaration précédente de même nom qui imposait aussi slug.

<?php
interface Named
{
    public string $name { get; }
}

final class FixedName implements Named
{
    public function __construct(public readonly string $name) {}
}

final class FullName implements Named
{
    public function __construct(private string $first, private string $last) {}

    public string $name {
        get => $this->first.' '.$this->last;
    }
}

function showName(Named $item): void
{
    echo $item->name, "\n";
}

showName(new FixedName('Ada'));
showName(new FullName('Ada', 'Lovelace'));

Les entrées produisent Ada, puis Ada Lovelace. showName() utilise le même accès public, alors que le premier object stocke la chaîne et le second la calcule. Ajouter set; au contrat ferait échouer ces deux implémentations : aucune ne fournit d'écriture publique de name. L'exemple affiche du texte en PHP ; l'échappement pour une page HTML reste une responsabilité distincte du rendu.

🌍 In Real Life

La situation : un guichet promet d'afficher un nom, sans préciser s'il lit une fiche ou le compose. Autoriser les visiteurs à le modifier serait une seconde promesse.

L’équivalent dans Symfony : lecture promise → { get; } ; écriture publique promise → { set; } ; fiche ou calcul → propriété stockée ou hook virtuel de l'objet PHP.

Retour à la réalité technique : en PHP 8.4, l'interface décrit l'accès, sans stocker la valeur. Une propriété publique readonly initialisée convient pour get, mais ne fournit pas le set public exigé. Le contrat ne génère ni slug ni échappement HTML.

🧠 Comment le mémoriser : « Voir n'est pas modifier. » Image mentale : affichage lisible à travers une vitre, sans bouton d'édition. Question-réflexe : le contrat promet-il une lecture, une écriture ou les deux ?

⚠️ À ne pas confondre : absence d'écriture promise et interdiction absolue d'écrire dans toute implémentation ; un contrat get seul ne rend pas automatiquement l'objet immuable.

Pièges d'examen

Piège à éviter

  • Voir l’explication : La règle d'avant 8.1 est le réflexe à corriger.

    La règle d'avant 8.1 est le réflexe à corriger. Pour expliquer les valeurs 3600 et 60 de notre exemple, cherche final, pas seulement interface. « Une constant d'interface ne se surcharge pas » est faux sur PHP 8.4 sauf si la constante est finale.

  • Voir l’explication : Déclarer une property n'est pas porter un état.

    Déclarer une property n'est pas porter un état. L'interface impose un contrat d'accès ; c'est la class qui décide s'il y a une valeur stockée derrière. Lire le nom de l'auteur ne permet donc pas de déduire qu'un champ le stocke : il peut être calculé à chaque accès.

  • Voir l’explication : readonly ne satisfait pas un set.

    readonly ne satisfait pas un set. Le réflexe « readonly est une property publique, donc ça passe » échoue précisément sur la moitié écriture. Applique le test à slug, puis à name : le premier promet set, le second seulement get. C'est la promesse précise qui décide, pas le seul mot public présent dans l'implémentation.

Passer du contrat à l'objet fourni au consommateur

  • Voir l’explication : de type chaîne

    Pour un modèle de lecture du blog, ne réclame que les capacités nécessaires au consommateur. Un contrat d'identifier de type chaîne peut utiliser public string $id { get; } sans imposer de stockage ; le type doit correspondre au modèle concret choisi. Si l'identifier de ton modèle est un entier, ne lui impose pas par simple copie un contrat string.

  • Constantes finales et câblage d’une interface

    Utilise final const seulement pour les valeurs qui doivent rester communes à toutes les implémentations. Enfin, si un service demande cette interface au constructor, il faut lui fournir une implémentation concrète : à la main en PHP, ou via le câblage du conteneur dans Symfony. L'interface vérifie une promesse ; elle n'est ni un service instanciable ni un algorithme d'autowiring.

  • Choix manuel d’une implémentation

    Reprenons le message préparé après l'inscription. Nous avions une class de salutation concrète ; Welcome demande maintenant seulement la capacité Greeter. Cet exemple PHP 8.4 construit toujours les objects manuellement : le choix de FrenchGreeter se trouve dans la dernière ligne.

<?php
interface Greeter
{
    public function greet(string $name): string;
}

final class FrenchGreeter implements Greeter
{
    public function greet(string $name): string
    {
        return 'Bonjour ' . $name;
    }
}

final class Welcome
{
    public function __construct(private Greeter $greeter) {}

    public function message(): string
    {
        return $this->greeter->greet('Ada');
    }
}

echo new Welcome(new FrenchGreeter())->message(), "\n";
Contrat de type contre qualité du comportement

L'entrée 'Ada' produit Bonjour Ada. Welcome connaît Greeter, pas le corps de FrenchGreeter::greet() ; on peut lui fournir une autre implémentation compatible. Cela ne garantit pas que son message soit correct dans toutes les langues : PHP vérifie le contrat de type, pas la qualité de la traduction. Le conteneur de Symfony pourra prendre en charge cet assemblage lorsque nous étudierons l'injection.

🌍 In Real Life

La situation : la fiche de poste exige de savoir saluer ; le responsable doit encore affecter une personne concrète au poste.

L’équivalent dans Symfony : capacité exigée → Greeter ; personne choisie → FrenchGreeter ; affectation → injection dans Welcome, manuelle ici ou configurée dans le conteneur.

Retour à la réalité technique : une interface n'est pas instanciable et ne choisit pas son implémentation. Le constructor reçoit un objet compatible ; le câblage précède son usage. PHP vérifie le contrat déclaré, non la justesse linguistique du message.

🧠 Comment le mémoriser : « La fiche exige ; l'assemblage fournit. » Image mentale : une fiche à côté d'un poste encore vacant. Question-réflexe : où le choix de l'objet concret est-il effectué ?

Fiche express

À mémoriser

Avant de brancher une implémentation au code du blog, relis six promesses :

  • Methods publiques et abstraites, sans corps ; implémentation publique.
  • Constantes publiques, surchargeables depuis 8.1, sauf final.
  • implements A, B ; une interface extends A, B.
