Objectif

Écrire un message et son handler, savoir ce qui les apparie, ce qui se passe quand il y a plusieurs handlers, et faire évoluer un message sans casser ceux qui attendent en file.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le message porte les données nécessaires.
  2. Aucune interface Messenger n'est imposée.

Un message est une class ordinaire qui porte des identifiers. Un handler porte #[AsMessageHandler], et c'est le type de son argument qui le relie au message. Plusieurs handlers pour un même message sont tous appelés. Et un message en file a été sérialisé par l'ancien code : il doit survivre au deployment.

Le schéma

À retenir en priorité
  1. L'attribute enregistre le handler.
  2. Le type détermine les messages acceptés.

Deux conséquences : priority ne trie qu'à l'intérieur d'un même type, et fromTransport ne concerne que les messages reçus.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. La priority n'exclut pas les autres handlers.
  2. Plusieurs traitements sont légitimes.
final class OrderPlaced
{
    public function __construct(public readonly int $orderId) {}
}

#[AsMessageHandler]
final class CreateInvoice
{
    public function __invoke(OrderPlaced $message): void { /* recharge l'achat, facture */ }
}

#[AsMessageHandler(priority: 10)]
final class NotifyCustomer
{
    public function __invoke(OrderPlaced $message): void { /* recharge l'achat, notifie */ }
}

dispatch(new OrderPlaced(42)) appelle les deux, NotifyCustomer d'abord.

Le message

À retenir en priorité
  1. Un message en file vient d'une ancienne version.
  2. Le défaut du constructor ne migre pas automatiquement l'object.

Une class ordinaire, sans interface ni class parente, qui doit être sérialisable : un transport asynchrone l'écrit puis la relit. On y met un identifier, pas un object chargé — la copie sérialisée serait périmée à la lecture ; le handler recharge l'état courant.

Le serializer par défaut s'appuie sur unserialize(), qui n'appelle pas le constructor. Un message de la version 1 lu par la version 2, PHP 8.4 :

Changement de la class Lecture de l'ancien message
property promue ajoutée au constructor, avec défaut Error : « must not be accessed before initialization »
property déclarée ajoutée, avec défaut lue avec sa default value
property retirée décodé, avec la deprecation « Creation of dynamic property »

Pour un changement de sens : une nouvelle class, l'ancienne gardée le temps que les files se vident.

Le handler

À retenir en priorité
  1. La restriction concerne la réception.
  2. Distinguer dispatch local et message reçu.
  • #[AsMessageHandler] est lu par l'autoconfiguration ; le type de l'argument désigne le message. Aucune table à écrire.
  • L'attribute se pose aussi sur des methods, plusieurs par class ; le type peut être une union (Ping|Pong) ou une interface.
  • Sans type, le build échoue : « must have a type-hint corresponding to the message class it handles ».
  • Les options de l'attribute en 8.0 : bus, fromTransport, handles, method, priority, sign.

fromTransport: 'async' écarte un message reçu d'un autre transport, mais pas un message traité en synchrone :

Le message arrive… Handler fromTransport: 'async' Handler sans option
lu par un worker sur other écarté appelé
lu par un worker sur async appelé appelé
dispatché sans routage, en synchrone appelé appelé

Sans ReceivedStamp, tout handler est gardé : fromTransport ne rend pas un handler « asynchrone seulement ».

Plusieurs handlers

À retenir en priorité
  1. Le type est examiné avant certains tris.
  2. Ne pas déduire un ordre global du seul nombre.
  • Tous sont appelés ; priority ordonne, sans exclure. Sans priority : l'ordre d'enregistrement.
  • Mais seulement dans un même type : les types du message sont parcourus dans l'ordre class, parents, interfaces, avant les priorities. Un handler typé Invoice passe avant un handler typé Billable à priority: 100.
  • Un HandledStamp par handler : last() rend le dernier, all() tous. Une return value n'a de sens qu'avec un handler unique, en synchrone.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le message doit rester durable et sérialisable.
  2. Le handler peut retrouver l'état utile à l'exécution.
  • Voir l’explication : Aucune interface à implémenter

    Aucune interface à implémenter, ni pour le message ni pour le handler.

  • Voir l’explication : Le message est apparié par le type de l'argument

    Le message est apparié par le type de l'argument — union et interface comprises ; sans type, le container refuse de se construire.

  • Voir l’explication : Plusieurs handlers sont légitimes

    Plusieurs handlers sont légitimes et tous s'exécutent ; priority les ordonne.

  • Voir l’explication : Une property promue ajoutée casse les messages déjà en file

    Une property promue ajoutée casse les messages déjà en file, même avec un défaut.

  • Voir l’explication : Ne pas transporter d'object chargé

    Ne pas transporter d'object chargé : un identifier, et un rechargement dans le handler.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Chaque handler possède son résultat.
  2. last() ne rend que le dernier stamp.

Si tu dois retenir seulement 7 choses :

  • Un message est une class ordinaire sérialisable, avec des identifiers.
  • #[AsMessageHandler] + le type de l'argument relient handler et message.
  • Union et interface acceptées ; sans type, le build échoue.
  • Plusieurs handlers : tous appelés, un HandledStamp chacun.
  • priority ordonne, et seulement dans un même type.
  • fromTransport ne concerne que les messages reçus.
  • Property promue ajoutée → les anciens messages cassent.

Moyen mnémotechnique : « le type relie, la priority range, la file se souvient ».

message = class + identifiers ; handler = #[AsMessageHandler] + type (union, interface) ; types : class > parents > interfaces > * ;
priority dans un type ; fromTransport si ReceivedStamp ; unserialize sans constructor : déclarée oui, promue non
