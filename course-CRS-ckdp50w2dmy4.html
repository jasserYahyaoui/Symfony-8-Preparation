Objectif

Le cours Messenger a séparé remise au bus et traitement. Pour prolonger l'import du blog, il faut maintenant définir les données du travail et les callables qui réagiront à son achèvement. Une publication peut intéresser plusieurs handlers : notification et journalisation, par exemple. Nous allons comprendre leur sélection, leur ordre et leurs échecs, puis ce que deviennent les messages encore en file lors d'un deployment.

L'essentiel

À comprendre

À retenir en priorité
  1. Le message porte les données nécessaires.
  2. Aucune interface Messenger n'est imposée.

Un message est une class ordinaire portant les données du travail. Pour une action visant l'état courant de l'article, transmettre son identifier 42 permet au handler de retrouver cet état plutôt que d'utiliser un ancien instantané. Le message n'exécute pas lui-même la publication.

Dans l'intégration FrameworkBundle, un service autoconfiguré marqué #[AsMessageHandler] est associé au type de son argument, sauf association explicite par handles. À l'exécution, le locator sélectionne les handlers ; HandleMessageMiddleware les appelle. Une priority les ordonne au sein d'un type, elle ne désigne pas un unique gagnant.

Si un transport sérialise le message, la lecture peut survenir avec une nouvelle version du code. L'association au handler et la compatibilité des données sont donc deux problèmes distincts : un handler correctement enregistré ne répare pas une property absente d'un ancien message.

Le schéma

À retenir en priorité
  1. L'attribute enregistre le handler.
  2. Le type détermine les messages acceptés.

Supposons que le bus ait atteint le traitement : aucun sender ne l'a arrêté, ou le message revient du transport. Pour le message de publication, la première question est « quels handlers sont candidats ? », avant « lequel passe en premier ? ». Les listes par type ont été préparées pendant la compilation.

Bleu : sélection ; ambre : filtre ; vert : issue pour ce candidat. Le locator sélectionne les handlers ; HandleMessageMiddleware les appelle. Le schéma montre le chemin réussi : un handler qui lève ne produit pas son HandledStamp.

Deux conséquences : priority ne trie qu'à l'intérieur d'un même type, et fromTransport ne concerne que les messages reçus.

L'exemple

Exemple concret

À retenir en priorité
  1. La priority n'exclut pas les autres handlers.
  2. Plusieurs traitements sont légitimes.

Deux réactions à une publication suivent les mêmes règles que cet exemple historique d'achat. Gardons ses noms pour comparer le code aux questions : OrderPlaced porte l'identifier, NotifyCustomer et CreateInvoice sont deux réactions indépendantes. L'équivalent éditorial serait un message ArticlePublished reçu par un handler de notification et un handler de journal. Ce n'est pas le traitement de GET /blog/42.

Fragment PHP 8.4 pour Symfony 8.0, les classes étant déclarées dans des fichiers autoloadés et les handlers enregistrés comme services autoconfigurés :

use Symfony\Component\Messenger\Attribute\AsMessageHandler;

final class OrderPlaced
{
    public function __construct(public readonly int $orderId) {}
}

#[AsMessageHandler]
final class CreateInvoice
{
    public function __invoke(OrderPlaced $message): void { /* recharge l'achat, facture */ }
}

#[AsMessageHandler(priority: 10)]
final class NotifyCustomer
{
    public function __invoke(OrderPlaced $message): void { /* recharge l'achat, notifie */ }
}

Un appel $bus->dispatch(new OrderPlaced(42)), avec un MessageBusInterface fourni par l'application, appelle les deux : NotifyCustomer (10), puis CreateInvoice (0). Les corps illustratifs retournent void : les deux HandledStamp portent donc un résultat null.

On suppose ici le bus par défaut, sans routage asynchrone, avec les deux services autoconfigurés. Les corps sont des emplacements pour le métier, pas une implémentation de facturation. L'ordre vient de deux handlers enregistrés pour le même type OrderPlaced, et non d'une priorité globale entre tous les types. Une priorité de notification ne doit pas servir à exprimer « notifier seulement si la facturation réussit » : l'ordre des handlers n'est pas un workflow conditionnel. La section sur leurs exceptions précisera cette limite.

Le message

À retenir en priorité
  1. Un message en file vient d'une ancienne version.
  2. Le défaut du constructor ne migre pas automatiquement l'object.

🌍 In Real Life

La situation : pour préparer la lettre du blog, on transmet soit « consulter la fiche 42 », soit une photocopie datée de cette fiche.

L’équivalent dans Symfony : numéro de fiche → identifiant dans le message ; photocopie → instantané de données ; consultation du dossier → lecture explicite par le handler.

Retour à la réalité technique : un message est un objet ordinaire. Son contrat détermine s'il faut l'état courant ou celui de l'émission. Un identifiant ne charge rien automatiquement ; le handler doit aussi traiter l'absence du billet.

🧠 Comment le mémoriser : « Numéro ou photographie ? » Image mentale : une étiquette 42 à côté d'une copie datée. Question-réflexe : de quel instant mon traitement a-t-il besoin ?

⚠️ À ne pas confondre : données sérialisables et objet vivant partagé entre processus.

Pour l'import, ImportBlogFile peut désigner le fichier à traiter ; pour une réaction à la publication, ArticlePublished peut désigner l'article 42. Ces noms décrivent l'intention. Aucune interface ou class parente Messenger n'est imposée. Avec un transport qui sérialise, les données doivent être sérialisables, c'est-à-dire convertibles dans une représentation que le receiver pourra relire.

Si le traitement doit utiliser l'état courant, préférer un identifier à un object chargé : le handler consulte ensuite le service applicatif et traite explicitement l'absence éventuelle. Le catalogue pédagogique contient 42, mais pas 999 ; Messenger ne charge pas automatiquement un article pour transformer cet identifier en object. Transporter volontairement un instantané de données reste un autre contrat, à définir comme tel, et non une interdiction générale des DTO dans les messages.

Pour isoler la séparation données/traitement sans accès à un fichier, conservons un calcul miniature : additionner deux nombres pour un rapport d'import. Le message porte 2 et 3 ; le handler porte l'opération.

<?php
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

final class AddNumbers
{
    public function __construct(public readonly int $left, public readonly int $right) {}
}

#[AsMessageHandler]
final class AddNumbersHandler
{
    public function __invoke(AddNumbers $message): int
    {
        return $message->left + $message->right;
    }
}

L'appel PHP direct (new AddNumbersHandler())(new AddNumbers(2, 3)) produit l'entier 5. Il ne passe pas par Messenger. Pour retrouver ce résultat dans un HandledStamp, il faut enregistrer le service handler et dispatcher avec la pile de traitement adéquate. L'attribute ne découvre pas à lui seul toutes les classes du disque. Ce petit calcul vérifie un résultat, pas une livraison asynchrone ou l'exécution unique du rapport.

Le serializer par défaut s'appuie sur unserialize(), qui n'appelle pas le constructor. Imaginons un import envoyé hier, consommé après le deployment d'aujourd'hui. Pour une class ordinaire, sans mécanisme personnalisé de désérialisation ni autorisation particulière des properties dynamiques, un message de la version 1 lu par la version 2 donne, en PHP 8.4 :

Changement de la class Lecture de l'ancien message
property typée promue ajoutée au constructor, avec défaut reste non initialisée ; son accès direct lève Error : « must not be accessed before initialization »
property déclarée ajoutée, avec défaut lue avec sa default value
property retirée décodé, avec la deprecation « Creation of dynamic property »

Pour un changement de sens : une nouvelle class, l'ancienne gardée le temps que les files se vident. Le défaut d'un parameter promu s'applique lors de l'appel du constructor, pas comme migration des objets sérialisés. Ne pas confondre « décodage possible » et « état compatible avec le nouveau handler ».

Le handler

À retenir en priorité
  1. La restriction concerne la réception.
  2. Distinguer dispatch local et message reçu.

🌍 In Real Life

La situation : le secrétariat du blog prépare son annuaire des compétences avant l'arrivée des dossiers.

L’équivalent dans Symfony : inscription d'un rôle → tag issu de #[AsMessageHandler] ; classement de l'annuaire → MessengerPass ; outils remis au collègue → dépendances résolues par autowiring.

Retour à la réalité technique : l'autoconfiguration et le compiler pass préparent les définitions et locators. À l'exécution, le middleware appelle le callable sélectionné. Cela ne signifie ni scanner toutes les classes à chaque message, ni instancier tous les services à la compilation.

🧠 Comment le mémoriser : « L'annuaire avant le dossier. » Image mentale : une liste préparée puis consultée. Question-réflexe : suis-je à la compilation ou au traitement ?

⚠️ À ne pas confondre : autoconfiguration des rôles et autowiring des dépendances.

L'intention est définie ; comment retrouver son callable sans table écrite à la main ? L'extension du framework fournit la configuration et les définitions de services Messenger. L'autoconfiguration ajoute le tag messenger.message_handler à partir de l'attribute. Le compiler pass MessengerPass lit les définitions taguées, déduit ou lit le type, puis prépare les locators et leurs listes. L'autowiring, lui, résout les dependencies des services. Ces rôles ne sont pas quatre noms du même mécanisme et cette préparation n'est pas relancée pour chaque message ou chaque GET.

  • #[AsMessageHandler] est lu par l'autoconfiguration ; le type de l'argument désigne le message. Le service doit avoir été découvert ou déclaré : l'attribute ne parcourt pas le disque pour enregistrer toute class.
  • L'attribute se pose aussi sur des methods, plusieurs par class ; le type peut être une union (Ping|Pong) ou une interface.
  • Sans type et sans option handles explicite, le build ne peut pas déduire le message et échoue. handles permet une association explicite.
  • Les options de l'attribute en 8.0 : bus, fromTransport, handles, method, priority, sign.

fromTransport: 'async' écarte un message reçu d'un autre transport, mais pas un message traité en synchrone :

Le message arrive… Handler fromTransport: 'async' Handler sans option
lu par un worker sur other écarté appelé
lu par un worker sur async appelé appelé
dispatché sans routage, en synchrone appelé appelé

Sans ReceivedStamp, ce filtre ne retire aucun des handlers candidats : fromTransport ne rend pas un handler « asynchrone seulement ». À l'inverse, sync:// ajoute lui aussi un ReceivedStamp lors de son redispatch immédiat ; la comparaison de provenance peut alors s'appliquer sans worker. Le critère réel est le stamp, pas simplement la présence d'un processus de fond.

Plusieurs handlers

À retenir en priorité
  1. Le type est examiné avant certains tris.
  2. Ne pas déduire un ordre global du seul nombre.

🌍 In Real Life

La situation : l'annonce de publication du billet 42 intéresse plusieurs bureaux, classés d'abord par spécialité, puis par priorité interne.

L’équivalent dans Symfony : spécialités → groupes de types parcourus par HandlersLocator ; rang interne → priorité dans chaque groupe ; visa déjà obtenu → HandledStamp.

Retour à la réalité technique : la priorité n'est pas un classement global entre classe concrète et interface. Le middleware ignore les handlers déjà marqués, collecte les échecs des autres et peut lever une exception après plusieurs traitements.

🧠 Comment le mémoriser : « Le groupe avant le rang. » Image mentale : des tiroirs numérotés contenant chacun leur liste. Question-réflexe : ces deux priorités appartiennent-elles au même groupe ?

⚠️ À ne pas confondre : plusieurs handlers et garantie transactionnelle de réussite globale.

Le message de publication doit intéresser deux handlers, sans que l'un élimine l'autre. MessengerPass trie les handlers par priority décroissante dans chaque groupe de type. À priorité égale, l'ordre d'enregistrement reste déterminant. HandlersLocator parcourt ensuite class, parents, interfaces, jokers de namespace et *, en filtrant la provenance et les doublons.

Ainsi, pour Invoice qui implémente Billable, un handler du type concret Invoice à priorité 0 passe avant un handler de l'interface Billable à priorité 100. Le nombre 100 n'est pas une priorité globale. Dans le groupe OrderPlaced de l'exemple, en revanche, 10 précède bien 0.

HandleMessageMiddleware ignore un handler dont le nom figure déjà dans un HandledStamp de l'Envelope, puis appelle les autres candidats. Chaque handler ordinaire réussi produit son stamp. Si un handler lève une exception, le middleware la collecte, poursuit les autres handlers, puis lève une HandlerFailedException regroupant les échecs. Il ne revient donc pas normalement à l'appelant, même si d'autres handlers ont réussi.

Pour la publication, cela signifie qu'un échec de notification n'annule pas automatiquement la journalisation. La priority n'est ni une transaction ni un arrêt de propagation comme celui d'un événement stoppable. Au retour réussi d'un dispatch synchrone, all(HandledStamp::class) permet de lire plusieurs résultats ; last() ne les agrège pas. C'est HandleTrait, et non Messenger en général, qui impose un résultat unique. Les reprises après échec seront traitées dans le cours sur les retries.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le message doit rester durable et sérialisable.
  2. Le handler peut retrouver l'état utile à l'exécution.
  • Voir l’explication : Aucune interface Messenger obligatoire

    Aucune interface Messenger obligatoire pour le message ou le handler ordinaire de publication. Cela n'interdit pas une interface applicative.

  • Voir l’explication : Le type de l'argument permet l'appariement automatique

    Le type de l'argument permet l'appariement automatique, union et interface comprises ; sans type, prévoir handles explicitement. La reconnaissance requiert toujours un service enregistré, pas seulement un fichier de class.

  • Voir l’explication : Plusieurs handlers sont légitimes

    Plusieurs handlers sont légitimes : la priority ordonne les candidats d'un même type, elle n'exclut pas les autres et ne les annule pas après l'échec de notification.

  • Voir l’explication : Une property typée promue ajoutée peut casser la lecture métier des anciens messages

    Une property typée promue ajoutée peut casser la lecture métier des anciens messages, même avec un défaut de parameter : avec la désérialisation PHP décrite, son accès direct échoue si rien ne l'a initialisée.

  • Voir l’explication : Pour retrouver l'état courant, préférer un identifier à l'object chargé

    Pour retrouver l'état courant, préférer un identifier à l'object chargé : le handler de publication retrouve l'article et décide quoi faire s'il manque. Il n'existe pas de rechargement automatique assuré par Messenger.

Fiche express

À mémoriser

À retenir en priorité
  1. Chaque handler possède son résultat.
  2. last() ne rend que le dernier stamp.

Si tu dois retenir seulement 7 choses :

  • Un message est une class ordinaire sérialisable, avec des identifiers.
  • #[AsMessageHandler] + le type de l'argument relient handler et message.
  • Union et interface acceptées ; sans type ni handles, le build échoue.
  • Plusieurs handlers ordinaires : candidats non déjà traités appelés, un HandledStamp par succès.
  • priority ordonne, et seulement dans un même type.
  • fromTransport ne concerne que les messages reçus.
  • Property typée promue ajoutée → accès direct en échec si elle reste non initialisée après désérialisation.

Moyen mnémotechnique : « le type relie, la priority range, la file se souvient ».

message = class + identifiers ; handler = #[AsMessageHandler] + type (union, interface) ; types : class > parents > interfaces > * ;
priority dans un type ; fromTransport si ReceivedStamp ; unserialize sans constructor : déclarée oui, promue non

Le mémo suppose les défauts et la désérialisation décrits plus haut. Une exception de handler est collectée sans annuler les succès des autres, puis remontée groupée. Poursuivre avec les transports, puis les retries et failures : l'article peut être lu par GET /blog/42 indépendamment de l'état d'une notification différée.
