Objectif

Savoir qui décide qu'un accès est accordé, par quel path, et quelle Response part quand il est refusé. Les voters eux-mêmes et les strategies ont leur propre item.

L'essentiel

À comprendre

À retenir en priorité
  1. L'attribute désigne l'action.
  2. Le subject désigne l'object concerné.

L'authorization répond à « avez-vous le droit ? », une fois l'identité connue. Une seule question, isGranted(attribute, sujet), passe par l'AccessDecisionManager : des voters votent, une strategy tranche, et un refus devient 401, 302 ou 403 selon que le user est connu.

Le schéma

À retenir en priorité
  1. Les voters évaluent leur domain.
  2. La strategy agrège leurs votes.

Bleu : appels ; ambre : décisions ; vert : résultat. isGranted() seul rend un booléen : il ne fabrique pas une réponse 403. Remember-me peut nécessiter une authentification plus forte ; les handlers personnalisés peuvent changer la réponse. L'autorisation existe aussi pour un visiteur anonyme.

L'exemple

Exemple concret

À retenir en priorité
  1. Le role ne suffit pas pour l'ownership.
  2. Le voter reçoit l'object à examiner.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[Route('/post/{id}/edit')]
public function edit(Post $post): Response
{
    $this->denyAccessUnlessGranted('POST_EDIT', $post);   // verbe métier + sujet
    // ...
}
{% if is_granted('ROLE_ADMIN') %}<a href="/admin">Admin</a>{% endif %}

Cacher ce lien améliore l'interface mais ne protège pas /admin : contrôler aussi la requête côté serveur. Le fragment edit() suppose un Post déjà résolu et doit retourner une Response après le contrôle ; le voter décide sur ce Post, pas sur tous les articles.

La question posée

À retenir en priorité
  1. Le même modèle d'autorisation est accessible dans Twig.
  2. L'affichage conditionnel ne remplace pas le contrôle serveur.

L'authorization s'exprime toujours de la même façon : denyAccessUnlessGranted() et isGranted() dans un controller, Security::isGranted() dans un service, is_granted() dans Twig.

Le path

À comprendre

À retenir en priorité
  1. Un accord suffit à la strategy affirmative.
  2. Ne pas utiliser les voters pour des effets de bord obligatoires.

C'est quoi ?

L'autorisation évalue un attribute, nom du droit demandé, éventuellement sur un subject, objet concerné. Un voter est un service qui peut accorder, refuser ou s'abstenir. L'AccessDecisionManager combine ces votes selon une stratégie.

À quoi ça sert ?

Un rôle global ne décrit pas à lui seul une relation avec un objet : être rédacteur ne signifie pas pouvoir modifier l'article d'un autre. Le subject permet de vérifier cette relation côté serveur.

Où dans Symfony ?

  • ROLE_ADMIN décrit un rôle ; un voter de rôles le traite.
  • IS_AUTHENTICATED_FULLY décrit un état d'authentication, pas un rôle métier.
  • POST_EDIT peut désigner une opération métier évaluée avec un article.

isGranted() pose la question ; denyAccessUnlessGranted() transforme le refus en exception. Twig dispose aussi de is_granted(), mais un affichage conditionnel n'est pas une barrière serveur.

Comment, étape par étape ?

  1. Transmettre attribute et subject à la décision.
  2. Chaque voter compétent répond ; les autres s'abstiennent.
  3. La stratégie agrège les votes. Avec affirmative, un accord suffit et peut interrompre la consultation : aucun effet obligatoire ne doit dépendre de l'exécution de tous les voters.
  4. En cas de refus HTTP, le contexte d'authentication décide de la suite : l'entry point peut demander une connexion ; un user suffisamment authentifié mais non autorisé reçoit normalement 403.

Exemple concret Twig

Dans un template où post est l'article et où un voter POST_EDIT existe :

{% if is_granted('POST_EDIT', post) %}
    <span>Modification autorisée</span>
{% endif %}

Le texte est affiché seulement lorsque la décision accorde ce droit sur cet article. Le controller qui modifie l'article doit répéter le contrôle serveur, car le client peut appeler son URL sans passer par ce template. Contre-exemple : ne tester que ROLE_EDITOR, sans subject, alors que la règle dépend de l'auteur. Correction : transmettre l'article au voter et refuser si la relation métier requise manque. Un subject absent peut faire s'abstenir le voter ; par défaut, l'abstention générale n'autorise rien.

Voters 8.0.

Passage canonique conservé
  • isGranted($attribute, $subject) délègue à l'AccessDecisionManager.
  • Chaque voter rend : accordé, refusé, ou abstention.
  • Une strategy transforme les votes en décision ; les voters sont consultés un par un, et la strategy peut s'arrêter avant la fin.
Strategy, deux voters A accorde, B refuse Voters consultés Décision
affirmative (défaut) A seulement accordé
consensus A et B accordé (égalité accordée par défaut)
unanimous A et B refusé

En affirmative, le journal ne montre que A.supports(EDIT) et A.vote : AffirmativeStrategy::decide() rend true au premier vote favorable. Un role n'a pas de traitement à part : RoleVoter le vote, comme un voter maison vote EDIT.

Deux familles d'attributes

À retenir en priorité
  1. Les attributes d'état sont distincts des roles.
  2. Les voters appropriés les interprètent.
Attribute Portée
ROLE_* ce que le user est
IS_AUTHENTICATED_FULLY, IS_AUTHENTICATED_REMEMBERED, PUBLIC_ACCESS l'état de l'authentication
un verbe métier — EDIT, PUBLISH ce que le user peut faire sur un object

La troisième famille est la raison d'être des voters : un role ne dit pas « l'auteur peut modifier son article ».

Le sujet

À retenir en priorité
  1. L'absence de subject peut empêcher le vote.
  2. L'abstention générale n'accorde pas l'accès par défaut.

Le second argument d'isGranted() est l'object concerné. Sans lui, un voter qui exige un Post s'abstient ; et quand tous s'abstiennent, l'accès est refusé.

Refuser

À retenir en priorité
  1. Le controller signale le refus par exception.
  2. L'entry point ou le refus final détermine la Response.

denyAccessUnlessGranted() lève une AccessDeniedException, que le firewall transforme :

Situation Response
anonyme, firewall http_basic 401, WWW-Authenticate: Basic realm="Secured Area"
anonyme, firewall form_login 302 vers la page de connexion
user pleinement authentifié, sans le droit 403 par défaut

Le status dépend de l'authentication et de l'entry point, pas de l'authorization.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un visiteur peut être invité à se connecter.
  2. 403 correspond normalement à un droit refusé après authentication suffisante.
  • Voir l’explication : Un role passe par un voter

    Un role passe par un voter, comme n'importe quel attribute.

  • Voir l’explication : Tous les voters ne votent pas toujours

    Tous les voters ne votent pas toujours : en affirmative, le premier « accordé » arrête la consultation.

  • Voir l’explication : Le statut n'est pas toujours 403

    Le statut n'est pas toujours 403 : un anonyme reçoit la Response de l'entry point — redirect pour un form, 401 pour HTTP Basic.

  • Voir l’explication : Sans sujet, un voter d'object ne peut rien décider

    Sans sujet, un voter d'object ne peut rien décider et s'abstient.

Fiche express

À mémoriser

À retenir en priorité
  1. Les roles suivent le même processus de décision.
  2. La strategy reste déterminante.

Si tu dois retenir seulement 7 choses :

  • isGranted(attribute, sujet) partout ; is_granted() dans Twig.
  • AccessDecisionManager : voters, puis strategy.
  • Vote : accordé, refusé, abstention.
  • affirmative (défaut) s'arrête au premier « accordé ».
  • Un role passe par un voter (RoleVoter).
  • Sans sujet, un voter d'object s'abstient ; tous abstenus : refus.
  • Refus : 401 ou 302 pour un anonyme (entry point), 403 pour un user pleinement authentifié.

Moyen mnémotechnique : « Demander, voter, trancher, répondre ».

isGranted → AccessDecisionManager → voters (accordé/refusé/abstention, un par un) → strategy (affirmative par défaut)
→ bool ; denyAccessUnlessGranted refusé → AccessDeniedException → entry point ou 403 si pleinement authentifié
