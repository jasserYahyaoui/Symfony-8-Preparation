Objectif

Rediriger le navigateur depuis un controller, et connaître le danger attaché à l'une des deux methods.

L'essentiel

À comprendre

À retenir en priorité
  1. redirectToRoute() génère d'abord la destination.
  2. Pour une URL complète, la générer explicitement puis appeler redirect().

Un controller redirige par redirectToRoute() (vers une route) ou redirect() (vers une URL). Les deux rendent une RedirectResponse : le navigateur repart, l'URL affichée change. Le statut est 302 par défaut, seuls six codes sont admis, et redirect() ne vérifie jamais sa destination.

Le schéma

À retenir en priorité
  1. Les parameters ordinaires non consommés par les variables du path ou du host vont en query, sauf ceux égaux aux défauts de route ; _query fournit des données de query explicites.
  2. _fragment désigne l'ancre de destination.

Bleu = construction côté serveur, ambre = décision du client, vert = nouvelle exécution. Ce chemin illustre un 303 après POST ; un client peut ne pas suivre la réponse. Le code 201 accepté par la classe n'est pas un ordre de navigation équivalent à un 303.

L'exemple : Post / Redirect / Get

Exemple concret

À retenir en priorité
  1. Le permanent n'est pas le défaut.
  2. 304 n'est pas accepté comme statut de RedirectResponse.
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;

final class SaveController extends AbstractController
{
    public function afterSuccessfulSave(): Response
    {
        return $this->redirectToRoute('blog_show', ['slug' => 'symfony', '_fragment' => 'comments'], 303);
    }
}

Branche après traitement réussi dans un contrôleur enregistré ; la route blog_show accepte le slug symfony. Le fragment est destiné au navigateur.

Les deux methods

redirectToRoute() est bâtie sur redirect() : elle génère l'URL avec generateUrl(), sans type de référence, donc en path absolu — Location porte normalement /accueil à host et schéma identiques. Une route exigeant un autre host ou schéma peut imposer une référence réseau ou une URL absolue. Pas de quatrième argument pour changer cela : une URL complète se construit soi-même, puis passe à redirect().

Le redirect dit au visiteur de rejoindre un autre guichet : le client effectue une nouvelle Request. Le forward demande au collègue de préparer le dossier sans faire bouger le visiteur.

Le statut

À comprendre

C'est quoi ?

Une redirection HTTP est une réponse qui indique une autre destination dans le header Location. Elle ne lance pas immédiatement l'action cible côté serveur. Le client décide de suivre cette indication et effectue alors une autre requête.

À quoi ça sert ?

Après un POST réussi, une redirection 303 exprime que le résultat doit être consulté séparément, habituellement par GET. À l'inverse, 307 et 308 préservent la méthode et le body : ils ne conviennent pas si l'objectif est précisément d'éviter de rejouer le POST. 301 et 308 annoncent une destination permanente, ce qui a des implications de cache.

Où dans Symfony ?

redirect(url, status) construit une RedirectResponse ; redirectToRoute(name, parameters, status) génère d'abord la destination. Le défaut est 302. Le troisième argument de redirectToRoute est un statut, pas un type de référence URL. Pour imposer une URL complète, la générer explicitement puis la passer à redirect.

Comment, étape par étape ?

  1. Distinguer déplacement temporaire, permanent ou consultation après une mutation.
  2. Décider si la méthode initiale doit être conservée.
  3. Générer une destination maîtrisée ; ne pas reprendre une URL fournie librement par le client.
  4. Retourner la réponse et vérifier son statut et son header Location, indépendamment du comportement du navigateur de test.

Exemple concret PHP

Avec HttpFoundation chargé, après qu'une opération ait réellement réussi :

<?php
use Symfony\Component\HttpFoundation\RedirectResponse;

$response = new RedirectResponse('/confirmation', 303);
var_dump($response->getStatusCode());
var_dump($response->headers->get('Location'));

On attend 303 et /confirmation. Dans une application, préférer une destination générée depuis la route correspondante plutôt qu'un chemin dupliqué. Contre-exemple : utiliser 307 après un POST alors que /confirmation n'accepte que GET. Le client conserve POST. Correction : choisir 303 pour ce parcours, ou rendre la cible compatible si la conservation est réellement voulue. Un statut 304 n'est pas une redirection vers une nouvelle URL ; RedirectResponse le refuse. Son acceptation technique de 201 ne fait pas de 201 le bon choix pour une redirection de navigation.

Passage canonique conservé

Le troisième argument porte le code, 302 par défaut : redirectToRoute('homepage', [], 301). Un 301 est mis en cache par le navigateur, parfois durablement : sans Cache-Control fourni, le constructor retire ce header. Le constructor vérifie le statut par isRedirect() : 201, 301, 302, 303, 307 et 308 seulement ; tout autre code — 304, 200 — lève une InvalidArgumentException, comme une URL vide.

Parameters utiles

  • les variables du path et du host consomment leurs parameters. Les parameters ordinaires restants deviennent des paramètres de query, sauf lorsqu'ils sont égaux aux valeurs par défaut de la route ;
  • la key spéciale _query permet de fournir explicitement des données de query ;
  • la key spéciale _fragment ajoute une ancre ;
  • $request->attributes->get('_route') redirige vers la route courante.

Exemples avec un contexte HTTPS sur www.example.test, sans préfixe de déploiement : une route /home dont le host est {sub}.example.test, générée avec sub=m, donne //m.example.test/home, pas ?sub=m. Pour une route /items avec le défaut non-placeholder page=1, fournir page=1 donne /items, tandis que page=2 donne /items?page=2.

redirectToRoute('blog_show', $request->query->all()) transmet ces parameters au générateur : il ne garantit donc pas une copie identique de la query string d'origine. Les paramètres obligatoires de route doivent être fournis.

Le danger de `redirect()`

Piège à éviter

À retenir en priorité
  1. Construire une RedirectResponse ne valide pas la destination.
  2. Ne pas transmettre directement une URL non fiable.

C'est quoi ?

Une redirection non validée laisse une entrée extérieure choisir une destination que l'application n'a pas autorisée. redirect construit la réponse ; il ne décide pas si l'adresse appartient au parcours attendu.

À quoi ça sert ?

Séparer choix fonctionnel et adresse empêche qu'un lien apparemment associé au site conduise librement ailleurs. Pour quelques destinations connues, une table de choix autorisés est plus simple à contrôler qu'une validation générale d'URL.

Où dans Symfony ?

Une valeur issue de Request.query reste une entrée utilisateur, même si elle ressemble à un chemin local. Un nom de route ou son host peut aussi devenir non maîtrisé si l'application le prend arbitrairement dans l'entrée. Le choix de route et ses paramètres doivent respecter le contrat du parcours.

Comment, étape par étape ?

  1. Accepter une clé fonctionnelle, pas nécessairement une URL.
  2. La comparer à une liste de destinations définie côté serveur.
  3. Utiliser un repli explicite pour une clé inconnue.
  4. Générer la destination autorisée et retourner la redirection.

Exemple concret PHP

Action d'AbstractController ; homepage et account_overview existent avec des destinations configurées de confiance :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function continueTo(\Symfony\Component\HttpFoundation\Request $request): \Symfony\Component\HttpFoundation\RedirectResponse
{
    $routes = ['home' => 'homepage', 'account' => 'account_overview'];
    $choice = $request->query->getString('destination', 'home');
    return $this->redirectToRoute($routes[$choice] ?? 'homepage', [], 303);
}

Contre-exemple : passer directement destination à redirect, ou vérifier seulement qu'elle commence par une barre ; une référence commençant par deux barres peut désigner un autre host. Correction : la table limite les choix sans tenter de reconnaître toutes les formes d'URL. Une destination externe légitime nécessite sa propre politique explicite.

Passage canonique conservé

redirect() ne vérifie pas sa destination : une valeur venue du user y ouvre un redirect non validé, vers le domain d'un attaquant. Toute URL redirigée est validée, ou vient d'une route.

Repère — Parameters utiles : Ordinary parameters unused by path or host placeholders become query parameters unless equal to route defaults. _query supplies explicit query data; _fragment supplies the fragment. Les parameters ordinaires non consommés par les variables du path ou du host vont en query, sauf ceux égaux aux défauts de route ; _query fournit des données de query explicites. _fragment désigne l'ancre de destination.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le statut par défaut est 302, pas 301.

    Le statut par défaut est 302, pas 301. Le permanent se demande explicitement, par le troisième argument — et un 301 mis en cache par le navigateur est difficile à reprendre.

  • Voir l’explication : 304 n'est pas un statut de redirect valide.

    304 n'est pas un statut de redirect valide. Il est dans la plage 3xx, mais la Response de redirect le refuse et lève.

  • Voir l’explication : redirectToRoute() demande un path absolu par défaut.

    redirectToRoute() demande un path absolu par défaut. Le générateur peut l'élargir pour respecter le host ou le schéma de la route ; le type de référence n'est pas exposé par ce raccourci.

  • Voir l’explication : Rediriger vers une URL ne valide pas cette URL.

    Rediriger vers une URL ne valide pas cette URL. Une destination construite depuis une entrée user ouvre un redirect non validé.

  • Voir l’explication : Un redirect est une vraie Response HTTP.

    Un redirect est une vraie Response HTTP. Le navigateur repart, l'URL affichée change, et le controller d'arrivée s'exécute dans une seconde Request — ce n'est pas un appel interne.

Application

À retenir en priorité
  1. redirectToRoute() génère d'abord la destination.
  2. Pour une URL complète, la générer explicitement puis appeler redirect().
  3. Le permanent n'est pas le défaut.
  4. 304 n'est pas accepté comme statut de RedirectResponse.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • redirectToRoute() = redirect(generateUrl()) : path absolu demandé.
  • Statut 302 par défaut ; 301 par le troisième argument.
  • Admis : 201, 301, 302, 303, 307, 308 ; le reste lève.
  • Suppléments non consommés par les variables path/host, hors valeurs identiques aux défauts → query string ; _query fournit des données explicites de query et _fragment désigne l'ancre.
  • 301 sans Cache-Control : header retiré, cache durable.
  • redirect() ne vérifie pas la confiance dans la destination : jamais d'entrée user brute.

Moyen mnémotechnique : « 302 par défaut, 301 pour toujours ».
