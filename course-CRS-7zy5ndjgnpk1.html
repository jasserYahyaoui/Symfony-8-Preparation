Objectif

Rediriger le navigateur depuis un controller, et connaître le danger attaché à l'une des deux methods.

L'essentiel

À comprendre

À retenir en priorité
  1. redirectToRoute() génère d'abord la destination.
  2. Pour une URL complète, la générer explicitement puis appeler redirect().

Un controller redirige par redirectToRoute() (vers une route) ou redirect() (vers une URL). Les deux rendent une RedirectResponse : le navigateur repart, l'URL affichée change. Le statut est 302 par défaut, seuls six codes sont admis, et redirect() ne vérifie jamais sa destination.

Le schéma

À retenir en priorité
  1. Les parameters ordinaires non consommés par les variables du path ou du host vont en query, sauf ceux égaux aux défauts de route ; _query fournit des données de query explicites.
  2. _fragment désigne l'ancre de destination.

Bleu = construction côté serveur, ambre = décision du client, vert = nouvelle exécution. Ce chemin illustre un 303 après POST ; un client peut ne pas suivre la réponse. Le code 201 accepté par la classe n'est pas un ordre de navigation équivalent à un 303.

L'exemple : Post / Redirect / Get

Exemple concret

À retenir en priorité
  1. Le permanent n'est pas le défaut.
  2. 304 n'est pas accepté comme statut de RedirectResponse.

Après une saisie réussie, nous voulons consulter l'article 42 sans renvoyer le POST au rafraîchissement. L'action construit donc un 303 ; le navigateur qui suit Location effectue un nouveau GET, passant de nouveau par routage, résolution du callable et arguments.

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;

final class SaveController extends AbstractController
{
    public function afterSuccessfulSave(): Response
    {
        return $this->redirectToRoute('blog_show', ['id' => 42, '_fragment' => 'comments'], 303);
    }
}

Branche après traitement réussi dans un contrôleur enregistré ; la route blog_show accepte l'identifiant 42. Le fragment est destiné au navigateur.

Les deux methods

Nous connaissons blog_show et id=42, pas nécessairement son URL finale : redirectToRoute() demande d'abord au générateur la destination. redirect() reçoit au contraire une destination déjà construite. Dans les deux cas, aucun appel de BlogController::show n'a lieu à la construction de la Response ; le client peut même ne pas la suivre.

redirectToRoute() est bâtie sur redirect() : elle génère l'URL avec generateUrl(), sans type de référence, donc en path absolu — Location porte normalement /accueil à host et schéma identiques. Une route exigeant un autre host ou schéma peut imposer une référence réseau ou une URL absolue. Pas de quatrième argument pour changer cela : une URL complète se construit soi-même, puis passe à redirect().

🌍 In Real Life

La situation : l'accueil peut chercher l'adresse d'une salle à partir de son nom dans le plan, ou recopier une adresse déjà connue sur un panneau. Préparer ce panneau ne déplace pas le visiteur.

L’équivalent dans Symfony : redirectToRoute() génère la destination depuis une route et ses paramètres, puis construit une RedirectResponse comme redirect(). Le navigateur ne fera une nouvelle requête que si la réponse lui est envoyée et qu'il la suit.

Retour à la réalité technique : le raccourci demande normalement un chemin absolu ; les contraintes de host ou schéma peuvent imposer une référence plus complète. La construction ne déclenche ni le matching de la cible ni son contrôleur. Ce n'est pas un appel interne.

🧠 Comment le mémoriser : « Le plan fournit l'adresse ; le panneau ne transporte personne. » Image mentale : plan consulté puis panneau remis au visiteur. Question-réflexe : ai-je un nom de route à résoudre ou déjà une destination ?

⚠️ À ne pas confondre : chemin absolu et URL absolue ; retourner une redirection et exécuter sa destination.

Le redirect dit au visiteur de rejoindre un autre guichet : le client effectue une nouvelle Request. Le forward demande au collègue de préparer le dossier sans faire bouger le visiteur.

Le statut

Le 303 après inscription exprime une consultation ultérieure, tandis qu'un déplacement permanent de page relève d'un autre choix. Ne déduis pas le comportement du client du seul fait que RedirectResponse accepte un code : 201 figure dans l'API, sans être interchangeable avec un ordre de navigation 303.

Le troisième argument porte le code, 302 par défaut : redirectToRoute('homepage', [], 301). Un 301 indique un déplacement permanent et peut être mis en cache. Sans Cache-Control fourni, le constructeur retire ce header ; cela ne fixe ni le stockage effectif ni sa durée. Les directives applicables et la politique du client ou du cache déterminent la réutilisation, éventuellement avec une fraîcheur heuristique. Le constructor vérifie le statut par isRedirect() : 201, 301, 302, 303, 307 et 308 seulement ; tout autre code — 304, 200 — lève une InvalidArgumentException, comme une URL vide.

🌍 In Real Life

La situation : après le dépôt d'un dossier, l'accueil indique « consultez maintenant la confirmation ». Ce n'est pas la même consigne que « ce bureau a déménagé définitivement » ou « déposez ce même dossier à l'autre adresse ».

L’équivalent dans Symfony : un 303 après POST mène à la consultation par GET ; 301 indique un déplacement permanent ; 307/308 préservent la méthode lors du suivi. Le statut choisi exprime la consigne HTTP, pas seulement la forme de l'objet PHP.

Retour à la réalité technique : les codes admis par RedirectResponse ne sont pas tous interchangeables : 201 n'ordonne pas une navigation comme 303, et 304 est refusé par cette classe. Un 301 peut être mémorisé par un cache ; « permanent » ne garantit pas une conservation littéralement éternelle.

🧠 Comment le mémoriser : « Consulter ensuite, déménager, ou redéposer : choisir la consigne. » Image mentale : trois panneaux aux actions différentes. Question-réflexe : quelle méthode et quelle permanence dois-je demander au client ?

⚠️ À ne pas confondre : code accepté par le constructeur, sémantique HTTP et comportement garanti du client.

Parameters utiles

Pour l'article, id remplit le placeholder et _fragment vise les commentaires dans la page reçue. Le fragment n'est pas envoyé au serveur dans la nouvelle requête HTTP. Les autres paramètres sont interprétés par le générateur, qui peut les consommer pour le host ou les omettre s'ils valent un défaut ; transmettre toute la query n'est pas la copier.

  • les variables du path et du host consomment leurs parameters. Les parameters ordinaires restants deviennent des paramètres de query, sauf lorsqu'ils sont égaux aux valeurs par défaut de la route ;
  • la key spéciale _query permet de fournir explicitement des données de query ;
  • la key spéciale _fragment ajoute une ancre ;
  • $request->attributes->get('_route') redirige vers la route courante.

Exemples avec un contexte HTTPS sur www.example.test, sans préfixe de déploiement : une route /home dont le host est {sub}.example.test, générée avec sub=m, donne //m.example.test/home, pas ?sub=m. Pour une route /items avec le défaut non-placeholder page=1, fournir page=1 donne /items, tandis que page=2 donne /items?page=2.

redirectToRoute('blog_show', $request->query->all()) transmet ces parameters au générateur : il ne garantit donc pas une copie identique de la query string d'origine. Les paramètres obligatoires de route doivent être fournis.

🌍 In Real Life

La situation : une fiche de destination contient une adresse, des indications complémentaires et un marque-page pour le lecteur. Le bureau distribue ces informations dans leurs cases ; il ne recopie pas nécessairement toute la fiche à la fin de l'adresse.

L’équivalent dans Symfony : les paramètres remplissent d'abord les variables de path et de host ; les suppléments ordinaires peuvent devenir la query. _query fournit des données explicites de query et _fragment un repère destiné au navigateur.

Retour à la réalité technique : les valeurs égales aux défauts peuvent être omises. Le fragment ne part pas dans la requête HTTP suivante. Lire _route dans les attributes fournit seulement le nom courant : il faut encore appeler le helper avec les paramètres nécessaires pour construire la redirection.

🧠 Comment le mémoriser : « Adresse au serveur, marque-page au lecteur. » Image mentale : enveloppe adressée et marque-page dans le document. Question-réflexe : ce paramètre sert-il au chemin, au host, à la query ou au fragment ?

⚠️ À ne pas confondre : transmettre un tableau au générateur et recopier exactement la query d'origine.

Le danger de `redirect()`

À retenir en priorité
  1. Construire une RedirectResponse ne valide pas la destination.
  2. Ne pas transmettre directement une URL non fiable.

Si l'inscription reçoit next du client, le succès du formulaire ne rend pas cette destination fiable. Préfère une route interne connue ou une politique explicite de destinations autorisées. Le helper prépare un en-tête ; il ne décide pas à la place du projet où le lecteur est autorisé à être envoyé.

redirect() ne vérifie pas sa destination : une valeur venue du user y ouvre un redirect non validé, vers le domain d'un attaquant. Toute URL redirigée est validée, ou vient d'une route.

🌍 In Real Life

La situation : un visiteur fournit lui-même l'adresse du « prochain guichet ». L'inscrire proprement sur le papier officiel du bureau ne prouve pas qu'elle appartient à un service autorisé.

L’équivalent dans Symfony : redirect() place la destination dans la réponse sans appliquer la politique de confiance du projet. Après inscription, une valeur next fournie par le client doit être contrôlée, ou remplacée par une route interne connue.

Retour à la réalité technique : validité syntaxique et destination autorisée sont deux contrôles distincts. Préférer une route connue ne dispense pas de maîtriser les paramètres influençant notamment le host. La validation réussie des autres champs du formulaire ne valide pas implicitement cette cible.

🧠 Comment le mémoriser : « Une adresse bien écrite n'est pas une adresse approuvée. » Image mentale : adresse non contrôlée sur un papier à en-tête officiel. Question-réflexe : qui choisit la destination, et quelle politique l'autorise ?

⚠️ À ne pas confondre : génération d'URL, validation du formulaire et contrôle des destinations de redirection.

Answer: Ordinary parameters unused by path or host placeholders become query parameters unless equal to route defaults. _query supplies explicit query data; _fragment supplies the fragment.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le statut par défaut est 302, pas 301.

    Le statut par défaut est 302, pas 301. Le permanent se demande explicitement, par le troisième argument — et un 301 mis en cache par le navigateur est difficile à reprendre.

  • Voir l’explication : 304 n'est pas un statut de redirect valide.

    304 n'est pas un statut de redirect valide. Il est dans la plage 3xx, mais la Response de redirect le refuse et lève.

  • Voir l’explication : redirectToRoute() demande un path absolu par défaut.

    redirectToRoute() demande un path absolu par défaut. Le générateur peut l'élargir pour respecter le host ou le schéma de la route ; le type de référence n'est pas exposé par ce raccourci.

  • Voir l’explication : Rediriger vers une URL ne valide pas cette URL.

    Rediriger vers une URL ne valide pas cette URL. Une destination construite depuis une entrée user ouvre un redirect non validé.

  • Voir l’explication : Un redirect est une vraie Response HTTP.

    Un redirect est une vraie Response HTTP. Le navigateur repart, l'URL affichée change, et le controller d'arrivée s'exécute dans une seconde Request — ce n'est pas un appel interne.

Application

À retenir en priorité
  1. redirectToRoute() génère d'abord la destination.
  2. Pour une URL complète, la générer explicitement puis appeler redirect().
  3. Le permanent n'est pas le défaut.
  4. 304 n'est pas accepté comme statut de RedirectResponse.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • redirectToRoute() = redirect(generateUrl()) : path absolu demandé.
  • Statut 302 par défaut ; 301 par le troisième argument.
  • Admis : 201, 301, 302, 303, 307, 308 ; le reste lève.
  • Suppléments non consommés par les variables path/host, hors valeurs identiques aux défauts → query string ; _query fournit des données explicites de query et _fragment désigne l'ancre.
  • 301 sans Cache-Control fourni : header retiré, mise en cache possible ; stockage et fraîcheur dépendent des règles du cache, pas d'une durée éternelle.
  • redirect() ne vérifie pas la confiance dans la destination : jamais d'entrée user brute.

Moyen mnémotechnique : « 302 par défaut, 301 déplacement permanent — pas cache éternel ».
