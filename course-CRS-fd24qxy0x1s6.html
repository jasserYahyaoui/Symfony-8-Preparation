Objectif

Distinguer un redirect interne d'un redirect HTTP, savoir ce que la sub-Request garde et ce qu'elle perd, et connaître les effets de bord.

L'essentiel

À comprendre

À retenir en priorité
  1. Le traitement reste dans le même cycle PHP.
  2. La Response de la cible revient au controller appelant.

forward() n'est pas un redirect : le kernel exécute une sub-Request dans le même cycle PHP et rend la Response du controller cible. Une seule Request HTTP, l'URL ne bouge pas. Tout le reste se lit dans un appel à duplicate() : les attributes sont remplacés, la query string est perdue, le body POST et la session sont gardés.

Le schéma

À retenir en priorité
  1. Le défaut [] remplace la query string.
  2. Le body POST reste partagé par la duplication.

L'exemple

Exemple concret

$response = $this->forward('App\Controller\OtherController::fancy', [
    'name'  => $name,
    'color' => 'green',
]);

Ce que fait `forward()`

Le kernel appelle l'autre controller dans le même cycle PHP et rend la Response que ce controller retourne. Le navigateur n'en sait rien, et la Response peut toujours être modifiée avant d'être retournée.

Le contraste

À retenir en priorité
  1. Un redirect demande au client de repartir.
  2. Un forward récupère le contenu sans changer l'URL affichée.

Un redirect dit au client d'aller ailleurs ; un forward va chercher le contenu sans le lui dire.

Le forward est le passage du guichetier dans l'arrière-bureau, puis son retour au même comptoir. Si seul un calcul commun est nécessaire, un service partagé évite de refaire un cycle kernel.

Repère — Ce que la sub-Request garde et perd : No. Pass it explicitly; the original POST body is preserved. Le défaut [] remplace la query string. Le body POST reste partagé par la duplication.

Ce que la sub-Request garde et perd

Les trois premiers parameters de duplicate() sont la query string, le body POST et les attributes ; null garde l'original, un array le remplace.

  • Perdus : les attributes, remplacés par l'array $path — seul _format est reporté —, et la query string, dont le défaut est []. Pour la transmettre : forward($ctrl, [], $request->query->all()).
  • Gardés : le body POST, passé à null ; les cookies, headers et variables serveur ; la session, partagée avec la Request en cours.

Les arguments passent par leur nom

À comprendre

À retenir en priorité
  1. Les keys deviennent des Request attributes.
  2. L'ordre des entrées n'est pas déterminant.

C'est quoi ?

Un forward est un traitement interne d'un autre controller par le kernel. AbstractController duplique la Request, remplace ses attributes par ceux fournis avec _controller, puis appelle le kernel avec le type SUB_REQUEST. Il retourne la Response obtenue ; aucune réponse de redirection n'est nécessaire.

À quoi ça sert ?

Il permet de réutiliser un traitement HTTP tout en gardant la même URL dans le navigateur. Si l'on souhaite seulement partager une règle métier, un service commun est généralement plus explicite et moins coûteux qu'un second passage par le cycle HTTP.

Où dans Symfony ?

forward(controller, path, query) reçoit une désignation de controller, un tableau d'attributes et un tableau de query string. Malgré son nom path, le deuxième argument n'est pas une chaîne de chemin. Les valeurs sont résolues d'après le nom des arguments du controller cible.

Comment, étape par étape ?

  1. Identifier la méthode cible et ses arguments.
  2. Fournir des clés portant exactement ces noms.
  3. Retourner la Response produite, éventuellement après une modification volontaire.
  4. Si la cible a besoin d'informations de route, transmettre explicitement _route et _route_params ; les attributes de la route initiale ne sont pas simplement tous conservés.

Exemple concret PHP

Deux actions d'un même controller, enregistré normalement :

<?php
namespace App\Controller;

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;

final class GreetingController extends AbstractController
{
    public function entry(): Response
    {
        return $this->forward(self::class.'::message', ['name' => 'Ada']);
    }

    public function message(string $name): Response
    {
        return new Response('Bonjour '.$name, headers: ['Content-Type' => 'text/plain']);
    }
}

La cible reçoit Ada parce que sa variable s'appelle name. Le texte est explicitement servi en texte brut. Contre-exemple : remplacer la clé name par user tout en conservant la signature. L'ordre des éléments ne corrige pas l'absence de valeur pour name. Correction : aligner le nom ou modifier le contrat de la cible. Une sous-Request ne crée pas un nouveau client ni une nouvelle navigation ; elle conserve un contexte partagé dont il faut considérer les effets de bord.

Passage canonique conservé

Les arguments passent par leur nom

L'array devient les attributes : il fournit les arguments de la cible comme une route. RequestAttributeValueResolver cherche une key portant le nom de l'argument ; l'ordre ne compte pas.

L'effet de bord à connaître

À comprendre

À retenir en priorité
  1. _route n'est pas automatiquement conservé.
  2. Transmettre _route et _route_params seulement si le contexte le demande.

C'est quoi ?

forward prépare une sous-Request avec les attributes fournis dans son deuxième argument, auxquels il ajoute _controller. Il ne recopie pas automatiquement toutes les métadonnées de la route d'origine dans ce nouveau tableau.

À quoi ça sert ?

La cible reçoit un contexte explicitement construit. Cela évite de supposer qu'elle a réellement été choisie par la même route que l'action initiale ; inversement, un template qui dépend du nom de route doit recevoir l'information voulue.

Où dans Symfony ?

app.current_route et app.current_route_parameters reflètent les attributes de la Request courante. Dans un forward ordinaire sans _route ni _route_params fournis, ils ne décrivent donc pas automatiquement la route initiale. La sous-Request courante est distincte de la principale.

Comment, étape par étape ?

  1. Identifier pourquoi le template cible a besoin de ces métadonnées.
  2. Ne transmettre que celles dont le sens est volontairement conservé.
  3. Ajouter _route et _route_params aux attributes du forward si ce choix convient.
  4. Ne pas présenter ces valeurs copiées comme le résultat d'un nouveau matching.

Exemple concret PHP

Action d'AbstractController ; SummaryController::show est un controller enregistré :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function summary(\Symfony\Component\HttpFoundation\Request $request): \Symfony\Component\HttpFoundation\Response
{
    return $this->forward('App\\Controller\\SummaryController::show', [
        '_route' => $request->attributes->get('_route'),
        '_route_params' => $request->attributes->get('_route_params', []),
    ]);
}

Le template cible peut afficher le contexte transmis. Contre-exemple : utiliser app.current_route pour générer un lien dans la cible sans avoir prévu son absence. Correction : transmettre les métadonnées nécessaires ou, mieux si le besoin est seulement un lien de retour, fournir directement cette donnée explicite au traitement plutôt que dépendre d'une route implicite.

Passage canonique conservé

L'effet de bord à connaître

Après un forward(), app.current_route, app.current_route_parameters et _route_params sont vides dans le template de la cible. On les fournit en ajoutant _route et _route_params à l'array passé.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un forward n'est pas un redirect.

    Un forward n'est pas un redirect. Il n'y a qu'une Request HTTP, l'URL affichée ne bouge pas, et c'est la Response du controller cible qui part au navigateur. Aucun 3xx n'est émis.

  • Voir l’explication : La query string d'origine n'arrive pas à la cible.

    La query string d'origine n'arrive pas à la cible. Le défaut du troisième argument est un array vide, qui remplace ; il faut la transmettre explicitement.

  • Voir l’explication : Le body POST, lui, arrive.

    Le body POST, lui, arrive. L'asymétrie avec la query string vient de ce que l'un est passé à null et l'autre à [].

  • Voir l’explication : Après un forward, la route courante est vide dans le template.

    Après un forward, la route courante est vide dans le template. Les attributes ont été remplacés ; _route n'est renseigné que si on le passe soi-même.

  • Voir l’explication : Les arguments du controller cible s'apparient par nom

    Les arguments du controller cible s'apparient par nom, comme pour une route.

Application

À retenir en priorité
  1. Le traitement reste dans le même cycle PHP.
  2. La Response de la cible revient au controller appelant.
  3. Un redirect demande au client de repartir.
  4. Un forward récupère le contenu sans changer l'URL affichée.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • forward() = sub-Request : une Request HTTP, URL inchangée, pas de 3xx.
  • duplicate() : un array remplace, null garde.
  • Attributes remplacés par l'array ; _format reporté.
  • Query string perdue par défaut ; body POST, cookies, session gardés.
  • Arguments de la cible : par nom, via RequestAttributeValueResolver.
  • app.current_route vide, sauf à passer _route.

Moyen mnémotechnique : « Forward ne dit rien au navigateur ».

Where are flash messages stored?

With Symfony Session integration, flash messages are stored in the session. A standalone FlashBag keeps them only in memory and provides no persistence between requests; get()/all() consume them, peek()/peekAll() preserve them.

La persistance entre requêtes vient du stockage de session intégré, pas de FlashBag seul. get()/all() consomment les messages, peek()/peekAll() les conservent. Le type du flash est une string libre, pas une enum imposée.
