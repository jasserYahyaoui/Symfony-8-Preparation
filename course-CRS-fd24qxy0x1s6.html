Objectif

Distinguer un redirect interne d'un redirect HTTP, savoir ce que la sub-Request garde et ce qu'elle perd, et connaître les effets de bord.

L'essentiel

À comprendre

À retenir en priorité
  1. Le traitement reste dans le même cycle PHP.
  2. La Response de la cible revient au controller appelant.

forward() n'est pas un redirect : le kernel exécute une sub-Request dans le même cycle PHP et rend la Response du controller cible. Une seule Request HTTP, l'URL ne bouge pas. Tout le reste se lit dans un appel à duplicate() : les attributes sont remplacés, la query string est perdue, le body POST et la session sont gardés.

Le schéma

À retenir en priorité
  1. Le défaut [] remplace la query string.
  2. Les données POST analysées sont conservées dans un bag cloné indépendant ; la session reste partagée.

Bleu = appels internes ; vert = réponse rendue à l'appelant, pas encore envoyée. forward() ne construit pas lui-même un 3xx, mais la cible peut retourner une RedirectResponse. Il ne remplace pas un service métier partagé et ne garantit pas que tous les listeners réservés à la requête principale s'exécutent.

L'exemple

Exemple concret

Un contrôleur du blog peut déléguer un rendu à une autre action. L'extrait transmet deux attributs à cette cible ; il suppose son callable disponible. Ce n'est pas le moyen de réutiliser simplement ArticleCatalog : un service partagé éviterait le coût et les effets d'une nouvelle traversée HTTP interne.

$response = $this->forward('App\Controller\OtherController::fancy', [
    'name'  => $name,
    'color' => 'green',
]);

Ce que fait `forward()`

Pendant /blog/42, forward() crée une sous-requête et appelle le kernel avec SUB_REQUEST. HttpKernel obtient encore un callable, prépare ses arguments et traite son retour ; le contrôleur appelant reçoit cette Response avant de décider ce qu'il retourne lui-même. Aucun échange réseau supplémentaire n'est requis par cette opération.

Le kernel appelle l'autre controller dans le même cycle PHP et rend la Response que ce controller retourne. Le navigateur n'en sait rien, et la Response peut encore être modifiée avant d'être retournée.

🌍 In Real Life

La situation : le serveur demande à un autre poste de préparer une partie du service, puis récupère le résultat avant de répondre au client resté à table. La coordination reste interne au restaurant.

L’équivalent dans Symfony : forward() prépare une Request dérivée et la confie à HttpKernel comme SUB_REQUEST. La résolution du callable et de ses arguments précède son invocation ; la Response revient ensuite au contrôleur appelant.

Retour à la réalité technique : aucun nouvel échange réseau n'est exigé par cette délégation. La Response reçue peut être modifiée ou utilisée avant le retour final ; elle n'est pas déjà envoyée. Les listeners peuvent distinguer requête principale et sous-requête.

🧠 Comment le mémoriser : « Le résultat revient au serveur avant d'aller à la table. » Image mentale : plateau circulant entre postes puis revenant au serveur. Question-réflexe : ai-je besoin d'un traitement HTTP interne ou seulement d'une opération de service métier ?

⚠️ À ne pas confondre : sous-requête HttpKernel, appel direct d'un service et redirection du client.

Le contraste

À retenir en priorité
  1. Un redirect demande au client de repartir.
  2. Un forward récupère le contenu sans changer l'URL affichée.

Après une inscription réussie, un forward ne réalise donc pas le Post/Redirect/Get : le navigateur reste sur sa requête d'origine. La comparaison suivante suppose que le client suit la redirection HTTP ; un client qui ne suit pas Location n'émet pas la seconde requête.

Requests HTTP deux une
Type de Request kernel main Request sub-Request

Un redirect dit au client d'aller ailleurs ; un forward va chercher le contenu sans le lui dire.

🌍 In Real Life

La situation : envoyer un dossier au bureau voisin pendant que le visiteur attend ne revient pas à lui demander de sortir et de se présenter à une nouvelle adresse.

L’équivalent dans Symfony : le forward effectue une délégation interne ; une redirection HTTP fournit une destination que le client peut suivre par une autre requête. Après un POST, le forward ne crée pas le GET de confirmation du schéma Post/Redirect/Get.

Retour à la réalité technique : cette différence concerne l'opération forward() elle-même. La cible peut retourner une RedirectResponse, que l'appelant peut à son tour retourner : une navigation peut alors résulter de cette réponse finale, pas du mécanisme de sous-requête.

🧠 Comment le mémoriser : « Faire circuler le dossier n'est pas faire revenir le visiteur. » Image mentale : dossier derrière le comptoir versus visiteur franchissant une autre porte. Question-réflexe : le navigateur a-t-il réellement commencé une nouvelle requête ?

⚠️ À ne pas confondre : délégation interne après POST et protection contre sa répétition au rafraîchissement.

Le forward est le passage du guichetier dans l'arrière-bureau, puis son retour au même comptoir. Si seul un calcul commun est nécessaire, un service partagé évite de refaire un cycle kernel.

Repère — Ce que la sub-Request garde et perd :

Question: Does forward() preserve the original query string by default?

Answer: No. Pass it explicitly; the original POST body is preserved.

Le défaut [] remplace la query string. Les données POST analysées sont conservées dans un bag cloné indépendant ; la session reste partagée.

Ce que la sub-Request garde et perd

Si /blog/42?preview=1 délègue un rendu, la cible ne doit pas compter sur query['preview'] sans transmission explicite. En revanche, une écriture en session est visible par l'appelant car l'objet session reste partagé. Le clonage des sacs n'est donc pas une isolation complète de tous les effets du traitement.

Les trois premiers parameters de duplicate() sont les données des bags query, request (POST analysé) et attributes ; null conserve leurs données dans des bags clonés indépendants, un array remplace les données du bag.

  • Perdus : les attributes, remplacés par l'array $path — seul _format est reporté —, et la query string, dont le défaut est []. Pour la transmettre : forward($ctrl, [], $request->query->all()).
  • Gardés : les données POST analysées, avec l'argument request à null ; les données des cookies, headers et variables serveur, dans leurs bags clonés. Modifier un de ces bags ne modifie pas celui de la Request d'origine. La session, elle, reste partagée avec la Request en cours.

Ici « query perdue » désigne le bag query : ?page=3 n'alimente plus $sub->query->get('page') sans transmission explicite. duplicate() ne réécrit pas pour autant REQUEST_URI ou QUERY_STRING dans le bag serveur conservé. Le bag POST contient les paramètres décodés, pas nécessairement tout le corps brut.

🌍 In Real Life

La situation : on prépare une copie de travail du dossier : certaines feuilles sont reprises, d'autres remplacées par une liste vide, tandis que le registre commun reste partagé.

L’équivalent dans Symfony : duplicate($query, null, $path) remplace le bag query par le tableau fourni et conserve les données POST analysées dans un bag cloné. Les attributes sont remplacés par $path, complété pour la cible ; la session reste partagée.

Retour à la réalité technique : [] signifie remplacer par vide, null conserver les données dans les sacs concernés. Cela ne garantit pas une copie profonde de tout objet contenu ni une isolation des effets métier. Un bag query vide ne réécrit pas les valeurs REQUEST_URI et QUERY_STRING du bag serveur.

🧠 Comment le mémoriser : « Copie des feuilles, registre encore commun. » Image mentale : dossiers séparés reliés au même registre. Question-réflexe : cette donnée est-elle remplacée, copiée ou réellement partagée ?

⚠️ À ne pas confondre : bag cloné et état totalement isolé ; paramètres POST analysés et corps brut.

Les arguments passent par leur nom

À retenir en priorité
  1. Les keys deviennent des Request attributes.
  2. L'ordre des entrées n'est pas déterminant.

Pour une cible show(int $id), fournis la clé id dans le deuxième argument de forward(). Le nom de route blog_show n'est pas la cible attendue : _controller désigne ici directement un callable. RouterListener peut sauter le matching puisque cette destination existe déjà ; HttpKernel appelle ensuite son ArgumentResolver.

L'array devient les attributes : il fournit les arguments de la cible comme une route. RequestAttributeValueResolver cherche une key portant le nom de l'argument ; l'ordre ne compte pas.

🌍 In Real Life

La situation : le poste destinataire reçoit des fiches marquées « nom » et « couleur ». Il les place selon leur étiquette, pas selon l'ordre dans lequel elles ont été empilées.

L’équivalent dans Symfony : les clés du deuxième tableau deviennent des attributes de la sous-requête. RequestAttributeValueResolver y recherche le nom du paramètre ; _controller désigne la cible que ControllerResolver doit rendre appelable.

Retour à la réalité technique : le premier argument du helper n'est pas un nom de route. La présence de _controller permet au RouterListener standard de ne pas refaire le matching. Cela ne supprime pas la résolution des arguments ni leurs contraintes ; aucune entité n'est automatiquement chargée par cet appariement de noms.

🧠 Comment le mémoriser : « Lire l'étiquette, pas la position dans la pile. » Image mentale : fiches nommées posées dans leurs cases. Question-réflexe : ma clé correspond-elle au nom attendu et ma valeur convient-elle à la cible ?

⚠️ À ne pas confondre : nom de route, désignation du callable et nom d'argument ; attributes de Request et métadonnées PHP.

L'effet de bord à connaître

À retenir en priorité
  1. _route n'est pas automatiquement conservé.
  2. Transmettre _route et _route_params seulement si le contexte le demande.

Un menu Twig qui marque le lien actif selon app.current_route peut cesser de fonctionner dans le rendu délégué, même si le navigateur affiche toujours /blog/42. Il consulte les attributs de la sous-requête courante, pas l'URL de la barre d'adresse. Transmettre les métadonnées nécessaires doit être un choix explicite, pas une supposition de copie complète.

Après un forward(), app.current_route, app.current_route_parameters et _route_params sont vides dans le template de la cible. On les fournit en ajoutant _route et _route_params à l'array passé.

🌍 In Real Life

La situation : le bureau voisin reçoit la fiche de travail mais pas l'étiquette indiquant le parcours initial du visiteur. Son affichage « vous êtes ici » ne peut pas retrouver cette information en regardant simplement la porte extérieure.

L’équivalent dans Symfony : le template de la cible consulte la Request courante, ici la sous-requête. Comme ses attributes ont été remplacés, _route et _route_params ne sont pas hérités automatiquement ; app.current_route peut donc être vide.

Retour à la réalité technique : transmettre explicitement ces métadonnées restaure le contexte nécessaire au rendu, sans effectuer un nouveau matching ni prouver que cette route a été sélectionnée pour la sous-requête. Choisir les données nécessaires est préférable à supposer une copie de tout le contexte.

🧠 Comment le mémoriser : « La porte reste la même, la fiche courante a changé. » Image mentale : même façade, nouvelle fiche interne sans étiquette de parcours. Question-réflexe : mon template lit-il le contexte principal ou celui de la sous-requête ?

⚠️ À ne pas confondre : URL visible, Request courante et métadonnées de route transmises.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un forward n'est pas un redirect.

    Un forward n'est pas un redirect. Il n'y a qu'une Request HTTP, l'URL affichée ne bouge pas, et c'est la Response du controller cible qui part au navigateur. Aucun 3xx n'est créé par forward() lui-même ; le statut vient de la cible.

  • Voir l’explication : La query string d'origine n'arrive pas à la cible.

    La query string d'origine n'arrive pas à la cible. Le défaut du troisième argument est un array vide, qui remplace ; il faut la transmettre explicitement.

  • Voir l’explication : Le body POST, lui, arrive.

    Le body POST, lui, arrive. L'asymétrie avec la query string vient de ce que l'un est passé à null et l'autre à [].

  • Voir l’explication : Après un forward, la route courante est vide dans le template.

    Après un forward, la route courante est vide dans le template. Les attributes ont été remplacés ; _route n'est renseigné que si on le passe soi-même.

  • Voir l’explication : Les arguments du controller cible s'apparient par nom

    Les arguments du controller cible s'apparient par nom, comme pour une route.

Application

À retenir en priorité
  1. Le traitement reste dans le même cycle PHP.
  2. La Response de la cible revient au controller appelant.
  3. Un redirect demande au client de repartir.
  4. Un forward récupère le contenu sans changer l'URL affichée.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • forward() = sub-Request : pas de navigation imposée ; la réponse cible peut être un 3xx.
  • duplicate() : un array remplace, null garde.
  • Attributes remplacés par l'array ; _format reporté.
  • Query string perdue par défaut ; body POST, cookies, session gardés.
  • Arguments de la cible : par nom, via RequestAttributeValueResolver.
  • app.current_route vide, sauf à passer _route.

Moyen mnémotechnique : « Forward ne dit rien au navigateur ».

Where are flash messages stored?

With Symfony Session integration, flash messages are stored in the session. A standalone FlashBag keeps them only in memory and provides no persistence between requests; get()/all() consume them, peek()/peekAll() preserve them.

La persistance entre requêtes vient du stockage de session intégré, pas de FlashBag seul. get()/all() consomment les messages, peek()/peekAll() les conservent. Le type du flash est une string libre, pas une enum imposée.
