Objectif

Séparer trois packages que l'on croit n'en former qu'un, et savoir lequel répond de quoi — et lequel dépend de l'autre.

L'essentiel

À comprendre

À retenir en priorité
  1. Le hash a son propre component.
  2. Un firewall n'est pas nécessaire pour hacher.

La security de Symfony n'est pas d'un seul tenant : le hash, les tokens CSRF et le modèle (users, tokens, voters, roles) vivent dans trois packages distincts. Hacher un password ou protéger un form n'exige pas le système complet — mais tous les packages ne s'installent pas seuls.

Le schéma

À retenir en priorité
  1. Le modèle et HTTP sont séparés.
  2. SecurityBundle configure leur intégration.

L'exemple

Exemple concret

À retenir en priorité
  1. Le token CSRF vérifie l'intention de soumission.
  2. Il ne prouve pas une identité utilisateur.
composer require symfony/password-hasher   → le hash, seul
composer require symfony/security-csrf     → les tokens CSRF, + security-core, + password-hasher
composer require symfony/security-bundle   → tout : core, csrf, http, password-hasher, configuration

Trois components, trois responsabilités

À comprendre

À retenir en priorité
  1. Security Core porte le modèle d'accès.
  2. PasswordHasher et CSRF ont des responsabilités distinctes.

C'est quoi ?

Un component est un package réutilisable ; SecurityBundle les assemble dans une application Symfony. Trois problèmes différents demandent trois mécanismes : représenter l'identité et décider d'un droit, protéger une soumission contre une origine indésirable, vérifier un mot de passe sans le stocker en clair.

À quoi ça sert ?

  • Security Core fournit users, tokens et voters : le modèle de décision d'accès.
  • Security CSRF fournit les tokens contre la falsification de requête intersite, ou CSRF. Le contrôle lie une soumission au contexte attendu ; il ne prouve pas l'identité de son auteur.
  • PasswordHasher calcule et vérifie les empreintes des mots de passe. Le hash est une représentation de vérification, pas un chiffrement à défaire.

Où dans Symfony ?

security-http ajoute le lien avec HTTP : un firewall sélectionne le dispositif d'authentication, c'est-à-dire de vérification d'identité. SecurityBundle expose security: et configure les services. Le modèle security-core ne dépend pas d'HttpFoundation : une décision d'accès n'exige pas en elle-même une Request HTTP.

Comment, étape par étape ?

  1. Identifier le problème : calculer un hash n'exige pas de connecter un user.
  2. Choisir le component : password-hasher peut s'utiliser seul ; security-csrf fonctionne sans firewall.
  3. Distinguer autonomie fonctionnelle et dependencies Composer : en 8.0, security-csrf dépend de security-core, qui dépend de password-hasher. Cela n'active pas automatiquement l'authentication HTTP.
  4. Dans le framework, laisser le bundle assembler ces services puis configurer les contrôles réellement nécessaires.

Exemple concret en shell

Dans un projet PHP disposant de Composer, la commande suivante installe le mécanisme de hash, pas un écran de connexion :

composer require symfony/password-hasher:"8.0.*"

Elle illustre le choix du package, sans être exécutée ici. Pour un formulaire anonyme, le contrôle CSRF reste utile même si aucun user n'est connecté. Contre-exemple : considérer un token CSRF valide comme une autorisation d'effacer un compte. Correction : vérifier séparément CSRF, identité et droit sur le compte. Ne désactiver aucun de ces contrôles pour contourner une erreur de configuration.

Trois components, trois responsabilités

Package Ce qu'il fournit
symfony/security-core le modèle : UserInterface, tokens, voters, décision d'accès, hiérarchie des roles
symfony/security-csrf la génération et la vérification de tokens CSRF
symfony/password-hasher le hash et la vérification des passwords

S'y ajoutent security-http, qui branche le modèle sur la Request HTTP — firewalls, authenticators, entry points —, et SecurityBundle, qui câble le tout dans le framework et expose la key security:.

Qui dépend de qui

À retenir en priorité
  1. Autonomie d'usage ne signifie pas absence de dependency.
  2. La chaîne de packages reste explicite.

Lu dans les composer.json de la branche 8.0 :

Package require (hors PHP et contrats)
password-hasher rien
security-core password-hasher
security-csrf security-core
security-http security-core, http-foundation, http-kernel, property-access
SecurityBundle les quatre, plus le framework

require symfony/password-hasher n'installe donc que lui ; require symfony/security-csrf tire aussi security-core et password-hasher, pour une raison modeste : security-csrf lève les exceptions de security-core.

Pourquoi la séparation compte

À retenir en priorité
  1. Le hash est utilisable séparément.
  2. L'authentication ajoute un autre traitement.

password-hasher peut hacher sans configurer de firewall. security-csrf permet de vérifier un token CSRF sans authentifier un user. Security Core fournit le modèle de décision indépendamment de la Request HTTP.

Ce qui vit dans `security-core`

À retenir en priorité
  1. Les voters portent une décision d'accès.
  2. La console peut utiliser ce modèle sans Request.
  • UserInterface et le contrat user ;
  • les tokens (TokenInterface) et leur stockage ;
  • l'authorization : AccessDecisionManager, Voter, strategies ;
  • la hiérarchie des roles.

Il ne dépend pas de HTTP : http-foundation n'y figure qu'en require-dev. Quelques classes optionnelles s'en servent quand il est présent, comme UsageTrackingTokenStorage pour la session. Une décision d'accès se prend donc aussi en console ou dans un worker.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Ne pas confondre modèle et intégration HTTP.
  2. Le firewall est lié à la Request.
  • Voir l’explication : Le hash n'est pas dans security-core

    Le hash n'est pas dans security-core : il a son propre package, password-hasher — dont security-core dépend.

  • Voir l’explication : La protection CSRF n'est pas liée à l'authentication

    La protection CSRF n'est pas liée à l'authentication : aucun firewall requis. Mais security-csrf n'est pas un package isolé : il installe security-core.

  • Dépendances des composants de sécurité

    Seul password-hasher s'installe vraiment seul.

  • Voir l’explication : security-core ne dépend pas de HTTP.

    security-core ne dépend pas de HTTP. Firewalls et authenticators appartiennent à security-http.

Fiche express

À mémoriser

À retenir en priorité
  1. Le bundle assemble les components.
  2. La key security configure cette intégration.

Si tu dois retenir seulement 5 choses :

  • password-hasher : le hash, sans aucune dependency de sécurité.
  • security-core : user, tokens, voters, roles — sans HTTP ; dépend de password-hasher.
  • security-csrf : tokens CSRF sans firewall ; dépend de security-core.
  • security-http : firewalls, authenticators, la Request.
  • SecurityBundle : les quatre + la configuration security:.

Moyen mnémotechnique : « Hacher seul, protéger sans compte, contrôler avec le core ».

password-hasher ← security-core ← security-csrf
                  security-core ← security-http ← SecurityBundle (+ csrf + hasher)
