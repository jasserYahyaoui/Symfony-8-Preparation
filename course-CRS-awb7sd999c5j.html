Objectif

GET /blog/42 affiche déjà un article public. Ajouter une inscription, un form de commentaire ou un droit de modification introduit trois problèmes différents. Avant de configurer un firewall, identifions le package qui répond à chacun : vérifier un password, protéger une soumission contre une action forgée, décider d'un droit. Une dependency installée n'implique pas que tous ces mécanismes s'exécutent à chaque lecture de l'article.

L'essentiel

À comprendre

À retenir en priorité
  1. Le hash a son propre component.
  2. Un firewall n'est pas nécessaire pour hacher.

À l'inscription, un hash permet de vérifier ensuite le password sans conserver sa valeur en clair. Ce n'est pas un chiffrement réversible : on vérifie un password candidat, on ne déchiffre pas le hash pour retrouver le password initial. Lors d'une soumission, un token CSRF participe à la protection contre une action qu'un autre site ferait envoyer au navigateur. Pour modifier l'article 42, l'authorization décide si l'identité courante possède le droit demandé ; elle ne se réduit ni au hash ni au contrôle CSRF.

Ces responsabilités vivent dans des packages distincts. Hacher un password ou protéger un form n'exige pas le système d'authentication complet — mais indépendance fonctionnelle ne signifie pas absence de dependencies Composer. Commençons par cette frontière d'installation avant de suivre les objets.

Le schéma

À retenir en priorité
  1. Le modèle et HTTP sont séparés.
  2. SecurityBundle configure leur intégration.

Pour choisir les packages du form de commentaire, lire chaque flèche comme « exige ce package », et non comme « appelle ensuite ce mécanisme ».

Bleu : packages fonctionnels ; gris : intégration. Les pointillés signifient dépendances Composer, jamais ordre d'appel. Vue réduite aux chemins utiles : les dépendances directes redondantes de SecurityBundle et les composants HTTP sont détaillés dans le tableau, pas toutes redessinées.

Une command CLI préparant les comptes des auteurs peut hacher leurs passwords sans démarrer de firewall. Le form public de commentaire peut vérifier un token CSRF sans connecter un user. Ce sont deux usages séparés : produire un hash ne vérifie pas encore un password, et vérifier un token CSRF n'identifie pas l'auteur du commentaire. Aucun des deux n'accorde à lui seul un droit métier.

Voici trois choix alternatifs de package, pas trois étapes à rejouer pendant GET /blog/42. Les flèches indiquent le résultat d'installation attendu parmi les packages de sécurité ; ce bloc est un mémo, pas une sortie de terminal. Le cours cible Symfony 8.0 avec PHP 8.4.

composer require symfony/password-hasher:"8.0.*"   → le hash, seul
composer require symfony/security-csrf:"8.0.*"     → les tokens CSRF, + security-core, + password-hasher
composer require symfony/security-bundle:"8.0.*"   → tout : core, csrf, http, password-hasher, configuration

Le choix du package principal ne verrouille pas à lui seul toutes ses dependencies transitives sur 8.0 : elles suivent les contraintes du projet. Une fois l'installation comprise, il reste à attribuer les responsabilités aux objets que l'application utilisera.

Trois components, trois responsabilités

À retenir en priorité
  1. Security Core porte le modèle d'accès.
  2. PasswordHasher et CSRF ont des responsabilités distinctes.

🌍 In Real Life

La situation : au restaurant du blog, vérifier un secret, contrôler un bon de commande et autoriser une modification sont trois tâches.

L’équivalent dans Symfony : vérificateur de secret → PasswordHasher ; contrôle du bon → CSRF ; décision sur la modification du billet 42 → autorisation de Security Core.

Retour à la réalité technique : un hash vérifie un mot de passe sans le déchiffrer. Un token CSRF lutte contre une soumission forgée, sans identifier son auteur ni lui accorder un droit. Ces contrôles exigent leurs appels ou intégrations.

🧠 Comment le mémoriser : « Trois questions, trois outils. » Image mentale : trois tampons distincts sur le comptoir. Question-réflexe : vérifie-t-on un secret, une soumission ou un droit ?

⚠️ À ne pas confondre : être connecté ne rend pas un token CSRF invalide acceptable.

Le besoin « sécuriser le blog » est trop large pour choisir une class. Partir de l'entrée et du résultat attendus : password en clair → hash ou vérification ; token soumis → validité CSRF ; identité et action sur l'article → décision d'accès.

Package Ce qu'il fournit
symfony/security-core le modèle : UserInterface, tokens, voters, décision d'accès, hiérarchie des roles
symfony/security-csrf la génération et la vérification de tokens CSRF
symfony/password-hasher le hash et la vérification des passwords

S'y ajoutent security-http, qui branche le modèle sur la Request HTTP — firewalls, authenticators, entry points —, et SecurityBundle, qui câble le tout dans le framework et expose la key security:. Un firewall sélectionne la configuration de sécurité applicable à une Request ; un authenticator traite une tentative d'authentication. Ils ne sont pas des synonymes de voter : le voter se prononce sur un droit. Cette séparation explique les dependencies du tableau suivant.

Qui dépend de qui

À retenir en priorité
  1. Autonomie d'usage ne signifie pas absence de dependency.
  2. La chaîne de packages reste explicite.

🌍 In Real Life

La situation : acheter un équipement du restaurant peut imposer ses accessoires, sans obliger à tous les utiliser pour chaque commande.

L’équivalent dans Symfony : liste des accessoires requis → dépendances Composer ; équipement effectivement utilisé → classes et services appelés.

Retour à la réalité technique : en Symfony 8.0, security-csrf requiert security-core, qui requiert password-hasher. Cette installation n'active pas à elle seule un firewall pour GET /blog/42.

🧠 Comment le mémoriser : « Livré n'est pas activé. » Image mentale : un carton encore fermé près du comptoir. Question-réflexe : parle-t-on d'installation ou d'exécution ?

⚠️ À ne pas confondre : dépendance de package et ordre des opérations HTTP.

Le form de commentaire n'a pas besoin de connecter son visiteur. Pourtant, installer son support CSRF apporte aussi le modèle de sécurité. Ce n'est pas un firewall implicite : c'est une dependency de code, visible dans les composer.json de la branche 8.0 :

Package require (hors PHP et contrats)
password-hasher rien
security-core password-hasher
security-csrf security-core
security-http security-core, http-foundation, http-kernel, property-access
SecurityBundle les quatre, plus le framework

require symfony/password-hasher n'installe donc que lui ; require symfony/security-csrf tire aussi security-core et password-hasher, pour une raison modeste : security-csrf lève les exceptions de security-core.

À l'examen, distinguer donc « le package est installé » de « l'application active un mécanisme ». La présence de password-hasher par dependency ne fait pas hacher un password lors de chaque consultation de l'article.

Pourquoi la séparation compte

À retenir en priorité
  1. Le hash est utilisable séparément.
  2. L'authentication ajoute un autre traitement.

La command de préparation des comptes n'a pas de Request à authentifier. PasswordHasherFactory choisit un hasher à partir de sa configuration ; avec auto et les options par défaut de Symfony 8.0, le hasher natif produit un hash bcrypt $2y$13$…. Vérifier ensuite le password correct donne true, un autre donne false. Cette opération n'exige ni firewall ni class de security-core chargée. Le préfixe et le coût décrivent ici cette configuration, pas un engagement sur toutes les versions futures ou toutes les options.

De son côté, le form de commentaire peut utiliser security-csrf sans firewall. Dans le mécanisme avec stockage de CsrfTokenManager, un identifiant de token désigne la valeur attendue ; le manager contrôle la valeur soumise contre celle du stockage. Un token absent ou incorrect échoue, même si le visiteur est connecté. Le component Form sait intégrer cette protection ; installer le package seul ne protège pas automatiquement tout form HTML.

Aucun de ces packages ne dépend de Doctrine ni d'une base de données. Le stockage des comptes est un autre choix. Pour décider qui peut modifier l'article après l'authentication, passons maintenant au modèle de security-core.

Ce qui vit dans `security-core`

À retenir en priorité
  1. Les voters portent une décision d'accès.
  2. La console peut utiliser ce modèle sans Request.

🌍 In Real Life

La situation : avant de modifier la fiche du plat 42, un responsable consulte l'identité de l'employé et les avis des personnes compétentes.

L’équivalent dans Symfony : identité → UserInterface ; dossier de sécurité courant → token ; avis → voters ; règle de décision → AccessDecisionManager.

Retour à la réalité technique : ces objets modélisent une décision d'accès. Le contrôle doit être appelé avec le contexte approprié ; le même modèle peut servir à la commande d'administration du blog, sans requête HTTP.

🧠 Comment le mémoriser : « Un dossier, des avis, une décision. » Image mentale : le dossier 42 sur une table de réunion. Question-réflexe : qui fournit le contexte et qui combine les votes ?

⚠️ À ne pas confondre : token de sécurité et token CSRF du formulaire.

Pour demander « cette identité peut-elle modifier l'article 42 ? », les responsabilités se répartissent ainsi :

  • UserInterface décrit le contrat de l'identité, pas son stockage en base ;
  • le token de sécurité (TokenInterface) porte le contexte de sécurité ; ce n'est pas le token CSRF soumis par un form ;
  • les voters examinent le droit demandé ; AccessDecisionManager combine leurs votes selon une strategy ;
  • la hiérarchie des roles exprime les roles hérités.

Il ne dépend pas de HTTP : http-foundation n'y figure qu'en require-dev. Quelques classes optionnelles s'en servent quand il est présent, comme UsageTrackingTokenStorage pour la session. Une décision d'accès se prend donc aussi en console ou dans un worker, à condition que l'application fournisse le contexte de sécurité nécessaire. Le token du navigateur n'est pas transporté automatiquement avec un message Messenger.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Ne pas confondre modèle et intégration HTTP.
  2. Le firewall est lié à la Request.
  • Voir l’explication : Le hash n'est pas dans security-core

    Le hash n'est pas dans security-core : préparer le password du nouvel auteur relève de password-hasher — dont security-core dépend.

  • Voir l’explication : La protection CSRF n'est pas liée à l'authentication

    La protection CSRF n'est pas liée à l'authentication : le commentaire public peut la demander sans firewall. Mais security-csrf n'est pas un package isolé : il installe security-core.

  • Voir l’explication : Seul password-hasher s'installe vraiment seul

    Seul password-hasher s'installe vraiment seul parmi ces trois packages : ne pas confondre l'autonomie de la command de hash avec celle du package CSRF.

  • Voir l’explication : security-core ne dépend pas de HTTP.

    security-core ne dépend pas de HTTP. Réutiliser une décision d'accès hors du navigateur n'impose donc pas un firewall ; firewalls et authenticators appartiennent à security-http, pas au modèle.

Fiche express

À mémoriser

À retenir en priorité
  1. Le bundle assemble les components.
  2. La key security configure cette intégration.

Avant de passer à l'authentication, vérifier qu'on sait distinguer les trois besoins rencontrés autour de l'article 42 : préparer le compte, contrôler une soumission, décider d'un droit.

Si tu dois retenir seulement 5 choses :

  • password-hasher : le hash, sans aucune dependency de sécurité.
  • security-core : user, tokens, voters, roles — sans HTTP ; dépend de password-hasher.
  • security-csrf : tokens CSRF sans firewall ; dépend de security-core.
  • security-http : firewalls, authenticators, la Request.
  • SecurityBundle : les quatre + la configuration security:.

Moyen mnémotechnique : « Hacher seul, protéger sans compte, contrôler avec le core ».

password-hasher ← security-core ← security-csrf
                  security-core ← security-http ← SecurityBundle (+ csrf + hasher)
