Objectif

Comprendre par quoi le container remplit un argument, pourquoi deux implémentations d'une même interface le bloquent, les trois façons de trancher, et ce que l'autowiring ne peut pas deviner.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le type guide la résolution.
  2. Le nom seul n'identifie pas normalement un service.

L'autowiring remplit un argument par son type : il cherche un service dont l'identifier est ce type. Une interface n'est le nom d'aucun service : il faut un alias, créé seul tant qu'il n'existe qu'une implémentation. Au-delà, on départage par un alias, un alias nommé ou #[Target]. Un scalaire, lui, ne se devine jamais.

Le schéma

À retenir en priorité
  1. L'inférence nécessite un seul candidat.
  2. Configurer l'alias pour décider.

Le fil rouge : deux transformers

À retenir en priorité
  1. Le type peut garder plusieurs usages.
  2. Le nom ciblé départage les implémentations.
interface TransformerInterface { public function transform(string $value): string; }
class Rot13Transformer implements TransformerInterface { /* … */ }
class UppercaseTransformer implements TransformerInterface { /* … */ }

L'arrivée d'UppercaseTransformer casse des services qui n'ont rien changé.

La règle, en une phrase : par le type

○ À comprendre

À retenir en priorité
  1. Le type reste déterminant.
  2. Les aliases nommés ajoutent une sélection particulière.

C'est quoi ?

L'autowiring est la résolution automatique des arguments d'un service à partir de leur type PHP et des indications de configuration. Le type demandé doit correspondre à un service ou à un alias utilisable. Ce n'est pas une recherche par ressemblance entre le nom de variable et les classes du projet.

À quoi ça sert ?

Le constructeur exprime les dépendances sans répéter chaque référence dans YAML. Le container peut signaler une dépendance impossible au lieu de laisser le code métier chercher un objet au hasard à l'exécution.

Où dans Symfony ?

Les classes découvertes ont habituellement leur nom complet comme identifiant, ce qui facilite la résolution. Un service enregistré seulement sous un identifiant métier peut nécessiter un alias de type. Un alias nommé ou #[Target] ajoute un choix spécifique ; cela ne change pas la règle de base du type.

Comment, étape par étape ?

  1. Lire le type de l'argument.
  2. Appliquer les indications explicites et alias nommés éventuels.
  3. Résoudre le type vers un service concret.
  4. Vérifier que l'objet injecté satisfait effectivement le type PHP.

Exemple concret YAML

App\Report demande App\Formatter $formatter au constructeur.

services:
    app.formatter:
        class: App\Formatter
    App\Formatter: '@app.formatter'
    App\Report:
        autowire: true

L'alias relie le type PHP à l'identifiant métier. Contre-exemple : supprimer l'alias puis renommer $formatter en $appFormatter en espérant réparer la résolution. Correction : rétablir le lien de type ou donner l'argument explicitement. Les types union et intersection n'autorisent pas un choix arbitraire : leur résolution doit aboutir à un service cohérent avec le type combiné, notamment via un alias complet ou des alias convergents.

Passage canonique conservé

La règle, en une phrase : par le type

  • Le container « looks for a service whose id exactly matches the type-hint ». Renommer l'argument ne change rien.
  • Un service d'identifier app.rot13.transformer redevient autowirable par un alias : Psr\Log\LoggerInterface est ainsi un alias vers logger.
  • Un type union ou intersection exige un alias pour le type complet, ou que chaque type soit un alias vers le même service (AutowirePass::getCombinedAlias()).

Pourquoi une interface a besoin d'un alias

○ À comprendre

À retenir en priorité
  1. L'interface décrit un contrat.
  2. L'alias relie ce contrat à un service.

C'est quoi ?

Une interface décrit un contrat ; elle ne peut pas être instanciée. L'alias d'interface indique quelle définition concrète satisfait ce contrat dans l'application. Le choix appartient à l'assemblage, pas au consommateur.

À quoi ça sert ?

Le même code peut utiliser un transport réel, une autre implémentation ou un substitut de test. L'alias explicite documente le choix par défaut et évite qu'un nouveau service rende l'assemblage ambigu.

Où dans Symfony ?

Lors de la découverte par ressource, Symfony peut créer automatiquement l'alias si une seule implémentation est découverte. Avec plusieurs candidats et sans choix existant, le container ne doit pas décider arbitrairement. #[AsAlias] est une autre manière de déclarer ce choix dans le parcours de découverte qui lit cet attribut.

Comment, étape par étape ?

  1. Définir l'interface que le consommateur demande.
  2. Enregistrer ses implémentations.
  3. Choisir explicitement celle qui correspond à l'usage par défaut.
  4. Ajouter des choix nommés seulement si différents consommateurs ont besoin de variantes.

Exemple concret YAML

services:
    App\Rot13Transformer: ~
    App\UppercaseTransformer: ~
    App\TransformerInterface: '@App\Rot13Transformer'
    App\MessageBuilder:
        autowire: true

Si MessageBuilder demande TransformerInterface, il reçoit Rot13Transformer. La deuxième implémentation reste disponible sans modifier ce choix. Contre-exemple : retirer l'alias en affirmant que Symfony prendra « la première classe ». Correction : conserver un choix explicite. L'alias automatique avec un candidat unique est une commodité de découverte, pas une règle universelle applicable à toute interface PHP présente dans le code ou dans vendor/.

Passage canonique conservé

Pourquoi une interface a besoin d'un alias

Une seule implémentation découverte : l'alias est automatique. Deux : la compilation échoue, « …references interface "…\TransformerInterface" but no such service exists. You should maybe alias this interface to one of these existing services ».

#[AsAlias] sur une implémentation en fait l'alias de son interface — lu à la découverte (resource) : sur un service déclaré un par un, sans effet.

Trois façons de départager

○ À comprendre

À retenir en priorité
  1. Le fallback peut masquer une faute de nom.
  2. Target rend le choix explicite.

C'est quoi ?

Plusieurs services peuvent satisfaire la même interface. L'alias par défaut choisit le cas général ; un alias nommé choisit selon le couple type et nom d'argument ; #[Target] exprime explicitement le nom de la cible d'autowiring sans imposer ce nom à la variable PHP.

À quoi ça sert ?

Un consommateur peut demander une transformation particulière sans connaître la classe concrète. Le choix explicite par attribut permet aussi de détecter une cible mal orthographiée au lieu de retomber involontairement sur le défaut.

Où dans Symfony ?

L'identifiant d'un alias nommé contient le type, une espace et le nom de l'argument avec $. debug:autowiring permet de voir ces choix. Un arguments explicite reste possible pour une définition particulière.

Comment, étape par étape ?

  1. Déclarer le choix général.
  2. Déclarer le choix nommé particulier.
  3. Utiliser le nom d'argument correspondant ou #[Target].
  4. Vérifier quel choix reste si le nom d'argument ne correspond à aucun alias nommé.

Exemple concret YAML

Les classes concrètes implémentent App\TransformerInterface.

services:
    App\Rot13Transformer: ~
    App\UppercaseTransformer: ~
    App\TransformerInterface: '@App\Rot13Transformer'
    App\TransformerInterface $shoutyTransformer: '@App\UppercaseTransformer'

Un argument autowiré TransformerInterface $transformer reçoit le défaut ; $shoutyTransformer reçoit la transformation en majuscules. Avec #[Target('shoutyTransformer')], la variable peut garder le nom $transformer. Contre-exemple : écrire $shoutyTransfomer sans attribut et supposer que la faute provoquera nécessairement une erreur : l'alias par défaut peut être utilisé. Correction : employer le nom exact ou un Target explicite, dont une cible inconnue est signalée. Le choix doit être vérifié par son effet, pas seulement par l'absence d'erreur de compilation.

Passage canonique conservé

Trois façons de départager

services:
    App\Util\TransformerInterface: '@App\Util\Rot13Transformer'                          # 1. alias par défaut
    App\Util\TransformerInterface $shoutyTransformer: '@App\Util\UppercaseTransformer'   # 2. alias nommé

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __construct(
    #[Target('shoutyTransformer')] private TransformerInterface $transformer,   // 3. #[Target]
) {}
Argument Reçoit
TransformerInterface $transformer rot13, l'alias par défaut
TransformerInterface $shoutyTransformer upper, l'alias nommé
$shoutyTransfomer, faute de frappe rot13, sans erreur
#[Target('shoutyTransfomer')], même faute erreur : « …but no such target exists. Did you mean… »
#[Target('shouty.transformer')] upper : le nom est normalisé en camelCase

registerAliasForArgument() crée l'alias nommé depuis une passe. debug:autowiring Transformer liste les alias, nommés compris.

Ce que `#[Target]` attend

○ À comprendre

À retenir en priorité
  1. Target sélectionne un alias nommé.
  2. Ne pas le traiter comme un identifiant arbitraire.

C'est quoi ?

#[Target] désigne un choix nommé d'autowiring pour le type de l'argument. Sa valeur usuelle est le nom associé à l'alias nommé, pas une demande générale de récupération de n'importe quel identifiant de service.

À quoi ça sert ?

La variable garde un nom fonctionnel tandis que l'attribut indique la variante voulue. Une faute de cible devient une erreur explicite. Le nom est normalisé en camelCase : la ponctuation admise peut conduire au même nom normalisé, mais ne justifie pas des noms ambigus.

Où dans Symfony ?

L'attribut vient de DependencyInjection. La documentation prescrit le nom de cible. Le code de AutowirePass 8.0 possède une nuance : un identifiant de service peut aussi être accepté s'il est déjà la cible d'un alias nommé du même type. Cela ne transforme pas Target en équivalent général de Autowire(service: ...).

Comment, étape par étape ?

  1. Déclarer un alias nommé pour l'interface.
  2. Donner son nom à Target sur l'argument typé.
  3. Laisser l'autowiring résoudre ce choix.
  4. Pour viser directement un identifiant sans cette convention, utiliser #[Autowire(service: ...)].

Exemple concret PHP

Cet extrait suppose l'alias App\TransformerInterface $shoutyTransformer configuré vers une implémentation et le service consommateur autowiré.

<?php
namespace App;
use Symfony\Component\DependencyInjection\Attribute\Target;
final class MessageBuilder
{
    public function __construct(
        #[Target('shoutyTransformer')]
        private TransformerInterface $transformer,
    ) {}
}

La variable $transformer reçoit le choix nommé. Contre-exemple : remplacer la valeur par un identifiant arbitraire existant, sans alias nommé correspondant, en supposant qu'existence implique résolution. Correction : utiliser le nom de cible déclaré, ou Autowire(service: ...) pour un identifiant explicite. Cette formulation préserve la nuance d'implémentation 8.0 sans en faire la convention recommandée.

Passage canonique conservé

Ce que #[Target] attend

Le nom de l'alias nommé. La documentation dit qu'il « does not accept service ids » ; en 8.0, un identifier passe pourtant s'il est déjà la cible d'un alias nommé du même type.

Câbler ce qui n'est pas un service

○ À comprendre

À retenir en priorité
  1. Un scalaire n'est pas déduit du type.
  2. Configurer sa valeur volontairement.

C'est quoi ?

Un argument peut être une valeur plutôt qu'un service : chaîne de chemin, booléen d'activation ou entier de limite. Le type seul ne permet pas de choisir sa valeur. Une closure, fonction stockée dans une variable, est un autre contrat : elle peut exposer une opération ou différer une récupération, mais ces deux usages ne sont pas identiques.

À quoi ça sert ?

Les valeurs explicites évitent les choix implicites fragiles. Les attributs spécialisés de callable permettent d'injecter une opération précise au lieu d'un objet entier, à condition de comprendre quand l'objet sous-jacent est construit.

Où dans Symfony ?

arguments, bind et #[Autowire] configurent les scalaires. AutowireServiceClosure fournit une closure de récupération de service. AutowireCallable adapte une méthode en callable ; sa création n'est pas paresseuse par défaut : lazy vaut false en Symfony 8.0. L'option lazy: true est nécessaire pour différer cette instanciation au premier appel dans ce mécanisme.

Comment, étape par étape ?

  1. Identifier le type et le sens de chaque valeur.
  2. Choisir paramètre, environnement converti ou valeur explicite.
  3. Configurer l'argument précis.
  4. Pour un callable, distinguer sa signature et sa stratégie d'instanciation ; ne pas déduire « différé » du seul mot closure.

Exemple concret PHP

Dans un service autowiré de l'application :

<?php
namespace App;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
final class ArchiveOptions
{
    public function __construct(
        #[Autowire('%kernel.project_dir%/var/archive')]
        public readonly string $directory,
        #[Autowire(env: 'bool:ARCHIVE_ENABLED')]
        public readonly bool $enabled,
    ) {}
}

La variable ARCHIVE_ENABLED doit être définie ou disposer d'un secours. Le processeur bool fournit un booléen. Contre-exemple : retirer les attributs en pensant que string et bool désignent des services uniques. Correction : fournir la source des valeurs. Autre erreur : regrouper tous les attributs de callable sous « construit seulement à l'appel » ; vérifier notamment l'option lazy de AutowireCallable.

Passage canonique conservé

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[Autowire(service: 'logger')] LoggerInterface $logger,
#[Autowire('%kernel.project_dir%/data')]       string $dataDir,
#[Autowire(param: 'kernel.debug')]             bool $debug,
#[Autowire(env: 'bool:FEATURE_FLAG')]          bool $flag,
  • Un scalaire non configuré : « …is type-hinted "string", you should configure its value explicitly », pour un service conservé — un privé inutilisé est retiré sans erreur.
  • #[AutowireServiceClosure] fournit une closure de récupération du service. #[AutowireCallable] adapte une opération en callable ; son option lazy vaut false par défaut en 8.0. lazy: true diffère l'instanciation au premier appel. Le seul type Closure, notamment avec #[AutowireMethodOf], ne garantit pas une construction différée.
  • #[Required] : une method ou une property publique typée, remplie par l'autowiring.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Une union ne résout pas l'ambiguïté.
  2. Les types doivent aboutir au même choix.
Types, alias nommés, Target et limites de l’autowiring
  • L'autowiring passe par le type, pas par le nom — sauf alias nommé et #[Target].
  • Deux implémentations d'une interface suppriment l'alias automatique.
  • Une faute dans le nom d'argument retombe en silence sur l'alias par défaut ; la même faute dans #[Target] lève une exception.
  • #[Target] vise le nom de l'alias nommé ; un identifier ne passe que s'il est déjà la cible d'un alias nommé du même type.
  • Un scalaire ne s'autowire jamais.
  • Un type union ne s'autowire que si chacun de ses types est un alias vers le même service : deux services différents, et la compilation échoue.
  • #[AsAlias] est lu à la découverte des classes (resource) : sur un service déclaré un par un, il ne départage rien.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. AutowireServiceClosure diffère la récupération du service ; cette règle ne s'étend pas à AutowireCallable, dont lazy vaut false par défaut.
  2. L'injection seule ne construit pas le service.

Si tu dois retenir seulement 7 choses :

  • Autowiring = par le type ; le nom ne compte que pour un alias nommé.
  • Interface : alias automatique avec une seule implémentation.
  • Départager : alias par défaut, alias nommé, #[Target].
  • Faute dans le nom d'argument : défaut en silence ; dans #[Target] : erreur.
  • #[Target] : nom normalisé en camelCase.
  • Union : chaque type vers le même service.
  • Scalaire : bind, argument explicite ou #[Autowire].

Moyen mnémotechnique : « Type, puis Nom, puis rien ».
