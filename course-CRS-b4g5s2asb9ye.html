Ce qu'un tag fait : un marqueur, sans effet propre

À comprendre

À retenir en priorité
  1. Un tag inconnu peut rester inutilisé.
  2. Contrôler le nom et son lecteur.

C'est quoi ?

Un tag est une étiquette attachée à une définition de service. Il peut porter des attributs comme une priorité ou une clé. Il ne constitue pas un appel de méthode : un autre mécanisme doit lire l'étiquette et décider de son effet.

À quoi ça sert ?

Les tags permettent de rassembler des services sans énumérer leurs identifiants dans chaque consommateur. Un bundle peut ainsi découvrir des extensions apportées par l'application. Le nom du tag est un contrat entre celui qui le pose et celui qui le lit.

Où dans Symfony ?

Une passe de compilation, un iterator tagué ou un locator tagué peut consommer ces métadonnées. L'autoconfiguration peut poser le tag, mais elle ne remplace pas son lecteur. Un nom préfixé comme app.exporter évite des collisions avec les tags d'autres intégrations.

Comment, étape par étape ?

  1. Déclarer le service.
  2. Poser le tag attendu.
  3. Configurer un consommateur de ce tag.
  4. Ce consommateur transforme les définitions marquées en références injectables ; le code applicatif décide ensuite quand appeler les objets.

Exemple concret YAML

ExportRegistry possède un constructeur __construct(iterable $exporters) ; CsvExporter est une classe existante.

services:
    App\CsvExporter:
        tags: ['app.exporter']
    App\ExportRegistry:
        arguments:
            $exporters: !tagged_iterator app.exporter

La collection injectée contient l'exporter lorsque le registry est utilisé. Contre-exemple : écrire app.exproter sur le service et app.exporter sur l'iterator. Le tag mal orthographié n'ajoute pas le service à la collection ; il n'est pas forcément une erreur bloquante. Correction : partager exactement le même nom et inspecter les services portant ce tag. Poser une étiquette sans lecteur ne lance aucun export.

Passage canonique conservé

Ce qu'un tag fait : un marqueur, sans effet propre

services:
    App\Handler\SmsHandler:
        tags: ['app.handler']
    App\Handler\EmailHandler:
        tags:
            - { name: 'app.handler', priority: 10 }

Un tag que rien ne lit ne lève aucune erreur. En debug, UnusedTagsPass le signale dans le journal de compilation : « Tag "app.handlr" was defined on service(s) …, but was never used. Did you mean "app.handler"? ».

Recevoir les services tagués : un iterable lazy

À comprendre

À retenir en priorité
  1. Le locator sélectionne un service.
  2. L'iterator parcourt le groupe.

C'est quoi ?

Un iterable tagué permet de parcourir les services portant une étiquette. Il est lazy, c'est-à-dire à chargement différé : recevoir la collection n'impose pas de construire immédiatement tous ses éléments. La construction nécessaire intervient lorsqu'on parcourt les éléments concernés.

À quoi ça sert ?

Cette forme convient à une chaîne de traitements ou à un ensemble de vérificateurs que le consommateur doit parcourir. Pour choisir directement un seul service à partir d'une clé, un locator est plus adapté : parcourir toute une collection pour atteindre une clé peut construire inutilement les éléments précédents.

Où dans Symfony ?

#[AutowireIterator('app.handler')] et !tagged_iterator app.handler demandent cette collection. exclude en retire certains services, sans supprimer leurs définitions du container ni les exclure de tous les autres consommateurs.

Comment, étape par étape ?

  1. Marquer les définitions des handlers, objets capables de traiter le même genre de demande.
  2. Injecter l'iterable dans le consommateur.
  3. Parcourir la collection au moment du besoin.
  4. Appeler explicitement les handlers ; l'injection seule n'exécute pas leur méthode métier.

Exemple concret PHP

Dans une application où les classes sont enregistrées et autowirées, les services tagués doivent tous exposer notify(string): void.

<?php
namespace App;
use Symfony\Component\DependencyInjection\Attribute\AutowireIterator;
final class Notifications
{
    public function __construct(
        #[AutowireIterator('app.handler')]
        private iterable $handlers,
    ) {}
    public function send(string $message): void
    {
        foreach ($this->handlers as $handler) {
            $handler->notify($message);
        }
    }
}

send() appelle chaque handler atteint dans l'ordre de la collection. Contre-exemple : convertir immédiatement l'iterable en tableau dans le constructeur puis annoncer que les objets resteront différés jusqu'à send(). Correction : conserver l'iterable et le parcourir au moment voulu. Les exceptions des handlers ne sont pas absorbées ici : une stratégie de poursuite après échec doit être explicite si elle est souhaitée.

Ordonner et nommer : `priority` et `index`

À comprendre

À retenir en priorité
  1. L'index déclaré n'active pas seul l'indexation.
  2. La configuration de l'iterator décide des keys.

C'est quoi ?

La priorité détermine la position d'un service dans une collection taguée : la plus haute vient d'abord. L'index détermine la clé sous laquelle le service est présenté. Une clé n'est pas un ordre, et une priorité n'est pas un identifiant.

À quoi ça sert ?

On peut placer une règle spécialisée avant une règle générale tout en donnant aux services des noms stables. Il faut configurer le lecteur pour qu'il utilise l'attribut d'index ; écrire une métadonnée ne garantit pas qu'un iterator la prendra comme clé.

Où dans Symfony ?

En YAML, index_by: key demande de lire l'attribut key du tag. L'équivalent attribut utilise indexAttribute. #[AsTaggedItem] permet aussi de définir index et priorité sur la classe. Les méthodes de priorité ou d'index par défaut sont des solutions de repli, pas une raison de mélanger plusieurs conventions sans vérifier leur priorité respective.

Comment, étape par étape ?

  1. Poser les priorités sur les tags.
  2. Choisir un attribut de clé commun.
  3. Configurer la collection avec cet attribut.
  4. Lire séparément l'ordre obtenu et les clés obtenues.

Exemple concret YAML

services:
    App\EmailHandler:
        tags: [{ name: app.handler, key: email, priority: 10 }]
    App\SmsHandler:
        tags: [{ name: app.handler, key: sms, priority: 0 }]
    App\HandlerRegistry:
        arguments:
            $handlers: !tagged_iterator { tag: app.handler, index_by: key }

L'iterator présente email, puis sms. Contre-exemple : retirer index_by et continuer à traiter la collection comme un tableau indexé par ces noms. Correction : demander explicitement l'indexation, ou utiliser un locator si le besoin est une sélection par clé. Choisir des clés uniques évite qu'un consommateur qui matérialise la collection en tableau écrase une entrée homonyme.

Passage canonique conservé

Ordonner et nommer : priority et index

#[AsTaggedItem(index: 'sms', priority: 10)] les pose depuis la class.

Injection Keys obtenues
#[AutowireIterator('app.handler')] 0, 1, 2… : l'index est ignoré
#[AutowireIterator('app.handler', indexAttribute: 'key')] sms, puis les noms de class
#[AutowireLocator('app.handler')] sms, puis les noms de class

  • default_index_method nomme une autre method.

Poser les tags sans configuration

À comprendre

À retenir en priorité
  1. L'interface peut porter le tag commun.
  2. L'autoconfiguration doit être active.

C'est quoi ?

L'autoconfiguration peut déduire une étiquette du contrat implémenté par une classe. Avec #[AutoconfigureTag] sur une interface, les services autoconfigurés qui l'implémentent reçoivent le tag sans répétition YAML sur chaque classe.

À quoi ça sert ?

Une nouvelle implémentation rejoint automatiquement le mécanisme prévu. L'interface décrit les méthodes attendues ; le tag relie les implémentations au lecteur de la collection. Ces deux contrats se complètent : PHP vérifie l'interface, le container organise les références.

Où dans Symfony ?

L'attribut vient de DependencyInjection. Les classes doivent être enregistrées et autoconfigurées. Le framework utilise également des règles enregistrées avec registerForAutoconfiguration() pour ses propres interfaces. Aucun de ces mécanismes ne découvre une classe située hors des ressources configurées.

Comment, étape par étape ?

  1. Définir une interface commune.
  2. Lui associer le nom de tag attendu.
  3. Enregistrer ses implémentations avec autoconfigure: true.
  4. Consommer ce même tag avec un iterator, un locator ou une passe.

Exemple concret PHP

<?php
namespace App;
use Symfony\Component\DependencyInjection\Attribute\AutoconfigureTag;
#[AutoconfigureTag('app.formatter')]
interface FormatterInterface
{
    public function format(string $value): string;
}
final class TrimFormatter implements FormatterInterface
{
    public function format(string $value): string { return trim($value); }
}

Avec découverte et autoconfiguration actives, la définition de TrimFormatter reçoit app.formatter. Son constructeur ou sa méthode n'est pas exécuté par la seule présence du tag. Contre-exemple : désactiver l'autoconfiguration puis attendre que l'interface suffise à remplir la collection. Correction : réactiver la règle pour ce service ou poser explicitement le tag. Sans lecteur de app.formatter, aucun formatage automatique n'a lieu.

Passage canonique conservé

Poser les tags sans configuration

#[AutoconfigureTag] sur une interface (répétable) tague toutes ses implémentations, avec autoconfigure: true. Le framework fait de même pour ses interfaces par registerForAutoconfiguration(), appelé dans FrameworkExtension.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le tri des services tagués est décroissant.
  2. Cet ordre diffère de l'empilement des decorators.
  • Voir l’explication : Un tag n'a d'effet que si quelque chose le lit.

    Un tag n'a d'effet que si quelque chose le lit. Taguer un service qu'aucune passe ne collecte ne produit rien — aucune erreur, au mieux une ligne de journal en debug.

  • Voir l’explication : priority haute = appelé en premier

    priority haute = appelé en premier, comme pour les event listeners.

  • Voir l’explication : L'iterator est lazy

    L'iterator est lazy : les services ne sont pas construits tant qu'on n'itère pas.

  • Voir l’explication : Un iterator sans index_by a des keys entières

    Un iterator sans index_by a des keys entières, même si les services déclarent un index.

  • Voir l’explication : Une faute de frappe dans un nom de tag ne lève aucune erreur.

    Une faute de frappe dans un nom de tag ne lève aucune erreur. Le service n'est simplement jamais collecté ; seul le journal de compilation, en debug, le signale.

Fiche express

À mémoriser

À retenir en priorité
  1. Le filtre concerne la collection injectée.
  2. Le service reste disponible ailleurs.

Si tu dois retenir seulement 7 choses :

  • Un tag est un marqueur : sans lecteur, aucun effet, aucune erreur.
  • #[AutowireIterator] : tous, lazy ; #[AutowireLocator] : un, par key.
  • priority haute = premier.
  • index ignoré sans indexAttribute / index_by.
  • #[AsTaggedItem] sur la class, #[AutoconfigureTag] sur l'interface.
  • exclude retire de l'iterator, pas du container.
  • Sous index_by: key : getDefaultKeyName(), getDefaultKeyPriority().

Moyen mnémotechnique : « Marquer, Lire, Trier » — sans le L, rien ne se passe.
