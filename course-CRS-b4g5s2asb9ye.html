Objectif

Marquer des services pour qu'un autre les retrouve sans les connaître par leur nom, les recevoir sous forme d'itérable lazy, les ordonner par priority, les indexer par une key, et poser les tags automatiquement depuis une interface.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Un tag est un marqueur.
  2. Son lecteur lui donne un effet.

Un NotificationChain qui nomme chaque canal doit changer à chaque nouveau canal. Un tag marque les services pour qu'un consommateur les reçoive tous sans les connaître. Le tag ne fait rien seul : il faut quelque chose qui le lise. On les reçoit en itérable lazy, ordonnés par priority, indexés seulement si on le demande.

Le schéma

À retenir en priorité
  1. L'injection fournit un iterable lazy.
  2. L'itération déclenche la construction nécessaire.

Le fil rouge : des handlers de notification

À retenir en priorité
  1. Le tag regroupe les handlers.
  2. Le consommateur dépend du groupe plutôt que de chaque class.
#[AutoconfigureTag('app.handler')]
interface HandlerInterface { public function notify(string $message): void; }

class HandlerChain
{
    public function __construct(
        #[AutowireIterator('app.handler')] private iterable $handlers,
    ) {
    }
}

Ce qu'un tag fait : un marqueur, sans effet propre

À retenir en priorité
  1. Un tag inconnu peut rester inutilisé.
  2. Contrôler le nom et son lecteur.
services:
    App\Handler\SmsHandler:
        tags: ['app.handler']
    App\Handler\EmailHandler:
        tags:
            - { name: 'app.handler', priority: 10 }

Un tag que rien ne lit ne lève aucune erreur. En debug, UnusedTagsPass le signale dans le journal de compilation : « Tag "app.handlr" was defined on service(s) …, but was never used. Did you mean "app.handler"? ».

Recevoir les services tagués : un iterable lazy

À retenir en priorité
  1. Le locator sélectionne un service.
  2. L'iterator parcourt le groupe.
Besoin Injection
appeler tous les services tagués, dans l'ordre #[AutowireIterator] / !tagged_iterator
en appeler un, choisi par sa key #[AutowireLocator] / !tagged_locator
  • L'iterable est un generator réembobinable : rien n'est construit avant l'itération.
  • exclude: [FaxHandler::class] retire des services de l'iterator.

Ordonner et nommer : `priority` et `index`

À retenir en priorité
  1. L'index déclaré n'active pas seul l'indexation.
  2. La configuration de l'iterator décide des keys.

#[AsTaggedItem(index: 'sms', priority: 10)] les pose depuis la class.

Injection Keys obtenues
#[AutowireIterator('app.handler')] 0, 1, 2… : l'index est ignoré
#[AutowireIterator('app.handler', indexAttribute: 'key')] sms, puis les noms de class
#[AutowireLocator('app.handler')] sms, puis les noms de class
  • Défauts fournis par la class : getDefaultPriority() ; sous index_by: key, getDefaultKeyName() et getDefaultKeyPriority() — le getDefaultPriority() est alors ignoré.
  • default_index_method nomme une autre method.

Poser les tags sans configuration

À retenir en priorité
  1. L'interface peut porter le tag commun.
  2. L'autoconfiguration doit être active.

#[AutoconfigureTag] sur une interface (répétable) tague toutes ses implémentations, avec autoconfigure: true. Le framework fait de même pour ses interfaces par registerForAutoconfiguration(), appelé dans FrameworkExtension.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le tri des services tagués est décroissant.
  2. Cet ordre diffère de l'empilement des decorators.

Un tag n'a d'effet que si quelque chose le lit. Taguer un service qu'aucune passe ne collecte ne produit rien — aucune erreur, au mieux une ligne de journal en debug.

priority haute = appelé en premier, comme pour les event listeners.

L'iterator est lazy : les services ne sont pas construits tant qu'on n'itère pas.

Un iterator sans index_by a des keys entières, même si les services déclarent un index.

Une faute de frappe dans un nom de tag ne lève aucune erreur. Le service n'est simplement jamais collecté ; seul le journal de compilation, en debug, le signale.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le filtre concerne la collection injectée.
  2. Le service reste disponible ailleurs.

Si tu dois retenir seulement 7 choses :

  • Un tag est un marqueur : sans lecteur, aucun effet, aucune erreur.
  • #[AutowireIterator] : tous, lazy ; #[AutowireLocator] : un, par key.
  • priority haute = premier.
  • index ignoré sans indexAttribute / index_by.
  • #[AsTaggedItem] sur la class, #[AutoconfigureTag] sur l'interface.
  • exclude retire de l'iterator, pas du container.
  • Sous index_by: key : getDefaultKeyName(), getDefaultKeyPriority().

Moyen mnémotechnique : « Marquer, Lire, Trier » — sans le L, rien ne se passe.
