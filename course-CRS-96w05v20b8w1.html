Objectif

Écrire une règle de validation arbitraire sans créer de class de constraint, et connaître la signature attendue — elle change selon que la method est d'instance ou statique.

L'essentiel

À comprendre

À retenir en priorité
  1. Le retour du callback est ignoré.
  2. Le contexte porte les violations.

Callback fait appeler ta method par le validator : elle seule décide des violations. Deux choses tombent à l'examen : la signature change selon que la method est d'instance ou statique, et la valeur retournée est ignorée — seule une violation ajoutée compte.

Le schéma

À retenir en priorité
  1. Le callback exprime la règle.
  2. addViolation() rend l'échec observable.

Bleu = appel ou données ; ambre = choix de signature ; vert = résultat. Les flèches représentent le traitement d'un callback valide, pas de l'héritage. Une méthode inexistante ou un callable invalide interrompt ce chemin par une exception de configuration ; return false ne crée aucune violation.

L'exemple : un `Author`

Exemple concret

À retenir en priorité
  1. Une règle de class voit l'Author entier.
  2. atPath() rattache l'erreur au field.

Pour le profil d'auteur du blog, la règle ci-dessous montre comment ajouter une erreur ciblée à partir d'une liste locale. C'est une politique illustrative, pas une méthode fiable pour établir l'identité réelle d'un lecteur. La règle ne crée pas de compte et n'écrit pas de Response : elle enrichit le résultat de validation que l'appelant traitera ensuite.

use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;

class Author
{
    public string $firstName = '';
    private array $fakeNames = ['Toto', 'Test', 'Foo'];

    #[Assert\Callback]
    private function validate(ExecutionContextInterface $context, mixed $payload): void
    {
        if (in_array($this->firstName, $this->fakeNames, true)) {
            $context->buildViolation('Ce prénom semble inventé.')
                ->atPath('firstName')
                ->addViolation();
        }
    }
}

Avec le mapping d'attributs activé, un Author dont firstName vaut Toto produit une violation au chemin firstName. Avec Ada, ce callback n'en produit aucune ; les autres contraintes éventuelles restent indépendantes.

Le principe

À retenir en priorité
  1. Callback convient à une règle locale.
  2. Une constraint dédiée favorise la réutilisation.

Si une combinaison propre à SignupData n'est pas exprimée simplement par une contrainte native, un callback peut examiner l'objet. Le placer sur une propriété change cependant son entrée : il reçoit cette valeur, pas automatiquement l'objet parent. Choisis la portée avant la signature.

Callback est la porte de sortie quand aucune constraint native n'exprime la règle, et qu'une class de constraint serait disproportionnée.

  • L'attribute se pose sur la method ; sur la class, il nomme la method : #[Assert\Callback(callback: 'validate')].
  • La method peut être privée : elle est appelée, et sa violation remonte.

Elle accepte aussi une property : le callback reçoit alors la valeur de la property, et sa violation porte le path de la property. Un nom de method seul y est cherché sur cette valeur — une string — d'où une ConstraintDefinitionException : « Method "nope" targeted by Callback constraint does not exist in class "string". ».

🌍 In Real Life

La situation : une checklist standard ne suffit pas pour comparer deux rubriques du dossier. On ajoute une consigne locale ; si on ne remet qu'une case au contrôleur, il ne reçoit pas pour autant tout le dossier.

L’équivalent dans Symfony : Callback délègue une règle personnalisée à du code. Sa cible de classe lui donne l'objet ; sa cible de propriété lui donne la valeur de cette propriété. Une méthode nommée est recherchée sur la valeur validée.

Retour à la réalité technique : les métadonnées et le groupe doivent sélectionner la règle. L'appel par réflexion d'une méthode privée nommée sur l'objet ne rend pas tout callable privé accessible par toute autre forme d'appel. Une cible incorrecte peut produire une erreur de configuration, pas une violation de donnée. Cette règle peut servir à SignupData après Form ou désérialisation JSON, sans créer le compte.

🧠 Comment le mémoriser : « Remettre une case ne remet pas le dossier. » Image mentale : contrôleur recevant soit un dossier, soit une seule case. Question-réflexe : quelle valeur la cible remet-elle à ce callback ?

⚠️ À ne pas confondre : portée de Callback, objet parent, callable valide, désérialisation et validation.

Les deux signatures

À retenir en priorité
  1. Une method statique n'a pas this.
  2. La valeur validée est donc son premier argument.

CallbackValidator décide des arguments selon la forme du callable. Il ne fait pas l'autowiring d'une action de contrôleur : le contexte et le payload ont des positions définies. Une méthode statique reçoit explicitement l'objet qui remplacerait $this, tandis que le payload vient de la contrainte et non du body HTTP.

Forme Signature
instance validate(ExecutionContextInterface $context, mixed $payload)
statique, closure validate(mixed $value, ExecutionContextInterface $context, mixed $payload)

Une method statique n'a pas $this : l'object validé lui est passé, en premier. CallbackValidator teste isStatic() et choisit l'appel. Une method statique écrite avec la signature d'instance lève une TypeError, pas une validation silencieusement fausse.

Le $payload est la donnée de l'option payload, transmise telle quelle : le validator ne s'en sert pas.

🌍 In Real Life

La situation : le contrôleur installé dans le dossier connaît déjà ce dossier. Le contrôleur externe doit recevoir d'abord la pièce à examiner, puis son carnet de remarques et la note jointe à la règle.

L’équivalent dans Symfony : pour la méthode d'instance désignée par son nom, CallbackValidator transmet contexte puis payload. Pour la méthode statique, la closure ou le callable en tableau, il transmet valeur, contexte, payload.

Retour à la réalité technique : c'est la forme d'appel qui détermine ce protocole, pas un autowiring par noms ou types. La valeur peut être scalaire, pas nécessairement un objet. Payload vient de l'option de contrainte, pas du corps HTTP. Une mauvaise signature typée peut provoquer TypeError ; cette erreur de programmation n'est pas un verdict faux.

🧠 Comment le mémoriser : « Dehors, livrer la pièce avant le carnet. » Image mentale : paquet valeur, carnet contexte, note payload dans cet ordre. Question-réflexe : est-ce une méthode nommée sur l'instance ou un callable recevant explicitement la valeur ?

⚠️ À ne pas confondre : signature Callback, ArgumentResolver HTTP, payload de contrainte et payload de requête.

Les formes du `callback`

À retenir en priorité
  1. Le nom seul vise la valeur courante.
  2. Un callable explicite permet une autre cible.

Une méthode nommée suffit lorsque la règle appartient à l'objet validé. Un callable externe permet de réutiliser un contrôle indépendant, mais une chaîne de nom de service n'est pas automatiquement résolue comme un contrôleur. Si la règle requiert des services, une contrainte et son validateur configuré peuvent offrir un contrat plus approprié.

Valeur de l'option Où la method est cherchée
un nom de method sur la valeur validée — l'object, sur une class
[Classe::class, 'méthode'] le callable statique désigné, hors de la class
une closure appelée avec ($value, $context, $payload)

Un nom de method absent lève une ConstraintDefinitionException.

🌍 In Real Life

La situation : « consulter la méthode locale » et « appeler ce spécialiste précis » sont deux adresses différentes. Un simple nom écrit sur une note ne demande pas à un standard de trouver n'importe quel service.

L’équivalent dans Symfony : le nom seul vise une méthode de la valeur validée ; un tableau callable ou une closure désigne explicitement le contrôle. CallbackValidator ne résout pas une chaîne de service comme un ControllerResolver.

Retour à la réalité technique : le tableau statique du cours est une forme de callable, pas l'obligation que toute règle soit dans une autre classe. Un tableau avec objet peut aussi être callable, sous réserve d'être appelable et de respecter la signature avec valeur. Si la règle dépend de services, préfère un validateur personnalisé correctement enregistré plutôt qu'une résolution de service supposée.

🧠 Comment le mémoriser : « Nom local ou adresse callable : pas d'annuaire magique. » Image mentale : étiquette locale à côté d'une adresse explicite. Question-réflexe : où cette forme cherche-t-elle réellement la méthode ?

⚠️ À ne pas confondre : méthode nommée, callable PHP, identifiant de service et contrôleur.

Ce que le callback doit faire

À retenir en priorité
  1. Sans atPath(), l'erreur conserve le path courant de l'objet : vide à la racine, préfixé lors d'une validation imbriquée.
  2. Le field doit être désigné volontairement.

Le booléen d'un getter avec IsTrue est interprété par son validateur ; le retour d'un Callback ne l'est pas. Pour signaler la fin de période incorrecte d'un article, ajoute donc une violation sur le chemin choisi. Sans cet enregistrement, ce callback reste silencieux, même si d'autres règles font déjà échouer le formulaire.

Ne pas ajouter de violation signifie que ce callback ne signale rien. Cela ne garantit pas la réussite des autres règles. Pour signaler un problème : $context->buildViolation('message'), puis ->atPath('firstName') si la règle vise un field, puis ->addViolation(). Sans atPath(), la violation garde le chemin courant : '' pour un objet validé à la racine, ou le préfixe de cet objet dans une validation imbriquée.

🌍 In Real Life

La situation : penser « non » ne laisse aucune remarque dans le dossier. Le contrôleur doit écrire et déposer sa fiche d'anomalie à l'emplacement concerné.

L’équivalent dans Symfony : CallbackValidator ignore le retour du callback. Le code ajoute la violation au contexte, directement ou via un builder terminé par addViolation ; atPath précise son emplacement relatif.

Retour à la réalité technique : return false ne joue pas le rôle du booléen contrôlé par IsTrue. Sans ajout, ce callback reste silencieux, sans effacer les violations des autres règles. Le chemin courant peut déjà être imbriqué ; le chemin de violation n'est pas un identifiant HTML et son affichage Form peut demander un mapping.

🧠 Comment le mémoriser : « Un non pensé n'est pas une remarque déposée. » Image mentale : fiche d'anomalie déposée sur la rubrique du dossier. Question-réflexe : ai-je effectivement enregistré une violation au bon chemin ?

⚠️ À ne pas confondre : retour booléen, builder préparé, violation ajoutée et affichage d'erreur.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'ordre des arguments fait partie du contrat.
  2. La valeur précède le contexte en statique.
  • Voir l’explication : La signature statique commence par la valeur, pas par le contexte

    La signature statique commence par la valeur, pas par le contexte ; la confondre lève une TypeError.

  • Voir l’explication : Le retour est ignoré.

    Le retour est ignoré. Une règle non respectée doit produire une violation, pas un return false.

  • Voir l’explication : Un nom de method seul est cherché sur la valeur validée

    Un nom de method seul est cherché sur la valeur validée — l'object quand la constraint est posée sur la class —, jamais ailleurs.

  • Voir l’explication : Posée sur la class, Callback voit tout l'object

    Posée sur la class, Callback voit tout l'object, ce qui la rend adaptée aux règles croisées — mais il faut alors atPath() pour attribuer l'erreur au bon field.

Fiche express

À mémoriser

À retenir en priorité
  1. Le payload est une donnée auxiliaire.
  2. La logique reste dans le callback.

Si tu dois retenir seulement 6 choses :

  • Callback appelle ta method ; elle seule décide des violations.
  • Instance : (context, payload) ; statique / closure : (value, context, payload) — sinon TypeError.
  • Nom seul : cherché sur la valeur validée ; array : callable statique externe.
  • Sur une property, le callback reçoit la valeur de la property.
  • Aucune violation ajoutée = aucun échec signalé par ce callback ; return false est ignoré.
  • atPath() pour rattacher l'erreur à un field.

Moyen mnémotechnique : « Statique, l'object d'abord ».
