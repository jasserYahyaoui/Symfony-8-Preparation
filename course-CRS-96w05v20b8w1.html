Objectifs d’apprentissage

  • Écrire la signature d'un callback d'instance et d'un callback statique
  • Énoncer que le retour est ignore et qu'une violation doit être ajoutée
  • Reconnaître un callable statique externe

Ces repères décrivent le rôle du bloc, pas une fréquence officielle à l’examen.

Précision, exception ou condition d’application d’une règle.

Objectif

Écrire une règle de validation arbitraire sans créer de class de constraint, et connaître la signature attendue — elle change selon que la method est d'instance ou statique.

L'essentiel

À comprendre

À retenir en priorité
  1. Le retour du callback est ignoré.
  2. Le contexte porte les violations.

Callback fait appeler ta method par le validator : elle seule décide des violations. Deux choses tombent à l'examen : la signature change selon que la method est d'instance ou statique, et la valeur retournée est ignorée — seule une violation ajoutée compte.

Le schéma

À retenir en priorité
  1. Le callback exprime la règle.
  2. addViolation() rend l'échec observable.

Bleu = appel ou données ; ambre = choix de signature ; vert = résultat. Les flèches représentent le traitement d'un callback valide, pas de l'héritage. Une méthode inexistante ou un callable invalide interrompt ce chemin par une exception de configuration ; return false ne crée aucune violation.

L'exemple : un `Author`

Exemple concret

À retenir en priorité
  1. Une règle de class voit l'Author entier.
  2. atPath() rattache l'erreur au field.
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;

class Author
{
    public string $firstName = '';
    private array $fakeNames = ['Toto', 'Test', 'Foo'];

    #[Assert\Callback]
    private function validate(ExecutionContextInterface $context, mixed $payload): void
    {
        if (in_array($this->firstName, $this->fakeNames, true)) {
            $context->buildViolation('Ce prénom semble inventé.')
                ->atPath('firstName')
                ->addViolation();
        }
    }
}

Avec le mapping d'attributs activé, un Author dont firstName vaut Toto produit une violation au chemin firstName. Avec Ada, ce callback n'en produit aucune ; les autres contraintes éventuelles restent indépendantes.

Le principe

À retenir en priorité
  1. Callback convient à une règle locale.
  2. Une constraint dédiée favorise la réutilisation.

Callback est la porte de sortie quand aucune constraint native n'exprime la règle, et qu'une class de constraint serait disproportionnée.

  • L'attribute se pose sur la method ; sur la class, il nomme la method : #[Assert\Callback(callback: 'validate')].
  • La method peut être privée : elle est appelée, et sa violation remonte.

Elle accepte aussi une property : le callback reçoit alors la valeur de la property, et sa violation porte le path de la property. Un nom de method seul y est cherché sur cette valeur — une string — d'où une ConstraintDefinitionException : « Method "nope" targeted by Callback constraint does not exist in class "string". ».

Les deux signatures

À comprendre

À retenir en priorité
  1. Une method statique n'a pas this.
  2. La valeur validée est donc son premier argument.

C'est quoi ?

Callback délègue une règle à une fonction ou une méthode. Pour une méthode d'instance de l'objet validé, cet objet est déjà disponible dans this : les arguments sont le contexte puis le payload. Pour une méthode statique ou une closure, la valeur validée est ajoutée en premier argument.

À quoi ça sert ?

Le callback exprime une règle particulière sans créer immédiatement une classe de contrainte dédiée. La signature correcte est essentielle : PHP ne réordonne pas les arguments parce qu'un type paraît correspondre à une autre position.

Où dans Symfony ?

ExecutionContextInterface permet de construire les violations. Le payload est une métadonnée de la contrainte, transmise au callback ; Validator ne l'interprète pas comme un résultat de validation. Un nom de méthode seul est recherché sur la valeur validée ; un callable statique peut être désigné explicitement par un tableau classe/méthode.

Comment, étape par étape ?

  1. Choisir instance, statique ou closure.
  2. Utiliser la signature correspondant à cette forme.
  3. Examiner la valeur sans la confondre avec le contexte.
  4. Enregistrer une violation si nécessaire ; retourner false ne suffit pas à en créer une.

Exemple concret PHP

Avec Validator chargé, une closure utilisée pour une valeur scalaire :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;
use Symfony\Component\Validator\Validation;

$rule = new Assert\Callback(callback: static function (mixed $value, ExecutionContextInterface $context, mixed $payload): void {
    if ('reserved' === $value) {
        $context->buildViolation('Cette valeur est réservée.')->addViolation();
    }
});
$violations = Validation::createValidator()->validate('reserved', $rule);
var_dump(count($violations));

On attend une violation ; pour une autre chaîne, aucune n'est ajoutée par cette règle. Contre-exemple : omettre value dans cette closure en recopiant la signature d'une méthode d'instance. Le contexte recevrait une valeur au mauvais emplacement et une TypeError peut survenir. Correction : conserver l'argument initial pour les formes statiques et closures. Une règle de format ou de présence complémentaire reste nécessaire si le contrat exige autre chose que l'exclusion de reserved.

Passage canonique conservé
Forme Signature
instance validate(ExecutionContextInterface $context, mixed $payload)
statique, closure validate(mixed $value, ExecutionContextInterface $context, mixed $payload)

Une method statique n'a pas $this : l'object validé lui est passé, en premier. CallbackValidator teste isStatic() et choisit l'appel. Une method statique écrite avec la signature d'instance lève une TypeError, pas une validation silencieusement fausse.

Le $payload est la donnée de l'option payload, transmise telle quelle : le validator ne s'en sert pas.

Les formes du `callback`

À comprendre

À retenir en priorité
  1. Le nom seul vise la valeur courante.
  2. Un callable explicite permet une autre cible.

C'est quoi ?

Un callable statique externe désigne explicitement une classe et une méthode, sous la forme [Classe::class, 'methode']. Contrairement à un simple nom de méthode recherché sur l'objet validé, il reçoit la valeur à contrôler en premier argument.

À quoi ça sert ?

Une petite règle peut être partagée hors de la classe de donnée sans dépendre de this. Si elle doit recevoir des services ou devenir une contrainte réutilisable configurable, une classe ConstraintValidator dédiée est souvent un meilleur contrat.

Où dans Symfony ?

Callback appelle cette forme avec la valeur, ExecutionContextInterface puis le payload. La méthode doit être accessible et statique pour ce tableau de classe/méthode. Une méthode inexistante est une erreur de définition, pas un refus métier ordinaire.

Comment, étape par étape ?

  1. Déclarer une méthode publique statique avec la signature adaptée.
  2. Passer son callable dans l'option callback.
  3. Examiner la valeur reçue, sans utiliser this.
  4. Ajouter les violations au contexte ; le retour booléen ne constitue pas le résultat de validation.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;
use Symfony\Component\Validator\Validation;
final class ReservedWordRule
{
    public static function check(mixed $value, ExecutionContextInterface $context, mixed $payload): void
    {
        if ('reserved' === $value) {
            $context->buildViolation('Cette valeur est réservée.')->addViolation();
        }
    }
}
$rule = new Assert\Callback(callback: [ReservedWordRule::class, 'check']);
$validator = Validation::createValidator();
var_dump(count($validator->validate('reserved', $rule)));
var_dump(count($validator->validate('public', $rule)));

On attend 1 puis 0. Contre-exemple : fournir seulement check comme nom pour faire chercher cette méthode sur une valeur scalaire. Correction : fournir le callable externe complet. Cette règle exclut une valeur précise ; elle n'impose pas à elle seule une chaîne non vide ou un format général.

Passage canonique conservé
Valeur de l'option Où la method est cherchée
un nom de method sur la valeur validée — l'object, sur une class
[Classe::class, 'méthode'] le callable statique désigné, hors de la class
une closure appelée avec ($value, $context, $payload)

Un nom de method absent lève une ConstraintDefinitionException.

Ce que le callback doit faire

À retenir en priorité
  1. Sans atPath(), l'erreur conserve le path courant de l'objet : vide à la racine, préfixé lors d'une validation imbriquée.
  2. Le field doit être désigné volontairement.

Ne pas ajouter de violation signifie que ce callback ne signale rien. Cela ne garantit pas la réussite des autres règles. Pour signaler un problème : $context->buildViolation('message'), puis ->atPath('firstName') si la règle vise un field, puis ->addViolation(). Sans atPath(), la violation garde le chemin courant : '' pour un objet validé à la racine, ou le préfixe de cet objet dans une validation imbriquée.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'ordre des arguments fait partie du contrat.
  2. La valeur précède le contexte en statique.
  • Voir l’explication : La signature statique commence par la valeur, pas par le contexte

    La signature statique commence par la valeur, pas par le contexte ; la confondre lève une TypeError.

  • Voir l’explication : Le retour est ignoré.

    Le retour est ignoré. Une règle non respectée doit produire une violation, pas un return false.

  • Voir l’explication : Un nom de method seul est cherché sur la valeur validée

    Un nom de method seul est cherché sur la valeur validée — l'object quand la constraint est posée sur la class —, jamais ailleurs.

  • Voir l’explication : Posée sur la class, Callback voit tout l'object

    Posée sur la class, Callback voit tout l'object, ce qui la rend adaptée aux règles croisées — mais il faut alors atPath() pour attribuer l'erreur au bon field.

Fiche express

À mémoriser

À retenir en priorité
  1. Le payload est une donnée auxiliaire.
  2. La logique reste dans le callback.

Si tu dois retenir seulement 6 choses :

  • Callback appelle ta method ; elle seule décide des violations.
  • Instance : (context, payload) ; statique / closure : (value, context, payload) — sinon TypeError.
  • Nom seul : cherché sur la valeur validée ; array : callable statique externe.
  • Sur une property, le callback reçoit la valeur de la property.
  • Aucune violation ajoutée = aucun échec signalé par ce callback ; return false est ignoré.
  • atPath() pour rattacher l'erreur à un field.

Moyen mnémotechnique : « Statique, l'object d'abord ».
