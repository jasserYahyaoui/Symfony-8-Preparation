Objectif

Écrire une règle de validation arbitraire sans créer de class de constraint, et connaître la signature attendue — elle change selon que la method est d'instance ou statique.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le retour du callback est ignoré.
  2. Le contexte porte les violations.

Callback fait appeler ta method par le validator : elle seule décide des violations. Deux choses tombent à l'examen : la signature change selon que la method est d'instance ou statique, et la valeur retournée est ignorée — seule une violation ajoutée compte.

Le schéma

À retenir en priorité
  1. Le callback exprime la règle.
  2. addViolation() rend l'échec observable.

L'exemple : un `Author`

▣ Exemple concret

À retenir en priorité
  1. Une règle de class voit l'Author entier.
  2. atPath() rattache l'erreur au field.
class Author
{
    public string $firstName = '';
    private array $fakeNames = ['Toto', 'Test', 'Foo'];

    #[Assert\Callback]
    private function validate(ExecutionContextInterface $context, mixed $payload): void
    {
        if (in_array($this->firstName, $this->fakeNames, true)) {
            $context->buildViolation('Ce prénom semble inventé.')
                ->atPath('firstName')
                ->addViolation();
        }
    }
}

Le principe

À retenir en priorité
  1. Callback convient à une règle locale.
  2. Une constraint dédiée favorise la réutilisation.

Callback est la porte de sortie quand aucune constraint native n'exprime la règle, et qu'une class de constraint serait disproportionnée.

  • L'attribute se pose sur la method ; sur la class, il nomme la method : #[Assert\Callback(callback: 'validate')].
  • La method peut être privée : elle est appelée, et sa violation remonte.

Elle accepte aussi une property : le callback reçoit alors la valeur de la property, et sa violation porte le path de la property. Un nom de method seul y est cherché sur cette valeur — une string — d'où une ConstraintDefinitionException : « Method "nope" targeted by Callback constraint does not exist in class "string". ».

Les deux signatures

À retenir en priorité
  1. Une method statique n'a pas this.
  2. La valeur validée est donc son premier argument.
Forme Signature
instance validate(ExecutionContextInterface $context, mixed $payload)
statique, closure validate(mixed $value, ExecutionContextInterface $context, mixed $payload)

Une method statique n'a pas $this : l'object validé lui est passé, en premier. CallbackValidator teste isStatic() et choisit l'appel. Une method statique écrite avec la signature d'instance lève une TypeError, pas une validation silencieusement fausse.

Le $payload est la donnée de l'option payload, transmise telle quelle : le validator ne s'en sert pas.

Les formes du `callback`

À retenir en priorité
  1. Le nom seul vise la valeur courante.
  2. Un callable explicite permet une autre cible.
Valeur de l'option Où la method est cherchée
un nom de method sur la valeur validée — l'object, sur une class
[Classe::class, 'méthode'] le callable statique désigné, hors de la class
une closure appelée avec ($value, $context, $payload)

Un nom de method absent lève une ConstraintDefinitionException.

Ce que le callback doit faire

À retenir en priorité
  1. Sans path explicite l'erreur reste globale.
  2. Le field doit être désigné volontairement.

Ne pas ajouter de violation, c'est dire « valide ». Pour signaler un problème : $context->buildViolation('message'), puis ->atPath('firstName') si la règle vise un field, puis ->addViolation(). Sans atPath(), la violation est rattachée à l'object : son path vaut ''.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. L'ordre des arguments fait partie du contrat.
  2. La valeur précède le contexte en statique.

La signature statique commence par la valeur, pas par le contexte ; la confondre lève une TypeError.

Le retour est ignoré. Une règle non respectée doit produire une violation, pas un return false.

Un nom de method seul est cherché sur la valeur validée — l'object quand la constraint est posée sur la class —, jamais ailleurs.

Posée sur la class, Callback voit tout l'object, ce qui la rend adaptée aux règles croisées — mais il faut alors atPath() pour attribuer l'erreur au bon field.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le payload est une donnée auxiliaire.
  2. La logique reste dans le callback.

Si tu dois retenir seulement 6 choses :

  • Callback appelle ta method ; elle seule décide des violations.
  • Instance : (context, payload) ; statique / closure : (value, context, payload) — sinon TypeError.
  • Nom seul : cherché sur la valeur validée ; array : callable statique externe.
  • Sur une property, le callback reçoit la valeur de la property.
  • Aucune violation = valide ; return false est ignoré.
  • atPath() pour rattacher l'erreur à un field.

Moyen mnémotechnique : « Statique, l'object d'abord ».
