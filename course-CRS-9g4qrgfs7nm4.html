Objectif

Reconnaître les conventions de nommage officielles de Symfony. La convention de nommage propre aux controllers est traitée dans le Module 04 — Contrôleurs.

L'essentiel

À comprendre

À retenir en priorité
  1. all() concerne la relation principale.
  2. Une relation secondaire utilise getXXXs(), pas allXXX().

Les standards de Symfony fixent la casse de chaque élément, quelques préfixes et suffixes, deux préfixes d'attributes, et douze noms de methods pour une collection. Rien n'est à déduire : tout se retient, et l'examen vise les exceptions — un cas d'enum, l'Abstract en préfixe, getXXXs() pour all().

Le schéma

À retenir en priorité
  1. Les enum cases suivent UpperCamelCase.
  2. Les constants restent en SCREAMING_SNAKE_CASE.

L'exemple : une collection principale

Exemple concret

$jar->all();            // relation principale : un CookieJar a des Cookie
$jar->getOptions();     // relation secondaire : getXXXs(), pas allOptions()

La casse

À comprendre

C'est quoi ?

La casse désigne la manière d'assembler majuscules, minuscules et séparateurs dans un nom. Une convention associe une forme à une catégorie pour rendre le code prévisible ; ce n'est pas toujours une contrainte imposée par PHP.

À quoi ça sert ?

Des noms réguliers permettent de reconnaître rapidement une classe, une constante ou une variable de template. Ils évitent aussi les incohérences de fichiers qui passent inaperçues sur certains systèmes mais cassent l'autoload sur un système sensible à la casse.

Où dans Symfony ?

  • camelCase : variables, paramètres PHP, fonctions et méthodes, comme hasSession.
  • UpperCamelCase : classes, interfaces, traits, enums, noms de fichiers PHP et cas d'enum.
  • SCREAMING_SNAKE_CASE : constantes, comme ITEMS_PER_PAGE.
  • snake_case : noms de routes, paramètres de configuration, variables et fichiers Twig ; les paramètres peuvent aussi être préfixés, comme app.contents_dir.

Comment, étape par étape ?

  1. Identifier la catégorie, pas seulement la langue du mot.
  2. Appliquer sa convention.
  3. Garder le même nom dans la déclaration, les références et le chemin attendu.
  4. Éviter les abréviations qui masquent le rôle même si leur casse est correcte.

Exemple concret PHP

<?php
final class PageOptions
{
    public const ITEMS_PER_PAGE = 10;
    public function pageCount(int $itemCount): int
    {
        return (int) ceil($itemCount / self::ITEMS_PER_PAGE);
    }
}
echo (new PageOptions())->pageCount(21), "\n";

PageOptions, ITEMS_PER_PAGE, pageCount et $itemCount illustrent quatre catégories ; la sortie est 3. Contre-exemple : utiliser la casse d'une constante pour un cas d'enum en pensant que tout élément fixe suit la même règle. Correction : les conventions Symfony nomment les cas d'enum en UpperCamelCase. Dans les types et PHPDoc, préférer les formes bool, int et float prescrites.

Passage canonique conservé

La casse

Élément Casse Exemple
variables, functions, methods, arguments camelCase hasSession()
parameters de configuration, route names, variables Twig snake_case framework.csrf_protection
constantes SCREAMING_SNAKE_CASE InputArgument::IS_ARRAY
cas d'enum UpperCamelCase InputArgumentMode::IsArray
classes, interfaces, traits, enums, files PHP UpperCamelCase EnvVarProcessor.php
templates Twig et ressources web snake_case section_layout.html.twig

Dans les PHPDoc et les transtypages : bool, int, float — jamais boolean, integer, double ou real.

Préfixes et suffixes

À comprendre

À retenir en priorité
  1. Abstract précède le nom.
  2. Interface, Trait et Exception sont des suffixes.

C'est quoi ?

Un préfixe ou suffixe conventionnel annonce le rôle d'une déclaration. Abstract précède une classe abstraite ; Interface, Trait et Exception terminent les catégories correspondantes. Une classe ordinaire n'a pas besoin d'un suffixe générique Class.

À quoi ça sert ?

Le lecteur comprend plus vite le type de collaboration attendu. Ces noms ne créent toutefois aucun comportement : appeler une classe SomethingInterface n'en fait pas une interface si elle est déclarée avec class.

Où dans Symfony ?

Les attributs As... expriment habituellement la configuration d'un service, comme AsCommand ou AsEventListener. Les attributs Map... expriment la fourniture d'un argument de controller. La convention des classes abstraites connaît l'exception des classes de test *TestCase ; des noms historiques peuvent également précéder les conventions actuelles.

Comment, étape par étape ?

  1. Identifier le rôle réel de la déclaration.
  2. Choisir le préfixe ou suffixe correspondant.
  3. Pour un attribut, distinguer configuration du service et résolution d'un argument.
  4. Vérifier le lecteur de l'attribut : son nom seul ne provoque aucune exécution.

Exemple concret text

FormatterInterface : contrat de formatage
AbstractFormatter  : base abstraite partageant une partie du comportement
FormattingException : échec représenté par une exception
AsEventListener    : abonnement d'un service à un événement
MapRequestPayload  : données du body fournies à un argument de controller

Contre-exemple : inventer un attribut AsPayload et attendre que Symfony le traite par reconnaissance du préfixe. Correction : utiliser un attribut documenté et son mécanisme de lecture ; les conventions nomment les API, elles ne les implémentent pas. Pour les collections, all() convient à la relation principale de l'objet ; une relation secondaire se nomme explicitement, par exemple getOptions(), afin de ne pas cacher ce qui est retourné.

Passage canonique conservé
  • Abstract en préfixe pour les abstract classes — sauf les *TestCase de PHPUnit.
  • Interface, Trait, Exception en suffixe ; aucun suffixe pour une class ordinaire ou une enum.
  • As... quand l'attribute configure un service (#[AsCommand]) ; Map... quand il remplit un argument de controller (#[MapRequestPayload]).

Un badge de fonction rend un rôle lisible avant d'ouvrir le dossier. Abstract, Interface et Trait rendent pareillement l'intention visible ; le badge ne remplace toutefois pas les règles PHP ni le type réel.

Nommer une method de collection

conventions.rst normalise douze noms quand un object a une relation principale : get(), set(), has(), all(), replace(), remove(), clear(), isEmpty(), add(), register(), count(), keys(). Un CookieJar a beaucoup de Cookie : la convention s'applique ; un Input de console a des arguments et des options : elle ne s'applique pas.

Relation principale Autre relation
all() getXXXs() — pas allXXX()
replace() setXXXs() — pas replaceXXXs()
keys() aucune
aucune replaceXXX()

setXXX() peut ajouter un élément ; replaceXXX() ne le peut pas et doit lever une exception sur une key inconnue.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un cas d'enum s'écrit UpperCamelCase, pas en majuscules.

    Un cas d'enum s'écrit UpperCamelCase, pas en majuscules. Les standards l'illustrent par InputArgumentMode::IsArray face à la constant InputArgument::IS_ARRAY ; seule la constant existe dans Console 8.0 — l'enum n'est qu'un exemple de nommage.

  • Voir l’explication : Abstract est un préfixe ; Interface, Trait et Exception sont des suffixes.

    Abstract est un préfixe ; Interface, Trait et Exception sont des suffixes. Il n'y a en revanche aucun suffixe pour une class ordinaire ou une enum : ni ...Class, ni ...Enum.

  • Voir l’explication : As... et Map... ne sont pas interchangeables.

    As... et Map... ne sont pas interchangeables. As... configure un service (#[AsCommand]), Map... concerne un argument de controller (#[MapRequestPayload]).

  • Voir l’explication : all() devient getXXXs(), pas allXXX().

    all() devient getXXXs(), pas allXXX(). De même replace() devient setXXXs(). Les deux lignes les moins régulières de la table.

  • Voir l’explication : setXXX() et replaceXXX() diffèrent par un droit.

    setXXX() et replaceXXX() diffèrent par un droit. Seul le premier peut ajouter ; le second doit lever une exception sur une key inconnue.

Application

À retenir en priorité
  1. all() concerne la relation principale.
  2. Une relation secondaire utilise getXXXs(), pas allXXX().
  3. Abstract précède le nom.
  4. Interface, Trait et Exception sont des suffixes.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • camelCase le code, snake_case config, routes et templates.
  • Cas d'enum en UpperCamelCase, constantes en SCREAMING_SNAKE_CASE.
  • Abstract en préfixe ; Interface, Trait, Exception en suffixe.
  • As... = service ; Map... = argument de controller.
  • all() → getXXXs(), replace() → setXXXs(), keys() → rien.
  • replaceXXX() ne peut pas ajouter ; setXXX() le peut.

Moyen mnémotechnique : « Abstract devant, le reste derrière ».
