Objectif

Décider ce qui arrive à un message dont le handler a levé une exception : le rejouer, l'abandonner, ou le mettre de côté. Trois mécanismes se superposent, et c'est leur ordre qui décide.

L'essentiel

À comprendre

À retenir en priorité
  1. Le worker n'intervient pas dans le dispatch direct.
  2. Le caller reçoit l'échec.

En synchrone, l'exception d'un handler remonte au dispatch(), emballée, sans retry. Dans un worker, elle déclenche un retry à délai croissant ; deux exceptions spéciales court-circuitent cette strategy ; et un message épuisé part dans le failure transport — ou est perdu s'il n'y en a pas.

Le schéma

À retenir en priorité
  1. La file d'échec conserve le message épuisé.
  2. Elle doit être configurée explicitement.

Chaque étage change l'issue, et c'est l'ordre qui compte : une UnrecoverableMessageHandlingException saute la strategy mais pas le failure transport.

L'exemple

Exemple concret

À retenir en priorité
  1. Le compteur exclut la première tentative.
  2. Ne pas confondre retries et tentatives totales.
framework:
    messenger:
        failure_transport: failed
        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'
                retry_strategy: { max_retries: 3, delay: 1000, multiplier: 2 }
            failed: '%env(MESSENGER_FAILED_DSN)%'
$customer = $this->customers->find($message->customerId)
    ?? throw new UnrecoverableMessageHandlingException('Customer deleted.');
$this->gateway->charge($customer);   // un timeout lève une exception ordinaire

Un timeout : quatre tentatives, à environ 1 s, 2 s, 4 s d'intervalle, puis la file failed. Un client supprimé : une seule tentative, puis la file failed.

Synchrone : l'exception remonte, emballée

À retenir en priorité
  1. L'exception du handler est emballée.
  2. Un catch du seul type métier ne suffit pas autour de dispatch().

Un message non routé n'a ni retry ni file d'échec. Ce qui remonte est une HandlerFailedException — « Handling "App\…\Boom" failed: boom » : un catch (\DomainException $e) autour de dispatch() ne l'attrape pas ; l'exception d'origine se lit dans getWrappedExceptions().

La strategy de retry

À comprendre

À retenir en priorité
  1. Le multiplier fait croître le délai.
  2. Le jitter répartit les nouvelles tentatives.

C'est quoi ?

Un retry est une nouvelle tentative de traitement après un échec. La retry strategy, ou politique de nouvelles tentatives, décide si le budget permet de recommencer et combien de millisecondes attendre. Elle ne répare pas les données et ne rend pas une opération répétable sans risque.

Un worker est le processus qui consomme les messages d'un transport. Un handler est le code appelé pour traiter un message. Cette politique intervient lors de la consommation par un worker ; elle ne transforme pas une exception issue d'un traitement synchrone dans dispatch() en traitement différé.

À quoi ça sert ?

Un service momentanément indisponible peut fonctionner au prochain essai. Espacer les essais évite de le solliciter immédiatement à nouveau ; limiter leur nombre évite de conserver indéfiniment un travail impossible.

  • Une panne temporaire peut justifier une nouvelle tentative.
  • Une donnée définitivement invalide exige une correction ou un classement en échec, pas davantage d'attente.
  • Un délai dépassé ne prouve pas que le service distant n'a rien fait. Rejouer sans précaution un paiement peut produire deux débits.

L'idempotence signifie que répéter la même opération logique ne multiplie pas son effet métier. Pour un effet externe, transmettre une clé stable liée à cette opération et utiliser le mécanisme de déduplication prévu par le service distant. Une nouvelle clé à chaque essai ne protège pas contre les doublons.

Où dans Symfony ?

Dans FrameworkBundle, retry_strategy appartient à la configuration de chaque transport Messenger. Ses défauts en 8.0 sont max_retries: 3, delay: 1000, multiplier: 2, max_delay: 0 et jitter: 0.1. Attention : le constructeur du component MultiplierRetryStrategy, employé directement hors de cette configuration, prend un multiplicateur de 1, pas de 2. Le framework lui fournit sa propre valeur.

Voici un fragment à placer sous la définition d'un transport déjà configuré dans framework.messenger.transports. Il ne déclare ni connexion ni routage : ces éléments doivent déjà exister.

retry_strategy:
    max_retries: 3
    delay: 1000
    multiplier: 2
    max_delay: 10000
    jitter: 0.1

Le plafond de 10 000 ms est un choix de cet exemple, pas le défaut. La valeur 0 signifie absence de plafond de délai ; elle ne signifie ni absence d'attente ni nombre illimité d'essais.

Comment, étape par étape ?

  1. Le worker appelle le handler. Si celui-ci échoue, la gestion d'échec examine l'exception et la politique du transport.
  2. Pour une exception ordinaire soumise à cette politique, le nombre de retries déjà effectués est comparé à max_retries. Trois retries autorisent au plus quatre tentatives : l'initiale, puis trois nouvelles.
  3. Le délai de base est delay × multiplier^n, où n vaut 0 avant le premier retry. Ici, les délais de base sont 1 000, 2 000 puis 4 000 ms.
  4. Le jitter, variation aléatoire du délai, répartit les reprises dans le temps. Avec 0.1, la variation est de ±10 % du délai de base. Un max_delay non nul plafonne ensuite le résultat.
  5. Lorsque le budget est épuisé, un failure transport configuré, c'est-à-dire une file réservée aux messages en échec, permet leur examen. Sans lui, Messenger ne conserve pas ces messages pour une reprise manuelle dans une telle file.

Ces délais sont des attentes demandées au transport, pas la promesse d'une heure exacte d'exécution. La disponibilité des workers compte aussi. Les exceptions spéciales peuvent court-circuiter la politique : voir Court-circuiter la strategy. Le budget présenté ici n'est donc pas une borne universelle de toutes les livraisons possibles.

Contre-exemple et correction. « Trois retries garantissent trois appels, et une transaction suffit à éviter tout doublon » est faux. Le premier appel ne compte pas comme un retry. De plus, un worker peut terminer son effet métier puis s'arrêter avant d'accuser réception du message : une nouvelle livraison reste possible. Une transaction de base de données peut rendre atomiques les écritures qu'elle englobe, mais ne peut pas annuler un courriel déjà envoyé ou un paiement externe déjà accepté. Corriger le raisonnement en séparant budget de reprise, transaction locale et idempotence de l'effet. Un simple contrôle préalable de présence ne suffit pas face à deux traitements concurrents : une contrainte d'unicité durable doit protéger les écritures concernées. Cela ne promet aucune livraison « exactement une fois ».

Exemple concret PHP

Ce calcul PHP autonome vérifie le budget et les délais de base, sans installer Symfony et sans lancer de worker. Il représente volontairement le cas sans jitter, pour obtenir un résultat déterministe ; ce n'est pas une réimplémentation du transport.

<?php
$maxRetries = 3;
$delayMilliseconds = 1000;
$multiplier = 2;
$maxDelayMilliseconds = 10000;
$delays = [];

for ($retry = 0; $retry < $maxRetries; ++$retry) {
    $delay = $delayMilliseconds * $multiplier ** $retry;
    $delays[] = $maxDelayMilliseconds === 0
        ? $delay
        : min($delay, $maxDelayMilliseconds);
}

echo json_encode($delays, JSON_THROW_ON_ERROR), PHP_EOL;
echo 'Tentatives maximales : ', 1 + $maxRetries, PHP_EOL;

Le résultat est [1000,2000,4000], puis Tentatives maximales : 4. Le tableau décrit les attentes entre tentatives, pas quatre délais. Avec maxRetries égal à 0, il devient vide : la tentative initiale reste possible. Avec un plafond de 1 500 ms, les délais deviennent [1000,1500,1500] ; le nombre d'essais ne change pas.

Ce calcul ne teste ni la gestion des exceptions spéciales, ni les accusés de réception, ni un service distant. Pour la configuration et les limites de redélivrance : Messenger 8.0.

Passage canonique conservé

La strategy de retry

retry_strategy:
    max_retries: 3
    delay: 1000        # premier délai, en millisecondes
    multiplier: 2      # 1s, 2s, 4s
    max_delay: 10000   # plafond ; 0 = pas de plafond
    jitter: 0.1        # aléatoire, de 0 à 1
  • Défauts de FrameworkBundle 8.0 : ceux-ci, sauf max_delay, qui vaut 0.
  • Le délai croît exponentiellement, delay × multiplier^n ; le jitter le fait varier de ±10 % pour que mille messages ne repartent pas ensemble.
  • max_retries: 3 = trois retries après l'échec initial, quatre tentatives.
  • Un retry ne rejoue que ce qui a échoué : un handler dont l'Envelope porte déjà le HandledStamp est sauté.

Court-circuiter la strategy

À retenir en priorité
  1. Un échec permanent ne se rejoue pas.
  2. Il peut rester consultable en file d'échec.
Exception Effet
UnrecoverableMessageHandlingException aucun retry : le message part directement en échec
RecoverableMessageHandlingException retry forcé, sans limite ; son quatrième argument, retryDelay, fixe le délai en ms
  • shouldRetry() renvoie true pour une exception recoverable avant de consulter max_retries.
  • new RecoverableMessageHandlingException('later', 0, null, 5000) renvoie le message avec un DelayStamp(5000), quelle que soit la strategy.
  • Plusieurs handlers échouent : il faut que toutes les exceptions emballées soient unrecoverable pour refuser le retry.

La strategy traite l'échec temporaire, Unrecoverable l'échec permanent — un identifier qui n'existera jamais.

À retenir en priorité
  1. L'exception recoverable force le retry.
  2. Prévoir une politique qui évite une boucle sans fin involontaire.

php bin/console messenger:failed:show --stats
php bin/console messenger:failed:retry
php bin/console messenger:failed:remove <id>
  • messenger:failed:retry traite lui-même le message, depuis la file d'échec ; le compteur a été remis à zéro à l'entrée (RedeliveryStamp(0)). Un nouvel échec le renvoie dans la file d'échec, pas vers async.
  • Hors mode interactif, il faut un id : « Message id must be passed when in non-interactive mode. » Pour tout rejouer : messenger:consume failed.

L'enchaînement complet

Piège à éviter

À retenir en priorité
  1. Le même handler peut être appelé dans deux contextes.
  2. Le contexte change la gestion de l'échec.
  3. Les retries ne garantissent pas une exécution unique.
  4. L'idempotence protège les effets métier lors d'une nouvelle livraison.

C'est quoi ?

La gestion d'un échec dépend du contexte d'exécution, de la nature de l'exception et de la configuration du transport. La file d'échec, ou failure transport, conserve des messages qui demandent un diagnostic ou une intervention plutôt qu'une réussite fictive.

À quoi ça sert ?

Distinguer échec temporaire, échec permanent et traitement direct évite deux erreurs opposées : abandonner un message récupérable ou rejouer indéfiniment une donnée définitivement invalide.

Où dans Symfony ?

En traitement synchrone, HandlerFailedException remonte au caller de dispatch() ; les exceptions métier emballées se lisent avec getWrappedExceptions(). Les retries de transport sont gérés lors de la consommation par un worker, pas par ce simple appel synchrone.

Comment, étape par étape ?

  1. Identifier où le handler s'exécute. En synchrone, traiter ou propager l'exception avec son contexte.
  2. Dans le worker, une exception ordinaire suit le budget de la retry strategy. Avec trois retries, quatre tentatives sont possibles pour ce parcours.
  3. UnrecoverableMessageHandlingException indique qu'une nouvelle tentative ne résoudra pas cet échec : elle saute les retries, mais pas la file d'échec configurée.
  4. RecoverableMessageHandlingException force la reprise au-delà du budget normal dans le cas correspondant ; en 8.0 son argument retryDelay peut imposer le délai. Réserver ce choix aux cas réellement récupérables et surveillés, pas à toutes les erreurs.
  5. Lorsqu'aucun retry n'est décidé, envoyer vers le failure transport configuré. Sans ce mécanisme, ne compter sur aucune conservation par Messenger pour une reprise manuelle.

Exemple concret en shell

Dans une application où un failure transport est configuré :

php bin/console messenger:failed:show --stats
php bin/console messenger:failed:retry

La première commande inspecte ; la seconde lance une reprise interactive et exécute du traitement. Elle n'est pas exécutée dans cette mission. Examiner d'abord la cause et les effets déjà produits. En mode non interactif, sélectionner explicitement le message requis par la commande, au lieu de supposer qu'un drapeau de confirmation signifie « tous ».

Contre-exemple : supprimer les messages en échec pour faire disparaître l'alerte, ou les rejouer en masse sans vérifier un paiement déjà effectué. Correction : corriger la cause, conserver la traçabilité, vérifier l'idempotence, puis reprendre les messages appropriés. Une nouvelle erreur de reprise peut encore aboutir à un échec ; aucun succès n'est garanti.

Avec plusieurs handlers, distinguer les exceptions emballées : l'abandon ne se déduit pas de la seule présence d'une exception non récupérable parmi d'autres. Un HandledStamp conservé peut éviter de rappeler un handler déjà réussi, mais ne garantit pas l'unicité de tous les effets en cas de nouvelle livraison ou d'interruption avant acquittement.

Passage canonique conservé

L'enchaînement complet

  1. Traité pendant dispatch() : HandlerFailedException, et rien d'autre.
  2. Dans un worker, une exception Recoverable… : retry, sans limite.
  3. Toutes les exceptions Unrecoverable… : aucun retry, directement à l'étape 5.
  4. Sinon : retry à délai croissant, tant que max_retries le permet.
  5. Épuisé : le failure transport s'il est configuré, sinon le message est perdu.

Une nouvelle livraison peut suivre un échec ou une interruption autour de l'acquittement. Le handler doit donc tolérer le traitement répété d'un même message : l'objectif est de ne pas reproduire un effet métier déjà réalisé. Un nombre limité de retries ne garantit pas une exécution unique. Cette propriété d'idempotence est distincte du délai choisi par la retry strategy.

Fiche express

À mémoriser

À retenir en priorité
  1. Le retry doit cibler le travail restant.
  2. L'Envelope conserve l'historique de traitement.

Si tu dois retenir seulement 7 choses :

  • Synchrone : une HandlerFailedException remonte, sans retry.
  • max_retries: 3 = quatre tentatives, délais exponentiels.
  • max_delay vaut 0 par défaut : pas de plafond.
  • Unrecoverable… saute les retries, pas la file d'échec.

  • Sans failure_transport, un message épuisé est perdu.

Moyen mnémotechnique : « réessayer, abandonner, mettre de côté ».

sync → HandlerFailedException (getWrappedExceptions) ; async → Recoverable ? retry sans fin : toutes Unrecoverable ? échec : max_retries (+1 tentative) ;
