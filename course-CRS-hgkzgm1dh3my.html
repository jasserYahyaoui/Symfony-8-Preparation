Objectif

Le worker a reçu ImportBlogFile, mais la lecture du fichier ou un service appelé par son handler échoue. La page GET /blog/42 peut déjà avoir été envoyée : on ne peut pas lui retourner rétroactivement cette exception. Il faut décider si le travail doit recommencer, s'arrêter ou rester consultable. Suivons ces décisions, puis le cas différent d'un import traité directement pendant dispatch().

L'essentiel

À comprendre

À retenir en priorité
  1. Le worker n'intervient pas dans le dispatch direct.
  2. Le caller reçoit l'échec.

Un retry est une nouvelle tentative, pas une réparation du message. Dans un dispatch synchrone direct avec le middleware standard, l'échec d'un handler ordinaire remonte sous forme de HandlerFailedException : le bus n'ajoute pas la boucle de retry d'un worker.

Lors de la consommation, le worker émet au contraire un événement d'échec. Un listener décide du retry selon l'exception et la politique du transport ; un autre peut envoyer le message au failure transport, la destination réservée aux échecs à examiner. Aucun de ces mécanismes ne garantit que répéter un effet externe est sans risque.

Le schéma

À retenir en priorité
  1. La file d'échec conserve le message épuisé.
  2. Elle doit être configurée explicitement.

Pour commencer, isolons un seul handler en échec. Un import dont le fichier est momentanément indisponible et un import devenu définitivement invalide ne devraient pas avoir la même politique. Ce schéma décrit la décision, pas la vitesse réelle à laquelle un worker sera disponible.

Bleu : origine ; ambre : décisions ordonnées ; vert : destination. La vue porte sur une exception directe ou un unique échec emballé : dans ce cas, recoverable passe avant le compteur. On suppose les listeners standards, la strategy standard configurée et des envois au transport réussis. « Perdu » signifie sans copie de récupération gérée par Messenger : un broker peut avoir sa propre politique de messages rejetés, hors de cette vue.

Chaque étage change l'issue, et c'est l'ordre qui compte : une UnrecoverableMessageHandlingException saute la strategy mais pas le failure transport.

L'exemple

Exemple concret

À retenir en priorité
  1. Le compteur exclut la première tentative.
  2. Ne pas confondre retries et tentatives totales.

La configuration suivante suppose les DSN fournis, des transports effectivement disponibles et le message routé vers async. Elle ne crée pas ce routage à elle seule. La politique appartient au transport : elle est préparée avec la configuration du container, pas recompilée à chaque échec.

framework:
    messenger:
        failure_transport: failed
        transports:
            async:
                dsn: '%env(MESSENGER_TRANSPORT_DSN)%'
                retry_strategy: { max_retries: 3, delay: 1000, multiplier: 2 }
            failed: '%env(MESSENGER_FAILED_DSN)%'
use Symfony\Component\Messenger\Exception\UnrecoverableMessageHandlingException;

// Extrait du corps d'un handler, pas un script autonome.
$customer = $this->customers->find($message->customerId)
    ?? throw new UnrecoverableMessageHandlingException('Customer deleted.');
$this->gateway->charge($customer);   // un timeout lève une exception ordinaire

Ce fragment conserve la variante d'abonnement payant au blog : elle rend visible le risque d'un effet externe répété. Pour une exception ordinaire qui persiste, la politique autorise quatre tentatives, avec des délais demandés d'environ 1 s, 2 s et 4 s, puis la file failed. Un client définitivement supprimé entraîne une seule tentative avant cette file, dans le cas à échec unique. Une réussite anticipée arrête évidemment cette séquence.

Le fragment suppose des services customers et gateway injectés. Un timeout ne prouve pas que le paiement a échoué côté prestataire : transmettre une clé d'idempotence stable avant de réessayer, sinon deux tentatives peuvent débiter deux fois. L'idempotence consiste à ne pas multiplier l'effet d'une même opération logique lorsqu'elle est répétée. Le retry apporte une nouvelle tentative, pas une garantie « une fois ». Le même besoin apparaît si l'import a déjà créé une partie de ses articles avant l'interruption.

Synchrone : l'exception remonte, emballée

À retenir en priorité
  1. L'exception du handler est emballée.
  2. Un catch du seul type métier ne suffit pas autour de dispatch().

Si app:blog:import dispatche directement sans sender, le handler peut échouer avant le retour de la command. Sans cycle worker, il n'y a pas de retry automatique ni d'envoi automatique en file d'échec. Pour un handler ordinaire appelé par HandleMessageMiddleware, ce qui remonte est une HandlerFailedException — « Handling "App\…\Boom" failed: boom » : un catch (\DomainException $e) autour de dispatch() ne l'attrape pas ; l'exception d'origine se lit dans getWrappedExceptions().

Le middleware peut avoir continué à appeler d'autres handlers avant de lever l'exception groupée. « Le dispatch a échoué » ne signifie donc pas « rien n'a été fait ». Le transport sync:// ne crée pas davantage un worker ; rester synchrone via ce transport ne suffit pas à activer les listeners de retry de consommation.

La strategy de retry

À retenir en priorité
  1. Le multiplier fait croître le délai.
  2. Le jitter répartit les nouvelles tentatives.

🌍 In Real Life

La situation : le secrétariat du blog rappelle un fournisseur indisponible, avec un budget de rappels et des intervalles.

L’équivalent dans Symfony : rappels autorisés → max_retries ; intervalle demandé → délai de retry ; nouvel appel → nouvelle tentative du message.

Retour à la réalité technique : avec le worker et les listeners configurés, la stratégie décide si et quand réessayer. Trois retries ordinaires autorisent jusqu'à quatre tentatives avec la première ; ils ne réparent ni les données ni les effets déjà produits.

🧠 Comment le mémoriser : « Refaire n'est pas réparer. » Image mentale : quatre cases, dont la première n'est pas un rappel. Question-réflexe : compte-t-on les tentatives ou les retries ?

⚠️ À ne pas confondre : retry du worker et exception d'un dispatch synchrone direct.

Pour l'import en file, une erreur temporaire mérite parfois une attente. La strategy répond à deux questions distinctes : reste-t-il un essai autorisé, et quel délai demander ? Ce fragment se place sous un transport déjà déclaré :

retry_strategy:
    max_retries: 3
    delay: 1000        # premier délai, en millisecondes
    multiplier: 2      # 1s, 2s, 4s
    max_delay: 10000   # plafond ; 0 = pas de plafond
    jitter: 0.1        # aléatoire, de 0 à 1
  • Défauts de FrameworkBundle 8.0 : ceux-ci, sauf max_delay, qui vaut 0. Le constructeur du component MultiplierRetryStrategy, employé directement, a un multiplier de 1 : le framework lui fournit sa propre valeur de 2.
  • Le délai croît exponentiellement, delay × multiplier^n ; le jitter le fait varier ici de ±10 % pour répartir les reprises. Le plafond max_delay non nul s'applique après cette variation. Un délai de base de 8 000 ms, jitter: 0.1 et un plafond de 8 100 ms donnent une valeur comprise entre 7 200 et 8 100 ms.
  • max_retries: 3 = trois retries après l'échec initial, quatre tentatives.
  • Un handler dont l'Envelope conserve déjà le HandledStamp correspondant est sauté par le middleware. Cette mémoire de traitement n'est pas une garantie universelle contre une nouvelle livraison après un crash : l'effet peut avoir eu lieu avant l'acquittement.

Avec n=0 avant le premier retry, les délais de base sont 1 000, 2 000 et 4 000 ms. Ce sont des attentes demandées au transport, pas des heures garanties d'exécution. Un worker disponible reste nécessaire.

Le petit calcul PHP 8.4 suivant conserve le cas déterministe sans jitter, indépendamment du transport. Il ne simule ni les événements ni l'acquittement :

<?php
$maxRetries = 3;
$delayMilliseconds = 1000;
$multiplier = 2;
$maxDelayMilliseconds = 10000;
$delays = [];

for ($retry = 0; $retry < $maxRetries; ++$retry) {
    $delay = $delayMilliseconds * $multiplier ** $retry;
    $delays[] = $maxDelayMilliseconds === 0
        ? $delay
        : min($delay, $maxDelayMilliseconds);
}

echo json_encode($delays, JSON_THROW_ON_ERROR), PHP_EOL;
echo 'Tentatives maximales : ', 1 + $maxRetries, PHP_EOL;

Résultat attendu : [1000,2000,4000], puis Tentatives maximales : 4. Avec zéro retry, le tableau serait vide mais l'essai initial resterait possible. Avec un plafond de 1 500 ms, les délais seraient [1000,1500,1500], sans changer le nombre d'essais.

Pour les articles importés, protéger l'opération logique contre les doublons est une décision métier supplémentaire. Une transaction locale ne peut pas annuler un courriel déjà envoyé ou un paiement externe déjà accepté. Un contrôle préalable « existe-t-il déjà ? » ne suffit pas face à deux traitements concurrents : protéger les écritures concernées par une unicité durable ou un mécanisme atomique adapté. Rien ici ne promet une livraison exactement une fois.

Court-circuiter la strategy

À retenir en priorité
  1. Un échec permanent ne se rejoue pas.
  2. Il peut rester consultable en file d'échec.

Attendre ne répare pas un identifier définitivement invalide. À l'inverse, une indisponibilité temporaire peut justifier de dépasser le budget ordinaire. Pour une exception directe ou une seule exception emballée, avec une strategy de retry configurée, ces deux classes expriment ce choix :

Exception Effet
UnrecoverableMessageHandlingException aucun retry : le message part directement en échec
RecoverableMessageHandlingException retry forcé, sans limite ; son quatrième argument, retryDelay, fixe le délai en ms
  • shouldRetry() renvoie true pour une exception recoverable avant de consulter max_retries.
  • new RecoverableMessageHandlingException('later', 0, null, 5000) renvoie le message avec un DelayStamp(5000) sur ce chemin de retry. L'exception seule ne crée ni strategy ni sender s'ils ne sont pas configurés.

Symfony 8.0 exige getRetryDelay(): ?int sur RecoverableExceptionInterface : null laisse la strategy calculer le délai. Pour plusieurs exceptions emballées, la sélection du délai et la décision de retry sont deux parcours distincts ; parmi les délais recoverable non négatifs fournis, le plus petit est retenu.

Plusieurs échecs emballés ne se réduisent pas à une priorité universelle. Dans Symfony 8.0.16, shouldRetry() parcourt les exceptions dans leur ordre : une recoverable rencontrée force le retry ; une unrecoverable laisse continuer ; la première exception ordinaire interrompt le parcours et renvoie la décision à la strategy. Une recoverable située après cette exception ordinaire n'est donc pas examinée. Si toutes sont unrecoverable, le retry est refusé sans consulter la strategy.

Avec max_retries: 0, [RuntimeException, Recoverable…] ne réessaie pas ; [Recoverable…, RuntimeException] réessaie. Cette limite décrit le code épinglé, pas une recommandation pour ordonner artificiellement les échecs.

La strategy traite l'échec temporaire, Unrecoverable l'échec permanent — un identifier qui n'existera jamais.

L'absence de 999 dans le catalogue pédagogique peut servir de cas permanent si le contrat exige un article existant. Ce n'est pas une règle universelle : dans un système où cet article peut arriver plus tard, l'absence aurait un autre sens. Choisir l'exception d'après le contrat métier, pas d'après son nom le plus commode.

Le failure transport

À retenir en priorité
  1. Une recoverable directe ou seule emballée force le retry avec strategy configurée ; en 8.0.16, une exception ordinaire précédente peut arrêter le parcours d'un ensemble mixte.
  2. Prévoir une politique qui évite une boucle sans fin involontaire.

🌍 In Real Life

La situation : les imports problématiques du blog sont placés dans un casier de diagnostic, s'il a été prévu.

L’équivalent dans Symfony : casier dédié → failure_transport ; dossier conservé → message envoyé en échec ; reprise manuelle → nouvelle tentative décidée après diagnostic.

Retour à la réalité technique : la conservation dépend de la configuration et de la réussite de l'envoi. Une erreur irrécupérable n'interdit pas cette conservation ; elle interdit le retry automatique dans le cas décrit.

🧠 Comment le mémoriser : « Échec conservé, pas corrigé. » Image mentale : un casier portant une loupe. Question-réflexe : où le message va-t-il si aucun retry n'est prévu ?

⚠️ À ne pas confondre : stockage d'échec et garantie de réussite lors d'une reprise.

Les tentatives n'ont pas résolu le problème. Il faut maintenant conserver l'import pour l'examiner, au lieu de supposer qu'une file d'échec existe par défaut. Pour l'échec unique persistant décrit ci-dessus, avec les listeners, la strategy et les envois fonctionnels, max_retries: 3 donne :

Exception Tentatives Sans failure_transport Avec
ordinaire 4 perdu en file d'échec
Unrecoverable… 1 perdu en file d'échec
Recoverable… non bornées par max_retries pas d'épuisement du budget ordinaire pas de transfert motivé par cet épuisement

« Perdu » signifie ici sans copie de reprise gérée par Messenger, pas sans aucune politique possible du système de transport. Les commands suivantes séparent observation, nouvel essai et suppression volontaire. Remplacer MESSAGE_ID par un identifier réellement obtenu lors de l'inspection :

php bin/console messenger:failed:show --stats
php bin/console messenger:failed:retry
php bin/console messenger:failed:remove MESSAGE_ID

Le résultat attendu de show --stats est une vue des effectifs d'échec ; retry déclenche le traitement choisi, tandis que remove retire le message sélectionné. Ne pas supprimer avant d'avoir décidé que sa récupération n'est plus nécessaire. Les interfaces offertes par le receiver conditionnent les opérations disponibles.

  • messenger:failed:retry traite lui-même le message, depuis la file d'échec ; le compteur a été remis à zéro à l'entrée (RedeliveryStamp(0)). Le traitement passe par un worker utilisant le receiver d'échec, pas par un simple déplacement vers async. Les nouvelles tentatives et l'issue dépendent de la configuration de ce trajet : ne pas considérer la file d'échec comme une garantie de conservation infinie après tous les rejeux.
  • Hors mode interactif, il faut un id : « Message id must be passed when in non-interactive mode. » Pour tout rejouer : messenger:consume failed.

L'enchaînement complet

À retenir en priorité
  1. Le même handler peut être appelé dans deux contextes.
  2. Le contexte change la gestion de l'échec.
  3. Les retries ne garantissent pas une exécution unique.
  4. L'idempotence protège les effets métier lors d'une nouvelle livraison.

Reprenons le même import avec les listeners standards. Le listener de retry intervient avant celui du failure transport ; ce dernier s'abstient si l'événement est déjà marqué pour retry. Ce sont des décisions d'exécution, pas des compiler passes qui reconstruisent la configuration.

  1. Échec d'un handler ordinaire dans un dispatch synchrone direct : HandlerFailedException remonte, sans ce cycle worker.
  2. Dans un worker avec strategy configurée, une exception directe Recoverable… force le retry. Pour un ensemble emballé, seule une recoverable rencontrée avant la première exception ordinaire le force.
  3. Une exception directe Unrecoverable…, ou toutes les exceptions emballées Unrecoverable… : aucun retry, directement à l'étape 5.
  4. Sinon : retry à délai croissant, tant que max_retries le permet.
  5. Épuisé : le failure transport s'il est configuré, sinon le message est sans copie de récupération Messenger.

Une interruption après création des articles mais avant acquittement peut entraîner une nouvelle livraison. Ni le budget de retry ni un ancien HandledStamp absent de cette livraison ne protège à lui seul l'effet métier. L'identifier stable de l'opération permet d'organiser sa déduplication ; inventer une nouvelle clé à chaque essai annulerait cette protection.

Une nouvelle livraison peut suivre un échec ou une interruption autour de l'acquittement. Le handler doit donc tolérer le traitement répété d'un même message : l'objectif est de ne pas reproduire un effet métier déjà réalisé. Un nombre limité de retries ne garantit pas une exécution unique. Cette propriété d'idempotence est distincte du délai choisi par la retry strategy.

Piège à éviter

À retenir en priorité
  1. La command exécute le traitement.
  2. Un nouvel échec reste géré comme un échec.
Échecs synchrones, retries et file d’échec
  • En synchrone, l'exception remonte au dispatch() : pas de retry.
  • Dans le worker, une exception déclenche la décision de retry ; un échec unrecoverable ou un compteur épuisé peut l'interdire.
  • max_retries: 3 = quatre tentatives au total.
  • Une exception recoverable directe ou seule emballée ignore max_retries avec strategy configurée ; pour plusieurs échecs, respecter la limite d'ordre décrite ci-dessus.
  • Sans failure_transport, ne compter sur aucune file de reprise implicite gérée par Messenger.
  • UnrecoverableMessageHandlingException saute les retries, pas la file d'échec.
  • Avec multiplier: 2, le délai de base croît exponentiellement ; multiplier: 1 serait constant avant jitter. max_delay vaut 0 par défaut.
  • messenger:failed:retry traite le message lui-même, depuis la file d'échec.

Fiche express

À mémoriser

À retenir en priorité
  1. Le retry doit cibler le travail restant.
  2. L'Envelope conserve l'historique de traitement.

À la fin de l'import échoué, savoir répondre à trois questions : qui a reçu l'exception, quelle politique autorise la suite et où retrouver le message ? Le navigateur qui lit l'article n'est pas le système de suivi de cette tâche.

Si tu dois retenir seulement 7 choses :

  • Synchrone : une HandlerFailedException remonte, sans retry.
  • max_retries: 3 = quatre tentatives, délais exponentiels.
  • max_delay vaut 0 par défaut : pas de plafond.
  • Unrecoverable… saute les retries, pas la file d'échec.
  • Échec unique, strategy configurée : Recoverable… force le retry au-delà du compteur ; retryDelay fixe le délai. Dans un ensemble mixte, une exception ordinaire précédente peut empêcher d'atteindre la recoverable.
  • Sans failure_transport, aucune copie de reprise Messenger n'est garantie.
  • messenger:failed:retry traite lui-même ; en script, un id.

Moyen mnémotechnique : « réessayer, abandonner, mettre de côté ».

sync → HandlerFailedException (getWrappedExceptions) ; async, strategy configurée, échec unique → Recoverable ? retry sans fin : Unrecoverable ? échec : max_retries (+1 tentative) ;
plusieurs erreurs emballées en 8.0.16 → parcourir dans l'ordre, s'arrêter à la première ordinaire avant d'appliquer la strategy ;
délai delay×multiplier^n, max_delay 0 ; échec → failure_transport ou perdu ; failed:retry traite lui-même, id hors interactif

Les middleware expliquent maintenant où placer les opérations autour du dispatch. Les événements Messenger montrent comment observer le retry sans le confondre avec un succès de handler.
