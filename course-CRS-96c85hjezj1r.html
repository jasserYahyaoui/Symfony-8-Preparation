Objectif

L'import produit maintenant un résultat, des diagnostics et un journal d'événements. Afficher chaque détail en permanence rendrait la commande difficile à utiliser. Nous allons garder un résumé normal et permettre un diagnostic plus précis à la demande, sans confondre silence, succès et conservation d'une trace.

L'essentiel

À comprendre

À retenir en priorité
  1. silent ajoute un niveau sous quiet.
  2. Les niveaux couvrent du silence au diagnostic détaillé.

La verbosité règle combien de détails la commande affiche, pas si son travail réussit. L'utilisateur choisit un niveau ; chaque message peut fixer un seuil minimal. Un message marqué VERBOSITY_VERBOSE devient visible à -v et aux niveaux supérieurs, sans devoir répéter le code pour chaque option.

Symfony 8.0 expose six niveaux, de --silent à -vvv. Le filtrage concerne les sorties gérées par Console : un echo direct contourne ce mécanisme.

Par exemple, le nombre de lignes lues dans articles.csv peut être un détail verbeux. Un échec d'import reste un échec même si cette ligne est masquée. Le nom DEBUG décrit ici un niveau de sortie Console, pas l'environnement dev, le réglage APP_DEBUG ou le débogage de GET /blog/42.

Le schéma

À retenir en priorité
  1. Un message verbose reste visible en debug.
  2. Le niveau demandé inclut les seuils inférieurs.

Output::write() compare le seuil demandé avec le niveau de la sortie. Si le niveau est insuffisant, il revient avant formatage et écriture ; les expressions passées en arguments PHP, elles, ont déjà été évaluées :

Bleu : traitement ; ambre : comparaison ; vert : résultat. Ce dessin suit un message VERBOSE, pas toutes les règles d'affichage des exceptions. Si construire ce message coûte cher, tester isVerbose() avant de le calculer : filtrer son écriture n'annule pas un calcul déjà effectué.

L'exemple : une command qui échoue

Exemple concret

À retenir en priorité
  1. quiet ne signifie pas silence total.
  2. silent masque également le diagnostic console.

Ce fragment se place dans le corps d'une commande qui reçoit $output, avec Symfony\Component\Console\Output\OutputInterface importé. Il isole un échec ordinaire du traitement d'import pour comparer les affichages :

$output->writeln('normal');
$output->writeln('verbose-only', OutputInterface::VERBOSITY_VERBOSE);
$output->writeln('quiet-level', OutputInterface::VERBOSITY_QUIET);
throw new \RuntimeException('boom');

Avec l'Application standard qui capture cette RuntimeException, une sortie Console avec canal d'erreur, et aucun listener qui remplace le résultat, les observations attendues sont :

Option normal verbose-only quiet-level erreur sur STDERR
aucune oui non oui oui
-q non non oui oui
--silent non non non non
-v, -vvv oui oui oui oui

Dans ces quatre variantes, l'exception de code 0 devient un statut d'échec 1. --silent ne la transforme pas en succès. Le message quiet-level n'est pas une erreur par son contenu : il traverse -q grâce au seuil explicitement demandé.

L'Application rend ses erreurs gérées au seuil QUIET, ce qui explique pourquoi elles restent visibles avec -q et disparaissent sous --silent. Mettre seulement <error> autour d'une écriture de seuil normal ne lui donne pas cette propriété.

Les six niveaux

À retenir en priorité
  1. Les répétitions augmentent le détail.
  2. Éviter une option debug parallèle inutile.

🌍 In Real Life

La situation : le rapport d'import du blog comporte un résumé, des détails et des annexes ; le lecteur choisit jusqu'où les afficher.

L’équivalent dans Symfony : profondeur choisie → niveau de verbosité ; niveau minimal d'une annexe → seuil du message.

Retour à la réalité technique : un niveau accepte les seuils inférieurs. La verbosité filtre les écritures Console, sans modifier la réussite métier ni le code de retour ; quiet et silent ne sont pas synonymes.

🧠 Comment le mémoriser : « Plus de détails, pas plus de succès. » Image mentale : un rapport déplié par couches. Question-réflexe : le niveau choisi atteint-il le seuil du message ?

⚠️ À ne pas confondre : verbosité Console et niveau de journalisation.

Les six constantes forment une échelle, pas six catégories étanches : un niveau plus élevé accepte les seuils inférieurs. Choisir le seuil selon l'utilité du message, et non selon son apparence :

Drapeau Constante Usage
--silent VERBOSITY_SILENT masque les écritures et erreurs gérées par Console
-q, --quiet VERBOSITY_QUIET aucun output normal
(défaut) VERBOSITY_NORMAL le message utile
-v VERBOSITY_VERBOSE information supplémentaire
-vv VERBOSITY_VERY_VERBOSE détail, messages non essentiels
-vvv VERBOSITY_DEBUG tout, traces d'exception comprises
  • Le seuil se passe en second argument de writeln() ($options), le troisième de write().
  • Quand le message coûte cher à calculer : if ($output->isVerbose()), et isSilent(), isQuiet(), isVeryVerbose(), isDebug().
  • Pas d'option --debug maison : les niveaux existent déjà.

Ce petit compte rendu s'utilise avec l'output reçu par la commande :

<?php
use Symfony\Component\Console\Output\OutputInterface;

function reportCount(OutputInterface $output, int $count): void
{
    $output->writeln('Éléments lus : '.$count, OutputInterface::VERBOSITY_VERBOSE);
}

Avec $count = 42, rien n'est écrit au niveau normal ; à -v, -vv ou -vvv, la ligne est Éléments lus : 42. Ce compteur ne dit pas que 42 opérations asynchrones ont été consommées : nommer ce qui a réellement été mesuré.

Pour un résumé coûteux, entourer son calcul d'un test isVerbose(). Ce prédicat accepte aussi les niveaux supérieurs ; isQuiet() et isSilent(), eux, testent leurs niveaux respectifs. Le rendu standard des exceptions peut déjà inclure une trace à partir de VERBOSE : ne pas réserver toute trace par principe au seul -vvv.

Même au niveau le plus détaillé, exclure secrets et données personnelles inutiles des diagnostics. La verbosity réduit l'affichage, pas la sensibilité d'un texte qui finit dans un terminal ou une capture de CI.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le filtre d'output n'évite pas le calcul préalable.
  2. Tester le niveau avant le travail coûteux.
  • Voir l’explication : --silent masque l'affichage Console, pas l'échec.

    --silent masque l'affichage Console, pas l'échec. Le code de sortie reste à vérifier. La journalisation est un mécanisme distinct : elle dépend des listeners, du logger et des handlers configurés ; l'option ne garantit pas à elle seule qu'une trace persistante sera conservée.

  • Voir l’explication : SHELL_VERBOSITY fixe le niveau globalement, mais -q et -v l'emportent sur lui.

    SHELL_VERBOSITY fixe le niveau globalement, mais -q et -v l'emportent sur lui. La variable vaut -2 pour --silent, -1 pour --quiet, 0, 1, 2, 3 pour les suivants. Ainsi, SHELL_VERBOSITY=1 seul affiche le message verbeux ; avec -q, plus rien d'autre que quiet-level.

  • Priorité des options de verbosité et repli d’environnement

    Application::configureIO() examine d'abord les options explicites, puis la variable d'environnement en repli. Dans cette sélection, --silent précède -q, qui précède les variantes verbeuses : ajouter -vvv à --silent ne rallume pas la sortie.

  • Voir l’explication : -q et --silent rendent aussi l'entrée non interactive

    -q et --silent rendent aussi l'entrée non interactive : interact() n'est pas appelée (voir Console component).

  • Quiet, interactivité et frontière Input/Output

    Un import qui dépend d'une confirmation ne doit donc pas supposer que quiet ne change que sa présentation. Cette adaptation relève de l'Application ; changer directement la verbosity d'un objet Output ne modifie pas magiquement l'objet Input associé.

  • Voir l’explication : Le niveau passé à writeln() est un seuil, pas un filter exact.

    Le niveau passé à writeln() est un seuil, pas un filter exact. Un message marqué VERBOSITY_VERBOSE s'affiche à -v, -vv et -vvv.

  • Voir l’explication : writeln() n'a que deux parameters

    writeln() n'a que deux parameters : le niveau est le second.

Application

🌍 In Real Life

La situation : l'équipe du blog calcule un bilan coûteux avant de découvrir que personne n'a demandé l'annexe détaillée.

L’équivalent dans Symfony : calcul du bilan → expression PHP passée à writeln() ; annexe masquée → filtrage par verbosité ; vérification préalable → isVerbose().

Retour à la réalité technique : les arguments sont évalués avant l'appel. Le seuil évite l'écriture, pas le calcul déjà effectué. Placer le calcul conditionnel dans le test de niveau évite ce coût inutile.

🧠 Comment le mémoriser : « Demander avant de calculer. » Image mentale : une annexe préparée puis jetée. Question-réflexe : le calcul se trouve-t-il avant ou dans la condition ?

⚠️ À ne pas confondre : filtrage de sortie et évaluation paresseuse des expressions.

À mémoriser

À retenir en priorité
  1. La variable fournit un réglage global.
  2. La ligne de command peut le surcharger.

Le même import peut désormais rester lisible au quotidien et fournir un diagnostic ciblé. Vérifier séparément la sortie, le code de retour, le mode interactif et la journalisation persistante réellement configurée.

Si tu dois retenir seulement 5 choses :

  • Six niveaux : --silent, -q, normal, -v, -vv, -vvv.
  • --silent tait même les erreurs ; -q seulement l'output normal.
  • Le niveau de writeln() est un seuil (second argument).
  • isVerbose() et ses variantes pour un message coûteux.
  • SHELL_VERBOSITY règle le défaut ; -q et -v l'emportent.

Moyen mnémotechnique : « Un seuil, pas un filter ».
