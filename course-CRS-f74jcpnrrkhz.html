Objectif

Savoir quelles recommandations du PHP-FIG Symfony implémente, lesquelles il suit, et laquelle il ne supporte que par un bridge.

L'essentiel

À comprendre

À retenir en priorité
  1. provide déclare des capacités virtuelles.
  2. Une entrée n'est pas nécessairement une PSR.

Symfony a trois rapports aux recommandations du PHP-FIG : il en implémente huit — il fournit le code derrière l'interface —, il en suit deux, des conventions, et il en ponte une, PSR-7, par un bridge. La source qui fait foi est la key provide du composer.json de symfony/symfony.

À retenir en priorité
  1. Le service container satisfait PSR-11.
  2. EventDispatcher satisfait PSR-14.

Les PSR implémentées

À comprendre

C'est quoi ?

Une PSR est une recommandation standardisée de l'écosystème PHP. Certaines définissent des interfaces : une implémentation fournit alors des objets respectant ce contrat, ce qui facilite leur substitution sans imposer le même framework partout.

À quoi ça sert ?

Une bibliothèque peut demander un logger ou un container standard plutôt qu'une classe concrète de Symfony. La compatibilité doit porter sur l'objet réellement fourni, pas seulement sur le nom du package installé.

Où dans Symfony ?

Le manifeste Symfony 8.0 déclare notamment ces implémentations :

  • PSR-3 : journalisation ; PSR-6 : pools et éléments de cache ; PSR-16 : interface de cache simplifiée.
  • PSR-11 : accès au container par get() et has() ; PSR-14 : distribution d'événements.
  • PSR-13 : liens web ; PSR-18 : client HTTP via l'intégration adaptée ; PSR-20 : horloge.

Les versions d'interfaces déclarées comptent : par exemple PSR-11 1.1|2.0 et PSR-6 2.0|3.0 dans ce manifeste. Cela ne signifie pas que chaque classe de chaque component implémente toutes ces interfaces.

Comment, étape par étape ?

  1. Identifier le rôle standard attendu par la bibliothèque.
  2. Vérifier la version du contrat et l'implémentation disponible.
  3. Fournir l'objet ou l'adaptateur approprié.
  4. Garder les dépendances métier explicites malgré la standardisation.

Exemple concret PHP

Cet extrait de point d'assemblage accepte tout container PSR-11, dont un container Symfony compatible :

<?php
use Psr\Container\ContainerInterface;
function containsService(ContainerInterface $container, string $id): bool
{
    return $container->has($id);
}

Aucune classe concrète Symfony n'est imposée par la signature. Contre-exemple : conclure que la compatibilité PSR-11 recommande d'injecter le container entier dans tous les services métier. Correction : distinguer interopérabilité du contrat et qualité de conception ; l'injection directe des dépendances reste préférable dans le cas ordinaire.

Le nom du package virtuel donne l'indice : psr/<nom>-implementation dans provide ⇒ implémentée ; absent ⇒ pas implémentée.

Les points d'attache standardisés d'une caisse permettent à plusieurs grues de la manipuler. Une interface PSR joue ce rôle : le client dépend de la forme du contrat, pas du nom de la class concrète.

Repère — Les deux autres familles de provide : No. Symfony contracts and HTTP-client interoperability contracts also appear. provide déclare des capacités virtuelles. Une entrée n'est pas nécessairement une PSR.

Les deux autres familles de `provide`

  • Cinq contrats Symfony — symfony/cache-implementation, event-dispatcher, http-client, service, translation : des abstractions publiées dans des packages minuscules. Une bibliothèque qui les exige fonctionne avec Symfony sans en dépendre.
  • Deux HTTPlug — php-http/client-implementation et php-http/async-client-implementation, déclarés à * : l'abstraction client qui précède PSR-18. HttpClient satisfait les deux.

Les PSR suivies

À comprendre

À retenir en priorité
  1. PSR-4 concerne l'autoloading.
  2. PSR-12 concerne les conventions de code.

C'est quoi ?

Une convention suivie n'est pas nécessairement une interface implémentée. PSR-4 décrit une correspondance d'autoload entre espaces de noms et fichiers ; PSR-12 concerne des règles de présentation du code. On ne crée pas un objet « implémentant PSR-4 » comme on implémente une interface de container.

À quoi ça sert ?

L'autoload évite d'écrire un require pour chaque classe. Des conventions de code communes facilitent la lecture. Ni l'un ni l'autre ne doit être confondu avec la liste des packages virtuels d'implémentation déclarés par Composer.

Où dans Symfony ?

Une application associe habituellement le préfixe App\ à src/. Les standards Symfony s'appuient sur les conventions PHP tout en documentant leurs choix propres. provide sert à déclarer des capacités de packages ; son absence pour une convention de style ne signifie pas que le projet ne la suit pas.

Comment, étape par étape ?

  1. Identifier le préfixe d'espace de noms.
  2. Lire son dossier associé dans Composer.
  3. Transformer le suffixe du nom de classe en chemin relatif.
  4. Vérifier nom de fichier et casse, notamment sur un système sensible à la casse.

Exemple concret JSON

Fragment à intégrer à la configuration Composer de l'application :

{
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}

App\Service\Mailer correspond à src/Service/Mailer.php. Contre-exemple : déplacer le fichier vers un dossier sans adapter la correspondance puis chercher une option provide pour réparer le chargement. Correction : modifier l'autoload et le régénérer dans le projet cible. Une convention suivie et une interface fournie répondent à deux problèmes différents.

Passage canonique conservé

Les PSR suivies

PSR-4 (autoloading) fait correspondre src/ au namespace App\ ; PSR-12 fonde les standards de codage. On ne « fournit » pas une convention : elles ne figurent pas dans provide.

Le cas PSR-7

À comprendre

À retenir en priorité
  1. HttpFoundation ne fournit pas directement PSR-7.
  2. Un contrat de messages immuables diffère de son modèle mutable.

C'est quoi ?

PSR-7 définit des interfaces de messages HTTP ; PSR-17 définit des factories, objets de création de ces messages. HttpFoundation utilise son propre modèle Request/Response et ne devient pas une implémentation PSR-7 parce qu'il traite également HTTP.

À quoi ça sert ?

Une bibliothèque peut exiger une Request PSR-7 alors que l'application manipule HttpFoundation. Un bridge convertit les représentations à cette frontière. Cela évite de réécrire toute l'application tout en respectant le contrat du composant externe.

Où dans Symfony ?

symfony/psr-http-message-bridge fournit les conversions. Pour produire des objets PSR-7 depuis HttpFoundation, il lui faut une implémentation PSR-7 et des factories PSR-17 adaptées. Le bridge n'est pas lui-même cette implémentation. Aucune bibliothèque supplémentaire n'est installée ou imposée par cet exemple conceptuel.

Comment, étape par étape ?

  1. Identifier le modèle exigé à la frontière.
  2. Fournir les factories nécessaires au bridge dans le sens HttpFoundation vers PSR-7.
  3. Convertir avant de transmettre l'objet.
  4. Respecter la différence de mutation : les méthodes PSR-7 de modification retournent un nouveau message, tandis que plusieurs opérations HttpFoundation modifient l'objet existant.

Exemple concret text

Application : HttpFoundation Request
Frontière : bridge + factories PSR-17
Bibliothèque destinataire : ServerRequestInterface PSR-7
Retour éventuel : conversion vers HttpFoundation Response

Contre-exemple : passer directement une Symfony\Component\HttpFoundation\Request à un argument Psr\Http\Message\ServerRequestInterface en supposant que les méthodes similaires suffisent. Correction : convertir avec le bridge configuré. Autre erreur : appeler une méthode PSR-7 with...() sans garder son résultat ; l'original reste inchangé. Le mot HTTP commun ne rend pas les contrats PHP interchangeables.

Passage canonique conservé

HttpFoundation n'implémente pas directement PSR-7 ni PSR-17. Son modèle Request/Response est mutable, tandis que PSR-7 définit des messages immuables. Connaître cette frontière suffit ici ; aucun package d'adaptation externe n'est enseigné.

Pièges d'examen

Piège à éviter

Conventions PSR, contrats implémentés et déclarations provide

HttpFoundation n'est pas une implémentation PSR-7. PSR-4 et PSR-12 sont des conventions suivies, pas des services déclarés dans provide. Le container satisfait Psr\Container\ContainerInterface et le dispatcher le contrat PSR-14. provide contient aussi des contrats Symfony, pas uniquement des PSR. Les versions prises en charge diffèrent selon le contrat.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Implémentées : PSR-3, 6, 11, 13, 14, 16, 18, 20.
  • Suivies : PSR-4 et PSR-12, absentes de provide.
  • PSR-7 / PSR-17 : bridge + implémentation tierce.
  • Container = PSR-11, dispatcher = PSR-14, sans adapter.
  • provide : 15 entrées — 8 psr/*, 5 contrats Symfony, 2 HTTPlug.
  • Versions : PSR-6 dès 2.0, PSR-11 dès 1.1.

Moyen mnémotechnique : « Implémenter, suivre, ponter ».
