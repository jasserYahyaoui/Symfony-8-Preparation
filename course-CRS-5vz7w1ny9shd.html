Objectif

Lire et écrire une valeur désignée par un path, et prévoir ce qui se passe quand ce path n'existe pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Les notations choisissent des cibles différentes.
  2. Les crochets ne sont pas décoratifs.

PropertyAccess lit et écrit une valeur désignée par un path : les crochets visent un index d'array, le point une property d'object. Le piège central : un path absent rend null sur un array, mais lève sur un object — deux défauts opposés, renversables par l'accessor builder.

Le schéma

À retenir en priorité
  1. Les deux défauts sont asymétriques.
  2. Le builder permet de les modifier.

L'exemple : une personne et ses enfants

Exemple concret

À retenir en priorité
  1. Un array utilise des index.
  2. Le point est réservé à la navigation de properties.
$propertyAccessor = PropertyAccess::createPropertyAccessor();

$propertyAccessor->getValue($person, 'firstName');
$propertyAccessor->setValue($person, 'children[0].firstName', 'Wouter');
// résout le setter ou l’accesseur magique selon les conventions de l’objet

if ($propertyAccessor->isWritable($person, 'children[0].firstName')) {
    // ...
}

Deux notations, deux cibles

À retenir en priorité
  1. L'écriture agit sur la donnée fournie.
  2. Il ne faut pas ignorer cette mutation.
Path Cible Résultat
a array NoSuchPropertyException, qui suggère [a]
[x] stdClass NoSuchIndexException : pas d'ArrayAccess

Écrire dans un array le modifie par référence : setValue($a, '[y]', 2) ajoute la key à $a. Les conventions d'accessors d'un object sont celles des forms (Module 07 — Formulaires).

Le path absent : deux comportements opposés

À retenir en priorité
  1. Le nullsafe traite null.
  2. Il ne désactive pas toute validation du path.
Cible Path absent Pour renverser
index d'array rend null enableExceptionOnInvalidIndex() → NoSuchIndexException
property d'object lève NoSuchPropertyException disableExceptionOnInvalidPropertyPath() → null

Le builder n'est pas la seule voie : new PropertyAccessor() prend les mêmes réglages en drapeaux — THROW_ON_INVALID_INDEX, THROW_ON_INVALID_PROPERTY_PATH, MAGIC_CALL —, et une application les fixe sous framework.property_access. Exécuté avec le seul drapeau THROW_ON_INVALID_INDEX : l'index absent lève, la property absente rend null.

Un maillon null est un troisième cas : person.firstname lève une UnexpectedTypeException, person?.firstname rend null.

Demander avant d'appeler

Piège à éviter

À retenir en priorité
  1. Le test peut avoir des effets de lecture.
  2. Ne pas supposer une inspection pure de metadata.
  3. isWritable() peut lire les getters intermédiaires sans appeler le setter final.

C'est quoi ?

PropertyAccess lit ou écrit une valeur à travers un property path : notation de navigation comme [profile][name] pour des tableaux ou profile.name pour des objets. Sur un objet, il peut utiliser un getter ou setter plutôt qu'un accès direct à une propriété.

À quoi ça sert ?

Un composant peut manipuler des structures différentes avec un même contrat d'accès. Cela ne transforme pas les getters en opérations sans effets : le parcours peut réellement appeler du code métier.

Où dans Symfony ?

isReadable() et isWritable() renseignent sur la possibilité d'accès. Ils ne sont pas des inspections purement statiques garanties sans exécution : la lecture d'un chemin et celle de ses éléments intermédiaires peuvent appeler des getters. Un getter qui interroge un service ou lève une exception conserve ce comportement.

Comment, étape par étape ?

  1. Choisir la notation selon la structure traversée.
  2. Distinguer une valeur nulle attendue d'un chemin erroné : par défaut, un index absent peut rendre null, alors qu'une propriété objet absente provoque une exception.
  3. Pour un index obligatoire, demander explicitement une exception avec le builder. Pour un segment vraiment optionnel, une notation null-safe exprime cette intention localement.
  4. Effectuer l'accès et traiter une erreur réelle ; une vérification préalable ne protège pas contre une modification concurrente et ne remplace pas la validation métier.

Exemple concret PHP

Avec PropertyAccess installé, un index manquant est une erreur de données, pas un null silencieux :

<?php
use Symfony\Component\PropertyAccess\PropertyAccess;

$accessor = PropertyAccess::createPropertyAccessorBuilder()
    ->enableExceptionOnInvalidIndex()
    ->getPropertyAccessor();
$data = ['profile' => ['name' => 'Ada']];
echo $accessor->getValue($data, '[profile][name]'), PHP_EOL;
$accessor->setValue($data, '[profile][name]', 'Grace');
echo $accessor->getValue($data, '[profile][name]'), PHP_EOL;

Les sorties attendues sont Ada puis Grace. Lire [profile][missing] avec cet accessor lèverait une NoSuchIndexException. Contre-exemple : remplacer tous les chemins par des segments null-safe pour dissimuler des noms de propriétés incorrects. Correction : réserver cette notation aux absences réellement autorisées.

__get() et __set() participent à l'accès magique usuel ; __call() demande une activation explicite. Pour une collection, les méthodes d'ajout et de retrait reconnues peuvent être préférées à une affectation brute. Ne pas présumer qu'un setValue() se réduit toujours à $object->property = $value ni qu'un test d'accessibilité est sans coût ou sans effets.

Passage canonique conservé

Demander avant d'appeler

isReadable() et isWritable() rendent un bool là où getValue() et setValue() lèveraient. Elles ne sont pas sans effet :

Appel Methods de l'object appelées
isReadable($person, 'firstName') getFirstName()
isWritable($person, 'firstName') aucune
isWritable($person, 'children[0].firstName') getChildren()

isReadable() lit le path entier ; isWritable() lit tout sauf le dernier maillon, qu'elle examine sans appeler le setter.

Les methods magiques

À retenir en priorité
  1. Les methods magiques n'ont pas toutes le même défaut.
  2. Configurer le comportement voulu.

__get() et __set() sont utilisées par défaut ; __call() doit être activée, enableMagicCall() : sans elle, une lecture qui ne passe que par __call() lève NoSuchPropertyException.

Pour une collection, le couple ajout/retrait l'emporte sur le setter, et seuls les éléments qui changent sont touchés : ['a'] → ['a', 'b'] appelle getChildren() puis addChild().

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le défaut null peut être renforcé.
  2. Le choix appartient à la configuration.
  • Voir l’explication : Un index d'array absent rend null ; une property d'object absente lève.

    Un index d'array absent rend null ; une property d'object absente lève. Les deux défauts sont opposés.

  • Voir l’explication : Les crochets ne sont pas décoratifs

    Les crochets ne sont pas décoratifs : ils choisissent la cible array.

  • Activation des méthodes magiques de PropertyAccess

    __get() marche seule ; __call() doit être activée.

  • Voir l’explication : isReadable() appelle le getter

    isReadable() appelle le getter — elle ne fait qu'éviter l'exception.

  • Voir l’explication : ? arrête sur null

    ? arrête sur null, pas sur une property absente.

Fiche express

À mémoriser

À retenir en priorité
  1. La mise à jour peut traiter seulement les différences.
  2. Le setter n'est pas toujours choisi.

Si tu dois retenir seulement 6 choses :

  • [index] pour un array, .property pour un object.
  • Absent : array → null, object → exception ; le builder renverse.
  • ? arrête sur un maillon null seulement.
  • isReadable() / isWritable() : un bool ; isReadable() appelle le getter.
  • __get() / __set() par défaut ; __call() sur activation.
  • Collection : ajout/retrait avant le setter.

Moyen mnémotechnique : « Crochet pour l'array, point pour l'object ».
