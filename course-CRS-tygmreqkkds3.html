Objectif

Séparer ce que le component HttpKernel fournit de ce que FrameworkBundle y ajoute. Le déroulé d'une Request et le catalogue des events sont traités dans le Module 03 — Architecture Symfony ; on regarde ici le partage des roles.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le component fournit les classes.
  2. Le bundle les enregistre et expose la configuration framework.

Le component HttpKernel est autonome : le contrat handle(), la class Kernel, les events, les resolvers, les exceptions HTTP. FrameworkBundle ne réécrit rien : il câble — listeners enregistrés, resolvers en services, arbre framework:, commands, AbstractController, MicroKernelTrait. Une question tranche : cela marche-t-il sans service container ? Oui → component.

Le schéma

À retenir en priorité
  1. HttpKernel fournit les mécanismes réutilisables.
  2. Le component n'exige pas FrameworkBundle.

L'exemple : le kernel d'une application

▣ Exemple concret

Revoir la règle : Le component fournit les classes.

namespace App;

use Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait;   // bundle
use Symfony\Component\HttpKernel\Kernel as BaseKernel;          // component

class Kernel extends BaseKernel
{
    use MicroKernelTrait;
}

Ce que le component fournit

Revoir la règle : HttpKernel fournit les mécanismes réutilisables.

HttpKernelInterface et son contrat handle(Request): Response ; l'abstract class Kernel, qui enregistre les bundles, construit le container et expose getEnvironment(), isDebug(), getProjectDir(), getCacheDir(), getLogDir() ; les huit events ; ControllerResolverInterface, ValueResolverInterface et leurs implémentations ; les exceptions HTTP. Avec cela seul, on écrit son propre framework.

Trois interfaces, et ce que chacune apporte

À retenir en priorité
  1. HttpKernelInterface définit handle().
  2. TerminableInterface ajoute le traitement après émission.

KernelInterface étend HttpKernelInterface : un Kernel porte handle() sans le déclarer.

Interface Ce qu'elle ajoute
KernelInterface dix-sept methods — boot(), shutdown(), registerBundles(), getBundle(), locateResource(), les accessors de directories… et handle() par inheritance
RebootableInterface reboot(?string $warmupDir): void
TerminableInterface terminate(Request, Response): void

Ce que FrameworkBundle ajoute

Revoir la règle : Le component fournit les classes.

Apport Effet
Listeners enregistrés RouterListener sur kernel.request, ErrorListener sur kernel.exception…
Resolvers en services tagués controller.argument_value_resolver, donc extensibles
Arbre framework: config/packages/framework.yaml
Commands bin/console debug:router, cache:clear…
Routes internes dont la prévisualisation /_error
AbstractController, MicroKernelTrait class de base, kernel sans files séparés

Les classes des listeners viennent du component ; leur enregistrement, du bundle.

MicroKernelTrait implémente registerBundles() et registerContainerConfiguration(), les deux methods restées abstraites dans Kernel, et appelle configureContainer() et configureRoutes() par réflexion, ce qui lui permet de lire la signature de configureContainer(). Que ces methods puissent être private ne doit rien à la réflexion : le trait est copié dans votre Kernel, qui appelle ses propres methods privées.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Le component fournit les classes.

Le component fonctionne sans le bundle. HttpKernel est autonome : le contrat handle(), la class Kernel, les events et les resolvers sont dans le component. On peut écrire un framework avec cela seul.

FrameworkBundle ne réécrit rien ; il câble. Listeners enregistrés, resolvers tagués comme services, arbre de configuration framework:, commands bin/console, routes internes. Chercher l'arbre de configuration dans le component, c'est ne pas le trouver.

AbstractController vient du bundle, pas du component — c'est le même partage. Le path le prouve : src/Symfony/Bundle/FrameworkBundle/Controller/AbstractController.php existe, le path équivalent sous src/Symfony/Component/HttpKernel/ n'existe pas.

Kernel porte handle() sans l'avoir déclaré. KernelInterface étend HttpKernelInterface ; chercher handle() dans la liste des methods de KernelInterface ne le donne pas.

Fiche express

◆ À mémoriser

Revoir la règle : Le component fournit les classes.

Si tu dois retenir seulement 6 choses :

  • Component : contrat, Kernel, events, resolvers ; il marche seul.
  • Bundle : il câble — listeners, framework:, bin/console.
  • Kernel : KernelInterface, RebootableInterface, TerminableInterface.
  • KernelInterface étend HttpKernelInterface → handle() hérité.
  • AbstractController et MicroKernelTrait : bundle.
  • Le trait implémente registerBundles() et registerContainerConfiguration().

Moyen mnémotechnique : « Le component sait faire, le bundle branche ».
