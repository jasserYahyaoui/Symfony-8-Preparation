Objectif

Le navigateur demande GET /blog/42. Avant de chercher l'article, il faut une application démarrée et un moteur capable de traiter sa Request. Ce sont deux responsabilités différentes, même si leurs noms contiennent tous deux « Kernel ».

Séparer ce que le component HttpKernel fournit de ce que FrameworkBundle y ajoute. Le déroulé d'une Request et le catalogue des events sont traités dans le Module 03 — Architecture Symfony ; on regarde ici le partage des roles.

L'essentiel

À comprendre

À retenir en priorité
  1. Le component fournit les classes.
  2. Le bundle les enregistre et expose la configuration framework.

Trois rôles, trois noms : HttpKernelInterface définit le contrat qui transforme une Request en Response ; HttpKernel exécute ce traitement ; la classe abstraite Kernel prépare l'application, ses bundles et son conteneur de services, puis délègue le traitement HTTP.

Un conteneur construit et fournit les services avec leurs dépendances. FrameworkBundle apporte l'intégration Symfony : configuration, définitions de services, listeners et resolvers enregistrés, commandes et classes d'assistance. Le component peut être utilisé sans ce bundle, mais pas sans ses propres dépendances. La classe Kernel utilise bien un conteneur : ce critère ne permet pas de distinguer component et bundle.

🌍 In Real Life

La situation : avant de traiter la commande 42, un restaurant doit être organisé ; pendant le service, un responsable coordonne chaque commande.

L’équivalent dans Symfony : préparer l’établissement → Kernel prépare l’application ; coordonner la commande → HttpKernel traite la Request ; bon et résultat préparé → objets Request et Response de HttpFoundation.

Retour à la réalité technique : Kernel gère notamment bundles et conteneur, puis délègue au service HTTP. HttpKernel orchestre événements, résolutions et appel du contrôleur. Le restaurant n’est pas reconstruit à chaque commande : compilation et instanciation ne sont pas synonymes.

🧠 Comment le mémoriser : « Préparer l’établissement, coordonner la demande. » Image mentale : plan d’ouverture à côté du bon 42. Question-réflexe : « Parle-t-on de l’application ou du traitement de cette Request ? »

⚠️ À ne pas confondre : HttpFoundation représente les échanges ; HttpKernel les orchestre. Une interface décrit un contrat, elle n’exécute rien.

Le schéma

À retenir en priorité
  1. HttpKernel fournit les mécanismes réutilisables.
  2. Le component n'exige pas FrameworkBundle.

Les contrats sont bleus et arrondis ; les classes, vertes et rectangulaires. Les pointillés vont du type spécialisé vers le contrat ou parent. Les noms Kernel, HttpKernel, KernelInterface et HttpKernelInterface appartiennent ici à Symfony\Component\HttpKernel ; App\Kernel est la classe du projet. Kernel et HttpKernel implémentent aussi TerminableInterface ; Kernel implémente en plus RebootableInterface.

Cette seconde vue montre des appels pleins et leurs retours, pas de l'héritage. Kernel::getHttpKernel() fait précisément $this->container->get('http_kernel'). Avec l'intégration FrameworkBundle, ce service utilise HttpKernel et ses collaborateurs injectés : EventDispatcherInterface, ControllerResolverInterface, RequestStack et ArgumentResolverInterface. Les deux noms de resolver dans le dessin désignent les objets qui satisfont ces contrats, pas les interfaces exécutées.

Chemin simplifié sans cache HTTP ni interruption : Kernel::handle() démarre l'application, puis délègue. HttpKernel diffuse kernel.request avant la résolution ; un listener comme RouterListener peut fournir _controller, ou un autre listener une Response immédiate. Les events kernel.controller et kernel.controller_arguments peuvent modifier le callable et ses arguments. Si le contrôleur ne retourne pas de Response, kernel.view doit en fournir une, sinon le traitement échoue.

Après kernel.response et kernel.finish_request, handle() retourne la réponse : il ne l'envoie pas. Le point d'entrée l'envoie, puis peut appeler terminate() ; ce dernier déclenche kernel.terminate, séparément de handle(). Une exception interceptée passe par kernel.exception ; sans réponse produite par un listener, elle est relancée. Le service optionnel http_cache peut intercepter une requête principale avant le chemin montré.

🌍 In Real Life

La situation : le responsable consulte la destination d’un bon, trouve le poste capable de le traiter, puis lui fournit les informations nécessaires.

L’équivalent dans Symfony : destination renseignée → attributs issus du routage ; poste identifié → callable fourni par ControllerResolver ; fiche préparée → valeurs fournies par ArgumentResolver. Le responsable → HttpKernel, qui appelle ses collaborateurs puis le contrôleur.

Retour à la réalité technique : ces flèches représentent des appels et retours, pas de l’héritage. Une réponse anticipée peut éviter les résolutions ; kernel.view intervient seulement sans Response retournée. Le retour de handle() n’est pas l’envoi réseau.

🧠 Comment le mémoriser : « Où, qui, avec quoi — puis appeler. » Image mentale : trois renseignements reviennent au même responsable. Question-réflexe : « Qui appelle réellement le contrôleur ? »

⚠️ À ne pas confondre : les resolvers ne s’appellent pas entre eux ; terminate() reste un appel séparé.

L'exemple : le kernel d'une application

Exemple concret

Ce fichier prépare le projet qui recevra /blog/42 ; ce n'est pas le contrôleur de l'article. Le parent fournit le cycle de vie de l'application, le trait complète les points de configuration attendus par ce parent.

namespace App;

use Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait;   // bundle
use Symfony\Component\HttpKernel\Kernel as BaseKernel;          // component

class Kernel extends BaseKernel
{
    use MicroKernelTrait;
}

🌍 In Real Life

La situation : un restaurant adapte un modèle d’organisation existant et y ajoute ses modalités d’ouverture ; ce dossier ne prépare aucun plat.

L’équivalent dans Symfony : modèle réutilisé → classe parente BaseKernel ; modalités complétées → méthodes apportées par MicroKernelTrait ; établissement particulier → App\Kernel.

Retour à la réalité technique : le trait compose des méthodes dans la classe du projet ; il n’est ni un objet autonome ni un contrôleur. L’héritage apporte le cycle de vie, tandis que le trait fournit notamment les implémentations de configuration attendues. Cette composition ne décrit pas l’ordre d’exécution d’une requête.

🧠 Comment le mémoriser : « Hériter du cadre, compléter la configuration. » Image mentale : dossier standard avec les pages du restaurant. Question-réflexe : « Cette méthode configure-t-elle l’application ou répond-elle au lecteur du billet ? »

⚠️ À ne pas confondre : App\Kernel et BlogController n’ont pas la même responsabilité.

Ce que le component fournit

Au moment où App\Kernel délègue la requête, le service http_kernel n'a pas besoin de connaître la classe métier Article. Il a besoin d'un dispatcher pour annoncer les étapes, d'un resolver pour obtenir un callable, puis d'un resolver d'arguments pour préparer son appel. Le contrat porte sur la transformation HTTP ; charger l'article reste une responsabilité de l'application ou d'une intégration explicitement configurée.

HttpKernelInterface et son contrat handle(Request): Response ; l'abstract class Kernel, qui enregistre les bundles, construit le container et expose getEnvironment(), isDebug(), getProjectDir(), getCacheDir(), getLogDir() ; les huit events ; ControllerResolverInterface, ValueResolverInterface et leurs implémentations ; les exceptions HTTP. Avec ces outils et leurs dépendances, on peut assembler son propre framework ; les classes disponibles ne constituent pas encore un câblage opérationnel.

🌍 In Real Life

La situation : disposer d’un système de bons et d’annonces permet d’organiser un service, mais ne dit pas où trouver les ingrédients.

L’équivalent dans Symfony : outils de coordination → classes et contrats du component HttpKernel ; raccordement des postes → collaborateurs injectés ; recherche du billet 42 → service applicatif ou intégration configurée.

Retour à la réalité technique : le component fournit des mécanismes HTTP réutilisables avec leurs dépendances. Leur présence ne constitue pas un assemblage opérationnel. HttpKernel ne connaît pas automatiquement une classe Article et le matching de l’URL ne prouve pas l’existence du billet.

🧠 Comment le mémoriser : « Les outils ne sont pas le service monté. » Image mentale : équipements disponibles, raccordements encore à faire. Question-réflexe : « Ai-je seulement une classe disponible, ou son instance et ses dépendances configurées ? »

⚠️ À ne pas confondre : orchestrer HTTP n’est pas accéder aux données métier.

Trois interfaces, et ce que chacune apporte

À retenir en priorité
  1. HttpKernelInterface définit handle().
  2. TerminableInterface ajoute le traitement après émission.

Pour /blog/42, un consommateur de HttpKernelInterface peut demander une réponse sans savoir comment les bundles ont été démarrés. Un outil qui redémarre l'application a besoin d'un autre contrat. Enfin, retourner la réponse n'autorise pas à supposer que terminate() existe sur toute implémentation de HttpKernelInterface : cette capacité est séparée.

KernelInterface étend HttpKernelInterface : l'interface hérite du contrat handle() sans le redéclarer. La classe abstraite Kernel, elle, implémente concrètement cette méthode et délègue au service HTTP.

Interface Ce qu'elle ajoute
KernelInterface dix-sept methods — boot(), shutdown(), registerBundles(), getBundle(), locateResource(), les accessors de directories… et handle() par inheritance
RebootableInterface reboot(?string $warmupDir): void
TerminableInterface terminate(Request, Response): void

🌍 In Real Life

La situation : savoir traiter une commande ne signifie pas savoir rouvrir l’établissement ni effectuer les opérations de fin de service.

L’équivalent dans Symfony : engagement à fournir un résultat → HttpKernelInterface ; gestion de l’établissement → KernelInterface ; capacité de redémarrage → RebootableInterface ; opérations de terminaison → TerminableInterface.

Retour à la réalité technique : ces interfaces déclarent des capacités distinctes. KernelInterface étend le contrat HTTP ; la classe Kernel l’implémente. Le contrat HTTP seul ne garantit pas terminate(). La terminaison n’est ni l’envoi de la réponse ni une garantie de travail durable en arrière-plan.

🧠 Comment le mémoriser : « Une capacité se vérifie, elle ne se devine pas. » Image mentale : badges de fonctions différents sur le même responsable. Question-réflexe : « Quelle interface garantit précisément la méthode appelée ? »

⚠️ À ne pas confondre : un badge représente ici un contrat de type, pas une autorisation de sécurité.

Ce que FrameworkBundle ajoute

Reprenons la requête : disposer de RouterListener dans les fichiers PHP ne le fait pas intervenir. L'intégration l'enregistre auprès du dispatcher ; pendant kernel.request, le résultat du matching de /blog/42 peut alors alimenter les attributs id, _route et _controller. Le resolver de contrôleur lit ensuite cette destination ; le routeur n'appelle pas l'action.

Apport Effet
Listeners enregistrés RouterListener sur kernel.request, ErrorListener sur kernel.exception…
Resolvers en services tagués controller.argument_value_resolver, donc extensibles
Arbre framework: config/packages/framework.yaml
Commands bin/console debug:router, cache:clear…
Routes internes dont la prévisualisation /_error
AbstractController, MicroKernelTrait class de base, kernel sans files séparés

Les classes des listeners viennent du component ; leur enregistrement, du bundle.

MicroKernelTrait implémente registerBundles() et registerContainerConfiguration(), les deux methods restées abstraites dans Kernel, et appelle configureContainer() et configureRoutes() par réflexion, ce qui lui permet de lire la signature de configureContainer(). Que ces methods puissent être private ne doit rien à la réflexion : le trait est copié dans votre Kernel, qui appelle ses propres methods privées.

🌍 In Real Life

La situation : une sonnerie existe en cuisine ; pour qu’elle soit utile, il faut la relier aux postes qui doivent réagir.

L’équivalent dans Symfony : équipement disponible → classe RouterListener du component ; raccordement → enregistrement par l’intégration FrameworkBundle ; annonce reçue → invocation du listener pendant kernel.request.

Retour à la réalité technique : FrameworkBundle fournit configuration et câblage, pas une seconde boucle HTTP. Une fois atteint, le routage alimente les attributes de la Request ; il n’appelle pas l’action. Une réponse plus précoce peut empêcher ce listener de s’exécuter.

🧠 Comment le mémoriser : « Présent ne veut pas dire branché. » Image mentale : sonnerie posée sur une étagère puis raccordée. Question-réflexe : « Le problème vient-il de la classe ou de son enregistrement ? »

⚠️ À ne pas confondre : _controller désigne la cible ; ControllerResolver fournit le callable. Les attributes de Request ne sont pas les attributs PHP #[...].

Pièges d'examen

Piège à éviter

  • Classe disponible contre service enregistré

    Pour diagnostiquer une requête qui n'atteint pas BlogController::show, demande d'abord si la classe nécessaire manque ou si son enregistrement manque. Ce diagnostic donne un sens pratique à la séparation suivante.

  • Voir l’explication : Le component fonctionne sans le bundle.

    Le component fonctionne sans le bundle. HttpKernel est autonome : le contrat handle(), la class Kernel, les events et les resolvers sont dans le component. On peut assembler un framework avec ses dépendances et un câblage explicite, sans FrameworkBundle.

  • Voir l’explication : FrameworkBundle fournit l'intégration et la configuration.

    FrameworkBundle fournit l'intégration et la configuration. Listeners enregistrés, resolvers tagués comme services, arbre de configuration framework:, commands bin/console, routes internes. Chercher l'arbre de configuration dans le component, c'est ne pas le trouver.

  • Voir l’explication : AbstractController vient du bundle

    AbstractController vient du bundle, pas du component — c'est le même partage. Le path le prouve : src/Symfony/Bundle/FrameworkBundle/Controller/AbstractController.php existe, le path équivalent sous src/Symfony/Component/HttpKernel/ n'existe pas.

  • Voir l’explication : Ne pas confondre interface et implémentation.

    Ne pas confondre interface et implémentation. KernelInterface hérite de la déclaration de handle() ; la classe Kernel contient une implémentation qui prépare l'application puis délègue. HttpKernel possède sa propre implémentation, qui coordonne les événements et les resolvers.

Application

À retenir en priorité
  1. Le component fournit les classes.
  2. Le bundle les enregistre et expose la configuration framework.
  3. HttpKernel fournit les mécanismes réutilisables.
  4. Le component n'exige pas FrameworkBundle.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Component : contrat, HttpKernel, Kernel, events et resolvers ; réutilisable sans FrameworkBundle, avec ses dépendances.
  • Bundle : il câble — listeners, framework:, bin/console.
  • Kernel : KernelInterface, RebootableInterface, TerminableInterface.
  • KernelInterface étend HttpKernelInterface → handle() hérité.
  • AbstractController et MicroKernelTrait : bundle.
  • Le trait implémente registerBundles() et registerContainerConfiguration().

Moyen mnémotechnique : « Le component sait faire, le bundle branche ».
