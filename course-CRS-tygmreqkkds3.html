Objectif

Séparer ce que le component HttpKernel fournit de ce que FrameworkBundle y ajoute. Le déroulé d'une Request et le catalogue des events sont traités dans le Module 03 — Architecture Symfony ; on regarde ici le partage des roles.

L'essentiel

À comprendre

À retenir en priorité
  1. Le component fournit les classes.
  2. Le bundle les enregistre et expose la configuration framework.

Trois rôles, trois noms : HttpKernelInterface définit le contrat qui transforme une Request en Response ; HttpKernel exécute ce traitement ; la classe abstraite Kernel prépare l'application, ses bundles et son conteneur de services, puis délègue le traitement HTTP.

Un conteneur construit et fournit les services avec leurs dépendances. FrameworkBundle apporte l'intégration Symfony : configuration, définitions de services, listeners et resolvers enregistrés, commandes et classes d'assistance. Le component peut être utilisé sans ce bundle, mais pas sans ses propres dépendances. La classe Kernel utilise bien un conteneur : ce critère ne permet pas de distinguer component et bundle.

Le schéma

À retenir en priorité
  1. HttpKernel fournit les mécanismes réutilisables.
  2. Le component n'exige pas FrameworkBundle.

Les contrats sont bleus et arrondis ; les classes, vertes et rectangulaires. Les pointillés vont du type spécialisé vers le contrat ou parent. Les noms Kernel, HttpKernel, KernelInterface et HttpKernelInterface appartiennent ici à Symfony\Component\HttpKernel ; App\Kernel est la classe du projet. Kernel et HttpKernel implémentent aussi TerminableInterface ; Kernel implémente en plus RebootableInterface.

Cette seconde vue montre des appels pleins et leurs retours, pas de l'héritage. Kernel::getHttpKernel() fait précisément $this->container->get('http_kernel'). Avec l'intégration FrameworkBundle, ce service utilise HttpKernel et ses collaborateurs injectés : EventDispatcherInterface, ControllerResolverInterface, RequestStack et ArgumentResolverInterface. Les deux noms de resolver dans le dessin désignent les objets qui satisfont ces contrats, pas les interfaces exécutées.

Chemin simplifié sans cache HTTP ni interruption : Kernel::handle() démarre l'application, puis délègue. HttpKernel diffuse kernel.request avant la résolution ; un listener comme RouterListener peut fournir _controller, ou un autre listener une Response immédiate. Les events kernel.controller et kernel.controller_arguments peuvent modifier le callable et ses arguments. Si le contrôleur ne retourne pas de Response, kernel.view doit en fournir une, sinon le traitement échoue.

Après kernel.response et kernel.finish_request, handle() retourne la réponse : il ne l'envoie pas. Le point d'entrée l'envoie, puis peut appeler terminate() ; ce dernier déclenche kernel.terminate, séparément de handle(). Une exception interceptée passe par kernel.exception ; sans réponse produite par un listener, elle est relancée. Le service optionnel http_cache peut intercepter une requête principale avant le chemin montré.

L'exemple : le kernel d'une application

Exemple concret

namespace App;

use Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait;   // bundle
use Symfony\Component\HttpKernel\Kernel as BaseKernel;          // component

class Kernel extends BaseKernel
{
    use MicroKernelTrait;
}

Ce que le component fournit

À comprendre

C'est quoi ?

Un component est une bibliothèque réutilisable : on peut appeler ses classes dans un programme PHP sans démarrer une application Symfony complète. Le component symfony/http-kernel fournit notamment un contrat pour transformer une Request en Response. Ces deux objets, fournis par HttpFoundation, représentent respectivement le message HTTP reçu et le message HTTP à renvoyer.

Trois noms proches désignent des choses différentes :

  • HttpKernelInterface est le contrat. Sa méthode handle(Request $request, int $type = self::MAIN_REQUEST, bool $catch = true): Response indique ce qu'un noyau HTTP doit permettre. Une interface n'exécute pas le traitement.
  • HttpKernel est une classe concrète qui organise ce traitement à l'aide d'events, de resolvers et d'un controller. Un event est un point de notification ; un listener est un traitement enregistré pour y réagir. Un resolver détermine soit le controller à appeler, soit les valeurs à lui transmettre. Le controller est le code chargé de traiter l'action demandée.
  • Kernel est une classe abstraite, également située dans le component. Elle organise le démarrage de l'application, les bundles et le service container, c'est-à-dire l'objet qui construit et fournit les services avec leurs dépendances. Elle délègue le traitement HTTP à un service implémentant HttpKernelInterface.

À quoi ça sert ?

Séparer ces responsabilités permet de réutiliser le traitement HTTP sans adopter toute la configuration de FrameworkBundle. On choisit directement HttpKernel pour un assemblage explicite ou un petit framework ; on utilise généralement une sous-classe de Kernel pour une application Symfony et sa configuration de services.

Autonome ne veut pas dire sans dépendances. HttpKernel utilise d'autres bibliothèques, notamment HttpFoundation et EventDispatcher. Cela signifie ici qu'il n'impose pas FrameworkBundle. La classe Kernel, bien que située dans un component, utilise un service container : « utilise un container » ne permet donc pas de décider « component ou bundle ».

Où dans Symfony ?

Les interfaces, les classes HttpKernel et Kernel, les resolvers et les exceptions HTTP se trouvent sous Symfony\Component\HttpKernel. Les huit noms d'events sont définis par KernelEvents : kernel.request, kernel.controller, kernel.controller_arguments, kernel.view, kernel.response, kernel.finish_request, kernel.exception et kernel.terminate.

Ils ne sont pas huit étapes systématiquement exécutées : kernel.view intervient si le controller n'a pas retourné une Response, kernel.exception sur le chemin d'une exception, et kernel.terminate lors de l'appel de terminaison. Le catalogue est fourni par le component ; les traitements abonnés dépendent de l'assemblage choisi.

Comment, étape par étape ?

  1. Construire une Request et indiquer son controller dans son attribute _controller. Un attribute de Request est une donnée attachée à l'objet ; ce n'est pas un attribute PHP #[...].
  2. Fournir à HttpKernel un dispatcher, qui diffuse les events, et un ControllerResolver, qui lit _controller.
  3. Fournir un ArgumentResolver. Ici, il trouve l'argument $name dans l'attribute name de la Request grâce à son resolver par défaut.
  4. Appeler handle(). Le controller produit une Response, puis le noyau la retourne après les notifications applicables.
  5. Dans un point d'entrée HTTP, envoyer cette Response avec send(), puis appeler terminate($request, $response). Le script de démonstration ci-dessous ne fait qu'afficher le contenu en ligne de commande.

Limites et échecs : aucun routage, service applicatif ou rendu Twig n'est installé par le simple new HttpKernel(...). Sans _controller ni listener capable de le déterminer, la résolution échoue. Sans listener de gestion d'erreur, une exception ne devient pas magiquement une jolie page HTML. De même, retourner une chaîne au lieu d'une Response échoue si aucun listener de kernel.view ne transforme cette valeur.

Exemple concret PHP

Placer ce script à la racine d'un projet disposant déjà de l'autoload Composer et des components Symfony 8.0 HttpKernel, HttpFoundation et EventDispatcher, avec leurs dépendances. Il ne nécessite ni FrameworkBundle ni une classe App\Kernel. PHP 8.4 est requis pour Symfony 8.0.

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\RequestStack;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Controller\ArgumentResolver;
use Symfony\Component\HttpKernel\Controller\ControllerResolver;
use Symfony\Component\HttpKernel\HttpKernel;

$request = Request::create('/bonjour');
$request->attributes->set('name', 'Ada');
$request->attributes->set(
    '_controller',
    static fn (string $name): Response => new Response(
        'Bonjour '.$name,
        200,
        ['Content-Type' => 'text/plain; charset=UTF-8'],
    ),
);

$kernel = new HttpKernel(
    new EventDispatcher(),
    new ControllerResolver(),
    new RequestStack(),
    new ArgumentResolver(),
);

$response = $kernel->handle($request);
echo $response->getStatusCode(), ' ', $response->getContent(), "\n";

Le résultat attendu est 200 Bonjour Ada. Le chemin /bonjour n'a pas été apparié à une route : nous avons posé _controller nous-mêmes. Le header text/plain indique que le contenu n'est pas du HTML.

Contre-exemple : remplacer _controller par une simple chaîne Bonjour Ada ne fournit pas un controller appelable. Correction : fournir une fonction, comme ci-dessus, qui construit et retourne la Response. Autre erreur : remplacer new HttpKernel(...) par new Kernel(...) ; Kernel est abstraite et ne se construit pas ainsi. Une application qui l'étend doit fournir ses méthodes abstraites, directement ou via MicroKernelTrait.

Cycle HTTP et utilisation autonome — Symfony 8.0.

Passage canonique conservé

HttpKernelInterface est le contrat handle(Request): Response ; HttpKernel est l'implémentation concrète qui orchestre les events et appelle les resolvers injectés pour produire une Response ; l'abstract class Kernel boote l'application, construit son container et expose getEnvironment(), isDebug(), getProjectDir(), getCacheDir() et getLogDir(). Le component reste utilisable sans FrameworkBundle, mais ses classes ne sont pas toutes sans dépendance : HttpKernel reçoit notamment un dispatcher et des resolvers. Avec ces APIs, on peut écrire son propre framework en fournissant le câblage.

Trois interfaces, et ce que chacune apporte

À retenir en priorité
  1. HttpKernelInterface définit handle().
  2. TerminableInterface ajoute le traitement après émission.

KernelInterface étend HttpKernelInterface : l'interface hérite du contrat handle() sans le redéclarer. La classe abstraite Kernel, elle, implémente concrètement cette méthode et délègue au service HTTP.

Interface Ce qu'elle ajoute
KernelInterface dix-sept methods — boot(), shutdown(), registerBundles(), getBundle(), locateResource(), les accessors de directories… et handle() par inheritance
RebootableInterface reboot(?string $warmupDir): void
TerminableInterface terminate(Request, Response): void

Ce que FrameworkBundle ajoute

À comprendre

C'est quoi ?

Un bundle est une unité d'intégration à l'application Symfony : il participe à sa configuration et à l'enregistrement de services. FrameworkBundle est le bundle qui assemble de nombreux mécanismes des components pour l'application. Un component fournit une bibliothèque réutilisable ; le bundle fournit son intégration au framework. Ce partage ne signifie ni « component sans dépendances » ni « bundle sans code propre ».

Le câblage consiste à créer les définitions de services, leur fournir leurs dépendances et enregistrer les traitements qui doivent réagir aux events. Par exemple, la classe RouterListener est dans le component HttpKernel ; quand le routage est activé, FrameworkBundle configure son service avec le routeur et la pile des Request. Le listener peut alors alimenter les attributes de la Request, dont _controller.

À quoi ça sert ?

FrameworkBundle évite de reconstruire manuellement l'assemblage du traitement HTTP dans chaque application. Il fournit notamment :

  • La configuration sous la clé framework, interprétée par son extension de configuration.
  • Des services de résolution du controller et de ses arguments. Un tag est une étiquette de configuration utilisée lors de la construction du container ; controller.argument_value_resolver permet de collecter les resolvers ordinaires.
  • Des commandes de diagnostic et de maintenance, comme debug:router et cache:clear, avec les dépendances requises.
  • AbstractController, une classe de base facultative qui propose des raccourcis protégés, utilisables depuis les méthodes d'une sous-classe.
  • MicroKernelTrait, un trait PHP qui fournit du code de configuration réutilisable à la classe du kernel applicatif.

On emploie cette intégration pour une application Symfony. On peut s'en passer pour un assemblage autonome de components, mais on assume alors explicitement les services et listeners nécessaires. Installer le bundle ne rend pas disponibles tous les packages facultatifs : un raccourci de rendu Twig exige aussi le moteur Twig et son intégration configurée.

Où dans Symfony ?

Les noms complets donnent les appartenances exactes :

  • Symfony\Component\HttpKernel\Kernel : la classe de base du component.
  • Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait : le trait fourni par le bundle.
  • Symfony\Bundle\FrameworkBundle\Controller\AbstractController : la classe de base facultative fournie par le bundle, pas par HttpKernel.

MicroKernelTrait implémente registerBundles() et registerContainerConfiguration(), les deux méthodes qui restent abstraites pour une sous-classe de Kernel. Il organise aussi la configuration des services et des routes. Sa configuration par défaut sait lire les fichiers du répertoire config : employer ce trait ne signifie donc pas « aucun fichier de configuration ».

Comment, étape par étape ?

  1. La classe applicative étend Kernel et incorpore MicroKernelTrait avec use. Ici, use dans la classe incorpore les méthodes du trait ; les use avant la classe importent seulement des noms PHP.
  2. Lors de l'initialisation, le trait fournit la liste des bundles. En Symfony 8.0, il lit config/bundles.php s'il existe ; à défaut de ce fichier, son implémentation enregistre FrameworkBundle. Si le fichier existe, il faut que son contenu active effectivement les bundles nécessaires pour l'environnement choisi.
  3. Le trait fournit registerContainerConfiguration() et fait intervenir configureContainer(). La configuration du bundle est interprétée et les services sont préparés.
  4. La configuration des routes fait intervenir configureRoutes(). Le routeur intégré pourra déterminer le controller associé à une URL.
  5. Lorsqu'une Request est traitée, Kernel délègue au service HTTP kernel configuré. Le bundle n'est pas une seconde boucle concurrente de traitement HTTP.

Dans l'implémentation 8.0, le trait utilise la réflexion pour examiner et appeler les méthodes de configuration. Le fait qu'une méthode du trait soit privée ne crée pas une méthode publique : elle fait partie de la classe qui utilise le trait. Il ne faut ni appeler ces méthodes privées depuis l'extérieur, ni présenter la réflexion comme un mécanisme d'injection automatique universel.

Exemple concret PHP

Voici le contenu complet de src/Kernel.php pour la forme conventionnelle d'une application dont l'autoload associe App\ à src/. Le projet doit déjà posséder FrameworkBundle 8.0, ses dépendances et sa configuration applicative. Ce fichier définit une classe : à lui seul, il ne reçoit pas une Request, ne crée aucune route et n'envoie aucune Response.

<?php
namespace App;

use Symfony\Bundle\FrameworkBundle\Kernel\MicroKernelTrait;
use Symfony\Component\HttpKernel\Kernel as BaseKernel;

class Kernel extends BaseKernel
{
    use MicroKernelTrait;
}

extends BaseKernel apporte le cycle de vie de l'application. use MicroKernelTrait fournit les méthodes de configuration manquantes. La classe applicative peut donc être concrète sans réécrire registerBundles() et registerContainerConfiguration(). Cet exemple conserve la forme existante du cours, mais en rend les dépendances et les limites explicites.

Contre-exemple : supprimer le trait de cette classe sans ajouter ces deux méthodes ne produit pas un micro-framework autonome ; PHP refuse une classe concrète qui laisse ces méthodes abstraites. Correction : rétablir le trait pour la forme Symfony conventionnelle, ou implémenter réellement les méthodes pour un assemblage choisi. Pour traiter une Request sans infrastructure de bundles, on peut aussi construire directement HttpKernel, comme dans le passage consacré au component.

Autre confusion : étendre AbstractController n'installe pas Twig et ne remplit pas automatiquement son accès aux services dans un objet construit à la main. Le bundle fournit les mécanismes d'intégration ; le service doit être configuré et ses dépendances disponibles.

Les classes des listeners viennent du component ; leur enregistrement, leurs services et leur configuration viennent de FrameworkBundle. Le bundle ne réimplémente donc pas HttpKernel::handle() : il compose le container et les abonnements qui rendent le chemin Symfony concret.

MicroKernelTrait implémente registerBundles() et registerContainerConfiguration(), les deux methods restées abstraites dans Kernel, et appelle configureContainer() et configureRoutes() par réflexion, ce qui lui permet de lire la signature de configureContainer(). Que ces methods puissent être private ne doit rien à la réflexion : le trait est copié dans votre Kernel, qui appelle ses propres methods privées.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le component fonctionne sans le bundle.

    Le component fonctionne sans le bundle. HttpKernel est autonome : le contrat handle(), la class Kernel, les events et les resolvers sont dans le component. On peut écrire un framework avec cela seul.

  • Voir l’explication : FrameworkBundle fournit l'intégration et la configuration.

    FrameworkBundle fournit l'intégration et la configuration. Listeners enregistrés, resolvers tagués comme services, arbre de configuration framework:, commands bin/console, routes internes. Chercher l'arbre de configuration dans le component, c'est ne pas le trouver.

  • Voir l’explication : AbstractController vient du bundle

    AbstractController vient du bundle, pas du component — c'est le même partage. Le path le prouve : src/Symfony/Bundle/FrameworkBundle/Controller/AbstractController.php existe, le path équivalent sous src/Symfony/Component/HttpKernel/ n'existe pas.

  • Voir l’explication : Ne pas confondre interface et implémentation.

    Ne pas confondre interface et implémentation. KernelInterface hérite de la déclaration de handle() ; la classe Kernel contient une implémentation qui prépare l'application puis délègue. HttpKernel possède sa propre implémentation, qui coordonne les événements et les resolvers.

Application

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Component : contrat, HttpKernel, Kernel, events et resolvers ; réutilisable sans FrameworkBundle, avec ses dépendances.
  • Bundle : il câble — listeners, framework:, bin/console.
  • Kernel : KernelInterface, RebootableInterface, TerminableInterface.
  • KernelInterface étend HttpKernelInterface → handle() hérité.
  • AbstractController et MicroKernelTrait : bundle.
  • Le trait implémente registerBundles() et registerContainerConfiguration().

Moyen mnémotechnique : « Le component sait faire, le bundle branche ».
