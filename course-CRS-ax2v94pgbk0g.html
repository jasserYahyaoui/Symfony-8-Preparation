Objectif

Attacher des constraints à une class PHP, et savoir jusqu'où la validation descend. Les scopes — property, accessor, class — sont traités dans Validation scopes.

L'essentiel

À comprendre

À retenir en priorité
  1. La descente n'est pas automatique.
  2. Valid et Cascade activent la validation imbriquée.

Les constraints d'une class se déclarent en attributes, YAML, XML ou PHP. La validation ne descend pas toute seule dans un object imbriqué : il faut #[Assert\Valid] ou #[Assert\Cascade]. Et les constraints d'un parent s'ajoutent à celles de l'enfant, sans jamais être remplacées.

Le schéma

À retenir en priorité
  1. Le path garde l'index de collection.
  2. La violation désigne ensuite la property imbriquée.

Bleu = travail du Validator ; ambre = activation de la cascade ; vert = résultat de ce chemin. Le dessin suppose une adresse présente et invalide. null ne déclenche pas la validation d'un objet absent : ajouter NotNull si sa présence est obligatoire. Les flèches ne sont pas de l'héritage PHP.

Le fil rouge : un auteur et son adresse

À retenir en priorité
  1. L'object racine et son adresse sont deux cibles.
  2. Déclarer la descente pour vérifier l'adresse.
use Symfony\Component\Validator\Constraints as Assert;

class Address
{
    #[Assert\NotBlank]
    public string $zipCode = '';
}

class Author
{
    #[Assert\NotBlank]
    #[Assert\Length(min: 3)]
    private string $name = 'Ada';

    public Address $address;      // sans Valid : l'adresse n'est pas validée

    public function __construct()
    {
        $this->address = new Address();
    }
}

Avec le mapping activé, cet auteur produit zéro violation malgré son code postal vide. Ajouter #[Assert\Valid] sur $address donne une violation address.zipCode. Le résultat vide initial signifie « aucune règle évaluée n'a échoué », pas « tous les objets accessibles sont valides ».

Les quatre formats de déclaration

À comprendre

À retenir en priorité
  1. Le mapping PHP utilise une method statique.
  2. Le standalone doit activer le loader correspondant.

C'est quoi ?

Un mapping de validation décrit quelles contraintes portent sur une classe, ses propriétés ou ses accessors. Les attributes placent cette description près de la déclaration PHP ; loadValidatorMetadata la construit dans une méthode statique. YAML et XML sont des formats externes de métadonnées.

À quoi ça sert ?

On peut séparer le contrat de validation du code qui déclenche le contrôle. Changer de format ne doit pas changer la règle voulue ; en revanche, une déclaration que le validator ne charge pas n'est jamais exécutée.

Où dans Symfony ?

Hors framework, le builder doit activer les loaders utilisés : enableAttributeMapping pour les attributes, addMethodMapping pour la méthode statique, ou les méthodes de chargement YAML/XML. Le validator sait lire une propriété privée via ses métadonnées ; il ne suit pas le mapping PropertyAccess d'un formulaire.

Comment, étape par étape ?

  1. Choisir le format qui convient à la classe.
  2. Déclarer la contrainte sur la cible exacte.
  3. Configurer le loader correspondant dans le validator autonome.
  4. Tester une valeur invalide pour confirmer que la règle est réellement chargée.

Exemple concret PHP

Avec Validator chargé, deux classes illustrent la même règle sans la déclarer deux fois sur la même classe :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Mapping\ClassMetadata;
use Symfony\Component\Validator\Validation;
final class AttributeLabel
{
    #[Assert\NotBlank]
    public string $text = '';
}
final class MetadataLabel
{
    public string $text = '';
    public static function loadValidatorMetadata(ClassMetadata $metadata): void
    {
        $metadata->addPropertyConstraint('text', new Assert\NotBlank());
    }
}
$attributes = Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator();
$methods = Validation::createValidatorBuilder()->addMethodMapping('loadValidatorMetadata')->getValidator();
var_dump(count($attributes->validate(new AttributeLabel())));
var_dump(count($methods->validate(new MetadataLabel())));

Chaque appel produit une violation. Contre-exemple : écrire la méthode sans static, ou oublier son loader hors framework. Correction : respecter sa signature statique et charger ce mapping. Activer plusieurs sources de métadonnées peut cumuler leurs contraintes ; cela ne signifie pas que la dernière efface les précédentes.

Passage canonique conservé
Format Où Hors framework, à activer
attributes sur la class enableAttributeMapping()
PHP loadValidatorMetadata(), statique addMethodMapping('loadValidatorMetadata')
YAML, XML config/validator/ addYamlMapping(), addXmlMapping()
  • Une property privée est lue sans accessor.
  • loadValidatorMetadata() non statique : StaticMethodLoader lève une MappingException, « …should be static. »

La validation ne descend pas toute seule

À retenir en priorité
  1. Valid vérifie l'object présent.
  2. Une constraint de présence traite null.
Déclaration Violations d'une adresse invalide
rien aucune
#[Assert\Valid] sur la property address.zipCode
#[Assert\Cascade] sur la class address.zipCode
#[Assert\Valid] sur un array d'adresses addresses[0].zipCode, addresses[1].zipCode
#[Assert\Valid], property à null aucune : NotNull en plus pour l'exiger
  • Cascade décide d'après le type déclaré, pas le contenu découvert : par exemple Address, ?Address et array sont éligibles. Un tableau d'adresses typé array est donc parcouru ; ses éléments scalaires ne sont pas des objets à valider. Une propriété sans type, mixed ou string n'est pas sélectionnée automatiquement. Les unions et intersections suivent les règles de ClassMetadata::canCascade(). exclude: ['address'] retire une propriété ; il n'a pas d'option groups — new Assert\Cascade(groups: ['A']) : « Unknown named parameter $groups ».
  • Valid sans groupes explicites active la cascade pour le groupe demandé : validé avec le groupe Registration, il descend et transmet ce group — une Address dont street porte NotBlank(groups: ['Registration']) signale address.street, pas address.zipCode.

L'inheritance fusionne, il ne remplace pas

Piège à éviter

À retenir en priorité
  1. L'inheritance cumule les constraints.
  2. Les groups permettent de séparer leurs usages.

C'est quoi ?

L'héritage des métadonnées de validation conserve les contraintes du parent et y ajoute celles de l'enfant. Redéclarer une propriété ou une contrainte dans une sous-classe ne signifie pas que les règles du parent sont annulées.

À quoi ça sert ?

Un contrat de base continue à être respecté par ses spécialisations. En contrepartie, on ne peut pas assouplir une règle héritée simplement en écrivant une autre règle sur le même champ. Si les scénarios diffèrent, il faut concevoir leurs groupes ou leurs modèles explicitement.

Où dans Symfony ?

Les métadonnées peuvent provenir d'attributes, d'une méthode statique loadValidatorMetadata, de YAML ou de XML. Hors FrameworkBundle, le builder doit activer les loaders utilisés, notamment enableAttributeMapping pour les attributes. Validator peut lire une propriété privée via ses métadonnées : cela ne suit pas le même contrat d'accessors que le mapping d'un formulaire.

Comment, étape par étape ?

  1. Identifier les contraintes déjà présentes sur la classe parente.
  2. Ajouter uniquement les règles réellement supplémentaires dans l'enfant.
  3. Activer le mapping correspondant dans le validator autonome.
  4. Tester une valeur qui échoue au parent et une autre qui ne viole que la spécialisation.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

class BaseLabel
{
    #[Assert\NotBlank]
    public string $text = '';
}

class DetailedLabel extends BaseLabel
{
    #[Assert\Length(min: 5)]
    public string $text = '';
}

$value = new DetailedLabel();
$value->text = 'abc';
$violations = Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator()->validate($value);
var_dump(count($violations));

On attend une violation de longueur pour abc ; la règle NotBlank du parent existe toujours. Contre-exemple : redéclarer NotBlank dans l'enfant pour « conserver » l'ancienne règle : on peut produire deux violations équivalentes. Correction : laisser l'héritage la transmettre. Valider un objet contenu dans une propriété demande par ailleurs une cascade adaptée, telle que Valid ; l'héritage et la descente dans le graphe sont deux mécanismes distincts.

Passage canonique conservé

Parent NotBlank, enfant Length(min: 5) : 'abc' échoue sur Length, et une valeur vide sur les deux. La même constraint redéclarée dans l'enfant produit deux violations identiques. Cela ne se désactive pas ; seuls des groups différents séparent le parent de l'enfant.

Contraindre une class qu'on ne peut pas modifier

À retenir en priorité
  1. La class d'origine peut rester inchangée.
  2. Le mapping externe doit être effectivement enregistré.

#[ExtendsValidationFor(Product::class)], sur une class séparée, ajoute ses constraints à celles de Product. Hors framework, le lien se déclare aussi : addAttributeMappings([Product::class => [MyProductValidation::class]]) — l'attribute seul n'a aucun effet.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Cascade s'appuie sur les types des properties.
  2. Un object contenu ne suffit pas sans type adapté.
  • Voir l’explication : Sans Valid ni Cascade, l'object imbriqué est ignoré

    Sans Valid ni Cascade, l'object imbriqué est ignoré — une validation qui passe à tort.

  • Voir l’explication : Valid n'impose pas la présence de l'object

    Valid n'impose pas la présence de l'object : null passe.

  • Voir l’explication : Redéclarer une constraint dans la fille ne remplace pas celle du parent

    Redéclarer une constraint dans la fille ne remplace pas celle du parent : les deux s'appliquent, et le comportement ne se désactive pas.

  • Voir l’explication : loadValidatorMetadata() est statique

    loadValidatorMetadata() est statique ; non statique, elle lève une MappingException.

  • Voir l’explication : Cascade ne regarde pas seulement la valeur d'une propriété

    Cascade ne regarde pas seulement la valeur d'une propriété : une propriété sans type contenant un objet n'est pas sélectionnée ; une propriété typée array contenant des objets peut l'être.

  • Voir l’explication : Valid sans groupes explicites ne se limite pas à Default

    Valid sans groupes explicites ne se limite pas à Default : il transmet le groupe demandé. Avec Valid(groups: ['Registration']), la cascade est elle-même sélectionnée par ces groupes.

Fiche express

À mémoriser

À retenir en priorité
  1. Valid transmet le group demandé.
  2. Les constraints imbriquées doivent appartenir à ce group.

Si tu dois retenir seulement 7 choses :

  • Quatre formats : attributes, YAML, XML, PHP statique.
  • La validation ne descend pas : #[Valid] ou #[Cascade].
  • Valid : null passe ; il transmet le group demandé.
  • Cascade : types déclarés éligibles, dont array, exclude, pas de groups.
  • Parent et enfant fusionnent ; une constraint redéclarée compte deux fois.
  • loadValidatorMetadata() non statique : MappingException.
  • #[ExtendsValidationFor] pour une class qu'on ne peut pas modifier.

Moyen mnémotechnique : « Déclarer, Descendre, Hériter » — et rien ne descend sans qu'on le dise.
