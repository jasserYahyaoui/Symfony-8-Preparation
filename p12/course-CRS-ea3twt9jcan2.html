Objectif

Sur GET /blog/42?limit=5, le contrôleur reçoit des valeurs qui viennent de trois endroits différents : la Request elle-même, l'identifiant 42 du chemin et la limite 5 de la query string. Ce cours répond à une seule question : d'où vient chaque valeur, et qui la fournit à mon code ?

Le modèle des sacs appartient au Module 02 — Fondamentaux HTTP, le component lui-même au Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Le type déclenche le resolver.
  2. Dans un service durable, utiliser RequestStack.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Votre code a besoin du contexte HTTP, mais il n'a pas accès aux variables globales $_GET ou $_POST. Symfony les enveloppe dans un objet Request et doit donc vous dire comment le récupérer.
  • Le piège de fond. Il existe deux chemins différents, selon que vous êtes dans un contrôleur ou dans un service. Les confondre est l'erreur classique de certification.
  • Ce que l'auteur veut que vous compreniez. Dans un contrôleur, Symfony vous donne la Request pendant l'appel. Dans un service, vous consultez la pile des requêtes quand vous en avez besoin.
  • Pourquoi c'est à l'examen. Les questions portent presque toujours sur cette frontière (résolution d'argument ≠ autowiring), sur RequestStack (courante, principale, parente, session) et sur getPayload().

Le schéma

La Request est un objet qui contient toutes les données HTTP reçues. Ce cours la suit en trois étapes :

La Request
   ├─ 1. Comment l'obtenir ?       → contrôleur / RequestStack
   ├─ 2. Où est l'info de l'URL ?  → attributes (route), query (?limit=5)
   └─ 3. Où est l'info du corps ?  → request (formulaire) ou JSON
                                      └─ getPayload() choisit entre les deux

Commençons par le chemin d'exécution complet de GET /blog/42?limit=5.

Nous allons zoomer sur deux cases : ArgumentResolver (contrôleur) et ce qui se passe quand c'est un service qui veut la Request.

L'exemple : une route à parameter

Exemple concret

On met les trois étapes dans un seul mini-contrôleur : on obtient la Request (1), on lit une valeur de route (2) et une valeur de query string (2). Le corps (3) vient plus loin.

Code minimal d'abord : un seul contrôleur, une seule route.

use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LuckyController
{
    #[Route('/lucky/number/{max}', requirements: ['max' => '\d+'])]
    public function number(Request $request, int $max): Response
    {
        $limit = $request->query->getInt('limit', 10);   // ?limit=5
        return new Response(sprintf('max=%d, limit=%d', $max, $limit));
    }
}

Pour /lucky/number/42?limit=5, le résultat est max=42, limit=5.

Avant / après, pour visualiser l'origine de chaque valeur :

/lucky/number/42?limit=5
              │  │     │
              │  │     └── query string  → $request->query   (lu explicitement)
              │  └──────── {max}         → attributes['max'] → argument $max
              └─────────── chemin reconnu par le routeur

Ce que Symfony voit dans number(Request $request, int $max) :

Argument Ce que Symfony cherche Qui le fournit
Request $request un argument typé Request le RequestValueResolver
int $max un attribut de Request nommé max le resolver d'attributs
(rien pour limit) — personne : on le lit nous-mêmes dans query

La route ne mappe pas automatiquement les paramètres de la query string vers les arguments.

🌍 In Real Life

La situation : le bon porte le numéro demandé et une note complémentaire. Lire le numéro ne revient pas à lire toutes les notes.

L’équivalent dans Symfony : numéro extrait de la destination → {max} dans les attributes ; note après ? → limit dans query ; lecture explicite de la note → query->getInt('limit', 10).

Retour à la réalité technique : pour /lucky/number/42?limit=5, les deux valeurs viennent de sources distinctes. Le requirement \d+ contraint le matching du segment ; il ne mappe pas la query string, ne valide pas toutes les règles métier et ne charge aucune donnée du blog.

🧠 Comment le mémoriser : « Même URL, tiroirs différents. » Image mentale : numéro et note dans deux cases du bon. Question-réflexe : « Cette valeur vient-elle du chemin reconnu ou de la query string ? »

⚠️ À ne pas confondre : obtenir un entier ne garantit pas qu’il soit acceptable pour le métier.

L'obtenir

Où en est-on ? Étape 1 sur 3 : avant de lire la moindre donnée HTTP, il faut déjà avoir la Request entre les mains. Un contrôleur et un service n'y arrivent pas de la même façon ; c'est ce que cette partie sépare.

1. Dans un contrôleur : pourquoi Symfony peut-il mettre une Request dans $request ?

Écrivons le contrôleur le plus simple possible :

public function index(Request $request): Response
{
}

Il y a ici un mystère : personne n'a écrit $controller->index($request). Qui appelle l'action, et d'où sort $request ?

Symfony doit appeler index(...). Avant de le faire, il inspecte la signature :

Je dois appeler index(Request $request)
        ↓
Je lis la liste des arguments demandés
        ↓
Je vois un argument de type Request
        ↓
RequestValueResolver sait fournir ce type
        ↓
il donne la Request actuellement traitée
        ↓
l'action est appelée avec cette Request

Ce mécanisme s'appelle la résolution d'argument (argument resolution). Le composant qui l'orchestre est l'ArgumentResolver ; le resolver spécialisé pour ce type est RequestValueResolver (dans le câblage standard).

Trois questions que l'on se pose naturellement :

Pourquoi le nom est-il libre ? Parce que Symfony regarde le type, pas le nom de variable. Request $request, Request $req et Request $toto fonctionnent de la même façon.

Symfony crée-t-il une nouvelle Request ? Non. Il fournit la Request qu'il est déjà en train de traiter. Une seule, celle de l'appel en cours.

Est-ce de l'autowiring ? Non, et c'est le point que le programme veut vous faire retenir. Comparons :

┌───────────────────────────────────────┐   ┌───────────────────────────────────────┐
│              CONTRÔLEUR               │   │                SERVICE                │
├───────────────────────────────────────┤   ├───────────────────────────────────────┤
│ public function index(                │   │ public function __construct(          │
│     Request $request                  │   │     RequestStack $requestStack        │
│ )                                     │   │ )                                     │
├───────────────────────────────────────┤   ├───────────────────────────────────────┤
│ Qui intervient ?                      │   │ Qui intervient ?                      │
│  → l'ArgumentResolver                 │   │  → le conteneur de services           │
│  → RequestValueResolver               │   │  → l'autowiring                       │
├───────────────────────────────────────┤   ├───────────────────────────────────────┤
│ Quand ?                               │   │ Quand ?                               │
│  → à CHAQUE appel de l'action         │   │  → une fois, à la construction        │
│                                       │   │    du service                         │
├───────────────────────────────────────┤   ├───────────────────────────────────────┤
│ Ce que je reçois                      │   │ Ce que je reçois                      │
│  → LA Request de cet appel            │   │  → la pile RequestStack               │
│                                       │   │    (pas une Request figée)            │
├───────────────────────────────────────┤   ├───────────────────────────────────────┤
│ Mécanisme                             │   │ Mécanisme                             │
│  = résolution d'argument              │   │  = service injecté                    │
│                                       │   │    puis CONSULTÉ au moment utile      │
│                                       │   │    getCurrentRequest()                │
└───────────────────────────────────────┘   └───────────────────────────────────────┘

Pourquoi la mauvaise réponse semble plausible : dans les deux cas on écrit un type dans une signature, donc on croit qu'une seule mécanique (l'autowiring) est à l'œuvre. Le contrôleur est résolu argument par argument, à chaque appel ; le service est construit par le conteneur, avec ses dépendances.

2. Dans un service : pourquoi RequestStack et pas Request ?

Un service est créé par le conteneur, puis réutilisé. Les services sont partagés par défaut dans leur conteneur, mais leur durée de vie n'est pas universellement « une fois pour toutes » : elle dépend du conteneur et de la configuration. La requête courante, elle, change (autre requête, sous-requête, absence totale de requête en console).

Si on figeait une Request dans le constructeur, on risquerait de conserver une ancienne requête. Donc on garde le moyen de la retrouver :

use Symfony\Component\HttpFoundation\RequestStack;

final class LocaleReader
{
    public function __construct(private RequestStack $requestStack)
    {
    }

    public function locale(): ?string
    {
        return $this->requestStack->getCurrentRequest()?->getLocale();
    }
}

?-> : hors HTTP (commande console), getCurrentRequest() peut rendre null.

3. Pourquoi une pile ?

Symfony peut traiter une requête pendant une autre : c'est la sous-requête (par exemple un fragment de page rendu séparément).

RequestStack  (le dessus = ce qui est traité maintenant)

┌─────────────────────────────┐
│ GET /fragment/menu          │ ← Current Request  (sous-requête)
├─────────────────────────────┤
│ GET /page                   │ ← Main Request  ET  Parent Request
└─────────────────────────────┘

Avec une seule requête sur la pile :

┌─────────────────────────────┐
│ GET /page                   │ ← Current = Main
└─────────────────────────────┘          Parent = null
Méthode Question posée Dans une sous-requête /fragment/menu Sur la requête principale /page
getCurrentRequest() Que traite-t-on maintenant ? /fragment/menu /page
getMainRequest() Qui a démarré tout ? /page /page
getParentRequest() Qui a déclenché la courante ? /page null
getSession() Session de la requête courante ? session, si elle existe session, si elle existe

Pourquoi getCurrentRequest() et getMainRequest() peuvent-elles différer ? Uniquement quand on est dans une sous-requête. Sur une requête simple, elles rendent la même Request.

getSession() ne rend pas null quand il n'y a pas de session : elle lève une SessionNotFoundException.

🌍 In Real Life

La situation : un poste reçoit le bon traité ; un autre consulte le porte-bons au moment utile. Garder la première fiche toute la journée risquerait de conserver une ancienne demande.

L’équivalent dans Symfony : bon remis à l’action → RequestValueResolver fournit la Request ; porte-bons consultable → service RequestStack ; fiche au sommet → requête courante, éventuellement une sous-requête.

Retour à la réalité technique : la pile décrit un contexte changeant, pas une file de tâches. Elle peut être vide ; la principale et la parente ne sont pas toujours la courante. Une Request d’action est résolue pour l’appel, non construite comme service applicatif par autowiring.

🧠 Comment le mémoriser : « Consulter maintenant, ne pas figer hier. » Image mentale : fiche du dessus qui change. Question-réflexe : « Ai-je besoin de la requête courante, principale ou parente ? »

⚠️ À ne pas confondre : service partagé dans son conteneur ne signifie pas contexte HTTP immuable.

Les parameters de route

À retenir en priorité
  1. Réordonner les arguments ne change pas la correspondance.
  2. Renommer un argument impose de vérifier le parameter de route.

Où en est-on ? Étape 2 sur 3 : on a la Request, on veut maintenant lire l'information portée par l'URL. Le routeur a déjà fait un travail avant l'appel du contrôleur : il a rangé les morceaux du chemin dans $request->attributes. Cette partie montre comment ils deviennent des arguments de l'action.

Pourquoi $id reçoit-il 42 ? Suivons GET /blog/42 pas à pas :

GET /blog/42
     ▼
RouterListener appelle le matcher
     ▼
le routeur reconnaît /blog/{id} et obtient  id = "42"
     ▼
RouterListener ajoute ce résultat à $request->attributes
     attributes = ['id' => '42', '_route' => ..., '_controller' => ...]
     ▼
ArgumentResolver : l'action demande $id
     ▼
le resolver d'attributs cherche un attribut nommé « id »
     ▼
show(..., $id = 42)

Ce qu'il faut voir :

  • id vaut la chaîne "42" avant les conversions éventuelles (int $id la convertit).
  • L'appariement se fait sur le nom de l'argument, jamais sur la position.
  • Aucune requête en base : le resolver d'attributs lit seulement $request->attributes. Le scénario principal consulte explicitement ArticleCatalog en mémoire dans l'action.
  • Une intégration Doctrine configurée peut résoudre une entité avant l’action ; ce comportement appartient au bridge, pas à HttpKernel seul, et l’ORM reste hors du programme étudié.

Avant / après un renommage, route /post/{year}/{slug} :

show(string $slug, int $year)   ← ordre inversé : fonctionne (nom = clé)
show(string $s,    int $y)      ← renommés : plus d'attribut « s » ni « y »
                                  → casse, sauf autre resolver ou valeur par défaut

attributes contient aussi _route et _controller.

🌍 In Real Life

La situation : le responsable recopie « numéro : 42 » sur le bon ; le poste cherche la case « numéro », pas la première case disponible.

L’équivalent dans Symfony : case renseignée après orientation → RouterListener ajoute id: '42' aux attributes ; recherche par étiquette → resolver d’attributs associé au nom $id ; consultation ultérieure du catalogue → appel métier distinct.

Retour à la réalité technique : l’appariement repose sur le nom, non sur la position. Renommer $id rompt cette correspondance, sauf autre source de valeur. Une intégration d’entité exige son resolver et son mapping configurés ; le routeur ne réalise pas cette lecture.

🧠 Comment le mémoriser : « L’étiquette relie, la place ne décide pas. » Image mentale : cases réordonnées dont les étiquettes restent identiques. Question-réflexe : « Quel attribute porte exactement le nom de cet argument ? »

⚠️ À ne pas confondre : attributes de la Request = données d’exécution ; attribut PHP #[Route] = métadonnée de configuration.

La suite précise comment ces valeurs et les services sont préparés dans les argument value resolvers.

Les parameters de route sont des notes agrafées au dossier par le bureau de routing. Les chercher dans query revient à ouvrir le tiroir des informations de l'URL après le point d'interrogation : ce n'est pas la même origine.

Body et query string

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.

Où en est-on ? Étape 3 sur 3 : l'URL n'est pas la seule source de données. Un POST (inscription, formulaire, appel d'API) envoie aussi un corps. La Request sait le lire : $request->query pour ce qui suit le ?, et la méthode getPayload() pour le corps. getPayload() n'est donc pas un autre sujet : c'est une méthode de la Request, qui sert à lire le corps du POST. Elle existe parce que le corps arrive sous deux formats possibles (formulaire ou JSON) et qu'on veut une seule façon de le lire.

Pourquoi deux sources ? Une URL transporte des données (?limit=5) ; un POST en transporte d'autres dans son corps (formulaire ou JSON). Chacune a son sac :

POST /register?ref=newsletter
Content-Type: application/x-www-form-urlencoded

email=a@b.c

?ref=newsletter   → $request->query     (query string)
email=a@b.c       → $request->request   (corps de formulaire)
corps JSON brut   → pas dans ->request : il faut le décoder

La consultation de /blog/42 n'utilise que query (limit=5) et n'a pas besoin de body. Le POST d'inscription ouvre une autre branche : formulaire encodé ou JSON selon le client.

getPayload() répond à : « Donne-moi les données du corps, quel que soit le format ». Elle procède dans cet ordre :

getPayload()
   │
   ├─ $request->request non vide ? ──► oui : un CLONE de ce sac (JSON ignoré)
   │
   ├─ corps vide ? ───────────────────► oui : InputBag vide
   │
   └─ sinon : décoder le JSON
          ├─ JSON valide qui donne un array ──► les données décodées
          └─ JSON invalide, ou pas un array ──► JsonException

Bleu = données retournées ; ambre = sélection ordonnée. Le JSON {} ou [] donne aussi un bag vide : « vide » ne signifie pas nécessairement « aucun body ».

Points d'attention :

  • Le formulaire l'emporte sur le JSON : pas de fusion.
  • Un JSON mal formé lève ; il ne devient jamais un sac vide.
  • Un body vide, ou un JSON {} / [], donne un sac vide.
  • getPayload() ne valide pas l'adresse e-mail, ne soumet pas un Form Symfony et ne lit pas la query string.

🌍 In Real Life

La situation : après avoir lu le billet, le lecteur envoie son inscription. Le guichet dispose soit de champs déjà transcrits, soit d’un document à décoder ; lire le document ne certifie pas son contenu.

L’équivalent dans Symfony : champs disponibles → sac request non vide, cloné par getPayload() ; document absent → InputBag vide ; document restant → décodage du body JSON.

Retour à la réalité technique : la sélection est ordonnée, sans fusion avec la query string ni avec une seconde source JSON. Un JSON invalide ou non décodable en tableau déclenche une exception. Ce choix d’entrée ne soumet pas un Form Symfony et ne valide pas une adresse e-mail.

🧠 Comment le mémoriser : « Choisir, décoder, puis contrôler. » Image mentale : deux formats d’inscription, puis un contrôle séparé. Question-réflexe : « Ai-je seulement obtenu des données ou déjà évalué leurs contraintes ? »

⚠️ À ne pas confondre : paramètres de formulaire HTTP, composant Form, désérialisation et Validation sont des opérations distinctes.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Les parameters de route s'apparient par leur nom, jamais par leur position.

    Les parameters de route s'apparient par leur nom, jamais par leur position. Réordonner les arguments ne casse pas cette correspondance ; renommer celui qui dépend d'un attribut la rompt, sauf autre resolver ou valeur par défaut capable de fournir l'argument. Pourquoi on se trompe : on pense que {year}/{slug} impose l'ordre ($year, $slug).

  • Voir l’explication : Request dans une action n'est pas un service Request obtenu par autowiring.

    Request dans une action n'est pas un service Request obtenu par autowiring. C'est une résolution d'argument faite par RequestValueResolver. Un service qui consulte le contexte reçoit RequestStack et lit la requête courante au moment utile. Pourquoi on se trompe : même syntaxe (un type dans une signature), mécanismes différents.

  • Voir l’explication : getSession() ≠ null sans session.

    getSession() ≠ null sans session. Elle lève SessionNotFoundException. Pourquoi on se trompe : getCurrentRequest() et getParentRequest() peuvent, eux, rendre null, d'où l'idée que tout rend null.

  • Voir l’explication : getPayload() ne fusionne pas form et JSON.

    getPayload() ne fusionne pas form et JSON. Si le sac des parameters de form n'est pas vide, elle rend celui-là et ne regarde même pas le body brut.

  • Voir l’explication : Un body JSON invalide ne donne pas un sac vide

    Un body JSON invalide ne donne pas un sac vide : il lève une exception. Le sac vide provient d'un body vide ou d'un JSON décodé en tableau vide.

  • Voir l’explication : getPayload() rend un clone.

    getPayload() rend un clone. Écrire dans l'object retourné ne change rien à la Request.

  • Voir l’explication : Requirement de route ≠ validation métier.

    Requirement de route ≠ validation métier. \d+ contraint le matching du segment, il ne dit pas si l'identifiant est acceptable pour le métier.

Application

À retenir en priorité
  1. Le form bag prime sur le JSON.
  2. Un JSON invalide lève ; un body vide donne un bag vide.
  3. Le type déclenche le resolver.
  4. Dans un service durable, utiliser RequestStack.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Controller veut la Request → résolution d'argument (RequestValueResolver), pas autowiring.
  • Service veut le contexte HTTP → RequestStack, consulté au moment utile.
  • Current = traitée maintenant ; Main = origine ; Parent = juste en dessous (null si on est sur la principale).
  • getSession() lève SessionNotFoundException au lieu de rendre null.
  • Route : attributes, puis le nom de l'argument ; _route et _controller y sont aussi.
  • getPayload() : form d'abord, en clone ; body vide → sac vide ; JSON invalide ou pas un array → JsonException.

Moyen mnémotechnique : « Contrôleur = Symfony me donne la Request. Service = je consulte la RequestStack. »
