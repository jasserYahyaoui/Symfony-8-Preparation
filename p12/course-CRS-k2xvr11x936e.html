Objectif

Le blog affiche l'article 42, propose une inscription et possède une commande d'import. Plusieurs organisations fonctionneraient techniquement : faut-il un bundle pour le catalogue, une variable d'environnement pour la taille des pages, ou une URL générée dans le test qui protège les liens publics ?

Le document Symfony Best Practices donne des choix de départ et leurs raisons. Nous les appliquons à ces décisions pour distinguer une recommandation officielle d'une obligation du framework, dans notre périmètre Symfony 8.0, PHP 8.4 et Twig 3.22.

Ce cours vient après Code organization (où ranger le code) et Naming conventions (comment le nommer) : ici on décide quel mécanisme choisir. Les parties Security, Forms et Tests renvoient à leurs modules dédiés.

L'essentiel

À comprendre

À retenir en priorité
  1. Une constante convient aux valeurs presque immuables.
  2. Les parameters applicatifs gardent des noms courts et préfixés app.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Symfony laisse presque toujours plusieurs façons de faire. Les best practices tranchent par défaut, avec une raison pour chaque choix : un point de départ cohérent, pas une loi.
  • Le piège de fond. Recommandé ≠ obligatoire. Un test d'examen oppose souvent une pratique conseillée à une règle technique imposée.
  • Ce que l'auteur veut que vous compreniez. La raison de chaque conseil, surtout les surprenants : pas de bundle applicatif, constantes pour ce qui bouge peu, boutons dans le template, URL en dur dans le test.
  • Pourquoi c'est à l'examen. Les questions portent sur le conseil exact (XLIFF, un seul firewall, contraintes sur l'objet, préfixe _) et sur son explication.

La référence étudiée regroupe trente recommandations en dix sections. Ce nombre situe le document ; il ne signifie pas que chaque recommandation décrit une règle contrôlée automatiquement par Symfony. Le document propose un point de départ pour une application web classique et autorise des choix différents lorsque leurs raisons sont claires.

Pour notre blog, nous gardons donc une structure simple sous App, des services auxquels on transmet leurs dépendances et des controllers qui coordonnent le traitement. Nous choisissons ensuite le lieu de chaque valeur selon ce qui doit pouvoir la faire varier. Enfin, les tests protègent le contrat public, pas seulement la cohérence interne de la configuration.

C'est ce raisonnement qui explique les conseils parfois surprenants : une constante pour une taille de page stable, un bouton ordinaire dans le template, et une URL littérale dans un test de compatibilité publique. Ces choix n'imposent ni de transformer tout réglage en constante ni d'écrire les liens ordinaires du site en dur.

UNE BEST PRACTICE = un choix par défaut + sa RAISON
 on peut y déroger  →  mais en nommant :
   1. le problème résolu par la dérogation
   2. la limite acceptée
   3. le test qui protège le résultat attendu

Le schéma

Où en est-on ? On a posé « choix + raison ». Le schéma applique ce principe à la première décision concrète : où ranger une valeur ? Pourquoi elle en premier ? Parce que c'est la plus fréquente et celle où l'on confond le plus « forme » (un entier, une chaîne) et « responsabilité » (qui la change).

La pagination /blog/page/{page} a besoin d'une taille de page ; l'inscription peut envoyer une notification ; le déploiement choisit le serveur d'envoi. Ces trois besoins ne doivent pas conduire à ranger toutes leurs valeurs dans la même catégorie :

Orange : questions à poser ; vert : emplacement recommandé. Le serveur SMTP, utilisé pour transporter les emails, peut changer entre déploiements sans changer la politique d'inscription : son adresse relève de l'infrastructure. Le mot de passe qui permet d'y accéder demande en plus une gestion de secrets. Un secret peut alimenter une référence d'environnement ; ces dimensions ne sont donc pas des types PHP mutuellement exclusifs.

À l'inverse, afficher dix articles par page peut être un choix stable du produit. Nous ne voulons pas que le changement d'une machine modifie accidentellement ce choix. Le diagramme mène alors à une constante. Si le produit doit réellement ajuster cette limite souvent, le chemin vers un paramètre redevient pertinent. La décision repose sur le besoin de variation, pas sur le seul fait que la valeur soit un entier.

L'exemple : une valeur qui ne change presque jamais

Exemple concret

À retenir en priorité
  1. Une valeur rarement modifiée peut rester une constante de class.
  2. Un parameter du container n'est pas nécessaire pour toute valeur applicative.

Où en est-on ? Du schéma à la branche « constante ». Pourquoi cette branche en exemple ? Parce que c'est la plus surprenante : beaucoup attendent un paramètre pour toute valeur configurable.

Le laboratoire historique nomme sa class Post. Nous la conservons pour illustrer une constante PHP, sans en faire une entité persistée ni remplacer ArticleView dans notre catalogue en mémoire :

final class Post
{
    public const NUMBER_OF_ITEMS = 10;   // lisible partout, même dans un template
}

La lecture Post::NUMBER_OF_ITEMS fournit 10, sans construire un objet Post ni demander le container. Pour une page numéro 2, cette limite peut servir à calculer un décalage (2 - 1) * 10, soit 10, dans la logique de pagination. Elle ne charge pas les articles et ne valide pas, à elle seule, le paramètre de route page.

Une constante publique peut aussi être lue depuis un template avec le mécanisme approprié de Twig ; cela suppose que sa class soit accessible à l'autoload. Le commentaire « lisible partout » n'autorise donc pas à supposer une variable Twig créée automatiquement. La contrepartie de cette simplicité est la rigidité : on ne remplace pas aisément la valeur dans un test ou par une configuration de déploiement. Si cette variation devient un besoin, mieux vaut transmettre une valeur configurable que contourner la constante.

Au démarrage du projet, le binaire Symfony et l'arborescence standard réduisent les décisions d'installation et les chemins particuliers à maintenir. Ce sont des conventions recommandées, pas une interdiction de créer le projet autrement. Une commande de création fondée sur la version stable du moment ne garantit d'ailleurs pas, à elle seule, notre cible fixe Symfony 8.0.

Dans le code métier, ArticleCatalog reste un service sous App. L'autowiring utilise les types des dépendances pour aider le container à fournir les services ; il ne devine pas toutes les valeurs scalaires ni tous les choix entre plusieurs implémentations. Garder les services privés pousse à les injecter plutôt qu'à les chercher partout avec $container->get(). « Privé » n'empêche pas qu'un autre service en ait besoin.

Dans le controller, étendre AbstractController fournit des raccourcis adaptés à la coordination HTTP. Cela ne justifie pas d'y déplacer toute la logique de recherche ou d'import. Les attributes rendent les métadonnées de route, de cache ou de sécurité proches du code concerné ; elles restent soumises à l'intégration qui les lit. Pour notre article, le controller reçoit le catalogue et coordonne la réponse.

Dans les vues et l'inscription, snake_case signifie des mots minuscules séparés par des soulignements, comme user_profile. Un nom _article_metadata.html.twig signale un fragment inclus dans une page, sans créer un traitement spécial du moteur Twig. Une class de form réutilisable décrit la saisie ; les contraintes placées sur l'objet de données peuvent être réutilisées ailleurs, à condition d'appeler effectivement la validation. Une seule action peut afficher le form sur GET puis traiter sa soumission, sans confondre les deux branches de comportement.

Pour les textes, XLIFF est un format de catalogues de traduction fondé sur XML, bien pris en charge par les outils des traducteurs. Une key telle que label.username décrit le sens du message, pas l'emplacement du form. Changer le texte affiché ne force alors pas à renommer la key dans tous les catalogues. La recommandation ne rend pas les autres formats invalides (le document cite d'ailleurs gettext, lui aussi bien outillé).

Pour les accès, un firewall Symfony est une configuration de traitement de l'authentification, pas le pare-feu réseau de la machine. Un même système d'utilisateurs pour les lecteurs et les rédacteurs peut rester dans un seul firewall. Des systèmes réellement distincts peuvent en justifier plusieurs. Pour décider finement qui peut modifier l'article 42, un voter centralise une décision d'autorisation plutôt que de disperser des expressions complexes. Cela ne remplace pas l'authentification de l'utilisateur.

Pour les tests, un smoke test est un contrôle préliminaire qui détecte des pannes grossières, comme une page publique devenue indisponible. Il complète, sans remplacer, les tests précis du catalogue, de la validation et des permissions. Nous reviendrons à son URL volontairement littérale.

Configuration : la règle des trois niveaux

Où en est-on ? Retour à la configuration, en détail. Pourquoi « trois niveaux » ? Parce que la question à se poser est toujours la même — qui doit changer cette valeur, et pourquoi ? — et que trois réponses (déploiement, application, code) mènent à trois endroits.

Avant d'ajouter un réglage, demandons qui doit le changer et pourquoi. L'adresse d'un serveur dépend du déploiement ; l'adresse affichée comme expéditeur des notifications exprime un choix de l'application ; un mot de passe reste confidentiel quel que soit le lieu où on le configure. La valeur stable de pagination du laboratoire relève, elle, du code.

Qui change la valeur ? Niveau Exemple du blog
le déploiement (machine, hébergeur) variable d'environnement hôte SMTP
l'application (choix produit ajustable) paramètre app.… adresse d'expédition
personne, ou presque (choix stable) constante de classe taille de page
(transversal) la confidentialité secret mot de passe SMTP

Les paramètres applicatifs ont des noms courts et descriptifs, préfixés par app. pour limiter les collisions avec ceux du framework ou des bundles. app.contents_dir décrit mieux sa responsabilité que app.dir. Voici deux valeurs fictives, dans la configuration chargée de l'application :

# config/services.yaml
parameters:
    app.contents_dir: '%kernel.project_dir%/content'
    app.notification_sender: 'notifications@example.test'

Avec un projet situé dans /srv/blog, le premier paramètre décrit /srv/blog/content ; le second fournit l'adresse d'expédition fictive. Le YAML ne crée pas le directory, n'envoie aucun email et ne rend pas ces valeurs automatiquement disponibles dans tous les services ou templates. Il faut les transmettre aux consommateurs par la configuration et l'injection. Le service qui reçoit la valeur n'a pas besoin de connaître lui-même le container.

Un secret n'est pas simplement un paramètre dont le nom contient private ou commence par app.. Les valeurs sensibles relèvent d'une gestion de secrets adaptée, et les éléments qui permettent leur déchiffrement doivent eux aussi être protégés. Nous ne plaçons aucune valeur confidentielle dans cet exemple. Une variable d'environnement peut être un moyen de fournir une valeur, mais son nom ne garantit ni confidentialité ni absence d'exposition.

La constante évite cette configuration pour un choix réellement stable. Le paramètre garde un intérêt si plusieurs contextes ou tests doivent varier la valeur. Il n'y a pas de raison d'ajouter un arbre de configuration complexe à une simple option non réutilisée et sans besoin de validation particulier.

🌍 In Real Life

La situation : une règle du produit, l'adresse du site et une clé confidentielle ne se rangent pas selon leur seule forme écrite.

L’équivalent dans Symfony : règle quasi fixe → constante ; option applicative ajustable → parameter ; infrastructure → environnement ; confidentialité → gestion de secrets.

Retour à la réalité technique : ces dimensions peuvent se combiner : un secret peut alimenter une référence env. Nommer un parameter private ne le protège pas ; le besoin de variation guide le choix.

Repère de l’exemple :

Question: Why is NUMBER_OF_ITEMS a class constant in the example?

Answer: It is an application value that changes rarely and does not need container configuration.

Une valeur rarement modifiée peut rester une constante de class. Un parameter du container n'est pas nécessaire pour toute valeur applicative.

Les recommandations qui surprennent

À retenir en priorité
  1. Une URL générée peut masquer un changement de route publique.
  2. Le functional test doit détecter cette rupture.
  3. Le FormType porte la structure réutilisable.
  4. Le template choisit le bouton adapté au contexte.

Où en est-on ? On revient aux conseils qui contredisent l'intuition. Pourquoi les isoler ? Parce que ce sont ceux sur lesquels le candidat hésite, et chacun a une raison précise qu'il faut connaître.

Ne pas créer un bundle juste pour le catalogue. App\Catalog peut organiser le code interne sans introduire une unité d'intégration au framework. Un bundle devient utile pour distribuer une fonctionnalité réutilisable entre plusieurs applications ; il n'est pas la forme obligatoire d'un domaine métier. Nous gardons donc le code de notre blog simple tant que ce besoin de réutilisation n'existe pas.

Écrire une URL publique en dur dans le test qui la protège. Les liens ordinaires du template doivent suivre les routes, mais le test doit détecter qu'un lien déjà partagé par un lecteur ne fonctionne plus. Voici l'exemple de disponibilité appliqué à /blog/42, avec FrameworkBundle et BrowserKit 8.0, PHP 8.4 et PHPUnit 12.x dans une application de test configurée : le kernel est identifiable, le mode de test est actif et le catalogue de test contient l'article 42.

<?php

namespace App\Tests;

use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

final class BlogAvailabilityTest extends WebTestCase
{
    public function testPublicUrlRemainsAvailable(): void
    {
        $client = static::createClient();
        $client->request('GET', '/blog/42');
        self::assertResponseIsSuccessful();
    }
}

Entrée : le GET de l'URL contractuelle, non recalculée par le générateur. Résultat attendu : le test accepte une Response 2xx ; il ne vérifie pas encore le titre ou le contenu de l'article. Si le chemin disparaît et produit 404, il échoue. Générer l'URL depuis blog_show ferait au contraire suivre automatiquement un nouveau chemin, ce qui masquerait la rupture recherchée. Si une redirection de compatibilité est décidée, il faut la tester explicitement avec son résultat attendu.

URL générée dans le test      URL littérale dans le test
 route renommée/déplacée       route renommée/déplacée
 → l'URL générée SUIT          → l'URL littérale donne 404
 → le test reste VERT          → le test devient ROUGE
 → rupture MASQUÉE             → rupture DÉTECTÉE (c'est le but)

Ce client de test appelle l'application en interne : il ne prouve ni le bon réglage du serveur web ni l'exécution de public/index.php et de Runtime. Un provider de données, qui fournit plusieurs entrées au même test, permet d'étendre le contrôle aux URL publiques représentatives avec leurs données préparées. Les pages qui doivent répondre 404, les accès protégés et les scénarios de soumission demandent des attentes adaptées, pas un 2xx imposé indistinctement à tous les chemins.

Mettre le bouton ordinaire dans le template. Une class de form réutilisée pour créer un profil puis l'éditer ne devrait pas imposer partout le libellé « Ajouter ». Le template peut choisir « S'inscrire » ou « Enregistrer » sans dupliquer la définition des champs. Nuance du document officiel : si plusieurs boutons de soumission doivent être distingués au traitement, on les ajoute au form côté PHP, dans le controller selon cette recommandation. De simples boutons HTML inconnus du form ne suffisent pas à interroger le bouton cliqué avec son mécanisme de traitement.

Ne pas confondre commodité de résolution et chargement métier obligatoire. Une intégration Doctrine configurée peut résoudre une entité avant l'action ; ce comportement appartient au bridge, pas à HttpKernel seul, et l'ORM reste hors du programme étudié. Le sigle ORM signifie Object-Relational Mapping. La recommandation concernant EntityValueResolver reste conditionnelle à cette intégration et à sa commodité. Elle ne signifie pas que HttpKernel charge notre ArticleView en mémoire. Dans notre scène, l'action coordonne un appel explicite à ArticleCatalog. Si une récupération est complexe, la rendre explicite au point de coordination ne signifie pas y entasser toutes les règles métier.

Choisir auto sans en faire un algorithme imaginaire. Un password hasher produit et vérifie une empreinte de mot de passe. auto désigne la sélection de la stratégie prévue par Symfony, pas un algorithme nommé « auto ». La référence 8.0 indique bcrypt comme défaut ; il faut garder cette indication liée à la version et à la configuration, pas la transformer en promesse éternelle. Ce réglage ne chiffre pas un mot de passe pour pouvoir le récupérer ensuite et ne dispense pas de choisir correctement les règles d'inscription.

🌍 In Real Life

La situation : pour vérifier qu'une ancienne adresse reste accessible, on suit l'adresse imprimée sur la carte déjà remise au client, pas un annuaire mis à jour simultanément.

L’équivalent dans Symfony : carte existante → URL littérale du test ; annuaire actuel → générateur de routes.

Retour à la réalité technique : le test de /blog/42 détecte sa disparition ; une URL générée pourrait suivre le nouveau chemin et masquer la rupture. Ce smoke test ne vérifie ni tout le contenu ni le serveur web réel.

🧠 Comment le mémoriser : « Tester la promesse déjà distribuée. » Image mentale : ancienne carte comparée au site actuel. Question-réflexe : le test suit-il involontairement ce qu'il devrait protéger ?

⚠️ À ne pas confondre : URL littérale de compatibilité et liens ordinaires du site, qui gagnent à être générés.

Au restaurant, le serveur reçoit la commande et apporte le résultat ; les postes de cuisine portent le travail spécialisé. Un controller reste ce point de coordination, sans devenir le lieu de toute la logique métier.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Stable ne veut pas dire techniquement interdit en configuration.

    Stable ne veut pas dire techniquement interdit en configuration. La recommandation favorise une constante pour la taille de page quasi fixe. Si le besoin de variation change, le choix peut changer. Une valeur injectée depuis un paramètre n'oblige pas le service consommateur à lire le container. Pourquoi on se trompe : « toute valeur configurable va dans un paramètre » est une habitude, pas une règle du document.

  • Voir l’explication : L'URL littérale protège une autre chose que l'URL générée.

    L'URL littérale protège une autre chose que l'URL générée. Dans le test, /blog/42 protège le lien public existant ; dans les templates, la génération depuis blog_show maintient la cohérence des liens applicatifs. Appliquer la recommandation de test à tous les liens du site ferait perdre ce second avantage. Pourquoi on se trompe : « en dur = mauvaise pratique » est une règle générale vraie ailleurs ; ici l'exception est voulue.

  • Voir l’explication : Un namespace n'a pas besoin de devenir un bundle.

    Un namespace n'a pas besoin de devenir un bundle. Le catalogue interne n'a pas besoin d'une nouvelle intégration au framework pour être organisé. Une fonctionnalité réellement distribuée entre applications peut, elle, justifier ce conditionnement.

  • Voir l’explication : Le bouton ordinaire et les boutons reconnus au traitement ne sont pas le même cas.

    Le bouton ordinaire et les boutons reconnus au traitement ne sont pas le même cas. Le libellé de création ou d'édition appartient au template dans le cas simple. Pour distinguer plusieurs soumissions par les APIs du form, leurs boutons doivent aussi exister dans sa définition côté PHP.

  • Voir l’explication : Le nom auto n'est ni un algorithme ni une garantie de valeur inchangée.

    Le nom auto n'est ni un algorithme ni une garantie de valeur inchangée. Le défaut bcrypt décrit la référence étudiée. La sélection du hasher, le stockage de l'empreinte et la politique d'autorisation restent des responsabilités distinctes : un mot de passe correctement haché ne donne pas à lui seul le droit de modifier l'article 42. Pourquoi on se trompe : le nom auto suggère un algorithme « automatique » nommé comme sha256, alors que c'est une stratégie de sélection.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Pour relire les choix du blog sans les transformer en obligations :

  1. Les trente recommandations et dix sections décrivent le document complet ; nous n'étendons pas pour autant le périmètre technique de ce parcours.
  2. Infrastructure, confidentialité, option applicative et règle stable sont des questions différentes : environnement, secrets, paramètres et constantes ont des rôles complémentaires.
  3. Le code interne reste sous App, avec services privés et dépendances injectées ; un bundle répond à un besoin réel de réutilisation.
  4. AbstractController facilite la coordination HTTP ; la résolution d'une entité dépend d'une intégration facultative, pas de HttpKernel seul.
  5. La class de form reste réutilisable, ses données portent les contraintes et les boutons suivent la distinction entre présentation simple et soumissions multiples reconnues au traitement.
  6. Un firewall suffit généralement à un même système d'authentification ; auto choisit un hasher, tandis que les voters portent les décisions fines.
  7. XLIFF et des keys de sens facilitent les traductions ; les smoke tests détectent les pannes grossières et les URL littérales protègent les liens publics.

« Recommandé n'est pas obligatoire » ne signifie pas « sans raison ». Pour déroger, nommons le problème résolu, la limite acceptée et le test qui protège le résultat attendu.

Phrase de mémorisation : « Qui change la valeur ? Secret, env, paramètre ou constante ; un seul firewall, XLIFF et des keys ; et l'URL du test s'écrit en dur. »
