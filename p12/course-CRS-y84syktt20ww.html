Objectif

Le blog affiche maintenant ses articles. L'équipe envisage de livrer une version installable à un client, avec Symfony dans l'archive. Avant de distribuer ce produit, elle doit répondre à deux questions différentes : peut-elle le vendre, et quelles mentions doit-elle conserver sur le code qu'elle réutilise ?

La réponse se trouve dans la licence de Symfony, pas dans le traitement de GET /blog/42. Nous allons lire les permissions et leurs conditions sans les confondre avec la licence choisie pour notre propre application.

Ce cours clôt le module : après avoir vu comment Symfony est organisé, versionné et compatible dans le temps, on répond à la dernière question pratique : à quelles conditions peut-on le redistribuer dans un produit ? L'installation des dépendances (donc de leurs licences) passe par Symfony Flex.

L'essentiel

À comprendre

À retenir en priorité
  1. MIT autorise l'usage propriétaire et commercial.
  2. Conserver les avis exigés dans les copies substantielles de Symfony.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un projet professionnel redistribue du code tiers : il faut savoir ce que la licence permet et ce qu'elle exige.
  • Le piège de fond. Trois choses distinctes : le droit d'utiliser (très large), la condition de conserver les avis, et les clauses d'absence de garantie / de responsabilité. Les confondre mène à de fausses réponses.
  • Ce que l'auteur veut que vous compreniez. MIT est permissive : on peut vendre un produit propriétaire, à condition de garder les avis.
  • Pourquoi c'est à l'examen. Questions sur le titulaire du copyright (Fabien Potencier, pas SensioLabs), sur le verbe sublicense, sur les « portions substantielles » et sur la key license du composer.json.

Symfony est publié sous licence MIT ; le fichier LICENSE de Symfony 8.0 porte l'avis de copyright de Fabien Potencier. Une licence permissive accorde de larges droits de réutilisation sans imposer ici de publier le code propre de l'application sous la même licence.

Notre équipe peut donc construire et commercialiser un produit propriétaire utilisant Symfony. Cela ne transforme pas Symfony en code sans attribution : les copies ou portions substantielles doivent conserver l'avis de copyright et l'avis de permission. En pratique, nous conservons le texte MIT concerné avec les éléments distribués.

Trois sujets restent distincts : le droit d'utiliser le logiciel, la condition de conservation des avis et les clauses d'absence de garantie et de responsabilité. Une permission large n'efface ni les mentions requises ni les conditions des autres bibliothèques présentes dans notre archive.

 MIT = 3 blocs de texte
 ┌────────────────────┐  ┌──────────────────────┐  ┌─────────────────────┐
 │ 1. PERMISSION      │  │ 2. CONDITION         │  │ 3. CLAUSES FINALES  │
 │ use, copy, modify, │  │ conserver copyright  │  │ AS IS (sans garantie)│
 │ merge, publish,    │  │ ET permission dans   │  │ + exclusion de      │
 │ distribute,        │  │ copies ou portions   │  │ responsabilité      │
 │ sublicense, sell   │  │ substantielles       │  │                     │
 └────────────────────┘  └──────────────────────┘  └─────────────────────┘

Le schéma

À retenir en priorité
  1. La condition porte sur les avis, pas sur l'ouverture du code applicatif.
  2. Les clauses AS IS et de limitation de responsabilité sont distinctes.

Où en est-on ? On a posé les trois blocs ; le schéma montre ce qu'une équipe fait concrètement quand elle redistribue. Pourquoi un schéma ? Parce qu'il isole la seule condition à respecter et rappelle que les autres dépendances sont une question séparée.

L'entrée du schéma est notre produit propriétaire embarquant Symfony. Nous ne cherchons pas à modifier le comportement du controller : nous vérifions la composition de la distribution. Les deux branches rappellent qu'une vérification de MIT ne remplace pas l'examen des autres dépendances.

Bleu : produit et examen des dépendances ; orange : condition MIT ; vert : permission correspondante. Distribuer un installateur propriétaire avec Symfony n'impose pas, au titre de MIT, d'ouvrir le code propre du blog. Supprimer les avis de Symfony pour présenter l'ensemble comme notre création exclusive serait en revanche incompatible avec la condition représentée.

La branche vers les autres packages reste nécessaire même si le contrôle Symfony est satisfait. Ce schéma résume MIT pour l'apprentissage ; il ne constitue pas un avis juridique sur un montage de distribution particulier.

L'exemple : un produit propriétaire

Exemple concret

Où en est-on ? Du schéma à un cas de livraison. Pourquoi un produit propriétaire ? C'est le cas qui fait hésiter : « puis-je fermer mon code alors que j'utilise un framework libre ? ».

Supposons que la société livre au client une archive contenant le blog et ses dépendances Symfony. Elle choisit une licence propriétaire pour son code applicatif et facture le produit. La permission MIT ne lui impose pas de publier ce code dans un dépôt public.

Son contrôle de livraison peut se lire ainsi :

Produit : application commerciale utilisant Symfony
Code applicatif : peut rester propriétaire
Code Symfony redistribué : conserver les mentions requises par MIT
Autres bibliothèques : vérifier leurs licences propres

Le résultat recherché n'est pas « tout le produit devient MIT » : c'est une distribution qui conserve les droits et conditions des éléments réutilisés. La faculté de sous-licencier figure aussi dans MIT, mais elle n'autorise pas à effacer les avis requis sur les parties de Symfony redistribuées.

Ce contrôle ne décide pas à lui seul de toutes les obligations du produit. Il faut maintenant identifier le texte applicable à chaque package plutôt que se fier au nom du framework.

La licence

À retenir en priorité
  1. Symfony est distribué sous MIT.
  2. Cette information ne détermine pas la licence d'un autre corpus.

Où en est-on ? On a un contrôle de livraison ; il faut maintenant savoir où lire la licence. Pourquoi deux sources (composer.json et LICENSE) ? Parce que l'une est une métadonnée pour les outils, l'autre le texte juridique.

Pour documenter la livraison, nous commençons par la déclaration du package. La key license du composer.json de symfony/symfony vaut MIT. Ce champ permet aux outils d'identifier la licence déclarée ; il ne contient pas à lui seul toutes ses conditions.

Le fichier LICENSE, à la racine du dépôt Symfony, donne le texte et l'avis Copyright (c) 2004-present Fabien Potencier. Pour la question de certification portant sur cet avis, le nom attendu est donc celui d'une personne physique, pas celui de SensioLabs. Lire cette mention évite de déduire le titulaire d'une marque ou d'un nom de société associé au projet.

L'équipe applique la même démarche aux autres dépendances : examiner leur déclaration et leur texte propre. Changer le champ license du composer.json de notre application ne change pas la licence du code Symfony qu'elle contient. Cette séparation entre métadonnée du projet et droits sur les composants protège le raisonnement qui suit.

Source Ce qu'elle donne Limite
key license de composer.json MIT (identifiant lisible par les outils) pas les conditions détaillées
fichier LICENSE texte complet + Copyright (c) 2004-present Fabien Potencier ne dit rien des autres packages

Repère — Le texte, clause par clause :

Question: Which notices must accompany substantial copies under MIT?

Answer: The copyright notice and the permission notice.

La condition porte sur les avis, pas sur l'ouverture du code applicatif. Les clauses AS IS et de limitation de responsabilité sont distinctes.

Ce qu'elle autorise

Où en est-on ? On sait où lire ; voyons ce que dit la permission. Pourquoi détailler les huit verbes ? Parce que l'examen demande lequel couvre quelle action (notamment sublicense).

Le texte accorde la permission « free of charge, to any person obtaining a copy ». Cela signifie que cette concession est gratuite ; cela n'interdit pas de vendre le produit qui utilise le logiciel. La liste des permissions inclut justement sell.

Les huit verbes se rattachent aux décisions de notre éditeur : use permet l'utilisation, copy la copie, modify la modification, merge l'intégration, publish la publication, distribute la distribution, sublicense la sous-licence et sell la vente. Nous conservons ces termes anglais parce qu'ils figurent dans le texte de référence, en précisant leur sens.

Verbe MIT Ce qu'il permet pour notre éditeur
use utiliser Symfony dans le blog
copy copier le code
modify le modifier
merge l'intégrer à notre propre code
publish le publier
distribute le distribuer (archive livrée)
sublicense accorder à son tour des droits sous d'autres termes
sell vendre les copies / le produit

La sous-licence permet d'accorder à son tour des droits sous d'autres termes, mais reste soumise à la condition de conservation des avis. « Redistribuer sous une autre licence » ne veut donc pas dire « faire disparaître MIT des copies du code d'origine ». Voici le contrôle concret de notre archive :

Archive livrée au client : application + dépendances Symfony
Action correcte : conserver les fichiers de licence et avis concernés
Action incorrecte : supprimer les avis (tout présenté comme création exclusive)

La vente n'est pas le problème dans ce contre-exemple ; la suppression des avis requis l'est. Pour vérifier exactement ce qui doit rester, séparons maintenant la condition de redistribution des clauses finales.

🌍 In Real Life

La situation : un atelier reçoit des plans réutilisables qui autorisent la fabrication et la vente, avec une condition : conserver les notices requises lorsqu'il transmet les plans concernés. Son propre ajout ne change pas les conditions des plans reçus.

L’équivalent dans Symfony : plans réutilisés → code Symfony sous MIT ; produit de l'atelier → application commerciale ; notices conservées → avis de copyright et de permission sur les copies ou portions substantielles redistribuées.

Retour à la réalité technique : MIT permet notamment l'usage, la modification et la vente sans imposer ici la publication du code propre de l'application. Cette permission n'efface pas les avis, ni les licences des autres dépendances. L'image résume des droits sur du logiciel, pas le droit de propriété sur un objet matériel ; elle ne remplace pas le texte ni un avis juridique adapté.

🧠 Comment le mémoriser : « Vendre son produit, conserver les avis du code repris. » Image mentale : l'archive livrée avec les notices de ses composants. Question-réflexe : quelles parties distribuées viennent de tiers et quelles mentions doivent les accompagner ?

⚠️ À ne pas confondre : permission d'utilisation et garantie de fonctionnement ; changer la licence déclarée de l'application ne réécrit pas celle de Symfony.

Une recette réutilisable illustre l'usage commercial permis : vendre le plat n'oblige pas à ouvrir toute la cuisine. La comparaison porte uniquement sur les permissions MIT de Symfony ; elle ne confère aucune licence à ce corpus.

Le texte, clause par clause

Où en est-on ? La permission est claire ; reste la condition et les deux clauses finales. Pourquoi les lire séparément ? Parce que chaque clause répond à une question différente et que l'examen mélange volontairement les objets.

Conserver les deux avis. La condition vise l'avis de copyright et l'avis de permission dans « all copies or substantial portions of the Software ». Notre archive complète est un cas évident ; ne reprendre qu'une portion substantielle ne permet pas de contourner cette condition. Il n'est pas nécessaire de redistribuer tout Symfony pour être concerné. Le cours ne fixe pas de seuil universel en lignes ou en nombre de fichiers.

Ne pas confondre permission et garantie. La clause AS IS, « en l'état », indique que le logiciel est fourni sans garantie selon le texte. Le droit d'utiliser Symfony ne constitue donc pas une promesse que notre blog fonctionnera sans défaut dans toutes les installations.

Lire séparément la responsabilité. La clause suivante énonce une exclusion de responsabilité des auteurs ou titulaires pour les réclamations et dommages visés. Ce n'est pas une répétition de la liste des permissions ni une obligation de citer Symfony dans l'interface. Nous décrivons ici ce qu'énonce le texte, sans trancher son application juridique dans chaque pays.

Enfin, MIT n'impose pas de réciprocité sur le code propre du blog. Le copyleft désigne une autre logique de licence, avec des obligations de réciprocité définies par son texte. Il ne faut pas en déduire que toutes les licences copyleft interdisent la vente ou imposent les mêmes obligations dans tous les modes de distribution. L'usage commercial et la fourniture des sources sont deux questions distinctes ; le présent cours établit les conditions MIT de Symfony, pas une comparaison juridique exhaustive.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Dernier regard sur les confusions typiques : permissif vs copyleft, avis vs propriété, permission vs garantie.

  • Voir l’explication : Utiliser Symfony ne choisit pas automatiquement la licence du blog.

    Utiliser Symfony ne choisit pas automatiquement la licence du blog. MIT n'est pas une licence copyleft : elle n'impose pas à notre code propre d'être publié sous MIT, ni d'être rendu public simplement parce qu'il utilise Symfony. Cette conclusion porte sur MIT ; elle ne dispense pas de vérifier les autres dépendances ou engagements du produit. Pourquoi on se trompe : on généralise la réciprocité de certaines licences libres à toutes.

  • Voir l’explication : Une application propriétaire doit tout de même garder les avis requis.

    Une application propriétaire doit tout de même garder les avis requis. Le caractère fermé de notre code ne permet pas d'effacer le copyright et la permission attachés aux copies ou portions substantielles de Symfony. Inversement, conserver ces avis n'oblige pas à transformer notre dépôt privé en dépôt public. Pourquoi on se trompe : « permissif » est lu comme « sans condition ».

  • Voir l’explication : La licence n'est pas une promesse de fonctionnement.

    La licence n'est pas une promesse de fonctionnement. Autorisation de vendre, condition sur les avis, absence de garantie et exclusion de responsabilité répondent à des questions différentes. À l'examen, associez chaque clause à son objet plutôt que de retenir le raccourci trop large « tout est permis ».

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Avant de livrer l'archive du blog, retrouvez ces cinq points :

  1. Symfony déclare MIT dans son composer.json ; son LICENSE porte l'avis 2004-present Fabien Potencier et donne le texte de référence.
  2. L'usage commercial et propriétaire est autorisé ; MIT n'impose pas de publication du code propre de notre application.
  3. Les copies ou portions substantielles du logiciel doivent conserver l'avis de copyright et l'avis de permission. Sous-licencier ne les efface pas.
  4. Le texte distingue la fourniture AS IS, sans garantie, de la clause d'exclusion de responsabilité.
  5. Les autres packages gardent leurs propres licences : la licence de Symfony ne vaut pas automatiquement pour toute la distribution.

Le contrôle porte sur les éléments réellement livrés et leurs mentions, pas sur une étape cachée du traitement HTTP. Nous pouvons ensuite revenir à l'organisation technique du projet avec une distinction claire entre code réutilisé, code applicatif et conditions de redistribution.

Phrase de mémorisation : « MIT : je peux vendre et fermer mon code, mais je garde les avis de Fabien Potencier ; AS IS, sans garantie. »
