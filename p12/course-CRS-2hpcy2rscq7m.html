Objectif

BlogController::show sait rendre l'article 42. Nous voulons ajouter un header commun aux Responses sans recopier cette opération dans chaque action. Sur la branche /blog/999, nous voulons aussi comprendre pourquoi un listener peut remplacer la page d'erreur avant le rendu intégré. Dans les deux cas, il faut intervenir au bon moment, avec les données alors disponibles.

Le cours Request handling décrit le trajet HTTP. Ici, avec Symfony 8.0, nous examinons le mécanisme de notification, l'enregistrement des callbacks et les pouvoirs de chaque event. Le component EventDispatcher fonctionne aussi hors HTTP : ses petits laboratoires ne sont pas des étapes supplémentaires imposées au GET du blog.

Les erreurs du kernel (kernel.exception) sont détaillées dans Exception handling ; le Module 20 reprend EventDispatcher dans un cadre plus général.

L'essentiel

À comprendre

À retenir en priorité
  1. La propagation concerne un event précis.
  2. Les events suivants du kernel ne sont pas annulés.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un framework doit laisser l'application s'insérer dans son déroulement (ajouter un header, répondre tôt, remplacer une page d'erreur) sans modifier le code du framework ni recopier la même opération dans chaque contrôleur. Le mécanisme de Symfony : « je prévois des points d'accroche nommés, vous y branchez vos callbacks ».
  • Le piège de fond. Quatre notions voisines se confondent : event (l'objet), listener (le callback), subscriber (un objet qui déclare ses callbacks) et dispatcher (celui qui appelle). Et « huit events du kernel » ne veut pas dire « huit étapes obligatoires ».
  • Ce que l'auteur veut que vous compreniez. Qui appelle qui, dans quel ordre (priorité décroissante), avec quels pouvoirs (selon la classe de l'event), et comment on peut couper la suite (propagation).
  • Pourquoi c'est à l'examen. Les questions portent sur le nom par défaut d'un dispatch, les arguments reçus par un listener, getListenerPriority(), la valeur retournée par dispatch(), StoppableEventInterface, et le rôle exact de chacun des huit events du kernel.

Un event est un objet portant les informations utiles à une notification. Un listener est un callable, c'est-à-dire une fonction ou une method que PHP peut appeler, enregistré pour cette notification. Le dispatcher retrouve les callbacks associés à son nom et les appelle de façon synchrone : le code qui a demandé le dispatch attend leur exécution.

Un subscriber regroupe la déclaration de plusieurs abonnements dans une class. Il n'a pas plus de pouvoirs qu'un listener ; les methods de l'objet event déterminent les opérations possibles. Un ResponseEvent donne accès à une Response déjà construite, tandis qu'un ControllerEvent intervient avant l'appel de l'action.

L'ordre dépend de la priority décroissante : un entier plus élevé passe avant un entier plus faible. Un event arrêtable peut interrompre ce parcours, sans annuler les effets des callbacks précédents. Les huit noms d'events du kernel constituent un catalogue de points d'intervention, pas huit étapes qui se produiraient obligatoirement pour chaque Request.

Qui fait quoi ?
┌────────────┬────────────────────────────────────────────────────────────┐
│ Event      │ l'objet distribué : les données de la notification         │
│ Listener   │ un callable enregistré pour un NOM d'event                 │
│ Subscriber │ un objet dont getSubscribedEvents() déclare ses listeners  │
│ Dispatcher │ retrouve les listeners du nom, les appelle dans l'ordre    │
└────────────┴────────────────────────────────────────────────────────────┘
   code appelant ──dispatch($event, 'nom')──► dispatcher ──► listener 1
                       ▲                                  └─► listener 2
                       └────────── retourne $event ◄──────────┘

🌍 In Real Life

La situation : le responsable annonce « commande prête » aux employés inscrits pour effectuer les dernières vérifications, l'un après l'autre.

L’équivalent dans Symfony : fiche d'annonce avec ses données → objet event ; responsable qui consulte les inscriptions → dispatcher ; geste de chaque employé → callable listener enregistré.

Retour à la réalité technique : EventDispatcher appelle les listeners synchroniquement, selon leur priorité et l'état de propagation. Le code appelant attend. Un objet event n'est pas la Request elle-même : un événement du kernel peut donner accès à cette Request et à d'autres données.

🧠 Comment le mémoriser : « Une annonce, des réactions enregistrées. » Image mentale : une fiche passant devant plusieurs postes. Question-réflexe : quel objet est distribué, sous quel nom, à quels callbacks ?

⚠️ À ne pas confondre : une notification synchrone et une tâche mise en file pour plus tard ; aucun traitement durable n'est promis ici.

Le schéma

À retenir en priorité
  1. Chaque event expose un pouvoir adapté à son étape.
  2. kernel.terminate intervient après l'émission de la Response.

Où en est-on ? Avant le cas du blog, on isole le mécanisme pur : un dispatcher, deux callbacks, une propagation. Pourquoi ? Parce que les huit events du kernel ne sont que ce même mécanisme, appelé par HttpKernel à huit endroits.

Avant d'ajouter notre header, isolons ce que fait le dispatcher avec deux callbacks. Le laboratoire historique les nomme notify et log : ces noms représentent des appels à observer, pas un envoi de mail ni une écriture de journal garantis. Le dispatcher ne connaît que leurs abonnements :

Bleu : appels ; losange orange : vérification ; capsule verte : retour du même objet event. Avec deux callbacks, un event initialement non arrêté et aucune exception, notify à 10 passe avant log à −10. Si notify arrête la propagation, log est sauté ; sinon les deux s'exécutent.

La vérification existe aussi avant le premier callback : un objet déjà arrêté peut n'en déclencher aucun. Les nombres 10 et −10 sont des choix de laboratoire, pas les bornes autorisées. Le retour ne contient pas une liste des résultats des listeners : dispatch() rend l'objet reçu, éventuellement modifié par eux. Une exception qui sort d'un callback interrompt normalement ce dispatch ; le dessin ne prétend pas gérer cette autre branche.

L'exemple : un subscriber

Exemple concret

À retenir en priorité
  1. Un listener est enregistré de l'extérieur.
  2. Un subscriber déclare lui-même ses subscriptions.

Où en est-on ? On rend le schéma exécutable. Pourquoi un subscriber en premier ? Parce que c'est la forme la plus complète : l'objet porte à la fois ses abonnements (méthode statique) et ses comportements (méthodes d'instance).

Conservons les noms OrderPlacedEvent et OrderSubscriber du laboratoire historique, sans ajouter un système de commandes commerciales au blog. Nous complétons l'extrait pour observer réellement ses deux methods. Avec PHP 8.4, EventDispatcher 8.0 et son autoload déjà chargé :

use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Contracts\EventDispatcher\Event;

final class OrderPlacedEvent extends Event {}

final class OrderSubscriber implements EventSubscriberInterface
{
    public array $trace = [];

    public static function getSubscribedEvents(): array
    {
        return [OrderPlacedEvent::class => [['notify', 10], ['log', -10]]];
    }

    public function notify(OrderPlacedEvent $event): void
    {
        $this->trace[] = 'notify';
    }

    public function log(OrderPlacedEvent $event): void
    {
        $this->trace[] = 'log';
    }
}

$dispatcher = new EventDispatcher();
$subscriber = new OrderSubscriber();
$dispatcher->addSubscriber($subscriber);
$event = new OrderPlacedEvent();
$returned = $dispatcher->dispatch($event);

echo implode(', ', $subscriber->trace), "\n";
var_dump($returned === $event);

Entrée : un event neuf et un subscriber explicitement enregistré. Résultat attendu : notify, log, puis bool(true). La déclaration statique associe les deux methods au nom de class utilisé par le dispatch sans nom explicite. Les methods ne font ici qu'ajouter des éléments à un tableau en mémoire ; rien n'est envoyé ou persisté.

Sans addSubscriber(), créer la class et l'objet ne suffit pas à les abonner. Pour notifier une étape d'import du blog, on pourrait appliquer le même mécanisme à un event applicatif adapté, émis explicitement par la commande. Cela ne créerait ni une file de travail durable ni une exécution parallèle : chaque callback allongerait le temps de l'appel qui l'a déclenché.

Le déroulé, ligne par ligne :

addSubscriber($subscriber)
   └─► lit OrderSubscriber::getSubscribedEvents()  (méthode STATIQUE)
         OrderPlacedEvent::class => [['notify', 10], ['log', -10]]
   └─► enregistre [$subscriber,'notify'] à 10 et [$subscriber,'log'] à -10
dispatch($event)            ← sans nom : le nom = OrderPlacedEvent::class
   └─► notify (10) → trace = ['notify']
   └─► log (-10)   → trace = ['notify', 'log']
   └─► retourne $event (le même objet : === donne true)

🌍 In Real Life

La situation : un employé arrive avec la liste des annonces auxquelles il sait réagir ; le responsable doit encore l'inscrire au planning.

L’équivalent dans Symfony : employé capable d'agir → objet OrderSubscriber ; liste déclarée → getSubscribedEvents() ; inscription → addSubscriber() ; gestes exécutés → méthodes notify() et log().

Retour à la réalité technique : le subscriber réunit déclaration et comportement. Sa méthode statique décrit les abonnements ; les callbacks de l'objet effectuent le travail. Construire l'objet ne l'enregistre pas. Ici les méthodes modifient seulement une trace en mémoire : leurs noms n'envoient ni mail ni journal.

🧠 Comment le mémoriser : « Le volontaire doit être inscrit. » Image mentale : l'employé avec sa liste devant le planning encore vide. Question-réflexe : qui a effectivement enregistré ce subscriber ?

⚠️ À ne pas confondre : le subscriber réel et un simple fichier de configuration ; la déclaration seule n'exécute rien.

Listener ou subscriber

Où en est-on ? Étape 1 sur 4 du cours : le choix de la forme d'enregistrement. Question : où écrit-on la déclaration « tel callback écoute tel nom » ? Les deux formes ont les mêmes pouvoirs ; seule change la place de la déclaration.

Le choix porte sur l'emplacement de la déclaration. Avec addListener($nom, $callable, $priority), le code qui assemble l'application choisit le nom, le callback et sa priorité. Avec addSubscriber($objet), le dispatcher lit la method statique getSubscribedEvents() de l'objet. Pour chaque nom d'event, elle peut rendre :

  • un nom de method, avec priorité 0 ;
  • un couple [méthode, priorité] ;
  • une liste de couples, comme nos deux callbacks du laboratoire.

Un deuxième laboratoire montre pourquoi le nom explicite compte. Le signal local demo.completed pourrait servir à notifier la fin d'une étape d'import ; il n'est émis que lorsque notre code appelle dispatch(). Cet extrait est indépendant du précédent :

use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;

final class AuditSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return ['demo.completed' => 'record'];
    }

    public function record(object $event): void
    {
        echo "appel reçu\n";
    }
}

$dispatcher = new EventDispatcher();
$dispatcher->addSubscriber(new AuditSubscriber());
$dispatcher->dispatch(new \stdClass(), 'demo.completed');

Le nom fourni correspond à l'abonnement : la sortie est appel reçu. Sans second argument, le nom serait stdClass, et ce subscriber ne serait pas appelé. Le dispatcher n'invente pas automatiquement order.placed à partir de OrderPlacedEvent, ni ne cherche les abonnements de toutes ses classes parentes. Le nom utilisé au dispatch doit correspondre à celui de l'enregistrement.

Dans le framework, le container peut réaliser ces raccords. Un service subscriber découvert et autoconfiguré reçoit l'intégration adaptée ; un listener peut être déclaré par le tag kernel.event_listener ou #[AsEventListener]. Un fichier de class ignoré par la découverte des services ne devient pas actif grâce à l'attribute seul.

AsEventListener permet de préciser event, method, priority et dispatcher, ce dernier désignant le service dispatcher à utiliser. Si event est absent, l'intégration peut déduire les noms depuis le type du premier argument de la method. Pour les events du kernel, les alias issus de KernelEvents::ALIASES relient notamment ResponseEvent::class à kernel.response. Une class d'event applicatif sans alias conserve son propre nom : la déduction n'est donc pas limitée aux huit events HTTP.

Une union de types de classes d'events peut produire plusieurs abonnements. Un argument non typé, un simple type générique object ou le seul Event des contrats ne fournit pas un nom suffisamment précis pour cette inférence : dans le cas qui en dépend, la compilation demande un event explicite. Ces alias sont traités lors de l'enregistrement par le container ; un new EventDispatcher() autonome ne reproduit pas cette intégration.

Comparaison des trois façons d'enregistrer :

addListener() addSubscriber() / EventSubscriberInterface #[AsEventListener]
Où est la déclaration ? dans le code d'assemblage dans getSubscribedEvents() (statique) sur la classe ou la méthode
Qui enregistre ? vous, à la main vous (addSubscriber) ou le container (autoconfiguration) le container (service découvert)
Nom d'event passé en argument clé du tableau retourné event: ou déduit du type du 1ᵉʳ argument
Priorité 3ᵉ argument valeur dans le tableau paramètre priority
Pouvoirs du callback identiques identiques identiques

Pourquoi la déduction par le type fonctionne-t-elle pour ResponseEvent ? Parce que le container consulte KernelEvents::ALIASES, table qui relie ResponseEvent::class à 'kernel.response' (et de même pour les sept autres events). Un new EventDispatcher() seul n'a pas cette table.

🌍 In Real Life

La situation : soit le responsable inscrit directement un geste au planning, soit un employé présente sa propre liste de réactions aux annonces.

L’équivalent dans Symfony : inscription extérieure d'un geste → addListener() ; objet déclarant ses réactions → EventSubscriberInterface ; intitulé exact de l'annonce → nom utilisé au dispatch et à l'enregistrement.

Retour à la réalité technique : les deux formes aboutissent à des listeners enregistrés, sans différence de pouvoirs. Le dispatcher autonome ne devine pas les alias du framework. L'intégration conteneur peut traduire ResponseEvent::class en kernel.response lors de l'enregistrement ; elle ne transforme pas arbitrairement tout nom de classe en nom d'événement.

🧠 Comment le mémoriser : « Même annonce, même intitulé. » Image mentale : deux colonnes dont les étiquettes doivent correspondre. Question-réflexe : le nom dispatché correspond-il à l'abonnement, après l'éventuel alias configuré ?

⚠️ À ne pas confondre : autoconfiguration d'un service découvert et activation magique de toute classe portant un attribute.

Priority

À retenir en priorité
  1. Une priority élevée passe d'abord.
  2. Les valeurs négatives sont valides.

Où en est-on ? Étape 2 sur 4. Les callbacks sont enregistrés ; reste la question de l'ordre. Pourquoi une priorité ? Parce que plusieurs listeners peuvent écouter le même nom, et que l'un dépend du résultat de l'autre (par exemple fournir une Response avant qu'un autre ne la décore).

Nous savons enregistrer les callbacks ; il reste à décider lequel doit voir l'event en premier. La priorité ordonne les listeners du même nom d'event. Elle ne déplace pas kernel.response avant kernel.request et ne transforme pas un traitement long en travail parallèle.

La valeur est un entier, positif ou négatif, avec 0 par défaut. Le dispatcher trie les groupes par ordre décroissant avec krsort() ; à priorité égale, il conserve l'ordre d'ajout. Ce laboratoire, avec le component chargé, rend l'ordre visible malgré un enregistrement différent :

use Symfony\Component\EventDispatcher\EventDispatcher;

$dispatcher = new EventDispatcher();
$dispatcher->addListener('demo', static function (): void { echo "zéro\n"; });
$dispatcher->addListener('demo', static function (): void { echo "dix\n"; }, 10);
$dispatcher->addListener('demo', static function (): void { echo "moins dix\n"; }, -10);
$dispatcher->dispatch(new \stdClass(), 'demo');

Résultat attendu :

dix
zéro
moins dix

Une priorité négative signifie « après zéro », pas « désactivé ». Nos callbacks PHP n'utilisent pas leurs arguments, mais EventDispatcher leur transmet l'event, le nom et le dispatcher ; le retour de chaque listener n'est pas collecté comme résultat du dispatch.

Dans le premier laboratoire, interroger getListenerPriority(OrderPlacedEvent::class, [$subscriber, 'notify']) sur le dispatcher correspondant rend 10. Pour un callback non enregistré sous le nom demandé, la method rend null, pas la priorité par défaut 0. Si un ordre est indispensable, mieux vaut le rendre explicite que dépendre d'un ordre de découverte des services.

Dans l'application Symfony 8.0 configurée, cette commande inspecte les abonnements au point où nous ajouterons le header :

php bin/console debug:event-dispatcher kernel.response

Résultat attendu : la liste des listeners enregistrés pour cet event et leurs priorités dans l'environnement courant. Après enregistrement de CourseHeaderListener présenté plus bas, sa method doit y apparaître. Le tableau exact dépend des services installés ; un listener absent n'est pas simplement « trop tardif ». Il faut vérifier sa découverte, son nom d'event et le dispatcher ciblé avant d'augmenter arbitrairement sa priorité.

Avant / après un tri, pour trois enregistrements dans l'ordre « zéro, dix, moins dix » :

ORDRE D'AJOUT              ORDRE D'EXÉCUTION (priorité décroissante)
1. zéro      (0)           1. dix        ( 10)   ← le plus grand passe d'abord
2. dix       (10)          2. zéro       (  0)
3. moins dix (-10)         3. moins dix  (-10)   ← négatif = après, pas désactivé
(à priorité égale : l'ordre d'ajout est conservé)

🌍 In Real Life

La situation : pour une même annonce, le planning donne la parole au poste 10, puis 0, puis −10.

L’équivalent dans Symfony : rang du poste sur cette annonce → priorité du listener ; égalité de rang → ordre d'ajout ; poste absent du planning → abonnement introuvable.

Retour à la réalité technique : l'ordre est décroissant, les priorités négatives restent actives. getListenerPriority() renvoie null pour un abonnement absent, pas 0. Cet ordre vaut pour le même nom d'événement ; il ne déplace pas une phase du cycle HTTP.

🧠 Comment le mémoriser : « Plus haut, plus tôt, pour la même annonce. » Image mentale : trois fiches 10, 0, −10 empilées dans cet ordre. Question-réflexe : compare-t-on des listeners du même événement ?

⚠️ À ne pas confondre : priorité élevée et exécution parallèle ; le callback long retarde toujours la suite synchrone.

Propagation

Où en est-on ? Étape 3 sur 4. L'ordre est fixé ; on veut parfois que le premier listener ait le dernier mot. Pourquoi ? Pour qu'un résultat de secours (une Response d'erreur, par exemple) ne soit pas écrasé par les listeners suivants.

Une fois un résultat de secours trouvé, nous pouvons vouloir empêcher les autres callbacks de l'écraser. La propagation est ce parcours des listeners pour un objet event. stopPropagation() demande d'en sauter la suite ; elle n'annule ni les changements déjà faits ni le programme qui a déclenché le dispatch.

Le dispatcher vérifie isPropagationStopped() seulement si l'objet implémente Psr\EventDispatcher\StoppableEventInterface, contrat défini par PSR-14 (voir Framework interoperability and PSRs). Symfony\Contracts\EventDispatcher\Event l'implémente et fournit le drapeau d'arrêt ; les events du kernel héritent de ce comportement. Une method nommée stopPropagation() dans une class sans ce contrat ne suffit pas. En l'absence de ce contrat, l'arrêt n'est pas consulté, mais une exception sortant d'un callback peut évidemment encore interrompre les appels.

Voici le laboratoire indépendant qui isole cet effet, avec les contrats et le component disponibles dans l'autoload :

use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Contracts\EventDispatcher\Event;

$dispatcher = new EventDispatcher();
$dispatcher->addListener('demo', static function (Event $event): void {
    echo "premier\n";
    $event->stopPropagation();
}, 10);
$dispatcher->addListener('demo', static function (): void { echo "second\n"; });
$dispatcher->dispatch(new Event(), 'demo');
echo "après dispatch\n";

La sortie contient premier, puis après dispatch, sans second. Le programme continue après le dispatch. Le callback aurait aussi pu exécuter du code après stopPropagation() : ce n'est pas un return. Avec l'implémentation Event utilisée ici, redistribuer le même objet déjà arrêté ne réinitialise pas son drapeau ; un event neuf représente une nouvelle notification.

Dans notre branche d'erreur /blog/999, ExceptionEvent::setResponse() arrête cette propagation après avoir fixé une Response. Le kernel peut ensuite distribuer kernel.response pour notre header. De même, répondre dès kernel.request évite l'action, mais pas nécessairement les events de réponse et de fin. Ne confondons pas la décision du kernel et le simple arrêt de la liste de callbacks.

dispatch($event, 'demo')
  ├─ listener priorité 10 : echo "premier" ; $event->stopPropagation()
  │      (le reste du callback s'exécute jusqu'au bout : ce n'est PAS un return)
  ├─ le dispatcher consulte isPropagationStopped() → true
  ├─ listener priorité 0  : SAUTÉ
  └─ dispatch() retourne $event ; le programme appelant continue ("après dispatch")

Quand la propagation s'arrête-t-elle dans le kernel ?

Appel Arrête la propagation ? Conséquence
RequestEvent::setResponse() oui (automatiquement) l'action n'est pas appelée ; la suite du traitement continue avec cette Response
ExceptionEvent::setResponse() oui (automatiquement) les listeners d'exception suivants sont sautés ; kernel.response peut suivre
ResponseEvent::setResponse() non un autre listener peut encore modifier la Response
$event->stopPropagation() oui saute les listeners restants du même nom

🌍 In Real Life

La situation : le responsable marque une fiche « ne plus transmettre » après la première intervention ; les gestes déjà effectués restent faits.

L’équivalent dans Symfony : marque d'arrêt sur cette fiche → état de l'objet event ; consultation de la marque → isPropagationStopped() via StoppableEventInterface ; postes suivants sautés → listeners restants non appelés.

Retour à la réalité technique : stopPropagation() n'est ni return, ni annulation des effets précédents, ni arrêt global de l'application. Le dispatcher vérifie aussi l'état avant le premier callback. Redistribuer le même Event des contrats déjà arrêté ne réinitialise pas son drapeau.

🧠 Comment le mémoriser : « Stop à la suite, pas retour en arrière. » Image mentale : une flèche barrée après une case déjà cochée. Question-réflexe : cet objet implémente-t-il le contrat arrêtable, et qu'a-t-on déjà exécuté ?

⚠️ À ne pas confondre : arrêter la propagation et produire une Response ; RequestEvent::setResponse() fait les deux, contrairement à un simple arrêt.

Le dispatcher gère une file de passages sur une fréquence. stopPropagation() ferme cette file pour l'event courant, pas toutes les fréquences ni tout le cycle de Request.

Le catalogue du kernel

Où en est-on ? Étape 4 sur 4, la plus importante pour l'examen : on applique le mécanisme aux huit points d'accroche de HttpKernel. Pourquoi cette dernière ? Parce que « quel event pour quel besoin ? » suppose d'avoir compris ce qu'est un event, un listener, une priorité et une propagation. Le chemin d'exécution complet est décrit dans Request handling ; ici, on se concentre sur ce que chaque event permet de faire.

Revenons au GET du blog. Tous ces objets étendent KernelEvent et donnent accès à getRequest(), getKernel(), getRequestType() et isMainRequest(). Le dernier permet de distinguer la Request principale d'une sub-Request interne, par exemple celle du rendu d'erreur. Le tableau indique les capacités utiles ; ce n'est pas un ordre inconditionnel d'exécution :

Nom Class d'event Pouvoir spécifique

kernel.controller ControllerEvent setController()
kernel.controller_arguments ControllerArgumentsEvent setArguments()
kernel.view ViewEvent getControllerResult(), setResponse()
kernel.response ResponseEvent getResponse(), setResponse()
kernel.finish_request FinishRequestEvent Pas de setter de Response — restauration d'état
kernel.terminate TerminateEvent getResponse() — pas de réécriture des octets déjà envoyés
kernel.exception ExceptionEvent setThrowable(), setResponse()

Avant l'action, kernel.request permet de travailler sur la Request ou de répondre tôt. Les attributes de Routing ne sont disponibles qu'après le listener qui les renseigne : être « dans kernel.request » ne prouve pas encore que blog_show a été trouvé. Une Response posée ici court-circuite la résolution et l'appel du controller pour ce traitement.

Si l'exécution continue, kernel.controller dispose du callable résolu ; setController() peut le remplacer avant la résolution des arguments. Puis HttpKernel appelle ArgumentResolver, qui utilise ses value resolvers. kernel.controller_arguments intervient après cette résolution, avant l'appel : setArguments() peut modifier la liste, à condition de respecter la signature du callable. Ce n'est pas un deuxième appel du controller.

Après l'action, notre version HTML qui rend une Response n'a pas besoin de kernel.view. Dans une variante JSON où une action rendrait un tableau, ce point permettrait à un listener approprié de lire getControllerResult() et de fournir une JsonResponse. HttpKernel seul ne sérialise pas automatiquement tous les tableaux : sans Response fournie, le résultat de controller n'est pas accepté comme réponse.

Quand une Response existe, kernel.response est le point adapté pour ajouter notre header avant l'envoi normal. Contrairement au setResponse() de RequestEvent, celui de ResponseEvent ne stoppe pas automatiquement la propagation : un autre listener peut encore voir ou modifier la Response.

Voici le service de démonstration à placer dans src/EventListener/CourseHeaderListener.php, avec la découverte et l'autoconfiguration des services activées :

<?php
namespace App\EventListener;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\ResponseEvent;
use Symfony\Component\HttpKernel\KernelEvents;

#[AsEventListener(event: KernelEvents::RESPONSE)]
final class CourseHeaderListener
{
    public function __invoke(ResponseEvent $event): void
    {
        if (!$event->isMainRequest()) {
            return;
        }

        $event->getResponse()->headers->set('X-Course', 'architecture');
    }
}

Entrée : une Response principale, comme celle de /blog/42, à laquelle le kernel applique kernel.response. Résultat attendu à l'issue de ce callback : X-Course: architecture. Une sub-Request est ignorée. La valeur fixe ne révèle aucun secret ; elle sert à observer l'intervention, pas à définir une politique de cache ou de sécurité. Sans filtre de route, ce service concerne aussi les autres Responses principales, y compris les erreurs qui atteignent ce point. Un listener ultérieur pourrait encore changer le header.

Ce que Symfony voit dans ce listener : une classe avec #[AsEventListener], donc un abonnement à kernel.response ; comme aucune method n'est donnée, la méthode appelée est __invoke ; le type ResponseEvent du paramètre est celui de l'event kernel.response.

À la fin du traitement interne, kernel.finish_request permet aux listeners de restaurer un contexte, notamment après une sub-Request. Il ne faut pas l'assimiler au pop() de RequestStack : HttpKernel effectue ce retrait séparément dans son finally. L'event ne signifie pas que les octets ont déjà été envoyés.

Après l'envoi dans le cycle normal, l'appel distinct à terminate() distribue kernel.terminate. handle() seul ne le déclenche pas. TerminateEvent donne toujours accès à l'objet Response, qui n'est pas devenu immuable ; le modifier en mémoire ne réécrit toutefois pas ce que le client a déjà reçu. Ce point n'est ni une garantie de tâche durable ni une preuve de livraison réseau.

Enfin, si une exception prise en charge survient, kernel.exception ouvre la branche de remplacement ou de réponse étudiée avec l'article 999. Elle n'est pas une étape supplémentaire du succès de l'article 42. Le nom, la phase et la class d'event nous disent ainsi ce que notre code peut raisonnablement modifier.

Choisir l'event selon le besoin :

Je veux… Event Pourquoi celui-là
répondre tôt (maintenance, redirection) kernel.request setResponse() court-circuite l'action
remplacer le controller choisi kernel.controller setController()
modifier les arguments déjà résolus kernel.controller_arguments setArguments()
transformer un résultat non-Response (array) kernel.view getControllerResult() + setResponse()
ajouter un header à toutes les Responses kernel.response la Response existe, avant l'envoi
restaurer un état après une sous-requête kernel.finish_request notification de fin interne
travailler après l'envoi kernel.terminate après la Response (sans la modifier chez le client)
remplacer la page d'erreur kernel.exception setResponse() / setThrowable()

🌍 In Real Life

La situation : un employé ajoute une étiquette au résultat encore sur le comptoir ; le faire après remise ne corrigerait pas ce qui est déjà parti.

L’équivalent dans Symfony : résultat disponible avant remise → kernel.response ; étiquette ajoutée → modification des headers ; rangement après émission → kernel.terminate.

Retour à la réalité technique : le type de l'event détermine les données et opérations disponibles. Une Response directe évite kernel.view ; l'exception ouvre une autre branche. ResponseEvent::setResponse() ne stoppe pas automatiquement la propagation. À la terminaison, modifier l'objet en mémoire ne réécrit pas les octets déjà émis ; cela ne prouve pas non plus leur réception.

🧠 Comment le mémoriser : « Modifier au bon état, pas au dernier moment. » Image mentale : l'étiquette posée avant le départ. Question-réflexe : la donnée existe-t-elle et son émission a-t-elle déjà eu lieu ?

⚠️ À ne pas confondre : catalogue de points d'intervention et huit étapes obligatoires ; finish_request notifie la fin interne, le finally dépile séparément.

Les constants de KernelEvents sont REQUEST, CONTROLLER, CONTROLLER_ARGUMENTS, VIEW, RESPONSE, FINISH_REQUEST, TERMINATE et EXCEPTION ; leurs valeurs sont les noms kernel.* du tableau.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le callback de secours passe trop tôt.

    Le callback de secours passe trop tôt. Vérifions l'ordre décroissant : 10 précède 0, puis −10. La priorité ne réordonne que les abonnements au même event ; elle n'avance pas une phase du kernel. Pourquoi on se trompe : « priorité 1 = premier » est l'intuition de la vie courante ; ici c'est le plus grand nombre qui passe d'abord.

  • Voir l’explication : Le programme continue après l'arrêt de propagation.

    Le programme continue après l'arrêt de propagation. C'est normal : seuls les callbacks restants pour l'objet arrêtable sont sautés. Un travail déjà effectué n'est pas annulé et un autre event peut ensuite être distribué. Pourquoi on se trompe : on assimile stopPropagation() à return ou à exit.

  • Voir l’explication : La class subscriber existe, mais rien ne se passe.

    La class subscriber existe, mais rien ne se passe. Sa method statique getSubscribedEvents() fournit une déclaration, pas un auto-enregistrement. Il faut addSubscriber() ou l'intégration effective du service dans le framework. Pourquoi on se trompe : on croit que l'implémentation de l'interface suffit.

  • Voir l’explication : Le header ajouté à terminate n'apparaît pas chez le client.

    Le header ajouté à terminate n'apparaît pas chez le client. Modifier encore l'objet Response ne modifie pas les données déjà émises. Le point prévu pour notre header est kernel.response, avant l'envoi normal. Pourquoi on se trompe : TerminateEvent donne bien accès à la Response, donc on la croit encore modifiable côté client.

  • Voir l’explication : La constante et le type ne sont pas le même identifiant brut.

    La constante et le type ne sont pas le même identifiant brut. KernelEvents::RESPONSE vaut kernel.response, alors que ResponseEvent::class est un nom de class. L'intégration sait appliquer les alias prévus lors de l'enregistrement ; le dispatcher autonome ne devine pas cette correspondance.

  • Voir l’explication : Le listener attend order.placed, mais le dispatch n'a pas de nom.

    Le listener attend order.placed, mais le dispatch n'a pas de nom. Il part sous le nom de class de l'objet. Il faut aligner le nom explicite et l'abonnement, pas attendre une conversion de casse ou de ponctuation. Pourquoi on se trompe : on imagine un « snake_case » automatique.

  • Voir l’explication : Une method nommée stopPropagation() n'est pas le contrat PSR-14.

    Une method nommée stopPropagation() n'est pas le contrat PSR-14. Le dispatcher consulte l'état uniquement via StoppableEventInterface. Le nom de method seul ne permet pas de déduire le comportement.

  • Voir l’explication : L'inférence ne sait plus quel event écouter.

    L'inférence ne sait plus quel event écouter. Si event n'est pas fourni, le type précis du premier argument est nécessaire dans le cas où l'intégration doit le déduire. Une union peut déclarer plusieurs classes d'events ; un type générique ne remplace pas leur nom. Avec un nom explicite, l'abonnement ne dépend plus de cette inférence, même si une signature PHP compatible reste requise.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Pour ajouter le header au blog sans modifier chaque action :

  1. Choisir kernel.response, où la Response existe avant l'envoi normal, plutôt que kernel.terminate.
  2. Enregistrer réellement le listener ou le subscriber ; la déclaration statique du subscriber et les attributes ne s'exécutent pas seuls.
  3. Vérifier le nom : à défaut d'argument explicite, dispatch() utilise la class de l'event et rend le même objet après les callbacks.
  4. Lire l'ordre décroissant des priorités, avec 0 par défaut et l'ordre d'ajout en cas d'égalité ; null signifie abonnement non trouvé.
  5. Distinguer les trois arguments transmis au callback de son retour, que le dispatcher ne collecte pas.
  6. Limiter l'arrêt aux events implémentant le contrat arrêtable ; cet arrêt n'annule ni les effets précédents ni les autres phases du kernel.
  7. Interpréter les huit events selon leurs conditions et leurs classes : view n'est pas obligatoire, une sub-Request peut aussi déclencher des points d'intervention, et l'inférence de type relève de l'intégration.

« Grand nombre, premier servi » résume les priorités, pas la chronologie complète du kernel. Nous pouvons maintenant garder les controllers centrés sur leur résultat tout en plaçant les opérations transversales aux bons points.

Phrase de mémorisation : « Le dispatcher appelle, dans l'ordre du plus grand nombre, les listeners inscrits sous le même nom, jusqu'à ce qu'un arrêt le coupe — et le kernel offre huit points d'accroche, pas huit étapes obligatoires. »
