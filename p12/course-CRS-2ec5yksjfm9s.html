Objectif

Le bon firewall traite /blog/42. Nous voulons maintenant garder cette lecture publique et réserver l'écran d'édition aux rédacteurs. La règle doit sélectionner la bonne requête avant que ses exigences soient évaluées ; un mauvais ordre peut rendre la restriction inaccessible.

Question du cours : sur GET /blog/42/edit, quelle règle access_control est choisie, qu'exige-t-elle, et que ne contrôle-t-elle pas ?

L'essentiel

À comprendre

À retenir en priorité
  1. L'ordre sélectionne une seule règle.
  2. Les règles suivantes ne renforcent pas la première.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le firewall dit comment s'authentifier ; access_control dit ce qu'il faut pour atteindre une URL. C'est le portier de la porte d'entrée, pas du contenu.
  • Le piège de fond. Deux questions distinctes se cachent derrière une règle : quelle règle correspond ? (sélection) puis ses exigences sont-elles satisfaites ? (décision). Un non-match n'est pas un refus.
  • Ce que l'auteur veut que vous compreniez. Seule la première règle correspondante compte ; l'ordre est donc du plus spécifique au plus général.
  • Pourquoi c'est à l'examen. request_matcher exclusif, ips qui ne fait que « correspondre », roles + allow_if selon la strategy, 301 de requires_channel, Request comme sujet.

access_control choisit une règle d'accès à partir de la requête : chemin, méthode HTTP, adresse IP ou autres critères. Il faut distinguer deux questions : quelle règle correspond ?, puis ses exigences sont-elles satisfaites ?

Seule la première règle correspondante s'applique. Un échec d'autorisation ne fait pas essayer la règle suivante. À l'inverse, une IP ou une méthode qui ne correspond pas fait poursuivre la recherche : ce n'est pas encore un refus.

Pourquoi le sujet est-il la Request ? Les matchers et la carte des accès sont préparés dans le container. Pendant la requête, la carte retourne les attributs de la première correspondance ; AccessListener les soumet à la décision avec la Request pour sujet, pas avec l'article automatiquement chargé.

Le schéma

À retenir en priorité
  1. La règle générale peut masquer les exceptions.
  2. L'ordre exprime la priorité réelle.

Le premier graphe sélectionne ; le second applique. Un accord n'est pas encore le HTML de l'article et un non-match n'est pas encore un refus : ces distinctions expliquent les résultats du prochain exemple.

L'exemple

Exemple concret

À retenir en priorité
  1. Une règle plus précise n'a pas de priorité automatique.
  2. La position dans la liste décide.

Où en est-on ? Du code minimal d'abord : deux règles qui séparent l'écran d'édition des pages publiques. Regardons quelle règle gagne pour chaque URL.

Avec un firewall actif et les voters usuels, ce fragment distingue l'écran d'édition et les pages publiques du blog :

security:
    access_control:
        - { path: '^/blog/[0-9]+/edit$', roles: ROLE_EDITOR }
        - { path: '^/blog(?:/|$)', roles: PUBLIC_ACCESS }

GET /blog/42 sélectionne la seconde règle. /blog/42/edit sélectionne la première, même si Alice n'a pas le rôle demandé : un refus ne retente pas la règle publique. Inverser les lignes annulerait cette restriction à ce niveau. L'autorisation sur l'article reste un contrôle serveur distinct.

URL Règle choisie Exigence Alice sans ROLE_EDITOR
/blog/42 2 (PUBLIC_ACCESS) aucune accès
/blog/42/edit 1 (ROLE_EDITOR) ROLE_EDITOR refus (pas de repli sur la règle 2)

L'exemple d'administration suivant conserve les autres critères :

security:
    access_control:
        - { path: '^/admin/users', roles: ROLE_SUPER_ADMIN }   # le plus précis d'abord
        - { path: '^/admin', roles: ROLE_ADMIN }
        - { path: '^/internal', roles: PUBLIC_ACCESS, ips: [127.0.0.1, ::1] }
        - { path: '^/internal', roles: ROLE_NO_ACCESS }          # tous les autres

La règle

À retenir en priorité
  1. L'absence de match n'est pas un refus.
  2. Les controllers et voters peuvent toujours contrôler l'accès.

Où en est-on ? Étape 1 sur 4 : le principe d'ordre. Pourquoi le plus spécifique doit-il venir en premier ? Parce que Symfony s'arrête à la première correspondance, sans chercher mieux.

Dans une règle route: blog_show, la valeur vise le nom de route, pas sa forme /blog/{id}. Un changement de nom et un changement de chemin ne demandent donc pas les mêmes vérifications de configuration.

  • Les règles sont évaluées dans l'ordre ; seule la première qui correspond est appliquée.
  • D'où l'écriture du plus spécifique au plus général : avec ^/admin avant ^/admin/users, un utilisateur ayant ROLE_SUPER_ADMIN mais ni ROLE_ADMIN ni hiérarchie se voit refuser l'accès à cette étape ; ROLE_ADMIN obtient l'accord de cette règle — sans erreur de configuration. Le statut HTTP final dépend ensuite du traitement de la requête ou du refus.
  • Une URL qu'aucune règle ne couvre n'est pas restreinte par cette liste.

Avant / après, pour /admin/users :

MAUVAIS ORDRE                        BON ORDRE
1. ^/admin       → ROLE_ADMIN ←gagne 1. ^/admin/users → ROLE_SUPER_ADMIN ←gagne
2. ^/admin/users → ROLE_SUPER_ADMIN  2. ^/admin       → ROLE_ADMIN
   (jamais atteinte)

super-admin sans ROLE_ADMIN : refusé super-admin : accepté

Ce qui fait correspondre une règle

À retenir en priorité
  1. ips sélectionne la règle.
  2. Ajouter un fallback si les autres clients doivent être refusés.

Où en est-on ? Étape 2 sur 4 : on a vu que la première correspondance gagne. Mais qu'est-ce qui fait « correspondre » ? Chaque clé de la règle est un critère de sélection, pas une interdiction.

🌍 In Real Life

La situation : au restaurant, une fiche de consigne concerne les livraisons du matin. Une livraison du soir n'est pas refusée par cette fiche : il faut chercher la consigne suivante.

L’équivalent dans Symfony : catégorie de demande → critères path, methods, ips ; fiche sélectionnée → première règle correspondante ; contrôle après sélection → exigences de cette règle.

Retour à la réalité technique : tous les critères configurés doivent correspondre, avec les alternatives prévues dans leurs listes. Un GET hors d'une règle POST ou une IP hors de sa liste poursuit la recherche ; ce non-match n'impose ni refus ni statut HTTP.

🧠 Comment le mémoriser : « Hors de la fiche n'est pas hors du restaurant. » Image mentale : demande passant à la fiche suivante. Question-réflexe : ai-je sélectionné une règle ou réellement refusé l'accès au blog ?

⚠️ À ne pas confondre : filtre de sélection et liste d'autorisation complète.

Key Ce qu'elle contraint
path, host le path, le host — expressions régulières, path sans la query string
ips (ou ip) l'adresse du client, masques acceptés
port, methods le port, les methods HTTP
route le nom de la route
attributes des attributes de la Request
request_matcher un service RequestMatcherInterface
  • Tous les critères d'une règle doivent correspondre.
  • request_matcher remplace les autres critères de correspondance : il peut être accompagné d'exigences comme roles, mais pas de path ou methods. Une telle combinaison de critères est refusée (InvalidConfigurationException, « should not be specified alongside other options »).
  • methods: [POST] est un critère : un GET ne correspond pas à cette règle, donc passe à la suivante ; cela n'impose ni un 200 ni un 405.
  • ips fait correspondre, il ne restreint pas : une Request d'ailleurs passe à la règle suivante. Pour fermer la zone, une seconde règle sur le même path exige ROLE_NO_ACCESS, un role que personne n'a.

ROLE_NO_ACCESS n'est pas un mot réservé signifiant « refuser » : ce modèle suppose que personne ne reçoit ce rôle, ni directement ni par hiérarchie, et qu'aucun autre voter n'accorde la demande. /blog/42?preview=1 a le même path que /blog/42 ; une condition sur preview ne se place pas dans la regex du path.

Pourquoi ips seul ne ferme-t-il pas /internal ? Parce que c'est un critère de sélection : une IP extérieure ne correspond simplement pas à la première règle, la recherche continue. Si aucune autre règle ne couvre /internal, rien n'est restreint.

GET /internal/x depuis 10.0.0.1, règles :
  1. ^/internal, ips [127.0.0.1, ::1], PUBLIC_ACCESS
        → IP différente : ne correspond pas
  2. ^/internal, ROLE_NO_ACCESS
        → correspond ; exige un rôle que personne n'a → refus
Sans la règle 2 : aucune règle ne correspond → pas de restriction (accès !)

Pourquoi request_matcher est-il exclusif ? Le matcher personnalisé contient déjà toute la logique de correspondance ; accepter aussi path ou ips rendrait ambigu qui décide. Le code de createAuthorization() lève une InvalidConfigurationException dès qu'un autre critère l'accompagne.

Ce que la règle exige

À retenir en priorité
  1. La strategy affirmative agrège par accord suffisant.
  2. Un role et une expression ne forment pas automatiquement un ET.

Où en est-on ? Étape 3 sur 4 : la règle est sélectionnée. Que demande-t-elle maintenant ? roles, allow_if, requires_channel : voyons comment ces exigences sont combinées par la strategy de vote.

🌍 In Real Life

La situation : le responsable du restaurant reçoit un avis sur l'habilitation et un autre sur une condition spéciale. Les placer côte à côte ne définit pas la manière de trancher.

L’équivalent dans Symfony : habilitation → attributs roles ; condition spéciale → expression allow_if ; règle d'agrégation → stratégie des votes.

Retour à la réalité technique : avec les voters standard et affirmative, un accord peut suffire malgré un autre refus. unanimous change l'agrégation des votes, mais ne transforme pas automatiquement une liste de rôles en obligation de les posséder tous.

🧠 Comment le mémoriser : « Deux avis ne signifient pas deux obligations cumulatives. » Image mentale : deux bulletins devant un règlement de décision. Question-réflexe : qui produit chaque vote et quelle stratégie les combine ?

⚠️ À ne pas confondre : combinaison des critères de correspondance et combinaison des exigences d'autorisation.

SecurityExtension ajoute l'expression allow_if à la liste des attributs issus de roles. Ce sont donc les voters et la stratégie, pas la juxtaposition des clés YAML, qui définissent le résultat :

  • roles — passés comme attributes à decide(), avec la Request pour sujet ;
  • allow_if — une expression, ajoutée aux attributes ; elle voit la Request sous request ;
  • requires_channel: https — une Request http reçoit un redirect 301.

Les exigences sont soumises ensemble à la strategy. Avec les voters standards de rôles et d'expressions, sans autre voter qui modifie la décision, le tableau décrit l'autorisation, pas le statut HTTP :

Règle affirmative (défaut) unanimous
roles: [ROLE_ADMIN, ROLE_EDITOR], user ROLE_EDITOR accordée accordée
roles: ROLE_ADMIN + allow_if vrai, user sans ROLE_ADMIN accordée refusée
même règle, visiteur anonyme accordée refusée

Deux roles valent « l'un ou l'autre » : le même voter les examine. Un role et une expression relèvent de deux voters : « ou » en affirmative, « et » en unanimous.

attributes = [ ROLE_ADMIN , expression(allow_if) ]
                  │                 │
          RoleVoter vote       ExpressionVoter vote
          (refuse : pas admin) (accorde : expression vraie)
                  └────────┬────────┘
   affirmative : un accord suffit  → ACCORDÉ
   unanimous   : aucun refus admis → REFUSÉ

Pour exiger deux rôles simultanément, ne pas déduire un « et » du seul passage à unanimous : le voter de rôles peut déjà rendre un accord pour l'un des rôles de sa liste. Exprimer délibérément la conjonction dans une politique adaptée et tester chaque cas manquant. Le canal HTTPS concerne le transport de la requête, pas l'identité ni le chiffrement des données stockées.

Un accord laisse continuer la Request : il ne construit pas une Response 200. Un refus déclenche le traitement d'une AccessDeniedException. Pour un utilisateur pleinement authentifié, le traitement standard conduit normalement à 403, sauf gestion du refus personnalisée. Si une authentification doit être commencée ou renforcée, l'entry point configuré peut répondre 401 (HTTP Basic) ou rediriger vers un formulaire de connexion. Un token remember-me n'est pas une authentification pleine pour cette décision.

Ce que cela ne fait pas

À retenir en priorité
  1. La règle URL ne connaît pas l'object métier.
  2. Le voter traite l'ownership.

Où en est-on ? Étape 4 sur 4 : on connaît la mécanique. Reste sa limite : access_control voit la Request, pas l'objet métier. Qui contrôle le droit sur l'article 42 ?

🌍 In Real Life

La situation : entrer dans le bureau de rédaction n'autorise pas Alice à modifier chaque manuscrit posé sur les tables.

L’équivalent dans Symfony : contrôle à l'entrée → access_control sur la Request ; manuscrit particulier → objet article ; droit de le modifier → voter métier recevant ce sujet.

Retour à la réalité technique : la règle d'accès ne charge pas automatiquement l'article 42. Le code ou un mécanisme de résolution configuré fournit cet objet, puis un contrôle adapté applique sa politique ; aucun stockage particulier n'est requis par ce principe.

🧠 Comment le mémoriser : « Entrer dans la salle n'est pas disposer de tous les dossiers. » Image mentale : porte ouverte, manuscrits avec auteurs distincts. Question-réflexe : où est contrôlé le droit sur cet article précis ?

⚠️ À ne pas confondre : permission sur la requête et permission sur l'objet métier.

access_control décide depuis la Request et ne charge pas automatiquement l'objet métier : « l'auteur modifie son article » demande une politique recevant cet article. Un refus produit une AccessDeniedException : normalement 403 pour un utilisateur pleinement authentifié ; sinon l'entry point peut demander une authentification, y compris plus forte qu'une connexion restaurée par remember-me.

Après l'accord sur /blog/42/edit, le contrôleur peut encore charger 42 et transmettre ce sujet à denyAccessUnlessGranted('POST_EDIT', $article). Un accord de cette liste ne transforme pas non plus l'article absent 999 en article existant.

access_control Voter métier
Sujet la Request l'objet (article 42)
Quand avant le contrôleur (AccessListener) dans le contrôleur / service
Question « puis-je atteindre cette URL ? » « puis-je modifier cet article ? »

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le path exclut la query string.
  2. Ne pas y placer une condition sur les parameters de query.
  • Voir l’explication : Seule la première règle correspondante s'applique

    Seule la première règle correspondante s'applique ; les autres ne sont pas cumulées. Pourquoi on se trompe : on imagine un ensemble de règles qui se cumulent comme des filtres.

  • Voir l’explication : Du plus spécifique au plus général

    Du plus spécifique au plus général, sinon la règle fine devient inatteignable. Pourquoi on se trompe : on attend du système qu'il choisisse la règle la plus précise, comme certains routeurs.

  • Voir l’explication : path est une expression régulière

    path est une expression régulière, comparée sans la query string. Pourquoi on se trompe : on met ?preview=1 dans la regex ; elle ne le voit jamais.

  • Voir l’explication : roles + allow_if accorde si l'un des deux suffit

    roles + allow_if accorde si l'un des deux suffit, avec la strategy par défaut. Pourquoi on se trompe : deux clés YAML ressemblent à deux obligations.

  • Voir l’explication : Aucune règle ne correspond : aucune restriction par access_control

    Aucune règle ne correspond : aucune restriction par access_control, pas une autorisation universelle de l'application. Pourquoi on se trompe : « pas de règle » ressemble à « tout refusé » ; c'est le contraire à ce niveau.

  • Voir l’explication : Le sujet d'access_control est la Request

    Le sujet d'access_control est la Request, pas l'article : le chargement et la permission métier restent à traiter. Pourquoi on se trompe : /blog/42/edit contient « 42 », donc on croit que l'article est évalué.

Fiche express

À mémoriser

À retenir en priorité
  1. Le matcher personnalisé remplace les critères intégrés.
  2. Une combinaison est refusée.

La zone et le rôle sont contrôlés ; les voters métier précisent maintenant la décision sur le sujet. Ne pas supprimer ce second contrôle parce que l'URL a déjà passé access_control.

🧠 À retenir pour la certification :

  • Première règle qui correspond, et elle seule.
  • Du plus spécifique au plus général.
  • path : regex, sans query string.
  • Critères : path, host, ips, port, methods, route, attributes — ou request_matcher à leur place, avec les exigences séparées.
  • ips fait correspondre ; ROLE_NO_ACCESS n'est un refus que si personne ne l'obtient et qu'aucun autre voter n'accorde.
  • roles + allow_if : « ou » en affirmative, « et » en unanimous. Un accord laisse continuer la Request ; il ne garantit pas HTTP 200.
  • Canal non respecté avec requires_channel → 301.

Moyen mnémotechnique : « Le premier qui correspond, et la strategy tranche ».

access_control : première règle qui correspond (précis d'abord) ;
path regex sans query ; ips = critère ; request_matcher remplace les critères ;
roles + allow_if = strategy (affirmative : ou) ; accord = continuer,
pas HTTP 200 garanti ; canal non respecté = 301 ;
sujet Request, pas d'article automatiquement chargé
