Objectif

Nous savons écrire les classes du blog. Il reste à décrire quelle méthode correspond à une adresse telle que /blog/42, sans glisser cette information dans la logique de lecture de l'article. Un attribute PHP attache des métadonnées structurées à une déclaration de code. Nous allons distinguer sa définition, son placement et sa lecture : trois opérations nécessaires pour comprendre #[Route], mais qui ne traitent pas à elles seules une Request.

Le fil du cours, en trois verbes (les trois sections du programme) :

  1. Déclarer : créer le type d'attribute (#[Attribute], cibles, répétition).
  2. Poser : placer une occurrence sur du code, avec des arguments constants.
  3. Lire : retrouver, évaluer, puis construire l'attribute par réflexion.

L'essentiel

À comprendre

À retenir en priorité
  1. getArguments() évalue les arguments sans instancier l'attribute extérieur ; un new imbriqué peut construire un objet.
  2. newInstance() déclenche le constructor et les contrôles de cible et répétition.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Avant PHP 8, pour dire « cette méthode répond à /blog/{id} », on écrivait des annotations dans des commentaires (@Route) ou un fichier YAML séparé. Les attributes sont une syntaxe native, vérifiée par le langage, qui colle la métadonnée à la déclaration concernée.
  • Ce que l'auteur veut que vous compreniez. Un attribute est inerte : il ne fait rien tout seul. Il faut un lecteur (le loader de routes de Symfony, ou votre propre code) qui utilise la réflexion pour le lire. Et la lecture a trois niveaux (découvrir, évaluer les arguments, construire) qui ne contrôlent pas les mêmes choses.
  • Pourquoi c'est à la certification. Symfony 8 repose sur #[Route], #[AsCommand]… Les QCM demandent quand l'erreur de cible/répétition est levée, ce que rend getArguments(), et ce qu'on peut mettre en argument.

La méthode BlogController::show sait produire un résultat ; la déclaration #[Route] placée sur elle décrit comment la retrouver. PHP permet d'attacher cette information, tandis qu'un lecteur Symfony lui donne un usage. La réflexion, API qui inspecte les déclarations PHP, permet ce passage du code déclaré à ses métadonnées.

Pour définir notre propre type d'attribute, nous marquons une class avec #[Attribute]. Ses cibles autorisées et le drapeau IS_REPEATABLE indiquent où et combien de fois l'utiliser. Ses arguments sont des expressions constantes, pas une lecture de la Request courante. getAttributes() trouve des descriptions ReflectionAttribute ; newInstance() construit l'object décrit et déclenche notamment les contrôles de cible et de répétition. La construction ne suffit toujours pas à créer une route : un lecteur doit exploiter les données obtenues.

Comparaison des trois niveaux de lecture :

┌──────────────────┬───────────────────┬────────────────────┬─────────────────┐
│                  │ getAttributes()   │ getArguments()     │ newInstance()   │
├──────────────────┼───────────────────┼────────────────────┼─────────────────┤
│ Rend             │ ReflectionAttribute│ array d'arguments │ l'objet attribute│
│ Évalue arguments │ non               │ oui                │ oui             │
│ Construit        │ rien              │ new imbriqués      │ l'attribute     │
│ Contrôle cible   │ non               │ non                │ OUI (Error)     │
│ Contrôle répét.  │ non               │ non                │ OUI (Error)     │
└──────────────────┴───────────────────┴────────────────────┴─────────────────┘

Le schéma

Où en est-on ? Vue d'ensemble avant le code : on suit un outil qui inspecte une méthode déjà marquée #[Route] (ce n'est pas l'arrivée d'un GET). Le schéma montre où se placent les trois niveaux de lecture et où tombent les erreurs.

Partons d'une méthode déjà marquée #[Route]. Le diagramme ne représente pas l'arrivée d'un GET : il suit un outil qui inspecte cette déclaration. Il peut vouloir les arguments pour les afficher, ou un object pour les exploiter. Ces choix expliquent les deux sorties de ReflectionAttribute.

Orange : métadonnée et contrôle ; bleu : objets de lecture ; vert : résultats ; rouge : usage invalide. Les deux sorties de ReflectionAttribute sont des choix de lecture, pas une obligation de les appeler ensemble. Un argument new Inner(...) est évalué lors de la lecture des arguments : « ne construit pas l'attribut externe » ne signifie pas « ne construit jamais aucun objet ». Nous allons d'abord lire une route de pagination, puis définir une métadonnée applicative pour voir ce que PHP contrôle et ce qu'un lecteur doit encore faire.

L'exemple

Exemple concret

Où en est-on ? On commence par le côté lecture, avec l'attribute Route déjà défini par Symfony, pour voir le résultat final avant d'apprendre à déclarer le sien.

Pour isoler la lecture, préparons une méthode de démonstration list. Elle décrit la branche de pagination /blog/page/{page} ; son corps vide ne sert aucune page et n'est pas une action HTTP complète. Cet exemple demande les classes Routing de Symfony 8.0 chargées par l'autoloader.

use Symfony\Component\Routing\Attribute\Route;

$controller = new class {
    #[Route('/blog/page/{page}', name: 'blog_page')]
    public function list(): void {}
};

Le bloc suivant se lit à sa suite, dans le même fichier et avec le même import de Route. Il inspecte list sans l'appeler :

$reflection = new \ReflectionMethod($controller, 'list');

foreach ($reflection->getAttributes(Route::class) as $attribute) {
    $route = $attribute->newInstance();     // instancie ENFIN la classe Route
    echo $route->path;                     // propriété publique de l'attribut Route en 8.0
}

La sortie est /blog/page/{page}, le modèle déclaré, et non une URL où {page} aurait été remplacé. L'object construit est l'attribute Route, pas une Response ni un article. Les données sont désormais disponibles ; le travail du loader de routes et le futur choix d'une route restent distincts de cette inspection PHP.

Pas à pas :

#[Route('/blog/page/{page}', name: 'blog_page')]  posé sur list()
        │ ReflectionMethod(list)->getAttributes(Route::class)
        ▼
[ReflectionAttribute "Route"]   (simple description, rien construit)
        │ ->newInstance()
        ▼
new Route('/blog/page/{page}', name: 'blog_page')   (contrôles cible + répétition)
        │ ->path
        ▼
"/blog/page/{page}"            (le modèle, pas l'URL /blog/page/3)

(Vérifié dans Symfony 8.0 : Route est déclaré #[\Attribute(\Attribute::IS_REPEATABLE | \Attribute::TARGET_CLASS | \Attribute::TARGET_METHOD)] et $path est une property publique du constructeur.)

Déclarer

À retenir en priorité
  1. Les flags définissent les cibles de l'attribute.
  2. IS_REPEATABLE autorise plusieurs occurrences au même endroit.

Où en est-on ? Étape 1 sur 3 : on a lu un attribute fourni par Symfony ; on apprend maintenant à en créer un. Question centrale : comment dire à PHP « cette class peut servir d'attribute, ici, et tant de fois » ?

Nous avons utilisé Route, défini par Symfony. Pour comprendre sa déclaration, imaginons maintenant un outil interne qui classe les rapports du blog par étiquettes. Nous définissons Label, une class ordinaire dont le constructor reçoit le nom d'une étiquette, puis nous indiquons à PHP qu'elle peut être utilisée comme attribute.

#[Attribute(...)] combine avec | les emplacements autorisés : TARGET_CLASS, TARGET_FUNCTION, TARGET_METHOD, TARGET_PROPERTY, TARGET_CLASS_CONSTANT et TARGET_PARAMETER. TARGET_ALL les autorise tous. IS_REPEATABLE n'est pas une cible : ce drapeau permet plusieurs occurrences sur la même déclaration. Pour nos rapports, deux étiquettes ont un sens, mais les poser sur une méthode n'en aurait pas dans ce contrat.

Drapeau Rôle
TARGET_CLASS, TARGET_FUNCTION, TARGET_METHOD, TARGET_PROPERTY, TARGET_CLASS_CONSTANT, TARGET_PARAMETER où l'attribute peut être posé
TARGET_ALL tous les emplacements
IS_REPEATABLE combien : plusieurs fois sur la même déclaration (pas une cible) 
#[Attribute(Attribute::TARGET_CLASS | Attribute::IS_REPEATABLE)]
final class Label
{
    public function __construct(public readonly string $name) {}
}

#[Label('daily')]
#[Label('sales')]
final class Report {}

foreach (new ReflectionClass(Report::class)->getAttributes(Label::class) as $metadata) {
    echo $metadata->newInstance()->name, "\n";
}

Ce script autonome, écrit dans l'espace global en PHP 8.4, affiche daily, puis sales. Les deux noms sont des données de classement ; ils ne lancent aucun rapport ni tâche quotidienne. Sans IS_REPEATABLE, PHP permettrait encore de retrouver les deux descriptions, mais newInstance() signalerait la répétition interdite. Sans notre boucle, Symfony ne lirait pas automatiquement ce Label applicatif.

Symfony\Component\Routing\Attribute\Route suit le même mécanisme PHP, avec TARGET_CLASS | TARGET_METHOD | IS_REPEATABLE, mais dispose d'un lecteur dans le component Routing. Définir la métadonnée et fournir son lecteur sont donc deux responsabilités différentes.

Qui fait quoi ?
 ┌───────────────────────┐   ┌───────────────────────┐   ┌─────────────────────┐
 │ Définition            │   │ Pose                  │   │ Lecteur             │
 │ class Label           │   │ #[Label('daily')]     │   │ ReflectionClass     │
 │ #[Attribute(...)]     │   │ sur Report            │   │ ->getAttributes()   │
 │ (PHP vérifie l'usage) │   │ (données constantes)  │   │ (VOTRE code/Symfony)│
 └───────────────────────┘   └───────────────────────┘   └─────────────────────┘

🌍 In Real Life

La situation : un atelier définit un modèle d'étiquette, les dossiers où elle est autorisée et la possibilité d'en coller plusieurs ; l'étiquette ne classe encore aucun dossier toute seule.

L’équivalent dans Symfony : modèle → classe d'attribute ; emplacements → TARGET_* ; répétition → IS_REPEATABLE ; agent de classement → lecteur de métadonnées.

Retour à la réalité technique : #[Attribute] décrit un usage PHP. Un Label applicatif exige son lecteur ; Route possède un lecteur Symfony quand ses déclarations sont chargées. Le drapeau de répétition n'est pas une cible.

🧠 Comment le mémoriser : « Une étiquette attend un lecteur. » Image mentale : dossier marqué mais encore non traité. Question-réflexe : quel code exploite cette métadonnée ?

⚠️ À ne pas confondre : déclaration de métadonnée et exécution d'une action.

Poser

À retenir en priorité
  1. Un argument d'attribute est une expression constante.
  2. Une variable ou un appel de function ne convient pas.

Où en est-on ? Étape 2 sur 3 : le type d'attribute existe. Question : que peut-on écrire entre les parenthèses quand on le pose, et pourquoi est-ce limité ?

Le type de métadonnée existe ; posons maintenant une occurrence avant la déclaration concernée. Les arguments suivent les conventions positionnelles ou nommées d'un appel, mais doivent être des valeurs littérales ou des expressions constantes : littéral, constante, constant de class, cas d'enum ou array de ces éléments. Une variable locale du controller et un appel tel que getPath() ne peuvent pas fournir le chemin de #[Route]. La déclaration décrit le code indépendamment d'un futur appel de la méthode.

Pourquoi seulement des constantes ? L'attribute est lu sans exécuter la méthode : il n'existe ni requête, ni variable locale, ni service à ce moment-là. PHP ne peut donc évaluer que ce qui est connu à la compilation.

Argument Valide ?
'/blog', 42, true (littéraux) oui
Report::TITLE, PHP_EOL (constantes) oui
Level::Admin (cas d'enum, pure ou backed) oui
['a', 'b'] (array de constantes) oui
new Options(20) oui depuis PHP 8.1
getPath(), $variable non

Depuis PHP 8.1, new est aussi admis dans les arguments d'attributes, notamment pour #[Outer([new Inner('a')])]. Cela autorise des objets de configuration imbriqués, pas n'importe quel calcul. L'exemple suivant prépare le titre et la taille de page d'un écran de rapports. Il est indépendant du précédent : sa class Report ne doit pas être chargée avec l'autre déclaration du même nom.

final class Options
{
    public function __construct(public readonly int $pageSize) {}
}

#[Attribute(Attribute::TARGET_CLASS)]
final class Screen
{
    public function __construct(
        public readonly string $title,
        public readonly Options $options,
    ) {}
}

#[Screen(title: Report::TITLE, options: new Options(20))]
final class Report
{
    public const string TITLE = 'Reports';
}

$metadata = new ReflectionClass(Report::class)->getAttributes(Screen::class)[0];
$screen = $metadata->newInstance();
echo $screen->title, ' ', $screen->options->pageSize, "\n";

Avec ces valeurs, la sortie est Reports 20. TITLE est une constant de class typée, syntaxe disponible depuis PHP 8.3 ; les accès directs après new ReflectionClass(...) utilisent ici PHP 8.4. Screen et Options sont nos classes locales, pas une variante imaginaire de l'API Route. L'écran n'est ni dessiné ni paginé : seul un lecteur futur pourra exploiter ces valeurs. La lecture des arguments évaluera bien new Options(20) ; « constant » n'implique donc pas l'absence de toute construction d'object.

Avant / après, pour Route : on ne peut pas écrire le chemin dynamique, on écrit le modèle et la valeur arrivera plus tard.

#[Route(path: getPath())]   ✗ ne compile pas (appel de fonction)
#[Route('/blog/{id}')]      ✓ modèle constant ; 42 viendra de la Request

Lire

À retenir en priorité
  1. getArguments() évalue les arguments sans instancier l'attribute extérieur ; un new imbriqué peut construire un objet.
  2. newInstance() déclenche le constructor et les contrôles de cible et répétition.
  3. Si le constructor lance une RuntimeException, newInstance() propage cette exception : le catch (RuntimeException) la reçoit et le chemin de succès est interrompu.

Où en est-on ? Étape 3 sur 3 : l'attribute est défini et posé. Reste l'étape qui lui donne un effet : le lecteur. On reprend les trois niveaux du schéma (getAttributes, getArguments, newInstance) et on dit ce que chacun contrôle.

Notre outil sait maintenant quelle métadonnée chercher. Il commence par obtenir une réflexion de la class ou de la méthode, puis appelle getAttributes(Nom::class). Le filtre compare le nom exact de la class d'attribute. Pour inclure ses sous-classes, il faut ReflectionAttribute::IS_INSTANCEOF ; ce drapeau ne décide pas à lui seul de l'héritage des routes d'un controller.

Pour afficher un inventaire, getArguments() peut suffire : il évalue les arguments et conserve leurs clés positionnelles ou nommées, sans construire l'attribute externe. Pour #[Route('/blog', name: 'b')], le résultat est ['/blog', 'name' => 'b'], pas un array où PHP aurait renommé le premier argument en path. Si les arguments contiennent new Options(20), cette évaluation construit en revanche l'object imbriqué.

Pour exploiter les propriétés de Screen ou Route, notre lecteur appelle newInstance(). C'est alors que PHP construit l'attribute et signale une cible non autorisée, une répétition interdite ou un constructor qui refuse ses arguments. Récupérer une description prouve donc sa présence, pas la validité de son usage. Et obtenir l'object ne lance toujours pas le controller : le lecteur reste responsable de ce qu'il en fait.

Vérifié sur PHP : un attribute TARGET_METHOD posé sur une class → getAttributes() rend 1 description, puis newInstance() lève Error: Attribute "M" cannot target class (allowed targets: method) ; deux #[L] sans IS_REPEATABLE → 2 descriptions, puis Attribute "L" must not be repeated à newInstance() ; filtre Base::class sans drapeau → 0 résultat, avec IS_INSTANCEOF → 1.

🌍 In Real Life

La situation : inventorier les étiquettes, lire leurs indications et construire l'objet décrit sont trois opérations distinctes.

L’équivalent dans Symfony : inventaire → getAttributes() ; arguments évalués → getArguments() ; construction et contrôles d'usage → newInstance().

Retour à la réalité technique : trouver une description ne valide pas sa cible ou sa répétition. Lire les arguments peut construire un objet imbriqué avec new, sans construire l'attribute externe. Le filtre exact nécessite IS_INSTANCEOF pour inclure des sous-classes.

🧠 Comment le mémoriser : « Trouver, lire, construire. » Image mentale : trois opérations sur une même étiquette. Question-réflexe : quelle construction ou vérification a réellement eu lieu ?

⚠️ À ne pas confondre : expressions constantes et absence de toute évaluation ou construction.

Un attribute ressemble à une étiquette de bagage : la poser ne déplace rien. getAttributes() repère les étiquettes ; newInstance() construit leur représentation et contrôle les cibles et répétitions autorisées.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM, avec la raison pour laquelle chaque mauvaise réponse paraît plausible.

  • Voir l’explication : Déclarer un attribute ne l'exécute pas.

    Déclarer un attribute ne l'exécute pas. Si l'outil de rapports ne lit jamais Label, les étiquettes ne classent rien. Pour Route, Symfony dispose d'un loader, à condition que la configuration charge les déclarations concernées. Ce n'est pas PHP qui associe spontanément un chemin à une méthode. Pourquoi on se trompe : la syntaxe #[...] ressemble à un appel, donc on croit qu'elle s'exécute.

  • Voir l’explication : getAttributes() ne construit pas l'attribute.

    getAttributes() ne construit pas l'attribute. Deux descriptions Label peuvent être trouvées même si leur répétition est interdite. Le contrôle arrive à newInstance(). Ne généralise pas cela à tous les arguments : getArguments() évalue un new imbriqué, dont le constructor peut exécuter du code. Distingue la découverte, l'évaluation et la construction externe. Pourquoi on se trompe : on pense que « obtenir l'attribute » le valide.

  • Voir l’explication : Les arguments sont des expressions constantes.

    Les arguments sont des expressions constantes. #[Route(path: getPath())] ne compile pas. Pour la page du blog, le modèle /blog/{id} est déclaré dans le code ; la valeur 42 sera obtenue plus tard au traitement de la Request, et non par un appel de function dans l'attribute. Pourquoi on se trompe : les arguments ressemblent à ceux d'un appel ordinaire, où une function est permise.

  • Voir l’explication : Sans IS_REPEATABLE, répéter un attribute est une erreur

    Sans IS_REPEATABLE, répéter un attribute est une erreur — levée par newInstance() : getAttributes() rend les deux occurrences sans rien dire. Le contrôle de placement suit la même frontière : poser notre Label réservé aux classes sur une méthode ne devient pas valide parce qu'un inventaire a réussi à l'énumérer. Pourquoi on se trompe : on croit que « trouvé » veut dire « valide ».

  • Voir l’explication : Le filtre est exact.

    Le filtre est exact. getAttributes(Base::class) ne trouve pas #[Child] sans IS_INSTANCEOF. Pourquoi on se trompe : on transpose instanceof.

  • Voir l’explication : getArguments() garde les clés écrites.

    getArguments() garde les clés écrites. ['/blog', 'name' => 'b'], pas ['path' => '/blog', ...] : PHP ne devine pas les noms de paramètres.

  • Voir l’explication : Un cas d'enum est une expression constante

    Un cas d'enum est une expression constante (pure ou backed), donc valide en argument.

Relire la route sans exécuter l'action

  • Voir l’explication : Où en est-on ?

    Où en est-on ? On referme la boucle avec le fil rouge du blog : la route /blog/{id} du début du cours.

  • Déclaration de route et mise en cache

    Revenons à BlogController::show, marqué d'un Route décrivant /blog/{id} et nommé blog_show. Un outil d'inspection peut lire ses arguments sans appeler l'action ni consulter ArticleCatalog. Le loader Symfony, lui, exploite ces métadonnées pour construire la configuration de routing. Cette configuration peut ensuite être mise en cache : ne suppose pas que chaque GET /blog/42 reconstruit tous les attributes.

  • Inspection et sélection sans instanciation

    Si l'outil veut seulement inventorier les chemins déclarés, il peut utiliser getArguments() sans instancier Route. S'il veut aussi reconnaître les sous-classes d'une famille de métadonnées, il choisit getAttributes(Base::class, ReflectionAttribute::IS_INSTANCEOF). Ce second choix élargit la sélection ; il n'exécute pas les descriptions trouvées.

  • Métadonnées PHP contre données de Request

    Lors du futur matching, les valeurs placées dans Request::attributes seront encore autre chose : des données de cette Request, telles que _route, _controller et id, pas des attributes PHP #[...]. Nous avons préparé une règle déclarative ; le parcours HTTP expliquera quand cette règle sert à choisir l'action puis ses arguments.

   AVANT la requête (configuration)          PENDANT GET /blog/42
┌─────────────────────────────────┐      ┌────────────────────────────────┐
│ #[Route('/blog/{id}')] sur show │      │ matching → Request::attributes │
│ loader lit les attributes PHP   │ ───► │   _route, _controller, id=42   │
│ → configuration (peut être cache)│     │ (données de la requête, pas    │
└─────────────────────────────────┘      │  des attributes PHP #[...])    │
                                         └────────────────────────────────┘

🌍 In Real Life

La situation : le plan du restaurant décrit où orienter les demandes ; le bon de la visite porte, lui, les valeurs de cette demande précise.

L’équivalent dans Symfony : règle du plan → attribute PHP Route lu par le loader ; informations du bon → _route, _controller, id dans Request::attributes après matching.

Retour à la réalité technique : inspecter Route n'appelle pas le controller. La configuration peut être mise en cache ; chaque GET ne réinstancie pas nécessairement les attributes. HttpKernel coordonnera ensuite résolution du callable et de ses arguments.

🧠 Comment le mémoriser : « Règle déclarée, valeurs de la demande. » Image mentale : plan fixe à côté du bon 42. Question-réflexe : parle-t-on de #[...] ou du sac de la Request ?

⚠️ À ne pas confondre : _format ou id de route et query parameters après ?.

Fiche express

À mémoriser

De la méthode déclarée à la métadonnée exploitable, retiens six étapes :

  • #[Attribute(cibles | IS_REPEATABLE)] sur une class ordinaire.
  • Arguments = expressions constantes ; new admis depuis 8.1.
  • Un attribute est inerte sans lecteur.
  • getAttributes() → ReflectionAttribute, nom exact (sinon IS_INSTANCEOF).
  • getArguments() : arguments évalués, clés conservées ; un new imbriqué peut construire un object. newInstance() construit l'attribute externe.
  • Cible, répétition, constructor : erreurs à newInstance().

🧠 À retenir pour la certification : déclarer (#[Attribute]), poser (arguments constants), lire (réflexion) sont trois temps ; getAttributes() découvre, getArguments() évalue, newInstance() construit et contrôle ; sans lecteur, un attribute ne fait rien ; Route = TARGET_CLASS | TARGET_METHOD | IS_REPEATABLE lu par le loader de routing.

Moyen mnémotechnique : « Décrire, découvrir, évaluer, construire, exploiter. » Seules les deux dernières opérations réunies permettent au lecteur de donner un usage à l'object ; aucune ne remplace le traitement de l'article.

Revoir : L'essentiel

Does getAttributes() construct attribute objects?

No. It returns ReflectionAttribute objects. newInstance() constructs the attribute and propagates any exception thrown by its constructor.

getArguments() évalue les arguments sans instancier l'attribute extérieur ; un new imbriqué peut construire un objet. newInstance() déclenche le constructor et les contrôles de cible et répétition. Si le constructor lance une RuntimeException, newInstance() propage cette exception : le catch (RuntimeException) la reçoit et le chemin de succès est interrompu.

Revoir : Déclarer

How does an attribute allow repeated use on one declaration?

Its Attribute flags include Attribute::IS_REPEATABLE.

Les flags définissent les cibles de l'attribute. IS_REPEATABLE autorise plusieurs occurrences au même endroit.

Revoir : Poser

Can an attribute argument call an ordinary function?

No. Arguments must be constant expressions; new expressions are allowed since PHP 8.1.

Un argument d'attribute est une expression constante. Une variable ou un appel de function ne convient pas.

Can one instance read a private property of another instance of the same class?

Yes, when the access occurs in that class's scope.

private limite l'accès au code de la class qui déclare la propriété, pas à une seule instance. Une method de cette class peut donc lire la propriété privée d'une autre instance de la même class.
