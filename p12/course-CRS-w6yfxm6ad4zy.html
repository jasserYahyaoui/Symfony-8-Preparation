Objectif

Le controller reçoit déjà son ArticleCatalog. Un service de présentation doit maintenant choisir comment transformer un libellé, et une seconde implémentation rend ce choix moins évident. Nous allons expliquer comment l'autowiring utilise types, aliases et instructions explicites, puis diagnostiquer une sélection incorrecte sans chercher un objet au hasard pendant /blog/42.

Question directrice : quand un constructeur écrit seulement un type, comment Symfony sait-il quel objet y mettre ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le type guide la résolution.
  2. Le nom seul n'identifie pas normalement un service.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Écrire à la main, pour chaque service, la liste de ses arguments est long et fragile. L'autowiring évite cette liste : le constructeur dit ce dont il a besoin (un type), Symfony trouve qui le fournit.
  • Le piège de fond. Le type seul ne suffit que s'il n'y a qu'un choix évident. Dès qu'il y en a deux, il faut exprimer l'intention (alias par défaut, alias nommé, #[Target]) : Symfony ne devine jamais.
  • Ce que l'auteur veut que vous compreniez. L'autowiring se fait à la compilation, à partir de types, pas du nom de variable, et il ne sait pas câbler un scalaire sans instruction.
  • Pourquoi c'est à l'examen. On vous demande ce qu'un argument reçoit selon son type, son nom, un #[Target] ou une faute de frappe, et la différence entre les attributs Autowire*.

L'autowiring prépare les arguments d'une définition autowirée à partir des types et des choix de configuration. Un identifiant correspondant au type, ou un alias vers le service choisi, fournit le lien. Une définition concrète peut aussi être enregistrée sous le nom d'une interface : un alias distinct n'est alors pas obligatoire.

La découverte peut créer un alias lorsqu'une seule implémentation appropriée est trouvée. Plusieurs candidats sans choix ne permettent pas de deviner l'intention métier. Un alias par défaut, un alias nommé ou Target exprime cette intention ; un argument explicite ou un binding peut déjà l'avoir fournie. Une valeur scalaire ne se déduit pas de son seul type.

🌍 In Real Life

La situation : le préparateur raccorde chaque poste à l'outil compatible prévu par le plan ; une autre fiche attribue les rôles des postes.

L’équivalent dans Symfony : choix des raccordements → autowiring des dépendances ; attribution de rôles selon les règles → autoconfiguration, notamment des tags.

Retour à la réalité technique : l'autowiring prépare les arguments des définitions à partir des types et de la configuration. L'autoconfiguration ajoute de la configuration liée aux types ou attributes ; elle ne choisit pas à sa place toutes les dépendances. Ces mécanismes supposent des services enregistrés et les options correspondantes activées.

🧠 Comment le mémoriser : « Raccorder n'est pas attribuer un rôle. » Image mentale : un câble et une étiquette distincts sur le même poste. Question-réflexe : résout-on un argument ou ajoute-t-on une configuration de rôle ?

⚠️ À ne pas confondre : câblage du constructeur à la compilation et résolution des arguments d'une action pour une Request.

Le schéma

À retenir en priorité
  1. L'inférence nécessite un seul candidat.
  2. Configurer l'alias pour décider.

Où en est-on ? Avant d'entrer dans le détail, voici la décision complète que prend l'autowiring pour un argument TransformerInterface. Les sections suivantes expliquent chaque flèche.

Nous gardons ROT13 comme laboratoire de sélection, non comme transformation utile du titre publié. Le diagramme suppose les deux aliases définis plus bas et aucun autre argument explicite :

Orange : résolution pendant la compilation ; vert : choix obtenu ; rouge : cible explicite introuvable. Le choix Uppercase donne BONJOUR pour l'entrée ASCII bonjour. Le choix ROT13 donne obawbhe. Une mauvaise sélection peut donc produire un résultat valide en PHP mais incorrect pour l'usage attendu : tester seulement la compilation ne suffit pas à vérifier le libellé.

Le fil rouge : deux transformers

À retenir en priorité
  1. Le type peut garder plusieurs usages.
  2. Le nom ciblé départage les implémentations.

Où en est-on ? On pose le décor : deux classes qui respectent le même contrat. C'est exactement la situation où le type seul ne suffit plus.

Un transformer implémente ici le contrat local qui transforme une string en une autre. Ces déclarations appartiennent au namespace utilisé par le YAML ; chacune occupe son fichier PSR-4 dans le projet :

namespace App\Util;

interface TransformerInterface { public function transform(string $value): string; }
class Rot13Transformer implements TransformerInterface
{
    public function transform(string $value): string { return str_rot13($value); }
}
class UppercaseTransformer implements TransformerInterface
{
    public function transform(string $value): string { return strtoupper($value); }
}

Les deux objets acceptent bonjour, mais rendent des valeurs différentes. ROT13 n'est pas un chiffrement de secret ; strtoupper() dans ce laboratoire n'est pas une normalisation Unicode générale ni un échappement HTML.

Ajouter UppercaseTransformer peut rendre ambigu un consommateur qui dépendait d'un alias automatique à candidat unique. Cela ne casse pas un alias explicite déjà dirigé vers Rot13Transformer. Le problème est l'absence de choix, pas l'existence de deux classes en soi.

La règle, en une phrase : par le type

À retenir en priorité
  1. Le type reste déterminant.
  2. Les aliases nommés ajoutent une sélection particulière.

Où en est-on ? Étape 1 sur 5. Question : sur quoi Symfony se base-t-il pour remplir un argument ? Réponse : sur le type, jamais sur le nom de la variable (sauf alias nommé, vu plus loin).

Dans le cas simple sans sélection nommée, le container cherche le lien correspondant au type demandé. Renommer $transformer en $outil ne crée pas ce lien. Psr\Log\LoggerInterface, par exemple, peut être relié à l'identifiant logger.

Mécanisme, étape par étape, pour __construct(App\Formatter $formatter) :

Je dois câbler App\Report
        ↓
Je lis le constructeur : un argument de type App\Formatter
        ↓
Existe-t-il un service dont l'identifiant EST « App\Formatter »
(ou un alias de ce nom) ?
        ↓ oui                               ↓ non
on injecte cette référence        erreur de compilation (si le service est conservé)

Le même principe s'observe sur un formatter du rapport d'import, avec App\Formatter sans argument requis et App\Report dont le constructeur demande App\Formatter $formatter :

services:
    app.formatter:
        class: App\Formatter
    App\Formatter: '@app.formatter'
    App\Report:
        autowire: true

Le Report conservé reçoit l'objet construit sous app.formatter. Sans cet alias, renommer l'argument ne remplace pas un câblage manquant. Le fragment suppose que ces classes existent et que le report est utilisé ; il ne crée ni rapport ni fichier à la compilation.

Un type union ou intersection ne donne pas une règle de préférence entre plusieurs services. Une configuration peut fournir le type complet, ou ses aliases constitutifs doivent converger vers le même service dans la résolution combinée. Deux aliases vers des cibles différentes ne signifient pas « prendre le premier ». L'objet retenu doit encore satisfaire les règles PHP : une intersection exige les deux contrats, une union autorise l'un des types.

Type demandé Ce que Symfony cherche Si les deux types mènent à des services différents
A le lien du type A —
A\|B (union) le type complet, ou des aliases qui convergent échec, pas de « premier gagnant »
A&B (intersection) idem ; l'objet doit respecter A et B échec

🌍 In Real Life

La situation : un poste réclame un outil d'un type précis ; renommer le tiroir du poste ne crée pas le raccord manquant vers cet outil.

L’équivalent dans Symfony : type d'outil demandé → type PHP de l'argument ; raccord connu → identifiant de service correspondant ou alias de type ; nom du tiroir → nom de variable, hors sélection nommée.

Retour à la réalité technique : dans le cas simple décrit, le type guide l'autowiring. Union et intersection n'ordonnent pas arbitrairement les candidats ; le câblage doit être résolu et l'objet respecter le type PHP.

🧠 Comment le mémoriser : « Chercher le raccord du type. » Image mentale : une prise étiquetée avec son type. Question-réflexe : quel service ou alias correspond au contrat demandé ?

⚠️ À ne pas confondre : règle par type et sélection nommée ; un alias nommé ou une instruction explicite peut préciser le choix.

Pourquoi une interface a besoin d'un alias

À retenir en priorité
  1. L'interface décrit un contrat.
  2. L'alias relie ce contrat à un service.

Où en est-on ? Étape 2 sur 5. Question : pourquoi UppercaseTransformer ne suffit-il pas à satisfaire TransformerInterface automatiquement ? Parce qu'une interface n'est pas un identifiant de service.

Une interface décrit des méthodes, pas l'identifiant à choisir parmi toutes ses implémentations. Lors de la découverte par ressource, Symfony peut créer le lien pour un candidat unique sans choix déjà déclaré. Avec plusieurs candidats, un consommateur conservé et aucun câblage suffisant, la compilation signale l'interface non résolue.

Choisir explicitement Rot13Transformer stabilise ce défaut : UppercaseTransformer peut alors rester disponible pour un autre usage. Le titre de cette section désigne ce besoin de liaison, pas l'obligation absolue d'un objet Alias si une définition porte déjà le nom du type.

#[AsAlias] peut exprimer ce choix sur une class dans le parcours de découverte qui traite ses attributes. Sans identifiant explicite, l'inférence suppose notamment une seule interface implémentée. Poser cet attribute sur une class déclarée seulement un par un ne déclenche pas ce parcours de découverte ; un alias YAML explicite reste alors une solution directe.

 Découverte par resource                  Alias créé ?
┌───────────────────────────────┐   ┌────────────────────────────────────┐
│ 1 seule implémentation        │ → │ oui, automatiquement               │
│ 2 implémentations, rien d'autre│ → │ non : erreur si consommateur gardé │
│ 2 impl. + alias / #[AsAlias]  │ → │ le choix déclaré s'applique        │
└───────────────────────────────┘   └────────────────────────────────────┘

🌍 In Real Life

La situation : deux outils satisfont la même exigence, mais un seul doit être choisi pour ce poste ; leur ordre sur l'étagère ne décide pas du besoin.

L’équivalent dans Symfony : exigence → interface ; outils compatibles → implémentations ; décision explicite → liaison vers le service choisi, souvent un alias.

Retour à la réalité technique : la découverte peut créer un alias pour un candidat unique. Plusieurs candidats sans choix suffisant rendent un consommateur autowiré conservé ambigu. Un choix explicite existant reste valable quand une nouvelle implémentation arrive. Une définition nommée comme le type peut aussi fournir le lien sans objet Alias distinct.

🧠 Comment le mémoriser : « Plusieurs possibles : exprimer le choix. » Image mentale : une flèche volontaire vers l'un des deux outils. Question-réflexe : ce défaut est-il déduit ou déclaré ?

⚠️ À ne pas confondre : interface compatible et implémentation adéquate au métier ; compiler ne prouve pas que le libellé obtenu est celui attendu.

Trois façons de départager

À retenir en priorité
  1. Le fallback peut masquer une faute de nom.
  2. Target rend le choix explicite.

Où en est-on ? Étape 3 sur 5. Le défaut est posé ; comment un consommateur particulier obtient-il l'autre implémentation ? Trois leviers, du plus implicite au plus explicite.

Enregistrons les deux classes et un consommateur de laboratoire, puis déclarons le défaut et l'usage nommé :

services:
    App\Util\Rot13Transformer: ~
    App\Util\UppercaseTransformer: ~
    App\Util\MessageBuilder:
        autowire: true
        public: true
    App\Util\TransformerInterface: '@App\Util\Rot13Transformer'                          # 1. alias par défaut
    App\Util\TransformerInterface $shoutyTransformer: '@App\Util\UppercaseTransformer'   # 2. alias nommé

Le consommateur est public uniquement pour faciliter son observation. Son attribute garde le rôle nommé même si la propriété s'appelle simplement $transformer :

namespace App\Util;

use Symfony\Component\DependencyInjection\Attribute\Target;

final class MessageBuilder
{
    public function __construct(
        #[Target('shoutyTransformer')] private TransformerInterface $transformer,   // 3. #[Target]
    ) {}

    public function build(string $value): string
    {
        return $this->transformer->transform($value);
    }
}

Avec cette configuration chargée et compilée, un MessageBuilder obtenu du container rend BONJOUR pour build('bonjour'). Les variantes suivantes sont des essais indépendants de sa signature :

Argument Reçoit
TransformerInterface $transformer rot13, l'alias par défaut
TransformerInterface $shoutyTransformer upper, l'alias nommé
$shoutyTransfomer, faute de frappe rot13, sans erreur
#[Target('shoutyTransfomer')], même faute erreur : « …but no such target exists. Did you mean… »
#[Target('shouty.transformer')] upper : le nom est normalisé en camelCase

Sans Target, la faute $shoutyTransfomer ne trouve pas l'alias nommé et retombe ici sur le défaut ROT13. Avec Target, la même faute est une sélection explicite invalide : elle ne doit pas être ignorée. Ces résultats supposent le défaut déclaré et l'absence d'un autre binding ou argument explicite.

Pourquoi cette différence ? Le nom d'argument est une convention implicite : s'il ne correspond à aucun alias nommé, Symfony retombe sur le défaut (c'est son comportement normal, pas une erreur). #[Target] est une demande explicite : si elle ne peut pas être satisfaite, la retomber sur le défaut cacherait une erreur du développeur ; Symfony échoue donc.

Alias par défaut Alias nommé #[Target]
Déclaré où ? Interface: '@Service' Interface $nom: '@Service' attribut sur l'argument
Sélection par le type seul type + nom d'argument nom d'usage explicite
Faute de frappe — retombe sur le défaut, sans erreur erreur de compilation

registerAliasForArgument() permet de préparer un alias nommé depuis une passe. Pour inspecter les choix de l'application :

php bin/console debug:autowiring Transformer

Résultat attendu avec ce laboratoire : les types et usages nommés correspondants, dont shoutyTransformer. La commande n'est pas exécutée ici et ne crée aucun des aliases affichés.

🌍 In Real Life

La situation : le poste reçoit l'outil standard sauf demande d'un usage particulier ; une demande explicite mal écrite doit être signalée.

L’équivalent dans Symfony : outil standard → alias par défaut ; usage nommé → alias type plus nom ; demande explicite d'usage → #[Target].

Retour à la réalité technique : dans le laboratoire, le nom d'argument mal orthographié peut retomber sur ROT13, alors qu'un Target introuvable produit une erreur. Ce contraste suppose le défaut déclaré et l'absence d'un autre binding ou argument explicite.

🧠 Comment le mémoriser : « Une intention explicite ne se devine pas. » Image mentale : une demande nominative refusée plutôt que remplacée silencieusement. Question-réflexe : le choix vient-il du défaut, du nom ou d'un Target explicite ?

⚠️ À ne pas confondre : absence d'erreur de câblage et résultat métier correct ; obawbhe et BONJOUR sont tous deux des strings.

Ce que `#[Target]` attend

À retenir en priorité
  1. Target sélectionne un alias nommé.
  2. Ne pas le traiter comme un identifiant arbitraire.

Où en est-on ? Étape 4 sur 5. Question : que doit-on écrire exactement dans #[Target('...')] ? Un nom d'usage, pas un identifiant de service.

Utilisons le nom de l'usage publié, shoutyTransformer, plutôt qu'un identifiant interne arbitraire. Le nom shouty.transformer est normalisé en camelCase pour retrouver cet usage. Il ne signifie pas « chercher automatiquement un service littéralement nommé shouty.transformer ».

Avant / après de la normalisation (Target::getParsedName()) :

 Écrit dans #[Target(...)]      Normalisé en camelCase      Alias nommé cherché
 'shouty.transformer'    ───▶   shoutyTransformer     ───▶  $shoutyTransformer
 'shoutyTransformer'     ───▶   shoutyTransformer     ───▶  $shoutyTransformer

Nuance d'implémentation Symfony 8.0 : un identifiant peut aussi être accepté lorsqu'il est déjà la cible d'un alias nommé du même type. Ce n'est pas un accès libre à tout service par Target. Pour imposer directement un identifiant, #[Autowire(service: '...')] exprime mieux le contrat. Une cible Target introuvable reste une erreur dans notre consommateur obligatoire, même si le défaut général existe.

🌍 In Real Life

La situation : le poste demande un usage publié dans le catalogue, pas n'importe quel numéro de stock interne.

L’équivalent dans Symfony : nom d'usage → valeur habituelle de Target ; numéro interne imposé directement → Autowire(service: ...).

Retour à la réalité technique : shouty.transformer est normalisé pour retrouver l'usage nommé shoutyTransformer. La compatibilité avec un identifiant déjà cible d'un alias nommé du même type reste un cas borné ; Target n'est pas un accès libre au conteneur.

🧠 Comment le mémoriser : « Target nomme l'usage. » Image mentale : une rubrique du catalogue, distincte du registre de stock. Question-réflexe : vise-t-on un usage d'autowiring ou directement un identifiant de service ?

⚠️ À ne pas confondre : normalisation du nom et correction automatique d'une cible inexistante.

Câbler ce qui n'est pas un service

À retenir en priorité
  1. Un scalaire n'est pas déduit du type.
  2. Configurer sa valeur volontairement.

Où en est-on ? Étape 5 sur 5. Jusqu'ici l'argument était un objet identifié par son type. Mais un constructeur demande aussi des chaînes, des booléens, des chemins : un string ne dit pas quelle chaîne. Il faut une instruction explicite : l'attribut #[Autowire].

La présentation reçoit aussi un directory de données et des options. Voici des arguments de constructeur, avec Autowire importé depuis Symfony\Component\DependencyInjection\Attribute et LoggerInterface depuis Psr\Log. La class consommatrice doit être enregistrée et autowirée :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[Autowire(service: 'logger')] LoggerInterface $logger,
#[Autowire('%kernel.project_dir%/data')]       string $dataDir,
#[Autowire(param: 'kernel.debug')]             bool $debug,
#[Autowire(env: 'bool:FEATURE_FLAG')]          bool $flag,

Avec le logger disponible, kernel.project_dir=/srv/blog, kernel.debug=false et FEATURE_FLAG='true', les valeurs attendues sont le logger, /srv/blog/data, false et true. Le chemin n'est pas créé ; le flag ne décide pas à lui seul quelle fonctionnalité l'application exécute. Une string obligatoire non configurée dans un consommateur conservé provoque un diagnostic ; un privé inutilisé peut être retiré avant que certaines erreurs différées d'autowiring soient signalées.

Écriture Ce qui est injecté
#[Autowire(service: 'logger')] le service logger
#[Autowire('%kernel.project_dir%/data')] une expression avec paramètre : /srv/blog/data
#[Autowire(param: 'kernel.debug')] la valeur du paramètre
#[Autowire(env: 'bool:FEATURE_FLAG')] la variable d'environnement, castée en bool

Pour un rapport coûteux et rarement utilisé, distinguons aussi obtenir l'objet et appeler une de ses méthodes. #[AutowireServiceClosure('app.report')] \Closure $report fournit une closure dont l'appel $report() récupère le service. Elle peut réutiliser un objet partagé déjà construit ; elle ne lance pas automatiquement sa méthode render().

Avec un service local app.report exposant render(): string, #[AutowireCallable(service: 'app.report', method: 'render')] sur un argument \Closure fournit au contraire un appel de méthode : invoquer la closure rend le résultat de render(). #[AutowireMethodOf('app.report')] \Closure $render déduit ce nom de méthode du nom de l'argument. Renommer cet argument change donc le contrat de cette forme courte.

Pour ces closures de méthode, lazy vaut false par défaut : la résolution de l'objet peut avoir lieu lors de leur préparation. lazy: true diffère cette résolution. Ne leur attribuons pas automatiquement la sémantique de ServiceClosure.

 $report()                       →  retourne le SERVICE app.report
 (AutowireServiceClosure)

 $render()                       →  appelle app.report->render()
 (AutowireCallable /                et retourne SON RÉSULTAT
  AutowireMethodOf)

Enfin, #[Required] permet aux passes d'autowiring de traiter une méthode ou une propriété publique typée sur la définition concernée. Il faut un service enregistré et autowiré ; le mot « Required » ne crée pas un lecteur universel d'attributes et ne transforme pas une propriété typée non initialisée en null.

🌍 In Real Life

La situation : le poste reçoit un réglage, un bon pour retirer un appareil plus tard, ou une commande qui déclenche une fonction de cet appareil.

L’équivalent dans Symfony : réglage → paramètre ou valeur env configurée ; bon de retrait → AutowireServiceClosure ; commande de fonction → AutowireCallable ou AutowireMethodOf.

Retour à la réalité technique : appeler la ServiceClosure récupère le service, éventuellement déjà partagé ; appeler la closure de méthode exécute la méthode et rend son résultat. Pour ces dernières, lazy: false peut résoudre l'objet dès la préparation ; lazy: true diffère cette résolution. Un type scalaire seul ne révèle pas sa valeur.

🧠 Comment le mémoriser : « Retirer l'appareil ou le faire agir ? » Image mentale : bon de retrait à côté d'un bouton de commande. Question-réflexe : l'appel de cette closure retourne-t-il le service ou le résultat d'une méthode ?

⚠️ À ne pas confondre : récupération différée, nouvelle instance garantie et travail asynchrone ; aucune de ces équivalences n'est automatique.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une union ne résout pas l'ambiguïté.
  2. Les types doivent aboutir au même choix.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Pour chaque piège : l'énoncé, puis pourquoi la mauvaise réponse paraît plausible.

  • Voir l’explication : Le nom peut compter.
    • Le nom peut compter. Le type fournit le contrat, mais les instructions explicites et usages nommés peuvent préciser la sélection. Renommer n'est pas toujours neutre. Plausible car « autowiring par type » fait croire que le nom ne compte jamais.
    • Une seconde implémentation ne détruit pas un choix explicite ; elle révèle l'ambiguïté d'un choix auparavant implicite. Plausible car l'erreur apparaît en ajoutant une classe, on accuse la classe.
    • Dans notre tableau, une faute de nom retombe sur ROT13, alors qu'une faute de Target échoue. Sans défaut, la première situation change aussi. Plausible car les deux fautes semblent équivalentes.
    • Target exprime un usage nommé, pas une recherche libre par identifiant ; sa compatibilité particulière avec certaines cibles d'aliases reste bornée. Plausible car Autowire(service:) accepte, lui, un identifiant.
    • Un scalaire n'est pas déduit du seul type ; Autowire, bind ou un argument explicite peut pourtant le fournir. Plausible car l'objet, lui, est déduit du type.
    • Union et intersection ne donnent pas une priorité arbitraire entre services ; la résolution doit converger et l'objet respecter le type PHP. Plausible car PHP, pour une union, accepte n'importe lequel des types.
    • AsAlias dépend du parcours de découverte applicable ; écrire un attribute sur une class non découverte ne suffit pas à créer le choix. Plausible car un attribut semble se suffire à lui-même.

Fiche express

À mémoriser

À retenir en priorité
  1. AutowireServiceClosure diffère la récupération du service ; cette règle ne s'étend pas à AutowireCallable, dont lazy vaut false par défaut.
  2. L'injection seule ne construit pas le service.

Pour vérifier le libellé avant de l'afficher :

  1. Retrouver la définition autowirée et le type de son argument.
  2. Lire les arguments explicites, bindings et aliases applicables.
  3. Stabiliser le défaut si plusieurs implémentations sont disponibles.
  4. Nommer les usages particuliers et tester leur résultat concret.
  5. Traiter un Target introuvable comme un choix invalide, pas un défaut implicite.
  6. Fournir les scalaires explicitement et distinguer closure d'accès au service et closure d'appel d'une méthode.
  7. Vérifier le contrat PHP final, notamment pour les types combinés.

Si l'application doit choisir un seul service parmi plusieurs à l'exécution, plutôt qu'un choix fixé lors du câblage, un locator restreint peut être le bon outil.

🧠 À retenir pour la certification

  • L'autowiring câble à la compilation, par type ; renommer la variable ne crée pas de lien (sauf alias nommé).
  • Interface : une seule implémentation découverte → alias auto ; plusieurs et rien d'explicite → échec ; #[AsAlias] sur la classe choisie (si découverte).
  • Trois leviers : alias par défaut, alias nommé (Interface $nom), #[Target].
  • Faute de nom d'argument → retombe sur le défaut sans erreur ; faute dans #[Target] → erreur ; Target normalise en camelCase.
  • Union/intersection : pas de priorité ; type complet ou aliases convergents.
  • Scalaires : #[Autowire(service|param|env)] ; AutowireServiceClosure → le service ; AutowireCallable/AutowireMethodOf → le résultat de la méthode.
  • Différer le choix à l'exécution → locator restreint.

Phrase de mémorisation : « Le type désigne la prise, l'alias choisit la fiche, Target nomme l'usage, et un scalaire ne se devine jamais. »
