Objectif

Après l'import d'un article, un journal et un autre service peuvent devoir réagir. Le service d'import ne devrait pas nommer tous ces destinataires. EventDispatcher lui permet de distribuer un événement ; un registre préparé séparément choisit les réactions à appeler. Le même mécanisme permet à HttpKernel de publier les étapes de GET /blog/42.

Ce cours suit le mécanisme en trois étapes : dans quel ordre les listeners sont appelés (priority), comment on les inscrit (listener ou subscriber), quel nom sélectionne la liste appelée (distribuer).

L'essentiel

À comprendre

À retenir en priorité
  1. Le tri est décroissant.
  2. Les priorities négatives sont autorisées.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Sans dispatcher, le service d'import appellerait directement le journal, puis le service de notification, etc. Chaque nouvelle réaction obligerait à modifier l'import. Le dispatcher inverse la dépendance : l'émetteur publie un fait, les réactions s'inscrivent ailleurs.
  • Le piège de fond. « S'abonner » n'est pas « être appelé tout seul » : il faut qu'un registre ait été rempli, et la sélection se fait par nom exact, jamais par ressemblance ni par type parent.
  • Ce que l'auteur veut que vous compreniez. Le trio registre → nom → priority : le dispatcher choisit une liste par nom, la trie par priority décroissante, puis appelle chaque callback de façon synchrone.
  • Pourquoi c'est à l'examen. Les QCM portent sur l'ordre (priority, égalité), le nom par défaut (la classe de l'event), la méthode choisie par #[AsEventListener] (on + nom camélisé, repli __invoke()) et le contraste listener / subscriber.

Le dispatcher tient un registre de listeners par nom d'event et les notifie quand l'event est distribué : le code qui déclenche ne connaît pas ceux qui écoutent. La priority la plus haute passe en premier ; à égalité, l'ordre d'ajout décide. On s'inscrit par un listener, branché de l'extérieur, ou un subscriber, qui se déclare lui-même.

Un listener est le callback appelé ; un subscriber regroupe la déclaration de ses abonnements. « Se déclare » ne veut pas dire « s'enregistre tout seul » : il faut l'ajouter au dispatcher, directement ou via l'intégration du framework. Ces appels sont synchrones : le service émetteur attend leur fin. Une tâche asynchrone nécessite un autre mécanisme, par exemple un message Messenger effectivement routé vers un transport asynchrone.

              ──▶ Notifier                                  │

Le schéma

À retenir en priorité
  1. L'égalité conserve l'ordre d'ajout.
  2. La priority ne suffit pas à décrire tous les cas.

Où en est-on ? Vue d'ensemble avant les trois notions : d'abord on prépare un registre (une fois), ensuite chaque dispatch() lit ce registre. Les trois sections qui suivent zooment sur l'ordre, l'inscription et la sélection par nom.

Lire d'abord la flèche pointillée : l'enregistrement prépare le registre, sans exécuter la réaction métier. Puis un dispatch sélectionne un nom et appelle ses listeners. Ce n'est pas une nouvelle compilation des services :

Gris/pointillé : enregistrement préalable ; bleu : exécution synchrone ; vert : retour. Ajouter un listener ne déclenche pas l'événement. Un nom explicite remplace le nom de classe : écouter OrderPlacedEvent::class ne reçoit pas automatiquement un dispatch nommé order.placed. Un arrêt de propagation ou une exception peut empêcher d'atteindre les listeners suivants.

Exemple concret

À retenir en priorité
  1. Le publisher exprime un fait.
  2. Le registre du dispatcher choisit les listeners.

Où en est-on ? Avant de détailler chaque notion, un code minimal qui montre les deux façons d'inscrire une réaction. Retenez seulement : un #[AsEventListener] sur une classe, et un subscriber qui liste ses events.

L'achat est ici une variante du même besoin de notification après un fait métier. OrderPlacedEvent est la classe applicative du cours Event, et non une classe livrée par Symfony. Pour l'import, une classe ArticleImported pourrait porter l'identifiant 42 ; son émission resterait une décision explicite du service, pas un effet du nom.

Ces fragments utilisent les imports suivants et des classes applicatives déjà chargées :

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Component\HttpKernel\KernelEvents;

#[AsEventListener]
final class SendConfirmation
{
    public function __invoke(OrderPlacedEvent $event): void {}   // event déduit du type
}

final class OrderSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [
            KernelEvents::RESPONSE => [['onResponsePre', 10], ['onResponsePost', -10]],
            OrderPlacedEvent::class => 'onPlacedOrder',
        ];
    }
}

Ce que Symfony voit :

Fragment Ce que Symfony en déduit
#[AsEventListener] sans event le nom = classe du type de l'argument de __invoke()
KernelEvents::RESPONSE => [[…, 10], […, -10]] deux callbacks sur kernel.response, priorities 10 et -10
OrderPlacedEvent::class => 'onPlacedOrder' un callback sur le nom OrderPlacedEvent

Le subscriber est ici un fragment de déclaration : fournir les trois méthodes annoncées et enregistrer le service (autoconfiguration active dans le framework, addSubscriber() hors framework). Le dispatcher n'envoie pas de confirmation lui-même : le corps vide du listener ne fait encore aucun métier.

Le tableau mélange volontairement deux abonnements HTTP et un abonnement métier. Distribuer OrderPlacedEvent n'appelle pas onResponsePre() : chaque entrée appartient à son nom d'événement. Les priorités 10 et -10 encadrent les listeners à 0, pas tous les listeners imaginables.

La priority, et son départage

À retenir en priorité
  1. La valeur la plus haute passe d'abord.
  2. Zéro n'est pas une priorité absolue.

Où en est-on ? Étape 1 sur 3 : l'ordre. Le registre contient déjà une liste de callbacks pour un nom ; avant de les appeler, le dispatcher doit décider qui passe en premier.

🌍 In Real Life

La situation : après un import du blog, les collègues consultent le dossier suivant un ordre prévu : préparation avant lecture du bilan.

L’équivalent dans Symfony : rang annoncé → priorité ; à rang égal, inscription antérieure → callback appelé avant le suivant.

Retour à la réalité technique : pour un nom d'événement, les priorités décroissent et les égalités gardent l'ordre d'ajout. Ce classement ne rend ni les appels parallèles ni leurs effets transactionnels.

🧠 Comment le mémoriser : « Le grand nombre passe devant. » Image mentale : badges 10, 0, 0, −5. Question-réflexe : le producteur de cette valeur a-t-il déjà été appelé ?

⚠️ À ne pas confondre : ordre d'enregistrement et ordre final après classement.

Pourquoi l'ordre compte-t-il ? Si un listener lit une valeur qu'un autre prépare, l'ordre devient une partie du contrat. EventDispatcher range les callbacks par nom et priorité, trie ces priorités en ordre décroissant, puis conserve l'ordre d'ajout à l'intérieur d'une même priorité :

  • Un int positif ou négatif, 0 par défaut ; plus il est élevé, plus le listener est appelé tôt.
  • À priority égale, l'ordre d'ajout : ajoutés 0, 0, 10, -5, ils tournent 10, les deux 0 dans leur ordre, puis -5.

Avant / après, sur les quatre listeners du QCM (x 0, y -5, z 10, w 0) :

ordre d'AJOUT :    x(0)   y(-5)   z(10)   w(0)
                    │      │       │       │
tri par priority ──▶ z(10) , x(0) , w(0) , y(-5)
                      └─ égalité x / w : x avant w (ajouté d'abord)

Avec EventDispatcher 8.0 chargé, cet exemple autonome observe l'ordre sans exécuter un import :

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;

$dispatcher = new EventDispatcher();
$order = [];
$dispatcher->addListener('blog.article_imported', static function () use (&$order): void {
    $order[] = 'normal';
});
$dispatcher->addListener('blog.article_imported', static function () use (&$order): void {
    $order[] = 'prioritaire';
}, 10);
$dispatcher->dispatch(new \stdClass(), 'blog.article_imported');
echo implode(', ', $order), PHP_EOL;

Sortie attendue : prioritaire, normal. Le listener ajouté en dernier passe d'abord grâce à 10. À égalité, il passerait après le premier. Un subscriber ne reçoit aucune priorité spéciale du fait de son interface ; ses callbacks entrent dans le même registre.

⚠️ À ne pas confondre : priority et ordre d'ajout

Ordre d'ajout Ordre d'appel
Définition quand on a appelé addListener() priority décroissante, puis ordre d'ajout
Sert à départager les égalités exécuter

Plausible car : « premier inscrit, premier servi » est l'intuition d'une file d'attente. Ici la priority passe avant l'ordre d'ajout, et un nombre bas (négatif) passe en dernier, pas en premier.

Listener ou subscriber

À retenir en priorité
  1. La liste vit dans la class du subscriber.
  2. Un listener peut être configuré de l'extérieur.

Où en est-on ? Étape 2 sur 3 : l'inscription. On sait comment le registre est trié ; reste à savoir comment les callbacks y entrent, et qui porte la déclaration.

🌍 In Real Life

La situation : un collègue du blog reçoit une mission ponctuelle ; un autre arrive avec sa liste de moments à suivre et sait comment réagir.

L’équivalent dans Symfony : callback inscrit pour une mission → listener ; objet exposant ses abonnements et ses méthodes → subscriber.

Retour à la réalité technique : les deux produisent des callbacks enregistrés. getSubscribedEvents() déclare les abonnements du subscriber, mais l'instance exécute les réactions ; elle doit être intégrée au dispatcher.

🧠 Comment le mémoriser : « La liste accompagne celui qui agit. » Image mentale : une personne avec sa liste de missions. Question-réflexe : où sont déclarés les abonnements et où est le comportement ?

⚠️ À ne pas confondre : déclaration statique des abonnements et fichier de configuration sans comportement.

Les deux formes aboutissent à des callbacks. Choisir où faire vivre les abonnements : près de la configuration qui les active, ou dans une classe réutilisable qui expose leur liste :

Listener Subscriber
inscription de l'extérieur : configuration ou #[AsEventListener] lui-même : getSubscribedEvents(), statique
atout (documentation) plus souple : un bundle l'active selon sa configuration plus réutilisable : la connaissance des events vit dans la class

Résolution de la method d'un listener (RegisterListenersPass, 8.0) :

Cas Method appelée
event: 'acme.foo_bar', onAcmeFooBar() présente onAcmeFooBar()
event: 'acme.other', sans onAcmeOther() __invoke(), en repli
pas d'event, __invoke(CustomEvent $e) __invoke(), event déduit du type
ni l'une ni l'autre la compilation du container échoue

#[AsEventListener] se répète pour configurer plusieurs methods ; un subscriber peut inscrire plusieurs methods sur un même event.

Pourquoi un simple attribut suffit-il dans le framework ? Parce que l'autoconfiguration pose les tags à votre place, puis un compiler pass les lit :

#[AsEventListener]            ─▶ tag kernel.event_listener  ─┐
implements EventSubscriber…   ─▶ tag kernel.event_subscriber ─┤
 (règles : FrameworkExtension)                               ▼
                                   RegisterListenersPass lit les tags
                                   et prépare les abonnements
                                   (méthode : tableau ci-dessus)

Dans le framework, FrameworkExtension enregistre les règles d'autoconfiguration : l'attribut produit le tag kernel.event_listener, l'interface du subscriber le tag kernel.event_subscriber. Le compiler pass RegisterListenersPass lit ces définitions et prépare les abonnements, avec la résolution de méthode décrite dans le tableau. L'autowiring, lui, résout les dépendances des services : ces responsabilités ne se confondent pas.

Une classe exclue de la découverte des services n'est pas rendue active par le seul attribut. Et new EventDispatcher() autonome ne parcourt pas les attributs des classes : utiliser addListener() ou addSubscriber(). Cette préparation se distingue des appels de listeners pendant la requête.

⚠️ À ne pas confondre : autoconfiguration et autowiring

Autoconfiguration Autowiring
Rôle ici poser les tags depuis l'attribut / l'interface injecter les dépendances du service
Quand compilation du container compilation du container
Concerne l'abonnement à un event les arguments du constructeur

Plausible car : les deux « se font tout seuls » dans le framework et reposent sur les types. Mais aucun n'existe avec un new EventDispatcher() autonome : il faut alors addListener() / addSubscriber().

Distribuer

À retenir en priorité
  1. Le FQCN sert de nom par défaut.
  2. Un nom explicite peut être fourni.

Où en est-on ? Étape 3 sur 3 : la sélection par nom. Le registre est trié et rempli ; voyons comment un dispatch() choisit la bonne liste, et ce que reçoivent émetteur et listeners.

🌍 In Real Life

La situation : le secrétariat du blog appelle les personnes inscrites sous l'intitulé exact « article importé », pas toutes celles inscrites sous un thème ressemblant.

L’équivalent dans Symfony : intitulé choisi → nom d'événement ; registre de cet intitulé → listeners sélectionnés ; dossier transmis → même objet event.

Retour à la réalité technique : sans nom explicite, la classe effective fournit ce nom. EventDispatcher ne diffuse pas automatiquement aux classes parentes et interfaces. Les alias préparés par l'intégration ne sont pas un polymorphisme général.

🧠 Comment le mémoriser : « Une étiquette, une liste. » Image mentale : un tiroir portant le nom complet. Question-réflexe : quel nom exact est dispatché ?

⚠️ À ne pas confondre : sélection par nom d'événement et résolution des handlers Messenger par type.

dispatch($event) ou dispatch($event, 'foo.event'). Sans nom, la class de l'object sert de nom, d'où OrderPlacedEvent::class comme key d'abonnement. dispatch() rend l'object event lui-même, modifié par les listeners. Chaque listener reçoit l'event, son nom et le dispatcher, ce qui lui permet d'en distribuer d'autres.

Le nom de classe est le nom complet de la classe effective. Le dispatcher ne cherche pas automatiquement les listeners de ses parents ou interfaces, et ne convertit pas ArticleImported en blog.article_imported. Les alias que l'intégration prépare pour certains événements du framework ne sont pas une diffusion polymorphe générale.

Quel tiroir est ouvert ? (nom exact, pas de ressemblance) :

dispatch(new OrderPlacedEvent())            → nom « …\OrderPlacedEvent »
dispatch(new OrderPlacedEvent(), 'order.placed')  → nom « order.placed »

écoute OrderPlacedEvent::class  ◀── reçoit le 1er, PAS le 2e
écoute 'order.placed'           ◀── reçoit le 2e,  PAS le 1er
écoute la classe parente        ◀── ne reçoit rien automatiquement

En retour normal, l'émetteur récupère le même objet, même sans listener. Les valeurs retournées individuellement par les listeners ne forment pas un résultat agrégé. Si l'un lève une exception, cette boucle ne la collecte pas pour continuer les suivants : elle remonte au caller. Cela diffère du mécanisme de collecte des erreurs des handlers Messenger.

⚠️ À ne pas confondre : EventDispatcher et MessageBus

EventDispatcher MessageBus (Messenger)
Sélection par nom d'event (classe par défaut) par type du message
Exécution listeners synchrones, même requête middlewares, éventuellement transport asynchrone
Exception remonte au caller, suivants non appelés mécanisme de collecte propre aux handlers

Plausible car : les deux ont une méthode dispatch() et un objet qui voyage. Seule la configuration Messenger (routage vers un transport) rend un traitement asynchrone.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La method peut être déduite.
  2. Vérifier la convention lorsqu'aucun nom n'est donné.
  • Voir l’explication : Priority haute = appelé en premier

    Priority haute = appelé en premier, et les valeurs négatives sont permises.

  • Départager des listeners de même priorité

    À priority égale, l'ordre d'ajout décide.

  • Nom implicite d’un événement

    dispatch() sans nom utilise la class de l'event.

  • Voir l’explication : method est optionnelle sur #[AsEventListener]

    method est optionnelle sur #[AsEventListener] ; le défaut est on + nom de l'event, et __invoke() sert de repli.

  • Plusieurs méthodes d’un subscriber pour un événement

    Un subscriber peut inscrire plusieurs methods sur un même event.

  • Voir l’explication : Deux dispatch() ne désignent pas la même abstraction.

    Deux dispatch() ne désignent pas la même abstraction. EventDispatcher appelle ses listeners synchrones ; MessageBus traverse des middlewares et peut envoyer vers un transport configuré. Ni le nom de la méthode ni la priorité ne prouvent un traitement en arrière-plan.

  • Voir l’explication : registre de callbacks par nom, trié par priority, appelé de façon synchrone

    Pourquoi on se trompe : on transpose une intuition (file d'attente, héritage de types, dispatch() = asynchrone) à un mécanisme qui n'est qu'un registre de callbacks par nom, trié par priority, appelé de façon synchrone.

Fiche express

À mémoriser

À retenir en priorité
  1. Les listeners partagent l'object.
  2. Le publisher peut lire le résultat après dispatch().

Le service d'import connaît le fait publié, pas chaque réaction. Cette souplesse impose de documenter le nom, les données, l'ordre et les exceptions acceptées ; elle ne supprime pas les dépendances fonctionnelles entre réactions.

Si tu dois retenir seulement 6 choses :

  • Priority haute d'abord ; négative permise ; égalité → ordre d'ajout.
  • addListener(nom, callable, priority).
  • dispatch($event) sans nom : la class ; rend le même object.
  • Listener souple, subscriber réutilisable.
  • Method par défaut : on + nom camélisé, puis __invoke().
  • Le listener reçoit event, nom, dispatcher.

Moyen mnémotechnique : « Le plus haut parle en premier ».

🧠 À retenir pour la certification

  • Le dispatcher = registre nom d'event → callbacks, appels synchrones.
  • Ordre : priority décroissante (négative permise, 0 par défaut), puis ordre d'ajout.
  • dispatch($event) sans nom : nom = classe effective ; pas de diffusion aux parents/interfaces ; rend le même objet.
  • Chaque listener reçoit ($event, $eventName, $dispatcher) ; son retour est ignoré.
  • Listener = souple (activé de l'extérieur) ; subscriber = réutilisable (getSubscribedEvents() statique, plusieurs methods par event).
  • #[AsEventListener] : method par défaut on + nom camélisé, repli __invoke(), event déduit du type de l'argument.
  • Autoconfiguration (tags kernel.event_listener / kernel.event_subscriber) ≠ autowiring ; hors framework : addListener() / addSubscriber().
  • Exception d'un listener : remonte au caller ; EventDispatcher ≠ MessageBus.

Phrase de mémorisation : « Le registre trie par nom puis par priority décroissante, appelle en synchrone chaque callback — le plus haut parle en premier — et rend l'event ; listener ou subscriber, tout finit comme un callback inscrit sous un nom exact. »

Le registre est compris. Le cours Event précise maintenant ce qui circule et comment un arrêt empêche la suite sans annuler les effets déjà produits.
