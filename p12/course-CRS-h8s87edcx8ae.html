Objectif

La route de GET /blog/42 a fourni une destination ; HttpKernel a obtenu le callable et préparé ses arguments. L'action doit maintenant produire une réponse. Hériter d'AbstractController simplifie cette dernière étape, mais n'effectue ni le matching ni la résolution des arguments à sa place.

Savoir ce que AbstractController apporte, ce qu'il n'apporte pas, et pourquoi il n'est pas un container déguisé. La production de la Response — render(), json(), file() — est traitée dans l'item The response (The response).

Question fil rouge : quand j'écris $this->render(...), d'où vient cette méthode, et où prend-elle Twig ?

L'essentiel

À comprendre

À retenir en priorité
  1. AbstractController est facultatif.
  2. Il vient de FrameworkBundle et apporte des raccourcis.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un contrôleur fait toujours les mêmes gestes : générer une URL, rendre un template, rediriger, lever une 404. Plutôt que de réinjecter router, Twig et serializer partout, FrameworkBundle fournit une classe de confort.
  • Le piège de fond. On confond « confort » et « obligation », et « accès à quelques services » avec « accès à tout le container ».
  • Ce que l'auteur veut que vous compreniez. Trois faits : la classe est optionnelle, ses raccourcis sont protected, et elle reçoit un locator restreint (onze services facultatifs), pas le container.
  • Pourquoi c'est à l'examen. Les nombres (24 / 2 / 2, onze services), le comportement quand un service manque, addLink() et sendEarlyHints() sont des questions classiques.

En résumé : AbstractController, de FrameworkBundle, est une class de base optionnelle : un controller est n'importe quel callable. Elle apporte des raccourcis, tous protected, et reçoit non pas le container mais un locator de onze services, tous facultatifs. Sans un service, le raccourci qui l'exige échoue à l'appel, pas à la compilation ; json() dispose toutefois d'un repli sans Serializer. Le locator implémente bien ContainerInterface, mais n'expose pas tous les services de l'application.

Les arguments de l'action ($id, services) sont remplis par un mécanisme distinct : Argument value resolvers.

Le schéma

Où en est-on ? Le cours répond à quatre questions : est-elle obligatoire ? (non), que contient-elle ? (des raccourcis protected), d'où viennent les outils ? (un locator restreint), comment la tester ? Le schéma montre le chemin d'un seul raccourci, render().

Action de ProductController
   │  $this->render('product/show.html.twig', [...])
   ▼
render()  (hérité, protected)
   │  container->get('twig')        ← locator restreint (11 entrées, setContainer)
   ▼
Twig Environment::render()  →  contenu  →  Response

Ambre = assemblage ; bleu = appels ; vert = résultat. Côté types, ProductController étend AbstractController, qui implémente ServiceSubscriberInterface. Ce contrat déclare les dépendances ; il ne rend aucun template. Le chemin montré suppose Twig disponible et un template existant.

L'exemple

Exemple concret

À retenir en priorité
  1. Le service métier est demandé par un argument typé de l'action.
  2. AbstractController apporte render(), mais ne remplace pas la dependency injection explicite.

Où en est-on ? Un cas concret avant le vocabulaire : une action qui reçoit une donnée de requête et un service, puis rend un template.

Le catalogue de produits ci-dessous joue le même rôle qu'un catalogue d'articles pour /blog/42 : id provient de la route, tandis que le catalogue est un service. L'extrait suppose le contrôleur enregistré avec le câblage des arguments de services et le catalogue disponible dans le conteneur. Son type PHP seul ne crée pas ce service.

final class ProductController extends AbstractController
{
    #[Route('/product/{id}')]
    public function show(int $id, ProductCatalog $catalog): Response   // service : type-hint
    {
        return $this->render('product/show.html.twig', ['product' => $catalog->get($id)]);
    }
}

Deux origines à distinguer dans cette seule signature :

int $id               → attribut de route (RequestAttributeValueResolver)
ProductCatalog $catalog → service injecté dans l'action (ServiceValueResolver)
$this->render(...)    → raccourci HÉRITÉ, qui prend Twig dans son locator

🌍 In Real Life

La situation : pour traiter le bon 42, un poste reçoit un numéro et l’accès au catalogue ; il consulte ce catalogue avant de préparer la présentation.

L’équivalent dans Symfony : numéro sur le bon → $id issu de la route ; outil de consultation → $catalog fourni comme service ; présentation du résultat → render() délègue à Twig et construit une Response.

Retour à la réalité technique : les arguments ne proviennent pas tous du même mécanisme. Le service doit être enregistré et son injection d’action câblée ; son type PHP ne suffit pas. Le catalogue est appelé explicitement dans l’action. Rien n’impose une base de données dans cet exemple.

🧠 Comment le mémoriser : « Le numéro désigne, le catalogue renseigne. » Image mentale : bon numéroté à côté d’un catalogue ouvert. Question-réflexe : « Cet argument est-il une donnée de requête ou un objet de service ? »

⚠️ À ne pas confondre : hériter du raccourci de rendu ne réalise ni le routage ni la résolution des arguments.

Elle est optionnelle

Où en est-on ? Étape 1 : peut-on s'en passer ? Oui, et c'est le point de départ pour comprendre ce qu'elle apporte réellement : du confort, rien de plus.

Pour notre article, une action peut recevoir explicitement ses dépendances et retourner new Response(...), sans parent commun. Avec Twig, elle peut aussi recevoir son environnement de rendu. Le choix de la classe de base modifie donc la façon d'accéder aux outils, pas la définition d'un contrôleur ni la réponse attendue par HttpKernel.

Un controller Symfony est n'importe quel callable PHP. Une class qui n'étend pas AbstractController fonctionne pareil ; elle écrit simplement plus de code. La class vient de FrameworkBundle, pas du component HttpKernel.

Sans AbstractController                 Avec AbstractController
 final class ShowController              final class ShowController
 {                                        extends AbstractController
   __construct(Environment $twig) …      {
   __invoke(): Response                    show(): Response
   { return new Response(                  { return $this->render(...); }
       $this->twig->render(...)); }      }
 }
 → même contrat pour HttpKernel : un callable qui retourne une Response

Pourquoi cela compte à l'examen : HttpKernel n'exige rien d'autre qu'un callable (voir HttpKernel component and FrameworkBundle). La classe appartient à FrameworkBundle, la couche « confort » au-dessus du composant.

🌍 In Real Life

La situation : un poste peut utiliser une desserte prééquipée ou recevoir directement les outils nécessaires ; dans les deux cas, il doit produire le résultat demandé.

L’équivalent dans Symfony : desserte pratique → raccourcis d’AbstractController ; outils reçus directement → dépendances injectées explicitement ; travail du poste → callable du contrôleur.

Retour à la réalité technique : AbstractController est une classe de commodité de FrameworkBundle, pas le contrat obligatoire d’un contrôleur. Sans elle, l’action peut utiliser Twig injecté ou construire une Response. Cela ne supprime pas les exigences de configuration et ne garantit pas que toute dépendance soit disponible.

🧠 Comment le mémoriser : « La desserte aide, elle ne définit pas le poste. » Image mentale : mêmes outils avec ou sans desserte. Question-réflexe : « Ai-je besoin de cet héritage ou seulement d’un callable et de ses dépendances ? »

⚠️ À ne pas confondre : hériter d’une classe de base ne donne aucun droit d’accès au billet.

Les raccourcis sont `protected`

À retenir en priorité
  1. Les raccourcis sont protected.
  2. Ils ne constituent pas une API publique du controller pour les tests.

Où en est-on ? Étape 2 : que contient la classe ? Des raccourcis. Leur visibilité protected répond à une question : qui peut les appeler ? Seulement la classe et ses enfants — jamais le navigateur ni un appel extérieur.

Une fois l'article obtenu, $this->render(...) délègue le rendu à Twig et construit la Response : le navigateur ne peut pas appeler ce raccourci comme une action publique. Si l'action doit vérifier une autorisation sur l'article, denyAccessUnlessGranted() intervient à cet endroit métier ; cela ne remplace pas les contrôles de Security qui ont pu intervenir plus tôt, avant le contrôleur.

Sur la branche 8.0, la class compte vingt-quatre methods protected, deux public et deux private. Les raccourcis sont accessibles depuis la classe qui les déclare et ses sous-classes, pas par un appel direct extérieur, notamment depuis un test qui traiterait le controller comme un service ordinaire. Les deux methods publiques sont les points d'attache de l'infrastructure : setContainer() et getSubscribedServices().

Vérifié dans la source 8.0 : un décompte par visibilité relève 24 methods protected ; setContainer() est public (avec #[Required]) et getSubscribedServices() est public static, ce qui explique le « deux public » de la source, tandis qu'un simple comptage de lignes public function n'en trouve qu'une.

Famille Methods
URL et navigation generateUrl(), redirect(), redirectToRoute(), forward()
Rendu render(), renderView(), renderBlock(), renderBlockView(), stream()
Response json(), file(), sendEarlyHints()
Erreurs createNotFoundException(), createAccessDeniedException()
Security isGranted(), getAccessDecision(), denyAccessUnlessGranted(), getUser(), isCsrfTokenValid()
Forms, divers createForm(), createFormBuilder(), addFlash(), getParameter(), addLink()

addLink() n'écrit rien dans la Response : elle remplit l'attribute de Request _links, dont un listener fera le header Link. sendEarlyHints() envoie ses headers immédiatement, en 103.

Trois moments d'effet à ne pas confondre :

render() / json()   → RETOURNE une Response (rien n'est encore envoyé)
addLink()           → STOCKE dans l'attribut _links ; un listener fera le Link
sendEarlyHints()    → ÉMET déjà des headers (statut 103), avant la Response finale

Voir The response pour render(), json(), file(), et Internal redirects pour forward().

🌍 In Real Life

La situation : le poste dispose de commandes internes pour présenter le résultat ou signaler une information ; le client ne manipule pas directement ces commandes.

L’équivalent dans Symfony : commande interne → helper protected appelé dans le contexte de la classe ou de ses sous-classes ; note sur le bon → addLink() remplit _links ; annonce immédiate → sendEarlyHints() émet des headers 103.

Retour à la réalité technique : la visibilité PHP règle l’accès aux méthodes, pas l’autorisation métier. render() construit une réponse avec Twig ; addLink() attend le listener qui produira le header. Les helpers n’ont donc pas tous le même moment d’effet.

🧠 Comment le mémoriser : « Interne ne veut pas dire immédiat. » Image mentale : bouton interne, note en attente, annonce déjà faite. Question-réflexe : « Ce helper stocke-t-il une information, retourne-t-il un objet ou émet-il déjà des headers ? »

⚠️ À ne pas confondre : protected n’est pas un contrôle Security ; denyAccessUnlessGranted() évalue une autorisation à son point d’appel.

Un subscriber à des services, pas un container

À retenir en priorité
  1. La class est un service subscriber.
  2. Injecter les autres services par les arguments ou le constructor.

Où en est-on ? Étape 3 : d'où viennent Twig, le router… ? Pourquoi un locator plutôt que le container complet ? Pour que le contrôleur ne puisse atteindre que ce que ses raccourcis déclarent : pas de « service locator sauvage ».

Le rendu de /blog/42 ne nécessite pas que le contrôleur puisse récupérer tous les services du projet. ServiceSubscriberInterface déclare les services accessibles aux raccourcis ; le locator permet d'obtenir celui qui est demandé. Il ne s'agit pas d'EventSubscriberInterface : aucune liste d'événements ni priorité de listener n'est déclarée ici.

getSubscribedServices() déclare onze entrées : router, request_stack, http_kernel, serializer, twig, form.factory, security.authorization_checker, security.token_storage, security.csrf.token_manager, parameter_bag et web_link.http_header_serializer. La class reçoit un container restreint à celles-là, injecté par setContainer(), marquée #[Required], qui retourne le container précédent.

Chaque entrée est préfixée par ? : facultative. Sans le service, le raccourci lève à l'appel — une LogicException explicite pour le rendu ; sans Serializer, json() ne lève pas : il se rabat sur json_encode. Sans router, generateUrl() lève une ServiceNotFoundException du locator, pas une LogicException. Pour tout autre service, la voie normale est le type-hint d'un argument d'action avec le contrôleur et le service correctement enregistrés, ou l'injection au constructeur. Le resolver de services utilise ce câblage ; le resolver de Request, lui, fournit la requête courante sans la traiter comme un service applicatif ordinaire.

Les 11 services du locator (tous préfixés « ? » = facultatifs)
 ├─ routing      : router
 ├─ requête      : request_stack, http_kernel
 ├─ rendu        : twig, serializer, form.factory
 ├─ security     : security.authorization_checker, security.token_storage,
 │                 security.csrf.token_manager
 └─ divers       : parameter_bag, web_link.http_header_serializer

Service absent → comportement du raccourci À L'APPEL :
   rendu       → LogicException explicite
   json()      → repli sur json_encode (aucune exception)
   generateUrl → ServiceNotFoundException du locator

Un service hors de cette liste n'est pas accessible par $this->container : il s'injecte par type-hint d'argument d'action (voir Argument value resolvers) ou par le constructeur.

🌍 In Real Life

La situation : la desserte du poste donne accès à une liste d’outils prévue pour lui, pas à tout l’équipement du restaurant. Un outil facultatif peut manquer.

L’équivalent dans Symfony : liste déclarée → getSubscribedServices() ; accès restreint → locator injecté par setContainer() ; outil obtenu sur demande → service utilisé par le helper.

Retour à la réalité technique : le locator implémente ContainerInterface mais n’expose que ses entrées. Le préfixe ? autorise l’absence d’un service ; il ne rend pas tout appel inoffensif. Le rendu sans Twig échoue, tandis que json() dispose d’un repli sans Serializer.

🧠 Comment le mémoriser : « Liste d’outils, pas liste d’annonces. » Image mentale : inventaire de la desserte, distinct du tableau des sonneries. Question-réflexe : « Ce subscriber déclare-t-il des services ou des événements ? »

⚠️ À ne pas confondre : ServiceSubscriberInterface n’est pas EventSubscriberInterface ; un service applicatif supplémentaire peut être injecté séparément.

AbstractController est un bureau équipé d'outils sélectionnés, pas l'entrepôt entier. Son locator rend les services déclarés accessibles à la demande ; un autre besoin appelle une injection explicite.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Étendre AbstractController est facultatif.

    Étendre AbstractController est facultatif. Un controller est n'importe quel appelable PHP ; la class de base fait gagner des raccourcis, pas des droits. Pourquoi on se trompe : tous les tutoriels l'étendent, on croit que c'est requis.

  • Voir l’explication : Ses raccourcis sont protected.

    Ses raccourcis sont protected. La classe qui les déclare et ses sous-classes peuvent les appeler ; un test qui traiterait le controller comme un service ordinaire ne peut pas les invoquer de l'extérieur. Les deux seules methods public sont setContainer() et getSubscribedServices(). Pourquoi on se trompe : on les imagine publics parce qu'on les appelle avec $this->.

  • Voir l’explication : Ce n'est pas le container.

    Ce n'est pas le container. La class est un subscriber : onze services déclarés, tous facultatifs, et rien d'autre n'est accessible. Pourquoi on se trompe : le locator implémente ContainerInterface, donc on le prend pour le container complet.

  • Voir l’explication : Elle vient de FrameworkBundle

    Elle vient de FrameworkBundle, pas du component HttpKernel. Pourquoi on se trompe : « controller » évoque HttpKernel.

  • Voir l’explication : addLink() n'écrit pas dans la Response.

    addLink() n'écrit pas dans la Response. Elle remplit l'attribute de Request _links ; le header est produit plus tard par un listener. Pourquoi on se trompe : le nom suggère un header immédiat, comme sendEarlyHints().

Application

À retenir en priorité
  1. AbstractController est facultatif.
  2. Il vient de FrameworkBundle et apporte des raccourcis.
  3. Les raccourcis sont protected.
  4. Ils ne constituent pas une API publique du controller pour les tests.

🌍 In Real Life

La situation : vérifier le travail d’un poste avec ses outils déjà préparés ne vérifie pas que l’organisation lui apportera les bons outils pendant le service.

L’équivalent dans Symfony : essai du poste isolé → appel de l’action publique avec dépendances préparées ; essai du parcours → test HTTP vérifiant aussi le câblage et la réponse.

Retour à la réalité technique : un test extérieur ne peut pas appeler directement un helper protected. Tester l’action et tester son intégration couvrent deux frontières différentes ; un test HTTP Symfony ne prouve pas à lui seul l’exécution d’un véritable serveur web ou de JavaScript.

🧠 Comment le mémoriser : « Tester le geste, puis la livraison des outils. » Image mentale : répétition au poste puis service complet. Question-réflexe : « Mes dépendances sont-elles fournies par le test ou réellement résolues par Symfony ? »

⚠️ À ne pas confondre : comportement du contrôleur et bon assemblage de ses services sont deux preuves distinctes.
