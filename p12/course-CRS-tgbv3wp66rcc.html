Objectif

Connaître les redirects que le routage déclenche de lui-même. Les redirects émis par un controller — redirect(), redirectToRoute() — et les options de RedirectController appartiennent au Module 04 — Contrôleurs.

Question fil rouge : « Un client demande /login alors que la route est /login/ en HTTPS : qui le renvoie vers la bonne adresse, et pourquoi un POST n'a-t-il pas droit au même traitement ? »

L'essentiel

À comprendre

À retenir en priorité
  1. UrlMatcher peut échouer sans rediriger.
  2. Le matcher du framework cible RedirectController.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une même page peut être demandée sous plusieurs formes (avec/sans barre finale, HTTP/HTTPS). Pour le référencement et la sécurité, une seule forme doit être canonique : le routage corrige les variantes.
  • Le piège de fond. Le component Routing seul ne redirige pas ; c'est le matcher de FrameworkBundle qui le fait, en déléguant à RedirectController.
  • Ce que l'auteur veut que vous compreniez. Redirection = 301, GET/HEAD seulement, query string recopiée. Un POST ne serait pas rejoué correctement : il reçoit un 404.
  • Pourquoi c'est à l'examen. Les deux déclencheurs (barre, schéma), le 301, POST → 404, un seul redirect pour barre + schéma, proxy TLS et boucle.

Le routage redirige de lui-même dans deux cas : la barre oblique finale et le schéma exigé par schemes. Toujours en 301, toujours seulement en GET et HEAD — un POST sur la mauvaise forme reçoit un 404. Ce n'est pas le component seul qui redirige, mais le matcher de FrameworkBundle, qui route la Request vers RedirectController.

En un coup d'œil

À retenir en priorité
  1. Le redirect canonique n'est pas universel pour toutes les methods.
  2. La correction du slash ne doit pas être confondue avec un redirect applicatif explicite.

Où en est-on ? Carte du cours, puis le schéma central : qui fait quoi pour produire un 301.

Cours « Trigger redirects »
   ├─ exemple                  → /login/ en HTTPS
   ├─ 1. Qui redirige, comment → matcher redirigeable → RedirectController
   ├─ 2. La barre oblique      → vers la forme déclarée
   ├─ 3. Le schéma             → schemes, génération et appariement
   └─ 4. Depuis une route      → RedirectController explicite

Bleu = coordination serveur ; vert = réponse construite. Le matcher ne fabrique pas lui-même la réponse et n'appelle pas le contrôleur. Les 404 décrits supposent qu'aucune autre route ne correspond. Un matching réussi ne garantit pas un 200 : le contrôleur décide ensuite du statut.

Où en est-on ? Le même parcours, avec les trois acteurs côte à côte.

Request GET /login
   │
   ▼  UrlMatcher redirigeable : « /login/ existe ! »
   │     → retourne _controller = RedirectController::urlRedirectAction
   │              permanent = true, path = /login/, _route = login
   ▼  HttpKernel : résout et APPELLE le controller
   ▼  RedirectController construit la RedirectResponse (301, Location)

L'exemple

Exemple concret

À retenir en priorité
  1. schemes intervient dans les deux sens.
  2. La génération doit exprimer le changement de schéma.

Où en est-on ? Cas concret : une page de connexion en HTTPS, avec barre finale.

La connexion au blog doit utiliser une URL canonique en HTTPS. Le GET mal formé ci-dessous peut recevoir une instruction de correction avant que LoginController ne soit appelé. Pour le POST d'inscription ou de connexion, génère directement la bonne cible : ne compte pas sur cette correction pour transporter le body.

use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LoginController
{
    #[Route('/login/', name: 'login', schemes: ['https'])]
    public function login(): Response
    {
        return new Response('Connexion');
    }
}
// GET http://example.com/login  → un seul 301 vers https://example.com/login/
// POST http://example.com/login/ → 404

Ces résultats supposent le matcher redirectable du framework et aucune autre route correspondante ; une instance autonome de UrlMatcher ne promet pas ces redirections.

Qui redirige, et comment

Où en est-on ? Étape 1 sur 4. Avant les cas, le mécanisme : le matcher ne fabrique pas la réponse, il désigne un controller.

Le matching ne produit pas encore une Response. Il choisit ici une autre destination _controller ; HttpKernel la résout, prépare les arguments, puis appelle RedirectController. Le contrôleur métier initial n'a donc pas traité la demande ; il pourra intervenir dans la nouvelle requête si le client suit la redirection.

Le UrlMatcher du component lève ResourceNotFoundException, qui devient un 404. Le redirect n'existe que si le matcher implémente RedirectableUrlMatcherInterface ; le component n'en fournit qu'une abstract class, l'implémentation concrète est RedirectableCompiledUrlMatcher, de FrameworkBundle. Sa method redirect() ne construit pas de Response : elle rend des attributes qui désignent RedirectController, avec permanent à true. D'où un 301, la query string recopiée sur la cible, et _route qui porte le nom de la route trouvée.

Comparaison :

Matcher Mauvaise forme d'URL
UrlMatcher du component (non redirigeable) ResourceNotFoundException → 404
RedirectableCompiledUrlMatcher (FrameworkBundle) attributes → RedirectController → 301

🌍 In Real Life

La situation : l'accueil détecte une adresse à corriger et prépare une fiche pour le poste chargé des réorientations. Il ne traite pas lui-même le dossier et ne remet pas encore le panneau au visiteur.

L’équivalent dans Symfony : le matcher redirigeable de FrameworkBundle retourne des attributes désignant RedirectController, notamment avec permanent=true. ControllerResolver obtient le callable, ArgumentResolver ses valeurs, puis HttpKernel l'appelle pour construire la réponse 301.

Retour à la réalité technique : le matcher ne fabrique pas la Response et ne l'envoie pas. Le UrlMatcher non redirigeable ne fournit pas cette correction. Le contrôleur métier pourra être appelé seulement dans une nouvelle requête si le client suit la réponse.

La barre oblique finale

À retenir en priorité
  1. La forme déclarée est la cible du redirect.
  2. Un POST ne doit pas perdre son body par cette correction automatique.

Où en est-on ? Étape 2 sur 4. Pourquoi corriger /foo ↔ /foo/ ? Parce que ce sont deux URL distinctes pour le serveur, mais généralement la même page pour l'utilisateur.

Si le lien vers l'article emploie une barre différente de la route déclarée, le matcher redirigeable peut corriger ce GET. Ce n'est pas une règle « supprimer toutes les barres » : la forme déclarée est la cible. Les résultats du tableau supposent une route compatible et aucun autre matching pertinent ; un POST ne bénéficie pas du même rattrapage.

Path de la route /foo demandé /foo/ demandé
/foo route trouvée 301 vers /foo
/foo/ 301 vers /foo/ route trouvée

Le redirect va vers la forme déclarée : la Request doit être en GET ou HEAD, la route candidate doit être compatible avec cette method, et la racine / n'est pas concernée. Une route limitée à HEAD peut donc canonicaliser une Request HEAD, dans les deux sens /foo ↔ /foo/ ; accepter GET n'est pas une condition universelle. Un POST vers /foo pour une route /foo/ reçoit un 404 : RFC 9110 (15.4.2) permet de rejouer en GET un POST redirigé en 301, et le body serait perdu.

Le redirect passe avant une route générique : avec /foo/ puis /{name}, GET /foo est redirigé vers /foo/ (test testFallbackPage).

Pourquoi le POST reçoit-il un 404 plutôt qu'un redirect ? Un 301 peut être suivi par un client en GET : le body du POST serait perdu en silence. Mieux vaut échouer visiblement.

Route déclarée : /foo/
   GET  /foo   → 301 → /foo/        (rejouable sans perte)
   HEAD /foo   → 301 → /foo/
   POST /foo   → 404                (le body serait perdu)
   GET  /      → (racine : non concernée)

🌍 In Real Life

La situation : le bureau utilise une orthographe officielle de son adresse. Il peut réorienter un lecteur arrivé avec une variante, mais ne suppose pas qu'un dépôt de dossier puisse être rejoué sans changer son sens.

L’équivalent dans Symfony : la correction de slash vise la forme déclarée, avec ou sans barre finale, pour une requête GET ou HEAD compatible avec la route. Elle ne s'applique pas automatiquement au POST d'inscription.

Retour à la réalité technique : la racine est un cas exclu de cette correction. Une route HEAD-only peut convenir à une Request HEAD ; GET n'est pas une condition universelle de la route. L'échec décrit suppose qu'aucune autre route ne convient ; le matcher ne valide pas encore les données du formulaire.

🧠 Comment le mémoriser : « Revenir à la forme déclarée, pas supprimer toutes les barres. » Image mentale : deux variantes corrigées vers une seule adresse officielle. Question-réflexe : quelle forme ai-je déclarée et quelle méthode arrive réellement ?

⚠️ À ne pas confondre : canonicalisation GET/HEAD, déplacement explicite d'une route et traitement POST du formulaire.

Un avis de réexpédition corrige la forme d'adresse pour GET ou HEAD, mais ne doit pas changer silencieusement le traitement d'un POST. Dans le cas du slash non correspondant décrit ici, retenir 404, pas le 405 proposé par l'analogie source2.

Question: Does an incorrect trailing slash automatically redirect every HTTP method?

Answer: No. This canonicalisation is restricted to GET and HEAD under the matching conditions.

Le redirect canonique n'est pas universel pour toutes les methods. La correction du slash ne doit pas être confondue avec un redirect applicatif explicite.

Le schéma

Où en est-on ? Étape 3 sur 4. Le schéma (http/https) intervient à deux moments : quand on génère un lien, et quand on reçoit une requête.

La même exigence HTTPS intervient à deux moments : pendant la génération du lien, puis lors du matching d'une requête reçue. Le premier peut éviter la redirection en produisant d'emblée la bonne URL. Derrière un proxy, le contexte doit refléter correctement le schéma externe, sinon le client peut être renvoyé sans fin vers l'URL qu'il utilise déjà.

schemes: ['https'] agit dans les deux sens.

À la génération, l'URL utilise HTTPS : path('login') produit le path absolu /login/ si la Request est déjà en HTTPS, mais https://example.com/login/ si elle est en HTTP.

À l'appariement, un GET en HTTP est redirigé en 301 vers HTTPS — pas un POST, qui reçoit un 404 ; la documentation omet cette restriction. Avec plusieurs schémas, aucun redirect si l'un correspond, sinon vers le premier. Barre finale et schéma faux sont corrigés par un seul redirect. schemes s'impose aussi à un import ; derrière un proxy TLS mal configuré, il produit une loop de redirect.

Pourquoi une boucle derrière un proxy ? Le proxy termine TLS et parle en HTTP à Symfony : si Symfony ne sait pas que le client était en HTTPS, il voit « HTTP », redirige vers HTTPS, le client revient… et le cycle recommence.

Client ──HTTPS──► Proxy TLS ──HTTP──► Symfony (contexte = http ?)
                                          │ « schéma faux ! »
Client ◄──301 vers https://…──────────────┘
   └─ recommence : même résultat → boucle de redirections
Remède : configurer le contexte de confiance (schéma externe réel).

🌍 In Real Life

La situation : le bureau indique le bon accès sur ses invitations et vérifie aussi l'accès emprunté à l'arrivée. Si un intermédiaire lui décrit mal le trajet déjà effectué, il risque de renvoyer le visiteur sans fin vers cette même entrée.

L’équivalent dans Symfony : schemes intervient dans la génération des URL et dans le matching. Une exigence HTTPS peut transformer le chemin demandé en URL complète ; le matcher redirigeable peut corriger une requête GET/HEAD reçue sous un autre schéma.

Retour à la réalité technique : cette politique ne chiffre pas rétroactivement une requête HTTP déjà reçue. Le POST doit viser directement la bonne cible. Derrière un proxy TLS, le contexte externe doit être établi par une configuration de confiance correcte ; une boucle indique un contexte ou une politique à diagnostiquer.

🧠 Comment le mémoriser : « Indiquer le bon accès avant, vérifier l'accès reçu ensuite. » Image mentale : invitation et contrôle d'entrée portant la même consigne. Question-réflexe : le schéma vu par Symfony correspond-il à celui utilisé par le client ?

Depuis une route

À retenir en priorité
  1. Les defaults configurent la destination.
  2. Une action applicative n'est pas nécessaire pour ce déplacement.

Où en est-on ? Étape 4 sur 4. Au-delà des corrections automatiques : déclarer soi-même une redirection pour une ancienne URL.

Une ancienne adresse du blog peut aussi choisir explicitement RedirectController. Cette déclaration est une décision de migration, distincte du rattrapage automatique de slash ou de schéma ; ses options déterminent alors le statut et la conservation de méthode souhaités.

Une route peut déléguer à RedirectController pour un simple déplacement d'URL, sans écrire de controller.

Redirection AUTOMATIQUE (ce cours)     Redirection EXPLICITE (lot Controllers)
 matcher → RedirectController           route → RedirectController
 301, GET/HEAD seulement                options : permanent, keepRequestMethod…
 déclenchée par la forme de l'URL       décidée par vous (migration d'URL)

🌍 In Real Life

La situation : corriger l'orthographe d'une adresse n'est pas annoncer le déménagement d'un bureau. Le déménagement nécessite sa propre destination et ses propres consignes.

L’équivalent dans Symfony : une route peut cibler explicitement RedirectController pour migrer une ancienne URL. Ses options définissent alors permanence et conservation de méthode, indépendamment du rattrapage automatique de slash ou de schéma.

Retour à la réalité technique : ne pas écrire de contrôleur applicatif ne signifie pas qu'aucun contrôleur s'exécute. Le mécanisme reste une réponse HTTP à retourner puis envoyer ; la destination et le statut doivent correspondre au besoin, notamment pour un POST.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM probables et la raison de leur plausibilité.

  • Voir l’explication : Ni barre finale ni schéma ne redirigent un POST.

    Ni barre finale ni schéma ne redirigent un POST. Les deux mécanismes sont réservés à GET et HEAD ; un POST qui ne correspond qu'à une autre forme d'URL reçoit un 404. Pourquoi on se trompe : on pense que « redirection » vaut pour tous les verbes.

  • Voir l’explication : Le schéma agit à l'appariement et à la génération.

    Le schéma agit à l'appariement et à la génération. Une Request dans le mauvais schéma est redirigée ; et l'URL générée devient absolue dès que le schéma courant diffère, alors qu'elle serait restée un path sans host (ABSOLUTE_PATH, pas RELATIVE_PATH). Pourquoi on se trompe : on ne voit que le redirect, pas l'effet sur les liens.

  • Voir l’explication : Le matcher non redirigeable ne redirige pas.

    Le matcher non redirigeable ne redirige pas. Son UrlMatcher lève une exception de routage, traduite en 404 par l'intégration HTTP ; c'est le matcher de FrameworkBundle qui sait rediriger. Pourquoi on se trompe : on attribue au component une capacité de l'intégration.

  • Voir l’explication : Aucun controller applicatif n'intervient.

    Aucun controller applicatif n'intervient. Le matcher route la Request vers RedirectController ; le 301 conserve la query string. Pourquoi on se trompe : on croit que votre controller est appelé, puis redirige.

À mémoriser

🧠 À retenir pour la certification :

  • Le component ne redirige pas ; RedirectableCompiledUrlMatcher si.
  • Redirect de routage = 301, query string recopiée.
  • Barre finale : vers la forme déclarée, route compatible avec la Request GET ou HEAD ; une route HEAD-only convient à une Request HEAD.
  • Barre ou schéma : GET et HEAD seulement ; POST → 404.
  • schemes : URL absolue générée si le schéma change ; 1er schéma listé.
  • Barre et schéma faux → un seul redirect.

Moyen mnémotechnique : « Le routage ne redirige que ce qui se relit ».
