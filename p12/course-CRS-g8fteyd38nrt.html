Objectif

Le service d'archivage de l'import existe et ses réglages sont choisis. Pourtant, sa seule présence dans src/ ne dit pas quelle définition le container utilisera. Nous allons suivre sa découverte, son câblage et ses options, puis expliquer pourquoi une déclaration ou un attribute peut sembler ignoré. Ce travail prépare l'assemblage ; il n'archive pas chaque Request /blog/42.

Question directrice : une classe est dans src/ : comment devient-elle un service, avec quels arguments, et pourquoi ma configuration est-elle parfois ignorée ?

L'essentiel

À comprendre

À retenir en priorité
  1. Enregistrer ne câble pas les arguments.
  2. Câbler ne pose pas automatiquement tous les tags.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Écrire une classe ne la rend pas service : le container travaille sur des définitions. Il faut savoir comment elles sont créées, dans quel ordre, et laquelle gagne.
  • Le piège de fond. Trois opérations distinctes : découvrir (créer la définition), câbler (résoudre les arguments), configurer (poser les tags/options). Et une définition ultérieure remplace la précédente, sans fusion.
  • Ce que l'auteur veut que vous compreniez. L'ordre dans services.yaml compte ; _defaults ne vaut que dans son bloc ; un attribute n'agit que si un mécanisme le lit.
  • Pourquoi c'est à l'examen. Ordre ressource/explicite, App::config() (autowire+autoconfigure par défaut en 8.0), when@test, #[When], #[Exclude], #[AsAlias], @ vs %.

Découvrir une class crée une définition à partir d'une ressource ; autowirer résout ses arguments ; autoconfigurer applique les règles enregistrées, notamment des tags. Ces opérations sont distinctes : un tag ne fournit pas un chemin, et l'autowiring ne découvre pas un fichier.

Une définition ultérieure du même identifiant remplace la précédente : elle ne la complète pas par fusion. Les _defaults du bloc concerné fournissent de nouveaux réglages par défaut. Les attributes, eux, ne produisent un effet que si le mécanisme approprié les lit.

Plan du cours :

Enregistrement des services
   ├─ 1. Découvrir / câbler / configurer → trois opérations distinctes
   ├─ 2. Le cas explicite                → named arguments ; ordre = remplacement

   └─ 4. Les attributes                  → une intention près de la classe

Le schéma

À retenir en priorité
  1. L'ordre des declarations compte.
  2. La dernière definition remplace la précédente.

Où en est-on ? Avant le détail : le point décisif est que la définition explicite et la définition découverte se disputent le même identifiant ; la dernière écrite gagne.

Partons d'une découverte générale puis d'un réglage particulier du chemin. Le point décisif est le remplacement de la définition, avant la création du service :

Orange : définitions, non objets ; vert : arguments et options préparés. Le logger est un service résoluble par type, tandis que le chemin est fourni explicitement. Les branches ne représentent pas l'ordre exhaustif des passes de compilation. Si nous inversons les deux déclarations, la découverte peut remplacer notre réglage particulier : c'est l'état final de la définition qu'il faut inspecter, pas seulement la présence d'une ligne correcte quelque part.

Le fil rouge : un `Archiver` et son subscriber

À retenir en priorité
  1. L'autowiring résout les services.
  2. Les scalaires demandent une valeur explicite.

Où en est-on ? On pose les deux classes utilisées dans tout le cours : un service avec un argument objet (autowirable) et un argument scalaire (à fournir), puis un subscriber qui illustre l'autoconfiguration.

Ces classes locales illustrent les trois mécanismes. Les déclarations sont réunies pour lecture ; dans le projet, elles occupent leurs fichiers PSR-4 respectifs sous src/Service/ :

namespace App\Service;

use Psr\Log\LoggerInterface;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;

class Archiver
{
    private string $format = 'zip';

    public function __construct(
        private LoggerInterface $logger,     // un service : autowirable
        private string $directory,           // un scalaire : à fournir
    ) {
    }

    public function setFormat(string $format): void
    {
        $this->format = $format;
    }
}

class ArchiveSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [];
    }
}

Avec la découverte et les options actives, Archiver est enregistré, son logger peut être résolu et son directory reste à fournir. La méthode setFormat() rend valide l'appel configuré plus bas ; elle stocke une valeur sans créer d'archive.

FrameworkBundle connaît une règle d'autoconfiguration pour EventSubscriberInterface. Elle peut taguer ArchiveSubscriber, mais sa liste d'événements est volontairement vide : aucun callback ne sera appelé. Être enregistré et reconnu comme subscriber ne suffit donc pas à observer un événement ; le contrat doit encore déclarer les événements et méthodes voulus.

🌍 In Real Life

La situation : un collaborateur figure au registre des personnes chargées de réagir aux annonces, mais n'a indiqué aucune annonce à suivre.

L’équivalent dans Symfony : collaborateur → objet subscriber ; reconnaissance du rôle → tag d'autoconfiguration ; liste vide → getSubscribedEvents() retourne [].

Retour à la réalité technique : enregistrement et tag ne créent aucun abonnement ni callback. Le subscriber doit déclarer événements et méthodes ; l'événement doit ensuite être émis. L'Archiver voisin a un autre besoin : fournir son argument scalaire.

🧠 Comment le mémoriser : « Reconnu pour un rôle, inscrit à aucune annonce. » Image mentale : fiche d'abonnements vide. Question-réflexe : manque-t-il le service, le tag, l'abonnement ou l'émission ?

⚠️ À ne pas confondre : objet subscriber avec ses méthodes et simple métadonnée de configuration.

Trois mécanismes : découvrir, câbler, configurer

À retenir en priorité
  1. exclude limite la découverte.
  2. Une definition explicite reste possible.

Où en est-on ? Étape 1 sur 4. Question : pourquoi trois mots pour « enregistrer un service » ? Parce que ce sont trois travaux indépendants : si l'un manque, les deux autres ne le remplacent pas.

Pour charger ces classes depuis config/services.yaml :

services:
    _defaults:
        autowire: true
        autoconfigure: true
    App\:
        resource: '../src/'
        exclude: '../src/{Entity,Kernel.php}'

Le chemin est relatif à ce fichier. Les classes admissibles découvertes reçoivent normalement leur FQCN comme identifiant et restent privées sauf option contraire. L'exclusion historique Entity désigne ici un directory exclu ; elle n'enseigne aucune intégration de persistance. Le résultat est un ensemble de définitions, pas des appels métier :

Mécanisme Écriture Ce qu'il fait Ce qu'il ne fait pas
découvrir App\: { resource: '../src/' } une definition par class, id = FQCN ne câble, ne tague, ne rend pas public
câbler autowire: true résout les arguments typés par un service ne devine pas un scalaire
configurer autoconfigure: true pose les tags d'après l'interface ou l'attribute ne crée pas de service

Une définition privée inutilisée peut être retirée par optimisation. Cela ne garantit pas que toute configuration invalide soit sans conséquence : certains contrôles interviennent avant sa suppression. exclude limite cette découverte ; une déclaration explicite distincte peut enregistrer une class exclue sans déplacer son fichier.

En Symfony 8.0, l'API PHP App::config() active autowiring et autoconfiguration par défaut. Ce n'est pas une propriété de tout fichier PHP. En YAML, on les active ici dans _defaults, ou sur une définition précise. Sans arguments fournis ni autowiring, un constructeur obligatoire reste non satisfait ; l'erreur dépend des contrôles et de l'utilisation, avec notamment un possible ArgumentCountError à l'instanciation.

 src/Service/Archiver.php
        │  1. DÉCOUVRIR  (resource)      → Définition « App\Service\Archiver »
        ▼
 Définition ── 2. CÂBLER (autowire)      → $logger résolu ; $directory ??? (scalaire)
        │
        └───── 3. CONFIGURER (autoconfigure) → tags posés d'après l'interface

🌍 In Real Life

La situation : préparer un atelier demande trois décisions : inventorier les postes, raccorder leurs outils, puis reconnaître leurs rôles.

L’équivalent dans Symfony : inventaire → découverte et définitions ; raccords → autowiring ; rôles configurés → autoconfiguration, notamment tags.

Retour à la réalité technique : ces mécanismes ne se remplacent pas. Une classe découverte n'est pas automatiquement publique ; l'autowiring ne devine pas son chemin scalaire ; un tag ne construit pas le service. Une exclusion de ressource laisse possible une déclaration explicite.

🧠 Comment le mémoriser : « Inventorier, raccorder, qualifier. » Image mentale : trois opérations sur le plan, avant tout travail. Question-réflexe : laquelle de ces décisions manque réellement ?

⚠️ À ne pas confondre : defaults de App::config() en Symfony 8.0 et comportement de tout fichier PHP.

Le cas explicite : des named arguments

À retenir en priorité
  1. Une surcharge peut perdre arguments et visibilité.
  2. Placer les réglages explicites après la découverte.

Où en est-on ? Étape 2 sur 4. Question : comment fournir le scalaire que l'autowiring ne devine pas ? Par un named argument dans une définition explicite, qui doit être écrite après la ressource.

Plaçons maintenant cette définition après la ressource précédente, dans le même bloc. Les noms $directory et $logger correspondent exactement à la signature PHP ; @logger est une référence de service, alors que %kernel.project_dir% référence une valeur :

services:
    # … _defaults et App\ au-dessus …
    App\Service\Archiver:
        arguments:
            $directory: '%kernel.project_dir%/var/archive'   # par son nom, pas sa position
            $logger: '@logger'               # @ = un service
        calls:
            - setFormat: ['zip']
        tags: ['app.archiver']

Avec kernel.project_dir=/srv/blog et logger disponible, le constructeur reçoit /srv/blog/var/archive et le logger ; le container appelle ensuite setFormat('zip'). Le tag app.archiver est une métadonnée : sans consommateur de ce tag, il ne lance aucune tâche. Ce code ne produit encore aucun fichier.

« Service definitions always replace previous ones » signifie que l'ordre change le plan final, pas qu'il crée deux instances concurrentes :

Position de la definition explicite Definition finale d'Archiver
après App\: resource privée par défaut, $directory fourni ; publique seulement si demandé
avant App\: resource privée, sans argument : remplacée en silence

Ces lignes supposent les réglages standards du bloc présenté. Une découverte plus tardive remplace les arguments explicitement déclarés, mais ses propres defaults peuvent encore activer l'autowiring. Celui-ci peut retrouver le logger, pas deviner notre directory.

 ORDRE A (correct)                      ORDRE B (piège)
 1. App\: resource  → Archiver (nu)     1. Archiver explicite (directory)
 2. Archiver explicite → REMPLACE       2. App\: resource → REMPLACE l'explicite
 ⇒ directory fourni                     ⇒ directory perdu, sans erreur immédiate

🌍 In Real Life

La situation : un bureau remplace la fiche d'un poste par une nouvelle version ; il ne recopie pas automatiquement les annotations de l'ancienne.

L’équivalent dans Symfony : fiche → définition de service ; même poste → même identifiant ; nouvelle fiche → déclaration ultérieure remplaçant la précédente.

Retour à la réalité technique : placer la découverte après la définition explicite peut perdre $directory. Les defaults applicables à la nouvelle définition peuvent réactiver autowiring, sans retrouver cette valeur par magie. Cela ne crée pas deux services concurrents sous le même identifiant.

🧠 Comment le mémoriser : « Dernière fiche, pas somme des fiches. » Image mentale : ancienne fiche retirée du classeur. Question-réflexe : quelle définition est finalement conservée ?

⚠️ À ne pas confondre : redéfinition remplaçante et décoration conservant l'original derrière une enveloppe.

Le scope de `_defaults`

À retenir en priorité
  1. Les defaults ont un scope local.
  2. Un block conditionnel possède sa propre configuration.

Où en est-on ? Étape 3 sur 4. Question : les réglages par défaut valent-ils pour tout le fichier ? Non : seulement pour le bloc services où ils sont écrits.

Le test de l'import utilise un reporter différent. Les defaults du bloc principal ne traversent pas automatiquement le bloc when@test :

services:
    _defaults:
        autowire: true
    App\ProductionReporter: ~

when@test:
    services:
        _defaults:
            autowire: true
        App\TestReporter: ~

Ce fragment suppose les deux classes autoloadables et leurs dépendances résolubles. Le reporter de test est enregistré dans l'environment test et y bénéficie des defaults de son bloc. Il ne remplace pas automatiquement ProductionReporter, dont l'identifiant est différent.

Si l'on omet ces defaults, des arguments explicites peuvent encore suffire. Sinon, une dépendance obligatoire reste sans valeur ; un ArgumentCountError éventuel décrit le symptôme, pas la portée oubliée. Pour diagnostiquer, retrouvons le bloc de la définition finale, ses defaults puis ses options propres.

🌍 In Real Life

La situation : les réglages standards d'un atelier ne s'appliquent pas automatiquement à l'atelier d'essai voisin.

L’équivalent dans Symfony : atelier → bloc services ; standards locaux → _defaults ; atelier d'essai → bloc when@test.

Retour à la réalité technique : la définition de test reçoit les defaults de son propre bloc. Un identifiant différent ne remplace pas celui de production. Sans autowiring, un câblage explicite peut encore satisfaire les arguments.

🧠 Comment le mémoriser : « Cherche les règles du bloc où vit la définition. » Image mentale : deux ateliers avec leurs fiches distinctes. Question-réflexe : ai-je suivi la portée avant de diagnostiquer l'argument manquant ?

⚠️ À ne pas confondre : nom d'environnement et héritage automatique de toutes les options d'un autre bloc.

Déclarer depuis la class : les attributes

À retenir en priorité
  1. When exprime une condition d'environment.
  2. Exclude exclut la découverte.

Où en est-on ? Étape 4 sur 4. Question : peut-on garder l'intention près du code plutôt que dans le YAML ? Oui, avec des attributes — à condition qu'un mécanisme les lise.

Une intention stable peut rester près du code. Pour chaque attribute, demandons quel lecteur agit et sur quelle définition : aucun de ces noms ne parcourt à lui seul tous les fichiers du projet.

Attribute Effet
#[AsAlias] un alias, privé, vers cette class
#[Autoconfigure] public, lazy, shared, tags, calls, bind…
#[AutoconfigureTag] sur une interface : tague toutes ses implémentations
#[Autowire] câble un argument précis
#[When(env: 'prod')] service seulement dans cet environment
#[Exclude] hors de la découverte, partout

Dans la découverte configurée pour traiter ces attributes, AsAlias publie un autre identifiant, privé par défaut ; Autoconfigure fournit des options ; AutoconfigureTag peut porter une règle d'interface appliquée aux implémentations autoconfigurées. Autowire précise un argument, sans installer son consommateur.

Par exemple, dans une application où App\ est découvert et autowiré :

namespace App;

use Symfony\Component\DependencyInjection\Attribute\Autowire;

final class ProjectPaths
{
    public function __construct(
        #[Autowire(param: 'kernel.project_dir')]
        public readonly string $root,
    ) {}
}

Avec kernel.project_dir=/srv/blog, l'objet construit expose $root === '/srv/blog'. Il ne crée aucun directory. La class doit être enregistrée et le lecteur d'autowiring actif.

When et Exclude filtrent la découverte lorsqu'elle traite ces métadonnées. Hors de l'environment admis par #[When(env: 'prod')], une marque container.excluded permet notamment un diagnostic explicite si un consommateur autowiré exige ce type. Cela ne fournit pas automatiquement null, et n'interdit pas au langage PHP d'instancier la class. Exclude écarte la découverte dans tous les environments, pas toute déclaration explicite possible.

🌍 In Real Life

La situation : une instruction est collée sur un équipement ; elle n'agit que si la procédure de préparation la lit.

L’équivalent dans Symfony : instruction → attribute PHP ; lecture → découverte, autoconfiguration ou autowiring approprié ; effet → alias, option, filtre ou argument.

Retour à la réalité technique : les attributes n'explorent pas seuls les fichiers. When et Exclude filtrent la découverte concernée ; ils ne rendent pas les dépendances nullables ni n'interdisent à PHP d'instancier la classe. Une déclaration explicite reste distincte.

🧠 Comment le mémoriser : « Une instruction exige son lecteur. » Image mentale : étiquette encore non lue sur l'équipement. Question-réflexe : quel mécanisme traite cet attribute sur cette définition ?

⚠️ À ne pas confondre : métadonnée présente et effet effectivement appliqué.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'autoconfiguration ne remplace pas l'enregistrement.
  2. La class doit d'abord être un service.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Chaque piège est suivi de pourquoi la mauvaise réponse paraît plausible.

  • Voir l’explication : Découverte ne signifie pas accès public.

    Découverte ne signifie pas accès public. Le service reste privé avec les defaults usuels ; une option explicite peut changer sa visibilité, sans changer sa class PHP. Plausible car « enregistré » fait penser à « récupérable avec get() ».

  • Voir l’explication : Exclure ne supprime ni le fichier ni la possibilité d'assemblage.

    Exclure ne supprime ni le fichier ni la possibilité d'assemblage. Une définition explicite peut enregistrer la class écartée de la ressource. L'enregistrer ne signifie toujours pas exécuter son travail. Plausible car exclude ressemble à une suppression.

  • Voir l’explication : La portée des defaults précède le diagnostic d'argument.

    La portée des defaults précède le diagnostic d'argument. Dans when@test, lisons son propre bloc ; l'absence de defaults n'est une panne que si aucun autre câblage suffisant n'est fourni. Plausible car on croit que _defaults est global au fichier.

  • Voir l’explication : Une exclusion découverte n'est pas une dépendance nullable.

    Une exclusion découverte n'est pas une dépendance nullable. Le consommateur exigeant le type peut échouer ; une variante de test doit proposer un assemblage compatible plutôt qu'attendre un null implicite. Plausible car « absent » évoque « null ».

  • Voir l’explication : La dernière définition du même identifiant remplace la précédente.

    La dernière définition du même identifiant remplace la précédente. Dans notre exemple, placer la ressource après Archiver perd son directory explicite. Déplaçons le réglage particulier après la découverte et vérifions les defaults réappliqués. Plausible car « explicite l'emporte toujours » semble naturel.

  • Voir l’explication : Un subscriber silencieux ne prouve pas une panne d'autoconfiguration.

    Un subscriber silencieux ne prouve pas une panne d'autoconfiguration. Notre subscriber peut être tagué tout en déclarant zéro événement. Vérifions définition, tag, abonnement, émission de l'événement et callback. Un chemin manquant relève, lui, du câblage des arguments. Plausible car « pas d'effet » est attribué à la dernière étape visible.

  • Voir l’explication : Comparer les APIs, pas seulement les extensions des fichiers.

    Comparer les APIs, pas seulement les extensions des fichiers. App::config() active les deux options par défaut en 8.0 ; en YAML, _defaults est pratique, mais une option sur chaque service ou un câblage entièrement explicite reste possible. Plausible car on suppose que tout fichier PHP se comporte comme App::config().

Fiche express

À mémoriser

À retenir en priorité
  1. Le FQCN devient l'identifier.
  2. La visibilité reste privée par défaut.

Pour retrouver l'Archiver effectivement assemblé :

  1. Suivre la ressource et ses exclusions jusqu'à son identifiant.
  2. Identifier la dernière définition de ce même identifiant.
  3. Lire les defaults de son bloc, sans supposer une fusion de l'ancienne.
  4. Résoudre les objets par références ou autowiring et fournir les valeurs.
  5. Vérifier les règles d'autoconfiguration et les lecteurs d'attributes.
  6. Distinguer une métadonnée, comme un tag, de son consommateur effectif.
  7. Tester l'assemblage de chaque environment concerné ; When n'invente pas de remplacement et Exclude n'efface pas la class.

Si nous voulons ensuite ajouter un comportement tout en conservant l'objet d'origine, remplacer sa définition n'est plus suffisant : la décoration est le mécanisme à examiner.

🧠 À retenir pour la certification

  • Trois opérations : découvrir (resource, id = FQCN, privé), câbler (autowire, services typés, pas les scalaires), configurer (autoconfigure, tags/options).
  • Une définition ultérieure du même id remplace (aucune fusion) : la ressource App\: écrite après l'explicite écrase ses arguments.
  • _defaults ne vaut que dans le bloc services où il est écrit (when@test a les siens).
  • App::config() : autowire + autoconfigure par défaut en 8.0 ; en YAML il faut _defaults ou l'option par service.
  • Attributes : AsAlias (alias privé), Autoconfigure (public/lazy/shared/tags/calls/bind…), AutoconfigureTag (interface), Autowire (un argument), When(env:), Exclude.
  • #[When] hors environnement → type marqué exclu : l'injection échoue (« this type has been excluded »), pas null.
  • YAML : @id = service, %param% = valeur ; un tag est une métadonnée sans consommateur par défaut.

Phrase de mémorisation : « Découvrir crée, câbler résout, configurer qualifie ; la dernière définition gagne et _defaults ne sort pas de son bloc. »

Revoir : L'essentiel

What are the distinct roles of resource discovery, autowiring and autoconfiguration?

Discovery registers classes, autowiring resolves arguments, and autoconfiguration applies metadata such as tags.

Enregistrer ne câble pas les arguments. Câbler ne pose pas automatiquement tous les tags.

Revoir : Le schéma

Why must an explicit service definition follow a broad resource declaration?

Later definitions replace earlier definitions, so the explicit customization must be last.
