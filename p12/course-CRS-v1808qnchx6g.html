Objectif

L'article 42 est le même, mais ses lecteurs n'ont pas tous la même langue. Nous allons traduire les libellés de sa page, sans prétendre traduire automatiquement son titre ou son contenu. Une mauvaise langue, une clé affichée et un placeholder non remplacé conduisent à trois diagnostics distincts.

Ce cours répond à quatre questions, dans cet ordre :

  1. Dans quel file trans() va-t-il chercher ma key ? (le nom du file)
  2. Que se passe-t-il quand deux ressources définissent la même key ?
  3. Comment écrire une valeur variable dans un message (%name% ou {name}) ?
  4. Que fait Symfony quand la key n'existe pas dans la locale demandée ?

L'essentiel

À comprendre

À retenir en priorité
  1. Une key absente ne lève pas nécessairement d'erreur.
  2. Le texte source sert de dernier repli.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un site ne peut pas écrire ses libellés en dur dans les templates : il faudrait un template par langue. Symfony sort les textes dans des catalogues et le code ne manipule plus que des keys.
  • Le problème que Symfony résout. Retrouver, pour une key, la bonne phrase dans la bonne langue, y insérer des valeurs, et ne pas casser la page si la phrase manque.
  • Ce que l'auteur veut que vous compreniez. Tout est piloté par le nom du file (domaine.locale.chargeur), par une fusion key par key et par une cascade de repli. Aucune de ces étapes n'est magique : on peut les dérouler à la main.
  • Pourquoi c'est à l'examen. Les questions portent sur les frontières : fusion ≠ repli, %name% ≠ {name}, filter |trans ≠ tag {% trans %}, traduire ≠ détecter la langue.

trans() cherche une key dans un catalogue choisi par le nom du file — domain, locale, loader — et rend la key telle quelle si rien ne répond. Deux syntaxes de placeholder coexistent : %name% en format classique, {name} avec ICU MessageFormat, activé par le suffixe +intl-icu. Une key absente suit une cascade de repli.

Une locale désigne une variante linguistique, par exemple en ou fr_FR. Un domaine regroupe des messages ; un catalogue rassemble leurs valeurs pour une locale. Le translator reçoit ou utilise une locale déjà choisie : traduire ne détecte pas automatiquement la langue depuis tout header HTTP.

Les trois mots à ne pas mélanger

Mot Question à laquelle il répond Exemple
domain « Dans quel groupe de messages ? » messages, validators, app
locale « Dans quelle langue / variante ? » en, fr_FR, es_AR
catalogue « Quelles valeurs, pour ce domain et cette locale ? » tout messages en fr

Le schéma

À retenir en priorité
  1. Le nom détermine le catalogue.
  2. L'extension choisit le loader.

Où en est-on ? Avant d'entrer dans le détail, on pose la carte du cours. Deux phases sont distinctes : la constitution des catalogues (quels files, quelle fusion) puis la recherche d'un message (quelle locale d'abord, quel repli). Les parties suivantes zooment tour à tour sur chaque case.

trans('blog_article', ['id' => 42], locale: 'en')
   │
   ├─ 1. Quel catalogue ?     → nom du file  domaine.locale.chargeur
   ├─ 2. Deux ressources ?    → fusion key par key, la dernière gagne
   ├─ 3. Où mettre l'id ?     → %id% (classique) ou {id} (ICU, +intl-icu)
   └─ 4. Key absente ?        → cascade de repli, sinon la key telle quelle

Il faut séparer la constitution des catalogues et la recherche d'un message. Un conflit entre deux ressources de la même locale se résout à la fusion ; une absence dans cette locale déclenche ensuite le repli du diagramme.

Bleu : recherche ; vert : résultat. Le repli s'arrête dès qu'une clé est trouvée. La priorité du projet sur les bundles est une priorité de valeurs, pas une recommandation de les charger dans cet ordre. Vue es_AR : toutes les locales n'ont pas un parent intermédiaire distinct de la langue.

Exemple concret

À retenir en priorité
  1. Le format classique remplace les keys littérales.
  2. Conserver les délimiteurs dans le parameter.

Où en est-on ? On pose un exemple minimal qui servira de fil rouge : un catalogue anglais, trois appels à trans(). Chaque partie suivante reprend un morceau de cet exemple.

Le service de traduction doit être configuré et injecté comme Symfony\Contracts\Translation\TranslatorInterface. L'exemple suppose les catalogues chargés et le formateur ICU disponible, notamment MessageFormatter fourni par l'extension PHP intl. Ce besoin de formatage n'introduit pas les utilitaires du composant Intl exclus du programme.

# translations/messages+intl-icu.en.yaml
say_hello: 'Hello {name}!'
blog_article: 'Reading article {id}'
num_of_apples: >-
    {apples, plural, =0 {There are no apples} =1 {There is one apple} other {There are # apples!}}
$translator->trans('say_hello', ['name' => 'Fabien'], locale: 'en'); // Hello Fabien!
$translator->trans('Hello World', domain: 'app');        // le domain app
$translator->trans('blog_article', ['id' => 42], locale: 'en');
// Reading article 42

Le salut et les pommes restent de petits tests du formateur : avec apples égal à 0, 1 puis 5, attendre « There are no apples », « There is one apple », puis « There are 5 apples! ». La traduction de blog_article ne vérifie pas que 42 existe : le catalogue applicatif reste responsable de cette recherche.

Ce que Symfony voit dans le premier appel :

Élément de l'appel Rôle
'say_hello' la key à retrouver
['name' => 'Fabien'] les valeurs des placeholders
locale: 'en' la locale demandée (sinon : locale courante du translator)
domain absent domain par défaut messages

Le nom du file n'est pas décoratif

À retenir en priorité
  1. Le domain regroupe les messages.
  2. Un autre domain doit être choisi explicitement.

Où en est-on ? Étape 1 sur 4. Avant même de chercher une key, trans() doit savoir dans quel catalogue regarder. La réponse est écrite dans le nom des files du dossier translations/.

🌍 In Real Life

La situation : le secrétariat multilingue du blog range les libellés selon leur usage et leur langue, avec une indication du format de fiche.

L’équivalent dans Symfony : usage → domaine ; langue → locale ; format de lecture → loader désigné par l'extension ; étiquette complète → nom de ressource.

Retour à la réalité technique : validators.fr.yaml n'alimente pas automatiquement une recherche dans messages. Traduire les libellés de l'article 42 ne traduit pas son contenu métier ni ne change son identité.

🧠 Comment le mémoriser : « Le bon mot dans le bon tiroir. » Image mentale : trois étiquettes usage/langue/format. Question-réflexe : domaine, locale et chargeur correspondent-ils à cet appel ?

⚠️ À ne pas confondre : clé absente du catalogue et article absent du catalogue métier.

Pourquoi le nom d'un file décide-t-il du catalogue ?

Symfony ne lit pas le contenu pour deviner la langue ou le groupe : il découpe le nom en trois segments séparés par des points.

   translations/ validators . fr . yaml
                 ─────┬────   ─┬   ──┬─
                    domain   locale  loader
                      │        │       └ extension → quel loader lit le file
                      │        └ langue / variante du catalogue
                      └ groupe de messages (messages par défaut)

Donc trans('Hello World', domain: 'app') avec la locale fr lit app.fr.yaml, jamais messages.fr.yaml.

Si la page affiche blog_article, vérifier le trio domaine/locale/chargeur avant de modifier le contrôleur. Une ressource validators.fr.yaml alimente validators, pas les libellés demandés dans messages.

  • domain (messages par défaut), locale (en, en_GB), loader choisi par l'extension : yaml, xlf, php, csv, json, ini, po, mo.
  • YAML pour un projet simple, XLIFF quand des translators et leurs outils interviennent.
  • translations/ du projet passe avant celui des bundles, key par key.
  • Un nouveau catalogue exige un cache:clear.
  • i18n sort les strings dans une couche traduisible ; la localisation fournit les valeurs d'une locale. Forme recommandée : fr_FR.
  • Hors périmètre : les utilitaires d'accès aux données ICU du component Intl.

Plusieurs catalogues pour une key

À retenir en priorité
  1. La fusion conserve les autres messages.
  2. Une collision concerne une key précise.

Où en est-on ? Étape 2 sur 4. Le nom de file désigne un catalogue, mais plusieurs ressources (projet, bundles, ou plusieurs files) peuvent porter le même domain et la même locale. Que devient alors une key définie deux fois ?

🌍 In Real Life

La situation : une feuille de corrections du blog remplace deux libellés du lexique français, sans jeter toutes les autres entrées.

L’équivalent dans Symfony : lexique initial → première ressource ; corrections suivantes → ressources chargées ensuite ; remplacement ciblé → fusion clé par clé.

Retour à la réalité technique : à domaine et locale identiques, l'ordre de chargement tranche les conflits. Cette fusion n'est pas le repli vers une autre locale ; conserver une seule définition intentionnelle par clé évite les collisions de formats.

🧠 Comment le mémoriser : « Corriger une entrée, pas jeter le dictionnaire. » Image mentale : deux lignes recouvertes dans un lexique intact. Question-réflexe : est-ce un conflit de ressources ou une absence dans la locale ?

⚠️ À ne pas confondre : priorité de fusion et ordre des locales de repli.

Imaginons une première ressource avec blog_article et blog_back, puis une seconde qui ne redéfinit que blog_article. Le lien de retour reste traduit par la première : on ne remplace pas tout le catalogue.

ressource 1 (chargée d'abord)    ressource 2 (chargée ensuite)
  blog_article: "Article {id}"     blog_article: "Reading {id}"
  blog_back:    "Retour"
                  │                          │
                  └────────── fusion ────────┘
                              ▼
  catalogue final : blog_article = "Reading {id}"   (la dernière gagne)
                    blog_back    = "Retour"         (conservée)
  • Deux resources d'un même domain et d'une même locale : la dernière chargée gagne, key par key ; les autres keys restent.
  • messages et messages+intl-icu comptent comme un seul domain : là aussi, la dernière chargée gagne. Les files d'un dossier se chargent par ordre de nom, et + passe avant . : avec messages.en.yaml et messages+intl-icu.en.yaml, c'est la version classique qui l'emporte.
  • Une key trouvée dans une locale de repli est formatée avec les règles de cette locale.

Pourquoi la version classique l'emporte-t-elle ici ?

On déroule : le Finder trie les files par nom (sortByName()). Dans messages+intl-icu.en.yaml le caractère après messages est +, dans messages.en.yaml c'est .. Or + précède . : le file ICU est chargé en premier, le classique ensuite, et « la dernière chargée gagne ».

MessageCatalogue::add() retire la clé de l'autre variante de la paire classique/ICU lorsqu'elle est remplacée. Le suffixe ICU n'est donc pas une priorité absolue. La découverte des ressources et le cache de traduction ne sont pas une recompilation du container à chaque appel de trans().

Règle la dernière ressource chargée gagne locale, parente, langue, fallbacks

⚠️ À ne pas confondre : priorité de fusion et ordre de repli. Plausible car les deux répondent à « quelle valeur est utilisée ? » ; mais l'une départage deux ressources de même locale, l'autre cherche dans des locales différentes.

Les deux syntaxes de placeholder

À retenir en priorité
  1. Le suffixe sélectionne le format de message.
  2. Ce n'est pas une option des utilitaires Intl.

Où en est-on ? Étape 3 sur 4. La key est retrouvée ; il reste à y insérer les valeurs (name, id). Deux syntaxes existent, et le nom du file choisit laquelle s'applique.

Un placeholder est une place réservée dans le texte traduit. Passer la valeur d'un identifiant séparément évite de fabriquer une clé différente pour chaque article ; cela n'autorise pas pour autant du HTML non fiable.

Format classique ICU MessageFormat
File messages.en.yaml messages+intl-icu.en.yaml
Écriture Hello %name%! Hello {name}!

Sans +intl-icu, le remplacement est un strtr littéral : ['name' => 'Ann'] sur Hello {name}! donne Hello {Ann}!. Dans un plural ICU, # reprend le nombre, =0 vise une valeur exacte, one, few, many, other sont des catégories propres à chaque langue : l'anglais n'a que one et other, le russe en a quatre.

Pourquoi Hello {name}! devient-il Hello {Ann}! en format classique ?

Le format classique ne connaît pas {...}. Il fait un strtr : il remplace la chaîne exacte donnée en clé du tableau. Avec ['name' => 'Ann'], il cherche littéralement name dans le texte, le remplace par Ann, et les accolades restent. Dans la syntaxe classique, la clé du tableau contient d'ailleurs les % ('%name%' => 'Ann').

 classique   "Hello %name%!"  + ['%name%' => 'Ann']  → "Hello Ann!"
 ICU         "Hello {name}!"  + ['name'   => 'Ann']  → "Hello Ann!"
 mélange     "Hello {name}!"  (sans +intl-icu)       → "Hello {Ann}!"

Plural ICU : exact ou catégorie ?

Écriture Sens Dépend de la langue ?
=0, =1 valeur exacte non
one, few, many, other catégorie grammaticale oui (anglais : one, other)
# le nombre lui-même non

Dans Twig avec autoescape HTML actif : {{ message|trans }} traduit une expression, puis l'autoescape Twig échappe le résultat ; {% trans %}Hello %name%{% endtrans %} traduit un block statique, et le tag n'échappe rien — parameters compris. {% trans_default_domain 'app' %} ne vaut que pour le template courant.

Pour afficher le libellé précédent sous autoescape HTML :

{{ 'blog_article'|trans({'id': 42}, 'messages', 'en') }}

Le résultat visible est « Reading article 42 ». Une valeur contenant du balisage doit rester du texte avec cette autoescape ; ne pas ajouter raw pour corriger un problème de placeholder. Le translator choisit et formate la chaîne, tandis que Twig gère ici son échappement à l'affichage.

Comparaison : filter |trans et tag {% trans %}

{{ x\|trans }} {% trans %}…{% endtrans %}
Ce qui est traduit une expression un block statique
Qui échappe l'autoescape Twig, sur le résultat personne : le tag n'échappe rien
Parameters échappés avec le résultat non échappés non plus
Domaine par défaut trans_default_domain du template idem

⚠️ À ne pas confondre : « le translator échappe » et « Twig échappe ». Plausible car le paramètre est passé au translator ; mais le translator ne fait que substituer, l'échappement est l'affaire de Twig à l'affichage.

La cascade de repli

À retenir en priorité
  1. Le repli suit une hiérarchie.
  2. Il ne se limite pas à couper le suffixe.

Où en est-on ? Étape 4 sur 4, la dernière : la key existe peut-être dans le projet mais pas dans la locale demandée. Que cherche Symfony ensuite, et dans quel ordre ? C'est la partie du schéma central en forme d'escalier.

🌍 In Real Life

La situation : le bureau du blog cherche un libellé dans le lexique régional, puis dans les lexiques de repli prévus, et s'arrête dès qu'il le trouve.

L’équivalent dans Symfony : lexique demandé → locale ; parcours prévu → parents et fallbacks ; première définition trouvée → message retenu et locale de formatage.

Retour à la réalité technique : la chaîne n'est pas toujours une simple suppression de suffixe : des locales parentes spécifiques existent. Si aucune définition ne répond, la clé demeure ; cela ne constitue pas une traduction générée.

🧠 Comment le mémoriser : « Chercher ailleurs, sans inventer. » Image mentale : index passant d'un lexique à l'autre. Question-réflexe : quelle locale définit réellement le message retourné ?

⚠️ À ne pas confondre : repli de traduction et négociation initiale de la langue de la requête.

Locale es_AR, key absente : es_AR, puis la locale parente, es_419 — définie pour certaines locales seulement —, puis es, puis l'option fallbacks, qui vaut default_locale si elle n'est pas configurée.

 locale demandée   es_AR ──absente──▶ es_419 ──absente──▶ es ──absente──▶
                                                                          │
        fallbacks (sinon default_locale) ◀────────────────────────────────┘
                 │
                 └──absente partout──▶  la key s'affiche telle quelle

Si blog_article n'existe qu'en es_419, la recherche s'arrête là, même si es possède aussi cette clé. Translator::trans() suit les catalogues de repli jusqu'à celui qui la définit et transmet sa locale au formateur. Si aucune ressource ne définit blog.missing, cet identifiant reste affiché : un statut HTTP 200 ne garantit donc pas que tous les libellés sont traduits. Tester le texte, la locale et le domaine attendus.

Pourquoi la locale de formatage change-t-elle ?

Une key trouvée dans es alors qu'on a demandé es_AR est un texte écrit pour es. Ses règles de pluriel ou de nombre sont celles de es : le formateur reçoit donc la locale du catalogue qui définit la key, pas la locale demandée.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Choisir la syntaxe du catalogue.
  2. Mélanger les formats produit un rendu inattendu.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les quatre étapes sont faites. Voici les erreurs de QCM les plus probables, chacune avec la raison pour laquelle la mauvaise réponse semble juste.

  • Traduction absente contre article absent

    Pour un article correctement chargé mais mal libellé, ne pas confondre absence de traduction et absence de donnée métier. Le repli corrige la première recherche, pas une erreur 404 du catalogue d'articles.

  • Voir l’explication : Un message non traduit est retourné tel quel

    Un message non traduit est retourné tel quel, sans erreur. Plausible car beaucoup de librairies lèvent une exception sur une clé manquante.

  • Voir l’explication : +intl-icu est un suffixe de nom de file

    +intl-icu est un suffixe de nom de file, pas une option de configuration. Plausible car ICU « s'active » comme une option dans d'autres outils.

  • Voir l’explication : %name% en format classique, {name} en ICU

    %name% en format classique, {name} en ICU — les deux ne se mélangent pas. Plausible car les deux sont des « placeholders » ; mais le choix dépend du nom du file.

  • Voir l’explication : Le directory translations/ du projet prime

    Le directory translations/ du projet prime sur celui des bundles, key par key. Plausible car on imagine que le bundle, chargé en premier, « gagne ».

  • Voir l’explication : La locale parente s'intercale

    La locale parente s'intercale dans le repli. Plausible car on croit que es_AR tombe directement sur es.

  • Voir l’explication : trans_default_domain ne franchit pas un include.

    trans_default_domain ne franchit pas un include. Plausible car le tag semble « global » dans le rendu.

  • Voir l’explication : Le tag {% trans %} n'échappe pas

    Le tag {% trans %} n'échappe pas ; avec le filter, c'est l'autoescape Twig actif qui protège l'affichage. Ne pas ajouter |raw à du contenu non fiable. Plausible car les deux syntaxes affichent « la même chose ».

Fiche express

À mémoriser

À retenir en priorité
  1. Le réglage reste local au template.
  2. Définir le domain là où il est utilisé.

La page peut maintenant varier ses libellés sans changer l'identité de 42. Si sa réponse est mise en cache, la représentation dépend aussi de la langue : revenir aux clés et variantes du cache HTTP plutôt que servir indistinctement la première langue calculée.

Si tu dois retenir seulement 7 choses :

  • domaine.locale.chargeur ; domain par défaut : messages.
  • Key introuvable : rendue telle quelle, sans erreur.
  • Projet avant bundles, key par key ; nouveau catalogue : cache:clear.
  • %name% classique, {name} ICU, par +intl-icu.
  • Plural ICU : =0 exact, one / other selon la langue.
  • Repli : locale, locale parente, langue, fallbacks.
  • |trans + autoescape protège le résultat ; {% trans %} non ; domaine local.

🧠 À retenir pour la certification :

  • Le nom du file décide de tout : domaine.locale.chargeur.
  • Même domain + même locale → fusion key par key, la dernière chargée gagne.
  • messages et messages+intl-icu = un seul domain ; + < . donc le classique gagne.
  • Classique %name% / ICU {name} ; sans +intl-icu, {name} n'est qu'un strtr littéral.
  • Repli : es_AR → es_419 → es → fallbacks (sinon default_locale) → la key brute.
  • La locale de formatage est celle du catalogue qui définit la key.
  • Traduire ≠ détecter la langue ; |trans est échappé par Twig, {% trans %} non.

Moyen mnémotechnique : « Domain, locale, loader — puis on remonte ».

Phrase de mémorisation : « Le file donne le tiroir, la fusion garde la dernière version, le placeholder suit le suffixe, et sans réponse on remonte l'escalier des locales jusqu'à rendre la key. »
