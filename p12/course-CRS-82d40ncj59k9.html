Objectif

Le rapport d'import est prêt ; l'équipe éditoriale doit être avertie. Avant de choisir comment envoyer la notification, il faut définir son contenu : texte lisible sans HTML, version enrichie et éventuelle pièce jointe. Mime construit ce document et ses relations entre parties.

Ce cours répond à une seule question : comment décrire un courriel comme un objet PHP, sans rien envoyer ? Le cours suivant, Mailer, s'occupera de l'envoi.

L'essentiel

À comprendre

À retenir en priorité
  1. Mime définit le contenu et la structure.
  2. Le transport est une responsabilité séparée.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un courriel n'est pas une simple chaîne : il a des en-têtes, plusieurs versions du texte, des images liées, des pièces jointes. Écrire ce format à la main est pénible et fragile. Le component Mime le fabrique pour vous.
  • Le piège de fond. Fabriquer n'est pas envoyer. Mime ne contacte aucun serveur ; l'envoi appartient à Mailer.
  • Ce que l'auteur veut que vous compreniez. La structure MIME est un arbre de conteneurs (alternative, related, mixed) dont chacun exprime une relation précise entre ses parties.
  • Pourquoi c'est à l'examen. Les questions portent sur la structure produite, sur les adresses (to() ≠ addTo(), UTF-8 et sender) et sur MimeTypes (ordre des résultats, devinette par contenu).

Le component Mime fabrique un message électronique ; il ne l'envoie pas. L'API Email, chaînable, couvre les besoins courants ; Message, bas niveau, se réserve aux cas rares. À l'examen : la structure MIME produite, les adresses, et MimeTypes, dont la devinette lit le contenu du file.

MIME décrit les types et l'assemblage des contenus du courriel. Une partie texte et une partie HTML peuvent raconter la même information ; une pièce jointe est un document supplémentaire. Ces relations expliquent les conteneurs du schéma, plutôt qu'une simple liste de termes à mémoriser. La notification reste distincte de la Response de GET /blog/42.

Le schéma

À retenir en priorité
  1. Chaque type exprime une relation.
  2. La structure MIME n'est pas arbitraire.

Où en est-on ? Étape 1 sur 4 : avant d'écrire du code, on regarde le résultat final. Le cours suit ensuite quatre questions : quelle API (Email ou Message), quelle arborescence, quelles adresses, quels types MIME.

Le component Mime
   ├─ 1. Quelle API ?        → Email (haut niveau) / Message (bas niveau)
   ├─ 2. Quelle structure ?  → alternative ⊂ related ⊂ mixed
   ├─ 3. Quelles adresses ?  → Address, to()/addTo(), UTF-8 et sender
   └─ 4. Quels types ?       → MimeTypes : table (extensions) ≠ contenu (guess)

Partons de la notification la plus complète : deux versions du texte, une image utilisée par le HTML et un PDF séparé. Lire l'arbre de l'intérieur vers l'extérieur pour comprendre pourquoi chaque conteneur est nécessaire :

Bleu : conteneurs MIME ; vert : parties de contenu. Les flèches représentent la composition, pas une chronologie d'envoi. Le client choisit une version qu'il sait afficher dans alternative ; il ne concatène pas le texte et le HTML.

Pourquoi trois conteneurs et pas un seul ? Parce que trois relations différentes existent entre les parties :

┌───────────────┬──────────────────────────┬───────────────────────────────┐
│ Conteneur     │ Relation entre parties   │ Exemple                       │
├───────────────┼──────────────────────────┼───────────────────────────────┤
│ alternative   │ même contenu, plusieurs  │ text/plain  puis  text/html   │
│               │ versions : on en choisit │ (préférée = la DERNIÈRE)      │
│               │ UNE                      │                               │
├───────────────┼──────────────────────────┼───────────────────────────────┤
│ related       │ parties qui forment UN   │ HTML + image intégrée (CID)   │
│               │ tout                     │                               │
├───────────────┼──────────────────────────┼───────────────────────────────┤
│ mixed         │ contenus de natures      │ corps du message + PDF joint  │
│               │ différentes              │                               │
└───────────────┴──────────────────────────┴───────────────────────────────┘

L'exemple : une notification

Exemple concret

À retenir en priorité
  1. Email couvre les usages courants.
  2. Message permet un contrôle plus bas niveau.

Où en est-on ? Toujours l'étape 1 : on écrit le code qui produit un arbre (la partie Email). Code minimal d'abord, détails ensuite.

Avec Mime 8.0 et PHP 8.4, ce message annonce le rapport. Les adresses sont fictives ; $reportPath désigne un PDF déjà produit, lisible et autorisé par l'application. Composer le message ne génère pas ce PDF :

use Symfony\Component\Mime\Email;

$email = new Email()
    ->from('reports@example.test')
    ->to('editor@example.test')
    ->addCc('reviewer@example.test')
    ->priority(Email::PRIORITY_HIGH)
    ->subject('Rapport d’import disponible')
    ->text('Le rapport de l’import des articles est disponible en pièce jointe.')
    ->html('<p>Le rapport de l’import des articles est disponible en pièce jointe.</p>')
    ->attachFromPath($reportPath);

Ce fragment suppose un PDF lisible au chemin indiqué. Il n'ajoute pas d'image intégrée : son arbre omet donc related et image/png, contrairement à la vue complète. Construire l'Email n'envoie aucun message.

Ce que Symfony en déduit, ligne par ligne :

Appel Effet sur le document
from(), to(), addCc() en-têtes d'adresses
priority(Email::PRIORITY_HIGH) indication de priorité du courriel
text() + html() deux versions → multipart/alternative
attachFromPath() pièce jointe → l'arbre est enveloppé dans multipart/mixed

PRIORITY_HIGH renseigne une priorité de courriel : elle ne choisit ni la priorité d'un listener EventDispatcher, ni l'ordre de consommation d'une file Messenger. Ne pas traiter une indication destinée aux clients mail comme une garantie d'exécution.

Deux API pour un même message

À retenir en priorité
  1. Le bas niveau offre plus de contrôle.
  2. Il ajoute aussi de la complexité.
  3. Un objet Email restauré et sa représentation MIME brute sont deux types distincts.

Où en est-on ? Étape 1 sur 4 (suite) : le code précédent utilisait Email. Existe-t-il autre chose, et quand l'utiliser ?

La notification courante n'a pas besoin de construire chaque partie à la main. Garder Email tant que ses méthodes décrivent le document voulu ; passer au bas niveau seulement pour un besoin d'assemblage explicite :

Email est l'API haut niveau ; Message contrôle chaque partie à la main, et la documentation la déconseille pour un besoin ordinaire. Email et Message peuvent être sérialisés comme objets PHP ; un RawMessage, lui, peut être construit depuis le texte MIME produit par toString(). Ne pas confondre ces représentations ni appeler unserialize() sur des données provenant d'une source non fiable.

┌─────────────────────────────┐  ┌──────────────────────┐  ┌───────────────────┐
│ Email                       │  │ Message              │  │ RawMessage        │
├─────────────────────────────┤  ├──────────────────────┤  ├───────────────────┤
│ Haut niveau, chaînable      │  │ Bas niveau           │  │ Texte MIME brut   │
│ text(), html(), attach...() │  │ chaque partie à la   │  │ construit depuis  │
│ construit l'arbre MIME      │  │ main (déconseillé    │  │ toString()        │
│ lui-même                    │  │ en usage courant)    │  │                   │
└─────────────────────────────┘  └──────────────────────┘  └───────────────────┘

Après restauration d'une sérialisation PHP fiable d'Email, le résultat est un objet Email, pas du texte MIME. Pour conserver ce dernier format, utiliser $raw = $email->toString(), puis new \Symfony\Component\Mime\RawMessage($raw). RawMessage ne transforme pas implicitement un Email passé à son constructeur et ne le reparcourt pas en objet de haut niveau. Un contrôle de type après unserialize() ne rend pas sûre une entrée non fiable.

Avant / après :

Email ──serialize()──▶ chaîne PHP ──unserialize()──▶ Email (objet)
Email ──toString()───▶ texte MIME ──new RawMessage()──▶ RawMessage (texte)

L'arborescence MIME

À retenir en priorité
  1. Les parties représentent le même contenu.
  2. L'ordre exprime la préférence.

Où en est-on ? Étape 2 sur 4 : on a vu le schéma complet au début ; on explique maintenant pourquoi chaque conteneur existe et qui le construit.

🌍 In Real Life

La situation : le dossier de notification du blog contient une note simple, sa version illustrée et un rapport indépendant.

L’équivalent dans Symfony : deux présentations de la note → alternative ; note avec ses illustrations liées → related ; ensemble avec rapport séparé → mixed.

Retour à la réalité technique : les conteneurs expriment des relations entre parties, pas trois phases d'envoi. Email ne crée que ceux nécessaires ; la variante préférée d'une alternative vient en dernier.

🧠 Comment le mémoriser : « Autre version, pièces liées, pièces séparées. » Image mentale : trois pochettes imbriquées portant ces indications. Question-réflexe : ces parties se remplacent-elles ou se complètent-elles ?

⚠️ À ne pas confondre : composer l'arbre MIME et remettre le courriel à un transport.

L'arbre ci-dessus est exactement celui qu'Email produit pour texte, HTML, image intégrée et PDF joint. alternative réunit des versions du même contenu, related des parties qui forment un tout, mixed des contenus de natures différentes.

Email::generateBody() construit d'abord les alternatives texte/HTML, les enveloppe dans related s'il existe des parties liées, puis dans mixed s'il existe des pièces indépendantes. Les conteneurs inutiles ne sont pas ajoutés : texte seul donne text/plain.

Contenu de l'Email            Arbre produit
─────────────────────────     ──────────────────────────────────
text()                        text/plain
text() + html()               alternative(plain, html)
+ image intégrée (CID)        related(alternative(...), image)
+ pièce jointe                mixed(related(...), pièce)

Voici une version sans fichier externe pour observer la représentation MIME, avec Mime 8.0 chargé :

<?php
use Symfony\Component\Mime\Address;
use Symfony\Component\Mime\Email;

$email = (new Email())
    ->from(new Address('reports@example.test', 'Rapports'))
    ->to('reader@example.test')
    ->subject('Rapport prêt')
    ->text('Votre rapport est prêt.')
    ->html('<p>Votre rapport est prêt.</p>');
echo $email->toString();

Le résultat est un texte MIME avec multipart/alternative, une partie text/plain puis text/html. Les frontières générées ne sont pas une chaîne fixe à comparer dans un test. Aucun transport n'est appelé. Une image simplement jointe n'apparaît pas automatiquement dans le HTML : une ressource intégrée demande une référence CID cohérente. Échapper les données non fiables avant de les inclure dans un corps HTML.

Les adresses

À retenir en priorité
  1. Le préfixe add conserve la liste.
  2. Un nouvel appel to remplace la destination.

Où en est-on ? Étape 3 sur 4 : l'arbre est clair. Reste à dire à qui le message va. Piège principal : l'adresse affichée et l'adresse de remise ne sont pas la même chose.

🌍 In Real Life

La situation : la lettre du blog affiche un en-tête élégant, tandis que le bordereau postal indique les adresses utilisées pour l'acheminement.

L’équivalent dans Symfony : nom imprimé → nom d'affichage ; en-têtes du message → adresses présentées ; bordereau d'acheminement → enveloppe Mailer.

Retour à la réalité technique : l'enveloppe et le contenu du message sont distincts, même lorsque l'enveloppe est déduite des en-têtes. to() remplace la liste ; addTo() la complète.

🧠 Comment le mémoriser : « Ce qui se lit n'est pas tout ce qui route. » Image mentale : lettre et bordereau côte à côte. Question-réflexe : modifie-t-on la présentation ou les destinataires de remise ?

⚠️ À ne pas confondre : enveloppe Mailer et Envelope Messenger portant des stamps.

L'adresse de destination, le nom affiché et l'expéditeur de l'enveloppe ne sont pas interchangeables. L'enveloppe Mailer décrit les adresses utilisées pour la remise ; elle est distincte des en-têtes présentés :

  • Une string ou un object Address ; Address::create('Fabien Potencier <fabien@example.com>') analyse la forme Nom <adresse>.
  • to(), cc(), bcc() remplacent ; addTo(), addCc(), addBcc() ajoutent.
  • L'UTF-8 est admis dans la partie locale, sauf pour le sender : Envelope refuse jösé@… comme sender, l'accepte comme destinataire.

Après to('a@example.test')->to('b@example.test'), la liste ne garde que b@example.test. Avec to('a@example.test')->addTo('b@example.test'), elle contient les deux. Le nom affiché « José » n'est pas la partie locale de jösé@example.test : identifier précisément le champ testé.

to('a')->to('b')       →  [ b ]          remplace
to('a')->addTo('b')    →  [ a, b ]       ajoute

Address::create('Fabien Potencier <fabien@example.com>')
                        │               │
                        │               └── adresse
                        └── nom affiché

L'acceptation d'un destinataire UTF-8 par l'enveloppe ne garantit pas les capacités du serveur SMTP. Cette restriction d'expéditeur est celle de Mailer\Envelope, pas une interdiction générale de tout texte UTF-8 dans un message Mime.

Rôle UTF-8 dans la partie locale (jösé@…)
Destinataire (to, cc, bcc) accepté par Envelope
Sender de l'enveloppe refusé par Envelope

Les types MIME

À retenir en priorité
  1. Un nom .txt peut contenir une image.
  2. Le contenu détermine la détection.

Où en est-on ? Étape 4 sur 4 : l'arbre et les adresses sont réglés. Reste la question du type de chaque partie (application/pdf, image/png…) et deux outils de MimeTypes qui n'ont rien à voir l'un avec l'autre.

🌍 In Real Life

La situation : l'archiviste du blog sait quelles étiquettes conviennent à un rapport, mais doit ouvrir un dossier reçu pour estimer ce qu'il contient.

L’équivalent dans Symfony : catalogue d'étiquettes → correspondances de MimeTypes ; examen du fichier → guessMimeType().

Retour à la réalité technique : une correspondance extension/type n'inspecte aucun fichier. Une détection de type reste une identification, pas une preuve d'innocuité ou une autorisation de publier.

🧠 Comment le mémoriser : « Lire l'étiquette ou examiner le contenu ? » Image mentale : catalogue fermé à côté d'un dossier ouvert. Question-réflexe : quelle information mon appel observe-t-il réellement ?

⚠️ À ne pas confondre : extension déclarée, type détecté et validation de sécurité.

Le PDF du rapport porte un type de contenu. Deux questions restent distinctes : « quelles extensions correspondent à ce type ? » consulte une table ; « quel est ce fichier ? » demande une inspection :

┌──────────────────────────────┐   ┌──────────────────────────────────┐
│ getExtensions / getMimeTypes │   │ guessMimeType($path)             │
├──────────────────────────────┤   ├──────────────────────────────────┤
│ Consulte une TABLE           │   │ INSPECTE le contenu du file      │
│ N'ouvre aucun fichier        │   │ Ignore le nom : PNG nommé .txt   │
│ Rend des arrays par priority │   │ → image/png                      │
│                              │   │ fileinfo l'accélère              │
└──────────────────────────────┘   └──────────────────────────────────┘
Appel Table intégrée 8.0
getExtensions('image/jpeg') jpg, jpeg, jpe, jfif
getMimeTypes('js') text/javascript d'abord

Les arrays sont classés par priority, le premier étant le préféré — la documentation 8.0 en montre un ordre que le code ne rend plus. guessMimeType() lit le contenu, pas le nom : un PNG nommé .txt est image/png. L'extension PHP fileinfo l'accélère ; un devineur maison implémente MimeTypeGuesserInterface, tag mime.mime_type_guesser.

Les résultats du tableau supposent les correspondances intégrées, sans remplacement personnalisé. Le registre de devineurs consulte d'abord le dernier enregistré, saute ceux qui ne sont pas disponibles, puis retient le premier résultat non nul. Il peut rendre null si les devineurs disponibles ne reconnaissent rien ; sans devineur disponible, il lève une LogicException.

La détection n'est pas une preuve d'innocuité d'un fichier téléversé. Renommer un contenu en .pdf ne le convertit pas, et le qualifier de PDF ne dispense pas de limiter taille, accès et usage. Le tag prépare l'intégration d'un devineur service ; il ne signifie pas que le conteneur inspecte chaque fichier pendant sa compilation.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le premier élément est préféré.
  2. Ne pas déduire une priorité de l'alphabet.
Voir l’explication : en dernier

Deux ordres voisins ont des sens différents : la variante MIME préférée vient en dernier, alors que le premier résultat d'une table MimeTypes est le préféré. Ne pas transférer la règle de l'un à l'autre :

multipart/alternative :  [ text/plain , text/html ]   préférée = DERNIÈRE
MimeTypes (tables)    :  [ premier , second , ... ]   préféré  = PREMIER
  • Voir l’explication : Dans multipart/alternative, la version préférée est la dernière.

    Dans multipart/alternative, la version préférée est la dernière. Plausible car : dans MimeTypes le premier est le préféré, on transfère la règle.

  • Voir l’explication : guessMimeType() ignore le nom du file

    guessMimeType() ignore le nom du file — il lit le contenu. Plausible car : getMimeTypes('js') part, lui, d'une extension ; on pense que la devinette fait pareil.

  • Voir l’explication : Les arrays de MimeTypes sont classés par priority, pas alphabétiquement

    Les arrays de MimeTypes sont classés par priority, pas alphabétiquement — et la priority réelle du code diffère de l'exemple de la documentation. Plausible car : la documentation 8.0 montre un autre ordre ; on la croit plutôt que le code.

  • Voir l’explication : L'UTF-8 dans la partie locale est refusé pour le sender seul.

    L'UTF-8 dans la partie locale est refusé pour le sender seul. Plausible car : « UTF-8 interdit » semble une règle générale ; or Envelope l'accepte pour un destinataire.

  • Voir l’explication : Construire un Email n'envoie rien.

    Construire un Email n'envoie rien. Plausible car : toString() affiche un message complet et on croit qu'il est parti ; aucun transport n'est appelé.

  • Voir l’explication : to() remplace, addTo() ajoute.

    to() remplace, addTo() ajoute. Plausible car : le préfixe add est facile à oublier lors d'une relecture rapide.

Fiche express

À mémoriser

À retenir en priorité
  1. Le nom affiché est distinct de l'adresse.
  2. Address représente les deux.

Nous avons maintenant un document structuré avec des destinataires explicites. Il peut exister et être inspecté sans qu'un email soit envoyé. Cette distinction permet de tester sa composition sans contacter un serveur.

🧠 À retenir pour la certification :

Si tu dois retenir seulement 6 choses :

  • Mime fabrique, Mailer envoie.
  • Email haut niveau ; Message pour les besoins rares.
  • alternative = même contenu, préféré en dernier ; related = un tout ; mixed = natures différentes.
  • to() remplace, addTo() ajoute ; UTF-8 refusé pour le sender.
  • MimeTypes : arrays par priority ; jpg et text/javascript d'abord.
  • guessMimeType() lit le contenu ; fileinfo accélère.

Moyen mnémotechnique : « Même contenu, un tout, des natures ».

Phrase de mémorisation : « Mime écrit la lettre : versions alternatives, pièces liées en un tout, pièces séparées en mixed ; l'étiquette se lit dans la table, le contenu se devine en l'ouvrant. »

Le cours Mailer prend le relais : transport, éventuelle mise en file et échecs. Une représentation MIME correcte n'est pas une preuve de livraison.
