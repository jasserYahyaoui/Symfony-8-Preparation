Objectif

Le dispatcher sait choisir les listeners de l'import. Il reste à définir ce qu'ils reçoivent : seulement l'identifiant de l'article 42, un objet consultable, ou une valeur qu'ils peuvent remplacer ? L'objet événement constitue ce contrat. Son éventuel contrôle de propagation décide aussi si les listeners suivants seront appelés.

Ce cours répond à trois questions : que contient la base Event (et que ne contient-elle pas) ?, que fait vraiment stopPropagation() ?, quand choisir GenericEvent plutôt qu'une classe dédiée ?

L'essentiel

À comprendre

À retenir en priorité
  1. La class de base reste minimale.
  2. Les données métier nécessitent un modèle supplémentaire.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le cours EventDispatcher a montré qui est appelé et dans quel ordre. Il reste le « quoi » : l'objet qui voyage entre l'émetteur et les listeners. Sans contrat clair, chaque listener devine ce qu'il peut lire ou modifier.
  • Le piège de fond. On croit que Event transporte quelque chose, ou que stopPropagation() « annule » un traitement. Ni l'un ni l'autre : la base ne sait que couper la suite.
  • Ce que l'auteur veut que vous compreniez. C'est la sous-classe (ou GenericEvent) qui définit les données et les opérations permises ; le drapeau d'arrêt borne seulement la diffusion en cours.
  • Pourquoi c'est à l'examen. Les QCM portent sur GenericEvent (ArrayAccess sur les arguments, pas sur le sujet), sur hasArgument() contre getArgument(), et sur l'effet réel de stopPropagation() selon les priorities.

L'object event circule entre le code qui déclenche et les listeners. La class de base, Event, est volontairement pauvre : elle sait seulement arrêter la propagation. Pour transporter une donnée, on écrit une sous-classe, ou l'on prend GenericEvent — un sujet et des arguments, au prix du typage.

L'héritage n'est pas obligatoire : dispatch() accepte un objet ordinaire. Étendre Symfony\Contracts\EventDispatcher\Event est un choix pour réutiliser son drapeau d'arrêt. Le dispatcher respecte le contrat Psr\EventDispatcher\StoppableEventInterface, pas une convention de nom de méthode sur n'importe quel objet.

Trois façons de définir ce qui voyage

│ Objet ordinaire   │ Sous-classe Event │ GenericEvent                │
├───────────────────┼───────────────────┼─────────────────────────────┤
│ aucun héritage    │ extends Event     │ sujet + tableau d'arguments │
│ pas de drapeau    │ drapeau d'arrêt   │ drapeau d'arrêt             │
│ données typées    │ données typées    │ données lues par clé        │
│ à vous            │ à vous            │ non typées                  │

Le schéma

À retenir en priorité
  1. L'arrêt concerne la suite.
  2. Les listeners déjà exécutés ne sont pas annulés.

Où en est-on ? Le cours EventDispatcher a fixé l'ordre d'appel (priority haute d'abord). Ici nous ne changeons pas cet ordre : nous suivons l'état d'un même événement pendant qu'il le traverse.

L'ordre vient du cours EventDispatcher. Ici, nous suivons l'état du même événement pendant cet ordre : le listener 5 pose un drapeau, puis le dispatcher le lit avant d'appeler le listener 0 :

Bleu : appels ; ambre : lecture du drapeau ; vert : retour. Un listener qui appelle stopPropagation() continue son propre code : ce n'est pas return ni une annulation de transaction. La base Contracts Event implémente StoppableEventInterface ; un objet ordinaire peut être dispatché sans hériter d'elle, mais ne bénéficie pas automatiquement de ce mécanisme.

L'exemple : un achat validé

Exemple concret

À retenir en priorité
  1. Une class dédiée documente le contrat.
  2. Elle évite les keys non typées.

Où en est-on ? Nous passons du schéma à un contrat concret : une sous-classe de Event qui porte une donnée, et le code émetteur qui relit l'état après le dispatch.

Conservons la variante d'achat du cours précédent pour montrer un contrat typé. Order est votre classe métier déjà chargée ; $order est son instance et $dispatcher le dispatcher configuré. Aucun achat ni paiement n'est réalisé par ce fragment :

use Symfony\Contracts\EventDispatcher\Event;

final class OrderPlacedEvent extends Event
{
    public function __construct(private Order $order) {}

    public function getOrder(): Order
    {
        return $this->order;
    }
}

$event = $dispatcher->dispatch(new OrderPlacedEvent($order));
if ($event->isPropagationStopped()) {
    // un listener a coupé la suite
}

Ce que Symfony et vous voyez ici :

Élément Qui le fournit
stopPropagation(), isPropagationStopped() la base Event (héritée)
getOrder() et le type Order vous : c'est le contrat métier
nom de l'événement (ici la classe) le dispatcher, faute de nom explicite

Le getter impose ce que le listener reçoit. Un événement ArticleImported pourrait exposer un int $articleId plutôt qu'un Order ; il ne chargerait pas automatiquement ArticleView depuis cet identifiant. Le listener doit connaître le contrat choisi, notamment identifiant ou instantané.

Le retour de dispatch() permet de lire le même état après les callbacks. Si un callback lève, il n'y a pas de retour normal à cette instruction : arrêt de propagation et exception sont deux issues différentes.

Une class de base délibérément pauvre

À retenir en priorité
  1. Event porte l'arrêt de propagation.
  2. GenericEvent ajoute un conteneur de données générique.

Où en est-on ? Première des trois notions : ce que la base Event offre (presque rien) et qui définit le reste (la classe concrète).

🌍 In Real Life

La situation : au restaurant, le responsable relit le plateau prévu pour la table. Pour changer le plat, le collègue remplace ce qui est indiqué sur la fiche commune, pas sur un billet qu'il garde.

L’équivalent dans Symfony : fiche commune → ResponseEvent ; remplacement prévu → setResponse() ; relecture par le responsable → HttpKernel récupérant la Response.

Retour à la réalité technique : dans le trajet de GET /blog/42, la classe concrète de l'événement autorise certaines mutations. Une Response simplement retournée par le listener n'est pas le canal de remplacement.

🧠 Comment le mémoriser : « Modifier ce qui sera relu. » Image mentale : une fiche centrale corrigée. Question-réflexe : quelle API porte le résultat attendu ?

⚠️ À ne pas confondre : retour d'un listener et retour du contrôleur.

Symfony\Contracts\EventDispatcher\Event n'offre guère que l'arrêt de propagation, pour laisser chaque API définir son object. Le framework fait de même : ResponseEvent expose de quoi lire et remplacer la Response (getResponse(), setResponse()).

Pourquoi un listener ne peut-il pas simplement « retourner » une Response ? Parce que le dispatcher ne rassemble pas les retours des listeners : il rend l'event. L'émetteur (ici HttpKernel) relit ensuite cet objet. Le canal de communication est donc la mutation de l'event, pas la valeur de retour.

Listener ──setResponse($r)──▶ ResponseEvent ◀──getResponse()── HttpKernel
   │                          (objet partagé)
   └─ return $r ──▶ dispatcher : ignoré, rien n'est collecté

Lors de GET /blog/42, remplacer la Response via ResponseEvent modifie donc un objet que HttpKernel relit ; retourner une Response depuis le listener ne suffit pas à la substituer. Le dispatcher ignore ce retour individuel. La classe concrète définit les opérations permises, pas la base Event.

ResponseEvent::setResponse() n'arrête pas lui-même la propagation : remplacer une donnée et couper les listeners suivants sont des mécanismes distincts. Ne pas généraliser à partir du comportement d'un autre événement du kernel dont un setter peut aussi poser ce drapeau.

⚠️ À ne pas confondre : Event de base et événement métier

Base Event Votre sous-classe
Données aucune celles que vous exposez (getters)
Mutations aucune celles que vous autorisez (setters)
Arrêt stopPropagation() hérité tel quel

Plausible car : le mot « Event » évoque un objet « plein » (date, payload…), comme dans d'autres bibliothèques. Ici, la base est un simple drapeau.

Arrêter la propagation

À retenir en priorité
  1. La priority détermine quels effets précèdent l'arrêt.
  2. L'arrêt ne fait pas de rollback.

Où en est-on ? Deuxième notion : le drapeau d'arrêt de la base Event. C'est la seule capacité qu'elle fournit ; il faut en connaître la portée exacte.

🌍 In Real Life

La situation : le dossier d'import du blog passe de bureau en bureau. Un agent pose « ne plus transmettre » après avoir écrit sa note.

L’équivalent dans Symfony : mention d'arrêt → stopPropagation() ; bureaux suivants → listeners non encore appelés ; notes déjà écrites → effets conservés.

Retour à la réalité technique : le dispatcher consulte le drapeau avant les callbacks suivants. Il ne défait pas les précédents et ne sort pas magiquement de la méthode du listener courant.

🧠 Comment le mémoriser : « Stop devant, pas effacement derrière. » Image mentale : une barrière après deux bureaux annotés. Question-réflexe : qui a déjà agi avant l'arrêt ?

⚠️ À ne pas confondre : arrêt de propagation et rollback métier.

Supposons qu'une vérification ait déjà pris en charge un événement et que les autres vérifications ne doivent plus intervenir. L'arrêt ne remet pas l'import dans son état initial ; il borne la diffusion en cours :

  • $event->stopPropagation() : les listeners pas encore appelés ne le seront pas ; ceux qui ont tourné ne sont pas défaits.
  • Listeners de priorities 10, 5 (qui arrête), 0, -5 : seuls 10 et 5 tournent. L'effet dépend donc de l'ordre, c'est-à-dire des priorities.
  • Côté déclencheur, isPropagationStopped() se lit après le dispatch().

Avant / après, sur quatre listeners dont le deuxième arrête :

priority   10     5 (stop)    0        -5
appelé ?   oui    oui         NON      NON
effets     gardés gardés      jamais   jamais
                  └─ son code se termine normalement

Avec EventDispatcher 8.0 chargé, voici un arrêt observable sans dépendance à une classe métier :

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;
use Symfony\Contracts\EventDispatcher\Event;

$dispatcher = new EventDispatcher();
$dispatcher->addListener('blog.import.checked', static function (Event $event): void {
    $event->stopPropagation();
}, 10);
$dispatcher->addListener('blog.import.checked', static function (): void {
    throw new \LogicException('Ce listener ne doit pas être atteint.');
});
$event = $dispatcher->dispatch(new Event(), 'blog.import.checked');
var_dump($event->isPropagationStopped());

Résultat attendu : bool(true), sans l'exception du second listener. Si le dernier listener pose le drapeau, il vaut également vrai, mais personne n'a été sauté. Le drapeau ne prouve donc pas à lui seul qu'un traitement a été évité.

La base Event ne réinitialise pas ce drapeau au dispatch suivant. Redistribuer le même événement déjà arrêté peut empêcher tous les callbacks de ce nouveau dispatch. Créer un nouvel objet pour un nouveau fait plutôt que réutiliser un état de diffusion précédent. Aucun arrêt ne reprend un courriel envoyé ni une écriture déjà réalisée.

⚠️ À ne pas confondre : arrêt, return, exception, rollback

Listeners déjà appelés Suite du listener courant Listeners suivants
stopPropagation() gardés continue sautés
return gardés termine appelés
exception gardés interrompue non appelés ; elle remonte au caller

Plausible car : le mot « stop » fait penser à return ou à un rollback. En réalité, c'est un drapeau lu par le dispatcher entre deux appels.

`GenericEvent`, quand une sous-classe ne se justifie pas

À retenir en priorité
  1. Le sujet possède son accès séparé.
  2. Les keys décrivent les arguments.

Où en est-on ? Troisième notion : le cas où l'on ne veut pas écrire de classe. GenericEvent fournit un sujet et un sac d'arguments, en échange du typage.

Pour une extension locale dont le contrat reste très petit, le sujet peut être l'article consulté et les arguments quelques informations supplémentaires. Dans ce fragment, $subject et $dispatcher existent déjà ; foo est un nom explicite à utiliser aussi lors de l'inscription :

use Symfony\Component\EventDispatcher\GenericEvent;

$event = new GenericEvent($subject, ['key' => 'value']);
$dispatcher->dispatch($event, 'foo');
$event->getSubject();
$event->getArgument('key');      // ou $event['key']
$event->hasArgument('key');

setArgument(), setArguments(), getArguments() complètent l'ensemble. ArrayAccess et IteratorAggregate portent sur les arguments, pas sur le sujet. Le compromis : pas de class à écrire, mais une donnée non typée lue par key.

Où va chaque morceau du constructeur :

new GenericEvent($subject, ['key' => 'value'])
                    │              │
                    │              └─ arguments : $event['key'], getArgument()
                    └──────────────── sujet : getSubject() uniquement

Ici, getArgument('key') rend 'value' et hasArgument('key') rend true. getSubject() rend l'objet ou la valeur fourni séparément. $event['subject'] ne lit pas ce sujet : en l'absence d'un argument nommé subject, cet accès lève InvalidArgumentException.

hasArgument('missing') rend false, tandis que getArgument('missing') lève. La présence utilise array_key_exists() : un argument présent avec la valeur null existe encore. L'itération ne parcourt que le tableau d'arguments. Une API destinée à plusieurs services gagne souvent à devenir une classe dédiée, avec des accesseurs et des types explicites.

⚠️ À ne pas confondre : lire le sujet, lire un argument

Appel Lit Clé absente
getSubject() le sujet —
getArgument('k') / $event['k'] un argument lève InvalidArgumentException
hasArgument('k') la présence (array_key_exists()) rend false
foreach ($event as …) les arguments seulement —

Plausible car : $event['subject'] ressemble à une clé « naturelle » du sac. Le sujet est stocké à part ; seuls les arguments sont dans le tableau.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le résultat reste sur le même event.
  2. Le publisher peut adapter sa suite.
  • Priorités, mutations et arrêt de propagation

    Pour prévoir le résultat, suivre d'abord les priorités, puis les mutations et le drapeau. Ne pas déduire une annulation métier du mot « stop » :

  • Voir l’explication : La base Event ne transporte aucune donnée métier

    La base Event ne transporte aucune donnée métier — définir son propre objet, hériter pour réutiliser l'arrêt, ou utiliser GenericEvent.

  • Voir l’explication : stopPropagation() n'annule rien

    stopPropagation() n'annule rien : elle empêche seulement les listeners suivants d'être appelés.

  • Voir l’explication : L'effet de l'arrêt dépend des priorities

    L'effet de l'arrêt dépend des priorities, puisqu'il dépend de l'ordre.

  • Voir l’explication : isPropagationStopped() se lit après le dispatch()

    isPropagationStopped() se lit après le dispatch(), côté déclencheur.

  • Voir l’explication : GenericEvent implémente ArrayAccess

    GenericEvent implémente ArrayAccess sur ses arguments, pas sur son sujet — et IteratorAggregate, sur les mêmes arguments. Pourquoi on se trompe : chacun de ces pièges exploite une intuition venue d'ailleurs (un événement « plein » de données, « stop » = annuler, un tableau qui contiendrait aussi le sujet). Se demander à chaque fois : qui définit la donnée ? qui lit le drapeau, et quand ?

Fiche express

À mémoriser

À retenir en priorité
  1. La flexibilité repose sur des keys.
  2. Une class dédiée rend les attentes plus visibles.

Le contrat d'événement décide ce qui est lisible, modifiable et arrêtable. Le dispatcher ne fournit ni persistance, ni transaction, ni contrat métier par défaut. Cette séparation vaut aussi pour les événements HTTP et CLI.

Si tu dois retenir seulement 5 choses :

  • Event : arrêt de propagation, rien d'autre.
  • Donnée à transporter : objet dédié, éventuellement sous-classe de Event.
  • stopPropagation() saute la suite, n'annule rien.
  • isPropagationStopped() après le dispatch().
  • GenericEvent : sujet + arguments ; ArrayAccess sur les arguments.

Moyen mnémotechnique : « Porter, arrêter, ou tout mettre dans un sac ».

🧠 À retenir pour la certification

  • La base Event (Contracts) = drapeau d'arrêt uniquement ; elle implémente StoppableEventInterface, mais dispatch() accepte aussi un objet ordinaire.
  • Les données et mutations permises viennent de la sous-classe (ex. ResponseEvent avec getResponse() / setResponse()).
  • Un retour de listener n'est pas collecté : on communique en mutant l'event.
  • stopPropagation() : listeners non appelés sautés, aucun effet défait ; dépend des priorities.
  • Le drapeau n'est pas réinitialisé : nouvel objet pour un nouveau fait.
  • GenericEvent : getSubject() ; arguments via getArgument(), $event['k'], itération.
  • hasArgument() rend false ; getArgument() / $event['k'] lèvent sur clé absente.

Phrase de mémorisation : « L'event est une fiche commune : la base ne sait que poser une barrière devant les suivants, tout le reste — données et droits de modification — vient de la classe qu'on écrit, ou du sac GenericEvent où seuls les arguments s'indexent. »

Revenir aux événements Console pour voir des objets portant une décision de sortie. Pour une tâche durable et éventuellement asynchrone après l'import, comparer ensuite Messages et handlers.
