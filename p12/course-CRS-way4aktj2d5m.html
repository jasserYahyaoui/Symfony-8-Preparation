Question fil rouge : quand j'appelle le Validator, qu'est-ce qui est vérifié, et que me rend-il ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le résultat est une liste de violations.
  2. Une donnée invalide ne produit pas un bool.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Avant de créer un compte, l'application doit décider si les données respectent ses règles. Le component Validator centralise cette décision, sans Request, sans Form, sans base de données.
  • Le piège de fond. On croit qu'une liste vide « prouve » que tout est bon. Elle prouve seulement qu'aucune règle exécutée n'a échoué : si le mapping n'est pas chargé ou si le mauvais group est demandé, la liste est vide aussi.
  • Ce que l'auteur veut que vous compreniez. Une contrainte décrit une règle (Email, NotBlank...) ; son validateur vérifie la valeur. validate() retourne une liste de violations, pas un booléen. Hors framework, createValidator() ne charge pas les attributs PHP ; il faut activer leur mapping ou fournir les contraintes explicitement. Les erreurs de configuration ou du code personnalisé peuvent lever une exception.
  • Pourquoi c'est à l'examen. Les QCM testent le type de retour, l'effet d'un group inconnu, les raccourcis Validation::create* et la différence entre donnée invalide (violation) et configuration invalide (exception).

Une liste vide signifie seulement qu'aucune règle exécutée n'a signalé d'erreur : ce n'est pas la preuve que les bonnes règles ont été chargées.

Le schéma

À retenir en priorité
  1. Les constraints sélectionnées sont évaluées.
  2. Une liste vide signifie zéro violation.

Où en est-on ? Vue d'ensemble du trajet d'un appel validate() : d'où viennent les règles (arguments ou métadonnées), quels groups les sélectionnent, et ce qui sort (une liste). Les sections suivantes reprennent chaque étape.

Ambre = choix, bleu = traitement, sortie verte = résultat normal. Les flèches décrivent le flux de validation, pas l'héritage des classes. Une configuration incorrecte interrompt ce chemin par une exception. Hors framework, le chargement YAML ou programmatique reste possible : enableAttributeMapping() n'est requis que pour lire les attributs PHP, pas pour toute validation.

Pourquoi deux sources de règles ? Quand on valide une valeur isolée (validate('x', new Email())), il n'y a pas de classe : les règles viennent de l'argument. Quand on valide un objet, ses règles viennent de ses métadonnées, que le builder charge depuis les attributs, le YAML ou le XML.

Le fil rouge : un `User` et son adresse

À retenir en priorité
  1. Le property path localise la donnée.
  2. La descente conserve le chemin de l'object imbriqué.

Où en est-on ? Étape 1 sur 5 : l'exemple unique du cours. Un User avec trois règles, dont une cascade vers Address. Tout le reste en découle.

Après réception des données d'inscription, l'application doit décider si elles satisfont ses règles avant de créer le compte. User et Address isolent ici ce contrôle, comparable à celui de SignupData : aucune Request, aucun Form et aucun stockage ne sont nécessaires à cet appel explicite. Le builder active le mapping des attributs pour rendre les règles visibles.

use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

class Address
{
    #[Assert\NotBlank]
    public string $city = '';
}

class User
{
    #[Assert\NotBlank]
    #[Assert\Email]
    public string $email = 'x';

    #[Assert\Length(min: 3)]
    public string $name = 'ab';

    #[Assert\Valid]
    public Address $address;
}

$user = new User();
$user->address = new Address();
$validator = Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator();
$violations = $validator->validate($user);
// count($violations) === 3 ; aucun ordre de présentation n'est supposé.

Trois violations : email, address.city, name.

Pourquoi trois ? email = 'x' passe NotBlank mais échoue Email ; name = 'ab' est plus court que 3 ; address.city est vide, et Valid a envoyé le Validator dans l'objet Address. Sans Valid, la ville ne serait jamais regardée.

User ──► email  'x'     NotBlank OK, Email KO          → violation "email"
     ──► name   'ab'    Length(min 3) KO               → violation "name"
     ──► address        #[Valid] : on descend
              └─► city  ''  NotBlank KO                → violation "address.city"

🌍 In Real Life

La situation : l'agent reçoit un dossier d'inscription et une annexe d'adresse. Les consignes écrites sur le modèle de dossier n'aident que s'il les a chargées ; une consigne lui demande aussi d'ouvrir l'annexe.

L’équivalent dans Symfony : les contraintes décrivent les règles ; leurs validateurs les exécutent. Le mapping des attributs PHP rend visibles NotBlank, Email et Length, tandis que Valid déclenche ici l'examen de l'objet Address.

Retour à la réalité technique : posséder des attributs dans le code ne déclenche pas seul une validation. Le service configuré ou le builder doit charger les métadonnées et une intégration ou un appel doit lancer le contrôle. Une désérialisation JSON peut produire le même objet à valider sans Form ; elle ne prouve pas sa validité. Valid ne signifie ni chargement de l'adresse en base ni obligation qu'elle existe.

🧠 Comment le mémoriser : « Charger les consignes, puis ouvrir les annexes demandées. » Image mentale : dossier et annexe contrôlés avec une liste de règles effectivement ouverte. Question-réflexe : quelles règles ont été chargées et quel parcours d'objets a réellement été demandé ?

⚠️ À ne pas confondre : attribut PHP, attribut Request, contrainte, validateur, désérialisation et cascade de validation.

Les trois manières de valider

À retenir en priorité
  1. La valeur candidate peut être testée avant affectation.
  2. Les metadata de la property fournissent les constraints.

Où en est-on ? Étape 2 sur 5 : on sait ce qu'on valide ; reste à choisir l'étendue du contrôle. Le Validator offre une méthode par besoin.

Injecter ValidatorInterface fournit le service configuré ; cela ne déclenche pas une validation automatique de chaque argument ou objet du contrôleur. Valider l'objet entier inclut ses règles de classe, alors qu'une valeur candidate d'email peut être vérifiée avant affectation. Choisis l'étendue selon la décision à prendre, sans assimiler un contrôle local à la validité de toute l'inscription.

Besoin Method
tout l'object, constraints de class comprises validate($object)
une property d'un object existant validateProperty($object, 'email')
une valeur avant de l'affecter validatePropertyValue(User::class, 'email', $candidat)
une valeur isolée, sans class validate($valeur, new Assert\Email())
  • Chaque method accepte les groups en dernier argument ; un group qu'aucune constraint ne porte rend une liste vide, sans erreur.
  • validateProperty() sur une property inexistante rend une liste vide.
  • Hors framework : Validation::createValidator() donne 0 violation sur le User ; createValidatorBuilder()->enableAttributeMapping()->getValidator() en donne 3. Dans une application, on injecte ValidatorInterface.

Pourquoi createValidator() donne-t-il 0 ? Il construit un validateur sans loader d'attributs : les #[Assert\...] sont de simples attributs PHP que personne ne lit. C'est enableAttributeMapping() qui ajoute l'AttributeLoader (à vérifier dans ValidatorBuilder, où l'option vaut false par défaut).

Pourquoi validatePropertyValue() accepte-t-elle un nom de class ? Elle ne lit que les constraints de la property : pas besoin d'un objet peuplé, donc pas besoin d'affecter la valeur candidate avant de la tester.

  validate($user)                      tout l'objet (+ règles de classe, cascade)
  validateProperty($user, 'email')     une property de CET objet (valeur actuelle)
  validatePropertyValue(User::class,   une valeur candidate contre les règles
        'email', $candidat)            de la property, sans objet peuplé
  validate('x', new Email())           une valeur seule, règles données en argument

🌍 In Real Life

La situation : le bureau peut examiner tout un dossier, relire sa case email actuelle ou vérifier une proposition d'email avant de l'inscrire. Vérifier cette proposition ne certifie pas les autres pages.

L’équivalent dans Symfony : validate() examine l'objet selon ses métadonnées ou une valeur selon des contraintes explicites ; validateProperty() vise une propriété existante ; validatePropertyValue() confronte une candidate aux règles de cette propriété.

Retour à la réalité technique : le contrôle local n'exécute pas toutes les règles de classe de l'objet complet et n'affecte pas la candidate à sa propriété. Les groupes et métadonnées sélectionnent les règles exécutées. Injecter ValidatorInterface donne accès au service, pas une validation universelle de tous les arguments du contrôleur.

🧠 Comment le mémoriser : « Dossier, case actuelle ou proposition : choisir l'étendue. » Image mentale : loupe passant du dossier à une case puis à un post-it candidat. Question-réflexe : mon résultat concerne-t-il toute l'inscription ou seulement une valeur ?

⚠️ À ne pas confondre : validation d'objet, validation de propriété, test de candidate et affectation.

Ce qu'il retourne : une liste, jamais un bool

À retenir en priorité
  1. Une liste vide reste un object.
  2. count() distingue succès et violations.

Où en est-on ? Étape 3 sur 5 : l'appel est fait ; que contient le retour et comment le lire sans se tromper ?

Le POST invalide doit pouvoir expliquer plusieurs problèmes au lecteur. La liste conserve donc chemins, messages et codes ; le contrôleur ou l'intégration Form décide comment les présenter. En JSON, sélectionne explicitement les données publiques : getInvalidValue() peut contenir un mot de passe ou une autre saisie qui ne doit pas être renvoyée.

if (0 !== count($violations)) {
    foreach ($violations as $violation) {
        $violation->getMessage();
        $violation->getPropertyPath();   // 'email', 'address.city'
        $violation->getInvalidValue();   // 'x'
        $violation->getCode();           // Assert\Email::INVALID_FORMAT_ERROR
        $violation->getConstraint();     // l'objet Email
    }
}
  • Une liste vide convertie en booléen vaut true : tester count().
  • findByCodes(Assert\Email::INVALID_FORMAT_ERROR) filtre par code ; (string) $violations donne une ligne par violation.
  • php bin/console debug:validator affiche les constraints d'une class.

Pourquoi if ($violations) est-il un piège ? $violations est un objet (ConstraintViolationList) : un objet est toujours « vrai » en PHP, même vide. Le test if ($violations) serait donc vrai dans tous les cas. Seul count($violations) (ou count() > 0) répond à la question.

Pourquoi une liste plutôt qu'un bool ? Un false ne dirait pas quoi corriger. La liste porte, pour chaque erreur, le message, le chemin, la valeur, le code et la constraint : de quoi afficher, traduire, filtrer ou journaliser.

🌍 In Real Life

La situation : l'agent rend un carnet d'anomalies, même lorsqu'il n'y a aucune ligne. La présence du carnet ne signifie pas présence d'erreurs ; un carnet vide ne prouve pas qu'on a utilisé la bonne liste de contrôle.

L’équivalent dans Symfony : le retour normal est une ConstraintViolationListInterface, avec messages, chemins, codes et contexte. Compte ses violations plutôt que de convertir l'objet en booléen.

Retour à la réalité technique : zéro violation signifie aucune erreur signalée par les règles effectivement exécutées. Inspecte mapping et groupes si le résultat surprend. Un chemin de violation est un repère de donnée, pas un ID HTML garanti. Pour HTML ou JSON, expose seulement les informations nécessaires et n'inclus pas automatiquement les valeurs sensibles ni tout le contexte.

🧠 Comment le mémoriser : « Compter les lignes, puis vérifier la liste de contrôle. » Image mentale : carnet vide à côté d'une checklist oubliée. Question-réflexe : combien de violations, pour quelles règles, et quelles informations puis-je publier ?

⚠️ À ne pas confondre : liste vide, booléen vrai, absence de règles, validité métier globale et réponse HTTP.

Donnée invalide ou configuration invalide

À retenir en priorité
  1. Séparer donnée invalide et configuration invalide.
  2. Une constraint incohérente peut lever une exception.

Où en est-on ? Étape 4 sur 5 : le retour normal est une liste ; mais certains cas ne passent pas par la liste. Il faut distinguer l'erreur attendue de saisie de l'erreur de programmation.

Une adresse mal formée est une erreur attendue de saisie. Une contrainte Length sans bornes révèle au contraire une erreur de programmation. Traiter ces deux cas comme un formulaire simplement invalide masquerait une panne du dispositif de contrôle. Une liste vide doit aussi être rapprochée des groupes et métadonnées réellement exécutés.

Situation Résultat
donnée invalide, même mal typée (un array soumis à Email) violation : « This value should be of type string. »
constraint mal configurée (new Assert\Length()) MissingOptionsException à sa construction
scalaire ou null sans constraint RuntimeException : « Cannot validate values of type "string" automatically… »
objet sans contraintes explicites utilise les métadonnées de sa classe ; liste vide seulement si aucune règle exécutée n'échoue
tableau sans contraintes explicites parcourt les objets qu'il contient et leurs métadonnées ; pas une garantie de liste vide

Pourquoi un array soumis à Email donne-t-il une violation et non une exception ? Le validateur de la contrainte lève une exception de type, que le validateur récursif attrape pour la transformer en violation « This value should be of type … ». C'est l'utilisateur qui s'est trompé, pas le développeur. En revanche, validate('x') sans constraint est une faute du développeur : le Validator ne devine pas de règle pour un scalaire, d'où la RuntimeException (« Cannot validate values of type … automatically. Please provide a constraint. »).

  donnée mauvaise (saisie)        ──►  violation dans la liste   (cas normal)
  règle mal construite / absente  ──►  exception                 (bug à corriger)

🌍 In Real Life

La situation : une case mal remplie produit une remarque au demandeur ; une règle « longueur autorisée » sans aucune borne révèle une checklist défectueuse. Demander au lecteur de recommencer ne répare pas cette checklist.

L’équivalent dans Symfony : une donnée refusée produit normalement une violation ; une contrainte mal construite, un appel sans règles appropriées ou une panne du code personnalisé peut lever une exception.

Retour à la réalité technique : le Validator ne devine pas une règle pour un scalaire sans contrainte explicite. Pour un objet, il consulte les métadonnées ; un tableau peut entraîner le parcours de ses objets, pas une validation arbitraire de tout son contenu. Ne masque pas une erreur de configuration en échec métier et ne promets pas que tout appel retourne normalement.

🧠 Comment le mémoriser : « Dossier incorrect ou checklist cassée ? » Image mentale : remarque sur une case face à une règle sans borne. Question-réflexe : dois-je corriger la saisie ou le dispositif qui la contrôle ?

⚠️ À ne pas confondre : violation attendue, configuration invalide, exception de programmation et règles absentes.

Deux raccourcis de `Validation`

À retenir en priorité
  1. createIsValidCallable() produit un bool.
  2. createCallable() conserve la valeur valide et lève sinon.

Où en est-on ? Étape 5 sur 5 : certains consommateurs n'attendent pas une liste mais une fonction (prédicat ou valeur). Validation fournit deux adaptateurs.

Un consommateur tel qu'OptionsResolver attend un prédicat booléen ; une saisie console peut préférer une exception pour demander de recommencer. Ces adaptateurs changent le contrat de retour pour ce consommateur. Ils ne changent pas celui de ValidatorInterface::validate() et ne déterminent pas à eux seuls un statut HTTP.

Method Valeur invalide Valeur valide
Validation::createIsValidCallable(...) la function rend false true
Validation::createCallable(...) elle lève ValidationFailedException elle rend la valeur

Utiles là où l'on attend une function : setAllowedValues() d'OptionsResolver, une saisie en console.

Pourquoi deux variantes ? Un setAllowedValues() attend un callable qui rend true/false : c'est createIsValidCallable(). Une saisie console, elle, veut récupérer la valeur acceptée ou être interrompue par une exception pour reposer la question : c'est createCallable(). Dans les deux cas, le callable ne valide rien tant qu'on ne l'appelle pas.

🌍 In Real Life

La situation : un poste veut seulement un feu vert ou rouge ; un autre veut récupérer la pièce acceptée ou recevoir un signal d'arrêt. Le contrôle peut être adapté à ces deux interfaces sans changer son carnet interne.

L’équivalent dans Symfony : createIsValidCallable() fournit un prédicat booléen ; createCallable() fournit une fonction qui retourne la valeur valide ou lève ValidationFailedException en cas de violations.

Retour à la réalité technique : créer le callable ne valide pas encore la valeur : il faut l'appeler. Ces adaptateurs ne changent pas le contrat de ValidatorInterface::validate() et ne garantissent pas l'absence d'autres exceptions techniques. Retourner la valeur acceptée n'est pas la nettoyer, la persister ou choisir un statut HTTP.

🧠 Comment le mémoriser : « Feu booléen ou valeur avec signal d'arrêt. » Image mentale : deux sorties adaptées à deux postes. Question-réflexe : le consommateur attend-il un booléen, une valeur ou une exception ?

⚠️ À ne pas confondre : fabrique de callable, exécution de validation, liste de violations et décision HTTP.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le standalone demande un mapping explicite.
  2. Le service du framework se configure séparément.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Récapitulatif des pièges, avec la raison de leur plausibilité.

  • Voir l’explication : Un échec de règle produit normalement une violation.

    Un échec de règle produit normalement une violation. Cela n'interdit pas les exceptions de configuration, de valeur sans contraintes ou de code personnalisé ; ne pas promettre que tout appel à validate() réussit. Pourquoi on se trompe : « jamais d'exception » est tentant, car le cas normal n'en lève pas.

  • Voir l’explication : Une liste vide est un object.

    Une liste vide est un object. Seul count() dit si la validation a réussi. Pourquoi on se trompe : on écrit if ($violations) en pensant « il y a des erreurs ».

  • Voir l’explication : createValidator() ignore les attributes

    createValidator() ignore les attributes : il faut enableAttributeMapping(). Pourquoi on se trompe : dans une application Symfony, le framework l'active pour nous.

  • Voir l’explication : validatePropertyValue() n'a pas besoin de l'object peuplé

    validatePropertyValue() n'a pas besoin de l'object peuplé : elle teste une valeur candidate contre les constraints de la property. Pourquoi on se trompe : on suppose qu'il faut d'abord affecter la valeur.

  • Voir l’explication : Un group mal orthographié fait paraître l'object valide

    Un group mal orthographié fait paraître l'object valide : aucune constraint n'y appartient, la liste rendue est vide, sans erreur. Pourquoi on se trompe : on attend une exception sur un nom inconnu.

Fiche express

À mémoriser

À retenir en priorité
  1. Un group inconnu ne sélectionne rien.
  2. Une liste vide ne prouve pas que toutes les règles ont été exécutées.

Si tu dois retenir seulement 7 choses :

  • validate(), validateProperty(), validatePropertyValue() (accepte un nom de class).
  • Retour : une liste, vide = valide ; tester count().
  • Violation : message, path, valeur, code, constraint.
  • Hors framework : enableAttributeMapping() pour les attributs ; les contraintes explicites et les autres mappings restent possibles.
  • Donnée invalide → violation ; constraint mal configurée → exception.
  • Scalaire sans constraint → RuntimeException.
  • createIsValidCallable() rend un bool ; createCallable() lève.

Moyen mnémotechnique : « Règles sur la class, liste en retour, count() pour conclure ».

🧠 À retenir pour la certification

  1. validate() rend une liste (objet toujours « vrai ») : tester count().
  2. Liste vide ≠ « bonnes règles chargées » : mapping absent ou group inconnu donnent aussi une liste vide.
  3. createValidator() ignore les attributs ; enableAttributeMapping() les lit.
  4. Trois portées : objet (validate), property (validateProperty), valeur candidate (validatePropertyValue, nom de class accepté).
  5. Donnée invalide → violation ; contrainte mal configurée ou scalaire sans constraint → exception.
  6. createIsValidCallable() → bool ; createCallable() → valeur ou ValidationFailedException.

Phrase de mémorisation : « Le Validator rend un carnet, pas un oui/non : on compte les lignes, et on vérifie d'abord que les règles ont été chargées. »
