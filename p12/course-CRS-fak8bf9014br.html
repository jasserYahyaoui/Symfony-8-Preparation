Objectif

Le test de /blog/42 reste vert, mais son traitement appelle une ancienne API. Une dépréciation annonce que cet usage doit évoluer alors que la fonctionnalité existe encore. Il faut observer le signal, retrouver l'appelant et migrer sans perdre le comportement vérifié.

Question centrale : si une dépréciation ne fait échouer ni l'appel ni le test, comment la voir, et pourquoi faut-il quand même la corriger ?

L'essentiel

À comprendre

À retenir en priorité
  1. Une deprecation n'est pas une suppression immédiate.
  2. La visibilité dépend du traitement des erreurs.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un test vert n'est pas un code à jour : l'ancienne API fonctionne encore, mais elle disparaîtra à la prochaine majeure.
  • Le piège de fond. La notice est silencée (@) : sans handler, on ne voit rien. Silence ne veut pas dire absence.
  • Ce que l'auteur veut que vous compreniez. Trois résultats distincts : le retour métier, l'observation de la notice, le code de sortie de la suite.
  • Pourquoi c'est à l'examen. info par défaut, jamais d'exception pour une deprecation, corriger sur la dernière mineure.

Une deprecation émise par trigger_deprecation() est une notice E_USER_DEPRECATED silencée : elle ne fait pas échouer l'appel par elle-même. Elle est émise même sans affichage ; un handler d'erreurs peut la recueillir pour le journal configuré ou la debug toolbar en développement. On la corrige sur la dernière mineure, avant que la majeure ne supprime le code.

Ce cours utilise le runner PHPUnit natif, sans extension d'intégration supplémentaire. Il traite la consommation d'un ancien usage ; déclarer une dépréciation relève du cours Deprecations best practices.

Trois résultats doivent rester séparés : le retour métier de l'appel, l'observation d'une notice et le code de sortie de la suite. Une assertion réussie ne garantit pas une suite réussie si sa politique refuse les dépréciations observées.

appel déprécié ──► résultat métier   (l'assertion du test)
              ├──► notice émise      (observée ou non, selon le handler)
              └──► code de sortie    (selon la politique du runner)
Ces trois canaux sont indépendants.

Le schéma

À retenir en priorité
  1. La mineure fournit les avertissements.
  2. La majeure peut retirer les APIs concernées.

Où en est-on ? Début du cours : un schéma qui suit la notice de son émission jusqu'aux observateurs possibles. Lisez-le de haut en bas : chaque branche est un observateur différent.

La notice accompagne l'appel ; ce n'est pas le statut HTTP du blog ni une exception métier. Le handler et le runner décident de son observation :

Bleu : émission/collecte ; ambre : observateur ; vert : effet. Le choix du handler compte : un handler applicatif peut décider de lever, et PHPUnit peut rendre la suite non réussie selon ses options. Le chemin « continue » décrit le traitement standard, pas une garantie pour tout environnement.

L'exemple

Exemple concret

À retenir en priorité
  1. L'absence d'affichage n'est pas absence de notice.
  2. Consulter le dispositif de collecte.

Où en est-on ? Le schéma est posé ; un cas concret : un adaptateur ancien qui émet la notice, et un appel qui réussit malgré tout.

Imaginons qu'un adaptateur ancien appelé lors de l'import du catalogue utilise la méthode suivante. L'exemple garde un paquet fictif distinct de Symfony : 1.2 est sa version de dépréciation, pas la version du framework.

// Exemple dans acme/pkg 1.2, avec le helper de dépréciation chargé.
final class DeprecatedService
{
    public function oldThing(): void
    {
        trigger_deprecation('acme/pkg', '1.2', 'Old thing is deprecated.');
        // … le code continue et fonctionne
    }
}

$service = new DeprecatedService();
$service->oldThing();   // l'appel réussit, en silence
// journal, si le handler de Symfony est actif :
// [info] User Deprecated: Since acme/pkg 1.2: Old thing is deprecated.

Le retour void n'apporte ici aucun résultat métier à comparer. Il illustre seulement le signal et la continuation avec le traitement standard. Dans le vrai import, conserver une assertion sur les données produites, puis rechercher la notice même si la commande retourne 0. Un handler personnalisé qui lève changerait cette continuation.

Rappel : reconnaître une deprecation

À retenir en priorité
  1. La documentation et le signal d'exécution sont distincts.
  2. Un marqueur PHPDoc ne déclenche pas seul une erreur.

Où en est-on ? Avant d'observer, il faut savoir reconnaître : une dépréciation passe par deux canaux, l'un pour le lecteur, l'autre pour le code qui tourne.

🌍 In Real Life

La situation : le manuel d'import du blog marque une ancienne procédure « à remplacer ». Un compteur peut aussi signaler chaque utilisation réelle de cette procédure.

L’équivalent dans Symfony : note dans le manuel → PHPDoc @deprecated ; signal pendant l'utilisation → trigger_deprecation().

Retour à la réalité technique : le commentaire renseigne lecteur et outils statiques ; il n'émet pas à lui seul une notice d'exécution. Le signal est observable selon le handler et la configuration du runner, sans être automatiquement une exception métier.

🧠 Comment le mémoriser : « Étiquette dans le manuel, signal pendant l'appel. » Image mentale : page marquée à côté d'un compteur. Question-réflexe : quel canal prouve que ce code a réellement tourné ?

⚠️ À ne pas confondre : API dépréciée et API déjà supprimée.

Le lecteur du code et l'outillage d'exécution n'apprennent pas l'obsolescence par le même canal. Le commentaire ne s'exécute pas :

Marqueur Pour qui
l'annotation PHPDoc @deprecated, avec la version le lecteur du code
l'appel trigger_deprecation() le code qui tourne

Dans les conventions Symfony, une dépréciation est normalement introduite dans la prochaine mineure du composant concerné, jamais sur une classe, interface, trait ou méthode nouvellement introduits. La documentation prévoit une exception pour des dépréciations critiques, qui peuvent être introduites dans des versions antérieures encore supportées. Le retrait incompatible du code déprécié relève d'une majeure, pas d'une mineure ordinaire.

Pourquoi ce cycle ? Cela laisse aux utilisateurs une version entière pour migrer : la mineure annonce, la majeure retire. Corriger les dépréciations sur la dernière mineure, c'est préparer le passage à la majeure sans surprise.

Ne pas projeter automatiquement cette politique sur tout paquet tiers. Pour l'usage rencontré dans le blog, lire le message et le guide UPGRADE du paquet concerné : une annotation seule n'a pas émis de notice, et une notice observée ne prouve pas que le résultat actuel est incorrect.

Une notice, et elle est silencée

À retenir en priorité
  1. La deprecation conserve la compatibilité.
  2. Elle doit néanmoins être suivie et corrigée.

Où en est-on ? Première question mécanique : que fait exactement trigger_deprecation() ? Pourquoi ne voit-on rien ? Parce que l'@ supprime l'affichage, mais pas l'émission.

trigger_deprecation() appelle @trigger_error(…, \E_USER_DEPRECATED), avec un message préfixé par Since <paquet> <version>: lorsque ces informations sont fournies. Si les deux chaînes sont vides, le helper omet ce préfixe. Sur PHP 8.4, avec display_errors actif et le niveau concerné inclus dans error_reporting pour le cas non supprimé :

Situation Ce qu'on voit
trigger_deprecation(), aucun handler rien ; le script continue
trigger_error(…, E_USER_DEPRECATED) sans @ Deprecated: … dans l'output
handler d'erreurs de Symfony + journal une entrée info : User Deprecated: Since acme/pkg 1.2: …

Le handler de Symfony ne lève jamais d'exception pour une deprecation, même réglé pour lever à tous les niveaux (throwAt(E_ALL, true)) : un E_USER_WARNING devient une ErrorException, une deprecation reste en info. L'option framework.php_errors.throw, active en dev, n'y change donc rien.

Le code de throwAt() retire explicitement E_DEPRECATED et E_USER_DEPRECATED des niveaux convertis en exceptions. C'est une règle du handler Symfony, pas de tout handler PHP imaginable. Le niveau de journal info est le défaut : la configuration suivante peut le changer sans changer la nature PHP de la notice.

Pourquoi jamais d'exception ? Une dépréciation n'est pas un défaut : le code marche. Faire échouer la requête pour un avertissement de migration casserait des applications qui fonctionnent. Le signal est donc journalisé, pas levé.

Les voir

À retenir en priorité
  1. Collecter et faire échouer sont deux réglages.
  2. Vérifier le comportement de la version PHPUnit utilisée.

Où en est-on ? La notice existe ; où la lire ? Trois endroits : la toolbar en dev, le journal, et le runner de test. Chacun a son réglage.

  • En dev : avec le handler et la collecte configurés, la toolbar peut présenter les dépréciations de la requête.
  • Dans le journal : framework.php_errors.log vaut true, et accepte une table qui associe un niveau de journal à chaque niveau d'erreur PHP.
framework:
    php_errors:
        log:
            !php/const \E_USER_DEPRECATED: !php/const Psr\Log\LogLevel::ERROR

Cette table change la sévérité de journalisation, pas le niveau PHP E_USER_DEPRECATED, et ne provoque pas une exception par elle-même. La commande app:blog:import n'a pas de page HTML où injecter une toolbar : observer son journal ou le runner de test. Ne pas activer l'affichage détaillé des erreurs sur une page de production pour y chercher ces signaux.

  • Dans les tests natifs PHPUnit 12.5.44, sur PHP 8.4 : la collecte d'une deprecation supprimée et le code de sortie de la suite sont distincts. Sans handler applicatif remplaçant celui de PHPUnit, créer tests/LegacyNoticeTest.php :
<?php

use PHPUnit\Framework\TestCase;

final class LegacyNoticeTest extends TestCase
{
    public function testLegacyNotice(): void
    {
        @trigger_error('Ancienne API : utiliser la nouvelle méthode.', E_USER_DEPRECATED);
        self::assertTrue(true);
    }
}

Le @ est essentiel : sans lui, ce test ne démontre pas la suppression. Configurer phpunit.xml :

<phpunit failOnDeprecation="true">
    <testsuites>
        <testsuite name="legacy"><file>tests/LegacyNoticeTest.php</file></testsuite>
    </testsuites>
    <source ignoreSuppressionOfDeprecations="true"/>
</phpunit>

Avec PHPUnit 12.5.44 installé et les extensions requises actives sur PHP 8.4 :

php8.4 vendor/bin/phpunit --configuration phpunit.xml --display-deprecations

Le rapport historique P10 de ce cours indique, avec PHPUnit 12.5.44 et PHP 8.4.27 dans un outil isolé : 1 test, 1 assertion, 1 deprecation, code de sortie 1, malgré l'assertion réussie. Ces résultats sont conservés comme preuve historique, pas comme une nouvelle exécution ou admission P11. Le comportement attendu des trois configurations est :

Configuration Résultat
failOnDeprecation="true" seul OK, exit code 0
<source ignoreSuppressionOfDeprecations="true"> la deprecation est listée ; code 0
les deux la deprecation est listée ; exit code 1

Contrôle supplémentaire : sans @, failOnDeprecation="true" seul détecte la notice et donne le code 1. La suppression et la politique d'échec sont donc bien deux réglages distincts.

Pourquoi deux réglages ? Premier réglage : PHPUnit prend-il en compte une notice supprimée par @ ? (ignoreSuppressionOfDeprecations). Second réglage : une notice prise en compte fait-elle échouer la suite ? (failOnDeprecation). Il faut les deux pour qu'une deprecation silencée donne le code 1.

notice @-silencée
   │ ignoreSuppressionOfDeprecations ? non → ignorée, exit 0
   ▼ oui → listée
   │ failOnDeprecation ? non → exit 0
   ▼ oui → exit 1

Référence : gestion native des erreurs dans PHPUnit 12.5. Le manifeste officiel de 12.5.44 exige PHP >=8.3 ; le cas a été exécuté sur PHP 8.4, avec les extensions requises selon le rapport historique. Ce minimum du runner ne change pas le minimum PHP 8.4 de Symfony 8.0. Cette réécriture n'installe aucun outil et ne rejoue pas le test.

L'ancien verrouillage 12.0.10 a été refusé par Composer à cause de GHSA-vvj3-c3rp-c85p (PKSA-z3gr-8qht-p93v, correction dans 12.5.8). Il n'a pas été forcé. Ce changement historique concerne seulement l'outil PHPUnit natif utilisé pour cette preuve ; les API étudiées restent celles de Symfony 8.0. Les autres exemples de tests du parcours utilisent PHPUnit 11.5 ; ne pas confondre cette cible avec le runner 12.5.44 du cas de suppression documenté ici, ni forcer une ancienne version bloquée par un avis de sécurité.

Les corriger

À retenir en priorité
  1. Corriger progressivement réduit le risque.
  2. Ne pas attendre la suppression pour commencer.

Où en est-on ? Le signal est visible ; reste le travail : remplacer l'usage. La difficulté est de prouver que le comportement est resté le même et que le signal a disparu.

🌍 In Real Life

La situation : retirer le voyant de l'ancienne machine du blog ne modernise pas sa procédure. Il faut remplacer l'usage puis refaire le même travail de contrôle.

L’équivalent dans Symfony : voyant → dépréciation observée ; procédure concernée → appel identifié par la trace ; nouvelle procédure → API de remplacement.

Retour à la réalité technique : corriger exige de conserver le comportement attendu et de rejouer le scénario avec une collecte opérationnelle. Une notice absente peut aussi signifier un chemin non exécuté ou un diagnostic désactivé.

🧠 Comment le mémoriser : « Corriger l'usage, pas éteindre le témoin. » Image mentale : outil remplacé, témoin toujours branché. Question-réflexe : ai-je prouvé le comportement et la disparition de l'appel obsolète ?

⚠️ À ne pas confondre : seuil de tolérance du runner et suppression de la dette technique.

La route blog_show peut réussir alors que le journal cite oldThing(). Procéder sur cette preuve concrète :

  1. Rejouer /blog/42, puis le scénario d'import s'il utilise le même adaptateur, avec une collecte dont on a vérifié le fonctionnement.
  2. Identifier le paquet émetteur et la ligne appelante : le remplacement peut concerner le code applicatif ou nécessiter une version corrigée d'une dépendance.
  3. Lire le message et le guide UPGRADE, puis remplacer l'usage en conservant les assertions du résultat attendu.
  4. Rejouer les mêmes scénarios, sans désactiver la collecte pour obtenir du vert. Vérifier séparément le résultat métier et la disparition du signal.

Zéro notice sur un seul test ne prouve pas l'absence de chemins dépréciés non couverts. Monter le seuil accepté ou masquer un paquet ne migre pas son API.

Une mise à jour ciblée telle que composer update "symfony/*" reste soumise aux contraintes du projet : ce n'est ni une migration automatique du code ni une permission de dépasser la cible du cours. Pour préparer une majeure, la démarche générale est : dernière mineure de la majeure actuelle, correction des dépréciations observées, puis changement de majeure. Le contenu technique enseigné ici reste borné à Symfony 8.0.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un signal absent peut être un défaut de collecte.
  2. La preuve dépend aussi du chemin exécuté.
Voir l’explication : Une deprecation ne fait échouer ni la Request ni le test
  • Une deprecation ne fait échouer ni la Request ni le test par elle-même. Pourquoi on se trompe : on la confond avec une erreur ou un warning.
  • La notice est silencée : rien dans l'output, et sans handler d'erreurs, aucune trace. Pourquoi on se trompe : « rien affiché » semble vouloir dire « rien émis ».
  • En dev, la toolbar peut les montrer si la collecte est configurée : l'absence d'affichage n'est pas l'absence de signal.
  • Déprécié n'est pas supprimé ; conserver le comportement pendant la migration ne signifie pas garantir l'absence de tout autre bug.
  • On corrige avant la majeure, pas après.
