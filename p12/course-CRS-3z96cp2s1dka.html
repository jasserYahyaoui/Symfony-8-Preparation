Objectif

GET /blog/42 sait déjà afficher un ArticleView. Une variante GET /api/blog/42 doit maintenant fournir des données JSON, sans publier accidentellement les informations internes d'un objet. Le Serializer sépare le choix de la représentation et son écriture dans un format. Dans l'autre sens, une entrée JSON doit devenir une valeur PHP contrôlable, pas être considérée comme valide du seul fait qu'elle est décodable.

Ce cours suit huit questions : quelles sont les deux étapes ? Qu'est-ce qui est pris par défaut ? Comment choisir selon le contexte (groups) ? Quel normalizer agit ? Comment dénormaliser ? Que règle le contexte ? Que faire des références circulaires ? Et quels pièges retenir ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le normalizer choisit la représentation.
  2. L'encoder produit le format.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une API doit transformer des objets PHP en JSON (ou XML, CSV, YAML) et inversement, sans publier tout l'état interne. Il faut séparer « quoi montrer » de « comment l'écrire ».
  • Le piège de fond. Le Serializer n'est ni serialize() natif, ni une politique de sécurité : choisir des champs n'autorise personne.
  • Ce que l'auteur veut que vous compreniez. Normalizer (quoi) puis encoder (format) ; au retour, decoder puis denormalizer ; le premier normalizer compatible agit ; les métadonnées (groups, #[Ignore]) n'existent que si le normalizer sait les lire.
  • Pourquoi c'est à l'examen. Questions sur la représentation intermédiaire (pas toujours un array), l'ordre des normalizers, groups, les extractors de types, OBJECT_TO_POPULATE, circular_reference_limit (défaut 1).

Une serialization se fait en deux étapes : un normalizer change la valeur PHP en représentation normalisée, un encoder change celle-ci en format. Le normalizer décide quelles properties sortent, sous quel nom, avec quelle valeur ; l'encoder traite la syntaxe du format et ses options. Les bridges vers des services tiers sont hors programme.

Il ne s'agit pas de serialize()/unserialize() natifs de PHP : le contrat décrit ici des représentations comme JSON, et non une sauvegarde automatique de l'état interne complet d'un objet. Le routage choisit l'action, PropertyAccess permet certains accès aux membres, le Serializer produit la représentation ; autoriser l'accès et valider l'entrée restent des responsabilités distinctes.

  objet PHP ──normalizer──▶ représentation ──encoder──▶ texte JSON/XML/CSV/YAML
  objet PHP ◀─denormalizer─ représentation ◀─decoder─── texte JSON/XML/CSV/YAML
            (« quoi »)       (array, string,            (« comment »)
                              int, float, bool,
                              ArrayObject, null)

Le schéma

À retenir en priorité
  1. Le decoder lit la syntaxe.
  2. Le denormalizer construit la valeur PHP.

Exemple concret

À retenir en priorité
  1. Les groups filtrent selon l'usage.
  2. Les metadata doivent être chargées.

Où en est-on ? Avant le détail, un exemple compact avec les deux sens : une sérialisation filtrée par group, puis une mise à jour d'objet.

Pour isoler la sélection de champs, gardons une fiche de personne, utilisable comme profil public d'un auteur. Ce fragment suppose le service $serializer du framework et un $person avec les métadonnées du tableau « Choisir selon le contexte ». Le deuxième appel est un cas distinct de mise à jour : Order est une classe métier déjà définie, avec qty accessible en écriture et note existant ; $existingOrder est son instance. Il n'introduit ni commande d'achat ni modification pendant GET /blog/42.

use Symfony\Component\Serializer\Normalizer\AbstractNormalizer;

$json = $serializer->serialize($person, 'json', ['groups' => 'public-view']);

$order = $serializer->deserialize('{"qty":7}', Order::class, 'json', [
    AbstractNormalizer::OBJECT_TO_POPULATE => $existingOrder,
]);

La vue publique suppose les métadonnées chargées par le service du framework : avec les groups du tableau, seuls name et fullName sortent. Le second appel rend la même instance que $existingOrder, avec qty = 7 et note inchangé. Il ne valide pas les règles métier : ne pas exposer toutes les propriétés modifiables d'une entité à un payload non fiable.

Argument de serialize() Rôle
$person la valeur PHP à représenter
'json' le format : choisit l'encoder
['groups' => 'public-view'] le contexte de cet appel (3e argument)

Deux étapes, deux responsabilités

À retenir en priorité
  1. La représentation dépend du normalizer.
  2. Array n'est pas une obligation universelle.
  3. BackedEnumNormalizer conserve le backing type : int|string, pas toujours string.

Où en est-on ? Question 1 sur 8 : pourquoi deux étapes et qui fait quoi ? C'est la base de tout le reste.

Pour diagnostiquer une mauvaise réponse, regarder d'abord la valeur normalisée : un champ confidentiel déjà présent à ce stade n'est pas une erreur de guillemets JSON. Inversement, changer le format de sortie ne choisit pas les propriétés publiques à la place du normalizer.

La représentation normalisée n'est pas toujours un array :

Valeur Normalizer JSON
object ordinaire ObjectNormalizer → array {"name":"Ada"}
DateTimeImmutable DateTimeNormalizer → string RFC 3339 "2026-01-02T03:04:05+00:00"
enum backed 'H' BackedEnumNormalizer → string "H"
l'int 42 aucun 42

Comparons les deux responsabilités :

┌────────────────────────────────┐   ┌────────────────────────────────────┐
│          NORMALIZER            │   │              ENCODER               │
├────────────────────────────────┤   ├────────────────────────────────────┤
│ décide : quelles properties,   │   │ décide : la syntaxe du format      │
│ quel nom, quelle valeur        │   │ (JSON, XML, CSV, YAML)             │
│ plusieurs, triés : le premier  │   │ un seul par opération              │
│ compatible agit                │   │                                    │
│ rend : array, string, int,     │   │ rend : le texte                    │
│ float, bool, ArrayObject, null │   │                                    │
│ fuite d'un champ : ICI         │   │ ne choisit jamais les champs       │
└────────────────────────────────┘   └────────────────────────────────────┘

Le service par défaut compose une liste triée de normalizers et un seul encoder par opération. Encoders fournis : JSON, XML, CSV, YAML — ['k' => 'v'] donne {"k":"v"}, <response><k>v</k></response>, k puis v sur deux lignes, { k: v }. Un format sans encoder lève une UnsupportedFormatException.

Avec Serializer 8.0 et son autoload chargés, on peut observer les deux étapes sur une date, sans démarrer le kernel :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\DateTimeNormalizer;
use Symfony\Component\Serializer\Serializer;

$serializer = new Serializer([new DateTimeNormalizer()], [new JsonEncoder()]);
$date = new DateTimeImmutable('2026-01-02T03:04:05+00:00');
$normalized = $serializer->normalize($date, null, ['datetime_format' => 'Y-m-d']);
$json = $serializer->serialize($date, 'json', ['datetime_format' => 'Y-m-d']);
var_dump($normalized, $json);

Les valeurs attendues sont la string 2026-01-02, puis la string contenant "2026-01-02" avec les guillemets JSON. Un objet d'article contenant une date peut mobiliser ObjectNormalizer puis DateTimeNormalizer pour son membre ; cela ne demande pas deux encoders JSON. Une enum backed conserve pour sa part le type int|string de sa valeur, pas nécessairement une string.

Le Serializer vérifie d'abord que le format est pris en charge. Son chemin général normalise lorsque l'encoder le demande, puis encode ; les exemples JSON suivent bien ces deux étapes. La configuration standalone ci-dessus ne reçoit pas les autres services du framework par magie.

L’équivalent dans Symfony : sélection et représentation des données → normalizer ; écriture du format → encoder ; opération composée → serialize().

Ce qui est pris par défaut

À retenir en priorité
  1. La lecture suit les propriétés accessibles et accessors reconnus.
  2. La visibilité et les méthodes influencent l'output.

Où en est-on ? Question 2 sur 8 : sans aucune configuration, que sort ObjectNormalizer ? Réponse courte : plus que ce que l'on croit.

ObjectNormalizer lit l'object par l'accès aux properties :

Membre Dans l'output
property publique oui
property privée avec getWithGetter() oui, sous withGetter
isActive(), hasKids(), canFly() oui : active, kids, fly
property protégée ou privée sans accessor non
fetchThing() non : préfixe inconnu

Autrement dit : ce qui compte est l'accès, pas la visibilité déclarée.

getWithGetter()  ─ préfixe get ─▶ « withGetter »
isActive()       ─ préfixe is  ─▶ « active »
hasKids()        ─ préfixe has ─▶ « kids »
canFly()         ─ préfixe can ─▶ « fly »
fetchThing()     ─ préfixe inconnu ─▶ ignoré

#[Ignore] exclut une property ou une method des vues traitées par ce normalizer lorsque ses métadonnées sont chargées.

Une propriété privée n'est donc pas une politique de confidentialité : son getter reconnu peut publier sa valeur. Ce getter s'exécute réellement, avec son coût et ses éventuels effets de bord. Pour l'API de lecture, préférer une représentation explicitement maîtrisée comme ArticleView, et tester les champs absents autant que ceux présents.

Choisir selon le contexte

À retenir en priorité
  1. Les deux systèmes de groups diffèrent.
  2. Ne pas transposer le défaut du Validator.

Où en est-on ? Question 3 sur 8 : on veut deux vues d'une même fiche (publique et admin). Les groups sont l'outil, mais ils dépendent des métadonnées.

Une même fiche d'auteur peut alimenter une page publique et un écran d'administration. Les groupes de sérialisation nomment ces usages ; ils ne sont ni des rôles de sécurité ni des groupes de validation.

Les groups excluent ici et gardent ailleurs. Avec name et fullName dans public-view, age dans admin-view, email sans group :

Contexte Sortie
aucun group les quatre
'groups' => 'public-view' name, fullName
'groups' => '*' les quatre
'groups' => ['Default'] rien

Pas de group Default implicite, contrairement au Validator : * seul reprend les properties sans group.

Groups, #[Ignore] et #[SerializedName] (qui renomme dans le format seul) sont des métadonnées. Le service serializer du framework les lit ; un ObjectNormalizer construit sans fabrique de métadonnées les ignore — groups demandés, toutes les properties sortent, y compris celle marquée #[Ignore]. De même, sans MetadataAwareNameConverter, fullName n'est pas renommé.

Comparons les deux situations :

┌────────────────────────────────┐   ┌────────────────────────────────────┐
│ Service `serializer` framework │   │ ObjectNormalizer construit à la    │
│                                │   │ main, sans fabrique de métadonnées │
├────────────────────────────────┤   ├────────────────────────────────────┤
│ groups : filtrent              │   │ groups : ignorés (tout sort)       │
│ #[Ignore] : exclut             │   │ #[Ignore] : sans effet             │
│ #[SerializedName] : renomme    │   │ renommage : absent                 │
└────────────────────────────────┘   └────────────────────────────────────┘

Voici une configuration minimale explicite, avec Serializer et PropertyAccess 8.0 disponibles. La classe locale PublicProfile sert de petite vue de profil ; elle ne remplace pas le contrat d'ArticleView :

<?php
use Symfony\Component\Serializer\Attribute\Groups;
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Mapping\Factory\ClassMetadataFactory;
use Symfony\Component\Serializer\Mapping\Loader\AttributeLoader;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class PublicProfile
{
    #[Groups(['public'])]
    public string $name = 'Ada';
    public string $internalNote = 'À vérifier';
}
$metadata = new ClassMetadataFactory(new AttributeLoader());
$serializer = new Serializer([new ObjectNormalizer($metadata)], [new JsonEncoder()]);
echo $serializer->serialize(new PublicProfile(), 'json', ['groups' => ['public']]);

Sortie attendue : {"name":"Ada"}. Retirer la fabrique de métadonnées supprime ici le filtrage attendu, même si les attributs restent écrits dans la classe. La sélection des groupes vient du code de l'application : ne pas laisser le client choisir librement une vue d'administration.

Quel normalizer agit ?

À retenir en priorité
  1. L'ordre peut changer la représentation.
  2. Le normalizer générique doit laisser passer les cas spécialisés.

Où en est-on ? Question 4 sur 8 : plusieurs normalizers sont enregistrés. Lequel traite quelle valeur ? L'ordre de la liste décide.

Le Serializer confie la valeur au premier normalizer dont supportsNormalization() répond vrai ; getSupportedTypes() évite les appels inutiles.

Ordre price dans le JSON
[MoneyNormalizer, ObjectNormalizer] "12.50 EUR"
[ObjectNormalizer, MoneyNormalizer] {"cents":1250,"currency":"EUR"} 
valeur Money ──▶ 1. MoneyNormalizer ? supportsNormalization() = true ─▶ il agit
                 2. ObjectNormalizer  (jamais consulté pour cette valeur)

ordre inversé :  1. ObjectNormalizer ? accepte tout objet ─▶ il agit
                 2. MoneyNormalizer   (jamais consulté)

Le framework enregistre ObjectNormalizer à la priority −1000 : un normalizer de l'application enregistré avec la priorité habituelle 0 passe avant lui. Une priorité explicitement plus basse peut changer cet ordre.

L'autoconfiguration ajoute le tag serializer.normalizer à un service enregistré qui respecte le contrat ; la préparation du conteneur assemble la liste. L'autowiring fournit ses dépendances. Aucun de ces préparatifs n'est relancé à chaque objet de la réponse ; à l'exécution, le Serializer sélectionne parmi les normalizers déjà disponibles.

Pour voir pourquoi le premier compatible compte, conservons un montant isolé comme exercice de représentation. Il ne suppose pas de paiement pendant la lecture du blog. Cet exemple est limité aux centimes EUR non négatifs, pas à un modèle monétaire ni à un formatage localisé universels. Avec Serializer et PropertyAccess 8.0 chargés :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Exception\InvalidArgumentException;
use Symfony\Component\Serializer\Normalizer\NormalizerInterface;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final readonly class Money
{
    public function __construct(public int $cents, public string $currency = 'EUR')
    {
        if ($cents < 0 || $currency !== 'EUR') {
            throw new \InvalidArgumentException('Cet exemple accepte des centimes EUR non négatifs.');
        }
    }
}

final class MoneyNormalizer implements NormalizerInterface
{
    public function normalize(mixed $data, ?string $format = null, array $context = []): array|string|int|float|bool|\ArrayObject|null
    {
        if (!$data instanceof Money) {
            throw new InvalidArgumentException('Money attendu.');
        }

        return sprintf('%d.%02d %s', intdiv($data->cents, 100), $data->cents % 100, $data->currency);
    }

    public function supportsNormalization(mixed $data, ?string $format = null, array $context = []): bool
    {
        return $data instanceof Money;
    }

    public function getSupportedTypes(?string $format): array
    {
        return [Money::class => true];
    }
}

$money = new Money(1250);
$dedicatedFirst = new Serializer([new MoneyNormalizer(), new ObjectNormalizer()], [new JsonEncoder()]);
$genericFirst = new Serializer([new ObjectNormalizer(), new MoneyNormalizer()], [new JsonEncoder()]);
echo $dedicatedFirst->serialize(['price' => $money], 'json'), PHP_EOL;
echo $genericFirst->serialize(['price' => $money], 'json'), PHP_EOL;

Sorties attendues : {"price":"12.50 EUR"}, puis {"price":{"cents":1250,"currency":"EUR"}}. Le second normalizer n'est pas un post-traitement automatique. Le calcul entier rend aussi 0.07 EUR pour new Money(7) sans arrondi flottant.

Les trois méthodes constituent le contrat : produire la représentation, répondre sur le support d'une valeur, annoncer les types potentiellement traités. La garde de normalize() protège aussi les appels directs : supportsNormalization(new stdClass()) rend faux ; appeler quand même normalize(new stdClass()) lève l'exception du Serializer.

Méthode du contrat Question posée
normalize() quelle représentation produire ?
supportsNormalization() acceptes-tu cette valeur (et ce format, ce contexte) ?
getSupportedTypes() quels types peux-tu potentiellement traiter ?

Dans getSupportedTypes(), true annonce une décision de support réutilisable pour ce type et ce format, pas une représentation mise en cache. false demande de réévaluer le support ; null exclut le type. Si la décision dépend du contexte, une annonce true serait incorrecte. Cette variante conserve les imports et Money du bloc précédent :

final class ContextMoneyNormalizer implements NormalizerInterface
{
    public function __construct(private MoneyNormalizer $inner) {}

    public function normalize(mixed $data, ?string $format = null, array $context = []): array|string|int|float|bool|\ArrayObject|null
    {
        if (!$this->supportsNormalization($data, $format, $context)) {
            throw new InvalidArgumentException('Money et contexte money_as_text=true attendus.');
        }

        return $this->inner->normalize($data, $format, $context);
    }

    public function supportsNormalization(mixed $data, ?string $format = null, array $context = []): bool
    {
        return $data instanceof Money && ($context['money_as_text'] ?? false) === true;
    }

    public function getSupportedTypes(?string $format): array
    {
        return [Money::class => false];
    }
}

$contextual = new Serializer([
    new ContextMoneyNormalizer(new MoneyNormalizer()),
    new ObjectNormalizer(),
], [new JsonEncoder()]);
echo $contextual->serialize($money, 'json', ['money_as_text' => true]), PHP_EOL;
echo $contextual->serialize($money, 'json', ['money_as_text' => false]), PHP_EOL;

La même instance produit d'abord "12.50 EUR", puis {"cents":1250,"currency":"EUR"}. Annoncer true pourrait réutiliser le premier accord malgré le contexte devenu faux ; ici, la garde défensive lèverait alors au lieu de laisser ObjectNormalizer agir. Corriger l'annonce en false, pas supprimer la garde. Ces classes normalisent seulement : reconstruire Money exige un contrat de dénormalisation distinct.

getSupportedTypes()   [Money::class => ?]       sens
────────────────────  ────────────────────────  ──────────────────────────────
true                  décision réutilisable     support ne dépend que du type
                      pour ce type + format     et du format (PAS un cache de
                                                la représentation)
false                 réévaluer à chaque appel  support dépend du contexte
null                  type exclu                ce normalizer ne traite pas ce type

Dénormaliser

À retenir en priorité
  1. L'identité de l'object est conservée.
  2. Les valeurs absentes peuvent rester inchangées.

Où en est-on ? Question 5 sur 8 : on remonte le chemin. Un texte arrive (import, action d'écriture) et doit redevenir un objet PHP. Le piège est de croire que « JSON valide » veut dire « donnée valide ».

Revenons à l'entrée d'un import ou d'une action d'écriture. Du JSON syntaxiquement correct peut contenir un type incompatible avec le modèle. Un extractor de types fournit les types attendus ; il ne convertit pas n'importe quel texte en donnée valide :

Le decoder rend ce que porte le format ("H" reste une string) ; le denormalizer en fait Suit::Hearts. Le contrôle des types vient d'un extractor de types, que le service du framework reçoit :

JSON vers int $qty Sans extractor Avec extractor
{"qty":"7"} 7 : PHP convertit NotNormalizableValueException
{"qty":"x"} NotNormalizableValueException idem 
{"qty":"7"} → int $qty
   sans extractor : le denormalizer assigne « 7 », PHP convertit en 7
   avec extractor : le type JSON (string) ≠ type attendu (int) → refusé
{"qty":"x"} → aucune valeur entière possible → refusé dans les deux cas

COLLECT_DENORMALIZATION_ERRORS rassemble les erreurs dans une PartialDenormalizationException ; #[MapRequestPayload] l'active et en fait des violations. OBJECT_TO_POPULATE remplit le même object : {"qty":7} change qty et laisse note intact.

Le tableau concerne la configuration de contrôle indiquée et une propriété accessible : ce n'est pas une garantie qu'un setter métier acceptera toute string numérique. La collecte vise les erreurs de dénormalisation compatibles, pas toutes les exceptions possibles. Un résultat partiel n'est ni validé, ni prêt à enregistrer, ni automatiquement restauré à son état antérieur.

L'identité conservée se voit sur des préférences de notification du lecteur, dans cet exemple indépendant avec Serializer et PropertyAccess 8.0 chargés :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class Preferences
{
    public string $locale = 'fr';
    public bool $digest = true;
}
$preferences = new Preferences();
$serializer = new Serializer([new ObjectNormalizer()], [new JsonEncoder()]);
$result = $serializer->deserialize('{"locale":"en"}', Preferences::class, 'json', [
    'object_to_populate' => $preferences,
]);
var_dump($result === $preferences, $preferences->locale, $preferences->digest);

Valeurs attendues : true, en, true. Le champ absent n'est pas une demande de remise à zéro. object_to_populate vise la racine ; deep_object_to_populate étend ce comportement à certains objets enfants existants, pas à une fusion générale des tableaux d'objets. Définir la sémantique métier du PATCH avant de lui associer cette option.

Le contexte

À retenir en priorité
  1. Le contexte ajuste un appel.
  2. Il ne change pas la donnée d'origine.
  3. MaxDepth déclare la limite dans les metadata.
  4. Le contexte doit activer son application.

Où en est-on ? Question 6 sur 8 : on a déjà croisé groups, datetime_format, object_to_populate. Ce sont tous des clés de contexte.

Le contexte règle un appel : troisième argument de serialize(), quatrième de deserialize(). skip_null_values retire les properties nulles, datetime_format à Y-m-d rend "2026-01-02".

Méthode Position du contexte
serialize($data, $format, $context) 3e argument
deserialize($data, $type, $format, $context) 4e argument

Ces clés sont interprétées par les normalizers concernés : DateTimeNormalizer pour la date, normalisation d'objet pour les propriétés nulles. Elles ne modifient pas les types du modèle ni tous les appels suivants. Omettre une propriété nulle peut être un contrat de sortie ; cela ne signifie pas effacer une propriété absente lors d'une entrée.

#[MaxDepth(n)] décrit une profondeur maximale dans les métadonnées. Il faut également enable_max_depth: true dans le contexte pour activer son application. Un arbre profond sans boucle et un retour vers le même objet sont deux problèmes différents, abordés juste après.

#[MaxDepth(n)] décrit une limite de profondeur dans les metadata, mais son respect demande aussi enable_max_depth: true dans le contexte du normalizer. La profondeur et la référence circulaire répondent à deux questions différentes : combien de niveaux parcourir, ou rencontre-t-on à nouveau le même object dans la branche courante ? Une limite de profondeur ne remplace pas automatiquement le traitement d'une référence circulaire.

Documentation Symfony 8.0.

Les références circulaires

À retenir en priorité
  1. Une limite supérieure ne résout pas la boucle.
  2. Un handler peut rendre un identifier stable.

Où en est-on ? Question 7 sur 8 : que se passe-t-il quand A pointe vers B et B vers A ? Le parcours ne finirait jamais.

Deux objects dont les relations parcourues se pointent lèvent, sans traitement adapté, une CircularReferenceException. circular_reference_limit — combien de fois un object est sérialisé avant d'être jugé circulaire — vaut 1 par défaut.

Contexte Résultat
par défaut CircularReferenceException
limite à 2 l'exception, plus tard
circular_reference_handler qui rend 'ref' {"members":[{"org":"ref","name":"m"}]}
un même object dans deux properties sœurs aucune exception

Le compteur suit la branche en cours, pas le document entier.

Cycle (exception)                   Sœurs (pas de cycle)
  Org ──members──▶ Member             Doc ──a──▶ Shared
   ▲                  │                  └─b──▶ Shared   (même objet, 2 branches)
   └────────org───────┘               chaque branche voit Shared UNE fois
  Org revu dans sa propre branche

Pour une vue d'article enrichie avec un auteur et sa liste d'articles, choisir d'abord si la relation inverse doit réellement être exposée. Un groupe peut l'exclure ; un handler peut remplacer la référence par un identifiant. Le modèle reste inchangé : on rend la représentation finie plutôt que relever indéfiniment le seuil.

Le cycle minimal suivant permet d'isoler le mécanisme sans changer ArticleView. Avec Serializer et PropertyAccess 8.0 chargés :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class Node
{
    public ?self $next = null;
    public function __construct(public string $id) {}
}
$node = new Node('n1');
$node->next = $node;
$serializer = new Serializer([new ObjectNormalizer()], [new JsonEncoder()]);
echo $serializer->serialize($node, 'json', [
    'circular_reference_handler' => static fn (Node $item): string => $item->id,
]);

La propriété next devient la string n1. Le handler est borné au modèle Node et renvoie une valeur finie, pas l'objet à reparcourir. Tester séparément un vrai cycle, deux branches sœurs partageant un objet et un arbre trop profond : leurs résultats ne sont pas interchangeables.

🌍 In Real Life

La situation : la fiche d'un auteur renvoie à son article du blog, qui renvoie au même auteur. Recopier intégralement chaque renvoi ne finit jamais.

L’équivalent dans Symfony : fiche revisitée → même objet rencontré dans le parcours ; limite → détection circulaire ; référence courte choisie → résultat du handler adapté.

Retour à la réalité technique : augmenter la limite retarde le problème sans changer le cycle. Choisir les relations exposées ou une représentation de référence évite la répétition ; la profondeur et l'identité répétée restent deux notions distinctes.
