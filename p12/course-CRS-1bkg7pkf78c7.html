Objectif

La notification d'inscription a désormais ses collaborateurs et ses valeurs. Certains objets doivent toutefois être créés par une méthode qui normalise les entrées ou choisit une implémentation. Une factory, ou fabrique, prend cette décision à la place de l'appel direct au constructeur par le container. Nous allons suivre son entrée, son retour et le partage de l'objet obtenu, sans ajouter un envoi d'email réel.

Question directrice : quand new Classe(...) ne suffit pas, comment dire au container « pour fabriquer ce service, appelle plutôt cette méthode » ?

L'essentiel

À comprendre

À retenir en priorité
  1. La factory décide de la construction.
  2. Sa valeur retournée devient le service.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un constructeur doit seulement ranger ses arguments. Si la création demande de nettoyer une entrée, de choisir entre deux implémentations ou de refuser une valeur, cette logique n'a pas sa place dans le constructeur : on la met dans une méthode de création.
  • Le piège de fond. Il y a deux signatures : celle de la factory (qui reçoit les arguments configurés) et celle du constructeur final (qui reçoit ce que la factory décide de lui passer). On les confond.
  • Ce que l'auteur veut que vous compreniez. Le container n'appelle que la factory ; la valeur retournée devient le service, sans conversion.
  • Pourquoi c'est à l'examen. Les questions portent sur les cinq écritures de factory, le null de [null, 'create'], constructor: vs factory: et ce que reçoit réellement le constructeur.

Un callable est une cible que PHP peut appeler : méthode statique, méthode d'un objet, objet invocable ou fonction. factory choisit ce callable pour produire le service. Les arguments configurés alimentent sa signature, pas directement celle du constructeur final.

La factory peut elle-même faire new, choisir un objet existant ou échouer. La valeur retournée devient le service ; déclarer class ne convertit pas cette valeur vers cette class. Les types PHP de retour et des consommateurs restent des contraintes réelles. Un simple constructeur reste préférable si aucun protocole de création supplémentaire n'est nécessaire.

Le schéma

À retenir en priorité
  1. Le container appelle la factory.
  2. La factory choisit ensuite les arguments du constructor.

Où en est-on ? Avant les cinq écritures, le chemin d'exécution complet d'un service fabriqué : qui appelle qui, avec quelle valeur.

Le laboratoire conserve le nom fabien pour rendre la transformation visible : il entre dans create(), puis reçoit le préfixe factory: avant d'atteindre le constructeur.

Le pointillé orange décrit l'instruction ; les flèches pleines suivent l'appel puis le retour. Le résultat vert est l'objet fabriqué, pas nécessairement l'objet factory. Ce chemin suppose la première résolution ordinaire réussie d'un service partagé. Le constructeur s'exécute bien, mais la factory décide de ses arguments. Une nouvelle utilisation d'une méthode du service ne rejoue pas automatiquement cette création.

Sans factory / avec factory :

 SANS factory                           AVEC factory
┌──────────────────────────┐          ┌─────────────────────────────────┐
│ container                │          │ container                       │
│   └─ new Classe($args)   │          │   └─ Classe::create($args)      │
│                          │          │          └─ new self(décidé)    │
└──────────────────────────┘          └─────────────────────────────────┘
 arguments → constructeur               arguments → FACTORY
                                        la factory → constructeur

Le fil rouge : un NewsletterManager

À retenir en priorité
  1. Le résultat suit le partage du service.
  2. shared: false redemande une construction.

Où en est-on ? On pose l'objet de laboratoire. Observez bien d'où vient chaque valeur : c'est tout l'enjeu du cours.

Ce type applicatif fictif conserve seulement un libellé d'expéditeur. L'accesseur permet d'observer ce que le constructeur a reçu :

class NewsletterManager
{
    public function __construct(private string $sender = 'none') {}

    public static function create(string $sender): self
    {
        return new self('factory:'.$sender);
    }

    public function sender(): string
    {
        return $this->sender;
    }
}

NewsletterManager::create('fabien')->sender() rend factory:fabien. (new NewsletterManager('fabien'))->sender() rend fabien. La différence vient de la méthode appelée, pas d'une transformation automatique des strings par DependencyInjection. Aucun message n'est envoyé par cette classe.

Les écritures : choisir selon la nature du callable

À retenir en priorité
  1. Le préfixe @ désigne un service.
  2. Sans @ le callable est statique.

Où en est-on ? Étape 1 sur 5. Question : comment dire au container quelle méthode appeler ? Tout dépend d'une seule interrogation : la création a-t-elle besoin d'une instance (avec ses propres dépendances) ou peut-elle être statique ?

Avant d'écrire le YAML, regardons la signature de la création : exige-t-elle une instance possédant ses propres dépendances, ou peut-elle être appelée statiquement ? Les classes et fonctions de ce tableau sont des variantes applicatives à fournir, pas des APIs Symfony :

Ce qui fabrique Écriture YAML
une method statique d'une autre class factory: ['App\Email\NewsletterManagerStaticFactory', 'createNewsletterManager']
une method statique de la class du service factory: [null, 'create']
une method d'un service factory: ['@App\Email\NewsletterManagerFactory', 'createNewsletterManager']
un service invocable factory: '@App\Email\InvokableNewsletterManagerFactory' → __invoke()
une function PHP factory: 'App\make_newsletter'

Sans @ dans le premier élément, le nom de class désigne un appel statique. Avec @, le container résout d'abord l'objet factory. La forme courte d'un service invocable appelle son __invoke(). Une fonction doit, elle aussi, être effectivement chargée ; l'autoload PSR-4 des classes ne découvre pas automatiquement les fonctions.

Arbre de décision :

La méthode de création est-elle statique ?
   ├─ oui ──▶ [ 'Classe', 'méthode' ]            (sans @)
   │           └─ c'est la classe du service ? ─▶ [ null, 'méthode' ]
   └─ non ──▶ [ '@service', 'méthode' ]          (avec @)
                └─ pas de méthode, objet invocable ─▶ '@service'  (__invoke)
Fonction PHP globale ou namespacée (chargée) ─▶ 'App\ma_fonction'

Par exemple, pour App\TokenFactory sans argument requis et sa méthode d'instance create(): Token, avec les deux classes autoloadables :

services:
    App\TokenFactory: ~
    App\Token:
        factory: ['@App\TokenFactory', 'create']

Demander Token appelle create() sur l'objet factory. Retirer @ tenterait un appel statique invalide ; dans ce cas, la configuration peut traverser la compilation puis échouer à l'exécution avec Non-static method ... cannot be called statically. Une compilation réussie ne valide donc pas tout comportement du callable.

L'API PHP propose aussi ->factory(NewsletterManagerStaticFactory::createNewsletterManager(...)) ou ->factory([service(...), 'createNewsletterManager']). La première forme utilise la syntaxe PHP de création d'un callable, pas un appel immédiat avec des arguments métier ; la seconde référence un service via le helper de configuration approprié.

🌍 In Real Life

La situation : une instruction de fabrication peut désigner une procédure directement, ou demander de passer par un atelier équipé de ses propres outils.

L’équivalent dans Symfony : procédure directe → callable statique ou fonction ; atelier à obtenir d'abord → service factory référencé par @ ; entrée unique de l'atelier → __invoke().

Retour à la réalité technique : ['Classe', 'méthode'] demande un appel statique ; ['@service', 'méthode'] appelle une instance résolue. La forme '@service' exige un objet invocable. Une fonction doit être chargée ; l'autoload des classes ne la découvre pas automatiquement. La syntaxe PHP méthode(...) crée un callable, sans lancer ici sa fabrication métier.

🧠 Comment le mémoriser : « Dois-je obtenir le fabricant avant de lui demander le produit ? » Image mentale : procédure écrite d'un côté, atelier équipé de l'autre. Question-réflexe : le callable exige-t-il une instance ?

⚠️ À ne pas confondre : objet factory et objet produit ; une compilation réussie ne rend pas statique une méthode d'instance.

`[null, 'create']` : la class du service elle-même

À retenir en priorité
  1. null reprend la class de la definition.
  2. Il ne désigne pas une function globale.

Où en est-on ? Étape 2 sur 5. Cas le plus courant : la méthode de création est dans la classe qu'on est en train de définir. Question : faut-il répéter le nom de la classe ? Non : null le remplace.

Le raccourci résout null vers la class de la définition courante. Pour notre NewsletterManager autoloadable :

services:
    NewsletterManager:
        factory: [null, 'create']
        arguments: ['fabien']
        public: true

Dans ce laboratoire, public: true permet l'observation par $container->get(NewsletterManager::class)->sender() après chargement et compilation : le résultat attendu est factory:fabien. Le null ne désigne ni un service absent ni une fonction globale.

constructor: 'create' exprime la même sélection de méthode statique. Il ne se combine pas avec factory sur la même définition : le loader YAML lève LogicException dès le chargement. #[Autoconfigure(constructor: 'create')] peut porter cette intention sur la class, à condition que l'autoconfiguration applicable la lise. Ce n'est pas une nouvelle règle PHP permettant d'appeler statiquement une méthode d'instance ou de contourner sa visibilité.

Écriture Équivalent Combinable avec factory ?
factory: [null, 'create'] méthode statique de la classe du service —
constructor: 'create' le loader en fait [null, 'create'] non : LogicException au chargement
#[Autoconfigure(constructor: 'create')] même intention portée par la classe si l'autoconfiguration la lit

🌍 In Real Life

La situation : sur la fiche d'un modèle, « utiliser sa procédure create » désigne la procédure du modèle inscrit sur cette fiche, pas un fabricant inconnu.

L’équivalent dans Symfony : modèle de la fiche → classe de la définition ; instruction relative → [null, 'create'] ; autre notation de ce choix → constructor: 'create'.

Retour à la réalité technique : le null est remplacé par la classe de la définition, sans promettre un retour nullable. factory et constructor sont deux instructions alternatives : les combiner provoque une erreur au chargement YAML. L'attribute correspondant exige que l'autoconfiguration applicable le lise.

🧠 Comment le mémoriser : « Ici, null veut dire cette classe. » Image mentale : une flèche de la procédure vers le nom en haut de sa propre fiche. Question-réflexe : quelle classe cette définition porte-t-elle ?

⚠️ À ne pas confondre : option de configuration constructor et appel direct imposé à __construct() ; ici l'option sélectionne une méthode statique.

Les arguments vont à la factory

À retenir en priorité
  1. La signature de la factory est câblée.
  2. Les arguments ne ciblent pas directement le constructor final.

Où en est-on ? Étape 3 sur 5, la plus piégeuse. Question : à quelle signature appartiennent les arguments: du YAML ? À celle de la factory, jamais directement à __construct().

Rejouons exactement le YAML précédent, sans intercaler un autre new :

Appel Valeur reçue
NewsletterManager::create(), par le container 'fabien'
__construct(), par new self(...) dans create() 'factory:fabien'

Le container n'injecte pas d'abord fabien dans le constructeur puis dans create() : il appelle seulement la factory configurée. Si l'autowiring est actif, il examine sa signature ; les valeurs scalaires nécessitent toujours un choix explicite. Les named arguments doivent donc correspondre aux noms de la factory.

Ce second laboratoire montre une validation avant création :

final class Newsletter
{
    private function __construct(public readonly string $sender) {}

    public static function create(string $rawSender): self
    {
        $sender = trim($rawSender);
        if ($sender === '') {
            throw new InvalidArgumentException('Expéditeur vide');
        }

        return new self($sender);
    }
}
$newsletter = Newsletter::create(' équipe ');
echo $newsletter->sender, "\n";

La sortie est équipe. Une entrée composée seulement d'espaces lève l'exception avant de construire l'objet. Dans sa définition de service, l'argument nommé serait $rawSender, et non $sender. La validation vérifie ici une string non vide, pas une adresse email valide.

Pourquoi un constructeur private ici ? Pour forcer le passage par create() : on ne peut plus fabriquer un Newsletter sans validation. La factory statique peut appeler ce constructeur privé parce qu'elle appartient à la même classe.

🌍 In Real Life

La situation : l'atelier reçoit un bon brut, nettoie le libellé et transmet seulement le libellé accepté à l'assemblage. Il peut refuser le bon avant de fabriquer quoi que ce soit.

L’équivalent dans Symfony : bon brut → arguments configurés de la factory ; nettoyage/refus → code de create() ; entrée d'assemblage → arguments qu'elle passe elle-même au constructeur.

Retour à la réalité technique : le conteneur appelle la factory configurée, pas d'abord le constructeur final. Autowiring et arguments nommés concernent sa signature. Dans l'exemple, $rawSender devient $sender après trim() ; une chaîne non vide n'est pas forcément une adresse email valide.

🧠 Comment le mémoriser : « La factory reçoit, puis décide ce que le constructeur reçoit. » Image mentale : deux bons successifs, brut puis préparé. Question-réflexe : à quelle signature appartient ce nom d'argument ?

⚠️ À ne pas confondre : transformation effectuée par le code de création et conversion automatique par DependencyInjection.

Ce que le container retient : la valeur retournée

À retenir en priorité
  1. La class guide l'autowiring.
  2. Le retour de la factory doit respecter le contrat.

Où en est-on ? Étape 4 sur 5. La factory a tourné. Question : que garde le container, et vérifie-t-il que c'est du bon type ?

Le service attendu par nos consommateurs est un objet compatible. Utiliser strtoupper comme factory, avec une string en argument, produit une string : une voie de récupération typée ?object la refuse. La signature nullable ne transforme pas le container en registre général de valeurs scalaires ; les valeurs de configuration ont leurs mécanismes propres.

L'option class sert notamment à décrire le service pour le câblage ; elle ne convertit pas un stdClass en Liar. Si une factory déclarée : Liar rend un autre objet, PHP peut déjà échouer à son retour. Si aucun type de retour n'intercepte la faute, un consommateur exigeant Liar peut la révéler lors de l'injection. « Le container ne convertit pas » ne signifie pas « aucun type n'est contrôlé ».

Pour une même définition partagée et un même container, l'objet produit est normalement conservé après une résolution réussie. shared: false demande une nouvelle production à chaque résolution, pas à chaque méthode appelée sur un objet déjà obtenu. Même une factory rappelée peut choisir de rendre le même objet : un nouvel appel n'est pas une garantie d'identité différente.

 factory retourne  ──▶  devient LE service  ──▶  injecté dans le consommateur
      │                       │                            │
      │ (type de retour PHP)  │ (class: = description,     │ (type du paramètre
      │  1re frontière        │  PAS une conversion)       │  2e frontière)

🌍 In Real Life

La situation : coller « modèle Liar » sur un colis ne transforme pas son contenu. Rappeler le fournisseur ne garantit pas non plus qu'il livre un objet différent.

L’équivalent dans Symfony : étiquette → option class ; contenu réel → retour de la factory ; rappel du fournisseur → nouvelle résolution avec shared: false.

Retour à la réalité technique : le retour devient le service, sans conversion vers la classe déclarée. Les types PHP du retour ou du consommateur peuvent rejeter l'objet incompatible. Pour une définition partagée, le résultat réussi est normalement conservé ; une factory rappelée peut volontairement retourner la même instance.

🧠 Comment le mémoriser : « Vérifie le produit, pas seulement l'étiquette. » Image mentale : un colis ouvert à côté de son étiquette. Question-réflexe : quel objet est réellement retourné et qui décide de le réutiliser ?

⚠️ À ne pas confondre : partage de la factory, partage du produit et appel d'une méthode sur un produit déjà obtenu.

Une expression comme factory

À retenir en priorité
  1. L'expression accède aux arguments configurés.
  2. ExpressionLanguage doit être disponible.

Où en est-on ? Étape 5 sur 5. Jusqu'ici la factory fabrique. Parfois il suffit de choisir parmi des services déjà définis, selon un paramètre : une expression le fait en une ligne.

Une sélection simple peut aussi être décrite par une expression. Ce fragment de définition suppose ExpressionLanguage 8.0 disponible, kernel.debug défini, et deux services existants et compatibles avec les consommateurs :

factory: '@=parameter("kernel.debug") ? service("tracable_newsletter") : service("newsletter")'

Si kernel.debug vaut true, l'expression rend le service nommé tracable_newsletter ; sinon elle rend newsletter. Ces identifiants historiques doivent correspondre à de vraies définitions. La factory sélectionne ici un objet plutôt que d'en construire forcément un neuf.

Dans ce contexte d'expression factory, arg(0) permet de lire le premier argument configuré de la définition. Sans ExpressionLanguage, cette syntaxe @= échoue au chargement. Le loader ne l'accepte pas comme configurator : un configurator intervient sur un objet déjà créé, ce qui est une responsabilité différente. Une sélection complexe serait souvent plus lisible et testable dans une classe factory explicite.

Factory Configurator
Moment crée (ou sélectionne) l'objet agit sur un objet déjà créé
Retour devient le service —
Expression @= acceptée refusée par le loader

🌍 In Real Life

La situation : le responsable choisit un équipement parmi deux déjà prévus, selon le mode de travail. Cette sélection n'exige pas de fabriquer un troisième équipement.

L’équivalent dans Symfony : critère de choix → kernel.debug ; équipements disponibles → services référencés ; sélection → expression @= utilisée comme factory.

Retour à la réalité technique : l'expression peut retourner un service existant ; les dépendances référencées doivent être disponibles et compatibles. Elle exige ExpressionLanguage. arg(0) lit l'argument configuré ; cette syntaxe de factory n'est pas acceptée comme configurator, qui intervient sur un objet déjà créé.

🧠 Comment le mémoriser : « Produire un résultat peut consister à choisir. » Image mentale : un aiguillage vers deux équipements disponibles. Question-réflexe : doit-on obtenir le service ou régler un objet déjà créé ?

⚠️ À ne pas confondre : factory et configurator ; une expression longue ne devient pas préférable à une classe de création testable.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Les deux mécanismes choisissent la construction.
  2. Il faut sélectionner une seule forme.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Pour chaque piège : l'énoncé, puis pourquoi la mauvaise réponse semble plausible.

  • Voir l’explication : Suivre les deux signatures, pas seulement la valeur finale.

    Suivre les deux signatures, pas seulement la valeur finale. create('fabien') reçoit la valeur configurée ; son new self() reçoit factory:fabien. Un argument nommé doit viser la première signature. Plausible car on lit arguments: ['fabien'] comme « le constructeur reçoit fabien ».

  • Voir l’explication : Le null du raccourci est une cible relative.

    Le null du raccourci est une cible relative. Il désigne la class du service, pas un résultat nullable ni une fonction à chercher dans le namespace global. Plausible car null évoque « rien » en PHP.

  • Voir l’explication : Le @ décide si l'on demande un objet factory.

    Le @ décide si l'on demande un objet factory. Une méthode d'instance exige cette instance ; la forme courte '@service' appelle son __invoke(), pas son constructeur comme résultat final. Plausible car @ est lu comme un simple préfixe de référence.

  • Voir l’explication : Compilation réussie ne rend pas une méthode statique.

    Compilation réussie ne rend pas une méthode statique. Le mauvais callable peut échouer au premier appel effectif. Vérifions la signature et la référence plutôt que déduire la validité de l'absence d'erreur lors du chargement. Plausible car « compilé » rassure sur la validité de tout.

  • Voir l’explication : La class déclarée ne transforme pas le retour.

    La class déclarée ne transforme pas le retour. Les signatures PHP de la factory, des accès et du consommateur peuvent chacune révéler une incompatibilité à leur frontière. Plausible car class: ressemble à un cast.

  • Voir l’explication : Choisir une seule instruction de fabrication.

    Choisir une seule instruction de fabrication. factory et constructor sur la même définition provoquent LogicException au chargement ; ce n'est pas une séquence de deux créations. Plausible car les deux semblent complémentaires.

  • Voir l’explication : Un attribute ignoré ne remplace pas le constructeur.

    Un attribute ignoré ne remplace pas le constructeur. Avec autoconfiguration désactivée et aucune autre factory explicite, la création ordinaire s'applique. L'attribute ne s'exécute pas de lui-même. Plausible car un attribut PHP paraît actif dès qu'il est écrit.

Fiche express

À mémoriser

À retenir en priorité
  1. Un service peut être callable.
  2. La factory invocable n'a pas besoin de nom de method séparé.

Avant de fabriquer le service de notification :

  1. Choisir constructeur ordinaire ou véritable protocole de création.
  2. Identifier callable statique, objet factory, invocable ou fonction.
  3. Fournir les arguments de ce callable.
  4. Vérifier la compatibilité du retour et les erreurs avant création.
  5. Ne pas combiner constructor et factory.
  6. Raisonner sur le partage du produit, séparément de celui de la factory.
  7. Réserver les expressions aux choix lisibles avec leurs dépendances disponibles.

Les services seront construits plus tard. Pour transformer leur plan collectivement avant cette utilisation, il faut comprendre les compiler passes.

🧠 À retenir pour la certification

  • factory désigne un callable ; les arguments vont à la factory, pas au constructeur final.
  • Sans @ → appel statique (['Classe','méthode']) ; avec @ → instance résolue ; '@service' seul → __invoke().
  • [null, 'create'] : null = la classe de la définition ; constructor: 'create' équivaut, mais jamais avec factory (LogicException).
  • Mauvais callable : la compilation peut réussir, l'erreur survient au premier appel.
  • La valeur retournée devient le service ; class: ne convertit rien, les types PHP contrôlent aux frontières.
  • shared: false → nouvelle production par résolution ; une factory peut rendre le même objet.
  • @= (ExpressionLanguage) : sélection OK comme factory, refusée comme configurator.

Revoir : L'essentiel

When a service has a factory, who constructs the service object?

The configured callable, not a direct container call to the service constructor.

La factory décide de la construction. Sa valeur retournée devient le service.

Revoir : Le schéma

Where are a factory-based definition's arguments passed?

To the factory callable.

Le container appelle la factory. La factory choisit ensuite les arguments du constructor.

Does a shared factory-based NewsletterManager call its factory on every retrieval?

No. The shared result is reused after the first creation.

Le résultat suit le partage du service. shared: false redemande une construction.

Revoir : Les écritures : choisir selon la nature du callable

How does ['@factory_service', 'create'] differ from ['FactoryClass', 'create']?

The first calls an instance service; the second calls a static class method.

Le préfixe @ désigne un service. Sans @ le callable est statique.

Revoir : `[null, 'create']` : la class du service elle-même

What does factory: [null, 'create'] mean?

Call create() statically on the class configured for that service.

null reprend la class de la definition. Il ne désigne pas une function globale.

Revoir : Les arguments vont à la factory

Can a factory receive autowired service arguments?

Yes, when autowiring is enabled for its definition.

La signature de la factory est câblée. Les arguments ne ciblent pas directement le constructor final.

Revoir : Ce que le container retient : la valeur retournée

Does declaring class: Expected guarantee that a factory returns Expected?

No. A wrong object type may fail later when injected into a typed consumer.

La class guide l'autowiring. Le retour de la factory doit respecter le contrat.

Revoir : Une expression comme factory

What does arg(0) refer to in a factory expression?

The first configured argument of the service definition.

L'expression accède aux arguments configurés. ExpressionLanguage doit être disponible.

Can factory and constructor be configured together on the same definition?

No. Their combination is rejected.

Les deux mécanismes choisissent la construction. Il faut sélectionner une seule forme.

What does a factory configured only as '@factory_service' invoke?

The service's __invoke() method.

Un service peut être callable. La factory invocable n'a pas besoin de nom de method séparé.
