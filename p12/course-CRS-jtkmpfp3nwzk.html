Objectif

Le controller de /blog/42 sait demander son catalogue. Pour produire une page, générer son lien ou enregistrer un diagnostic, il lui faut maintenant des collaborateurs que nous n'avons pas écrits. Nous allons retrouver leur origine, choisir leur contrat d'injection et diagnostiquer une absence sans confondre bibliothèque installée et service configuré.

Question directrice : je n'ai écrit ni logger, ni router, ni Twig : d'où viennent-ils, et comment savoir quel type écrire dans mon constructeur ?

L'essentiel

À comprendre

À retenir en priorité
  1. Les bundles enregistrent les services.
  2. Une fonctionnalité désactivée peut retirer ses aliases.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un projet Symfony démarre avec des dizaines de services déjà prêts. Savoir d'où ils viennent évite d'en recréer et permet de diagnostiquer leur absence.
  • Le piège de fond. Bibliothèque installée ≠ bundle actif ≠ service configuré. Et l'identifiant (logger), la classe concrète et le type injectable sont trois choses différentes.
  • Ce que l'auteur veut que vous compreniez. Les bundles chargent des définitions et publient des alias de type ; debug:autowiring donne le type à écrire, debug:container explique la définition.
  • Pourquoi c'est à l'examen. LoggerInterface, RequestStack, --all, section enabled: false, TwigBundle absent.

Dans l'application Symfony 8.0, les bundles activés chargent des définitions de services. FrameworkBundle fournit le socle ; d'autres intégrations ajoutent leurs capacités selon les packages présents et les fonctionnalités activées. Le bundle peut publier un alias reliant un type PHP à l'identifiant du service.

Nous cherchons donc le rôle nécessaire avec debug:autowiring, puis inspectons la définition avec debug:container. Le premier outil aide à écrire le type du constructeur ; le second explique ce qui est enregistré. Une section désactivée retire son câblage automatique, pas la possibilité pour l'application de déclarer elle-même une implémentation.

Plan du cours :

Le schéma

À retenir en priorité
  1. Le type doit correspondre à un service ou alias.
  2. La présence d'une bibliothèque seule ne suffit pas.

Où en est-on ? On sait qu'un bundle fournit des services. Voyons la chaîne complète : bundle activé → service → alias de type → argument de constructeur, avec la commande qui permet de la constater.

Pour rendre l'article, la bibliothèque Twig doit être disponible, mais il faut aussi un objet Twig\Environment configuré. Le diagramme utilise le consommateur historique InvoiceMailer : la même distinction installation, intégration et injection vaut pour notre rendu de page.

Orange : l'intégration active enregistre le service et son alias ; bleu : la commande constate ce câblage ; vert : l'autowiring peut fournir l'objet au consommateur enregistré. Exécuter la commande ne crée ni alias ni service manquant. Sans TwigBundle, installer twig/twig apporte les classes mais pas cette configuration automatique. Une déclaration manuelle reste possible, à condition de configurer aussi les dépendances nécessaires de Twig.

Le fil rouge : un `InvoiceMailer`

À retenir en priorité
  1. Le service configuré est injecté.
  2. Le consommateur n'assemble pas son infrastructure.

Où en est-on ? Le schéma est posé ; voici le consommateur concret. Il demande trois collaborateurs que nous n'avons pas écrits.

Conservons cette classe de laboratoire pour examiner trois besoins : journaliser, générer une URL et rendre un template. Son nom historique n'ajoute pas une fonctionnalité de facturation au blog. Les imports rendent explicites les contrats PHP utilisés :

use Psr\Log\LoggerInterface;
use Symfony\Component\Routing\Generator\UrlGeneratorInterface;
use Twig\Environment;

class InvoiceMailer
{
    public function __construct(
        private LoggerInterface $logger,              // Psr\Log\LoggerInterface
        private UrlGeneratorInterface $urls,          // Symfony\Component\Routing\Generator\…
        private Environment $twig,                    // Twig\Environment
    ) {
    }
}

Avec cette classe enregistrée et autowirée, Routing et Twig configurés et leurs aliases disponibles, le constructeur reçoit trois objets compatibles. Il ne rend encore aucun template et n'envoie aucun email : il conserve seulement les collaborateurs. Si Twig\Environment manque, ajouter un argument string $twig ne réparerait pas l'assemblage. Il faut retrouver la définition ou l'intégration absente.

Pour le lien vers l'article, le générateur peut utiliser blog_show avec id = 42 lorsque cette route est chargée. La génération d'URL ne consulte pas ArticleCatalog : un lien bien formé ne prouve pas que l'article existe.

🌍 In Real Life

La situation : un poste reçoit un carnet de diagnostic, un annuaire et un outil de mise en page. Leur remise ne rédige encore aucun document.

L’équivalent dans Symfony : diagnostic → LoggerInterface ; fabrication du lien → UrlGeneratorInterface ; rendu de template → Twig\Environment ; remise au poste → injection dans le constructor.

Retour à la réalité technique : le consommateur enregistré reçoit des collaborateurs grâce au câblage disponible. Son nom InvoiceMailer ne déclenche ni facturation ni envoi d'email. Générer le lien de blog_show ne prouve pas l'existence de l'article ; recevoir Twig ne rend aucun template.

🧠 Comment le mémoriser : « Recevoir les outils n'exécute pas le travail. » Image mentale : trois outils posés sur une table encore inutilisés. Question-réflexe : voit-on seulement l'assemblage ou un appel métier explicite ?

⚠️ À ne pas confondre : objet injecté, identifiant du service et simple chaîne contenant son nom.

D'où viennent les services intégrés

À retenir en priorité
  1. La bibliothèque fournit la class.
  2. Le bundle fournit son intégration au service container.

Où en est-on ? Étape 1 sur 2. Question : qui crée ces services avant que j'écrive la moindre ligne ? Les extensions de bundle, à partir de leur configuration — et seulement si le package est présent et la fonctionnalité activée.

Une extension de bundle traduit sa configuration en définitions. FrameworkBundle câble notamment le router, le dispatcher, RequestStack, le cache et le filesystem. Serializer, Validator et HttpClient dépendent aussi de la présence des packages et de l'activation des sections correspondantes. TwigBundle et SecurityBundle ont leurs propres intégrations.

La déclaration ->alias(RequestStack::class, 'request_stack') relie ici le nom complet d'une class au service interne. Ce n'est pas une interface inventée pour les besoins de l'autowiring. La recipe Flex peut aider à activer le bundle ; une activation manuelle reste possible, et installer un package ne suffit pas toujours.

Voici comment lire quatre états de configuration, en supposant FrameworkBundle actif pour les deux lignes Serializer :

Situation Injectable ?
TwigBundle activé Twig\Environment : oui
twig/twig installé, sans TwigBundle pas d'enregistrement automatique par ce bundle ; une définition applicative peut fournir Twig\Environment
symfony/serializer installé, section par défaut SerializerInterface : oui
framework.serializer.enabled: false pas d'alias fourni par cette section ; une déclaration applicative reste possible

Si TwigBundle est actif et correctement configuré, le consommateur peut recevoir son environnement Twig. Si seule la bibliothèque est présente, nous devons activer l'intégration ou fournir une définition applicative. Pour Serializer, l'installation du package autorise le câblage par défaut de la section ; le désactiver retire ce câblage, pas les classes PHP. Une définition applicative distincte peut toujours publier le contrat.

 package installé ──▶ bundle actif ──▶ section enabled ──▶ service + alias
   (classes PHP)      (config/bundles)   (framework.yaml)     (injectable)
 Les TROIS maillons doivent tenir ; un seul manquant = pas d'alias automatique.

Un autre besoin apparaît dans le journal de consultation : connaître le chemin courant, tout en réutilisant le service lors d'un import CLI. Cette classe complète interroge la pile au moment de la méthode :

use Symfony\Component\HttpFoundation\RequestStack;

final class CurrentPath
{
    public function __construct(private RequestStack $requests) {}

    public function read(): ?string
    {
        return $this->requests->getCurrentRequest()?->getPathInfo();
    }
}

Avec la Request /blog/42 au sommet de la pile, read() rend /blog/42. Avec une pile vide dans une commande ordinaire, il rend null ; l'opérateur ?-> évite l'appel d'une méthode sur null. L'injection de RequestStack ne crée pas de Request. Une commande qui pousse elle-même un contexte n'a plus une pile vide : c'est l'état de la pile, pas le nom « CLI », qui détermine le résultat.

Nous ne conservons pas la Request dans le constructeur d'un service partagé : le contexte actif peut changer. L'argument Request d'une action de controller relève, lui, des value resolvers de HttpKernel, pas de l'enregistrement d'un service ordinaire Request dans le container.

🌍 In Real Life

La situation : avoir livré un équipement au bâtiment ne suffit pas à le raccorder au poste ; le raccordement dépend du plan et des fonctions activées.

L’équivalent dans Symfony : équipement livré → package installé ; préparation du raccordement → intégration du bundle actif ; raccord annoncé → définition et alias ; fonction désactivée → câblage automatique de cette section absent.

Retour à la réalité technique : installer les classes de Twig ne suffit pas à publier son environnement configuré. L'intégration peut l'enregistrer ; une définition applicative peut aussi le faire. Désactiver Serializer n'interdit pas une déclaration distincte. RequestStack peut être injectée sans contenir de Request ; la Request d'action vient des resolvers, non d'un service ordinaire.

🧠 Comment le mémoriser : « Livré, intégré, configuré : vérifier les trois. » Image mentale : un appareil livré mais pas encore raccordé. Question-réflexe : manque-t-il la bibliothèque, l'intégration active ou le câblage demandé ?

⚠️ À ne pas confondre : disparition d'un alias automatique et impossibilité de fournir soi-même une implémentation.

Trouver le bon type : `debug:autowiring`

À retenir en priorité
  1. La command expose les types configurés.
  2. Elle évite de deviner une class concrète.

Où en est-on ? Étape 2 sur 2. Question : quel type exact écrire dans le constructeur ? On ne devine pas : on interroge le container avec deux commandes complémentaires.

Le diagnostic du blog doit dépendre d'un contrat de journalisation, pas d'une implémentation découverte par hasard. logger est un identifiant, la class concrète implémente le comportement, et Psr\Log\LoggerInterface est le type que le câblage proposé permet de demander. Cherchons ce contrat, puis la définition correspondante :

php bin/console debug:autowiring LoggerInterface
php bin/console debug:container logger

Résultat attendu avec le câblage standard : la première indique le contrat Psr\Log\LoggerInterface associé à logger ; la seconde décrit ce service. Ces commandes documentaires ne sont pas exécutées ici. Elles observent le container de l'environnement choisi : un bundle activé seulement en développement ne promet rien en production. Copier une classe interne vue dans debug:container ne garantit pas sa disponibilité comme type injectable. Demander le type annoncé et vérifier la configuration ; si plusieurs usages existent, choisir l'alias approprié. Une classe publique comme RequestStack peut être le bon contrat, sans inventer une interface.

Écriture Résultat
debug:autowiring les types utilisables comme type-hint
debug:autowiring log ceux qui contiennent « log » : Psr\Log\LoggerInterface - alias:logger
debug:autowiring zzzz « No autowirable classes or interfaces found », exit code 1
debug:autowiring RedirectController --all ajoute les services sans alias de type

Le filtre réduit la liste ; il n'installe rien. La ligne zzzz suppose qu'aucun type ne correspond à cette recherche. --all inclut les services sans alias ; il ne rend aucun service public. La liste ordinaire de debug:container inclut déjà les privés : l'option --show-private n'existe pas en Symfony 8.0.

Si l'on demande Symfony\Component\HttpKernel\Log\Logger sans définition ni alias de ce nom, l'autowiring peut échouer et suggérer Psr\Log\LoggerInterface. La class existe pourtant : c'est son enregistrement sous le type demandé qui manque. Une définition applicative adaptée changerait cette situation. À l'inverse, RequestStack, Filesystem et Twig\Environment sont des classes publiées comme types : « toujours injecter une interface » serait une fausse règle.

 identifiant      classe concrète                     type injectable
 ───────────      ──────────────────────────────      ─────────────────────
 logger     ──▶   HttpKernel\Log\Logger         ◀──   Psr\Log\LoggerInterface
 (debug:container)  (implémentation interne)         (alias → debug:autowiring)

🌍 In Real Life

La situation : le catalogue indique quel équipement on peut demander ; l'inventaire explique ce qui est enregistré. Lire l'un ou l'autre n'ajoute aucun équipement manquant.

L’équivalent dans Symfony : types proposés au consommateur → debug:autowiring ; définition enregistrée → debug:container ; recherche → filtre de consultation, pas installation.

Retour à la réalité technique : l'identifiant logger, sa classe concrète et le type publié sont trois informations distinctes. Le type adapté peut être une interface ou une classe comme RequestStack. --all élargit l'inspection sans rendre les services publics ; les résultats concernent l'environnement inspecté.

🧠 Comment le mémoriser : « Catalogue pour demander, inventaire pour comprendre. » Image mentale : deux listes consultées devant le même poste. Question-réflexe : ai-je trouvé un type injectable ou seulement un identifiant visible ?

⚠️ À ne pas confondre : inspection de configuration et modification du conteneur ; une commande de diagnostic ne crée pas l'alias absent.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'alias peut viser une class.
  2. Le contrat n'est pas nécessairement une interface PHP.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Chaque piège est suivi de pourquoi la mauvaise réponse paraît plausible.

  • Voir l’explication : Voir un identifiant ne suffit pas à choisir un type.

    Voir un identifiant ne suffit pas à choisir un type. logger peut être décrit par debug:container sans que sa class concrète soit publiée comme type autowirable. La liste ordinaire ne montre pas non plus tous les identifiants internes cachés : « tous » serait trop large. Plausible car ce qu'on voit dans l'inventaire semble demandable.

  • Voir l’explication : L'échec d'un type concret n'est pas une interdiction du langage.

    L'échec d'un type concret n'est pas une interdiction du langage. Pour notre diagnostic, le contrat publié est LoggerInterface. Un autre câblage pourrait exposer la class concrète, mais changerait la dépendance exprimée par le consommateur. Plausible car la classe existe bel et bien en PHP.

  • Voir l’explication : Une class peut être le bon contrat publié.

    Une class peut être le bon contrat publié. RequestStack fournit le contexte courant, éventuellement absent. Son injection n'autorise pas à supposer une Request non nulle, ni à confondre injection de service et argument d'action. Plausible car on retient « toujours injecter une interface ».

  • Voir l’explication : Bibliothèque, bundle actif et configuration sont trois vérifications.

    Bibliothèque, bundle actif et configuration sont trois vérifications. Retirer TwigBundle retire son intégration automatique, pas la possibilité de construire et déclarer un environnement Twig soi-même. Plausible car « installé » est confondu avec « configuré ».

  • Voir l’explication : Désactiver une section ne supprime pas toutes les définitions applicatives.

    Désactiver une section ne supprime pas toutes les définitions applicatives. Avec framework.serializer.enabled: false, ce câblage automatique de SerializerInterface disparaît. Il faut inspecter les éventuelles déclarations distinctes avant de conclure que le contrat est introuvable. Plausible car « désactivé » semble signifier « introuvable partout ».

Fiche express

À mémoriser

À retenir en priorité
  1. Installation et activation sont distinctes.
  2. La configuration décide des services enregistrés.

Avant d'ajouter un constructeur au blog :

  1. Nommer le rôle utile : générer un lien, rendre une page, journaliser.
  2. Vérifier package, bundle actif et section de configuration.
  3. Chercher le type publié avec debug:autowiring, puis la définition avec debug:container, dans le bon environment.
  4. Accepter une interface ou une class publique appropriée ; ne pas deviner un type d'après l'implémentation interne.
  5. Pour le contexte HTTP, demander RequestStack et traiter l'absence au moment de l'utilisation, notamment dans l'import CLI.
  6. Utiliser --all pour les services sans alias, sans le confondre avec une modification de visibilité.

Ces collaborateurs sont des objets. Le chapitre des paramètres traite maintenant l'autre moitié du constructeur : les valeurs de configuration.

🧠 À retenir pour la certification

  • Les services intégrés viennent des extensions de bundles activés (FrameworkBundle = socle ; Twig, Security… ont les leurs).
  • Trois vérifications distinctes : package installé, bundle actif, section/fonctionnalité activée.
  • debug:autowiring [recherche] → types injectables (--all ajoute les services sans alias de type, sans les rendre publics) ; aucun résultat → « No autowirable classes or interfaces found », exit code 1.
  • debug:container <id> décrit la définition ; --show-private n'existe pas en 8.0 (la liste inclut déjà les privés).
  • Identifiant (logger), classe concrète et type injectable (Psr\Log\LoggerInterface) sont trois choses ; le bon type peut être une classe (RequestStack, Filesystem).
  • framework.serializer.enabled: false retire le câblage automatique ; une déclaration applicative reste possible.
  • RequestStack s'injecte sans garantir une Request : getCurrentRequest() peut rendre null ; l'argument Request d'une action vient des value resolvers.

Phrase de mémorisation : « Livré, intégré, configuré : demande le type publié, pas l'identifiant ni la classe interne. »
