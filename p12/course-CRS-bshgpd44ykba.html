Objectif

Le blog possède déjà des classes avec leurs propres responsabilités. Nous voulons partager une petite opération d'horodatage, puis plusieurs formats de compte rendu d'import, sans imposer une nouvelle class parente à tous ces objets. Un trait réutilise des membres dans une class. Nous allons voir comment les importer, quelle implémentation est appelée et comment rendre explicite un conflit de noms.

Le fil du cours, en quatre questions :

  1. Qu'est-ce qu'un trait apporte à la class qui l'importe (et que n'apporte-t-il pas) ?
  2. Qui gagne quand la class, le trait et le parent définissent la même méthode ?
  3. Que faire quand deux traits définissent la même méthode ?
  4. Que peut-on tester sur un trait (instanceof, class_uses()) ?

L'essentiel

À comprendre

À retenir en priorité
  1. La class décide avant le trait.
  2. Le trait prend le dessus sur la class parente.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi les traits existent. PHP n'a que l'héritage simple : une class a un seul parent. Si deux classes sans lien (Article et un compte rendu d'import) veulent la même petite méthode, on ne veut ni dupliquer le code, ni inventer un parent commun artificiel. Le trait est un copier-coller contrôlé par le langage : on écrit le code une fois, chaque class qui l'importe le reçoit comme si elle l'avait écrit.
  • Ce que l'auteur veut que vous compreniez. Le trait est de la réutilisation de code, pas de la typologie. Il n'y a pas d'objet de trait, et la class ne devient pas un sous-type du trait.
  • Pourquoi c'est à la certification. Les questions portent sur trois mécaniques : l'ordre class > trait > parent, la résolution de conflit (insteadof / as) et les limites (statique, propriétés, instanceof, class_uses()).

Importer un trait avec use apporte ses membres à la class hôte. On ne construit pas un object de trait, et la class ne devient pas son sous-type. Ce mécanisme de réutilisation est distinct d'une interface qui promet une capacité et d'une base abstraite dont la class hérite.

Pour une méthode, le code propre à la class prime sur celui du trait, qui prime sur celui de la class parente. Ce n'est pas un ordre d'exécution de trois méthodes. Si deux traits apportent la même méthode sans arbitrage ni méthode locale qui tranche, la composition échoue. insteadof choisit une implémentation ; as ajoute un alias, un autre nom d'accès, ou adapte la visibilité.

Trois mécanismes proches à ne pas mélanger :

┌──────────────────┬──────────────────┬──────────────────┬──────────────────┐
│                  │ Trait            │ Interface        │ Classe parente   │
├──────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Mot-clé          │ use              │ implements       │ extends          │
│ Apporte du code  │ oui              │ non (contrat)    │ oui              │
│ Crée un type     │ non              │ oui              │ oui              │
│ instanceof       │ toujours false   │ true             │ true             │
│ Combien par hôte │ plusieurs        │ plusieurs        │ un seul          │
│ Instanciable     │ non (Error)      │ non              │ oui (si concrète)│
└──────────────────┴──────────────────┴──────────────────┴──────────────────┘

Pourquoi la confusion est plausible : les trois se déclarent en tête de class et les trois « donnent quelque chose » à la class. Seuls l'interface et le parent donnent un type ; seuls le trait et le parent donnent du code.

Le schéma

À retenir en priorité
  1. Un trait partage du code sans créer un type.
  2. La class host doit implémenter ses methods abstraites.

Où en est-on ? Avant le détail, une vue d'ensemble : le cas le plus difficile du cours (deux traits, même nom de méthode) montre d'un coup la composition à la déclaration et les appels à l'exécution.

Le compte rendu d'import doit rester exportable en CSV et en JSON. Deux traits proposent malheureusement le même nom export(). Nous choisissons CSV pour ce nom et conservons JSON sous exportJson(). Le diagramme sépare la composition des méthodes de leurs appels futurs.

Pointillés orange : composition à la déclaration ; flèches pleines : appels sur un objet, sans instance de trait. as expose un autre nom ; il ne suffit pas à résoudre le conflit sur export, d'où insteadof. L'exemple suppose que la classe ne redéfinit pas elle-même ces méthodes.

Lecture en deux temps : (1) à la déclaration de Reporter, PHP assemble les noms (qui s'appelle comment) ; (2) à l'exécution, l'appel $reporter->export() retrouve simplement une méthode de Reporter. Le trait n'intervient plus comme acteur.

Avant de détailler cet arbitrage, observons un trait sans collision : il permet de comprendre où se trouvent l'état et les obligations importées.

L'exemple

Exemple concret

À retenir en priorité
  1. Un trait peut imposer une method abstraite à la class hôte.
  2. La class Article fournit getId() tout en réutilisant touch() et l'état du trait.

Où en est-on ? Étape 1 : le cas le plus simple, un seul trait, aucune collision. On regarde ce qui est copié dans la class et ce qui reste à la charge de l'hôte.

Un article modifiable peut mémoriser le moment où l'application l'a touché. Cette petite class Article, dont l'identifiant de démonstration vaut 1, est isolée : elle ne remplace ni ArticleView ni le catalogue du parcours GET /blog/42. Le trait apporte l'horodatage et exige une méthode getId().

trait Timestampable
{
    private ?\DateTimeImmutable $updatedAt = null;

    public function touch(): void
    {
        $this->updatedAt = new \DateTimeImmutable();
    }

    abstract public function getId(): int;   // exigence sur la classe hôte
}

class Article
{
    use Timestampable;

    public function getId(): int { return 1; }
}

Ce que PHP voit : Article contient use Timestampable;. À la compilation, PHP copie dans Article la property $updatedAt, la méthode touch() et l'exigence abstraite getId(). Après cela, Article se comporte comme si ces membres étaient écrits dedans.

 trait Timestampable                       class Article
┌───────────────────────────┐             ┌───────────────────────────┐
│ $updatedAt (private)      │  ── use ──► │ $updatedAt  (copiée)      │
│ touch()                   │             │ touch()     (copiée)      │
│ abstract getId(): int     │             │ getId() { return 1; }  ◄─ │ écrit par
└───────────────────────────┘             └───────────────────────────┘ l'hôte
  aucune instance du trait                  $article = new Article()

Les déclarations seules n'affichent rien. Après $article = new Article(), $article->getId() retourne 1. Appeler $article->touch() affecte l'instant courant à sa property privée $updatedAt, initialement null, et ne retourne aucune valeur utile. Il n'y a pas d'instance séparée de Timestampable, et ce code ne persiste pas l'horodatage.

Pourquoi le trait exige-t-il getId() alors que touch() ne s'en sert pas ? Pour montrer qu'un trait peut demander une opération à son hôte (une méthode abstraite). L'exigence getId() montre qu'un trait peut demander une opération à son hôte, même si touch() ne l'utilise pas dans cet exemple minimal. Importer du code n'exonère donc pas la class de satisfaire les obligations qu'il apporte : si Article n'écrivait pas getId(), la composition échouerait.

🌍 In Real Life

La situation : deux ateliers recopient une procédure d'horodatage dans leur propre manuel. Chaque atelier l'applique à ses propres dossiers ; aucun troisième atelier n'exécute la procédure pour eux.

L’équivalent dans Symfony : procédure réutilisée → trait Timestampable ; manuel hôte → classe Article ; horodatage du dossier → état de l'instance qui appelle touch().

Retour à la réalité technique : le trait apporte des membres à la classe, sans instance séparée ni nouveau sous-type. La méthode abstraite getId() reste une obligation de l'hôte. Cet appel PHP ne persiste pas la date et ne déclenche aucun mécanisme Symfony à lui seul.

🧠 Comment le mémoriser : « Le code vient du trait, l'objet reste l'hôte. » Image mentale : la même page dans deux manuels distincts. Question-réflexe : où sont l'état et l'objet réellement utilisés ?

⚠️ À ne pas confondre : utiliser un trait et implémenter une interface utilisable comme contrat de type.

Ce qu'un trait apporte

Où en est-on ? Étape 2 : on a vu un trait simple ; on liste maintenant tout ce qu'il peut contenir et on précise les pièges d'état (statique, propriétés homonymes), avant de parler de priorité entre méthodes.

Nous pouvons apporter le même horodatage à un compte rendu sans déclarer que compte rendu et article sont de la même famille. C'est la réutilisation horizontale : partager du code entre classes qui n'ont pas de relation d'héritage (l'héritage, lui, est vertical : parent → fille).

Le trait peut fournir properties, méthodes concrètes ou statiques, méthodes abstraites et, depuis PHP 8.2, constantes. La class concrète doit satisfaire les obligations abstraites ; un trait peut notamment déclarer une méthode abstract private depuis PHP 8.0, contrairement à une class abstraite.

Membre du trait Disponible Remarque
Properties toujours copiées dans chaque hôte
Méthodes concrètes / statiques toujours exécutées dans l'objet hôte
Méthodes abstraites toujours l'hôte doit les implémenter ; abstract private depuis PHP 8.0
Constantes depuis PHP 8.2 une class ne peut pas redéfinir une constante du trait avec une valeur différente

Pourquoi abstract private est-il remarquable ? Dans une class abstraite classique, une méthode abstraite ne peut pas être private (la fille ne la verrait pas). Dans un trait, le code est copié dans l'hôte lui-même, donc la méthode privée est bien visible : PHP l'autorise depuis 8.0.

L'état n'est pas partagé « globalement »

Le code partagé ne signifie pas un état global partagé par tous les hôtes. Deux classes indépendantes important un trait de compteur ont chacune leur property statique : deux incréments dans l'une et un dans l'autre ne produisent pas automatiquement un total commun de trois.

trait Counter { public static int $count = 0; }
class A { use Counter; }
class B { use Counter; }
A::$count++; A::$count++; B::$count++;
// A::$count === 2, B::$count === 1
        trait Counter  (modèle, pas un compteur)
              │ copié          │ copié
              ▼                ▼
        ┌──────────┐     ┌──────────┐
        │ A::$count│     │ B::$count│      deux propriétés statiques
        │    = 2   │     │    = 1   │      indépendantes
        └──────────┘     └──────────┘

Depuis PHP 8.3, une fille qui réimporte le trait obtient également une property statique distincte de celle du parent. Sans ce use, il faut raisonner sur l'héritage ordinaire (la fille partage la statique du parent, comme pour toute propriété statique héritée).

class P { use Counter; }
class Q extends P { use Counter; }   ← réimport : Q::$count distincte (8.3+)
class R extends P { }                ← pas de use : R::$count = P::$count

Enfin, des properties de même nom doivent respecter leurs règles de compatibilité : une valeur initiale 0 dans le trait et 1 dans la class ne se départagent pas par la précédence des méthodes. Cette distinction évitera de généraliser la règle suivante à tous les membres. (Vérifié : PHP lève une erreur fatale « define the same property … the definition differs and is considered incompatible ».)

Détail complémentaire : depuis PHP 8.1, appeler une méthode statique ou accéder à une property statique directement sur le trait est déprécié ; on passe par une class qui l'utilise.

🌍 In Real Life

La situation : deux ateliers indépendants adoptent la même règle de comptage, mais conservent chacun leur tableau de chiffres.

L’équivalent dans Symfony : règle commune → trait ; tableau de chaque atelier → propriété statique de chacune des classes indépendantes qui l'importent.

Retour à la réalité technique : réutiliser la déclaration ne crée pas un compteur global au trait. Depuis PHP 8.3, réimporter le trait dans une fille sépare aussi cette propriété statique ; sans réimport, il faut appliquer l'héritage ordinaire. Les propriétés homonymes doivent respecter leurs règles de compatibilité.

🧠 Comment le mémoriser : « Même règle, tableaux distincts. » Image mentale : deux compteurs portant des valeurs différentes. Question-réflexe : quelles classes importent le trait, et la fille le réimporte-t-elle ?

⚠️ À ne pas confondre : état statique de classe et instances partagées du conteneur Symfony ; leurs règles sont indépendantes.

Repère de l’exemple : Un trait peut imposer une method abstraite à la class hôte. La class Article fournit getId() tout en réutilisant touch() et l'état du trait.

L'ordre de précédence

Où en est-on ? Étape 3 : une même méthode peut exister à trois endroits (class, trait, parent). Avant de gérer le cas de deux traits, on règle la question simple : lequel répond ?

Le rapport possède déjà un libellé hérité, puis reçoit un trait qui en propose un autre. Quelle version répond à label() ? Une méthode écrite dans la class prime ; sinon celle du trait prime sur celle du parent. La provenance applicative ou Symfony du trait ne change pas ces règles PHP.

Quelle méthode label() est appelée ?

  la class l'écrit elle-même ? ── oui ──► celle de la CLASS
            │ non
  un trait importé l'a ? ──────── oui ──► celle du TRAIT
            │ non
  la class parente l'a ? ──────── oui ──► celle du PARENT
class BaseReport
{
    public function label(): string { return 'parent'; }
}

trait SharedLabel
{
    public function label(): string { return 'trait'; }
}

final class LocalReport extends BaseReport
{
    use SharedLabel;
    public function label(): string { return 'class'; }
}

final class SharedReport extends BaseReport
{
    use SharedLabel;
}

final class InheritedReport extends BaseReport {}

echo new LocalReport()->label(), "\n";
echo new SharedReport()->label(), "\n";
echo new InheritedReport()->label(), "\n";

En PHP 8.4, la sortie est class, trait, puis parent. Chaque appel exécute une seule version ; PHP ne fusionne pas les résultats. La class peut ainsi adapter son libellé sans modifier le trait pour tous ses autres utilisateurs. Signatures, visibilité et contraintes final restent applicables : la précédence n'autorise pas une redéfinition autrement interdite.

Pourquoi le trait bat-il le parent ? Parce que le code du trait est copié dans la class : il devient une méthode propre de la class, et une méthode propre de la fille masque toujours celle du parent. La class bat le trait parce que, en cas de doublon, ce que la class écrit explicitement est retenu.

Cas Qui répond à label() Pourquoi
LocalReport la class (class) méthode écrite dans la class
SharedReport le trait (trait) copié dans la fille, masque le parent
InheritedReport le parent (parent) rien d'autre n'existe

🌍 In Real Life

La situation : pour une opération, le manuel local remplace la fiche commune importée, qui remplace elle-même la consigne héritée. On suit une seule consigne, pas les trois successivement.

L’équivalent dans Symfony : consigne locale → méthode de classe ; fiche importée → méthode du trait ; ancienne consigne → méthode du parent.

Retour à la réalité technique : pour ces méthodes, la priorité est classe, puis trait, puis parent. L'appel sélectionne un corps, sans concaténation automatique des résultats. Les signatures, visibilités et contraintes final restent applicables.

🧠 Comment le mémoriser : « Priorité choisit, elle n'enchaîne pas. » Image mentale : une fiche retenue, deux mises de côté. Question-réflexe : quelle définition porte finalement le nom appelé ?

⚠️ À ne pas confondre : précédence des méthodes et compatibilité des propriétés, qui ne se règle pas par cette priorité.

Le trait est un tampon de méthodes sur la page de la class : l'écriture propre de la class reste prioritaire, puis le tampon, puis le modèle hérité. Deux tampons concurrents exigent un choix explicite.

Résolution de conflit

À retenir en priorité
  1. insteadof écarte une implémentation.
  2. as conserve l'original et ajoute un alias ou modifie la visibilité.

Où en est-on ? Étape 4 : la précédence ne départage pas deux traits entre eux. C'est le cas du schéma d'ouverture ; ici on écrit le code et on comprend pourquoi chaque mot-clé est nécessaire.

Reprenons les deux exports du schéma. Les traits locaux suivants rendent le fragment de composition autonome ; leurs chaînes identifient le format choisi, sans constituer un véritable export des articles :

trait Csv
{
    public function export(): string { return 'csv'; }
}

trait Json
{
    public function export(): string { return 'json'; }
}

Pourquoi PHP ne choisit-il pas le premier trait ? Deviner serait dangereux : deux traits peuvent avoir deux sens très différents pour le même nom. PHP refuse donc de composer et lève une erreur fatale tant que vous n'avez pas tranché explicitement.

Après ces définitions, la class choisit l'opération à garder sous le nom commun, puis préserve l'autre sous un alias :

class Reporter
{
    use Csv, Json {
        Csv::export insteadof Json;   // on choisit
        Json::export as exportJson;   // on garde l'autre sous un alias
    }
}

Pour une instance de Reporter, export() retourne csv et exportJson() retourne json. insteadof écarte l'implémentation concurrente pour le nom commun ; as ne la renomme pas en supprimant son ancien nom. Écrire seulement l'alias laisserait donc le conflit sur export non résolu.

┌──────────────────────────────┬──────────────────────────────────────┐
│ insteadof                    │ as                                   │
├──────────────────────────────┼──────────────────────────────────────┤
│ CHOISIT qui garde le nom     │ AJOUTE un nom (alias)                │
│ écarte l'autre pour ce nom   │ l'ancien nom reste                   │
│ résout le conflit            │ ne résout pas le conflit seul        │
│ Csv::export insteadof Json   │ Json::export as exportJson           │
│                              │ hi as protected  (visibilité seule)  │
└──────────────────────────────┴──────────────────────────────────────┘

La visibilité de l'alias est un choix distinct : Csv::export as protected internalExport; ajoute un accès protégé, sans rendre export() protégé. Sans nouveau nom, hi as protected; adapterait la visibilité de la méthode importée hi elle-même. La variante indépendante suivante montre les deux accès et un appel interne. Ne la charge pas avec la précédente class Reporter :

trait TextFormat
{
    public function export(): string { return 'text'; }
}

trait JsonFormat
{
    public function export(): string { return '{"format":"json"}'; }
}

final class Reporter
{
    use TextFormat, JsonFormat {
        TextFormat::export insteadof JsonFormat;
        JsonFormat::export as exportJson;
        TextFormat::export as protected internalText;
    }

    public function preview(): string
    {
        return $this->internalText();
    }
}

$reporter = new Reporter();
echo $reporter->export(), "\n";
echo $reporter->exportJson(), "\n";
echo $reporter->preview(), "\n";

La sortie est text, {"format":"json"}, puis text. Le troisième résultat passe par l'alias protégé, accessible depuis la class. Ce sont des formats de démonstration : aucun article n'est chargé et aucune Response JSON n'est envoyée. Ni un alias de service ni l'ordre de chargement du container Symfony ne résoudrait à la place de PHP la collision entre méthodes de traits.

Avant / après, pour Reporter :

Avant (conflit)                Après (arbitré)
Csv::export  ┐                 export()      → Csv::export
Json::export ┴─ même nom       exportJson()  → Json::export
   ⇒ erreur fatale             internalText()→ TextFormat::export (protégé)

🌍 In Real Life

La situation : deux procédures s'appellent « exporter ». Le responsable choisit CSV sous ce nom et ajoute une entrée « exporter JSON » pour conserver l'autre possibilité.

L’équivalent dans Symfony : choix pour le nom commun → insteadof ; accès supplémentaire → as exportJson ; accès réservé à l'intérieur → alias protected.

Retour à la réalité technique : as n'efface pas le nom d'origine et ne résout donc pas seul la collision. Un alias nommé peut avoir une visibilité différente sans modifier celle de l'accès initial ; sans nouveau nom, as protected adapte la méthode importée elle-même. Tout s'exécute dans l'objet hôte.

🧠 Comment le mémoriser : « Choisir le nom commun, puis ajouter l'autre accès. » Image mentale : deux entrées distinctes dans un manuel. Question-réflexe : ai-je arbitré la collision, ou seulement ajouté un nom ?

⚠️ À ne pas confondre : alias de méthode PHP, alias de service Symfony et négociation d'une représentation HTTP.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Dernière étape avant l'entraînement : les erreurs qui reviennent en QCM, chacune avec la raison pour laquelle la mauvaise réponse semble plausible.

  • Voir l’explication : Le conflit n'est pas résolu automatiquement.

    Le conflit n'est pas résolu automatiquement. Sans insteadof, c'est une erreur fatale dans notre Reporter qui ne définit pas lui-même export(), pas un choix silencieux du premier trait. Une méthode locale aurait priorité, comme dans LocalReport : lis aussi la class hôte avant de conclure à un conflit. Pourquoi on se trompe : on transpose l'idée « le dernier gagne » des surcharges ou des tableaux PHP.

  • Voir l’explication : as n'écarte rien.

    as n'écarte rien. Il ajoute un nom ; l'original reste. Utiliser as seul face à un conflit ne le résout pas. Notre besoin comporte deux décisions : choisir le sens de export(), puis garder l'autre comportement sous exportJson(). Un alias ne remplace pas le premier choix. Pourquoi on se trompe : « alias » évoque « renommer », donc on croit que l'ancien nom disparaît.

  • Voir l’explication : Un trait n'est pas un type.

    Un trait n'est pas un type. $x instanceof Timestampable compile, mais rend false même si la class de $x utilise le trait. Pour notre Article, class_uses() peut retrouver le trait directement importé, mais cette function ne remonte pas automatiquement les imports du parent. Une fille sans use propre peut donc hériter des méthodes sans que class_uses() liste le trait du parent. Pour promettre une capacité à l'appelant, utilise une interface plutôt qu'un test sur le trait. Pourquoi on se trompe : le mot « use » ressemble à « implements » et le nom du trait ressemble à un nom de type.

  • Voir l’explication : Le statique n'est pas global.

    Le statique n'est pas global. Deux classes indépendantes = deux compteurs ; 3 est la mauvaise réponse tentante parce qu'on pense « une seule déclaration, donc une seule variable ».

  • Voir l’explication : Propriétés homonymes ≠ précédence.

    Propriétés homonymes ≠ précédence. 0 dans le trait et 1 dans la class : erreur fatale, pas « la class gagne ». On généralise à tort la règle des méthodes.

  • Voir l’explication : On n'instancie pas un trait.

    On n'instancie pas un trait. new Timestampable() lève une Error (« Cannot instantiate trait »), ce n'est ni null ni un objet vide.

Exposer un contrat malgré le choix interne de réutilisation

Interface publique et réutilisation interne

L'horodatage d'un article et celui d'un compte rendu peuvent réutiliser touch() sans parent commun. Si un service doit accepter n'importe quel object offrant cette opération, une interface décrit ce contrat ; la class peut l'implémenter tout en utilisant le trait pour son code. L'appelant ne dépend alors pas du choix interne de réutilisation.

interface Touchable { touch(): void }       ← ce que l'appelant voit (type)
         ▲                    ▲
 class Article           class ImportReport
   implements Touchable    implements Touchable
   use Timestampable       use Timestampable     ← comment elles le font (code)
Composition PHP contre négociation HTTP

Pour l'export d'import, les noms publics doivent exprimer clairement les formats disponibles. Choisir insteadof, garder un alias et fixer sa visibilité résout la composition PHP, pas la négociation HTTP. Le chemin GET /blog/42 continue d'utiliser son controller et son catalogue ; un trait n'ajoute aucune étape réseau ni aucun object intermédiaire à ce trajet.

Application

À retenir en priorité
  1. Un trait partage du code sans créer un type.
  2. La class host doit implémenter ses methods abstraites.
  3. La class décide avant le trait.
  4. Le trait prend le dessus sur la class parente.

Fiche express

À mémoriser

Pour composer les prochaines classes du blog, garde six repères :

  • Précédence des méthodes : class > trait > parent, pas une fusion ni une règle générale de résolution des properties.
  • Conflit non arbitré : erreur fatale.
  • insteadof écarte ; as ajoute un nom ou change une visibilité.
  • Method abstraite du trait : à implémenter par la class host.
  • Static de trait : copies distinctes dans deux classes indépendantes ; en PHP 8.3+, réimporter le trait dans la fille sépare aussi son état.
  • instanceof trait → false ; class_uses() voit les imports de la class, pas automatiquement ceux de ses parents ; typer par interface.

🧠 À retenir pour la certification : un trait copie du code dans l'hôte (pas de type, pas d'instance) ; la class gagne sur le trait, qui gagne sur le parent ; deux traits en collision exigent insteadof (choisir) et éventuellement as (ajouter un nom) ; l'état statique est par class.

Moyen mnémotechnique : « La class décide ; insteadof choisit ; as ajoute un accès. » Le code s'exécute dans l'object hôte, pas dans un object de trait.
