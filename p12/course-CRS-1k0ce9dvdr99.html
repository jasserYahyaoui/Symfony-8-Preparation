Objectif

GET /blog/42 produit déjà une réponse correcte. Si son contenu public reste identique, pourquoi refaire le routage, la lecture du catalogue et le rendu à chaque visite ? Le cache HTTP permet de réutiliser cette réponse selon une politique explicite, sans confondre fraîcheur et preuve que la représentation n'a pas changé.

Le cours suit un seul fil : une réponse déjà calculée peut-elle être resservie, et qui en décide ? Quatre étapes :

  1. Activer un reverse proxy devant l'application (http_cache).
  2. Déclarer la politique de réutilisation (#[Cache], Response).
  3. Comprendre ce que le proxy fait de chaque Request (schémas).
  4. Connaître ses limites : ce que le cache ne fera pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Le proxy raisonne sur le protocole HTTP.
  2. La politique vient des headers de Response.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le travail le plus coûteux d'une page publique (routage, base de données, Twig) est répété à l'identique. Mieux vaut le sauter quand la réponse n'a pas changé.
  • Le problème que Symfony résout. Fournir un proxy en PHP, activable en une ligne de configuration, et un attribute pour déclarer la politique en HTTP.
  • Ce que l'auteur veut que vous compreniez. L'application déclare, le cache décide. Le contrôleur n'« exécute » pas le cache : il pose des en-têtes (Cache-Control, ETag) que le proxy lit.
  • Pourquoi c'est à l'examen. Les questions portent sur : la clé de cache (l'URI), les méthodes cachables, max-age explicite vs #[Cache], la casse des options (camelCase / snake_case), la trace X-Symfony-Cache, l'invalidation hors HTTP.

🌍 In Real Life

La situation : au restaurant, l'accueil conserve une copie du menu public et la remet tant que sa consigne de validité l'autorise, sans retourner en cuisine.

L’équivalent dans Symfony : accueil intermédiaire → reverse proxy ; copie complète → réponse HTTP stockée ; service direct → hit réutilisable pour GET /blog/42.

Retour à la réalité technique : ce trajet suppose un cache déployé et une réponse admissible. Il peut éviter l'exécution de l'application en aval ; un cache de calcul interne, lui, ne remplace pas automatiquement la réponse HTTP.

🧠 Comment le mémoriser : « Une réponse prête avant la cuisine. » Image mentale : menu public au comptoir. Question-réflexe : réutilise-t-on une réponse ou seulement une valeur calculée ?

⚠️ À ne pas confondre : cache HTTP et cache applicatif.

Un reverse proxy reçoit les requêtes avant l'application et peut réutiliser une réponse stockée. Une réponse encore fraîche et réutilisable évite d'exécuter à nouveau le controller. Une réponse périmée peut être revalidée : l'application confirme alors si sa représentation a changé.

Symfony fournit un proxy PHP (HttpCache), une configuration d'activation et l'attribute #[Cache] pour déclarer une politique. L'attribute ne crée pas un cache à lui seul : il règle les en-têtes HTTP. X-Symfony-Cache, lorsqu'il est activé, permet de suivre les décisions du proxy. Les mécanismes d'inclusion externes ne sont pas enseignés ici.

Pour ce proxy, le cache ne vaut que pour les méthodes sûres ; la clé principale est l'URI, et Vary distingue les variantes.

L'expiration autorise la réutilisation pendant une durée de fraîcheur. La validation compare un validateur, par exemple un ETag identifiant une version de la représentation, pour confirmer une copie conservée. Ce n'est pas le cache applicatif : ce dernier réutilise une valeur pendant le travail de l'application, alors qu'un hit du proxy peut éviter ce travail.

Le schéma

À retenir en priorité
  1. Une Response fraîche évite le serveur d'origine.
  2. Une Response périmée peut être revalidée.

Où en est-on ? Étape 3 sur 4, mais on la place ici car elle donne la carte de tout le cours. Le proxy applique d'abord un tri (cette Request peut-elle être cherchée dans le cache ?) puis une recherche (a-t-on une entrée, est-elle fraîche ?). Deux schémas, dans cet ordre.

🌍 In Real Life

La situation : la durée affichée sur la copie du menu est dépassée. L'accueil demande si la version est toujours la bonne au lieu d'exiger aussitôt une nouvelle copie complète.

L’équivalent dans Symfony : durée admise → fraîcheur ; numéro ou date de version → validateur HTTP ; confirmation sans nouveau corps → réponse 304 de revalidation.

Retour à la réalité technique : expiration et validation sont deux mécanismes. Une réponse périmée n'est pas forcément différente ; la revalidation contacte l'origine, contrairement à un hit frais directement réutilisable.

🧠 Comment le mémoriser : « Périmé exige un contrôle, pas forcément un remplacement. » Image mentale : tampon de confirmation sur la copie. Question-réflexe : ai-je évité l'appel à l'origine ou seulement le transfert du corps ?

⚠️ À ne pas confondre : fraîcheur déclarée et preuve que les données métier n'ont jamais changé.

Avant de chercher l'article en cache, le proxy trie les requêtes. Une écriture ne devient pas cachable parce que son action ajoute max-age. La recherche de fraîcheur ne concerne que la branche admise :

Les losanges ambre sont des décisions, les rectangles bleus des traitements et les formes vertes des étapes d'entrée ou de sortie. pass signifie que le proxy délègue à l'application, pas que l'accès est autorisé par Security.

Où en est-on ? La Request a passé le tri : on est dans la branche « recherche dans le cache ». Le second schéma zoome sur cette case.

Cette seconde vue simplifie le parcours normal : elle suppose une variante compatible avec Vary et, pour une revalidation conditionnelle, un validateur tel qu'un ETag ou Last-Modified. Sans validateur utilisable, l'application doit fournir une nouvelle réponse. Les erreurs, verrous et politiques de réutilisation d'une réponse périmée ne sont pas représentés.

Exemple : /blog/42, identique pour tous, a max-age=60 et l'ETag "v1". Une seconde lecture pendant sa fraîcheur peut être servie sans controller. Après expiration, une revalidation qui obtient 304 confirme le corps déjà stocké ; ce 304 entre application et proxy ne signifie pas que le visiteur reçoit nécessairement une page vide.

Pourquoi la trace des lectures est-elle un diagnostic ?

Chaque flèche du schéma correspond à un mot de la trace : miss, store, fresh, valid, invalid, pass, invalidate. Lire X-Symfony-Cache, c'est relire le chemin dans le diagramme.

L'exemple : une page publique d'une heure

Exemple concret

À retenir en priorité
  1. max-age fixe une durée de fraîcheur.
  2. s-maxage cible les caches partagés.

Où en est-on ? On passe du schéma au code minimal : une ligne de configuration pour activer le proxy, une ligne d'attribute pour déclarer la politique. Rien d'autre à écrire.

Configuration à placer dans les packages de l'application utilisant l'intégration HTTP standard. Elle prépare le proxy en production ; elle ne recompile pas le conteneur à chaque lecture :

when@prod:
    framework:
        http_cache: true
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\Cache;

#[Cache(public: true, maxage: 3600, mustRevalidate: true)]
public function index(): Response
{
    return $this->render('blog/index.html.twig');
}

Le PHP est une méthode d'un contrôleur héritant d'AbstractController, avec route et template blog/index.html.twig déjà définis. Il illustre la liste publique voisine de la page article, pas une classe complète. La même politique ne convient à /blog/42 que si sa représentation est réellement partageable et si une heure d'ancienneté est acceptable. must-revalidate n'annule pas cette heure de fraîcheur : il impose la revalidation lorsque la réponse est périmée. smaxage permettrait une durée spécifique aux caches partagés, distincte de celle du navigateur.

Ce que Symfony fait de ces options :

Option de l'attribute Directive posée sur la Response
public: true public
maxage: 3600 max-age=3600
mustRevalidate: true must-revalidate
smaxage (non utilisé ici) s-maxage, pour les caches partagés

Le reverse proxy de Symfony

À retenir en priorité
  1. L'intégration utilise un proxy PHP.
  2. L'application continue d'exprimer sa politique en HTTP.

Où en est-on ? Étape 1 sur 4 : avant de déclarer quoi que ce soit, il faut qu'un proxy existe. Cette partie dit ce qu'active http_cache: true, ce que ce proxy n'est pas, et comment lire ses décisions.

  • framework.http_cache: true active l'intégration du proxy PHP dans l'application standard : le proxy enveloppe le kernel, stocke les Responses admissibles et les ressert. Sous when@prod, parce qu'un cache masquerait les changements pendant le développement.
  • Ce n'est pas Varnish : son coût et son déploiement sont ceux d'un proxy PHP. La politique de réponse reste exprimée en HTTP ; changer de proxy demande une configuration d'infrastructure et des mesures, pas de réinventer Cache-Control dans les contrôleurs.
  • En debug, le header X-Symfony-Cache trace chaque décision (miss, store puis fresh) ; hors debug, trace_level vaut none. short, conçu pour les journaux du serveur, ne trace que la main Request ; full, tout ; trace_header renomme le header.
  Navigateur ──▶ [ HttpCache (proxy PHP) ] ──▶ Kernel ──▶ Controller
                   │  stocke les Responses admissibles
                   └─ ressert sans réveiller le Kernel (hit fresh)

Pourquoi when@prod ?

En dev, vous modifiez un template et rechargez : un cache vous resservirait l'ancienne Response jusqu'à son échéance. On active donc le proxy là où l'on veut ses effets.

Comparaison : les trois valeurs de trace_level

trace_level Ce qui est tracé Usage
none rien (valeur hors debug) production silencieuse
short la main Request seulement journaux du serveur
full tout investigation

Sur une page publique admissible, une première lecture peut montrer miss, store, la suivante fresh. L'absence de trace en production ne prouve pas l'absence de cache. Ne pas activer le mode debug public pour ce seul diagnostic : utiliser la configuration de trace adaptée et les journaux du serveur. X-Debug-Token appartient au profiler, pas à la décision de réutilisation HTTP.

⚠️ À ne pas confondre : X-Symfony-Cache et X-Debug-Token. Plausible car les deux sont des headers X-… ajoutés en debug ; mais le premier trace le cache, le second désigne le profil du profiler.

Déclarer plutôt que construire

À retenir en priorité
  1. L'attribute fournit une politique par défaut.
  2. Le controller peut la préciser.
  3. Les validators sont définis avant isNotModified().
  4. Un 304 réutilise la représentation déjà stockée.

Où en est-on ? Étape 2 sur 4 : le proxy est là. Qui lui dit « cette page est partageable une heure » ? C'est l'application, par déclaration, non par code de cache écrit à la main.

La décision « ce contenu est partageable pendant tant de secondes » appartient à l'application. L'attribut exprime une politique réutilisable ; le listener la reporte sur la réponse au cours du traitement HTTP :

  • #[Cache] pose une politique par défaut ; les headers posés dans le controller l'emportent : #[Cache(maxage: 60)] et setMaxAge(10) donnent max-age=10.
  • L'attribute écrit ses options en camelCase (maxage, smaxage, mustRevalidate, lastModified, etag) ; $response->setCache([...]) les mêmes en snake_case (max_age, s_maxage, must_revalidate, last_modified, etag). Côté attribute, lastModified et etag sont des expressions évaluées, pas des valeurs directes.
  • $response->expire() marque la Response périmée ; $response->setNotModified() en fait un 304 sans contenu.

Pourquoi le max-age du controller l'emporte-t-il ?

Le listener CacheAttributeListener agit sur kernel.response, après le controller. À ce moment, la Response porte peut-être déjà un max-age. Le listener ne pose celui de l'attribute que s'il est absent.

 #[Cache(maxage: 60)] + $response->setMaxAge(10)  →  Cache-Control: max-age=10
 #[Cache(maxage: 60)] seul                        →  Cache-Control: max-age=60

La priorité du cas max-age vient précisément de CacheAttributeListener sur kernel.response : il ne pose cette directive que si elle n'a pas été explicitement définie. Ce n'est pas une règle générale de priorité entre tous les attributs et tous les listeners ; mustRevalidate: true, par exemple, ajoute sa directive.

Comparaison : camelCase (attribute) et snake_case (setCache())

Notion #[Cache(...)] $response->setCache([...])
durée navigateur maxage max_age
durée cache partagé smaxage s_maxage
revalidation forcée mustRevalidate must_revalidate
validateur (date) lastModified (expression) last_modified
validateur (étiquette) etag (expression) etag

La validation demande un autre geste : fixer les validateurs avant isNotModified($request). Ce fragment indépendant de contrôleur suppose un $request HttpFoundation et une représentation de démonstration publique et statique de l'article 42 :

$response = new \Symfony\Component\HttpFoundation\Response();
$response->setPublic();
$response->setMaxAge(60);
$response->setEtag('article-42-v1');
if ($response->isNotModified($request)) {
    return $response;
}
$response->setContent('Article 42, version publique 1');
return $response;

Sans condition correspondante, l'action retourne 200 avec ce texte. Avec If-None-Match: "article-42-v1", la réponse devient 304, sans corps, et le retour anticipé évite de produire le contenu. Si ETag et date sont configurés, la comparaison If-None-Match est prioritaire sur If-Modified-Since. Le client réutilise sa représentation conservée ; un proxy intermédiaire peut, lui, resservir le corps qu'il possède.

Pourquoi fixer l'ETag avant isNotModified() ?

isNotModified($request) compare les en-têtes conditionnels de la Request (If-None-Match, If-Modified-Since) aux validateurs déjà présents sur la Response. Sans ETag posé avant, il n'y a rien à comparer : la réponse reste un 200.

 Request : If-None-Match: "article-42-v1"
                  │ comparé à
 Response : ETag "article-42-v1"  ──▶ identiques ──▶ 304, sans corps

Dans une vraie page, le validateur doit refléter toute la représentation pertinente, y compris les variantes. Garder article-42-v1 après une modification de contenu ou de rendu ferait confirmer une ancienne copie. Un validateur calculé seulement après un rendu coûteux économise le transfert, mais pas le travail déjà effectué pour le calculer.

Après avoir défini l'ETag ou Last-Modified, le controller peut appeler $response->isNotModified($request). Si la condition de la Request est satisfaite, la Response devient 304 et son body est retiré ; retourner à ce moment évite de produire le contenu. Lorsque If-None-Match est présent, il prime sur If-Modified-Since dans la vérification conditionnelle. Un 304 n'est pas une nouvelle représentation vide à stocker comme contenu.

Ce que le cache ne fera pas

À retenir en priorité
  1. public autorise le partage.
  2. La personnalisation doit être prise en compte dans la politique.

Où en est-on ? Étape 4 sur 4 : le mécanisme fonctionne, il reste ses limites. Le cache ne devine ni les changements métier, ni qui est le lecteur, ni les écritures « cachables ». Connaître ces limites évite les fuites de pages personnelles.

🌍 In Real Life

La situation : l'accueil du restaurant peut distribuer le menu public, pas la note personnelle d'une table à tous les nouveaux clients.

L’équivalent dans Symfony : document commun → réponse partageable ; note individuelle → réponse personnalisée ; séparation des versions → politique et variantes de cache appropriées.

Retour à la réalité technique : public autorise un cache partagé à réutiliser une réponse selon les règles HTTP ; ce mot ne rend pas ses données publiques sans risque. private exclut le cache partagé, pas nécessairement celui du navigateur ; no-store a une autre portée.

🧠 Comment le mémoriser : « Vérifier le lecteur avant de partager. » Image mentale : menu commun à côté d'une note nominative. Question-réflexe : cette copie convient-elle vraiment au prochain lecteur de /blog/42 ?

⚠️ À ne pas confondre : private, no-cache et no-store.

  • La key de cache est l'URI, query string normalisée : ?b=2&a=1 et ?a=1&b=2 partagent leur entrée. Pour QUERY, le body entre aussi dans la key.
  • Une entrée public peut être réutilisée par un cache partagé : ne pas rendre publique une page personnalisée par utilisateur sans séparation adaptée. Sans déclaration publique explicite, les cookies de la Request ou Authorization entraînent la politique private de ce proxy ; cette réponse n'est pas stockée par ce cache partagé. Cela ne signifie pas qu'un cache privé de navigateur est interdit : private n'est pas no-store.
  • Safe methods seulement : jamais PUT ou DELETE ; ne jamais modifier l'état sur un GET ou un HEAD. En 8.0, Request::isMethodCacheable() retient aussi QUERY. Un POST passe à l'application ; si sa réponse est un succès ou une redirection et si l'invalidation réussit, la trace comporte pass, invalidate. Une réponse d'erreur ne déclenche pas cette invalidation, même avec max-age=60.
  • L'invalidation à la demande n'est pas dans la spécification HTTP : avec l'expiration seule, il faut attendre l'échéance.

Avant / après : la clé de cache

 /search?b=2&a=1   ──normalisation──▶  /search?a=1&b=2  ──▶ même entrée
 /search?a=1&b=2   ──────────────────▶  /search?a=1&b=2  ──▶ (fresh)
 route + paramètres : ne sont PAS la clé ; seule l'URI compte
 QUERY : URI + corps de la requête

Comparaison : private, no-cache, no-store

Directive Cache partagé Cache du navigateur Idée
public peut réutiliser peut réutiliser partageable
private exclu peut réutiliser réponse pour un seul lecteur
no-cache stocke mais revalide avant réutilisation idem « demande avant de servir »
no-store ne stocke pas ne stocke pas « ne garde rien »

Les lignes no-cache / no-store complètent le cours à titre de rappel ; elles ne sont pas un fait propre au proxy Symfony.

Ainsi, importer un nouveau titre par app:blog:import ne traverse pas ce proxy comme une requête HTTP mutante : le cache ne peut pas deviner que /blog/42 a changé. Il faut une stratégie cohérente d'expiration, de validation ou de purge propre à l'infrastructure. Invalider un tag dans un pool applicatif n'efface pas automatiquement une réponse HTTP.

Vary sélectionne des variantes par en-têtes de requête ; il n'invente ni partition par utilisateur ni autorisation. Sur un hit frais, le contrôleur et ses contrôles ne sont pas rejoués. Ne jamais rendre publique une page contenant des informations propres au lecteur pour gagner du temps.

Pourquoi un POST ne se cache-t-il pas, même avec max-age ?

Une écriture n'a pas de sens à resservir : elle doit atteindre l'application. Le proxy applique donc pass. Si la réponse est un succès ou une redirection, il invalide ensuite l'entrée de cette URI (RFC 9111 §4.4) : la trace montre pass, invalidate. Une erreur n'invalide pas.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. 304 signifie réutiliser la représentation conservée.
  2. Le body ne doit pas être renvoyé.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les quatre étapes sont vues. Voici les erreurs de QCM probables, avec la raison de leur plausibilité.

  • Voir l’explication : framework.http_cache: true suffit

    framework.http_cache: true suffit à activer le proxy ; aucune class à écrire. Pourquoi on se trompe : on pense qu'il faut un service ou un kernel personnalisé.

  • Voir l’explication : Le max-age explicite du controller l'emporte sur celui de #[Cache]

    Le max-age explicite du controller l'emporte sur celui de #[Cache] ; ne pas transformer ce cas en priorité universelle entre tous les mécanismes. Pourquoi on se trompe : « l'attribute est plus visible, donc prioritaire ».

  • Voir l’explication : La key de cache est l'URI

    La key de cache est l'URI, pas la route ni ses parameters — corps compris pour QUERY. Pourquoi on se trompe : on raisonne en « route + paramètres » côté Symfony, mais le proxy ne voit que l'URI HTTP.

  • Voir l’explication : Le proxy Symfony étudié ne stocke que les méthodes cachables qu'il admet

    Le proxy Symfony étudié ne stocke que les méthodes cachables qu'il admet ; ne pas généraliser cette restriction à tous les mécanismes définis par HTTP. Pourquoi on se trompe : on prend une limite d'implémentation pour une règle du protocole.

  • Voir l’explication : L'invalidation à la demande est hors spécification HTTP

    L'invalidation à la demande est hors spécification HTTP ; RFC 9111 §4.4 n'impose que celle qui suit une method non sûre réussie. Pourquoi on se trompe : on suppose qu'un « purge » est une méthode standard.

  • Voir l’explication : X-Symfony-Cache n'apparaît qu'en debug

    X-Symfony-Cache n'apparaît qu'en debug ou si trace_level le demande. Pourquoi on se trompe : on conclut « pas de header = pas de cache ».

À mémoriser

À retenir en priorité

Pour expliquer une seconde lecture de /blog/42, identifier la variante, sa fraîcheur, puis l'éventuelle validation. « Le contrôleur ne s'est pas exécuté » est un résultat normal d'un hit, pas une garantie que l'article est toujours à jour dans la source métier.

  • framework.http_cache: true : un reverse proxy en PHP, remplaçable.

  • Attribute en camelCase, setCache() en snake_case.
  • Key : l'URI, query normalisée ; body compris pour QUERY.
  • Méthodes cachables seulement ; Cookie ou Authorization rendent la réponse privée dans ce proxy sauf déclaration publique explicite.
  • Invalidation à la demande : hors HTTP.

🧠 À retenir pour la certification :

  • Activer : framework.http_cache: true (sous when@prod), pas de class à écrire.
  • L'application déclare (#[Cache], setCache()), le proxy décide.
  • Trace : miss, store → fresh ; valid / invalid après revalidation ; pass, invalidate pour un POST réussi.
  • Clé = URI normalisée (+ corps pour QUERY) ; Vary choisit la variante.
  • max-age posé dans le controller > maxage de l'attribute ; attribute camelCase, setCache() snake_case.
  • Cookie / Authorization sans public explicite → réponse private, non stockée par le proxy.
  • Aucune invalidation à la demande dans HTTP ; un tag de cache applicatif n'efface pas une réponse HTTP.

Moyen mnémotechnique : « Activer, déclarer, tracer ».

Phrase de mémorisation : « Le proxy garde la réponse sous son URI, l'application dit combien de temps elle reste fraîche, et pour savoir ce qui s'est passé on lit X-Symfony-Cache. »

Lorsque la réponse entière ne peut pas être partagée, le composant Cache peut encore mémoriser un calcul réutilisable sans contourner le traitement de la requête.
