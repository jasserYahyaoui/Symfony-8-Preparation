Objectif

Savoir ce que le component Form protège seul contre le CSRF, comment le régler, et ce qui change avec des tokens sans état. La vérification manuelle par isCsrfTokenValid() dans un controller appartient au Module 04 — Contrôleurs.

Question centrale : qu'est-ce qui empêche un autre site de soumettre à ma place le formulaire d'un utilisateur connecté, et que fait Symfony pour cela ?

L'essentiel

À comprendre

À retenir en priorité
  1. Sans état signifie sans stockage de token en session.
  2. Les contrôles de provenance restent nécessaires.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le navigateur joint automatiquement les cookies à toute requête vers un site. Un site pirate peut donc déclencher un POST vers votre application avec la session de la victime.
  • Le piège de fond. Le token CSRF prouve « cette soumission vient bien de mon formulaire ». Il ne prouve ni l'identité, ni le droit, ni la validité des données.
  • Ce que l'auteur veut que vous compreniez. Qui pose le champ (l'extension Form), sur quel form (la racine), comment il est contrôlé (avec ou sans état) et quelles options le règlent.
  • Pourquoi c'est à l'examen. Questions sur : un seul _token pour toute la vue, form soumis mais invalide, identifier par défaut, stateless sans preuve.

La protection CSRF empêche de confondre une soumission autorisée avec une requête provoquée par un autre site utilisant les cookies du navigateur. Elle ne remplace ni l'autorisation ni la validation des données métier. L'extension CSRF de Form ajoute un champ caché au formulaire racine ; form_end() rend ce champ s'il reste à rendre. À la soumission, le gestionnaire vérifie le token : un refus rend le formulaire soumis mais invalide.

Avec état, le token est vérifié à l'aide de la session. Sans état, le gestionnaire utilise les preuves d'origine et/ou de double envoi. Une preuve invalide provoque un refus ; une session déjà utilisée peut imposer de conserver la stratégie précédente. « Sans état » ne veut donc pas dire « sans contrôle ».

Le schéma

À retenir en priorité
  1. Le nom du field est distinct de l'identifier du token.
  2. csrf_token_id choisit le contexte du token.

Où en est-on ? Début du cours. Voici l'attaque que l'on veut empêcher, puis la réponse de Symfony. Question : pourquoi le pirate ne peut-il pas fabriquer le token ?

SANS protection                         AVEC token CSRF
---------------                         ---------------
site-pirate.test                        site-pirate.test
  └─ <form action=votre-site/supprimer>   └─ même formulaire caché
        │ le navigateur ajoute                  │ cookie de session ajouté
        │ le cookie de session                  │ MAIS pas de _token valide
        ▼                                       ▼
votre-site : « session OK » → exécute   votre-site : token absent → REFUS

Le pirate peut faire envoyer une requête (cookies inclus), mais il ne peut pas lire la page de votre site pour y copier le token : c'est ce secret-là qui distingue votre formulaire du sien.

Bleu : transport du token ; losange ambre : décision ; sorties arrondies : résultat du contrôle. Les flèches représentent des opérations, pas de l'héritage. Le détail du contrôle sans état est expliqué dans « Tokens avec ou sans état ».

L'exemple : le form `task`

Exemple concret

À retenir en priorité
  1. Le token ne détermine pas isSubmitted().
  2. L'erreur CSRF appartient au form racine.

Où en est-on ? On passe du principe à un cas concret : un form task avec un sous-form. Question : où est le token, et que devient la soumission quand il manque ?

L'inscription est une opération distincte de la lecture de /blog/42. Le formulaire protégé doit distinguer une soumission attendue d'une requête provoquée depuis un autre site avec les cookies du lecteur. L'exemple task illustre le transport classique avec état ; le cas sans état repose sur les preuves décrites plus bas, pas sur la seule présence du champ.

Un form task avec un field title et un sous-form address :

vue de task      : title, address, _token
vue de address   : city
soumis sans token
   → invalide, « The CSRF token is invalid. Please try to resubmit the form. »
soumis avec un token valide
   → contrôle CSRF satisfait ; autres contraintes toujours applicables
option CSRF du sous-form seul
   → aucun token enfant indépendant
racine désactivée + enfant activé
   → la racine reste non protégée
token avec état de task sur other, identifiants distincts
   → refusé

Ce que Symfony voit :

Situation Résultat Raison
Token absent soumis, invalide la racine reçoit l'erreur CSRF
Token valide contrôle CSRF OK les contraintes métier s'appliquent encore
Sous-form protégé seul pas de token propre seule la racine reçoit un champ
Racine désactivée racine non protégée l'enfant ne compense pas
Token de task présenté à other refusé identifiants distincts

Ce qui est automatique

Où en est-on ? Étape 1 sur 4. Ce que vous n'avez pas à écrire : l'extension pose le champ et branche le contrôle. Question « Pourquoi ? » : comment un simple createForm() devient-il protégé ?

Le contrôle est branché par l'extension Form, pas par HttpKernel seul. Il accompagne la soumission de la racine ; la vue ajoutée au GET ne constitue pas encore une validation. Après un refus, affiche aussi les erreurs racine pour que le lecteur comprenne pourquoi recommencer.

  • Dans le cas avec état, token absent ou altéré : le form est soumis (isSubmitted() vaut true) mais invalide ; l'erreur est portée par le form racine.
  • FormTypeCsrfExtension ajoute le field dans finishView(), sur le form racine seulement : un sous-form n'a pas de token propre.
  • form_end() rend le token parmi les champs restants. Avec render_rest: false, il faut l'avoir rendu explicitement, par exemple avec form_row(form._token) si le nom du champ n'a pas été personnalisé.

Mécanisme dans le code 8.0 (vérifié) :

  • FormTypeCsrfExtension étend FormType (getExtendedTypes() renvoie [FormType::class]) : tout type de form reçoit l'extension.
  • buildForm() : si csrf_protection est vrai, calcule l'identifier du token et ajoute un CsrfValidationListener qui contrôlera la soumission.
  • finishView() : ajoute un enfant HiddenType nommé csrf_field_name uniquement si !$view->parent (racine) et compound — d'où « un seul token ».
createForm(TaskType)
   │  buildForm   : ajoute le listener qui VÉRIFIE (à la soumission)
   │  createView  : finishView ajoute le champ _token (racine seulement)
   ▼
form_end() ─► rend _token parmi les champs restants
   ▼
POST ─► listener : token valide ? ─ non ─► erreur sur la racine (invalide)

🌍 In Real Life

La situation : un bureau joint un justificatif technique au dossier complet, pas à chaque page d'adresse. À son retour, le bureau vérifie ce justificatif ; le recevoir ne signifie pas que les informations du dossier sont correctes.

L’équivalent dans Symfony : l'extension CSRF configurée ajoute la vue du champ technique à la racine dans finishView() et branche le contrôle lors de la soumission. Le rendu doit transporter ce champ ; un refus ajoute une erreur à la racine.

Retour à la réalité technique : CSRF signifie falsification de requête intersite : on protège notamment contre une requête provoquée ailleurs avec les cookies automatiquement envoyés par le navigateur. Le contrôle n'est pas une preuve d'intention humaine, d'identité ou de droit métier. Dans le cas stateful, un token absent rend le formulaire soumis mais invalide ; les contrôles stateless ont les conditions décrites plus bas. Désactiver la racine n'est pas compensé par un enfant.

🧠 Comment le mémoriser : « Justificatif du dossier, pas certificat de vérité. » Image mentale : justificatif sur la couverture, pages métier encore à examiner. Question-réflexe : l'extension, le rendu et le contrôle de la racine sont-ils tous présents ?

⚠️ À ne pas confondre : protection CSRF, authentication, autorisation et validation des données ; afficher le token n'est pas le vérifier.

Les options du form

Où en est-on ? Étape 2 sur 4. On sait que le token existe ; comment le règle-t-on ? Question : quel rôle exact joue chacune des quatre options ?

Le nom _token est une clé de transport, tandis que csrf_token_id identifie le contexte de protection. Changer le message adapte le retour au lecteur ; désactiver la protection change le contrôle lui-même. Le simple fait qu'une route retourne du JSON ne justifie pas sa désactivation : il faut examiner comment le navigateur authentifie la requête.

Option Role Défaut
csrf_protection active ou désactive la protection pour ce form la configuration globale
csrf_field_name le nom du field caché _token
csrf_token_id la string qui génère le token voir ci-dessous
csrf_message le message d'erreur « The CSRF token is invalid… »

csrf_protection: false supprime le contrôle CSRF, pas les autres causes d'invalidité. csrf_message: 'Jeton refusé.' remplace le message. Globalement : framework.csrf_protection ; les options de form par défaut sous framework.form.csrf_protection (token_id, field_name).

Pour distinguer les quatre rôles :

Je veux changer… Option Ce qui bouge
le nom du champ HTML csrf_field_name le transport
le contexte du token csrf_token_id quel token est valable où
le texte de l'erreur csrf_message l'affichage seulement
l'existence du contrôle csrf_protection la protection elle-même

Vérifié dans configureOptions() : csrf_field_name vaut _token par défaut, csrf_message vaut « The CSRF token is invalid. Please try to resubmit the form. », et csrf_protection reprend le défaut de la configuration globale.

🌍 In Real Life

La situation : le bureau distingue l'étiquette de la pochette, la référence du contrôle, le message de refus et l'interrupteur qui active ce contrôle. Renommer la pochette n'améliore pas la preuve qu'elle contient.

L’équivalent dans Symfony : csrf_field_name nomme le champ transporté ; csrf_token_id désigne son contexte ; csrf_message règle le retour d'erreur ; csrf_protection active ou désactive le contrôle Form.

Retour à la réalité technique : l'identifiant n'est pas à lui seul un secret générateur de sécurité. Vérifie les options effectives et la configuration de l'extension. Désactiver CSRF ne rend pas les données valides ; retourner du JSON ne supprime pas le risque si le navigateur joint automatiquement les moyens d'authentification.

🧠 Comment le mémoriser : « Pochette, référence, message, interrupteur : quatre rôles. » Image mentale : justificatif rangé dans une pochette étiquetée sous un contrôle activé. Question-réflexe : suis-je en train de changer le transport, le contexte, le message ou la protection ?

⚠️ À ne pas confondre : nom du champ, identifiant CSRF, valeur du token et format de réponse.

Un identifier par form

À retenir en priorité
  1. Le token id définit le contexte de validation.
  2. Un identifier distinct évite une réutilisation entre contexts différents.

Où en est-on ? Étape 3 sur 4. Le token est lié à un contexte. Question « Pourquoi ? » : pourquoi ne pas utiliser le même identifier pour tous les forms ?

Séparer inscription et suppression de compte permet de ne pas réutiliser le même contexte stateful pour deux intentions différentes. Cet identifiant n'est ni un secret ni l'identifiant du compte, et un token valide ne prouve pas le droit de supprimer ce compte. Le contrôle d'autorisation reste indépendant du contrôle CSRF.

Sans csrf_token_id : le défaut configuré pour le type, sinon le nom du form, sinon la class du type. Avec des tokens à état, un token du form task est refusé par le form other, accepté si other reçoit csrf_token_id: 'task'. Un identifier distinct par form sensible empêche de rejouer un token volé ailleurs.

Ordre de résolution (code 8.0, buildForm()) :

1. option csrf_token_id du form           (si non vide)
2. défaut configuré pour ce type          (ex. 'submit' via Flex)
3. nom du form                            ($builder->getName())
4. classe du form type                    (dernier recours)

Pourquoi séparer ? Un token généré pour task est stocké sous l'identifier task. Présenté au form other, il est cherché sous other : introuvable, donc refusé. Un token volé sur un formulaire anodin ne sert pas sur un formulaire sensible.

🌍 In Real Life

La situation : le bureau classe séparément les justificatifs d'inscription et de suppression. Une pièce prévue pour l'inscription ne devient pas une pièce de suppression parce que son porteur est le même.

L’équivalent dans Symfony : des csrf_token_id distincts séparent les contextes des tokens stateful ; partager volontairement un identifiant partage ce contexte. Le défaut effectif peut venir de la configuration du type avant le nom du formulaire.

Retour à la réalité technique : cette séparation limite la réutilisation entre contextes distincts ; ce n'est pas un mécanisme général d'usage unique ni une garantie contre tout rejeu ou une faille XSS. Le token ne confère pas le droit de supprimer un compte. Inspecte la configuration réellement installée par la recette, car elle peut être modifiée.

🧠 Comment le mémoriser : « Même porteur, justificatifs de fonctions différentes. » Image mentale : tiroirs inscription et suppression séparés. Question-réflexe : quel identifiant effectif partage mon action avec les autres ?

⚠️ À ne pas confondre : contexte CSRF, identifiant du compte, autorisation et token à usage unique.

Dans le modèle de token avec état, le badge appartient à un contexte nommé par csrf_token_id. Le nom visible du field n'est pas ce contexte ; changer csrf_field_name ne crée pas une nouvelle identité de token.

Tokens avec ou sans état

Où en est-on ? Étape 4 sur 4, la plus subtile. Deux façons de contrôler : avec un registre en session, ou avec des preuves de provenance. Question : « sans état » veut-il dire « sans contrôle » ? Non.

Une page publique proposant l'inscription peut chercher à éviter un token stocké dans la session de chaque visiteur. Le gestionnaire sans état offre une autre preuve, pas l'absence de preuve. Pour analyser un refus, observe ensemble les headers d'origine, le double envoi configuré et l'éventuelle stratégie mémorisée : aucune ligne isolée ne résume la décision.

Avec état Sans état
stockage token conservé en session pas de token persistant côté serveur ; cela ne garantit pas à lui seul la mise en cache de la page
validation vérification à l'aide du token en session preuves d'origine et/ou de double envoi, sans refus explicite ni dégradation de stratégie
déclaration le défaut sans configuration framework.csrf_protection.stateless_token_ids
  • Pour la preuve d'origine, Sec-Fetch-Site, s'il existe, est prioritaire : seule la valeur same-origin convient. Sinon, le gestionnaire examine Origin et Referer.
  • Sans preuve d'origine, un double envoi valide peut suffire : la valeur est présentée dans la soumission et dans un cookie et/ou un header selon la configuration. Sans aucune preuve, le contrôle échoue. Une preuve explicitement invalide n'est pas compensée par l'autre.
  • Avec une session existante ayant mémorisé une stratégie, retirer une preuve précédemment utilisée peut faire échouer le contrôle. À l'examen, ne déduire ni acceptation ni refus de la seule absence de Origin.
  • Dans une application Flex, la configuration fournie déclare stateless_token_ids: ['submit', 'authenticate', 'logout'].
  • Hors form : {{ csrf_token('delete-item') }} dans le template.

Arbre de décision du gestionnaire sans état (SameOriginCsrfTokenManager, vérifié dans le code 8.0) :

isValidOrigin ?
   Sec-Fetch-Site présent ? ── oui ─► valide ssi == 'same-origin'
                            └─ non ─► Origin puis Referer : même origine ?
                                      (aucun header exploitable → null)
isValidDoubleSubmit ? (cookie / header vs valeur soumise → true/false/null)

origine = false                       → REFUS (preuve invalide explicite)
origine = null ET double envoi = null → REFUS (aucune preuve)
sinon                                 → accepté si une preuve valide,
                                        sous réserve de la stratégie mémorisée

Pourquoi Sec-Fetch-Site d'abord ? C'est un header que le navigateur impose : un site tiers ne peut pas le falsifier. Il est donc plus fiable qu'Origin ou Referer, qui ne sont qu'un repli.

Comparaison :

Cas du POST Accepté ? Pourquoi
Sec-Fetch-Site: same-origin oui preuve d'origine valide
Sec-Fetch-Site: cross-site non preuve explicitement invalide
aucun header, aucun double envoi non aucune preuve
aucun header d'origine, double envoi valide oui l'autre preuve suffit

🌍 In Real Life

La situation : un bureau peut comparer un justificatif à son registre, ou contrôler des preuves de provenance et leur concordance sans conserver ce justificatif. Dans le second cas, une preuve contradictoire ne disparaît pas parce qu'une autre paraît correcte.

L’équivalent dans Symfony : le gestionnaire stateful utilise la session ; le gestionnaire stateless configuré examine origine et/ou double envoi, ainsi que l'absence de dégradation d'une stratégie mémorisée dans une session existante.

Retour à la réalité technique : les headers et preuves ne forment pas un simple « l'un ou l'autre » inconditionnel. Respecte priorité de Sec-Fetch-Site, invalidité explicite, configuration du double envoi et stratégie antérieure. Absence de token persistant côté serveur ne signifie ni absence totale de session ni réponse publiquement cacheable. Hors Form, csrf_token() produit une valeur : il faut encore organiser son transport et sa vérification.

🧠 Comment le mémoriser : « Sans registre de tokens, pas sans dossier de preuves. » Image mentale : registre remplacé par provenance et pièces concordantes. Question-réflexe : ai-je examiné toutes les preuves et les exigences déjà mémorisées ?

⚠️ À ne pas confondre : stateless, protection désactivée, absence d'Origin et garantie de cache public.

Pièges d'examen

Piège à éviter

  • Voir l’explication : form_end() rend les champs restants.

    form_end() rend les champs restants. Désactiver render_rest ne supprime pas un token déjà rendu explicitement. Pourquoi on se trompe : on croit que render_rest: false « retire » le token, alors qu'il n'évite que le rendu automatique des champs non encore rendus.

  • Voir l’explication : Un form sans token valide est invalide

    Un form sans token valide est invalide ; c'est le component qui refuse. Pourquoi on se trompe : on imagine une exception ou un 403, alors que le form est simplement soumis et invalide.

  • Voir l’explication : Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form

    Sans csrf_token_id, l'identifier est le défaut du type, sinon le nom du form — et dans une application Flex, la configuration fournie donne submit à tous les form types autoconfigurés : un identifier commun. Pourquoi on se trompe : on pense à « un identifier par form » comme à un automatisme.

  • Voir l’explication : Sans état ne veut pas dire sans contrôle

    Sans état ne veut pas dire sans contrôle : preuves d'origine, double envoi et stratégie antérieure doivent être considérés ensemble. Pourquoi on se trompe : « sans état » sonne comme « sans vérification ».

  • Voir l’explication : Un sous-form n'a pas son propre token

    Un sous-form n'a pas son propre token : seul le form racine en reçoit un. Pourquoi on se trompe : on imagine un token par form de l'arbre.

Application

À retenir en priorité
  1. Le nom du field est distinct de l'identifier du token.
  2. csrf_token_id choisit le contexte du token.
  3. Le token id définit le contexte de validation.
  4. Un identifier distinct évite une réutilisation entre contexts différents.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Field caché _token, sur le form racine seulement, rendu par form_end().
  • Token absent ou faux : soumis, mais invalide.
  • Quatre options : csrf_protection, csrf_field_name, csrf_token_id, csrf_message.
  • Identifier par défaut : défaut du type, sinon nom du form ; submit avec Flex.
  • Avec état : session ; sans état : origine et/ou double envoi, sans preuve invalide ni dégradation d'une stratégie mémorisée.
  • Hors form : csrf_token('id') dans le template.

Moyen mnémotechnique : « Poser, rendre, vérifier ».

Phrase de mémorisation : « L'extension pose le token sur la racine, form_end() le rend, la soumission le vérifie — et un token valide ne prouve que la provenance, jamais le droit ni la validité des données. »
