Objectif

Savoir diagnostiquer un problème de routage avec les deux commands prévues pour cela : lire la liste des routes dans l'ordre où Symfony les essaie, en filtrer ou en détailler une, et demander directement quelle route répondrait à un path donné, avec sa method, son host et son schéma.

Question fil rouge : « /blog/new ne m'amène pas à l'action de création : comment voir, sans deviner, quelle route répond vraiment et pourquoi ? »

L'essentiel

À comprendre

À retenir en priorité
  1. Sans option, router:match conserve le contexte configuré : GET sur localhost seulement pour le contexte standard non personnalisé. Les options fournies remplacent les valeurs correspondantes.
  2. Aucune correspondance produit un exit code 1.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Quand une URL « ne marche pas », la cause est rarement dans le contrôleur : c'est souvent une autre route qui a répondu avant. Symfony fournit deux commandes pour le voir au lieu de le deviner.
  • Le piège de fond. Le routeur essaie les routes dans un ordre et la première qui correspond gagne. Lire ce qui est écrit dans les fichiers ne suffit pas : seule la collection chargée et triée compte.
  • Ce que l'auteur veut que vous compreniez. debug:router répond à « quelles routes, dans quel ordre ? » ; router:match répond à « pour ce chemin, dans ce contexte, laquelle ? ».
  • Pourquoi c'est à l'examen. Ordre ≠ alphabétique, priority, --method=ANY contre --method=GET, nom partiel, contexte standard GET/localhost, exit code 1.

Deux commands de FrameworkBundle diagnostiquent le routage : debug:router liste les routes dans l'ordre où Symfony les essaie, et router:match simule l'appariement d'un chemin dans un contexte, sans exécuter le contrôleur. La première route qui correspond gagne ; une route peut correspondre par son path et être écartée par sa method, son host ou son schéma.

Le schéma

À retenir en priorité
  1. La liste révèle les routes qui masquent les suivantes.
  2. Ce n'est pas un tri alphabétique.

Où en est-on ? Vue d'ensemble des deux outils : qui fournit quoi, et ce qu'on obtient au bout. Les sections suivantes reprennent chaque branche.

Cours « Router debugging »
   ├─ exemple                 → la collision /blog/{slug} contre /blog/new
   ├─ 1. debug:router         → la liste, dans l'ordre d'évaluation
   ├─ 2. options de debug:router → nom partiel, --method, --format, colonnes
   └─ 3. router:match         → simuler un path dans un contexte (+ exit code)

Bleu : entrées et outil ; ambre : décision ; sorties arrondies : diagnostic. Le code de sortie est celui de la commande, pas un statut HTTP.

L'exemple

Exemple concret

Où en est-on ? On pose le cas concret qui servira de fil rouge aux trois étapes : une collision de routes. Nous cherchons ici pourquoi la page de création n'atteint pas son action, avant de regarder le contrôleur.

Cette collection historique utilise un slug libre, contrairement au fil principal blog_show avec id=42. Elle permet justement de reproduire une capture trop large sans modifier le contrat de ce fil principal.

Nom Path Restrictions
blog_list /blog aucune
blog_show /blog/{slug} method GET
blog_new /blog/new methods GET et POST
api_post_edit /api/posts/{id} method PUT, host api.example.com, schéma https

/blog/{slug} est déclaré avant /blog/new : en GET, /blog/new est servi par blog_show, avec $slug = 'new'.

Mécanisme étape par étape pour GET /blog/new :

GET /blog/new
   │
   ├─ 1. blog_list    /blog          → "/blog/new" ≠ "/blog"        → écartée
   ├─ 2. blog_show    /blog/{slug}   → slug = "new", GET accepté    → GAGNE
   └─ 3. blog_new     /blog/new      → jamais essayée (déjà tranché)

Pourquoi {slug} accepte-t-il new ? Sans requirements, une variable de path accepte tout caractère sauf /. new en fait partie.

`debug:router` : la liste, dans l'ordre d'évaluation

Où en est-on ? Étape 1 sur 3 : voir ce que l'application a réellement chargé, dans quel ordre. Pourquoi commencer par là ? Parce qu'un bug de collision se lit dans l'ordre de la liste, pas dans le contrôleur.

Commence par vérifier ce que l'application a effectivement chargé, dans le même environnement que la panne. La déclaration écrite dans un fichier ne prouve pas sa présence ni sa position dans la collection finale. Voir blog_show avant blog_new explique la collision ; changer le contrôleur de création n'y remédierait pas.

La command « lists all your application routes in the same order in which Symfony evaluates them » — ni alphabétique ni par file. Sur l'exemple, blog_show est listée au-dessus de blog_new : le bug se lit dans la liste.

  • Le tri compare d'abord la priority décroissante (valeur par défaut : 0), puis conserve l'ordre de déclaration à priorité égale : « Routes with higher priority are sorted before routes with lower priority ». Une route déclarée en dernier avec priority: 2 est listée et évaluée avant les routes de priorité 0, mais après celles de priorité supérieure à 2.
  • ANY veut dire « aucune restriction » ; les colonnes Scheme et Host n'apparaissent que si une route en restreint un.

Avant / après, avec une priority :

AVANT (déclaration)                 APRÈS tri (ordre d'évaluation)
 1. blog_list   (priority 0)         1. blog_new    (priority 2)  ← remontée
 2. blog_show   (priority 0)         2. blog_list   (priority 0)
 3. blog_new    (priority 2)         3. blog_show   (priority 0)

Remarque : blog_new passe devant blog_show, donc /blog/new atteint enfin son action. À priorité égale, l'ordre de déclaration est conservé.

🌍 In Real Life

La situation : l'accueil suit une liste ordonnée de consignes. Pour comprendre pourquoi « nouveau dossier » est pris pour un nom de dossier, on consulte la liste effectivement distribuée, pas le brouillon rangé ailleurs.

L’équivalent dans Symfony : debug:router expose la collection chargée et son ordre : priorité décroissante, puis ordre conservé à égalité. Une route à slug libre placée avant /blog/new peut prendre cette demande si tous ses critères correspondent.

Retour à la réalité technique : il faut comparer le même environnement et la même configuration. Une priorité 2 précède 0, mais pas une priorité supérieure à 2. La liste montre les candidates ; elle ne prouve pas qu'une requête précise satisfait toutes leurs conditions.

🧠 Comment le mémoriser : « Lire les consignes distribuées, pas le brouillon. » Image mentale : plan d'accueil réellement utilisé, avec ses lignes numérotées. Question-réflexe : quelle collection et quel ordre l'application a-t-elle chargés ?

⚠️ À ne pas confondre : ordre des fichiers, ordre d'évaluation et correspondance effective.

Les options de `debug:router`

À retenir en priorité
  1. Le filtre conserve les routes compatibles.
  2. --method=ANY sélectionne seulement les routes sans restriction.

Où en est-on ? Étape 2 sur 3. On sait lire la liste ; comment la réduire ou zoomer sur une route ? Une fois la candidate identifiée, son détail expose les defaults, dont _controller, et les requirements qui décideront du matching.

Le filtre par méthode réduit la liste à examiner ; il ne simule ni les données d'une Request précise ni l'autorisation de l'utilisateur.

Écriture Effet
debug:router <nom> le détail d'une route : path, regex, host, schéma, methods, requirements, defaults, options
--show-controllers une colonne Controller
--show-aliases une colonne Aliases
--method=GET les routes GET… et celles sans restriction
--method=ANY seulement les routes sans restriction de method
--format=json txt (défaut), xml, json, md ; sinon « Unsupported format "…" »
--raw sortie brute

L'argument peut être un nom partiel, casse ignorée (la commande utilise stripos sur le nom de la route) : un seul résultat affiche son détail ; plusieurs, un choix (ou la liste en non interactif) ; aucun, « The route "…" does not exist. » et l'exit code 1.

Pourquoi --method=GET garde-t-il les routes sans restriction ? Une route sans methods accepte tout verbe, donc aussi GET : elle est candidate. Le filtre retire seulement les routes qui déclarent des methods sans GET. Pour --method=ANY, rien ne déclare « ANY » dans une liste de methods : seules restent les routes dont la liste est vide.

Routes : A (GET)   B (POST)   C (GET, POST)   D (aucune restriction)

--method=GET   → A, C, D            (B retirée)
--method=POST  → B, C, D            (A retirée)
--method=ANY   → D                  (aucune des autres ne contient "ANY")

🌍 In Real Life

La situation : l'archiviste filtre les fiches par type de demande, puis ouvre une fiche pour consulter ses conditions. Choisir les fiches compatibles avec « consultation » inclut aussi celles qui acceptent toute demande.

L’équivalent dans Symfony : --method=GET garde les routes GET et sans restriction ; --method=ANY ne garde que les secondes. Le détail par nom expose defaults et requirements ; les options de colonnes et format changent la présentation.

Retour à la réalité technique : le nom partiel peut donner plusieurs candidates et demander un choix, ou produire une liste en mode non interactif. Filtrer la collection n'exécute ni matching complet ni contrôleur, et n'accorde aucun droit.

🧠 Comment le mémoriser : « Filtrer les fiches n'est pas traiter une visite. » Image mentale : fiches sélectionnées sur une table, visiteur encore absent. Question-réflexe : ai-je sélectionné des déclarations ou testé une entrée concrète ?

⚠️ À ne pas confondre : filtre d'affichage, nom partiel et paramètres de matching.

`router:match` : quelle route répondrait

Où en est-on ? Étape 3 sur 3. La liste dit ce qui est possible ; il reste à dire ce qui arrive pour un chemin donné. D'où router:match, qui rejoue l'appariement.

Rejoue ensuite les dimensions pertinentes de l'entrée réelle. Pour la route API du tableau, un GET sur localhost n'est pas le PUT HTTPS reçu par api.example.com. Un succès console prouve cette sélection dans le contexte fourni, pas que l'ArgumentResolver, l'action ou le rendu réussiront.

  • L'argument est un path (path_info), pas une URL : method, host et schéma passent par --method, --host, --scheme.
  • Sans option, la commande garde le contexte du routeur : GET sur localhost dans le contexte standard. Une configuration telle que framework.router.default_uri peut changer l'hôte et le schéma.
  • RouterMatchCommand s'appuie sur TraceableUrlMatcher et ses trois niveaux de trace :
Situation Affichage
correspond presque « Route "…" almost matches but … », avec la raison
correspond « [OK] Route "…" matches », puis le détail ; exit code 0
aucune route « [ERROR] None of the routes match the path "…" » ; exit code 1
-v en plus, chaque route qui ne correspond pas, avec la raison

router:match /blog/new répond blog_show : déclarer blog_new avant, ou lui donner une priority plus haute.

Les trois niveaux de trace de TraceableUrlMatcher (ROUTE_DOES_NOT_MATCH, ROUTE_ALMOST_MATCHES, ROUTE_MATCHES) :

Pour chaque route, dans l'ordre :
   le path ne correspond pas ───────────────→ DOES_NOT_MATCH (visible avec -v)
   le path correspond MAIS method, host,
   schéma ou condition écarte la route ─────→ ALMOST_MATCHES (« almost… »)
   tout correspond ─────────────────────────→ MATCHES (« [OK] … matches »)

Exemple sur la route API avec le contexte standard (GET, localhost, sans --scheme) :

$ router:match /api/posts/1
 Route "api_post_edit" almost matches but host "localhost" does not match …
 [ERROR] None of the routes match the path "/api/posts/1"        → exit code 1

$ router:match /api/posts/1 --method=PUT --host=api.example.com --scheme=https
 [OK] Route "api_post_edit" matches                              → exit code 0

🌍 In Real Life

La situation : pendant une répétition, on donne à l'accueil une adresse et un type de visite pour voir quelle consigne il choisirait. Personne n'a encore exécuté le service prévu derrière cette porte.

L’équivalent dans Symfony : router:match transmet un path et un contexte à TraceableUrlMatcher ; ses traces expliquent les rejets ou la route sélectionnée. --method, --host et --scheme reproduisent les dimensions pertinentes.

Retour à la réalité technique : le contexte standard n'est pas forcément celui de production ; la configuration peut aussi le modifier. Ce diagnostic ne parcourt pas le traitement HttpKernel complet, les résolutions et l'action. Le code de sortie console 0 ou 1 n'est pas un statut HTTP.

🧠 Comment le mémoriser : « Répéter l'orientation n'exécute pas le service. » Image mentale : répétition à l'accueil, portes des services encore fermées. Question-réflexe : ai-je reproduit le contexte réel, et quelle partie du parcours ai-je réellement testée ?

⚠️ À ne pas confondre : diagnostic de matching et test fonctionnel de réponse.

router:match est un simulateur d'itinéraire : il explique aussi les routes presque compatibles. Lui donner le bon path mais oublier host ou method revient à simuler le trajet depuis le mauvais contexte.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM probables, chacune avec la raison pour laquelle la mauvaise réponse paraît crédible.

  • Voir l’explication : L'ordre de debug:router n'est pas alphabétique.

    L'ordre de debug:router n'est pas alphabétique. C'est l'ordre dans lequel Symfony évalue les routes, et donc l'explication de « pourquoi est-ce l'autre route qui répond ? ». Un énoncé qui parle de tri par nom ou par path se trompe. Pourquoi on se trompe : beaucoup d'outils de liste trient par nom.

  • Voir l’explication : Une route paramétrée déclarée plus haut intercepte un path fixe.

    Une route paramétrée déclarée plus haut intercepte un path fixe. Avec /blog/{slug} avant /blog/new, le path /blog/new en GET est servi par la route de l'article : la première correspondance gagne, même si une route plus précise existe plus bas. Pourquoi on se trompe : on suppose que Symfony préfère la route « la plus précise », comme certains autres routeurs.

  • Voir l’explication : La priority change l'ordre affiché.

    La priority change l'ordre affiché. Une route déclarée en dernier mais avec priority: 2 est listée et évaluée avant les routes de priority 0 ; debug:router montre cet ordre réel, pas l'ordre des files. Pourquoi on se trompe : on lit la liste comme l'ordre des fichiers.

  • Voir l’explication : --method=POST n'affiche pas que les routes POST.

    --method=POST n'affiche pas que les routes POST. Les routes sans restriction de method acceptent tout verbe et restent dans la liste filtrée ; --method=ANY, à l'inverse, n'affiche que celles-là. Pourquoi on se trompe : « filtrer sur POST » suggère un filtre strict ; et « ANY » suggère « toutes », alors que c'est « sans restriction » seulement.

  • Voir l’explication : router:match prend un path, pas une URL.

    router:match prend un path, pas une URL. Host, schéma et method passent par --host, --scheme et --method. Pourquoi on se trompe : le mot « match » fait penser qu'on colle l'URL complète.

  • Voir l’explication : Avec le contexte standard, router:match teste un GET sur localhost.

    Avec le contexte standard, router:match teste un GET sur localhost. Une route restreinte à un host ou à une autre method y apparaît au mieux en « almost matches », et la command finit en erreur. Pourquoi on se trompe : on croit que le path suffit à valider la route.

  • Voir l’explication : Aucune correspondance, c'est l'exit code 1.

    Aucune correspondance, c'est l'exit code 1. Ni 0 avec une table vide, ni un code calqué sur HTTP : un script peut s'appuyer dessus. Pourquoi on se trompe : on confond code de sortie console et statut 404.

  • Voir l’explication : Un nom partiel suffit à debug:router, et la casse est ignorée.

    Un nom partiel suffit à debug:router, et la casse est ignorée. Avec plusieurs résultats, la command demande de choisir, ou liste les routes en mode non interactif. Pourquoi on se trompe : on pense qu'il faut le nom exact de la route.

Application

À retenir en priorité
  1. Sans option, router:match conserve le contexte configuré : GET sur localhost seulement pour le contexte standard non personnalisé. Les options fournies remplacent les valeurs correspondantes.
  2. Aucune correspondance produit un exit code 1.
  3. Le filtre conserve les routes compatibles.
  4. --method=ANY sélectionne seulement les routes sans restriction.

🌍 In Real Life

La situation : l'accueil connaît le guichet des dossiers numérotés, mais l'archiviste ne trouve aucun dossier 999. Le plan est correct ; c'est la ressource demandée qui manque.

L’équivalent dans Symfony : une route compatible avec /blog/999 peut être trouvée, puis ArticleCatalog ne rien retourner et l'action produire une erreur 404. Le succès de router:match ne démontre pas l'existence de l'article.

Retour à la réalité technique : distinguer échec de sélection de route et absence métier guide le diagnostic. Le matching ne charge pas automatiquement une entité ; un éventuel resolver d'entité exige son intégration configurée.

🧠 Comment le mémoriser : « Guichet trouvé, dossier pas garanti. » Image mentale : bon guichet devant un emplacement 999 vide. Question-réflexe : la 404 vient-elle du routage ou de la recherche de ressource ?

⚠️ À ne pas confondre : route trouvée, argument résolu et ressource existante.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • debug:router : les routes dans l'ordre d'évaluation.
  • Ordre : priority décroissante (défaut 0), puis déclaration à égalité ; la première qui correspond gagne.
  • --method=X garde aussi les routes ANY ; --method=ANY ne garde qu'elles.
  • Nom partiel, casse ignorée.
  • router:match : un path ; contexte standard GET sur localhost, modifiable par la configuration et les options.
  • « almost matches » + raison ; aucune route : exit code 1.

Moyen mnémotechnique : « debug LISTE, match TESTE ».

Phrase de mémorisation : « Symfony essaie les routes dans l'ordre de la liste (priority d'abord) et la première qui correspond gagne : debug:router me montre la liste, router:match me dit pour quel path, dans quel contexte, laquelle répond. »

ROUTES ESSAYÉES DANS L'ORDRE (priority décroissante, puis déclaration)
  → PREMIÈRE CORRESPONDANCE GAGNE
  debug:router  → montre cet ordre (filtres : --method, détail : <nom partiel>)
  router:match  → rejoue un path dans un contexte (--method --host --scheme)
                  → almost matches + raison · OK + détail · sinon exit 1
