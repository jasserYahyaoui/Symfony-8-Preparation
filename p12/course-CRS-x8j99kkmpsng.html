Objectif

Les commandes ont confirmé la route et le câblage de /blog/42. Nous voulons maintenant relier les mesures d'une même requête : quel statut, combien d'accès au catalogue, quelles données de diagnostic ? Le profiler conserve cette observation pour la relire après le traitement, y compris pour la variante JSON qui n'affiche aucune barre.

L'essentiel

À comprendre

À retenir en priorité
  1. La collecte précède le stockage.
  2. La barre est une vue du profil.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une fois la requête terminée, ses mesures disparaissent avec le processus. Le profiler enregistre ce qui s'est passé pour qu'on puisse le relire plus tard, sans refaire la requête.
  • Le piège de fond. Trois fonctions différentes se cachent derrière « le profiler » : relever, conserver, afficher. La barre est seulement l'affichage ; elle peut manquer alors que le profil existe.
  • Ce que l'auteur veut que vous compreniez. Un collector copie des mesures dans un enregistrement sérialisable ; la relecture lit cette copie, jamais le service vivant.
  • Pourquoi c'est à l'examen. Questions sur quand la barre est injectée, collect() contre lateCollect(), nom par défaut (getName()), attribut id du tag, purge 1/10, et interdiction en production.

Trois pièces : les data collectors ramassent l'information, le profiler la stocke sous un token, la debug toolbar en affiche un résumé. La barre n'est qu'une vue : elle manque souvent (JSON, redirect), un profil peut exister même sans barre, si la collecte est active. Le tout s'installe en dependency de développement, jamais en production.

Le token est un identifiant de profil, pas un droit d'accès. Les données peuvent révéler la configuration et des informations de requête : ne pas confondre cet outil de développement avec une fonctionnalité publique du blog ou une solution de supervision de production.

Le schéma

À retenir en priorité
  1. La présentation et la collecte sont distinctes.
  2. Examiner les headers de diagnostic lorsqu'ils sont présents.

Où en est-on ? Module 15, cours 2 sur 2. Le cours précédent a livré une version ; celui-ci présente l'outil qui sert à observer une requête en développement et qu'il ne faut pas livrer. Fil : schéma du collector → exemple de code → trois pièces → barre → collectors → bout en bout.

Le compteur appartient à l'application ; le collector copie ses mesures dans un enregistrement. L'affichage ultérieur ne doit pas recommencer les appels au catalogue pour « retrouver » leurs résultats :

Bleu : mesure/appels ; vert : snapshots. Vue d'une requête principale collectée avec terminaison normale. Une fermeture brutale, une collecte désactivée ou une erreur de stockage peut empêcher la relecture. Le token identifie le profil ; la toolbar est une vue distincte, pas le mécanisme de collecte.

L'exemple : un collector de hits

Exemple concret

À retenir en priorité
  1. Le profil est sérialisé.
  2. Conserver des données plutôt que des ressources actives.

Où en est-on ? On connaît le chemin ; voici le code minimal qui le parcourt. Deux classes : un compteur (l'appareil vivant) et un collector (qui copie ses valeurs). Question guide : que copie-t-on, et quand ?

Le compteur suivant peut être appelé par une instrumentation de ArticleCatalog à chaque recherche. Pour le diagnostic de 42 comme de 999, on compte une recherche, pas une preuve d'existence de l'article. Placer chaque classe dans son fichier sous src/Profiler/ et les enregistrer comme services de développement/test ; les imports sont explicites :

<?php
namespace App\Profiler;

use Symfony\Bundle\FrameworkBundle\DataCollector\AbstractDataCollector;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\DataCollector\LateDataCollectorInterface;
use Symfony\Contracts\Service\ResetInterface;

final class HitCounter implements ResetInterface
{
    private int $hits = 0;

    public function hit(): void { ++$this->hits; }
    public function count(): int { return $this->hits; }
    public function reset(): void { $this->hits = 0; }
}

final class HitCollector extends AbstractDataCollector implements LateDataCollectorInterface
{
    public function __construct(private HitCounter $counter) {}

    public function collect(Request $request, Response $response, ?\Throwable $exception = null): void
    {
        $this->data['hits'] = $this->counter->count();      // ramasse, ne mesure pas
        $this->data['status'] = $response->getStatusCode();
    }

    public function lateCollect(): void
    {
        $this->data['late_hits'] = $this->counter->count(); // après la Response
    }

    public function getHits(): int { return $this->data['hits']; }
    public function getLateHits(): int { return $this->data['late_hits']; }
    public function getStatus(): int { return $this->data['status']; }
}

Si l'instrumentation appelle hit() une fois avant kernel.response, le profil enregistre hits = 1. Un second appel avant la sauvegarde tardive donne late_hits = 2. Sans ce second appel, les deux valeurs restent 1. Le clone du collector garde une référence au même compteur vivant jusqu'à la sauvegarde ; ses getters relisent ensuite les valeurs enregistrées. Le reset du collector vide ses données, celui du compteur remet la mesure à zéro : nettoyer l'un ne nettoie pas automatiquement l'autre.

Déroulé chiffré :

hit()                       → compteur = 1
kernel.response  collect()  → data['hits'] = 1, data['status'] = 200
hit()                       → compteur = 2   (avant la sauvegarde)
kernel.terminate lateCollect() → data['late_hits'] = 2
relecture : getHits() = 1, getLateHits() = 2   (valeurs enregistrées)

Trois pièces, trois roles

À retenir en priorité
  1. Le diagnostic est sensible.
  2. Ne pas confondre outil de développement et fonctionnalité publique.

Où en est-on ? Étape 1 sur 4 : avant les détails, séparer les rôles. Question guide : quelle fonction manque quand « le profiler ne marche pas » : relever, conserver ou montrer ?

🌍 In Real Life

La situation : au restaurant, des observateurs remplissent des relevés, les archives les conservent sous un numéro et un panneau affiche un résumé.

L’équivalent dans Symfony : relevés spécialisés → collectors ; archivage numéroté → profiler et token ; panneau → debug toolbar.

Retour à la réalité technique : pour /blog/42, collecte, conservation et affichage sont distincts et configurables. Une réponse JSON peut avoir un profil sans recevoir une barre HTML ; l'absence de panneau n'établit pas l'absence d'archive.

⚠️ À ne pas confondre : token de profil et preuve d'authentification.

La documentation propose le pack de développement symfony/profiler-pack. Dans ce parcours, les composants restent sur Symfony 8.0 et Twig au plus 3.22 ; vérifier les contraintes du projet plutôt que traiter le nom du pack comme un verrou de version. Aucune installation n'est effectuée ici.

Ne jamais activer le profiler en production. Une dépendance optionnelle vers Symfony\Component\HttpKernel\Profiler\Profiler peut être nullable, par exemple ?Profiler, lorsque le service n'est pas enregistré. La nullabilité ne désactive pas un service présent : ce sont les bundles et la configuration d'environnement qui déterminent sa disponibilité.

La barre n'apparaît pas toujours

À retenir en priorité
  1. Le lien peut exister sur une Response non HTML.
  2. Son absence ne se traite pas comme une erreur fonctionnelle.

Où en est-on ? Étape 2 sur 4 : la troisième pièce, la barre. Question guide : pourquoi une requête profilée peut-elle ne montrer aucune barre ? Parce que la barre est un morceau de HTML injecté, donc soumis à des conditions sur la Response.

Le tableau suppose une collecte active, un token, le listener et les routes du profiler disponibles, la toolbar activée et aucune interception de redirection. Il décrit une requête principale, pas une pièce jointe :

Response Barre injectée X-Debug-Token-Link
HTML avec </body> oui présent
JSON, redirect 302, HTML demandé en XHR non présent
HTML sans tag </body> non présent

X-Debug-Token porte le token, X-Debug-Token-Link l'URL du profil, et /_profiler permet de rechercher les profils conservés. Le listener construit le lien depuis le token avant de décider s'il peut injecter la barre. Sans route de génération disponible, le lien peut manquer ; sans stockage réussi, un token ne garantit pas la relecture.

L'option d'interception des redirects peut transformer une redirection HTML en page de diagnostic 200 et retirer Location : ne pas la confondre avec le suivi normal d'un 302. Une page non-HTML, une requête XHR, un format non-HTML ou une réponse en pièce jointe ne suit pas le cas simple d'injection.

Arbre de décision de la barre :

Response d'une requête principale profilée
   ├─ lien de profil : X-Debug-Token-Link (si route + token disponibles)
   └─ barre injectée ?
        ├─ HTML + </body>, pas XHR, pas redirect → OUI
        └─ JSON / redirect / XHR / sans </body>   → NON (profil conservé)

Dans FileProfilerStorage 8.0, l'ajout à l'index d'un nouveau profil a une probabilité de 1/10 de déclencher la purge des profils de plus de 2 * 86400 secondes. Réécrire un profil déjà indexé ne refait pas ce tirage. Ce n'est ni un minuteur de deux jours ni une purge exactement à chaque dixième requête : un ancien profil peut rester plus longtemps.

Les collectors

À retenir en priorité
  1. La collecte tardive observe la fin du cycle.
  2. Les deux étapes ne sont pas interchangeables.

Où en est-on ? Étape 3 sur 4 : comment un service devient un collector. Question guide : qui l'enregistre, qui l'appelle, et que devient la donnée qu'il range ?

  • Un service qui implémente DataCollectorInterface — collect(), reset(), getName() — ou étend AbstractDataCollector, qui fournit $this->data.
  • collect() est appelée pour la requête profilée, sur kernel.response : elle relève ce qu'un service a mesuré. Dans le cycle normal, ProfilerListener::onKernelTerminate() appelle ensuite saveProfile(), qui exécute lateCollect() sur les collectors concernés avant l'écriture.
  • Les données sont sérialisées : une connexion, une closure ne passent pas.
  • php bin/console debug:container --tag=data_collector permet d'attendre une liste des services tagués, dont le collector s'il a été enregistré. Cette commande de diagnostic n'est pas exécutée ici.

L'autowiring fournit HitCounter au constructeur. L'autoconfiguration, si activée pour un service enregistré, ajoute le tag data_collector reconnu grâce à l'interface. FrameworkExtension déclare cette règle ; ProfilerPass assemble les services tagués lors de la compilation. Aucun de ces préparatifs n'est relancé pour chaque lecture de /blog/42.

La collecte peut être filtrée, désactivée ou limitée aux requêtes principales. Si les sous-requêtes sont aussi collectées, elles peuvent avoir leurs propres profils attachés au parent. « Une collecte » décrit donc une requête profilée, pas nécessairement tout le trafic d'une page. La terminaison doit être appelée : la collecte tardive n'est pas déclenchée simplement en ouvrant l'interface web.

Comparaison des deux moments de collecte :

collect() lateCollect()
Quand kernel.response à saveProfile(), normalement après kernel.terminate
Interface DataCollectorInterface LateDataCollectorInterface
Appelée sur chaque requête profilée le clone rangé dans le profil
Usage relever ce que le service a mesuré compléter après la Response

Un collector de bout en bout

À retenir en priorité
  1. Les données doivent survivre au stockage.
  2. Une function active n'est pas une donnée de profil.

Où en est-on ? Étape 4 sur 4 : on relit le profil enregistré. Question guide : sous quel nom retrouve-t-on le collector, et que contient-il vraiment ?

🌍 In Real Life

La situation : l'observateur copie le compteur de recherches du blog sur une feuille datée. Lire cette archive demain doit relire le nombre copié, pas le compteur actuel.

L’équivalent dans Symfony : copie de mesures → données collectées ; feuille préparée pour archivage → clone dans le Profile ; dernière mise à jour → lateCollect() avant sauvegarde.

Retour à la réalité technique : les données conservées doivent être sérialisables. Les getters de relecture utilisent ces données, pas un service vivant. La collecte tardive du cycle normal de terminaison n'est pas une tâche de fond durable.

🧠 Comment le mémoriser : « Archiver la mesure, pas l'appareil. » Image mentale : nombre écrit face à un compteur encore mobile. Question-réflexe : mon getter relit-il l'enregistrement ou interroge-t-il à nouveau le service ?

⚠️ À ne pas confondre : clone pour collecte et objet applicatif recréé à la relecture.

La donnée stockée doit survivre à la fin de la requête. Dans l'exemple, les entiers hits, late_hits et status le peuvent ; le compteur vivant n'est pas ce que les getters de relecture doivent utiliser :

Étape Résultat
getName() non redéfini le FQCN de la class ; getTemplate() rend null
Profiler::collect() appelle collect(), range un clone dans le profil
saveProfile() lateCollect() sur ce clone, puis serialization
loadProfile($token)->getCollector($nom) une copie désérialisée ; nom inconnu : InvalidArgumentException
une Closure dans $this->data saveProfile() lève « Serialization of 'Closure' is not allowed »
reset() vide $this->data

Pour une configuration manuelle explicite, garder l'id du tag cohérent avec getName(), notamment pour associer un template. Le nom stocké provient réellement de getName(), pas du tag : changer seulement son id ne renomme pas le collector dans le profil. Le pass accepte aussi des cas sans id explicite, notamment le repli sur la classe pour le template ; ce n'est pas un attribut universellement nécessaire à la collecte seule.

Dans cet exemple sans redéfinition, utiliser getCollector(\App\Profiler\HitCollector::class), pas 'app.hit'. En test, appeler enableProfiler() avant la requête, puis vérifier que getProfile() retourne un Profile avant de lire son collector. HitCounter est un service applicatif à fournir ; le collector n'incrémente pas lui-même le compteur.

Après vérification d'un Profile chargé et du collector présent, getCollector(\App\Profiler\HitCollector::class)->getStatus() rend le statut enregistré, par exemple 200 pour l'article 42 ou 404 pour 999. Pour choisir volontairement 'app.hit', redéfinir getName(): string pour renvoyer cette valeur et l'utiliser aussi à la relecture. getTemplate() étant null par défaut, enregistrer des données ne crée pas automatiquement un nouveau panneau graphique.

La sérialisation héritée de DataCollector conserve $this->data, pas les dépendances injectées. Après désérialisation, ne pas rappeler collect() ou lateCollect() pour consulter le profil : les getters doivent lire les données sauvegardées. Une closure dans ce tableau échoue lors de sa sérialisation par le stockage fichier, même si l'affectation dans collect() avait réussi.

Avant / après la sérialisation :

Pendant la requête            Après relecture (loadProfile)
─────────────────────────     ─────────────────────────────
HitCollector                  HitCollector désérialisé
 ├─ $counter (service vivant)  ├─ $counter : ABSENT
 └─ $data['hits'] = 1          └─ $data['hits'] = 1  ← les getters lisent ça
Clé d'accès : getName() = \App\Profiler\HitCollector (FQCN par défaut)

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le nom sert de key.
  2. Le tag et la récupération doivent rester cohérents.
  • Voir l’explication : La barre n'est injectée que dans du HTML qui a un </body>

    La barre n'est injectée que dans du HTML qui a un </body>, hors redirect et hors XHR ; si le profil est collecté et le listener installé, X-Debug-Token-Link permet l'accès sans barre. Plausible car « pas de barre » ressemble à « pas de profil » ; or la barre n'est qu'une vue.

  • Voir l’explication : collect() relève une requête profilée sur kernel.response

    collect() relève une requête profilée sur kernel.response ; lateCollect() intervient lors de la sauvegarde, normalement à la terminaison. Plausible car les deux méthodes ramassent des données et on les croit simultanées.

  • Voir l’explication : La purge fichier n'a pas d'échéance exacte

    La purge fichier n'a pas d'échéance exacte : seuil de deux jours, tirage 1/10 à l'indexation d'un nouveau profil, pas à chaque réécriture. Plausible car « 2 jours » évoque un minuteur et « 1/10 » une purge régulière.

  • Voir l’explication : getName() est la key d'accès

    getName() est la key d'accès — par défaut le FQCN, avec AbstractDataCollector. Plausible car le tag porte un id et le service un nom : on cherche une clé de type 'app.hit', qui n'existe que si getName() la renvoie.

  • Voir l’explication : Le token n'est pas un droit d'accès.

    Le token n'est pas un droit d'accès. Plausible car il ressemble à un jeton de session ; il identifie seulement un profil de développement.

Fiche express

À mémoriser

À retenir en priorité
  1. Un service peut être réutilisé.
  2. Le reset évite de mélanger plusieurs Requests.

Nous pouvons maintenant relire les mesures de l'article sans réexécuter le catalogue. Distinguer une barre absente, une collecte absente et un profil devenu introuvable évite trois diagnostics différents réduits à tort à « le profiler ne marche pas ».

🧠 À retenir pour la certification :

  • Collectors ramassent, profiler stocke (token), barre affiche.
  • Dépendance de développement, jamais en production ; ?Profiler si optionnel.
  • Barre : HTML avec </body>, hors redirect et XHR ; sinon X-Debug-Token-Link ou /_profiler.
  • collect() sur kernel.response ; lateCollect() à saveProfile(), normalement après kernel.terminate.
  • Données sérialisées (pas de Closure) ; purge des profils de plus de 2 jours, tirage 1/10 à la nouvelle indexation.
  • Nom par défaut : le FQCN ; tag data_collector avec id = getName().

Si tu dois retenir seulement 6 choses :

  • Collectors ramassent, profiler stocke, barre affiche.
  • --dev, jamais en production ; ?Profiler dans un controller.
  • Barre : HTML avec </body>, hors redirect et XHR ; sinon X-Debug-Token-Link ou /_profiler.
  • collect() sur kernel.response pour chaque requête profilée ; lateCollect() à la sauvegarde, normalement kernel.terminate.
  • Données sérialisées ; purge fichier des profils de plus de 2 jours, tirage 1/10 à la nouvelle indexation.
  • Nom par défaut : le FQCN ; tag data_collector avec id.

Moyen mnémotechnique : « Ramasser, stocker, montrer ».

Phrase de mémorisation : « Le collector copie la mesure sur kernel.response, le profiler la complète et la sérialise à la terminaison sous un token, et la barre n'est qu'une vue qui peut manquer. »

Le profiler dans les tests exploite cette même observation par assertions. Avant une publication, les pratiques de déploiement vérifient notamment que ces outils de développement ne sont pas exposés.
