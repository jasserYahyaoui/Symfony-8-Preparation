Objectif

Pour traiter GET /blog/42, notre application doit représenter ce qu'elle reçoit et ce qu'elle rend. Lire directement les variables globales puis afficher du HTML fonctionnerait dans un script simple, mais compliquerait l'inspection du résultat et l'isolation des tests.

HttpFoundation fournit les objets Request et Response qui rendent ces entrées et sorties explicites. Nous allons situer cette couche sous l'orchestration de HttpKernel, puis résoudre une seconde difficulté : comment un même service retrouve-t-il la Request courante si le contexte change ? RequestStack répond à cette question, sans créer de Request pour la commande d'import lorsqu'elle n'en a pas.

Les sacs de paramètres, InputBag et les headers sont détaillés dans le Module 02 — Fondamentaux HTTP ; l'emploi de ces objets dans une action l'est dans le Module 04 — Contrôleurs. Ici, nous suivons leur rôle architectural et leur durée de vie. Le trajet complet d'une requête dans le kernel est décrit dans Request handling ; les événements qui le jalonnent, dans Event dispatcher et kernel events.

L'essentiel

À comprendre

À retenir en priorité
  1. HttpFoundation fonctionne sans le framework.
  2. Le kernel dépend de son vocabulaire Request et Response.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le PHP « brut » lit des superglobales et écrit des octets au moment où on l'appelle : entrées et sorties sont un état global et un effet. HttpFoundation les transforme en valeurs (objets) que l'on peut passer, inspecter et tester.
  • Le piège de fond. Une valeur n'est pas une action : construire une Response ne l'envoie pas ; créer une Request ne contacte aucun serveur.
  • Ce que l'auteur veut que vous compreniez. La pile RequestStack : un service partagé vit longtemps, la Request courante change ; il faut donc garder la pile et la consulter au moment utile.
  • Pourquoi c'est à l'examen. Les questions précisent quel élément rend chaque accessor (dernier, premier, avant-dernier), null sur pile vide, et qui appelle push()/pop().

Une Request peut être construite à partir de l'environnement reçu ou fabriquée localement pour un test. Une Response conserve son contenu, son statut et ses headers avant l'émission. Nous pouvons donc examiner le résultat de BlogController::show sans confondre « objet retourné » et « octets envoyés ». HttpFoundation ne choisit toutefois ni la route blog_show, ni le controller, ni l'article dans ArticleCatalog.

Le component est autonome : on peut utiliser ses objets sans démarrer le framework complet, avec ses dépendances et un PHP compatible. HttpKernel emploie ces objets pour organiser un traitement. Il utilise aussi une pile, RequestStack, où la dernière Request empilée représente le contexte courant. Cette pile suit des traitements imbriqués ; ce n'est pas l'historique des visiteurs du blog.

Un service réutilisé consulte cette pile au moment où il a besoin du contexte, plutôt que de conserver la Request rencontrée à sa construction. Cela permet de distinguer trois situations : affichage principal, traitement imbriqué et absence de contexte HTTP.

PHP BRUT                          HTTPFOUNDATION
 $_GET, $_POST, $_SERVER   ──►     Request  (valeur, inspectable)
 header() + echo           ──►     Response (valeur, envoyée plus tard)
 état global, effet direct         objets explicites, testables
 « quelle requête est       ──►    RequestStack (pile des traitements actifs)
   en cours ? » : ???

Le schéma

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.

Où en est-on ? On a vu quoi représente chaque objet ; il reste où vit la Request courante. Pourquoi un schéma ? Parce que la pile change pendant le traitement : seule une suite d'états montre pourquoi « parent » n'est pas « main ».

Pendant l'affichage ordinaire de l'article 42, la pile peut ne contenir que la Request principale, notée main. Supposons maintenant qu'un rendu déclenche explicitement un traitement interne A, puis que A déclenche B. Une sub-Request est ici cette Request traitée de manière imbriquée par le kernel ; ce n'est ni un appel réseau HttpClient ni un passage obligatoire de chaque page.

Les rectangles bleus représentent les états successifs, les capsules vertes les lectures possibles pendant B. getCurrentRequest() donne B ; getParentRequest() donne A ; getMainRequest() donne main, restée au bas de la pile. Quand B se termine, le dépilage restaure A comme courante.

HttpKernel encadre ce traitement avec une restauration dans finally, y compris lorsqu'une exception sort du traitement. Il ne faut pas attribuer le pop() à l'événement kernel.finish_request lui-même. Dans l'application, les services lisent la pile ; ils ne doublent pas les push()/pop() du kernel. Après la sortie du traitement principal, une pile vide rend null pour les trois lectures de Request. Voyons pourquoi cette distinction change un service apparemment aussi simple qu'un lecteur de locale.

L'exemple : un service qui lit la Request

Exemple concret

Où en est-on ? Du schéma au code. Pourquoi une locale ? Parce que c'est l'exemple le plus simple d'une valeur qui dépend du contexte courant : elle change d'une Request à l'autre alors que le service, lui, est partagé.

Le rendu de l'article utilise une locale, le code de langue et éventuellement de région du contexte courant. LocaleReader lit cette valeur déjà portée par la Request ; il ne traduit pas l'article et ne négocie pas Accept-Language. Avec HttpFoundation 8.0, PHP 8.4 et l'autoloader du projet chargé :

use Symfony\Component\HttpFoundation\RequestStack;

final class LocaleReader
{
    public function __construct(private RequestStack $requestStack) {}

    public function locale(): ?string
    {
        return $this->requestStack->getCurrentRequest()?->getLocale();
    }
}

Le constructeur garde la pile, pas son élément courant. L'opérateur ?-> interrompt l'accès lorsque getCurrentRequest() rend null : le contrat ?string permet de signaler l'absence de contexte au code appelant.

Pour observer les trois états sans démarrer de serveur, exécutons la suite dans un laboratoire qui instancie lui-même le service :

use Symfony\Component\HttpFoundation\Request;

$stack = new RequestStack();
$reader = new LocaleReader($stack);
var_export($reader->locale());
echo "\n";

$request = Request::create('/blog/42');
$request->setLocale('fr');
$stack->push($request);
try {
    var_export($reader->locale());
    echo "\n";
} finally {
    $stack->pop();
}

var_export($reader->locale());
echo "\n";

Résultat attendu : NULL, puis 'fr', puis NULL. Le même objet lecteur suit le contexte sans être reconstruit. Nous avons fixé fr explicitement ; Request::create() n'a ni exécuté le Routing ni choisi une langue à partir d'un header. Les mutations manuelles de pile servent exclusivement à cette simulation ; HttpKernel les prend en charge dans le trajet applicatif normal.

La commande d'import peut recevoir un service sans Request courante. Elle doit alors choisir une locale explicite ou une politique de repli adaptée, pas supposer que le lecteur retrouve la dernière page visitée.

Avant / après, pour fixer l'idée :

MAUVAIS : capturer la Request à la construction
  __construct(Request $r)  → le service garde la Request d'un instant T
  puis la Request change (sous-requête…) → le service lit une valeur périmée

BON : garder la pile et consulter au moment utile
  __construct(RequestStack $s)  → locale() relit getCurrentRequest()
  la pile suit le contexte, le service n'a pas à être reconstruit

🌍 In Real Life

La situation : le serveur consulte le bon actuellement posé sur le dessus du porte-bons. Photographier ce bon à sa prise de poste lui ferait ensuite lire une ancienne demande.

L’équivalent dans Symfony : porte-bons conservé → RequestStack injectée ; consultation au moment utile → getCurrentRequest() dans locale() ; photographie ancienne → Request mémorisée au constructor.

Retour à la réalité technique : le service partagé peut survivre au changement de contexte. Il conserve la pile, pas la Request courante ; une pile vide donne null. Lire la locale ne négocie pas la langue, et l'injection de la pile ne crée aucune Request.

🧠 Comment le mémoriser : « Consulte le support, pas la photo du premier bon. » Image mentale : un porte-bons dont le dessus change. Question-réflexe : est-ce le contexte actuel ou celui capturé à la construction ?

⚠️ À ne pas confondre : pile des traitements actifs et historique des visiteurs ; une commande sans contexte HTTP ne retrouve pas la dernière visite.

Ce qu'il remplace

À retenir en priorité
  1. Request représente les entrées HTTP.
  2. Response regroupe statut, headers et body.

Où en est-on ? On revient à la première question : pourquoi des objets plutôt que le PHP brut ? Pourquoi après la pile ? Parce que maintenant on sait que ces objets circulent entre services : on comprend mieux ce que le PHP brut ne permettait pas.

Sans cette couche objet, un script peut lire $_GET, $_POST ou $_SERVER, puis appeler header() et echo. Les entrées sont alors un état global et la sortie un effet immédiat, extérieur à la valeur retournée par la fonction. Modifier des superglobales dans un test est techniquement possible ; il faut cependant isoler et restaurer cet état partagé. L'avantage des objets n'est pas une impossibilité de tester PHP, mais des entrées et sorties plus explicites.

Request::create('/blog') fabrique ainsi une Request locale sans serveur. Request::createFromGlobals() lit l'environnement PHP disponible pour construire un objet. Ni l'une ni l'autre ne décide que l'article 42 existe : cette décision appartient toujours à la logique appelée par le controller. De même, construire une Response n'envoie pas encore son contenu.

PHP brut HttpFoundation
Entrée $_GET, $_POST, $_SERVER (global) objet Request
Sortie header() + echo (effet immédiat) objet Response (valeur)
Test état global à isoler et restaurer Request::create() local
Qui décide de l'existence de l'article ? votre code votre code (inchangé)

Ce petit laboratoire indépendant reprend un message d'accueil, sans déclarer de nouvelle route dans le blog. L'autoloader HttpFoundation doit être chargé :

use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

$request = Request::create('/bonjour?name=Lea');
$response = new Response('Bonjour '.$request->query->get('name', 'visiteur'));
echo $response->getStatusCode(), ' ', $response->getContent(), "\n";

La sortie d'inspection attendue est 200 Bonjour Lea. L'echo appartient au laboratoire : il affiche ce que contient l'objet sans appeler send(). Dans une fonction censée retourner une Response, faire cet echo puis retourner un objet vide dissocierait le contenu visible du résultat testé. Pour un véritable rendu HTML, il faut aussi échapper les données selon leur contexte ; cette concaténation de texte n'est pas un template HTML sécurisé.

Nous avons donc rendu le message manipulable. Il reste à distinguer ce vocabulaire HTTP de l'orchestrateur qui l'utilise.

🌍 In Real Life

La situation : avant de remettre un document au client, le restaurant peut inspecter une fiche d'entrée et une fiche de réponse préparée. Rédiger cette dernière n'est pas encore la livrer.

L’équivalent dans Symfony : entrée inspectable → objet Request ; résultat préparé → contenu, statut et headers de Response ; remise effective → émission ultérieure.

Retour à la réalité technique : Request::create() construit localement ; createFromGlobals() lit l'environnement PHP. Aucune de ces méthodes ne contacte un serveur ni ne choisit une route. Une Response construite ou retournée n'est pas automatiquement envoyée ; un echo de laboratoire n'est pas son contenu retourné.

🧠 Comment le mémoriser : « Préparer la réponse n'est pas la remettre. » Image mentale : une fiche complète encore sur le comptoir. Question-réflexe : inspecte-t-on un objet ou produit-on déjà un effet de sortie ?

⚠️ À ne pas confondre : construire une Request locale et effectuer une requête sortante avec HttpClient.

Sa place

Où en est-on ? Dernière question avant le détail de la pile : où se situe HttpFoundation par rapport à HttpKernel et au framework ? Pourquoi la poser ? Parce que « autonome » est une notion qui se confond facilement avec « sans dépendance » ou « qui fait tout ».

Pour un petit outil, nous pouvons nous arrêter à ces objets. HttpFoundation n'exige ni kernel ni bundles pour cet usage. À l'inverse, le contrat de HttpKernel reçoit une Request et retourne une Response : son orchestration est exprimée dans le vocabulaire de HttpFoundation. Cela ne fait pas de HttpFoundation un moteur de Routing.

« Autonome » ne signifie pas « sans dépendances Composer ». Le paquet symfony/http-foundation 8.0 exige PHP 8.4 et déclare notamment le polyfill mbstring, une bibliothèque de compatibilité de fonctions. Il n'impose pas le framework complet. Respecter les dépendances et charger l'autoloader reste nécessaire même pour un laboratoire sans serveur.

 HttpFoundation   vocabulaire : Request, Response, RequestStack
        ▲  utilisé par
 HttpKernel       orchestration : Request → Response (contrat)
        ▲  démarré par
 Kernel + bundles préparation de l'application et du container
 Routing, controllers : couches distinctes, non fournies par HttpFoundation

Conservons cet exemple d'inspection d'URL, indépendant des routes du blog :

<?php
use Symfony\Component\HttpFoundation\Request;
$request = Request::create('https://example.test/catalogue?page=2');
echo $request->getPathInfo(), "\n";
echo $request->query->get('page'), "\n";

Il affiche /catalogue puis 2, sans contacter example.test. La query contient ici page=2 ; ce laboratoire ne remplace pas notre route de pagination /blog/page/{page} et ne prouve pas qu'une route /catalogue existe. Un client HTTP effectue un appel sortant ; Request::create() construit un objet local ; HttpKernel orchestre un traitement si nous l'appelons. Ces trois opérations ne sont pas interchangeables.

Dans le framework, un service partagé est réutilisé tant que son instance reste conservée dans le container. La Request courante, elle, peut changer pendant cette durée. C'est pourquoi LocaleReader reçoit RequestStack et consulte son contenu dans locale(). Lire la Request dans le constructeur puis la stocker figerait le contexte rencontré à cet instant. Un service non partagé n'a pas la même garantie de réutilisation ; cela ne justifie pas pour autant d'inventer une Request lorsqu'aucun traitement HTTP n'est actif.

🌍 In Real Life

La situation : les formulaires du restaurant décrivent la commande et son résultat ; l'organisation prépare les postes ; le responsable du service coordonne leur travail.

L’équivalent dans Symfony : formulaires et supports HTTP → HttpFoundation ; préparation de l'application et du conteneur → Kernel ; coordination du traitement HTTP → HttpKernel concret.

Retour à la réalité technique : HttpFoundation fournit notamment Request, Response et RequestStack, sans routage automatique. HttpKernel utilise ces objets pour son orchestration ; une interface de kernel en décrit le contrat, pas l'implémentation. Utiliser HttpFoundation seul dispense du framework complet, pas de ses dépendances ni de PHP ≥8.4 pour la version 8.0.

🧠 Comment le mémoriser : « Le formulaire ne dirige pas le service. » Image mentale : les fiches sur le bureau, distinctes du responsable qui les traite. Question-réflexe : cet élément représente-t-il les données, prépare-t-il l'application ou coordonne-t-il le traitement ?

⚠️ À ne pas confondre : bibliothèque autonome et bibliothèque sans dépendances ; construire un Kernel n'est pas encore le démarrer.

Les trois accessors, exactement

Où en est-on ? On revient à la pile pour le point le plus testé à l'examen. Pourquoi « exactement » ? Parce que les trois noms se ressemblent, et que seule la position dans la pile les distingue.

Un accessor est ici une method qui donne accès à un élément de la pile. Pendant le traitement B du schéma, la question « quelle Request ? » a trois réponses selon le rôle recherché :

Accessor Ce qu'il rend Si la pile est vide
getCurrentRequest() le dernier empilé null
getMainRequest() le premier null
getParentRequest() l'avant-dernier, index count - 2 null

Si main est seule, elle est à la fois première et dernière ; elle n'a pas de parent. Avec main, A, B, le parent de B est A, pas main. Après le pop() de B, A devient courante et son parent redevient main. Les positions évoluent avec l'imbrication ; ce ne sont pas des liens permanents entre objets.

 index :     0      1      2
 pile  :   [main]  [ A ]  [ B ]
             │       │      └─ getCurrentRequest()   (dernier)
             │       └──────── getParentRequest()    (count − 2)
             └──────────────── getMainRequest()      (premier)

Ce laboratoire indépendant conserve les chemins pédagogiques /page et /fragment. Ils ne déclarent aucune route et n'émettent aucune Request :

use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\RequestStack;

$stack = new RequestStack();
$stack->push(Request::create('/page'));
$stack->push(Request::create('/fragment'));
echo $stack->getCurrentRequest()?->getPathInfo(), "\n";
echo $stack->getMainRequest()?->getPathInfo(), "\n";
echo $stack->getParentRequest()?->getPathInfo(), "\n";
$stack->pop();
var_export($stack->getParentRequest());
$stack->pop();

Résultat attendu : /fragment, /page, /page, puis NULL. Dans cette profondeur de deux éléments, parent et principale coïncident ; le schéma à trois éléments montre pourquoi ce n'est pas une règle générale. Le dernier pop() nettoie la pile du laboratoire sans ajouter de sortie.

Les docblocks déconseillent en général d'appeler directement push() et pop() : l'orchestrateur en possède la responsabilité. Ils avertissent aussi qu'un fragment dépendant de la Request principale ou parente peut mal fonctionner lorsqu'il est traité séparément. La conséquence utile ici est simple : un fragment doit disposer des entrées nécessaires à son propre traitement, plutôt que compter systématiquement sur un parent présent. ESI reste hors de ce cours.

Enfin, getSession() n'a pas le contrat d'absence des trois accessors. Il demande la session associée à la Request courante et lève une SessionNotFoundException si la pile est vide ou si cette Request n'a pas de session. Créer une Request locale, voire l'empiler, ne lui associe pas automatiquement une session. Le service doit distinguer « pas de Request » de « une Request existe, mais aucune session n'est disponible ».

🌍 In Real Life

La situation : pendant un service imbriqué, trois bons sont posés l'un sur l'autre : principal, A, B. Celui du dessus est en cours ; son parent est celui immédiatement dessous.

L’équivalent dans Symfony : dessus B → getCurrentRequest() ; dessous immédiat A → getParentRequest() ; premier bon principal → getMainRequest().

Retour à la réalité technique : ces rôles dépendent des positions dans RequestStack, pas de liens permanents entre objets. HttpKernel restaure la pile dans finally ; kernel.finish_request n'effectue pas lui-même le pop(). La pile vide donne null aux trois lecteurs, tandis que getSession() lève une exception si aucune session n'est disponible.

🧠 Comment le mémoriser : « Dessus, dessous immédiat, fond. » Image mentale : trois bons dont on retire B pour retrouver A. Question-réflexe : cherche-t-on le contexte courant, son parent immédiat ou la principale ?

⚠️ À ne pas confondre : absence de Request et Request sans session ; empiler un objet ne lui crée pas une session.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Garder la pile n'est pas garder son premier élément.

    Garder la pile n'est pas garder son premier élément. Si LocaleReader stockait getCurrentRequest() à sa construction pendant main, il lirait encore cet objet durant B. Injecter la pile puis lire au moment utile suit le contexte. Passer explicitement une Request à une method reste également valable : ce n'est pas l'autowirer au constructeur ni conserver indéfiniment un contexte périmé. Pourquoi on se trompe : « injecter la Request » semble plus direct que « injecter la pile », et ça marche… tant qu'aucune sous-requête ne change le contexte.

  • Voir l’explication : La dépendance architecturale ne dispense pas des dépendances du paquet.

    La dépendance architecturale ne dispense pas des dépendances du paquet. HttpKernel emploie les objets HttpFoundation ; utiliser ces objets seuls n'impose pas HttpKernel. Cela ne signifie ni « fonctionne avec tout PHP » ni « aucune dépendance Composer ». Pour la version 8.0, PHP >= 8.4 demeure requis. Pourquoi on se trompe : « autonome » est lu comme « sans rien d'autre ».

  • Voir l’explication : Une pile vide n'est pas une Request vide.

    Une pile vide n'est pas une Request vide. La commande d'import sans traitement HTTP obtient null, pas un objet factice ni la dernière Request du serveur. Elle peut néanmoins construire volontairement une Request pour un laboratoire : c'est l'état de la pile, non le simple mot « console », qui détermine les résultats. getSession() conserve son comportement distinct par exception en l'absence de session. Pourquoi on se trompe : on suppose qu'un framework « fournit toujours quelque chose » plutôt qu'un null à gérer.

Application

À retenir en priorité
  1. getCurrentRequest() désigne le sommet de la pile.
  2. getMainRequest() désigne la première Request ; getParentRequest() la précédente.
  3. HttpFoundation fonctionne sans le framework.
  4. Le kernel dépend de son vocabulaire Request et Response.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Pour retrouver le rôle de HttpFoundation dans l'affichage de l'article 42 :

  1. Représenter les entrées par Request et le résultat par Response permet de les inspecter avant émission. Request::create() ne contacte aucun serveur.
  2. Construire ces objets ne choisit ni route ni controller : HttpKernel apporte l'orchestration. Le component reste utilisable seul, avec les dépendances compatibles de sa version 8.0 et PHP >= 8.4.
  3. Un service partagé qui lit le contexte consulte RequestStack au moment utile ; passer explicitement une Request à une method est une autre possibilité, distincte de la capture d'un contexte au constructeur.
  4. current désigne le dernier élément, main le premier, parent l'avant-dernier. Les trois rendent null sur une pile vide ; une seule Request n'a pas de parent.
  5. Demander la session est une autre opération : getSession() lève SessionNotFoundException si aucune session n'est disponible. Une Request locale ne crée pas implicitement cette session.

« Pile, pas registre » rappelle que nous suivons les traitements actifs, non l'historique des visites. Cette frontière rend compréhensible la suite du trajet : HttpKernel peut organiser des objets HTTP sans obliger les outils CLI du blog à vivre dans un contexte HTTP.

Phrase de mémorisation : « Dernier = courante, premier = main, avant-dernier = parent ; pile vide = null ; le kernel empile, pas moi. »

Do isRedirect() and isRedirection() accept the same status codes?

No. isRedirection() tests 3xx; isRedirect() includes 201 and excludes 300 and 304.

isRedirection() teste la class 3xx. isRedirect() suit une liste distincte de statuts.
