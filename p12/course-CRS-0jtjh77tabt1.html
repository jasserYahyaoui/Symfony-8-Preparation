Objectif

Le blog prépare plusieurs messages : une salutation après inscription, puis un compte rendu de son import en ligne de commande. Ils peuvent partager une façon d'assembler le texte tout en choisissant chacun leur libellé. Une abstract class, class abstraite, permet ce partage sans offrir une instance directe de la base. Nous allons déterminer ce que la base fournit, ce que la fille doit compléter et quand un simple contrat d'interface serait préférable.

Le cours se déroule en quatre étapes : (1) le mécanisme d'une abstract class sur un exemple minimal, (2) les règles que PHP vérifie, (3) les properties abstraites de PHP 8.4, (4) le choix entre interface et abstract class.

L'essentiel

À comprendre

À retenir en priorité
  1. L'interface décrit le contrat.
  2. L'abstract class peut partager constructor, état et comportement.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Deux classes peuvent suivre la même procédure en changeant un seul détail. Copier la procédure dans chacune est fragile ; une base commune écrit la procédure une fois et laisse un trou (la méthode abstraite) pour le détail qui varie.
  • Le piège de fond. Une abstract class n'est pas « un objet parent » qui parle à un objet enfant : il n'y a qu'un seul objet, de la classe concrète, qui a hérité du code de la base.
  • Pourquoi c'est à l'examen. Les questions portent sur les règles que PHP fait respecter (instanciation, private, visibilité de la fille, abstract + final, property abstraite sans hook) et sur la différence avec une interface ou un trait.

Notre assembleur de messages sait ajouter un préfixe, mais laisse le choix du libellé à chaque variante. La base peut fournir constructor, état et méthodes concrètes ; une méthode abstraite déclare une signature sans corps que la fille concrète doit implémenter. On construit cette fille, pas la base. Même une class entièrement implémentée peut rester volontairement abstract et donc non instanciable.

Les méthodes abstraites d'une class sont public ou protected, jamais private. Depuis PHP 8.4, la base peut aussi exiger un accès à une property au moyen d'un hook, une définition d'accès en lecture ou écriture, laissé sans corps. Le besoin est distinct de celui d'une interface : promettre une capacité ne suffit pas à partager son code d'assemblage.

Résumé en une grille :

┌──────────────────────┬───────────────────────────────────────────────┐
│ Élément              │ Ce que PHP impose                             │
├──────────────────────┼───────────────────────────────────────────────┤
│ new sur la base      │ Error « Cannot instantiate abstract class »   │
│ méthode abstraite    │ sans corps ; public ou protected ; pas private│
│ fille concrète       │ implémente TOUT ; visibilité égale ou +large  │
│ property abstraite   │ PHP 8.4 ; au moins un hook sans corps         │
│ abstract + final     │ incompatibles sur le même élément             │
└──────────────────────┴───────────────────────────────────────────────┘

Le schéma

À retenir en priorité
  1. Une property abstraite exige un hook sans body.
  2. La fille peut élargir la visibilité, pas la restreindre.

Où en est-on ? Étape 1 sur 4 : avant de lire une seule règle, il faut voir comment un appel circule dans une abstract class. La question à garder en tête : « sur quel objet le code hérité s'exécute-t-il ? ».

La confirmation d'inscription utilise un GreetingRenderer. Suivons son appel à render() : le code partagé récupère le préfixe, demande le libellé à la spécialisation puis concatène les deux. Le dessin sépare la relation entre classes du trajet réel d'un appel.

Le pointillé exprime l'héritage, pas un appel. Les flèches pleines suivent l'exécution sur un seul objet concret. Le rectangle orange est la base abstraite ; les bleus portent le code exécuté ; les capsules vertes montrent l'entrée et le résultat. Une base abstraite n'est donc pas un objet intermédiaire. En particulier, le message ne passe pas d'un object parent à un object enfant. Nous allons construire une seule instance et observer cette collaboration entre méthodes.

Pourquoi render() peut-il appeler label() alors que la base ne l'écrit pas ? Parce que $this désigne l'objet réellement créé, ici un GreetingRenderer. PHP cherche label() dans la classe de cet objet, trouve celle de la fille, et l'exécute. La base ne fait que déclarer qu'elle existera (la méthode abstraite) ; cette promesse est vérifiée dès le chargement de la fille.

new GreetingRenderer('> ')           ← UN seul objet
┌──────────────────────────────────────────────┐
│ classe réelle : GreetingRenderer             │
│  hérité de LabelRenderer : $prefix, render() │
│  écrit par la fille      : label()           │
└──────────────────────────────────────────────┘
render() → $this->prefix . $this->label()
           └ cherche label() dans la classe réelle → « Hello »

L'exemple

Exemple concret

Où en est-on ? Toujours étape 1 sur 4 : on passe du dessin au code minimal qui le réalise. Question : que fait chaque classe, et qui est construit ?

Avec le préfixe > et le libellé de démonstration Hello, nous attendons > Hello. Le code suivant assemble une chaîne ; malgré le nom render, il n'utilise pas Twig, n'envoie pas de courriel et ne crée pas de Response.

abstract class LabelRenderer
{
    public function __construct(protected string $prefix) {}

    abstract protected function label(): string;

    public function render(): string
    {
        return $this->prefix.$this->label();
    }
}

final class GreetingRenderer extends LabelRenderer
{
    protected function label(): string { return 'Hello'; }
}

echo (new GreetingRenderer('> '))->render(); // > Hello

Le constructor hérité prépare le préfixe dans GreetingRenderer. render() peut ensuite appeler son label() protégé, qui retourne Hello, sans recopier l'assemblage dans la fille. L'appel extérieur utilise uniquement la méthode publique render(). Une autre spécialisation pourrait fournir un autre libellé tout en gardant cette procédure.

Ce que PHP voit, ligne par ligne :

Élément Ce que PHP en fait
abstract class LabelRenderer classe non instanciable, qui peut porter état et code
abstract protected function label(): string; un « trou » : signature sans corps
render() méthode concrète, héritée telle quelle par la fille
final class GreetingRenderer extends LabelRenderer classe concrète : elle comble le trou
new GreetingRenderer('> ') le constructor hérité reçoit '> '

La limite est délibérée : nous avons factorisé du PHP, pas mis en place le parcours d'inscription. Le service qui prépare la confirmation devra encore choisir et appeler la variante adaptée. Vérifions maintenant ce que PHP impose à cette variante avant qu'elle puisse être construite.

🌍 In Real Life

La situation : un atelier suit une procédure commune d'impression, mais chaque modèle fournit son propre libellé. Une seule machine spécialisée exécute l'ensemble.

L’équivalent dans Symfony : procédure commune → LabelRenderer::render() ; détail spécialisé → GreetingRenderer::label() ; machine effective → instance de GreetingRenderer.

Retour à la réalité technique : le code hérité appelle $this->label() sur le même objet concret. Le constructor prépare son état ; aucune instance séparée de la base ne transmet un message à une instance fille. Ce PHP peut servir à un service Symfony sans constituer un rendu Twig.

🧠 Comment le mémoriser : « Un objet, une procédure partagée, un détail spécialisé. » Image mentale : une seule machine portant la fiche de procédure et son libellé. Question-réflexe : sur quel objet $this travaille-t-il ?

⚠️ À ne pas confondre : héritage du comportement et collaboration entre deux objets injectés.

Règles

À retenir en priorité
  1. Une abstract class ne s'instancie pas.
  2. Une fille concrète doit satisfaire les methods abstraites.

Où en est-on ? Étape 2 sur 4. Nous savons comment ça marche ; voici ce que PHP refuse. Quatre règles, chacune testée par l'examen : instanciation, absence de corps, visibilité, obligations de la fille.

Tenter new LabelRenderer('> ') échouerait avec une Error : « Cannot instantiate abstract class ». Fournir le préfixe ne résout pas l'interdiction d'instancier la base. Il faut une fille concrète qui remplisse les obligations restantes ; une fille qui en conserve doit elle-même rester abstract.

La méthode abstraite n'a pas de corps. Sa signature peut être public ou protected, et éventuellement static, mais pas private dans une class. L'implémentation doit rester compatible et ne pas restreindre la visibilité promise. Pour le compte rendu d'import, la variante suivante rend même son titre public :

abstract class Report
{
    abstract protected function title(): string;

    public function render(): string
    {
        return '['.$this->title().']';
    }
}

final class DailyReport extends Report
{
    public function title(): string
    {
        return 'Daily';
    }
}

echo new DailyReport()->render(), "\n";

En PHP 8.4, cet exemple autonome affiche [Daily]. La fille élargit légalement protected en public et hérite de l'assemblage commun. new Report() resterait interdit. Le code ne collecte aucune statistique et ne lance pas l'import : il illustre le choix du titre d'un rapport. (new DailyReport()->render() sans parenthèses autour du new est permis depuis PHP 8.4.)

Pourquoi private est-il interdit pour une méthode abstraite de classe ? Une méthode private n'est pas visible par la fille : elle ne pourrait jamais l'implémenter. Une obligation impossible à satisfaire n'a pas de sens, donc PHP refuse (erreur fatale). Pourquoi protected est-il le choix courant ? Parce qu'il permet à la fille de fournir le détail sans en faire une opération publique que tout appelant pourrait invoquer.

Pourquoi la fille peut-elle élargir la visibilité mais pas la restreindre ? Un appelant qui utilise la base doit pouvoir faire ce que la base promet. Rendre protected en public promet plus : acceptable. Rendre public en protected retirerait une promesse : refusé.

Visibilité promise par la base       Visibilité de la fille
  protected  ─────────────────────►  protected  ✔   public  ✔   private ✘
  public     ─────────────────────►  public     ✔   protected ✘  private ✘
         (on peut élargir, jamais restreindre)

La règle de class ne doit pas être transposée aux traits : un trait admet une méthode abstract private depuis PHP 8.0. Enfin, toute property restée abstraite constitue elle aussi une obligation ; c'est l'extension PHP 8.4 que nous examinons maintenant.

Abstract class Trait
Méthode abstract private erreur fatale permise depuis PHP 8.0
Méthode abstraite public/protected oui oui

🌍 In Real Life

La situation : un modèle d'équipement est réservé à la déclinaison en versions utilisables ; fournir ses réglages ne permet pas de commander directement ce modèle abstrait.

L’équivalent dans Symfony : modèle non commandable → classe abstract ; version utilisable → fille concrète ; exigences restantes → méthodes abstraites à implémenter.

Retour à la réalité technique : PHP interdit l'instanciation d'une classe abstraite, même sans méthode manquante. La fille concrète doit satisfaire les obligations et leurs signatures ; elle peut élargir protected en public, pas réduire l'accès. Dans une classe, une méthode abstraite n'est pas privée.

🧠 Comment le mémoriser : « Les réglages ne rendent pas le modèle instanciable. » Image mentale : fiche du modèle marquée « choisir une version ». Question-réflexe : la classe est-elle concrète et toutes ses obligations sont-elles satisfaites ?

⚠️ À ne pas confondre : règle des classes et règle des traits, qui permettent abstract private depuis PHP 8.0.

Repère — Les properties abstraites — depuis PHP 8.4 : Une property abstraite exige un hook sans body. La fille peut élargir la visibilité, pas la restreindre.

Les properties abstraites — depuis PHP 8.4

Où en est-on ? Étape 3 sur 4. Jusqu'ici l'obligation portait sur une méthode. Depuis PHP 8.4, elle peut porter sur une property : la base n'impose pas comment la valeur est stockée, seulement quel accès existe (lecture, écriture, ou les deux).

Jusqu'ici, le code partagé demandait le texte par une méthode. Si le contrat demande plutôt une property lisible, PHP 8.4 permet de déclarer explicitement l'accès attendu. Gardons le petit exemple géométrique Shape/Circle pour isoler cette règle ; il n'est pas une nouvelle étape du traitement de l'article.

abstract class Shape
{
    abstract public string $label { get; }   // exigence : lisible en public
}

final class Circle extends Shape
{
    public string $label = 'cercle';         // une property ordinaire suffit
}

Après ces déclarations, (new Circle())->label vaut cercle. L'absence de hook explicite dans Circle est légale : une property ordinaire satisfait l'accès { get; }, comme peut le faire une property readonly ou munie d'un hook défini, sous réserve de compatibilité. Le contrat exige la lecture, pas une technique particulière de stockage.

Pourquoi { get; } et pas juste abstract public string $label; ? Un hook est un bloc d'accès (get, set) attaché à une property. Écrit sans corps (get;), il dit : « il faut un accès en lecture ici ». Sans ce hook, PHP ne saurait pas quelle obligation exprimer.

En revanche, la déclaration abstraite doit préciser au moins un hook sans corps : sans hook, PHP refuse avec « Only hooked properties may be declared abstract ». L'autre hook peut fournir un corps par défaut. La property abstraite est public ou protected, jamais private, et une fille concrète qui ne satisfait pas l'obligation est refusée.

abstract class Base
{
    abstract public string $foo {
        get;                              // la fille DOIT fournir la lecture
        set { $this->foo = $value; }      // écriture par défaut, redéfinissable
    }
}

La même logique explique la visibilité : un accès protégé peut devenir public, mais la lecture publique promise par Shape ne peut devenir protégée dans Circle. Si le contrat exige une écriture publique par set, une property readonly ne la fournit pas. Pour les libellés de l'application, demander seulement get conserve donc plus de liberté qu'exiger un libellé modifiable par tous les appelants.

Contrat de la base Fille acceptée Fille refusée
abstract public string $label { get; } public string $label ; public readonly ; hook get défini protected string $label
abstract protected string $x { get; } protected ou public private
abstract public string $x { set; } public modifiable public readonly (pas d'écriture publique)
abstract public string $x; — erreur fatale : aucun hook

🌍 In Real Life

La situation : le plan impose un afficheur public du libellé, sans imposer si celui-ci provient d'une valeur mémorisée ou d'un calcul.

L’équivalent dans Symfony : afficheur exigé → propriété abstraite { get; } ; réalisation → propriété ordinaire compatible ou hook défini ; éventuel bouton d'édition → accès set.

Retour à la réalité technique : en PHP 8.4, la déclaration abstraite exige au moins un hook sans corps ; son implémentation n'a pas nécessairement besoin d'un hook explicite. Une lecture publique ne peut devenir protégée. Une propriété readonly ne fournit pas une écriture publique.

🧠 Comment le mémoriser : « Imposer l'accès, laisser sa réalisation. » Image mentale : un afficheur obligatoire sur plusieurs modèles différents. Question-réflexe : quel accès reste abstrait, et l'implémentation le fournit-elle avec la bonne visibilité ?

⚠️ À ne pas confondre : hook de propriété PHP et événement du HttpKernel.

Interface ou abstract class ?

Où en est-on ? Étape 4 sur 4, la dernière : on a vu ce qu'offre une abstract class ; reste à décider quand la choisir plutôt qu'une interface. La question est : veut-on seulement accepter une capacité, ou aussi partager du code ?

Nous avons maintenant deux besoins distincts : permettre à l'appelant de recevoir « quelque chose qui formate », et partager une procédure entre certains formateurs. Le tableau compare les mécanismes, sans en faire des solutions mutuellement exclusives.

Interface Abstract class
Corps de method Non Oui
Properties d'état Non Oui
Constructor Signature seulement, déconseillée Oui
Visibilité d'une method abstraite Publique uniquement public ou protected
Property exigée (PHP 8.4) public, hooks sans corps public ou protected ; un hook peut avoir un body
Nombre par class Plusieurs Une seule

L'interface décrit ce qu'un object sait faire sans porter d'état d'instance ni de corps de méthode. Une signature de constructor y est possible, mais généralement déconseillée : elle réduit la liberté de construction de toutes les implémentations. Une base abstraite convient si une famille de variantes doit réellement partager cette construction, de l'état ou une procédure ; ce n'est pas une obligation dès qu'un object possède un constructor.

Pour les messages de l'import, combinons le contrat Formatter avec une base PrefixedFormatter. L'appelant dépend du premier ; la variante choisit de réutiliser la seconde :

interface Formatter
{
    public function format(string $message): string;
}

abstract class PrefixedFormatter implements Formatter
{
    public function __construct(private string $prefix) {}

    abstract protected function transform(string $message): string;

    public function format(string $message): string
    {
        return $this->prefix.$this->transform($message);
    }
}

final class UpperFormatter extends PrefixedFormatter
{
    protected function transform(string $message): string
    {
        return strtoupper($message);
    }
}

function printMessage(Formatter $formatter): void
{
    echo $formatter->format('ready'), "\n";
}

printMessage(new UpperFormatter('INFO: '));

L'entrée ready et le préfixe INFO: produisent INFO: READY. printMessage() ne connaît ni le stockage du préfixe ni la transformation protégée. Une autre implémentation de Formatter pourrait éviter cette base. Ce script PHP autonome ne configure pas le component Console ; il fournit seulement le formateur qu'une commande pourrait utiliser.

        printMessage(Formatter $f)        ← l'appelant ne voit QUE ceci
                    │
            interface Formatter           ← le contrat (ce qu'on sait faire)
              ▲                 ▲
   PrefixedFormatter        AutreFormatter   ← deux façons de le remplir
   (abstract : préfixe +        (sans la base)
    transform() abstraite)
              ▲
        UpperFormatter                   ← classe concrète

Dans Symfony 8.0, étendre Symfony\Bundle\FrameworkBundle\Controller\AbstractController permet de réutiliser ses helpers, mais n'est pas nécessaire pour être controller. BlogController::show n'acquiert donc pas sa fonction HTTP par le seul mot-clé extends. PHP autorise plusieurs interfaces, mais une seule class parente : ce choix de réutilisation engage aussi cette place.

🌍 In Real Life

La situation : un acheteur exige un format de sortie ; certains fabricants réutilisent le même mécanisme interne, mais un autre peut satisfaire l'exigence avec une conception différente.

L’équivalent dans Symfony : exigence vue par l'acheteur → Formatter ; mécanisme réutilisable → PrefixedFormatter ; produit concret → UpperFormatter. Les helpers d'AbstractController relèvent aussi d'une réutilisation facultative.

Retour à la réalité technique : une interface définit le contrat du consommateur ; une base abstraite peut partager code et état. Une classe n'a qu'un parent, mais peut implémenter plusieurs interfaces. Recevoir un formateur par injection permet de collaborer sans hériter de son code.

🧠 Comment le mémoriser : « Le client demande une capacité, pas une généalogie. » Image mentale : plusieurs machines répondent à la même fiche de résultat. Question-réflexe : veut-on partager une procédure ou seulement accepter une capacité ?

⚠️ À ne pas confondre : étendre AbstractController et être sélectionné comme callable HTTP ; l'héritage n'effectue pas le routage.

Le manuel d'une franchise fournit une procédure commune mais laisse une étape locale à compléter. Une abstract class fournit ce comportement partagé ; seule une class concrète ayant rempli les obligations peut être instanciée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Fin du parcours : voici les erreurs que les QCM exploitent, avec la raison pour laquelle chacune paraît plausible.

  • Voir l’explication : Dans une classe, abstract private est une erreur fatale.

    Dans une classe, abstract private est une erreur fatale. Ce n'est pas la règle des traits : PHP 8.0 autorise une méthode abstraite privée dans un trait. Dans LabelRenderer, la variation attendue est protected pour pouvoir être fournie par la fille sans devenir une opération publique obligatoire. Pourquoi on se trompe : on a lu « les traits l'autorisent » et on généralise à toutes les classes.

  • Voir l’explication : Une seule class parente.

    Une seule class parente. Besoin de deux jeux de comportements partagés : c'est un trait ou une composition, pas un second extends. La composition consiste à confier un travail à un autre object : un service du blog peut recevoir un Formatter au lieu d'hériter lui-même de son assemblage. Pourquoi on se trompe : une classe peut implémenter plusieurs interfaces, on croit que c'est vrai aussi pour extends.

  • Voir l’explication : abstract et final sont incompatibles

    abstract et final sont incompatibles : l'un exige une extension, l'autre l'interdit lorsqu'on les applique à la même class ou méthode. Cela n'empêche pas DailyReport d'être final : c'est une fille concrète. Une base abstraite peut également fournir des méthodes concrètes finales ; ne transforme pas l'incompatibilité sur un même élément en interdiction de rencontrer les deux mots dans une famille de classes. Pourquoi on se trompe : on voit les deux mots dans la même hiérarchie et on oublie que la règle vise le même élément.

  • Voir l’explication : Une property abstraite sans hook est une erreur fatale.

    Une property abstraite sans hook est une erreur fatale. abstract public string $label; ne compile pas : il faut { get; }, { set; } ou les deux, dont au moins un sans corps. L'obligation porte sur un accès : écrire seulement le type et le nom du libellé ne précise pas cet accès abstrait. Pourquoi on se trompe : pour une méthode, abstract suffit ; on pense que c'est pareil pour une property.

  • Voir l’explication : Une property protected ne satisfait pas une lecture publique.

    Une property protected ne satisfait pas une lecture publique. Seul l'élargissement de visibilité est permis (Circle avec protected string $label est refusé face à abstract public string $label { get; }). Pourquoi on se trompe : on confond « plus permissif » et « plus restreint » ; une fille peut ouvrir la visibilité, jamais la réduire.

  • Voir l’explication : new sur une abstract class lève une Error

    new sur une abstract class lève une Error, même si toutes ses méthodes sont concrètes et même si on fournit les arguments du constructor. Pourquoi on se trompe : sans méthode abstraite, la classe semble « complète » et donc instanciable ; c'est le mot abstract qui interdit new.

Partager une procédure sans imposer un ancêtre artificiel

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Sous-section de conception : comment décider qu'une base abstraite se justifie dans l'application du blog.

  • Base facultative contre contrat commun

    Pour l'inscription, GreetingRenderer partage l'assemblage et choisit le libellé. Pour l'import, Formatter permet à l'appelant d'accepter des classes sans parent commun ; PrefixedFormatter reste une aide facultative pour celles qui partagent réellement le préfixe et la procédure. Ces objets sont des outils de l'application, pas des passages obligatoires de GET /blog/42.

  • Éviter une hiérarchie sans comportement commun

    L'exemple classique de repositories partageant une connexion et findAll() dans une base qui exige table() illustre le même partage de procédure. Ces noms désignent alors une conception applicative, pas une API universelle de Symfony. Notre ArticleCatalog en mémoire n'a besoin ni de cette connexion ni de cette hiérarchie. Ne crée une base que pour un comportement commun réel, pas pour donner artificiellement le même ancêtre à toutes les classes du blog.

  • Contrat d’interface et réutilisation par trait

    Les interfaces approfondissent le contrat vu par l'appelant ; les traits présentent une autre forme de réutilisation, avec ses propres règles.

Application

À retenir en priorité
  1. L'interface décrit le contrat.
  2. L'abstract class peut partager constructor, état et comportement.
  3. Une property abstraite exige un hook sans body.
  4. La fille peut élargir la visibilité, pas la restreindre.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Non instanciable (Error) ; une seule abstract class par extends.
  • Method abstraite de class : sans corps, public ou protected, jamais private ; ne pas confondre avec la règle des traits.
  • Fille concrète : tout implémenter, visibilité égale ou plus large.
  • 8.4 : property abstraite = hook sans corps ; jamais private.
  • abstract + final : incompatibles sur le même élément.
  • Interface = contrat ; abstract class = comportement partagé.
  • Un seul objet concret exécute le code hérité ($this).

Moyen mnémotechnique : « L'interface promet, la base partage, la fille complète. » Le résultat exécuté reste porté par un seul object concret.
