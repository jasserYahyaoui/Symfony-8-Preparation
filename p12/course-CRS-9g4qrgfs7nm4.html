Objectif

Nous relisons le code qui sert l'article 42 et prépare les pages de liste. Un collègue doit reconnaître rapidement une class, une constante, un nom de route ou une variable Twig sans reconstituer tout le projet. Les conventions officielles donnent ce vocabulaire commun.

Nous les appliquons aux valeurs et contrats du blog en PHP 8.4 et Symfony 8.0. Elles organisent la lecture et la contribution ; elles ne créent ni méthodes, ni services, ni traitement HTTP. Les conventions propres aux controllers sont étudiées séparément (voir Request handling et Code organization pour l'emplacement des fichiers).

L'essentiel

À comprendre

À retenir en priorité
  1. all() concerne la relation principale.
  2. Une relation secondaire utilise getXXXs(), pas allXXX().

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un nom est le premier contrat lu par un humain : avant de lire le corps d'une méthode, on déduit son rôle de sa forme. Les conventions rendent cette déduction prévisible pour tous.
  • Le piège de fond. Une convention de nommage informe le lecteur ; elle ne crée rien. SomethingInterface déclaré avec class reste une class ; AsPayload inventé n'est lu par personne.
  • Ce que l'auteur veut que vous compreniez. Trois questions dans l'ordre : quelle catégorie (casse), quel rôle (préfixe/suffixe), quelle relation (méthodes de collection).
  • Pourquoi c'est à l'examen. Les questions portent sur des détails précis : la case vide de keys(), bool et non boolean, l'exception *TestCase, la différence setXXX() / replaceXXX().

La casse désigne l'usage des majuscules et minuscules. Nous choisissons d'abord la catégorie : ArticleView est une class, blog_show un nom de route et $articleTitle une variable PHP. Une même idée peut donc changer de forme selon le rôle du nom.

Les préfixes et suffixes renseignent ensuite le contrat : FormatterInterface annonce une interface, AbstractFormatter une base abstraite. Les préfixes d'attributes signalent le domaine de leur métadonnée, sans remplacer le mécanisme qui la lit.

Enfin, une méthode de collection doit dire de quelle relation elle parle. all() est clair quand une seule collection est la responsabilité principale de l'objet ; getOptions() l'est davantage pour une relation secondaire. Le nom facilite l'usage, mais l'implémentation doit encore respecter le comportement annoncé.

TROIS QUESTIONS POUR NOMMER
 1. Quelle catégorie ?  class / méthode / constante / enum / route / Twig
        → détermine la CASSE
 2. Quel rôle ?         abstraite / interface / trait / exception / attribute
        → détermine le PRÉFIXE ou le SUFFIXE
 3. Quelle relation ?   collection principale ou secondaire ?
        → détermine le nom de MÉTHODE (all() ou getXXXs()…)
 Le nom informe le lecteur ; il ne crée aucun comportement.

Le schéma

À retenir en priorité
  1. Les enum cases suivent UpperCamelCase.
  2. Les constants restent en SCREAMING_SNAKE_CASE.

Où en est-on ? Nous avons les trois questions ; le schéma illustre la troisième, la plus subtile : choisir le nom d'une méthode d'ajout. Pourquoi ce cas ? Parce qu'il montre qu'un même type de valeur (une collection) reçoit un nom différent selon la responsabilité de l'objet.

Pour choisir entre add() et un nom plus explicite, nous examinons la responsabilité de l'objet, pas seulement le type des valeurs. Le diagramme conserve RouteCollection et le laboratoire indépendant Order pour montrer cette décision :

Une collection de routes peut dire add() : le lecteur sait déjà ce qu'elle rassemble. Order::addLine() nomme au contraire la relation que l'objet manipule ; il ne signifie pas que nous ajoutons un domaine de commandes commerciales au blog.

Le losange orange représente une décision humaine de nommage, les capsules vertes les noms retenus. Le même raisonnement peut guider une collection d'articles ou les tags d'une vue d'article. Il n'impose pas de renommer toutes les recherches de ArticleCatalog en get() : le rôle réel et le contrat existant restent à examiner.

L'exemple : une collection principale

Exemple concret

Où en est-on ? On passe du schéma au code. Pourquoi un objet fictif ? Parce que le CookieJar des conventions officielles sert d'illustration documentaire ; nous ne voulons pas attribuer à une vraie class de BrowserKit une méthode qu'elle n'a pas.

Le petit exemple historique distingue cookies et options. Pour ne pas prêter une méthode inventée au CookieJar de BrowserKit, nous le rendons autonome avec un objet fictif. Ses cookies sont des valeurs simplifiées, pas des objets ou headers HTTP :

final class DemoCookieJar
{
    public function __construct(private array $cookies, private array $options) {}

    public function all(): array
    {
        return $this->cookies;
    }

    public function getOptions(): array
    {
        return $this->options;
    }
}

$jar = new DemoCookieJar(['theme' => 'dark'], ['strict' => true]);
$jar->all();            // relation principale : les cookies simplifiés
$jar->getOptions();     // relation secondaire : getXXXs(), pas allOptions()

Le premier appel renvoie ['theme' => 'dark'], le second ['strict' => true]. Aucune valeur n'est affichée par ces seuls appels : ils retournent des tableaux. L'option strict appartient uniquement au laboratoire ; elle n'active aucun comportement Symfony.

Le résultat dépend des méthodes que nous avons réellement écrites. La convention ne garantit donc pas que tout objet nommé CookieJar possède getOptions(), et ne sérialise aucun cookie vers le navigateur. Nous utilisons ce modèle seulement pour rendre la relation principale et la relation secondaire reconnaissables.

La casse

Où en est-on ? Question 1 sur 3 : quelle catégorie ? Pourquoi la casse d'abord ? Parce qu'elle se lit avant tout le reste : un coup d'œil sépare UpperCamelCase (types, fichiers) de camelCase (méthodes, variables) et de snake_case (configuration, routes, Twig).

Voici les catégories à comparer pendant la relecture. InputArgumentMode::IsArray, conservé dans la table comme illustration des standards, est un exemple de nommage, pas une enum Console à utiliser en Symfony 8.0. InputArgument::IS_ARRAY est, lui, une constante existante :

Élément Casse Exemple
variables, functions, methods, arguments camelCase hasSession()
parameters de configuration, route names, variables Twig snake_case framework.csrf_protection
constantes SCREAMING_SNAKE_CASE InputArgument::IS_ARRAY
cas d'enum UpperCamelCase InputArgumentMode::IsArray
classes, interfaces, traits, enums, files PHP UpperCamelCase EnvVarProcessor.php
templates Twig et ressources web snake_case section_layout.html.twig

camelCase commence par une minuscule puis distingue les mots par des majuscules. UpperCamelCase commence aussi par une majuscule. snake_case sépare les mots par des soulignements ; sa forme SCREAMING_SNAKE_CASE les écrit en majuscules. Le préfixe app. d'un paramètre reste compatible avec un nom descriptif comme app.contents_dir.

Moyen mnémotechnique en une ligne :

code PHP « qui agit »       → camelCase        pageCount(), $itemCount
types et fichiers PHP       → UpperCamelCase   PageOptions, PageOptions.php
valeurs fixes (constantes)  → SCREAMING_SNAKE  ITEMS_PER_PAGE
cas d'enum                  → UpperCamelCase   InputArgumentMode::IsArray
config, routes, Twig        → snake_case       blog_show, section_layout

La pagination fournit un exemple PHP 8.4 de ces catégories :

final class PageOptions
{
    public const ITEMS_PER_PAGE = 10;

    public function pageCount(int $itemCount): int
    {
        return (int) ceil($itemCount / self::ITEMS_PER_PAGE);
    }
}
echo (new PageOptions())->pageCount(21), "\n";

Avec un compte fictif de 21 éléments, le résultat est 3. PageOptions, ITEMS_PER_PAGE, pageCount et $itemCount illustrent quatre rôles. Le laboratoire suppose un compte non négatif ; il ne compte pas réellement le catalogue, ne charge pas une page et ne valide pas le paramètre de /blog/page/{page}.

Un cas d'enum utilise UpperCamelCase selon les standards Symfony, même s'il représente une valeur fixe. Cela ne transforme pas sa valeur adossée en nom de constante et ne rend pas les autres casses impossibles pour le moteur PHP. Dans les PHPDoc et transtypages, les formes prescrites sont bool, int et float, plutôt que les synonymes longs.

Enfin, la cohérence du nom de class et du fichier importe pour l'autoload : une différence de casse peut passer inaperçue sur un filesystem puis échouer sur un autre. La convention améliore la lecture, mais les chemins et références doivent eux aussi correspondre.

🌍 In Real Life

La situation : dans un catalogue technique, titres de modèles, références fixes et noms d'opérations suivent des formes visuelles distinctes pour que le lecteur reconnaisse leur rôle.

L’équivalent dans Symfony : modèle → PageOptions ; référence constante → ITEMS_PER_PAGE ; opération → pageCount ; variable → $itemCount. Un nom de route comme blog_show suit une autre catégorie.

Retour à la réalité technique : la convention de casse facilite la lecture, sans créer les éléments nommés. Les cas d'enum suivent UpperCamelCase dans ces standards, non la casse des constantes. Chemin de fichier et nom de classe doivent rester cohérents pour l'autoload, notamment sur un système sensible à la casse.

🧠 Comment le mémoriser : « Classer le rôle avant d'écrire le nom. » Image mentale : une légende typographique à côté du catalogue. Question-réflexe : est-ce une classe, une méthode, une constante, un cas d'enum ou un nom de configuration ?

⚠️ À ne pas confondre : exemple de style et API disponible ; InputArgumentMode::IsArray n'est pas une enum Console 8.0 à appeler.

Préfixes et suffixes

À retenir en priorité
  1. Abstract précède le nom.
  2. Interface, Trait et Exception sont des suffixes.

Où en est-on ? Question 2 sur 3 : quel rôle ? Pourquoi après la casse ? Parce que la casse dit « quelle catégorie de nom », alors que le préfixe ou le suffixe dit « quel contrat » : base abstraite, interface, trait, exception, et pour les attributes, configuration de service ou argument de controller.

Pour un outil de formatage de l'import, AbstractFormatter indique une base abstraite. FormatterInterface, FormatterTrait et FormattingException annoncent respectivement un contrat, du code réutilisé et une exception. Une class ordinaire ou une enum n'ajoute pas un suffixe artificiel Class ou Enum : ArticleView suffit à désigner notre objet.

Abstract est un préfixe, alors que Interface, Trait et Exception sont des suffixes. La convention des bases abstraites prévoit l'exception des *TestCase de PHPUnit. Certains noms historiques Symfony ne suivent pas non plus la forme actuelle et sont conservés pour compatibilité ; ce n'est pas une invitation à reproduire cette irrégularité dans une nouvelle class.

Rôle Forme Exemple
base abstraite préfixe Abstract (sauf *TestCase) AbstractFormatter
interface suffixe Interface FormatterInterface
trait suffixe Trait FormatterTrait
exception suffixe Exception FormattingException
class ordinaire, enum aucun suffixe artificiel ArticleView

Pour les attributes, As... signale la configuration d'un service, comme AsCommand pour une commande ou AsEventListener pour un listener. Map... concerne un argument de controller, comme MapRequestPayload pour le traitement des données du body vers cet argument. La convention ne décrit pas à elle seule toutes les conditions de résolution.

Dans la branche JSON de l'inscription, le nom MapRequestPayload oriente donc vers la fourniture d'un argument ; dans la commande d'import, AsCommand oriente vers la configuration du service de commande. Ni l'un ni l'autre n'est découvert simplement parce que son nom commence par ces lettres. Il faut l'attribute documenté et l'intégration qui le lit. Inventer AsPayload ne crée pas automatiquement un nouveau mécanisme Symfony.

🌍 In Real Life

La situation : une fiche porte « configurer le poste » ou « préparer l'entrée du traitement ». Le titre oriente vers la bonne procédure, mais personne ne l'exécute par le seul fait de l'avoir écrit.

L’équivalent dans Symfony : indication de configuration de service → préfixe As... ; indication liée à un argument de controller → Map... ; procédure réelle → intégration qui lit l'attribute documenté.

Retour à la réalité technique : les préfixes renseignent le lecteur ; ils n'enregistrent ni ne résolvent rien par eux-mêmes. De même, le suffixe Interface ne transforme pas une déclaration class en interface PHP. Inventer un nom ressemblant à un attribute existant n'en crée pas le mécanisme.

🧠 Comment le mémoriser : « Le titre indique ; le mécanisme agit. » Image mentale : une fiche attendant son lecteur. Question-réflexe : quel composant lit réellement cette métadonnée ?

⚠️ À ne pas confondre : configuration d'un service et résolution d'un argument d'action. #[As...] indique une catégorie, pas un attribute utilisable tel quel ; un event subscriber reste un objet déclarant ses abonnements, que l'intégration doit enregistrer.

Un badge de fonction rend un rôle lisible avant d'ouvrir le dossier. Abstract, Interface et Trait rendent pareillement l'intention visible ; le badge ne remplace toutefois pas les règles PHP ni le type réel.

Nommer une method de collection

Où en est-on ? Question 3 sur 3 : quelle relation ? Pourquoi ce point est le plus piégeux ? Parce que c'est le seul où le nom doit promettre un comportement (refuser ou ajouter) et non seulement une forme.

Une relation est principale quand elle décrit sans ambiguïté ce que l'objet rassemble. Les conventions normalisent alors douze noms : get(), set(), has(), all(), replace(), remove(), clear(), isEmpty(), add(), register(), count() et keys(). Cette liste ne promet pas que toutes les classes les implémentent toutes.

Pour le container, les services constituent la relation principale ; les paramètres sont nommés explicitement, par exemple getParameter(). Pour un Input Console, arguments et options sont deux relations importantes : getArgument() et getOption() évitent l'ambiguïté d'un simple get(). L'import peut ainsi distinguer son argument de fichier d'une option de comportement.

La plupart des variantes nomment la relation, comme hasXXX() ou addXXX(). Les quatre lignes suivantes demandent une attention particulière :

Relation principale Autre relation
all() getXXXs() — pas allXXX()
replace() setXXXs() — pas replaceXXXs()
keys() aucune
aucune replaceXXX()

all() devient getXXXs() pour retourner les éléments d'une relation explicitement nommée. Le replace() de la collection complète correspond à setXXXs(), et non à un replaceXXXs() déduit mécaniquement. La table ne propose pas de variante suffixée à keys() ; elle ne rend pas illégal un nom applicatif défini et documenté hors de cette table.

Il faut surtout distinguer l'élément de la collection complète. setXXX() peut remplacer ou ajouter un élément ; replaceXXX() ne peut que remplacer une key existante et doit lever une exception pour une key inconnue. Si les options d'import n'ont pas encore la key encoding, un contrat setOption('encoding', 'UTF-8') peut l'ajouter ; un contrat replaceOption(...) conforme à cette convention doit la refuser. Cet exemple décrit le comportement à implémenter dans notre objet, pas une méthode supposée disponible sur n'importe quelle class Symfony.

La distinction n'est pas produite par le nom au runtime. Elle devient utile lorsque le code et les tests respectent réellement la promesse annoncée au lecteur.

Clé 'encoding' ABSENTE des options :
  setOption('encoding', 'UTF-8')      → ajoute la clé        (autorisé)
  replaceOption('encoding', 'UTF-8')  → lève une exception   (clé inconnue)
Clé 'encoding' PRÉSENTE :
  setOption(...) et replaceOption(...) → remplacent la valeur

🌍 In Real Life

La situation : demander « tous » dans une armoire de dossiers désigne naturellement les dossiers ; sur un bureau qui contient aussi des notes et des réglages, il faut préciser la catégorie.

L’équivalent dans Symfony : contenu principal de l'armoire → relation principale avec all() ; catégorie secondaire → getXXXs() ; changement d'un élément existant seulement → contrat replaceXXX().

Retour à la réalité technique : la convention nomme la responsabilité, sans générer les méthodes. setXXX() peut ajouter ou remplacer ; replaceXXX() doit refuser une clé inconnue. Remplacer la collection secondaire entière se nomme setXXXs() dans la table, pas par simple ajout d'un suffixe à replace().

🧠 Comment le mémoriser : « Tous les quoi ? Et remplacer quoi ? » Image mentale : une armoire identifiée face à un bureau aux catégories multiples. Question-réflexe : la relation est-elle principale, et manipule-t-on un élément ou toute la collection ?

⚠️ À ne pas confondre : promesse de nommage et preuve du comportement ; seul le code et ses tests confirment le refus d'une clé absente.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Valeur fixe ne signifie pas nom de constante.

    Valeur fixe ne signifie pas nom de constante. Les cas d'enum suivent UpperCamelCase dans ces standards. InputArgumentMode::IsArray reste une illustration documentaire, pas une API Console 8.0 ; ne remplaçons pas InputArgument::IS_ARRAY par une référence inexistante. Pourquoi on se trompe : une enum « contient des constantes », donc on écrit ses cas en SCREAMING_SNAKE_CASE.

  • Voir l’explication : Le rôle est annoncé, pas créé, par le nom.

    Le rôle est annoncé, pas créé, par le nom. Abstract précède la base abstraite, Interface, Trait et Exception suivent leur nom. Une déclaration class nommée SomethingInterface ne devient pas une interface PHP. Une class ordinaire n'a pas besoin de Class ou Enum en suffixe.

  • Voir l’explication : Le préfixe d'attribute ne fournit pas son lecteur.

    Le préfixe d'attribute ne fournit pas son lecteur. As... concerne la configuration de service, Map... un argument de controller. Les mécanismes documentés doivent être présents : choisir le bon préfixe ne suffit pas à brancher une conversion.

  • Voir l’explication : Les pluriels ne se déduisent pas toujours par concaténation.

    Les pluriels ne se déduisent pas toujours par concaténation. Pour une relation secondaire, la table donne getXXXs() pour all() et setXXXs() pour replace(). Il faut lire le contrat de collection plutôt qu'inventer allXXX() ou confondre collection et élément. Pourquoi on se trompe : la règle « nom principal + XXX » semble régulière, et allXXX() ressemble à une extension naturelle de all().

  • Voir l’explication : Remplacer suppose ici une key existante.

    Remplacer suppose ici une key existante. Dans notre contrat d'options, setOption() peut ajouter encoding, mais replaceOption() doit refuser cette key si elle manque. Le test de cette entrée absente vérifie le comportement ; un contrôle de style sur le seul nom ne le prouve pas.

Application

À retenir en priorité
  1. all() concerne la relation principale.
  2. Une relation secondaire utilise getXXXs(), pas allXXX().
  3. Abstract précède le nom.
  4. Interface, Trait et Exception sont des suffixes.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Lors de la relecture du blog :

  1. Classer le nom avant de choisir sa casse : $articleTitle, blog_show, ArticleView et ITEMS_PER_PAGE n'ont pas le même rôle.
  2. Garder les cas d'enum en UpperCamelCase et les constantes en SCREAMING_SNAKE_CASE, sans inventer une API à partir d'un exemple de style.
  3. Placer Abstract devant, Interface, Trait et Exception derrière ; connaître l'exception *TestCase et les noms historiques conservés.
  4. Lire As... comme une indication de configuration de service, Map... comme une indication liée aux arguments, puis vérifier leur intégration.
  5. Pour une relation secondaire, retenir getXXXs() et setXXXs() ; la table ne donne pas de variante à keys().
  6. Vérifier par le comportement que replaceXXX() refuse une key absente, alors que setXXX() peut l'ajouter.

Les bons noms réduisent les surprises à la lecture. Ils ne remplacent ni les déclarations PHP, ni les chemins d'autoload, ni les tests du contrat réel.

Phrase de mémorisation : « La casse dit la catégorie, le préfixe ou suffixe dit le rôle, et replace refuse ce que set accepte — mais un nom n'agit jamais seul. »
