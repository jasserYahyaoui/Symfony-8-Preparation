Module 17 — Cache HTTP

Symfony 8.0 · API PHP ≤ 8.4 · Twig ≤ 3.22. Préparation indépendante.

Comprendre ce module dans le projet

Deux lecteurs demandent la même version publique de /blog/42. Si une réponse conservée est encore réutilisable pour la nouvelle demande, pourquoi refaire tout le traitement ? Le cache HTTP raisonne sur des réponses et leurs représentations, pas sur une simple valeur calculée dans ArticleCatalog.

Le cours relie la politique annoncée par les en-têtes à l'emplacement du cache : navigateur, reverse proxy externe ou cache HTTP Symfony configuré. Un cache externe peut répondre avant PHP ; le cache Symfony peut éviter le HttpKernel interne et l'action. Cela ne signifie pas que tous les caches ont le même point d'entrée.

L'expiration décide si une copie est suffisamment fraîche. La validation conditionnelle, avec un identifiant de représentation ou une date de modification, demande si la copie correspond encore à l'état servi. Une réponse 304 permet de réutiliser cette copie : ce n'est pas une redirection. Les réglages de réponse et l'attribut Cache permettent d'exprimer la politique ; les variantes et le caractère public ou privé déterminent à qui une réponse peut être resservie. La fraîcheur seule ne rend pas partageable une page personnalisée.

Vous pourrez expliquer une seconde consultation de l'article : quelle copie est candidate, pourquoi elle est réutilisable, et si une revalidation doit atteindre l'application. L'objectif est de choisir une politique cohérente avec le contenu, sans promettre que le contrôleur s'exécute toujours ou qu'un cache connaît spontanément toute modification.

Revoyez le cache dans le protocole HTTP et la construction d'une Response. Le Cache applicatif traite une autre frontière : réutiliser le résultat d'un calcul à l'intérieur du code ne remplace pas la politique de réutilisation de la réponse complète.
