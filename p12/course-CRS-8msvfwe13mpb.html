Objectif

Construire un form, le lier à un object, et savoir quand un field ne doit pas l'être.

Question centrale : comment Symfony sait-il quel champ correspond à quelle propriété de mon objet, et que se passe-t-il quand ce n'est pas le cas ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le nom relie le field aux données.
  2. Le type et ses options définissent le comportement.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un formulaire est un échange entre des champs HTML et un objet PHP. Il faut donc décrire une fois quels champs existent et à quelle donnée chacun est relié.
  • Le piège de fond. Le lien champ ↔ propriété repose sur le nom du champ. Rien de magique : un nom qui ne correspond à rien fait échouer la lecture.
  • Ce que l'auteur veut que vous compreniez. Il y a trois leviers : data_class (quel objet), mapped (ce champ participe-t-il ?), property_path / inherit_data (relier ailleurs que sous son nom).
  • Pourquoi c'est à l'examen. Les questions portent sur le type deviné (guessers, repli TextType), sur data_class devinée ou non, et sur l'ordre de lecture des accessors.

Un form se décrit dans une class de type dès qu'il sert plus d'une fois. Chaque add() relie un field à une property par son nom ; data_class dit quelle class le form manipule. Un field sans property est déclaré mapped: false, ou relié ailleurs par property_path.

Le schéma

À retenir en priorité
  1. property_path redirige un field.
  2. inherit_data partage les données du parent.

Où en est-on ? Début du cours. Cette carte relie les 5 étapes qui suivent : (1) où construire, (2) add(), (3) data_class, (4) la correspondance nom ↔ property, (5) les champs hors mapping.

createForm(TaskType::class, $task)
      │
      ▼
 buildForm()  ── add('task') ── add('dueDate') ── add('agreeTerms', mapped:false)
      │               │              │                      │
      ▼               ▼              ▼                      ▼
   Form ───────► Task::$task   Task::$dueDate        (valeur propre à l'enfant)

Le dessin suivant détaille qui fait quoi : la factory résout les options, buildForm() ajoute les enfants, le mapper relie les enfants mappés à l'objet.

Bleu = construction/mapping, vert = données. La flèche de mapping résume lecture initiale et écriture à la soumission ; elle n'implique pas une validation réussie. agreeTerms doit avoir sa propre contrainte IsTrue si l'accord est obligatoire côté serveur.

L'exemple : un `TaskType`

Exemple concret

À retenir en priorité
  1. Le FormType se réutilise entre actions.
  2. Un builder local convient à un besoin ponctuel.

Où en est-on ? Avant le détail de chaque mécanisme, on regarde la classe complète la plus petite possible. Chaque ligne sera expliquée dans une section précise ci-dessous.

La branche /inscription emploierait un SignupType lié à SignupData, pas le modèle d'affichage ArticleView. Le type de tâche ci-dessous conserve le même mécanisme avec deux données mappées et une case indépendante. C'est un extrait de classe : ses imports, la classe Task et les contraintes d'accord restent à fournir pour une application exécutable.

class TaskType extends AbstractType
{
    public function buildForm(FormBuilderInterface $builder, array $options): void
    {
        $builder
            ->add('task', TextType::class)
            ->add('dueDate', DateType::class)
            ->add('agreeTerms', CheckboxType::class, ['mapped' => false]);
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['data_class' => Task::class]);
    }
}

Ce que Symfony voit :

Ligne Ce que Symfony en tire
add('task', TextType::class) un enfant nommé task, relié à Task::$task
add('dueDate', DateType::class) un enfant nommé dueDate, relié à Task::$dueDate
add('agreeTerms', …, ['mapped' => false]) un enfant qui n'est pas relié à Task
data_class => Task::class l'objet manipulé est de classe Task

Deux endroits pour le construire

Où en est-on ? Étape 1 sur 5. Avant de décrire les champs, une question de rangement : où écrire cette description ?

Une description réutilisable n'est pas le formulaire soumis lui-même. La factory utilise cette description et ses options pour construire une instance par traitement ; la Request sera prise en compte ensuite. Le GET d'inscription peut donc préparer un formulaire sans le soumettre et sans valider une saisie inexistante.

Besoin Où
un form jetable, une seule action $this->createFormBuilder($task)->add(…)->getForm()
un form réutilisé (recommandé) une class AbstractType, puis $this->createForm(TaskType::class, $task)

Pourquoi préférer la classe de type ? Parce qu'un même formulaire sert souvent à plusieurs actions (création, édition) et peut être testé, étendu et configuré (options) sans toucher au contrôleur.

CLASSE TaskType (description)         INSTANCE Form (un traitement)
┌───────────────────────────┐         ┌───────────────────────────┐
│ buildForm()  → les champs │ factory │ enfants construits        │
│ configureOptions()        │ ──────► │ données de CE traitement  │
│ (écrite une fois)         │         │ (une par requête)         │
└───────────────────────────┘         └───────────────────────────┘

🌍 In Real Life

La situation : le bureau d'inscription possède un modèle de fiche réutilisable, puis prépare une fiche pour chaque traitement. Le modèle ne contient pas les réponses d'un candidat particulier.

L’équivalent dans Symfony : une classe AbstractType décrit la construction et les options ; la factory et le builder produisent une instance de Form. La construction directe dans le contrôleur utilise les mêmes mécanismes sans extraire cette description.

Retour à la réalité technique : créer le formulaire ne le soumet pas, ne valide pas une saisie et ne crée pas de compte. Dans la branche habituelle GET d'inscription, on prépare une vue ; la soumission dépend ensuite du traitement de Request et de la méthode configurée. Le type réutilisable n'est pas un stockage des réponses.

🧠 Comment le mémoriser : « Modèle de fiche, puis fiche de traitement. » Image mentale : modèle vierge au-dessus de fiches individuelles. Question-réflexe : est-ce la description du formulaire ou une instance liée aux données courantes ?

⚠️ À ne pas confondre : FormType, builder, Form, soumission et création métier.

`add()` et ses trois arguments

Où en est-on ? Étape 2 sur 5. On ouvre la boîte buildForm() : chaque ligne est un appel à add(). Question : que signifient ses trois arguments, et que se passe-t-il si on en omet un ?

Pour l'email de SignupData, le nom sélectionne la donnée et le type organise son traitement et sa représentation. Déclarer ce type explicitement évite de dépendre d'un guesser non enregistré. L'inférence décrite ci-dessous dépend des extensions disponibles ; l'exception des enums ne signifie pas que tout type PHP est converti en type de champ.

add(nom, type, options). Le nom relie par défaut le champ à une propriété ; les options de mapping peuvent modifier cette correspondance.

->add( 'email' , EmailType::class , ['required' => true] )
         │              │                    │
         │              │                    └─ options : comportement
         │              └────────────────────── type : traitement + représentation
         └───────────────────────────────────── nom : adresse de la propriété

Si le type est omis ou null et qu'une data_class est disponible, FormBuilder demande à FormFactory de construire le champ pour cette propriété. La factory consulte les type guessers enregistrés. Dans le périmètre étudié, ValidatorTypeGuesser exploite les contraintes de validation chargées ; EnumFormTypeGuesser reconnaît une propriété typée par une enum. Ce dernier cas n'est pas une conversion générale de tous les types PHP en types de formulaire.

Sans guesser ou sans proposition de type, la factory choisit TextType. Sans data_class, FormBuilder choisit directement TextType lorsque le type est omis. Déclarer data_class ne déclenche aucune recherche Doctrine.

Dans le code 8.0, ce chemin est celui de FormBuilder::add() : si le type est null et que la data_class est null, TextType est choisi tout de suite ; sinon FormFactory::createBuilderForProperty() interroge les guessers et retombe sur TextType quand aucun n'a de proposition.

Pour l'email de SignupData, une contrainte Email peut donc fournir un indice au guesser Validator disponible ; écrire explicitement EmailType::class rend ce choix indépendant de l'inférence. Dans les deux cas, choisir le champ ne valide pas encore l'adresse soumise : les contraintes serveur devront être exécutées lors du traitement.

Pourquoi le type PHP (float, int…) ne suffit-il pas ? Parce que les guessers lisent des métadonnées (contraintes de validation, mapping de base de données, enum), pas la déclaration de type de la propriété. Un public float $price sans contrainte ni mapping ne donne aucune proposition : TextType.

🌍 In Real Life

La situation : chaque case de la fiche porte une adresse, un mode de saisie et des consignes. Si le mode manque, un agent équipé peut consulter les règles connues ; il ne devine pas arbitrairement toutes les intentions.

L’équivalent dans Symfony : add(nom, type, options) nomme l'enfant, choisit son type et règle son comportement. Le nom sert au mapping par défaut ; le type omis dépend des guessers enregistrés et des métadonnées accessibles.

Retour à la réalité technique : le repli décrit est TextType ; l'inférence d'enum n'est pas une conversion générale de tous les types PHP. Déclarer EmailType pour SignupData ne prouve pas qu'une adresse soumise satisfait les contraintes serveur. Les options mapped et property_path peuvent modifier le lien nominal.

🧠 Comment le mémoriser : « Adresse, outil, consignes pour chaque case. » Image mentale : trois mentions sur la marge d'un champ email. Question-réflexe : ai-je choisi explicitement le type ou dépend-il d'un guesser réellement disponible ?

⚠️ À ne pas confondre : nom de champ, type Form, type PHP et contrainte Validator.

`data_class`

À retenir en priorité
  1. Un object initial peut fournir la data_class.
  2. La déclaration explicite documente le modèle attendu.

Où en est-on ? Étape 3 sur 5. On a des champs ; il faut maintenant dire quel objet ils décrivent. C'est le rôle de data_class.

Choisir SignupData annonce la forme des données du formulaire. Cela n'injecte pas un service SignupData ni ne crée immédiatement un compte. Si les données initiales sont nulles, la construction éventuelle par empty_data appartient au traitement de soumission ; l'enregistrement métier viendra seulement après les contrôles requis.

Création Résultat
un Task passé, sans data_class déclarée getDataClass() vaut Task : devinée
data_class déclarée, sans object données initiales null ; à la soumission, le défaut empty_data peut créer new Task()
ni data_class ni object après soumission d'un form composé, un array tel que ['task' => 'x']

La déclarer fixe le modèle attendu. Le défaut empty_data crée un objet à la soumission si nécessaire, sauf form vide non requis ; son constructeur doit alors accepter zéro argument. Une closure empty_data personnalisée permet une autre construction : ce n'est pas le rôle de data_class seule.

Dans FormType::configureOptions(), la valeur par défaut de data_class est dérivée de l'objet passé en data, et le défaut de empty_data est une closure construite à partir de data_class.

createForm(TaskType::class, $task)          createForm(TaskType::class)
        │                                           │
 data_class deviné = Task                    data_class = Task (déclarée)
 données initiales = $task                   données initiales = null
        │                                           │
 soumission : $task est modifié              soumission : empty_data → new Task()
                                                       (constructeur sans argument)

Pourquoi data_class n'instancie-t-elle pas tout de suite ? Parce que lors du GET on n'a rien à construire : le formulaire est juste affiché vide. C'est à la soumission, quand il faut une destination pour les valeurs reçues, que empty_data fabrique l'objet.

🌍 In Real Life

La situation : l'en-tête « dossier d'inscription » annonce la forme du dossier attendu. Il ne prouve pas qu'un dossier existe déjà ; un dossier peut être fourni ou préparé au moment nécessaire selon une règle de création.

L’équivalent dans Symfony : data_class fixe la classe attendue, ou peut être déduite d'un objet initial. empty_data définit le traitement de données vides à la soumission et peut construire l'objet si les conditions s'y prêtent.

Retour à la réalité technique : déclarer data_class ne déclenche pas l'autowiring. Déclarer data_class ne déclenche aucune recherche Doctrine. Pour la construction par défaut décrite, la classe doit pouvoir être instanciée sans argument ; une closure empty_data permet une autre stratégie. Un formulaire composé sans classe ni objet peut produire un tableau. Dans tous les cas, objet obtenu ne signifie ni données valides ni compte enregistré.

🧠 Comment le mémoriser : « L'en-tête annonce le dossier, il ne le fabrique pas. » Image mentale : étiquette de classe devant un emplacement encore vide. Question-réflexe : qui fournit ou construit l'objet, et à quel moment ?

⚠️ À ne pas confondre : classe attendue, objet initial, empty_data, injection de service et persistance.

Le FormType est le formulaire vierge, le modèle le dossier à remplir. Sans object initial ni data_class, les réponses restent des notes indexées dans un array ; data_class nomme le type de dossier attendu.

La correspondance nom ↔ property

À retenir en priorité
  1. Le nom du field pilote le mapping.
  2. Une property privée exige un chemin d'accès utilisable.

Où en est-on ? Étape 4 sur 5. On sait quel objet : reste à savoir comment une valeur passe du champ dueDate à la propriété dueDate, et dans l'autre sens.

Le mapper doit lire les données initiales puis écrire les données soumises. Ce chemin utilise PropertyAccess, pas la résolution d'attribut Twig : ne transpose pas l'ordre « propriété avant getter » du rendu à ce mapping. Renommer un champ peut changer sa destination ; property_path permet de conserver explicitement le lien voulu.

Pour lire dueDate, PropertyAccess essaie : getDueDate(), isDueDate(), hasDueDate(), canDueDate(), une method dueDate(), et seulement ensuite la property publique. Pour écrire : setDueDate() ou la property publique. Une property privée sans accessor lève une NoSuchPropertyException.

LIRE  dueDate (affichage initial)       ÉCRIRE dueDate (soumission)
  1. getDueDate()                         1. setDueDate()
  2. isDueDate()                          2. propriété publique $dueDate
  3. hasDueDate()                         (sinon NoSuchPropertyException)
  4. canDueDate()
  5. dueDate()
  6. propriété publique $dueDate
  (sinon NoSuchPropertyException)

Comparaison de deux mécanismes qu'on confond :

Mapping Form (PropertyAccess) Résolution d'attribut Twig
Quand ? lire/écrire les données du formulaire {{ objet.attr }} dans un template
Ordre accessors d'abord, propriété publique ensuite propriété avant méthode (selon Twig)
Erreur typique NoSuchPropertyException variable/attribut inexistant

🌍 In Real Life

La situation : l'agent copie les données entre fiche et dossier en empruntant les accès autorisés du dossier. Une porte de lecture et une porte d'écriture peuvent être différentes ; un champ ne perce pas un tiroir privé fermé.

L’équivalent dans Symfony : le mapping standard s'appuie sur PropertyAccess pour lire les données initiales et reporter les données des enfants admissibles. Les accessors de lecture précèdent la propriété publique dans le comportement décrit ; l'écriture utilise ses propres accès.

Retour à la réalité technique : ce n'est pas l'ordre de résolution d'attribut Twig. Le mapping n'est pas une transaction qui attend nécessairement la validité globale : un objet peut déjà être modifié lorsque le formulaire s'avère invalide. Les enfants non mappés, désactivés ou non synchronisés ne suivent pas tous le même chemin d'écriture.

🧠 Comment le mémoriser : « Lire par la bonne porte, écrire par la bonne porte. » Image mentale : dossier avec entrées distinctes lecture et écriture. Question-réflexe : quel accès PropertyAccess utilise-t-il et le mapping doit-il intervenir pour cet enfant ?

⚠️ À ne pas confondre : PropertyAccess, lookup Twig, mapping, validation et transaction de stockage.

Le field non mappé

À retenir en priorité
  1. mapped: false exclut le binding au modèle.
  2. Le field conserve ses propres données.

Où en est-on ? Étape 5a sur 5. Que faire d'un champ qui n'a aucune propriété correspondante ? Si on ne dit rien, le mapper essaie quand même de lire une propriété qui n'existe pas.

L'accord aux conditions est une entrée du formulaire même s'il ne figure pas dans SignupData. mapped: false conserve sa valeur et ses contraintes propres ; il retire seulement sa participation au mapping du parent. Le lire ne suffit pas à exiger l'accord : une contrainte serveur doit imposer la valeur attendue.

Une case « j'accepte les conditions », un file téléversé : pas de property, donc 'mapped' => false lorsqu'aucune donnée correspondante n'est prévue. Sans cela, l'initialisation qui tente de lire la propriété peut échouer (elle peut être différée après la construction) : NoSuchPropertyException, « Can't get a way to read the property "agreeTerms" in class "Task" ». Sa valeur se lit par $form->get('agreeTerms')->getData().

mapped: true (défaut)                  mapped: false
 champ ◄──► propriété de l'objet        champ ◄─ ✂ ─► objet
 (lecture + écriture)                   valeur gardée par le champ lui-même
                                        lecture : $form->get('agreeTerms')->getData()

🌍 In Real Life

La situation : la fiche comporte une case d'accord traitée au guichet mais non recopiée dans le dossier principal. Ne pas recopier cette case ne signifie pas qu'on cesse de la lire ou de contrôler sa réponse.

L’équivalent dans Symfony : mapped: false retire l'enfant du mapping des données parentes. Sa donnée reste accessible sur l'enfant Form et ses contraintes propres peuvent être appliquées.

Retour à la réalité technique : pour imposer l'accord côté serveur, une contrainte adaptée telle qu'IsTrue reste nécessaire ; ni lecture de la valeur ni required HTML ne suffisent. Un upload peut être mappé si le modèle le prévoit : « fichier » ne signifie pas automatiquement « unmapped ». Le traitement métier explicite reste distinct.

🧠 Comment le mémoriser : « Non recopié ne veut pas dire non contrôlé. » Image mentale : case d'accord cochée au guichet hors du dossier principal. Question-réflexe : où lire cette valeur et quelle règle serveur doit-elle satisfaire ?

⚠️ À ne pas confondre : non mappé, non soumis, désactivé et non validé.

Ailleurs que sous son nom

Où en est-on ? Étape 5b sur 5, la dernière : le champ a une propriété correspondante, mais pas sous le même nom, ou le groupe de champs travaille sur l'objet du parent.

Un nom HTML stable peut devoir pointer vers une propriété renommée : property_path change cette adresse, sans créer un autre modèle. inherit_data répond plutôt au regroupement visuel de champs qui utilisent encore le modèle parent ; ne le confonds pas avec une propriété contenant un objet enfant distinct.

  • property_path : un field title avec property_path: 'name' sert $author->name ; 'profile.bio' descend dans un object imbriqué.
  • inherit_data: true sur un type : ses fields travaillent sur les données du parent — un AddressType écrit city sur l'Author lui-même.

Avant / après :

SANS property_path
  add('title')
    → cherche $author->title

AVEC property_path
  add('title', null, ['property_path' => 'name'])
    → lit/écrit $author->name
  add('bio', null, ['property_path' => 'profile.bio'])
    → $author->profile->bio

Comparaison de deux options proches :

property_path inherit_data
Portée un champ un type composé (groupe de champs)
Effet change l'adresse de la propriété le groupe utilise les données du parent
Exemple title → name AddressType écrit city sur Author
Objet enfant distinct ? non non (c'est justement la différence)

🌍 In Real Life

La situation : une case appelée « titre » peut renvoyer vers la rubrique « nom » du dossier. Un encadré « adresse » peut aussi regrouper plusieurs rubriques du même dossier, sans créer un second dossier.

L’équivalent dans Symfony : property_path change le chemin de lecture/écriture d'un champ ; inherit_data: true fait travailler le groupe sur les données parentes plutôt que sur un modèle enfant distinct.

Retour à la réalité technique : un chemin imbriqué suppose des données et accès compatibles ; il ne promet pas un chargement ORM automatique. Ces options appartiennent à Form. Pour une API JSON utilisant Serializer plutôt que Form, la correspondance des noms exige son mécanisme de sérialisation propre, puis une validation distincte ; property_path du formulaire ne configure pas le Serializer.

🧠 Comment le mémoriser : « Autre rubrique ou même dossier regroupé ? » Image mentale : flèche de renvoi face à un encadré sur la fiche. Question-réflexe : veux-je changer une destination, partager les données parentes ou traiter un objet enfant ?

⚠️ À ne pas confondre : property_path, inherit_data, modèle enfant et mapping du Serializer.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le nom du field n'est pas décoratif.

    Le nom du field n'est pas décoratif. Le renommer casse le binding. Pourquoi on se trompe : on pense que le nom n'est qu'une étiquette HTML, alors qu'il sert d'adresse de la propriété.

  • Voir l’explication : Les accessors passent avant la property publique

    Les accessors passent avant la property publique : un getter l'emporte. Pourquoi on se trompe : on transpose l'ordre de Twig, où la propriété passe avant la méthode.

  • Voir l’explication : Le type omis est deviné par les guessers

    Le type omis est deviné par les guessers, pas par le type PHP ; à défaut, TextType. Pourquoi on se trompe : un float appelle naturellement NumberType, mais personne ne lit ce type.

  • Voir l’explication : data_class se devine de l'object passé

    data_class se devine de l'object passé ; elle guide empty_data, mais n'instancie pas immédiatement un objet. Pourquoi on se trompe : le mot « class » évoque un new immédiat.

  • Voir l’explication : Un field sans property correspondante doit être déclaré non mappé.

    Un field sans property correspondante doit être déclaré non mappé. Pourquoi on se trompe : on croit que Form ignore silencieusement un champ inconnu de l'objet ; il lève NoSuchPropertyException.

  • Voir l’explication : mapped: false ne dispense pas de contrainte.

    mapped: false ne dispense pas de contrainte. Une case d'accord reste à valider (IsTrue) côté serveur.

  • Voir l’explication : data_class ≠ accès à la base ≠ autowiring.

    data_class ≠ accès à la base ≠ autowiring. Elle ne cherche rien en base et n'injecte aucun service.

Application

À retenir en priorité
  1. mapped: false exclut le binding au modèle.
  2. Le field conserve ses propres données.
  3. Le nom relie le field aux données.

À mémoriser

🧠 À retenir pour la certification :

  • Form réutilisé : class de type ; jetable : createFormBuilder().
  • add(nom, type, options) : le nom relie le field à la property.
  • Type omis : guessers, sinon TextType (toujours TextType sans data_class).
  • data_class : modèle déclaré ou deviné ; empty_data intervient à la soumission, pas comme constructeur immédiat.
  • Lecture : accessors d'abord (get, is, has, can, x()), puis property publique.
  • Field sans property : mapped: false ; autre path : property_path ; données du parent : inherit_data.

Moyen mnémotechnique : « Le nom est l'adresse ».

Phrase de mémorisation : « Chaque add() envoie une lettre à l'adresse du nom ; sans adresse, mapped: false ; adresse différente, property_path. »
