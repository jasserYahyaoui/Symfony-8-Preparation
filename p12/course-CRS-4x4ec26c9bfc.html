Objectif

Le test de /blog/42 utilise désormais les bons services. Il reste à préciser le visiteur simulé : quel hôte demande-t-il, quelle langue annonce-t-il, quelle préférence a-t-il enregistrée ? Ces entrées HTTP ne sont pas les options qui démarrent le kernel.

Question centrale : où règle-t-on quoi — le kernel, le visiteur, une seule requête, la session — et sous quel nom ?

L'essentiel

À comprendre

À retenir en priorité
  1. L'environment appartient au premier array.
  2. Les headers simulés appartiennent au second.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une requête de test doit ressembler à celle d'un vrai visiteur : bon hôte, langue, cookies, session. Symfony a donc plusieurs « endroits » où poser ces réglages, chacun avec sa portée.
  • Le piège de fond. Confondre les niveaux : options du kernel (environnement, debug), paramètres serveur du client (headers pour toutes les requêtes), paramètres serveur d'une requête (une seule fois), session (côté serveur) et cookies (côté client).
  • Ce que l'auteur veut que vous compreniez. Le tableau serveur de BrowserKit suit la convention CGI : X-Foo s'écrit HTTP_X_FOO. Et une session préparée doit être sauvegardée pour être vue.
  • Pourquoi c'est à l'examen. Ordre des deux arguments de createClient(), nommage CGI, 5ᵉ argument de request(), save(), cookie BrowserKit.

createClient() sépare les options du kernel des paramètres serveur par défaut du client. Le 5ᵉ argument de request() surcharge ces derniers pour un appel. Un header personnalisé s'y écrit sous son nom CGI : la convention de paramètres serveur utilise HTTP_, les majuscules et des soulignés à la place des tirets.

La session est un stockage côté serveur identifié par un cookie du client. Une préférence préparée dans un objet de session doit être sauvegardée et rattachée à ce client pour que la requête suivante la retrouve. Ni un header arbitraire ni une clé de session n'authentifie automatiquement un utilisateur.

Le schéma

À retenir en priorité
  1. La surcharge locale ne modifie pas le défaut.
  2. Les Requests suivantes peuvent retrouver l'ancienne valeur.

Où en est-on ? Début du cours : la carte de tous les réglages. Chaque case sera détaillée dans une section : createClient (partie 1), nommage CGI (partie 2), surcharge par requête, session (partie 3).

Lire la fusion de gauche à droite : un défaut réutilisable, puis une surcharge locale. Cela ne modifie pas les options du kernel déjà démarré.

Bleu : préparation ; ambre : conversion CGI ; vert : valeur visible. Le premier argument de createClient() règle le kernel, pas ces headers. CONTENT_TYPE et CONTENT_LENGTH sont des exceptions au préfixe HTTP_. La session suit un autre mécanisme : getSession() prépare la session et son cookie, set() modifie l'objet, puis save() persiste pour la requête suivante.

Les quatre « endroits » à ne pas mélanger :

┌───────────────────┬──────────────────────┬─────────────────────────────┐
│ Où                │ Portée               │ Exemple                     │
├───────────────────┼──────────────────────┼─────────────────────────────┤
│ createClient(1er) │ démarrage du kernel  │ ['environment' => 'test']   │
│ createClient(2e)  │ toutes les Requests  │ ['HTTP_HOST' => 'a.com']    │
│ request(…, 5e)    │ cette Request seule  │ ['HTTP_X_FOO' => '1']       │
│ session / cookies │ état serveur/client  │ set() + save() ; CookieJar  │
└───────────────────┴──────────────────────┴─────────────────────────────┘

L'exemple

Exemple concret

À retenir en priorité
  1. Le nom suit la convention CGI.
  2. Majuscules et underscores remplacent la forme HTTP.

Où en est-on ? Un exemple unique rassemble trois réglages (défaut client, header ponctuel, session) avant le détail. Code minimal d'abord, explication ensuite.

Dans une méthode de WebTestCase, avec la variante /api/blog/42 et les sessions de test configurées, le header ci-dessous sert uniquement à observer le nom reçu. abc est une valeur fictive, pas un vrai secret ni une preuve de connexion :

$client = static::createClient([], [                 // 1ᵉʳ : kernel ; 2ᵉ : serveur
    'HTTP_HOST' => 'en.example.com',                  // toutes les Requests
]);

$client->request('GET', '/api/blog/42', [], [], [
    'HTTP_X_SESSION_TOKEN' => 'abc',                  // X-Session-Token, une fois
]);

$session = $client->getSession();
self::assertNotNull($session);
$session->set('preferred_locale', 'fr');
$session->save();                                     // sinon, invisible

La requête /api/blog/42 voit X-Session-Token: abc. Une nouvelle requête faite après save() peut lire preferred_locale = fr ; le changement n'affecte pas rétroactivement la requête achevée. Il faut une politique applicative pour appliquer cette préférence à la locale. Pour un vrai formulaire CSRF, préférer sa soumission avec le token rendu plutôt que fabriquer une clé interne.

Lecture ligne par ligne :

Ligne Ce que Symfony fait
createClient([], [...]) 1ᵉʳ tableau vide : kernel par défaut ; 2ᵉ : paramètres serveur durables
request(..., [], [], [...]) 3ᵉ params, 4ᵉ fichiers, 5ᵉ serveur : valable une fois
getSession() crée la session et prépare son cookie
set() puis save() écrit puis persiste ; sans save(), invisible

Les deux arguments de `createClient()`

À retenir en priorité
  1. Ce sont des options du kernel.
  2. Ne pas les mélanger aux parameters serveur.

Où en est-on ? Étape 1 sur 3 : à quoi servent les deux tableaux de createClient() ? Les inverser est une erreur d'examen classique.

🌍 In Real Life

La situation : la répétition au restaurant choisit d'abord la salle équipée pour le test, puis les préférences du visiteur qui demande le menu du blog.

L’équivalent dans Symfony : salle et équipement → options environment/debug du Kernel ; préférences de visite → paramètres serveur du client.

Retour à la réalité technique : les deux tableaux de createClient() alimentent des niveaux distincts. Un header HTTP ne choisit pas l'environnement de l'application et ne recompile pas son conteneur.

🧠 Comment le mémoriser : « Préparer le lieu, puis le visiteur. » Image mentale : deux fiches, installation et demande. Question-réflexe : ce réglage concerne-t-il le Kernel ou la requête simulée ?

⚠️ À ne pas confondre : paramètres serveur d'une requête et variables d'environnement du processus.

Le premier porte les options du kernel — environment, debug, celles de bootKernel(). Le second porte les parameters serveur, donc les headers, pour toutes les Requests du client.

WebTestCase utilise les options pour démarrer le kernel, récupère test.client, puis lui transmet les paramètres serveur. Mettre un header dans les options de boot ne le convertit donc pas en entrée HTTP.

Pourquoi deux tableaux ? Parce que deux objets différents sont configurés, à deux moments différents :

createClient($options, $server)
   ├─ bootKernel($options)           → le KERNEL (environment, debug)
   ├─ get('test.client')             → le CLIENT (KernelBrowser)
   └─ $client->setServerParameters($server)   → les headers du client

Dans un test indépendant du précédent, avec Symfony 8.0/PHPUnit 11.5 :

$client = static::createClient(
    ['environment' => 'test'],
    ['HTTP_ACCEPT_LANGUAGE' => 'fr'],
);
$client->request('GET', '/blog/42');
self::assertSame('fr', $client->getRequest()->headers->get('Accept-Language'));

Cette assertion confirme le header de la requête reçue. Elle ne prouve pas une traduction automatique du titre ; la politique de locale et les traductions restent à configurer et à tester séparément.

La règle de nommage des headers

À retenir en priorité
  1. Certains headers CGI ont un nom spécial.
  2. Ne pas préfixer systématiquement sans vérifier.

Où en est-on ? Étape 2 sur 3 : on sait où poser un header, il faut maintenant savoir sous quel nom. Pourquoi X-Session-Token n'arrive-t-il pas si on l'écrit tel quel ?

Un header personnalisé suit la RFC 3875 : tirets → soulignés, majuscules, préfixe HTTP_. X-Session-Token devient HTTP_X_SESSION_TOKEN.

Pourquoi ? Le tableau passé à BrowserKit imite $_SERVER d'un vrai serveur : c'est la convention CGI, où un serveur web transforme chaque header reçu en variable HTTP_.... Symfony refait ensuite le chemin inverse pour reconstruire $request->headers.

Avant / après :

header HTTP voulu :   X-Session-Token: abc
clé du tableau    :   HTTP_X_SESSION_TOKEN   ← tirets → _, majuscules, préfixe HTTP_
côté Request      :   $request->headers->get('X-Session-Token')  → "abc"
Key passée au client X-Session-Token côté serveur
HTTP_X_SESSION_TOKEN abc
X-Session-Token null
X_SESSION_TOKEN null
  • Les headers standards de CGI échappent au préfixe : CONTENT_TYPE, sans préfixe, arrive bien comme Content-Type.
  • HTTP_AUTHORIZATION arrive comme Authorization ; AUTHORIZATION donne null.
  • Sans réglage, le user agent vaut Symfony BrowserKit.

La table concerne le tableau serveur de BrowserKit, pas $request->headers->get('X-Session-Token'), qui utilise le nom HTTP. De même, HTTP_AUTHORIZATION transporte une donnée ; l'authenticator configuré doit encore la vérifier. N'insérer que des credentials fictifs dans les exemples et diagnostics.

Par Request plutôt que par client

À retenir en priorité
  1. Les parameters de form sont ailleurs.
  2. La position évite de confondre body et headers.

Où en est-on ? Intermède entre les étapes 2 et 3 : un réglage pour une seule requête, sans changer le défaut du client.

🌍 In Real Life

La situation : le visiteur du restaurant demande habituellement la carte française, mais une fois la carte anglaise. Cette exception ne change pas sa préférence habituelle.

L’équivalent dans Symfony : préférence habituelle → défaut du client ; demande ponctuelle → cinquième argument de request() ; visite suivante sans exception → défaut réutilisé.

Retour à la réalité technique : les paramètres de l'appel surchargent ceux du client pour cette requête. Le cas d'hôte décrit suppose une URI relative ; une URI absolue porte elle-même des informations d'adresse.

🧠 Comment le mémoriser : « Une exception n'efface pas le défaut. » Image mentale : pense-bête posé puis retiré de la fiche du visiteur. Question-réflexe : cette valeur a-t-elle été changée sur le client ou seulement sur cet appel ?

⚠️ À ne pas confondre : surcharge ponctuelle et modification persistante de configuration.

L'array de la Request est fusionné par-dessus celui du client, pour cette Request seulement. Pour des URI relatives comme /blog/42, client créé avec HTTP_HOST a.example.com :

Request Host reçu
5ᵉ argument HTTP_HOST b.example.com b.example.com
la suivante, sans 5ᵉ argument a.example.com
après setServerParameter('HTTP_HOST', 'c.example.com') c.example.com

setServerParameter() modifie le client pour la suite du test.

En interne, AbstractBrowser::request() fait array_merge($this->server, $server) : les clés du 5ᵉ argument écrasent celles du client, mais ne les modifient pas (le tableau du client reste intact). setServerParameter(), lui, modifie ce tableau du client.

Le code fusionne d'abord les deux tableaux, puis construit l'URI et la requête. Une URI absolue porte déjà son hôte et son schéma : ne pas généraliser ce tableau sans examiner la requête résultante. Le troisième argument contient les paramètres, le quatrième les fichiers, le cinquième les paramètres serveur ; le sixième peut porter le corps brut. Placer HTTP_HOST dans les paramètres de formulaire n'agit pas sur le Host.

Préparer la session

À retenir en priorité
  1. L'écriture doit être persistée.
  2. Le client doit retrouver la même session.

Où en est-on ? Étape 3 sur 3 : l'état côté serveur. Pourquoi une valeur de session posée dans le test peut-elle être invisible à la requête suivante ? Parce qu'il faut la sauvegarder.

🌍 In Real Life

La situation : le vestiaire du restaurant conserve une fiche ; le visiteur porte seulement son ticket. Une correction doit être rangée pour être retrouvée lors de la visite suivante.

L’équivalent dans Symfony : fiche conservée → données de session ; ticket → cookie d'identifiant ; rangement → sauvegarde des écritures de session préparées par le test.

Retour à la réalité technique : getSession() nécessite la factory configurée et prépare le lien avec le cookie. Relire le même objet en mémoire ne démontre pas que la prochaine requête retrouvera les données dans le stockage.

🧠 Comment le mémoriser : « Fiche sauvegardée et ticket correspondant. » Image mentale : ticket en poche, fiche dans le casier. Question-réflexe : la prochaine requête peut-elle retrouver cette session et son écriture ?

⚠️ À ne pas confondre : donnée de session serveur et simple cookie de préférence envoyé par le client.

En Symfony 8.0, KernelBrowser::getSession() retourne null sans session.factory. Sinon, il crée une session, reprend l'identifiant du cookie existant lorsqu'il le trouve, la démarre et prépare le cookie s'il manque. Le test doit ensuite sauvegarder ses écritures.

getSession()
   ├─ pas de session.factory ? ──► null
   ├─ cookie de session déjà dans le CookieJar ? ──► reprend son identifiant
   ├─ démarre la session
   └─ pas de cookie ? ──► en crée un avec l'identifiant de session

Le tableau suppose une clé initialement absente et le cycle normal où la requête relit le stockage persistant ; il ne décrit pas la simple relecture de l'objet encore en mémoire :

Avant la Request Valeur lue par le controller
set('k', 'unsaved') null
set('k', 'saved') puis save() saved
set + save() avant toute Request lue aussi

Pour vérifier réellement la préférence du lecteur, la fixture suivante expose GET /test/preference uniquement dans la configuration de test. Elle lit la session sans prétendre changer la langue de tout le blog :

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

final class PreferenceProbeController
{
    public function __invoke(Request $request): Response
    {
        return new Response($request->getSession()->get('preferred_locale', 'unset'));
    }
}

Après enregistrement de cette route et de ce contrôleur de fixture, avec la session activée, le test associé est :

<?php
use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

final class PreferenceSessionTest extends WebTestCase
{
    public function testReadsPreparedSession(): void
    {
        $client = self::createClient();
        $session = $client->getSession();
        self::assertNotNull($session);
        $session->set('preferred_locale', 'fr');
        $session->save();

        $client->request('GET', '/test/preference');
        self::assertResponseIsSuccessful();
        self::assertSame('fr', $client->getResponse()->getContent());
    }
}

Le corps attendu fr prouve la relecture côté contrôleur ; sans préparation, la fixture renvoie unset. Un objet Session indépendant sans le cookie correspondant ne garantit pas cette continuité. Pour CSRF, conserver le vrai formulaire, son token et sa session : ne pas fabriquer une clé interne _csrf/... comme solution générale. Aucun kernel de fixture ni test PHPUnit n'est exécuté par ce cours.

Les cookies

À retenir en priorité
  1. Le cookie de test appartient à BrowserKit.
  2. Ne pas confondre avec le cookie HttpFoundation de Response.

Où en est-on ? Complément à la session : la partie client du couple « ticket + fiche ». Le cookie est ce que le client renvoie, pas ce que le serveur conserve.

$client->getCookieJar()->set(new Cookie('flavor', 'choco')) — le Cookie de BrowserKit — et la Request suivante porte le cookie flavor.

La classe complète est Symfony\Component\BrowserKit\Cookie, distincte de Symfony\Component\HttpFoundation\Cookie, employée pour construire les cookies d'une réponse. Le CookieJar sélectionne les cookies pertinents pour l'URI : expiration, domaine, chemin et HTTPS pour les cookies secure. Un cookie de préférence n'est pas une valeur enregistrée dans la session, et ne devient pas fiable parce que le client l'envoie.

Cookie BrowserKit Cookie HttpFoundation
Rôle simuler un cookie envoyé par le client construire un cookie de réponse
Namespace Symfony\Component\BrowserKit\Cookie Symfony\Component\HttpFoundation\Cookie

Voir les exceptions

À retenir en priorité
  1. La modification est locale au client.
  2. L'application garde son traitement normal.

Où en est-on ? Dernier réglage du client : que devient une exception levée pendant la requête ? Par défaut, HttpKernel la convertit en page d'erreur ; on peut demander au test de la voir.

$client->catchExceptions(false) demande au traitement du kernel de laisser remonter les exceptions au test plutôt que de les convertir par son traitement habituel. Le code métier et la configuration de production ne sont pas modifiés, mais le chemin d'observation du test l'est. Une réponse explicitement retournée avec le statut 500 n'est pas une exception : ce réglage ne la transforme pas en throwable.

Le client est le service test.client, fourni lorsque framework.test est activé dans l'environnement choisi. Le nom test seul n'invente pas ce service. Pour tester une page d'erreur personnalisée, garder le traitement des exceptions ; pour diagnostiquer l'origine d'une exception, la laisser remonter peut être plus utile.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La modification concerne le client.
  2. Une surcharge de request() reste ponctuelle.
  • Voir l’explication : createClient() prend d'abord les options du kernel, ensuite les headers.

    createClient() prend d'abord les options du kernel, ensuite les headers. Pourquoi on se trompe : on pense « client = headers d'abord » ; or le kernel doit être démarré avant le client.

  • Voir l’explication : Un header personnalisé devient HTTP_ + majuscules + soulignés.

    Un header personnalisé devient HTTP_ + majuscules + soulignés. Pourquoi on se trompe : X-Session-Token « semble » correct tel quel, et ne produit aucune erreur, seulement null côté serveur.

  • Voir l’explication : Les headers de Request sont le cinquième argument

    Les headers de Request sont le cinquième argument de request(). Pourquoi on se trompe : le 3ᵉ argument (paramètres) est le premier tableau visible.

  • Voir l’explication : $session->save() persiste la préparation

    $session->save() persiste la préparation avant sa relecture dans la requête suivante ; le cookie doit identifier cette même session.

  • Voir l’explication : catchExceptions(false) ne réécrit pas le métier ni la production

    catchExceptions(false) ne réécrit pas le métier ni la production, mais change la propagation des exceptions dans le test.

Fiche express

À mémoriser

À retenir en priorité
  1. Le header suit la convention CGI du client.
  2. AUTHORIZATION seul n'est pas équivalent.

Le test prépare maintenant des entrées observables, pas des suppositions : configuration du kernel, défauts HTTP, surcharge ponctuelle, puis session persistée et cookie correspondant.

🧠 À retenir pour la certification :

  • createClient() : options du kernel, puis parameters serveur.
  • Header personnalisé : HTTP_ + MAJUSCULES + _.
  • CONTENT_TYPE échappe au préfixe.
  • 5ᵉ argument de request() : une Request, prioritaire.
  • setServerParameter() pour la suite du test.
  • save() après set() en session.
  • catchExceptions(false) : propagation au test, pas transformation d'une réponse 500 en exception.

Moyen mnémotechnique : « Kernel, puis serveur ; HTTP_ en majuscules ; save ».

Phrase de mémorisation : le kernel d'abord, le visiteur ensuite ; un header s'écrit en CGI (HTTP_X_FOO), et une session ne se voit qu'une fois sauvée.

createClient(kernel, serveur) ; X-Foo-Bar → HTTP_X_FOO_BAR
(CONTENT_TYPE à part) ; request(…, 5ᵉ) l'emporte une fois
setServerParameter() pour la suite ; session : set + save
cookies : getCookieJar() ; catchExceptions(false)

Le cours inspection de la requête et de la réponse vérifie ce qui a réellement traversé cette frontière.
