Objectif

Une page en français doit devenir une page en anglais sans toucher au template. Ce cours explique comment : le template ne contient plus le texte, il contient une clé, et un service (le translator) échange la clé contre la phrase de la bonne langue. On voit ensuite ce que le filter et le tag font différemment, comment on gère le plural, et ce que devient un message préparé à l'avance.

Traduire depuis un template, gérer le plural et savoir ce que le filter et le tag font différemment. L'organisation des catalogues et la détection de la locale appartiennent aux Module 16 — Internationalisation et traduction et Module 05 — Routage.

L'essentiel

À comprendre

À retenir en priorité
  1. Le suffixe active l'interprétation MessageFormat.
  2. Les emplacements ICU utilisent des accolades.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Séparer le texte (qui change selon la langue) de la structure (qui ne change pas).
  • Le piège de fond. Trois outils qui se ressemblent mais n'ont ni le même ordre d'arguments, ni la même règle d'escaping, ni la même façon de remplir les emplacements.
  • Ce que l'auteur veut que vous compreniez. Le plural n'est pas un « s » : c'est un format de catalogue (ICU) qu'on active par le nom du fichier.
  • Pourquoi c'est à l'examen. Les QCM testent strtr (%name% ≠ name), la syntaxe du tag, le %% et le suffixe +intl-icu.

Twig traduit avec un filter, |trans, un tag, {% trans %}, et une function, t(), qui crée un message traduit plus tard. Ils diffèrent par l'ordre des arguments, l'escaping et les emplacements. Le plural passe par ICU, dans un catalogue suffixé +intl-icu.

filter  {{ 'cle'|trans(params, domain, locale, count) }}   traduit maintenant
tag     {% trans with … from … into … %}texte{% endtrans %} traduit maintenant
t()     {{ t('cle', params, domain)|trans }}                traduit plus tard

Le schéma

Où en est-on ? Vue d'ensemble avant le détail : on suit un message de l'appel |trans jusqu'au texte affiché. Chaque losange est une question que Symfony se pose ; chaque section suivante détaille une de ces questions.

'user.greeting'|trans(...)
   ▼
message = objet traduisible ?  ── oui ─▶ il se traduit lui-même (locale = 2e arg)
   │ non
   ▼
2e argument = array ?  ── non ─▶ TypeError (vue dans le template : RuntimeError)
   │ oui
   ▼
domain ? argument, sinon trans_default_domain, sinon « messages »
   ▼
catalogue +intl-icu ?  ── oui ─▶ ICU (MessageFormat)   ── non ─▶ strtr / barres
   ▼
texte → autoescape de Twig (filter) → affichage

Ambre = sélection, bleu = traduction. Les flèches sont des transferts de données ; le filtre ne lit pas lui-même les fichiers YAML. Pour une page HTML avec autoescape actif, Twig échappe le texte obtenu après |trans.

Le filter

À retenir en priorité
  1. Les parameters précèdent domain et locale.
  2. Les named arguments rendent l'appel moins ambigu.

Où en est-on ? Étape 1 : la forme de base. On sait qu'un template contient une clé ; voyons exactement ce qu'on passe au filter et dans quel ordre.

La locale a été choisie avant le rendu de l'article. Pour un bouton « Lire », le template transmet une clé au translator, qui cherche dans le domaine et la locale sélectionnés. Il ne traduit pas automatiquement le texte libre d'ArticleView ; les messages du catalogue sont préparés à cet effet.

<p>{{ 'user.greeting'|trans({'%name%': user.name}) }}</p>
<p>{{ 'checkout.total'|trans({}, 'store') }}</p>
<p>{{ 'legal.notice'|trans({}, 'messages', 'de') }}</p>
<p>{{ 'checkout.total'|trans(domain: 'store') }}</p>
  • Signature : trans(arguments = [], domain = null, locale = null, count = null). Domain omis : messages ; locale omise : la locale courante ; count renseigne %count%.
  • Les named arguments évitent l'array vide : trans(domain: 'store').
  • Le deuxième argument doit être un array. Une string n'y est admise que si le message est un object traduisible — elle désigne alors la locale. Sur une string ordinaire, |trans('store') lève une TypeError, que le template reçoit dans une RuntimeError.

Pourquoi cet ordre (paramètres, domain, locale) ? Parce que le cas le plus fréquent est « une clé + des valeurs » ; les paramètres viennent donc en premier, et le domaine, rarement utile, après. D'où le piège : on écrit |trans('store') en pensant désigner le domaine, comme on pense « à quel dossier ? » avant « avec quelles valeurs ? ».

{{ 'checkout.total'|trans('store') }}
                         └─ string ordinaire en 2e position → TypeError
{{ 'checkout.total'|trans({}, 'store') }}   → OK (array vide, puis domain)
{{ 'checkout.total'|trans(domain: 'store') }} → OK (named argument)

🌍 In Real Life

La situation : l'imprimerie conserve des modèles de salutations classés par collection et par langue. On lui donne la référence du modèle et le nom du destinataire ; elle ne traduit pas spontanément tout le manuscrit reçu.

L’équivalent dans Symfony : |trans transmet message, paramètres, domaine et locale au translator. Le domaine sélectionne une collection de messages ; la locale choisit la langue selon la configuration et les replis disponibles.

Retour à la réalité technique : le filtre ne lit pas directement chaque fichier YAML et n'est pas un service de traduction libre. Pour une chaîne ordinaire, son premier argument explicite est le tableau de paramètres, pas le domaine. Le domaine explicite prime sur le défaut du template ; sinon le défaut usuel est messages.

🧠 Comment le mémoriser : « Référence, données, collection, langue. » Image mentale : fiche de commande devant des casiers multilingues. Question-réflexe : ai-je fourni les paramètres dans la bonne case et choisi le bon domaine ?

⚠️ À ne pas confondre : identifiant de message, texte métier libre, domaine et locale.

Le catalogue est un guide de conversation : domain choisit l'onglet, locale l'édition, la key l'entrée stable. Changer la formulation n'exige donc pas de renommer la key dans tous les templates.

Repère — Échappé ou non :

Question: Do the trans filter and trans tag escape output identically?

Answer: No. The filter output is escaped; the tag output is not automatically escaped.

Le filter conserve l'auto-escaping. Le tag nécessite de maîtriser son contenu et ses parameters.

Les emplacements

À retenir en priorité
  1. Le remplacement doit viser la key exacte.
  2. name ne remplace pas proprement %name% si les délimiteurs restent dans le texte.

Où en est-on ? Étape 2 : une clé stable, mais une phrase qui contient une valeur variable (le nom du lecteur). Comment la valeur entre-t-elle dans la phrase ?

La confirmation d'inscription peut saluer le nom saisi sans construire une clé différente pour chaque lecteur. Garde une clé stable et transmets le nom comme paramètre. Hors ICU, le remplacement est textuel et exact : les délimiteurs font partie de la clé de remplacement, pas d'une syntaxe qui serait automatiquement reconnue.

Hors format ICU, Symfony remplace les emplacements par strtr(). Les pourcents de %name% sont une convention : #name# ou {name} marchent aussi, pourvu que la key corresponde exactement. Avec l'array {'name': 'Ada'} et le message Bonjour %name%, on obtient Bonjour %Ada%.

Mécanisme : strtr($message, $parametres) parcourt le message et remplace chaque clé du tableau, telle quelle, par sa valeur. Il ne connaît pas la notion d'« emplacement ».

message :  Bonjour %name%
tableau :  {'name': 'Ada'}          clé = « name »
strtr   :  cherche « name » dans le message → le trouve entre les %
résultat:  Bonjour %Ada%            les % restent : ils ne faisaient pas partie
                                    de la clé

tableau :  {'%name%': 'Ada'}        clé = « %name% » (pourcents compris)
résultat:  Bonjour Ada

Pourquoi la mauvaise réponse est plausible : on croit que Symfony « sait » que %…% marque un emplacement, comme dans sprintf. Ce n'est qu'une convention d'écriture.

🌍 In Real Life

La situation : un publipostage remplace exactement l'étiquette imprimée sur le modèle. Demander de remplacer seulement « name » dans « %name% » laisse les deux pourcents autour du nom.

L’équivalent dans Symfony : hors ICU, le remplacement textuel par strtr() cherche les clés exactes du tableau. Pour Bonjour %name%, la clé %name% remplace toute l'étiquette ; name ne remplace que son intérieur.

Retour à la réalité technique : les pourcents sont une convention du message non ICU, pas une grammaire universelle du translator. Une clé stable avec paramètres évite de fabriquer un identifiant par destinataire. Ce remplacement ne valide ni n'échappe la donnée.

🧠 Comment le mémoriser : « Remplacer toute l'étiquette, bordures comprises. » Image mentale : ciseaux entourant %name% en entier. Question-réflexe : ma clé de remplacement correspond-elle exactement au texte du modèle ?

⚠️ À ne pas confondre : substitution textuelle, paramètre ICU et échappement de sortie.

Le tag

À retenir en priorité
  1. Le domain par défaut a une portée locale.
  2. Un include conserve sa propre configuration de domain.

Où en est-on ? Étape 3 : même travail que le filter, mais avec une autre syntaxe — un bloc de texte entouré de mots-clés. Le tag est plus rigide : ordre imposé, corps textuel uniquement.

Le tag prépare un message textuel avec ses emplacements, pas un fragment Twig à exécuter dans le message. Passer explicitement le nom via with évite une dépendance cachée au contexte du layout. Si la carte incluse emploie un autre domaine, elle doit le déclarer ou le passer elle-même.

{% trans with {'%name%': 'Fabien'} from 'app' into 'fr' %}Hello %name%{% endtrans %}
  • count, with, from, into, dans cet ordre ; un mot hors de place est une SyntaxError.
  • Le body est du texte simple : {{ name }} dans le body est une SyntaxError ; la notation %name% est obligatoire.
  • Un emplacement absent de with est lu dans le contexte (TransNode) : %name% vaut la variable name — erreur sous strict_variables si elle n'existe pas.
  • Un pourcent littéral se double : %percent%%%.

{% trans_default_domain 'app' %} fixe le domain du template courant seul : un template inclus garde messages.

Pourquoi un corps « texte simple » ? Le tag transforme le corps en clé de catalogue : il a besoin d'une chaîne figée, pas d'une expression évaluée à l'exécution. D'où %name% plutôt que {{ name }}.

Comparaison filter / tag :

filter \|trans tag {% trans %}
Message clé ou texte (string) corps du tag, texte simple
Paramètres 1er argument (array) with {…}
Ordre paramètres, domain, locale, count count, with, from, into
Emplacement absent reste tel quel lu dans le contexte
Autoescape oui non

🌍 In Real Life

La situation : une machine à composer accepte une fiche ordonnée : quantité, données, collection, langue. Le corps est le modèle à traduire, pas une seconde machine dans laquelle insérer des commandes.

L’équivalent dans Symfony : le tag trans impose l'ordre count, with, from, into. Ses emplacements %name% peuvent recevoir une valeur explicite ou être reliés au contexte par TransNode ; son corps n'accepte pas une interpolation Twig {{ name }} ordinaire.

Retour à la réalité technique : l'inférence depuis le contexte concerne les emplacements reconnus par le tag ; elle ne rend pas les pourcents obligatoires pour toute substitution explicitement fournie au translator. trans_default_domain est local au template compilé : un include ne reçoit pas automatiquement ce choix. Une variable implicite absente peut échouer en mode strict.

🧠 Comment le mémoriser : « Fiche ordonnée, modèle textuel, domaine local. » Image mentale : fiche en quatre cases devant une feuille sans commandes imbriquées. Question-réflexe : quelles données et quel domaine mon fragment déclare-t-il lui-même ?

⚠️ À ne pas confondre : syntaxe du tag, remplacement du translator et contexte transmis par include.

Échappé ou non

À retenir en priorité
  1. Le filter conserve l'auto-escaping.
  2. Le tag nécessite de maîtriser son contenu et ses parameters.

Où en est-on ? Étape 4 : le texte est traduit. Reste une question de sécurité : qui l'échappe avant de l'écrire dans la page HTML ?

Un nom de lecteur peut contenir des caractères HTML même après validation de l'inscription. Avec le filtre et l'autoescape HTML actif, le texte traduit est échappé à la sortie. Avec le tag, cette protection n'est pas appliquée : une traduction n'est donc pas une frontière de confiance entre saisie et HTML.

Le résultat du filter suit l'autoescaping du template ; le tag ne l'applique pas. Préférer {{ message|trans }} pour du texte ordinaire. |trans|raw désactive cette protection : ne l'employer que pour du HTML de confiance, avec paramètres non fiables échappés pour leur contexte. Traduire n'assainit ni le catalogue ni ses paramètres.

filter :  {{ msg|trans(...) }}  ─▶ résultat ─▶ autoescape Twig ─▶ HTML sûr
tag    :  {% trans %}…{% endtrans %} ─▶ résultat ─▶ écrit tel quel (pas d'autoescape)
raw    :  {{ msg|trans|raw }}   ─▶ autoescape désactivé volontairement

Pourquoi c'est un piège : on pense que « le catalogue est écrit par nous, donc sûr ». Mais les paramètres (le nom saisi par un lecteur) entrent dans la phrase : c'est eux qui peuvent contenir du HTML.

🌍 In Real Life

La situation : traduire une invitation et préparer son impression sont deux métiers. Un nom correctement saisi peut contenir des signes que l'imprimeur doit reproduire comme du texte, et non comme des instructions de mise en page.

L’équivalent dans Symfony : le filtre trans rend une valeur soumise à l'autoescape actif ; le tag trans n'applique pas cette protection au résultat. Le nom validé à l'inscription reste une donnée à traiter selon le contexte de sortie.

Retour à la réalité technique : traduction et Validator ne remplacent pas l'échappement HTML. Pour du texte ordinaire, préfère le filtre avec autoescape approprié ; raw retire cette protection. Un catalogue de confiance ne rend pas automatiquement fiables ses paramètres.

🧠 Comment le mémoriser : « Traduire les mots, protéger leur impression. » Image mentale : traducteur puis poste d'impression séparé. Question-réflexe : qui échappe le résultat final et ses données dans ce contexte ?

⚠️ À ne pas confondre : traduction, validation de saisie, confiance du catalogue et sécurité du HTML produit.

Le plural

Où en est-on ? Étape 5 : « 1 commentaire », « 2 commentaires », « aucun commentaire ». Une simple substitution ne suffit plus : il faut choisir une phrase selon un nombre.

Le compteur de commentaires de l'article doit choisir une phrase, pas simplement ajouter un « s ». Le catalogue ICU porte les règles de message et la locale détermine les catégories ; le template fournit le nombre. Le suffixe du catalogue sélectionne ce format et ne doit pas être ajouté comme un correctif aléatoire à un message legacy.

La documentation 8.0 traite plural, genre et formats par ICU MessageFormat : le file de catalogue porte le suffixe +intl-icu — messages+intl-icu.fr.yaml —, et les emplacements s'écrivent {name}. Sans le suffixe, les accolades ne sont pas interprétées.

La syntaxe à barres — '{0} Aucun|{1} Un|]1,Inf[ %count% résultats' — sélectionne d'après %count%. La documentation la dit legacy ; elle garde les intervalles personnalisés, qu'ICU n'a pas.

Mécanisme : le nom du fichier décide du lecteur. Le translator choisit le formateur d'après le suffixe du domaine.

messages.fr.yaml              → formateur classique : strtr + syntaxe à barres
messages+intl-icu.fr.yaml     → ICU MessageFormat : {name}, plural, select
Classique (legacy) ICU
Fichier messages.fr.yaml messages+intl-icu.fr.yaml
Emplacement %name% (clé exacte) {name}
Plural barres {0} …\|{1} …\|]1,Inf[ … d'après %count% {n, plural, one {…} other {…}}
Intervalles personnalisés oui non

🌍 In Real Life

La situation : un atelier reçoit soit une fiche de substitutions simples, soit une fiche de phrases conditionnelles. Le même texte à accolades ne peut pas être traité correctement si l'on choisit le mauvais lecteur.

L’équivalent dans Symfony : le catalogue +intl-icu active le traitement ICU MessageFormat, avec paramètres et branches grammaticales. Le template fournit le nombre ; le catalogue et la locale déterminent le message composé.

Retour à la réalité technique : hors ICU, des accolades peuvent rester du texte ou être remplacées comme une clé exacte ; elles ne deviennent pas pour autant une expression plural. La syntaxe legacy à barres reste un autre mécanisme, avec ses intervalles propres. Renommer un catalogue ne convertit pas automatiquement tous ses messages.

🧠 Comment le mémoriser : « Bonne fiche, bon lecteur. » Image mentale : deux lecteurs devant une fiche simple et une fiche à branches. Question-réflexe : mon catalogue et mes messages utilisent-ils le même format ?

⚠️ À ne pas confondre : substitution non ICU, pluralisation legacy et grammaire ICU.

Plural et select, exécutés

À retenir en priorité
  1. other fournit le cas de repli obligatoire.
  2. Les catégories de plural dépendent de la locale.

Où en est-on ? Étape 6 : on fait tourner le format ICU sur des valeurs réelles. C'est ici qu'on voit que one ne veut pas dire « exactement 1 » et que la locale pilote les règles.

Pour zéro commentaire, one ne signifie pas universellement « entier 1 ». Les exemples ci-dessous exposent justement le rôle de la locale et des branches exactes comme =0. Changer la locale du formateur change les règles numériques, mais ne réécrit pas les mots français d'un message littéral.

Message ICU Résultat
{n, plural, one {# fichier} other {# fichiers}}, locale fr 0 fichier, 1,5 fichier, 2 fichiers
le même message littéral avec locale en 0 fichiers : catégorie other, sans traduction automatique des mots
=0 {aucun fichier} placé avant one =0 l'emporte pour 0
select ou plural sans other InvalidArgumentException à chaque trans()
select contenant un plural les deux s'imbriquent

Les catégories one, few… suivent la locale : en français, 0 et 1,5 sont one. Une key %name% remplit aussi {name} : Symfony retire les pourcents.

Lecture pas à pas du premier exemple, avec n = 0 puis n = 2 :

{n, plural, one {# fichier} other {# fichiers}}   locale = fr
n = 0   → règle fr : 0 est « one »    → « 0 fichier »
n = 1,5 → règle fr : 1,5 est « one »  → « 1,5 fichier »
n = 2   → règle fr : « other »        → « 2 fichiers »
locale en : 0 → « other » → « 0 fichiers » (les mots restent ceux du message)

Pourquoi other est obligatoire : c'est la branche de secours quand aucune autre catégorie ne correspond ; sans elle, ICU lève une InvalidArgumentException à chaque appel.

🌍 In Real Life

La situation : le rédacteur choisit une formule dans un arbre de phrases. Une consigne spéciale « exactement zéro » peut passer avant la règle grammaticale générale ; une branche de secours reste indispensable.

L’équivalent dans Symfony : ICU distingue les valeurs exactes comme =0, les catégories de plural dépendantes de la locale et les sélections select. other fournit la branche obligatoire ; # insère le nombre formaté dans une branche plurielle.

Retour à la réalité technique : one ne signifie pas universellement le nombre 1 : les exemples français incluent 0 et 1,5. La priorité d'une valeur exacte ne dépend pas seulement de sa position visuelle avant one. Changer la locale du formateur ne traduit pas les mots littéraux ; select choisit une valeur fournie sans déduire une identité personnelle.

🧠 Comment le mémoriser : « Valeur exacte, règle locale, secours obligatoire. » Image mentale : arbre de phrases avec sortie spéciale 0 et branche other. Question-réflexe : est-ce une valeur exacte ou une catégorie grammaticale, et où est mon other ?

⚠️ À ne pas confondre : égalité numérique, catégorie de pluriel, sélection textuelle et traduction du vocabulaire.

L'object traduisible

À retenir en priorité
  1. t() conserve message, parameters et domain.
  2. Le filter trans effectue la translation à l'affichage.

Où en est-on ? Étape 7, dernière : parfois le code PHP prépare le message (clé, paramètres, domaine) mais c'est le template qui le traduit. Voyons ce qu'est cet objet et pourquoi on ne peut pas l'afficher seul.

Une couche applicative peut préparer la confirmation sans décider encore de sa langue d'affichage : l'objet conserve clé, paramètres et domaine. Le template déclenche la traduction avec |trans dans son contexte. Afficher directement l'objet ne réalise pas cette étape et échoue en 8.0.

t('notification.welcome', {…}, 'domaine') construit un TranslatableMessage qui garde ses parameters et son domain, et se traduit à l'affichage par |trans. Une enum qui retourne une key brute perd parameters et domain.

En 8.0, TranslatableMessage n'a plus de __toString() : {{ message }} seul fait échouer le rendu — une Error PHP, « could not be converted to string », sur Twig 3.22 —, là où 7.4 affichait la key. Seul {{ message|trans }} produit le texte.

PHP   : new TranslatableMessage('notification.welcome', {…}, 'domaine')
        (enveloppe : clé + paramètres + domaine, PAS encore de texte)
Twig  : {{ message }}         → Error : pas de __toString() en 8.0
        {{ message|trans }}   → le translator ouvre l'enveloppe → texte
        {{ message|trans('de') }} → la string en 2e argument = locale

Pourquoi l'enveloppe plutôt que le texte ? Le code applicatif ne connaît pas la locale du lecteur : il transmet de quoi traduire, et la vue décide au dernier moment. Pourquoi la string en deuxième argument est-elle une locale ici ? Parce que l'objet porte déjà ses propres paramètres et son domaine : il ne reste qu'à désigner la langue.

🌍 In Real Life

La situation : on prépare une enveloppe contenant la référence d'une lettre, ses données et sa collection, sans encore choisir la langue finale. Présenter l'enveloppe ne donne pas une lettre lisible ; il faut la faire composer.

L’équivalent dans Symfony : t() crée un TranslatableMessage conservant message, paramètres et domaine. |trans délègue sa traduction au moment voulu avec la locale applicable.

Retour à la réalité technique : en Symfony 8.0, cet objet n'a pas de conversion __toString() permettant son affichage direct. Pour un objet traduisible, la chaîne passée au premier argument explicite de trans peut désigner la locale ; ce raccourci ne vaut pas pour une simple clé chaîne. L'objet n'est ni du HTML sûr ni un texte déjà traduit.

🧠 Comment le mémoriser : « L'enveloppe prépare, trans compose. » Image mentale : enveloppe de données devenant une lettre dans la langue choisie. Question-réflexe : ai-je un message à traduire ou déjà son texte final ?

⚠️ À ne pas confondre : clé brute, TranslatableMessage, texte traduit et sûreté de sortie.

Pièges d'examen

Piège à éviter

  • Voir l’explication : L'ordre des arguments du filter est parameters, puis domain, puis locale.

    L'ordre des arguments du filter est parameters, puis domain, puis locale. Les named arguments évitent de le deviner. Pourquoi on se trompe : on met le domaine en premier, comme on désigne d'abord le dossier.

  • Voir l’explication : Une string en deuxième argument

    Une string en deuxième argument n'est une locale que pour un object traduisible ; ailleurs, c'est une erreur. Pourquoi on se trompe : l'exemple de la locale pour t() est généralisé à toutes les strings.

  • Voir l’explication : L'autoescape protège le résultat du filter

    L'autoescape protège le résultat du filter, pas celui du tag ; raw annule cette protection. Pourquoi on se trompe : on suppose que tout ce qui sort d'une traduction est traité de la même façon.

  • Voir l’explication : trans_default_domain ne traverse pas un include.

    trans_default_domain ne traverse pas un include. Pourquoi on se trompe : on le prend pour un réglage global, alors qu'il est compilé dans le template courant.

  • Voir l’explication : Dans le tag, un emplacement non fourni vient du contexte.

    Dans le tag, un emplacement non fourni vient du contexte. Pourquoi on se trompe : on croit qu'il reste littéral, comme avec le filter.

  • Voir l’explication : Accolades et pluriel

    Accolades et pluriel : sans le suffixe +intl-icu, {name} n'est qu'un emplacement ordinaire — rien n'est pluralisé. Pourquoi on se trompe : on pense que la syntaxe {…plural…} s'active seule.

Application

À retenir en priorité
  1. Le suffixe active l'interprétation MessageFormat.
  2. Les emplacements ICU utilisent des accolades.
  3. Le remplacement doit viser la key exacte.
  4. name ne remplace pas proprement %name% si les délimiteurs restent dans le texte.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • |trans(paramètres, domaine, locale, count), named arguments admis.
  • String en 2ᵉ argument : locale pour t(), erreur pour une string.
  • strtr() : {'%name%': …}, pas {'name': …}.
  • Tag : count with from into, texte simple, %var% du contexte.
  • Filter soumis à autoescape, tag non ; raw réservé au HTML de confiance.
  • trans_default_domain : le template courant, pas les inclus.
  • ICU : +intl-icu, {name}, catégories de la locale, other obligatoire.
  • t() se traduit par |trans ; seul, il fait échouer le rendu.

Moyen mnémotechnique : « PDL : parameters, puis domain, puis locale — le filter échappe, le tag fait confiance ».

trans(params, domain, locale, count) ; 2e arg string = locale pour t() seul ;
strtr exact ; tag : count with from into, texte simple, non échappé ;
default domain local ; ICU = +intl-icu + {name} ; t() via |trans
