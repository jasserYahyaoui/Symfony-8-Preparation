Objectif

Le lecteur de /blog/42 choisit un thème sombre. Au prochain chargement, comment retrouver ce choix sans l'ajouter à chaque URL ? Un cookie permet au navigateur de conserver une petite valeur et de la renvoyer dans les Requests auxquelles elle s'applique.

Nous allons suivre ce trajet complet : préparer Set-Cookie, laisser le navigateur appliquer ses règles, relire la valeur reçue puis demander sa suppression. Les attributes de sécurité interviennent à des étapes différentes ; aucun ne transforme une valeur cliente en donnée fiable.

Fil du cours :

1. Lire et écrire   → Cookie, Response, Request : qui fait quoi ?
2. Attributes       → HttpOnly, Secure, SameSite, Path, Domain, Partitioned
3. SameSite         → strict, lax, none : dans quel contexte renvoyer ?
4. Préfixes         → __Secure-, __Host- : le nom impose des contraintes

L'essentiel

À comprendre

À retenir en priorité
  1. __Host- interdit Domain.
  2. Le navigateur applique ces règles ; Symfony ne les garantit pas à la construction.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. HTTP ne garde aucune mémoire entre deux requêtes. Le cookie est le mécanisme standard pour que le serveur demande au navigateur de conserver une petite valeur et de la renvoyer.
  • Le piège de fond. Trois moments distincts se confondent facilement : construire le cookie en PHP, faire accepter le header par le navigateur, le voir revenir dans une Request suivante. Symfony ne contrôle que le premier.
  • Ce que l'auteur veut que vous compreniez. Chaque attribut contrôle une seule dimension (accès par script, transport, portée, contexte intersite). Aucun ne rend la valeur fiable : elle vient du client.
  • Pourquoi c'est à l'examen. Les questions portent sur les défauts de Cookie::create(), l'immutabilité de with*(), clearCookie() contre removeCookie(), les trois valeurs de SameSite, Partitioned, et ce que Symfony ne vérifie pas (préfixes).

La Request contient ce que le navigateur a déjà envoyé ; la Response décrit ce que le serveur lui demande de conserver pour la suite. $request->cookies et $response->headers->setCookie() ne sont donc pas deux accès au même stockage. Poser theme=dark dans la Response ne modifie pas rétroactivement les cookies de la Request courante.

Cookie::create() fournit notamment HttpOnly et SameSite=Lax. Son paramètre secure vaut null par défaut : une préparation de Response à partir d'une Request sécurisée peut alors activer Secure. Un object Cookie isolé ne détecte pas lui-même HTTPS.

Les méthodes with…() retournent une copie configurée ; il faut conserver cette valeur. Ensuite, même une construction PHP réussie ne prouve pas l'acceptation du header par le navigateur. Nous séparerons les validations de Symfony, les règles de réception et les conditions de renvoi.

Pourquoi Secure peut-il s'activer « tout seul » ? Au moment d'envoyer la Response, Response::prepare($request) regarde si la Request est sécurisée ; si oui, il appelle setSecureDefault(true) sur chaque cookie. Cookie::isSecure() rend alors $this->secure ?? $this->secureDefault : un secure explicite (true ou false) gagne toujours, seul null suit le défaut.

Le schéma

À retenir en priorité
  1. removeCookie() retire seulement un Set-Cookie de la Response.
  2. clearCookie() doit reprendre path et domain pour viser le cookie existant.

Où en est-on ? Vue d'ensemble avant les détails : le voyage complet d'une valeur de cookie, de la Response d'aujourd'hui à la Request de demain. Les quatre parties suivantes détaillent chacune une zone de ce voyage (écrire/lire, attributes, SameSite, préfixes).

Le lecteur vient de confirmer son choix. Nous suivons la Response de cette action, puis une nouvelle visite de /blog/42 :

En bleu figurent les messages ; le losange orange appartient au navigateur, pas à Symfony. Le cylindre représente son stockage. Un header refusé n'atteint pas cette étape ; un cookie stocké peut ensuite ne pas être envoyé si le contexte ne remplit pas ses conditions.

La boucle suppose donc acceptation puis renvoi : SameSite, Secure, domaine, chemin et politique du navigateur comptent. En diagnostic, inspecte d'abord Set-Cookie dans la Response, puis le stockage du navigateur, enfin Cookie dans la Request suivante. Chercher immédiatement la nouvelle valeur dans la Request initiale confondrait deux instants.

Qui contrôle quoi ?

L'exemple : un cookie de préférence

Exemple concret

À retenir en priorité
  1. Les méthodes with* renvoient une copie ; setSecureDefault() peut modifier le défaut contextuel.
  2. Conserver la return value avant setCookie().

Où en est-on ? On applique le premier tiers du schéma (« construire ») : préparer la Response qui demande au navigateur de retenir theme=dark. Code minimal d'abord, puis ce que Symfony en fait.

Dans la branche de choix du thème, supposons que la valeur dark ait été acceptée par l'application. Avec PHP 8.4 et HttpFoundation 8.0 chargés par l'autoloader, préparons une Response indépendante :

use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Response;

$response = new Response('Préférence enregistrée');

Le fragment suivant conserve le cookie configuré à chaque étape de la chaîne, puis l'ajoute aux headers de cette Response :

$response->headers->setCookie(
    Cookie::create('theme')
        ->withValue('dark')
        ->withExpires(new \DateTimeImmutable('+1 year'))
        ->withSecure(true)
        ->withSameSite(Cookie::SAMESITE_LAX)
);

Le résultat préparé contient theme=dark, une expiration calculée à un an, Path=/, Secure, HttpOnly et SameSite=Lax, sans Domain. La date exacte dépend de l'instant d'exécution. Le controller retournerait cette Response ; le fragment ne l'émet pas lui-même.

Concrètement, la ligne qui part sur le réseau ressemble à (forme de Cookie::__toString()) :

Set-Cookie: theme=dark; expires=<date +1 an>; Max-Age=31536000; path=/;
            secure; httponly; samesite=lax

Si le navigateur l'accepte depuis notre site HTTPS, il pourra renvoyer theme=dark lors d'une visite admissible de /blog/42. L'expiration n'oblige pas le navigateur à conserver la valeur pendant un an : l'utilisateur peut l'effacer ou sa politique de stockage la limiter. Ici le rendu du thème est décidé côté serveur ; HttpOnly empêcherait un script de lire directement cette préférence par les API de cookies.

Lire et écrire

Où en est-on ? Étape 1 sur 4 : on boucle le trajet. Demain, le navigateur renvoie le cookie ; nous le lisons dans la Request (pas dans l'object Cookie d'hier, qui n'existe plus), puis nous voyons comment le modifier et le supprimer.

Lors de la visite suivante, nous lisons une entrée cliente, pas l'object Cookie construit précédemment. Ce laboratoire simule le renvoi de la préférence ; Request::create() ne contacte aucun navigateur :

use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/blog/42', 'GET', [], ['theme' => 'dark']);
$theme = $request->cookies->get('theme', 'light');
$theme = in_array($theme, ['light', 'dark'], true) ? $theme : 'light';
echo $theme;

La sortie est dark. Sans cette entrée, le défaut est light ; une autre valeur scalaire est ramenée à ce même défaut. Un cookie n'accorde donc pas de permission : nous validons la préférence au lieu de traiter toute valeur reçue comme un choix reconnu.

Pourquoi valider ? Le cookie est un champ que l'utilisateur peut modifier avec ses outils de développement. $request->cookies est un InputBag : même contrat que query (voir le cours sur la Request).

Modifier : pourquoi with*() retourne-t-il une copie ?

Cookie est conçu comme un object immuable : chaque with*() fait clone $this, modifie la copie et la retourne. L'instance d'origine ne bouge jamais. Oublier de récupérer le retour, c'est jeter la modification.

Pour modifier la prochaine valeur, conserve le résultat de with*(). Par exemple, dans un autre laboratoire :

use Symfony\Component\HttpFoundation\Cookie;

$initial = Cookie::create('theme', 'light');
$modified = $initial->withValue('dark');
echo $initial->getValue(), ' / ', $modified->getValue();

La sortie light / dark montre pourquoi ignorer le retour de withValue() ne modifie pas l'instance initiale. La chaîne de l'exemple précédent transmet justement chaque nouvelle instance à l'appel suivant.

secure=null : une décision reportée

Le réglage secure=null est une autre frontière : Response::prepare($request) active le défaut Secure pour les cookies concernés lorsque la Request est sécurisée. Il ne remplace pas un choix explicite false. Derrière un proxy, cette décision dépend aussi d'une configuration de confiance correcte pour reconnaître HTTPS ; le cookie ne devine pas la connexion originale.

Expiration : session, persistant, suppression

Trois cas à ne pas mélanger :

Valeur Expiration Ce que sérialise Set-Cookie
non vide 0 (ou négative → ramenée à 0) pas de expires : cookie de session
non vide date future expires=…; Max-Age=… : persistant
null ou '' n'importe laquelle, même 0 name=deleted; expires=<passé>; Max-Age=0 : suppression

Si nous ne voulons pas d'expiration persistante explicite, withExpires(0) produit un cookie de session, à condition que sa valeur ne soit ni null ni ''. Une échéance négative est normalisée à zéro. La fin de cette session dépend du navigateur : une restauration peut conserver le cookie après fermeture. Ce terme ne signifie pas que Symfony a automatiquement créé une session d'authentification.

Avec une valeur null ou '', la sérialisation produit au contraire une instruction de suppression : expiration passée et Max-Age=0, même si l'expiration stockée vaut zéro. Pour retirer une préférence déjà présente chez le client, clearCookie() prépare cette instruction. removeCookie() retire seulement un cookie des headers de la Response en cours : il n'envoie pas de demande d'effacement.

removeCookie('theme')   → enlève l'entrée de la Response en préparation
                          (rien n'est envoyé ; le navigateur garde son cookie)
clearCookie('theme')    → AJOUTE un cookie expiré (Max-Age=0)
                          (le navigateur, s'il l'accepte, efface le sien)

🌍 In Real Life

La situation : le restaurant remet une carte de préférence que le client pourra présenter à sa prochaine visite ; la carte ne change pas la demande déjà reçue.

L’équivalent dans Symfony : carte proposée → Set-Cookie dans la Response ; carte effectivement rapportée → Cookie puis request.cookies ; nouvelle version préparée → retour de with*() à conserver.

Retour à la réalité technique : stockage et renvoi dépendent du navigateur. La valeur reçue reste cliente et doit être validée ; l'objet Cookie n'est pas un stockage partagé avec la Request courante.

🧠 Comment le mémoriser : « Proposer maintenant, relire ensuite. » Image mentale : carte passant entre deux visites. Question-réflexe : inspecte-t-on l'instruction, le stockage ou le renvoi ?

⚠️ À ne pas confondre : cookie de session navigateur et session d'authentification Symfony.

Set-Cookie remet au navigateur une note à conserver ; Cookie est cette note présentée lors d'un échange ultérieur. Les deux headers vont donc dans des sens opposés, même lorsqu'ils portent la même valeur.

Les attributes de sécurité

À retenir en priorité
  1. HttpOnly limite l'accès JavaScript.
  2. Secure limite l'envoi à HTTPS ; SameSite traite le contexte intersite.

Où en est-on ? Étape 2 sur 4 : le cookie de préférence est anodin ; un identifiant de session ne l'est pas. On regarde les attributs qui encadrent l'accès, le transport, la portée et le contexte du cookie. Chacun agit à un endroit différent du schéma (stockage ou renvoi), et aucun n'est une garantie universelle.

La préférence sombre est peu sensible ; un identifiant de session demanderait davantage de précautions. Deux risques à distinguer : une XSS est l'exécution de script non souhaité dans le contexte du site ; une CSRF fait déclencher une action non souhaitée avec des informations que le navigateur envoie automatiquement. Bloquer la lecture d'un cookie par script ne bloque pas cet envoi automatique.

XSS  : un script étranger tourne DANS ta page
       → il lit document.cookie        ← HttpOnly bloque CETTE lecture
CSRF : un autre site déclenche une requête VERS ton site
       → le navigateur joint le cookie ← HttpOnly n'y change rien
                                         (SameSite limite certains cas)
Attribute Ce qu'il protège
HttpOnly Rend le cookie invisible à JavaScript — atténue le vol par XSS
Secure N'envoie le cookie que sur HTTPS
SameSite Contrôle l'envoi en contexte tiers — atténue le CSRF
Path Restreint l'envoi à un path et ses sous-répertoires
Domain Élargit aux sous-domaines du domaine accepté ; l'omettre limite à l'hôte, pas à une origine définie par protocole, hôte et port

Path choisit les demandes auxquelles le cookie s'applique ; ce n'est pas une barrière d'autorisation entre applications d'un même hôte. Sans Domain, le cookie est lié à l'hôte exact. Ajouter un domaine accepté peut étendre sa portée aux sous-domaines, pas la renforcer. Cette portée ne sépare pas les ports comme le ferait une origine définie par protocole, hôte et port.

Pourquoi Domain est-il contre-intuitif ? On pense « je précise, donc je restreins ». C'est l'inverse : sans Domain, le cookie reste attaché à l'hôte exact (shop.example.com) ; avec Domain=example.com, tous les sous-domaines le reçoivent.

Partitioned (CHIPS)

Si le blog fournit un widget intégré sur d'autres sites, la partition de stockage devient une question distincte. withPartitioned() ajoute Partitioned : les navigateurs compatibles peuvent isoler ce cookie selon le site de premier niveau qui intègre le widget. Cette technique, appelée CHIPS, ne fusionne donc pas toutes ses visites dans le même stockage tiers. Dans Cookie 8.0, l'attribute est sérialisé en dernier, après samesite lorsqu'il est présent.

La prise en charge reste côté navigateur. Tout cookie Partitioned doit porter Secure pour être accepté par un navigateur compatible, quelle que soit sa valeur de SameSite. Dans HttpFoundation 8.0, withPartitioned() n'active pas Secure et ne vérifie pas cette association : PHP peut donc sérialiser un cookie que le navigateur refusera. Vérifie le header final, après l'éventuelle préparation de la Response.

Pour notre widget intégré dans une page d'un autre site, SameSite=None permet le renvoi du cookie dans ce contexte intersite. Ce choix répond au contexte d'utilisation ; il n'est pas imposé par Partitioned lui-même. Le partitionnement ne contourne ni SameSite ni les autres politiques du navigateur. Ce détour ne concerne pas la simple préférence de notre page visitée directement.

Sans Partitioned                     Avec Partitioned (navigateur compatible)
widget.example (cookie unique)       un cookie PAR site de premier niveau
 ├─ vu depuis siteA.test  ┐          ├─ [siteA.test] → cookie A
 ├─ vu depuis siteB.test  ┘ même     └─ [siteB.test] → cookie B (séparé)
                      stockage

🌍 In Real Life

La situation : une carte peut avoir une règle d'accès, une règle de transport et une zone d'utilisation ; aucune de ces règles ne garantit la vérité de ce qui y est écrit.

L’équivalent dans Symfony : accès par script limité → HttpOnly ; transport HTTPS → Secure ; portée de renvoi → Domain et Path ; contexte intersite → SameSite.

Retour à la réalité technique : HttpOnly ne supprime pas une XSS ni les envois CSRF ; Path n'est pas une barrière d'autorisation. Domain peut élargir aux sous-domaines. Partitioned ajoute une séparation de stockage liée au site de premier niveau, selon le navigateur.

🧠 Comment le mémoriser : « Chaque attribut contrôle une dimension. » Image mentale : plusieurs règles indépendantes sur la même carte. Question-réflexe : accès, transport, portée ou contexte ?

⚠️ À ne pas confondre : Secure et chiffrement de la valeur elle-même ; hôte et origine avec port.

Les trois valeurs de SameSite

À retenir en priorité
  1. SameSite=None nécessite Secure.
  2. Lax autorise les navigations de premier niveau avec une safe method.

Où en est-on ? Étape 3 sur 4 : on zoome sur l'attribut le plus testé. La question qu'il pose est toujours la même : « la requête qui arrive est-elle une requête intersite ? » ; selon sa réponse (strict, lax, none), le navigateur joint ou non le cookie.

Le lecteur ouvre maintenant un lien vers /blog/42 depuis un autre site. SameSite détermine si ce contexte permet le renvoi du cookie. Dans nos URLs web classiques, la notion de site tient notamment compte du schéma et du domaine enregistrable ; elle n'est pas simplement l'égalité des origines ou des chemins.

Avec strict, le cookie n'accompagne pas cette navigation intersite. Si c'est le seul identifiant utilisé pour retrouver la session, l'utilisateur peut paraître déconnecté sur cette première visite. Cela ne signifie pas que sa session serveur a été supprimée.

Avec lax, le cookie peut accompagner une navigation intersite de premier niveau utilisant une méthode sûre, comme l'ouverture du lien en GET. Il n'est pas envoyé pour un POST intersite avec ce réglage explicite. Ce compromis est le défaut de Cookie::create() ; il ne remplace pas une protection CSRF pour les actions qui modifient l'état.

Avec none, SameSite ne restreint plus cet envoi, mais le navigateur exige Secure. Les autres règles, dont le domaine, le chemin et les politiques de blocage des cookies tiers, continuent à s'appliquer. « None » ne signifie donc pas « envoyé dans toutes les circonstances ».

Comparaison selon le contexte d'arrivée :

Contexte strict lax none (+ Secure)
Navigation interne au site envoyé envoyé envoyé
Lien GET depuis un autre site non envoyé envoyé
POST intersite (formulaire d'un autre site) non non envoyé
Sous-ressource intersite (iframe, image…) non non envoyé
Prérequis navigateur — — Secure obligatoire

(La dernière colonne reste soumise aux politiques de blocage des cookies tiers, domaine et chemin.)

Côté API, withSameSite('Strict') normalise la valeur en strict. Une valeur inconnue lève une InvalidArgumentException. null ou la string vide permettent d'omettre l'attribute ; cette omission est différente de la valeur explicite none, et laisse intervenir les règles par défaut du navigateur.

🌍 In Real Life

La situation : une carte peut accompagner certaines visites venues d'ailleurs sans être admise dans toutes les situations.

L’équivalent dans Symfony : restriction intersite forte → Strict ; exception pour navigation de premier niveau sûre → Lax ; absence de restriction SameSite → None.

Retour à la réalité technique : None exige Secure et ne contourne pas les autres politiques. Omettre l'attribut n'équivaut pas à None. Le site n'est pas simplement l'origine ; aucune de ces valeurs ne remplace la protection CSRF adaptée.

🧠 Comment le mémoriser : « Examiner la visite, pas seulement la carte. » Image mentale : arrivée par lien GET face à un POST intersite. Question-réflexe : quel contexte permet le renvoi ?

⚠️ À ne pas confondre : cookie non envoyé et session serveur supprimée.

Les préfixes `__Secure-` et `__Host-`

Où en est-on ? Étape 4 sur 4, la dernière : jusqu'ici les contraintes venaient des attributs. Ici, c'est le nom du cookie qui déclenche des vérifications côté navigateur, au moment de l'acceptation (2ᵉ case du schéma « qui contrôle quoi »). Symfony, lui, ne les vérifie pas.

Un nom peut aussi annoncer des contraintes que le navigateur compatible doit vérifier avant d'accepter le cookie. Pour une préférence liée au seul hôte du blog, le préfixe __Host- rend notamment incompatible l'ajout accidentel d'un Domain. Ces contraintes supposent une origine sécurisée :

Préfixe Ce que le navigateur exige, sinon il rejette
__Secure- l'attribute Secure
__Host- Secure, Path=/, et aucun Domain

Le brouillon officiel cité prévoit une reconnaissance des préfixes sans tenir compte de la casse ; utilise néanmoins leur orthographe conventionnelle pour éviter de dépendre de différences de prise en charge. Symfony 8.0 ne vérifie pas la combinaison d'attributes exigée par ces préfixes à partir du nom. Cela ne veut pas dire que Cookie ne valide aucun autre paramètre, comme les valeurs SameSite.

Voici un header isolé, envoyé depuis notre origine HTTPS, qui respecte les contraintes du préfixe :

Set-Cookie: __Host-preference=compact; Path=/; Secure; HttpOnly; SameSite=Lax

Le navigateur compatible peut le conserver pour l'hôte exact. Ajouter Domain=example.test romprait ce contrat, même si ce domaine est celui du site. Le nom ne remplace pas HttpOnly, SameSite ou la validation de session ; il n'isole pas non plus les ports.

Une instance Cookie::create('__Host-session') peut être construite sans exception liée au préfixe. Si le header final ne contient pas Secure, le navigateur appliquant ces règles le refuse. Inspecte toutefois le header final : la préparation d'une Response HTTPS peut avoir activé Secure pour le réglage null. L'absence d'un appel explicite withSecure(true) ne prouve donc pas à elle seule son absence à l'envoi.

Cookie::create('__Host-session')          (PHP : aucune exception)
        │ Response::prepare() sur Request HTTPS → Secure par défaut
        ▼
Set-Cookie final : __Host-session=...; path=/; secure; httponly; samesite=lax
        │ navigateur : Secure ? Path=/ ? pas de Domain ?  → accepte ou rejette

Pièges d'examen

Piège à éviter

  • Voir l’explication : SameSite=none sans Secure est rejeté.

    SameSite=none sans Secure est rejeté. Ce n'est pas un avertissement : le cookie n'est pas posé du tout par le navigateur appliquant cette règle. Une Response inspectée en PHP peut pourtant contenir ce header : construction et acceptation sont deux contrôles distincts. Pourquoi on se trompe : PHP ne lève rien, donc on croit que « ça passe ».

  • Voir l’explication : HttpOnly ne protège pas du CSRF.

    HttpOnly ne protège pas du CSRF. Il empêche l'accès au cookie par les API de script, pas son envoi automatique par le navigateur. Il ne supprime pas une faille XSS. SameSite limite certains envois intersites et atténue le CSRF ; ce n'est pas une garantie générale contre toutes les requêtes indésirables. Pour l'inscription ou une modification de préférence, garde donc les contrôles adaptés à l'action, plutôt que d'attendre qu'un attribute de cookie valide l'intention de l'utilisateur. Pourquoi on se trompe : « sécurisé » dans le nom des attributs laisse croire à une protection générale.

  • Voir l’explication : Supprimer un cookie demande une instruction visant sa portée.

    Supprimer un cookie demande une instruction visant sa portée. clearCookie() ajoute un cookie expiré à la Response ; il ne retourne pas un cookie à manipuler. Il faut reprendre le nom et les mêmes path et domain, sinon l'original peut rester stocké. Pour notre préférence non partitionnée, sur HTTPS :

use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Response;

$response = new Response('Préférence supprimée');
$response->headers->clearCookie('theme', '/', null, true, true, Cookie::SAMESITE_LAX);
  • Instruction d’effacement et acceptation du cookie

    La Response prépare theme=deleted, une expiration passée et Max-Age=0 avec la portée initiale. Ce n'est pas un effacement immédiat à distance : le navigateur doit encore recevoir et accepter l'instruction. Pour un cookie partitionné ou préfixé, respecte aussi les conditions de ce cookie lors de l'effacement.

  • Voir l’explication : Un cookie de session n'a pas d'expiration persistante explicite

    Un cookie de session n'a pas d'expiration persistante explicite : withExpires(0) le produit si sa valeur n'est ni null ni vide. Une valeur nulle ou vide déclenche la sérialisation de suppression. La fin de session dépend du navigateur ; la restauration de session peut le conserver après fermeture. Ne déduis pas une déconnexion serveur de la seule fermeture d'une fenêtre. Pourquoi on se trompe : « cookie de session » évoque la session PHP ou Symfony ; ici c'est seulement « sans date d'expiration ».

  • Voir l’explication : Cookie::fromString() n'a pas les mêmes défauts que create().

    Cookie::fromString() n'a pas les mêmes défauts que create(). Sa table interne pose secure => false, httponly => false, samesite => null : une lecture de header brut ne rajoute donc pas ces protections lorsqu'elles sont absentes. Le rôle du parseur est de représenter le header reçu, pas d'inventer une politique d'émission.

  • Voir l’explication : removeCookie() n'efface rien chez le client.

    removeCookie() n'efface rien chez le client. Son propre docblock le dit : « removes a cookie from the array, but does not unset it in the browser ». Il retire le Set-Cookie de la Response ; c'est clearCookie() qui envoie le cookie expiré qui demande l'effacement. Annuler un header en préparation et retirer une valeur déjà stockée chez le client répondent à deux problèmes. Pourquoi on se trompe : « remove » ressemble à « supprimer le cookie ».

  • Voir l’explication : Cookie::create() fournit déjà certains attributes protecteurs.

    Cookie::create() fournit déjà certains attributes protecteurs. httpOnly vaut true et sameSite vaut lax sans réglage supplémentaire. La factory exige au moins un nom ; ces défauts ne dispensent ni de choisir la bonne portée ni de vérifier Secure dans le contexte réel. Ils ne garantissent pas non plus la confidentialité ou l'intégrité de la valeur stockée chez le client.

🌍 In Real Life

La situation : retirer une carte d'un courrier encore au départ n'annule pas celle que le client possède déjà ; il faut lui transmettre une instruction visant la bonne carte.

L’équivalent dans Symfony : retirer l'instruction en préparation → removeCookie() ; demander l'effacement chez le client → clearCookie() avec portée correspondante.

Retour à la réalité technique : le cookie expiré doit être reçu et accepté ; nom, path et domain doivent viser le stockage initial, avec les conditions supplémentaires d'un cookie préfixé ou partitionné.

🧠 Comment le mémoriser : « Retirer du courrier ou effacer chez le client ? » Image mentale : enveloppe non envoyée face à une carte déjà détenue. Question-réflexe : quel stockage veut-on modifier ?

⚠️ À ne pas confondre : expiration de session et garantie d'effacement à la fermeture du navigateur.

Application

À retenir en priorité
  1. SameSite=None nécessite Secure.
  2. Lax autorise les navigations de premier niveau avec une safe method.
  3. HttpOnly limite l'accès JavaScript.
  4. Secure limite l'envoi à HTTPS ; SameSite traite le contexte intersite.

Fiche express

À mémoriser

De la préférence choisie à la Request suivante, retiens sept repères :

  • Lire par $request->cookies, écrire par setCookie() ; conserver les copies renvoyées par with*().
  • create() : path '/', httpOnly, lax, secure=null, dont le défaut peut être activé par la préparation d'une Response HTTPS. Expiration zéro : session pour une valeur non vide ; valeur nulle ou vide : instruction de suppression.
  • fromString() : ne rajoute pas les protections absentes du header.
  • HttpOnly bloque l'accès au cookie par script, pas la faille XSS ; SameSite limite les envois intersites ; Secure réserve l'envoi à HTTPS.
  • Domain élargit aux sous-domaines ; son absence restreint à l'hôte.
  • SameSite=none exige Secure ; Partitioned exige lui aussi Secure, indépendamment de SameSite. __Host- exige Secure, Path=/ sans Domain.
  • clearCookie() avec les mêmes path et domain ; removeCookie() n'efface rien chez le client.

Moyen mnémotechnique : « HttpOnly limite l'accès, SameSite limite l'envoi, Secure exige le transport sécurisé ». L'attribut Secure ne chiffre pas la valeur du cookie lui-même.

🧠 À retenir pour la certification

  • Trois temps : construire (Symfony) → accepter (navigateur) → renvoyer (navigateur) ; la Request courante ne voit jamais le cookie que la Response vient de poser.
  • Cookie est immuable : with*() retourne une copie.
  • Défauts de create() : HttpOnly, SameSite=Lax, Path=/, secure=null (activé par Response::prepare() en HTTPS).
  • Suppression : clearCookie() (même path/domain) ; removeCookie() retire seulement de la Response.
  • SameSite=None et Partitioned exigent Secure côté navigateur ; __Host- : Secure, Path=/, pas de Domain (non vérifié par Symfony).
  • Aucun attribut ne valide la valeur : la lire, c'est la valider.

Phrase de mémorisation : « Je construis le cookie, le navigateur décide de le garder et de me le rendre, et ce qu'il me rend, je le valide. »
