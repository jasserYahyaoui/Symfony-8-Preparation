Objectif

L'aide de app:blog:import peut annoncer un fichier et une limite, mais du texte d'aide ne les rend pas utilisables. Il faut une définition d'entrée qui distingue le chemin positionnel, une option de format et un drapeau. En Symfony 8.0, les attributs relient cette définition aux paramètres PHP ; le type et la valeur par défaut déterminent le mode accepté.

L'essentiel

À comprendre

À retenir en priorité
  1. La position identifie l'argument.
  2. Le nom identifie l'option.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une commande reçoit des chaînes brutes (argv). Pour qu'elles deviennent des paramètres PHP typés (int, bool, enum…), Console doit savoir ce qui est attendu : c'est la définition d'entrée.
  • Le piège de fond. Le mot required : il porte sur la valeur d'une option quand elle est présente, jamais sur sa présence.
  • Ce que l'auteur veut que vous compreniez. En 8.0, on ne déclare plus le mode à la main : la signature décide (type + valeur par défaut).
  • Pourquoi c'est à l'examen. Tableau signature → mode, --no-x, union bool|string, défaut obligatoire des options, ordre des arguments, nom en kebab-case.

Un argument est positionnel (app:greet Alice), une option est nommée (--iterations=5). En 8.0, #[Argument] et #[Option] se posent sur les parameters de __invoke(), et le mode — requis, optionnel, array, drapeau — se déduit de la signature : type et default value.

Le piège central est le mot required : VALUE_REQUIRED exige une valeur si l'option est présente, pas la présence de l'option. Ainsi #[Option] string $format = 'json' autorise l'absence de --format et utilise json, mais --format seul ne fournit pas la valeur attendue.

Pour l'import, articles.csv peut remplir #[Argument] string $file, tandis que #[Option] int $maxItems = 10 décrit --max-items. L'absence de cette option garde 10 ; sa présence doit apporter une valeur. Le type entier ne garantit pas encore qu'une limite de zéro ou négative ait un sens métier.

app:blog:import articles.csv --max-items=5 --dry-run
                │              │              │
                │              │              └ option sans valeur (drapeau)
                │              └ option nommée avec valeur
                └ argument positionnel

Le schéma

À retenir en priorité
  1. La signature décrit le mode.
  2. Les attributes ajoutent les metadata.

Où en est-on ? Nous savons que la signature décide. Deux schémas montrent maintenant, pas à pas, comment Console interprète une option selon qu'elle est absente, présente sans valeur ou présente avec valeur.

Avant d'écrire le parseur du fichier, isolons le choix du format. Deux questions se succèdent : l'utilisateur a-t-il fourni l'option, puis a-t-il fourni sa valeur ?

Losanges ambre : décisions du parsing ; formes vertes : valeur ou erreur. Cette vue suppose la signature #[Option] string $format = 'json' et aucun token suivant utilisable comme valeur.

Où en est-on ? Le premier schéma traitait une option à valeur. Le second traite un cas plus riche : une option qui peut aussi servir de simple drapeau.

Un rapport facultatif d'import introduit un autre contrat : absence de rapport, rapport demandé sans chemin, ou chemin explicite. L'union bool|string avec défaut false distingue ces trois états au niveau du paramètre PHP :

Le true du second schéma est une conversion de l'attribut Option. La valeur brute de l'entrée classique peut être null à cette étape : la section sur les modes distingue ces deux niveaux.

L'exemple : saluer

Exemple concret

À retenir en priorité
  1. Un bool à false est un drapeau.
  2. Il n'attend pas de valeur après le nom.

Où en est-on ? Place au code minimal : une commande d'accueil avec deux arguments et deux options, sans traitement, pour observer quelles valeurs arrivent dans quels paramètres.

Gardons la petite commande d'accueil pour observer les valeurs sans lancer un import ni modifier les articles. Cette variante remplace la précédente GreetCommand ; ses imports sont inclus et son service doit être découvert :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\Argument;
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Attribute\Option;
use Symfony\Component\Console\Command\Command;

#[AsCommand(name: 'app:greet')]
class GreetCommand
{
    public function __invoke(
        #[Argument] string $name,
        #[Argument] string $lastName = '',
        #[Option] int $iterations = 1,
        #[Option] bool $yell = false,
    ): int {
        // app:greet Alice Martin --iterations=3 --yell
        return Command::SUCCESS;
    }
}

L'exemple décrit la signature, pas encore l'affichage d'une salutation. Pour l'invocation indiquée en commentaire, le corps reçoit $name = 'Alice', $lastName = 'Martin', $iterations = 3 et $yell = true, puis retourne 0. Sans --iterations, il recevrait 1 ; sans --yell, false.

--yell est un drapeau sans valeur : il ne s'écrit pas --yell=true. La salutation n'étant pas encore affichée par ce corps minimal, aucune ligne de sortie n'est attendue. Séparer « valeur correctement transmise » de « traitement implémenté » évite de diagnostiquer à tort le parseur.

Ce que Console voit dans cette signature :

Paramètre Ce que Console en déduit Saisie → valeur
#[Argument] string $name argument requis (pas de défaut) Alice → 'Alice'
#[Argument] string $lastName = '' argument optionnel Martin → 'Martin', absent → ''
#[Option] int $iterations = 1 option --iterations, valeur requise si présente --iterations=3 → 3, absent → 1
#[Option] bool $yell = false drapeau --yell, sans valeur présent → true, absent → false

Déclarer

À retenir en priorité
  1. Le nom est converti en kebab-case.
  2. Utiliser ce nom dans InputInterface.

Où en est-on ? Étape 1 sur 3 : comment les attributs deviennent une définition. Mécanisme : au moment où la commande est construite, InvokableCommand lit les attributs de chaque paramètre et fabrique les objets de définition ; la saisie réelle n'est liée qu'ensuite.

🌍 In Real Life

La situation : le bordereau d'import du blog prévoit un emplacement pour le fichier et des cases nommées pour les réglages.

L’équivalent dans Symfony : emplacement ordonné → argument ; case nommée → option ; modèle vierge → InputDefinition ; bordereau rempli → entrée liée à cette définition.

Retour à la réalité technique : les attributs des paramètres permettent de construire InputArgument et InputOption. Les valeurs sont ensuite résolues ; déclarer le paramètre fichier ne lit pas son contenu.

🧠 Comment le mémoriser : « Le modèle avant la saisie. » Image mentale : formulaire vierge puis rempli. Question-réflexe : suis-je en train de définir ou de lire une valeur ?

⚠️ À ne pas confondre : type accepté par Console et n'importe quel type PHP automatiquement résolvable.

InvokableCommand examine les attributs, crée les InputArgument et InputOption correspondants, puis les place dans une InputDefinition. Au lancement, l'entrée est liée à cette définition avant l'appel PHP. Nous ne lisons donc pas un fichier CSV à ce stade : nous définissons les paramètres qui permettront ensuite de le sélectionner.

signature PHP ──► #[Argument]/#[Option] ──► InputArgument / InputOption
                                              │
                                              ▼
                                       InputDefinition   (modèle vierge)
                                              │  lié à argv au lancement
                                              ▼
                                        entrée parsée ──► valeurs des paramètres
  • Chaque attribute accepte description, name et suggestedValues ; #[Option] accepte en plus shortcut.
  • Le name par défaut est le nom du parameter en kebab-case : $lastName devient last-name, la key de $input->getArgument('last-name').
  • Un argument sans default value et non nullable est requis.
  • Types admis : string, bool, int, float, array et les enums typées (BackedEnum), dont les cas alimentent l'autocomplétion ; une valeur inconnue est refusée en listant les valeurs valides.

La liste de types ci-dessus concerne les types nommés ; les arguments n'acceptent pas les unions. Les options n'acceptent que les unions limitées décrites dans la section suivante. DateTimeImmutable n'est pas un type de valeur automatiquement résolu pour ces attributs.

suggestedValues sert à la complétion, pas à une validation métier générale. Une BackedEnum, en revanche, est résolue en cas d'enum et rejette une valeur inconnue. Le chemin du fichier, son existence et son contenu demandent toujours des contrôles adaptés.

suggestedValues BackedEnum
Rôle proposer à la complétion contraindre la valeur
Valeur inconnue acceptée refusée, avec liste des valeurs valides

Le mode d'une option

À retenir en priorité
  1. La présence de l'option reste facultative.
  2. La valeur peut être obligatoire à l'usage.
  3. Une option à valeur facultative a trois états.
  4. false et null peuvent distinguer absence et présence sans valeur.

Où en est-on ? Étape 2 sur 3 : le tableau le plus important du cours. Pour chaque signature PHP, quel mode d'option Console produit-il ? On distingue deux niveaux : la définition (forme de saisie) et la résolution (valeur du paramètre).

🌍 In Real Life

La situation : sur le bordereau du blog, choisir « format personnalisé » exige de préciser lequel ; on peut aussi conserver le format prévu.

L’équivalent dans Symfony : option choisie avec détail obligatoire → VALUE_REQUIRED ; choix omis → valeur par défaut ; simple case cochée → VALUE_NONE.

Retour à la réalité technique : VALUE_REQUIRED exige une valeur lorsque l'option est présente, pas sa présence dans chaque appel. Un paramètre #[Option] doit lui-même déclarer un défaut ; les unions admises ont des règles spécifiques.

🧠 Comment le mémoriser : « Requis pour la valeur, pas pour la présence. » Image mentale : une case suivie d'un champ à remplir. Question-réflexe : qu'est-ce qui est réellement obligatoire ?

⚠️ À ne pas confondre : option absente, option sans valeur et valeur explicitement fournie.

La définition répond à la forme de saisie ; la résolution prépare la valeur du paramètre. Lire chaque ligne en suivant ces deux étapes, plutôt que d'associer « required » à la présence obligatoire de --option :

Signature Mode Usage
bool $yell = false VALUE_NONE --yell
bool $yell = true ou ?bool $yell = null VALUE_NONE + VALUE_NEGATABLE --yell ou --no-yell
string $format = 'json', int $limit = 10 VALUE_REQUIRED --format=csv
array $roles = [] VALUE_REQUIRED + VALUE_IS_ARRAY --roles=ADMIN --roles=USER
string\|bool $output = false VALUE_OPTIONAL --output ou --output=f.txt
  • Un paramètre #[Option] doit déclarer une valeur par défaut : sans elle, Option::tryFrom() lève une LogicException lors de la construction de la définition — « must declare a default value ». L'ajout d'une commande non lazy demande cette définition ; avec un chargement différé, ne pas supposer que la simple présence dans list a déjà tout validé. Le mécanisme ne rend pas obligatoire la présence de l'option.
  • Types union : seuls bool|string, bool|int et bool|float, avec la default value false (sinon « must have a default value of false ») ; --output seul rend true, --output=f.txt la string.

Pour l'option union, le parcours est précis : l'absence garde le défaut false ; la présence sans valeur fournit null dans l'entrée, puis Option::resolveValue() transforme ce null en true pour le paramètre union. Une option classique VALUE_OPTIONAL de défaut false, lue avec getOption() sans cet attribut, distingue donc false, null et une chaîne — pas false, true et une chaîne. Le même nom de mode ne signifie pas que toutes les couches exposent exactement la même valeur.

bool|string $output = false          présence sans valeur
  entrée Console (InputOption)   :   null    ← valeur brute
  paramètre PHP (resolveValue)   :   true    ← conversion de l'attribut #[Option]

Voici le contrôle isolé de limite conservé pour préparer l'import. Enregistrer src/Command/ShowLimitCommand.php comme service :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Attribute\Option;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Output\OutputInterface;

#[AsCommand(name: 'app:show-limit')]
final class ShowLimitCommand
{
    public function __invoke(OutputInterface $output, #[Option] int $maxItems = 10): int
    {
        if ($maxItems < 1) {
            return Command::INVALID;
        }

        $output->writeln((string) $maxItems);

        return Command::SUCCESS;
    }
}
php bin/console app:show-limit --max-items=3

Sortie attendue en verbosity normale, avec code 0 :

3

Sans option, la sortie est 10. Avec --max-items=0, le contrôle retourne INVALID (2) sans afficher de valeur. Nous avons ajouté une règle métier à une entrée syntaxiquement recevable, pas changé le mode de l'option.

Une option classique InputOption::VALUE_OPTIONAL possède trois situations utiles à distinguer : absente, présente sans valeur, présente avec valeur. En configurant explicitement false comme valeur par défaut de l'option, l'absence vaut false, --output sans valeur vaut null, et --output=report.txt fournit la string. L'absence n'est donc pas équivalente à une option explicitement demandée sans valeur.

L'équivalent classique

À retenir en priorité
  1. L'array absorbe les valeurs restantes.
  2. Aucun argument ne doit le suivre.

Où en est-on ? Étape 3 sur 3 : l'écriture explicite des mêmes définitions dans configure(). Les attributs ne sont qu'un raccourci : les objets produits sont identiques, il faut donc connaître leurs constantes.

Ces attributs ne créent pas un second langage d'entrée. Dans le configure() d'une sous-classe de Command, avec les imports Symfony\Component\Console\Input\InputArgument et InputOption, les mêmes définitions s'écrivent explicitement :

$this
    ->addArgument('name', InputArgument::REQUIRED, 'Who to greet')
    ->addOption('iterations', 'i', InputOption::VALUE_REQUIRED, 'How many times', 1)
;

InputArgument : REQUIRED, OPTIONAL, IS_ARRAY. InputOption : VALUE_NONE, VALUE_REQUIRED, VALUE_OPTIONAL, VALUE_IS_ARRAY, VALUE_NEGATABLE. Les attributs produisent ces objets et ajoutent la résolution des valeurs vers leurs paramètres, dont la conversion union décrite plus haut.

Pour importer plusieurs fichiers, un argument IS_ARRAY absorbe les valeurs positionnelles restantes. Une destination placée après lui serait indéterminable : placer la destination avant, ou en faire une option nommée. Pour répéter une option, combiner les modes avec | : InputOption::VALUE_REQUIRED | InputOption::VALUE_IS_ARRAY, avec défaut [].

Comparaison attribut / classique :

┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│ ATTRIBUTS (8.0)                  │   │ CLASSIQUE (configure())          │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ #[Argument] string $name         │   │ addArgument('name',              │
│                                  │   │   InputArgument::REQUIRED)       │
│ #[Option] int $iterations = 1    │   │ addOption('iterations', 'i',     │
│                                  │   │   InputOption::VALUE_REQUIRED,   │
│                                  │   │   '…', 1)                        │
│ mode déduit de la signature      │   │ mode écrit à la main             │
│ valeur injectée dans le paramètre│   │ lue via $input->getOption()      │

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une option sans défaut est invalide.
  2. Ne pas confondre mode de valeur et présence.
  • Voir l’explication : Un paramètre #[Option] sans défaut est invalide

    Un paramètre #[Option] sans défaut est invalide, pas obligatoire à saisir. La présence d'une option peut faire l'objet d'un contrôle applicatif, mais VALUE_REQUIRED ne réalise pas ce contrôle. Pourquoi on se trompe : « required » semble vouloir dire « l'utilisateur doit la fournir ».

  • Voir l’explication : bool $flag = true n'est pas un drapeau simple

    bool $flag = true n'est pas un drapeau simple : il accepte une forme négative, donc --no-flag existe. Pourquoi on se trompe : on croit qu'un drapeau actif par défaut ne peut pas être désactivé.

  • Voir l’explication : Le nom par défaut est kebab-case

    Le nom par défaut est kebab-case, pas le nom du parameter tel quel.

  • Voir l’explication : shortcut n'existe que pour les options

    shortcut n'existe que pour les options. Un argument a bien un nom dans la définition (name, last-name), mais sa valeur est fournie par sa position : il n'a pas de drapeau court comme -i.

  • Voir l’explication : L'ordre des arguments est contraint.

    L'ordre des arguments est contraint. InputDefinition lève une LogicException pour un argument requis déclaré après un argument optionnel, et pour tout argument déclaré après un argument array — celui-ci absorbant toutes les valeurs positionnelles restantes. Dans cette définition : array $a = [], string $b = '' est refusé, même $b optionnel, avec un message trompeur : « Cannot add a required argument "b" after an array argument "a". »

  • Voir l’explication : Une erreur de définition précède le traitement métier

    Une erreur de définition précède le traitement métier, mais sa découverte dépend du moment où cette définition est demandée. Ne pas confondre l'ajout d'un objet commande concret avec l'enregistrement de métadonnées pour une commande lazy.

  • Voir l’explication : Un format suggéré n'est pas automatiquement imposé

    Un format suggéré n'est pas automatiquement imposé : la complétion propose ; une enum ou une validation explicite contraint.

À mémoriser

À retenir en priorité
  1. Un bool activé par défaut est négatable.
  2. La signature crée la forme négative.

Le contrat d'import peut maintenant préciser ce qui doit être saisi et ce qui possède un défaut. Pour raisonner sur une valeur, suivre signature → définition → entrée parsée → paramètre résolu → règle métier.

🧠 À retenir pour la certification — si tu dois retenir seulement 6 choses :

  • Argument positionnel, option nommée.
  • Mode déduit du type et de la default value.
  • Argument sans défaut, non nullable : requis.
  • Paramètre #[Option] : défaut obligatoire ; présence non imposée par les modes de Console.
  • bool $x = true → --no-x ; bool|string $x = false → valeur optionnelle.
  • Nom par défaut en kebab-case ; shortcut pour les options seulement.

Moyen mnémotechnique : « La signature décide ». Phrase de mémorisation : « Type et valeur par défaut fixent le mode ; « requis » concerne la valeur d'une option présente, jamais sa présence. »
