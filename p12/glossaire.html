Application, composant, bundle, bridge

Application : notre projet avec son Kernel, BlogController et ArticleCatalog. Composant : bibliothèque réutilisable avec un rôle défini. Bundle : intégration enregistrée par l’application. Bridge : adaptation d’une autre bibliothèque. Ne confondez pas installation d’un paquet, activation d’un bundle et invocation d’un service.

🌍 In Real Life

La situation : un restaurant équipe sa cuisine avec des appareils et leurs raccords.

L’équivalent dans Symfony : établissement → application ; appareil spécialisé → composant ; installation intégrée → bundle ; adaptateur → bridge.

Retour à la réalité technique : bibliothèque, intégration et adaptation sont des rôles distincts. Acheter l’appareil ne le raccorde pas : installer Doctrine Bridge ne prouve ni ORM disponible ni résolution d’entité configurée.

🧠 Comment le mémoriser : « Posséder, raccorder, utiliser. » Image : appareil encore débranché. Réflexe : « Le paquet est-il seulement installé ou réellement intégré ? »

⚠️ À ne pas confondre : un bundle n’est pas le parent PHP obligatoire d’un contrôleur.

Composants et bridges.

Kernel et HttpKernel

Kernel : prépare l’application, ses bundles et son conteneur, puis délègue le traitement. HttpKernel : concret qui orchestre Request → Response. HttpKernelInterface définit un contrat ; KernelInterface l’étend. Une interface n’est pas l’algorithme exécuté.

🌍 In Real Life

La situation : préparer l’établissement et coordonner une commande sont deux responsabilités.

L’équivalent dans Symfony : préparation de l’ensemble → Kernel ; coordination Request → Response → HttpKernel ; engagement sur les opérations disponibles → interface.

Retour à la réalité technique : App\Kernel étend Kernel, qui prépare bundles/conteneur et délègue. Le concret HttpKernel orchestre le traitement HTTP. Une interface décrit un contrat ; elle ne traite rien seule.

🧠 Comment le mémoriser : « L’établissement, puis la demande. » Image : plan d’ensemble face à un bon unique. Réflexe : « Parle-t-on du cycle applicatif ou du traitement HTTP ? »

⚠️ À ne pas confondre : construire le Kernel, le booter et compiler son conteneur.

Kernel, interfaces et FrameworkBundle.

Request, attribut et route

Request : objet HttpFoundation représentant la demande, pas le moteur qui la traite. Attribut de Request : donnée dans attributes, comme _controller ou l’id capturé. Attribut PHP : métadonnée #[Route]. Route : règle de matching et de génération d’URL ; son nom blog_show n’est ni le chemin /blog/42 ni le callable.

🌍 In Real Life

La situation : l’accueil annote le bon 42 en consultant une règle de destination.

L’équivalent dans Symfony : bon → Request ; annotations internes → attributes ; règle de destination → route ; inscription de cette règle dans le code → attribut PHP #[Route].

Retour à la réalité technique : RouterListener peut enrichir les attributes après matching. Une route sert aussi à générer des URL. Son nom identifie la règle, pas le callable ; les annotations ne sont pas les paramètres query du client.

🧠 Comment le mémoriser : « Règle, bon, annotation. » Image : registre séparé du bon. Réflexe : « Où cette donnée est-elle déclarée ou stockée ? »

⚠️ À ne pas confondre : attribut PHP et attribut de Request.

Request · Routing.

Callable et resolver

Callable : valeur PHP invocable. ControllerResolver détermine cette valeur ; ArgumentResolver prépare les arguments en interrogeant des value resolvers. Résoudre n’est pas appeler. Un résultat vide d’un value resolver signifie qu’il laisse la suite essayer, pas qu’il a nécessairement fourni null.

🌍 In Real Life

La situation : le responsable choisit un poste puis rassemble sa fiche ; un aide sans réponse laisse le suivant chercher.

L’équivalent dans Symfony : poste choisi → callable du ControllerResolver ; fiche complète → arguments de l’ArgumentResolver ; aide spécialisé → value resolver.

Retour à la réalité technique : un callable est une valeur PHP invocable. HttpKernel obtient callable et arguments avant l’invocation. Un iterable vide laisse poursuivre la résolution ; produire null est fournir une valeur.

🧠 Comment le mémoriser : « Choisir n’est pas appeler. » Image : poste prêt, ordre encore retenu. Réflexe : « Le resolver s’abstient-il ou fournit-il une valeur ? »

⚠️ À ne pas confondre : le routeur détermine des paramètres, il n’invoque pas l’action.

Arguments du contrôleur.

Service, définition, alias et compilation

Service : objet auquel l’application confie une responsabilité. Définition : description de sa construction/configuration. Alias : référence alternative vers un service. Compilation : traitement du graphe des définitions, distinct de la construction de toutes les instances. Le conteneur fournit les services ; il n’est pas synonyme d’un service ni d’une nouvelle instance par requête.

🌍 In Real Life

La situation : une cuisine tient ses fiches d’équipement et plusieurs noms peuvent désigner le même appareil.

L’équivalent dans Symfony : appareil utilisable → service ; fiche de montage → définition ; autre nom → alias ; plan vérifié → compilation ; fourniture selon le plan → conteneur.

Retour à la réalité technique : le service est un objet ; la définition décrit sa construction. Compiler traite les définitions, sans instancier tout le graphe. Un alias ne crée pas une copie de l’objet.

🧠 Comment le mémoriser : « La fiche n’est pas l’appareil. » Image : deux étiquettes, un équipement. Réflexe : « Est-ce une définition, une référence ou une instance ? »

⚠️ À ne pas confondre : partagé dans un conteneur et recréé par requête.

Conteneur.

Autowiring et autoconfiguration

Autowiring : résolution des dépendances à partir notamment des types et alias configurés. Autoconfiguration : application de règles de configuration aux services reconnus, souvent des tags. L’une répond à « quelle dépendance ? », l’autre à « quel rôle enregistré ? ». Aucune ne scanne magiquement toute classe non enregistrée.

🌍 In Real Life

La situation : on fournit au poste l’équipement demandé et on lui attribue séparément un rôle dans l’organisation.

L’équivalent dans Symfony : raccord adapté au besoin déclaré → autowiring ; rôle reconnu et marqué → autoconfiguration, notamment tags.

Retour à la réalité technique : l’autowiring résout les dépendances à partir des types et alias ; l’autoconfiguration applique des règles aux services concernés. Ces mécanismes configurent des définitions, pas des employés qui choisissent librement à chaque commande.

🧠 Comment le mémoriser : « Avec quoi ? À quel rôle ? » Image : prise et badge distincts. Réflexe : « Manque-t-il une dépendance ou un enregistrement de rôle ? »

⚠️ À ne pas confondre : une classe présente sur disque et un service enregistré.

Autowiring · Déclaration des services.

Extension et compiler pass

Une extension de conteneur traite une configuration et alimente des définitions. Un compiler pass inspecte ou transforme les définitions pendant la compilation. Ils ne traitent pas le GET /blog/42 comme des listeners kernel.request.

🌍 In Real Life

La situation : l’installateur traduit les besoins en fiches, puis un coordinateur assemble les postes repérés sur le plan.

L’équivalent dans Symfony : besoins vers définitions → extension ; inspection et modification du plan → compiler pass, par exemple pour raccorder des services tagués.

Retour à la réalité technique : l’extension traite la configuration ; le pass opère sur le graphe pendant la compilation. Cette préparation ne signifie pas que les instances existent déjà ni qu’elle recommence pour chaque GET.

🧠 Comment le mémoriser : « Alimenter le plan, transformer le plan. » Image : fiches ajoutées puis reliées. Réflexe : « Quel travail porte sur les définitions ? »

⚠️ À ne pas confondre : compiler pass et listener HTTP.

Construction du conteneur.

Événement, listener et subscriber

Un événement est dispatché à un point d’extension. Un listener est un callable enregistré. Un subscriber est une classe qui déclare ses abonnements ; il n’est pas un fichier de configuration. La priorité ordonne les appels effectivement atteints ; une interruption peut empêcher les suivants.

🌍 In Real Life

La situation : à une annonce, certains intervenants réagissent ; l’un déclare lui-même les annonces et réactions dont il s’occupe.

L’équivalent dans Symfony : annonce → événement ; réaction enregistrée → listener ; intervenant avec déclaration et réactions → subscriber.

Retour à la réalité technique : le listener est un callable. Un subscriber est une classe implémentant EventSubscriberInterface, déclarant ses abonnements via getSubscribedEvents() ; ses méthodes assurent les réactions. L’enregistrement reste nécessaire ; priorité et propagation limitent les appels.

🧠 Comment le mémoriser : « L’abonné déclare et réagit. » Image : intervenant tenant sa liste d’annonces. Réflexe : « Qui déclare quels événements et quelles méthodes ? »

⚠️ À ne pas confondre : subscriber et simple fichier de procédure ; dispatch d’événement et file durable.

Événements.

Authentification et autorisation

L’authentification établit une identité dans un contexte de sécurité. L’autorisation décide si une action est permise. Un utilisateur connu peut être refusé. Un voter participe à une décision ; il n’est pas un chargeur d’article ni une étape obligatoire après l’accès aux données.

🌍 In Real Life

La situation : un employé reconnu à l’accueil n’a pas forcément le droit de modifier toutes les fiches du restaurant.

L’équivalent dans Symfony : identité établie → authentification ; permission sur une action/un article → autorisation ; avis sur cette permission → voter.

Retour à la réalité technique : Security établit un contexte puis évalue les droits aux points configurés. Des contrôles précoces peuvent interrompre le trajet ; un voter participe à une décision, sans charger automatiquement l’article.

🧠 Comment le mémoriser : « Connu ne veut pas dire autorisé. » Image : badge devant une porte fermée. Réflexe : « Qui est-il, puis peut-il faire ceci ? »

⚠️ À ne pas confondre : contrôle d’identité et permission sur l’objet concerné.

Authentification · Autorisation.

DTO, transformation et validation

Un DTO transporte des données comme SignupData ; le nom n’ajoute aucun comportement automatique. Une transformation change leur représentation. La validation applique des contraintes et produit des violations. Une donnée transformable n’est pas forcément acceptable ; valider ne sauvegarde pas et n’autorise pas.

🌍 In Real Life

La situation : l’accueil transcrit une inscription dans une fiche, puis vérifie les règles avant de l’enregistrer.

L’équivalent dans Symfony : fiche de données → DTO SignupData ; transcription vers une représentation exploitable → transformation ; règles vérifiées → validation.

Retour à la réalité technique : DTO signifie objet de transfert de données. Transformer change la représentation ; valider applique des contraintes et retourne des violations. Aucune de ces opérations ne sauvegarde automatiquement ni ne garantit une autorisation.

🧠 Comment le mémoriser : « Transcrit n’est pas validé. » Image : fiche lisible avec une case encore refusée. Réflexe : « Ai-je changé la forme ou vérifié une règle ? »

⚠️ À ne pas confondre : type PHP accepté et contraintes métier satisfaites.

Form · Validator.

Normalisation et encodage

La normalisation transforme un objet en structure de données ; l’encodage produit une représentation, par exemple JSON. La sérialisation peut combiner les deux ; la désérialisation emprunte le trajet inverse. Une chaîne déjà JSON ne doit pas être encodée involontairement une seconde fois.

🌍 In Real Life

La situation : le restaurant extrait les champs partageables d’une fiche puis les écrit dans un format convenu avec son partenaire.

L’équivalent dans Symfony : objet vers champs structurés → normalisation ; structure vers texte JSON → encodage ; lecture puis reconstruction → décodage et dénormalisation.

Retour à la réalité technique : Serializer peut composer ces opérations selon normalizers, encoders et contexte. La conversion ne valide pas les données et ne décide pas seule des droits d’accès.

🧠 Comment le mémoriser : « Structurer, puis écrire le format. » Image : tableau de champs puis document JSON. Réflexe : « Ai-je encore un objet, une structure ou déjà du JSON ? »

⚠️ À ne pas confondre : encodage initial et double encodage d’une chaîne déjà JSON.

Serializer.

Message, transport et worker

Un message exprime une information ou une demande de travail. Un transport assure l’envoi/réception selon sa configuration. Un worker reçoit et traite les messages. Le bus et ses middleware peuvent aussi traiter immédiatement : dispatch() n’est pas une preuve d’asynchronisme.

🌍 In Real Life

La situation : une consigne d’inventaire est exécutée sur place ou acheminée vers un poste qui la reprendra plus tard.

L’équivalent dans Symfony : consigne → message ; acheminement → transport ; reprise → worker ; travail effectué → handler.

Retour à la réalité technique : le bus traverse ses middleware. Sans sender routé et avec handler disponible, le traitement peut être immédiat ; sync:// l’est aussi. Le différé exige une configuration appropriée ; le retour de dispatch ne certifie pas l’achèvement.

🧠 Comment le mémoriser : « La consigne ne fixe pas l’horaire. » Image : remise directe ou bac de tâches. Réflexe : « Où ce message est-il routé et qui le consomme ? »

⚠️ À ne pas confondre : envoi, réception et réussite du handler.

Messenger · Workers.

Cache HTTP et cache applicatif

Le cache HTTP réutilise une réponse selon la sémantique HTTP ; un proxy peut répondre avant PHP. Le cache applicatif réutilise une donnée ou un calcul dans l’application. La présence d’une valeur n’exclut pas tout recalcul anticipé avec Cache Contracts. Le mot « cache » ne suffit donc pas à prédire quel code sera évité.

🌍 In Real Life

La situation : l’accueil garde une copie d’une fiche publique ; un poste garde le résultat d’un calcul interne.

L’équivalent dans Symfony : réponse complète réutilisée → cache HTTP ; donnée/calcul réutilisé dans un service → cache applicatif.

Retour à la réalité technique : HTTP impose des règles de réutilisation, variation et revalidation ; un proxy peut éviter PHP. Le cache applicatif n’évite que le travail ciblé ; Cache Contracts peut recalculer par anticipation. Une copie numérique n’est pas une assiette périssable.

🧠 Comment le mémoriser : « Copie de réponse ou résultat de calcul ? » Image : accueil et poste interne. Réflexe : « À quelle couche répond ce cache ? »

⚠️ À ne pas confondre : valeur présente et absence garantie de recalcul.

HTTP · Application.

Sous-requête, envoi et terminaison

Une sous-requête est un autre appel de traitement HTTP dans l’application, pas nécessairement un nouvel échange réseau. Envoyer une Response émet statut, headers et contenu ; terminer appelle un hook ultérieur si le noyau et l’appelant le prennent en charge. handle() seul ne fait pas les deux. Terminate n’offre pas les garanties d’un worker durable.

🌍 In Real Life

La situation : un poste demande une préparation interne, assemble le résultat, le remet, puis effectue une opération locale de fin.

L’équivalent dans Symfony : demande interne → sous-requête ; résultat assemblé → Response ; remise → envoi ; opération ultérieure → terminate().

Retour à la réalité technique : une sous-requête est un appel interne de traitement HTTP, sans échange réseau nécessaire. handle() retourne ; l’appelant envoie puis termine si pris en charge. La réception des octets dépend aussi du serveur ; terminate n’est pas un worker durable.

🧠 Comment le mémoriser : « Produire, envoyer, terminer. » Image : résultat au comptoir, puis remis. Réflexe : « Quel appel a réellement eu lieu ? »

⚠️ À ne pas confondre : kernel.finish_request, émission et garantie de travail en arrière-plan.
