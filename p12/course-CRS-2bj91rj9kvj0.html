Objectif

Sur GET /blog/42, le contrôleur veut afficher un article avec un template Twig. Trois questions se posent alors : qui compile ce template, où Symfony le cherche, et quels réglages de config/packages/twig.yaml changent le résultat ? Ce cours répond à ces trois questions.

Il faut savoir ce que TwigBundle ajoute à Twig, où il cherche les templates, et quelles options de configuration comptent. La distinction component / bridge / bundle est traitée dans le Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Distinguer engine et intégration du framework.
  2. Le bundle expose paths, options et services.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Twig est une bibliothèque PHP indépendante de Symfony : elle ne sait ni où sont vos fichiers, ni ce qu'est une route, ni ce qu'est un formulaire. Quelqu'un doit la brancher sur le framework.
  • Ce que l'auteur veut que vous compreniez. Ce « quelqu'un » est TwigBundle. Il dit où chercher les templates, comment surcharger ceux d'un bundle, et quelles options de config/packages/twig.yaml changent le comportement.
  • Le piège de fond. Trois packages portent le mot « Twig » (engine, bridge, bundle) et deux préfixes servent à nommer un template de bundle (@Nom et @!Nom). Les confondre est la source des erreurs de QCM.
  • Pourquoi c'est à l'examen. Les questions portent sur le nom du namespace (sans Bundle), le directory de surcharge (avec Bundle), le préfixe @!, la valeur par défaut de strict_variables et ce que debug:twig / lint:twig prouvent ou ne prouvent pas.

Twig seul compile et rend un template. TwigBundle le branche sur Symfony : il dit où chercher les templates, comment surcharger ceux d'un bundle, et quelles options de config/packages/twig.yaml changent le comportement.

Le schéma

À retenir en priorité
  1. La surcharge prend priorité sur l'original.
  2. @! permet de reprendre l'original sans récursion.

Où en est-on ? Vue d'ensemble du cours : le schéma ci-dessous répond à la question centrale « quel fichier sert un template de bundle ? ». Il sera détaillé dans la section « Surcharger le template d'un bundle » ; les trois sections qui le précèdent (packages, emplacements) posent le vocabulaire nécessaire pour le lire.

Le cours en 5 étapes
   ├─ 1. Qui fait quoi ?             → engine / bridge / bundle
   ├─ 2. Où sont les templates ?     → templates/, twig.paths, @Namespace
   ├─ 3. Comment surcharger ?        → templates/bundles/XxxBundle/, @!Xxx
   ├─ 4. Quelles options comptent ?  → strict_variables, globals, form_themes…
   └─ 5. Comment diagnostiquer ?     → debug:twig, lint:twig

Les losanges ambre représentent les choix du loader ; les sorties vertes, les fichiers retenus. Les flèches pleines décrivent la recherche du fichier, les pointillés un extends Twig, pas un héritage PHP. La dernière flèche est un piège : la surcharge s'étend elle-même. Vue simplifiée pour les emplacements du bundle, sans chemin twig.paths personnalisé prioritaire ; si aucun fichier n'existe, le loader échoue.

L'exemple

Exemple concret

À retenir en priorité
  1. Le préfixe @! cible le template original, pas la surcharge.
  2. parent() conserve le contenu du block parent après le bandeau ajouté.

Où en est-on ? Avant le détail, un cas concret qui résume le mécanisme de surcharge (étape 3). On montre le code minimal, puis on dit ce que Twig voit.

Le lecteur connecté consulte son profil depuis le blog. Si cette page vient d'un bundle, l'application peut ajouter son bandeau sans copier tout le template fourni. La surcharge ci-dessous reprend l'original par son nom dédié, puis laisse parent() insérer son block body.

{# templates/bundles/AcmeBlogBundle/user/profile.html.twig #}
{% extends '@!AcmeBlog/user/profile.html.twig' %}

{% block body %}
    <p class="banner">Bienvenue</p>
    {{ parent() }}
{% endblock %}

@AcmeBlog/user/profile.html.twig rend désormais le bandeau puis le contenu d'origine ; @!AcmeBlog/… rend l'original seul.

Ce que Twig voit, ligne par ligne :

Élément Ce que Twig fait Pourquoi
Fichier placé dans templates/bundles/AcmeBlogBundle/… il est trouvé en premier pour le nom @AcmeBlog/… l'application a priorité sur le bundle
extends '@!AcmeBlog/…' va chercher le fichier du bundle @! saute la surcharge
{% block body %} remplace le block body du parent c'est l'héritage Twig
{{ parent() }} insère le contenu du block body d'origine on enrichit au lieu de copier

Trois packages, trois roles

Où en est-on ? Étape 1 sur 5 : avant de parler de chemins ou d'options, il faut savoir qui fait quoi quand on écrit {{ path('blog_show') }} dans un template. Trois packages collaborent ; chacun a un rôle.

Quand BlogController::show() demande le rendu d'ArticleView, HttpKernel ne compile pas lui-même le template. Twig réalise ce rendu ; le bridge fournit les fonctions liées à Symfony et le bundle configure leurs services. Une Response HTML peut donc employer Twig, sans faire de Twig une étape obligatoire pour une redirection ou une réponse JSON.

Package Role
twig/twig l'engine : syntaxe, compiler, filters de base
symfony/twig-bridge les extensions qui exposent les components : path(), trans, le rendu de form
symfony/twig-bundle l'intégration : configuration, paths, services

composer require symfony/twig-bundle installe les trois : le bundle exige le bridge, qui exige twig/twig.

Pourquoi trois packages et pas un seul ? Parce que chaque couche a un public différent :

┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐
│      twig/twig       │ │ symfony/twig-bridge  │ │ symfony/twig-bundle  │
├──────────────────────┤ ├──────────────────────┤ ├──────────────────────┤
│ Sert à               │ │ Sert à               │ │ Sert à               │
│  compiler et rendre  │ │  exposer path(),     │ │  configurer, ranger  │
│                      │ │  trans, forms        │ │  les paths, services │
├──────────────────────┤ ├──────────────────────┤ ├──────────────────────┤
│ Connaît Symfony ?    │ │ Connaît Symfony ?    │ │ Connaît Symfony ?    │
│  non                 │ │  ses components      │ │  son container       │
├──────────────────────┤ ├──────────────────────┤ ├──────────────────────┤
│ Je l'installe ?      │ │ Je l'installe ?      │ │ Je l'installe ?      │
│  tiré par les autres │ │  tiré par le bundle  │ │  composer require    │
└──────────────────────┘ └──────────────────────┘ └──────────────────────┘

Pourquoi un seul composer require suffit-il ? Le bundle exige le bridge, qui exige l'engine : Composer remonte la chaîne de dépendances.

🌍 In Real Life

La situation : l'atelier d'impression possède une machine de composition, des adaptateurs pour les outils de l'établissement et une installation qui relie le tout. Ce sont trois responsabilités, même si on commande l'ensemble en une fois.

L’équivalent dans Symfony : twig/twig compile et rend ; Twig Bridge fournit les extensions d'accès aux composants ; TwigBundle configure chemins, options et services dans Symfony.

Retour à la réalité technique : les dépendances installées ne rendent pas tous les composants optionnels disponibles sans configuration. HttpKernel n'est pas le compilateur Twig. Une réponse JSON ou une redirection n'impose pas de passer par ce moteur de templates.

🧠 Comment le mémoriser : « La machine compose, les adaptateurs relient, l'installation configure. » Image mentale : machine, prises adaptées et plan d'installation. Question-réflexe : mon problème concerne-t-il le moteur, une extension ou son intégration ?

⚠️ À ne pas confondre : moteur Twig, extensions Symfony et configuration du bundle.

Où vivent les templates

À retenir en priorité
  1. default_path choisit le directory principal.
  2. paths complète les emplacements disponibles.

Où en est-on ? Étape 2 sur 5 : le contrôleur écrit $this->render('blog/show.html.twig'). Ce texte n'est pas un chemin de fichier. Il faut comprendre comment Twig le transforme en fichier réel.

Le nom blog/show.html.twig désigne un template relatif aux chemins du loader, pas une URL et pas un chemin lu depuis le navigateur. Ajouter un namespace permet de distinguer deux espaces de templates sans changer la route blog_show. Le loader doit résoudre ce nom avant tout affichage.

Le chemin d'exécution, du nom au fichier :

render('blog/show.html.twig')
        ▼
le loader parcourt ses chemins, dans l'ordre
        ▼
templates/blog/show.html.twig existe ?  → oui : c'est le fichier à compiler
                                        → non : il essaie le chemin suivant
        ▼
aucun chemin ne contient le nom → LoaderError
  • Par défaut dans templates/ : twig.default_path vaut %kernel.project_dir%/templates.
  • twig.paths ajoute des directories ; la valeur est un namespace facultatif. Sans namespace, le path rejoint l'espace principal ; avec, il se référence en @Nom/….
  • Un bundle expose ses templates sous @NomDuBundle/… sans le suffixe Bundle : @AcmeBlog/user/profile.html.twig.

Code minimal, côté configuration :

# config/packages/twig.yaml
twig:
    paths:
        '%kernel.project_dir%/extra': Admin   # → '@Admin/ns.html.twig'
        '%kernel.project_dir%/shared': ~      # → 'ns.html.twig' (espace principal)

Avant / après, un même fichier, deux façons de l'appeler :

extra/ns.html.twig
   avec namespace « Admin »  →  render('@Admin/ns.html.twig')
   sans namespace            →  render('ns.html.twig')   (espace principal)

Pourquoi un namespace ? Deux dossiers peuvent contenir un profile.html.twig. Sans namespace, le premier dossier gagnerait toujours ; avec, on désigne celui qu'on veut.

Comparaison de deux options proches :

default_path paths
Effet remplace le directory principal ajoute des directories
Défaut %kernel.project_dir%/templates aucun
Namespace non facultatif (@Nom/…)

🌍 In Real Life

La situation : l'imprimeur cherche un modèle dans des classeurs. Une étiquette de collection permet de distinguer deux modèles nommés « profil » ; elle n'est pas l'adresse publique du document imprimé.

L’équivalent dans Symfony : le loader résout un nom relatif dans ses chemins configurés. default_path désigne le répertoire principal ; paths ajoute des emplacements, avec éventuellement un namespace tel que @AcmeBlog.

Retour à la réalité technique : modifier l'option ne déplace pas physiquement les fichiers. Le namespace de bundle omet le suffixe Bundle, contrairement au répertoire de surcharge. Ce nom n'est ni une route ni une URL demandée par le navigateur.

🧠 Comment le mémoriser : « L'étiquette du classeur n'est pas l'adresse du lecteur. » Image mentale : modèle classé sous un namespace, document livré ailleurs. Question-réflexe : quel loader et quels chemins résolvent ce nom ?

⚠️ À ne pas confondre : nom logique de template, chemin de fichier et chemin HTTP.

Surcharger le template d'un bundle

Où en est-on ? Étape 3 sur 5 : on sait nommer un template ; on veut maintenant remplacer celui d'un bundle sans modifier vendor/. C'est la partie du schéma Mermaid vu plus haut.

Au rendu du profil, le premier fichier trouvé devient l'entrée exécutée. Si cette entrée étend son propre nom public, le loader retrouve la même surcharge : aucun original ne termine la chaîne. Le préfixe @! sert précisément à poursuivre vers le template fourni par le bundle.

Pour chaque bundle, deux emplacements, dans cet ordre — le premier gagne :

  1. templates/bundles/AcmeBlogBundle/ — le nom complet, suffixe compris ;
  2. le directory du bundle.

L'original reste accessible sous @!AcmeBlog, ce qui permet à la surcharge de l'étendre. Étendre @AcmeBlog/… depuis la surcharge la fait s'étendre elle-même : le rendu entre dans une récursion. L'échec concret dépend du runtime et de ses limites ; l'épuisement mémoire est un symptôme possible, pas une garantie, et aucun message d'erreur unique ne caractérise ce cas.

Pourquoi @!AcmeBlog existe-t-il ? Dans TwigExtension, chaque bundle est enregistré deux fois dans le loader : une fois sous le namespace AcmeBlog (l'application d'abord, le bundle ensuite) et une fois sous !AcmeBlog (le bundle seul). Le point d'exclamation n'est pas une syntaxe magique : c'est un second namespace, créé exactement pour pouvoir viser l'original.

Pourquoi la récursion ? Déroulons une surcharge qui étend @AcmeBlog :

render('@AcmeBlog/user/profile.html.twig')
   ▼
le loader sert  templates/bundles/AcmeBlogBundle/user/profile.html.twig
   ▼
ce fichier dit  extends '@AcmeBlog/user/profile.html.twig'
   ▼
le loader sert le MÊME fichier (la surcharge gagne toujours)
   ▼
… et ainsi de suite : jamais d'original, la chaîne ne se termine pas

Comparaison des deux noms :

┌───────────────────────────────────┐ ┌───────────────────────────────────┐
│          @AcmeBlog/…              │ │          @!AcmeBlog/…             │
├───────────────────────────────────┤ ├───────────────────────────────────┤
│ Cherche dans                      │ │ Cherche dans                      │
│  1. templates/bundles/…Bundle/    │ │  le directory du bundle seul      │
│  2. le directory du bundle        │ │                                   │
├───────────────────────────────────┤ ├───────────────────────────────────┤
│ Sert à                            │ │ Sert à                            │
│  rendre la page (surcharge       │ │  étendre l'original depuis la     │
│  d'abord si elle existe)          │ │  surcharge                        │
├───────────────────────────────────┤ ├───────────────────────────────────┤
│ Dans un extends de la surcharge   │ │ Dans un extends de la surcharge   │
│  → récursion                      │ │  → atteint l'original             │
└───────────────────────────────────┘ └───────────────────────────────────┘

🌍 In Real Life

La situation : une fiche de présentation locale remplace celle du fournisseur, mais veut réutiliser son texte. Si elle demande simplement « la fiche courante », elle se retrouve elle-même ; elle doit désigner l'original.

L’équivalent dans Symfony : dans la configuration décrite, le template d'application masque celui du bundle. @!AcmeBlog/… permet à la surcharge d'étendre l'original ; parent() reprend le bloc parent, pas un fichier choisi au hasard.

Retour à la réalité technique : les chemins personnalisés peuvent modifier la recherche ; le loader échoue si aucun fichier ne convient. Une référence à soi crée une récursion, dont l'échec concret dépend du runtime et de ses limites : un message mémoire n'en est pas une preuve suffisante.

🧠 Comment le mémoriser : « Demander l'original évite de se citer soi-même. » Image mentale : fiche locale pointant vers le classeur du fournisseur, pas vers son propre titre. Question-réflexe : mon extends résout-il un autre fichier ou encore cette surcharge ?

⚠️ À ne pas confondre : priorité de recherche, héritage Twig et héritage PHP.

Repère de l’exemple :

Question: How does the overriding Twig template add a banner while retaining the original body?

Answer: It extends the original with @! and calls parent() inside its body block.

Le préfixe @! cible le template original, pas la surcharge. parent() conserve le contenu du block parent après le bandeau ajouté.

Les options qui changent le comportement

À retenir en priorité
  1. Une variable absente peut lever en debug.
  2. default, defined et ?? permettent de gérer une absence prévue.

Où en est-on ? Étape 4 sur 5 : le template est trouvé. Reste à régler comment il se comporte : où chercher, quelles variables communes, quel thème de formulaire, et que faire quand une variable manque.

Une faute artcile dans le template peut sembler disparaître lorsque debug est désactivé : la donnée n'a pas été réparée, l'absence est seulement tolérée. Utilise un repli pour une donnée réellement facultative ; ne masque pas une erreur dans le contrat article fourni par show().

Option Effet Défaut
default_path déplace le directory des templates templates/
paths ajoute des directories, nommés ou non aucun
globals variables disponibles dans tous les templates aucune
form_themes theme de rendu des forms form_div_layout.html.twig
strict_variables variable inexistante : erreur au lieu de null %kernel.debug%

Par défaut, strict_variables suit kernel.debug, pas le nom de l'environnement. Avec debug activé, {{ typo }} lève une RuntimeError si la variable manque ; sans debug, il rend une chaîne vide. C'est habituellement le contraste dev/prod, mais on peut configurer ces valeurs autrement. typo|default('x'), typo is defined et user.name ?? 'anon' traitent explicitement l'absence de donnée, même en mode strict.

Dans globals, '@id' désigne un service ; '@@texte' produit la string @texte.

Pourquoi strict_variables suit-il kernel.debug ? En développement, une faute de frappe doit faire mal tout de suite ; en production, on préfère ne pas casser une page pour une variable absente. Le défaut vient de Configuration.php : defaultValue('%kernel.debug%').

Code minimal :

twig:
    strict_variables: true
    globals:
        site_name: 'Mon blog'          # string simple
        clock: '@app.clock'            # le SERVICE app.clock
        mail: '@@contact'              # la string littérale "@contact"

Ce que Twig fait face à {{ typo }} selon la configuration :

{{ typo }}  (variable absente)
   ├─ strict_variables = true   → RuntimeError
   └─ strict_variables = false  → chaîne vide (null affiché vide)

{{ typo|default('x') }}  → 'x' dans les deux cas
{{ typo is defined }}    → false dans les deux cas
{{ typo ?? 'x' }}        → 'x' dans les deux cas

Pourquoi la mauvaise réponse est plausible : on croit que « prod » désactive toujours le mode strict. En réalité l'option suit kernel.debug, et on peut la fixer à la main : le nom de l'environnement n'intervient pas.

🌍 In Real Life

La situation : l'atelier choisit les classeurs à consulter, les informations communes aux imprimés et leur présentation. Une règle distincte décide si une case manquante bloque le travail ou reste vide.

L’équivalent dans Symfony : chemins, globals et form_themes pilotent des aspects différents du rendu. strict_variables gouverne les accès aux données absentes ; sa valeur par défaut suit kernel.debug, pas le simple nom « dev » ou « prod ».

Retour à la réalité technique : une absence tolérée ne corrige pas une faute de variable. default, is defined et ?? traitent explicitement l'absence, mais leurs critères ne sont pas interchangeables, notamment pour false ou une valeur vide. Dans les globals configurées, @id référence un service et @@texte conserve un @ littéral.

🧠 Comment le mémoriser : « Changer la tolérance ne remplit pas la case. » Image mentale : case vide sous deux règlements, bloquant ou permissif. Question-réflexe : donnée facultative, faute de nom ou mauvais réglage de strictness ?

⚠️ À ne pas confondre : configuration de rendu, validité des données et valeurs de repli.

Les commands

À retenir en priorité
  1. lint:twig détecte les erreurs de syntaxe.
  2. debug:twig inventorie les extensions et paths disponibles.

Où en est-on ? Étape 5 sur 5 : quand « ça ne marche pas », on diagnostique dans l'ordre du chemin d'exécution : résolution (quel fichier ?), puis compilation (la syntaxe est-elle valide ?), puis exécution (les données sont-elles là ?). Deux commandes couvrent les deux premières.

Si le bandeau n'apparaît pas, cherche d'abord quel fichier le loader choisit avec debug:twig. Si ce fichier est le bon mais ne compile pas, utilise le lint. Un lint réussi ne rend pas ArticleView : il ne prouve ni la présence de article au runtime ni la validité des liens générés pendant le rendu.

  • debug:twig — filters, functions, tests, globales et paths ; avec un nom de template, le file qui le sert : « Matched File », puis les « Overridden Files » qu'il masque ; --filter restreint la liste.
  • lint:twig — vérifie la syntaxe sans rendre, et sort avec le code 1 en cas d'erreur ; --show-deprecations traite les deprecations comme des erreurs.
php bin/console debug:twig @AcmeBlog/user/profile.html.twig
   ▼
Matched File      → templates/bundles/AcmeBlogBundle/user/profile.html.twig
Overridden Files  → vendor/…/AcmeBlogBundle/…/user/profile.html.twig  (masqué)
Question Commande Ce qu'elle prouve Ce qu'elle ne prouve pas
Quel fichier est servi ? debug:twig <nom> résolution du nom que le template compile
La syntaxe est-elle valide ? lint:twig compilation possible que article existe au runtime
Le rendu est-il correct ? un test de rendu exécution avec données —

🌍 In Real Life

La situation : avant d'imprimer, on vérifie quel modèle a été sorti du classeur, puis si ses instructions sont lisibles. Ces contrôles ne prouvent pas que les données du client rempliront correctement chaque case.

L’équivalent dans Symfony : debug:twig expose l'environnement et le fichier résolu, avec ceux qu'il masque. lint:twig contrôle la syntaxe sans exécuter le rendu ; --show-deprecations rend aussi les dépréciations bloquantes pour ce contrôle.

Retour à la réalité technique : un lint réussi ne prouve ni la présence runtime de article, ni le succès de path(), ni la réponse finale. Le code de sortie concerne la commande. Ces outils complètent un test de rendu, ils ne le remplacent pas.

🧠 Comment le mémoriser : « Bon modèle, syntaxe correcte, rendu encore à vérifier. » Image mentale : modèle identifié et relu, cases client encore vides. Question-réflexe : ai-je contrôlé la résolution, la compilation ou l'exécution avec de vraies données ?

⚠️ À ne pas confondre : inspection de l'environnement Twig, lint et test de rendu.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Trois packages, un seul à installer.

    Trois packages, un seul à installer. L'engine, le bridge et le bundle sont distincts : le bundle tire les deux autres et expose la configuration Symfony sous twig:. Twig reste configurable sans le bundle, directement via son Environment et ses loaders. Pourquoi on se trompe : on lit « twig/twig » et « symfony/twig-bundle » comme deux alternatives, alors que l'un dépend de l'autre.

  • Voir l’explication : Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde.

    Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde. @AcmeBlog/... d'un côté, templates/bundles/AcmeBlogBundle/ de l'autre. Pourquoi on se trompe : les deux noms désignent le même bundle, on suppose donc qu'ils s'écrivent pareil ; normalizeBundleName ne retire le suffixe que pour le namespace.

  • Voir l’explication : strict_variables n'a pas la même valeur partout.

    strict_variables n'a pas la même valeur partout. Par défaut elle vaut kernel.debug. Pourquoi on se trompe : on l'associe au nom de l'environnement (« dev » / « prod ») alors que c'est le drapeau debug qui compte.

  • Voir l’explication : Le directory par défaut se change, mais on peut aussi en ajouter.

    Le directory par défaut se change, mais on peut aussi en ajouter. Ce sont deux options différentes : l'une remplace, l'autre complète. Pourquoi on se trompe : les deux parlent de « directories de templates ».

  • Voir l’explication : @AcmeBlog et @!AcmeBlog ne sont pas interchangeables dans un extends de surcharge.

    @AcmeBlog et @!AcmeBlog ne sont pas interchangeables dans un extends de surcharge. Le premier boucle sur la surcharge, le second atteint l'original. Pourquoi on se trompe : le point d'exclamation ressemble à une négation et on ne devine pas qu'il désigne le namespace « bundle seul ».

  • Voir l’explication : Un lint:twig vert n'est pas un rendu réussi.

    Un lint:twig vert n'est pas un rendu réussi. Il valide la syntaxe, rien de plus. Pourquoi on se trompe : « vert » évoque « tout fonctionne ».

Application

À retenir en priorité
  1. lint:twig détecte les erreurs de syntaxe.
  2. debug:twig inventorie les extensions et paths disponibles.
  3. La surcharge prend priorité sur l'original.
  4. @! permet de reprendre l'original sans récursion.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Engine, bridge, bundle : le bundle tire les deux autres et configure.
  • default_path remplace templates/ ; paths ajoute.
  • Namespace de bundle sans suffixe (@AcmeBlog) ; surcharge dans templates/bundles/AcmeBlogBundle/ ; original : @!AcmeBlog.
  • strict_variables = %kernel.debug% ; default, is defined, ?? passent toujours.
  • globals : @ service, @@ littéral.
  • debug:twig <nom> dit qui sert ; lint:twig sort en 1 sur erreur.

Moyen mnémotechnique : « la surcharge d'abord, le bang pour l'original ».

twig/twig ← twig-bridge ← twig-bundle (configure) ; templates/ + paths (@Nom) ;
@AcmeBlog = surcharge puis bundle ; @!AcmeBlog = bundle ;
