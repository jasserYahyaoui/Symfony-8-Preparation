Objectif

Le provider doit rendre Alice, pas un tableau arbitraire. Quel objet Security attend-il pour reconnaître cette lectrice ou rédactrice ? Nous construisons le contrat minimal, puis suivons ce qui reste dans son token lorsqu'elle revient sur /blog/42.

Question du cours : de quoi est fait un « user » pour Symfony, comment est-il comparé quand Alice revient, et où refuse-t-on un compte suspendu ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le contrat user comporte deux methods.
  2. Le password relève d'une autre interface.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Security ne connaît ni votre table ni votre ORM : il lui faut un contrat minimal pour identifier quelqu'un.
  • Le piège de fond. Croire que le user contient tout (password, rôle minimal, statut). En 8.0, le contrat est volontairement minuscule.
  • Ce que l'auteur veut que vous compreniez. Deux méthodes, un password dans une interface à part, une comparaison au refresh, un user checker pour les comptes interdits.
  • Pourquoi c'est à l'examen. eraseCredentials() retirée, ROLE_USER est une convention, isEqualTo() remplace la comparaison, le checker n'agit qu'à la connexion.

En 8.0, UserInterface n'a que deux methods. Le password vit dans une interface séparée. Lors de la restauration d'un token de session, le user rechargé est comparé à celui du token. Un compte suspendu se refuse à l'authentification dans un user checker, pas dans getRoles().

UserInterface                      getRoles()  +  getUserIdentifier()
PasswordAuthenticatedUserInterface getPassword()   (optionnelle)
EquatableInterface                 isEqualTo()     (optionnelle)
UserCheckerInterface               checkPreAuth / checkPostAuth (à part)

Le schéma

À retenir en priorité
  1. La relecture peut invalider le token.
  2. La comparaison détecte les changements importants.

Où en est-on ? Carte du cours : la vie d'un user en deux moments. La connexion (le checker juge l'admissibilité), puis la requête suivante (le refresh juge la continuité).

La connexion et la requête suivante sont deux moments distincts. Le checker juge l'admissibilité du compte pendant l'authentification ; le refresh vérifie la continuité d'un contexte déjà établi.

Bleu : appels ; ambre : validations ; vert : issue. Le pointillé traverse deux requêtes via la session, pas via un appel direct. Vue du password et du refresh standard, hors pré-authentification ; le statut ou redirect d'échec dépend de l'authenticator. Un firewall lazy peut différer la restauration.

L'exemple

Exemple concret

À retenir en priorité
  1. ROLE_USER est une convention.
  2. Une identité sans role peut être authentifiée.

Où en est-on ? Une classe User minimale. On y repère les deux méthodes du contrat, getPassword() (autre interface) et le ROLE_USER ajouté par notre code.

Avec Security Core 8.0 et son autoload, cette classe représente une identité à mot de passe, indépendamment de tout stockage :

use Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface;
use Symfony\Component\Security\Core\User\UserInterface;

class User implements UserInterface, PasswordAuthenticatedUserInterface
{
    public function __construct(
        private string $email,
        private ?string $password,
        private array $roles = [],
    ) {}

    public function getUserIdentifier(): string { return $this->email; }        // pas l'id SQL
    public function getRoles(): array { return [...$this->roles, 'ROLE_USER']; } // convention
    public function getPassword(): ?string { return $this->password; }          // interface à part
}

Ce modèle stocke un hash, pas le mot de passe en clair. Il n'a pas de champ transitoire à exclure ; si le modèle en ajoute, définir une sérialisation qui l'omet et tester sa restauration. __serialize() contrôle les données persistées : il n'efface pas un secret déjà présent en mémoire.

Pour une entrée fictive alice@example.test, getUserIdentifier() rend cette chaîne ; le provider doit savoir la rechercher. Avec des rôles directs vides, cette implémentation rend tout de même ['ROLE_USER'] parce que notre code l'ajoute. Construire cet objet ne connecte personne.

Appel sur new User('alice@example.test', $hash) Résultat
getUserIdentifier() alice@example.test
getRoles() ['ROLE_USER'] (ajouté par la classe)
getPassword() le hash

`UserInterface`, en 8.0

À retenir en priorité
  1. Ne pas dépendre de l'ancien appel automatique.
  2. Écarter les données sensibles de la sérialisation.

Où en est-on ? Étape 1 sur 5 : le contrat lui-même. Question : que doit vraiment fournir un user, et qu'a-t-on retiré en 8.0 ?

Le contrat ne dicte ni table, ni email obligatoire, ni mot de passe. Voici une identité de lecture sans mot de passe, conservée depuis le passage P10 et utilisable par un mécanisme qui vérifie sa propre preuve :

final class ReaderIdentity implements UserInterface
{
    public function __construct(private string $identifier) {}
    public function getUserIdentifier(): string { return $this->identifier; }
    public function getRoles(): array { return ['ROLE_READER']; }
}

Le fragment utilise l'import précédent de UserInterface. Le contrat suivant est un extrait de référence, pas une interface applicative à redéclarer :

interface UserInterface
{
    public function getRoles(): array;
    public function getUserIdentifier(): string;
}
  • eraseCredentials() n'existe plus (dépréciée en 7.3, retirée en 8.0) ; le CHANGELOG renvoie à __serialize() pour écarter les données sensibles. Une class peut encore la déclarer, mais ne doit plus attendre son appel automatique par ce mécanisme Symfony.
  • getUserIdentifier() rend l'identifier de recherche — email, login —, celui que reçoit loadUserByIdentifier(), pas forcément la key primaire.

Pourquoi un contrat si petit ? Pour ne rien imposer sur le stockage : le même contrat sert un user en base, un user en mémoire ou une identité d'API.

`getRoles()` : aucun minimum imposé

À retenir en priorité
  1. Le user fournit ses roles directs.
  2. La décision calcule les roles atteignables.

Où en est-on ? Étape 2 sur 5 : le contenu de getRoles(). Question : le framework impose-t-il un rôle de base ?

Ajouter ROLE_USER est une convention de la class, pas une exigence : un user dont getRoles() rend [] se connecte, IS_AUTHENTICATED_FULLY est vrai, mais isGranted('ROLE_USER') est faux.

Ce résultat suppose une authentification complète et les voters usuels, sans règle applicative accordant ce rôle. Il ne faut donc pas vider les rôles pour interdire la connexion d'un compte suspendu. La hiérarchie, lorsqu'elle existe, enrichit la décision, pas ce tableau.

getRoles() = []   ─►  connecté : OUI
                      IS_AUTHENTICATED_FULLY : vrai
                      isGranted('ROLE_USER')  : FAUX

Le password est une interface séparée

À retenir en priorité
  1. Un user peut exister sans password.
  2. Le contrat password reste séparé.

Où en est-on ? Étape 3 sur 5 : où vit le mot de passe. Question : pourquoi n'est-il pas dans UserInterface ?

🌍 In Real Life

La situation : le secrétariat du blog connaît l'identifiant et les fonctions d'Alice. Une fiche complémentaire n'existe que si sa connexion utilise un mot de passe.

L’équivalent dans Symfony : contrat d'identité → UserInterface ; capacité à fournir un hash de mot de passe → PasswordAuthenticatedUserInterface.

Retour à la réalité technique : une identité sans mot de passe peut être authentifiée par un autre mécanisme vérifié. getPassword() fournit un hash, pas le secret en clair ; les interfaces ne prescrivent aucun stockage particulier.

🧠 Comment le mémoriser : « Identité de base, capacité supplémentaire. » Image mentale : fiche principale avec volet optionnel. Question-réflexe : ce mécanisme a-t-il réellement besoin d'un mot de passe ?

⚠️ À ne pas confondre : absence de mot de passe local et absence de preuve d'authentification.

Un user peut ne pas avoir de password (token d'API, identité externe) : getPassword() vient de PasswordAuthenticatedUserInterface, l'interface que le hasher attend.

getPassword() rend un hash ou null, jamais la preuve saisie à conserver pour la prochaine requête. La branche /inscription valide la saisie puis la hache ; la simple construction de ReaderIdentity ne réalise aucune de ces opérations.

Comparer deux users

À retenir en priorité
  1. La comparaison personnalisée remplace la règle normale.
  2. Elle peut conserver un token malgré des données modifiées.

Où en est-on ? Étape 4 sur 5 : le retour d'Alice. Question : comment Symfony décide-t-il que le user relu est « le même » que celui du token ?

🌍 In Real Life

La situation : au retour d'Alice, l'accueil compare sa fiche actuelle à celle de la visite précédente. Changer les critères de comparaison peut conserver un ancien laissez-passer sans en réécrire les mentions.

L’équivalent dans Symfony : comparaison → contrôle de continuité lors du refresh ; critères personnalisés → EquatableInterface ; mentions du laissez-passer → rôles du token.

Retour à la réalité technique : la comparaison personnalisée remplace le contrôle standard. Déclarer les utilisateurs égaux ne reconstruit pas automatiquement les rôles du token et peut maintenir une session après un changement sensible.

🧠 Comment le mémoriser : « Conserver n'est pas réémettre. » Image mentale : ancienne carte à côté d'une fiche actualisée. Question-réflexe : quels changements doivent invalider ce contexte ?

⚠️ À ne pas confondre : utilisateur rechargé et token nouvellement authentifié.

Lors de la restauration effective d'un token avec état, ContextListener::hasUserChanged() compare le user rechargé à celui du token : password, roles, identifier. Une différence abandonne le token. Une class EquatableInterface remplace cette règle par isEqualTo().

Class Changement Request suivante
ordinaire ROLE_EDITOR ajouté, ou password changé déconnectée
isEqualTo() ne comparant que l'identifier ROLE_EDITOR ajouté connectée, mais isGranted('ROLE_EDITOR') faux
la même password changé toujours connectée

Le token garde les roles de la connexion : c'est lui que les voters lisent.

Pourquoi « connectée mais ROLE_EDITOR faux » ? Parce que isEqualTo() dit seulement « garde ce token ». Le token n'est pas reconstruit : ses rôles restent ceux de la connexion, et ce sont eux que lisent les voters.

Dans le code, la comparaison personnalisée du user original est consultée avant les contrôles standard. Sinon les rôles relus sont comparés aux rôles du token, pas à une hiérarchie recalculée sur le user. Le tableau suppose ce parcours normal, sans nouvelle authentification ni remplacement explicite du token. Une égalité trop permissive peut conserver une session après un changement que l'équipe voulait révoquer.

Connexion : token.roles = [ROLE_USER]
   (en base : on ajoute ROLE_EDITOR)
Requête suivante :
   classe ordinaire         roles différents ─► token abandonné
   isEqualTo(identifier)    « égaux »         ─► token gardé,
                                                 roles du token = [ROLE_USER]

Interdire un compte

À retenir en priorité
  1. Le statut du compte relève du user checker.
  2. Vider les roles n'empêche pas l'authentication.

Où en est-on ? Étape 5 sur 5 : refuser un compte suspendu. Question : à quel moment le user checker agit-il, et que devient une session déjà ouverte ?

🌍 In Real Life

La situation : le bureau du blog contrôle l'admissibilité d'Alice lors de la délivrance de son laissez-passer. La suspendre ensuite exige aussi une politique pour les laissez-passer déjà émis.

L’équivalent dans Symfony : contrôle d'admission → user checker configuré ; laissez-passer existant → token de session ; retrait ultérieur → révocation ou comparaison adaptée.

Retour à la réalité technique : les contrôles pre/post-auth concernent l'authentification ; la seule restauration d'un token ne les rejoue pas. Un checker n'est donc pas une vérification automatique de suspension sur chaque lecture d'article.

🧠 Comment le mémoriser : « Contrôler l'entrée, prévoir aussi la révocation. » Image mentale : poste d'émission et registre des cartes retirées. Question-réflexe : que deviennent les sessions déjà ouvertes ?

⚠️ À ne pas confondre : admissibilité du compte et droit métier sur l'article 42.

Un compte suspendu ou expiré se refuse dans un user checker (UserCheckerInterface), déclaré par user_checker sur le firewall :

  • checkPreAuth() écoute CheckPassportEvent en priority 256, avant la vérification du password — il tourne même si le password est faux ;
  • checkPostAuth(UserInterface $user, ?TokenInterface $token = null) tourne après le succès ;
  • la seule restauration d'un token de session ne rappelle pas ces checkers ; une nouvelle authentification est un autre chemin.

Si Alice est suspendue alors qu'elle possède déjà une session, prévoir aussi sa révocation ou une politique de comparaison adaptée. Le checker de connexion n'est pas un contrôle automatique de chaque lecture d'article. Une erreur de checkPreAuth() peut survenir avant la validation du password ; son exposition doit respecter la configuration étudiée précédemment.

Connexion :  CheckPassportEvent (256) ─► checkPreAuth(user)
             vérification du password
             AuthenticationSuccessEvent ─► checkPostAuth(user, token)
Requête avec cookie de session : AUCUN user checker

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le token garde les roles de la connexion.
  2. Une nouvelle authentication peut être nécessaire.
  • Construction, authentification et restauration

    Pour chaque question, identifier le moment : objet construit, nouvelle authentification ou contexte restauré. Les mêmes méthodes ne tournent pas à chacun de ces moments.

  • Voir l’explication : UserInterface n'a que deux methods en Symfony 8.0

    UserInterface n'a que deux methods en Symfony 8.0 ; eraseCredentials() a été retirée. Pourquoi on se trompe : les anciens tutoriels et la 6.x montrent trois méthodes.

  • Voir l’explication : getPassword() vient de PasswordAuthenticatedUserInterface.

    getPassword() vient de PasswordAuthenticatedUserInterface. Pourquoi on se trompe : on la croit dans UserInterface à cause des anciennes versions.

  • Voir l’explication : getUserIdentifier() n'est pas nécessairement la clé de base de données

    getUserIdentifier() n'est pas nécessairement la clé de base de données : il peut coïncider avec elle si le provider recherche ainsi le user. Pourquoi on se trompe : « identifier » évoque un id SQL.

  • Voir l’explication : Un user sans role est authentifié

    Un user sans role est authentifié ; ROLE_USER est une convention. Pourquoi on se trompe : tous les exemples ajoutent ROLE_USER, ça ressemble à une règle.

  • Voir l’explication : Les roles sont déjà comparés par défaut

    Les roles sont déjà comparés par défaut : en changer déconnecte. Pourquoi on se trompe : on imagine que le refresh met simplement à jour les rôles.

  • Voir l’explication : Le token fige les roles de la connexion

    Le token fige les roles de la connexion, même quand isEqualTo() garde le user connecté. Pourquoi on se trompe : on confond user rechargé et token réémis.

  • Voir l’explication : Un compte désactivé relève d'un user checker

    Un compte désactivé relève d'un user checker, appelé à la connexion seulement. Pourquoi on se trompe : « vérifié à chaque requête » semble plus sûr, donc on le suppose.

Fiche express

À mémoriser

À retenir en priorité
  1. Le contrat porte sur la recherche d'identité.
  2. Un email ou login peut servir d'identifier.

Le contrat d'Alice est établi ; son identité ne dit toujours pas si elle peut modifier 42. Les rôles expliquent les permissions globales et les voters les décisions sur un article.

🧠 À retenir pour la certification :

  • UserInterface : getRoles() et getUserIdentifier(), rien d'autre.
  • eraseCredentials() retirée ; __serialize() contrôle la persistance, mais n'efface pas un secret déjà présent en mémoire.
  • getPassword() : PasswordAuthenticatedUserInterface.
  • ROLE_USER : convention, pas obligation.
  • Comparaison par défaut : password, roles, identifier.
  • isEqualTo() remplace tout ; le token fige les roles.
  • User checker à la connexion : checkPreAuth() avant le password.

Moyen mnémotechnique : « Deux methods, trois comparaisons, un checker à la porte ».

UserInterface = getRoles + getUserIdentifier ;
password = PasswordAuthenticatedUserInterface ;
hasUserChanged (password, roles, identifier) ou isEqualTo ;
user checker : pre (CheckPassportEvent, 256), post
