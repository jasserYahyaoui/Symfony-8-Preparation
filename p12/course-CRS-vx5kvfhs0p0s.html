Objectif

Le template affiche un titre vide et vous ne savez pas pourquoi. Avant de deviner, vous voulez regarder ce que contient la variable. Ce cours montre comment l'afficher, où le résultat apparaît selon la forme choisie, pourquoi cet outil disparaît (ou casse tout) en production, et quelles commandes contrôlent un template sans le rendre.

Inspecter le contenu d'une variable dans un template, savoir où le résultat apparaît, et ce qui se passe hors du développement.

L'essentiel

À comprendre

À retenir en priorité
  1. La disponibilité dépend des extensions et du mode debug.
  2. Retirer les dumps avant publication.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Voir une donnée sans passer par un débogueur PHP.
  • Le piège de fond. « dump » n'est pas une seule chose : une function et un tag, deux destinations, et leur existence dépend des extensions chargées plus que du nom de l'environnement.
  • Ce que l'auteur veut que vous compreniez. Un dump() oublié ne s'ignore pas en production : la compilation échoue.
  • Pourquoi c'est à l'examen. Les QCM croisent DebugBundle × kernel.debug, les named arguments refusés et le code de sortie de lint:twig.

dump existe en function et en tag, qui n'écrivent pas au même endroit. Les deux viennent de DebugBundle, actif en dev et test : un dump() oublié en production fait échouer la compilation. Deux commands inspectent les templates sans les rendre.

{{ dump(x) }}   function : écrit dans le HTML, à l'endroit de l'appel
{% dump x %}    tag      : envoie à VarDumper (toolbar), page intacte

Le schéma

À retenir en priorité
  1. La function modifie le contenu de la page.
  2. Le tag utilise l'intégration de debug.

Où en est-on ? Vue d'ensemble : deux questions décident de tout — « DebugBundle est-il chargé ? » puis « kernel.debug est-il actif ? ». Quatre combinaisons, quatre comportements ; les sections suivantes les détaillent.

DebugBundle chargé ?
 ├─ oui ─ kernel.debug ?
 │         ├─ oui : function = HTML dans la page ; tag = vers la toolbar
 │         └─ non : function et tag ne font rien
 └─ non ─ kernel.debug ?
           ├─ oui : function Twig = var_dump dans la page ; tag inconnu
           └─ non : compilation en erreur (dump inconnu)

Ambre = configuration ; bleu = destination ou absence de sortie. Cette vue conserve les quatre cas utiles, avec la configuration standard où twig.debug suit kernel.debug. Ce sont les extensions chargées et Environment::isDebug(), pas le nom prod, qui décident réellement du résultat. Le tag utilise VarDumper : la toolbar est la destination habituelle lorsque son collecteur est actif, pas une dépendance obligatoire du tag.

Deux formes, deux destinations

Où en est-on ? Étape 1 sur 3 : le cas normal (DebugBundle + debug). On compare la function et le tag, qui font le même travail avec une destination différente.

Si le titre de l'article 42 manque, inspecte article dans un environnement local avec des données de test. La function écrit dans le HTML de la page ; le tag passe par VarDumper et son collecteur éventuel. Choisir le tag évite de modifier la structure HTML, mais ne rend pas les données collectées publiques ou sans risque : évite secrets et contexte complet.

Écriture Où va le résultat
{{ dump(article) }} dans la page, à l'endroit de l'appel
{% dump articles %} dans la debug toolbar, la page reste intacte
  • Sans argument, {{ dump() }} comme {% dump %} sortent tout le contexte du template, macros exclues.
  • Le tag nomme ce qu'il affiche : {% dump articles, user %}.
  • La function n'accepte que des arguments positionnels : l'exemple de la documentation {{ dump(blog_posts: articles, user: app.user) }} lève SyntaxError: Unknown arguments avec Twig 3.22.

Mécanisme : la function est une TwigFunction qui retourne du HTML ; Twig l'écrit à la place de {{ … }}. Le tag, lui, est compilé en un appel VarDumper::dump(...) qui ne retourne rien : il n'écrit pas dans la page.

{{ dump(article) }}
   ▼
DumpExtension::dump() → renvoie le HTML (sf-dump)  ▶ écrit dans la page

{% dump article %}
   ▼
code compilé : if (isDebug()) { VarDumper::dump($article); }
   ▼
VarDumper → collecteur DebugBundle → debug toolbar        (page intacte)

Pourquoi choisir le tag dans un <table> ? Un {{ dump() }} insère du HTML au milieu du tableau et le déforme ; le tag laisse la page telle quelle.

🌍 In Real Life

La situation : l'imprimeur peut inscrire sa note de contrôle directement sur l'épreuve ou l'envoyer au carnet de diagnostic de l'atelier. La première option modifie le document ; la seconde dépend du circuit de collecte installé.

L’équivalent dans Symfony : la fonction dump() produit une sortie à l'endroit affiché dans le template ; le tag transmet les données à VarDumper. La toolbar les présente lorsque le collecteur correspondant est actif.

Retour à la réalité technique : « hors du HTML » ne signifie pas « confidentiel par nature ». Inspecte localement des données de test minimales, pas les secrets ni tout le contexte. Dans l'intégration Symfony 8.0/Twig 3.22 décrite, ne transpose pas les arguments nommés d'autres fonctions à dump() ; le tag dispose de sa propre syntaxe de nomination.

🧠 Comment le mémoriser : « Note sur l'épreuve ou note au carnet. » Image mentale : document annoté face au carnet de contrôle séparé. Question-réflexe : où part ce diagnostic et qui peut le consulter ?

⚠️ À ne pas confondre : sortie du template, collecte VarDumper, affichage de toolbar et confidentialité.

La valise de diagnostic affiche les mêmes données soit sur le tableau de bord, soit sur une console d'atelier. De même, la function dump imprime dans la page, tandis que le tag utilise la destination de debug.

Hors du développement

Où en est-on ? Étape 2 sur 3 : que devient dump quand kernel.debug est éteint, ou quand DebugBundle n'est pas installé ? Quatre combinaisons à connaître par cœur.

Le passage en production change normalement les extensions disponibles. Un template qui compilait avec dump peut alors échouer avant d'afficher le titre. Vérifie la configuration réelle plutôt que le seul nom de l'environnement et retire le diagnostic ; activer debug publiquement n'est pas une correction acceptable de ce défaut.

DebugBundle enregistre l'extension (twig.extension.dump). Selon le cas :

DebugBundle kernel.debug {{ dump(x) }} {% dump x %}
oui oui dump HTML dans la page vers la toolbar
oui non rien rien
non oui var_dump brut de Twig tag inconnu
non non « Unknown function "dump" » tag inconnu

La production standard correspond à la dernière ligne : un dump() oublié fait échouer la compilation du template — l'« erreur PHP » que décrit la documentation. C'est délibéré : un dump divulguerait l'état interne de l'application.

Pourquoi « l'extension est absente » et « l'extension est muette » sont-ils deux cas distincts ? Dans le premier, le compilateur ne connaît pas le nom dump : il refuse le template entier, même si la branche n'est jamais rendue. Dans le second, l'extension existe, le template compile, et c'est au rendu que isDebug() coupe la sortie.

extension absente  → erreur à la COMPILATION (rien ne s'affiche, même le titre)
extension présente,
debug éteint       → compile, rend, mais dump ne produit RIEN

🌍 In Real Life

La situation : un atelier peut avoir un appareil de diagnostic installé mais éteint, ou ne pas posséder cet appareil du tout. Une consigne utilisant un outil absent n'est pas équivalente à une mesure volontairement silencieuse.

L’équivalent dans Symfony : les extensions chargées déterminent si fonction et tag sont connus ; le mode debug de Twig détermine ensuite leur activité dans les cas décrits. L'intégration native de Twig sans DebugBundle ne fournit pas nécessairement les mêmes opérations.

Retour à la réalité technique : « prod » n'est pas une règle magique du moteur. Une opération inconnue peut faire échouer la compilation même dans une branche qui ne serait jamais rendue ; une opération enregistrée mais inactive est un autre cas. Retire le diagnostic avant publication plutôt que d'activer debug publiquement pour faire disparaître l'erreur.

🧠 Comment le mémoriser : « Outil absent ou outil éteint : deux diagnostics. » Image mentale : emplacement vide à côté d'un appareil éteint. Question-réflexe : l'extension manque-t-elle ou son mode debug est-il désactivé ?

⚠️ À ne pas confondre : présence de l'extension, drapeau debug, nom d'environnement et absence de sortie.

Les commands

À retenir en priorité
  1. Le lint n'exécute pas les branches du template.
  2. Un test de rendu reste nécessaire pour les données runtime.

Où en est-on ? Étape 3 sur 3 : deux commandes qui répondent à d'autres questions que dump, sans rendre le template.

Pour cette panne, debug:twig répond « l'opération est-elle enregistrée ? » et lint:twig « le template compile-t-il ? ». Aucun ne prouve que show() passe un ArticleView sous le bon nom. Cette dernière vérification exige un rendu avec des données représentatives, sans publier un dump au lecteur.

  • php bin/console debug:twig — filters, functions, tests, globales et paths disponibles ; --filter=date restreint la liste.
  • php bin/console lint:twig templates/ — vérifie la syntaxe sans rendre : une variable indéfinie n'est pas détectée ; l'exit code vaut 1 en cas d'erreur. --show-deprecations traite les deprecations comme des erreurs.

Trois preuves, trois niveaux :

Question Outil Ce que ça prouve
L'opération existe-t-elle ? debug:twig inventaire des filters, functions, tests, globales
Le template compile-t-il ? lint:twig syntaxe correcte (variables non vérifiées)
La variable a-t-elle la bonne forme ? rendu réel / dump contrat controller ↔ template

Pourquoi lint:twig ne voit-il pas une variable indéfinie ? Il compile sans exécuter : une variable n'est lue qu'au rendu, avec un contexte réel qu'il n'a pas.

🌍 In Real Life

La situation : avant un tirage, on vérifie l'inventaire des outils puis la lisibilité des consignes. Cela ne remplace pas un essai avec les vraies catégories de données à imprimer.

L’équivalent dans Symfony : debug:twig inventorie les opérations et ressources connues de l'environnement chargé ; lint:twig contrôle la compilation sans rendre le template. Un rendu représentatif vérifie ensuite le contrat entre contrôleur et template.

Retour à la réalité technique : un lint réussi ne prouve pas qu'article existe à l'exécution ni que sa propriété attendue est accessible. L'environnement vérifié doit correspondre à la cible de déploiement. Le code de sortie de la commande est un résultat de processus, pas un statut HTTP de la page.

🧠 Comment le mémoriser : « Inventaire, consignes, essai : trois preuves différentes. » Image mentale : liste d'outils, fiche relue, puis épreuve avec données. Question-réflexe : ai-je vérifié la disponibilité, la compilation ou réellement le rendu ?

⚠️ À ne pas confondre : introspection de configuration, lint syntaxique et test de rendu.

Pièges d'examen

Piège à éviter

  • Voir l’explication : La function et le tag n'écrivent pas au même endroit.

    La function et le tag n'écrivent pas au même endroit. Pourquoi on se trompe : les deux s'appellent « dump », on les croit interchangeables.

  • Voir l’explication : Sans extension de dump chargée, la function n'existe pas

    Sans extension de dump chargée, la function n'existe pas : erreur à la compilation, pas un avertissement. Pourquoi on se trompe : on croit qu'un outil de debug est simplement ignoré en production.

  • Voir l’explication : Sans argument, c'est tout le contexte qui sort.

    Sans argument, c'est tout le contexte qui sort. Pourquoi on se trompe : on imagine qu'un dump vide n'affiche rien.

  • Voir l’explication : Le tag indexe par nom de variable ; la function refuse les named arguments

    Le tag indexe par nom de variable ; la function refuse les named arguments avec Twig 3.22, malgré l'exemple de la documentation. Pourquoi on se trompe : on fait confiance à l'exemple de la doc, ou on généralise les named arguments d'autres functions.

Application

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Function : dans la page ; tag : vers la toolbar.
  • Sans argument : tout le contexte.
  • Function : arguments positionnels seulement ; tag : chaque variable nommée.
  • DebugBundle hors debug : rien.
  • Sans DebugBundle : debug → var_dump de Twig, tag inconnu ; sinon Unknown function.
  • debug:twig --filter=… : ce que Twig connaît.
  • lint:twig : syntaxe seulement, exit code 1 en cas d'erreur.

Moyen mnémotechnique : « accolades dans la page, tag dans la barre, prod sans bundle : erreur ».

{{ dump }} = page, {% dump %} = toolbar ; sans argument = tout le contexte ;
function sans named arguments ; DebugBundle + debug = actif, sans debug = muet ;
sans bundle : debug = var_dump de Twig, prod = Unknown function ; lint = syntaxe
