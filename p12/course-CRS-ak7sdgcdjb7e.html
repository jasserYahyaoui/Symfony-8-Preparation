Objectif

Poser un flash message, savoir où il est stocké et quand il disparaît.

Question fil rouge : après un POST réussi et une redirection, comment le GET suivant peut-il afficher « Vos modifications ont été enregistrées » une seule fois ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le flash message est une donnée de session.
  2. Son type est une string libre, pas une enum imposée.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une redirection (voir HTTP redirects) met fin à la Request : le contrôleur qui a réussi l'opération ne peut pas « passer » un message à la page suivante, qui est une autre Request. Il faut un relais entre deux requêtes : la session.
  • Le piège de fond. Un flash est à consommation unique : le lire le retire. Le même message demandé deux fois (layout + corps de page) n'est affiché qu'une fois.
  • Ce que l'auteur veut que vous compreniez. La différence entre ce qui consomme (get, all, clear) et ce qui regarde (peek, peekAll), et entre add() qui empile et set() qui écrase.
  • Pourquoi c'est à l'examen. Ces distinctions, plus la LogicException de addFlash() sans session, sont des classiques de QCM.

En résumé : un flash message est un message de session utilisé une seule fois : il disparaît dès qu'il est lu. C'est l'outil du Post / Redirect / Get : traiter, poser un message, rediriger, l'afficher. Tout tient dans la différence entre ce qui consomme et ce qui regarde — et entre add(), qui empile, et set(), qui écrase.

Le support de stockage (session, son démarrage paresseux) est expliqué dans The session : un flash est un FlashBag, un sac particulier de la session.

Le schéma

À retenir en priorité
  1. get() consomme un type ; all() consomme tout.
  2. peek() et peekAll() consultent sans consommer.

Où en est-on ? Le cours suit trois étapes : ce que c'est (où vit le message), poser (comment l'ajouter), lire (consommer ou regarder, et le piège qui en découle). Le schéma ci-dessous porte sur les étapes « poser » et « lire » : on empile deux notices, puis on compare deux lectures.

Un flash message
   ├─ 1. Ce que c'est   → un message de SESSION, lu une fois
   ├─ 2. Poser          → addFlash() = getFlashBag()->add() ; set() remplace
   └─ 3. Lire           → get/all/clear CONSOMMENT ; peek/peekAll REGARDENT

Bleu = messages conservés, ambre = consommation. Le diagramme compare deux lectures alternatives du même état. Un flash non consommé n'expire pas simplement parce qu'une redirection a eu lieu ; sa durée reste celle du stockage de session.

Lecture : à partir de l'état « notice contient A et B », peek renvoie A, B et l'état reste identique ; get renvoie A, B et l'état devient « notice absent ». Un second get renvoie donc une liste vide.

L'exemple : après un enregistrement

Exemple concret

Où en est-on ? Le cas typique avant le détail : modifier, poser un flash, rediriger. C'est le Post / Redirect / Get complété par un message.

Après une modification réussie de l'article 42, la Response de redirection ne porte pas elle-même la confirmation HTML. Le flash est enregistré dans la session pour que la requête suivante puisse l'afficher. L'exemple historique utilise app_post_show ; dans le récit, la destination équivalente est blog_show avec id=42.

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;

final class EditController extends AbstractController
{
    public function afterSuccessfulEdit(): Response
    {
        $this->addFlash('notice', 'Vos modifications ont été enregistrées.');
        return $this->redirectToRoute('app_post_show', ['id' => 42], 303);
    }
}

Exemple de la branche après enregistrement réussi : la session est activée, le contrôleur enregistré, et la route app_post_show accepte l'identifiant 42.

Les deux requêtes en jeu :

Requête 1 : POST /post/42/edit               Requête 2 : GET /post/42
  ├─ enregistre l'article                      ├─ layout lit le FlashBag
  ├─ addFlash('notice', '…')  ─► SESSION ─────►│     get('notice') → ['Vos modif…']
  └─ 303 Location: /post/42                    │     (et le retire)
                                               └─ affiche la page avec le message
Requête 3 : F5 (rafraîchir le GET)  → le flash est consommé : plus de message

Ce que c'est

Où en est-on ? Étape 1 sur 3 : où vit ce message ? Réponse courte : pas dans le contrôleur, pas dans la Response, mais dans la session.

Le message traverse la frontière entre le POST terminé et le GET suivant grâce au stockage de session, pas grâce à une mémoire du contrôleur. Sa disparition dépend de l'opération de lecture : une redirection sans consommation ne l'efface pas. Il ne constitue donc ni une notification durable ni une preuve que son destinataire l'a effectivement vu.

Un flash est un message à consommation contrôlée : get() et all() consomment les messages lus, peek() et peekAll() les conservent. Dans l'application usuelle, la session assure leur continuité entre requêtes, généralement à l'aide d'un cookie ; un FlashBag isolé fonctionne aussi en mémoire. Le type — notice, warning, error — est une string libre.

Pourquoi la session et pas un paramètre d'URL ? Parce qu'un paramètre d'URL serait visible, rejouable au rafraîchissement et falsifiable ; la session reste côté serveur, identifiée par un cookie (voir The cookies).

Structure interne : un tableau type => [messages].

FlashBag
 ├─ 'notice'  => ['Vos modifications ont été enregistrées.']
 ├─ 'warning' => ['Quota presque atteint.', 'Mot de passe ancien.']
 └─ 'error'   => []          ← type présent mais vide : compte pour ABSENT

🌍 In Real Life

La situation : après le traitement d'un dossier, le bureau laisse une note de confirmation dans le casier du visiteur. Le guichet suivant pourra la reprendre ; l'agent n'a pas besoin de garder personnellement le souvenir de la visite.

L’équivalent dans Symfony : la session conserve le flash entre le POST réussi et le GET après redirection. Le type du message nomme un compartiment librement choisi, comme notice, et non un niveau imposé par une enum.

Retour à la réalité technique : un FlashBag seul peut fonctionner en mémoire ; la continuité HTTP exige l'intégration de session. Le flash disparaît par consommation, effacement ou fin de conservation du stockage, pas simplement parce que la redirection a eu lieu.

🧠 Comment le mémoriser : « La note attend dans le casier, pas dans la mémoire de l'agent. » Image mentale : note entre deux passages au guichet. Question-réflexe : qu'est-ce qui conserve le message entre ces deux requêtes ?

⚠️ À ne pas confondre : message temporaire et notification durable avec accusé de lecture ; consommation serveur et lecture humaine.

Poser

À retenir en priorité
  1. add() accumule les messages.
  2. set() remplace la liste du type.

Où en est-on ? Étape 2 sur 3 : comment ajouter un message ? Deux verbes, deux effets très différents : add() empile, set() écrase.

La branche de succès doit poser la confirmation après l'opération réussie, puis retourner la redirection. Si plusieurs traitements ajoutent des notices, add() préserve leurs messages ; un set() ultérieur les remplace pour ce type. La création du message utilise la session et peut donc affecter la politique de cache.

addFlash() équivaut strictement à $request->getSession()->getFlashBag()->add(). Il lève une LogicException si les sessions sont désactivées, ou si la session n'implémente pas FlashBagAwareSessionInterface. Le sac expose aussi set(), qui remplace tout le type : deux add() puis un set() ne laissent que le dernier message.

Vérifié dans AbstractController::addFlash() (8.0) : méthode protected addFlash(string $type, mixed $message): void ; elle obtient la session par request_stack->getSession() (une SessionNotFoundException est convertie en LogicException « You cannot use the addFlash method if sessions are disabled »), vérifie instanceof FlashBagAwareSessionInterface (sinon LogicException), puis appelle getFlashBag()->add($type, $message). Dans FlashBag, set($type, string|array $messages) fait $this->flashes[$type] = (array) $messages, d'où le remplacement complet.

Illustration add contre set :

add('notice', 'a')   →  notice: [a]
add('notice', 'b')   →  notice: [a, b]
set('notice', 'X')   →  notice: [X]          ← a et b sont perdus
set('notice', ['X','Y']) → notice: [X, Y]    ← set peut poser plusieurs messages
┌──────────────────────────────────────┐ ┌──────────────────────────────────────┐
│               add()                  │ │                set()                 │
├──────────────────────────────────────┤ ├──────────────────────────────────────┤
│ Effet sur le type : AJOUTE           │ │ Effet sur le type : REMPLACE         │
│ Messages précédents : conservés      │ │ Messages précédents : perdus         │
│ Via le helper : addFlash()           │ │ Via le helper : non (FlashBag direct)│
└──────────────────────────────────────┘ └──────────────────────────────────────┘

Pourquoi poser après le succès ? Parce qu'un flash annonce un résultat : le poser avant l'opération (ou sur un échec) afficherait une confirmation mensongère.

🌍 In Real Life

La situation : deux agents ajoutent chacun une note au compartiment « confirmations ». Un troisième peut soit ajouter sa note, soit remplacer toutes celles de ce compartiment par une nouvelle liste.

L’équivalent dans Symfony : add() ajoute un message au type ; set() remplace les messages de ce type. addFlash() passe par le FlashBag de la session disponible ; on l'appelle après le succès métier, avant de retourner la redirection.

Retour à la réalité technique : le helper nécessite une session compatible avec les flashs et ne transforme pas un échec métier en succès. Son usage implique un accès à la session, avec des conséquences possibles sur le cache ; il ne signifie pas qu'un nouveau cookie sera toujours émis.

🧠 Comment le mémoriser : « Ajouter une note n'est pas remplacer la pile. » Image mentale : note ajoutée au-dessus, puis pile entièrement remplacée. Question-réflexe : dois-je préserver les messages déjà ajoutés par d'autres traitements ?

⚠️ À ne pas confondre : type du flash, contenu du message et statut HTTP ; set() peut remplacer par plusieurs messages, pas seulement un.

Lire, et le piège

Où en est-on ? Étape 3 sur 3 : comment afficher, et pourquoi le même message disparaît-il parfois ? Le piège vient d'un seul fait : lire = retirer.

Au GET de retour sur l'article, le layout et le corps peuvent demander les mêmes notices. Si le layout fait déjà get('notice'), le corps ne retrouve plus rien : le premier appel a consommé le type. Choisis un emplacement de consommation, ou une consultation peek en amont, plutôt que de compter sur deux affichages identiques.

Method Effet
get('warning') / all() retourne les messages et les consomme
peek('warning') / peekAll() retourne les messages sans les consommer

get() ne vide que son type, all() vide tout ; clear() est un alias de all() — elle vide et retourne. Un type présent mais vide compte pour absent : has() répond false, et get() rend sa default value.

Vérifié dans FlashBag (8.0) : get($type, $default = []) rend $default si !has($type), sinon retourne $this->flashes[$type] puis le retire (unset) ; all() appelle peekAll() puis vide le tableau ; has() vaut array_key_exists(...) && $this->flashes[$type] (donc faux pour un array vide) ; clear() retourne $this->all().

Comparaison des méthodes de lecture

Méthode Portée Consomme ? Retourne
get($type, $default) un type oui (ce type seul) messages du type, ou le défaut
peek($type) un type non messages du type
all() tous les types oui (tout) tous les messages
peekAll() tous les types non tous les messages
clear() tous les types oui (alias de all()) tous les messages
has($type) un type non bool (faux si type vide)

Le piège du layout, étape par étape

GET /post/42  (flash 'notice' présent)
   ├─ layout.html.twig : app.flashes('notice')  → consomme  → affiché
   └─ post/show.html.twig : app.flashes('notice') → type absent → rien

Correction : consommer à UN seul endroit, ou regarder sans consommer :
   layout (en haut)  : app.session.flashbag.peekAll()   (ne retire rien)
   corps de page     : app.flashes   (une seule fois, consomme)

En Twig, app.flashes est le raccourci qui consomme (comme get/all selon l'appel) ; app.session.flashbag.peekAll() regarde sans consommer.

🌍 In Real Life

La situation : regarder les notes à travers la vitre du casier les laisse en place. Prendre les notes pour les afficher vide le compartiment : le second agent qui arrive n'y retrouve plus les mêmes notes.

L’équivalent dans Symfony : peek() consulte un type sans le vider ; get() le retourne et le consomme. peekAll() regarde l'ensemble ; all() et clear() retournent l'ensemble en le vidant. Le layout et le corps doivent donc coordonner leurs lectures.

Retour à la réalité technique : la consommation retire les messages du bag, pas les copies déjà retournées. Elle n'attend pas l'affichage effectif dans le navigateur. has() teste la présence de messages non vides sans les consommer ; l'accès à la session reste distinct de cette consommation.

🧠 Comment le mémoriser : « Regarder laisse ; prendre retire. » Image mentale : vitre transparente puis compartiment vidé. Question-réflexe : quel premier appel a pu prendre mes messages avant ce second affichage ?

⚠️ À ne pas confondre : get() du FlashBag, qui consomme, et get() d'un bag ordinaire ; consommer et sécuriser le HTML affiché.

Un flash est un post-it qu'on décolle après lecture. peek() permet seulement d'y jeter un œil : le lecteur suivant pourra toujours le consommer.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Lire un flash le consomme.

    Lire un flash le consomme. Afficher les messages deux fois dans la même page par le path ordinaire ne les affiche qu'au premier emplacement : la seconde lecture ne trouve plus rien. La consultation sans consommation existe, c'est une autre method. Pourquoi on se trompe : « lire » semble sans effet de bord, comme lire un attribut.

  • Voir l’explication : set() n'ajoute pas, elle remplace.

    set() n'ajoute pas, elle remplace. Deux add() puis un set() ne laissent qu'un message. Seul add() empile. Pourquoi on se trompe : set ressemble au set d'un bag ordinaire, mais ici on s'attend à un empilement.

  • Voir l’explication : clear() retourne les messages qu'elle efface.

    clear() retourne les messages qu'elle efface. Ignorer sa return value jette les messages. Pourquoi on se trompe : le nom évoque un void.

  • Voir l’explication : get() ne vide que son type.

    get() ne vide que son type. Vider tout demande all(). Pourquoi on se trompe : on suppose qu'une lecture consomme tout le sac.

  • Voir l’explication : La continuité entre requêtes est distincte du sac en mémoire.

    La continuité entre requêtes est distincte du sac en mémoire. Dans l'application usuelle, ajouter un flash via la session démarre celle-ci ; un FlashBag autonome ne requiert pas de cookie. Il faut distinguer l'usage de la session de l'émission d'un nouveau cookie. Pourquoi on se trompe : on confond le sac (mémoire) et le relais entre requêtes (session).

  • Voir l’explication : Le type du message est libre.

    Le type du message est libre. notice, warning, error sont des usages, pas une enum imposée par le framework. Pourquoi on se trompe : la documentation n'utilise que ces trois noms.

  • Voir l’explication : Une redirection n'efface pas le flash.

    Une redirection n'efface pas le flash. Seule la consommation (ou la fin du stockage de session) le retire. Pourquoi on se trompe : on imagine un mécanisme « valable une requête ».

Revoir : L'essentiel

Where are flash messages stored?

With Symfony Session integration, flash messages are stored in the session. A standalone FlashBag keeps them only in memory and provides no persistence between requests; get()/all() consume them, peek()/peekAll() preserve them.

La persistance entre requêtes vient du stockage de session intégré, pas de FlashBag seul. get()/all() consomment les messages, peek()/peekAll() les conservent. Le type du flash est une string libre, pas une enum imposée.

Revoir : Le schéma

How do you read flash messages without consuming them?

Use peek() or peekAll(), not get() or all().

get() consomme un type ; all() consomme tout. peek() et peekAll() consultent sans consommer.
