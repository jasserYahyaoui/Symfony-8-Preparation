Objectif

La page /blog/42 fonctionne, mais le nombre d'articles par page doit varier entre les machines sans réécrire le contrôleur. Nous allons suivre une valeur depuis sa source jusqu'au service qui la consomme : emplacement, priorité, conversion et moment de résolution expliquent des pannes très différentes.

Quatre questions guident le cours, dans cet ordre :

  1. Quand la valeur est-elle fixée (compilation ou exécution) ?
  2. Quel fichier ou quelle variable gagne quand plusieurs la définissent ?
  3. Quel processeur la convertit (une variable est toujours une string) ?
  4. Comment écrire une petite règle d'une ligne avec ExpressionLanguage ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le système fournit la valeur prioritaire.
  2. Dotenv complète normalement les valeurs manquantes.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le même code doit tourner sur votre poste, en test et en production, avec des réglages différents (port, taille de page, URL de base de données). Symfony sépare donc ce qui est décidé par le projet (parameters) de ce qui est décidé par la machine (variables d'environment).
  • Le piège de fond. Trois questions se mélangent : « où est écrite la valeur ? », « qui gagne en cas de conflit ? », « quand est-elle lue ? ». La certification les sépare ; vous devez faire de même.
  • Pourquoi c'est à l'examen. Les questions portent sur l'ordre de la cascade .env, sur .env.local ignoré en test, sur .env.local.php, sur APP_DEBUG, sur l'ordre des processeurs et sur evaluate()/compile()/lint().

Un parameter est figé à la compilation du container ; une variable d'environment est lue à l'exécution. Les files .env se chargent en cascade — le dernier chargé gagne —, mais une vraie variable du serveur passe avant eux. Et ExpressionLanguage évalue ou compile une expression d'une ligne, écrite en configuration.

Ici, « à l'exécution » ne signifie pas « relu à chaque appel » : le container mémorise les valeurs d'environnement qu'il résout. Il faut distinguer la préparation du container, l'amorçage du processus et l'utilisation d'un service déjà construit.

Le schéma

À retenir en priorité
  1. Le moment de résolution diffère.
  2. Un placeholder permet de garder une valeur dépendante du serveur.

Où en est-on ? Ce cours suit une valeur en quatre étapes : (1) deux mécanismes et deux moments, (2) la cascade .env, (3) les processeurs, (4) ExpressionLanguage. Le schéma ci-dessous résume les étapes 2 et 3.

Valeur de config
   ├─ 1. Parameter (services.yaml)  → figé à la COMPILATION
   │      └─ peut contenir %env(...)% → référence DIFFÉRÉE
   ├─ 2. Variable d'environment     → lue à l'EXÉCUTION (puis mémorisée)
   │      └─ vraie variable > .env.<env>.local > .env.<env> > .env.local > .env
   ├─ 3. Processeur (int:, bool:, json:, base64:)  → convertit la string
   └─ 4. ExpressionLanguage → évalue / compile une règle d'une ligne

Lire le diagramme avec deux questions successives : quelle source fournit la chaîne, puis quel processeur la convertit ? Dotenv ne choisit pas les services, et un processeur ne décide pas quelle règle métier est autorisée.

Bleu : chargement/transformation ; ambre : choix ; vert : valeurs retenues. La priorité système s'applique aussi au dump PHP : il ne remplace pas automatiquement les vraies variables. Pour PORT=443, %env(int:PORT)% produit l'entier 443, pas la chaîne du fichier de développement.

L'exemple

Exemple concret

À retenir en priorité
  1. Les variables sont des strings.
  2. Le processor impose la conversion attendue.

Où en est-on ? Avant la théorie, un cas concret : le même mécanisme sert à un port serveur et à la taille de page du blog. Code minimal d'abord.

Le port ci-dessous illustre une valeur propre au serveur. Pour la pagination /blog/page/{page}, le même mécanisme peut fournir un BLOG_PAGE_SIZE :

parameters:
    app.blog_page_size: '%env(int:BLOG_PAGE_SIZE)%'

Avec la valeur fictive BLOG_PAGE_SIZE=20, le paramètre résolu vaut l'entier 20. Ce fragment ne l'injecte pas automatiquement dans un service : configurer l'argument qui en a besoin. La conversion int ne remplace pas la validation métier, par exemple exiger un nombre strictement positif.

Ce que Symfony voit :

Élément Ce que Symfony fait Ce qu'il ne fait pas
app.blog_page_size enregistre un parameter contenant une référence ne lit pas encore BLOG_PAGE_SIZE
%env(int:...)% résout la variable, la convertit en int ne vérifie pas que le nombre est > 0
le service consommateur reçoit la valeur si on configure son argument n'est pas câblé automatiquement par ce YAML

Les fragments suivants sont des configurations à lire, pas des fichiers d'environnement créés par ce cours :

# config/services.yaml
parameters:
    app.admin_email: 'admin@example.com'          # figé à la compilation
    app.port: '%env(int:PORT)%'                    # lu à l'exécution, converti
# .env          → PORT=8000           (versionné, valeur par défaut)
# .env.local    → PORT=8080           (ce poste, hors test)
# .env.prod     → PORT=80             (la production, versionné)
# serveur       → export PORT=443     (vraie variable : elle gagne)

Avant / après, pour PORT selon l'endroit où on regarde (en prod) :

.env            PORT=8000
.env.local      PORT=8080      ← chargé après .env : remplace 8000
.env.prod       PORT=80        ← chargé après .env.local : remplace 8080
serveur         PORT=443       ← vraie variable : gagne sur tous les files
                                 %env(int:PORT)% → l'entier 443

Deux mécanismes, deux moments

À retenir en priorité
  1. Le code compilé peut rester identique.
  2. La résolution fournit les valeurs propres à la machine.

Où en est-on ? Étape 1 sur 4 : avant de parler de fichiers, il faut savoir quand une valeur est décidée. Tout le reste en découle.

🌍 In Real Life

La situation : le manuel d'exploitation du blog fixe certaines règles, mais laisse une case pour la taille des lots propre au lieu de déploiement.

L’équivalent dans Symfony : règle intégrée au manuel → paramètre ordinaire compilé ; case à résoudre plus tard → référence %env(...)%.

Retour à la réalité technique : mettre une référence env dans parameters ne la transforme pas automatiquement en valeur déjà résolue à la compilation. Résolution à l'exécution ne signifie pas relecture du disque à chaque appel : le conteneur peut mémoriser la valeur.

🧠 Comment le mémoriser : « Une règle écrite peut contenir une case différée. » Image mentale : manuel imprimé avec un emplacement étiqueté. Question-réflexe : la valeur est-elle littérale, différée ou déjà résolue ?

⚠️ À ne pas confondre : préparation du conteneur et construction des objets qui reçoivent ces valeurs.

Pourquoi deux mécanismes ? Parce qu'on veut compiler le container une seule fois et le déployer partout. Si la valeur du port était écrite dans le container compilé, il faudrait recompiler pour chaque machine. Une variable d'environment reste donc une référence que l'on résout plus tard.

Parameter Variable d'environment
Écrit dans config/services.yaml, key parameters un file .env, ou le système
Référencé par %app.admin_email% %env(DATABASE_URL)%
Résolu à la compilation à l'exécution

C'est ce qui permet de déployer le même container compilé sur plusieurs machines. Une entrée parameters contenant %env(...)%, comme app.port, reste une référence différée : ne pas confondre son emplacement YAML avec le moment où sa valeur est résolue.

Les extensions de bundles chargent et interprètent leurs configurations ; les compiler passes transforment les définitions. L'autowiring raccorde les dépendances et l'autoconfiguration attribue des conventions comme les tags. Ces opérations préparent le container réutilisable : GET /blog/42 ne recommence pas cette compilation à chaque passage. À l'utilisation d'un placeholder, Container::getEnv() consulte son cache, sinon appelle le processeur et mémorise le résultat. Un worker d'import déjà lancé n'est donc pas un lecteur permanent des changements du serveur.

 COMPILATION (une fois)         AMORÇAGE du processus      UTILISATION
 ─────────────────────         ──────────────────────      ───────────────
 extensions, compiler passes   Dotenv lit les .env         getEnv(): cache ?
 autowiring, parameters        (ou le dump .env.local.php)   oui → valeur gardée
 %env()% = référence           variables d'environment       non → processeur
                                                              puis mémorisation

Les parameters

À retenir en priorité
  1. Le tag enum conserve le case.
  2. Ne pas le confondre avec sa backing value.

Où en est-on ? Suite de l'étape 1 : ce qui est décidé par le projet (les parameters) et ce qu'on peut y écrire.

Les langues disponibles appartiennent à la politique du projet, alors que sa taille de page peut être laissée au déploiement. Dans ce fragment, BlogPost::MAX_ITEMS et PostState::Published supposent des types PHP déjà définis et autoloadables ; le namespace ne configure aucune persistance :

parameters:
    app.supported_locales: ['en', 'es', 'fr']
    app.some_constant: !php/const App\Entity\BlogPost::MAX_ITEMS
    app.some_enum: !php/enum App\Enum\PostState::Published
  • !php/enum donne le case lui-même, l'object enum ; !php/const, la valeur de la constant.
  • Un % littéral se double : 'a %%s b' est lu a %s b.
  • Le préfixe app. est une convention.

Pourquoi doubler le % ? Parce que %nom% est la syntaxe de référence : un % isolé serait pris pour le début d'une référence. %% signifie « un vrai % ».

Écriture YAML Valeur résolue
'a %%s b' la string a %s b
!php/enum App\Enum\PostState::Published le case PostState::Published (object)
!php/const App\Entity\BlogPost::MAX_ITEMS la valeur de la constant

La cascade `.env`

À retenir en priorité
  1. Les tests évitent les réglages personnels généraux.
  2. Les couches propres à test restent disponibles.

Où en est-on ? Étape 2 sur 4 : la valeur vient d'une variable d'environment ; plusieurs fichiers peuvent la définir. Qui gagne ?

Supposons un import qui lit encore la taille 10 malgré une valeur locale 20. Avant de vider un cache, rechercher une vraie variable prioritaire, un dump applicable, puis l'ordre des fichiers. Les fichiers versionnés ne contiennent que des valeurs publiques par défaut, jamais des secrets.

File Portée Versionné
.env default values, tous environments oui
.env.local cette machine — ignoré en test non
.env.<env> un environment oui
.env.<env>.local cette machine, un environment non
  • Entre les files, le dernier chargé gagne, dans cet ordre : en dev, .env.dev l'emporte sur .env.local.
  • Une vraie variable d'environment l'emporte sur les files .env, qui ajoutent seulement ce qui manque — sauf si Dotenv est appelé avec overrideExistingVars: true. variables_order doit contenir E.
  • Sans dump, les fichiers sont lus à l'amorçage. Dans le modèle PHP par requête, cela se répète à chaque requête ; un worker long ne les relit pas automatiquement. Redémarrer ce worker après un changement de configuration.
  • composer dump-env prod écrit .env.local.php ; s'il existe, et si son APP_ENV correspond, les files .env ne sont plus analysés. La command dotenv:dump exige de déclarer le service DotenvDumpCommand.
  • bootEnv() fixe APP_DEBUG quand il manque : '1' si l'environment n'est pas prod (donc en dev, et aussi en test), '0' en prod ; c'est une string.
  • Syntaxe : #, ${AUTRE_VAR}, ${VAR:-defaut} ; guillemets simples = littéral, doubles = interpolation.

Pourquoi .env.local est-il ignoré en test ? Pour que les tests restent reproductibles : les réglages personnels d'un poste ne doivent pas changer le résultat de la suite de tests. .env.test.local reste, lui, chargé.

Ordre de chargement, en dev, du plus faible au plus fort :

.env  →  .env.local  →  .env.dev  →  .env.dev.local  →  vraie variable
(faible)                                                      (la plus forte)

en test : .env → .env.test → .env.test.local   (.env.local est sauté)

Comparaison des deux modes de lecture :

┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│       SANS .env.local.php        │   │        AVEC .env.local.php       │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ Qui lit ?  Dotenv (bootEnv)      │   │ Qui lit ?  bootEnv, le dump PHP  │
│ Quand ?    à l'amorçage          │   │ Quand ?    à l'amorçage          │
│ Fichiers   .env* analysés        │   │ Fichiers   .env* PAS analysés    │
│ Condition  aucune                │   │ Condition  APP_ENV identique     │
│ Création   (rien)                │   │ Création   composer dump-env prod│
└──────────────────────────────────┘   └──────────────────────────────────┘

Dans les deux cas, une vraie variable d'environment reste prioritaire.

Les processeurs d'environment

À retenir en priorité
  1. La chaîne transforme progressivement la valeur.
  2. Inverser les processors peut changer ou casser le résultat.

Où en est-on ? Étape 3 sur 4 : on a choisi la valeur, mais c'est une string. Les processeurs la convertissent.

🌍 In Real Life

La situation : les réglages publics du blog arrivent sous un emballage encodé. Il faut retirer l'emballage avant de lire la fiche structurée.

L’équivalent dans Symfony : emballage → base64 ; texte structuré → JSON ; opérations imbriquées → json:base64:CONFIG.

Retour à la réalité technique : la chaîne part de la variable à droite, applique base64 puis JSON. Les processeurs convertissent les données ; ils ne changent pas la priorité de leur source. Base64 ne chiffre ni ne protège un secret.

🧠 Comment le mémoriser : « Déballer avant de lire. » Image mentale : enveloppe ouverte puis formulaire interprété. Question-réflexe : quel type reçoit chaque processeur ?

⚠️ À ne pas confondre : encodage, conversion de type et chiffrement.

Pour transporter des options publiques d'affichage, supposons que CONFIG contient le résultat de base64_encode('{"pageSize":20}'). L'ordre json:base64:CONFIG rend alors ['pageSize' => 20] ; base64 n'est pas du chiffrement et ne protège pas un secret. Le tableau concerne cette entrée base64 pour les deux dernières lignes :

Une variable d'environment est une string ; un processeur la convertit, et ils se chaînent de droite à gauche :

Référence Valeur
%env(bool:APP_DEBUG)%, avec 0 false
%env(json:base64:CONFIG)% base64 décodé, puis JSON lu : l'array
%env(base64:json:CONFIG)% RuntimeException : Invalid JSON in env var "CONFIG"

Pourquoi de droite à gauche ? Comme des fonctions imbriquées : json(base64(CONFIG)). On part de la variable (à droite), on applique le processeur le plus proche, puis le suivant vers la gauche.

%env(json:base64:CONFIG)%          %env(base64:json:CONFIG)%
         CONFIG                             CONFIG
           ▼ base64 (décode)                  ▼ json (lit du JSON)
        '{"pageSize":20}'              texte base64 ≠ JSON → ÉCHEC
           ▼ json                      RuntimeException
   ['pageSize' => 20]                  Invalid JSON in env var "CONFIG"

ExpressionLanguage

À retenir en priorité
  1. ExpressionLanguage possède sa syntaxe.
  2. Ne pas transposer les opérateurs PHP sans vérifier.

Où en est-on ? Étape 4 sur 4 : dernière brique. On quitte les valeurs fournies par la machine : ici, on écrit une petite règle d'une ligne (condition de route, règle d'authorization).

🌍 In Real Life

La situation : une règle de publication du blog utilise les cases autorisées d'une petite fiche de calcul, pas tous les dossiers du bureau.

L’équivalent dans Symfony : cases disponibles → variables exposées ; opérations admises → fonctions de l'intégration ; formule → expression.

Retour à la réalité technique : ExpressionLanguage évalue une grammaire dédiée, pas un script PHP complet. Les capacités dépendent des variables, objets et fonctions exposés ; cela ne justifie pas d'accepter des expressions non fiables sans contrôle.

🧠 Comment le mémoriser : « La formule ne voit que son contexte exposé. » Image mentale : calculatrice avec cases nommées. Question-réflexe : quelles capacités cette intégration rend-elle accessibles ?

⚠️ À ne pas confondre : expression compilée en code et résultat de son évaluation.

Une expression décrit une petite règle à partir de valeurs explicitement exposées ; ce n'est pas un script PHP complet. Les intégrations de routage ou de sécurité définissent leurs propres variables et fonctions. Une règle complexe de publication mérite plutôt un service testable.

Avec ExpressionLanguage 8.0 et son autoload déjà disponibles :

use Symfony\Component\ExpressionLanguage\ExpressionLanguage;

$el = new ExpressionLanguage();
$el->evaluate('1 + 2');   // 3 — évalué, sans compilation
$el->compile('1 + 2');    // '(1 + 2)' — compilé en PHP, donc cachable

Le premier appel calcule 3 ; le second produit une chaîne de code, sans l'exécuter. L'exemple de calcul conserve cette distinction :

echo $el->evaluate('quantity * unitPrice', [
    'quantity' => 3,
    'unitPrice' => 20,
]), PHP_EOL; // 60
echo $el->compile('1 + 2'), PHP_EOL; // (1 + 2)
echo $el->evaluate('"Article " ~ id', ['id' => 42]); // Article 42

evaluate() analyse l'expression puis évalue ses nœuds avec les valeurs ; compile() analyse puis produit du PHP. La mise en cache de l'analyse n'est pas la mise en cache du résultat métier. Ne pas accepter des expressions arbitraires de lecteurs du blog : les objets exposés peuvent donner accès à leurs méthodes.

Méthode Ce que je donne Ce que je reçois
evaluate($expr, $valeurs) l'expression et les valeurs le résultat (3, 60…)
compile($expr) l'expression une string de code PHP ((1 + 2))
parse($expr, $noms) l'expression et les noms un ParsedExpression
lint($expr, $noms) l'expression et les noms rien (void) ou SyntaxError
  • parse() rend un ParsedExpression ; lint() ne rend rien et lève une SyntaxError — variable ou function inconnue, sauf flags Parser::IGNORE_*.
  • ~ concatène : "Hi " ~ name donne Hi Ana avec name = 'Ana' ; "Hi " + name lève une TypeError dans ce cas non numérique. in, properties, methods et ternaire sont acceptés.
  • Dans le framework : une condition de route, une règle d'authorization.

Pour vérifier une variable connue, passer son nom dans le tableau de lint(). Ignorer les variables inconnues diffère de leur fournir une valeur : lint($expr, [], Parser::IGNORE_UNKNOWN_VARIABLES) ne garantit pas qu'une évaluation future réussira. Importer Parser depuis le même namespace ; en Symfony 8.0, l'argument des noms est un tableau, pas null.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le dump est lié à un environment.
  2. Ne pas appliquer un dump incompatible.
  • Priorité, conversion, résolution et processus

    Pour expliquer une mauvaise taille de page, annoncer d'abord le mécanisme : priorité de source, conversion, résolution différée ou ancien processus. Les règles suivantes ne sont pas quatre variantes de « vider le cache ».

  • Voir l’explication : Un parameter est résolu à la compilation, une variable d'environment à l'exécution.

    Un parameter est résolu à la compilation, une variable d'environment à l'exécution. Pourquoi on se trompe : %env()% s'écrit dans parameters, donc on le croit résolu comme un parameter.

  • Voir l’explication : La vraie variable d'environment gagne

    La vraie variable d'environment gagne contre les files .env, sauf avec overrideExistingVars: true. Plausible car : un fichier « plus spécifique » (.env.local) semble devoir tout écraser ; mais il ne fait qu'ajouter ce qui manque.

  • Voir l’explication : .env.local ne s'applique pas en test.

    .env.local ne s'applique pas en test. Plausible car : « local » évoque « toujours chargé sur ce poste ».

  • Voir l’explication : .env.<env> l'emporte sur .env.local

    .env.<env> l'emporte sur .env.local : le dernier file chargé gagne. Plausible car : « local » évoque la priorité maximale ; mais l'ordre est .env, .env.local, .env.<env>, .env.<env>.local.

  • Voir l’explication : Avec un dump compatible avec APP_ENV

    Avec un dump compatible avec APP_ENV, les fichiers texte ne sont plus lus. Plausible car : modifier .env.local « devrait » toujours agir ; il faut relancer composer dump-env prod.

  • Voir l’explication : Amorçage par requête ≠ worker long

    Amorçage par requête ≠ worker long : une modification n'actualise pas magiquement un processus déjà démarré.

  • Voir l’explication : Les processeurs se chaînent de droite à gauche.

    Les processeurs se chaînent de droite à gauche. Plausible car : on lit naturellement de gauche à droite.

  • Échapper le signe pour cent

    %% pour un % littéral.

  • Voir l’explication : APP_DEBUG dérivé reste une string

    APP_DEBUG dérivé reste une string ('0'/'1'), pas un booléen PHP.

Fiche express

À mémoriser

À retenir en priorité
  1. Évaluer exécute l'expression.
  2. Compiler produit une représentation exécutable.

Le réglage peut maintenant varier sans modifier la logique de l'article. La prochaine étape consiste à transporter code, configuration et processus de façon cohérente : déploiement.

🧠 À retenir pour la certification :

  • Parameter : compilation ; %env()% : exécution (puis mémorisée).
  • .env → .env.local → .env.<env> → .env.<env>.local ; le dernier gagne.
  • .env.local ignoré en test.
  • Vraie variable > .env, sauf overrideExistingVars: true.
  • .env.local.php remplace les .env (même APP_ENV).
  • Lecture à l'amorçage sans dump ; redémarrer les processus longs.
  • Processeurs de droite à gauche ; %% = %.
  • ExpressionLanguage : evaluate() / compile() / lint(), ~ concatène.

Si tu dois retenir seulement 8 choses : celles ci-dessus.
