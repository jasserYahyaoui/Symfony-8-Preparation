Objectif

Le bus sait appeler un handler, mais cela ne suffit pas à différer un travail. Après avoir affiché GET /blog/42, l'équipe souhaite importer d'autres articles sans immobiliser l'appelant. Ce cours explique la décision manquante : choisir le trajet de ImportBlogFile, puis distinguer son envoi de son traitement. Le même choix s'applique à un dispatch depuis app:blog:import, sans inventer de Request HTTP dans cette command.

Question centrale : où part un message quand je fais dispatch(), et comment Symfony le décide-t-il ?

L'essentiel

À comprendre

À retenir en priorité
  1. L'absence de routage n'est pas une file implicite.
  2. Le bus appelle les handlers.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un handler n'est pas différé par magie. Il faut une destination (un transport), une règle qui y envoie le message (le routage), et un exécutant (un worker, vu au cours suivant).
  • Le piège de fond. Le nom async est une étiquette, pas une promesse. Un transport déclaré mais jamais sélectionné ne change rien ; un transport sync:// est un vrai transport qui traite sur place.
  • Ce que l'auteur veut que vous compreniez. L'ordre de sélection des destinations (stamp, configuration, attribute, sinon rien) et le moment où une erreur apparaît (build ou dispatch).
  • Pourquoi c'est à l'examen. Les questions portent sur la priorité des sources de routage, le joker *, in-memory:// et la sérialisation.

Un transport assure l'envoi ou la réception des Envelope ; un DSN est la chaîne qui permet de choisir sa fabrique et ses paramètres. Le nom async est seulement un alias de service : il ne prouve pas que le transport travaille en différé. Le routage Messenger associe un type de message à un ou plusieurs de ces aliases. Contrairement au routage de blog_show, il ne sélectionne pas une action depuis une URL.

Avec la pile standard, sans destination applicable, le bus poursuit vers les handlers immédiatement. Avec une destination, SendMessageMiddleware passe au sender : celui-ci peut conserver le message, l'envoyer vers une file configurée ou, avec sync://, le redispatcher sur place. Déclarer, router et consommer sont donc trois opérations distinctes.

Le schéma

À retenir en priorité
  1. La configuration adapte le routage à l'environment.
  2. Le stamp fournit un choix ponctuel.

Où en est-on ? Étape 1/4 : la vue d'ensemble. Le cours suit l'ordre déclarer (les transports), router (les règles), non routé (le cas par défaut), puis ce qui est vérifié au démarrage.

Transports
   ├─ 1. Déclarer       → transports: { nom: DSN }   (sync://, in-memory://…)
   ├─ 2. Router         → routing: { Message: nom }  ou #[AsMessage]
   ├─ 3. Non routé      → pas de sender : handlers tout de suite
   └─ 4. Vérifications  → quand une erreur de config apparaît-elle ?

Partons d'un nouveau dispatch, avant toute réception par un worker. Le SendersLocator cherche les destinations dans cet ordre. Une Envelope reçue avec ReceivedStamp suit un autre chemin : le middleware d'envoi ne la renvoie pas automatiquement aux mêmes destinations.

Bleu : demande ; ambre : sélection ; vert : issue. Le dernier chemin suppose la pile par défaut et un handler enregistré. Il ne signifie pas qu'un message sans handler réussit : HandleMessageMiddleware peut lever NoHandlerForMessageException. La sélection d'un sender ne prouve pas non plus que sa connexion ou son envoi réussira.

Deux conséquences pour l'import : une destination obtenue par la configuration évite la lecture des attributes ; un joker n'est pas un abonnement à tous les messages déjà routés. La première règle de type n'arrête toutefois pas la recherche sur les classes parentes et interfaces.

Pourquoi la configuration gagne-t-elle sur l'attribute ? Le code de SendersLocator::getSenders() le dit en commentaire : la map pilotée par la configuration surcharge les attributes, pour qu'une configuration propre à un environnement puisse remplacer un nom de transport écrit en dur dans la class.

L'exemple

Exemple concret

À retenir en priorité
  1. Un message peut avoir plusieurs destinations.
  2. Ce choix ne signifie pas un seul traitement métier.

Où en est-on ? Étape 2/4 : un fichier de configuration complet avant de détailler chaque ligne.

Conservons les messages de notification déjà utilisés : SendWelcomeEmail accueille un abonné, SmsNotification l'avertit d'une publication et ResizeAvatar prépare son image. ChargeCard reste une variante d'abonnement payant, pas une opération nécessaire à la lecture de l'article.

Dans ce fragment de config/packages/messenger.yaml, les classes nommées existent, leurs handlers sont enregistrés et les deux variables de DSN sont fournies par l'environnement. Aucun DSN externe précis n'est prescrit ici :

framework:
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
            audit: '%env(AUDIT_TRANSPORT_DSN)%'
            sync:  'sync://'
        routing:
            'App\Message\SendWelcomeEmail': async
            'App\Message\ChargeCard': sync
namespace App\Message;

use Symfony\Component\Messenger\Attribute\AsMessage;

#[AsMessage(['async', 'audit'])]
final class SmsNotification {}
final class ResizeAvatar {}   // routé nulle part

SendWelcomeEmail sélectionne async ; son mode d'exécution dépend du DSN réel. ChargeCard est traité sur place par le transport sync. SmsNotification sélectionne deux transports, donc potentiellement deux traitements à réception. ResizeAvatar, sans autre règle ni attribute applicable, atteint ses handlers avant le retour de dispatch(), aussi bien dans une command que dans une Request.

Pour l'import des articles, il faut de même une classe ImportBlogFile existante, une destination explicitement configurée et une règle qui les relie. Changer seulement le nom du transport ne crée pas une file asynchrone.

Message Source de la destination Résultat
SendWelcomeEmail routing → async envoyé au DSN d'async
ChargeCard routing → sync sync:// : traité sur place
SmsNotification #[AsMessage] envoyé à async et audit
ResizeAvatar aucune handlers avant le retour de dispatch()

Déclarer

À retenir en priorité
  1. sync est un vrai transport synchrone.
  2. in-memory sert à observer l'envoi en test.

Où en est-on ? Étape 3/4 (partie 1) : déclarer. On commence par les deux transports intégrés, qui permettent de comprendre le sort de l'Envelope sans installer de broker.

Avant de brancher une file, les deux transports intégrés permettent de comprendre ce qui arrive à l'Envelope sans ajouter d'intégration externe :

  • sync:// redispatche immédiatement dans le même process. Le middleware d'envoi ajoute SentStamp, puis le transport ajoute ReceivedStamp pour éviter un nouvel envoi lors de ce redispatch. Des handlers correspondants peuvent donc produire des HandledStamp avant le retour initial.
  • in-memory:// conserve les Envelope dans l'instance du transport pour les tests. Son send() n'appelle pas les handlers ; getSent() permet d'inspecter l'envoi. Il ne lance pas un worker et n'est pas une file durable partagée avec un autre process.
sync:// in-memory://
Handlers appelés à l'envoi oui, via redispatch non
Stamps ajoutés SentStamp, ReceivedStamp, HandledStamp SentStamp, TransportMessageIdStamp
Usage exécution immédiate tests (getSent())
Durable / partagé entre process non applicable non

La sérialisation transforme le message en données transportables ; la désérialisation permet de le reconstituer. Le transport mémoire ne fait pas cette conversion par défaut. Avec in-memory://?serialize=true, sa fabrique lui fournit le serializer configuré. Avec celui de PHP, une closure dans le message provoque « Serialization of 'Closure' is not allowed ».

Pour ImportBlogFile, préférer les données nécessaires au travail — par exemple une référence de fichier accessible à l'exécutant — plutôt qu'un service ou un object vivant. Un identifier permet au handler de rechercher l'état actuel ; un snapshot est un autre contrat à décider explicitement. Ne jamais désérialiser de contenu externe non fiable.

Les intégrations externes restent hors de ce cours. Pour un transport différé réellement installé et configuré, séparer les travaux par latence peut éviter qu'un long import retarde les notifications. Un worker par transport est une possibilité d'exploitation, pas une obligation du protocole Messenger.

🌍 In Real Life

La situation : le secrétariat du blog dispose d'un guichet immédiat et d'une corbeille de démonstration.

L’équivalent dans Symfony : guichet retransmettant aussitôt → sync:// ; corbeille inspectable → in-memory:// et getSent().

Retour à la réalité technique : le premier redispatche dans le même processus ; le second conserve les Envelope dans son instance sans appeler les handlers à l'envoi. La corbeille de test n'est pas un stockage durable partagé avec un worker distant.

Router

À retenir en priorité
  1. Le joker sert de repli.
  2. Les routes précises ne reçoivent pas systématiquement sa destination.

Où en est-on ? Étape 3/4 (partie 2) : router. Les transports existent ; quels messages les utilisent ? On lit les règles du plus fort au plus faible.

Les transports existent ; il reste à décider quels messages les utilisent. Le fragment suivant appartient à framework.messenger.routing. Il montre trois granularités, et non trois étapes d'un traitement métier :

routing:
    'App\Message\SmsNotification': [async, audit]
    'App\Message\AsyncMessageInterface': async
    'App\Message\*': async
  • Une key peut être une class, une class parente, une interface, un namespace terminé par *, ou * seul ; un message peut viser plusieurs transports.
  • Si la configuration trouve au moins un sender, elle gagne sur les attributes. Elle permet donc de modifier la destination par environment sans modifier la classe du message.
  • Parent et enfant s'additionnent ; un joker ne sert que si rien de plus précis n'a trouvé de transport — « the '*' acts as a fallback ». Les aliases déjà rencontrés dans la map de configuration sont dédupliqués par le locator.
routing Message Transports
SmsNotification: async, Notification: audit (parente) SmsNotification async et audit
Welcome: async, '*': audit Welcome async seulement
'*': audit SmsNotification, avec #[AsMessage(['async', 'audit'])] audit seulement

Ces lignes sont des cas indépendants. La parente Notification est supposée exister dans le premier ; aucune autre route n'intervient dans les suivants. Envoyer vers deux destinations ne garantit ni un traitement unique ni une transaction commune aux deux envois.

Pourquoi « parent et enfant s'additionnent » mais pas le joker ? Le locator parcourt les types dans l'ordre classe, parents, interfaces, jokers de namespace, *. Chaque règle trouvée ajoute ses alias. Seule exception : une clé qui se termine par * est sautée dès qu'un alias a déjà été trouvé. D'où « repli », et non « abonné à tout ».

Au dispatch initial, le dernier TransportNamesStamp remplace la sélection des destinations : dispatch(new Welcome(), [new TransportNamesStamp(['sync'])]) ignore la key async. Ce fragment suppose Welcome disponible et Symfony\Component\Messenger\Stamp\TransportNamesStamp importé. Le stamp ne change pas la configuration globale et ne transforme pas les autres dispatchs.

Pour observer un envoi sans exécuter le travail, le rapport d'import peut utiliser cette configuration de test. La classe App\Message\GenerateReport doit déjà exister ; le test vérifie l'envoi, pas la production du rapport :

framework:
    messenger:
        transports:
            test_queue: 'in-memory://?serialize=true'
        routing:
            'App\Message\GenerateReport': test_queue

Le résultat attendu est une Envelope inspectable dans le transport mémoire, sans appel automatique du handler. Ce test exerce la sérialisation configurée, mais ne prouve ni disponibilité d'un transport distant ni livraison unique.

Routage HTTP (blog_show) Routage Messenger
Entrée URL + méthode type du message (class, parent, interface, namespace)
Sortie une action de contrôleur un ou plusieurs senders
Plusieurs cibles non oui

🌍 In Real Life

La situation : les dossiers de publication du blog portent une consigne d'expédition ; un plan de distribution détermine leurs destinataires.

L’équivalent dans Symfony : catégories de dossiers → classes, interfaces et motifs de messages ; destinations → senders configurés ; consigne portée par l'Envelope → TransportNamesStamp.

Retour à la réalité technique : le routage Messenger sélectionne des senders selon ses règles et priorités de sélection. Il ne choisit pas le contrôleur de /blog/42, et nommer une destination ne lance pas son consommateur.

Non routé : traité tout de suite

À retenir en priorité
  1. Déclarer un transport ne route pas les messages.
  2. Le routage décide pour chaque type.

Où en est-on ? Étape 3/4 (partie 3) : que se passe-t-il quand aucune règle ne s'applique ? Réponse : rien n'est différé.

Sans sender applicable, la pile standard continue vers le traitement synchrone. Un handler correspondant peut alors travailler immédiatement. S'il n'y en a aucun, HandleMessageMiddleware lève normalement NoHandlerForMessageException ; des options ou une pile personnalisée peuvent changer ce comportement. Ne pas généraliser cette règle à un bus vide.

Par exemple, ajouter seulement un transport nommé async ne change pas ResizeAvatar : sans règle applicable ni attribute, son handler reste appelé avant le retour de dispatch(). Ajouter une règle vers un vrai transport différé déplace ce travail à la consommation ; vers sync://, il reste immédiat. Pour ImportBlogFile, vérifier donc ensemble le message, sa route, le DSN sélectionné et l'existence d'un consommateur.

Pourquoi n'y a-t-il pas d'envoi implicite ? Parce que SendMessageMiddleware ne passe la main au middleware suivant que si $sender === null. Sans sender trouvé, il appelle $stack->next() : le chemin continue vers HandleMessageMiddleware.

🌍 In Real Life

La situation : sans consigne d'expédition, le secrétariat du blog poursuit le travail au bureau présent au lieu d'inventer une livraison.

L’équivalent dans Symfony : aucune destination trouvée → aucun sender applicable ; bureau suivant → HandleMessageMiddleware ; travail local → handler correspondant.

Retour à la réalité technique : c'est le comportement de la pile standard, avec un handler disponible. Une pile vide ou personnalisée ne promet pas ce traitement. Un transport nommé async mais jamais sélectionné ne change rien.

🧠 Comment le mémoriser : « Pas d'envoi implicite. » Image mentale : une fiche restant sur le bureau. Question-réflexe : une règle sélectionne-t-elle réellement un sender ?

⚠️ À ne pas confondre : absence de routage et absence de handler, qui peut provoquer une exception.

Ce qui est vérifié au démarrage

À retenir en priorité
  1. La configuration est contrôlée à la compilation.
  2. Une erreur d'attribute peut être différée.

Où en est-on ? Étape 4/4 : quand une erreur de configuration apparaît-elle ? Au build du container, ou seulement au dispatch ?

FrameworkBundle contrôle la configuration de routing lors de la préparation du service container. Ce contrôle ne recommence pas intégralement à chaque GET /blog/42 : le container compilé peut être réutilisé. Il distingue les références invalides des règles qui, simplement, ne correspondent à rien :

Key de routing Résultat
class mal orthographiée LogicException au build : « class or interface … not found »
transport inexistant (asyncc) LogicException : « This is not a valid transport or service id »
App\Other\* (namespace sans message) aucune erreur de référence ; les messages non correspondants suivent leurs autres règles, ou le chemin sans sender

La destination portée par l'attribute est résolue au dispatch, lorsque ce chemin est effectivement atteint. Sans sender async disponible, le container peut se construire, puis SendersLocator lève une RuntimeException en recherchant cet alias. Une route de configuration ou un stamp qui supplante l'attribute peut éviter ce chemin. Enfin, un build réussi ne prouve pas que la connexion et l'envoi ultérieurs réussiront.

 Source de la destination      Quand l'erreur apparaît      Exception
 ───────────────────────────   ──────────────────────────   ───────────────
 routing (class / transport)   build du container           LogicException
 #[AsMessage('async')]         premier dispatch concerné    RuntimeException
 connexion au broker           envoi / consommation         selon le transport

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le mode synchrone peut passer par un transport.
  2. Les stamps révèlent ce trajet.
  • Voir l’explication : Sans sender, la pile standard poursuit vers les handlers

    Sans sender, la pile standard poursuit vers les handlers : pas de file implicite pour l'import. Un handler absent ou une pile différente change le résultat. Pourquoi on se trompe : on pense qu'un transport async déclaré devient la destination par défaut.

  • Voir l’explication : Une class mal orthographiée dans routing fait échouer le build

    Une class mal orthographiée dans routing fait échouer le build ; seul un namespace sans correspondance échappe à ce contrôle de classe. Cela ne supprime pas les autres routes éventuellement applicables. Pourquoi on se trompe : un joker App\Other\* ressemble à une classe inconnue, mais c'est un motif de namespace, pas une référence de class.

  • Voir l’explication : Une sélection issue de la configuration l'emporte sur #[AsMessage]

    Une sélection issue de la configuration l'emporte sur #[AsMessage] ; le dernier TransportNamesStamp peut encore imposer un choix ponctuel. Pourquoi on se trompe : l'attribute, écrit sur la class, paraît « plus proche » du message donc plus fort.

  • Voir l’explication : sync:// n'est pas « pas de transport »

    sync:// n'est pas « pas de transport » : traitement sur place, mais SentStamp ajouté par le middleware et ReceivedStamp par le transport. Pourquoi on se trompe : le résultat (handlers avant le retour) est identique à l'absence de routage ; seuls les stamps diffèrent.

  • Voir l’explication : in-memory:// sert aux tests

    in-memory:// sert aux tests : l'envoi seul ne traite pas le message. Un envoi observé n'est ni un rapport généré ni une preuve de durabilité. Pourquoi on se trompe : « mémoire » évoque un traitement local immédiat.

Fiche express

À mémoriser

À retenir en priorité
  1. Un test mémoire peut masquer une erreur de sérialisation.
  2. L'option permet de tester cette frontière.

Pour l'import, lire la configuration avant de promettre une réponse rapide : le nom du transport, sa sélection et son mode d'exécution sont trois indices différents.

Si tu dois retenir seulement 7 choses :

  • Le DSN configure un transport ; sync:// traite, in-memory:// garde.
  • routing ou #[AsMessage] ; la configuration gagne.
  • Parent et enfant s'additionnent ; un joker n'est qu'un repli.
  • Non routé : traitement immédiat, si un handler est disponible.
  • Référence configurée invalide → build ; alias d'attribute consulté mais absent → dispatch.
  • TransportNamesStamp passe avant tout.
  • in-memory:// ne sérialise qu'avec ?serialize=true.

Moyen mnémotechnique : « le stamp, puis la configuration, puis l'attribute, sinon tout de suite ».

TransportNamesStamp > routing (class + parents + interfaces ; * en repli)
  > #[AsMessage] > rien = synchrone ;
routing vérifié au build, attribute au dispatch ;
sync:// traite avec SentStamp ; in-memory:// sans serialize par défaut

Le trajet est choisi. Pour comprendre qui récupère un travail différé et quand il l'acquitte, continuer avec les workers. Les retries et failures traitent ensuite le cas où l'envoi ou le handler ne produit pas le résultat attendu.

🧠 À retenir pour la certification

  • Transport = envoi/réception d'Envelope ; DSN = chaîne qui choisit fabrique et paramètres ; async n'est qu'un alias.
  • Ordre de sélection : TransportNamesStamp → routing (class, parents, interfaces, * en repli) → #[AsMessage] → rien.
  • La configuration gagne sur l'attribute dès qu'un sender est trouvé ; parent et enfant s'additionnent.
  • Sans sender, la pile standard va aux handlers ; sans handler : NoHandlerForMessageException.
  • sync:// : SentStamp + ReceivedStamp + HandledStamp, traité sur place ; in-memory:// : garde sans traiter, sans sérialiser par défaut.
  • Erreur de routing (class ou transport inconnu) → LogicException au build ; alias d'attribute absent → RuntimeException au dispatch.

Phrase de mémorisation : « Le stamp décide d'abord, la configuration ensuite, l'attribute en dernier ; sans destination le handler travaille tout de suite — et le nom async ne prouve rien. »
