Objectif

Nous savons distinguer identité et permission. Il reste à raccorder ces mécanismes : /blog/42 public, un espace d'administration protégé, puis éventuellement /api/blog/42 avec une autre méthode d'authentification. Un YAML valide peut pourtant sélectionner le mauvais dispositif.

Ce cours répond à une seule question : quand une Request arrive, quelle ligne de security.yaml décide de quoi, et dans quel ordre ?

L'essentiel

À comprendre

À retenir en priorité
  1. Deux décisions suivent l'ordre de déclaration.
  2. Leurs listes ne doivent pas être confondues.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Les cours précédents ont présenté les pièces une par une (users, providers, hashers, authenticators, voters). Il faut maintenant savoir qui les assemble : security.yaml.
  • Le piège de fond. Deux sections, firewalls et access_control, appliquent la première entrée qui correspond. Une erreur d'ordre est silencieuse : le YAML est valide, mais il protège (ou ouvre) la mauvaise URL.
  • Ce que l'auteur veut que vous compreniez. Il y a deux sélections successives et indépendantes : « quel ensemble de mécanismes ? » (firewall) puis « quelle exigence pour cette requête ? » (access_control).
  • Pourquoi c'est à l'examen. Les questions portent sur l'ordre, sur security: false, sur l'ambiguïté de plusieurs providers et sur expose_security_errors.

security.yaml réunit cinq sections qui répondent chacune à une question. Deux d'entre elles, firewalls et access_control, appliquent la première entrée qui correspond — et une erreur d'ordre passe sans un message.

Pourquoi ne recompile-t-on pas security.yaml à chaque article ? Parce que la configuration décrit les services et les règles à préparer. SecurityExtension construit leurs définitions ; les compiler passes complètent le container. Au traitement HTTP, les matchers déjà préparés choisissent le firewall puis la règle : on ne recompile pas security.yaml pour chaque article.

Le schéma

À retenir en priorité
  1. Un matcher général masque les suivants.
  2. Placer les cas précis en premier.

Où en est-on ? Nous avons posé le problème (deux sélections). Avant de lire le YAML, regardons le chemin d'une Request à travers ces deux choix : c'est la carte du cours. Chaque partie suivante zoome sur une case.

Le premier choix répond « quel ensemble de mécanismes ? », le second « quelle exigence pour cette requête ? ». Le hasher n'est pas une étape obligatoire de toute API : il intervient quand la preuve est un mot de passe.

Bleu : traitement ; ambre : sélection ; vert : issue. Le hasher n'intervient que si le mécanisme utilise un password. Sans règle d'accès correspondante, cette liste n'impose rien ; un controller peut toujours faire son propre contrôle. Sélectionner le firewall ne sélectionne donc pas le droit d'accès.

Lecture du schéma, étape par étape pour GET /admin :

  1. La Request arrive ; Symfony parcourt les firewalls dans l'ordre et garde le premier dont le matcher correspond.
  2. Si ce firewall est en security: false, on s'arrête : plus rien n'est exécuté côté sécurité.
  3. Sinon, ses authenticators (avec leur provider, et le hasher si la preuve est un password) identifient — ou non — le visiteur.
  4. Puis AccessListener cherche la première règle access_control correspondante et soumet ses exigences aux voters.

L'exemple

Exemple concret

À retenir en priorité
  1. Les règles ne se cumulent pas.
  2. La règle générale peut rendre la restriction inaccessible.

Où en est-on ? Place au code minimal : un seul fichier security.yaml qui contient les cinq sections du tableau de la partie suivante. On regarde ce que chaque ligne déclare, sans encore parler des pièges.

Le fragment suppose des classes applicatives enregistrées et des routes de connexion existantes. App\Entity\User est ici un nom de classe, pas une configuration de stockage ; le provider doit fournir ce type compatible avec le hasher.

security:
    password_hashers:                 # comment les passwords sont hachés
        App\Entity\User: { algorithm: auto }
    providers:                        # d'où viennent les users
        app_users:
            id: App\Security\AppUserProvider
    firewalls:                        # comment on s'authentifie
        dev:  { pattern: ^/(_profiler|_wdt)/, security: false }
        main: { lazy: true, provider: app_users, form_login: ~ }
    access_control:                   # ce qu'il faut pour entrer
        - { path: ^/admin, roles: ROLE_ADMIN }

AppUserProvider est un service applicatif implémentant UserProviderInterface, à fournir avec les routes de login. L'exemple reste ainsi dans le Security Core, sans dépendance à un stockage externe. Une route /admin est réservée à ROLE_ADMIN même si la connexion réussit avec seulement ROLE_USER.

Ce que Symfony voit dans ce fichier :

Ligne Ce que Symfony en fait
dev (security: false) un firewall sans listener, pour le profiler
main un firewall général : provider app_users, form_login
access_control une règle lue par AccessListener : /admin demande ROLE_ADMIN

Sans autre règle ni contrôle serveur, /blog/42 reste public ; /admin déclenche le login pour un visiteur et un refus pour Alice pleinement authentifiée sans ROLE_ADMIN. Le firewall nommé dev n'est pas désactivé automatiquement parce que le serveur passe en production : ne pas y exposer les routes du profiler.

Ce qui décide de quoi

À retenir en priorité
  1. Le provider charge l'identité.
  2. La hiérarchie définit des implications de roles.
  3. Le limiter combine username+IP et IP seule.
  4. L'intervalle d'exemple ne doit pas être confondu avec le défaut d'une minute.

Où en est-on ? Étape 1 sur 5 de la lecture du fichier : avant d'étudier l'ordre, il faut savoir à quelle section poser quelle question. Une panne se diagnostique dans la bonne section, pas dans la plus familière.

Pour un utilisateur introuvable, examiner le provider ; pour un rôle hérité absent, examiner la hiérarchie. Modifier le hasher pour corriger une URL publique ne traite pas la bonne question :

Section Question
password_hashers comment un password est stocké et vérifié
providers d'où le user est chargé
firewalls comment on prouve son identité
access_control ce qu'il faut pour atteindre une URL
role_hierarchy quels roles en impliquent d'autres

Avant / après, un diagnostic :

Symptôme                               Où regarder
─────────────────────────────────────  ─────────────────────────
« user introuvable »                   providers
« ROLE_ADMIN absent alors qu'hérité »  role_hierarchy
« /blog public alors que protégé »     access_control (ordre !)
« mauvais mécanisme de login »         firewalls (ordre, matcher)
« le hash ne correspond pas »          password_hashers

Une protection complémentaire, login_throttling, se configure sur le firewall et nécessite RateLimiter. Le mécanisme par défaut combine identifier+IP et IP seule ; la seconde limite vaut cinq fois max_attempts. Les valeurs par défaut sont cinq tentatives et une minute : une configuration de quinze minutes est une surcharge. Ce mécanisme limite les tentatives ; il ne remplace ni le hasher, ni la politique d'accès, ni les protections réseau.

login_throttling se configure sur le firewall et utilise RateLimiter. Le limiter par défaut combine une limite par identifier de user et IP avec une limite plus large par IP seule, égale à cinq fois max_attempts. Changer d'identifier à chaque tentative ne remet donc pas à zéro le compteur IP commun. Les valeurs par défaut sont cinq tentatives et un intervalle d'une minute ; un exemple à quinze minutes est une surcharge, pas le défaut.

Les deux règles d'ordre

À retenir en priorité
  1. Le firewall choisit l'authentication.
  2. La première règle d'accès impose ses exigences.

Où en est-on ? Étape 2 sur 5 : c'est le cœur du cours. On a vu qu'une Request subit deux sélections ; on étudie maintenant comment chacune choisit son entrée. La réponse tient en une phrase : la première qui correspond gagne, et rien ne vous prévient si ce n'est pas celle que vous pensiez.

🌍 In Real Life

La situation : l'accueil du restaurant choisit d'abord l'équipe chargée de la demande, puis cette équipe consulte sa liste d'exigences d'accès.

L’équivalent dans Symfony : première sélection → premier firewall correspondant ; deuxième sélection → première règle access_control correspondante pour la requête.

Retour à la réalité technique : les listes ne se fusionnent pas et ne cherchent pas automatiquement la règle la plus spécifique. Pour la branche d'administration du blog, un catch-all placé trop tôt peut masquer une entrée ultérieure, sans erreur de syntaxe.

🧠 Comment le mémoriser : « Deux listes, deux premiers matchs. » Image mentale : deux listes, chacune avec une seule ligne entourée. Question-réflexe : quelle première ligne est effectivement retenue dans chaque liste ?

⚠️ À ne pas confondre : choix des mécanismes de sécurité et exigence d'autorisation.

  • Dans firewalls, le premier matcher applicable sélectionne le firewall ; sans matcher effectif, l'entrée accepte toute Request.
  • Dans access_control, la première règle correspondante s'applique.

Pourquoi un firewall sans pattern n'est-il pas forcément « sans matcher » ? En Symfony 8.0.16, request_matcher personnalisé est prioritaire. À défaut, le matcher généré n'est construit que si pattern ou host est configuré ; methods seul ne crée pas ce matcher. Sans pattern ne signifie donc pas sans matcher : un host ou un matcher personnalisé peut encore filtrer.

Matcher d'un firewall, dans l'ordre de décision :
  1. request_matcher personnalisé ?  → oui : c'est lui
  2. sinon pattern ou host présent ? → oui : matcher généré
  3. sinon (même avec methods seul)  → aucun matcher effectif
                                       → le firewall accepte toute Request

L'entrée la plus générale vient en dernier. Sinon, rien n'est signalé : main sans matcher effectif déclaré avant api (pattern: ^/api, stateless: true) prend /api/…. Un cookie de session dépend ensuite de l'utilisation effective de la session ; il n'est pas garanti par la sélection. ^/rules en PUBLIC_ACCESS avant ^/rules/a en ROLE_ADMIN ouvre /rules/a à un anonyme.

Avant / après, avec GET /api/fw :

MAUVAIS ORDRE                        BON ORDRE
firewalls:                           firewalls:
  main: (aucun matcher)  ← gagne       api:  ^/api, stateless ← gagne
  api:  ^/api, stateless               main: (catch-all)

→ /api/fw traitée par main           → /api/fw traitée par api
  (sans erreur, sans avertissement)

Même logique pour access_control :

- { path: ^/rules,   roles: PUBLIC_ACCESS }   ← /rules/a s'arrête ici
- { path: ^/rules/a, roles: ROLE_ADMIN }      ← jamais atteinte

Transposé à l'article, une règle publique trop générale pour ^/blog placée avant la restriction de l'écran d'édition masque cette restriction. Placer le cas réservé avant le cas public, puis vérifier les deux chemins. La règle la plus précise ne gagne pas automatiquement.

`security: false` éteint tout

À retenir en priorité
  1. security: false coupe le traitement de sécurité.
  2. Une règle d'accès ne le réactive pas.

Où en est-on ? Étape 3 sur 5 : on sait que le firewall est choisi en premier. Reste le cas particulier le plus piégeux : un firewall qui n'a pas de sécurité du tout. La question : que devient access_control pour ses URL ?

🌍 In Real Life

La situation : une entrée du restaurant n'a pas d'équipe de contrôle. Ajouter une consigne dans son classeur ne crée pas l'agent chargé de la lire.

L’équivalent dans Symfony : équipe absente → listeners du firewall désactivés ; consigne non appliquée par cette équipe → règle access_control sans AccessListener.

Retour à la réalité technique : security: false sur le firewall retenu supprime ses listeners. Ce n'est pas une règle d'accès public exécutée par une sécurité active ; cela ne supprime pas magiquement les autres contrôles applicatifs ou d'infrastructure.

🧠 Comment le mémoriser : « Pas d'agent, pas de lecture du classeur. » Image mentale : consigne devant un poste inoccupé. Question-réflexe : le mécanisme chargé d'appliquer ma règle est-il présent ?

⚠️ À ne pas confondre : security: false et PUBLIC_ACCESS pour la page publique du blog.

Un firewall security: false n'a aucun listener — ni authentication, ni AccessListener —, et SecurityExtension lui rend une liste vide. Une règle access_control sur ses URL est donc morte : avec un firewall free (^/free, security: false) et une règle ROLE_ADMIN sur ^/free, /free/page répond 200 à un anonyme. C'est l'usage du firewall dev.

Pourquoi la règle est-elle morte ? Parce que c'est AccessListener qui lit access_control, et que cet écouteur est enregistré dans le firewall. Pas de listener, personne ne lit la règle.

security: false PUBLIC_ACCESS
Listeners du firewall aucun présents
access_control lu ? non oui (la règle autorise)
Mécanismes de sécurité disponibles non oui
Usage typique profiler, assets page publique du blog

Ce résultat suppose une route qui répond normalement 200 sans contrôle supplémentaire : désactiver le firewall ne crée pas une route inexistante. PUBLIC_ACCESS laisse au contraire les mécanismes de sécurité disponibles tout en autorisant la requête concernée. Ne pas élargir security: false à /blog pour réparer un problème de login.

Plusieurs providers

À retenir en priorité
  1. Plusieurs providers rendent le choix ambigu.
  2. Le firewall doit désigner son provider.

Où en est-on ? Étape 4 sur 5 : jusqu'ici un seul provider, donc aucun choix. Que se passe-t-il quand on en déclare deux ? Symfony refuse de deviner.

Avec plusieurs providers, choisir explicitement celui utilisé, normalement par provider sur le firewall. Un authenticator qui accepte son propre réglage provider peut aussi préciser ce choix. Le cas http_basic sans choix effectif échoue par InvalidConfigurationException : « … is ambiguous as there is more than one registered provider ». Un firewall désactivé ne suit pas ce montage ; cette erreur ne signifie pas que tout firewall doit charger un utilisateur.

1 provider déclaré  → utilisé tout seul
2+ providers        → il faut nommer le choix (firewall ou authenticator)
                      sinon InvalidConfigurationException (« ambiguous »)
security: false     → pas de provider requis (aucun mécanisme)

Ce que l'échec révèle

À retenir en priorité
  1. Les erreurs sensibles sont masquées par défaut.
  2. La configuration contrôle leur exposition.

Où en est-on ? Étape 5 sur 5 : la configuration sait maintenant qui sélectionner et quoi exiger. Dernière question : quand la connexion échoue, que raconte l'erreur à un client ? Un message trop précis révèle quels comptes existent.

security.expose_security_errors — à la racine de security — règle ce que voit un client en échec ; hide_user_not_found n'existe plus en 8.0.

Valeur User inconnu Statut du compte (bloqué, expiré)
none (défaut) masqué masqué
account_status masqué non masqué, même si checkPreAuth() échoue avant vérification du password
all montré montré

Masqué veut dire remplacé par une BadCredentialsException : un user inconnu et un mauvais password donnent la même erreur. La default value, none, est lue dans MainConfiguration.

Le tableau concerne les exceptions de statut ordinaires. CustomUserMessageAccountStatusException, destinée explicitement au client, n'est pas masquée même sous none. AuthenticatorManager examine le type d'exception et le niveau d'exposition ; ce test ne prouve pas qu'un mot de passe a déjà été validé. Un contrôle placé dans checkPreAuth() peut échouer avant cette validation ; placer dans checkPostAuth() celui qui doit suivre une preuve effectivement vérifiée. Le masquage n'ordonne pas les contrôles et ne garantit pas cette précondition.

Le test est celui d'isSensitiveException() :

exception reçue                          niveau none   account_status   all
UserNotFoundException                    masquée       masquée          montrée
AccountStatusException ordinaire         masquée       montrée          montrée
CustomUserMessageAccountStatusException  montrée       montrée          montrée

Pourquoi est-ce raisonnable ? Si « utilisateur inconnu » et « mauvais mot de passe » donnaient deux messages, un attaquant pourrait énumérer les comptes existants.

L'exception est ensuite transmise au traitement d'échec. Ne pas confondre son message interne, sa clé traduisible et le corps finalement envoyé. Conserver un diagnostic privé sans exposer l'existence des comptes aux lecteurs.

Vérifier

À retenir en priorité
  1. debug:config montre les valeurs actives.
  2. dump-reference décrit les options disponibles.

Où en est-on ? Fin du parcours : on a tout lu, on veut prouver ce que la configuration fait réellement, sans se fier à ce qu'on croit avoir écrit.

php bin/console debug:config security    # la configuration résolue, défauts compris
php bin/console debug:firewall main      # les firewalls, et le détail de main

Résultats attendus, non exécutés ici : les valeurs effectives avec leurs défauts, puis le détail du firewall main. Sans nom, debug:firewall liste les firewalls ; config:dump-reference security décrit les options, pas la configuration effective. Utiliser le même environnement que la panne, puis tester /blog/42 et la zone protégée : la liste ne prouve pas leurs réponses.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une configuration syntaxiquement valide peut être mal ordonnée.
  2. Vérifier le firewall effectivement choisi.
  • Voir l’explication : firewalls et access_control ont chacun leur règle de première correspondance

    firewalls et access_control ont chacun leur règle de première correspondance, et ce sont deux décisions différentes. Pourquoi on se trompe : on croit qu'une seule sélection choisit « le bon dispositif » ; il y en a deux, indépendantes.

  • Voir l’explication : Un firewall security: false désactive aussi access_control

    Un firewall security: false désactive aussi access_control pour ses URL : aucun listener, aucune règle appliquée. Pourquoi on se trompe : on imagine access_control comme un filtre global, alors qu'il est appliqué par un listener du firewall.

  • Voir l’explication : Un firewall sans matcher effectif déclaré en premier capte tout, sans erreur.

    Un firewall sans matcher effectif déclaré en premier capte tout, sans erreur. L'absence de pattern seule ne suffit pas : vérifier host et request_matcher. Dans cette version, methods seul ne le rend pas filtrant. Pourquoi on se trompe : on pense que « le pattern le plus précis gagne ».

  • Voir l’explication : Plusieurs providers demandent un choix non ambigu

    Plusieurs providers demandent un choix non ambigu pour le mécanisme qui en a besoin, au niveau du firewall ou de l'authenticator concerné. Pourquoi on se trompe : on croit que Symfony prend le premier déclaré.

  • Voir l’explication : Par défaut, un user inconnu et un mauvais password donnent la même erreur

    Par défaut, un user inconnu et un mauvais password donnent la même erreur : expose_security_errors vaut none. Pourquoi on se trompe : le message « User not found » existe bien, mais seulement avec all.

Fiche express

À mémoriser

À retenir en priorité
  1. Employer l'option Symfony 8.0.
  2. Ne pas recopier une ancienne option supprimée.

Le diagnostic part maintenant d'une requête concrète et suit deux sélections distinctes. Les firewalls et les providers détaillent leurs responsabilités, sans changer l'ordre réel du traitement.

🧠 À retenir pour la certification :

  • Cinq sections : hashers, providers, firewalls, access_control, role_hierarchy.
  • Firewalls : premier matcher applicable ; access_control : première règle. Sans pattern n'exclut ni host ni un request_matcher personnalisé.
  • Le plus général en dernier ; une erreur d'ordre est silencieuse.
  • security: false : aucun listener, access_control mort.
  • Plusieurs providers : nommer le choix effectif du mécanisme concerné.
  • expose_security_errors : none par défaut, erreur de credentials générique.

Moyen mnémotechnique : « Le premier qui correspond gagne, deux fois ».

hashers / providers / firewalls (1er matcher applicable)
/ access_control (1re règle) / role_hierarchy ;
security: false = pas de listener ; 2 providers = provider explicite ;
expose_security_errors: none
