Objectif

N'appliquer qu'une partie des constraints d'une class, et connaître les deux groups que Symfony crée sans qu'on les déclare.

Question fil rouge : comment dire à Symfony « pour cette opération, applique seulement ces règles-là » ?

L'essentiel

À comprendre

À retenir en priorité
  1. Default est sélectionné implicitement.
  2. Les groups nommés demandent une sélection explicite.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un même modèle sert plusieurs scénarios : l'inscription exige un mot de passe, la modification de profil non. Dupliquer la classe serait absurde ; on étiquette les règles et on choisit les étiquettes à la validation.
  • Le piège de fond. Les étiquettes (groups) filtrent des règles : elles ne changent ni les données ni les droits d'accès. Et deux groups existent sans qu'on les déclare : Default et le nom court de la class, avec une relation à sens unique entre eux.
  • Ce que l'auteur veut que vous compreniez. Un group est un nom posé sur une constraint ; à la validation, on choisit les noms à appliquer. Sans group demandé, Default est demandé. Une contrainte de classe ou de propriété appartenant à Default reçoit aussi le groupe du nom court de sa classe. L'inverse n'est pas automatique.
  • Pourquoi c'est à l'examen. Les QCM jouent sur : ce que valide un appel sans groupe, la différence Default/nom de classe, la propagation en cascade, et l'héritage.

Les groupes filtrent donc des règles ; ils ne changent ni les données ni les droits d'accès de l'utilisateur.

Le schéma

À retenir en priorité
  1. Un group sélectionne des constraints.
  2. L'ordre nécessite une group sequence.

Où en est-on ? Vue d'ensemble : on valide un User avec le group registration. Le Validator sélectionne les règles de User portant ce group, descend dans Address via Valid en transmettant le même group, et sélectionne là-bas les règles qui le portent. Les sections suivantes détaillent : groups implicites, appel avec groups, Default contre nom de classe.

Bleu = sélection et propagation ; vert = résultat de validation. Les flèches suivent le travail du Validator, pas des appels entre les objets métier. Sans Valid, cette propriété imbriquée n'est pas suivie dans cet exemple. Une séquence de classe peut remplacer Default : voir Group sequence.

Pourquoi le nom du group est-il « transmis » plutôt que traduit en Default chez l'enfant ? Parce que le Validator travaille avec une liste de groups demandés pour tout l'arbre ; en descendant, il garde cette liste telle quelle. C'est chaque classe qui décide quelles constraints portent ces noms.

L'exemple : un `User` à deux usages

Exemple concret

À retenir en priorité
  1. Le group décrit un usage de validation.
  2. L'édition du profil peut choisir un autre jeu.

Où en est-on ? Le code minimal qui illustre les trois groups du cours (Default, registration, nom de la class). Gardez-le en tête : tout le reste le commente.

L'inscription du lecteur et la modification de son profil ne demandent pas nécessairement les mêmes données. Cet exemple conserve User comme modèle de démonstration ; SignupData pourrait porter la même sélection de règles. Choisir registration exprime un scénario de validation, pas un rôle Security accordé à l'utilisateur.

use Symfony\Component\Validator\Constraints as Assert;

class User
{
    #[Assert\Email(groups: ['registration'])]
    private string $email = 'invalide';

    #[Assert\NotBlank(groups: ['registration'])]
    #[Assert\Length(min: 7, groups: ['registration'])]
    private string $password = '';

    #[Assert\Length(min: 2)]
    private string $city = 'x';
}

À l'inscription, le password compte ; à la modification du profil, seule la ville est vérifiée. Avec le mapping activé, validate(new User()) signale donc city. Demander registration signale les erreurs d'email et de mot de passe, mais pas celle de la ville : il faut demander les deux groupes pour la conserver.

Tableau de lecture :

Champ Groups portés validate($u) validate($u, null, ['registration'])
email registration non vérifié violation
password registration non vérifié violation (vide)
city Default, User violation non vérifié

Les groups implicites

À retenir en priorité
  1. Les groups sont des noms libres.
  2. Aucun registre préalable n'est nécessaire.

Où en est-on ? Étape 1 sur 3 : d'où viennent Default et le nom de la class, alors qu'on ne les a écrits nulle part ? Le mécanisme est dans Constraint::addImplicitGroupName().

Une règle de ville commune reste dans Default, tandis qu'une règle de mot de passe réservée à l'inscription porte son groupe explicite. Le nom court de classe est un groupe ajouté aux règles Default lors du mapping ; ce n'est pas une nouvelle règle ni une seconde exécution obligatoire de chaque contrainte.

Group Contenu
Default les constraints sans groupe explicite ou avec groups: ['Default'] — ici city
User le nom de la class : les constraints de User qui sont dans Default
registration les constraints étiquetées — email et password
  • new Assert\NotBlank() porte ["Default"] ; rattachée à la class (addImplicitGroupName('User')), elle porte ["Default", "User"].
  • Un group ne se déclare nulle part : il existe dès qu'une constraint le nomme.

Un écart entre la documentation et le code. groups.rst range dans Default les constraints configurées avec le nom de la class. Exécuté : une constraint groups: ['User'] a pour seuls groups ["User"] et ne s'exécute pas en validant Default. Ce qui est dans Default est dans User, pas l'inverse.

Le mécanisme, en trois temps (le code de addImplicitGroupName()) :

1. La constraint est créée        NotBlank()               groups = ["Default"]
2. Elle est rattachée à User      addImplicitGroupName('User')
3. Le code teste : "Default" est dans groups ET 'User' n'y est pas encore ?
      oui → on AJOUTE 'User'                              groups = ["Default","User"]

   groups: ['User'] explicite   → "Default" absent → rien n'est ajouté
                                                     groups = ["User"] seulement

Pourquoi le sens unique ? La condition de départ est « Default est dans les groups ». Une constraint qui n'a que User ne remplit pas cette condition : Symfony n'ajoute pas Default. On se retrouve donc avec une flèche dans un seul sens : Default → User, jamais User → Default.

  ┌───────────────────────────┐        ┌───────────────────────────────┐
  │ NotBlank()                │        │ NotBlank(groups: ['User'])    │
  │ groups: Default           │        │ groups: User                  │
  │   + User (ajouté)         │        │ (pas de Default)              │
  ├───────────────────────────┤        ├───────────────────────────────┤
  │ validate($u)  → exécutée  │        │ validate($u)  → NON exécutée  │
  │ ['User']      → exécutée  │        │ ['User']      → exécutée      │
  └───────────────────────────┘        └───────────────────────────────┘

🌍 In Real Life

La situation : l'agent étiquette certaines règles « inscription » et garde les règles ordinaires dans Default. Lors du classement des règles ordinaires du dossier User, il leur ajoute aussi l'étiquette User ; poser seulement User sur une autre règle ne lui ajoute pas Default en retour.

L’équivalent dans Symfony : une contrainte sans groupe explicite appartient à Default. Son rattachement aux métadonnées de classe lui ajoute le groupe du nom court ; une contrainte explicitement limitée à User n'appartient pas automatiquement à Default.

Retour à la réalité technique : les étiquettes sélectionnent des règles, pas des données ou des droits. Elles ne constituent pas deux copies obligatoirement exécutées de chaque règle. Les groupes explicites remplacent la sélection implicite de la contrainte ; vérifie les métadonnées effectives plutôt que d'inférer un groupe depuis un nom de propriété.

🧠 Comment le mémoriser : « Default reçoit l'étiquette User ; User seul ne reçoit pas Default. » Image mentale : une flèche d'ajout d'étiquette dans un seul sens. Question-réflexe : quels groupes cette contrainte porte-t-elle réellement après mapping ?

⚠️ À ne pas confondre : groupe implicite, groupe explicite, rôle Security et groupe du Serializer.

Valider avec un group

À retenir en priorité
  1. Une faute de nom peut rendre la liste vide.
  2. Le validator ne signale pas le group inconnu.

Où en est-on ? Étape 2 sur 3 : on sait quels groups existent ; comment choisit-on ceux qu'on applique ? Par le troisième argument de validate() (ou validation_groups dans un form).

Pour garder les contrôles communs au POST d'inscription, demande Default et registration. Un simple tableau sélectionne ces groupes sans introduire un arrêt entre eux ; l'ordonnancement conditionnel relève d'une séquence. Ne prends pas le nom de groupe directement dans une saisie du client : le serveur choisit les règles nécessaires au scénario.

$validator->validate($user);                                   // Default
$validator->validate($user, null, ['registration']);           // registration seul
$validator->validate($user, null, ['Default', 'registration']); // les deux
  • Sans argument : Default, pas « toutes les constraints ».
  • Le troisième argument accepte aussi une string : 'Default'.
  • Un group inconnu ne lève rien : il ne sélectionne aucune constraint.
  • Dans un form : l'option validation_groups.

Pourquoi registration seul oublie-t-il la ville ? Parce que la ville est dans Default, pas dans registration. Demander un group sélectionne uniquement ses constraints ; Default n'est pas ajouté d'office.

Pourquoi un group inconnu ne lève-t-il rien ? Un group n'est pas un objet déclaré quelque part : c'est un simple nom. Un nom que personne n'utilise sélectionne zéro constraint ; le résultat est donc une liste vide, ce qui peut cacher une faute de frappe. D'où la prudence : une liste de violations vide ne prouve pas qu'on a choisi les bons groups.

validate($user)                      → [Default]            → city
validate($user, null, ['registration']) → [registration]    → email, password
validate($user, null, ['Default','registration'])           → city, email, password
validate($user, null, ['registraton'])  (faute de frappe)   → (rien, sans erreur !)

🌍 In Real Life

La situation : pour l'inscription, le bureau choisit la checklist commune et la checklist spécifique. Demander seulement la seconde laisse de côté les contrôles communs ; un nom mal écrit peut sélectionner une pile vide.

L’équivalent dans Symfony : l'argument groups ou validation_groups choisit les règles. ['Default', 'registration'] conserve les deux ensembles, tandis que registration seul n'ajoute pas Default.

Retour à la réalité technique : une liste de groupes n'impose pas l'arrêt conditionnel d'une GroupSequence. Sans groupe demandé, Default est demandé ; une séquence de classe configurée peut ensuite le remplacer. Une liste de violations vide ne prouve pas qu'on a choisi les bons groupes. Le serveur fixe ce choix selon l'opération autorisée, pas selon un nom arbitraire envoyé par le client.

🧠 Comment le mémoriser : « Checklist spécifique ne veut pas dire checklist commune incluse. » Image mentale : deux piles de règles qu'il faut sélectionner ensemble. Question-réflexe : quelles règles communes dois-je conserver dans ce scénario ?

⚠️ À ne pas confondre : sélection de groupes, séquence de groupes, validité globale et autorisation.

`Default` contre le nom de la class

À retenir en priorité
  1. La cascade transmet le nom sélectionné.
  2. Default garde son sens sur chaque class.

Où en est-on ? Étape 3 sur 3 : quand y a-t-il une vraie différence entre demander Default et demander User ? Dès qu'il y a un objet imbriqué ou de l'héritage.

L'adresse embarquée reçoit le groupe propagé, puis ses propres métadonnées décident quelles règles correspondent. Demander User ne signifie donc pas « valider par défaut tous les objets de cet utilisateur ». Avant d'interpréter une absence de violation sur l'adresse, vérifie à la fois le parcours Valid et les groupes portés par ses contraintes.

Dans une variante, User::$address porte #[Assert\Valid] sans groupes explicites. Supposons city et Address::$zip invalides dans Default, email et Address::$street invalides dans registration, et aucune règle User dans Address :

Group demandé Violations
Default city, address.zip
User city, sans address.zip
registration email, address.street

Le groupe demandé est transmis à Address. Ici User n'y sélectionne aucune règle ; il est bien transmis, et sélectionnerait une contrainte explicitement étiquetée User. Ce n'est pas une interdiction de cascade.

Pourquoi address.zip est-il absent avec User ? Dans Address, la constraint de zip porte Default et Address (le nom court de sa propre class), pas User. Le group transmis User ne la sélectionne donc pas. En revanche, Default est dans les groups de zip : il la sélectionne.

Avec l'inheritance, User extends BaseUser :

Group demandé Violations
Default ou User celles de User et de BaseUser
BaseUser celles de BaseUser seulement

La troisième différence, avec une group sequence, est traitée dans l'item Group sequence.

Pourquoi User couvre-t-il aussi BaseUser ? Les constraints héritées sont fusionnées dans les métadonnées de User ; celles qui étaient dans Default reçoivent aussi le nom court de la class qui les charge. Elles se retrouvent donc dans User. L'inverse est faux : les constraints propres à User n'existent pas dans les métadonnées de BaseUser.

          BaseUser                    User extends BaseUser
     NotBlank (Default,BaseUser)      NotBlank hérité (Default, User)
                                       + règles propres (Default, User)
['BaseUser'] → règles du parent seul  ['User'] / Default → parent + enfant

🌍 In Real Life

La situation : l'annexe d'adresse reçoit la même consigne « utiliser les règles registration » que le dossier principal, mais cherche ces règles dans son propre classeur. Une consigne User n'y devient pas magiquement Default.

L’équivalent dans Symfony : avec Valid sans groupes explicites, dans le scénario sans séquence décrit, le groupe demandé est propagé à Address. Ses métadonnées sélectionnent ensuite les contraintes correspondantes. L'héritage User/BaseUser est une autre relation : il fusionne des métadonnées de classe.

Retour à la réalité technique : absence de violation peut signifier groupe transmis sans règle correspondante, pas cascade interdite. Pour l'héritage, les résultats du tableau concernent les groupes implicites illustrés ; des étiquettes explicites peuvent ajouter d'autres correspondances. Ne généralise pas ce parcours aux séquences Default redéfinies sans examiner leur contrat.

🧠 Comment le mémoriser : « Même consigne transmise, classeur local consulté. » Image mentale : note registration voyageant du dossier à l'annexe. Question-réflexe : le groupe a-t-il été transmis, et quelles règles trouve-t-il dans l'objet atteint ?

⚠️ À ne pas confondre : cascade d'objets, héritage de classes, correspondance de groupes et redéfinition de Default.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le group de class reçoit les constraints Default.
  2. L'association inverse n'est pas automatique.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Récapitulatif des pièges, avec la raison de leur plausibilité.

  • Voir l’explication : Sans group passé, seul Default est validé.

    Sans group passé, seul Default est validé. Une constraint étiquetée registration ne s'exécute jamais si personne ne demande ce group. Pourquoi on se trompe : « sans filtre » fait penser « tout ».

  • Voir l’explication : Default et le nom de la class ne sont pas interchangeables

    Default et le nom de la class ne sont pas interchangeables dès qu'il y a un object imbriqué. Pourquoi on se trompe : sur une seule class, les deux donnent le même résultat.

  • Voir l’explication : Une constraint étiquetée du seul nom de la class n'est pas dans Default

    Une constraint étiquetée du seul nom de la class n'est pas dans Default, quoi qu'en dise la documentation. Pourquoi on se trompe : la phrase de groups.rst laisse croire à une équivalence bidirectionnelle.

  • Voir l’explication : Un group ne se déclare nulle part

    Un group ne se déclare nulle part : il existe dès qu'une constraint le nomme. Pourquoi on se trompe : on cherche une configuration ou une classe Group.

Fiche express

À mémoriser

À retenir en priorité
  1. La sélection peut se faire depuis le form.
  2. Le même mécanisme de groups reste utilisé.

Si tu dois retenir seulement 6 choses :

  • Contrainte sans groupe explicite, rattachée à une classe : Default et le groupe du nom court de cette classe ; appel sans groupe : Default.
  • validate($o) n'applique que Default.
  • groups: ['User'] n'est pas dans Default.
  • Cascade avec Valid sans groupes : le groupe demandé est transmis, même le nom de classe ; seules les règles portant ce groupe sont sélectionnées.
  • Inheritance : le group de la sous-classe couvre le parent ; celui du parent, le parent seul.
  • Un group inconnu ne lève rien : il ne sélectionne rien.

Moyen mnémotechnique : « Default par défaut, le reste sur demande ».

🧠 À retenir pour la certification

  1. Un group = une étiquette sur une constraint ; il n'existe nulle part ailleurs, et un nom inconnu ne lève rien.
  2. Sans group demandé : Default, jamais « toutes les constraints ».
  3. Sens unique : une constraint de Default reçoit le nom court de sa class ; groups: ['User'] n'entre pas dans Default (écart doc/code).
  4. Plusieurs groups : tableau (['Default', 'registration']), sans arrêt entre eux.
  5. Valid sans groupes explicites transmet le groupe demandé à l'objet imbriqué.
  6. Héritage : la sous-classe couvre le parent (groups implicites), pas l'inverse.

Phrase de mémorisation : « Sans rien, c'est Default ; Default reçoit le nom de la class mais pas l'inverse ; le group demandé voyage tel quel dans la cascade. »
