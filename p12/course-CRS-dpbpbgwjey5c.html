Objectif

Sur la page d'accueil du blog, chaque carte d'article doit contenir un lien vers /blog/42. Plutôt que d'écrire /blog/42 dans le HTML, on demande à Symfony de fabriquer cette adresse à partir du nom de la route. Ce cours explique qui fabrique l'URL, ce que le générateur décide seul, et pourquoi on n'écrit jamais une URL à la main.

Il s'agit de générer une URL depuis un template. Le generator lui-même et ses quatre types de référence sont traités dans le Module 05 — Routage.

L'essentiel

À comprendre

À retenir en priorité
  1. path() et url() génèrent depuis une route.
  2. absolute_url() complète un path.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une URL écrite à la main casse dès que le chemin d'une route change. Le nom de route, lui, reste stable : le template le cite, le routeur retrouve le chemin.
  • Le piège de fond. Quatre functions se ressemblent mais n'ont pas la même entrée : path() et url() prennent un nom de route, absolute_url() et relative_path() prennent un path.
  • Ce que l'auteur veut que vous compreniez. Le troisième argument true n'a pas le même sens pour path() et url(), et le générateur peut élargir la référence demandée (schéma ou host différent).
  • Pourquoi c'est à l'examen. Les QCM portent sur les quatre types de référence, le cas //host/…, localhost sans Request, &amp; dans la source HTML et le comportement de relative_path().

Deux functions prennent un route name — path() pour un path, url() pour une URL complète — et deux autres prennent un path — absolute_url() et relative_path(). Le generator peut élargir la référence demandée, et une URL ne s'écrit jamais à la main.

Le schéma

Où en est-on ? Vue d'ensemble, en quatre étapes : les deux functions de route (1), ce que le générateur décide seul (2), les deux functions de path (3), puis l'échappement (4) et la règle d'or (5). Le schéma Mermaid ci-dessous rassemble les trois premières ; on y reviendra section par section.

Un lien dans un template
   ├─ J'ai un NOM de route  → path(nom, params)  /  url(nom, params)
   │        └─ le générateur applique les contraintes de la route
   │           (schéma ? host ? paramètres en trop ?)
   └─ J'ai un PATH          → absolute_url('/x')  /  relative_path('/x')

Ambre = choix de référence ; bleu = résultat. Les chemins relatifs illustrés supposent la page /products/hover-board. Un changement de host ne raccourcit jamais une URL déjà absolue : url() reste absolue. Ne pas appliquer raw pour retirer les &amp; nécessaires au source HTML d'un lien.

Deux functions

À retenir en priorité
  1. Les deux functions partagent nom et parameters.
  2. Leur troisième argument ne signifie pas la même chose.

Où en est-on ? Étape 1 sur 5 : on part d'un nom de route et on veut une adresse. Deux functions du Twig Bridge s'en chargent : path() et url().

La carte de l'article42 reçoit son identifiant ; le bridge transmet blog_show et id au générateur. Le navigateur n'atteindra l'action qu'après une navigation. Les exemples à slug et /post/… conservés ici décrivent une autre déclaration de route : dans le fil principal, les deux appels emploient {id: article.id}.

<a href="{{ path('blog_show', {slug: post.slug}) }}">Lire</a>
<link rel="canonical" href="{{ url('blog_show', {slug: post.slug}) }}">
Appel Type de référence Depuis /products/hover-board
path(nom, params) ABSOLUTE_PATH /post/mon-article
path(nom, params, true) RELATIVE_PATH ../post/mon-article
url(nom, params) ABSOLUTE_URL http://example.com/post/mon-article
url(nom, params, true) NETWORK_PATH //example.com/post/mon-article

Les deux premiers arguments sont communs ; le troisième diffère : relative pour path(), schemeRelative pour url().

Pourquoi le troisième argument n'a-t-il pas le même sens ? Regardons ce que fait le bridge (RoutingExtension) :

path($nom, $params, $relative = false)
   └─ $relative ? RELATIVE_PATH  : ABSOLUTE_PATH

url($nom, $params, $schemeRelative = false)
   └─ $schemeRelative ? NETWORK_PATH : ABSOLUTE_URL

Chemin d'exécution de path('blog_show', {id: 42}) :

Twig rencontre path('blog_show', {id: 42})
   ▼
RoutingExtension::getPath()
   ▼
UrlGenerator::generate('blog_show', ['id' => 42], ABSOLUTE_PATH)
   ▼
"/blog/42"  → écrit dans le HTML ; aucun contrôleur n'est exécuté

Les quatre types de référence, côte à côte :

┌──────────────┬──────────────┬──────────────┬─────────────────────────────┐
│ path()       │ path(…, true)│ url()        │ url(…, true)                │
├──────────────┼──────────────┼──────────────┼─────────────────────────────┤
│ ABSOLUTE_PATH│RELATIVE_PATH │ ABSOLUTE_URL │ NETWORK_PATH                │
├──────────────┼──────────────┼──────────────┼─────────────────────────────┤
│ /post/x      │ ../post/x    │ http://h/p/x │ //h/post/x                  │
└──────────────┴──────────────┴──────────────┴─────────────────────────────┘

Pourquoi la mauvaise réponse est plausible : true paraît toujours signifier « version plus courte/relative ». Pour url(), il signifie « sans schéma », ce qui reste une référence réseau, pas un chemin relatif.

🌍 In Real Life

La situation : l'accueil du restaurant imprime une indication pour rejoindre une destination connue : un chemin local pour le visiteur sur place, ou une adresse complète pour une invitation envoyée ailleurs.

L’équivalent dans Symfony : path() et url() transmettent un nom de route et des paramètres au générateur. Pour le fil /blog/42, blog_show et id: 42 désignent le contrat de destination, pas un appel de l'action.

Retour à la réalité technique : les fonctions demandent respectivement un chemin absolu et une URL absolue. Le troisième argument true demande un chemin relatif pour path(), mais une référence réseau sans schéma pour url(). Ce sont des demandes soumises aux contraintes de route et au contexte.

🧠 Comment le mémoriser : « Imprimer l'adresse n'effectue pas la visite. » Image mentale : invitation prête, visiteur encore immobile. Question-réflexe : quel type de référence ai-je demandé, et que signifie ici le troisième argument ?

⚠️ À ne pas confondre : génération, navigation HTTP et exécution du contrôleur.

Un numéro de salle suffit souvent à quelqu'un déjà dans le bâtiment ; une adresse complète convient à un destinataire extérieur. Pour un lien d'email, url() exprime cette adresse complète plutôt qu'un simple path.

Repère — Ce que le generator décide seul :

Question: Can path() return more than an absolute path?

Answer: Yes. A different host or scheme can require a network-path or absolute URL.

Le generator respecte host et schemes. Le nom path() n'interdit pas ces formes nécessaires.

Repère — Deux functions voisines, sans route :

Question: Does absolute_url() accept a route name?

Answer: No. It accepts a path.

path() et url() génèrent depuis une route. absolute_url() complète un path.

Repère — L'escaping :

Question: Is an ampersand escaped as &amp; in an HTML link a broken query string?

Answer: No. That is the correct HTML representation.

Le contexte HTML impose son escaping. Ne pas utiliser raw pour corriger un ampersand correctement échappé.

Ce que le generator décide seul

À retenir en priorité
  1. Le generator respecte host et schemes.
  2. Le nom path() n'interdit pas ces formes nécessaires.

Où en est-on ? Étape 2 sur 5 : on a demandé un type de référence, mais la route impose parfois ses propres règles (schéma, host). Le générateur adapte alors le résultat. Cette partie liste ces cas.

Depuis la page HTML du blog, la forme demandée reste soumise à la destination configurée. Un simple path ne peut pas envoyer le lecteur sur un autre host ; le générateur l'élargit. Dans une newsletter, configure le contexte explicitement : le rendu console ne connaît ni le domaine public par intuition ni la future Request du lecteur.

  • Une route qui exige un autre schéma que la Request rend une URL absolue, même par path() : https://example.com/sec.
  • Avec path(), un autre host, sans changement de schéma imposé, produit //api.example.com/o ; url() conserve son URL absolue.
  • Un paramètre supplémentaire ordinaire, non utilisé par les variables de route et non égal à un défaut, peut alimenter la query string : /post/x?ref=nl. Les clés spéciales, comme _fragment, ont un autre rôle.
  • Une route inconnue lève RouteNotFoundException, que le template reçoit dans une RuntimeError.
  • Sans Request — une command qui envoie un email —, url() prend le host du contexte du router, localhost par défaut : http://localhost/post/z. framework.router.default_uri le corrige.

Pourquoi un simple path ne peut-il pas aller sur un autre host ? Un chemin /status n'a de sens que sur le site courant. Si la route est liée à api.example.com, il faut dire où : le générateur écrit //api.example.com/status.

Page servie sur example.com, route "status" liée à api.example.com :

path('status')   →  //api.example.com/status       (élargi : référence réseau)
url('status')    →  http://api.example.com/status  (déjà absolue : inchangée)

Route "sec" exigeant https, page servie en http :

path('sec')      →  https://example.com/sec        (schéma différent → absolue)

Pourquoi /post/x?ref=nl ? ref n'est pas une variable de la route /post/{slug} : le générateur le range en query string. Mais si une variable obligatoire reste sans valeur (faute de nom : idd: 42 au lieu de id), il lève MissingMandatoryParametersException — rien n'est silencieux.

Cas Résultat
paramètre en trop (ref: 'nl') ?ref=nl
paramètre en trop égal à un défaut omis
_fragment: 'top' ancre #top, pas un paramètre de query
variable obligatoire manquante MissingMandatoryParametersException
route inconnue RouteNotFoundException (dans une RuntimeError côté template)
pas de Request (console) host du contexte : localhost sans default_uri

🌍 In Real Life

La situation : une indication « porte suivante » ne suffit plus lorsque la destination appartient à un autre établissement. Le service d'adressage ajoute les coordonnées nécessaires ; il ne devine pas une adresse publique absente de son carnet.

L’équivalent dans Symfony : un changement de host peut imposer //host/…, un changement de schéma une URL absolue. Hors Request, le générateur utilise son contexte configuré, notamment framework.router.default_uri.

Retour à la réalité technique : une URL déjà absolue n'est pas raccourcie par le changement de host. Les paramètres supplémentaires ordinaires peuvent devenir une query string ; les paramètres spéciaux, comme _fragment, ont leur traitement propre. Une faute de nom qui laisse un paramètre obligatoire sans valeur peut néanmoins faire échouer la génération. Une route inexistante échoue aussi, sans recherche de contenu métier.

🧠 Comment le mémoriser : « La destination impose les coordonnées utiles. » Image mentale : indication locale complétée par l'adresse de l'autre établissement. Question-réflexe : quels host, schéma et paramètres le contexte et la route exigent-ils ?

⚠️ À ne pas confondre : paramètre supplémentaire, paramètre requis manquant et route inconnue.

Deux functions voisines, sans route

Où en est-on ? Étape 3 sur 5 : parfois on n'a pas de nom de route, juste un chemin déjà connu (un logo, un fichier statique). Deux autres functions, fournies par HttpFoundationExtension, travaillent alors sur ce chemin.

Pour rendre absolu le chemin du logo déjà obtenu, absolute_url() convient. Pour l'article, pars en revanche du nom de route avec url(). Confondre les deux entrées produirait un chemin basé sur le texte blog_show, pas une résolution de ses paramètres.

HttpFoundationExtension ajoute deux functions qui prennent un path :

  • absolute_url('/images/logo.png') → http://example.com/images/logo.png, souvent combinée à asset() ;
  • relative_path('/human.txt') → ../human.txt depuis /products/hover-board.

relative_path() rend inchangée une URL complète : avec 'http://example.com/human.txt', le résultat est l'URL elle-même — contrairement à l'exemple de la documentation de référence ; le code 8.0 tranche.

Pourquoi relative_path() laisse-t-il une URL complète inchangée ? Dans UrlHelper::getRelativePath(), un argument qui contient :// (ou commence par //) est rendu tel quel : on ne peut pas exprimer « relativement » une adresse qui désigne déjà un autre endroit.

Depuis la page /products/hover-board :

relative_path('/human.txt')                   → ../human.txt
relative_path('http://example.com/human.txt') → http://example.com/human.txt
absolute_url('/images/logo.png')              → http://example.com/images/logo.png
absolute_url('blog_show')                     → chemin basé sur le texte blog_show

Comparaison des deux familles :

path() / url() absolute_url() / relative_path()
Entrée nom de route + paramètres un path
Qui travaille RoutingExtension → UrlGenerator HttpFoundationExtension → UrlHelper
Applique les contraintes de route oui non
Cas d'usage liens vers l'application logo, fichier statique

🌍 In Real Life

La situation : compléter une adresse déjà écrite avec sa ville n'est pas rechercher dans l'annuaire le lieu nommé « accueil ». Le premier travail transforme une adresse ; le second résout un nom.

L’équivalent dans Symfony : absolute_url() et relative_path() travaillent sur des chemins via HttpFoundation, contrairement à url() et path() qui consultent les routes nommées.

Retour à la réalité technique : relative_path() laisse une URL complète inchangée dans le comportement Symfony8.0 décrit ici. absolute_url('blog_show') n'applique ni les placeholders ni la définition de cette route. Aucun de ces helpers ne vérifie que la ressource distante existe ou que sa destination est autorisée.

🧠 Comment le mémoriser : « Transformer une adresse, ce n'est pas consulter l'annuaire. » Image mentale : adresse déjà écrite face à une fiche portant seulement un nom. Question-réflexe : mon entrée est-elle un chemin ou un nom de route ?

⚠️ À ne pas confondre : transformation de chemin, génération par route et validation de destination.

L'escaping

À retenir en priorité
  1. Le contexte HTML impose son escaping.
  2. Ne pas utiliser raw pour corriger un ampersand correctement échappé.

Où en est-on ? Étape 4 sur 5 : l'URL est générée ; il faut maintenant l'insérer dans le HTML. C'est une étape distincte de la génération, avec un effet visible : le &amp; dans le source.

Le lien de suivi peut contenir deux paramètres séparés par &. Dans l'attribut HTML, &amp; représente correctement ce séparateur : le navigateur le décodera. Ce résultat n'est pas une URL cassée à « réparer » avec raw ; encodage URL et échappement du contexte HTML se complètent.

path() et url() déclarent un is_safe_callback : leur output n'échappe pas sans parameters, ou avec un seul parameter littéral. Sinon il est échappé : le & d'une query string devient &amp;, ce qui est correct dans un attribute HTML.

Pourquoi cette règle ? Le générateur encode en pourcentage tout caractère non alphanumérique : une URL générée ne contient donc rien de dangereux, sauf un caractère qui doit être échappé en HTML : le & qui sépare les paramètres de query. Twig ne peut le savoir à la compilation que s'il n'y a pas de paramètres ou un seul paramètre constant ; dans les autres cas, il laisse l'autoescape agir.

path('post', {slug: 'x'})                         → un seul paramètre constant
   → déclaré sûr : aucun échappement ajouté
path('post', {slug: 'x', ref: 'nl', utm: 'a'})    → plusieurs paramètres
   → échappé : source HTML  /post/x?ref=nl&amp;utm=a
   → le navigateur décode  &amp;  en  &  : l'URL suivie est /post/x?ref=nl&utm=a

🌍 In Real Life

La situation : l'adresse d'une invitation doit être transcrite selon les règles de l'imprimeur. Les signes employés dans le document ne sont pas forcément ceux que le lecteur manipulera après lecture.

L’équivalent dans Symfony : l'encodage du générateur prépare l'URL ; l'échappement Twig prépare son insertion HTML. Dans un attribut entre guillemets, &amp; représente le & que le navigateur interprétera dans l'URL.

Retour à la réalité technique : le callback de sûreté de path()/url() permet certaines optimisations d'échappement HTML selon les arguments connus à la compilation. Ce n'est pas une garantie pour tous les contextes, notamment JavaScript, ni une validation d'URL arbitraire. Ne supprime pas l'échappement avec raw pour modifier l'apparence du source HTML.

🧠 Comment le mémoriser : « Adresse correcte, transcription correcte : deux étapes. » Image mentale : adresse puis version imprimable dans le document. Question-réflexe : suis-je en train d'encoder une URL ou de l'insérer dans un contexte de sortie ?

⚠️ À ne pas confondre : encodage URL, échappement HTML et autorisation d'une destination.

Jamais d'URL écrite à la main

À retenir en priorité
  1. Le route name constitue le point de référence.
  2. Le generator encode et applique les contraintes de destination.

Où en est-on ? Étape 5 sur 5 : la règle qui justifie tout le reste. Après avoir vu comment générer, voyons pourquoi on ne tape jamais /blog/42 directement dans un template.

Pour les routes de l'application, génère les liens par leur nom : changer le path ne doit pas obliger à rechercher chaque occurrence dans les templates. Des tests peuvent détecter des liens cassés, mais ne remplacent pas ce contrat. Une URL externe connue n'est pas pour autant un nom de route interne. Le generator applique aussi le schéma et le host exigés, retire un parameter égal à sa default value et encode les valeurs.

Avant / après, quand la route passe de /blog/{id} à /articles/{id} :

URL écrite à la main  : <a href="/blog/42">   → 404 : à corriger partout
Nom de route          : path('blog_show', …)  → /articles/42 : rien à changer

Ce que le générateur fait à votre place :

Tâche Écrit à la main Via path() / url()
Suivre un changement de chemin oublis possibles automatique
Schéma / host exigés par la route à gérer soi-même appliqués
Paramètre égal à sa valeur par défaut présent retiré
Encodage des valeurs à faire soi-même fait

🌍 In Real Life

La situation : le restaurant change l'emplacement de son accueil. Les invitations qui consultent le nom stable « accueil » prennent la nouvelle adresse ; celles qui recopient l'ancien chemin deviennent obsolètes.

L’équivalent dans Symfony : référencer le nom de route centralise la définition du chemin, des paramètres, du host et du schéma. Les templates n'ont pas à recopier la forme physique de chaque URL interne.

Retour à la réalité technique : le nom et les paramètres constituent tout de même un contrat à maintenir. L'omission des valeurs par défaut dépend des règles de génération, de la position des segments optionnels et d'une éventuelle inclusion forcée. Une URL externe connue n'est pas transformée en route interne par cette recommandation.

🧠 Comment le mémoriser : « Garder le nom, centraliser l'adresse. » Image mentale : plusieurs invitations consultant une même fiche de destination. Question-réflexe : si le chemin change, combien de templates devront être corrigés ?

⚠️ À ne pas confondre : nom de route stable, chemin actuel et URL externe.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le troisième argument n'a pas le même sens dans les deux functions

    Le troisième argument n'a pas le même sens dans les deux functions : path relatif pour l'une, URL sans schéma pour l'autre. Pourquoi on se trompe : les deux signatures ont un booléen en troisième position, on suppose donc qu'il fait la même chose.

  • Voir l’explication : La function de path peut retourner une URL absolue

    La function de path peut retourner une URL absolue, quand la route exige un autre schéma — ou une référence //hôte/… quand elle est liée à un autre host. Pourquoi on se trompe : le nom path() suggère « toujours un chemin ».

  • Voir l’explication : Un paramètre supplémentaire ordinaire peut alimenter la query string, mais une faute de nom n'est pas forcément silencieuse.

    Un paramètre supplémentaire ordinaire peut alimenter la query string, mais une faute de nom n'est pas forcément silencieuse. Si idd: 42 laisse le {id} obligatoire sans valeur dans les paramètres, les défauts et le contexte, le générateur lève MissingMandatoryParametersException. Les clés spéciales ne suivent pas la règle ordinaire : _fragment fournit l'ancre, pas un paramètre de query. Pourquoi on se trompe : « les paramètres en trop vont dans la query » fait croire qu'une faute de frappe passe toujours sans erreur.

  • Voir l’explication : absolute_url() prend un path, pas un route name.

    absolute_url() prend un path, pas un route name. Pourquoi on se trompe : elle ressemble à url(), qui, elle, prend un nom de route.

  • Voir l’explication : relative_path() laisse une URL complète inchangée

    relative_path() laisse une URL complète inchangée : seul un path, /human.txt, devient relatif — contrairement à l'exemple de la documentation de référence. Pourquoi on se trompe : la doc de référence montre un résultat relatif ; le code 8.0 renvoie l'URL telle quelle.

  • Voir l’explication : &amp; dans le source n'est pas un bug.

    &amp; dans le source n'est pas un bug. C'est l'échappement HTML correct d'un séparateur de query. Pourquoi on se trompe : on lit le source brut et on oublie que le navigateur décode l'attribut.

Application

À retenir en priorité
  1. path() et url() génèrent depuis une route.
  2. absolute_url() complète un path.
  3. Les deux functions partagent nom et parameters.
  4. Leur troisième argument ne signifie pas la même chose.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • path() : path absolu ; url() : URL complète.
  • true en troisième argument : relatif pour path(), sans schéma pour url().
  • Autre schéma → URL absolue ; autre host → au moins //host/…, sans raccourcir une URL déjà absolue.
  • Paramètre supplémentaire ordinaire → query string sauf valeur égale à un défaut ; variable obligatoire sans valeur → erreur ; _fragment → ancre.
  • Plus d'un parameter → output échappé (&amp;).
  • absolute_url() / relative_path() : un path ; une URL complète reste inchangée.
  • Hors Request, url() rend http://localhost/… sans default_uri.

Moyen mnémotechnique : « path pour la page, url pour l'extérieur, et jamais à la main ».

path = /x, url = http://host/x ; true = relatif / sans schéma ;
schéma ≠ → absolue ; host ≠ → au moins //host ;
extra ordinaire → query (hors défaut identique) ; requis manquant → erreur ;
_fragment → ancre ; >1 param → &amp; ;
absolute_url/relative_path sur un path, URL complète inchangée

Revoir : Deux functions

What does the third true argument mean for path() and url()?

For path() it requests a relative path; for url() a scheme-relative URL.

Les deux functions partagent nom et parameters. Leur troisième argument ne signifie pas la même chose.

Revoir le passage précis

Revoir : Ce que le generator décide seul

Can path() return more than an absolute path?

Yes. A different host or scheme can require a network-path or absolute URL.

Le generator respecte host et schemes. Le nom path() n'interdit pas ces formes nécessaires.

Revoir : L'escaping

Is an ampersand escaped as &amp; in an HTML link a broken query string?

No. That is the correct HTML representation.

Le contexte HTML impose son escaping. Ne pas utiliser raw pour corriger un ampersand correctement échappé.

Revoir : Jamais d'URL écrite à la main

Why generate application links from route names?

Path changes then propagate through the URL generator.

Le route name constitue le point de référence. Le generator encode et applique les contraintes de destination.

Avant de poursuivre : Template includes.

When is embed useful instead of include?

When including a fragment while overriding some of its blocks.

include réutilise un fragment tel quel. embed combine inclusion et personnalisation des blocks.

Relire la correction dans le cours antérieur

Avant le quiz : Sur la page d'accueil du blog, chaque carte d'article doit contenir un lien vers /blog/42. Plutôt que d'écrire /blog/42 dans le HTML, on demande à Symfony de fabriquer cette adresse à partir du nom de la route. Ce cours explique qui fabrique l'URL, ce que le générateur décide seul, et pourquoi on n'écrit jamais une URL à la main.

Quelle donnée entre, quelle responsabilité agit et quelle condition change le résultat ? Pour chaque correction, vérifiez ces conditions dans le passage enseigné, sans supposer que toutes les branches du blog sont exécutées.
