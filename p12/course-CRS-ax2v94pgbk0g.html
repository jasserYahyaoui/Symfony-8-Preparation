Objectif

La lecture de /blog/42 n'impose pas de valider l'article. En revanche, l'inscription d'un auteur donne à l'application un objet saisi qu'elle doit vérifier avant de l'accepter. Déclarer les contraintes décrit les règles ; un appel au Validator ou une intégration Form configurée doit encore demander leur évaluation.

Attacher des constraints à une class PHP, et savoir jusqu'où la validation descend. Les scopes — property, accessor, class — sont traités dans Validation scopes.

Question fil rouge : quand je valide un objet, quelles règles sont réellement chargées, et jusqu'où le Validator va-t-il dans ses objets imbriqués ?

L'essentiel

À comprendre

À retenir en priorité
  1. La descente n'est pas automatique.
  2. Valid et Cascade activent la validation imbriquée.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une application valide rarement un scalaire isolé : elle valide un objet (un auteur, une facture) qui en contient d'autres. Il faut donc savoir où écrire les règles, comment le Validator les retrouve, et jusqu'où il descend.
  • Le piège de fond. « Aucune violation » est la réponse la plus trompeuse du Validator : elle veut seulement dire que les règles chargées et évaluées n'ont rien trouvé. Une règle non chargée, ou un objet imbriqué non parcouru, produit le même silence.
  • Ce que l'auteur veut que vous compreniez. Les constraints d'une class se déclarent en attributes, YAML, XML ou PHP. La validation ne descend pas toute seule dans un object imbriqué : il faut #[Assert\Valid] ou #[Assert\Cascade]. Et les constraints d'un parent s'ajoutent à celles de l'enfant, sans jamais être remplacées.
  • Pourquoi c'est à l'examen. Les QCM jouent sur la cascade silencieuse, sur Cascade (types éligibles, exclude, pas de groups), sur loadValidatorMetadata() statique et sur la fusion d'héritage.

Le schéma

À retenir en priorité
  1. Le path garde l'index de collection.
  2. La violation désigne ensuite la property imbriquée.

Où en est-on ? Vue d'ensemble du cours : on valide un Author. Le Validator charge d'abord les règles (fusionnées avec celles du parent), puis, pour la propriété address, il se demande « la cascade est-elle activée ? ». Les sections suivantes suivent exactement cet ordre : formats de déclaration → cascade → héritage → class tierce.

Bleu = travail du Validator ; ambre = activation de la cascade ; vert = résultat de ce chemin. Le dessin suppose une adresse présente et invalide. null ne déclenche pas la validation d'un objet absent : ajouter NotNull si sa présence est obligatoire. Les flèches ne sont pas de l'héritage PHP.

Pourquoi le Validator ne descend-il pas tout seul ? Parce que descendre est un choix : un objet imbriqué peut être énorme (entité liée en base, graphe cyclique) ou déjà validé ailleurs. Symfony préfère un comportement explicite plutôt qu'un parcours automatique du graphe.

Le fil rouge : un auteur et son adresse

À retenir en priorité
  1. L'object racine et son adresse sont deux cibles.
  2. Déclarer la descente pour vérifier l'adresse.

Où en est-on ? Un exemple minimal avant de détailler : il isole la frontière entre « objet validé » et « objet contenu ». Observez le code postal vide dans Address.

L'auteur du blog possède une adresse, mais posséder un objet PHP ne signifie pas que ses règles seront parcourues. L'exemple isole cette frontière : le nom satisfait ses contraintes, tandis que le code postal imbriqué est vide. Le résultat dépend donc de la cascade configurée, pas du nombre d'objets accessibles depuis l'auteur.

use Symfony\Component\Validator\Constraints as Assert;

class Address
{
    #[Assert\NotBlank]
    public string $zipCode = '';
}

class Author
{
    #[Assert\NotBlank]
    #[Assert\Length(min: 3)]
    private string $name = 'Ada';

    public Address $address;      // sans Valid : l'adresse n'est pas validée

    public function __construct()
    {
        $this->address = new Address();
    }
}

Avec le mapping activé, cet auteur produit zéro violation malgré son code postal vide. Ajouter #[Assert\Valid] sur $address donne une violation address.zipCode. Le résultat vide initial signifie « aucune règle évaluée n'a échoué », pas « tous les objets accessibles sont valides ».

Avant / après :

SANS Valid                          AVEC #[Assert\Valid] sur $address
Author  ── name  : vérifié ✔        Author  ── name    : vérifié ✔
        └─ address : ignorée                 └─ address : parcourue
           (zipCode vide : invisible)           └─ zipCode vide → violation
résultat : 0 violation              résultat : address.zipCode

🌍 In Real Life

La situation : l'agent vérifie le nom sur la couverture d'un dossier, mais n'ouvre pas la pièce jointe contenant l'adresse. Son compte rendu peut être sans erreur alors que le code postal manque dans la pièce jointe.

L’équivalent dans Symfony : valider Author évalue les contraintes sélectionnées de l'auteur ; atteindre Address exige une cascade configurée. Avec Valid, la violation peut porter le chemin address.zipCode, qui indique où chercher la donnée fautive.

Retour à la réalité technique : une liste vide signifie qu'aucune contrainte évaluée n'a produit de violation. Elle ne prouve ni le chargement de toutes les métadonnées attendues ni l'examen de tous les objets accessibles.

🧠 Comment le mémoriser : « Aucun défaut trouvé ne dit pas tout a été inspecté. » Image mentale : couverture cochée, annexe encore fermée. Question-réflexe : quelles règles et quels objets ont réellement été parcourus ?

⚠️ À ne pas confondre : absence de violations et certificat universel de validité.

Les quatre formats de déclaration

À retenir en priorité
  1. Le mapping PHP utilise une method statique.
  2. Le standalone doit activer le loader correspondant.

Où en est-on ? Étape 1 sur 4 : avant même de descendre dans des objets, le Validator doit connaître les règles. D'où viennent-elles ? Des métadonnées de la class, déclarées dans l'un des quatre formats.

Le Validator doit charger les métadonnées avant d'examiner l'auteur. Les quatre formats expriment les règles ; ils ne changent pas la nature de la saisie ni ne déclenchent eux-mêmes sa validation. Hors framework, oublier d'activer le loader approprié peut expliquer l'absence de violations alors que la classe porte visiblement des attributs de contrainte.

Format Où Hors framework, à activer
attributes sur la class enableAttributeMapping()
PHP loadValidatorMetadata(), statique addMethodMapping('loadValidatorMetadata')
YAML, XML config/validator/ addYamlMapping(), addXmlMapping()
  • Une property privée est lue sans accessor.
  • loadValidatorMetadata() non statique : StaticMethodLoader lève une MappingException, « …should be static. »

Code minimal du format PHP :

use Symfony\Component\Validator\Mapping\ClassMetadata;

class Author
{
    public static function loadValidatorMetadata(ClassMetadata $metadata): void
    {
        $metadata->addPropertyConstraint('name', new Assert\NotBlank());
    }
}

Pourquoi static ? Au moment où le Validator charge les règles, il n'existe aucune instance : StaticMethodLoader appelle la méthode sur la class (Author::loadValidatorMetadata($metadata)). D'où la MappingException « should be static » si ce n'est pas le cas.

Pourquoi une property privée est-elle lisible ? Les métadonnées de propriété lisent la valeur par réflexion : pas besoin de getter public.

Un piège de vocabulaire : les attributes #[Assert\…] sont des attributs PHP qui décrivent des règles ; ils n'ont rien à voir avec les attributes de la Request (route, _controller…).

🌍 In Real Life

La situation : les critères d'inscription peuvent figurer sur le dossier ou dans un règlement séparé. Pour contrôler un dossier, l'agent doit d'abord disposer du bon règlement, puis effectuer le contrôle.

L’équivalent dans Symfony : attributes, YAML, XML et méthode PHP décrivent les métadonnées de validation. Les loaders configurés les chargent ; un appel de validation, direct ou via l'intégration Form, demande ensuite leur évaluation.

Retour à la réalité technique : déclarer une contrainte n'exécute pas son validateur. Hors framework, activer les mappings nécessaires est explicite. loadValidatorMetadata() est statique ; les métadonnées de propriété permettent aussi l'accès à une propriété privée sans imposer un getter public.

🧠 Comment le mémoriser : « Écrire la règle, charger la règle, appliquer la règle. » Image mentale : règlement livré au poste de contrôle. Question-réflexe : le Validator connaît-il réellement ce format de déclaration ?

⚠️ À ne pas confondre : métadonnées PHP #[Assert\…] et attributs de la Request ; déclaration et exécution.

La validation ne descend pas toute seule

À retenir en priorité
  1. Valid vérifie l'object présent.
  2. Une constraint de présence traite null.

Où en est-on ? Étape 2 sur 4 : les règles sont chargées ; reste la question du schéma : le Validator entre-t-il dans $address ? Deux outils l'activent : Valid (par property) et Cascade (pour toute la class).

Après la validation du nom, nous voulons que l'adresse soit examinée et qu'une erreur puisse être reliée à address.zipCode dans le formulaire. Valid active ce parcours à la propriété ; Cascade peut le déclarer à l'échelle de la classe selon les types éligibles. Aucun des deux ne crée une adresse manquante : exiger sa présence reste une contrainte distincte.

Déclaration Violations d'une adresse invalide
rien aucune
#[Assert\Valid] sur la property address.zipCode
#[Assert\Cascade] sur la class address.zipCode
#[Assert\Valid] sur un array d'adresses addresses[0].zipCode, addresses[1].zipCode
#[Assert\Valid], property à null aucune : NotNull en plus pour l'exiger
  • Cascade décide d'après le type déclaré, pas le contenu découvert : par exemple Address, ?Address et array sont éligibles. Un tableau d'adresses typé array est donc parcouru ; ses éléments scalaires ne sont pas des objets à valider. Une propriété sans type, mixed ou string n'est pas sélectionnée automatiquement. Les unions et intersections suivent les règles de ClassMetadata::canCascade(). exclude: ['address'] retire une propriété ; il n'a pas d'option groups — new Assert\Cascade(groups: ['A']) : « Unknown named parameter $groups ».
  • Valid sans groupes explicites active la cascade pour le groupe demandé : validé avec le groupe Registration, il descend et transmet ce group — une Address dont street porte NotBlank(groups: ['Registration']) signale address.street, pas address.zipCode.

Comparaison des deux outils :

┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│ #[Assert\Valid]                  │   │ #[Assert\Cascade]                │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ posé sur UNE property            │   │ posé sur la CLASSE               │
│ choix explicite, property par    │   │ toutes les properties dont le    │
│ property                         │   │ TYPE DÉCLARÉ est éligible        │
│ marche aussi sur un array        │   │ (classe, ?classe, array)         │
│ d'objets (chemins [0], [1])      │   │ exclude: ['address'] pour        │
│ option traverse                  │   │ retirer une property             │
│                                  │   │ pas d'option groups (erreur PHP) │
└──────────────────────────────────┘   └──────────────────────────────────┘

Pourquoi Cascade ignore-t-elle une property sans type ? Dans le code de ClassMetadata::addConstraint(), Cascade parcourt les properties de la class et, pour chacune, appelle canCascade($property->getType()) : un type null (property non typée) rend false. Le contenu de la valeur n'est jamais regardé, seul le type compte. Pour un type nommé, la décision est vraie si c'est array, null ou une class existante : un string n'est pas éligible.

Pourquoi Cascade(groups: …) échoue-t-il ? Le constructeur de Cascade n'accepte que exclude : PHP refuse le named argument inconnu avec une Error, avant toute logique Symfony.

🌍 In Real Life

La situation : le dossier porte l'instruction « examiner aussi l'annexe adresse ». Cette instruction ne crée pas une annexe absente et ne décide pas à elle seule quelles vérifications s'appliquent à l'inscription.

L’équivalent dans Symfony : Valid ouvre le parcours de la propriété ; Cascade sélectionne des propriétés éligibles à l'échelle de la classe. Les groupes déterminent les contraintes pertinentes ; NotNull exige séparément la présence de l'adresse.

Retour à la réalité technique : Cascade se fonde sur les types déclarés éligibles et ses exclusions, pas sur une fouille arbitraire des valeurs. Valid sans groupes explicites transmet le groupe demandé. Aucun de ces mécanismes ne charge automatiquement un objet en base.

🧠 Comment le mémoriser : « Ouvrir l'annexe n'est pas exiger sa présence. » Image mentale : instruction de lecture sur une pochette vide. Question-réflexe : dois-je exiger l'objet, parcourir son contenu, ou sélectionner ses règles ?

⚠️ À ne pas confondre : cascade Validator, cascade de persistance et désérialisation d'objets imbriqués.

L'inheritance fusionne, il ne remplace pas

À retenir en priorité
  1. L'inheritance cumule les constraints.
  2. Les groups permettent de séparer leurs usages.

Où en est-on ? Étape 3 sur 4 : jusqu'ici une seule class. Que se passe-t-il quand SpecialAuthor extends Author ? Les règles chargées sont celles de toute la chaîne.

Si un auteur spécialisé ajoute une longueur minimale au nom déjà contraint par sa classe parente, il enrichit les règles chargées. Le Validator ne traite pas une redéclaration comme le remplacement d'une méthode PHP : la règle héritée reste présente. Avant de modifier les groupes, vérifie donc si deux messages identiques viennent de deux contraintes réellement déclarées.

Parent NotBlank, enfant Length(min: 5) : 'abc' échoue sur Length, et une valeur vide sur les deux. La même constraint redéclarée dans l'enfant produit deux violations identiques. Cela ne se désactive pas ; seuls des groups différents séparent le parent de l'enfant.

Author (parent)           SpecialAuthor (enfant)       Règles chargées
name : NotBlank      +    name : Length(min: 5)   =    NotBlank + Length(5)
name : NotBlank      +    name : NotBlank         =    NotBlank + NotBlank
                                                       → 2 violations identiques

Pourquoi deux violations et pas une ? Chaque déclaration devient une constraint distincte dans les métadonnées ; le Validator évalue chacune et n'a aucune raison de dédupliquer. Ce n'est pas du polymorphisme PHP (où l'enfant masquerait le parent) : c'est une fusion de listes.

🌍 In Real Life

La situation : un dossier d'auteur spécialisé suit le règlement commun et une annexe supplémentaire. Ajouter « nom d'au moins cinq caractères » ne retire pas l'obligation commune de renseigner le nom.

L’équivalent dans Symfony : les métadonnées héritées fusionnent avec celles de la classe enfant. Le NotBlank du parent reste présent lorsque l'enfant ajoute Length ; redéclarer la même contrainte peut ajouter un second contrôle.

Retour à la réalité technique : cette fusion n'est pas le remplacement d'une méthode PHP. Les groupes peuvent sélectionner des contraintes différentes lors d'une validation, mais ne suppriment pas les métadonnées héritées. Deux déclarations évaluées et violées peuvent produire deux messages.

🧠 Comment le mémoriser : « L'annexe s'ajoute au règlement. » Image mentale : deux listes agrafées, aucune ligne barrée. Question-réflexe : suis-je en train d'ajouter une règle ou de croire que je remplace celle du parent ?

⚠️ À ne pas confondre : sélection de groupes et suppression de l'héritage des contraintes.

Contraindre une class qu'on ne peut pas modifier

À retenir en priorité
  1. La class d'origine peut rester inchangée.
  2. Le mapping externe doit être effectivement enregistré.

Où en est-on ? Étape 4 sur 4 : et si la class vient d'une bibliothèque ? On ne peut pas y écrire d'attributes. Symfony offre un moyen d'ajouter des règles de l'extérieur.

Supposons que l'inscription réutilise un objet fourni par une bibliothèque. Modifier son fichier fournisseur rendrait les mises à jour fragiles ; une classe d'extension de validation permet d'ajouter les règles du blog sans toucher à cet objet. Le lien doit toutefois être connu du système de mapping : une annotation isolée n'est pas une découverte universelle.

#[ExtendsValidationFor(Product::class)], sur une class séparée, ajoute ses constraints à celles de Product. Hors framework, le lien se déclare aussi : addAttributeMappings([Product::class => [MyProductValidation::class]]) — l'attribute seul n'a aucun effet.

// la class tierce reste intacte
#[ExtendsValidationFor(Product::class)]
final class MyProductValidation
{
    #[Assert\NotBlank]
    public string $name;
}

// hors framework : relier cible et extension
$validator = Validation::createValidatorBuilder()
    ->enableAttributeMapping()
    ->addAttributeMappings([Product::class => [MyProductValidation::class]])
    ->getValidator();

Pourquoi l'attribute seul ne suffit-il pas ? Le Validator ne scanne pas le disque à la recherche de classes marquées : il faut lui dire « pour valider Product, regarde aussi MyProductValidation ». Le framework le fait via la configuration ; hors framework, c'est addAttributeMappings().

🌍 In Real Life

La situation : un organisme fournit un dossier standard que le bureau ne peut pas réimprimer. Le bureau lui associe une feuille de critères locaux dans son registre, sans modifier l'original.

L’équivalent dans Symfony : une classe portant ExtendsValidationFor déclare des contraintes complémentaires pour une classe tierce. Le mapping relie explicitement la cible et sa classe d'extension afin que le Validator trouve ces règles.

Retour à la réalité technique : l'extension de validation n'est pas une sous-classe nécessaire du modèle et ne change pas ses données. Hors framework, la liaison via addAttributeMappings() doit être configurée ; la seule présence de l'attribut dans un fichier ne garantit pas sa découverte.

🧠 Comment le mémoriser : « Ajouter la fiche de contrôle, pas retoucher le fournisseur. » Image mentale : fiche locale reliée à un dossier intact. Question-réflexe : quel mapping rattache mes contraintes à la classe tierce ?

⚠️ À ne pas confondre : extension des métadonnées et héritage PHP ou modification du code fournisseur.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Cascade s'appuie sur les types des properties.
  2. Un object contenu ne suffit pas sans type adapté.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Récapitulatif des pièges, avec la raison de leur plausibilité.

  • Voir l’explication : sélectionnées et évaluées

    Une liste vide de violations est une conclusion sur les règles sélectionnées et évaluées, pas un certificat sur tout le graphe d'objets. Pour l'adresse de l'auteur, vérifie successivement le mapping chargé, la cascade, la présence de l'objet et les groupes demandés.

  • Voir l’explication : Sans Valid ni Cascade, l'object imbriqué est ignoré

    Sans Valid ni Cascade, l'object imbriqué est ignoré — une validation qui passe à tort. Pourquoi on se trompe : on suppose qu'un validateur « complet » suit les références.

  • Voir l’explication : Valid n'impose pas la présence de l'object

    Valid n'impose pas la présence de l'object : null passe. Pourquoi on se trompe : « valider l'adresse » semble inclure « l'adresse existe ».

  • Voir l’explication : Redéclarer une constraint dans la fille ne remplace pas celle du parent

    Redéclarer une constraint dans la fille ne remplace pas celle du parent : les deux s'appliquent, et le comportement ne se désactive pas. Pourquoi on se trompe : on transpose la redéfinition de méthode PHP.

  • Voir l’explication : loadValidatorMetadata() est statique

    loadValidatorMetadata() est statique ; non statique, elle lève une MappingException. Pourquoi on se trompe : les autres hooks d'objets sont des méthodes d'instance.

  • Voir l’explication : Cascade ne regarde pas seulement la valeur d'une propriété

    Cascade ne regarde pas seulement la valeur d'une propriété : une propriété sans type contenant un objet n'est pas sélectionnée ; une propriété typée array contenant des objets peut l'être. Pourquoi on se trompe : on croit que Symfony inspecte le contenu à l'exécution.

  • Voir l’explication : Valid sans groupes explicites ne se limite pas à Default

    Valid sans groupes explicites ne se limite pas à Default : il transmet le groupe demandé. Avec Valid(groups: ['Registration']), la cascade est elle-même sélectionnée par ces groupes. Pourquoi on se trompe : le nom « Default » est associé à tout ce qui n'a pas de groupe.

Fiche express

À mémoriser

À retenir en priorité
  1. Valid transmet le group demandé.
  2. Les constraints imbriquées doivent appartenir à ce group.

Si tu dois retenir seulement 7 choses :

  • Quatre formats : attributes, YAML, XML, PHP statique.
  • La validation ne descend pas : #[Valid] ou #[Cascade].
  • Valid : null passe ; il transmet le group demandé.
  • Cascade : types déclarés éligibles, dont array, exclude, pas de groups.
  • Parent et enfant fusionnent ; une constraint redéclarée compte deux fois.
  • loadValidatorMetadata() non statique : MappingException.
  • #[ExtendsValidationFor] pour une class qu'on ne peut pas modifier.

Moyen mnémotechnique : « Déclarer, Descendre, Hériter » — et rien ne descend sans qu'on le dise.

🧠 À retenir pour la certification

  1. Les règles viennent des métadonnées (attributes, YAML, XML, méthode PHP statique) ; hors framework, chaque loader s'active explicitement.
  2. « Aucune violation » = aucune règle chargée et évaluée n'a échoué, rien de plus.
  3. La cascade est opt-in : Valid (par property, null passe) ou Cascade (par class, d'après le type déclaré, exclude, pas de groups).
  4. NotNull exige l'objet ; Valid parcourt son contenu : deux rôles.
  5. L'héritage additionne les constraints ; redéclarer = doublon.
  6. ExtendsValidationFor + addAttributeMappings() pour une class non modifiable.

Phrase de mémorisation : « Je charge les règles, j'ouvre explicitement chaque objet imbriqué, et rien ne se remplace en héritage : tout s'ajoute. »

Revoir : Le schéma
