Objectif

Pour GET /blog/42, la Request porte déjà id = '42' et _controller = App\Controller\BlogController::show. Le callable est connu ; il reste à fournir son identifiant, la Request et son service ArticleCatalog. Ces trois valeurs n'ont pas la même origine.

Comprendre le mécanisme qui remplit les arguments d'un controller : qui décide, dans quel ordre, et comment s'y insérer. C'est ce mécanisme qui explique pourquoi typer Request, SessionInterface ou une enum suffit.

Question fil rouge : quand j'écris show(Request $request, int $id, ArticleCatalog $catalog), qui fabrique chacune de ces trois valeurs, et dans quel ordre ? La réponse tient en une phrase : une chaîne de petits spécialistes interrogés un par un pour chaque argument.

L'essentiel

À comprendre

À retenir en priorité
  1. La priority détermine l'ordre d'essai.
  2. Un default resolver doit laisser les resolvers spécialisés agir d'abord.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce mécanisme existe. Le routeur a trouvé le callable (The request : _controller et id sont des attributs de la Request), mais PHP ne sait pas appeler show() sans arguments. Sans mécanisme, chaque action devrait lire la Request à la main. Le noyau délègue ce travail de « remplissage de cases » à ArgumentResolver.
  • Le piège de fond. On croit que la signature est « magique ». Elle ne l'est pas : chaque type reconnu correspond à un resolver précis, enregistré avec une priorité précise.
  • Ce que l'auteur veut que vous compreniez. Qui décide (ArgumentResolver), dans quel ordre (priorités des services tagués), comment un resolver décline (iterable vide) ou répond (une valeur), et comment s'y insérer (resolver maison, #[ValueResolver], resolvers ciblés).
  • Pourquoi c'est à l'examen. Le nombre de resolvers de la chaîne épinglée, les exceptions (InvalidArgumentException, RuntimeException, LogicException) et les codes 404/422/400/415 sont des questions classiques.

En résumé : HttpKernel appelle ArgumentResolver, qui interroge les value resolvers. Pour chaque argument, le premier resolver de la chaîne configurée qui produit une valeur termine la recherche ; si aucun n'en fournit, la résolution échoue. Les resolvers ne s'appellent pas entre eux. Les mappings ciblés décrits plus bas choisissent explicitement une source ; leurs statuts 404/422 ne sont pas une règle universelle applicable à toute URL ou tout body invalide.

Ce cours prolonge The base AbstractController class (le contrôleur reçoit ses arguments) et prépare HttpKernel component and FrameworkBundle (où se situe ce mécanisme dans la séquence du noyau).

Le schéma

À retenir en priorité
  1. Le premier résultat arrête la recherche.
  2. Plusieurs valeurs exigent un argument variadique.

Où en est-on ? Le cours avance du plus général au plus précis : le schéma (la chaîne en une image), l'exemple (un resolver maison), le contrat (ce que resolve() rend), ce que fait ArgumentResolver (la boucle), l'ordre (les priorités), le catalogue (les resolvers fournis), les resolvers ciblés (ceux qui n'agissent que sur demande). Le premier schéma ci-dessous répond à : « comment une case est-elle remplie ? ».

Pour CHAQUE argument de la signature
   resolver 1 ── iterable vide ──► resolver 2 ── iterable vide ──► … ──► resolver N
        │                              │                                    │
   une valeur                      une valeur                       toujours vide
        ▼                              ▼                                    ▼
   argument rempli               argument rempli               RuntimeException
   (on passe au suivant)         (on passe au suivant)

Où en est-on ? Le second schéma répond à une autre question : « comment changer la chaîne pour un argument ? » avec #[ValueResolver].

Bleu = appels orchestrés par ArgumentResolver, ambre = décision/configuration. Les resolvers ne s'appellent pas entre eux. yield null fournit une valeur ; un return sans yield exécuté n'en fournit aucune.

Lecture : sans #[ValueResolver], la chaîne contient tous les resolvers tagués, triés par priorité. Avec lui, elle se réduit à trois éléments : l'épinglé, puis RequestAttributeValueResolver, puis DefaultValueResolver.

L'exemple : un resolver maison

Exemple concret

À retenir en priorité
  1. Un generator convient au contrat iterable.
  2. Un iterable vide signifie que ce resolver passe la main.

Où en est-on ? Avant la théorie, un cas concret : écrire le plus petit resolver utile. Il montre déjà les deux comportements clés : répondre (un yield) et décliner (un return sans valeur).

Le blog veut transmettre une valeur métier Locale, plutôt qu'obliger chaque action à lire la Request. Le resolver ci-dessous ne répond qu'à ce type : pour $id ou ArticleCatalog, il ne produit rien et laisse ArgumentResolver poursuivre. Locale est ici un objet applicatif supposé défini avec un constructeur acceptant la locale ; ce n'est pas une API Symfony.

final class CurrentLocaleResolver implements ValueResolverInterface
{
    public function resolve(Request $request, ArgumentMetadata $argument): iterable
    {
        if (Locale::class !== $argument->getType()) {
            return;   // rien produit : le resolver suivant essaie
        }

        yield new Locale($request->getLocale());
    }
}

Pourquoi return; et pas return null; ? Parce que la méthode est un generator (elle contient yield) : un return exécuté avant tout yield produit un iterable vide, donc « pas moi ». Un yield null, lui, produit une valeur : null. C'est la confusion la plus fréquente.

return;                  → []        → 0 valeur  → le suivant essaie
yield null;              → [null]    → 1 valeur  → l'argument vaut null
yield [];                → [[]]      → 1 valeur  → l'argument vaut un tableau vide

🌍 In Real Life

La situation : au restaurant, un poste prépare la fiche de langue du service. Si on lui demande un numéro de commande ou un catalogue, il ne propose rien.

L’équivalent dans Symfony : spécialité du poste → vérification de ArgumentMetadata::getType() ; langue du bon → Request::getLocale() ; fiche produite → objet applicatif Locale fourni par yield.

Retour à la réalité technique : ce resolver doit être enregistré pour être interrogé. Son générateur ne produit aucune valeur pour les autres types ; ArgumentResolver peut alors essayer un autre candidat. Locale désigne ici la classe du projet, pas une classe fournie automatiquement par Symfony.

🧠 Comment le mémoriser : « Une spécialité précise, un refus sans valeur. » Image mentale : poste langue laissant passer les demandes de catalogue. Question-réflexe : « Mon resolver reconnaît-il exactement cet argument avant de produire quelque chose ? »

⚠️ À ne pas confondre : un générateur vide décline ; yield null fournit déjà une valeur.

Le contrat

Où en est-on ? Étape 1 : que reçoit et que rend un resolver ? On définit le vocabulaire (ValueResolverInterface, ArgumentMetadata, iterable) après avoir vu le mécanisme dans l'exemple.

Quand il examine $id, ArgumentResolver possède deux entrées distinctes : la Request avec ses attributs et les métadonnées de la signature de show(). Un resolver compare ces informations, puis produit une ou plusieurs valeurs dans un iterable. Pour un identifiant ordinaire, produire ['42'] signifie « un argument trouvé » ; produire [] signifie « chercher ailleurs », pas « appeler le contrôleur avec un tableau vide ».

Chaque resolver implémente ValueResolverInterface et sa method unique resolve(Request $request, ArgumentMetadata $argument): iterable. ArgumentMetadata porte ce que la signature déclare : nom, type, variadicité, default value, attributes. La documentation dit « toujours un array » — vide, à un élément, à plusieurs pour un variadique ; le type est iterable, et un generator fonctionne. Retourner la valeur elle-même est l'erreur classique.

resolve(Request, ArgumentMetadata) : iterable
   entrées                                  sortie
   ├─ Request : attributs (id = '42')       ├─ []          → décline
   └─ ArgumentMetadata :                    ├─ ['42']      → une valeur
        nom, type, variadique,              └─ ['a','b']   → plusieurs :
        default value, attributes                              variadique seulement

Vérifié dans ArgumentResolver::getArguments() (8.0) : la boucle parcourt $resolver->resolve($request, $metadata) avec un foreach ; une seconde valeur pour un argument non variadique déclenche \InvalidArgumentException (« must yield at most one value for non-variadic arguments ») ; si la chaîne est épuisée, une \RuntimeException indique que le controller requiert un argument « that could not be resolved ».

🌍 In Real Life

La situation : pour remplir une case du bon, le coordinateur reçoit une liste de propositions. Une liste vide signifie « aucune proposition », pas « proposer une liste vide ».

L’équivalent dans Symfony : description de la case → ArgumentMetadata ; bon disponible → Request ; propositions → iterable retourné par resolve().

Retour à la réalité technique : [] contient zéro valeur ; [null] en contient une ; [[]] fournit une valeur qui est elle-même un tableau vide. Le contrat porte sur un iterable, donc tableau et générateur conviennent. Plusieurs valeurs ne conviennent qu’à un argument variadique.

🧠 Comment le mémoriser : « Compter les propositions, pas leur contenu. » Image mentale : panier vide, panier avec une étiquette null, panier contenant un petit panier vide. Question-réflexe : « Combien de valeurs cet iterable produit-il réellement ? »

⚠️ À ne pas confondre : l’enveloppe iterable n’est pas nécessairement la valeur de l’argument.

Ce que fait `ArgumentResolver`

Où en est-on ? Étape 2 : la boucle. On a vu un resolver isolé ; voyons qui les appelle, et jusqu'où va « arrêter la recherche ».

Supposons show(Request $request, int $id, ArticleCatalog $catalog). La résolution de $request ne doit pas arrêter celle de $id et de $catalog : l'arrêt concerne seulement la chaîne de candidats pour l'argument courant. Une fois la liste complète obtenue, HttpKernel diffuse kernel.controller_arguments, récupère ses éventuelles modifications du callable et des valeurs, puis appelle l'action.

Le premier resolver qui produit une valeur arrête la chaîne de resolvers ; deux valeurs pour un argument non variadique lèvent une InvalidArgumentException. Un array vide passe la main sans erreur : seul l'échec de toute la chaîne de resolvers lève.

show(Request $request, int $id, ArticleCatalog $catalog)
   │
   ├─ $request  → chaîne de candidats → RequestValueResolver répond   ┐
   ├─ $id       → chaîne de candidats → RequestAttributeValueResolver ├─ 3 boucles
   └─ $catalog  → chaîne de candidats → ServiceValueResolver répond   ┘ indépendantes
   │
   ▼ liste complète [Request, 42, ArticleCatalog]
   kernel.controller_arguments (peut modifier callable et valeurs)
   ▼
   appel de show(...)

Trois niveaux d'arrêt à ne pas confondre :

Niveau Ce qui s'arrête
Candidat un resolver qui décline cède la main au suivant
Argument le premier resolver qui produit une valeur termine la chaîne de cet argument
Appel seule une exception (aucun resolver, valeurs multiples…) empêche l'appel

Rappel de rôle : ControllerResolver choisit le callable, ArgumentResolver prépare les valeurs, HttpKernel appelle (voir HttpKernel component and FrameworkBundle).

🌍 In Real Life

La situation : le responsable fait préparer trois renseignements pour un poste : le bon, son numéro et le catalogue. Trouver le bon ne dispense pas de préparer les deux autres.

L’équivalent dans Symfony : liste des besoins → signature du callable ; recherche pour chaque besoin → boucle d’ArgumentResolver ; propositions successives → value resolvers ; dossier complet remis au responsable → liste d’arguments retournée à HttpKernel.

Retour à la réalité technique : un resolver productif termine la recherche pour l’argument courant, pas pour toute l’action. L’iterable reste consommé et des valeurs multiples non variadiques échouent. Un resolver peut aussi lever sa propre exception. Ensuite kernel.controller_arguments peut encore modifier callable et valeurs avant l’appel.

🧠 Comment le mémoriser : « Une case remplie, puis la suivante. » Image mentale : trois cases cochées séparément. Question-réflexe : « L’arrêt concerne-t-il ce candidat, cet argument ou l’appel entier ? »

⚠️ À ne pas confondre : ControllerResolver choisit le callable ; ArgumentResolver prépare les valeurs ; HttpKernel appelle.

Une file de traducteurs spécialisés examine le type demandé. Produire zéro valeur signifie « je passe la main », pas « je fournis null » : yield null est déjà une valeur et arrête la recherche.

L'ordre

Où en est-on ? Étape 3 : qui passe en premier ? Quand deux resolvers pourraient répondre, l'ordre décide. Cet ordre ne vient pas du code PHP du resolver mais de la priorité de son tag de service.

La valeur id de /blog/42 pourrait intéresser un resolver personnalisé et le resolver d'attributs. Leur ordre détermine lequel fournit l'argument. Les priorités appartiennent au câblage des services, pas au type PHP de la valeur ; vérifie donc le correctif utilisé avant de comparer des nombres.

Les services tagués controller.argument_value_resolver sont triés par priority, fixée par FrameworkBundle. En v8.0.0, attributs, enum et date sont à 100, Request/Session à 50, services à -50, défaut à -100 et variadique à -150. Des versions correctives 8.0 ont remonté Request/Session à 120 : ne pas mélanger deux câblages. SessionValueResolver passe avant le défaut : la session s'il y en a une, puis un défaut nullable si prévu. Un resolver maison qui lit les attributes se place à 100 ou plus. La documentation écrit SessionInterface $session = null ; PHP 8.4 déprécie ce nullable implicite : écrire ?SessionInterface $session = null.

priorité décroissante : on essaie d'abord les valeurs les plus hautes

  120 (branche 8.0 actuelle)   Request, Session     ← 50 en v8.0.0
  100                          attributs de route, enum, date (et uid)
   ..  votre resolver maison : 100 ou plus s'il lit les attributes
  -50                          services (locator de l'action)
 -100                          valeur par défaut (DefaultValueResolver)
 -150                          variadique

Vérifié dans web.php (branche 8.0) : le commentaire du code indique que Request et Session passent avant le resolver d'entités de DoctrineBundle (priorité 110), d'où la valeur 120 ; la table ci-dessus conserve les nombres de la source (v8.0.0) et signale cette évolution. Tous les resolvers controller.argument_value_resolver portent aussi un name (leur FQCN), ce qui rend possible l'épinglage par #[ValueResolver].

Pourquoi le défaut est-il presque en dernier ? Parce qu'il ne doit servir que si personne n'a rien trouvé : ?SessionInterface $session = null reçoit d'abord la session réelle (50 ou 120 contre -100), et null seulement sans session.

🌍 In Real Life

La situation : deux postes savent renseigner le numéro du bon. Le responsable consulte d’abord celui placé en tête de la liste de service.

L’équivalent dans Symfony : ordre de consultation → priorités des services tagués controller.argument_value_resolver ; premier poste productif → resolver dont les valeurs sont retenues pour cet argument.

Retour à la réalité technique : les priorités appartiennent à la configuration, pas à une propriété de la valeur 42. Un resolver consulté tôt peut décliner en produisant un iterable vide. Les nombres documentés ici distinguent v8.0.0 de correctifs ultérieurs ; une égalité de priorité ne garantit pas à elle seule que votre service passe avant un autre.

🧠 Comment le mémoriser : « Prioritaire pour essayer, pas obligé de fournir. » Image mentale : liste ordonnée avec une case « sans proposition ». Question-réflexe : « Quel ordre réel mon câblage et ma version donnent-ils aux candidats ? »

⚠️ À ne pas confondre : priorité d’essai et validation de la valeur sont indépendantes.

Le catalogue

À retenir en priorité
  1. Le nom relie route attribute et argument.
  2. RequestValueResolver utilise le type Request.

Où en est-on ? Étape 4 : qui sont les spécialistes fournis ? On passe de l'ordre à l'inventaire, en repartant du scénario show().

Dans le scénario principal, RequestValueResolver fournit la Request, RequestAttributeValueResolver trouve id et ServiceValueResolver consulte le locator préparé pour l'action afin d'obtenir ArticleCatalog. Ce dernier lit des ArticleView en mémoire : 42 existe, 999 manque. La présence d'un type d'objet dans une signature ne signifie pas que Routing charge une entité.

Une intégration Doctrine configurée peut résoudre une entité avant l’action ; ce comportement appartient au bridge, pas à HttpKernel seul, et l’ORM reste hors du programme étudié.

Cette variante exige le mapping approprié et se situe pendant la résolution, contrairement à la lecture explicite du catalogue dans l'action. Ce sont deux variantes, pas deux lectures obligatoires.

Resolver Ce qu'il remplit
RequestAttributeValueResolver un argument qui porte le nom d'un attribute — les parameters de route
RequestValueResolver un argument typé Request ou une sous-classe
SessionValueResolver un argument typé SessionInterface
BackedEnumValueResolver un cas d'enum adossée
DateTimeValueResolver un \DateTimeInterface — un DateTimeImmutable si le type est l'interface
ServiceValueResolver un service du locator propre à l'action
DefaultValueResolver la default value, ou null pour un type nullable
VariadicValueResolver un argument variadique depuis un attribute array

Une valeur invalide venue de l'URL donne 404 pour une enum ou une date. Un Request mal importé reçoit « Looks like you required a Request object with the wrong class name ».

Comment lire ce tableau : l'argument se reconnaît à son nom ($id ↔ attribut id) ou à son type (Request, SessionInterface, une enum…). Aucun resolver ne « devine » : chacun a une condition de prise en charge. (Le framework en fournit d'autres, comme celui des Uid, hors du périmètre de ce tableau.)

Ce que je vois dans la signature         Qui répond
$id          (nom = attribut de route)   RequestAttributeValueResolver
Request $r                               RequestValueResolver
SessionInterface $s                      SessionValueResolver
Status $status  (enum adossée)           BackedEnumValueResolver  → 404 si invalide
\DateTimeInterface $d                    DateTimeValueResolver    → 404 si invalide
ArticleCatalog $c  (service de l'action) ServiceValueResolver
int $page = 1                            DefaultValueResolver
string ...$tags                          VariadicValueResolver

🌍 In Real Life

La situation : le poste reçoit le bon, une référence extraite du bon et un outil pour consulter le catalogue. Recevoir l’outil ne signifie pas avoir déjà trouvé l’article.

L’équivalent dans Symfony : bon → RequestValueResolver ; référence → RequestAttributeValueResolver ; outil disponible → ServiceValueResolver et locator de l’action ; consultation → appel explicite à ArticleCatalog.

Retour à la réalité technique : chaque resolver a une condition de prise en charge ; le tableau n’annonce pas leur exécution à chaque requête. La variante qui fournit directement une entité exige une intégration et un mapping configurés et intervient avant l’action. Elle ne s’ajoute pas obligatoirement à la lecture explicite.

🧠 Comment le mémoriser : « Recevoir le catalogue n’est pas lire la fiche. » Image mentale : catalogue fermé à côté du bon 42. Question-réflexe : « Reçoit-on un service de lecture ou un objet métier déjà obtenu ? »

⚠️ À ne pas confondre : type d’objet dans la signature ne signifie pas chargement ORM automatique par Routing.

Les resolvers ciblés

À retenir en priorité
  1. Distinguer décodage, format et validation.
  2. Un targeted resolver ne s'exécute que lorsqu'il est sélectionné.

Où en est-on ? Étape 5 : ceux qui n'agissent que sur demande. Jusqu'ici tous les resolvers étaient dans la chaîne par défaut. Les resolvers ciblés sont hors chaîne : un attribut PHP sur l'argument les convoque.

L'affichage simple de l'article n'a pas besoin de transformer un body. Pour POST /inscription, en revanche, #[MapRequestPayload] peut désigner le mapping vers SignupData, avec les intégrations nécessaires de sérialisation et validation. Une entrée illisible échoue avant l'évaluation des contraintes ; une entrée décodée mais invalide échoue à une autre étape. C'est pourquoi le tableau ne suffit pas sans les distinctions 400/415 qui le suivent.

RequestPayloadValueResolver et QueryParameterValueResolver portent le tag controller.targeted_value_resolver : hors de la chaîne de resolvers, ils ne s'exécutent que si un attribute les désigne.

#[ValueResolver] épingle un resolver par son nom — le FQCN pour ceux du framework. La chaîne de resolvers compte alors trois éléments : l'épinglé, RequestAttributeValueResolver, DefaultValueResolver ; la documentation ne cite que le dernier. Deux épinglés sur un argument lèvent une LogicException ; disabled: true en saute un.

Attribute Source Échec par défaut
#[MapQueryParameter] un parameter de la query string 404
#[MapQueryString] la query string, vers un object 404
#[MapRequestPayload] le body, vers un object 422
#[MapUploadedFile] un file téléversé 422

Un body illisible — JSON malformé — donne 400, un format sans decoder 415 ; validationFailedStatusCode change le 422, pas ceux-là. #[MapQueryParameter] accepte filter, flags et options : avec FILTER_NULL_ON_FAILURE, une valeur invalide devient null au lieu de lever.

Le raisonnement en trois étapes pour un payload — chacune a son propre échec :

POST /inscription  (body)
   ├─ 1. lire / décoder le body   ── illisible (JSON cassé) ──► 400
   │                              ── format sans decoder ─────► 415
   ├─ 2. mapper vers SignupData   (serializer)
   └─ 3. valider les contraintes  ── échec ───────────────────► 422 (par défaut)

validationFailedStatusCode ne touche que l'étape 3. Pour l'épinglage : #[ValueResolver] à deux endroits sur le même argument est une erreur de configuration (LogicException, « You can only pin one resolver per argument »), alors qu'disabled: true retire simplement un resolver de la chaîne. Un nom introuvable lève ResolverNotFoundException. Voir aussi File upload pour #[MapUploadedFile].

🌍 In Real Life

La situation : pour l’inscription au blog, un dossier porte une consigne explicite : utiliser les champs reçus pour préparer la fiche d’inscription, puis contrôler ses règles.

L’équivalent dans Symfony : consigne sur le dossier → attribut PHP ciblant un resolver ; fiche construite → mapping vers SignupData ; contrôle → intégration Validator configurée. L’absence de consigne n’active pas ce traitement sur chaque GET.

Retour à la réalité technique : #[ValueResolver] sélectionne une chaîne ciblée avec les replis décrits ci-dessus. Pour le payload, convertir et valider sont deux opérations : JSON malformé → 400, format non pris en charge → 415, échec de validation → 422 par défaut. Ces codes ne résument pas toutes les erreurs possibles.

🧠 Comment le mémoriser : « Une consigne choisit la source ; une règle contrôle les données. » Image mentale : fiche marquée « payload », puis tampon de contrôle séparé. Question-réflexe : « L’échec vient-il du format, du mapping ou des contraintes ? »

⚠️ À ne pas confondre : désérialisation, validation et autorisation restent distinctes.

Pièges d'examen

Piège à éviter

Voir l’explication : arrête
  • La documentation dit « toujours un array » ; le type est iterable. Pourquoi on se trompe : la doc simplifie, et un tableau est l'exemple usuel.
  • Un array vide passe la main ; si aucun resolver ne fournit de valeur, une RuntimeException est levée. Pourquoi on se trompe : un resolver vide ressemble à une erreur, alors que c'est un simple « pas moi ».
  • Le premier resolver qui fournit une valeur arrête la chaîne de resolvers. Pourquoi on se trompe : on croit que l'arrêt vaut pour toute l'action.
  • Les conversions enum/date de l'URL décrites ici échouent en 404 ; ce n'est pas le statut universel de toute entrée invalide. Pourquoi on se trompe : on généralise un cas à tous.
  • #[MapQueryParameter] échoue en 404, #[MapRequestPayload] en 422. Pourquoi on se trompe : les deux « mappent une entrée », donc on suppose le même code.
  • Un JSON malformé donne 400, pas 422 : il n'y a rien à valider. Pourquoi on se trompe : 422 semble être « le code des mauvaises données ».
  • Un resolver ciblé ne s'exécute pas sans son attribute. Pourquoi on se trompe : on le croit dans la chaîne par défaut.
  • SessionInterface $session = null est déprécié en PHP 8.4. Pourquoi on se trompe : la doc historique écrit encore cette forme.
