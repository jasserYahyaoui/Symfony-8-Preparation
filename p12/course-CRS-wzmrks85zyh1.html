Objectif

Savoir sur quoi une constraint peut être posée, et ce que chaque scope permet que les autres ne permettent pas.

Question fil rouge : quelle valeur le validateur va-t-il recevoir selon l'endroit où je pose la constraint ?

L'essentiel

À comprendre

À retenir en priorité
  1. Une règle croisée vise la class.
  2. Une property ne fournit que sa valeur.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une règle ne porte pas toujours sur une valeur stockée : parfois elle porte sur un résultat calculé, parfois sur l'objet entier. Le scope (la cible) décide de ce que le validateur reçoit.
  • Le piège de fond. On choisit la cible d'après « combien de propriétés la règle utilise ». Mauvais critère : ce qui compte est la valeur reçue. Un getter qui lit deux propriétés ne transmet qu'un booléen.
  • Ce que l'auteur veut que vous compreniez. Une constraint se pose à trois endroits : une property (la valeur stockée), un accessor (une valeur calculée par une method get, is ou has) ou la class (l'objet entier transmis au validateur).
  • Pourquoi c'est à l'examen. Les QCM testent le path d'une violation d'accessor, les noms de méthodes acceptés, la property non initialisée (validée comme null) et la cible par défaut d'une constraint maison.

La différence est la valeur reçue par la contrainte, pas le nombre de propriétés utilisées pour la calculer : un getter peut comparer deux propriétés et retourner un booléen que IsTrue vérifiera.

Le schéma

À retenir en priorité
  1. Distinguer valeur stockée et calculée.
  2. La class donne accès à l'ensemble de l'object.

Où en est-on ? Vue d'ensemble : les métadonnées déterminent la cible ; chaque cible fournit une valeur différente au même validateur. Les sections suivantes détaillent les trois cibles, puis chacune à son tour.

Ambre = sélection de cible, bleu = valeur fournie, vert = vérification. Ce flux de données suppose un mapping valide et un getter appelable sans argument obligatoire. Les erreurs de mapping et d'exécution ne deviennent pas automatiquement des violations métier.

Le validateur de Length, IsTrue ou Callback est le même quelle que soit la cible : seule change la chose qu'on lui tend.

L'exemple : un `Author`

Exemple concret

À retenir en priorité
  1. La règle doit voir les deux noms.
  2. atPath() choisit le field de correction.

Où en est-on ? Un exemple qui contient déjà deux scopes (property et accessor). La class viendra plus loin avec un Contract.

La branche d'inscription peut comparer prénom et mot de passe avant toute création de compte. Author illustre une règle de cohérence limitée : le getter calcule un booléen et IsTrue juge ce booléen. Cela ne constitue ni une politique complète de robustesse ni une recommandation de conserver le mot de passe en clair dans le modèle durable.

use Symfony\Component\Validator\Constraints as Assert;

class Author
{
    #[Assert\Length(min: 3)]                  // stocké : property
    private string $firstName = 'Ada';

    private string $password = 'Ada';

    #[Assert\IsTrue(message: 'Le mot de passe ne peut pas reprendre le prénom.')]
    private function isPasswordSafe(): bool   // calculé : accessor
    {
        return $this->firstName !== $this->password;
    }
}

Ici, Length accepte Ada, mais isPasswordSafe() retourne false : IsTrue produit une violation au chemin passwordSafe. La règle croise bien deux propriétés, sans être une contrainte de classe.

 firstName (property)   'Ada'  ──► Length(min 3)  reçoit 'Ada'     → OK
 isPasswordSafe() (accessor)    ──► IsTrue        reçoit false     → violation
        └─ lit firstName ET password, mais ne transmet qu'UN booléen
                                                    chemin : passwordSafe

Les trois cibles

À retenir en priorité
  1. Le scope property inclut les accessors.
  2. Le scope class reste distinct.

Où en est-on ? Étape 1 sur 4 : la grille de décision. Avant de détailler chaque cible, on apprend la question à se poser : « qu'est-ce que le validateur doit recevoir ? ».

Décide quelle valeur le validateur doit recevoir. Une propriété transmet son contenu, un getter transmet son résultat, une contrainte de classe reçoit l'objet. Le nombre de propriétés consultées ne suffit pas à choisir : le getter de l'exemple lit deux propriétés mais ne transmet qu'un booléen.

Cible Ce qu'elle valide Quand la choisir
property la valeur stockée le cas courant
accessor la valeur retournée par une method la règle est calculée
class l'object entier la règle croise plusieurs properties

Pourquoi la dernière ligne n'est-elle qu'une indication ? Parce qu'une règle croisée simple se règle souvent avec un accessor booléen (l'exemple Author). On passe à la class quand le validateur a besoin de l'objet entier, par exemple pour placer plusieurs erreurs sur des chemins distincts.

🌍 In Real Life

La situation : l'agent peut recevoir une case recopiée, le résultat d'un calcul ou le dossier complet. Un calcul fondé sur deux cases reste un résultat unique si c'est seulement ce résultat qu'on lui remet.

L’équivalent dans Symfony : la cible détermine l'entrée du validateur : valeur de propriété, retour d'accessor ou objet entier pour une contrainte de classe. IsTrue sur isPasswordSafe() reçoit ici un booléen, même si le getter compare deux propriétés.

Retour à la réalité technique : « règle croisée » ne signifie pas automatiquement CLASS_CONSTRAINT. Choisis selon la valeur requise et la localisation des violations. Une contrainte doit autoriser la cible choisie ; les métadonnées doivent être chargées. Aucun de ces choix ne crée le compte ni ne hache un mot de passe.

🧠 Comment le mémoriser : « Case, résultat ou dossier : regarder ce qui entre. » Image mentale : trois plateaux portant une valeur, un résultat et un dossier. Question-réflexe : qu'est-ce que le validateur doit réellement recevoir ?

⚠️ À ne pas confondre : cible de contrainte, nombre de propriétés consultées, validation et traitement métier.

La property

À retenir en priorité
  1. Une property non initialisée est lue comme null.
  2. La constraint détermine alors le résultat.

Où en est-on ? Étape 2 sur 4 : le scope le plus courant. Deux questions : la visibilité compte-t-elle, et que devient une property jamais affectée ?

Une propriété privée de SignupData n'est pas invisible au Validator configuré pour son mapping. Inversement, sa déclaration PHP string ne rend pas sa présence validée : si elle reste non initialisée, la validation la considère comme nulle. Ne généralise pas ce traitement aux lectures ordinaires du getter, de Twig ou de ton code PHP.

La visibilité n'a aucune importance : le validator lit la property par réflexion, private comprise. Une property typée non initialisée est validée comme null : NotBlank la refuse, Length la laisse passer.

Pourquoi null plutôt qu'une erreur PHP ? En PHP, lire une property typée non initialisée lève une Error. Le Validator vérifie d'abord si elle est initialisée (isInitialized) ; si non, il fournit null au lieu de lire. Ensuite, chaque constraint réagit à null selon sa propre règle :

 property typée jamais affectée  ──►  valeur transmise : null
        NotBlank  → violation        (null n'est pas un contenu)
        Length    → aucune violation (Length ignore null)
        Email     → aucune violation (Email ignore null)

D'où la règle de prudence : si la présence est obligatoire, ajoute NotBlank ou NotNull ; Length seul ne l'impose pas.

🌍 In Real Life

La situation : l'agent habilité à examiner les rubriques internes peut lire une case non exposée au public. Si la case n'a jamais reçu de valeur, son protocole note une absence ; cela ne remplit pas la case.

L’équivalent dans Symfony : les métadonnées de propriété permettent au Validator de lire par réflexion une propriété privée. Une propriété typée non initialisée est présentée comme null au contrôle décrit.

Retour à la réalité technique : ce traitement n'initialise pas la propriété et ne rend pas sa lecture PHP ordinaire sûre. Un getter qui la lit peut encore échouer. Length acceptant null ne remplace pas NotBlank ou NotNull lorsque la présence est requise. La réflexion du Validator ne donne pas les mêmes droits d'accès à Twig, au mapper Form ou au code appelant.

🧠 Comment le mémoriser : « Absence constatée n'est pas case remplie. » Image mentale : case interne vide avec constat null posé à côté. Question-réflexe : la propriété est-elle initialisée, et quelle règle juge son absence ?

⚠️ À ne pas confondre : visibilité PHP, lecture de métadonnée, propriété non initialisée, null et affectation.

L'accessor

À retenir en priorité
  1. Le préfixe is disparaît du path.
  2. Le path représente la valeur calculée.

Où en est-on ? Étape 3 sur 4 : la valeur calculée. Elle suppose des conditions précises : un nom reconnu, aucun argument obligatoire.

Validator n'utilise pas l'ArgumentResolver du contrôleur pour appeler un getter : il ne lui injecte ni Request ni date courante. Le nom doit respecter le mapping et la méthode doit être appelable sans argument obligatoire. Le chemin produit est celui de la propriété calculée, qui peut nécessiter un mapping vers un champ visible du formulaire.

Method annotée Résultat
private function isPasswordSafe() violation au path passwordSafe
public function getFullName() violation au path fullName
private function checkPasswordSafety() MappingException : « Constraints can only be added on methods beginning with "get", "is" or "has". »
public function isOk(int $x) ArgumentCountError à la validation
  • Le path est le nom sans le préfixe, première lettre en minuscule ; le préfixe ignore la casse, et une method statique est acceptée.
  • En YAML, ces constraints vont sous getters:, avec le nom sans préfixe.
  • Un mauvais nom échoue à la lecture des metadata ; un argument requis n'est pas vérifié au chargement : c'est l'appel qui casse.

Pourquoi deux erreurs différentes ? Le nom est contrôlé quand le loader lit les attributs (regex sur get|is|has, sans tenir compte de la casse) : c'est un problème de mapping, d'où MappingException. Les arguments, eux, ne sont jamais inspectés au chargement : c'est PHP qui refuse l'appel sans argument, au moment de valider, d'où ArgumentCountError.

 chargement des metadata :  nom ∈ get… / is… / has… ?
                                non → MappingException        (tôt)
 validation :               appel de la method sans argument
                                argument requis → ArgumentCountError  (tard)

🌍 In Real Life

La situation : l'agent actionne un calcul prédéfini et juge son résultat. La commande doit porter un nom reconnu et fonctionner sans qu'il fournisse une information supplémentaire.

L’équivalent dans Symfony : le mapping getter reconnaît les méthodes get…, is…, has… du cas décrit, puis Validator les appelle sans argument fourni. La violation vise le nom calculé sans préfixe, comme passwordSafe.

Retour à la réalité technique : un mauvais nom peut échouer au chargement du mapping ; un argument obligatoire échoue lors de l'appel. Aucun ArgumentResolver ne fournit Request ou service à ce getter. Cette lecture par réflexion, y compris privée, ne s'étend pas aux appels ordinaires. Garde le calcul sans effet de bord ; le chemin calculé peut nécessiter un error_mapping Form pour rejoindre un champ visible.

🧠 Comment le mémoriser : « Commande reconnue, résultat calculé, aucun argument livré. » Image mentale : bouton de calcul reconnu relié à son résultat nommé. Question-réflexe : le getter est-il mappé, appelable sans apport et relié au bon chemin d'erreur ?

⚠️ À ne pas confondre : getter validé, callback, action de contrôleur et champ HTML.

La class

À retenir en priorité
  1. Sans atPath(), la violation conserve le path courant de l'objet : vide à la racine, préfixé lorsqu'il est imbriqué.
  2. atPath() permet de viser une property.

Où en est-on ? Étape 4 sur 4 : la cible qui reçoit l'objet entier. Elle sert quand la règle a besoin de tout l'objet et doit choisir où poser l'erreur.

Pour une période de publication du blog, la règle peut recevoir début et fin dans le même objet et placer l'erreur sur la fin. Le callback ci-dessous illustre ce choix : le chemin est relatif au contexte courant, donc un objet imbriqué conserve son préfixe. Cette localisation sert à présenter l'erreur, pas à modifier la date incorrecte.

Callback s'applique à l'object lui-même. Une constraint maison y accède en rendant Constraint::CLASS_CONSTRAINT depuis getTargets() ; par défaut, elle rend Constraint::PROPERTY_CONSTRAINT, qui couvre properties et accessors.

Cette portée convient à une règle croisée qui doit recevoir directement l'objet et choisir le chemin de son erreur :

#[Assert\Callback('check')]
// Même alias Assert que plus haut ; contexte reçu par le callback.
class Contract
{
    public function __construct(
        public \DateTimeImmutable $start,
        public \DateTimeImmutable $end,
    ) {
    }

    public function check(\Symfony\Component\Validator\Context\ExecutionContextInterface $context): void
    {
        if ($this->end < $this->start) {
            $context->buildViolation('La fin précède le début.')
                ->atPath('end')
                ->addViolation();
        }
    }
}

Sans atPath(), la violation conserve le path courant de l'object : vide seulement à la racine de validation, par exemple child pour un objet imbriqué validé à cet emplacement. atPath('firstName') ajoute un chemin relatif : firstName à la racine, child.firstName dans ce contexte imbriqué.

Pourquoi une cible par défaut PROPERTY_CONSTRAINT ? La grande majorité des constraints jugent une valeur isolée ; Symfony part donc du cas courant. Pour viser la class, une constraint maison doit le déclarer dans getTargets() ; sinon, la poser sur une class lève une ConstraintDefinitionException. Le code de Constraint définit les deux constantes CLASS_CONSTRAINT ('class') et PROPERTY_CONSTRAINT ('property').

 getTargets() de la constraint     peut se poser sur
 ───────────────────────────────   ──────────────────────────────────────
 PROPERTY_CONSTRAINT (défaut)      property, accessor (get/is/has)
 CLASS_CONSTRAINT                  la class (l'objet entier)
 [les deux]                        les deux familles

🌍 In Real Life

La situation : l'agent reçoit tout le calendrier pour comparer début et fin. Il pose ensuite une remarque sur la case fin ; déplacer la remarque ne corrige pas la date.

L’équivalent dans Symfony : une contrainte de classe permet au validateur d'examiner l'objet entier. Le callback construit une violation, ajoute un chemin relatif avec atPath('end'), puis l'enregistre avec addViolation().

Retour à la réalité technique : PROPERTY_CONSTRAINT couvre propriétés et getters ; une contrainte personnalisée de classe doit déclarer sa cible et, lorsqu'elle s'emploie comme attribut PHP, les cibles PHP compatibles. atPath() conserve le préfixe du contexte imbriqué, ne lit ni ne modifie la propriété et n'ajoute pas seul la violation. Un getter booléen reste une alternative pour une règle croisée simple.

🧠 Comment le mémoriser : « Lire tout le calendrier, poser la remarque au bon endroit. » Image mentale : calendrier complet avec remarque sur la fin d'une période. Question-réflexe : quelle cible reçoit l'objet et quel chemin relatif localise réellement la violation ?

⚠️ À ne pas confondre : cible Validator, cible d'attribut PHP, chemin de violation, chemin de mapping et correction de donnée.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La visibilité n'empêche pas la lecture.
  2. Un argument requis casse l'appel du getter.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Récapitulatif des pièges, avec la raison de leur plausibilité.

  • Voir l’explication : Un accessor doit s'appeler get…, is… ou has…

    Un accessor doit s'appeler get…, is… ou has… ; sinon, une MappingException, pas un oubli silencieux. Pourquoi on se trompe : on croit qu'une méthode « non reconnue » est simplement ignorée.

  • Voir l’explication : La visibilité ne bloque rien

    La visibilité ne bloque rien, ni sur une property ni sur un accessor. Pourquoi on se trompe : en PHP ordinaire, private interdit l'accès ; ici, la réflexion le contourne.

  • Voir l’explication : Le path d'une violation d'accessor perd le préfixe

    Le path d'une violation d'accessor perd le préfixe : isPasswordSafe donne passwordSafe. Pourquoi on se trompe : on s'attend au nom de la méthode, comme dans un stack trace.

  • Voir l’explication : Une règle croisée n'impose pas toujours la portée classe.

    Une règle croisée n'impose pas toujours la portée classe. Un getter calculé avec IsTrue peut suffire. Choisir une contrainte de classe lorsque son validateur doit recevoir l'objet entier, par exemple pour produire plusieurs erreurs sur des chemins distincts. Pourquoi on se trompe : « plusieurs propriétés » évoque « class » par réflexe.

  • Voir l’explication : Une property typée jamais affectée est validée comme null

    Une property typée jamais affectée est validée comme null : NotBlank la refuse, mais Length ou Email la laissent passer. Pourquoi on se trompe : on attend une Error PHP ou une violation « trop court ».

Fiche express

À mémoriser

À retenir en priorité
  1. Les getters suivent les préfixes reconnus.
  2. Un mauvais nom n'est pas ignoré silencieusement.

Si tu dois retenir seulement 6 choses :

  • Trois cibles : property (stocké), accessor (calculé), class (croisé).
  • La visibilité ne compte jamais.
  • Accessor : get / is / has, sans argument ; path sans préfixe.
  • Mauvais nom : MappingException ; argument requis : ArgumentCountError.
  • Property typée non initialisée : validée comme null.
  • Règle entre deux fields : Callback de class + atPath().

Moyen mnémotechnique : « Stocké, Calculé, Croisé » — property, accessor, class.

🧠 À retenir pour la certification

  1. Le scope décide de la valeur reçue : stockée (property), retournée (accessor), objet entier (class).
  2. La visibilité PHP n'empêche rien : lecture par réflexion.
  3. Accessor : get/is/has (casse ignorée), sans argument obligatoire ; path = nom sans préfixe, première lettre en minuscule.
  4. Mauvais nom → MappingException (chargement) ; argument requis → ArgumentCountError (validation).
  5. Property typée non initialisée → null : NotBlank refuse, Length passe.
  6. Cible par défaut d'une constraint : PROPERTY_CONSTRAINT ; pour la class, getTargets() doit rendre CLASS_CONSTRAINT.

Phrase de mémorisation : « Stocké, calculé, croisé : on choisit la cible d'après ce que le validateur reçoit, pas d'après le nombre de champs lus. »
