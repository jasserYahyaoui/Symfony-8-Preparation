Objectif

L'inscription au blog peut déclencher plusieurs notifications. Si le service central nomme chaque canal dans son constructeur, ajouter un canal impose de le modifier. Nous allons déclarer une famille de services, la collecter, puis décider dans le code quand et dans quel ordre les appeler. Le même mécanisme pourra réunir les exporteurs de l'import CLI.

Question directrice : comment ajouter un canal de notification sans toucher au service qui les appelle tous ?

L'essentiel

À comprendre

À retenir en priorité
  1. Un tag est un marqueur.
  2. Son lecteur lui donne un effet.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Sans tag, HandlerChain liste ses canaux : chaque nouveau canal modifie une classe existante. Le tag inverse la dépendance : c'est le canal qui s'annonce.
  • Le piège de fond. Un tag est un simple libellé sur une définition. Il ne fait rien seul : il faut un lecteur du même nom exact, puis un code qui appelle les méthodes. Marquer, collecter, appeler : trois actions.
  • Ce que l'auteur veut que vous compreniez. AutowireIterator donne une collection ordonnée et différée ; AutowireLocator donne un accès par clé ; priority ordonne, index nomme.
  • Pourquoi c'est à l'examen. Questions sur index_by, les méthodes getDefault…Name/Priority, exclude, AsTaggedItem, AutoconfigureTag et registerForAutoconfiguration().

Un tag est une métadonnée nommée sur une définition de service. Un lecteur de ce tag, par exemple un iterator tagué ou une passe de compilation, rassemble les références correspondantes. Le nom exact relie donc deux côtés du contrat : celui qui marque et celui qui collecte.

AutowireIterator fournit une collection à parcourir ; AutowireLocator fournit une sélection par clé. Dans l'iterator tagué, les références sont ordonnées par priorité et leur récupération est différée. Ni le tag ni l'injection n'appellent automatiquement notify().

Plan du cours :

Tags

   ├─ 2. Recevoir           → iterator (tous, dans l'ordre) / locator (par clé)

   └─ 4. Marquer sans YAML  → AutoconfigureTag sur l'interface

Le schéma

À retenir en priorité
  1. L'injection fournit un iterable lazy.
  2. L'itération déclenche la construction nécessaire.

Où en est-on ? Avant le détail : une vue d'ensemble en deux temps. La compilation prépare la collection ; l'exécution la parcourt.

La compilation prépare Email avant SMS ; le code d'exécution choisit ensuite de parcourir cette collection. Les deux temps restent distincts :

Orange et pointillés : configuration ; bleu : parcours ; vert : effets des méthodes appelées. Une exception du premier handler peut arrêter la boucle avant SMS. Le tri est celui de ce lecteur de tags, pas une propriété universelle d'un champ nommé priority. Un service partagé peut déjà avoir été créé ailleurs : la récupération différée ne garantit pas son absence en mémoire.

Le fil rouge : des handlers de notification

À retenir en priorité
  1. Le tag regroupe les handlers.
  2. Le consommateur dépend du groupe plutôt que de chaque class.

Où en est-on ? On pose le code de base, utilisé dans toutes les sections. À repérer : où est le tag, où est le lecteur, où est l'appel à notify().

Un handler est ici un objet chargé de traiter une notification. Le contrat local exige notify(string): void. Les imports et la boucle rendent visible la différence entre recevoir les objets et les appeler :

namespace App\Handler;

use Symfony\Component\DependencyInjection\Attribute\AutoconfigureTag;
use Symfony\Component\DependencyInjection\Attribute\AutowireIterator;

#[AutoconfigureTag('app.handler')]
interface HandlerInterface { public function notify(string $message): void; }

class HandlerChain
{
    public function __construct(
        #[AutowireIterator('app.handler')] private iterable $handlers,
    ) {
    }

    public function send(string $message): void
    {
        foreach ($this->handlers as $handler) {
            $handler->notify($message);
        }
    }
}

Les classes doivent être enregistrées, HandlerChain autowiré, et les implémentations taguées explicitement ou autoconfigurées. Avec EmailHandler puis SmsHandler dans la collection, send('Inscription reçue') passe cette même string à chacun dans cet ordre. Pour tester sans réseau, chaque handler peut enregistrer le message dans un array ; le mécanisme de collection ne fournit aucun transport d'email ou de SMS.

 Marquer              Collecter                    Appeler
┌────────────┐       ┌─────────────────────┐      ┌─────────────────────┐
│ tag        │  ───▶ │ AutowireIterator    │ ───▶ │ foreach + notify()  │
│ app.handler│       │ ('app.handler')     │      │ écrit par VOUS      │
└────────────┘       └─────────────────────┘      └─────────────────────┘
 sur la définition    lecteur du même nom exact    code métier

Ce qu'un tag fait : un marqueur, sans effet propre

À retenir en priorité
  1. Un tag inconnu peut rester inutilisé.
  2. Contrôler le nom et son lecteur.

Où en est-on ? Étape 1 sur 4. Question : qu'est-ce qu'un tag change réellement dans le container ? Presque rien : il ajoute une étiquette. Tout l'effet vient de celui qui la lit.

Voici la variante explicite pour des classes autoloadables App\Handler\SmsHandler et EmailHandler implémentant notre contrat. On ne cumule pas ici ce marquage avec celui de l'interface :

services:
    _defaults:
        autowire: true
        autoconfigure: false
    App\Handler\HandlerChain: ~
    App\Handler\SmsHandler:
        tags: ['app.handler']
    App\Handler\EmailHandler:
        tags:
            - { name: 'app.handler', priority: 10 }

Lorsque HandlerChain est utilisé, son iterator collecte ces deux services : Email, priorité 10, précède SMS, dont la priorité vaut par défaut 0. Le tag n'impose pas leur interface PHP ; nos implémentations doivent réellement fournir notify().

Sans lecteur, un tag inconnu n'est pas en lui-même une erreur bloquante. En debug, UnusedTagsPass peut signaler un tag inutilisé dans le journal de compilation et proposer un nom proche. Ce n'est pas une garantie qu'une faute de frappe sera corrigée, ni que tout lecteur de tag acceptera n'importe quels attributs.

Le même assemblage sert à l'export, sans lier les deux workflows :

services:
    App\CsvExporter:
        tags: ['app.exporter']
    App\ExportRegistry:
        arguments:
            $exporters: !tagged_iterator app.exporter

Ce fragment suppose CsvExporter autoloadable sans argument requis et ExportRegistry avec __construct(iterable $exporters). La collection donne accès à l'exporteur ; aucune donnée n'est exportée par le seul chargement du YAML. Écrire app.exproter sur le service le laisserait hors de la collection app.exporter.

🌍 In Real Life

La situation : des dossiers portent une mention commune ; quelqu'un doit rechercher exactement cette mention pour réunir les dossiers, puis demander le travail.

L’équivalent dans Symfony : mention → tag de définition ; recherche → lecteur du tag ; demande de travail → appel métier du consommateur.

Retour à la réalité technique : app.exporter et app.exproter ne correspondent pas. Sans lecteur, le tag ne fait rien ; un diagnostic de debug ne corrige pas la faute. Le tag n'impose pas non plus le contrat PHP des objets collectés.

🧠 Comment le mémoriser : « Marquer, collecter, appeler : trois actions. » Image mentale : dossiers marqués encore immobiles. Question-réflexe : qui lit ce nom exact et qui appelle la méthode ?

⚠️ À ne pas confondre : métadonnée et transport effectif d'email ou de SMS.

Recevoir les services tagués : un iterable lazy

À retenir en priorité
  1. Le locator sélectionne un service.
  2. L'iterator parcourt le groupe.

Où en est-on ? Étape 2 sur 4. Le tag est posé. Question : sous quelle forme le consommateur reçoit-il les services ? Selon son besoin : tous, dans l'ordre, ou un seul, choisi par clé.

Notre chaîne veut parcourir tous les canaux. Une autre politique pourrait n'en sélectionner qu'un, par exemple sms choisi par le lecteur. Choisissons la forme d'accès avant de construire les objets :

Besoin Injection
appeler tous les services tagués, dans l'ordre #[AutowireIterator] / !tagged_iterator
en appeler un, choisi par sa key #[AutowireLocator] / !tagged_locator

L'iterator fourni est réitérable : un nouveau parcours peut récupérer les services à nouveau. La résolution des éléments est différée, mais un élément partagé peut déjà exister à cause d'un autre accès. Rejouer send() rejoue les méthodes métier ; « réitérable » n'est ni « idempotent » ni « nouveau handler à chaque passage ».

Si la boucle s'arrête après Email, elle n'a pas besoin de récupérer SMS par cette voie. Pour accéder directement à une clé, un locator évite de parcourir les éléments précédents. exclude: [FaxHandler::class] écarte ce service de cet iterator lorsque son identifiant est son FQCN ; il reste disponible pour d'autres consommateurs.

 ITERATOR                          LOCATOR
 ┌─────┐ ┌─────┐ ┌─────┐          ┌──────────────────────────┐
 │Email│→│ SMS │→│ Fax │          │ get('sms') ─▶ SmsHandler │
 └─────┘ └─────┘ └─────┘          └──────────────────────────┘
 parcours dans l'ordre            accès direct par clé
 (lazy : créé à la demande)       (lazy : créé au get())

🌍 In Real Life

La situation : une tournée passe successivement aux postes ; un annuaire permet au contraire d'atteindre directement un poste choisi.

L’équivalent dans Symfony : tournée → iterator tagué ; annuaire → locator ; passage au poste → récupération du service, puis appel explicite.

Retour à la réalité technique : les éléments sont récupérés au fil du parcours ; arrêter tôt peut éviter les suivants par cette voie. Un service partagé peut déjà exister. Refaire la tournée peut rappeler le même objet et répéter ses effets ; exclure un service d'un iterator ne le supprime pas partout.

🧠 Comment le mémoriser : « Parcourir tous ou choisir une clé ? » Image mentale : itinéraire face à un annuaire. Question-réflexe : mon besoin exige-t-il une boucle ou un accès direct ?

⚠️ À ne pas confondre : réitérable, nouvel objet et opération idempotente.

Ordonner et nommer : `priority` et `index`

À retenir en priorité
  1. L'index déclaré n'active pas seul l'indexation.
  2. La configuration de l'iterator décide des keys.

Où en est-on ? Étape 3 sur 4. On sait collecter. Question : comment fixer l'ordre, et comment donner un nom utilisable (sms) à un service ? Deux notions distinctes : la priorité classe, l'index identifie.

Nous voulons maintenant nommer le canal SMS, sans confondre position et identité. #[AsTaggedItem(index: 'sms', priority: 10)] fournit des métadonnées depuis la class lorsque l'autoconfiguration est active et les attributes non ignorés. Il ne pose pas à lui seul app.handler. Le lecteur doit encore demander une indexation pour utiliser ce nom :

Injection Keys obtenues
#[AutowireIterator('app.handler')] 0, 1, 2… : l'index est ignoré
#[AutowireIterator('app.handler', indexAttribute: 'key')] sms pour ce service ; à défaut d'index fourni, l'identifiant du service
#[AutowireLocator('app.handler')] sms pour ce service ; à défaut d'index fourni, l'identifiant du service

La première forme conserve une liste numérique malgré l'index annoncé. La deuxième demande une clé et peut donc utiliser sms. Le locator a besoin de clés pour ses recherches. Ces lignes supposent qu'aucun attribut de tag ou méthode statique ne fournit un autre index ; en dernier recours, l'identifiant du service sert de clé, souvent son FQCN avec la découverte habituelle.

La priorité explicite du tag est prioritaire sur les valeurs par défaut. Sans elle, le lecteur peut utiliser une méthode publique statique getDefaultPriority(). Avec index_by: key, les noms déduits deviennent getDefaultKeyName() pour la clé et getDefaultKeyPriority() pour la priorité. Déclarer seulement getDefaultPriority() ne satisfait plus ce dernier choix implicite de méthode.

default_index_method peut nommer une autre méthode de clé ; default_priority_method peut fixer celle de priorité. L'indexation est alors un contrat entre configuration et méthodes réelles, pas une convention de nom universelle. Choisissons des clés distinctes : une map ne conserve pas plusieurs services indépendants sous la même clé. Pour une même priorité, l'ordre d'ajout est conservé, mais il vaut mieux exprimer une priorité distincte si l'ordre métier est important.

Dérivation du nom des méthodes par défaut (vérifiée dans TaggedIteratorArgument) : getDefault + attribut d'index en CamelCase + Name ou Priority.

 indexAttribute: 'key'   →  getDefaultKeyName()      (la clé)
                            getDefaultKeyPriority()  (la priorité)
 sans indexAttribute     →  getDefaultPriority()     (priorité seule)

🌍 In Real Life

La situation : les postes ont un nom et un rang de visite ; un parcours numéroté peut suivre le rang sans utiliser leurs noms comme clés.

L’équivalent dans Symfony : nom → index ; rang → priorité ; usage du nom → indexation demandée par le lecteur.

Retour à la réalité technique : AsTaggedItem ne pose pas le tag à lui seul. L'iterator simple peut garder des clés numériques ; l'indexation et ses méthodes de défaut doivent correspondre à la configuration. index_by: key change aussi le nom attendu pour la méthode de priorité par défaut. Des clés identiques ne préservent pas plusieurs entrées indépendantes dans une map.

🧠 Comment le mémoriser : « Le rang ordonne, la clé identifie. » Image mentale : un nom et un numéro distincts sur chaque poste. Question-réflexe : quelle règle produit la clé et quelle règle produit l'ordre ?

⚠️ À ne pas confondre : priorité de ce lecteur de tags et règle universelle applicable à toute métadonnée priority.

Poser les tags sans configuration

À retenir en priorité
  1. L'interface peut porter le tag commun.
  2. L'autoconfiguration doit être active.

Où en est-on ? Étape 4 sur 4. Poser le tag à la main sur chaque service devient vite répétitif. Question : comment marquer toute une famille d'un coup ? En déclarant la règle sur l'interface commune.

Après validation du marquage explicite, nous pouvons déplacer la règle sur HandlerInterface avec #[AutoconfigureTag('app.handler')], comme dans le premier extrait. Les implémentations enregistrées et autoconfigurées reçoivent alors le tag sans répéter la ligne YAML. L'attribute est répétable, mais il ne découvre pas une class hors des ressources chargées et ne crée pas le lecteur du tag.

Le mécanisme se transpose à une famille de formatters :

use Symfony\Component\DependencyInjection\Attribute\AutoconfigureTag;

#[AutoconfigureTag('app.formatter')]
interface FormatterInterface
{
    public function format(string $value): string;
}

Une implémentation enregistrée avec autoconfigure: true peut ainsi rejoindre une collection qui demande app.formatter. L'interface impose format() ; le tag organise les références ; le consommateur appelle la méthode. Aucun de ces trois rôles ne remplace les deux autres.

FrameworkBundle procède aussi par des règles enregistrées avec registerForAutoconfiguration(), notamment pour EventSubscriberInterface. Il n'est pas nécessaire que cette interface du framework porte elle-même notre attribute applicatif.

Qui pose la règle d'autoconfiguration ? Où
Votre code applicatif #[AutoconfigureTag] sur votre interface
Le framework (ex. EventSubscriberInterface) registerForAutoconfiguration() dans l'extension

🌍 In Real Life

La situation : les postes reconnus comme formateurs reçoivent automatiquement une marque de famille ; ils doivent encore être inventoriés, et quelqu'un doit exploiter cette marque.

L’équivalent dans Symfony : capacité déclarée → interface ; règle de marquage → AutoconfigureTag ou règle enregistrée ; inventaire → services enregistrés et autoconfigurés ; exploitation → lecteur du tag.

Retour à la réalité technique : l'interface impose format(), le tag organise les références, le consommateur appelle. FrameworkBundle peut enregistrer une règle pour EventSubscriberInterface sans que cette interface porte l'attribute applicatif. Aucune règle ne découvre implicitement toutes les classes.

🧠 Comment le mémoriser : « La capacité, la marque, le travail restent distincts. » Image mentale : poste marqué mais pas encore sollicité. Question-réflexe : l'enregistrement, l'autoconfiguration et le lecteur sont-ils présents ?

⚠️ À ne pas confondre : « sans YAML répété » et « sans configuration ni intégration ».

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le tri des services tagués est décroissant.
  2. Cet ordre diffère de l'empilement des decorators.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Pour chaque piège : l'énoncé, puis pourquoi la mauvaise réponse paraît plausible.

  • Voir l’explication : Marquer n'est ni collecter ni appeler.

    Marquer n'est ni collecter ni appeler. Un tag sans lecteur ne lance aucune notification. Vérifions successivement la définition, le nom exact, le lecteur et la boucle métier. Plausible car « tagger un service » sonne comme « l'activer ».

  • Voir l’explication : La priorité ordonne cette collection, pas tous les tags.

    La priorité ordonne cette collection, pas tous les tags. Avec notre iterator, Email 10 précède SMS 0 si la boucle poursuit son parcours ; une exception ou un arrêt peut empêcher le second appel. Plausible car le mot priority existe ailleurs dans Symfony avec d'autres règles.

  • Voir l’explication : Lazy concerne cette voie de récupération.

    Lazy concerne cette voie de récupération. Un handler partagé peut déjà être construit ailleurs. Parcourir de nouveau la collection peut rappeler le même objet, sans rendre sa notification idempotente. Plausible car « lazy » fait croire que rien n'existe avant le parcours.

  • Voir l’explication : Un index annoncé doit être demandé par le lecteur.

    Un index annoncé doit être demandé par le lecteur. Sans configuration d'indexation, l'iterator conserve des clés entières. Une méthode d'index explicite ou un locator change le cas ; la seule absence de index_by ne permet pas de conclure. Plausible car AsTaggedItem(index: 'sms') semble suffire à nommer la clé.

  • Voir l’explication : Une collection vide peut être une faute de contrat.

    Une collection vide peut être une faute de contrat. app.handlr et app.handler sont deux noms distincts. Le diagnostic de debug aide, mais l'absence de compilation bloquante ne prouve pas que le canal attendu a rejoint la collection. Plausible car un container qui compile paraît correct.

Fiche express

À mémoriser

À retenir en priorité
  1. Le filtre concerne la collection injectée.
  2. Le service reste disponible ailleurs.

Pour ajouter un canal sans modifier HandlerChain :

  1. Enregistrer une implémentation du contrat notify().
  2. Poser exactement le tag lu, explicitement ou par autoconfiguration.
  3. Choisir parcours de collection ou sélection par clé.
  4. Fixer la priorité utile et vérifier l'ordre de parcours réel.
  5. Demander l'indexation si la clé sms doit être exploitable.
  6. Vérifier les méthodes de défaut correspondant à l'attribut d'index.
  7. Tester l'appel métier et son comportement d'erreur : le câblage seul ne prouve aucune notification.

La collecte standard suffit souvent. Si des règles de configuration doivent décider quelles définitions créer, passons à la configuration sémantique du bundle.

🧠 À retenir pour la certification

  • Tag = métadonnée sur une définition ; il ne fait rien sans lecteur au nom exact, ni sans code qui appelle.
  • #[AutowireIterator] / !tagged_iterator : tous, ordonnés par priorité, récupération différée, réitérable (pas idempotent).
  • #[AutowireLocator] / !tagged_locator : accès par clé ; exclude: [...] retire un service de cet iterator seulement.
  • Iterator simple : clés 0, 1, 2… ; clés nommées seulement avec indexAttribute/index_by ou locator ; repli : identifiant du service (souvent FQCN).
  • index_by: key → getDefaultKeyName() et getDefaultKeyPriority() ; priorité du tag > méthode par défaut.
  • AsTaggedItem fournit index/priorité mais ne pose pas le tag ; AutoconfigureTag sur l'interface pose le tag aux classes autoconfigurées.
  • UnusedTagsPass signale un tag jamais utilisé (debug) ; EventSubscriberInterface : registerForAutoconfiguration().

Phrase de mémorisation : « Le tag marque, le lecteur collecte, le code appelle ; la priorité range, l'index nomme. »
