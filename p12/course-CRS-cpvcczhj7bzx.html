Objectif

Brancher un téléversement sur un form sans corrompre l'entité. UploadedFile, move() et le caractère non fiable des métadonnées client sont traités dans le Module 04 — Contrôleurs.

Question centrale : comment un fichier envoyé par le navigateur traverse-t-il un form sans que l'entité, qui ne garde qu'un nom, ne soit corrompue ?

L'essentiel

À comprendre

À retenir en priorité
  1. Séparer le file temporaire et sa référence persistante.
  2. Appliquer les constraints directement au field non mappé.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un upload met en jeu deux objets différents : le fichier reçu (temporaire, volumineux) et le nom durable stocké en base. Les confondre casse le mapping.
  • Le piège de fond. Un field mappé sur la propriété brochure (une string) recevrait un objet fichier : erreur de type ou chemin temporaire écrit en base.
  • Ce que l'auteur veut que vous compreniez. mapped: false, contraintes sur le field, lecture par get('brochure')->getData(), test de null, ordre « déplacer puis nommer ».
  • Pourquoi c'est à l'examen. LogicException sans Mime, string postée → null, multiple → array, form valide sans fichier.

L'entité stocke le nom d'un file ; le form reçoit un file téléversé. Le field FileType est donc déclaré mapped: false, porte ses propres constraints, et le controller lit le file sur le form avant de le déplacer et d'écrire le nom sur l'entité.

Le schéma

Où en est-on ? Début du cours. Voici le trajet du fichier de la Request à l'entité. Question : à quel moment le fichier cesse-t-il d'être un objet pour devenir un simple nom ?

Request (files)  ──►  FileType (mapped: false)  ──►  constraints du field
                            │ PRE_SUBMIT : ne garde que de vrais fichiers
                            ▼
                      form valide ?  ── non ──► réafficher
                            │ oui
                            ▼
              $form->get('brochure')->getData()   (UploadedFile ou null)
                            │ si non null
                            ▼
             déplacer le fichier ─► écrire le NOM sur Product::$brochure

Ambre = filtrage, bleu = données/actions. Reconnaître un UploadedFile ne prouve ni le succès de l'upload ni sa conformité : erreurs PHP et contraintes peuvent encore invalider le form. Le stockage n'est pas transactionnel avec l'entité ; prévoir le traitement d'un échec de déplacement.

L'exemple : la brochure

Exemple concret

À retenir en priorité
  1. FileType fournit un UploadedFile, pas le nom final du file.
  2. La property string reçoit le nom après traitement ; mapped: false évite ce mapping incompatible.

Où en est-on ? On pose le modèle avant le field. Question : pourquoi la propriété brochure ne peut-elle pas contenir le fichier lui-même ?

Un auteur peut joindre un PDF à un article, dans une branche d'édition séparée du GET public. Le modèle Product ci-dessous conserve le problème minimal : sa propriété brochure contient un nom durable, alors que la Request transporte un fichier temporaire. Employer mapped: false sépare ces deux contrats au lieu de demander au mapper de les confondre.

class Product
{
    public string $name = '';
    public string $brochure = '';   // le nom du fichier, pas le fichier
}

Deux objets, deux durées de vie :

Fichier reçu Nom stocké
Nature UploadedFile string
Durée temporaire (jusqu'à la fin de la requête) durable (en base)
Où $form->get('brochure')->getData() $product->brochure

Le field

Où en est-on ? Étape 1 sur 3. Déclarer le champ. Question « Pourquoi ? » : pourquoi mapped: false et des contraintes sur le field et non sur l'entité ?

Le request handler alimentera ce champ depuis les fichiers de la Request. La contrainte File vérifie ensuite ce qui a été reçu ; le libellé « PDF » et l'interface du navigateur n'imposent pas cette règle côté serveur. Un champ facultatif autorise l'absence dans cet exemple, mais conserver l'ancienne référence exige encore la branche explicite du contrôleur.

use Symfony\Component\Form\FormBuilderInterface;
use Symfony\Component\Form\Extension\Core\Type\FileType;
use Symfony\Component\Validator\Constraints as Assert;

function addBrochureField(FormBuilderInterface $builder): void
{
    $builder->add('brochure', FileType::class, [
        'label' => 'Brochure (PDF)',
        'mapped' => false,
        'required' => false,
        'constraints' => [
            new Assert\File(maxSize: '1024k', extensions: ['pdf']),
        ],
    ]);
}
Option Pourquoi
mapped: false le modèle conserve un nom durable, pas l'objet reçu par FileType
required: false saisie non requise dans le HTML ; avec ces contraintes, l'absence est acceptée et le contrôleur peut garder l'existant
constraints un field non mappé ne profite pas des constraints de l'entité
  • Mapper ce field sur une propriété de nom de fichier mélange deux modèles : FileType attend normalement un File, pas le nom stocké. Selon les données initiales et les accessors, cela peut lever une LogicException dès la construction, une erreur de type ou une conversion indésirable en path temporaire. Ce n'est pas une conversion fiable vers le nom final.
  • Un b.txt échoue : « The extension of the file is invalid ("txt"). Allowed extensions are "pdf". ».
  • L'option extensions exige le component Mime : sans lui, FileValidator lève une LogicException.

Vérifié dans FileType 8.0 : compound vaut false ; data_class vaut File (ou null si multiple) ; empty_data vaut null (ou [] si multiple) ; finishView() pose multipart = true, ce qui fait écrire enctype="multipart/form-data" sur la balise <form>.

Comparaison mapped / non mapped :

mapped: true (sur string $brochure) mapped: false
Valeur du field un File à écrire dans une string un File, laissé au controller
Résultat erreur de type / chemin temporaire en base modèle intact
Constraints de l'entité oui non : à mettre sur le field

Pourquoi required: false ? C'est le HTML : l'attribut required n'est pas posé. Avec ces contraintes, l'absence de fichier est acceptée côté serveur, ce qui permet de garder l'ancienne brochure à l'édition.

🌍 In Real Life

La situation : l'accueil reçoit une brochure dans un bac provisoire ; le catalogue du magasin ne conserve que sa référence de rangement. On ne colle pas le colis entier dans la case « référence » du catalogue.

L’équivalent dans Symfony : FileType reçoit le fichier ; mapped: false évite de l'écrire directement dans la propriété string brochure. Les contraintes du champ vérifient taille et extensions avant le traitement durable.

Retour à la réalité technique : non mappé ne signifie pas non validé. Ce choix répond au modèle présenté ; une propriété compatible File peut être mappée. required: false règle le rendu HTML, tandis que les contraintes déterminent l'acceptation serveur de l'absence. extensions utilise Mime et ne se réduit pas à croire le libellé ou le nom fourni par le client ; une contrainte File n'est pas un antivirus.

🧠 Comment le mémoriser : « Le bac reçoit le fichier, le catalogue garde la référence. » Image mentale : brochure dans le bac et ligne de catalogue encore vide. Question-réflexe : mon champ et ma propriété représentent-ils vraiment la même donnée ?

⚠️ À ne pas confondre : fichier reçu, nom durable, mapping, contraintes et indication HTML.

Un CV agrafé à un dossier voyage avec le formulaire mais ne devient pas automatiquement le texte d'une case. mapped: false sépare l'attachment du modèle, sans supprimer les contraintes du field.

Repère — Ce que FileType écarte :

Question: Does posting an ordinary string make it a valid UploadedFile?

Answer: No. FileType filters out non-upload values.

Le handler distingue les files des strings. multiple: true produit un array de files.

Repère de l’exemple :

Question: Why should the upload field not map directly to Product::$brochure when that property stores a filename?

Answer: The field contains an UploadedFile, while the property stores a string; use mapped: false and assign the stored filename explicitly.

FileType fournit un UploadedFile, pas le nom final du file. La property string reçoit le nom après traitement ; mapped: false évite ce mapping incompatible.

Récupérer le file

À retenir en priorité
  1. Tester la présence du file avant déplacement.
  2. Lire la donnée sur le field non mappé.

Où en est-on ? Étape 2 sur 3. Le form est valide ; que fait le controller ? Question : dans quel ordre déplacer le fichier et mettre à jour la référence ?

Après handleRequest(), le formulaire soumis et valide autorise la suite de ce scénario, sous réserve des droits de l'auteur. Lis le champ, traite null comme « pas de nouveau fichier », puis déplace sous un nom serveur avant de mettre à jour la référence. Une validation réussie ne garantit ni l'espace disque ni la réussite de cette écriture.

if ($form->isSubmitted() && $form->isValid()) {
    $file = $form->get('brochure')->getData();
    if ($file !== null) {
        // Déplacer vers un stockage contrôlé ; écrire le nom après succès.
    }
}

Un file envoyé : un UploadedFile, et $product->brochure reste vide. Rien envoyé, avec les options ci-dessus : le field vaut null. Cela ne rend pas automatiquement tout le form valide ; les autres contraintes restent actives. Sans fichier envoyé, dans le cas valide, getData() vaut null — d'où le test.

Ordre des opérations, et pourquoi :

1. form soumis ET valide
2. $file = $form->get('brochure')->getData()
3. $file === null ?  ── oui ──► rien à faire (on garde l'ancienne brochure)
                     └─ non ──► 4. déplacer sous un nom serveur contrôlé
                                5. SI succès : écrire ce nom sur $product->brochure

Pourquoi déplacer avant d'écrire le nom ? Si le déplacement échoue, la base ne doit pas contenir une référence à un fichier inexistant. Et le disque n'est pas transactionnel avec la base : à vous de prévoir nettoyage et erreurs.

🌍 In Real Life

La situation : une brochure contrôlée doit encore être rangée. Le magasinier inscrit sa nouvelle référence après le rangement réussi ; sans nouvelle brochure, il conserve celle qui figure déjà au catalogue.

L’équivalent dans Symfony : après soumission valide et contrôle des droits, le code lit get('brochure')->getData(), traite null, déplace le fichier sous un nom contrôlé puis met à jour la référence du modèle.

Retour à la réalité technique : la validité Form ne garantit pas la réussite disque. mapped: false ne fait ni déplacement ni persistance. Le système de fichiers et le stockage de la référence ne deviennent pas transactionnels ensemble : prévois erreurs et nettoyage. Ne transforme pas le nom client en chemin de destination fiable ; le téléchargement ultérieur conserve ses propres règles d'accès.

🧠 Comment le mémoriser : « Ranger avec succès avant d'inscrire la nouvelle référence. » Image mentale : étagère remplie avant mise à jour du catalogue. Question-réflexe : que conserver ou nettoyer si le fichier manque ou si une étape échoue ?

⚠️ À ne pas confondre : validation, autorisation, déplacement et persistance de la référence.

Ce que `FileType` écarte

À retenir en priorité
  1. Le handler distingue les files des strings.
  2. multiple: true produit un array de files.

Où en est-on ? Étape 3 sur 3. Que se passe-t-il si le client envoie autre chose qu'un fichier ? Question : comment FileType se protège-t-il d'une string comme /etc/passwd ?

Poster un chemin en texte n'accorde pas au client le droit de lire ce chemin sur le serveur. Le listener garde les formes reconnues par le handler ; le résultat null n'est toutefois pas un certificat d'innocuité de tout le formulaire. Exiger une pièce jointe demande une contrainte d'absence adaptée en plus des contrôles du fichier.

  • Un listener PRE_SUBMIT de FileType ne garde que de vrais files téléversés : une string postée à la place devient null, sans erreur.
  • multiple: true : la valeur est un array de files, et data_class vaut null.
  • Le handler compte : HttpFoundationRequestHandler, celui du framework, reconnaît un UploadedFile ; le handler natif attend l'array de $_FILES.

Mécanisme vérifié dans FileType::buildForm() 8.0 :

PRE_SUBMIT sur le champ :
  multiple ?
    oui → ne garde que les éléments où isFileUpload() est vrai (sinon empty_data)
    non → isFileUpload(donnée) ?  oui → garde (+ erreur si l'upload PHP a échoué)
                                   non → setData(null)

Pourquoi null plutôt qu'une erreur ? Le champ devient simplement « vide » : une string n'est jamais prise pour un fichier. C'est l'absence de pièce, à traiter ensuite par les contraintes (par exemple NotNull) si le fichier est obligatoire.

Comparaison :

Donnée envoyée multiple: false multiple: true
un vrai fichier UploadedFile [UploadedFile]
deux fichiers un seul est pertinent [UploadedFile, UploadedFile]
une string null [] (éléments non fichiers écartés)

🌍 In Real Life

La situation : le guichet des colis ne traite pas un papier portant une adresse d'étagère comme un colis livré. Il peut aussi recevoir plusieurs colis ; les reconnaître ne prouve pas qu'ils respectent les règles du magasin.

L’équivalent dans Symfony : le listener PRE_SUBMIT de FileType filtre selon la représentation reconnue par le request handler. Une string à la place du fichier devient null dans le cas simple ; multiple: true attend une collection de fichiers.

Retour à la réalité technique : HttpFoundation reconnaît des UploadedFile, le handler natif une structure de fichier PHP. Reconnaissance structurelle, succès de l'upload et contraintes sont trois vérifications distinctes. Si la présence est obligatoire, ajoute une contrainte adaptée ; rendre la saisie HTML required ne suffit pas. Pour plusieurs fichiers, adapte aussi les contraintes à la collection et à ses éléments.

🧠 Comment le mémoriser : « Une adresse écrite n'est pas un colis reçu. » Image mentale : papier d'adresse écarté du bac des vrais colis. Question-réflexe : quel handler reconnaît quelle forme, puis qui vérifie présence et contenu ?

⚠️ À ne pas confondre : filtrage FileType, validation File, fichier obligatoire et lecture d'un chemin serveur.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Ne pas mapper directement un fichier sur une propriété de nom

    Ne pas mapper directement un fichier sur une propriété de nom : erreur de type ou conversion indésirable possible. Un modèle ayant une véritable propriété File peut, lui, employer un field mappé. Pourquoi on se trompe : c'est le réflexe habituel d'un add('brochure', ...) mappé.

  • Voir l’explication : Un field non mappé n'arrive pas dans l'object

    Un field non mappé n'arrive pas dans l'object, et vaut null quand rien n'a été envoyé. Pourquoi on se trompe : on croit que $product->brochure sera rempli automatiquement.

  • Voir l’explication : Les constraints d'un field non mappé se déclarent sur le field.

    Les constraints d'un field non mappé se déclarent sur le field. Pourquoi on se trompe : on les place sur l'entité, qui n'est pas consultée pour ce champ.

  • Voir l’explication : extensions sans le component Mime

    extensions sans le component Mime : LogicException. Pourquoi on se trompe : on imagine une vérification faite sur le simple nom de fichier.

Application

À retenir en priorité
  1. Tester la présence du file avant déplacement.
  2. Lire la donnée sur le field non mappé.
  3. Séparer le file temporaire et sa référence persistante.
  4. Appliquer les constraints directement au field non mappé.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Nom stocké ≠ fichier reçu : mapped: false sépare ces données.
  • Lire le file sur le form, par son field : get(), puis getData().
  • Rien envoyé : null ; tester avant d'utiliser.
  • Constraints : sur le field, option constraints.
  • extensions sans Mime : LogicException.
  • Une string postée → null ; multiple: true → un array.

Moyen mnémotechnique : « Recevoir, valider, déplacer, nommer ».

Phrase de mémorisation : « L'entité garde un nom, le form reçoit un fichier : je ne mappe pas l'un sur l'autre, je lis le fichier sur le field, je le déplace, puis seulement j'écris son nom. »
