Objectif

L'import du blog prépare ses lots lorsqu'un calcul échoue. Ailleurs, une opération métier peut être refusée sans que PHP lui-même soit en panne. Nous devons distinguer ces échecs, choisir où les traiter et remettre les ressources temporaires en état sans annoncer un faux succès. La hiérarchie Throwable nous aide à sélectionner le bon traitement ; elle ne définit pas encore la Response HTTP ni le résultat d'une commande.

Le fil du cours, en quatre questions :

  1. La hiérarchie : de quelle branche vient l'échec (Error ou Exception) ?
  2. La conséquence pratique : quel catch PHP choisit-il, et que devient un échec non reconnu ?
  3. Écrire ses propres exceptions : comment nommer un échec métier ?
  4. Multi-catch et finally : comment réunir deux types et nettoyer sans mentir ?

L'essentiel

À comprendre

À retenir en priorité
  1. Throwable couvre les deux branches.
  2. Placer les catch spécifiques avant le catch général.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Quand une opération échoue, il faut interrompre le trajet normal sans continuer avec des données fausses, et laisser le code qui a le contexte décider de la suite. throw / catch est ce mécanisme de transmission.
  • Le piège de fond. Depuis PHP 7, les erreurs du moteur sont des objets Error, rattrapables, mais pas des Exception. Dire « exception » en conversation ne dit pas quelle branche choisir.
  • Pourquoi c'est à la certification. Les QCM testent la parenté exacte (ErrorException, ArgumentCountError…), le premier-catch-compatible, la syntaxe PHP 8 (variable de catch facultative, multi-catch) et le comportement de finally.

Un throw interrompt le trajet normal et transmet un object lançable, un Throwable, jusqu'à un catch compatible. Cette interface commune couvre deux branches sœurs : Error, notamment pour des erreurs du moteur PHP, et Exception, notamment pour les conditions applicatives. Le mot « exception » dans une conversation ne suffit donc pas à choisir catch (Exception) : ce dernier laisse passer une Error.

PHP choisit le premier catch compatible, pas automatiquement le plus précis. finally exécute ensuite le nettoyage lors du déroulement normal des blocs, y compris avant de quitter la function sur un return. Ces règles ne promettent pas de récupérer tous les incidents : un warning ordinaire n'est pas automatiquement un Throwable, et un arrêt abrupt du processus peut empêcher le nettoyage.

La hiérarchie à garder en tête :

                    Throwable   (interface)
                   ┌─────┴──────┐
                 Error        Exception          ← deux branches SŒURS
        ┌───────────┼─────────┐      │
   TypeError   ValueError  ArithmeticError   ErrorException, RuntimeException…
        │                        │
 ArgumentCountError      DivisionByZeroError

Le schéma

À retenir en priorité
  1. Error et Exception sont deux branches sœurs.
  2. ErrorException appartient à la branche Exception.

Où en est-on ? Vue d'ensemble avant le code : on suit un objet levé (DivisionByZeroError) à travers une série de catch, puis jusqu'au finally. Les flèches montrent le parcours d'exécution, pas l'héritage.

Isolons le défaut de calcul rencontré par l'import : une division entière avec un diviseur nul. Suivons l'object levé jusqu'au traitement qui accepte son type, puis jusqu'au nettoyage. L'ordre des blocs sera aussi important que leurs noms.

Bleu : exécution ; orange : sélection du handler ; vert : nettoyage. Les flèches sont un parcours d'exécution, pas de l'héritage. On suppose aucun arrêt abrupt ni nouvelle exception dans le handler. Throwable couvre les objets lançables, pas tous les warnings PHP ni tous les arrêts du processus. finally convient au nettoyage, pas à un return qui masquerait l'échec initial. Le schéma ne choisit aucune politique métier : continuer l'import, arrêter le lot ou propager l'échec reste une décision de l'appelant. Le prochain bloc rend seulement visible la sélection des branches.

L'exemple

Exemple concret

Où en est-on ? Le schéma en code minimal : une seule instruction qui échoue, deux catch, un finally. On cherche lequel s'exécute et pourquoi.

Avec les entrées 1 et 0, intdiv() ne peut fournir aucun quotient. Cet exemple autonome montre où le contrôle passe :

try {
    $result = intdiv(1, 0);
} catch (Exception $e) {
    // JAMAIS atteint : DivisionByZeroError est une Error, pas une Exception
} catch (DivisionByZeroError $e) {
    // atteint
} finally {
    // exécuté sur ces chemins, hors exit() ou arrêt abrupt
}

Le deuxième catch est atteint, puis finally ; le premier ne correspond pas au type levé. Le bloc n'affiche rien et l'affectation de $result n'aboutit pas. Les commentaires ne constituent pas une gestion d'import : dans le vrai traitement, il faut décider de la suite ou laisser remonter l'échec, plutôt que conserver des handlers vides qui le feraient disparaître.

Pas à pas :

intdiv(1, 0)  → lève DivisionByZeroError
catch (Exception)           ? DivisionByZeroError instanceof Exception → non
catch (DivisionByZeroError) ? instanceof → oui → exécuté (les autres sont ignorés)
finally                     → exécuté ensuite

La hiérarchie

Où en est-on ? Étape 1 sur 4 : on répond à la question laissée ouverte par l'exemple : pourquoi le premier catch n'a-t-il pas fonctionné ?

Pourquoi le premier catch n'a-t-il pas fonctionné ? Depuis PHP 7, de nombreuses erreurs du moteur sont représentées par des objects Error rattrapables, sans devenir des sous-classes d'Exception. DivisionByZeroError descend d'ArithmeticError, elle-même une Error. ArgumentCountError descend de TypeError, également dans la branche Error. ValueError est une autre sous-class d'Error : un diviseur nul ne relève pas automatiquement d'elle parce que la valeur semble « mauvaise ».

Vérifions la parenté au lieu de nous fier au nom :

try {
    intdiv(1, 0);
} catch (Throwable $failure) {
    var_dump($failure instanceof Throwable);
    var_dump($failure instanceof Error);
    var_dump($failure instanceof Exception);
}
$convertedWarning = new ErrorException('Example warning');
var_dump($convertedWarning instanceof Exception);

La sortie donne bool(true), bool(true), bool(false), puis bool(true). ErrorException, malgré son nom, appartient à la branche Exception. Sa construction est explicite ici : aucun warning n'a été converti automatiquement. Certaines erreurs de compilation peuvent par ailleurs empêcher le programme d'atteindre son try.

(Parentés vérifiées sur PHP : DivisionByZeroError < ArithmeticError < Error, ArgumentCountError < TypeError < Error, ValueError < Error, ErrorException < Exception.)

Dans Symfony 8.0, ExceptionEvent::getThrowable() peut exposer un object de l'une ou l'autre branche quand la gestion d'erreur du kernel s'applique. Le nom de l'événement et l'ErrorHandler ne changent pas la parenté PHP. Nous gardons donc cette hiérarchie, que l'appelant soit une commande d'import ou le traitement d'une page du blog.

Comparaison des deux branches :

Error Exception
Usage typique erreurs du moteur PHP (type, arithmétique, nombre d'arguments…) conditions applicatives, échecs métier
Attrapée par catch (Exception) non oui
Attrapée par catch (Throwable) oui oui
Exemples TypeError, ValueError, DivisionByZeroError RuntimeException, ErrorException

La conséquence pratique

Où en est-on ? Étape 2 sur 4 : on connaît les branches ; la question devient qui rattrape quoi, et dans quel ordre les catch sont essayés.

À la frontière de l'import, nous pouvons vouloir reconnaître précisément une division impossible ; plus haut, l'appelant peut signaler tout échec lançable inattendu. catch (Throwable) couvre les deux branches, mais ne répare pas l'état du traitement. Il doit correspondre à une décision réelle, pas servir de filet silencieux autour de chaque méthode.

Le premier essai ci-dessous choisit le handler précis ; le second laisse l'échec traverser un catch incompatible jusqu'au niveau extérieur :

try {
    intdiv(1, 0);
} catch (DivisionByZeroError) {
    echo "specific\n";
} catch (Throwable) {
    echo "general\n";
}

try {
    try {
        intdiv(1, 0);
    } catch (Exception) {
        echo "exception branch\n";
    }
} catch (Throwable) {
    echo "outer\n";
}

La sortie est specific, puis outer. PHP ne compare pas tous les handlers pour élire le plus spécialisé : placer Throwable en premier dans la même série rendrait les suivants inatteignables. Et un échec non reconnu localement continue sa propagation ; cela permet au code qui possède le contexte nécessaire de choisir la suite.

try interne : catch (Exception)   ✗ ne correspond pas (c'est une Error)
      │ l'échec continue de remonter (propagation)
      ▼
try externe : catch (Throwable)   ✓ → "outer"

🌍 In Real Life

La situation : un incident parcourt des postes de traitement dans leur ordre ; le premier poste compétent le prend, sans concours entre tous les spécialistes.

L’équivalent dans Symfony : catégorie de l'incident → type Throwable ; compétence du poste → type du catch ; premier poste compatible → handler exécuté.

Retour à la réalité technique : Error et Exception sont deux branches sœurs ; catch Exception ne couvre pas Error. Catch Throwable couvre les objets lançables, pas tous les warnings ni les arrêts abrupts. Attraper ne répare pas l'état.

🧠 Comment le mémoriser : « Le premier compatible prend la main. » Image mentale : incident passant devant des postes ordonnés. Question-réflexe : mon catch général masque-t-il le traitement précis ?

⚠️ À ne pas confondre : nom ErrorException et appartenance à la branche Error.

Pensez à deux circuits d'alarme reliés au même panneau Throwable : surveiller uniquement Exception laisse passer Error. Le panneau commun ne rend pas les deux branches interchangeables.

Écrire ses propres exceptions

À retenir en priorité
  1. Une interface de marquage peut étendre Throwable.
  2. La class d'exception doit hériter d'Exception ou d'Error.

Où en est-on ? Étape 3 sur 4 : jusqu'ici on attrapait des types fournis par PHP. Comment créer les nôtres, et pourquoi plutôt que de comparer des messages ?

Un échec métier mérite un type reconnaissable plutôt qu'une comparaison fragile de messages. Conservons l'exemple PaymentDeclined comme variante d'une opération refusée ; ce nom ne suppose pas que notre parcours de lecture de l'article effectue un paiement :

interface DomainFailure extends \Throwable {}
final class PaymentDeclined extends \RuntimeException implements DomainFailure {}

Ces déclarations ne lèvent rien. new PaymentDeclined('Refused') créerait un object qui est à la fois RuntimeException et DomainFailure ; throw serait encore nécessaire pour lancer sa propagation.

Une class ne peut pas implémenter Throwable directement : elle doit hériter d'Exception ou d'Error, éventuellement par une sous-class. Pour une condition métier, la branche Exception est généralement adaptée. Une interface de marquage regroupe des types sans fournir leur comportement : elle peut étendre Throwable. catch (DomainFailure $e) reconnaît alors les exceptions qui la portent sans imposer une même sous-branche de la bibliothèque standard PHP, la SPL.

(Vérifié : class T implements Throwable {} donne l'erreur fatale « Class T cannot implement interface Throwable, extend Exception or Error instead ».)

Pourquoi cette règle ? Throwable exige des méthodes (trace, message, code…) que seules Exception et Error fournissent ; PHP interdit donc de les réimplémenter à la main.

        Throwable (interface)  ◄── interface DomainFailure extends Throwable
         ▲                            ▲
   Exception                          │ implements
     ▲                                │
RuntimeException ◄── PaymentDeclined ─┘

La variante autonome suivante conserve deux échecs de livraison, par exemple pour un module qui transmet les résultats du blog. Ces noms sont locaux, pas des interfaces Symfony :

interface DeliveryFailure extends Throwable {}

final class AddressUnavailable extends Exception implements DeliveryFailure {}
final class ParcelRejected extends Exception implements DeliveryFailure {}

try {
    throw new AddressUnavailable('Destination unavailable');
} catch (DeliveryFailure $failure) {
    echo $failure::class, "\n";
    echo $failure->getMessage(), "\n";
    var_dump($failure instanceof Exception);
}

La sortie est AddressUnavailable, Destination unavailable, puis bool(true). Le handler reconnaît la catégorie sans analyser le texte. Il n'effectue aucune livraison et ne transforme pas le refus en succès. Dans l'application, nomme d'abord la condition, choisis sa base et son éventuel marqueur, puis traite-la là où une suite peut être décidée. Si elle traduit une autre exception, préserver cette cause dans previous garde le diagnostic ; le message ne doit contenir aucun secret.

🌍 In Real Life

La situation : des incidents différents portent une étiquette commune « livraison », sans devoir avoir exactement le même dossier spécialisé.

L’équivalent dans Symfony : étiquette commune → interface de marquage ; dossier lançable → classe héritant d'Exception ou Error ; prise en charge commune → catch sur l'interface.

Retour à la réalité technique : une interface peut étendre Throwable, mais une classe ne l'implémente pas directement sans base autorisée. Construire l'exception ne la lance pas ; throw propage. Préserver previous conserve la cause lors d'une traduction.

🧠 Comment le mémoriser : « La famille nomme, la base rend lançable. » Image mentale : même étiquette sur plusieurs dossiers d'incident. Question-réflexe : quel type exprime la condition sans analyser son message ?

⚠️ À ne pas confondre : exception métier et statut HTTP automatiquement choisi.

Multi-catch et finally

À retenir en priorité
  1. finally s'exécute après return.
  2. exit() interrompt le script sans passer par finally.

Où en est-on ? Étape 4 sur 4 : deux outils de confort, indépendants : réunir plusieurs types dans un même catch, et exécuter un nettoyage quoi qu'il arrive dans le déroulement normal.

Deux types différents peuvent justifier le même traitement à une frontière bien choisie. catch (TypeError | ValueError $e) les réunit dans un multi-catch, sans absorber les autres sous-classes d'Error. Depuis PHP 8.0, la variable peut être omise si le handler n'utilise pas l'object ; ce n'est pas une permission réservée à Throwable.

Indépendamment de cette sélection, le service peut devoir remettre un indicateur temporaire en état avant de rendre son résultat. finally sert à ce nettoyage. Observons le moment où il intervient :

try {
    strlen([]);
} catch (TypeError | ValueError) {
    echo "invalid input\n";
}

function result(): string
{
    try {
        return 'ready';
    } finally {
        echo "cleanup\n";
    }
}

echo result(), "\n";

Le type array donné à strlen() déclenche TypeError, reconnu par le multi-catch. Ensuite result() prépare ready, mais exécute finally avant de rendre cette valeur à l'appelant. La sortie complète est donc invalid input, cleanup, puis ready. Ce script illustre deux mécanismes ; il ne valide pas les données d'un import réel.

Un return dans finally remplacerait le retour précédent et pourrait masquer un échec en propagation : garde le nettoyage distinct de la décision de succès. exit() n'est pas un substitut à return ; il arrête le script sans passer par ce finally. Ce bloc PHP n'est pas non plus un événement de fin de Request ni une garantie contre l'arrêt brutal du processus.

Chronologie de result() :

return 'ready'  → la valeur est préparée
finally         → "cleanup" affiché
retour effectif → l'appelant reçoit 'ready'   →  echo : ready
(un return dans finally remplacerait 'ready', même si le try échouait)

(Vérifié sur PHP : sortie cleanup puis ready ; try { throw … } finally { return "masked"; } rend masked et fait disparaître l'exception ; exit() dans un try n'exécute pas le finally.)

🌍 In Real Life

La situation : avant de rendre un dossier ou de transmettre son incident, on libère le matériel temporaire ; le rangement ne déclare pas le travail réussi.

L’équivalent dans Symfony : libération → finally ; résultat préparé → return du try ; incident encore transmis → Throwable en propagation.

Retour à la réalité technique : finally précède le retour effectif dans ces chemins. Y retourner une autre valeur peut masquer le résultat ou l'échec. Exit et arrêt brutal ne garantissent pas ce nettoyage.

🧠 Comment le mémoriser : « Nettoyer sans réécrire le verdict. » Image mentale : matériel rangé à côté d'un dossier toujours en échec. Question-réflexe : mon nettoyage conserve-t-il le résultat initial ?

⚠️ À ne pas confondre : finally PHP, kernel.finish_request et kernel.terminate.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM les plus fréquentes, chacune avec la raison de sa plausibilité.

  • Voir l’explication : Error n'étend pas Exception.

    Error n'étend pas Exception. Les deux implémentent Throwable, et c'est leur point commun dans la hiérarchie. Pour le quotient impossible, un handler d'exception métier ne correspond donc pas ; vérifie le type réel au lieu d'élargir aveuglément tous les catch. Pourquoi on se trompe : le mot « exception » est employé pour tout incident.

  • Voir l’explication : finally s'exécute même après un return

    finally s'exécute même après un return dans le try — et un return dans le finally écrase celui du try. Pas après un exit(), en revanche : exécuté, le script s'arrête sans passer par le finally. Le résultat ready de l'exemple arrive bien après cleanup, mais ajouter un autre retour dans le nettoyage changerait ce résultat. Une préparation de rapport ne doit pas annoncer « terminé » simplement parce qu'elle a réinitialisé son état temporaire. Pourquoi on se trompe : on croit que return quitte immédiatement la fonction.

  • Voir l’explication : L'ordre des catch compte

    L'ordre des catch compte : le premier block compatible gagne. Placer catch (Throwable) en premier rend les suivants inatteignables. Le traitement précis de DivisionByZeroError doit précéder le traitement général si les deux sont dans la même série. Un handler compatible exécuté n'entraîne pas ensuite l'exécution des autres handlers de cette série. Pourquoi on se trompe : on imagine que PHP choisit le plus spécifique, comme une surcharge.

  • Voir l’explication : ErrorException n'est pas une Error.

    ErrorException n'est pas une Error. Elle étend Exception. Pourquoi on se trompe : son nom contient « Error ».

  • Voir l’explication : La variable du catch est facultative depuis PHP 8.0

    La variable du catch est facultative depuis PHP 8.0, pour tout type (pas seulement Throwable).

Distinguer une entrée refusée d'une panne inattendue

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Retour au fil rouge du blog : que fait-on en pratique d'un échec connu et d'un échec inattendu ?

  • Cibler la bonne famille d’erreurs PHP

    L'import peut prévenir un diviseur nul par validation ; s'il doit traiter l'erreur produite par intdiv(), le type pertinent est DivisionByZeroError, pas Exception. Pour plusieurs refus annoncés par une bibliothèque applicative, une interface de marquage étendant Throwable permet de viser la famille, tout en conservant une base d'exception valide pour chaque class.

  • Ne pas masquer un bug en article absent

    Sur la branche HTTP, l'absence connue de l'article 999 et une panne inattendue du code ne méritent pas le même résultat. Un catch (Throwable) qui transforme tout en « article absent » cacherait les bugs. La politique de traduction vers une Response appartient à la couche qui connaît le contrat HTTP ; PHP fournit ici le mécanisme de propagation et de nettoyage. Le traitement de la Request montre ensuite quand HttpKernel intervient et pourquoi une capture activée ne garantit pas à elle seule une page d'erreur.

article 999 absent  (échec CONNU)     → type précis → réponse « introuvable »
bug inattendu       (échec INCONNU)   → on laisse remonter → page d'erreur / log
                    catch (Throwable) qui répond « absent » = bug caché ✗

Application

À retenir en priorité
  1. Throwable couvre les deux branches.
  2. Placer les catch spécifiques avant le catch général.
  3. Une interface de marquage peut étendre Throwable.
  4. La class d'exception doit hériter d'Exception ou d'Error.

Fiche express

À mémoriser

Avant de traiter un échec de l'import ou de la page, vérifie six repères :

  • Throwable → Error et Exception, deux branches sœurs.
  • catch (Exception) laisse passer les Error ; Throwable couvre les deux branches, pas les simples warnings ni les arrêts abrupts.
  • ErrorException est une Exception.
  • Pas d'implements Throwable sur une class ; une interface peut l'étendre.
  • Premier catch compatible gagne.
  • finally : après return, pas après exit() ; son return gagne.

🧠 À retenir pour la certification : Error et Exception sont sœurs sous Throwable ; le premier catch compatible est exécuté, les autres ignorés ; une classe lançable étend Exception ou Error (jamais implements Throwable seul) ; finally nettoie sans décider du succès.

Moyen mnémotechnique : « Le type sélectionne, l'ordre départage, finally nettoie. » Le nom de la class ne remplace pas sa hiérarchie : ErrorException en est le contre-exemple.

Does finally run after return and after exit?

It runs after return, but not after exit; a return in finally replaces the earlier return.

finally s'exécute après return. exit() interrompt le script sans passer par finally.

Can a class override an interface constant in PHP 8.4?

Yes, unless that constant is final.

Depuis PHP 8.1, une constant d'interface peut être redéfinie. final interdit cette redéfinition.
