Objectif

GET /blog/42 sait déjà afficher un article : Messenger n'est pas nécessaire à cette lecture. En revanche, accueillir un nouvel abonné ou prolonger la command app:blog:import introduit un travail distinct de la Response HTTP. Nous allons confier ce travail à un bus, puis déterminer s'il s'exécute immédiatement ou dans un worker. Transports, handlers et middleware seront ensuite approfondis séparément.

Ce cours répond à une seule question : quand j'appelle dispatch(), que se passe-t-il vraiment, et qu'est-ce que je reçois en retour ?

L'essentiel

À comprendre

À retenir en priorité
  1. Envoyer et traiter sont deux étapes.
  2. Le worker peut exécuter plus tard.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi Messenger existe. Une requête HTTP doit répondre vite. Certains travaux (envoyer un mail, importer un fichier) sont longs ou n'ont pas besoin d'être terminés avant la Response. Messenger sépare décrire le travail (un message) de l'exécuter (un handler), et laisse la configuration décider où et quand il s'exécute.
  • Ce que l'auteur veut que vous compreniez. L'appel dispatch() ne change jamais ; ce qui change, c'est le chemin que le bus fait suivre au message. Par défaut (aucun sender), le handler tourne pendant dispatch(). Avec un transport différé, il tourne plus tard, dans un worker.
  • Le piège de fond. « Envoyé » n'est pas « traité ». C'est la source de la plupart des questions de certification sur ce sujet.
  • Pourquoi c'est à l'examen. On vous interroge sur les six concepts de la documentation, sur le rôle exact de chaque middleware, sur la lecture du résultat (HandledStamp) et sur l'immutabilité de l'Envelope.

Un message est un object qui décrit les données d'un travail ; le handler est le callable qui réalise ce travail. Le bus fait passer le message dans une suite de middleware, capables de le traiter, de le transmettre ou d'interrompre la suite. Un controller, une command ou un service peut appeler dispatch() : le bus n'est pas réservé au chemin HTTP.

Avec les middleware standard et un handler enregistré, l'absence de sender routé laisse le traitement s'exécuter immédiatement. Un transport sync:// reste immédiat lui aussi. Seul un transport différé approprié, son routage et un worker permettent le chemin asynchrone. La configuration change le chemin sans changer l'appel dispatch(), mais pas son sens : au retour d'un envoi différé, le travail n'est pas nécessairement terminé.

Une Envelope porte le message et des stamps, informations sur son traitement. Les opérations d'ajout de stamps retournent une nouvelle Envelope : c'est celle retournée par dispatch() qu'il faut examiner.

Le schéma

À retenir en priorité
  1. Le message ne choisit pas seul son mode.
  2. Le routage configure l'envoi.

Où en est-on ? Étape 1/4 du cours : la vue d'ensemble. Les trois sections suivantes (les six concepts, dispatch(), l'Envelope) zooment chacune sur une partie de ce dessin. Commençons par le plan :

Messenger component
   ├─ 1. Qui joue quel rôle ?   → six concepts (sender, receiver, handler…)
   ├─ 2. Que fait dispatch() ?  → synchrone / différé / sync://
   └─ 3. Que me rend le bus ?   → Envelope + stamps (HandledStamp…)

Pour l'accueil de l'abonné, le choix important n'est pas « depuis un controller ou depuis la console », mais « quel sender le bus trouve-t-il ? ». Ce dessin compare le traitement direct au transport différé ; les handlers ordinaires sont supposés réussir. La variante sync:// est décrite après l'exemple.

Bleu : opérations ; ambre : choix du routage ; vert : résultat du passage. Le pointillé représente un passage ultérieur dans un autre processus, pas un appel direct du sender au worker. Vue du transport asynchrone : sync://, décrit ci-dessous, redispatche immédiatement sans worker.

Un middleware placé avant l'envoi voit donc le départ, puis la réception lorsque le worker redispatche le message. Cela fait deux passages dans le cas nominal représenté, pas une garantie de deux appels de chaque middleware : celui placé après send_message n'est pas atteint à l'envoi différé, et une nouvelle réception après échec peut ajouter d'autres passages.

Pourquoi un message traverse-t-il le bus deux fois ? Parce que le bus est le même à l'aller et au retour. À l'aller, SendMessageMiddleware voit un message sans ReceivedStamp : il l'envoie et coupe la chaîne. Au retour, le worker redispatche le message avec ReceivedStamp : le même middleware comprend « message reçu, ne pas le renvoyer » et laisse passer jusqu'aux handlers. Un seul stamp suffit à éviter une boucle infinie.

L'exemple

Exemple concret

À retenir en priorité
  1. Sans routage le traitement est immédiat.
  2. Il faut toujours un handler approprié.

Où en est-on ? Étape 2/4 : un cas concret avant le vocabulaire. On construit le plus petit chemin complet : un message, un handler, un appel dispatch().

Le lecteur de l'article s'inscrit à la lettre du blog. Pour observer le bus sans dépendre d'un serveur de mail, conservons un handler minimal qui retourne une string. Malgré son nom WelcomeMailer, il n'envoie aucun email : mailed alice sera seulement la valeur calculée.

Dans une application FrameworkBundle Symfony 8.0, PHP 8.4, avec Messenger configuré, les namespaces suivants supposent l'autoload PSR-4 App\ vers src/. Premier fichier, src/Message/Welcome.php :

<?php
namespace App\Message;

final class Welcome                        // un object PHP ordinaire, sans interface
{
    public function __construct(public string $who) {}
}

Welcome('alice') transporte le nom, sans exécuter le travail lui-même. Le callable suivant transforme cette entrée en résultat. Deuxième fichier, src/MessageHandler/WelcomeMailer.php :

<?php
namespace App\MessageHandler;

use App\Message\Welcome;
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
final class WelcomeMailer
{
    public function __invoke(Welcome $message): string
    {
        return 'mailed '.$message->who;
    }
}

Pourquoi Symfony trouve-t-il ce handler sans que je le déclare ? Le handler doit être enregistré comme service avec autoconfiguration pour que l'attribute soit reconnu. Autoconfiguration signifie ici appliquer la configuration de handler signalée par #[AsMessageHandler] ; autowiring résout les dependencies injectées, comme le bus du service appelant. Ce sont des préparations du service container, pas une découverte de tous les handlers répétée à chaque consultation de /blog/42. Le type de l'argument de __invoke() (Welcome) indique au container quel message ce handler traite.

Le bus doit conserver les middleware standard send_message et handle_message. Fragment d'une méthode de service ou de controller, avec App\Message\Welcome importé dans son fichier et une propriété $this->bus de type Symfony\Component\Messenger\MessageBusInterface injectée par le constructeur :

$envelope = $this->bus->dispatch(new Welcome('alice'));

Sans sender correspondant, WelcomeMailer tourne pendant dispatch() et le résultat mailed alice est porté par un HandledStamp de l'Envelope retournée. Avec routing: { App\Message\Welcome: async }, un transport async configuré et un worker qui consomme ce transport, il tourne dans ce worker. Ici async doit désigner un transport réellement différé : son nom n'impose pas ce comportement. L'attribute seul ne configure ni ce transport ni son routage. Pour l'import long du blog, la même distinction s'appliquera à ImportBlogFile : le message décrit le fichier, le handler exécute l'import.

Ce que Symfony voit dans cet exemple :

Élément Ce que Symfony fait Qui intervient
new Welcome('alice') rien : c'est une simple donnée vous
dispatch() emballe le message dans une Envelope le bus
aucun routage laisse la chaîne continuer SendMessageMiddleware
__invoke(Welcome $m) appelé, résultat rangé dans un HandledStamp HandleMessageMiddleware

Les six concepts de la documentation

À retenir en priorité
  1. Le sender écrit vers le transport.
  2. Le receiver récupère pour le worker.

Où en est-on ? Étape 3/4 : maintenant que le chemin est vu, on nomme les rôles. La documentation officielle en liste six ; on les rattache à ce que l'exemple vient de montrer.

L'exemple a séparé les données de l'accueil et son traitement. Pour déplacer ce traitement hors du processus appelant, il faut aussi identifier qui remet l'Envelope et qui la récupère. Lire ce tableau comme une répartition de rôles, pas comme six étapes obligatoires de chaque message.

Concept Role
Sender envoie l'Envelope vers une destination ; un transport externe peut sérialiser le message
Receiver fournit des Envelope au worker ; le worker les redispatche au bus
Handler exécute la logique métier ; appelé par HandleMessageMiddleware
Middleware accède au message et à l'Envelope pendant la traversée du bus
Envelope emballe le message pour y attacher des informations
Envelope Stamps ces informations : délai, transport, résultat, marqueurs

Ni le message — une class ordinaire — ni le bus, qui fait traverser la suite de middleware, ne figurent dans cette liste documentaire de six concepts. Ils restent indispensables à l'explication. Un sender n'est pas le handler : remettre l'accueil au transport ne prouve pas qu'il a calculé mailed alice. Le routage Messenger associe des messages à des transports ; il ne choisit pas le controller de blog_show, contrairement au routage HTTP.

Les rôles se répartissent entre l'aller (côté appelant) et le retour (côté worker) :

 CÔTÉ APPELANT                 TRANSPORT              CÔTÉ WORKER
 ┌──────────────┐  Envelope  ┌───────────┐  Envelope  ┌──────────────┐
 │ dispatch()   │ ─────────► │   queue   │ ─────────► │  Receiver    │
 │ middleware   │  (Sender)  └───────────┘            │  → bus       │
 │ Sender       │                                     │  → middleware│
 └──────────────┘                                     │  → Handler   │
                                                      └──────────────┘

🌍 In Real Life

La situation : le secrétariat du blog prépare les courriers d'accueil des abonnés.

L’équivalent dans Symfony : fiche de travail → message ; pochette → Envelope ; annotations → stamps ; poste d'expédition → sender ; poste de réception → receiver ; personne réalisant la tâche → handler ; contrôles du circuit → middleware.

Retour à la réalité technique : le bus traverse une pile de middleware. Le worker peut recevoir puis redispatcher une Envelope ; le sender n'appelle pas directement ce worker. Sans transport différé, le traitement peut rester local.

🧠 Comment le mémoriser : « La fiche voyage, le handler travaille. » Image mentale : une pochette passant entre deux bureaux. Question-réflexe : qui transporte, qui reçoit, qui exécute ?

⚠️ À ne pas confondre : transport du travail et réalisation du travail.

Dispatcher

À retenir en priorité
  1. Le résultat appartient à l'Envelope retournée.
  2. Un envoi asynchrone ne fournit pas ce résultat immédiatement.

Où en est-on ? Étape 3/4 (suite) : le cœur du sujet. On compare trois configurations pour répondre à « qu'est-ce qui est déjà fait quand dispatch() rend la main ? ».

Ajoutons mentalement un second handler ordinaire pour journaliser l'accueil. Les deux réussissent, le bus FrameworkBundle conserve ses middleware standard, dont celui qui ajoute BusNameStamp, et aucun stamp de résultat antérieur n'est fourni. Le tableau compare trois configurations pour un nouveau Welcome accompagné de DelayStamp(5000), une consigne de délai de 5 000 ms :

Routage Handlers exécutés avant le retour Stamps de l'Envelope retournée
aucun (synchrone) les deux DelayStamp, BusNameStamp, HandledStamp ×2
in-memory:// aucun DelayStamp, BusNameStamp, SentStamp, TransportMessageIdStamp
sync:// les deux DelayStamp, BusNameStamp, SentStamp, ReceivedStamp, HandledStamp ×2
  • Synchrone : déjà traité au retour. Asynchrone : seulement envoyé.
  • sync:// est un vrai transport qui redispatche aussitôt : envoyé et traité.
  • Un DelayStamp n'a aucun effet en synchrone : c'est une consigne pour le transport.
  • Non routé et sans handler : NoHandlerForMessageException avec le réglage par défaut allow_no_handlers: false.

Pourquoi la ligne sync:// contient-elle SentStamp ET HandledStamp ? Déroulons : SendMessageMiddleware trouve le sender sync:// et appelle send() avec un SentStamp. Ce sender redispatche aussitôt le message avec un ReceivedStamp. Au second passage, le middleware d'envoi voit le ReceivedStamp, ne renvoie pas, et laisse continuer vers les handlers. Les stamps des deux passages sont cumulés dans l'Envelope retournée.

SendMessageMiddleware cherche les senders, appelle leur send() avec un SentStamp, puis ne passe pas au middleware suivant s'il a envoyé. SyncTransport redispatche aussitôt avec ReceivedStamp : au second passage, le middleware d'envoi laisse continuer vers les handlers. Cela explique pourquoi « il y a un transport » ne suffit pas à conclure « c'est asynchrone ».

La ligne in-memory:// décrit un stockage en mémoire pour observer les envois, pas une queue durable partagée entre processus. Pour l'import de production, choisir le transport adapté relève du cours sur les transports. Le tableau décrit des succès ; une exception de handler empêche un retour normal et ne doit pas être interprétée comme un résultat métier.

🌍 In Real Life

La situation : au secrétariat du blog, remettre une demande au collègue présent ou la déposer pour une autre équipe ne donne pas la même preuve d'achèvement.

L’équivalent dans Symfony : traitement devant vous → handlers synchrones ; dépôt pour traitement ultérieur → transport différé ; guichet qui retransmet immédiatement → sync://.

Retour à la réalité technique : dispatch() retourne une Envelope. Avec la pile standard et les handlers ordinaires requis, le synchrone termine avant le retour normal ; l'envoi différé ne prouve pas l'exécution distante. DelayStamp ne transforme pas le synchrone en attente.

🧠 Comment le mémoriser : « Remis n'est pas fini. » Image mentale : deux cases, « envoyé » et « traité ». Question-réflexe : quel transport et quels stamps prouvent ce qui s'est passé ?

⚠️ À ne pas confondre : le nom async et le comportement réel du DSN.

L'Envelope et les stamps

À retenir en priorité
  1. L'Envelope est immuable.
  2. Utiliser la valeur retournée.

Où en est-on ? Étape 4/4 : dispatch() a rendu une Envelope. Que contient-elle, et comment la lire sans se tromper de variable ?

Le bus a rendu une Envelope ; cherchons maintenant ce qu'elle prouve. Dans la méthode appelante de l'exemple, avec Welcome, DelayStamp et HandledStamp importés depuis leurs namespaces respectifs App\Message et Symfony\Component\Messenger\Stamp, le fragment devient :

$message = new Welcome('alice');
$envelope = $this->bus->dispatch($message, [new DelayStamp(5000)]);
$result   = $envelope->last(HandledStamp::class)?->getResult();

Avec le seul WelcomeMailer et un traitement synchrone réussi, $result vaut mailed alice, sans attendre cinq secondes. Après un envoi différé sans traitement local, aucun HandledStamp n'est présent et l'accès nullsafe donne null. Ce null ne promet pas qu'une valeur arrivera automatiquement dans cette variable quand le worker terminera.

Avec deux handlers réussis, last(HandledStamp::class) sélectionne le dernier résultat enregistré ; all(HandledStamp::class) conserve les deux. HandleTrait::handle() sert au besoin différent d'un résultat unique : après le dispatch, il exige exactement un HandledStamp, sinon LogicException, « was handled multiple times » ou « was handled zero times ». Une exception levée par le bus peut aussi remonter avant ce contrôle.

Enfin, with() clone l'Envelope avant d'ajouter les stamps. Lire l'Envelope d'entrée ferait manquer les stamps ajoutés pendant le parcours. Cette immutabilité de l'enveloppe ne rend pas récursivement immuables l'object message et tous les objects qu'il référence.

Avant / après with() :

$a = new Envelope($msg)           $a : [ $msg | (aucun stamp) ]
$b = $a->with(new DelayStamp(1))  $a : [ $msg | (aucun stamp) ]   ← inchangée
                                  $b : [ $msg | DelayStamp ]      ← nouvelle
                                  $a->getMessage() === $b->getMessage()  (même objet)
Méthode Rôle
last(X::class) le dernier stamp de ce type, ou null
all(X::class) tous les stamps de ce type (array)
with(...$stamps) clone, puis ajoute (variadique)
HandleTrait::handle() dispatch + exige exactement un HandledStamp

🌍 In Real Life

La situation : le secrétariat rend une copie annotée de la demande d'accueil, pas une promesse que votre ancienne copie se mettra à jour.

L’équivalent dans Symfony : copie annotée rendue → Envelope retournée ; annotation de traitement → HandledStamp et son résultat.

Retour à la réalité technique : les opérations d'ajout de stamps produisent une nouvelle Envelope. Lire celle rendue par le bus ; un résultat absent après envoi différé n'apparaîtra pas spontanément dans la variable de l'appelant.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le stamp est une consigne au transport.
  2. Il ne retarde pas le traitement direct.
  • Voir l’explication : pourquoi la mauvaise réponse semble plausible

    Pour chaque piège : l'énoncé, pourquoi la mauvaise réponse semble plausible.

  • Voir l’explication : dispatch() ne signifie pas « traité » en asynchrone

    dispatch() ne signifie pas « traité » en asynchrone : la command d'import peut n'avoir fait qu'envoyer le travail. En synchrone, avec les handlers ordinaires de l'exemple et un retour normal, ils ont déjà terminé. Pourquoi on se trompe : le verbe « dispatch » (répartir) et l'appel bloquant du mode synchrone donnent l'impression d'un travail fini.

  • Voir l’explication : Un message n'a aucune interface Messenger obligatoire.

    Un message n'a aucune interface Messenger obligatoire. Welcome est une class ordinaire ; une interface applicative reste possible, ce n'est pas interdit. Pourquoi on se trompe : beaucoup de bibliothèques exigent un Command ou Event marqueur.

  • Voir l’explication : Le résultat se lit sur l'Envelope retournée

    Le résultat se lit sur l'Envelope retournée, via HandledStamp. L'appelant qui a seulement envoyé Welcome en différé ne reçoit pas ainsi le résultat futur du worker. Pourquoi on se trompe : on imagine dispatch() comme une promesse (Promise).

  • Voir l’explication : Un DelayStamp ne retarde rien en synchrone

    Un DelayStamp ne retarde rien en synchrone : ajouter 5000 au message d'accueil ne transforme pas le handler direct en travail de fond. Pourquoi on se trompe : le nom du stamp promet un délai ; or c'est une consigne lue par le transport, pas par le bus.

  • Voir l’explication : Sans handler ni routage, dispatch() lève une exception avec les réglages standard.

    Sans handler ni routage, dispatch() lève une exception avec les réglages standard. Si l'accueil ne trouve aucun handler, vérifier l'enregistrement du service avant de modifier allow_no_handlers. Pourquoi on se trompe : on croit qu'un message sans destinataire est ignoré silencieusement, comme un événement sans listener.

  • Voir l’explication : Les six concepts de la documentation

    Les six concepts de la documentation sont sender, receiver, handler, middleware, envelope et stamps — pas « message » ni « bus ». Cette liste est un vocabulaire de référence, pas une chronologie à imposer à Welcome. Pourquoi on se trompe : « message » et « bus » sont les mots les plus utilisés ; on les suppose dans la liste.

Fiche express

À mémoriser

À retenir en priorité
  1. HandleTrait attend un résultat unique.
  2. Un dispatch général peut avoir plusieurs handlers.

Si tu dois retenir seulement 6 choses :

  • Six concepts : sender, receiver, handler, middleware, envelope, stamps.
  • Un message est une class ordinaire ; routage et middleware déterminent son parcours.
  • Synchrone réussi : handlers ordinaires terminés ; envoi asynchrone : achèvement non garanti.
  • Le résultat : HandledStamp, sur l'Envelope retournée.
  • HandleTrait : exactement un HandledStamp après dispatch, sinon LogicException.
  • Un middleware atteint à l'envoi et à la réception voit deux passages nominaux ; retries possibles.

Moyen mnémotechnique : « emballer, envoyer ou traiter, lire le retour ».

dispatch → Envelope (immuable) → middleware →
  sender ? oui : SentStamp, stop / non : handlers, HandledStamp ;
worker → ReceivedStamp → middleware à nouveau → handlers ;
HandleTrait = un seul handler, synchrone

Le mémo décrit la branche différée lorsqu'un sender est choisi ; sync:// redispatche immédiatement. Pour continuer, définir les messages et handlers, puis choisir les transports de l'import. Ces chemins ne changent pas le service de lecture utilisé par GET /blog/42.

🧠 À retenir pour la certification

  • Messenger sépare décrire (message) et exécuter (handler) ; le bus fait traverser des middleware.
  • Six concepts officiels : sender, receiver, handler, middleware, envelope, stamps. Pas « message », pas « bus ».
  • Sans sender routé : handlers pendant dispatch(). sync:// : idem, via un redispatch avec ReceivedStamp.
  • Transport différé : SentStamp, la chaîne s'arrête ; le worker redispatche avec ReceivedStamp.
  • DelayStamp : consigne pour le transport, sans effet en synchrone.
  • Résultat = HandledStamp sur l'Envelope retournée ; with() clone toujours.
  • HandleTrait::handle() : exactement un HandledStamp, sinon LogicException (zéro ou plusieurs fois).
  • Sans handler : NoHandlerForMessageException (allow_no_handlers: false par défaut).

Phrase de mémorisation : « Le message voyage dans une Envelope que le bus fait passer entre middleware : s'il trouve un sender il s'arrête (envoyé), sinon le handler travaille tout de suite (traité) — et le résultat se lit sur le reçu rendu. »
