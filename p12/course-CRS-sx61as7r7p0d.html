Objectif

Générer une URL depuis une route, et maîtriser ce qui arrive aux parameters qui ne font pas partie de la route.

Question fil rouge : « Je donne un nom de route et des valeurs : comment Symfony fabrique-t-il l'URL, et que devient une valeur que le path n'utilise pas ? »

L'essentiel

À comprendre

À retenir en priorité
  1. Un service injecte UrlGeneratorInterface.
  2. Le controller dispose aussi de generateUrl().

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Écrire /blog/42 à la main fige le path dans tout le code. En passant par le nom de la route, un changement de path met à jour tous les liens.
  • Le piège de fond. La génération est le sens inverse du matching : on part d'un nom et de valeurs, on aboutit à une chaîne. Elle n'exécute rien.
  • Ce que l'auteur veut que vous compreniez. Variables obligatoires d'abord, extras ensuite (query string), avec des règles précises : défaut retiré, _query prioritaire, objets convertis.
  • Pourquoi c'est à l'examen. ABSOLUTE_URL = 0 mais défaut = ABSOLUTE_PATH = 1, MissingMandatoryParametersException, RouteNotFoundException, _query array.

Une URL se génère toujours depuis une route : generateUrl() dans un controller, generate() d'UrlGeneratorInterface dans un service, path() et url() en Twig. Le troisième argument choisit la forme — path absolu par défaut. Une fois les variables obligatoires du path et du host satisfaites, un parameter ordinaire non consommé peut partir en query string, sauf s'il égale son défaut de route. Une faute qui laisse une variable obligatoire sans valeur ni défaut lève MissingMandatoryParametersException. Un object supplémentaire est converti, contrairement à ce que dit la documentation.

Le schéma

Où en est-on ? Carte du cours, puis le schéma central de la génération.

Cours « URLs generation »
   ├─ exemple                      → generateUrl('blog', [...])
   ├─ 1. Où et comment             → controller, service, Twig
   ├─ 2. Les quatre types          → ABSOLUTE_URL/PATH, RELATIVE, NETWORK
   ├─ 3. Les parameters en trop    → query string, défaut, _query, objets
   └─ 4. Route absente             → RouteNotFoundException

Ambre = résolution ; bleu = données calculées. Chemin simplifié pour des paramètres valides : manque d'une variable obligatoire et violation de requirement peuvent interrompre la génération. Générer une URL n'exécute pas la route.

Où en est-on ? Le sens inverse du matching, côte à côte.

MATCHING  (entrant)  /blog/42            →  _route=blog_show, id=42
GÉNÉRATION (sortant) blog_show + id=42   →  /blog/42
                     (aucun controller appelé, aucune requête envoyée)

L'exemple

Exemple concret

Où en est-on ? Cas concret : un lien de pagination, puis une URL absolue pour un email.

Pour le récit principal, generateUrl('blog_show', ['id' => 42]) produit le lien vers l'article, sans l'exécuter. Les exemples historiques suivants emploient une route de pagination isolée blog : dans notre application commune, la pagination utilise /blog/page/{page} afin de ne pas confondre page 42 et article 42.

$this->generateUrl('blog', ['page' => 2, 'category' => 'Symfony']);
// la route blog ne définit que page → /blog/2?category=Symfony

$this->generateUrl('blog', ['page' => 2], UrlGeneratorInterface::ABSOLUTE_URL);
// lien pour un email → https://example.com/blog/2

Où et comment

Où en est-on ? Étape 1 sur 4. Qui peut générer une URL ? Trois endroits, un seul contrat.

Le contrôleur, un service d'email et Twig peuvent tous demander le lien vers l'article 42. Ils utilisent le même contrat de génération mais n'ont pas le même accès au service. Dans un service, injecter UrlGeneratorInterface rend cette dépendance explicite ; cela ne lui injecte pas la Request comme argument de contrôleur.

Contexte Appel
controller (AbstractController) $this->generateUrl('nom', [...])
service injecter UrlGeneratorInterface, appeler generate()
template Twig path('nom', {...}) et url('nom', {...})

On ne construit jamais une URL à la main : changer le path d'une route met alors à jour tous les liens.

🌍 In Real Life

La situation : l'accueil, le service courrier et l'imprimeur consultent le même répertoire pour écrire l'adresse d'une salle. Ils ne recopient pas chacun une ancienne adresse dans leur propre carnet.

L’équivalent dans Symfony : helper du contrôleur, UrlGeneratorInterface injecté et fonctions Twig demandent au routage une URL à partir du nom et des paramètres. Les liens nouvellement générés suivent ainsi la configuration de la route.

Retour à la réalité technique : il s'agit des liens vers les routes de l'application, pas d'une interdiction universelle de manipuler une URL externe. Générer ne déclenche ni requête, ni contrôleur, ni chargement de l'article ; les liens déjà envoyés par email ne sont pas réécrits rétroactivement.

🧠 Comment le mémoriser : « Un répertoire commun, plusieurs guichets de demande. » Image mentale : trois bureaux consultant le même plan. Question-réflexe : ai-je déclaré ma dépendance au générateur plutôt que recopié le chemin ?

⚠️ À ne pas confondre : génération sortante, matching entrant et invocation du contrôleur.

Le route name joue le rôle d'un contact téléphonique : changer son numéro une fois met à jour les appels futurs. Recopier le path partout revient à mémoriser des numéros qui deviendront périmés.

Les quatre types de référence

À retenir en priorité
  1. Le défaut produit un path absolu.
  2. Un lien complet pour un email exige ABSOLUTE_URL.

Où en est-on ? Étape 2 sur 4. Pourquoi plusieurs formes ? Selon que le lecteur est dans la page, ou loin (email), l'adresse doit être plus ou moins complète.

Le lien interne du blog peut être /blog/42 ; celui de l'email doit inclure le host et le schéma pour être utilisable hors de la page actuelle. Le générateur s'appuie sur son contexte : en Console, ce contexte doit être configuré convenablement, aucune Request HTTP du destinataire n'existe. Le nombre 0 de la constante ne signifie pas « option par défaut ».

Les constants sont sur UrlGeneratorInterface : ABSOLUTE_URL vaut 0, ABSOLUTE_PATH vaut 1 et c'est le défaut, RELATIVE_PATH vaut 2, NETWORK_PATH vaut 3. La constant qui vaut 0 n'est donc pas le défaut. NETWORK_PATH reprend le schéma courant ; RELATIVE_PATH est relatif au path courant.

Constante       Val.  Exemple de résultat          Remarque
--------------  ----  ---------------------------  -----------------------
ABSOLUTE_URL     0    https://example.com/blog/2   emails, console
ABSOLUTE_PATH    1    /blog/2                      LE DÉFAUT
RELATIVE_PATH    2    ../blog/2                    relatif au path courant
NETWORK_PATH     3    //example.com/blog/2         reprend le schéma courant

Moyen de ne pas confondre : path() en Twig = ABSOLUTE_PATH (1), url() = ABSOLUTE_URL (0).

🌍 In Real Life

La situation : « depuis l'entrée », « depuis votre position » et « à telle adresse complète » donnent des indications de portée différente. Une invitation envoyée loin du bâtiment ne peut pas supposer que le lecteur est déjà dans le couloir.

L’équivalent dans Symfony : ABSOLUTE_PATH part de la racine du site, RELATIVE_PATH dépend du chemin courant, NETWORK_PATH inclut l'hôte sans imposer le schéma, et ABSOLUTE_URL fournit l'adresse complète. Pour un email, cette dernière forme évite de dépendre de la page actuelle.

Retour à la réalité technique : le contexte du générateur fournit les informations nécessaires et doit être configuré hors HTTP. Les contraintes de host ou schéma de la route peuvent élargir la référence produite. La valeur numérique zéro d'une constante ne signifie pas qu'elle est le défaut.

🧠 Comment le mémoriser : « Plus loin est le lecteur, plus complète doit être l'adresse. » Image mentale : flèche de couloir puis enveloppe avec adresse complète. Question-réflexe : quelles informations de contexte le destinataire possède-t-il réellement ?

⚠️ À ne pas confondre : chemin absolu, URL absolue et chemin relatif au contexte.

Les parameters en trop

À retenir en priorité
  1. Une fois les variables obligatoires du path et du host satisfaites, les extras ordinaires peuvent devenir des parameters de query, sauf égalité avec leurs défauts.
  2. _query explicite prime sur les extras de même nom.

Où en est-on ? Étape 3 sur 4. Que fait le générateur des valeurs qu'on lui donne mais que le path n'utilise pas ? Ordre : variables obligatoires d'abord, extras ensuite.

En générant blog_show avec id=42 et ref=letter, id remplit le chemin tandis que ref peut devenir query. Une faute articleId ne remplit pas {id} : le générateur échoue avant de simplement ajouter un extra. Les exemples ci-dessous montrent ensuite le conflit entre extra ordinaire et _query, sans valider le sens métier de ces paramètres.

Une fois toutes les variables obligatoires du path et du host satisfaites par une valeur fournie ou un défaut, un parameter ordinaire non consommé part en query string. Deux nuances : un parameter en trop égal à la default value de même nom est retiré ; la key réservée _query fournit un array de parameters qui l'emportent sur les parameters en trop de même nom — une valeur qui n'est pas un array lève une InvalidParameterException.

Exemple Twig avec l'extension Routing, la route article_show définie par /articles/{slug}, et aucun défaut pour sort :

{{ path('article_show', {slug: 'guide', sort: 'date', _query: {sort: 'title'}}) }}

Le résultat est /articles/guide?sort=title : slug remplit le path et _query remplace l'extra sort. Fournir _query: 'sort=title' n'est pas fournir un array. Remplacer slug par articleSlug laisse une variable obligatoire manquante, même si une clé ressemblante existe. La query générée n'effectue aucune validation métier du tri demandé.

Arbre de décision pour chaque valeur fournie :

Valeur fournie pour la clé k
   ├─ k est une variable du path/host ?  → remplit le path
   └─ sinon (extra)
        ├─ égale au default de même nom ? → retirée
        ├─ _query[k] existe ?             → _query[k] l'emporte
        └─ sinon                          → ?k=valeur (query string)
Variable obligatoire sans valeur ni défaut → MissingMandatoryParametersException

🌍 In Real Life

La situation : une fiche doit d'abord remplir les cases obligatoires de l'adresse. Une note supplémentaire ne remplace pas un numéro manquant ; une instruction explicite peut ensuite remplacer une ancienne note du même nom.

L’équivalent dans Symfony : les variables obligatoires du path et du host doivent avoir leur valeur. Les extras ordinaires peuvent former la query ; ceux égaux à un défaut sont omis et le tableau _query prend priorité sur les extras de même nom.

Retour à la réalité technique : une clé ressemblante ne satisfait pas un placeholder mal orthographié. _query doit être un tableau ; encoder sa valeur ne valide pas le sens métier du tri ou du filtre transmis. Cette priorité concerne la query, pas le remplacement rétroactif des variables du chemin.

🧠 Comment le mémoriser : « Compléter l'adresse avant d'ajouter les notes. » Image mentale : cases obligatoires remplies puis notes complémentaires. Question-réflexe : manque-t-il une variable, ou ai-je vraiment un paramètre supplémentaire ?

⚠️ À ne pas confondre : variable obligatoire absente, extra omis par défaut et extra remplacé par _query.

Repère — Les objects en parameter supplémentaire :

Question: How are extra object parameters converted during URL generation?

Answer: Public properties are used first; otherwise a Stringable object can be converted to a string.

Les properties publiques ont priorité. La conversion Stringable concerne les objects sans properties publiques.

Les objects en parameter supplémentaire

À retenir en priorité
  1. Les properties publiques ont priorité.
  2. La conversion Stringable concerne les objects sans properties publiques.

Passer tout ArticleView comme extra pour économiser une extraction explicite risque d'exposer des propriétés publiques dans l'URL, donc dans les historiques et journaux. Choisis plutôt la donnée publique nécessaire, par exemple l'identifiant. La conversion automatique du générateur explique le résultat technique ; elle ne constitue pas une politique d'exposition.

Pour un objet supplémentaire, le code 8.0 doGenerate() prend ses properties publiques en array s'il en a, sinon le convertit en chaîne s'il est Stringable, et lève sur une référence circulaire. Préférer une valeur scalaire explicite pour maîtriser ce qui est publié dans la query string.

Object en extra
   ├─ a des properties publiques ? → array de ces properties (→ query)
   ├─ sinon, Stringable ?          → chaîne (__toString)
   └─ référence circulaire         → InvalidParameterException
Bonne pratique : passer l'identifiant (scalaire), pas l'object.

🌍 In Real Life

La situation : pour inscrire un numéro de dossier sur une enveloppe, on transmet par erreur toute une fiche dont les rubriques publiques sont recopiées. Une conversion réussie peut alors publier bien plus que prévu.

L’équivalent dans Symfony : pour un objet supplémentaire, le générateur Symfony 8.0 utilise ses propriétés publiques ; à défaut, un objet Stringable peut fournir une chaîne. Cela peut transformer un objet métier en données de query visibles dans les URL.

Retour à la réalité technique : cette conversion n'est ni une sélection de champs autorisés ni un chargement d'entité. Une référence circulaire peut provoquer une erreur. Fournir explicitement l'identifiant public utile rend l'exposition prévisible ; une URL peut être conservée dans des historiques et journaux.

🧠 Comment le mémoriser : « Pour écrire un numéro, ne donne pas tout le dossier. » Image mentale : enveloppe portant involontairement toutes les rubriques de la fiche. Question-réflexe : quelles données cet objet risque-t-il de rendre publiques dans la query ?

⚠️ À ne pas confondre : conversion technique, politique de publication et validation métier.

Route absente

À retenir en priorité
  1. Ne pas charger toute la RouteCollection pour ce simple test.
  2. Traiter explicitement RouteNotFoundException.

Où en est-on ? Étape 4 sur 4. Que faire quand la route demandée n'existe pas (fonctionnalité optionnelle non chargée) ?

Si une fonctionnalité optionnelle n'a pas chargé sa route, le lien ne peut pas être généré, même si l'article existe. Intercepter RouteNotFoundException permet de traiter ce cas ; charger toute la collection pour chaque lien ajouterait un travail inutile et ne remplace pas le générateur compilé.

Ne pas appeler getRouteCollection() pour tester l'existence d'une route : cela peut charger l'ensemble des ressources de routage au lieu d'utiliser le seul générateur compilé. Tenter la génération et rattraper RouteNotFoundException.

try {
    $url = $generator->generate('optional_feature');
} catch (RouteNotFoundException) {
    $url = null; // lien optionnel : on ne l'affiche pas
}

🌍 In Real Life

La situation : le répertoire ne connaît pas la salle demandée. Relire tous les plans du bâtiment pour chaque enveloppe n'est pas nécessaire si le service d'adressage peut déjà signaler précisément cette absence.

L’équivalent dans Symfony : la génération d'un nom inconnu lève RouteNotFoundException. Pour un lien réellement optionnel, traiter cette exception évite d'utiliser getRouteCollection() comme vérification préalable coûteuse.

Retour à la réalité technique : charger la collection peut charger les ressources de routage plutôt qu'utiliser seulement le générateur compilé. L'absence de route est distincte d'un paramètre obligatoire manquant et de l'absence de l'article ; une erreur de configuration inattendue ne doit pas être cachée systématiquement.

🧠 Comment le mémoriser : « Nom absent du plan n'est pas dossier absent de l'archive. » Image mentale : répertoire sans salle, archive encore indépendante. Question-réflexe : est-ce un lien optionnel absent ou une configuration attendue mais cassée ?

⚠️ À ne pas confondre : RouteNotFoundException de génération et réponse 404 d'une future requête.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM probables et la raison de leur plausibilité.

  • Voir l’explication : Une clé inutilisée peut devenir un extra, mais ne satisfait pas une variable obligatoire.

    Une clé inutilisée peut devenir un extra, mais ne satisfait pas une variable obligatoire. Avec /articles/{slug} sans défaut pour slug, fournir seulement articleSlug='guide' lève MissingMandatoryParametersException. Fournir aussi slug='guide' permet la génération : articleSlug='extra' donne alors /articles/guide?articleSlug=extra. La règle des extras suppose donc que toutes les variables obligatoires du path et du host soient satisfaites ; les extras égaux à leurs défauts restent omis et _query conserve sa priorité. Pourquoi on se trompe : « tout ce qui ne sert pas va en query » semble s'appliquer aussi à une variable mal nommée.

  • Voir l’explication : Un object en parameter supplémentaire est converti, selon le code 8.0.

    Un object en parameter supplémentaire est converti, selon le code 8.0. Les properties publiques d'abord, en array ; __toString() seulement s'il n'en a pas. La documentation dit encore le contraire. Pourquoi on se trompe : on se fie à la documentation, qui est en retard sur le code.

  • Voir l’explication : Un parameter en trop égal au défaut disparaît de la query string.

    Un parameter en trop égal au défaut disparaît de la query string. Pourquoi on se trompe : on pense que tout extra fourni apparaît dans l'URL.

  • Voir l’explication : Le type de référence par défaut est le path absolu, pas l'URL absolue.

    Le type de référence par défaut est le path absolu, pas l'URL absolue. Générer un lien pour un email demande de le dire explicitement. Pourquoi on se trompe : ABSOLUTE_URL vaut 0, ce qui ressemble à « valeur par défaut ».

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Jamais d'URL à la main : generateUrl(), generate(), path(), url().
  • Défaut : ABSOLUTE_PATH (1) ; ABSOLUTE_URL vaut 0.
  • Variables obligatoires du path et du host satisfaites → extras ordinaires en query string ; une clé mal nommée ne remplace pas une variable manquante.
  • Égal au défaut → retiré ; _query : un array, prioritaire.
  • Object en trop : properties publiques → array, sinon Stringable → string.
  • Route absente : rattraper RouteNotFoundException.

Moyen mnémotechnique : « Zéro, c'est tout : l'URL complète ».

Phrase de mémorisation : « Un nom de route et des valeurs : d'abord remplir les variables obligatoires, ensuite les extras partent en query string — et le défaut, c'est le path absolu, pas l'URL. »
