Objectif

La page /blog/42 et sa représentation /api/blog/42 peuvent exposer le même article sans conserver l'identité de la même façon. Le firewall choisit les mécanismes applicables à chacune ; son nom ne crée ni route, ni permission, ni authenticator à lui seul.

Ce cours répond à : pour une Request donnée, quel firewall s'en occupe, que porte-t-il, et comment gère-t-il l'état de la connexion ?

L'essentiel

À comprendre

À retenir en priorité
  1. Les firewalls ne s'empilent pas.
  2. L'ordre est déterminant.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un site réel mélange des zones qui n'ont pas les mêmes besoins : outils de développement (aucune sécurité), API (jeton, pas de session), site (formulaire, session). Un firewall est le moyen de découper les URL en zones qui s'authentifient chacune à leur façon.
  • Le piège de fond. Un seul firewall traite une Request : le premier dont le matcher correspond. Ce n'est pas « le plus précis », et ce n'est pas une combinaison.
  • Ce que l'auteur veut que vous compreniez. Le firewall répond à « comment on s'authentifie ici ? » ; ce n'est pas lui qui décide des droits sur l'article.
  • Pourquoi c'est à l'examen. Questions fréquentes : ordre des firewalls, methods seul, context, stateless, lazy, security: false.

Un firewall découpe les URL en zones qui s'authentifient chacune à leur façon : outils de développement, API sans session, site avec form. Un seul firewall traite une Request : le premier dont le matcher correspond.

Il s'agit du firewall applicatif de Symfony, pas d'un filtre réseau. Un matcher est un service qui répond si la requête correspond à ses critères. Au plus un firewall est sélectionné ; sans correspondance, cette sélection ne fournit aucun dispositif de sécurité.

Le schéma

À retenir en priorité
  1. La sélection s'arrête au premier match.
  2. L'API doit précéder le catch-all.

Où en est-on ? Carte du cours. Nous partons d'une Request qui arrive et nous suivons ses embranchements : sélection du firewall, puis options du firewall retenu (security: false, stateless, lazy). Chaque case sera détaillée dans une partie dédiée.

Suivre d'abord la sélection, puis lire les options du firewall retenu. La déclaration de ces services est préparée avec le container ; les matchers sont utilisés pendant la requête, pas reconstruits par compilation à chaque fois.

Bleu : progression ; ambre : choix ; vert : effet. Vue de configuration, pas ordre exhaustif des listeners. Un request_matcher explicite peut remplacer les critères usuels. « Attrape tout » suppose donc l'absence de matcher, pas seulement l'absence de pattern. Le firewall ne garantit pas que la route existe ni que son controller autorise l'opération.

Un seul firewall par Request

À retenir en priorité
  1. Le path est un critère possible.
  2. Le matcher définit la zone réelle.

Où en est-on ? Étape 1 sur 4 : le principe de sélection. Question posée : quand plusieurs firewalls sont déclarés, lequel reçoit la Request, et que se passe-t-il pour ceux qui suivent ?

🌍 In Real Life

La situation : l'accueil oriente une demande vers le premier guichet dont les critères conviennent. Un guichet « toutes demandes » placé devant les spécialistes les masque.

L’équivalent dans Symfony : critères du guichet → matcher ; première affectation → firewall sélectionné ; guichet général → entrée sans matcher effectif.

Retour à la réalité technique : pour /blog/42 comme pour sa variante API, la sélection dépend de la Request et de l'ordre configuré, pas du nom du firewall. Choisir un firewall ne crée ni route ni permission.

🧠 Comment le mémoriser : « Premier guichet compatible, pas meilleur guichet imaginable. » Image mentale : demande arrêtée au premier comptoir ouvert. Question-réflexe : une entrée précédente capture-t-elle déjà cette requête ?

⚠️ À ne pas confondre : matcher de firewall et reconnaissance de route.

  • Les firewalls sont essayés dans l'ordre de déclaration ; le premier qui correspond prend la Request, les autres ne sont jamais consultés.
  • Un firewall sans matcher correspond à tout : il se déclare en dernier. Placé en premier, il capte tout, sans erreur.
  • Un firewall peut aussi se choisir par host.
  • Un request_matcher personnalisé est prioritaire et décide lui-même de la correspondance : l'absence de pattern ne suffit donc jamais à conclure « catch-all ».
  • methods n'entre dans le matcher qu'avec un pattern ou un host : un firewall qui ne déclare que methods: [POST] attrape aussi les GET.
  • $security->getFirewallConfig($request)?->getName() permet d'inspecter le firewall correspondant ; getFirewallConfig() peut rendre null si aucun n'est trouvé. La forme sans ?-> suppose une correspondance.

Pourquoi methods seul ne filtre-t-il pas ? Dans createFirewall(), le matcher n'est construit que lorsqu'un pattern ou un host existe ; les methods sont ensuite ajoutés à ce matcher. Sans l'un des deux, il n'y a pas de matcher du tout.

firewalls:                      GET /fw  →  quel firewall ?
  post: { methods: [POST] }     →  post   (aucun matcher construit : prend tout)
  main: ~

firewalls:                      GET /fw  →  main
  post: { pattern: ^/, methods: [POST] }   (matcher construit, GET refusé)
  main: ~

Un firewall décide comment on s'authentifie ; access_control décide ce qu'il faut pour entrer, et c'est le firewall qui l'applique.

Ce qu'un firewall porte

À retenir en priorité
  1. Le firewall assemble l'authentication de sa zone.
  2. Les règles d'accès restent une décision distincte.
  3. switch_user appartient au firewall.
  4. _exit restaure l'identité d'origine ; IS_IMPERSONATOR décrit l'état.
  5. stateless concerne l'authentication en session du firewall, pas une interdiction générale des cookies applicatifs.

Où en est-on ? Étape 2 sur 4 : le firewall est choisi. Que contient-il exactement ? On regarde ses services, puis la notion de contexte (où est rangée l'identité) et ce qui arrive quand on a plusieurs firewalls.

🌍 In Real Life

La situation : deux accueils du blog disposent de leurs procédures et de leurs registres. Ils peuvent convenir de consulter le même registre sans devenir un seul accueil.

L’équivalent dans Symfony : procédures locales → authenticators et autres services du firewall ; registre de contexte → clé de session ; registre partagé → même context configuré.

Retour à la réalité technique : partager le contexte suppose des firewalls avec état et des configurations compatibles. Cela ne fusionne pas les authenticators, ne dispense pas de refresh et n'accorde pas les mêmes droits sur toutes les ressources.

🧠 Comment le mémoriser : « Registre partagé, procédures distinctes. » Image mentale : deux guichets reliés à un même classeur. Question-réflexe : est-ce le contexte ou le nom du firewall que cette option attend ?

⚠️ À ne pas confondre : partage du contexte de sécurité et sélection de plusieurs firewalls pour une requête.

Une fois main choisi pour l'article, ce sont ses services qui déterminent la connexion et l'entrée en authentification. api ne lui prête pas ses authenticators parce que les deux servent le même catalogue.

  • ses authenticators, son provider, son entry point, son user checker ;
  • son caractère stateless ou non ;
  • l'AccessListener, qui applique access_control.

Chaque firewall a son propre contexte de session : se connecter sur main ne connecte pas sur admin. Avec context: shared sur les deux, alice connectée sur main est reconnue sur /admin/whoami. Dans un test, le second argument de loginUser() est ce contexte, pas le nom du firewall.

Pourquoi se reconnecter sur /admin ? Le token est rangé en session sous une clé dérivée du contexte ; par défaut, le contexte porte le nom du firewall ($firewall['context'] ?? $id). Deux noms, deux clés, deux « classeurs ».

Sans context commun                 Avec context: shared (sur les deux)
┌──────────────┐ ┌──────────────┐   ┌──────────────┐ ┌──────────────┐
│ firewall main│ │ firewall admin│  │ firewall main│ │ firewall admin│
│ clé: main    │ │ clé: admin   │   │ clé: shared  │ │ clé: shared  │
└──────────────┘ └──────────────┘   └──────┬───────┘ └──────┬───────┘
 deux tokens distincts                      └──── même token ┘

Sans état (stateless: true), le firewall ne persiste pas le token en session. D'autres services peuvent encore poser des cookies ; leur présence seule ne prouve pas qu'un autre firewall a été sélectionné.

Le partage par context concerne des firewalls avec état et des providers capables de restaurer le user concerné. Dans un test, loginUser($alice, 'shared') vise ce contexte ; il ne teste pas le formulaire de connexion et ne donne aucun rôle supplémentaire à Alice.

L'impersonation se configure avec switch_user sur le firewall. Par défaut, ROLE_ALLOWED_TO_SWITCH autorise la demande ?_switch_user=<identifier> ; ?_switch_user=_exit restaure l'identité d'origine. IS_IMPERSONATOR teste cet état, ce n'est pas un rôle à ajouter à l'utilisateur ciblé. Réserver cette capacité aux personnes habilitées et à un besoin d'assistance contrôlé, pas à une connexion publique.

`lazy`

À retenir en priorité
  1. Une page sans accès au user évite ce travail.
  2. Lire le user déclenche la restauration.

Où en est-on ? Étape 3 sur 4 : on sait que le firewall stocke l'identité en session. Question : faut-il la recharger à chaque requête, même pour une page publique qui ne l'utilise pas ? lazy répond « seulement si on en a besoin ».

🌍 In Real Life

La situation : pour remettre le menu public, l'accueil n'ouvre pas le dossier personnel du visiteur. Il l'ouvre si le service demandé exige de connaître son identité.

L’équivalent dans Symfony : dossier non consulté → contexte stateful différé ; question sur l'identité → utilisation de la sécurité pouvant initialiser le contexte ; menu → lecture publique de /blog/42.

Retour à la réalité technique : lazy diffère ce travail lorsque rien d'autre ne le force. Une authentification effectivement prise en charge reste active ; une consultation du user peut déclencher le refresh. Aucun en-tête de cache public n'est garanti.

🧠 Comment le mémoriser : « Ouvrir le dossier au besoin. » Image mentale : classeur fermé à côté du menu. Question-réflexe : mon rendu consulte-t-il inutilement l'identité ?

⚠️ À ne pas confondre : sécurité différée et sécurité désactivée.

lazy: true diffère l'initialisation du contexte avec état jusqu'à ce que la sécurité soit requise. Pour une requête avec un token de session restaurable, sans autre mécanisme qui force ce travail, /blog/42 peut éviter le refresh si son rendu ne consulte pas le user. Ajouter getUser() ou un contrôle de sécurité peut déclencher ce travail. Un formulaire de connexion effectivement pris en charge ne devient pas inactif parce que son contrôleur ne lit pas le user.

Éviter l'ouverture de session peut préserver les conditions de mise en cache ; lazy ne rend pas automatiquement la réponse publique et ne fixe pas max-age. L'observation historique P10 rapportait le même Cache-Control dans les deux modes et un appel au provider évité ; ce n'est ni une mesure P11 ni une garantie générale de performance.

lazy est ignoré sur un firewall stateless : le contexte est un LazyFirewallContext avec état, un FirewallContext ordinaire sans état.

page qui NE lit PAS le user   →  provider non appelé (pas de refreshUser)
page qui lit getUser()        →  ContextListener::refreshUser(alice)
                                 → provider appelé, à la demande

firewall stateless: true      →  lazy ignoré (FirewallContext ordinaire)

`security: false`

À retenir en priorité
  1. Ce réglage coupe l'authentication et l'accès.
  2. Il n'est pas équivalent à PUBLIC_ACCESS.

Où en est-on ? Étape 4 sur 4 : le cas extrême du firewall, celui qui ne fait rien. Question : à quoi sert-il, et pourquoi ne pas l'employer pour « rendre une page publique » ?

Ce firewall n'a aucun listener : ni authentication, ni AccessListener. Une règle access_control sur ses URL est morte. Réservé aux outils de développement et aux files statiques.

Pour laisser lire l'article en conservant une identité éventuelle, préférer une politique publique adaptée plutôt que supprimer ce traitement. PUBLIC_ACCESS ne supprime pas le firewall. Un contrôleur ou une autre couche peut encore refuser indépendamment ; « aucun listener de ce firewall » ne signifie pas « toute réponse sera 200 ». Le profiler doit rester absent de l'exposition publique de production.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Chaque contexte reste indépendant.
  2. Un context commun est nécessaire pour partager.
  • Voir l’explication : Un seul firewall s'applique

    Un seul firewall s'applique, le premier qui correspond ; les autres sont ignorés. Pourquoi on se trompe : on transpose le routage, où l'on pense à une spécificité croissante.

  • Voir l’explication : Un firewall sans matcher attrape tout

    Un firewall sans matcher attrape tout et se déclare en dernier. Pourquoi on se trompe : on lit « pas de pattern » comme « inactif ».

  • Voir l’explication : Deux firewalls n'échangent pas leur authentication

    Deux firewalls n'échangent pas leur authentication sans context commun. Pourquoi on se trompe : on pense que la session est unique, alors que la clé de session dépend du contexte.

  • Voir l’explication : security: false désactive aussi access_control

    security: false désactive aussi access_control pour ses URL. Pourquoi on se trompe : on imagine access_control comme un filtre indépendant.

  • Voir l’explication : lazy épargne le rechargement du user

    lazy épargne le rechargement du user sur les pages qui ne s'en servent pas, si rien d'autre ne force l'initialisation — et la création du contexte lazy est ignorée sur un firewall stateless. Pourquoi on se trompe : « lazy » fait croire à une désactivation ; l'identité reste disponible à la demande.

Fiche express

À mémoriser

À retenir en priorité
  1. Le token de test doit viser le bon contexte.
  2. Ce n'est pas toujours le nom du firewall.

Le bon firewall est identifié ; il reste à vérifier la première règle d'accès, puis le droit sur l'article lui-même. Une bonne sélection n'est pas encore une autorisation.

🧠 À retenir pour la certification :

  • Un seul firewall par Request : le premier qui correspond.
  • Sans matcher : attrape tout, en dernier.
  • methods seul ne forme pas de matcher.
  • Chaque firewall a son contexte dans la session ; context commun pour partager.
  • stateless: true : pas de token de sécurité persisté en session par ce firewall.
  • lazy diffère le rechargement du user ; ignoré si stateless.
  • security: false : aucun listener, access_control mort.

Moyen mnémotechnique : « Premier matcher correspondant ; contexte partagé avec état ».

firewalls dans l'ordre, premier matcher gagne ; sans matcher = tout, en dernier ;
contexte propre dans la session ; context partagé si stateful ;
stateless = pas de token persistant ; lazy ignoré si stateless
