Objectif

Vous ouvrez un template Twig pour la première fois : des accolades partout, des points, des ~, des ??. Pour lire (et écrire) ce langage, il faut répondre à trois questions : que fait chaque type d'accolade, comment Twig lit article.title (un point n'est pas un ->), et quels opérateurs il connaît — proches de PHP, mais pas identiques. Tout le reste du module Twig repose sur ce socle.

Maîtriser la syntaxe de base de Twig 3.22 : les trois délimiteurs, la façon dont foo.bar est résolu, et le jeu d'operators. C'est le socle des treize autres items du module.

La version compte : le syllabus dit « Twig syntax up to 3.22 version ». Ce qu'une version ultérieure a ajouté est hors périmètre.

L'essentiel

À comprendre

À retenir en priorité
  1. L'accès array est prioritaire.
  2. Methods et getters arrivent après les accès directs.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un langage de template doit distinguer ce qu'on affiche, ce qu'on exécute et ce qu'on commente.
  • Le piège de fond. foo.bar n'est pas $foo->bar : c'est une recherche ordonnée, et la première réponse gagne. Les opérateurs ressemblent à PHP mais divergent (~, and, ?? vs ?:).
  • Ce que l'auteur veut que vous compreniez. L'ordre exact (array, property, constante, méthodes, __call) et les cas limites des opérateurs.
  • Pourquoi c'est à l'examen. Les QCM testent //, la constante qui masque le getter, attribute() déprécié sans notice, et ?: contre ?? sur 0.

Trois choses à savoir : quel délimiteur fait quoi, dans quel ordre Twig cherche foo.bar, et quels operators il comprend — proches de ceux de PHP, mais pas identiques.

{{ expression }}   AFFICHE
{% instruction %}  EXÉCUTE
{# note #}         COMMENTE
foo.bar            recherche ordonnée (pas un simple ->)
~  concatène       +  additionne  ?: teste la vérité     ?? teste l'existence

Le schéma

Où en est-on ? Vue d'ensemble de la partie la plus subtile du cours : la résolution de foo.bar. On lit le schéma comme une liste de questions posées dans l'ordre ; la première réponse « oui » arrête la recherche.

L'ordre que suit CoreExtension::getAttribute() pour {{ foo.bar }} :

{{ foo.bar }}
   ▼
1. foo est array / ArrayObject / ArrayAccess avec la clé « bar » ?  → foo['bar']
2. propriété publique (ou magie __isset/__get) « bar » ?             → foo->bar
3. constante de classe « bar » (casse exacte) ?                      → Foo::bar
4. méthode bar() / getBar() / isBar() / hasBar() (casse ignorée) ?   → l'appel
5. __call() déclaré ?                                                → __call('bar')
6. rien                                                             → null / erreur

Ambre = recherche, bleu = valeur choisie. Ce chemin simplifié suppose un accès ordinaire, hors sandbox ; les contrôles d'accès peuvent refuser une property ou une method. Les properties accessibles par magie PHP (__isset/__get) et certains cas spéciaux, comme DateTime, complètent la branche « property ». Les étapes ne s'exécutent pas toutes : le premier résultat arrête la recherche.

L'exemple

Exemple concret

À retenir en priorité
  1. Les doubles accolades affichent.
  2. Les tags et commentaires ont des délimiteurs distincts.

Où en est-on ? Un template réel qui utilise les trois délimiteurs, la résolution d'attributs et plusieurs opérateurs. Chaque ligne sera expliquée dans les sections suivantes.

Dans le blog, le même contrat commence par une variable article fournie au rendu et {{ article.title }} pour son titre. L'exemple de commande ci-dessous conserve un cas plus riche : il exige que order et ses données existent dans le contexte. Twig ne les charge pas depuis une route.

{% set total = order.amount * 1.2 %}
<h1>Commande {{ order.reference ~ ' — ' ~ order.status }}</h1>
{% if order.paid and order.items has some item => item.qty > 1 %}
    <p>{{ order.customer.nickname ?? 'client' }}, total {{ total }} €</p>
{% endif %}
{% set total = … %}                 → instruction : prépare une variable
{{ order.reference ~ ' — ' ~ … }}   → affiche un texte concaténé (~)
{% if … and … has some … %}         → instruction : condition (and, has some)
{{ order.customer.nickname ?? … }}  → affiche, avec un repli si absent

Les trois délimiteurs

Où en est-on ? Étape 1 sur 4 : les trois types d'accolades. C'est la base : sans elle, on ne sait pas si une ligne écrit, décide ou note.

Pour afficher le titre d'ArticleView, les doubles accolades évaluent puis écrivent une valeur, avec l'échappement configuré. Un if décide si une portion sera rendue ; un commentaire documente le template sans devenir un commentaire HTML visible. Aucun de ces délimiteurs n'envoie la Response.

Délimiteur Role
{{ … }} affiche le résultat d'une expression
{% … %} exécute une instruction : if, for, extends, set
{# … #} commentaire, jamais rendu

Pourquoi trois ? Ils répondent à trois besoins distincts : produire de la sortie ({{ }}), contrôler le déroulement ({% %}), documenter la source ({# #}). Un commentaire Twig n'arrive jamais dans le HTML, contrairement à <!-- … -->, que le visiteur peut lire en affichant la source de la page.

{# note interne #}      → absent du HTML livré
<!-- note visible -->   → présent dans le HTML (visible via « afficher la source »)

Nuance : {% include %} est une instruction, et pourtant elle produit du contenu. La règle « {% %} n'écrit rien » est donc fausse ; la vraie règle est que {% %} exécute une opération qui peut ou non écrire.

🌍 In Real Life

La situation : une maquette d'imprimerie distingue le texte à inscrire, les consignes de composition et les notes internes qui ne figurent pas sur l'exemplaire livré.

L’équivalent dans Symfony : dans Twig, {{ … }} évalue et écrit une expression ; {% … %} porte une instruction ; {# … #} conserve un commentaire dans la source sans l'inclure au rendu.

Retour à la réalité technique : certaines instructions, comme include, produisent aussi du contenu. L'échappement configuré intervient sur les sorties concernées ; la syntaxe n'autorise pas à considérer toute donnée comme sûre dans tout contexte. Rendre un template n'est pas envoyer la Response.

🧠 Comment le mémoriser : « Texte livré, consigne d'atelier, note interne. » Image mentale : trois couleurs sur une maquette, une seule pour les notes non imprimées. Question-réflexe : veux-je écrire une valeur, piloter le rendu ou documenter la source ?

⚠️ À ne pas confondre : commentaire Twig non rendu et commentaire HTML présent dans le document.

Dans un script de théâtre, les expressions affichées sont les répliques ; les tags organisent l'action ; les commentaires sont les notes privées. Certains tags rendent du contenu, mais ce ne sont pas des expressions affichées par doubles accolades.

`foo.bar` : l'ordre de résolution

Où en est-on ? Étape 2 sur 4 : le point .. En PHP, $a->b et $a['b'] sont deux syntaxes. En Twig, une seule (a.b) : Twig devine laquelle convient. Comment ? Par une recherche ordonnée.

article.title n'est pas une traduction littérale de PHP $article->title. Selon l'objet fourni, une propriété publique ou une méthode peut fournir la valeur ; un objet ArrayAccess peut même satisfaire la recherche avant la propriété. Stabiliser ArticleView évite que l'affichage dépende involontairement de ces formes concurrentes.

Pour {{ foo.bar }}, Twig essaie dans cet ordre :

  1. $foo['bar'] — array, ArrayObject ou ArrayAccess ;
  2. $foo->bar — property accessible, publique ou via la magie PHP prise en charge ;
  3. Foo::bar — constante de class, dont le nom correspond à la casse près ;
  4. bar(), getBar(), isBar(), hasBar() — methods, casse ignorée ; un hasser est écarté quand un isser du même nom existe ;
  5. __call('bar'), si la class le déclare ;
  6. sinon null — ou une RuntimeError avec strict_variables.

Conséquences : l'array passe avant l'object (un ArrayAccess gagne sur la property) ; const STATUS ne masque pas getStatus(), mais const status le masque. La documentation Symfony énumère sept étapes sans la constant ; l'engine 3.22 l'implémente — un énoncé d'examen peut n'en citer que sept.

  • {{ foo.bar() }} force l'appel d'une method.
  • Nom dynamique ou avec un tiret : {{ user.(name) }}, {{ user.('first-name') }} (3.15).
  • attribute() est dépréciée depuis 3.15, mais en 3.22 elle fonctionne sans notice de deprecation.

À propos de la constante : le nom est comparé exactement, majuscules et minuscules comprises (PHP traite STATUS et status comme deux constantes différentes). C'est pourquoi const status (minuscules) attrape o.status alors que const STATUS (majuscules) laisse passer jusqu'au getter. À l'inverse, les méthodes sont cherchées sans tenir compte de la casse.

Exemple pas à pas, avec une classe qui déclare const status = 'CONST' et getStatus() qui retourne 'GETTER' :

{{ o.status }}
   ▼
1. o est un array/ArrayAccess ? non
2. propriété publique « status » ? non
3. constante « status » (casse exacte) ? OUI → 'CONST'      ← recherche arrêtée
   (getStatus() n'est jamais appelé)

avec const STATUS (majuscules) :
3. constante « status » ? non (STATUS ≠ status)
4. méthode getStatus() ? OUI → 'GETTER'

Pourquoi l'ordre compte : une même classe peut offrir plusieurs façons de fournir bar. Savoir quelle gagne explique des affichages « inexplicables » (le template montre une valeur qui n'est pas celle du getter).

Expression Force Pourquoi
foo.bar recherche ordonnée Twig choisit
foo.bar() appel de méthode les parenthèses imposent la méthode
foo.(name) nom dynamique (3.15) le nom vient d'une variable
foo.('first-name') nom avec tiret (3.15) foo.first-name serait une soustraction

🌍 In Real Life

La situation : pour connaître le titre d'un dossier, l'archiviste suit une procédure : case indexée, fiche accessible, mention fixe, puis interlocuteurs prévus. La première réponse trouvée évite d'interroger les suivants.

L’équivalent dans Symfony : foo.bar suit l'ordre d'accès de Twig 3.22 : clé, propriété accessible, constante au nom exact, méthodes puis éventuel __call. Une clé ArrayAccess peut donc devancer un getter.

Retour à la réalité technique : la recherche dépend du type reçu, de l'accessibilité et des règles de sandbox éventuelles. Une constante respecte la casse ; les méthodes sont recherchées sans cette distinction. L'accès peut exécuter du code PHP et lever : ce n'est pas une simple lecture de champ ni un chargement automatique depuis Routing.

🧠 Comment le mémoriser : « La première source répondante arrête la tournée. » Image mentale : archiviste quittant la liste dès qu'une case fournit le titre. Question-réflexe : quelle branche fournit réellement cette valeur sur cet objet ?

⚠️ À ne pas confondre : attribut Twig, propriété PHP et attribute de Request ; foo.bar() demande un accès méthode.

L’operator ?: remplace une valeur fausse, tandis que ?? remplace une valeur absente ou null. Une variable absente déclenche strict_variables avec ?:, mais pas avec ??.

Les operators

À retenir en priorité
  1. ~ concatène les strings.
  2. + effectue une addition et peut échouer sur des strings non numériques.

Où en est-on ? Étape 3 sur 4 : les opérateurs. Beaucoup ressemblent à PHP, mais quelques-uns n'existent pas (&&), d'autres ont un sens différent (~, //). Cette section est celle qui donne le plus de points à l'examen.

Le libellé 'Article ' ~ article.id concatène du texte ; remplacer ~ par + demande une opération arithmétique. Pour un compteur de commentaires, zéro est au contraire une valeur utile : ?? peut conserver ce zéro là où ?: choisirait le repli. Choisis selon la signification de l'absence, pas seulement selon l'apparence du résultat.

Famille Operators
Arithmétique + - * / % // **
Comparaison == != < > <= >= <=>
Logique and or not xor — pas && \|\| ! ; bit à bit : b-and b-or b-xor
Strings ~ concatène ; starts with, ends with, matches
Appartenance in, not in (aussi dans une string) ; .. construit une plage
Itérables has some, has every, avec une function fléchée
Test is : defined, empty, null, iterable, same as
Confort ?: (Elvis), ?? (coalescence)
Functions => function fléchée ; ... étend une séquence (3.7) ou des arguments (3.15)

Ce qui tombe à l'examen :

  • {{ 'a' + 'b' }} casse le rendu : + additionne, PHP 8.4 refuse deux strings non numériques, et Twig remonte la TypeError dans une RuntimeError ;
  • // est la division entière et arrondit vers le bas : -7 // 2 vaut -4 ;
  • ** s'associe à droite : 2 ** 3 ** 2 vaut 512 ;
  • ?: remplace une valeur fausse (0, ''), ?? une valeur absente ou null ; sur une variable absente, ?: déclenche strict_variables, ?? non ;
  • sur un itérable vide, has every vaut true, has some vaut false ;
  • true && false ne compile pas.

Pourquoi -7 // 2 vaut -4 : -7 / 2 = -3,5 ; arrondir vers le bas (le plancher) donne -4, pas -3 (qui serait un arrondi vers zéro).

-7 / 2   = -3,5
-7 // 2  = plancher(-3,5) = -4        (PAS -3 : ce n'est pas vers zéro)
2 ** 3 ** 2 = 2 ** (3 ** 2) = 2 ** 9 = 512     (droite → gauche)

Comparaison ?: et ?? pour une variable zero = 0 :

{{ zero ?: 'E' }}   → 0 est « faux »      → 'E'
{{ zero ?? 'C' }}   → 0 existe, non null  → 0
variable absente :  ?:  déclenche strict_variables ;  ??  non
?: (Elvis) ?? (coalescence)
Remplace si… valeur fausse (0, '', false, null) valeur absente ou null
0 remplacé conservé
Variable inexistante (strict) erreur pas d'erreur

Pourquoi has every est vrai sur une liste vide : il n'existe aucun élément qui contredise la condition (principe de la logique : « tous les éléments d'un ensemble vide » est vrai). has some demande un élément qui la satisfasse : il n'y en a pas, donc faux.

Pourquoi 'a' + 'b' casse : + est arithmétique uniquement. Contrairement à JavaScript, il ne concatène jamais. Pour joindre du texte, c'est ~.

🌍 In Real Life

La situation : préparer une étiquette « Article 42 », additionner des quantités et remplacer une case non renseignée sont trois tâches différentes. Un compteur à zéro est renseigné, même si sa valeur ne déclenche pas une condition vraie.

L’équivalent dans Symfony : ~ assemble le texte, + calcule, ?: choisit selon la vérité et ?? selon l'absence ou null. Pour une liste, has some cherche un témoin satisfaisant le prédicat ; has every cherche à vérifier tous ses éléments.

Retour à la réalité technique : sur liste vide, aucun témoin n'existe, mais aucun contre-exemple non plus : has some est faux et has every vrai. ?? conserve zéro et false ; ?: peut lever sur une variable absente en mode strict. Les autres opérateurs conservent leurs règles propres : // prend le plancher, ** s'associe à droite ; parenthéser clarifie les calculs.

🧠 Comment le mémoriser : « Zéro renseigné n'est pas une case vide. » Image mentale : compteur marqué 0 à côté d'une case inconnue, puis liste sans témoin ni contre-exemple. Question-réflexe : ai-je besoin de texte, d'arithmétique, de vérité ou d'un test d'absence ?

⚠️ À ne pas confondre : syntaxe Twig et PHP ; logique and/or/not, opérations bit à bit et tests ne sont pas interchangeables.

Affectation et espaces

À retenir en priorité
  1. Le contrôle - retire tous les blancs du côté concerné.
  2. Le contrôle ~ conserve les sauts de ligne.

Où en est-on ? Étape 4 sur 4 : stocker une valeur (set) et contrôler les espaces blancs autour des tags. Peu de théorie, mais un piège : deux caractères (- et ~) qui ne font pas la même chose.

Un set prépare une valeur dans le contexte du rendu, sans modifier ArticleCatalog. La capture prépare du contenu à réutiliser ; elle ne crée ni block d'héritage ni réponse HTTP. Enfin, retirer les espaces près de deux liens peut coller leurs libellés : contrôle le texte obtenu autant que l'indentation du fichier Twig.

{% set total = 0 %} déclare une variable ; {% set body %}…{% endset %} capture un block.

Twig retire d'office le premier saut de ligne qui suit un tag. Ensuite :

  • - ({{-, -}}, {%-, -%}) supprime tout le blanc de ce côté ;
  • ~ le supprime sauf les sauts de ligne.

Le filter spaceless est déprécié depuis 3.12, et lui émet une notice.

Exemple de contrôle des blancs :

<a>Un</a>
{{- ' ' -}}
<a>Deux</a>
   ▼
<a>Un</a> <a>Deux</a>      (les blancs de part et d'autre du tag ont disparu)
Marqueur Effet de son côté Sauts de ligne
aucun blancs conservés (sauf le 1er saut de ligne après un tag) conservés
- supprime tout le blanc supprimés
~ supprime les blancs préservés

Attention : le ~ du contrôle des blancs (collé à un délimiteur) n'est pas le ~ de concaténation (au milieu d'une expression).

Pourquoi retirer les blancs peut être risqué : deux liens séparés par un retour à la ligne s'affichent avec un espace ; si on supprime ce blanc, leurs libellés se collent (UnDeux).

🌍 In Real Life

La situation : le maquettiste garde un calcul sur une note de travail ou réserve un fragment déjà composé. Il peut aussi rogner les marges, au risque de coller deux mots qui devaient rester séparés.

L’équivalent dans Symfony : set affecte une variable du contexte ; sa forme par capture conserve le contenu rendu. Les marqueurs de blanc accolés aux délimiteurs retirent les espaces du côté concerné : - inclut les sauts de ligne, ~ les préserve.

Retour à la réalité technique : l'affectation seule ne persiste rien dans ArticleCatalog et la capture n'est ni un bloc d'héritage ni une Response. Le ~ de contrôle des blancs n'est pas l'opérateur de concaténation à l'intérieur d'une expression. Réduire les blancs ne garantit pas un HTML visuellement équivalent ; spaceless est déprécié dans le périmètre 3.22.

🧠 Comment le mémoriser : « Préparer un fragment, rogner avec prudence. » Image mentale : fragment mis de côté et marge découpée entre deux libellés. Question-réflexe : ai-je changé une valeur, capturé une sortie ou supprimé un séparateur visible ?

⚠️ À ne pas confondre : variable de rendu, bloc Twig et modification persistante de données.

Pièges d'examen

Piège à éviter

Voir l’explication : array
  • {{ }} affiche une expression ; {% %} porte une instruction, dont certaines produisent aussi du contenu (include, par exemple). Pourquoi on se trompe : on retient « {% %} n'écrit rien ».
  • L'ordre de résolution commence par l'array, pas par la property. Pourquoi on se trompe : le réflexe PHP est de lire d'abord ->.
  • Une constante de class est lue avant le getter si son nom est identique, casse comprise : const STATUS ne masque pas getStatus(). Pourquoi on se trompe : on suppose que les méthodes passent toujours avant les constantes.
  • and / or / not, jamais && / || / !. Pourquoi on se trompe : habitude PHP.
  • ~ concatène ; + additionne. Pourquoi on se trompe : habitude JavaScript.
  • Sans strict_variables, une variable inconnue vaut null silencieusement. Pourquoi on se trompe : on s'attend à une erreur.
  • attribute() (3.15) et spaceless (3.12) sont dépréciés en 3.22. Pourquoi on se trompe : on croit que « déprécié » signifie « notice affichée » ; attribute() n'en émet pas.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • {{ }} affiche, {% %} exécute, {# #} commente.
  • foo.bar : array, property, constante à la casse exacte, methods sans casse, __call.
  • Rien trouvé : null, ou RuntimeError avec strict_variables.
  • ~ concatène ; + additionne et échoue sur des strings non numériques.
  • // arrondit vers le bas ; ** s'associe à droite.
  • ?: teste la vérité, ?? l'existence.
  • has every sur vide : vrai ; has some : faux.
  • attribute() dépréciée sans notice ; spaceless dépréciée avec.

Moyen mnémotechnique : « array d'abord, constante exacte, method sans casse ».

{{ }} affiche, {% %} exécute ; foo.bar = [key] > prop > CONST exacte >
méthode/get/is/has (sans casse) > __call > null|erreur ;
~ concatène, // plancher, ** à droite, ?: vérité, ?? existence, and/or/not ;
- et ~ pour les blancs
