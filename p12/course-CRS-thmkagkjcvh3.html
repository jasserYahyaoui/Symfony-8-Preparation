Objectif

Savoir de quel côté un cookie se lit et de quel côté il s'écrit dans un controller. Les attributes de sécurité — SameSite, Secure, HttpOnly — et la constraint de suppression sont traités dans le Module 02 — Fondamentaux HTTP.

Question fil rouge : le visiteur choisit le thème sombre. Dans mon contrôleur, où lis-je son ancien choix, où écris-je le nouveau, et comment lui faire oublier un cookie ?

L'essentiel

À comprendre

À retenir en priorité
  1. La Request contient ce que le client a envoyé.
  2. La Response contient les instructions Set-Cookie.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. HTTP est sans mémoire (voir The request). Le cookie est le moyen pour le serveur de demander au navigateur de « se souvenir » d'une petite valeur, que le navigateur renverra à chaque requête suivante. C'est aussi le support du cookie de session (The session).
  • Le piège de fond. Request et Response sont deux objets serveur à sens unique : l'un décrit ce qui est arrivé, l'autre ce qu'on demande d'enregistrer. Modifier l'un ne touche pas le navigateur.
  • Ce que l'auteur veut que vous compreniez. Lire sur la Request, écrire sur la Response, et la différence entre removeCookie() (annule un envoi) et clearCookie() (efface chez le client).
  • Pourquoi c'est à l'examen. Les noms voisins removeCookie / clearCookie, l'index domain → path → nom, et le format de getCookies().

En résumé : un cookie se lit sur la Request — c'est ce que le client a envoyé — et s'écrit sur la Response, dans le header Set-Cookie. Un controller qui veut poser un cookie doit donc tenir la Response. Deux methods aux noms voisins font le contraire l'une de l'autre : removeCookie() annule un envoi, clearCookie() efface chez le client.

Le schéma

Où en est-on ? Le cours suit trois étapes : l'exemple (poser un cookie), deux objets, deux sens (lire / écrire), puis la conséquence pratique (supprimer sans se tromper). Le schéma résume les quatre gestes.

            SERVEUR                                   NAVIGATEUR
 Request  ── lire ── cookies->get('theme')  ◄── Cookie: theme=dark ──┐
 Response ── écrire ─ setCookie(...)  ── Set-Cookie: theme=dark ───► │ stocke
 Response ── effacer ─ clearCookie('sid') ─ Set-Cookie: sid=deleted; │ expire
                                             expires=passé ────────► │ efface
 Response ── annuler ─ removeCookie('theme') → rien n'est envoyé     │

Bleu = représentation serveur ; ambre = stockage côté client. Le cycle suppose un navigateur qui accepte le cookie. clearCookie() doit viser le même domaine et chemin : effacer theme sur / ne retire pas celui de /admin. La Request déjà reçue ne change pas après l'ajout du cookie à la Response.

L'exemple : poser un cookie de préférence

Exemple concret

Où en est-on ? Un cas concret avant le détail : poser theme=dark sur la Response d'une page.

Le lecteur de /blog/42 choisit un thème sombre. L'action conserve la Response rendue pour lui ajouter une instruction destinée au navigateur ; la préférence ne reviendra dans Request::cookies que lors d'une requête ultérieure, si le client l'accepte. Cookie désigne ici Symfony\Component\HttpFoundation\Cookie.

$response = $this->render('page.html.twig');
$response->headers->setCookie(Cookie::create('theme', 'dark'));

return $response;

Pourquoi garder $response dans une variable ? Parce que render() retourne une Response (The response) : le cookie doit être posé sur cet objet avant de le retourner. return $this->render(...) direct ne laisserait aucune prise.

Visite 1 : GET /blog/42           → Response + Set-Cookie: theme=dark
Visite 2 : GET /blog/42           → Cookie: theme=dark
                                    $request->cookies->get('theme') = 'dark'
(pendant la visite 1, $request->cookies ne contient PAS encore theme)

Vérifié (Cookie 8.0) : Cookie::create($name, $value = null, $expire = 0, $path = '/', $domain = null, $secure = null, $httpOnly = true, $raw = false, $sameSite = 'lax', $partitioned = false) ; les valeurs par défaut sont donc déjà prudentes (HttpOnly, SameSite=Lax). Les détails de ces attributs relèvent du Module 02 — Fondamentaux HTTP.

🌍 In Real Life

La situation : l'accueil remet au lecteur une carte « préférence : ambiance sombre » pour sa prochaine visite. Il prépare cette carte avec les documents de sortie ; cela ne change pas rétroactivement ce que le visiteur avait présenté en arrivant.

L’équivalent dans Symfony : le contrôleur conserve la Response de render(), lui ajoute le cookie theme=dark, puis la retourne. Set-Cookie demandera au navigateur de mémoriser cette préférence lorsque la réponse sera envoyée.

Retour à la réalité technique : ajouter le cookie n'est pas l'envoyer immédiatement. Le client peut le refuser ; son retour dépendra d'une requête ultérieure et de la portée du cookie. Le HTML déjà rendu ne change pas simplement parce qu'un header a été ajouté.

🧠 Comment le mémoriser : « La préférence part avec la réponse, revient avec une autre demande. » Image mentale : carte remise à la sortie, représentée à la visite suivante. Question-réflexe : ai-je préparé une instruction ou observé son retour réel ?

⚠️ À ne pas confondre : préférence client, identité authentifiée et droit d'accès ; retourner la Response et l'envoyer.

Deux objects, deux sens

Où en est-on ? Étape 1 : qui lit, qui écrit ? Pourquoi deux objets : la Request est le passé (ce que le client a envoyé), la Response est le futur (ce que le serveur demande).

La Request contient déjà les cookies envoyés pour cette visite : modifier son sac ne réécrit pas le stockage du navigateur. Pour la prochaine visite du blog, c'est Set-Cookie dans la Response qui exprime le changement. Le tableau distingue donc l'état reçu de l'instruction de sortie, pas deux accès équivalents à une même variable partagée.

Opération Object Path
lire un cookie Request $request->cookies->get('nom')
écrire un cookie Response $response->headers->setCookie(...)
supprimer un cookie chez le client Response $response->headers->clearCookie('nom')
retirer un cookie de la Response Response $response->headers->removeCookie('nom') 
Request->cookies          Response->headers (ResponseHeaderBag)
 ├─ ce que le client        ├─ ce que le serveur DEMANDE d'enregistrer
 │  a déjà envoyé           └─ envoyé en Set-Cookie à l'envoi de la Response
 └─ lecture seule en         
    pratique : la modifier
    ne touche pas le navigateur

🌍 In Real Life

La situation : le bureau garde la copie du courrier reçu et prépare un courrier sortant. Corriger la copie reçue ne modifie pas les papiers conservés chez l'expéditeur.

L’équivalent dans Symfony : Request::cookies représente les valeurs reçues ; Response::headers porte les instructions Set-Cookie à émettre. Modifier le sac de la Request ne commande aucune écriture dans le navigateur.

Retour à la réalité technique : ce sont deux objets serveur aux rôles distincts, pas deux accès à un stockage partagé avec le client. Le cookie reçu reste une entrée client à interpréter avec prudence ; l'instruction de sortie reste soumise au traitement de la réponse et aux règles du navigateur.

🧠 Comment le mémoriser : « Le courrier reçu n'est pas la boîte aux lettres du client. » Image mentale : bac entrant et bac sortant séparés. Question-réflexe : veux-je lire l'état reçu ou demander un changement pour plus tard ?

⚠️ À ne pas confondre : mutation locale d'un objet Request et modification du stockage navigateur.

Le ticket de vestiaire reçu maintenant sera présenté lors d'une visite suivante. Un Set-Cookie dans la Response ne réécrit donc pas magiquement les cookies de la Request déjà reçue.

Conséquence pratique

À retenir en priorité
  1. Le header appartient au modèle Response.
  2. L'émission native contourne ce modèle.

Où en est-on ? Étape 2 : supprimer sans se tromper. Deux verbes voisins, deux effets opposés. La clé : un cookie déjà stocké chez le client ne disparaît que si on lui envoie une expiration.

Supposons que l'action ajoute theme=dark, puis décide de ne pas mémoriser la préférence. removeCookie() retire cette instruction encore locale ; il ne retire pas un ancien cookie déjà conservé par le navigateur. Pour oublier cet ancien thème, il faut au contraire envoyer son expiration avec clearCookie(), en visant le même domaine et chemin.

Le controller construit la Response, y attache le cookie, puis la retourne. La function PHP setcookie() marche au niveau du protocole, mais écrit le header hors de la Response : le cookie échappe aux listeners de kernel.response et aux functional tests qui inspectent la Response.

removeCookie() fait un unset dans le sac : aucun Set-Cookie ne part. clearCookie() appelle setCookie() avec une valeur nulle et une date d'expiration dans le passé : c'est un header envoyé. Les cookies sont rangés sur trois niveaux — domain, path, nom — d'où le path (/ par défaut) et le domain de removeCookie(). getCookies() rend une liste à plat, ou l'arborescence avec ResponseHeaderBag::COOKIES_ARRAY ; un autre format lève une InvalidArgumentException.

                       sac de la Response      header envoyé    navigateur
 setCookie(theme)         theme ajouté          Set-Cookie       stocke
 removeCookie(theme)      theme RETIRÉ          (rien)           inchangé
 clearCookie(theme)       theme expiré ajouté   Set-Cookie:      supprime
                                                theme=deleted;
                                                expires=passé

Vérifié dans ResponseHeaderBag (8.0) : setCookie() range le cookie dans $this->cookies[domain ?? ''][path][nom] ; clearCookie() fait setCookie(new Cookie($name, null, 1, $path, $domain, …)) — valeur nulle, expiration 1 (1970, donc dans le passé), path / par défaut ; getCookies() refuse tout format autre que COOKIES_FLAT ou COOKIES_ARRAY avec une InvalidArgumentException.

Exemple d'index : deux cookies t, l'un sur /, l'autre sur /admin :

cookies
 └─ '' (domaine absent)
      ├─ '/'       → t
      └─ '/admin'  → t        ← deux entrées, deux Set-Cookie
removeCookie('t')  → vise '/' par défaut : seul le premier est retiré

🌍 In Real Life

La situation : retirer un avis de l'enveloppe avant son départ n'annule pas une ancienne carte déjà chez le lecteur. Pour faire oublier cette ancienne carte, il faut lui envoyer une consigne d'expiration visant la bonne référence.

L’équivalent dans Symfony : removeCookie() retire l'instruction encore présente dans la Response ; clearCookie() y prépare un cookie expiré. Domaine, chemin et nom distinguent les entrées : viser theme sur / ne vise pas celui de /admin.

Retour à la réalité technique : ces méthodes ne pilotent pas directement le navigateur. La Response doit être envoyée et traitée côté client. Garder les cookies dans son ResponseHeaderBag, plutôt que recourir à setcookie() hors de cet objet, permet aux listeners et tests de les inspecter.

🧠 Comment le mémoriser : « Retirer l'avis, ou envoyer l'expiration ? » Image mentale : enveloppe vidée d'un côté, avis d'expiration adressé de l'autre. Question-réflexe : est-ce l'envoi en préparation ou le cookie déjà stocké que je veux supprimer ?

⚠️ À ne pas confondre : annuler une instruction locale et demander l'effacement distant ; nom identique et même portée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : avant

    Observe la Response avant son envoi pour tester l'instruction, puis une nouvelle Request pour observer ce que le client renvoie. Ces deux preuves ne sont pas interchangeables : une instruction correcte n'oblige pas le navigateur à accepter un cookie.

  • Voir l’explication : On lit un cookie sur la Request et on l'écrit sur la Response.

    On lit un cookie sur la Request et on l'écrit sur la Response. Poser un cookie sur l'object Request ne l'envoie nulle part : la Request est ce que le client a déjà envoyé. Pourquoi on se trompe : les deux objets ont un sac cookies/headers, on les croit symétriques.

  • Voir l’explication : removeCookie() ne supprime rien chez le client.

    removeCookie() ne supprime rien chez le client. Elle retire l'entrée du sac, donc le cookie n'est pas envoyé du tout. Pour faire oublier un cookie déjà posé, il faut en envoyer un — c'est clearCookie(). Pourquoi on se trompe : « remove » évoque la suppression côté client.

  • Voir l’explication : La fonction native de PHP fonctionne, et c'est le problème.

    La fonction native de PHP fonctionne, et c'est le problème. Elle écrit le header hors du modèle de Symfony : le cookie échappe aux listeners de kernel.response et n'apparaît pas dans un functional test qui inspecte la Response. Pourquoi on se trompe : « ça marche dans le navigateur », donc on pense que c'est correct.

  • Voir l’explication : Écrire via Symfony demande une Response.

    Écrire via Symfony demande une Response. Le contrôleur peut la conserver après render() ; un listener kernel.response peut aussi y attacher un cookie. Pourquoi on se trompe : on retourne directement $this->render() et on n'a plus de Response à manipuler.

Application

À retenir en priorité
  1. La Request contient ce que le client a envoyé.
  2. La Response contient les instructions Set-Cookie.
  3. Le header appartient au modèle Response.
  4. L'émission native contourne ce modèle.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Si tu dois retenir seulement 5 choses :

  • Lire sur la Request, écrire sur la Response.
  • setcookie() de PHP contourne la Response : à éviter.
  • clearCookie() envoie une expiration passée ; removeCookie() n'envoie rien.
  • Index domain → path → nom ; removeCookie() vise / par défaut.
  • getCookies() : à plat ou en array ; autre format → exception.

Moyen mnémotechnique : « Clear efface chez lui, remove annule chez moi ».

Phrase de mémorisation complète : « Je lis ce que le client m'a envoyé sur la Request, j'écris ce que je lui demande sur la Response ; clear envoie l'expiration, remove ne fait que retirer mon brouillon. »
