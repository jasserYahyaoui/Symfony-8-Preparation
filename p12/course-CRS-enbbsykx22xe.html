Objectif

Alice revient consulter l'article avec sa session, mais son compte a pu changer depuis sa connexion. Le provider relie l'identifiant à la source actuelle des utilisateurs : nous distinguons le chargement initial, le rafraîchissement et la décision d'abandonner un ancien contexte.

Question du cours : qui retrouve l'utilisateur à partir d'un identifiant, quand le relit-on, et que se passe-t-il quand il a changé ou disparu ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le provider charge et relit le user.
  2. supportsClass() décrit les classes prises en charge.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une session conserve une copie d'Alice. Entre deux requêtes, le compte réel peut changer : il faut une façon de le relire.
  • Le piège de fond. Le provider retrouve un user ; il ne vérifie ni son mot de passe ni son droit d'agir.
  • Ce que l'auteur veut que vous compreniez. Deux moments distincts : loadUserByIdentifier() (chargement) et refreshUser() (restauration d'un token de session sur un firewall avec état).
  • Pourquoi c'est à l'examen. Stateless contre stateful, user supprimé, rôles modifiés, chaîne de providers, choix du provider avec plusieurs sources.

Un user provider retrouve un objet utilisateur depuis un identifiant. Il répond à « quel utilisateur correspond à cet identifiant ? », pas à « son mot de passe est-il correct ? » ni à « a-t-il le droit d'agir ? ». Ces responsabilités appartiennent aux autres étapes de Security.

Lorsqu'un firewall avec état restaure un token de session, ContextListener demande au provider de rafraîchir l'utilisateur et vérifie s'il est toujours acceptable. Avec un firewall lazy, ce travail peut être différé jusqu'à l'utilisation de la sécurité. Il ne faut donc pas imaginer un chargement inconditionnel pour toute requête, même publique et sans token.

ArticleCatalog cherche l'article 42 ; le user provider cherche Alice. Ces deux recherches ne partagent ni le même contrat ni le même résultat : un article absent peut conduire à 404, un utilisateur absent fait échouer la résolution d'identité avant la décision d'accès.

 Provider           ne fait PAS                     fait
 ────────           ────────────────────────────    ──────────────────────
 retrouve Alice     vérifier son mot de passe       identifiant → UserInterface
                    décider si elle peut éditer     ou UserNotFoundException

Le schéma

À retenir en priorité
  1. La restauration déclenche une relecture.
  2. Un firewall stateless ne suit pas ce cycle de session.

Où en est-on ? Carte du cours, en deux graphes : le premier concerne la preuve présentée aujourd'hui (chargement), le second la relecture d'une identité gardée en session (refresh). Les séparer explique pourquoi une API stateless ne restaure pas le token d'une précédente lecture.

Bleu : acteurs ; ambre : condition ; vert : données ou résultat. Les flèches sont des appels et des retours, pas une relation d'héritage. Un UserBadge peut fournir son propre chargeur : le provider configuré n'est pas un passage obligatoire de toute forme d'authentification.

Ce parcours suppose un token restaurable. La comparaison par défaut vérifie notamment les rôles, le mot de passe et l'identifiant ; EquatableInterface permet au user de définir sa comparaison. Une déconnexion peut ensuite entraîner un 401 ou une redirection sur une ressource protégée, selon l'authentification configurée ; le provider ne décide pas lui-même du statut HTTP.

L'exemple

Exemple concret

À retenir en priorité
  1. Le contrat suffit pour un provider maison.
  2. Aucun stockage tiers n'est requis par ce contrat.

Où en est-on ? Un provider maison minimal. On y repère les trois méthodes du contrat et ce qu'elles rendent ou lèvent.

Extrait du contrat d'un provider maison : all() représente ici une méthode applicative qui lit une source de confiance et retourne les utilisateurs indexés par identifiant. pw contient un hash, jamais un mot de passe en clair. Les imports sont indiqués ; la lecture de cette source reste à fournir.

use Symfony\Component\Security\Core\Exception\UnsupportedUserException;
use Symfony\Component\Security\Core\Exception\UserNotFoundException;
use Symfony\Component\Security\Core\User\InMemoryUser;
use Symfony\Component\Security\Core\User\UserInterface;
use Symfony\Component\Security\Core\User\UserProviderInterface;

class FileUserProvider implements UserProviderInterface
{
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        $data = $this->all()[$identifier] ?? throw new UserNotFoundException();

        return new InMemoryUser($identifier, $data['pw'], $data['roles']);
    }

    public function refreshUser(UserInterface $user): UserInterface
    {
        if (!$this->supportsClass($user::class)) {
            throw new UnsupportedUserException('Type utilisateur non pris en charge');
        }

        return $this->loadUserByIdentifier($user->getUserIdentifier());
    }

    public function supportsClass(string $class): bool
    {
        return InMemoryUser::class === $class;
    }
}

L'extrait nécessite toujours l'implémentation applicative de all() : il n'est pas un programme autonome ni un lecteur de fichiers non fiables. Avec une entrée Alice contenant un hash valide et ['ROLE_USER'], loadUserByIdentifier('alice') rend un InMemoryUser portant cet identifiant. Avec une clé absente, il lève UserNotFoundException, pas null. Le résultat trouvé ne prouve pas que le mot de passe présenté correspond.

Appel Entrée Sortie
loadUserByIdentifier('alice') clé présente InMemoryUser
loadUserByIdentifier('zoe') clé absente UserNotFoundException
refreshUser($user) autre classe de user UnsupportedUserException
supportsClass(InMemoryUser::class) type PHP true

Le contrat

À retenir en priorité
  1. L'identifier est celui de l'authentication.
  2. Il n'est pas nécessairement une key de stockage.

Où en est-on ? Étape 1 sur 4 : les trois méthodes du contrat. Question : quand chacune est-elle appelée ?

🌍 In Real Life

La situation : le secrétariat du blog retrouve la fiche d'Alice par son identifiant. À son retour, il relit sa fiche actuelle plutôt que croire éternellement une ancienne copie.

L’équivalent dans Symfony : recherche initiale → loadUserByIdentifier() ; relecture de l'utilisateur restauré → refreshUser() ; compatibilité du type de fiche → supportsClass().

Retour à la réalité technique : le provider fournit un utilisateur, sans vérifier lui-même son mot de passe ni décider son droit sur l'article. Le refresh décrit le parcours de restauration de session, pas une étape universelle de toute requête.

🧠 Comment le mémoriser : « Trouver la fiche, puis la relire au retour. » Image mentale : fiche courante comparée à sa copie. Question-réflexe : est-ce un chargement initial ou une restauration ?

⚠️ À ne pas confondre : retrouver un compte et authentifier son détenteur.

Method Quand
loadUserByIdentifier() lorsque la résolution d'identité utilise ce provider
refreshUser() lors de la restauration du user d'un token de session sur un firewall avec état
supportsClass() dire si ce provider gère cette class

Le user n'est pas conservé tel quel : il est rechargé, puis comparé à celui du token.

Pourquoi recharger au lieu de faire confiance à la session ? Parce que la session contient une photo ancienne. Si on la croyait toujours, un compte supprimé ou rétrogradé resterait actif jusqu'à l'expiration de la session.

supportsClass() répond sur le type PHP, pas sur l'existence d'Alice ni sur son autorisation de modifier 42. Dans cet exemple, refreshUser() réutilise loadUserByIdentifier() : le chargement n'est donc pas une méthode réservée exclusivement à la première connexion.

  • ContextListener::hasUserChanged() abandonne le token quand le password, les roles ou l'identifier diffèrent — ou quand isEqualTo() rend false pour une class EquatableInterface. Un role ajouté en base déconnecte.

Une relecture invalide ne détruit pas nécessairement les autres données de session, comme une préférence de langue. Et si un autre mécanisme réauthentifie ensuite la requête avec des credentials valides, le résultat final dépend de ce second chemin : le tableau isole la restauration.

Les providers fournis

À retenir en priorité
  1. Le chain compose plusieurs sources.
  2. L'ordre de recherche compte.

Où en est-on ? Étape 3 sur 4 : quels providers existent dans Security Core et comment on les déclare. Question : comment combiner plusieurs sources ?

🌍 In Real Life

La situation : le secrétariat cherche Alice dans un annuaire puis, seulement si elle n'y figure pas, dans un autre. Une panne du premier n'est pas simplement « personne absente ».

L’équivalent dans Symfony : annuaires ordonnés → providers de la chaîne ; premier utilisateur trouvé → résultat conservé ; absence reconnue → UserNotFoundException permettant de poursuivre le chargement.

Retour à la réalité technique : la chaîne ne fusionne ni comptes ni rôles et ne relance pas une autre authentification après un mot de passe incorrect. D'autres exceptions peuvent interrompre la recherche ; le refresh a son propre parcours.

🧠 Comment le mémoriser : « Première fiche trouvée, pas addition des fiches. » Image mentale : annuaire suivant encore fermé. Question-réflexe : quel événement autorise vraiment le passage au provider suivant ?

⚠️ À ne pas confondre : utilisateur introuvable et preuve d'identité invalide.

Une source mémoire suffit aux comptes d'exercice du blog. Pour essayer deux sources de confiance, une chaîne est un provider composé, pas deux authentifications indépendantes :

Mécanisme Core ou configuration associée Rôle
memory des users écrits dans la configuration (tests, prototypes)
chain plusieurs providers essayés dans l'ordre
id un service qui implémente UserProviderInterface

Le périmètre évalué ici est Security Core : InMemoryUserProvider, ChainUserProvider et le contrat d'un provider maison. Les clés memory, chain et id sont les moyens de les déclarer dans l'intégration framework, pas trois méthodes de UserProviderInterface.

ChainUserProvider::loadUserByIdentifier() essaie les providers dans l'ordre, retourne le premier utilisateur trouvé et ne poursuit qu'après UserNotFoundException. Un mauvais mot de passe vérifié ensuite ne relance pas la recherche dans la source suivante. Les autres erreurs ne deviennent pas silencieusement « utilisateur absent ». Au refresh, la chaîne filtre par supportsClass() et peut poursuivre après UnsupportedUserException ou UserNotFoundException.

chain : [ annuaire A , annuaire B ]
  loadUserByIdentifier('alice')
     A trouve alice            ─► résultat = alice de A (B jamais consulté)
     A : UserNotFoundException ─► on essaie B
     A : autre exception       ─► la recherche s'arrête (pas « absent »)
  mot de passe faux (vérifié plus tard) ─► on ne retourne PAS chercher dans B

Les providers ldap et entity relèvent d'intégrations distinctes et restent hors du contenu évalué de ce cours. Leur existence ne les transforme pas en providers livrés par Security Core.

Provider et firewall

À retenir en priorité
  1. Le hasher calcule le nouveau hash.
  2. L'upgrader l'enregistre.

Où en est-on ? Étape 4 sur 4 : relier provider et firewall. Question : quand il y a plusieurs sources, lequel est utilisé, et qui le dit ?

Un firewall peut désigner un provider par défaut, éventuellement une chaîne. Avec plusieurs sources, rendre explicite le choix utilisé par le mécanisme : provider sur le firewall, ou sur l'authenticator qui propose ce réglage. L'absence de choix effectif est ambiguë pour HTTP Basic et provoque InvalidConfigurationException ; un loader explicite de UserBadge reste un autre contrat, pas une recherche automatique dans toutes les sources.

Un provider qui implémente PasswordUpgraderInterface reçoit le password réencodé quand l'algorithme change.

Le hasher calcule le nouveau hash ; l'upgrader l'enregistre lorsque le parcours de connexion et de migration le permet. Implémenter l'interface sans persister la valeur reçue ne met pas à jour la source d'Alice.

Pourquoi l'ambiguïté est-elle une erreur ? Symfony refuse de deviner : avec deux sources, choisir au hasard celle qui authentifie serait un risque de sécurité. D'où l'exception de configuration plutôt qu'un choix silencieux.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le mode stateless évite la restauration de session.
  2. Le chargement suit la preuve de chaque Request.
  • Voir l’explication : refreshUser() appartient au parcours de restauration du token de session

    refreshUser() appartient au parcours de restauration du token de session, pas seulement à la connexion. Un firewall stateless ne suit pas ce parcours. Pourquoi on se trompe : le mot « refresh » fait penser à un rechargement à chaque requête, ou au contraire à un simple appel de connexion.

  • Voir l’explication : Un user supprimé est déconnecté

    Un user supprimé est déconnecté au rechargement suivant : 401 ou redirect, pas 500 ; la session survit, sans son token. Pourquoi on se trompe : une exception non attrapée évoque spontanément une 500.

  • Voir l’explication : Avec la comparaison standard, des rôles modifiés invalident aussi le token

    Avec la comparaison standard, des rôles modifiés invalident aussi le token : le nouveau rôle n'est pas simplement ajouté au token existant. EquatableInterface peut personnaliser cette comparaison. Pourquoi on se trompe : on imagine que le refresh « met à jour » le token plutôt que de le jeter.

  • Voir l’explication : entity n'est pas fourni par SecurityBundle

    entity n'est pas fourni par SecurityBundle : il faut l'intégration Doctrine. id branche un provider maison. Pourquoi on se trompe : entity est omniprésent dans les tutoriels.

  • Voir l’explication : Plusieurs providers exigent un choix effectif non ambigu

    Plusieurs providers exigent un choix effectif non ambigu pour le mécanisme concerné ; les sources ne sont pas essayées automatiquement. Pourquoi on se trompe : la chaîne existe, donc on suppose qu'elle est implicite.

Fiche express

À mémoriser

À retenir en priorité
  1. Les roles font partie de la comparaison par défaut.
  2. Une comparaison personnalisée doit rester prudente.

Le user obtenu reste un objet avec un contrat précis. La suite examine les utilisateurs, puis le hachage des mots de passe : charger Alice n'effectue ni l'un ni l'autre à sa place.

🧠 À retenir pour la certification :

  • loadUserByIdentifier() lorsque le provider est utilisé pour charger l'identité ; un loader explicite de UserBadge peut le remplacer.
  • refreshUser() pour restaurer le user d'un token sur un firewall avec état.
  • Sans état : pas de refreshUser() par restauration d'un token de session.
  • User supprimé : anonyme ; l'entry point peut répondre 401 ou rediriger, sans erreur 500 imposée ; la session survit.
  • Rôles, password ou identifier changés : déconnexion selon la comparaison du user ; EquatableInterface permet de la personnaliser.
  • Core : provider mémoire, chaîne et provider maison par id ; les providers de stockage externe restent hors périmètre.
  • Plusieurs providers : choix explicite du provider utilisé.

Moyen mnémotechnique : « Charger l'identité, rafraîchir le contexte restauré ».

provider : charger le user ; contexte avec token de session : le
rafraîchir et le comparer ; stateless : pas de restauration du token ;
Core : mémoire, chaîne, contrat maison ; intégrations externes exclues
