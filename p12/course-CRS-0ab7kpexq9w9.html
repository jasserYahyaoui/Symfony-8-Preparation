Objectif

L'import accepte maintenant un fichier et ses options. Nous voulons aussi produire un export exploitable par un autre outil et tester son résultat. Une ligne de diagnostic mélangée aux données peut suffire à casser cet échange. Les objets Input et Output permettent de séparer lecture, données et diagnostic, sans enfermer le traitement dans un terminal réel.

L'essentiel

À comprendre

À retenir en priorité
  1. L'output centralise le comportement console.
  2. echo contourne ces mécanismes.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une commande qui lit $argv et fait echo est impossible à tester et mélange tout. Console donne deux contrats (InputInterface, OutputInterface) que le terminal comme les tests implémentent différemment.
  • Le piège de fond. Trois choses qu'on confond : la déclaration d'une option, sa valeur et sa saisie brute ; et côté sortie, la couleur d'un message (<error>) et sa destination (STDERR).
  • Ce que l'auteur veut que vous compreniez. Données sur STDOUT, diagnostic sur STDERR, statut dans le code de retour : trois canaux indépendants, tous testables.
  • Pourquoi c'est à l'examen. hasOption vs hasParameterOption, kebab-case, modes OUTPUT_*, getErrorOutput() réservé à ConsoleOutputInterface, CommandTester vs ApplicationTester.

InputInterface décrit les opérations de lecture ; OutputInterface décrit les opérations d'écriture. Ce sont des contrats, pas des objets qui exécutent le travail. La commande reçoit leurs implémentations : par exemple ArgvInput et ConsoleOutput au terminal, ArrayInput et une sortie capturée dans un test. Écrire par $output préserve le formatage et la verbosité ; echo contournerait ces mécanismes.

Pour un export CSV, les données vont sur la sortie standard (STDOUT) et les diagnostics sur la sortie d'erreur (STDERR). Un message « export terminé » ne devient ainsi pas une ligne du fichier de données.

Le même principe s'applique à un rapport d'import des articles : la commande travaille avec les services métier, mais le terminal et le test fournissent des implémentations différentes des mêmes contrats. Ce ne sont ni les objets Request/Response de GET /blog/42, ni une seconde implémentation du domaine.

┌──────────────────────┐   ┌──────────────────────┐   ┌──────────────────────┐
│ Données              │   │ Diagnostic           │   │ Statut               │
│ STDOUT (getOutput…)  │   │ STDERR (ErrorOutput) │   │ code de retour (int) │
│ « id;nom »           │   │ « En-tête écrit »    │   │ 0                    │
└──────────────────────┘   └──────────────────────┘   └──────────────────────┘
        trois canaux indépendants, à vérifier séparément

Le schéma

À retenir en priorité
  1. La même logique peut recevoir plusieurs entrées.
  2. Les tests peuvent capturer la sortie.

Où en est-on ? Nous venons de poser le « pourquoi ». Deux schémas suivent : le premier montre qui parle à qui (commande, objets, contrats) ; le second zoome sur la seconde sortie, celle du diagnostic.

La commande reste l'appelant. Elle demande une valeur à l'entrée déjà liée à sa définition et écrit sur la sortie reçue. Le contrat ne fait pas le travail à sa place :

Les rectangles bleus représentent les objets en action, les formes arrondies grises leurs contrats, le cylindre vert un flux. Les traits pleins sont des appels ou des écritures ; les pointillés sont des relations de contrat.

Pourquoi un second schéma ? Parce que OutputInterface seul ne promet qu'une sortie. La seconde (STDERR) est un contrat plus précis.

Il reste à protéger les données exportées des messages destinés à la personne. La seconde sortie n'est disponible que si l'objet reçu fournit le contrat plus précis ConsoleOutputInterface :

Le losange indique une condition, pas une conversion de type. Ces vues montrent le cas terminal ; un test peut remplacer les flux par des buffers.

L'exemple : une command d'export

Exemple concret

À retenir en priorité
  1. Séparer données et diagnostic.
  2. STDERR évite de corrompre l'export.

Où en est-on ? Code minimal : une commande qui écrit une donnée sur STDOUT et un diagnostic sur STDERR. Tout le reste du cours part de cet exemple (lecture, écriture, test).

Cette petite commande exporte uniquement l'en-tête d'un fichier d'auteurs, utile à la branche d'administration du blog. Placer la classe dans src/Command/HeaderCommand.php avec la découverte des services active :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Input\InputInterface;
use Symfony\Component\Console\Output\ConsoleOutputInterface;
use Symfony\Component\Console\Output\OutputInterface;

#[AsCommand(name: 'app:export-header')]
final class HeaderCommand
{
    public function __invoke(InputInterface $input, OutputInterface $output): int
    {
        $output->writeln('id;nom');                    // les données : STDOUT
        if ($output instanceof ConsoleOutputInterface) {
            $output->getErrorOutput()->writeln('<info>En-tête écrit</info>'); // diagnostic : STDERR
        }

        return Command::SUCCESS;
    }
}

Cet extrait suppose une commande app:export-header déjà enregistrée et les classes Console importées. Il écrit seulement l'en-tête id;nom, pas 42 lignes d'enregistrements. Une redirection de la seule sortie standard capture cet en-tête ; « En-tête écrit » reste sur la sortie d'erreur.

php bin/console app:export-header

En verbosity normale, la sortie standard contient :

id;nom

La sortie d'erreur contient En-tête écrit, éventuellement coloré, et le code retourné vaut 0. Le diagnostic peut sembler voisin des données sur un terminal ; cela ne signifie pas que les deux flux ont été fusionnés.

Pour le vérifier soi-même :

php bin/console app:export-header > export.csv
  → à l'écran : « En-tête écrit »   (STDERR n'est pas redirigé)
  → export.csv contient : id;nom    (STDOUT seulement)

`InputInterface` — lire

À retenir en priorité
  1. La définition et la saisie sont distinctes.
  2. Choisir la bonne interrogation.

Où en est-on ? Étape 1 sur 4 : la lecture. Mécanisme : Console lie la saisie à la définition (cours précédent), puis expose trois niveaux d'information que le programme veut vous voir distinguer.

🌍 In Real Life

La situation : le bordereau d'import possède une case « simulation ». Son existence ne dit pas si l'opérateur l'a cochée.

L’équivalent dans Symfony : case prévue → hasOption() ; valeur retenue → getOption() ; saisie brute → méthodes *ParameterOption().

Retour à la réalité technique : définition, valeur avec défaut et présence dans l'entrée sont trois observations distinctes. Lire hasOption('dry-run') ne démontre pas que la simulation a été demandée.

🧠 Comment le mémoriser : « Case présente, choix absent. » Image mentale : une case vide imprimée sur tous les formulaires. Question-réflexe : cherche-t-on la déclaration, la valeur ou la saisie ?

⚠️ À ne pas confondre : contrat InputInterface et implémentation concrète de l'entrée.

Pour savoir si un import est une simulation, trois questions sont possibles : l'option dry-run existe-t-elle, quelle est sa valeur, a-t-elle été explicitement saisie ? Elles ne sont pas interchangeables :

Appel Ce qu'il rend
getArgument('username'), getOption('iterations') la valeur, ou la default value
hasOption('dry-run') l'option est-elle déclarée ? — true même non passée
hasParameterOption('--env'), getParameterOption('--env') lus sur la ligne brute, sans definition
isInteractive() état interactif de l'objet ; l'Application standard le désactive notamment avec -n, -q ou --silent

setArgument() et setOption() permettent à interact() de compléter une valeur. Le nom attendu est le nom kebab-case déclaré : un #[Argument] string $userName se lit getArgument('user-name').

Avec un drapeau dry-run déclaré et de défaut false, une invocation qui l'omet peut donc donner hasOption('dry-run') === true et getOption('dry-run') === false. Pour la logique métier, lire la valeur ; pour diagnostiquer la saisie brute, utiliser l'API appropriée.

php bin/console app:import f.csv          (--dry-run NON passé)

hasOption('dry-run')           → true    (déclarée dans la définition)
getOption('dry-run')           → false   (valeur par défaut)
hasParameterOption('--dry-run')→ false   (absente de la ligne brute)

Sur ArgvInput, la lecture brute ignore la définition. Avec onlyParams: true, elle s'arrête au séparateur -- ; sans ce réglage, elle peut aussi examiner des tokens qui suivent ce séparateur. Ne pas prendre cette recherche pour un parseur métier validant le sens des options.

isInteractive() ne recherche pas un terminal : il lit un booléen que setInteractive() peut modifier. Un test ou une application personnalisée peut donc rendre l'entrée non interactive sans aucun drapeau CLI.

`OutputInterface` — écrire

À retenir en priorité
  1. Les tags peuvent modifier l'affichage.
  2. Échapper le texte externe avant formatage.

Où en est-on ? Étape 2 sur 4 : l'écriture et son formatage. Pourquoi s'y attarder ? Parce qu'un titre d'article contenant <error> ne doit pas prendre le contrôle des couleurs : il faut savoir quand le formateur interprète les balises et quand il faut les échapper.

Les titres des articles et les noms d'auteurs peuvent contenir des caractères qui ressemblent aux balises du formateur. Avant de les inclure dans un diagnostic stylé, distinguer le texte externe des instructions de présentation :

  • write(), writeln(), avec un array pour plusieurs lignes.
  • Quatre tags par défaut : <info> vert, <comment> jaune, <question> noir sur cyan, <error> blanc sur rouge. Un tag inconnu, <script>, passe intact.
  • Une string venue de l'extérieur passe par OutputFormatter::escape().
  • Modes : OUTPUT_NORMAL interprète les tags, OUTPUT_RAW les laisse, OUTPUT_PLAIN les interprète puis applique strip_tags() : sur un output décoré, <info>ok</info> reste toujours en vert.
  • SymfonyStyle enveloppe le tout : title(), success(), error(), ask(), table(), et getErrorStyle() pour la sortie d'erreur si elle existe ; sinon ce style réutilise la sortie reçue.

Dans Output::write(), le niveau de verbosity filtre d'abord les messages. Ensuite le mode sélectionne le formatage, avant l'écriture effective. OUTPUT_PLAIN ne veut pas dire « sans séquence ANSI » : strip_tags() supprime les balises restantes, pas les codes de couleur déjà produits. OUTPUT_RAW évite l'interprétation, mais affiche aussi littéralement les balises que le programme avait éventuellement ajoutées.

Comparaison des trois modes sur '<info>ok</info> <script>x</script>' (output décoré) :

Mode Étape 1 : formatage Étape 2 Résultat affiché
OUTPUT_NORMAL tags connus interprétés — ok en vert, <script>x</script> intact
OUTPUT_RAW aucune interprétation — <info>ok</info> <script>x</script>
OUTPUT_PLAIN tags connus interprétés (couleur produite) strip_tags() ok en vert, puis x

Cette fonction conserve un repli explicite pour une commande de diagnostic qui accepte de n'avoir qu'une sortie :

<?php
use Symfony\Component\Console\Formatter\OutputFormatter;
use Symfony\Component\Console\Output\ConsoleOutputInterface;
use Symfony\Component\Console\Output\OutputInterface;

function writeDiagnostic(OutputInterface $output, string $message): void
{
    $errors = $output instanceof ConsoleOutputInterface
        ? $output->getErrorOutput()
        : $output;
    $errors->writeln('<error>'.OutputFormatter::escape($message).'</error>');
}

Avec le message <info>Alice</info>, ces caractères restent du texte dans le bloc d'erreur au lieu d'imposer leur propre style. Cet échappement vise les balises Console ; ce n'est pas un encodeur CSV ou HTML. Le repli vers $output n'est pas adapté tel quel à un export qui exige une séparation stricte : il y mélangerait le diagnostic aux données.

L'output d'erreur

À retenir en priorité
  1. Tous les outputs n'ont pas STDERR séparé.
  2. Tester le contrat avant l'appel.

Où en est-on ? Étape 3 sur 4 : la destination du diagnostic. Question centrale : pourquoi <error> ne suffit-il pas à écrire sur STDERR ? Parce qu'une balise change un style, jamais une adresse.

🌍 In Real Life

La situation : le blog remet un fichier d'export à une machine et une note de diagnostic à l'opérateur, dans deux corbeilles.

L’équivalent dans Symfony : données → sortie normale ; note → sortie d'erreur de ConsoleOutputInterface ; couleur de la note → style du formateur.

Retour à la réalité technique : <error> ne choisit pas STDERR. Il faut écrire sur la sortie appropriée, si l'objet expose ce contrat. Le code de retour reste indépendant des deux flux.

🧠 Comment le mémoriser : « La couleur n'est pas l'adresse. » Image mentale : une feuille rouge dans la mauvaise corbeille. Question-réflexe : sur quel objet Output écrit-on ?

⚠️ À ne pas confondre : sortie d'erreur, style d'erreur et statut d'échec.

getErrorOutput() appartient à ConsoleOutputInterface, pas à OutputInterface : un BufferedOutput ne l'a pas, d'où le test de type.

Une balise <error> change un style, pas une destination. Un appel à writeln('<error>…</error>') sur la sortie normale reste sur cette sortie. Pour l'export, choisir explicitement une seconde sortie, ou une politique documentée lorsque ce contrat manque : l'exemple d'en-tête omet le diagnostic dans ce cas. Un autre outil peut exiger deux sorties plutôt que continuer avec un repli.

De même, afficher une erreur ne change pas le code de retour de la commande. Le statut et les deux flux restent trois observations distinctes à tester.

$output->writeln('<error>boom</error>')              → STDOUT, en rouge
$output->getErrorOutput()->writeln('boom')           → STDERR, sans couleur
$output->getErrorOutput()->writeln('<error>boom</error>') → STDERR, en rouge
return Command::SUCCESS;                             → code 0 malgré le « boom »

Tester une command

À retenir en priorité
  1. Le cycle Application porte les events.
  2. Tester seulement la command ne les déclenche pas.

Où en est-on ? Étape 4 sur 4 : vérifier tout cela sans terminal. Mécanisme : CommandTester remplace ArgvInput/ConsoleOutput par des objets qui capturent la sortie, puis appelle Command::run().

Commençons par tester l'en-tête, pas une salutation interactive étrangère à ce comportement. Dans un contexte où l'autoload du projet est chargé :

<?php
use App\Command\HeaderCommand;
use Symfony\Component\Console\Tester\CommandTester;

$tester = new CommandTester(new HeaderCommand());
$status = $tester->execute([], [
    'interactive' => false,
    'capture_stderr_separately' => true,
]);

$data = $tester->getDisplay(true);       // "id;nom\n"
$diagnostic = $tester->getErrorOutput(true); // "En-tête écrit\n"
// $status vaut 0 ; ces trois valeurs se vérifient séparément.

Le testeur accepte l'objet invocable et l'adapte en Command. L'option de capture séparée prépare des sorties distinctes ; appeler getErrorOutput() sur le testeur sans cette option lève une LogicException. La normalisation demandée ici rend les fins de ligne comparables.

Pour une autre commande qui pose réellement une question, conserver le principe setInputs(['Bob']) : cela fournit une réponse simulée, pas un argument nommé. Avec interactive: false, cette réserve ne remplit pas magiquement un argument requis ; transmettre sa valeur dans le premier tableau d'execute() ou attendre l'erreur de validation.

  • CommandTester appelle la command seule : aucun event console. ApplicationTester passe par l'Application, avec setAutoExit(false). Les événements Console sont distribués si l'Application dispose d'un dispatcher : changer de testeur n'installe pas à lui seul les listeners.
  • Ordre : initialize(), interact() (en interactif), validation de l'entrée, execute() ; non interactive, un argument requis manquant lève « Not enough arguments ».
  • Avec capture_stderr_separately, ce qu'écrit getErrorStyle() passe dans getErrorOutput(), comme le libellé d'une question de QuestionHelper ; celui de SymfonyStyle::ask() reste dans getDisplay().

QuestionHelper bascule vers la sortie d'erreur lorsqu'il reçoit une ConsoleOutputInterface. SymfonyStyle::ask() lui passe le style comme objet de sortie : ne pas déduire le flux d'une question de son seul texte. Enfin, CommandTester contourne Application::configureIO() ; configurer interactive et verbosity dans le test plutôt que présumer que toutes les options globales du vrai entry point ont été appliquées.

Comparaison des deux testeurs :

┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│ CommandTester                    │   │ ApplicationTester                │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ Appelle : Command::run()         │   │ Appelle : Application::run()     │
│ Événements Console : aucun       │   │ Événements : si dispatcher       │
│ Nom de commande : inutile        │   │ Nom de commande : dans l'entrée  │
│ configureIO() : contourné        │   │ autoExit : false                 │
└──────────────────────────────────┘   └──────────────────────────────────┘

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le nom PHP et le nom CLI diffèrent.
  2. Lire la définition effective.
  • Voir l’explication : Passer par l'output plutôt que echo

    Passer par l'output plutôt que echo : cet echo ne figure pas dans CommandTester::getDisplay() et échappe à la verbosity de Console. Un autre dispositif de capture PHP peut le voir, mais ce n'est pas le contrat du testeur présenté ici. Pourquoi on se trompe : à l'écran, echo et writeln ont l'air identiques.

  • Voir l’explication : getErrorOutput() n'appartient pas à OutputInterface

    getErrorOutput() n'appartient pas à OutputInterface mais à ConsoleOutputInterface — d'où le test de type. Pourquoi on se trompe : on suppose que tout objet « Output » possède deux flux.

  • Voir l’explication : hasOption() interroge la definition

    hasOption() interroge la definition, pas la ligne de command : il vaut true même quand l'option n'a pas été passée. C'est hasParameterOption() qui lit la ligne brute. Pourquoi on se trompe : le verbe « has » évoque « la saisie contient ».

  • Voir l’explication : OUTPUT_PLAIN garde les couleurs

    OUTPUT_PLAIN garde les couleurs d'un output décoré. Pourquoi on se trompe : « plain » évoque « sans rien ».

  • Voir l’explication : Le nom passé à getArgument() est le nom kebab-case

    Le nom passé à getArgument() est le nom kebab-case déclaré, pas celui du paramètre PHP lorsque le nom est inféré. Un name explicite dans l'attribut remplace cette convention : lire le nom réellement déclaré.

Fiche express

À mémoriser

À retenir en priorité
  1. Les deux flux peuvent être vérifiés séparément.
  2. Le diagnostic ne doit pas polluer les données.

Le rapport d'import ou l'export peut maintenant conserver ses données, son diagnostic et son statut séparés au terminal comme en test. Cette séparation est le résultat recherché, pas seulement une préférence de style.

🧠 À retenir pour la certification — si tu dois retenir seulement 7 choses :

  • Lire par InputInterface, écrire par OutputInterface ; jamais echo.
  • ArgvInput, ArrayInput, StringInput : même contrat.
  • hasOption() : déclarée ? ; hasParameterOption() : ligne brute.
  • Arguments et options sous leur nom kebab-case.
  • Quatre tags ; escape() pour ce qui vient de l'extérieur.
  • getErrorOutput() (ConsoleOutputInterface) pour STDERR.
  • CommandTester : la commande seule ; ApplicationTester : le parcours Application, avec événements si un dispatcher est configuré.

Moyen mnémotechnique : « Lire l'entrée, écrire l'output, crier sur STDERR ». Phrase de mémorisation : « La commande lit un contrat, écrit les données sur STDOUT, le diagnostic sur STDERR, rend son statut en int — et le testeur capture les trois. »

Pour présenter progression, tableaux et questions sans reconstruire ces mécanismes, poursuivre avec Built-in helpers. Les événements Console expliqueront ensuite ce que le parcours ApplicationTester ajoute au test de la commande seule.
