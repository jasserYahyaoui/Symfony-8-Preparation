Objectif

Le blog a vingt pages. Toutes affichent le même en-tête, le même menu, le même pied de page. Copier ce squelette dans vingt templates serait une catastrophe de maintenance. Ce cours explique comment Twig écrit le squelette une seule fois et laisse chaque page ne fournir que ce qui change, puis ce que le compilateur refuse et comment partager des morceaux sans créer un deuxième parent.

Il s'agit de construire une hiérarchie de templates, de savoir ce que l'inheritance autorise, et de distinguer l'inheritance de la réutilisation horizontale.

L'essentiel

À comprendre

À retenir en priorité
  1. extends choisit le parent.
  2. Le child remplace seulement les blocks qu'il redéfinit.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Éviter la duplication du layout : un parent porte la structure, les enfants ne portent que les variations.
  • Le piège de fond. Un block défini n'est pas un block affiché : c'est le layout qui décide de l'appeler, et Twig n'invente jamais l'emplacement.
  • Ce que l'auteur veut que vous compreniez. Le compilateur est strict : du contenu hors block dans un enfant, deux extends, un block dans un if sont des erreurs de syntaxe, pas des oublis silencieux.
  • Pourquoi c'est à l'examen. Les QCM testent set avant extends, la liste de parents candidats, la priorité des blocks importés par use, et le fait que use exige une string.

Toutes les pages partagent un header, un menu, un pied de page. Un parent les déclare une fois et laisse des trous — les blocks ; chaque page enfant l'étend et remplit les trous qui l'intéressent. Le compiler refuse tout ce qui rendrait cette mécanique ambiguë.

Le schéma

À retenir en priorité
  1. Un child place son contenu dans les blocks.
  2. Un set sans output peut rester hors block.

Où en est-on ? Vue d'ensemble, en cinq étapes : le mécanisme parent/enfant (1), l'interdiction du contenu hors block (2), les règles de l'inheritance (3), les trois gestes sur un block (4), la réutilisation horizontale (5). Le schéma ci-dessous répond à la question qui sous-tend tout le cours : quel contenu Twig rend-il quand le layout atteint un block ?

Layout parent (base.html.twig)       Page enfant (article.html.twig)
┌───────────────────────────┐        ┌───────────────────────────┐
│ <header>…</header>        │        │ {% extends 'base…' %}     │
│ {% block title %}         │◄───────│ {% block title %}Articles │
│ {% block body %}          │◄───────│ {% block body %}…         │
│ <footer>…</footer>        │        └───────────────────────────┘
└───────────────────────────┘

Bleu = layout exécuté, ambre = choix de block, vert = contenu rendu. Les flèches montrent la sélection au rendu, pas un héritage PHP. Cette vue suppose un template valide et un parent trouvé : une syntaxe interdite échoue avant le rendu, un parent introuvable produit une LoaderError.

Le mécanisme

Où en est-on ? Étape 1 sur 5 : le principe parent / enfant. On part d'un exemple concret et on suit qui appelle qui.

La page de l'article42 et celle du catalogue partagent navigation et pied de page. Leur parent définit cette structure ; chaque enfant fournit ses variations nommées. Le contrôleur rend l'enfant, puis Twig utilise le layout et les redéfinitions pour produire une seule représentation HTML.

Un template parent déclare des blocks ; un template enfant extends le parent et redéfinit ceux qui l'intéressent.

{% extends 'base.html.twig' %}

{% block title %}Articles{% endblock %}

{% block stylesheets %}
    {{ parent() }}
    <link rel="stylesheet" href="page.css">
{% endblock %}

Un block non redéfini garde le contenu du parent. Le squelette affiché reste celui du parent, avec les redéfinitions de l'enfant aux endroits où les blocks sont appelés. Un block enfant jamais appelé par le layout ne s'affiche pas simplement parce qu'il est défini. On peut empiler les niveaux : base → layout de section → page.

Que se passe-t-il quand le contrôleur écrit $this->render('article.html.twig') ?

render('article.html.twig')
   ▼
Twig compile l'enfant ; il voit {% extends 'base.html.twig' %}
   ▼
il charge et compile le parent base.html.twig
   ▼
il exécute le PARENT (c'est lui qui écrit le squelette)
   ▼
le parent atteint {% block title %} → Twig cherche la redéfinition la plus proche
   ▼
  l'enfant en a une → rendue                  ┐
  sinon → le contenu par défaut du parent     ┘ → une seule page HTML

Piège central : le parent est exécuté, pas l'enfant. L'enfant ne sert qu'à fournir des définitions. D'où la règle : un block défini par l'enfant mais jamais appelé par le parent n'apparaît pas.

Avant / après, avec un parent qui définit title et body et un enfant qui redéfinit seulement title :

Parent                         Enfant
{% block title %}Site{% … %}   {% block title %}Articles{% endblock %}
{% block body %}Accueil{% … %}   (rien pour body)

Résultat : title = « Articles »  (redéfini)     body = « Accueil » (hérité)

🌍 In Real Life

La situation : le journal utilise une maquette commune avec des emplacements nommés « titre » et « article ». Chaque édition fournit ses variantes ; une rubrique préparée sans emplacement appelé ne s'imprime pas toute seule.

L’équivalent dans Symfony : extends sélectionne le layout et les block de l'enfant redéfinissent ses points d'extension. Lorsque le rendu atteint un appel de bloc, Twig utilise la définition applicable, sinon celle héritée.

Retour à la réalité technique : une définition n'est pas une garantie d'affichage ; le flux de rendu doit appeler le bloc. Plusieurs niveaux peuvent se succéder, mais ce mécanisme ne représente ni un héritage de contrôleurs ni plusieurs réponses HTTP assemblées.

🧠 Comment le mémoriser : « La maquette place, l'édition remplit. » Image mentale : rubriques étiquetées déposées dans les emplacements du journal. Question-réflexe : quel layout appelle le bloc que je redéfinis ?

⚠️ À ne pas confondre : définition d'un bloc, appel du bloc et rendu complet du template.

Hors d'un block : une erreur, pas un oubli silencieux

Où en est-on ? Étape 2 sur 5 : un enfant ne remplit que des trous. Que devient du texte écrit à côté des trous ? Twig le refuse, et c'est une question d'examen classique.

Ajouter <h1>{{ article.title }}</h1> après extends ne précise pas où placer le titre dans le layout. Twig refuse ce contenu orphelin à la compilation. Place-le dans le block que le parent appelle ; un set extérieur reste possible puisqu'il prépare une donnée sans l'afficher.

Dans un template qui étend un parent, du texte ou un {{ … }} écrit hors de tout block lève une SyntaxError : « A template that extends another one cannot include content outside Twig blocks ». Seuls les blancs et les tags qui n'affichent rien, comme {% set %}, sont tolérés ; la variable ainsi posée est lisible dans les blocks.

Pourquoi cette règle ? Un enfant ne s'exécute pas comme une page : c'est le parent qui produit la sortie. Un <h1> hors block ne saurait pas où se placer dans le squelette du parent. Plutôt que de deviner, Twig refuse (le Parser vérifie le corps de l'enfant).

{% extends 'base.html.twig' %}
<h1>{{ article.title }}</h1>       ← où le mettre dans base ?  → SyntaxError
{% set x = 1 %}                    ← n'affiche rien           → toléré
{% block body %}{{ x }}{% endblock %}   ← OK
Élément hors block Accepté ? Pourquoi
blancs, retours à la ligne oui rien à afficher
{% set x = 1 %} oui prépare une donnée, n'affiche rien
<h1>…</h1> ou {{ x }} non : SyntaxError contenu sans emplacement

🌍 In Real Life

La situation : une édition remet un titre sans indiquer sa rubrique. L'atelier refuse cette instruction de placement ; une note de calcul interne, elle, peut rester hors des zones imprimées.

L’équivalent dans Symfony : un enfant qui étend un parent ne peut produire librement du texte ou une expression affichée hors des blocs. Twig signale une SyntaxError ; un set non affichant peut préparer une valeur utilisée ensuite.

Retour à la réalité technique : le contenu interdit n'est pas silencieusement perdu au rendu. Les blancs et les constructions non affichantes autorisées ne sont pas assimilables à du HTML libre ; envelopper arbitrairement une sortie dans une instruction ne résout pas la règle.

🧠 Comment le mémoriser : « Un titre sans rubrique est refusé, pas oublié. » Image mentale : titre retourné par l'atelier, note de calcul conservée. Question-réflexe : cette instruction prépare-t-elle une donnée ou produit-elle du contenu hors bloc ?

⚠️ À ne pas confondre : erreur de structure à la compilation et bloc valide jamais appelé.

Les règles de l'inheritance

À retenir en priorité
  1. Un seul extends est autorisé.
  2. Une expression peut choisir le parent.

Où en est-on ? Étape 3 sur 5 : maintenant que l'on sait ce qui est interdit hors des blocks, on regarde les autres règles de la structure, et le choix du parent (qui peut être dynamique).

Une variante imprimable de l'article peut choisir un layout minimal par une expression. Cela sélectionne un parent, sans assembler plusieurs parents concurrents. Une liste fournit des replis de chargement : elle ne concatène pas les templates trouvés et ne dispense pas de traiter l'absence de tous les candidats.

Template Résultat
deux extends SyntaxError : « Multiple extends tags are forbidden »
extends dans un block SyntaxError
deux {% block body %} SyntaxError : un nom de block est unique
{% set x = 1 %} avant extends accepté : « extends en tête » est une consigne de la documentation, pas un contrôle du parser

Le parent peut être une expression :

  • {% extends some_var %} — une variable ;
  • {% extends ['layout.html.twig', 'base.html.twig'] %} — le premier template qui existe ; si aucun n'existe, une LoaderError : « Unable to find one of the following templates » ;
  • {% extends standalone ? 'minimum.html.twig' : 'base.html.twig' %}.

Pourquoi un seul extends ? Un template qui aurait deux parents poserait la question : lequel exécuter ? Twig n'a pas d'héritage multiple ; la solution est use (étape 5).

Chemin d'exécution de la liste de parents :

{% extends ['layout.html.twig', 'base.html.twig'] %}
   ▼
Twig essaie layout.html.twig → existe ? oui → c'est le parent
                                       non → essaie base.html.twig
   ▼
aucun n'existe → LoaderError : Unable to find one of the following templates

Pourquoi la mauvaise réponse est plausible pour set avant extends : la documentation recommande de mettre extends en premier ; on en conclut que le parser refuse tout ce qui le précède. Mais c'est une consigne de style : seul le contenu qui affiche quelque chose hors block est refusé.

🌍 In Real Life

La situation : pour l'édition imprimable, on choisit une maquette parmi plusieurs possibilités. Une liste de secours signifie « prendre la première disponible », pas empiler toutes les maquettes.

L’équivalent dans Symfony : un seul extends peut contenir une expression ou une liste de templates candidats. Twig choisit le parent applicable ; deux extends, un extends dans un bloc ou deux définitions locales de même nom sont interdits.

Retour à la réalité technique : l'absence de tous les candidats produit une LoaderError, pas un document vide garanti. Recommander extends en tête n'interdit pas au parser un set non affichant avant lui. Choix dynamique ne signifie pas héritage multiple.

🧠 Comment le mémoriser : « Plusieurs candidats, une seule maquette retenue. » Image mentale : pile de maquettes de secours dont une seule part à l'impression. Question-réflexe : ai-je sélectionné un parent ou tenté d'en déclarer plusieurs ?

⚠️ À ne pas confondre : erreur de syntaxe, échec de chargement et recommandation de style.

Reprendre, réafficher, tester un block

À retenir en priorité
  1. parent() complète le contenu hérité.
  2. block() réaffiche un block nommé.

Où en est-on ? Étape 4 sur 5 : le parent et l'enfant sont en place. Trois gestes permettent de manipuler un block : parent() (reprendre), block() (réafficher) et is defined (tester).

La feuille de style de l'article doit compléter celles du site : parent() reprend le contenu hérité dans le block redéfini. Réafficher le titre dans un second emplacement relève plutôt de block('title'). Dans les deux cas, les appels déterminent l'affichage ; définir un block n'assure pas qu'un emplacement l'appellera.

  • {{ parent() }} insère le contenu du block parent : on ajoute au lieu de remplacer.
  • Un block s'affiche chaque fois que le flux de rendu atteint son appel : placé dans une boucle du parent, il peut donc s'afficher plusieurs fois. La function block('title') permet un appel explicite supplémentaire, y compris depuis un autre template : block('title', 'common.html.twig').
  • block('footer') is defined teste son existence.
  • Un block dans un if reste défini : seul son affichage suit la condition. Dans un enfant, un block imbriqué sous un if est une SyntaxError.

Comparaison des trois gestes :

┌────────────────────┐ ┌────────────────────┐ ┌────────────────────┐
│     parent()       │ │   block('title')   │ │ block('x') is      │
│                    │ │                    │ │ defined            │
├────────────────────┤ ├────────────────────┤ ├────────────────────┤
│ Où ?               │ │ Où ?               │ │ Où ?               │
│ DANS un block      │ │ n'importe où       │ │ dans une condition │
│ redéfini           │ │                    │ │                    │
├────────────────────┤ ├────────────────────┤ ├────────────────────┤
│ Rend               │ │ Rend               │ │ Rend               │
│ le contenu du      │ │ le block (autre    │ │ un booléen         │
│ block PARENT       │ │ template possible) │ │ (existence)        │
└────────────────────┘ └────────────────────┘ └────────────────────┘

Pourquoi un block peut-il s'afficher plusieurs fois ? Parce qu'il est rendu à chaque fois que le flux atteint son appel. Si le parent le place dans une boucle, il est rendu à chaque tour.

Pourquoi « un block dans un if reste défini » ? La définition d'un block est décidée à la compilation ; seul son affichage suit la condition. Et dans un enfant, un block sous un if est refusé : on ne peut pas définir conditionnellement.

🌍 In Real Life

La situation : l'éditeur peut reprendre une rubrique de l'édition précédente, imprimer à nouveau le titre ou vérifier qu'une rubrique existe. Ces trois opérations ne font pas le même travail.

L’équivalent dans Symfony : parent() reprend le contenu hérité dans le bloc courant ; block('title') demande son rendu ; block('footer') is defined teste sa disponibilité. Le nombre d'affichages dépend des appels réellement atteints.

Retour à la réalité technique : un appel dans une boucle peut produire plusieurs rendus. Dans les structures autorisées, une condition autour d'un appel n'efface pas la définition ; déclarer un bloc sous un if dans un enfant qui étend un parent reste interdit. L'existence n'implique ni contenu non vide ni affichage.

🧠 Comment le mémoriser : « Reprendre, imprimer, vérifier : trois gestes. » Image mentale : rubrique héritée, titre réimprimé et case de contrôle d'existence. Question-réflexe : ai-je besoin du parent, d'un rendu ou seulement d'un test ?

⚠️ À ne pas confondre : définition disponible, contenu rendu et condition de passage dans le flux.

Le parent est un papier à en-tête dont les blocks sont les zones modifiables. parent() conserve ce qui était imprimé dans la zone, puis permet de compléter ; l'override seul le remplace.

Réutilisation horizontale

À retenir en priorité
  1. use importe des blocks sans rendu immédiat.
  2. Les blocks locaux priment sur les imports.

Où en est-on ? Étape 5 sur 5 : l'héritage est vertical (parent → enfant) et n'autorise qu'un parent. Comment partager des blocks entre deux pages sans leur donner un nouveau parent ? C'est le rôle de use.

Deux pages peuvent partager une définition de sidebar sans partager un nouveau layout. use importe alors des blocks disponibles pour la résolution, sans rendre immédiatement un fragment. Un include répondrait à une autre demande : produire maintenant le contenu du template inclus.

{% use 'blocks.html.twig' %} importe les blocks d'un autre template sans l'étendre ni les afficher — la solution de Twig à l'inheritance multiple : un seul extends, plusieurs use.

  • Un block importé compte comme un block de l'enfant : il remplace celui du parent du même nom.
  • Un block du template courant l'emporte sur un block importé.
  • with sidebar as base_sidebar renomme à l'import.
  • La cible de use est une string : une variable est une SyntaxError.

Le template importé doit être réutilisable comme trait : pas de parent extends, pas de macros, pas de contenu de corps hors blocs. Il peut lui-même utiliser use. Si deux imports fournissent le même block, le dernier import gagne ; une définition locale reste prioritaire.

Pourquoi use n'est-il pas un héritage ? Il apporte des définitions de blocks (comme un trait PHP apporte des méthodes) ; il n'ajoute pas de parent à la chaîne. Il ne rend rien lui-même.

Ordre de priorité quand plusieurs sources définissent le même block sidebar :

1. block défini dans le template COURANT       ← gagne toujours
2. block importé par le DERNIER {% use %}
3. block importé par un use précédent
4. block du PARENT (extends)                   ← perd contre tout ce qui précède

Comparaison des trois mécanismes proches :

extends use include
Rôle choisir le parent importer des définitions de blocks produire un fragment maintenant
Nombre un seul plusieurs autant qu'on veut
Affiche immédiatement ? non (le parent s'exécute) non oui
Cible dynamique ? oui (variable, liste) non : string oui

🌍 In Real Life

La situation : deux journaux empruntent un jeu de rubriques à un atelier commun sans adopter toute sa maquette. La rédaction peut renommer une rubrique ou fournir sa propre version.

L’équivalent dans Symfony : use importe des définitions de blocs, sans rendre immédiatement le template ni en faire un parent. Les blocs locaux priment ; entre imports concurrents de même nom, le dernier gagne ; un renommage évite la collision.

Retour à la réalité technique : la cible est une chaîne littérale et le template doit être utilisable comme trait : pas de parent, pas de macros ni de corps hors blocs incompatibles. Un include rend du contenu ; use apporte des définitions pour les appels ultérieurs.

🧠 Comment le mémoriser : « Emprunter les rubriques n'adopte pas la maquette. » Image mentale : fiches de rubriques communes transférées dans deux rédactions. Question-réflexe : veux-je importer des définitions ou produire un fragment maintenant ?

⚠️ À ne pas confondre : use, extends et include.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Du contenu hors block dans un enfant est une erreur de syntaxe

    Du contenu hors block dans un enfant est une erreur de syntaxe, pas un contenu ignoré. Pourquoi on se trompe : en HTML, du texte « en trop » est simplement affiché ; on suppose que Twig l'ignore ou l'affiche.

  • Voir l’explication : Un seul parent

    Un seul parent, mais un parent choisi dynamiquement : variable, liste dont le premier existant gagne, ou ternaire. Pourquoi on se trompe : « liste » évoque « plusieurs parents » alors qu'un seul est retenu.

  • Voir l’explication : block() appelle un block ; parent() reprend son contenu hérité.

    block() appelle un block ; parent() reprend son contenu hérité. Le nombre d'affichages dépend des appels, notamment des boucles du layout, pas du nombre de définitions. Pourquoi on se trompe : on compte les {% block %} écrits au lieu des appels atteints.

  • Voir l’explication : Un block dans un if reste défini.

    Un block dans un if reste défini. Seul son rendu dépend de la condition. Pourquoi on se trompe : en PHP, une déclaration dans un if n'existe que si la condition est vraie.

  • Voir l’explication : Importer les blocks d'un autre template n'est pas en hériter.

    Importer les blocks d'un autre template n'est pas en hériter. use ne fait pas de parent ; sa cible est une string. Pourquoi on se trompe : use et extends « apportent du contenu d'un autre template ».

  • Voir l’explication : set avant extends est accepté.

    set avant extends est accepté. « extends en tête » est une consigne, pas un contrôle du parser. Pourquoi on se trompe : on prend une bonne pratique pour une règle de compilation.

Application

À retenir en priorité
  1. parent() complète le contenu hérité.
  2. block() réaffiche un block nommé.
  3. Un child place son contenu dans les blocks.
  4. Un set sans output peut rester hors block.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • extends + block ; un block non redéfini garde le parent ; le parent est exécuté, l'enfant fournit des définitions.
  • Hors block, dans un enfant : SyntaxError, sauf blancs et set.
  • Un seul parent, jamais dans un block ; un nom de block unique.
  • Parent dynamique : liste (premier existant, sinon LoaderError), ternaire, variable.
  • parent() ajoute, block() réaffiche, is defined teste.
  • Un block sous un if reste défini (mais interdit dans un enfant).
  • use importe des blocks (cible = string), qui masquent ceux du parent.

Moyen mnémotechnique : « un parent, des trous, rien hors des trous ».

enfant = extends (1 seul, expression permise) + blocks (noms uniques) ;
hors block : SyntaxError sauf set/blancs ;
parent() reprend, block() réaffiche, is defined teste ;
use = blocks importés (masquent le parent), cible = string
