Objectif

Restreindre une route à certaines methods HTTP, et contourner la limite des forms HTML.

Question fil rouge : « GET /api/posts/42 et PUT /api/posts/42 ont le même path : comment Symfony les envoie-t-il vers deux actions, et comment un simple form HTML peut-il atteindre un DELETE ? »

L'essentiel

À comprendre

À retenir en priorité
  1. Le form HTML transmet GET ou POST.
  2. _method exige http_method_override pour être interprété.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un path identifie une ressource ; la method exprime l'intention (lire, modifier, supprimer). Une API REST réutilise le même path pour plusieurs intentions : le routage doit donc filtrer sur le verbe.
  • Le piège de fond. Deux problèmes distincts : (1) restreindre la route (methods) ; (2) faire croire à Symfony que le verbe est PUT/DELETE alors que le navigateur envoie POST (override).
  • Ce que l'auteur veut que vous compreniez. Le routeur ne voit que la method « effective » rendue par Request::getMethod(). L'override la change, pas le POST réellement envoyé (getRealMethod() reste POST).
  • Pourquoi c'est à l'examen. Défaut « tous les verbes », GET accepte HEAD, http_method_override (false par défaut), priorité header avant _method, verbes interdits, allowed_http_method_override: [].

Sans option methods, une route accepte tous les verbes ; avec methods: ['GET'], elle accepte aussi HEAD. Un form HTML ne sait envoyer que GET et POST : pour simuler PUT ou DELETE, un field caché _method, lu seulement si framework.http_method_override vaut true — false par défaut. Le header d'override, lui, ne dépend pas de cette option.

Le schéma

À retenir en priorité
  1. Le header est examiné sur un POST avant le parameter.
  2. Une liste allowed_http_method_override vide désactive les remplacements.

Où en est-on ? Carte du cours, puis l'arbre de décision de getMethod() : de la method réellement envoyée à celle que voit le routeur.

Cours « HTTP methods matching »
   ├─ exemple                  → /api/posts/{id} : GET et PUT
   ├─ 1. L'option methods      → restreindre, HEAD, 405
   ├─ 2. La limite des forms   → _method caché dans un POST
   └─ 3. Request::getMethod()  → header, _method, liste autorisée

Ambre = méthode réelle ; bleu = traitement. allowed_http_method_override: [] arrête le chemin avant même la lecture du header. Pour une liste non vide, le rejet d'un verbe précède son contrôle alphabétique : PUT2 non autorisé peut donc être ignoré plutôt que lever. Le remplacement change la méthode vue par le routeur, pas le POST réellement envoyé ; getRealMethod() reste POST.

Où en est-on ? Même arbre, en version « tableau noir » : l'ordre exact des contrôles dans getMethod() (8.0).

getMethod() sur un POST
   1. liste autorisée vide ([]) ?            → POST, fin
   2. header X-HTTP-METHOD-OVERRIDE ?        → sinon, si http_method_override:
      _method (body puis query)                 true, on lit _method
   3. rien de lisible ?                      → POST, fin
   4. majuscules ; GET/HEAD/CONNECT/TRACE ?  → POST, fin (verbe interdit)
   5. liste non vide et verbe absent ?       → POST, fin (verbe non autorisé)
   6. autre chose que des lettres A-Z ?      → SuspiciousOperationException
   7. sinon                                  → le verbe remplace la method

L'exemple : deux routes, un path

Exemple concret

À retenir en priorité
  1. Le path peut être identique si les methods distinguent les routes.
  2. La route GET accepte également HEAD ; PUT sélectionne l'autre action.

Où en est-on ? Cas concret : l'API du blog lit puis modifie le même article. Deux actions, un seul path, deux methods.

L'API du blog peut lire puis modifier le même article via deux méthodes. Les signatures suivantes montrent la sélection des actions, pas des implémentations exécutables. Restreindre la méthode choisit une route ; cela ne vérifie ni les droits de modification ni la validité du body.

#[Route('/api/posts/{id}', methods: ['GET'])]
public function show(int $id): Response {}

#[Route('/api/posts/{id}', methods: ['PUT'])]
public function edit(int $id): Response {}

Ce que Symfony voit :

Requête              Route show (GET)  Route edit (PUT)  Résultat
-------------------  ----------------  ----------------  ---------------
GET  /api/posts/42   correspond        (non essayée)     show(42)
HEAD /api/posts/42   correspond        (non essayée)     show(42)
PUT  /api/posts/42   method refusée    correspond        edit(42)
POST /api/posts/42   method refusée    method refusée    405 + Allow

Remarque : le 405 liste les methods acceptées par les routes dont le path correspond (Allow) ; il est produit par RouterListener.

L'option `methods`

À retenir en priorité
  1. L'absence de methods n'implique pas GET.
  2. HEAD est comparé comme GET au matching.

Où en est-on ? Étape 1 sur 3. Pourquoi restreindre ? Pour que la route exprime son contrat : une route de lecture ne doit pas répondre à un POST.

Pour /blog/42, déclarer GET explicite le contrat de lecture. Sans restriction, le même chemin pourrait sélectionner l'action pour un POST. Un refus de méthode se distingue d'un chemin introuvable ; il peut mener à 405 et Allow via RouterListener, selon les autres candidates.

Par défaut une route accepte tous les verbes. methods restreint, et deux routes peuvent partager le même path en ne différant que par la method — le pattern REST. Ajouter HEAD à une route déjà ouverte à GET est superflu : le matcher accepte également HEAD pour cette route. Le matcher compilé de l'application vérifie la méthode originale et sa forme canonique GET ; il peut donc aussi reconnaître une route réservée à HEAD. Ne généralise pas ce dernier cas au UrlMatcher non compilé, qui remplace HEAD par GET avant sa comparaison. Cette distinction vient de CompiledUrlMatcherTrait::doMatch() et de UrlMatcher::matchCollection().

Pourquoi HEAD « gratuit » ? HEAD est un GET sans corps : mêmes en-têtes, pas de body. Le serveur de routage traite donc HEAD comme GET (forme canonique) ; vous n'avez pas à déclarer les deux.

Comparaison des trois façons de déclarer :

Déclaration Verbes acceptés
(pas de methods) tous
methods: ['GET'] GET et HEAD
methods: ['PUT'] PUT seulement

🌍 In Real Life

La situation : au même guichet des archives, consulter le dossier 42 et demander sa modification suivent deux procédures différentes. Trouver le bon guichet ne suffit pas : la nature de la demande compte.

L’équivalent dans Symfony : methods distingue les routes portant le même chemin par la méthode HTTP effective. Sans cette option, aucun filtre de méthode ne s'ajoute ; une route GET accepte également HEAD.

Retour à la réalité technique : les autres critères de matching et l'ordre restent applicables. Une incompatibilité de méthode peut produire 405 avec Allow via l'intégration, selon les autres candidates. Le cas HEAD seul dépend du matcher décrit ci-dessus. Ce filtrage ne valide ni le body ni les droits de modification.

⚠️ À ne pas confondre : chemin existant, méthode admise, données valides et action autorisée.

Un guichet peut exister mais ne traiter que certaines opérations. Le path correspond et la method non : le 405 et son header Allow décrivent cette différence, contrairement à une absence de route.

Repère de l’exemple :

Question: How can the same /api/posts/{id} path select different actions for GET and PUT?

Answer: Give the two routes different methods requirements; GET also accepts HEAD.

Le path peut être identique si les methods distinguent les routes. La route GET accepte également HEAD ; PUT sélectionne l'autre action.

La limite des forms HTML

Où en est-on ? Étape 2 sur 3. Problème : un <form> ne sait faire que GET ou POST. Comment atteindre PUT/PATCH/DELETE depuis un bouton HTML ?

Le bouton de suppression de l'article peut émettre un POST réel avec _method=DELETE. Le thème Twig sait écrire ce champ, mais le serveur doit encore autoriser son interprétation. La présence du champ dans le HTML n'est donc pas une preuve que Routing verra DELETE.

Un form HTML envoie GET ou POST. Pour atteindre une route en PUT, PATCH ou DELETE, on ajoute un field caché _method :

<input type="hidden" name="_method" value="PUT">

Symfony ne le lit que si framework.http_method_override vaut true. Le theme de form Twig ajoute ce field dès que la method du form n'est ni GET ni POST, que l'option soit activée ou non.

Deux moitiés indépendantes :

┌───────────────────────────────────┐   ┌───────────────────────────────────┐
│        CÔTÉ HTML (rendu)          │   │       CÔTÉ SERVEUR (lecture)      │
├───────────────────────────────────┤   ├───────────────────────────────────┤
│ Le thème de form Twig écrit       │   │ Request::getMethod() lit _method  │
│ <input hidden name="_method">     │   │ SEULEMENT si                      │
│ dès que la method n'est ni GET    │   │ framework.http_method_override    │
│ ni POST                           │   │ vaut true (false par défaut)      │
├───────────────────────────────────┤   ├───────────────────────────────────┤
│ Indépendant de l'option           │   │ Sans l'option : le champ est      │
│                                   │   │ ignoré, la Request reste POST     │
└───────────────────────────────────┘   └───────────────────────────────────┘

🌍 In Real Life

La situation : une enveloppe utilise le canal ordinaire du courrier, mais contient une instruction « traiter comme demande de suppression ». L'administration doit avoir décidé de reconnaître cette instruction ; l'imprimer ne la rend pas active.

L’équivalent dans Symfony : un formulaire HTML transporte un POST avec _method=DELETE. Le thème Twig peut produire le champ caché, mais Request ne l'interprète que lorsque la configuration autorise cette substitution et cette méthode.

Retour à la réalité technique : le POST envoyé sur le réseau ne devient pas rétroactivement DELETE. Un client capable d'envoyer directement DELETE n'a pas besoin de cette simulation. Ni champ caché ni méthode effective ne remplacent autorisation, validation ou protection CSRF adaptée.

⚠️ À ne pas confondre : rendu du formulaire, transport HTTP et interprétation serveur.

Ce que fait `Request::getMethod()` (8.0)

Où en est-on ? Étape 3 sur 3 : le détail du mécanisme d'override. Avant le matching, distingue le verbe transporté de la méthode effective.

Avec override autorisé, un POST peut être présenté au routeur comme PUT ; getRealMethod() reste POST. L'ordre header, paramètre et liste autorisée explique pourquoi deux saisies apparemment semblables n'atteignent pas la même action.

  • Rien n'est remplacé si la method réelle n'est pas POST.
  • Le header X-HTTP-METHOD-OVERRIDE est lu en premier, et il ne dépend pas de http_method_override, qui ne gouverne que _method.
  • _method est cherché dans le body, puis dans la query string.
  • Un remplacement vers GET, HEAD, CONNECT ou TRACE est ignoré.
  • Le nom est d'abord mis en majuscules : _method=put donne PUT. Un nom qui contient autre chose que des lettres lève une SuspiciousOperationException s'il n'a pas déjà été rejeté par la liste autorisée.

framework.allowed_http_method_override restreint les methods simulables : null, le défaut, n'ajoute pas de liste restrictive (les quatre verbes interdits restent exclus) ; une liste les limite, une method hors liste laissant le POST ; un array vide désactive tout remplacement, header compris.

Pourquoi le header ne dépend-il pas de http_method_override ? Un header est posé par un client programmatique ou un proxy, pas par un <form> HTML : il n'y a pas lieu de le désactiver par défaut. L'option ne gouverne que le paramètre _method, qui est la solution « pour formulaires ».

Exemples (override activé, liste null) :

Requête réelle Header _method getMethod()
POST — put PUT (majuscules)
POST DELETE PUT DELETE (header prioritaire)
POST — GET POST (verbe interdit)
POST — PUT2 exception (non alphabétique)
GET — PUT GET (pas un POST)

Comparaison des trois réglages de allowed_http_method_override :

Valeur Effet
null (défaut) pas de liste restrictive ; 4 verbes interdits restent exclus
['DELETE'] seuls ces verbes ; les autres laissent le POST
[] aucun remplacement, header compris

🌍 In Real Life

La situation : le service courrier garde le tampon d'arrivée, mais peut ajouter une consigne interne. Il vérifie d'abord que le canal autorise ce traitement, lit la mention prioritaire, puis contrôle les consignes permises.

L’équivalent dans Symfony : getRealMethod() conserve POST ; getMethod() peut donner la méthode substituée. Le header est prioritaire sur _method, lequel exige son option d'activation. La liste autorisée s'applique aux deux mécanismes.

Retour à la réalité technique : hors POST, pas de remplacement ; une liste vide désactive tout override. Une liste null n'ajoute pas de restriction, mais les quatre verbes interdits restent exclus. Normalisation puis rejet éventuel précèdent le contrôle alphabétique : toute saisie non alphabétique ne lève donc pas nécessairement.

🧠 Comment le mémoriser : « Le tampon reste ; la consigne passe les filtres. » Image mentale : tampon POST intact sous une étiquette PUT vérifiée. Question-réflexe : quelle méthode réelle, quelle source prioritaire et quelle politique autorisée ?

⚠️ À ne pas confondre : option _method, politique globale des overrides et methods acceptées par la route.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les erreurs de QCM probables et la raison de leur plausibilité.

  • Voir l’explication : Sans restriction de method, une route accepte tous les verbes.

    Sans restriction de method, une route accepte tous les verbes. L'absence de l'option n'est pas un GET implicite. Pourquoi on se trompe : on suppose qu'une route « normale » est une page GET.

  • Voir l’explication : Le field caché ne suffit pas.

    Le field caché ne suffit pas. Simuler un verbe par _method exige http_method_override: true ; désactivée — ce qui est le cas par défaut — le field est ignoré et la Request reste un POST. Pourquoi on se trompe : le thème Twig écrit bien le champ, donc « ça doit marcher ».

  • Voir l’explication : Le header, lui, n'attend pas cette option.

    Le header, lui, n'attend pas cette option. Seul allowed_http_method_override: [] le neutralise. Pourquoi on se trompe : on généralise « override = option activée » aux deux mécanismes.

  • Voir l’explication : methods: ['GET'] accepte HEAD.

    methods: ['GET'] accepte HEAD. Pourquoi on se trompe : on lit la liste littéralement.

  • Voir l’explication : Deux routes peuvent partager exactement le même path

    Deux routes peuvent partager exactement le même path et ne différer que par la method : c'est le pattern REST, et il rend la lecture de la liste des routes indispensable. Pourquoi on se trompe : on croit qu'un path est unique par route.

  • Voir l’explication : L'override ne change pas le POST envoyé.

    L'override ne change pas le POST envoyé. getRealMethod() reste POST. Pourquoi on se trompe : « getMethod() renvoie PUT » fait croire que la requête HTTP était un PUT.

À mémoriser

🧠 À retenir pour la certification :

  • Sans methods → tous les verbes ; GET accepte HEAD.
  • _method lu seulement si http_method_override: true (false par défaut).
  • Remplacement depuis un POST seulement.
  • Header X-HTTP-METHOD-OVERRIDE lu en premier, même option désactivée.
  • Jamais vers GET, HEAD, CONNECT, TRACE ; nom non alphabétique → exception si la politique autorisée ne l'a pas déjà rejeté.
  • allowed_http_method_override: [] coupe tout, header compris.

Moyen mnémotechnique : « Le header passe avant le field ».

Phrase de mémorisation : « Le routeur voit la method que getMethod() lui rend : un POST peut en devenir un autre par header d'abord, par _method si l'option est activée, après filtre — mais le POST réel, lui, ne change jamais. »
