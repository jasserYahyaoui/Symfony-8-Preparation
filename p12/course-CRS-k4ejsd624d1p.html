Objectif

Modifier un type de field existant — y compris un type fourni par Symfony ou par un bundle tiers — sans le remplacer, et savoir jusqu'où la modification s'étend.

Question centrale : comment ajouter une capacité à tous les fields d'un type, sans modifier un seul form, et jusqu'où cette capacité se propage-t-elle ?

L'essentiel

À comprendre

À retenir en priorité
  1. La propagation suit l'inheritance des form types.
  2. FormType n'est pas la racine des boutons.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Vous ne contrôlez pas les types de Symfony ni ceux des bundles : impossible de les modifier. L'extension est le point d'ajout prévu.
  • Le piège de fond. Confondre « type » (crée un field) et « extension » (modifie ceux qui existent), et croire qu'elle touche aussi les frères.
  • Ce que l'auteur veut que vous compreniez. getExtendedTypes() statique et non vide, propagation par getParent(), ordre parent → enfant, tag et priorité.
  • Pourquoi c'est à l'examen. Cas IntegerType refusé, boutons exclus, AsTaggedItem ignoré.

Une form type extension greffe un comportement sur un type existant — TextType, FileType, un type de bundle — partout dans l'application, sans toucher un seul form. Un type crée un nouveau field ; une extension modifie ceux qui existent. Elle suit l'inheritance des types : elle atteint leurs descendants, pas leurs frères.

Le schéma

Où en est-on ? Début du cours. Voici l'arbre des types et la zone touchée par une extension de TextType. Question : qui reçoit l'option, qui ne la reçoit pas ?

FormType ─┬─ TextType  ◄── extension "help_icon" ──┬─ EmailType   (touché)
          │      (touché)                           └─ TextType    (touché)
          └─ IntegerType                  (NON touché : autre branche)

ButtonType ── SubmitType     (racine séparée : aucune extension de FormType)

Pointillés = parent de form, non héritage PHP ni appels directs. Vert = portée de help_icon, bleu = autres branches, ambre = racines. Déclarer l'option et la copier dans FormView ne dessine pas encore une icône : un bloc du thème doit lire help_icon. Cela sépare comportement du type et HTML.

L'exemple : `help_icon`

Exemple concret

À retenir en priorité
  1. La method est statique.
  2. Une liste vide est une erreur d'enregistrement.

Où en est-on ? On pose le code complet d'une extension. Question : quelles sont les trois choses qu'elle fait, et pourquoi pas un IconTextType ?

L'inscription et les formulaires d'édition veulent afficher une icône d'aide sur les champs texte. Cette extension rend une option disponible sans remplacer chaque TextType par un type maison. L'extrait suppose les imports des classes Form et OptionsResolver ; un block du thème devra encore lire la variable pour dessiner l'icône.

class HelpIconExtension extends AbstractTypeExtension
{
    public static function getExtendedTypes(): iterable
    {
        return [TextType::class];
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefined('help_icon');
    }

    public function buildView(FormView $view, FormInterface $form, array $options): void
    {
        $view->vars['help_icon'] = $options['help_icon'] ?? null;
    }
}

Ce que Symfony voit :

Méthode Rôle Sans elle
getExtendedTypes() à quels types se greffer erreur à la compilation
configureOptions() accepter l'option help_icon UndefinedOptionsException
buildView() copier l'option dans view.vars le thème ne la voit pas

Un IconTextType obligerait à remplacer TextType dans chaque form, et ne toucherait pas les forms des bundles.

Le principe

À retenir en priorité
  1. Une extension enrichit les types existants.
  2. Un nouveau type impose de le sélectionner aux call sites.

Où en est-on ? Étape 1 sur 4. Comprendre ce qu'est une extension. Question « Pourquoi ? » : pourquoi une extension plutôt qu'un type maison ?

L'extension participe à la construction des occurrences futures ; elle ne parcourt pas le HTML déjà rendu pour le réécrire. Choisis-la pour une capacité transversale, éventuellement activée par option. Un type personnalisé reste plus explicite si une spécialisation doit être choisie uniquement sur quelques champs.

Une extension étend AbstractTypeExtension et s'applique à tous les fields des types qu'elle désigne. Elle redéfinit les mêmes points d'accroche qu'un type : buildForm(), configureOptions(), buildView(), finishView().

Comparaison :

Type personnalisé Extension
Effet crée un nouveau field modifie des fields existants
Activation je le choisis dans add() automatique pour les types visés
Types de bundles non touchés touchés
Quand spécialisation sur quelques champs capacité transversale

Vérifié dans ResolvedFormType 8.0 : buildForm() appelle d'abord le parent ($this->parent?->buildForm), puis le type, puis boucle sur ses extensions. Même principe pour buildView() et finishView().

🌍 In Real Life

La situation : l'imprimerie ajoute à son modèle de fiche texte une option « pictogramme d'aide ». Les commandes qui utilisent ce modèle peuvent en profiter sans commander une nouvelle catégorie de fiche.

L’équivalent dans Symfony : une extension de type participe aux hooks de configuration, construction et préparation des vues des types ciblés. Elle enrichit leur usage sans remplacer chaque appel à add() par un type personnalisé.

Retour à la réalité technique : elle intervient dans le cycle Form du registre configuré, pas en réécriture rétroactive du HTML. Déclarer help_icon puis le copier dans les variables de vue ne dessine rien tant qu'un thème ne le consomme. Une option peut rendre le comportement conditionnel ; un nouveau type reste utile pour une spécialisation explicitement choisie.

🧠 Comment le mémoriser : « Ajouter une capacité au modèle, pas repeindre les feuilles livrées. » Image mentale : option d'icône sur le plan d'impression, feuilles encore à produire. Question-réflexe : est-ce une capacité transversale du type ou un nouveau type à choisir ?

⚠️ À ne pas confondre : type personnalisé, type extension, variable de vue et thème de formulaire.

La seule method obligatoire

Où en est-on ? Étape 2 sur 4. La déclaration des types visés. Question : pourquoi cette méthode est-elle statique, et que se passe-t-il si elle est vide ?

La compilation du conteneur doit savoir à quels types rattacher le service avant de traiter une inscription. getExtendedTypes() fournit cette déclaration statique ; elle n'inspecte pas la Request du lecteur. Une liste vide est donc une erreur de configuration en amont du formulaire, pas un formulaire valide qui ignorerait l'extension.

getExtendedTypes() est statique, retourne un itérable, et peut nommer plusieurs types. Un itérable vide est refusé à la compilation du container : FormPass lève une InvalidArgumentException, « The getExtendedTypes() method for service "e" does not return any extended types. ».

Pourquoi statique ? Pour que FormPass puisse l'appeler sans instancier le service, pendant la compilation. Vérifié dans FormPass::processFormTypeExtensions() 8.0 : il appelle $typeExtensionClass::getExtendedTypes() sur la classe, remplit $typeExtensions[$extendedType][] pour chaque type, et lève l'exception si rien n'a été ajouté ($extendsTypes reste faux). Le message exact est bien « The getExtendedTypes() method for service "%s" does not return any extended types. ».

compilation du container
  pour chaque service tagué form.type_extension (triés par priorité) :
      types = Classe::getExtendedTypes()          (statique, sans instance)
      aucun type ?  → InvalidArgumentException
      sinon         → rattacher le service à chaque type

🌍 In Real Life

La situation : avant d'ouvrir l'atelier, on inscrit quels modèles recevront un nouvel accessoire. Une déclaration sans modèle destinataire ne permet pas de préparer la chaîne de fabrication.

L’équivalent dans Symfony : getExtendedTypes() déclare statiquement les classes ciblées sous forme d'itérable. Dans l'intégration conteneur décrite, FormPass utilise cette déclaration et refuse une liste vide.

Retour à la réalité technique : avec AbstractTypeExtension, les autres hooks ont des implémentations par défaut ; redéfinis ceux dont tu as besoin. La méthode statique n'est pas un sélecteur dépendant du lecteur ou de sa Request. Le refus à la compilation est celui du chemin FormPass, pas une contrainte métier appliquée à une soumission.

🧠 Comment le mémoriser : « Déclarer les modèles avant d'ouvrir l'atelier. » Image mentale : liste des modèles affichée avant les commandes. Question-réflexe : quels types sont déclarés, indépendamment de la requête courante ?

⚠️ À ne pas confondre : déclaration de types, hook d'occurrence, compilation du conteneur et validation du formulaire.

Qui est touché, et quand

Où en est-on ? Étape 3 sur 4. La portée. Question : pourquoi EmailType reçoit-il l'option mais pas IntegerType ?

Le champ email reçoit l'option via TextType, mais le champ âge ne suit pas cette branche. Si l'option est refusée avant buildView(), inspecte la lignée et les types étendus avant le thème Twig. L'ordre des hooks de construction ne fixe pas à lui seul l'ordre ultérieur des listeners qu'ils peuvent enregistrer.

Field Extension de TextType
TextType option acceptée
EmailType, enfant de TextType option acceptée
IntegerType, enfant de FormType UndefinedOptionsException : « The option "help_icon" does not exist »
  • Étendre FormType::class touche tous les fields, mais pas les boutons : ButtonType n'a pas de parent.
  • Ordre : chaque extension s'exécute juste après le type qu'elle étend. Pour un EmailType, l'extension de FormType passe avant celle de TextType.

Pourquoi ? Le ResolvedFormType d'un type garde une référence vers celui de son parent et clone ses options (clone $this->parent->getOptionsResolver()) avant d'y ajouter celles du type puis de ses extensions. Les options d'une extension de TextType sont donc dans le résolveur de EmailType (son parent), mais pas dans celui de IntegerType, qui n'a pas TextType dans sa chaîne.

Ordre pour un EmailType :

1. FormType::buildForm          4. extensions de TextType
2. extensions de FormType       5. EmailType::buildForm
3. TextType::buildForm          6. extensions de EmailType

Lecture simplifiée : de la racine vers le field, chaque extension venant juste après le type qu'elle étend.

🌍 In Real Life

La situation : une amélioration du modèle texte se transmet aux fiches email qui le réutilisent, mais pas aux fiches numériques fabriquées sur une autre branche. Les accessoires de chaque modèle sont montés après ce modèle.

L’équivalent dans Symfony : l'extension suit la lignée Form getParent() : TextType et ses descendants sont concernés, pas IntegerType. Pour les hooks décrits, le parent et ses extensions précèdent le type enfant et ses extensions.

Retour à la réalité technique : étendre FormType vise sa lignée, pas la racine séparée ButtonType ni un type personnalisé hors de cette lignée. Une option refusée indique d'abord un problème de définition, portée ou enregistrement, pas un défaut Twig. L'ordre des hooks ne remplace pas les priorités des listeners qu'ils enregistrent.

🧠 Comment le mémoriser : « L'accessoire suit sa branche, pas le rayon voisin. » Image mentale : branche texte–email équipée, branche entière séparée. Question-réflexe : le champ descend-il réellement du type étendu ?

⚠️ À ne pas confondre : descendants de type, champs enfants d'un formulaire, familles documentaires et ordre des événements.

Une coque annonce les modèles de téléphone compatibles ; getExtendedTypes() annonce les types concernés. Étendre FormType n'équipe pas tous les objets sans exception : les boutons appartiennent à une autre racine.

L'enregistrement

À retenir en priorité
  1. La priority la plus haute passe d'abord.
  2. debug:form permet de vérifier l'enregistrement.

Où en est-on ? Étape 4 sur 4. Brancher l'extension sur le container. Question : quel tag, quelle priorité, et pourquoi AsTaggedItem ne marche pas ?

Une classe présente sur disque doit être découverte comme service et autoconfigurée, ou déclarée avec son tag. Pour plusieurs extensions du même type, configure la priorité du tag lu par FormPass ; une convention d'un autre mécanisme de services tagués n'est pas automatiquement transférable. Le diagnostic porte d'abord sur l'enregistrement, puis sur l'option résolue.

  • Un service tagué form.type_extension, posé par l'autoconfiguration pour une class de src/.
  • Plusieurs extensions d'un même type s'ordonnent par l'attribute priority du tag : 0 par défaut, la plus haute d'abord.
  • Cette priority exige de déclarer le service explicitement : #[AsTaggedItem(priority: 10)] sur une extension autoconfigurée est ignoré par FormPass.
  • php bin/console debug:form vérifie l'enregistrement.

Pourquoi ? FormPass parcourt findAndSortTaggedServices('form.type_extension', …) : le tri vient de la priorité portée par le tag. Un attribut PHP n'est lu que par un mécanisme prévu pour lui ; ici, le tag n'est pas construit à partir de lui.

Chaîne complète :

classe dans src/  ─►  service autoconfiguré  ─►  tag form.type_extension
                                                      │ (priority du tag)
                                                      ▼
                                   FormPass trie, appelle getExtendedTypes()
                                                      ▼
                                      registre des extensions par type

Comparaison des priorités :

Source de la priorité Lue par FormPass ?
attribut priority du tag, service déclaré explicitement oui
#[AsTaggedItem(priority: 10)] sur extension autoconfigurée non, ignoré
rien 0 par défaut

🌍 In Real Life

La situation : posséder une notice d'accessoire ne suffit pas : l'atelier doit l'inscrire à son planning. Lorsque plusieurs accessoires visent le même modèle, seul l'ordre inscrit sur le planning reconnu organise leur montage.

L’équivalent dans Symfony : la classe doit être enregistrée comme service, puis porter le tag form.type_extension. FormPass lit la priorité de ce tag ; une annotation d'un autre mécanisme n'est pas automatiquement interprétée.

Retour à la réalité technique : présence dans src/ n'est suffisante qu'avec découverte et autoconfiguration appropriées. Dans ce chemin8.0, AsTaggedItem ne fournit pas la priorité attendue ; configure celle du tag effectif. Une priorité plus haute signifie exécution plus tôt pour les extensions du même type, pas garantie de « gagner » une valeur écrasée ensuite. debug:form aide au diagnostic, sans prouver le rendu final.

🧠 Comment le mémoriser : « La notice existe ; le planning doit encore la connaître. » Image mentale : notice sur le bureau face au planning de montage. Question-réflexe : quel service, quel tag et quelle priorité FormPass voit-il réellement ?

⚠️ À ne pas confondre : fichier présent, service découvert, tag effectif, priorité d'exécution et résultat final.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Une extension modifie les occurrences d'un type sans changer les appels à add().

    Une extension modifie les occurrences d'un type sans changer les appels à add(). Un nouveau type reste utile si seuls certains fields doivent adopter le comportement. Pourquoi on se trompe : on croit qu'il faut toujours un type maison pour changer un comportement.

  • Voir l’explication : La method qui désigne les types étendus est statique

    La method qui désigne les types étendus est statique, retourne un itérable, et ne peut pas être vide. Pourquoi on se trompe : on la imagine comme une méthode d'instance ou une valeur par défaut tolérante.

  • Voir l’explication : Une extension atteint les types enfants

    Une extension atteint les types enfants, pas les types frères : étendre TextType touche EmailType, pas IntegerType. Pourquoi on se trompe : « tout ce qui ressemble à un champ de saisie » semble concerné.

  • Voir l’explication : Étendre le type racine touche tous les fields, pas les boutons.

    Étendre le type racine touche tous les fields, pas les boutons. Pourquoi on se trompe : un bouton est aussi un enfant du form, mais ButtonType n'a pas de parent.

  • Voir l’explication : La priority se règle sur le tag

    La priority se règle sur le tag, dans la configuration du service. Pourquoi on se trompe : AsTaggedItem fonctionne ailleurs et on le croit universel.

Application

À retenir en priorité
  1. La propagation suit l'inheritance des form types.
  2. FormType n'est pas la racine des boutons.
  3. La method est statique.
  4. Une liste vide est une erreur d'enregistrement.

À mémoriser

🧠 À retenir pour la certification :

  • Un type crée un field ; une extension modifie ceux qui existent.
  • getExtendedTypes() : statique, itérable, jamais vide.
  • Elle atteint les descendants : TextType → EmailType, pas IntegerType.
  • Étendre FormType : tous les fields, pas les boutons.
  • Tag form.type_extension, autoconfiguré ; priority sur le tag, la plus haute d'abord.
  • #[AsTaggedItem] : ignoré par FormPass.

Moyen mnémotechnique : « Greffer, pas remplacer ».
