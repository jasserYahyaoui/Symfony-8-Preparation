Objectif

L'iterator tagué suffit à réunir nos canaux de notification. Une intégration existante peut cependant demander des appels addHandler() plutôt qu'un iterable, ou exposer un argument à adapter. Une compiler pass transforme alors les définitions avant leur utilisation. Nous allons choisir ce qu'elle modifie et surtout l'état du graphe dont elle a besoin, sans la confondre avec un listener de /blog/42.

Question directrice : quand le câblage standard ne suffit pas, à quel moment de la compilation et sur quelles définitions intervenir ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le compiler pass modifie le plan.
  2. La création des instances reste ultérieure.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le container est compilé : ses définitions sont figées avant la première Request. Pour les modifier globalement (après la fusion des bundles), il faut s'insérer dans la compilation.
  • Le piège de fond. Une passe manipule des plans (Definition), jamais des objets métier. Et elle voit l'état laissé par les passes précédentes : le moment (phase + priorité) décide de ce qu'elle voit.
  • Ce que l'auteur veut que vous compreniez. Phase d'abord, priorité ensuite ; défaut = TYPE_BEFORE_OPTIMIZATION, 0 ; une passe est un dernier recours après la configuration publique et l'iterator tagué.
  • Pourquoi c'est à l'examen. getDefinition vs findDefinition, findTaggedServiceIds sans tri, priorités 100/-1000/-10000, setArgument vs replaceArgument, redéclaration = remplacement total.

Une compiler pass implémente CompilerPassInterface et reçoit un ContainerBuilder dans process(). Elle transforme le plan des services : arguments, références, tags ou appels de méthodes prévus. Son rôle n'est pas de récupérer les objets avec get() pour exécuter leur travail métier.

On l'enregistre à une phase et une priorité. Elle voit le résultat des passes précédentes, pas les informations qu'une passe ultérieure produira. Elle est exécutée lors des compilations auxquelles elle participe, pas une seule fois dans la vie du projet ni à chaque Request.

Le schéma

À retenir en priorité
  1. Le cache chaud réutilise le résultat.
  2. Les passes ne font pas partie du traitement courant.

Où en est-on ? Avant le détail, le principe en un schéma : la passe prépare un appel à la compilation ; le container l'exécute plus tard.

La chaîne du laboratoire accepte l'ajout de handlers après construction. La passe prépare ces ajouts ; elle ne les exécute pas :

Orange : manipulation des définitions ; bleu : construction ultérieure ; vert : chaîne configurée. addMethodCall() conserve le nom de méthode et ses références d'arguments. Lorsqu'il construit la chaîne, le container résout les objets puis effectue les appels préparés. Même alors, addHandler() ne signifie pas nécessairement notify() : la méthode peut seulement mémoriser le collaborateur.

Le fil rouge : une chaîne de handlers

À retenir en priorité
  1. La passe déclare les appels.
  2. Elle ne doit pas instancier les handlers.

Où en est-on ? On écrit la première passe concrète. À repérer : process() ne crée aucun objet, il ajoute des appels prévus.

Cette variante remplace l'injection d'une collection au constructeur par une méthode d'ajout. Supposons HandlerChain enregistré avec addHandler(HandlerInterface $handler): void, et des services tagués app.handler implémentant ce contrat local. Avec les imports DI, la passe est :

use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Reference;

class HandlerPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has(HandlerChain::class)) {   // sinon : ServiceNotFoundException
            return;
        }
        $chain = $container->findDefinition(HandlerChain::class);
        foreach ($container->findTaggedServiceIds('app.handler') as $id => $tags) {
            $chain->addMethodCall('addHandler', [new Reference($id)]);
        }
    }
}

Si deux définitions portent ce tag, la définition de la chaîne reçoit deux appels prévus. La passe n'a appelé ni leur constructeur ni addHandler() ni notify(). Le garde has() choisit ici de ne rien faire si la chaîne est absente ; pour une intégration obligatoire, lever une erreur explicite serait un autre contrat.

$tags est une liste de jeux d'attributs pour un même service. Cette boucle ajoute volontairement une fois chaque service, sans parcourir chaque occurrence du tag et sans trier ses priorités. Elle convient à ce contrat simple ; une intégration utilisant les attributs de chaque occurrence doit traiter cette liste.

 AVANT la passe                      APRÈS la passe (plan modifié)
┌──────────────────────┐            ┌────────────────────────────────┐
│ Definition           │            │ Definition                     │
│  HandlerChain        │   ───▶     │  HandlerChain                  │
│  appels : (aucun)    │            │  appels : addHandler(@email)   │
└──────────────────────┘            │           addHandler(@sms)     │
                                    └────────────────────────────────┘
 Rien n'est instancié : seul le plan change.

🌍 In Real Life

La situation : avant le service, on inscrit sur le plan quels postes devront recevoir chaque outil ; personne ne cuisine pendant cette annotation.

L’équivalent dans Symfony : repérer les outils étiquetés → findTaggedServiceIds() ; inscrire une future remise → addMethodCall('addHandler', [new Reference(...)]) ; effectuer la remise plus tard → appel lors de la construction de la chaîne.

Retour à la réalité technique : la passe modifie une définition, sans appeler les handlers. Ici, la boucle ajoute une fois chaque service ; elle n'itère pas chaque occurrence du tag et ne trie pas ses priorités.

🧠 Comment le mémoriser : « Inscrire l'appel n'est pas appeler. » Image mentale : un geste dessiné sur un plan. Question-réflexe : cette ligne transforme-t-elle la définition ou exécute-t-elle un objet ?

⚠️ À ne pas confondre : ajouter le handler à la chaîne et exécuter son métier ; même à l'instanciation, addHandler() peut seulement mémoriser le collaborateur.

Ce qu'une passe est

À retenir en priorité
  1. findDefinition() suit les alias.
  2. getDefinition() ne les résout pas.

Où en est-on ? Étape 1 sur 5. Question : sur quoi une passe travaille-t-elle exactement ? Sur le ContainerBuilder, qui contient des plans (définitions et alias), pas des objets vivants.

Le builder contient des définitions et des aliases, pas seulement des objets déjà construits. getDefinition('priv') rend le plan ; si aucun code n'a demandé l'instance, initialized('priv') reste false. Lire une définition ne construit pas le service. Les méthodes suivantes modifient ou inspectent ce graphe :

Method Ce qu'elle fait
has($id) / hasDefinition($id) definition ou alias / definition seulement
getDefinition($id) la definition ; sur un alias, ServiceNotFoundException
findDefinition($id) la definition, en suivant les alias
findTaggedServiceIds($tag) id => liste d'attributes, dans l'ordre de déclaration, sans tri
removeDefinition($id) retire la définition, sans réparer automatiquement ses consommateurs
$def->setArgument('$region', 'eu') fixe un argument, nommé ou par index
$def->replaceArgument() exige un argument existant, sinon OutOfBoundsException

has() peut reconnaître aussi un service déjà fourni au builder ; ce n'est donc pas une preuve universelle que findDefinition() trouvera un plan. Dans notre laboratoire, la chaîne est bien définie ou aliasée vers une définition. setArgument() peut fixer un emplacement ; replaceArgument() exige qu'il existe déjà. findDefinition() suit les aliases que getDefinition() ne suit pas.

Pour un tri de tags, une passe peut employer PriorityTaggedServiceTrait::findAndSortTaggedServices(). findTaggedServiceIds() seul ne lit pas priority pour trier. Préfixer un tag de bundle, comme acme_mailer.transport, évite des collisions de noms ; cela n'ajoute pas de lecteur.

Voici une adaptation ciblée de l'export CLI, pour un service fictif vendor.exporter dont le constructeur attend string $region :

final class ExportRegionPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has('vendor.exporter')) {
            throw new LogicException('Le service vendor.exporter est requis.');
        }
        $container->findDefinition('vendor.exporter')
            ->setArgument('$region', 'eu');
    }
}

Avec cette définition ou un alias vers elle présent à la phase choisie, le futur objet reçoit eu. Les autres arguments, tags et appels restent sur sa définition. Le code n'exporte aucune donnée et n'instancie aucun service ; les imports sont ceux de la passe précédente.

 mailer  ──(alias)──▶  app.mailer ──▶ Definition
   getDefinition('mailer')   → ServiceNotFoundException (ne suit pas l'alias)
   findDefinition('mailer')  → Definition de app.mailer (suit l'alias)

🌍 In Real Life

La situation : le responsable consulte la fiche d'un poste, éventuellement en suivant un renvoi du registre, puis corrige son réglage prévu.

L’équivalent dans Symfony : fiche → Definition ; renvoi → alias ; lecture directe → getDefinition() ; lecture suivant le renvoi → findDefinition() ; réglage prévu → setArgument().

Retour à la réalité technique : ces méthodes manipulent le graphe du builder, pas des instances métier. replaceArgument() exige un emplacement existant. has() peut reconnaître davantage qu'une définition ; il ne garantit donc pas universellement que findDefinition() aboutira.

🧠 Comment le mémoriser : « Lire le plan, suivre le renvoi. » Image mentale : un doigt suivant une flèche entre deux fiches. Question-réflexe : cet identifiant désigne-t-il une définition, un alias ou un objet déjà fourni ?

⚠️ À ne pas confondre : recueillir les identifiants tagués et les trier ; le tri nécessite un mécanisme distinct.

Où l'enregistrer

À retenir en priorité
  1. Le kernel peut enregistrer une passe dédiée.
  2. Un bundle peut utiliser son build().

Où en est-on ? Étape 2 sur 5. La passe est écrite. Question : qui l'exécute ? Personne, tant qu'elle n'est pas enregistrée auprès du compilateur.

Une classe découverte comme service n'est pas, pour cette seule raison, une passe exécutée par le compilateur. L'application ou le bundle doit l'enregistrer au point prévu :

Qui Écriture Priority
un bundle build() : $container->addCompilerPass(new HandlerPass()) 0
l'application, une class de passe Kernel::build() : addCompilerPass() 0
une extension qui implémente l'interface rien : exécutée d'office -1000
l'application, le kernel lui-même Kernel implements CompilerPassInterface -10000

Les deux raccourcis des dernières lignes concernent l'extension enregistrée et le kernel effectif, pas n'importe quelle classe qui implémente l'interface. Pour le laboratoire d'export, un bundle actif peut porter l'enregistrement :

use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\HttpKernel\Bundle\AbstractBundle;

final class ExportBundle extends AbstractBundle
{
    public function build(ContainerBuilder $container): void
    {
        $container->addCompilerPass(new ExportRegionPass());
    }
}

ExportRegionPass doit être dans ce namespace ou importé. Résultat attendu : sa méthode process() participe à la compilation avec phase et priorité par défaut. Appeler cette méthode depuis une action de controller serait trop tard pour modifier le plan du container déjà utilisé.

🌍 In Real Life

La situation : une procédure de préparation existe dans un classeur ; il faut l'ajouter au programme de préparation pour qu'elle soit suivie.

L’équivalent dans Symfony : procédure → objet CompilerPass ; programme → liste des passes ; inscription → addCompilerPass() dans le build() approprié.

Retour à la réalité technique : une classe enregistrée comme service ne devient pas automatiquement une passe active. Les raccords particuliers de l'extension et du kernel effectifs ont leurs priorités propres. La passe intervient lors d'une compilation à laquelle elle participe, pas à chaque GET.

🧠 Comment le mémoriser : « Écrite ne veut pas dire programmée. » Image mentale : une procédure sortie du classeur et placée au planning. Question-réflexe : où cette passe est-elle enregistrée ?

⚠️ À ne pas confondre : CompilerPass préparant le conteneur et listener réagissant à un événement HTTP.

Les cinq étapes

À retenir en priorité
  1. L'étape précède l'optimisation par défaut.
  2. Une priority haute agit plus tôt dans la même étape.

Où en est-on ? Étape 3 sur 5. La passe est enregistrée. Question : quand s'exécute-t-elle, par rapport aux autres ? La compilation est découpée en cinq phases ; le choix de la phase précède celui de la priorité.

Le chargement et la fusion des extensions précèdent les cinq groupes de passes exposés par PassConfig, dans cet ordre :

  1. TYPE_BEFORE_OPTIMIZATION : transformations avant les optimisations.
  2. TYPE_OPTIMIZE : résolution et optimisation du graphe.
  3. TYPE_BEFORE_REMOVING : dernières adaptations avant les suppressions.
  4. TYPE_REMOVE : retrait et intégration des définitions selon leur usage.
  5. TYPE_AFTER_REMOVING : travail sur le graphe déjà réduit.

addCompilerPass($pass, $type, $priority) utilise par défaut TYPE_BEFORE_OPTIMIZATION et 0. La priorité la plus haute passe d'abord dans son groupe ; elle ne permet pas de franchir la frontière d'une phase.

Ainsi, deux passes enregistrées avant optimisation avec priorités 20 puis 0 exécutent d'abord 20. Une passe après suppression à priorité 1000 demeure après les deux. Choisissons d'abord l'état du graphe nécessaire, puis l'ordre local.

 extensions chargées + fusionnées (MergeExtensionConfigurationPass)
        │
        ▼
 ┌─ 1. BEFORE_OPTIMIZATION ─ (défaut) ─ priorités : 200 … 100 … 0 … -1000 … -10000
 ├─ 2. OPTIMIZE
 ├─ 3. BEFORE_REMOVING
 ├─ 4. REMOVE            ← les privés inutilisés disparaissent
 └─ 5. AFTER_REMOVING
 Dans chaque phase : priorité la plus haute d'abord.
 On ne remonte jamais d'une phase à l'autre avec une priorité.

🌍 In Real Life

La situation : le planning sépare préparation, contrôle et rangement ; être prioritaire au rangement ne permet pas de passer avant la préparation.

L’équivalent dans Symfony : créneau → groupe PassConfig ; rang dans le créneau → priorité de la passe ; planning global → ordre des cinq phases.

Retour à la réalité technique : la priorité décroissante s'applique dans le groupe choisi. TYPE_BEFORE_OPTIMIZATION et priorité 0 sont les valeurs par défaut ; une passe après suppression reste après cette suppression, même à priorité 1000.

🧠 Comment le mémoriser : « D'abord le créneau, ensuite le rang. » Image mentale : des colonnes de planning contenant chacune une liste triée. Question-réflexe : ces deux passes sont-elles dans la même phase ?

⚠️ À ne pas confondre : phases de compilation et événements de traitement d'une Request ; deux ordonnancements distincts.

Ce que l'étape rend visible

À retenir en priorité
  1. Référencer avant la suppression préserve le service.
  2. Une passe tardive ne restaure pas automatiquement la definition.

Où en est-on ? Étape 4 sur 5. Conséquence directe des phases : une passe ne voit que ce qui a déjà été produit. Question : quelle information est disponible, ou déjà perdue, à tel moment ?

Supposons un handler privé inutilisé que nous voulons raccorder à une chaîne conservée. Avant suppression, une nouvelle référence peut encore le rendre utile. Après suppression, la définition peut ne plus exister :

Passe Résultat
ajoute une référence à un service privé en TYPE_BEFORE_REMOVING conservé et injecté
la même en TYPE_AFTER_REMOVING compilation réussie ; ServiceNotFoundException à l'instanciation du consommateur
lit un tag de registerForAutoconfiguration(), priority 0 le tag est vu
la même, priority 200 rien : l'autoconfiguration tourne à 100

Les deux premières lignes décrivent ce cas précis : privé encore disponible avant retrait, puis supprimé parce qu'aucune référence ne le conservait. Ajouter trop tard une référence ne le ressuscite pas. Dans un graphe où les contrôles utiles sont déjà passés, l'erreur peut n'apparaître qu'à l'instanciation ; ce n'est pas une garantie universelle du moment d'échec ni la preuve que tous les privés ont nécessairement été supprimés.

Les deux dernières lignes concernent un tag produit par les règles d'autoconfiguration à priorité 100 avant optimisation. Une passe à 200 ne voit pas encore ce tag automatique ; elle pourrait voir un tag posé explicitement plus tôt. Une passe à 0 peut observer le résultat de cette autoconfiguration.

Le kernel qui implémente directement l'interface est enregistré à -10000 dans cette phase. Il passe après les priorités ordinaires, mais une passe personnalisée à -20000 pourrait passer après lui. Si le démarrage réutilise un cache compilé à jour sans recompilation, aucune de ces transformations n'est rejouée.

 priorité :  200        100               0        -1000        -10000
              │          │                │          │             │
          (votre passe)  autoconfiguration (votre   ExtensionPass  Kernel
           ne voit pas   pose les tags     passe     (extensions    (implements
           le tag auto)  automatiques      le voit)   avec passe)    interface)

🌍 In Real Life

La situation : lire un plan avant l'ajout d'une étiquette ne permet pas de la voir ; réclamer une fiche après son retrait ne la restaure pas.

L’équivalent dans Symfony : étiquette ajoutée → tag produit par autoconfiguration ; fiche retirée → définition privée supprimée ; consultation → passe exécutée à sa phase et priorité.

Retour à la réalité technique : la passe voit le résultat des transformations précédentes. Dans le cas décrit, priorité 200 précède l'autoconfiguration à 100 ; priorité 0 la suit. Une référence tardive ne recrée pas une cible supprimée. Le moment du diagnostic dépend des contrôles restant à effectuer.

🧠 Comment le mémoriser : « Ni demain, ni hier : le graphe maintenant. » Image mentale : un plan daté à l'instant de sa consultation. Question-réflexe : qui a déjà produit ou retiré l'information recherchée ?

⚠️ À ne pas confondre : absence d'un tag automatique encore à produire et absence d'un tag explicite déjà présent.

Passe ou configuration

À retenir en priorité
  1. Utiliser l'abstraction existante pour une collection.
  2. Réserver la passe aux modifications nécessaires.

Où en est-on ? Étape 5 sur 5. On sait écrire et placer une passe. Question : faut-il vraiment en écrire une ? Souvent non : une passe est couplée aux détails internes des définitions qu'elle touche.

Avant d'écrire une transformation du graphe, cherchons une option publique du bundle. Elle protège mieux des changements de détails internes. À défaut, une modification ciblée évite de recopier toute une définition :

Besoin Outil
un argument de ton service configuration (arguments, bind, #[Autowire])
un argument d'un service d'un bundle d'abord sa configuration publique ; sinon une passe ciblée avec setArgument()
les services d'un tag, injectés ensemble #[AutowireIterator] d'abord, une passe sinon
retirer un service d'un bundle tiers une passe : removeDefinition()

Pour notre propre service, arguments, bind ou Autowire sont plus directs. Pour une collection standard, l'iterator tagué évite une passe manuelle. Pour une transformation qui dépend du graphe fusionné, la passe est adaptée, mais elle devient couplée aux définitions qu'elle manipule.

Les extensions chargent leurs définitions dans des builders temporaires ; leur load() n'est pas le bon endroit pour chercher le graphe complet des autres bundles. La fusion réapplique ensuite les définitions et aliases applicatifs sauvegardés. Redéclarer un identifiant remplace donc toute sa définition ; cela ne fusionne pas automatiquement les arguments, tags et appels. Une passe ultérieure voit le graphe fusionné, dans l'état laissé par les passes précédentes, pas forcément toutes les définitions historiques.

Enfin, retirer une définition oblige à traiter les références qui la demandaient. removeDefinition() n'est ni un arrêt propre d'un service déjà construit ni une réparation de ses consommateurs.

 Extension A (container temp) ─┐
 Extension B (container temp) ─┼─▶ fusion ─▶ graphe complet ─▶ vos passes
 Application (services.yaml)  ─┘   (l'appli est ré-appliquée en DERNIER :
                                    même id = définition remplacée en entier)

🌍 In Real Life

La situation : chaque fournisseur apporte son plan de poste ; une fois les plans réunis, le responsable peut ajuster un raccord entre postes.

L’équivalent dans Symfony : plan du fournisseur → définitions chargées par une extension ; plans réunis → graphe fusionné ; ajustement transversal → CompilerPass à la phase adaptée.

Retour à la réalité technique : l'extension classique charge son sous-ensemble dans un builder temporaire ; une passe ultérieure voit le graphe fusionné dans son état courant. Préférer une option publique quand elle suffit. Redéclarer un identifiant remplace sa définition entière ; modifier un argument précis n'est pas la même opération.

🧠 Comment le mémoriser : « L'extension apporte ; la passe ajuste. » Image mentale : plusieurs plans réunis sur une table. Question-réflexe : faut-il charger une configuration locale ou transformer un graphe déjà assemblé ?

⚠️ À ne pas confondre : retirer une définition et réparer ses consommateurs ; leurs références doivent aussi être traitées.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La collecte et le tri sont distincts.
  2. Ne pas supposer un ordre de priority.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Chaque piège est suivi de pourquoi la mauvaise réponse paraît plausible.

  • Voir l’explication : Préparer n'est pas appeler.
    • Préparer n'est pas appeler. Préparer addHandler() ne l'appelle pas ; obtenir la chaîne configurée ne signifie pas encore envoyer les notifications. Plausible car « ajouter un appel » ressemble à « appeler ».
    • Le défaut est avant optimisation, priorité 0 : vérifier les deux valeurs, pas seulement la priorité. Plausible car on ne retient souvent que la priorité.
    • Une référence ajoutée après retrait ne recrée pas sa cible supprimée ; le moment du diagnostic dépend des contrôles encore exécutés. Plausible car on attend une erreur dès la compilation.
    • Une priorité 200 précède l'autoconfiguration à 100 dans cette phase, mais n'efface pas un tag explicite déjà présent. Plausible car « plus haut = plus puissant ».
    • Le kernel à -10000 n'est pas absolument la dernière passe possible. Plausible car -10000 paraît extrême.
    • Un cache réutilisé sans compilation ne rejoue pas process(). Plausible car on imagine la passe exécutée à chaque Request.
    • Un service peut porter plusieurs occurrences d'un tag : choisir une fois par service ou une fois par occurrence. Plausible car findTaggedServiceIds() rend un id par service.
    • findTaggedServiceIds() n'applique pas le tri de l'iterator tagué ; utiliser le helper approprié si la priorité fait partie du contrat. Plausible car l'iterator tagué, lui, trie.
    • Pour un alias, findDefinition() atteint la cible ; getDefinition() ne le suit pas. Plausible car les deux noms se ressemblent.
    • L'extension charge son sous-ensemble ; la passe voit le graphe fusionné à sa phase, éventuellement déjà transformé ou réduit. Plausible car « toute la configuration est chargée » semble s'appliquer partout.

Fiche express

À mémoriser

À retenir en priorité
  1. Les extensions chargent leur configuration.
  2. La passe intervient sur l'ensemble assemblé.

Pour transformer l'assemblage sans exécuter le blog :

  1. Préférer une option publique ou un iterator standard quand ils suffisent.
  2. Modifier des définitions, pas des instances métier obtenues par get().
  3. Enregistrer la passe dans le kernel ou le bundle approprié.
  4. Choisir la phase avant la priorité et nommer les données attendues.
  5. Raccorder les services nécessaires avant leur retrait.
  6. Suivre les aliases et interpréter explicitement occurrences et priorité des tags.
  7. Recompiler le container lorsque la règle change ; ne pas attendre son exécution à chaque Request ou chaque commande.

L'autowiring est lui-même une transformation du plan. Nous pouvons maintenant étudier précisément comment il choisit les arguments.

🧠 À retenir pour la certification

  • Une passe implémente CompilerPassInterface::process(ContainerBuilder) et modifie des définitions, jamais des objets métier.
  • Enregistrement : addCompilerPass() dans Bundle::build() ou Kernel::build() ; défaut TYPE_BEFORE_OPTIMIZATION, priorité 0.
  • Cinq phases : BEFORE_OPTIMIZATION → OPTIMIZE → BEFORE_REMOVING → REMOVE → AFTER_REMOVING ; priorité haute d'abord dans la phase.
  • Autoconfiguration à 100 ; extension avec passe à -1000 ; kernel implémentant l'interface à -10000.
  • getDefinition() ne suit pas les alias, findDefinition() si ; findTaggedServiceIds() ne trie pas ; replaceArgument() exige l'emplacement.
  • Extension : container temporaire ; l'application est ré-appliquée en dernier ; redéclarer un id remplace toute la définition.
  • Une référence ajoutée après le retrait des privés ne ressuscite rien ; un cache à jour ne rejoue pas les passes.

Phrase de mémorisation : « La passe réécrit le plan, pas l'objet : d'abord la phase, ensuite la priorité, et elle ne voit que ce qui précède. »
