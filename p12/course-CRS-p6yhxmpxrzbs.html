Objectif

La requête GET /blog/42 peut encore exécuter son contrôleur alors qu'un calcul réutilisable n'a pas changé. De même, consulter un rapport d'import ne devrait pas recalculer son résumé coûteux à chaque lecture. Le composant Cache mémorise ces valeurs applicatives, sans décider à lui seul si une réponse HTTP peut être partagée.

Le fil du cours : demander une valeur au cache en lui donnant la recette pour la refaire. On le déroule en sept étapes : l'idée (get() + callable), le vocabulaire (item, pool…), l'API qui surprend, la ruée, PSR-6, PSR-16 et les bridges, enfin les pools du framework.

L'essentiel

À comprendre

À retenir en priorité
  1. La lecture et le calcul sont réunis.
  2. Le caller fournit la stratégie de reconstruction.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Certains calculs sont coûteux et leur résultat change rarement. Écrire à la main « lire, tester, calculer, sauvegarder » dans chaque action est répétitif et dangereux sous charge.
  • Le problème que Symfony résout. Une API où lecture et reconstruction sont un seul appel (get() + callable), protégée par défaut contre la ruée.
  • Ce que l'auteur veut que vous compreniez. Il n'y a pas de set() : on ne « range » pas une valeur, on demande une valeur avec la recette pour la refaire. Les autres API (PSR-6, PSR-16) existent pour les bibliothèques tierces.
  • Pourquoi c'est à l'examen. Les questions portent sur : l'absence de set(), $save par référence, beta, null ≠ absence (isHit()/has()), saveDeferred() + commit(), les bridges, cache.app ≠ cache.system, les tags.

Le component Cache met des valeurs en cache dans le code. L'API recommandée, les Cache Contracts, n'a que get() et delete() : pas de set(), car get() reçoit un callable qui produit la valeur au manque. Le reste de la page répond à trois questions : quelle API, que fait get() au juste, et quel pool.

Un pool est un espace logique d'entrées, chacune identifiée par une clé. Le code déclare comment reconstruire la valeur si nécessaire. Il faut donc pouvoir la recalculer : ce cache n'est pas le stockage de référence du catalogue ni une file durable de travaux Messenger. Le cache HTTP, lui, peut répondre avant que ce code soit atteint.

Comparaison : cache applicatif et cache HTTP

Cache applicatif (ce cours) Cache HTTP
Ce qui est mémorisé une valeur calculée une réponse HTTP entière
Où il agit dans le code (controller, service) avant le code (proxy)
Clé celle que vous choisissez l'URI
Invalidation delete(), tags expiration / validation

Le schéma

À retenir en priorité
  1. Le miss déclenche le calcul.
  2. La valeur retournée peut ensuite être réutilisée.

Où en est-on ? Étape 1 sur 7 : avant le vocabulaire, on regarde ce que fait l'appel central, get(). Tout le reste du cours (ruée, PSR-6, pools) se rattache à ce diagramme.

Lire le losange comme une décision de réutilisation, pas comme un simple test « la clé existe ». Une valeur présente peut être recalculée en avance :

Bleu : opérations ; ambre : décisions ; vert : valeur retournée. Vue logique hors coordination du lock et pannes du stockage. Le callback doit supporter plusieurs exécutions : le cache n'est pas une garantie d'exécution métier unique.

Les trois chemins, en une ligne

 get('k', $recette)
   ├─ valeur présente, pas élue en avance → rendue, recette NON exécutée
   ├─ manque, ou recalcul anticipé        → recette exécutée
   │       ├─ $save = true  → stockée puis rendue
   │       └─ $save = false → rendue seulement (rien n'est écrit)

L'exemple : un calcul coûteux

Exemple concret

À retenir en priorité
  1. Le pool applicatif contient les données métier mises en cache.
  2. Le pool système a une autre finalité.
  3. Les tags de cet exemple exigent TagAwareCacheInterface ; l'alias standard est cache.app.taggable, pas le pool cache.app non tag-aware.

Où en est-on ? Étape 2 sur 7 : un exemple complet mais court, pour voir get(), une échéance, un tag et $save ensemble. On reviendra sur chaque élément dans les parties suivantes.

Le rapport résume ici le dernier état global de l'import du blog. Un tag regroupe des entrées à invalider ensemble ; ce n'est pas leur clé. Cet exemple reçoit explicitement un TagAwareCacheInterface. Le callable $compute représente le calcul métier fourni par l'appelant ; il doit retourner une string. La fonction conserve une valeur non vide pendant une heure et associe le tag reports. Une valeur vide est retournée mais non sauvegardée.

use Symfony\Contracts\Cache\ItemInterface;
use Symfony\Contracts\Cache\TagAwareCacheInterface;

function cachedReport(TagAwareCacheInterface $cache, callable $compute): string
{
    return $cache->get('blog.import.report.v1', function (ItemInterface $item, bool &$save) use ($compute): string {
        $item->expiresAfter(3600);
        $item->tag(['reports']);
        $result = $compute();
        $save = '' !== $result;

        return $result;
    }, 0.0);
}

Avec un pool compatible, deux appels successifs réutilisent la valeur non vide ; $cache->invalidateTags(['reports']) impose un nouveau calcul au prochain appel. Le beta égal à zéro désactive ici le recalcul anticipé, pas la mémorisation. Dans la configuration standard de FrameworkBundle 8.0, l'autowiring de TagAwareCacheInterface fournit cache.app.taggable, qui enveloppe cache.app. L'alias de CacheInterface reste cache.app : son adapter filesystem standard n'est pas tag-aware. Appeler tag() sur cet item non taggable lève une LogicException. Une application peut remplacer ces alias : vérifier sa configuration effective plutôt que déduire la capacité des tags du nom du pool.

Les appels réutilisent la valeur tant qu'elle reste présente et non périmée, sans invalidation entre eux. Après un import qui change les données du rapport, l'application invalide le tag ; elle ne recompte pas sur un redémarrage du conteneur. Pour des rapports par import, langue ou lecteur, la clé doit inclure ces dimensions autorisées : une clé globale ne les sépare pas. Le calcul doit rester répétable et ne pas envoyer lui-même la notification.

Ce que fait chaque ligne de la recette

Ligne Rôle
$item->expiresAfter(3600) l'entrée vit une heure
$item->tag(['reports']) l'entrée rejoint le groupe reports
$save = '' !== $result ne sauvegarde pas une chaîne vide
0.0 (3ᵉ argument) beta : aucun recalcul anticipé

Pourquoi l'item reçoit-il tag() alors que CacheInterface n'a pas de tags ?

Parce que les tags sont une capacité du pool, pas de l'API get(). Avec l'autowiring de TagAwareCacheInterface, Symfony injecte cache.app.taggable (qui enveloppe cache.app) ; avec CacheInterface, c'est cache.app, dont l'adapter filesystem n'est pas tag-aware, et tag() lève une LogicException.

Trois API, une recommandée

À retenir en priorité
  1. Choisir l'API selon le contrat consommateur.
  2. Un stockage peut servir plusieurs abstractions.

Où en est-on ? Étape 3 sur 7 : avant le vocabulaire, il faut savoir quelle API utiliser : trois existent pour des raisons historiques et d'interopérabilité.

Un service applicatif peut choisir les Contracts ; une bibliothèque existante impose parfois une autre interface. Ce choix ne dit pas encore si la valeur vit en mémoire, dans un fichier ou sur un serveur de cache :

  • les Cache Contracts — recommandés : moins de code, et protection contre la ruée par défaut ;
  • PSR-6 — pools et items, quand une bibliothèque tierce l'exige ;
  • PSR-16 — un cache « simple », sans object item.

Les adapters parlent à la fois les Cache Contracts et PSR-6 : on choisit l'API selon le contrat qu'attend le code consommateur.

La protection évoquée concerne l'implémentation Symfony et ses conditions de fonctionnement ; déclarer une interface n'installe pas un verrou distribué universel. Nous préciserons ce point dans « La ruée sur le cache ».

Comparaison des trois API

Cache Contracts PSR-6 PSR-16
Opérations clés get(), delete() getItem(), save(), commit()… get(), set(), has()
Objet item ItemInterface dans le callback oui (CacheItemInterface) non
Écriture via le callback set() puis save() set() direct
Anti-ruée par défaut oui non non
Quand code applicatif bibliothèque exigeant PSR-6 bibliothèque exigeant PSR-16

Quatre mots

À retenir en priorité
  1. Le pool isole les keys.
  2. L'adapter choisit le mécanisme de stockage.

Où en est-on ? Étape 4 sur 7 : le vocabulaire. Les mots item, pool, adapter, provider reviennent dans toutes les parties suivantes ; ils désignent quatre rôles différents.

🌍 In Real Life

La situation : le secrétariat du blog range les résumés d'import dans des casiers nommés, éventuellement installés dans le même dépôt.

L’équivalent dans Symfony : fiche identifiée → item ; casier logique → pool ; dispositif de rangement → adapter ; liaison vers le dépôt → provider.

Retour à la réalité technique : les pools du framework disposent de namespaces pour séparer leurs clés. Cette séparation logique n'est pas une barrière d'autorisation entre utilisateurs et ne suppose pas des serveurs distincts.

🧠 Comment le mémoriser : « La même étiquette peut vivre dans deux casiers. » Image mentale : deux tiroirs contenant chacun une fiche 42. Question-réflexe : quel pool et quel namespace utilise cet appel ?

⚠️ À ne pas confondre : interface de cache, adapter de stockage et connexion au stockage.

Terme Definition
Item une unité stockée : une key, une valeur
Pool un repository logique d'items ; toutes les opérations passent par lui
Adapter la class qui implémente le stockage réel — files, Redis…
Provider le service de connexion au stockage, notion propre au framework 
 votre code ──▶ Pool (interface) ──▶ Adapter ──▶ Provider ──▶ stockage
   get('k')     « mon casier »       Filesystem   connexion    files, Redis…
                                      / Redis…    (DSN)

Chaque pool du framework reçoit un namespace dérivé de son nom : deux pools ne se heurtent pas sur un stockage partagé.

Par exemple, deux pools nommés peuvent stocker chacun une clé summary sur la même connexion sans désigner la même entrée. Ce namespace est une séparation logique, pas une permission : un code ayant accès au stockage n'est pas isolé comme par un contrôle d'accès. En standalone, deux adapters auxquels on donne volontairement le même namespace et le même stockage peuvent au contraire partager les données.

Pourquoi deux pools peuvent-ils avoir la même clé sans collision ?

Le namespace est préfixé à la clé avant d'arriver au stockage. summary dans le pool A et summary dans le pool B deviennent donc deux clés distinctes, même sur la même connexion.

⚠️ À ne pas confondre : adapter et provider. Plausible car les deux « parlent au stockage » ; mais l'adapter implémente le stockage, le provider est seulement la connexion que l'adapter utilise.

L'API qui surprend

À retenir en priorité
  1. Un callback ne signifie pas toujours un miss.
  2. Le recalcul anticipé peut voir un hit.

Où en est-on ? Étape 5 sur 7 : on revient sur get() pour comprendre ce qui surprend : un callable qui n'est pas toujours exécuté, et un $save passé par référence.

🌍 In Real Life

La situation : on demande au secrétariat le résumé d'import du blog en lui donnant aussi la recette pour le refaire si nécessaire.

L’équivalent dans Symfony : résumé demandé → clé ; recette → callback de get() ; résumé réutilisé → valeur du cache ; préparation requise → calcul puis retour.

Retour à la réalité technique : les Contracts regroupent lecture et reconstruction. Le callback peut aussi être choisi pour un recalcul anticipé ; sa présence ne prouve ni son exécution à chaque appel ni une absence systématique de valeur.

🧠 Comment le mémoriser : « Demander avec la recette de secours. » Image mentale : fiche conservée avec son mode de fabrication. Question-réflexe : pourquoi le callback est-il appelé cette fois ?

⚠️ À ne pas confondre : valeur retournée au demandeur et valeur effectivement sauvegardée.

La fonction de reconstruction évite de répéter « lire, tester, calculer, sauvegarder » dans chaque action. La présence d'un callback ne signifie pas qu'il sera exécuté à chaque demande :

  • get() lit et écrit : la valeur et la façon de la produire sont déclarées au même endroit.
  • Le callable tourne au manque, et sur une key présente quand le recalcul anticipé l'élit ou que beta vaut INF ; $item->isHit() y rend alors true.
  • bool &$save, passé par référence : false empêche l'enregistrement.

Pourquoi $save est-il passé par référence ?

Le callback retourne la valeur ; il n'a pas d'autre canal pour dire « ne la sauvegarde pas ». Le & permet à Symfony de lire, après l'appel, ce que le callback a mis dans $save. Sans &, la modification resterait locale.

Avec Cache 8.0 et son autoload chargés, ce petit calcul en mémoire permet d'observer la réutilisation sans stockage externe :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;
use Symfony\Contracts\Cache\ItemInterface;

$cache = new ArrayAdapter();
$calls = 0;
$compute = static function (ItemInterface $item) use (&$calls): int {
    ++$calls;
    $item->expiresAfter(60);
    return 6 * 7;
};
$first = $cache->get('answer', $compute, 0.0);
$second = $cache->get('answer', $compute, 0.0);
var_dump($first, $second, $calls);

Avant expiration, valeurs attendues : 42, 42, 1. Cet ArrayAdapter appartient à cette instance PHP : ce test ne démontre pas un partage entre un worker et le serveur HTTP. $save = false ne supprime pas la valeur retournée, ne prouve pas une sauvegarde et ne vaut pas delete() d'une ancienne entrée. Une exception du calcul n'est pas transformée en résultat métier valide.

Dérouler l'exemple, appel par appel

 appel 1 : get('answer')  → manque → recette exécutée ($calls = 1) → 42 stocké
 appel 2 : get('answer')  → présent, beta = 0.0 → recette NON exécutée → 42
 résultat : var_dump → 42, 42, 1

Comparaison : valeur retournée et valeur sauvegardée

Valeur retournée Valeur sauvegardée
$save = true (défaut) oui oui
$save = false oui non
exception dans le callback non (propagée) non

La ruée sur le cache

À retenir en priorité
  1. Zéro ne désactive pas le cache.
  2. INF demande le calcul immédiatement.

Où en est-on ? Étape 6 sur 7 (partie 1/2) : on comprend ce que la « protection par défaut » des Contracts fait vraiment, et ce qu'elle ne fait pas.

🌍 In Real Life

La situation : toute l'équipe réclame le même résumé périmé. Un bureau coordonne sa préparation et peut choisir de le refaire avant l'heure limite.

L’équivalent dans Symfony : coordination locale → verrou ; préparation choisie avant échéance → recalcul probabiliste ; anticipation réglée → beta.

Retour à la réalité technique : le verrou local ne devient pas distribué parce que le stockage est partagé. beta = 0 désactive l'anticipation, pas le cache ; une expiration et les métadonnées adaptées permettent la sélection anticipée.

🧠 Comment le mémoriser : « Anticiper la file, sans promettre un chef mondial. » Image mentale : un responsable dans chaque bureau. Question-réflexe : quelle est la portée réelle du verrou ?

⚠️ À ne pas confondre : protection contre les recalculs concurrents et garantie globale d'exécution unique.

Quand une key coûteuse expire, des Requests simultanées pourraient toutes refaire le même travail. L'implémentation Symfony réduit cette ruée par un verrou local et un recalcul anticipé probabiliste. Le verrou de calcul ne devient pas un mutex distribué parce que deux serveurs utilisent la même clé ou le même stockage. Le beta, troisième parameter de get(), règle l'anticipation : 1.0 par défaut, plus haut = plus tôt, 0 la désactive sans désactiver le cache, INF force le recalcul. Seul un item doté d'une échéance peut être élu en avance, avec les métadonnées de durée de calcul utilisées par le mécanisme.

 sans protection :   100 requêtes ─ clé expirée ─▶ 100 calculs coûteux
 avec protection :   100 requêtes ─ clé expirée ─▶ 1 calcul (verrou local)
                     + recalcul élu AVANT l'échéance (beta) pour éviter le trou

Le calcul élu s'effectue dans l'appel courant, sauf intégration de recalcul asynchrone explicitement configurée. Ce n'est pas un worker Messenger implicite. Augmenter beta favorise une reconstruction plus précoce ; ce n'est ni une nouvelle durée de vie ni une garantie de cadence.

Le verrou par défaut s'appuie sur des fichiers locaux et flock(). Il dépend du support disponible et est désactivé par défaut sur Windows ; certains chemins exécutent le callback sans verrou, notamment si son ouverture n'est pas possible. Il ne faut donc jamais traiter le callback comme une opération métier « exactement une fois ». Le rapport se recalcule ; l'envoi du courriel et la publication d'un article demandent un autre contrat.

Comparaison des valeurs de beta

beta Effet Cas d'usage
0 aucun recalcul anticipé ; le cache reste actif comportement prévisible
1.0 défaut équilibre
> 1 anticipation plus précoce calcul très coûteux
INF recalcul immédiat même sur une key présente forcer / tester

PSR-6 : écrire soi-même

À retenir en priorité
  1. L'item modifié reste local avant sauvegarde.
  2. save() réalise la persistance.

Où en est-on ? Étape 6 sur 7 (partie 2/2) : les Contracts cachent « lire / écrire ». PSR-6 les rend visibles : on obtient un item, on le modifie, on demande au pool de le sauvegarder.

🌍 In Real Life

La situation : corriger une fiche de résumé sur son bureau ne la remet pas dans l'armoire commune du blog.

L’équivalent dans Symfony : fiche locale modifiée → CacheItem::set() ; demande de rangement → save() ; pile d'attente → saveDeferred() ; enregistrement du lot → commit().

Retour à la réalité technique : l'item et le pool jouent des rôles distincts. Un null sauvegardé peut être un hit ; le manque se détermine par isHit(), pas seulement par la valeur. Le moment du commit dépend aussi du pool.

🧠 Comment le mémoriser : « Corriger, puis ranger. » Image mentale : fiche encore posée devant l'armoire fermée. Question-réflexe : quelle opération a demandé la sauvegarde ?

⚠️ À ne pas confondre : écriture différée locale et file de travail Messenger.

PSR-6 rend visibles les étapes que les Contracts regroupent. L'item obtenu est un objet local ; le modifier n'est pas encore demander au pool de sauvegarder sa nouvelle valeur :

Opération Effet
set('x') sans save() rien n'est stocké
set(null) puis save() isHit() vrai, get() rend null
saveDeferred() avec FilesystemAdapter reste différé jusqu'à un commit() explicite ou déclenché par le pool
deleteItem('k') l'item disparaît

ArrayAdapter enregistre tout de suite : son saveDeferred() appelle save(). expiresAfter() et expiresAt() fixent l'échéance.

 $item = $pool->getItem('k')   ← objet LOCAL (copie de travail)
 $item->set($v)                ← modifie la copie, rien n'est stocké
 $pool->save($item)            ← écrit tout de suite
 $pool->saveDeferred($item)    ← met en file ; écrit au commit()
 $pool->commit()               ← écrit la file

Dans l'implémentation des adapters fondés sur AbstractAdapterTrait, getItem() d'une clé encore différée appelle commit() avant de lire. Cela peut rendre les sauvegardes visibles à un autre pool partageant le stockage ; ce n'est pas une visibilité spéciale réservée au premier objet PHP. La sauvegarde reste soumise à son résultat et à l'expiration. Pour vider explicitement le lot, appeler commit() plutôt que dépendre d'un effet de bord de lecture ; cela ne constitue pas une transaction métier.

Un résultat absent du catalogue peut être représenté volontairement par null, avec une politique d'expiration adaptée. Voici la différence entre cette valeur et un manque, en mémoire :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;

$pool = new ArrayAdapter();
$item = $pool->getItem('optional-result');
$item->set(null);
$pool->save($item);
$loaded = $pool->getItem('optional-result');
var_dump($loaded->isHit(), $loaded->get());

Résultat attendu : true, puis null. Tester seulement $loaded->get() === null ferait recalculer inutilement ce résultat connu. À l'inverse, garder indéfiniment l'absence de l'article 999 empêcherait de voir sa création ultérieure sans invalidation.

Pourquoi isHit() et non get() === null ?

get() rend null dans deux situations : valeur null sauvegardée, ou manque. Seul isHit() les distingue.

Situation isHit() get()
null sauvegardé true null
clé absente false null

PSR-16 et les bridges

À retenir en priorité
  1. null peut être une valeur valide.
  2. L'existence est une information distincte.

Où en est-on ? Étape 7 sur 7 : la dernière API. Les bridges relient les trois API entre elles pour qu'une bibliothèque PSR-16 puisse parler à votre code Contracts, et inversement.

Ici, « bridge » désigne seulement l'adaptation entre contrats de cache fournie par le composant Cache, pas une intégration tierce supplémentaire. La bibliothèque consommatrice choisit le sens nécessaire :

get('k', 'défaut') rend le défaut au manque ; has() distingue un null stocké d'une absence. Psr16Cache fait d'un pool PSR-6 un cache PSR-16 ; Psr16Adapter fait l'inverse, et parle aussi les Cache Contracts.

   pool PSR-6 ──────── Psr16Cache ────────▶ cache PSR-16
   cache PSR-16 ────── Psr16Adapter ──────▶ pool PSR-6 (+ Cache Contracts)

Avec Cache 8.0, les interfaces PSR-6 et PSR-16 disponibles et l'autoload chargé, cet exemple ne manipule que des données en mémoire :

<?php
use Symfony\Component\Cache\Adapter\ArrayAdapter;
use Symfony\Component\Cache\Adapter\Psr16Adapter;
use Symfony\Component\Cache\Psr16Cache;

$pool = new ArrayAdapter();
$simple = new Psr16Cache($pool);
if (!$simple->set('optional', null, 60)) {
    throw new RuntimeException('Échec de sauvegarde.');
}
var_dump($simple->has('optional'));
var_dump($simple->get('optional', 'absent'));
var_dump($simple->get('missing', 'absent'));

$poolForAnotherConsumer = new Psr16Adapter($simple);
$item = $poolForAnotherConsumer->getItem('optional');
var_dump($item->isHit(), $item->get());

Sorties attendues avant expiration : true, null, absent, puis true et null. Le défaut PSR-16 n'est pas le callback des Contracts. Le dernier wrapper sert à comparer les interfaces ; il est inutile si le consommateur accepte déjà le pool initial. L'adaptation ne rend pas les données durables et n'ajoute pas les tags. Enfin, has() puis get() ne sont pas une lecture atomique : une autre opération peut modifier l'entrée entre les deux appels.

Pourquoi get('optional', 'absent') rend-il null et non 'absent' ?

La clé existe avec la valeur null : ce n'est pas un manque, donc le défaut n'est pas utilisé. Seule missing, absente, rend 'absent'.

Part de un pool PSR-6 un cache PSR-16
Donne un cache PSR-16 un pool PSR-6 (et Cache Contracts)

Les pools du framework

À retenir en priorité
  1. Le cache système suit le code déployé.
  2. Il n'est pas seulement un cache applicatif plus rapide.
  3. Le tag regroupe des items par préoccupation.
  4. L'invalidation par tag exige un pool tag-aware.

Où en est-on ? Fin du parcours : on sait appeler le cache ; reste à savoir quel pool le framework nous fournit et pourquoi il y en a deux.

Le rapport d'import change avec les données métier ; des métadonnées dérivées des classes changent avec le code déployé. Cette différence, pas une préférence de vitesse, guide le choix :

Pool Usage Adapter par défaut
cache.app données applicatives cache.adapter.filesystem
cache.system ce qui dérive du code source cache.adapter.system

cache.system se régénère au préchauffage et ne change qu'au deployment ; cache.adapter.system choisit le stockage : files PHP, chaînés derrière APCu quand il est là. Pour cache.app, Redis permet de survivre au deployment et de partager entre serveurs. Adapters : apcu, array, filesystem, memcached, pdo, psr6, redis, valkey.

La survie à un déploiement exige aussi un stockage conservé, un namespace stable et une représentation compatible avec le nouveau code. Changer simplement le nom d'adapter ne garantit aucune de ces conditions. Le préchauffage du cache système n'est pas le recalcul systématique du rapport à chaque requête, ni la reconstruction de tous les services.

Avec un pool tag-aware, deux rapports portant reports sont invalidés par invalidateTags(['reports']) sans connaître leurs clés ; une entrée portant seulement settings n'est pas ciblée. delete('reports') viserait une clé, et clear() viderait plus largement le pool. Les tags servent à la cohérence de valeurs applicatives : ils ne purgent pas automatiquement un reverse proxy HTTP.

Comparaison : delete(), invalidateTags(), clear()

Opération Portée Exemple
delete('reports') une clé l'entrée nommée reports
invalidateTags(['reports']) toutes les entrées portant ce tag deux rapports, sans connaître leurs clés
clear() tout le pool tout cache.app

Pourquoi cache.system n'est-il pas un cache.app plus rapide ?

Il suppose que ses données se recalculent depuis le code source : il est régénéré au préchauffage et ne change qu'au deployment. Y stocker un rapport métier qui change avec les données serait une erreur de catégorie.

⚠️ À ne pas confondre : « stocker durablement » et « survivre à un déploiement ». Plausible car un file ou Redis persistent ; mais il faut aussi un namespace stable et une représentation compatible avec le nouveau code.

Un pool compatible TagAwareCacheInterface associe des tags aux items dans le callback avec $item->tag(['products']). invalidateTags(['products']) invalide ensuite les items liés à cette préoccupation sans connaître chacune de leurs keys. Le pool doit être tag-aware ; les tags ne sont pas une propriété de toutes les implémentations PSR-6.

Piège à éviter

À retenir en priorité
  1. Le callback contrôle la sauvegarde.
  2. Le passage par référence est essentiel.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les sept étapes sont faites. Voici les erreurs de QCM probables et la raison de leur plausibilité.

  • Voir l’explication : Il n'existe pas de set()

    Il n'existe pas de set() dans les Cache Contracts ; en PSR-6, set() sans save() n'écrit rien. Pourquoi on se trompe : PSR-16 a un set() et l'on généralise.

  • Voir l’explication : null n'est pas une absence

    null n'est pas une absence : isHit() en PSR-6, has() en PSR-16. Pourquoi on se trompe : en PHP, null évoque « rien ».

  • Voir l’explication : $save est passé par référence

    $save est passé par référence ; le mettre à false empêche l'enregistrement. Pourquoi on se trompe : on croit qu'il faut le retourner.

  • Voir l’explication : Le rappel ne tourne pas qu'au manque.

    Le rappel ne tourne pas qu'au manque. Avec beta à INF, il tourne sur une key présente, et isHit() y rend true. Pourquoi on se trompe : « callback = cache miss » est le cas le plus courant.

  • Voir l’explication : cache.system n'est pas un cache.app plus rapide

    cache.system n'est pas un cache.app plus rapide : il suppose des données dérivables du code source. Pourquoi on se trompe : le nom « system » évoque un cache générique optimisé.

Fiche express

À mémoriser

À retenir en priorité
  1. La valeur et l'état de présence sont indépendants.
  2. Utiliser isHit() pour décider.

Pour la consultation du rapport, la question est : « puis-je réutiliser cette valeur et comment la reconstruire ? » Pour /blog/42 au niveau HTTP, c'est : « puis-je réutiliser cette réponse pour ce lecteur ? » Les deux caches peuvent coexister, mais leurs clés et invalidations ne se synchronisent pas automatiquement.

Si tu dois retenir seulement 7 choses :

  • Item, pool, adapter, provider ; un namespace par pool.
  • Cache Contracts : get() et delete(), pas de set().
  • Callable : au manque ou en avance ; &$save ; beta 0 = jamais en avance, INF = tout de suite.
  • PSR-6 : save() ; saveDeferred() + commit() explicite, avec des déclenchements anticipés possibles selon l'adapter.
  • null n'est pas une absence : isHit(), has().
  • cache.app pour les données, cache.system pour le dérivé du code.
  • tag() + invalidateTags() (TagAwareCacheInterface).

🧠 À retenir pour la certification :

  • Cache Contracts = get() + delete() ; pas de set() : le callable produit la valeur.
  • Le callable tourne au manque ou en recalcul anticipé ; &$save = false n'écrit pas mais la valeur est retournée.
  • beta : 0 désactive l'anticipation, INF force le recalcul ; le verrou est local, pas distribué.
  • PSR-6 : set() ne stocke rien sans save() ; saveDeferred() attend commit() (ou un getItem() de la même clé).
  • null stocké = hit : isHit() (PSR-6), has() (PSR-16).
  • Psr16Cache : pool PSR-6 → PSR-16 ; Psr16Adapter : PSR-16 → pool (et Contracts).
  • cache.app (données) ≠ cache.system (dérivé du code) ; tags → TagAwareCacheInterface, jamais le proxy HTTP.

Moyen mnémotechnique : « Demander, pas écrire ».

Phrase de mémorisation : « Je demande une valeur au pool avec la recette pour la refaire ; le cache la rend telle quelle ou la recalcule, et isHit() me dit si une valeur null est un vrai hit. »

Pour vérifier ces contrats sans réseau, repartir des tests unitaires et d'un pool mémoire ; tester séparément le stockage partagé et la concurrence dans un environnement adapté.
