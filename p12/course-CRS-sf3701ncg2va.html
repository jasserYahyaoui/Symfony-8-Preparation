Objectif

app:blog:import est enregistrée. Nous voulons maintenant qu'une autre personne sache l'utiliser sans lire son code, et qu'un ancien script continue à fonctionner après un changement de nom. Décrire la commande résout ces deux problèmes sans exécuter l'import. La branche de création d'un auteur illustrera les mêmes métadonnées et leurs limites.

L'essentiel

À comprendre

À retenir en priorité
  1. La metadata permet une découverte lazy.
  2. Lister les commands évite une construction inutile.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une commande est une interface : on doit pouvoir la trouver, la lire (liste, aide) et la renommer sans casser les scripts existants. Tout cela relève de métadonnées, pas du traitement.
  • Le piège de fond. Les métadonnées d'identité (nom, alias, description) ne sont pas les valeurs passées à l'exécution, et hidden n'est pas une protection.
  • Ce que l'auteur veut que vous compreniez. Déclarer dans l'attribut permet à Symfony de lister sans construire la commande (chargement lazy) ; configure() fait la même chose en style classique mais à la construction.
  • Pourquoi c'est à l'examen. La syntaxe a|b|c, le premier segment vide, l'ordre propriétés / parent::__construct() et le sort des usages.

La configuration décrit comment appeler une commande : son nom, ses alias et l'aide affichée. Elle ne doit pas effectuer son traitement métier. #[AsCommand] rend ces métadonnées accessibles sans construire l'objet commande ; le framework peut ainsi afficher une liste sans charger toutes les dépendances coûteuses.

Ces métadonnées sont des informations de présentation et d'identité. Elles ne sont ni les valeurs du fichier CSV à traiter, ni une configuration à recalculer pour chaque article. Le chargement lazy, ou différé, permet de reporter la construction réelle jusqu'à ce qu'elle soit utile.

Dans le style classique, configure() s'exécute pendant la construction de Command. Toute propriété qu'elle lit doit donc déjà être initialisée. Déclarer hidden: true masque une entrée de catalogue, mais ne protège ni ne désactive son exécution.

MÉTADONNÉES (décrire)               VALEURS (exécuter)
name, aliases, description,         Alice, articles.csv, --dry-run
help, usages, hidden                (entrée Console, à chaque appel)
  → lues pour `list` et `help`        → lues dans __invoke()

Le schéma

À retenir en priorité
  1. La définition précède l'exécution.
  2. Elle ne dépend pas toujours de l'entrée utilisateur.

Où en est-on ? Nous savons qu'on décrit sans exécuter. Reste à comprendre pourquoi déclarer dans l'attribut change quelque chose : le schéma montre comment une description arrive jusqu'à list sans construire le service.

Si la description de l'import exigeait de construire son service et toutes ses dépendances, un simple list pourrait coûter cher. Le framework prépare un représentant léger, LazyCommand, avec les informations nécessaires à la liste :

Gris et pointillés : préparation du container ; bleu et traits pleins : objets et opérations à l'exécution ; vert : résultat visible. Ce parcours suppose une commande enregistrée et une description disponible dans ses métadonnées. Une description calculée seulement dans configure() impose au contraire de construire l'objet pour la connaître.

La limite est volontaire : LazyCommand::getDefinition() et getHelp() délèguent à la vraie commande. Ne pas transformer « la liste ordinaire peut lire la description sans construire le service » en « aucune lecture d'aide ne construit jamais une commande ». Un constructeur doit rester sans import, création de compte ou autre effet métier.

L'exemple : créer un user

Exemple concret

À retenir en priorité
  1. L'ordre du constructor est essentiel.
  2. configure() doit voir un état initialisé.

Où en est-on ? Du schéma au code : la commande d'administration des auteurs, cette fois avec toutes ses métadonnées. Observez surtout ce que le code déclare et ce qu'il ne définit pas (les usages ne créent pas d'option).

Reprenons la commande d'administration des auteurs du cours précédent. Cette variante remplace l'autre classe d'exemple ; ne pas enregistrer deux classes concurrentes sous app:create-user. Cet exemple illustre les métadonnées, pas la création effective d'un compte. Le corps retourne seulement un succès ; les usages sont du texte d'aide, ils ne déclarent pas les arguments ni les options correspondants.

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;

#[AsCommand(
    name: 'app:create-user',
    description: 'Creates a new user.',
    help: 'This command allows you to create a user...',
    usages: ['bob', 'alice --as-admin'],
    aliases: ['app:add-user'],
)]
class CreateUserCommand
{
    public function __invoke(): int
    {
        return Command::SUCCESS;
    }
}

Une fois ce service enregistré, l'aide du nom principal et celle de l'alias désignent le même traitement :

php bin/console help app:add-user

Le nom principal reste app:create-user, la description attendue est Creates a new user. et l'aide longue contient This command allows you to create a user.... Ne pas essayer alice --as-admin comme si l'option était déjà définie : aucune option de ce nom n'existe dans la méthode montrée. La propagation des usages présente en outre une particularité de FrameworkBundle 8.0, détaillée ensuite.

Tout dans l'attribute

À retenir en priorité
  1. La liste affiche une description courte.
  2. L'aide développe les instructions.

Où en est-on ? Étape 1 sur 3 : le rôle de chaque paramètre de #[AsCommand]. Chacun répond à une question différente de l'utilisateur (quoi taper ? que fait-elle ? comment l'utiliser ?).

🌍 In Real Life

La situation : l'équipe du blog consulte la fiche d'un outil d'import sans démarrer la machine.

L’équivalent dans Symfony : référence de l'outil → name ; ligne du catalogue → description ; notice → help ; exemples d'emploi → usages.

Retour à la réalité technique : les métadonnées de commande décrivent son interface. Avec le chargement lazy approprié, la description peut être accessible sans construire toute la commande. Décrire n'exécute pas l'import.

🧠 Comment le mémoriser : « Lire la notice sans allumer. » Image mentale : une fiche devant un appareil éteint. Question-réflexe : cette information exige-t-elle une instance métier ?

⚠️ À ne pas confondre : aide descriptive et définition effective des arguments.

Chaque donnée répond à une question distincte : quel nom taper, quel résumé lire dans la liste, quelles instructions consulter dans l'aide ? Leur séparation permet d'améliorer la documentation de l'import sans changer son traitement :

Parameter Role
name le nom tapé après bin/console — seul obligatoire
description la ligne affichée par list
help le texte long de --help
usages des exemples, sans répéter le nom
aliases d'autres noms pour la même command
hidden retire la command de list, sans l'empêcher de tourner
  • Une description non vide disponible dans l'attribute permet au compiler pass de préparer une LazyCommand. La liste ordinaire utilise cette description sans construire le service concerné ; une description disponible seulement dans configure() exige sa construction.
  • La documentation montre usages dans l'attribute, mais FrameworkBundle 8.0 ne transmet que name, description et help au tag console.command : une command invocable y perd ses usages (getUsages() vaut []).

Pourquoi les usages disparaissent-ils ? Voici le mécanisme : AddConsoleCommandPass prépare l'invocable avec une définition de Command et un appel ultérieur à setCode(). Les usages absents du tag ne sont pas transférés par cette voie. Une sous-classe de Command, elle, lit ses propres usages d'attribut dans le constructeur parent. Le constat ci-dessus suppose l'autoconfiguration standard, sans tag manuel ni configuration supplémentaire des usages.

#[AsCommand(name, description, help, usages, aliases, hidden)]
        │ autoconfiguration FrameworkBundle 8.0
        ▼
tag console.command { command, description, help }     ← pas de « usages »
        ▼
AddConsoleCommandPass → Command + setCode(invocable)   → getUsages() = []

extends Command : le constructeur parent relit l'attribut → usages conservés

Lorsqu'un usage est effectivement ajouté, addUsage('bob') préfixe le nom : pour cette commande, l'usage devient app:create-user bob. Il reste du texte documentaire, pas une définition d'argument ou un appel de commande.

Pour observer les autres métadonnées sans dépendance métier, cette version de GreetCommand remplace celle du cours précédent :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Style\SymfonyStyle;

#[AsCommand(
    name: 'app:greet',
    description: 'Affiche un accueil.',
    aliases: ['app:hello'],
    hidden: false,
    help: 'Affiche un accueil et retourne un code de succès.',
)]
final class GreetCommand
{
    public function __invoke(SymfonyStyle $io): int
    {
        $io->writeln('Bonjour !');

        return Command::SUCCESS;
    }
}
php bin/console app:hello

Avec la découverte du service active et une verbosity normale :

Bonjour !

Le code vaut 0 et app:greet donne le même résultat. L'alias n'a pas créé un second traitement ni fourni une nouvelle valeur d'entrée.

Les alias

À retenir en priorité
  1. Le premier segment est le nom principal.
  2. Les suivants ajoutent des aliases.

Où en est-on ? Étape 2 sur 3 : renommer sans casser. Mécanisme : le paramètre name de l'attribut accepte une chaîne séparée par | ; Symfony la découpe, le premier segment est le nom, les suivants des alias.

🌍 In Real Life

La situation : le bureau du blog a changé de nom, mais l'ancienne plaque renvoie toujours au même guichet.

L’équivalent dans Symfony : plaque principale → nom de commande ; anciennes plaques → alias ; guichet unique → même commande.

Retour à la réalité technique : un alias déclaré fournit un autre nom d'appel, pas une copie du traitement. Une commande hidden reste appelable ; la retirer du catalogue visible ne constitue pas un contrôle d'accès.

🧠 Comment le mémoriser : « Plusieurs noms, un guichet. » Image mentale : deux flèches vers la même porte. Question-réflexe : ai-je déclaré un alias ou simplement abrégé un nom ?

⚠️ À ne pas confondre : invisibilité dans list et interdiction d'exécution.

Un ancien script peut encore appeler app:add-user. Plutôt que dupliquer le code, enregistrer cet ancien nom comme alias du même service. Voici un attribut à placer sur la classe, pas un programme PHP autonome :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[AsCommand(name: 'app:create-user|app:add-user|app:new-user')]

Le premier segment est le nom, les suivants des alias — la même chose que aliases, que l'attribute fusionne avec |. Un premier segment vide cache la command : name: '|app:secret' équivaut à hidden: true, et la command reste exécutable.

'app:create-user | app:add-user | app:new-user'
     nom réel      alias 1         alias 2

'  | app:secret'   → segment 1 vide = hidden ; app:secret reste appelable

La même règle permet de conserver app:import comme alias de app:blog:import. Ce lien est déclaré, contrairement à une abréviation déduite de l'ensemble des noms disponibles. Masquer un outil de maintenance évite seulement d'encombrer la liste : cela ne donne ni permission ni protection supplémentaire au fichier importé.

La method `configure()`

À retenir en priorité
  1. Définir et lire l'entrée sont deux phases.
  2. Utiliser InputInterface à l'exécution.

Où en est-on ? Étape 3 sur 3 : l'équivalent classique. Même but (décrire la commande), autre moment : configure() est appelée à la fin du constructeur de Command, d'où un piège d'ordre d'initialisation.

Dans une sous-classe de Command, la définition peut être écrite impérativement. La méthode suivante appartient à cette classe ; elle suppose l'import de Symfony\Component\Console\Input\InputArgument. Elle déclare un nom d'auteur requis, sans encore recevoir sa valeur :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

protected function configure(): void
{
    $this
        ->setDescription('Creates a new user.')
        ->addArgument('username', InputArgument::REQUIRED, 'How the user should be named?')
    ;
}

configure() appartient au style classique et est appelée à la fin du constructeur de Command. Une commande qui définit son propre constructeur affecte donc les propriétés nécessaires avant parent::__construct().

Le constructeur suivant est un autre fragment de sous-classe ; déclarer également private bool $requirePassword;. Il montre l'ordre à respecter si une variante de configure() lit cette propriété :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __construct(bool $requirePassword = false)
{
    $this->requirePassword = $requirePassword;   // d'abord
    parent::__construct();                       // ensuite : configure() tourne ici
}

Si l'affectation était déplacée après l'appel parent et que configure() lisait la propriété à ce moment, PHP lèverait une Error pour accès avant initialisation. Un type bool ne donne pas implicitement la valeur false. Le fragment de définition précédent ne lit pas encore cette propriété : ne pas lui attribuer une validation de mot de passe qu'il n'implémente pas.

new CreateUserCommand(true)
  1. $this->requirePassword = true      ← propriété prête
  2. parent::__construct()
        └─ configure()                  ← peut lire $this->requirePassword

La valeur Alice ou le chemin articles.csv appartient à l'exécution, via l'entrée Console. configure() définit leur place et leurs contraintes ; elle n'est ni initialize() ni un compiler pass du conteneur.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le masquage est une présentation.
  2. Ce n'est pas un contrôle d'accès.
  • Argument obligatoire de AsCommand

    name est le seul parameter obligatoire de #[AsCommand].

  • Voir l’explication : configure() s'exécute à la construction

    configure() s'exécute à la construction, pas à l'exécution : elle ne voit pas l'entrée du user. Pourquoi on se trompe : son nom évoque « configuration au lancement », alors que initialize() est le moment lié à l'entrée.

  • Voir l’explication : Properties avant parent::__construct()

    Properties avant parent::__construct() quand configure() en dépend.

  • Voir l’explication : Une command hidden reste exécutable

    Une command hidden reste exécutable — elle disparaît de list, elle n'est pas désactivée. Pourquoi on se trompe : « caché » suggère « protégé ».

  • Voir l’explication : Le premier segment avant | est le nom

    Le premier segment avant | est le nom, le reste sont des alias ; un premier segment vide cache la command.

  • Voir l’explication : Des usages dans l'attribute d'une command invocable sont ignorés

    Des usages dans l'attribute d'une command invocable sont ignorés dans une application FrameworkBundle 8.0 utilisant la voie standard décrite ici. Un paramètre accepté par l'attribut n'est pas la preuve que chaque voie d'intégration le transmet ; vérifier ce qui arrive à la vraie commande.

  • Voir l’explication : Un alias n'est pas une abréviation

    Un alias n'est pas une abréviation, et un usage n'est pas un argument. Le premier est enregistré, le second documente un appel. Ni l'un ni l'autre ne définit à lui seul les valeurs que __invoke() accepte.

Fiche express

À mémoriser

À retenir en priorité
  1. La syntaxe du nom peut porter le masquage.
  2. La command reste exécutable.

L'import peut maintenant être présenté et renommé sans dupliquer son traitement. Avant de passer aux valeurs acceptées, séparer encore trois moments : métadonnées préparées, construction éventuelle, travail exécuté.

🧠 À retenir pour la certification — si tu dois retenir seulement 6 choses :

  • #[AsCommand] : name seul obligatoire ; description, help, usages, aliases, hidden.
  • 'a|b|c' : a est le nom, b et c des alias.
  • Premier segment vide : command cachée, mais exécutable.
  • Description déclarative non vide : chargement différé pour la liste ordinaire ; pas une garantie pour toute opération d'aide.
  • usages d'une command invocable : non transmis par l'autoconfiguration standard de FrameworkBundle 8.0.
  • configure() à la fin du constructor : properties d'abord.

Moyen mnémotechnique : « Déclarer dans l'attribute, configurer dans le constructor ». Phrase de mémorisation : « Je décris la commande dans l'attribut pour que list n'ait rien à construire ; en style classique configure() tourne dans le constructeur, donc mes propriétés passent avant parent::__construct(). »

Poursuivre avec Options et arguments : le chemin du fichier et le mode de l'import doivent maintenant devenir une vraie définition d'entrée, pas seulement des exemples dans l'aide.
