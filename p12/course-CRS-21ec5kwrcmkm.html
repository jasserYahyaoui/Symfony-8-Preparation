Objectif

Le blog fonctionne en Symfony 8.0. Avant une mise à jour dans la même branche majeure, nous voulons conserver l'affichage de /blog/42, la validation de l'inscription et la commande d'import. La backward compatibility promise est la promesse de compatibilité avec les usages antérieurs de l'API. Elle aide à préparer cette maintenance, mais ne couvre pas tout ce que PHP permet techniquement de faire.

Nous allons classer nos dépendances au framework : appeler une API, implémenter son contrat ou étendre une class. Le risque dépend aussi des annotations et de la partie exacte de l'API sur laquelle notre code s'appuie.

Ce cours se lit après Release management and roadmap schedule (le calendrier des versions) et avant Deprecations best practices (comment se préparer concrètement à la majeure).

L'essentiel

À comprendre

À retenir en priorité
  1. Utiliser une API n'est pas la même chose que l'étendre.
  2. Un nouveau membre Symfony peut entrer en collision avec un membre ajouté.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Des milliers d'applications dépendent de Symfony. Si chaque mineure pouvait casser une API, personne ne mettrait à jour. Symfony prend donc un engagement écrit : dans un périmètre précis, une mise à jour mineure ne casse pas votre code.
  • Le piège de fond. La promesse n'est pas « tout ce que PHP permet reste valide ». Elle couvre des usages précis d'API précises. Étendre, ajouter une méthode, lire un privé par réflexion, nommer un argument : chacun a son niveau de garantie.
  • Ce que l'auteur veut que vous compreniez. Il faut raisonner avec une grille : quelle API ? quel usage ? quelle annotation ?
  • Pourquoi c'est à l'examen. Les questions portent sur les exclusions (@internal, *\Tests\, @experimental, traductions internes), sur les named arguments, sur final / @final / @final since, et sur le procédé d'ajout d'un argument en dernier.

Le semantic versioning distingue version majeure, mineure et corrective. Dans le périmètre couvert, une mineure peut ajouter des fonctionnalités et déprécier des usages, c'est-à-dire annoncer leur abandon tout en les conservant. La majeure est le moment prévu pour les ruptures. Des exclusions et une tolérance pour les corrections de sécurité empêchent toutefois de résumer la règle à « une mineure ne peut jamais affecter mon application ».

Appeler une méthode publique documentée n'engage pas les mêmes détails que lire une propriété privée par réflexion, mécanisme d'inspection du code. Ajouter notre propre méthode à une sous-classe crée encore un autre risque : le parent peut introduire plus tard le même nom. Nous examinerons donc le périmètre, puis l'usage, puis le détail auquel l'application se lie.

Cette promesse concerne le code fourni par Symfony. Elle ne garantit pas automatiquement les APIs de ArticleCatalog, les packages tiers ou les URLs que notre équipe décide de modifier. Le test de /blog/42 continue à protéger notre propre contrat public.

Semantic versioning : MAJEURE . MINEURE . CORRECTIVE
                         8    .    0    .    3
┌──────────────┬───────────────────────────────┬────────────────────────────┐
│ Corrective   │ corrige des bogues            │ ne casse pas               │
│ Mineure      │ ajoute, DÉPRÉCIE (annonce)    │ ne casse pas (périmètre    │
│              │                               │ couvert)                   │
│ Majeure      │ retire ce qui était déprécié  │ rupture autorisée          │
└──────────────┴───────────────────────────────┴────────────────────────────┘
Exceptions : exclusions (interne, expérimental, tests, traductions internes)
             et rupture nécessaire à une correction de sécurité.

Le schéma

À retenir en priorité
  1. Les named arguments ordinaires ne sont pas garantis.
  2. Les constructors d'attributes constituent l'exception.

Où en est-on ? On connaît le principe. Avant de classer nos usages, un schéma sur un cas qui prête à confusion : les arguments nommés. La syntaxe PHP est identique d'un cas à l'autre, mais la garantie ne l'est pas ; ce schéma pose la question dans le bon ordre.

La route du blog utilise des arguments nommés, par exemple path: dans #[Route(...)]. Une commande peut aussi appeler une méthode avec timeout:. La syntaxe PHP ressemble à la même chose ; la garantie sur le nom n'est pourtant pas identique. Le schéma isole cette question :

Le premier contrôle élimine les APIs hors promesse. Le second distingue le constructeur d'une class d'attribute d'une méthode ordinaire. Pour #[Route(path: '/blog')], le nom path bénéficie de la protection spécifique ; cet exemple historique de route ne change pas notre route blog_show. Pour une méthode ordinaire, timeout peut être renommé sans déplacer la valeur dans la signature.

Bleu : appel ; orange : contrôles ; vert ou rouge : couverture du nom. Le rouge ne dit pas que l'appel est invalide aujourd'hui ni que toute la méthode est hors promesse. Le vert ne dispense pas de respecter les autres conditions de l'API et les exceptions de sécurité.

L'exemple : un argument ajouté en mineure

Exemple concret

À retenir en priorité
  1. L'argument ajouté vient en dernière position.
  2. Le comportement antérieur reste le défaut effectif.

Où en est-on ? Changement de point de vue : jusqu'ici nous étions utilisateur de l'API. Ici nous sommes l'auteur d'une bibliothèque qui veut ajouter un argument sans casser ses sous-classes. Pourquoi ? Voir le problème de l'autre côté explique la règle « toujours en dernier ».

Passons du côté de l'auteur d'une bibliothèque utilisée par la commande d'import. Son ancien say() conserve les espaces ; il souhaite proposer leur suppression sans modifier immédiatement la signature redéfinie par des sous-classes. Le laboratoire PHP 8.4 conserve le procédé documentaire, et ajoute une sortie pour observer le résultat :

class ImportReporter
{
    /** @param bool $stripWhitespace */
    public function say(string $text, /* bool $stripWhitespace = true */): void
    {
        $stripWhitespace = 2 <= \func_num_args() ? func_get_arg(1) : false;
        echo $stripWhitespace ? trim($text) : $text;
        echo "\n";
    }
}

$reporter = new ImportReporter();
$reporter->say(' Article 42 ');
$reporter->say(' Article 42 ', true);

Le premier appel conserve l'espace initial et final ; le second affiche Article 42 sans ces espaces. func_num_args() compte les arguments fournis ; func_get_arg(1) lit le deuxième, l'index commençant à zéro. Le commentaire = true n'est pas une valeur par défaut exécutée par PHP : l'absence de second argument suit bien la branche false.

Ce fragment montre une transition d'API, pas une API Symfony nommée ImportReporter. Le booléen commenté n'impose pas non plus un type PHP au second argument. Une bibliothèque doit documenter et encadrer ses entrées ; ce procédé n'est pas un modèle à généraliser à toutes les nouvelles méthodes.

Pourquoi ne pas simplement écrire bool $stripWhitespace = false dans la signature ? Parce qu'une sous-classe qui redéfinit say(string $text) serait alors incompatible avec la signature du parent (PHP lèverait une erreur fatale) : la mineure casserait des applications. Le commentaire permet de préparer la transition sans toucher à la signature réelle.

Utiliser, étendre, implémenter

Où en est-on ? Étape 1 sur 5 : le classement des usages, cœur du programme. Question : selon ce que je fais d'une API (appeler, implémenter, étendre), qu'est-ce que Symfony me garantit ?

Commençons par le code qui produit la Response de l'article. Utiliser une class publique signifie notamment l'instancier et appeler ses méthodes publiques. Implémenter une interface signifie fournir les méthodes du contrat dans notre propre class. Ces usages relèvent de la promesse pour les éléments couverts, sous réserve de signatures PHP compatibles et des exclusions examinées plus bas.

Étendre une class permet de réutiliser ses points publics et protégés. La grille protège largement ces usages et leurs redéfinitions compatibles, mais pas quatre opérations : ajouter une property, ajouter une méthode, appeler une méthode privée ou lire une property privée par réflexion. Les deux ajouts peuvent entrer en collision avec une évolution du parent :

Version A du parent : aucune méthode normalize()
Application : sous-classe avec normalize(int): int
Version B du parent : ajout public normalize(string): string
Résultat : collision de signatures dans la sous-classe

Cette évolution peut laisser intacts les anciens appels publics du parent tout en cassant la sous-classe. Il ne s'agit pas d'une modification réelle d'une class Symfony nommée ici. C'est le risque à reconnaître avant d'ajouter un helper d'import à une class du framework : un service applicatif séparé, reçu par composition, évite de réserver ce nom chez le parent. La promesse ne rend pas une signature incompatible valide en PHP.

Récapitulatif de la grille pour une classe :

Usage Couvert par la promesse ? Pourquoi
Instancier, appeler une méthode publique oui contrat public
Implémenter une interface oui (éléments couverts) contrat
Étendre, utiliser le public/protégé hérité oui points d'extension
Redéfinir de façon compatible oui signature identique
Ajouter une property non le parent peut ajouter le même nom
Ajouter une méthode non idem (collision future)
Appeler une méthode privée (réflexion) non détail interne
Lire une property privée (réflexion) non détail interne

🌍 In Real Life

La situation : utiliser les commandes prévues d'une machine ne revient pas à ajouter ses propres pièces à l'intérieur.

L’équivalent dans Symfony : commandes documentées → API publique couverte ; pièce ajoutée → nouveau membre d'une sous-classe ; inspection interne → réflexion sur le privé du parent.

Retour à la réalité technique : un futur membre du parent peut entrer en collision avec l'ajout. La promesse dépend du périmètre et de l'usage, pas de tout ce que PHP autorise.

🧠 Comment le mémoriser : « Utiliser n'est pas modifier l'intérieur. » Image mentale : panneau de commande face au mécanisme ouvert. Question-réflexe : quelle opération la grille couvre-t-elle ?

⚠️ À ne pas confondre : privé du parent et membre importé d'un trait public couvert, dont la grille est différente.

Repère — Les traits, et leur asymétrie avec les classes :

Question: Does the compatibility promise treat private trait members like private class members?

Answer: No. Trait members become part of the consuming class and receive broader protection, unless internal.

Le trait est intégré dans la class consommatrice. Le privé d'une class Symfony n'a pas la même garantie.

Repère — Ajouter un argument : toujours en dernier :

Question: Where is an added public-method argument placed under the documented compatibility technique?

Answer: Last, documented without breaking the existing signature, and read through func_get_arg().

L'argument ajouté vient en dernière position. Le comportement antérieur reste le défaut effectif.

Les traits, et leur asymétrie avec les classes

À retenir en priorité
  1. Le trait est intégré dans la class consommatrice.
  2. Le privé d'une class Symfony n'a pas la même garantie.

Où en est-on ? Étape 2 sur 5 : un cas qui inverse la règle précédente. Pourquoi le traiter ? Parce que « privé du parent = non couvert » est vrai pour une classe, mais faux pour un trait, et la différence est un classique de QCM.

Un trait importe des membres dans la class qui l'utilise ; ce n'est pas un objet parent distinct. Cette différence explique pourquoi la grille de compatibilité des traits couvre l'utilisation de leurs properties et méthodes publiques, protégées et privées.

Supposons que notre commande utilise un trait public du framework : un helper privé importé appartient alors à sa propre class. Le retirer peut casser directement cette utilisation. À l'inverse, sonder un helper privé d'un parent Symfony par réflexion dépend d'un détail que ce parent ne promet pas de conserver.

La grille des traits n'a donc pas de ligne « non » pour les usages qu'elle énumère. Cela ne transforme pas un trait @internal en API publique, n'efface pas les exclusions générales et ne règle pas automatiquement les conflits entre plusieurs traits choisis par l'application.

        CLASSE PARENTE                         TRAIT
┌───────────────────────────┐        ┌───────────────────────────┐
│ class Parent {            │        │ trait T {                 │
│   private function h()    │        │   private function h()    │
│ }                         │        │ }                         │
│ class Enfant extends Parent        │ class Cmd { use T; }      │
├───────────────────────────┤        ├───────────────────────────┤
│ h() reste chez le parent  │        │ h() est COPIÉ dans Cmd    │
│ → détail interne          │        │ → membre de ma classe     │
│ → NON couvert             │        │ → couvert                 │
└───────────────────────────┘        └───────────────────────────┘

(Un trait marqué @internal reste, lui, exclu : voir plus bas.)

Ajouter un argument : toujours en dernier

Où en est-on ? Étape 3 sur 5 : on revient à l'exemple ImportReporter pour en tirer la règle et son raisonnement. Question : où met-on le nouvel argument, et que fait-on tant que la majeure n'est pas arrivée ?

Le reporter a déjà des appelants : insérer le nouveau drapeau avant $text changerait leur interprétation. L'ajout envisagé doit donc être en dernière position. Pour la transition d'une méthode publique concernée par les contraintes d'héritage, la procédure documentée garde d'abord l'argument en commentaire, le décrit en PHPDoc et le lit avec les fonctions de comptage.

Le défaut exécuté conserve le comportement précédent : false dans notre exemple. Si la future valeur par défaut change ce comportement, l'auteur avertit les appelants qui n'explicitent pas leur choix. À la majeure prévue, il peut rendre le paramètre réel et retirer le code de transition.

Ce procédé répond à une contrainte de compatibilité, pas à une limitation de syntaxe PHP. La grille traite les constructeurs séparément : elle autorise l'ajout de paramètres optionnels en dernière position. Des cas de classes ou méthodes finales ont aussi leurs règles propres. Il faut lire la bonne ligne plutôt que conclure que tout nouvel argument doit éternellement rester commenté.

Les quatre temps de la transition :

1. Mineure N     signature inchangée  say(string $text, /* bool $strip = true */)
                 corps : func_num_args() ? func_get_arg(1) : false
2. Mineure N     (si le défaut futur diffère) : avertir quand l'argument manque
3. Majeure N+1   le paramètre devient réel : say(string $text, bool $strip = true)
4. Majeure N+1   le code de transition disparaît

🌍 In Real Life

La situation : un formulaire conserve ses anciennes cases ; une option future est décrite en marge, mais le traitement actuel garde l'ancien choix quand elle manque.

L’équivalent dans Symfony : marge → argument commenté/PHPDoc ; lecture réelle → func_num_args() et func_get_arg() ; ancien choix → défaut exécuté false.

Retour à la réalité technique : le commentaire ne crée ni paramètre PHP ni défaut true. Cette transition répond aux contraintes d'héritage ; constructeurs et éléments finals ont leurs propres règles.

🧠 Comment le mémoriser : « La marge annonce, le corps décide. » Image mentale : annotation à côté du formulaire actif. Question-réflexe : quelle branche s'exécute si l'argument manque ?

⚠️ À ne pas confondre : procédé de compatibilité et style conseillé pour toute nouvelle méthode.

Les trois exclusions

À retenir en priorité
  1. @internal exclut l'API du contrat de stabilité.
  2. Une fonctionnalité experimental possède une fenêtre limitée.

Où en est-on ? Étape 4 sur 5 : ce qui sort du périmètre. Pourquoi ces exclusions ? Parce que Symfony doit pouvoir faire évoluer ses détails internes, tester de nouvelles idées et corriger des failles sans attendre la majeure. Trois familles à connaître, plus la tolérance de sécurité.

Les internes ne sont pas un raccourci de production. Une méthode peut être publique en PHP et porter @internal : la visibilité autorise l'appel, mais la promesse ne le couvre pas. Les classes des namespaces *\Tests\ du framework sont également exclues. Pour fabriquer les données de l'article 42, nous conservons nos propres fixtures au lieu de dépendre d'un helper de tests interne de Symfony.

L'expérimental sert à stabiliser un contrat. @experimental indique une API encore susceptible de changer. La période prévue est une mineure, prolongeable exceptionnellement d'une autre ; une fonctionnalité ne peut pas être introduite comme expérimentale dans une LTS, version à support prolongé. Les ruptures de cette période doivent être expliquées dans le changelog. Choisir ce code demande donc un suivi explicite, pas la confiance réservée à une API stabilisée.

Le texte traduit n'est pas un identifiant métier. Le form d'inscription affiche des messages de validation ; leurs traductions internes, comme celles de sécurité, peuvent changer ou disparaître. Ce laboratoire formule la mauvaise dépendance puis son remplacement :

Mauvais contrat : si le message traduit vaut exactement « valeur incorrecte »,
                  classer l'erreur X
Contrat préférable : utiliser le type ou le code d'erreur documenté,
                  puis traduire pour l'affichage

Une reformulation destinée au lecteur ne change alors pas la décision métier. Il faut bien choisir un code ou type documenté, pas simplement un autre détail interne. Enfin, une rupture nécessaire à la correction d'une faille de sécurité est tolérée : elle constitue une exception supplémentaire, pas une autorisation générale de casser les usages stables.

Exclusion Marqueur Pourquoi on s'y laisse prendre Alternative
Interne @internal la méthode est public en PHP n'utiliser que l'API documentée
Tests du framework namespaces *\Tests\ classes accessibles via l'autoload ses propres fixtures
Expérimental @experimental l'API est présente et fonctionne suivre le changelog
Traductions internes messages de validation / security texte stable en apparence code ou type d'erreur
Sécurité — « une mineure ne casse jamais » tolérance pour une faille

Un contrat de location protège les pièces qui en font partie, pas les zones explicitement réservées au personnel. @internal marque pareillement une frontière : la visibilité PHP seule ne suffit pas à promettre la stabilité.

Le piège des named arguments

Où en est-on ? Étape 5 sur 5 : on revient à la question du schéma. Pourquoi cette partie ? Parce que le nom d'un paramètre est une seconde dépendance (en plus de sa position) que beaucoup de développeurs ignorent.

Les arguments nommés associent une valeur au nom d'un paramètre, au lieu de se fonder seulement sur sa position. Ils rendent certains appels lisibles, mais ajoutent une dépendance au vocabulaire de la signature. Ce laboratoire autonome illustre le mécanisme avec un libellé d'import :

<?php
function formatLabel(string $text, bool $uppercase = false): string
{
    return $uppercase ? strtoupper($text) : $text;
}
echo formatLabel(text: 'demo', uppercase: true), "\n";

L'entrée demo et le drapeau true produisent DEMO. Si l'auteur renomme $uppercase en $capitalize et adapte le corps sans conserver l'ancien nom, cet appel nommé échoue ; l'appel positionnel formatLabel('demo', true) garde la même association. Ce n'est pas une fonction Symfony réelle ni une promesse sur les règles de notre application.

Dans Symfony, les noms de paramètres ne sont couverts que pour les constructeurs de classes d'attribute, dans le périmètre de la promesse. La route #[Route(path: '/blog')] bénéficie de cette protection sur path. Une méthode ordinaire appelée avec timeout: 5 n'en bénéficie pas automatiquement. La validité immédiate en PHP ne suffit donc pas à établir la stabilité lors d'une mise à jour.

Avant / après un renommage $uppercase → $capitalize :

formatLabel('demo', true)                      ← positionnel : fonctionne toujours
formatLabel(text: 'demo', uppercase: true)     ← nommé : Error (paramètre inconnu)

🌍 In Real Life

La situation : un guichet peut garder ses cases dans le même ordre tout en changeant leur intitulé ; demander une case par son ancien nom devient alors fragile.

L’équivalent dans Symfony : ordre → arguments positionnels ; intitulé → arguments nommés ; intitulés spécialement protégés → constructeurs d'attributes couverts.

Retour à la réalité technique : la promesse Symfony ne protège pas généralement les noms des paramètres ordinaires. Cela ne rend pas les appels nommés invalides aujourd'hui ni toute la méthode instable.

🧠 Comment le mémoriser : « Position et nom sont deux dépendances. » Image mentale : cases inchangées, étiquettes remplacées. Question-réflexe : ce nom appartient-il à un constructeur d'attribute couvert ?

⚠️ À ne pas confondre : syntaxe PHP valide et garantie de stabilité future.

final et @final

À retenir en priorité
  1. final bloque techniquement l'extension.
  2. @final peut exclure l'extension de la promesse sans la bloquer.

Où en est-on ? Dernier thème : la finalité d'une classe. Pourquoi ici ? Parce que « puis-je étendre cette classe ? » est la question qui précède presque toute extension, et que trois écritures (final, @final, @final since) ont trois sens.

Nous voulons enrichir le format d'affichage d'un diagnostic d'import. Si sa class porte le mot-clé PHP final, l'héritage est interdit. Avec la seule annotation PHPDoc @final, PHP peut encore accepter l'héritage, mais Symfony considère la class finale pour sa grille de compatibilité : cette extension n'est pas protégée.

La forme @final since Symfony x.y annonce au contraire une transition vers la prochaine majeure. Pendant cette transition, la class n'est pas encore considérée finale. À la majeure, le projet peut employer le mot-clé ou l'annotation simple : l'annonce ne garantit pas à elle seule une future forme syntaxique précise.

Nous pouvons ajouter notre présentation sans hériter. Ces deux classes du laboratoire PHP 8.4 sont indépendantes du framework :

<?php
final class BaseFormatter
{
    public function format(string $value): string { return trim($value); }
}
final class ApplicationFormatter
{
    public function __construct(private BaseFormatter $formatter) {}
    public function format(string $value): string
    {
        return '['.$this->formatter->format($value).']';
    }
}
echo (new ApplicationFormatter(new BaseFormatter()))->format(' demo '), "\n";

L'entrée entourée d'espaces produit [demo]. L'objet applicatif délègue la normalisation puis ajoute ses crochets : c'est de la composition. Il dépend toujours du contrat public format() et n'est pas une sous-classe de BaseFormatter. Retirer final dans une dépendance installée ne fournirait aucune garantie équivalente et créerait une modification locale à maintenir.

Comparaison des trois écritures :

┌────────────────┬──────────────────┬───────────────────┬───────────────────────┐
│                │ final            │ @final            │ @final since Symfony  │
│                │ (mot-clé PHP)    │ (PHPDoc)          │ x.y                   │
├────────────────┼──────────────────┼───────────────────┼───────────────────────┤
│ PHP bloque     │ oui              │ non               │ non                   │
│ l'héritage ?   │                  │                   │                       │
├────────────────┼──────────────────┼───────────────────┼───────────────────────┤
│ Extension      │ impossible       │ non protégée par  │ encore protégée       │
│ couverte ?     │                  │ la promesse       │ jusqu'à la majeure    │

Note : Symfony n'ajoute pas @final simple en mineure, sauf annonce préalable sous la forme @final since Symfony x.y ; l'annonce se matérialise dans les messages de dépréciation, ce qui prépare la migration avant la majeure (voir Deprecations best practices).

🌍 In Real Life

La situation : une porte peut être verrouillée, simplement signalée comme non destinée au passage, ou annoncée fermée lors de la prochaine rénovation.

L’équivalent dans Symfony : verrou → final PHP ; périmètre non garanti → @final ; transition annoncée → @final since Symfony x.y.

Retour à la réalité technique : le mot-clé interdit l'héritage ; l'annotation simple exclut sa protection ; l'annonce datée vise la prochaine majeure. Composer un service autour de l'API publique évite cet héritage sans supprimer toute dépendance.

🧠 Comment le mémoriser : « Interdit, non garanti, bientôt retiré. » Image mentale : trois panneaux distincts. Question-réflexe : quelle forme exacte est écrite ?

⚠️ À ne pas confondre : commentaire de maintenance et contrôle effectué par le moteur PHP.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Une méthode ajoutée n'est pas une méthode redéfinie.

    Une méthode ajoutée n'est pas une méthode redéfinie. Le helper inventé dans notre sous-classe expose à une collision future ; redéfinir un point public ou protégé couvert suit une autre ligne de la grille. Les deux autres usages non couverts de la class concernent son privé lu ou appelé par réflexion. Pourquoi on se trompe : dans les deux cas on « touche » la sous-classe, donc on suppose la même garantie.

  • Voir l’explication : Un nom n'est pas une position.

    Un nom n'est pas une position. Renommer un paramètre peut préserver l'appel positionnel et casser l'appel nommé. Vérifions l'exception des constructeurs d'attributes plutôt que d'étendre leur garantie à tout service. Pourquoi on se trompe : l'attribut #[Route(path: …)] est partout dans la documentation, d'où l'idée que tous les noms sont protégés.

  • Voir l’explication : Un commentaire peut changer l'engagement sans changer le moteur PHP.

    Un commentaire peut changer l'engagement sans changer le moteur PHP. @final simple exclut l'héritage de la promesse ; final le bloque. La forme since Symfony x.y donne un délai jusqu'à la majeure, elle n'est pas équivalente à une class déjà finale. Pourquoi on se trompe : on croit que seul le mot-clé PHP « compte ».

  • Voir l’explication : Le mot « privé » ne suffit pas à choisir la grille.

    Le mot « privé » ne suffit pas à choisir la grille. Dans un trait public couvert, le membre est importé dans notre class ; dans un parent, il reste un détail interne. La réflexion ne transforme pas ce détail en contrat. Pourquoi on se trompe : même mot-clé private, deux mécanismes différents.

  • Voir l’explication : Le commentaire d'argument n'est pas son défaut exécuté.

    Le commentaire d'argument n'est pas son défaut exécuté. Notre reporter utilise false quand le deuxième argument manque, même si le commentaire mentionne true. Il conserve ainsi les anciens appels pendant la transition ; les constructeurs et les cas finals doivent être examinés selon leurs propres règles. Pourquoi on se trompe : on lit = true comme un défaut PHP.

Application

À retenir en priorité
  1. Le trait est intégré dans la class consommatrice.
  2. Le privé d'une class Symfony n'a pas la même garantie.
  3. Les named arguments ordinaires ne sont pas garantis.
  4. Les constructors d'attributes constituent l'exception.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Avant de mettre à jour le blog, relisons sept dépendances :

  1. L'API est-elle couverte, ou interne, expérimentale, issue des tests du framework ou de ses traductions internes ?
  2. L'utilisons-nous, l'implémentons-nous, ou étendons-nous sa class ? Les garanties ne couvrent pas les mêmes opérations.
  3. Notre helper ajouté à une sous-classe peut-il entrer en collision avec un futur membre du parent ? La composition peut éviter ce couplage.
  4. Le membre privé vient-il d'un trait importé ou d'un parent sondé par réflexion ? Seul le premier usage figure dans la grille protégée.
  5. Un appel nommé dépend-il d'un constructeur d'attribute ou d'un nom ordinaire non garanti ?
  6. La transition d'argument conserve-t-elle les appels existants et leur défaut réel, avec l'ajout en dernière position ?
  7. La class est-elle final, @final, ou annoncée finale à la prochaine majeure ? Préparons la migration avant que l'héritage ne soit retiré.

Les tests restent nécessaires, notamment pour nos propres URLs et règles métier. La promesse organise la maintenance ; elle n'abolit ni les exclusions, ni les corrections de sécurité, ni les responsabilités de l'application.

Phrase de mémorisation : « Utiliser, implémenter, étendre : je ne m'appuie que sur le public documenté — pas d'interne, de test ou d'expérimental, et un nom d'argument n'est sûr que dans un attribut. »
