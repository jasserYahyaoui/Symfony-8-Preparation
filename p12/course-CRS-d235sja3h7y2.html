Objectif

Signaler une violation depuis un callback ou un validator, et savoir laquelle des deux methods du contexte utiliser.

Question fil rouge : comment une règle écrite par moi « dit » à Symfony qu'une donnée est invalide, avec quel message, quel code, quel chemin ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le builder prépare la violation.
  2. addViolation() l'enregistre.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une règle personnalisée (callback ou validator) ne retourne ni true ni false : elle écrit une violation dans le contexte d'exécution. Il faut donc connaître l'API d'écriture, et savoir ce qu'on peut y préciser (chemin, code stable, paramètres, valeur fautive).
  • Le piège de fond. buildViolation() ressemble à « créer une violation » mais ne crée rien : elle prépare un builder. Sans l'appel final addViolation(), la règle échoue sans rien signaler.
  • Ce que l'auteur veut que vous compreniez. Le contexte d'exécution signale une violation de deux façons : directement, ou par un builder qu'on configure — field visé, code, parameters — puis qu'on enregistre par addViolation(). L'oubli de ce dernier appel est le piège central : la règle échoue mais n'ajoute aucune violation ; les autres règles peuvent encore rendre la validation invalide.
  • Pourquoi c'est à l'examen. Les QCM jouent sur : builder non enregistré, addViolation() à deux endroits, atPath() contre setInvalidValue(), UnexpectedValueException contre UnexpectedTypeException, cible d'une constraint (getTargets()).

Le schéma

À retenir en priorité
  1. Le path situe l'erreur.
  2. Le code permet un traitement machine stable.

Où en est-on ? Vue d'ensemble : deux chemins mènent à la liste des violations. Le chemin court (addViolation(message) sur le contexte) et le chemin long (buildViolation() → configuration → addViolation() sur le builder). Les sections suivantes détaillent : les deux façons, l'oubli final, les réglages, les emplacements du message, puis une constraint complète.

Bleu = contexte d'exécution ; ambre = construction sans effet sur la liste ; vert = violation enregistrée. Les flèches sont des appels, pas de l'héritage. Configurer plusieurs options ne crée pas plusieurs violations ; oublier l'appel final n'en crée aucune, même si d'autres règles ont déjà échoué.

Pourquoi un builder ? Parce qu'une violation a beaucoup de propriétés optionnelles (chemin, code, paramètres, valeur, pluriel, cause…). Plutôt qu'une méthode à dix arguments, Symfony offre une chaîne fluide, terminée par un appel qui valide la construction.

L'exemple : une adresse déjà réservée

Exemple concret

À retenir en priorité
  1. Le path et la valeur sont indépendants.
  2. Régler les deux si nécessaire.

Où en est-on ? Le code minimal du schéma complet : un callback de class qui utilise le chemin long. Chaque ligne du builder sera expliquée dans les sections suivantes.

Le POST d'inscription doit pouvoir distinguer un email mal formé d'une adresse réservée par la politique de l'application. L'exemple emploie une réservation locale déterministe, sans base de données. Le callback prépare message, chemin et code pour l'appelant ; il ne choisit pas si l'interface sera un formulaire HTML ou une réponse JSON.

use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;

#[Assert\Callback('check')]
class Registration
{
    public const EMAIL_TAKEN = 'EMAIL_TAKEN';
    public string $email = '';

    private function isReserved(string $email): bool
    {
        return 'reserved@example.com' === $email;
    }

    public function check(ExecutionContextInterface $context): void
    {
        if ($this->isReserved($this->email)) {
            $context->buildViolation('L\'adresse {{ value }} est déjà prise.')
                ->setParameter('{{ value }}', $this->email)
                ->atPath('email')
                ->setCode(self::EMAIL_TAKEN)
                ->setInvalidValue($this->email)
                ->addViolation();
        }
    }
}

Lecture ligne à ligne :

Appel Ce qu'il fait
buildViolation('… {{ value }} …') crée un builder avec le modèle de message
setParameter('{{ value }}', …) remplit l'emplacement {{ value }}
atPath('email') rattache la violation au champ email
setCode(self::EMAIL_TAKEN) code machine stable
setInvalidValue(…) valeur enregistrée comme fautive
addViolation() enregistre : sans cet appel, rien

Les deux façons

À retenir en priorité
  1. Le contexte peut enregistrer directement.
  2. Le builder permet une configuration supplémentaire.

Où en est-on ? Étape 1 sur 5 : le contexte offre deux méthodes qui portent presque le même nom. Laquelle choisir, et pourquoi existent-elles toutes les deux ?

Depuis un callback de classe, l'erreur par défaut concerne l'objet au chemin courant. Si le lecteur doit la voir près de l'email, le builder permet d'ajouter cette localisation et un code stable. L'appel direct convient quand le contexte possède déjà l'emplacement et les informations nécessaires.

Method du contexte Effet
addViolation('msg', [params]) enregistre immédiatement, au path courant
buildViolation('msg', [params]) rend un builder : field, code, valeur fautive réglables

Seul le builder permet de choisir le field visé, le code ou la valeur fautive.

Code minimal des deux façons :

// façon 1 : directe, au chemin courant, rien à régler
$context->addViolation('Ce prénom semble inventé.');

// façon 2 : builder, tout est réglable
$context->buildViolation('Ce prénom semble inventé.')
    ->atPath('firstName')
    ->setCode('FAKE_NAME')
    ->addViolation();

Comparaison :

┌──────────────────────────────┐   ┌───────────────────────────────────┐
│ $context->addViolation()     │   │ $context->buildViolation()        │
├──────────────────────────────┤   ├───────────────────────────────────┤
│ enregistre tout de suite     │   │ retourne un builder (rien écrit)  │
│ chemin = chemin courant      │   │ atPath, code, valeur, plural…     │
│ message + paramètres         │   │ finir par ->addViolation()        │
└──────────────────────────────┘   └───────────────────────────────────┘

🌍 In Real Life

La situation : l'agent peut déposer immédiatement une remarque à la rubrique courante, ou préparer une fiche détaillée avec une autre localisation et une catégorie d'anomalie.

L’équivalent dans Symfony : ExecutionContextInterface::addViolation() ajoute directement au chemin courant. buildViolation() fournit un builder pour préciser chemin, code ou valeur fautive avant l'ajout.

Retour à la réalité technique : ce choix porte sur la construction du résultat, pas sur l'exécution de la règle ni sur la réponse HTTP. Parmi ces deux API, le builder expose les réglages détaillés. Le chemin de validation n'est pas à lui seul la position visuelle dans un Form ; mapping et bubbling interviennent ensuite.

⚠️ À ne pas confondre : ajout au contexte, construction de violation, placement Form et réponse JSON.

Le builder n'écrit rien tout seul

À retenir en priorité
  1. Configurer n'écrit pas dans la liste.
  2. L'oubli final laisse la validation réussir.

Où en est-on ? Étape 2 sur 5 : le piège central du cours. On a vu qu'il existe un builder ; que se passe-t-il si on ne le termine pas ?

Après buildViolation(), la liste que retournera Validator n'a pas encore changé. Configurer atPath('email') ou le code ne modifie que cet objet de préparation. L'appel final fait passer de la description d'un problème à son enregistrement ; vérifie donc le contenu de la liste, pas seulement que la branche de code a été exécutée.

buildViolation() ne crée aucune violation : elle prépare un object. Tant que addViolation() n'est pas appelée au bout de la chaîne d'appels, rien n'est enregistré. addViolation() existe donc des deux côtés : sur le contexte, elle enregistre ; sur le builder, elle termine la chaîne d'appels.

Pourquoi rien n'est-il enregistré ? Dans le code de ConstraintViolationBuilder (branche 8.0), seul addViolation() construit l'objet ConstraintViolation (message traduit, chemin, valeur, code…) et l'ajoute à la liste ($this->violations->add(...)). Les autres méthodes se contentent de modifier les champs du builder.

Avant / après :

// ❌ le builder est préparé puis abandonné : aucune violation
$context->buildViolation('Trop court')->atPath('title')->setCode('SHORT');

// ✅ le dernier appel enregistre
$context->buildViolation('Trop court')->atPath('title')->setCode('SHORT')->addViolation();

Le piège de nom : addViolation() existe sur deux objets (le contexte et le builder). Même nom, deux rôles : sur le contexte il enregistre un message, sur le builder il termine une chaîne.

🌍 In Real Life

La situation : une fiche remplie mais laissée sur la table n'entre pas dans le registre. Changer sa catégorie ou son adresse ne remplace jamais le dépôt.

L’équivalent dans Symfony : les méthodes du builder préparent la violation ; seul son addViolation() l'ajoute à la liste du contexte. Sur le contexte, la méthode du même nom reçoit le message directement.

Retour à la réalité technique : construire puis abandonner le builder ne signale rien pour cette règle. L'ajout n'est ni une écriture en base ni un envoi au navigateur. Vérifie la liste et ses propriétés, pas seulement le passage dans la branche d'échec ; les autres règles peuvent déjà avoir ajouté leurs violations.

🧠 Comment le mémoriser : « Fiche remplie, registre inchangé tant qu'elle n'est pas déposée. » Image mentale : fiche prête à côté d'un registre encore inchangé. Question-réflexe : quel appel ajoute effectivement cette violation ?

⚠️ À ne pas confondre : builder configuré, liste modifiée, persistance et émission HTTP.

Ce que l'on peut régler

À retenir en priorité
  1. Le code identifie la règle en échec.
  2. La cause aide au diagnostic.

Où en est-on ? Étape 3 sur 5 : le builder est lancé ; que peut-on y préciser ? Dix méthodes, que l'on range par rôle : où, quoi, comment l'afficher, pour qui.

Pour une inscription imbriquée, le chemin email doit conserver le préfixe du contexte. Le code identifie la catégorie d'erreur indépendamment de la langue du message ; la valeur fautive reste une autre information. Ne renvoie pas automatiquement cette valeur ni la cause technique dans une API publique : elles peuvent contenir des données sensibles.

Les dix methods de ConstraintViolationBuilderInterface (8.0, relues par réflexion) :

Method Effet
atPath() ajoute un chemin relatif au chemin courant
setParameter() / setParameters() remplit les emplacements {{ … }}
setCode() un code machine stable, lu par getCode()
setInvalidValue() la valeur affichée comme fautive
setPlural() le nombre qui choisit la forme plurielle
setTranslationDomain() / disableTranslation() le traitement du message
setCause() la cause technique, pour le debug
addViolation() enregistre, en fin de chaîne d'appels
  • Sans atPath(), une violation de class conserve le path courant de l'object : vide à la racine de validation, mais par exemple child pour un objet imbriqué. Sa construction ne décide pas à elle seule de l'emplacement dans un formulaire : celui-ci dépend du mapping et du bubbling des erreurs. Pour l'objet du formulaire racine, avec le mapping standard sans redirection d'erreur, une violation au path vide reste sur ce formulaire, pas sur un field particulier.
  • Le path se compose : depuis la racine, atPath('address.city') donne address.city ; depuis addresses[0], atPath('city') donne addresses[0].city. Ce n'est pas un chemin absolu qui efface le préfixe.
  • atPath() ne change pas la valeur fautive : elle reste l'object entier ; setInvalidValue() la corrige.

Pourquoi atPath() compose-t-il au lieu de remplacer ? Son code est PropertyPath::append($this->propertyPath, $path) : on ajoute à la fin du chemin courant. Dans une cascade, le chemin courant est déjà addresses[0] ; un atPath('city') donne addresses[0].city, jamais city seul.

Pourquoi atPath() ne change-t-il pas la valeur fautive ? Ce sont deux champs distincts du builder : propertyPath et invalidValue. Pour une violation de class, invalidValue est l'objet entier ; pour qu'elle porte l'email, il faut setInvalidValue($this->email).

Chemin courant (cascade)     atPath()              Chemin final
(racine)                     'address.city'        address.city
addresses[0]                 'city'                addresses[0].city
(racine, Callback de class)  (aucun atPath)        (vide : sur l'objet)

                      ┌──────────────┐    ┌─────────────────┐
 atPath('email')  ──► │ propertyPath │    │  invalidValue   │ ◄── setInvalidValue()
                      └──────────────┘    └─────────────────┘
                        deux champs indépendants

🌍 In Real Life

La situation : une fiche d'anomalie a une adresse, un code de catégorie, un extrait concerné et une note interne. Changer l'adresse ne change ni l'extrait ni le dossier original.

L’équivalent dans Symfony : atPath compose le chemin relatif ; setCode identifie l'erreur ; setInvalidValue précise la valeur enregistrée comme fautive ; setCause conserve une cause. Traduction et pluriel règlent le message.

Retour à la réalité technique : ces métadonnées sont distinctes. Depuis addresses[0], city donne addresses[0].city ; atPath ne lit pas cette propriété et setInvalidValue ne la corrige pas. La valeur fautive n'est pas automatiquement affichée ni remplacée dans le message. L'API publique doit sélectionner les informations exposées, sans recopier aveuglément valeur, objet ou cause ; le code de violation n'est pas un statut HTTP.

🧠 Comment le mémoriser : « Adresse, catégorie, extrait : trois cases différentes. » Image mentale : fiche avec cases séparées et note interne repliée. Question-réflexe : quelle métadonnée suis-je en train de changer et peut-elle être rendue publique ?

⚠️ À ne pas confondre : chemin, valeur fautive, paramètre du message, cause technique, code métier et statut HTTP.

Les emplacements du message

À retenir en priorité
  1. Le template reste traduisible.
  2. Les parameters portent les valeurs variables.

Où en est-on ? Étape 4 sur 5 : le message lui-même. Pourquoi écrire {{ value }} plutôt que concaténer l'adresse dans la phrase ?

Garde un modèle de message stable et transmets séparément l'adresse. Les doubles accolades sont ici des emplacements du message, pas du Twig exécuté une seconde fois. Une fois traduit et rempli, le message reste à échapper dans son contexte de sortie HTML ; la traduction ne rend pas la saisie sûre.

Le message porte des emplacements {{ … }}, remplis par setParameter(). C'est ce qui permet de le traduire sans y concaténer la valeur. La violation garde les deux formes : getMessageTemplate() rend le modèle, getMessage() le texte rempli.

Pourquoi ne pas concaténer ? Le modèle (L'adresse {{ value }} est déjà prise.) est ce qu'on envoie au traducteur ; la valeur, elle, change à chaque appel. En séparant les deux, une seule traduction sert pour toutes les valeurs.

modèle      : L'adresse {{ value }} est déjà prise.     ← getMessageTemplate()
paramètre   : {{ value }} = reserved@example.com
résultat    : L'adresse reserved@example.com est déjà prise.   ← getMessage()

Une nuance de signature : setParameter(string $key, string $value) attend une string ; pour une valeur non textuelle, on la formate soi-même (les validators natifs utilisent formatValue()).

🌍 In Real Life

La situation : le bureau utilise une lettre type traduisible et remplit séparément la case « adresse concernée ». Il ne transforme pas le texte de cette case en une nouvelle instruction d'impression.

L’équivalent dans Symfony : le modèle du message et ses paramètres restent distincts ; setParameter renseigne l'emplacement choisi. getMessageTemplate conserve le modèle, getMessage donne le texte traité.

Retour à la réalité technique : les doubles accolades du message ne déclenchent pas Twig. Traduire et substituer ne rendent pas une saisie sûre pour HTML : l'échappement dépend encore du contexte de sortie. Pour JSON, l'encodage JSON est une autre étape. Évite d'insérer des secrets dans les paramètres, même si la valeur fautive n'est pas exportée.

🧠 Comment le mémoriser : « Remplir la lettre n'exécute pas son contenu. » Image mentale : lettre type et case d'adresse remplie séparément. Question-réflexe : ai-je séparé traduction, substitution et protection de la sortie ?

⚠️ À ne pas confondre : emplacement de message, expression Twig, traduction, échappement HTML et encodage JSON.

Une constraint sur mesure

À retenir en priorité
  1. Le nom de validator suit une convention.
  2. validatedBy() permet de choisir autrement.
  3. La cible PHP autorise le placement de l'attribute.
  4. getTargets() déclare séparément le scope de validation.

Où en est-on ? Étape 5 sur 5 : jusqu'ici le builder servait dans un callback. Son usage « normal » est dans un ConstraintValidator, la classe qui exécute une constraint réutilisable.

Une règle de slug réutilisée par plusieurs modèles mérite sa propre contrainte et son validateur. Le fragment ci-dessous est une méthode de SlugValidator, pas une classe complète : il suppose les classes Constraint et les exceptions du namespace Validator, ainsi que Slug et son message. Ces exceptions distinguent mauvaise configuration de la règle et forme incorrecte de la valeur, sans remplacer le contrôle d'autorisation sur l'article.

Le builder sert d'abord dans un ConstraintValidator : une class Slug (extends Constraint) et sa class SlugValidator.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function validate(mixed $value, Constraint $constraint): void
{
    if (!$constraint instanceof Slug) {
        throw new UnexpectedTypeException($constraint, Slug::class);
    }
    if (null === $value || '' === $value) {
        return;
    }
    if (!is_string($value)) {
        throw new UnexpectedValueException($value, 'string');
    }
    if (!preg_match('/^[a-z0-9-]+$/', $value)) {
        $this->context->buildViolation($constraint->message)
            ->setParameter('{{ value }}', $value)
            ->addViolation();
    }
}
  • validatedBy() rend par défaut le nom de la class suivi de Validator.
  • Le validator reçoit null : le return est son travail, pour laisser NotNull ou NotBlank décider.
  • UnexpectedValueException devient une violation ; UnexpectedTypeException remonte : c'est une erreur de code.
  • getTargets() vaut PROPERTY_CONSTRAINT : posée sur une class, la constraint lève une ConstraintDefinitionException.
  • En 8.0, une option se déclare dans le constructor, qui appelle parent::__construct(null, $groups, $payload).

Pourquoi deux exceptions différentes ? UnexpectedTypeException signifie « le validator a reçu une mauvaise constraint » : c'est une erreur de programmation, elle remonte. UnexpectedValueException signifie « la valeur n'a pas le type attendu » : c'est un problème de donnée. Le RecursiveContextualValidator (dans validateInGroup) l'attrape et construit lui-même une violation « This value should be of type {{ type }}. ».

validate($value, $constraint)
   ├─ mauvaise Constraint     → UnexpectedTypeException  → REMONTE (bug de code)
   ├─ null / ''               → return                   → rien (présence ailleurs)
   ├─ type de valeur invalide → UnexpectedValueException → devient une VIOLATION
   └─ format invalide         → buildViolation()…addViolation()

Pourquoi une ConstraintDefinitionException sur une class ? Constraint::getTargets() retourne par défaut self::PROPERTY_CONSTRAINT : la constraint n'est autorisée que sur une property (ou un getter). Pour l'autoriser sur une class, il faut redéfinir getTargets() et rendre CLASS_CONSTRAINT.

🌍 In Real Life

La situation : la fiche de consigne définit la règle du slug ; l'inspecteur applique cette règle et dépose les anomalies. Recevoir la mauvaise consigne n'est pas la même chose que recevoir une valeur du mauvais type.

L’équivalent dans Symfony : Slug porte la configuration, SlugValidator exécute le contrôle et utilise son contexte. validatedBy fournit par défaut le nom du validateur ; la factory et, si nécessaire, les services configurés permettent de l'obtenir.

Retour à la réalité technique : dans le parcours standard RecursiveContextualValidator, UnexpectedValueException du composant est convertie en violation, contrairement à UnexpectedTypeException sur la contrainte. Un appel direct au validateur n'assure pas cette conversion. Ignorer null/vide est ici un choix laissant la présence à d'autres contraintes. Le fragment ne fournit ni classe complète ni garantie d'unicité ou d'autorisation. Attention aussi à la regex illustrative : $ peut accepter une position avant un saut de ligne final ; une politique de slug stricte doit traiter ce cas explicitement.

🧠 Comment le mémoriser : « Consigne décrit, inspecteur contrôle, contexte enregistre. » Image mentale : fiche Slug, inspecteur SlugValidator et registre distincts. Question-réflexe : ai-je une mauvaise contrainte, un mauvais type de valeur ou un véritable défaut de format ?

⚠️ À ne pas confondre : Constraint, ConstraintValidator, cible autorisée, présence, format et unicité.

Pour une constraint utilisée en attribute de class, deux déclarations ont des rôles différents : la cible PHP Attribute::TARGET_CLASS autorise le placement de l'attribute ; getTargets() doit aussi annoncer Constraint::CLASS_CONSTRAINT au Validator. La cible PHP seule ne change pas la portée du Validator.

Documentation Symfony 8.0.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le validator reçoit null.
  2. La séparation présence et format doit être explicite.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Récapitulatif des pièges, avec la raison de leur plausibilité.

  • Voir l’explication : buildViolation() seule n'enregistre rien.

    buildViolation() seule n'enregistre rien. Sans addViolation() au bout de la chaîne d'appels, cette règle ne signale rien malgré son échec ; les autres contraintes continuent à déterminer le résultat global. Pourquoi on se trompe : le nom « build » laisse croire que l'objet est créé et ajouté.

  • Voir l’explication : addViolation() existe des deux côtés

    addViolation() existe des deux côtés : sur le contexte, elle enregistre directement ; sur le builder, elle termine la chaîne d'appels. Ce ne sont pas les mêmes methods. Pourquoi on se trompe : même nom, donc même signature supposée.

  • Voir l’explication : Sans atPath(), une violation de portée class garde le path de l'object courant

    Sans atPath(), une violation de portée class garde le path de l'object courant, pas nécessairement un path vide. Le placement dans un formulaire dépend ensuite du mapping et du bubbling ; ne pas en déduire une position universelle en tête du formulaire racine. Pourquoi on se trompe : à la racine le chemin est vide, d'où la généralisation abusive.

  • Voir l’explication : atPath() déplace le path, pas la valeur fautive.

    atPath() déplace le path, pas la valeur fautive. Pourquoi on se trompe : on pense que viser un champ désigne aussi sa valeur.

  • Voir l’explication : Le traitement de null appartient au validator.

    Le traitement de null appartient au validator. Une règle de format l'ignore généralement pour laisser NotNull ou NotBlank gérer la présence ; une contrainte dont le rôle est précisément d'exiger une valeur le refuse. Pourquoi on se trompe : on croit que null est toujours filtré en amont par le framework.

Fiche express

À mémoriser

À retenir en priorité
  1. Conserver le modèle facilite la traduction.
  2. Le message final contient les parameters.

Si tu dois retenir seulement 6 choses :

  • addViolation() du contexte : immédiat ; buildViolation() : un builder.
  • Le builder n'enregistre rien sans ->addViolation() à la fin.
  • atPath() ajoute un path relatif ; sans lui, le path courant reste inchangé, vide seulement à la racine de validation. Le mapping du form décide ensuite du placement.
  • atPath() ne change pas la valeur fautive : setInvalidValue().
  • setParameter() remplit {{ … }} ; setCode() donne un code stable.
  • Constraint maison : SlugValidator par défaut, return sur null, UnexpectedValueException → violation.

Moyen mnémotechnique : « Construire, viser, coder, ajouter ».

🧠 À retenir pour la certification

  1. Deux façons de signaler : $context->addViolation() (direct) ou buildViolation() → builder → addViolation().
  2. buildViolation() ne crée rien : sans addViolation() final, aucune violation.
  3. Dix méthodes de builder : atPath, setParameter(s), setCode, setInvalidValue, setPlural, setTranslationDomain, disableTranslation, setCause, addViolation.
  4. atPath() compose avec le chemin courant et ne touche pas la valeur fautive.
  5. Modèle {{ … }} + setParameter() : getMessageTemplate() ≠ getMessage().
  6. Validator maison : Slug/SlugValidator, null ignoré, UnexpectedValueException → violation, UnexpectedTypeException remonte, getTargets() = property par défaut.

Phrase de mémorisation : « Je construis la fiche, je vise le champ, je donne un code, et rien n'existe tant que je n'ai pas dit addViolation(). »
