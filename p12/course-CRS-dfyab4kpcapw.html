Objectif

Le titre d'une page doit afficher « Article 42 », où 42 vient de l'objet article. Écrire le texte et la valeur dans deux {{ … }} fonctionne, mais Twig offre mieux : glisser l'expression directement dans la chaîne. Ce cours explique comment, avec quelle limite (les guillemets), comment afficher le marqueur lui-même, et pourquoi le résultat est échappé.

Il s'agit d'insérer une expression dans une string, de connaître la constraint qui l'entoure, et de savoir ce que Twig fait des barres obliques inverses dans une string.

L'essentiel

À comprendre

À retenir en priorité
  1. Twig traite les séquences reconnues dans les deux formes de guillemets.
  2. Doubler les barres d'un path littéral.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Assembler une phrase à partir de valeurs est quotidien dans un template. #{…} évite de multiplier les ~.
  • Le piège de fond. La syntaxe dépend des guillemets : les doubles interpolent, les simples non — et rien ne signale l'erreur.
  • Ce que l'auteur veut que vous compreniez. Twig ne traite pas les barres obliques inverses comme PHP, et une chaîne interpolée est une valeur dynamique : elle n'est plus une constante sûre.
  • Pourquoi c'est à l'examen. Les QCM testent \#{, \n entre guillemets simples, \x41 / \101, \P déprécié, l'échappement de la chaîne entière et la précédence de ~ face à +.

#{expression} insère une expression dans une string — entre guillemets doubles seulement. Les barres obliques inverses sont traitées dans les deux sortes de guillemets, à l'inverse de PHP. Et une string interpolée est échappée en entier lors de son affichage sous autoescape, sauf si une opération extérieure la marque explicitement sûre. Interpoler assemble une valeur ; ce n'est pas une manière de rendre du HTML de confiance.

Le schéma

À retenir en priorité
  1. Les guillemets doubles activent l'interpolation.
  2. Les guillemets simples conservent le texte #{...}.

Où en est-on ? Vue d'ensemble. Le cours suit le trajet d'une string littérale dans Twig : sa syntaxe (1), la contrainte des guillemets (2), l'échappement du marqueur (3), les séquences de barres (4), l'échappement de la chaîne entière (5) puis l'alternative avec ~ (6). Le schéma ci-dessous montre tout ce trajet d'un coup.

Une string littérale Twig
   ├─ 1. "#{expr}" ?        → l'expression est évaluée
   ├─ 2. guillemets simples → '#{expr}' reste du texte
   ├─ 3. \#{                → le marqueur est affiché tel quel
   ├─ 4. \n \x41 \101       → décodés dans LES DEUX sortes de guillemets
   ├─ 5. affichage          → chaîne interpolée = échappée EN ENTIER
   └─ 6. ~ et +             → ~ concatène, + additionne

Bleu = transformation ; ambre = choix syntaxique. Le chemin d'affichage suppose autoescape 'html' et aucun raw appliqué au résultat final. Avec name = 'Ada', "Bonjour #{name}" donne Bonjour Ada ; le calcul précède l'échappement.

La syntaxe

À retenir en priorité
  1. L'interpolation accepte calculs et filters.
  2. Elle utilise #{...} dans une string double-quoted.

Où en est-on ? Étape 1 sur 6 : on regarde la forme de base, "…#{expression}…", avant toute subtilité.

Le titre de page peut assembler "Article #{article.id}" à partir d'ArticleView déjà fourni. Twig calcule cette chaîne dans le rendu ; il ne recherche pas l'article et ne traduit pas son libellé. Pour un texte multilingue, une clé de traduction avec paramètre est un contrat différent.

{{ "premier #{middle} dernier" }}
{{ "résultat : #{1 + 2}" }}
{{ "Bonjour #{user.name|upper}" }}

#{…} accepte n'importe quelle expression — variable, calcul, filter, et même une autre string interpolée.

Que fait Twig avec "Bonjour #{user.name|upper}" ?

Le lexer lit la chaîne à guillemets doubles
   ▼
il y repère #{ … } et isole l'expression  user.name|upper
   ▼
au rendu, il évalue l'expression : « Ada » → « ADA »
   ▼
il concatène : "Bonjour " ~ "ADA"   →   Bonjour ADA

Avant / après, avec name = 'Ada' :

"Bonjour #{name}"        →  Bonjour Ada
"Bonjour " ~ name        →  Bonjour Ada     (équivalent, plus verbeux)
"résultat : #{1 + 2}"    →  résultat : 3

Pourquoi l'interpolation ne cherche-t-elle pas l'article ? Elle n'évalue que l'expression écrite, avec les variables que le contrôleur a déjà fournies.

🌍 In Real Life

La situation : l'étiqueteuse assemble « Article » et le numéro calculé depuis la fiche déjà posée devant elle. Elle peut aussi effectuer un petit calcul avant d'insérer son résultat.

L’équivalent dans Symfony : dans une chaîne Twig à guillemets doubles, #{expression} évalue une expression puis l'intègre au texte. article.id, une addition ou un filtre peuvent produire cette valeur.

Retour à la réalité technique : interpolation ne signifie ni chargement de l'article ni traduction du libellé. L'expression doit être valide et son résultat utilisable dans la composition de chaîne ; les erreurs de résolution ou d'exécution ne disparaissent pas. L'échappement de sortie est une étape distincte.

🧠 Comment le mémoriser : « Calculer la case, puis coller sa valeur. » Image mentale : case numérique remplie avant collage sur l'étiquette. Question-réflexe : quelle expression est évaluée et quelles données lui ont déjà été fournies ?

⚠️ À ne pas confondre : interpolation Twig, lookup métier, traduction et affichage sécurisé.

~ concatène mais sa précédence peut surprendre. Écrire un calcul entre parenthèses rend l'intention explicite.

La constraint

Où en est-on ? Étape 2 sur 6 : la syntaxe marche… sauf si on a choisi les mauvais guillemets. C'est l'erreur la plus fréquente, et la plus silencieuse.

Si le navigateur affiche Article #{article.id}, inspecte d'abord les guillemets du littéral Twig : la variable peut être parfaitement présente. Des guillemets simples désactivent cette interpolation, pas toutes les transformations de chaîne. Les séquences d'échappement restent traitées.

L'interpolation ne fonctionne qu'entre guillemets doubles. Entre guillemets simples, #{…} est du texte affiché tel quel, sans erreur. Un # qui n'est pas suivi de { reste du texte. Le choix des guillemets n'a aucun effet sur les performances.

Comparaison, avec name = 'Ada' :

┌─────────────────────────────────────┐ ┌─────────────────────────────────────┐
│          GUILLEMETS DOUBLES         │ │          GUILLEMETS SIMPLES         │
├─────────────────────────────────────┤ ├─────────────────────────────────────┤
│ {{ "Salut #{name}" }}               │ │ {{ 'Salut #{name}' }}               │
├─────────────────────────────────────┤ ├─────────────────────────────────────┤
│ Interpolation                       │ │ Interpolation                       │
│  → active                           │ │  → inactive                         │
├─────────────────────────────────────┤ ├─────────────────────────────────────┤
│ Affiché                             │ │ Affiché                             │
│  → Salut Ada                        │ │  → Salut #{name}   (sans erreur)    │
├─────────────────────────────────────┤ ├─────────────────────────────────────┤
│ Séquences \n, \x41…                 │ │ Séquences \n, \x41…                 │
│  → décodées                         │ │  → décodées aussi                   │
└─────────────────────────────────────┘ └─────────────────────────────────────┘

Pourquoi la mauvaise réponse est plausible : on pense qu'une variable absente déclencherait une erreur. Mais en guillemets simples il n'y a aucune variable, seulement du texte : Twig n'a donc rien à signaler.

Autres points à retenir : un # seul ("Prix #3") reste du texte, et ces guillemets sont ceux du littéral Twig, pas ceux d'un attribut HTML qui l'entoure.

🌍 In Real Life

La situation : l'étiqueteuse a un mode « remplir les cases » et un mode « copier les marqueurs ». En mode copie, voir le nom d'une case imprimé ne signifie pas que sa donnée est absente.

L’équivalent dans Symfony : les guillemets doubles activent l'interpolation #{…} ; les simples la laissent littérale. Un # non suivi de { n'ouvre aucune interpolation.

Retour à la réalité technique : ces délimiteurs sont ceux du littéral Twig, pas ceux d'un attribut HTML qui l'entoure. Les guillemets simples ne désactivent pas les séquences de caractères comme \n. Choisis la syntaxe pour son sens, pas comme promesse de gain de performance ; cette « constraint » est syntaxique, pas une contrainte Validator.

🧠 Comment le mémoriser : « Doubles : remplir ; simples : garder le marqueur. » Image mentale : commutateur de mode devant la même étiquette. Question-réflexe : ai-je désactivé l'interpolation avec les délimiteurs du littéral ?

⚠️ À ne pas confondre : guillemets Twig, guillemets HTML et contrainte de validation.

L'interpolation est un champ de publipostage ; ~ assemble du texte et + calcule. Pour Twig 3.22, ne pas reprendre la précédence inversée de l'analogie source2 : écrire "total " ~ (1 + 2).

Repère — Les séquences d'escaping, dans les deux guillemets :

Question: Does Twig process newline escapes in single-quoted strings?

Answer: Yes, unlike PHP single-quoted string behaviour.

Twig traite les séquences reconnues dans les deux formes de guillemets. Doubler les barres d'un path littéral.

Échapper

À retenir en priorité
  1. La barre avant # empêche l'interpolation.
  2. La séquence reste du texte affiché.

Où en est-on ? Étape 3 sur 6 : et si on veut afficher #{1 + 2} tel quel, par exemple dans un tutoriel ? Il faut dire au lexer de ne pas ouvrir l'interpolation.

Pour enseigner la syntaxe sur une page du blog, il faut montrer le marqueur sans évaluer son contenu. La barre avant #{ agit au niveau du lexer Twig. Elle ne protège pas du HTML et ne remplace donc pas l'autoescape au moment où une donnée du lecteur est affichée.

{# affiche : premier #{1 + 2} dernier #}
{{ "premier \#{1 + 2} dernier" }}

Pourquoi ça marche ? Le lexer rencontre \#{ : dans stripcslashes(), une barre suivie de #{ produit le texte #{ sans ouvrir d'interpolation.

"premier \#{1 + 2} dernier"
          └─ barre + #{ → texte « #{ » (pas d'évaluation)
Résultat : premier #{1 + 2} dernier

🌍 In Real Life

La situation : une fiche de démonstration doit afficher le nom d'une case à remplir sans que l'étiqueteuse la remplisse. On marque cette occurrence comme « à recopier ».

L’équivalent dans Symfony : \#{ dans le littéral à guillemets doubles neutralise l'ouverture d'interpolation à cette position. Le lexer produit les caractères du marqueur au lieu de demander l'évaluation de son expression.

Retour à la réalité technique : c'est un échappement de syntaxe du template. Ce mécanisme n'assainit pas une donnée HTML et ne doit pas servir à fabriquer du code Twig depuis une saisie. Les valeurs transmises au template restent des données ; elles ne sont pas automatiquement réanalysées comme une nouvelle source Twig.

🧠 Comment le mémoriser : « Montrer la case, sans la remplir. » Image mentale : marqueur de démonstration protégé sur la fiche. Question-réflexe : veux-je afficher la syntaxe ou évaluer l'expression qu'elle contient ?

⚠️ À ne pas confondre : neutralisation du marqueur, échappement HTML et exécution d'une source de template.

Les séquences d'escaping, dans les deux guillemets

Où en est-on ? Étape 4 sur 6 : le lexer ne s'intéresse pas seulement à #{. Il décode aussi les barres obliques inverses de toute string, avant le moindre rendu. Cette partie casse une habitude venue de PHP.

Un chemin affiché dans un tutoriel traverse d'abord la lecture du littéral. Le backslash doit survivre à cette étape pour être présent dans le texte obtenu. C'est pourquoi recopier une chaîne PHP à guillemets simples telle quelle dans Twig peut changer ses caractères avant même le rendu HTML.

Contrairement à PHP, Twig traite les séquences d'escaping aussi entre guillemets simples : 'a\nb' contient un vrai saut de ligne. Sont reconnus \n, \t, \r, \v, \f, \\, l'hexadécimal \x41, l'octal \101, et le guillemet de la string.

Tout autre caractère précédé d'une barre est déprécié depuis Twig 3.12 : la barre est ignorée en Twig 3, avec une notice. Un path Windows double donc ses barres : 'c:\\Program Files'.

Comparaison PHP / Twig, pour la même écriture 'a\nb' :

PHP Twig 3.22
'a\nb' texte a\nb (4 caractères + barre) saut de ligne entre a et b
"a\nb" saut de ligne saut de ligne
'\x41' texte \x41 A
'\101' (octal) texte \101 A

Déroulé pour 'c:\Program Files' (le piège du chemin Windows) :

'c:\Program Files'
      └─ \P : séquence inconnue
         → la barre est ignorée + notice de dépréciation (Twig 3.12)
Résultat : c:Program Files

'c:\\Program Files'
      └─ \\ : séquence reconnue → une vraie barre
Résultat : c:\Program Files

Pourquoi la mauvaise réponse est plausible : en PHP, '\P' garde sa barre. On transpose donc la règle PHP à Twig, alors que Twig décode dans les deux sortes de guillemets. Et la tolérance de 3.22 (barre ignorée) n'est pas un contrat : elle est dépréciée.

🌍 In Real Life

La situation : l'étiqueteuse lit certains signes comme des instructions de composition : « nouvelle ligne », « tabulation ». Pour imprimer la barre elle-même, il faut lui donner le code qui représente une barre.

L’équivalent dans Symfony : Twig décode les séquences reconnues dans les littéraux à guillemets simples comme doubles. \\ produit une barre ; \n produit un saut de ligne. Un chemin écrit dans la source doit survivre à ce décodage.

Retour à la réalité technique : ne transpose pas les règles des chaînes PHP simples à Twig. Dans la version3.22 décrite, les échappements inconnus concernés perdent leur barre avec une dépréciation ; cette tolérance n'est pas un contrat pour les versions futures. Une valeur de chemin reçue comme variable n'a pas à être rééchappée comme si elle était du code littéral Twig.

🧠 Comment le mémoriser : « Une barre imprimée doit traverser le lecteur. » Image mentale : deux barres à l'entrée, une barre sur l'étiquette. Question-réflexe : suis-je en train d'écrire une source Twig ou de transmettre une valeur déjà constituée ?

⚠️ À ne pas confondre : représentation dans la source, caractères de la valeur et représentation HTML.

L'escaping de la string entière

À retenir en priorité
  1. Garder le HTML structurel hors de l'expression dynamique.
  2. Échapper les valeurs à leur point d'affichage.

Où en est-on ? Étape 5 sur 6 : la chaîne est construite. Reste à l'afficher : c'est là que l'autoescape intervient, et c'est le point le plus important pour la sécurité.

Le titre de l'article reste une donnée, même lorsqu'on l'entoure de <strong> dans une expression interpolée. L'autoescape traite le résultat dynamique complet ; place donc le balisage structurel dans le template et la valeur dans son expression. Ne marque pas tout le résultat raw pour contourner cette séparation.

Une string littérale est une constant, jugée sûre : {{ '<b>x</b>' }} affiche du gras. Une string interpolée — ou concaténée avec une variable — est échappée en entier : {{ "<b>#{name}</b>" }} écrit &lt;b&gt;Ada&lt;/b&gt;, et raw à l'intérieur ne protège rien. On écrit le HTML hors de l'expression : <b>{{ name }}</b>.

Pourquoi une chaîne littérale est-elle sûre, mais pas une chaîne interpolée ? L'analyse de sûreté de Twig (SafeAnalysisNodeVisitor) considère une constante comme sûre : l'auteur du template l'a écrite. Dès qu'une valeur variable entre dans la chaîne, plus personne ne garantit son contenu : le résultat entier est donc échappé.

{{ '<b>x</b>' }}          constante            → <b>x</b>              (gras)
{{ "<b>#{name}</b>" }}    interpolée (dynamique)
                          → échappée en entier → &lt;b&gt;Ada&lt;/b&gt; (texte)
<b>{{ name }}</b>         balisage HORS expression
                          → <b>Ada</b> : le gras est le vôtre, name est échappé

Pourquoi raw à l'intérieur ne sauve-t-il rien ? Parce que le marquage sûr d'un morceau ne se transmet pas à la chaîne dynamique complète : l'échappement est appliqué sur le résultat final. Et mettre raw sur le tout exposerait les données non fiables (XSS).

🌍 In Real Life

La situation : une étiquette assemblée avec une donnée variable arrive entière au poste d'impression. Celui-ci n'accorde pas automatiquement à ses morceaux les privilèges du cadre de page conçu par le maquettiste.

L’équivalent dans Symfony : sous autoescape HTML, la chaîne interpolée dynamique est échappée comme résultat complet. Le balisage structurel placé dans le template reste distinct de la donnée affichée dans {{ … }}.

Retour à la réalité technique : un littéral constant de la source est traité différemment par l'analyse de sûreté ; cela suppose une source de template de confiance. Un raw sur un morceau ne rend pas toute la concaténation sûre, et raw sur le tout peut exposer les données non fiables. Interpoler ne réalise pas lui-même l'échappement.

🧠 Comment le mémoriser : « Cadre dans le template, donnée dans la case. » Image mentale : cadre HTML autour d'une étiquette de texte protégée. Question-réflexe : ai-je mélangé le balisage et les données dans une seule chaîne dynamique ?

⚠️ À ne pas confondre : sûreté du littéral, sûreté d'un morceau et sûreté du résultat complet.

L'alternative

À retenir en priorité
  1. ~ concatène mais sa précédence peut surprendre.
  2. Écrire un calcul entre parenthèses rend l'intention explicite.

Où en est-on ? Étape 6 sur 6 : l'interpolation n'est pas la seule façon d'assembler du texte. L'opérateur ~ existe — avec un piège de précédence face à +.

Pour combiner un libellé et un total, calcule le total dans des parenthèses ou dans l'expression interpolée. La concaténation ne doit pas transformer prématurément le premier nombre en texte avant une addition. Les règles ci-dessous sont celles de Twig3.22, pas celles d'une version ultérieure.

~ concatène : {{ "Bonjour " ~ user.name ~ " !" }}. + additionne, il ne concatène pas.

Attention à la précédence : en Twig 3.22, ~ lie plus fort que +. {{ "total " ~ 1 + 2 }} échoue — « Unsupported operand types: string + int » ; on écrit "total " ~ (1 + 2) ou "total #{1 + 2}".

Pourquoi échoue-t-il ? Twig groupe d'abord ce qui lie le plus fort. Dans la table des précédences de Twig 3.22, ~ vaut 40 et + vaut 30 (un nombre plus grand lie plus fort). La doc indique que ~ passera à 27 en Twig 4.0 : c'est pourquoi on précise « Twig 3.22 ».

"total " ~ 1 + 2
   Twig 3.22 : ~ (40) lie plus fort que + (30)
   ▼
("total " ~ 1) + 2
   ▼
"total 1" + 2   → addition d'une chaîne non numérique et d'un entier
   ▼
erreur au rendu : Unsupported operand types: string + int
Écriture Résultat Pourquoi
"total " ~ 1 + 2 erreur au rendu ~ avant +
"total " ~ (1 + 2) total 3 parenthèses : le calcul d'abord
"total #{1 + 2}" total 3 l'expression interpolée est calculée seule

🌍 In Real Life

La situation : avant de coller « total » sur un résultat, l'agent finit son addition. Coller le libellé au premier nombre puis tenter d'additionner le second mélange texte et calcul.

L’équivalent dans Symfony : ~ concatène, + additionne. Les parenthèses autour du calcul fixent ce qui doit être calculé avant l'assemblage du libellé.

Retour à la réalité technique : en Twig3.22, ~ a une précédence supérieure à + ; l'expression non parenthésée montrée ci-dessus tente une addition inadéquate. La concaténation ne contourne pas l'autoescape et ne fournit pas de traduction. Les règles de précédence doivent rester liées à la version étudiée.

🧠 Comment le mémoriser : « Calcul d'abord, étiquette ensuite. » Image mentale : calculatrice avant rouleau d'étiquettes. Question-réflexe : mes parenthèses rendent-elles explicite l'ordre entre calcul et texte ?

⚠️ À ne pas confondre : addition, concaténation et priorité des opérateurs.

Pièges d'examen

Piège à éviter

  • Voir l’explication : L'interpolation ne fonctionne qu'entre guillemets doubles.

    L'interpolation ne fonctionne qu'entre guillemets doubles. En guillemets simples, la même écriture est du texte littéral affiché tel quel — et rien ne signale l'erreur. Pourquoi on se trompe : on s'attend à une erreur si la variable n'est pas résolue ; or il n'y a pas de variable, seulement du texte.

  • Voir l’explication : Le choix des guillemets ne coûte rien en performance.

    Le choix des guillemets ne coûte rien en performance. Pourquoi on se trompe : en PHP, on entend souvent que les guillemets simples sont plus rapides.

  • Voir l’explication : \n est un saut de ligne même entre guillemets simples

    \n est un saut de ligne même entre guillemets simples, à l'inverse de PHP. Pourquoi on se trompe : on applique la règle PHP.

  • Voir l’explication : L'operator d'addition ne concatène pas.

    L'operator d'addition ne concatène pas. + additionne ; ~ concatène. Pourquoi on se trompe : JavaScript utilise + pour les deux.

  • Voir l’explication : Une chaîne interpolée est échappée en entier.

    Une chaîne interpolée est échappée en entier. raw à l'intérieur ne protège rien. Pourquoi on se trompe : on croit que l'interpolation « laisse passer » le HTML écrit par le développeur, comme une constante.

  • Voir l’explication : ~ lie plus fort que + en Twig 3.22.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • #{expression} : toute expression, guillemets doubles seulement.
  • Guillemets simples : texte littéral, sans erreur.
  • \#{ affiche le marqueur ; un # seul reste du texte.
  • \n, \x41, \101 traités dans les deux guillemets.
  • \P inconnu : barre ignorée, deprecation ; doubler les barres.
  • Sous autoescape : string interpolée échappée en entier ; littérale sûre.
  • ~ lie plus fort que + (Twig 3.22) : des parenthèses.

Moyen mnémotechnique : « doubles pour interpoler, simples pour copier, et des parenthèses autour du calcul ».

#{expr} entre doubles seulement ; \#{ pour l'afficher ;
escapes dans les deux guillemets, \P déprécié ;
littérale = constante sûre ; interpolée sous autoescape = échappée en entier
sauf marquage sûr ; ~ avant + : parenthèses
