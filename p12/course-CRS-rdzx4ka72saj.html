Objectif

Un visiteur peut lire /blog/42 sans compte. Avant de lui proposer une opération réservée aux rédacteurs, il faut établir son identité, puis examiner ses droits séparément. Nous suivons d'abord la preuve d'identité et sa réutilisation éventuelle entre deux requêtes.

Question du cours : comment Symfony passe-t-il d'une requête anonyme à un utilisateur connu, et que garde-t-il d'une requête à l'autre ?

L'essentiel

À comprendre

À retenir en priorité
  1. Connaître l'identité ne donne pas tous les droits.
  2. isGranted() pose la question d'accès.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Avant de décider ce qu'on a le droit de faire, il faut savoir qui est là. L'authentication est la première étape, distincte.
  • Le piège de fond. Confondre « qui » et « quel droit », ou croire qu'un anonyme a un token spécial. En 8.0, sans user, il n'y a pas de token.
  • Ce que l'auteur veut que vous compreniez. Le trajet firewall → authenticator → passport → token → TokenStorage, puis la différence entre firewall avec état et stateless.
  • Pourquoi c'est à l'examen. getToken()/getUser() à null, 401 contre 403, rechargement du user depuis la session, session_fixation_strategy: migrate.

L'authentication répond à « qui êtes-vous ? ». Un firewall transforme des credentials en token, rangé dans le TokenStorage pour la Request courante. Sans user, il n'y a pas de token. Avec état, le token survit en session ; sans état, chaque Request se réauthentifie.

Les credentials sont les preuves présentées, par exemple un mot de passe. Le token de sécurité représente l'identité obtenue ; ce n'est ni ce mot de passe, ni le token CSRF d'un formulaire, ni nécessairement une chaîne envoyée par le client. Le firewall sélectionne un ensemble de mécanismes pour la requête ; les services qui le composent ont été préparés en amont.

Le schéma

À retenir en priorité
  1. Le passport rassemble les preuves.
  2. Le token représente ensuite l'identité authentifiée.

Où en est-on ? Carte du cours : deux chemins possibles pour une requête (restaurer une session ou authentifier à neuf). Lire séparément une première connexion et le retour avec une session. Restaurer un contexte ne signifie pas redemander le mot de passe à chaque consultation de l'article ; échouer à restaurer n'accorde aucun droit.

Bleu : traitement ; ambre : choix ; vert : observation. Vue simplifiée des chemins réussis : un refresh refusé ou des credentials invalides ne produisent pas de token valide. Le matcher peut utiliser autre chose que le chemin. HTTP Basic produit un 401 ; un login par formulaire peut rediriger.

Exemple concret

À retenir en priorité
  1. Le status code dépend de l'entry point.
  2. Un form login peut produire un redirect.

Où en est-on ? Une configuration minimale avec HTTP Basic. Le but : avoir une route /whoami qui rend l'identité observable sans écrire de formulaire.

Nous gardons /blog/42 public et utilisons /whoami comme sonde protégée de l'identité avant d'aborder l'édition. HTTP Basic rend le résultat observable sans construire un formulaire de connexion. Il exige HTTPS en usage réel : l'encodage des credentials ne les chiffre pas.

security:
    password_hashers:
        Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface: auto
    providers:
        mem:
            memory:
                users:
                    alice: { password: '<hash généré pour alice>', roles: ['ROLE_USER'] }
    firewalls:
        main:
            provider: mem
            http_basic: ~
    access_control:
        - { path: ^/whoami, roles: ROLE_USER }

Configuration à compléter avec un hash réel, jamais avec le password en clair. Les observations et QCM ci-dessous supposent ce firewall HTTP Basic, des routes existantes et, pour Alice, une authentification complète (pas remember-me). Pour la question stateless, la route rappelée est protégée par ROLE_USER.

Le hash indiqué est volontairement un emplacement à compléter, pas un secret utilisable. Sans credentials, l'article public peut répondre 200 et la sonde 401 ; avec Alice correctement authentifiée, la sonde peut répondre 200. Un mot de passe valide ne donne pas ROLE_ADMIN : cette autre question appartient au contrôle d'accès.

GET /blog/42, sans credentials 200 (public)
GET /whoami, sans credentials 401 (entry point HTTP Basic)

La question posée

À retenir en priorité
  1. L'identité et l'autorisation sont distinctes.
  2. Un user présent peut être refusé.

Où en est-on ? Étape 1 sur 4 : poser la bonne question. Avant le trajet, distinguer qui de quel droit.

🌍 In Real Life

La situation : l'accueil du restaurant reconnaît Alice ; cela ne lui donne pas automatiquement accès à la cuisine où se prépare la publication du blog.

L’équivalent dans Symfony : établir qui se présente → authentification ; décider si cette personne peut modifier l'article 42 → autorisation.

Retour à la réalité technique : une identité authentifiée et ses rôles alimentent les contrôles d'accès, sans les remplacer. Lire getUser() consulte l'identité courante ; cela ne valide pas de nouveaux credentials et n'accorde aucun droit.

🧠 Comment le mémoriser : « Reconnaître n'est pas autoriser. » Image mentale : nom sur une fiche, porte encore fermée. Question-réflexe : ma condition vérifie-t-elle l'identité ou la permission demandée ?

⚠️ À ne pas confondre : absence d'utilisateur et interdiction de toute page publique.

L'authentication répond à « qui êtes-vous ? », l'authorization à « avez-vous le droit ? ». Les deux sont indépendantes : un user authentifié peut n'avoir aucun droit.

Le provider retrouve un utilisateur ; le hasher vérifie le mot de passe ; l'authenticator coordonne les preuves de sa méthode de connexion. Aucun des trois ne constitue à lui seul une règle « peut modifier 42 ».

Authentication : « qui est-ce ? »      ─► getUser(), token
Authorization  : « a-t-il le droit ? » ─► isGranted(), voters
(un user authentifié peut n'avoir AUCUN droit)

Le trajet

À retenir en priorité
  1. Le passport précède le token.
  2. Les badges sont vérifiés avant le succès.
  3. La connexion programmée passe par un authenticator.
  4. La Response du succès peut déterminer la suite du controller.

Où en est-on ? Étape 2 sur 4 : les cinq stations d'une nouvelle authentification. Question : à quel moment le token apparaît-il ?

🌍 In Real Life

La situation : pour l'espace rédaction du blog, l'accueil reçoit un dossier, fait contrôler ses pièces puis inscrit l'identité reconnue au poste courant.

L’équivalent dans Symfony : agent adapté à la demande → authenticator ; dossier à vérifier → Passport ; pièces et capacités → badges ; identité authentifiée courante → token dans TokenStorage.

Retour à la réalité technique : ce trajet suppose un firewall actif et un mécanisme qui prend la requête en charge. Le Passport n'est pas encore le token ; une réponse de succès peut rediriger sans exécuter le contrôleur demandé.

🧠 Comment le mémoriser : « Dossier d'abord, identité établie ensuite. » Image mentale : dossier passant du bac à vérifier au registre courant. Question-réflexe : suis-je avant ou après les vérifications ?

⚠️ À ne pas confondre : token de sécurité interne et chaîne bearer reçue par HTTP.

Pour une nouvelle authentification prise en charge :

  1. La Request entre dans le premier firewall dont le matcher correspond.
  2. Un authenticator de ce firewall la prend en charge.
  3. Il construit un passport, dont les badges sont vérifiés.
  4. Un token (TokenInterface) est produit, avec le user et ses roles.
  5. Le token est déposé dans le TokenStorage.

$this->getUser() et Security::getUser() ne sont que des raccourcis vers le TokenStorage.

Request ─► firewall ─► authenticator ─► passport ─► token ─► TokenStorage
                       (prend la       (user +     (user +   (identité
                        requête)        badges)     roles)    courante)
 getUser() / Security::getUser() lisent simplement le TokenStorage

Le passport rassemble le user et les éléments à vérifier ; les badges décrivent ces vérifications ou capacités. Ce n'est pas encore le token authentifié. La réponse de succès peut interrompre le trajet HTTP normal, par exemple par une redirection : le contrôleur de la page demandée n'est donc pas garanti d'être exécuté.

Après la branche /inscription, Security::login() permet une connexion programmée d'un UserInterface via un authenticator et un firewall. Les sélectionner explicitement si plusieurs conviennent, et traiter l'éventuelle Response de succès renvoyée, plutôt que supposer null. Cela ne remplace ni la validation de l'inscription ni le hachage du mot de passe.

Security::login() permet une connexion programmée d'un UserInterface, par exemple après une inscription. Elle utilise un authenticator et un firewall ; lorsqu'il y a plusieurs possibilités, les sélectionner explicitement. La method peut retourner la Response du succès d'authentication : le controller doit la prendre en compte, plutôt que supposer que la connexion ne produit jamais de Response.

Pas de token sans user

À retenir en priorité
  1. Le token anonyme historique n'est plus requis.
  2. Le code doit accepter l'absence de token.

Où en est-on ? Étape 3 sur 4 : le cas du visiteur anonyme. Question : que contient le TokenStorage quand personne n'est connecté ?

Depuis la disparition du token anonyme, une Request non authentifiée n'a aucun token :

Request getToken() getUser() Response
/public, sans credentials null null 200
/whoami (exige ROLE_USER), sans credentials — — 401, entry point
/whoami, credentials valides UsernamePasswordToken alice 200

Le firewall l'explique : « the user is not fully authenticated; redirecting to authentication entry point ».

« Pas de token » décrit ici le stockage de l'identité authentifiée. Pour décider d'un accès anonyme, AuthorizationChecker peut créer temporairement un NullToken sans le placer dans TokenStorage. Il ne réintroduit pas l'ancien AnonymousToken. La ligne /public du tableau représente le même cas public que /blog/42.

Pourquoi un NullToken alors ? Pour que les voters aient quelque chose à lire quand on évalue un accès anonyme : il n'est jamais stocké dans le TokenStorage, donc getToken() reste null.

Avec ou sans état

À retenir en priorité
  1. Le firewall stateless ne mémorise pas le token en session.
  2. Chaque Request doit fournir sa preuve.

Où en est-on ? Étape 4 sur 4 : que garde-t-on d'une requête à l'autre ? Question : d'où vient l'identité d'une requête précise ?

🌍 In Real Life

La situation : un accueil conserve le dossier de visite d'Alice ; un autre lui demande de présenter une preuve à chaque passage.

L’équivalent dans Symfony : dossier conservé → contexte de sécurité en session ; consultation et actualisation au retour → restauration avec refresh ; preuve par appel → mécanisme stateless du blog.

Retour à la réalité technique : stateless empêche ce firewall de persister le token en session, pas tous les cookies applicatifs. Avec état, la restauration peut être différée par lazy et invalidée après comparaison de l'utilisateur.

🧠 Comment le mémoriser : « Dossier restauré ou preuve renouvelée. » Image mentale : registre conservé face à un guichet sans registre de visites. Question-réflexe : d'où vient l'identité de cette requête précise ?

⚠️ À ne pas confondre : persistance du contexte et autorisation de la ressource.

  • Par défaut, stateless: false : le token est sérialisé en session. À la Request suivante, le log dit « Read existing security token from the session », puis « User was reloaded from a user provider » : le user est rechargé par le provider, pas recopié tel quel.
  • stateless: true : ce firewall ne persiste pas le token en session. Dans notre cas HTTP Basic protégé, l'appel suivant sans credentials reçoit 401 ; un endpoint public n'est pas refusé pour cette seule raison.
  • Après une connexion, l'ID de session est régénéré contre la fixation de session : session_fixation_strategy vaut migrate par défaut.
stateless: false (défaut) stateless: true
Token sérialisé en session jamais persisté par ce firewall
Requête suivante token lu, user rechargé credentials à chaque requête
Usage typique site avec login API

La restauration stateful recharge et compare le user ; une modification peut invalider le contexte selon les règles de comparaison. Un firewall lazy peut différer ce travail jusqu'à l'utilisation de la sécurité. stateless ne supprime pas tous les cookies ni tous les usages applicatifs de session ; ne pas le confondre avec l'attribut de route _stateless qui signale une autre contrainte.

Ce que le controller voit

À retenir en priorité
  1. null décrit l'identité courante.
  2. Le contrôle d'accès décide ensuite du refus.

Où en est-on ? Dernier regard : ce que lit un contrôleur. Question : que signifie un null de getUser() ?

Dans une méthode d'un contrôleur héritant d'AbstractController, les observations suivantes lisent l'état courant. Elles n'authentifient pas une chaîne arbitraire reçue en paramètre :

$this->getUser();                 // le user, ou null
$this->isGranted('ROLE_ADMIN');   // authorization, pas authentication

getUser() à null signifie « pas authentifié », pas « accès refusé ». Une Request anonyme sur une page protégée sollicite l'entry point (401 ici) ; un user pleinement authentifié sans le droit reçoit 403, hors handler d'accès refusé personnalisé.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La session conserve le token.
  2. Le provider relit l'identité.
  • Voir l’explication : Authentication ≠ authorization.

    Authentication ≠ authorization. getUser() répond à la première, isGranted() à la seconde. Pourquoi on se trompe : « connecté » et « autorisé » se disent presque pareil.

  • Voir l’explication : Pas de user, pas de token

    Pas de user, pas de token : getToken() rend null pour une Request anonyme ; le token anonyme n'existe plus. Pourquoi on se trompe : les anciennes versions avaient un AnonymousToken.

  • Voir l’explication : stateless: true n'écrit pas le token en session

    stateless: true n'écrit pas le token en session : le user n'est plus mémorisé d'une Request à l'autre. Pourquoi on se trompe : on imagine que le cookie de session persiste quand même.

  • Voir l’explication : Le token en session ne fige pas le user

    Le token en session ne fige pas le user : il est rechargé par le provider lors de la restauration du contexte, éventuellement différée par un firewall lazy. Pourquoi on se trompe : « sérialisé en session » suggère une copie figée.

Fiche express

À mémoriser

À retenir en priorité
  1. La connexion régénère l'identifier de session.
  2. Cela ne transforme pas un firewall stateless en stateful.

Nous savons maintenant distinguer visiteur et Alice sans transformer l'identité en permission. La suite pose explicitement la question d'autorisation.

🧠 À retenir pour la certification :

  • Authentication = qui ; authorization = quel droit.
  • Firewall → authenticator → passport → token → TokenStorage.
  • Pas de user, pas de token : getToken() et getUser() à null.
  • Anonyme refusé : entry point (401 ici) ; pleinement authentifié refusé : 403.
  • Avec état : token en session ; sa restauration rafraîchit le user, éventuellement lors de l'initialisation différée d'un firewall lazy.
  • stateless: true : pas de persistance du token de ce firewall en session ; credentials à chaque requête qui exige une authentification.
  • session_fixation_strategy: migrate : nouvel ID après connexion.

Moyen mnémotechnique : « Qui d'abord, droit ensuite ».

firewall → authenticator → passport → token → TokenStorage ;
pas de token anonyme ; entry point pour identité insuffisante,
403 si pleinement authentifié refusé ; session : token restauré
et user rafraîchi ; stateless : pas de persistance ; migrate
