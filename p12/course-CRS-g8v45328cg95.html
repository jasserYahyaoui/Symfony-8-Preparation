Objectif

Le test HTTP de /blog/42 échoue : le problème vient-il du catalogue, de son câblage ou du rendu ? Un test d'intégration peut obtenir le vrai service ArticleCatalog sans passer par le contrôleur. Il faut alors démarrer l'application et accéder au conteneur prévu pour les tests, sans rendre tous les services publics en production.

Question centrale : comment un test atteint-il un service qui est privé en production, et comment le remplacer sans casser le câblage ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le TestContainer élargit l'accès pour les tests.
  2. Il ne recrée pas les services supprimés.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Pour isoler un défaut (catalogue ? câblage ? rendu ?), il faut parfois prendre le service réel, sans HTTP.
  • Le piège de fond. Les services sont privés par défaut : le conteneur du kernel refuse de les rendre. Le container de test est une façade qui les atteint, mais il n'invente rien.
  • Ce que l'auteur veut que vous compreniez. Une doublure se pose avant l'initialisation du service qui la consomme : après, c'est trop tard.
  • Pourquoi c'est à l'examen. framework.test, LogicException, ServiceNotFoundException, InvalidArgumentException « already initialized », ordre set() puis get().

KernelTestCase isole les tests : le kernel est arrêté au nettoyage, puis redémarré à la demande dans le test suivant. static::getContainer() rend un container de test qui atteint aussi les services privés — sauf ceux supprimés à la compilation. Il permet de poser une doublure, à condition de le faire avant le premier get() du service qui en dépend.

Le conteneur construit et relie des services. Une doublure remplace une dépendance par un objet contrôlé qui respecte le même contrat. Cela permet, par exemple, de fixer l'heure d'un rapport d'import. Ce n'est pas le profil conservé d'une requête : on obtient ici les objets vivants qui vont exécuter le comportement.

Les deux façons d'atteindre un service, en boîtes :

┌──────────────────────────┐        ┌───────────────────────────────┐
│ container du kernel      │        │ container de test             │
├──────────────────────────┤        ├───────────────────────────────┤
│ services publics         │        │ publics + privés conservés    │
│ privés : refusés         │        │ (façade, localisateur privé)  │
│ (ServiceNotFound)        │        │ supprimés : toujours refusés  │
└──────────────────────────┘        └───────────────────────────────┘

Le schéma

À retenir en priorité
  1. La création du consommateur capture ses dependencies.
  2. Le remplacement doit précéder l'initialisation.

Où en est-on ? Début du cours : un schéma qui suit le test, de la classe du kernel jusqu'à la doublure. Les losanges ambre sont les moments où l'accès peut réussir ou échouer.

La classe du kernel est un choix de configuration. Son démarrage donne accès aux services ; le remplacement d'une dépendance précède leur utilisation :

Bleu : objets/configuration ; ambre : accès ; vert : résultat. Le pointillé configure la classe, il n'appelle pas le kernel. Vue de services privés conservés et non initialisés : le container de test ne ressuscite pas les services supprimés ou intégrés à un autre service lors de la compilation.

L'exemple

Exemple concret

À retenir en priorité
  1. La doublure contrôle le temps.
  2. Le service consommateur doit être construit ensuite.

Où en est-on ? Le schéma est posé ; voici le code correspondant au chemin « set() avant get() ». Retenez l'ordre des deux dernières lignes.

Le générateur historique représente une branche de la lettre du blog : il reçoit des nouvelles via un contrat, sans présumer une base de données. Ce fragment suppose NewsRepositoryInterface, NewsletterGenerator et leur câblage déjà définis dans l'application, leurs noms importés dans le fichier de test, et la dépendance privée conservée et non initialisée :

use Symfony\Bundle\FrameworkBundle\Test\KernelTestCase;

class NewsletterGeneratorTest extends KernelTestCase
{
    public function testGenerate(): void
    {
        $container = static::getContainer();             // démarre le kernel
        $repository = $this->createMock(NewsRepositoryInterface::class);
        $container->set(NewsRepositoryInterface::class, $repository); // d'abord
        $generator = $container->get(NewsletterGenerator::class);     // ensuite
    }
}

Ce fragment prépare une doublure, mais ne teste pas encore generate(). Ajouter des attentes sur le repository, appeler le générateur et vérifier son résultat métier. L'ordre set puis get permet ici au consommateur de recevoir la doublure, au lieu de garder une dépendance déjà construite. Un boot listener qui aurait déjà utilisé ce service peut cependant rendre la substitution trop tardive : « avant mon premier get explicite » n'est pas toujours « avant toute initialisation ».

Pour le catalogue du récit, conserver d'abord le service réel et vérifier son contrat : 42 fournit un article, 999 n'en fournit pas. Le remplacer par une doublure dans ce même test ne vérifierait plus son implémentation ; cela conviendrait à un autre test, centré sur son consommateur.

Démarrer le kernel

À retenir en priorité
  1. Le test doit trouver la class du kernel.
  2. Une surcharge peut fournir cette décision.

Où en est-on ? Étape 1 sur 3 : avant tout service, il faut un kernel démarré. Quelle classe ? Quelles options ? Et pourquoi un test n'a-t-il pas toujours besoin de le démarrer ?

  • Le kernel est normalement désigné par KERNEL_CLASS, fournie par le bootstrap ou la configuration PHPUnit, souvent depuis .env.test. Une redéfinition de getKernelClass() ou de createKernel() peut fournir ce choix autrement ; elle n'ignore la variable que si elle remplace réellement cette lecture, sans la déléguer au parent.
  • bootKernel() rend le kernel démarré et accepte des options : self::bootKernel(['environment' => 'my_test_env', 'debug' => false]).
  • debug: false évite notamment les vérifications de fraîcheur du conteneur compilé. Cela peut accélérer une CI ; préparer ou nettoyer correctement le cache de test reste nécessaire quand les sources ou la configuration changent. Ce n'est pas un réglage qui efface les données métier.

bootKernel() arrête d'abord un kernel précédent, crée puis démarre le nouveau et le retourne. getContainer() ne réclame pas cet appel explicite si aucun choix d'options n'est nécessaire. Un nouveau kernel et de nouvelles instances ne signifient pas que la compilation doit se refaire : le conteneur compilé en cache peut être réutilisé.

Pourquoi « à la demande » ? Démarrer un kernel coûte du temps. Les tests qui n'ont pas besoin du conteneur (calcul pur) ne le paient pas ; ceux qui en ont besoin le démarrent via getContainer() ou bootKernel(). Le kernel est arrêté au nettoyage pour que chaque test parte d'un état propre.

Le container de test

À retenir en priorité
  1. Privé et supprimé ne sont pas synonymes.
  2. Un service supprimé n'est plus disponible.

Où en est-on ? Étape 2 sur 3 : le kernel tourne ; comment atteindre un service privé ? Via le TestContainer. C'est ici que se jouent LogicException et ServiceNotFoundException.

🌍 In Real Life

La situation : pendant le contrôle du restaurant, une entrée de maintenance permet d'atteindre des équipements internes. Elle ne recrée pas ceux retirés du bâtiment.

L’équivalent dans Symfony : entrée spéciale → TestContainer ; équipements internes conservés → services privés accessibles ; équipement supprimé → service retiré lors de la compilation.

Retour à la réalité technique : framework.test prépare ce dispositif. Le conteneur de test ne rend pas les services publics en production et ne ressuscite pas une définition supprimée ou un service devenu inaccessible par optimisation.

🧠 Comment le mémoriser : « Accès spécial, pas création magique. » Image mentale : porte de maintenance devant une étagère vide. Question-réflexe : le service privé a-t-il été conservé ?

⚠️ À ne pas confondre : service privé et service absent du conteneur compilé.

static::getContainer() démarre le kernel s'il ne l'est pas, puis rend le service test.service_container, un TestContainer. Sans framework.test : LogicException, « Could not find service "test.service_container" ».

Un premier contrôle utile, dans une méthode de KernelTestCase avec l'environnement de test configuré, est :

self::bootKernel();
$container = static::getContainer();
self::assertSame('test', $container->getParameter('kernel.environment'));

Le résultat attendu est une assertion réussie pour l'environnement test. Elle vérifie le contexte démarré, pas encore le catalogue. Avec un environnement personnalisé, adapter l'attente et y activer framework.test.

Trois services privés par défaut — Clock (utilisé par Greeter), son alias ClockInterface, et Unused (utilisé par personne) :

get() sur… Container de test Container du kernel
ClockInterface, Clock l'instance ServiceNotFoundException
Unused ServiceNotFoundException : « …has been removed or inlined when the container was compiled » idem

Le service privé ne devient pas public : c'est une façade de test, reliée au conteneur du kernel et à un localisateur de services privés. Elle essaie ce localisateur pour les identifiants qu'il expose, sinon le conteneur public. Elle n'invente aucune définition manquante.

Pourquoi Unused disparaît-il ? À la compilation, Symfony retire les services privés que personne n'utilise, et incorpore ceux utilisés une seule fois. Un service que rien ne référence n'existe donc plus dans le conteneur compilé : le container de test n'a rien à retrouver.

Le tableau suppose que Clock et son alias restent conservés ; un service privé peut aussi avoir été incorporé à son consommateur lors de l'optimisation. Pour préserver un service dont le test a réellement besoin, le rendre public dans la seule configuration de test, par exemple config/services_test.yaml. Cette modification agit lors de la préparation suivante du conteneur, pas rétroactivement sur un conteneur déjà compilé et chargé.

Remplacer un service par une doublure

À retenir en priorité
  1. Le container conserve ses instances partagées.
  2. L'ordre d'installation de la doublure compte.

Où en est-on ? Étape 3 sur 3 : on a le container de test ; on veut y substituer une dépendance. La question est une question d'ordre : que se passe-t-il si le consommateur est déjà construit ?

🌍 In Real Life

La situation : avant la répétition de la lettre du blog, on désigne un collègue qui fournira des nouvelles fictives. Le générateur doit recevoir ce collègue dès sa préparation.

L’équivalent dans Symfony : collègue de répétition → doublure ; affectation préalable → set() ; consommateur préparé ensuite → get() et injection.

Retour à la réalité technique : pour les services partagés non paresseux décrits, remplacer après initialisation est refusé. Remplacer une entrée n'est pas réécrire rétroactivement les références déjà reçues par les objets.

🧠 Comment le mémoriser : « Distribuer les rôles avant la répétition. » Image mentale : fiche d'affectation remise avant l'arrivée du générateur. Question-réflexe : la dépendance ou son consommateur est-il déjà initialisé ?

⚠️ À ne pas confondre : substitution de test et modification du câblage de production.

set() peut remplacer un service privé conservé, y compris via son alias privé reconnu. Le remplacement doit précéder son initialisation. Pour les services partagés non paresseux Clock et Greeter du tableau, où le constructeur du second reçoit le premier :

Ordre Résultat
set(ClockInterface, double) puis get(Greeter) hello at fake
get(Greeter) puis set(ClockInterface, double) InvalidArgumentException : « …service is already initialized, you cannot replace it. »

TestContainer::set() résout les identifiants renommés ; pour un service du localisateur privé, il refuse une instance déjà présente dans le stockage privé du conteneur. Sinon, il y place la doublure. Les autres cas passent par set() du conteneur public. La règle n'est donc pas « tout get quelconque interdit tout set » : c'est la dépendance visée et son état qui comptent.

Pourquoi l'ordre compte-t-il ? Greeter reçoit Clock dans son constructeur, une seule fois. Si Greeter est déjà construit, il garde sa référence à l'ancien Clock : remplacer l'entrée du conteneur ne modifie pas cet objet. Symfony préfère donc refuser (InvalidArgumentException) plutôt que de laisser croire que la doublure est utilisée.

set(double) → get(Greeter)        get(Greeter) → set(double)
  Greeter construit avec double     Greeter construit avec le vrai Clock
  "hello at fake"                   set refusé : already initialized

La substitution ne réécrit pas les propriétés d'objets déjà construits. Elle ne rend pas non plus une doublure incompatible acceptable : respecter les types et le comportement requis. Ne pas neutraliser les autorisations ou la validation si le test prétend précisément vérifier ces protections.

Depuis un test d'application

À retenir en priorité
  1. Les deux accès visent l'intégration de test.
  2. La frontière de service reste commune.

Où en est-on ? Dernier angle : dans un WebTestCase, on a aussi un client. Atteint-il le même container ? Oui, avec une règle d'ordre pour le créer.

$client->getContainer() rend test.service_container quand il existe — le même object que static::getContainer() — sinon le container du kernel. $client->getKernel() rend le kernel.

Dans un WebTestCase, créer le client avant d'appeler le helper statique : createClient() attend que le kernel ne soit pas déjà démarré. On peut alors poser une doublure avant la première requête, puis demander /blog/42. Les deux accès au conteneur visent la même application à cet instant ; après un reboot entre requêtes, ne pas supposer qu'une ancienne référence de service ou une substitution manuelle a été transportée dans les nouvelles instances.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le helper gère l'initialisation nécessaire.
  2. Ne pas multiplier les boots sans raison.
  • Voir l’explication : static::getContainer() rend un container de test

    static::getContainer() rend un container de test, pas le container de production : les services privés y sont accessibles. Pourquoi on se trompe : le mot « container » fait croire qu'il s'agit du même objet qu'en production.

  • Voir l’explication : Un service privé supprimé reste inaccessible

    Un service privé supprimé reste inaccessible — il faut le rendre public dans config/services_test.yaml.

  • Voir l’explication : container->set() doit précéder get()

    container->set() doit précéder get() du service consommateur — après, la dépendance privée du cas étudié est déjà initialisée et le remplacement est refusé. Ne pas en faire une règle universelle sur tous les services.

  • Voir l’explication : getContainer() démarre le kernel

    getContainer() démarre le kernel s'il ne l'est pas.

  • Voir l’explication : KERNEL_CLASS désigne le kernel

    KERNEL_CLASS désigne le kernel ; getKernelClass() l'emporte sur elle.

  • Voir l’explication : Le kernel est arrêté au nettoyage de chaque test

    Le kernel est arrêté au nettoyage de chaque test, puis démarre à la demande dans le suivant. Un test qui n'en a pas besoin n'est pas automatiquement booté. Si tearDown() est redéfinie, préserver le nettoyage du parent.

Fiche express

À mémoriser

À retenir en priorité
  1. L'état ne doit pas passer d'un test au suivant.
  2. Chaque test retrouve sa frontière d'isolation.

Le catalogue réel teste le câblage et son comportement ; une doublure contrôle une dépendance pour isoler son consommateur. Dans les deux cas, la frontière d'isolation est explicite et ne nécessite pas de modifier la visibilité de production.

🧠 À retenir pour la certification :

  • KERNEL_CLASS désigne le kernel ; getKernelClass() l'emporte.
  • Le kernel est nettoyé entre tests et redémarre à la demande.
  • static::getContainer() démarre le kernel si besoin.
  • Il rend un TestContainer ; sans framework.test, LogicException.
  • Services privés accessibles, sauf supprimés à la compilation.
  • set() d'une doublure avant le get() du consommateur.
  • $client->getContainer() : le même container de test.

Moyen mnémotechnique : « Démarrer, atteindre, doubler avant ».

Phrase de mémorisation : getContainer() démarre le kernel et ouvre la porte de maintenance des services privés ; on distribue la doublure avant que le consommateur ne soit construit.

KERNEL_CLASS (ou choix redéfini) → kernel démarré à la demande
getContainer() boote → TestContainer (framework.test)
privés OK sauf supprimés (services_test.yaml)
set() avant get(), sinon already initialized

Le paramétrage du client permet maintenant de distinguer les options de ce kernel des informations envoyées dans les requêtes.
