Objectif

Le blog veut réutiliser une bibliothèque sans lui imposer toutes les classes de Symfony. Elle peut demander un logger, un dispatcher ou un message HTTP selon un contrat commun. Nous devons vérifier si l'objet que nous possédons respecte ce contrat, ou si une adaptation est nécessaire.

Le PHP-FIG publie des PHP Standard Recommendations, ou PSR, pour faciliter cette interopérabilité entre projets. Nous distinguons les contrats implémentés, les conventions suivies et la frontière entre HttpFoundation et les messages PSR-7, dans notre périmètre Symfony 8.0.

Ce cours prolonge Components et Bridges (où vit le bridge PSR-7) et HttpFoundation (le modèle Request/Response qu'on adapte). La mise en œuvre de PSR-4 côté projet rejoint Code organization.

L'essentiel

À comprendre

À retenir en priorité
  1. provide déclare des capacités virtuelles.
  2. Une entrée n'est pas nécessairement une PSR.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Deux bibliothèques écrites par des équipes différentes ne peuvent collaborer que si elles se mettent d'accord sur des interfaces. Les PSR sont ces accords. Sans eux, chaque bibliothèque imposerait son logger, son cache, son client HTTP.
  • Le piège de fond. Trois choses sont confondues : une PSR implémentée (un contrat fourni), une PSR suivie (une convention de code) et une PSR à adapter (PSR-7 face à HttpFoundation).
  • Ce que l'auteur veut que vous compreniez. provide est une annonce de capacité à Composer, pas une configuration de services ; les versions déclarées comptent autant que le numéro de PSR.
  • Pourquoi c'est à l'examen. Les questions portent sur des chiffres exacts : 15 entrées (8 + 5 + 2), 1.1|2.0 pour le container, 2.0|3.0 pour PSR-6, * pour HTTPlug, WebLink pour PSR-13.

Une interface décrit les opérations attendues ; une implémentation fournit un objet qui les réalise. Une bibliothèque typée sur cette interface peut donc accepter plusieurs fournisseurs sans connaître leur organisation interne. Elle doit toutefois recevoir le bon objet et une version compatible du contrat.

Le manifeste composer.json de symfony/symfony 8.0 déclare huit capacités PSR dans provide. Cette déclaration aide Composer à satisfaire des dépendances sur des packages virtuels, noms représentant une capacité plutôt qu'un package unique à télécharger. Elle ne configure pas à elle seule les services du blog et ne rend pas chaque class Symfony conforme à toutes ces interfaces.

Deux conventions étudiées ici, PSR-4 et PSR-12, répondent à un autre besoin : charger et présenter le code de manière prévisible. Enfin, la Request HttpFoundation de /blog/42 n'est pas directement un message PSR-7. L'adaptation concerne cette frontière précise, pas toutes les bibliothèques externes ni une nouvelle étape obligatoire du traitement HTTP.

TROIS RELATIONS AUX PSR
 1. IMPLÉMENTÉES  → Symfony fournit un objet conforme    (PSR-3, 6, 11, 13,
                    annoncé dans « provide »              14, 16, 18, 20)
 2. SUIVIES       → conventions de code, pas de contrat   (PSR-4, PSR-12)
                    absentes de « provide »
 3. À ADAPTER     → HttpFoundation ≠ PSR-7 : il faut un   (PSR-7 + PSR-17)
                    bridge et des fabriques

Le schéma

À retenir en priorité
  1. Le service container satisfait PSR-11.
  2. EventDispatcher satisfait PSR-14.

Où en est-on ? On a distingué trois relations. Le schéma traite la troisième, la moins intuitive : pourquoi une Request HTTP n'est-elle pas « déjà » un message PSR-7 ? Parce que ce sont deux types PHP différents qui décrivent le même protocole.

Imaginons qu'une bibliothèque destinataire exige ServerRequestInterface, interface PSR-7 représentant une Request reçue côté serveur. Notre Request HttpFoundation ne satisfait pas ce type. Le schéma existant montre conceptuellement la conversion nécessaire ; il ne décrit pas une installation ou une API d'adaptation à mettre en œuvre ici :

Une fabrique construit les objets conformes au contrat demandé. PSR-17 définit les interfaces de ces fabriques ; une implémentation concrète reste nécessaire pour produire des messages PSR-7. Le bridge représente l'adaptation entre modèles : sa présence ne transforme pas l'objet HttpFoundation initial en implémentation de l'interface attendue.

Bleu : conversion ; orange : dépendances de construction ; vert : consommateur. L'entrée et le résultat sont deux représentations qu'il faut transmettre explicitement au bon destinataire. Ce schéma ne promet pas que tous les objets métier éventuellement stockés dans la Request deviendront portables entre bibliothèques.

Un middleware est un élément d'une chaîne de traitement. Convertir un message ne construit ni n'exécute automatiquement une chaîne PSR-15 ; cette intégration constitue une responsabilité distincte. Nous restons ici à la compréhension de la frontière, sans installer ni enseigner un package d'adaptation externe.

L'exemple : une bibliothèque qui type contre une PSR

Exemple concret

Où en est-on ? Le schéma montrait un cas qui demande une conversion ; voici le cas inverse, qui n'en demande aucune. Pourquoi les opposer ? Parce que le contraste est le cœur du cours : Symfony implémente PSR-11 et PSR-14, mais adapte PSR-7.

La situation est plus directe pour le container et le dispatcher. Le Plugin du laboratoire demande les contrats PSR-11 et PSR-14 ; les objets Symfony correspondants peuvent être fournis sans adaptateur. Ce script suppose PHP 8.4, DependencyInjection et EventDispatcher 8.0, les interfaces PSR compatibles et l'autoload du projet chargé :

<?php
require __DIR__.'/vendor/autoload.php';

use Psr\Container\ContainerInterface;
use Psr\EventDispatcher\EventDispatcherInterface;
use Symfony\Component\DependencyInjection\Container;
use Symfony\Component\EventDispatcher\EventDispatcher;

final class Plugin
{
    public function __construct(
        private ContainerInterface $container,          // le container de Symfony convient
        private EventDispatcherInterface $dispatcher,   // le dispatcher aussi, sans adapter
    ) {}
}

function containsService(ContainerInterface $container, string $id): bool
{
    return $container->has($id);
}

$container = new Container();
$dispatcher = new EventDispatcher();
$plugin = new Plugin($container, $dispatcher);

var_dump($container instanceof ContainerInterface);
var_dump($dispatcher instanceof EventDispatcherInterface);
var_dump(containsService($container, 'article.catalog'));

Résultat attendu : bool(true), bool(true), puis bool(false). Les deux objets satisfont les contrats du constructeur, mais ce container de laboratoire ne contient pas notre catalogue : aucun service article.catalog n'y a été enregistré. La fonction containsService() lit une capacité du contrat PSR-11 sans imposer de class concrète Symfony.

Construire le Plugin n'enregistre aucun listener et ne charge pas l'article 42. Dans l'application complète, le container compilé possède les services réellement configurés. La compatibilité PSR-11 ne conseille pas d'injecter ce container entier dans tous les services métier : recevoir directement ArticleCatalog reste préférable quand c'est la seule dépendance nécessaire.

Les PSR implémentées

Où en est-on ? Relation n° 1 sur 3 : les contrats que Symfony fournit. Pourquoi une table ? Parce que l'examen demande de relier trois informations : le numéro de PSR, le component qui la porte, et les versions déclarées. Les apprendre ensemble évite de les confondre.

La table est un instantané des déclarations du package symfony/symfony 8.0. Les nombres de sa dernière colonne sont des versions déclarées pour les capacités Composer, pas les numéros des PSR, de PHP ou de Symfony :

PSR Object Component Symfony Versions déclarées
PSR-3 Logger notamment le logger d'HttpKernel 1.0, 2.0, 3.0
PSR-6 Cache Cache 2.0, 3.0 — pas 1.0
PSR-11 Container DependencyInjection 1.1, 2.0 — pas 1.0
PSR-13 Link WebLink 1.0, 2.0
PSR-14 Event Dispatcher EventDispatcher 1.0
PSR-16 Simple Cache Cache 1.0, 2.0, 3.0
PSR-18 HTTP Client HttpClient 1.0
PSR-20 Clock Clock 1.0

Pour l'import, PSR-3 définit le contrat de journalisation : la bibliothèque signale une étape ou une erreur sans choisir notre destination de logs. PSR-6 organise le cache autour de pools et d'objets représentant des entrées ; PSR-16 propose une interface plus directe de clés et valeurs. Ces contrats de stockage ne décident pas si la Response publique de l'article est cacheable selon HTTP (voir le Module 17 — Cache HTTP).

PSR-11 permet notamment get() et has() sur un container ; PSR-14 définit la distribution d'événements. Notre laboratoire vient de vérifier les objets fournis pour ces deux rôles. Cela ne garantit pas la présence d'un service particulier ou d'un listener métier.

PSR-13 concerne les liens hypermédia, relations entre ressources ; WebLink porte ce rôle. Ce n'est pas la même chose que générer le chemin de blog_show avec Routing. PSR-18 définit le contrat d'un client HTTP : HttpClient fournit l'intégration adaptée, notamment Psr18Client. L'API Contracts obtenue avec HttpClient::create() n'est pas, par simple ressemblance, l'interface PSR-18. Il faut fournir l'objet approprié et les dépendances de messages qu'il demande.

Enfin, PSR-20 définit une horloge : une bibliothèque peut demander l'heure courante sans imposer une source concrète. Cela permet de rendre un test dépendant du temps plus maîtrisable, sans modifier l'horloge de toute la machine.

Une entrée psr/<nom>-implementation dans provide annonce donc une capacité pour les versions déclarées. Son absence ne prouve pas qu'aucune class ou aucun autre package de l'écosystème ne puisse réaliser un contrat. Il faut lire le manifeste du package réellement utilisé, puis vérifier l'objet fourni. Une application installant seulement quelques composants ne possède pas automatiquement toutes les capacités du package complet.

Pourquoi les versions comptent : un package virtuel s'écrit psr/container-implementation avec une contrainte de version. Une bibliothèque qui exige 1.0 n'est pas satisfaite par 1.1|2.0 ; Composer refuse alors l'installation.

 bibliothèque exige               symfony/symfony 8.0 déclare      résultat
 psr/container-implementation 1.0   1.1 | 2.0                     NON satisfait
 psr/container-implementation ^2.0  1.1 | 2.0                     satisfait
 psr/cache-implementation 1.0       2.0 | 3.0                     NON satisfait
 php-http/client-implementation     *                             satisfait

🌍 In Real Life

La situation : une prise conforme doit correspondre au format demandé ; le catalogue du fabricant ne prouve pas qu'un appareil particulier est déjà branché.

L’équivalent dans Symfony : format → interface et version ; capacité annoncée → provide ; appareil branché → objet effectivement fourni au consommateur.

Retour à la réalité technique : compatibilité PSR-11 ne garantit aucun service particulier ; PSR-14 n'enregistre aucun listener. PSR-6/16 concernent le stockage applicatif, pas la réutilisation HTTP d'une Response.

🧠 Comment le mémoriser : « Vérifier le contrat et l'objet livré. » Image mentale : prise comparée à sa fiche technique. Question-réflexe : quel type et quelle version sont réellement attendus ?

⚠️ À ne pas confondre : conventions PSR-4/12 et capacités d'implémentation déclarées.

Les points d'attache standardisés d'une caisse permettent à plusieurs grues de la manipuler. Une interface PSR joue ce rôle : le client dépend de la forme du contrat, pas du nom de la class concrète.

Les deux autres familles de `provide`

Où en est-on ? Suite de la relation n° 1 : la table ne montrait que 8 des 15 entrées. Pourquoi les 7 autres ? Parce que la question « combien d'entrées ? » tombe à l'examen, et parce qu'elles montrent d'autres types de contrats que les PSR.

Notre bibliothèque peut choisir une abstraction propre aux Contracts Symfony plutôt qu'une PSR. Le manifeste déclare cinq capacités correspondantes : symfony/cache-implementation, symfony/event-dispatcher-implementation, symfony/http-client-implementation, symfony/service-implementation et symfony/translation-implementation.

Les contrats sont publiés séparément du framework complet. Une bibliothèque peut dépendre de ces abstractions sans exiger toute l'application Symfony ; elle conserve bien une dépendance aux contrats choisis. Le fournisseur concret et son assemblage restent nécessaires. Une interface de traduction ne crée pas à elle seule les catalogues de l'inscription.

Les deux autres entrées sont php-http/client-implementation et php-http/async-client-implementation, issues de l'abstraction HTTPlug, antérieure à PSR-18. Elles sont déclarées à * dans ce manifeste. Cela signifie que cette déclaration n'impose pas de version particulière de la capacité virtuelle ; ce n'est pas une promesse que toute configuration, toute dépendance ou tout objet retourné possède automatiquement la même API.

Nous comptons ainsi quinze entrées : huit PSR, cinq Contracts Symfony et deux HTTPlug. Ce compte décrit le manifeste étudié, pas une constante universelle de toutes les versions futures.

Famille Nombre Entrées
PSR 8 psr/log, cache, container, link, event-dispatcher, simple-cache, http-client, clock (suffixe -implementation)
Contracts Symfony 5 symfony/cache, event-dispatcher, http-client, service, translation (suffixe -implementation)
HTTPlug 2 php-http/client-implementation, php-http/async-client-implementation (version *)

Les PSR suivies

À retenir en priorité
  1. PSR-4 concerne l'autoloading.
  2. PSR-12 concerne les conventions de code.

Où en est-on ? Relation n° 2 sur 3 : les PSR qui ne sont pas des contrats à fournir mais des conventions à respecter. Pourquoi les séparer ? Parce qu'elles n'apparaissent jamais dans provide, ce qui trompe les candidats.

Une autre difficulté apparaît avant même l'appel d'un service : PHP doit trouver sa class. PSR-4 décrit une correspondance entre préfixes de namespaces et directories. App\ vers src/ est la configuration habituelle de l'application, pas un chemin imposé par la PSR elle-même. Voici le fragment à intégrer au manifeste Composer existant, sans écraser ses autres clés :

{
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}

Avec cette correspondance, App\Catalog\ArticleCatalog est recherché dans src/Catalog/ArticleCatalog.php. Le nom déclaré, le chemin et leur casse doivent correspondre. Le fragment ne crée pas ce fichier et ne déclare pas automatiquement un service dans le container.

 App\Catalog\ArticleCatalog
 └┬─┘ └──┬──┘ └─────┬─────┘
  │      │          └─ nom du fichier : ArticleCatalog.php
  │      └──────────── sous-dossier : Catalog/
  └─────────────────── préfixe « App\ » → dossier « src/ »
 ⇒ src/Catalog/ArticleCatalog.php

Après une modification de la configuration d'autoload, Composer 2 peut régénérer ses fichiers avec :

composer dump-autoload

Résultat attendu si la commande réussit : les fichiers d'autoload reflètent la configuration du projet. Elle ne répare pas une class mal nommée et ne déplace pas les sources. Aucune commande n'est exécutée ici.

PSR-12 concerne la présentation du code ; les standards Symfony s'y appuient avec leurs choix propres. Suivre une convention de style ou d'autoload ne se déclare pas comme une capacité psr/*-implementation dans provide. Leur absence de cette clé n'indique donc pas qu'elles seraient ignorées. Les conventions de nommage propres à Symfony sont détaillées dans Naming conventions.

Le cas PSR-7

À retenir en priorité
  1. HttpFoundation ne fournit pas directement PSR-7.
  2. Un contrat de messages immuables diffère de son modèle mutable.

Où en est-on ? Relation n° 3 sur 3 : celle du schéma. Pourquoi la reprendre maintenant ? Parce que les deux autres relations donnent le contraste nécessaire pour comprendre qu'ici, rien n'est fourni tel quel.

Revenons à la bibliothèque qui attend le message du GET /blog/42. HttpFoundation possède son propre modèle Request/Response, antérieur à PSR-7. Passer directement sa Request à un argument Psr\Http\Message\ServerRequestInterface ne devient pas valide parce que les deux objets représentent du HTTP.

La frontière étudiée est la suivante :

Application : HttpFoundation Request
Frontière : bridge et fabriques adaptées
Destinataire : message conforme à ServerRequestInterface, PSR-7
Retour éventuel : conversion vers HttpFoundation Response

Dans le sens HttpFoundation vers PSR-7, il faut une implémentation concrète des messages et les fabriques PSR-17 nécessaires à leur construction. Un bridge convertit les représentations ; il ne remplace pas ces objets. Nous n'enseignons pas ici leur installation ou leur configuration. La règle porte sur cette frontière, pas sur l'affirmation excessive qu'aucune class Symfony ne pourrait implémenter une interface de fabrique.

La mutation diffère également. Plusieurs opérations HttpFoundation changent l'objet existant ; les méthodes de modification with...() des messages PSR-7 retournent un message avec la modification, dont il faut conserver le résultat. Cette immutabilité du message ne promet pas une copie profonde de tout objet contenu ni l'immutabilité du flux représentant le body.

HttpFoundation (mutable)            PSR-7 (immuable)
  $request->setLocale('fr');          $psr = $psr->withHeader('X-A', '1');
  modifie l'objet existant            retourne un NOUVEAU message ;
                                      oublier d'affecter = modification perdue

L'adaptation doit donc être explicite au point d'intégration. Elle ne change pas notre ArticleCatalog en bibliothèque PSR-7 et n'insère pas automatiquement un middleware dans HttpKernel.

🌍 In Real Life

La situation : le même contenu doit être transcrit sur un formulaire différent pour être accepté par un autre guichet.

L’équivalent dans Symfony : formulaire initial → Request HttpFoundation ; transcription → bridge ; formulaire reçu → message PSR-7 construit avec les fabriques adaptées.

Retour à la réalité technique : l'objet initial ne change pas d'interface. Les méthodes PSR-7 with...() retournent le message modifié à conserver ; cela ne promet pas l'immutabilité profonde du flux. La conversion ne lance aucune chaîne PSR-15.

Pièges d'examen

Piège à éviter

  • Voir l’explication : HTTP commun ne signifie pas type PHP commun.

    HTTP commun ne signifie pas type PHP commun. La Request HttpFoundation n'est pas ServerRequestInterface. La conversion demande des objets concrets ; un bridge seul n'est pas une implémentation complète de messages, et la conversion n'exécute pas une chaîne de middleware. Pourquoi on se trompe : les deux objets s'appellent « Request » et décrivent le même protocole ; on les croit interchangeables.

  • Voir l’explication : Une convention suivie n'est pas un service disponible.

    Une convention suivie n'est pas un service disponible. PSR-4 explique comment trouver ArticleCatalog.php ; PSR-12 aide à lire son code. Aucune entrée provide ne remplace la configuration d'autoload ou le contenu du fichier.

  • Voir l’explication : Une interface satisfaite ne promet pas toutes les dépendances métier.

    Une interface satisfaite ne promet pas toutes les dépendances métier. Le container et le dispatcher de notre laboratoire satisfont PSR-11 et PSR-14 sans adaptateur, mais le catalogue y est absent et aucun listener n'a été enregistré. L'injection directe reste adaptée au service métier.

  • Voir l’explication : Le compte de quinze est un instantané, pas quinze PSR.

    Le compte de quinze est un instantané, pas quinze PSR. Les cinq capacités Contracts et les deux HTTPlug ont d'autres noms et contrats. Un package virtuel ne se confond pas avec un service actif. Pourquoi on se trompe : la clé provide est souvent présentée comme « les PSR de Symfony » ; le suffixe -implementation est commun aux trois familles.

  • Voir l’explication : Lire les versions autant que le numéro de PSR.

    Lire les versions autant que le numéro de PSR. La capacité PSR-6 est déclarée en 2.0|3.0, celle du container en 1.1|2.0. Une exigence exactement 1.0 ne devient pas satisfaite parce que le numéro « PSR-11 » apparaît dans une présentation générale. Les autres lignes ont leurs propres ensembles de versions. Pourquoi on se trompe : « Symfony implémente PSR-11 » est vrai, ce qui fait oublier de vérifier quelle version du paquet virtuel.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

Avant de fournir un objet à la bibliothèque du blog :

  1. Identifier son contrat : les capacités PSR déclarées ici concernent 3, 6, 11, 13, 14, 16, 18 et 20.
  2. Vérifier la version demandée et l'objet concret, pas seulement le package installé : notamment 2.0|3.0 pour le cache PSR-6 et 1.1|2.0 pour le container.
  3. Distinguer PSR-4, correspondance d'autoload, et PSR-12, conventions de code, des capacités listées dans provide.
  4. Fournir directement les objets compatibles PSR-11/PSR-14 quand ils conviennent, sans en déduire qu'un container entier est la bonne dépendance métier.
  5. Pour PSR-7, reconnaître la frontière avec HttpFoundation et les objets de message/fabrique nécessaires, sans supposer de conversion automatique.
  6. Lire les quinze entrées du manifeste dans leurs trois familles : huit PSR, cinq Contracts Symfony, deux HTTPlug.

Le bon test vérifie ce que reçoit effectivement le consommateur. Un nom de standard dans une dépendance ne charge pas l'article 42, ne remplit pas le cache et ne configure pas l'intégration à notre place.

Phrase de mémorisation : « Quinze annonces — 8 PSR, 5 Contracts, 2 HTTPlug ; PSR-4 et 12 se suivent, PSR-7 s'adapte ; et la version compte autant que le numéro. »
