Objectif

Un premier test lit /blog/42. Un scénario plus long ouvre ensuite une autre page, suit une redirection ou accède à un écran réservé au rédacteur. Le client conserve un état de navigation, tandis que le kernel et ses services peuvent être renouvelés entre deux requêtes. Il faut distinguer ces deux états pour comprendre le résultat observé.

Question centrale : qu'est-ce qui survit d'une requête à l'autre dans un test, et qu'est-ce qui est remis à zéro ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le client est simulé.
  2. Un comportement JavaScript nécessite un autre niveau de test.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un vrai navigateur garde cookies, historique et session ; le serveur, lui, traite chaque requête de façon indépendante. Le client de test imite cette séparation : il garde l'état « navigateur » et reconstruit le côté « serveur » entre deux requêtes.
  • Le piège de fond. Croire que tout persiste (ou que rien ne persiste). En réalité : cookies, historique, document courant survivent dans le client ; container, services et token en mémoire sont renouvelés.
  • Ce que l'auteur veut que vous compreniez. Trois réflexes : request() rend un Crawler (pas une Response), les redirects ne sont pas suivis par défaut, et le kernel redémarre entre deux requêtes.
  • Pourquoi c'est à l'examen. Les QCM jouent sur followRedirect() ≠ followRedirects(), sur le défaut de KernelBrowser ≠ BrowserKit, sur back() et sur le sort du token de sécurité.

static::createClient() rend un KernelBrowser qui simule un navigateur en mémoire : pas de serveur, pas de JavaScript. request() rend un Crawler. Le client ne suit pas les redirects par défaut. Et entre deux Requests, le kernel redémarre : le token de sécurité en mémoire est perdu.

Le Crawler représente le document à inspecter ; ce n'est pas la réponse HTTP elle-même. Le token de sécurité porte l'authentification courante du serveur ; ce n'est pas un jeton CSRF. Les cookies du navigateur et une session peuvent permettre de retrouver l'identité après le redémarrage, mais une variable gardée dans un service ne devient pas pour autant une session.

Le schéma

À retenir en priorité
  1. Le résultat facilite l'inspection HTML.
  2. La Response reste accessible séparément.

Où en est-on ? Début du cours : on pose la carte complète avant de zoomer. Elle contient deux choix indépendants — suivre ou non une redirection, et redémarrer ou non le kernel avant la requête suivante — que les sections suivantes détaillent une par une.

Lire d'abord une requête et sa réponse, puis les deux choix indépendants : suivre ou non une redirection, et renouveler ou réinitialiser les services avant la requête suivante :

Bleu : exécution ; ambre : choix ; vert : observation. La restauration suppose un token de session valide, un context correspondant et un provider capable de rafraîchir le user. Stateless ne signifie pas toujours anonyme : des credentials présents sur la nouvelle requête peuvent l'authentifier.

Qui garde quoi, en un coup d'œil :

┌──────────────────────────────┐   ┌─────────────────────────────────────┐
│ CLIENT (survit)              │   │ KERNEL / CONTAINER (renouvelé)      │
├──────────────────────────────┤   ├─────────────────────────────────────┤
│ cookies (CookieJar)          │   │ nouvelles instances de services     │
│ historique (back, forward)   │   │ token de sécurité en mémoire perdu  │
│ document courant (Crawler)   │   │ (sauf relu depuis la session)       │
│ dernière Response            │   │ sauf après disableReboot()          │
└──────────────────────────────┘   └─────────────────────────────────────┘

L'exemple

Exemple concret

À retenir en priorité
  1. Le mode de test laisse remonter l'exception.
  2. Le code applicatif n'est pas modifié.

Où en est-on ? On écrit d'abord le plus petit geste (une requête, deux assertions), puis un scénario avec redirection qui montre pourquoi le suivi manuel existe.

Le premier geste du parcours reste simple, dans une méthode de test WebTestCase avec l'application et ses fixtures configurées :

$client = static::createClient();
$crawler = $client->request('GET', '/blog/42');
self::assertResponseStatusCodeSame(200);
self::assertSelectorCount(1, 'h1');

Ce que Symfony fait : request() construit une requête BrowserKit, la convertit en Request HttpKernel, la passe au kernel dans le même processus, garde la Response et rend un Crawler sur le HTML reçu. $crawler sert à inspecter le document ; le statut se lit par les assertions (ou getResponse()).

Le scénario historique de commandes ci-dessous illustre une écriture suivie d'une redirection ; il est indépendant du blog et ne doit pas être ajouté à GET /blog/42. Il suppose des routes /orders existantes, un utilisateur de test autorisé, un firewall avec état et des paramètres valides pour l'annulation, y compris le jeton CSRF si l'action le demande. Ce fragment s'exécute dans un autre test, pas après un second createClient() sur un kernel déjà démarré :

$client = static::createClient();
$client->loginUser($user);                      // sans form de connexion
$crawler = $client->request('GET', '/orders');  // un Crawler, pas une Response
$client->request('POST', '/orders/42/cancel', $cancelParameters); // répond par un redirect
$this->assertResponseRedirects('/orders');      // le client ne l'a pas suivi
$client->followRedirect();                      // on le suit, une fois

Le helper de connexion évite de rejouer le formulaire pour ce scénario ; il ne teste ni le mot de passe ni l'authenticator. L'annulation et sa protection restent des comportements applicatifs à vérifier séparément.

Faire une Request

À retenir en priorité
  1. Le helper marque la Request comme AJAX.
  2. Il n'exécute pas de JavaScript.

Où en est-on ? Étape 1 sur 3 : l'acte de base. Comment le client fabrique-t-il une requête, et que rend-il ? Les deux autres étapes (redirects, requêtes multiples) s'appuient sur ce retour.

Le client construit une requête BrowserKit, la convertit pour HttpKernel et conserve la réponse reçue. Le retour facilite la lecture du document :

  • request($method, $uri, $parameters, $files, $server, $content, $changeHistory) rend un Crawler ; la Response se lit par $client->getResponse().
  • xmlHttpRequest() prend les mêmes arguments et ajoute HTTP_X_REQUESTED_WITH : isXmlHttpRequest() vaut true côté serveur.
  • Naviguer : back(), forward(), reload(), et restart(), qui vide les cookies et l'historique.
  • Le client est le service test.client, déclaré par framework.test.

Pourquoi request() rend-il un Crawler et pas une Response ? Parce que le cas d'usage dominant d'un test fonctionnel est d'inspecter le HTML (chercher un lien, un formulaire). Le Crawler est cet outil d'inspection ; la Response brute reste accessible par getResponse().

Méthode Ce qu'elle fait
request() requête simple ; rend un Crawler
xmlHttpRequest() idem + en-tête HTTP_X_REQUESTED_WITH
back() / forward() navigue dans l'historique
reload() rejoue la page courante
restart() vide cookies et historique

Les paramètres de formulaire et le contenu brut ne sont pas interchangeables : un document JSON attendu par /api/blog/42 doit être envoyé comme tel, avec son type de contenu. xmlHttpRequest() n'effectue ni ce choix de format, ni une requête JavaScript réelle ; il ajoute seulement le marqueur AJAX. reload() rejoue la page courante ; restart() efface notamment cookies et historique, sans recréer les données métier de test.

Les redirects

À retenir en priorité
  1. Le mode par défaut garde la Response de redirect.
  2. Distinguer action ponctuelle et réglage persistant.

Où en est-on ? Étape 2 sur 3 : la requête a abouti, mais la réponse est un 302. Le client s'arrête-t-il ou continue-t-il ? C'est le premier des deux choix du schéma.

🌍 In Real Life

La situation : le visiteur venu consulter le dossier du blog est renvoyé vers l'accueil. Trouver cet accueil ouvert ne prouve pas qu'il a consulté le dossier.

L’équivalent dans Symfony : renvoi → réponse de redirection ; déplacement suivant → followRedirect() ; accueil ouvert → éventuel 200 de la page de connexion.

Retour à la réalité technique : KernelBrowser ne suit pas les redirections par défaut. Observer d'abord statut et destination protège le contrat de la première réponse ; suivre ensuite est une nouvelle requête.

🧠 Comment le mémoriser : « Le 200 final peut être la mauvaise porte. » Image mentale : flèche vers l'accueil, dossier toujours fermé. Question-réflexe : quelle réponse suis-je réellement en train d'asserter ?

⚠️ À ne pas confondre : accès à la page demandée et succès de navigation après redirection.

Un écran d'édition du blog peut répondre par une redirection vers la connexion plutôt que par son contenu. Si le test suit tout automatiquement, un dernier 200 peut simplement être la page de connexion. Il faut donc observer la première réponse lorsque ce comportement fait partie du contrat.

Method Effet
followRedirect() suit la redirect en attente, une fois
followRedirects() change le mode : toutes les suivantes, à appeler avant la Request
followRedirects(false) revient au défaut
  • Le défaut n'est pas celui de BrowserKit : AbstractBrowser suit les redirects, mais HttpKernelBrowser, parent de KernelBrowser, désactive ce comportement. Un HttpBrowser, qui parle à un vrai serveur, les suit.
  • back() saute les redirects, mais seulement celles que le client a suivies seul, en mode followRedirects() :
Mode du client /created, puis /go qui redirige vers /hello ; après back()
followRedirects() /created, 201
par défaut, puis followRedirect() /go, de nouveau 302

Pourquoi cette différence pour back() ? AbstractBrowser::request() ne remplit sa liste interne $redirects que lorsque followRedirects est actif. back() boucle sur l'historique tant que l'URL reculée figure dans cette liste : un redirect suivi à la main n'y figure jamais, donc back() retombe sur l'URL qui a redirigé.

Mode followRedirects() :  /created → /go (302, noté) → /hello
                          back() saute /go           → /created
Suivi manuel            :  /created → /go (302) → followRedirect() → /hello
                          back() ne saute rien       → /go (302 de nouveau)

Pour un écran configuré /admin/blog/42 redirigeant un visiteur anonyme vers /login, ce fragment de WebTestCase distingue les deux réponses :

$client = static::createClient();
$client->request('GET', '/admin/blog/42');
self::assertResponseRedirects('/login');
$client->followRedirect();
self::assertResponseIsSuccessful();

Le premier contrôle prouve la redirection attendue ; le second prouve seulement un statut 2xx sur la destination. Ajouter une assertion sur son contenu si le contrat exige de reconnaître le formulaire de connexion. Dans le tableau d'historique, les routes /created, /go, /hello sont une fixture distincte : le client enregistre les redirections automatiquement suivies pour les sauter avec back(), contrairement au suivi manuel indiqué.

Plusieurs Requests dans un test

À retenir en priorité
  1. Le container peut changer entre Requests.
  2. Désactiver le reboot ne supprime pas tous les resets.

Où en est-on ? Étape 3 sur 3 : on enchaîne plusieurs requêtes dans un même test. C'est le second choix du schéma : que devient le côté serveur (kernel, container, token) entre deux appels ?

🌍 In Real Life

La situation : le client garde ses tickets de visite au restaurant, tandis que le personnel de service est renouvelé ou que ses notes temporaires sont effacées.

L’équivalent dans Symfony : tickets conservés → état BrowserKit ; nouvelle équipe → conteneur après reboot ; mêmes personnes aux notes effacées → services soumis au reset.

Retour à la réalité technique : disableReboot() ne désactive pas kernel.reset. Une référence PHP ancienne n'est pas nécessairement le service utilisé ensuite ; reconstruire des instances ne signifie pas recompiler le conteneur.

🧠 Comment le mémoriser : « Le visiteur continue, les services changent d'état. » Image mentale : mêmes tickets devant un bureau renouvelé. Question-réflexe : quel objet et quel état survivent à la prochaine requête ?

⚠️ À ne pas confondre : cookie de session, token en mémoire et authentification stateless.

La Request suivante redémarre le kernel : deux Requests, deux objects container différents. disableReboot() garde le même container, mais réinitialise les services kernel.reset — le stockage du token compris.

Pourquoi Symfony redémarre-t-il le kernel ? Pour imiter la réalité : en production, chaque requête HTTP part d'un état serveur vierge. Sans reboot, un service qui garde de l'état (compteur, cache mémoire) fausserait le scénario. Dans KernelBrowser::doRequest(), si une requête a déjà été faite et que le reboot est actif, le kernel est démarré puis arrêté (boot() puis shutdown()), ce qui force un container neuf à la prochaine gestion. Avant la toute première requête, il n'y a pas de reboot : createClient() a déjà démarré le kernel.

Par défaut Après disableReboot()
Container entre deux Requests nouveau le même
Services kernel.reset nouvelles instances réinitialisés
Token en mémoire perdu réinitialisé (perdu aussi)

Un conteneur neuf signifie ici de nouvelles instances de services : cela ne signifie pas que les extensions et compiler passes sont relancés à chaque requête. Le kernel peut réutiliser le conteneur compilé en cache. Après un reboot, une référence PHP conservée vers un ancien service n'est pas nécessairement celle utilisée par la requête suivante.

loginUser($user) place le token dans le stockage et, s'il y a une session, dans la session. Le deuxième argument nomme le firewall context, main par défaut.

Concrètement, loginUser() crée un TestBrowserToken, le met dans security.untracked_token_storage, puis, si une session existe, écrit _security_<contexte> (le token sérialisé) dans la session. C'est cette copie en session qui survit au reboot.

Le contexte détermine la clé de session de sécurité ; il doit correspondre au firewall testé, notamment si plusieurs firewalls partagent un contexte. Voici l'observation à interpréter sous les préconditions de session et de provider annoncées, pas une recommandation d'injection en mode stateless :

Firewall 1ʳᵉ Request 2ᵉ Request
avec état alice alice, relu de la session (« Read existing security token from the session »)
stateless: true alice anonyme

La ligne stateless décrit une observation d'injection en mémoire, sans credentials sur les requêtes ; ce n'est pas une garantie d'usage de loginUser(). L'exemple /orders suppose un firewall avec état et des routes existantes.

Pour l'API stateless, fournir la preuve attendue sur chaque requête. disableReboot() ne remplace ni cette preuve ni la restauration stateful, et ne garantit pas la conservation de tout état d'un service réinitialisable.

catchExceptions(false) laisse remonter l'exception que HttpKernel aurait sinon traitée en réponse d'erreur, notamment une page 500. Il ne crée pas une exception pour chaque statut 500 retourné volontairement par le code. C'est un choix de diagnostic du client, pas un changement du contrôleur.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le helper vise surtout un contexte stateful.
  2. Fournir la preuve requise à chaque Request stateless.
  • Voir l’explication : request() retourne un Crawler

    request() retourne un Crawler, pas une Response. Pourquoi on se trompe : on pense « requête → réponse » ; ici, la réponse est à part (getResponse()).

  • Voir l’explication : Le client de test ne suit pas les redirects par défaut

    Le client de test ne suit pas les redirects par défaut — alors que le AbstractBrowser de BrowserKit, lui, les suit. Pourquoi on se trompe : on généralise le défaut de BrowserKit à KernelBrowser, qui l'inverse.

  • Voir l’explication : followRedirect() ≠ followRedirects()

    followRedirect() ≠ followRedirects() : une fois, contre un réglage.

  • Voir l’explication : back() ne saute que les redirects suivis en mode followRedirects()

    back() ne saute que les redirects suivis en mode followRedirects() ; après un followRedirect() manuel, il revient sur l'URL qui a redirigé.

  • Voir l’explication : Le kernel redémarre entre deux Requests

    Le kernel redémarre entre deux Requests et le token en mémoire est perdu ; un firewall avec état le restaure depuis la session, un firewall stateless non. Pourquoi on se trompe : après loginUser(), on croit l'identité « collée » au client.

  • Voir l’explication : Aucun JavaScript n'est exécuté

    Aucun JavaScript n'est exécuté : c'est un client simulé, pas un navigateur.

Fiche express

À mémoriser

À retenir en priorité
  1. restart réinitialise l'état navigateur.
  2. Ce n'est pas seulement recharger la dernière page.

Dans le scénario du blog, vérifier d'abord quelle réponse est observée, puis quel état a survécu : document courant, historique, cookies, session et services ne sont pas un même objet persistant.

🧠 À retenir pour la certification :

  • request() → Crawler ; getResponse() → Response.
  • Pas de redirect suivi par défaut ; followRedirect() (une fois) / followRedirects() (mode, avant la Request).
  • back() saute seulement les redirects suivis en mode.
  • Kernel redémarré entre deux Requests ; disableReboot().
  • loginUser() : helper stateful avec session/contexte adaptés ; en stateless, credentials sur chaque requête.
  • catchExceptions(false) pour voir l'exception.
  • Aucun JavaScript ; xmlHttpRequest() pour l'AJAX.

Moyen mnémotechnique : « Requêter, rediriger à la main, redémarrer ».

Phrase de mémorisation : le client garde le navigateur (cookies, historique), le kernel est refait à chaque requête, et un redirect attend qu'on le suive.

createClient() = KernelBrowser (test.client) ; request() → Crawler
redirects : à la main (followRedirect) ou en mode (followRedirects)
entre deux Requests : reboot (disableReboot), token perdu sauf session
catchExceptions(false) ; pas de JavaScript

Le Crawler permet maintenant de sélectionner les éléments du document reçu ; sélectionner un lien n'est pas encore effectuer la requête suivante.
