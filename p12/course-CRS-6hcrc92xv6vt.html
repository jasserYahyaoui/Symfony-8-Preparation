Objectif

L'article 42 est consultable ; imaginons maintenant un lien temporaire permettant sa prévisualisation. Le même test doit pouvoir vérifier ce lien avant son échéance et après, quelle que soit l'heure de lancement. Clock résout ce problème en découplant l'application de l'heure système : le temps devient une dépendance que le test contrôle.

Le cours suit un fil en quatre temps : pourquoi l'heure doit être injectée, quelle clock choisir, comment l'injecter, comment tester.

L'essentiel

À comprendre

À retenir en priorité
  1. La dependency rend le temps remplaçable.
  2. Le test devient déterministe.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un service qui écrit new \DateTimeImmutable() lit l'heure de la machine : son résultat change selon l'heure du test. Il est impossible de tester « avant » et « après » une échéance de façon fiable.
  • Le problème que Symfony résout. Faire du temps une dépendance (une ClockInterface) qu'on remplace par une clock figée en test.
  • Ce que l'auteur veut que vous compreniez. Il y a trois sources de temps pour trois questions (date, durée, répétition), et deux traits pour deux rôles (service, test).
  • Pourquoi c'est à l'examen. Les questions portent sur : NativeClock / MockClock / MonotonicClock, sleep() instantané, DatePoint, ClockAwareTrait (#[Required] = autowiring), mockTime(), Clock::set().

Le component Clock existe pour découpler le code de la clock système : un service qui lit l'heure par une ClockInterface injectée se teste pour n'importe quelle date. NativeClock en production, MockClock en test, MonotonicClock pour chronométrer. Une MockClock ne bouge jamais seule.

Une clock fournit « maintenant » ; elle ne décide pas si un lien est autorisé ou un article publié. Cette décision reste dans le service métier. Le contrat PSR-20, Psr\Clock\ClockInterface, fournit now() ; l'interface Symfony du même nom ajoute notamment sleep() et withTimeZone(). Un service qui ne demande que l'heure peut dépendre du contrat PSR-20.

Comparaison : contrat PSR-20 et interface Symfony

Psr\Clock\ClockInterface Symfony\Component\Clock\ClockInterface
Méthodes now() now(), plus sleep(), withTimeZone()
Quand le type-hinter le service ne lit que l'heure le service doit aussi dormir / changer de fuseau

Le schéma

À retenir en priorité
  1. Une durée demande un temps monotone.
  2. L'heure civile peut être corrigée par le système.

Où en est-on ? Étape 1 sur 4 : la carte du cours. Trois éléments sont séparés : la source de l'heure, l'échéance donnée au service, la comparaison. Le test ne déplace que la première.

Nous séparons trois éléments : la source de l'heure, l'échéance fournie au service, puis la comparaison. Le test déplace la première, sans changer ni l'échéance ni l'algorithme :

Bleu : objets et appels ; vert : valeurs observées. Le code métier ne connaît pas MockClock : le test choisit l'implémentation. En production, injecter NativeClock conserve le même appel ; la clock globale et le chronomètre sont des choix distincts, décrits plus bas.

Avant / après : de la clock système à la clock injectée

 AVANT   isExpired() { return new \DateTimeImmutable() > $limit; }
         → heure de la machine, test non déterministe
 APRÈS   isExpired() { return $this->clock->now() > $limit; }
         → production : NativeClock    test : MockClock figée

L'exemple : un token qui expire

Exemple concret

À retenir en priorité
  1. Le temps simulé peut avancer instantanément.
  2. Le test n'attend pas le délai réel.

Où en est-on ? Étape 2 sur 4 : le code minimal. Un service de 3 lignes qui compare l'heure de la clock à une échéance, puis un test qui avance le temps sans attendre.

Ici, « token » désigne seulement le lien temporaire du scénario. Ce checker ne génère pas sa valeur, ne vérifie pas sa signature et ne remplace ni l'authentification ni la protection CSRF. Avec Symfony Clock 8.0 chargé :

<?php
use Psr\Clock\ClockInterface;
use Symfony\Component\Clock\MockClock;

class ExpirationChecker
{
    public function __construct(private ClockInterface $clock) {}

    public function isExpired(\DateTimeInterface $validUntil): bool
    {
        return $this->clock->now() > $validUntil;
    }
}

$clock = new MockClock('2022-11-16T15:20:00+00:00');
$checker = new ExpirationChecker($clock);
$limit = new \DateTimeImmutable('2022-11-16T15:25:00+00:00');
$checker->isExpired($limit); // false
$clock->sleep(600);          // 15:30:00, sans attendre
$checker->isExpired($limit); // true

Les deux dates utilisent ici le même fuseau. Le > signifie qu'à exactement 15h25 le token n'est pas encore expiré ; choisir >= si la règle métier exclut aussi la borne, puis tester explicitement ce cas.

Le fuseau est explicite : sans cela, une chaîne passée à MockClock utilise par défaut UTC alors qu'une DateTimeImmutable native sans fuseau dépend de la configuration PHP. Un test supposant des heures comparables ne doit pas laisser cette différence implicite.

Pourquoi isExpired() passe-t-il de false à true sans attendre ?

Étape par étape :

 MockClock créée à 15:20          now() = 15:20  → 15:20 > 15:25 ?  false
 $clock->sleep(600)               l'état interne avance de 600 s
 now() = 15:30                    15:30 > 15:25 ?                    true

sleep() de MockClock ne suspend pas le processus : il déplace l'heure simulée. Les 10 minutes sont virtuelles.

Trois clocks, trois usages

À retenir en priorité
  1. Chaque implémentation répond à un usage.
  2. Ne pas utiliser l'heure civile comme chronomètre fiable.

Où en est-on ? Étape 3 sur 4 (partie 1/2) : avant d'injecter, il faut choisir quelle clock. La bonne dépend de la question posée : une date, une durée ou une répétition.

🌍 In Real Life

La situation : au bureau du blog, une pendule indique la date limite, un chronomètre mesure l'import et une pendule de démonstration permet de répéter un exercice.

L’équivalent dans Symfony : heure civile → NativeClock ; durée monotone → MonotonicClock ; instant contrôlé → MockClock.

Retour à la réalité technique : choisir la source selon la question posée. Une mesure monotone évite les sauts de l'horloge système ; une heure simulée ne modifie pas l'heure de la machine.

🧠 Comment le mémoriser : « Date, durée ou répétition ? » Image mentale : trois instruments sur le bureau. Question-réflexe : quel temps ma règle utilise-t-elle ?

⚠️ À ne pas confondre : source temporelle et convention métier d'expiration.

L'échéance du lien appartient au temps civil ; la durée de app:blog:import est une mesure écoulée. Ce sont deux questions distinctes :

Implémentation Ce qu'elle fait Quand
NativeClock l'heure système — équivalent à new \DateTimeImmutable() production
MockClock une heure figée, déplacée à la main tests
MonotonicClock hrtime(), haute résolution et monotone mesurer une durée

NativeClock::now(), comme la function now(), rend un DatePoint, accepté partout où un DateTimeImmutable est attendu. MonotonicClock est un chronomètre : la clock système peut reculer au milieu d'une mesure, elle non.

MonotonicClock expose aussi des dates, mais calcule leur progression à partir de hrtime() après son initialisation. Son intérêt est la différence entre deux mesures, pas le suivi des corrections ultérieures de l'heure civile. MockClock, à l'inverse, avance seulement quand le test le demande. Ne pas remplacer un temps civil de publication par une mesure de durée.

Quelle clock pour quelle question ?

 « Cette offre est-elle expirée ? »     → date civile    → NativeClock (prod)
 « Combien de temps a duré l'import ? » → durée écoulée  → MonotonicClock
 « Et si on était le 1er janvier ? »    → temps simulé   → MockClock (test)

Pourquoi MonotonicClock pour chronométrer ?

Si l'heure système est corrigée (synchronisation réseau, changement d'heure) pendant l'import, la différence entre deux now() civils peut être fausse, voire négative. hrtime() croît régulièrement : la différence reste valable.

⚠️ À ne pas confondre : MonotonicClock et NativeClock. Plausible car les deux ont un now() qui rend une date ; mais seule la première convient à une durée, seule la seconde à une date civile de publication.

Injecter la clock

À retenir en priorité
  1. Le setter utilise Required.
  2. L'autoconfiguration seule ne câble pas cet argument.

Où en est-on ? Étape 3 sur 4 (partie 2/2) : on connaît les clocks ; comment le service reçoit-il la sienne ? Deux voies : le constructeur (vu ci-dessus) ou ClockAwareTrait.

Dans le premier exemple, le constructeur rend la dépendance visible et le test passe directement son objet. En application, le conteneur peut résoudre le type si un service/alias de clock approprié est configuré. Il prépare ce câblage ; il ne recompile pas ses définitions à chaque consultation de /blog/42 ni à chaque appel de now().

  • Remplacer new \DateTimeImmutable() par $this->clock->now() ; la logique ne change pas.
  • Variante sans parameter de constructor : ClockAwareTrait, puis $this->now(). La documentation attribue l'appel de setClock() à l'autoconfiguration ; le code le fait par l'autowiring (#[Required]) : injectée avec autowire seul, pas avec autoconfigure seul. Sans injection, now() se replie sur la clock globale Clock.
  • Clock::set() accepte toute clock PSR-20 ; now('+3 hours') accepte un modificateur ; new DatePoint() lit Clock, d'où son usage comme default value testable.

L'autowiring résout les arguments et les méthodes requises ; l'autoconfiguration applique des règles de définition, comme des tags. Lire #[Required] ne signifie donc pas « cette classe est un listener ».

Le repli du trait initialise sa propriété readonly avec un objet Clock qui consulte la globale. Injecter explicitement une MockClock fixe, au contraire, cette dépendance précise. Modifier la globale ne parcourt pas les services déjà construits pour remplacer leurs propriétés.

Pourquoi #[Required] relève-t-il de l'autowiring ?

#[Required] marque une méthode (ici setClock()) que le conteneur doit appeler après construction en lui passant les services dont elle a besoin : c'est une résolution d'arguments, donc de l'autowiring. L'autoconfiguration, elle, applique des tags et des règles de définition.

 autowire: true       → setClock() (#[Required]) appelée, ClockInterface résolue
 autoconfigure: true  → tags / règles par interface ; n'appelle PAS setClock()
 aucune injection     → now() se replie sur la clock globale Clock

Comparaison : injection explicite et repli global

Injection (constructeur ou setClock()) Repli global Clock
Source de l'heure l'objet reçu (ex. MockClock) Clock::get()
Suit Clock::set() non (dépendance déjà fixée) oui
Test passer la clock directement mockTime() + restauration

Pour isoler la règle inclusive avant d'utiliser le trait, on peut vérifier directement le même changement d'instant :

<?php
use Symfony\Component\Clock\MockClock;

$clock = new MockClock('2026-01-01T10:00:00+00:00');
$expiresAt = new \DateTimeImmutable('2026-01-01T10:01:00+00:00');
var_dump($clock->now() >= $expiresAt);
$clock->sleep(60);
var_dump($clock->now() >= $expiresAt);

Résultat attendu : bool(false), puis bool(true), sans minute d'attente. L'instant avance dans la clock ; une date immutable précédemment récupérée ne se transforme pas rétroactivement.

Tester

À retenir en priorité
  1. Le test maîtrise chaque changement.
  2. Deux now() successifs peuvent être identiques.

Où en est-on ? Étape 4 sur 4 : la clock est injectée ; reste à écrire le test sans contaminer les autres. Ici interviennent la clock globale, le trait ClockSensitiveTrait et la restauration par les hooks PHPUnit.

🌍 In Real Life

La situation : pour répéter la fermeture des prévisualisations du blog, on avance une pendule de démonstration puis on remet le bureau dans son état initial.

L’équivalent dans Symfony : avancer sans attendre → MockClock::sleep() ; remplacer la référence commune → clock globale ; remettre l'ancienne référence → hooks du trait de test.

Retour à la réalité technique : une clock injectée localement et le repli global n'ont pas la même portée. Les hooks PHPUnit restaurent la clock sauvegardée ; un appel statique hors de ce cycle ne déclenche pas cette restauration.

🧠 Comment le mémoriser : « Simuler, puis restituer. » Image mentale : l'ancienne pendule étiquetée à côté. Question-réflexe : qui utilise cette référence et qui la restaure ?

⚠️ À ne pas confondre : temps simulé écoulé et attente réelle du processus.

La règle métier fonctionne ; le risque suivant est de laisser un temps figé contaminer les autres tests. Choisir l'injection locale suffit au premier exemple. Si le code utilise le repli global, il faut aussi gérer le cycle de sauvegarde et de restauration :

MockClock n'avance pas d'elle-même : sleep(600) déplace l'heure en 0 seconde réelle, modify('+1 day') accepte les formats de DateTimeImmutable::modify().

ClockSensitiveTrait::mockTime() pilote la clock globale. Les hooks PHPUnit sauvegardent la clock présente avant le test et la restaurent ensuite : elle peut être personnalisée, pas nécessairement une NativeClock. Un appel statique hors PHPUnit ne déclenche pas automatiquement ces hooks.

Appel Résultat
mockTime('1996-07-01') une MockClock à 1996-07-01 00:00
puis mockTime('+2 days') 1996-07-03 : l'intervalle part de l'heure déjà figée
mockTime(false) la clock sauvegardée avant le test
après restauration, avant le test suivant Clock::get() retrouve la clock sauvegardée, éventuellement personnalisée 
  avant le test       pendant le test           après le test
  Clock::get() = A ─▶ mockTime() → MockClock ─▶ hooks restaurent A
  (sauvegardée)       (A mise de côté)          (même A, pas forcément Native)

Pourquoi mockTime('+2 days') donne-t-il le 3 juillet ?

Après mockTime('1996-07-01'), la clock globale est une MockClock à cette date. Un second appel avec un intervalle (+2 days) le déplace depuis l'heure déjà figée, pas depuis l'heure réelle : 1996-07-03.

Un test de frontière doit être déterministe et ne pas contaminer les suivants. Voici le service utilisant réellement ClockAwareTrait ; on choisit ici la convention expiré à l'échéance exacte (>=) :

<?php
use Symfony\Component\Clock\ClockAwareTrait;

final class DeadlineChecker
{
    use ClockAwareTrait;

    public function isExpired(\DateTimeInterface $deadline): bool
    {
        return $this->now() >= $deadline;
    }
}

Avec cette classe chargée, l'autoload Symfony Clock 8.0 et PHPUnit 11.5 disponibles :

<?php
use PHPUnit\Framework\TestCase;
use Symfony\Component\Clock\Test\ClockSensitiveTrait;

final class DeadlineCheckerTest extends TestCase
{
    use ClockSensitiveTrait;

    public function testBoundary(): void
    {
        $clock = self::mockTime('2026-01-01T10:00:00+00:00');
        $checker = new DeadlineChecker();
        $checker->setClock($clock);
        $deadline = new \DateTimeImmutable('2026-01-01T10:01:00+00:00');

        self::assertFalse($checker->isExpired($deadline));
        $clock->sleep(60);
        self::assertTrue($checker->isExpired($deadline));
    }
}

La minute est virtuelle. L'injection explicite fixe la clock de ce service : changer une globale ne remplace pas une dependency déjà injectée. Ne pas réinitialiser la property readonly du même service ; en construire un nouveau si l'injection doit changer. Les hooks restaurent la globale ; hors PHPUnit, une modification manuelle exige sa propre restauration dans un finally. L'exemple précédent en > exprime une autre convention de frontière et ne sert pas de référence à ces assertions en >=.

Les deux assertions protègent deux états : lien encore valable à 10h00, puis expiré à 10h01 exactement. Ajouter un appel HTTP n'est pas nécessaire pour tester cette comparaison ; un test fonctionnel séparé vérifiera que le contrôleur utilise réellement le service et traduit le refus en réponse.

Comparaison : les deux traits

ClockAwareTrait ClockSensitiveTrait
Où dans le service dans la classe de test
Fournit now(), setClock() mockTime(), sauvegarde/restauration
Rôle lire l'heure injectée figer et restaurer la clock globale

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le nom reprend le contrat de clock.
  2. L'implémentation de test évite l'attente.
  • Voir l’explication : Où en est-on ?

    Où en est-on ? Les quatre étapes sont faites. Voici les erreurs de QCM probables, avec la raison pour laquelle la mauvaise réponse semble juste.

  • Source de l’heure et convention de borne

    Pour chaque question, identifier l'objet qui fournit l'heure et la convention de borne avant de choisir une API. Une globale, une dépendance injectée et l'horloge du système ne sont pas un seul objet :

  • Voir l’explication : MockClock n'avance jamais seule.

    MockClock n'avance jamais seule. Sans sleep() ni modify(), deux appels à now() rendent la même heure. Plausible car on l'imagine comme une horloge qui tourne à partir d'un point de départ.

  • Voir l’explication : sleep() ne suspend pas l'exécution

    sleep() ne suspend pas l'exécution dans une MockClock : elle déplace l'heure simulée instantanément. Plausible car sleep() natif de PHP, lui, bloque.

  • Voir l’explication : NativeClock est l'équivalent de new \DateTimeImmutable()

    NativeClock est l'équivalent de new \DateTimeImmutable() — l'intérêt n'est pas ce qu'elle rend, c'est qu'on puisse la remplacer. Plausible car on cherche une valeur ajoutée « fonctionnelle ».

  • Voir l’explication : MonotonicClock sert à mesurer une durée

    MonotonicClock sert à mesurer une durée, pas à connaître la date. Plausible car elle expose des dates et semble plus « précise ».

  • Voir l’explication : Deux traits, deux roles

    Deux traits, deux roles : ClockAwareTrait dans le service, ClockSensitiveTrait dans le test. Plausible car leurs noms se ressemblent.

  • Voir l’explication : setClock() est appelé par l'autowiring

    setClock() est appelé par l'autowiring (#[Required]), pas par l'autoconfiguration. Plausible car la documentation parle d'autoconfiguration.

  • Voir l’explication : DatePoint lit Clock

    DatePoint lit Clock : ce n'est pas un DateTimeImmutable ordinaire — et c'est ce que rendent NativeClock::now() et now(). Plausible car il est accepté partout où un DateTimeImmutable l'est.

  • Voir l’explication : mockTime('+2 days') part de l'heure figée

    mockTime('+2 days') part de l'heure figée, pas de l'heure réelle. Plausible car « +2 days » s'entend naturellement comme « à partir d'aujourd'hui ».

Fiche express

À mémoriser

À retenir en priorité
  1. Une clock globale modifiée doit être réinitialisée.
  2. L'isolation évite d'affecter les tests suivants.

Nous pouvons maintenant traverser une échéance sans attente réelle et sans toucher à l'horloge de la machine. Le résultat métier reste une décision explicite du checker ; Clock fournit seulement une entrée contrôlée.

Si tu dois retenir seulement 7 choses :

  • But : découpler du temps système, pour tester.
  • NativeClock prod, MockClock test, MonotonicClock durée.
  • $this->clock->now() remplace new \DateTimeImmutable().
  • MockClock figée ; sleep() et modify() instantanés.
  • ClockAwareTrait : setClock() par l'autowiring.
  • ClockSensitiveTrait::mockTime() : string, DateTimeImmutable, booléen.
  • DatePoint lit Clock ; Clock::set() accepte une clock PSR-20.

🧠 À retenir pour la certification :

  • Clock = le temps devient une dépendance : ClockInterface injectée, jamais new \DateTimeImmutable() dans la logique.
  • NativeClock (prod, rend un DatePoint), MockClock (test, figée), MonotonicClock (hrtime(), durées).
  • MockClock::sleep() et modify() déplacent l'heure sans attendre ; elle n'avance jamais seule.
  • ClockAwareTrait (service) : setClock() en #[Required] → autowiring ; sans injection, repli sur Clock globale.
  • ClockSensitiveTrait::mockTime() (test) : false restaure ; '+2 days' part de l'heure figée ; hooks PHPUnit restaurent.
  • Clock::set() accepte toute clock PSR-20 ; DatePoint lit Clock.
  • Une clock fournit l'heure ; la règle d'expiration (> ou >=) reste dans le service.

Moyen mnémotechnique : « Injecter l'heure, figer le test ».

Phrase de mémorisation : « Le service demande l'heure à une clock qu'on lui injecte : NativeClock en prod, MockClock figée en test, MonotonicClock pour chronométrer, et les hooks du test remettent la globale en place. »

Poursuivre avec les tests unitaires pour choisir ce qu'on isole. Une expiration d'objet en cache applicatif ou une fraîcheur HTTP relève ensuite de son propre mécanisme : injecter cette clock ne règle pas automatiquement leurs durées.
