Objectif

Le blog a besoin d'une page de confidentialité et de conserver une ancienne adresse. Aucun de ces besoins n'exige de lire ArticleCatalog : une action fournie par le framework peut produire la réponse. Elle reste un contrôleur résolu et appelé par HttpKernel, pas un raccourci qui contourne tout le cycle.

Connaître les controllers que FrameworkBundle fournit tout faits, et le cas d'usage de chacun : afficher une page sans écrire de code.

Question fil rouge : comment une route peut-elle produire une page ou une redirection sans qu'on écrive la moindre classe de contrôleur, et quelles décisions ce « sans code » cache-t-il ? Ce cours s'appuie sur le trajet vu dans HttpKernel component and FrameworkBundle et sur le matching des arguments de Argument value resolvers.

L'essentiel

À comprendre

À retenir en priorité
  1. Les defaults deviennent des Request attributes.
  2. Ils fournissent les arguments par leur nom.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une page statique ou une vieille URL à rediriger ne justifie pas une classe PHP. Le framework fournit des contrôleurs génériques pilotés par la configuration de la route.
  • Le piège de fond. « Sans code » ne veut pas dire « sans contrôleur » : le cycle HTTP reste le même, seul le contrôleur est standard.
  • Ce que l'auteur veut que vous compreniez. Les defaults de la route deviennent des attributes de Request, puis des arguments appariés par nom.
  • Pourquoi c'est à l'examen. Les détails que le code tranche : cache public, 307/308, cible vide, mode path contre mode route.

Une route peut viser un controller fourni par FrameworkBundle, réglé par ses seuls defaults : TemplateController rend un template, RedirectController redirige. L'examen interroge ce que le code tranche : cache public, 307/308, cible vide, mode path contre mode route.

Le schéma

Où en est-on ? On sait qu'une route peut viser un contrôleur du framework. Le plan ci-dessous résume les deux contrôleurs et leurs options ; lisez-le d'abord en texte, puis dans le détail du diagramme.

route + controller: <FQCN du framework> + defaults
        │  (defaults ─► Request::attributes ─► arguments, par nom)
        ├─► TemplateController : template (seul obligatoire), maxAge, ...
        └─► RedirectController
              ├─ route  ─► URL absolue générée
              ├─ path   ─► path complété, ou URL complète telle quelle
              └─ les deux, ou aucun ─► RuntimeException

Bleu = données et construction de réponse ; ambre = sélection de destination. Le statut ne valide pas la destination : garder ces defaults sous contrôle de l'application. Une page en cache public ne doit pas intégrer de contenu personnalisé ; le listener de session peut encore modifier ses headers.

L'exemple : deux routes sans code

Exemple concret

Où en est-on ? Voici le cas concret avant les détails : deux routes YAML, aucune classe PHP.

/privacy doit rendre un contenu public stable ; /old-blog doit renvoyer le client vers une autre route. L'exemple suppose blog_index définie et Twig configuré pour le premier cas. Il configure les réponses, il n'effectue pas lui-même la nouvelle requête du navigateur.

acme_privacy:
    path: /privacy
    controller: Symfony\Bundle\FrameworkBundle\Controller\TemplateController
    defaults:
        template: 'static/privacy.html.twig'
        maxAge: 86400

legacy_blog:
    path: /old-blog
    controller: Symfony\Bundle\FrameworkBundle\Controller\RedirectController
    defaults:
        route: 'blog_index'
        permanent: true

Remarquez que template, maxAge, route et permanent ne sont pas des clés spéciales du routeur : ce sont de simples defaults, comme _format ou page. Leur sens vient uniquement des noms d'arguments du contrôleur.

Le principe

Où en est-on ? Le mécanisme commun aux deux contrôleurs : comment un default de route arrive-t-il dans une méthode PHP ?

Les defaults de la route ont déjà été copiés dans Request::attributes. Le resolver de contrôleur obtient le callable fourni par le framework ; l'ArgumentResolver fournit ensuite template, route ou les autres options selon la signature. Ces valeurs sont de la configuration de route, pas des services injectés à partir de leur nom.

Rien n'oblige le controller d'une route à être une class de l'application. Les defaults deviennent des attributes de la Request, puis des arguments, appariés par nom.

defaults: { template: 'static/privacy.html.twig', maxAge: 86400 }
   ─► Request::attributes['template'], ['maxAge']      (matching du routeur)
   ─► ArgumentResolver : argument $template  ◄── attributes['template']
                         argument $maxAge    ◄── attributes['maxAge']
   ─► TemplateController::__invoke($template, $maxAge, ...)

Vérifié (8.0) : TemplateController::__invoke(string $template, ?int $maxAge = null, ?int $sharedAge = null, ?bool $private = null, array $context = [], int $statusCode = 200, array $headers = []) délègue à templateAction().

🌍 In Real Life

La situation : pour remettre le règlement du restaurant, l'accueil utilise une procédure déjà prête plutôt que d'inventer une recette. La demande suit toujours l'organisation du service ; seule la tâche choisie est standard.

L’équivalent dans Symfony : la route désigne un contrôleur fourni par le framework. Le matching fournit les attributs de Request, ControllerResolver obtient le callable, ArgumentResolver prépare ses valeurs, puis HttpKernel appelle le contrôleur.

Retour à la réalité technique : « sans code applicatif » ne signifie pas « sans contrôleur » ou « hors cycle HTTP ». Les defaults tels que template sont des valeurs de configuration appariées aux arguments, pas des services découverts par leur nom.

🧠 Comment le mémoriser : « Une tâche standard suit le même service. » Image mentale : fiche de procédure prête dans le circuit habituel. Question-réflexe : qu'est-ce qui est réutilisé : le contrôleur ou tout un autre trajet HTTP ?

⚠️ À ne pas confondre : cible de route, callable résolu, valeurs d'arguments et invocation.

Pour une brochure statique ou une indication de déménagement, la réception suit une fiche sans appeler un responsable. TemplateController et RedirectController jouent ce rôle à partir des defaults de route.

`TemplateController`

À retenir en priorité
  1. template est le parameter obligatoire.
  2. Un maxAge configuré peut rendre la Response publique sans private explicite.

Où en est-on ? Premier contrôleur : afficher une page. Pourquoi il existe : rendre un template n'exige aucun calcul ; seule la décision de cache demande de la réflexion.

Pour la page de confidentialité, le choix du template suffit si aucun calcul applicatif n'est nécessaire. Le cache public peut être adapté à ce contenu identique pour tous ; il ne le serait pas à une page affichant le nom du lecteur. Les options ci-dessous façonnent la Response avant les listeners de réponse, qui peuvent encore la modifier.

Rend un template sans code, pour une page statique. template est le seul obligatoire ; statusCode vaut 200 par défaut ; sans TwigBundle, le controller lève une LogicException. Pour le cache :

  • sans private, poser maxAge ou sharedAge rend la Response publique ;
  • private: true la rend privée, private: false publique ;
  • maxAge n'est appliqué que s'il est non nul : maxAge: 0 ne pose aucun max-age, mais la Response devient publique quand même ; sharedAge: 0 pose bien un s-maxage=0.

Pourquoi ces cas zéro surprennent : le code teste if ($maxAge) (faux pour 0) mais null !== $sharedAge (vrai pour 0), et la décision publique/privée regarde null !== $maxAge, donc 0 compte comme « renseigné ».

private   maxAge   sharedAge    Cache-Control
 null      null      null       (rien posé)
 null      86400     null       public, max-age=86400
 null       0        null       public            (pas de max-age)
 null      null       0         public, s-maxage=0
 true      86400     null       private, max-age=86400
 false     null      null       public

Vérifié (8.0, templateAction) : if ($maxAge) setMaxAge ; if (null !== $sharedAge) setSharedMaxAge ; if ($private) setPrivate() sinon elseif (false === $private || (null === $private && (null !== $maxAge || null !== $sharedAge))) setPublic(). Le constructeur reçoit ?Environment $twig = null ; null → LogicException.

🌍 In Real Life

La situation : l'accueil distribue une notice identique à tous. On peut en garder des copies communes ; une lettre portant le nom et les informations d'un visiteur ne doit pas rejoindre cette pile.

L’équivalent dans Symfony : TemplateController rend le template configuré et construit la Response. Ses options de cache indiquent si les caches peuvent partager la réponse et combien de temps elle reste fraîche ; elles ne rendent pas un contenu personnalisé partageable.

Retour à la réalité technique : Twig doit être disponible. Les réglages de ce contrôleur peuvent rendre la réponse publique lorsqu'un âge est fourni sans choix private. Les cas zéro diffèrent entre maxAge et sharedAge comme indiqué ci-dessus ; les listeners peuvent encore modifier les headers.

🧠 Comment le mémoriser : « Notice commune, copie commune ; lettre personnelle, pas de pile publique. » Image mentale : deux piles bien séparées. Question-réflexe : le contenu est-il réellement identique pour tous les destinataires autorisés ?

⚠️ À ne pas confondre : cache privé et contrôle d'accès ; âge de cache et garantie qu'une copie sera effectivement stockée.

`RedirectController`

À retenir en priorité
  1. La permanence et la conservation de method sont deux axes.
  2. route et path sont des modes exclusifs.

Où en est-on ? Second contrôleur : rediriger. Pourquoi une redirection n'est pas un forward : le serveur ne sert pas la page, il dit au client d'aller la chercher ailleurs (voir Internal redirects pour le forward interne).

Pour une ancienne URL de l'article, le contrôleur prépare Location et un statut 3xx. Il ne rend pas le contenu de /blog/42 : le client doit faire une autre requête. Choisis ensuite si la destination est un nom de route ou un chemin, et si la méthode d'origine doit être conservée.

Redirige depuis la route elle-même. Deux modes exclusifs : route pour viser une route, path pour un path ou une URL.

Option Effet
permanent: true 301 au lieu de 302
keepRequestMethod: true conserve la method HTTP : 307, ou 308 si permanent
keepQueryParams: true conserve la query string — mode route seulement
ignoreAttributes true n'en transmet aucun, un array retire ceux-là 
                permanent: false     permanent: true
keepRequestMethod
   false            302                  301
   true             307                  308

🌍 In Real Life

La situation : à l'ancienne entrée du restaurant, un panneau indique la nouvelle adresse. Il ne sert pas le repas : le visiteur doit se déplacer. Une consigne précise peut demander de présenter la même commande à la nouvelle entrée.

L’équivalent dans Symfony : RedirectController renvoie une Response 3xx avec Location. Le client décide de suivre cette indication avec une nouvelle requête. permanent et keepRequestMethod distinguent permanence et conservation de la méthode.

Retour à la réalité technique : 307 et 308 préservent la méthode lors du suivi conforme ; 308 ajoute la permanence. Ce n'est pas un appel serveur du contrôleur cible. Une destination maîtrisée reste indispensable, surtout si la requête contient des données de formulaire.

🧠 Comment le mémoriser : « Le panneau indique, le client repart. » Image mentale : ancienne entrée et flèche vers la nouvelle. Question-réflexe : dois-je déplacer cette requête avec sa méthode ou conduire vers une page de confirmation ?

⚠️ À ne pas confondre : redirection HTTP, forward interne et redirection après traitement réussi d'un POST.

Repère — Ce que le code tranche :

Question: Can RedirectController receive both route and path destinations?

Answer: No. Ambiguous redirection settings throw an exception.

Choisir une seule destination. Une cible vide produit 404 ou 410 selon la permanence.

Ce que le code tranche

À retenir en priorité
  1. Choisir une seule destination.
  2. Une cible vide produit 404 ou 410 selon la permanence.

Où en est-on ? Les options sont connues ; reste ce que le code décide dans les cas limites. C'est là que se logent les questions d'examen.

Supposons /old-blog/42 destiné à blog_show. En mode route, id sert à générer une URL absolue vers l'article. En mode path, la destination est déjà un chemin ou une URL : les paramètres ne suivent pas la même règle. Avant d'interpréter un échec comme une erreur de configuration, distingue l'absence de choix de mode, deux modes simultanés et une cible vide.

  • route et path ensemble lèvent une RuntimeException (Ambiguous redirection settings) ; aucun des deux en lève une aussi.
  • Une cible vide lève une HttpException 404, ou 410 si permanente.
  • Mode route : les parameters de la route courante sont transmis à la cible, et l'URL générée est absolue — à l'inverse de redirectToRoute().
  • Mode path : la query string est recopiée sur un path, sans option pour s'en passer ; une URL complète https://… part telle quelle, sans la query d'origine. Une référence //… reçoit d'abord le schéma choisi, sans cette query non plus. Un path est complété par le schéma, le host et le port, que scheme, httpPort et httpsPort permettent de fixer.

Ainsi, « conserver les paramètres » ne décrit pas un comportement universel : /old-blog/42?ref=mail exige de regarder le mode et la forme de la cible. Une exception levée ici n'est pas une Response de redirection ; elle peut être prise en charge par le chemin d'erreur configuré, traité ci-dessous.

__invoke : lit _route_params
  'route' présent ?  ── + 'path' présent ──► RuntimeException (ambigu)
        │ oui                      
        └─► redirectAction : route vide ? 404 / 410 ; sinon URL absolue
  'path' seul ?      ──► urlRedirectAction : path vide ? 404 / 410
        │                 URL complète ? telle quelle
        │                 sinon schéma://host[:port]baseUrl + path + query
  aucun des deux ?   ──► RuntimeException (paramètre requis)

Vérifié (8.0, RedirectController) : __invoke() lit _route_params ; redirectAction() fait array_key_exists-puis router->generate($route, $attributes, ABSOLUTE_URL) et retire des attributs route, permanent, ignoreAttributes, keepRequestMethod, keepQueryParams ; avec keepQueryParams, la query est fusionnée sous les paramètres de route (array_merge($query, $attributes)). urlRedirectAction() construit scheme://host[:port]baseUrl.path.query ; le port n'est ajouté que s'il diffère de 80 (http) ou 443 (https).

🌍 In Real Life

La situation : le panneau peut nommer une salle connue du plan interne ou donner une adresse complète. Traduire « salle des réservations » en adresse n'est pas recopier une adresse déjà écrite ; les notes annexes ne suivent pas forcément de la même façon.

L’équivalent dans Symfony : le mode route génère une URL absolue avec les paramètres transmis selon sa configuration. Le mode path traite un chemin ou une URL ; la copie de query string dépend de cette forme, et non de keepQueryParams comme en mode route.

Retour à la réalité technique : choisir les deux modes ou aucun est une erreur de configuration. Une cible vide suit un autre cas : exception HTTP 404 ou 410 selon la permanence, pas une redirection réussie. Paramètres de route et query string doivent être examinés séparément.

🧠 Comment le mémoriser : « Nom à résoudre ou adresse à reprendre ? » Image mentale : plan interne à côté d'une enveloppe adressée. Question-réflexe : quel mode, quelle forme de cible, quelles données seront retransmises ?

⚠️ À ne pas confondre : cible vide, mode absent et mode ambigu ; construction d'URL et approbation de sa destination.

`ErrorController`

À retenir en priorité
  1. ErrorController centralise le rendu d'erreur.
  2. Le preview de développement utilise notamment /_error/404.

Où en est-on ? Dernier contrôleur intégré, d'une autre famille : il ne répond pas à une route que vous écrivez, il intervient quand une exception survient. Voir aussi Generate 404 pages.

Si l'ancienne cible est vide ou si l'application lève une 404 pour l'article 999, le traitement d'exception configuré peut déléguer le rendu à ErrorController. Cette classe appartient au composant HttpKernel ; son intégration ne signifie pas que chaque requête traverse ce contrôleur. Elle construit une réponse d'erreur avec le renderer disponible.

Il produit les pages d'erreur ; en développement, /_error/404 les prévisualise.

Contraste utile : TemplateController et RedirectController viennent de FrameworkBundle ; ErrorController vient du component HttpKernel (cf. HttpKernel component and FrameworkBundle).

🌍 In Real Life

La situation : si l'accueil ne peut fournir la prestation demandée, une procédure prévue prépare un avis explicatif. Cette procédure ne participe pas à chaque service réussi et ne répare pas la cause du problème.

L’équivalent dans Symfony : le chemin d'exception configuré peut déléguer à ErrorController la construction d'une réponse d'erreur avec le renderer disponible. Cette classe appartient à HttpKernel, contrairement aux deux contrôleurs FrameworkBundle précédents.

Retour à la réalité technique : une exception n'est pas encore une Response. Des listeners et l'intégration configurée rendent cette conversion possible ; un chemin différent peut traiter l'erreur. La prévisualisation /_error/404 suppose les routes de prévisualisation chargées, pas seulement la présence de la classe.

🧠 Comment le mémoriser : « Préparer l'avis n'efface pas l'incident. » Image mentale : procédure d'incident rangée à côté du service normal. Question-réflexe : quel composant transforme ici l'exception en réponse, avec quelle intégration ?

⚠️ À ne pas confondre : contrôleur d'erreur, cause de l'exception et passage obligatoire de toute requête.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Conserver la method HTTP change le status code

    Conserver la method HTTP change le status code : 307 si temporaire, 308 si permanente. Pourquoi on se trompe : on retient 301/302 comme « les » codes de redirection.

  • Voir l’explication : Un redirect vers une cible vide renvoie 404 ou 410

    Un redirect vers une cible vide renvoie 404 ou 410, pas une erreur de configuration. Pourquoi on se trompe : une cible vide ressemble à un oubli de configuration, donc à une exception.

  • Voir l’explication : route et path ensemble lèvent une exception

    route et path ensemble lèvent une exception : les modes sont exclusifs, et le code le vérifie. Pourquoi on se trompe : on imagine que l'un prend le pas sur l'autre.

  • Voir l’explication : keepQueryParams n'existe qu'en mode route.

    keepQueryParams n'existe qu'en mode route. En mode path, la query string suit un path, jamais une URL complète. Pourquoi on se trompe : le nom de l'option suggère une portée générale.

  • Voir l’explication : Un maxAge seul rend la Response publique.

    Un maxAge seul rend la Response publique. Il faut private: true pour l'éviter. Pourquoi on se trompe : on pense que « max-age » est neutre côté visibilité.

  • Voir l’explication : Un controller de route n'est pas forcément dans App\.

    Un controller de route n'est pas forcément dans App\. Pourquoi on se trompe : par habitude, on associe « contrôleur » à son propre code.

À mémoriser

🧠 À retenir pour la certification :

Si tu dois retenir seulement 6 choses :

  • TemplateController : template obligatoire ; sans Twig → LogicException.
  • maxAge ou sharedAge sans private → Response publique.
  • RedirectController : route ou path ; les deux, ou aucun → exception.
  • 302 · 301 permanent · 307 / 308 avec keepRequestMethod.
  • Cible vide : 404, ou 410 si permanente.
  • Mode route : URL absolue, parameters transmis ; mode path : query string sur un path seulement.

Moyen mnémotechnique : « 7 garde la method, 8 la garde pour toujours ».
