Objectif

La page /blog/42 fonctionne, mais le même controller reçoit maintenant GET /blog/999. La route existe ; c'est l'article qui manque dans ArticleCatalog. Si BlogController::show lève une NotFoundHttpException, qui transforme cette interruption en Response, et pourquoi une page d'erreur construite avec un code 200 ne doit-elle pas annoncer un succès ?

Nous suivons cette branche du traitement avec Symfony 8.0. Nous distinguerons l'exception PHP, sa traduction HTTP et la fabrication du contenu d'erreur : trois décisions liées, mais pas interchangeables.

Ce cours est la branche d'échec du trajet décrit dans Request handling ; le mécanisme de priorité des listeners et de stopPropagation vient de Event dispatcher et kernel events, et la Request/Response de HttpFoundation.

L'essentiel

À comprendre

À retenir en priorité
  1. Un statut 200 n'est pas conservé automatiquement lors d'une erreur.
  2. allowCustomResponseCode() autorise explicitement ce choix.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un throw PHP interrompt le controller, mais le client HTTP attend une réponse avec un code. Il faut un traducteur : exception → Response.
  • Le piège de fond. Trois choses distinctes : l'exception (objet PHP), son statut HTTP (404, 422, 500…) et le contenu de la page. Le texte « introuvable » ne décide jamais du code.
  • Ce que l'auteur veut que vous compreniez. Le kernel contrôle le code de la Response proposée par un listener, selon un ordre précis ; ce contrôle explique tous les cas d'examen.
  • Pourquoi c'est à l'examen. Les questions portent sur l'ordre de cette règle, HttpExceptionInterface, setThrowable vs setResponse, les quatre callbacks de ErrorListener sur trois events, et le cas terminate.

Lorsqu'une exception échappe au controller et que HttpKernel::handle() la prend en charge, HttpKernel distribue l'event kernel.exception. Un event est ici un objet transmis aux callbacks enregistrés ; un listener est l'un de ces callbacks. Il peut remplacer l'exception courante ou proposer une Response sans reprendre l'action à la ligne qui a échoué.

Ce traitement dépend du contexte : $catch = false désactive cette prise en charge dans handle(), et la gestion des Error PHP dépend aussi de handleAllThrowables. Une erreur survenue avant l'entrée dans ce traitement ou dans une commande CLI n'emprunte pas automatiquement ce trajet HTTP.

Dans l'application configurée, ErrorListener peut construire une page d'erreur par un traitement interne supplémentaire. Ce n'est pas une garantie de HttpKernel utilisé seul : si aucun listener ne fournit de Response, l'exception remonte. Lorsqu'une Response existe, HttpKernel contrôle son code avant de poursuivre le cycle de réponse. C'est cette distinction entre Response proposée et Response contrôlée qui explique les cas d'examen.

exception  ──►  kernel.exception  ──►  un listener fournit-il une Response ?
                                          │ non → l'exception REMONTE
                                          │ oui → le kernel CONTRÔLE son code
                                                   (4xx/5xx/redirect : gardé ;
                                                    sinon exception HTTP : son code ;
                                                    sinon 500)

Le schéma

Où en est-on ? On connaît le trajet global. Le schéma détaille la phase de contrôle du code : c'est elle qui transforme notre 200 fautif en 404. Pourquoi un schéma de décision ? Parce que le kernel applique trois tests dans l'ordre, et l'ordre est la réponse aux questions d'examen.

Pour l'article 999 absent, imaginons qu'un listener construise le bon message mais oublie le code HTTP : new Response('Article introuvable') vaut 200. Le diagramme commence après la distribution de kernel.exception, avec cette Response candidate et l'exception courante :

Bleu : Response candidate ; orange : tests successifs ; vert : code retenu à cette étape. Notre 200 n'est ni autorisé explicitement ni déjà une erreur ou un cas reconnu par isRedirect() : le contrat HTTP de NotFoundHttpException fournit donc 404. Le message peut rester identique, mais le client ne doit plus interpréter la page comme un article trouvé.

La branche 429 montre une autre entrée : une exception qui porte Retry-After. Dans cette branche, HttpKernel ajoute ses headers. Les branches « conserver » n'effectuent pas cet ajout automatiquement : conserver une Response 429 déjà construite ne lui invente pas un Retry-After absent. Enfin, sans Response candidate, on n'entre pas dans ces tests : l'exception remonte après kernel.finish_request. Des listeners de kernel.response pourront encore agir ensuite.

L'exemple : une exception qui porte son statut

Exemple concret

À retenir en priorité
  1. L'attribute associe un status code à cette exception précise.
  2. Ce choix explicite ne signifie pas que tout échec de validation doit produire 422.

Où en est-on ? Du schéma à un cas concret où l'exception porte son statut sans implémenter l'interface HTTP. Pourquoi InvalidQuantity ? Parce qu'elle montre la troisième façon d'obtenir un code : un attribute lu par un listener, sans écrire de listener applicatif.

Le blog possède aussi une entrée HTTP demandant un import d'articles. Une quantité nulle peut être refusée par une règle applicative connue. Nous gardons ce petit laboratoire InvalidQuantity pour distinguer cette erreur attendue d'une panne inattendue ; il ne fait pas partie du GET de lecture.

Dans un fichier PHP chargé par l'application, cette déclaration ajoute des métadonnées à la class :

use Symfony\Component\HttpKernel\Attribute\WithHttpStatus;

#[WithHttpStatus(422)]
final class InvalidQuantity extends \InvalidArgumentException {}
// ErrorListener peut traduire cette exception en erreur HTTP 422.

Entrée du scénario : l'action constate une quantité 0 et lève new InvalidQuantity('La quantité doit être positive.'). Avec ErrorListener enregistré, sa conversion atteinte, aucun mapping prioritaire différent et le rendu d'erreur habituel, le résultat attendu est une Response 422. Ce code exprime ici une instruction comprise mais refusée selon la règle métier ; toute erreur de saisie n'impose pas universellement 422.

L'attribute ne lance pas l'exception, ne vérifie pas la quantité et ne change pas son interface PHP à la déclaration. C'est le listener qui lit #[WithHttpStatus(422)] et remplace l'objet courant par une exception portant le contrat HTTP. Un programme CLI qui utilise la même class ne reçoit pas magiquement une Response. Un listener HTTP plus prioritaire peut également arrêter la propagation avant cette conversion.

Le mécanisme

À retenir en priorité
  1. setThrowable() remplace l'erreur traitée.
  2. setResponse() fournit la Response et arrête la propagation de cet event.

Où en est-on ? On regarde maintenant ce que peut faire un listener de kernel.exception et qui est déjà branché. Pourquoi les deux actions (setThrowable, setResponse) ? Parce que leurs effets sont très différents et que l'examen les oppose.

Pour traduire l'article absent, un listener reçoit un ExceptionEvent qui donne accès à la Request et au throwable courant. Un throwable est un objet PHP qui implémente Throwable, donc notamment une Exception ou une Error. Deux actions différentes sont possibles :

  • setThrowable() remplace l'objet courant. Les listeners suivants peuvent voir ce remplacement ; cela ne fournit aucune Response et n'arrête pas, à lui seul, la propagation.
  • setResponse() fournit une Response et arrête la propagation de cet event. Les callbacks suivants de kernel.exception ne sont plus appelés. Cela n'interrompt pas le callback courant comme le ferait return, n'envoie rien au navigateur et n'annule pas kernel.response.

Si l'application a enregistré ErrorListener, que son callback de rendu est atteint et qu'un controller d'erreur est configuré, il peut prendre le relais. Ses quatre callbacks concernent trois noms d'events, et non quatre events différents :

Event Callback Rôle dans ce trajet
kernel.exception logKernelException, priorité 0 Résout les règles de log et les conversions HTTP, puis sollicite la journalisation
kernel.exception onKernelException, priorité −128 Lance le rendu d'erreur si ses conditions le permettent
kernel.controller_arguments onControllerArguments Peut adapter l'exception fournie au controller à la représentation FlattenException attendue pour le rendu
kernel.response removeCspHeader, priorité −128 Retire le header Content-Security-Policy dans le cas debug marqué par le rendu d'erreur

FlattenException est une représentation des informations d'exception pour le rendu, pas l'article recherché ni un nouvel appel au catalogue. Le dernier callback est conditionnel au debug et au marqueur interne ; ce n'est pas une consigne de retirer la politique de sécurité des pages du blog en production.

Les priorités les plus élevées passent d'abord. Un listener à 100 qui pose une Response peut donc empêcher le callback à 0, y compris sa conversion de InvalidQuantity. À −64, il intervient après ce callback mais avant le rendu à −128, sauf arrêt antérieur. Atteindre le callback de log ne prouve pas qu'un journal externe a effectivement été écrit : cela dépend du logger disponible et de sa configuration.

 priorité   listener                         effet
   100      listener applicatif (exemple)    setResponse() ⇒ arrête les suivants
     0      ErrorListener::logKernelException  conversion HTTP + log
   −64      listener applicatif (exemple)    après la conversion, avant le rendu
  −128      ErrorListener::onKernelException   rendu de la page (sub-Request)
 (plus grand = appelé plus tôt)

🌍 In Real Life

La situation : le responsable reçoit une fiche d'incident ; il peut la corriger ou préparer une réponse au client, deux gestes différents.

L’équivalent dans Symfony : corriger l'incident courant → setThrowable() ; proposer une réponse → setResponse().

Retour à la réalité technique : seul le second arrête la propagation de cet ExceptionEvent. Il ne fait ni return dans le callback ni envoi réseau. Une réponse précoce peut empêcher conversion et rendu intégrés ; sans réponse, le throwable remonte.

Question: Is an exception in the error controller caught through another normal error sub-request?

Answer: No. The error sub-request uses catch=false.

La page d'erreur est une vraie sub-Request

À retenir en priorité
  1. Le controller d'erreur s'exécute dans une sub-Request.
  2. Une nouvelle exception remonte avec l'erreur originale chaînée.

Où en est-on ? On suit la dernière branche : le rendu à −128. Pourquoi parler de « vraie sub-Request » ? Parce que le rendu repasse par le kernel, donc par ses listeners — avec les conséquences que cela a (et un risque d'échec du rendu lui-même).

Revenons à /blog/999 sans listener applicatif qui aurait déjà répondu. onKernelException prépare une copie de la Request avec le controller d'erreur et l'exception dans ses attributes, puis impose la method GET à cette copie. Il appelle handle($request, SUB_REQUEST, false) sur le kernel. Cette sub-Request est un traitement interne : le navigateur n'a pas reçu de redirection et n'a pas émis une seconde Request réseau.

Le controller d'erreur doit produire une Response sans dépendre de l'article qui vient justement de manquer. C'est pourquoi un template d'erreur qui rappellerait obligatoirement le même service défaillant est fragile. On garde un contenu public sobre ; les détails techniques et secrets ne doivent pas être exposés aux visiteurs.

Le dernier argument false empêche le handle() interne de redistribuer automatiquement sa nouvelle erreur dans le même mécanisme. Il serait toutefois inexact de dire qu'aucun catch n'existe : ErrorListener intercepte une nouvelle \Exception, sollicite sa journalisation, rattache l'erreur initiale à sa chaîne previous si elle n'y figure pas déjà, puis la relance. L'initiale n'est donc pas nécessairement le previous immédiat si une chaîne existait. Une \Error, telle qu'une TypeError, n'est pas interceptée par ce catch (\Exception) : ce rattachement n'est pas garanti pour elle.

Enfin, lors de la terminaison, le listener renonce au rendu si son mode debug est désactivé et que l'event indique isKernelTerminating(). C'est le cas de production habituel, mais la condition exacte porte sur le debug, pas sur le seul nom prod. Dans le cycle normal handle → send → terminate, l'envoi a déjà eu lieu : on ne réécrit pas rétroactivement une Response reçue par le client. Cela ne transforme pas terminate en tâche durable ni en confirmation de réception réseau.

 handle()  ──► exception ──► kernel.exception ──► onKernelException (−128)
                                                     │ copie de la Request, GET,
                                                     │ controller d'erreur
                                                     ▼
                                    handle($copie, SUB_REQUEST, catch = false)
                                                     │ échec du rendu ?
                          \Exception : log, chaînage « previous », relancée
                          \Error     : non interceptée par ce catch

🌍 In Real Life

La situation : faute de plat disponible, le restaurant prépare en interne une explication ; le client ne repasse pas lui-même une seconde commande.

L’équivalent dans Symfony : préparation interne → sub-Request de rendu d'erreur ; explication → Response du controller d'erreur.

Retour à la réalité technique : ErrorListener appelle handle(..., SUB_REQUEST, false), sans redirection réseau. Le rendu peut échouer ; son catch d'Exception ne couvre pas toute Error. Après envoi, terminate ne réécrit pas rétroactivement la réponse.

Le choix du status code

Où en est-on ? On revient au schéma de décision pour le dérouler pas à pas. Pourquoi cette section est la plus testée ? Parce que le contrôle est après les listeners : peu importe ce qu'ils ont produit, le kernel re-vérifie.

Que la Response vienne de notre listener ou du rendu intégré, HttpKernel examine l'exception courante après les listeners. Une conversion a pu la remplacer depuis le throw initial. Si l'event autorise un code personnalisé avec allowCustomResponseCode(), le contrôle suivant ne le corrige pas. Sinon, l'ordre est :

  1. Une Response reconnue par isClientError(), isServerError() ou isRedirect() conserve son code.
  2. À défaut, si l'exception courante implémente HttpExceptionInterface, HttpKernel prend son getStatusCode() et ajoute ses getHeaders().
  3. À défaut de ce contrat, il donne à la Response le code 500.

Pour notre article absent, une candidate 200 ou 204 devient donc 404. Avec une exception ordinaire non convertie, elle devient 500. Avec une HttpException portant 429 et Retry-After: 60, une candidate 200 devient 429 avec ce header. Une candidate déjà 403 reste en revanche 403 : la règle ne recopie pas systématiquement le code et les headers de l'exception.

Candidate de départ Exception courante Résultat
200 NotFoundHttpException 404
204 NotFoundHttpException 404
200 exception ordinaire 500
200 HttpException(429) + Retry-After 429 + Retry-After: 60
403 n'importe laquelle 403 (gardé, headers non ajoutés)
201, 301, 302, 303, 307, 308 n'importe laquelle gardé (isRedirect())
304 n'importe laquelle non protégé : corrigé comme 200
n'importe quel code, après allowCustomResponseCode() n'importe laquelle gardé

Nuance de Symfony 8.0 : isRedirect() reconnaît 201, 301, 302, 303, 307 et 308, sans vérifier la présence de Location lorsqu'on l'appelle sans argument. Ce n'est ni « tous les 3xx » ni la définition HTTP de tous les redirects. Une candidate 304 n'est pas protégée par ce test ; une 201 l'est. Il faut suivre le prédicat réellement appelé, pas sa traduction approximative.

Il existe des dérogations légitimes et limitées. Dans une variante où une demande d'import a déjà été acceptée, une exception applicative précise AlreadyAccepted peut être traduite en 202 pour décrire cet état. La fonction suivante suppose son enregistrement comme listener de kernel.exception, par exemple à −64, et suppose que ce fait métier a été établi en amont :

use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Event\ExceptionEvent;

final class AlreadyAccepted extends \RuntimeException {}

function handleAlreadyAccepted(ExceptionEvent $event): void
{
    if (!$event->getThrowable() instanceof AlreadyAccepted) {
        return;
    }

    $event->allowCustomResponseCode();
    $event->setResponse(new Response('', 202));
}

Entrée : un event dont l'exception courante est AlreadyAccepted. Résultat : une Response vide 202 et l'autorisation de conserver ce code à cette étape. Sans l'autorisation, cette exception ordinaire non convertie ferait corriger la candidate en 500. Une autre exception laisse l'event inchangé. Cet extrait ne lance pas l'import, n'enregistre pas lui-même le listener et ne prouve pas que le travail est terminé.

Nous appelons l'autorisation avant setResponse() pour rendre l'intention visible ; setResponse() n'arrête pas l'exécution PHP du callback courant. L'important est que le drapeau soit établi avant le contrôle du kernel. Il ne faut pas généraliser cette dérogation pour masquer toutes les pannes par des 200 ou des 202. Les listeners de kernel.response restent ensuite capables de modifier la Response.

🌍 In Real Life

La situation : une lettre dit « article introuvable », mais porte encore le tampon « succès » ; un contrôle vérifie ce tampon séparément du texte.

L’équivalent dans Symfony : lettre → Response candidate ; tampon → status code ; informations d'incident HTTP → HttpExceptionInterface.

Retour à la réalité technique : le kernel applique les prédicats décrits, puis éventuellement statut et headers de l'exception courante, sinon 500. Un code conservé ne reçoit pas systématiquement ses headers. Le code PHP d'une RuntimeException n'est pas un statut HTTP.

HttpExceptionInterface

À retenir en priorité
  1. Le contrat HttpExceptionInterface porte statut et headers.
  2. WithHttpStatus peut transformer une exception avant cette décision.

Où en est-on ? Dernière brique : le contrat que le kernel teste à l'étape 2. Pourquoi une interface plutôt qu'une classe ? Parce que HttpKernel teste instanceof HttpExceptionInterface — peu importe la hiérarchie PHP de la classe.

Pour séparer la décision HTTP du contenu de la page, ce contrat expose getStatusCode() et getHeaders(). NotFoundHttpException porte 404, AccessDeniedHttpException porte 403, BadRequestHttpException porte 400. HttpException permet de fournir un code et des headers explicitement. Son ancêtre PHP est \RuntimeException, mais c'est bien HttpExceptionInterface que teste HttpKernel.

Voici le laboratoire de lecture du cas 429, avec HttpKernel 8.0 disponible dans l'autoload :

use Symfony\Component\HttpKernel\Exception\HttpException;

$error = new HttpException(429, 'Limite temporaire', null, ['Retry-After' => '60']);
echo $error->getStatusCode(), "\n";
echo $error->getHeaders()['Retry-After'], "\n";

Le résultat est 429, puis 60 sur la ligne suivante. Nous inspectons l'objet sans le lancer ni envoyer une Response. Si la limite d'appels de l'entrée HTTP d'import utilise ce contrat, le délai peut être transmis au client par le traitement approprié ; cet objet ne compte pas les appels et ne fait attendre aucun processus par lui-même.

À l'inverse, new \RuntimeException('Introuvable', 404) possède un code PHP accessible par getCode(), pas ce contrat de status code HTTP. Le nombre 404 ne suffit donc pas à traduire automatiquement l'exception en 404.

Une traduction peut aussi être configurée sans modifier la class d'exception. Dans framework.exceptions, status_code définit le code HTTP associé, log_level le niveau de journalisation et log_channel son canal. Le niveau qualifie le message à journaliser ; le canal permet d'orienter cette journalisation. Aucun de ces réglages ne constitue un template d'erreur.

Dans logKernelException, un mapping applicable avec un status_code effectif peut convertir l'exception en une HttpException. Un mapping qui ne règle que le log n'impose pas de code HTTP. À défaut de contrat HTTP déjà présent, #[WithHttpStatus] peut fournir cette conversion ; une conversion HTTP par la configuration passe avant cette lecture de l'attribute. Il faut que le callback soit atteint : une Response posée avant lui peut empêcher la conversion. Ce mécanisme évite d'écrire un listener applicatif pour chaque exception, sans rendre les métadonnées actives toutes seules.

Source du statut Où se décide-t-il ? Précédence
framework.exceptions (status_code) logKernelException 1re
#[WithHttpStatus] sur la class logKernelException 2e
HttpExceptionInterface déjà implémentée étape 2 du contrôle du kernel —
rien de tout cela étape 3 : 500 —

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un contenu d'erreur et un code d'erreur sont deux choix.

    Un contenu d'erreur et un code d'erreur sont deux choix. Le texte « article introuvable » n'est pas analysé pour décider du code. Pour /blog/999, la candidate 200 devient 404 grâce à l'exception courante, sauf dérogation. Une Response déjà protégée par les tests du kernel garde son propre code ; ses headers manquants ne sont pas automatiquement complétés par cette branche. Pourquoi on se trompe : on lit la page, on voit « introuvable », on suppose que le client verra 404.

  • Voir l’explication : L'ancêtre RuntimeException ne décide pas du résultat HTTP.

    L'ancêtre RuntimeException ne décide pas du résultat HTTP. HttpException en hérite mais implémente le contrat HTTP. Une exception ordinaire portant le code PHP 404 ne le fait pas. Cherchons l'interface ou la conversion réellement effectuée, pas seulement le nom de la class mère. Pourquoi on se trompe : getCode() renvoie 404, ce qui ressemble à un statut.

  • Voir l’explication : Une priorité élevée peut empêcher plus que le rendu intégré.

    Une priorité élevée peut empêcher plus que le rendu intégré. À 100, poser une Response arrête aussi le callback à 0 s'il n'a pas encore été atteint ; à −64, ce callback est déjà passé sauf arrêt antérieur. Cela concerne la conversion et la sollicitation du log. Ni ce constat ni la présence d'un fichier de configuration ne prouvent une écriture externe. Le cycle ultérieur de la Response, lui, n'est pas supprimé.

  • Voir l’explication : Une annotation ne suffit pas si personne ne la lit.

    Une annotation ne suffit pas si personne ne la lit. InvalidQuantity n'implémente pas directement HttpExceptionInterface, mais le listener peut la convertir en 422. À l'inverse, sans ce callback atteint, il ne faut pas attribuer ce résultat à l'attribute seul. Une entrée de configuration sans code HTTP effectif peut ne régler que la journalisation.

  • Voir l’explication : Le rendu d'erreur peut lui-même échouer.

    Le rendu d'erreur peut lui-même échouer. La sub-Request utilise $catch = false pour ne pas repartir automatiquement dans le même traitement. Le listener peut rattacher l'originale à la chaîne d'une nouvelle Exception puis la relancer ; il ne garantit pas cette opération pour toute Error. « Pas de nouvelle page produite » ne signifie donc ni « aucune interception » ni « aucune trace technique disponible ».

Application

À retenir en priorité
  1. Un statut 200 n'est pas conservé automatiquement lors d'une erreur.
  2. allowCustomResponseCode() autorise explicitement ce choix.
  3. Le contrat HttpExceptionInterface porte statut et headers.
  4. WithHttpStatus peut transformer une exception avant cette décision.

À mémoriser

🧠 À retenir pour la certification :

Pour expliquer l'échec de lecture de l'article 999, suivons sept repères :

  1. L'exception prise en charge par HttpKernel arrive dans kernel.exception ; sans Response à l'issue de cet event, elle remonte.
  2. setThrowable() remplace l'objet courant ; setResponse() arrête la propagation de cet event, pas le cycle complet ni le callback en cours.
  3. Sans dérogation, le kernel conserve les codes reconnus par ses tests d'erreur ou isRedirect() ; sinon il utilise le contrat HTTP courant, ou 500 en son absence.
  4. Les headers de l'exception sont ajoutés dans la branche qui applique ce contrat, pas dans toutes les branches qui conservent une Response.
  5. allowCustomResponseCode() autorise une politique explicite ; il ne doit pas transformer une panne inconnue en faux succès.
  6. La conversion par configuration ou WithHttpStatus dépend du callback à 0 ; le rendu intégré à −128 est distinct. Quatre callbacks concernent trois noms d'events.
  7. Le rendu utilise une sub-Request interne avec $catch = false. L'échec de ce rendu remonte ; hors debug, la terminaison ne déclenche pas ce rendu par ErrorListener.

« Logguer tôt, répondre tard » résume les priorités intégrées, sans garantir qu'un callback non atteint journalise quoi que ce soit. Pour choisir correctement où ajouter notre propre listener, il reste à comprendre l'ordre général des events du kernel.

Phrase de mémorisation : « Le kernel relit le tampon : 4xx, 5xx ou redirection gardés, sinon le code de HttpExceptionInterface, sinon 500 — et le rendu d'erreur est une sub-Request à −128. »
