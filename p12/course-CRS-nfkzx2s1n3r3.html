Objectif

Après avoir lu /blog/42, le visiteur ouvre /inscription. Cette nouvelle action construit un formulaire lié à SignupData ; le GET l'affiche, le POST peut le soumettre. Le contrôleur existe déjà dans le trajet HTTP : Form intervient parce qu'il est appelé ici, pas parce que tout GET exige une validation.

Traiter une submission dans le bon ordre, savoir ce que handleRequest() décide à ta place, et ce que submit($data, false) valide vraiment.

Question centrale : quand la même URL sert à afficher et à traiter un formulaire, comment Symfony sait-il dans quel cas on est, et que garantit chaque appel ?

L'essentiel

À comprendre

À retenir en priorité
  1. Une action peut afficher et traiter le form.
  2. Après succès, un redirect sépare traitement et affichage.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une même action reçoit deux sortes de requêtes : celle qui demande le formulaire (GET) et celle qui le remplit (POST). Il faut un mécanisme qui les distingue sans if à la main.
  • Le piège de fond. On confond trois états : soumis, valide, enregistré. Form ne gère que les deux premiers, et même isValid() ne fait que consulter un résultat déjà calculé.
  • Ce que l'auteur veut que vous compreniez. handleRequest() décide pour vous si le form est destiné à cette Request ; ensuite le garde isSubmitted() && isValid() sépare succès et réaffichage.
  • Pourquoi c'est à l'examen. Questions classiques : exception de isValid() avant soumission, objet déjà modifié, AlreadySubmittedException, statut 422, clearMissing.

Une seule action affiche et traite le form : handleRequest() soumet le form seulement si la Request lui est destinée, puis le garde isSubmitted() && isValid() décide entre le redirect et le rendu. Après une submission, les champs mappés et synchronisés ont déjà pu modifier l'objet : isValid() ne déclenche pas cette écriture et ne l'annule pas en cas d'erreur. submit($data, false) garde les fields absents, sans les dispenser des constraints de la class.

Le schéma

À retenir en priorité
  1. isSubmitted() ne signifie pas valide.
  2. isValid() sur un form non soumis lève une LogicException.

Où en est-on ? Début du cours. On voit la carte complète du traitement ; les sections suivantes zooment sur : (1) le pattern, (2) la décision de handleRequest(), (3) l'ordre des tests, (4) l'objet déjà modifié, (5) submit() manuel, (6) clearMissing.

GET  /inscription ──► handleRequest() : rien à soumettre ──► render() 200
POST /inscription ──► handleRequest() : submit(données)
                         ├─ valide   ──► traitement métier ──► redirect
                         └─ invalide ──► render() avec erreurs (422)

Le dessin suivant détaille les décisions du handler et du contrôleur.

Bleu = opérations, losanges ambre = décisions, sorties arrondies = réponses. La redirection est le choix du contrôleur après le traitement métier, pas un effet automatique de isValid(). Ne persister les données qu'après le succès du garde. Le dessin ne couvre pas les formulaires sans nom ni un dépassement de post_max_size.

L'exemple : une `Task`

Exemple concret

À retenir en priorité
  1. Tester d'abord si la Request a réellement soumis le form.
  2. isValid() vient ensuite ; le garde court-circuité évite l'appel prématuré.

Où en est-on ? Avant de détailler, on lit le code complet minimal : c'est lui que toutes les sections suivantes expliquent ligne par ligne.

L'exemple historique Task garde le même mécanisme que l'inscription : un objet initial, un type de formulaire, une Request et deux issues. L'absence de code d'enregistrement est volontaire : handleRequest() peut modifier l'objet mais ne sauvegarde rien. La redirection reste une décision de l'action après succès.

#[Route('/task/new', name: 'task_new')]
public function new(Request $request): Response
{
    $task = new Task();                          // #[Assert\NotBlank] sur $title
    $form = $this->createForm(TaskType::class, $task);
    $form->handleRequest($request);

    if ($form->isSubmitted() && $form->isValid()) {
        // $task contient déjà les valeurs saisies
        return $this->redirectToRoute('task_success');
    }

    return $this->render('task/new.html.twig', ['form' => $form]);
}

Ce que fait chaque ligne :

Ligne Rôle
new Task() l'objet qui recevra les valeurs
createForm(...) construit un nouveau Form lié à cet objet
handleRequest($request) soumet si la Request est destinée à ce form
isSubmitted() && isValid() garde : succès seulement si soumis puis sans erreur
redirectToRoute() décision de l'action après succès
render(..., ['form' => $form]) réaffichage (GET, ou POST invalide)

Le pattern recommandé

Où en est-on ? Étape 1 sur 6. Pourquoi ce code tient-il en une action ? Parce que handleRequest() rend le premier passage (GET) et le second (POST) indiscernables pour le contrôleur.

Au premier GET de /inscription, le formulaire configuré pour POST reste non soumis. Au POST suivant, un nouvel objet Form traite les données de cette nouvelle Request. Le garde sépare ces deux passages ; il ne fait pas de isValid() le déclencheur du mapping ou de la validation intégrée. Avec l'extension Validator, le listener de POST_SUBMIT de la racine a déjà lancé la validation au cours de la soumission.

handleRequest() est ce qui permet à une seule action de servir l'affichage et le traitement : sans submission pour ce form, il ne fait rien, et le code tombe sur le render(). Le redirect après succès évite qu'un rafraîchissement renvoie le POST.

Pourquoi un nouvel objet Form à chaque requête ? Parce que PHP ne garde rien entre deux requêtes HTTP : le Form du GET n'existe plus au POST. Ce qui relie les deux passages, c'est le HTML envoyé au navigateur, pas un objet.

Pourquoi redirect après un POST réussi ? Si on rendait directement la page de confirmation, un rafraîchissement du navigateur renverrait le POST (et refrapperait la logique métier). La redirection fait finir sur un GET.

🌍 In Real Life

La situation : au bureau d'inscription, on vient d'abord chercher un dossier, puis déposer les réponses. Après acceptation, on reçoit une indication pour consulter la confirmation, pas l'ordre de déposer encore le dossier.

L’équivalent dans Symfony : le GET affiche le formulaire POST non soumis ; le POST suivant construit un nouveau Form et traite les données. Le garde sépare l'affichage du succès ; la redirection choisie par le contrôleur conduit à la page de confirmation.

Retour à la réalité technique : l'action peut gérer les deux requêtes, mais pas avec un unique objet Form conservé entre elles. Avec l'intégration Validator, la validation intervient pendant la soumission ; isValid() en consulte le résultat. La redirection n'enregistre rien elle-même.

🧠 Comment le mémoriser : « Retirer, déposer, consulter : trois passages distincts. » Image mentale : dossier vierge, dossier rempli, reçu. Question-réflexe : suis-je en affichage initial, en traitement ou après succès ?

⚠️ À ne pas confondre : redirection après POST et garantie contre toute double opération métier.

Quand `handleRequest()` soumet-il ?

À retenir en priorité
  1. handleRequest() ignore une method différente.
  2. Le nom du form détermine aussi les données recherchées.

Où en est-on ? Étape 2 sur 6. On ouvre la boîte handleRequest(). Question « Pourquoi ? » : pourquoi un POST sur l'action ne suffit-il pas à soumettre le formulaire ? Parce que plusieurs formulaires peuvent coexister sur la page.

Recevoir un POST sur l'action ne suffit pas : plusieurs formulaires peuvent coexister, et le handler doit reconnaître celui auquel les données sont destinées. Si notre formulaire s'appelle signup, il cherche les données sous ce nom. La méthode HTTP de la route et l'option method du formulaire sont deux configurations distinctes.

HttpFoundationRequestHandler (8.0) teste, dans l'ordre :

  1. La method de la Request = l'option method du form (POST par défaut).
  2. Le nom du form : lu dans la query string pour GET, HEAD et TRACE, dans le body et les files sinon.
  3. Puis submit($data, 'PATCH' !== $method).
Request ──► méthode == option method du form ? ── non ──► rien (non soumis)
               │ oui
               ▼
   GET/HEAD/TRACE : cherche dans $request->query
   autre          : cherche dans $request->request + $request->files
               │
        données sous le NOM du form ? ── non ──► rien (non soumis)
               │ oui
               ▼
   submit($data, clearMissing = ('PATCH' !== méthode))

Deux exceptions à la règle simplifiée du nom : un formulaire sans nom lit les données à la racine et exige au moins un champ connu ; un dépassement de post_max_size entraîne une soumission sans effacer les valeurs, puis une erreur de taille. Le handler standard ne décode pas arbitrairement un corps JSON : pour ce cas, choisir explicitement les données de getPayload() et les transmettre à submit().

Situation isSubmitted()
form POST, Request GET portant ses fields false
form 'method' => 'GET', ?task_form[title]=x true
form POST, Request POST sans key task_form false
form 'method' => 'PATCH', Request PATCH partielle true, absents conservés

Pourquoi la première ligne est plausible à tort : une Request GET qui porte les champs dans l'URL ressemble à un envoi, mais le form est configuré pour POST : le handler s'arrête dès le premier test.

Comparaison de deux « méthodes » à ne pas mélanger :

Méthode de la route Option method du form
Où ? #[Route(methods: [...])] createForm(..., ['method' => 'GET'])
Rôle quelles requêtes atteignent l'action quelle requête soumet ce form
Défaut toutes POST

🌍 In Real Life

La situation : le bureau reçoit des enveloppes de plusieurs services. Il vérifie le canal de dépôt et l'étiquette du dossier avant de traiter son contenu ; une enveloppe reçue n'est pas nécessairement destinée à l'inscription.

L’équivalent dans Symfony : le canal représente l'option method du Form ; l'étiquette, son nom dans les données de la Request. Le handler standard vérifie ces éléments avant d'appeler submit() dans le cas nommé courant.

Retour à la réalité technique : les données viennent de la query pour GET, HEAD et TRACE, sinon des paramètres du corps et des fichiers. Les formulaires sans nom et les dépassements de taille ont les règles particulières décrites ci-dessus. Un corps JSON demande un décodage et un choix explicites de données.

🧠 Comment le mémoriser : « Bonne méthode, bon dossier. » Image mentale : deux contrôles sur l'enveloppe. Question-réflexe : quelle condition manque pour que ce Form soit effectivement soumis ?

⚠️ À ne pas confondre : méthodes autorisées par la route et méthode configurée du formulaire.

L'ordre des deux tests

Où en est-on ? Étape 3 sur 6. Le handler a (ou non) soumis. Pourquoi le garde s'écrit-il toujours isSubmitted() && isValid() et jamais l'inverse ?

L'affichage initial est une situation normale, pas un formulaire invalide. Le court-circuit de && évite donc l'appel interdit à isValid(). Après soumission, isSubmitted() prouve seulement que le traitement a eu lieu ; les erreurs de transformation, de validation ou ajoutées au formulaire déterminent encore si l'action peut accepter l'inscription.

isValid() sur un form non soumis lève une LogicException : « Cannot check if an unsubmitted form is valid… ». isSubmitted() vaut true même si les données sont invalides ; isValid() compte aussi les erreurs des fields enfants.

              isSubmitted()      isValid()
GET initial       false      →  (jamais appelé grâce à &&)
POST valide       true       →  true   → succès
POST invalide     true       →  false  → réaffichage avec erreurs
isValid() seul sur un GET : LogicException

Pourquoi lever une exception plutôt que rendre false ? Parce que « pas encore soumis » n'est pas « invalide » : retourner false masquerait une erreur de logique du développeur.

🌍 In Real Life

La situation : on ne demande pas le verdict d'un dossier jamais déposé. Un dossier déposé peut, en revanche, revenir avec plusieurs demandes de correction.

L’équivalent dans Symfony : isSubmitted() vérifie le dépôt ; isValid() vérifie l'absence d'erreurs pertinentes du formulaire et de ses enfants. Le && court-circuite le second appel lorsque le premier vaut false.

Retour à la réalité technique : appeler isValid() avant la soumission lève une LogicException. La soumission n'implique pas la validité ; des erreurs de transformation, de contraintes ou ajoutées au Form peuvent empêcher le succès. Ce garde ne crée pas à lui seul une politique d'autorisation.

🧠 Comment le mémoriser : « Déposé avant jugé ; déposé ne veut pas dire accepté. » Image mentale : une case « reçu », puis une case « sans erreurs ». Question-réflexe : ai-je vérifié l'état de soumission avant de demander le verdict ?

⚠️ À ne pas confondre : état soumis, validité des données et droit d'effectuer l'action.

Le guichet distingue « le document a-t-il été remis ? » de « a-t-il passé les contrôles ? ». isSubmitted() et isValid() posent ces deux questions dans cet ordre, même lorsqu'une submission est invalide.

Repère de l’exemple :

Question: Why must isSubmitted() be checked before isValid() in the form action?

Answer: Calling isValid() on an unsubmitted form raises a LogicException.

Tester d'abord si la Request a réellement soumis le form. isValid() vient ensuite ; le garde court-circuité évite l'appel prématuré.

L'object est déjà à jour

À retenir en priorité
  1. La submission met à jour le modèle mappé.
  2. Ne pas soumettre le même form une deuxième fois.

Où en est-on ? Étape 4 sur 6. Le garde vient de dire « invalide ». Question : l'objet $task contient-il encore ses anciennes valeurs ? Non, et c'est un point d'examen.

Si l'adresse e-mail soumise n'est pas acceptable, SignupData peut déjà contenir cette saisie. Le contrôleur ne doit donc pas prendre « objet modifié » pour « inscription autorisée ». Lire les erreurs, réafficher le formulaire et réserver les effets métier au succès garde une frontière claire entre mapping, validation et enregistrement.

  • Dans cet exemple avec mapping standard, l'objet est modifié en place : $form->getData() === $task. Une transformation impossible ou un champ non mappé ne suit pas ce chemin ; d'autres configurations peuvent remplacer l'objet. Form n'enregistre rien en base de données.
  • Un form ne se soumet qu'une fois : un second submit() lève une AlreadySubmittedException, « A form can only be submitted once. ».
  • AbstractController::render() passe la Response en 422 pour un form soumis et invalide passé comme paramètre direct, si son statut est encore 200, et convertit le form en vue sans createView(). renderView() rend une string : pas de 422.

Chronologie de la soumission d'un champ mappé (cas simple) :

submit(données)
   │ 1. conversion (reverseTransform)      ← erreur = non synchronisé
   │ 2. écriture dans l'objet (mapping)    ← l'objet est modifié ICI
   │ 3. validation (listener POST_SUBMIT)  ← erreurs enregistrées sur le form
   ▼
isValid() : consulte les erreurs, n'écrit rien, n'annule rien

Comparaison de deux rendus :

render() renderView()
Retourne une Response une string
Form soumis et invalide passé directement statut 422 (si encore 200) pas de 422
Form converti en vue automatiquement ? oui (render() convertit le form en vue) rend seulement une string

🌍 In Real Life

La situation : l'agent recopie les réponses dans le dossier de travail avant que le contrôle relève une adresse incorrecte. Le refus ne fait pas disparaître l'écriture et ne signifie pas que le dossier a été archivé.

L’équivalent dans Symfony : le mapping peut modifier SignupData pendant la soumission, avant le verdict consulté avec isValid(). Réafficher les erreurs conserve une trace de la saisie ; l'enregistrement métier reste une opération séparée.

Retour à la réalité technique : les champs mappés et synchronisés suivent ce chemin ; une transformation impossible ou une autre configuration peut produire un résultat différent. Form ne sauvegarde pas en base et n'annule pas les mutations invalides. Une même instance ne peut pas être soumise deux fois.

🧠 Comment le mémoriser : « Recopié n'est ni approuvé ni archivé. » Image mentale : un brouillon annoté en rouge devant une armoire fermée. Question-réflexe : quel effet a déjà eu lieu, et lequel dois-je réserver au succès ?

⚠️ À ne pas confondre : objet modifié, objet valide et objet persisté. Le 422 éventuel du rendu signale une réponse, pas un rollback.

`submit()`, pour le contrôle fin

À retenir en priorité
  1. clearMissing vaut true par défaut.
  2. Le false correspond au traitement partiel.

Où en est-on ? Étape 5 sur 6. Jusqu'ici handleRequest() décidait seul. Question : que faire quand on ne veut pas son comportement (par exemple un client JSON) ? On appelle submit() soi-même.

Si le client d'inscription envoie du JSON, choisis explicitement le sous-tableau destiné au formulaire. Le code suivant suppose que le payload contient un tableau sous son nom ; il ne remplace pas le choix du format attendu ni la gestion d'une erreur de décodage. Il ne faut pas le cumuler avec un handleRequest() qui a déjà soumis ce même Form.

if ($request->isMethod('POST')) {
    $form->submit($request->getPayload()->all($form->getName()));
}
  • L'exemple de forms.rst écrit getPayload()->get(…) : pour un form composé, la valeur est un array, et InputBag::get() lève une BadRequestException. Il faut all().
  • $clearMissing vaut true par défaut : un field absent devient null ; false le garde — le choix de handleRequest() pour un form PATCH.

Pourquoi get() échoue-t-il ? Dans HttpFoundation, InputBag::get() n'accepte que des scalaires ; un formulaire composé est un tableau de champs, d'où BadRequestException. all('nom') rend le sous-tableau tel quel.

Comparaison :

handleRequest($request) submit($data)
Qui décide si soumettre ? le handler (méthode + nom) vous
Où lit-il les données ? query / body / files ce que vous passez
JSON non décodé vous choisissez getPayload()->all(nom)
clearMissing false seulement si PATCH true par défaut, réglable

🌍 In Real Life

La situation : une inscription arrive dans une enveloppe numérique plutôt que sur le formulaire papier habituel. L'agent ouvre l'enveloppe, sélectionne le bon dossier, puis le confie au circuit de traitement une seule fois.

L’équivalent dans Symfony : getPayload() donne accès aux données du corps ; all($form->getName()) récupère le sous-tableau attendu ; submit() le transmet au Form. Le développeur assume alors le choix de méthode, de structure et de politique pour les champs absents.

Retour à la réalité technique : submit() ne décode pas lui-même le JSON. Une erreur de décodage ou une structure incorrecte doit être traitée ; get() ne convient pas à un tableau. Ne pas resoumettre une instance déjà traitée par handleRequest().

🧠 Comment le mémoriser : « Ouvrir, choisir, soumettre une fois. » Image mentale : une enveloppe contenant plusieurs dossiers, dont un seul entre au guichet. Question-réflexe : ai-je sélectionné le tableau et son mode de mise à jour ?

⚠️ À ne pas confondre : décodage du payload, soumission Form et validation des contraintes ; une API peut aussi choisir un autre circuit sans Form.

`clearMissing` et la validation

À retenir en priorité
  1. Distinguer constraints du field et du modèle.
  2. Préserver une valeur ne la dispense pas de validation d'object.

Où en est-on ? Étape 6 sur 6, la dernière. Question : quand certains champs ne sont pas envoyés (PATCH), que deviennent-ils, et sont-ils validés ?

Pour modifier seulement le surnom d'un inscrit, le PATCH doit conserver son adresse e-mail absente de la saisie. Cela explique clearMissing=false, mais ne rend pas l'objet stocké valide par définition : la validation de l'objet peut encore examiner son adresse existante. Le tableau sépare la contrainte attachée au champ non soumis et celle attachée à l'objet.

La documentation (« Constraints At Field Level ») dit qu'avec false, seules les constraints des fields soumis sont évaluées. Le code 8.0 nuance :

Constraint de email, absent de submit(['nick' => 'z'], false) Résultat
option constraints du field sautée
attribute sur User::$email, valeur stockée invalide invalide : l'object entier est validé

Pour forcer la validation d'un field absent : ajouter sa key à null avant de soumettre — null remplace alors la valeur stockée.

Avant / après pour submit(['nick' => 'z'], false) :

clearMissing = true  (défaut)           clearMissing = false
  nick  ← "z"                             nick  ← "z"
  email ← null (absent = effacé)          email = valeur stockée conservée

Pourquoi deux niveaux de contraintes ? L'option constraints d'un champ est attachée au champ Form (donc sautée s'il n'est pas soumis). Un attribut #[Assert\Email] sur la propriété appartient à l'objet, qui est validé en entier : sa valeur stockée est donc contrôlée même si le champ est absent.

🌍 In Real Life

La situation : un inscrit demande seulement de changer son surnom. Le bureau garde l'adresse déjà au dossier ; cela ne prouve pas qu'elle respecte encore les règles du dossier complet.

L’équivalent dans Symfony : avec submit($data, false), les enfants absents ne sont pas soumis et leurs valeurs sont conservées. Le contrôle local d'un champ non soumis est distinct de la validation de l'objet associé, qui peut encore révéler une adresse invalide.

Retour à la réalité technique : clearMissing gouverne le traitement des absents, pas une dispense générale de contraintes. Les contraintes de l'objet applicables aux groupes actifs restent pertinentes. Une clé présente avec null est une soumission explicite, non une absence ; transformations et empty_data peuvent influer sur la valeur finale.

🧠 Comment le mémoriser : « Conserver n'est pas certifier. » Image mentale : une ancienne adresse gardée, mais entourée en rouge. Question-réflexe : l'erreur vient-elle du champ soumis ou des contraintes de l'objet ?

⚠️ À ne pas confondre : clé absente et valeur null ; contraintes du champ Form et métadonnées Validator de l'objet.

Pièges d'examen

Piège à éviter

  • Voir l’explication : isValid() sur un form non soumis lève une exception.

    isValid() sur un form non soumis lève une exception. Le garde isSubmitted() && isValid() n'est pas facultatif. Pourquoi on se trompe : on s'attend à un simple false, comme pour « pas valide ».

  • Voir l’explication : Une Request d'une autre method que celle du form est ignorée.

    Une Request d'une autre method que celle du form est ignorée. Pourquoi on se trompe : les champs sont bien présents dans l'URL, donc on croit qu'ils suffisent.

  • Voir l’explication : Après une submission valide, l'object est déjà à jour.

    Après une submission valide, l'object est déjà à jour. Pourquoi on se trompe : on imagine qu'un « enregistrement » est nécessaire pour que l'objet change ; seul l'enregistrement en base est séparé.

  • Voir l’explication : La submission manuelle vide les fields absents par défaut

    La submission manuelle vide les fields absents par défaut ; false les préserve. Pourquoi on se trompe : on suppose que « absent » signifie « inchangé ».

  • Voir l’explication : false ne dispense pas un field absent des constraints de la class

    false ne dispense pas un field absent des constraints de la class : il est validé avec sa valeur stockée ; seule l'option constraints du field est sautée. Pourquoi on se trompe : la documentation dit « seules les contraintes des champs soumis », ce qui ne vaut que pour l'option du champ.

  • Voir l’explication : getPayload()->get() refuse un form composé

    getPayload()->get() refuse un form composé : la valeur est un array, il faut all(). Pourquoi on se trompe : get() est la méthode habituelle pour lire un paramètre.

  • Voir l’explication : Un form ne se soumet qu'une fois.

    Un form ne se soumet qu'une fois. Un second submit() (après un handleRequest() qui a déjà soumis) lève AlreadySubmittedException.

  • Voir l’explication : Le 422 vient de render()

    Le 422 vient de render(), pas de renderView(), et seulement si le form est passé directement dans les paramètres.

Application

À retenir en priorité
  1. handleRequest() ignore une method différente.
  2. Le nom du form détermine aussi les données recherchées.
  3. isSubmitted() ne signifie pas valide.
  4. isValid() sur un form non soumis lève une LogicException.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Une action : handleRequest(), garde, redirect, render().
  • Cas courant nommé : method = option method et nom du form présent ; voir les exceptions du handler.
  • isSubmitted() avant isValid(), sinon LogicException.
  • L'object est modifié en place ; un form ne se soumet qu'une fois.
  • render() : 422 pour un form soumis et invalide passé comme objet, si la réponse est encore à 200.
  • submit($data, false) garde les absents ; PATCH le fait seul.
  • false saute l'option constraints, pas les constraints de la class.

Moyen mnémotechnique : « Method, nom, submission ; soumis, puis valide ».

Phrase de mémorisation : « Le handler vérifie la méthode et le nom, soumet une seule fois, l'objet change avant le verdict, et on ne demande jamais isValid() avant isSubmitted(). »
