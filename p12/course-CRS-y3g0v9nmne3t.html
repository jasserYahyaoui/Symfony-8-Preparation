Objectif

L'accès à l'écran d'édition est permis à un rédacteur, mais cela ne dit pas encore quel article il peut modifier. Nous allons transmettre le sujet à une politique métier, puis comprendre pourquoi plusieurs voters peuvent produire une décision différente avec exactement les mêmes avis.

Question du cours : comment écrit-on une règle « l'auteur peut modifier son article », et comment plusieurs règles sont-elles combinées en une décision ?

L'essentiel

À comprendre

À retenir en priorité
  1. Un voter peut ne pas être compétent.
  2. L'abstention n'est pas un refus individuel.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un rôle dit ce qu'on est. Il ne dit jamais « sur cet objet ». Pour cela, il faut un voter.
  • Le piège de fond. Croire qu'un voter ne peut que refuser ou accorder. Il a trois réponses ; l'abstention est la réponse normale hors domaine.
  • Ce que l'auteur veut que vous compreniez. supports() trie, voteOnAttribute() tranche, la strategy agrège : mêmes votes, décision possiblement différente.
  • Pourquoi c'est à l'examen. Signature 8.0 avec ?Vote $vote, quatre stratégies, allow_if_all_abstain, NullToken, isGrantedForUser().

Un role dit ce qu'un user est ; un voter décide sur un object — « l'auteur peut modifier son article ». Chaque voter accorde, refuse ou s'abstient, et une strategy agrège les votes : à votes identiques, elle change la décision.

Les voters ne sont pas réservés aux objets métier : les rôles et les états d'authentification ont aussi les leurs. Un voter d'articles doit délimiter son domaine pour ne pas refuser arbitrairement ces autres questions.

        question : (attribute, sujet)
                    │
   ┌────────────────┼────────────────┐
   ▼                ▼                ▼
 RoleVoter   AuthenticatedVoter   PostVoter ...  chacun : GRANTED/DENIED/ABSTAIN
   └────────────────┼────────────────┘
                    ▼
              strategy (agrège)  ─►  accordé / refusé

Le schéma

À retenir en priorité
  1. Le voter délimite son domain.
  2. La strategy décide à partir des votes.

Où en est-on ? Carte du cours : la boucle interne d'un voter. Plus loin, la boucle du manager, qui agrège plusieurs voters.

Il existe deux boucles : les attributs examinés par un voter, puis les votes demandés par le manager. La première explique le retour local ; la seconde applique la stratégie. Ce ne sont pas deux votes identiques.

Bleu : état local ; ambre : tests ; vert : retour. Cette boucle est celle d'un voter, pas celle du manager qui agrège plusieurs voters. Elle explique pourquoi une abstention n'est pas un refus et pourquoi un attribut supporté mais refusé change le résultat par défaut.

Les deux methods, en 8.0

À retenir en priorité
  1. La signature a évolué en 8.0.
  2. Vote permet notamment d'ajouter une raison.

Où en est-on ? Étape 1 sur 5 : écrire un voter. On y repère les deux méthodes : supports() (le tri) et voteOnAttribute() (la décision).

L'exemple d'auteur utilise un modèle d'édition Post avec getAuthor(), distinct du contrat de lecture ArticleView (id, titre, contenu). Post et User sont des classes applicatives à fournir/importer : aucun ORM ni résolution automatique d'entité n'est supposé. Si le contrôleur transmet ArticleView, ce voter s'abstient ; adapter alors explicitement le type et fournir une politique par identifiant, ou charger le modèle d'édition requis. Ne pas inventer un auteur dans la vue.

use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Authorization\Voter\Vote;
use Symfony\Component\Security\Core\Authorization\Voter\Voter;

class PostVoter extends Voter
{
    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, ['POST_EDIT', 'POST_VIEW'], true) && $subject instanceof Post;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token, ?Vote $vote = null): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }
        if ('POST_EDIT' === $attribute && $subject->getAuthor() !== $user) {
            $vote?->addReason('Only the author may edit this post.');

            return false;
        }

        return true;
    }
}

Avec ce modèle, Alice peut voir un Post ; elle ne peut le modifier que si getAuthor() retourne la même instance qu'elle. Pour un modèle rechargeant des objets distincts, comparer des identifiants métier stables plutôt que l'identité PHP. Le service doit être découvert et autoconfiguré ; Post, User, Voter, TokenInterface et Vote doivent être importés.

  • supports() à false : le voter s'abstient, il ne refuse pas.
  • voteOnAttribute() rend un bool : accordé ou refusé.
  • Le quatrième parameter, ?Vote $vote = null, est obligatoire dans la signature en 8.0 : l'ancienne signature à trois parameters est une erreur fatale (« must be compatible with Voter::voteOnAttribute(…) »).
  • Vote::addReason() explique un refus : « Access Denied. Only the author may edit this post. ».
  • Le service doit être enregistré. L'autoconfiguration habituelle fournit son tag security.voter ; sans elle, le déclarer explicitement. L'autowiring raccorde ses éventuelles dépendances ; le pass de compilation assemble les voters. Leur consultation pendant la requête ne refait pas ce montage.

Avec un Post d'édition représentant 42, Alice authentifiée obtient POST_VIEW. POST_EDIT est accordé seulement si l'auteur est cette même instance ; Bob obtient un refus. Un visiteur anonyme est refusé par ce voter, même pour POST_VIEW : cette politique d'édition ne remplace pas implicitement la lecture publique /blog/42. Une faute POST_EDTI produit une abstention, pas le refus explicite de la branche auteur.

Appel supports() Vote du PostVoter
POST_EDIT sur le Post 42, Alice auteure oui accordé
POST_EDIT sur le Post 42, Bob oui refusé (raison ajoutée)
POST_VIEW sur le Post 42, Bob oui accordé
POST_EDTI (faute de frappe) non abstention
POST_EDIT sur un ArticleView non abstention

Trois valeurs, pas deux

À retenir en priorité
  1. Le voter ne prend pas position.
  2. Un autre voter peut traiter l'attribute.

Où en est-on ? Étape 2 sur 5 : les trois réponses possibles. Question : quelle différence concrète entre refuser et s'abstenir ?

🌍 In Real Life

La situation : le comité du blog peut répondre « oui », « non » ou « ce dossier n'est pas de mon ressort ». Le troisième avis n'est pas un veto.

L’équivalent dans Symfony : accord → ACCESS_GRANTED ; refus → ACCESS_DENIED ; hors compétence → ACCESS_ABSTAIN, notamment lorsque supports() ne reconnaît pas le couple attribut/sujet.

Retour à la réalité technique : pour refuser une action reconnue, le voter doit la supporter puis voter négativement. Se retirer laisse les autres voters se prononcer ; le résultat final dépend de la stratégie.

🧠 Comment le mémoriser : « Hors sujet n'est pas contre. » Image mentale : trois bulletins oui/non/hors compétence. Question-réflexe : ai-je exprimé un refus ou retiré mon voter de la décision utile ?

⚠️ À ne pas confondre : supports() et voteOnAttribute().

ACCESS_GRANTED (1), ACCESS_ABSTAIN (0), ACCESS_DENIED (-1). L'abstention est le cas normal : chaque voter ne se prononce que sur son domain.

Pour interdire une action reconnue, supports() doit donc rendre true, puis voteOnAttribute() rendre false. Retourner false dans supports() retire simplement ce voter de la décision utile : un autre peut encore accorder.

 supports() = false  ──►  ABSTAIN (0)    « pas mon domaine »
 supports() = true, voteOnAttribute() = false ──►  DENIED (-1)  « je refuse »
 supports() = true, voteOnAttribute() = true  ──►  GRANTED (1)

Pourquoi ne pas simplement refuser quand ce n'est pas son domaine ? Parce que d'autres voters (rôles, authentification) répondent à d'autres questions. Un voter qui refuserait tout ce qu'il ne connaît pas bloquerait leurs accords.

Les quatre strategies

À retenir en priorité
  1. Les mêmes votes peuvent produire des décisions différentes.
  2. priority dépend de l'ordre des voters.

Où en est-on ? Étape 3 sur 5 : l'agrégation. Question : avec les mêmes votes, comment le règlement change-t-il la décision ?

🌍 In Real Life

La situation : le comité du blog applique un règlement avant d'interroger ses membres. Le même ensemble d'avis peut conduire à des résultats différents selon ce règlement.

L’équivalent dans Symfony : un accord suffit → affirmative ; compter accords/refus → consensus ; un refus oppose un veto → unanimous ; premier avis non abstenu dans l'ordre de priorité → priority.

Retour à la réalité technique : les consultations sont séquentielles et peuvent s'arrêter tôt. L'abstention n'est pas un accord ; les égalités et l'abstention générale ont des options dédiées, avec refus par défaut si tous s'abstiennent.

🧠 Comment le mémoriser : « Lire le règlement avant les bulletins. » Image mentale : règlement posé au-dessus de l'urne. Question-réflexe : quel avis peut arrêter cette consultation ?

⚠️ À ne pas confondre : unanimité des votes exprimés et obligation que tous les voters accordent.

Le tableau suppose les votes dans l'ordre indiqué et les options par défaut. Voici la configuration P10 qui exprime un veto dès qu'un voter refuse :

security:
    access_decision_manager:
        strategy: unanimous
        allow_if_all_abstain: false

Avec accord puis refus, elle refuse ; avec deux abstentions, elle refuse aussi. C'est la politique choisie, pas un « meilleur » réglage universel.

security.access_decision_manager.strategy : affirmative (défaut), consensus, unanimous, priority ; une strategy maison passe par strategy_service (pas avec strategy). Les voters sont interrogés un par un :

Votes affirmative consensus unanimous priority
accordé, refusé accordé accordé refusé accordé
refusé, accordé accordé accordé refusé refusé
accordé, refusé, refusé accordé refusé refusé accordé
  • affirmative accorde au premier accord ; unanimous refuse au premier refus ; priority suit le premier voter qui ne s'abstient pas, dans l'ordre des voters triés par priorité de tag, les plus fortes d'abord ; consensus consomme tous les votes des voters retenus.
 affirmative : un ACCORD suffit            (stop au 1er accord)
 unanimous   : un REFUS suffit             (stop au 1er refus)
 priority    : le 1er qui ne s'abstient pas décide
 consensus   : majorité sur tous les votes (égalité : option dédiée)

Pourquoi la ligne « refusé, accordé » diffère-t-elle ? Parce que priority s'arrête au premier vote non abstenu : ici un refus. En affirmative, ce refus est dépassé par l'accord suivant.

AccessDecisionManager produit ces votes progressivement par un générateur. Les pré-filtres de support peuvent exclure des services avant leur vote : « tous » ne signifie pas systématiquement chaque service enregistré. Si un voter lève une exception, le manager ne la transforme pas en abstention et ne collecte pas automatiquement les autres erreurs comme certains parcours Messenger. Un effet métier ou un journal indispensable ne doit pas dépendre de l'exécution de tous les voters.

Les deux cas limites

À retenir en priorité
  1. Deux cas limites ont des réglages distincts.
  2. Ne pas assimiler égalité et absence de vote.

Où en est-on ? Étape 4 sur 5 : les situations où la règle ne tranche pas d'elle-même. Question : que décide-t-on à égalité, ou quand personne ne vote ?

  • Égalité en consensus : allow_if_equal_granted_denied, défaut true.
  • Tous abstenus : allow_if_all_abstain, défaut false — refusé, y compris en unanimous. Avec true, un attribute mal orthographié est accordé.

Zéro accord et zéro refus n'est pas l'égalité ordinaire du consensus : c'est l'abstention générale, avec son propre réglage. Garder le refus par défaut et corriger le nom ou l'enregistrement du voter au lieu d'ouvrir l'accès pour faire disparaître le symptôme.

 1 accord + 1 refus (consensus)  ─► allow_if_equal_granted_denied  (défaut true)
 0 accord + 0 refus (tous ABSTAIN) ─► allow_if_all_abstain          (défaut false)

Ce que le voter reçoit vraiment

À retenir en priorité
  1. Le voter ne doit pas supposer un user.
  2. Le subject et l'identité se vérifient séparément.

Où en est-on ? Étape 5 sur 5 : le contexte du vote. Question : quel token le voter reçoit-il, et que ne doit-il pas mettre en cache ?

🌍 In Real Life

La situation : pendant l'import du blog, le responsable examine une demande au nom d'Alice. Il doit lire le dossier transmis, pas substituer l'identité de la personne assise au bureau.

L’équivalent dans Symfony : identité du dossier → token reçu par le voter ; personne du contexte ambiant → utilisateur éventuellement lu ailleurs ; compétence connue du spécialiste → support d'attribut/type mis en cache.

Retour à la réalité technique : une décision imbriquée doit conserver le token reçu. Le cache de compétence du voter ne mémorise pas le droit d'Alice sur l'article 42 ; une règle dépendant de l'auteur courant ne doit pas y être figée.

🧠 Comment le mémoriser : « Juger le dossier transmis. » Image mentale : nom d'Alice sur le dossier, distinct du nom sur le bureau. Question-réflexe : quel token et quel sujet ma décision utilise-t-elle réellement ?

⚠️ À ne pas confondre : cache du support du voter et cache d'une décision d'autorisation.

Le token fourni fait foi pour cette décision, notamment dans app:blog:import lorsqu'une politique est évaluée pour un utilisateur explicitement désigné. Ce n'est pas forcément le visiteur d'une requête HTTP :

  • Un anonyme passe aussi par les voters, avec un NullToken : $token->getUser() vaut null.
  • isGranted($attribute, $subject, $accessDecision) remplit un AccessDecision : getMessage(), strategy.
  • Security::isGrantedForUser($user, …) décide pour un autre user (command, notification) ; un attribute d'état de connexion y lève InvalidArgumentException.
  • Dans un voter, vérifier un role par AccessDecisionManagerInterface::decide(), sur le token reçu, pas par Security::isGranted().
  • supportsAttribute() et supportsType() (CacheableVoterInterface) excluent un voter d'avance ; leur résultat est mis en cache, pas la décision d'accès au Post. Ne pas y placer une règle dépendant de l'auteur courant.

Dans un vote imbriqué, demander un rôle avec le token reçu évite de relire un autre contexte implicite. Ne pas redemander le même droit métier au même manager depuis sa propre décision : on créerait une récursion. Les raisons enregistrées dans Vote et AccessDecision servent au diagnostic ; ne pas les exposer sans examen si elles révèlent des données privées.

Pourquoi isGrantedForUser() refuse-t-il IS_AUTHENTICATED_* ? Parce que le token utilisé est « hors connexion » (offline) : il représente un user, pas une authentification réelle, donc l'état de connexion n'a pas de sens.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Aucun refus ne suffit pas sans vote favorable.
  2. Le cas tout-abstention utilise son réglage.
Voir l’explication : abstention
  • supports() à false = abstention, pas refus. Pourquoi on se trompe : « ne supporte pas » ressemble à « n'accepte pas ».
  • L'ancienne signature de voteOnAttribute() est une erreur fatale en 8.0. Pourquoi on se trompe : le paramètre ?Vote est optionnel à l'appel, mais obligatoire dans la signature de la classe fille.
  • Le défaut est affirmative : un seul accord suffit, même si un autre refuse. Pourquoi on se trompe : on imagine un défaut prudent comme unanimous.
  • unanimous = « aucun refus et au moins un accord » ; si tous s'abstiennent, allow_if_all_abstain décide, et refuse par défaut. Pourquoi on se trompe : « unanimité » est lue comme « tous les voters accordent ».
  • Certaines stratégies s'arrêtent tôt ; consensus consulte les voters retenus par le filtrage de support, sauf interruption par une erreur. Pourquoi on se trompe : on croit que tous les voters sont toujours appelés.
  • priority dépend de l'ordre des voters. Pourquoi on se trompe : le mot « priority » est pris pour une priorité de rôle.

🧠 À retenir pour la certification :

  • supports() trie (faux = abstention), voteOnAttribute() tranche.
  • Signature 8.0 : ?Vote $vote = null obligatoire ; addReason().
  • Votes : 1, 0, -1.
  • affirmative (défaut) : un accord suffit ; unanimous : un refus suffit ; priority : le premier qui vote ; consensus : la majorité.
  • Tous abstenus : refusé (allow_if_all_abstain: false).
  • Un anonyme vote aussi : NullToken.
  • isGrantedForUser() pour un autre user, sans attribute d'état.

Moyen mnémotechnique : « supports trie, voteOnAttribute tranche, la strategy agrège ».

supports (faux = abstain) → voteOnAttribute(…, ?Vote) →
GRANTED/ABSTAIN/DENIED ; affirmative | consensus (égalité = accordé) |
unanimous | priority (ordre) ; tous abstenus = refusé
