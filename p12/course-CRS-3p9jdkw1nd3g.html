Objectif

L'import peut lire ses options et séparer données et diagnostics. Il reste à expliquer ce qu'il fait pendant un traitement long : attendre une confirmation, afficher les étapes réellement accomplies, puis présenter un bilan. Les helpers de Console évitent de réécrire ces interactions, sans prendre la responsabilité du traitement des articles.

L'essentiel

À comprendre

À retenir en priorité
  1. SymfonyStyle fournit une interface cohérente.
  2. Il enveloppe les helpers courants.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Poser une question, afficher une barre ou un tableau sont des besoins répétitifs ; réécrire fgets(STDIN) et des echo produit des commandes fragiles et intestables.
  • Le piège de fond. Un helper affiche et interagit : il ne traite rien, ne consent pas à votre place et ne prouve aucun avancement.
  • Ce que l'auteur veut que vous compreniez. Sans interaction (-n, cron), la question n'est pas posée : c'est son défaut qui décide.
  • Pourquoi c'est à l'examen. Défauts des questions, regex /^y/i, MissingInputException, total facultatif de ProgressBar, getHelper() réservé à Command.

Un helper réalise une tâche de présentation ou d'interaction : poser une question, compter les lignes traitées ou afficher un tableau. SymfonyStyle regroupe les usages courants avec une présentation cohérente ; il ne réalise pas l'import ou le traitement métier à votre place.

Pour automatiser une commande, choisir explicitement ses valeurs par défaut. En mode non interactif, une question n'attend pas l'opérateur : son défaut est utilisé. Un défaut false pour confirmer un import évite de le lancer silencieusement depuis un cron.

Il faut distinguer deux situations : une question effectivement appelée avec une entrée non interactive utilise son repli ; une méthode interact() sautée n'appelle même pas la question. Dans les deux cas, le code métier doit posséder toutes les valeurs nécessaires avant de commencer.

┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│ Interaction       │   │ Progression       │   │ Présentation      │
│ QuestionHelper    │   │ ProgressBar       │   │ Table, Formatter  │
│ (défaut si -n)    │   │ ProgressIndicator │   │ Tree, Cursor      │
└───────────────────┘   └───────────────────┘   └───────────────────┘
         SymfonyStyle les regroupe ; le métier reste ailleurs

Le schéma

À retenir en priorité
  1. Compter et attendre sont deux besoins.
  2. Choisir l'outil selon la progression observable.

Où en est-on ? Nous avons posé le « pourquoi ». Le schéma suivant suit le chemin d'une confirmation : c'est le mécanisme le plus testé, car il décide si l'import démarre.

La décision d'importer précède la progression. Ce schéma part d'un appel à confirm() atteint dans les deux modes, avec refus par défaut ; il ne suppose pas que cet appel se trouve dans une méthode interact() qui serait sautée :

Bleu : opérations du helper ; losanges ambre : conditions ; vert : résultat pour la commande. Ce parcours suppose une réponse valide. Une fin d'entrée sans valeur exploitable peut lever une exception, comme détaillé plus bas.

L'exemple : confirmer avant d'importer

Exemple concret

À retenir en priorité
  1. Le défaut doit protéger l'action destructive.
  2. Une saisie vide peut accepter le défaut.

Où en est-on ? Un exemple concret qui enchaîne les trois familles : question, progression, tableau. Retenez surtout ce que -n provoque.

Extrait du corps d'une commande, avec Command et SymfonyStyle importés depuis Console, $input et $output reçus, et $rows chargé par le service d'import. Ici le fichier contient 42 lignes ; ce total ne désigne pas l'identifiant de l'article consulté par GET /blog/42.

$io = new SymfonyStyle($input, $output);
if (!$io->confirm('Importer 42 lignes ?', false)) {
    return Command::SUCCESS;
}
$io->progressStart(42);
foreach ($rows as $row) {
    // …
    $io->progressAdvance();
}
$io->progressFinish();
$io->table(['ID', 'Nom'], $summary);

Cet extrait suppose 42 éléments dans $rows, un traitement métier à la place du commentaire et un tableau $summary construit par ce traitement. Avec -n, la confirmation vaut false : aucune ligne n'est importée et la commande retourne un succès sans lancer la barre. Avec confirmation positive, chaque progressAdvance() doit correspondre à une ligne réellement traitée.

php bin/console app:import f.csv        → « Importer 42 lignes ? [no] »
php bin/console app:import f.csv -n     → pas de question, défaut false,
                                          aucun import, code 0

Le code 0 du refus signifie ici « annulation gérée normalement », pas « 42 articles importés ». Pour un automate exigeant un import effectif, définir un contrat différent et explicite plutôt que déduire le travail accompli d'une barre ou du seul mot SUCCESS.

Si une opération lève, laisser remonter l'échec ou le traiter clairement. Ne pas appeler systématiquement progressFinish() dans un finally comme s'il prouvait que les lignes restantes avaient été traitées.

Le catalogue

À retenir en priorité
  1. L'invocable n'hérite pas des methods de Command.
  2. Les helpers restent utilisables.

Où en est-on ? Avant de détailler questions et progression, une carte : quel helper pour quel besoin. Le mécanisme de choix est simple — on part du besoin, pas du nom de la classe.

Le catalogue documenté en 8.0 couvre neuf outils ou familles de helpers. Les reconnaître par le besoin évite de choisir une barre pour une tâche qui n'a aucune unité mesurable :

Besoin dans l'outil d'import Helper
demander une valeur, confirmer ou choisir QuestionHelper
compter les lignes traitées ProgressBar
signaler une attente sans quantité mesurable ProgressIndicator
présenter un bilan en colonnes Table
représenter une hiérarchie outils Tree
construire des blocs formatés FormatterHelper
lancer un process et afficher son déroulement ProcessHelper
présenter ses diagnostics d'exécution DebugFormatterHelper
déplacer le curseur du terminal Cursor
  • Une command qui étend Command y accède par $this->getHelper('question').
  • Une command invocable ordinaire qui n'étend pas Command n'a pas getHelper() : new QuestionHelper(), ou SymfonyStyle — la règle : SymfonyStyle d'abord.

getHelper('question') consulte un HelperSet disponible sur la commande : ce n'est pas une fabrique universelle de tous les éléments du tableau. Table et ProgressBar se construisent aussi directement avec leur sortie. Le helper de process n'est pas Messenger et ne rend pas l'import automatiquement asynchrone.

Command ──getHelper('question')──▶ HelperSet ──▶ QuestionHelper
invocable seule : pas de getHelper() → SymfonyStyle (ou new QuestionHelper())

Les questions

À retenir en priorité
  1. Le mode non interactif ne pose pas de question.
  2. Prévoir une valeur exploitable.

Où en est-on ? Premier helper en détail. Mécanisme : un objet Question décrit l'invite et son défaut ; seul le helper la pose, et il consulte d'abord le mode interactif.

🌍 In Real Life

La situation : le secrétariat du blog prépare une question de confirmation et une consigne de repli quand personne ne répond.

L’équivalent dans Symfony : fiche de question → objet Question ; personne qui la pose → helper ; consigne de repli → valeur par défaut.

Retour à la réalité technique : construire la question ne lit rien. Le helper tient compte du mode interactif et de la normalisation prévue ; sans interaction, il n'obtient pas un consentement humain.

🧠 Comment le mémoriser : « Préparer n'est pas demander. » Image mentale : une question écrite mais non prononcée. Question-réflexe : quelle valeur sera utilisée avec -n ?

⚠️ À ne pas confondre : réponse saisie et défaut utilisé par automatisation.

Une question décrit une invite et son défaut ; elle ne lit rien tant qu'un helper ne la pose. Ces trois expressions supposent les imports de Question, ConfirmationQuestion et ChoiceQuestion depuis Symfony\Component\Console\Question :

new Question('Nom du projet ?', 'defaut');
new ConfirmationQuestion('Continuer ?', false);
new ChoiceQuestion('Environnement ?', ['dev', 'prod'], 0);

Le tableau décrit leur usage avec le helper standard, sans remplacement du normalizer, de la regex de confirmation ou ajout d'un validateur personnalisé :

Situation Résultat
ConfirmationQuestion('?', false), saisie yeti ou Yes true : toute saisie commençant par y
ConfirmationQuestion('?'), saisie vide true : le défaut omis vaut true
non interactive, ChoiceQuestion(…, ['dev', 'prod'], 0) 'dev' — la valeur, pas l'index
non interactive, Question('?') sans défaut null
interactive, sans défaut, fin de l'entrée MissingInputException : « Aborted. »

La confirmation utilise par défaut la regex /^y/i : yeti commence par y, donc confirme. Le libellé français ne traduit pas automatiquement cette règle en reconnaissance de « oui ». Le défaut false protège l'absence de réponse, pas une saisie non vide reconnue positive.

La dernière ligne correspond notamment à un cron dont l'entrée reste interactive et atteint sa fin sans réponse ni repli exploitable. L'absence de terminal ne fixe pas à elle seule ce mode. Prévoir des valeurs explicites pour l'automatisation ; si une question est dans interact(), prévoir aussi que cette méthode puisse être sautée.

Un choix qui rend 'prod' ne reconfigure pas un kernel déjà démarré. Ici c'est une valeur de réponse : sélectionner l'environnement de la commande reste le rôle de l'entry point et de ses options.

Question posée ?
  ├─ entrée interactive, saisie        → la saisie (normalisée)
  ├─ entrée interactive, saisie vide   → le défaut
  ├─ entrée interactive, fin d'entrée  → MissingInputException
  └─ non interactive (-n)              → le défaut (ou null), sans poser

La progression

À retenir en priorité
  1. Le total est facultatif.
  2. Sans total il n'y a pas de pourcentage fiable.
  3. La fréquence règle le redraw du terminal.
  4. Le compteur et le travail métier restent inchangés.

Où en est-on ? Deuxième helper. Question guide : que mesure exactement la barre ? Le helper n'affiche que ce que le code lui annonce.

🌍 In Real Life

La situation : l'équipe compte les enveloppes d'import déposées, tandis qu'une autre équipe traite encore leur contenu.

L’équivalent dans Symfony : unité comptée → appel à advance() ; total connu → maximum de la barre ; simple activité → ProgressIndicator.

Retour à la réalité technique : le helper affiche ce que le programme lui annonce. Compter les dispatchs vers un transport différé ne mesure pas les handlers achevés ; finish() ne termine aucun travail métier.

🧠 Comment le mémoriser : « Une barre mesure son unité. » Image mentale : deux compteurs, déposés et traités. Question-réflexe : quel fait exact fait avancer la barre ?

⚠️ À ne pas confondre : animation d'attente et pourcentage de travail terminé.

Après confirmation, choisir ce que le compteur mesure : une ligne traitée, un fichier terminé ou un envoi accepté. Pour un ImportBlogFile routé vers un transport asynchrone, compter les dispatchs ne mesure pas l'avancement du worker. Le libellé doit nommer l'étape réellement observée.

  • ProgressBar($output, 100) : start(), advance(), finish(). Le total est facultatif : sans lui, la barre passe en mode throbber, un compteur sans pourcentage (0 [>---…] au lieu de 0/3 [>---…] 0%) ; setMaxSteps() le corrige en route.
  • ProgressIndicator n'a pas de compteur : il anime une attente — une réponse réseau — sans unité de progression.
Besoin Outil Affichage
total connu ProgressBar($output, 3) 0/3 [>---] 0%
total inconnu, on compte ProgressBar($output) 0 [>---] (throbber)
rien à compter, on attend ProgressIndicator animation seule

Cette fonction reçoit des opérations applicatives et ne fait avancer la barre qu'après leur retour normal :

<?php
use Symfony\Component\Console\Helper\ProgressBar;
use Symfony\Component\Console\Output\OutputInterface;

/** @param list<callable(): void> $steps */
function runSteps(OutputInterface $output, array $steps): void
{
    $bar = new ProgressBar($output, count($steps));
    $bar->start();
    foreach ($steps as $step) {
        $step();
        $bar->advance();
    }
    $bar->finish();
}

Avec trois opérations qui reviennent normalement, trois étapes sont comptées. Si la deuxième lève, la première a déjà eu ses effets ; aucun rollback n'est fourni par la barre et finish() n'est pas atteint. La représentation exacte dépend du terminal, de la décoration et de la verbosity, pas seulement du compteur.

Pour de nombreuses opérations rapides, setRedrawFrequency(100) règle le redessin, pas le traitement : toutes les étapes continuent d'être comptées. Les intervalles temporels de redessin participent aussi à la décision d'afficher ; ne pas promettre exactement une écriture toutes les cent lignes. Le gain recherché est de réduire les écritures terminal, sans inventer un résultat de benchmark.

$io->progressIterate($rows) fournit un iterable à parcourir avec foreach. L'obtenir sans l'itérer ne réalise ni l'import ni la progression. Le corps de la boucle reste responsable du travail métier.

Une ProgressBar peut compter chaque étape sans redessiner à chaque étape : setRedrawFrequency() réduit les écritures au terminal. Cela ne saute pas le travail métier et ne modifie pas le nombre d'étapes ; c'est un réglage de présentation utile pour de nombreuses opérations rapides.

Le helper Table

À retenir en priorité
  1. Le helper Table structure l'output.
  2. Il évite un alignement manuel fragile.

Où en est-on ? Dernier helper de l'exemple : le bilan. Mécanisme simple : setHeaders() et setRows() préparent, render() écrit.

Après le traitement, présentons deux auteurs dans le bilan. L'extrait suppose Symfony\Component\Console\Helper\Table importé et un $output disponible :

(new Table($output))
    ->setHeaders(['ID', 'Nom'])
    ->setRows([[1, 'Alice'], [2, 'Bob']])
    ->render();

$io->table(['ID', 'Nom'], $rows) fait la même chose par SymfonyStyle.

Les appels setHeaders() et setRows() préparent le tableau ; render() l'écrit. Les données affichées sont exactement celles fournies, ici les couples 1/Alice et 2/Bob : le helper ne consulte ni ArticleCatalog ni un stockage d'utilisateurs. Ce tableau est destiné à la lecture humaine ; pour un export machine, conserver le format de données séparé du diagnostic comme dans le cours précédent.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une entrée vide n'est pas un mode non interactif.
  2. Les scripts doivent utiliser -n et des valeurs explicites.
  • Voir l’explication : Sans interaction, le helper ne lit pas de réponse humaine

    Sans interaction, le helper ne lit pas de réponse humaine : il utilise son défaut selon le type de question. Un validateur personnalisé appliqué à ce défaut peut encore échouer ; ce mode n'est pas une garantie de succès. Pourquoi on se trompe : on croit que -n répond « oui » pour nous.

  • Voir l’explication : ConfirmationQuestion vaut true par défaut

    ConfirmationQuestion vaut true par défaut si le second argument est omis. Pourquoi on se trompe : le réflexe prudent serait false.

  • Voir l’explication : ProgressBar n'exige pas de total

    ProgressBar n'exige pas de total : sans lui, elle compte sans pourcentage. ProgressIndicator sert quand il n'y a rien à compter. Pourquoi on se trompe : une « barre » évoque un pourcentage obligatoire.

  • Voir l’explication : Une question sans défaut, en interactif, sur une entrée vide

    Une question sans défaut, en interactif, sur une entrée vide lève MissingInputException. Pourquoi on se trompe : on attend null, valeur du cas non interactif.

  • Voir l’explication : getHelper() vient de Command

    getHelper() vient de Command — indisponible dans une command invocable qui ne l'étend pas.

  • Voir l’explication : Une animation n'est pas une preuve d'avancement.

    Une animation n'est pas une preuve d'avancement. Ne pas afficher un pourcentage pendant une attente dont aucun total n'est connu ; ne pas confondre envoi du message et fin de son traitement.

Fiche express

À mémoriser

À retenir en priorité
  1. L'index sert à la sélection.
  2. Le résultat est la valeur du choix.

Le terminal présente maintenant des faits : choix effectivement obtenu, étapes réellement comptées, bilan explicitement fourni. Aucun helper ne crée un consentement, un import ou une transaction par sa seule présence.

🧠 À retenir pour la certification — si tu dois retenir seulement 6 choses :

  • Neuf helpers, à connaître par leur usage.
  • Trois questions : Question, ConfirmationQuestion (défaut true, tout y… = oui), ChoiceQuestion (rend la valeur).
  • Non interactive : default value, ou null, sans rien demander.
  • Interactive sans défaut sur une entrée vide : MissingInputException.
  • ProgressBar : total facultatif ; ProgressIndicator : rien à compter.
  • SymfonyStyle d'abord ; getHelper() seulement si la class étend Command.

Moyen mnémotechnique : « Demander, compter, afficher — SymfonyStyle d'abord ». Phrase de mémorisation : « Un helper affiche et demande ; sans humain, c'est le défaut qui répond, et la barre ne mesure que ce qu'on lui annonce. »

Pour observer le début, l'erreur et la fin de la commande plutôt que ses seules lignes de sortie, poursuivre avec Console events.
