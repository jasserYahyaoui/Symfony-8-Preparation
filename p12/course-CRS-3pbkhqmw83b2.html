Objectif

Le journal du bus montre les passages de ImportBlogFile, mais l'équipe veut surtout être alertée lorsqu'aucun retry n'est prévu. Observer chaque dispatch ne répond pas à cette question : il faut écouter le bon moment du cycle du worker. Ce cours relie les événements à l'envoi, à la réception et à la décision d'échec, sans les confondre avec les événements HTTP de GET /blog/42.

Question centrale : à quel moment précis du cycle d'envoi et du worker dois-je me brancher pour observer (ou influencer) ce qui m'intéresse ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le worker n'existe pas dans ce trajet.
  2. Le middleware couvre chaque dispatch.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un middleware voit chaque dispatch, mais pas les moments propres au worker (réception, échec, retry, arrêt). Les events couvrent ces instants.
  • Le piège de fond. Les events n'existent pas pour tout message : un dispatch synchrone non routé n'en émet aucun côté transport/worker.
  • Ce que l'auteur veut que vous compreniez. Le catalogue, ce qu'un listener peut changer, et surtout l'ordre des priorités autour de willRetry().
  • Pourquoi c'est à l'examen. Nombre d'events émis, priorité 100 du retry, shouldHandle(false), WorkerRunningEvent à vide.

Un event est un object émis à un point précis du traitement ; un listener est le service appelé pour y réagir. Ici, ces points appartiennent à l'envoi vers un transport et au cycle du worker. Ils n'existent pas tous pour chaque message : un dispatch initial synchrone non routé n'entame aucun cycle worker.

Un listener peut observer l'exception et la décision de retry, mais cette décision est elle-même prise par un autre listener. L'ordre devient donc important. Certains événements permettent aussi de modifier l'Envelope ou de refuser son traitement : « listener » n'est pas synonyme d'observateur incapable de changer le trajet.

Le schéma

À retenir en priorité
  1. Les events ont des points d'émission précis.
  2. Ils ne remplacent pas tous les middleware.

Où en est-on ? Étape 1/5 : le cycle d'un message dans le worker, puis un zoom sur la diffusion de l'échec. Ensuite : exemple, event ou middleware, catalogue, ce qu'un listener peut changer, les deux events clés.

Events Messenger
   ├─ Envoi    → SendMessageToTransports, MessageSentToTransports
   ├─ Worker   → Started, Running, Stopped
   └─ Message  → Received, Handled | Failed, Retried

L'import est routé puis consommé avec max_retries: 1. Son handler ordinaire échoue. La première vue montre un passage de consommation, pas une liste d'événements que tout message déclencherait obligatoirement :

Bleu : appel/notification ; losange ambre : décision ; vert : résultat observable. Vue d'un message, hors batch handlers et listeners qui lèvent eux-mêmes une exception. Le dispatcher doit être présent. Le démarrage et l'arrêt du worker ne sont pas des conséquences directes de l'envoi : un worker peut déjà tourner.

Handled est émis avant l'appel d'acquittement au receiver. Il décrit le chemin de traitement considéré comme réussi par le worker, pas la preuve que cet acquittement est déjà terminé ni que chaque règle métier attendue a réellement été exécutée dans une pile personnalisée.

Où en est-on ? Étape 1/5 (zoom) : l'ordre à l'intérieur de la diffusion de Failed, qui explique pourquoi la priorité compte.

Pour comprendre l'alerte, zoomons maintenant à l'intérieur de la diffusion de Failed. Une notification Retried peut survenir avant que tous les listeners de Failed aient été appelés :

Pourquoi ce zoom ? Les listeners d'un même event s'exécutent par priorité décroissante : 100 (retry), puis 0 (votre code), puis -100 (failure transport). Savoir qui passe avant vous détermine ce que vous lisez.

Exemple concret

Où en est-on ? Étape 2/5 : le listener d'alerte, en quelques lignes.

Extrait à placer dans une classe enregistrée comme service et autoconfigurée, avec alerting injecté. Les classes à importer sont Symfony\Component\EventDispatcher\Attribute\AsEventListener et Symfony\Component\Messenger\Event\WorkerMessageFailedEvent. Ce fragment de méthode n'est pas un programme autonome :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[AsEventListener]
public function onFailed(WorkerMessageFailedEvent $event): void
{
    if (!$event->willRetry()) {      // juste à la priority par défaut, 0
        $this->alerting->notify($event->getThrowable());
    }
}

Avec les listeners standards et un envoi de retry réussi, le premier échec ordinaire de l'import peut donner willRetry() === true à priorité 0 : pas d'alerte dans ce fragment. Au prochain échec, budget épuisé, willRetry() vaut false : notify() est appelé.

Le contenu de l'alerte doit dire « aucun retry prévu », pas nécessairement « import perdu ». Un failure transport peut encore recevoir le message. Un service d'alerte qui lève peut lui-même perturber le traitement de l'échec ; prévoir ce cas plutôt que considérer la journalisation comme infaillible.

Event ou middleware

À retenir en priorité
  1. Les events de worker couvrent seulement leur contexte.
  2. Le bus est la frontière commune.

Où en est-on ? Étape 3/5 : quel mécanisme choisir ? Question directrice : à quelle frontière est-il atteint ?

🌍 In Real Life

La situation : le secrétariat du blog distingue le contrôle de chaque dossier et l'annonce « nouvelle tentative prévue ».

L’équivalent dans Symfony : poste du circuit → middleware du bus ; annonce à un instant précis → événement ; collègue inscrit pour réagir → listener.

Retour à la réalité technique : un middleware doit être atteint sur le bus concerné. Les événements du worker exigent ce cycle et un dispatcher. Un subscriber est un objet qui déclare ses abonnements et exécute ses méthodes, pas seulement une liste de configuration.

🧠 Comment le mémoriser : « Un poste ou un moment ? » Image mentale : un bureau à côté d'un haut-parleur. Question-réflexe : quelle frontière dois-je observer ?

⚠️ À ne pas confondre : EventDispatcher et bus Messenger.

Pour enrichir toutes les demandes d'import, y compris celles exécutées directement par une command, le bus est la frontière commune. Pour observer un retry, c'est le cycle worker. La distinction n'est donc pas « observer contre modifier », mais où le mécanisme est atteint.

  • Un dispatch() entre dans sa chaîne de middleware, message synchrone compris. Un middleware particulier doit être installé sur le bus concerné et ne pas être court-circuité avant son tour.
  • Les events ne sont émis qu'à l'envoi vers un transport et dans un worker : SendMessageToTransportsEvent exige des senders.

Pour couvrir les dispatchs directs et différés, choisir un middleware placé au bon endroit sur les bus utilisés. Pour une étape d'envoi ou de worker, choisir le listener correspondant. Un sender sync:// peut produire des événements d'envoi sans pour autant créer un worker.

Besoin Outil Pourquoi
Agir sur tout dispatch, sync compris middleware chaîne atteinte à chaque dispatch()
Alerter sur l'absence de retry listener de Failed moment propre au worker
Enrichir avant l'envoi listener SendMessageToTransportsEvent seulement si des senders
Mesurer la boucle du worker WorkerRunningEvent tours avec message et à vide

Le catalogue

À retenir en priorité
  1. Une loop vide émet toujours l'event.
  2. Éviter un traitement coûteux à chaque notification.

Où en est-on ? Étape 4/5 : la liste des events, regroupée par besoin.

Regroupons le catalogue documenté en trois besoins : savoir si l'envoi est terminé, suivre le process, puis suivre chaque travail reçu. La documentation 8.0 présente les dix événements suivants ; leur émission suppose un dispatcher présent et un parcours qui atteint le point indiqué :

Event Quand
SendMessageToTransportsEvent avant l'envoi vers les transports
MessageSentToTransportsEvent après le retour des envois sélectionnés, sans exception interrompant cette étape
WorkerStartedEvent le worker démarre
WorkerRunningEvent après chaque Envelope prise en charge par la boucle, et sur les tours à vide
WorkerMessageReceivedEvent un message vient d'être récupéré
WorkerMessageHandledEvent chemin de succès du worker, avant acquittement
WorkerMessageFailedEvent échec capturé lors du dispatch de réception
WorkerMessageRetriedEvent le message est remis en file pour un retry
WorkerRateLimitedEvent le worker est ralenti par un limiteur de débit
WorkerStoppedEvent le worker s'arrête
  • Le code 8.0 en contient un onzième, WorkerMessageSkipEvent, émis par messenger:failed:retry quand on choisit de ne pas rejouer un message.
  • Un envoi vers deux transports donne un seul MessageSentToTransportsEvent après la boucle d'envoi réussie, pas un par sender. Si le second sender lève, le premier a pu recevoir le message sans que cet événement final soit émis. Aucune atomicité entre destinations ne découle du nombre d'événements.
Envoi    : SendMessageToTransports  →  (senders)  →  MessageSentToTransports
Process  : WorkerStarted  ...  WorkerRunning (aussi à vide)  ...  WorkerStopped
Message  : WorkerMessageReceived → Handled | Failed → (Retried) ; RateLimited

Ce qu'un listener peut changer

À retenir en priorité
  1. Le listener peut interrompre ce traitement.
  2. Ce n'est pas un succès de handler.

Où en est-on ? Étape 4/5 (suite) : un event n'est pas toujours une simple notification, certains permettent d'agir.

Nous voulons rattacher une corrélation à l'import pour suivre ses tentatives. L'enrichissement avant envoi et celui après réception ne se font pas au même point. La nouvelle Envelope de with() doit être conservée :

Event Method Effet
SendMessageToTransportsEvent setEnvelope() remplace l'Envelope remise aux senders ; son passage au worker dépend ensuite du transport et de la sérialisation
WorkerMessageReceivedEvent shouldHandle(false) empêche ce dispatch de réception si la valeur reste fausse après les listeners
WorkerMessageReceivedEvent addStamps() enrichit l'Envelope avant son passage au bus

Après shouldHandle(false), l'event suivant est directement WorkerRunningEvent, sur le chemin standard sans autre intervention. Le worker n'a alors appelé ni le bus ni son chemin normal d'acquittement : ce n'est ni un succès de handler ni une planification de retry. Une arrivée ultérieure reste possible selon le transport ; le refus ne signifie pas « jamais traité dans toute l'histoire de ce message ».

Les deux qui comptent

À retenir en priorité
  1. Les listeners sont ordonnés par priority.
  2. Lire après la décision de retry.

Où en est-on ? Étape 5/5 : les deux events à maîtriser, Failed (et willRetry()) puis Running.

🌍 In Real Life

La situation : le responsable consulte la fiche d'incident après que le planificateur a décidé d'un rappel.

L’équivalent dans Symfony : décision inscrite → willRetry() positionné par le listener de retry ; consultation ensuite → listener de priorité inférieure.

Retour à la réalité technique : les priorités décroissantes déterminent l'état observé. Lire avant le listener à 100 peut montrer false alors qu'un retry sera décidé. À 0, on ne prouve pas encore la conservation par le failure transport à -100.

🧠 Comment le mémoriser : « Lire après celui qui écrit. » Image mentale : un stylo suivi d'une loupe. Question-réflexe : qui a déjà modifié l'événement à ma priorité ?

⚠️ À ne pas confondre : absence de retry prévu et message définitivement perdu.

L'alerte de l'import lit WorkerMessageFailedEvent, qui porte l'exception et willRetry(). Mais willRetry() est positionné par SendFailedMessageForRetryListener, à la priority 100 :

Listener willRetry() d'un message qui sera rejoué
priority 150 false
priority 0 (défaut) true

Ce même listener émet WorkerMessageRetriedEvent pendant la diffusion de l'échec : un listener de priority 0 sur l'échec écrit après celui du retry. Le failure transport écoute à -100. À priorité 0, on est donc après la décision de retry, mais avant la tentative de transfert en file d'échec. Un false à cet instant ne prouve pas que cette conservation a déjà réussi.

priorité 150 : votre listener   → willRetry() = false (pas encore décidé)
priorité 100 : SendFailedMessageForRetryListener → décide, émet Retried
priorité   0 : votre listener   → willRetry() fiable
priorité -100: SendFailedMessageToFailureTransportListener → file d'échec

Cette fonction d'observation conserve l'exemple de décision sans effet externe ; elle doit être appelée par un listener au moment voulu :

<?php
use Symfony\Component\Messenger\Event\WorkerMessageFailedEvent;

function failureStage(WorkerMessageFailedEvent $event): string
{
    return $event->willRetry() ? 'retry-planned' : 'no-retry-planned';
}

true produit retry-planned, false produit no-retry-planned. Ce résultat décrit une décision observée, pas la réussite future de l'import.

WorkerRunningEvent répond à une autre question : la boucle tourne-t-elle après un message ou à vide ? isWorkerIdle() distingue ces cas. Un lot de plusieurs Envelope peut produire plusieurs événements non idle ; ce n'est pas un compteur de lots ni de succès métier. Éviter un accès réseau coûteux sur chaque tour idle, qui se répéterait sans nouvel import.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'event décrit une tentative en échec.
  2. La suite dépend de la politique de retry.
  • Voir l’explication : WorkerRunningEvent se déclenche à vide

    WorkerRunningEvent se déclenche à vide : y placer du travail lourd le fait tourner en permanence. Pourquoi on se trompe : le nom évoque « un message est en cours ».

  • Voir l’explication : WorkerMessageFailedEvent n'est pas un abandon

    WorkerMessageFailedEvent n'est pas un abandon : willRetry() exprime la décision prise, pas seulement le compteur restant. Le lire après le listener standard de priorité 100, sans oublier les exceptions spéciales. Pourquoi on se trompe : « Failed » fait penser à la fin de l'histoire.

  • Voir l’explication : Un dispatch initial non routé n'émet pas ces events de transport/worker

    Un dispatch initial non routé n'émet pas ces events de transport/worker : un middleware peut l'observer. Cela n'interdit pas les events applicatifs émis par le handler et ne décrit pas une réception déjà prise en charge par un worker.

  • Voir l’explication : Un listener peut empêcher le traitement

    Un listener peut empêcher le traitement : shouldHandle(false) sur WorkerMessageReceivedEvent. Cela ne réussit pas l'import et ne garantit pas sa remise en file. Pourquoi on se trompe : on croit qu'un listener ne fait qu'observer.

Fiche express

À mémoriser

À retenir en priorité
  1. Le retry a son event distinct.
  2. Il peut être émis pendant le traitement de l'event d'échec.

Pour suivre le fichier importé, noter le point d'émission plutôt que compter une suite obligatoire d'événements. L'envoi, le traitement, l'acquittement et la conservation d'un échec restent des étapes distinctes.

Si tu dois retenir seulement 7 choses :

  • Dispatch initial non routé : pas de ces events transport/worker dans la pile standard.
  • À l'envoi réussi : SendMessageToTransportsEvent, puis MessageSentToTransportsEvent, une fois pour la sélection de senders.
  • Worker : started/stopped concernent le process ; received puis handled/failed concernent le trajet d'un message, avec les branches décrites.
  • willRetry() : après la priority 100.
  • WorkerMessageRetriedEvent : pendant l'échec, par le listener de retry.
  • WorkerRunningEvent : même à vide.
  • shouldHandle(false) : pas de dispatch de cette réception, ni acquittement/retry automatique par ce seul choix.

Moyen mnémotechnique : « envoyer, recevoir, réussir ou échouer, tourner, s'arrêter ».

envoi : SendMessageToTransports (setEnvelope) → MessageSentToTransports (×1)
worker : Started → Received (shouldHandle, addStamps)
  → Handled | Failed (willRetry après 100 ; Retried émis dedans)
  → Running (même idle) → Stopped
dispatch initial non routé : pas de ces events transport/worker

Le parcours Messenger peut maintenant être observé sans confondre notification et travail accompli. Pour définir ses propres abonnements, poursuivre avec EventDispatcher. Pour lancer l'import et ses outils d'exploitation, revenir à Console.

🧠 À retenir pour la certification

  • Dix events documentés (envoi : SendMessageToTransports, MessageSentToTransports ; worker : Started, Running, Stopped, RateLimited ; message : Received, Handled, Failed, Retried) + WorkerMessageSkipEvent (11ᵉ, code 8.0, messenger:failed:retry).
  • Un envoi vers plusieurs transports ⇒ un seul MessageSentToTransportsEvent, après la boucle d'envoi réussie.
  • SendFailedMessageForRetryListener écoute Failed à la priorité 100 ; le failure transport à -100 ; willRetry() est fiable à partir de 0.
  • Retried est émis pendant la diffusion de Failed.
  • WorkerRunningEvent : aussi sur les tours à vide (isWorkerIdle()) ; pas de travail lourd.
  • shouldHandle(false) (Received) : ni bus, ni acquittement normal, ni retry ; setEnvelope() / addStamps() enrichissent.
  • Dispatch initial synchrone non routé : pas d'events transport/worker ; le middleware couvre tout dispatch().

Phrase de mémorisation : « Un middleware est un poste sur chaque dispatch, un event est un moment du cycle d'envoi ou du worker — et willRetry() ne se lit qu'après la priorité 100. »
