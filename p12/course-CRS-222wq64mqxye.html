Objectif

GET /blog/42 a atteint l'application. Avant que BlogController::show consulte ArticleCatalog, il faut savoir d'où vient chaque valeur : l'identifiant extrait du chemin, une option après ?, un cookie ou un champ envoyé par le formulaire d'inscription ne sont pas interchangeables.

Nous allons lire ces données dans leur collection dédiée, traiter une entrée dont la forme ne convient pas, puis préciser ce que le serveur peut croire lorsqu'un reverse proxy transmet la demande.

Fil du cours en quatre étapes :

1. Les sacs        → d'où vient la valeur ? (provenance)
2. InputBag        → sous quelle forme la lire ? (scalaire ou tableau)
3. Client / proxys → quelle IP croire derrière un reverse proxy ?
4. Host            → quel nom d'hôte accepter ?

L'essentiel

À comprendre

À retenir en priorité
  1. InputBag::get() refuse un array.
  2. all($key) attend un array et rend [] si la key est absente.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. En PHP « nu », $_GET, $_POST, $_COOKIE et $_SERVER sont des tableaux globaux mélangés, sans contrat. La Request d'HttpFoundation range chaque provenance dans un sac distinct : le code dit explicitement d'où il lit.
  • Le piège de fond. Une valeur lue n'est ni validée ni digne de confiance parce qu'elle est dans un bon sac. Le sac répond à « d'où ? », jamais à « est-ce acceptable ? ». Même chose pour les en-têtes de proxy : leur présence ne prouve rien.
  • Ce que l'auteur veut que vous compreniez. Trois décisions séparées : quel sac (provenance), quel accesseur (scalaire ou tableau), à qui je fais confiance (proxys, puis hosts : deux listes différentes).
  • Pourquoi c'est à l'examen. Les questions testent la disparition de Request::get(), les exceptions de InputBag (laquelle, quand), les règles de getMethod(), l'adresse que renvoie getClientIp() et les regex non ancrées de setTrustedHosts().

La Request d'HttpFoundation représente une demande reçue. Un sac, ou bag, est un object qui regroupe des valeurs de même provenance. Nommer ce sac rend la lecture explicite ; le raccourci Request::get(), qui cherchait dans plusieurs collections, n'existe plus en Symfony 8.0.

Après la reconnaissance de blog_show, id et _route sont dans attributes. Un ?id=999 supplémentaire serait dans query : il ne remplace pas automatiquement l'identifiant 42 extrait du chemin. Cette distinction préserve l'intention du code, sans rendre les valeurs de route intrinsèquement fiables ou déjà validées.

Trois sacs sont des InputBag : query, request et cookies. Ils peuvent contenir des arrays, mais leur méthode get() refuse de les retourner comme une valeur scalaire. Enfin, lire une adresse annoncée par un header ne prouve pas sa provenance : proxys et noms d'hôtes autorisés demandent deux configurations de confiance différentes.

Le schéma

À retenir en priorité
  1. Nommer explicitement le bag évite les collisions.
  2. request contient le body de form, pas toute la Request.

Où en est-on ? Avant de détailler les sacs, voici la situation la plus parlante de tout le cours : une page de recherche. Nous savons déjà d'où viennent ses données (la partie query de l'URL) ; reste à choisir une lecture adaptée à leur forme. Ce schéma annonce les étapes 1 et 2.

La page de recherche liée au blog ajoute un mot-clé et plusieurs tags. Nous savons d'où viennent ces données — la partie query de l'URL — mais il reste à choisir une lecture adaptée à leur forme :

Bleu : données entrantes et sac ; capsules vertes : valeurs obtenues ; rouge : lecture incompatible. q=php décrit une seule valeur ; tags[]=php décrit une collection. Le résultat rouge ne signifie pas « aucun tag » : il signifie que le code a demandé une forme incompatible.

Ce schéma ne décrit pas le body JSON d'un import. Celui-ci demande une lecture explicite par toArray() ou getPayload(), et ne se retrouve pas dans query. Dans les deux cas, obtenir une string ou un array ne valide pas encore les tags autorisés par le blog.

L'exemple : lire une recherche

Exemple concret

Où en est-on ? Avant le détail des sacs, on exécute le mécanisme du schéma sur du code minimal. Aucun navigateur, aucun kernel : on fabrique une Request à la main pour voir ce que Symfony met dans chaque sac.

Les exemples supposent PHP 8.4 et HttpFoundation 8.0 chargés par l'autoloader du projet. Pour reproduire la lecture sans navigateur ni kernel, construis cette Request locale :

use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/search?q=php&tags[]=php&tags[]=http');

Le bloc suivant compare des lectures indépendantes. Il n'affiche rien ; les commentaires indiquent les résultats :

// /search?q=php&tags[]=php&tags[]=http
$request->query->get('q');       // 'php'
$request->query->all('tags');    // ['php', 'http']
$request->query->get('tags');    // BadRequestException : valeur non scalaire
$request->attributes->get('_route');

Les deux premières lectures retournent 'php' et ['php', 'http']. La troisième lève une BadRequestException : dans une exécution linéaire sans capture, la dernière ligne ne serait donc pas atteinte. Lue séparément sur notre object local, _route vaut null, car Request::create() n'exécute pas le Routing. Dans l'application, ce nom est disponible après la reconnaissance d'une route.

Pourquoi _route vaut-il null ici ? Parce que attributes est rempli par le routeur (RouterListener) pendant le traitement par HttpKernel. Request::create() se contente de construire l'object : personne n'a lancé le routage, donc rien n'a rangé _route dans attributes.

Les sacs

Où en est-on ? Étape 1 sur 4 : la provenance. Le but : savoir, pour chaque valeur, dans quel tiroir de la Request elle se trouve. Sans cela, on lit au mauvais endroit et on obtient null sans comprendre pourquoi.

La recherche a fixé le premier réflexe : choisir une provenance avant de choisir un accesseur. La même méthode s'applique à l'inscription, au téléversement lié à un article et aux métadonnées de la connexion :

Property Type Contenu
$query InputBag Parameters d'URL ($_GET)
$request InputBag Corps de form ($_POST)
$cookies InputBag Cookies
$attributes ParameterBag Données de l'application (route, _route, _controller)
$headers, $server, $files HeaderBag, ServerBag, FileBag Headers, $_SERVER, files téléversés

Vue d'ensemble pour POST /article/42?page=2 avec un formulaire :

POST /article/42?page=2          Cookie: PHPSESSID=abc
title=Bonjour    (corps form)    X-Foo: bar

  ?page=2          → $request->query       (InputBag)
  title=Bonjour    → $request->request     (InputBag)
  PHPSESSID=abc    → $request->cookies     (InputBag)
  id = 42 (route)  → $request->attributes  (ParameterBag, posé par le routeur)
  X-Foo: bar       → $request->headers     (HeaderBag)
  REMOTE_ADDR...   → $request->server      (ServerBag)
  fichiers         → $request->files       (FileBag)

Dans $request->request, la variable est la Request entière, la propriété request son sac de paramètres de formulaire analysés. Ce n'est pas le body brut universel de tout POST. getContent() permet de lire ce contenu brut ; un formulaire analysé et un texte JSON ne sont pas automatiquement la même collection.

Cet exemple indépendant conserve le chemin pédagogique /article/42 pour juxtaposer trois provenances. Il ne configure ni cette route ni la pagination canonique /blog/page/{page} :

use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/article/42?page=2', 'POST', ['title' => 'Bonjour']);
$request->attributes->set('id', 42);
echo $request->attributes->get('id'), "\n";
echo $request->query->get('page'), "\n";
echo $request->request->get('title'), "\n";

La sortie est 42, 2, Bonjour. L'identifiant a été posé manuellement par le laboratoire ; page vient de l'URL et title du formulaire simulé. Lire title dans query ne trouverait pas la valeur simplement parce que l'autre sac la contient.

Pourquoi Request::get() a-t-il disparu ?

Ce raccourci cherchait « un peu partout » (attributes, puis query, puis request) : deux sacs portant la même clé donnaient un résultat dépendant de l'ordre de recherche, et un paramètre d'URL pouvait masquer une valeur applicative. Le supprimer force à nommer la provenance. En 8.0, $request->get('id') provoque une Error (méthode inexistante), pas un null ni une deprecation.

getPayload() et toArray() : le corps, formulaire ou JSON

Pour une entrée acceptant formulaire ou JSON, getPayload() retourne un InputBag : il clone d'abord le sac request si celui-ci n'est pas vide ; sinon il décode le contenu JSON. Il ne fusionne pas les deux sources. Un contenu vide donne un sac vide. À l'inverse, toArray() décode le contenu brut et lève une exception s'il est vide.

getPayload()                                toArray()
  $request->request non vide ? → CLONE        contenu vide ?  → JsonException
  contenu vide ?               → InputBag []  sinon json_decode
  sinon json_decode                           pas un array ?  → JsonException
  pas un array / invalide → JsonException     (ignore le sac request)

Pour le JSON, ces deux méthodes exigent un résultat PHP de type array : un object JSON ou une liste JSON conviennent, un scalaire tel que "42" ne convient pas. Un JSON invalide ou un résultat scalaire provoque Symfony\Component\HttpFoundation\Exception\JsonException, à distinguer de la classe native \JsonException. Cette vérification ne remplace pas le contrôle du schéma attendu par l'import.

🌍 In Real Life

La situation : au restaurant, numéro de table, annotation du client et formulaire de réservation restent sur des supports distincts, même s'ils portent une rubrique « id ».

L’équivalent dans Symfony : résultat du routage → attributes ; paramètres après ? → query ; formulaire analysé → request ; contenu brut → getContent().

Retour à la réalité technique : id=42 de la route n'est pas remplacé automatiquement par ?id=999. getPayload() privilégie le formulaire non vide, sinon lit le JSON ; il ne fusionne pas tout. Une valeur lue reste à valider.

🧠 Comment le mémoriser : « Même nom, provenance différente. » Image mentale : trois supports étiquetés. Question-réflexe : de quel sac cette valeur doit-elle venir ?

⚠️ À ne pas confondre : attributs de Request, attributs PHP #[...] et paramètres de query.

Une Request est un courrier trié dans des bacs nommés : query pour l'adresse enrichie, request pour le form body, headers pour les indications de traitement. Les attributes sont les notes ajoutées par l'application, pas un autre bag de saisie client.

InputBag n'accepte que des scalaires

Où en est-on ? Étape 2 sur 4 : on sait dans quel sac chercher ; on choisit maintenant comment lire. query, request et cookies sont des InputBag, et leur get() a un contrat strict : il rend une valeur simple. C'est ce qui fait échouer la lecture de tags[]=php avec get('tags').

Pourquoi get() refuse-t-il un array ? Parce que ces sacs contiennent des données saisies par l'utilisateur. Un ?q[]=x malicieux transformerait un string attendu en array et ferait planter le code en aval (strlen, SQL…). InputBag::get() transforme cette surprise en erreur claire, BadRequestException (réponse HTTP 400), au lieu de laisser l'array circuler.

Le titre résume la contrainte de lecture par get(), pas une interdiction de stocker des arrays dans le sac. Un scalaire PHP est une string, un entier, un flottant ou un booléen ; null est également permis ici, et l'implémentation accepte aussi les objets Stringable. Le cas important pour notre recherche reste l'array reçu là où get() attend une valeur simple : il provoque une BadRequestException, pas une sélection du premier élément.

Le défaut fourni par le programme suit aussi un contrat. Passer un array comme deuxième argument de get() provoque une InvalidArgumentException : l'erreur est dans l'appel, même avant d'examiner la valeur entrante. Cela diffère de la BadRequestException provoquée par un array reçu.

Deux fautes, deux exceptions, deux responsables :

┌──────────────────────────────┐   ┌───────────────────────────────────────┐
│ ?page[]=2    get('page')     │   │ get('page', ['défaut'])               │
├──────────────────────────────┤   ├───────────────────────────────────────┤
│ Faute : le CLIENT            │   │ Faute : le CODE appelant              │
│ Exception : BadRequest-      │   │ Exception : InvalidArgument-          │
│   Exception                  │   │   Exception                           │
│ Quand : valeur reçue = array │   │ Quand : 2e argument non scalaire      │
│ Vérifié même sans la clé ?   │   │ Vérifié même si la clé est absente :  │
│   non, seulement si présente │   │   oui, avant de lire la valeur        │
└──────────────────────────────┘   └───────────────────────────────────────┘

Pour la collection de tags, utilise all('tags'). Une clé absente ou dont la valeur est null donne [] ; une valeur présente non nulle qui n'est pas un array provoque une BadRequestException. Sans clé, all() retourne tout le contenu du sac, même s'il contient des scalaires : ne confonds pas ces deux formes d'appel.

Appel Attend Résultat
get('q') un scalaire la valeur, ou le défaut si absente ; array reçu → BadRequestException
all('tags') un array l'array ; clé absente ou null → [] ; scalaire présent → BadRequestException
all() rien tout le contenu du sac (scalaires et arrays)

Le ParameterBag de attributes permet, lui, à get() de retourner des arrays ou des objets. Sa provenance applicative ne dispense pas de valider les valeurs issues du chemin. Lire l'identifiant et vérifier qu'il désigne un article sont encore deux opérations distinctes.

La méthode HTTP effective : un autre cas « donnée reçue ≠ interprétation »

Où en est-on ? Même idée, appliquée à la méthode HTTP : ce que le navigateur envoie (POST) n'est pas forcément ce que getMethod() rend.

Une autre entrée mérite de séparer donnée reçue et interprétation : la méthode HTTP. Pour un formulaire d'édition envoyé en POST, X-HTTP-Method-Override: PUT peut conduire getMethod() à retourner PUT sans activer la lecture du paramètre _method. Ce paramètre, lui, exige enableHttpMethodParameterOverride(). Le header est prioritaire ; getRealMethod() conserve la méthode reçue, POST.

Cette règle décrit le comportement sans restriction d'override configurée. Une liste de méthodes autorisées peut le restreindre. En Symfony 8.0, les cibles GET, HEAD, CONNECT et TRACE sont ignorées ; le code ne transforme donc pas n'importe quel POST en lecture de l'article. La méthode effective ne constitue pas non plus une autorisation d'édition.

REQUEST_METHOD = POST ?  ── non ──► getMethod() = méthode reçue
        │ oui
        ▼
header X-HTTP-Method-Override présent ?
        │ non → paramètre _method lu SEULEMENT si
        │       enableHttpMethodParameterOverride() a été appelé
        ▼
cible ∈ {GET, HEAD, CONNECT, TRACE} ?  → ignorée (méthode reçue gardée)
liste setAllowedHttpMethodOverride() et cible absente ? → ignorée
sinon → getMethod() = cible (ex. PUT) ;  getRealMethod() = POST

🌍 In Real Life

La situation : une case attend une réponse simple ; une feuille jointe contient plusieurs choix. Demander la case ne signifie pas prendre arbitrairement le premier choix de la feuille.

L’équivalent dans Symfony : lecture simple → InputBag::get() ; collection nommée → all('tags') ; dossier entier → all().

Retour à la réalité technique : un array reçu par get() provoque BadRequestException ; un défaut array fourni par le code provoque InvalidArgumentException. Le sac peut pourtant stocker des arrays. Changer d'accesseur ne valide pas les valeurs métier.

🧠 Comment le mémoriser : « Choisir la forme après la provenance. » Image mentale : case unique et feuille de choix. Question-réflexe : attend-on un scalaire ou une collection ?

⚠️ À ne pas confondre : mauvaise donnée entrante et mauvais contrat d'appel ; méthode HTTP effective et méthode réellement reçue.

Client et proxys

À retenir en priorité
  1. Déclarer les proxys de confiance avant de lire les headers transférés.
  2. L'adresse la plus à gauche n'est pas automatiquement fiable.

Où en est-on ? Étape 3 sur 4 : on quitte les données de l'utilisateur pour les métadonnées de la connexion : « quelle est l'adresse IP du client ? ». Elle vit dans $request->server (REMOTE_ADDR) et dans des headers (X-Forwarded-For) que n'importe qui peut écrire. Tout l'enjeu : savoir lesquels croire.

Pourquoi la réponse n'est-elle pas « lis le header » ? Un header se forge en une ligne. Seul le pair réseau immédiat (REMOTE_ADDR) est garanti par la connexion TCP. Si ce pair est un proxy que vous contrôlez, alors ce qu'il écrit dans X-Forwarded-For devient crédible ; sinon non.

Le blog peut être derrière un reverse proxy, serveur qui reçoit la connexion du navigateur puis transmet la demande à l'application. REMOTE_ADDR désigne alors le pair réseau immédiat, souvent ce proxy, pas nécessairement le navigateur. X-Forwarded-For annonce des adresses en amont, mais sa simple présence ne rend pas ses valeurs authentiques.

Navigateur ──► Proxy A ──► Proxy B ──► Application Symfony
 1.2.3.4       5.6.7.8     10.0.0.2      voit REMOTE_ADDR = 10.0.0.2
                           X-Forwarded-For: 1.2.3.4, 5.6.7.8

Sans proxy de confiance correspondant au pair, getClientIp() utilise REMOTE_ADDR et ignore cette chaîne annoncée. Il faut configurer à la fois les proxys maîtrisés (setTrustedProxies() ou trusted_proxies) et les headers à croire, par un masque de constantes ou trusted_headers. Le proxy doit contrôler les informations qu'il transmet ; croire tous les expéditeurs pour obtenir « la vraie IP » supprimerait cette frontière.

Dans une chaîne reconnue, Symfony ajoute REMOTE_ADDR, normalise et filtre les adresses, retire celles des proxys fiables, puis renverse les adresses restantes. getClientIp() prend la première : l'adresse non fiable la plus proche du serveur, pas automatiquement la plus à gauche du header.

Ce laboratoire isolé emploie des adresses réservées à la documentation. Il modifie un réglage statique et le remet à vide ; ne le colle pas dans un processus d'application déjà configuré :

use Symfony\Component\HttpFoundation\Request;

Request::setTrustedProxies(['192.0.2.10'], Request::HEADER_X_FORWARDED_FOR);
$request = Request::create('/demo');
$request->server->set('REMOTE_ADDR', '192.0.2.10');
$request->headers->set('X-Forwarded-For', '198.51.100.1, 203.0.113.8');
echo $request->getClientIp(), "\n";
Request::setTrustedProxies([], 0);

Il affiche 203.0.113.8. Le pair 192.0.2.10 est reconnu et retiré ; parmi les deux valeurs restantes, la plus proche est retenue. Le fragment historique suivant exprime la même règle avec d'autres adresses. Il suppose lui aussi un pair déclaré fiable et le header autorisé ; ce ne sont pas les réglages laissés après le laboratoire :

// X-Forwarded-For: 1.2.3.4, 5.6.7.8   (aucun des deux de confiance)
$request->getClientIp();    // '5.6.7.8', et non '1.2.3.4'

Le résultat est donc '5.6.7.8' dans ces conditions. Retrouver l'adresse du client d'origine suppose une chaîne correctement transmise et tous les proxys intermédiaires reconnus ; l'IP n'est pas une identité utilisateur. Si toutes les adresses filtrées appartiennent à la plage de confiance, l'implémentation possède un repli vers une adresse fiable rencontrée : « premier non fiable » décrit le cas usuel, pas l'existence garantie d'une telle adresse.

Pourquoi « la plus proche du serveur » et pas « la plus à gauche » ? La partie gauche de X-Forwarded-For est ce que le client a écrit : il peut y mettre n'importe quoi. Chaque proxy honnête ajoute à droite l'adresse de ce qu'il a vu. En remontant depuis le serveur et en sautant les proxys de confiance, on s'arrête à la première adresse qu'aucun de nos proxys ne garantit : c'est la plus récente donnée vérifiable, la moins falsifiable.

Situation getClientIp()
aucun trusted proxy configuré REMOTE_ADDR (IP du proxy si présent : comportement sûr)
pair fiable, header autorisé, chaîne partiellement fiable première adresse non fiable depuis le serveur
toute la chaîne est fiable le vrai client d'origine (repli sur une adresse fiable rencontrée si plus rien de non fiable)

🌍 In Real Life

La situation : un accueil ne croit pas une liste de messagers simplement parce qu'elle est écrite sur une enveloppe ; il part du relais qu'il connaît réellement.

L’équivalent dans Symfony : relais immédiat → REMOTE_ADDR ; relais maîtrisés → trusted proxies ; informations autorisées → masque des trusted headers.

Retour à la réalité technique : dans la chaîne reconnue, Symfony filtre les proxys fiables et retient usuellement l'adresse non fiable la plus proche du serveur, pas automatiquement celle de gauche. Les relais doivent contrôler ce qu'ils transmettent ; l'IP ne prouve pas une identité.

🧠 Comment le mémoriser : « Remonter depuis le voisin connu. » Image mentale : chaîne examinée depuis l'accueil. Question-réflexe : qui garantit chaque information de transfert ?

⚠️ À ne pas confondre : confiance dans le proxy et confiance dans tous les noms d'hôtes qu'il transmet.

Le host, et la seconde liste de confiance

À retenir en priorité
  1. trusted_hosts protège le Host, pas la chaîne de proxys.
  2. Ancrer les regex ; une liste vide n'impose pas de restriction.

Où en est-on ? Étape 4 sur 4, la dernière : après « quel expéditeur croire ? » (proxys), on pose une autre question : « quel nom d'hôte l'application accepte-t-elle de servir ? ». Deux listes, deux rôles ; les confondre est le piège central de cette partie.

Après l'inscription, le blog peut produire un lien absolu dans un email. Le host, nom d'hôte demandé, devient alors une donnée sensible : un nom inattendu ne doit pas contaminer ce lien ou une clé de cache. La confiance accordée au proxy ne définit pas à elle seule les noms que l'application accepte de servir.

Pourquoi le host est-il dangereux ? Il vient du header Host (ou d'un header de proxy), donc du client. Un attaquant qui envoie Host: evil.test peut obtenir un email de réinitialisation avec un lien vers evil.test (host header injection), ou empoisonner un cache. La parade : une liste blanche de patterns.

Request::setTrustedHosts(['^(.+\.)?example\.com$']) autorise ici example.com et ses sous-domaines. getHost() lève une SuspiciousOperationException si le host lu ne correspond pas à la liste. Un pattern est une expression régulière : Symfony ajoute les délimiteurs et l'option insensible à la casse ({motif}i), mais pas les ancres. ^ marque le début, $ la fin et \. un point littéral.

Le contre-exemple ['example.com'] peut donc accepter example.com.attaquant.test : le point n'est pas échappé et la correspondance n'est pas limitée au nom complet. Si aucun sous-domaine n'est nécessaire, un motif plus étroit rend cette intention visible :

Pattern écrit            Regex réelle         example.com.attaquant.test ?
'example.com'            {example.com}i       ACCEPTÉ  (non ancré, « . » = tout)
'^example\.com$'         {^example\.com$}i    refusé
'^(.+\.)?example\.com$'  {...}i               refusé ; accepte www.example.com
use Symfony\Component\HttpFoundation\Request;

Request::setTrustedHosts(['^example\.test$']);
$request = Request::create('https://example.test/demo');
echo $request->getHost(), "\n";
Request::setTrustedHosts([]);

Ce laboratoire indépendant affiche example.test. Avec cette même liste encore active, une nouvelle Request visant example.test.other.test serait refusée à la lecture du host. Le dernier appel remet le réglage statique à vide pour ce laboratoire, pas comme recommandation de production.

Une liste vide supprime le contrôle d'appartenance aux noms autorisés, pas les vérifications syntaxiques de getHost(). Selon la configuration, un host transmis par un proxy fiable peut aussi être utilisé ; la liste des hôtes limite le nom retenu. Garde donc les deux questions séparées : quel expéditeur peut fournir des informations de transfert, et quel nom l'application accepte-t-elle ?

🌍 In Real Life

La situation : connaître le livreur ne dispense pas de vérifier que le nom de restaurant sur son colis est bien le nôtre.

L’équivalent dans Symfony : livreur admis → proxy fiable ; établissement destinataire autorisé → trusted_hosts.

Retour à la réalité technique : les expressions de hosts doivent limiter le nom complet avec leurs ancres et points échappés. Une liste vide retire le contrôle d'appartenance, pas les vérifications syntaxiques. Le réglage ne choisit pas les proxys fiables.

🧠 Comment le mémoriser : « Expéditeur et destination : deux contrôles. » Image mentale : badge du livreur et adresse du colis. Question-réflexe : mon motif accepte-t-il uniquement les hôtes voulus ?

⚠️ À ne pas confondre : suffixe visuellement ressemblant et nom entièrement autorisé.

Pièges d'examen

Piège à éviter

  • Voir l’explication : $request->request n'est pas la Request

    $request->request n'est pas la Request : c'est le sac de paramètres de formulaire analysés. Pour le JSON de l'import, choisis explicitement la lecture du contenu ; ne suppose pas qu'un POST le remplit toujours. Pourquoi on se trompe : $request->request ressemble à « le corps de la requête », alors que c'est seulement le corps déjà analysé comme formulaire.

  • Voir l’explication : get() sur un array lève.

    get() sur un array lève. Ce n'est pas null, ni le premier élément. Pour tags, change le contrat de lecture en all('tags') ; ne masque pas l'erreur par une valeur de repli qui ferait disparaître une entrée mal formée. Pourquoi on se trompe : en PHP, $_GET['q'] rend simplement l'array.

  • Voir l’explication : getClientIp() sans trusted proxies renvoie l'IP du proxy

    getClientIp() sans trusted proxies renvoie l'IP du proxy, pas celle du client dans une chaîne passant par ce proxy — et c'est le comportement sûr. Sans intermédiaire, le pair immédiat peut être le client lui-même. Pourquoi on se trompe : on croit que X-Forwarded-For est lu par défaut.

  • Voir l’explication : getClientIp() ne renvoie pas « la plus à gauche ».

    getClientIp() ne renvoie pas « la plus à gauche ». Il renvoie l'adresse non fiable la plus proche du serveur — ce qui coïncide avec le client d'origine uniquement quand toute la chaîne de proxies est déclarée de confiance. Fonder une allow-list sur la lecture inverse revient à faire confiance à une valeur que le client contrôle. Le masque des headers de confiance et le contrôle effectué par le proxy sont aussi nécessaires que sa présence dans la liste. Pourquoi on se trompe : « le client est le premier de la liste » est vrai dans la tête de l'utilisateur, mais c'est la valeur la plus falsifiable.

  • Voir l’explication : Request::create() n'est pas createFromGlobals().

    Request::create() n'est pas createFromGlobals(). La première fabrique une Request arbitraire — tests, sub-Requests ; la seconde lit les superglobales. Construire cet object n'envoie aucune demande réseau et ne déclenche pas le Routing. Les valeurs _route et id de notre parcours principal apparaissent au moment approprié du traitement par HttpKernel, avant la lecture du catalogue et la construction de la Response.

  • Voir l’explication : Regex de trusted hosts non ancrée.

    Regex de trusted hosts non ancrée. ['example.com'] n'est pas ^example\.com$ : Symfony n'ajoute que les délimiteurs et i. Pourquoi on se trompe : on croit que la liste compare des noms complets.

  • Voir l’explication : Deux erreurs de InputBag::get() distinctes

    Deux erreurs de InputBag::get() distinctes : array reçu → BadRequestException ; défaut non scalaire → InvalidArgumentException. Pourquoi on se trompe : les deux concernent « un array dans get() ».

Application

À retenir en priorité
  1. Nommer explicitement le bag évite les collisions.
  2. request contient le body de form, pas toute la Request.
  3. trusted_hosts protège le Host, pas la chaîne de proxys.
  4. Ancrer les regex ; une liste vide n'impose pas de restriction.

Fiche express

À mémoriser

De la provenance d'une valeur à son interprétation, garde sept repères :

  • Nommer le sac : Request::get() n'existe plus en 8.0.
  • $request->request = paramètres de formulaire analysés ; $attributes = données applicatives, dont les paramètres de route encore à valider.
  • InputBag::get() refuse un array ; all($key) attend un array, tandis que all() sans clé retourne le sac complet.
  • getPayload() : formulaire non vide en priorité, sinon JSON ou sac vide si contenu vide ; résultat InputBag, sans validation métier.
  • X-HTTP-Method-Override sur POST : pas d'activation de _method nécessaire, mais restrictions configurées possibles ; vers GET ignoré en 8.0.
  • getClientIp() : l'adresse non fiable la plus proche du serveur — le client d'origine seulement si toute la chaîne de proxies est de confiance.
  • Trusted hosts : regex non ancrées automatiquement ; liste vide = pas de contrôle d'appartenance, mais syntaxe du host encore vérifiée.

Moyen mnémotechnique : « Nommer le sac, ancrer le host, déclarer le proxy ».

🧠 À retenir pour la certification

  • Provenance d'abord : query (?), request (form analysé), cookies, attributes (routeur), headers, server, files. Plus de Request::get().
  • InputBag::get() : scalaire ou Stringable ou null ; array reçu → BadRequestException, défaut non scalaire → InvalidArgumentException.
  • all('tags') pour une collection ; all() pour tout le sac.
  • getPayload() : form non vide cloné, sinon JSON ; body vide → sac vide ; invalide ou non-array → JsonException de HttpFoundation.
  • getClientIp() : tri depuis le serveur ; proxys et headers de confiance.
  • setTrustedHosts() : {motif}i, jamais d'ancres ajoutées ; liste vide ≠ plus de vérification syntaxique.

Phrase de mémorisation : « Je nomme le sac d'où vient la valeur, je lis sa forme avec le bon accesseur, je ne crois que les proxys que je déclare et je n'accepte que les hosts que j'ancre. »
