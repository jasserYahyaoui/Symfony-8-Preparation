Module 22 — Mailer et Mime

Symfony 8.0 · API PHP ≤ 8.4 · Twig ≤ 3.22. Préparation indépendante.

Comprendre ce module dans le projet

Le rapport d'import est prêt et l'équipe éditoriale doit être avertie. Il faut d'abord composer un message, puis le confier à un mécanisme d'expédition. Mime et Mailer séparent ces deux travaux ; aucun email n'est requis pour simplement lire /blog/42.

Mime construit le document : adresses, version texte, version HTML, pièces jointes et organisation des parties. L'API Email couvre les cas courants ; les objets de plus bas niveau donnent le contrôle de l'assemblage. Les types MIME décrivent le contenu : une extension de fichier et un type déduit de son contenu ne constituent pas la même information. Le message peut ainsi être inspecté sans qu'un envoi ait lieu.

Mailer relie ce document à un transport configuré. Le cours explique le choix des transports, les contrats d'envoi et l'observation des erreurs ou événements. Un appel peut conduire à un envoi immédiat ou passer par Messenger. Le différé exige une configuration effective du bus, du routage, du transport approprié et de sa consommation ; installer Messenger ne suffit pas.

Vous pourrez distinguer composition, demande d'envoi, remise au transport et livraison finale. C'est la capacité attendue pour produire une notification correcte et situer une panne sans annoncer prématurément « le destinataire a reçu le rapport ». L'acceptation par un transport ne prouve pas l'arrivée dans sa boîte.

Le principe d'injection de dépendances explique comment fournir le service d'envoi au code du blog. Le module Messenger approfondit la branche différée et ses reprises ; il n'est pas nécessaire pour comprendre la composition MIME ou l'envoi direct.

Objectif de départ : Choisir un transport intégré et reconnaître celui que la documentation déconseille.

RADIO — Select one answer. Mailer::send() returns normally. Does that alone prove mail-transport acceptance or delivery to the recipient's inbox?

Correction de consultation — non notée.

Distinguer retour du Mailer, mise en file Messenger, acceptation effective par le transport mail et livraison finale. Le retour seul ne démontre pas les étapes suivantes.

  • Distractor: Yes; send() waits until the recipient opens the message.

    send() n'attend pas l'ouverture par le destinataire ; avec Messenger il peut même précéder l'appel au transport mail.

  • Distractor: No; successful sending means the message was never accepted.

    Le retour normal ne prouve ni acceptation ni absence d'acceptation : le chemin peut être synchrone, mis en file, ou rejeté par un listener sans exception.

  • Correct: No; it may only have queued the message. Neither mail-transport acceptance nor inbox delivery is guaranteed.

    Avec une route asynchrone, send() peut revenir après la mise en file, avant tout appel au transport mail. Même une acceptation effective ne prouve pas la remise finale.
