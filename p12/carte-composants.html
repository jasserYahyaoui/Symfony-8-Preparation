Préparer l’application

Une carte répond à « qui fait quoi ? », pas à « qui s’exécute ensuite ? ». Pour voir la chronologie de /blog/42, ouvrez plutôt le parcours de la requête. Les schémas de la vue d’ensemble distinguent assemblage et utilisation.

Responsable Entrée → résultat Où approfondir
Application et Kernel Environnement et bundles activés → application préparée ; délégation HTTP Kernel et FrameworkBundle
FrameworkBundle Configuration des fonctionnalités → services et intégration des composants Architecture
Config et DependencyInjection Configuration → définitions → conteneur compilé si nécessaire Conteneur
Autowiring Types et alias configurés → références de dépendances Autowiring
Runtime Callable d’entrée résolu → application puis runner adapté Runtime

Une définition n’est pas encore une instance. Une extension traite la configuration pour alimenter le conteneur ; un compiler pass transforme son graphe de définitions. Ni l’un ni l’autre n’est un listener du GET. Un service partagé peut déjà exister quand on le demande.

🌍 In Real Life

La situation : avant le service, on traduit les besoins du restaurant en plan d’équipement, puis on vérifie les raccordements.

L’équivalent dans Symfony : besoins traduits en fiches → extension de conteneur ; plan inspecté/modifié → compiler pass ; raccord choisi par type → autowiring ; établissement préparé → Kernel ; lancement adapté à l’entrée → Runtime et runner.

Retour à la réalité technique : Config et DependencyInjection traitent configuration et définitions ; FrameworkBundle intègre les composants. La compilation prépare le conteneur utilisable à l’exécution, sans construire tous les services. Le calendrier du restaurant ne décrit pas la durée de vie d’un processus PHP.

🧠 Comment le mémoriser : « Le plan se prépare, l’instance se fournit. » Image : fiche puis équipement. Réflexe : « Modifie-t-on une définition ou utilise-t-on un objet ? »

⚠️ À ne pas confondre : extension et compiler pass travaillent sur la construction du conteneur, pas comme listeners de chaque GET.

Répondre en HTTP

Responsable Entrée → résultat Où approfondir
HttpFoundation Superglobales/données PHP → Request et Response manipulables HttpFoundation
HttpKernel Request et collaborateurs → Response, avec points d’extension conditionnels Traitement de requête
Routing et RouterListener Chemin/contexte → matching puis attributes de Request dans l’intégration HTTP Routing
ControllerResolver _controller → callable, éventuellement contrôleur-service Contrôleur
ArgumentResolver Request et signature → valeurs des arguments de l’action Arguments
ArticleCatalog applicatif Identifiant → article en mémoire ou absence Injection de dépendances
Twig Template et données → contenu HTML, pas émission HTTP TwigBundle
Security Identité, contexte et décision demandée → authentification/autorisation selon configuration Sécurité

HttpKernel appelle ses collaborateurs : le routeur n’appelle pas ControllerResolver qui appellerait ArgumentResolver. Request::attributes n’est pas Request::query, et #[Route] est une métadonnée PHP, pas un attribut du message HTTP. Une route connue ne garantit pas un article existant.

🌍 In Real Life

La situation : le responsable répartit la commande 42 entre des postes précis, sans demander à chaque poste de diriger les suivants.

L’équivalent dans Symfony : bon/résultat → objets HttpFoundation ; coordination → HttpKernel ; destination annotée → RouterListener/Routing ; responsable sélectionné → ControllerResolver ; informations remises → ArgumentResolver ; fiche consultée → ArticleCatalog ; présentation → Twig ; contrôle des droits → Security.

Retour à la réalité technique : HttpKernel obtient un callable et des arguments, puis l’invoque. Les services remplissent leurs responsabilités, sans chaîne automatique entre resolvers. Twig produit du HTML, pas l’émission HTTP ; Security intervient aux points configurés.

🧠 Comment le mémoriser : « Un responsable, des résultats distincts. » Image : coordinateur au centre des postes. Réflexe : « Quel collaborateur produit exactement cette valeur ? »

⚠️ À ne pas confondre : Request représente la demande ; elle ne l’orchestre pas.

Traiter une saisie et une autre représentation

GET /blog/42 ne demande pas de validation de formulaire. C’est l’inscription à la lettre du blog qui introduit un SignupData, les données soumises et les erreurs affichées. Le client JSON demande ensuite une représentation différente des informations d’article.

Responsable Entrée → résultat Où approfondir
Form Données initiales/soumises → arbre de champs, transformations, erreurs selon intégrations Formulaires
Validator Valeur/objet et contraintes → violations, pas sauvegarde Validation
Serializer Objet → normalisation → encodage, ou trajet inverse Serializer
CSRF Jeton et contexte attendu → contrôle contre certaines soumissions intersites CSRF

Transformer une chaîne en donnée métier n’atteste pas qu’elle est acceptable. Valider n’autorise pas l’utilisateur. Normaliser n’encode pas encore du JSON. Ces distinctions expliquent pourquoi une réponse peut être syntaxiquement correcte tout en exposant trop de données.

🌍 In Real Life

La situation : l’accueil recueille une inscription, vérifie ses champs puis prépare une fiche partageable, sans y recopier les notes internes.

L’équivalent dans Symfony : champs saisis et convertis → Form ; règles contrôlées → Validator ; objet converti en données puis JSON → Serializer ; jeton attendu vérifié → protection CSRF.

Retour à la réalité technique : Form gère champs et transformations ; Validator produit des violations ; Serializer change la représentation. CSRF contrôle un jeton dans un contexte prévu contre certaines soumissions intersites : ce n’est ni une preuve d’identité ni une validation métier. La fiche papier simplifie cette protection, elle n’en décrit pas le protocole.

🧠 Comment le mémoriser : « Lisible, acceptable, partageable : trois questions. » Image : trois contrôles sur une fiche. Réflexe : « Quelle vérification manque encore ? »

⚠️ À ne pas confondre : données valides, droit d’agir et choix des données exposées.

Exécuter hors HTTP

Le rédacteur peut importer des articles sans navigateur. Une commande et un worker réutilisent des services du blog ; ils ne sont pas des contrôleurs auxquels on aurait caché la Request.

Responsable Entrée → résultat Où approfondir
Console Nom de commande, Input et Output → exécution et code de sortie Console
Messenger Message et middleware configurés → traitement immédiat ou envoi Messenger
Transport et worker Messages reçus → handlers, acknowledgements ou échecs selon configuration Workers
EventDispatcher Événement dispatché → listeners enregistrés, selon priorité et propagation Événements

Un subscriber est une classe qui déclare ses abonnements, pas simplement un fichier de configuration. Le dispatcher n’est pas un transport Messenger. Un dispatch Messenger sans sender routé peut appeler le handler immédiatement ; une réponse HTTP d’acceptation ne prouve pas qu’un import différé est fini.

🌍 In Real Life

La situation : le responsable lance un inventaire depuis le bureau ; une tâche peut être faite immédiatement ou déposée dans un circuit de travail différé.

L’équivalent dans Symfony : lancement au bureau → Console/Input/Output/code de sortie ; consigne → message ; acheminement → transport ; reprise des tâches → worker et handlers ; annonce interne → EventDispatcher et listeners.

Retour à la réalité technique : Console est une entrée distincte de HTTP. Messenger dépend du routage et des middleware : sans sender routé, un handler peut agir immédiatement ; sync:// aussi. Un dispatcher appelle les listeners enregistrés, il n’assure pas une livraison durable. Un subscriber est une classe déclarant ses abonnements.

🧠 Comment le mémoriser : « Transmettre ne dit pas quand traiter. » Image : tâche remise en main propre ou déposée. Réflexe : « Quel sender, transport et consommateur sont configurés ? »

⚠️ À ne pas confondre : EventDispatcher, bus Messenger et worker ne sont pas trois noms de la même chose.
