Objectif

Avant de suivre GET /blog/42, préparons les valeurs que le blog manipulera : un nom d'auteur, des options de lecture et les données d'un import JSON. PHP détermine comment ces valeurs se construisent, se comparent et se transforment ; Symfony ne remplace pas ces règles.

Nous travaillons avec Symfony 8.0, qui exige PHP 8.4 au minimum, et étudions les API du langage jusqu'à 8.4. Dater une fonctionnalité permettra de lire les exemples et les questions de certification sans confondre version d'introduction et version requise par l'application.

Plan en cinq étapes : (1) les nouveautés 8.4 du cœur du langage (hooks, visibilité asymétrique, lazy objects), (2) un rappel daté des versions 8.0 à 8.3, (3) arrays, comparaisons et JSON, (4) les fonctions ajoutées par version, (5) les pièges.

L'essentiel

À comprendre

À retenir en priorité
  1. private(set) limite qui écrit, pas le nombre d'écritures.
  2. readonly interdit la réaffectation après initialisation.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. La certification interroge sur des API PHP datées : « depuis quelle version ? », « que rend cette fonction ? ». Sans repère de version, on mélange 8.1 (readonly), 8.3 (#[\Override]) et 8.4 (hooks).
  • Le piège de fond. Deux outils qui se ressemblent répondent à des besoins différents : readonly (interdire de remplacer) contre private(set) (limiter qui écrit) ; array_merge() contre + (qui gagne, et que deviennent les clés).
  • Pourquoi c'est à l'examen. Les QCM donnent un petit code et demandent la sortie exacte : elle ne dépend pas de Symfony, seulement des règles PHP.

Nous allons répondre à trois problèmes successifs. D'abord, comment exposer une valeur calculée sans maintenir deux copies du nom d'auteur ? Ensuite, qui peut modifier une donnée, et combien de fois ? Enfin, comment préserver le sens des clés et des types lorsqu'un import transforme des arrays ?

PHP 8.4 apporte notamment les property hooks, code associé à la lecture ou à l'écriture d'une propriété, et la visibilité asymétrique, qui sépare les droits de lecture et d'écriture. Cela ne rend pas les mécanismes antérieurs obsolètes : readonly, introduit pour les propriétés en 8.1, répond à un autre besoin que private(set).

Pour les collections, garde la même discipline : array_merge() et + ne sont pas deux orthographes d'une fusion identique. Choisir la bonne opération évite de perdre un identifiant ou d'écraser une option explicite.

L'exemple : un property hook

Exemple concret

À retenir en priorité
  1. Le get hook calcule fullName à partir de first et last.
  2. Le set hook répartit la valeur affectée ; il ne s'agit pas d'une method appelée explicitement.

Où en est-on ? Étape 1 sur 5 : on traduit le schéma en code. Question : où est stockée la valeur de fullName ? (Réponse attendue : nulle part.)

La classe locale Person matérialise ce modèle réduit. Le hook set reçoit la valeur affectée dans $value, puis la répartit ; get construit la valeur lue à partir des deux champs :

class Person
{
    public string $first = '';
    public string $last = '';

    public string $fullName {
        get => $this->first.' '.$this->last;
        set { [$this->first, $this->last] = array_pad(explode(' ', $value, 2), 2, ''); }
    }
}

Après cette déclaration, voici les opérations du diagramme :

$author = new Person();
$author->fullName = 'Ada Lovelace';
echo $author->first, "\n";
echo $author->fullName, "\n";
$author->first = 'Augusta';
echo $author->fullName, "\n";

La sortie est Ada, Ada Lovelace, puis Augusta Lovelace. La dernière lecture tient compte du changement de first parce que get recalcule le résultat. explode(..., 2) limite le découpage à deux parties et array_pad() fournit une seconde string vide si nécessaire. Ce code PHP prépare une donnée d'affichage ; il n'envoie aucune Response.

$author->fullName = 'Ada Lovelace'      echo $author->fullName
        │                                        │
   hook set { ... }                         hook get => ...
   [first, last] = ['Ada','Lovelace']       first.' '.last
        │                                        │
        ▼                                        ▼
   STOCKÉ : first, last                    CALCULÉ à chaque lecture
   (fullName n'a pas de case mémoire : propriété VIRTUELLE)

🌍 In Real Life

La situation : un afficheur recompose un nom depuis deux cases à chaque consultation ; il ne conserve pas une troisième fiche à synchroniser.

L’équivalent dans Symfony : cases stockées → first/last ; afficheur → propriété virtuelle fullName ; saisie répartie → hook set ; affichage recalculé → hook get.

Retour à la réalité technique : ce mécanisme est PHP 8.4, utilisable dans les objets du blog. La forme courte set peut créer une valeur adossée et changer ce modèle ; aucun cache ni validation générale des noms n'est implicite.

🧠 Comment le mémoriser : « Calculer la vue, stocker les sources. » Image mentale : afficheur alimenté par deux cases. Question-réflexe : où la valeur est-elle réellement stockée ?

⚠️ À ne pas confondre : propriété virtuelle, cache applicatif et réponse HTTP.

Ce que 8.4 ajoute au cœur du langage

À retenir en priorité
  1. Le hook get s'exécute à chaque lecture.
  2. Une property virtuelle ne stocke pas automatiquement le résultat.
  3. private(set) limite qui écrit, pas le nombre d'écritures.
  4. readonly interdit la réaffectation après initialisation.

Où en est-on ? Étape 1 sur 5 (suite) : le hook fullName est le premier des trois apports 8.4 du cœur du langage ; voici le détail des trois (hooks, visibilité asymétrique, lazy objects), plus deux petits ajouts.

Property hooks. Un accessor est ici le code associé à un accès en lecture ou écriture. Aucun hook de Person ne lit ni n'écrit $this->fullName : cette propriété est virtuelle, sans stockage propre. Ne remplace pas mécaniquement le bloc set { ... } par set => expr : la forme courte écrit le résultat de l'expression dans la valeur adossée. Avec set => $this->first = …, par exemple, cette valeur serait le prénom. La propriété devient alors adossée ; ce n'est plus le même modèle de stockage.

Propriété virtuelle Propriété adossée (backed)
Stockage propre non (aucun hook ne touche $this->prop) oui (un hook y lit ou écrit)
set { ... } (bloc) libre : répartit dans d'autres propriétés à vous d'écrire la valeur
set => expr (forme courte) — le résultat de expr devient la valeur stockée

Visibilité asymétrique. Le nom calculé a résolu un problème de synchronisation, pas de droits d'écriture. Pour exposer un titre tout en réservant ses modifications à sa classe, public private(set) string $title sépare ces deux droits. protected(set) ouvre aussi l'écriture à la hiérarchie. Les écritures permises peuvent se répéter : ce n'est pas la contrainte d'initialisation de readonly.

Et aussi : un lazy object retarde son initialisation jusqu'à une opération qui la nécessite, typiquement l'accès à une propriété. Ce n'est pas simplement « toute méthode appelée initialise l'object ». L'attribute natif #[\Deprecated] signale l'usage d'une fonction, méthode ou constante de classe dépréciée ; il ne retarde aucune initialisation. Enfin, new Foo()->method() devient valide sans parenthèses autour de new Foo() en 8.4, mais reste une erreur de syntaxe en 8.3.

Gardons l'exemple isolé Product pour observer ensemble initialisation différée, titre modifiable par sa classe et lecture calculée. Un ghost est ici l'object dont les propriétés seront initialisées à la demande :

class Product
{
    public private(set) string $title;

    public function __construct(string $title)
    {
        $this->title = $title;
    }

    public string $label {
        get => strtoupper($this->title);
    }

    public function rename(string $title): void
    {
        $this->title = $title;
    }
}

$initializations = 0;
$product = new ReflectionClass(Product::class)->newLazyGhost(
    static function (Product $product) use (&$initializations): void {
        ++$initializations;
        $product->__construct('livre');
    },
);
echo $initializations, "\n";
echo $product->label, "\n";
echo $initializations, "\n";
$product->rename('cahier');
echo $product->label, "\n";

La sortie est 0, LIVRE, 1, puis CAHIER. La lecture de label conduit à l'accès à title, qui nécessite l'initialisation ; le callback appelle ici explicitement le constructor. Le changement suivant est autorisé depuis rename(), et la nouvelle lecture recalcule le libellé. strtoupper() suffit aux mots ASCII de cet exemple, pas à une promesse générale de conversion Unicode.

newLazyGhost(initializer)  →  $product existe, MAIS vide (compteur = 0)
echo $product->label       →  get lit $this->title
                              → accès à une propriété non initialisée
                              → l'initializer s'exécute UNE fois (compteur = 1)
                              → __construct('livre') remplit title
                              → label = 'LIVRE'
rename('cahier')           →  écriture permise (dans la classe) → 'CAHIER'

Cette expérience ne configure aucun service du blog. DependencyInjection peut exploiter les lazy objects pour des services lazy, mais un hook PHP ne déclare ni service ni chargement différé à lui seul.

🌍 In Real Life

La situation : un dossier est repéré avant d'être rempli ; sa préparation attend qu'une opération ait réellement besoin de ses données.

L’équivalent dans Symfony : dossier repéré → lazy ghost ; remplissage différé → initializer ; donnée nécessaire → accès déclenchant l'initialisation dans le laboratoire.

Retour à la réalité technique : la lecture de label accède à title, puis le callback appelle explicitement le constructeur. Toute méthode ne déclenche pas forcément l'initialisation. Un hook ne rend pas seul un service lazy et ne l'enregistre pas dans le container.

🧠 Comment le mémoriser : « Exister avant d'être initialisé. » Image mentale : dossier identifié encore vide. Question-réflexe : quelle opération exige maintenant les propriétés ?

⚠️ À ne pas confondre : initialisation différée PHP et lecture différée d'une Response HttpClient.

Repère de l’exemple : Le get hook calcule fullName à partir de first et last. Le set hook répartit la valeur affectée ; il ne s'agit pas d'une method appelée explicitement.

Rappel des versions antérieures

Où en est-on ? Étape 2 sur 5 : on remonte le temps. Le titre modifiable nous ramène à une distinction plus ancienne ; le tableau date les outils que l'on croise dans le code Symfony. Question : quelle version a introduit quoi ?

Le titre modifiable nous ramène à une distinction plus ancienne : la possibilité de lire une valeur ne dit pas si on peut la remplacer. Le tableau date les outils rencontrés ; les lignes antérieures à 8.4 ne sont pas des runtimes alternatifs pour Symfony 8.0.

Version Apports les plus examinables
8.0 Named arguments, promotion de constructor, match, types union, ?->, static en return type
8.1 Enums, readonly, never, callable de première class foo(...), constantes de class final
8.2 readonly sur la class entière, types DNF, properties dynamiques dépréciées
8.3 Constantes de class typées, #[\Override], json_validate()

Les named arguments associent une valeur au nom du paramètre plutôt qu'à sa position ; la promotion déclare et initialise une propriété dans la signature du constructor. match compare strictement ses branches, un type union accepte l'un des types annoncés, ?-> arrête la chaîne d'accès si son object vaut null, et le type de retour static désigne la classe appelée.

Avec 8.1, une enum ferme la liste des choix, never annonce qu'une fonction ne revient pas normalement et foo(...) acquiert un callable sans l'appeler. Une constante final ne peut pas être redéfinie dans une classe enfant. En 8.2, les types DNF combinent unions et intersections, par exemple (A&B)|C : un object répond à la fois à A et B, ou à C. La dépréciation des propriétés dynamiques concerne leur création dans les cas ordinaires ; elle ne remplace pas les propriétés déclarées.

Cet exemple indépendant Price rend visible la différence entre une valeur fixée et une valeur dont l'écriture reste réservée à la classe :

final class Price
{
    public function __construct(
        public readonly int $amount,
        public private(set) string $currency,
    ) {}

    public function changeCurrency(string $currency): void
    {
        $this->currency = $currency;
    }
}

$price = new Price(currency: 'USD', amount: 12);
$price->changeCurrency('GBP');
$price->changeCurrency('EUR');
echo $price->amount, ' ', $price->currency, "\n";

Il affiche 12 EUR : promotion et arguments nommés viennent de 8.0, readonly de 8.1 et private(set) de 8.4. Les deux écritures de currency sont permises, alors que le montant reste fixé. Ce n'est pas une conversion monétaire ni un modèle de facturation : le détour sert uniquement à isoler les règles d'affectation. Pour ArticleView, pose la même question avant de choisir un modificateur : faut-il interdire le remplacement de la valeur ou seulement limiter qui peut l'écrire ?

readonly private(set)
Depuis PHP 8.1 PHP 8.4
Question posée peut-on remplacer la valeur ? qui peut l'écrire ?
Écritures répétées dans la classe non (une initialisation) oui
Écriture depuis l'extérieur non non

Comme un mécanicien reconnaît le millésime d'une pièce, dater la syntaxe permet de choisir la bonne règle : match évoque 8.0, enum 8.1, readonly class 8.2, Override 8.3 et private(set) 8.4.

Arrays, comparaisons et JSON : ce que renvoie PHP

À retenir en priorité
  1. L'opérateur + conserve la valeur de gauche.
  2. array_merge() remplace une string key par la valeur de droite.

Où en est-on ? Étape 3 sur 5 : on quitte les objets pour les données de l'import. Question à garder : quelles clés survivent, et qui gagne en cas de doublon ?

L'import prépare maintenant plusieurs valeurs à la fois. Un array PHP associe des clés à des valeurs : il n'est pas forcément une liste numérotée sans trous. Si ses clés sont des identifiants d'articles, les renuméroter changerait leur sens. Si ce sont des options nommées, il faut décider quelle source gagne lorsqu'une clé apparaît deux fois.

Avec array_merge(), les valeurs à clés numériques sont rassemblées et renumérotées ; une même clé textuelle prend la dernière valeur. Avec +, les associations de gauche gagnent et seules les clés absentes sont ajoutées. Lis donc les clés réelles avant de lire les valeurs :

Expression Résultat
array_merge(['a'], ['b']) ['a', 'b'] — keys numériques renumérotées
['a'] + ['b'] ['a'] — la key 0 existe déjà à gauche
array_merge(['k' => 1], ['k' => 2]) ['k' => 2] — la dernière string key gagne
['k' => 1] + ['k' => 2] ['k' => 1] — + garde la gauche
array_filter([1, 0, 2, null, '0', 'a']) [0 => 1, 2 => 2, 5 => 'a'] — keys conservées
array_map($f, ['k' => 1]) key k conservée ; réindexée dès deux arrays 
        array_merge($left, $right)            $left + $right
 clé texte en double : DROITE gagne     clé en double : GAUCHE gagne
 clés numériques : RENUMÉROTÉES         clés numériques : conservées,
                                         seules les clés ABSENTES s'ajoutent

Le filtre sans callback retire les valeurs considérées fausses, dont 0, null et '0', mais ne renumérote pas les clés. Il ne convient donc pas tel quel si zéro est une donnée valide à conserver. array_map() transforme les valeurs ; un seul array conserve ses clés, plusieurs arrays produisent un résultat réindexé.

PHP 8 compare un nombre et une string non numérique comme deux strings : 0 == 'a' et 0 == '' valent false. Deux strings numériques restent comparées comme des nombres : '1' == '01' vaut true. La comparaison souple == peut donc masquer une différence de représentation. === exige aussi le même type ; in_array() utilise == par défaut, mais une comparaison stricte si son troisième argument vaut true.

json_decode() transforme un texte JSON, pas un array déjà présent. Un object JSON devient un stdClass par défaut, ou un array avec true en second argument. Sans JSON_THROW_ON_ERROR, un JSON invalide peut donner null, tout comme le texte JSON valide null. Il faut donc contrôler l'erreur ou demander une exception, puis valider la structure et les types attendus : une syntaxe JSON valide ne prouve pas qu'un article exploitable a été fourni.

Cette expérience réduit l'import à des valeurs fixes pour observer fusion, filtrage, comparaison et décodage sans dépendance Symfony :

$left = ['mode' => 'old', 0 => 'a'];
$right = ['mode' => 'new', 0 => 'b'];
var_export(array_merge($left, $right));
echo "\n";
var_export($left + $right);
echo "\n";
var_export(array_filter([1, 0, 2, null, '0', 'a']));
echo "\n";
var_dump(0 == 'a', '1' == '01');
var_dump(in_array('1', [1]), in_array('1', [1], true));
$data = json_decode('{"count":2}', true, flags: JSON_THROW_ON_ERROR);
echo $data['count'], "\n";
try {
    json_decode('{', flags: JSON_THROW_ON_ERROR);
} catch (JsonException) {
    echo "invalid JSON\n";
}

La fusion affiche ['mode' => 'new', 0 => 'a', 1 => 'b'], l'union ['mode' => 'old', 0 => 'a'], puis le filtre conserve les clés 0, 2, 5. Les quatre booléens sont false, true, true, false. Le décodage termine par 2 puis invalid JSON. Ces sorties ne sont ni des status codes HTTP ni des validations métier ; elles permettent au code appelant de prendre sa décision.

🌍 In Real Life

La situation : réunir des fiches en une nouvelle pile numérotée n'est pas compléter un registre en conservant ses numéros et ses choix déjà inscrits.

L’équivalent dans Symfony : pile renumérotée → array_merge pour clés numériques ; registre gardant la gauche → union + ; cases textuelles remplacées par la droite → array_merge.

Retour à la réalité technique : les clés peuvent être des identifiants, pas des positions jetables. Filter conserve les clés et, sans callback, retire aussi zéro. Comparer strictement et vérifier le décodage JSON évitent d'assimiler des représentations différentes ; aucune opération ne valide l'article.

🧠 Comment le mémoriser : « Préserver le numéro ou refaire la pile ? » Image mentale : registre identifié face à une pile renumérotée. Question-réflexe : quelle source gagne et quelles clés doivent survivre ?

⚠️ À ne pas confondre : JSON syntaxiquement valide, structure attendue et donnée métier autorisée.

Functions ajoutées, par version

À retenir en priorité
  1. array_find() rend une valeur, pas une key.
  2. Le callback reçoit valeur puis key.

Où en est-on ? Étape 4 sur 5 : les données sont transformées ; reste à les chercher sans confondre valeur et clé, et à dater les fonctions correspondantes. Question : quel type de résultat veut mon appelant ?

Nous savons transformer les données ; il reste à chercher un élément sans confondre sa valeur avec sa clé. La bibliothèque PHP fournit des fonctions nommées pour ces opérations. Leur date d'introduction reste une question distincte de leur résultat :

Version Functions
8.0 str_contains(), str_starts_with(), str_ends_with()
8.1 array_is_list()
8.3 json_validate()
8.4 array_find(), array_find_key(), array_any(), array_all(), mb_trim(), mb_ucfirst()

Les trois fonctions de string de 8.0 testent respectivement la présence, le début et la fin d'un texte. array_is_list() vérifie que les clés sont exactement 0 à count - 1, dans cet ordre ; l'array vide est une liste. json_validate() vérifie la syntaxe JSON sans fournir la donnée décodée. Si l'import a besoin de cette donnée, décoder avec gestion d'erreur évite une validation syntaxique préalable redondante.

En 8.4, array_find() rend la première valeur acceptée, ou null ; array_find_key() rend sa clé, ou null en l'absence de correspondance. Le callback, fonction appelée pour tester chaque élément, reçoit la valeur puis la clé. array_any() demande si au moins un élément convient ; array_all() si tous conviennent. Ces recherches peuvent s'arrêter dès que leur réponse est déterminée, sans construire un array filtré.

Fonction (8.4) Question Rend
array_find() première valeur acceptée ? la valeur ou null
array_find_key() clé de cette valeur ? la clé ou null
array_any() au moins un élément convient ? bool
array_all() tous conviennent ? bool

Gardons les quantités d'un petit stock pour rendre clé et valeur immédiatement différentes :

$stock = ['east' => 3, 'west' => 12, 'north' => 20];
$enough = static fn (int $quantity, string $key): bool => $quantity > 10;
var_dump(array_find($stock, $enough));
var_dump(array_find_key($stock, $enough));
var_dump(array_any($stock, $enough));
var_dump(array_all($stock, $enough));
var_dump(array_all([], $enough));
var_dump(array_is_list($stock));

La sortie est int(12), string(4) "west", bool(true), bool(false), bool(true), bool(false). Le callback n'utilise pas $key dans son test, mais la reçoit. Sur un array vide, aucun élément ne contredit all, donc le résultat est vrai ; aucun ne satisfait any, donc son résultat serait faux. Cela ne prouve pas qu'un import contient des données.

Autre limite : si null est une valeur acceptée dans l'array, le résultat de array_find() seul ne distingue pas cette correspondance de l'absence de résultat. Choisis la recherche de clé lorsque cette distinction compte. Enfin, mb_trim() et mb_ucfirst() nécessitent l'extension mbstring ; leur présence dans la ligne 8.4 n'en garantit pas l'activation dans chaque environnement.

🌍 In Real Life

La situation : devant un stock, on peut demander la première quantité suffisante, son emplacement, s'il en existe une ou si toutes suffisent.

L’équivalent dans Symfony : quantité → array_find ; emplacement → array_find_key ; existence → array_any ; universalité → array_all.

Retour à la réalité technique : ces fonctions PHP 8.4 peuvent s'arrêter dès la réponse connue. Sur le vide, all vaut true et any false ; cela ne prouve pas qu'un import contient des lignes. Une valeur null trouvée impose de distinguer correspondance et absence, notamment par la clé.

🧠 Comment le mémoriser : « Valeur, clé, au moins une, toutes. » Image mentale : quantité et adresse sur une étagère. Question-réflexe : quel type de résultat mon appelant attend-il ?

⚠️ À ne pas confondre : recherche dans une collection déjà chargée et chargement d'un article par un service.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Étape 5 sur 5 : les erreurs que les QCM exploitent, avec la raison pour laquelle elles semblent plausibles.

  • Voir l’explication : readonly n'est pas private(set).

    readonly n'est pas private(set). Dans les affectations ordinaires, une propriété readonly ne s'initialise qu'une fois ; depuis PHP 8.4, elle est implicitement protected(set), donc une classe enfant peut l'initialiser. Cela ne donne pas le droit de la remplacer ensuite. private(set) seul autorise des écritures répétées depuis la classe. La règle vise la propriété : elle ne fige pas profondément l'object qu'elle contient. Le cas particulier de réinitialisation pendant __clone(), depuis PHP 8.3, est détaillé dans le cours objet. Pourquoi on se trompe : les deux limitent l'écriture, on les croit interchangeables.

  • Voir l’explication : Les property hooks ne sont pas des properties calculées mises en cache.

    Les property hooks ne sont pas des properties calculées mises en cache. Le hook get s'exécute à chaque lecture. Person et Product montrent pourquoi une modification des données sous-jacentes change le résultat : aucun cache de fullName ou de label n'a été créé implicitement. Pourquoi on se trompe : « propriété calculée » évoque une valeur mémorisée.

  • Voir l’explication : #[\Override] est 8.3, pas 8.4.

    #[\Override] est 8.3, pas 8.4. Il vérifie qu'une method surcharge bien une méthode héritée ou implémente un contrat de méthode d'interface ; sinon, erreur de compilation. Cette vérification protège notamment contre un renommage mal répercuté. Elle ne garantit pas que le comportement de la méthode est correct. Pourquoi on se trompe : il est souvent cité avec les nouveautés « récentes » de 8.4 (hooks, #[\Deprecated]).

  • Voir l’explication : array_merge() n'est pas +.

    array_merge() n'est pas +. Les clés numériques sont renumérotées par array_merge() mais conservées par + (la gauche gagne). Pourquoi on se trompe : les deux « fusionnent ».

  • Voir l’explication : new Foo()->m() sans parenthèses

    new Foo()->m() sans parenthèses : valide en 8.4, erreur de syntaxe en 8.3.

Conserver les options et les identifiants du blog

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Sous-section de conception : appliquer la discipline des clés aux options et aux identifiants du blog.

  • Conserver le choix de pagination de l’appelant

    Revenons au blog. L'appelant a choisi une taille de page ; le code fournit aussi un tri par défaut. L'union conserve le choix explicite :

$options = ['limit' => 5];
$defaults = ['limit' => 10, 'order' => 'newest'];
$effective = $options + $defaults;
var_export($effective);
  • Union d’options et validation métier

    Le résultat est ['limit' => 5, 'order' => 'newest']. L'opération n'est pas récursive et ne valide pas les options : les règles de pagination de /blog/page/{page} doivent encore contrôler les valeurs reçues.

  • Rechercher une valeur sans perdre les identifiants

    Pour retrouver le premier article satisfaisant une condition dans une collection déjà chargée, array_find() est disponible en 8.4. Si les clés représentent les identifiants, préserve-les au lieu de choisir array_merge() par habitude. L'existence de l'article 42 ou l'absence de 999 relève ensuite d'ArticleCatalog ; ces fonctions PHP ne fabriquent ni une page ni une erreur HTTP.

  • Réaffectation et portée d’écriture

    readonly interdit une réaffectation après initialisation ; private(set) limite la portée d’écriture, sans limiter le nombre d’écritures depuis cette portée.
