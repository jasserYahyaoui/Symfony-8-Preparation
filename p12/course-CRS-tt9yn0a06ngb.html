Objectif

La page /blog/42 dépend de plusieurs décisions : une règle de préparation du titre, un service correctement câblé, une route et une vue correctes. Un seul test HTTP ne localise pas toutes les régressions. Choisir le plus petit périmètre suffisant permet de savoir ce qui a réellement échoué, avant d'ajouter les vérifications d'intégration et d'application.

Ce cours répond à une question : quel est le plus petit test qui détecte ce défaut, et que faut-il (ou ne faut-il pas) démarrer pour l'écrire ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le test unitaire isole la logique.
  2. Le kernel appartient à une frontière d'intégration.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Quand /blog/42 casse, le coupable peut être un calcul, un câblage de services ou une route. Si le seul test dont on dispose est un appel HTTP complet, il dit « ça casse » mais pas « où ». Symfony range donc les tests par périmètre : plus le périmètre est petit, plus l'échec est précis (et rapide).
  • Le piège de fond. On croit que le type de test dépend du dossier ou du runner. Faux : il dépend du code réellement exécuté. PHPUnit lance les trois catégories ; c'est ce que votre test démarre (un kernel ? un client HTTP ?) qui décide.
  • Ce que l'auteur veut que vous compreniez. Un test unitaire n'a rien de spécifique à Symfony : c'est du PHPUnit ordinaire, sans kernel ni container.
  • Pourquoi c'est à l'examen. Les questions portent sur le vocabulaire (trois types, « functional » = « application »), sur la frontière bootKernel(), sur les noms de fichiers de configuration PHPUnit et sur le suffixe Test.

La documentation Symfony distingue trois types de tests : unitaire, intégration, application. La mise en place peut utiliser PHPUnit directement comme dépendance de développement et vendor/bin/phpunit, sans intégration supplémentaire pour l'unitaire. La convention tests/ reproduit src/.

Le périmètre vient du code exécuté, pas du nom du dossier ni du runner : PHPUnit peut lancer les trois catégories. Un test isolé d'ArticleCatalog en mémoire peut vérifier 42 présent et 999 absent ; il ne prouve pas que blog_show appelle ce catalogue ou transforme l'absence en HTTP 404.

Le schéma

À retenir en priorité
  1. Chaque base correspond à un scope.
  2. Choisir la plus légère adaptée au comportement.

Où en est-on ? Début du cours : avant d'écrire une ligne de test, il faut savoir lequel écrire. Le schéma ci-dessous est un arbre de décision, pas une chaîne d'appels : on part du défaut que l'on veut détecter.

Partir du défaut que l'on veut détecter : mauvais résultat de calcul, mauvais assemblage de services, ou mauvais comportement de la page. Les trois branches ne sont pas trois étapes à exécuter systématiquement :

Ambre : besoin à vérifier ; vert : périmètre choisi. Ne démarrer le kernel que si son câblage fait partie du comportement testé : un test isolé du calcul doit échouer sur une mauvaise addition, pas sur une configuration de services.

Les trois périmètres sont emboîtés : chacun inclut davantage de code que le précédent.

┌────────────────────────────────────────────────────────────────────┐
│ APPLICATION (WebTestCase)  route → controller → vue → Response      │
│  ┌───────────────────────────────────────────────────────────────┐ │
│  │ INTÉGRATION (KernelTestCase)  kernel + container + services    │ │
│  │  ┌─────────────────────────────────────────────────────────┐  │ │
│  │  │ UNITAIRE (TestCase)  une class, une method, aucun kernel │  │ │
│  │  └─────────────────────────────────────────────────────────┘  │ │

L'exemple : un calcul

Exemple concret

À retenir en priorité
  1. La construction locale garde le test isolé.
  2. Aucune configuration du kernel n'est requise.

Où en est-on ? On passe du choix du niveau à son écriture, avec le niveau le plus simple : l'unitaire. Pour isoler la mécanique de l'assertion, conservons un calcul connu plutôt qu'un gros exemple métier.

Le test prépare les entrées 30 et 12, appelle add(), puis exige un résultat entier ; ce n'est pas un test de la réponse HTTP du blog :

use App\Util\Calculator;
use PHPUnit\Framework\TestCase;

// tests/Util/CalculatorTest.php — reflète src/Util/Calculator.php
class CalculatorTest extends TestCase
{
    public function testAdd(): void
    {
        $this->assertSame(42, (new Calculator())->add(30, 12));
    }
}

Aucun kernel n'est démarré, aucun container n'est construit.

Ce que PHPUnit voit : une classe dont le nom finit par Test, qui étend TestCase, avec une méthode publique testAdd() (préfixe test). Il l'instancie, l'appelle, et l'assertion décide du verdict. Aucune étape Symfony n'intervient.

Le fragment suppose Calculator::add(int, int): int dans l'application et les imports de Calculator et PHPUnit\Framework\TestCase. Le résultat attendu est l'entier 42 : assertSame rejette aussi la chaîne "42" (il compare avec ===, type compris). Les exemples de résolution des fichiers de configuration ci-dessous ciblent PHPUnit 11.5, utilisable ici avec PHP 8.4. Un résultat simplement imprimé ne devient pas une assertion : le test doit comparer le contrat attendu au résultat.

Trois types, trois périmètres

À retenir en priorité
  1. Le container assemble plusieurs services.
  2. La frontière du test s'élargit.
  3. Une ligne de provider produit une exécution du test.
  4. Le provider public static fournit des données, pas un kernel de test.

Où en est-on ? Étape 1 sur 3 : on nomme précisément les trois types de tests de la documentation et on voit ce que chacun démarre. C'est la partie la plus interrogée à l'examen.

🌍 In Real Life

La situation : au restaurant, on peut vérifier une balance seule, son intégration au poste de préparation ou le service d'une commande complète.

L’équivalent dans Symfony : règle isolée → test unitaire ; services assemblés → test d'intégration ; entrée /blog/42 jusqu'à sa réponse → test d'application.

Retour à la réalité technique : démarrer le Kernel franchit une frontière que le test unitaire isolé n'utilise pas. Tester une réponse via KernelBrowser ne teste toutefois pas un navigateur JavaScript ni toute l'infrastructure réseau.

🧠 Comment le mémoriser : « Instrument, assemblage, service rendu. » Image mentale : trois cadres de largeur croissante. Question-réflexe : quelle frontière doit franchir ce test pour détecter le défaut ?

⚠️ À ne pas confondre : plusieurs assertions et plusieurs niveaux de test.

Type Ce qu'il couvre Class de base
Unitaire une class, une method TestCase de PHPUnit
Intégration plusieurs classes ensemble, souvent via le container KernelTestCase
Application l'application complète, de la route à la vue WebTestCase

Comparaison de ce que chaque niveau démarre :

Unitaire Intégration Application
Kernel démarré ? non oui (bootKernel()) oui (via le client)
Container disponible ? non oui oui
Requête HTTP simulée ? non non oui (createClient())
Ce qu'un échec désigne la logique d'une class un mauvais câblage route, controller ou vue
Configuration Symfony requise aucune KERNEL_CLASS KERNEL_CLASS

« Test d'application » et functional test sont synonymes. Un test qui appelle bootKernel() franchit la frontière d'intégration ; sans kernel désigné, il échoue — « You must set the KERNEL_CLASS environment variable… » —, alors qu'un TestCase isolé n'a pas besoin de cette configuration Symfony. KERNEL_CLASS est la voie par défaut ; surcharger getKernelClass() ou createKernel() est une autre manière explicite de désigner le kernel.

Pourquoi KernelTestCase a-t-il besoin de KERNEL_CLASS ? Parce que bootKernel() doit instancier un kernel, et PHPUnit ne sait pas quelle classe de votre application c'est. getKernelClass() lit donc la variable d'environnement (fournie par défaut dans .env.test par Symfony Flex) ; si elle manque, il lève une LogicException dont le message commence par « You must set the KERNEL_CLASS environment variable… ». Il vous propose aussi la sortie de secours : surcharger createKernel() ou getKernelClass(). Le KernelTestCase redémarre aussi le kernel à chaque test, pour que les tests restent indépendants.

bootKernel()
   ↓
getKernelClass() : KERNEL_CLASS défini ?
   ├─ non → LogicException « You must set the KERNEL_CLASS… »
   └─ oui → la classe existe ? non → RuntimeException
                               oui → kernel créé, démarré

Pour une ligne d'import, supprimer des espaces est une règle distincte de l'interdiction de publier un titre vide. Cet exemple complet de logique isolée conserve deux attentes différentes ; PHPUnit 11.5 doit être chargé :

<?php
use PHPUnit\Framework\TestCase;

final class Label
{
    public static function normalize(string $value): string
    {
        return trim($value);
    }
}

final class LabelTest extends TestCase
{
    public function testRemovesSurroundingSpaces(): void
    {
        self::assertSame('Bonjour', Label::normalize(' Bonjour '));
    }

    public function testAllowsEmptyLabel(): void
    {
        self::assertSame('', Label::normalize('   '));
    }
}

Le second cas affirme que cette normalisation accepte un résultat vide ; il ne déclare pas ce titre publiable. Une validation métier se teste séparément. Modifier seulement l'addition ne doit pas faire échouer ces tests de libellé, et une erreur de services ne doit pas les empêcher de démarrer.

Pour plusieurs jeux d'entrées, un data provider fournit des tableaux d'arguments. En PHPUnit 11.5, #[DataProvider('cases')] désigne une méthode public static cases() renvoyant un iterable de tels tableaux ; chaque ligne donne une exécution du test. Le provider s'exécute avant setUp() : y préparer des données, pas un kernel ou un graphe de services dépendant de l'initialisation du test.

Pourquoi le provider ne peut-il pas utiliser ce que prépare setUp() ? PHPUnit doit connaître toutes les lignes de données avant de créer et d'exécuter les tests ; il appelle donc le provider d'abord, puis seulement setUp() pour chaque exécution.

Un data provider PHPUnit permet d'exécuter le même test unitaire sur plusieurs cas, sans démarrer le kernel. Dans le contrat PHPUnit 11.5 utilisé ici, #[DataProvider('cases')] désigne une method public static qui retourne un iterable d'arrays d'arguments ; chaque ligne devient une exécution distincte. Préparer les données dans ce provider ne remplace pas l'arrangement des services dans le test lui-même.

L'installation

À retenir en priorité
  1. La configuration locale est prioritaire.
  2. La version dist fournit le réglage partagé.

Où en est-on ? Étape 2 sur 3 : le périmètre unitaire est choisi, il faut maintenant disposer de PHPUnit et comprendre quelle configuration il lit.

Sur un projet de développement préparé pour cette démonstration, avec Composer 2 et PHP 8.4, la voie directe conserve le périmètre unitaire :

composer require --dev phpunit/phpunit:^11.5
vendor/bin/phpunit

Résultat attendu : PHPUnit est ajouté aux dépendances de développement, puis le runner découvre la suite configurée et affiche son bilan. Ces commandes sont des instructions d'installation, pas une exécution effectuée pour ce cours. Installer le runner seul ne crée pas automatiquement un bootstrap Symfony, des services de test ou une suite complète. Le projet doit configurer l'autoload, le bootstrap et les répertoires concernés.

Pour information, la documentation 8.0 présente aussi la voie « application Symfony » : composer require --dev symfony/test-pack (qui installe phpunit/phpunit et d'autres paquets de test), puis php bin/phpunit ; Flex crée alors phpunit.dist.xml et tests/bootstrap.php. Le test unitaire, lui, n'exige pas ce lanceur.

Sans option de configuration explicite, PHPUnit 11.5 choisit le premier fichier applicable dans cet ordre :

Files présents à la racine Configuration retenue
phpunit.xml, phpunit.dist.xml, phpunit.xml.dist phpunit.xml
phpunit.dist.xml, phpunit.xml.dist phpunit.dist.xml
phpunit.xml.dist seul phpunit.xml.dist — encore lu

phpunit.xml, généralement non versionné, est choisi à la place du fichier partagé : PHPUnit ne fusionne pas automatiquement les deux configurations.

phpunit.xml ?  ── oui ──► retenu (local, non versionné)
     │ non
phpunit.dist.xml ? ── oui ──► retenu (nom actuel du fichier partagé)
     │ non
phpunit.xml.dist ? ── oui ──► retenu (ancien nom, encore lu)
     │ non
aucune configuration

Pourquoi cet ordre ? Le fichier local (phpunit.xml) permet à chaque développeur d'adapter sa machine sans toucher au fichier partagé (*.dist) versionné. Le nom phpunit.xml.dist est l'ancien nom (avant PHPUnit 10) ; la documentation 8.0 donne phpunit.dist.xml.

Si un test existe mais n'est pas lancé, regarder d'abord la configuration retenue et la découverte avant d'accuser son code. Un fichier local prioritaire peut masquer la suite définie dans le fichier partagé.

Où vivent les tests

À retenir en priorité
  1. La découverte utilise un suffixe.
  2. Un nom proche mais différent peut être ignoré.

Où en est-on ? Étape 3 sur 3 : PHPUnit est installé et configuré ; reste à savoir où poser les fichiers pour qu'ils soient trouvés.

🌍 In Real Life

La situation : l'équipe du blog cherche les fiches de contrôle selon un classement et une terminaison de nom convenus. Une fiche mal étiquetée peut rester sur l'étagère.

L’équivalent dans Symfony : rangement miroir → convention tests/ et src/ ; étiquette reconnue → suffixe de fichier de test ; fiche désignée directement → chemin explicite.

Retour à la réalité technique : PHPUnit découvre les tests selon sa configuration et ses conventions. Une suite réussie ne prouve pas qu'un fichier ignoré a été exécuté ; vérifier aussi les tests effectivement sélectionnés.

🧠 Comment le mémoriser : « Non trouvé n'est pas réussi. » Image mentale : fiche de contrôle restée hors de la pile. Question-réflexe : ce test figure-t-il dans la sélection exécutée ?

⚠️ À ne pas confondre : organisation recommandée et règle de découverte effective.

Dans tests/, dont l'arborescence reproduit par convention celle de src/, chaque class se terminant par Test. Le suffixe compte : en parcourant un directory, avec la découverte conventionnelle, PHPUnit retient CalcTest.php, pas CalcTests.php, qui peut être désigné explicitement.

Avant / après, pour une classe de src/Form/ :

src/Form/UserType.php          ← code testé
tests/Form/UserTypeTest.php    ← test : même sous-dossier, suffixe « Test »
tests/Form/UserTypeTests.php   ← ignoré au parcours de tests/Form (suffixe « Tests »)
vendor/bin/phpunit tests/Form                   # un répertoire
vendor/bin/phpunit tests/Form/UserTypeTest.php   # un fichier

Le premier appel doit lancer les tests découverts du répertoire, le second ce fichier existant. Les noms illustrent le classement, pas une exigence d'utiliser des formulaires pour tester le catalogue. Les options de découverte peuvent être configurées ; ne pas confondre la convention Test.php avec une interdiction absolue de tout autre nom.

La documentation 8.0 ajoute, pour les grosses suites, qu'on peut créer un sous-dossier par type de test (tests/Unit/, tests/Integration/, tests/Application/).

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le vocabulaire décrit le même scope.
  2. Ne pas compter deux niveaux distincts.
  • Voir l’explication : Un unit test ne démarre pas le kernel.

    Un unit test ne démarre pas le kernel. Dès qu'un test appelle bootKernel(), il est d'intégration. Pourquoi on se trompe : le test ne teste qu'une seule class, donc on le croit unitaire ; or le critère est la frontière franchie (le kernel), pas le nombre de classes testées.

  • Voir l’explication : « Functional test » et « test d'application » désignent la même chose

    « Functional test » et « test d'application » désignent la même chose dans le vocabulaire Symfony. Pourquoi on se trompe : « fonctionnel » ressemble à « unitaire » dans le langage courant.

  • Voir l’explication : vendor/bin/phpunit

    vendor/bin/phpunit lance l'installation directe présentée ici. Un lanceur propre au projet n'est pas une exigence du test unitaire.

  • Voir l’explication : Un file …Tests.php est ignoré

    Un file …Tests.php est ignoré par la découverte conventionnelle d'un répertoire ; un fichier explicitement ciblé est un autre cas. Pourquoi on se trompe : on généralise « le suffixe est ignoré » à tous les modes de lancement.

  • Voir l’explication : phpunit.xml passe avant phpunit.dist.xml.

    phpunit.xml passe avant phpunit.dist.xml. Pourquoi on se trompe : on imagine une fusion des deux fichiers ; PHPUnit n'en retient qu'un.

  • Voir l’explication : tests/ reflète src/

    tests/ reflète src/, et les classes se terminent par Test.

Fiche express

À mémoriser

À retenir en priorité
  1. La structure facilite la navigation.
  2. Elle ne prouve pas à elle seule une couverture comportementale.

Le test du titre isole une règle ; celui du conteneur vérifie un assemblage ; celui de /blog/42 protège une entrée publique. Une suite utile combine ces responsabilités sans appeler chaque test « unitaire ».

🧠 À retenir pour la certification :

  • Trois types : unitaire, intégration, application (= functional).
  • Un unit test : TestCase, sans kernel ni container.
  • bootKernel() → frontière d'intégration ; KERNEL_CLASS par défaut, ou désignation explicite via les méthodes prévues (getKernelClass(), createKernel()).
  • PHPUnit directement en développement, puis vendor/bin/phpunit.
  • phpunit.xml > phpunit.dist.xml > phpunit.xml.dist (un seul retenu, pas de fusion).
  • tests/ reflète src/, suffixe Test au parcours d'un répertoire.

Moyen mnémotechnique : « Une class, un kernel, toute l'application » (unitaire → intégration → application). Phrase de mémorisation : le type d'un test se lit à ce qu'il démarre : rien, le kernel, ou une requête complète.

Passer ensuite au test d'application : le catalogue peut être juste alors que la route ou la vue est cassée.
