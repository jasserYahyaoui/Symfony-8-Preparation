Objectif

BlogController::show a trouvé l'ArticleView 42 dans ArticleCatalog. Il doit maintenant transformer ce résultat applicatif en contenu, statut et en-têtes HTTP. Le même article peut alimenter une page HTML ou une réponse JSON ; ce sont deux sorties possibles, pas deux opérations obligatoires successives.

Produire la Response depuis un controller, et choisir le bon raccourci. Le catalogue des sous-classes de Response et les methods de test de statut appartiennent au Module 02 — Fondamentaux HTTP.

Question fil rouge : mon action a fini son travail ; que doit-elle rendre à Symfony, et quel raccourci d'AbstractController fabrique le bon objet ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le contrat final exige une Response.
  2. Une string seule n'est pas une Response.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le contrat d'HttpKernel est simple : une action doit rendre une Response. Mais fabriquer une Response à la main est fastidieux ; AbstractController offre des raccourcis (render, json, file, stream…) et chacun a un type de retour précis.
  • Le piège de fond. Les noms se ressemblent (render / renderView) mais les retours diffèrent : une Response contre une simple string. Retourner la string déclenche kernel.view, qui échoue s'il n'y a pas de listener.
  • Ce que l'auteur veut que vous compreniez. Que le contrôleur n'« envoie » rien : il retourne un objet ; le kernel et le front controller se chargent de la suite. Et que render() fait un travail discret mais important avec les formulaires (422).
  • Pourquoi c'est à l'examen. Types de retour des helpers, conditions exactes du 422, valeur null de json(), disposition attachment de file().

En résumé : un controller retourne une Response ; sinon, kernel.view doit convertir la valeur. Les raccourcis d'AbstractController se distinguent par leur return type : render() rend une Response, renderView() une string, file() une BinaryFileResponse qui télécharge par défaut. Le piège central est le 422 automatique, qui exige trois conditions à la fois.

Les sous-classes de Response et ses méthodes de test de statut sont dans le module HTTP ; les redirections (autre type de Response) ont leur cours : HTTP redirects. Les helpers appartiennent à The base AbstractController class.

Le schéma

À retenir en priorité
  1. render() convient au retour du controller.
  2. renderView() fournit uniquement le contenu.

Où en est-on ? Le cours suit quatre étapes : la règle (que doit rendre l'action ?), rendre un template, JSON, servir un file. Le premier schéma traite l'étape 1 : que devient la valeur retournée ? Le second est un guide de choix des raccourcis pour les étapes 2 à 4.

Le retour d'un controller
   ├─ 1. La règle            → Response, sinon kernel.view
   ├─ 2. Rendre un template  → render() / renderView() / stream()
   ├─ 3. JSON                → json()
   └─ 4. Servir un file      → file()

Où en est-on ? Une fois la règle comprise, le second schéma sert de carte : selon la donnée à produire (template, JSON, fichier), quel helper choisir et que se passe-t-il pour les formulaires.

Ambre = décision ; bleu = traitement ou résultat. Ces helpers construisent des réponses : ils ne garantissent pas un envoi immédiat. stream() diffère le rendu jusqu'à l'exécution de son callback ; il ne suit pas la conversion automatique des formulaires ni le contrôle 422 de render(). La réponse facultative est le troisième argument de render(), mais le quatrième de renderBlock(view, block, parameters, response).

L'exemple : un form, deux issues

Exemple concret

À retenir en priorité
  1. Un form non soumis ne déclenche pas 422.
  2. Un statut explicite n'est pas remplacé par cette règle.

Où en est-on ? Avant la règle, un exemple concret qui concentre le piège le plus testé (le 422) : une action de saisie qui peut rediriger ou réafficher.

Quittons provisoirement la lecture de l'article pour la saisie d'un billet. Le formulaire n'appartient pas au trajet obligatoire de /blog/42 : il existe parce que cette action de création le construit et lui présente la Request. Le premier affichage ne signifie pas soumission ; après un POST, le résultat de la validation décide entre redirection et réaffichage.

public function new(Request $request): Response
{
    $form = $this->createForm(PostType::class)->handleRequest($request);
    if ($form->isSubmitted() && $form->isValid()) {
        // … enregistrement
        return $this->redirectToRoute('post_index');
    }

    // 200 au premier affichage, 422 si soumis et invalide
    return $this->render('post/new.html.twig', ['form' => $form]);
}

Les trois issues possibles de cette action :

GET  /post/new                    → form non soumis          → render → 200
POST /post/new  (données valides) → redirectToRoute          → 302
POST /post/new  (données fausses) → soumis ET invalide       → render → 422

Pourquoi un 422 et pas un 200 au réaffichage ? Le client (navigateur moderne, Turbo, fetch…) doit pouvoir distinguer « page affichée » de « soumission refusée » ; 422 (« Unprocessable Entity ») dit : le contenu est bien formé mais inacceptable.

🌍 In Real Life

La situation : l’auteur du blog reçoit une fiche vierge pour proposer un billet. Une fiche affichée n’est pas encore déposée ; une fiche déposée avec des erreurs doit revenir pour correction.

L’équivalent dans Symfony : fiche construite → createForm() ; réception des données → handleRequest() ; dépôt et contrôle → isSubmitted() puis isValid() ; orientation après réussite → réponse de redirection.

Retour à la réalité technique : cette action de saisie est une branche distincte de la lecture de /blog/42, comme l’inscription du lecteur. Le réaffichage utilise ici render() avec le FormInterface direct et une réponse initialement 200 ; soumis et invalide, il permet le passage à 422. L’enregistrement métier reste à implémenter.

🧠 Comment le mémoriser : « Afficher n’est pas déposer ; déposer n’est pas réussir. » Image mentale : fiche vierge, fiche remise, fiche annotée. Question-réflexe : « Le formulaire est-il soumis, valide, et quel helper construit la réponse ? »

⚠️ À ne pas confondre : un formulaire valide n’enregistre pas automatiquement le billet.

La règle

Où en est-on ? Étape 1 sur 4 : que doit rendre l'action ? C'est le contrat qui explique tout le reste : si le helper produit une Response, rien d'autre à faire.

Pourquoi une action doit-elle retourner une Response ?

Parce que HttpKernel::handle() doit retourner une Response à son appelant (le front controller), qui l'enverra. L'action est le maillon qui la fournit.

Dans la branche HTML, retourner $this->render('blog/show.html.twig', ...) fournit directement la Response : HttpKernel saute alors kernel.view. Retourner seulement un ArticleView ou une string ne choisit pas automatiquement un template ou du JSON. Un listener de kernel.view doit explicitement prendre en charge cette autre valeur.

Un controller doit retourner un object Response. S'il retourne autre chose, l'event kernel.view est dispatché pour convertir la valeur ; sans listener capable de le faire, la Request échoue.

Une réponse obtenue suit normalement kernel.response, puis kernel.finish_request, avant le retour de handle() et le dépilement de la Request. L'appelant l'envoie ensuite ; la terminaison est un appel séparé. Si la conversion échoue, le chemin d'exception applicable remplace cette suite nominale : tous les événements ne sont pas garantis.

action retourne ──► Response ?  oui ──► kernel.response ──► kernel.finish_request
                        │                                         │
                        non                                       ▼
                        ▼                              handle() rend la Response
                  kernel.view (un listener convertit ?)     │
                     oui │   non                            ▼
                         │    └──► exception            le front controller
                         └──► Response ───────────────►  send() puis terminate()

Ce chemin est celui du module Architecture (HttpKernel) : voir HttpKernel component and FrameworkBundle pour le détail des événements.

🌍 In Real Life

La situation : le poste remet au responsable un résultat préparé. S’il ne remet qu’un élément brut, une étape supplémentaire doit le rendre présentable ; quelqu’un doit encore le transmettre au client.

L’équivalent dans Symfony : résultat préparé → Response retournée ; élément brut → autre valeur de retour ; adaptation éventuelle → listener de kernel.view ; transmission → appel d’envoi par l’entrée HTTP.

Retour à la réalité technique : une Response saute kernel.view. Sinon, sans listener produisant une réponse, le traitement échoue. handle() retourne l’objet après le chemin de filtrage applicable ; il n’appelle pas automatiquement send() ni terminate(). Les erreurs peuvent interrompre ce chemin.

🧠 Comment le mémoriser : « Prêt à remettre n’est pas déjà remis. » Image mentale : résultat au passe avant son départ vers la salle. Question-réflexe : « Suis-je au retour PHP ou à l’émission HTTP ? »

⚠️ À ne pas confondre : kernel.view est une branche conditionnelle, pas le passage obligatoire de tout rendu Twig.

Le controller prépare une enveloppe de sortie : JsonResponse pour des données JSON, BinaryFileResponse pour un file, StreamedResponse pour un contenu produit progressivement. Le kernel reste chargé d'obtenir une Response exploitable.

Repère — JSON :

Question: What does the json() controller helper return?

Answer: A JsonResponse, using the Serializer when available.

json() produit une Response JSON. Sans Serializer, le helper utilise l'encodage JSON natif.

Rendre un template

À retenir en priorité
  1. render() convient au retour du controller.
  2. renderView() fournit uniquement le contenu.
  3. Un form non soumis ne déclenche pas 422.
  4. Un statut explicite n'est pas remplacé par cette règle.

Où en est-on ? Étape 2 sur 4 : produire du HTML avec Twig. Pourquoi trois helpers ? Parce que l'on veut parfois seulement le texte (corps d'un email), parfois la Response complète, parfois un rendu au fil de l'eau.

Pour l'article 42, Twig reçoit l'objet comme donnée de template et produit du texte ; le helper render() place ce texte dans une Response. Un appel à renderView() s'arrête au texte, utile pour le corps d'un email mais insuffisant comme retour HTTP sans conversion. L'échappement Twig protège la sortie selon son contexte ; il ne valide pas les données ni les droits du lecteur.

Method Retourne
render(), renderBlock() un object Response
renderView(), renderBlockView() une string
stream() une StreamedResponse, envoyée au fil du rendu

Vérifié dans AbstractController (8.0) : render(string $view, array $parameters = [], ?Response $response = null): Response, renderBlock(string $view, string $block, array $parameters = [], ?Response $response = null): Response, renderView(...): string, stream(string $view, array $parameters = [], ?StreamedResponse $response = null): StreamedResponse. Toutes ces méthodes sont protected.

Le troisième argument de render() est une Response déjà construite, dont il remplit le contenu : c'est ainsi qu'on impose un autre statut. Sans le bundle Twig, ces methods lèvent une LogicException qui nomme la method appelée et le package à installer.

Le formulaire et le 422 automatique

Un form est converti pour vous par les helpers de rendu concernés, pas par stream(). Chaque parameter direct FormInterface est remplacé par son createView() avant le rendu : l'appeler à la main est redondant, pas faux.

Le 422 automatique tient à trois conditions : la Response est encore en 200, un parameter est un FormInterface, et ce form est soumis et invalide. Un statut autre que 200 est conservé ; un form jamais soumis laisse le 200. renderBlock() suit la même règle.

Pourquoi trois conditions ? Chacune écarte un cas où promouvoir en 422 serait faux :

Condition                              Si elle manque…
───────────────────────────────────────────────────────────────────────────
1. statut encore 200                   vous avez choisi un statut : conservé
2. paramètre de type FormInterface     une FormView passée à la main : aucun
                                       contrôle possible (la validité est perdue)
3. formulaire soumis ET invalide       jamais soumis → 200 ; valide → 200

Comparaison utile : pourquoi stream() n'a pas ce mécanisme ? Parce que le rendu y est différé : le template n'est exécuté qu'au moment de l'envoi (dans le callback), donc trop tard pour modifier le statut.

┌──────────────────────────────────────┐ ┌──────────────────────────────────────┐
│     render() / renderBlock()         │ │              stream()                │
├──────────────────────────────────────┤ ├──────────────────────────────────────┤
│ Rend le template : TOUT DE SUITE     │ │ Rend le template : à l'envoi         │
│ Retour : Response                    │ │ Retour : StreamedResponse            │
│ FormInterface → createView() auto    │ │ pas de conversion de formulaire      │
│ 422 si form soumis et invalide       │ │ pas de contrôle 422                  │
└──────────────────────────────────────┘ └──────────────────────────────────────┘

🌍 In Real Life

La situation : rédiger le texte d’une lettre ne prépare pas encore son enveloppe. Une réponse complète ajoute les informations nécessaires à sa remise.

L’équivalent dans Symfony : texte seul → renderView() ou renderBlockView() ; texte avec enveloppe HTTP → render() ou renderBlock() ; production différée du texte → callback de la StreamedResponse de stream().

Retour à la réalité technique : la Response porte contenu, statut et headers. Dans les rendus concernés, un FormInterface direct, soumis et invalide, fait passer une réponse encore 200 à 422 ; une simple FormView ne donne pas ce même contrôle. stream() ne reprend pas ce mécanisme.

🧠 Comment le mémoriser : « Le texte n’est pas l’enveloppe. » Image mentale : feuille seule, puis enveloppe étiquetée. Question-réflexe : « Mon destinataire attend-il une string ou une Response, et le helper voit-il encore le FormInterface ? »

⚠️ À ne pas confondre : échappement de sortie, validation des données et autorisation du lecteur répondent à trois questions différentes.

JSON

À retenir en priorité
  1. json() produit une Response JSON.
  2. Sans Serializer, le helper utilise l'encodage JSON natif.

Où en est-on ? Étape 3 sur 4 : répondre à une autre application plutôt qu'à un lecteur. Ici, pas de template : des données à encoder.

Sur la branche /api/blog/42, sélectionne les données publiques de l'article avant de produire le JSON. Avec Serializer configuré, le contexte contrôle cette représentation ; ni la normalisation ni l'encodage n'accordent une autorisation et ne remplacent la validation d'une saisie. Un tableau de données donné à json() n'est pas une string déjà encodée : évite de l'encoder une seconde fois.

json() retourne une JsonResponse. Avec le Serializer, le contexte est fusionné par-dessus les options d'encoding par défaut : c'est par lui qu'on les change. Sans Serializer, json_encode sert, et une donnée null donne la string null.

Vérifié dans AbstractController::json() (8.0) : avec le service serializer, le résultat est serialize($data, 'json', array_merge(['json_encode_options' => JsonResponse::DEFAULT_ENCODING_OPTIONS], $context)) puis new JsonResponse($json, $status, $headers, true) — le true signifie « déjà encodé ». Sans Serializer : si $data === null, new JsonResponse('null', …, true) ; sinon new JsonResponse($data, …).

json($data)
   │
   ├─ Serializer présent ? ── oui ─► serialize(..., contexte fusionné)
   │                                 └─► JsonResponse(string, déjà encodé)
   │
   └─ non ─► $data === null ?
                ├─ oui ─► JsonResponse('null', déjà encodé)   → body : null
                └─ non ─► JsonResponse($data)   → json_encode par la Response

Pourquoi le cas null est-il traité à part ? Une JsonResponse construite avec null est remplacée par un objet vide {} ; le helper veut que json(null) produise réellement null (voir Question 2).

🌍 In Real Life

La situation : le blog remet la fiche publique du billet dans un format lisible par une autre application, plutôt que dans une mise en page destinée au lecteur.

L’équivalent dans Symfony : sélection de la fiche publique → choix des données et du contexte ; conversion en représentation transportable → Serializer configuré ; réponse à l’autre application → JsonResponse retournée par json().

Retour à la réalité technique : HTML et JSON sont deux sorties possibles. Le helper dispose d’un repli sans Serializer ; cela ne lui donne pas les mêmes capacités de normalisation d’objets. Fournir une string JSON comme donnée risque de l’encoder comme une string, au lieu de produire la structure attendue.

🧠 Comment le mémoriser : « Une représentation, un encodage. » Image mentale : fiche publique exportée une seule fois. Question-réflexe : « Ai-je des données à encoder ou du JSON déjà encodé ? »

⚠️ À ne pas confondre : choisir les champs exposés n’autorise pas à lui seul l’accès à l’article ; sérialiser ne valide pas une inscription.

Servir un file

À retenir en priorité
  1. file() produit une BinaryFileResponse.
  2. Le nom présenté au client peut différer du nom sur disque.

Où en est-on ? Étape 4 sur 4 : remettre un fichier existant. Pas de rendu : un chemin sur disque à transformer en Response.

Si le blog propose une annexe PDF, l'action dispose cette fois d'un chemin de fichier autorisé, pas d'un template à rendre. Le helper prépare une réponse de fichier ; ne transmets pas directement un chemin arbitraire fourni par le client. Le nom proposé au téléchargement et le chemin réel sur disque remplissent deux rôles distincts.

file() retourne une BinaryFileResponse en disposition attachment : le navigateur télécharge. Pour afficher dans la page, il faut ResponseHeaderBag::DISPOSITION_INLINE. Le deuxième argument renomme le file vu par le user ; omis, c'est le nom réel sur disque. Le header de disposition est écrit dans tous les cas.

Signature vérifiée (8.0) : file(\SplFileInfo|string $file, ?string $fileName = null, string $disposition = ResponseHeaderBag::DISPOSITION_ATTACHMENT): BinaryFileResponse.

file('/var/data/f81c.pdf')
   → attachment; filename="f81c.pdf"      (téléchargement)

file('/var/data/f81c.pdf', 'annexe.pdf')
   → attachment; filename="annexe.pdf"    (renommé pour l'utilisateur)

file('/var/data/f81c.pdf', null, ResponseHeaderBag::DISPOSITION_INLINE)
   → inline; filename="f81c.pdf"          (affiché dans la page)
(valeurs du header Content-Disposition)

Le chemin réel (premier argument) et le nom présenté (deuxième argument) sont deux informations distinctes : le renommage ne touche pas le fichier source. Un téléversement, en sens inverse, est traité dans File upload.

🌍 In Real Life

La situation : le service documentaire du blog remet une annexe PDF. Son emplacement dans les archives et le titre imprimé sur la copie ne sont pas la même information.

L’équivalent dans Symfony : emplacement d’archive → chemin de fichier fiable ; titre de la copie → nom proposé au téléchargement ; consigne de remise → Content-Disposition, attachment par défaut avec file().

Retour à la réalité technique : le helper retourne une BinaryFileResponse, sans envoyer immédiatement le fichier. inline demande une présentation intégrée, selon les capacités du client ; ce n’est ni une autorisation d’accès ni une garantie d’affichage. Changer le nom téléchargé ne renomme pas le fichier source.

🧠 Comment le mémoriser : « Où il est stocké, comment il est remis. » Image mentale : cote d’archive cachée et titre public sur la copie. Question-réflexe : « Ce paramètre désigne-t-il le fichier réel ou son nom de présentation ? »

⚠️ À ne pas confondre : accepter un nom de téléchargement ne justifie jamais d’ouvrir un chemin arbitraire fourni par le client.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Deux methods de rendu, deux return types.

    Deux methods de rendu, deux return types. L'une retourne une Response prête à être retournée par le controller, l'autre une simple string. Retourner la string depuis un controller déclenche kernel.view, et sans listener pour la convertir, la Request échoue. Pourquoi on se trompe : les deux noms (render, renderView) sont presque identiques et produisent le même HTML.

  • Voir l’explication : Le 422 n'est pas inconditionnel.

    Le 422 n'est pas inconditionnel. Il faut un statut encore à 200, un parameter FormInterface, et un form soumis et invalide. Un statut autre que 200 est conservé ; un form non soumis ne déclenche rien. Pourquoi on se trompe : « formulaire invalide → 422 » est retenu sans les deux autres conditions.

  • Voir l’explication : Servir un file télécharge par défaut.

    Servir un file télécharge par défaut. L'affichage dans la page demande de changer explicitement la disposition. Pourquoi on se trompe : on imagine qu'un PDF « s'affiche » naturellement.

  • Voir l’explication : Sans Twig, le rendu lève.

    Sans Twig, le rendu lève. La LogicException nomme la method et le package manquant ; ce n'est pas une Response vide. Pourquoi on se trompe : on suppose une dégradation silencieuse.

  • Voir l’explication : json(null) ne donne pas {}.

    json(null) ne donne pas {}. Sans Serializer, le helper passe la string null déjà encodée. Pourquoi on se trompe : new JsonResponse(null) donne {}, d'où l'idée que le helper fait de même.

  • Voir l’explication : Le contrôleur n'envoie rien.

    Le contrôleur n'envoie rien. Il retourne une Response ; l'envoi (send()) puis terminate() sont faits par l'appelant. Pourquoi on se trompe : « renvoyer une réponse » est lu comme « l'envoyer ».

À mémoriser

🧠 À retenir pour la certification :

  • Retourner une Response, sinon kernel.view doit convertir.
  • render() → Response, renderView() → string.
  • Form en parameter : createView() automatique.
  • 422 : statut 200 + FormInterface + soumis et invalide ; un statut autre que 200 est conservé.
  • json() : Serializer si présent, contexte = options d'encoding ; null → null.
  • file() : attachment par défaut, DISPOSITION_INLINE pour afficher.

Moyen mnémotechnique : « View, c'est la vue seule : une string ».

Phrase de mémorisation complète : « L'action retourne une Response — render l'habille, renderView ne rend que la string, json et file fabriquent la leur — et le 422 n'arrive que pour un FormInterface soumis, invalide, sur un 200. »
