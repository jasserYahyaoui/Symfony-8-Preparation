Module 25 — Runtime

Symfony 8.0 · API PHP ≤ 8.4 · Twig ≤ 3.22. Préparation indépendante.

Comprendre ce module dans le projet

Le serveur transmet /blog/42 à public/index.php, mais une entrée utilisant Runtime peut ne contenir aucun appel visible à handle() ou à l'envoi de la réponse. Qui lance réellement l'application ? Ce module remonte avant le contrôleur pour séparer description de l'application, amorçage et exécution.

Sur le chemin Symfony Runtime HTTP standard étudié, le fichier d'entrée retourne un callable qui construit App\Kernel. L'amorçage prépare les arguments de ce callable, l'appelle, puis choisit un runner, l'objet chargé d'exécuter le résultat. Construire le Kernel n'est pas encore démarrer l'application. Le résolveur de Runtime prépare le callable d'entrée ; ce n'est pas l'ArgumentResolver des actions HTTP.

Le runner HTTP appelle handle(), organise l'émission de la réponse, puis la terminaison lorsque le contrat du noyau le permet. Le retour de handle() et l'envoi restent donc distincts. La terminaison n'est pas un worker durable. Le cours explique aussi les précautions liées à l'amorçage du fichier d'entrée et le choix du runtime et de ses options d'environnement.

La commande d'import possède une autre entrée et un runner adapté à Console : partager le principe d'amorçage ne lui impose pas un cycle Request/Response. Une entrée manuelle sans Runtime constitue encore une autre variante ; on ne superpose pas ses appels à ceux du runner.

Vous pourrez retrouver qui construit, lance et termine l'application en lisant son point d'entrée, puis distinguer cet amorçage de l'exécution de BlogController::show. Les closures PHP et les rôles de Kernel et HttpKernel sont les repères de départ. Le module Console précise le contrat de l'autre entrée ; il n'est pas un préalable au chemin HTTP.

Objectif de départ : Expliquer pourquoi le file d'entrée retourne une function plutôt que d'exécuter l'application.
