Objectif

Avant de servir GET /blog/42, nous devons définir les objets que le code manipulera : un article dont le titre peut évoluer, des valeurs qui doivent rester stables et des méthodes de création réutilisables. Ce travail relève du langage PHP, pas du traitement HTTP. Nous allons décider qui peut lire ou modifier ces données, puis quelle class une méthode héritée construit.

Le cours suit quatre questions : (1) quelle class une factory héritée construit (self / static), (2) qui peut lire et écrire (visibilité), (3) comment déclarer et affecter sans répétition (promotion), (4) ce que readonly garantit vraiment.

Attributes, Interfaces, Abstract classes, Traits et Enums ont chacun leur propre item. Cette page ne les réexplique pas.

L'essentiel

À comprendre

À retenir en priorité
  1. private est une règle de class, pas d'instance.
  2. public private(set) sépare lecture publique et écriture privée.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Symfony est écrit avec des objets : services, value objects, entités. Si vous ne maîtrisez pas qui peut toucher à quoi (visibilité) et ce que readonly protège, vous ne pouvez pas concevoir d'objets sûrs.
  • Les trois pièges de fond. La visibilité se juge par classe, pas par instance ; readonly bloque la réaffectation, pas la mutation de l'objet contenu ; self est figé à la déclaration, static suit l'appelant.
  • Pourquoi c'est à l'examen. Chacun de ces points a un QCM « que se passe-t-il ? » dont la mauvaise réponse est tentante.

Une class décrit un type d'object : ses properties portent l'état, ses methods le comportement. Une instance est un object construit à partir de cette class. Deux articles peuvent donc avoir des titres différents tout en obéissant aux mêmes règles de visibilité.

Le lecteur du blog doit pouvoir consulter un titre sans contourner la méthode qui le modifie : la visibilité délimite ces accès. PHP 8.4 permet de séparer lecture et écriture avec private(set). Cette règle dépend de la class où s'exécute le code, et non de l'identité de l'instance.

Une fois l'accès choisi, la promotion évite de répéter la déclaration et l'affectation d'une property dans le constructeur. readonly ajoute une contrainte différente : pas de réaffectation ordinaire après initialisation, sans rendre immuable un object contenu. Enfin, si nous héritons d'une méthode de création, self désigne la class où elle est écrite tandis que static suit la class appelée. Commençons par isoler cette dernière différence.

Le schéma

À retenir en priorité
  1. self désigne la class déclarante.
  2. static suit la class appelée : late static binding.

Où en est-on ? Étape 1 sur 4. Avant la visibilité, on isole la question la plus subtile : quelle class construit une méthode héritée ? Le schéma ne montre pas un trajet de requête, mais la class réellement obtenue.

Une factory est ici une méthode qui construit et retourne un object. Pour choisir le comportement d'une future factory d'articles, comparons deux appels sur la même class fille, sans constructeur spécialisé ni accès aux données. Le diagramme montre la class obtenue, pas un trajet de requête.

Les rectangles bleus représentent l'appel et la résolution du nom de classe ; les capsules vertes, l'objet produit. Ce sont deux appels séparés, sans constructeur spécialisé dans cet exemple. static suit la classe appelée ; il ne copie pas la méthode dans la classe fille.

Pourquoi deux résultats alors que la méthode est héritée ? L'héritage ne recopie pas la méthode : il fait pointer ChildClass vers le code écrit dans ParentClass. Ce code contient un mot-clé qui doit être résolu : self est résolu à la compilation du texte (la classe où on l'écrit) ; static est résolu à l'exécution (la classe sur laquelle on a écrit ::).

L'exemple

Exemple concret

Où en est-on ? Toujours étape 1 sur 4 : le code minimal qui réalise le schéma. Les noms neutres isolent la règle ; le blog n'intervient pas.

Les noms neutres ParentClass et ChildClass isolent la règle que nous appliquerions à une class d'article et à sa spécialisation. Les deux appels n'ont aucun argument : seul le choix new self() ou new static() change.

class ParentClass
{
    public static function createSelf(): self     { return new self(); }
    public static function createStatic(): static { return new static(); }
}

final class ChildClass extends ParentClass {}

ChildClass::createSelf();     // ParentClass — self est figé à la déclaration
ChildClass::createStatic();   // ChildClass  — static suit l'appelant

Le premier appel retourne un ParentClass, le second un ChildClass ; aucun des deux n'affiche de texte. Hériter de la méthode ne déplace donc pas son lieu de déclaration. Ce test ne garantit pas qu'un futur constructeur spécialisé acceptera les mêmes arguments. Après le choix de l'object à créer, il reste à protéger les données qu'il expose.

Appel : ChildClass::createSelf()          Appel : ChildClass::createStatic()

        │                                         │
 new self  → « où est écrit ce code ? »    new static → « sur quoi a-t-on appelé ? »

Visibilité

À retenir en priorité
  1. private limite l'accès au code de la class qui déclare la propriété, pas à une seule instance.
  2. Une method de cette class peut donc lire la propriété privée d'une autre instance de la même class.

Où en est-on ? Étape 2 sur 4. Nous savons quelle class est construite ; reste à décider qui peut lire et écrire ses données. La question à se poser : « depuis quelle classe ce code s'exécute-t-il ? ».

Le titre de l'article 42 doit être lisible par le code de présentation, mais sa modification peut rester réservée à la class de l'article. public autorise l'accès extérieur ; protected le réserve à la class et à ses descendants ; private à la class déclarante. Le code d'une class peut lire un membre privé d'une autre instance de cette même class : « privé » ne veut pas dire « accessible seulement sur $this ».

Visibilité Qui peut accéder
public tout le code
protected la class déclarante et ses descendants
private la class déclarante uniquement (toutes ses instances)

Pourquoi par classe et pas par instance ? Parce que PHP vérifie dans quelle classe le code qui accède est écrit. Une méthode de Money est du code de Money : elle peut donc ouvrir le membre privé de n'importe quel objet Money, y compris un autre. C'est pratique pour comparer deux valeurs.

Depuis PHP 8.4, on peut rendre la lecture publique tout en restreignant l'écriture. Voici une déclaration à placer dans la class de l'article, et non un programme autonome :

public private(set) string $title;   // lisible partout, écrivable par la classe

Si cette class initialise $title à 'Premier article', un code extérieur lit cette chaîne ; une affectation extérieure $post->title = 'x' lève une Error. La class peut encore modifier son propre titre : private(set) n'est donc pas readonly. La visibilité d'écriture ne peut pas être plus permissive que celle de lecture. Il nous faut maintenant initialiser les valeurs au moment où nous construisons l'object.

public private(set) string $title;
  │       │
  │       └── qui peut ÉCRIRE ? → la classe seulement
  └────────── qui peut LIRE ?   → tout le monde
Règle : écriture jamais plus ouverte que la lecture

Cette visibilité PHP ne décide pas si un utilisateur du blog a le droit d'éditer un article : c'est une question d'autorisation applicative distincte. De même, déclarer un service « public » dans le conteneur ne rend pas ses properties privées accessibles au code extérieur.

Pour observer les deux frontières sans démarrer Symfony, conservons l'exercice Book : une fiche de lecture préparée pour un article du blog. Deux fiches reçoivent le titre 'First'. sameTitle() compare leur état privé ; rename() modifie seulement l'étiquette publique label.

<?php
final class Book
{
    public private(set) string $label;

    public function __construct(private string $title)
    {
        $this->label = $title;
    }

    public function sameTitle(self $other): bool
    {
        return $this->title === $other->title;
    }

    public function rename(string $label): void
    {
        $this->label = $label;
    }
}

$book = new Book('First');
var_dump($book->sameTitle(new Book('First')));
$book->rename('Second');
echo $book->label, "\n";
try {
    $book->label = 'Outside';
} catch (Error) {
    echo "write denied\n";
}

Le résultat attendu sous PHP 8.4 est bool(true), puis Second, puis write denied, chacun sur sa ligne. La comparaison privée est permise depuis Book ; l'écriture extérieure est refusée. Le catch intercepte l'Error pour montrer le résultat sans arrêter l'exercice. Ce modèle distingue volontairement titre interne et étiquette : il ne constitue pas une règle complète de modification d'article.

🌍 In Real Life

La situation : une fiche est consultable depuis l'extérieur, mais seules les opérations du service qui la gère peuvent la modifier ; ce service peut examiner plusieurs de ses fiches.

L’équivalent dans Symfony : consultation publique → public ; écriture réservée à la classe → private(set) ; accès aux fiches de même catégorie → accès privé entre instances de la même classe.

Retour à la réalité technique : PHP contrôle le scope de classe, pas seulement l'identité de $this. Private(set) permet des écritures répétées depuis le scope autorisé. Ces règles ne décident pas des droits d'un utilisateur HTTP.

🧠 Comment le mémoriser : « Qui lit, qui écrit, depuis quelle classe ? » Image mentale : fiche visible et zone d'édition réservée. Question-réflexe : l'accès est-il permis au code appelant ?

⚠️ À ne pas confondre : visibilité PHP, service public du container et autorisation métier.

Promotion de constructor

À retenir en priorité
  1. La promotion déclare et type la property.
  2. Le constructor affecte automatiquement l'argument.

Où en est-on ? Étape 3 sur 4. L'accès est choisi ; il faut maintenant déclarer et initialiser les properties sans écrire trois fois la même chose. C'est le rôle de la promotion.

Sans promotion, une property s'écrit trois fois : déclaration, paramètre, affectation. La promotion fusionne les trois.

Sans promotion                          Avec promotion (PHP 8.0)
 private int $amount;                    public function __construct(
 public function __construct(                public readonly int $amount,
     int $amount) {                      ) {}
     $this->amount = $amount;
 }

Prenons une valeur annexe de l'application : le montant d'une formule d'inscription au blog. Money regroupe le montant entier et sa devise. La promotion de constructor, disponible depuis PHP 8.0, transforme les paramètres munis d'une visibilité en properties et les affecte lors de la construction. Le readonly utilisé ici exige PHP 8.1 ou ultérieur.

final class Money
{
    public function __construct(
        public readonly int $amount,
        public readonly string $currency,
    ) {}
}

Un paramètre sans visibilité reste simplement un paramètre. Pour un paramètre promu, PHP affecte la property avant d'exécuter le corps du constructor. Avec new Money(1200, 'EUR'), les properties amount et currency valent respectivement 1200 et 'EUR'. Notre convention peut exprimer le montant en centimes, mais le type int ne l'impose pas. La promotion déclare, type et affecte ; elle ne vérifie ni que le montant est positif ni que la devise est reconnue. Ces règles métier demanderaient du code supplémentaire.

Ajoutons justement une règle : refuser un montant négatif à l'inscription. Cette variante de Money s'exécute séparément de la précédente, car elle redéclare la même class. Elle conserve aussi l'exemple du défaut de paramètre promu : ne pas fournir la devise choisit 'EUR'.

<?php
final class Money
{
    public function __construct(
        public readonly int $amount,
        public readonly string $currency = 'EUR',
    ) {
        if ($this->amount < 0) {
            throw new Exception('Amount must be non-negative');
        }
    }
}

$money = new Money(25);
echo $money->amount, ' ', $money->currency, "\n";
try {
    new Money(-1);
} catch (Exception $error) {
    echo $error->getMessage(), "\n";
}

La sortie attendue est 25 EUR, puis Amount must be non-negative. Le premier object est construit ; le second appel échoue avant de fournir un object utilisable à l'appelant. Ce contrôle vient du corps du constructor, pas de la promotion ni du type int. Le défaut 'EUR' appartient au paramètre, ce qui le rend compatible avec readonly. Il reste à examiner ce que cette contrainte protège après la construction.

Pourquoi le corps du constructor peut-il lire $this->amount ? Parce que PHP affecte les properties promues avant d'exécuter le corps : la validation voit donc déjà les valeurs.

Repère — readonly : readonly ne rend pas l'object référencé immuable. En PHP 8.4, son écriture est implicitement protected(set).

`readonly`

À retenir en priorité
  1. readonly ne rend pas l'object référencé immuable.
  2. En PHP 8.4, son écriture est implicitement protected(set).

Où en est-on ? Étape 4 sur 4 : les valeurs sont construites. Que garantit readonly ? La question clé : « remplace-t-on la property, ou modifie-t-on l'objet qu'elle référence ? ».

Une fois le montant construit, nous ne voulons pas qu'un autre morceau du code remplace sa valeur. Une propriété readonly ne se réaffecte pas après son initialisation ordinaire et n'accepte pas de défaut directement sur sa déclaration. La promotion peut porter un défaut de paramètre ; __clone() peut réinitialiser celle du clone depuis PHP 8.3. Depuis PHP 8.4, elle est implicitement protected(set) : une class fille peut donc l'initialiser. Depuis 8.2, une readonly class rend toutes ses properties readonly. readonly interdit la réaffectation, pas la mutation de l'object référencé. Ainsi, remplacer amount sur notre Money initialisé est interdit. En revanche, si une autre class conserve un ArrayObject dans une property readonly, ajouter un élément à cet object reste possible : la property référence toujours le même object. Pour concevoir une valeur réellement immuable, il faut aussi examiner ses données internes, pas seulement le mot-clé sur son enveloppe.

public readonly ArrayObject $items
        │
        ▼  la property pointe vers UN objet
   ┌─────────────┐
   │ ArrayObject │   $this->items = autre   → Error  (réaffectation)
   │  [ 1, 2 ]   │   $this->items->append(3) → OK     (mutation de l'objet)
   └─────────────┘
Version PHP Ce qui change pour readonly
8.1 readonly sur property typée ; pas de défaut sur la déclaration
8.2 readonly class : toutes les properties deviennent readonly
8.3 __clone() peut réinitialiser une property readonly du clone
8.4 implicitement protected(set) (avant : écriture limitée à la classe)

🌍 In Real Life

La situation : une référence fixée vers un classeur ne permet pas de désigner un autre classeur, mais les feuilles du classeur initial peuvent encore changer.

L’équivalent dans Symfony : référence non réaffectable → propriété readonly ; classeur mutable → objet contenu, comme ArrayObject.

Retour à la réalité technique : readonly interdit la réaffectation ordinaire après initialisation, pas la mutation profonde. Le défaut d'un paramètre promu et la réinitialisation du clone sont des cas distincts ; PHP 8.4 permet l'initialisation via le protected(set) implicite.

🧠 Comment le mémoriser : « Référence fixe, contenu à examiner. » Image mentale : flèche fixée vers un classeur aux feuilles mobiles. Question-réflexe : remplace-t-on la propriété ou modifie-t-on son objet ?

⚠️ À ne pas confondre : readonly et garantie d'immuabilité de toute la valeur.

`self` contre `static`

Où en est-on ? Retour à l'étape 1 pour la comparer à fond, maintenant que le vocabulaire (class, héritage, constructor) est en place : quelle class une factory héritée doit-elle produire ?

Revenons à la création des articles. Si une spécialisation hérite de la factory de base, voulons-nous produire la class de base ou la spécialisation ? self se résout à la class où le code est écrit ; c'est pourquoi ChildClass::createSelf() a produit ParentClass. static conserve la class réellement appelée : cette résolution tardive s'appelle late static binding et explique le résultat ChildClass du second appel.

parent:: cible la class parente ; dans ce contexte d'instance, $this:: permet de viser la class de l'object, comme static::. Ne déduis pas la class construite du seul nom placé avant :: dans l'appel : retrouve aussi la déclaration et l'expression new. C'est cette lecture complète que les pièges suivants mettent à l'épreuve.

self static
Résolu selon… la class où le code est écrit la class appelée à l'exécution
Moment figé à la déclaration late static binding (tardif)
ChildClass::create…() ParentClass ChildClass
Return type possible self static
Voisins parent:: (la class parente) $this:: (class de l'objet)

La même décision apparaît si l'inscription produit un document spécialisé. Cet exercice indépendant conserve la distinction Document/Invoice : la facture hérite des deux factories, sans ajouter de constructor.

<?php
class Document
{
    public static function createSelf(): self
    {
        return new self();
    }

    public static function createStatic(): static
    {
        return new static();
    }
}

final class Invoice extends Document {}

echo Invoice::createSelf()::class, "\n";
echo Invoice::createStatic()::class, "\n";

Les appels sans argument affichent Document, puis Invoice. Le nom de la class appelée ne suffit donc toujours pas : il faut lire le new de la factory héritée. Aucune configuration du conteneur ne change le sens de self, et le mot static de cette résolution ne signifie pas que toutes les données de l'object seraient partagées.

🌍 In Real Life

La situation : une instruction de fabrication peut désigner le modèle de son rédacteur ou celui du service qui l'utilise.

L’équivalent dans Symfony : modèle du rédacteur → new self ; modèle appelé → new static dans la factory héritée.

Retour à la réalité technique : self reste lié à la classe de déclaration ; static suit la classe appelée. Le constructeur de la spécialisation doit encore être compatible. Le container ne change pas cette résolution PHP.

🧠 Comment le mémoriser : « Où est-ce écrit, sur quelle classe est-ce appelé ? » Image mentale : instruction originale face au nom du modèle commandé. Question-réflexe : quel new détermine effectivement la classe produite ?

⚠️ À ne pas confondre : late static binding et partage global des données d'instances.

Imaginez deux tampons : self porte le nom gravé du bureau qui l'a fabriqué ; static lit le badge de la personne qui l'utilise. Une factory héritée peut ainsi garder son code tout en construisant la class appelée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Fin du parcours : les erreurs que les QCM exploitent, avec la raison pour laquelle on les commet.

  • Voir l’explication : self ne suit pas l'inheritance.

    self ne suit pas l'inheritance. Dans la factory héritée de notre exemple, appeler depuis ChildClass ne transforme pas new self() : la class construite reste ParentClass, où la méthode est déclarée. Pourquoi on se trompe : le nom avant :: est ChildClass, on croit qu'il détermine le résultat.

  • Voir l’explication : private bloque la surcharge.

    private bloque la surcharge. Si une class d'article possède une method privée de préparation du titre, une method de même nom dans sa fille est une method différente, pas une surcharge de celle du parent. #[\Override], introduit en PHP 8.3, permet de vérifier une intention de surcharge ; il ne rend pas une method privée accessible à l'enfant. Pourquoi on se trompe : même nom = même méthode, pense-t-on ; mais la fille ne voit pas la méthode privée du parent.

  • Voir l’explication : Une property readonly typée n'a pas de default value

    Une property readonly typée n'a pas de default value : elle ne peut pas en avoir directement. Un paramètre promu peut en revanche avoir un défaut : __construct(public readonly int $n = 0) initialise la propriété lors de la construction. Depuis PHP 8.3, __clone() peut aussi réinitialiser une propriété readonly sur le clone ; « une écriture » décrit le cas ordinaire. Pour une valeur d'inscription construite sans argument, demande-toi donc où se trouve le défaut : sur le paramètre du constructeur ou directement sur la property ? Le résultat n'est pas interchangeable. Pourquoi on se trompe : le défaut du paramètre promu ressemble à un défaut de property.

  • Voir l’explication : readonly ≠ immuable en profondeur.

    readonly ≠ immuable en profondeur. $bag->items->append(1) réussit même si items est readonly : seule la réaffectation lève une Error. Pourquoi on se trompe : « readonly » évoque un objet gelé ; il fige seulement la référence stockée.

  • Voir l’explication : private(set) ≠ readonly.

    private(set) ≠ readonly. La class peut réécrire plusieurs fois une property private(set). Pourquoi on se trompe : les deux restreignent l'écriture depuis l'extérieur ; seul readonly limite aussi le nombre d'écritures.

Choisir les objets puis assembler leurs dépendances

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Dernier regard de conception : comment ces règles servent à préparer les objets que Symfony assemblera ensuite.

  • Contrat d’objet, écriture restreinte et immutabilité

    Pour préparer les données affichées par GET /blog/42, choisis d'abord le contrat de chaque object. Le titre reste modifiable par la class qui porte les règles éditoriales : une visibilité d'écriture restreinte peut convenir. Un value object, object représentant une valeur plutôt qu'une identité, peut utiliser la promotion public readonly ou une readonly class, à condition de ne pas cacher de mutation dans ses objects internes.

  • Factory spécialisée et compatibilité des constructeurs

    Si une factory doit construire la spécialisation appelée, new static() avec un return type static exprime cette intention ; vérifie encore la compatibilité de ses constructeurs. Ces choix PHP ne chargent aucun article depuis une base de données. Ils préparent les contrats que les services de l'application utiliseront ensuite.

  • Injection manuelle sans route implicite

    On retrouve ces règles lorsqu'une inscription prépare un message d'accueil. Dans l'exemple conservé ci-dessous, GreetingService reçoit un préfixe et GreetingController reçoit ce service : transmettre une dépendance déjà construite s'appelle l'injection de dépendances. Ici tout est assemblé manuellement ; le nom Controller ne crée ni route ni réponse HTTP.

<?php
final class GreetingService
{
    public function __construct(private readonly string $prefix) {}

    public function greet(string $name): string
    {
        return $this->prefix . ' ' . $name;
    }
}

final class GreetingController
{
    public function __construct(private readonly GreetingService $greeting) {}

    public function __invoke(): string
    {
        return $this->greeting->greet('Ada');
    }
}

$controller = new GreetingController(new GreetingService('Bonjour'));
echo $controller(), "\n";
Invocation, promotion et assemblage des dépendances

Avec le préfixe 'Bonjour' et le nom 'Ada', la sortie est Bonjour Ada. L'appel $controller() utilise la method spéciale __invoke(). Les deux properties sont promues, privées et readonly ; seul le comportement public est utilisé ici. Symfony pourra fournir les dépendances via son conteneur, mais ne changera pas ces règles PHP. Le prochain enjeu est de dépendre d'un contrat d'interface plutôt que d'imposer une implémentation concrète.

🌍 In Real Life

La situation : on équipe un poste avec son outil avant de lui confier un travail ; lui remettre l'outil n'exécute pas encore ce travail.

L’équivalent dans Symfony : outil fourni → dépendance injectée au constructeur ; poste prêt → objet construit ; travail demandé → appel ultérieur à sa méthode ou à __invoke().

Retour à la réalité technique : le laboratoire assemble manuellement les objets. La promotion déclare et affecte la propriété avant le corps du constructeur ; elle ne choisit pas le fournisseur ni ne valide le métier. Le container peut fournir les dépendances, sans créer une route par le nom Controller.

🧠 Comment le mémoriser : « Équiper avant d'appeler. » Image mentale : outil posé sur un poste encore inactif. Question-réflexe : configure-t-on une dépendance durable ou un argument de cet appel ?

⚠️ À ne pas confondre : injection au constructeur et résolution des arguments d'action par HttpKernel.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • private = class déclarante, pas instance.
  • PHP 8.4 : private(set) sépare lecture et écriture ; écriture jamais plus permissive que la lecture.
  • Promotion : déclare, type et affecte en une fois (avant le corps).
  • readonly : pas de réaffectation ordinaire ; objet contenu potentiellement mutable. Défaut du paramètre promu et réinitialisation dans __clone() possibles ; protected(set) implicite en 8.4.
  • self = class écrite ; static = class appelée.
  • $this:: ≡ static:: ; readonly class (8.2) : tout readonly.

Moyen mnémotechnique : « self se souvient, static regarde qui appelle ».

Can one instance read a private property of another instance of the same class?

Yes, when the access occurs in that class's scope.

private limite l'accès au code de la class qui déclare la propriété, pas à une seule instance. Une method de cette class peut donc lire la propriété privée d'une autre instance de la même class.

Which class does new static() instantiate in an inherited factory?

The called class; new self() uses the class where the factory was defined.

Revoir : `readonly`

Does a readonly property freeze the object it references?

No. It prevents reassignment of the property, not mutation of the referenced object.

readonly ne rend pas l'object référencé immuable. En PHP 8.4, son écriture est implicitement protected(set).
