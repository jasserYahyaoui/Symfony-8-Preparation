Objectif

Une carte d'article (titre, résumé, lien) apparaît sur la page d'accueil, dans la liste, dans la barre latérale. Écrire son HTML trois fois, c'est trois endroits à corriger plus tard. Ce cours explique comment écrire la carte une fois et l'insérer partout, ce que la carte « voit » des variables de la page, ce qui arrive si le fichier manque, et quand utiliser embed plutôt que include.

Insérer un template dans un autre, contrôler ce qu'il voit, et choisir entre include et embed.

L'essentiel

À comprendre

À retenir en priorité
  1. include réutilise un fragment tel quel.
  2. embed combine inclusion et personnalisation des blocks.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Réutiliser un fragment au lieu de le dupliquer.
  • Le piège de fond. Par défaut, le fragment voit tout le contexte de l'appelant : il marche « par accident » tant que la page possède les bonnes variables, puis casse ailleurs.
  • Ce que l'auteur veut que vous compreniez. Il y a deux écritures (function / tag), deux façons de restreindre le contexte, deux façons de tolérer l'absence — et only n'est pas une sécurité.
  • Pourquoi c'est à l'examen. Les QCM testent ce qui remonte (rien), les globales sous only, LoaderError et sandboxed sans extension.

Un fragment — une carte d'article, un bandeau — s'insère dans plusieurs pages. include l'insère tel quel, embed l'insère en redéfinissant certains de ses blocks. Par défaut, le fragment voit tout le contexte de l'appelant ; only le limite à ce qu'on lui passe.

include : insère le fragment tel quel
embed   : insère le fragment ET redéfinit certains de ses blocks
only    : le fragment ne voit que ce qu'on lui passe (+ les globales)

Le schéma

À retenir en priorité
  1. only limite les variables héritées de l'appelant.
  2. with_context: false est l'équivalent de la function.

Où en est-on ? Vue d'ensemble en deux questions : (1) Twig trouve-t-il le fragment ? (2) Que voit le fragment une fois trouvé ? Les sections suivantes reprennent ces deux questions.

include('x.html.twig', {a: 1})
   ▼
Q1 : nom (ou liste) → un template existe ?
        ├─ non ─ ignore missing ? ── oui : rien n'est rendu
        │                          └ non : LoaderError
        └─ oui ▼
Q2 : only / with_context:false ?
        ├─ non : contexte appelant + {a: 1} (+ globales)
        └─ oui : {a: 1} seul (+ globales)
   ▼
rendu du fragment

Ambre = décision ; bleu = données ; vert = résultat ; rouge = erreur. Les flèches décrivent la résolution puis la transmission de variables. only définit une interface de données plus explicite ; ce n'est pas un bac à sable de sécurité.

L'exemple

Exemple concret

Où en est-on ? Avant le détail : un exemple complet qui utilise les deux formes (include en boucle, embed pour la mise à la une).

La liste /blog/page/1 peut afficher plusieurs ArticleView dans une carte, puis mettre l'article 42 à la une. posts et featured sont fournis au rendu : ni include ni embed ne recherchent ces articles. Le fragment reçoit un nom d'entrée stable, article, quelle que soit la variable employée par l'appelant.

{% for post in posts %}
    {{ include('article/_card.html.twig', {article: post}, with_context: false) }}
{% endfor %}

{% embed 'article/_card.html.twig' with {article: featured} only %}
    {% block footer %}<strong>À la une</strong>{% endblock %}
{% endembed %}

Lecture : dans la boucle, la carte reçoit article = chaque post et rien d'autre ; l'embed rend la même carte pour featured, mais remplace son block footer.

Les deux écritures

À retenir en priorité
  1. La function include() se compose avec d'autres expressions.
  2. Le tag inclut directement le fragment.

Où en est-on ? Étape 1 sur 4 : la function et le tag — deux syntaxes pour la même opération. Laquelle choisir, et pourquoi ?

Une inclusion Twig ne déclenche pas une subrequest HTTP : elle rend un autre template dans le même travail de présentation. La function permet de conserver son résultat dans une variable avant de l'utiliser ; le tag écrit le fragment à l'endroit rencontré. Le préfixe _ documente cette intention de réutilisation, sans imposer un comportement au loader.

  • La function {{ include('x.html.twig', {a: 1}) }} est la forme recommandée : elle se compose — {% set html = include('x.html.twig') %}, include('x.html.twig')|upper — et ses named arguments n'imposent aucun ordre.
  • Le tag {% include 'x.html.twig' with {a: 1} %} fait la même chose.

Un fragment est souvent préfixé d'un souligné, _card.html.twig ; la documentation Symfony précise que ce préfixe est facultatif.

Pourquoi la function est-elle recommandée ? Parce que c'est une expression : elle retourne le HTML comme valeur, donc on peut le stocker, le filtrer, le passer à une autre function. Le tag, lui, écrit directement.

function include() tag {% include %}
Retourne une valeur oui (string) non (écrit à l'endroit)
Composable (set, filters) oui non
Restreindre le contexte with_context: false only
Tolérer l'absence ignore_missing: true ignore missing

🌍 In Real Life

La situation : l'imprimeur prépare un encart. Il peut l'insérer immédiatement dans la page ou garder le résultat composé pour l'utiliser ensuite.

L’équivalent dans Symfony : le tag include rend le fragment à l'endroit rencontré ; la fonction include() fournit un résultat utilisable dans une expression ou une affectation. Le préfixe _ du nom de fichier n'est qu'une convention.

Retour à la réalité technique : il s'agit d'un rendu de template, pas d'une sous-requête HttpKernel ni d'une recherche d'ArticleView. Conserver le résultat ne crée pas automatiquement un cache partagé ou une Response.

🧠 Comment le mémoriser : « Insérer l'encart maintenant ou garder sa composition. » Image mentale : encart posé sur la page ou conservé sur le bureau. Question-réflexe : ai-je besoin d'une sortie immédiate ou d'une valeur réutilisable ?

⚠️ À ne pas confondre : inclusion Twig, fragment HTTP et convention de nommage.

Le contexte

Où en est-on ? Étape 2 sur 4 : le fragment est trouvé. Quelles variables peut-il lire ? C'est le piège central du cours.

Sans restriction, la carte pourrait fonctionner uniquement parce que la page possède accidentellement title. En passant article avec with_context: false, son contrat devient visible et portable. Cela ne retire pas app ni les autres globales : l'isolation du contexte n'est ni un clonage d'ArticleView ni une barrière d'accès aux services.

Écriture Le fragment voit
include('x.html.twig', {a: 1}) tout le contexte de l'appelant, plus a
{% include 'x.html.twig' with {a: 1} only %} a et les globales
include('x.html.twig', {a: 1}, with_context: false) a et les globales
  • Les globales restent visibles, même avec only.
  • Rien ne remonte : une variable posée par set dans le fragment n'existe pas chez l'appelant.

Exemple : l'appelant possède article = A, mais passe {article: B} au fragment. Celui-ci affiche B ; après l'inclusion, l'appelant garde A. Cette séparation concerne les variables de contexte, pas une copie profonde des objets : elle ne neutralise pas les effets des méthodes d'objets partagés.

Mécanisme (code de include()) : si le contexte est conservé, Twig fait array_merge($contexte, $variables) — les variables explicites écrasent celles de l'appelant — puis rend le fragment avec ce nouveau tableau. Comme c'est une copie, le fragment ne peut rien réaffecter chez l'appelant.

appelant : article = A, title = 'Page'
include(..., {article: B})                     (contexte conservé)
   ▼
tableau transmis : {article: B, title: 'Page', + globales}   ← copie fusionnée
   ▼
le fragment fait {% set leaked = 'L' %}   → modifie SA copie seulement
   ▼
retour chez l'appelant : article = A, leaked inexistant

Pourquoi only ne protège pas : les objets sont passés par référence ; et les globales (dont app, donc des services) restent accessibles. only clarifie le contrat de données, il n'isole pas l'exécution.

🌍 In Real Life

La situation : pour composer une carte, l'atelier reçoit soit tout le dossier de commande, soit une fiche d'entrée précise. Les consignes communes restent disponibles ; changer une note locale ne réécrit pas le dossier de l'appelant.

L’équivalent dans Symfony : les variables explicites complètent ou remplacent le contexte transmis. only ou with_context: false retirent le contexte appelant, pas les globales. Un set du fragment reste local au contexte de ce rendu.

Retour à la réalité technique : les objets transmis ne sont pas clonés en profondeur ; leurs méthodes peuvent produire des effets visibles ailleurs. only clarifie l'interface de données, sans constituer une sandbox ni supprimer l'accès aux services exposés par les globales.

🧠 Comment le mémoriser : « Fiche d'entrée réduite, atelier toujours partagé. » Image mentale : fiche article seule devant les mêmes outils communs. Question-réflexe : quelles variables ai-je transmises, et quels objets ou services restent partagés ?

⚠️ À ne pas confondre : isolation des noms de contexte, copie des objets et sécurité d'exécution.

Un include avec only reçoit une boîte contenant les variables explicitement fournies, pas tout le plan de travail de l'appelant. Les globales restent accessibles : la boîte n'est pas une sandbox de sécurité.

Quel template, et s'il manque

À retenir en priorité
  1. La liste fournit des alternatives, pas plusieurs rendus.
  2. ignore_missing permet un résultat vide si aucune ne convient.

Où en est-on ? Étape 3 sur 4 : avant même le contexte, il faut trouver le fichier. Le nom est une expression, et son absence est une erreur… sauf si on la tolère explicitement.

Un bandeau saisonnier absent peut être réellement facultatif ; la carte qui porte le titre et le lien de l'article ne l'est généralement pas. N'emploie donc pas ignore_missing pour masquer une faute dans ce nom. Une fois un fichier trouvé, une erreur dans son rendu reste une erreur à traiter, pas une invitation à essayer silencieusement le suivant.

Le nom est une expression : variable, ternaire, ou liste dont le premier template existant est inclus.

Un template absent lève une LoaderError au rendu, sauf :

  • en tag, ignore missing, juste après le nom : {% include 'x.html.twig' ignore missing with {a: 1} only %} ;
  • en function, ignore_missing: true, qui rend une string vide.

ignore_missing tolère l'absence de la cible, pas une erreur de syntaxe ni une erreur métier pendant le rendu d'un template trouvé.

Pour un template écrit par un user, include('page.html.twig', sandboxed: true) — effectif seulement si SandboxExtension est enregistrée ; sinon l'option est ignorée, sans erreur.

Mécanisme : ignore_missing n'attrape que la LoaderError de la résolution du template. Le rendu du fragment trouvé n'est pas dans ce try.

resolveTemplate(nom ou liste)
   ├─ LoaderError (rien trouvé) ─ ignore_missing ? ── oui : retourne ''
   │                                               └─ non : relance l'erreur
   └─ trouvé ─▶ render(...)   ← une erreur ICI n'est PAS rattrapée

Pourquoi sandboxed: true sans extension n'échoue pas ? Le code active le bac à sable seulement si SandboxExtension est enregistrée ; sinon la condition est fausse et le fragment est rendu normalement : aucune alerte, aucune protection. D'où le risque : croire à une sécurité qui n'existe pas.

🌍 In Real Life

La situation : un encart saisonnier est facultatif. On cherche la première version disponible ; son absence peut être tolérée, mais une version trouvée et mal composée ne devient pas acceptable pour autant.

L’équivalent dans Symfony : une liste de noms fournit des candidats de chargement, dont le premier existant est retenu. ignore_missing tolère l'absence de la cible, pas une erreur dans le rendu du template trouvé.

Retour à la réalité technique : sans cette tolérance, l'absence produit une LoaderError. Une faute de syntaxe ou une erreur métier ne déclenche pas automatiquement un repli vers le candidat suivant. Pour du code de template non fiable, sandboxed: true exige une SandboxExtension enregistrée et une politique adaptée ; ce drapeau seul ne suffit pas.

🧠 Comment le mémoriser : « Facultatif s'il manque, pas s'il est cassé. » Image mentale : emplacement saisonnier vide autorisé, encart défectueux refusé. Question-réflexe : la cible manque-t-elle ou son exécution échoue-t-elle ?

⚠️ À ne pas confondre : repli de chargement, tolérance d'absence et contrôle de sécurité.

`include` ou `embed`

Où en est-on ? Étape 4 sur 4 : dernière question — le fragment doit-il simplement être inséré, ou faut-il en changer un morceau à l'endroit de l'appel ?

Pour la carte mise à la une, le footer change mais la structure reste commune : embed définit ce remplacement à l'appel. Le block dispose des entrées de cet embed ; avec only, une variable oubliée de la page ne lui est pas transmise. Passe explicitement tout libellé nécessaire.

{% embed %} combine include et extends : il insère un template et redéfinit ses blocks au point d'insertion. Il accepte les mêmes arguments que le tag include : with, only, ignore missing.

  • Fragment identique à chaque appel : include ; une partie à changer : embed.
  • Un block redéfini dans un embed … only ne voit que les variables de l'embed, pas celles de l'appelant.

Comparaison :

include embed
Insère un template oui oui
Redéfinit des blocks au point d'appel non oui
Arguments (with, only, ignore missing) oui oui (mêmes)
Quand ? fragment identique (les données peuvent varier) une zone du fragment change

Pourquoi « les données peuvent varier » avec include ? Passer article différent produit une carte différente : c'est une variation de données. embed sert quand c'est la structure (un block) qui change.

🌍 In Real Life

La situation : une carte standard possède une zone de pied. Pour l'édition « À la une », on garde le modèle et remplace cette zone à l'endroit où la carte est commandée.

L’équivalent dans Symfony : embed associe inclusion et redéfinition locale des blocs du fragment. include rend le template avec ses entrées sans fournir cette redéfinition de blocs au point d'appel.

Retour à la réalité technique : les données peuvent déjà faire varier le résultat d'un simple include ; la différence porte sur les blocs. Avec embed … only, les blocs voient les entrées de l'embed et les globales, pas les variables oubliées de l'appelant. Le fragment doit appeler le bloc pour afficher sa redéfinition.

🧠 Comment le mémoriser : « Même carte, zone remplacée sur commande. » Image mentale : carte standard portant un pied « À la une ». Question-réflexe : est-ce une variation de données ou une redéfinition de bloc dont j'ai besoin ?

⚠️ À ne pas confondre : paramètres du fragment, blocs redéfinis et héritage du layout de toute la page.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Par défaut, le template inclus voit tout le contexte de l'appelant.

    Par défaut, le template inclus voit tout le contexte de l'appelant. Le fragment marche par accident tant que l'appelant possède la variable, puis casse ailleurs. Pourquoi on se trompe : le fragment « marche » dans la page de test, donc on ne voit pas la dépendance cachée.

  • Voir l’explication : Restreindre le contexte s'écrit différemment selon la forme employée

    Restreindre le contexte s'écrit différemment selon la forme employée — un mot-clé dans le tag, un named argument dans la function. Pourquoi on se trompe : on écrit only dans la function ou with_context dans le tag.

  • Voir l’explication : Tolérer l'absence aussi

    Tolérer l'absence aussi : ignore missing en tag, ignore_missing: true en function. Même confusion de syntaxe.

  • Voir l’explication : Une liste de noms n'inclut qu'un template

    Une liste de noms n'inclut qu'un template : le premier qui existe. Pourquoi on se trompe : « liste » évoque « tout inclure ».

Application

À retenir en priorité
  1. only limite les variables héritées de l'appelant.
  2. with_context: false est l'équivalent de la function.
  3. La liste fournit des alternatives, pas plusieurs rendus.
  4. ignore_missing permet un résultat vide si aucune ne convient.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • include() recommandée : composable, named arguments.
  • Contexte hérité par défaut ; only / with_context: false le coupe.
  • Les globales restent visibles ; rien ne remonte du fragment.
  • Liste : le premier existant ; absent : LoaderError au rendu.
  • ignore missing juste après le nom ; ignore_missing: true en function.
  • sandboxed: true n'agit qu'avec SandboxExtension.
  • embed : include + blocks redéfinis, mêmes arguments.

Moyen mnémotechnique : « include insère, only isole, embed retouche ».

include() > {% include %} ; contexte hérité sauf only/with_context:false
(globales gardées), rien ne remonte ; nom = expression ou liste ;
absent = LoaderError sauf ignore missing ; sandboxed sans extension = rien ;
embed = blocks
