Objectif

Le navigateur demande GET /blog/42. Notre catalogue possède l'article, mais cela ne dit pas encore sous quelle forme le client le recevra : page HTML ou données JSON ? Pour raisonner correctement sur cette décision, il faut distinguer la cible, sa représentation et le message qui la transporte.

Une RFC est un document technique de la série de référence des protocoles Internet. RFC 9110 décrit le sens commun d'HTTP. Nous allons nous en servir pour lire cet échange, puis choisir le bon document quand la question porte plutôt sur le cache ou sur le format des messages.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. HTTP est défini par plusieurs RFC qui se sont recomposées en 2022. Savoir quel document répond à quelle question évite de chercher la mauvaise règle, et le vocabulaire exact évite les faux amis (ressource ≠ fichier, proxy ≠ gateway).
  • Le piège de fond. Trois niveaux se mélangent : le sens (que veut dire GET ?), la réutilisation d'une réponse stockée (cache), et l'encodage sur la connexion (octets). Un problème appartient à un seul de ces niveaux.
  • Ce que l'auteur veut que vous compreniez. Une URI identifie une ressource, jamais un format ; le serveur livre une représentation. Tout le reste (Accept, Content-Type, Vary, ETag) en découle.
  • Pourquoi c'est à l'examen. Questions sur la liste des RFC remplacées (2818 oui, 7234 non, 7230 en partie), sur Obsoletes contre Updates, sur les rôles d'intermédiaires, sur Set-Cookie et la casse des champs.

RFC 9110, HTTP Semantics (2022), définit le sens des méthodes, status codes, champs et règles de négociation. GET exprime une demande de représentation ; il n'oblige pas le serveur à lire un fichier HTML portant le nom de l'URL.

Dans notre scène, l'article 42 est la ressource, c'est-à-dire la cible conceptuelle. Le document HTML ou les données JSON qui en décrivent l'état forment des représentations possibles. La content negotiation, ou négociation de contenu, consiste à choisir une représentation selon les préférences reçues et les capacités du serveur.

Ce sens demeure commun à HTTP/1.1, HTTP/2 et HTTP/3, même si leurs formats de messages diffèrent. RFC 9111 précise les règles de cache et RFC 9112 le format HTTP/1.1. Pour l'examen comme pour un diagnostic, commence donc par demander si le problème concerne le sens, la réutilisation d'une réponse stockée ou son encodage sur la connexion.

├──────────────────────┼──────────────────────┼────────────────────────────┤
│ RFC 9110             │ RFC 9111             │ 9112 (HTTP/1.1)            │

Le schéma

Où en est-on ? Étape 1 sur 3 : ressource et représentation. Avant de parler des RFC, on isole la distinction fondatrice : qu'est-ce qu'on cible et qu'est-ce qu'on reçoit ? Le schéma suit une seule demande jusqu'à ses deux issues possibles.

Isolons le choix de représentation avant de revenir au controller. Le diagramme et l'exemple historique utilisent /article/42 : c'est un chemin d'illustration distinct, pas un alias ni une redirection automatiquement configurés pour /blog/42. La distinction cible/format est la même dans les deux scènes.

Le bleu désigne la cible, le losange orange la décision et le vert deux résultats alternatifs, pas deux ressources. Nous supposons ici l'article existant et une représentation acceptable disponible ; le cas 999 absent est un autre problème que le choix HTML/JSON.

Accept exprime les préférences du client. Content-Type décrit la forme effectivement envoyée. Vary: Accept indique que ce champ de la Request a participé à la sélection, ce qui compte pour réutiliser une réponse stockée. Enfin, un ETag, s'il est envoyé, est un validateur permettant de comparer des versions de la représentation sélectionnée. Ces champs ne sont donc pas trois noms pour le même mécanisme.

Champ Rôle Côté
Accept préférence du client sur la représentation Request
Content-Type forme effectivement envoyée Response
Vary: Accept ce champ de Request a servi à choisir (utile au cache) Response
ETag validateur pour comparer des versions de la représentation Response

L'exemple : une ressource, deux représentations

Exemple concret

À retenir en priorité
  1. L'URI identifie la ressource, pas une représentation unique.
  2. Content-Type décrit la représentation ; Vary distingue les choix liés aux headers.

Où en est-on ? Toujours étape 1 : on lit un échange réel, ligne par ligne, pour retrouver les quatre champs du tableau. Code minimal : une Request et sa Response.

Voici un extrait pédagogique de Request suivi de sa Response : le client préfère JSON et le serveur dispose de cette représentation. Le bloc omet notamment Host, le contenu et le cadrage complet du message ; ce n'est pas une transcription réseau prête à envoyer.

GET /article/42 HTTP/1.1
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Vary: Accept
ETag: "a42-json"

Le résultat annoncé est 200, avec Content-Type: application/json. "a42-json" est une valeur illustrative d'ETag, pas une formule fournie par HTTP. Si les données changent, le serveur doit maintenir correctement son validateur ; garder cette constante pour toutes les versions serait faux. La même URI peut proposer du HTML : la cible demeure la même, les octets et éventuellement le validateur changent.

Pourquoi l'ETag doit-il différer entre JSON et HTML ? Un validateur sert à répondre à « ma copie est-elle toujours la bonne ? » (requête conditionnelle). Si JSON et HTML partageaient un ETag fort, un client possédant la version HTML pourrait croire détenir la version JSON.

Un validateur fort distingue des représentations dont les données diffèrent octet par octet. Si le serveur choisit d'en émettre pour <p>bonjour</p> et {"message":"bonjour"}, les valeurs doivent donc être distinctes. Sans cette distinction, une comparaison conditionnelle pourrait faire passer les données d'une variante pour celles de l'autre. Vary: Accept aide le cache à sélectionner la bonne variante ; il ne répare pas une collision d'ETag au serveur d'origine.

La nuance de certification porte sur les conditions de cette règle : négocier n'impose pas à lui seul d'émettre un ETag. Des variantes simultanées aux données identiques peuvent partager un validateur fort, même si certaines métadonnées diffèrent. Un validateur faible, marqué par W/, peut regrouper des données jugées équivalentes sans garantir leur identité octet par octet (RFC 9110 §8.8.1).

ETag fort  "a42-json"   → identique ⇔ mêmes octets
ETag faible W/"a42"     → équivalence jugée suffisante, octets non garantis

JSON et HTML d'octets différents + ETag fort émis → 2 valeurs distinctes
Négocier n'oblige PAS à émettre un ETag

🌍 In Real Life

La situation : le même menu du restaurant peut être présenté sur une fiche imprimée ou un écran ; les supports décrivent le même contenu de référence.

L’équivalent dans Symfony : cible du menu → ressource ; document fourni → représentation HTML ou JSON ; préférence → Accept ; format livré → Content-Type.

Retour à la réalité technique : Vary décrit les critères de sélection ; un ETag fort distingue des données différentes, sans être rendu obligatoire par la négociation. Ces headers ne génèrent pas la représentation.

🧠 Comment le mémoriser : « Même cible, formes distinctes. » Image mentale : menu sur papier et écran. Question-réflexe : identifie-t-on la ressource, la variante ou sa version ?

⚠️ À ne pas confondre : URI et fichier physique, validateur et durée de fraîcheur.

Ce que RFC 9110 remplace

Où en est-on ? Étape 2 sur 3 : quel document consulter ? L'échange fonctionne ; maintenant on veut vérifier une règle, et il faut savoir dans quelle RFC elle se trouve. La liste des textes remplacés explique ce découpage, et c'est un classique de QCM.

L'échange fonctionne conceptuellement ; imaginons maintenant que nous voulions vérifier deux règles : le sens de Accept et la durée pendant laquelle une réponse stockée reste fraîche. Elles n'ont pas la même référence. Ce partage explique la liste des textes remplacés.

Le résumé de RFC 9110 indique qu'elle obsolète les RFC 2818, 7231, 7232, 7233, 7235, 7538, 7615, 7694, et des parties de 7230.

  • 7230 n'est obsolétée qu'en partie : la sémantique passe dans 9110, la syntaxe de trame HTTP/1.1 dans 9112 — seule ligne marquée d'un astérisque dans la Table 1 du §1.4.
  • 7234 n'y figure pas : le caching est repris par RFC 9111.
  • 2818, HTTP Over TLS, y figure, et on l'oublie presque toujours.
  • Obsolète n'est pas met à jour : 9110 porte Updates: 3864, qui reste en vigueur, amendée.
Avant (2014)                     Après (2022)
RFC 7230  syntaxe+routage  ──►  9110 (sémantique) + 9112 (trame)   [partiel*]
RFC 7231  sémantique       ──►  9110
RFC 7232  requêtes conditionnelles ► 9110
RFC 7233  requêtes d'intervalle    ► 9110
RFC 7234  cache            ──►  9111   (NON listée dans l'Obsoletes de 9110)
RFC 7235  authentification ──►  9110
RFC 2818  HTTP over TLS    ──►  9110   (souvent oubliée)
7538, 7615, 7694           ──►  9110

Pour Accept, consulte donc RFC 9110. Pour la définition de Cache-Control: max-age, consulte RFC 9111. Pour savoir comment délimiter un message HTTP/1.1, notamment avec le transfert chunked, consulte RFC 9112. HTTP/2 et HTTP/3 ont leurs propres descriptions, RFC 9113 et 9114.

L'extrait de Request suivant rend la séparation visible :

GET /article/42 HTTP/1.1
Host: example.test
Accept: application/json

Il exprime une lecture et une préférence JSON ; il n'annonce pas encore le résultat choisi par le serveur. Le sens de GET relève de 9110, la ligne textuelle terminée par HTTP/1.1 du format de 9112. HTTP/2 ne transmet pas cette même ligne textuelle, sans changer pour autant le sens de GET. HttpFoundation et HttpClient présentent ces notions en objets ; leurs aides ne remplacent pas la règle du protocole.

Pourquoi « obsolète » ≠ « met à jour » ? Dans les en-têtes de RFC, Obsoletes: X signifie « X est remplacée, ne plus s'y référer » ; Updates: Y signifie « Y reste en vigueur, mais 9110 la complète ou la corrige ». C'est pourquoi la RFC 3864 reste valide.

Le sens d'un recommandé ne dépend pas du camion ou de l'avion qui le transporte. De même, RFC 9110 définit le sens des messages, tandis que les RFC des versions HTTP décrivent leur transport.

Vocabulaire imposé

Où en est-on ? Étape 3 sur 3 : le vocabulaire exact. On suit GET /blog/42 d'un bout à l'autre en nommant chaque acteur et chaque morceau du message avec les mots de la spécification, car les QCM jouent sur ces termes.

Suivons maintenant le trajet logique de GET /blog/42 avec les mots de la spécification. Le client émet la Request et le serveur traite la demande. Le serveur d'origine est celui qui peut fournir une réponse faisant autorité pour la ressource cible ; il peut se trouver derrière un autre serveur visible du navigateur.

La Request et la Response sont des messages (§6). L'abstraction distingue données de contrôle, champs de header, contenu et champs de fin, appelés trailers, lorsqu'ils sont présents. Les contrôles annoncent notamment la méthode ou le status code ; les autres parties ne sont pas toutes présentes dans chaque message. La « ligne de départ » est leur expression HTTP/1.1, pas une syntaxe commune imposée à toutes les versions.

MESSAGE (§6)
 ├─ données de contrôle    méthode / URI (Request), status code (Response)
 ├─ champs de header       Accept, Content-Type, Vary, ETag…
 ├─ contenu                le corps (s'il y en a un)
 └─ champs de fin          trailers (seulement s'ils sont présents)
« ligne de départ » = expression HTTP/1.1 des données de contrôle (pas universelle)

La ressource est ce que la Request vise. Une URI, identifiant uniforme de ressource, identifie la cible dans notre exemple ; sa partie chemin est /blog/42. Cela ne suppose pas un fichier physique 42. La représentation est une forme de l'état de cette ressource à un instant donné, avec données et métadonnées de représentation. L'HTML affiché et le JSON lu par un autre client peuvent donc décrire le même article.

Un field de header possède un nom et une valeur. Le nom est insensible à la casse, mais la valeur suit sa propre grammaire. ETag et etag désignent le même champ ; "AbC" et "abc" sont deux entity-tags distincts, car leur partie opaque se compare caractère par caractère (§8.8.3.2). Mettre toutes les valeurs en minuscules altérerait ici le validateur au lieu de normaliser innocemment le message.

nom du champ  : ETag  ==  etag  ==  ETAG        (insensible à la casse)
valeur ETag   : "AbC" !=  "abc"      (partie opaque : caractère par caractère)

La même prudence vaut pour les champs répétés. Combiner des lignes par des virgules suppose que leur définition permette une liste. Set-Cookie est le cas particulier à conserver séparément : deux cookies renvoyés après une inscription ne deviennent pas un seul champ combiné par simple commodité de stockage.

Pourquoi Set-Cookie fait-il exception ? Fusionner A, B n'est légitime que si la grammaire du champ est une liste séparée par des virgules. Or une valeur de cookie ou une date expires=Wed, 21 Oct… contient déjà des virgules : la fusion rendrait le résultat ambigu. La RFC 9110 le mentionne explicitement comme champ qui n'utilise pas la syntaxe de liste.

Enfin, des intermédiaires (§3.7) peuvent intervenir. Un proxy est choisi par le client pour transmettre ses demandes. Une gateway, également appelée reverse proxy, se présente comme le serveur d'origine au client puis relaie la demande vers l'intérieur. Un tunnel relaie les données sans interpréter les messages une fois établi. Ces rôles décrivent le comportement sur le trajet ; un cache partagé n'est pas un synonyme automatique de chacun d'eux.

┌──────────────┬──────────────────────┬──────────────────────┬─────────────────┐
│              │ proxy                │ gateway (reverse     │ tunnel          │
│              │                      │ proxy)               │                 │
├──────────────┼──────────────────────┼──────────────────────┼─────────────────┤
│ Choisi par   │ le CLIENT            │ l'origine (le client │ établi, puis    │
│              │                      │ ne le choisit pas)   │ opaque          │
│ Se présente  │ comme un relais      │ comme le serveur     │ ne se présente  │
│ comme        │ du client            │ d'origine            │ pas, relaie     │
│ Messages     │ interprétés          │ interprétés, relayés │ NON interprétés │
│              │                      │ vers l'intérieur     │                 │
└──────────────┴──────────────────────┴──────────────────────┴─────────────────┘
(un cache partagé n'est pas un synonyme de ces trois rôles)

Si un reverse proxy se trouve devant le blog, il peut donc être serveur vis-à-vis du navigateur et client vis-à-vis du serveur interne. N'en déduis pas que toute Request atteint nécessairement PHP : un intermédiaire disposant d'une réponse réutilisable peut répondre selon les règles du cache. La scène applicative où BlogController::show est appelé suppose que la Request a effectivement atteint l'application.

🌍 In Real Life

La situation : un client confie sa demande à son mandataire ; le restaurant peut, lui, placer un accueil devant sa cuisine. Les deux relais ne jouent pas le même rôle.

L’équivalent dans Symfony : mandataire choisi par le client → proxy ; accueil représentant l'origine → gateway/reverse proxy ; relais opaque établi → tunnel.

Retour à la réalité technique : ces rôles appartiennent au trajet HTTP, pas à une étape obligatoire du controller. Un intermédiaire peut répondre avant PHP si une copie est réutilisable ; être relais ne signifie pas automatiquement être cache.

Pièges d'examen

Piège à éviter

  • Voir l’explication : « RFC 9110 remplace RFC 2616 » est un raccourci.

    « RFC 9110 remplace RFC 2616 » est un raccourci. 2616 a d'abord été éclatée en 7230-7235 ; c'est cette série-là que les 911x remplacent, et pas d'un bloc : 9110 prend la sémantique, 9111 le cache, 9112 le format HTTP/1.1. Si une ancienne documentation cite 2616 pour un comportement du blog, retrouve la règle dans le texte actuel correspondant à ce comportement, plutôt que de remplacer mécaniquement tous les numéros par 9110. Pourquoi on se trompe : le raccourci est répété partout, mais il saute l'étape 7230-7235 et le fait que 9110 n'est qu'une des trois RFC héritières.

  • Voir l’explication : Une ressource n'est pas sa représentation, et ce n'est pas un détail de vocabulaire.

    Une ressource n'est pas sa représentation, et ce n'est pas un détail de vocabulaire. /article/42 désigne une ressource ; le JSON français et le HTML anglais qu'elle peut rendre sont des représentations. C'est pourquoi la content negotiation porte sur la représentation, et pourquoi Vary nomme les fields qui ont servi à la choisir. Si la langue dépend aussi d'Accept-Language, le serveur doit tenir compte de cette dimension dans Vary, pas seulement du choix HTML/JSON. Vary ne choisit pas lui-même la représentation : il décrit une variation déjà décidée. Pourquoi on se trompe : en PHP « nu », une URL correspond à un fichier.

  • Voir l’explication : Les properties des methods — sûre, idempotente — sont bien définies par RFC 9110 (§9.2), mais elles sont évaluées sous l'item HTTP methods

    Les properties des methods — sûre, idempotente — sont bien définies par RFC 9110 (§9.2), mais elles sont évaluées sous l'item HTTP methods de ce module. Une méthode sûre ne demande pas de changement d'état ; l'idempotence concerne l'effet attendu de répétitions identiques. Lire l'article ne signifie donc pas « aucune activité serveur », et répéter une opération idempotente ne garantit pas des Responses identiques. Pourquoi on se trompe : « sûr » fait penser à « sans aucun effet » et « idempotent » à « même réponse ».

  • Voir l’explication : RFC 9110 ne décrit aucune syntaxe de trame.

    RFC 9110 ne décrit aucune syntaxe de trame. Le codage chunked ou la ligne de Request HTTP/1.1 relèvent de RFC 9112. Chercher dans 9110 le sens de GET est correct ; y chercher seul la manière de découper ses octets sur une connexion HTTP/1.1 confond deux niveaux.

  • Voir l’explication : Liste de l'Obsoletes : 2818 oui, 7234 non, 7230 partiel.

    Liste de l'Obsoletes : 2818 oui, 7234 non, 7230 partiel. Pourquoi on se trompe : on suppose que le cache (7234) a été absorbé par 9110 ; il a sa propre RFC, 9111.

  • Voir l’explication : Obsoletes ≠ Updates.

    Obsoletes ≠ Updates. 9110 Updates: 3864, qui reste en vigueur.

  • Cible, représentation et résultat HTTP

    Pour poursuivre le parcours, pose désormais trois questions sur la Response de l'article 42 : quelle cible a été demandée, quelle représentation a été sélectionnée, et quel résultat le serveur annonce-t-il ? Le cours sur les status codes approfondit la troisième. L'absence de 999 sera un résultat à expliquer, pas une autre manière d'encoder la représentation de 42.

Application

À retenir en priorité
  1. 9110 définit la sémantique indépendamment du transport.
  2. 9111 traite le cache ; 9112 la trame HTTP/1.1.
  3. L'URI identifie la ressource, pas une représentation unique.

Fiche express

À mémoriser

Pour lire l'échange du blog sans confondre les niveaux, garde ces repères :

  • 9110 sémantique, 9111 cache, 9112 HTTP/1.1, 9113 HTTP/2, 9114 HTTP/3.
  • 9110 obsolète une partie de 7230 ; la trame va dans 9112.
  • 7234 n'est pas dans sa liste ; 2818 y est.
  • Obsoletes remplace, Updates amende (3864 reste en vigueur).
  • Ressource ≠ représentation : d'où la négociation, Vary, l'ETag.
  • Noms de fields insensibles à la casse ; valeurs soumises à leurs règles propres, sans mise en minuscules générale.
  • Devant un énoncé absolu — « toute », « aucune », « jamais » — relire : §3.1 écrit « most resources are identified by a URI ».

Moyen mnémotechnique : « 10, 11, 12 » du plus général au plus concret — le sens, le cache, le format HTTP/1.1. Ce repère aide à trouver une règle ; il ne décrit pas trois étapes exécutées successivement par le controller.

🧠 À retenir pour la certification

  • Question sur le sens → 9110 ; sur le cache → 9111 ; sur le format HTTP/1.1 → 9112 (HTTP/2 : 9113, HTTP/3 : 9114).
  • Obsoletes de 9110 : 2818, 7231, 7232, 7233, 7235, 7538, 7615, 7694 et partie de 7230 ; pas 7234 (→ 9111). Updates: 3864.
  • Une URI identifie une ressource ; le serveur livre une représentation (Accept → Content-Type, Vary, ETag).
  • ETag fort : une valeur par représentation d'octets différents ; non obligatoire du seul fait de négocier.
  • Noms de champs insensibles à la casse, valeurs d'ETag sensibles ; Set-Cookie jamais fusionné.
  • Proxy (choisi par le client), gateway = reverse proxy (se présente comme l'origine), tunnel (opaque).

How does an HTTP resource differ from a representation?

The resource is the URI-identified target; a representation is a concrete form of its state at a given time.

La ressource n’est pas nécessairement un file ; sa représentation en exprime un état concret.

Why do negotiated representations matter to Vary?

One resource can have several representations; Vary identifies request fields used to select the representation.

Une ressource peut avoir plusieurs langues ou media types ; le cache doit distinguer les représentations négociées.

Are HTTP header field names and all field values case-insensitive?

Field names are case-insensitive; a value follows the rules of its own field, not a universal case-insensitivity rule.

L’insensibilité à la casse concerne le nom du field ; elle ne se généralise pas aux valeurs.
