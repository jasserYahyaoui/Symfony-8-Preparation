Objectif

BlogController::show a retrouvé l'article 42 et préparé sa représentation. Il lui reste à décrire le résultat HTTP : contenu, status code et headers. La Response rassemble ces éléments sans les envoyer au moment où on la construit.

Nous allons choisir la forme adaptée à une page, au JSON ou à une redirection, inspecter ce résultat, puis suivre son émission. Cette séparation permet aussi de comprendre pourquoi deux méthodes de test aux noms proches ne répondent pas à la même question.

L'essentiel

À comprendre

À retenir en priorité
  1. isRedirection() teste la class 3xx.
  2. isRedirect() suit une liste distincte de statuts.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Un contrôleur doit décrire un résultat HTTP (contenu, status code, headers) sans parler au réseau. Response est cette description : un simple objet PHP, construit puis rendu à quelqu'un d'autre qui l'enverra.
  • Le piège de fond. Construire, retourner, émettre et terminer sont quatre moments différents. Beaucoup de questions jouent sur cet ordre.
  • Ce que l'auteur veut que vous compreniez. Qui envoie réellement la réponse (le runner, pas le contrôleur), et pourquoi des méthodes de test aux noms proches (isRedirect() / isRedirection(), isOk() / isSuccessful()) répondent à des questions différentes.
  • Pourquoi c'est à l'examen. Détails d'API vérifiables : la liste exacte de isRedirect(), le 302 par défaut, HTTP/1.0 initial, getContent() de StreamedResponse, send(false).

Dans le trajet habituel de notre page, le controller retourne une Response, éventuellement spécialisée. Le kernel poursuit son traitement avant de rendre cet object au code chargé de l'émission. Avec le Runtime HTTP standard étudié ici, ce rôle revient à HttpKernelRunner. Ce n'est pas une règle universelle imposant Runtime à tout usage d'HttpFoundation.

Avant l'envoi, l'object peut être inspecté : le GET réussi annonce 200, l'absence de 999 peut être traduite en 404, et une inscription réussie peut demander une confirmation par 303. Construire l'object ne prouve pas que l'opération métier a eu lieu : le code doit choisir un résultat conforme à ce qui s'est réellement passé.

Un prédicat retourne vrai ou faux sur une propriété de cet object. isRedirection() reconnaît la famille 3xx ; isRedirect() utilise une liste Symfony particulière incluant 201 et excluant 304. Nous allons observer cette différence sans la confondre avec une nouvelle définition des status codes HTTP.

Le fil du cours, en quatre étapes :

Controller construit une Response
   ├─ 1. La class de base      → quelle sous-classe pour quel besoin ?
   ├─ 2. isRedirect / isRedirection → classer le status code
   ├─ 3. Autres methods de test     → isOk, isSuccessful, isNotFound...
   └─ 4. L'émission                 → qui appelle send(), et quand ?

Le schéma

À retenir en priorité
  1. Le controller retourne une Response.
  2. Le runner appelle send(false), finalise selon disponibilité/debug puis appelle terminate() si TerminableInterface ; la réception complète par le client n'est pas garantie.

Où en est-on ? On vient de dire que construire ≠ envoyer. Ce schéma montre la fin du chemin : ce qui arrive à la Response après que le kernel l'a retournée. Il anticipe l'étape 4 du cours (« L'émission »).

La représentation est prête, mais aucun octet n'a nécessairement quitté PHP. Le diagramme commence après le traitement par handle() et suit le runner Runtime dans le chemin sans exception :

Bleu : appels ; losanges orange : conditions ; capsules vertes : issues. Les conditions portent sur l'environnement d'exécution et sur le contrat du kernel, pas sur l'existence de l'article. send(false) émet headers et contenu, puis laisse la finalisation au runner. Celui-ci n'appelle terminate() que pour un kernel implémentant TerminableInterface.

Retourner, émettre et terminer sont donc trois opérations distinctes. Un test peut s'arrêter à l'inspection de l'object sans envoyer de headers ; un travail de terminaison n'est pas pour autant une tâche durable exécutée par un autre processus.

L'exemple : la bonne sous-classe

Exemple concret

À retenir en priorité
  1. JsonResponse encode des données PHP.
  2. fromJsonString() accepte un document JSON déjà encodé.

Où en est-on ? Retour au début du fil : le contrôleur doit choisir quel objet retourner. Code minimal d'abord, mécanisme ensuite.

La lecture HTML de 42 peut utiliser Response. Les branches voisines ont d'autres besoins : données JSON après une création effective, navigation vers une confirmation ou téléchargement d'un rapport existant. Avec PHP 8.4 et HttpFoundation 8.0 chargés par l'autoloader, les fragments suivants supposent ces imports :

use Symfony\Component\HttpFoundation\BinaryFileResponse;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Response;

$alreadyEncoded = '{"id":42}';

Choisis ensuite une seule ligne dans une action ; les chemins /orders/42 et /var/exports/report.pdf restent des exemples isolés, pas des routes ou fichiers créés par ce cours :

// Alternatives indépendantes : choisir une seule ligne par action.
return new JsonResponse(['id' => 42], Response::HTTP_CREATED);
return new RedirectResponse('/orders/42');           // 302 par défaut
return JsonResponse::fromJsonString($alreadyEncoded);
return new BinaryFileResponse('/var/exports/report.pdf');

La première alternative produit le JSON {"id":42} avec 201 : elle suppose que la création est déjà accomplie, et ne convient pas au simple GET de notre article existant. La deuxième construit un 302 avec Location: /orders/42 et une petite page HTML de redirection ; elle n'exécute pas cette destination.

La troisième réutilise la string JSON fournie, sans l'encoder une seconde fois ; sa validité reste à la charge de l'appelant. La quatrième suppose un fichier existant et lisible. Elle ne génère ni le rapport ni l'autorisation de le consulter. Ces choix préparent chacun une réponse, pas quatre émissions successives.

Ce que le contrôleur fait (et ne fait pas) :

contrôleur ──new JsonResponse(...)──▶ objet PHP en mémoire
                                       │ status, headers, contenu décrits
                                       ▼
                    return $response   (rien n'est envoyé au navigateur)

La class de base

Où en est-on ? Étape 1 sur 4 : la famille Response. Pourquoi des sous-classes ? Parce que préparer un contenu JSON, une redirection ou un fichier demande chaque fois des headers et un mode de production différents.

Response reçoit contenu, status code et headers. Son sac public $response->headers est un ResponseHeaderBag, qui gère aussi les cookies. La classe représente un résultat HTTP ; ses sous-classes spécialisent la préparation ou la production du contenu :

Class Usage
JsonResponse encode en JSON, pose le Content-Type ; fromJsonString() n'encode pas deux fois
RedirectResponse pose Location, statut 302 par défaut
BinaryFileResponse sert un file, Requests de plage comprises
StreamedResponse body produit par un callable, sans tout charger
StreamedJsonResponse JSON diffusé à partir d'un itérable

Pour l'export d'un long import, StreamedResponse peut produire le contenu au moment de sendContent() au moyen d'un callable, code appelable. getContent() retourne false, même après cette émission : la classe ne mémorise pas automatiquement toute la sortie. Le streaming réduit la mémoire seulement si le producteur ne charge pas lui-même toutes les données ; les buffers peuvent aussi retarder leur arrivée au client.

Avant l'émission, prepare($request) adapte la réponse à la demande. Une Response neuve, dont la version initiale est HTTP/1.0, reste à 1.0 si SERVER_PROTOCOL vaut HTTP/1.0 et passe à 1.1 sinon. La méthode ne négocie pas elle-même une connexion HTTP/2 avec le navigateur. Elle ajuste notamment Content-Type, retire le contenu pour HEAD et pour les status codes sans contenu, et traite certains headers associés. Pour HEAD, un Content-Length déjà présent peut être conservé alors que le contenu est retiré.

Dans le cycle Symfony standard, ResponseListener, abonné à kernel.response, appelle cette préparation pour la Request principale. Ne prête pas cette configuration à un HttpKernel isolé sans ce listener. Construire une Response seule ne la prépare pas, et send() n'appelle pas automatiquement prepare() à sa place.

new Response('x')           prepare($request)          send()
 version 1.0   ─────────────▶ version 1.1 (sauf    ───▶ headers + contenu
 pas de Content-Type ajusté   SERVER_PROTOCOL=1.0)       partent au client
                              Content-Type ajusté
                              contenu retiré (HEAD, 204...)
 ▲ construit                  ▲ ResponseListener         ▲ runner (send(false))
                                (kernel.response)

JsonResponse utilise json_encode() avec, par défaut, quatre options d'échappement supplémentaires pour certains caractères HTML. Le texte peut donc différer d'un encodage PHP sans options tout en représentant les mêmes données. Pour tester ces données, compare leur forme décodée ; si le contrat porte réellement sur les octets, vérifie aussi l'encodage choisi au lieu de déclarer toute comparaison textuelle interdite.

Sans argument, new JsonResponse() encode un object vide, {} : le constructor remplace null par un ArrayObject vide. Ce n'est ni une liste [] ni une réponse sans contenu.

Exemple autonome avec l'autoload HttpFoundation chargé : le premier appel encode les données ; le second reçoit du JSON déjà encodé, sans le doubler.

<?php
use Symfony\Component\HttpFoundation\JsonResponse;
$response = new JsonResponse(['id' => 42], 201);
$alreadyEncoded = JsonResponse::fromJsonString('{"id":42}', 201);
echo $response->getStatusCode(), "\n";
echo $alreadyEncoded->getContent(), "\n";

Les sorties sont 201 et {"id":42}. Cette expérience indépendante inspecte le résultat et l'affiche avec echo ; elle n'appelle pas Response::send(). Le 201 est choisi explicitement et ne crée aucune ressource à lui seul.

🌍 In Real Life

La situation : un restaurant peut préparer un plateau complet ou servir progressivement une préparation ; le mode de service ne décide pas à lui seul de l'accès du client.

L’équivalent dans Symfony : contenu préparé → Response ordinaire ; production pendant l'émission → callable de StreamedResponse ; adaptation à la demande → prepare().

Retour à la réalité technique : le streaming ne réduit la mémoire que si le producteur ne charge pas tout ; getContent() reste false, même après émission. ResponseListener prépare la Request principale dans le cycle configuré ; send() ne le remplace pas.

🧠 Comment le mémoriser : « Préparer, produire, transmettre : trois décisions. » Image mentale : plateau prêt face à un service progressif. Question-réflexe : quand le contenu est-il produit et où est-il conservé ?

⚠️ À ne pas confondre : sous-classe de Response, autorisation métier et preuve de livraison.

La Response rassemble l'enveloppe de retour : status code, headers et body. prepare() adapte cette enveloppe à la Request avant que l'émission ait lieu ; construire son contenu ne signifie pas l'avoir déjà envoyé.

`isRedirect()` contre `isRedirection()`

Où en est-on ? Étape 2 sur 4 : on a une Response, on veut la classer. Pourquoi deux méthodes aux noms presque identiques ? Parce qu'elles répondent à deux questions : « quelle famille de status ? » et « Symfony reconnaît-il un statut de redirection ? ».

Après l'inscription, nous voulons vérifier la confirmation annoncée. « Est-ce un 3xx ? » et « cette aide Symfony reconnaît-elle une destination ? » ne sont pas le même test.

isRedirection() compare le nombre à l'intervalle 300–399. isRedirect() reconnaît exactement 201, 301, 302, 303, 307 et 308. Sans argument, il ne vérifie même pas la présence de Location. Avec une URL passée en argument, il compare aussi la valeur de ce header. Voici un laboratoire qui n'envoie aucune Response :

use Symfony\Component\HttpFoundation\Response;

foreach ([201, 300, 304, 307] as $status) {
    $response = new Response('', $status);
    printf("%d: redirect=%d redirection=%d\n", $status,
        $response->isRedirect(), $response->isRedirection());
}

Les couples affichés sont 1/0, 0/1, 0/1, puis 1/1. Aucun des deux ensembles n'englobe l'autre. Le 304 de revalidation d'une copie est bien 3xx, mais n'ordonne pas une navigation ; le 201 reconnu par isRedirect() reste un succès de création.

Status :     201   300   301 302 303 304   307 308
isRedirection()  ✘    ✔     ✔   ✔   ✔   ✔     ✔   ✔     (300–399)
isRedirect()     ✔    ✘     ✔   ✔   ✔   ✘     ✔   ✔     (liste fixe)

Le constructor de RedirectResponse utilise cette même liste : new RedirectResponse($url, 304) lève une InvalidArgumentException, alors que new RedirectResponse($url, 201) est accepté pour une destination non vide. C'est un comportement d'API à connaître, pas une recommandation de transformer chaque création en redirection.

🌍 In Real Life

La situation : deux listes de contrôle ont des noms voisins, mais leurs critères ne sélectionnent pas les mêmes dossiers.

L’équivalent dans Symfony : classement numérique → isRedirection() pour 300–399 ; liste particulière → isRedirect() pour 201, 301, 302, 303, 307, 308.

Retour à la réalité technique : sans URL, isRedirect() ne vérifie pas Location. Son acceptation de 201 ne transforme pas ce succès en 3xx. Avec une URL, il compare aussi la destination.

🧠 Comment le mémoriser : « Lire le critère, pas seulement le nom. » Image mentale : deux listes partiellement superposées. Question-réflexe : cherche-t-on une famille, une liste ou une destination précise ?

⚠️ À ne pas confondre : prédicat vrai et redirection réellement suivie par un client.

Autres methods de test

À retenir en priorité
  1. isOk() vérifie 200 précisément.
  2. isSuccessful() vérifie toute la class 2xx.

Où en est-on ? Étape 3 sur 4 : les autres prédicats de classification. Même principe : chacun classe un nombre, aucun ne vérifie le contenu.

Pour la page 42, un test exigeant exactement 200 utilise isOk(). Un contrat acceptant n'importe quel succès utilise isSuccessful(), qui couvre les 2xx. La différence devient visible avec une réponse volontairement sans contenu :

use Symfony\Component\HttpFoundation\Response;

$response = new Response('', Response::HTTP_NO_CONTENT);
var_export($response->isOk());
echo "\n";
var_export($response->isSuccessful());

La sortie est false, puis true : 204 est un succès, pas 200. Ne rends pas un test de création artificiellement permissif pour qu'il « survive » au changement de code si le contrat exige précisément 201 et un header donné. Le choix du prédicat suit le contrat de l'action.

De même, isClientError() couvre les 4xx tandis que isNotFound() vise 404 exactement, utile pour la branche article 999 absent. isServerError() couvre les 5xx. Ces méthodes classent un nombre : elles ne vérifient ni la cohérence du contenu, ni l'existence de l'article, ni la réussite réelle d'une opération.

Prédicat Ce qu'il teste Exemple
isOk() exactement 200 GET réussi
isSuccessful() toute la famille 2xx 200, 201, 204
isClientError() famille 4xx 400, 404, 422
isNotFound() exactement 404 article 999 absent
isServerError() famille 5xx 500, 503

L'émission : `send()`, et qui l'appelle

Où en est-on ? Étape 4 sur 4, la dernière : on revient au schéma du début. Qui envoie réellement la Response, et que change send(false) ? On suit le chemin de l'objet jusqu'au navigateur.

Nous avons choisi et inspecté le résultat. Dans le trajet Runtime standard, le controller le retourne au kernel, puis le runner récupère la Response issue de handle(). Appeler send() dans l'action interromprait cette séparation et risquerait une émission prématurée avant les modifications attendues des listeners.

send() appelle sendHeaders(), puis sendContent(). Son paramètre $flush=false ne signifie donc pas « ne rien envoyer » : il saute la finalisation effectuée ensuite par cette méthode. Avec sa valeur par défaut true, elle utilise fastcgi_finish_request() si disponible, sinon l'alternative LiteSpeed, sinon ferme les buffers et appelle flush() hors des environnements cli, phpdbg et embed. Un buffer retient temporairement une sortie avant sa transmission.

HttpKernelRunner::run() choisit justement send(false) pour gérer lui-même cette étape : fonction de fin FastCGI ou LiteSpeed disponible et hors debug, sinon traitement des buffers ; puis terminate() si le kernel est terminable. Ce dernier appel peut déclencher kernel.terminate dans le kernel Symfony. Il ne fait pas partie de Response::send() et ne découle pas de la simple construction de l'object.

send()          = sendHeaders() + sendContent() + finalisation (si $flush=true)
send(false)     = sendHeaders() + sendContent()          (le runner finalise)
terminate()     = appelé APRÈS, seulement si le kernel est TerminableInterface

Sans prise en charge serveur adaptée, le client peut encore attendre. Même lorsque l'échange est finalisé côté serveur, cela ne prouve pas que tous les octets ont atteint le navigateur. Un email lent avec reprise sur échec demande un mécanisme asynchrone persistant distinct : le travail de terminaison occupe toujours le processus PHP courant.

Supposons maintenant qu'une sortie de diagnostic ait été émise trop tôt. Si headers_sent() est vrai, sendHeaders() ne parcourt plus les headers. Hors des SAPIs cli, phpdbg et embed, elle tente encore la ligne de statut : PHP peut alors signaler Cannot modify header information, sans pouvoir remplacer le statut déjà transmis. Un echo encore retenu dans un buffer ne suffit pas à établir que les headers sont partis. Distinguer cette émission effective d'un simple contrôle en ligne de commande : une sortie observée en CLI ne reproduit pas toutes les contraintes du serveur HTTP. La bonne correction consiste à préparer le résultat avant l'émission, pas à espérer qu'un changement tardif de l'object réécrive le passé.

🌍 In Real Life

La situation : le cuisinier remet le plateau au service ; une fois parti, corriger la fiche en cuisine ne rappelle pas ce qui a déjà été remis.

L’équivalent dans Symfony : plateau retourné → Response issue de handle() ; service chargé de l'émission → HttpKernelRunner ; rangement ultérieur éventuel → terminate().

Retour à la réalité technique : le runner appelle send(false), finalise selon l'environnement, puis termine seulement un kernel terminable. false n'interdit pas l'émission. Des headers déjà transmis ne sont pas réparés en modifiant l'objet ; les buffers compliquent l'observation.

🧠 Comment le mémoriser : « Retourner n'est pas envoyer. » Image mentale : plateau passant de la cuisine au service. Question-réflexe : qui détient encore la réponse et quels octets sont déjà partis ?

⚠️ À ne pas confondre : terminaison locale, tâche asynchrone durable et réception garantie par le navigateur.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Où en est-on ?

    Où en est-on ? Bilan : les erreurs de QCM les plus probables, avec la raison pour laquelle la mauvaise réponse semble juste.

  • Voir l’explication : isRedirect() n'est pas « le statut est 3xx ».

    isRedirect() n'est pas « le statut est 3xx ». Retenir 201 inclus, 304 exclu. Pour la confirmation d'inscription, vérifie aussi la destination attendue ; pour 304, raisonne en revalidation, pas en navigation. Pourquoi on se trompe : le nom évoque « redirection », donc la famille 3xx.

  • Voir l’explication : send() n'appartient pas au controller.

    send() n'appartient pas au controller. Un controller retourne une Response ; il ne l'envoie pas. Et le runner l'appelle avec false, pas avec le défaut. Cette précision vise le runner Runtime décrit plus haut : une entrée manuelle doit organiser elle-même préparation, émission et éventuelle terminaison. Pourquoi on se trompe : en PHP « nu », on écrit header() et echo soi-même ; ici l'objet est seulement une description.

  • Voir l’explication : isOk() n'est pas isSuccessful()

    isOk() n'est pas isSuccessful() : le premier teste 200 exactement, le second toute la class 2xx. Leur résultat ne dispense pas de vérifier le contenu promis par l'action. Pourquoi on se trompe : « OK » se lit comme « ça a marché », donc comme tout 2xx.

  • Voir l’explication : Un RedirectResponse renvoie 302 par défaut

    Un RedirectResponse renvoie 302 par défaut ; un permanent demande new RedirectResponse($url, 301). Si le contrat exige en plus de conserver la méthode lors du suivi automatique, 308 exprime cette autre nuance ; la permanence seule ne répond pas à la question de la méthode.

  • Voir l’explication : Son constructor valide le statut avec isRedirect()

    Son constructor valide le statut avec isRedirect() et lève une \InvalidArgumentException sinon. Conséquence directe de la liste ci-dessus : new RedirectResponse($url, 304) échoue, alors que new RedirectResponse($url, 201) est accepté. Ne déduis pas de cette acceptation que 201 appartient à la famille 3xx : le sens HTTP du status code reste distinct du prédicat Symfony. Pourquoi on se trompe : on croit que 304 est « plus redirection » que 201 parce qu'il est 3xx ; le constructor ne regarde que la liste.

Application

À retenir en priorité
  1. isOk() vérifie 200 précisément.
  2. isSuccessful() vérifie toute la class 2xx.
  3. Le controller retourne une Response.
  4. Le runner appelle send(false), finalise selon disponibilité/debug puis appelle terminate() si TerminableInterface ; la réception complète par le client n'est pas garantie.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Le controller rend, le runner Runtime HTTP décrit émet — avec send(false), puis gère la finalisation.
  • isRedirection() = 3xx ; isRedirect() = 201, 301, 302, 303, 307, 308.
  • RedirectResponse : 302 par défaut ; refuse 304, accepte 201.
  • isOk() = 200 pile ; isSuccessful() = 2xx.
  • Response neuve en HTTP/1.0 ; prepare() conserve 1.0 pour une Request HTTP/1.0, passe en 1.1 sinon.
  • JsonResponse ajoute par défaut des options d'échappement ; fromJsonString() reprend le JSON fourni sans le réencoder ni le valider.
  • Headers déjà partis : statut transmis non réparable ; avertissement possible hors cli, phpdbg et embed. Un buffer peut retarder l'émission.

Moyen mnémotechnique pour isRedirect() : « 201 dedans, 304 dehors ». Ce repère décrit la liste du prédicat, pas une obligation de navigation ni une preuve d'émission réseau.

Phrase de mémorisation : « Le contrôleur construit et retourne, le runner envoie avec send(false) puis termine ; et chaque prédicat classe un nombre, rien de plus. »
