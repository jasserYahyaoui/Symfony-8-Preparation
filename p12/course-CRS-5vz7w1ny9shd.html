Objectif

Une ligne d'import représente un article sous forme de tableau ; un formulaire d'édition manipule plutôt un objet. Un adaptateur doit lire ou écrire une valeur sans coder une branche pour chaque structure. PropertyAccess décrit l'accès par un chemin, tout en respectant les mécanismes exposés par la cible.

Ce cours suit quatre questions : quelle notation pour quelle cible ? Que se passe-t-il quand le path est absent ? Peut-on demander avant d'appeler (isReadable(), isWritable()) ? Et que changent les méthodes magiques et les collections ?

L'essentiel

À comprendre

À retenir en priorité
  1. Les notations choisissent des cibles différentes.
  2. Les crochets ne sont pas décoratifs.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le composant Form, le Serializer et bien d'autres ont besoin de lire et d'écrire « le champ title » sans savoir si la donnée est dans un tableau, un getter/setter ou une propriété. PropertyAccessor est ce traducteur unique.
  • Le piège de fond. Le path ne dit pas seulement où aller : sa notation dit quel type de cible on suppose. Crochets = index d'array, point = property d'object.
  • Ce que l'auteur veut que vous compreniez. Deux défauts opposés pour un path absent (array → null, object → exception), un isWritable() qui parcourt les intermédiaires, et la hiérarchie de résolution magique.
  • Pourquoi c'est à l'examen. Les questions portent sur [x] contre .x, les exceptions (NoSuchPropertyException, NoSuchIndexException, UnexpectedTypeException), le nullsafe ?, enableMagicCall() et le couple add…() / remove…().

PropertyAccess lit et écrit une valeur désignée par un path : les crochets visent un index d'array, le point une property d'object. Le piège central : un path absent rend null sur un array, mais lève sur un object — deux défauts opposés, renversables par l'accessor builder.

Un property path est une suite d'étapes d'accès, pas un chemin de fichier, une route HTTP ou une requête en base. Il peut mélanger objets et index. Le composant trouve comment accéder à la valeur ; il ne valide pas le titre d'un article ni le droit de l'utilisateur à le modifier.

Découpons un path pour voir ce que chaque morceau désigne :

children[0].firstName
│        │  │
│        │  └── .firstName  → property de l'objet enfant (getter/setter/propriété)
│        └───── [0]         → index 0 de la collection (array ou ArrayAccess)
└────────────── children    → property de l'objet de départ ($person)

Le schéma

À retenir en priorité
  1. Les deux défauts sont asymétriques.
  2. Le builder permet de les modifier.

Où en est-on ? On a vu qu'un path est une suite d'étapes. Voici comment l'accessor les parcourt une par une, en distinguant lecture, écriture et simple vérification.

La structure personne/enfants permet de voir les changements de type : objet, collection indexée, objet enfant. C'est la même lecture pas à pas qu'un objet d'édition contenant une liste d'articles, sans supposer que chaque point correspond à une propriété publique :

Bleu : objets parcourus ; vert : effet ou réponse. Le chemin suppose un enfant à l'index zéro ; une collection vide ou un intermédiaire null suit les erreurs décrites plus bas. Le path est un mode d'accès, pas une permission : ne pas laisser un client choisir librement les propriétés métier qu'il peut modifier.

L'exemple : une personne et ses enfants

Exemple concret

À retenir en priorité
  1. Un array utilise des index.
  2. Le point est réservé à la navigation de properties.

Où en est-on ? Avant les quatre sections thématiques, un exemple minimal qui montre les trois verbes du composant : lire, écrire, demander.

Fragment avec PropertyAccess 8.0 chargé : $person expose getFirstName() et getChildren(), ce dernier renvoyant un tableau avec un enfant à l'index 0. L'enfant expose getFirstName() et setFirstName(string $name). Ces classes métier ne sont pas fournies par le composant :

use Symfony\Component\PropertyAccess\PropertyAccess;

$propertyAccessor = PropertyAccess::createPropertyAccessor();

$propertyAccessor->getValue($person, 'firstName');
$propertyAccessor->setValue($person, 'children[0].firstName', 'Wouter');
// atteint le premier enfant ; appelle son setter si disponible, sinon écrit la propriété accessible

if ($propertyAccessor->isWritable($person, 'children[0].firstName')) {
    // ...
}
Appel Ce que Symfony fait
getValue($person, 'firstName') cherche un accès en lecture sur $person (ex. getFirstName())
setValue($person, 'children[0].firstName', 'Wouter') lit children, prend l'index 0, écrit firstName
isWritable(...) répond par un bool au lieu de lever

Deux notations, deux cibles

À retenir en priorité
  1. L'écriture agit sur la donnée fournie.
  2. Il ne faut pas ignorer cette mutation.

Où en est-on ? Question 1 sur 4 : comment dire à l'accessor si l'étape visée est un index ou une property ? Cette notation est la base de tous les comportements suivants.

Le premier appel de l'exemple lit la personne ; le deuxième change le prénom de l'enfant en Wouter, pas celui du parent. Choisir la notation selon le type de chaque intermédiaire, et non selon l'apparence de son nom. Les crochets conviennent aussi aux objets qui implémentent ArrayAccess ; un stdClass ordinaire ne le fait pas :

Path Cible Résultat
a array NoSuchPropertyException, qui suggère [a]
[x] stdClass NoSuchIndexException : pas d'ArrayAccess

Comparons les deux notations :

┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│      [title]  (crochets)        │   │       title  (point / nom)      │
├─────────────────────────────────┤   ├─────────────────────────────────┤
│ cible : array ou ArrayAccess    │   │ cible : object                  │
│ mécanisme : index               │   │ mécanisme : getter/setter,      │
│                                 │   │   propriété accessible, magie   │
│ absent : null (par défaut)      │   │ absent : NoSuchPropertyException│
│ sur array avec « title » :      │   │ sur array avec « title » :      │
│   fonctionne                    │   │   NoSuchPropertyException       │
│ sur stdClass :                  │   │ sur stdClass :                  │
│   NoSuchIndexException          │   │   fonctionne (propriété)        │
└─────────────────────────────────┘   └─────────────────────────────────┘

Écrire dans un array le modifie par référence : setValue($a, '[y]', 2) ajoute la key à $a. Les conventions d'accessors d'un object sont celles des forms (Module 07 — Formulaires).

Pour une ligne d'import, voici une mutation observable sans classe métier :

<?php
use Symfony\Component\PropertyAccess\PropertyAccess;

$accessor = PropertyAccess::createPropertyAccessor();
$row = ['id' => 42, 'title' => 'Brouillon'];
$accessor->setValue($row, '[title]', 'Article relu');
echo $accessor->getValue($row, '[title]');

Sortie attendue : Article relu. La modification concerne $row ; elle ne met pas à jour à elle seule ArticleCatalog ni la réponse de GET /blog/42. Un objet ne devient pas modifiable simplement parce que l'on connaît son chemin : il doit exposer un mécanisme d'écriture.

🌍 In Real Life

La situation : pour corriger une fiche du blog, on demande un dossier au responsable, prend la case numérotée puis modifie le champ de la fiche trouvée.

L’équivalent dans Symfony : accès nommé sur objet → propriété ; case indexée → crochets ; succession d'étapes → chemin comme children[0].firstName.

Retour à la réalité technique : chaque segment dépend de son intermédiaire : objet à propriétés, tableau ou ArrayAccess. Le chemin peut appeler des getters et setters ; il ne charge ni ne persiste automatiquement les données métier.

🧠 Comment le mémoriser : « Vérifier le support à chaque pas. » Image mentale : porte, casier, fiche. Question-réflexe : quel type ai-je atteint avant ce segment ?

⚠️ À ne pas confondre : propriété logique et accès direct à une propriété publique.

Le path absent : deux comportements opposés

À retenir en priorité
  1. Le nullsafe traite null.
  2. Il ne désactive pas toute validation du path.

Où en est-on ? Question 2 sur 4 : le path est bien écrit, mais la valeur n'existe pas. Selon que la cible est un array ou un object, la réaction n'est pas la même.

Une colonne facultative et une propriété métier mal nommée ne représentent pas nécessairement la même erreur. Les défauts ci-dessous décrivent une lecture ; ils ne signifient pas qu'écrire un index absent soit interdit :

Cible Path absent Pour renverser
index d'array rend null enableExceptionOnInvalidIndex() → NoSuchIndexException
property d'object lève NoSuchPropertyException disableExceptionOnInvalidPropertyPath() → null

Pourquoi ces défauts opposés ? Un tableau de données (ligne d'import, configuration) a naturellement des colonnes facultatives ; une propriété d'objet mal nommée est plus probablement une faute de frappe dans le code, que l'on veut voir tout de suite.

Le builder n'est pas la seule voie : new PropertyAccessor() prend les mêmes réglages en drapeaux — THROW_ON_INVALID_INDEX, THROW_ON_INVALID_PROPERTY_PATH, MAGIC_CALL —, et une application les fixe sous framework.property_access. Avec le seul drapeau THROW_ON_INVALID_INDEX : l'index absent lève, la property absente rend null.

Un maillon null est un troisième cas : person.firstname lève une UnexpectedTypeException, person?.firstname rend null.

Les trois situations côte à côte :

Lecture de… Défaut Réglage ou nullsafe
['a' => 1], [b] (index absent) null enableExceptionOnInvalidIndex() → NoSuchIndexException
objet sans title, title NoSuchPropertyException disableExceptionOnInvalidPropertyPath() → null
$person nul, person.firstname UnexpectedTypeException person?.firstname → null

Pour rendre explicites les deux politiques, terminer le builder par la construction de l'accessor :

$accessor = PropertyAccess::createPropertyAccessorBuilder()
    ->enableExceptionOnInvalidIndex()
    ->disableExceptionOnInvalidPropertyPath()
    ->getPropertyAccessor();

Ce réglage peut convenir à une colonne requise d'import et une propriété d'objet facultative, mais doit rester un choix de contrat. Retourner null ne distingue pas à lui seul une absence d'une valeur réellement nulle. Le nullsafe de person?.firstname protège le maillon person nul : si person existe mais n'expose pas firstname, ce n'est pas le même cas.

Demander avant d'appeler

À retenir en priorité
  1. Le test peut avoir des effets de lecture.
  2. Ne pas supposer une inspection pure de metadata.
  3. isWritable() peut lire les getters intermédiaires sans appeler le setter final.

Où en est-on ? Question 3 sur 4 : au lieu d'attraper une exception, on peut demander à l'accessor si le path est lisible ou modifiable. Le piège : demander n'est pas sans effet.

Avant de brancher un champ d'édition, vérifier l'accès paraît rassurant. La vérification traverse pourtant les données : ce n'est pas une analyse purement statique des métadonnées :

isReadable() et isWritable() rendent un bool là où getValue() et setValue() lèveraient pour un chemin inaccessible. Elles ne masquent pas toute exception métier provenant d'un getter et ne sont pas sans effet :

Appel Methods de l'object appelées
isReadable($person, 'firstName') getFirstName()
isWritable($person, 'firstName') aucune
isWritable($person, 'children[0].firstName') getChildren()

isReadable() lit le path entier ; isWritable() lit tout sauf le dernier maillon, qu'elle examine sans appeler le setter.

Pourquoi isWritable() appelle-t-elle getChildren() ? Pour savoir si firstName est modifiable sur l'enfant, il faut atteindre l'enfant, donc traverser les maillons qui le précèdent ; seul le dernier est inspecté.

isWritable($person, 'children[0].firstName')

  $person ──getChildren()──▶ [enfant0] ──[0]──▶ enfant ──▶ setFirstName() existe ?
          ▲ appelé                                         ▲ inspecté, PAS appelé

Ces méthodes interceptent notamment les erreurs d'accès et de type d'intermédiaire ; une exception métier arbitraire dans un getter peut toujours remonter. Une réponse vraie ne prouve ni permission, ni présence non nulle, ni acceptation de la future valeur par le setter. Éviter de doubler inutilement des getters coûteux par un contrôle suivi immédiatement de la même lecture.

🌍 In Real Life

La situation : vérifier si une fiche du blog est modifiable oblige à aller la chercher, même sans y écrire.

L’équivalent dans Symfony : parcours vers la fiche → getters intermédiaires ; contrôle du dernier accès → isWritable() ; écriture finale → setValue().

Retour à la réalité technique : le contrôle n'est pas une analyse purement statique. Les accesseurs intermédiaires peuvent s'exécuter et produire leurs effets ; ne pas appeler le setter final ne signifie pas « aucun code métier appelé ».

🧠 Comment le mémoriser : « Vérifier le bout exige de parcourir le chemin. » Image mentale : portes ouvertes avant un stylo encore fermé. Question-réflexe : quels getters seront traversés ?

⚠️ À ne pas confondre : accessibilité technique, autorisation métier et validation de la nouvelle valeur.

Les methods magiques

À retenir en priorité
  1. Les methods magiques n'ont pas toutes le même défaut.
  2. Configurer le comportement voulu.

Où en est-on ? Question 4 sur 4 : la cible n'a pas toujours de vrais getters. Elle peut passer par les méthodes magiques de PHP ou par une paire add…() / remove…() pour une collection.

Une cible peut exposer ses données via les méthodes magiques de PHP plutôt que des getters réels. Cela ajoute une autre voie de résolution, qui doit être choisie consciemment :

__get() et __set() sont utilisées par défaut ; __call() doit être activée, enableMagicCall() : sans elle, une lecture qui ne passe que par __call() lève NoSuchPropertyException.

Méthode magique Activée par défaut ? Pour l'activer
__get() / __set() oui —
__call() non enableMagicCall() (drapeau MAGIC_CALL)

Pour une collection, le couple ajout/retrait l'emporte sur le setter, et seuls les éléments qui changent sont touchés : ['a'] → ['a', 'b'] appelle getChildren() puis addChild().

Écrire ['a', 'b'] dans « children » alors que children vaut ['a'] :

  1. getChildren()        → ['a']              (lecture de l'existant)
  2. retirer l'absent     → rien à retirer     (removeChild() non appelé)
  3. ajouter le nouveau   → addChild('b')      (comparaison stricte)
  setChildren() n'est PAS appelé : le couple add/remove prime sur le setter

Cette préférence suppose que les deux méthodes d'ajout et de retrait soient détectées et qu'une valeur itérable soit fournie. L'accessor lit la collection existante, retire les éléments absents de la nouvelle collection, puis ajoute ceux qui n'y étaient pas, avec comparaison stricte. Il n'appelle pas aveuglément le setter de collection.

Pour une édition d'articles liés, ce comportement permet aux méthodes métier de contrôler chaque changement. Mais il ne fournit pas de rollback : une exception après un premier ajout ne défait pas les appels précédents. Configurer un accessor ne remplace ni les invariants de ces méthodes, ni les permissions sur les chemins exposés au client.

⚠️ À ne pas confondre

Confusion Plausible car… Réalité
« Un path absent rend toujours null » c'est le cas sur un array sur un object : NoSuchPropertyException
isWritable() « n'appelle rien » elle ne modifie rien elle appelle les getters intermédiaires (getChildren())
isReadable() est sûre elle rend un bool elle appelle le getter et ne masque pas une exception métier
person?.firstname protège une propriété manquante le ? ressemble au nullsafe PHP il protège seulement un maillon person nul
__call() marche comme __get() les deux sont magiques __get()/__set() par défaut ; __call() après enableMagicCall()
Écrire un index absent lève la lecture peut lever l'écriture ajoute la key, par référence, sans exception
a fonctionne sur un array on lit une « clé a » il faut [a] ; sinon NoSuchPropertyException qui suggère [a]

Fiche express

À mémoriser

À retenir en priorité
  1. La mise à jour peut traiter seulement les différences.
  2. Le setter n'est pas toujours choisi.

La ligne d'import et l'objet d'édition restent deux structures différentes. Le chemin décrit comment atteindre leur valeur, pas comment autoriser, valider ou enregistrer une modification métier.

Si tu dois retenir seulement 6 choses :

  • [index] pour un array, .property pour un object.
  • Absent : array → null, object → exception ; le builder renverse.
  • ? arrête sur un maillon null seulement.
  • isReadable() / isWritable() : un bool ; isReadable() appelle le getter.
  • __get() / __set() par défaut ; __call() sur activation.
  • Collection : ajout/retrait avant le setter.

Moyen mnémotechnique : « Crochet pour l'array, point pour l'object ».

Le Serializer traite une autre étape : transformer une structure en représentation de données, puis éventuellement en texte JSON. Un accès à une propriété ne réalise pas à lui seul cette conversion.
