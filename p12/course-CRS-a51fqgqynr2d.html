Objectif

Obtenir la session depuis un controller, connaître son API de base, et comprendre quand elle démarre réellement.

Question fil rouge : HTTP n'a pas de mémoire ; comment garder un état entre deux requêtes, et à partir de quand cela me coûte-t-il quelque chose ?

L'essentiel

À comprendre

À retenir en priorité
  1. La régénération d'identifier ne vide pas les données.
  2. invalidate() vide puis appelle migrate(true).

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. HTTP est sans état : chaque Request est indépendante. La session associe un identifiant (porté par un cookie) à un stockage côté serveur, pour retrouver l'état du visiteur d'une requête à l'autre (panier, sélection, utilisateur connecté).
  • Le piège de fond. On croit que « session activée » veut dire « session démarrée », et que tester une valeur (has()) est neutre. Faux dans les deux cas : le démarrage est paresseux et le moindre accès au bag le déclenche — avec des conséquences sur le cookie et le cache.
  • Ce que l'auteur veut que vous compreniez. Trois choses : comment l'obtenir (trois chemins), quand elle démarre (au premier accès, test compris), et la différence migrate() / invalidate().
  • Pourquoi c'est à l'examen. has() démarre la session, migrate() ne détruit pas l'ancienne session par défaut, invalidate() vide puis migre.

En résumé : la session s'obtient par la Request, par un argument typé SessionInterface ou, dans un service, par RequestStack. Elle démarre paresseusement : pas parce que la configuration l'active, mais au premier accès — lire, écrire ou tester. migrate() change l'identifier en gardant les données ; invalidate() vide le stockage, puis appelle migrate(true).

Ce cours prolonge The request (getSession() de la RequestStack y est présenté) ; les messages éphémères stockés en session sont le sujet de The flash messages ; l'identifiant de session voyage dans un cookie, voir The cookies.

Le schéma

Où en est-on ? Le cours suit trois questions : comment l'obtenir ?, quand démarre-t-elle ?, quelle API (et que font migrate et invalidate) ? Le schéma ci-dessous raconte la deuxième, la plus piégeuse : de l'accès au bag jusqu'aux effets sur la Response.

Bleu = opérations ; vert = effet standard sans désactivation du cache automatique. Stockage, cookie d'identification et politique HTTP sont distincts.

Lecture : tout se joue à l'événement kernel.response de la requête principale. Le listener regarde trois choses — la session a-t-elle servi ? est-elle vide ? l'identifiant diffère-t-il de celui reçu dans le cookie ? — et en déduit deux effets indépendants : le Set-Cookie et le caractère privé de la Response.

L'exemple

Exemple concret

À retenir en priorité
  1. has() n'est pas une consultation neutre.
  2. La Response peut devenir private même sans cookie émis pour une session vide.

Où en est-on ? Un cas concret avant le détail : un panier minimal qui utilise les trois verbes de base get, set et le redirect.

Le panier ci-dessous est une variante d'état conservé entre requêtes, comme une sélection d'articles du blog. Il ne fait pas partie de la lecture publique obligatoire de /blog/42. L'action obtient une session attachée à sa Request ; le cookie éventuel identifie ce stockage, il ne contient pas nécessairement le tableau cart.

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpFoundation\Session\SessionInterface;

final class CartController extends AbstractController
{
    public function addToCart(SessionInterface $session, int $id): Response
    {
        $cart = $session->get('cart', []);   // [] par défaut
        $cart[] = $id;
        $session->set('cart', $cart);
        return $this->redirectToRoute('cart_show', [], 303);
    }
}

Le contrôleur est enregistré dans une application avec session et route cart_show configurées ; l'identifiant reçu a déjà été validé.

Ce que cet exemple montre :

POST /cart/add/7
   │ Cookie: PHPSESSID=abc  (identifiant seulement)
   ▼
get('cart', [])  ← lit dans le STOCKAGE serveur sous l'id « abc »
set('cart', [..., 7])
   ▼
303 → cart_show   (voir HTTP redirects : Post / Redirect / Get)

Le cookie ne contient pas le panier : il contient l'identifiant qui permet de retrouver le stockage côté serveur.

L'obtenir

À retenir en priorité
  1. Un controller peut recevoir SessionInterface.
  2. RequestStack retrouve la session liée à la Request courante.

Où en est-on ? Question 1 sur 3 : par où récupère-t-on la session ? Même logique que pour la Request : le chemin dépend du contexte (contrôleur ou service).

Dans l'action du blog, SessionValueResolver fournit la session de la Request courante ; ce n'est pas l'autowiring d'un service session universel. Un service applicatif reçoit plutôt RequestStack et consulte le contexte au moment utile. Ces accès supposent une session disponible : hors HTTP ou sans intégration, ne présume pas qu'elle existe.

Contexte Accès
controller, Request en main $request->getSession()
controller, argument typé SessionInterface $session, via SessionValueResolver
service RequestStack::getSession()

Pourquoi l'argument SessionInterface $session fonctionne-t-il dans une action ? Même raisonnement que pour Request $request (voir The request) : Symfony lit la signature, un resolver dédié reconnaît le type et fournit la session de la Request en cours. Ce n'est pas de l'autowiring ; la liste des resolvers est détaillée dans Argument value resolvers.

┌───────────────────────────────────────┐ ┌───────────────────────────────────────┐
│              CONTRÔLEUR               │ │                SERVICE                │
├───────────────────────────────────────┤ ├───────────────────────────────────────┤
│ SessionInterface $session             │ │ __construct(RequestStack $stack)      │
│ Qui : SessionValueResolver            │ │ Qui : conteneur / autowiring          │
│ Quand : à chaque appel de l'action    │ │ Quand : consultation au moment utile  │
│ Reçoit : la session de CETTE Request  │ │ $stack->getSession()                  │
└───────────────────────────────────────┘ └───────────────────────────────────────┘

Rappel (cours The request) : RequestStack::getSession() lève une exception s'il n'y a pas de session, au lieu de rendre null.

🌍 In Real Life

La situation : un bureau retrouve le dossier du visiteur en cours, pas un dossier unique partagé entre tous les visiteurs. Le conseiller demande le dossier au moment de traiter cette visite.

L’équivalent dans Symfony : SessionValueResolver fournit à l'action la session attachée à sa Request. Un service peut consulter RequestStack au moment utile pour accéder au contexte courant, au lieu de supposer une session universelle injectée.

Retour à la réalité technique : obtenir cette session suppose l'intégration et le contexte appropriés. Une commande sans requête HTTP ne dispose pas automatiquement d'une session. Le cookie d'identification et les données du stockage de session sont deux éléments distincts.

🧠 Comment le mémoriser : « Le dossier de cette visite, pas celui de tout le bureau. » Image mentale : dossier correspondant au visiteur devant le guichet. Question-réflexe : quelle Request fournit cette session, et existe-t-elle ici ?

⚠️ À ne pas confondre : résolution d'un argument de contrôleur et autowiring d'un service ; session et preuve d'authentification.

Le démarrage est lazy

Où en est-on ? Question 2 sur 3, le cœur du cours : à quel moment la session démarre-t-elle réellement ? Pourquoi c'est important : démarrer la session a un coût (lecture du stockage) et des effets sur la Response (cookie, cache privé).

Pourquoi « paresseux » ?

Une page d'article publique peut être rendue sans session. Mais ajouter « si le lecteur possède une sélection » avec has('selection') accède déjà au bag : ce simple test change le traitement de la réponse par le listener standard. Vérifie séparément démarrage, émission d'un cookie et cache privé ; ce ne sont pas trois synonymes du même effet.

La documentation écrit que la session démarre quand on la lit ou l'écrit. Le code va plus loin : sept methods de Session — has(), get(), set(), all(), replace(), remove(), clear() — passent par getAttributeBag(), qui démarre la session. Il n'y a donc aucune consultation neutre : has() la démarre comme get().

config : session activée      →  RIEN ne démarre
$session->has('x')            →  getAttributeBag() → start()   ◄ démarre
$session->get('x')            →  getAttributeBag() → start()   ◄ démarre
$session->set('x', 1)         →  getAttributeBag() → start()   ◄ démarre

Les trois effets, qu'il ne faut pas confondre

Sans usage de session, ce mécanisme n'impose pas de cookie ni de privatisation ; cela ne rend pas automatiquement la réponse publiquement cachable. Avec la configuration standard, l'usage du bag rend la réponse principale privée. Si les cookies sont activés, une session non vide reçoit un cookie lorsque son identifiant diffère de celui reçu ; il n'est pas renvoyé à chaque lecture. Une session devenue vide peut produire un cookie d'expiration. Un simple has() sur une session neuve vide donne « privée sans nouveau cookie ».

Vérifié dans AbstractSessionListener (8.0) : le cookie n'est posé que si les cookies de session sont utilisés et que la session n'est pas vide avec un identifiant différent de celui reçu ; si un cookie de session était reçu et que la session est devenue vide, le cookie est effacé (clearCookie). Le cache automatique est désactivable par l'en-tête interne Symfony-Session-NoAutoCacheControl (constante NO_AUTO_CACHE_CONTROL_HEADER) : c'est ce que le texte appelle « cache automatique non désactivé ».

Situation (listener standard, cookies activés) Session démarrée ? Réponse privée ? Set-Cookie ?
Aucun accès à la session non non (rien ne la privatise) non
has('x') sur une session neuve vide oui oui non (vide)
set('cart', [1]) sur une session neuve oui oui oui (non vide, id différent)
get() avec cookie reçu, session non vide, même id oui oui non (déjà connu)
session devenue vide avec cookie reçu oui oui cookie d'expiration

Pourquoi privée ? Parce que le contenu dépend du visiteur : un cache partagé (proxy) ne doit pas servir la page d'un visiteur à un autre.

🌍 In Real Life

La situation : l'armoire peut rester fermée tant qu'on sert une brochure publique. Demander « le dossier contient-il une sélection ? » oblige déjà à l'ouvrir, même si la réponse est non.

L’équivalent dans Symfony : has() accède au bag de données comme get() ; ce n'est pas une consultation sans démarrage. L'usage de la session est ensuite pris en compte par le listener de réponse pour la sauvegarde et, normalement, le cache privé.

Retour à la réalité technique : disponibilité de la session, démarrage du stockage, cookie émis et politique de cache sont distincts. Une session neuve vide peut rendre la réponse privée sans nouveau cookie. Le comportement décrit suppose l'intégration standard et le cache automatique non désactivé.

🧠 Comment le mémoriser : « Vérifier le contenu, c'est déjà ouvrir l'armoire. » Image mentale : armoire ouverte pour une simple question oui/non. Question-réflexe : un test ou un layout accède-t-il au bag malgré mon intention de servir une page publique ?

⚠️ À ne pas confondre : absence de Set-Cookie, absence d'usage de session et autorisation de mise en cache partagée.

Le cookie de session est le ticket, les données restent dans le casier côté serveur. Attention à la limite de l'image du vestiaire : même demander si un objet est présent avec has() démarre l'accès à la session.

L'API

Où en est-on ? Question 3 sur 3 : que puis-je faire avec la session, et que font exactement migrate() et invalidate() ? Pourquoi ces deux-là ? Parce qu'ils répondent à deux événements de sécurité : la connexion et la déconnexion.

Après connexion, on veut éviter de continuer avec un identifiant fixé avant l'authentification tout en gardant la sélection. À la déconnexion, on peut vouloir effacer ces données. La différence migrate/invalidate porte donc sur l'identifiant et le contenu ; l'intégration Security gère normalement sa stratégie, il ne faut pas la doubler sans raison.

set(), get($name, $default), has(), remove(), all(), clear(). Pour la security, deux methods, l'une bâtie sur l'autre :

  • migrate($destroy = false, $lifetime = null) régénère l'identifier et garde les données ; avec destroy à false, l'ancienne session reste sur le serveur. On l'appelle après une authentication réussie, contre la fixation de session.
  • invalidate($lifetime = null) vide le stockage, puis appelle migrate(true, $lifetime). C'est le vidage qui supprime les données, pas la régénération. On l'appelle à la déconnexion.

Les deux rendent un bool.

Vérifié dans Session (8.0) : invalidate() fait $this->storage->clear(); return $this->migrate(true, $lifetime); et migrate() fait return $this->storage->regenerate($destroy, $lifetime);.

Pourquoi régénérer l'identifiant après une connexion ?

Contre la fixation de session : un attaquant fait adopter à la victime un identifiant qu'il connaît, la victime se connecte, et l'attaquant, qui possède le même identifiant, est alors connecté. Changer l'identifiant à la connexion rend l'identifiant connu de l'attaquant inutile.

Comparaison

┌──────────────────────────────────────┐ ┌──────────────────────────────────────┐
│           migrate($destroy=false)    │ │           invalidate()               │
├──────────────────────────────────────┤ ├──────────────────────────────────────┤
│ Données           : GARDÉES          │ │ Données           : VIDÉES           │
│ Identifiant       : nouveau          │ │ Identifiant       : nouveau          │
│ Ancien stockage   : reste (destroy   │ │ Ancien stockage   : détruit          │
│                     = false)         │ │                     (migrate(true))  │
│ Usage typique     : après connexion  │ │ Usage typique     : déconnexion      │
├──────────────────────────────────────┤ ├──────────────────────────────────────┤
│ Mécanisme : regenerate($destroy)     │ │ Mécanisme : clear() PUIS migrate(true)│
└──────────────────────────────────────┘ └──────────────────────────────────────┘

🌍 In Real Life

La situation : le bureau peut attribuer un nouveau numéro à un dossier en conservant ses feuilles, ou vider le dossier avant de lui attribuer ce nouveau numéro. Ce sont deux opérations différentes.

L’équivalent dans Symfony : les méthodes ordinaires lisent et modifient les données ; migrate() régénère l'identifiant en conservant le contenu. invalidate() vide le stockage puis appelle migrate(true, …).

Retour à la réalité technique : l'option $destroy concerne l'ancien stockage, pas l'effacement des données conservées sous le nouvel identifiant. Elle vaut false par défaut. La stratégie Security configurée gère normalement les transitions de connexion ; changer un identifiant ne réalise pas à lui seul une authentification ou une déconnexion complète.

🧠 Comment le mémoriser : « Nouveau numéro ne signifie pas dossier vide. » Image mentale : même pile de feuilles avec une nouvelle étiquette, puis dossier vidé. Question-réflexe : veux-je garder les données, détruire l'ancien stockage, ou les deux ?

⚠️ À ne pas confondre : migrate(true) conserve les données courantes ; invalidate() les vide avant la migration.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Tester une valeur démarre la session, comme la lire.

    Tester une valeur démarre la session, comme la lire. Il n'existe pas de consultation neutre : has() passe par le même accès au sac que get(). La vérification suffit à rendre la page non cachable par un proxy partagé — sans nouveau cookie d'identification pour une session neuve vide. Une session vide avec cookie reçu peut au contraire produire son expiration. Pourquoi on se trompe : « has » ressemble à une simple question, sans effet de bord.

  • Voir l’explication : Activer la session dans la configuration ne la démarre pas.

    Activer la session dans la configuration ne la démarre pas. Le démarrage est lazy ; sans autre intervention, une page qui n'y touche jamais ne déclenche pas de cookie par ce mécanisme. Pourquoi on se trompe : on confond « disponible » et « démarrée ».

  • Voir l’explication : invalidate() n'est pas l'opposé de migrate(), elle l'utilise.

    invalidate() n'est pas l'opposé de migrate(), elle l'utilise. Elle vide le stockage puis appelle migrate(true, …). La suppression des données vient du vidage, pas de la régénération. Pourquoi on se trompe : le nom « invalider » suggère une destruction, on attribue donc l'effacement à la régénération.

  • Voir l’explication : migrate() seule ne détruit pas l'ancienne session.

    migrate() seule ne détruit pas l'ancienne session. Son argument $destroy vaut false par défaut : l'identifier change, mais la session précédente reste sur le serveur. C'est invalidate() qui passe true. Pourquoi on se trompe : « changer d'identifiant » semble supprimer l'ancien.

  • Voir l’explication : La documentation ne mentionne pas le test.

    La documentation ne mentionne pas le test. Elle parle de lire et d'écrire ; c'est le code qui montre que tester compte aussi. Sur ce point précis, se fier au texte seul donne une réponse fausse.

  • Voir l’explication : Cookie, démarrage et cache privé sont trois effets distincts.

    Cookie, démarrage et cache privé sont trois effets distincts. Une session neuve vide, simplement testée, rend la réponse privée mais n'envoie aucun cookie. Pourquoi on se trompe : on les croit liés par une même cause.

Does Session::has() necessarily send a session cookie?
