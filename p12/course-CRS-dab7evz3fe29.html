Objectif

L'article 42 existe dans le catalogue. Le navigateur veut une page HTML, tandis qu'un client de notre branche JSON veut des données structurées. La ressource reste la même ; sa représentation, la forme transmise au client, peut changer.

Nous allons lire les préférences de GET /blog/42, les confronter aux formats réellement disponibles, puis annoncer le choix et ses critères de cache. Lire un header avec Symfony n'effectue pas à lui seul ces trois opérations.

Fil du cours
1. LIRE        Accept, Accept-Language…      → ce que le client préfère
2. CHOISIR     parmi ce que l'action produit → décision du serveur (q, spécificité)
3. ANNONCER    Content-Type, Content-Language, Vary → ce qui a été choisi et pourquoi

L'essentiel

À comprendre

À retenir en priorité
  1. Content-Type annonce la représentation choisie.
  2. Vary protège la séparation des variantes en cache.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Une même URL (/blog/42) doit pouvoir servir un navigateur (HTML) et une API (JSON). Plutôt que deux URL, HTTP prévoit que le client exprime des préférences et que le serveur choisit : c'est la content negotiation.
  • Le piège de fond. Lire Accept n'est qu'un tiers du travail. Trier une liste ≠ choisir une représentation ≠ annoncer le choix. Symfony fournit des accessors, pas le moteur de décision.
  • Ce que l'auteur veut que vous compreniez. q est une préférence relative, q=0 est un refus, la règle la plus spécifique fixe le poids d'un candidat, et Vary décrit les critères pour les caches.
  • Pourquoi c'est à l'examen. Les questions portent sur la grammaire de q, identity, proactive/réactive, Vary: *, 406/415, et sur ce que getAcceptableContentTypes() et getPreferredFormat() font — et ne font pas.

Supposons que l'action sache produire HTML et JSON. Accept décrit les types de contenu souhaités, appelés media types, comme text/html ou application/json. Accept-Language porte des préférences de langue ; Accept-Encoding concerne les codages du contenu, par exemple la compression. Ces informations ne créent pas un format que le serveur ne sait pas produire.

Le paramètre q, facteur de qualité, exprime une préférence relative, pas la qualité technique du document. Il vaut 1 lorsqu'il est absent. Le serveur doit déterminer la préférence applicable à chaque représentation disponible avant de choisir.

Côté Symfony 8.0, getAcceptableContentTypes() expose une liste triée, pas un moteur complet de négociation. getPreferredFormat() retourne un nom de format et donne priorité au format déjà fixé sur la Request, notamment par _format, lors de son calcul. Nous allons observer ces raccourcis sans leur attribuer une validation complète du contrat HTTP. Si aucun format connu n'est trouvé, getPreferredFormat() retourne son argument de repli, html par défaut. Ce résultat ne prouve donc pas à lui seul une préférence HTML exprimée par le client.

┌──────────────────────────────┐   ┌───────────────────────────────────────┐
│ ACCESSOR SYMFONY             │   │ CE QU'IL NE FAIT PAS                  │
├──────────────────────────────┤   ├───────────────────────────────────────┤
│ getAcceptableContentTypes()  │   │ ne choisit pas ; ne retire pas q=0 ;  │
│  → liste triée (q, puis      │   │ n'applique pas la spécificité aux     │
│    ordre d'écriture)         │   │ candidats disponibles                 │
├──────────────────────────────┤   ├───────────────────────────────────────┤
│ getPreferredFormat('html')   │   │ ne sérialise rien ; ne vérifie pas    │
│  → format déjà posé (_format)│   │ que l'action sait produire ce format ;│
│    sinon 1er format connu    │   │ repli 'html' ≠ préférence HTML        │
│    sinon l'argument de repli │   │ exprimée                              │
└──────────────────────────────┘   └───────────────────────────────────────┘

Le schéma

À retenir en priorité
  1. Proactive signifie server-driven.
  2. Réactive signifie agent-driven.

Où en est-on ? Avant de lire les headers un par un, voici la règle la plus contre-intuitive du cours : laquelle des règles d'un header Accept s'applique à un candidat donné ? On ajoute une variante texte brut au laboratoire pour la rendre visible. Ce schéma prépare l'étape 2 (choisir).

Pour isoler la règle de spécificité, ajoutons une variante texte brut à notre laboratoire. Le client accepte les types text/* avec un poids de 0.8, mais nomme HTML précisément avec un poids de 0.2. Lequel s'applique à HTML ?

En bleu, la règle applicable attribue à chaque candidat son poids. HTML reçoit 0.2, et non le meilleur poids de tous les motifs auxquels il correspond. Le texte brut reçoit 0.8. En orange, la politique applicative choisit ensuite entre les variantes disponibles ; ici elle privilégie cette qualité et retient le texte brut.

En vert, Content-Type annonce le résultat et Vary: Accept décrit le critère de variation pour le cache. Vary ne produit pas la variante et ne rend pas à lui seul la Response stockable. Aucun accessor de Request n'accomplit seul toute cette chaîne.

Pourquoi HTML reçoit-il 0.2 et pas 0.8 ? Le client a écrit une règle nominative pour HTML. Elle exprime sa volonté précise ; la règle générique text/* couvre « le reste des types texte ». Prendre le plus grand poids parmi les règles qui correspondent ignorerait cette exception.

L'exemple : lire les préférences

Exemple concret

À retenir en priorité
  1. getAcceptableContentTypes() lit les media types du header Accept.
  2. getPreferredFormat() donne priorité au format déjà fixé sur la Request.

Où en est-on ? Étape 1 sur 3 : lire. Retour aux préférences habituelles d'un navigateur, avec du code minimal : on fabrique la Request, on lit la liste triée, puis le format préféré.

Revenons aux préférences usuelles d'un navigateur. Avec PHP 8.4 et HttpFoundation 8.0 chargés par l'autoloader, construisons une Request locale, sans envoyer de message réseau :

use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/blog/42', 'GET');
$request->headers->set('Accept', 'text/html,application/xhtml+xml,application/json;q=0.9,*/*;q=0.8');

Les appels suivants retournent les valeurs indiquées en commentaire ; ils ne rendent ni page HTML ni document JSON :

// Accept: text/html,application/xhtml+xml,application/json;q=0.9,*/*;q=0.8
$request->getAcceptableContentTypes();
// ['text/html', 'application/xhtml+xml', 'application/json', '*/*']

$request->getPreferredFormat();     // 'html' — sauf si _format est posé

HTML et XHTML ont chacun le poids implicite 1 ; leur ordre initial départage ces deux entrées dans la liste Symfony. JSON suit avec 0.9, puis le joker avec 0.8. Le nom de format retourné est html.

Accept: text/html , application/xhtml+xml , application/json;q=0.9 , */*;q=0.8
        q=1 (défaut)   q=1 (défaut)          q=0.9                   q=0.8
        └ index 0      └ index 1             └ 3ᵉ                    └ 4ᵉ
tri : qualité décroissante, puis ordre d'écriture à qualité égale

Pourquoi getPreferredFormat() rend-il html ? Il parcourt la liste triée et traduit le premier media type qu'il sait nommer (text/html → html). Si rien n'est reconnu, il rend l'argument de repli ('html' par défaut) : ce html peut donc être un simple défaut.

Pour observer la priorité du format de Request, utilisons un autre object, configuré avant le premier appel :

use Symfony\Component\HttpFoundation\Request;

$request = Request::create('/blog/42', 'GET');
$request->headers->set('Accept', 'text/html');
$request->attributes->set('_format', 'json');
echo $request->getPreferredFormat();

La sortie est json. Nous avons posé l'attribute à la main pour simuler une information de route ; aucune route n'a été exécutée. Ce retour ne sérialise pas l'ArticleView, ne vérifie pas que l'action sait produire du JSON et ne garantit pas que le client l'acceptera. Ces accessors mémorisent des résultats sur la Request : modifier les entrées après leur lecture n'est pas une façon fiable de relancer la négociation. Prépare les entrées avant l'inspection, comme ici.

Le facteur de qualité, exactement

À retenir en priorité
  1. Sans q, la qualité vaut 1.
  2. q=0 est un refus, pas une faible préférence.

Où en est-on ? Étape 2 sur 3 : choisir. On connaît la liste des préférences ; il faut maintenant leur donner un sens exact (valeur par défaut, bornes, refus, spécificité) pour décider entre HTML et JSON.

Nous devons maintenant choisir entre HTML et JSON, pas simplement afficher la liste du header. Sans q, une entrée vaut 1, quelle que soit sa position. L'échelle va de 0 à 1, avec au plus trois décimales : 0.001 est le plus petit poids positif représentable, et q=0.3333 est mal formé selon la grammaire HTTP. Le nom du paramètre q est insensible à la casse.

La valeur 0 signifie « non acceptable », pas « disponible en dernier recours parmi les choix acceptés ». Il faut aussi appliquer le motif le plus spécifique à chaque candidat. Pour HTML, text/html est plus précis que text/*, lui-même plus précis que */*. Cette opération fixe d'abord le poids du candidat ; elle n'est pas un classement universel des noms de types.

Écriture Verdict
q absent poids 1
q=0.001 valide, le plus petit poids positif
Q=1.000 valide (nom q insensible à la casse ; 3 décimales max)
q=0 valide : non acceptable
q=0.3333 mal formé (4 décimales)

Prenons ce header isolé :

Accept: text/*;q=0.8, text/html;q=0.2, application/json;q=0.5

Si l'action propose seulement HTML et JSON, HTML reçoit 0.2 et JSON 0.5. Une politique privilégiant ce poids choisit JSON. Elle ne peut pas attribuer 0.8 à HTML en ignorant la règle exacte, ni produire du texte brut simplement parce que text/* est en tête.

Candidat        Règles qui correspondent            Règle retenue   Poids
text/html       text/* (0.8)  text/html (0.2)       text/html       0.2
application/json application/json (0.5)             application/json 0.5
→ JSON (0.5) l'emporte sur HTML (0.2)

La même règle explique l'exclusion suivante :

Accept: */*;q=0.8, image/png;q=0

PNG est refusé selon la préférence exprimée malgré le joker général. Choisir le maximum de tous les poids correspondants annulerait à tort cette exclusion.

Pour Accept-Language, ne fonde pas un contrat portable sur l'ordre d'écriture de langues de qualité égale : la RFC précise qu'on ne peut pas s'y fier. Dans Accept-Encoding, identity signifie absence de codage de contenu ; ce n'est ni l'identité de l'utilisateur ni « tout codage est acceptable ».

getAcceptableContentTypes() trie les entrées par qualité décroissante, puis par ordre d'écriture, sans appliquer ce raisonnement de spécificité à tous les candidats disponibles et sans retirer les q=0. AcceptHeader permet de lire des entrées et leurs attributes, mais lire ou trier ces données ne remplace pas la politique de sélection. Le nom « acceptable » de l'accessor ne doit pas te faire perdre les exclusions exprimées.

Pourquoi l'accessor ne suffit-il pas ? Il rend les clés du header triées (array_keys(AcceptHeader::all())) : les q=0 y figurent encore, et aucune comparaison avec vos formats disponibles n'a eu lieu. (La classe AcceptHeader de la branche 8.0 propose par ailleurs get(), qui pour un type donné préfère la règle la plus spécifique ; l'accessor Request, lui, ne l'utilise pas.)

🌍 In Real Life

La situation : un convive préfère les desserts en général, mais refuse précisément un dessert donné ; la préférence générale n'annule pas cette exception.

L’équivalent dans Symfony : préférence générale → joker Accept ; exception précise → media range spécifique ; refus → q=0 ; plats disponibles → représentations réellement produisibles.

Retour à la réalité technique : la spécificité fixe d'abord le poids applicable à chaque candidat. getAcceptableContentTypes() trie des entrées sans réaliser tout ce choix ni éliminer les refus ; la politique applicative reste nécessaire.

🧠 Comment le mémoriser : « La règle précise fixe le poids. » Image mentale : un dessert barré dans une catégorie appréciée. Question-réflexe : quelle règle s'applique à ce candidat exact ?

⚠️ À ne pas confondre : préférence relative, qualité du document et disponibilité du format.

Repère — Proactive contre réactive :

Question: Who selects the representation in proactive negotiation?

Answer: The server; in reactive negotiation the client selects from alternatives.

Proactive signifie server-driven. Réactive signifie agent-driven.

Repère de l’exemple :

Question: Which Request method returns the client's accepted media types in preference order?

Answer: getAcceptableContentTypes(); getPreferredFormat() instead returns a known format and gives an existing request format priority.

getAcceptableContentTypes() lit les media types du header Accept. getPreferredFormat() donne priorité au format déjà fixé sur la Request.

Les headers de Response

Où en est-on ? Étape 3 sur 3 : annoncer. Le choix est fait ; il faut le dire dans la Response, et dire aux caches de quoi il dépendait. Sans cette annonce, un cache pourrait resservir du HTML à un client JSON.

Notre action a choisi une représentation JSON destinée au lectorat francophone, en tenant compte d'Accept et d'Accept-Language. Elle peut décrire ce résultat par ces headers, extrait d'une Response :

Content-Type: application/json
Content-Language: fr
Vary: Accept, Accept-Language

Content-Type annonce le type effectivement envoyé. Content-Language décrit la langue du public auquel la représentation est destinée ; il ne traduit pas son contenu. Vary énumère les headers de Request qui ont influencé la sélection afin de distinguer les copies réutilisables. Si _format impose une variante indépendamment d'Accept, ne prétends pas que cet accessor a négocié le résultat à partir d'Accept.

Header de Response Dit… Ne fait pas…
Content-Type le type réellement envoyé ne produit ni ne convertit le contenu
Content-Language la langue du public visé ne traduit rien
Vary quels headers de Request ont influencé le choix ne produit pas la variante ; ne rend pas seul la Response stockable

Pourquoi Vary ? Un cache stocke la Response sous l'URL /blog/42. Sans Vary: Accept, il ne sait pas que cette copie JSON ne convient qu'aux requêtes qui demandaient du JSON : le client suivant, qui voulait du HTML, reçoit du JSON. Vary est la « clé secondaire » de la copie.

RFC 9110 §12.5.5 formule pour Vary une recommandation SHOULD, avec des exceptions, notamment lorsque d'autres directives limitent déjà la réutilisation. Ce n'est pas une obligation universelle pour toute Response. Pour les variantes publiques de notre exemple, annoncer les critères réels évite néanmoins de servir du HTML à un client qui avait sélectionné du JSON.

Vary: * est légal pour l'origine : le cache ne peut pas déterminer la réutilisation à partir des seuls headers de la Request. Un proxy ne doit pas générer cette valeur. Elle n'est ni une déclaration de tous les formats disponibles ni un synonyme de no-store.

Si aucune représentation ne convient aux préférences, le serveur peut répondre 406 Not Acceptable, ou décider de les ignorer et d'envoyer une représentation correctement annoncée. Le client pourrait alors ne pas savoir l'utiliser : le contrat de notre API doit rendre ce comportement prévisible. Ce problème de sortie est distinct du 415 d'un import dont le format entrant n'est pas pris en charge.

406 Not Acceptable            415 Unsupported Media Type
 sens : SORTIE                 sens : ENTRÉE
 « je n'ai rien qui           « je ne sais pas lire le corps
   corresponde à ton Accept »   que tu m'envoies (Content-Type) »

🌍 In Real Life

La situation : la cuisine étiquette le plat servi et note les critères qui ont distingué cette commande d'une autre.

L’équivalent dans Symfony : plat livré → Content-Type ; public linguistique visé → Content-Language ; critères de sélection utiles aux copies → Vary.

Retour à la réalité technique : ces champs décrivent la décision, sans produire ni traduire le contenu. Vary ne rend pas seul une réponse stockable ; Vary: * n'est pas no-store. Un _format imposé n'est pas une négociation complète d'Accept.

🧠 Comment le mémoriser : « Décrire le résultat et sa variation. » Image mentale : étiquette du plat et fiche de sélection. Question-réflexe : quels headers ont réellement influencé cette variante ?

⚠️ À ne pas confondre : 406 pour l'offre de sortie et 415 pour le contenu entrant.

Le client commande « français si possible, sinon anglais ». Content-Language annonce le choix servi ; Vary indique au classeur du cache de garder des versions séparées selon Accept-Language.

Proactive contre réactive

Où en est-on ? Prolongement des trois étapes : jusqu'ici, c'est le serveur qui a décidé. La RFC décrit une seconde famille, où le client décide. Question unique : qui pilote le choix ?

Dans le trajet que nous venons de suivre, le client envoie ses préférences avec GET et le serveur choisit la représentation de l'article. C'est la négociation proactive, dite server-driven (§12.1). Le serveur peut prendre en compte des informations explicites comme Accept et des caractéristiques implicites, par exemple l'adresse réseau ou des éléments de User-Agent. Ces indices ne prouvent pas l'identité ou les capacités réelles du lecteur.

Une autre politique consiste à proposer des alternatives puis à laisser le client choisir celle qu'il redemandera. C'est la négociation réactive, dite agent-driven (§12.2), illustrée notamment par une réponse 300 Multiple Choices contenant des possibilités. Elle peut nécessiter un échange supplémentaire ; ce n'est pas un mécanisme asynchrone ou un événement Symfony.

Le mot driven désigne donc celui qui pilote le choix : le serveur dans la première approche, le client dans la seconde. Connaître les deux évite de confondre une liste d'alternatives avec un échec obligatoirement traduit en 406.

🌍 In Real Life

La situation : le restaurant choisit un plat d'après les préférences reçues, ou présente une liste pour laisser le convive commander ensuite.

L’équivalent dans Symfony : choix par le serveur → négociation proactive ; alternatives puis nouveau choix du client → négociation réactive.

Retour à la réalité technique : la seconde peut demander un échange supplémentaire, par exemple après 300. Aucun accessor de Request ne réalise automatiquement ce parcours ; un repli ignorant une préférence est une politique distincte.

🧠 Comment le mémoriser : « Qui choisit la variante ? » Image mentale : cuisine décidant face au convive choisissant sur la liste. Question-réflexe : le choix est-il déjà effectué ou reste-t-il au client ?

⚠️ À ne pas confondre : négociation réactive, événement Symfony et tâche asynchrone.

Pièges d'examen

Piège à éviter

  • Voir l’explication : q=0 refuse explicitement.

    q=0 refuse explicitement. Accept: */*;q=0.8, image/png;q=0 signifie « tout sauf du PNG ». Si la politique respecte ces préférences, le joker ne peut pas réhabiliter PNG ; un repli ignorant Accept est une décision distincte à annoncer, pas une autre interprétation de q. Pourquoi on se trompe : 0 « ressemble » au plus petit poids, donc à « dernier recours ».

  • Voir l’explication : Sans q, la valeur est 1.0

    Sans q, la valeur est 1.0 — pas 0, et pas une pondération implicite par la position. Dans l'exemple du navigateur, HTML et XHTML ont donc le même poids ; le tri de l'accessor les conserve dans l'ordre initial. Pourquoi on se trompe : on croit que « premier écrit = préféré » par défaut, alors que c'est seulement le départage à qualité égale.

  • Voir l’explication : Oublier Vary peut masquer un bug de cache pendant le développement.

    Oublier Vary peut masquer un bug de cache pendant le développement. Sans cache réutilisant les variantes dans ton test, les réponses semblent correctes ; avec réutilisation, une mauvaise représentation peut ressortir. Un environnement local peut aussi disposer d'un cache : ce n'est pas le lieu d'exécution qui garantit l'absence de symptôme. Pourquoi on se trompe : « ça marche chez moi » prouve seulement l'absence de cache partagé.

  • Voir l’explication : Accept est une préférence, pas une constraint.

    Accept est une préférence, pas une constraint. Un serveur peut répondre autre chose ; il l'annonce par Content-Type. Pour notre branche JSON, décide explicitement entre 406 et repli documenté. Le droit de ne pas suivre une préférence n'est pas une raison de décrire un body JSON comme du HTML. Pourquoi on se trompe : on croit que 406 est obligatoire dès que Accept n'est pas satisfait.

  • Voir l’explication : getAcceptableContentTypes() ≠ moteur de négociation.

    getAcceptableContentTypes() ≠ moteur de négociation. Il trie et ne filtre rien : les q=0 restent dans la liste. Pourquoi on se trompe : « acceptable » dans le nom laisse croire que la liste est déjà filtrée.

Application

À retenir en priorité
  1. Content-Type annonce la représentation choisie.
  2. Vary protège la séparation des variantes en cache.
  3. Sans q, la qualité vaut 1.
  4. q=0 est un refus, pas une faible préférence.

Fiche express

À mémoriser

De la préférence reçue à la variante envoyée, garde sept repères :

  • Une ressource, plusieurs représentations ; le client préfère, le serveur choisit.
  • q par défaut 1 ; q=0 refuse ; 0.001 le plus faible ; 3 décimales.
  • La spécificité choisit le pattern qui fixe le q d'un type, elle n'ordonne pas deux types entre eux.
  • getAcceptableContentTypes() : qualité, puis ordre d'écriture.
  • getPreferredFormat() : format de Request, notamment _format, avant Accept lors du calcul ; pas un sérialiseur ni une vérification complète des préférences.
  • Variantes réutilisables : annoncer leurs critères avec Vary. Sans représentation acceptable : 406 ou préférence ignorée, pas un 406 systématiquement obligatoire.
  • Proactive = server-driven ; réactive = agent-driven.

Moyen mnémotechnique pour l'approche proactive : « Le client préfère, le serveur choisit, Content-Type décrit, Vary distingue les variantes ».

🧠 À retenir pour la certification

  • Accept = préférence (pas contrainte) ; q ∈ [0 ; 1], 3 décimales, défaut 1, 0 = refus.
  • La règle la plus spécifique fixe le poids d'un candidat (text/html > text/* > */*).
  • getAcceptableContentTypes() : tri qualité puis ordre d'écriture, q=0 conservés ; getPreferredFormat() : _format d'abord, repli html.
  • Réponse : Content-Type, Content-Language, Vary (SHOULD, pas MUST universel) ; Vary: * interdit à un proxy.
  • 406 = sortie impossible, 415 = entrée non supportée.
  • Proactive = serveur pilote ; réactive = client pilote (ex. 300).

Phrase de mémorisation : « Le client préfère avec q, la règle précise fixe le poids, le serveur choisit puis annonce avec Content-Type et Vary. »
