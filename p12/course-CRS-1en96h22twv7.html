Objectif

Le catalogue en mémoire sait distinguer l'article 42 de l'article 999 absent. Il reste à vérifier le contrat HTTP : /blog/42 doit atteindre blog_show et afficher l'article ; /blog/999 doit produire une réponse 404. Le test d'application relie ces résultats au routage, aux services et au rendu, sans lancer un serveur HTTP externe.

Question centrale du cours : comment simuler un visiteur qui appelle /blog/42, et que vérifier dans ce qu'il reçoit ?

L'essentiel

À comprendre

À retenir en priorité
  1. WebTestCase ajoute le client de test.
  2. Il hérite de KernelTestCase.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Le test unitaire du catalogue ne prouve pas que la route, le contrôleur et la vue sont bien assemblés. Il faut un test qui envoie une requête comme un visiteur et regarde la réponse. Mais lancer un vrai serveur HTTP serait lent et fragile : Symfony fournit un client qui appelle directement le kernel.
  • Le piège de fond. « Application » ne veut pas dire « navigateur ». Le client ne traverse ni serveur frontal, ni réseau, ni JavaScript. Et envoyer la requête n'est pas tester : sans assertion, rien n'est prouvé.
  • Ce que l'auteur veut que vous compreniez. Trois attentes distinctes (statut, route, contenu) valent mieux qu'une seule : chacune détecte une panne que les autres laissent passer.
  • Pourquoi c'est à l'examen. WebTestCase étend KernelTestCase, createClient() démarre déjà le kernel, l'ordre de lecture des fichiers .env, when@test, et la portée exacte des assertions (2xx ≠ 200).

Un test d'application vérifie ce qu'un utilisateur peut observer : statut HTTP, redirection, titre ou contenu d'une page. WebTestCase fournit un KernelBrowser qui envoie les requêtes à l'application sans serveur HTTP externe. Il ne lance pas un navigateur JavaScript.

WebTestCase étend KernelTestCase ; createClient() démarre déjà le kernel, normalement en environnement test. Une assertion Symfony exprime ensuite l'attente et rend l'échec lisible. Par exemple, « réponse réussie » accepte tout statut 2xx, tandis que « statut exactement 200 » exige une assertion sur ce code précis.

Il traverse l'application dans ce périmètre, pas le serveur frontal, le réseau, un reverse proxy externe ou un moteur JavaScript. Une assertion est une attente vérifiée ; envoyer la requête sans examiner son résultat ne prouve pas que le visiteur a obtenu la bonne page.

Le schéma

À retenir en priorité
  1. Le kernel est déjà démarré par cet appel.
  2. Éviter un bootKernel() préalable.

Où en est-on ? Début du cours : avant le code, on regarde le chemin d'un test d'application. C'est la vue d'ensemble ; les sections suivantes zooment sur chaque case (le squelette, l'environnement, les assertions).

La première observation vient immédiatement après la réponse. Il n'est pas nécessaire de cliquer pour transformer un appel en test :

Rectangles bleus : appels et objets ; cylindre : données reçues ; losange : vérification. Le schéma montre un test d'une seule réponse. Pour un parcours plus long, clickLink() ou submitForm() déclenche une nouvelle requête : vérifier chaque étape utile plutôt que seulement la dernière page.

Ce que le client ne traverse pas :

Navigateur réel ─► réseau ─► serveur frontal ─► reverse proxy ─► PHP ─► kernel
                                                                       ▲
  KernelBrowser (test) ────────────────────────────────────────────────┘
  → saute tout ce qui précède le kernel, et n'exécute aucun JavaScript

L'exemple : la page d'accueil

Exemple concret

À retenir en priorité
  1. Une Request seule n'est pas une assertion.
  2. Vérifier le comportement observable.

Où en est-on ? On écrit le plus petit test d'application possible, avant de détailler le squelette. Code minimal d'abord : un client, une requête, trois assertions.

L'accueil reste un petit contrat indépendant : ce fragment suppose une route / nommée home, dont le h1 contient Hello World. Il s'inscrit dans une application Symfony 8.0 préparée pour les tests, avec PHPUnit 11.5 et les composants de navigation nécessaires :

use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

class PostControllerTest extends WebTestCase
{
    public function testHome(): void
    {
        $client = static::createClient();
        $client->request('GET', '/');           // une URL écrite en dur

        $this->assertResponseIsSuccessful();
        $this->assertRouteSame('home');
        $this->assertSelectorTextContains('h1', 'Hello World');
    }
}

Le statut, le nom de route et le texte sont trois attentes différentes. Une page d'erreur peut contenir un h1, et un autre contrôleur peut répondre 200 : aucune de ces observations isolée ne prouve les deux autres.

Ce que fait chaque ligne :

Ligne Ce que Symfony fait
static::createClient() démarre le kernel (env test) et rend un KernelBrowser
$client->request('GET', '/') construit une Request, la passe au kernel, garde la Response
assertResponseIsSuccessful() le statut est dans la famille 2xx
assertRouteSame('home') la route qui a répondu s'appelle home
assertSelectorTextContains('h1', …) le HTML contient un h1 avec ce texte

Le squelette

À retenir en priorité
  1. L'ordre d'initialisation est imposé.
  2. Créer le client directement dans WebTestCase.

Où en est-on ? Étape 1 sur 3 : on regarde la structure d'un test d'application (qui crée le client, quelle URL utiliser). C'est le « comment j'arrange mon test » avant de parler d'environnement et d'assertions.

🌍 In Real Life

La situation : un contrôleur qualité vient au restaurant avec l'adresse imprimée sur l'ancienne invitation. Il vérifie qu'elle mène toujours à la bonne entrée, sans demander d'abord la nouvelle adresse au personnel.

L’équivalent dans Symfony : adresse promise → URL littérale /blog/42 ; visite de contrôle → requête du client ; résultat attendu → assertions.

Retour à la réalité technique : générer l'URL à partir de la route modifiée peut masquer une rupture du contrat public. createClient() prépare déjà le Kernel ; un démarrage manuel préalable n'est pas requis.

🧠 Comment le mémoriser : « Tester l'adresse promise. » Image mentale : invitation conservée face à la porte actuelle. Question-réflexe : mon test suit-il le changement qu'il devait détecter ?

⚠️ À ne pas confondre : test du générateur d'URL et test de stabilité d'une URL publique.

L'arrangement commence par le client, pas par un démarrage manuel du kernel :

  • WebTestCase étend KernelTestCase et lui ajoute le client.
  • createClient() démarre le kernel : bootKernel() puis createClient() lève une LogicException — « Booting the kernel before calling "…WebTestCase::createClient()" is not supported, the kernel should only be booted once. ».
  • La documentation recommande une URL en dur : un test qui génère son URL suit un changement de route au lieu de le détecter.

Pourquoi bootKernel() puis createClient() échoue-t-il ? Parce que createClient() commence par vérifier que le kernel n'est pas déjà démarré (static::$booted), puis appelle lui-même bootKernel() et récupère le service test.client. Démarrer deux fois romprait l'idée « un kernel par test ».

createClient()
   ├─ kernel déjà démarré ? ── oui ──► LogicException
   └─ non → bootKernel() → service test.client → KernelBrowser

Avant / après, pourquoi l'URL en dur :

URL générée :  route renommée /blog/{id} → /articles/{id}
               le test génère la nouvelle URL → il reste VERT (changement caché)
URL en dur  :  le test appelle toujours /blog/42
               → 404 : la rupture du contrat public est détectée

Une version plus stricte du contrat d'accueil, indépendante du précédent texte de fixture, exige exactement 200 et le titre Accueil :

<?php
use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

final class HomePageTest extends WebTestCase
{
    public function testHomeContract(): void
    {
        $client = static::createClient();
        $client->request('GET', '/');
        self::assertResponseStatusCodeSame(200);
        self::assertSelectorTextContains('h1', 'Accueil');
    }
}

Cette route et ce titre sont les prérequis de cet exemple, pas deux attentes contradictoires à appliquer simultanément à une même fixture. Pour le scénario commun du blog, dans une méthode d'un WebTestCase :

$client = static::createClient();
$client->request('GET', '/blog/42');
self::assertResponseStatusCodeSame(200);
self::assertRouteSame('blog_show');
self::assertSelectorCount(1, 'h1');

$client->request('GET', '/blog/999');
self::assertResponseStatusCodeSame(404);

Ce fragment suppose le catalogue stable 42 présent/999 absent et une vue avec un seul h1. Ajouter une attente sur le titre exact de la fixture pour distinguer l'article voulu d'un autre. La seconde requête teste l'absence d'article sur une route connue ; un chemin sans route est une autre cause de 404 à tester séparément.

L'environment `test`

À retenir en priorité
  1. Les tests doivent rester reproductibles.
  2. Les réglages test spécifiques restent séparés.

Où en est-on ? Étape 2 sur 3 : le client démarre le kernel « en environnement test ». Pourquoi ce nom compte-t-il, et d'où viennent les valeurs de configuration ? C'est ce que cette partie déroule.

Le jeu en mémoire doit rester stable d'une machine à l'autre. Le nom test sélectionne une configuration, pas une protection automatique contre l'accès à des services externes de production : vérifier les dépendances et adresses réellement utilisées.

La configuration propre aux tests va dans config/packages/test/ ou sous when@test. Les variables d'environment, une variable A définie dans les quatre files. Le tableau suppose le chargement Dotenv standard, sans remplacement forcé des variables existantes ni autre surcharge :

Situation Valeur de A
APP_ENV=test, les quatre files celle de .env.test.local
APP_ENV=test, sans .env.test.local celle de .env.test
APP_ENV=dev celle de .env.local
APP_ENV=test, A déjà définie dans le shell celle du shell

.env.local n'est pas lu en test, délibérément : une machine de développement ne doit pas modifier le résultat des tests.

Pourquoi ces résultats ? Dotenv::loadEnv() lit d'abord .env, puis .env.local seulement si l'environnement n'est pas dans la liste des environnements de test (['test'] par défaut), puis .env.<env>, puis .env.<env>.local. Le dernier fichier qui définit la variable gagne, sauf si la variable existe déjà dans le processus (pas de remplacement forcé).

APP_ENV=dev  :  .env → .env.local → .env.dev → .env.dev.local
APP_ENV=test :  .env →      (saut)  → .env.test → .env.test.local
                           └ .env.local volontairement ignoré
Le shell (vraie variable du processus) bat tous les fichiers.

Les « quatre fichiers » sont ici .env, .env.local, .env.test et .env.test.local ; en dev, le tableau suppose donc qu'aucun fichier spécifique à dev n'ajoute une autre valeur. Une vraie variable du processus garde sa priorité dans ce chargement. Les options explicites du kernel, la configuration PHPUnit et un bootstrap personnalisé doivent aussi être examinés avant de conclure qu'une variable vient d'un fichier donné.

framework.test: true rend disponible le client de test. PHPUnit seul ne l'installe pas : si createClient() signale que test.client manque, vérifier cette configuration et la présence de BrowserKit. Ne pas corriger cette erreur en démarrant le kernel une deuxième fois.

Les assertions de Symfony

À retenir en priorité
  1. 201 est aussi un succès HTTP.
  2. Utiliser une assertion exacte si le contrat exige un code précis.

Où en est-on ? Étape 3 sur 3 : le client a fourni une réponse ; il faut maintenant la juger. Les assertions Symfony (trait BrowserKit) expriment chaque attente et expliquent l'échec.

🌍 In Real Life

La situation : recevoir une assiette ne prouve pas qu'elle contient le plat commandé. Le contrôle qualité vérifie séparément livraison, destination et contenu.

L’équivalent dans Symfony : livraison → statut HTTP ; commande reconnue → attribut de route ; plat attendu → titre et contenu HTML de /blog/42.

Retour à la réalité technique : une assertion 2xx, une assertion de route et une assertion de sélecteur établissent des faits différents. Un cookie envoyé dans cette réponse n'est pas la même observation qu'un cookie déjà présent dans le navigateur simulé.

🧠 Comment le mémoriser : « Une preuve par promesse. » Image mentale : trois cases distinctes sur le contrôle. Question-réflexe : quelle erreur pourrait encore passer malgré cette assertion ?

⚠️ À ne pas confondre : réponse réussie et contenu métier correct.

Choisir l'assertion selon la preuve cherchée : « article rendu », « redirection vers la connexion », « erreur de saisie 422 » ne se résument pas à « il y a du HTML ». Le tableau distingue également cookies envoyés dans la réponse et état conservé par le navigateur simulé :

Sur… Assertions
la Response assertResponseIsSuccessful() (tout 2xx), assertResponseStatusCodeSame(), assertResponseRedirects(), assertResponseHasHeader(), assertResponseHasCookie(), assertResponseIsUnprocessable() (422)
la Request assertRouteSame(), assertRequestAttributeValueSame()
le navigateur assertBrowserHasCookie(), assertBrowserHistoryIsOnFirstPage()
le contenu assertSelectorExists(), assertSelectorCount(), assertSelectorTextContains(), assertPageTitleSame(), assertInputValueSame(), assertCheckboxChecked()

Comparaison utile : cookie de la réponse ≠ cookie du navigateur.

assertResponseHasCookie() assertBrowserHasCookie()
Observe la réponse qui vient d'arriver le jar du navigateur simulé
Question « cette réponse envoie-t-elle ce cookie ? » « le navigateur le conserve-t-il ? »

Sur un échec, les assertions de réponse peuvent afficher headers et corps de la Response, là où assertEquals(200, $code) n'affiche qu'un nombre. self::setBrowserKitAssertionsAsVerbose(false) réduit l'affichage aux headers ; le parameter $verbose fait de même au cas par cas.

Pourquoi ce mode verbeux ? Quand un 200 attendu devient 500, le corps de la réponse contient la page d'erreur Symfony : sans lui, on devine. Le mode est actif par défaut ($defaultVerboseMode = true), et chaque assertion de réponse accepte ?bool $verbose pour le contourner.

Une assertion de texte « contient » n'exige pas l'égalité de tout le document. assertSelectorCount(1, 'h1') porte sur le nombre d'éléments ; elle ne vérifie ni le statut ni le nom de route. Garder ces attentes distinctes rend le diagnostic utile lorsqu'une page de connexion remplace la page article. Les détails d'échec peuvent contenir des données sensibles : employer des fixtures fictives et ne pas publier sans contrôle les réponses de test.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le test peut protéger l'URL publique.
  2. La génération suivrait la modification de route.
  • Voir l’explication : WebTestCase étend KernelTestCase

    WebTestCase étend KernelTestCase ; createClient() démarre déjà le kernel. Pourquoi on se trompe : on appelle bootKernel() « par prudence » avant createClient(), ce qui lève une LogicException.

  • Voir l’explication : .env.local est ignoré en test

    .env.local est ignoré en test, contrairement à .env.test.local. Pourquoi on se trompe : le nom « local » fait croire que tous les fichiers locaux sont lus partout.

  • Voir l’explication : assertResponseIsSuccessful() couvre tout le 2xx

    assertResponseIsSuccessful() couvre tout le 2xx, pas seulement 200 — une Response 201 satisfait aussi cette assertion. Pourquoi on se trompe : « success » est associé au code 200.

  • Voir l’explication : Une variable du shell bat .env.test.local

    Une variable du shell bat .env.test.local dans le chargement standard, sans remplacement forcé.

  • Voir l’explication : Une URL en dur protège le chemin public attendu

    Une URL en dur protège le chemin public attendu ; générer l'URL est un autre choix de contrat, qui ne détecte pas son changement de la même façon.

Fiche express

À mémoriser

À retenir en priorité
  1. La configuration de test est conditionnelle.
  2. Elle ne doit pas modifier l'environment de production.

Le test relie une entrée concrète à des résultats indépendants : 200, blog_show, structure et contenu de l'article ; puis 404 pour l'absence. Il complète le test unitaire du catalogue, il ne le remplace pas.

🧠 À retenir pour la certification :

  • WebTestCase étend KernelTestCase ; createClient() démarre le kernel (bootKernel() avant lui → LogicException).
  • Request et assertions ; interaction facultative si le scénario l'exige.
  • Config de test : when@test ou config/packages/test/.
  • .env → .env.test → .env.test.local ; .env.local ignoré ; le processus prioritaire dans le chargement standard.
  • assertResponseIsSuccessful() : tout 2xx ; assertRouteSame() : la route qui a répondu.
  • URL en dur, pas générée.

Moyen mnémotechnique : « Request, assertions ; interaction facultative selon le scénario ». Phrase de mémorisation : le client appelle le kernel sans réseau, et chaque attente (statut, route, contenu) est une preuve séparée.

Le client de test explique maintenant ce qui persiste entre ces requêtes, et pourquoi une redirection ou un redémarrage du kernel peut changer l'observation.
