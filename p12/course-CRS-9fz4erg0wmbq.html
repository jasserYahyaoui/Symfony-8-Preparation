Objectif

Pour afficher l'article 42, nous nommons trois choses différentes : le chemin /blog/42, la route blog_show et le callable App\Controller\BlogController::show. Un lien utilise le nom de route ; l'exécution utilise le callable. Les conventions rendent ces choix lisibles, elles ne remplacent pas leur configuration.

Connaître les conventions propres aux controllers, et savoir lesquelles sont obligatoires. Les conventions générales du framework — casse, préfixes Abstract, suffixes Interface et Trait — sont traitées dans le Module 03 — Architecture Symfony.

Question fil rouge : quand je n'écris pas un nom, qui l'invente, et d'après quelle règle exacte ?

L'essentiel

À comprendre

À retenir en priorité
  1. Le nom généré n'est pas une conversion générale en snake_case.
  2. Pour une même méthode, seuls les noms générés reçoivent les suffixes _1, _2 à partir du deuxième nom généré ; des noms explicites identiques peuvent se remplacer dans la collection.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Symfony a besoin de trois identifiants pour un même écran : un chemin (pour le navigateur), un nom de route (pour générer des liens) et un callable (pour exécuter le code). Comme on écrit rarement les trois à la main, il existe des conventions et des règles de génération automatique.
  • Le piège de fond. « Convention » ne veut pas dire « obligation ». Presque tout est libre ; une seule chose est obligatoire : l'unicité du nom de route.
  • Ce que l'auteur veut que vous compreniez. Le nom de route généré est calculé en deux couches : le component Routing produit un nom long, puis FrameworkBundle le raccourcit. L'examen vous demande de refaire ce calcul.
  • Pourquoi c'est à l'examen. Calculer app_lucky_number à partir de App\Controller\LuckyController::number, savoir que _1 ne concerne que les noms générés, et distinguer ce qui est obligatoire de ce qui ne l'est pas.

En résumé : presque rien n'est imposé à un controller : le suffixe Controller, la class de base, l'absence de suffixe Action sont des conventions. Une seule obligation : un route name unique. Quand on l'omet, Symfony le génère en deux couches — le component, puis FrameworkBundle qui le raccourcit — et c'est ce nom généré que l'examen fait calculer.

Les routes elles-mêmes (attributs #[Route], paramètres, génération d'URL) sont l'objet du module Routing ; ce cours ne traite que les noms.

Le schéma

À retenir en priorité
  1. _controller identifie le callable cible.
  2. Une class invocable peut omettre ::__invoke.

Où en est-on ? Le cours suit trois questions : qu'est-ce qui est obligatoire ? (« Rien n'est imposé, presque »), comment Symfony retrouve-t-il le code à exécuter ? (« Le format _controller »), comment une route sans nom en reçoit-elle un ? (« Le route name »). Le schéma ci-dessous répond à la troisième, la plus technique, en suivant la transformation du nom.

Trois noms pour un même écran « article 42 »
   ├─ chemin        /blog/42                         → matching de l'URL
   ├─ nom de route  blog_show                        → génération de liens
   └─ callable      App\Controller\BlogController::show  → exécution (_controller)

Bleu = calcul du nom, vert = identifiant utilisé pour générer une URL. Le dessin n'est pas une chaîne d'appels HTTP : ces noms sont déterminés au chargement des routes. L'exemple du tableau détaille les suffixes et alias. Un nom explicite stable évite qu'un renommage PHP casse les liens.

L'exemple : une route sans nom

Exemple concret

À retenir en priorité
  1. Sans name explicite, le loader construit un route name depuis la class et la method.
  2. FrameworkBundle raccourcit le nom ; ici le résultat est app_lucky_number.

Où en est-on ? Avant les règles, un cas minimal : une route sans name, dont on veut deviner le nom généré.

L'exemple réduit le problème à une action qui renvoie 42, sans accès aux données. Avant toute requête, le loader calcule app_lucky_number. Lors du matching, le chemin sélectionnera la route ; ce nom calculé servira notamment à retrouver la même route pour générer un lien.

namespace App\Controller;

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LuckyController extends AbstractController
{
    #[Route('/lucky/number')]
    public function number(): Response   // nom généré : app_lucky_number
    {
        return new Response('42');
    }
}

Le calcul, pas à pas (détaillé plus bas) :

App\Controller\LuckyController::number
  1. \ → _  et  + "_" + méthode       app_controller_luckycontroller_number
  2. tout en minuscules               (déjà fait ci-dessus)
  3. FrameworkBundle retire controller_ → app_lucky_number

🌍 In Real Life

La situation : une fiche du restaurant n’a pas reçu de référence manuelle ; le secrétariat en fabrique une à partir du poste et de l’opération décrits.

L’équivalent dans Symfony : fiche sans référence → #[Route('/lucky/number')] sans name ; référence calculée → app_lucky_number avec le loader FrameworkBundle ; consultation de la fiche → génération d’URL par son nom.

Retour à la réalité technique : le nom est établi au chargement des routes, pas par le contrôleur à chaque requête. Le contenu '42' de la Response ne participe pas à ce calcul. Le chemin et le nom de route restent deux valeurs distinctes.

🧠 Comment le mémoriser : « Sans nom écrit, un nom calculé. » Image mentale : tampon de référence sur une fiche déjà décrite. Question-réflexe : « Le nom vient-il d’un name explicite ou du loader utilisé ? »

⚠️ À ne pas confondre : charger la configuration des routes n’est pas charger un article.

Rien n'est imposé, presque

À retenir en priorité
  1. Un controller est un callable.
  2. Les route names doivent en revanche être uniques.

Où en est-on ? Question 1 sur 3 : qu'est-ce que je suis obligé de faire ? Pourquoi la poser d'abord ? Parce qu'au QCM, la tentation est de croire que les conventions (suffixe, classe de base) sont des règles du framework.

Nous pourrions appeler la classe du blog ShowArticle et la rendre invocable : ce choix ne change pas le contrat HTTP. En revanche, réutiliser blog_show pour une autre route peut écraser la première définition et changer la destination des liens. Le tableau distingue donc conventions de lisibilité et nécessité d'un identifiant non ambigu, pas toutes les obligations PHP d'un callable valide.

Élément Convention Obligatoire ?
class de controller suffixe Controller non
method d'action aucun suffixe Action non — mais le suffixe reste reconnu
class de base étendre AbstractController non
template snake_case, deux extensions non
route name unique dans l'application oui

Le template porte deux extensions : index.html.twig, la première étant le format produit. Cette convention ne fixe pas à elle seule le Content-Type de la Response. De même, l'unicité d'un nom de route est une exigence de conception : ne pas compter sur une exception systématique pour détecter les noms écrasés au chargement.

Décomposition d'un nom de template :

   blog/index.html.twig
          │     │    │
          │     │    └── engine : Twig le rend
          │     └─────── format produit : HTML
          └───────────── nom en snake_case

Pourquoi donc une seule obligation ? Parce qu'un nom de route est une clé dans une collection : deux routes de même nom ne peuvent pas coexister, la seconde remplace la première et tous les liens générés changent de cible. Un suffixe Controller ou une classe de base ne sont que du confort de lecture.

🌍 In Real Life

La situation : les postes du restaurant peuvent avoir des intitulés variés, mais deux fiches du registre ne doivent pas partager la même référence.

L’équivalent dans Symfony : intitulé lisible → convention du suffixe Controller ; référence de fiche → nom de route ; nouvelle fiche sous la même référence → définition susceptible de remplacer l’ancienne.

Retour à la réalité technique : les conventions de nommage ne dispensent pas d’un callable PHP valide ni d’une configuration correcte. L’unicité des noms évite l’écrasement dans la collection ; elle ne signifie pas qu’un doublon provoquera toujours une exception. Les extensions du template sont une convention, pas un en-tête HTTP.

🧠 Comment le mémoriser : « L’intitulé aide ; la référence identifie. » Image mentale : deux fiches disputant une même case. Question-réflexe : « Est-ce une convention de lecture ou une clé de configuration ? »

⚠️ À ne pas confondre : index.html.twig ne fixe pas à lui seul le Content-Type.

Le format `_controller`

Où en est-on ? Question 2 sur 3 : comment Symfony passe-t-il du nom de route au code à exécuter ? Le pont, c'est l'attribut de Request _controller.

Après le matching de /blog/42, _controller désigne l'action, tandis que id vaut encore une donnée de la Request. Le ControllerResolver transforme la désignation en callable utilisable, éventuellement en récupérant un contrôleur enregistré comme service. Ce n'est qu'ensuite que l'ArgumentResolver prépare les valeurs de show(). Ni le nom de la route ni son suffixe Controller ne chargent l'article en base.

App\Controller\BlogController::show : class pleinement qualifiée, ::, nom de method — la string que le router dépose dans l'attribute _controller. Pour une class invocable, la class seule suffit.

GET /blog/42
   │ Router : route reconnue → attributes
   │     _route      = blog_show
   │     _controller = App\Controller\BlogController::show
   │     id          = "42"
   ▼
ControllerResolver : _controller → callable
   ▼
ArgumentResolver   : prépare les arguments de show()
   ▼
show(...) est appelé

Vérifié dans AttributeRouteControllerLoader::configureRoute() (8.0) : si la méthode est __invoke, le défaut _controller vaut Classe::class seule ; sinon Classe::méthode. C'est exactement la règle « classe invocable → classe seule ».

🌍 In Real Life

La situation : le bon 42 indique « poste desserts, préparer ». Cette indication permet de trouver qui appeler ; elle n’est ni la personne ni les ingrédients.

L’équivalent dans Symfony : désignation écrite → _controller ; poste effectivement trouvé → callable fourni par ControllerResolver ; informations préparées séparément → arguments fournis par ArgumentResolver.

Retour à la réalité technique : la chaîne App\Controller\BlogController::show désigne classe et méthode ; une classe invocable peut être désignée seule. HttpKernel demande ces résolutions puis invoque l’action. La syntaxe avec :: n’impose pas une méthode statique : un contrôleur-service peut être obtenu par l’intégration conteneur.

🧠 Comment le mémoriser : « Une adresse d’appel n’est pas un appel. » Image mentale : nom du poste sur le bon, avant toute préparation. Question-réflexe : « Ai-je une désignation, un callable ou son résultat ? »

⚠️ À ne pas confondre : _route, _controller et id ne désignent pas la même chose ; aucun suffixe ne charge une entité.

Un standard téléphonique a besoin d'une extension qui répond, pas d'un intitulé de poste particulier. Le ControllerResolver cherche un callable ; le suffixe Controller améliore surtout la lecture humaine.

Le route name, et qui le génère

Où en est-on ? Question 3 sur 3, la plus calculatoire : quel nom reçoit une route sans name ? Rappel : si vous écrivez name: 'blog_show', tout ce qui suit est ignoré.

Si nous omettons name sur BlogController::show, les liens dépendent d'un nom dérivé de PHP. Renommer la méthode peut donc casser la génération d'URL alors que le chemin /blog/{id} reste identique. Un nom explicite blog_show sépare ce contrat de navigation du nom de la méthode ; les règles ci-dessous expliquent exactement le cas où ce nom explicite manque.

Couche 1 : le component Routing

Le component Routing, dans AttributeClassLoader::getDefaultRouteName(), remplace les \ par des _, ajoute _ et le nom de la method, met le tout en minuscules, puis ajoute _ et defaultRouteIndex à partir du deuxième nom généré pour une même method. Une route au nom explicite n'appelle pas ce calcul et n'incrémente pas cet index.

Couche 2 : FrameworkBundle

AttributeRouteControllerLoader, de FrameworkBundle, retire ensuite les segments bundle_ et controller_, un suffixe action, et les __ restants.

Vérifié dans le code 8.0 : l'expression utilisée est preg_replace('/(bundle|controller)_/', '_', …), puis, si la méthode se termine par Action ou _action, preg_replace('/action(_\d+)?$/', '\\1', …) (l'index _1 éventuel est conservé), et enfin str_replace('__', '_', …). Conséquence : controller_ est retiré partout dans la chaîne, y compris à la fin d'un mot (blogcontroller_ → blog_), ce qui explique que luckycontroller_number devienne lucky_number.

Method Component seul Avec FrameworkBundle
LuckyController::number app_controller_luckycontroller_number app_lucky_number
BlogController::showAction app_controller_blogcontroller_showaction app_blog_show
deuxième route sans nom explicite de la même method suffixe _1 app_lucky_number_1

Rien ne découpe le CamelCase : LuckyController devient luckycontroller. Un name porté par la class est préfixé. Une method qui ne déclare qu'une route reçoit en plus l'alias App\Controller\LuckyController::number.

Calcul détaillé de BlogController::showAction :

App\Controller\BlogController::showAction
  1. \ → _ , + _méthode, minuscules   app_controller_blogcontroller_showaction
  2. retrait de « controller_ »       app__blog_showaction   (deux fois)
  3. suffixe action retiré            app__blog_show
  4. __ → _                           app_blog_show

Comparaison des deux couches :

┌──────────────────────────────────────┐ ┌──────────────────────────────────────┐
│     COMPONENT Routing seul           │ │   AVEC FrameworkBundle (Symfony)     │
├──────────────────────────────────────┤ ├──────────────────────────────────────┤
│ \ → _, + méthode, minuscules         │ │ idem, PUIS retire bundle_/controller_│
│ index _1, _2 pour les noms générés   │ │ retire le suffixe action, __ → _     │
│ app_controller_luckycontroller_number│ │ app_lucky_number                     │
└──────────────────────────────────────┘ └──────────────────────────────────────┘

Préfixe de classe, index et alias

  • Un name sur la class est un préfixe posé devant le nom généré complet (voir Question 2).
  • _1, _2 : uniquement pour les noms générés d'une même méthode ; un nom explicite n'incrémente rien.
  • L'alias FQCN::méthode n'est ajouté que si la méthode ne porte qu'une route.

🌍 In Real Life

La situation : le registre peut fabriquer une référence à partir d’un intitulé long, puis la raccourcir selon les règles de l’établissement. Renommer l’intitulé change alors la référence calculée.

L’équivalent dans Symfony : première référence → calcul de AttributeClassLoader ; raccourcissement → loader FrameworkBundle ; référence choisie indépendamment → name: 'blog_show'.

Retour à la réalité technique : le tableau décrit des règles précises, pas une conversion générale de CamelCase en snake_case. Le calcul concerne les noms par défaut ; préfixes et index éventuels restent à prendre en compte. Un alias classe/méthode suppose ici une seule route sur la méthode.

🧠 Comment le mémoriser : « Un nom calculé suit son origine. » Image mentale : référence automatique attachée à l’étiquette PHP. Question-réflexe : « Un renommage de méthode modifierait-il les liens générés par ce nom ? »

⚠️ À ne pas confondre : le nom explicite stabilise l’identifiant de navigation, pas toutes les autres configurations du contrôleur.

Sans name explicite, le loader construit un route name depuis la class et la method. FrameworkBundle raccourcit le nom ; ici le résultat est app_lucky_number.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le suffixe Controller est une convention, pas une constraint

    Le suffixe Controller est une convention, pas une constraint — pas plus qu'étendre une class de base ne l'est. Pourquoi on se trompe : tous les exemples de la documentation utilisent ce suffixe, on le prend pour une règle.

  • Voir l’explication : Le nom généré n'est pas du snake_case.

    Le nom généré n'est pas du snake_case. Rien ne découpe le CamelCase : LuckyController devient luckycontroller, pas lucky_controller. La lisibilité de app_lucky_number vient du retrait du segment controller_, pas d'une conversion de casse. Le snake_case est recommandé pour les templates. Pourquoi on se trompe : le résultat final ressemble à du snake_case.

  • Voir l’explication : Sans FrameworkBundle, le nom généré reste celui du component.

    Sans FrameworkBundle, le nom généré reste celui du component. Le nom court est un apport du bundle. Pourquoi on se trompe : on pense que le component produit déjà le nom court.

  • Voir l’explication : Les suffixes _1, _2 concernent les noms générés, pas les noms explicites.

    Les suffixes _1, _2 concernent les noms générés, pas les noms explicites. Pour une même méthode, le deuxième nom généré reçoit _1, le troisième _2. Deux routes portant le même nom explicite ne sont pas renommées ainsi : l'ajout dans la collection peut remplacer la route précédente. Pourquoi on se trompe : on imagine un anti-doublon automatique.

  • Voir l’explication : Le suffixe Action n'est plus utilisé, mais il est encore reconnu

    Le suffixe Action n'est plus utilisé, mais il est encore reconnu : le loader du bundle le retire du nom généré. Pourquoi on se trompe : « n'est plus utilisé » est lu comme « n'est plus géré ».

  • Voir l’explication : _controller ne charge rien.

    _controller ne charge rien. C'est une désignation (FQCN::méthode) ; c'est le ControllerResolver qui la transforme en callable. Pourquoi on se trompe : on confond la chaîne et ce qu'elle désigne.

Application

À retenir en priorité
  1. Le nom généré n'est pas une conversion générale en snake_case.
  2. Pour une même méthode, seuls les noms générés reçoivent les suffixes _1, _2 à partir du deuxième nom généré ; des noms explicites identiques peuvent se remplacer dans la collection.
  3. Un controller est un callable.
  4. Les route names doivent en revanche être uniques.

Fiche express

À mémoriser

🧠 À retenir pour la certification :

  • Une seule obligation : un route name unique.
  • Controller, AbstractController, pas d'Action : des conventions.
  • _controller = FQCN::méthode, ou le FQCN seul si invocable.
  • Nom généré : component en minuscules, sans découpe du CamelCase.
  • FrameworkBundle retire controller_ et action → app_lucky_number.
  • Deuxième nom généré de la méthode : _1, puis _2 ; aucun de ces suffixes pour les noms explicites. Alias FQCN seulement pour une route.

Repère de révision : « Nom implicite : calcul du component, puis normalisation du bundle ». Un nom explicite peut contenir controller ; sa seule orthographe ne permet pas de déduire le loader utilisé.

Phrase de mémorisation complète : « Je ne suis obligé qu'à un nom de route unique ; sans nom, le component en fabrique un long en minuscules et FrameworkBundle y retire controller_ et action. »
