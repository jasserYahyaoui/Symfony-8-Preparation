Objectif

Le client a reçu le HTML de /blog/42. Un statut 200 ne dit pas encore si le bon titre, les liens ou le formulaire attendu sont présents. Le Crawler permet de sélectionner ces éléments et d'en lire les données ; le client reste responsable d'envoyer la requête suivante.

Question centrale : comment, depuis une chaîne de HTML, retrouver un nœud précis, lire ses données, puis préparer l'envoi d'un formulaire ?

L'essentiel

À comprendre

À retenir en priorité
  1. CssSelector ne parcourt pas le document.
  2. DomCrawler exploite les sélections.

Ce que cette partie veut réellement vous apprendre.

  • Pourquoi ce sujet existe. Vérifier un statut 200 ne suffit pas : la page peut être la mauvaise. Il faut lire le HTML reçu. Or on n'écrit pas de regex sur du HTML : on le charge comme un arbre (le DOM) et on y sélectionne des nœuds.
  • Le piège de fond. Deux composants, deux rôles : CssSelector traduit (CSS → XPath), DomCrawler parcourt. Et un nouveau Crawler est une sélection, pas une copie du document.
  • Ce que l'auteur veut que vous compreniez. Le crawler ne bouge pas : c'est le client qui envoie la requête suivante. Le Crawler prépare seulement les données (lien, Form).
  • Pourquoi c'est à l'examen. filter() exige CssSelector et filterXpath() non ; text()/attr() = premier nœud ; siblings() exclut le nœud courant ; selectButton()->form() ≠ filter('form')->form().

DomCrawler parcourt le document et en extrait des nodes ; CssSelector ne parcourt rien, il traduit un selector CSS en XPath. Chaque method de parcours rend un nouveau Crawler. text() et attr() ne lisent que le premier node. Pour reproduire un choix de soumission, on part du bouton concerné ; sélectionner le formulaire seul est aussi possible.

Le DOM est l'arbre des nœuds du document HTML ou XML. Un sélecteur décrit les nœuds recherchés ; XPath est le langage de parcours utilisé après conversion du CSS. Aucun de ces composants ne calcule la mise en page visuelle ni n'exécute le JavaScript.

Le schéma

À retenir en priorité
  1. La sélection produit un nouvel object.
  2. L'original reste disponible.

Où en est-on ? Début du cours : deux schémas. Le premier suit le chemin « sélecteur → sélection → données ». Le second prépare l'étape finale : transformer un nœud en Form. Les sections suivantes détaillent chaque flèche.

La première vue s'arrête aux données observées. La seconde prépare une interaction : construire un objet Form n'envoie encore rien.

Bleu : conversion/parcours ; vert : résultat. Un nouveau Crawler représente une nouvelle sélection, pas une copie indépendante du document DOM.

Le rôle de chaque composant, en boîtes :

┌─────────────────────────┐        ┌──────────────────────────────┐
│ CssSelector             │        │ DomCrawler                   │
├─────────────────────────┤        ├──────────────────────────────┤
│ 'h1.title'  (string)    │        │ document HTML chargé (DOM)   │
│    ↓ toXPath()          │  ───►  │ + expression XPath           │
│ expression XPath        │        │    ↓ filtre                  │
│ (aucun document lu)     │        │ nouvelle sélection (Crawler) │
└─────────────────────────┘        └──────────────────────────────┘

L'exemple

Exemple concret

À retenir en priorité
  1. Le bouton peut choisir action et method.
  2. La sélection du form seul n'envoie pas sa valeur.

Où en est-on ? Code minimal d'abord : lire le titre de /blog/42, puis un scénario plus long jusqu'à la soumission d'un formulaire.

Pour la page article, un fragment de test peut d'abord lire $crawler = $client->request('GET', '/blog/42'), puis $crawler->filter('h1')->text(). Il suppose un titre présent ; vérifier le nombre de correspondances si le contrat exige exactement un titre.

Le fragment historique suivant va jusqu'à une soumission. Il suppose un catalogue de produits de test distinct du blog, un utilisateur autorisé, un h1, des liens .product a et un formulaire Supprimer valide. La requête GET ne doit rien supprimer ; c'est la soumission protégée à une méthode d'écriture qui porte l'action :

$crawler = $client->request('GET', '/products');
$titre = $crawler->filter('h1')->text();                    // le premier h1
$liens = $crawler->filter('.product a')->extract(['_text', 'href']);
$form  = $crawler->selectButton('Supprimer')->form();       // le bouton compte
$client->submit($form);

Le formulaire lu conserve ses champs, notamment le jeton CSRF lorsqu'il est présent. Ne pas désactiver cette protection pour faire passer le test. Après submit(), vérifier la nouvelle réponse : sélectionner correctement le bouton ne prouve pas que le serveur a accepté l'opération.

Qui fait quoi dans ces cinq lignes :

Ligne Acteur Ce qui se passe
filter('h1')->text() DomCrawler (+ CssSelector) sélection, puis texte du 1ᵉʳ nœud
extract(['_text', 'href']) DomCrawler un tableau, tous les nœuds
selectButton(...)->form() DomCrawler construit un Form, n'envoie rien
$client->submit($form) le client envoie la requête suivante

Deux components, un role chacun

À retenir en priorité
  1. XPath évite la conversion CSS.
  2. Les deux methods n'ont pas la même dependency.

Où en est-on ? Étape 1 sur 3 : avant de parcourir, on sépare les deux composants. Pourquoi filter('h1') peut-il échouer alors que la page contient bien un h1 ?

🌍 In Real Life

La situation : pour contrôler la brochure du blog, un traducteur reformule « tous les titres principaux » en consigne précise ; un lecteur cherche ensuite dans la brochure.

L’équivalent dans Symfony : traduction de la consigne → CssSelector convertissant CSS en XPath ; recherche dans le document → DomCrawler.

Retour à la réalité technique : produire une expression XPath ne parcourt aucun DOM. Le Crawler travaille sur le document reçu, pas sur les changements qu'un script JavaScript aurait produits dans un vrai navigateur.

🧠 Comment le mémoriser : « Traduire la recherche, puis chercher. » Image mentale : consigne traduite à côté de la brochure ouverte. Question-réflexe : cet outil transforme-t-il une expression ou sélectionne-t-il des nœuds ?

⚠️ À ne pas confondre : sélecteur CSS et moteur de rendu CSS.

Le titre d'article peut être trouvé par une expression CSS ou XPath, mais ce sont deux étapes différentes : produire l'expression, puis l'exécuter sur un document donné.

  • (new CssSelectorConverter())->toXPath('h1.title') rend une string : descendant-or-self::h1[@class and contains(…)].
  • filter() crée ce convertisseur, puis filtre par l'expression XPath obtenue : il exige CssSelector. filterXpath() non — sans le component, filter() lève une LogicException.

CssSelectorConverter est la classe Symfony\Component\CssSelector\CssSelectorConverter. La string qu'elle retourne ne contient aucun titre extrait : elle est indépendante du HTML sur lequel DomCrawler l'utilisera. Une erreur de composant manquant n'est donc pas une preuve que la page ne contient pas de h1.

Pourquoi XPath en coulisse ? Le DOM de PHP (DOMXPath) ne sait interroger un document qu'en XPath. CSS est plus lisible pour un développeur ; Symfony fournit donc un traducteur. Sans lui (composant non installé), le message de l'exception est explicite : installer symfony/css-selector, ou utiliser filterXpath.

filter('h1.title') filterXpath('//h1')
Syntaxe sélecteur CSS expression XPath
Dépend de CssSelector oui non
Sans le composant LogicException fonctionne

Parcourir

À retenir en priorité
  1. Les frères sont les autres nodes du même parent.
  2. Le node courant n'est pas inclus.

Où en est-on ? Étape 2 sur 3 : la sélection existe ; on la réduit ou on se déplace dedans. Chaque méthode ci-dessous rend un nouveau Crawler sur les mêmes nœuds du DOM.

Après le filtrage, on travaille sur une sélection. Réduire celle-ci au deuxième lien ne détruit ni la sélection initiale ni les autres liens du document :

Method Ce qu'elle rend
eq(1) le node à cet index — 0 est le premier
first(), last() le premier, le dernier
siblings() les frères, le node courant exclu
nextAll(), previousAll() les frères après, avant — du plus proche au plus lointain
ancestors(), children() les ascendants jusqu'à <html>, les enfants directs
reduce($fn) retire les nodes pour lesquels la function rend false ; tout autre retour garde le node
  • Une sélection vide n'est pas une erreur : eq(5) sur trois <li> rend un Crawler vide, count() à 0.
  • L'erreur vient d'une method qui a besoin d'un node : « The current node list is empty. »
  • reduce() avec une function sans return garde tous les nodes.

Ce dernier cas vient d'une comparaison stricte à false : null ou 0 ne retire pas le nœud. Ce n'est pas le comportement d'un filtre générique fondé sur toute valeur fausse au sens booléen.

Pourquoi une sélection vide ne lève-t-elle pas tout de suite ? Parce que « rien trouvé » est une réponse légitime (on veut parfois tester l'absence : count() === 0). L'erreur est repoussée au moment où l'on demande une donnée (text(), attr(), siblings()…) à un ensemble sans nœud : l'exception est alors une InvalidArgumentException « The current node list is empty. ».

<ul><li>a</li><li>b</li><li>c</li></ul>

filter('li')             → [a, b, c]
filter('li')->eq(1)      → [b]
filter('li')->last()     → [c]
  ->previousAll()        → [b, a]   (du plus proche au plus lointain)
filter('li')->eq(1)->siblings() → [a, c]   (b exclu)
filter('li')->eq(5)      → []       (vide : count() = 0, pas d'erreur)

Pour isoler index et lecture facultative sans serveur, avec DomCrawler et CssSelector 8.0 et leur autoload chargés :

<?php
use Symfony\Component\DomCrawler\Crawler;

$crawler = new Crawler('<ul><li>Paris</li><li>Lyon</li></ul>');
$cities = $crawler->filter('li');
echo $cities->count(), PHP_EOL;
echo $cities->eq(1)->text(), PHP_EOL;
echo $crawler->filter('h1')->text('Titre absent'), PHP_EOL;

Sorties attendues : 2, Lyon, Titre absent. Ce défaut est approprié à une lecture facultative. Pour le titre obligatoire de /blog/42, masquer l'absence par une valeur par défaut affaiblirait le test : une assertion doit alors signaler le défaut de la page. Les nouveaux Crawlers partagent les nœuds du DOM ; ils ne sont pas des copies indépendantes de tout le document.

Extraire

À retenir en priorité
  1. Une sélection multiple ne change pas cette règle.
  2. Choisir une extraction collective si nécessaire.

Où en est-on ? Complément à l'étape 2 : on a une sélection, on veut maintenant des données. La portée de chaque méthode (un nœud ou tous) est le piège central.

🌍 In Real Life

La situation : l'archiviste du blog retient cinq fiches. Lire le titre de la première ne dresse pas la liste des cinq titres.

L’équivalent dans Symfony : fiches retenues → sélection Crawler ; première fiche → text() ou attr() ; relevé complet → extract() ou each().

Retour à la réalité technique : sélectionner plusieurs nœuds ne change pas la portée des méthodes de lecture du premier nœud. Une sélection vide exige une gestion explicite ; lire un lien ne déclenche pas sa navigation.

🧠 Comment le mémoriser : « Une sélection multiple n'est pas une lecture multiple. » Image mentale : cinq fiches, un doigt posé sur la première. Question-réflexe : quel nombre de résultats cet appel rend-il ?

⚠️ À ne pas confondre : nombre de nœuds sélectionnés et nombre de valeurs extraites.

Choisir maintenant la forme du résultat. Sur plusieurs liens d'articles, attr('href') ne donne que le premier ; extract() produit des données pour tous, sans lancer de navigation :

$crawler->text();                     // le texte du premier nœud, espaces normalisés
$crawler->text('Défaut');             // ce texte si le nœud n'existe pas
$crawler->text(null, false);          // sans normaliser les espaces
$crawler->attr('class');              // un attribut du premier nœud
$crawler->extract(['_text', 'href']); // un tableau, pour tous les nœuds
$crawler->each(fn ($node, $i) => $node->attr('href'));

text() sur une sélection vide, sans default value, lève une InvalidArgumentException.

Avec <a href="/blog/42">Article</a><a href="/blog/page/2">Suite</a>, une sélection de ces deux liens donne [['Article', '/blog/42'], ['Suite', '/blog/page/2']] pour extract(['_text', 'href']). Avec un seul nom demandé, par exemple extract(['href']), le résultat est une liste simple d'URLs.

text() normalise les espaces par défaut ; extract(['_text']) utilise le texte des nœuds sans cette même normalisation. Ne pas supposer que les deux sorties sont identiques sur du HTML indenté. attr('class', 'none') peut rendre le défaut si le nœud ou l'attribut manque ; sans défaut, une sélection vide lève, alors qu'un attribut absent sur un nœud existant rend null.

Méthode Portée Rend Sélection vide
text() 1ᵉʳ nœud string exception (sans défaut)
attr('x') 1ᵉʳ nœud ?string exception (sans défaut)
extract([...]) tous les nœuds array tableau vide
each(fn) tous les nœuds array des retours tableau vide

Cliquer et soumettre

À retenir en priorité
  1. Chaque bouton peut représenter une action.
  2. Le form seul ne choisit pas ce bouton.

Où en est-on ? Étape 3 sur 3 : on passe de la lecture à l'action. Le Crawler prépare (lien, Form) ; le client envoie. Pourquoi le bouton choisi change-t-il la requête ? C'est la question de cette partie.

🌍 In Real Life

La situation : remplir le bulletin d'inscription du blog sur la table ne le remet pas au secrétariat.

L’équivalent dans Symfony : bulletin préparé → objet Form issu du Crawler ; choix du bouton → action de soumission représentée ; remise → appel du client pour soumettre.

Retour à la réalité technique : form() prépare les données et le contexte de soumission ; il n'envoie pas de requête. Le client simule ensuite l'interaction HTTP, sans exécuter les scripts éventuels de la page.

🧠 Comment le mémoriser : « Remplir avant de remettre. » Image mentale : bulletin signé encore posé sur la table. Question-réflexe : ai-je seulement construit le Form ou réellement soumis via le client ?

⚠️ À ne pas confondre : Form de DomCrawler et formulaire serveur du composant Form.

Pour passer de l'article à l'inscription, un test peut sélectionner un lien ou remplir le formulaire réellement reçu. Les appels suivants sont des fragments indépendants, avec les libellés et champs correspondants déjà présents dans le document ; ils ne sont pas une séquence garantie sur toutes les pages :

$client->clickLink('Cliquez ici');
$client->submitForm('Ajouter', ['comment_form[content]' => '…']);
$form = $crawler->selectButton('submit')->form();
  • On sélectionne un bouton : par son texte, sa value, son id ou son name. C'est lui qui décide de ce qui est envoyé.
  • Form à deux boutons Save (a=A) et Delete (b=B) :
Origine du Form Valeurs envoyées
selectButton('Delete')->form() b=B, q=1, vers le formaction du bouton, avec son formmethod
filter('#f')->form() — le <form> q=1 seulement, vers l'action du form
filter('input[name=q]')->form() LogicException « Unable to submit on a "input" tag. »
  • Fields : select() pour une liste ou un radio button, tick() pour une case, upload() pour un file.

Le tableau suppose un bouton nommé b avec value="B" et un champ q=1 : le texte visible Delete ne crée pas cette valeur. Les attributs formaction et formmethod peuvent remplacer la destination et la méthode du formulaire. Ils décrivent ce que le client enverra, pas ce que le serveur autorisera.

Pourquoi le bouton compte-t-il ? Dans un vrai navigateur, un bouton submit cliqué ajoute son name=value aux données et peut redéfinir l'action/method (formaction, formmethod). DomCrawler reproduit cela : Form::setNode() accepte un <button> ou un <input type=submit|button|image> et remonte jusqu'au <form> parent (ou celui désigné par l'attribut form). Si on lui donne le <form> directement, aucun bouton n'est « cliqué » ; si on lui donne un nœud d'un autre type, c'est une LogicException.

Nœud passé à ->form()      Ce que Form reçoit
<button name=b value=B>    bouton retenu → b=B envoyé, formaction/formmethod
<form id=f>                aucun bouton → champs seuls (q=1)
<input name=q> (ordinaire) LogicException « Unable to submit on a "input" tag. »

Dans une vraie action de suppression, utiliser une méthode d'écriture et les protections adaptées. Le cas mécanique formmethod="get" présenté dans les exercices démontre l'override HTML ; il ne recommande pas de modifier l'état par GET. Après une navigation, récupérer le Crawler de la nouvelle réponse : l'ancien représente toujours l'ancien document.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Une sélection vide est autorisée.
  2. La lecture d'un node absent exige un fallback.
  • Voir l’explication : CssSelector ne parcourt pas le DOM

    CssSelector ne parcourt pas le DOM : il traduit CSS en XPath. Pourquoi on se trompe : les deux composants s'utilisent ensemble dans filter(), donc on croit qu'il n'y en a qu'un.

  • Voir l’explication : text() et attr() ne lisent que le premier node.

    text() et attr() ne lisent que le premier node. Pourquoi on se trompe : on sélectionne cinq liens et on s'attend à cinq valeurs.

  • Voir l’explication : siblings() exclut le node courant.

    siblings() exclut le node courant. Pourquoi on se trompe : « frères » fait penser à « tous les <li> de la liste ».

  • Voir l’explication : On sélectionne un bouton pour obtenir un form

    On sélectionne un bouton pour obtenir un form quand le bouton compte ; le <form> seul marche aussi, mais n'envoie aucun bouton.

  • Voir l’explication : text() normalise les espaces par défaut

    text() normalise les espaces par défaut, et lève une exception sur une sélection vide sans default value.

  • Voir l’explication : Chaque method de parcours rend un nouveau Crawler

    Chaque method de parcours rend un nouveau Crawler ; l'object d'origine n'est pas modifié.

Fiche express

À mémoriser

À retenir en priorité
  1. Le texte extrait n'est pas le HTML brut.
  2. Tenir compte de la normalisation dans les assertions.

Le test sait maintenant passer d'un HTML reçu à des preuves précises : nombre de titres, texte, liste de liens, bouton effectivement soumis. Ces observations complètent le statut et les en-têtes HTTP ; elles ne mesurent ni le rendu visuel ni le coût du traitement serveur.

🧠 À retenir pour la certification :

  • CssSelector traduit CSS → XPath ; DomCrawler parcourt.
  • filter() exige CssSelector (LogicException sinon) ; filterXpath() non.
  • Chaque method de parcours rend un nouveau Crawler (une sélection).
  • siblings() exclut le node courant ; eq(5) hors limites → Crawler vide.
  • text()/attr() : premier node ; extract()/each() : tous.
  • text() normalise, et lève une exception sur du vide sans default value.
  • selectButton()->form() : le bouton, sa cible, sa method.

Moyen mnémotechnique : « Traduire, parcourir, partir du bouton ».

Phrase de mémorisation : CssSelector traduit en XPath, DomCrawler sélectionne des nœuds ; on lit le premier ou on extrait tous, et c'est le bouton choisi qui décide de ce que le client enverra.

CSS --CssSelector--> XPath --DomCrawler--> nouvelle sélection Crawler
text/attr = 1er node, extract/each = tous
selectButton()->form() = bouton + formaction + formmethod
<form> seul = aucun bouton ; input = LogicException

Pour examiner ce coût et les données collectées pendant la requête, passer au profiler dans les tests.
