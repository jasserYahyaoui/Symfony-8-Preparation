Objectif

Un lecteur a déjà reçu la page de l'article 42. Lorsqu'il la redemande, faut-il refaire le trajet jusqu'au controller et transférer le même HTML ? Les headers de cache permettent de répondre à deux questions : « puis-je réutiliser cette copie maintenant ? » et « correspond-elle encore à la représentation actuelle ? ».

Nous travaillons ici sur la version publique non personnalisée de GET /blog/42. Si le thème d'un cookie ou une identité modifie son HTML, ne lui applique pas aveuglément la politique partagée de cet exemple. Comprendre qui peut conserver une copie vient avant le choix de sa durée.

Périmètre. Cette page couvre les headers du protocole. Le reverse proxy Symfony et les strategies d'expiration et de validation qu'il implémente appartiennent à l'item HTTP Caching (reverse proxies, expiration, validation) du sujet Miscellaneous.

L'essentiel

À comprendre

À retenir en priorité
  1. no-cache impose une revalidation.
  2. no-store interdit le stockage.

Un cache conserve des réponses pour les réutiliser. Le cache privé du navigateur sert son utilisateur ; un cache partagé peut servir plusieurs utilisateurs. Cette différence interdit de traiter une page personnalisée comme un document public par simple souci de performance.

L'expiration indique une durée de fraîcheur. Une copie admissible encore fraîche peut être utilisée sans contacter l'origine, si les autres directives le permettent. La validation demande au serveur si une copie est toujours utilisable : le GET conditionnel reçoit 304 si la condition correspond, sinon normalement la représentation actuelle. Ces mécanismes se complètent plutôt qu'ils ne s'excluent.

Une Response Symfony neuve sans réglage de cache porte no-cache, private. Une politique publique explicite peut employer setPublic() ou setSharedMaxAge(), mais ni le nom GET ni ces méthodes ne vérifient que le contenu est réellement partageable. Nous décrivons les headers ; installer ou configurer le reverse proxy Symfony reste le sujet du cours HTTP Caching.

🌍 In Real Life

La situation : le client garde sa copie du menu ; l'accueil peut aussi conserver un menu public pour plusieurs clients. Une note de calcul en cuisine sert, elle, à éviter un travail interne.

L’équivalent dans Symfony : copie du client → cache HTTP privé ; copie réutilisée par l'accueil → cache HTTP partagé ; résultat de calcul interne → cache applicatif, mécanisme distinct.

Retour à la réalité technique : les headers HTTP règlent la réutilisation des réponses par les caches concernés. Un cache externe peut répondre avant PHP ; un cache applicatif économise un calcul sans supprimer automatiquement le cycle HTTP. L'objet Response représente la réponse, mais n'est pas à lui seul un stockage de cache.

🧠 Comment le mémoriser : « Qui garde quoi ? » Image mentale : menu chez le client, menu à l'accueil, note en cuisine. Question-réflexe : cache-t-on une réponse HTTP ou un résultat interne, pour un utilisateur ou plusieurs ?

⚠️ À ne pas confondre : public et sûr à partager ; aucun header ne détecte automatiquement des données personnalisées.

Le schéma

À retenir en priorité
  1. max-age s'applique aussi aux caches partagés.
  2. s-maxage les cible et prime pour eux.

La première Response de l'article est déjà stockée et sa réutilisation est admissible. Le diagramme commence à la nouvelle demande du lecteur, pas à la création du cache :

En bleu figurent stockage et Request ; en orange les décisions ; en vert les issues. Si la copie peut être servie directement, PHP peut ne pas être exécuté du tout. Dans l'autre branche, un validateur permet au serveur de comparer la version annoncée par le client.

Cette vue suppose une ressource existante sans erreur réseau ni décision d'autorisation supplémentaire. Une représentation modifiée demande un nouveau contenu, pas 304. Sans validateur utilisable, il faut demander une réponse complète plutôt qu'inventer une validation réussie. no-cache impose de valider avant réutilisation ; no-store interdit le stockage concerné. Ni l'un ni l'autre ne signifie que l'article a été supprimé.

L'exemple : expiration et validation

Exemple concret

À retenir en priorité
  1. La garde accepte GET, HEAD et QUERY.
  2. Une validation réussie produit 304 et vide le body.

Avec PHP 8.4 et HttpFoundation 8.0 chargés par l'autoloader, voici un laboratoire de données fixes. $article expose ici une date de modification par getUpdatedAt() ; cette méthode est un contrat local de l'exemple, pas une API imposée à notre ArticleView.

use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;

$article = new class {
    public function getUpdatedAt(): \DateTimeImmutable
    {
        return new \DateTimeImmutable('2026-01-01T12:00:00+00:00');
    }
};
$request = Request::create('/blog/42', 'GET', [], [], [], [
    'HTTP_IF_NONE_MATCH' => '"a1b2c3"',
]);
$response = new Response('<h1>Article 42</h1>');

$response->setPublic();
$response->setMaxAge(3600);                // public, max-age=3600
$response->setEtag('a1b2c3');
$response->setLastModified($article->getUpdatedAt());

if ($response->isNotModified($request)) {
    return $response;                      // 304, body vidé
}

return $response;

Le validateur reçu est "a1b2c3", celui que nous assignons à cette représentation fixe. isNotModified() retourne donc true, change le status code en 304 et retire le contenu avant le retour. Sans le header conditionnel, le résultat reste 200 avec le HTML. Dans une action, ce retour confierait la Response au kernel ; ici la construction locale n'envoie rien au réseau.

La string a1b2c3 est une valeur de démonstration, pas un ETag constant à copier sur tous les articles et toutes leurs versions. Le serveur doit produire un validateur cohérent avec la représentation sélectionnée. La date de modification doit elle aussi représenter un changement réel, pas l'heure de chaque consultation.

🌍 In Real Life

La situation : le client montre le numéro de version de son menu ; si cette version convient toujours, l'accueil lui dit de garder sa copie plutôt que lui remettre un menu vide.

L’équivalent dans Symfony : version annoncée → If-None-Match ; version sélectionnée → ETag de Response ; confirmation sans nouveau document → 304 sans body.

Retour à la réalité technique : isNotModified() peut modifier la Response : statut 304 et contenu retiré. Le client réutilise sa représentation stockée. L'ETag fixe de ce laboratoire ne convient pas à tous les articles ; sa valeur doit suivre la représentation sélectionnée. L'objet retourné n'est pas encore envoyé.

🧠 Comment le mémoriser : « Garde ta copie, pas une page blanche. » Image mentale : le client conserve son menu après confirmation. Question-réflexe : quel contenu déjà stocké ce 304 autorise-t-il à réutiliser ?

⚠️ À ne pas confondre : décision de validation et économie de tout calcul serveur ; l'application peut déjà avoir produit le HTML.

Deux modèles

À retenir en priorité
  1. L'expiration évite une Request vers l'origine.
  2. La validation peut produire 304 sans body.

Au premier chargement, le client reçoit le document. Tant que les règles permettent de réutiliser sa copie fraîche, l'expiration évite un nouvel aller-retour vers l'origine. Une durée longue accepte cependant de montrer cette version pendant plus longtemps : c'est un choix de cohérence éditoriale, pas seulement un réglage de vitesse.

Lorsque la copie doit être revalidée, la demande repart au serveur. Un 304 Not Modified économise le transfert du body ; il ne garantit pas que l'application n'a effectué aucun travail pour décider ce résultat. Si elle a déjà rendu tout le HTML avant de calculer son ETag, ce rendu a bien eu lieu.

L'ETag est un identifiant opaque de représentation : le client le renvoie sans devoir comprendre son calcul. Il peut dériver d'une version ou d'une empreinte, mais n'est pas nécessairement un hash. Last-Modified fournit une date. L'un n'est pas une durée de fraîcheur et l'autre ne prouve pas automatiquement l'identité de tous les octets.

Dans cet échange indépendant, /article/42 est une cible illustrative, pas un alias configuré de /blog/42 :

GET /article/42 HTTP/1.1
Host: example.test
If-None-Match: "article-v2"

Si la représentation actuelle conserve cet ETag, une réponse partielle peut être décrite ainsi :

HTTP/1.1 304 Not Modified
ETag: "article-v2"
Cache-Control: max-age=60

Les autres headers éventuels sont omis de cet extrait. Le client réutilise le contenu déjà stocké ; le serveur ne lui demande pas de remplacer l'article par un document vide. Un ETag aléatoire à chaque lecture empêcherait cette correspondance même si le contenu ne changeait pas.

🌍 In Real Life

La situation : le menu peut porter une durée de validité annoncée, ou nécessiter une confirmation de sa version à l'accueil.

L’équivalent dans Symfony : réutilisation pendant la durée permise → expiration ; question sur la version → requête conditionnelle ; confirmation → validation et éventuel 304.

Retour à la réalité technique : une copie fraîche et admissible peut éviter un aller-retour à l'origine. Une validation contacte le serveur et peut économiser le body, pas nécessairement son calcul. L'ETag est opaque, pas forcément un hash ; la date Last-Modified n'est pas une durée.

🧠 Comment le mémoriser : « La durée évite une question ; la version évite une copie. » Image mentale : horloge d'un côté, numéro de version de l'autre. Question-réflexe : cherche-t-on la fraîcheur ou la correspondance d'un validateur ?

⚠️ À ne pas confondre : menu physique qui s'use et réponse numérique copiable ; la péremption HTTP ne signifie pas que les données sont nécessairement fausses.

La date limite sur une boîte illustre l'expiration : tant qu'elle est fraîche, inutile de demander. La validation ressemble à un appel « est-ce identique ? » : la Request existe, mais un 304 évite de retransmettre le body.

Expiration

Nous choisissons maintenant combien de temps la copie publique peut être considérée fraîche. Les durées de Cache-Control sont en secondes. max-age s'applique aux caches privés et partagés ; s-maxage remplace cette durée pour les seuls caches partagés.

Supposons que l'âge courant de la copie soit de 90 secondes :

Cache-Control: public, max-age=60, s-maxage=300
Age: 90

En isolant ce calcul et en supposant les autres conditions satisfaites, le cache privé la considère périmée (90 > 60), tandis que le cache partagé peut encore la considérer fraîche (90 < 300). L'âge accumulé ne repart pas de zéro à chaque transmission. Sans s-maxage, le cache partagé utiliserait lui aussi max-age. Dans l'API Symfony, getMaxAge() privilégie s-maxage lorsqu'il existe : ce retour ne signifie pas que le navigateur doit appliquer cette valeur.

Les méthodes configurent des directives distinctes, qui peuvent coexister. Sur une Response neuve, setMaxAge(3600) seul donne max-age=3600, private : il ne décide pas du partage. setSharedMaxAge() appelle au contraire setPublic() avant d'ajouter s-maxage. setPublic() retire private, mais ne supprime pas magiquement toute autre restriction de cache déjà configurée.

Expires fournit une date absolue plutôt qu'une durée. Plus précisément que « Cache-Control prime », c'est la présence de max-age, ou de s-maxage pour un cache partagé, qui fait ignorer Expires dans ce calcul de fraîcheur.

La documentation Symfony 8.0 recommande setPublic() et setMaxAge() plutôt que de les remplacer mécaniquement par setSharedMaxAge(). Elle signale l'effet de s-maxage sur la réutilisation d'une copie périmée en cas d'erreur, scénario nommé stale-if-error. Ce dernier vise la disponibilité en présence d'une panne ; ce n'est pas la même décision que donner des durées différentes aux caches privés et partagés.

Les directives suivantes expriment encore d'autres contraintes :

Directive Effet
must-revalidate Une copie périmée ne doit pas être réutilisée sans validation réussie
stale-while-revalidate=N Autorise une fenêtre de N secondes après péremption pour réutiliser la copie pendant la revalidation, sous les conditions applicables
immutable Indique que la représentation ne changera pas pendant sa durée de fraîcheur et évite les revalidations inutiles pendant cette durée

Ces noms ne déclenchent pas une tâche de fond dans notre controller : ils s'adressent aux caches qui les prennent en charge. Une copie périmée n'est pas nécessairement fausse ; elle exige une décision de réutilisation conforme aux directives. Mnémonique : s- = shared, et il prime pour le cache partagé, sans rendre max-age exclusif au navigateur.

🌍 In Real Life

La situation : une même copie du menu porte deux délais autorisés, l'un général et l'autre réservé à l'accueil qui sert plusieurs clients.

L’équivalent dans Symfony : délai général → max-age ; délai du cache partagé → s-maxage ; temps déjà écoulé → âge de la copie.

Retour à la réalité technique : à 90 secondes, avec max-age=60, s-maxage=300, la copie est périmée pour le cache privé et encore fraîche pour le partagé, sous les autres conditions applicables. Sans s-maxage, le partagé utilise aussi max-age. Transmettre la copie ne remet pas son âge à zéro.

🧠 Comment le mémoriser : « Même âge, règle du bon cache. » Image mentale : une horloge devant deux échéances. Question-réflexe : quel cache lit la directive, et quelle durée doit-il appliquer ?

⚠️ À ne pas confondre : no-cache impose la validation avant réutilisation ; no-store interdit le stockage concerné. Ni l'un ni l'autre n'est une protection de transport.

Validation

La copie n'est plus réutilisable directement. Le client peut renvoyer If-None-Match, comparé à l'ETag, ou If-Modified-Since, comparé à Last-Modified. Pour notre GET, la comparaison réussie permet 304. L'application doit d'abord avoir sélectionné la bonne représentation et effectué les contrôles qui conditionnent son accès.

isNotModified() est une méthode qui peut modifier la Response, pas seulement un booléen de lecture. En Symfony 8.0, elle commence par une garde de méthode : hors GET, HEAD et QUERY, elle retourne false sans comparer les validateurs. La présence de QUERY dans cette liste est une particularité de l'API ; elle ne change pas le catalogue de méthodes défini par RFC 9110.

La priorité des validateurs demande une lecture précise. Selon RFC 9110 §13.1.3, If-Modified-Since est ignoré lorsque la Request contient If-None-Match. Dans l'implémentation Symfony étudiée, la branche ETag nécessite à la fois des tags dans la Request et un ETag dans la Response. Si cette dernière n'en a pas, la branche de comparaison des dates peut encore réussir et produire 304. C'est une différence à connaître pour répondre à une question d'implémentation, pas une nouvelle règle du protocole.

Un ETag fort doit distinguer des représentations dont les données diffèrent. Un ETag faible exprime une équivalence plus souple : $response->setEtag('a1b2c3', true) produit W/"a1b2c3". La comparaison d'If-None-Match utilise cette forme faible ; isNotModified() retire le préfixe W/ avant la comparaison. Ne réutilise donc pas ce résultat comme preuve générale d'identité octet pour octet ou comme validation de toute précondition HTTP.

🌍 In Real Life

La situation : deux éditions d'un menu peuvent être équivalentes pour la lecture sans être des copies identiques caractère par caractère.

L’équivalent dans Symfony : identité stricte de représentation → validateur fort ; équivalence plus souple → ETag faible W/... ; comparaison pour le GET conditionnel → If-None-Match.

Retour à la réalité technique : la comparaison faible d'If-None-Match n'est pas une preuve générale d'identité octet pour octet. La garde de méthode de isNotModified() et la nuance Symfony 8.0 sur la branche date restent celles décrites ci-dessus ; l'image ne remplace ni ces conditions ni la priorité normative des préconditions HTTP.

🧠 Comment le mémoriser : « Équivalent n'est pas identique. » Image mentale : deux éditions lisibles différemment mises en page. Question-réflexe : quelle comparaison ce validateur autorise-t-il réellement ?

⚠️ À ne pas confondre : comportement précis d'une méthode Symfony et règle générale de RFC 9110 ; le cas sans ETag de Response exige cette distinction.

Vary

À retenir en priorité
  1. Vary nomme les headers ayant influencé la représentation.
  2. Sans cette distinction, un cache peut servir la mauvaise langue.

Une autre difficulté apparaît si /blog/42 possède une version française et une version anglaise sélectionnées par Accept-Language. Un cache ne doit pas confondre ces représentations parce que l'URL est identique. Si la représentation varie aussi selon l'encodage accepté, le fragment suivant s'applique à la Response déjà construite :

$response->setVary(['Accept-Language', 'Accept-Encoding']);

Le header obtenu annonce Accept-Language et Accept-Encoding comme critères de sélection d'une copie stockée. Une demande anglophone ne doit plus réutiliser aveuglément la copie sélectionnée pour un autre ensemble de valeurs.

Vary ne traduit pas l'article et ne compresse pas le contenu : il décrit les entrées dont dépend un choix réalisé ailleurs. Il ne rend pas non plus une Response stockable et ne répare pas un ETag fort identique attribué à des données différentes. Choisir la variante, vérifier sa fraîcheur et comparer son validateur restent trois décisions distinctes.

🌍 In Real Life

La situation : l'accueil classe ses copies du menu par langue et format ; l'adresse du restaurant ne suffit pas à choisir la bonne pile.

L’équivalent dans Symfony : critères de classement → headers nommés dans Vary ; pile pertinente → représentation stockée compatible avec la demande.

Retour à la réalité technique : Vary: Accept-Language, Accept-Encoding décrit les entrées de sélection. Il ne traduit ni ne compresse, ne rend pas la Response stockable et ne répare pas un ETag fort mal attribué. Après sélection, fraîcheur et validation restent à examiner.

🧠 Comment le mémoriser : « La bonne pile avant la bonne date. » Image mentale : piles de menus français et anglais. Question-réflexe : cette copie correspond-elle aux critères de la Request ?

⚠️ À ne pas confondre : choisir une variante et autoriser son partage ; une représentation personnalisée demande sa propre politique.

Pièges d'examen

Piège à éviter

  • Voir l’explication : private est le défaut prudent de Symfony.

    private est le défaut prudent de Symfony. Cela ne signifie pas qu'un appel explicite à setPublic() est l'unique moyen de configurer le partage : setSharedMaxAge() l'appelle lui-même. À l'inverse, aucun de ces réglages ne vérifie que le HTML ne contient pas un nom d'utilisateur ou une préférence privée.

  • Voir l’explication : s-maxage prime sur max-age, mais seulement pour les caches partagés.

    s-maxage prime sur max-age, mais seulement pour les caches partagés. Relis l'exemple âgé de 90 secondes : les deux caches voient la même copie, mais n'appliquent pas la même durée de fraîcheur.

  • Voir l’explication : Distinguer les variantes réutilisables.

    Distinguer les variantes réutilisables. RFC 9110 §12.5.5 recommande Vary (SHOULD) pour leur sélection. Elle admet des exceptions, par exemple quand des directives limitent déjà la réutilisation ; ne pas transformer cette recommandation en obligation absolue pour toute Response. Pour nos variantes publiques réutilisables, annoncer les critères réels évite néanmoins de servir la mauvaise langue.

  • Voir l’explication : no-cache ne veut pas dire « ne pas stocker ».

    no-cache ne veut pas dire « ne pas stocker ». Il impose une revalidation avant chaque réutilisation. « Ne pas stocker » s'écrit no-store. Ces règles de cache ne remplacent ni le chiffrement du transport ni les contrôles d'accès au document.

  • Voir l’explication : isNotModified() sur un POST renvoie false.

    isNotModified() sur un POST renvoie false. La garde de method passe avant la comparaison d'ETag : ce n'est pas « l'ETag ne correspond pas », c'est « la question n'est pas posée ». Ne transforme pas l'échec de cette garde en diagnostic de modification de l'article.

  • Voir l’explication : setSharedMaxAge() rend la Response publique

    setSharedMaxAge() rend la Response publique — mais la doc recommande setPublic() + setMaxAge(), à cause de stale-if-error. Conserve cette justification : mémoriser seulement « toujours éviter s-maxage » ferait perdre le besoin de durées différenciées.

  • Voir l’explication : max-age n'est pas « pour les caches privés ».

    max-age n'est pas « pour les caches privés ». Un cache partagé l'utilise dès que s-maxage est absent ; c'est bien pourquoi s-maxage « prime » sur lui. La prochaine question sera de savoir comment le serveur choisit les représentations dont nous venons de protéger la réutilisation : c'est le rôle de la négociation de contenu.

Repère — Validation :

Question: Does Symfony isNotModified() compare validators for a POST request?

Answer: No. Its method guard excludes POST before comparing validators.

La garde accepte GET, HEAD et QUERY. Une validation réussie produit 304 et vide le body.

Application

À retenir en priorité
  1. La garde accepte GET, HEAD et QUERY.
  2. Une validation réussie produit 304 et vide le body.
  3. L'expiration évite une Request vers l'origine.
  4. La validation peut produire 304 sans body.

Fiche express

À mémoriser

Pour relire la page sans confondre stockage, fraîcheur et validation :

  • Expiration (max-age, s-maxage) contre validation (ETag, Last-Modified).
  • Défaut : private ; rien demandé → no-cache, private.
  • setSharedMaxAge() rend public ; setMaxAge() non.
  • s-maxage prime pour les caches partagés ; max-age vaut pour tous.
  • isNotModified() : false hors GET/HEAD/QUERY ; si le validateur correspond, 304 et body vidé.
  • no-cache = revalider ; no-store = ne rien garder.
  • Variantes réutilisables : Vary indique leurs critères de sélection.

Moyen mnémotechnique : « La fraîcheur peut épargner des Requests, la validation peut épargner des octets ». Dans les deux cas, la réutilisation doit porter sur une copie admissible de la bonne variante.
