Objectif

Suivre ce qui se passe entre une Request anonyme et un user connu, et ce qui change selon qu'un firewall garde ou non le token d'une Request à l'autre. Le détail des authenticators, passports et badges a son propre item.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Connaître l'identité ne donne pas tous les droits.
  2. isGranted() pose la question d'accès.

L'authentication répond à « qui êtes-vous ? ». Un firewall transforme des credentials en token, rangé dans le TokenStorage pour la Request courante. Sans user, il n'y a pas de token. Avec état, le token survit en session ; sans état, chaque Request se réauthentifie.

Le schéma

À retenir en priorité
  1. Le passport rassemble les preuves.
  2. Le token représente ensuite l'identité authentifiée.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le status code dépend de l'entry point.
  2. Un form login peut produire un redirect.
security:
    providers:
        mem:
            memory:
                users:
                    alice: { password: 'x', roles: ['ROLE_USER'] }
    firewalls:
        main:
            provider: mem
            http_basic: ~
    access_control:
        - { path: ^/whoami, roles: ROLE_USER }

La question posée

À retenir en priorité
  1. L'identité et l'autorisation sont distinctes.
  2. Un user présent peut être refusé.

L'authentication répond à « qui êtes-vous ? », l'authorization à « avez-vous le droit ? ». Les deux sont indépendantes : un user authentifié peut n'avoir aucun droit.

Le trajet

○ À comprendre

À retenir en priorité
  1. Le passport précède le token.
  2. Les badges sont vérifiés avant le succès.
  3. La connexion programmée passe par un authenticator.
  4. La Response du succès peut déterminer la suite du controller.

C'est quoi ?

L'authentication vérifie une identité ; l'authorization décide si cette identité peut effectuer une action. Un user connecté n'est donc pas automatiquement administrateur. Le token de sécurité représente l'identité authentifiée dans l'application ; ce n'est pas nécessairement le jeton envoyé par le client.

À quoi ça sert ?

Séparer les deux décisions permet de refuser une action à un user pourtant correctement connecté, et d'ouvrir une page publique sans inventer de user anonyme.

Où dans Symfony ?

Le firewall est la configuration de sécurité sélectionnée pour la Request. Son authenticator examine la preuve présentée. Le Passport rassemble user et éléments à vérifier ; le TokenStorage contient ensuite le token courant. Security::getUser() et le raccourci du controller donnent accès au user de ce contexte.

Comment, étape par étape ?

  1. Symfony choisit le premier firewall correspondant.
  2. Un authenticator applicable construit un Passport. Les vérifications des credentials et badges doivent réussir : construire le Passport n'est pas déjà une connexion.
  3. Après validation, un token contenant le user est créé et installé dans le TokenStorage.
  4. Avec état, le token peut être conservé en session et le provider recharge le user lors de la restauration. Sans état, stateless: true, aucune authentication n'est restaurée depuis la session de ce firewall : chaque Request doit fournir sa preuve.
  5. L'autorisation est ensuite évaluée pour l'action demandée. Sans authentication, getUser() peut rendre null ; cela n'interdit pas de servir une page publique.

Exemple concret PHP

Fragment utilisable avec le service Security configuré ; il ne réalise pas une connexion :

<?php
use Symfony\Bundle\SecurityBundle\Security;

function currentIdentifier(Security $security): ?string
{
    return $security->getUser()?->getUserIdentifier();
}

Sur une page publique sans token, le résultat est null. Après une authentication réussie, il s'agit de l'identifier du user. Contre-exemple : autoriser une opération parce que cette fonction ne rend pas null. Correction : effectuer aussi le contrôle d'accès sur l'action et son objet. Un refus peut déclencher une redirection vers le login ou un 401 selon l'entry point, le mécanisme qui démarre l'authentication ; ce n'est pas toujours un 403. De même, stateless ne promet pas qu'aucun autre code de l'application n'utilisera une session.

Authentication Symfony 8.0.

Passage canonique conservé

Le trajet

  1. La Request entre dans un firewall, choisi par son pattern.
  2. Un authenticator de ce firewall la prend en charge.
  3. Il construit un passport, dont les badges sont vérifiés.
  4. Un token (TokenInterface) est produit, avec le user et ses roles.
  5. Le token est déposé dans le TokenStorage.

$this->getUser() et Security::getUser() ne sont que des raccourcis vers le TokenStorage.

Security::login() permet une connexion programmée d'un UserInterface, par exemple après une inscription. Elle utilise un authenticator et un firewall ; lorsqu'il y a plusieurs possibilités, les sélectionner explicitement. La method peut retourner la Response du succès d'authentication : le controller doit la prendre en compte, plutôt que supposer que la connexion ne produit jamais de Response.

Documentation Symfony 8.0.

Pas de token sans user

À retenir en priorité
  1. Le token anonyme historique n'est plus requis.
  2. Le code doit accepter l'absence de token.

Depuis la disparition du token anonyme, une Request non authentifiée n'a aucun token :

Request getToken() getUser() Response
/public, sans credentials null null 200
/whoami (exige ROLE_USER), sans credentials — — 401, entry point
/whoami, credentials valides UsernamePasswordToken alice 200

Le firewall l'explique : « the user is not fully authenticated; redirecting to authentication entry point ».

Avec ou sans état

À retenir en priorité
  1. Le firewall stateless ne mémorise pas le token en session.
  2. Chaque Request doit fournir sa preuve.
  • Par défaut, stateless: false : le token est sérialisé en session. À la Request suivante, le log dit « Read existing security token from the session », puis « User was reloaded from a user provider » : le user est rechargé par le provider, pas recopié tel quel.
  • stateless: true (une API à tokens) : le token n'est jamais écrit en session ; une Request suivante sans credentials reçoit 401.
  • Après une connexion, l'ID de session est régénéré contre la fixation de session : session_fixation_strategy vaut migrate par défaut.

Ce que le controller voit

À retenir en priorité
  1. null décrit l'identité courante.
  2. Le contrôle d'accès décide ensuite du refus.

getUser() à null indique l'absence de user courant, pas une Response de refus déjà produite. Sur une ressource protégée, le firewall peut démarrer l'authentication : HTTP Basic répond typiquement 401, tandis qu'un form login peut rediriger en 302. Un user suffisamment authentifié auquel le droit est refusé reçoit normalement 403.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. La session conserve le token.
  2. Le provider relit l'identité.
  • Voir l’explication : Authentication ≠ authorization.

    Authentication ≠ authorization. getUser() répond à la première, isGranted() à la seconde.

  • Voir l’explication : Pas de user, pas de token

    Pas de user, pas de token : getToken() rend null pour une Request anonyme ; le token anonyme n'existe plus.

  • Voir l’explication : stateless: true n'écrit pas le token en session

    stateless: true n'écrit pas le token en session : le user n'est plus mémorisé d'une Request à l'autre.

  • Voir l’explication : Le token en session ne fige pas le user

    Le token en session ne fige pas le user : il est rechargé par le provider à chaque Request.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. La connexion régénère l'identifier de session.
  2. Cela ne transforme pas un firewall stateless en stateful.

Si tu dois retenir seulement 7 choses :

  • Authentication = qui ; authorization = quel droit.
  • Firewall → authenticator → passport → token → TokenStorage.
  • Pas de user, pas de token : getToken() et getUser() à null.
  • Anonyme refusé : Response de l’entry point, par exemple 401 ou 302 ; user suffisamment authentifié refusé : 403.
  • Avec état : token en session, user rechargé à chaque Request.
  • stateless: true : rien en session, credentials à chaque Request.
  • session_fixation_strategy: migrate : nouvel ID après connexion.

Moyen mnémotechnique : « Qui d'abord, droit ensuite ».

firewall → authenticator → passport → token → TokenStorage ; pas de token anonyme ;
entry point : 401 ou redirect ; refus après authentication suffisante : 403 ; session : token gardé, user rechargé ; stateless : rien gardé ; migrate
