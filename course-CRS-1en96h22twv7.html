Objectif

Écrire un test qui traverse l'application entière, et connaître les assertions que Symfony ajoute à PHPUnit — c'est là que se joue la lisibilité du test.

L'essentiel

○ À comprendre

À retenir en priorité
  1. WebTestCase ajoute le client de test.
  2. Il hérite de KernelTestCase.

Un test d'application étend WebTestCase, qui ajoute un client à KernelTestCase : createClient() démarre le kernel, en environment test. Les assertions de Symfony rendent l'échec lisible, et la configuration des tests a ses propres files — .env.local n'en fait pas partie.

Le schéma

À retenir en priorité
  1. Le kernel est déjà démarré par cet appel.
  2. Éviter un bootKernel() préalable.

L'exemple : la page d'accueil

▣ Exemple concret

À retenir en priorité
  1. Une Request seule n'est pas une assertion.
  2. Vérifier le comportement observable.
class PostControllerTest extends WebTestCase
{
    public function testHome(): void
    {
        $client = static::createClient();
        $client->request('GET', '/');           // une URL écrite en dur

        $this->assertResponseIsSuccessful();
        $this->assertRouteSame('home');
        $this->assertSelectorTextContains('h1', 'Hello World');
    }
}

Le squelette

▣ Exemple concret

À retenir en priorité
  1. L'ordre d'initialisation est imposé.
  2. Créer le client directement dans WebTestCase.

C'est quoi ?

Un test d'application vérifie ce qu'une Request produit à travers le kernel, les services et le controller. WebTestCase ajoute un client simulé à KernelTestCase ; ce n'est pas un navigateur qui exécute JavaScript.

À quoi ça sert ?

Il protège un contrat observable : URL disponible, statut HTTP précis, redirection ou contenu attendu. Le test doit échouer lorsque ce contrat change involontairement.

Où dans Symfony ?

La configuration spécifique se place sous when@test ou dans config/packages/test/. Dans le chargement Dotenv standard, .env.local est ignoré pour les tests ; les fichiers propres à test et les vraies variables d'environment restent à considérer. Ne pas utiliser une base de production comme fixture de test.

Comment, étape par étape ?

  1. Appeler directement static::createClient() : il démarre déjà le kernel.
  2. Envoyer la Request vers l'URL du contrat.
  3. Vérifier le statut puis le contenu utile.
  4. Choisir la précision de l'assertion : assertResponseIsSuccessful() accepte tous les 2xx, tandis que assertResponseStatusCodeSame(200) impose exactement 200.

Exemple concret PHP

Test pour une application dont / doit répondre 200 avec un titre contenant « Accueil ». Cette route et cette vue sont des prérequis, pas des fichiers créés ici :

<?php
use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;

final class HomePageTest extends WebTestCase
{
    public function testHomeContract(): void
    {
        $client = static::createClient();
        $client->request('GET', '/');
        self::assertResponseStatusCodeSame(200);
        self::assertSelectorTextContains('h1', 'Accueil');
    }
}

Contre-exemple : appeler bootKernel() puis createClient() dans le même arrangement. Correction : créer le client directement ; éviter le double démarrage refusé par WebTestCase. Autre erreur : faire seulement la Request sans assertion. Cela ne démontre ni bonne page ni bon statut. Une URL littérale est utile si le test doit détecter son changement ; une URL générée suivrait silencieusement le renommage du chemin.

Tests d'application 8.0.

Passage canonique conservé

Le squelette

  • WebTestCase étend KernelTestCase et lui ajoute le client.
  • createClient() démarre le kernel : bootKernel() puis createClient() lève une LogicException — « Booting the kernel before calling "…WebTestCase::createClient()" is not supported, the kernel should only be booted once. ».
  • La documentation recommande une URL en dur : un test qui génère son URL suit un changement de route au lieu de le détecter.

L'environment `test`

À retenir en priorité
  1. Les tests doivent rester reproductibles.
  2. Les réglages test spécifiques restent séparés.

La configuration propre aux tests va dans config/packages/test/ ou sous when@test. Les variables d'environment, une variable A définie dans les quatre files :

Situation Valeur de A
APP_ENV=test, les quatre files celle de .env.test.local
APP_ENV=test, sans .env.test.local celle de .env.test
APP_ENV=dev celle de .env.local
APP_ENV=test, A déjà définie dans le shell celle du shell

.env.local n'est pas lu en test, délibérément : une machine de développement ne doit pas modifier le résultat des tests.

Les assertions de Symfony

À retenir en priorité
  1. 201 est aussi un succès HTTP.
  2. Utiliser une assertion exacte si le contrat exige un code précis.
Sur… Assertions
la Response assertResponseIsSuccessful() (tout 2xx), assertResponseStatusCodeSame(), assertResponseRedirects(), assertResponseHasHeader(), assertResponseHasCookie(), assertResponseIsUnprocessable() (422)
la Request assertRouteSame(), assertRequestAttributeValueSame()
le navigateur assertBrowserHasCookie(), assertBrowserHistoryIsOnFirstPage()
le contenu assertSelectorExists(), assertSelectorCount(), assertSelectorTextContains(), assertPageTitleSame(), assertInputValueSame(), assertCheckboxChecked()

Sur un échec, l'assertion affiche headers et corps de la Response, là où assertEquals(200, $code) n'affiche qu'un nombre. self::setBrowserKitAssertionsAsVerbose(false) réduit l'affichage aux headers ; le parameter $verbose fait de même au cas par cas.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le test peut protéger l'URL publique.
  2. La génération suivrait la modification de route.
  • Voir l’explication : WebTestCase étend KernelTestCase

    WebTestCase étend KernelTestCase ; createClient() démarre déjà le kernel.

  • Voir l’explication : .env.local est ignoré en test

    .env.local est ignoré en test, contrairement à .env.test.local.

  • Voir l’explication : assertResponseIsSuccessful() couvre tout le 2xx

    assertResponseIsSuccessful() couvre tout le 2xx, pas seulement 200 — exécuté : une Response 201 passe.

  • Priorité du shell sur la configuration de test

    Une variable du shell bat .env.test.local.

  • Voir l’explication : Une URL en dur est la bonne pratique

    Une URL en dur est la bonne pratique, à rebours de l'intuition.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. La configuration de test est conditionnelle.
  2. Elle ne doit pas modifier l'environment de production.

Si tu dois retenir seulement 6 choses :

  • WebTestCase étend KernelTestCase ; createClient() démarre le kernel.
  • Quatre temps : Request, interaction, assertion, recommencer.
  • Config de test : when@test ou config/packages/test/.
  • .env → .env.test → .env.test.local ; .env.local ignoré ; le shell bat tout.
  • assertResponseIsSuccessful() : tout 2xx ; assertRouteSame() : la route qui a répondu.
  • URL en dur, pas générée.

Moyen mnémotechnique : « Request, clic, assertion, toujours ».
