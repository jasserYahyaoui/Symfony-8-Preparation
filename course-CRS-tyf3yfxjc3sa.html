Objectif

Savoir ce qu'est Flex techniquement, ce qu'une recipe fait, et quels files Flex écrit dans le projet.

L'essentiel

○ À comprendre

À retenir en priorité
  1. symfony.lock conserve les recipes appliquées.
  2. Les deux lock files ont des responsabilités distinctes.

Flex est un plugin Composer : il ne s'appelle pas, il change ce que font composer require, update et remove. Il apporte trois mécanismes — l'alias, la recipe, le pack — et note les recipes appliquées dans symfony.lock, à committer. Deux repositories de recipes, deux comportements.

Le schéma

À retenir en priorité
  1. Flex modifie le workflow Composer.
  2. Il ne s'enregistre pas dans config/bundles.php.

Ce que Flex est

Revoir la règle : Flex modifie le workflow Composer.

Un plugin Composer, ni bundle ni command : il n'apparaît pas dans config/bundles.php. Sans lui, composer require twig échoue, parce que twig n'est le nom d'aucun package Composer.

Alias et recipes

À retenir en priorité
  1. L'alias twig résout un nom de package.
  2. La recipe configure ; le pack regroupe des dependencies.

Trois mots, trois choses distinctes :

  • un alias est un nom court que Flex résout — twig en symfony/twig-bundle, api en api-platform/api-pack, un pack tiers ;
  • une recipe est la configuration qu'un package apporte : activer un bundle, créer des files et des directories, ajouter des variables à .env ;
  • un pack est un métapaquet sans code. Flex le dépaquette : on cherche en vain symfony/debug-pack dans composer.json après l'installation.

La liste complète des recipes et des alias est publiée dans RECIPES.md, sur le repository des recipes.

symfony.lock

Revoir la règle : symfony.lock conserve les recipes appliquées.

Il recense les recipes appliquées et leur version, et se committe : c'est lui qui permet de savoir qu'une recipe a évolué. Il joue pour les recipes le role que composer.lock joue pour les dependencies — deux files distincts.

Le package est un meuble livré en kit, la recipe sa notice d'assemblage. symfony.lock conserve la version de notice appliquée ; composer.lock conserve celle des pièces installées.

Les deux repositories de recipes

À retenir en priorité
  1. symfony/recipes constitue le catalogue sélectionné.
  2. recipes-contrib demande une autorisation.
Repository Contenu Comportement de Flex
symfony/recipes liste curée, packages de qualité et maintenus seul consulté par défaut
symfony/recipes-contrib les recipes de la communauté demande votre permission

Les recipes contrib « are guaranteed to work » : c'est le package associé qui « could be unmaintained ».

Pièges d'examen

△ Piège à éviter

Revoir la règle : symfony/recipes constitue le catalogue sélectionné.

Flex est un plugin Composer, pas un bundle ni une command. Il n'y a rien à appeler : il modifie composer require, update et remove. C'est aussi pourquoi composer require twig fonctionne alors qu'aucun package ne s'appelle twig.

symfony.lock n'est pas composer.lock. Il recense les recipes appliquées, et il se committe.

Les deux repositories de recipes ne se comportent pas pareil. symfony/recipes est appliqué sans question ; symfony/recipes-contrib demande une permission. La raison n'est pas que ses recipes seraient douteuses — la documentation les dit « guaranteed to work » — mais que les packages qu'elles configurent peuvent être abandonnés.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Flex = plugin Composer ; il change require, update, remove.
  • Alias : nom court ; recipe : configuration ; pack : métapaquet.
  • Un pack est dépaqueté : il n'apparaît pas dans composer.json.
  • symfony.lock recense les recipes et se committe.
  • symfony/recipes sans question ; recipes-contrib demande.
  • Contrib : recipe garantie, package peut-être abandonné.

Moyen mnémotechnique : « Un nom, une config, un package ».
