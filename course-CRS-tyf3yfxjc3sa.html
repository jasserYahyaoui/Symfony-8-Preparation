Objectif

Pour que BlogController::show affiche l'article 42 avec Twig, le projet doit posséder le moteur de templates et son intégration à Symfony. Télécharger du code ne suffit pas toujours : il faut aussi activer le bundle et préparer sa configuration. Ce cours se place au moment de l'installation, pas dans le traitement de GET /blog/42.

Nous allons suivre ce que Composer et Flex changent, puis reconnaître les traces à conserver pour que l'équipe comprenne cet état du projet. Les commandes illustrent un projet d'exercice ; elles ne sont pas exécutées ici.

L'essentiel

À comprendre

À retenir en priorité
  1. symfony.lock conserve les recipes appliquées.
  2. Les deux lock files ont des responsabilités distinctes.

Composer est le gestionnaire de dépendances PHP : il résout les versions compatibles et installe les packages. Flex est un plugin Composer, une extension qui accompagne notamment les opérations require, update et remove pour automatiser la préparation du projet.

Trois notions interviennent dans notre installation. L'alias permet de demander un package par un nom court. La recipe contient les instructions de configuration à appliquer au projet. Un pack regroupe des dépendances sans fournir lui-même leur code applicatif. Un alias peut désigner un pack ; ces mots ne sont donc pas trois noms du même objet.

Après application, symfony.lock mémorise l'état des recipes. Il complète composer.lock, qui décrit les versions résolues des dépendances, sans le remplacer. Nous examinerons aussi la provenance d'une recipe : automatiser une configuration ne dispense pas de choisir ce que l'on accepte dans le projet.

Le schéma

À retenir en priorité
  1. Flex modifie le workflow Composer.
  2. Il ne s'enregistre pas dans config/bundles.php.

Partons d'une application minimale qui n'a pas encore TwigBundle. Flex est installé et autorisé comme plugin. Le dessin sépare la traduction du nom, l'installation du code et la configuration ; le controller n'est exécuté à aucune de ces étapes.

Bleu : résolution et installation ; orange : configuration ; cylindres verts : deux traces distinctes. La flèche après composer.lock représente la suite des opérations, pas l'exécution du fichier. Composer reste responsable des versions installées ; Flex traite la recipe disponible et autorisée.

À l'arrivée, l'équipe possède du code sous vendor/ et une configuration dans son propre projet. Le nom et le contenu précis des fichiers ajoutés dépendent de la recipe sélectionnée. Sa version n'est pas nécessairement celle de TwigBundle ou du moteur Twig : les trois évoluent selon des objets différents.

L'exemple : installer et configurer en une command

Exemple concret

Prérequis de cet exemple : PHP 8.4, Composer 2.x et Flex 2.x actif, dans un projet dont les contraintes maintiennent Symfony en 8.0 et Twig dans la ligne 3.22 étudiée. La commande seule ne fixe pas ces bornes : sans ces contraintes, Composer peut sélectionner d'autres versions compatibles.

composer require twig
# Flex résout l'alias, Composer installe symfony/twig-bundle,
# la recipe active le bundle et dépose sa configuration et templates/

Le résultat attendu est l'installation de symfony/twig-bundle et de ses dépendances compatibles, accompagnée de la configuration de sa recipe. Selon la version de celle-ci, on retrouve notamment l'activation dans config/bundles.php, des paramètres sous config/packages/ et une base dans templates/. Il s'agit des effets à vérifier, pas d'une sortie terminal octet pour octet ni de fichiers garantis identiques pour toutes les recipes.

Cette préparation ne crée ni blog_show, ni BlogController::show, ni notre ArticleView. Elle rend les outils disponibles pour que notre code réalise ensuite le rendu. Le contrôle utile consiste à relire les changements du projet et les deux locks avant de poursuivre, pas à conclure « la page de l'article existe » parce que l'installation a réussi.

Ce que Flex est

La ligne de commande précédente a demandé une fonctionnalité ; elle n'a pas appelé Flex depuis le controller. Le plugin s'intègre aux opérations Composer. Ce n'est pas un bundle à inscrire dans config/bundles.php, ni une command applicative bin/console qui traiterait les visiteurs du blog.

Cette distinction explique une panne fréquente : dans un projet sans Flex, le nom court twig ne bénéficie pas de sa résolution vers symfony/twig-bundle. Il faut utiliser le nom Composer complet et prendre en charge la configuration nécessaire autrement. Installer seulement twig/twig désigne le moteur, pas le même package d'intégration au framework.

L'autorisation du plugin concerne son exécution par Composer. L'activation de TwigBundle concerne le fonctionnement de l'application. Ajouter Symfony\Flex\Flex à la liste des bundles ne résoudrait donc pas un problème de plugin désactivé. Flex peut proposer des outils Composer pour gérer les recipes ; cela ne change pas sa nature de plugin ni ne le transforme en command du kernel.

Alias et recipes

À retenir en priorité
  1. L'alias twig résout un nom de package.
  2. La recipe configure ; le pack regroupe des dependencies.

Reprenons les trois questions que l'installation vient de résoudre.

Quel nom demander ? L'alias twig pointe vers symfony/twig-bundle. Le raccourci n'est pas une classe PHP et ne choisit pas à lui seul une version. L'exemple historique api pointe vers api-platform/api-pack, un pack tiers : il montre qu'un alias ne désigne pas nécessairement un bundle Symfony. Nous ne l'installons pas et n'étudions pas ici le fonctionnement de ce produit.

Comment préparer l'application ? Une recipe peut activer un bundle, créer ou modifier des fichiers et des répertoires, ou ajouter des noms de variables et des valeurs d'exemple dans .env. Elle adapte l'installation au projet ; elle ne contient pas le code métier qui choisit l'article 42. Les valeurs d'exemple ne sont pas des secrets de production à publier. Il faut lire les fichiers réellement modifiés avant d'y ajouter nos adaptations.

Quels packages regrouper ? Un pack est un métapaquet : il décrit des dépendances sans contenir leur implémentation. Pour préparer les outils de diagnostic du blog, l'exemple suivant demande le pack de développement :

composer require --dev debug

Avec le comportement de dépaquetage de Flex, le résultat attendu dans composer.json est l'inscription des dépendances concrètes en require-dev, par exemple symfony/var-dumper, plutôt que le maintien de symfony/debug-pack comme exigence directe. Le contenu exact dépend de la version du pack résolue. L'absence de son nom ne signifie donc pas que l'installation a échoué.

La liste publiée des recipes et des alias se consulte dans RECIPES.md du repository des recipes. Cette liste décrit les possibilités disponibles ; pour savoir ce qui a été appliqué à notre projet, il faut regarder une autre trace.

🌍 In Real Life

La situation : l'installateur reçoit un nom commercial, une liste d'équipements et une notice de montage.

L’équivalent dans Symfony : nom court → alias ; liste de dépendances → pack ; préparation du projet → recipe ; installation des versions → Composer accompagné de Flex.

Retour à la réalité technique : Flex est un plugin d'installation, pas un bundle exécuté sur chaque GET. Le dépaquetage inscrit les dépendances concrètes ; la recipe ne crée pas notre page métier.

🧠 Comment le mémoriser : « Nommer, regrouper, préparer. » Image mentale : trois documents distincts. Question-réflexe : est-ce un raccourci, un ensemble de packages ou une instruction de configuration ?

⚠️ À ne pas confondre : alias Flex et alias du conteneur de services.

symfony.lock

Après l'ajout de TwigBundle, une collègue veut comprendre les changements : quelle bibliothèque a été installée, quelle recipe a été appliquée et quel est le contenu actuel de notre configuration ? Ces questions ont trois réponses complémentaires.

composer.lock conserve les versions résolues des dépendances. symfony.lock conserve les informations sur les recipes appliquées, notamment leur version et leur référence lorsqu'elles sont présentes. Les fichiers sous config/ et templates/ portent, eux, le contenu réellement utilisé, avec nos adaptations éventuelles. Un lock de recipes n'est pas une sauvegarde complète de ces fichiers.

Dans le projet applicatif, symfony.lock se versionne, comme composer.lock et les fichiers de configuration utiles. Cela donne à l'équipe une référence pour identifier une évolution de recipe sans la confondre avec un changement local. Le supprimer parce que Composer possède déjà un lock ferait perdre une information différente ; il ne faut pas le recréer au hasard.

De même, mettre à jour un package et réexaminer sa recipe sont deux sujets distincts. Une nouvelle version de bibliothèque n'implique pas que toutes les adaptations locales doivent être remplacées. Lors d'une suppression, Flex peut désinstaller les éléments suivis par une recipe ; cette automatisation ne doit pas être interprétée comme l'annulation parfaite de toutes les modifications que l'équipe a faites depuis.

🌍 In Real Life

La situation : la livraison possède un inventaire des modèles installés et un registre des notices appliquées ; l'aménagement actuel peut ensuite être personnalisé.

L’équivalent dans Symfony : inventaire → composer.lock ; registre des recipes → symfony.lock ; aménagement → fichiers configurés.

Retour à la réalité technique : les locks décrivent des objets différents. Le registre des recipes n'est pas une sauvegarde complète de la configuration ; désinstaller une recipe n'annule pas parfaitement toutes les modifications locales.

🧠 Comment le mémoriser : « Versions, recettes, état actuel. » Image mentale : deux registres devant l'installation. Question-réflexe : quelle information cherche-t-on à retrouver ?

⚠️ À ne pas confondre : mise à jour du package et remplacement automatique des adaptations locales.

Le package est un meuble livré en kit, la recipe sa notice d'assemblage. symfony.lock conserve la version de notice appliquée ; composer.lock conserve celle des pièces installées.

Les deux repositories de recipes

À retenir en priorité
  1. symfony/recipes constitue le catalogue sélectionné.
  2. recipes-contrib demande une autorisation.

Un repository est un dépôt de fichiers. L'équipe connaît maintenant les effets possibles d'une recipe ; elle doit décider de quelles sources elle accepte ces instructions. Les deux dépôts publics historiques n'ont pas la même politique de sélection :

Repository Contenu Comportement de Flex
symfony/recipes sélection de recipes pour des packages de qualité et maintenus source principale utilisée par défaut
symfony/recipes-contrib contributions communautaires plus larges application soumise à autorisation selon les choix et la configuration

Pour le projet du blog, recevoir une proposition issue de contrib n'est pas une étape à valider mécaniquement. Il faut distinguer l'autorisation de cette provenance, l'autorisation d'exécuter le plugin Composer et l'activation d'un bundle : elles portent sur trois décisions différentes. Une permission déjà enregistrée peut aussi modifier l'interaction ; « demande permission » ne signifie pas nécessairement « repose la même question à chaque installation ».

La documentation présente les recipes contrib comme fonctionnelles (guaranteed to work), tout en avertissant que le package associé peut ne plus être maintenu (could be unmaintained). Cela décrit la différence entre les instructions de configuration et la bibliothèque qu'elles préparent, pas une garantie illimitée sur toutes les versions futures ou tous les projets. Nous gardons donc deux vérifications : la recipe convient-elle à notre configuration, et le package convient-il durablement au besoin ?

🌍 In Real Life

La situation : accepter une notice provenant d'un fournisseur ne garantit pas que son équipement restera entretenu indéfiniment.

L’équivalent dans Symfony : provenance de notice → dépôt de recipes ; équipement → package ; accord → autorisation de cette provenance.

Retour à la réalité technique : autoriser contrib, autoriser le plugin Composer et activer un bundle sont trois décisions. Une recipe fonctionnelle ne garantit pas la maintenance future du package.

🧠 Comment le mémoriser : « Vérifier la notice et son équipement. » Image mentale : deux contrôles séparés. Question-réflexe : mon accord porte-t-il sur la provenance, l'exécution du plugin ou l'intégration applicative ?

⚠️ À ne pas confondre : autorisation déjà enregistrée et nouvelle question nécessaire à chaque installation.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Chercher Flex dans les bundles confond installation et exécution.

    Chercher Flex dans les bundles confond installation et exécution. Le plugin accompagne Composer ; TwigBundle, lui, participe à l'intégration de Twig dans l'application. La résolution de twig vient de Flex, non du traitement de GET /blog/42. Un package installé ne prouve pas qu'une recipe a été appliquée ni que notre page métier a été écrite.

  • Voir l’explication : Un lock n'en remplace pas un autre.

    Un lock n'en remplace pas un autre. Si l'équipe a perdu symfony.lock, composer.lock renseigne encore les dépendances résolues, mais pas la même trace des recipes. Les fichiers de configuration ne doivent pas non plus être supprimés au motif qu'un lock en contiendrait une copie complète.

  • Voir l’explication : L'origine d'une recipe et la santé du package sont deux questions.

    L'origine d'une recipe et la santé du package sont deux questions. L'autorisation contrib ne transforme pas le package en bundle officiel ni en bibliothèque maintenue indéfiniment. Inversement, « communautaire » ne signifie pas « instructions nécessairement défectueuses ». À l'examen, il faut nommer l'objet concerné par chaque affirmation avant de choisir la réponse.

Fiche express

À mémoriser

Avant de revenir au rendu de l'article 42, vérifiez les six distinctions :

  1. Flex est un plugin Composer, pas le kernel ni un bundle du blog.
  2. L'alias donne un nom court ; la recipe prépare la configuration ; le pack regroupe des dépendances. twig et twig/twig ne désignent pas le même package demandé.
  3. Le dépaquetage inscrit les dépendances concrètes du pack dans le projet : ne pas retrouver son nom comme exigence directe n'est pas une panne.
  4. composer.lock, symfony.lock et les fichiers configurés décrivent respectivement dépendances, recipes appliquées et contenu actuel. Les traces utiles se versionnent ensemble dans le projet.
  5. Le dépôt principal et recipes-contrib ont des politiques distinctes ; l'autorisation contrib dépend aussi des choix déjà enregistrés.
  6. Une recipe fonctionnelle ne garantit pas la maintenance future du package ni l'adéquation de toutes ses valeurs par défaut au blog.

Nous avons préparé les outils. La prochaine responsabilité appartient au code de l'application : fournir les données au template et retourner une Response. Flex ne rejoue pas l'installation à chaque visite.
