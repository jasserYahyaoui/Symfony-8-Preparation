Objectif

Savoir ce qu'est Flex techniquement, ce qu'une recipe fait, et quels files Flex écrit dans le projet.

L'essentiel

À comprendre

À retenir en priorité
  1. symfony.lock conserve les recipes appliquées.
  2. Les deux lock files ont des responsabilités distinctes.

Flex est un plugin Composer : il ne s'appelle pas, il change ce que font composer require, update et remove. Il apporte trois mécanismes — l'alias, la recipe, le pack — et note les recipes appliquées dans symfony.lock, à committer. Deux repositories de recipes, deux comportements.

Le schéma

À retenir en priorité
  1. Flex modifie le workflow Composer.
  2. Il ne s'enregistre pas dans config/bundles.php.

L'exemple : installer et configurer en une command

Exemple concret

composer require twig
# Flex résout l'alias, Composer installe symfony/twig-bundle,
# la recipe active le bundle et dépose sa configuration et templates/

Ce que Flex est

À comprendre

C'est quoi ?

Symfony Flex est un plugin de Composer, le gestionnaire de dépendances PHP. Il enrichit les opérations d'installation, mise à jour et suppression pour automatiser la configuration courante des packages dans une application Symfony.

À quoi ça sert ?

Installer le code d'un bundle ne suffit pas toujours : il faut souvent l'activer et ajouter sa configuration. Flex applique des instructions appelées recipes pour réduire ce travail répétitif. Il ne remplace ni Composer pour résoudre les versions, ni le kernel pour traiter les requêtes.

Où dans Symfony ?

Flex agit pendant les opérations Composer. Ce n'est pas un bundle à activer dans config/bundles.php, ni une commande du kernel. Son installation comme plugin est distincte de l'activation d'un bundle installé grâce à lui.

Comment, étape par étape ?

  1. Une commande Composer demande un package ou un alias compris par Flex.
  2. Flex résout éventuellement le nom court.
  3. Composer résout et installe les dépendances.
  4. Flex applique la recipe disponible et suit son état.

Exemple concret shell

Dans une application d'exercice déjà contrainte à Symfony 8.0, cette commande installerait TwigBundle 8.0 et Twig 3.22 ; elle n'est pas exécutée dans cette mission.

composer require 'symfony/twig-bundle:8.0.*' 'twig/twig:3.22.*'

Avec Flex actif, la recipe peut notamment activer TwigBundle et préparer sa configuration. Contre-exemple : ajouter Symfony\Flex\Flex à bundles.php pour « activer Flex ». Correction : gérer Flex comme plugin Composer ; seuls les bundles d'application vont dans la liste des bundles. L'automatisation ne dispense pas de relire les fichiers modifiés.

Passage canonique conservé

Ce que Flex est

Un plugin Composer, ni bundle ni command : il n'apparaît pas dans config/bundles.php. Sans lui, composer require twig échoue, parce que twig n'est le nom d'aucun package Composer.

Alias et recipes

À comprendre

À retenir en priorité
  1. L'alias twig résout un nom de package.
  2. La recipe configure ; le pack regroupe des dependencies.

C'est quoi ?

Un alias Flex est un nom court de package. Une recipe est un ensemble d'instructions de configuration. Un pack est un métapaquet qui regroupe des dépendances ; il ne constitue pas lui-même leur code applicatif. Ces trois notions répondent à trois questions différentes : quel nom demander, comment préparer l'application, quels packages regrouper.

À quoi ça sert ?

Le nom court facilite la commande, la recipe évite la configuration répétitive, et le pack installe un ensemble cohérent de fonctionnalités. Confondre ces rôles conduit à chercher un alias dans les classes PHP ou une recipe dans les dépendances d'exécution.

Où dans Symfony ?

L'alias twig pointe vers symfony/twig-bundle. Sa recipe peut activer le bundle et créer des fichiers sous config/ et templates/. Flex dépaquette les packs pour inscrire leurs dépendances concrètes dans le projet.

Comment, étape par étape ?

  1. Résoudre l'alias vers un vrai nom Composer.
  2. Installer le package et ses dépendances.
  3. Appliquer la recipe correspondante si elle existe.
  4. Examiner séparément changements de dépendances et changements de configuration.

Exemple concret text

Nom court demandé : twig
Package correspondant : symfony/twig-bundle
Effet de recipe : activation du bundle et configuration Twig
Code du moteur : fourni par la dépendance twig/twig

Cette chaîne explique pourquoi twig et twig/twig ne désignent pas la même demande. Contre-exemple : installer seulement la bibliothèque twig/twig puis attendre tous les fichiers de la recipe de TwigBundle. Correction : distinguer moteur et intégration au framework. Sans Flex, utiliser le nom Composer complet ; un nom court Flex n'est pas automatiquement un package valide pour Composer seul.

Passage canonique conservé

Alias et recipes

Trois mots, trois choses distinctes :

  • un alias est un nom court que Flex résout — twig en symfony/twig-bundle, api en api-platform/api-pack, un pack tiers ;
  • une recipe est la configuration qu'un package apporte : activer un bundle, créer des files et des directories, ajouter des variables à .env ;
  • un pack est un métapaquet sans code. Flex le dépaquette : on cherche en vain symfony/debug-pack dans composer.json après l'installation.

La liste complète des recipes et des alias est publiée dans RECIPES.md, sur le repository des recipes.

symfony.lock

À comprendre

C'est quoi ?

symfony.lock enregistre l'état des recipes appliquées par Flex. composer.lock enregistre les versions résolues des dépendances. Les deux fichiers suivent des objets différents et ne se remplacent pas.

À quoi ça sert ?

L'équipe doit savoir quelle configuration automatisée a été appliquée, pas seulement quelle version de bibliothèque est installée. Cet historique permet d'identifier une évolution de recipe et de distinguer ses changements des adaptations locales de l'application.

Où dans Symfony ?

Les deux fichiers de verrouillage vivent à la racine du projet et sont normalement versionnés avec les changements de configuration. symfony.lock ne remplace pas les fichiers créés par la recipe : leur contenu réel et leurs modifications applicatives restent à conserver.

Comment, étape par étape ?

  1. Flex applique une recipe.
  2. Son état est inscrit dans symfony.lock.
  3. Le développeur relit les changements de configuration.
  4. L'équipe conserve ensemble configuration et état des recipes, afin de comprendre les évolutions futures.

Exemple concret text

composer.lock : quelle version de symfony/twig-bundle est installée ?
symfony.lock  : quelle recipe TwigBundle a été appliquée ?
config/packages/twig.yaml : quelle configuration le projet utilise-t-il ?

Ces trois réponses sont complémentaires. Contre-exemple : ignorer symfony.lock parce que composer.lock existe déjà, ou supprimer une configuration en supposant que le lock contient sa copie complète. Correction : conserver les deux locks et les fichiers de configuration utiles. Le terme « versionné » décrit ici la pratique du projet cible ; aucune opération Git n'est réalisée par ce paquet de session.

Passage canonique conservé

symfony.lock

Il recense les recipes appliquées et leur version, et se committe : c'est lui qui permet de savoir qu'une recipe a évolué. Il joue pour les recipes le role que composer.lock joue pour les dependencies — deux files distincts.

Le package est un meuble livré en kit, la recipe sa notice d'assemblage. symfony.lock conserve la version de notice appliquée ; composer.lock conserve celle des pièces installées.

Les deux repositories de recipes

À comprendre

À retenir en priorité
  1. symfony/recipes constitue le catalogue sélectionné.
  2. recipes-contrib demande une autorisation.

C'est quoi ?

Un repository est un dépôt de fichiers. Le dépôt principal symfony/recipes contient une sélection de recipes pour des packages maintenus et de qualité. symfony/recipes-contrib accueille les contributions communautaires plus largement.

À quoi ça sert ?

Cette distinction rend visible une différence de sélection et de confiance. La présence d'une recipe fonctionnelle ne prouve pas à elle seule que le package associé sera maintenu dans la durée ni qu'il convient à l'application.

Où dans Symfony ?

Flex consulte le dépôt principal par défaut. L'installation d'une recipe de contrib demande une autorisation selon la configuration et les choix de l'utilisateur. Il ne faut pas assimiler cette permission à l'activation du bundle : elle concerne la provenance des instructions de configuration.

Comment, étape par étape ?

  1. Identifier le package demandé et la recipe proposée.
  2. Vérifier si elle provient du dépôt principal ou de contrib.
  3. Lire les changements qu'elle prévoit et l'état de maintenance du package.
  4. Autoriser ou refuser consciemment, puis relire les modifications appliquées.

Exemple concret text

Recipe A : dépôt principal, package sélectionné et maintenu
Recipe B : dépôt contrib, instructions utilisables mais maintenance du package à examiner

Le choix ne se réduit pas à « les deux déposent un fichier YAML ». Contre-exemple : accepter automatiquement toute recipe contrib parce qu'elle appartient à un dépôt de la communauté Symfony. Correction : distinguer fonctionnement des instructions, maintenance du package et pertinence pour le projet. La documentation présente les recipes contrib comme fonctionnelles ; ce n'est pas une garantie illimitée sur toutes les versions futures de leurs dépendances.

Passage canonique conservé

Les deux repositories de recipes

Repository Contenu Comportement de Flex
symfony/recipes liste curée, packages de qualité et maintenus seul consulté par défaut
symfony/recipes-contrib les recipes de la communauté demande votre permission

Les recipes contrib « are guaranteed to work » : c'est le package associé qui « could be unmaintained ».

Pièges d'examen

Piège à éviter

  • Voir l’explication : Flex est un plugin Composer, pas un bundle ni une command.

    Flex est un plugin Composer, pas un bundle ni une command. Il n'y a rien à appeler : il modifie composer require, update et remove. C'est aussi pourquoi composer require twig fonctionne alors qu'aucun package ne s'appelle twig.

  • Voir l’explication : symfony.lock n'est pas composer.lock.

    symfony.lock n'est pas composer.lock. Il recense les recipes appliquées, et il se committe.

  • Voir l’explication : Les deux repositories de recipes ne se comportent pas pareil.

    Les deux repositories de recipes ne se comportent pas pareil. symfony/recipes est appliqué sans question ; symfony/recipes-contrib demande une permission. La raison n'est pas que ses recipes seraient douteuses — la documentation les dit « guaranteed to work » — mais que les packages qu'elles configurent peuvent être abandonnés.

Application

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Flex = plugin Composer ; il change require, update, remove.
  • Alias : nom court ; recipe : configuration ; pack : métapaquet.
  • Un pack est dépaqueté : il n'apparaît pas dans composer.json.
  • symfony.lock recense les recipes et se committe.
  • symfony/recipes sans question ; recipes-contrib demande.
  • Contrib : recipe garantie, package peut-être abandonné.

Moyen mnémotechnique : « Un nom, une config, un package ».
