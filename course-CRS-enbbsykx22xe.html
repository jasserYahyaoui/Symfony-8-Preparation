Objectif

Savoir d'où vient l'object user, quelle method du provider est appelée à quel moment, et ce qui arrive quand le user change pendant sa session.

L'essentiel

À comprendre

À retenir en priorité
  1. Le provider charge et relit le user.
  2. supportsClass() décrit les classes prises en charge.

Un user provider retrouve un objet utilisateur depuis un identifiant. Il répond à « quel utilisateur correspond à cet identifiant ? », pas à « son mot de passe est-il correct ? » ni à « a-t-il le droit d'agir ? ». Ces responsabilités appartiennent aux autres étapes de Security.

Lorsqu'un firewall avec état restaure un token de session, ContextListener demande au provider de rafraîchir l'utilisateur et vérifie s'il est toujours acceptable. Avec un firewall lazy, ce travail peut être différé jusqu'à l'utilisation de la sécurité. Il ne faut donc pas imaginer un chargement inconditionnel pour toute requête, même publique et sans token.

Le schéma

À retenir en priorité
  1. La restauration déclenche une relecture.
  2. Un firewall stateless ne suit pas ce cycle de session.

Bleu : acteurs ; ambre : condition ; vert : données ou résultat. Les flèches sont des appels et des retours, pas une relation d'héritage. Un UserBadge peut fournir son propre chargeur : le provider configuré n'est pas un passage obligatoire de toute forme d'authentification.

Ce parcours suppose un token restaurable. La comparaison par défaut vérifie notamment les rôles, le mot de passe et l'identifiant ; EquatableInterface permet au user de définir sa comparaison. Une déconnexion peut ensuite entraîner un 401 ou une redirection sur une ressource protégée, selon l'authentification configurée ; le provider ne décide pas lui-même du statut HTTP.

L'exemple

Exemple concret

À retenir en priorité
  1. Le contrat suffit pour un provider maison.
  2. Aucun stockage tiers n'est requis par ce contrat.

Extrait du contrat d'un provider maison : all() représente ici une méthode applicative qui lit une source de confiance et retourne les utilisateurs indexés par identifiant. pw contient un hash, jamais un mot de passe en clair. Les imports et cette lecture de fichier ne sont pas détaillés.

class FileUserProvider implements UserProviderInterface
{
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        $data = $this->all()[$identifier] ?? throw new UserNotFoundException();

        return new InMemoryUser($identifier, $data['pw'], $data['roles']);
    }

    public function refreshUser(UserInterface $user): UserInterface
    {
        return $this->loadUserByIdentifier($user->getUserIdentifier());
    }

    public function supportsClass(string $class): bool
    {
        return InMemoryUser::class === $class;
    }
}

Le contrat

À retenir en priorité
  1. L'identifier est celui de l'authentication.
  2. Il n'est pas nécessairement une key de stockage.
Method Quand
loadUserByIdentifier() à la connexion : trouver le user
refreshUser() lors de la restauration du user d'un token de session sur un firewall avec état
supportsClass() dire si ce provider gère cette class

Le user n'est pas conservé tel quel : il est rechargé, puis comparé à celui du token.

Ce que l'exécution montre

À retenir en priorité
  1. Un user disparu ne reste pas authentifié.
  2. La session peut subsister sans son token.

Ces scénarios utilisent HTTP Basic, un token de session restauré pour le parcours avec état, et la comparaison standard du user, sans personnalisation par EquatableInterface. Les réponses 200 supposent une ressource autorisée.

Request Methods appelées Résultat
connexion HTTP Basic loadUserByIdentifier(alice) 200
Request suivante, cookie de session refreshUser(alice) 200
après suppression d'alice refreshUser lève UserNotFoundException 401 : token retiré
après ajout de ROLE_EDITOR à alice refreshUser(alice) token abandonné, alice anonyme
firewall sans état, deux Requests loadUserByIdentifier à chaque fois 200, jamais refreshUser
  • Un user supprimé : ContextListener retire la key du token de la session, qui survit ; le user redevient anonyme.
  • ContextListener::hasUserChanged() abandonne le token quand le password, les roles ou l'identifier diffèrent — ou quand isEqualTo() rend false pour une class EquatableInterface. Un role ajouté en base déconnecte.

Les providers fournis

À retenir en priorité
  1. Le chain compose plusieurs sources.
  2. L'ordre de recherche compte.
Mécanisme Core ou configuration associée Rôle
memory des users écrits dans la configuration (tests, prototypes)
chain plusieurs providers essayés dans l'ordre
id un service qui implémente UserProviderInterface

Le périmètre évalué ici est Security Core : InMemoryUserProvider, ChainUserProvider et le contrat d'un provider maison. Les clés memory, chain et id sont les moyens de les déclarer dans l'intégration framework, pas trois méthodes de UserProviderInterface.

Les providers ldap et entity relèvent d'intégrations distinctes et restent hors du contenu évalué de ce cours. Leur existence ne les transforme pas en providers livrés par Security Core.

Provider et firewall

À retenir en priorité
  1. Le hasher calcule le nouveau hash.
  2. L'upgrader l'enregistre.

Un firewall utilise un provider. Avec plusieurs providers, chaque firewall nomme le sien par la key provider, sinon InvalidConfigurationException.

Un provider qui implémente PasswordUpgraderInterface reçoit le password réencodé quand l'algorithme change.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le mode stateless évite la restauration de session.
  2. Le chargement suit la preuve de chaque Request.
  • Voir l’explication : refreshUser() appartient au parcours de restauration du token de session

    refreshUser() appartient au parcours de restauration du token de session, pas seulement à la connexion. Un firewall stateless ne suit pas ce parcours.

  • Voir l’explication : Un user supprimé est déconnecté

    Un user supprimé est déconnecté au rechargement suivant : 401 ou redirect, pas 500 ; la session survit, sans son token.

  • Voir l’explication : Avec la comparaison standard, des rôles modifiés invalident aussi le token

    Avec la comparaison standard, des rôles modifiés invalident aussi le token : le nouveau rôle n'est pas simplement ajouté au token existant. EquatableInterface peut personnaliser cette comparaison.

  • Choisir le provider du firewall

    Plusieurs providers imposent de nommer celui du firewall.

Fiche express

À mémoriser

À retenir en priorité
  1. Les roles font partie de la comparaison par défaut.
  2. Une comparaison personnalisée doit rester prudente.

Si tu dois retenir seulement 7 choses :

  • loadUserByIdentifier() lorsque le provider est utilisé pour charger l'identité ; un loader explicite de UserBadge peut le remplacer.
  • refreshUser() pour restaurer le user d'un token sur un firewall avec état.
  • Sans état : jamais refreshUser().
  • User supprimé : anonyme ; l'entry point peut répondre 401 ou rediriger, sans erreur 500 imposée ; la session survit.
  • Rôles, password ou identifier changés : déconnexion selon la comparaison du user ; EquatableInterface permet de la personnaliser.
  • Core : provider mémoire, chaîne et provider maison par id ; les providers de stockage externe restent hors périmètre.
  • Plusieurs providers : provider sur chaque firewall.

Moyen mnémotechnique : « Charger une fois, relire à chaque fois ».

provider : charger le user ; contexte avec token de session : le rafraîchir et le comparer ;
stateless : pas de restauration du token ; Core : mémoire, chaîne, contrat maison ; intégrations externes exclues
