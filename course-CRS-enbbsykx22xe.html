Objectif

Savoir d'où vient l'object user, quelle method du provider est appelée à quel moment, et ce qui arrive quand le user change pendant sa session.

L'essentiel

À comprendre

À retenir en priorité
  1. Le provider charge et relit le user.
  2. supportsClass() décrit les classes prises en charge.

Un provider charge le user à partir de l'identifier saisi, puis le relit à chaque Request d'un firewall avec état. Un user supprimé ou modifié est donc déconnecté au rechargement suivant, sans erreur 500.

Le schéma

À retenir en priorité
  1. La restauration déclenche une relecture.
  2. Un firewall stateless ne suit pas ce cycle de session.

L'exemple

Exemple concret

À retenir en priorité
  1. Le contrat suffit pour un provider maison.
  2. Aucun stockage tiers n'est requis par ce contrat.
class FileUserProvider implements UserProviderInterface
{
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        $data = $this->all()[$identifier] ?? throw new UserNotFoundException();

        return new InMemoryUser($identifier, $data['pw'], $data['roles']);
    }

    public function refreshUser(UserInterface $user): UserInterface
    {
        return $this->loadUserByIdentifier($user->getUserIdentifier());
    }

    public function supportsClass(string $class): bool
    {
        return InMemoryUser::class === $class;
    }
}

Le contrat

À comprendre

À retenir en priorité
  1. L'identifier est celui de l'authentication.
  2. Il n'est pas nécessairement une key de stockage.

C'est quoi ?

Un user provider est le service chargé de retrouver un user à partir de son identifier et de le recharger lorsqu'une authentication avec état est restaurée. Il ne remplace ni le hasher ni le voter.

À quoi ça sert ?

Une identité sauvegardée hier en session peut avoir changé : compte supprimé, mot de passe renouvelé ou rôles modifiés. Le rechargement évite de prendre l'objet de session pour une vérité permanente.

Où dans Symfony ?

UserProviderInterface expose loadUserByIdentifier(), refreshUser() et supportsClass(). Les sources configurables comprennent memory, ldap, chain et id pour un service personnalisé. entity dépend de l'intégration Doctrine ; ce n'est pas une capacité autonome de Security Core.

Comment, étape par étape ?

  1. À l'authentication, le provider charge l'identifier transmis, qui peut être un email plutôt qu'une clé primaire.
  2. Lors de la restauration d'un token avec état, refreshUser() retrouve le user actuel ; supportsClass() indique si ce provider sait traiter sa classe.
  3. Symfony compare les informations pertinentes. Un user disparu ne reste pas connecté simplement parce que sa session existe encore. Des changements d'identifier, de hash ou de rôles peuvent invalider le token selon la comparaison utilisée.
  4. En mode stateless, ce cycle de restauration n'a pas lieu : la preuve de chaque Request conduit au chargement nécessaire.

Exemple concret YAML

Fragment de configuration d'un provider applicatif déjà enregistré comme service :

security:
    providers:
        app_users:
            id: App\Security\UserProvider

App\Security\UserProvider doit réellement implémenter le contrat ; le YAML seul ne crée pas son code ni son stockage. Si plusieurs providers existent, sélectionner explicitement le provider du firewall qui en a besoin. Un provider chain essaie ses sources dans l'ordre : ce choix est utile pour plusieurs annuaires, mais un identifier présent dans plusieurs sources rend l'ordre significatif.

Contre-exemple : garder le user de session sans le recharger pour préserver artificiellement une connexion après suppression du compte. Correction : laisser le provider signaler l'absence et accepter l'invalidation du token. Une implémentation d'EquatableInterface personnalise la comparaison, mais ne doit pas faire ignorer des changements sensibles. Pour une migration de hash, le hasher calcule ; un PasswordUpgraderInterface doit encore enregistrer le résultat.

Le contrat

Method Quand
loadUserByIdentifier() à la connexion : trouver le user
refreshUser() à chaque Request suivante d'un firewall avec état

Le user n'est pas conservé tel quel : il est rechargé, puis comparé à celui du token.

Provider et firewall

À retenir en priorité
  1. Le hasher calcule le nouveau hash.
  2. L'upgrader l'enregistre.

Un firewall utilise un provider. Avec plusieurs providers, chaque firewall nomme le sien par la key provider, sinon InvalidConfigurationException.

Un provider qui implémente PasswordUpgraderInterface reçoit le password réencodé quand l'algorithme change.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le mode stateless évite la restauration de session.
  2. Le chargement suit la preuve de chaque Request.
  • Voir l’explication : refreshUser() s'exécute à chaque Request d'un firewall avec état

    refreshUser() s'exécute à chaque Request d'un firewall avec état, pas seulement à la connexion — et jamais sur un firewall sans état.

  • Voir l’explication : Un user supprimé est déconnecté

    Un user supprimé est déconnecté au rechargement suivant : 401 ou redirect, pas 500 ; la session survit, sans son token.

  • Voir l’explication : Des roles modifiés en base déconnectent aussi

    Des roles modifiés en base déconnectent aussi : le nouveau role ne s'obtient qu'en se reconnectant.

  • Choisir le provider du firewall

    Plusieurs providers imposent de nommer celui du firewall.

Fiche express

À mémoriser

À retenir en priorité
  1. Les roles font partie de la comparaison par défaut.
  2. Une comparaison personnalisée doit rester prudente.

Si tu dois retenir seulement 7 choses :

  • loadUserByIdentifier() à la connexion.
  • refreshUser() à chaque Request d'un firewall avec état.
  • Sans état : jamais refreshUser().
  • User supprimé : anonyme ; l'entry point peut répondre 401 ou rediriger, pas d'erreur 500 imposée ; la session survit.
  • Roles, password ou identifier changés : déconnexion selon la comparaison du user ; EquatableInterface personnalise cette comparaison.
  • memory, chain, id pour les providers couverts ici.
  • Plusieurs providers : provider sur chaque firewall.

Moyen mnémotechnique : « Charger une fois, relire à chaque fois ».

loadUserByIdentifier (connexion) → refreshUser (chaque Request avec état) → comparaison du user ;
supprimé = anonyme ; stateless = pas de refresh ; memory/chain/id
