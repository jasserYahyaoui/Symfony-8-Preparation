Objectif

Écrire une décision d'authorization qui dépend de l'object, et savoir comment les votes de plusieurs voters sont agrégés — parce que la strategy choisie change la décision à votes identiques.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Un voter peut ne pas être compétent.
  2. L'abstention n'est pas un refus individuel.

Un role dit ce qu'un user est ; un voter décide sur un object — « l'auteur peut modifier son article ». Chaque voter accorde, refuse ou s'abstient, et une strategy agrège les votes : à votes identiques, elle change la décision.

Le schéma

À retenir en priorité
  1. Le voter délimite son domain.
  2. La strategy décide à partir des votes.

Les deux methods, en 8.0

À retenir en priorité
  1. La signature a évolué en 8.0.
  2. Vote permet notamment d'ajouter une raison.
class PostVoter extends Voter
{
    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, ['POST_EDIT', 'POST_VIEW'], true) && $subject instanceof Post;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token, ?Vote $vote = null): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }
        if ('POST_EDIT' === $attribute && $subject->getAuthor() !== $user) {
            $vote?->addReason('Only the author may edit this post.');

            return false;
        }

        return true;
    }
}
  • supports() à false : le voter s'abstient, il ne refuse pas.
  • voteOnAttribute() rend un bool : accordé ou refusé.
  • Le quatrième parameter, ?Vote $vote = null, est obligatoire dans la signature en 8.0 : l'ancienne signature à trois parameters est une erreur fatale (« must be compatible with Voter::voteOnAttribute(…) »).
  • Vote::addReason() explique un refus : « Access Denied. Only the author may edit this post. ».
  • Un voter est un service autoconfiguré : aucune déclaration à écrire.

Trois valeurs, pas deux

À retenir en priorité
  1. Le voter ne prend pas position.
  2. Un autre voter peut traiter l'attribute.

ACCESS_GRANTED (1), ACCESS_ABSTAIN (0), ACCESS_DENIED (-1). L'abstention est le cas normal : chaque voter ne se prononce que sur son domain.

Les quatre strategies

À retenir en priorité
  1. Les mêmes votes peuvent produire des décisions différentes.
  2. priority dépend de l'ordre des voters.

security.access_decision_manager.strategy : affirmative (défaut), consensus, unanimous, priority ; une strategy maison passe par strategy_service (pas avec strategy). Les voters sont interrogés un par un :

Votes affirmative consensus unanimous priority
accordé, refusé accordé accordé refusé accordé
refusé, accordé accordé accordé refusé refusé
accordé, refusé, refusé accordé refusé refusé accordé
  • affirmative accorde au premier accord ; unanimous refuse au premier refus ; priority suit le premier voter qui ne s'abstient pas, dans l'ordre de la priority de leur tag ; seul consensus interroge tout le monde.

Les deux cas limites

À retenir en priorité
  1. Deux cas limites ont des réglages distincts.
  2. Ne pas assimiler égalité et absence de vote.
  • Égalité en consensus : allow_if_equal_granted_denied, défaut true.
  • Tous abstenus : allow_if_all_abstain, défaut false — refusé, y compris en unanimous. Avec true, un attribute mal orthographié est accordé.

Ce que le voter reçoit vraiment

À retenir en priorité
  1. Le voter ne doit pas supposer un user.
  2. Le subject et l'identité se vérifient séparément.
  • Un anonyme passe aussi par les voters, avec un NullToken : $token->getUser() vaut null.
  • isGranted($attribute, $subject, $accessDecision) remplit un AccessDecision : getMessage(), strategy.
  • Security::isGrantedForUser($user, …) décide pour un autre user (command, notification) ; un attribute d'état de connexion y lève InvalidArgumentException.
  • Dans un voter, vérifier un role par AccessDecisionManagerInterface::decide(), sur le token reçu, pas par Security::isGranted().
  • supportsAttribute() et supportsType() (CacheableVoterInterface) excluent un voter d'avance ; le résultat est mis en cache.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Aucun refus ne suffit pas sans vote favorable.
  2. Le cas tout-abstention utilise son réglage.
  • supports() à false = abstention, pas refus.
  • L'ancienne signature de voteOnAttribute() est une erreur fatale en 8.0.
  • Le défaut est affirmative : un seul accord suffit, même si un autre refuse.
  • unanimous = « aucun refus et au moins un accord » ; si tous s'abstiennent, allow_if_all_abstain décide, et refuse par défaut.
  • Les voters ne sont pas tous interrogés : seule consensus les consulte tous.
  • priority dépend de l'ordre des voters.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Réutiliser le token du vote en cours.
  2. Éviter une lecture implicite d'un autre contexte de sécurité.

Si tu dois retenir seulement 7 choses :

  • supports() trie (faux = abstention), voteOnAttribute() tranche.
  • Signature 8.0 : ?Vote $vote = null obligatoire ; addReason().
  • Votes : 1, 0, -1.
  • affirmative (défaut) : un accord suffit ; unanimous : un refus suffit ; priority : le premier qui vote ; consensus : la majorité.
  • Tous abstenus : refusé (allow_if_all_abstain: false).
  • Un anonyme vote aussi : NullToken.
  • isGrantedForUser() pour un autre user, sans attribute d'état.

Moyen mnémotechnique : « supports trie, voteOnAttribute tranche, la strategy agrège ».

supports (faux = abstain) → voteOnAttribute(…, ?Vote) → GRANTED/ABSTAIN/DENIED ;
affirmative | consensus (égalité = accordé) | unanimous | priority (ordre) ; tous abstenus = refusé
