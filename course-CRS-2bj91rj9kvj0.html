Objectif

Savoir ce que TwigBundle ajoute à Twig, où il cherche les templates, et quelles options de configuration comptent. La distinction component / bridge / bundle est traitée dans le Module 03 — Architecture Symfony.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Distinguer engine et intégration du framework.
  2. Le bundle expose paths, options et services.

Twig seul compile et rend un template. TwigBundle le branche sur Symfony : il dit où chercher les templates, comment surcharger ceux d'un bundle, et quelles options de config/packages/twig.yaml changent le comportement.

Le schéma

À retenir en priorité
  1. La surcharge prend priorité sur l'original.
  2. @! permet de reprendre l'original sans récursion.

La dernière flèche est un piège : la surcharge s'étend elle-même.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le préfixe @! cible le template original, pas la surcharge.
  2. parent() conserve le contenu du block parent après le bandeau ajouté.
{# templates/bundles/AcmeBlogBundle/user/profile.html.twig #}
{% extends '@!AcmeBlog/user/profile.html.twig' %}

{% block body %}
    <p class="banner">Bienvenue</p>
    {{ parent() }}
{% endblock %}

@AcmeBlog/user/profile.html.twig rend désormais le bandeau puis le contenu d'origine ; @!AcmeBlog/… rend l'original seul.

Trois packages, trois roles

Package Role
twig/twig l'engine : syntaxe, compiler, filters de base
symfony/twig-bridge les extensions qui exposent les components : path(), trans, le rendu de form
symfony/twig-bundle l'intégration : configuration, paths, services

composer require symfony/twig-bundle installe les trois : le bundle exige le bridge, qui exige twig/twig.

Où vivent les templates

À retenir en priorité
  1. default_path choisit le directory principal.
  2. paths complète les emplacements disponibles.
  • Par défaut dans templates/ : twig.default_path vaut %kernel.project_dir%/templates.
  • twig.paths ajoute des directories ; la valeur est un namespace facultatif. Sans namespace, le path rejoint l'espace principal ; avec, il se référence en @Nom/….
  • Un bundle expose ses templates sous @NomDuBundle/… sans le suffixe Bundle : @AcmeBlog/user/profile.html.twig.

Surcharger le template d'un bundle

Pour chaque bundle, deux emplacements, dans cet ordre — le premier gagne :

  1. templates/bundles/AcmeBlogBundle/ — le nom complet, suffixe compris ;
  2. le directory du bundle.

L'original reste accessible sous @!AcmeBlog, ce qui permet à la surcharge de l'étendre. Étendre @AcmeBlog/… depuis la surcharge la fait s'étendre elle-même : le rendu tourne jusqu'à épuiser la mémoire, sans message Twig.

Repère de l’exemple : It extends the original with @! and calls parent() inside its body block. Le préfixe @! cible le template original, pas la surcharge. parent() conserve le contenu du block parent après le bandeau ajouté.

Les options qui changent le comportement

À retenir en priorité
  1. Une variable absente peut lever en debug.
  2. default, defined et ?? permettent de gérer une absence prévue.
Option Effet Défaut
default_path déplace le directory des templates templates/
paths ajoute des directories, nommés ou non aucun
globals variables disponibles dans tous les templates aucune
form_themes theme de rendu des forms form_div_layout.html.twig
strict_variables variable inexistante : erreur au lieu de null %kernel.debug%

strict_variables suit kernel.debug : stricte en dev, permissive en prod. {{ typo }} lève une RuntimeError en dev et rend une string vide en prod ; typo|default('x'), typo is defined et user.name ?? 'anon' passent partout.

Dans globals, '@id' désigne un service ; '@@texte' produit la string @texte.

Les commands

À retenir en priorité
  1. lint:twig détecte les erreurs de syntaxe.
  2. debug:twig inventorie les extensions et paths disponibles.
  • debug:twig — filters, functions, tests, globales et paths ; avec un nom de template, le file qui le sert : « Matched File », puis les « Overridden Files » qu'il masque ; --filter restreint la liste.
  • lint:twig — vérifie la syntaxe sans rendre, et sort avec le code 1 en cas d'erreur ; --show-deprecations traite les deprecations comme des erreurs.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Trois packages, un seul à installer.

    Trois packages, un seul à installer. L'engine, le bridge et le bundle sont distincts : c'est le bundle qui tire les deux autres, et c'est lui seul qui rend Twig configurable.

  • Voir l’explication : Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde.

    Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde. @AcmeBlog/... d'un côté, templates/bundles/AcmeBlogBundle/ de l'autre.

  • Voir l’explication : strict_variables n'a pas la même valeur partout.

    strict_variables n'a pas la même valeur partout. Par défaut elle vaut kernel.debug.

  • Voir l’explication : Le directory par défaut se change, mais on peut aussi en ajouter.

    Le directory par défaut se change, mais on peut aussi en ajouter. Ce sont deux options différentes : l'une remplace, l'autre complète.

Application

À retenir en priorité
  1. lint:twig détecte les erreurs de syntaxe.
  2. debug:twig inventorie les extensions et paths disponibles.
  3. La surcharge prend priorité sur l'original.
  4. @! permet de reprendre l'original sans récursion.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Engine, bridge, bundle : le bundle tire les deux autres et configure.
  • default_path remplace templates/ ; paths ajoute.
  • Surcharge : templates/bundles/AcmeBlogBundle/ ; original : @!AcmeBlog.
  • strict_variables = %kernel.debug% ; default, is defined, ?? passent toujours.
  • globals : @ service, @@ littéral.
  • debug:twig <nom> dit qui sert ; lint:twig sort en 1 sur erreur.

Moyen mnémotechnique : « la surcharge d'abord, le bang pour l'original ».

twig/twig ← twig-bridge ← twig-bundle (configure) ; templates/ + paths (@Nom) ;
@AcmeBlog = surcharge puis bundle ; @!AcmeBlog = bundle ; strict_variables = kernel.debug
