Objectif

Savoir ce que TwigBundle ajoute à Twig, où il cherche les templates, et quelles options de configuration comptent. La distinction component / bridge / bundle est traitée dans le Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Distinguer engine et intégration du framework.
  2. Le bundle expose paths, options et services.

Twig seul compile et rend un template. TwigBundle le branche sur Symfony : il dit où chercher les templates, comment surcharger ceux d'un bundle, et quelles options de config/packages/twig.yaml changent le comportement.

Le schéma

À retenir en priorité
  1. La surcharge prend priorité sur l'original.
  2. @! permet de reprendre l'original sans récursion.

Les losanges ambre représentent les choix du loader ; les sorties vertes, les fichiers retenus. Les flèches pleines décrivent la recherche du fichier, les pointillés un extends Twig, pas un héritage PHP. La dernière flèche est un piège : la surcharge s'étend elle-même. Vue simplifiée pour les emplacements du bundle, sans chemin twig.paths personnalisé prioritaire ; si aucun fichier n'existe, le loader échoue.

L'exemple

Exemple concret

À retenir en priorité
  1. Le préfixe @! cible le template original, pas la surcharge.
  2. parent() conserve le contenu du block parent après le bandeau ajouté.
{# templates/bundles/AcmeBlogBundle/user/profile.html.twig #}
{% extends '@!AcmeBlog/user/profile.html.twig' %}

{% block body %}
    <p class="banner">Bienvenue</p>
    {{ parent() }}
{% endblock %}

@AcmeBlog/user/profile.html.twig rend désormais le bandeau puis le contenu d'origine ; @!AcmeBlog/… rend l'original seul.

Trois packages, trois roles

À comprendre

C'est quoi ?

Twig est un moteur de templates : il combine une structure de présentation avec des variables pour produire du texte. Trois packages ont des responsabilités distinctes : twig/twig comprend le langage ; symfony/twig-bridge fournit des extensions qui relient Twig aux components Symfony ; symfony/twig-bundle configure leur intégration à l'application.

À quoi ça sert ?

Cette séparation explique pourquoi un template Twig valide peut échouer dans un autre environnement : une fonction comme path() n'appartient pas au langage de base. Le moteur peut fonctionner hors Symfony ; les fonctions du bridge nécessitent leurs dépendances et leur enregistrement.

Où dans Symfony ?

TwigBundle fournit le service de rendu et la configuration twig. Par défaut, les templates se trouvent dans templates/. default_path change ce répertoire principal ; paths ajoute des emplacements, éventuellement associés à un namespace, préfixe logique comme @Shared. Il ne s'agit pas d'un namespace PHP.

Comment, étape par étape ?

  1. Vérifier quels packages et extensions sont disponibles.
  2. Fournir un template existant et les variables attendues.
  3. Configurer strict_variables pour choisir entre erreur et valeur nulle lorsqu'une variable manque. Son défaut suit kernel.debug, qui peut être configuré : ne pas déduire le comportement du seul nom d'environnement.
  4. Utiliser debug:twig pour examiner l'environnement et lint:twig pour contrôler la syntaxe, sans confondre ce dernier avec un rendu réel.

Exemple concret YAML

Dans config/packages/twig.yaml :

twig:
    default_path: '%kernel.project_dir%/templates'
    strict_variables: true
    paths:
        '%kernel.project_dir%/shared_templates': Shared

Un fichier shared_templates/card.html.twig se référence par @Shared/card.html.twig. Contre-exemple : écrire ce nom dans un Twig autonome dont aucun loader ne connaît Shared. Correction : configurer le loader ou l'intégration correspondante ; le préfixe ne découvre pas un dossier tout seul.

Pour surcharger un template de bundle, le répertoire applicatif utilise le nom complet du bundle, tandis que le namespace omet habituellement le suffixe Bundle. Si la surcharge étend l'original, utiliser le namespace @!Nom prévu à cet effet plutôt que se référencer elle-même.

Passage canonique conservé
Package Role
twig/twig l'engine : syntaxe, compiler, filters de base
symfony/twig-bridge les extensions qui exposent les components : path(), trans, le rendu de form
symfony/twig-bundle l'intégration : configuration, paths, services

composer require symfony/twig-bundle installe les trois : le bundle exige le bridge, qui exige twig/twig.

Où vivent les templates

À retenir en priorité
  1. default_path choisit le directory principal.
  2. paths complète les emplacements disponibles.
  • Par défaut dans templates/ : twig.default_path vaut %kernel.project_dir%/templates.
  • twig.paths ajoute des directories ; la valeur est un namespace facultatif. Sans namespace, le path rejoint l'espace principal ; avec, il se référence en @Nom/….
  • Un bundle expose ses templates sous @NomDuBundle/… sans le suffixe Bundle : @AcmeBlog/user/profile.html.twig.

Surcharger le template d'un bundle

À comprendre

C'est quoi ?

Une surcharge applicative fournit un template à la place de celui d'un bundle, sans modifier le package du bundle. Le namespace Twig est un nom logique de recherche, distinct du nom de répertoire utilisé pour la surcharge.

À quoi ça sert ?

On personnalise une présentation tout en conservant la possibilité de mettre à jour le bundle. Étendre son template original permet aussi de ne remplacer que les blocks nécessaires plutôt que copier tout le fichier.

Où dans Symfony ?

Pour AcmeBlogBundle, le namespace est @AcmeBlog et le répertoire applicatif est templates/bundles/AcmeBlogBundle. Le loader cherche la surcharge avant l'original. @!AcmeBlog demande l'original en contournant la surcharge applicative.

Comment, étape par étape ?

  1. Repérer le chemin relatif du template fourni par le bundle.
  2. Reproduire ce chemin sous le répertoire de surcharge.
  3. Étendre l'original avec le préfixe @! si l'on souhaite en conserver la structure.
  4. Ne remplacer que les blocks réellement définis par ce template.

Exemple concret Twig

Supposons AcmeBlogBundle installé, avec layout.html.twig contenant un block title. Dans templates/bundles/AcmeBlogBundle/layout.html.twig :

{% extends '@!AcmeBlog/layout.html.twig' %}
{% block title %}Mon site — {{ parent() }}{% endblock %}

Un rendu de @AcmeBlog/layout.html.twig choisit cette surcharge ; parent conserve le titre original. Contre-exemple : étendre @AcmeBlog/layout.html.twig depuis ce même fichier. Le loader retrouve la surcharge elle-même, ce qui entraîne une récursion. Correction : employer @!AcmeBlog. Le point d'exclamation ne crée pas un bundle absent et le block choisi doit exister dans son contrat de template.

Passage canonique conservé

Pour chaque bundle, deux emplacements, dans cet ordre — le premier gagne :

  1. templates/bundles/AcmeBlogBundle/ — le nom complet, suffixe compris ;
  2. le directory du bundle.

L'original reste accessible sous @!AcmeBlog, ce qui permet à la surcharge de l'étendre. Étendre @AcmeBlog/… depuis la surcharge la fait s'étendre elle-même : le rendu tourne jusqu'à épuiser la mémoire, sans message Twig.

Repère de l’exemple : It extends the original with @! and calls parent() inside its body block. Le préfixe @! cible le template original, pas la surcharge. parent() conserve le contenu du block parent après le bandeau ajouté.

Les options qui changent le comportement

À retenir en priorité
  1. Une variable absente peut lever en debug.
  2. default, defined et ?? permettent de gérer une absence prévue.
Option Effet Défaut
default_path déplace le directory des templates templates/
paths ajoute des directories, nommés ou non aucun
globals variables disponibles dans tous les templates aucune
form_themes theme de rendu des forms form_div_layout.html.twig
strict_variables variable inexistante : erreur au lieu de null %kernel.debug%

Par défaut, strict_variables suit kernel.debug, pas le nom de l'environnement. Avec debug activé, {{ typo }} lève une RuntimeError si la variable manque ; sans debug, il rend une chaîne vide. C'est habituellement le contraste dev/prod, mais on peut configurer ces valeurs autrement. typo|default('x'), typo is defined et user.name ?? 'anon' traitent explicitement l'absence de donnée, même en mode strict.

Dans globals, '@id' désigne un service ; '@@texte' produit la string @texte.

Les commands

À comprendre

À retenir en priorité
  1. lint:twig détecte les erreurs de syntaxe.
  2. debug:twig inventorie les extensions et paths disponibles.

C'est quoi ?

debug:twig inspecte l'environnement Twig chargé : fonctions, filtres, tests, globales et chemins. lint:twig vérifie la syntaxe des templates sans produire leur rendu avec les données métier.

À quoi ça sert ?

Les deux commandes isolent des problèmes différents. Une fonction inconnue peut venir d'une extension non enregistrée ; une variable inexistante au rendu ne sera pas nécessairement détectée par le lint.

Où dans Symfony ?

Ces commandes appartiennent à l'intégration Symfony de Twig et s'exécutent dans l'application concernée, avec ses services et sa configuration. Donner un nom de template à debug:twig permet aussi de voir le fichier sélectionné et les fichiers qu'il masque.

Comment, étape par étape ?

  1. Linter le fichier ou le répertoire suspect.
  2. Inspecter le nom de fonction ou de filtre recherché.
  3. En cas de surcharge inattendue, inspecter le template résolu.
  4. Compléter par un rendu avec le contexte réel ; un succès syntaxique ne garantit pas les valeurs.

Exemple concret shell

Dans une application où le namespace Shared et card.html.twig sont configurés :

php bin/console lint:twig templates/
php bin/console debug:twig --filter=path
php bin/console debug:twig '@Shared/card.html.twig'

La première commande contrôle la syntaxe ; la deuxième cherche les éléments correspondants ; la troisième explique la résolution du fichier. Contre-exemple : considérer un lint réussi comme preuve que customer.address existe. Correction : tester également le rendu, notamment sous strict_variables. lint:twig --show-deprecations signale aussi les dépréciations comme des erreurs ; ce contrôle n'exécute pas la logique métier des pages.

Passage canonique conservé
  • debug:twig — filters, functions, tests, globales et paths ; avec un nom de template, le file qui le sert : « Matched File », puis les « Overridden Files » qu'il masque ; --filter restreint la liste.
  • lint:twig — vérifie la syntaxe sans rendre, et sort avec le code 1 en cas d'erreur ; --show-deprecations traite les deprecations comme des erreurs.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Trois packages, un seul à installer.

    Trois packages, un seul à installer. L'engine, le bridge et le bundle sont distincts : le bundle tire les deux autres et expose la configuration Symfony sous twig:. Twig reste configurable sans le bundle, directement via son Environment et ses loaders.

  • Voir l’explication : Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde.

    Le nom d'espace d'un bundle perd son suffixe ; le directory de surcharge le garde. @AcmeBlog/... d'un côté, templates/bundles/AcmeBlogBundle/ de l'autre.

  • Voir l’explication : strict_variables n'a pas la même valeur partout.

    strict_variables n'a pas la même valeur partout. Par défaut elle vaut kernel.debug.

  • Voir l’explication : Le directory par défaut se change, mais on peut aussi en ajouter.

    Le directory par défaut se change, mais on peut aussi en ajouter. Ce sont deux options différentes : l'une remplace, l'autre complète.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Engine, bridge, bundle : le bundle tire les deux autres et configure.
  • default_path remplace templates/ ; paths ajoute.
  • Surcharge : templates/bundles/AcmeBlogBundle/ ; original : @!AcmeBlog.
  • strict_variables = %kernel.debug% ; default, is defined, ?? passent toujours.
  • globals : @ service, @@ littéral.
  • debug:twig <nom> dit qui sert ; lint:twig sort en 1 sur erreur.

Moyen mnémotechnique : « la surcharge d'abord, le bang pour l'original ».

twig/twig ← twig-bridge ← twig-bundle (configure) ; templates/ + paths (@Nom) ;
@AcmeBlog = surcharge puis bundle ; @!AcmeBlog = bundle ; strict_variables = kernel.debug
