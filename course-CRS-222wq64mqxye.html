Objectif

Choisir le bon sac de la Request et connaître la constraint que InputBag impose — c'est là que se situe le piège.

L'essentiel

○ À comprendre

À retenir en priorité
  1. InputBag::get() refuse un array.
  2. all($key) attend un array et rend [] si la key est absente.

La Request range chaque source de données dans un sac typé ; on nomme toujours le sac, car Request::get() n'existe plus en 8.0. Trois sacs sont des InputBag, qui refusent un array dans get(). Deux données viennent du client et se falsifient : l'adresse IP et le Host — chacune a sa propre liste de confiance, vide par défaut.

Le schéma

À retenir en priorité
  1. Nommer explicitement le bag évite les collisions.
  2. request contient le body de form, pas toute la Request.

L'exemple : lire une recherche

▣ Exemple concret

// /search?q=php&tags[]=php&tags[]=http
$request->query->get('q');       // 'php'
$request->query->all('tags');    // ['php', 'http']
$request->query->get('tags');    // BadRequestException : valeur non scalaire
$request->attributes->get('_route');

Les sacs

○ À comprendre

C'est quoi ?

Un sac, ou bag, est un objet regroupant des valeurs de même provenance dans la Request. Lire le bon sac rend explicite l'origine des données au lieu de fusionner indistinctement URL, formulaire, cookies et informations de routage.

À quoi ça sert ?

Le même nom peut exister à plusieurs endroits : un id de route n'est pas nécessairement l'id envoyé dans le formulaire. Une lecture précise évite qu'un changement de contenu client remplace implicitement la donnée que le code pensait utiliser.

Où dans Symfony ?

  • query : paramètres de l'URL ; request : paramètres de corps de formulaire.
  • cookies : cookies reçus ; files : fichiers téléversés.
  • headers : champs HTTP ; server : informations fournies par le serveur.
  • attributes : données applicatives, notamment route et controller.

$request->request est donc un sac, pas l'objet Request entier. Le JSON brut n'est pas automatiquement la même chose qu'un formulaire POST : getPayload() fournit un InputBag à partir des paramètres de formulaire disponibles ou du JSON décodé ; getContent() lit les données brutes.

Comment, étape par étape ?

  1. Identifier la provenance attendue par le contrat de l'action.
  2. Lire le sac correspondant.
  3. Choisir une lecture scalaire ou multiple adaptée.
  4. Valider le sens métier de la valeur ; sélectionner le bon sac ne suffit pas à valider son contenu.

Exemple concret PHP

Avec HttpFoundation 8.0 chargé :

<?php
use Symfony\Component\HttpFoundation\Request;
$request = Request::create('/article/42?page=2', 'POST', ['title' => 'Bonjour']);
$request->attributes->set('id', 42);
echo $request->attributes->get('id'), "\n";
echo $request->query->get('page'), "\n";
echo $request->request->get('title'), "\n";

On attend 42, 2, Bonjour. Contre-exemple : lire title dans query alors que le formulaire l'envoie dans son corps. Correction : lire request, ou getPayload() si le contrat accepte aussi du JSON. Request::create() construit ici une demande locale ; il ne lit pas les superglobales comme createFromGlobals().

Passage canonique conservé

Les sacs

Property Type Contenu
$query InputBag Parameters d'URL ($_GET)
$request InputBag Corps de form ($_POST)
$cookies InputBag Cookies
$attributes ParameterBag Données de l'application (route, _route, _controller)
$headers, $server, $files HeaderBag, ServerBag, FileBag Headers, $_SERVER, files téléversés

Le nom $request désigne le corps POST, pas la Request entière. getPayload() lit le body JSON ou form-data et rend, lui aussi, un InputBag.

Une Request est un courrier trié dans des bacs nommés : query pour l'adresse enrichie, request pour le form body, headers pour les indications de traitement. Les attributes sont les notes ajoutées par l'application, pas un autre bag de saisie client.

InputBag n'accepte que des scalaires

○ À comprendre

C'est quoi ?

Le titre vise la lecture par InputBag::get() : le sac peut contenir des tableaux, mais get() ne doit pas les retourner comme une valeur scalaire. all($key) lit une entrée tableau ; all() lit le contenu complet du sac.

À quoi ça sert ?

Un client peut envoyer tags[]=php là où le programme attendait tags=php. Refuser une forme inattendue évite de traiter arbitrairement le premier élément ou de convertir un tableau en chaîne sans savoir quelle donnée a été acceptée.

Où dans Symfony ?

query, request et cookies utilisent InputBag dans les cas usuels. get() lève une BadRequestException si la valeur est un tableau. all('tags') refuse une valeur non tableau et retourne [] si la clé manque. attributes, un ParameterBag applicatif, peut porter d'autres types ; cela ne supprime pas le besoin d'un contrat sur ce qu'on y stocke.

Comment, étape par étape ?

  1. Définir si l'entrée attendue est unique ou multiple.
  2. Utiliser get() pour une valeur scalaire.
  3. Utiliser all($key) pour un tableau.
  4. Valider ensuite les éléments : obtenir un tableau ne garantit pas qu'il ne contient que les chaînes autorisées.

Exemple concret PHP

<?php
use Symfony\Component\HttpFoundation\Request;
$request = Request::create('/search?q=php&tags[]=php&tags[]=http');
echo $request->query->get('q'), "\n";
echo implode(', ', $request->query->all('tags')), "\n";
var_export($request->query->all('missing'));

On attend php, php, http, puis un tableau vide. Contre-exemple : remplacer all('tags') par get('tags') ; l'appel échoue au lieu de retourner le premier tag. Correction : choisir la méthode correspondant à la forme prévue. De même, get('tags[0]') ne parcourt pas automatiquement un tableau imbriqué : lire le tableau puis son élément selon le contrat validé.

Passage canonique conservé

InputBag n'accepte que des scalaires

InputBag::get() lève une BadRequestException sur une valeur non scalaire : un array reçu là où un scalaire est attendu doit échouer bruyamment. all($key) en est le miroir : il refuse ce qui n'est pas un array, et rend [] pour une key absente. $attributes, un ParameterBag, n'a pas cette restriction : son contenu vient de l'application, pas du client.

Sur un POST, getMethod() lit X-HTTP-Method-Override sans rien activer ; seul _method exige enableHttpMethodParameterOverride(). En 8.0, un override vers GET, HEAD, CONNECT ou TRACE est ignoré ; getRealMethod() donne la method reçue.

Client et proxys

○ À comprendre

À retenir en priorité
  1. Déclarer les proxys de confiance avant de lire les headers transférés.
  2. L'adresse la plus à gauche n'est pas automatiquement fiable.

C'est quoi ?

Un reverse proxy reçoit la connexion du client puis transmet la demande à l'application. REMOTE_ADDR décrit alors le pair réseau immédiat, souvent ce proxy. Les champs Forwarded ou X-Forwarded-* peuvent décrire le trajet précédent, mais leur contenu n'est fiable que si l'expéditeur autorisé les contrôle.

À quoi ça sert ?

Déclarer les proxys de confiance permet de retrouver des informations externes sans accepter aveuglément des valeurs envoyées par n'importe quel client. Une adresse déclarée dans un header ne prouve pas son authenticité.

Où dans Symfony ?

setTrustedProxies() ou la configuration trusted_proxies identifie les proxys ; le masque ou trusted_headers sélectionne les champs à croire. Sans cette confiance, getClientIp() se fonde sur REMOTE_ADDR. Avec une chaîne reconnue, il retient l'adresse non fiable la plus proche après retrait des proxys fiables, pas automatiquement la première valeur à gauche.

Comment, étape par étape ?

  1. Identifier les véritables proxys devant l'application.
  2. Limiter la confiance à leurs adresses et aux champs qu'ils réécrivent correctement.
  3. Lire l'adresse avec l'API Request, pas par découpage artisanal du header.
  4. Vérifier toute la chaîne et les accès directs possibles au serveur applicatif.

Exemple concret PHP

Laboratoire isolé avec adresses réservées à la documentation ; ne pas recopier cette liste comme configuration de production.

<?php
use Symfony\Component\HttpFoundation\Request;
Request::setTrustedProxies(['192.0.2.10'], Request::HEADER_X_FORWARDED_FOR);
$request = Request::create('/demo');
$request->server->set('REMOTE_ADDR', '192.0.2.10');
$request->headers->set('X-Forwarded-For', '198.51.100.1, 203.0.113.8');
echo $request->getClientIp(), "\n";
Request::setTrustedProxies([], 0);

Le résultat attendu est 203.0.113.8, la valeur non fiable la plus proche du proxy connu, pas 198.51.100.1. Contre-exemple : croire tous les expéditeurs pour obtenir « la vraie IP ». Correction : définir la frontière réseau réelle et ne faire confiance qu'aux proxys maîtrisés ; sinon un client peut fournir lui-même les informations supposées fiables.

Passage canonique conservé

Client et proxys

Sans proxys de confiance (setTrustedProxies() ou trusted_proxies), getClientIp() ignore X-Forwarded-For et rend l'adresse du proxy. Une fois déclarés, Symfony complète la chaîne d'adresses avec REMOTE_ADDR, retire toute adresse appartenant à un proxy de confiance, renverse le reste et rend le premier élément : l'adresse non fiable la plus proche du serveur.

// X-Forwarded-For: 1.2.3.4, 5.6.7.8   (aucun des deux de confiance)
$request->getClientIp();    // '5.6.7.8', et non '1.2.3.4'

Le client d'origine n'est renvoyé que si toute la chaîne de proxies est déclarée de confiance.

Le host, et la seconde liste de confiance

○ À comprendre

À retenir en priorité
  1. trusted_hosts protège le Host, pas la chaîne de proxys.
  2. Ancrer les regex ; une liste vide n'impose pas de restriction.

C'est quoi ?

Le host est le nom d'hôte demandé, utilisé notamment pour construire des URL absolues. La liste des hôtes de confiance limite les noms acceptés. Elle est distincte de la liste des proxys de confiance, qui porte sur les expéditeurs et leurs informations de transfert.

À quoi ça sert ?

Un hôte inattendu peut contaminer un lien absolu ou une clé de cache. Une expression régulière, motif de correspondance, doit donc décrire le nom complet autorisé, pas seulement une sous-chaîne ressemblante.

Où dans Symfony ?

Request::setTrustedHosts() reçoit des motifs que Symfony entoure de délimiteurs et traite sans sensibilité à la casse, mais sans ajouter automatiquement ^ et $. Ces ancres bornent respectivement le début et la fin. Un point littéral s'écrit \. dans le motif, car . seul signifie un caractère quelconque.

Comment, étape par étape ?

  1. Définir les noms réellement servis.
  2. Écrire un motif ancré et échapper les points.
  3. Configurer la liste avant de lire l'hôte.
  4. Refuser les hôtes hors liste ; une liste vide n'impose pas ce contrôle supplémentaire.

Exemple concret PHP

Laboratoire HttpFoundation 8.0 isolé :

<?php
use Symfony\Component\HttpFoundation\Request;
Request::setTrustedHosts(['^example\.test$']);
$request = Request::create('https://example.test/demo');
echo $request->getHost(), "\n";
Request::setTrustedHosts([]);

Le résultat attendu est example.test. Avec la même liste, example.test.other.test serait refusé lors de la lecture de l'hôte. Contre-exemple : utiliser seulement example.test : le point n'est pas échappé et l'absence d'ancres autorise des correspondances partielles. Correction : employer le motif complet montré. Autoriser les sous-domaines doit être un choix explicite, pas un effet accidentel d'une expression trop large.

Passage canonique conservé

Le host, et la seconde liste de confiance

Un Host falsifié empoisonne une URL absolue d'email ou une key de cache. Request::setTrustedHosts(['^(.+\.)?example\.com$']) fait lever une SuspiciousOperationException à getHost() sur un host hors liste. Les patterns sont des regex non ancrées ({motif}i) : ['example.com'] accepte example.com.attaquant.test. Et une liste vide ne vérifie rien. Deux listes, deux dangers : trusted_proxies garde X-Forwarded-For, trusted_hosts garde Host.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : $request->request n'est pas la Request

    $request->request n'est pas la Request : c'est le body POST.

  • Voir l’explication : get() sur un array lève.

    get() sur un array lève. Ce n'est pas null, ni le premier élément.

  • Voir l’explication : getClientIp() sans trusted proxies renvoie l'IP du proxy

    getClientIp() sans trusted proxies renvoie l'IP du proxy, pas celle du client — et c'est le comportement sûr.

  • Voir l’explication : getClientIp() ne renvoie pas « la plus à gauche ».

    getClientIp() ne renvoie pas « la plus à gauche ». Il renvoie l'adresse non fiable la plus proche du serveur — ce qui coïncide avec le client d'origine uniquement quand toute la chaîne de proxies est déclarée de confiance. Fonder une allow-list sur la lecture inverse revient à faire confiance à une valeur que le client contrôle.

  • Voir l’explication : Request::create() n'est pas createFromGlobals().

    Request::create() n'est pas createFromGlobals(). La première fabrique une Request arbitraire — tests, sub-Requests ; la seconde lit les superglobales.

Application

À retenir en priorité
  1. Nommer explicitement le bag évite les collisions.
  2. request contient le body de form, pas toute la Request.
  3. trusted_hosts protège le Host, pas la chaîne de proxys.
  4. Ancrer les regex ; une liste vide n'impose pas de restriction.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • Nommer le sac : Request::get() n'existe plus en 8.0.
  • $request = body POST ; $attributes = données de l'application.
  • InputBag::get() refuse un array, all() refuse un scalaire.
  • getPayload() : JSON ou form-data, rendu en InputBag.
  • X-HTTP-Method-Override lu sans activation ; vers GET ignoré en 8.0.
  • getClientIp() : l'adresse non fiable la plus proche du serveur — le client d'origine seulement si toute la chaîne de proxies est de confiance.
  • Trusted hosts : regex non ancrées, liste vide = aucun contrôle.

Moyen mnémotechnique : « Nommer le sac, ancrer le host, déclarer le proxy ».
