Objectif

Choisir le bon sac de la Request et connaître la constraint que InputBag impose — c'est là que se situe le piège.

L'essentiel

○ À comprendre

À retenir en priorité
  1. InputBag::get() refuse un array.
  2. all($key) attend un array et rend [] si la key est absente.

La Request range chaque source de données dans un sac typé ; on nomme toujours le sac, car Request::get() n'existe plus en 8.0. Trois sacs sont des InputBag, qui refusent un array dans get(). Deux données viennent du client et se falsifient : l'adresse IP et le Host — chacune a sa propre liste de confiance, vide par défaut.

Le schéma

À retenir en priorité
  1. Nommer explicitement le bag évite les collisions.
  2. request contient le body de form, pas toute la Request.

L'exemple : lire une recherche

▣ Exemple concret

Revoir la règle : Nommer explicitement le bag évite les collisions.

// /search?q=php&tags[]=php&tags[]=http
$request->query->get('q');       // 'php'
$request->query->all('tags');    // ['php', 'http']
$request->query->get('tags');    // BadRequestException : valeur non scalaire
$request->attributes->get('_route');

Les sacs

Revoir la règle : Nommer explicitement le bag évite les collisions.

Property Type Contenu
$query InputBag Parameters d'URL ($_GET)
$request InputBag Corps de form ($_POST)
$cookies InputBag Cookies
$attributes ParameterBag Données de l'application (route, _route, _controller)
$headers, $server, $files HeaderBag, ServerBag, FileBag Headers, $_SERVER, files téléversés

Le nom $request désigne le corps POST, pas la Request entière. getPayload() lit le body JSON ou form-data et rend, lui aussi, un InputBag.

Une Request est un courrier trié dans des bacs nommés : query pour l'adresse enrichie, request pour le form body, headers pour les indications de traitement. Les attributes sont les notes ajoutées par l'application, pas un autre bag de saisie client.

InputBag n'accepte que des scalaires

Revoir la règle : InputBag::get() refuse un array.

InputBag::get() lève une BadRequestException sur une valeur non scalaire : un array reçu là où un scalaire est attendu doit échouer bruyamment. all($key) en est le miroir : il refuse ce qui n'est pas un array, et rend [] pour une key absente. $attributes, un ParameterBag, n'a pas cette restriction : son contenu vient de l'application, pas du client.

Sur un POST, getMethod() lit X-HTTP-Method-Override sans rien activer ; seul _method exige enableHttpMethodParameterOverride(). En 8.0, un override vers GET, HEAD, CONNECT ou TRACE est ignoré ; getRealMethod() donne la method reçue.

Client et proxys

À retenir en priorité
  1. Déclarer les proxys de confiance avant de lire les headers transférés.
  2. L'adresse la plus à gauche n'est pas automatiquement fiable.

Sans proxys de confiance (setTrustedProxies() ou trusted_proxies), getClientIp() ignore X-Forwarded-For et rend l'adresse du proxy. Une fois déclarés, Symfony complète la chaîne d'adresses avec REMOTE_ADDR, retire toute adresse appartenant à un proxy de confiance, renverse le reste et rend le premier élément : l'adresse non fiable la plus proche du serveur.

// X-Forwarded-For: 1.2.3.4, 5.6.7.8   (aucun des deux de confiance)
$request->getClientIp();    // '5.6.7.8', et non '1.2.3.4'

Le client d'origine n'est renvoyé que si toute la chaîne de proxies est déclarée de confiance.

Le host, et la seconde liste de confiance

À retenir en priorité
  1. trusted_hosts protège le Host, pas la chaîne de proxys.
  2. Ancrer les regex ; une liste vide n'impose pas de restriction.

Un Host falsifié empoisonne une URL absolue d'email ou une key de cache. Request::setTrustedHosts(['^(.+\.)?example\.com$']) fait lever une SuspiciousOperationException à getHost() sur un host hors liste. Les patterns sont des regex non ancrées ({motif}i) : ['example.com'] accepte example.com.attaquant.test. Et une liste vide ne vérifie rien. Deux listes, deux dangers : trusted_proxies garde X-Forwarded-For, trusted_hosts garde Host.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Déclarer les proxys de confiance avant de lire les headers transférés.

$request->request n'est pas la Request : c'est le body POST.

get() sur un array lève. Ce n'est pas null, ni le premier élément.

getClientIp() sans trusted proxies renvoie l'IP du proxy, pas celle du client — et c'est le comportement sûr.

getClientIp() ne renvoie pas « la plus à gauche ». Il renvoie l'adresse non fiable la plus proche du serveur — ce qui coïncide avec le client d'origine uniquement quand toute la chaîne de proxies est déclarée de confiance. Fonder une allow-list sur la lecture inverse revient à faire confiance à une valeur que le client contrôle.

Request::create() n'est pas createFromGlobals(). La première fabrique une Request arbitraire — tests, sub-Requests ; la seconde lit les superglobales.

Fiche express

◆ À mémoriser

Revoir la règle : Nommer explicitement le bag évite les collisions.

Si tu dois retenir seulement 7 choses :

  • Nommer le sac : Request::get() n'existe plus en 8.0.
  • $request = body POST ; $attributes = données de l'application.
  • InputBag::get() refuse un array, all() refuse un scalaire.
  • getPayload() : JSON ou form-data, rendu en InputBag.
  • X-HTTP-Method-Override lu sans activation ; vers GET ignoré en 8.0.
  • getClientIp() : l'adresse non fiable la plus proche du serveur — le client d'origine seulement si toute la chaîne de proxies est de confiance.
  • Trusted hosts : regex non ancrées, liste vide = aucun contrôle.

Moyen mnémotechnique : « Nommer le sac, ancrer le host, déclarer le proxy ».
