Objectif

Manipuler files et directories avec un comportement uniforme entre systèmes, et surtout : des erreurs qui lèvent une exception au lieu de rendre false silencieusement comme les functions natives de PHP.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Une opération de path n'implique pas une lecture disque.
  2. Choisir la class selon l'effet recherché.

Le component Filesystem manipule files et directories avec un comportement uniforme, et surtout des erreurs qui lèvent une exception au lieu de rendre false en silence. Deux classes : Filesystem agit sur le disque, Path calcule des strings de path sans y toucher.

Le schéma

À retenir en priorité
  1. Le remplacement évite une écriture partielle visible.
  2. Le directory parent est créé si nécessaire.

L'exemple : publier un rapport

▣ Exemple concret

À retenir en priorité
  1. Un rapport complet remplace le contenu.
  2. appendToFile() ajoute à l'existant.
$filesystem = new Filesystem();
try {
    $filesystem->mkdir('/var/reports', 0700);
    $filesystem->dumpFile('/var/reports/today.html', $html);   // un lecteur voit l'ancien ou le nouveau, entier
    $filesystem->appendToFile('/var/log/reports.log', "ok\n", true);
} catch (IOExceptionInterface $e) {
    echo 'Échec sur '.$e->getPath();
}

Les opérations à connaître

À retenir en priorité
  1. mkdir() facilite une préparation idempotente.
  2. Les permissions restent soumises au umask.
Appel Résultat (umask 022)
mkdir('a/b/c') trois niveaux, mode 0755 (0777 moins le umask)
mkdir() sur l'existant aucune exception
rename() sur une cible existante IOException ; avec true, la cible est remplacée
remove(['lien', '/un/dossier', 'f.log']) files, directories et liens

mkdir() et remove() acceptent un array ou tout Traversable. symlink() a un troisième argument qui duplique le directory au lieu de créer le lien — sous Windows seulement : le code le nomme $copyOnWindows. Exécuté sous Linux avec true, c'est bien un lien qui est créé.

Écrire et lire

○ À comprendre

À retenir en priorité
  1. L'échec est explicite.
  2. Le caller doit gérer ou propager l'exception.

C'est quoi ?

Filesystem réalise des opérations sur fichiers et répertoires ; Path manipule leurs noms sans garantir leur existence. Une écriture atomique rend visible soit l'ancien fichier complet, soit le nouveau, plutôt qu'un contenu partiellement écrit.

À quoi ça sert ?

Publier un rapport complet demande un remplacement, pas l'ajout de morceaux à un ancien rapport. Distinguer les opérations évite une corruption logique même lorsque chaque appel système réussit.

Où dans Symfony ?

  • mkdir() prépare les répertoires ; les permissions effectives dépendent notamment du umask.
  • dumpFile() remplace via un fichier temporaire puis déplacement.
  • appendToFile() ajoute en fin et peut demander un verrou d'écriture.
  • rename() déplace ; l'écrasement d'une cible doit être intentionnel.
  • readFile() lève une exception en cas de lecture impossible ; remove() supprime fichiers, liens ou répertoires ciblés.

Comment, étape par étape ?

  1. Délimiter les chemins dont l'application est propriétaire ; ne pas accepter arbitrairement un chemin de suppression fourni par un client.
  2. Choisir remplacement ou ajout selon le résultat attendu.
  3. Propager ou traiter les exceptions avec leur contexte ; IOExceptionInterface::getPath() aide, mais ne doit pas être supposé toujours renseigné.
  4. En test, utiliser un répertoire temporaire dédié et le nettoyer dans un finally ; ne jamais supprimer un répertoire temporaire partagé entier.

Exemple concret PHP

Fonction d'écriture d'un rapport, avec chemin fourni par la configuration de l'application et component installé :

<?php
use Symfony\Component\Filesystem\Filesystem;

function publishReport(Filesystem $filesystem, string $ownedPath, string $content): string
{
    $filesystem->dumpFile($ownedPath, $content);
    return $filesystem->readFile($ownedPath);
}

L'appelant choisit un chemin autorisé ; cette fonction ne fait pas une validation universelle de chemins utilisateurs. Une erreur remonte, au lieu de renvoyer un contenu vide comme faux succès. Cet exemple d'écriture n'est pas exécuté dans le projet canonique.

Contre-exemple : employer appendToFile() pour remplacer un rapport, ou croire que l'atomicité règle deux mises à jour concurrentes. Correction : utiliser le remplacement pour un document complet et un protocole de concurrence si nécessaire. L'atomicité de visibilité ne constitue ni une transaction multi-fichiers ni une garantie contre toute perte de mise à jour. Pour des tests portables, construire les chemins sans dépendre d'un répertoire local fixe et distinguer normalisation lexicale et résolution réelle sur disque.

Filesystem 8.0.

Passage canonique conservé

Écrire et lire

  • dumpFile() est atomique : file temporaire, puis déplacement. Elle crée le file et son directory au besoin.
  • appendToFile() ajoute à la fin, crée file et directory s'ils manquent, et accepte un troisième argument pour verrouiller l'écriture.
  • readFile() lève une IOException là où file_get_contents() rendrait false : file absent, ou directory.

Les erreurs

À retenir en priorité
  1. Le path peut aider au diagnostic.
  2. Ne pas supposer qu'il est renseigné dans tous les cas.

Tout échec lève une exception ExceptionInterface ou IOExceptionInterface, dont getPath() dit sur quel path l'opération a échoué. Exception exécutée : readFile() sur un directory construit l'exception sans path — getPath() rend null, le path n'est que dans le message.

Un environment de test portable

▣ Exemple concret

À retenir en priorité
  1. Ne pas dépendre d'un path local fixe.
  2. Le nettoyage isole les exécutions.

C'est quoi ?

Un test de fichiers portable choisit un emplacement temporaire disponible sur la machine, isole les fichiers qu'il possède et les nettoie même si une assertion échoue. Il ne dépend pas d'un /var/reports préexistant ni des données d'un autre test.

À quoi ça sert ?

Deux tests simultanés ne doivent pas écraser le même rapport. Un test raté ne doit pas laisser une ancienne sortie faire réussir le suivant.

Où dans Symfony ?

Filesystem::tempnam() réserve un fichier temporaire au nom unique ; dumpFile() remplace son contenu ; readFile() le relit ou lève une exception ; remove() nettoie seulement la cible possédée. Path manipule des chemins lexicalement : il ne prouve ni existence ni droit d'accès.

Comment, étape par étape ?

  1. Demander un nom unique sous sys_get_temp_dir() ; ne pas utiliser un chemin fixe partagé.
  2. Mettre l'écriture et les assertions dans un bloc try.
  3. Vérifier le remplacement complet, puis le cas de contenu vide : vide est une valeur valide, pas une erreur de lecture.
  4. Dans finally, retirer uniquement le fichier créé. Si une opération échoue, laisser remonter l'exception ; ne pas convertir une erreur de lecture en chaîne vide.

Exemple concret PHP

Test PHPUnit avec Filesystem disponible, à exécuter dans un environnement autorisé à créer des fichiers temporaires :

<?php
use PHPUnit\Framework\TestCase;
use Symfony\Component\Filesystem\Filesystem;

final class ReportFileTest extends TestCase
{
    public function testReplacesContentAndAllowsEmptyReport(): void
    {
        $filesystem = new Filesystem();
        $path = $filesystem->tempnam(sys_get_temp_dir(), 'report_test_', '.txt');
        try {
            $filesystem->dumpFile($path, 'ancien');
            $filesystem->dumpFile($path, 'nouveau');
            self::assertSame('nouveau', $filesystem->readFile($path));
            $filesystem->dumpFile($path, '');
            self::assertSame('', $filesystem->readFile($path));
        } finally {
            $filesystem->remove($path);
        }
    }
}

Contre-exemple : ajouter le nouveau rapport par append puis supprimer tout le répertoire temporaire partagé pour nettoyer. Correction : remplacer le document et supprimer uniquement le chemin réservé au test. Ce test vérifie le contenu et le nettoyage, pas l'atomicité face à des lecteurs concurrents ni une garantie de durabilité après panne. Aucune écriture de cet exemple n'est exécutée dans cette mission, limitée à ses deux JSON privés.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Append et remplacement sont différents.
  2. Un verrou d'écriture n'est pas un remplacement atomique.
  • Voir l’explication : mkdir() est récursive et ignore l'existant

    mkdir() est récursive et ignore l'existant — elle n'échoue pas sur un directory déjà là.

  • Voir l’explication : dumpFile() est atomique

    dumpFile() est atomique, appendToFile() ne l'est pas.

  • Voir l’explication : readFile() lève sur un directory

    readFile() lève sur un directory, contrairement à file_get_contents().

  • Voir l’explication : remove() accepte un array

    remove() accepte un array et traite files, directories et liens.

  • Voir l’explication : getPath() est sur IOExceptionInterface

    getPath() est sur IOExceptionInterface et nomme le path fautif — sauf pour readFile() sur un directory, où il rend null.

  • Distinguer manipulation de paths et accès au disque

    Path ne touche pas au disque.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le défaut protège la cible existante.
  2. L'écrasement doit être demandé.

Si tu dois retenir seulement 6 choses :

  • Filesystem agit, Path calcule sans toucher au disque.
  • mkdir() récursive, existant ignoré, umask appliqué.
  • dumpFile() atomique ; appendToFile() avec lock optionnel.
  • readFile() lève au lieu de rendre false.
  • IOExceptionInterface::getPath() — null pour un directory lu.
  • rename(…, true) pour écraser ; remove() prend un array.

Moyen mnémotechnique : « Agir sur le disque, calculer sur les strings ».
