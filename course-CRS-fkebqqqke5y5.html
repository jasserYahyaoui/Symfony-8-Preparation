Objectif

Après l'inscription au blog, un service prépare une notification. Nous voulons observer ses appels sans recopier son comportement ni modifier chaque consommateur. La décoration change l'objet obtenu sous un identifiant tout en conservant l'original derrière lui. Nous allons suivre cette délégation, son contrat de type et l'ordre réel des appels lorsque plusieurs couches interviennent.

L'essentiel

À comprendre

À retenir en priorité
  1. La décoration conserve l'original.
  2. Le consommateur reçoit le decorator.

Un decorator reçoit un service intérieur et expose un contrat compatible aux consommateurs. Le container redirige l'identifiant décoré vers cette enveloppe ; l'original reste accessible au decorator par une référence interne. La délégation n'est pas automatique : c'est sa méthode qui choisit d'appeler l'intérieur, avant ou après son traitement supplémentaire.

La priorité règle l'assemblage : la plus haute est appliquée d'abord, donc près de la cible. La plus basse finit à l'extérieur et reçoit le premier appel du consommateur. Cette règle n'est pas celle de l'ordre d'appel des event listeners.

Le schéma

À retenir en priorité
  1. La priority haute se place au cœur.
  2. La plus basse est appelée en premier depuis l'extérieur.

La notification fournit un exemple où l'on journalise avant de déléguer. Les pointillés représentent le câblage compilé, les flèches pleines les appels ultérieurs :

Le consommateur reçoit LoggingMailer sous le contrat attendu, puis celui-ci utilise le logger et son service intérieur. MailerInterface et LoggerInterface sont des types, pas des objets interfaces. Le résultat vert suppose que les deux opérations réussissent. Si le logger lève une exception, la délégation suivante n'a pas lieu ; la ligne sending ne prouve donc pas à elle seule une livraison. Le laboratoire suivant remplace volontairement tout envoi réel par un stockage en mémoire.

Le fil rouge : un `LoggingMailer`

À retenir en priorité
  1. Le contrat commun rend la substitution possible.
  2. Le type concret peut provoquer une TypeError.

Message, MailerInterface et Mailer sont ici des types locaux de démonstration, pas les signatures du composant Mailer. Dans le projet PSR-4, leurs déclarations vont dans leurs fichiers sous src/Mailer/. Ce petit support rend l'effet observable :

namespace App\Mailer;

final class Message
{
    public function __construct(public readonly string $text) {}
}

interface MailerInterface
{
    public function send(Message $message): void;
}

class Mailer implements MailerInterface
{
    public array $sent = [];

    public function send(Message $message): void
    {
        $this->sent[] = $message;
    }
}

Le decorator utilise le même contrat local et le logger PSR-3 :

namespace App\Mailer;

use Psr\Log\LoggerInterface;
use Symfony\Component\DependencyInjection\Attribute\AsDecorator;
use Symfony\Component\DependencyInjection\Attribute\AutowireDecorated;

#[AsDecorator(decorates: Mailer::class)]
class LoggingMailer implements MailerInterface
{
    public function __construct(
        #[AutowireDecorated]
        private MailerInterface $inner,     // l'original, câblé sur .inner
        private LoggerInterface $logger,
    ) {
    }

    public function send(Message $message): void
    {
        $this->logger->info('sending');
        $this->inner->send($message);
    }
}

Avec les définitions enregistrées, les lecteurs d'attributes actifs et un logger disponible, send(new Message('Inscription reçue')) émet d'abord sending, puis ajoute ce même Message au tableau du Mailer intérieur. Le logger peut être un logger de test ; aucune connexion ni livraison d'email n'est réalisée par ce laboratoire. La décoration conserve aussi le résultat et les exceptions du contrat : elle ne dispense pas de choisir le comportement en cas d'échec.

🌍 In Real Life

La situation : un guichet note la demande avant de la transmettre au poste intérieur. Si la prise de note échoue, la transmission suivante n'a pas lieu.

L’équivalent dans Symfony : guichet → LoggingMailer ; note → appel du logger ; transmission → appel explicite de $inner->send().

Retour à la réalité technique : le câblage fournit l'intérieur mais ne délègue pas à la place du code. L'exemple local conserve le message en mémoire, sans email réel. Une ligne sending ne prouve aucune livraison.

🧠 Comment le mémoriser : « Disposer de l'intérieur ne veut pas dire l'appeler. » Image mentale : demande encore au guichet. Question-réflexe : quelle ligne délègue, et peut-on échouer avant ?

⚠️ À ne pas confondre : contrat de type commun et comportement métier effectivement préservé.

Le mécanisme : prendre la place, garder l'identifier

À retenir en priorité
  1. L'identifier de la cible reste utilisable.
  2. La substitution est centralisée dans le container.

Voici la variante de configuration externe, à utiliser à la place des instructions de décoration portées par les attributes. Elle déclare la cible, publie l'interface et fournit les deux arguments du LoggingMailer :

services:
    App\Mailer\Mailer: ~
    App\Mailer\MailerInterface: '@App\Mailer\Mailer'
    App\Mailer\LoggingMailer:
        decorates: App\Mailer\Mailer
        arguments:
            $inner: '@.inner'
            $logger: '@logger'

Avec logger défini, un consommateur de l'interface reçoit maintenant LoggingMailer, qui conserve Mailer. Aucun consommateur n'a besoin de connaître le nouvel identifiant interne. AsDecorator propose decorates, priority (défaut 0) et onInvalid ; leurs équivalents YAML sont decorates, decoration_priority et decoration_on_invalid.

L'identifiant conservé ne modifie pas les règles de type PHP :

Le consommateur est typé par… Ce qu'il reçoit
l'interface MailerInterface Logging(Mailer)
la class Mailer TypeError : « must be of type App\Mailer, App\LoggingMailer given »

La deuxième ligne décrit notre LoggingMailer, qui n'étend pas Mailer. Le diagnostic peut apparaître pendant les vérifications du câblage ou lors de l'injection ; conserver le même nom de service ne rend pas l'objet compatible. L'interface commune évite ce couplage concret.

Pour isoler la composition de toute intégration, conservons aussi ce laboratoire PHP autonome de formatage d'un libellé :

interface Formatter { public function format(string $value): string; }
final class PlainFormatter implements Formatter
{
    public function format(string $value): string { return trim($value); }
}
final class BracketFormatter implements Formatter
{
    public function __construct(private Formatter $inner) {}
    public function format(string $value): string
    {
        return '['.$this->inner->format($value).']';
    }
}
$formatter = new BracketFormatter(new PlainFormatter());
echo $formatter->format(' prêt '), "\n";

La sortie [prêt] montre deux responsabilités conservées : l'intérieur retire les espaces, l'extérieur ajoute les crochets. Cet assemblage manuel ne configure aucun service Symfony. Remplacer complètement PlainFormatter ferait perdre sa recette ; le décorer conserve un chemin de délégation.

🌍 In Real Life

La situation : la même adresse de guichet mène désormais à un nouvel intermédiaire. Les clients doivent accepter le service qu'il rend, pas exiger l'identité de l'ancien employé.

L’équivalent dans Symfony : adresse conservée → identifiant décoré ; intermédiaire → decorator ; capacité commune → interface implémentée.

Retour à la réalité technique : la redirection de l'identifiant ne transforme pas LoggingMailer en instance de Mailer. Une injection typée par cette classe concrète peut échouer ; l'interface commune permet la composition illustrée.

🧠 Comment le mémoriser : « Même adresse, objet différent. » Image mentale : un nouveau guichet derrière la même enseigne. Question-réflexe : le consommateur accepte-t-il réellement le type de l'enveloppe ?

⚠️ À ne pas confondre : décoration conservant un chemin vers l'original et remplacement complet de sa définition.

`.inner` : l'original n'est pas perdu

À retenir en priorité
  1. L'original est disponible en inner.
  2. Une injection explicite clarifie la délégation.

Par défaut, le nom interne est <id du decorator>.inner, donc ici App\Mailer\LoggingMailer.inner, pas App\Mailer\Mailer.inner. Il désigne la cible conservée pour cette couche ; avec plusieurs decorators, l'intérieur immédiat peut être une autre couche.

La référence '@.inner' du YAML est réécrite pour viser ce service. #[AutowireDecorated] l'indique explicitement dans un argument autowiré. L'autowiring peut aussi reconnaître l'intérieur par son type lorsqu'un seul argument approprié correspond au type de la cible à travers les méthodes autowirées. Deux arguments compatibles peuvent rendre cette inférence insuffisante : mieux vaut nommer la dépendance voulue.

decoration_inner_name permet de choisir le nom interne. En revanche, injecter à la place l'identifiant externe décoré peut ramener vers le decorator lui-même et créer une dépendance circulaire. L'identifiant interne est un détail d'assemblage, pas une invitation à le récupérer partout dans le code métier.

🌍 In Real Life

La situation : le guichet possède un passage intérieur ; s'adresser à sa propre entrée publique pour transmettre une demande le ramènerait vers lui-même.

L’équivalent dans Symfony : passage intérieur → référence @.inner ou #[AutowireDecorated] ; entrée publique → identifiant décoré.

Retour à la réalité technique : le nom interne par défaut utilise l'identifiant du decorator suivi de .inner, pas celui de la cible. Avec plusieurs couches, l'intérieur immédiat peut être une autre enveloppe. Réinjecter l'identifiant externe peut créer un cycle.

🧠 Comment le mémoriser : « Pour déléguer, prends le passage intérieur. » Image mentale : une porte vers le poste suivant, distincte de l'entrée du guichet. Question-réflexe : cette référence mène-t-elle à l'intérieur ou revient-elle vers moi ?

⚠️ À ne pas confondre : nom interne d'assemblage et API à récupérer partout dans le métier.

Empiler des decorators : l'ordre contre-intuitif

À retenir en priorité
  1. L'ordre de construction inverse l'ordre d'entrée.
  2. Ne pas confondre priority et premier appel.

Le catalogue en mémoire peut aussi illustrer plusieurs couches, sans ajouter de persistance. Conservons les noms abstraits Repo, Metrics, Cache et Log : leurs classes doivent partager un contrat et recevoir leur service intérieur.

En partant de Repo, la priorité 10 assemble Metrics(Repo). La priorité 5 enveloppe ce résultat : Cache(Metrics(Repo)). La priorité 0 donne enfin Log(Cache(Metrics(Repo))). Le consommateur entre donc dans Log, puis éventuellement Cache, Metrics et Repo. Les traitements placés après délégation reviennent dans l'ordre inverse.

Si Cache rend déjà un résultat sans déléguer, Metrics et Repo ne sont pas appelés pour cet accès. Mesurer « toutes les consultations » ou seulement « les calculs du catalogue » exige donc un placement différent. Le container n'invente aucune politique de cache à partir de ces noms.

À priorité égale, le premier decorator déclaré est appliqué d'abord, donc devient le plus interne : First puis Second donne Second(First(Core)). Il faut lire l'enveloppe finale, pas déduire le premier appel du plus grand nombre.

🌍 In Real Life

La situation : on pose trois housses successives sur un objet ; la première posée est la plus profonde, la dernière est touchée en premier.

L’équivalent dans Symfony : première housse, priorité haute → couche interne ; dernière, priorité basse → couche externe ; accès depuis l'extérieur → premier appel du consommateur.

Retour à la réalité technique : 10, 5, 0 produisent Log(Cache(Metrics(Repo))). La délégation peut s'arrêter dans Cache ; les noms seuls ne créent aucune politique. À égalité, la première décoration déclarée est appliquée d'abord et devient plus interne.

🧠 Comment le mémoriser : « Première posée, dernière atteinte. » Image mentale : housses imbriquées. Question-réflexe : quelle est l'enveloppe finale, et chaque couche délègue-t-elle ?

⚠️ À ne pas confondre : priorité d'assemblage des decorators et ordre d'appel des event listeners.

Si la cible n'existe pas

À retenir en priorité
  1. ignore retire le decorator.
  2. null conserve un decorator avec un inner nul.

Une intégration de notification optionnelle n'est pas présente dans tous les environments. La décoration doit choisir une politique pour cette absence, indépendamment de la nullabilité PHP :

decoration_on_invalid Résultat
exception (défaut) ServiceNotFoundException : « …has a dependency on a non-existent service "nope" »
ignore le decorator est retiré
null nope existe et désigne le decorator, avec null pour original

Avec exception, l'assemblage échoue : c'est utile si l'absence signale une configuration incorrecte. Avec ignore, la définition du decorator est retirée ; ses autres consommateurs doivent encore former un graphe valide.

Avec null, le decorator doit réellement accepter un argument ?MailerInterface et définir un comportement sans intérieur. Notre LoggingMailer actuel ne le permet pas : ajouter seulement decoration_on_invalid: null ne transforme pas sa signature et ne fournit pas un faux Mailer qui ne ferait rien. Le service conserve aussi les règles ordinaires de visibilité et d'optimisation ; un decorator privé inutilisé n'est pas garanti accessible directement après toutes les passes.

🌍 In Real Life

La situation : le poste intérieur manque : on peut refuser l'installation, retirer le guichet supplémentaire, ou garder un guichet explicitement capable de travailler seul.

L’équivalent dans Symfony : refus → exception ; retrait → ignore ; enveloppe sans intérieur → null.

Retour à la réalité technique : accepter null exige une signature nullable et un comportement adapté ; la configuration ne les invente pas. ignore retire le decorator, sans garantir que ses autres consommateurs restent valides. Visibilité et optimisation ordinaires restent applicables.

🧠 Comment le mémoriser : « Refuser, retirer ou savoir fonctionner sans intérieur. » Image mentale : trois décisions devant un poste vide. Question-réflexe : mon decorator est-il réellement conçu pour cette absence ?

⚠️ À ne pas confondre : intérieur null et faux service neutre créé automatiquement.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le type concret reste vérifié par PHP.
  2. Typer le contrat commun évite cette incompatibilité.
  • Voir l’explication : Conserver la cible n'est pas garantir son appel.

    Conserver la cible n'est pas garantir son appel. L'intérieur est disponible sous le nom du decorator suivi de .inner, mais la méthode doit déléguer ; notre log peut même échouer avant cet appel.

  • Voir l’explication : Priorité d'assemblage et ordre d'entrée sont inversés.

    Priorité d'assemblage et ordre d'entrée sont inversés. Construisons les enveloppes depuis Repo ; Log, de priorité la plus basse, reçoit alors le premier appel. Un cache peut interrompre cette descente.

  • Voir l’explication : L'identifiant reste, pas nécessairement la class concrète.

    L'identifiant reste, pas nécessairement la class concrète. Le consommateur garde sa référence mais doit accepter l'objet livré. La compatibilité de signature ne suffit pas non plus si le comportement du contrat est arbitrairement changé.

  • Voir l’explication : ignore et null sont deux politiques différentes.

    ignore et null sont deux politiques différentes. Le premier retire le decorator ; le second peut conserver une enveloppe sans intérieur, qui doit être conçue pour cette absence.

  • Voir l’explication : Notre interface locale est le contrat commun.

    Notre interface locale est le contrat commun. LoggingMailer n'est pas une instance de Mailer. Un héritage compatible serait techniquement possible si la cible l'autorise, mais la décoration par composition n'exige pas cette dépendance à la class concrète.

  • Voir l’explication : À priorité égale, suivre encore l'ordre d'assemblage.

    À priorité égale, suivre encore l'ordre d'assemblage. First est appliqué avant Second, donc Second devient l'enveloppe externe ; ce départage ne signifie pas que les deux services sont fusionnés.

Fiche express

À mémoriser

À retenir en priorité
  1. La déclaration départage les priorities égales.
  2. Le premier se retrouve plus près de l'original.

Avant d'ajouter la journalisation de notification :

  1. Vérifier le contrat réellement demandé par les consommateurs.
  2. Conserver la cible via l'intérieur et fournir les autres dépendances.
  3. Choisir les appels avant/après délégation et leur politique d'erreur.
  4. Construire les enveloppes de priorité haute vers basse, puis lire l'exécution depuis l'extérieur.
  5. Départager les priorités égales par l'ordre de déclaration.
  6. Choisir explicitement erreur, retrait ou intérieur nullable si la cible manque.

La décoration organise une chaîne autour d'un service. Pour réunir plusieurs services indépendants, comme les canaux de notification, nous avons besoin d'un autre mécanisme : les tags.
