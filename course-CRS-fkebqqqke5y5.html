Objectif

Envelopper un service existant sans le remplacer ni toucher à ses consommateurs, atteindre l'original par .inner, empiler plusieurs decorators dans le bon ordre et choisir le comportement quand la cible manque. Quand décorer plutôt qu'employer un compiler pass relève de Framework overloading.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La décoration conserve l'original.
  2. Le consommateur reçoit le decorator.

Un decorator prend la place d'un service sous son identifier : ses consommateurs le reçoivent sans changer une ligne. L'original n'est pas perdu : il devient .inner. Empilés, les decorators s'appliquent de la plus haute priority à la plus basse — la plus basse finit à l'extérieur.

Le schéma

À retenir en priorité
  1. La priority haute se place au cœur.
  2. La plus basse est appelée en premier depuis l'extérieur.

Le fil rouge : un `LoggingMailer`

À retenir en priorité
  1. Le contrat commun rend la substitution possible.
  2. Le type concret peut provoquer une TypeError.
#[AsDecorator(decorates: Mailer::class)]
class LoggingMailer implements MailerInterface
{
    public function __construct(
        private MailerInterface $inner,     // l'original, câblé sur .inner
        private LoggerInterface $logger,
    ) {
    }

    public function send(Message $message): void
    {
        $this->logger->info('sending');
        $this->inner->send($message);
    }
}

Le mécanisme : prendre la place, garder l'identifier

À retenir en priorité
  1. L'identifier de la cible reste utilisable.
  2. La substitution est centralisée dans le container.
services:
    App\Mailer\LoggingMailer:
        decorates: App\Mailer\Mailer
        arguments: ['@.inner']
  • #[AsDecorator] : decorates, priority (0), onInvalid — en YAML decorates, decoration_priority, decoration_on_invalid.
  • Le decorator implémente la même interface que la cible :
Le consommateur est typé par… Ce qu'il reçoit
l'interface MailerInterface Logging(Mailer)
la class Mailer TypeError : « must be of type App\Mailer, App\LoggingMailer given »

Remplacer fait disparaître l'original ; décorer le garde, en délégation.

`.inner` : l'original n'est pas perdu

À retenir en priorité
  1. L'original est disponible en inner.
  2. Une injection explicite clarifie la délégation.

Le service décoré est renommé <id du decorator>.inner. Le decorator le reçoit :

  • en autowiring, par un argument typé comme la cible — automatiquement ;
  • par #[AutowireDecorated] sur l'argument ;
  • par '@.inner' en configuration.

decoration_inner_name change ce nom.

Empiler des decorators : l'ordre contre-intuitif

À retenir en priorité
  1. L'ordre de construction inverse l'ordre d'entrée.
  2. Ne pas confondre priority et premier appel.

Une priority plus haute est appliquée plus tôt, donc au plus près de la cible. Trois decorators de Repo — Metrics (10), Cache (5), Log (0) — donnent Log(Cache(Metrics(Repo))) : le consommateur appelle Log d'abord.

À priority égale, le premier déclaré est le plus interne.

Si la cible n'existe pas

À retenir en priorité
  1. ignore retire le decorator.
  2. null conserve un decorator avec un inner nul.
decoration_on_invalid Résultat
exception (défaut) ServiceNotFoundException : « …has a dependency on a non-existent service "nope" »
ignore le decorator est retiré
null nope existe et désigne le decorator, avec null pour original

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le type concret reste vérifié par PHP.
  2. Typer le contrat commun évite cette incompatibilité.
  • Voir l’explication : L'original n'est pas supprimé

    L'original n'est pas supprimé : il devient <décorateur>.inner.

  • Voir l’explication : La priority la plus haute est la plus interne.

    La priority la plus haute est la plus interne. Elle est appliquée en premier, donc enveloppe directement le service décoré ; c'est la plus basse qui finit à l'extérieur.

  • Voir l’explication : Le decorator prend l'identifier de la cible

    Le decorator prend l'identifier de la cible ; rien ailleurs n'a besoin de changer — à condition que les consommateurs typent l'interface.

  • Voir l’explication : ignore retire le decorator

    ignore retire le decorator, il ne décore pas « à vide ».

  • Voir l’explication : Un consommateur typé par la class décorée casse.

    Un consommateur typé par la class décorée casse. Il reçoit le decorator, qui n'est pas de cette class : TypeError. Seul le typage par interface rend la décoration invisible.

  • Voir l’explication : À priority égale, le premier déclaré est le plus interne

    À priority égale, le premier déclaré est le plus interne, pas le dernier.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. La déclaration départage les priorities égales.
  2. Le premier se retrouve plus près de l'original.

Si tu dois retenir seulement 6 choses :

  • Le decorator prend l'identifier de la cible ; les consommateurs ne changent pas.
  • Même interface ; un consommateur typé par la class décorée casse.
  • L'original devient .inner ; autowiring, #[AutowireDecorated] ou '@.inner'.
  • Priority haute = au plus près de la cible ; la plus basse, à l'extérieur.
  • Priority égale : le premier déclaré est le plus interne.
  • Cible absente : exception (défaut), ignore (retiré), null.

Moyen mnémotechnique : « Haute priority, au cœur ; basse priority, à la porte ».
