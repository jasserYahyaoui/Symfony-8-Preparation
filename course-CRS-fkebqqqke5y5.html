Objectif

Envelopper un service existant sans le remplacer ni toucher à ses consommateurs, atteindre l'original par .inner, empiler plusieurs decorators dans le bon ordre et choisir le comportement quand la cible manque. Quand décorer plutôt qu'employer un compiler pass relève de Framework overloading.

L'essentiel

À comprendre

À retenir en priorité
  1. La décoration conserve l'original.
  2. Le consommateur reçoit le decorator.

Un decorator prend la place d'un service sous son identifier : ses consommateurs le reçoivent sans changer une ligne. L'original n'est pas perdu : il devient .inner. Empilés, les decorators s'appliquent de la plus haute priority à la plus basse — la plus basse finit à l'extérieur.

Le schéma

À retenir en priorité
  1. La priority haute se place au cœur.
  2. La plus basse est appelée en premier depuis l'extérieur.

Pointillés orange : résolution de l'identifiant ; bleu : appels ; vert : résultat. Les libellés MailerInterface et LoggerInterface sont des types, pas des objets interfaces. Le chemin suppose que le log et l'envoi réussissent : une exception du logger empêcherait ici l'appel suivant.

Le fil rouge : un `LoggingMailer`

À retenir en priorité
  1. Le contrat commun rend la substitution possible.
  2. Le type concret peut provoquer une TypeError.
#[AsDecorator(decorates: Mailer::class)]
class LoggingMailer implements MailerInterface
{
    public function __construct(
        private MailerInterface $inner,     // l'original, câblé sur .inner
        private LoggerInterface $logger,
    ) {
    }

    public function send(Message $message): void
    {
        $this->logger->info('sending');
        $this->inner->send($message);
    }
}

Le mécanisme : prendre la place, garder l'identifier

À comprendre

À retenir en priorité
  1. L'identifier de la cible reste utilisable.
  2. La substitution est centralisée dans le container.

C'est quoi ?

Décorer consiste à interposer un objet qui ajoute un comportement puis délègue à l'objet d'origine. Le consommateur continue de demander le même service ; le container lui fournit le décorateur sous l'identifiant attendu.

À quoi ça sert ?

On peut ajouter journalisation, mesure ou contrôle sans modifier tous les consommateurs ni réécrire le service initial. Contrairement à un remplacement complet, la décoration conserve un chemin vers l'original. Elle convient si le décorateur respecte le contrat utilisé par les consommateurs.

Où dans Symfony ?

decorates désigne la cible. Le container réorganise les identifiants et fournit l'original au décorateur via .inner. L'interface commune évite qu'un consommateur exige une classe concrète que le décorateur n'est pas.

Comment, étape par étape ?

  1. Le consommateur demande le contrat habituel.
  2. La définition de décoration remplace la résolution de la cible par le décorateur.
  3. Le décorateur effectue son traitement supplémentaire.
  4. Il appelle l'original lorsqu'une délégation est nécessaire, puis retourne un résultat compatible.

Exemple concret PHP

Ce PHP autonome montre le contrat et la délégation ; le container peut réaliser le même assemblage.

<?php
interface Formatter { public function format(string $value): string; }
final class PlainFormatter implements Formatter
{
    public function format(string $value): string { return trim($value); }
}
final class BracketFormatter implements Formatter
{
    public function __construct(private Formatter $inner) {}
    public function format(string $value): string
    {
        return '['.$this->inner->format($value).']';
    }
}
$formatter = new BracketFormatter(new PlainFormatter());
echo $formatter->format(' prêt '), "\n";

La sortie est [prêt] : l'original retire les espaces, le décorateur ajoute les crochets. Contre-exemple : imposer PlainFormatter comme type du consommateur puis lui injecter BracketFormatter ; les classes sont différentes. Correction : demander Formatter. Le décorateur doit aussi préserver les attentes du contrat, pas seulement la signature : changer arbitrairement la signification d'un résultat peut casser les consommateurs.

Passage canonique conservé
services:
    App\Mailer\LoggingMailer:
        decorates: App\Mailer\Mailer
        arguments: ['@.inner']
  • #[AsDecorator] : decorates, priority (0), onInvalid — en YAML decorates, decoration_priority, decoration_on_invalid.
  • Le decorator implémente la même interface que la cible :
Le consommateur est typé par… Ce qu'il reçoit
l'interface MailerInterface Logging(Mailer)
la class Mailer TypeError : « must be of type App\Mailer, App\LoggingMailer given »

Remplacer fait disparaître l'original ; décorer le garde, en délégation.

`.inner` : l'original n'est pas perdu

À comprendre

À retenir en priorité
  1. L'original est disponible en inner.
  2. Une injection explicite clarifie la délégation.

C'est quoi ?

.inner désigne l'original conservé pour une décoration. L'identifiant interne généré est fondé sur l'identifiant du décorateur, suivi de .inner, et non sur celui de la cible. La référence abrégée '@.inner' dans la définition du décorateur évite de dépendre de ce nom généré.

À quoi ça sert ?

Le décorateur doit appeler l'original, pas se redemander lui-même sous l'identifiant qu'il vient de remplacer. Une mauvaise référence crée une dépendance circulaire ou une récursion au lieu d'une délégation.

Où dans Symfony ?

Le lien peut être configuré avec '@.inner', #[AutowireDecorated] ou le câblage automatique adapté. decoration_inner_name permet de choisir explicitement le nom interne. La visibilité publique ou privée de l'accès externe ne change pas la nécessité d'un contrat PHP compatible.

Comment, étape par étape ?

  1. Déclarer le service original.
  2. Déclarer la cible de décoration.
  3. Injecter l'original dans l'argument de délégation.
  4. Réserver les autres dépendances du décorateur à leurs propres arguments.

Exemple concret YAML

PlainFormatter et BracketFormatter implémentent Formatter ; le second attend Formatter $inner.

services:
    App\PlainFormatter: ~
    App\Formatter: '@App\PlainFormatter'
    App\BracketFormatter:
        decorates: App\PlainFormatter
        arguments:
            $inner: '@.inner'

Une demande de App\Formatter atteint le décorateur ; son $inner reste le formatter original. Contre-exemple : remplacer $inner: '@.inner' par $inner: '@App\PlainFormatter', l'identifiant externe désormais décoré. Correction : utiliser .inner, qui désigne explicitement l'original. Si la cible peut être absente, choisir consciemment le comportement : erreur par défaut, retrait du décorateur avec ignore, ou original null avec un constructeur réellement capable de le traiter.

Passage canonique conservé

Le service décoré est renommé <id du decorator>.inner. Le decorator le reçoit :

  • en autowiring, par un argument typé comme la cible — automatiquement ;
  • par #[AutowireDecorated] sur l'argument ;
  • par '@.inner' en configuration.

decoration_inner_name change ce nom.

Empiler des decorators : l'ordre contre-intuitif

À comprendre

À retenir en priorité
  1. L'ordre de construction inverse l'ordre d'entrée.
  2. Ne pas confondre priority et premier appel.

C'est quoi ?

Plusieurs décorateurs forment une composition imbriquée. La priorité de décoration règle l'ordre d'assemblage : une valeur plus haute est appliquée plus tôt, donc plus près du service original. Ce n'est pas directement l'ordre des appels observés depuis le consommateur.

À quoi ça sert ?

L'ordre change le comportement : une mesure placée à l'intérieur d'un cache ne mesure pas un résultat déjà servi par le cache ; placée à l'extérieur, elle peut mesurer tout l'accès. Il faut donc raisonner sur la composition finale, pas seulement trier les nombres.

Où dans Symfony ?

decoration_priority en YAML et priority dans #[AsDecorator] règlent cet ordre. Il ne faut pas transposer la règle des listeners d'événements : leurs priorités élevées sont appelées plus tôt, alors que la décoration assemble des objets avant l'appel métier.

Comment, étape par étape ?

  1. Partir de la cible originale.
  2. Appliquer d'abord le décorateur de priorité la plus haute.
  3. Envelopper le résultat avec la priorité suivante.
  4. Lire les appels métier depuis l'extérieur vers l'intérieur ; les traitements après délégation reviennent dans l'ordre inverse.

Exemple concret YAML

Les trois classes sont supposées déclarées et acceptent leur service intérieur en premier argument.

services:
    App\Repository: ~
    App\MetricsRepository:
        decorates: App\Repository
        decoration_priority: 10
        arguments: ['@.inner']
    App\CacheRepository:
        decorates: App\Repository
        decoration_priority: 5
        arguments: ['@.inner']
    App\LogRepository:
        decorates: App\Repository
        decoration_priority: 0
        arguments: ['@.inner']

La composition attendue est Log(Cache(Metrics(Repository))). Le consommateur entre donc par Log. Contre-exemple : annoncer que Metrics s'exécute d'abord parce que 10 est le nombre le plus haut. Correction : distinguer application à la compilation et appel à l'exécution. Pour un ordre important, préférer des priorités distinctes plutôt que dépendre d'un ordre de déclaration à égalité.

Passage canonique conservé

Une priority plus haute est appliquée plus tôt, donc au plus près de la cible. Trois decorators de Repo — Metrics (10), Cache (5), Log (0) — donnent Log(Cache(Metrics(Repo))) : le consommateur appelle Log d'abord.

À priority égale, le premier déclaré est le plus interne.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le type concret reste vérifié par PHP.
  2. Typer le contrat commun évite cette incompatibilité.
  • Voir l’explication : L'original n'est pas supprimé

    L'original n'est pas supprimé : il devient <décorateur>.inner.

  • Voir l’explication : La priority la plus haute est la plus interne.

    La priority la plus haute est la plus interne. Elle est appliquée en premier, donc enveloppe directement le service décoré ; c'est la plus basse qui finit à l'extérieur.

  • Voir l’explication : Le décorateur reprend l'identifiant de la cible

    Le décorateur reprend l'identifiant de la cible ; les consommateurs gardent leur référence, à condition que le type reçu respecte leur contrat.

  • Voir l’explication : ignore retire le decorator

    ignore retire le decorator, il ne décore pas « à vide ».

  • Voir l’explication : Le décorateur doit respecter le type demandé.

    Le décorateur doit respecter le type demandé. Dans cet exemple, LoggingMailer implémente l'interface mais n'étend pas Mailer : un consommateur typé Mailer reçoit donc un objet incompatible. L'interface est le choix recommandé ; hériter de la classe cible serait une autre possibilité technique si cette classe autorise l'héritage.

  • Voir l’explication : À priority égale, le premier déclaré est le plus interne

    À priority égale, le premier déclaré est le plus interne, pas le dernier.

Fiche express

À mémoriser

À retenir en priorité
  1. La déclaration départage les priorities égales.
  2. Le premier se retrouve plus près de l'original.

Si tu dois retenir seulement 6 choses :

  • Le decorator prend l'identifier de la cible ; les consommateurs ne changent pas.
  • Type compatible ; dans cet exemple, LoggingMailer n'étend pas Mailer, donc les consommateurs doivent demander leur interface commune.
  • L'original devient .inner ; autowiring, #[AutowireDecorated] ou '@.inner'.
  • Priority haute = au plus près de la cible ; la plus basse, à l'extérieur.
  • Priority égale : le premier déclaré est le plus interne.
  • Cible absente : exception (défaut), ignore (retiré), null.

Moyen mnémotechnique : « Haute priority, au cœur ; basse priority, à la porte ».
