Objectif

Le visiteur de /blog/42 choisit de s'inscrire à la lettre du blog : la branche /inscription doit maintenant relier SignupData aux champs saisis. Le routage et les arguments ont déjà amené la Request au contrôleur ; Form répond à un autre problème, celui des représentations des données.

Comprendre ce que le component Form fait réellement : convertir un object applicatif en fields HTML, et le path inverse. C'est ce modèle qui explique tout le reste du module.

L'essentiel

À comprendre

À retenir en priorité
  1. getData() expose le modèle.
  2. getNormData() et getViewData() exposent les deux autres couches.

Une saisie HTML et une donnée métier n'ont pas nécessairement le même format : le champ affiche "42" tandis que l'application utilise l'entier 42. Le component Form convertit dans les deux sens à travers trois couches : model (le format de l'application), normalized (un format pivot), view (la représentation adaptée au champ). La vue n'est pas le HTML : ce sont les données utilisées pour préparer son rendu. Selon le type, elle peut être une chaîne, un tableau, un objet ou une valeur vide. Form est utilisable sans FrameworkBundle ; ses intégrations de rendu et de validation se configurent.

Le schéma

Vert = métier, ambre = pivot, bleu = présentation. Les flèches indiquent des conversions, pas des classes qui s'appellent entre elles. Le deuxième dessin simplifie un champ simple, activé, sans inherit_data et sans erreur : un formulaire composé soumet d'abord ses enfants et utilise un data mapper. Une conversion impossible rend le formulaire non synchronisé ; ne pas confondre « soumis » avec « valide ». POST_SUBMIT peut aussi être émis après un échec de transformation.

L'exemple : l'échéance d'une tâche

Exemple concret

L'échéance de tâche conserve un exemple simple de date, transposable à une date utile au service d'inscription. La factory est supposée disponible, et DateType importé. Observer les trois getters montre la conversion, sans encore rendre du HTML ni soumettre une Request.

$form = $formFactory->create(DateType::class, new \DateTime('2026-10-18'), [
    'widget' => 'choice',
]);
$form->getData();      // DateTime(2026-10-18)                              — model
$form->getNormData();  // DateTime(2026-10-18)                              — normalized
$form->getViewData();  // ['year' => '2026', 'month' => '10', 'day' => '18'] — view

Le problème résolu

À retenir en priorité
  1. Le component gère construction et submission.
  2. FrameworkBundle fournit l'intégration, pas le contrat fondamental.

Un champ ne peut pas afficher directement tous les formats métier : une date PHP et les valeurs des sélecteurs année/mois/jour diffèrent. Form organise leur correspondance, puis conserve les erreurs si le chemin inverse échoue. Ni cette conversion ni la création d'un FormView ne sauvegarde l'inscription ; les effets métier restent dans le traitement applicatif.

Le component construit les fields à partir d'un object, et reconstruit l'object à partir de ce que le navigateur renvoie. Forms::createFormFactory(), sans kernel ni FrameworkBundle, suffit à créer et soumettre un form.

🌍 In Real Life

La situation : le bureau d'inscription tient un agenda, tandis que le visiteur remplit trois cases jour, mois et année. Il faut transcrire dans les deux sens sans confondre l'écriture sur la fiche et l'information utilisée par le bureau.

L’équivalent dans Symfony : Form organise les correspondances entre donnée applicative et représentation des champs. Une date PHP peut devenir plusieurs valeurs de saisie ; la soumission tente de reconstruire la date.

Retour à la réalité technique : le composant peut fonctionner sans kernel. Les types et options configurent la structure et les transformations ; il ne devine pas universellement tous les champs d'un objet. Rendu, validation intégrée et persistance sont des opérations distinctes.

⚠️ À ne pas confondre : transformation des données et acceptation métier de ces données.

Les trois couches de données

Pour comprendre une date affichée incorrectement, demande d'abord quelle couche tu observes. Le modèle appartient à l'application, le pivot aux transformations du type et la donnée de vue à la présentation du champ. FormView contient ensuite les variables destinées au renderer ; ce n'est pas une quatrième version du modèle à persister.

Couche Contenu Method
Model le format de l'application ; ce qu'on passe à createForm() getData()
Normalized le pivot, identique au modèle pour la plupart des types getNormData()
View représentation adaptée au type ; chaîne pour IntegerType, tableau pour une date composée getViewData()

Les model transformers relient modèle et normalisée ; les view transformers, normalisée et vue. Un IntegerType : model 42, normalized 42, view "42".

🌍 In Real Life

La situation : un traducteur reçoit le dossier du bureau, passe par une fiche de travail commune, puis prépare les valeurs destinées au formulaire imprimé. Cette dernière fiche n'est pas encore la page mise en forme.

L’équivalent dans Symfony : modèle → pivot normalisé → donnée de vue correspondent à getData(), getNormData() et getViewData(). Les model transformers relient les deux premières couches ; les view transformers relient les deux dernières.

Retour à la réalité technique : deux couches peuvent contenir la même valeur sans perdre leurs rôles distincts. La donnée de vue dépend du type ; createView() prépare ensuite un FormView, dont les variables servent au renderer. Aucun de ces getters ne renvoie nécessairement du HTML.

🧠 Comment le mémoriser : « Dossier, fiche pivot, valeurs à présenter. » Image mentale : trois plateaux avant l'imprimante. Question-réflexe : quel getter correspond à la couche que je cherche ?

⚠️ À ne pas confondre : view data, objet FormView et HTML rendu.

Repère — Le DateType, et une erreur de la documentation :

Question: What is DateType's normalized data representation?

Answer: For a nonempty successfully transformed date, a DateTime value regardless of the configured model input format; an empty date can have null normalized data.

Pour une date non vide correctement transformée, DateType utilise un pivot DateTime ; une date vide peut avoir null comme donnée normalisée. input change le modèle, pas la nature de ce pivot.

Le `DateType`, et une erreur de la documentation

À retenir en priorité
  1. Pour une date non vide correctement transformée, DateType utilise un pivot DateTime ; une date vide peut avoir null comme donnée normalisée.
  2. input change le modèle, pas la nature de ce pivot.

Avec une date non vide, widget: 'choice' doit préparer trois valeurs affichables. DateTimeToArrayTransformer reçoit le pivot DateTime, puis produit le tableau de vue. Choisir input: 'array' change ce que l'application fournit et récupère, mais pas ce pivot : le tableau d'entiers du modèle ne doit pas être confondu avec le tableau de chaînes de la vue.

La documentation 8.0 donne pour norm data un array d'ints. Le code dit autre chose : le view transformer, DateTimeToArrayTransformer, part d'un DateTime.

Option input Model data Normalized data
datetime (défaut) DateTime DateTime
array ['year' => 2026, …] DateTime
string '2026-10-18' DateTime
datetime_immutable DateTimeImmutable DateTime

Pour une date non vide correctement transformée, la norm data d'un DateType est un DateTime : le format pivot vers lequel chaque format d'entrée est ramené. L'array d'ints est la donnée modèle quand input vaut array. Avec widget: 'choice', la vue est un tableau de chaînes ; avec single_text, une chaîne. Une date vide peut avoir null comme donnée normalisée : « toujours DateTime » serait trop absolu.

Pour le 18 octobre 2026, observer ['year' => '2026', 'month' => '10', 'day' => '18'] signifie donc regarder la vue composée, pas le HTML final. La soumission doit parcourir ces conversions dans l'autre sens ; une date impossible signale une erreur de transformation, tandis qu'une date convertible mais interdite demande une règle de validation.

🌍 In Real Life

La situation : le bureau reçoit la même date sous forme de phrase, de tableau de cases ou de fiche d'agenda. Il la ramène à sa fiche de travail avant de préparer les trois sélecteurs du formulaire.

L’équivalent dans Symfony : l'option input de DateType choisit le format modèle ; pour une date non vide correctement transformée, le pivot est un DateTime. Avec widget: 'choice', le view transformer produit un tableau de chaînes pour année, mois et jour.

Retour à la réalité technique : input: 'array' donne un tableau d'entiers côté modèle, pas le pivot. datetime_immutable ne rend pas ce pivot immutable. Une date vide peut produire null ; une transformation échouée exige d'inspecter l'état de synchronisation.

🧠 Comment le mémoriser : « L'entrée varie, la date pivot reste le repère. » Image mentale : plusieurs formats convergent vers un calendrier, puis trois cases. Question-réflexe : suis-je en train de lire le modèle, le pivot ou le tableau de vue ?

⚠️ À ne pas confondre : option input du modèle et option widget de présentation.

Les deux sens

À retenir en priorité
  1. La submission remonte la chaîne des transformations.
  2. La mise en place des données utilise transform().

L'initialisation des données peut être différée dans Form : les transformers ne sont pas synonymes de la seule exécution de buildForm(). Lorsqu'une opération exige les données, l'initialisation les synchronise ; sur le chemin actif, la soumission initialise au besoin avant de convertir la saisie. Le rendu HTML et la validation intégrée restent d'autres opérations.

  • Au rendu : model → model transformers → norm → view transformers → view.
  • À la submission : view → view transformers à l'envers → norm → model transformers à l'envers → model, réécrite dans l'object. Un DateType soumis avec ['year' => '2026', 'month' => '10', 'day' => '18'] rend un DateTime(2026-10-18).

Les mêmes transformers servent dans les deux sens ; à la submission, c'est leur method inverse qui est appelée.

🌍 In Real Life

La situation : pour préparer une fiche, l'agent traduit l'agenda en cases. Au retour, il relit les cases pour reconstruire une date ; une combinaison impossible l'empêche de terminer cette transcription.

L’équivalent dans Symfony : l'initialisation utilise transform() vers la vue ; la soumission utilise les reverseTransform() de vue puis de modèle. Dans un formulaire composé, le traitement des enfants et le data mapper participent aussi au passage vers les données du parent.

Retour à la réalité technique : l'initialisation peut être différée ; elle n'est pas synonyme de buildForm(). Une conversion impossible rend le Form non synchronisé. Une conversion réussie ne valide pas les contraintes métier et ne persiste rien ; POST_SUBMIT n'est pas une preuve de succès.

🧠 Comment le mémoriser : « Préparer les cases, puis reconstruire la date. » Image mentale : deux flèches opposées autour du calendrier. Question-réflexe : quel sens de transformation et quelle étape ont échoué ?

⚠️ À ne pas confondre : soumis, synchronisé et valide ; transformer une valeur et mapper les champs d'un objet.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Trois couches de données, pas deux.

    Trois couches de données, pas deux. Modèle, normalisée, vue : la couche intermédiaire est identique au modèle pour la plupart des types, ce qui la rend facile à oublier.

  • Voir l’explication : Pour une date non vide correctement transformée, la norm data d'un DateType est un DateTime

    Pour une date non vide correctement transformée, la norm data d'un DateType est un DateTime, pas l'array d'ints de l'exemple documenté. Une date vide peut avoir null comme donnée normalisée.

  • Voir l’explication : Donnée de vue ne signifie pas toujours chaîne.

    Donnée de vue ne signifie pas toujours chaîne. Un champ composé utilise notamment des tableaux ; les fichiers suivent un traitement spécifique.

  • Voir l’explication : Le component est autonome.

    Le component est autonome. Ce n'est pas une fonctionnalité de FrameworkBundle.

  • Voir l’explication : Un DateTimeImmutable en model devient un DateTime en norm data

    Un DateTimeImmutable en model devient un DateTime en norm data : le pivot du DateType est mutable, quel que soit le format de l'application.

Application

À retenir en priorité
  1. getData() expose le modèle.
  2. getNormData() et getViewData() exposent les deux autres couches.
  3. Pour une date non vide correctement transformée, DateType utilise un pivot DateTime ; une date vide peut avoir null comme donnée normalisée.
  4. input change le modèle, pas la nature de ce pivot.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Trois couches : model, normalized, view.
  • getData(), getNormData(), getViewData().
  • Model transformers : modèle ↔ norm ; view transformers : norm ↔ vue.
  • La vue dépend du type ; ce n'est pas du HTML.
  • DateType non vide et synchronisé : pivot DateTime, quel que soit input.
  • Le component est autonome.

Repère : « Métier, pivot, représentation du champ » — model, normalized, view. La vue n'est pas toujours du texte.
