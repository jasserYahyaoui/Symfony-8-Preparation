Objectif

Comprendre ce que le component Form fait réellement : convertir un object applicatif en fields HTML, et le path inverse. C'est ce modèle qui explique tout le reste du module.

L'essentiel

À comprendre

À retenir en priorité
  1. getData() expose le modèle.
  2. getNormData() et getViewData() exposent les deux autres couches.

Le navigateur transmet des données de form, notamment des strings, des arrays et des uploads ; l'application manipule ses propres objects. Le component Form convertit dans les deux sens à travers trois couches : model (le format de l'application), normalized (un format pivot), view (la représentation attendue par les fields). Il est autonome : utilisable sans FrameworkBundle.

Le schéma

L'exemple : l'échéance d'une tâche

Exemple concret

$form = $formFactory->create(DateType::class, new \DateTime('2026-10-18'), [
    'widget' => 'choice',
]);
$form->getData();      // DateTime(2026-10-18)                              — model
$form->getNormData();  // DateTime(2026-10-18)                              — normalized
$form->getViewData();  // ['year' => '2026', 'month' => '10', 'day' => '18'] — view

Le problème résolu

À comprendre

À retenir en priorité
  1. Le component gère construction et submission.
  2. FrameworkBundle fournit l'intégration, pas le contrat fondamental.

C'est quoi ?

Le component Form décrit des champs, leur organisation et la conversion des données échangées avec une application. Un Form n'est pas le HTML final : c'est un objet qui peut recevoir des données et suivre un état de soumission. Une FormView est une représentation destinée au rendu.

À quoi ça sert ?

Le même contrat relie les données initiales, la saisie et le résultat exploitable. Cela évite de disperser le nom des champs, les conversions et leur organisation dans des lectures manuelles de paramètres HTTP.

Où dans Symfony ?

Le component peut être utilisé sans kernel ni FrameworkBundle. Forms crée une factory, fabrique d'objets Form. FrameworkBundle ajoute le câblage et les extensions disponibles dans l'application. Un component autonome n'active pas magiquement Twig, Validator ou CSRF : ces capacités nécessitent leur intégration.

Comment, étape par étape ?

  1. Créer une factory puis un builder, objet de construction du formulaire.
  2. Déclarer les enfants avec leurs types et options.
  3. Obtenir le Form, puis lui soumettre les données au niveau attendu.
  4. Lire son résultat ; effectuer la validation et la persistance selon les extensions et le contrat de l'application.

Exemple concret PHP

Avec le component Form et ses dépendances chargés, sans intégration HTTP ni protection CSRF :

<?php
use Symfony\Component\Form\Extension\Core\Type\TextType;
use Symfony\Component\Form\Forms;

$form = Forms::createFormFactory()->createBuilder()
    ->add('title', TextType::class)
    ->getForm();
$form->submit(['title' => 'Guide']);
var_dump($form->isSubmitted(), $form->getData());

On attend true et un tableau contenant title égal à Guide. Aucun HTML ni stockage durable n'a été produit. Contre-exemple : croire que submit enregistre le résultat en base ou qu'un Form standalone possède toutes les protections de l'application. Correction : distinguer traitement des données, extensions de validation/sécurité et opération de sauvegarde explicite.

Passage canonique conservé

Le problème résolu

Le component construit les fields à partir d'un object, et reconstruit l'object à partir de ce que le navigateur renvoie. Forms::createFormFactory(), sans kernel ni FrameworkBundle, suffit à créer et soumettre un form.

Les trois couches de données

À comprendre

C'est quoi ?

Un formulaire n'est pas seulement du HTML. Le component Form organise la conversion entre la donnée de l'application et la donnée saisie. Il distingue trois représentations d'une même information :

  • Model data, donnée du modèle : le type utilisé par l'application, par exemple l'entier 42.
  • Normalized data, donnée normalisée : représentation intermédiaire utilisée par les transformations du type.
  • View data, donnée de présentation : représentation destinée au champ, par exemple la chaîne '42'.

La vue FormView, utilisée par Twig, est encore autre chose : elle contient les variables et enfants nécessaires au rendu. getViewData() ne retourne pas une FormView.

À quoi ça sert ?

Le navigateur envoie généralement du texte, alors que le métier utilise des nombres, dates ou objets. Séparer ces couches permet de changer le format de saisie sans changer le modèle. Ce n'est pas une validation métier : convertir '42' en 42 ne démontre pas que cette quantité est autorisée.

Où dans Symfony ?

getData() lit le modèle, getNormData() le pivot et getViewData() la représentation de présentation. Les model transformers, objets de conversion modèle/pivot, relient les deux premières couches. Les view transformers relient pivot et présentation. Leur présence et les types exacts dépendent du type de champ et de ses options ; il ne faut pas généraliser l'exemple IntegerType à DateType.

Comment, étape par étape ?

  1. Fournir une donnée modèle au formulaire : les transformations calculent ses autres représentations.
  2. Créer une FormView pour le rendu. Cette opération prépare la vue ; elle n'est pas le déclencheur initial des conversions.
  3. Soumettre les données de présentation avec submit() ou le gestionnaire HTTP configuré.
  4. Effectuer les transformations inverses vers le pivot puis le modèle ; lire getData() seulement en tenant compte de la soumission et des erreurs.

Exemple concret PHP

Dans un projet avec Form 8.0 et son autoload, cet exemple ne démarre pas de kernel et ne rend pas de HTML.

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Form\Extension\Core\Type\IntegerType;
use Symfony\Component\Form\Forms;

$form = Forms::createFormFactory()->create(IntegerType::class, 42);
var_dump($form->getData(), $form->getNormData(), $form->getViewData());
$form->submit('7');
var_dump($form->isSynchronized(), $form->getData());

On attend d'abord deux entiers 42, puis une chaîne '42', et après soumission true puis l'entier 7. Contre-exemple : stocker getViewData() en supposant qu'il s'agit toujours du type métier. Correction : employer getData() après traitement réussi. Une saisie non convertible désynchronise le champ ; ne pas assimiler cette situation à une conversion valide vers zéro.

Passage canonique conservé

Les trois couches de données

Couche Contenu Method
Model le format de l'application ; ce qu'on passe à createForm() getData()
Normalized le pivot, identique au modèle pour la plupart des types getNormData()
View le format des fields HTML : des strings getViewData()

Les model transformers relient modèle et normalisée ; les view transformers, normalisée et vue. Un IntegerType : model 42, normalized 42, view "42".

Repère — Le DateType, et une erreur de la documentation : A DateTime value, regardless of the configured model input format. DateType utilise un pivot DateTime. input change le modèle, pas la nature de ce pivot.

Le `DateType`, et une erreur de la documentation

À retenir en priorité
  1. DateType utilise un pivot DateTime.
  2. input change le modèle, pas la nature de ce pivot.

La documentation 8.0 donne pour norm data un array d'ints. Le code dit autre chose : le view transformer, DateTimeToArrayTransformer, part d'un DateTime.

Option input Model data Normalized data
datetime (défaut) DateTime DateTime
array ['year' => 2026, …] DateTime
string '2026-10-18' DateTime
datetime_immutable DateTimeImmutable DateTime

La norm data d'un DateType est toujours un DateTime : le format pivot vers lequel chaque format d'entrée est ramené. L'array d'ints est la donnée modèle quand input vaut array. La vue est un array de strings.

Les deux sens

À retenir en priorité
  1. La submission remonte la chaîne des transformations.
  2. La mise en place des données utilise transform().
  • Au rendu : model → model transformers → norm → view transformers → view.
  • À la submission : view → view transformers à l'envers → norm → model transformers à l'envers → model, réécrite dans l'object. Un DateType soumis avec ['year' => '2026', 'month' => '10', 'day' => '18'] rend un DateTime(2026-10-18).

Les mêmes transformers servent dans les deux sens ; à la submission, c'est leur method inverse qui est appelée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Trois couches de données, pas deux.

    Trois couches de données, pas deux. Modèle, normalisée, vue : la couche intermédiaire est identique au modèle pour la plupart des types, ce qui la rend facile à oublier.

  • Voir l’explication : La norm data d'un DateType est un DateTime

    La norm data d'un DateType est un DateTime, pas l'array d'ints de l'exemple documenté.

  • Voir l’explication : La vue est faite de strings.

    La vue est faite de strings. Un navigateur n'envoie que du texte.

  • Voir l’explication : Le component est autonome.

    Le component est autonome. Ce n'est pas une fonctionnalité de FrameworkBundle.

  • Voir l’explication : Un DateTimeImmutable en model devient un DateTime en norm data

    Un DateTimeImmutable en model devient un DateTime en norm data : le pivot du DateType est mutable, quel que soit le format de l'application.

Application

À retenir en priorité
  1. getData() expose le modèle.
  2. getNormData() et getViewData() exposent les deux autres couches.
  3. DateType utilise un pivot DateTime.
  4. input change le modèle, pas la nature de ce pivot.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Trois couches : model, normalized, view.
  • getData(), getNormData(), getViewData().
  • Model transformers : modèle ↔ norm ; view transformers : norm ↔ vue.
  • La vue est faite de strings.
  • DateType : norm data toujours DateTime, quel que soit input.
  • Le component est autonome.

Moyen mnémotechnique : « Métier, Pivot, Texte » — model, normalized, view.
