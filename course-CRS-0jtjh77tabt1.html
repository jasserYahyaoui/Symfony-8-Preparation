Objectif

Écrire une abstract class correcte et savoir quand la préférer à une interface.

L'essentiel

À comprendre

À retenir en priorité
  1. L'interface décrit le contrat.
  2. L'abstract class peut partager constructor, état et comportement.

Une abstract class ne s'instancie pas ; elle fournit du comportement partagé — constructor, état, methods concrètes — et impose à ses filles des methods abstraites, jamais private. Depuis PHP 8.4, elle peut aussi exiger une property, par un hook sans corps. Face à une interface, la règle tient en une ligne : l'interface décrit un contrat, l'abstract class partage du code.

Le schéma

À retenir en priorité
  1. Une property abstraite exige un hook sans body.
  2. La fille peut élargir la visibilité, pas la restreindre.

Le pointillé exprime l'héritage, pas un appel. Les flèches pleines suivent l'exécution sur un seul objet concret. Le rectangle orange est la base abstraite ; les bleus portent le code exécuté ; les capsules vertes montrent l'entrée et le résultat. Une base abstraite n'est donc pas un objet intermédiaire.

L'exemple

Exemple concret

abstract class LabelRenderer
{
    public function __construct(protected string $prefix) {}

    abstract protected function label(): string;

    public function render(): string
    {
        return $this->prefix.$this->label();
    }
}

final class GreetingRenderer extends LabelRenderer
{
    protected function label(): string { return 'Hello'; }
}

echo (new GreetingRenderer('> '))->render(); // > Hello

Le constructeur partagé prépare le préfixe ; label() spécialise le comportement sans recopier render(). Il n'existe qu'une instance concrète : la méthode héritée appelle la méthode de cette instance. Cet exemple conserve le mécanisme d'héritage sans dépendre d'une couche de persistance.

Règles

À comprendre

À retenir en priorité
  1. Une abstract class ne s'instancie pas.
  2. Une fille concrète doit satisfaire les methods abstraites.

C'est quoi ?

Une abstract class est une class qui ne peut pas être instanciée directement. Elle peut fournir un constructor, de l'état et des methods concrètes, tout en laissant certaines methods sans corps avec abstract. Toute class qui conserve une method ou property abstraite doit elle-même être déclarée abstraite.

Une method abstraite de class peut être public ou protected, et éventuellement static, mais pas private : l'enfant doit pouvoir remplir l'obligation. L'enfant concret doit tout implémenter avec une signature compatible et une visibilité au moins aussi ouverte. Une method protected peut ainsi devenir public, pas l'inverse.

À quoi ça sert ?

Une recette de franchise décrit les étapes communes et laisse à chaque boutique le choix d'une garniture. La recette correspond à la class abstraite, l'étape déjà écrite à la method concrète, le choix manquant à la method abstraite, et la boutique à l'enfant concret. Limite : une class abstraite peut être entièrement implémentée et rester volontairement non instanciable ; elle n'est pas toujours un programme « incomplet ».

L'intérêt est de partager une procédure qui appelle une variation bien identifiée, plutôt que de recopier la procédure dans chaque class enfant.

Où dans Symfony ?

Symfony\Bundle\FrameworkBundle\Controller\AbstractController est une class de base qui fournit des helpers aux controllers. On peut l'étendre pour réutiliser ces helpers ; être controller ne l'exige pas. Le mécanisme abstract reste du PHP. Le modèle de rapport ci-dessous est local et n'utilise ni base de données ni pseudo-interface externe.

Comment, étape par étape ?

  1. Placer le comportement réellement partagé dans des methods concrètes.
  2. Déclarer les points à compléter sans corps, avec les types et la visibilité nécessaires.
  3. Dans l'enfant, fournir toutes les obligations ou le déclarer abstrait à son tour.
  4. Instancier uniquement la class concrète. Ne pas combiner abstract avec final sur la même class ou method : empêcher l'extension contredirait l'obligation de compléter.

Exemple concret PHP

La method render() est fournie une seule fois ; elle appelle le titre choisi par l'enfant. Celui-ci élargit légalement protected en public. La sortie est [Daily]. L'appel direct new Report() serait interdit, contrairement à new DailyReport().

<?php
abstract class Report
{
    abstract protected function title(): string;

    public function render(): string
    {
        return '['.$this->title().']';
    }
}

final class DailyReport extends Report
{
    public function title(): string
    {
        return 'Daily';
    }
}

echo new DailyReport()->render(), "\n";

Le cas abstract private admis dans un trait depuis PHP 8.0 est distinct de cette règle de class. Référence : class abstraction.

Passage canonique conservé
  • Une abstract class ne peut pas être instanciée : « Cannot instantiate abstract class ».
  • Une method abstraite n'a pas de corps et peut être public ou protected, jamais private dans une class ; un trait, lui, admet abstract private depuis PHP 8.0. Elle peut être static.
  • Une class qui contient au moins une method — ou une property — abstraite doit être déclarée abstract.
  • La class fille implémente toutes les methods abstraites, sauf à être elle-même abstraite, avec une visibilité égale ou plus permissive et une signature compatible : une method protected peut devenir public.

Repère — Les properties abstraites — depuis PHP 8.4 : Une property abstraite exige un hook sans body. La fille peut élargir la visibilité, pas la restreindre.

Les properties abstraites — depuis PHP 8.4

abstract class Shape
{
    abstract public string $label { get; }   // exigence : lisible en public
}

final class Circle extends Shape
{
    public string $label = 'cercle';         // une property ordinaire suffit
}

Une property ordinaire, readonly ou hookée satisfait { get; }. Les règles :

  • Pas de hook, pas d'abstract : PHP refuse avec « Only hooked properties may be declared abstract ».
  • Au moins un hook sans corps ; l'autre peut porter un body par défaut.
  • public ou protected, jamais private.
  • Elle compte comme une method abstraite : une fille concrète qui ne la fournit pas est refusée.
  • La fille peut élargir, pas restreindre : protected devient public, mais un get public ne devient pas protected. Un set exige une écriture publique si le contrat déclare public set, ce qu'une property readonly ne fournit pas.

Interface ou abstract class ?

À comprendre

C'est quoi ?

Une interface définit une promesse publique sans corps de method ni état d'instance. Une abstract class peut fournir du code, un constructor et des properties d'état, en plus de ses obligations abstraites. Une class peut implémenter plusieurs interfaces, mais n'étendre qu'une seule class, abstraite ou non.

Une interface peut déclarer une signature de constructor, mais cela réduit la liberté de construction des implémentations et reste généralement déconseillé. Pour les properties PHP 8.4, une interface déclare des accès publics sans corps ; une abstract class autorise aussi protected et peut fournir le corps de l'un des hooks tout en laissant l'autre abstrait.

À quoi ça sert ?

Un contrat de livraison promet un résultat ; un manuel d'atelier fournit une façon commune de travailler. Le contrat correspond à l'interface, le manuel à l'abstract class, chaque atelier à une class concrète. Limite : posséder un manuel n'oblige pas à exposer tout son fonctionnement au client ; les methods partagées peuvent rester protégées.

On choisit donc l'interface pour permettre des implémentations interchangeables. On ajoute une abstract class lorsqu'un groupe d'implémentations a réellement du code et de l'état à partager. Les deux peuvent se compléter ; ce n'est pas un choix exclusif.

Où dans Symfony ?

Un controller peut être une class PHP ordinaire ; étendre Symfony\Bundle\FrameworkBundle\Controller\AbstractController permet de réutiliser ses helpers. Cela illustre le partage de code, pas une obligation universelle. Dans l'application, une interface locale peut représenter un service sans forcer toutes ses implémentations à partager une class parente. Voir controller Symfony 8.0.

Comment, étape par étape ?

  1. Identifier ce que le client doit pouvoir appeler et le placer dans un contrat public.
  2. Chercher un comportement effectivement commun, pas seulement des noms de methods semblables.
  3. Si ce comportement justifie une base commune, l'écrire dans une abstract class qui implémente le contrat.
  4. Si la class a déjà une autre parente ou si les comportements varient indépendamment, préférer la composition ; ne pas tenter un second extends.

Exemple concret PHP

Formatter est la promesse utilisée par printMessage(). PrefixedFormatter fournit le stockage du préfixe et l'assemblage commun. UpperFormatter ne choisit que la transformation. La sortie est INFO: READY ; le client ne dépend pas de la class de base.

<?php
interface Formatter
{
    public function format(string $message): string;
}

abstract class PrefixedFormatter implements Formatter
{
    public function __construct(private string $prefix) {}

    abstract protected function transform(string $message): string;

    public function format(string $message): string
    {
        return $this->prefix.$this->transform($message);
    }
}

final class UpperFormatter extends PrefixedFormatter
{
    protected function transform(string $message): string
    {
        return strtoupper($message);
    }
}

function printMessage(Formatter $formatter): void
{
    echo $formatter->format('ready'), "\n";
}

printMessage(new UpperFormatter('INFO: '));

Une interface décrit ce qu'un object sait faire ; une abstract class fournit du comportement partagé. Un besoin de constructor ou d'état commun tranche pour l'abstract class.

Le manuel d'une franchise fournit une procédure commune mais laisse une étape locale à compléter. Une abstract class fournit ce comportement partagé ; seule une class concrète ayant rempli les obligations peut être instanciée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Dans une classe, abstract private est une erreur fatale.

    Dans une classe, abstract private est une erreur fatale. Ce n'est pas la règle des traits : PHP 8.0 autorise une méthode abstraite privée dans un trait.

  • Voir l’explication : Une seule class parente.

    Une seule class parente. Besoin de deux jeux de comportements partagés : c'est un trait ou une composition, pas un second extends.

  • Voir l’explication : abstract et final sont incompatibles

    abstract et final sont incompatibles : l'un exige une extension, l'autre l'interdit.

  • Voir l’explication : Une property abstraite sans hook est une erreur fatale.

    Une property abstraite sans hook est une erreur fatale. abstract public string $label; ne compile pas : il faut { get; }, { set; } ou les deux, dont au moins un sans corps.

Application

À retenir en priorité
  1. L'interface décrit le contrat.
  2. L'abstract class peut partager constructor, état et comportement.
  3. Une property abstraite exige un hook sans body.
  4. La fille peut élargir la visibilité, pas la restreindre.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Non instanciable ; une seule abstract class par extends.
  • Method abstraite : sans corps, public ou protected, jamais private.
  • Fille concrète : tout implémenter, visibilité égale ou plus large.
  • 8.4 : property abstraite = hook sans corps ; jamais private.
  • abstract + final : incompatibles.
  • Interface = contrat ; abstract class = comportement partagé.

Moyen mnémotechnique : « L'interface promet, l'abstract class aide ».
