Objectif

Comprendre comment Symfony fait évoluer son API sans casser les applications : dans quelle version une fonctionnalité peut être dépréciée, comment la deprecation est signalée, où elle est documentée, et quand le code déprécié disparaît.

L'essentiel

À comprendre

À retenir en priorité
  1. Déprécier en mineure prépare la migration.
  2. Supprimer en majeure rend la rupture explicite.

Déprécier, c'est garder l'ancienne API fonctionnelle en annonçant son remplacement. Une mineure prévient, la majeure suivante supprime ; entre les deux, l'application migre.

Le schéma

Le fil rouge : `Request::get()`, de 7.4 à 8.0

À retenir en priorité
  1. Request::get() illustre la dépréciation en 7.4 puis la suppression en 8.0.
  2. Lire explicitement query, request ou attributes selon l'origine des données.

Request::get() cherchait une valeur dans les attributes, la query string puis le body POST, sans dire d'où elle venait. Dépréciée en 7.4, supprimée en 8.0 ; le remplacement dit la provenance :

$id    = $request->attributes->get('id');    // placeholder de route : /article/{id}
$page  = $request->query->get('page');       // query string : ?page=2
$title = $request->request->get('title');    // body d'un form envoyé en POST

Règle 1 : déprécier en mineure, supprimer en majeure

À comprendre

C'est quoi ?

Déprécier signifie annoncer qu'une API ou un comportement doit être abandonné, tout en le conservant pendant une transition. Supprimer signifie qu'il n'est plus disponible. Une dépréciation n'est donc ni une suppression immédiate ni une garantie de conservation indéfinie.

À quoi ça sert ?

L'application peut migrer progressivement avant une majeure. Le remplacement devient disponible tandis que l'ancien usage signale son avenir limité ; les tests et outils de diagnostic permettent de repérer les chemins réellement concernés.

Où dans Symfony ?

La règle est d'introduire la dépréciation dans la prochaine mineure, puis de supprimer dans la prochaine majeure. Une dépréciation critique peut exceptionnellement être introduite dans une version maintenue antérieure. Une nouvelle classe ou méthode ne doit pas être introduite déjà dépréciée.

Comment, étape par étape ?

  1. Fournir l'alternative et documenter la migration.
  2. Conserver l'ancien comportement compatible pendant la mineure.
  3. Signaler les usages dépréciés.
  4. Corriger l'application avant la majeure qui retire l'ancien code.

Exemple concret text

Symfony 7.4 : Request::get() est dépréciée ; lire le sac précis reste possible
Symfony 8.0 : Request::get() est supprimée ; utiliser attributes, query ou request selon l'origine

Pour /article/12?page=2, l'identifiant de route et la page de query string n'ont pas la même origine. Contre-exemple : attendre la mise à jour 8.0 pour découvrir tous les appels à l'ancienne méthode. Correction : observer et corriger les dépréciations sur la dernière mineure précédente. L'absence de notice dans un parcours jamais exécuté ne prouve pas l'absence de code déprécié : compléter les tests par la lecture et les outils d'analyse disponibles.

Passage canonique conservé

Règle 1 : déprécier en mineure, supprimer en majeure

  • Deprecation : la prochaine mineure du component, bundle, bridge ou contrat ; exceptionnellement une version antérieure maintenue, si elle est critique.
  • Suppression : la prochaine majeure seulement, environ tous les deux ans.
  • 7.4 et 8.0 ont les mêmes nouveautés : 8.0 = 7.4 moins le code déprécié.
  • Une nouvelle class, interface, trait ou method ne naît jamais dépréciée.

Une deprecation est un panneau « cette sortie fermera, utilisez l'autre » : l'ancienne voie fonctionne pendant la migration. Ce panneau n'est pas la barrière de suppression, réservée à la majeure.

Règle 2 : deux signaux, deux publics

À comprendre

À retenir en priorité
  1. Le PHPDoc informe à la lecture.
  2. Le signal runtime révèle les usages effectivement exécutés.

C'est quoi ?

@deprecated est une annotation PHPDoc lisible dans le code et par les outils. trigger_deprecation() est un appel qui produit un signal à l'exécution. L'un décrit l'état de l'API ; l'autre permet de repérer qu'un chemin déprécié a réellement été emprunté.

À quoi ça sert ?

La documentation informe avant l'exécution ; le signal d'exécution peut révéler un usage caché dans une dépendance. Ils sont complémentaires : une annotation seule n'émet aucune notice et une notice n'observe pas le code jamais exécuté.

Où dans Symfony ?

L'annotation indique la version d'introduction de la dépréciation et, si possible, le remplacement. Si ce remplacement est dans un autre espace de noms, son nom complet évite l'ambiguïté. La fonction est fournie par symfony/deprecation-contracts, indépendamment du framework complet.

Comment, étape par étape ?

  1. Annoter la déclaration concernée.
  2. Placer le signal dans le chemin ancien conservé.
  3. Donner une alternative précise dans le message.
  4. Laisser le comportement compatible s'exécuter pendant la transition.

Exemple concret PHP

Exemple d'une bibliothèque fictive ; l'autoload de Deprecation Contracts doit être chargé.

<?php
/** @deprecated since acme/demo 1.2, use normalizedLabel() instead */
function legacyLabel(string $value): string
{
    trigger_deprecation('acme/demo', '1.2', 'Use normalizedLabel() instead of legacyLabel().');
    return normalizedLabel($value);
}
function normalizedLabel(string $value): string
{
    return trim($value);
}

L'ancien appel garde son résultat tout en signalant la migration. Contre-exemple : remplacer immédiatement le corps par une exception pour forcer le changement pendant une version censée rester compatible. Correction : conserver le comportement et signaler la dépréciation ; la suppression appartient à la version de rupture prévue. L'annotation et la fonction ne sont pas interchangeables.

Passage canonique conservé

Règle 2 : deux signaux, deux publics

@deprecated trigger_deprecation()
nature annotation PHPDoc appel de function
agit à la lecture du code à l'exécution, à chaque passage
ne voit pas un appel caché dans une dependency un code déprécié jamais exécuté

L'annotation porte la version (obligatoire), le remplacement si possible, et son FQCN s'il vit dans un autre namespace :

/**
 * @deprecated since Symfony 7.4, use properties `->attributes`, `query` or `request` directly instead
 */

La function vient d'un package de contrats minuscule, sans le framework :

composer require symfony/deprecation-contracts

`trigger_deprecation()` ligne par ligne

À comprendre

À retenir en priorité
  1. Le premier argument nomme le package Composer.
  2. Le deuxième date l'introduction de la deprecation.

C'est quoi ?

trigger_deprecation() est une fonction globale de symfony/deprecation-contracts. Elle reçoit le nom Composer du package, la version qui introduit la dépréciation, le message et éventuellement des valeurs de formatage.

À quoi ça sert ?

Un message uniforme permet d'identifier le propriétaire de l'ancienne API, le début de la transition et le remplacement attendu. La version n'est pas celle de la suppression : confondre les deux fausse la chronologie de migration.

Où dans Symfony ?

La version 3.6.0 consultée utilise @trigger_error(..., E_USER_DEPRECATED). Le signal est volontairement silencé pour l'affichage ordinaire, mais un gestionnaire d'erreurs approprié peut le collecter. Il n'interrompt pas lui-même le programme comme le ferait une exception ; la politique du gestionnaire ou des tests peut toutefois rendre les dépréciations bloquantes.

Comment, étape par étape ?

  1. Identifier le package responsable.
  2. Indiquer la version où l'ancien usage devient déprécié.
  3. Nommer le remplacement précisément.
  4. Placer l'appel dans la méthode pour signaler ses usages, ou au chargement du fichier pour une classe entièrement dépréciée, après les imports selon la convention de contribution.

Exemple concret PHP

Avec l'autoload du package de contrats chargé :

<?php
trigger_deprecation(
    'acme/demo',
    '1.2',
    'The "%s" option is deprecated; use "%s" instead.',
    'old_mode',
    'mode',
);

Le message identifie acme/demo 1.2, puis remplace les deux %s par les noms d'options. Contre-exemple : passer 2.0 parce que la suppression est prévue dans cette majeure, ou écrire le namespace PHP à la place du package. Correction : utiliser la version d'introduction 1.2 et le nom Composer. Une exécution silencieuse à l'écran ne prouve pas qu'aucune dépréciation n'a été émise.

Passage canonique conservé

trigger_deprecation() ligne par ligne

trigger_deprecation(
    'symfony/http-foundation',   // 1. le nom Composer du package, pas le namespace
    '7.4',                       // 2. la version d'INTRODUCTION, jamais celle de suppression
    'Request::get() is deprecated, use properties ->attributes, query or request directly instead.', // 3. le message
);                               // 4. puis, facultatifs, les ...$args insérés au format printf()
  • Elle appelle @trigger_error(…, E_USER_DEPRECATED), message Since symfony/http-foundation 7.4: … : silencée, l'exécution continue ; seul un error handler la recueille.
  • Pour une method : dans son body ; une notice à chaque appel.
  • Pour une class entière : au niveau du file, après les use. Placé avant, le ::class du remplacement est résolu dans le namespace courant et nomme une class qui n'existe pas. La notice part une fois, au chargement.

Repère — Le fil rouge : Request::get(), de 7.4 à 8.0 : Request::get(); use the appropriate explicit input bag instead. Request::get() illustre la dépréciation en 7.4 puis la suppression en 8.0. Lire explicitement query, request ou attributes selon l'origine des données.

Règle 3 : la trace écrite, trois files dans une pull request

À comprendre

À retenir en priorité
  1. La trace de migration accompagne la deprecation.
  2. La même pull request documente introduction et suppression prévue.

C'est quoi ?

La trace écrite d'une dépréciation relie l'annonce dans une mineure à sa conséquence dans la majeure suivante. Une pull request, proposition de modification, doit documenter ces deux moments et l'historique du component concerné.

À quoi ça sert ?

Les utilisateurs qui mettent à jour progressivement doivent comprendre l'avertissement ; ceux qui préparent la majeure doivent savoir quoi remplacer. Un simple commentaire dans le code ne fournit pas une vue de migration complète.

Où dans Symfony ?

La convention prévoit le CHANGELOG.md du component, le guide UPGRADE-<mineure>.md et le guide UPGRADE-<majeure suivante>.md. Les changelogs agrégés de la racine sont générés : ils ne remplacent pas la modification du changelog du component.

Comment, étape par étape ?

  1. Décrire la dépréciation sous la version mineure du changelog.
  2. Expliquer le remplacement dans le guide de cette mineure.
  3. Annoncer la suppression et la migration dans le guide de la majeure.
  4. Lors de la suppression effective, ajouter sa propre trace au changelog de la majeure.

Exemple concret text

CHANGELOG du component, 7.4 : ancien usage déprécié
UPGRADE-7.4.md             : comment remplacer l'ancien usage
UPGRADE-8.0.md             : ancien usage supprimé en 8.0
CHANGELOG du component, 8.0 : trace ajoutée lors de la suppression effective

Les trois premières lignes décrivent la documentation à préparer lors de la dépréciation ; la quatrième appartient à sa suppression. Contre-exemple : écrire seulement « deprecated » sans version ni alternative, ou ne documenter que la majeure. Correction : couvrir l'annonce, le chemin de migration et le retrait. Une entrée de changelog reste courte ; le guide de mise à jour porte l'explication nécessaire à l'utilisateur.

Passage canonique conservé

Règle 3 : la trace écrite, trois files dans une pull request

File Pour Request::get()
CHANGELOG.md du component section 7.4 : « Deprecate method Request::get(), … »
UPGRADE-<mineure>.md UPGRADE-7.4.md : la deprecation
UPGRADE-<majeure suivante>.md UPGRADE-8.0.md : « Remove Request::get(), … »

Les trois, obligatoires, dans la même pull request : Deprecate dans la mineure, Remove dans la majeure.

Repère — Le CHANGELOG.md a ses propres règles : The component changelog, not generated root CHANGELOG-* files. Les entrées nouvelles vont en haut de la section mineure. Le message est bref, impératif et sans point final.

Le `CHANGELOG.md` a ses propres règles

À retenir en priorité
  1. Les entrées nouvelles vont en haut de la section mineure.
  2. Le message est bref, impératif et sans point final.
  • titre CHANGELOG, une section par version mineure ;
  • aucune section de troisième niveau (pas de ### Deprecations) ;
  • un message court, à l'impératif, capitalisé, sans point final ;
  • les nouvelles entrées en haut ;
  • les CHANGELOG-* de la racine de symfony/symfony sont générés : on édite celui du component.

La suppression a sa propre trace

À retenir en priorité
  1. La deprecation et la suppression sont deux changements.
  2. La suppression ajoute sa propre trace.

La pull request qui supprime ajoute les conséquences au CHANGELOG.md du component : « Remove the Deprecated class, use Replacement instead ». HttpFoundation porte ainsi Deprecate sous 7.4 et Remove sous 8.0 : une fonctionnalité dépréciée puis supprimée laisse quatre entrées.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le deuxième argument de trigger_deprecation() est la version d'introduction, pas celle de suppression.

    Le deuxième argument de trigger_deprecation() est la version d'introduction, pas celle de suppression. '7.4' signifie « déprécié depuis 7.4 » ; la suppression en 8.0 n'est écrite nulle part dans l'appel.

  • Voir l’explication : Le premier argument est un nom de package Composer.

    Le premier argument est un nom de package Composer. 'symfony/http-foundation', pas 'HttpFoundation' ni un namespace.

  • Voir l’explication : trigger_deprecation() n'appartient pas au framework.

    trigger_deprecation() n'appartient pas au framework. Elle vient d'un package de contrats dédié, installé à part — précisément pour qu'une bibliothèque puisse l'appeler sans dépendre de Symfony.

  • Voir l’explication : @deprecated seul ne prévient personne à l'exécution.

    @deprecated seul ne prévient personne à l'exécution. C'est de la documentation : le signal qui atteint une application en marche est trigger_deprecation().

  • Voir l’explication : Rien ne naît déprécié.

    Rien ne naît déprécié. Une nouvelle class ne peut pas être introduite dépréciée, ni contenir des methods dépréciées ; une nouvelle method non plus.

  • Voir l’explication : Déprécier et supprimer ne se font pas dans la même version.

    Déprécier et supprimer ne se font pas dans la même version. Deprecation en mineure, suppression en majeure suivante — et la trace écrite va aux trois endroits (CHANGELOG.md, les deux UPGRADE-*.md) dans la même pull request.

  • Voir l’explication : La suppression écrit à son tour.

    La suppression écrit à son tour. Une quatrième entrée de CHANGELOG.md décrit les conséquences, dans la pull request qui supprime.

  • Voir l’explication : Les CHANGELOG-* de la racine ne se modifient pas à la main.

    Les CHANGELOG-* de la racine ne se modifient pas à la main. Ils sont générés à la préparation des versions. Celui qu'on édite est celui du component.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Mineure : je préviens. Majeure : je supprime. Exception : critique, sur une version antérieure maintenue.
  • Rien ne naît déprécié.
  • @deprecated pour lire (version, remplacement, FQCN) ; trigger_deprecation() pour l'exécution, silencée.
  • Arguments : package Composer, version d'introduction, message ; pour une class, après les use.
  • Trois files, une pull request ; la suppression en ajoute une quatrième.
  • CHANGELOG.md : pas de troisième niveau, I-M-P (impératif, majuscule, pas de point), en haut ; racine générée.

Moyen mnémotechnique : « Mineure, je préviens. Majeure, je supprime. »
