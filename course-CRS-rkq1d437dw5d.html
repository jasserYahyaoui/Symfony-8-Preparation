Objectif

Notre blog cible Symfony 8.0, mais un ancien controller utilisait Request::get() pour lire l'identifiant d'article. Ce code doit être migré : la méthode n'existe plus en 8.0. Pour comprendre pourquoi l'équipe pouvait anticiper cette rupture, nous revenons explicitement à la transition historique 7.4 → 8.0, sans présenter l'ancienne API comme disponible aujourd'hui.

Nous suivrons les deux côtés de cette transition : l'application qui repère et remplace un usage, puis l'auteur du composant qui l'annonce, conserve temporairement le comportement et documente son retrait.

L'essentiel

À comprendre

À retenir en priorité
  1. Déprécier en mineure prépare la migration.
  2. Supprimer en majeure rend la rupture explicite.

Une deprecation annonce qu'un usage doit être abandonné tout en conservant son fonctionnement pendant une transition. Elle n'est donc ni une suppression immédiate ni une garantie de disponibilité indéfinie.

Sur l'ancienne branche, le controller pouvait encore répondre à /blog/42 alors qu'un signal invitait l'équipe à remplacer sa lecture ambiguë. La règle normale est : une mineure prévient, la majeure suivante supprime. Le temps intermédiaire sert à choisir le bon remplacement, pas seulement à masquer les notices.

Deux observations se complètent : lire les annotations et guides avant l'exécution, puis collecter les signaux des chemins réellement exécutés. Un GET réussi ne prouve pas l'absence de deprecations, et une commande d'import jamais lancée ne peut pas révéler ses usages par un signal d'exécution.

Le schéma

Le diagramme suit une migration déjà réalisée dans l'histoire du framework. L'entrée n'est pas une nouvelle Request en 8.0, mais un appel hérité encore exécutable en 7.4. La décision appartient à l'équipe de maintenance :

Le chemin vert demande de choisir la provenance de la donnée avant le passage en 8.0. Pour la variante historique ?page=2, query lit la query string ; pour l'identifiant de blog_show, il faut les attributes renseignés par le Routing. Notre pagination principale /blog/page/{page} utiliserait elle aussi un attribute de route, pas cette query string de laboratoire.

Le chemin rouge aboutit à une Error parce qu'une méthode supprimée est appelée. Il ne s'agit plus d'une simple notice de migration. Bleu : ancien usage ; orange : travail de remplacement ; vert/rouge : conséquences. La collecte n'observe que les passages exécutés : il faut couvrir aussi l'inscription, les erreurs et l'import, puis compléter cette observation par la lecture et l'analyse du code.

Le fil rouge : `Request::get()`, de 7.4 à 8.0

À retenir en priorité
  1. Request::get() illustre la dépréciation en 7.4 puis la suppression en 8.0.
  2. Lire explicitement query, request ou attributes selon l'origine des données.

Dans l'ancienne version, Request::get() cherchait dans les attributes, puis la query string, puis les données POST parsées. Un même nom pouvait donc désigner plusieurs entrées. Le remplacement ne consiste pas à choisir un autre raccourci universel, mais à rendre l'intention visible.

Le code suivant suppose une variable $request de type HttpFoundation Request. Chaque ligne correspond à une provenance ; le commentaire /article/{id} conserve l'ancien chemin du laboratoire :

$id    = $request->attributes->get('id');    // placeholder de route : /article/{id}
$page  = $request->query->get('page');       // query string : ?page=2
$title = $request->request->get('title');    // body d'un form envoyé en POST

Après le matching de /blog/42, avec l'attribute id contenant la chaîne '42', la première lecture renvoie cette valeur. Si ce GET porte aussi ?page=2, la deuxième renvoie '2'. La troisième renvoie null sur ce GET sans données de form ; dans un scénario distinct de soumission de titre, elle lit le champ POST parsé.

Ces getters ne prouvent ni l'existence de l'article dans ArticleCatalog, ni la validité métier de la page ou du titre. Ils ne convertissent pas non plus automatiquement un body JSON en données de form. La migration conserve la bonne provenance ; la validation et la recherche restent les étapes suivantes.

🌍 In Real Life

La situation : un ancien guichet mélangeait plusieurs bacs ; sa fermeture annoncée impose désormais de choisir le bac qui correspond réellement au document.

L’équivalent dans Symfony : ancien accès → Request::get() historique ; bacs distincts → attributes, query, request.

Retour à la réalité technique : la migration choisit la provenance, pas un nouveau getter universel. Le routage place id dans les attributes ; un body JSON n'est pas automatiquement un form parsé. Déprécié en 7.4 ne signifie pas encore disponible en 8.0.

🧠 Comment le mémoriser : « Remplacer l'accès, conserver l'intention. » Image mentale : trois bacs identifiés. Question-réflexe : d'où cette valeur doit-elle venir ?

⚠️ À ne pas confondre : lecture, validation et recherche de l'article.

Règle 1 : déprécier en mineure, supprimer en majeure

L'auteur de Symfony introduit normalement la deprecation dans la prochaine mineure du composant, bundle, bridge ou contrat concerné. Une deprecation critique peut exceptionnellement rejoindre une version antérieure encore maintenue. Ce n'est pas une autorisation d'ajouter librement ces changements dans tous les correctifs.

La suppression appartient à la prochaine majeure, selon le rythme normal d'une majeure tous les deux ans. Ainsi, l'équipe du blog pouvait remplacer l'ancien getter en 7.4 avant sa disparition en 8.0. Arriver directement en 8.0 avec cet appel ne laisse plus de période d'avertissement.

Le repère « 8.0 = 7.4 moins le code déprécié » décrit le partage des nouveautés entre ces versions publiées ensemble et le retrait des anciens usages. Il ne signifie pas que leurs exigences de plateforme sont identiques : Symfony 8.0 exige notamment PHP 8.4 ou supérieur, notre enseignement restant limité aux APIs PHP 8.4.

Enfin, les conventions de contribution interdisent d'introduire une nouvelle class, interface ou trait déjà déprécié, ou contenant des méthodes dépréciées ; une nouvelle méthode ne naît pas dépréciée non plus. C'est une règle du projet, pas une impossibilité de syntaxe PHP.

Une deprecation est un panneau « cette sortie fermera, utilisez l'autre » : l'ancienne voie fonctionne pendant la migration. Ce panneau n'est pas la barrière de suppression, réservée à la majeure.

Règle 2 : deux signaux, deux publics

À retenir en priorité
  1. Le PHPDoc informe à la lecture.
  2. Le signal runtime révèle les usages effectivement exécutés.

Le développeur qui ouvre l'ancien controller doit comprendre le remplacement avant de lancer le site. Celui qui ne connaît pas encore l'appel caché dans une dépendance doit pouvoir le découvrir à l'exécution. Ces deux besoins expliquent les deux signaux :

@deprecated trigger_deprecation()
nature annotation PHPDoc appel de function
agit à la lecture du code à l'exécution, à chaque passage
limite n'émet aucune notice à elle seule ne signale pas un chemin jamais exécuté

L'annotation PHPDoc est un commentaire destiné aux lecteurs et outils d'analyse ; ces outils peuvent aussi inspecter des dépendances. Elle porte la version d'introduction (obligatoire) et, si possible, le remplacement. Si celui-ci vit dans un autre namespace, son FQCN, nom de class entièrement qualifié, lève l'ambiguïté. Voici l'indication historique concernant notre getter :

/**
 * @deprecated since Symfony 7.4, use properties `->attributes`, `query` or `request` directly instead
 */

Ce commentaire n'émet rien lorsqu'on le lit ou lorsqu'on appelle la méthode. Le signal d'exécution vient de la fonction globale trigger_deprecation(), fournie par symfony/deprecation-contracts, utilisable sans installer le framework complet. La commande suivante illustre sa déclaration comme dépendance avec Composer 2 ; pour le laboratoire PHP 8.4, on retient la branche Contracts 3.6 compatible, selon les contraintes du projet :

composer require symfony/deprecation-contracts

Effet attendu si la résolution réussit : Composer ajoute la dépendance et prépare son autoload. Cette commande sans contrainte de version explicite ne garantit pas à elle seule la branche 3.6 ; ce n'est pas une commande exécutée pour ce cours.

Voici une bibliothèque fictive acme/demo : le blog pourrait en utiliser le formatage dans son import. Le script est placé à la racine d'un projet disposant de l'autoload et du package de contrats :

<?php
require __DIR__.'/vendor/autoload.php';

/** @deprecated since acme/demo 1.2, use normalizedLabel() instead */
function legacyLabel(string $value): string
{
    trigger_deprecation('acme/demo', '1.2', 'Use normalizedLabel() instead of legacyLabel().');
    return normalizedLabel($value);
}
function normalizedLabel(string $value): string
{
    return trim($value);
}

$notices = [];
set_error_handler(static function (int $severity, string $message) use (&$notices): bool {
    if (E_USER_DEPRECATED !== $severity) {
        return false;
    }
    $notices[] = $message;
    return true;
});
try {
    echo legacyLabel(' Article 42 '), "\n";
} finally {
    restore_error_handler();
}
echo count($notices), "\n";

Résultat attendu : Article 42, puis 1. L'ancienne fonction garde son résultat et le handler de ce laboratoire collecte une notice ; l'appel direct à normalizedLabel() ne produirait pas cette notice. Le finally restaure le handler précédent. Ce collecteur minimal n'est pas une politique de journalisation de production et ne démontre pas que tous les autres chemins de l'application sont exempts de deprecations.

Repère — La suppression a sa propre trace :

Question: Does removing deprecated code require another changelog entry?

Answer: Yes. The removal change documents its consequences separately.

La deprecation et la suppression sont deux changements. La suppression ajoute sa propre trace.

`trigger_deprecation()` ligne par ligne

À retenir en priorité
  1. Le premier argument nomme le package Composer.
  2. Le deuxième date l'introduction de la deprecation.

Relisons maintenant le signal historique lui-même. Cet appel peut illustrer le message avec le package de contrats chargé ; il ne remet pas Request::get() à disposition en Symfony 8.0 :

trigger_deprecation(
    'symfony/http-foundation',   // 1. le nom Composer du package, pas le namespace
    '7.4',                       // 2. la version d'INTRODUCTION, jamais celle de suppression
    'Request::get() is deprecated, use properties ->attributes, query or request directly instead.', // 3. le message
);                               // 4. puis, facultatifs, les ...$args insérés au format printf()

Le premier argument désigne le propriétaire Composer de l'API. Le deuxième date l'introduction de la deprecation, pas la suppression, ni la version de PHP, ni nécessairement la version actuellement installée. Le message explique le remplacement ; des arguments supplémentaires peuvent remplir ses marqueurs de formatage.

Avec Contracts 3.6, la fonction appelle @trigger_error(..., E_USER_DEPRECATED). Le message commence ici par Since symfony/http-foundation 7.4:. L'operator @ supprime l'affichage ordinaire de la notice ; un handler approprié peut néanmoins la collecter, comme dans le laboratoire précédent. La fonction ne lève pas elle-même une exception pour forcer la migration. Un handler ou la politique des tests peut toutefois décider de transformer le signal en échec.

Pour observer le formatage, cet autre appel fictif utilise deux marqueurs :

trigger_deprecation(
    'acme/demo',
    '1.2',
    'The "%s" option is deprecated; use "%s" instead.',
    'old_mode',
    'mode',
);

Le message collectable est Since acme/demo 1.2: The "old_mode" option is deprecated; use "mode" instead. Il faut toujours le package chargé et un collecteur pour l'observer dans ce scénario silencé. Le message conseille une migration ; il ne renomme pas l'option dans la configuration.

Pour une méthode, le signal se place dans son corps et se déclenche à chaque passage qui l'atteint. Pour une class entière, la convention le place au niveau du fichier, après les déclarations use : les noms courts des classes visées sont alors interprétés dans le contexte des imports prévus. Le signal est lié au chargement du fichier, pas à chaque construction d'objet. Un chargement unique ne recense donc pas toutes les utilisations ultérieures de la class.

🌍 In Real Life

La situation : un panneau annonce un ancien passage ; un compteur signale ceux qui l'empruntent. Un compteur silencieux ne dit rien des passages jamais visités.

L’équivalent dans Symfony : panneau → @deprecated ; signal observé → trigger_deprecation() ; collecteur → error handler adapté.

Retour à la réalité technique : le signal indique package et version d'introduction, pas de retrait. @ masque l'affichage ordinaire sans empêcher toute collecte. Une méthode signale au passage ; une classe entière au chargement du fichier.

🧠 Comment le mémoriser : « Lire les panneaux et observer les passages. » Image mentale : panneau devant un compteur. Question-réflexe : quels chemins n'ont pas été exercés ?

⚠️ À ne pas confondre : écran silencieux, absence de dépréciation et migration automatique.

Règle 3 : la trace écrite, trois files dans une pull request

À retenir en priorité
  1. La trace de migration accompagne la deprecation.
  2. La même pull request documente introduction et suppression prévue.

Le signal atteint un développeur pendant ses essais ; les guides doivent aussi aider l'équipe qui planifie une migration sans avoir exécuté ce chemin. Une pull request propose un ensemble de modifications à faire relire. Lors de celle qui introduit la deprecation, les trois traces ont des rôles distincts :

File Pour Request::get()
CHANGELOG.md du component section 7.4 : « Deprecate method Request::get(), … »
UPGRADE-<mineure>.md UPGRADE-7.4.md : la deprecation
UPGRADE-<majeure suivante>.md UPGRADE-8.0.md : « Remove Request::get(), … »

Le changelog annonce brièvement ce qui change dans le composant. Le guide de la mineure indique comment abandonner l'ancien usage pendant qu'il fonctionne encore. Le guide de la majeure décrit les conséquences du retrait à venir : pour notre controller, choisir le bag approprié au lieu de conserver l'appel global.

Ces trois modifications sont obligatoires dans la même pull request selon les conventions Symfony. Écrire « Remove » dans le guide de 8.0 ne signifie pas que la méthode disparaît déjà de 7.4 : la version du fichier fait partie de l'information. Un simple commentaire PHPDoc ne remplace aucune de ces trois traces.

Repère — Le CHANGELOG.md a ses propres règles :

Question: Which changelog should a contributor edit?

Answer: The component changelog, not generated root CHANGELOG-* files.

Les entrées nouvelles vont en haut de la section mineure. Le message est bref, impératif et sans point final.

Le `CHANGELOG.md` a ses propres règles

À retenir en priorité
  1. Les entrées nouvelles vont en haut de la section mineure.
  2. Le message est bref, impératif et sans point final.

Le changelog doit permettre à l'équipe du blog de repérer rapidement les changements de la version qu'elle adopte. Le titre reste CHANGELOG, avec une section par version mineure et les nouvelles entrées en haut de la liste. Une rubrique supplémentaire ### Deprecations ne respecte pas cette convention : il n'y a pas de troisième niveau.

Le message est court, commence par un verbe à l'impératif avec majuscule et ne se termine pas par un point. Le guide de migration, lui, peut porter l'explication détaillée des trois provenances de données. Ce fragment historique 5.3 illustre seulement le format documentaire ; il ne décrit pas une API MagicConfig à employer en Symfony 8.0 :

CHANGELOG
=========

5.3
---

 * Add `MagicConfig` that allows configuring things

Lu comme une entrée de changelog, il annonce un ajout dans la section 5.3 ; ce n'est ni du PHP à exécuter ni une configuration chargée par le blog. L'auteur modifie le CHANGELOG.md du composant concerné. Les CHANGELOG-* à la racine de symfony/symfony sont des agrégats générés à la préparation des versions, et ne doivent pas être édités manuellement.

La suppression a sa propre trace

À retenir en priorité
  1. La deprecation et la suppression sont deux changements.
  2. La suppression ajoute sa propre trace.

La transition a été annoncée ; vient ensuite la modification qui retire effectivement l'ancienne API. Sa pull request ajoute les conséquences au CHANGELOG.md du composant sous la nouvelle majeure, par exemple « Remove the Deprecated class, use Replacement instead ».

Pour HttpFoundation, l'équipe retrouve ainsi Deprecate sous 7.4 et Remove sous 8.0. Avec les deux guides de mise à jour, la transition laisse quatre entrées documentaires, pas nécessairement quatre fichiers distincts : deux entrées appartiennent au même changelog.

Cette dernière trace confirme le retrait, elle ne remplace pas l'annonce antérieure. Si le controller appelle encore la méthode supprimée, relire le guide permet de la corriger, mais le changelog n'adapte pas le code automatiquement.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Lire la bonne date.

    Lire la bonne date. Dans le message du getter, '7.4' signifie « déprécié depuis 7.4 ». Remplacer cette valeur par '8.0' parce que la méthode y disparaît fausserait l'histoire du signal.

  • Voir l’explication : Nommer le bon propriétaire.

    Nommer le bon propriétaire. 'symfony/http-foundation' identifie le package Composer ; 'HttpFoundation' ou son namespace PHP ne respecte pas ce rôle. La version s'interprète par rapport à ce package.

  • Voir l’explication : Charger la fonction avant de l'appeler.

    Charger la fonction avant de l'appeler. Le package de contrats fournit la fonction globale indépendamment du framework complet. Un simple commentaire ou un nom de package cité dans un message ne l'installe pas.

  • Voir l’explication : Distinguer silence et absence.

    Distinguer silence et absence. @deprecated documente ; le signal d'exécution est collectable malgré @. Un écran silencieux ou un chemin jamais exécuté ne prouve pas que le projet est prêt pour la majeure.

  • Voir l’explication : Ne pas appliquer une convention comme une règle du moteur.

    Ne pas appliquer une convention comme une règle du moteur. Symfony n'introduit pas de nouvelle class, interface, trait ou méthode déjà déprécié selon ses conventions de contribution ; PHP n'interdit pas techniquement d'écrire un tel commentaire.

  • Voir l’explication : Conserver la période de migration.

    Conserver la période de migration. La prochaine mineure annonce normalement le retrait, la majeure suivante l'effectue ; l'exception critique vise l'annonce sur une version antérieure maintenue. Les trois premières traces documentaires accompagnent l'annonce.

  • Voir l’explication : Compter les entrées, pas inventer un quatrième fichier.

    Compter les entrées, pas inventer un quatrième fichier. La suppression ajoute sa propre entrée au changelog du composant dans sa pull request. Cette entrée s'ajoute à la trace de deprecation et aux deux guides.

  • Voir l’explication : Modifier la source documentaire, pas l'agrégat.

    Modifier la source documentaire, pas l'agrégat. Les changelogs de racine sont générés ; la contribution se fait dans celui du composant. Cela évite de perdre une correction au prochain assemblage des notes de version.

Fiche express

À mémoriser

Pour terminer la migration du blog, vérifions six points :

  1. L'ancien usage a été repéré sur la dernière mineure précédente et remplacé avant sa suppression en majeure ; l'annonce critique sur une version antérieure maintenue reste exceptionnelle.
  2. Le remplacement choisit la bonne provenance : attribute de route, query string ou données de form, puis validation et recherche.
  3. L'annotation indique la version et le remplacement précis ; le signal d'exécution complète cette documentation sans couvrir les chemins jamais parcourus.
  4. L'appel fournit le package Composer, la version d'introduction, le message et éventuellement ses valeurs de formatage. Une class entière est signalée au chargement après les imports.
  5. Trois fichiers documentent l'annonce dans une même pull request ; le retrait ajoute une quatrième entrée, dans le changelog du composant.
  6. Le changelog conserve son format court : version mineure, pas de troisième niveau, impératif, majuscule, pas de point, nouvelles entrées en haut ; les agrégats de racine restent générés.

Une Request de l'article 42 qui réussit ne clôt pas cet audit : l'inscription, les erreurs et la commande d'import doivent aussi être examinées. Les notices collectées renseignent les usages observés, pas l'ensemble des usages possibles.
