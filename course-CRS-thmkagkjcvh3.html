Objectif

Savoir de quel côté un cookie se lit et de quel côté il s'écrit dans un controller. Les attributes de sécurité — SameSite, Secure, HttpOnly — et la constraint de suppression sont traités dans le Module 02 — Fondamentaux HTTP.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La Request contient ce que le client a envoyé.
  2. La Response contient les instructions Set-Cookie.

Un cookie se lit sur la Request — c'est ce que le client a envoyé — et s'écrit sur la Response, dans le header Set-Cookie. Un controller qui veut poser un cookie doit donc tenir la Response. Deux methods aux noms voisins font le contraire l'une de l'autre : removeCookie() annule un envoi, clearCookie() efface chez le client.

L'exemple : poser un cookie de préférence

▣ Exemple concret

Revoir la règle : La Request contient ce que le client a envoyé.

$response = $this->render('page.html.twig');
$response->headers->setCookie(Cookie::create('theme', 'dark'));

return $response;

Deux objects, deux sens

Revoir la règle : La Request contient ce que le client a envoyé.

Opération Object Path
lire un cookie Request $request->cookies->get('nom')
écrire un cookie Response $response->headers->setCookie(...)
supprimer un cookie chez le client Response $response->headers->clearCookie('nom')
retirer un cookie de la Response Response $response->headers->removeCookie('nom')

Le ticket de vestiaire reçu maintenant sera présenté lors d'une visite suivante. Un Set-Cookie dans la Response ne réécrit donc pas magiquement les cookies de la Request déjà reçue.

Conséquence pratique

À retenir en priorité
  1. Le header appartient au modèle Response.
  2. L'émission native contourne ce modèle.

Le controller construit la Response, y attache le cookie, puis la retourne. La function PHP setcookie() marche au niveau du protocole, mais écrit le header hors de la Response : le cookie échappe aux listeners de kernel.response et aux functional tests qui inspectent la Response.

removeCookie() fait un unset dans le sac : aucun Set-Cookie ne part. clearCookie() appelle setCookie() avec une valeur nulle et une date d'expiration dans le passé : c'est un header envoyé. Les cookies sont rangés sur trois niveaux — domain, path, nom — d'où le path (/ par défaut) et le domain de removeCookie(). getCookies() rend une liste à plat, ou l'arborescence avec ResponseHeaderBag::COOKIES_ARRAY ; un autre format lève une InvalidArgumentException.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Le header appartient au modèle Response.

On lit un cookie sur la Request et on l'écrit sur la Response. Poser un cookie sur l'object Request ne l'envoie nulle part : la Request est ce que le client a déjà envoyé.

removeCookie() ne supprime rien chez le client. Elle retire l'entrée du sac, donc le cookie n'est pas envoyé du tout. Pour faire oublier un cookie déjà posé, il faut en envoyer un — c'est clearCookie().

La fonction native de PHP fonctionne, et c'est le problème. Elle écrit le header hors du modèle de Symfony : le cookie échappe aux listeners de kernel.response et n'apparaît pas dans un functional test qui inspecte la Response.

Écrire un cookie oblige donc à tenir la Response. Un controller qui délègue entièrement le rendu n'a pas d'endroit où l'attacher.

Fiche express

◆ À mémoriser

Revoir la règle : La Request contient ce que le client a envoyé.

Si tu dois retenir seulement 5 choses :

  • Lire sur la Request, écrire sur la Response.
  • setcookie() de PHP contourne la Response : à éviter.
  • clearCookie() envoie une expiration passée ; removeCookie() n'envoie rien.
  • Index domain → path → nom ; removeCookie() vise / par défaut.
  • getCookies() : à plat ou en array ; autre format → exception.

Moyen mnémotechnique : « Clear efface chez lui, remove annule chez moi ».
