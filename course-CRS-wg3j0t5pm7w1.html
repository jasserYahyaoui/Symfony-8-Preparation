Objectif

Contraindre la valeur d'un parameter de route, et savoir quand ce requirement s'applique.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le requirement filtre la valeur entrante.
  2. La génération contrôle les valeurs fournies selon strict_requirements.

Un requirement est une expression régulière PHP que la valeur d'un parameter doit vérifier pour que la route corresponde. Il peut distinguer /blog/{page} de /blog/{slug} si les valeurs admises sont disjointes ; sinon l'ordre reste décisif. Il s'écrit en option, inline ou par l'enum Requirement, et il vaut aussi à la génération : par défaut, une valeur non conforme y lève une exception.

Le schéma

À retenir en priorité
  1. DIGITS accepte 0.
  2. POSITIVE_INT commence par un chiffre de 1 à 9.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Un requirement élimine les valeurs refusées.
  2. Deux routes qui acceptent la même valeur restent départagées par l'ordre.
class Exampleb27ebd18
{
    #[Route('/blog/{page}', name: 'blog_list', requirements: ['page' => Requirement::DIGITS])]
    public function list(int $page = 1): Response {}

    #[Route('/blog/{slug}', name: 'blog_show')]
    public function show(string $slug): Response {}
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Le problème qu'elle résout

△ Piège à éviter

C'est quoi ?

Un requirement est une expression régulière qui restreint les valeurs acceptées pour un paramètre de route. Il réduit l'ensemble des chemins correspondants ; il n'ajoute pas une priorité implicite à la route.

À quoi ça sert ?

Une pagination numérique ne doit pas interpréter le slug introduction comme un numéro de page. Cependant, restreindre page à [0-9]+ ne suffit pas à empêcher une route slug générale d'accepter elle aussi 2. Le chevauchement subsiste pour les chiffres si slug reste sans restriction.

Où dans Symfony ?

On peut utiliser requirements, la forme inline {page<[0-9]+>}, ou une constante de Requirement, telle que DIGITS. Ces constantes sont des chaînes de motifs ; DIGITS autorise zéro, POSITIVE_INT l'exclut. Les valeurs par défaut de route ne proviennent pas de l'URL et ne doivent pas être assimilées à des valeurs entrantes filtrées par le requirement.

Comment, étape par étape ?

  1. Définir les valeurs autorisées pour chaque route concurrente.
  2. Vérifier si leurs ensembles se recouvrent encore.
  3. Si oui, fixer l'ordre voulu ; si non, vérifier les cas limites de chaque ensemble.
  4. Tester également la génération : elle vérifie les requirements selon strict_requirements, contrairement à une condition de matching.

Exemple concret YAML

blog_list:
    path: /blog/{page}
    controller: App\Controller\BlogController::list
    requirements:
        page: '[0-9]+'

blog_show:
    path: /blog/{slug}
    controller: App\Controller\BlogController::show

Avec cet ordre, /blog/2 va vers list et /blog/introduction vers show. Contre-exemple : inverser les déclarations et affirmer que le requirement numérique maintient ce résultat. La route slug accepte 2 et gagne. Correction : garder la route numérique d'abord, ou définir pour slug une règle qui exclut les suites uniquement numériques si c'est réellement le contrat métier.

En génération, strict_requirements vaut true par défaut : une valeur incompatible lève InvalidParameterException. Avec false, le générateur signale l'erreur via le logger lorsqu'il est disponible et retourne une chaîne vide ; avec null, il ne contrôle pas les requirements. Aucun de ces réglages ne valide la signification métier du numéro.

Passage canonique conservé

Sans requirement, /blog/{page} et /blog/{slug} acceptent les mêmes formes ; la première correspondance gagne. Avec [0-9]+ sur page, la route de page refuse /blog/mon-article. Mais la route de slug non restreinte accepte toujours /blog/2 : l'ordre reste important pour cette valeur, sauf requirements réellement disjoints.

Le requirement ressemble à une fente qui accepte certaines formes de pièces. Une forme refusée laisse essayer une autre route ; une forme acceptée ne prouve pas qu'une ressource métier existe.

Trois façons de l'écrire

○ À comprendre

C'est quoi ?

Un requirement exprime le motif accepté pour une variable de route. La forme requirements, le motif inline dans le path et les constantes Requirement décrivent la même catégorie de restriction ; ils ne changent pas le type de donnée métier par eux-mêmes.

À quoi ça sert ?

La forme explicite regroupe les règles, la forme inline rapproche variable et motif, la constante évite de recopier une expression standard. Il faut choisir le domaine voulu : des chiffres ne signifient pas forcément un entier strictement positif.

Où dans Symfony ?

Requirement est une enum sans cas, utilisée comme porteuse de constantes chaînes. DIGITS vaut [0-9]+ ; POSITIVE_INT vaut [1-9][0-9]*. En YAML Symfony, !php/const demande la valeur de la constante au loader : ce n'est pas une chaîne contenant son nom.

Comment, étape par étape ?

  1. Choisir les valeurs autorisées, dont zéro et les signes éventuels.
  2. Déclarer le motif sans délimiteurs PHP de preg_match.
  3. Vérifier le nom de variable auquel il s'applique.
  4. Tester une valeur acceptée et une refusée, sans oublier les routes concurrentes.

Exemple concret YAML

blog_list:
    path: /blog/{page}
    controller: App\Controller\BlogController::list
    requirements:
        page: !php/const Symfony\Component\Routing\Requirement\Requirement::DIGITS

Deux écritures alternatives du même motif sont requirements: {page: '[0-9]+'} et le path /blog/{page<[0-9]+>}. Elles acceptent 0 et 12, pas moins1. Contre-exemple : choisir DIGITS pour interdire la page zéro. Correction : POSITIVE_INT si c'est le domaine voulu. Ni l'une ni l'autre ne prouve qu'une page existe ; la vérification métier reste distincte. Un parseur YAML générique doit connaître le tag Symfony pour interpréter !php/const.

Passage canonique conservé

Trois façons de l'écrire

Forme Exemple
option requirements requirements: ['page' => '[0-9]+']
inline dans le path /blog/{page<[0-9]+>}
constante de l'enum requirements: ['page' => Requirement::DIGITS]

L'enum Symfony\Component\Routing\Requirement\Requirement n'a aucun cas : elle porte des constants string — chiffres, dates, UUID. En YAML, on l'utilise avec !php/const. DIGITS vaut [0-9]+ et laisse passer /blog/0 ; POSITIVE_INT vaut [1-9][0-9]* et exclut 0.

Repère — Ce qui est autorisé : utf8: true. Les requirements sont des expressions régulières. L'option utf8 permet les properties Unicode.

Ce qui est autorisé

À retenir en priorité
  1. Les requirements sont des expressions régulières.
  2. L'option utf8 permet les properties Unicode.

Un requirement peut contenir un parameter de configuration, pour définir une expression compliquée une fois. Il accepte les properties Unicode PCRE avec l'option utf8: true de la route : \p{Lu} correspond alors à toute majuscule.

Deux pièges

△ Piège à éviter

C'est quoi ?

Un requirement filtre le texte présent dans l'URL. Une valeur par défaut est fournie par la configuration lorsque la variable facultative n'apparaît pas : elle n'est pas une portion de texte à filtrer dans cette URL.

À quoi ça sert ?

Une route peut ainsi accepter un numéro explicite tout en utilisant une valeur spéciale pour son état sans numéro. Ce contrat doit être reflété dans l'action : un argument strictement numérique ne convient pas si le défaut est une chaîne métier.

Où dans Symfony ?

La fin facultative du path est compilée en tenant compte des defaults. À la génération, les requirements sont contrôlés suivant strict_requirements : true lève en cas de valeur incompatible ; false produit une chaîne vide et peut journaliser ; null désactive ce contrôle. Cela ne transforme pas le défaut en une valeur entrante explicitement reconnue.

Comment, étape par étape ?

  1. Séparer le cas segment absent du cas segment présent.
  2. Définir un défaut adapté au premier.
  3. Restreindre les segments effectivement reçus.
  4. Tester les deux cas et adapter le type de l'action à leurs résultats.

Exemple concret YAML

archive:
    path: /archive/{page}
    controller: App\Controller\ArchiveController::list
    defaults:
        page: all
    requirements:
        page: '[0-9]+'

/archive fournit all ; /archive/2 fournit 2 ; /archive/all ne correspond pas à cette route. Contre-exemple : conclure que all est autorisé dans le chemin parce qu'il est le défaut. Correction : distinguer valeur injectée et segment apparié. Si la même valeur doit être permise explicitement, écrire un requirement qui l'autorise et tester les éventuels chevauchements de routes.

Passage canonique conservé

Deux pièges

Une default value n'est pas tenue de satisfaire le requirement : celui-ci filtre l'URL entrante, et la default value n'y est pas.

Le generator relit chaque requirement. Selon framework.router.strict_requirements : true, le défaut, lève une InvalidParameterException ; false journalise l'erreur et rend une string vide — l'aide de l'option annonce null, le code 8.0 rend '' ; null ne vérifie rien. L'aide suggère true en développement, false ou null en production.

Pièges d'examen

△ Piège à éviter

Chevauchement des routes, Unicode et contrôle des requirements

Un requirement réduit les valeurs acceptées, pas forcément tout chevauchement entre routes. Deux routes qui acceptent le même path restent départagées par l'ordre. Les properties Unicode comme \p{Lu} exigent utf8: true. Le generator contrôle également les requirements : une valeur incompatible lève par défaut.

Application

À retenir en priorité
  1. DIGITS accepte 0.
  2. POSITIVE_INT commence par un chiffre de 1 à 9.
  3. Les requirements sont des expressions régulières.
  4. L'option utf8 permet les properties Unicode.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Requirement = regex PHP ; sans lui, l'ordre de déclaration départage.
  • Option, inline {page<[0-9]+>}, ou enum Requirement (sans cas).
  • DIGITS accepte 0 ; POSITIVE_INT non.
  • \p{…} exige utf8: true.
  • Default value : pas tenue de vérifier le requirement.
  • Génération : true → exception, false → '', null → rien.

Moyen mnémotechnique : « Le requirement vaut à l'arrivée comme à la génération ».
