Objectif

Le catalogue sert /blog/42, mais l'import CLI doit aussi archiver ses fichiers sources. Son service reçoit des objets, comme le logger, et des valeurs : un directory, une destination et une limite. Comment fournir ces valeurs sans coder les réglages du serveur dans la classe ? Nous allons suivre leur déclaration, leur résolution et leur injection, puis distinguer conversion technique et règle métier.

L'essentiel

À comprendre

À retenir en priorité
  1. Les parameters ordinaires sont compilés.
  2. Les valeurs d'environment restent résolues à l'usage.

Un parameter est une valeur de configuration nommée, référencée par %nom%. Une valeur ordinaire est résolue pendant la compilation. Un parameter peut cependant contenir %env(NOM)% : cette référence à une variable d'environment reste normalement différée jusqu'à son utilisation.

Une variable brute fournit une string ; un processeur transforme ou sélectionne sa valeur, par exemple int: pour obtenir un entier. Le container peut mémoriser le résultat : lecture différée ne signifie pas actualisation à chaque méthode. Enfin, bind et #[Autowire] indiquent quel argument reçoit quelle valeur ; ils ne devinent pas la signification d'un argument string.

Le schéma

À retenir en priorité
  1. Le placeholder conserve une résolution dynamique.
  2. Un parameter ordinaire devient une valeur compilée.

L'exploitation fournit ARCHIVE_MAX=12. Notre service attend pourtant un int. Le schéma suit la référence jusqu'au constructeur, sans placer artificiellement cette opération dans chaque étape HTTP :

Orange : l'instruction conservée ; bleu : lecture puis conversion ; vert : l'entier 12 ; rouge : la variable absente sans secours. Ce chemin suppose une résolution usuelle, non forcée à la compilation. Une chaîne non numérique ferait également échouer la conversion, mais pour une autre raison que l'absence de variable.

L'Archiver construit conserve l'argument reçu. Modifier ensuite l'environment ne change ni cet argument ni nécessairement la valeur déjà mémorisée par le container. Pour un worker d'import persistant, le renouvellement du processus reste une décision d'exploitation.

Le fil rouge : un `Archiver`

À retenir en priorité
  1. Un type string ne désigne pas un service unique.
  2. Utiliser arguments, bind ou Autowire.

Cette classe de laboratoire conserve les trois valeurs de l'archivage. Le DSN est une chaîne décrivant une destination de connexion ; la stocker ne crée pas une connexion. Le code est volontairement limité au contrat du constructeur, sans écriture de fichier :

class Archiver
{
    public function __construct(
        private string $archiveDir,      // un dossier du projet : un parameter
        private string $storageDsn,      // change selon le serveur : une variable d'environment
        private int $maxFiles,           // réglé par l'exploitation : variable + processeur int
    ) {
    }
}

Le résultat attendu de l'assemblage est un objet contenant le directory, la destination et la limite choisies. Aucun des trois types ne dit quel chemin ou quelle limite convient au projet : le container a besoin des instructions suivantes. Une valeur correctement typée peut encore être inutilisable, par exemple un directory non accessible.

Compilation ou exécution : `%nom%` contre `%env()%`

À retenir en priorité
  1. La résolution est différée.
  2. Une compilation réussie ne garantit pas la présence de la variable.

Le directory relatif au projet est stable dans notre configuration. La destination de stockage et la limite peuvent varier entre déploiements. Le tableau distingue ces valeurs ordinaires d'une référence différée :

La valeur… Écriture Résolue
est propre au projet %app.archive_dir% à la compilation
change selon le serveur, sans recompiler %env(ARCHIVE_DSN)% à l'exécution
sert seulement à en calculer d'autres %.nom_temporaire% à la compilation, puis supprimée

Dans l'application, le kernel fournit notamment kernel.project_dir, kernel.environment, kernel.debug et kernel.cache_dir. Pour notre classe Archiver autoloadable, ce fragment fournit explicitement les trois arguments :

parameters:
    app.archive_dir: '%kernel.project_dir%/var/archive'
    env(ARCHIVE_MAX): '100'

services:
    Archiver:
        arguments:
            $archiveDir: '%app.archive_dir%'
            $storageDsn: '%env(ARCHIVE_DSN)%'
            $maxFiles: '%env(int:ARCHIVE_MAX)%'

Avec kernel.project_dir=/srv/blog, une destination fournie par ARCHIVE_DSN et aucune variable ARCHIVE_MAX, le constructeur reçoit /srv/blog/var/archive, la destination donnée et l'entier 100. Le parameter env(ARCHIVE_MAX) sert de secours ; il n'écrit pas une variable dans le système et ne crée pas le directory.

Un parameter ordinaire ne se modifie plus avec setParameter() après compilation. En revanche, la même classe de container générée peut être instanciée dans deux contextes de processus, avec PORT=6379 puis PORT=6380, et résoudre deux valeurs différentes sans recompiler sa référence env. Ce n'est pas la promesse qu'un même cache convient à toute configuration dev et prod, ni qu'un container existant relira constamment la variable.

Sans variable ni secours, une référence env usuelle peut traverser la compilation puis lever EnvNotFoundException à sa résolution, par exemple lors de la construction du consommateur. Une résolution explicitement forcée plus tôt avance ce contrôle.

Un parameter .build.hash commençant par un point sert seulement pendant la compilation : app.version: 'v1-%.build.hash%' conserve le résultat calculé, mais demander ensuite .build.hash échoue. Enfin, parameterCannotBeEmpty() déclare une exigence de non-vacuité contrôlée à la lecture de la valeur ; ce n'est pas une preuve que tous les réglages ont été validés par la seule déclaration.

Lire via ParameterBagInterface ne rend pas les paramètres dynamiques. get() d'un nom absent lève ParameterNotFoundException, alors qu'un parameter explicitement déclaré null rend null ; has() permet de distinguer ces deux situations.

🌍 In Real Life

La situation : une fiche de préparation contient une mesure déjà calculée et une consigne « consulter le réglage du site au besoin ». L'équipement assemblé conserve ensuite le réglage reçu.

L’équivalent dans Symfony : mesure calculée → parameter ordinaire ; consigne différée → référence %env(...)% ; équipement réglé → consommateur construit.

Retour à la réalité technique : la résolution env usuelle est différée, mais peut être forcée plus tôt et son résultat mémorisé. Elle ne reconfigure pas les instances existantes. Un parameter temporaire peut disparaître après avoir contribué au calcul d'une valeur conservée.

🧠 Comment le mémoriser : « Différé n'est pas continuellement relu. » Image mentale : consigne consultée puis réglage fixé sur l'appareil. Question-réflexe : quand cette valeur est-elle résolue, puis conservée ?

⚠️ À ne pas confondre : parameter absent, valeur null déclarée et variable env manquante sans secours.

Le pourcent littéral : `%%`

À retenir en priorité
  1. Les pourcents délimitent les références.
  2. Doubler le caractère le rend littéral.

L'import affiche maintenant un libellé de progression contenant %. Les guillemets YAML protègent sa syntaxe YAML, mais n'empêchent pas le traitement ultérieur des références par DependencyInjection. %off% désigne un parameter ; %% est un échappement, pas une référence à un parameter vide.

Pour conserver les caractères sans ambiguïté :

parameters:
    app.progress_label: '100%%'
    app.discount_label: '5%%off%%now'

Les valeurs résolues sont 100% et 5%off%now. Le second libellé est un exemple lexical historique, pas une politique commerciale du blog. Voici pourquoi les variantes non échappées n'ont pas toutes le même effet :

Valeur écrite Valeur obtenue
'100%%' 100%
'50%', 'from 5% to 10% off' inchangées
'5%off%now' ParameterNotFoundException : « …has a dependency on a non-existent parameter "off". »

La dernière ligne suppose que off n'est pas défini. Un % isolé, ou une paire contenant des espaces, ne forme pas cette référence. La règle concerne les valeurs lues par le container : ce n'est pas une instruction de doubler chaque % dans du PHP, un template Twig ou une URL.

🌍 In Real Life

La situation : un formulaire traverse deux lecteurs : le premier comprend sa mise en page, le second interprète ses références. Protéger la mise en page n'arrête pas ce second lecteur.

L’équivalent dans Symfony : premier lecteur → YAML ; second → résolution des paramètres DI ; référence → %off% ; caractère conservé → %%.

Retour à la réalité technique : les guillemets YAML ne neutralisent pas les références DI. '5%%off%%now' conserve les pourcents, tandis que '5%off%now' cherche off. Cette règle vise les valeurs interprétées par DI, pas tout texte PHP ou toute URL.

🧠 Comment le mémoriser : « Deux lecteurs, deux syntaxes. » Image mentale : le formulaire passant devant deux bureaux. Question-réflexe : quelle couche interprète ce caractère ?

⚠️ À ne pas confondre : pourcent isolé et référence reconnue entre pourcents.

Les processeurs : convertir et composer

À retenir en priorité
  1. Les processeurs se lisent de droite à gauche.
  2. Le plus proche de la variable agit d'abord.

Une limite brute '12' n'est pas encore un entier et un texte JSON n'est pas encore un array PHP. Dans un bloc arguments adapté à un consommateur déclarant ces noms, les trois formes suivantes expriment conversion, décodage et secours :

$maxFiles: '%env(int:ARCHIVE_MAX)%'                              # string → int
$options:  '%env(json:ARCHIVE_OPTIONS)%'                         # JSON → array
$dsn:      '%env(default:app.fallback_dsn:ARCHIVE_DSN)%'         # parameter de secours

Avec ARCHIVE_MAX='12', int: fournit 12. Avec ARCHIVE_OPTIONS='{"limit":3}', json: fournit ['limit' => 3]. La troisième ligne suppose le parameter app.fallback_dsn déclaré : il sert de secours lorsque la variable manque ou donne une valeur vide selon le traitement default. Ce fragment n'ajoute pas $options ou $dsn au constructeur précédent : c'est une comparaison de syntaxes.

Symfony 8.0 fournit vingt et un préfixes intégrés, dont bool, int, json, csv, base64, default, enum et trim. Une conversion ne valide pas toute la règle métier. int: accepte aussi des valeurs numériques qu'il convertit : il ne garantit pas une limite positive. json: accepte un array ou null décodé, rejette les autres scalaires JSON, mais ne garantit pas la présence de la clé limit.

Les processeurs se composent de droite à gauche :

parameters:
    env(ARCHIVE_OPTIONS): 'eyJsaW1pdCI6M30='
    app.archive_options: '%env(json:base64:ARCHIVE_OPTIONS)%'

Sans variable externe, base64 transforme le secours en {"limit":3}, puis json donne ['limit' => 3]. Inverser base64 et json tenterait d'abord de lire la chaîne encodée comme du JSON. Le même ordre explique %env(json:base64:SECRETS)% ; base64 est un encodage, pas un chiffrement.

default::VAR, sans nom de parameter de secours, peut rendre null si la variable manque ou est vide. Le consommateur doit accepter cette absence. Ajouter int: à gauche transforme ce null en 0 : ce résultat ne prouve pas qu'une configuration correcte a été fournie. Enfin, kernel.runtime_environment utilise %env(default:kernel.environment:APP_RUNTIME_ENV)% : l'environment du kernel est le secours, pas une constante universelle prod.

🌍 In Real Life

La situation : on ouvre l'emballage d'un document avant d'en lire les rubriques ; savoir le lire ne prouve pas qu'il contient la rubrique attendue.

L’équivalent dans Symfony : ouvrir l'encodage → base64 ; lire la structure → json ; vérifier la rubrique → validation du consommateur.

Retour à la réalité technique : json:base64:VAR traite la valeur depuis la droite. int: convertit sans imposer une limite positive ; json: ne garantit pas la clé limit. Un secours null converti ensuite en entier peut devenir 0, sans prouver une configuration correcte.

🧠 Comment le mémoriser : « Ouvrir, lire, vérifier. » Image mentale : document extrait puis contrôlé. Question-réflexe : quelle valeur exacte entre et sort de chaque processeur ?

⚠️ À ne pas confondre : encodage base64 et chiffrement, conversion et validation métier.

`bind` et `#[Autowire]` : injecter un scalaire

À retenir en priorité
  1. bind mutualise une valeur dans son scope.
  2. Autowire configure une injection précise.

Nous savons produire le chemin, mais plusieurs services peuvent avoir un argument de même rôle. Un binding associe un nom et éventuellement un type d'argument à une valeur dans sa portée de configuration. L'exemple suppose app.archive_dir déclaré et des services enregistrés dans ce même bloc avec l'argument string $archiveDir :

services:
    _defaults:
        autowire: true
        bind:
            string $archiveDir: '%app.archive_dir%'

Ces consommateurs reçoivent le chemin calculé ; ce fragment seul ne découvre aucune class. Pour un argument particulier, l'attribute Symfony\Component\DependencyInjection\Attribute\Autowire exprime le choix près du constructeur. Avec son import PHP, dans une class enregistrée et autowirée :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __construct(
    #[Autowire('%app.archive_dir%')] private string $archiveDir,
    #[Autowire(env: 'int:ARCHIVE_MAX')] private int $maxFiles,
    #[Autowire(param: 'kernel.environment')] private string $env,
) {}

Le premier argument reçoit le parameter du chemin ; le deuxième la variable ARCHIVE_MAX convertie ; le troisième le nom d'environment du kernel. env: attend le nom avec ses processeurs, sans %env(...)% ; param: attend un nom de parameter, sans %...%. Cet extrait montre une autre signature de constructeur, pas une seconde méthode à coller dans le premier Archiver.

Le binding de _defaults vaut pour les définitions de son bloc, pas pour tous les fichiers importés ou tous les blocs when@. Il doit correspondre aux noms et types concernés. Un binding inutilisé, par exemple $archiveDri au lieu de $archiveDir, peut faire échouer la compilation avec le diagnostic de ResolveBindingsPass. La précision évite qu'un réglage apparemment déclaré reste silencieusement sans consommateur.

🌍 In Real Life

La situation : une consigne de réglage s'adresse aux postes d'un atelier dont l'entrée porte un nom précis ; elle ne concerne pas automatiquement tous les ateliers voisins.

L’équivalent dans Symfony : atelier → bloc de définitions ; entrée nommée et typée → cible du bind ; instruction locale → #[Autowire] sur l'argument.

Retour à la réalité technique : le binding de _defaults a une portée ; il ne découvre aucune classe. Un nom erroné peut rester inutilisé et faire échouer la compilation. env: attend le nom avec processeurs ; param: attend le nom du parameter.

🧠 Comment le mémoriser : « Le bon réglage, à la bonne entrée, dans la bonne portée. » Image mentale : une consigne fixée au poste concerné. Question-réflexe : quel argument enregistré consomme réellement ce binding ?

⚠️ À ne pas confondre : configuration des arguments et enregistrement des services.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un bind orphelin signale une configuration incohérente.
  2. Vérifier type et nom de l'argument.
  • Voir l’explication : Le nom parameter ne garantit pas une valeur finale figée.

    Le nom parameter ne garantit pas une valeur finale figée. Un parameter ordinaire est résolu à la compilation ; il peut aussi contenir une référence env différée. Ni l'une ni l'autre ne reconfigure magiquement un Archiver déjà construit.

  • Voir l’explication : Lire la chaîne de transformations depuis la variable.

    Lire la chaîne de transformations depuis la variable. Dans json:base64:ARCHIVE_OPTIONS, le décodage base64 précède le décodage JSON ; inverser les noms change l'entrée de chaque étape.

  • Voir l’explication : Les guillemets YAML ne désactivent pas les références.

    Les guillemets YAML ne désactivent pas les références. '5%off%now' cherche off ; '5%%off%%now' conserve les caractères. L'absence d'erreur avec '50%' ne généralise pas à toutes les chaînes.

  • Voir l’explication : Le binding a une portée et un consommateur.

    Le binding a une portée et un consommateur. Un nom ou type incorrect peut laisser le binding inutilisé et provoquer une erreur de compilation. Répéter une valeur au hasard ne répare pas une mauvaise signature.

  • Voir l’explication : Le moment de l'erreur dépend du moment de la résolution.

    Le moment de l'erreur dépend du moment de la résolution. L'absence sans secours échoue normalement à l'utilisation de la référence, et bloque les consommateurs qui en dépendent. Une résolution forcée pendant la compilation avance ce moment ; déclarer un secours peut l'éviter.

  • Voir l’explication : Conversion et validation restent distinctes.

    Conversion et validation restent distinctes. La variable brute PORT=6379 fournit une string ; int: demande un entier. Le succès de la conversion ne valide ni une plage de ports ni une limite d'archives positive.

  • Voir l’explication : Un parameter temporaire peut laisser un résultat durable.

    Un parameter temporaire peut laisser un résultat durable. .build.hash disparaît après compilation, mais la valeur calculée de app.version demeure. Ne confondons pas absence de ce parameter, valeur explicitement null et variable env manquante.

Fiche express

À mémoriser

À retenir en priorité
  1. Le contenu numérique ne change pas le type.
  2. La conversion se demande explicitement.

Pour préparer l'import sans modifier le traitement de /blog/42 :

  1. Séparer valeur ordinaire du projet et référence env différée.
  2. Prévoir le comportement si la variable est absente, sans promettre une mise à jour automatique des instances existantes.
  3. Convertir la string brute puis valider les contraintes du consommateur.
  4. Échapper les pourcents littéraux dans les valeurs interprétées par DependencyInjection, pas indistinctement dans tout le projet.
  5. Lire les processeurs de droite à gauche et suivre les résultats, notamment null puis éventuellement 0.
  6. Choisir entre argument explicite, binding de bloc et attribute d'argument ; une class reste à enregistrer.
  7. Distinguer parameter temporaire supprimé, parameter absent et parameter déclaré null.

Le prochain problème n'est plus la valeur elle-même : il faut vérifier quelle définition de service la reçoit réellement.
