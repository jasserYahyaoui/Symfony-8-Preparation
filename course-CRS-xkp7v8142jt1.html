Objectifs d’apprentissage

  • Distinguer les objects BrowserKit des objects HttpFoundation
  • Lire code, headers et contenu de la Response
  • Identifier la route ayant répondu

Objectif

Lire ce que le client a réellement envoyé et reçu. La difficulté tient à ce que deux couches existent, avec deux objects pour la Request et deux pour la Response.

L'essentiel

○ À comprendre

À retenir en priorité
  1. internal désigne le navigateur simulé.
  2. Les methods sans internal exposent HttpFoundation.

Le client expose deux couches : getRequest() et getResponse() rendent les objects HttpFoundation que l'application a vus ; getInternalRequest() et getInternalResponse() rendent ceux du navigateur simulé, BrowserKit. Avant toute Request, ils lèvent une exception. Après un redirect non suivi, getRequest() est la Request qui a redirigé.

Le schéma

À retenir en priorité
  1. Le client adapte les deux couches.
  2. Le controller utilise HttpFoundation.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. La Response applicative porte le HeaderBag.
  2. La version BrowserKit possède une autre API.
$client->request('POST', '/go');                       // répond 302 vers /hello
$client->getResponse()->getStatusCode();               // 302, côté application
$client->getRequest()->attributes->get('_route');      // 'go' : la Request qui a redirigé
$client->followRedirect();
$client->getRequest()->getMethod();                    // 'GET' : un 302 ne garde pas POST
$this->assertRouteSame('hello');

Les deux couches

○ À comprendre

À retenir en priorité
  1. Les APIs ne sont pas interchangeables.
  2. Choisir selon la couche inspectée.

C'est quoi ?

Le navigateur simulé et l'application utilisent deux modèles HTTP. BrowserKit représente la navigation ; HttpFoundation représente les objets reçus et produits par l'application Symfony. Le client adapte l'un à l'autre.

À quoi ça sert ?

Identifier la couche évite d'appeler une méthode ou une propriété sur le mauvais objet. Cela permet aussi de vérifier la route réellement exécutée plutôt que de la déduire du seul HTML.

Où dans Symfony ?

  • getRequest() et getResponse() exposent HttpFoundation.
  • getInternalRequest() et getInternalResponse() exposent BrowserKit.
  • « internal » désigne donc ici la couche navigateur simulé, pas l'intérieur du controller.

Comment, étape par étape ?

  1. Envoyer une Request avant d'attendre une Response exploitable.
  2. Choisir la couche qui porte l'information voulue.
  3. Lire le statut, les headers et le contenu de la Response ; pour une assertion de contrat, préférer les helpers Symfony qui fournissent un diagnostic utile.
  4. Lire _route dans les attributes de la Request pour connaître la route sélectionnée. Après une redirection suivie, la Request courante est celle de la destination.

Exemple concret PHP

Extrait d'un test WebTestCase dont / est servi par la route homepage :

$client = static::createClient();
$client->request('GET', '/');
self::assertResponseStatusCodeSame(200);
self::assertRouteSame('homepage');
$contentType = $client->getResponse()->headers->get('Content-Type');
self::assertNotNull($contentType);

Les deux premières assertions distinguent le succès HTTP de la route attendue. La dernière vérifie la présence d'un header, pas sa valeur exacte ; renforcer cette assertion si le contrat impose un type précis.

Contre-exemple : utiliser getInternalResponse()->headers comme s'il s'agissait du HeaderBag HttpFoundation. Correction : choisir getResponse() ou utiliser les méthodes BrowserKit getHeader() et getHeaders(). Un statut 200 et un titre plausible ne prouvent pas que la bonne route a été appelée ; une page de repli pourrait satisfaire ces deux observations.

Introspection dans les tests 8.0.

Passage canonique conservé

Les deux couches

Method Class rendue Couche
getRequest() HttpFoundation\Request application
getInternalRequest() BrowserKit\Request navigateur simulé
getResponse() HttpFoundation\Response application
getInternalResponse() BrowserKit\Response navigateur simulé
  • internal désigne le navigateur, pas l'application.
  • HttpKernelBrowser, parent du client, traduit d'une couche à l'autre : filterRequest() et filterResponse().
  • La Response BrowserKit n'a pas de property headers : getHeader(), getHeaders(), getStatusCode(), getContent().

Les autres objects internes

À retenir en priorité
  1. L'historique appartient au client.
  2. Il est distinct de la Request courante.
Method Class rendue
getHistory() BrowserKit\History
getCookieJar() BrowserKit\CookieJar
getCrawler() DomCrawler\Crawler, le même object que celui rendu par request()

Avant la première Request

À retenir en priorité
  1. La Response n'existe pas toujours.
  2. Envoyer une Request avant introspection.
Appel avant toute Request Résultat
getRequest(), getResponse(), leurs versions internal, getCrawler() BadMethodCallException : « The "request()" method must be called before … »
getHistory() un historique vide
getCookieJar() utilisable : on peut y poser un cookie

Introspecter la Response

À retenir en priorité
  1. Le message d'échec aide à comprendre le comportement.
  2. L'assertion exprime aussi l'intention.

getResponse() est un HttpFoundation\Response ordinaire. Pour affirmer, préférer les assertions de Symfony : assertResponseStatusCodeSame(404) affiche en échec la Response entière — statut, headers, corps —, là où assertSame() ne montre que deux nombres.

Introspecter la Request

À retenir en priorité
  1. L'HTML ne révèle pas forcément la route.
  2. L'attribute permet un contrôle précis.
  • _route dit quelle route a répondu — ce que vérifie assertRouteSame(), et qu'aucune inspection du HTML ne donne.
  • _controller vaut Classe::méthode pour une route posée sur une method. Pour un controller invocable, la class seule : AttributeRouteControllerLoader omet le nom de la method.
  • getRequest()->getPathInfo() rend /hello ; getUri(), des deux côtés, http://localhost/hello.

Après un redirect

À retenir en priorité
  1. La destination n'a pas toujours été appelée.
  2. Le contexte change après followRedirect().

Le client ne suit pas les redirects par défaut : getRequest() est la Request qui a redirigé.

Étape getResponse() _route
request('GET', '/go') 302 go
followRedirect() 200 hello

Après un 301, 302 ou 303, followRedirect() envoie un GET sans les parameters ; après un 307 ou un 308, la method et les parameters sont gardés.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le client possède déjà son état navigateur.
  2. Request, Response et Crawler nécessitent une navigation.
  • Voir l’explication : getInternalRequest() est l'object BrowserKit

    getInternalRequest() est l'object BrowserKit, pas celui de l'application.

  • Voir l’explication : getRequest() et getResponse() sont les objects HttpFoundation

    getRequest() et getResponse() sont les objects HttpFoundation — ceux que le controller a vus et produits.

  • Voir l’explication : Avant toute Request, ils lèvent BadMethodCallException

    Avant toute Request, ils lèvent BadMethodCallException — ils ne rendent pas null. L'historique et les cookies, eux, existent déjà.

  • Voir l’explication : Un redirect non suivi

    Un redirect non suivi laisse _route sur la route qui a redirigé.

  • Voir l’explication : Préférer les assertions Symfony

    Préférer les assertions Symfony aux lectures brutes, pour le message d'échec.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le status code détermine la conservation de method.
  2. Ne pas assimiler tous les redirects.

Si tu dois retenir seulement 7 choses :

  • internal = navigateur simulé (BrowserKit).
  • getRequest(), getResponse() = HttpFoundation, ce qu'a vu l'application.
  • Avant toute Request : exception, sauf historique et cookies.
  • getCrawler() : le crawler de la dernière Request.
  • _route et _controller dans les attributes de la Request.
  • Redirect non suivi : _route de la route qui a redirigé.
  • 302 suivi → GET ; 307/308 → même method.

Moyen mnémotechnique : « Interne = navigateur ; rien avant request() ».

internal = BrowserKit, sinon HttpFoundation ; rien avant request() (sauf History, CookieJar) ; _route / _controller ;
redirect non suivi = Request d'origine ; followRedirect : 301/302/303 → GET, 307/308 → même method
