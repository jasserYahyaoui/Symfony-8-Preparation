Objectif

L'import du blog peut choisir un seul exporteur parmi plusieurs formats. Injecter une grande collection pour la parcourir jusqu'au bon choix n'est pas toujours utile. Un locator déclare un petit ensemble de choix et diffère leur récupération. Nous allons expliquer ce compromis, ses erreurs et sa portée, sans donner au service métier un accès illimité au container. AbstractController reste traité dans son cours propre.

L'essentiel

À comprendre

À retenir en priorité
  1. Le locator limite les dependencies accessibles.
  2. La création est différée au get().

Un service locator fournit has() et get() sur un ensemble restreint de clés. Il s'agit bien d'une recherche de service à l'utilisation, mais ses possibilités sont déclarées et peuvent être câblées à la compilation. Un service subscriber annonce cette liste via ServiceSubscriberInterface.

Le locator diffère la récupération, pas nécessairement toute construction : un objet partagé déjà obtenu ailleurs peut être réutilisé. Pour deux collaborateurs toujours nécessaires, l'injection directe reste souvent plus simple. Le locator devient utile lorsque le choix se fait à l'exécution et qu'une seule branche sera utilisée.

🌍 In Real Life

La situation : le poste reçoit accès à quelques casiers identifiés et choisit l'outil utile au moment de travailler, sans vider tous les casiers.

L’équivalent dans Symfony : casiers déclarés → clés du locator ; choix local → clé demandée à l'exécution ; retrait → get() ; liste préparée → déclaration du service subscriber.

Retour à la réalité technique : le locator borne les services récupérables et diffère leur récupération. Il peut retrouver une instance partagée déjà construite ailleurs. Deux dépendances toujours nécessaires restent souvent plus claires en injection directe.

🧠 Comment le mémoriser : « Petit choix déclaré, retrait au besoin. » Image mentale : quelques casiers nommés, un seul ouvert. Question-réflexe : le choix doit-il réellement attendre l'exécution ?

⚠️ À ne pas confondre : service subscriber déclarant des dépendances et event subscriber déclarant des réactions aux événements.

Le schéma

À retenir en priorité
  1. Le locator n'est pas le container global.
  2. Son contrat est une liste explicite.

La première vue concerne le subscriber enregistré et conservé, avec l'intégration qui lit sa liste. Les références obligatoires et facultatives n'ont pas la même politique d'absence :

La seconde vue commence après cet assemblage : une clé choisie par le code applicatif provoque la récupération puis l'appel métier.

Bleu : travail effectué ; orange : décision ; vert ou rouge : résultat. Une clé absente au runtime ne signifie pas que sa déclaration obligatoire a échappé au contrôle : elle peut simplement n'avoir jamais été déclarée, ou correspondre à un service facultatif absent.

Pour la suite, les handlers sont partagés et n'ont pas encore été construits ailleurs. Avec shared: false, une nouvelle résolution est demandée à chaque récupération ; le locator ne change pas la recette de création. Si une factory rend toujours le même objet, un nouvel appel n'impose pas une identité différente.

Le fil rouge : un CommandBus

À retenir en priorité
  1. Le bus connaît les keys de sélection.
  2. Les handlers inutilisés restent non construits.

Ce bus local illustre la sélection d'un traitement ; il n'est pas une implémentation du composant Messenger. Command représente ici une instruction applicative dont la clé a été choisie par notre code, pas un identifiant de service copié librement depuis une entrée utilisateur. FooHandler et BarHandler sont des classes applicatives exposant handle(Command $command): void.

use Psr\Container\ContainerInterface;
use Psr\Log\LoggerInterface;
use Symfony\Contracts\Service\ServiceSubscriberInterface;

final class Command
{
    public function __construct(private string $handler) {}

    public function handlerId(): string
    {
        return $this->handler;
    }
}

class CommandBus implements ServiceSubscriberInterface
{
    public function __construct(private ContainerInterface $locator) {}

    public static function getSubscribedServices(): array
    {
        return [
            'App\Handler\FooHandler',
            '?App\Handler\BarHandler',       // facultatif
            'logger' => LoggerInterface::class,
        ];
    }

    public function handle(Command $c): void
    {
        $this->locator->get($c->handlerId())->handle($c);
    }
}

Le bus doit être enregistré et autowiré, avec l'autoconfiguration FrameworkBundle qui le reconnaît comme subscriber, ou le tag équivalent explicitement configuré. Le type PSR-11 ContainerInterface reçoit alors le locator préparé pour ce subscriber, pas le container global.

Si FooHandler et le logger sont disponibles, le bus peut être construit même si BarHandler manque. handle(new Command('App\Handler\FooHandler')) récupère FooHandler et lui transmet le même Command. L'entrée locale 'logger' est destinée à la journalisation, pas à être sélectionnée comme handler : la liste déclarée ne rend pas tous ses objets interchangeables.

Appeler la branche Bar absente ferait échouer get() ; le préfixe ? n'ajoute pas un objet vide et ne fait pas retourner automatiquement null. Une politique autorisant cette branche optionnelle doit tester sa disponibilité avant de la demander.

🌍 In Real Life

La situation : le responsable retire l'outil choisi, puis demande au poste correspondant de travailler ; un casier facultatif peut être absent.

L’équivalent dans Symfony : retrait → $locator->get(...) ; travail demandé ensuite → appel explicite à handle() ; casier facultatif absent → service déclaré avec ? mais indisponible.

Retour à la réalité technique : le bus local effectue la sélection puis l'appel. ? permet l'absence lors du câblage, pas un get() retournant automatiquement null. Il faut vérifier has() avant une branche facultative. Le logger déclaré n'est pas pour autant un handler interchangeable.

🧠 Comment le mémoriser : « Trouver, puis appeler. » Image mentale : la main retire l'outil avant le geste. Question-réflexe : la clé est-elle disponible et son objet respecte-t-il le contrat du traitement ?

⚠️ À ne pas confondre : ce CommandBus local et Messenger ; ni queue ni asynchronisme ne découlent du nom.

Le cas légitime : beaucoup de dependencies, une seule utilisée

À retenir en priorité
  1. Le préfixe rend l'absence acceptable.
  2. Le code doit tester la disponibilité.

Nous évitons ici de récupérer tous les handlers pour n'en utiliser qu'un. Le tableau suit les deux temps, en supposant la définition du bus conservée :

Situation Résultat
après construction du bus aucun handler construit
get(FooHandler::class) construit si nécessaire ; réutilisé aux appels suivants avec shared: true
?…\Missing absent has() rend false ; absent de getProvidedServices() et de count()
le même, sans ? la compilation échoue : « …has a dependency on a non-existent service… »
get() d'un service non déclaré « even though it exists in the app's container, the container inside … is a smaller service locator… »

La première ligne signifie « aucun handler demandé par cette injection », sous notre hypothèse d'absence de construction préalable. Un second get() de Foo réutilise normalement l'instance partagée. En revanche, la vérification d'une référence obligatoire concerne le graphe conservé ; un subscriber privé inutilisé peut être retiré avec ses dépendances avant certains contrôles.

getSubscribedServices() est statique parce que cette liste sert à préparer le câblage, avant l'existence de l'objet métier. Une clé textuelle comme 'logger' est un nom local ; sans clé explicite, le type déclaré sert de clé, sans son éventuel ?.

Le locator Symfony 8.0 implémente ServiceCollectionInterface, qui étend ServiceProviderInterface, Countable et IteratorAggregate. getProvidedServices() décrit les clés et types sans récupérer les services ; count() compte ces entrées. En revanche, foreach récupère les services au fil de l'itération : ce n'est pas seulement une inspection gratuite des noms.

Pour changer la cible derrière une clé locale, l'intégration accepte le tag container.service_subscriber avec key et id, ou un SubscribedService portant new Autowire(service: ...). La clé doit appartenir à la liste annoncée et la cible respecter son contrat : ce mécanisme ne doit pas servir à cacher un accès global.

🌍 In Real Life

La situation : lire la liste des casiers n'en sort aucun outil ; ouvrir successivement tous les casiers est une autre opération.

L’équivalent dans Symfony : inventaire → getProvidedServices() ; nombre d'entrées → count() ; retraits au fil du parcours → itération foreach du locator.

Retour à la réalité technique : les métadonnées n'obtiennent pas les instances. L'itération récupère les services ; une entrée présente n'est pas une preuve d'objet déjà construit. Le facultatif absent disparaît de l'inventaire. La vérification des références obligatoires concerne le graphe compilé conservé.

🧠 Comment le mémoriser : « Compter les noms n'ouvre pas les casiers. » Image mentale : une liste cochée devant des portes fermées. Question-réflexe : cette API lit-elle les métadonnées ou récupère-t-elle les objets ?

⚠️ À ne pas confondre : nombre d'entrées, nombre de résolutions et nombre d'instances distinctes.

Ce que cela n'est pas : le container

À retenir en priorité
  1. Privé n'interdit pas une référence déclarée.
  2. Le locator garde un accès restreint.

Le petit locator constitue une capacité d'accès bornée. Un service peut exister dans l'application sans être accessible par cette voie :

Container injecté Service locator
contenu accessible par get() services publics disponibles la liste déclarée
services privés inaccessibles accessibles s'ils sont déclarés
dependency manquante à l'exécution à la compilation (sans ?)

La dernière ligne compare une recherche dynamique globale à des références obligatoires déclarées dans un locator compilé et conservé. Elle ne garantit pas que toute erreur possible soit détectée avant usage : la clé choisie à l'exécution peut manquer, ou la factory du service disponible peut échouer.

Déclarer un privé dans le locator n'en fait pas un service public dans toute l'application. Inversement, rendre un service public ne l'ajoute pas à un locator qui ne le connaît pas. Le message « smaller service locator » invite à vérifier cette portée, pas à supprimer la restriction en injectant tout le container.

Dans un test unitaire, fournir un petit locator ou un double PSR-11 avec les seules clés nécessaires permet de vérifier les branches. Un locator construit manuellement avec des closures dépend de ces closures pour son partage : il ne reproduit pas automatiquement toutes les règles d'une définition Symfony compilée.

🌍 In Real Life

La situation : un outil existe dans la réserve générale, mais ne figure pas dans le petit ensemble attribué à ce poste.

L’équivalent dans Symfony : réserve générale → conteneur applicatif ; ensemble du poste → locator compilé ; outil non attribué → clé absente de ce locator.

Retour à la réalité technique : rendre le service public ne l'ajoute pas au locator. Un service privé peut au contraire y être accessible s'il est déclaré. Cette restriction d'assemblage ne remplace pas l'autorisation métier ; la factory d'un service présent peut encore échouer lors de sa récupération.

🧠 Comment le mémoriser : « Existe quelque part ne veut pas dire disponible ici. » Image mentale : deux inventaires différents. Question-réflexe : dans quel conteneur ou locator effectue-t-on ce get() ?

⚠️ À ne pas confondre : clé absente et service absent de toute l'application.

La forme courte : `#[AutowireLocator]`

À retenir en priorité
  1. Le tag définit les membres.
  2. Le locator sélectionne par key.

Pour une liste locale proche du constructeur, la classe peut éviter l'interface subscriber. Avec AutowireLocator importé depuis Symfony\Component\DependencyInjection\Attribute, les classes FooHandler, BazHandler et BarHandler importées, et le consommateur autowiré :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __construct(
    #[AutowireLocator([
        'foo' => FooHandler::class,
        'optionalBaz' => '?'.BazHandler::class,
        BarHandler::class,
    ])]
    private ContainerInterface $handlers,
) {}

Les clés sont ici foo, éventuellement optionalBaz, et le FQCN de BarHandler. Baz absent ne produit pas une entrée nullable à récupérer : cette entrée facultative disparaît. Foo et Bar doivent pouvoir être résolus pour un consommateur conservé.

L'export CLI peut appliquer le même choix à deux formats :

namespace App;

use Psr\Container\ContainerInterface;
use Symfony\Component\DependencyInjection\Attribute\AutowireLocator;

final class ExportChoice
{
    public function __construct(
        #[AutowireLocator([
            'csv' => CsvExporter::class,
            'json' => JsonExporter::class,
        ])]
        private ContainerInterface $exporters,
    ) {}

    public function select(string $format): object
    {
        if (!$this->exporters->has($format)) {
            throw new \InvalidArgumentException('Format inconnu');
        }

        return $this->exporters->get($format);
    }
}

Avec CsvExporter et JsonExporter enregistrés et autoloadables, select('json') rend JsonExporter sans demander CsvExporter par cette voie. select('xml') lève l'erreur applicative avant get(). La sélection ne réalise aucun export ; les deux classes doivent encore exposer le contrat qu'utilisera le code appelant.

#[AutowireLocator('app.handler')] ou !tagged_locator app.handler collecte plutôt une famille extensible. Les clés dépendent des attributs d'index, méthodes de défaut et métadonnées AsTaggedItem applicables, puis de l'identifiant de service en dernier recours. Ce n'est pas toujours un champ littéralement nommé index.

Une autre commodité, ServiceMethodsSubscriberTrait, associe les méthodes annotées #[SubscribedService] à une déclaration de dépendance. Avec la configuration subscriber appropriée, une méthode d'accès typée peut utiliser $this->container->get(__METHOD__). Sa clé par défaut est Classe::method, pas le nom court de la méthode ni simplement son type de retour. Le trait prépare la liste et le raccord du container ; l'attribute ne récupère pas seul l'objet.

🌍 In Real Life

La situation : le poste conserve près de lui une liste courte : « csv » et « json » ; les étiquettes locales désignent les équipements réels.

L’équivalent dans Symfony : liste près du poste → #[AutowireLocator] sur l'argument ; noms locaux → clés ; équipements cibles → services d'export enregistrés.

Retour à la réalité technique : l'attribute est traité pour le consommateur autowiré ; il ne récupère pas seul les services. select('json') retourne un objet sans lancer l'export. Une liste issue de tags suit ses règles d'indexation ; avec le trait décrit, la clé par défaut d'une méthode est Classe::method.

🧠 Comment le mémoriser : « Nom local, cible déclarée. » Image mentale : deux étiquettes reliées à deux casiers. Question-réflexe : quelle règle produit la clé que mon code demande ?

⚠️ À ne pas confondre : nom court de méthode, type retourné et clé __METHOD__.

Hériter : fusionner avec le parent

À retenir en priorité
  1. La redéfinition ne fusionne pas automatiquement.
  2. Conserver explicitement les services hérités.

Une variante de bus ajoute un handler mais continue d'utiliser les méthodes héritées. Sa liste remplace celle du parent si elle ne la fusionne pas :

return array_merge(parent::getSubscribedServices(), [
    'extra' => 'App\Handler\BazHandler',
]);

Ce corps de ChildBus::getSubscribedServices() suppose BazHandler enregistré et conserve Foo, le logger et l'éventuel Bar du parent. Sans parent::, la nouvelle liste peut être cohérente à la compilation tout en ne contenant plus Foo : une méthode héritée échouera lorsqu'elle le demandera.

Avec array_merge(), une clé textuelle répétée à droite remplace sa valeur précédente, tandis que les clés numériques sont réindexées. La fusion peut donc aussi surcharger volontairement un nom local. Testons une méthode héritée et une nouvelle branche, pas seulement la construction réussie de ChildBus.

🌍 In Real Life

La situation : un nouveau poste reprend les tâches d'un ancien et ajoute un outil ; remplacer sa liste par ce seul ajout ferait oublier l'équipement des tâches héritées.

L’équivalent dans Symfony : besoins hérités → parent::getSubscribedServices() ; nouvel outil → entrée ajoutée ; liste complète → fusion explicite.

Retour à la réalité technique : redéfinir la méthode remplace la déclaration du parent. array_merge() conserve les entrées, remplace les clés textuelles répétées par celles de droite et réindexe les clés numériques. Une compilation réussie ne prouve pas qu'une méthode héritée retrouvera toutes ses clés.

🧠 Comment le mémoriser : « Hériter du travail, conserver ses outils. » Image mentale : ancienne liste augmentée, non jetée. Question-réflexe : une méthode héritée demande-t-elle encore une clé oubliée ?

⚠️ À ne pas confondre : héritage des méthodes et fusion automatique des tableaux qu'elles retournent.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La liste est disponible sans instance.
  2. Elle participe à la compilation.
  • Voir l’explication : La déclaration précède les objets métier.

    La déclaration précède les objets métier. getSubscribedServices() est statique ; elle n'est pas calculée à partir du lecteur courant de /blog/42.

  • Voir l’explication : Existence globale et accès local sont deux questions.

    Existence globale et accès local sont deux questions. Un service public peut rester inconnu de ce locator ; un privé déclaré peut y être accessible sans devenir public partout.

  • Voir l’explication : Différer un accès n'efface pas un objet déjà construit.

    Différer un accès n'efface pas un objet déjà construit. La définition cible et sa factory gouvernent le partage. Un parcours foreach peut demander plusieurs services, contrairement à la simple lecture de leurs métadonnées.

  • Voir l’explication : Facultatif ne signifie pas résultat null garanti.

    Facultatif ne signifie pas résultat null garanti. Dans le locator compilé, une référence facultative absente disparaît ; has() rend false et un get() direct de cette clé échoue. Une référence obligatoire du graphe conservé doit être résolue.

  • Voir l’explication : Une liste d'enfant ne conserve pas implicitement les besoins hérités.

    Une liste d'enfant ne conserve pas implicitement les besoins hérités. Fusionnons le parent, puis contrôlons les clés textuelles redéfinies et une méthode qui utilise encore une dépendance du parent.

  • Voir l’explication : Compter les entrées ne compte pas les instances construites.

    Compter les entrées ne compte pas les instances construites. L'optionnel absent n'apparaît ni dans getProvidedServices() ni dans count(). Une entrée présente peut exister avant toute récupération de l'objet correspondant.

Fiche express

À mémoriser

À retenir en priorité
  1. Le locator change l'accès, pas le partage.
  2. La definition du service reste déterminante.

Pour choisir un traitement d'import sans ouvrir tout le container :

  1. Justifier le choix différé plutôt qu'une injection directe plus simple.
  2. Déclarer les clés et contrats du petit ensemble autorisé.
  3. Raccorder le subscriber ou utiliser AutowireLocator sur le consommateur autowiré.
  4. Tester la présence d'une branche facultative avant de la demander.
  5. Distinguer récupération, partage, inventaire et appel métier.
  6. Préserver les besoins hérités lors de l'extension d'un subscriber.

Le blog et ses commandes peuvent ainsi partager des services bien définis sans confondre préparation du container, sélection d'un collaborateur et exécution de son travail.
