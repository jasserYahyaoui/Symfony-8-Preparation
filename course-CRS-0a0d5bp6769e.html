Objectif

Recevoir un petit container restreint quand injecter tout est absurde, sans retomber dans la récupération de services. Le cas particulier d'AbstractController est traité dans son propre item (Module 04 — Contrôleurs).

L'essentiel

À comprendre

À retenir en priorité
  1. Le locator limite les dependencies accessibles.
  2. La création est différée au get().

Une class qui dispatche vers dix handlers n'en utilise qu'un par appel. Un service locator est un petit container limité aux services qu'elle déclare. Il diffère leur récupération jusqu'au get() ; un service déjà construit et partagé est réutilisé. Ce n'est pas le container de l'application : ses dependencies restent lisibles et vérifiées à la compilation.

Le schéma

À retenir en priorité
  1. Le locator n'est pas le container global.
  2. Son contrat est une liste explicite.

Les rectangles bleus représentent le travail effectué, les losanges orange une décision, les capsules un résultat (vert) ou un échec (rouge). La première vue décrit la compilation ; la seconde, les appels à l'exécution, pas un héritage. Hypothèse du tableau suivant : handlers partagés (shared: true, le défaut), pas encore construits ailleurs. shared: false demande une nouvelle instance à chaque récupération ; le locator ne change pas cette configuration.

Le fil rouge : un CommandBus

À retenir en priorité
  1. Le bus connaît les keys de sélection.
  2. Les handlers inutilisés restent non construits.
class CommandBus implements ServiceSubscriberInterface
{
    public function __construct(private ContainerInterface $locator) {}

    public static function getSubscribedServices(): array
    {
        return [
            'App\Handler\FooHandler',
            '?App\Handler\BarHandler',       // facultatif
            'logger' => LoggerInterface::class,
        ];
    }

    public function handle(Command $c): void
    {
        $this->locator->get($c->handlerId())->handle($c);
    }
}

Le cas légitime : beaucoup de dependencies, une seule utilisée

À retenir en priorité
  1. Le préfixe rend l'absence acceptable.
  2. Le code doit tester la disponibilité.

après construction du bus aucun handler construit
get(FooHandler::class) construit si nécessaire ; réutilisé aux appels suivants avec shared: true
?…\Missing absent has() rend false ; absent de getProvidedServices() et de count()
le même, sans ? la compilation échoue : « …has a dependency on a non-existent service… »
get() d'un service non déclaré « even though it exists in the app's container, the container inside … is a smaller service locator… »
  • getSubscribedServices() est statique ; une key ('logger') donne un nom local.
  • Le locator est aussi un ServiceProviderInterface : getProvidedServices(), count(), foreach.
  • Viser un autre service derrière une key : un tag container.service_subscriber avec key et id, ou un SubscribedService avec new Autowire(service: …).

  2. Le locator garde un accès restreint.

La forme courte : `#[AutowireLocator]`

À comprendre

À retenir en priorité
  1. Le tag définit les membres.
  2. Le locator sélectionne par key.

C'est quoi ?

#[AutowireLocator] demande un locator directement sur un argument de constructeur. On peut fournir une liste explicite de services, avec des clés locales, ou le nom d'un tag dont les services doivent être collectés.

À quoi ça sert ?

La liste des dépendances reste près de l'argument sans imposer l'implémentation de ServiceSubscriberInterface. Cette forme convient à un petit ensemble de choix locaux ; un tag convient mieux lorsque des extensions doivent pouvoir ajouter de nouveaux candidats.

Où dans Symfony ?

L'attribut appartient à DependencyInjection et requiert le câblage automatique du service consommateur. Les valeurs précédées de ? sont facultatives. La liste ne rend pas les services publics et ne fournit pas un accès illimité au container.

Comment, étape par étape ?

  1. Enregistrer les services candidats.
  2. Déclarer leurs clés et types dans l'attribut.
  3. Laisser le container construire le locator restreint.
  4. Vérifier la clé à l'exécution avant d'appeler le candidat sélectionné.

Exemple concret PHP

CsvExporter et JsonExporter sont des services de l'application ; leur contrat doit être compatible avec l'usage du consommateur.

<?php
namespace App;
use Psr\Container\ContainerInterface;
use Symfony\Component\DependencyInjection\Attribute\AutowireLocator;
final class ExportChoice
{
    public function __construct(
        #[AutowireLocator([
            'csv' => CsvExporter::class,
            'json' => JsonExporter::class,
        ])]
        private ContainerInterface $exporters,
    ) {}
    public function select(string $format): object
    {
        if (!$this->exporters->has($format)) {
            throw new \InvalidArgumentException('Format non pris en charge : '.$format);
        }
        return $this->exporters->get($format);
    }
}

select('csv') demande seulement l'exporter CSV ; select('xml') est refusé. Contre-exemple : transmettre un identifiant de service arbitraire fourni par l'utilisateur en supposant qu'il sera disponible. Correction : limiter les choix aux clés déclarées et refuser explicitement les autres. Le locator choisit un objet ; il ne valide pas à lui seul les données à exporter.

Passage canonique conservé

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __construct(
    #[AutowireLocator([
        'foo' => FooHandler::class,
        'optionalBaz' => '?'.BazHandler::class,
        BarHandler::class,
    ])]
    private ContainerInterface $handlers,
) {}
  • Sans implémenter l'interface. #[AutowireLocator('app.handler')] le construit depuis un tag : keys = index du service, sinon son identifier.
  • En YAML : !tagged_locator app.handler, ou un service ServiceLocator déclaré à la main.
  • ServiceMethodsSubscriberTrait : une method #[SubscribedService] par service, de key __METHOD__.

Hériter : fusionner avec le parent

À comprendre

À retenir en priorité
  1. La redéfinition ne fusionne pas automatiquement.
  2. Conserver explicitement les services hérités.

C'est quoi ?

Redéfinir getSubscribedServices() remplace la méthode héritée. PHP ne fusionne pas automatiquement les tableaux retournés par le parent et l'enfant. Si des méthodes héritées utilisent les services du parent, ces références doivent rester dans la déclaration finale.

À quoi ça sert ?

La fusion permet à une sous-classe d'ajouter un besoin sans casser les fonctionnalités héritées. L'oubli peut rester invisible à la compilation : la liste de l'enfant est cohérente en elle-même, mais la méthode du parent échouera lorsqu'elle demandera une clé disparue.

Où dans Symfony ?

Le problème concerne notamment les sous-classes d'AbstractController, mais le principe vaut pour tout service subscriber hérité. Une clé textuelle redéfinie dans le second tableau d'array_merge() remplace sa valeur précédente : la fusion peut donc également effectuer une surcharge volontaire.

Comment, étape par étape ?

  1. Récupérer la liste du parent.
  2. Ajouter les dépendances propres à l'enfant.
  3. Vérifier les clés communes pour éviter une surcharge accidentelle.
  4. Tester une méthode héritée, pas seulement la nouvelle méthode.

Exemple concret PHP

Dans une application FrameworkBundle, ce controller étend sa liste sans perdre les services utilisés par les méthodes de base.

<?php
namespace App\Controller;
use App\FormatterInterface;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
final class PreviewController extends AbstractController
{
    public static function getSubscribedServices(): array
    {
        return array_merge(parent::getSubscribedServices(), [
            'formatter' => FormatterInterface::class,
        ]);
    }
}

Le service FormatterInterface doit être enregistré. Contre-exemple : retourner seulement ['formatter' => FormatterInterface::class] puis appeler une méthode héritée qui utilise un autre service. Correction : conserver la liste parent comme ci-dessus. L'héritage d'une méthode ne garantit pas l'héritage des données produites par une méthode remplacée.

Passage canonique conservé
return array_merge(parent::getSubscribedServices(), ['…']);

Un ChildBus qui oublie parent:: perd en silence les services du parent : has(FooHandler::class) vaut false, sans erreur avant l'usage.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La liste est disponible sans instance.
  2. Elle participe à la compilation.
  • Déclarer getSubscribedServices() statique

    getSubscribedServices() est statique.

  • Voir l’explication : Le locator n'est pas le container

    Le locator n'est pas le container : il est restreint à la liste déclarée, et le dit dans son message d'erreur.

  • Voir l’explication : Le locator récupère les services à la demande

    Le locator récupère les services à la demande — partagés par défaut, mais pas si leur définition indique shared: false.

  • Voir l’explication : Sans ?, un service manquant bloque la compilation

    Sans ?, un service manquant bloque la compilation ; avec ?, has() rend false.

  • Conserver les services souscrits du parent

    En inheritance, il faut fusionner avec parent::.

  • Voir l’explication : Un service facultatif absent disparaît du locator

    Un service facultatif absent disparaît du locator : exécuté, getProvidedServices() ne le liste pas et count() ne le compte pas.

Fiche express

À mémoriser

À retenir en priorité
  1. Le locator change l'accès, pas le partage.
  2. La definition du service reste déterminante.

Si tu dois retenir seulement 6 choses :

  • getSubscribedServices() est statique.
  • Locator ≠ container : la liste déclarée, privés compris.
  • Récupéré au get(), partagé si shared: true.
  • Sans ? : échec à la compilation ; avec ? : has() faux.
  • #[AutowireLocator] : sans l'interface, depuis une liste ou un tag.
  • Inheritance : array_merge(parent::…).

Moyen mnémotechnique : « Déclarer, puis demander » — injecter le locator ne demande pas à lui seul la construction de ses services.
