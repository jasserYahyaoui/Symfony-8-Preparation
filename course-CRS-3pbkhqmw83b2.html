Objectif

Réagir au cycle de vie d'un message sans écrire de middleware, savoir quel event porte quelle information — et ce qu'un listener peut y changer. Le mécanisme d'abonnement lui-même est traité dans Event dispatcher and kernel events.

L'essentiel

À comprendre

À retenir en priorité
  1. Le worker n'existe pas dans ce trajet.
  2. Le middleware couvre chaque dispatch.

Messenger émet des events à deux endroits seulement : à l'envoi vers un transport et dans le worker. Un message traité en synchrone, non routé, n'en émet aucun. Un listener peut lire l'échec, savoir s'il sera rejoué — s'il écoute au bon moment —, et même empêcher le traitement d'un message reçu.

Exemple concret

À retenir en priorité
  1. Le moment d'écoute compte.
  2. Un échec intermédiaire n'est pas un abandon.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[AsEventListener]
public function onFailed(WorkerMessageFailedEvent $event): void
{
    if (!$event->willRetry()) {      // juste à la priority par défaut, 0
        $this->alerting->notify($event->getThrowable());
    }
}

Au premier échec d'un message qui sera rejoué, willRetry() vaut true : pas d'alerte. Au dernier, false : l'alerte part.

Event ou middleware

À retenir en priorité
  1. Les events de worker couvrent seulement leur contexte.
  2. Le bus est la frontière commune.

La frontière n'est pas « observer contre modifier » : plusieurs events se modifient. Elle tient à où ils sont émis.

  • La chaîne de middleware est traversée à chaque dispatch(), message synchrone compris.
  • Les events ne sont émis qu'à l'envoi vers un transport et dans un worker : SendMessageToTransportsEvent exige des senders.

Pour agir sur tous les messages : un middleware. À l'envoi ou autour d'un worker : un listener suffit.

Le catalogue

À retenir en priorité
  1. Une loop vide émet toujours l'event.
  2. Éviter un traitement coûteux à chaque notification.

La documentation 8.0 en liste dix :

Event Quand
SendMessageToTransportsEvent avant l'envoi vers les transports
MessageSentToTransportsEvent après l'envoi
WorkerStartedEvent le worker démarre
WorkerRunningEvent à chaque loop, y compris à vide
WorkerMessageReceivedEvent un message vient d'être récupéré
WorkerMessageHandledEvent un message a été traité avec succès
WorkerMessageFailedEvent le handler a levé
WorkerMessageRetriedEvent le message est remis en file pour un retry
WorkerRateLimitedEvent le worker est ralenti par un limiteur de débit
WorkerStoppedEvent le worker s'arrête
  • Le code 8.0 en contient un onzième, WorkerMessageSkipEvent, émis par messenger:failed:retry quand on choisit de ne pas rejouer un message.
  • Un message routé vers deux transports donne un seul MessageSentToTransportsEvent : « the event is dispatched only once ».

Ce qu'un listener peut changer

À retenir en priorité
  1. Le listener peut interrompre ce traitement.
  2. Ce n'est pas un succès de handler.
Event Method Effet
SendMessageToTransportsEvent setEnvelope() le stamp ajouté voyage jusqu'au worker
WorkerMessageReceivedEvent shouldHandle(false) handler jamais appelé, ni succès ni échec
WorkerMessageReceivedEvent addStamps() le stamp atteint le handler

Après shouldHandle(false), l'event suivant est directement WorkerRunningEvent.

Les deux qui comptent

À comprendre

À retenir en priorité
  1. Les listeners sont ordonnés par priority.
  2. Lire après la décision de retry.

C'est quoi ?

Un event Messenger est une notification émise à un point précis du cycle d'envoi ou du worker. Un listener est le service appelé pour réagir à cette notification. Cela ne remplace pas le trajet de tous les messages dans les middlewares.

À quoi ça sert ?

On peut suivre l'activité, distinguer une tentative échouée d'un abandon et observer les arrêts. Le bon point d'observation évite de compter une boucle vide comme un message traité.

Où dans Symfony ?

  • Envoi : SendMessageToTransportsEvent, puis MessageSentToTransportsEvent.
  • Vie du worker : WorkerStartedEvent, WorkerRunningEvent, WorkerStoppedEvent.
  • Message : WorkerMessageReceivedEvent, puis WorkerMessageHandledEvent ou WorkerMessageFailedEvent ; un retry possède WorkerMessageRetriedEvent.
  • Limitation de débit : WorkerRateLimitedEvent.

Le catalogue documenté ne signifie pas qu'un dispatch synchrone déclenche ces events de worker.

Comment, étape par étape ?

  1. Choisir l'event dont le moment correspond à l'information recherchée.
  2. Sur WorkerRunningEvent, consulter isWorkerIdle() : l'event existe aussi quand la file est vide.
  3. Sur WorkerMessageFailedEvent, lire willRetry() après le listener de décision de retry, de priorité 100 dans Symfony 8.0. Une priorité plus élevée passe avant lui et peut donc observer une valeur encore fausse.
  4. Utiliser un middleware si la règle doit couvrir chaque dispatch, y compris synchrone.

Exemple concret PHP

Fonction d'observation appelée par un listener de priorité 0, après la décision standard de retry :

<?php
use Symfony\Component\Messenger\Event\WorkerMessageFailedEvent;

function failureStage(WorkerMessageFailedEvent $event): string
{
    return $event->willRetry() ? 'retry-planned' : 'no-retry-planned';
}

Le résultat décrit la décision observée à cet instant, pas la réussite future de l'envoi ni du handler. Contre-exemple : alerter « message définitivement perdu » dès chaque FailedEvent. Correction : distinguer la reprise prévue, la file d'échec et le résultat réel des opérations suivantes. Éviter aussi un accès réseau coûteux sur chaque RunningEvent : il serait répété même sans travail. Des events peuvent être modifiés ; la vraie frontière avec un middleware est leur point d'émission, pas simplement « observer contre modifier ».

Les deux qui comptent

WorkerMessageFailedEvent porte l'exception et willRetry(). Mais willRetry() est positionné par SendFailedMessageForRetryListener, à la priority 100 :

Listener willRetry() d'un message qui sera rejoué
priority 150 false
priority 0 (défaut) true

Ce même listener émet WorkerMessageRetriedEvent pendant la diffusion de l'échec : un listener de priority 0 sur l'échec écrit après celui du retry. Le failure transport écoute à -100.

WorkerRunningEvent est émis à chaque itération, même file vide ; isWorkerIdle() le signale. Un traitement coûteux placé là tourne en boucle.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'event décrit une tentative en échec.
  2. La suite dépend de la politique de retry.
  • Voir l’explication : WorkerRunningEvent se déclenche à vide

    WorkerRunningEvent se déclenche à vide : y placer du travail lourd le fait tourner en permanence.

  • Voir l’explication : WorkerMessageFailedEvent n'est pas un abandon

    WorkerMessageFailedEvent n'est pas un abandon : willRetry() dit s'il reste des tentatives — à condition d'écouter après la priority 100.

  • Voir l’explication : Un message non routé n'émet aucun event Messenger

    Un message non routé n'émet aucun event Messenger : seul un middleware le voit.

Fiche express

À mémoriser

À retenir en priorité
  1. Le retry a son event distinct.
  2. Il peut être émis pendant le traitement de l'event d'échec.

Si tu dois retenir seulement 7 choses :

  • Non routé : aucun event Messenger ; un middleware le voit.
  • À l'envoi : SendMessageToTransportsEvent, puis MessageSentToTransportsEvent, une fois.
  • Worker : started, received, handled ou failed, running, stopped.
  • willRetry() : après la priority 100.
  • WorkerMessageRetriedEvent : pendant l'échec, par le listener de retry.
  • WorkerRunningEvent : même à vide.
  • shouldHandle(false) : ni handler, ni succès, ni échec.

Moyen mnémotechnique : « envoyer, recevoir, réussir ou échouer, tourner, s'arrêter ».

envoi : SendMessageToTransports (setEnvelope) → MessageSentToTransports (×1) ; worker : Started → Received (shouldHandle, addStamps)
→ Handled | Failed (willRetry après 100 ; Retried émis dedans) → Running (même idle) → Stopped ; non routé : rien
