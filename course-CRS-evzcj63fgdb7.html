Objectifs d’apprentissage

  • Fixer la locale par le parameter _locale

Objectif

Savoir comment le framework fixe la locale de la Request à partir du routage, et ce que LocaleListener fait quand l'URL ne dit rien. La négociation HTTP détaillée appartient au Module 02 — Fondamentaux HTTP ; la translation elle-même au Module 16 — Internationalisation et traduction.

L'essentiel

○ À comprendre

À retenir en priorité
  1. RouterListener fournit l'attribute.
  2. LocaleListener applique ensuite la locale.

La locale de la Request vient de l'URL : un parameter _locale dans le path, ou une route localisée, que LocaleListener applique sur kernel.request à la priority 16. Quand l'URL ne dit rien, il consulte Accept-Language — seulement si on l'a activé — puis retombe sur framework.default_locale. Appeler setLocale() depuis un controller arrive trop tard.

Le schéma

L'exemple

▣ Exemple concret

À retenir en priorité
  1. Le parameter réservé _locale transporte la locale depuis le path.
  2. LocaleListener l'applique pendant kernel.request, sans appel dans le controller.
contact:
    path: '/{_locale}/contact'
    controller: App\Controller\ContactController::contact
    requirements:
        _locale: en|fr|de

Une visite de /fr/contact fixe la locale fr sans une ligne de code.

Par le parameter `_locale`

La valeur appariée est automatiquement posée sur la Request : $request->getLocale() la retourne. Le requirement gagne à être un parameter de configuration, pour ne pas répéter la liste des locales. LocaleListener écoute kernel.request à la priority 16, après RouterListener (32) dont il lit l'attribute, et recopie la locale dans le contexte du router.

Repère de l’exemple : The captured _locale route parameter, applied by LocaleListener. Le parameter réservé _locale transporte la locale depuis le path. LocaleListener l'applique pendant kernel.request, sans appel dans le controller.

Par des paths localisés

À retenir en priorité
  1. Chaque variante impose sa locale à la Request.
  2. La génération peut choisir la variante de locale courante.

Une route peut définir un path par locale :

class ExampleController
{
    #[Route(path: [
        'en' => '/about-us',
        'nl' => '/over-ons',
        '/about-us',        // repli pour toute autre locale
    ], name: 'about_us')]
    public function __invoke(): \Symfony\Component\HttpFoundation\Response
    {
        return new \Symfony\Component\HttpFoundation\Response();
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

AttributeClassLoader crée about_us.en et about_us.nl, chacune avec la default value _locale, un requirement et _canonical_route ; l'entrée sans key devient about_us, sans locale. En attributes, l'array passe par le parameter nommé path. Une route localisée appariée impose sa locale pour toute la Request. À la génération, generate('about_us') vise la route de la locale courante ; pour fr_CA, il essaie fr, puis la route sans suffixe.

Deux portes de musée mènent à la même exposition mais choisissent la langue du parcours. Les paths localisés jouent ce rôle : la locale s'applique à la Request, pas seulement au titre de la page.

Quand l'URL ne dit rien

À retenir en priorité
  1. _locale est prioritaire.
  2. La sélection par header exige une configuration explicite.

LocaleListener décide dans cet ordre : un attribute _locale l'emporte ; sinon, si framework.set_locale_from_accept_language vaut true, la langue préférée du header Accept-Language parmi framework.enabled_locales, et la Response reçoit Vary: Accept-Language ; sinon framework.default_locale, en par défaut. L'option vaut false par défaut : sans elle, le header ne compte pas.

Le piège de l'instant

À retenir en priorité
  1. La locale se fixe avant le traitement applicatif.
  2. Un listener approprié précède LocaleListener.

$request->setLocale() dans un controller arrive trop tard : le translator est déjà configuré. La locale se fixe par l'URL, par un listener, ou par setLocale() sur le service translator. Un listener maison doit passer avant LocaleListener, donc porter une priority supérieure à 16 — lisible par debug:event kernel.request.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Fixer la locale depuis un controller arrive trop tard.

    Fixer la locale depuis un controller arrive trop tard. Le translator est déjà configuré : la locale se fixe par l'URL, par un listener, ou sur le service de translation lui-même.

  • Voir l’explication : Un listener maison doit passer avant celui du framework

    Un listener maison doit passer avant celui du framework, donc porter une priority plus élevée — priority plus grande veut dire plus tôt.

  • Voir l’explication : Accept-Language n'agit pas par défaut.

    Accept-Language n'agit pas par défaut. Il faut set_locale_from_accept_language: true, et un _locale venu de l'URL passe toujours devant.

  • Voir l’explication : Une route localisée impose sa locale pour toute la Request

    Une route localisée impose sa locale pour toute la Request, pas seulement pour le rendu du template.

Application

À retenir en priorité
  1. La locale se fixe avant le traitement applicatif.
  2. Un listener approprié précède LocaleListener.
  3. _locale est prioritaire.
  4. La sélection par header exige une configuration explicite.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • _locale dans le path → locale posée par LocaleListener (16).
  • Après RouterListener (32), dont il lit l'attribute.
  • Ordre : _locale → Accept-Language si activé → default_locale.
  • Paths localisés : nom.locale + nom pour l'entrée sans key.
  • Génération : locale → langue seule → route sans suffixe.
  • setLocale() en controller : trop tard ; listener de priority > 16.

Moyen mnémotechnique : « L'URL parle d'abord, le navigateur s'il est invité ».
