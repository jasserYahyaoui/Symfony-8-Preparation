Objectif

Préparer les dependencies, l'environment de production, le cache et le redémarrage des process longs. Distinguer installation des packages et optimisation de l'autoloading ; aucune opération sur un stockage applicatif n'est enseignée ici.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le cache dépend de l'environment.
  2. La préparation doit viser prod.

Une préparation de production doit rendre disponibles le code et ses dependencies, choisir les paramètres de production, puis reconstruire le cache de cet environment. Les process longs doivent charger la nouvelle version. Symfony n'impose pas un produit unique de deployment.

Le schéma

À retenir en priorité
  1. Le cache compile l'application disponible.
  2. Les dependencies doivent être présentes.

Exemple de séquence à comprendre, sans l'exécuter ici : installer les dependencies de production avec un autoloader optimisé, fixer APP_ENV=prod et APP_DEBUG=0, préparer le cache de production, puis renouveler les process longs. Les scripts doivent s'arrêter si une étape nécessaire échoue.

Les quatre étapes du tronc commun

À retenir en priorité
  1. La configuration doit correspondre à prod.
  2. Les process longs doivent charger la nouvelle version.
  1. Rendre disponibles le code et les dependencies de production.
  2. Fournir la configuration correspondant à l'environment de production.
  3. Vider ou préchauffer le cache de cet environment.
  4. Renouveler les process longs pour qu'ils chargent la nouvelle version.

Le titre canonique est conservé ; les opérations sur des données applicatives de l'original sont exclues de ce périmètre.

Les deux commands à connaître exactement

À retenir en priorité
  1. Ne pas confondre les responsabilités.
  2. Une optimisation ne choisit pas les packages.
  • composer install --no-dev --optimize-autoloader : --no-dev n'installe pas les packages de développement ; --optimize-autoloader construit une class map, pour les performances de l'autochargeur.
  • APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear : le cache dépend de l'environment ; vider celui de dev ne sert à rien en production.
  • Si composer install échoue sur class not found, exporter APP_ENV=prod avant de le relancer, pour que les scripts post-install-cmd tournent en prod.
  • --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler, en dependency ordinaire.

Les variables d'environment en production

À retenir en priorité
  1. Le dump prépare les valeurs d'environment.
  2. Il doit être régénéré lorsque ces valeurs changent.
  • De vraies variables, posées par le serveur web, l'hébergeur ou la ligne de command, ou un file .env.prod.local : la documentation ne départage pas.
  • composer dump-env prod produit un .env.local.php qui prend le pas sur les autres files ; --empty génère la même structure sans valeurs. Sans Composer sur le serveur, la command dotenv:dump fait la même chose.
  • Sur un serveur sans la CLI Symfony, symfony/requirements-checker vérifie les prérequis.
  • kernel.project_dir est le directory du composer.json principal ; Kernel::getProjectDir() remonte depuis le kernel et, sans en trouver, rend le directory du kernel, sans erreur : kernel dans app/src/, aucun composer.json, le résultat est app/src — silencieusement faux. Un deployment sans composer.json redéfinit donc cette method.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Un serveur de production ne fixe pas automatiquement la command.
  2. Le réglage d'environment reste nécessaire.
  • Voir l’explication : --no-dev et --optimize-autoloader répondent à deux besoins différents

    --no-dev et --optimize-autoloader répondent à deux besoins différents : ne pas installer le superflu, et accélérer l'autochargement.

  • Voir l’explication : cache:clear s'exécute avec APP_ENV=prod

    cache:clear s'exécute avec APP_ENV=prod, pas avec l'environment courant.

  • Voir l’explication : .env.local.php l'emporte

    .env.local.php l'emporte sur les autres files de configuration.

  • Voir l’explication : kernel.project_dir vient de l'emplacement du composer.json

    kernel.project_dir vient de l'emplacement du composer.json ; sans lui, le directory du kernel est rendu sans erreur.

  • Voir l’explication : --no-dev ne retire pas dump()

    --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler.

  • Voir l’explication : Aucun outil n'est prescrit

    Aucun outil n'est prescrit : FTP, repository versionné, PaaS ou script de deployment sont tous cités.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Le contrat porte sur les étapes nécessaires.
  2. L'outil dépend de l'infrastructure.
  • --no-dev omet les packages de développement.
  • --optimize-autoloader optimise la résolution des classes.
  • Le cache doit être préparé pour prod, avec debug désactivé.
  • Un dump d'environment doit correspondre aux valeurs et à l'environment attendus.
  • Les process longs doivent être renouvelés.
  • Aucun outil de deployment unique n'est imposé.
