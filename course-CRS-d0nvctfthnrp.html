Objectif

Connaître les responsabilités d'un deployment Symfony, les étapes applicables au projet et les commands qui les réalisent.

L'essentiel

À comprendre

À retenir en priorité
  1. Le cache dépend de l'environment.
  2. La préparation doit viser prod.

La documentation ne prescrit aucun outil de deployment, mais quatre étapes à examiner : transférer le code, installer les dependencies, migrer les données si nécessaire, renouveler le cache. Deux commands sont à connaître exactement, et les variables d'environment de production peuvent être compilées dans un .env.local.php.

Le schéma

À retenir en priorité
  1. Le cache compile l'application disponible.
  2. Les dependencies doivent être présentes.

Bleu : préparation ; ambre : besoin de migration ; vert : état vérifié. Vue d'une release préparée à part, pas un script universel à exécuter sur le répertoire actif. Ancien et nouveau code peuvent coexister pendant la bascule : prévoir compatibilité des données, retour arrière et renouvellement des workers.

L'exemple : un script de deployment

Exemple concret

À retenir en priorité
  1. Les deux flags répondent à des besoins différents.
  2. L'un réduit les packages, l'autre optimise leur chargement.
set -e
APP_ENV=prod APP_DEBUG=0 composer install --no-dev --optimize-autoloader
composer dump-env prod

Séquence illustrative pour une release séparée, avec Symfony Flex fournissant composer dump-env, pas un script universel à exécuter ici. Coordonner les adaptations externes des données si nécessaires (hors du contrat de ce cours), les contrôles de santé, la bascule et le renouvellement des processus longs. Arrêter la séquence lorsqu'une étape nécessaire échoue.

Les quatre étapes du tronc commun

À retenir en priorité
  1. La configuration doit correspondre à prod.
  2. Les process longs doivent charger la nouvelle version.
  1. Rendre disponibles le code et les dependencies de production.
  2. Fournir la configuration correspondant à l'environment de production.
  3. Vider ou préchauffer le cache de cet environment.
  4. Renouveler les process longs pour qu'ils chargent la nouvelle version.

Le titre canonique est conservé ; les opérations sur des données applicatives de l'original sont exclues de ce périmètre.

Les deux commands à connaître exactement

À comprendre

À retenir en priorité
  1. Ne pas confondre les responsabilités.
  2. Une optimisation ne choisit pas les packages.

C'est quoi ?

Déployer prépare une version utilisable par l'environnement de production. Les quatre étapes typiques de la documentation sont transférer le code, installer ses dependencies, mettre à jour les structures de données si nécessaire, puis préparer le cache. Elles ne constituent pas une recette universelle autorisant toute migration sans analyse.

À quoi ça sert ?

Une version de code, ses packages et son cache doivent correspondre. Les tests, la possibilité de revenir à une version précédente et la relance des processus longs restent des préoccupations d'exploitation, même si deux commandes techniques sont connues par cœur.

Où dans Symfony ?

Composer installe les packages ; cache:clear prépare le cache Symfony de l'environment choisi. --no-dev exclut les packages de développement ; --optimize-autoloader construit une class map, table de correspondance des classes vers leurs fichiers. Ces options répondent à deux problèmes différents.

Comment, étape par étape ?

  1. Préparer la nouvelle version et sa configuration de production ; vérifier les prérequis et les changements de données nécessaires.
  2. Installer les dependencies avec l'environment prod déjà disponible pour les scripts Composer.
  3. Appliquer les changements de données selon la procédure adaptée, puis préparer le cache de la même version.
  4. Relancer les workers concernés et vérifier le comportement réel. Si une étape échoue, interrompre la procédure au lieu de déclarer la version prête.

Exemple concret en shell

Deux commandes à lire depuis le répertoire d'une application préparée ; elles ne sont pas exécutées ici :

APP_ENV=prod APP_DEBUG=0 composer install --no-dev --optimize-autoloader
APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear

Les affectations s'appliquent à chaque commande, d'où leur répétition. APP_DEBUG=0 choisit le mode sans débogage, pas la suppression des erreurs ou de leur journalisation.

Les variables de production peuvent être fournies réellement par l'exploitation ou par des fichiers locaux adaptés. composer dump-env prod prépare un .env.local.php pour éviter leur analyse répétée ; un dump périmé doit être régénéré. dotenv:dump exige son enregistrement si la commande n'est pas disponible. Aucun secret ni fichier d'environment n'est lu dans cette mission.

Contre-exemple : vider le cache de dev sur un serveur de production, ou croire que l'optimisation de l'autoloader exclut les packages de développement. Correction : sélectionner explicitement prod et appliquer séparément les deux options. Une application sans son composer.json habituel doit aussi vérifier la détermination de kernel.project_dir ; ne pas supposer que le nom du dossier déployé suffit.

Déploiement 8.0.

Passage canonique conservé
  • composer install --no-dev --optimize-autoloader : --no-dev n'installe pas les packages de développement ; --optimize-autoloader construit une class map, pour les performances de l'autochargeur.
  • APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear : le cache dépend de l'environment ; vider celui de dev ne sert à rien en production.
  • Si composer install échoue sur class not found, exporter APP_ENV=prod avant de le relancer, pour que les scripts post-install-cmd tournent en prod.
  • --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler, en dependency ordinaire.

Les variables d'environment en production

À retenir en priorité
  1. Le dump prépare les valeurs d'environment.
  2. Il doit être régénéré lorsque ces valeurs changent.
  • De vraies variables, posées par le serveur web, l'hébergeur ou la ligne de command, ou un file .env.prod.local : la documentation ne départage pas.
  • composer dump-env prod produit un .env.local.php qui prend le pas sur les autres files ; --empty génère la même structure sans valeurs. Sans Composer sur le serveur, la command dotenv:dump fait la même chose.
  • Sur un serveur sans la CLI Symfony, symfony/requirements-checker vérifie les prérequis.
  • kernel.project_dir est le directory du composer.json principal ; Kernel::getProjectDir() remonte depuis le kernel et, sans en trouver, rend le directory du kernel, sans erreur : kernel dans app/src/, aucun composer.json, le résultat est app/src — silencieusement faux. Un deployment sans composer.json redéfinit donc cette method.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un serveur de production ne fixe pas automatiquement la command.
  2. Le réglage d'environment reste nécessaire.
  • Voir l’explication : --no-dev et --optimize-autoloader répondent à deux besoins différents

    --no-dev et --optimize-autoloader répondent à deux besoins différents : ne pas installer le superflu, et accélérer l'autochargement.

  • Voir l’explication : cache:clear s'exécute avec APP_ENV=prod

    cache:clear s'exécute avec APP_ENV=prod, pas avec l'environment courant.

  • Voir l’explication : Un dump Dotenv compatible évite les fichiers texte d'environnement

    Un dump Dotenv compatible évite les fichiers texte d'environnement ; il ne remplace ni security.yaml ni une vraie variable système prioritaire.

  • Voir l’explication : kernel.project_dir vient de l'emplacement du composer.json

    kernel.project_dir vient de l'emplacement du composer.json ; sans lui, le directory du kernel est rendu sans erreur.

  • Voir l’explication : --no-dev ne retire pas dump()

    --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler.

  • Voir l’explication : Aucun outil n'est prescrit

    Aucun outil n'est prescrit : FTP, repository versionné, PaaS ou script de deployment sont tous cités.

Fiche express

À mémoriser

À retenir en priorité
  1. Le contrat porte sur les étapes nécessaires.
  2. L'outil dépend de l'infrastructure.
  • --no-dev omet les packages de développement.
  • --optimize-autoloader optimise la résolution des classes.
  • Le cache doit être préparé pour prod, avec debug désactivé.
  • Un dump d'environment doit correspondre aux valeurs et à l'environment attendus.
  • Les process longs doivent être renouvelés.
  • Aucun outil de deployment unique n'est imposé.
