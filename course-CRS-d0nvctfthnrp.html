Objectif

Les tests de /blog/42 passent et la configuration est maîtrisée. Copier les fichiers ne suffit pourtant pas : un worker peut encore importer avec l'ancien code, ou le cache avoir été préparé pour dev. Déployer consiste à rendre une version cohérente réellement utilisable, puis à vérifier le comportement qui sera servi aux lecteurs.

L'essentiel

À comprendre

À retenir en priorité
  1. Le cache dépend de l'environment.
  2. La préparation doit viser prod.

La documentation ne prescrit aucun outil de deployment, mais quatre étapes à examiner : transférer le code, installer les dependencies, migrer les données si nécessaire, renouveler le cache. Deux commands sont à connaître exactement, et les variables d'environment de production peuvent être compilées dans un .env.local.php.

Une release est cet ensemble identifié de code, dépendances et configuration. Symfony 8.0 exige PHP au moins 8.4 ; les exemples de ce parcours restent sur l'API PHP 8.4. Vérifier la plateforme de destination, pas seulement la version de PHP qui a exécuté les tests.

Le schéma

À retenir en priorité
  1. Le cache compile l'application disponible.
  2. Les dependencies doivent être présentes.

Le catalogue en mémoire de cet exercice n'a aucune migration de base de données à lancer. La branche « migration nécessaire » reste un repère général pour les projets qui en ont besoin, pas une nouvelle dépendance du blog.

Bleu : préparation ; ambre : besoin de migration ; vert : état vérifié. Vue d'une release préparée à part, pas un script universel à exécuter sur le répertoire actif. Ancien et nouveau code peuvent coexister pendant la bascule : prévoir compatibilité des données, retour arrière et renouvellement des workers.

Ces commandes emploient la syntaxe d'un shell POSIX. Elles supposent une release séparée, son composer.lock, ses contraintes Symfony 8.0 et les paramètres de production déjà disponibles. Elles ne sont pas exécutées ici.

Séquence illustrative pour une release séparée, avec Symfony Flex fournissant composer dump-env, pas un script universel à exécuter ici. Coordonner les adaptations externes des données si nécessaires (hors du contrat de ce cours), les contrôles de santé, la bascule et le renouvellement des processus longs. Arrêter la séquence lorsqu'une étape nécessaire échoue.

Résultats attendus : les dépendances verrouillées de production sont installées, le dump d'environnement est produit, puis le cache prod est reconstruit avec debug désactivé. Un code de sortie nul n'est pas encore un test HTTP. Après activation contrôlée, vérifier 42 → 200, 999 → 404, l'absence de profiler exposé et la prise en charge d'un import par les nouveaux workers si la branche Messenger est configurée.

Les quatre étapes du tronc commun

À retenir en priorité
  1. La configuration doit correspondre à prod.
  2. Les process longs doivent charger la nouvelle version.

🌍 In Real Life

La situation : le restaurant prépare une nouvelle carte avec les bons outils et les bonnes consignes avant de la proposer. Déposer les cartons n'est pas ouvrir le service.

L’équivalent dans Symfony : nouvelle carte → code de release ; outils compatibles → dépendances ; préparation du poste → caches/configuration ; relève du personnel → renouvellement des processus longs.

Retour à la réalité technique : la cohérence du déploiement du blog exige ces éléments ensemble. Une migration n'est pertinente que si les données l'exigent ; notre catalogue en mémoire n'en impose pas. L'analogie n'est pas une procédure à exécuter sur ce site statique.

🧠 Comment le mémoriser : « Livré n'est pas activé. » Image mentale : cartons fermés devant une salle prête à ouvrir. Question-réflexe : quel code les processus servent-ils réellement ?

⚠️ À ne pas confondre : succès des commandes préparatoires et comportement de la version active.

  1. Transférer le code sur le serveur de production.
  2. Installer les dependencies, par Composer, avant ou après le transfert.
  3. Exécuter les migrations, ou toute mise à jour de structure de données.
  4. Vider le cache, et éventuellement le préchauffer.

Pour notre parcours sans persistance, la troisième étape est une décision « non applicable », pas une commande fictive à exécuter. La liste documentaire et la checklist opérationnelle ne se remplacent pas : contrôler également la configuration prod, le renouvellement des processus longs et le comportement après bascule. Copier une classe ne change pas celle déjà chargée dans un worker ; son renouvellement doit être organisé.

Étiqueter une version, préparer une zone temporaire, lancer les tests, vider un cache externe : cités comme fréquents, non comme obligatoires.

Les deux commands à connaître exactement

À retenir en priorité
  1. Ne pas confondre les responsabilités.
  2. Une optimisation ne choisit pas les packages.

🌍 In Real Life

La situation : le restaurant tient un annuaire des équipements et un plan de préparation du service. Mettre à jour l'annuaire ne réorganise pas les postes.

L’équivalent dans Symfony : annuaire classe/fichier → class map Composer ; plan de services → conteneur compilé ; réponses conservées à l'accueil → cache HTTP.

Retour à la réalité technique : optimiser l'autoload ne prépare pas à lui seul le conteneur Symfony et ne purge pas le proxy HTTP. Le cache d'environnement doit être préparé pour l'environnement réellement ciblé.

🧠 Comment le mémoriser : « Annuaire, plan, copies : trois objets. » Image mentale : trois classeurs séparés. Question-réflexe : quel artefact cette commande modifie-t-elle ?

⚠️ À ne pas confondre : autoload optimisé, cache du framework et cache HTTP.

Composer prépare les classes disponibles ; Symfony peut ensuite préparer les services et autres caches de sa version. Une class map associe des noms de classes à leurs fichiers : elle ne choisit pas l'environnement, ne remplace pas le container compilé et ne purge pas un cache HTTP.

  • composer install --no-dev --optimize-autoloader : --no-dev n'installe pas les packages de développement ; --optimize-autoloader construit une class map, pour les performances de l'autochargeur.
  • APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear : le cache dépend de l'environment ; vider celui de dev ne sert à rien en production.
  • Si un script post-install-cmd recherche une classe de développement absente, vérifier notamment son environnement et fournir APP_ENV=prod avant de relancer. Ce diagnostic ne répare pas toute erreur class not found.
  • --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler, en dependency ordinaire.

Les affectations POSIX placées devant une commande ne fixent que son environnement ; d'où leur répétition dans le script. APP_DEBUG=0 ne supprime ni les erreurs ni leur journalisation. La préparation du cache ne doit pas être racontée comme un travail répété avant chaque article. Les caches applicatifs et les réponses HTTP déjà stockées demandent leur propre politique d'invalidation, distincte du cache de configuration.

Les variables d'environment en production

À retenir en priorité
  1. Le dump prépare les valeurs d'environment.
  2. Il doit être régénéré lorsque ces valeurs changent.

Le nouveau processus doit recevoir la configuration prévue dès son démarrage. Ne publier ni secrets ni dump contenant des secrets dans le dépôt ou le répertoire accessible au Web. Modifier un fichier sur disque ne recharge pas magiquement les valeurs déjà résolues par un processus long.

  • De vraies variables, posées par le serveur web, l'hébergeur ou la ligne de command, ou un file .env.prod.local : la documentation ne départage pas.
  • composer dump-env prod produit un .env.local.php : si ce dump est compatible avec l'environnement choisi, les fichiers texte ne sont plus analysés. Les vraies variables restent prioritaires par défaut. --empty génère une structure sans valeurs. Sans Composer sur le serveur, dotenv:dump exige l'enregistrement de DotenvDumpCommand ; installer Dotenv seul ne garantit pas cette commande.
  • Sur un serveur sans la CLI Symfony, symfony/requirements-checker vérifie les prérequis.
  • kernel.project_dir est le directory du composer.json principal ; Kernel::getProjectDir() remonte depuis le kernel et, sans en trouver, rend le directory du kernel, sans erreur : kernel dans app/src/, aucun composer.json, le résultat est app/src — silencieusement faux. Un deployment sans composer.json redéfinit donc cette method.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un serveur de production ne fixe pas automatiquement la command.
  2. Le réglage d'environment reste nécessaire.
  • Artefact déployé et processus utilisateur

    Un déploiement peut avoir toutes ses commandes « réussies » et servir encore l'ancien import ou le mauvais environnement. Pour chaque piège, identifier l'artefact changé et le processus qui va réellement l'utiliser.

  • Voir l’explication : --no-dev et --optimize-autoloader répondent à deux besoins différents

    --no-dev et --optimize-autoloader répondent à deux besoins différents : ne pas installer le superflu, et accélérer l'autochargement.

  • Voir l’explication : cache:clear s'exécute avec APP_ENV=prod

    cache:clear s'exécute avec APP_ENV=prod, pas avec l'environment courant.

  • Voir l’explication : Un dump Dotenv compatible évite les fichiers texte d'environnement

    Un dump Dotenv compatible évite les fichiers texte d'environnement ; il ne remplace ni security.yaml ni une vraie variable système prioritaire.

  • Voir l’explication : kernel.project_dir vient de l'emplacement du composer.json

    kernel.project_dir vient de l'emplacement du composer.json ; sans lui, le directory du kernel est rendu sans erreur.

  • Voir l’explication : --no-dev ne retire pas dump()

    --no-dev ne retire pas dump() d'une application FrameworkBundle : VarDumper arrive par ErrorHandler.

  • Voir l’explication : Aucun outil n'est prescrit

    Aucun outil n'est prescrit : FTP, repository versionné, PaaS ou script de deployment sont tous cités.

Le contrôle final revient au comportement initial : lire 42, traiter l'absence de 999, et conserver des diagnostics privés. Si un résultat diffère, repartir de la configuration et des outils de diagnostic, plutôt que répéter aveuglément toutes les commandes.

  • Quatre étapes : code, dependencies, migrations, cache.
