Objectif

Écrire un type de form, savoir quand le spécialiser par getParent() et quand l'ajouter comme field, et prévoir ce que fait une collection de types.

L'essentiel

○ À comprendre

À retenir en priorité
  1. add() imbrique des données.
  2. getParent() reprend un comportement au même niveau.

Un form est un type, comme chacun de ses fields. Pour réutiliser un type, trois voies : le spécialiser (getParent() : on hérite et on change quelques options), le composer (add() : il devient un field, ses données s'imbriquent), le répéter (CollectionType).

Le schéma

À retenir en priorité
  1. Le parent de form est une composition de comportement.
  2. Ses options sont héritées puis personnalisables.

L'exemple : l'achat

▣ Exemple concret

Revoir la règle : Le parent de form est une composition de comportement.

class ShippingType extends AbstractType       // spécialise un type existant
{
    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults([
            'choices' => ['Standard' => 'standard', 'Express' => 'express'],
            'expanded' => true,
        ]);
    }

    public function getParent(): string
    {
        return ChoiceType::class;
    }
}

// dans OrderType::buildForm()
$builder
    ->add('shipping', ShippingType::class)                    // spécialisé
    ->add('address', AddressType::class)                      // composé
    ->add('tags', CollectionType::class, ['entry_type' => TextType::class]); // répété

Ce qu'est un type

À retenir en priorité
  1. Un FormType décrit un élément composable.
  2. Un form peut donc devenir enfant d'un autre.

Un type décrit un field ou un form entier : la distinction n'existe pas. C'est ce qui permet d'imbriquer un form dans un autre. Un type étend AbstractType et c'est un service ordinaire, autoconfiguré : il peut recevoir des dependencies par son constructor.

Les six methods

À retenir en priorité
  1. buildView() prépare la vue du type.
  2. finishView() intervient après les vues enfants.
Method Role Défaut dans AbstractType
buildForm() ajoute les fields enfants vide
configureOptions() déclare les options et leurs défauts vide
getParent() le type dont on hérite FormType::class
getBlockPrefix() le préfixe des blocks Twig dérivé du nom de class
buildView() passe des variables à la vue vide
finishView() ajuste la vue une fois les enfants construits vide

Relu par réflexion : aucune n'est abstraite. Dans buildView(), la vue n'a toujours aucun enfant ; dans finishView(), elle les a.

`getParent()` : spécialiser un type existant

Revoir la règle : Le parent de form est une composition de comportement.

  • Sans getParent(), le parent est FormType, la racine ; parmi les types du cœur, seuls FormType et ButtonType rendent null.
  • ResolvedFormType enchaîne parent, puis type, puis extensions, et clone le resolver du parent avant configureOptions() : un type hérite des options de ses ancêtres et peut en changer les défauts.
  • getBlockPrefix() : nom de class sans Type, en snake case — DeliveryAddressType → delivery_address. La vue reçoit toute la lignée dans block_prefixes, du plus général au plus spécifique : ["form", "choice", "shipping", "_order_shipping"].

Un modèle spécialisé ajoute seulement son écart au modèle parent. Le parent fournit d'abord options et comportement ; le type enfant peut ensuite en personnaliser les valeurs.

Revoir la règle : add() imbrique des données.

->add('address', AddressType::class) les fields vont dans $order->address->city
OrderType::getParent() rend AddressType::class OrderType devient une adresse : city au niveau de l'Order

Ajouter imbrique des données ; hériter reprend un comportement.

Une collection de types

À retenir en priorité
  1. Les entrées supplémentaires sont refusées sans allow_add.
  2. Une absence ne supprime pas automatiquement une entrée sans allow_delete.

Tags ['a', 'b'], entry_type: TextType :

Soumis Sans option Avec l'option
['a', 'b', 'c'] ignoré, « This form should not contain extra fields. » allow_add : ajouté, et un prototype __name__
['a'] ['a', null] allow_delete : ['a']
['a', ''] avec allow_delete : ['a', null] delete_empty en plus : ['a']

by_reference, sur une collection object : avec true (le défaut), ni setter, ni adder, ni remover n'est appelé — l'instance change sur place ; avec false, removeTag() / addTag(), ou setTags() avec une nouvelle instance.

Pièges d'examen

△ Piège à éviter

Revoir la règle : Un FormType décrit un élément composable.

Un form est un type ; la distinction field / form n'existe pas.

Aucune des methods d'un type n'est obligatoire.

Sans parent déclaré, le parent est la racine de tous les types, pas « aucun ».

Le parent passe avant l'enfant : son buildForm() s'exécute d'abord, ses options sont reprises puis modifiables.

Sans allow_add, un élément en trop n'est pas ajouté ; sans allow_delete, un élément absent devient null au lieu de disparaître.

by_reference: true n'appelle jamais addTag() sur une collection object.

Fiche express

◆ À mémoriser

Revoir la règle : Le parent de form est une composition de comportement.

Si tu dois retenir seulement 6 choses :

  • Un form est un type ; aucune des six methods n'est obligatoire.
  • Sans getParent() : FormType.
  • Parent d'abord, options clonées puis modifiables.
  • Spécialiser (getParent()) ≠ composer (add(), données imbriquées).
  • CollectionType : allow_add, allow_delete, delete_empty.
  • by_reference: false pour que l'adder soit appelé.

Moyen mnémotechnique : « Spécialiser, composer, répéter ».
