Objectif

Écrire un type de form, savoir quand le spécialiser par getParent() et quand l'ajouter comme field, et prévoir ce que fait une collection de types.

L'essentiel

À comprendre

À retenir en priorité
  1. add() imbrique des données.
  2. getParent() reprend un comportement au même niveau.

Un form est un type, comme chacun de ses fields. Pour réutiliser un type, trois voies : le spécialiser (getParent() : on hérite et on change quelques options), le composer (add() : il devient un field, ses données s'imbriquent), le répéter (CollectionType).

Le schéma

À retenir en priorité
  1. Le parent de form est une composition de comportement.
  2. Ses options sont héritées puis personnalisables.

L'exemple : l'achat

Exemple concret

class ShippingType extends AbstractType       // spécialise un type existant
{
    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults([
            'choices' => ['Standard' => 'standard', 'Express' => 'express'],
            'expanded' => true,
        ]);
    }

    public function getParent(): string
    {
        return ChoiceType::class;
    }
}

// dans OrderType::buildForm()
$builder
    ->add('shipping', ShippingType::class)                    // spécialisé
    ->add('address', AddressType::class)                      // composé
    ->add('tags', CollectionType::class, ['entry_type' => TextType::class]); // répété

Ce qu'est un type

À retenir en priorité
  1. Un FormType décrit un élément composable.
  2. Un form peut donc devenir enfant d'un autre.

Un type décrit un field ou un form entier : la distinction n'existe pas. C'est ce qui permet d'imbriquer un form dans un autre. Un type étend AbstractType et c'est un service ordinaire, autoconfiguré : il peut recevoir des dependencies par son constructor.

Les six methods

À comprendre

À retenir en priorité
  1. buildView() prépare la vue du type.
  2. finishView() intervient après les vues enfants.

C'est quoi ?

Les méthodes d'AbstractType interviennent à des phases distinctes : configureOptions décrit la configuration, buildForm construit les champs, buildView prépare les variables de vue et finishView intervient après les vues enfants. getParent choisit le type parent ; getBlockPrefix fournit un préfixe pour le rendu et le nom par défaut.

À quoi ça sert ?

Une option n'est pas automatiquement une variable Twig, et modifier une vue ne transforme pas les données métier. Chaque opération doit être placée au moment où les informations dont elle dépend existent.

Où dans Symfony ?

Aucune de ces six méthodes n'est abstraite dans AbstractType : on ne redéfinit que celles nécessaires. Le parent par défaut est FormType et le préfixe découle du nom de classe. buildView ne dispose pas des vues enfants achevées ; finishView peut les examiner.

Comment, étape par étape ?

  1. Déclarer les options avant de les lire.
  2. Construire la structure dans buildForm.
  3. Transmettre les variables propres à la vue dans buildView.
  4. Réserver les calculs dépendant des enfants à finishView ; choisir un préfixe intentionnel pour le theming.

Exemple concret PHP

Type enregistré dans l'application ; les noms complets rendent les signatures explicites :

<?php
final class NoticeType extends \Symfony\Component\Form\AbstractType
{
    public function getParent(): string { return \Symfony\Component\Form\Extension\Core\Type\FormType::class; }
    public function getBlockPrefix(): string { return 'notice'; }
    public function configureOptions(\Symfony\Component\OptionsResolver\OptionsResolver $resolver): void
    {
        $resolver->setDefault('hint', 'Titre public')->setAllowedTypes('hint', 'string');
    }
    public function buildForm(\Symfony\Component\Form\FormBuilderInterface $builder, array $options): void
    {
        $builder->add('title', \Symfony\Component\Form\Extension\Core\Type\TextType::class);
    }
    public function buildView(\Symfony\Component\Form\FormView $view, \Symfony\Component\Form\FormInterface $form, array $options): void
    {
        $view->vars['hint'] = $options['hint'];
    }
    public function finishView(\Symfony\Component\Form\FormView $view, \Symfony\Component\Form\FormInterface $form, array $options): void
    {
        $view->vars['child_count'] = count($view->children);
    }
}

Sans enfant technique ajouté par une extension, la vue contient title et child_count vaut 1. Avec la protection CSRF d'un form racine composé, _token compte aussi : on obtient ici 2. finishView permet de compter les vues enfants achevées ; hint est une variable, pas une vue enfant. Ne pas désactiver CSRF pour forcer le résultat 1. Un template peut lire form.vars.hint ; aucune saisie supplémentaire n'a été créée pour cette variable. Contre-exemple : compter les vues enfants dans buildView puis interpréter zéro comme absence de champs. Correction : effectuer ce calcul dans finishView. Le nom de préfixe ne remplace pas le choix du type parent.

Passage canonique conservé
Method Role Défaut dans AbstractType
buildForm() ajoute les fields enfants vide
configureOptions() déclare les options et leurs défauts vide
getParent() le type dont on hérite FormType::class
getBlockPrefix() le préfixe des blocks Twig dérivé du nom de class
buildView() passe des variables à la vue vide
finishView() ajuste la vue une fois les enfants construits vide

Relu par réflexion : aucune n'est abstraite. Dans buildView(), la vue n'a toujours aucun enfant ; dans finishView(), elle les a.

`getParent()` : spécialiser un type existant

À comprendre

C'est quoi ?

Le parent d'un type Form est un autre type dont il reprend les options et le comportement de construction. Cette parenté fonctionnelle se déclare avec getParent ; elle n'exige pas d'hériter en PHP de la classe concrète de ce type. La classe applicative peut simplement étendre AbstractType.

À quoi ça sert ?

Une sélection spécialisée conserve les mécanismes de ChoiceType tout en fixant ses choix et ses défauts. Dupliquer le rendu ou les transformations du type de base serait plus fragile que préciser son contrat.

Où dans Symfony ?

Sans getParent, AbstractType utilise FormType. Les options du parent sont reprises avant configureOptions du type enfant ; buildForm, buildView et finishView interviennent à leurs phases respectives. buildView prépare les variables avant la construction des vues enfants ; finishView peut les examiner une fois construites.

Comment, étape par étape ?

  1. Choisir le type parent correspondant à la nature de la donnée.
  2. Déclarer ce parent avec getParent.
  3. Fixer seulement les options et comportements spécialisés.
  4. Si nécessaire, définir un block prefix pour le rendu, sans le confondre avec le nom du champ dans la soumission.

Exemple concret PHP

Type enregistré par l'autoconfiguration habituelle de l'application :

<?php
use Symfony\Component\Form\AbstractType;
use Symfony\Component\Form\Extension\Core\Type\ChoiceType;
use Symfony\Component\OptionsResolver\OptionsResolver;

final class PublicationStateType extends AbstractType
{
    public function getParent(): string
    {
        return ChoiceType::class;
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['choices' => ['Brouillon' => 'draft', 'Publié' => 'published']]);
    }
}

Le champ reçoit la logique de ChoiceType et propose les deux valeurs définies. Contre-exemple : ajouter un champ enfant nommé state dans ce type pour en faire un choix scalaire : on construit alors un formulaire composé supplémentaire. Correction : spécialiser ChoiceType directement. À l'inverse, pour une adresse composée de plusieurs champs, la composition sous FormType est appropriée.

Passage canonique conservé

getParent() : spécialiser un type existant

  • Sans getParent(), le parent est FormType, la racine ; parmi les types du cœur, seuls FormType et ButtonType rendent null.
  • ResolvedFormType enchaîne parent, puis type, puis extensions, et clone le resolver du parent avant configureOptions() : un type hérite des options de ses ancêtres et peut en changer les défauts.
  • getBlockPrefix() : nom de class sans Type, en snake case — DeliveryAddressType → delivery_address. La vue reçoit toute la lignée dans block_prefixes, du plus général au plus spécifique : ["form", "choice", "shipping", "_order_shipping"].

Un modèle spécialisé ajoute seulement son écart au modèle parent. Le parent fournit d'abord options et comportement ; le type enfant peut ensuite en personnaliser les valeurs.

Composer plutôt qu'étendre

À comprendre

C'est quoi ?

Un form type est une description réutilisable de formulaire : champs, options et variables de vue. Ce n'est ni l'objet métier ni une instance déjà soumise. getParent() indique une spécialisation de comportement ; add('address', AddressType::class) ajoute au contraire un enfant, donc un niveau dans la structure des données.

À quoi ça sert ?

Hériter convient pour une variante d'un même champ, par exemple un choix de livraison. Composer convient pour une commande qui possède une adresse. Confondre les deux déplace les champs au mauvais niveau : un formulaire commande qui hérite d'un type adresse devient lui-même un formulaire adresse.

Où dans Symfony ?

Une classe étend habituellement AbstractType. buildForm() ajoute les enfants ; configureOptions() définit les options ; buildView() et finishView() préparent la vue, avant puis après les enfants ; getBlockPrefix() fournit un préfixe de thème. Le parent implicite d'AbstractType est FormType : l'héritage des types Form est distinct de l'héritage PHP de la classe.

Comment, étape par étape ?

  1. Décrire la forme des données : adresse imbriquée ou propriétés au niveau racine ?
  2. Choisir la composition pour une donnée imbriquée.
  3. Choisir getParent() seulement pour reprendre le comportement d'un type et ses options.
  4. Pour une liste d'enfants, employer CollectionType : allow_add autorise les nouvelles entrées, allow_delete les suppressions par omission. Le prototype prépare le rendu d'une nouvelle entrée ; il ne l'ajoute pas seul au navigateur.

Exemple concret PHP

Définition complète d'un type spécialisé, enregistré comme service avec l'autoconfiguration habituelle du framework. Il reste un choix, pas un formulaire contenant un enfant nommé livraison.

<?php
namespace App\Form;

use Symfony\Component\Form\AbstractType;
use Symfony\Component\Form\Extension\Core\Type\ChoiceType;
use Symfony\Component\OptionsResolver\OptionsResolver;

final class DeliveryType extends AbstractType
{
    public function getParent(): string
    {
        return ChoiceType::class;
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['choices' => ['Standard' => 'standard', 'Express' => 'express']]);
    }
}

Le formulaire parent peut ajouter DeliveryType comme enfant et obtenir la valeur standard ou express. Contre-exemple : faire hériter tout OrderType de DeliveryType pour y « mettre » la livraison. Correction : ajouter un champ delivery de ce type dans OrderType::buildForm(). Sur une collection d'objets, vérifier aussi by_reference : modifier une instance en place n'équivaut pas à appeler les méthodes d'ajout ou de suppression du parent.

Une collection de types

À comprendre

À retenir en priorité
  1. Les entrées supplémentaires sont refusées sans allow_add.
  2. Une absence ne supprime pas automatiquement une entrée sans allow_delete.

C'est quoi ?

CollectionType organise plusieurs entrées d'un même entry_type. allow_add accepte de nouvelles clés soumises ; allow_delete autorise la suppression d'entrées absentes. Le prototype est une vue d'entrée utilisable pour préparer de nouveaux contrôles côté client, pas une nouvelle donnée enregistrée automatiquement.

À quoi ça sert ?

Une liste de tags peut évoluer sans connaître sa taille à l'avance. Les options distinguent un ajout autorisé d'un champ supplémentaire inattendu, et une suppression intentionnelle d'une valeur manquante conservée selon le traitement.

Où dans Symfony ?

Avec allow_add et prototype actifs, la vue expose le prototype et son nom remplaçable, name par défaut. Le code client doit gérer ses indices. Pour une propriété contenant une collection objet, by_reference influence les modifications en place et l'utilisation des setters ou adders/removers ; il ne pilote pas la suppression en base de données.

Comment, étape par étape ?

  1. Choisir entry_type selon la donnée d'une entrée.
  2. Autoriser explicitement ajouts et suppressions nécessaires.
  3. Distinguer omission d'une clé et entrée présente mais vide : delete_empty traite ce second besoin selon la donnée normalisée.
  4. Sur une collection objet, vérifier les méthodes réellement appelées et choisir by_reference en fonction du contrat du modèle.

Exemple concret PHP

Avec Form chargé, cet exemple utilise des tableaux, pas une collection persistée :

<?php
use Symfony\Component\Form\Forms;
use Symfony\Component\Form\Extension\Core\Type\FormType;
use Symfony\Component\Form\Extension\Core\Type\CollectionType;
use Symfony\Component\Form\Extension\Core\Type\TextType;
$form = Forms::createFormFactory()->createBuilder(FormType::class, ['tags' => ['a', 'b']])
    ->add('tags', CollectionType::class, ['entry_type' => TextType::class, 'allow_add' => true, 'allow_delete' => true])
    ->getForm();
$form->submit(['tags' => [1 => 'b', 2 => 'c']]);
var_export($form->getData());

L'entrée 0 est retirée, 1 reste b et 2 devient c. Contre-exemple : activer seulement le prototype et attendre que toute nouvelle clé soit acceptée, ou activer allow_delete et attendre que toute chaîne vide soit supprimée. Correction : configurer l'autorisation et, si nécessaire, delete_empty séparément. Pour faire passer les changements d'une collection objet par les méthodes de son propriétaire, envisager by_reference false et tester ces méthodes ; le cas tableau ci-dessus ne démontre pas des appels d'adders.

Passage canonique conservé

Une collection de types

Tags ['a', 'b'], entry_type: TextType :

Soumis Sans option Avec l'option
['a', 'b', 'c'] ignoré, « This form should not contain extra fields. » allow_add : ajouté, et un prototype __name__
['a'] ['a', null] allow_delete : ['a']
['a', ''] avec allow_delete : ['a', null] delete_empty en plus : ['a']

by_reference, sur une collection object : avec true (le défaut), ni setter, ni adder, ni remover n'est appelé — l'instance change sur place ; avec false, removeTag() / addTag(), ou setTags() avec une nouvelle instance.

Pièges d'examen

Piège à éviter

  • Champ et formulaire dans le système de types

    Un form est un type ; la distinction field / form n'existe pas.

  • Méthodes facultatives d’un type de formulaire

    Aucune des methods d'un type n'est obligatoire.

  • Voir l’explication : Sans parent déclaré, le parent est la racine de tous les types

    Sans parent déclaré, le parent est la racine de tous les types, pas « aucun ».

  • Voir l’explication : Le parent passe avant l'enfant

    Le parent passe avant l'enfant : son buildForm() s'exécute d'abord, ses options sont reprises puis modifiables.

  • Voir l’explication : Sans allow_add, un élément en trop n'est pas ajouté

    Sans allow_add, un élément en trop n'est pas ajouté ; sans allow_delete, un élément absent devient null au lieu de disparaître.

  • Voir l’explication : by_reference: true n'appelle jamais addTag()

    by_reference: true n'appelle jamais addTag() sur une collection object.

Application

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Un form est un type ; aucune des six methods n'est obligatoire.
  • Sans getParent() : FormType.
  • Parent d'abord, options clonées puis modifiables.
  • Spécialiser (getParent()) ≠ composer (add(), données imbriquées).
  • CollectionType : allow_add, allow_delete, delete_empty.
  • by_reference: false pour que l'adder soit appelé.

Moyen mnémotechnique : « Spécialiser, composer, répéter ».
