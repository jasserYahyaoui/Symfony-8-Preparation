Objectif

Écrire un type de form, savoir quand le spécialiser par getParent() et quand l'ajouter comme field, et prévoir ce que fait une collection de types.

L'essentiel

À comprendre

À retenir en priorité
  1. add() imbrique des données.
  2. getParent() reprend un comportement au même niveau.

Un form et ses fields sont construits à partir de types. Le type est une description réutilisable ; l'instance Form porte les données et l'état de soumission d'une occurrence. Pour réutiliser un type, trois voies : le spécialiser (getParent() : on hérite et on change quelques options), le composer (add() : il devient un field, ses données s'imbriquent), le répéter (CollectionType).

Le schéma

À retenir en priorité
  1. Le parent de form est une composition de comportement.
  2. Ses options sont héritées puis personnalisables.

Ambre = choix de conception, bleu = configuration. ShippingType étend AbstractType en PHP mais désigne ChoiceType comme parent de form. ResolvedFormType orchestre les appels parent → type → extensions ; aucune flèche ne représente un appel direct du parent vers l'enfant.

L'exemple : l'achat

Exemple concret

L'inscription du lecteur peut réutiliser un choix spécialisé, regrouper une adresse ou répéter des préférences. L'achat ci-dessous illustre ces trois relations sans les imposer au GET de l'article. Il s'agit d'extraits de types : les imports et les modèles Order/Address doivent être définis dans l'application qui les emploie.

class ShippingType extends AbstractType       // spécialise un type existant
{
    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults([
            'choices' => ['Standard' => 'standard', 'Express' => 'express'],
            'expanded' => true,
        ]);
    }

    public function getParent(): string
    {
        return ChoiceType::class;
    }
}

// dans OrderType::buildForm()
$builder
    ->add('shipping', ShippingType::class)                    // spécialisé
    ->add('address', AddressType::class)                      // composé
    ->add('tags', CollectionType::class, ['entry_type' => TextType::class]); // répété

Ce qu'est un type

À retenir en priorité
  1. Un FormType décrit un élément composable.
  2. Un form peut donc devenir enfant d'un autre.

Un service de type peut recevoir un catalogue de choix par injection, mais il ne doit pas conserver la saisie propre à un lecteur dans son état. Cette saisie appartient à l'instance Form construite pour le traitement. La même description peut ainsi servir à plusieurs inscriptions sans confondre leurs valeurs ni leur état soumis.

Un type décrit un field ou un form entier : la distinction n'existe pas. C'est ce qui permet d'imbriquer un form dans un autre. Un type étend AbstractType et c'est un service ordinaire, autoconfiguré : il peut recevoir des dependencies par son constructor.

🌍 In Real Life

La situation : un modèle administratif décrit aussi bien une fiche complète qu'un encadré réutilisable. Le bureau qui conserve ces modèles peut disposer d'un annuaire, mais ne range pas les réponses d'un candidat dans le modèle commun.

L’équivalent dans Symfony : un FormType décrit la construction d'une racine ou d'un enfant ; Form porte les données et l'état d'une occurrence. Un type enregistré comme service peut recevoir ses dépendances.

Retour à la réalité technique : découverte, autoconfiguration et injection supposent la configuration de services adaptée ; hériter d'AbstractType ne suffit pas à rendre une classe découverte partout. La réutilisation d'instances dépend du registre/container et de sa durée de vie. Garde les données propres au traitement dans Form, ses données ou ses options, pas dans un état mutable du service partagé.

🧠 Comment le mémoriser : « Le modèle reste commun, les réponses restent individuelles. » Image mentale : modèle au classeur, fiches remplies séparément. Question-réflexe : cette information décrit-elle le type ou seulement l'inscription en cours ?

⚠️ À ne pas confondre : type réutilisable, service injecté et instance Form soumise.

Les six methods

À retenir en priorité
  1. buildView() prépare la vue du type.
  2. finishView() intervient après les vues enfants.

La factory résout d'abord les options utilisées pour bâtir les enfants. Quand on demandera une vue, buildView() préparera ses variables puis finishView() pourra consulter les vues enfants. Ajouter une classe CSS à un enfant déjà construit ne se place donc pas au même moment qu'ajouter ce champ à l'arbre Form.

Method Role Défaut dans AbstractType
buildForm() ajoute les fields enfants vide
configureOptions() déclare les options et leurs défauts vide
getParent() le type dont on hérite FormType::class
getBlockPrefix() le préfixe des blocks Twig dérivé du nom de class
buildView() passe des variables à la vue vide
finishView() ajuste la vue une fois les enfants construits vide

Relu par réflexion : aucune n'est abstraite. Dans buildView(), la vue n'a encore aucun enfant ; dans finishView(), elle les a.

🌍 In Real Life

La situation : préparer une fiche demande plusieurs interventions : fixer les consignes, ajouter les cases, choisir leur famille, préparer leur présentation puis ajuster les encadrés une fois assemblés.

L’équivalent dans Symfony : configureOptions() définit les options, buildForm() configure l'arbre Form, getParent() sa lignée de type, getBlockPrefix() le préfixe de rendu. buildView() prépare les variables de vue ; finishView() intervient après construction des vues enfants.

Retour à la réalité technique : AbstractType fournit des implémentations par défaut ; aucune de ces six méthodes n'est à redéfinir systématiquement. Une variable de FormView ne crée pas un champ soumis, et un préfixe de bloc ne sélectionne pas une propriété métier. Le moment de construction de la vue diffère de celui du formulaire.

🧠 Comment le mémoriser : « Construire la fiche, puis préparer sa présentation. » Image mentale : arbre de cases avant épreuve mise en page. Question-réflexe : dois-je modifier la structure Form ou une vue dont les enfants doivent déjà exister ?

⚠️ À ne pas confondre : options de construction, enfants Form, variables FormView et blocs de thème.

`getParent()` : spécialiser un type existant

ShippingType reprend la mécanique de ChoiceType tout en fixant ses choix. Ce n'est pas ChoiceType qui appelle directement la classe ShippingType : ResolvedFormType coordonne la hiérarchie. Les préfixes obtenus serviront ensuite au renderer pour trouver un block, pas au mapper pour choisir une propriété du modèle.

  • Sans getParent(), le parent est FormType, la racine ; parmi les types du cœur, seuls FormType et ButtonType rendent null.
  • ResolvedFormType enchaîne parent, puis type, puis extensions, et clone le resolver du parent avant configureOptions() : un type hérite des options de ses ancêtres et peut en changer les défauts.
  • getBlockPrefix() : nom de class sans Type, en snake case — DeliveryAddressType → delivery_address. La vue reçoit toute la lignée dans block_prefixes, du plus général au plus spécifique : ["form", "choice", "shipping", "_order_shipping"].

🌍 In Real Life

La situation : une fiche de livraison reprend le modèle général de choix, puis précise « Standard » ou « Express ». Le coordinateur applique le modèle de base avant les particularités, sans demander à la fiche générale de connaître toutes ses variantes.

L’équivalent dans Symfony : getParent() désigne ChoiceType comme parent de ShippingType dans le système Form. ResolvedFormType coordonne la hiérarchie, clone le resolver d'options parental puis applique les adaptations et extensions concernées.

Retour à la réalité technique : cela ne change pas l'héritage PHP extends AbstractType. FormType est le parent par défaut d'AbstractType ; ButtonType possède sa propre racine. Les block_prefixes préparent la recherche de rendu, avec un préfixe spécifique à l'occurrence, sans déplacer les données mappées.

🧠 Comment le mémoriser : « Reprendre la règle de base, préciser la variante. » Image mentale : modèle Choice annoté pour la livraison. Question-réflexe : quel comportement de type veux-je reprendre, indépendamment de ma classe parente PHP ?

⚠️ À ne pas confondre : héritage PHP, parent Form, parent dans l'arbre de champs et préfixe Twig.

Un modèle spécialisé ajoute seulement son écart au modèle parent. Le parent fournit d'abord options et comportement ; le type enfant peut ensuite en personnaliser les valeurs.

Composer plutôt qu'étendre

Si SignupData contient une adresse, ajouter AddressType sous address conserve cette frontière de données. Le déclarer comme parent de SignupType réutiliserait au contraire sa description au niveau courant. Choisis selon la structure du modèle avant de chercher à obtenir le même aspect HTML.

Écriture Résultat
->add('address', AddressType::class) les fields vont dans $order->address->city
OrderType::getParent() rend AddressType::class OrderType devient une adresse : city au niveau de l'Order

Ajouter imbrique des données ; hériter reprend un comportement.

🌍 In Real Life

La situation : une fiche d'achat peut contenir un sous-dossier d'adresse. C'est différent d'utiliser une fiche d'adresse comme modèle de base pour toute la fiche d'achat.

L’équivalent dans Symfony : add('address', AddressType::class) ajoute un enfant associé à la donnée d'adresse ; déclarer AddressType comme parent réutilise sa configuration au niveau du type courant.

Retour à la réalité technique : l'imbrication usuelle dépend du mapping et du modèle compatibles. inherit_data constitue une autre configuration où les données parentes sont partagées. Hériter d'un type qui impose une data_class incompatible ne transforme pas magiquement Order en Address : les options et données doivent rester cohérentes.

🧠 Comment le mémoriser : « Contenir une adresse n'est pas devenir une adresse. » Image mentale : sous-dossier Address dans Order, face à une fiche entièrement basée sur Address. Question-réflexe : ai-je un objet enfant à mapper ou un comportement de type à spécialiser ?

⚠️ À ne pas confondre : composition de champs, spécialisation de type et partage des données parentes.

Une collection de types

À retenir en priorité
  1. Les entrées supplémentaires sont refusées sans allow_add.
  2. Une absence ne supprime pas automatiquement une entrée sans allow_delete.

Quand le lecteur ajoute une préférence, le navigateur peut transmettre une nouvelle clé, mais le serveur doit encore accepter l'ajout d'un enfant. allow_add pilote cette adaptation de l'arbre ; le prototype facilite l'interface, sans autoriser à lui seul la donnée. Le tableau suppose une soumission complète : un PATCH partiel et sa politique de champs manquants ne doivent pas être déduits de ces exemples.

Pour une collection objet, le cas by_reference: true décrit ci-dessous suppose que la même instance est modifiée sur place. Si les méthodes d'ajout portent une règle métier, configure leur passage explicitement et vérifie le mapping ; rendre le formulaire valide n'appelle pas par magie une opération métier séparée.

Tags ['a', 'b'], entry_type: TextType :

Soumis Sans option Avec l'option
['a', 'b', 'c'] ignoré, « This form should not contain extra fields. » allow_add : ajouté, et un prototype __name__
['a'] ['a', null] allow_delete : ['a']
['a', ''] avec allow_delete : ['a', null] delete_empty en plus : ['a']

by_reference, sur une collection object : avec true (le défaut), ni setter, ni adder, ni remover n'est appelé — l'instance change sur place ; avec false, removeTag() / addTag(), ou setTags() avec une nouvelle instance.

🌍 In Real Life

La situation : un dossier contient plusieurs fiches de préférence du même modèle. Ajouter une nouvelle fiche, retirer une fiche absente et éliminer une fiche vide sont trois décisions ; modifier directement le classeur peut aussi contourner le guichet chargé d'enregistrer chaque ajout.

L’équivalent dans Symfony : CollectionType répète entry_type. allow_add, allow_delete et delete_empty règlent des opérations différentes sur les entrées ; by_reference influence ensuite l'écriture vers le modèle et le passage éventuel par ses accessors.

Retour à la réalité technique : le prototype aide l'interface mais n'autorise pas les données. Les résultats du tableau supposent les TextType et la soumission complète indiqués ; ne généralise pas null à tout type ni à PATCH. delete_empty dépend de la valeur normalisée ou du callable configuré. Le contournement des adders avec by_reference: true vise la même collection modifiée sur place ; false nécessite encore des méthodes et un mapping compatibles, sans garantir persistance ni règles métier.

🧠 Comment le mémoriser : « Ajouter, retirer, vider ; puis choisir la porte d'écriture. » Image mentale : fiches répétées devant trois décisions, puis guichet du classeur. Question-réflexe : quelle entrée change, et quelle méthode doit réellement recevoir cette modification ?

⚠️ À ne pas confondre : arbre Form, prototype HTML, données normalisées, accessors métier et opérations de base de données.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le même système de types décrit racine et fields

    Le même système de types décrit racine et fields, mais un type n'est pas l'instance Form qui reçoit la soumission.

  • Méthodes facultatives d’un type de formulaire

    Aucune des methods d'un type n'est obligatoire.

  • Voir l’explication : Sans parent déclaré, le parent est la racine de tous les types

    Sans parent déclaré, le parent est la racine de tous les types, pas « aucun ».

  • Voir l’explication : Le parent passe avant l'enfant

    Le parent passe avant l'enfant : son buildForm() s'exécute d'abord, ses options sont reprises puis modifiables.

  • Voir l’explication : Sans allow_add, un élément en trop n'est pas ajouté

    Sans allow_add, un élément en trop n'est pas ajouté ; sans allow_delete, un élément absent devient null au lieu de disparaître.

  • Voir l’explication : by_reference: true n'appelle jamais addTag()

    by_reference: true n'appelle jamais addTag() sur une collection object.

Application

À retenir en priorité
  1. Le parent de form est une composition de comportement.
  2. Ses options sont héritées puis personnalisables.
  3. Les entrées supplémentaires sont refusées sans allow_add.
  4. Une absence ne supprime pas automatiquement une entrée sans allow_delete.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Un type décrit un form ou un field ; les six methods ont des défauts.
  • Sans getParent() : FormType.
  • Parent d'abord, options clonées puis modifiables.
  • Spécialiser (getParent()) ≠ composer (add(), données imbriquées).
  • CollectionType : allow_add, allow_delete, delete_empty.
  • by_reference: false pour que l'adder soit appelé.

Moyen mnémotechnique : « Spécialiser, composer, répéter ».
