Objectif

Brancher du code sur un event sans modifier celui qui le déclenche. C'est le mécanisme qui rend Symfony extensible : le kernel ne connaît pas vos listeners, il publie des events.

L'essentiel

À comprendre

À retenir en priorité
  1. Le tri est décroissant.
  2. Les priorities négatives sont autorisées.

Le dispatcher tient un registre de listeners par nom d'event et les notifie quand l'event est distribué : le code qui déclenche ne connaît pas ceux qui écoutent. La priority la plus haute passe en premier ; à égalité, l'ordre d'ajout décide. On s'inscrit par un listener, branché de l'extérieur, ou un subscriber, qui se déclare lui-même.

Le schéma

À retenir en priorité
  1. L'égalité conserve l'ordre d'ajout.
  2. La priority ne suffit pas à décrire tous les cas.

Gris/pointillé : enregistrement préalable ; bleu : exécution synchrone ; vert : retour. Ajouter un listener ne déclenche pas l'événement. Un nom explicite remplace le nom de classe : écouter OrderPlacedEvent::class ne reçoit pas automatiquement un dispatch nommé order.placed. Un arrêt de propagation ou une exception peut empêcher d'atteindre les listeners suivants.

Exemple concret

À retenir en priorité
  1. Le publisher exprime un fait.
  2. Le registre du dispatcher choisit les listeners.
#[AsEventListener]
final class SendConfirmation
{
    public function __invoke(OrderPlacedEvent $event): void {}   // event déduit du type
}

final class OrderSubscriber implements EventSubscriberInterface
{
    public static function getSubscribedEvents(): array
    {
        return [
            KernelEvents::RESPONSE => [['onResponsePre', 10], ['onResponsePost', -10]],
            OrderPlacedEvent::class => 'onPlacedOrder',
        ];
    }
}

Le subscriber est ici un fragment de déclaration : fournir les trois méthodes annoncées et enregistrer le service (autoconfiguration active dans le framework, addSubscriber() hors framework). Le dispatcher n'envoie pas de confirmation lui-même : le corps vide du listener ne fait encore aucun métier.

La priority, et son départage

À comprendre

À retenir en priorité
  1. La valeur la plus haute passe d'abord.
  2. Zéro n'est pas une priorité absolue.

C'est quoi ?

EventDispatcher appelle les listeners inscrits pour un événement. Le code émetteur connaît l'event, pas nécessairement tous les services qui y réagiront : c'est une composition de comportements par notification.

À quoi ça sert ?

Des réactions indépendantes peuvent être ajoutées sans accumuler leurs appels dans l'émetteur. Il faut néanmoins documenter l'ordre lorsque les listeners lisent ou modifient un même objet.

Où dans Symfony ?

Un listener est inscrit depuis l'extérieur, par configuration, attribute ou addListener(). Un subscriber regroupe ses abonnements dans getSubscribedEvents(), méthode statique : c'est utile pour rendre cet ensemble réutilisable. Sans nom explicite, dispatch($event) utilise le nom de classe de l'objet.

Comment, étape par étape ?

  1. Choisir une classe d'event ou un nom explicite cohérent avec l'inscription.
  2. Inscrire les listeners ; une priorité plus haute passe avant une plus basse, zéro étant le défaut.
  3. À priorité égale, l'ordre d'ajout départage les listeners.
  4. Distribuer l'event. Le même objet peut être modifié et dispatch() le retourne ; ce mécanisme est synchrone, il n'est pas une file Messenger.

Exemple concret PHP

Avec EventDispatcher installé, exemple local sans framework :

<?php
use Symfony\Component\EventDispatcher\EventDispatcher;

$dispatcher = new EventDispatcher();
$order = [];
$dispatcher->addListener('lesson.ready', static function () use (&$order): void {
    $order[] = 'normal';
});
$dispatcher->addListener('lesson.ready', static function () use (&$order): void {
    $order[] = 'prioritaire';
}, 10);
$dispatcher->dispatch(new stdClass(), 'lesson.ready');
echo implode(', ', $order), PHP_EOL;

La sortie attendue est prioritaire, normal, bien que le listener normal ait été ajouté d'abord. Contre-exemple : utiliser une priorité négative pour faire passer un listener avant tous les autres. Correction : le tri est décroissant. Autre erreur : s'abonner au nom de classe puis distribuer sous un nom explicite différent ; les noms doivent correspondre. Un subscriber peut déclarer plusieurs méthodes pour un même event, mais cela ne supprime pas les règles d'ordre ni les effets d'un éventuel arrêt de propagation.

EventDispatcher 8.0.

Passage canonique conservé
  • Un int positif ou négatif, 0 par défaut ; plus il est élevé, plus le listener est appelé tôt.
  • À priority égale, l'ordre d'ajout : ajoutés 0, 0, 10, -5, ils tournent 10, les deux 0 dans leur ordre, puis -5.

Listener ou subscriber

À retenir en priorité
  1. La liste vit dans la class du subscriber.
  2. Un listener peut être configuré de l'extérieur.
Listener Subscriber
inscription de l'extérieur : configuration ou #[AsEventListener] lui-même : getSubscribedEvents(), statique
atout (documentation) plus souple : un bundle l'active selon sa configuration plus réutilisable : la connaissance des events vit dans la class

Résolution de la method d'un listener (RegisterListenersPass, 8.0) :

Cas Method appelée
event: 'acme.foo_bar', onAcmeFooBar() présente onAcmeFooBar()
event: 'acme.other', sans onAcmeOther() __invoke(), en repli
pas d'event, __invoke(CustomEvent $e) __invoke(), event déduit du type
ni l'une ni l'autre la compilation du container échoue

#[AsEventListener] se répète pour configurer plusieurs methods ; un subscriber peut inscrire plusieurs methods sur un même event.

Distribuer

À retenir en priorité
  1. Le FQCN sert de nom par défaut.
  2. Un nom explicite peut être fourni.

dispatch($event) ou dispatch($event, 'foo.event'). Sans nom, la class de l'object sert de nom, d'où OrderPlacedEvent::class comme key d'abonnement. dispatch() rend l'object event lui-même, modifié par les listeners. Chaque listener reçoit l'event, son nom et le dispatcher, ce qui lui permet d'en distribuer d'autres.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La method peut être déduite.
  2. Vérifier la convention lorsqu'aucun nom n'est donné.
  • Voir l’explication : Priority haute = appelé en premier

    Priority haute = appelé en premier, et les valeurs négatives sont permises.

  • Départager des listeners de même priorité

    À priority égale, l'ordre d'ajout décide.

  • Nom implicite d’un événement

    dispatch() sans nom utilise la class de l'event.

  • Voir l’explication : method est optionnelle sur #[AsEventListener]

    method est optionnelle sur #[AsEventListener] ; le défaut est on + nom de l'event, et __invoke() sert de repli.

  • Plusieurs méthodes d’un subscriber pour un événement

    Un subscriber peut inscrire plusieurs methods sur un même event.

Fiche express

À mémoriser

À retenir en priorité
  1. Les listeners partagent l'object.
  2. Le publisher peut lire le résultat après dispatch().

Si tu dois retenir seulement 6 choses :

  • Priority haute d'abord ; négative permise ; égalité → ordre d'ajout.
  • addListener(nom, callable, priority).
  • dispatch($event) sans nom : la class ; rend le même object.
  • Listener souple, subscriber réutilisable.
  • Method par défaut : on + nom camélisé, puis __invoke().
  • Le listener reçoit event, nom, dispatcher.

Moyen mnémotechnique : « Le plus haut parle en premier ».
