Objectif

Connaître les parameters que Symfony réserve, leur effet réel dans le code 8.0, et les formes courtes qui les posent — celles qui existent vraiment.

L'essentiel

À comprendre

À retenir en priorité
  1. locale et format ont des formes courtes valides.
  2. query n'est pas un argument du constructor Route 8.0.

Cinq parameters préfixés d'un souligné sont réservés : _controller, _format, _locale, _fragment, _query. #[Route] pose les trois premiers par des arguments courts — locale, format, stateless — mais n'a pas d'argument query, malgré l'exemple officiel. _query n'agit qu'à la génération, et _fragment est le seul que la documentation exclut des imports.

Le schéma

À retenir en priorité
  1. _query se passe à generate(), path() ou url().
  2. Ne pas le confondre avec _fragment, également lu dans les defaults.

L'exemple

Exemple concret

À retenir en priorité
  1. _locale et _format décrivent le contexte de Request.
  2. _fragment intervient dans l'URL générée.
class ExampleController
{
    #[Route(
        path: '/articles/{_locale}/search.{_format}',
        locale: 'en',
        format: 'html',
        requirements: ['_locale' => 'en|fr', '_format' => 'html|xml'],
    )]
    public function __invoke(): \Symfony\Component\HttpFoundation\Response
    {
        return new \Symfony\Component\HttpFoundation\Response();
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Les cinq parameters réservés

À comprendre

C'est quoi ?

Certains paramètres de routage ont un sens reconnu par l'infrastructure. _controller désigne le traitement ; _locale la locale ; _format le format demandé. _fragment et _query servent à la construction de l'URL. Le préfixe commun ne signifie pas qu'ils sont tous lus au même moment ou par le même component.

À quoi ça sert ?

Ces noms évitent de réimplémenter des conventions déjà prises en charge. Il faut toutefois distinguer une intention de format d'une conversion réelle : déclarer json n'encode pas automatiquement un objet PHP en JSON.

Où dans Symfony ?

Le controller resolver lit _controller, LocaleListener exploite _locale, Request expose _format comme request format. Le générateur utilise _fragment après le caractère # et _query pour des paramètres de query string. Un fragment d'URL est traité par le client et ne devient pas un segment du chemin envoyé au serveur.

Comment, étape par étape ?

  1. Déterminer si la donnée concerne le traitement entrant ou l'URL générée.
  2. Choisir le paramètre réservé correspondant, plutôt qu'une clé ressemblante inventée.
  3. Pour format et locale, vérifier ce que l'action et les services font réellement de cette information.
  4. Laisser une Response au Content-Type explicitement fixé conserver ce choix ; la préparation ne doit pas être confondue avec une sérialisation.

Exemple concret PHP

Générateur configuré avec une route guide sur /guide :

<?php
use Symfony\Component\Routing\Generator\UrlGeneratorInterface;

function sectionLink(UrlGeneratorInterface $generator): string
{
    return $generator->generate('guide', [
        '_query' => ['page' => 2],
        '_fragment' => 'installation',
    ]);
}

Sans autre contrainte, le résultat est /guide?page=2#installation. Contre-exemple : utiliser query: comme argument nommé de Route en Symfony 8.0 : cet argument n'existe pas. Correction : fournir _query au générateur ; locale, format et stateless ont, eux, des formes courtes reconnues dans la déclaration de route.

La documentation réserve _fragment à une route plutôt qu'à un import. Le fait qu'un chemin interne de configuration puisse recopier certains defaults ne transforme pas ce comportement en contrat recommandé ; préserver cette distinction entre API documentée et détail d'implémentation.

Passage canonique conservé

Les cinq parameters réservés

Parameter Effet Qui le lit (8.0)
_controller le controller exécuté quand la route correspond le resolver de controller
_format le request format de la Request Request::getRequestFormat()
_locale la locale de la Request LocaleListener
_fragment la partie après # de l'URL générée UrlGenerator
_query des parameters de query string dans l'URL générée UrlGenerator

À Response::prepare(), si la Response n'a pas de header Content-Type, Symfony en pose un d'après le format : json donne application/json. Un controller qui fixe le header l'emporte. Ainsi /search.json et /search.xml partagent une route.

Sur une étiquette de transport, certaines cases décrivent le traitement : _controller, _format et _locale. D'autres, comme _route et _route_params, sont normalement renseignées par le routing ; distinguer la consigne du résultat évite les collisions.

Repère — _query n'agit qu'à la génération : No. The generator reads _query from parameters supplied to generate(). _query se passe à generate(), path() ou url(). Ne pas le confondre avec _fragment, également lu dans les defaults.

Les formes courtes

À comprendre

C'est quoi ?

locale, format et stateless sont des formes de configuration qui alimentent respectivement les defaults internes _locale, _format et _stateless. Elles rendent une intention lisible sans changer la nature des informations transmises au traitement.

À quoi ça sert ?

Le controller et les listeners reçoivent une convention cohérente sans recopie manuelle. Cependant, décrire le format attendu n'encode pas le contenu : la réponse doit effectivement être construite dans ce format.

Où dans Symfony ?

Route accepte ces arguments nommés en Symfony 8.0 ; le loader YAML reconnaît les formes correspondantes. utf8 configure une option du compilateur, pas un default de même catégorie. L'argument query n'existe pas dans cette signature : la query string de génération utilise _query.

Comment, étape par étape ?

  1. Choisir la locale et le format réellement voulus.
  2. Déclarer les formes courtes reconnues.
  3. Laisser les listeners configurer le contexte entrant.
  4. Produire explicitement une réponse cohérente ; respecter l'absence d'usage de session si stateless est déclaré.

Exemple concret PHP

Action découverte par les attributes :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[\Symfony\Component\Routing\Attribute\Route('/status', name: 'status', locale: 'fr', format: 'json', stateless: true)]
public function status(\Symfony\Component\HttpFoundation\Request $request): \Symfony\Component\HttpFoundation\JsonResponse
{
    return new \Symfony\Component\HttpFoundation\JsonResponse(['locale' => $request->getLocale()]);
}

La locale de route est fr ; JsonResponse assure l'encodage JSON. Contre-exemple : retourner une Response contenant du HTML en pensant que format json le convertira. Correction : sérialiser correctement le contenu et fixer un type de réponse adapté. Déclarer stateless n'autorise pas à lire discrètement la session ; un usage contradictoire peut être signalé ou rejeté par l'intégration.

Passage canonique conservé

Les formes courtes

Le constructor de #[Route] recopie locale, format et stateless en default values _locale, _format et _stateless ; utf8: true devient l'option utf8. En YAML, les keys locale, format et stateless font de même.

Écart avec la documentation. Son exemple ajoute query: ['page' => 1]. En 8.0, #[Route] n'a pas cet argument : PHP lève une Error « Unknown named parameter ». Le loader YAML ne connaît pas non plus la key query et lève une InvalidArgumentException.

`_query` n'agit qu'à la génération

UrlGenerator::doGenerate() lit _query uniquement dans les parameters passés à generate() — donc à path() ou url(). Posée en default value de la route, elle n'apparaît pas dans l'URL. _fragment, lui, est lu aux deux endroits : la default value d'abord, remplacée par un _fragment passé à la génération.

La limite documentée : `_fragment` et les imports

À comprendre

À retenir en priorité
  1. La règle documentée limite _fragment à la route.
  2. Ne pas transformer une tolérance du loader en contrat documentaire.

C'est quoi ?

Un import charge plusieurs routes et peut leur transmettre des valeurs communes. Un fragment d'URL désigne au contraire une partie de la destination côté client, après #. La documentation réserve _fragment à une route plutôt qu'à une déclaration d'import.

À quoi ça sert ?

Il faut éviter de confondre des defaults communs de traitement avec un emplacement de navigation pertinent seulement pour une page donnée. Le fragment ne fait pas partie du path envoyé au serveur et ne doit pas servir à choisir le controller entrant.

Où dans Symfony ?

Le code de RouteCollection peut recopier des defaults d'import sans rejeter cette clé. Cette tolérance n'annule pas la limite du contrat documenté. Les routes localisées conservent aussi leur propre locale plutôt que se laisser redéfinir par un _locale hérité de l'import.

Comment, étape par étape ?

  1. Réserver les defaults d'import aux données communes compatibles avec ses routes.
  2. Choisir le fragment au niveau du lien ou de la route concernée.
  3. Générer l'URL complète avant le traitement du fragment par le client.
  4. Ne pas prendre l'absence d'exception du loader pour une recommandation de configuration.

Exemple concret Twig

La route guide existe sur /guide et la page possède un élément dont l'ID est installation :

<a href="{{ path('guide', {_fragment: 'installation'}) }}">Installation</a>

Le lien devient /guide#installation ; le serveur reçoit le chemin /guide. Contre-exemple : mettre _fragment dans les defaults d'un import de toutes les pages et attendre un même élément cible présent partout. Correction : fournir le fragment au lien concerné, en respectant le contrat documenté. Le générateur ne vérifie pas l'existence de l'ID HTML dans la page : elle doit être assurée par le template.

Passage canonique conservé

La limite documentée : _fragment et les imports

Selon la documentation, ces parameters s'emploient dans une route comme dans un import, sauf _fragment, réservé à une route. Le code 8.0 ne contrôle rien : RouteCollection::addDefaults() recopie tous les defaults d'un import. Retenez la règle documentée. Autre détail du code : une route localisée ignore un _locale hérité d'un import et garde sa propre locale.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Les parameters réservés commencent tous par un souligné ; les arguments courts de l'attribute, non.

    Les parameters réservés commencent tous par un souligné ; les arguments courts de l'attribute, non. Ce sont deux écritures de la même chose : l'argument pose la default value du parameter réservé.

  • Voir l’explication : Un seul des cinq est exclu des imports par la documentation

    Un seul des cinq est exclu des imports par la documentation : celui qui pose l'identifier de fragment. Rien dans le code ne le rejette.

  • Voir l’explication : Pas d'argument query dans #[Route] en 8.0

    Pas d'argument query dans #[Route] en 8.0, malgré l'exemple officiel. _query se passe à la génération.

  • Voir l’explication : Le format de Request ne décide du Content-Type qu'en l'absence de header.

    Le format de Request ne décide du Content-Type qu'en l'absence de header. C'est ce qui permet à deux extensions d'URL de partager une seule route.

Application

À retenir en priorité
  1. _query se passe à generate(), path() ou url().
  2. Ne pas le confondre avec _fragment, également lu dans les defaults.
  3. La règle documentée limite _fragment à la route.
  4. Ne pas transformer une tolérance du loader en contrat documentaire.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Réservés : _controller, _format, _locale, _fragment, _query.
  • _format → Content-Type seulement s'il manque.
  • #[Route] : locale, format, stateless ; utf8 est une option.
  • Pas d'argument query en 8.0 (Error) ; en YAML, exception.
  • _query : génération seulement ; _fragment : défaut puis génération.
  • Imports : tout sauf _fragment (documentation) ; route localisée garde sa locale.

Moyen mnémotechnique : « Query se demande, il ne se déclare pas ».
