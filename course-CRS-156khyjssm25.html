Objectif

Connaître l'arborescence par défaut d'une application Symfony, le rôle de chaque directory, et par quel mécanisme chacun se déplace.

L'essentiel

À comprendre

À retenir en priorité
  1. public/ est le document root.
  2. src/, config/ et vendor/ ne sont pas des directories publics.

Une application Symfony a une arborescence par défaut où deux directories structurent tout : public/, le seul servi par le serveur web, et var/, qui accueille habituellement cache et logs. Ce n'est pas une restriction imposée à toutes les écritures métier. Chaque directory se déplace, mais par trois voies différentes : composer.json, la configuration d'un bundle, ou le kernel.

Le schéma

À retenir en priorité
  1. Le cache sépare les environments.
  2. Le log directory par défaut n'ajoute pas cet environment.

Les flèches pleines montrent le traitement ou les écritures ; le pointillé montre le chargement du code et de la configuration. Bleu : acteurs ; orange : fichiers privés du projet ; vert : données produites ou servies. Cette vue suppose la racine web recommandée, sans alias serveur supplémentaire. Un contrôleur peut envoyer un fichier situé hors de public/ après contrôle d'accès : « non servi directement » ne signifie pas « impossible à télécharger ».

L'arborescence par défaut

À comprendre

C'est quoi ?

L'arborescence sépare code source, configuration, ressources publiques, dépendances et fichiers générés. Le serveur web doit exposer public/, pas la racine entière du projet.

À quoi ça sert ?

Cette séparation rend prévisible l'emplacement des fichiers et évite de publier configuration, code interne ou dépendances par erreur. Elle permet aussi de distinguer les fichiers à maintenir des caches et logs qui sont produits à l'exécution.

Où dans Symfony ?

  • src/ contient le code applicatif et le kernel ; config/ contient sa configuration.
  • templates/ contient les templates Twig ; translations/, les catalogues ; tests/, les tests.
  • assets/ contient des sources de ressources web ; public/ contient ce que le serveur peut servir et le front controller index.php.
  • bin/ contient notamment la console ; vendor/ les dépendances Composer.
  • var/cache/ et var/log/ contiennent les fichiers générés correspondants.

Comment, étape par étape ?

  1. Le serveur reçoit une URL sous sa racine documentaire public/.
  2. Une ressource publique peut être servie directement selon sa configuration.
  3. Le front controller traite les demandes applicatives prévues par le serveur.
  4. Le code charge ses dépendances hors de la racine publique.

Exemple concret text

projet/public/index.php       : point d'entrée HTTP
projet/src/Controller/        : code chargé par PHP, pas fichier public à télécharger
projet/config/services.yaml  : configuration interne
projet/var/cache/             : résultat généré, pas source métier

Contre-exemple : choisir projet/ comme racine documentaire pour rendre index.php accessible. Cela expose potentiellement des fichiers qui ne doivent pas être servis. Correction : viser projet/public/ et régler le routage du serveur autour de ce front controller. Ne pas modifier vendor/ à la main pour une personnalisation durable : utiliser les points de configuration et d'extension prévus.

Passage canonique conservé
Directory Role
assets/ sources front — JavaScript, CSS, images
bin/ exécutables, dont bin/console
config/ configuration ; packages/ par bundle, routes/, services.yaml
public/ seul directory exposé par le serveur web ; contient index.php
src/ le code, namespace App\, dont Kernel.php
templates/, translations/, tests/ templates Twig, catalogues, tests
var/ files générés à l'exécution : cache/, log/
vendor/ dependencies Composer — jamais modifié à la main
.env à la racine, pas dans config/

Dans un atelier, public/ est le comptoir accessible, src/ l'établi, config/ le classeur de réglages et var/ les résultats temporaires du travail. Le comptoir ne doit pas devenir l'atelier entier.

Repère — Les quatre accessors du kernel : No. getLogDir() uses var/log, while cache paths include the environment. Le cache sépare les environments. Le log directory par défaut n'ajoute pas cet environment.

Sous config/

À comprendre

À retenir en priorité
  1. La configuration commune reste la base.
  2. Le sous-directory d'environment fournit ses surcharges.

C'est quoi ?

config/packages/ porte les options des bundles. Les sous-dossiers nommés par environnement, comme config/packages/test/, ajoutent les réglages propres à cet environnement dans l'organisation standard de l'application.

À quoi ça sert ?

La configuration commune reste centralisée ; seules les différences sont répétées. Un environnement Symfony est un contexte de configuration, comme dev, test ou prod, pas nécessairement une machine physique différente.

Où dans Symfony ?

Le chargement habituel du kernel prend d'abord les fichiers communs puis ceux de l'environnement. Les options sont fusionnées selon l'arbre du bundle ; « surcharge » ne signifie pas remplacement aveugle de toutes les clés et listes de tous les bundles.

Comment, étape par étape ?

  1. Déclarer les options communes dans config/packages/.
  2. Mettre les différences sous le dossier d'environnement.
  3. Démarrer l'application dans cet environnement.
  4. Vérifier le résultat fusionné, surtout lorsqu'une option est une liste ou possède une règle de fusion particulière.

Exemple concret YAML

# config/packages/twig.yaml
twig:
    strict_variables: false
# config/packages/test/twig.yaml
twig:
    strict_variables: true

Dans test, l'accès à une variable Twig absente est traité strictement ; l'option commune reste celle des autres environnements sauf autre surcharge. Contre-exemple : placer un réglage uniquement dans test/ et attendre son effet en production. Correction : le placer dans le commun s'il doit être partagé, ou dans le dossier réellement ciblé. Un projet qui personnalise le chargement du kernel doit respecter ou redéfinir explicitement ces conventions.

Passage canonique conservé

config/packages/ contient un file par bundle configuré. Un sous-répertoire d'environment — config/packages/test/ — n'est lu que dans cet environment, et surcharge la configuration commune.

Déplacer un directory

À comprendre

À retenir en priorité
  1. Déplacer src/ exige de corriger autoload.psr-4.
  2. composer dump-autoload reconstruit l'autoloading.

C'est quoi ?

Déplacer un dossier change un chemin, mais ce chemin peut être lu par plusieurs systèmes : Composer pour l'autoload, Flex pour les recipes, un bundle pour ses ressources ou le kernel pour les fichiers générés.

À quoi ça sert ?

Une organisation spécifique peut être utile, mais renommer le dossier seul laisse des références périmées. Il faut configurer le lecteur réel du chemin, pas chercher une option universelle qui déplacerait toute l'application.

Où dans Symfony ?

  • Pour les templates, twig.default_path règle le dossier principal ; twig.paths permet plusieurs chemins.
  • Pour les traductions, utiliser les options du translator.
  • Pour src/, adapter aussi autoload.psr-4 et reconstruire l'autoload Composer.
  • Pour public/, adapter le serveur, les indications de recipe et les chemins d'autoload du front controller si leur relation change.
  • Pour cache et logs, utiliser les points de configuration du kernel appropriés, en gardant la séparation des environnements.

Comment, étape par étape ?

  1. Identifier tous les lecteurs du chemin actuel.
  2. Choisir l'option documentée de chacun.
  3. Déplacer les fichiers dans le projet cible.
  4. Renouveler les artefacts concernés et vérifier chargement, permissions et chemins relatifs.

Exemple concret YAML

# config/packages/twig.yaml
twig:
    default_path: '%kernel.project_dir%/resources/views'

Les templates sont recherchés dans ce dossier principal ; cette option ne déplace ni src/ ni public/. Contre-exemple : renommer src/ en code/ sans modifier la correspondance PSR-4 de Composer. La classe peut exister sur disque mais ne plus être trouvée par l'autoload. Correction : adapter la correspondance et régénérer l'autoload dans le projet cible. Aucun déplacement de fichiers n'est exécuté par ce paquet.

Passage canonique conservé

Trois voies : ce que Composer doit connaître avant que PHP ne démarre (extra, et config.vendor-dir), ce qu'un bundle configure (twig.default_path ou twig.paths, framework.translator.default_path), et ce que seul le kernel connaît. .env passe par extra.runtime.dotenv_path. Déplacer src/ demande aussi de corriger autoload.psr-4 et de relancer composer dump-autoload ; déplacer public/ demande de corriger, dans index.php, le path de vendor/autoload_runtime.php.

Repère de l’exemple : Override getCacheDir(); the environment suffix keeps different environments' caches separate. Surcharger getCacheDir() change le directory du cache. Conserver l'environment dans le path sépare les caches dev et prod.

Les quatre accessors du kernel

Method Défaut
getCacheDir() <projet>/var/cache/<environnement>
getBuildDir() délègue à getCacheDir()
getShareDir(): ?string délègue à getCacheDir() ; peut rendre null
getLogDir() <projet>/var/log — sans l'environment

APP_CACHE_DIR, APP_BUILD_DIR, APP_SHARE_DIR et APP_LOG_DIR sont lues par MicroKernelTrait, pas par Kernel. Les trois premières passent par getEnvDir(), qui ajoute /<environnement> et résout un path relatif depuis la racine du projet ; APP_LOG_DIR est prise telle quelle. APP_SHARE_DIR à false fait rendre null à getShareDir() : %kernel.share_dir% n'est alors pas enregistré.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Aucune key extra ne déplace templates/, translations/ ni vendor/.

    Aucune key extra ne déplace templates/, translations/ ni vendor/. Les deux premiers se déplacent par configuration de bundle — twig.default_path, framework.translator.default_path — et vendor/ par la key config de Composer. extra.templates-dir n'existe pas.

  • Voir l’explication : extra.src-dir seul ne suffit pas.

    extra.src-dir seul ne suffit pas. Sans autoload.psr-4 corrigé et composer dump-autoload relancé, l'autochargement cherche toujours l'ancien path.

  • Voir l’explication : Les APP_*_DIR ne sont pas lues par Kernel.

    Les APP_*_DIR ne sont pas lues par Kernel. C'est MicroKernelTrait qui les lit ; et trois d'entre elles se voient ajouter l'environment, pas APP_LOG_DIR.

  • Voir l’explication : config/packages/test/ complète ou surcharge la configuration commune.

    config/packages/test/ complète ou surcharge la configuration commune. Il est chargé pour cet environnement seulement ; les valeurs se fusionnent selon l'arbre de configuration du bundle, sans supprimer tout le fichier commun.

  • Voir l’explication : public/ est la racine web recommandée.

    public/ est la racine web recommandée. Un fichier extérieur n'est pas servi directement dans cette configuration. Une réponse de téléchargement contrôlée par Symfony reste possible.

Application

À retenir en priorité
  1. Le cache sépare les environments.
  2. Le log directory par défaut n'ajoute pas cet environment.
  3. public/ est le document root.
  4. src/, config/ et vendor/ ne sont pas des directories publics.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • public/ : racine web ; var/ : cache et logs par défaut.
  • config/packages/<env>/ surcharge, dans cet environment seulement.
  • extra.*-dir pour bin, config, src, public ; config.vendor-dir pour vendor/.
  • Templates et translations : configuration de bundle, pas extra.
  • Cache avec l'environment, log sans.
  • APP_*_DIR : lues par MicroKernelTrait ; trois reçoivent l'environment.

Moyen mnémotechnique : « Composer, bundle, kernel : trois voies ».
