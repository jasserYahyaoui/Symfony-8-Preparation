Objectif

Nous savons quels objets rendent l'article 42. Il faut maintenant savoir où placer leur code, leur configuration et leurs résultats sans publier les fichiers internes du blog. Une URL comme /blog/42 ne désigne pas un fichier src/Controller/BlogController.php à télécharger : elle atteint l'entrée HTTP, puis le framework appelle le code approprié.

Nous allons lire l'arborescence standard de Symfony 8.0, puis résoudre deux besoins de déploiement : déplacer le cache et retrouver des templates rangés ailleurs. Le point décisif sera toujours le même : quel outil lit ce chemin ?

L'essentiel

À comprendre

À retenir en priorité
  1. public/ est le document root.
  2. src/, config/ et vendor/ ne sont pas des directories publics.

Le serveur web doit avoir public/ comme racine documentaire, c'est-à-dire comme point de départ des fichiers qu'il peut servir directement. Avec cette configuration, sans alias supplémentaire, le visiteur n'accède pas directement à config/, src/ ou vendor/. Le programme PHP peut pourtant les lire : ne pas publier le code n'empêche pas de l'exécuter.

var/ accueille habituellement les fichiers générés, notamment cache et logs. Le cache du kernel contient des éléments de fonctionnement préparés pour l'application ; il ne faut pas le confondre avec une Response HTTP mise en cache. Des écritures métier peuvent utiliser d'autres emplacements : var/ n'est pas une restriction universelle imposée au système de fichiers.

Conserver les conventions facilite le travail de l'équipe et des recipes. Quand un déplacement est nécessaire, trois familles de réglages interviennent : Composer et les outils qui lisent ses métadonnées, la configuration des bundles, ou les methods du kernel. Un changement de nom sur disque ne met pas automatiquement à jour tous ces lecteurs.

🌍 In Real Life

La situation : le restaurant expose une salle d'accueil, pas ses dossiers internes. Le personnel peut pourtant consulter ces dossiers pour répondre au client.

L’équivalent dans Symfony : espace directement accessible → racine web public/ ; dossiers internes → src/, config/, vendor/ ; travail du personnel → exécution PHP.

Retour à la réalité technique : la frontière dépend de la configuration du serveur, pas du nom du dossier. Un controller peut transmettre un fichier privé après autorisation. Le cache du kernel n'est pas un cache de réponses HTTP.

🧠 Comment le mémoriser : « Utilisé en interne ne veut pas dire publié. » Image mentale : comptoir devant une réserve fermée. Question-réflexe : quel chemin le serveur peut-il servir directement ?

⚠️ À ne pas confondre : URL /blog/42 et chemin d'un fichier source.

Le schéma

À retenir en priorité
  1. Le cache sépare les environments.
  2. Le log directory par défaut n'ajoute pas cet environment.

Pour GET /blog/42, le serveur transmet l'exécution à public/index.php selon sa configuration. Le chemin de l'URL ne fait pas entrer le navigateur dans src/. Une image déjà disponible sous public/ peut, au contraire, être servie sans exécuter le controller :

Les flèches pleines distinguent le traitement dynamique, les écritures et le service direct d'un fichier ; le pointillé représente l'accès au code et à la configuration. Bleu : acteurs ; orange : fichiers internes ; vert : résultats. Le dessin ne signifie pas que chaque Request relit chaque fichier de configuration ni qu'elle produit nécessairement un nouveau log.

La séparation repose sur la configuration du serveur, pas sur un pouvoir spécial du nom public. Exposer la racine du projet annulerait cette frontière. Inversement, un controller peut envoyer un document conservé hors de public/ après les contrôles d'accès nécessaires : « non servi directement » ne veut pas dire « impossible à télécharger ». Pour un export privé du blog, cette distinction évite de publier le document simplement pour pouvoir le transmettre.

L'exemple : sortir le cache de `var/`

Exemple concret

À retenir en priorité
  1. Surcharger getCacheDir() change le directory du cache.
  2. Conserver l'environment dans le path sépare les caches dev et prod.

Supposons un déploiement Linux où le code reste dans son emplacement habituel, mais où un répertoire temporaire privé et accessible au processus PHP doit recevoir le cache. Voici une method à placer dans la class App\Kernel existante, sans supprimer ses autres methods ni son trait :

// src/Kernel.php
public function getCacheDir(): string
{
    return '/tmp/app/cache/'.$this->environment;
}

Avec l'environnement prod, cette method renvoie /tmp/app/cache/prod ; avec dev, elle renvoie /tmp/app/cache/dev. Elle ne déplace pas elle-même les anciens fichiers : elle fournit le chemin que le kernel utilisera. Le nouvel emplacement doit être préparé avec les permissions appropriées et le cache nécessaire à ce déploiement doit y être reconstruit.

Le suffixe d'environnement évite de mélanger des configurations générées différentes. /tmp reste un exemple temporaire, potentiellement nettoyé par le système, non une recommandation de stockage durable ou partagé. Cette surcharge ne change ni public/ ni les templates. Elle peut en revanche influer sur les autres accessors qui délèguent par défaut à getCacheDir() ; nous les distinguerons après avoir situé les fichiers.

L'arborescence par défaut

Le controller de l'article et son ArticleCatalog appartiennent à notre code ; Twig appartient aux dépendances ; le template que l'équipe écrit est une ressource de l'application. L'arborescence évite de mélanger ces responsabilités :

Directory Role
assets/ sources front — JavaScript, CSS, images
bin/ exécutables, dont bin/console
config/ configuration ; packages/ par bundle, routes/, services.yaml
public/ seul directory exposé par le serveur web ; contient index.php
src/ le code, namespace App\, dont Kernel.php
templates/, translations/, tests/ templates Twig, catalogues, tests
var/ files générés à l'exécution : cache/, log/
vendor/ dependencies Composer — jamais modifié à la main
.env à la racine, pas dans config/

Cette carte décrit les conventions usuelles ; certains directories apparaissent avec les fonctionnalités installées. Pour préparer le rendu de l'article, on modifiera par exemple src/Controller/BlogController.php et templates/blog/show.html.twig, pas les fichiers du moteur Twig sous vendor/. Une personnalisation faite directement dans une dépendance peut disparaître à sa prochaine installation.

Le laboratoire suivant résume la frontière d'accès, sans créer ces fichiers :

projet/public/index.php      : entrée HTTP exécutée par PHP
projet/src/Controller/       : code applicatif chargé par PHP
projet/config/services.yaml : configuration interne des services
projet/var/cache/            : fichiers générés, pas source du catalogue

Le navigateur reçoit le résultat du traitement, pas ces sources internes. bin/console constitue une autre entrée pour une commande d'import ; elle peut utiliser le même code sous src/ sans passer par public/index.php. Les sources CSS ou JavaScript sous assets/ ne deviennent pas publiques par leur simple présence : leur mise à disposition dépend de l'outillage choisi, que cette carte ne configure pas.

Enfin, .env est situé à la racine dans cette organisation. Ni ce fichier ni les secrets de déploiement ne doivent être exposés par le serveur web.

Dans un atelier, public/ est le comptoir accessible, src/ l'établi, config/ le classeur de réglages et var/ les résultats temporaires du travail. Le comptoir ne doit pas devenir l'atelier entier.

Sous config/

À retenir en priorité
  1. La configuration commune reste la base.
  2. Le sous-directory d'environment fournit ses surcharges.

Le template du blog doit être plus strict pendant les tests : une variable oubliée doit signaler une erreur au lieu de passer inaperçue. Nous conservons une configuration commune et ne plaçons que cette différence dans le contexte test. Un environnement Symfony est ici un nom de contexte de configuration, tel que dev, test ou prod, pas nécessairement une machine distincte.

config/packages/ regroupe les réglages des bundles, habituellement répartis dans des fichiers nommés d'après eux ; ce n'est pas une obligation d'avoir exactement un fichier par bundle. Avec le chargement standard de MicroKernelTrait, les fichiers communs sont importés avant ceux de config/packages/<environnement>/.

Avec TwigBundle installé et actif, l'exemple conserve ces deux réglages :

# config/packages/twig.yaml
twig:
    strict_variables: false
# config/packages/test/twig.yaml
twig:
    strict_variables: true

Pour un accès direct à une variable Twig absente, sans valeur de repli dans le template, le mode test provoque une erreur ; le réglage commun ne le fait pas. Cet exemple suppose qu'aucune autre configuration ne remplace ces valeurs. La différence est celle du contexte de configuration, pas celle de la route blog_show : écrire le fichier dans test/ ne change pas prod.

Les valeurs se fusionnent selon l'arbre de configuration du bundle. « Surcharger » ne signifie donc pas supprimer aveuglément tout le fichier commun ni remplacer toutes les listes de tous les bundles de la même façon. Si le projet personnalise le chargement du kernel, il doit conserver ou redéfinir explicitement ces conventions.

Déplacer un directory

À retenir en priorité
  1. Déplacer src/ exige de corriger autoload.psr-4.
  2. composer dump-autoload reconstruit l'autoloading.

L'équipe veut maintenant ranger blog/show.html.twig sous resources/views/. C'est Twig qui recherche les templates : le réglage correspondant appartient à TwigBundle, pas à une key inventée de Composer. En conservant l'intégration Twig existante :

# config/packages/twig.yaml
twig:
    default_path: '%kernel.project_dir%/resources/views'

%kernel.project_dir% désigne la racine du projet. Après déplacement physique du template, le nom logique blog/show.html.twig permet de rechercher resources/views/blog/show.html.twig. Le réglage change le répertoire principal de recherche ; il ne déplace aucun fichier et ne modifie pas src/. Pour plusieurs répertoires, twig.paths permet de configurer des chemins supplémentaires. Pour les catalogues de traduction, la capacité correspondante se configure avec framework.translator.default_path plutôt qu'avec Twig.

Changer le lieu du code PHP pose un autre problème. Si src/ devient code/, la correspondance autoload.psr-4 de Composer doit associer le namespace App\ au nouveau chemin. PSR-4 est la convention qui permet de retrouver un fichier de class à partir de son namespace. Le réglage extra.src-dir, utilisé par l'outillage de projet, ne remplace pas cette correspondance. Il faut aussi vérifier les chemins de chargement des services et des routes qui mentionnaient l'ancien emplacement.

Dans le projet ainsi adapté, avec Composer 2.x, on régénère l'autoload :

composer dump-autoload

Résultat attendu : les fichiers d'autoload sont régénérés avec la nouvelle correspondance ; le texte exact affiché dépend des options et des scripts du projet. La commande ne déplace pas les classes et ne corrige pas des imports de configuration laissés sur src/.

Les métadonnées extra.bin-dir, extra.config-dir, extra.src-dir et extra.public-dir servent aux conventions de l'outillage, notamment aux recipes. config.vendor-dir appartient, lui, à la configuration de Composer pour son répertoire de dépendances. Ces clés ne constituent pas une commande universelle de déménagement de l'application.

Pour .env, une application utilisant Symfony Runtime peut définir extra.runtime.dotenv_path, puis régénérer l'autoload Runtime avec les opérations Composer appropriées. Le chemin doit désigner le fichier réellement placé au nouvel endroit ; nous ne modifions aucun secret dans cet exemple. Enfin, renommer ou déplacer public/ impose de régler la racine documentaire du serveur et de vérifier le chemin vers vendor/autoload_runtime.php dans index.php. Un renommage au même niveau peut laisser ce chemin relatif valide ; un changement de profondeur peut le casser.

🌍 In Real Life

La situation : déménager un atelier exige de prévenir chaque service qui utilise son adresse ; modifier un seul annuaire ne déplace aucun équipement.

L’équivalent dans Symfony : annuaire des classes → autoload Composer ; recherche des templates → Twig ; ressources services/routes → leurs imports ; accès public → configuration serveur.

Retour à la réalité technique : chaque lecteur possède son réglage. extra.src-dir ne remplace pas PSR-4 ; twig.default_path ne déplace pas les fichiers ; régénérer l'autoload ne corrige pas les anciens imports.

Les quatre accessors du kernel

Le cache déplacé au début du cours ne suffit pas à décrire tous les chemins du kernel. Un accessor est ici une method qui fournit une valeur de chemin. La class de base Kernel de HttpKernel utilise les valeurs suivantes :

Method Défaut
getCacheDir() <projet>/var/cache/<environnement>
getBuildDir() délègue à getCacheDir()
getShareDir(): ?string délègue à getCacheDir() ; peut rendre null
getLogDir() <projet>/var/log — sans l'environment

getBuildDir() permet de distinguer l'emplacement des fichiers construits pour l'application ; getShareDir() fournit un emplacement destiné aux données partagées. Leurs valeurs par défaut coïncident avec le cache : elles ne créent ni trois disques ni un système de fichiers partagé entre serveurs. Si plusieurs serveurs doivent voir les mêmes données, cette mise à disposition doit être assurée par le déploiement.

Le kernel habituel de l'application emploie MicroKernelTrait, fourni par FrameworkBundle. Ce trait lit dans $_SERVER les valeurs APP_CACHE_DIR, APP_BUILD_DIR, APP_SHARE_DIR et APP_LOG_DIR. La class de base Kernel, seule, ne leur donne pas cet effet.

Pour un projet situé dans /srv/blog, en prod, et sans surcharge de ces methods dans notre class, voici des entrées et leurs résultats :

Valeur disponible pour le trait Résultat
APP_CACHE_DIR=/data/cache getCacheDir() rend /data/cache/prod
APP_BUILD_DIR=var/build getBuildDir() rend /srv/blog/var/build/prod
APP_SHARE_DIR=/data/shared getShareDir() rend /data/shared/prod
APP_LOG_DIR=/data/log getLogDir() rend /data/log

Les trois premiers chemins passent par getEnvDir(), qui ajoute /<environnement> et résout les chemins relatifs depuis la racine du projet. APP_LOG_DIR est prise telle quelle : ce trait n'y ajoute ni environnement ni racine du projet. On préfère donc un chemin absolu explicite pour ce réglage.

APP_SHARE_DIR comporte aussi un choix de désactivation : une valeur reconnue comme fausse, par exemple la chaîne false, fait rendre null à getShareDir(). Le paramètre %kernel.share_dir% n'est alors pas enregistré ; un service ne peut pas supposer sa présence. Sans ce choix ni chemin spécifique, le comportement hérité reste applicable.

Ces variables représentent une alternative à une surcharge explicite de method comme notre premier exemple. Une method définie dans la class prend le pas sur celle importée du trait : ne mélangeons pas les deux expériences pour conclure que APP_CACHE_DIR devrait toujours gagner.

🌍 In Real Life

La situation : un plan donne plusieurs adresses de stockage, parfois identiques par défaut ; écrire « partagé » ne construit pas un entrepôt commun entre sites.

L’équivalent dans Symfony : adresses → accessors cache/build/share/log ; interprète des APP_*_DIR → MicroKernelTrait.

Retour à la réalité technique : le trait ajoute l'environnement aux trois premiers chemins, pas aux logs. Share peut être désactivé ; une surcharge de méthode dans la classe prime sur le trait. Les chemins ne fournissent ni permissions ni stockage réseau.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le template existe, mais Twig ne le trouve plus.

    Le template existe, mais Twig ne le trouve plus. Après son déplacement, chercher une key extra.templates-dir ne résout rien : ce n'est pas l'option prévue. Le chemin principal relève de twig.default_path, les chemins supplémentaires de twig.paths. Les traductions et les dépendances ont encore leurs propres lecteurs : framework.translator.default_path et config.vendor-dir.

  • Voir l’explication : La class existe, mais l'autoload cherche encore dans src/.

    La class existe, mais l'autoload cherche encore dans src/. extra.src-dir seul ne corrige pas autoload.psr-4. La régénération de l'autoload ne corrige pas non plus un ancien chemin de ressource dans la configuration des services. Il faut distinguer ces deux recherches.

  • Voir l’explication : Le cache reste à son emplacement par défaut malgré une variable définie.

    Le cache reste à son emplacement par défaut malgré une variable définie. Vérifions que le kernel utilise le trait qui la lit et qu'une surcharge locale ne court-circuite pas sa method. Pour la certification, distinguons aussi les trois chemins suffixés par l'environnement du chemin de logs pris tel quel.

  • Voir l’explication : Le test est strict, la production ne l'est pas.

    Le test est strict, la production ne l'est pas. Un réglage placé uniquement dans config/packages/test/ n'est pas une configuration globale. La fusion avec le commun dépend du bundle ; le sous-répertoire ne remplace pas automatiquement tous les réglages communs.

  • Voir l’explication : Un export privé doit être téléchargeable, pas directement public.

    Un export privé doit être téléchargeable, pas directement public. Le placer hors de public/ est compatible avec une Response de téléchargement contrôlée. À l'inverse, choisir la racine entière du projet comme racine web pour rendre l'export accessible exposerait aussi des fichiers internes.

Application

À retenir en priorité
  1. Le cache sépare les environments.
  2. Le log directory par défaut n'ajoute pas cet environment.
  3. public/ est le document root.
  4. src/, config/ et vendor/ ne sont pas des directories publics.

Fiche express

À mémoriser

Avant de déployer le rendu de l'article 42, six vérifications relient les chemins à leurs lecteurs :

  1. Le serveur expose public/, pas la racine entière ; PHP peut charger le code interne sans le rendre téléchargeable directement.
  2. var/ reçoit cache et logs par défaut, sans imposer l'emplacement de toutes les écritures métier.
  3. Le chargement standard fusionne la configuration commune puis celle du contexte courant ; test/ ne change pas prod.
  4. Les métadonnées extra.*-dir guident l'outillage ; config.vendor-dir règle Composer. Déplacer src/ exige aussi un autoload cohérent.
  5. Twig et les traductions recherchent leurs ressources selon la configuration des bundles, pas selon une key extra.templates-dir.
  6. MicroKernelTrait lit les quatre APP_*_DIR présentées ; cache, build et share reçoivent le suffixe d'environnement, log non. Share peut être désactivé.

« Composer, bundle, kernel : trois voies » aide à choisir le lecteur concerné, mais ne dispense pas de vérifier les autres références au chemin déplacé. Si le blog échoue encore après ces vérifications, nous pourrons distinguer une mauvaise organisation des fichiers d'une exception pendant le traitement.
