Objectif

Construire la bonne sous-classe de Response et distinguer ses methods de test — dont deux sont dangereusement proches.

L'essentiel

○ À comprendre

À retenir en priorité
  1. isRedirection() teste la class 3xx.
  2. isRedirect() suit une liste distincte de statuts.

Un controller rend une Response — ou une sous-classe spécialisée — et ne l'envoie pas : c'est le runner du component Runtime qui l'émet, une fois. L'examen vise surtout les methods de test, dont deux sont dangereusement proches : isRedirection() (la class 3xx) et isRedirect() (une liste qui inclut 201 et exclut 304).

Le schéma

À retenir en priorité
  1. Le controller retourne une Response.
  2. Le runner appelle send(false), finalise selon disponibilité/debug puis appelle terminate() si TerminableInterface ; la réception complète par le client n'est pas garantie.

L'exemple : la bonne sous-classe

▣ Exemple concret

À retenir en priorité
  1. JsonResponse encode des données PHP.
  2. fromJsonString() accepte un document JSON déjà encodé.
return new JsonResponse(['id' => 42], Response::HTTP_CREATED);
return new RedirectResponse('/orders/42');           // 302 par défaut
return JsonResponse::fromJsonString($alreadyEncoded);
return new BinaryFileResponse('/var/exports/report.pdf');

La class de base

○ À comprendre

C'est quoi ?

Une Response rassemble statut, headers et contenu. Ses sous-classes spécialisent la manière de produire ce contenu ou les en-têtes associés : elles évitent de reproduire manuellement des comportements HTTP déjà implémentés.

À quoi ça sert ?

  • JsonResponse encode des données et annonce JSON ; fromJsonString() accepte du JSON déjà encodé sans l'encoder une deuxième fois.
  • RedirectResponse annonce une cible via Location, avec 302 par défaut.
  • BinaryFileResponse sert un fichier et gère les demandes de plage prévues par son intégration.
  • StreamedResponse produit le contenu par un callable ; StreamedJsonResponse permet une production JSON depuis des données itérables.

Où dans Symfony ?

ResponseHeaderBag porte les headers et cookies. prepare($request) adapte la réponse au contexte, notamment pour HEAD et les statuts sans contenu. Dans le parcours du framework, cette préparation est assurée ; un programme qui utilise seulement le component doit gérer son propre cycle. La construction seule n'émet rien.

Comment, étape par étape ?

  1. Déterminer si la donnée est déjà encodée, un fichier ou un contenu produit progressivement.
  2. Choisir la sous-classe correspondante.
  3. Définir statut et headers cohérents.
  4. Retourner l'objet au framework au lieu de l'envoyer depuis le controller.

Exemple concret PHP

Avec HttpFoundation 8.0 chargé :

<?php
use Symfony\Component\HttpFoundation\JsonResponse;
$response = new JsonResponse(['id' => 42], 201);
$alreadyEncoded = JsonResponse::fromJsonString('{"id":42}', 201);
echo $response->getStatusCode(), "\n";
echo $alreadyEncoded->getContent(), "\n";

On attend 201, puis {"id":42}. Contre-exemple : passer la chaîne JSON à new JsonResponse($json) en pensant qu'elle sera reconnue comme déjà encodée ; elle devient une valeur chaîne JSON. Correction : transmettre les données à encoder ou utiliser fromJsonString(). Les options d'encodage de JsonResponse peuvent échapper certains caractères : comparer des données décodées est souvent plus pertinent que supposer une chaîne identique à un json_encode() sans options.

Passage canonique conservé

La class de base

$response->headers est un ResponseHeaderBag, qui porte aussi les cookies. Une Response neuve est en HTTP/1.0 : prepare($request) la promeut en 1.1, vide le body sur un HEAD ou un statut sans corps et complète le Content-Type. Le kernel l'appelle ; une Response fabriquée hors du cycle, non.

Class Usage
JsonResponse encode en JSON, pose le Content-Type ; fromJsonString() n'encode pas deux fois
RedirectResponse pose Location, statut 302 par défaut
BinaryFileResponse sert un file, Requests de plage comprises
StreamedResponse body produit par un callable, sans tout charger
StreamedJsonResponse JSON diffusé à partir d'un itérable

JsonResponse n'écrit pas le JSON de json_encode() : elle ajoute quatre options d'escaping HTML. Comparer les données décodées, jamais la string.

La Response rassemble l'enveloppe de retour : status code, headers et body. prepare() adapte cette enveloppe à la Request avant que l'émission ait lieu ; construire son contenu ne signifie pas l'avoir déjà envoyé.

`isRedirect()` contre `isRedirection()`

○ À comprendre

C'est quoi ?

isRedirection() teste la classe numérique 300 à 399. isRedirect() teste une liste précise de statuts : 201, 301, 302, 303, 307, 308. Les deux prédicats ne sont donc pas équivalents, et aucun n'englobe entièrement l'autre.

À quoi ça sert ?

Un test doit vérifier la propriété voulue. Pour une classe générale de statut, utiliser la classification numérique ; pour vérifier une redirection vers une cible dans le sens de l'API Symfony, utiliser le prédicat spécifique avec la cible lorsque nécessaire.

Où dans Symfony ?

Sans argument, isRedirect() ne vérifie pas à lui seul la présence effective d'un header Location : il teste la liste. Avec une URL, il compare aussi la valeur de Location. RedirectResponse utilise ce prédicat pour accepter son statut ; le sens de cette API est donc plus particulier que le mot français « redirection ».

Comment, étape par étape ?

  1. Lire le statut exact.
  2. Pour isRedirection(), vérifier l'intervalle 3xx.
  3. Pour isRedirect(), vérifier l'appartenance à la liste.
  4. Si une cible est passée, comparer également Location.

Exemple concret PHP

<?php
use Symfony\Component\HttpFoundation\Response;
foreach ([201, 300, 304, 307] as $status) {
    $response = new Response('', $status);
    printf("%d: redirect=%d redirection=%d\n", $status,
        $response->isRedirect(), $response->isRedirection());
}

On attend 201: 1/0, 300: 0/1, 304: 0/1, 307: 1/1 pour les deux valeurs booléennes affichées. Contre-exemple : traiter 304 comme une nouvelle navigation parce que isRedirection() est vrai. Correction : appliquer son sens précis de validation d'une copie. De même, 201 vrai pour isRedirect() ne signifie pas que tout succès de création exige une navigation client.

Passage canonique conservé

isRedirect() contre isRedirection()

  • isRedirection() est la class 3xx, littéralement.
  • isRedirect() est la liste des statuts qui portent un Location : elle inclut 201 et exclut 300 et 304. Avec une URL en argument, elle vérifie aussi Location — pratique en functional test.

Les deux ne sont ni équivalentes ni imbriquées : un 304 est 3xx sans être un redirect. La même liste valide le statut de RedirectResponse : new RedirectResponse($url, 304) lève une InvalidArgumentException, new RedirectResponse($url, 201) est accepté.

Autres methods de test

○ À comprendre

À retenir en priorité
  1. isOk() vérifie 200 précisément.
  2. isSuccessful() vérifie toute la class 2xx.

C'est quoi ?

Une méthode de test de Response est un prédicat : elle retourne vrai ou faux sur une propriété du statut. Certaines reconnaissent une classe entière, d'autres un code exact. isOk() signifie 200 exactement ; isSuccessful() couvre tous les 2xx.

À quoi ça sert ?

Un test trop large peut accepter un résultat incorrect pour le contrat de l'action ; un test trop étroit peut refuser un succès volontaire comme 201 Created ou 204 No Content. Il faut d'abord savoir ce que l'API promet.

Où dans Symfony ?

isClientError() couvre les 4xx et isServerError() les 5xx. isNotFound() vise 404 seulement. Ces méthodes classent un nombre ; elles ne vérifient pas que le body correspond au statut ni que le traitement métier a réellement réussi.

Comment, étape par étape ?

  1. Définir le résultat attendu de l'action.
  2. Choisir code exact ou famille selon ce contrat.
  3. Vérifier séparément headers et contenu nécessaires.
  4. Ne pas traiter un prédicat vrai comme preuve de toutes les autres propriétés HTTP.

Exemple concret PHP

<?php
use Symfony\Component\HttpFoundation\Response;
$response = new Response('', Response::HTTP_NO_CONTENT);
var_export($response->isOk());
echo "\n";
var_export($response->isSuccessful());
echo "\n";

Les sorties attendues sont false puis true : 204 est un succès, pas 200. Contre-exemple : un test de création accepte n'importe quel 2xx alors que le contrat exige 201 et une localisation de la ressource. Correction : vérifier ce statut précis et le header attendu. À l'inverse, ne pas annoncer un échec seulement parce qu'un 204 donne faux à isOk().

Passage canonique conservé

Autres methods de test

isSuccessful() teste la class 2xx, isOk() 200 exactement ; isClientError() la class 4xx, isNotFound() 404 exactement ; isServerError() la class 5xx.

L'émission : `send()`, et qui l'appelle

○ À comprendre

C'est quoi ?

Une Response est un objet qui contient le statut, les headers — les champs d'en-tête HTTP — et le body, c'est-à-dire le contenu à transmettre. La construire n'envoie rien. send() déclenche l'émission : d'abord sendHeaders(), puis sendContent(). Son argument $flush décide ensuite si la méthode demande aussi la finalisation ou le vidage des buffers, les zones où la sortie peut être retenue avant transmission.

kernel.terminate est un event, un événement auquel des fonctions peuvent réagir, déclenché par terminate() après le traitement principal. Dans le parcours du runner HTTP de Runtime — l'objet qui conduit l'exécution de l'application — cet appel vient après send(false). Cet ordre d'appels ne garantit pas, sur tous les serveurs et dans tous les modes, que le client ait déjà reçu la réponse complète.

À quoi ça sert ?

Séparer construction et émission permet au framework d'inspecter et de modifier la Response avant sa transmission : statut, cookies, headers et contenu restent regroupés dans un objet. Un controller retourne cet objet au lieu d'écrire directement dans la connexion.

Un traitement dans kernel.terminate ne doit pas servir à fabriquer le résultat HTTP que le client attend. Lorsqu'une finalisation anticipée est disponible et utilisée, les modifications arrivent trop tard. Dans d'autres conditions, le client peut au contraire attendre la fin de ces listeners, les fonctions abonnées à l'événement. Il est donc faux de promettre qu'un travail lent y est toujours sans coût pour l'utilisateur. Le processus PHP reste occupé pendant ce travail ; le déplacer ici n'en fait pas une tâche exécutée par un autre processus.

Où dans Symfony ?

Response appartient à HttpFoundation. HttpKernel transforme une Request, l'objet représentant la demande HTTP, en Response. HttpKernelRunner, dans Runtime, organise l'envoi puis appelle terminate() si le kernel implémente TerminableInterface, le contrat qui expose cette méthode.

En Symfony 8.0, ce runner appelle send(false). Hors mode debug, il utilise fastcgi_finish_request() si cette fonction est disponible, sinon litespeed_finish_request() si elle l'est. Dans les autres cas, il ferme les buffers de sortie et appelle flush(). La disponibilité des fonctions, le mode debug et le serveur comptent donc : « après send » ne signifie pas universellement « le client est libéré ».

Comment, étape par étape ?

  1. Le controller construit et retourne la Response. Il n'appelle pas send() et ne produit pas son body avec echo.
  2. Le cycle du kernel laisse les listeners de kernel.response traiter l'objet avant de le retourner.
  3. Le runner appelle send(false) : les headers et le contenu sont émis, sans laisser Response::send() réaliser elle-même l'étape finale de vidage.
  4. Le runner choisit la finalisation adaptée à l'environnement, puis appelle terminate() si ce contrat est disponible.
  5. Les listeners de kernel.terminate exécutent leur travail. Une modification nécessaire au résultat HTTP doit avoir eu lieu avant l'envoi ; la réception effective par le client dépend de l'environnement décrit ci-dessus.

Exemple concret PHP

Cet extrait suppose l'autoload Composer d'un projet disposant de HttpFoundation 8.0 déjà chargé. Il isole une action de controller : confirmation() retourne un objet, sans l'envoyer. Le petit contrôle en ligne de commande affiche 200, puis Enregistré. Il inspecte l'objet ; ce n'est pas une émission HTTP et il ne mesure pas le délai perçu par un navigateur.

<?php
use Symfony\Component\HttpFoundation\Response;

function confirmation(): Response
{
    return new Response('Enregistré', Response::HTTP_OK, [
        'Content-Type' => 'text/plain; charset=UTF-8',
    ]);
}

$response = confirmation();
echo $response->getStatusCode(), "\n";
echo $response->getContent(), "\n";

Contre-exemple : un controller fait echo 'Enregistré', appelle send(), puis retourne la même Response. Il contourne la construction normale du body et risque une émission prématurée ou répétée. Correction : retourner seulement l'objet, comme ci-dessus, et laisser le runner l'envoyer. Autre conclusion incorrecte : « un calcul de dix secondes dans terminate ne ralentit jamais le client ». La correction est de distinguer l'ordre d'exécution de la finalisation réellement permise par le serveur.

Référence : cycle HttpKernel Symfony 8.0, dont les limites de kernel.terminate.

Passage canonique conservé

L'émission : send(), et qui l'appelle

send() appelle sendHeaders() puis sendContent(). Avec $flush=false, il retourne sans finaliser ; sinon, il utilise fastcgi si disponible, puis litespeed en alternative, ou les buffers/flush hors CLI, phpdbg et embed. Le controller rend la Response ; le runner gère son émission : Dans Runtime 8.0, HttpKernelRunner::run() appelle send(false), puis finalise la sortie : fastcgi_finish_request() si disponible hors debug, sinon litespeed_finish_request() si disponible hors debug, sinon clôture des buffers et flush(). Il appelle ensuite terminate() seulement si le kernel implémente TerminableInterface. Cet ordre ne garantit pas que le client ait déjà reçu toute la réponse. Le processus PHP reste occupé pendant le travail des listeners.

Si les headers sont déjà partis, sendHeaders() tente seulement de réémettre la ligne de statut. Exécuté sous php -S, un echo avant send() donne un E_WARNING Cannot modify header information, et un 404 arrive en 200 : pas d'exception, mais un avertissement, et un statut perdu.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : isRedirect() n'est pas « le statut est 3xx ».

    isRedirect() n'est pas « le statut est 3xx ». Retenir 201 inclus, 304 exclu.

  • Voir l’explication : send() n'appartient pas au controller.

    send() n'appartient pas au controller. Un controller retourne une Response ; il ne l'envoie pas. Et le runner l'appelle avec false, pas avec le défaut.

  • Voir l’explication : isOk() n'est pas isSuccessful()

    isOk() n'est pas isSuccessful() : le premier teste 200 exactement, le second toute la class 2xx.

  • Voir l’explication : Un RedirectResponse renvoie 302 par défaut

    Un RedirectResponse renvoie 302 par défaut ; un permanent demande new RedirectResponse($url, 301).

  • Voir l’explication : Son constructor valide le statut avec isRedirect()

    Son constructor valide le statut avec isRedirect() et lève une \InvalidArgumentException sinon. Conséquence directe de la liste ci-dessus : new RedirectResponse($url, 304) échoue, alors que new RedirectResponse($url, 201) est accepté.

Application

À retenir en priorité
  1. isOk() vérifie 200 précisément.
  2. isSuccessful() vérifie toute la class 2xx.
  3. Le controller retourne une Response.
  4. Le runner appelle send(false), finalise selon disponibilité/debug puis appelle terminate() si TerminableInterface ; la réception complète par le client n'est pas garantie.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • Le controller rend, le runner émet — avec send(false).
  • isRedirection() = 3xx ; isRedirect() = 201, 301, 302, 303, 307, 308.
  • RedirectResponse : 302 par défaut ; refuse 304, accepte 201.
  • isOk() = 200 pile ; isSuccessful() = 2xx.
  • Response neuve en HTTP/1.0 ; prepare() corrige.
  • JsonResponse échappe le HTML ; fromJsonString() n'encode pas.
  • Headers déjà partis : E_WARNING, statut perdu.

Moyen mnémotechnique : « 201 dedans, 304 dehors ».
