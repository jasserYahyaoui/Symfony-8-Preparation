Objectif

Savoir où une valeur de configuration est écrite, qui l'emporte quand plusieurs sources la définissent, et comment une expression peut la calculer.

L'essentiel

À comprendre

À retenir en priorité
  1. Le système fournit la valeur prioritaire.
  2. Dotenv complète normalement les valeurs manquantes.

Un parameter est figé à la compilation du container ; une variable d'environment est lue à l'exécution. Les files .env se chargent en cascade — le dernier chargé gagne —, mais une vraie variable du serveur passe avant eux. Et ExpressionLanguage évalue ou compile une expression d'une ligne, écrite en configuration.

Le schéma

À retenir en priorité
  1. Le moment de résolution diffère.
  2. Un placeholder permet de garder une valeur dépendante du serveur.

L'exemple

Exemple concret

À retenir en priorité
  1. Les variables sont des strings.
  2. Le processor impose la conversion attendue.
# config/services.yaml
parameters:
    app.admin_email: 'admin@example.com'          # figé à la compilation
    app.port: '%env(int:PORT)%'                    # lu à l'exécution, converti
# .env          → PORT=8000           (versionné, valeur par défaut)
# .env.local    → PORT=8080           (ce poste, hors test)
# .env.prod     → PORT=80             (la production, versionné)
# serveur       → export PORT=443     (vraie variable : elle gagne)

Deux mécanismes, deux moments

À comprendre

À retenir en priorité
  1. Le code compilé peut rester identique.
  2. La résolution fournit les valeurs propres à la machine.

C'est quoi ?

Un parameter du container est une valeur de configuration utilisée lors de sa construction. Une référence %env(NOM)% conserve une résolution liée à l'environment d'exécution. Dotenv fournit des valeurs depuis des fichiers lorsque les vraies variables ne les ont pas déjà fournies dans le fonctionnement standard.

À quoi ça sert ?

Le même code compilé peut ainsi servir sur plusieurs machines avec des valeurs d'exploitation différentes. Cela ne signifie pas que chaque service déjà construit relit une variable à chaque appel.

Où dans Symfony ?

Les parameters se déclarent notamment sous parameters dans services.yaml. Les références %env(...)% peuvent employer des processors pour convertir les strings en types attendus, par exemple int pour une limite numérique.

Comment, étape par étape ?

  1. Dans le chargement Dotenv standard, lire les valeurs générales, puis les surcharges : .env, .env.local, .env.<environment>, .env.<environment>.local.
  2. En test, ignorer .env.local afin d'éviter les réglages personnels généraux ; les fichiers propres à test restent distincts.
  3. Les vraies variables d'environment restent prioritaires par défaut. Ne pas activer une politique d'écrasement pour contourner un diagnostic.
  4. Un dump .env.local.php compatible avec l'environment peut remplacer l'analyse des fichiers. Après un changement des valeurs dumpées, régénérer ce dump ; vider seulement un cache ne réécrit pas les valeurs qu'il contient.

Exemple concret YAML

Fragment de configuration d'un paramètre numérique alimenté par l'exploitation :

parameters:
    app.page_size: '%env(int:APP_PAGE_SIZE)%'

La variable APP_PAGE_SIZE doit être fournie avec une valeur entière appropriée. Le processor convertit son type ; le service consommateur doit encore valider les limites métier, par exemple refuser une taille négative.

Contre-exemple : modifier un fichier de valeurs puis attendre qu'un processus long déjà initialisé reconstruise spontanément toutes ses dependencies. Correction : distinguer source des valeurs, résolution des références et cycle de vie des services ; redémarrer les processus concernés lors du déploiement. Aucun contenu de fichier d'environment ni secret n'est lu ou affiché dans cette mission.

Les parameters

À retenir en priorité
  1. Le tag enum conserve le case.
  2. Ne pas le confondre avec sa backing value.
parameters:
    app.supported_locales: ['en', 'es', 'fr']
    app.some_constant: !php/const App\Entity\BlogPost::MAX_ITEMS
    app.some_enum: !php/enum App\Enum\PostState::Published
  • !php/enum donne le case lui-même, l'object enum ; !php/const, la valeur de la constant.
  • Un % littéral se double : 'a %%s b' est lu a %s b.
  • Le préfixe app. est une convention.

La cascade `.env`

À retenir en priorité
  1. Les tests évitent les réglages personnels généraux.
  2. Les couches propres à test restent disponibles.
File Portée Versionné
.env default values, tous environments oui
.env.local cette machine — ignoré en test non
.env.<env> un environment oui
.env.<env>.local cette machine, un environment non
  • Entre les files, le dernier chargé gagne, dans cet ordre : en dev, .env.dev l'emporte sur .env.local.
  • Une vraie variable d'environment l'emporte sur les files .env, qui ajoutent seulement ce qui manque — sauf si Dotenv est appelé avec overrideExistingVars: true. variables_order doit contenir E.
  • .env est relu à chaque Request : aucun cache à vider.
  • composer dump-env prod écrit .env.local.php ; s'il existe, et si son APP_ENV correspond, les files .env ne sont plus analysés. La command dotenv:dump exige de déclarer le service DotenvDumpCommand.
  • bootEnv() fixe APP_DEBUG quand il manque : '1' en dev, '0' en prod, une string.
  • Syntaxe : #, ${AUTRE_VAR}, ${VAR:-defaut} ; guillemets simples = littéral, doubles = interpolation.

Les processeurs d'environment

À retenir en priorité
  1. La chaîne transforme progressivement la valeur.
  2. Inverser les processors peut changer ou casser le résultat.

Une variable d'environment est une string ; un processeur la convertit, et ils se chaînent de droite à gauche :

Référence Valeur
%env(bool:APP_DEBUG)%, avec 0 false
%env(json:base64:CONFIG)% base64 décodé, puis JSON lu : l'array
%env(base64:json:CONFIG)% RuntimeException : Invalid JSON in env var "CONFIG"

ExpressionLanguage

Exemple concret

À retenir en priorité
  1. ExpressionLanguage possède sa syntaxe.
  2. Ne pas transposer les opérateurs PHP sans vérifier.

C'est quoi ?

ExpressionLanguage est un langage d'expressions distinct de PHP. Il évalue une expression à partir de valeurs explicitement fournies ; sa syntaxe n'est pas celle d'un script PHP complet.

À quoi ça sert ?

Une règle courte peut être exprimée dans une configuration, par exemple une condition. Pour une logique métier complexe, un service testable reste plus lisible qu'une expression de plus en plus longue.

Où dans Symfony ?

Le component propose evaluate() pour obtenir un résultat et compile() pour obtenir une représentation PHP. Compiler ne signifie pas exécuter. Les intégrations du framework définissent les variables et fonctions disponibles dans leur propre contexte.

Comment, étape par étape ?

  1. Définir les variables autorisées et l'expression contrôlée par l'application.
  2. Vérifier la syntaxe ; une variable ou fonction inconnue doit être diagnostiquée.
  3. Évaluer avec les valeurs appropriées, ou compiler si l'intégration a besoin de code généré.
  4. Ne pas interpréter librement des expressions arbitraires fournies par un utilisateur non fiable : les objets exposés peuvent donner accès à leurs méthodes.

Exemple concret PHP

Avec symfony/expression-language 8.0 installé :

<?php
use Symfony\Component\ExpressionLanguage\ExpressionLanguage;

$language = new ExpressionLanguage();
echo $language->evaluate('quantity * unitPrice', [
    'quantity' => 3,
    'unitPrice' => 20,
]), PHP_EOL;
echo $language->compile('1 + 2'), PHP_EOL;

Le premier appel calcule 60 ; le second produit (1 + 2), une chaîne de code, pas le nombre 3. Contre-exemple : traiter le résultat de compile() comme si la règle avait déjà été évaluée. Correction : choisir l'opération selon le résultat attendu. Le langage utilise notamment ~ pour concaténer ; ne pas transposer les opérateurs PHP sans vérifier leur sens.

ExpressionLanguage 8.0.

Passage canonique conservé

ExpressionLanguage

$el = new ExpressionLanguage();
$el->evaluate('1 + 2');   // 3 — évalué, sans compilation
$el->compile('1 + 2');    // '(1 + 2)' — compilé en PHP, donc cachable
  • parse() rend un ParsedExpression ; lint() ne rend rien et lève une SyntaxError — variable ou function inconnue, sauf flags Parser::IGNORE_*.
  • ~ concatène : "Hi " ~ name donne Hi Ana ; + sur une string lève une TypeError. in, properties, methods et ternaire sont acceptés.
  • Dans le framework : une condition de route, une règle d'authorization.

Fiche express

À mémoriser

À retenir en priorité
  1. Évaluer exécute l'expression.
  2. Compiler produit une représentation exécutable.

Si tu dois retenir seulement 8 choses :

  • Parameter : compilation ; %env()% : exécution.
  • .env → .env.local → .env.<env> → .env.<env>.local ; le dernier gagne.
  • .env.local ignoré en test.
  • Vraie variable > .env, sauf overrideExistingVars: true.
  • .env.local.php remplace les .env (même APP_ENV).
  • .env relu à chaque Request : pas de cache.
  • Processeurs de droite à gauche ; %% = %.
  • ExpressionLanguage : evaluate() / compile() / lint(), ~ concatène.

Moyen mnémotechnique : « Compilé ou lu ; le dernier gagne ; le serveur d'abord ».

parameter = compilé, %env()% = lu ; .env < .env.local (sauf test) < .env.ENV < .env.ENV.local < vraie variable (sauf override) ;
.env.local.php court-circuite tout ; processeurs droite→gauche ; EL : evaluate/compile/lint, ~ concatène
