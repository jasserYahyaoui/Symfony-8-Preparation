L'essentiel

À comprendre

À retenir en priorité
  1. Le résultat est une liste de violations.
  2. Une donnée invalide ne produit pas un bool.

Le Validator confronte une valeur à des constraints et rend toujours une liste de violations — vide si tout va bien, jamais un bool. Une donnée invalide ne lève rien ; une constraint mal configurée, si. Hors framework, createValidator() ne lit pas les attributes.

Le fil rouge : un `User` et son adresse

À retenir en priorité
  1. Le property path localise la donnée.
  2. La descente conserve le chemin de l'object imbriqué.
class User
{
    #[Assert\NotBlank]
    #[Assert\Email]
    public string $email = 'x';

    #[Assert\Length(min: 3)]
    public string $name = 'ab';

    #[Assert\Valid]
    public Address $address;          // Address::$city porte #[Assert\NotBlank], vide
}

Trois violations : email, address.city, name.

Les trois manières de valider

À comprendre

À retenir en priorité
  1. La valeur candidate peut être testée avant affectation.
  2. Les metadata de la property fournissent les constraints.

C'est quoi ?

Une constraint, contrainte, décrit une règle. Le validator exécute les règles applicables et retourne une liste de violations, constats d'échec avec message et chemin. Une liste vide signifie qu'aucune règle exécutée n'a signalé d'erreur ; elle ne prouve pas qu'on a chargé toutes les règles voulues.

À quoi ça sert ?

Trois entrées répondent à des besoins différents : validate($object) vérifie l'objet, y compris les contraintes de classe ; validateProperty($object, 'email') vise une propriété existante ; validatePropertyValue(User::class, 'email', $candidate) contrôle une valeur candidate selon les métadonnées de cette propriété, avant de l'affecter. Ce dernier contrôle ne remplace pas une validation complète des relations entre propriétés.

Où dans Symfony ?

Le service du framework implémente ValidatorInterface. Hors framework, Validation::createValidator() suffit pour des contraintes explicitement passées, mais la lecture des attributes nécessite un builder avec enableAttributeMapping(). Déclarer #[Assert\Email] sans activer son chargement ne fait pas exécuter la règle.

Comment, étape par étape ?

  1. Choisir la portée : objet, propriété ou valeur candidate.
  2. S'assurer que le format des métadonnées est chargé.
  3. Appeler la méthode avec le groupe approprié, puis compter les violations.
  4. Présenter les messages et chemins utiles ; distinguer donnée refusée et configuration invalide, cette dernière pouvant lever une exception.

Exemple concret PHP

Avec Validator 8.0 et son autoload :

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

final class Contact
{
    #[Assert\Email]
    public string $email = '';
}

$validator = Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator();
$errors = $validator->validatePropertyValue(Contact::class, 'email', 'sans-arobase');
echo count($errors), "\n";
foreach ($errors as $error) {
    echo json_encode($error->getPropertyPath()), "\n";
}

On attend une violation et un chemin vide, affiché "" par json_encode : cet appel fournit un nom de classe, pas une instance. Les métadonnées de la propriété email sont utilisées sans créer ni modifier Contact. En passant une instance à validatePropertyValue(), le chemin inclut email. Contre-exemple : if ($errors) pour savoir s'il y a une erreur. La liste est un objet et reste vraie en contexte booléen, même vide. Correction : count($errors) > 0. Autre limite : Email accepte une valeur vide ; ajouter une contrainte de présence si le besoin exige une adresse renseignée.

Les trois manières de valider

Besoin Method
tout l'object, constraints de class comprises validate($object)
une property d'un object existant validateProperty($object, 'email')
une valeur avant de l'affecter validatePropertyValue(User::class, 'email', $candidat)
une valeur isolée, sans class validate($valeur, new Assert\Email())
  • Chaque method accepte les groups en dernier argument ; un group qu'aucune constraint ne porte rend une liste vide, sans erreur.
  • validateProperty() sur une property inexistante rend une liste vide.
  • Hors framework : Validation::createValidator() donne 0 violation sur le User ; createValidatorBuilder()->enableAttributeMapping()->getValidator() en donne 3. Dans une application, on injecte ValidatorInterface.

Ce qu'il retourne : une liste, jamais un bool

À comprendre

À retenir en priorité
  1. Une liste vide reste un object.
  2. count() distingue succès et violations.

C'est quoi ?

Une ConstraintViolation décrit une règle non satisfaite : message, emplacement, valeur en cause et autres métadonnées. Validator retourne une ConstraintViolationListInterface, liste d'objets violation ; il ne retourne pas directement vrai ou faux.

À quoi ça sert ?

Une interface peut afficher plusieurs problèmes et les rattacher aux bonnes données. Le code appelant peut distinguer un message destiné à l'utilisateur d'un code stable destiné au programme, sans analyser le texte traduit pour prendre une décision.

Où dans Symfony ?

validate traite une valeur ou un objet selon les contraintes sélectionnées. Une liste vide signifie aucune violation trouvée par ces contrôles, pas une preuve universelle de validité ni la présence de toutes les contraintes souhaitées. debug:validator aide à examiner les contraintes configurées sur une classe.

Comment, étape par étape ?

  1. Définir les contraintes réellement à exécuter.
  2. Appeler validate.
  3. Tester le nombre de violations, et non la conversion booléenne de l'objet liste.
  4. Parcourir les violations et utiliser getPropertyPath, getMessage et, si nécessaire, getCode pour les présenter ou les traiter.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

$validator = Validation::createValidator();
$violations = $validator->validate('', new Assert\NotBlank());
if (count($violations) > 0) {
    foreach ($violations as $violation) {
        echo $violation->getMessage(), PHP_EOL;
    }
}

La chaîne vide produit une violation NotBlank. Remplacée par Guide, elle n'en produit aucune. Contre-exemple : écrire if ($violations) pour détecter les erreurs : un objet reste vrai même si sa liste est vide. Correction : compter ses éléments. Pour un log ou un message public, ne pas afficher systématiquement getInvalidValue : une donnée invalide peut aussi être une donnée sensible.

Passage canonique conservé

Ce qu'il retourne : une liste, jamais un bool

if (0 !== count($violations)) {
    foreach ($violations as $violation) {
        $violation->getMessage();
        $violation->getPropertyPath();   // 'email', 'address.city'
        $violation->getInvalidValue();   // 'x'
        $violation->getCode();           // Assert\Email::INVALID_FORMAT_ERROR
        $violation->getConstraint();     // l'objet Email
    }
}
  • Une liste vide convertie en booléen vaut true : tester count().
  • findByCodes(Assert\Email::INVALID_FORMAT_ERROR) filtre par code ; (string) $violations donne une ligne par violation.
  • php bin/console debug:validator affiche les constraints d'une class.

Donnée invalide ou configuration invalide

À retenir en priorité
  1. Séparer donnée invalide et configuration invalide.
  2. Une constraint incohérente peut lever une exception.
Situation Résultat
donnée invalide, même mal typée (un array soumis à Email) violation : « This value should be of type string. »
constraint mal configurée (new Assert\Length()) MissingOptionsException à sa construction
scalaire ou null sans constraint RuntimeException : « Cannot validate values of type "string" automatically… »
object ou array sans constraint liste vide

Deux raccourcis de `Validation`

À retenir en priorité
  1. createIsValidCallable() produit un bool.
  2. createCallable() conserve la valeur valide et lève sinon.
Method Valeur invalide Valeur valide
Validation::createIsValidCallable(...) la function rend false true
Validation::createCallable(...) elle lève ValidationFailedException elle rend la valeur

Utiles là où l'on attend une function : setAllowedValues() d'OptionsResolver, une saisie en console.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le standalone demande un mapping explicite.
  2. Le service du framework se configure séparément.
  • Voir l’explication : validate() ne lève rien pour une donnée invalide

    validate() ne lève rien pour une donnée invalide, même mal typée ; une constraint mal configurée ou un scalaire sans constraint, si.

  • Voir l’explication : Une liste vide est un object.

    Une liste vide est un object. Seul count() dit si la validation a réussi.

  • Voir l’explication : createValidator() ignore les attributes

    createValidator() ignore les attributes : il faut enableAttributeMapping().

  • Voir l’explication : validatePropertyValue() n'a pas besoin de l'object peuplé

    validatePropertyValue() n'a pas besoin de l'object peuplé : elle teste une valeur candidate contre les constraints de la property.

  • Voir l’explication : Un group mal orthographié fait paraître l'object valide

    Un group mal orthographié fait paraître l'object valide : aucune constraint n'y appartient, la liste rendue est vide, sans erreur.

Fiche express

À mémoriser

À retenir en priorité
  1. Un group inconnu ne sélectionne rien.
  2. Une liste vide ne prouve pas que toutes les règles ont été exécutées.

Si tu dois retenir seulement 7 choses :

  • validate(), validateProperty(), validatePropertyValue() (accepte un nom de class).
  • Retour : une liste, vide = valide ; tester count().
  • Violation : message, path, valeur, code, constraint.
  • Hors framework : enableAttributeMapping(), sinon 0 violation.
  • Donnée invalide → violation ; constraint mal configurée → exception.
  • Scalaire sans constraint → RuntimeException.
  • createIsValidCallable() rend un bool ; createCallable() lève.

Moyen mnémotechnique : « Règles sur la class, liste en retour, count() pour conclure ».
