Objectif

Protéger des URL par la configuration, connaître la règle d'ordre, et savoir comment se combinent plusieurs exigences dans une même règle.

L'essentiel

À comprendre

À retenir en priorité
  1. L'ordre sélectionne une seule règle.
  2. Les règles suivantes ne renforcent pas la première.

access_control choisit une règle d'accès à partir de la requête : chemin, méthode HTTP, adresse IP ou autres critères. Il faut distinguer deux questions : quelle règle correspond ?, puis ses exigences sont-elles satisfaites ?

Seule la première règle correspondante s'applique. Un échec d'autorisation ne fait pas essayer la règle suivante. À l'inverse, une IP ou une méthode qui ne correspond pas fait poursuivre la recherche : ce n'est pas encore un refus.

Le schéma

À retenir en priorité
  1. La règle générale peut masquer les exceptions.
  2. L'ordre exprime la priorité réelle.

Les losanges ambre sont des décisions ; les formes vertes sont les résultats de cette étape. Ces vues ne décrivent que access_control : une route absente, un attribut de controller ou un voter métier peut encore refuser la requête. L'entry point dépend de l'authentification configurée, par exemple un 401 HTTP Basic ou une redirection vers un formulaire de connexion.

L'exemple

Exemple concret

À retenir en priorité
  1. Une règle plus précise n'a pas de priorité automatique.
  2. La position dans la liste décide.
security:
    access_control:
        - { path: '^/admin/users', roles: ROLE_SUPER_ADMIN }   # le plus précis d'abord
        - { path: '^/admin', roles: ROLE_ADMIN }
        - { path: '^/internal', roles: PUBLIC_ACCESS, ips: [127.0.0.1, ::1] }
        - { path: '^/internal', roles: ROLE_NO_ACCESS }          # tous les autres

La règle

À retenir en priorité
  1. L'absence de match n'est pas un refus.
  2. Les controllers et voters peuvent toujours contrôler l'accès.
  • Les règles sont évaluées dans l'ordre ; seule la première qui correspond est appliquée.
  • D'où l'écriture du plus spécifique au plus général : avec ^/admin avant ^/admin/users, un utilisateur ayant ROLE_SUPER_ADMIN mais ni ROLE_ADMIN ni hiérarchie se voit refuser l'accès à cette étape ; ROLE_ADMIN obtient l'accord de cette règle — sans erreur de configuration. Le statut HTTP final dépend ensuite du traitement de la requête ou du refus.
  • Une URL qu'aucune règle ne couvre n'est pas restreinte par cette liste.

Ce qui fait correspondre une règle

À retenir en priorité
  1. ips sélectionne la règle.
  2. Ajouter un fallback si les autres clients doivent être refusés.
Key Ce qu'elle contraint
path, host le path, le host — expressions régulières, path sans la query string
ips (ou ip) l'adresse du client, masques acceptés
port, methods le port, les methods HTTP
route le nom de la route
attributes des attributes de la Request
request_matcher un service RequestMatcherInterface
  • Tous les critères d'une règle doivent correspondre.
  • request_matcher ne se combine avec aucun autre : la configuration est refusée (InvalidConfigurationException, « should not be specified alongside other options »).
  • methods: [POST] est un critère : un GET ne correspond pas à cette règle, donc passe à la suivante ; cela n'impose ni un 200 ni un 405.
  • ips fait correspondre, il ne restreint pas : une Request d'ailleurs passe à la règle suivante. Pour fermer la zone, une seconde règle sur le même path exige ROLE_NO_ACCESS, un role que personne n'a.

Ce que la règle exige

À retenir en priorité
  1. La strategy affirmative agrège par accord suffisant.
  2. Un role et une expression ne forment pas automatiquement un ET.
  • roles — passés comme attributes à decide(), avec la Request pour sujet ;
  • allow_if — une expression, ajoutée aux attributes ; elle voit la Request sous request ;
  • requires_channel: https — une Request http reçoit un redirect 301.

Les exigences sont soumises ensemble à la strategy. Avec les voters standards de rôles et d'expressions, sans autre voter qui modifie la décision, le tableau décrit l'autorisation, pas le statut HTTP :

Règle affirmative (défaut) unanimous
roles: [ROLE_ADMIN, ROLE_EDITOR], user ROLE_EDITOR accordée accordée
roles: ROLE_ADMIN + allow_if vrai, user sans ROLE_ADMIN accordée refusée
même règle, visiteur anonyme accordée refusée

Deux roles valent « l'un ou l'autre » : le même voter les examine. Un role et une expression relèvent de deux voters : « ou » en affirmative, « et » en unanimous.

Un accord laisse continuer la Request : il ne construit pas une Response 200. Un refus déclenche le traitement d'une AccessDeniedException. Pour un utilisateur pleinement authentifié, le traitement standard conduit normalement à 403, sauf gestion du refus personnalisée. Si une authentification doit être commencée ou renforcée, l'entry point configuré peut répondre 401 (HTTP Basic) ou rediriger vers un formulaire de connexion. Un token remember-me n'est pas une authentification pleine pour cette décision.

Ce que cela ne fait pas

À retenir en priorité
  1. La règle URL ne connaît pas l'object métier.
  2. Le voter traite l'ownership.

access_control protège des URL et ignore les objects : « l'auteur modifie son article » est le travail d'un voter. Un refus produit une AccessDeniedException : normalement 403 pour un utilisateur pleinement authentifié ; sinon l'entry point peut demander une authentification, y compris plus forte qu'une connexion restaurée par remember-me.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le path exclut la query string.
  2. Ne pas y placer une condition sur les parameters de query.
  • Voir l’explication : Seule la première règle correspondante s'applique

    Seule la première règle correspondante s'applique ; les autres ne sont pas cumulées.

  • Voir l’explication : Du plus spécifique au plus général

    Du plus spécifique au plus général, sinon la règle fine devient inatteignable.

  • Voir l’explication : path est une expression régulière

    path est une expression régulière, comparée sans la query string.

  • Voir l’explication : roles + allow_if accorde si l'un des deux suffit

    roles + allow_if accorde si l'un des deux suffit, avec la strategy par défaut.

  • Voir l’explication : Aucune règle ne correspond : aucune restriction par access_control

    Aucune règle ne correspond : aucune restriction par access_control, pas une autorisation universelle de l'application.

  • Voir l’explication : access_control ne remplace pas un voter

    access_control ne remplace pas un voter : il ignore les objects.

Fiche express

À mémoriser

À retenir en priorité
  1. Le matcher personnalisé remplace les critères intégrés.
  2. Une combinaison est refusée.

Si tu dois retenir seulement 7 choses :

  • Première règle qui correspond, et elle seule.
  • Du plus spécifique au plus général.
  • path : regex, sans query string.
  • Critères : path, host, ips, port, methods, route, attributes — ou request_matcher seul.
  • ips fait correspondre ; ROLE_NO_ACCESS ferme le reste.
  • roles + allow_if : « ou » en affirmative, « et » en unanimous. Un accord laisse continuer la Request ; il ne garantit pas HTTP 200.
  • requires_channel → 301.

Moyen mnémotechnique : « Le premier qui correspond, et la strategy tranche ».

access_control : première règle qui correspond (précis d'abord) ; path regex sans query ; ips = critère ;
request_matcher seul ; roles + allow_if = strategy (affirmative : ou) ; accord = continuer, pas HTTP 200 garanti ;
requires_channel = 301 ; pas d'objects
