Objectif

Comprendre le mécanisme qui remplit les arguments d'un controller : qui décide, dans quel ordre, et comment s'y insérer. C'est ce mécanisme qui explique pourquoi typer Request, SessionInterface ou une enum suffit.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La priority détermine l'ordre d'essai.
  2. Un default resolver doit laisser les resolvers spécialisés agir d'abord.

Le kernel ne remplit pas lui-même les arguments d'un controller : il essaie une chaîne de resolvers, triés par priority, et le premier qui fournit une valeur gagne ; si aucun ne sait, une RuntimeException part. Deux resolvers, dits ciblés, ne tournent que si un attribute les désigne : ce sont les #[Map…], qui échouent en 404 sur l'URL, en 422 sur le body.

Le schéma

À retenir en priorité
  1. Le premier résultat arrête la recherche.
  2. Plusieurs valeurs exigent un argument variadique.

L'exemple : un resolver maison

▣ Exemple concret

À retenir en priorité
  1. Un generator convient au contrat iterable.
  2. Un iterable vide signifie que ce resolver passe la main.
final class CurrentLocaleResolver implements ValueResolverInterface
{
    public function resolve(Request $request, ArgumentMetadata $argument): iterable
    {
        if (Locale::class !== $argument->getType()) {
            return;   // rien produit : le resolver suivant essaie
        }

        yield new Locale($request->getLocale());
    }
}

Le contrat

○ À comprendre

C'est quoi ?

Un argument value resolver, résolveur de valeur d'argument, propose une ou plusieurs valeurs pour un paramètre d'action. Le contrat est resolve(Request, ArgumentMetadata): iterable. ArgumentMetadata décrit notamment le nom, le type, les attributes et l'éventuelle valeur par défaut du paramètre.

À quoi ça sert ?

Il sépare l'obtention d'une valeur de l'action qui l'utilise. Le controller ne doit pas recopier le même accès au contexte HTTP dans toutes ses méthodes. Un resolver doit cependant être assez ciblé pour ne pas fournir une valeur à un argument sans rapport.

Où dans Symfony ?

ArgumentResolver parcourt ses resolvers pour chaque argument. Un itérable vide signifie « je ne fournis aucune valeur » ; une valeur produite arrête cette recherche. Plusieurs valeurs sont réservées à un argument variadique. Le type de retour n'est pas forcément array : un générateur PHP avec yield convient aussi.

Comment, étape par étape ?

  1. Examiner les métadonnées et décider si ce resolver est compétent.
  2. Retourner un itérable vide s'il ne l'est pas, afin de laisser une autre stratégie agir.
  3. Produire la valeur attendue s'il l'est ; ne pas retourner directement cette valeur scalaire.
  4. Enregistrer le service avec le tag et l'ordre appropriés. Les resolvers ciblés par des attributes comme MapRequestPayload ne sont pas simplement exécutés pour chaque argument de la chaîne générale.

Exemple concret PHP

Exemple de contrat pour l'argument très précis string $trainingLabel ; l'enregistrement comme service est une étape séparée :

<?php
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpKernel\Controller\ValueResolverInterface;
use Symfony\Component\HttpKernel\ControllerMetadata\ArgumentMetadata;

final class TrainingLabelResolver implements ValueResolverInterface
{
    public function resolve(Request $request, ArgumentMetadata $argument): iterable
    {
        if ('trainingLabel' !== $argument->getName() || 'string' !== $argument->getType()) {
            return [];
        }

        return ['Symfony 8.0'];
    }
}

Le tableau contient une valeur, il n'est pas la valeur finale de l'argument. Contre-exemple : return 'Symfony 8.0'; viole iterable ; return [null]; ne signifie pas « passer la main », mais « fournir null ». Correction : [] pour l'absence de proposition, et un élément uniquement lorsque le resolver prend effectivement en charge l'argument.

Passage canonique conservé

Le contrat

Chaque resolver implémente ValueResolverInterface et sa method unique resolve(Request $request, ArgumentMetadata $argument): iterable. ArgumentMetadata porte ce que la signature déclare : nom, type, variadicité, default value, attributes. La documentation dit « toujours un array » — vide, à un élément, à plusieurs pour un variadique ; le type est iterable, et un generator fonctionne. Retourner la valeur elle-même est l'erreur classique.

Ce que fait `ArgumentResolver`

Le premier resolver qui produit une valeur arrête la chaîne de resolvers ; deux valeurs pour un argument non variadique lèvent une InvalidArgumentException. Un array vide passe la main sans erreur : seul l'échec de toute la chaîne de resolvers lève.

Une file de traducteurs spécialisés examine le type demandé. Produire zéro valeur signifie « je passe la main », pas « je fournis null » : yield null est déjà une valeur et arrête la recherche.

L'ordre

△ Piège à éviter

C'est quoi ?

La priority d'un resolver ordinaire détermine sa position dans la chaîne : les valeurs les plus élevées passent d'abord. Ce sont des valeurs de câblage des services, pas des propriétés du type PHP de l'argument.

À quoi ça sert ?

Une stratégie spécialisée doit pouvoir agir avant qu'une stratégie plus générale fournisse déjà une valeur. Une priorité très élevée n'est pas automatiquement meilleure : un resolver trop large peut intercepter des arguments destinés à un autre mécanisme.

Où dans Symfony ?

Dans le fichier de configuration web de FrameworkBundle v8.0.0, SessionValueResolver a la priorité 50, et DefaultValueResolver -100. La valeur 120 ne décrit pas ce câblage. RequestAttributeValueResolver intervient à 100. Les services applicatifs peuvent changer l'ensemble réellement utilisé : il faut distinguer ces valeurs de référence de la configuration finale du projet.

Comment, étape par étape ?

  1. Déterminer quelle stratégie risque déjà de résoudre l'argument.
  2. Cibler précisément le resolver par métadonnées ou par attribute de résolution.
  3. Pour un resolver ordinaire, choisir une priorité justifiée relativement aux stratégies concernées.
  4. Vérifier les cas pris en charge et les cas où le resolver doit retourner un itérable vide. Une égalité de priorité ne constitue pas une garantie universelle de précédence sur tous les services.

Exemple concret PHP

Cette signature exprime un repli nullable compatible PHP 8.4, dans une action dont les services de résolution habituels sont disponibles :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function show(?\Symfony\Component\HttpFoundation\Session\SessionInterface $session = null): \Symfony\Component\HttpFoundation\Response
{
    return new \Symfony\Component\HttpFoundation\Response(null === $session ? 'Session absente' : 'Session disponible');
}

Le resolver de session peut fournir l'objet avant le resolver des valeurs par défaut ; en l'absence de proposition adaptée, le défaut null est disponible. L'exemple ne lit pas le sac de session. Contre-exemple : SessionInterface $session = null repose sur une nullabilité implicite dépréciée en PHP 8.4. Correction : écrire ?SessionInterface explicitement. Les resolvers ciblés obéissent à une sélection différente ; épingler un resolver ne signifie pas réordonner toute la chaîne générale.

Passage canonique conservé

L'ordre

Les services tagués controller.argument_value_resolver sont triés par priority, fixée par FrameworkBundle. Attention à la version : en v8.0.0, RequestValueResolver et SessionValueResolver valent tous deux 50 ; en 8.0.16, ils valent tous deux 120. Le diagramme ci-dessus décrit v8.0.0, pas un mélange des versions. Dans v8.0.0, SessionValueResolver, à 50, passe après RequestAttributeValueResolver (100), mais avant DefaultValueResolver (-100) : la session s'il y en a une, null sinon. Un resolver maison qui lit les attributes se place à 100 ou plus. La documentation écrit SessionInterface $session = null ; PHP 8.4 déprécie ce nullable implicite : écrire ?SessionInterface $session = null.

Le catalogue

○ À comprendre

À retenir en priorité
  1. Le nom relie route attribute et argument.
  2. RequestValueResolver utilise le type Request.

C'est quoi ?

Les resolvers intégrés associent une origine de donnée et un type d'argument. RequestAttributeValueResolver lit une clé nommée ; RequestValueResolver fournit la Request ; SessionValueResolver fournit la session ; ServiceValueResolver consulte le locator de l'action. D'autres convertissent des valeurs de route vers enum, date ou Uid.

À quoi ça sert ?

La signature peut exprimer un objet utilisable plutôt qu'une chaîne brute. Cette conversion a un contrat d'échec : une valeur qui ne correspond pas à un cas d'enum n'est pas automatiquement remplacée par une valeur métier arbitraire.

Où dans Symfony ?

BackedEnumValueResolver vise une enum adossée à une valeur scalaire et un attribute portant le nom de l'argument. Une valeur de route invalide aboutit à NotFoundHttpException, donc 404 dans le traitement HTTP habituel. DefaultValueResolver fournit un défaut lorsque les stratégies précédentes ne proposent rien ; VariadicValueResolver développe une liste pour un argument variadique.

Comment, étape par étape ?

  1. Identifier la source et le type attendu.
  2. Vérifier que le resolver et ses dépendances sont disponibles.
  3. Aligner le nom de l'argument avec celui de l'attribute.
  4. Tester une valeur valide puis une valeur hors du domaine.

Exemple concret PHP

Enum et action d'un controller enregistré, pour une route contenant {state} :

<?php
enum PublicationState: string
{
    case Draft = 'draft';
    case Published = 'published';
}

final class PublicationController
{
    public function show(PublicationState $state): \Symfony\Component\HttpFoundation\JsonResponse
    {
        return new \Symfony\Component\HttpFoundation\JsonResponse(['state' => $state->value]);
    }
}

La valeur draft devient PublicationState::Draft ; unknown ne fait pas entrer dans l'action et conduit au 404 prévu. Contre-exemple : supposer qu'un type d'enum seul lit aussi un paramètre query du même nom. Correction : distinguer attributes de route et mapping ciblé de query ; la source de donnée fait partie du contrat.

Passage canonique conservé

DateTimeValueResolver date ; DateTimeImmutable pour DateTimeInterface
ServiceValueResolver service du locator de l'action

Une valeur invalide pour une enum ou une date dans l'URL produit 404. Importer la bonne class Request reste nécessaire.

Les resolvers ciblés

○ À comprendre

À retenir en priorité
  1. Distinguer décodage, format et validation.
  2. Un targeted resolver ne s'exécute que lorsqu'il est sélectionné.

C'est quoi ?

Un resolver ciblé est sélectionné explicitement pour un argument, généralement par un attribute. Contrairement à un resolver ordinaire de la chaîne générale, il ne tente pas systématiquement de résoudre tous les arguments uniquement grâce à sa priorité.

À quoi ça sert ?

Une signature peut préciser que page vient de la query string, ou qu'un objet doit être construit à partir du body. Sans cette indication, un nom de variable ressemblant à une entrée HTTP ne suffit pas à définir son origine et sa validation.

Où dans Symfony ?

MapQueryParameter vise une valeur de query ; MapQueryString un objet construit depuis la query ; MapRequestPayload un objet construit depuis le body ; MapUploadedFile les fichiers. Leurs défauts d'échec de validation ne sont pas identiques : 404 pour les deux premiers, 422 pour les deux derniers. Un JSON illisible peut produire 400, un format non pris en charge 415 : validationFailedStatusCode ne remplace pas toutes ces erreurs.

Comment, étape par étape ?

  1. Choisir l'attribute correspondant à la source.
  2. Déclarer le type, le défaut et les contrôles nécessaires.
  3. Vérifier les dépendances du mapping, notamment Serializer/Validator lorsqu'ils interviennent.
  4. Tester absence, valeur mal formée et valeur valide comme des cas distincts.

Exemple concret PHP

Action de controller avec le resolver ciblé de query disponible :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function list(#[\Symfony\Component\HttpKernel\Attribute\MapQueryParameter] int $page = 1): \Symfony\Component\HttpFoundation\JsonResponse
{
    return new \Symfony\Component\HttpFoundation\JsonResponse(['page' => $page]);
}

?page=2 fournit un entier ; l'absence permet le défaut. Cela ne garantit pas page positif : le contrôle métier reste à ajouter si nécessaire. Contre-exemple : retirer l'attribute puis attendre que le resolver de route lise automatiquement la query. Correction : exprimer sa source. Un ValueResolver explicitement épinglé conserve les replis prévus vers attributes et valeur par défaut ; ce n'est pas l'exécution de toute la chaîne générale.

Passage canonique conservé

Les resolvers ciblés

RequestPayloadValueResolver et QueryParameterValueResolver portent le tag controller.targeted_value_resolver : hors de la chaîne de resolvers, ils ne s'exécutent que si un attribute les désigne.

#[ValueResolver] épingle un resolver par son nom — le FQCN pour ceux du framework. La chaîne de resolvers compte alors trois éléments : l'épinglé, RequestAttributeValueResolver, DefaultValueResolver ; la documentation ne cite que le dernier. Deux épinglés sur un argument lèvent une LogicException ; disabled: true en saute un.

Attribute Source Échec par défaut
#[MapQueryParameter] un parameter de la query string 404
#[MapQueryString] la query string, vers un object 404
#[MapRequestPayload] le body, vers un object 422
#[MapUploadedFile] un file téléversé 422

Un body illisible — JSON malformé — donne 400, un format sans decoder 415 ; validationFailedStatusCode change le 422, pas ceux-là. #[MapQueryParameter] accepte filter, flags et options : avec FILTER_NULL_ON_FAILURE, une valeur invalide devient null au lieu de lever.

Pièges d'examen

△ Piège à éviter

Valeurs des resolvers, ordre de résolution et erreurs HTTP
  • La documentation dit « toujours un array » ; le type est iterable.
  • Un array vide passe la main ; si aucun resolver ne fournit de valeur, une RuntimeException est levée.
  • Le premier resolver qui fournit une valeur arrête la chaîne de resolvers.
  • Une valeur invalide dans l'URL donne 404, pas 400.
  • #[MapQueryParameter] échoue en 404, #[MapRequestPayload] en 422.
  • Un JSON malformé donne 400, pas 422 : il n'y a rien à valider.
  • Un resolver ciblé ne s'exécute pas sans son attribute.
  • SessionInterface $session = null est déprécié en PHP 8.4.

Application

À retenir en priorité
  1. La priority détermine l'ordre d'essai.
  2. Un default resolver doit laisser les resolvers spécialisés agir d'abord.
  3. Le nom relie route attribute et argument.
  4. RequestValueResolver utilise le type Request.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • resolve() rend un iterable : vide = « pas moi ».
  • Premier resolver qui fournit → gagne ; aucun → RuntimeException.
  • FrameworkBundle v8.0.0 : 100 attributes, 50 Request et Session, −100 défaut. En 8.0.16, Request et Session passent tous deux à 120. Ne pas combiner Request 120 et Session 50 comme un ordre unique.
  • Valeur d'URL invalide (enum, date) → 404.
  • Ciblés : payload et query parameter, seulement sur attribute.
  • #[ValueResolver] → épinglé + attributes + défaut ; deux épinglés → exception.
  • #[Map…] : URL 404, body 422, illisible 400.

Moyen mnémotechnique : « Premier qui donne, premier servi ».
