Objectif

Classer une method selon les trois properties de RFC 9110 — sûre, idempotente, cacheable — qui sont indépendantes les unes des autres.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La liste Symfony inclut QUERY.
  2. Distinguer cette API des règles RFC permettant certaines Responses POST en cache.

Trois properties indépendantes classent une method : sûre (lecture seule), idempotente (la rejouer ne change rien de plus) et cacheable. Toute method sûre est idempotente, pas l'inverse. Le piège de l'examen : la RFC et Symfony ne donnent pas la même liste de cacheables. Lire d'abord le référentiel de la question : les deux affirmations sont justes, chacune chez elle.

Le schéma

L'exemple : les trois questions de `Request`

▣ Exemple concret

$request->isMethodSafe();        // GET, HEAD, OPTIONS, TRACE, QUERY
$request->isMethodIdempotent();  // + PUT, DELETE, PURGE
$request->isMethodCacheable();   // GET, HEAD, QUERY uniquement

PURGE n'est pas une method standard, mais une convention de reverse proxy.

Les trois properties

○ À comprendre

À retenir en priorité
  1. Idempotence décrit l'effet sur l'état.
  2. Deux DELETE peuvent produire des status codes différents.

C'est quoi ?

Une méthode sûre ne demande pas de modification d'état au serveur. Une méthode idempotente conserve le même effet intentionnel quand on répète la même demande. Une réponse cacheable peut être stockée et réutilisée sous les conditions applicables. Ces trois propriétés ne sont pas synonymes.

À quoi ça sert ?

La sûreté permet notamment des récupérations automatiques sans demander une action métier. L'idempotence aide à raisonner sur une nouvelle tentative après une coupure. Le cache réduit les transferts ou les traitements, mais dépend aussi du statut, des headers et du contexte, pas uniquement du nom de méthode.

Où dans Symfony ?

Dans Request 8.0, les méthodes reconnues comme sûres sont GET, HEAD, OPTIONS, TRACE et QUERY. Les idempotentes ajoutent PUT, DELETE et PURGE. isMethodCacheable() reconnaît GET, HEAD et QUERY. QUERY et PURGE dans ces listes sont des choix d'API à distinguer du catalogue de méthodes de RFC 9110 ; PURGE est notamment une convention de cache intermédiaire.

Comment, étape par étape ?

  1. Demander si le client réclame un changement d'état.
  2. Demander si répéter cette intention change davantage l'état final.
  3. Examiner les règles de stockage et réutilisation de la réponse.
  4. Distinguer ces règles normatives du raccourci de classification fourni par Symfony.

Exemple concret PHP

<?php
use Symfony\Component\HttpFoundation\Request;
$request = Request::create('/items/42', 'DELETE');
printf("safe=%d idempotent=%d cacheable=%d\n",
    $request->isMethodSafe(), $request->isMethodIdempotent(), $request->isMethodCacheable());

On attend safe=0 idempotent=1 cacheable=0. Contre-exemple : interpréter « sûre » comme « protégée contre les attaques » ; cela décrit l'intention HTTP, pas l'authentification. Un GET peut produire des logs sans perdre sa sûreté, mais ne devrait pas demander une suppression métier. Correction : choisir une méthode correspondant à l'action, puis appliquer séparément les contrôles d'accès nécessaires.

Passage canonique conservé

Les trois properties

  • Sûre (safe) : la method ne demande aucune modification d'état. « Sûre » décrit l'intention, pas le code : rien n'empêche un GET d'incrémenter un compteur.
  • Idempotente : rejouer la même Request N fois a le même effet sur l'état que l'exécuter une fois — le status code peut différer.
  • Cacheable : la Response peut être stockée et réutilisée.

Demander plusieurs fois de remplacer une fiche par le même contenu laisse le même état : c'est l'idée de PUT idempotent. Les accusés reçus peuvent différer sans changer ce résultat sur l'état.

Ce que la table enseigne

○ À comprendre

À retenir en priorité
  1. Une safe method ne demande pas de modification d'état.
  2. PUT et DELETE restent idempotents sans être safe.

C'est quoi ?

PUT demande de créer ou remplacer l'état de la ressource cible par la représentation fournie. DELETE demande de retirer son association actuelle. Ces actions modifient l'état, donc ne sont pas sûres, mais leur répétition peut laisser le même état intentionnel final : elles sont idempotentes.

À quoi ça sert ?

Après une coupure réseau, le client peut ignorer si la première demande a été appliquée. La propriété idempotente permet de raisonner sur la répétition de la même intention sans exiger que le serveur renvoie exactement la même réponse.

Où dans Symfony ?

Request classe PUT et DELETE comme idempotentes. POST n'a pas cette garantie générale : un endpoint, point d'entrée HTTP, de création peut créer deux ressources. PATCH, défini par RFC 5789, n'est pas garanti idempotent par sa méthode, mais une opération de patch particulière peut l'être. Dire que tout PATCH est nécessairement relatif et non idempotent serait trop absolu.

Comment, étape par étape ?

  1. Identifier la ressource cible et l'état demandé.
  2. Appliquer la demande une fois.
  3. Imaginer la même demande sur l'état obtenu.
  4. Comparer les effets intentionnels, pas seulement les messages de réponse.

Exemple concret HTTP

PUT /preferences/theme HTTP/1.1
Host: example.test
Content-Type: application/json
Content-Length: 16

{"theme":"dark"}

Le contenu JSON comporte 16 octets, sans retour à la ligne final transmis dans ce contenu. Si le contrat de cette ressource est de remplacer la préférence, deux demandes identiques laissent theme=dark. Contre-exemple : implémenter ce PUT comme « basculer dark vers light ou inversement » ; la répétition change à nouveau l'état. Correction : affecter la valeur fournie ou choisir une action dont le contrat reflète réellement l'opération. De même, un PATCH « fixer le nom à Léa » peut être idempotent, contrairement à « incrémenter un compteur » : la méthode seule n'accorde pas la garantie à tout document de patch.

Passage canonique conservé
  • PUT et DELETE sont idempotents sans être sûrs : remplacer par la même valeur, supprimer ce qui est déjà supprimé.
  • POST n'offre pas de garantie générale de sûreté ou d'idempotence. Un endpoint de création peut créer deux ressources si la demande est répétée ; une autre opération POST peut être idempotente par contrat. Le nom de méthode ne décrit pas à lui seul le comportement métier.
  • PATCH n'est pas garanti idempotent : une modification relative peut ne pas l'être ; une opération particulière peut toutefois être idempotente. Il est défini par RFC 5789, pas par 9110.
  • QUERY porte un body comme POST mais garde la sémantique de GET : sûre, idempotente et cacheable dans Symfony 8.0.
  • Symfony ajoute, et retire : QUERY aux safe methods, QUERY et PURGE aux idempotentes — mais il retire POST des cacheables.
  • Le nom d'une method est sensible à la casse (§9.1), à l'inverse des noms de fields.

Pièges d'examen

○ À comprendre

C'est quoi ?

L'idempotence porte sur l'effet demandé au serveur, pas sur l'égalité des statuts ou des bodies. Deux réponses différentes peuvent donc correspondre à une répétition idempotente.

À quoi ça sert ?

Cette distinction évite de rejeter à tort DELETE comme non idempotente et de promettre une réponse identique à chaque nouvelle tentative. Elle évite aussi de considérer une opération comme sûre simplement parce qu'elle est rejouable.

Où dans Symfony ?

isMethodIdempotent() est une classification de méthode, pas une analyse de votre controller. isMethodCacheable() utilise GET, HEAD et QUERY en 8.0 ; OPTIONS et TRACE sont sûres mais ne sont pas dans cette liste. Le protocole autorise certains usages de cache de POST sous conditions, tandis que cette méthode d'aide Symfony ne classe pas POST comme cacheable.

Comment, étape par étape ?

  1. Décrire l'état avant la première demande.
  2. Décrire l'état après cette demande.
  3. Répéter la même intention.
  4. Comparer l'état final ; traiter séparément le statut et les effets annexes comme les logs.

Exemple concret HTTP

Première suppression réussie :

HTTP/1.1 204 No Content

Nouvelle demande DELETE sur la même cible déjà absente, selon ce contrat d'API :

HTTP/1.1 404 Not Found

L'état reste « ressource absente ». Le changement 204 vers 404 ne contredit donc pas l'idempotence. Contre-exemple : conclure qu'il faut recréer la ressource pour obtenir de nouveau 204, ou déclarer DELETE non idempotente à cause du 404. Correction : raisonner sur l'intention de suppression. Le protocole n'exige pas cette paire exacte de statuts à chaque implémentation ; elle illustre pourquoi l'état et la réponse sont deux dimensions distinctes.

Passage canonique conservé

Pièges d'examen

« Sûre » ne veut pas dire « sécurisée ». Le terme signifie « sans effet de bord attendu ».

OPTIONS et TRACE sont sûrs mais non cacheables.

Les cacheables sont GET, HEAD et QUERY — trois, pas deux. Oublier QUERY est l'erreur attendue, et elle se propage : Response::isNotModified() s'ouvre sur isMethodCacheable(), donc la validation d'une Response suit exactement cette liste.

DELETE est idempotent. L'intuition « la seconde suppression échoue, donc ce n'est pas idempotent » confond l'effet sur l'état, qui est identique, avec le status code renvoyé, qui peut différer.

Application

À retenir en priorité
  1. Une safe method ne demande pas de modification d'état.
  2. PUT et DELETE restent idempotents sans être safe.
  3. Idempotence décrit l'effet sur l'état.
  4. Deux DELETE peuvent produire des status codes différents.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Sûre ⊂ idempotente ; cacheable est indépendante.
  • PUT/DELETE : idempotents, non sûrs. POST/PATCH : aucune garantie générale d'idempotence.
  • Idempotence = effet sur l'état, pas status code.
  • Symfony cacheables : GET, HEAD, QUERY ; RFC : GET, HEAD, POST.
  • OPTIONS et TRACE : sûrs, non cacheables.
  • PATCH vient de RFC 5789 ; methods sensibles à la casse.

Moyen mnémotechnique : « Sûre implique idempotente, jamais l'inverse ».
