Le document Symfony Best Practices énonce trente recommandations en dix sections, pour une application web classique : ce ne sont pas des règles du framework, rien ne casse si on les ignore. L'examen vise celles que l'intuition contredit — la constant plutôt que le parameter, l'URL en dur, pas de bundle applicatif, les boutons dans le template.

L'exemple : une valeur qui ne change presque jamais

Configuration : la règle des trois niveaux

Variable d'environment pour ce qui dépend de la machine, secret pour le sensible, parameter pour l'applicatif — et une constante de class pour ce qui ne change presque jamais : elle est lisible partout, y compris dans un template, là où un parameter exige le container ; le prix est qu'elle se redéfinit mal dans un test. Les parameters applicatifs se préfixent par app., avec un ou deux mots descriptifs : app.contents_dir plutôt que app.dir.

Repère de l’exemple : It is an application value that changes rarely and does not need container configuration. Une valeur rarement modifiée peut rester une constante de class. Un parameter du container n'est pas nécessaire pour toute valeur applicative.

Les recommandations qui surprennent

À retenir en priorité
  1. Une URL générée peut masquer un changement de route publique.
  2. Le functional test doit détecter cette rupture.
  3. Le FormType porte la structure réutilisable.
  4. Le template choisit le bouton adapté au contexte.
  • Ne pas créer de bundle pour organiser le code de l'application.
  • Coder les URL publiques littéralement dans les functional tests pour détecter un changement de contrat.
  • Placer les boutons dans les templates afin de réutiliser le FormType pour création et édition.
  • Garder le controller comme point de coordination ; confier les opérations métier aux services.

Au restaurant, le serveur reçoit la commande et apporte le résultat ; les postes de cuisine portent le travail spécialisé. Un controller reste ce point de coordination, sans devenir le lieu de toute la logique métier.

Repère — Les trente, par section : No. Keep application code in the standard structure; bundles serve reusable integration. Le code applicatif reste dans l'arborescence standard. Un bundle est un mécanisme de réutilisation et d'intégration, pas un dossier métier obligatoire.

Pièges d'examen

△ Piège à éviter

Constantes, URLs de test, bundles et présentation des formulaires

Une valeur presque immuable convient à une constante de class, pas nécessairement à un parameter du container. Une URL générée dans un functional test peut masquer un changement du path public. Un bundle sert au code partagé, pas au découpage interne d'une application. Les boutons de form appartiennent au contexte de présentation.
