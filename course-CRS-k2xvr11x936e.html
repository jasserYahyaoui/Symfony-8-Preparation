Configuration : la règle des trois niveaux

À comprendre

C'est quoi ?

Une valeur de configuration peut appartenir à l'infrastructure, au comportement de l'application ou à une règle stable du code. Son caractère sensible ajoute une exigence de protection : un secret n'est pas simplement un paramètre portant un nom différent.

À quoi ça sert ?

Placer chaque valeur au bon endroit évite de modifier le code pour un changement de serveur, de publier des informations sensibles ou de rendre artificiellement configurable une règle qui ne doit pas varier.

Où dans Symfony ?

  • Une adresse de service dépendant de la machine relève d'une variable d'environnement.
  • Une clé confidentielle relève d'une gestion de secrets adaptée, pas d'un littéral dans le dépôt.
  • Une option de comportement applicatif réutilisée relève d'un paramètre, avec un nom court et précis préfixé par app..
  • Une valeur qui change très rarement peut être une constante de classe, accessible sans container ; elle est moins facile à remplacer dans un test.

Comment, étape par étape ?

  1. Demander qui doit pouvoir changer la valeur et à quel moment.
  2. Déterminer si elle est sensible indépendamment de cette première réponse.
  3. Choisir environnement, secret, paramètre ou constante.
  4. Donner un nom exprimant le sens, comme app.contents_dir, plutôt qu'un terme générique comme app.dir.

Exemple concret YAML

parameters:
    app.contents_dir: '%kernel.project_dir%/content'
    app.notification_sender: 'notifications@example.test'

Ces valeurs fictives décrivent l'organisation et le comportement de l'application. Elles ne sont pas des mots de passe. Une limite métier stable pourrait au contraire être public const ITEMS_PER_PAGE = 10 dans la classe concernée. Contre-exemple : stocker une clé privée dans app.api_key parce que le préfixe app. paraît « interne ». Correction : traiter la confidentialité par le système de secrets ; le nom du paramètre n'offre aucune protection. Autre limite : si un test ou un déploiement doit souvent varier la valeur, une constante peut être trop rigide malgré sa simplicité.

Passage canonique conservé

Variable d'environment pour ce qui dépend de la machine, secret pour le sensible, parameter pour l'applicatif — et une constante de class pour ce qui ne change presque jamais : elle est lisible partout, y compris dans un template, là où un parameter exige le container ; le prix est qu'elle se redéfinit mal dans un test. Les parameters applicatifs se préfixent par app., avec un ou deux mots descriptifs : app.contents_dir plutôt que app.dir.

Repère de l’exemple : It is an application value that changes rarely and does not need container configuration. Une valeur rarement modifiée peut rester une constante de class. Un parameter du container n'est pas nécessaire pour toute valeur applicative.

Les recommandations qui surprennent

À comprendre

À retenir en priorité
  1. Une URL générée peut masquer un changement de route publique.
  2. Le functional test doit détecter cette rupture.
  3. Le FormType porte la structure réutilisable.
  4. Le template choisit le bouton adapté au contexte.

C'est quoi ?

Une bonne pratique officielle est un choix recommandé avec une raison et un contexte, pas une interdiction du langage. Le but est de réduire le couplage et la configuration inutile tout en gardant visibles les contrats réellement importants.

À quoi ça sert ?

Plusieurs recommandations deviennent compréhensibles quand on nomme le problème évité :

  • Organiser l'application par espaces de noms, sans bundle par domaine, évite une couche d'intégration inutile. Un bundle devient pertinent pour partager une fonctionnalité entre applications.
  • Garder les services privés et utiliser l'injection rend leurs dépendances explicites.
  • Mettre les boutons ordinaires d'un formulaire dans le template permet de réutiliser sa classe pour création et édition. Si plusieurs boutons doivent être distingués au traitement, ils doivent être déclarés dans le formulaire selon le mécanisme prévu, pas seulement ajoutés en HTML.
  • Placer les contraintes sur l'objet sous-jacent permet de réutiliser la validation hors du formulaire.
  • Employer des clés de traduction exprimant le sens évite de renommer toutes les traductions lorsqu'un texte source change.
  • Préférer un seul firewall simplifie l'authentification ; des systèmes d'authentification réellement distincts peuvent justifier plusieurs firewalls.
  • Le hasher auto choisit l'algorithme adapté ; ce nom désigne un choix automatique, pas un algorithme nommé « auto ».

Où dans Symfony ?

Les recommandations couvrent structure, services, controllers, templates, formulaires, sécurité et tests. EntityValueResolver facilite une récupération simple ; dès qu'elle exige une requête particulière, écrire explicitement cette récupération est plus clair que forcer l'automatisme. Les fragments Twig préfixés par _ se distinguent des pages complètes.

Comment, étape par étape ?

  1. Identifier le contrat à protéger : par exemple une URL publique.
  2. Choisir un test qui ne recalcule pas automatiquement cette même information.
  3. Tester ensuite le comportement métier plus fin ; un simple contrôle de disponibilité ne suffit pas à valider tout le contenu.

Exemple concret PHP

Dans une application de test où /blog doit rester une URL publique disponible, avec les outils de test Symfony installés :

<?php
namespace App\Tests;
use Symfony\Bundle\FrameworkBundle\Test\WebTestCase;
final class BlogAvailabilityTest extends WebTestCase
{
    public function testPublicUrlRemainsAvailable(): void
    {
        $client = static::createClient();
        $client->request('GET', '/blog');
        self::assertResponseIsSuccessful();
    }
}

Ce smoke test, contrôle préliminaire de disponibilité, utilise volontairement l'URL en dur. Contre-exemple : générer cette URL avec la route puis penser que le test détectera son changement public ; le test suivrait automatiquement la nouvelle URL. Correction : garder l'URL contractuelle dans ce test et prévoir une redirection si elle change. Les liens ordinaires de l'application, eux, doivent normalement être générés depuis les routes.

Passage canonique conservé
  • Ne pas créer de bundle pour organiser le code de l'application.
  • Coder les URL publiques littéralement dans les functional tests pour détecter un changement de contrat.
  • Placer les boutons dans les templates afin de réutiliser le FormType pour création et édition.
  • Garder le controller comme point de coordination ; confier les opérations métier aux services.

Au restaurant, le serveur reçoit la commande et apporte le résultat ; les postes de cuisine portent le travail spécialisé. Un controller reste ce point de coordination, sans devenir le lieu de toute la logique métier.

Repère — Les trente, par section : No. Keep application code in the standard structure; bundles serve reusable integration. Le code applicatif reste dans l'arborescence standard. Un bundle est un mécanisme de réutilisation et d'intégration, pas un dossier métier obligatoire.
