Objectif

Connaître les variables disponibles dans tous les templates sans qu'un controller les passe, et savoir en déclarer.

L'essentiel

À comprendre

À retenir en priorité
  1. Ces globales appartiennent à Twig.
  2. app est ajouté par Symfony.

Un template lit des variables qui viennent de deux endroits : le contexte passé au rendu par le controller, et les globales, disponibles partout. Twig en fournit trois, Symfony en ajoute une — app — et l'application peut déclarer les siennes. Le contexte gagne toujours.

Le schéma

Ambre = recherche ; bleu = valeur disponible. La priorité concerne les noms ordinaires comme title, y compris un {% set title = 'Page' %} local. _self, _context et _charset sont des variables spéciales de Twig, pas des noms de configuration à redéfinir. Lire app.request consulte la pile courante : ce n'est pas un instantané de la requête principale.

L'exemple

Exemple concret

À retenir en priorité
  1. app.flashes consomme les messages.
  2. Deux lectures ordinaires ne rendent pas deux fois la même liste.

Le titre de l'article42 appartient au contexte passé par show(), tandis que le nom du site concerne tous les rendus. Le layout peut aussi consulter app pour une navigation personnalisée. Cette commodité introduit toutefois des lectures de services : afficher les flashes n'est pas une simple lecture d'un tableau de constantes.

<title>{{ site_name }} — {{ title }}</title>
{% if app.user %}Bonjour {{ app.user.userIdentifier }}{% endif %}
{% for message in app.flashes('notice') %}
    <div class="flash">{{ message }}</div>
{% endfor %}
<nav class="{{ app.current_route == 'home' ? 'active' }}">…</nav>

site_name vient de twig.globals, title du controller, le reste de app.

Les trois globales de Twig lui-même

Pour une carte incluse depuis la page de l'article, _self désigne la carte en cours de rendu et _context son contexte visible. Ce dernier peut contenir des objets et des données sensibles ; ne l'affiche pas entièrement pour fabriquer le contenu public ou un diagnostic de production.

Variable Contenu
_self le nom du template courant
_context toutes les variables visibles, passées et globales
_charset le jeu de caractères courant

🌍 In Real Life

La situation : sur son poste, le maquettiste voit le nom du modèle ouvert, les données disponibles sur le bureau et le jeu de caractères utilisé. Ces repères décrivent son travail courant, pas tout le système d'information.

L’équivalent dans Symfony : Twig fournit _self, _context et _charset indépendamment de Symfony. Dans une carte incluse, ces repères concernent son rendu et les variables qu'elle voit.

Retour à la réalité technique : ce sont des variables spéciales, pas des noms ordinaires à remplacer via twig.globals. _context peut contenir objets et données sensibles : être visible par le template ne signifie pas pouvoir être publié intégralement.

🧠 Comment le mémoriser : « Modèle ouvert, bureau visible, alphabet choisi. » Image mentale : poste de composition avec trois repères distincts. Question-réflexe : est-ce un repère du moteur ou une donnée métier explicitement fournie ?

⚠️ À ne pas confondre : contexte visible du rendu et ensemble des données de l'application.

La variable `app`

À retenir en priorité
  1. Un template ne s'exécute pas toujours dans une Request HTTP.
  2. Tester les accès qui dépendent du contexte.

app.request retrouve la Request courante via la pile, alors que article reste une entrée explicite du rendu. Dans une subrequest, ce ne sont donc pas nécessairement les attributs de la page principale. Dans un email rendu en console, aucune Request n'est inventée pour rendre ces propriétés disponibles : prévois un template et des données adaptés.

TwigBundle expose app, un object AppVariable, dans chaque template :

Property Contenu
app.user le user courant, ou null s'il n'est pas authentifié
app.request la Request courante
app.session la session, ou null
app.flashes les flash messages ; app.flashes('notice') filtre par type
app.environment, app.debug l'environment et le mode debug
app.token le token de sécurité
app.current_route, app.current_route_parameters la route courante et ses parameters
app.locale, app.enabled_locales la locale courante et les locales activées
  • Sans Request — une command qui rend un email —, app.request et app.session valent null, et app.flashes rend [].
  • Une property dont le service manque lève une exception : app.user sans le component Security. Dans le template, elle arrive comme une Twig\Error\RuntimeError — qui n'est pas une \RuntimeException. Seul app.flashes retombe sur un array vide.
  • Lire app.flashes accède au bag et démarre la session si une session compatible existe ; sinon le résultat est [].

🌍 In Real Life

La situation : l'atelier dispose d'un guichet interne pour demander qui est servi maintenant et quelles consignes s'appliquent. Ce guichet interroge les services présents ; il ne possède pas une photographie immuable de chaque visite.

L’équivalent dans Symfony : app est un AppVariable fourni par l'intégration. Ses accès consultent notamment RequestStack et les services configurés ; app.request vise la Request courante, qui peut être une sous-requête.

Retour à la réalité technique : hors requête, certains accès donnent null ou une liste vide, sans inventer de Request. Un service nécessaire absent peut au contraire provoquer une exception enveloppée par Twig. Lire des données de session peut la démarrer ; disposer d'un utilisateur ne prouve pas l'autorisation de chaque action.

🧠 Comment le mémoriser : « Un guichet vivant, pas une photo globale. » Image mentale : guichet consultant la pile des demandes en cours. Question-réflexe : quelle requête et quels services existent au moment de ce rendu ?

⚠️ À ne pas confondre : Request courante et principale ; utilisateur courant et décision d'autorisation.

app ressemble au tableau de contexte partagé du bureau, consultable sans parameter explicite à chaque rendu. Le tableau peut ne pas avoir de Request à afficher dans un traitement CLI.

Avec une Request courante, app.current_route correspond à app.request.attributes.get('_route').

Déclarer ses propres globales

À retenir en priorité
  1. Les variables passées au rendu masquent les globales homonymes.
  2. Les macros conservent l'accès aux globales.

Déclare comme globale une donnée transversale stable, telle que le nom du blog, plutôt que l'article sélectionné par une URL. Un service global expose des méthodes appelables depuis le rendu : rendre un mailer accessible n'est pas une recommandation pour envoyer des emails depuis un template. Laisse l'action applicative décider des effets et passe ses résultats à Twig.

# config/packages/twig.yaml
twig:
    globals:
        ga_tracking: 'UA-xxxxx-x'
        mailer: '@app.mailer'

Une valeur qui commence par @ désigne un service. Une extension Twig déclare des globales par GlobalsInterface::getGlobals().

  • Une variable passée au rendu masque la globale du même nom.
  • Les globales sont visibles dans les macros, qui ne voient pourtant pas les variables du template appelant.

🌍 In Real Life

La situation : chaque poste d'impression connaît le nom de l'établissement. Une fiche de commande peut néanmoins fournir sa propre valeur pour un champ ordinaire ; une petite machine de composition reçoit ses arguments, pas tout le bureau de l'appelant.

L’équivalent dans Symfony : twig.globals ou GlobalsInterface::getGlobals() fournissent les valeurs transversales ; le contexte masque une globale ordinaire homonyme. Les macros voient les globales et leurs arguments, pas automatiquement les variables du template appelant.

Retour à la réalité technique : un service référencé par @id expose des méthodes, pas seulement une constante. Éviter les effets applicatifs, comme envoyer un email, pendant le rendu. Une valeur dépendant du visiteur ne doit pas devenir un instantané durable dans un environnement réutilisé ; garder les données de page explicites.

🧠 Comment le mémoriser : « L'enseigne est commune, la commande reste explicite. » Image mentale : enseigne au-dessus des postes et fiche propre à chaque impression. Question-réflexe : cette donnée est-elle vraiment transversale et stable, ou appartient-elle à ce rendu ?

⚠️ À ne pas confondre : globale disponible, valeur prioritaire du contexte et état partagé sans limite de durée.

Le piège

Après la modification de l'article, le layout et une carte peuvent tous deux demander les notices. Le premier appel consommant obtient les messages, le second ne les retrouvera plus. Désigne un endroit de consommation ; peekAll() évite la consommation mais exige une session disponible et n'évite pas les effets d'accès à celle-ci.

app.flashes consomme les messages : les afficher deux fois dans une page n'en montre qu'une. La lecture sans consommer est app.session.flashbag.peekAll().

🌍 In Real Life

La situation : le premier employé retire les avis d'une corbeille pour les afficher. Le suivant trouve la corbeille vide ; il pourrait pourtant réutiliser une copie déjà retirée.

L’équivalent dans Symfony : app.flashes consomme les messages lus du FlashBag. Deux appels consommants successifs pour les mêmes messages ne les retrouvent pas deux fois ; peekAll() consulte sans les retirer.

Retour à la réalité technique : la consommation ne garantit pas qu'un humain ait vu l'avis et n'interdit pas de rendre plusieurs fois une valeur déjà récupérée. peekAll() exige une session adaptée et ne supprime pas les effets d'accès à la session, notamment sur le cache.

🧠 Comment le mémoriser : « Corbeille vidée, copie encore utilisable. » Image mentale : avis en main et corbeille vide derrière. Question-réflexe : est-ce une nouvelle lecture du bag ou une réutilisation du résultat déjà obtenu ?

⚠️ À ne pas confondre : consommation, affichage, consultation non consommatrice et absence d'effet de session.

Pièges d'examen

Piège à éviter

  • Voir l’explication : La session vue depuis un template peut être null

    La session vue depuis un template peut être null — et lire son contenu la démarre, avec l'effet que cela a sur la cachabilité de la page.

  • Voir l’explication : Le user courant vaut null quand personne n'est authentifié.

    Le user courant vaut null quand personne n'est authentifié. Lire app.user.email lève alors une RuntimeError — « Impossible to access an attribute ("email") on a null variable » — en mode strict, actif en dev par défaut, et rend null sinon. Et app.user lève une exception si le component Security n'est pas installé.

  • Voir l’explication : _self, _context, _charset existent sans Symfony.

    _self, _context, _charset existent sans Symfony. Ce sont les globales de Twig ; app est celle de Symfony.

  • Voir l’explication : La forme courte de la route courante existe.

    La forme courte de la route courante existe. Traverser les attributes de la Request pour l'obtenir fonctionne, mais c'est le path long de la même chose.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Twig fournit _self, _context, _charset.
  • Symfony fournit app, dont user, request, session, flashes, current_route.
  • app.flashes consomme les messages ; peekAll() non.
  • Sans Request : app.request et app.session à null.
  • Service absent : exception, en RuntimeError dans le template.
  • twig.globals déclare ; @ pour un service ; visibles dans les macros.
  • Le contexte masque une globale : il masque la globale de même nom.

Moyen mnémotechnique : « Twig en souligné, Symfony dans app, le reste en globals ».

contexte > globales (Twig : _self _context _charset ; TwigBundle : app ; twig.globals / GlobalsInterface) ;
app : user request session flashes(consomme) environment debug token current_route locale
