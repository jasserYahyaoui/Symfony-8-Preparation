Objectif

Connaître les variables disponibles dans tous les templates sans qu'un controller les passe, et savoir en déclarer.

L'essentiel

À comprendre

À retenir en priorité
  1. Ces globales appartiennent à Twig.
  2. app est ajouté par Symfony.

Un template lit des variables qui viennent de deux endroits : le contexte passé au rendu par le controller, et les globales, disponibles partout. Twig en fournit trois, Symfony en ajoute une — app — et l'application peut déclarer les siennes. Le contexte gagne toujours.

Le schéma

L'exemple

Exemple concret

À retenir en priorité
  1. app.flashes consomme les messages.
  2. Deux lectures ordinaires ne rendent pas deux fois la même liste.
<title>{{ site_name }} — {{ title }}</title>
{% if app.user %}Bonjour {{ app.user.userIdentifier }}{% endif %}
{% for message in app.flashes('notice') %}
    <div class="flash">{{ message }}</div>
{% endfor %}
<nav class="{{ app.current_route == 'home' ? 'active' }}">…</nav>

site_name vient de twig.globals, title du controller, le reste de app.

Les trois globales de Twig lui-même

Variable Contenu
_self le nom du template courant
_context toutes les variables visibles, passées et globales
_charset le jeu de caractères courant

La variable `app`

À comprendre

À retenir en priorité
  1. Un template ne s'exécute pas toujours dans une Request HTTP.
  2. Tester les accès qui dépendent du contexte.

C'est quoi ?

app est un objet AppVariable exposé par l'intégration Twig. Ses accès décrivent le contexte courant, pas un tableau de données toujours rempli : request et session peuvent être null, user et token dépendent de Security, locale et enabled_locales décrivent la configuration linguistique, environment et debug celle du kernel.

À quoi ça sert ?

Une présentation peut connaître sa route ou adapter un élément au contexte sans retransmettre ces informations partout. Il faut cependant distinguer une dépendance disponible sans valeur, comme un utilisateur non connecté, d'un service non configuré qui peut provoquer une exception.

Où dans Symfony ?

Avec une Request disponible, app.current_route lit son attribute _route ; app.current_route_parameters lit _route_params. Sans Request mais avec RequestStack configuré, les résultats sont respectivement null et un tableau vide. Ils ne représentent ni la query string complète ni un chemin d'URL.

Comment, étape par étape ?

  1. Déterminer si le rendu est HTTP ou hors HTTP.
  2. Ne demander que les propriétés dont les services sont configurés.
  3. Tester la présence de Request avant un accès direct à ses attributes.
  4. Employer le raccourci de route lorsque seul le nom courant est nécessaire.

Exemple concret Twig

<p>Route : {{ app.current_route ?? 'Aucune route courante' }}</p>
{% if app.request is not null %}
    <p>Lecture explicite : {{ app.request.attributes.get('_route') ?? 'Non appariée' }}</p>
{% endif %}

Dans un rendu HTTP après routage, les deux expressions affichent le même nom. Contre-exemple : appeler directement app.request.attributes dans un email rendu par une commande. Correction : traiter l'absence de Request ou transmettre une donnée de présentation explicite. La présence de app ne prouve pas qu'une session ou Security est utilisable ; app.flashes possède en outre un effet de consommation.

Passage canonique conservé

La variable app

TwigBundle expose app, un object AppVariable, dans chaque template :

Property Contenu
app.user le user courant, ou null s'il n'est pas authentifié
app.request la Request courante
app.session la session, ou null
app.flashes les flash messages ; app.flashes('notice') filtre par type
app.environment, app.debug l'environment et le mode debug
app.token le token de sécurité
app.current_route, app.current_route_parameters la route courante et ses parameters
app.locale, app.enabled_locales la locale courante et les locales activées
  • Sans Request — une command qui rend un email —, app.request et app.session valent null, et app.flashes rend [].
  • Une property dont le service manque lève une exception : app.user sans le component Security. Dans le template, elle arrive comme une Twig\Error\RuntimeError — qui n'est pas une \RuntimeException. Seul app.flashes retombe sur un array vide.
  • Lire app.flashes démarre la session.

app ressemble au tableau de contexte partagé du bureau, consultable sans parameter explicite à chaque rendu. Le tableau peut ne pas avoir de Request à afficher dans un traitement CLI.

Avec une Request courante, app.current_route correspond à app.request.attributes.get('_route').

Déclarer ses propres globales

À comprendre

À retenir en priorité
  1. Les variables passées au rendu masquent les globales homonymes.
  2. Les macros conservent l'accès aux globales.

C'est quoi ?

Une globale Twig est une variable rendue disponible dans l'environnement de templates, sans la transmettre à chaque appel de rendu. Elle n'est pas une variable globale PHP. TwigBundle ajoute notamment app, objet d'accès au contexte de l'application.

À quoi ça sert ?

Une donnée vraiment commune, comme le nom du site, peut ainsi être configurée une fois. Cela ne justifie pas de cacher toutes les dépendances d'une page dans des globales : une donnée propre à cette page reste plus explicite dans ses paramètres de rendu.

Où dans Symfony ?

twig.globals déclare les globales applicatives ; une valeur commençant par @ référence un service. app.environment et app.debug décrivent le kernel ; app.request, les informations de route, l'utilisateur et la session dépendent du contexte disponible. Une variable passée au rendu peut masquer une globale de même nom : cette priorité doit être intentionnelle.

Comment, étape par étape ?

  1. Vérifier que la donnée est commune et non un état propre à une seule page.
  2. La déclarer sous twig.globals.
  3. Utiliser son nom directement dans le template.
  4. Si l'on consulte app, tenir compte d'un rendu sans Request, comme dans une commande. Une globale disponible n'implique pas que tout le contexte HTTP existe.

Exemple concret YAML et Twig

Dans config/packages/twig.yaml :

twig:
    globals:
        site_name: 'Guide Symfony'

Dans un template HTML :

<header>{{ site_name }}</header>
<p>Environnement : {{ app.environment }}</p>

La première variable vient de la configuration ; la seconde de l'intégration Symfony. Contre-exemple : lire app.flashes dans un en-tête puis espérer retrouver les mêmes messages dans le corps. Cette lecture les consomme. Correction : lire une fois et conserver le résultat pour ses usages, ou employer une consultation sans consommation lorsque c'est réellement l'intention. L'accès aux flash messages implique aussi les dépendances de session ; ce n'est pas une simple constante de présentation.

Passage canonique conservé

Déclarer ses propres globales

# config/packages/twig.yaml
twig:
    globals:
        ga_tracking: 'UA-xxxxx-x'
        mailer: '@app.mailer'

Une valeur qui commence par @ désigne un service. Une extension Twig déclare des globales par GlobalsInterface::getGlobals().

  • Une variable passée au rendu masque la globale du même nom.
  • Les globales sont visibles dans les macros, qui ne voient pourtant pas les variables du template appelant.

Repère — Les trois globales de Twig lui-même : _self, _context and _charset. Ces globales appartiennent à Twig. app est ajouté par Symfony.

Le piège

Piège à éviter

C'est quoi ?

app.flashes lit les messages du sac de flash de session en les retirant de ce sac. Avec un type, il consomme ce type ; sans type, il consomme tous les messages disponibles. Ce n'est donc pas une propriété de présentation sans effet de bord.

À quoi ça sert ?

Une notification peut être affichée après une redirection sans réapparaître à chaque page. Si plusieurs parties d'une page ont besoin du même résultat, il faut partager les messages lus plutôt que redemander leur consommation.

Où dans Symfony ?

AppVariable délègue à get ou all du FlashBag. Lorsque la session adaptée n'est pas disponible, app.flashes retourne un tableau vide. Quand elle est utilisée, cette lecture peut démarrer la session ; peek et peekAll consultent sans retirer les messages, mais supposent une session utilisable.

Comment, étape par étape ?

  1. Choisir le type de messages à afficher.
  2. Lire une seule fois les messages destinés à cette page.
  3. Conserver le tableau obtenu si plusieurs rendus en ont besoin.
  4. Ne pas relire le sac pour tester ce qui vient d'être consommé.

Exemple concret Twig

{% set notices = app.flashes('notice') %}
{% for message in notices %}
    <p role="status">{{ message }}</p>
{% endfor %}
<p>{{ notices|length }} notification(s) affichée(s).</p>

Le compteur utilise le tableau déjà lu ; il ne consomme rien de plus. Contre-exemple : afficher app.flashes('notice') dans la boucle puis l'appeler à nouveau pour compter : le second résultat est vide. Correction : conserver le premier résultat, comme ci-dessus. Pour une inspection sans consommation, choisir peek explicitement plutôt que modifier la durée de vie des notifications par accident.

Passage canonique conservé

Le piège

app.flashes consomme les messages : les afficher deux fois dans une page n'en montre qu'une. La lecture sans consommer est app.session.flashbag.peekAll().

Pièges d'examen

Piège à éviter

  • Voir l’explication : La session vue depuis un template peut être null

    La session vue depuis un template peut être null — et lire son contenu la démarre, avec l'effet que cela a sur la cachabilité de la page.

  • Voir l’explication : Le user courant vaut null quand personne n'est authentifié.

    Le user courant vaut null quand personne n'est authentifié. Lire app.user.email lève alors une RuntimeError — « Impossible to access an attribute ("email") on a null variable » — en mode strict, actif en dev par défaut, et rend null sinon. Et app.user lève une exception si le component Security n'est pas installé.

  • Voir l’explication : _self, _context, _charset existent sans Symfony.

    _self, _context, _charset existent sans Symfony. Ce sont les globales de Twig ; app est celle de Symfony.

  • Voir l’explication : La forme courte de la route courante existe.

    La forme courte de la route courante existe. Traverser les attributes de la Request pour l'obtenir fonctionne, mais c'est le path long de la même chose.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Twig fournit _self, _context, _charset.
  • Symfony fournit app, dont user, request, session, flashes, current_route.
  • app.flashes consomme les messages ; peekAll() non.
  • Sans Request : app.request et app.session à null.
  • Service absent : exception, en RuntimeError dans le template.
  • twig.globals déclare ; @ pour un service ; visibles dans les macros.
  • Le contexte masque une globale : il masque la globale de même nom.

Moyen mnémotechnique : « Twig en souligné, Symfony dans app, le reste en globals ».

contexte > globales (Twig : _self _context _charset ; TwigBundle : app ; twig.globals / GlobalsInterface) ;
app : user request session flashes(consomme) environment debug token current_route locale
