Objectif

Décrire le flux d'authentication de Symfony 8.0 en nommant correctement chaque object, savoir lequel construire selon qu'il y a ou non des identifiers à vérifier, et diagnostiquer un badge qui n'a pas l'effet attendu.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le passport rassemble les informations.
  2. Les listeners vérifient ensuite les badges.

Trois objects se partagent l'authentication : l'authenticator décide s'il prend la Request et constitue un dossier, le passport ; chaque badge du dossier porte une information ou déclenche une vérification. L'authenticator ne valide rien lui-même : des listeners vérifient chaque badge.

Le schéma

À retenir en priorité
  1. Le token représente le succès.
  2. Un badge non résolu empêche ce succès.

Remember-me et rehachage arrivent après onAuthenticationSuccess(). Une exception levée dans authenticate() mène au même échec que les vérifications.

L'exemple

▣ Exemple concret

À retenir en priorité
  1. UserBadge identifie le user.
  2. PasswordCredentials porte la preuve à vérifier.

Le service applicatif ApiKeyVerifier doit vérifier réellement la clé et lever BadCredentialsException si elle est invalide ; il ne doit jamais accepter un identifier simplement fourni par le client. Le contrat ci-dessous remplace le placeholder non exécutable de l'original, sans inventer une implémentation de stockage.

interface ApiKeyVerifier
{
    /** @throws BadCredentialsException */
    public function validateAndIdentify(string $apiKey): string;
}

class ApiKeyAuthenticator extends AbstractAuthenticator
{
    public function __construct(private ApiKeyVerifier $apiKeys)
    {
    }

    public function supports(Request $request): ?bool
    {
        return $request->headers->has('auth-token');
    }

    public function authenticate(Request $request): Passport
    {
        $userIdentifier = $this->apiKeys->validateAndIdentify(
            (string) $request->headers->get('auth-token')
        );

        return new SelfValidatingPassport(new UserBadge($userIdentifier));
    }

    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null; // la Request continue vers le controller
    }

    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        return new JsonResponse(['message' => strtr($exception->getMessageKey(), $exception->getMessageData())], 401);
    }
}

SelfValidatingPassport convient ici parce que le service a déjà vérifié la preuve. Les imports Symfony et le service applicatif concret restent à fournir dans l'application ; ce fragment illustre le contrat de l'authenticator.

Les cinq methods de l'authenticator

À retenir en priorité
  1. null laisse poursuivre le traitement.
  2. Une Response fixe la suite immédiatement.
Method Ce qu'elle fait Retour
supports() prendre ou non la Request true, false ou null
authenticate() constituer le dossier un Passport, jamais un user ni un bool
createToken() transformer le passport validé en token un TokenInterface
onAuthenticationSuccess() la suite après succès une Response, ou null pour continuer
onAuthenticationFailure() la suite après échec une Response, ou null pour continuer

AbstractAuthenticator fournit createToken() (un PostAuthenticationToken) ; l'ancien createAuthenticatedToken() n'existe plus.

`supports()` : trois retours possibles

À retenir en priorité
  1. null peut autoriser un traitement lazy.
  2. Ce n'est pas un accord immédiat.
  • true — authenticate() est appelé ; false — l'authenticator est ignoré ;
  • null — authenticate() « can be called lazily when accessing the token storage » : seulement si quelqu'un lit le token.
  • Ce null n'agit que sur un firewall lazy avec état : avec stateless: true, lazy est ignoré sans avertissement.

Passport ou SelfValidatingPassport

À retenir en priorité
  1. SelfValidatingPassport évite une vérification de credentials supplémentaire.
  2. Il ne rend pas une entrée arbitraire fiable.

Passport exige des credentials : __construct(UserBadge $userBadge, CredentialsInterface $credentials, array $badges = []).

  • Une preuve à contrôler (password, callable) → Passport et des credentials.
  • Rien à vérifier (token d'API déjà digne de confiance) → SelfValidatingPassport, qui ne prend que UserBadge et les badges.

Les badges

À retenir en priorité
  1. Un résultat truthy ne suffit pas.
  2. Le contrôle attend true strict.
Badge Role
UserBadge l'identifier du user — obligatoire
PasswordCredentials password en clair, vérifié par le hasher
CustomCredentials vérification par un callable, qui doit rendre exactement true
PasswordUpgradeBadge autorise le réencodage du password
RememberMeBadge demande le cookie « se souvenir de moi »
CsrfTokenBadge fait vérifier un token CSRF
PreAuthenticatedUserBadge user authentifié en amont : checkPreAuth() n'est pas appelé
  • UserBadge accepte un user loader ; s'il rend null, l'échec est masqué par défaut en « Invalid credentials. », pour ne pas révéler quels users existent ; seule security.expose_security_errors: all montre « Username could not be found. ».
  • Un identifier vide ou de plus de 4096 octets est refusé dès la construction (BadCredentialsException).
  • CustomCredentials compare avec true au sens strict : 1 échoue.

Diagnostiquer un badge

À retenir en priorité
  1. Le badge indique une capacité.
  2. La configuration et l'activation restent nécessaires.
  • Un badge non résolu fait échouer l'authentication : « Security badge … is not resolved, did you forget to register the correct listeners? ».
  • RememberMeBadge est désactivé à sa création : il faut le badge, la key remember_me sur le firewall, et l'activation — _remember_me dans la Request, always_remember_me, ou enable().
  • Ordre du diagnostic : authenticate() est-il appelé (supports(), lazy) ? L'échec vient-il des vérifications (CheckPassportEvent) ? L'effet manque-t-il après le succès (LoginSuccessEvent) ?

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Chaque badge requis doit être résolu.
  2. Vérifier les listeners enregistrés.

supports() = null n'est pas « redemande-moi » : c'est l'authentication lazy, et seulement sur un firewall lazy avec état.

RememberMeBadge n'active rien à lui seul : sans remember_me ni activation, aucun cookie.

Un badge non résolu est une panne, pas une permission silencieuse.

getUser() sur un passport sans UserBadge lève une LogicException : erreur de programmation, pas échec de connexion.

createToken(), pas createAuthenticatedToken().

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Employer la method actuelle.
  2. L'ancienne method createAuthenticatedToken n'est plus le contrat.

Si tu dois retenir seulement 8 choses :

  • Authenticator (process) → passport (dossier) → badges (pièces).
  • Cinq methods ; createToken() fourni par AbstractAuthenticator.
  • supports() = null : lazy, seulement sur un firewall lazy avec état.
  • Une preuve à vérifier : Passport ; aucune : SelfValidatingPassport.
  • UserBadge obligatoire ; user introuvable masqué en « Invalid credentials. ».
  • CustomCredentials : true strict.
  • Badge non résolu = échec.
  • RememberMeBadge : badge + remember_me + activation.

Moyen mnémotechnique : « l'authenticator remplit, les listeners vérifient ».

supports (true/false/null=lazy) → authenticate → Passport(UserBadge, credentials, badges) | SelfValidatingPassport
→ CheckPassportEvent → createToken → onAuthenticationSuccess → LoginSuccessEvent (remember-me) ; échec → onAuthenticationFailure
