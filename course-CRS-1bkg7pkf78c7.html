Objectif

Faire construire un service par autre chose que new, choisir l'écriture de l'option factory selon le callable, savoir à qui vont les arguments, et prévoir ce que le container fait de la valeur retournée.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La factory décide de la construction.
  2. Sa valeur retournée devient le service.

Avec l'option factory, le container ne fait pas new : il appelle un callable — une method statique, la method d'un service (@), un service invocable, une function. Les arguments vont à la factory, et la valeur retournée devient le service, sans contrôle de son type.

Le schéma

À retenir en priorité
  1. Le container appelle la factory.
  2. La factory choisit ensuite les arguments du constructor.

Le fil rouge : un NewsletterManager

À retenir en priorité
  1. Le résultat suit le partage du service.
  2. shared: false redemande une construction.
class NewsletterManager
{
    public function __construct(private string $sender = 'none') {}

    public static function create(string $sender): self
    {
        return new self('factory:'.$sender);
    }
}

Les écritures : choisir selon la nature du callable

À retenir en priorité
  1. Le préfixe @ désigne un service.
  2. Sans @ le callable est statique.
Ce qui fabrique Écriture YAML
une method statique d'une autre class factory: ['App\Email\NewsletterManagerStaticFactory', 'createNewsletterManager']
une method statique de la class du service factory: [null, 'create']
une method d'un service factory: ['@App\Email\NewsletterManagerFactory', 'createNewsletterManager']
un service invocable factory: '@App\Email\InvokableNewsletterManagerFactory' → __invoke()
une function PHP factory: 'App\make_newsletter'
  • Sans @, un nom de class : appel statique. Avec @, un id de service : le container le récupère, puis appelle la method.
  • Une method d'instance sans @ passe la compilation, puis le premier get() lève Error : « Non-static method … cannot be called statically ».
  • En PHP : ->factory(NewsletterManagerStaticFactory::createNewsletterManager(...)) ou ->factory([service(…), 'createNewsletterManager']).

`[null, 'create']` : la class du service elle-même

À retenir en priorité
  1. null reprend la class de la definition.
  2. Il ne désigne pas une function globale.
  • null = la class de ce service ; ni une function globale, ni un service.
  • constructor: 'create' dit la même chose ; avec factory sur le même service : LogicException, « …cannot declare a factory as well as a constructor ».
  • #[Autoconfigure(constructor: 'create')] sur la class : appliqué seulement si le service est autoconfiguré.

Les arguments vont à la factory

À retenir en priorité
  1. La signature de la factory est câblée.
  2. Les arguments ne ciblent pas directement le constructor final.

Avec factory: [null, 'create'] et arguments: ['fabien'] :

Appel Valeur reçue
NewsletterManager::create(), par le container 'fabien'
__construct(), par new self(...) dans create() 'factory:fabien'

Les arguments de la factory sont autowirés si l'autowiring est actif.

Ce que le container retient : la valeur retournée

À retenir en priorité
  1. La class guide l'autowiring.
  2. Le retour de la factory doit respecter le contrat.
  • Un object obligatoire : factory: 'strtoupper' lève au premier get() « Return value must be of type ?object, string returned ».
  • Type non contrôlé : class n'a pas d'effet sur l'object obtenu, mais l'autowiring la lit. Une factory qui rend un stdClass pour la class Liar fait échouer son consommateur : « must be of type App\Liar, stdClass given ».
  • Partagé par défaut : la factory est appelée une fois ; avec shared: false, à chaque get().

Une expression comme factory

À retenir en priorité
  1. L'expression accède aux arguments configurés.
  2. ExpressionLanguage doit être disponible.
factory: '@=parameter("kernel.debug") ? service("tracable_newsletter") : service("newsletter")'

arg(0) y lit le premier argument de la definition. Sans le component ExpressionLanguage, le file ne se charge pas ; @= n'est accepté que pour factory, pas pour configurator.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Les deux mécanismes choisissent la construction.
  2. Il faut sélectionner une seule forme.

Les arguments vont à la factory. Le container n'appelle pas le constructor du service lui-même ; si la factory fait new self(…), c'est elle qui choisit ce qu'elle lui passe.

[null, 'create'] désigne la class du service, pas une function globale.

Une factory de service utilise @ ; une factory statique nomme la class ; '@service' seul appelle __invoke().

Une method d'instance sans @ échoue au premier get(), pas à la compilation : Error, « Non-static method … cannot be called statically ».

Le container ne contrôle pas le type retourné : l'erreur arrive chez le consommateur.

factory et constructor ne se combinent pas : LogicException dès le chargement de la configuration.

#[Autoconfigure(constructor: …)] dépend de l'autoconfiguration : avec autoconfigure: false, l'attribute est ignoré et le constructor est utilisé.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Un service peut être callable.
  2. La factory invocable n'a pas besoin de nom de method séparé.

Si tu dois retenir seulement 7 choses :

  • Sans @ : statique ; avec @ : un service ; '@service' seul : __invoke().
  • [null, 'create'] = la class du service ; constructor: équivaut.
  • factory et constructor : LogicException.
  • Les arguments vont à la factory, jamais directement au constructor.
  • La valeur retournée est le service : un object, type non contrôlé.
  • Partagée par défaut ; shared: false rappelle la factory.
  • @= : une expression, avec ExpressionLanguage.

Moyen mnémotechnique : « Qui fabrique ? Avec quoi ? Que rend-il ? »
