Objectif

Faire construire un service par autre chose que new, choisir l'écriture de l'option factory selon le callable, savoir à qui vont les arguments, et prévoir ce que le container fait de la valeur retournée.

L'essentiel

À comprendre

À retenir en priorité
  1. La factory décide de la construction.
  2. Sa valeur retournée devient le service.

Avec l'option factory, le container ne fait pas new : il appelle un callable — une method statique, la method d'un service (@), un service invocable, une function. Les arguments vont à la factory, et la valeur retournée devient le service, sans contrôle de son type.

Le schéma

À retenir en priorité
  1. Le container appelle la factory.
  2. La factory choisit ensuite les arguments du constructor.

Le fil rouge : un NewsletterManager

À retenir en priorité
  1. Le résultat suit le partage du service.
  2. shared: false redemande une construction.
class NewsletterManager
{
    public function __construct(private string $sender = 'none') {}

    public static function create(string $sender): self
    {
        return new self('factory:'.$sender);
    }
}

Les écritures : choisir selon la nature du callable

À comprendre

À retenir en priorité
  1. Le préfixe @ désigne un service.
  2. Sans @ le callable est statique.

C'est quoi ?

Une factory, ou fabrique, est un callable chargé de produire le service. Un callable est une fonction ou méthode que PHP peut appeler. Le container utilise sa valeur de retour au lieu d'appeler directement le constructeur configuré de la classe du service.

À quoi ça sert ?

La fabrique convient lorsqu'une création exige une méthode statique, une sélection ou un objet constructeur spécialisé. Elle ne sert pas à déplacer gratuitement un simple new : un constructeur ordinaire reste plus simple si aucun protocole de création supplémentaire n'existe.

Où dans Symfony ?

  • ['Classe', 'create'] désigne une méthode statique.
  • ['@service.factory', 'create'] désigne une méthode d'un service.
  • '@service.factory' seul utilise son __invoke().
  • [null, 'create'] prend la classe du service en cours de définition.

Comment, étape par étape ?

  1. Identifier si la méthode est statique ou nécessite une instance.
  2. Enregistrer la fabrique comme service lorsqu'elle possède ses propres dépendances.
  3. Configurer le callable du service produit.
  4. Au besoin du service, appeler la fabrique et conserver l'objet retourné selon la règle de partage.

Exemple concret YAML

TokenFactory possède une méthode d'instance create(): Token, et les deux classes existent.

services:
    App\TokenFactory: ~
    App\Token:
        factory: ['@App\TokenFactory', 'create']

Le @ demande l'instance de fabrique avant l'appel. Contre-exemple : le retirer alors que create() n'est pas statique ; l'appel statique devient invalide. Correction : conserver la référence de service. La fabrique doit retourner un objet compatible avec les consommateurs ; déclarer class: App\Token ne convertit pas un objet d'un autre type en Token.

Ce qui fabrique Écriture YAML
une method statique d'une autre class factory: ['App\Email\NewsletterManagerStaticFactory', 'createNewsletterManager']
une method statique de la class du service factory: [null, 'create']
une method d'un service factory: ['@App\Email\NewsletterManagerFactory', 'createNewsletterManager']

une function PHP factory: 'App\make_newsletter'
  • Sans @, un nom de class : appel statique. Avec @, un id de service : le container le récupère, puis appelle la method.
  • Une method d'instance sans @ passe la compilation, puis le premier get() lève Error : « Non-static method … cannot be called statically ».
  • En PHP : ->factory(NewsletterManagerStaticFactory::createNewsletterManager(...)) ou ->factory([service(…), 'createNewsletterManager']).

`[null, 'create']` : la class du service elle-même

À comprendre

À retenir en priorité
  1. null reprend la class de la definition.
  2. Il ne désigne pas une function globale.

C'est quoi ?

Dans factory: [null, 'create'], null est un raccourci de configuration pour la classe du service défini. Il ne désigne ni un service nommé null, ni l'absence de factory, ni une fonction globale create().

À quoi ça sert ?

La classe peut exposer un constructeur nommé, une méthode statique qui valide les entrées puis appelle un constructeur éventuellement privé. Le raccourci évite de répéter son nom complet dans la même définition.

Où dans Symfony ?

Le loader de DependencyInjection transforme cette notation en factory statique de la classe définie. La forme constructor: 'create' exprime également ce choix ; il ne faut pas la combiner avec une option factory sur la même définition. L'attribut d'autoconfiguration équivalent dépend de l'activation de l'autoconfiguration.

Comment, étape par étape ?

  1. Déterminer la classe de la définition.
  2. Résoudre null vers cette classe.
  3. Appeler sa méthode statique create() avec les arguments configurés.
  4. Utiliser l'objet retourné comme service.

Exemple concret YAML

La classe App\Newsletter expose public static function create(string $rawSender): self et valide une chaîne non vide.

services:
    App\Newsletter:
        factory: [null, 'create']
        arguments:
            $rawSender: 'équipe'

L'appel attendu est App\Newsletter::create('équipe'), pas new App\Newsletter('équipe') décidé directement par le container. Contre-exemple : conserver ce raccourci alors que create() est une méthode d'instance nécessitant une factory distincte. Correction : enregistrer cette factory et utiliser ['@son_identifiant', 'create']. Le raccourci ne contourne pas les règles PHP de visibilité, de type ou d'appel statique.

Passage canonique conservé

[null, 'create'] : la class du service elle-même

  • null = la class de ce service ; ni une function globale, ni un service.
  • constructor: 'create' dit la même chose ; avec factory sur le même service : LogicException, « …cannot declare a factory as well as a constructor ».
  • #[Autoconfigure(constructor: 'create')] sur la class : appliqué seulement si le service est autoconfiguré.

Les arguments vont à la factory

À comprendre

À retenir en priorité
  1. La signature de la factory est câblée.
  2. Les arguments ne ciblent pas directement le constructor final.

C'est quoi ?

Lorsqu'une définition utilise une factory, ses arguments alimentent l'appel de cette factory. Le constructeur de l'objet produit reçoit uniquement ce que la factory décide de lui transmettre.

À quoi ça sert ?

La séparation permet à la factory de normaliser ou de valider des données avant la création. Elle explique aussi pourquoi nommer les arguments d'après le constructeur peut être incorrect si la factory possède une signature différente.

Où dans Symfony ?

L'autowiring, s'il est actif, examine les arguments du callable de fabrication. Le partage concerne le service produit : par défaut, la factory n'est pas rappelée à chaque utilisation d'une méthode de ce service. shared: false demande une nouvelle production à chaque résolution du service concerné.

Comment, étape par étape ?

  1. Le container résout les arguments de la factory.
  2. Il appelle le callable configuré.
  3. La factory construit ou choisit l'objet et le retourne.
  4. Le container fournit cette valeur aux consommateurs.

Exemple concret PHP

Ce PHP autonome isole les deux appels ; une définition factory: [null, 'create'] avec l'argument ' équipe ' aurait la même chaîne de transmission.

<?php
final class Newsletter
{
    private function __construct(public readonly string $sender) {}
    public static function create(string $rawSender): self
    {
        $sender = trim($rawSender);
        if ($sender === '') {
            throw new InvalidArgumentException('Expéditeur vide');
        }
        return new self($sender);
    }
}
$newsletter = Newsletter::create(' équipe ');
echo $newsletter->sender, "\n";

La factory reçoit les espaces ; le constructeur reçoit équipe. Une chaîne vide après nettoyage est refusée. Contre-exemple : configurer $sender comme argument nommé de la factory alors que son paramètre est $rawSender. Correction : nommer l'argument d'après la méthode réellement appelée. La validation ne doit pas être remplacée par un objet partiellement construit ou un null silencieux.

Passage canonique conservé

Les arguments vont à la factory

Avec factory: [null, 'create'] et arguments: ['fabien'] :

Appel Valeur reçue
NewsletterManager::create(), par le container 'fabien'
__construct(), par new self(...) dans create() 'factory:fabien'

Les arguments de la factory sont autowirés si l'autowiring est actif.

Ce que le container retient : la valeur retournée

À retenir en priorité
  1. La class guide l'autowiring.
  2. Le retour de la factory doit respecter le contrat.
  • Un object obligatoire : factory: 'strtoupper' lève au premier get() « Return value must be of type ?object, string returned ».
  • Type non contrôlé : class n'a pas d'effet sur l'object obtenu, mais l'autowiring la lit. Une factory qui rend un stdClass pour la class Liar fait échouer son consommateur : « must be of type App\Liar, stdClass given ».
  • Partagé par défaut : la factory est appelée une fois ; avec shared: false, à chaque get().

Une expression comme factory

À retenir en priorité
  1. L'expression accède aux arguments configurés.
  2. ExpressionLanguage doit être disponible.
factory: '@=parameter("kernel.debug") ? service("tracable_newsletter") : service("newsletter")'

arg(0) y lit le premier argument de la definition. Sans le component ExpressionLanguage, le file ne se charge pas ; @= n'est accepté que pour factory, pas pour configurator.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Les deux mécanismes choisissent la construction.
  2. Il faut sélectionner une seule forme.
  • Voir l’explication : Les arguments vont à la factory.

    Les arguments vont à la factory. Le container n'appelle pas le constructor du service lui-même ; si la factory fait new self(…), c'est elle qui choisit ce qu'elle lui passe.

  • Voir l’explication : [null, 'create'] désigne la class du service

    [null, 'create'] désigne la class du service, pas une function globale.

  • Voir l’explication : Une factory de service utilise @

    Une factory de service utilise @ ; une factory statique nomme la class ; '@service' seul appelle __invoke().

  • Voir l’explication : Une method d'instance sans @ échoue au premier get()

    Une method d'instance sans @ échoue au premier get(), pas à la compilation : Error, « Non-static method … cannot be called statically ».

  • Voir l’explication : Le container ne contrôle pas le type retourné

    Le container ne contrôle pas le type retourné : l'erreur arrive chez le consommateur.

  • Voir l’explication : factory et constructor ne se combinent pas

    factory et constructor ne se combinent pas : LogicException dès le chargement de la configuration.

  • Voir l’explication : #[Autoconfigure(constructor: …)] dépend de l'autoconfiguration

    #[Autoconfigure(constructor: …)] dépend de l'autoconfiguration : avec autoconfigure: false, l'attribute est ignoré et le constructor est utilisé.

Fiche express

À mémoriser

À retenir en priorité
  1. Un service peut être callable.
  2. La factory invocable n'a pas besoin de nom de method séparé.

Si tu dois retenir seulement 7 choses :

  • Sans @ : statique ; avec @ : un service ; '@service' seul : __invoke().
  • [null, 'create'] = la class du service ; constructor: équivaut.
  • factory et constructor : LogicException.
  • Les arguments vont à la factory, jamais directement au constructor.
  • La valeur retournée est le service : un object, type non contrôlé.
  • Partagée par défaut ; shared: false rappelle la factory.
  • @= : une expression, avec ExpressionLanguage.

Moyen mnémotechnique : « Qui fabrique ? Avec quoi ? Que rend-il ? »
