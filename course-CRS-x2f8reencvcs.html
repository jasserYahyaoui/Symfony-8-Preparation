Les trois délimiteurs

À comprendre

C'est quoi ?

Les délimiteurs indiquent au parseur Twig ce qu'il doit faire : {{ }} affiche une expression, {% %} introduit une instruction du langage et {# #} contient un commentaire retiré du rendu.

À quoi ça sert ?

Ils séparent la décision d'afficher, la valeur affichée et les notes destinées aux auteurs. Une instruction peut organiser ou produire du contenu ; cela ne la transforme pas en expression à placer entre doubles accolades.

Où dans Symfony ?

Ces règles appartiennent à Twig, sans extension Symfony. Le texte hors délimiteurs est généralement envoyé tel quel ; les expressions affichées passent par la politique d'échappement du template.

Comment, étape par étape ?

  1. Affecter ou tester des données avec un tag d'instruction.
  2. Placer l'expression à afficher entre doubles accolades.
  3. Utiliser le commentaire Twig pour une note absente du résultat.
  4. Fermer les structures comme if et for avec leur tag de fin.

Exemple concret Twig

{% set name = 'Ada' %}
{# Cette note ne figure pas dans le HTML rendu. #}
{% if name is not empty %}
    <p>Bonjour {{ name }}</p>
{% endif %}

set prépare la variable sans afficher son affectation ; if choisit le paragraphe ; les doubles accolades affichent Ada. Contre-exemple : écrire {{ if name }} pour ouvrir une condition. Correction : employer {% if name %} et {% endif %}. Un commentaire HTML, contrairement à un commentaire Twig, reste dans le HTML envoyé au navigateur ; il ne convient pas à une note que l'on souhaite retirer du rendu.

Passage canonique conservé

Les trois délimiteurs

Délimiteur Role
{{ … }} affiche le résultat d'une expression
{% … %} exécute une instruction : if, for, extends, set
{# … #} commentaire, jamais rendu

Dans un script de théâtre, les expressions affichées sont les répliques ; les tags organisent l'action ; les commentaires sont les notes privées. Certains tags rendent du contenu, mais ce ne sont pas des expressions affichées par doubles accolades.

`foo.bar` : l'ordre de résolution

À comprendre

C'est quoi ?

La notation foo.bar demande à Twig de résoudre une donnée nommée bar sur foo. Elle ne signifie pas uniquement « lire une propriété PHP ». Twig examine notamment une clé de tableau, une propriété accessible, une constante ou une méthode selon les règles de résolution du langage.

À quoi ça sert ?

Un template peut ainsi présenter des tableaux et des objets avec une syntaxe similaire. La contrepartie est qu'une expression apparemment identique peut appeler une méthode : elle n'est pas forcément une lecture de champ sans coût. La résolution et la gestion du vide sont aussi deux sujets distincts.

Où dans Symfony ?

TwigBundle fournit les données du rendu, mais l'ordre de résolution appartient à Twig. En 3.22, il faut distinguer accès tableau, propriété, constante et méthodes bar(), getBar(), isBar(), hasBar(), puis le cas __call. Si rien n'est résolu, strict_variables décide entre erreur et valeur nulle. L'ordre détaillé conservé ci-dessous reste important pour les objets exposant plusieurs accès concurrents.

Comment, étape par étape ?

  1. Identifier si foo est un tableau, un objet ou une valeur absente.
  2. Appliquer l'ordre de résolution, sans supposer que le nom désigne toujours la même catégorie de membre.
  3. Choisir le repli : ?? remplace une valeur absente ou nulle ; ?: choisit selon la valeur booléenne et remplace donc aussi zéro ou faux.
  4. Employer {{ ... }} pour afficher, {% ... %} pour une instruction, {# ... #} pour un commentaire.

Exemple concret Twig

{% set product = {stock: 0} %}
<p>{{ product.stock ?? 10 }}</p>
<p>{{ product.stock ?: 10 }}</p>
<p>{{ product.missing ?? 'inconnu' }}</p>

Les trois contenus attendus sont 0, 10 et inconnu. Contre-exemple : utiliser ?: 10 pour un stock dont zéro est une valeur légitime. Correction : ?? 10 si seul le manque de donnée doit déclencher le défaut. Pour concaténer du texte, utiliser ~, pas le point PHP. Les marqueurs {{- et -}} retirent les blancs voisins : les ajouter systématiquement peut coller deux mots qui devaient rester séparés.

Passage canonique conservé

foo.bar : l'ordre de résolution

Pour {{ foo.bar }}, Twig essaie dans cet ordre :

  1. $foo['bar'] — array, ArrayObject ou ArrayAccess ;
  2. $foo->bar — property publique ;
  3. Foo::bar — constante de class, dont le nom correspond à la casse près ;
  4. bar(), getBar(), isBar(), hasBar() — methods, casse ignorée ; un hasser est écarté quand un isser du même nom existe ;
  5. __call('bar'), si la class le déclare ;
  6. sinon null — ou une RuntimeError avec strict_variables.

Conséquences : l'array passe avant l'object (un ArrayAccess gagne sur la property) ; const STATUS ne masque pas getStatus(), mais const status le masque. La documentation Symfony énumère sept étapes sans la constant ; l'engine 3.22 l'implémente — un énoncé d'examen peut n'en citer que sept.

  • {{ foo.bar() }} force l'appel d'une method.
  • Nom dynamique ou avec un tiret : {{ user.(name) }}, {{ user.('first-name') }} (3.15).
  • attribute() est dépréciée depuis 3.15, mais en 3.22 elle fonctionne sans notice de deprecation.

L’operator ?: remplace une valeur fausse, tandis que ?? remplace une valeur absente ou null. Une variable absente déclenche strict_variables avec ?:, mais pas avec ??.

Les operators

À comprendre

À retenir en priorité
  1. ~ concatène les strings.
  2. + effectue une addition et peut échouer sur des strings non numériques.

C'est quoi ?

Un operator combine des valeurs ou produit une condition. Twig utilise notamment ~ pour concaténer du texte, + pour additionner, and/or/not pour la logique et is pour appliquer un test nommé. Ce n'est pas une copie de la syntaxe PHP.

À quoi ça sert ?

Choisir l'opération selon l'intention évite les conversions inattendues et les erreurs de compilation. Pour une égalité stricte, le test same as vérifie valeur et type ; == ne possède pas ce même contrat.

Où dans Symfony ?

Ces opérateurs sont ceux du langage Twig 3.22. Les parenthèses rendent explicite l'ordre d'un calcul combiné avec une concaténation ou un filtre. in vérifie une appartenance ; is not nie un test ; &&, || et === ne sont pas des remplacements valides des formes Twig correspondantes.

Comment, étape par étape ?

  1. Déterminer si le résultat attendu est un texte, un nombre ou un booléen.
  2. Choisir la famille d'opérateur adaptée.
  3. Parenthéser les mélanges d'opérations plutôt que compter sur une priorité intuitive.
  4. Tester les valeurs de même représentation mais de types différents.

Exemple concret Twig

{% set total = 1 + 2 %}
<p>{{ 'Total : ' ~ total }}</p>
{% if total is same as(3) and 'guide' in ['guide', 'aide'] %}
    <p>Trois éléments dans une catégorie connue.</p>
{% endif %}

Le premier paragraphe affiche Total : 3. Contre-exemple : utiliser 'Total : ' + total, ou transposer total === 3. Correction : ~ construit le texte et is same as(3) effectue le test strict. Pour un repli, ?? vise l'absence ou null alors que ?: vise une valeur fausse, dont zéro ; ces intentions ne doivent pas être confondues.

Passage canonique conservé

Les operators

Famille Operators
Arithmétique + - * / % // **
Comparaison == != < > <= >= <=>
Logique and or not xor — pas && \|\| ! ; bit à bit : b-and b-or b-xor
Strings ~ concatène ; starts with, ends with, matches
Appartenance in, not in (aussi dans une string) ; .. construit une plage
Itérables has some, has every, avec une function fléchée
Test is : defined, empty, null, iterable, same as
Confort ?: (Elvis), ?? (coalescence)
Functions => function fléchée ; ... étend une séquence (3.7) ou des arguments (3.15)

Ce qui tombe à l'examen :

  • {{ 'a' + 'b' }} casse le rendu : + additionne, PHP 8.4 refuse deux strings non numériques, et Twig remonte la TypeError dans une RuntimeError ;
  • // est la division entière et arrondit vers le bas : -7 // 2 vaut -4 ;
  • ** s'associe à droite : 2 ** 3 ** 2 vaut 512 ;
  • ?: remplace une valeur fausse (0, ''), ?? une valeur absente ou null ; sur une variable absente, ?: déclenche strict_variables, ?? non ;
  • sur un itérable vide, has every vaut true, has some vaut false ;
  • true && false ne compile pas.

Affectation et espaces

À comprendre

À retenir en priorité
  1. Le contrôle - retire tous les blancs du côté concerné.
  2. Le contrôle ~ conserve les sauts de ligne.

C'est quoi ?

Le signe - accolé à un délimiteur Twig retire les blancs voisins du côté concerné, y compris les sauts de ligne. Le signe ~ retire les blancs de ligne mais préserve les sauts de ligne ; à droite il empêche également leur retrait automatique habituel.

À quoi ça sert ?

Ce contrôle aide à produire un texte ou un attribut dont les espaces doivent être exacts. L'appliquer systématiquement peut cependant coller des mots ou supprimer des séparateurs significatifs : le résultat doit être vérifié comme du texte, pas seulement comme du code indenté.

Où dans Symfony ?

Twig retire déjà le premier saut de ligne après un tag d'instruction. Les modificateurs agissent sur les blancs autour du tag, pas comme un trim général appliqué à toutes les données d'une variable. set peut affecter une expression ou capturer un block de texte.

Comment, étape par étape ?

  1. Écrire le texte exact attendu, espaces compris.
  2. Repérer les blancs provenant du template plutôt que de la donnée.
  3. Choisir le côté à retirer.
  4. Contrôler le résultat ; conserver les espaces qui séparent réellement les mots.

Exemple concret Twig

A {{- 'B' -}} C

Les espaces immédiatement avant et après l'expression disparaissent : la ligne contient ABC. Contre-exemple : employer ces deux marqueurs autour d'un nom dans une phrase et attendre des espaces conservés. Correction : employer A {{ 'B' }} C pour obtenir A B C. Ne pas utiliser le filtre spaceless comme réponse universelle : il est déprécié depuis Twig 3.12 et vise les espaces entre balises HTML, pas tous les besoins de séparation d'un texte.

Passage canonique conservé

Affectation et espaces

{% set total = 0 %} déclare une variable ; {% set body %}…{% endset %} capture un block.

Twig retire d'office le premier saut de ligne qui suit un tag. Ensuite :

  • - ({{-, -}}, {%-, -%}) supprime tout le blanc de ce côté ;
  • ~ le supprime sauf les sauts de ligne.

Le filter spaceless est déprécié depuis 3.12, et lui émet une notice.

Pièges d'examen

Piège à éviter

Expressions, résolution des valeurs et opérateurs Twig
  • {{ }} affiche, {% %} exécute — un tag n'est pas l'affichage direct d'une expression ; certains tags produisent du contenu.
  • L'ordre de résolution commence par l'array, pas par la property.
  • Une constante de class est lue avant le getter si son nom est identique, casse comprise : const STATUS ne masque pas getStatus().
  • and / or / not, jamais && / || / !.
  • ~ concatène ; + additionne.
  • Sans strict_variables, une variable inconnue vaut null silencieusement.
  • attribute() (3.15) et spaceless (3.12) sont dépréciés en 3.22.

Fiche express

À mémoriser

Si tu dois retenir seulement 8 choses :

  • {{ }} affiche, {% %} exécute, {# #} commente.
  • foo.bar : array, property, constante à la casse exacte, methods sans casse, __call.
  • Rien trouvé : null, ou RuntimeError avec strict_variables.
  • ~ concatène ; + additionne et casse sur des strings.
  • // arrondit vers le bas ; ** s'associe à droite.
  • ?: teste la vérité, ?? l'existence.
  • has every sur vide : vrai ; has some : faux.
  • attribute() dépréciée sans notice ; spaceless dépréciée avec.

Moyen mnémotechnique : « array d'abord, constante exacte, method sans casse ».

{{ }} affiche, {% %} exécute ; foo.bar = [key] > prop > CONST exacte > méthode/get/is/has (sans casse) > __call > null|erreur ;
~ concatène, // plancher, ** à droite, ?: vérité, ?? existence, and/or/not ; - et ~ pour les blancs
