Objectif

Reconnaître les types fournis par Symfony, choisir le bon, et savoir de qui chacun hérite — c'est la lignée, pas la famille, qui décide du rendu.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Une famille documentaire n'est pas une lignée.
  2. Le parent détermine réellement options, extensions et blocks.

Symfony fournit une quarantaine de types, rangés par familles dans la documentation. Mais c'est la lignée — getParent() — qui décide du rendu et des extensions : les types numériques, rangés sous « texte », n'héritent pas de TextType, et les boutons ne descendent pas de FormType.

Le schéma

À retenir en priorité
  1. EmailType descend de TextType.
  2. IntegerType est un autre enfant de FormType.

Le catalogue

○ À comprendre

C'est quoi ?

Un type natif fournit un contrat de données, des options et un rendu adaptés à une famille de saisies. Les familles documentaires aident à chercher un type ; elles ne représentent pas toutes une chaîne d'héritage identique ni seulement le nom d'une balise HTML.

À quoi ça sert ?

Un entier doit être converti en nombre, un choix doit rester parmi des valeurs proposées, une date doit suivre ses options de représentation. Choisir seulement selon l'apparence d'un input peut donc donner un modèle de donnée incorrect.

Où dans Symfony ?

Les familles comprennent texte et nombres, choix, dates/heures, fichiers et cases, UID, groupes, champs cachés et boutons. FormType sert à composer des enfants ; CollectionType représente une liste et RepeatedType une saisie répétée à comparer. Les types UID demandent le component Uid. Un widget caché n'est pas une donnée de confiance et un EmailType ne remplace pas à lui seul toutes les contraintes serveur voulues.

Comment, étape par étape ?

  1. Définir le type modèle attendu.
  2. Choisir une famille puis un type selon la conversion et la cardinalité.
  3. Fixer les options plutôt que déduire le comportement du HTML seul.
  4. Vérifier les dépendances et rester dans les types du périmètre : aucun besoin d'introduire EntityType ou un champ UX pour une liste native fixe.

Exemple concret PHP

Dans buildForm, avec builder fourni :

$builder
    ->add('title', \Symfony\Component\Form\Extension\Core\Type\TextType::class)
    ->add('quantity', \Symfony\Component\Form\Extension\Core\Type\IntegerType::class)
    ->add('state', \Symfony\Component\Form\Extension\Core\Type\ChoiceType::class, [
        'choices' => ['Brouillon' => 'draft', 'Publié' => 'published'],
    ]);

title est du texte, quantity utilise une conversion numérique et state fournit draft ou published. Contre-exemple : remplacer quantity par TextType et supposer que sa ressemblance visuelle suffit à produire un entier. Correction : choisir le contrat de données voulu puis ses contraintes métier, par exemple une limite de quantité. Les catégories du catalogue guident ce choix sans imposer des dépendances de base de données hors programme.

Ce catalogue conserve les types du component Form admis au syllabus. Les types dépendant de couches de persistance, de bibliothèques d'interface ou de components d'identifiers non listés ne sont pas nécessaires pour ces objectifs.

La famille des choix

○ À comprendre

À retenir en priorité
  1. expanded choisit le rendu développé.
  2. multiple autorise plusieurs valeurs.

C'est quoi ?

ChoiceType décrit un choix parmi des valeurs autorisées. Le libellé est ce que l'utilisateur lit ; la valeur est la donnée que l'application conserve. Ces deux éléments peuvent être différents. Les types spécialisés de choix réutilisent ce comportement, mais une famille fonctionnelle de la documentation n'est pas toujours une lignée d'héritage PHP.

À quoi ça sert ?

Deux options séparent la cardinalité, c'est-à-dire le nombre de valeurs possibles, de la présentation :

  • multiple: false, expanded: false : liste déroulante, un choix.
  • multiple: false, expanded: true : boutons radio.
  • multiple: true, expanded: false : liste à sélection multiple.
  • multiple: true, expanded: true : cases à cocher.

Changer la présentation ne doit pas changer la signification métier des valeurs.

Où dans Symfony ?

Dans choices, les clés sont les libellés et les valeurs les données. EnumType représente les cas d'une enum avec l'option class. D'autres types ciblent du texte, des dates, des fichiers ou des collections. Les types liés à une base de données et les extensions UX ne sont pas introduits ici : ils sont hors du périmètre fixé pour ce cours.

Comment, étape par étape ?

  1. Définir les valeurs réellement autorisées, pas seulement les textes à afficher.
  2. Choisir si la donnée finale est unique ou multiple.
  3. Choisir ensuite entre présentation compacte et développée.
  4. Au retour, laisser Form vérifier que la valeur appartient au choix ; une modification manuelle du HTML ne doit pas créer une nouvelle valeur autorisée.

Exemple concret PHP

Dans buildForm(), avec $builder reçu de l'infrastructure Form :

$builder->add('country', \Symfony\Component\Form\Extension\Core\Type\ChoiceType::class, [
    'choices' => ['France' => 'fr', 'Belgique' => 'be'],
    'multiple' => false,
    'expanded' => true,
]);

Le rendu contient des radios ; le modèle reçoit fr ou be, pas le texte France ou Belgique. Contre-exemple : inverser clés et valeurs puis supposer que le modèle contiendra encore les codes. Correction : relire le tableau comme « libellé => donnée ». Pour un champ multiple, ne pas traiter le résultat comme une chaîne unique : adapter le modèle au tableau de choix attendu.

  • Dans choices, la key est le libellé, la valeur est la donnée : avec ['France' => 'fr'], soumettre France donne « The selected choice is invalid. ».
  • EnumType exige l'option class : sans elle, MissingOptionsException.

Au menu, multiple demande combien de plats on peut choisir ; expanded décide si les choix sont tous visibles. Plusieurs choix visibles donnent des checkboxes ; un seul choix replié donne un select.

Repère — RepeatedType : No. Matching inputs produce one value; mismatches make it invalid. Deux fields vérifient la même donnée. L'erreur de correspondance ne produit pas deux valeurs valides.

`RepeatedType`

À retenir en priorité
  1. Deux fields vérifient la même donnée.
  2. L'erreur de correspondance ne produit pas deux valeurs valides.

Deux enfants, first et second, du type donné par type. Valeurs égales : une seule donnée. Sinon : « The values do not match. », et la donnée vaut null. Dans une application complète, RepeatedTypeValidatorExtension redirige cette erreur vers first par error_mapping.

Les boutons

ButtonType n'a pas de parent : une extension de FormType ne touche pas un SubmitType. Un bouton est un SubmitButton : absent de getData(), et isClicked() dit s'il a servi ; getClickedButton() le rend.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Famille ≠ lignée : les types numériques héritent de FormType.
  • Toute la famille des choix hérite de ChoiceType.
  • multiple / expanded : select, radio, select multiple, checkboxes.
  • choices : key = libellé, valeur = donnée.
  • RepeatedType : deux fields, une donnée ; erreur sur first.
  • Boutons : ButtonType, sans parent ; hors de getData().

Moyen mnémotechnique : « La famille range, le parent décide ».
