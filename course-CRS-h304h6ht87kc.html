Objectif

Envoyer un message, choisir son transport, et savoir ce que l'envoi rend — ou ne rend pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Le retour du Mailer ne prouve ni envoi ni acceptation ; une acceptation effective n'est pas la remise finale.
  2. La suite échappe au contrat immédiat.

Mailer envoie un message par un transport, décrit par un DSN : smtp, sendmail ou native. MailerInterface::send() ne rend rien, parce qu'il peut différer l'envoi par Messenger ; TransportInterface::send() envoie de façon synchrone et rend un SentMessage si l'envoi réussit, ou null si un listener rejette le message. Un succès ne prouve pas la remise en boîte.

Le schéma

À retenir en priorité
  1. La construction est séparée de l'envoi.
  2. Un message MIME peut exister sans transport.

Bleu : appels ; ambre : décisions ; vert : résultats. Le pointillé traverse une file et un worker, pas un appel direct dans la requête web. Vue des transports standards avec dispatcher ; une exception de listener peut interrompre le chemin. Même SentMessage ne prouve pas une remise en boîte.

L'exemple : envoyer depuis un controller

Exemple concret

À retenir en priorité
  1. L'envoi peut être différé.
  2. Ne pas attendre un résultat de livraison.
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Mailer\MailerInterface;
use Symfony\Component\Mime\Email;

final class EmailController
{
    public function sendEmail(MailerInterface $mailer): Response
    {
        $email = new Email()->from('hello@example.com')->to('you@example.com')
            ->subject('Time for Symfony Mailer!')->text('Sending emails is fun again!');
        $mailer->send($email);   // ne rend rien
        return new Response('Demande d’envoi prise en charge.', 202);
    }
}

Le 202 évite de promettre une livraison : avec routage async, le transport mail n'a peut-être pas encore été appelé. Si le handler du worker échoue plus tard, l'exception n'arrive pas dans ce controller ; observer les échecs et retries Messenger. Le DSN suivant est un gabarit, pas un secret à versionner.

MAILER_DSN=smtp://user:pass@smtp.example.com:port

Le transport

À retenir en priorité
  1. Le DSN choisit le mécanisme.
  2. Les intégrations de providers externes restent hors de ce périmètre.
DSN Comportement
smtp un serveur SMTP
sendmail le binaire sendmail local
native le binaire et les options de php.ini — déconseillé

Avec native://default et sendmail -t dans php.ini : pas de remontée d'erreur, Bcc non retirés. Un caractère réservé d'URI dans le DSN doit être encodé. Les bridges vers des services tiers sont hors périmètre.

Envoyer

À retenir en priorité
  1. L'installation permet l'intégration.
  2. Le routage détermine le report de l'envoi.
  3. Un bus intégré ne suffit pas : le routage asynchrone de SendEmailMessage diffère l'appel au transport.

Une simple installation de Messenger ne suffit pas à différer l'envoi. Sans bus, Mailer appelle directement son transport. Avec un bus, send() distribue un SendEmailMessage : il est différé seulement s'il est routé vers un transport asynchrone. Sans ce routage, la pile standard et le handler Mailer traitent le message pendant le dispatch. Exécuté : sans routage, l'email part pendant send() ; routé vers un transport in-memory://, il y reste en attente.

Ce que rend l'envoi

À comprendre

À retenir en priorité
  1. Le transport est synchrone : SentMessage après envoi, ou null après rejet avant envoi sans exception imposée.
  2. Le mailer peut déléguer au bus.

C'est quoi ?

Mailer coordonne l'envoi d'un message construit par Mime. Un transport est le mécanisme de remise, par exemple SMTP ou sendmail. Un DSN décrit sa connexion ; il doit être fourni par une configuration protégée, pas inscrit avec des credentials dans le code.

À quoi ça sert ?

Le service métier peut demander une notification sans connaître tous les détails du transport. Il doit toutefois distinguer demande d'envoi, acceptation par le transport et livraison finale au destinataire : aucune de ces étapes ne prouve automatiquement la suivante.

Où dans Symfony ?

MailerInterface::send() retourne void. TransportInterface::send() est synchrone et peut retourner un SentMessage, ou null si le message est rejeté dans le mécanisme prévu. Le transport direct ne devient pas asynchrone parce que Messenger est installé.

Comment, étape par étape ?

  1. Construire le message Mime puis le transmettre au mailer.
  2. En usage synchrone, une erreur de transport peut remonter par TransportExceptionInterface ; ne pas la convertir en succès silencieux.
  3. Pour différer réellement, intégrer le bus et router SendEmailMessage vers un transport Messenger traité par un worker. Une simple installation de Messenger ne suffit pas.
  4. En asynchrone, l'échec réel peut survenir plus tard dans le worker : la réussite de la Request ne démontre pas la livraison.
  5. Avec plusieurs transports nommés, le premier est le défaut ; X-Transport peut sélectionner un autre nom et est retiré du courriel final.

Exemple concret YAML

Fragment complet des deux sections concernées, pour des DSN fournis par l'exploitation et un worker consommant async :

framework:
    mailer:
        dsn: '%env(MAILER_DSN)%'
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
        routing:
            'Symfony\Component\Mailer\Messenger\SendEmailMessage': async

La route porte sur la classe du message Messenger, pas sur Email. Elle déplace le moment de l'envoi ; elle n'élimine ni les reprises ni les possibles doublons. Ces commandes et DSN ne sont pas exécutés ou lus ici.

Contre-exemple : conserver le résultat de $mailer->send() comme preuve de livraison ou capturer seulement les erreurs dans le controller d'une architecture asynchrone. Correction : respecter le retour void et observer aussi les échecs du worker et du transport. Les informations de debug d'un SentMessage ne doivent pas être publiées sans filtrage. native://default est déconseillé : sa dépendance à la configuration PHP/sendmail peut empêcher un diagnostic fiable et affecter la gestion des destinataires cachés. Préférer un transport explicitement maîtrisé.

Quand l'envoi échoue

À retenir en priorité
  1. L'échec de remise au transport est explicite.
  2. Il ne faut pas le confondre avec un échec ultérieur de livraison.

Distinguer retour du Mailer, mise en file Messenger et acceptation effective par le transport mail. Un retour normal de Mailer::send() peut précéder tout appel au transport, ou suivre un rejet par listener sans exception. Même une acceptation effective par le transport ne garantit pas la remise finale. Une erreur de remise au transport lève une TransportExceptionInterface.

Plusieurs transports

À retenir en priorité
  1. Le header sert au routage interne.
  2. Il ne doit pas parvenir au destinataire.

transports remplace dsn ; le premier déclaré sert par défaut. Le header X-Transport en désigne un autre, et Mailer le retire du message envoyé comme de l'object Email d'origine.

framework.mailer.envelope fixe sender et recipients pour tous les envois, framework.mailer.headers des headers communs, From compris. Trois events : MessageEvent avant l'envoi (modifier, ou reject(), qui arrête aussi la propagation), SentMessageEvent après un succès, FailedMessageEvent après un échec, avec getError().

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un rejet volontaire est distinct d'une panne.
  2. Le transport peut alors retourner null.
  • Voir l’explication : Installer Messenger ne suffit pas à rendre l'envoi asynchrone.

    Installer Messenger ne suffit pas à rendre l'envoi asynchrone. Mailer doit utiliser le bus et SendEmailMessage doit être routé vers un transport asynchrone ; sans ce routage, la pile standard avec le handler Mailer appelle le transport pendant send().

  • Voir l’explication : MailerInterface::send() ne rend rien

    MailerInterface::send() ne rend rien ; TransportInterface::send() rend un SentMessage après succès, ou null après rejet par listener ; cet appel au transport est synchrone.

  • Voir l’explication : Le premier transport déclaré est celui par défaut

    Le premier transport déclaré est celui par défaut ; X-Transport choisit.

  • Voir l’explication : native://default est déconseillé

    native://default est déconseillé : ni erreurs ni retrait des Bcc.

  • Voir l’explication : Un message rejeté par reject() ne lève rien

    Un message rejeté par reject() ne lève rien : le transport rend null.

Fiche express

À mémoriser

À retenir en priorité
  1. L'ordre fixe le défaut.
  2. Un choix explicite peut le surcharger.

Si tu dois retenir seulement 6 choses :

  • Transports intégrés : smtp, sendmail, native (déconseillé).
  • MailerInterface::send() ne rend rien ; TransportInterface::send() rend un SentMessage si accepté, ou null si rejeté ; appel synchrone.
  • Asynchrone avec bus, handler standard et SendEmailMessage routé vers un transport asynchrone.
  • Retour normal du Mailer ≠ acceptation par le transport ≠ remise finale : une mise en file ou un rejet sans exception peut aussi rendre la main.
  • Premier transport par défaut ; X-Transport choisit, puis disparaît.
  • MessageEvent (et reject()), SentMessageEvent, FailedMessageEvent.

Moyen mnémotechnique : « Accepté n'est pas remis ».

Correction de consultation — non notée.

  • Distractor: Yes; send() waits until the recipient opens the message.
