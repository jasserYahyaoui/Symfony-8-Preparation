Objectif

Le serveur transmet GET /blog/42 au front controller. Pourtant, le petit public/index.php d'une application Runtime ne contient ni appel au controller ni envoi de Response. Pour retrouver qui lance réellement le traitement, suivons le callable retourné par ce fichier jusqu'au runner. La command app:blog:import utilise une autre entrée, mais peut partager ce même mécanisme d'amorçage.

L'essentiel

À comprendre

À retenir en priorité
  1. Le script décrit la création.
  2. Le runtime exécute l'application retournée.

Le component Runtime sépare la description de l'application de son exécution. Le fichier d'entrée retourne un callable, ici une closure qui construit App\Kernel. L'amorçage demande au runtime un resolver pour préparer les arguments de cette closure, l'appelle, puis demande un runner, l'object chargé d'exécuter le résultat.

Pour le chemin HTTP standard, le runner reçoit le Kernel et une Request, appelle handle(), puis envoie la Response et termine si le contrat le permet. Pour une Application Console, un autre runner gère les entrées/sorties de command. Ce choix ne transforme pas la console en cycle HTTP.

Deux précisions structurent la suite : l'amorçage standard réinclut le script d'entrée, et la résolution de ses arguments array dépend du type et du nom. Ce resolver de Runtime n'est pas l'ArgumentResolver des actions HTTP.

Le schéma

À retenir en priorité
  1. L'amorçage réinclut le script.
  2. Un effet de bord pourrait être dupliqué.

Avant de chercher blog_show, il faut obtenir l'application capable de traiter la Request. Le dessin décrit l'amorçage généré par Runtime v8.0.0, sans variante personnalisée ni autoload déjà chargé. Les deux passages concernent le fichier d'entrée, pas deux appels de BlogController::show.

Bleu : amorçage/appels ; vert : valeurs rendues ou fin. Le second passage du script retourne la closure ; elle n'est appelée qu'après la résolution des arguments. Le runner HTTP prend ensuite en charge requête et réponse : le front controller ne doit pas refaire ces opérations.

L'exemple : le front controller

Exemple concret

À retenir en priorité
  1. Le callable crée l'object.
  2. Le runner gère son exécution.

Dans le projet pédagogique Symfony 8.0 sous PHP 8.4, App\Kernel existe et le plugin Composer a généré vendor/autoload_runtime.php. Ce fichier d'entrée n'est donc pas un script autonome à exécuter sans projet :

<?php
// public/index.php
use App\Kernel;

require_once dirname(__DIR__).'/vendor/autoload_runtime.php';

return function (array $context): Kernel {
    return new Kernel($context['APP_ENV'], (bool) $context['APP_DEBUG']);
};

La closure reçoit par exemple APP_ENV=prod et APP_DEBUG=0 dans son contexte et construit le Kernel correspondant. Elle ne le boote pas explicitement et ne traite pas encore l'article 42. Dans cette variante standard, c'est ensuite SymfonyRuntime::getRunner() qui crée la Request depuis les superglobales. Une closure demandant elle-même une Request représente une autre variante : ne pas superposer les deux chronologies.

Le file d'entrée ne lance rien

À retenir en priorité
  1. Le bootstrap est généré par le plugin.
  2. Désactiver les plugins peut empêcher sa création.

🌍 In Real Life

La situation : l'ouverture du restaurant commence par une fiche indiquant comment préparer l'établissement, pas par la préparation du plat 42.

L’équivalent dans Symfony : fiche de création → callable retourné par le script ; établissement obtenu → objet App\Kernel ; procédure d'exploitation → runner choisi.

Retour à la réalité technique : le require_once amorce bien Runtime. Le bootstrap résout puis appelle le callable ; le runner lance l'application. Construire Kernel n'est ni le booter ni traiter la requête.

🧠 Comment le mémoriser : « Décrire, construire, lancer. » Image mentale : fiche, établissement, bouton de mise en service. Question-réflexe : quel retour contient le callable et lequel contient l'application ?

⚠️ À ne pas confondre : Kernel prépare l'application ; HttpKernel coordonne le traitement HTTP.

Dans l'exemple, le script ne construit ni n'envoie la Response : il rend la function qui construit le Kernel. Le titre signifie « ne lance pas lui-même le traitement métier » ; son require_once déclenche bien l'amorçage. vendor/autoload_runtime.php est écrit par le plugin Composer du component. --no-plugins empêche cette génération ; ce n'est pas une instruction qui efface un fichier éventuellement déjà présent.

Deux frontières de retour sont à distinguer : le script fournit le callable, puis le callable fournit l'application. Avec SymfonyRuntime, ces variations ne donnent pas le même résultat :

Le script rend Résultat
42 au lieu d'une function TypeError : callable object expected
une function qui rend une string TypeError : object expected
une function qui rend une Response la Response est envoyée

C'est la nature de l'object rendu qui choisit HTTP ou console : un même mécanisme peut servir public/index.php et bin/console. Retourner une Response directement depuis la closure permet son envoi sans parcourir le Kernel de l'exemple. Retourner une Application Console permet l'import sans Request HTTP obligatoire. Un object arbitraire, lui, n'est pas automatiquement exécutable : le runtime doit connaître un runner adapté.

Les cinq étapes

À retenir en priorité
  1. Rendre une application remplace l'amorçage manuel.
  2. La responsabilité est déplacée vers le runtime.

🌍 In Real Life

La situation : le restaurant reçoit la commande 42 ; préparer le résultat, le remettre et effectuer la clôture locale sont des actions distinctes.

L’équivalent dans Symfony : résultat préparé → retour de handle() ; remise → envoi de la Response ; clôture locale → appel séparé à terminate() si disponible.

Retour à la réalité technique : dans la variante HTTP Runtime standard, le runner gère cette séquence. La terminaison n'est pas un worker durable et ne garantit pas la réception de tous les octets par le client sur chaque serveur.

🧠 Comment le mémoriser : « Prêt n'est pas envoyé. » Image mentale : une assiette au passe, puis en salle. Question-réflexe : qui appelle l'envoi et la terminaison ?

⚠️ À ne pas confondre : ce runner standard et une boucle personnalisée de worker.

Le fichier d'entrée a décrit la création du Kernel. Voici l'ordre effectif dans autoload_runtime.template v8.0.0, une fois son autoload chargé :

  1. Réinclure le script désigné par SCRIPT_FILENAME pour obtenir son callable.
  2. Instancier le runtime choisi, SymfonyRuntime par défaut, avec ses options.
  3. Appeler getResolver($app)->resolve() pour obtenir callable et arguments.
  4. Appeler le callable avec ces arguments : ici, construire App\Kernel.
  5. Obtenir le runner par getRunner($app), appeler run(), puis utiliser son code de sortie dans exit().

La présentation documentaire historique plaçait l'instanciation avant la réinclusion ; le template fait l'inverse. Conserver cette distinction plutôt que transformer le résumé documentaire en trace exacte du code.

Ligne du script Exécutions
au-dessus du require_once deux
au-dessous une seule

La première exécution s'achève par l'exit d'autoload_runtime.php ; la seconde trouve ce fichier déjà chargé et continue jusqu'au retour de la closure. Un compteur de visites placé au-dessus du require_once pourrait donc compter deux fois une seule visite : garder le bootstrap sans effet métier. Charger vendor/autoload.php avant fait sortir prématurément l'amorçage : le require_once de l'autoload déjà chargé vaut true, condition du retour anticipé. Dans ce petit script sans autre action, aucun runner n'est appelé, avec une fin silencieuse et un exit code 0.

Revenons à la cinquième étape réussie. HttpKernelRunner::run() appelle Kernel::handle() ; le Kernel prépare l'application puis délègue au service http_kernel. Charger un service container compilé utilisable n'en refait pas systématiquement la compilation. Après le retour de la Response, le runner v8.0.0 appelle send(false) avec Symfony 8, gère la fin de sortie du serveur, puis appelle terminate() si le Kernel implémente TerminableInterface. Une exception peut interrompre ce parcours : ce n'est pas une garantie d'envoi ou de terminaison sur toute panne.

Sans Runtime, une entrée manuelle doit assumer ces opérations. C'est une alternative, pas du code à ajouter en plus du runner dans notre closure.

Les arguments sont résolus par type *et* par nom

À retenir en priorité
  1. Le nom participe au contrat.
  2. Renommer librement l'argument peut casser la résolution.

🌍 In Real Life

La situation : à l'ouverture du restaurant, trois classeurs de même format portent des étiquettes différentes.

L’équivalent dans Symfony : format du classeur → type array ; étiquette → nom context, argv ou request ; contenu fourni → données d'amorçage correspondantes.

Retour à la réalité technique : le resolver Runtime utilise les contrats de type et de nom. Renommer arbitrairement $context en $ctx peut empêcher la résolution. L'identifiant de route 42 n'est pas encore disponible dans ce mécanisme.

🧠 Comment le mémoriser : « Même format, autre étiquette. » Image mentale : trois classeurs identiques mais nommés. Question-réflexe : le nom fait-il partie du contrat ici ?

⚠️ À ne pas confondre : resolver Runtime, autowiring du constructeur et ArgumentResolver d'une action HTTP.

Le Kernel n'existe pas encore lorsque Runtime prépare array $context. Cette résolution fournit les données d'amorçage, pas l'identifier de route id=42, qui ne sera produit que plus tard par le routage HTTP.

Argument Reçoit
array $context part de $_SERVER ; ajoute les clés manquantes de $_ENV si celui-ci est non vide et si ni PATH ni Path n'est défini dans $_SERVER
array $argv les arguments de la ligne de command
array $request query, body, files, session

Un argument obligatoire array $ctx, sans résolution personnalisée, lève une InvalidArgumentException qui énumère ces trois noms. SymfonyRuntime accepte en plus une Request créée depuis les superglobales et les objects d'entrée et de sortie de console. Renommer $context en $argv ne constitue donc pas une simple amélioration de style : la closure recevrait les arguments de ligne de command, pas le contexte attendu.

Choisir le runtime

À retenir en priorité
  1. La classe d'amorçage est configurable.
  2. Les options du runtime sont un réglage distinct.

Le point d'entrée de l'article et celui de l'import ont maintenant un contrat commun. Pour changer la façon de les lancer, choisir la class de runtime ; pour changer son environnement, régler ses options. Ce sont deux décisions distinctes, pas deux modifications de BlogController.

SymfonyRuntime est le défaut ; GenericRuntime s'appuie sur les superglobales. Le chargement Dotenv suppose le composant installé, un project_dir et l'absence de disable_dotenv. Un chemin attendu absent peut alors lever PathException. Désactiver Dotenv ne choisit pas la production : sans options ni variables contraires, les valeurs de repli restent dev et debug activé. Fournir explicitement l'environnement et le mode debug en production.

Pour choisir Pour les options
APP_RUNTIME APP_RUNTIME_OPTIONS, en JSON
extra.runtime.class dans composer.json extra.runtime

Pour le déploiement du blog, vérifier séparément le runtime sélectionné, l'environnement et le mode debug effectifs. L'absence de fichier Dotenv ne prouve aucun de ces trois choix.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Respecter l'entry point généré.
  2. L'ordre des includes fait partie du mécanisme.
  • Voir l’explication : Le file d'entrée retourne une function ; il ne traite pas lui-même l'article.

    Le file d'entrée retourne une function ; il ne traite pas lui-même l'article. Le bootstrap appelle la closure et le runner exécute le Kernel.

  • Voir l’explication : Le script d'entrée est réexécuté

    Le script d'entrée est réexécuté par le runtime : ce qui précède le require_once tourne deux fois sur le chemin standard décrit ; cela ne signifie pas deux lectures métier de l'article.

  • Voir l’explication : autoload.php chargé avant autoload_runtime.php

    autoload.php chargé avant autoload_runtime.php peut court-circuiter silencieusement le runner. Le script peut continuer, mais le Kernel retourné n'est pas traité par ce bootstrap.

  • Voir l’explication : Le type et le nom de l'argument sont significatifs

    Le type et le nom de l'argument sont significatifs pour les arrays prédéfinis : $context n'est ni $argv ni $request.

  • Voir l’explication : --no-plugins empêche la création de autoload_runtime.php

    --no-plugins empêche la création de autoload_runtime.php par le plugin. Sur une installation fraîche, le front controller ne trouvera donc pas ce fichier requis ; sur une installation existante, contrôler sa provenance.

Fiche express

À mémoriser

À retenir en priorité
  1. Un kernel HTTP et une application console ont des runners adaptés.
  2. Le callable reste la frontière commune.

Si tu dois retenir seulement 6 choses :

  • index.php rend une closure ; le bootstrap résout ses arguments, l'appelle, puis lance le runner adapté au résultat.
  • Le script tourne deux fois au-dessus du require_once : aucun effet de bord.
  • autoload.php chargé avant : le bootstrap peut revenir sans lancer le runner.
  • $context, $argv, $request : type et nom.
  • --no-plugins : aucune génération d'autoload_runtime.php par le plugin.
  • APP_RUNTIME ou extra.runtime.class ; options en APP_RUNTIME_OPTIONS.

Moyen mnémotechnique : « Rendre, pas lancer ».

L'application est désormais lancée, pas encore expliquée de bout en bout. Poursuivre avec le traitement de la Request pour suivre l'article jusqu'à sa Response, ou avec Console pour l'entrée app:blog:import.
