Objectif

Comprendre ce qui s'exécute entre le chargement de l'autoload et la remise d'une Request au kernel, et pourquoi le file d'entrée retourne au lieu d'exécuter.

L'essentiel

À comprendre

À retenir en priorité
  1. Le script décrit la création.
  2. Le runtime exécute l'application retournée.

Le component Runtime sort l'amorçage du file d'entrée : public/index.php retourne une function, et c'est le runtime qui l'appelle, résout ses arguments et exécute ce qu'elle rend — un kernel HTTP ou une application de console. Deux conséquences à l'examen : le script d'entrée s'exécute deux fois, et les arguments de la function sont reconnus par leur type et leur nom.

Le schéma

À retenir en priorité
  1. L'amorçage réinclut le script.
  2. Un effet de bord pourrait être dupliqué.

L'exemple : le front controller

Exemple concret

À retenir en priorité
  1. Le callable crée l'object.
  2. Le runner gère son exécution.
// public/index.php
require_once dirname(__DIR__).'/vendor/autoload_runtime.php';

return function (array $context): Kernel {
    return new Kernel($context['APP_ENV'], (bool) $context['APP_DEBUG']);
};

Le file d'entrée ne lance rien

À retenir en priorité
  1. Le bootstrap est généré par le plugin.
  2. Désactiver les plugins peut empêcher sa création.

Le script ne construit ni n'envoie la Response : il rend une function. vendor/autoload_runtime.php est écrit par le plugin Composer du component ; avec --no-plugins, il n'existe pas.

Le script rend Résultat
42 au lieu d'une function TypeError : callable object expected
une function qui rend une string TypeError : object expected
une function qui rend une Response la Response est envoyée

C'est la nature de l'object rendu qui choisit HTTP ou console : un même mécanisme sert public/index.php et bin/console.

Les cinq étapes

À comprendre

À retenir en priorité
  1. Rendre une application remplace l'amorçage manuel.
  2. La responsabilité est déplacée vers le runtime.

C'est quoi ?

Runtime sépare le bootstrap, préparation de l'exécution, de l'application à exécuter. Le script d'entrée retourne un callable ; le runtime résout ses arguments, obtient l'application puis choisit un runner qui la fait fonctionner.

À quoi ça sert ?

Le script décrit l'application sans recopier la gestion complète de Request, Response ou Console. Changer le mode d'exécution relève ainsi d'un contrat explicite plutôt que de transformations dispersées dans le controller d'entrée.

Où dans Symfony ?

Le plugin Composer de symfony/runtime génère vendor/autoload_runtime.php. Ce fichier n'est pas une classe applicative à écrire manuellement. APP_RUNTIME ou extra.runtime.class permet de sélectionner le runtime ; un plugin désactivé peut empêcher la génération du fichier requis.

Comment, étape par étape ?

  1. Le script d'entrée charge autoload_runtime.php.
  2. Dans le template de Symfony v8.0.0, le script d'entrée est réinclus pour récupérer l'objet callable qu'il retourne.
  3. Le runtime est alors instancié et son resolver prépare le callable et ses arguments. Cette séquence précise vient du template ; ne pas inverser réinclusion et instanciation en décrivant son code ligne à ligne.
  4. Le callable est appelé pour obtenir l'objet application.
  5. Le runner adapté exécute cet objet et fournit un code de sortie.

Exemple concret PHP

Dans public/index.php d'une application Symfony disposant de son Kernel et de l'autoload généré :

<?php
use App\Kernel;

require_once dirname(__DIR__).'/vendor/autoload_runtime.php';

return static function (array $context): Kernel {
    return new Kernel($context['APP_ENV'], (bool) $context['APP_DEBUG']);
};

Ce fichier est un point d'entrée de framework, pas un script autonome exécutable sans projet. Aucun bootstrap ni fichier d'environment n'est lancé ici. La closure construit l'application ; elle ne doit pas appeler elle-même son traitement HTTP à la place du runner.

Contre-exemple : produire une sortie ou effectuer une écriture avant require_once, en supposant que le script ne sera parcouru qu'une fois. Correction : garder le point d'entrée sans effet externe avant la récupération du callable ; la réinclusion peut répéter ces effets.

La résolution des arguments dépend de leur type et de leur nom : array $context et array $argv ne désignent pas la même donnée. Renommer arbitrairement un paramètre peut casser la résolution. Un objet retourné non pris en charge par le runtime n'est pas rendu exécutable par son seul caractère objet ; resolver et runner remplissent deux rôles distincts.

Les cinq étapes

La documentation 8.0 les énumère : runtime instancié, script d'entrée inclus à nouveau, arguments de la function résolus, function appelée, application exécutée. Le code 8.0 inverse les deux premières ; un runtime qui journalise son constructor donne script returns closure, puis runtime constructed. Le code l'emporte.

Ligne du script Exécutions
au-dessus du require_once deux
au-dessous une seule

La première exécution s'achève par l'exit d'autoload_runtime.php ; la seconde trouve le file déjà chargé et continue. D'où la règle : aucun effet de bord dans ce script. Charger vendor/autoload.php avant désactive tout : le script va au bout, l'application ne tourne pas, exit code 0, aucun message.

Les arguments sont résolus par type *et* par nom

À retenir en priorité
  1. Le nom participe au contrat.
  2. Renommer librement l'argument peut casser la résolution.
Argument Reçoit
array $context $_SERVER + $_ENV selon la documentation ; le code n'ajoute $_ENV que sans PATH dans $_SERVER
array $argv les arguments de la ligne de command
array $request query, body, files, session

array $ctx lève une InvalidArgumentException qui énumère ces trois noms. SymfonyRuntime accepte en plus une Request créée depuis les superglobales et les objects d'entrée et de sortie de console.

Choisir le runtime

À retenir en priorité
  1. La classe d'amorçage est configurable.
  2. Les options du runtime sont un réglage distinct.

SymfonyRuntime est le défaut ; GenericRuntime s'appuie sur les superglobales. SymfonyRuntime charge les files .env : sans .env, il lève une PathException ; avec disable_dotenv, il démarre en dev, debug à 1.

Pour choisir Pour les options
APP_RUNTIME APP_RUNTIME_OPTIONS, en JSON
extra.runtime.class dans composer.json extra.runtime

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Respecter l'entry point généré.
  2. L'ordre des includes fait partie du mécanisme.
  • Rôle du fichier d’entrée Runtime

    Le file d'entrée retourne une function ; il n'exécute pas l'application.

  • Voir l’explication : Le script d'entrée est réexécuté

    Le script d'entrée est réexécuté par le runtime : ce qui précède le require_once tourne deux fois.

  • Voir l’explication : autoload.php chargé avant autoload_runtime.php

    autoload.php chargé avant autoload_runtime.php : rien ne s'exécute, sans erreur.

  • Résolution des arguments par Runtime

    Le type et le nom de l'argument sont significatifs.

  • Plugins Composer et génération de autoload_runtime.php

    --no-plugins empêche la création de autoload_runtime.php.

Fiche express

À mémoriser

À retenir en priorité
  1. Un kernel HTTP et une application console ont des runners adaptés.
  2. Le callable reste la frontière commune.

Si tu dois retenir seulement 6 choses :

  • index.php rend une closure ; le runtime l'appelle et exécute le résultat.
  • Le script tourne deux fois au-dessus du require_once : aucun effet de bord.
  • autoload.php chargé avant : rien ne tourne, sans erreur.
  • $context, $argv, $request : type et nom.
  • --no-plugins : pas d'autoload_runtime.php.
  • APP_RUNTIME ou extra.runtime.class ; options en APP_RUNTIME_OPTIONS.

Moyen mnémotechnique : « Rendre, pas lancer ».
