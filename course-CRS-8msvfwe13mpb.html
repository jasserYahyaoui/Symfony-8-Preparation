Objectif

Construire un form, le lier à un object, et savoir quand un field ne doit pas l'être.

L'essentiel

À comprendre

À retenir en priorité
  1. Le nom relie le field aux données.
  2. Le type et ses options définissent le comportement.

Un form se décrit dans une class de type dès qu'il sert plus d'une fois. Chaque add() relie un field à une property par son nom ; data_class dit quelle class le form manipule. Un field sans property est déclaré mapped: false, ou relié ailleurs par property_path.

Le schéma

À retenir en priorité
  1. property_path redirige un field.
  2. inherit_data partage les données du parent.

Bleu = construction/mapping, vert = données. La flèche de mapping résume lecture initiale et écriture à la soumission ; elle n'implique pas une validation réussie. agreeTerms doit avoir sa propre contrainte IsTrue si l'accord est obligatoire côté serveur.

L'exemple : un `TaskType`

Exemple concret

À retenir en priorité
  1. Le FormType se réutilise entre actions.
  2. Un builder local convient à un besoin ponctuel.
class TaskType extends AbstractType
{
    public function buildForm(FormBuilderInterface $builder, array $options): void
    {
        $builder
            ->add('task', TextType::class)
            ->add('dueDate', DateType::class)
            ->add('agreeTerms', CheckboxType::class, ['mapped' => false]);
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['data_class' => Task::class]);
    }
}

Deux endroits pour le construire

À comprendre

C'est quoi ?

Un builder construit une instance de formulaire. Une classe de type réutilisable décrit comment la construire ; elle n'est pas cette instance et ne conserve pas les données d'une soumission particulière. On peut construire localement dans une action ou déléguer cette description à AbstractType.

À quoi ça sert ?

Le builder local convient à un besoin ponctuel. Un type rend les champs et options réutilisables sans recopier leur définition dans plusieurs controllers. Dans les deux cas, add reçoit un nom, un type et des options ; le nom sert normalement au mapping vers la donnée du parent.

Où dans Symfony ?

AbstractController fournit createFormBuilder et createForm. Le type place les appels add dans buildForm et déclare data_class dans configureOptions. Le mapping utilise des propriétés publiques ou des accesseurs accessibles ; un nom identique ne rend pas une propriété privée accessible.

Comment, étape par étape ?

  1. Identifier le modèle et ses propriétés accessibles.
  2. Déclarer explicitement le type de chaque champ et ses options.
  3. Extraire une classe AbstractType si la définition doit être réutilisée.
  4. Créer une instance de Form pour chaque traitement, avec ses données propres.

Exemple concret PHP

Déclarations applicatives, chacune dans son fichier sous App\Form :

<?php
namespace App\Form;
use Symfony\Component\Form\AbstractType;
use Symfony\Component\Form\FormBuilderInterface;
use Symfony\Component\Form\Extension\Core\Type\TextType;
use Symfony\Component\OptionsResolver\OptionsResolver;

final class ProfileInput { public string $name = ''; }
final class ProfileType extends AbstractType
{
    public function buildForm(FormBuilderInterface $builder, array $options): void
    {
        $builder->add('name', TextType::class, ['label' => 'Nom']);
    }
    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['data_class' => ProfileInput::class]);
    }
}

Dans une action d'AbstractController, créer le modèle puis choisir l'une des constructions :

$profile = new \App\Form\ProfileInput();
$form = $this->createForm(\App\Form\ProfileType::class, $profile);

La variante locale est $this->createFormBuilder($profile)->add('name', \Symfony\Component\Form\Extension\Core\Type\TextType::class, ['label' => 'Nom'])->getForm(). Contre-exemple : renommer le champ displayName sans modifier le modèle ni property_path. Correction : garder name ou déclarer le mapping voulu. Le libellé Nom change l'affichage, pas la propriété ciblée.

Passage canonique conservé
Besoin Où
un form jetable, une seule action $this->createFormBuilder($task)->add(…)->getForm()
un form réutilisé (recommandé) une class AbstractType, puis $this->createForm(TaskType::class, $task)

`add()` et ses trois arguments

add(nom, type, options) relie le field aux données par son nom. Si le type est omis, les guessers enregistrés peuvent le déterminer ; à défaut, TextType est utilisé. Ne pas supposer que toute déclaration de type PHP est automatiquement convertie en FormType. Déclarer explicitement le type rend le comportement clair.

`data_class`

À retenir en priorité
  1. Un object initial peut fournir la data_class.
  2. La déclaration explicite documente le modèle attendu.
Création Résultat
un Task passé, sans data_class déclarée getDataClass() vaut Task : devinée
data_class déclarée, sans object données initiales null ; à la soumission, le défaut empty_data peut créer new Task()
ni data_class ni object après soumission d'un form composé, un array tel que ['task' => 'x']

La déclarer fixe le modèle attendu. Le défaut empty_data crée un objet à la soumission si nécessaire, sauf form vide non requis ; son constructeur doit alors accepter zéro argument. Une closure empty_data personnalisée permet une autre construction : ce n'est pas le rôle de data_class seule.

Le FormType est le formulaire vierge, le modèle le dossier à remplir. Sans object initial ni data_class, les réponses restent des notes indexées dans un array ; data_class nomme le type de dossier attendu.

La correspondance nom ↔ property

À retenir en priorité
  1. Le nom du field pilote le mapping.
  2. Une property privée exige un chemin d'accès utilisable.

Pour lire dueDate, PropertyAccess essaie : getDueDate(), isDueDate(), hasDueDate(), canDueDate(), une method dueDate(), et seulement ensuite la property publique. Pour écrire : setDueDate() ou la property publique. Une property privée sans accessor lève une NoSuchPropertyException.

Le field non mappé

À comprendre

À retenir en priorité
  1. mapped: false exclut le binding au modèle.
  2. Le field conserve ses propres données.

C'est quoi ?

Un champ mapped, mappé, participe à la lecture et à l'écriture des données du formulaire parent. mapped: false retire ce lien automatique ; le champ continue cependant d'avoir une valeur, une vue et, si configurées, des contraintes de validation.

À quoi ça sert ?

Une confirmation, un fichier reçu ou une instruction auxiliaire ne correspond pas toujours à une propriété du modèle. La déclarer non mappée évite d'inventer une propriété uniquement pour satisfaire le formulaire. Ce choix oblige en contrepartie l'action à traiter explicitement sa valeur lorsqu'elle a un effet.

Où dans Symfony ?

add(name, type, options) définit le nom du champ et son contrat. Avec data_class, les champs mappés utilisent l'accès aux propriétés configuré pour le modèle ; une propriété privée inaccessible n'est pas rendue publique par son nom. Une classe AbstractType rend cette définition réutilisable ; un builder local convient à une construction ponctuelle.

Comment, étape par étape ?

  1. Décider si le champ représente réellement une donnée du parent.
  2. Si non, désactiver son mapping et lui donner explicitement son type.
  3. Ajouter les contraintes nécessaires au champ lui-même.
  4. Après soumission valide, récupérer sa donnée avec get(name)->getData, pas dans la donnée du parent.

Exemple concret PHP

Extrait de buildForm d'un type applicatif ; les imports sont donnés en noms complets :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function buildForm(\Symfony\Component\Form\FormBuilderInterface $builder, array $options): void
{
    $builder->add('agreeTerms', \Symfony\Component\Form\Extension\Core\Type\CheckboxType::class, [
        'mapped' => false,
        'constraints' => [new \Symfony\Component\Validator\Constraints\IsTrue(message: 'Veuillez accepter les conditions.')],
    ]);
}

L'extension Validator doit être disponible pour exécuter IsTrue. Contre-exemple : croire que required et la case cochable du navigateur suffisent à imposer l'acceptation côté serveur. Correction : valider la donnée et lire le champ non mappé explicitement. Il ne faut pas attendre qu'il apparaisse automatiquement dans getData du parent.

Passage canonique conservé

Une case « j'accepte les conditions », un file téléversé : pas de property, donc 'mapped' => false. Sans cela, getForm() échoue : NoSuchPropertyException, « Can't get a way to read the property "agreeTerms" in class "Task" ». Sa valeur se lit par $form->get('agreeTerms')->getData().

Ailleurs que sous son nom

À comprendre

C'est quoi ?

Le mapping est la correspondance entre un champ et une partie des données du formulaire. Par défaut, le nom du champ sert de chemin. property_path change ce chemin sans changer le nom envoyé par le navigateur ; mapped: false supprime cette correspondance ; inherit_data: true fait travailler les enfants d'un sous-formulaire sur les données du parent.

À quoi ça sert ?

Ces options répondent à trois problèmes distincts : présenter un nom de champ différent de la propriété ; demander une information qui ne doit pas être écrite dans l'objet ; regrouper visuellement des champs sans créer un objet imbriqué. Elles ne rendent pas une propriété privée accessible sans mécanisme de lecture/écriture adapté.

Où dans Symfony ?

Un builder construit le formulaire par add(nom, type, options), puis getForm(). Une classe AbstractType réutilisable place ces appels dans buildForm(). L'option data_class précise le type d'objet attendu ; PropertyAccess réalise les accès aux propriétés et méthodes prévues. Sans objet ni data_class, un formulaire composé travaille normalement sur un tableau.

Comment, étape par étape ?

  1. Identifier la donnée du formulaire parent, avant de choisir les noms des champs.
  2. Déclarer explicitement les types de champs pour que le format attendu soit clair.
  3. Utiliser property_path pour un alias, mapped: false pour une donnée séparée.
  4. Lire un champ non mappé sur le formulaire lui-même ; il ne se retrouve pas automatiquement dans l'objet.

Exemple concret PHP

Exemple autonome avec les dépendances Form et PropertyAccess 8.0 installées. La propriété publique simplifie volontairement la démonstration ; une application peut employer des accesseurs.

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Form\Extension\Core\Type\FormType;
use Symfony\Component\Form\Extension\Core\Type\TextType;
use Symfony\Component\Form\Forms;

final class Profile
{
    public string $name = 'Ada';
}

$profile = new Profile();
$form = Forms::createFormFactory()->createBuilder(FormType::class, $profile)
    ->add('displayName', TextType::class, ['property_path' => 'name'])
    ->add('note', TextType::class, ['mapped' => false])
    ->getForm();
$form->submit(['displayName' => 'Grace', 'note' => 'À rappeler']);
echo $profile->name, "\n", $form->get('note')->getData(), "\n";

Le résultat attendu est Grace, puis À rappeler. Contre-exemple : retirer mapped: false de note sans ajouter de propriété accessible à Profile. Le formulaire essaiera de lire/écrire une donnée qui n'existe pas. Correction : conserver le champ non mappé, ou ajouter un vrai mapping si cette donnée appartient au modèle.

Passage canonique conservé
  • property_path : un field title avec property_path: 'name' sert $author->name ; 'profile.bio' descend dans un object imbriqué.
  • inherit_data: true sur un type : ses fields travaillent sur les données du parent — un AddressType écrit city sur l'Author lui-même.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le nom du field n'est pas décoratif.

    Le nom du field n'est pas décoratif. Le renommer casse le binding.

  • Voir l’explication : Les accessors passent avant la property publique

    Les accessors passent avant la property publique : un getter l'emporte.

  • Voir l’explication : Le type omis est deviné par les guessers

    Le type omis est deviné par les guessers, pas par le type PHP ; à défaut, TextType.

  • Voir l’explication : data_class se devine de l'object passé

    data_class se devine de l'object passé ; elle guide empty_data, mais n'instancie pas immédiatement un objet.

  • Déclarer un champ sans propriété correspondante

    Un field sans property correspondante doit être déclaré non mappé.

Application

À retenir en priorité
  1. mapped: false exclut le binding au modèle.
  2. Le field conserve ses propres données.
  3. Le nom relie le field aux données.
  4. Le type et ses options définissent le comportement.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Form réutilisé : class de type ; jetable : createFormBuilder().
  • add(nom, type, options) : le nom relie le field à la property.
  • Type omis : guessers, sinon TextType (toujours TextType sans data_class).
  • data_class : modèle déclaré ou deviné ; empty_data intervient à la soumission, pas comme constructeur immédiat.
  • Lecture : accessors d'abord (get, is, has, can, x()), puis property publique.
  • Field sans property : mapped: false ; autre path : property_path ; données du parent : inherit_data.

Moyen mnémotechnique : « Le nom est l'adresse ».
