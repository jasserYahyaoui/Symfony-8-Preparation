Objectif

Comprendre comment une class de src/ devient un service sans une ligne de configuration, en séparant les trois mécanismes en jeu ; savoir déclarer un service explicitement, connaître le scope de _defaults et l'effet de l'ordre dans le file, et reconnaître les attributes qui déclarent depuis la class.

L'essentiel

À comprendre

À retenir en priorité
  1. Enregistrer ne câble pas les arguments.
  2. Câbler ne pose pas automatiquement tous les tags.

Une class de src/ devient un service par trois mécanismes distincts : découvrir (resource), câbler (autowire), configurer (autoconfigure). Une déclaration explicite complète la definition découverte — à condition d'être écrite dessous. _defaults ne vaut que pour son block. Et des attributes décident depuis la class.

Le schéma

À retenir en priorité
  1. L'ordre des declarations compte.
  2. La dernière definition remplace la précédente.

Le fil rouge : un `Archiver` et son subscriber

À retenir en priorité
  1. L'autowiring résout les services.
  2. Les scalaires demandent une valeur explicite.
class Archiver
{
    public function __construct(
        private LoggerInterface $logger,     // un service : autowirable
        private string $directory,           // un scalaire : à fournir
    ) {
    }
}

class ArchiveSubscriber implements EventSubscriberInterface { /* … */ }

Archiver est découvert, son logger câblé, son $directory à fournir. ArchiveSubscriber reçoit son tag de subscriber sans une ligne.

Trois mécanismes : découvrir, câbler, configurer

À comprendre

À retenir en priorité
  1. exclude limite la découverte.
  2. Une definition explicite reste possible.

C'est quoi ?

Trois opérations se complètent sans se remplacer :

  • La découverte crée des définitions à partir des classes d'une ressource.
  • L'autowiring, câblage automatique, détermine les arguments à injecter à partir des types et des indications explicites.
  • L'autoconfiguration applique des règles de configuration, souvent des tags, selon les interfaces ou attributs reconnus.

À quoi ça sert ?

Cette séparation permet de diagnostiquer une classe « non prise en compte ». Si elle n'est pas enregistrée, activer l'autowiring ne la découvre pas. Si elle est enregistrée mais attend une chaîne sans valeur, un tag automatique ne résout pas son argument.

Où dans Symfony ?

En YAML, resource indique où chercher, autowire active le câblage et autoconfigure active les règles. La découverte d'une classe ne la rend pas publique. Une exclusion limite cette découverte ; elle n'efface pas la classe du projet.

Comment, étape par étape ?

  1. Parcourir la ressource et appliquer les exclusions.
  2. Enregistrer les définitions obtenues.
  3. Appliquer les règles d'autoconfiguration aux services concernés.
  4. Résoudre les arguments autowirables et les valeurs explicites.
  5. Vérifier et optimiser le graphe final.

Exemple concret YAML

services:
    _defaults:
        autowire: true
        autoconfigure: true
    App\:
        resource: '../src/'
        exclude: '../src/{Entity,Kernel.php}'

Une classe de src/Service/ peut devenir un service privé ; une classe exclue n'est pas découverte par cette ressource. Contre-exemple : mettre un attribut de configuration sur une classe hors de toute ressource puis attendre sa création automatique. Correction : l'enregistrer explicitement ou étendre la ressource adaptée. Autre erreur : croire qu'autoconfigure choisit la valeur d'un argument string $directory ; cette valeur nécessite arguments, bind ou #[Autowire].

Passage canonique conservé

Trois mécanismes : découvrir, câbler, configurer

Mécanisme Écriture Ce qu'il fait Ce qu'il ne fait pas
découvrir App\: { resource: '../src/' } une definition par class, id = FQCN ne câble, ne tague, ne rend pas public
câbler autowire: true résout les arguments typés par un service ne devine pas un scalaire
configurer autoconfigure: true pose les tags d'après l'interface ou l'attribute ne crée pas de service
  • Une class découverte et inutilisée ne gêne rien : privée, jamais référencée, elle est retirée à la compilation.
  • exclude: '../src/{Entity,Kernel.php}' retire de la découverte seulement : une class exclue mais déclarée plus bas est enregistrée.
  • En PHP avec App::config(), les services sont autowirés et autoconfigurés par défaut ; en YAML sans _defaults, non — ArgumentCountError à l'instanciation.

Le cas explicite : des named arguments

À comprendre

À retenir en priorité
  1. Une surcharge peut perdre arguments et visibilité.
  2. Placer les réglages explicites après la découverte.

C'est quoi ?

Un argument nommé dans une définition de service utilise le nom du paramètre PHP, précédé de $, au lieu de sa position. Il permet de fournir une valeur particulière tout en laissant les autres arguments au câblage automatique.

À quoi ça sert ?

La configuration reste compréhensible lorsque le constructeur possède plusieurs paramètres : $directory exprime mieux le besoin que l'index 1. En contrepartie, renommer ce paramètre PHP exige d'adapter la configuration qui le désigne.

Où dans Symfony ?

arguments configure le constructeur ou, lorsqu'une factory est définie, les arguments de cette factory. @identifiant désigne un service ; %parametre% désigne une valeur du container. Une définition explicite doit venir après la ressource qui découvre la même classe, car une définition ultérieure remplace la précédente.

Comment, étape par étape ?

  1. Déclarer les valeurs par défaut et la ressource générale.
  2. Ajouter la définition particulière sous le même identifiant.
  3. Nommer les arguments qui nécessitent un choix explicite.
  4. Ne pas supposer que toutes les options de l'ancienne définition sont fusionnées : vérifier les options nécessaires et les _defaults applicables.

Exemple concret YAML

Archiver possède un argument string $directory ; ses autres dépendances objet sont autowirables.

services:
    _defaults:
        autowire: true
    App\:
        resource: '../src/'
        exclude: '../src/Kernel.php'
    App\Service\Archiver:
        arguments:
            $directory: '%kernel.project_dir%/var/archive'

Le chemin est fourni après la découverte générale. Contre-exemple : placer cette définition avant App\: resource ; la découverte ultérieure peut remplacer la configuration particulière. Correction : conserver l'ordre montré. Cette définition reste privée : fournir un argument ne signifie pas la rendre publique, contrairement à ce que laisserait croire une lecture trop rapide d'un exemple combinant les deux options.

Passage canonique conservé
services:
    # … _defaults et App\ au-dessus …
    App\Service\Archiver:
        arguments:
            $directory: '%kernel.project_dir%/var/archive'   # par son nom, pas sa position
            $logger: '@logger'               # @ = un service
        calls:
            - setFormat: ['zip']
        tags: ['app.archiver']

« Service definitions always replace previous ones » : avec les defaults privés utilisés ici, une définition explicite reste privée. Seule une option applicable public: true la rend publique ; sa position ne le fait pas.

Position de la definition explicite Definition finale d'Archiver
après App\: resource privée avec les defaults utilisés ici, $directory fourni
avant App\: resource privée, sans argument : remplacée en silence

Le scope de `_defaults`

À comprendre

À retenir en priorité
  1. Les defaults ont un scope local.
  2. Un block conditionnel possède sa propre configuration.

C'est quoi ?

La portée, ou scope, de _defaults est le bloc services dans lequel il apparaît. Il fournit des options par défaut aux définitions de ce bloc, pas une règle globale de toute l'application.

À quoi ça sert ?

Des fichiers importés ou des blocs conditionnels peuvent avoir des besoins différents. Une portée locale évite qu'un changement de fichier modifie silencieusement les options de tous les bundles. Elle oblige aussi à répéter les options nécessaires lorsqu'un nouveau bloc est créé.

Où dans Symfony ?

Chaque bloc when@dev, when@test ou when@prod possède sa propre portée de services. Ses définitions ne récupèrent pas automatiquement les _defaults du bloc principal. Une option explicite sur un service peut ensuite remplacer la valeur par défaut de son propre bloc.

Comment, étape par étape ?

  1. Identifier le bloc qui contient la définition finale du service.
  2. Lire les _defaults de ce bloc seulement.
  3. Appliquer ses options explicites.
  4. Vérifier le constructeur : sans arguments fournis et sans autowiring actif, une dépendance obligatoire reste non satisfaite.

Exemple concret YAML

services:
    _defaults:
        autowire: true
    App\ProductionReporter: ~

when@test:
    services:
        _defaults:
            autowire: true
        App\TestReporter: ~

Les deux reporters sont autowirés grâce à deux déclarations locales. Contre-exemple : supprimer le second _defaults en supposant qu'il hérite du premier ; un constructeur obligatoire peut alors manquer d'arguments à l'instanciation. Correction : activer l'autowiring dans le bloc when@test, ou fournir tous les arguments explicitement. La classe doit naturellement exister et ses dépendances être disponibles : la portée correcte ne résout pas un type inconnu.

Passage canonique conservé

Le scope de _defaults

_defaults ne s'applique qu'au block où il est écrit : chaque when@dev ou when@test a le sien. Oublié, il se paie à l'instanciation par une ArgumentCountError (« Too few arguments… ») qui ne nomme pas la cause.

Déclarer depuis la class : les attributes

À comprendre

À retenir en priorité
  1. When exprime une condition d'environment.
  2. Exclude exclut la découverte.

C'est quoi ?

Un attribut PHP est une métadonnée attachée à une déclaration. Pour les services, son effet dépend du lecteur Symfony qui le traite : PHP ne configure pas le container tout seul à la lecture de #[...].

À quoi ça sert ?

Les attributs placent une intention près de la classe ou de l'argument concerné. Ils sont utiles lorsqu'une règle appartient naturellement à ce code ; une configuration externe reste préférable pour un choix propre au déploiement ou pour configurer une classe tierce.

Où dans Symfony ?

  • #[AsAlias] déclare un alias lors de la découverte de la classe.
  • #[Autoconfigure] fournit des options de service.
  • #[AutoconfigureTag] peut associer un tag aux implémentations d'une interface.
  • #[Autowire] renseigne un argument précis.
  • #[When] limite l'enregistrement à un environnement ; #[Exclude] exclut la classe de la découverte.

Comment, étape par étape ?

  1. La classe doit être chargée par le mécanisme de découverte ou enregistrée selon le mécanisme concerné.
  2. Le lecteur approprié examine les attributs.
  3. Les options ou références deviennent des informations de définition.
  4. La compilation vérifie l'assemblage ; l'attribut n'exécute pas la méthode métier.

Exemple concret PHP

Dans une application Symfony 8.0 où App\ est découvert et autowiré, ce service demande le paramètre du framework, pas une chaîne devinée.

<?php
namespace App;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
final class ProjectPaths
{
    public function __construct(
        #[Autowire(param: 'kernel.project_dir')]
        public readonly string $root,
    ) {}
}

$root reçoit le dossier du projet lors de la construction par le container. Contre-exemple : appeler manuellement new ProjectPaths() en pensant que PHP lira l'attribut pour fournir l'argument. Correction : fournir l'argument lors d'une construction manuelle, ou faire construire le service par le container. Ne pas non plus confondre autoconfiguration et découverte : une classe exclue n'est pas réintroduite par le simple fait de porter un attribut.

Passage canonique conservé

Déclarer depuis la class : les attributes

Attribute Effet
#[AsAlias] un alias, privé, vers cette class
#[Autoconfigure] public, lazy, shared, tags, calls, bind…
#[AutoconfigureTag] sur une interface : tague toutes ses implémentations
#[Autowire] câble un argument précis
#[When(env: 'prod')] service seulement dans cet environment
#[Exclude] hors de la découverte, partout

Hors de son environment, une class #[When] garde une definition marquée container.excluded : l'injecter échoue, « …but this type has been excluded ».

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'autoconfiguration ne remplace pas l'enregistrement.
  2. La class doit d'abord être un service.
  • Voir l’explication : Un service découvert est privé

    Un service découvert est privé : la découverte ne le rend pas public.

  • Voir l’explication : exclude ne supprime pas la class

    exclude ne supprime pas la class : elle l'exclut de l'enregistrement automatique. Une class exclue mais déclarée explicitement est enregistrée — exécuté, avec la visibilité demandée.

  • Voir l’explication : _defaults ne traverse pas les blocks when@

    _defaults ne traverse pas les blocks when@, et l'oubli se paie par une ArgumentCountError qui ne le mentionne pas.

  • Voir l’explication : #[When] exclut hors de son environment

    #[When] exclut hors de son environment ; #[Exclude] exclut partout.

  • Voir l’explication : Une definition explicite placée au-dessus de App\: est perdue.

    Une definition explicite placée au-dessus de App\: est perdue. La découverte, écrite plus bas, la remplace en silence : le service redevient privé et perd ses arguments. Les configurations explicites se placent dessous.

  • Voir l’explication : autowire et autoconfigure sont deux réglages distincts.

    autowire et autoconfigure sont deux réglages distincts. Le premier résout les arguments ; le second pose les tags. Un subscriber qui n'est pas appelé pointe vers l'autoconfiguration, un argument vide vers l'autowiring.

  • Voir l’explication : En PHP avec App::config(), autowire et autoconfigure sont actifs par défaut

    En PHP avec App::config(), autowire et autoconfigure sont actifs par défaut ; en YAML, il faut _defaults.

Fiche express

À mémoriser

À retenir en priorité
  1. Le FQCN devient l'identifier.
  2. La visibilité reste privée par défaut.

Si tu dois retenir seulement 7 choses :

  • Découvrir (resource), câbler (autowire), configurer (autoconfigure) : trois mécanismes.
  • Découvert = privé, id = FQCN.
  • exclude : hors de la découverte, pas du projet.
  • Explicite sous App\:, sinon remplacé en silence.
  • _defaults : son block seulement ; when@ a le sien.
  • App::config() : autowire et autoconfigure par défaut.
  • #[When] : un environment ; #[Exclude] : partout.

Moyen mnémotechnique : « D-C-C : Découvrir, Câbler, Configurer ».
