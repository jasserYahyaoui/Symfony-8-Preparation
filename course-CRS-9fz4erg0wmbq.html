Objectif

Connaître les conventions propres aux controllers, et savoir lesquelles sont obligatoires. Les conventions générales du framework — casse, préfixes Abstract, suffixes Interface et Trait — sont traitées dans le Module 03 — Architecture Symfony.

L'essentiel

À comprendre

À retenir en priorité
  1. Le nom généré n'est pas une conversion générale en snake_case.
  2. Plusieurs routes d'une method reçoivent des suffixes distincts.

Presque rien n'est imposé à un controller : le suffixe Controller, la class de base, l'absence de suffixe Action sont des conventions. Une seule obligation : un route name unique. Quand on l'omet, Symfony le génère en deux couches — le component, puis FrameworkBundle qui le raccourcit — et c'est ce nom généré que l'examen fait calculer.

Le schéma

À retenir en priorité
  1. _controller identifie le callable cible.
  2. Une class invocable peut omettre ::__invoke.

L'exemple : une route sans nom

Exemple concret

À retenir en priorité
  1. Sans name explicite, le loader construit un route name depuis la class et la method.
  2. FrameworkBundle raccourcit le nom ; ici le résultat est app_lucky_number.
namespace App\Controller;

final class LuckyController extends AbstractController
{
    #[Route('/lucky/number')]
    public function number(): Response   // nom généré : app_lucky_number
    {
        // ...
    }
}

Rien n'est imposé, presque

À comprendre

À retenir en priorité
  1. Un controller est un callable.
  2. Les route names doivent en revanche être uniques.

C'est quoi ?

Une convention de nom rend le code reconnaissable par les personnes ; une exigence technique conditionne son fonctionnement. Le suffixe Controller est une convention. Le resolver doit finalement obtenir un callable PHP, pas seulement reconnaître un suffixe.

À quoi ça sert ?

Cette distinction permet d'intégrer une classe existante sans la renommer inutilement. Suivre la convention reste utile pour retrouver les actions ; cela ne dispense jamais de configurer leur découverte et leurs dépendances.

Où dans Symfony ?

Ni le suffixe Controller ni l'héritage d'AbstractController ne sont obligatoires. Une méthode d'action doit pouvoir être appelée. Une classe invocable expose __invoke ; le nom de classe peut alors désigner le controller. Les noms de routes doivent identifier distinctement les routes conservées dans la collection.

Comment, étape par étape ?

  1. Écrire un callable retournant une Response.
  2. Le rendre disponible au resolver, généralement comme service dans l'application.
  3. Le désigner depuis une route.
  4. Choisir ensuite un nom lisible conforme aux habitudes du projet.

Exemple concret PHP

Classe sans suffixe Controller, à enregistrer et associer à une route :

<?php
namespace App\Controller;
use Symfony\Component\HttpFoundation\Response;

final class HealthEndpoint
{
    public function __invoke(): Response
    {
        return new Response('ok');
    }
}

La méthode publique rend l'objet invocable. Contre-exemple : ajouter le suffixe Controller à une classe sans méthode appelable puis attendre que Symfony invente son action. Correction : fournir le callable et son raccord de routage ; le renommage ne crée aucun comportement.

Le format `_controller`

À comprendre

C'est quoi ?

_controller est un attribute de la Request qui désigne le callable à exécuter. Un callable PHP est une valeur que PHP peut appeler : fonction, méthode d'objet ou objet invocable. Dans une route, la notation habituelle App\Controller\StatusController::show associe un nom de classe complet à une méthode.

À quoi ça sert ?

Le nom de route, le chemin et le controller sont trois identités distinctes : le nom sert notamment à générer un lien, le chemin participe à la correspondance HTTP, le controller réalise le traitement. Les confondre conduit à passer une URL là où une méthode est attendue.

Où dans Symfony ?

Le router fournit _controller, puis le controller resolver le transforme en callable. FrameworkBundle peut retrouver le controller comme service. Le suffixe Controller, l'absence de suffixe Action et le nom de template en snake_case sont des conventions ; étendre AbstractController n'est pas obligatoire. En revanche, des noms de routes distincts sont nécessaires pour conserver des routes distinctes dans la collection : réutiliser un nom ne crée pas une surcharge adressable séparément.

Comment, étape par étape ?

  1. Écrire une méthode publique qui retourne une Response.
  2. Enregistrer et rendre le controller accessible selon la configuration de l'application.
  3. L'associer à une route par attribute PHP ou configuration externe.
  4. Donner un nom de route explicite lorsqu'il doit rester stable après un renommage de classe ou de méthode. Les noms automatiques dépendent du loader ; FrameworkBundle simplifie le nom produit par le component.

Exemple concret YAML

Avec un service controller App\Controller\StatusController qui expose show() :

status:
    path: /status
    controller: App\Controller\StatusController::show

La clé status est le nom de route, /status son chemin, et la dernière valeur le controller. Pour une classe dont l'action est __invoke(), le nom de classe seul suffit. Contre-exemple : écrire controller: status en pensant référencer la route ; cette valeur est cherchée comme désignation de callable ou de service. Correction : fournir la classe et la méthode, ou l'identifiant d'un controller réellement enregistré.

Passage canonique conservé

Le format _controller

App\Controller\BlogController::show : class pleinement qualifiée, ::, nom de method — la string que le router dépose dans l'attribute _controller. Pour une class invocable, la class seule suffit.

Un standard téléphonique a besoin d'une extension qui répond, pas d'un intitulé de poste particulier. Le ControllerResolver cherche un callable ; le suffixe Controller améliore surtout la lecture humaine.

Le route name, et qui le génère

À comprendre

C'est quoi ?

Le nom de route est la clé utilisée pour générer un lien. Si name est omis sur un attribute Route, le loader en construit un à partir de la classe et de la méthode. Il ne le déduit pas du chemin de l'URL.

À quoi ça sert ?

Un nom automatique évite une déclaration pour une route locale simple. Un nom explicite est préférable lorsque des liens ou une intégration doivent rester stables après un renommage du code.

Où dans Symfony ?

AttributeClassLoader du component remplace les séparateurs de namespace par des underscores, ajoute la méthode, met en minuscules et suffixe les routes supplémentaires de la même méthode. AttributeRouteControllerLoader de FrameworkBundle simplifie notamment les segments controller et bundle ainsi qu'un suffixe Action. Le résultat dépend donc du loader employé.

Comment, étape par étape ?

  1. Identifier classe, namespace et méthode réels.
  2. Tenir compte du loader et d'un éventuel préfixe de nom porté par la classe.
  3. Examiner le résultat avec debug:router.
  4. Fixer name si cette identité doit survivre aux changements de nom du code.

Exemple concret PHP

Avec le loader de FrameworkBundle, sans préfixe de classe :

<?php
namespace App\Controller;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class LuckyController
{
    #[Route('/lucky')]
    public function number(): Response { return new Response('7'); }
}

Le nom attendu est app_lucky_number ; le component seul produit app_controller_luckycontroller_number. Contre-exemple : renommer number en draw tout en conservant des liens vers l'ancien nom automatique. Correction : déclarer name: 'lucky_number' et utiliser cette identité explicite dans les liens. Le chemin /lucky n'a pas besoin de changer.

Passage canonique conservé

Le route name, et qui le génère

Le component Routing, dans AttributeClassLoader::getDefaultRouteName(), remplace les \ par des _, ajoute _ et le nom de la method, met le tout en minuscules, puis ajoute _ et defaultRouteIndex à partir de la deuxième route d'une même method. AttributeRouteControllerLoader, de FrameworkBundle, retire ensuite les segments bundle_ et controller_, un suffixe action, et les __ restants.

Method Component seul Avec FrameworkBundle
LuckyController::number app_controller_luckycontroller_number app_lucky_number
BlogController::showAction app_controller_blogcontroller_showaction app_blog_show
deuxième route de la même method suffixe _1 app_lucky_number_1

Rien ne découpe le CamelCase : LuckyController devient luckycontroller. Un name porté par la class est préfixé. Une method qui ne déclare qu'une route reçoit en plus l'alias App\Controller\LuckyController::number.

Repère de l’exemple : app_lucky_number. Sans name explicite, le loader construit un route name depuis la class et la method. FrameworkBundle raccourcit le nom ; ici le résultat est app_lucky_number.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le suffixe Controller est une convention, pas une constraint

    Le suffixe Controller est une convention, pas une constraint — pas plus qu'étendre une class de base ne l'est.

  • Voir l’explication : Le nom généré n'est pas du snake_case.

    Le nom généré n'est pas du snake_case. Rien ne découpe le CamelCase : LuckyController devient luckycontroller, pas lucky_controller. La lisibilité de app_lucky_number vient du retrait du segment controller_, pas d'une conversion de casse. Le snake_case est recommandé pour les templates.

  • Voir l’explication : Sans FrameworkBundle, le nom généré reste celui du component.

    Sans FrameworkBundle, le nom généré reste celui du component. Le nom court est un apport du bundle.

  • Voir l’explication : Une deuxième route sur la même method ne collisionne pas

    Une deuxième route sur la même method ne collisionne pas : elle reçoit un suffixe numérique, _1, _2…

  • Voir l’explication : Le suffixe Action n'est plus utilisé, mais il est toujours reconnu

    Le suffixe Action n'est plus utilisé, mais il est toujours reconnu : le loader du bundle le retire du nom généré.

Application

À retenir en priorité
  1. Le nom généré n'est pas une conversion générale en snake_case.
  2. Plusieurs routes d'une method reçoivent des suffixes distincts.
  3. Un controller est un callable.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Une seule obligation : un route name unique.
  • Controller, AbstractController, pas d'Action : des conventions.
  • _controller = FQCN::méthode, ou le FQCN seul si invocable.
  • Nom généré : component en minuscules, sans découpe du CamelCase.
  • FrameworkBundle retire controller_ et action → app_lucky_number.
  • Deuxième route : _1 ; alias FQCN seulement pour une route.

Moyen mnémotechnique : « S'il contient controller, c'est le component nu ».
