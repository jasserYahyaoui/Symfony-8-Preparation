Objectif

Savoir sur quoi une constraint peut être posée, et ce que chaque scope permet que les autres ne permettent pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Une règle croisée vise la class.
  2. Une property ne fournit que sa valeur.

Une constraint se pose à trois endroits : une property (la valeur stockée), un accessor (une valeur calculée par une method get, is ou has) ou la class (l'objet entier transmis au validateur). La différence est la valeur reçue par la contrainte, pas le nombre de propriétés utilisées pour la calculer : un getter peut comparer deux propriétés et retourner un booléen que IsTrue vérifiera.

Le schéma

À retenir en priorité
  1. Distinguer valeur stockée et calculée.
  2. La class donne accès à l'ensemble de l'object.

Ambre = sélection de cible, bleu = valeur fournie, vert = vérification. Ce flux de données suppose un mapping valide et un getter appelable sans argument obligatoire. Les erreurs de mapping et d'exécution ne deviennent pas automatiquement des violations métier.

L'exemple : un `Author`

Exemple concret

À retenir en priorité
  1. La règle doit voir les deux noms.
  2. atPath() choisit le field de correction.
use Symfony\Component\Validator\Constraints as Assert;

class Author
{
    #[Assert\Length(min: 3)]                  // stocké : property
    private string $firstName = 'Ada';

    private string $password = 'Ada';

    #[Assert\IsTrue(message: 'Le mot de passe ne peut pas reprendre le prénom.')]
    private function isPasswordSafe(): bool   // calculé : accessor
    {
        return $this->firstName !== $this->password;
    }
}

Ici, Length accepte Ada, mais isPasswordSafe() retourne false : IsTrue produit une violation au chemin passwordSafe. La règle croise bien deux propriétés, sans être une contrainte de classe.

Les trois cibles

À comprendre

À retenir en priorité
  1. Le scope property inclut les accessors.
  2. Le scope class reste distinct.

C'est quoi ?

La cible d'une contrainte détermine la valeur examinée. Une contrainte de propriété reçoit la donnée stockée ; une contrainte sur accessor reçoit le résultat d'une méthode ; une contrainte de classe reçoit l'objet et peut examiner plusieurs données liées.

À quoi ça sert ?

Choisir une portée adaptée évite de placer une règle sur une valeur qui ne contient pas les informations nécessaires. Vérifier la longueur d'un nom concerne sa valeur ; vérifier la cohérence entre début et fin nécessite de considérer leur relation, par une règle de classe ou une contrainte conçue pour la comparaison appropriée.

Où dans Symfony ?

Les getters de validation correspondent aux préfixes reconnus get, is et has. Dans les métadonnées, le nom logique retire ce préfixe. Une contrainte personnalisée déclare ses cibles via getTargets ; PROPERTY_CONSTRAINT couvre propriétés et accessors, CLASS_CONSTRAINT la classe.

Comment, étape par étape ?

  1. Identifier la valeur dont la règle a besoin.
  2. Choisir propriété, résultat calculé ou objet.
  3. Garder les accessors de validation sans effet de bord : ils peuvent être appelés lors d'un contrôle.
  4. Rattacher la violation à une propriété pertinente si une règle de classe doit être présentée près d'un champ.

Exemple concret PHP

Classe dont une règle calculée porte sur une méthode, avec le mapping d'attributes activé dans Validator :

<?php
use Symfony\Component\Validator\Constraints as Assert;

final class DateIntervalInput
{
    public int $start = 10;
    public int $end = 5;

    #[Assert\IsTrue(message: 'La fin doit suivre le début.')]
    public function isChronological(): bool
    {
        return $this->end >= $this->start;
    }
}

Le validator examine le booléen retourné et associe la règle au nom logique chronological. Contre-exemple : mettre IsTrue sur l'entier end en pensant comparer automatiquement les deux propriétés. Correction : valider le calcul explicite, ou utiliser une règle croisée adaptée. Pour placer l'erreur sur end dans un formulaire, une règle de classe avec atPath('end') exprime ce rattachement sans prétendre qu'un accessor porte déjà ce chemin.

Passage canonique conservé
Cible Ce qu'elle valide Quand la choisir
property la valeur stockée le cas courant
accessor la valeur retournée par une method la règle est calculée
class l'object entier la règle croise plusieurs properties

La property

À retenir en priorité
  1. Une property non initialisée est lue comme null.
  2. La constraint détermine alors le résultat.

La visibilité n'a aucune importance : le validator lit la property par réflexion, private comprise. Une property typée non initialisée est validée comme null : NotBlank la refuse, Length la laisse passer.

L'accessor

À comprendre

À retenir en priorité
  1. Le préfixe is disparaît du path.
  2. Le path représente la valeur calculée.

C'est quoi ?

Un accessor, méthode de lecture, expose une valeur calculée plutôt qu'une propriété stockée. Une contrainte placée sur un accessor valide sa valeur de retour. Pour ce mapping, Symfony reconnaît les préfixes get, is et has : ce n'est pas une permission de placer une contrainte sur n'importe quelle méthode.

À quoi ça sert ?

Une valeur dérivée peut être validée sans ajouter une propriété redondante à l'objet. Cela convient à un prédicat simple qui retourne vrai ou faux. Une règle de classe convient mieux lorsqu'on veut produire plusieurs violations ou choisir finement leurs chemins. Une contrainte de propriété reste le choix direct pour contrôler une valeur stockée.

Où dans Symfony ?

Le validator invoque l'accessor sans argument. Sa visibilité peut être privée, protégée ou publique. Le chemin de propriété utilisé pour la violation retire le préfixe : isChronological() correspond à chronological. Dans une déclaration YAML, cette cible se place sous getters, avec ce nom logique.

Comment, étape par étape ?

  1. Choisir une méthode sans argument requis et au nom reconnu.
  2. Lui faire retourner la valeur que la contrainte sait contrôler.
  3. Déclarer la contrainte et charger ses métadonnées.
  4. Vérifier le chemin de l'erreur : ce n'est pas automatiquement la propriété que l'utilisateur doit modifier.

Exemple concret PHP

Avec Validator 8.0 et le mapping par attributes activé :

<?php
use Symfony\Component\Validator\Constraints as Assert;

final class Period
{
    public function __construct(private int $start, private int $end) {}

    #[Assert\IsTrue(message: 'La fin doit suivre le début.')]
    public function isChronological(): bool
    {
        return $this->end >= $this->start;
    }
}

Valider new Period(5, 2) produit une violation au chemin chronological ; new Period(2, 5) satisfait cette règle. Contre-exemple : renommer la méthode checkChronology() sans changer le mapping : son nom n'est plus un accessor reconnu. Correction : conserver un préfixe admis ou utiliser une contrainte Callback adaptée. Autre erreur : ajouter un paramètre obligatoire ; le validator ne sait pas quelle valeur lui fournir. Pour rattacher l'erreur à end, préférer une règle de classe qui construit une violation avec atPath('end').

Passage canonique conservé
Method annotée Résultat
private function isPasswordSafe() violation au path passwordSafe
public function getFullName() violation au path fullName
private function checkPasswordSafety() MappingException : « Constraints can only be added on methods beginning with "get", "is" or "has". »
public function isOk(int $x) ArgumentCountError à la validation
  • Le path est le nom sans le préfixe, première lettre en minuscule ; le préfixe ignore la casse, et une method statique est acceptée.
  • En YAML, ces constraints vont sous getters:, avec le nom sans préfixe.
  • Un mauvais nom échoue à la lecture des metadata ; un argument requis n'est pas vérifié au chargement : c'est l'appel qui casse.

La class

À retenir en priorité
  1. Sans atPath(), la violation conserve le path courant de l'objet : vide à la racine, préfixé lorsqu'il est imbriqué.
  2. atPath() permet de viser une property.

Callback s'applique à l'object lui-même. Une constraint maison y accède en rendant Constraint::CLASS_CONSTRAINT depuis getTargets() ; par défaut, elle rend Constraint::PROPERTY_CONSTRAINT, qui couvre properties et accessors.

Cette portée convient à une règle croisée qui doit recevoir directement l'objet et choisir le chemin de son erreur :

#[Assert\Callback('check')]
// Même alias Assert que plus haut ; contexte reçu par le callback.
class Contract
{
    public function __construct(
        public \DateTimeImmutable $start,
        public \DateTimeImmutable $end,
    ) {
    }

    public function check(\Symfony\Component\Validator\Context\ExecutionContextInterface $context): void
    {
        if ($this->end < $this->start) {
            $context->buildViolation('La fin précède le début.')
                ->atPath('end')
                ->addViolation();
        }
    }
}

Sans atPath(), la violation conserve le path courant de l'object : vide seulement à la racine de validation, par exemple child pour un objet imbriqué validé à cet emplacement. atPath('firstName') ajoute un chemin relatif : firstName à la racine, child.firstName dans ce contexte imbriqué.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La visibilité n'empêche pas la lecture.
  2. Un argument requis casse l'appel du getter.
  • Voir l’explication : Un accessor doit s'appeler get…, is… ou has…

    Un accessor doit s'appeler get…, is… ou has… ; sinon, une MappingException, pas un oubli silencieux.

  • Voir l’explication : La visibilité ne bloque rien

    La visibilité ne bloque rien, ni sur une property ni sur un accessor.

  • Voir l’explication : Le path d'une violation d'accessor perd le préfixe

    Le path d'une violation d'accessor perd le préfixe : isPasswordSafe donne passwordSafe.

  • Voir l’explication : Une règle croisée n'impose pas toujours la portée classe.

    Une règle croisée n'impose pas toujours la portée classe. Un getter calculé avec IsTrue peut suffire. Choisir une contrainte de classe lorsque son validateur doit recevoir l'objet entier, par exemple pour produire plusieurs erreurs sur des chemins distincts.

  • Voir l’explication : Une property typée jamais affectée est validée comme null

    Une property typée jamais affectée est validée comme null : NotBlank la refuse, mais Length ou Email la laissent passer.

Fiche express

À mémoriser

À retenir en priorité
  1. Les getters suivent les préfixes reconnus.
  2. Un mauvais nom n'est pas ignoré silencieusement.

Si tu dois retenir seulement 6 choses :

  • Trois cibles : property (stocké), accessor (calculé), class (croisé).
  • La visibilité ne compte jamais.
  • Accessor : get / is / has, sans argument ; path sans préfixe.
  • Mauvais nom : MappingException ; argument requis : ArgumentCountError.
  • Property typée non initialisée : validée comme null.
  • Règle entre deux fields : Callback de class + atPath().

Moyen mnémotechnique : « Stocké, Calculé, Croisé » — property, accessor, class.
