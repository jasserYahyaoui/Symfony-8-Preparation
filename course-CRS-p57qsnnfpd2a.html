Objectif

/blog/42 trouve un article ; /blog/999 reconnaît la même route mais ArticleCatalog ne trouve rien. Une URL inconnue peut au contraire échouer avant tout contrôleur. Nous voulons une réponse 404 adaptée à ces absences, sans transformer une panne inattendue en « article introuvable ».

Produire un 404 depuis un controller, savoir quel statut produit une exception, et personnaliser la page affichée.

L'essentiel

À comprendre

À retenir en priorité
  1. Le helper construit l'exception.
  2. throw interrompt le controller et déclenche le traitement HTTP.

createNotFoundException() construit une NotFoundHttpException : sans throw, rien ne se passe. Le statut d'une exception se décide en trois lignes — celui d'une exception HTTP, 400 pour une RequestExceptionInterface, sinon 500. La page se personnalise par des templates Twig, qui reçoivent une FlattenException. Le rendu debug remplace normalement ces templates ; une 404 de routage peut survenir avant l'initialisation du contexte de sécurité.

Le schéma

À retenir en priorité
  1. La personnalisation ne requiert pas un template par statut.
  2. Le template reçoit une FlattenException, pas l'exception originale.

Bleu = données et rendu ; ambre = décision. C'est le chemin HTML standard après traitement de l'exception, sans listener applicatif remplaçant la réponse. Lever une exception ne signifie pas que son message doit être publié : préférer un texte public générique à un détail technique.

L'exemple

Exemple concret

Le catalogue de produits conserve un exemple autonome du même contrat que notre catalogue d'articles en mémoire : find() peut retourner null. La route numérique accepte l'identifiant 999 ; seule la consultation du catalogue permet ensuite de constater l'absence. Le requirement ne garantit pas l'existence de la ressource.

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

interface ProductCatalog
{
    public function find(int $id): ?object;
}

final class ProductController extends AbstractController
{
    public function __construct(private ProductCatalog $catalog) {}

    #[Route('/product/{id}', requirements: ['id' => '\d+'])]
    public function show(int $id): Response
    {
        $product = $this->catalog->find($id);
        if (null === $product) {
            throw $this->createNotFoundException('The product does not exist');
        }
        return $this->render('product/show.html.twig', ['product' => $product]);
    }
}

L'application fournit une implémentation du contrat ProductCatalog, le template indiqué et l'enregistrement du contrôleur. Aucune persistance particulière n'est requise par cet exemple.

🌍 In Real Life

La situation : l'accueil sait à quel service adresser une demande numérotée, mais ce service peut constater que la référence demandée n'existe pas. Trouver le bon guichet ne prouve pas qu'il possède le dossier.

L’équivalent dans Symfony : /blog/999 peut satisfaire la route numérique comme /blog/42. C'est ensuite la recherche explicite dans ArticleCatalog, ou dans le catalogue de produits de l'exemple, qui constate l'absence.

Retour à la réalité technique : un requirement contrôle la forme du paramètre, pas l'existence de la ressource. L'application fournit l'implémentation du catalogue ; aucun ORM ni entity resolver implicite n'est requis. Une route inexistante peut produire une autre 404 avant ce contrôleur.

🧠 Comment le mémoriser : « Bon guichet ne garantit pas dossier trouvé. » Image mentale : guichet correct, casier 999 vide. Question-réflexe : l'échec concerne-t-il le matching ou la recherche métier ?

⚠️ À ne pas confondre : absence constatée et panne inattendue du catalogue ; les transformer toutes deux en 404 masque le diagnostic.

Produire le 404

Dans BlogController::show, la branche « article absent » doit interrompre le rendu normal. Lever l'exception permet au traitement d'erreur configuré de produire la page 404. Construire l'objet exception puis continuer vers Twig ne réalise pas cette interruption.

Le mot important est throw. createNotFoundException() construit et retourne l'exception ; elle ne la lève pas. Sans throw, le controller continue ; le statut dépend alors de la réponse réellement retournée. Sans argument, le message vaut 'Not Found'.

🌍 In Real Life

La situation : rédiger un avis « dossier introuvable » et le laisser sur son bureau n'interrompt pas le service. Il faut signaler l'incident pour quitter le traitement normal.

L’équivalent dans Symfony : createNotFoundException() fabrique l'objet exception ; throw le lève et interrompt le chemin courant. Le traitement d'exception configuré peut alors construire la réponse 404.

Retour à la réalité technique : créer ou retourner cet objet n'équivaut pas à retourner une Response HTTP. À l'inverse, construire explicitement une Response de statut 404 reste possible sans exception. L'interruption ne garantit pas à elle seule qu'un listener produira une réponse ni que celle-ci sera envoyée.

🧠 Comment le mémoriser : « Rédiger l'avis n'est pas donner l'alerte. » Image mentale : avis posé puis transmis. Question-réflexe : ai-je seulement construit l'exception ou réellement quitté le chemin normal ?

⚠️ À ne pas confondre : construire, lever, convertir en Response et envoyer.

Préparer un drapeau « introuvable » n'est pas le lever. createNotFoundException() prépare l'object ; throw déclenche le signal que le kernel transforme en page d'erreur.

Repère — Quel statut pour quelle exception :

Question: Do all non-HttpExceptionInterface errors become 500?

Answer: No. RequestExceptionInterface errors become 400.

HttpExceptionInterface porte son propre statut. Une Request malformée peut produire 400 plutôt que 500.

Quel statut pour quelle exception

À retenir en priorité
  1. HttpExceptionInterface porte son propre statut.
  2. Une Request malformée peut produire 400 plutôt que 500.

Le client JSON de l'inscription peut envoyer un body illisible : c'est une erreur de requête, différente de l'article absent et d'une panne du catalogue. Le tableau décrit le choix standard de statut lors de l'aplatissement ; il ne promet pas que tout Throwable, dans toute configuration, atteigne nécessairement ce renderer.

FlattenException::createFromThrowable() décide, dans cet ordre :

Exception levée Statut
implémente HttpExceptionInterface celui qu'elle porte
implémente RequestExceptionInterface 400
toute autre 500

La documentation omet la deuxième ligne. Cinq exceptions de HttpFoundation l'implémentent et donnent un 400 : BadRequestException, SuspiciousOperationException, ConflictingHeadersException, SessionNotFoundException et JsonException, que lève getPayload() sur un body invalide.

Avec capture applicable, kernel.exception offre aux listeners la possibilité de fournir une Response ; sans réponse, l'exception remonte. $catch=false ou une Error non prise en charge peut éviter cet événement. Une panne pendant le boot ou l'envoi ne suit pas nécessairement le chemin du contrôleur.

🌍 In Real Life

La situation : le bureau classe les incidents : demande illisible, dossier absent, panne interne. Employer la même étiquette pour tous empêche le destinataire de comprendre s'il doit corriger sa demande ou attendre une réparation.

L’équivalent dans Symfony : lors de l'aplatissement standard décrit ici, HttpExceptionInterface fournit son statut ; sinon RequestExceptionInterface conduit à 400 ; le cas restant utilise 500 par défaut. La classe HttpFoundation JsonException appartient au deuxième cas.

Retour à la réalité technique : ce classement concerne ce chemin de conversion, pas tous les Throwable dans toute configuration. Capture, listeners et renderer déterminent si une Response sera produite. Le code numérique PHP d'une exception ordinaire n'est pas automatiquement son statut HTTP.

🧠 Comment le mémoriser : « Classer la cause avant d'écrire le statut. » Image mentale : trois bacs d'incidents. Question-réflexe : quelle interface porte cette exception et quel traitement l'a reçue ?

⚠️ À ne pas confondre : JSON illisible, données décodées mais invalides et panne serveur ; statut et format du corps de réponse.

Personnaliser la page

Pour /blog/999, la page publique peut proposer un retour au blog sans révéler comment le catalogue est organisé. Le renderer reçoit une représentation de l'erreur, pas l'ArticleView que le contrôleur espérait trouver. Le template doit donc rester utilisable lorsque cette donnée métier est absente.

Un template d'erreur personnalise la présentation HTML d'une réponse en échec. Il ne déclenche pas l'erreur lui-même et ne remplace pas le choix du statut HTTP. Une page publique peut expliquer l'échec et proposer une navigation simple sans exposer la trace technique ; un template générique évite un fichier par code, tandis qu'un template 404 permet un message plus précis.

On surcharge les templates de TwigBundle dans templates/bundles/TwigBundle/Exception/. Pour une 404, TwigErrorRenderer cherche error404.html.twig, puis error.html.twig, puis passe la main au rendu HTML intégré, HtmlErrorRenderer. Un file par statut n'est donc pas nécessaire. Ces templates ne servent qu'au HTML.

Le template reçoit status_code, status_text et exception. La documentation présente exception comme l'exception levée ; le code passe une FlattenException, une class autonome qui n'étend pas Exception. exception.message fonctionne, un test sur la class d'origine échoue. Ne jamais afficher exception.traceAsString à un user final.

Comment, étape par étape ?

  1. Écrire le fichier générique ou celui du statut voulu.
  2. Utiliser des données disponibles même si le traitement normal a échoué tôt.
  3. Garder les détails techniques dans les dispositifs de diagnostic, pas dans la page publique.
  4. Tester sans debug ou avec la prévisualisation prévue : la page de diagnostic de développement suit un autre choix de rendu.

Exemple concret Twig

Contenu de templates/bundles/TwigBundle/Exception/error404.html.twig :

<h1>{{ status_code }} — Page introuvable</h1>
<p>La ressource demandée n'est pas disponible.</p>
<p><a href="/">Revenir à l'accueil du site</a></p>

Le chemin racine est ici un choix explicite de cet exemple, à adapter si l'application est déployée sous un préfixe. Contre-exemple : afficher exception.traceAsString ou supposer qu'exception est exactement l'objet Throwable levé. Afficher plutôt un message utilisateur et les données de statut : FlattenException transporte une représentation de l'erreur, pas son identité PHP originale.

🌍 In Real Life

La situation : le bureau prépare un avis public à partir d'une fiche résumant l'incident. Il choisit un modèle spécifique si disponible, sinon un modèle général ; il ne publie pas le carnet technique interne.

L’équivalent dans Symfony : TwigErrorRenderer cherche le template du statut, puis le générique, avant le rendu HTML de secours. Le template reçoit les données de statut et une FlattenException, représentation de l'erreur.

Retour à la réalité technique : la représentation n'est pas le Throwable original et ne devient pas automatiquement sûre à publier. Le template change la présentation HTML, pas la cause ni le statut. Il doit fonctionner sans l'article absent et sans divulguer message technique ou trace ; les réponses JSON relèvent d'un autre rendu.

🧠 Comment le mémoriser : « Un avis public, pas le carnet d'incident. » Image mentale : résumé destiné au visiteur devant un dossier technique fermé. Question-réflexe : quelles données sont disponibles et réellement publiables ici ?

⚠️ À ne pas confondre : FlattenException et exception d'origine ; fichier nommé 404 et Response réellement dotée du statut 404.

Deux pièges

À retenir en priorité
  1. Le mode debug change le rendu d'erreur.
  2. Les routes /_error permettent une prévisualisation dédiée.

Teste séparément /blog/999 et une URL sans route. La première peut avoir atteint les listeners de sécurité puis l'action ; la seconde peut échouer plus tôt. Une page d'erreur commune ne doit pas supposer que le contexte utilisateur a été initialisé dans les deux cas.

En développement, le mode debug fait sauter le template : la grande page d'exception s'affiche. Pour prévisualiser, on importe en when@dev les routes de FrameworkBundle sous le préfixe /_error : /_error/404, ou /_error/404.json pour un autre format.

Une 404 peut précéder la sécurité. Quand le routeur ne trouve aucune route, le firewall n'a pas nécessairement initialisé l'utilisateur. Une 404 levée plus tard dans un contrôleur n'implique pas la même situation. Construire une page qui fonctionne sans utilisateur, plutôt que supposer sa présence ou son absence.

🌍 In Real Life

La situation : une erreur peut être constatée dès la porte, avant l'identification du visiteur, ou plus tard au guichet. La notice commune doit aider dans les deux cas, sans exiger une fiche nominative déjà ouverte.

L’équivalent dans Symfony : une 404 de routage peut précéder l'initialisation du contexte de sécurité ; une 404 levée dans le contrôleur survient ailleurs dans le cycle. Le template commun ne doit pas supposer qu'un utilisateur est disponible.

Retour à la réalité technique : le point d'échec compte, sans prouver universellement la présence ou l'absence d'une identité. Le rendu debug remplace normalement la page publique ; les routes de prévisualisation configurées permettent de tester celle-ci, mais ne reproduisent pas tous les états d'un échec réel.

🧠 Comment le mémoriser : « La notice doit fonctionner dès la porte. » Image mentale : panneau lisible avant le guichet d'identification. Question-réflexe : que reste-t-il disponible si la requête échoue très tôt ?

⚠️ À ne pas confondre : prévisualisation du rendu et test de tout le chemin d'exception ; identité disponible et droit accordé.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • throw devant createNotFoundException() ; défaut 'Not Found'.
  • Statut : HTTP → le sien ; RequestExceptionInterface → 400 ; sinon 500.
  • Templates pour une 404 : error404.html.twig → error.html.twig → rendu intégré.
  • exception = une FlattenException, pas l'exception levée.
  • Debug : page d'exception ; /_error/404 pour prévisualiser.
  • Contexte de sécurité non garanti, notamment lors d'une 404 de routage.

Repère : « Le helper construit ; throw interrompt ». Une Response explicitement construite avec le statut 404 reste possible sans exception ; le slogan ne doit pas l'exclure.
