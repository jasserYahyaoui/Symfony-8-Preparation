Objectif

Produire un 404 depuis un controller, savoir quel statut produit une exception, et personnaliser la page affichée.

L'essentiel

À comprendre

À retenir en priorité
  1. Le helper construit l'exception.
  2. throw interrompt le controller et déclenche le traitement HTTP.

createNotFoundException() construit une NotFoundHttpException : sans throw, rien ne se passe. Le statut d'une exception se décide en trois lignes — celui d'une exception HTTP, 400 pour une RequestExceptionInterface, sinon 500. La page se personnalise par des templates Twig, qui reçoivent une FlattenException. Le rendu debug remplace normalement ces templates ; une 404 de routage peut survenir avant l'initialisation du contexte de sécurité.

Le schéma

À retenir en priorité
  1. La personnalisation ne requiert pas un template par statut.
  2. Le template reçoit une FlattenException, pas l'exception originale.

Bleu = données et rendu ; ambre = décision. C'est le chemin HTML standard après traitement de l'exception, sans listener applicatif remplaçant la réponse. Lever une exception ne signifie pas que son message doit être publié : préférer un texte public générique à un détail technique.

L'exemple

Exemple concret

use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

interface ProductCatalog
{
    public function find(int $id): ?object;
}

final class ProductController extends AbstractController
{
    public function __construct(private ProductCatalog $catalog) {}

    #[Route('/product/{id}', requirements: ['id' => '\d+'])]
    public function show(int $id): Response
    {
        $product = $this->catalog->find($id);
        if (null === $product) {
            throw $this->createNotFoundException('The product does not exist');
        }
        return $this->render('product/show.html.twig', ['product' => $product]);
    }
}

L'application fournit une implémentation du contrat ProductCatalog, le template indiqué et l'enregistrement du contrôleur. Aucune persistance particulière n'est requise par cet exemple.

Produire le 404

Le mot important est throw. createNotFoundException() construit et retourne l'exception ; elle ne la lève pas. Sans throw, le controller continue ; le statut dépend alors de la réponse réellement retournée. Sans argument, le message vaut 'Not Found'.

Préparer un drapeau « introuvable » n'est pas le lever. createNotFoundException() prépare l'object ; throw déclenche le signal que le kernel transforme en page d'erreur.

Repère — Quel statut pour quelle exception : No. RequestExceptionInterface errors become 400. HttpExceptionInterface porte son propre statut. Une Request malformée peut produire 400 plutôt que 500.

Quel statut pour quelle exception

À retenir en priorité
  1. HttpExceptionInterface porte son propre statut.
  2. Une Request malformée peut produire 400 plutôt que 500.

FlattenException::createFromThrowable() décide, dans cet ordre :

Exception levée Statut
implémente HttpExceptionInterface celui qu'elle porte
implémente RequestExceptionInterface 400
toute autre 500

La documentation omet la deuxième ligne. Cinq exceptions de HttpFoundation l'implémentent et donnent un 400 : BadRequestException, SuspiciousOperationException, ConflictingHeadersException, SessionNotFoundException et JsonException, que lève getPayload() sur un body invalide.

Personnaliser la page

Un template d'erreur personnalise la présentation HTML d'une réponse en échec. Il ne déclenche pas l'erreur lui-même et ne remplace pas le choix du statut HTTP. Une page publique peut expliquer l'échec et proposer une navigation simple sans exposer la trace technique ; un template générique évite un fichier par code, tandis qu'un template 404 permet un message plus précis.

On surcharge les templates de TwigBundle dans templates/bundles/TwigBundle/Exception/. Pour une 404, TwigErrorRenderer cherche error404.html.twig, puis error.html.twig, puis passe la main au rendu HTML intégré, HtmlErrorRenderer. Un file par statut n'est donc pas nécessaire. Ces templates ne servent qu'au HTML.

Le template reçoit status_code, status_text et exception. La documentation présente exception comme l'exception levée ; le code passe une FlattenException, une class autonome qui n'étend pas Exception. exception.message fonctionne, un test sur la class d'origine échoue. Ne jamais afficher exception.traceAsString à un user final.

Comment, étape par étape ?

  1. Écrire le fichier générique ou celui du statut voulu.
  2. Utiliser des données disponibles même si le traitement normal a échoué tôt.
  3. Garder les détails techniques dans les dispositifs de diagnostic, pas dans la page publique.
  4. Tester sans debug ou avec la prévisualisation prévue : la page de diagnostic de développement suit un autre choix de rendu.

Exemple concret Twig

Contenu de templates/bundles/TwigBundle/Exception/error404.html.twig :

<h1>{{ status_code }} — Page introuvable</h1>
<p>La ressource demandée n'est pas disponible.</p>
<p><a href="/">Revenir à l'accueil du site</a></p>

Le chemin racine est ici un choix explicite de cet exemple, à adapter si l'application est déployée sous un préfixe. Contre-exemple : afficher exception.traceAsString ou supposer qu'exception est exactement l'objet Throwable levé. Afficher plutôt un message utilisateur et les données de statut : FlattenException transporte une représentation de l'erreur, pas son identité PHP originale.

Deux pièges

À retenir en priorité
  1. Le mode debug change le rendu d'erreur.
  2. Les routes /_error permettent une prévisualisation dédiée.

En développement, le mode debug fait sauter le template : la grande page d'exception s'affiche. Pour prévisualiser, on importe en when@dev les routes de FrameworkBundle sous le préfixe /_error : /_error/404, ou /_error/404.json pour un autre format.

Une 404 peut précéder la sécurité. Quand le routeur ne trouve aucune route, le firewall n'a pas nécessairement initialisé l'utilisateur. Une 404 levée plus tard dans un contrôleur n'implique pas la même situation. Construire une page qui fonctionne sans utilisateur, plutôt que supposer sa présence ou son absence.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • throw devant createNotFoundException() ; défaut 'Not Found'.
  • Statut : HTTP → le sien ; RequestExceptionInterface → 400 ; sinon 500.
  • Templates pour une 404 : error404.html.twig → error.html.twig → rendu intégré.
  • exception = une FlattenException, pas l'exception levée.
  • Debug : page d'exception ; /_error/404 pour prévisualiser.
  • Contexte de sécurité non garanti, notamment lors d'une 404 de routage.

Moyen mnémotechnique : « Sans throw, pas de 404 ».
