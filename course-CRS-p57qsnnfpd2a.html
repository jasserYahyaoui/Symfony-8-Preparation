Objectif

Produire un 404 depuis un controller, savoir quel statut produit une exception, et personnaliser la page affichée.

L'essentiel

À comprendre

À retenir en priorité
  1. Le helper construit l'exception.
  2. throw interrompt le controller et déclenche le traitement HTTP.

createNotFoundException() construit une NotFoundHttpException : sans throw, rien ne se passe. Le statut d'une exception se décide en trois lignes — celui d'une exception HTTP, 400 pour une RequestExceptionInterface, sinon 500. La page se personnalise par des templates Twig, qui reçoivent une FlattenException, et sont utilisées en mode non-debug ; une page d'erreur ne doit pas supposer qu'un utilisateur est disponible.

Le schéma

À retenir en priorité
  1. La personnalisation ne requiert pas un template par statut.
  2. Le template reçoit une FlattenException, pas l'exception originale.

L'exemple

Exemple concret

class Example05d29581
{
    #[Route('/product/{id}')]
    public function show(int $id): Response
    {
        $product = $this->catalog->find($id);
        if (null === $product) {
            throw $this->createNotFoundException('The product does not exist');
        }
        // ...
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Produire le 404

Le mot important est throw. createNotFoundException() construit et retourne l'exception ; elle ne la lève pas. Sans throw, le controller continue et la page s'affiche normalement, en 200. Sans argument, le message vaut 'Not Found'.

Préparer un drapeau « introuvable » n'est pas le lever. createNotFoundException() prépare l'object ; throw déclenche le signal que le kernel transforme en page d'erreur.

Repère — Quel statut pour quelle exception : No. RequestExceptionInterface errors become 400. HttpExceptionInterface porte son propre statut. Une Request malformée peut produire 400 plutôt que 500.

Quel statut pour quelle exception

À retenir en priorité
  1. HttpExceptionInterface porte son propre statut.
  2. Une Request malformée peut produire 400 plutôt que 500.

FlattenException::createFromThrowable() décide, dans cet ordre :

Exception levée Statut
implémente HttpExceptionInterface celui qu'elle porte
implémente RequestExceptionInterface 400
toute autre 500

La documentation omet la deuxième ligne. Cinq exceptions de HttpFoundation l'implémentent et donnent un 400 : BadRequestException, SuspiciousOperationException, ConflictingHeadersException, SessionNotFoundException et JsonException, que lève getPayload() sur un body invalide.

Personnaliser la page

À comprendre

C'est quoi ?

Un template d'erreur personnalise la présentation HTML d'une réponse en échec. Il ne déclenche pas l'erreur lui-même et ne remplace pas le choix du statut HTTP. Le rendu cherche d'abord le fichier du statut, puis un fichier générique.

À quoi ça sert ?

Une page publique peut expliquer l'échec et proposer une navigation simple sans exposer la trace technique. Un template générique évite de créer un fichier pour chaque code, tandis qu'un template 404 permet un message plus précis.

Où dans Symfony ?

Placer error404.html.twig dans templates/bundles/TwigBundle/Exception/. Le repli est error.html.twig dans le même répertoire, puis le renderer HTML intégré. Twig reçoit status_code, status_text et exception, qui est une FlattenException préparée pour le rendu. Cette personnalisation concerne HTML, pas toute réponse JSON.

Comment, étape par étape ?

  1. Écrire le fichier générique ou celui du statut voulu.
  2. Utiliser des données disponibles même si le traitement normal a échoué tôt.
  3. Garder les détails techniques dans les dispositifs de diagnostic, pas dans la page publique.
  4. Tester sans debug ou avec la prévisualisation prévue : la page de diagnostic de développement suit un autre choix de rendu.

Exemple concret Twig

Contenu de templates/bundles/TwigBundle/Exception/error404.html.twig :

<h1>{{ status_code }} — Page introuvable</h1>
<p>La ressource demandée n'est pas disponible.</p>
<p><a href="/">Revenir à l'accueil du site</a></p>

Le chemin racine est ici un choix explicite de cet exemple, à adapter si l'application est déployée sous un préfixe. Contre-exemple : afficher exception.traceAsString ou supposer qu'exception est exactement l'objet Throwable levé. Correction : afficher un message utilisateur et les données de statut ; FlattenException transporte une représentation de l'erreur, pas son identité PHP originale.

Passage canonique conservé

Personnaliser la page

On surcharge les templates de TwigBundle dans templates/bundles/TwigBundle/Exception/. TwigErrorRenderer cherche error404.html.twig, puis error.html.twig, puis passe la main au rendu HTML intégré, HtmlErrorRenderer. Un file par statut n'est donc pas nécessaire. Ces templates ne servent qu'au HTML.

Le template reçoit status_code, status_text et exception. La documentation présente exception comme l'exception levée ; le code passe une FlattenException, une class autonome qui n'étend pas Exception. exception.message fonctionne, un test sur la class d'origine échoue. Ne jamais afficher exception.traceAsString à un user final.

Deux pièges

Piège à éviter

À retenir en priorité
  1. Le mode debug change le rendu d'erreur.
  2. Les routes /_error permettent une prévisualisation dédiée.

C'est quoi ?

Une réponse 404 indique qu'une ressource n'a pas été trouvée. Elle peut résulter de l'absence de route ou d'une décision du controller après résolution de la route. Ces deux moments du cycle ne garantissent pas le même état des services liés à la Request.

À quoi ça sert ?

Une page d'erreur doit fonctionner même lorsque le parcours normal a été interrompu tôt. Elle ne doit pas dépendre systématiquement d'un utilisateur authentifié, d'une route courante ou d'une ressource métier précisément absente.

Où dans Symfony ?

Le rendu d'erreur en mode debug privilégie la page de diagnostic ; il ne valide pas à lui seul le template de production. Pour HTML, les surcharges se placent dans templates/bundles/TwigBundle/Exception/, avec error404.html.twig, puis un repli vers error.html.twig. L'objet exception exposé au template est une FlattenException, pas nécessairement l'instance Throwable originale.

Comment, étape par étape ?

  1. Dans l'action, lever réellement l'exception : createNotFoundException la construit seulement.
  2. Écrire une page d'erreur dont les données essentielles sont status_code et status_text.
  3. Prévisualiser le rendu adapté via les routes de développement prévues, puis vérifier un vrai cas d'erreur sans debug.
  4. Tester une route introuvable et une ressource introuvable dans une route valide. Lorsque le routage échoue avant le firewall, l'authentification n'a pas nécessairement été établie ; cela ne signifie pas que Security est indisponible sur toute 404 possible.

Exemple concret PHP

Dans une action d'un controller étendant AbstractController, avec une collection locale pour rendre le cas reproductible :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function show(string $slug): \Symfony\Component\HttpFoundation\Response
{
    $articles = ['introduction' => 'Bienvenue'];
    if (!array_key_exists($slug, $articles)) {
        throw $this->createNotFoundException('Article introuvable.');
    }

    return new \Symfony\Component\HttpFoundation\Response($articles[$slug]);
}

Pour le slug absent, l'action s'interrompt et le traitement d'exception prend le relais. Contre-exemple : supprimer throw : l'objet exception est créé puis ignoré, et l'exécution continue. Correction : le lever. Dans le template public, ne pas afficher une trace technique ni compter sur exception instanceof la classe d'origine ; utiliser un message utilisateur adapté et les données de statut.

Passage canonique conservé

Deux pièges

En développement, le mode debug fait sauter le template : la grande page d'exception s'affiche. Pour prévisualiser, on importe en when@dev les routes de FrameworkBundle sous le préfixe /_error : /_error/404, ou /_error/404.json pour un autre format.

Le statut 404 ne décrit pas à lui seul l'état de security. Un échec du routage peut survenir avant l'initialisation du contexte de sécurité : le template doit tolérer l'absence d'utilisateur. Une 404 levée dans une action après le passage du firewall n'implique pas automatiquement une déconnexion.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • throw devant createNotFoundException() ; défaut 'Not Found'.
  • Statut : HTTP → le sien ; RequestExceptionInterface → 400 ; sinon 500.
  • Templates : error404.html.twig → error.html.twig → rendu intégré.
  • exception = une FlattenException, pas l'exception levée.
  • Debug : page d'exception ; /_error/404 pour prévisualiser.
  • 404 de routage : contexte de security potentiellement absent ; 404 d'action après firewall : pas de déconnexion automatique. Template robuste dans les deux cas.

Moyen mnémotechnique : « Sans throw, pas de 404 ».
