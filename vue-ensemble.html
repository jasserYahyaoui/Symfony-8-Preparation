Une URL ne suffit pas

Vous savez lire du PHP orienté objet, mais vous ne voyez pas encore comment les classes Symfony coopèrent ? Ce parcours prépare Symfony 8.0, les API PHP jusqu’à 8.4 et Twig jusqu’à 3.22. Symfony 8 exige PHP 8.4 minimum pour s’exécuter : le périmètre d’examen n’est pas une compatibilité avec PHP 8.3.

Notre navigateur demande GET /blog/42. L’application doit comprendre le message, choisir une action, lui fournir les bonnes données, lire l’article, puis construire et envoyer une réponse. Une URL ne construit ni un contrôleur ni son catalogue d’articles. Nous allons attribuer chaque décision à son vrai responsable, puis examiner ce qui change si l’article manque.

Le blog pédagogique utilise ArticleView pour représenter un article et un service ArticleCatalog avec des données en mémoire : 42 existe, 999 manque. Ce n’est pas l’application qui sert ce site statique. Aucune base de données n’est nécessaire pour suivre le premier trajet.

🌍 In Real Life

La situation : au restaurant, demander le numéro 42 ne dit pas encore qui préparera ni comment le résultat arrivera.

L’équivalent dans Symfony : client → navigateur ; demande consignée → Request ; consultation du catalogue → appel à ArticleCatalog ; résultat préparé → Response.

Retour à la réalité technique : Request et Response représentent des messages HTTP. L’application choisit et exécute les opérations entre les deux. Ici, les données sont en mémoire : ni base ni cuisine physique à reconstituer.

🧠 Comment le mémoriser : « Le numéro désigne, le code réalise. » Image : un bon 42 face à plusieurs postes. Réflexe : « Qui transforme cette entrée en résultat ? »

⚠️ À ne pas confondre : construire la Response ne l’envoie pas au navigateur.

Application, bundles et composants

BlogController et ArticleCatalog appartiennent à notre application. HttpFoundation fournit les objets Request et Response. HttpKernel organise leur traitement ; Routing sait comparer un chemin aux routes déclarées. FrameworkBundle raccorde ces composants avec des services et de la configuration. Symfony Flex aide à installer/configurer des paquets ; il ne participe pas à chaque requête.

Les flèches ne signifient pas « exécuter ensuite ». Un composant peut être utilisé seul si vous assemblez ses dépendances. Un bundle est une intégration à l’application ; un bridge adapte une autre bibliothèque. Aucun de ces mots ne désigne automatiquement le parent PHP d’un contrôleur.

🌍 In Real Life

La situation : un restaurant choisit ses équipements et les raccorde avant d’accueillir les commandes.

L’équivalent dans Symfony : établissement avec ses choix → application ; équipement spécialisé → composant ; installation intégrée → bundle ; adaptateur entre équipements → bridge ; raccordement commun → FrameworkBundle.

Retour à la réalité technique : un composant est une bibliothèque réutilisable ; un bundle l’intègre à l’application, un bridge adapte une autre bibliothèque. Ce sont des relations d’assemblage, pas des étapes successives de GET. Flex aide à installer/configurer les paquets, hors traitement de chaque demande.

🧠 Comment le mémoriser : « L’équipement n’est pas son installation. » Image : appareil, raccord et plan d’ensemble. Réflexe : « Est-ce une bibliothèque, une intégration ou une adaptation ? »

⚠️ À ne pas confondre : HttpFoundation fournit les objets HTTP ; HttpKernel orchestre leur traitement.

Approfondissez composants et bridges puis Kernel, HttpKernel et FrameworkBundle.

Ce que prépare le conteneur

Le contrôleur veut consulter ArticleCatalog, pas choisir comment le construire. Une définition décrit sa construction. L’autowiring peut déduire une référence à partir d’un type ; l’autoconfiguration peut ajouter des métadonnées, comme des tags, selon les règles activées. L’une ne remplace pas l’autre.

Compiler le plan n’instancie pas tous les services. Le plan n’est pas recompilé à chaque GET ; une instance partagée n’est pas une promesse de nouvelle instance par requête, notamment dans un processus long. Les arguments du constructeur sont distincts des arguments de l’action, résolus pendant son traitement HTTP.

🌍 In Real Life

La situation : le plan de cuisine indique les équipements nécessaires à chaque poste ; on ne refait pas ce plan à chaque commande.

L’équivalent dans Symfony : fiche de montage → définition ; raccord choisi selon le besoin → autowiring ; rôle marqué sur la fiche → autoconfiguration ; plan vérifié → compilation ; équipement fourni → instance de service.

Retour à la réalité technique : le conteneur fournit les services selon leurs définitions. Compiler transforme le graphe de définitions sans instancier tous les objets. Une instance partagée dépend de la durée de vie du conteneur, pas du nombre de clients.

🧠 Comment le mémoriser : « Préparer le plan, puis fournir l’objet. » Image : plan mural et poste équipé. Réflexe : « Suis-je à la compilation ou à l’exécution ? »

⚠️ À ne pas confondre : autowiring = dépendances ; autoconfiguration = règles de configuration, notamment tags.

Lire le conteneur et l’autowiring.
