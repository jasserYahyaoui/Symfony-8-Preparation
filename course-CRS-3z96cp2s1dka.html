Objectifs d’apprentissage

  • Séparer le role des normalizers de celui des encoders et prévoir la forme normalisée (array, string, scalaire)
  • Savoir que plusieurs normalizers interviennent mais un seul encoder par opération
  • Connaître ce que la normalization d'objects retient par défaut et comment l'exclure
  • Prévoir l'effet d'une demande de group sur une property qui n'en déclare aucun
  • Connaître le traitement des références circulaires et son seuil par défaut
  • Prévoir quel normalizer traite une valeur selon leur ordre, et écrire un normalizer dédié
  • Prévoir la denormalization — contrôle des types selon l'extractor, erreurs collectées, object à remplir
  • Régler un appel par le contexte — valeurs nulles omises, format des dates

Objectif

Savoir en quoi se décompose une serialization, et prévoir ce qui figure ou non dans le résultat.

L'essentiel

À comprendre

À retenir en priorité
  1. Le normalizer choisit la représentation.
  2. L'encoder produit le format.

Une serialization se fait en deux étapes : un normalizer change la valeur PHP en représentation normalisée, un encoder change celle-ci en format. Le normalizer décide de tout ce qui compte à l'examen — quelles properties sortent, sous quel nom, avec quelle valeur ; l'encoder ne sait que produire et lire un format. Les bridges vers des services tiers sont hors programme.

Le schéma

À retenir en priorité
  1. Le decoder lit la syntaxe.
  2. Le denormalizer construit la valeur PHP.

L'exemple : une vue publique

Exemple concret

À retenir en priorité
  1. Les groups filtrent selon l'usage.
  2. Les metadata doivent être chargées.

Supposons que $serializer soit le service configuré du framework, que $person existe avec ses métadonnées de groups, et que Order et $existingOrder soient déjà définis. Ce sont les prérequis de cet extrait, pas des objets qu’il construit. Voir choisir les propriétés selon le contexte pour le group public-view. Le premier appel produit le JSON des propriétés de ce group ; le second met à jour qty à 7 sur l’instance fournie, si cette propriété est accessible au normalizer. L’option OBJECT_TO_POPULATE réutilise cet objet.

$json = $serializer->serialize($person, 'json', ['groups' => 'public-view']);

$order = $serializer->deserialize('{"qty":7}', Order::class, 'json', [
    AbstractNormalizer::OBJECT_TO_POPULATE => $existingOrder,
]);

Deux étapes, deux responsabilités

À comprendre

À retenir en priorité
  1. La représentation dépend du normalizer.
  2. Array n'est pas une obligation universelle.
  3. BackedEnumNormalizer conserve le backing type : int|string, pas toujours string.

C'est quoi ?

La normalisation transforme une valeur PHP en une représentation utilisable par un encoder. L'encodage produit le format de sortie, comme JSON. Le trajet inverse commence par décoder la syntaxe, puis dénormalise les valeurs obtenues vers les types PHP demandés.

À quoi ça sert ?

Séparer les étapes permet de distinguer une erreur de JSON d'une erreur de type métier. Cela évite aussi de croire que choisir JSON décide quelles propriétés d'un objet sont exposées.

Où dans Symfony ?

Un Serializer compose des normalizers et des encoders. Le premier normalizer capable de traiter la valeur est sélectionné ; un normalizer générique placé trop tôt peut prendre la place d'un normalizer spécialisé. Un objet imbriqué peut nécessiter d'autres normalizers pendant le parcours.

Comment, étape par étape ?

  1. Donner la valeur et le format au Serializer.
  2. Sélectionner la normalisation appropriée à la valeur et au contexte.
  3. Encoder la représentation normalisée.
  4. Dans l'autre sens, décoder d'abord puis dénormaliser vers la classe cible. Ne pas inverser ces deux étapes.

Exemple concret PHP

Avec Serializer installé, exemple limité à une date et JSON :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\DateTimeNormalizer;
use Symfony\Component\Serializer\Serializer;

$serializer = new Serializer([new DateTimeNormalizer()], [new JsonEncoder()]);
$date = new DateTimeImmutable('2026-01-02T03:04:05+00:00');
$normalized = $serializer->normalize($date, null, ['datetime_format' => 'Y-m-d']);
$json = $serializer->serialize($date, 'json', ['datetime_format' => 'Y-m-d']);
var_dump($normalized, $json);

La représentation normalisée est la string 2026-01-02. Le JSON contient cette valeur entre guillemets JSON : la normalisation n'a donc pas nécessairement produit un tableau. Contre-exemple : imposer partout un retour array à un normalizer de date ou d'enum backed. Correction : respecter le contrat de représentation ; une enum backed produit sa valeur int ou string selon son backing type.

Un normalizer personnalisé déclare ses types pris en charge et implémente son contrat ; annoncer une décision de support toujours réutilisable alors qu'elle dépend du contexte peut entraîner une mauvaise sélection. Une configuration standalone doit construire ses dependencies : elle n'hérite pas automatiquement des réglages du service Serializer du framework.

Deux étapes, deux responsabilités

La représentation normalisée n'est pas toujours un array :

Valeur Normalizer JSON
object ordinaire ObjectNormalizer → array {"name":"Ada"}
DateTimeImmutable DateTimeNormalizer → string RFC 3339 "2026-01-02T03:04:05+00:00"
enum backed 'H' BackedEnumNormalizer → string "H"
l'int 42 aucun 42

Le service par défaut compose une liste triée de normalizers et un seul encoder par opération. Encoders fournis : JSON, XML, CSV, YAML — ['k' => 'v'] donne {"k":"v"}, <response><k>v</k></response>, k puis v sur deux lignes, { k: v }. Un format sans encoder lève une UnsupportedFormatException.

Ce qui est pris par défaut

À retenir en priorité
  1. La lecture suit les propriétés accessibles et accessors reconnus.
  2. La visibilité et les méthodes influencent l'output.

ObjectNormalizer lit l'object par l'accès aux properties :

Membre Dans l'output
property publique oui
property privée avec getWithGetter() oui, sous withGetter
isActive(), hasKids(), canFly() oui : active, kids, fly
property protégée ou privée sans accessor non
fetchThing() non : préfixe inconnu

#[Ignore] exclut une property ou une method partout.

Choisir selon le contexte

Exemple concret

À retenir en priorité
  1. Les deux systèmes de groups diffèrent.
  2. Ne pas transposer le défaut du Validator.

C'est quoi ?

Un serialization group sélectionne les propriétés exposées pour un usage. Sans sélection de groupes, ObjectNormalizer lit les propriétés et accessors accessibles selon ses règles ; une méthode de lecture peut donc contribuer à la représentation même sans propriété publique correspondante.

À quoi ça sert ?

Une vue publique peut présenter le nom d'un objet sans publier tous ses champs internes. Cette sélection évite de confondre facilité d'accès PHP et intention de publication.

Où dans Symfony ?

Les attributes Groups et Ignore nécessitent des metadata chargées. Le service du framework configure cette intégration ; créer new ObjectNormalizer() à la main ne fournit pas automatiquement une factory de metadata.

Comment, étape par étape ?

  1. Définir les groupes sur les propriétés ou accessors concernés.
  2. Configurer le chargement de ces metadata, explicitement en standalone.
  3. Passer les groupes souhaités dans le contexte de l'appel.
  4. Tester les champs absents autant que ceux présents. Le groupe Default implicite du Validator ne doit pas être transposé au Serializer ; * sélectionne tous les groupes, y compris les propriétés sans groupe selon les règles de sélection.

Exemple concret PHP

Avec Serializer et PropertyAccess installés :

<?php
use Symfony\Component\Serializer\Attribute\Groups;
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Mapping\Factory\ClassMetadataFactory;
use Symfony\Component\Serializer\Mapping\Loader\AttributeLoader;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class PublicProfile
{
    #[Groups(['public'])]
    public string $name = 'Ada';
    public string $internalNote = 'À vérifier';
}
$metadata = new ClassMetadataFactory(new AttributeLoader());
$serializer = new Serializer([new ObjectNormalizer($metadata)], [new JsonEncoder()]);
echo $serializer->serialize(new PublicProfile(), 'json', ['groups' => ['public']]);

La sortie attendue ne contient que name. Contre-exemple : retirer la factory en supposant que les attributes suffisent à eux seuls. Correction : fournir le loader de metadata ou utiliser le service déjà configuré du framework. Un #[Ignore] est une exclusion explicite, pas un simple groupe oublié. Les groups structurent la représentation ; ils ne remplacent ni l'autorisation d'accéder à l'objet ni la validation des données entrantes.

Choisir selon le contexte

Les groups excluent ici et gardent ailleurs. Avec name et fullName dans public-view, age dans admin-view, email sans group :

Contexte Sortie
aucun group les quatre
'groups' => 'public-view' name, fullName
'groups' => '*' les quatre
'groups' => ['Default'] rien

Pas de group Default implicite, contrairement au Validator : * seul reprend les properties sans group.

Groups, #[Ignore] et #[SerializedName] (qui renomme dans le format seul) sont des métadonnées. Le service serializer du framework les lit ; un ObjectNormalizer construit sans fabrique de métadonnées les ignore — groups demandés, toutes les properties sortent, y compris celle marquée #[Ignore]. De même, sans MetadataAwareNameConverter, fullName n'est pas renommé.

Quel normalizer agit ?

Exemple concret

À retenir en priorité
  1. L'ordre peut changer la représentation.
  2. Le normalizer générique doit laisser passer les cas spécialisés.

C'est quoi ?

Un normalizer dédié transforme un type PHP précis en une représentation choisie par l'application. Le support signifie ici « cette classe sait-elle traiter cette valeur, pour ce format et ce contexte ? ». Ce choix précède l'encodage JSON ; il ne valide pas à lui seul une entrée métier.

À quoi ça sert ?

Un montant peut être représenté par 12.50 EUR plutôt que par toutes ses propriétés publiques. L'objet reste un montant : seule sa représentation change. Le type Money ci-dessous est volontairement limité à des centimes d'euro non négatifs ; ce n'est pas un modèle monétaire universel ni un formatage localisé.

Où dans Symfony ?

NormalizerInterface en Symfony 8.0 impose trois méthodes, toutes implémentées avec leurs signatures exactes dans l'exemple :

  • normalize() produit la représentation. Son contrat autorise tableau, scalaire, ArrayObject ou null ; notre implémentation produit une string.
  • supportsNormalization() répond pour une valeur, un format et un contexte. Elle doit fonctionner même sans appel préalable à getSupportedTypes().
  • getSupportedTypes(?string $format) annonce les types potentiellement traités et si la décision de support est mémorisable. true signifie décision réutilisable pour ce type/format ; false impose de réévaluer le support ; null exclut le type. Ce n'est jamais un cache du montant normalisé.

Comment, étape par étape ?

  1. Définir un type de valeur et sa représentation attendue.
  2. Dans supportsNormalization(), vérifier le type ; n'accepter que les valeurs dont le normalizer respecte le contrat.
  3. Dans normalize(), garder une vérification défensive : un appel direct peut ne pas avoir demandé le support. Une valeur étrangère doit produire une exception explicite, pas une string vide.
  4. Déclarer Money::class => true seulement si la décision ne dépend ni du contenu de l'objet ni du contexte. Le format est fourni à getSupportedTypes() et peut délimiter son annonce.
  5. En standalone, placer le normalizer dédié avant ObjectNormalizer. Dans le framework, enregistrer le service avec l'autoconfiguration ou le tag serializer.normalizer ; les priorités les plus hautes passent d'abord. Vérifier l'ordre effectif plutôt que supposer qu'un service non enregistré sera utilisé.

Exemple concret PHP

Avec Serializer et PropertyAccess 8.0 disponibles et leur autoload chargé, ce programme est complet ; il ne démarre pas de kernel :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Exception\InvalidArgumentException;
use Symfony\Component\Serializer\Normalizer\NormalizerInterface;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final readonly class Money
{
    public function __construct(public int $cents, public string $currency = 'EUR')
    {
        if ($cents < 0 || $currency !== 'EUR') {
            throw new \InvalidArgumentException('Cet exemple accepte des centimes EUR non négatifs.');
        }
    }
}

final class MoneyNormalizer implements NormalizerInterface
{
    public function normalize(mixed $data, ?string $format = null, array $context = []): array|string|int|float|bool|\ArrayObject|null
    {
        if (!$data instanceof Money) {
            throw new InvalidArgumentException('Money attendu.');
        }

        return sprintf('%d.%02d %s', intdiv($data->cents, 100), $data->cents % 100, $data->currency);
    }

    public function supportsNormalization(mixed $data, ?string $format = null, array $context = []): bool
    {
        return $data instanceof Money;
    }

    public function getSupportedTypes(?string $format): array
    {
        return [Money::class => true];
    }
}

$money = new Money(1250);
$dedicatedFirst = new Serializer([new MoneyNormalizer(), new ObjectNormalizer()], [new JsonEncoder()]);
$genericFirst = new Serializer([new ObjectNormalizer(), new MoneyNormalizer()], [new JsonEncoder()]);
echo $dedicatedFirst->serialize(['price' => $money], 'json'), PHP_EOL;
echo $genericFirst->serialize(['price' => $money], 'json'), PHP_EOL;

Les sorties sont respectivement {"price":"12.50 EUR"} et {"price":{"cents":1250,"currency":"EUR"}}. Le premier normalizer qui accepte l'objet le traite ; le second n'est pas un post-traitement automatique. Le calcul utilise division et reste entiers, sans arrondi flottant. Une seconde valeur new Money(7) produit 0.07 EUR : mémoriser le support ne fige pas le premier montant.

(new MoneyNormalizer())->supportsNormalization(new stdClass()) rend faux. Appeler quand même normalize(new stdClass()) lève l'InvalidArgumentException du Serializer ; c'est une erreur d'usage, pas une valeur métier nulle. Dans une chaîne, un autre normalizer peut prendre en charge cet objet : ne pas confondre refus de ce normalizer et refus de tout le Serializer.

Si le support dépend du contexte, il faut changer l'annonce. Voici une variante complète utilisant par composition le normalizer précédent ; conserver les imports et la classe Money du premier bloc :

final class ContextMoneyNormalizer implements NormalizerInterface
{
    public function __construct(private MoneyNormalizer $inner) {}

    public function normalize(mixed $data, ?string $format = null, array $context = []): array|string|int|float|bool|\ArrayObject|null
    {
        if (!$this->supportsNormalization($data, $format, $context)) {
            throw new InvalidArgumentException('Money et contexte money_as_text=true attendus.');
        }

        return $this->inner->normalize($data, $format, $context);
    }

    public function supportsNormalization(mixed $data, ?string $format = null, array $context = []): bool
    {
        return $data instanceof Money && ($context['money_as_text'] ?? false) === true;
    }

    public function getSupportedTypes(?string $format): array
    {
        return [Money::class => false];
    }
}

$contextual = new Serializer([
    new ContextMoneyNormalizer(new MoneyNormalizer()),
    new ObjectNormalizer(),
], [new JsonEncoder()]);
echo $contextual->serialize($money, 'json', ['money_as_text' => true]), PHP_EOL;
echo $contextual->serialize($money, 'json', ['money_as_text' => false]), PHP_EOL;

La même instance de Serializer donne d'abord "12.50 EUR", puis {"cents":1250,"currency":"EUR"}. false dans getSupportedTypes() ne veut donc pas dire « Money interdit » : la décision est recalculée et ObjectNormalizer prend le relais quand le drapeau est faux.

Contre-exemples et corrections. Mettre ObjectNormalizer en premier empêche ici la représentation dédiée : inverser l'ordre. Annoncer true pour le normalizer contextuel est également faux : après un premier appel accepté, le Serializer peut réutiliser cette décision malgré un contexte devenu faux ; notre garde défensive lèverait alors une exception au lieu de choisir ObjectNormalizer. Corriger l'annonce en false, pas supprimer la garde. Cette classe ne dénormalise rien : reconstruire Money depuis des données entrantes demanderait un contrat de dénormalisation et ses validations propres.

Quel normalizer agit ?

Le Serializer confie la valeur au premier normalizer dont supportsNormalization() répond vrai ; getSupportedTypes() évite les appels inutiles.

Ordre price dans le JSON
[MoneyNormalizer, ObjectNormalizer] "12.50 EUR"
[ObjectNormalizer, MoneyNormalizer] {"cents":1250,"currency":"EUR"}

Le framework enregistre ObjectNormalizer à la priority −1000 : un normalizer de l'application, autoconfiguré, passe avant lui.

Dénormaliser

À comprendre

À retenir en priorité
  1. L'identité de l'object est conservée.
  2. Les valeurs absentes peuvent rester inchangées.

C'est quoi ?

Dénormaliser construit ou met à jour une valeur PHP depuis des données déjà décodées. Le contexte précise comment traiter cet appel : types, objet existant, format de date ou options de parcours.

À quoi ça sert ?

On peut distinguer la mise à jour d'un objet existant de la création d'un nouvel objet, sans désactiver les erreurs de type ou considérer toute entrée comme valide.

Où dans Symfony ?

object_to_populate désigne l'objet racine à mettre à jour. deep_object_to_populate étend ce comportement à certains objets enfants existants, pas à une fusion générale des tableaux d'objets. Les extractors de types aident à contrôler ce qui est accepté ; une string numérique n'est pas toujours équivalente à un entier pour le normalizer concerné.

Comment, étape par étape ?

  1. Décoder le document avec l'encoder approprié.
  2. Choisir la classe cible et, si nécessaire, un objet existant.
  3. Dénormaliser avec un contexte explicite et conserver les erreurs utiles.
  4. Pour collecter les erreurs de dénormalisation compatibles, demander leur collecte et traiter PartialDenormalizationException ; l'objet partiel n'est pas pour autant validé ni prêt à persister.

Exemple concret PHP

Avec Serializer et PropertyAccess installés :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class Preferences
{
    public string $locale = 'fr';
    public bool $digest = true;
}
$preferences = new Preferences();
$serializer = new Serializer([new ObjectNormalizer()], [new JsonEncoder()]);
$result = $serializer->deserialize('{"locale":"en"}', Preferences::class, 'json', [
    'object_to_populate' => $preferences,
]);
var_dump($result === $preferences, $preferences->locale, $preferences->digest);

Les valeurs attendues sont vrai, en, vrai : l'identité est conservée et le champ absent n'est pas remis à zéro. Contre-exemple : interpréter cet appel comme un remplacement intégral de tout le graphe ou une validation métier réussie. Correction : définir explicitement la sémantique de mise à jour et valider avant tout effet durable.

Les options de contexte sont propres à leurs normalizers : datetime_format règle DateTimeNormalizer ; skip_null_values peut omettre des valeurs nulles à la normalisation. Leur présence dans un appel ne modifie pas magiquement les types du modèle ni tous les appels suivants. Ne pas désactiver les contrôles de type pour faire disparaître une erreur d'entrée.

Contexte et dénormalisation 8.0.

Passage canonique conservé

Dénormaliser

Le decoder rend ce que porte le format ("H" reste une string) ; le denormalizer en fait Suit::Hearts. Le contrôle des types vient d'un extractor de types, que le service du framework reçoit :

JSON vers int $qty Sans extractor Avec extractor
{"qty":"7"} 7 : PHP convertit NotNormalizableValueException
{"qty":"x"} NotNormalizableValueException idem

COLLECT_DENORMALIZATION_ERRORS rassemble les erreurs dans une PartialDenormalizationException ; #[MapRequestPayload] l'active et en fait des violations. OBJECT_TO_POPULATE remplit le même object : {"qty":7} change qty et laisse note intact.

Le contexte

À retenir en priorité
  1. Le contexte ajuste un appel.
  2. Il ne change pas la donnée d'origine.
  3. MaxDepth déclare la limite dans les metadata.
  4. Le contexte doit activer son application.

Le troisième argument règle un appel : skip_null_values retire les properties nulles, datetime_format à Y-m-d rend "2026-01-02".

#[MaxDepth(n)] décrit une limite de profondeur dans les metadata, mais son respect demande aussi enable_max_depth: true dans le contexte du normalizer. La profondeur et la référence circulaire répondent à deux questions différentes : combien de niveaux parcourir, ou rencontre-t-on à nouveau le même object dans la branche courante ? Une limite de profondeur ne remplace pas automatiquement le traitement d'une référence circulaire.

Documentation Symfony 8.0.

Les références circulaires

Piège à éviter

À retenir en priorité
  1. Une limite supérieure ne résout pas la boucle.
  2. Un handler peut rendre un identifier stable.

C'est quoi ?

Une référence circulaire ramène au même objet dans la branche en cours de normalisation. Une profondeur maximale borne le nombre de niveaux parcourus. Ces deux conditions ne sont pas équivalentes : un long arbre sans boucle peut atteindre une limite de profondeur.

À quoi ça sert ?

Une représentation de sortie doit rester finie même si le modèle contient des relations bidirectionnelles. Choisir une vue ou un identifiant stable exprime une intention plus claire qu'augmenter indéfiniment une limite.

Où dans Symfony ?

circular_reference_limit vaut 1 par défaut. Un handler peut remplacer la référence circulaire par une valeur adaptée. #[MaxDepth] est une metadata qui nécessite aussi l'activation enable_max_depth dans le contexte.

Comment, étape par étape ?

  1. Identifier la relation qui ferme la boucle.
  2. Décider si cette relation doit être exclue de la vue ou représentée par un identifiant.
  3. Configurer un handler qui retourne une valeur finie, pas le même objet à parcourir de nouveau.
  4. Tester séparément boucle réelle et profondeur excessive ; relever un seuil ne supprime pas la boucle.

Exemple concret PHP

Avec Serializer et PropertyAccess installés, cycle volontaire et remplacement par identifiant :

<?php
use Symfony\Component\Serializer\Encoder\JsonEncoder;
use Symfony\Component\Serializer\Normalizer\ObjectNormalizer;
use Symfony\Component\Serializer\Serializer;

final class Node
{
    public ?self $next = null;
    public function __construct(public string $id) {}
}
$node = new Node('n1');
$node->next = $node;
$serializer = new Serializer([new ObjectNormalizer()], [new JsonEncoder()]);
echo $serializer->serialize($node, 'json', [
    'circular_reference_handler' => static fn (Node $item): string => $item->id,
]);

La propriété next devient la string n1, plutôt qu'un développement infini. Le handler est volontairement borné à ce modèle Node. Contre-exemple : passer la limite de 1 à 100 et déclarer la boucle corrigée. Correction : choisir une représentation finie ; une limite plus haute ne ferait que retarder l'échec. La présence d'un même objet dans deux branches indépendantes ne doit pas être confondue avec un retour sur cet objet dans la branche courante.

Cycles et profondeur 8.0.

Passage canonique conservé

Les références circulaires

Deux objects qui se pointent lèvent une CircularReferenceException. circular_reference_limit — combien de fois un object est sérialisé avant d'être jugé circulaire — vaut 1 par défaut.

Contexte Résultat
par défaut CircularReferenceException
limite à 2 l'exception, plus tard
circular_reference_handler qui rend 'ref' {"members":[{"org":"ref","name":"m"}]}
un même object dans deux properties sœurs aucune exception

À mémoriser

À retenir en priorité
  1. Répétition et cycle sont distincts.
  2. La récursion revient sur un object du chemin courant.

Si tu dois retenir seulement 8 choses :

  • Normalizer (valeur ⇄ représentation) puis encoder (⇄ format).
  • Représentation : pas nécessairement un array ; une date formatée peut devenir une string, une enum backed conserve sa valeur int|string.
  • Plusieurs normalizers, un encoder ; le premier qui accepte agit.
  • ObjectNormalizer : public + get/has/is/can.
  • #[Ignore] partout ; groups au cas par cas ; Default ne rend rien, * tout.
  • Métadonnées lues par le service du framework, pas par un normalizer nu.
  • "7" vers int : refusé seulement avec l'extractor de types.
  • Cycle : exception, limite 1, handler pour rendre un identifier.

Moyen mnémotechnique : « Normaliser décide, encoder écrit ».
