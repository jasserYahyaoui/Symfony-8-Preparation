Objectif

Reconnaître les familles de constraints fournies et trancher entre celles qui se ressemblent. Le catalogue complet ne se mémorise pas : debug:validator et la référence le donnent.

L'essentiel

À comprendre

À retenir en priorité
  1. Le format ne rend pas une valeur obligatoire.
  2. Associer présence et format.

Le catalogue ne s'apprend pas : il se range en familles. Ce qui se joue à l'examen, ce sont les distinctions — NotBlank contre NotNull, null contre la string vide, All contre Collection — et la configuration 8.0 en named arguments.

Le schéma

À retenir en priorité
  1. All répète une règle par élément.
  2. Collection décrit les keys séparément.

Le fil rouge : un form de contact

À retenir en priorité
  1. NotBlank impose la présence.
  2. Email vérifie le format.
class Contact
{
    #[Assert\NotBlank]
    #[Assert\Email]
    public ?string $email = null;

    #[Assert\NotNull]
    public ?string $comment = null;      // '' accepté, null refusé

    #[Assert\Positive]
    public ?int $age = null;             // null accepté : facultatif

    #[Assert\All([new Assert\Length(max: 20)])]
    public array $tags = [];
}

Les distinctions qui décident

À comprendre

À retenir en priorité
  1. Zéro n'est pas vide pour NotBlank.
  2. Le trim doit être demandé explicitement.

C'est quoi ?

Une contrainte de présence et une contrainte de format répondent à des questions différentes. NotNull refuse seulement null. NotBlank, avec ses options par défaut, refuse notamment null, false, la chaîne vide et le tableau vide, mais accepte 0 et '0'. « Obligatoire » doit donc être traduit par la règle réellement souhaitée.

À quoi ça sert ?

Une adresse email facultative peut accepter le vide tout en refusant un texte mal formé. Une adresse obligatoire demande à la fois présence et format. De même, les espaces ne sont pas automatiquement supprimés : ' ' n'est pas vide pour NotBlank sans normalizer adapté.

Où dans Symfony ?

Les contraintes de valeur, de comparaison, de structure et de cascade se composent. All applique une règle à chaque élément ; Collection décrit des règles par clé ; Sequentially arrête les étapes suivantes après un échec ; AtLeastOneOf accepte si une des alternatives réussit. Aucune de ces compositions ne transforme une chaîne en donnée métier par elle-même.

Comment, étape par étape ?

  1. Préciser le domaine de valeurs : null, vide, zéro, espaces doivent-ils être permis ?
  2. Choisir une règle de présence si nécessaire, puis la règle de format ou de plage.
  3. Configurer les contraintes 8.0 avec des arguments nommés explicites, par exemple new Assert\Choice(choices: ['draft', 'published']).
  4. Tester une valeur valide et chaque frontière significative ; ne pas généraliser à toutes les contraintes le traitement du vide d'une seule.

Exemple concret PHP

Avec Validator 8.0 installé :

<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

$validator = Validation::createValidator();
foreach ([null, '', false, [], 0, '0', ' '] as $value) {
    echo json_encode($value), ': ',
        count($validator->validate($value, new Assert\NotBlank())), '/',
        count($validator->validate($value, new Assert\NotNull())), "\n";
}

Les couples attendus sont 1/1 pour null, 1/0 pour '', false et [], puis 0/0 pour les trois dernières valeurs. Contre-exemple : employer uniquement NotNull pour interdire un nom vide ; '' passe. Correction : NotBlank, éventuellement avec normalizer: 'trim' pour la politique concernant les espaces. Le normalizer de la contrainte sert à son contrôle : ce n'est pas une promesse de réécriture de la propriété de l'objet.

  • L'int 0 passe donc NotBlank ; normalizer: 'trim' fait refuser ' ' ; allowNull fait accepter null.
  • EqualTo compare par ==, IdenticalTo par === : '1' passe le premier, pas le second.
  • Length compte des caractères ('été' en fait 3) ; Count, des éléments.

null et la string vide

À comprendre

À retenir en priorité
  1. null est souvent laissé aux constraints de présence.
  2. La string vide dépend de chaque règle.

C'est quoi ?

La présence et le format sont des contrats distincts. Plusieurs contraintes de format, dont Email, acceptent null et la chaîne vide afin de permettre une donnée facultative. Ce n'est pas une règle universelle applicable à toute contrainte et à toutes ses options.

À quoi ça sert ?

Une adresse facultative doit pouvoir être absente sans accepter un texte mal formé. Une adresse obligatoire demande en plus une règle de présence. Type contrôle un type, pas la présence ; Choice contrôle l'appartenance à des valeurs configurées ; les contraintes de structure organisent d'autres règles.

Où dans Symfony ?

NotNull refuse seulement null ; NotBlank avec ses défauts refuse notamment null et ''. Length avec un minimum positif refuse la chaîne vide. Choice peut accepter '' si cette valeur figure dans ses choix : affirmer qu'elle la refuse toujours serait incorrect. Le traitement du vide doit être vérifié pour la contrainte et les options réellement choisies.

Comment, étape par étape ?

  1. Décider si null et '' représentent une absence autorisée.
  2. Choisir séparément présence et format.
  3. Combiner les règles nécessaires, sans supposer qu'un widget HTML les remplace.
  4. Tester vide, null, valeur mal formée et valeur correcte.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;
$validator = Validation::createValidator();
foreach ([null, '', 'not-an-email', 'ada@example.com'] as $value) {
    echo count($validator->validate($value, new Assert\Email())), '/',
        count($validator->validate($value, [new Assert\NotBlank(), new Assert\Email()])), "\n";
}

Les couples attendus sont 0/1, 0/1, 1/1 et 0/0. Contre-exemple : employer Email seul pour une adresse obligatoire et considérer zéro violation sur '' comme preuve de présence. Correction : ajouter NotBlank. Cette composition ne supprime pas les espaces ni ne réécrit la donnée stockée ; une politique de normalisation doit être explicite.

Passage canonique conservé

null et la string vide

Une constraint de valeur ignore null : Length, Email, Regex, Choice, Positive, Count, Url, Type ne signalent rien. Sur '', Email, Regex, Url et Type('string') acceptent ; Length(min: 3) et Positive refusent. Choice accepte '' si cette valeur figure explicitement parmi les choix autorisés, sinon la refuse ; null est ignoré. La comparaison est stricte : '1' ne correspond pas au choix entier 1. Ajouter NotBlank quand la présence non vide est une règle métier.

Configurer une constraint en 8.0

À comprendre

À retenir en priorité
  1. Les options se passent en named arguments.
  2. choices: nomme explicitement la liste.

C'est quoi ?

Configurer une contrainte consiste à fournir les arguments de son constructeur selon sa signature Symfony 8.0. Les anciens tableaux d'options positionnels ne sont plus un contrat général accepté. Les arguments nommés rendent explicite l'option choisie.

À quoi ça sert ?

Une mauvaise configuration doit être distinguée d'une valeur métier invalide : si la contrainte ne peut pas être construite, aucune validation normale de la donnée n'a eu lieu. Les défauts de version comptent également, notamment requireTld de Url, égal à true en 8.0.

Où dans Symfony ?

Choice utilise choices pour sa liste ; Length exige au moins une borne min ou max. Url contrôle par défaut les protocoles HTTP/HTTPS et exige un domaine de premier niveau ; requireTld false permet notamment le cas localhost. Cela ne prouve ni l'existence ni la confiance de la destination.

Comment, étape par étape ?

  1. Lire la signature de la contrainte dans la version ciblée.
  2. Fournir les options par leur nom.
  3. Vérifier les défauts qui affectent les données limites.
  4. Tester une mauvaise donnée séparément d'une mauvaise construction de contrainte.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;
$validator = Validation::createValidator();
$state = new Assert\Choice(choices: ['draft', 'published']);
var_dump(count($validator->validate('draft', $state)));
var_dump(count($validator->validate('http://localhost', new Assert\Url())));
var_dump(count($validator->validate('http://localhost', new Assert\Url(requireTld: false))));

On attend 0, 1 puis 0. Contre-exemple : recopier new Assert\Choice(['draft', 'published']) comme ancien tableau d'options. Correction : nommer choices. De même, Length sans min ni max est une configuration incomplète, pas une contrainte qui accepte arbitrairement toutes les longueurs. Une URL syntaxiquement admise ne constitue pas une autorisation d'effectuer une requête serveur vers cette adresse.

Passage canonique conservé

Configurer une constraint en 8.0

  • Options en named arguments : new Assert\Choice(['draft', 'published']) lève « Passing an array of options to configure the "…\Choice" constraint is no longer supported. » — il faut choices:.
  • Url exige un TLD par défaut : http://localhost échoue sans requireTld: false.
  • new Assert\Length() sans min ni max : MissingOptionsException.

Les constraints de structure

À comprendre

À retenir en priorité
  1. Sequentially évite les contrôles suivants après échec.
  2. AtLeastOneOf exprime des alternatives.
  3. Optional distingue absence de key et valeur présente.
  4. Les constraints internes vérifient la valeur fournie.

C'est quoi ?

Les contraintes de structure organisent d'autres contraintes. All applique une règle à chaque élément ; Collection définit des règles par clé d'un tableau ; Sequentially les exécute en s'arrêtant après un échec ; AtLeastOneOf accepte qu'au moins une alternative réussisse. Elles répondent à des besoins différents, pas à une simple préférence de syntaxe.

À quoi ça sert ?

Une liste d'emails a une règle homogène par élément, tandis qu'un tableau avec email et age possède des contrats différents par clé. Choisir la bonne structure rend explicites les champs manquants ou supplémentaires et l'endroit où une violation se rattache.

Où dans Symfony ?

Ces contraintes appartiennent à Validator et s'utilisent sans Form. When applique des règles selon une expression ; Compound encapsule un ensemble réutilisable. Elles ne convertissent pas toutes les entrées vers un type attendu : Type valide un type, ce n'est pas un transformer.

Comment, étape par étape ?

  1. Décrire la forme de la donnée et les clés attendues.
  2. Choisir une règle par élément, par clé, en séquence ou en alternatives.
  3. Ajouter séparément présence et format si les deux sont requis : plusieurs contraintes de format ignorent null ou la chaîne vide.
  4. Tester une valeur correcte, une clé absente et une clé supplémentaire selon le contrat choisi.

Exemple concret PHP

Avec Validator chargé :

<?php
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

$rules = new Assert\Collection(fields: [
    'email' => [new Assert\NotBlank(), new Assert\Email()],
]);
$validator = Validation::createValidator();
var_dump(count($validator->validate(['email' => 'ada@example.test'], $rules)));
var_dump(count($validator->validate([], $rules)));

On attend zéro violation puis une violation de champ manquant. Contre-exemple : remplacer Collection par All et attendre qu'All connaisse le nom email et son caractère obligatoire. Correction : choisir Collection pour un contrat de clés. En Symfony 8.0, les options des contraintes doivent suivre leurs signatures, notamment les arguments nommés tels que fields ou choices ; ne pas recopier indistinctement un ancien tableau d'options positionnel.

Passage canonique conservé

Les constraints de structure

Besoin Constraint
la même règle pour chaque élément All
une règle par key d'un array (This field is missing., This field was not expected.) Collection
ne pas lancer la vérification suivante si la précédente échoue Sequentially
accepter l'une ou l'autre forme ; si toutes échouent, une violation qui les résume AtLeastOneOf
une règle seulement si une expression est vraie When
un jeu de constraints réutilisable sous un nom Compound

Dans une Collection, Optional autorise l'absence de la key mais valide sa valeur lorsqu'elle est présente. Required signale une key absente avec les réglages ordinaires de la collection ; les options globales de présence de la collection restent à considérer. Une key présente avec null n'est pas une key absente : la constraint interne décide si null est autorisé.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. IdenticalTo compare aussi le type.
  2. EqualTo utilise la comparaison souple.
  • Voir l’explication : NotBlank accepte 0, '0' et ' '.

    NotBlank accepte 0, '0' et ' '. Il refuse le vide au sens de PHP, sauf ces valeurs. Pour une string dont le vide est légitime, c'est NotNull.

  • Voir l’explication : All n'est pas Collection.

    All n'est pas Collection. All traite les éléments uniformément ; Collection décrit un array key par key.

  • Voir l’explication : Sans Sequentially, toutes les constraints s'exécutent

    Sans Sequentially, toutes les constraints s'exécutent et cumulent leurs violations sur la même property.

  • Catégorie de la constraint DivisibleBy

    DivisibleBy est rangée en comparaison.

  • Voir l’explication : Email seule accepte null et ''.

    Email seule accepte null et ''. L'obligation vient de NotBlank.

  • Voir l’explication : Choice(['a', 'b']) lève une exception en 8.0

    Choice(['a', 'b']) lève une exception en 8.0 : choices: est nommé.
