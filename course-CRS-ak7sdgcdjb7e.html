Objectif

Poser un flash message, savoir où il est stocké et quand il disparaît.

L'essentiel

À comprendre

À retenir en priorité
  1. Le flash message est une donnée de session.
  2. Son type est une string libre, pas une enum imposée.

Un flash message est un message de session utilisé une seule fois : il disparaît dès qu'il est lu. C'est l'outil du Post / Redirect / Get : traiter, poser un message, rediriger, l'afficher. Tout tient dans la différence entre ce qui consomme et ce qui regarde — et entre add(), qui empile, et set(), qui écrase.

Le schéma

À retenir en priorité
  1. get() consomme un type ; all() consomme tout.
  2. peek() et peekAll() consultent sans consommer.

L'exemple : après un enregistrement

Exemple concret

class Exampleb0c88cd8
{
    public function edit(Request $request): Response
    {
        // … traitement du form
        $this->addFlash('notice', 'Vos modifications ont été enregistrées.');

        return $this->redirectToRoute('app_post_show', ['id' => $post->getId()]);
    }
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Ce que c'est

À comprendre

C'est quoi ?

Un flash message est une notification rangée par type dans un sac de messages. Dans l'usage HTTP habituel, ce sac appartient à la session afin de retrouver le message après une redirection. Sa disparition dépend d'une lecture consommatrice, pas de toute méthode de consultation.

À quoi ça sert ?

Après un POST réussi, l'application peut rediriger vers un GET puis afficher la confirmation sans renvoyer le POST au rafraîchissement. Les types notice, warning ou error sont des conventions applicatives, pas une enum imposée.

Où dans Symfony ?

FlashBag appartient à HttpFoundation et fonctionne aussi comme objet isolé. Dans l'intégration de session habituelle, son accès démarre la session et la continuité entre requêtes repose généralement sur le cookie de session. Cela ne signifie pas que construire et utiliser un FlashBag en mémoire exige un cookie.

Comment, étape par étape ?

  1. Ajouter le message après l'opération réussie.
  2. Conserver la continuité de session lors de la redirection HTTP.
  3. Lire avec get ou all pour consommer, avec peek ou peekAll pour consulter sans retirer.
  4. Ne pas confondre stockage temporaire en mémoire, persistance de session et durée de conservation de la notification.

Exemple concret PHP

Avec HttpFoundation chargé, sans session HTTP :

<?php
use Symfony\Component\HttpFoundation\Session\Flash\FlashBag;
$flashes = new FlashBag();
$flashes->add('notice', 'Enregistré.');
var_export($flashes->peek('notice'));
var_export($flashes->get('notice'));
var_export($flashes->get('notice'));

Les deux premiers résultats contiennent Enregistré ; le troisième est vide. Contre-exemple : remplacer peek par get dans un test préalable puis attendre de retrouver le message à l'affichage. Correction : consulter sans consommer, ou conserver le résultat de la lecture unique. Ce script illustre le sac ; il ne rend pas ses données persistantes entre deux requêtes.

Passage canonique conservé

Ce que c'est

Un flash est un message à consommation contrôlée : get() et all() consomment les messages lus, peek() et peekAll() les conservent. Dans l'application usuelle, la session assure leur continuité entre Request, généralement à l'aide d'un cookie ; un FlashBag isolé fonctionne aussi en mémoire. Le type — notice, warning, error — est une string libre.

Poser

À comprendre

À retenir en priorité
  1. add() accumule les messages.
  2. set() remplace la liste du type.

C'est quoi ?

addFlash est un raccourci d'AbstractController qui ajoute un message au sac de flash de la session. Son opération de stockage correspond à getSession()->getFlashBag()->add(type, message), avec les vérifications de disponibilité prévues par le raccourci.

À quoi ça sert ?

Après une opération réussie, plusieurs informations peuvent être ajoutées sous un même type sans se remplacer. Le type sert à organiser l'affichage ; ce n'est pas un niveau de gravité imposé par Symfony.

Où dans Symfony ?

La session doit être disponible et prendre en charge les flash messages. addFlash lève une LogicException si cette intégration manque. Sur le sac, add ajoute un élément ; set remplace l'ensemble des messages du type. Un succès ne doit être ajouté qu'après la réussite réelle de l'opération annoncée.

Comment, étape par étape ?

  1. Effectuer l'opération applicative.
  2. Ajouter son message avec addFlash dans une action, ou avec le sac de flash disponible.
  3. Retourner une réponse, souvent une redirection vers une route connue.
  4. Lire ensuite les messages dans la page chargée ; l'ajout seul ne les affiche pas.

Exemple concret PHP

Action d'AbstractController, sessions actives et route homepage existante :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function confirm(): \Symfony\Component\HttpFoundation\RedirectResponse
{
    $this->addFlash('notice', 'Votre demande a été reçue.');
    $this->addFlash('notice', 'Vous pouvez consulter son état.');
    return $this->redirectToRoute('homepage', [], 303);
}

Le sac contient deux messages notice avant leur consommation. Contre-exemple : remplacer le deuxième ajout par set sur le sac en attendant deux messages : set remplace la liste. Correction : employer add pour accumuler, set seulement pour remplacer volontairement. Le raccourci n'est pas disponible dans une classe simple n'héritant pas d'AbstractController.

Passage canonique conservé

Poser

addFlash() équivaut strictement à $request->getSession()->getFlashBag()->add(). Il lève une LogicException si les sessions sont désactivées, ou si la session n'implémente pas FlashBagAwareSessionInterface. Le sac expose aussi set(), qui remplace tout le type : deux add() puis un set() ne laissent que le dernier message.

Lire, et le piège

À comprendre

C'est quoi ?

Un flash message est un message temporaire stocké dans un sac de session et consommé lorsqu'on le lit par une méthode de consommation. Le type du message, tel que notice ou warning, est une clé choisie par l'application, pas un niveau imposé par le protocole HTTP.

À quoi ça sert ?

Après une opération suivie d'une redirection, la page suivante peut afficher une confirmation sans la placer dans l'URL. « Temporaire » ne signifie pas qu'une simple navigation précise constitue à elle seule une garantie d'affichage : la consommation dépend de la lecture effective et du sac utilisé.

Où dans Symfony ?

AbstractController propose addFlash ; la session doit prendre en charge le sac de flash messages. add(type, message) ajoute à la liste ; set(type, messages) remplace la liste du type. Dans Twig, les accès app.flashes consomment les messages comme les méthodes correspondantes du sac.

Comment, étape par étape ?

  1. Ajouter le message après l'opération réellement réussie.
  2. Dans la page de destination, choisir qui en est responsable de l'affichage.
  3. Utiliser get(type) pour consommer un type, all() pour tout consommer.
  4. Utiliser peek(type) ou peekAll() pour consulter sans retirer ; conserver ensuite le résultat si plusieurs zones doivent l'afficher.

Exemple concret PHP

Le comportement du sac peut être observé sans session HTTP, avec HttpFoundation chargé :

<?php
use Symfony\Component\HttpFoundation\Session\Flash\FlashBag;

$bag = new FlashBag();
$bag->add('notice', 'Enregistrement effectué.');
var_dump($bag->peek('notice'));
var_dump($bag->get('notice'));
var_dump($bag->get('notice'));

Les deux premières lectures contiennent le message ; la troisième retourne un tableau vide. Le sac isolé démontre la consommation, pas la persistance entre requêtes. Contre-exemple : lire les messages dans l'en-tête puis les lire à nouveau dans le corps en attendant deux affichages identiques. Correction : une seule consommation et réutilisation de la liste, ou une consultation non consommatrice si c'est l'intention. Ajouter un flash dans l'application utilise la session et doit être pris en compte pour le cache ; ce n'est pas une notification indépendante du contexte HTTP.

Passage canonique conservé

Lire, et le piège

Method Effet
get('warning') / all() retourne les messages et les consomme
peek('warning') / peekAll() retourne les messages sans les consommer

get() ne vide que son type, all() vide tout ; clear() est un alias de all() — elle vide et retourne. Un type présent mais vide compte pour absent : has() répond false, et get() rend sa default value.

Un flash est un post-it qu'on décolle après lecture. peek() permet seulement d'y jeter un œil : le lecteur suivant pourra toujours le consommer.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Lire un flash le consomme.

    Lire un flash le consomme. Afficher les messages deux fois dans la même page par le path ordinaire en fait disparaître la moitié : la seconde lecture ne trouve plus rien. La consultation sans consommation existe, c'est une autre method.

  • Voir l’explication : set() n'ajoute pas, elle remplace.

    set() n'ajoute pas, elle remplace. Deux add() puis un set() ne laissent qu'un message. Seul add() empile.

  • Voir l’explication : clear() retourne les messages qu'elle efface.

    clear() retourne les messages qu'elle efface. Ignorer sa return value jette les messages.

  • Voir l’explication : get() ne vide que son type.

    get() ne vide que son type. Vider tout demande all().

  • Voir l’explication : La continuité entre Request est distincte du sac en mémoire.

    La continuité entre Request est distincte du sac en mémoire. Dans l'application usuelle, ajouter un flash via la session démarre celle-ci ; un FlashBag autonome ne requiert pas de cookie. peek() et peekAll() conservent les messages ; get() et all() les consomment.

  • Voir l’explication : Le type du message est libre.

    Le type du message est libre. notice, warning, error sont des usages, pas une enum imposée par le framework.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Flash = session, lu une fois ; poser un flash démarre la session.
  • addFlash() ≡ getFlashBag()->add(), et lève sans session.
  • add() empile, set() écrase le type.
  • get() / all() / clear() consomment ; peek() / peekAll() non.
  • get() vide son type ; clear() vide et retourne.
  • Type vide = absent pour has().

Moyen mnémotechnique : « Peek regarde, le reste consomme ».

Revoir : L'essentiel

Where are flash messages stored?

With Symfony Session integration, flash messages are stored in the session. A standalone FlashBag keeps them only in memory and provides no persistence between requests; get()/all() consume them, peek()/peekAll() preserve them.

La persistance entre requêtes vient du stockage de session intégré, pas de FlashBag seul. get()/all() consomment les messages, peek()/peekAll() les conservent. Le type du flash est une string libre, pas une enum imposée.

Revoir : Le schéma

How do you read flash messages without consuming them?

Use peek() or peekAll(), not get() or all().

get() consomme un type ; all() consomme tout. peek() et peekAll() consultent sans consommer.
