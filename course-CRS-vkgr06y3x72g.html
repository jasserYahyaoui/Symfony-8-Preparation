Objectif

À côté de l'article /blog/42, la liste utilise /blog/page/{page}. Nous voulons que /blog/page affiche la première page sans confondre page 42 et article 42. Le défaut doit donc être disponible au matching, avant même que l'action soit appelée.

Rendre un parameter facultatif, et connaître les deux règles qui en découlent.

L'essentiel

À comprendre

À retenir en priorité
  1. La correspondance se fait par nom.
  2. Un defaults explicite non null prime sur le défaut d'argument ; null ne bloque pas sa copie par le loader.

Un parameter de path est obligatoire tant qu'il n'a pas de default value. En attributes, cette valeur peut venir du défaut de l'argument homonyme du controller, d'un defaults explicite ou de la syntaxe inline. Deux règles en découlent : tout ce qui suit un parameter facultatif doit l'être aussi, et une default value en fin de path disparaît de l'URL générée — sauf avec {!page}, qui rend aussi le parameter obligatoire à l'appariement.

Le schéma

À retenir en priorité
  1. Un placeholder exige une valeur sans défaut.
  2. Un défaut null impose un argument nullable.

Bleu = configuration et compilation ; vert = deux usages distincts, pas deux appels successifs. Le défaut ne rend pas une valeur reçue arbitraire valide : /blog/page/abc doit toujours satisfaire le requirement, même si /blog/page utilise 1.

L'exemple

Exemple concret

À retenir en priorité
  1. La valeur par défaut de l'argument rend ici le dernier parameter facultatif.
  2. Le generator omet la valeur par défaut en fin de path, sauf demande explicite contraire.

La route de liste suivante est distincte de blog_show. Elle produit une Response minimale afin d'observer le défaut sans dépendre de Twig ou du catalogue.

use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

final class BlogController
{
    #[Route('/blog/page/{page}', name: 'blog_list', requirements: ['page' => '\d+'])]
    public function list(int $page = 1): Response
    {
        return new Response('Page '.$page);
    }
}   // /blog/page → Page 1 ; génération avec page=1 → /blog/page

La règle de base

Le matcher ne peut pas attendre l'appel PHP pour savoir si le segment manque légalement : la route doit déjà contenir son défaut. Les formats du tableau établissent cette configuration en amont. L'ArgumentResolver utilisera plus tard l'attribut fourni par le matching.

Dès qu'un parameter apparaît dans le path, il doit avoir une valeur : /blog/page/{page} ne correspond pas à /blog/page. Une default value le rend facultatif.

Format Où
attribute PHP argument du controller : list(int $page = 1)
YAML / PHP option defaults
inline {page?1}, combinable : /blog/page/{page<[0-9]+>?1}

Un ? sans valeur, {page?}, donne la default value null : l'argument du controller doit alors être nullable.

🌍 In Real Life

La situation : au restaurant, demander la carte sans préciser de page signifie commencer à la première, si cette convention est inscrite dans les consignes d'accueil. Le serveur ne doit pas attendre la cuisine pour découvrir cette convention.

L’équivalent dans Symfony : pour /blog/page, le matcher doit déjà connaître le défaut de {page} dans la route. Il fournit cette valeur au matching ; la résolution des arguments du contrôleur vient ensuite.

Retour à la réalité technique : un défaut autorise l'omission dans un suffixe facultatif approprié, sans marqueur !. Les différentes syntaxes configurent la route en amont. Un défaut null effectivement conservé doit être compatible avec l'argument qui le recevra.

🧠 Comment le mémoriser : « La convention est connue avant l'accueil. » Image mentale : consigne « page 1 si rien n'est précisé » au comptoir. Question-réflexe : la route possède-t-elle déjà ce défaut au matching ?

⚠️ À ne pas confondre : défaut de route et valeur choisie tardivement lors de l'appel PHP ; numéro de page et identifiant d'article.

Repère — D'où vient le défaut en attributes :

Question: Does any default controller argument become a route default?

Answer: No. It must match a path parameter name. An explicit non-null route default takes precedence; explicit null can be replaced by an admissible action default because the loader uses isset.

La correspondance se fait par nom. Un defaults explicite non null prime sur le défaut d'argument ; null ne bloque pas sa copie par le loader.

Repère de l’exemple :

Question: Which page value does /blog use when the action argument is int $page = 1?

Answer: It uses 1; the trailing parameter can be omitted from both matching and the default generated URL.

La valeur par défaut de l'argument rend ici le dernier parameter facultatif. Le generator omet la valeur par défaut en fin de path, sauf demande explicite contraire.

D'où vient le défaut en attributes

Notre action de liste déclare $page = 1, mais cette valeur PHP n'est pas magiquement un défaut pour tous les paramètres de route. Au chargement, AttributeClassLoader rapproche le nom $page du placeholder {page}. Un $limit = 10 ne fournit rien à {page} : c'est une autre donnée.

AttributeClassLoader copie dans la route la default value d'un argument qui porte le nom d'un parameter du path si isset($defaults[$param]) est faux. Un défaut explicite non null conserve donc la priorité ; une entrée explicite null ne bloque pas la copie. Avec defaults: ['page' => null] et action(?int $page = 1), le défaut chargé devient 1 ; avec defaults: ['page' => 2], il reste 2. Seules les valeurs scalaires, null et les cas d'enum adossée, dont il copie la value, sont reprises. Un argument par défaut sans parameter homonyme ne rend rien facultatif.

Ainsi, pour /blog/page, un défaut explicite null peut finalement produire 1, alors qu'un défaut explicite 2 reste 2. Ce résultat est fixé dans la route avant la requête ; ce n'est pas ArgumentResolver qui choisit entre ces déclarations. Il reste à vérifier que la position du segment permet effectivement son omission.

🌍 In Real Life

La situation : avant le service, un responsable recopie la consigne « page : 1 » dans la fiche d'accueil portant le même libellé. Une case déjà renseignée à 2 reste prioritaire ; une case vide ne bloque pas la copie.

L’équivalent dans Symfony : AttributeClassLoader rapproche le nom de l'argument PHP et celui du paramètre du path. Il peut copier le défaut admissible si isset() ne trouve pas de défaut explicite non nul.

Retour à la réalité technique : null et absence font ici échouer isset() ; un défaut explicite non nul conserve sa priorité. Le loader reprend les valeurs admises décrites ci-dessus, notamment la valeur d'une enum adossée. Cette décision précède la Request.

🧠 Comment le mémoriser : « Même étiquette, copie avant service. » Image mentale : deux cases « page » reliées par une flèche. Question-réflexe : nom identique, valeur admissible, défaut explicite non nul déjà présent ?

⚠️ À ne pas confondre : lecture des attributs PHP au chargement et lecture des attributs de Request par les value resolvers.

Tout ce qui suit un parameter facultatif doit l'être

À retenir en priorité
  1. Les segments facultatifs doivent former la fin du path.
  2. Un segment fixe après le parameter empêche son omission.

La suppression doit laisser un chemin non ambigu. Dans notre liste, page est final ; si nous ajoutons un segment obligatoire après lui, sa valeur par défaut ne suffit plus à autoriser son absence. Le défaut peut exister dans la configuration sans rendre ce segment facultatif au matching.

/blog/{slug}/{page} admet plusieurs parameters facultatifs, mais tout ce qui suit un parameter facultatif doit l'être aussi. /{page}/blog est valide, mais page y reste toujours obligatoire, default value ou non : /blog ne correspond pas.

🌍 In Real Life

La situation : une fiche de commande abrégée peut omettre les dernières cases convenues, mais pas supprimer une case au milieu en décalant la signification des suivantes.

L’équivalent dans Symfony : l'omission concerne le suffixe facultatif du path. Dans /{page}/blog, le segment fixe qui suit empêche de retirer {page}, même si la route possède une valeur par défaut.

Retour à la réalité technique : posséder un défaut et être omissible sont deux propriétés distinctes. La compilation du path prend en compte les segments suivants ; la route reste valide lorsqu'un défaut ne suffit pas à rendre son paramètre facultatif.

🧠 Comment le mémoriser : « On raccourcit la fin, on ne creuse pas le milieu. » Image mentale : une bande de cases dont seul le bout se replie. Question-réflexe : reste-t-il un segment obligatoire après celui que je voudrais omettre ?

⚠️ À ne pas confondre : configuration de défaut et acceptation d'un chemin sans ce segment.

On peut omettre la dernière ligne facultative d'une adresse, pas une ligne au milieu sans déplacer le sens des suivantes. C'est l'intuition des parameters facultatifs uniquement en fin de path.

Le point d'exclamation

À retenir en priorité
  1. Le ! maintient le parameter dans l'URL générée.
  2. Le compiler ne le traite plus comme facultatif.

Si les liens du blog doivent afficher explicitement la page 1, le marqueur ! change la génération, mais aussi le matching. C'est donc un changement de contrat d'URL, pas seulement une préférence visuelle.

Une default value en fin de path disparaît de l'URL générée : blog_list avec page = 1 produit /blog/page. Au milieu du path, elle reste. Pour forcer l'inclusion, on écrit /blog/page/{!page}.

La documentation n'en décrit que cet effet. RouteCompiler ne rend facultative qu'une variable « not important » ayant une default value : avec {!page}, page redevient obligatoire à l'appariement, et /blog/page ne correspond plus. Le ! agit des deux côtés.

🌍 In Real Life

La situation : le restaurant décide que chaque fiche doit désormais afficher le numéro de page, même pour la première. Cette nouvelle consigne vaut pour les fiches imprimées comme pour celles acceptées à l'accueil.

L’équivalent dans Symfony : {!page} force l'inclusion dans l'URL générée et empêche le compilateur de rendre ce segment facultatif au matching. Le défaut ne suffit plus à faire correspondre /blog/page.

Retour à la réalité technique : génération et matching sont deux usages de la configuration, pas deux étapes successives d'une même requête. Le marqueur change leur contrat ; il n'installe pas automatiquement une redirection des anciennes URL abrégées.

🧠 Comment le mémoriser : « Numéro écrit à la sortie, exigé à l'entrée. » Image mentale : un numéro entouré sur les deux piles de fiches. Question-réflexe : ai-je testé le lien produit et le chemin accepté ?

⚠️ À ne pas confondre : inclusion forcée du segment, redirection et simple préférence d'affichage.

Défaut et requirement

À retenir en priorité
  1. Le défaut est fourni par la route.
  2. Il n'est pas filtré comme une valeur entrante.

Lorsque le client fournit abc à la place du numéro de page, le requirement numérique refuse cette valeur. Lorsqu'il ne fournit aucun segment facultatif, le matcher utilise une valeur de configuration, pas une capture de l'URL. L'application doit donc choisir un défaut cohérent avec ce qu'elle accepte ensuite, même si Routing ne lui applique pas le même filtre.

La default value n'a pas à satisfaire le requirement : elle ne vient pas de l'URL, donc elle n'est pas filtrée.

🌍 In Real Life

La situation : l'accueil contrôle les numéros écrits par les visiteurs ; si une case peut rester vide, il utilise une consigne interne. Une faute dans cette consigne interne n'est pas réparée par le contrôle des fiches reçues.

L’équivalent dans Symfony : le requirement filtre la capture présente dans l'URL ; le défaut utilisé pour un segment absent vient de la configuration. Un défaut peut donc ne pas satisfaire le requirement.

Retour à la réalité technique : cela ne rend pas /blog/page/abc acceptable avec une exigence numérique. L'application doit choisir un défaut compatible avec ses types et son métier. Une expression régulière de routage ne transforme pas à elle seule la capture en entier.

🧠 Comment le mémoriser : « Contrôler l'entrée ne corrige pas la consigne. » Image mentale : filtre sur les fiches entrantes, note interne à côté. Question-réflexe : cette valeur vient-elle de l'URL ou de la configuration ?

⚠️ À ne pas confondre : requirement Routing, conversion d'argument et contrainte Validator.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Tout ce qui suit un parameter facultatif doit l'être aussi.

    Tout ce qui suit un parameter facultatif doit l'être aussi. La conséquence surprend : un path qui place le parameter avant un segment fixe rend ce parameter toujours obligatoire, default value ou non.

  • Voir l’explication : Une default value en fin de path disparaît de l'URL générée.

    Une default value en fin de path disparaît de l'URL générée. L'inclure de force s'écrit {!page}.

  • Voir l’explication : {!page} rend aussi le parameter obligatoire à l'appariement.

    {!page} rend aussi le parameter obligatoire à l'appariement. Une variable importante n'est jamais facultative pour le compiler.

  • Lien entre argument par défaut et paramètre de route

    Un défaut d'argument ne compte que si le path porte un parameter du même nom.

  • Voir l’explication : La default value n'a pas à satisfaire le requirement du parameter.

    La default value n'a pas à satisfaire le requirement du parameter. Le requirement porte sur ce qui vient de l'URL, pas sur ce que la route fournit elle-même.

Application

À retenir en priorité
  1. Les segments facultatifs doivent former la fin du path.
  2. Un segment fixe après le parameter empêche son omission.
  3. Le ! maintient le parameter dans l'URL générée.
  4. Le compiler ne le traite plus comme facultatif.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Sans default value, un parameter est obligatoire.
  • Attributes : défaut = argument du controller, si le path a le parameter.
  • Un defaults explicite non null l'emporte ; une entrée null peut être remplacée par le défaut d'argument. Enum adossée → sa value.
  • Après un facultatif, tout doit être facultatif.
  • Défaut en fin de path → omis ; {!page} → écrit et obligatoire.
  • La default value peut violer le requirement.

Moyen mnémotechnique : « Le point d'exclamation crie : je suis obligatoire ».
