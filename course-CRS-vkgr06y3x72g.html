Objectif

Rendre un parameter facultatif, et connaître les deux règles qui en découlent.

L'essentiel

À comprendre

À retenir en priorité
  1. La correspondance se fait par nom.
  2. defaults explicite prime sur le défaut d'argument.

Un parameter de path est obligatoire tant qu'il n'a pas de default value. En attributes, cette valeur est l'argument du controller. Deux règles en découlent : tout ce qui suit un parameter facultatif doit l'être aussi, et une default value en fin de path disparaît de l'URL générée — sauf avec {!page}, qui rend aussi le parameter obligatoire à l'appariement.

Le schéma

À retenir en priorité
  1. Un placeholder exige une valeur sans défaut.
  2. Un défaut null impose un argument nullable.

L'exemple

Exemple concret

À retenir en priorité
  1. La valeur par défaut de l'argument rend ici le dernier parameter facultatif.
  2. Le generator omet la valeur par défaut en fin de path, sauf demande explicite contraire.
class Example73edfb9b
{
    #[Route('/blog/{page}', name: 'blog_list', requirements: ['page' => '\d+'])]
    public function list(int $page = 1): Response {}   // /blog → page = 1 ; génération → /blog
}

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

La règle de base

À comprendre

C'est quoi ?

Un default donne une valeur à un paramètre sans exiger qu'il figure dans le chemin reçu, lorsque sa position le rend omissible. Il ne supprime pas un segment obligatoire placé après lui.

À quoi ça sert ?

La première page d'une liste peut disposer d'une URL courte tout en transmettant page égal à 1 à l'action. Le défaut appartient au contrat de route ; il doit être compatible avec le type et le traitement de l'argument.

Où dans Symfony ?

En YAML ou configuration PHP, utiliser defaults. Le loader des attributes de controller peut déduire le défaut de la signature. La forme inline {page?1} est une autre déclaration ; {page?} donne null et suppose un argument nullable.

Comment, étape par étape ?

  1. Placer les segments à rendre facultatifs à la fin du chemin.
  2. Choisir une seule manière cohérente de déclarer leur défaut.
  3. Aligner la signature de l'action.
  4. Tester chemin court et chemin explicite.

Exemple concret PHP et YAML

Dans un controller découvert par les attributes :

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[\Symfony\Component\Routing\Attribute\Route('/blog/{page}', name: 'blog_list')]
public function list(int $page = 1): \Symfony\Component\HttpFoundation\JsonResponse
{
    return new \Symfony\Component\HttpFoundation\JsonResponse(['page' => $page]);
}

L'alternative YAML pour la même action sans attribute est :

blog_list:
    path: /blog/{page}
    controller: App\Controller\BlogController::list
    defaults: {page: 1}

Le path /blog/{page?1} exprime aussi ce défaut inline. Contre-exemple : utiliser {page?} avec un argument int non nullable puis attendre un nombre par magie. Correction : choisir un défaut numérique, ou déclarer ?int $page = null et gérer cette absence. Ces formes ne doivent pas être chargées simultanément comme définitions concurrentes du même nom.

Passage canonique conservé

La règle de base

Dès qu'un parameter apparaît dans le path, il doit avoir une valeur : /blog/{page} ne correspond pas à /blog. Une default value le rend facultatif.

Format Où
attribute PHP argument du controller : list(int $page = 1)
YAML / PHP option defaults
inline {page?1}, combinable : /blog/{page<[0-9]+>?1}

Un ? sans valeur, {page?}, donne la default value null : l'argument du controller doit alors être nullable.

Repère — D'où vient le défaut en attributes : No. It must match a path parameter name, and an explicit route default takes precedence. La correspondance se fait par nom. defaults explicite prime sur le défaut d'argument.

Repère de l’exemple : It uses 1; the trailing parameter can be omitted from both matching and the default generated URL. La valeur par défaut de l'argument rend ici le dernier parameter facultatif. Le generator omet la valeur par défaut en fin de path, sauf demande explicite contraire.

D'où vient le défaut en attributes

AttributeClassLoader copie dans la route la default value d'un argument qui porte le nom d'un parameter du path et n'a pas déjà de défaut dans defaults — qui l'emporte donc. Seules les valeurs scalaires, null et les cas d'enum adossée, dont il copie la value, sont reprises. Un argument par défaut sans parameter homonyme ne rend rien facultatif.

Tout ce qui suit un parameter facultatif doit l'être

À comprendre

À retenir en priorité
  1. Les segments facultatifs doivent former la fin du path.
  2. Un segment fixe après le parameter empêche son omission.

C'est quoi ?

Une valeur par défaut fournit un paramètre lorsque l'URL ne le contient pas. Elle peut rendre facultative la fin d'un chemin, mais elle ne supprime pas arbitrairement un segment situé avant une partie obligatoire. Il faut distinguer « la route connaît une valeur par défaut » et « l'URL peut omettre ce segment ».

À quoi ça sert ?

Une liste paginée peut accepter /blog comme première page et /blog/2 comme deuxième page. Le défaut évite de répéter la valeur habituelle dans chaque lien tout en conservant une valeur disponible pour le controller.

Où dans Symfony ?

Les defaults se déclarent dans la configuration, dans la forme inline {page?1}, ou sont déduits d'un argument de méthode lorsque le loader d'attributes le permet. {page?} donne null et suppose un contrat nullable côté action. Une default value ne rend pas les segments qui la suivent facultatifs par elle-même.

Comment, étape par étape ?

  1. Partir de la fin du chemin.
  2. Vérifier que les variables à omettre possèdent toutes un défaut et qu'aucun texte obligatoire ne les suit.
  3. Définir les types d'arguments capables de recevoir ces défauts.
  4. Tester l'appariement et la génération, car l'omission dans un lien et l'acceptation d'un chemin sont deux observations différentes.

Exemple concret YAML

blog_list:
    path: /blog/{page}
    controller: App\Controller\BlogController::list
    defaults:
        page: 1
    requirements:
        page: '[0-9]+'

/blog fournit page égal à 1 ; /blog/2 fournit la valeur issue du chemin. La génération avec page égal à son défaut peut omettre le dernier segment. Contre-exemple : changer le path en /{page}/blog puis attendre que /blog corresponde. Le texte final est obligatoire et page n'est plus omissible. Correction : garder la partie optionnelle à la fin, ou déclarer une route séparée.

La notation {!page} force son importance : elle conserve le segment dans l'URL générée et, dans le compiler 8.0, l'empêche également de devenir facultatif à l'appariement. Ce n'est donc pas un simple choix cosmétique du générateur. Le défaut n'a pas à satisfaire le requirement puisqu'il n'est pas lu dans le chemin entrant.

Passage canonique conservé

Tout ce qui suit un parameter facultatif doit l'être

/blog/{slug}/{page} admet plusieurs parameters facultatifs, mais tout ce qui suit un parameter facultatif doit l'être aussi. /{page}/blog est valide, mais page y reste toujours obligatoire, default value ou non : /blog ne correspond pas.

On peut omettre la dernière ligne facultative d'une adresse, pas une ligne au milieu sans déplacer le sens des suivantes. C'est l'intuition des parameters facultatifs uniquement en fin de path.

Le point d'exclamation

À comprendre

À retenir en priorité
  1. Le ! maintient le parameter dans l'URL générée.
  2. Le compiler ne le traite plus comme facultatif.

C'est quoi ?

Le marqueur ! d'une variable de route la rend importante : sa valeur n'est pas omise du lien généré simplement parce qu'elle égale son défaut. Dans le compiler Symfony 8.0, cette importance empêche aussi de rendre ce segment facultatif au matching.

À quoi ça sert ?

Une application peut vouloir publier systématiquement le numéro de page, y compris 1. Ce choix donne des liens plus explicites, mais modifie aussi les chemins acceptés ; il faut donc décider si l'ancienne forme courte doit disposer d'une route séparée.

Où dans Symfony ?

La notation s'écrit dans le path, par exemple /blog/{!page}. Une valeur par défaut continue à fournir une valeur au générateur ; elle n'autorise plus l'omission du segment important à l'appariement.

Comment, étape par étape ?

  1. Déclarer le défaut de page.
  2. Ajouter ! si le segment doit rester dans le lien.
  3. Comparer les liens générés avant/après.
  4. Tester également une requête sans segment ; ne pas limiter le test au générateur.

Exemple concret YAML

blog_list:
    path: /blog/{!page}
    controller: App\Controller\BlogController::list
    defaults: {page: 1}
    requirements: {page: '[0-9]+'}

La génération de blog_list sans page explicite utilise le défaut et produit /blog/1. /blog/1 correspond ; /blog ne correspond plus à cette route. Contre-exemple : traiter ! comme une option uniquement cosmétique puis conserver des liens vers /blog. Correction : garder la syntaxe sans ! si l'omission doit rester admise, ou déclarer explicitement le parcours de la forme courte. La règle résulte du compiler 8.0, pas seulement d'une convention d'affichage.

Passage canonique conservé

Le point d'exclamation

Une default value en fin de path disparaît de l'URL générée : blog_list avec page = 1 produit /blog. Au milieu du path, elle reste. Pour forcer l'inclusion, on écrit /blog/{!page}.

La documentation n'en décrit que cet effet. RouteCompiler ne rend facultative qu'une variable « not important » ayant une default value : avec {!page}, page redevient obligatoire à l'appariement, et /blog ne correspond plus. Le ! agit des deux côtés.

Défaut et requirement

À comprendre

À retenir en priorité
  1. Le défaut est fourni par la route.
  2. Il n'est pas filtré comme une valeur entrante.

C'est quoi ?

Un défaut provient de la configuration ; un requirement vérifie la portion reçue dans le chemin. Le défaut peut donc ne pas satisfaire le motif imposé aux valeurs présentes dans l'URL.

À quoi ça sert ?

Un défaut null peut représenter l'absence de filtre tandis qu'un numéro explicite doit respecter une syntaxe numérique. Cette séparation évite de réserver une fausse valeur numérique pour exprimer « non précisé ».

Où dans Symfony ?

Le matcher fournit le défaut lorsque le segment final facultatif manque. Le controller doit accepter le type correspondant ; cette possibilité n'autorise pas le client à envoyer littéralement null sous forme de texte dans le chemin.

Comment, étape par étape ?

  1. Définir la signification de l'absence.
  2. Choisir le défaut et le type nullable si nécessaire.
  3. Appliquer le requirement aux valeurs explicites.
  4. Tester absence, valeur correcte et texte incorrect séparément.

Exemple concret YAML

archive_year:
    path: /archive/{year}
    controller: App\Controller\ArchiveController::year
    defaults: {year: null}
    requirements: {year: '[0-9]{4}'}

L'action déclare par exemple ?int $year = null. /archive fournit null ; /archive/2026 fournit la valeur du segment ; /archive/null ne correspond pas. Contre-exemple : utiliser un argument int obligatoire parce que le requirement contient uniquement des chiffres. Correction : prendre en compte aussi le chemin sans segment, qui ne produit aucun chiffre à convertir. Le motif vérifie une forme de quatre chiffres, pas toutes les règles métier d'une année utilisable.

Passage canonique conservé

Défaut et requirement

La default value n'a pas à satisfaire le requirement : elle ne vient pas de l'URL, donc elle n'est pas filtrée.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Tout ce qui suit un parameter facultatif doit l'être aussi.

    Tout ce qui suit un parameter facultatif doit l'être aussi. La conséquence surprend : un path qui place le parameter avant un segment fixe rend ce parameter toujours obligatoire, default value ou non.

  • Voir l’explication : Une default value en fin de path disparaît de l'URL générée.

    Une default value en fin de path disparaît de l'URL générée. L'inclure de force s'écrit {!page}.

  • Voir l’explication : {!page} rend aussi le parameter obligatoire à l'appariement.

    {!page} rend aussi le parameter obligatoire à l'appariement. Une variable importante n'est jamais facultative pour le compiler.

  • Lien entre argument par défaut et paramètre de route

    Un défaut d'argument ne compte que si le path porte un parameter du même nom.

  • Voir l’explication : La default value n'a pas à satisfaire le requirement du parameter.

    La default value n'a pas à satisfaire le requirement du parameter. Le requirement porte sur ce qui vient de l'URL, pas sur ce que la route fournit elle-même.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Sans default value, un parameter est obligatoire.
  • Attributes : défaut = argument du controller, si le path a le parameter.
  • defaults l'emporte sur l'argument ; enum adossée → sa value.
  • Après un facultatif, tout doit être facultatif.
  • Défaut en fin de path → omis ; {!page} → écrit et obligatoire.
  • La default value peut violer le requirement.
