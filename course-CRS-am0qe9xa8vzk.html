Objectif

Finder a sélectionné les fichiers d'import. Si leur conversion exige un programme externe, l'application doit lui transmettre des arguments, attendre ou surveiller son exécution, puis interpréter son résultat. Process gère cette frontière avec un processus enfant ; il ne remplace pas le service qui décide si les données obtenues sont utilisables.

L'essentiel

À comprendre

À retenir en priorité
  1. Les arguments restent littéraux.
  2. Le shell n'est pas nécessaire pour un exécutable simple.

Process exécute un programme externe dans un sous-processus, en gérant les différences entre systèmes et l'escaping des arguments ; il remplace exec(), passthru(), shell_exec() et system(). Trois questions décident de tout : la forme de la command (array ou string), le moment où l'appel rend la main, et ce qui l'interrompt — deux délais et stop().

Le parent et l'enfant sont deux processus : partager un service Symfony n'est pas possible par simple appel d'objet à travers cette frontière. L'enfant reçoit des arguments, un environnement et éventuellement une entrée standard ; il produit des flux et un code de sortie. Lancer bin/console comme enfant démarre une autre application, pas une étape obligatoire de GET /blog/42.

Le schéma

À retenir en priorité
  1. Le mode d'attente et la gestion d'erreur sont distincts.
  2. Un démarrage async exige un suivi.

Construire Process ne lance pas encore le programme. Après le lancement, le parent reste responsable de la surveillance : les délais sont vérifiés à des points de contrôle, pas par un thread de surveillance autonome.

Bleu : appels ; ambre : état ; vert : fin observable. Cette boucle est un modèle, pas une boucle PHP à copier sans pause : éviter une attente active coûteuse. wait() gère l'attente bloquante ; start() ne crée ni daemon supervisé ni garantie de survie après la fin du processus parent.

L'exemple : lister un dossier

Exemple concret

À retenir en priorité
  1. La valeur n'est pas interprétée par un shell.
  2. La forme array protège les frontières d'arguments.

Avant de brancher un convertisseur, ce petit exemple vérifie le contrat lancement/résultat avec un outil Unix connu. Avec Symfony Process 8.0 chargé et ls disponible :

use Symfony\Component\Process\Exception\ProcessFailedException;
use Symfony\Component\Process\Process;

$process = new Process(['ls', '-lsa']);
$process->setTimeout(120);
$process->run();

if (!$process->isSuccessful()) {
    throw new ProcessFailedException($process);
}
echo $process->getOutput();

Cet exemple et les questions sur sleep, SIGTERM et SIGKILL supposent Unix. La sortie de ls dépend du répertoire courant. Le tableau d'arguments protège la séparation des arguments, mais il faut encore valider les options acceptées par le programme cible (et utiliser -- quand il le prend en charge).

Si ls termine à 0, son listing est affiché ; sinon le code lève l'exception. La sortie n'est pas un format stable de lot d'import : pour sélectionner les fichiers depuis PHP, garder Finder. Process est pertinent quand le programme externe réalise une opération dont l'application a besoin.

Array ou string

À retenir en priorité
  1. Le shell apporte pipes et redirections.
  2. Il ajoute une responsabilité d'échappement.

🌍 In Real Life

La situation : le blog remet au convertisseur des cases séparées « outil », « format », « fichier », plutôt qu'une phrase à réinterpréter comme des instructions.

L’équivalent dans Symfony : cases séparées → tableau d'arguments ; phrase utilisant une grammaire supplémentaire → ligne interprétée par le shell.

Retour à la réalité technique : le tableau préserve les frontières des arguments sans interpolation shell des valeurs. Il ne valide pas les options métier du programme appelé : une valeur reste à contrôler selon ce programme.

🧠 Comment le mémoriser : « Des cases, pas une phrase à deviner. » Image mentale : trois compartiments fermés. Question-réflexe : ai-je réellement besoin des opérateurs du shell ?

⚠️ À ne pas confondre : échappement des arguments et autorisation d'exécuter n'importe quelle commande.

  • Le array d'arguments est la forme recommandée : pas d'escaping manuel, les signaux passent. ['printf', '%s', 'a b;c $HOME'] affiche a b;c $HOME, littéral.
  • Une string, par Process::fromShellCommandline(), sert aux fonctionnalités du shell (>, |) ; les valeurs passent par des variables d'environment, "${:NOM}" restant portable. Une valeur non fournie lève une InvalidArgumentException au lancement.
  • Un processus CLI hérite de l'environnement du parent ; passer ['OTHER' => 'x'] laisse une variable non nommée toujours héritée : pour en retirer une, la passer à false.

Le tableau protège les frontières d'arguments, pas le choix du binaire, les options de ce binaire ou les chemins auxquels il aura accès. Fixer l'exécutable depuis une configuration maîtrisée ; ne pas concaténer une valeur utilisateur dans une ligne shell.

L'environnement explicite complète celui hérité, il n'est pas une liste d'autorisation exhaustive. Ne pas transmettre ou journaliser des secrets inutiles. L'implémentation 8.0.16 filtre aussi certaines variables de contexte de requête sous les SAPIs non CLI : « toutes les variables de la machine » ne décrit donc pas le contrat réel.

Trois façons de lancer

À retenir en priorité
  1. Le retour immédiat n'est pas une réussite finale.
  2. wait() peut attendre la fin.

🌍 In Real Life

La situation : au bureau du blog, on peut attendre le convertisseur, exiger un résultat réussi ou le lancer puis surveiller son avancement.

L’équivalent dans Symfony : attendre le code → run() ; attendre et lever sur échec → mustRun() ; lancer sans attendre la fin → start().

Retour à la réalité technique : rendre la main tôt n'apporte aucune preuve de réussite finale. Le parent doit encore observer la fin et le code ; le sous-processus n'est pas pour autant une tâche durable supervisée.

🧠 Comment le mémoriser : « Parti n'est pas fini. » Image mentale : un bon de lancement sans bon de livraison. Question-réflexe : où sera contrôlé le résultat final ?

⚠️ À ne pas confondre : attente et politique de transformation d'un échec en exception.

L'attente et la politique d'erreur sont deux choix séparés. Si un convertisseur termine normalement avec le code 7, run() rend 7, mustRun() transforme ce résultat en exception, et un lancement par start() exige une observation ultérieure :

Appel Rend la main En cas d'échec
run() à la fin du process rend un exit code
mustRun() à la fin du process lève ProcessFailedException
start() après le lancement, sans attendre la fin comme run() résultat final à vérifier

Ce tableau compare les codes de sortie non nuls. Un lancement peut lui-même lever une exception. mustRun() ne lève ProcessFailedException que si le programme termine en échec, pas à chaque appel.

Après start(), isRunning() interroge l'état et wait() bloque. ExecutableFinder trouve le path d'un exécutable, PhpExecutableFinder celui du binaire PHP.

start() effectue lui-même des opérations et un contrôle initial : « non bloquant jusqu'à la fin » ne signifie pas « temps de lancement nul ». Pour du travail durable, ce n'est pas un substitut à une file Messenger configurée et à un worker supervisé. Le code de sortie de l'enfant doit ensuite être traduit selon le contrat de la commande d'import parente.

Récupérer l'output

À retenir en priorité
  1. Le flux peut être suivi par morceaux.
  2. Le buffer complet reste une autre vue.

getOutput() et getErrorOutput() lisent les buffers stdout et stderr. getIncrementalOutput() lit stdout depuis la dernière lecture incrémentale ; un getOutput() ordinaire ne déplace pas ce curseur. Lire par morceaux ne signifie pas que les données déjà capturées sont automatiquement libérées.

Une ligne stderr peut être un diagnostic d'un enfant qui réussit ; stdout peut contenir des données partielles avant un échec. Inspecter le code final et le contenu attendu, pas seulement la présence de texte.

disableOutput() évite la collecte mais interdit les lectures capturées et l'activation d'un idle timeout : la combinaison lève LogicException, quel que soit l'ordre de préparation. setIdleTimeout(null) retire ce délai et reste distinct de son activation. Changer la collecte avec disableOutput() ou enableOutput() pendant l'exécution lève RuntimeException. Le statut final et le délai total restent utilisables.

Les deux délais

À retenir en priorité
  1. Deux horloges surveillent le process.
  2. La première limite atteinte peut l'interrompre.

🌍 In Real Life

La situation : l'équipe du blog borne la durée de conversion et le silence entre deux nouvelles du convertisseur. Un opérateur vérifie les deux montres.

L’équivalent dans Symfony : durée depuis le départ → timeout total ; temps depuis la dernière sortie → idle timeout ; contrôle de l'opérateur → vérification par le parent.

Retour à la réalité technique : le silence ne prouve pas l'absence de calcul. Après start(), une surveillance adaptée reste nécessaire ; la configuration d'un délai n'est pas un gardien indépendant du processus parent.

🧠 Comment le mémoriser : « Deux montres, un contrôle. » Image mentale : départ et dernière nouvelle sur deux cadrans. Question-réflexe : mesure-t-on le temps total ou le silence observé ?

⚠️ À ne pas confondre : sortie produite et progrès métier réel.

Le convertisseur peut rester vivant sans produire de résultat. Un calcul silencieux peut pourtant progresser : le délai d'inactivité mesure une absence de sortie observée, pas une absence de travail métier.

  • setTimeout() borne la durée totale : 60 secondes par défaut.
  • setIdleTimeout() borne le temps depuis la dernière sortie.
  • Lors d'un contrôle, un dépassement détecté arrête le process et lève ProcessTimedOutException.

checkTimeout() teste d'abord le délai total, puis l'inactivité. Si les deux sont déjà dépassés au moment où le parent reprend le contrôle, c'est le dépassement total qui est signalé, pas nécessairement celui dont l'échéance était chronologiquement la plus proche.

Avec un interpréteur PHP 8.4 CLI pour le parent et Process 8.0 chargé, cet enfant minimal permet d'observer une réussite sans outil de conversion :

<?php
use Symfony\Component\Process\Process;

$process = new Process([PHP_BINARY, '-r', 'fwrite(STDOUT, "ready\n");']);
$process->setTimeout(5);
$process->setIdleTimeout(2);
$process->mustRun();
echo $process->getOutput();

Sortie attendue : ready suivi d'un saut de ligne. L'enfant termine normalement à 0 ; cela ne dit rien de la réussite d'un import qui n'est pas exécuté ici. Les délais doivent convenir au vrai programme, notamment à ses phases silencieuses.

Après un lancement asynchrone, le parent doit continuer les contrôles. Dans le scénario suivant, l'enfant Unix est encore en cours à 1,5 s :

À 1,5 s, sleep 3 limité à 1 s Résultat
isRunning(), getOutput() rien n'est levé
checkTimeout() ProcessTimedOutException
wait() ProcessTimedOutException : il vérifie le délai en attendant

stop() envoie d'abord SIGTERM, puis, si le process tourne encore à l'échéance (10 s par défaut), le signal passé — SIGKILL par défaut.

Si l'enfant réagit à SIGTERM, il n'est pas nécessaire d'attendre toute la période ni d'envoyer le second signal. Cet arrêt n'annule pas les fichiers déjà produits ; prévoir leur publication et leur nettoyage avec Filesystem. Les signaux restent dépendants de la plateforme.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un process async n'est pas surveillé par magie.
  2. isRunning() seul ne remplace pas ce contrôle.
  • Voir l’explication : L'array d'arguments est la forme recommandée

    L'array d'arguments est la forme recommandée ; la string transfère l'escaping et la portabilité à l'appelant.

  • Voir l’explication : Le délai par défaut est de 60 secondes

    Le délai par défaut est de 60 secondes, et sur un process asynchrone il faut appeler checkTimeout() soi-même.

  • Voir l’explication : disableOutput() interdit l'activation d'un idle timeout.

    disableOutput() interdit l'activation d'un idle timeout. Retirer ce délai par setIdleTimeout(null) n'est pas l'activer.

  • Voir l’explication : Pour retirer une variable d'environment héritée, il faut la mettre à false

    Pour retirer une variable d'environment héritée, il faut la mettre à false — passer d'autres variables ne la retire pas.

  • Voir l’explication : stop() commence par SIGTERM

    stop() commence par SIGTERM ; SIGKILL n'arrive qu'à l'échéance.

  • Voir l’explication : wait() vérifie le délai

    wait() vérifie le délai, mais isRunning() et getOutput() non.

Fiche express

À mémoriser

À retenir en priorité
  1. Sans output observé le délai idle n'a pas de mesure.
  2. Le component refuse cette combinaison.

Le lot sélectionné peut maintenant traverser un programme externe sous surveillance. La preuve attendue reste précise : lancement, fin, code et sortie validée sont quatre observations, pas un seul « succès ».

Si tu dois retenir seulement 7 choses :

  • Array recommandé ; string = shell, escaping à votre charge, "${:NOM}".
  • run() attend et rend le code ; mustRun() lève ; start() rend la main.
  • Délai total 60 s par défaut ; idle = depuis la dernière sortie.
  • Asynchrone : checkTimeout() à appeler ; wait() vérifie aussi.
  • disableOutput() interdit getOutput() et l'activation d'un idle timeout.
  • Variable héritée retirée seulement par false.
  • stop() : SIGTERM, puis SIGKILL à l'échéance.

Moyen mnémotechnique : « Lancer, attendre, couper ».

Revenir à Filesystem pour publier seulement les résultats complets. Si la conversion doit être différée hors de la requête, comparer les transports Messenger plutôt que supposer qu'un enfant survivra seul au parent HTTP.
