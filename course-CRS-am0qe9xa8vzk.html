Objectif

Exécuter un programme externe, savoir quand l'appel rend la main, et savoir ce qui l'interrompt.

L'essentiel

À comprendre

À retenir en priorité
  1. Les arguments restent littéraux.
  2. Le shell n'est pas nécessaire pour un exécutable simple.

Process exécute un programme externe dans un sous-processus, en gérant les différences entre systèmes et l'escaping des arguments ; il remplace exec(), passthru(), shell_exec() et system(). Trois questions décident de tout : la forme de la command (array ou string), le moment où l'appel rend la main, et ce qui l'interrompt — deux délais et stop().

Le schéma

À retenir en priorité
  1. Le mode d'attente et la gestion d'erreur sont distincts.
  2. Un démarrage async exige un suivi.

Bleu : appels ; ambre : état ; vert : fin observable. Cette boucle est un modèle, pas une boucle PHP à copier sans pause : éviter une attente active coûteuse. wait() gère l'attente bloquante ; start() ne crée ni daemon supervisé ni garantie de survie après la fin du processus parent.

L'exemple : lister un dossier

Exemple concret

À retenir en priorité
  1. La valeur n'est pas interprétée par un shell.
  2. La forme array protège les frontières d'arguments.
$process = new Process(['ls', '-lsa']);
$process->setTimeout(120);
$process->run();

if (!$process->isSuccessful()) {
    throw new ProcessFailedException($process);
}
echo $process->getOutput();

Cet exemple et les questions sur sleep, SIGTERM et SIGKILL supposent Unix. La sortie de ls dépend du répertoire courant. Le tableau d'arguments protège la séparation des arguments, mais il faut encore valider les options acceptées par le programme cible (et utiliser -- quand il le prend en charge).

Array ou string

À retenir en priorité
  1. Le shell apporte pipes et redirections.
  2. Il ajoute une responsabilité d'échappement.
  • Le array d'arguments est la forme recommandée : pas d'escaping manuel, les signaux passent. ['printf', '%s', 'a b;c $HOME'] affiche a b;c $HOME, littéral.
  • Une string, par Process::fromShellCommandline(), sert aux fonctionnalités du shell (>, |) ; les valeurs passent par des variables d'environment, "${:NOM}" restant portable. Une valeur non fournie lève une InvalidArgumentException au lancement.
  • Un process hérite de toutes les variables du système ; passer ['OTHER' => 'x'] laisse une variable non nommée toujours héritée : pour en retirer une, la passer à false.

Trois façons de lancer

À retenir en priorité
  1. Le retour immédiat n'est pas une réussite finale.
  2. wait() peut attendre la fin.
Appel Rend la main En cas d'échec
run() à la fin du process rend un exit code
mustRun() à la fin du process lève ProcessFailedException
start() immédiatement rien : à vous de vérifier

Ce tableau compare les codes de sortie non nuls. Un lancement peut lui-même lever une exception. mustRun() ne lève ProcessFailedException que si le programme termine en échec, pas à chaque appel.

Après start(), isRunning() interroge l'état et wait() bloque. ExecutableFinder trouve le path d'un exécutable, PhpExecutableFinder celui du binaire PHP.

Récupérer l'output

À retenir en priorité
  1. Le flux peut être suivi par morceaux.
  2. Le buffer complet reste une autre vue.

getOutput() et getErrorOutput() rendent tout ; getIncrementalOutput() seulement ce qui est arrivé depuis le dernier appel. disableOutput() économise la mémoire mais interdit ces lectures et setIdleTimeout() — dans les deux ordres, LogicException ; pendant l'exécution, RuntimeException.

Les deux délais

À comprendre

À retenir en priorité
  1. Deux horloges surveillent le process.
  2. La première limite atteinte peut l'interrompre.

C'est quoi ?

Process lance un programme enfant et permet d'observer son état, sa sortie et son résultat. Un timeout total borne la durée globale ; un idle timeout borne la durée sans nouvelle sortie.

À quoi ça sert ?

Un programme peut être bloqué tout en gardant son processus vivant. Les limites doivent être surveillées ; démarrer de façon asynchrone ne fournit pas un surveillant autonome qui fera tous les contrôles à la place du caller.

Où dans Symfony ?

run() attend et donne le code de sortie. mustRun() lève une ProcessFailedException en cas de code non nul. start() démarre sans attendre ; wait() ou une boucle appropriée doit ensuite gérer la fin, les limites et le résultat. stdout et stderr sont deux flux distincts, tous deux utiles au diagnostic.

Comment, étape par étape ?

  1. Construire de préférence un tableau d'arguments : chaque élément est un argument, sans concaténation de syntaxe shell.
  2. Définir les limites avant le lancement ; le timeout total par défaut est 60 secondes.
  3. En attente synchrone, laisser Process contrôler les limites. Dans une boucle asynchrone, appeler checkTimeout() ; isRunning() seul ne remplace pas ce contrôle.
  4. Lire les flux et vérifier le code final. Une sortie stderr ne signifie pas automatiquement échec, et une sortie stdout ne garantit pas succès.

Exemple concret PHP

Avec Process installé et un interpréteur PHP 8.4 sélectionné pour le script parent :

<?php
use Symfony\Component\Process\Process;

$process = new Process([PHP_BINARY, '-r', 'fwrite(STDOUT, "ready\n");']);
$process->setTimeout(5);
$process->setIdleTimeout(2);
$process->mustRun();
echo $process->getOutput();

L'enfant écrit ready puis se termine. Si le binaire échoue, l'exception remonte ; rien n'annonce faussement un succès. Aucun shell n'est nécessaire pour cet exemple.

Contre-exemple : désactiver la collecte de sortie puis attendre qu'un idle timeout détecte le silence. Correction : ce délai dépend de l'observation des sorties et n'est pas compatible avec leur désactivation. Un calcul légitimement silencieux peut atteindre cette limite même s'il progresse ; choisir le bon critère.

Le tableau d'arguments évite l'interprétation shell, pas les options propres au programme appelé : un nom commençant par - peut encore devenir une option. Valider le binaire et les valeurs, employer -- lorsque le programme le prévoit, et contrôler l'environment transmis sans journaliser de secrets. Les signaux et la gestion asynchrone restent dépendants de la plateforme.

Process 8.0.

Passage canonique conservé
  • setTimeout() borne la durée totale : 60 secondes par défaut.
  • setIdleTimeout() borne le temps depuis la dernière sortie.
  • Le premier dépassé expire le process : ProcessTimedOutException.

Sur un process asynchrone, personne ne surveille le délai :

À 1,5 s, sleep 3 limité à 1 s Résultat
isRunning(), getOutput() rien n'est levé
checkTimeout() ProcessTimedOutException
wait() ProcessTimedOutException : il vérifie le délai en attendant

stop() envoie d'abord SIGTERM, puis, si le process tourne toujours à l'échéance (10 s par défaut), le signal passé — SIGKILL par défaut.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Un process async n'est pas surveillé par magie.
  2. isRunning() seul ne remplace pas ce contrôle.
  • Voir l’explication : L'array d'arguments est la forme recommandée

    L'array d'arguments est la forme recommandée ; la string transfère l'escaping et la portabilité à l'appelant.

  • Voir l’explication : Le délai par défaut est de 60 secondes

    Le délai par défaut est de 60 secondes, et sur un process asynchrone il faut appeler checkTimeout() soi-même.

  • Sortie désactivée et délai d’inactivité

    disableOutput() interdit aussi setIdleTimeout().

  • Voir l’explication : Pour retirer une variable d'environment héritée, il faut la mettre à false

    Pour retirer une variable d'environment héritée, il faut la mettre à false — passer d'autres variables ne la retire pas.

  • Voir l’explication : stop() commence par SIGTERM

    stop() commence par SIGTERM ; SIGKILL n'arrive qu'à l'échéance.

  • Voir l’explication : wait() vérifie le délai

    wait() vérifie le délai, mais isRunning() et getOutput() non.

Fiche express

À mémoriser

À retenir en priorité
  1. Sans output observé le délai idle n'a pas de mesure.
  2. Le component refuse cette combinaison.

Si tu dois retenir seulement 7 choses :

  • Array recommandé ; string = shell, escaping à votre charge, "${:NOM}".
  • run() attend et rend le code ; mustRun() lève ; start() rend la main.
  • Délai total 60 s par défaut ; idle = depuis la dernière sortie.
  • Asynchrone : checkTimeout() à appeler ; wait() vérifie aussi.
  • disableOutput() interdit getOutput() et setIdleTimeout().
  • Variable héritée retirée seulement par false.
  • stop() : SIGTERM, puis SIGKILL à l'échéance.

Moyen mnémotechnique : « Lancer, attendre, couper ».
