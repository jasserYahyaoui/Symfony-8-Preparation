Objectifs d’apprentissage

  • Lister les routes dans leur ordre d'évaluation

  • Utiliser router:match pour diagnostiquer une URL

Nuance à connaître

Précision, exception ou condition d’application d’une règle.

Objectif

Savoir diagnostiquer un problème de routage avec les deux commands prévues pour cela : lire la liste des routes dans l'ordre où Symfony les essaie, en filtrer ou en détailler une, et demander directement quelle route répondrait à un path donné, avec sa method, son host et son schéma.

L'essentiel

À comprendre

À retenir en priorité
  1. Le défaut teste GET sur localhost.
  2. Aucune correspondance produit un exit code 1.

Deux commands de FrameworkBundle diagnostiquent le routage : debug:router liste les routes dans l'ordre où Symfony les essaie, et router:match rejoue un appel pour dire laquelle répond. La première route qui correspond gagne ; une route peut correspondre par son path et être écartée par sa method, son host ou son schéma.

Le schéma

À retenir en priorité
  1. La liste révèle les routes qui masquent les suivantes.
  2. Ce n'est pas un tri alphabétique.

L'exemple

Exemple concret

Nom Path Restrictions
blog_list /blog aucune
blog_show /blog/{slug} method GET
blog_new /blog/new methods GET et POST
api_post_edit /api/posts/{id} method PUT, host api.example.com, schéma https

/blog/{slug} est déclaré avant /blog/new : en GET, /blog/new est servi par blog_show, avec $slug = 'new'.

`debug:router` : la liste, dans l'ordre d'évaluation

La command « lists all your application routes in the same order in which Symfony evaluates them » — ni alphabétique ni par file. Sur l'exemple, blog_show est listée au-dessus de blog_new : le bug se lit dans la liste.

  • L'ordre est celui de la déclaration, puis la priority : « Routes with higher priority are sorted before routes with lower priority », défaut
  • Une route déclarée en dernier avec priority: 2 est listée et évaluée en premier.
  • ANY veut dire « aucune restriction » ; les colonnes Scheme et Host n'apparaissent que si une route en restreint un.

Les options de `debug:router`

À comprendre

À retenir en priorité
  1. Le filtre conserve les routes compatibles.
  2. --method=ANY sélectionne seulement les routes sans restriction.

C'est quoi ?

Les options de debug:router changent les informations affichées et leur sélection. Elles ne changent pas la configuration de la route ni n'exécutent son controller. Le détail d'un nom permet d'inspecter son path, ses restrictions, ses defaults et ses options.

À quoi ça sert ?

Un inventaire volumineux devient exploitable en filtrant par méthode, en affichant les controllers ou en choisissant une sortie structurée. Il faut comprendre le filtre : une route sans restriction de méthode participe aussi aux requêtes GET.

Où dans Symfony ?

show-controllers et show-aliases ajoutent les informations correspondantes. method GET inclut les routes GET et celles sans restriction ; method ANY sélectionne seulement ces dernières. format choisit txt, xml, json ou md ; raw demande la forme brute. Un nom partiel peut nécessiter un choix parmi plusieurs résultats.

Comment, étape par étape ?

  1. Examiner la collection dans son ordre effectif.
  2. Ajouter la colonne utile au diagnostic.
  3. Filtrer sans confondre ANY et toutes les routes de toutes les méthodes.
  4. Ouvrir le détail du nom exact avant de modifier sa déclaration.

Exemple concret shell

Dans l'application à inspecter :

php bin/console debug:router --show-controllers --show-aliases
php bin/console debug:router --method=GET
php bin/console debug:router --method=ANY --format=json

La dernière commande exporte les routes non restreintes, pas toute la collection. Contre-exemple : retirer du diagnostic une route marquée ANY parce que l'incident concerne GET. Correction : la considérer comme candidate aussi, puis vérifier son ordre et ses autres restrictions. Une absence dans une liste filtrée n'est pas une preuve d'absence dans la collection complète.

Passage canonique conservé

Les options de debug:router

Écriture Effet
debug:router <nom> le détail d'une route : path, regex, host, schéma, methods, requirements, defaults, options
--show-controllers une colonne Controller
--show-aliases une colonne Aliases
--method=GET les routes GET… et celles sans restriction
--method=ANY seulement les routes sans restriction de method
--format=json txt (défaut), xml, json, md ; sinon « Unsupported format "…" »
--raw sortie brute

L'argument peut être un nom partiel, casse ignorée : un seul résultat affiche son détail ; plusieurs, un choix (ou la liste en non interactif) ; aucun, « The route "…" does not exist. » et l'exit code 1.

`router:match` : quelle route répondrait

À comprendre

C'est quoi ?

debug:router décrit la collection et l'ordre des routes ; router:match simule la recherche d'une correspondance pour un chemin et un contexte. Ce sont des outils de routage, pas une exécution de l'action et de tous ses effets.

À quoi ça sert ?

La liste permet d'identifier une route générale placée avant une route spécifique. La simulation montre pourquoi un candidat ne correspond pas : chemin, host, méthode ou autre restriction. Ces outils évitent de déduire le routage uniquement d'une réponse HTTP finale qui peut avoir été modifiée plus tard.

Où dans Symfony ?

FrameworkBundle fournit ces commandes. L'argument de router:match est un path, pas une URL complète ; host, scheme et method se donnent par options. Sans préciser le host et la méthode, le contexte de diagnostic usuel est localhost et GET, qui peut différer fortement de la requête réelle.

Comment, étape par étape ?

  1. Examiner debug:router pour l'ordre effectif, pas l'ordre alphabétique des noms.
  2. Afficher le détail d'une route suspecte et ses requirements/defaults.
  3. Simuler le chemin avec la méthode, le host et le schéma réels.
  4. Ajouter la verbosité pour comprendre les rejets ; si le matching est correct, poursuivre le diagnostic dans le traitement HTTP plutôt que modifier la route sans preuve.

Exemple concret shell

Dans une application possédant une route de mise à jour de rapport :

php bin/console debug:router --show-controllers
php bin/console debug:router report_update
php bin/console router:match /reports/42 --method=PATCH --host=api.example.test --scheme=https -v

La dernière commande évalue ce contexte précis sans exécuter la mise à jour du rapport. Contre-exemple : passer https://api.example.test/reports/42 comme argument path et conclure que la route est absente. Correction : séparer chemin et options comme ci-dessus. ANY dans la liste signifie absence de restriction de méthode ; filtrer GET inclut aussi ces routes. Le succès du diagnostic ne prouve pas que les données du controller, l'autorisation ou la validation réussiront ensuite.

Passage canonique conservé

router:match : quelle route répondrait

  • L'argument est un path (path_info), pas une URL : method, host et schéma passent par --method, --host, --scheme.
  • Sans option : un GET sur localhost.
  • RouterMatchCommand s'appuie sur TraceableUrlMatcher et ses trois niveaux de trace :
Situation Affichage
correspond presque « Route "…" almost matches but … », avec la raison
correspond « [OK] Route "…" matches », puis le détail ; exit code 0
aucune route « [ERROR] None of the routes match the path "…" » ; exit code 1
-v en plus, chaque route qui ne correspond pas, avec la raison

router:match /blog/new répond blog_show : déclarer blog_new avant, ou lui donner une priority plus haute.

router:match est un simulateur d'itinéraire : il explique aussi les routes presque compatibles. Lui donner le bon path mais oublier host ou method revient à simuler le trajet depuis le mauvais contexte.

Pièges d'examen

Piège à éviter

  • Voir l’explication : L'ordre de debug:router n'est pas alphabétique.

    L'ordre de debug:router n'est pas alphabétique. C'est l'ordre dans lequel Symfony évalue les routes, et donc l'explication de « pourquoi est-ce l'autre route qui répond ? ». Un énoncé qui parle de tri par nom ou par path se trompe.

  • Voir l’explication : Une route paramétrée déclarée plus haut intercepte un path fixe.

    Une route paramétrée déclarée plus haut intercepte un path fixe. Avec /blog/{slug} avant /blog/new, le path /blog/new en GET est servi par la route de l'article : la première correspondance gagne, même si une route plus précise existe plus bas.

  • Voir l’explication : La priority change l'ordre affiché.

    La priority change l'ordre affiché. Une route déclarée en dernier mais avec priority: 2 est listée et évaluée avant les routes de priority 0 ; debug:router montre cet ordre réel, pas l'ordre des files.

  • Voir l’explication : --method=POST n'affiche pas que les routes POST.

    --method=POST n'affiche pas que les routes POST. Les routes sans restriction de method acceptent tout verbe et restent dans la liste filtrée ; --method=ANY, à l'inverse, n'affiche que celles-là.

  • Voir l’explication : router:match prend un path, pas une URL.

    router:match prend un path, pas une URL. Host, schéma et method passent par --host, --scheme et --method.

  • Voir l’explication : Sans options, router:match teste un GET sur localhost.

    Sans options, router:match teste un GET sur localhost. Une route restreinte à un host ou à une autre method y apparaît au mieux en « almost matches », et la command finit en erreur.

  • Voir l’explication : Aucune correspondance, c'est l'exit code 1.

    Aucune correspondance, c'est l'exit code 1. Ni 0 avec une table vide, ni un code calqué sur HTTP : un script peut s'appuyer dessus.

  • Voir l’explication : Un nom partiel suffit à debug:router, et la casse est ignorée.

    Un nom partiel suffit à debug:router, et la casse est ignorée. Avec plusieurs résultats, la command demande de choisir, ou liste les routes en mode non interactif.

Application

À retenir en priorité
  1. Le défaut teste GET sur localhost.
  2. Aucune correspondance produit un exit code 1.
  3. Le filtre conserve les routes compatibles.
  4. --method=ANY sélectionne seulement les routes sans restriction.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • debug:router : les routes dans l'ordre d'évaluation.
  • Ordre : déclaration, puis priority (défaut 0) ; la première qui correspond gagne.
  • --method=X garde aussi les routes ANY ; --method=ANY ne garde qu'elles.
  • Nom partiel, casse ignorée.
  • router:match : un path ; défaut GET sur localhost.
  • « almost matches » + raison ; aucune route : exit code 1.

Moyen mnémotechnique : « debug LISTE, match TESTE ».

ROUTES ESSAYÉES DANS L'ORDRE (déclaration, puis priority) → LA PREMIÈRE QUI CORRESPOND GAGNE
  debug:router  → montre cet ordre (filtres : --method, détail : <nom partiel>)
  router:match  → rejoue un path dans un contexte (--method --host --scheme)
                  → almost matches + raison · OK + détail · sinon exit 1
