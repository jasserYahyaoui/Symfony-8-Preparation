Objectif

Signaler une violation depuis un callback ou un validator, et savoir laquelle des deux methods du contexte utiliser.

L'essentiel

À comprendre

À retenir en priorité
  1. Le builder prépare la violation.
  2. addViolation() l'enregistre.

Le contexte d'exécution signale une violation de deux façons : directement, ou par un builder qu'on configure — field visé, code, parameters — puis qu'on enregistre par addViolation(). L'oubli de ce dernier appel est le piège central : la règle échoue, et la validation passe.

Le schéma

À retenir en priorité
  1. Le path situe l'erreur.
  2. Le code permet un traitement machine stable.

Bleu = contexte d'exécution ; ambre = construction sans effet sur la liste ; vert = violation enregistrée. Les flèches sont des appels, pas de l'héritage. Configurer plusieurs options ne crée pas plusieurs violations ; oublier l'appel final n'en crée aucune, même si d'autres règles ont déjà échoué.

L'exemple : une adresse déjà réservée

Exemple concret

À retenir en priorité
  1. Le path et la valeur sont indépendants.
  2. Régler les deux si nécessaire.
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Context\ExecutionContextInterface;

#[Assert\Callback('check')]
class Registration
{
    public const EMAIL_TAKEN = 'EMAIL_TAKEN';
    public string $email = '';

    private function isReserved(string $email): bool
    {
        return 'reserved@example.com' === $email;
    }

    public function check(ExecutionContextInterface $context): void
    {
        if ($this->isReserved($this->email)) {
            $context->buildViolation('L\'adresse {{ value }} est déjà prise.')
                ->setParameter('{{ value }}', $this->email)
                ->atPath('email')
                ->setCode(self::EMAIL_TAKEN)
                ->setInvalidValue($this->email)
                ->addViolation();
        }
    }
}

Les deux façons

À retenir en priorité
  1. Le contexte peut enregistrer directement.
  2. Le builder permet une configuration supplémentaire.
Method du contexte Effet
addViolation('msg', [params]) enregistre immédiatement, au path courant
buildViolation('msg', [params]) rend un builder : field, code, valeur fautive réglables

Seul le builder permet de choisir le field visé, le code ou la valeur fautive.

Le builder n'écrit rien tout seul

Piège à éviter

À retenir en priorité
  1. Configurer n'écrit pas dans la liste.
  2. L'oubli final laisse la validation réussir.

C'est quoi ?

buildViolation crée un builder, objet de préparation d'une violation. Le builder permet d'en préciser le chemin, les paramètres, le code et d'autres métadonnées ; il n'enregistre la violation que lorsque sa méthode addViolation est appelée.

À quoi ça sert ?

Une règle portant sur un objet entier peut présenter l'erreur près d'un champ précis et conserver un code exploitable par un programme. La préparation en plusieurs appels distingue les détails de l'erreur de l'acte final qui l'ajoute au résultat du validator.

Où dans Symfony ?

Le contexte possède aussi addViolation, qui enregistre directement au chemin courant. Ce n'est pas un builder. Sur le builder, atPath compose un chemin relatif au contexte de validation ; il ne change pas automatiquement la valeur enregistrée comme invalide. setInvalidValue permet de la préciser séparément.

Comment, étape par étape ?

  1. Choisir un message avec des paramètres plutôt qu'une concaténation de données.
  2. Construire le builder depuis le contexte.
  3. Régler le chemin et les métadonnées utiles.
  4. Terminer par addViolation et vérifier que le résultat du validator contient réellement l'erreur.

Exemple concret PHP

Fonction appelée depuis une règle avec le contexte de validation d'un objet et la valeur de son champ end :

<?php
use Symfony\Component\Validator\Context\ExecutionContextInterface;

function reportInvalidEnd(ExecutionContextInterface $context, int $end): void
{
    $context->buildViolation('La valeur {{ value }} précède le début.')
        ->setParameter('{{ value }}', (string) $end)
        ->atPath('end')
        ->setInvalidValue($end)
        ->setCode('END_BEFORE_START')
        ->addViolation();
}

La règle appelante décide quand la relation est invalide ; cette fonction enregistre son diagnostic. Contre-exemple : retirer le dernier appel puis attendre une erreur de formulaire. Aucun enregistrement n'a eu lieu. Correction : terminer la chaîne. Le message modèle reste accessible par getMessageTemplate et le message résolu par getMessage ; un code stable ne doit pas être extrait du texte traduit.

Passage canonique conservé

buildViolation() ne crée aucune violation : elle prépare un object. Tant que addViolation() n'est pas appelée au bout de la chaîne d'appels, rien n'est enregistré. addViolation() existe donc des deux côtés : sur le contexte, elle enregistre ; sur le builder, elle termine la chaîne d'appels.

Ce que l'on peut régler

À retenir en priorité
  1. Le code identifie la règle en échec.
  2. La cause aide au diagnostic.

Les dix methods de ConstraintViolationBuilderInterface (8.0, relues par réflexion) :

Method Effet
atPath() ajoute un chemin relatif au chemin courant
setParameter() / setParameters() remplit les emplacements {{ … }}
setCode() un code machine stable, lu par getCode()
setInvalidValue() la valeur affichée comme fautive
setPlural() le nombre qui choisit la forme plurielle
setTranslationDomain() / disableTranslation() le traitement du message
setCause() la cause technique, pour le debug
addViolation() enregistre, en fin de chaîne d'appels
  • Sans atPath(), une violation de class conserve le path courant de l'object : vide à la racine de validation, mais par exemple child pour un objet imbriqué. Sa construction ne décide pas à elle seule de l'emplacement dans un formulaire : celui-ci dépend du mapping et du bubbling des erreurs. Pour l'objet du formulaire racine, avec le mapping standard sans redirection d'erreur, une violation au path vide reste sur ce formulaire, pas sur un field particulier.
  • Le path se compose : depuis la racine, atPath('address.city') donne address.city ; depuis addresses[0], atPath('city') donne addresses[0].city. Ce n'est pas un chemin absolu qui efface le préfixe.
  • atPath() ne change pas la valeur fautive : elle reste l'object entier ; setInvalidValue() la corrige.

Les emplacements du message

À retenir en priorité
  1. Le template reste traduisible.
  2. Les parameters portent les valeurs variables.

Le message porte des emplacements {{ … }}, remplis par setParameter(). C'est ce qui permet de le traduire sans y concaténer la valeur. La violation garde les deux formes : getMessageTemplate() rend le modèle, getMessage() le texte rempli.

Une constraint sur mesure

À comprendre

À retenir en priorité
  1. Le nom de validator suit une convention.
  2. validatedBy() permet de choisir autrement.
  3. La cible PHP autorise le placement de l'attribute.
  4. getTargets() déclare séparément le scope de validation.

C'est quoi ?

Une contrainte personnalisée sépare sa configuration, portée par une classe Constraint, du contrôle, porté par une classe ConstraintValidator. Par défaut, validatedBy() associe le nom de la contrainte au même nom suivi de Validator. Le builder de violation prépare un constat d'échec ; seul son addViolation() l'enregistre.

À quoi ça sert ?

Cette séparation permet de réutiliser une règle avec ses messages et groupes, au lieu de recopier une condition dans plusieurs controllers. Elle distingue une mauvaise contrainte transmise au validator, une donnée d'un type inattendu et une valeur du bon type qui enfreint la règle.

Où dans Symfony ?

Dans validate(mixed $value, Constraint $constraint): void, UnexpectedTypeException signale une contrainte inadaptée ; UnexpectedValueException signale un type de donnée inattendu. Le traitement de null et du vide doit être choisi explicitement. Les contraintes de format les ignorent souvent pour laisser une contrainte de présence décider si une valeur est obligatoire.

Comment, étape par étape ?

  1. Vérifier le type de contrainte.
  2. Traiter le vide selon le contrat, puis vérifier le type de donnée.
  3. Tester la règle de format.
  4. Construire la violation avec son message et ses paramètres, puis l'enregistrer. atPath() ajoute un chemin relatif au contexte courant : ne pas y répéter un préfixe déjà présent.

Exemple concret PHP

Déclarations complètes, avec Validator 8.0 chargé par l'application. La contrainte peut être passée directement à validate($value, new LowercaseCode()) ; cet exemple ne déclare pas son usage comme attribute PHP.

<?php
use Symfony\Component\Validator\Constraint;
use Symfony\Component\Validator\ConstraintValidator;
use Symfony\Component\Validator\Exception\UnexpectedTypeException;
use Symfony\Component\Validator\Exception\UnexpectedValueException;

final class LowercaseCode extends Constraint
{
    public string $message = 'Le code {{ value }} doit contenir seulement des lettres minuscules.';
}

final class LowercaseCodeValidator extends ConstraintValidator
{
    public function validate(mixed $value, Constraint $constraint): void
    {
        if (!$constraint instanceof LowercaseCode) {
            throw new UnexpectedTypeException($constraint, LowercaseCode::class);
        }
        if (null === $value || '' === $value) {
            return;
        }
        if (!is_string($value)) {
            throw new UnexpectedValueException($value, 'string');
        }
        if (!preg_match('/^[a-z]+$/D', $value)) {
            $this->context->buildViolation($constraint->message)
                ->setParameter('{{ value }}', $value)
                ->addViolation();
        }
    }
}

abc satisfait la règle, Abc produit une violation. Contre-exemple : retirer le dernier addViolation() ; le message est préparé mais aucune erreur n'est ajoutée. Correction : terminer le builder. Pour un code obligatoire, ajouter NotBlank : le retour anticipé sur le vide est délibéré. Les paramètres du message servent à la traduction ; ils ne constituent pas une garantie d'échappement HTML lors de son affichage.

Passage canonique conservé

Le builder sert d'abord dans un ConstraintValidator : une class Slug (extends Constraint) et sa class SlugValidator.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function validate(mixed $value, Constraint $constraint): void
{
    if (!$constraint instanceof Slug) {
        throw new UnexpectedTypeException($constraint, Slug::class);
    }
    if (null === $value || '' === $value) {
        return;
    }
    if (!is_string($value)) {
        throw new UnexpectedValueException($value, 'string');
    }
    if (!preg_match('/^[a-z0-9-]+$/', $value)) {
        $this->context->buildViolation($constraint->message)
            ->setParameter('{{ value }}', $value)
            ->addViolation();
    }
}
  • validatedBy() rend par défaut le nom de la class suivi de Validator.
  • Le validator reçoit null : le return est son travail, pour laisser NotNull ou NotBlank décider.
  • UnexpectedValueException devient une violation ; UnexpectedTypeException remonte : c'est une erreur de code.
  • getTargets() vaut PROPERTY_CONSTRAINT : posée sur une class, la constraint lève une ConstraintDefinitionException.
  • En 8.0, une option se déclare dans le constructor, qui appelle parent::__construct(null, $groups, $payload).

Pour une constraint utilisée en attribute de class, deux déclarations ont des rôles différents : la cible PHP Attribute::TARGET_CLASS autorise le placement de l'attribute ; getTargets() doit aussi annoncer Constraint::CLASS_CONSTRAINT au Validator. La cible PHP seule ne change pas la portée du Validator.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le validator reçoit null.
  2. La séparation présence et format doit être explicite.
  • Voir l’explication : buildViolation() seule n'enregistre rien.

    buildViolation() seule n'enregistre rien. Sans addViolation() au bout de la chaîne d'appels, la validation passe alors que la règle est violée.

  • Voir l’explication : addViolation() existe des deux côtés

    addViolation() existe des deux côtés : sur le contexte, elle enregistre directement ; sur le builder, elle termine la chaîne d'appels. Ce ne sont pas les mêmes methods.

  • Voir l’explication : Sans atPath(), une violation de portée class garde le path de l'object courant

    Sans atPath(), une violation de portée class garde le path de l'object courant, pas nécessairement un path vide. Le placement dans un formulaire dépend ensuite du mapping et du bubbling ; ne pas en déduire une position universelle en tête du formulaire racine.

  • Chemin de violation et valeur fautive

    atPath() déplace le path, pas la valeur fautive.

  • Voir l’explication : Le traitement de null appartient au validator.

    Le traitement de null appartient au validator. Une règle de format l'ignore généralement pour laisser NotNull ou NotBlank gérer la présence ; une contrainte dont le rôle est précisément d'exiger une valeur le refuse.

Fiche express

À mémoriser

À retenir en priorité
  1. Conserver le modèle facilite la traduction.
  2. Le message final contient les parameters.

Si tu dois retenir seulement 6 choses :

  • addViolation() du contexte : immédiat ; buildViolation() : un builder.
  • Le builder n'enregistre rien sans ->addViolation() à la fin.
  • atPath() ajoute un path relatif ; sans lui, le path courant reste inchangé, vide seulement à la racine de validation. Le mapping du form décide ensuite du placement.
  • atPath() ne change pas la valeur fautive : setInvalidValue().
  • setParameter() remplit {{ … }} ; setCode() donne un code stable.
  • Constraint maison : SlugValidator par défaut, return sur null, UnexpectedValueException → violation.

Moyen mnémotechnique : « Construire, viser, coder, ajouter ».
