Objectif

Séparer le component Routing de ce que FrameworkBundle en fait dans une application, et savoir quel morceau vient d'où. La déclaration d'une route est traitée par l'item Configuration (YAML and PHP attributes).

L'essentiel

À comprendre

À retenir en priorité
  1. RouterListener appartient à HttpKernel.
  2. FrameworkBundle l'enregistre. RouterListener, dans HttpKernel, convertit les erreurs de matching en exceptions HTTP 404 ou 405 (avec Allow).

Le component Routing fait correspondre une Request à des variables — _controller n'en est qu'une — et ne dépend d'aucun autre component Symfony. Apparier et générer sont deux classes distinctes. FrameworkBundle câble le tout : router compilé, matcher qui sait rediriger, loader des attributes, et RouterListener — une class de HttpKernel, pas du bundle.

Exemple concret

À retenir en priorité
  1. UrlMatcher transforme une URL en variables.
  2. UrlGenerator effectue le trajet inverse.
// route post : /post/{id}, defaults _controller et page = 1
// GET /post/7 → attributes de la Request :
['_controller' => 'App\C::show', 'page' => 1, 'id' => '7',
 '_route' => 'post', '_route_params' => ['page' => 1, 'id' => '7']];

Le component

À comprendre

C'est quoi ?

Le component Routing associe une requête à des variables de configuration et sait effectuer l'opération inverse pour produire une URL. Le matching, recherche de correspondance, ne signifie pas exécution du controller. Le generator, générateur, produit une adresse à partir d'un nom de route et de paramètres.

À quoi ça sert ?

Séparer les deux opérations permet d'utiliser le routage sans application FrameworkBundle, ou de générer un lien hors du traitement d'une requête. Le component est réutilisable ; FrameworkBundle est l'intégration qui configure ses services, ses loaders et son branchement au cycle HTTP.

Où dans Symfony ?

Route décrit une route ; RouteCollection maintient un ensemble ordonné ; RequestContext porte le host, la méthode, le schéma et les informations de base ; UrlMatcher cherche une correspondance ; UrlGenerator produit une URL. Router assemble un loader, un matcher et un generator. FrameworkBundle ajoute notamment le chargement de configuration habituel et les commandes de diagnostic.

Comment, étape par étape ?

  1. Définir les routes et leurs noms dans une collection.
  2. Fournir un contexte cohérent avec l'opération.
  3. Appeler match pour obtenir les paramètres ou generate pour obtenir une adresse.
  4. Dans une application HTTP, laisser RouterListener placer les résultats dans les attributes de la Request ; le kernel résout et appelle ensuite le controller.

Exemple concret PHP

Avec le component Routing chargé, sans FrameworkBundle :

<?php
use Symfony\Component\Routing\Generator\UrlGenerator;
use Symfony\Component\Routing\Matcher\UrlMatcher;
use Symfony\Component\Routing\RequestContext;
use Symfony\Component\Routing\Route;
use Symfony\Component\Routing\RouteCollection;

$routes = new RouteCollection();
$routes->add('article', new Route('/articles/{slug}'));
$context = new RequestContext();
$match = (new UrlMatcher($routes, $context))->match('/articles/introduction');
$url = (new UrlGenerator($routes, $context))->generate('article', ['slug' => 'introduction']);
var_dump($match['slug'], $match['_route'], $url);

On attend introduction, article et /articles/introduction. Aucun controller n'a été exécuté. Contre-exemple : attendre qu'ajouter un default _controller transforme cet appel match en réponse HTTP. Correction : distinguer le résultat du routage de son utilisation par HttpKernel, ou assembler explicitement cette utilisation hors du bundle.

Passage canonique conservé

Le component

Sa description officielle : « Maps an HTTP request to a set of configuration variables ». Une route produit un jeu de variables. Ses dependencies : PHP 8.4 et un package de contrats, aucun autre component Symfony — il s'installe seul.

Class Role
Route, RouteCollection une route ; l'ensemble ordonné des routes
UrlMatcher de l'URL vers les variables — le matching
UrlGenerator des variables vers l'URL — la génération
RequestContext host, schéma, method, port courants
Router assemble un loader, un matcher et un generator

Apparier et générer étant deux classes, une option peut compter pour l'un et pas pour l'autre.

Repère — Trois morceaux, trois origines : No. It skips routing for that request. RouterListener appartient à HttpKernel. FrameworkBundle l'enregistre. RouterListener, dans HttpKernel, convertit les erreurs de matching en exceptions HTTP 404 ou 405 (avec Allow).

Trois morceaux, trois origines

Morceau Class fournie par Ce que fait FrameworkBundle
Router, matcher, generator Routing déclare router.default avec RedirectableCompiledUrlMatcher et CompiledUrlGenerator, compilés dans le cache
RouterListener HttpKernel l'enregistre comme service router_listener
loader routing.controllers Routing (AttributeServicesLoader) tague routing.controller toute class portant #[Route]

RouterListener, de namespace Symfony\Component\HttpKernel\EventListener, écoute kernel.request à la priority 32. Il saute le routage si la Request porte déjà _controller — une sub-Request de forward() n'est pas routée à nouveau ; il dépose les variables dans les attributes et recopie dans _route_params celles qui ne sont ni _route ni _controller ; il traduit ResourceNotFoundException en NotFoundHttpException (404) et MethodNotAllowedException en MethodNotAllowedHttpException (405), avec le header Allow. Ces exceptions HTTP existent sans FrameworkBundle. HttpKernel les transmet à kernel.exception : sans Response fournie par un listener, il relance l'exception ; avec une Response 200 sans dérogation de statut, il applique le statut et les headers de l'exception. FrameworkBundle configure les services et le traitement d'erreur ; le resolver résout ensuite le controller, il ne convertit pas les échecs de matching.

Les routes d'attributes viennent des services étiquetés : par autoconfiguration, une class qui porte #[Route] reçoit routing.controller et controller.service_arguments. Le matcher du bundle répond par un redirect plutôt qu'un 404, vers RedirectController::urlRedirectAction, en permanent.

Ce que FrameworkBundle ajoute encore

À retenir en priorité
  1. Le component fournit matcher et generator.
  2. Le bundle ajoute les commands et le chargement de configuration.
  • le chargement de config/routes/ et config/routes.yaml par MicroKernelTrait, qui importe aussi les attributes du kernel ;
  • les commands debug:router et router:match ;
  • les controllers RedirectController et TemplateController.

Piège à éviter

  • Voir l’explication : RouterListener appartient à HttpKernel, pas à FrameworkBundle.

    RouterListener appartient à HttpKernel, pas à FrameworkBundle. Le bundle l'enregistre ; il ne le définit pas.

  • Voir l’explication : Apparier et générer sont deux classes distinctes.

    Apparier et générer sont deux classes distinctes. Le generator ne voit pas la Request ; il ne peut pas évaluer ce qui en dépend.

  • Autonomie du component Routing

    Le component ne dépend d'aucun autre component Symfony.

  • Distinguer matching et résolution du controller

    Une route produit des variables, pas un controller.

  • Routage et présence préalable de _controller

    Une Request qui porte déjà _controller n'est pas routée.

Fiche express

À mémoriser

Si tu dois retenir seulement 6 choses :

  • Routing : Request → variables ; autonome, sans autre component Symfony.
  • UrlMatcher apparie, UrlGenerator génère : deux classes.
  • RouterListener : HttpKernel, kernel.request à 32.
  • Aucune route → 404 ; mauvaise method → 405 + Allow.
  • _controller déjà présent → routage sauté.
  • Bundle : matcher redirigeant compilé, router_listener, routes des services étiquetés.

Moyen mnémotechnique : « Le component trouve, le kernel écoute, le bundle branche ».
