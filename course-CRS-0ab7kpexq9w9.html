Objectif

Lire l'entrée et écrire l'output par les deux abstractions du component, sans jamais toucher $argv, echo ni STDOUT directement. C'est ce découplage qui rend une command testable.

L'essentiel

○ À comprendre

À retenir en priorité
  1. L'output centralise le comportement console.
  2. echo contourne ces mécanismes.

Une command lit par InputInterface et écrit par OutputInterface, jamais par $argv, echo ou STDOUT. Ce découplage la rend testable : la même command tourne avec $argv, un array ou une string. Les messages de diagnostic vont sur un second flux, STDERR.

Le schéma

À retenir en priorité
  1. La même logique peut recevoir plusieurs entrées.
  2. Les tests peuvent capturer la sortie.

L'exemple : une command d'export

▣ Exemple concret

À retenir en priorité
  1. Séparer données et diagnostic.
  2. STDERR évite de corrompre l'export.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

public function __invoke(InputInterface $input, OutputInterface $output): int
{
    $dryRun = $input->getOption('dry-run');            // false si non passée
    $output->writeln('id;nom');                        // les données : STDOUT
    if ($output instanceof ConsoleOutputInterface) {
        $output->getErrorOutput()->writeln('<info>42 lignes</info>');   // diagnostic : STDERR
    }

    return Command::SUCCESS;
}

php bin/console app:export > data.csv ne mélange pas le diagnostic aux données.

`InputInterface` — lire

À retenir en priorité
  1. La définition et la saisie sont distinctes.
  2. Choisir la bonne interrogation.
Appel Ce qu'il rend
getArgument('username'), getOption('iterations') la valeur, ou la default value
hasOption('dry-run') l'option est-elle déclarée ? — true même non passée
hasParameterOption('--env'), getParameterOption('--env') lus sur la ligne brute, sans definition
isInteractive() faux avec -n, -q ou --silent

setArgument() et setOption() permettent à interact() de compléter une valeur. Le nom attendu est le nom kebab-case déclaré : un #[Argument] string $userName se lit getArgument('user-name').

`OutputInterface` — écrire

○ À comprendre

À retenir en priorité
  1. Les tags peuvent modifier l'affichage.
  2. Échapper le texte externe avant formatage.

C'est quoi ?

InputInterface donne accès à l'entrée analysée ; OutputInterface gère les écritures, le formatage et la verbosity. Passer par ces contrats rend les commandes plus faciles à tester qu'un mélange de lecture globale et d'echo.

À quoi ça sert ?

Un export doit pouvoir envoyer ses données sur la sortie normale et ses diagnostics sur la sortie d'erreur, ou STDERR, sans corrompre le fichier consommé par un autre programme.

Où dans Symfony ?

getArgument() et getOption() lisent les valeurs. hasOption() demande si une option est déclarée, pas si l'utilisateur l'a fournie. hasParameterOption() inspecte la saisie brute. write() et writeln() écrivent ; SymfonyStyle propose des présentations comme titres, tableaux et erreurs.

Comment, étape par étape ?

  1. Lire les noms tels que Console les connaît, notamment en kebab-case.
  2. Échapper les chaînes externes avant de les inclure dans un message à tags de style.
  3. Pour un diagnostic séparé, vérifier ConsoleOutputInterface avant getErrorOutput() : tous les outputs ne possèdent pas ce second flux.
  4. En test, utiliser CommandTester pour la commande seule ou ApplicationTester pour le cycle de l'Application, notamment ses événements.

Exemple concret PHP

Fonction réutilisable dans une commande, compatible aussi avec un output de test sans STDERR distinct :

<?php
use Symfony\Component\Console\Formatter\OutputFormatter;
use Symfony\Component\Console\Output\ConsoleOutputInterface;
use Symfony\Component\Console\Output\OutputInterface;

function writeDiagnostic(OutputInterface $output, string $message): void
{
    $errors = $output instanceof ConsoleOutputInterface
        ? $output->getErrorOutput()
        : $output;
    $errors->writeln('<error>'.OutputFormatter::escape($message).'</error>');
}

Le texte externe reste du texte, même s'il contient des séquences ressemblant à des tags Console. Contre-exemple : appeler directement getErrorOutput() sur un BufferedOutput. Correction : tester le contrat ou fournir explicitement deux flux à son abstraction. Tester séparément la sortie et le code de retour ; une erreur affichée ne modifie pas ce code. Pour vérifier les listeners Console, ne pas conclure depuis un test qui contourne l'Application.

Entrées Console 8.0 et Console 8.0.

Passage canonique conservé

OutputInterface — écrire

  • write(), writeln(), avec un array pour plusieurs lignes.
  • Quatre tags par défaut : <info> vert, <comment> jaune, <question> noir sur cyan, <error> blanc sur rouge. Un tag inconnu, <script>, passe intact.
  • Une string venue de l'extérieur passe par OutputFormatter::escape().
  • Modes : OUTPUT_NORMAL interprète les tags, OUTPUT_RAW les laisse, OUTPUT_PLAIN les interprète puis applique strip_tags() : sur un output décoré, <info>ok</info> reste toujours en vert.
  • SymfonyStyle enveloppe le tout : title(), success(), error(), ask(), table(), et getErrorStyle() pour STDERR.

L'output d'erreur

À retenir en priorité
  1. Tous les outputs n'ont pas STDERR séparé.
  2. Tester le contrat avant l'appel.

getErrorOutput() appartient à ConsoleOutputInterface, pas à OutputInterface : un BufferedOutput ne l'a pas, d'où le test de type.

Tester une command

À retenir en priorité
  1. Le cycle Application porte les events.
  2. Tester seulement la command ne les déclenche pas.
$tester = new CommandTester($application->find('app:greet'));
$tester->setInputs(['Bob']);                                   // réponses aux questions
$tester->execute([], ['interactive' => false]);
$tester->execute([], ['capture_stderr_separately' => true]);
  • CommandTester appelle la command seule : aucun event console. ApplicationTester passe par l'Application, avec setAutoExit(false).
  • Ordre : initialize(), interact() (en interactif), validation de l'entrée, execute() ; non interactive, un argument requis manquant lève « Not enough arguments ».
  • Avec capture_stderr_separately, ce qu'écrit getErrorStyle() passe dans getErrorOutput(), comme le libellé d'une question de QuestionHelper ; celui de SymfonyStyle::ask() reste dans getDisplay().

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le nom PHP et le nom CLI diffèrent.
  2. Lire la définition effective.
  • Voir l’explication : Ne jamais utiliser echo

    Ne jamais utiliser echo : l'output échapperait à la verbosity, au formateur et aux tests.

  • Voir l’explication : getErrorOutput() n'appartient pas à OutputInterface

    getErrorOutput() n'appartient pas à OutputInterface mais à ConsoleOutputInterface — d'où le test de type.

  • Voir l’explication : hasOption() interroge la definition

    hasOption() interroge la definition, pas la ligne de command : il vaut true même quand l'option n'a pas été passée. C'est hasParameterOption() qui lit la ligne brute.

  • Voir l’explication : OUTPUT_PLAIN garde les couleurs

    OUTPUT_PLAIN garde les couleurs d'un output décoré.

  • Voir l’explication : Le nom passé à getArgument() est le nom kebab-case

    Le nom passé à getArgument() est le nom kebab-case déclaré, pas celui du parameter PHP.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Les deux flux peuvent être vérifiés séparément.
  2. Le diagnostic ne doit pas polluer les données.

Si tu dois retenir seulement 7 choses :

  • Lire par InputInterface, écrire par OutputInterface ; jamais echo.
  • ArgvInput, ArrayInput, StringInput : même contrat.
  • hasOption() : déclarée ? ; hasParameterOption() : ligne brute.
  • Arguments et options sous leur nom kebab-case.
  • Quatre tags ; escape() pour ce qui vient de l'extérieur.
  • getErrorOutput() (ConsoleOutputInterface) pour STDERR.
  • CommandTester : la command seule ; ApplicationTester : avec events.

Moyen mnémotechnique : « Lire l'entrée, écrire l'output, crier sur STDERR ».
