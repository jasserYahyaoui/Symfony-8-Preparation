Objectif

Savoir quel mécanisme employer pour surcharger chaque partie d'un bundle tiers — et pourquoi ils diffèrent.

L'essentiel

À comprendre

À retenir en priorité
  1. La surcharge suit le domain.
  2. Le nom d'un bundle dans un catalogue peut n'être qu'un nom de domain.

Il n'existe pas de mécanisme unique pour surcharger un bundle tiers : chaque sous-système a le sien. Pour la révision, distinguer notamment la validation, qui ne se surcharge pas, et le routage, qui ne s'importe jamais tout seul. Et le controller a deux cas.

Le schéma

À retenir en priorité
  1. Un controller-service relève de la décoration.
  2. Ne pas confondre cette approche avec la priorité de routes.

Bleu : résolution Twig ; orange : fichier applicatif prioritaire ; vert : résultat. Exemple avec le namespace de template Acme et un bundle AcmeBundle. Le ! ne veut pas dire « autre bundle » : il contourne la surcharge de ce namespace pour atteindre son original.

L'exemple : étendre le template que l'on surcharge

Exemple concret

À retenir en priorité
  1. Le template de surcharge doit pouvoir retrouver l'original.
  2. Le préfixe @! évite de réétendre la surcharge elle-même.
{# templates/bundles/AcmeUserBundle/registration/confirmed.html.twig #}
{% extends "@!AcmeUser/registration/confirmed.html.twig" %}

{% block content %}Bienvenue !{% endblock %}

Vue d'ensemble

À retenir en priorité
  1. Une route externe n'entre pas automatiquement dans l'application.
  2. Contrôler l'import permet de choisir les routes exposées.

Dix lignes pour les huit sections du document officiel : décoration et compiler pass relèvent tous deux de Services & Configuration, et le controller se dédouble. Activer un bundle ne suffit pas à importer toutes ses routes : vérifier les imports configurés, y compris ceux créés par une recette Flex. La « surcharger », c'est ne pas l'importer, ou copier le file et importer sa copie.

Repère — Le controller a deux cas : Service decoration. Un controller-service relève de la décoration. Ne pas confondre cette approche avec la priorité de routes.

Les templates

À comprendre

À retenir en priorité
  1. Le nom ordinaire peut résoudre vers la surcharge elle-même.
  2. @! désigne l'original et évite la récursion.

C'est quoi ?

Une surcharge de template fournit dans l'application un fichier de même chemin relatif que celui du bundle. Le moteur le trouve prioritairement. Le préfixe spécial @! permet, depuis cette surcharge, de viser le template original du bundle plutôt que de se désigner soi-même.

À quoi ça sert ?

L'application peut personnaliser seulement un bloc tout en conservant la structure et les autres blocs du bundle. Sans accès explicite à l'original, un extends utilisant le nom normal peut revenir sur le fichier de surcharge et créer une récursion.

Où dans Symfony ?

Pour AcmeUserBundle, une ressource registration/confirmed.html.twig se surcharge sous templates/bundles/AcmeUserBundle/registration/confirmed.html.twig. Le namespace Twig usuel est @AcmeUser, sans le suffixe Bundle. Cette résolution relève de l'intégration Symfony de Twig.

Comment, étape par étape ?

  1. Reprendre le chemin relatif exact de la ressource.
  2. Créer la surcharge sous le dossier du nom complet du bundle.
  3. Étendre l'original avec @! si l'on souhaite en conserver la structure.
  4. Remplacer seulement les blocs nécessaires ; vérifier le cache si un nouvel emplacement n'est pas détecté.

Exemple concret Twig

Le template original doit exposer un bloc content. Syntaxe compatible avec Twig 3.22 :

{# templates/bundles/AcmeUserBundle/registration/confirmed.html.twig #}
{% extends '@!AcmeUser/registration/confirmed.html.twig' %}

{% block content %}
    <p>Votre inscription est confirmée.</p>
{% endblock %}

La structure originale est conservée, seul le bloc est remplacé. Contre-exemple : utiliser @AcmeUser/registration/confirmed.html.twig dans l'extends de ce même fichier. Correction : utiliser @!AcmeUser/... pour contourner la surcharge lors de la résolution du parent. Un nom de bloc inexistant ne personnalise pas automatiquement la bonne zone : il faut vérifier le contrat du template original.

Passage canonique conservé

Un file de même nom et de même path relatif sous templates/bundles/<NomDuBundle>/. L'étendre par son nom ordinaire crée une loop infinie : le nom résout vers la surcharge elle-même. @! désigne le template original. Un template ajouté à un emplacement nouveau demande parfois de vider le cache, même en mode debug.

Personnaliser un appartement meublé ne consiste pas à détruire les meubles : la surcharge utilise un emplacement prévu, sans modifier vendor/. @! permet de reprendre le meuble original sous la personnalisation.

Repère — Les translations ne dépendent pas des bundles : Its translation domain and locale, not a special bundle relationship. La surcharge suit le domain. Le nom d'un bundle dans un catalogue peut n'être qu'un nom de domain.

Repère de l’exemple : The exclamation mark selects the original bundle template instead of recursively loading the override. Le template de surcharge doit pouvoir retrouver l'original. Le préfixe @! évite de réétendre la surcharge elle-même.

Le controller a deux cas

Le document ouvre sa section par une condition : « si le controller est un service, voir la section suivante » : la décoration. La route de même path, chargée avant celle du bundle, n'est que la branche « sinon » — et les controllers modernes sont des services autoconfigurés.

Les translations ne dépendent pas des bundles

Elles sont liées à un domain : translations/AcmeUserBundle.es.yaml à la racine surcharge celui du bundle sans rien déclarer, le nom du bundle n'étant que celui du domain.

La validation ne se surcharge pas

À comprendre

À retenir en priorité
  1. La configuration ajoute des constraints.
  2. Les groups permettent une sélection prévue par le modèle.

C'est quoi ?

Les métadonnées de validation chargées pour une propriété se combinent. Ajouter une contrainte dans l'application ne remplace pas automatiquement une contrainte du bundle sur cette même propriété.

À quoi ça sert ?

La composition permet d'ajouter des exigences locales. Elle devient une limite lorsqu'on veut assouplir une exigence existante : une nouvelle règle moins stricte n'efface pas l'ancienne. Il faut alors un mécanisme prévu par le bundle, notamment des groupes de validation configurables.

Où dans Symfony ?

Le Validator utilise les métadonnées chargées depuis les sources de configuration. Un groupe sélectionne un ensemble de contraintes à exécuter. Pour éviter une règle du bundle par les groupes, le bundle doit permettre de choisir les groupes appropriés ; inventer un groupe dans l'application ne change pas automatiquement celui qu'il valide.

Comment, étape par étape ?

  1. Identifier les contraintes déjà présentes et leurs groupes.
  2. Déterminer si le besoin est d'ajouter une règle ou d'en remplacer une.
  3. Pour un ajout, déclarer la nouvelle contrainte.
  4. Pour un remplacement logique, utiliser le point de configuration des groupes prévu par le bundle et vérifier les groupes effectivement évalués.

Exemple concret text

Bundle : longueur minimale 8 dans le groupe Default
Application : longueur minimale 4 ajoutée dans le même groupe
Validation Default : les deux règles s'appliquent ; 6 caractères restent invalides

Contre-exemple : considérer la seconde déclaration comme une surcharge qui ramène la limite à quatre. Correction : ne pas ajouter une contrainte contradictoire ; utiliser un groupe distinct si le bundle permet de sélectionner un contrat alternatif. En l'absence de ce point d'extension, l'assouplissement ne peut pas être promis par une simple déclaration supplémentaire. Une règle de validation n'est pas résolue comme un template prioritaire.

Passage canonique conservé

Symfony fusionne la configuration de validation de tous les bundles en un seul arbre de métadonnées : on ajoute une constraint à une property, on n'en remplace jamais. Le contournement suppose des validation groups prévus par le bundle.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Étendre le template que l'on surcharge crée une loop infinie.

    Étendre le template que l'on surcharge crée une loop infinie. Le nom résout vers la surcharge, donc vers lui-même. Le préfixe @! désigne l'original et rompt le cycle.

  • Voir l’explication : Une constraint de validation ne se remplace pas.

    Une constraint de validation ne se remplace pas. Symfony fusionne la configuration de tous les bundles : on ajoute, on ne retire jamais. Le seul contournement est un validation group prévu par le bundle.

  • Voir l’explication : Décoration et compiler pass ne sont pas au même niveau.

    Décoration et compiler pass ne sont pas au même niveau. La décoration enveloppe un service existant ; supprimer ou modifier une definition demande une compiler pass.

  • Voir l’explication : Remplacer un service contrôleur et sélectionner l'endpoint sont deux actions distinctes.

    Remplacer un service contrôleur et sélectionner l'endpoint sont deux actions distinctes. Pour remplacer le service, le document renvoie d'abord à la décoration ; sa solution de route de même path figure dans la branche où le controller n'est pas un service. Une route prioritaire peut néanmoins choisir un autre controller pour cette URL, sans remplacer ni décorer la définition du service contrôleur original dans le container.

  • Voir l’explication : Une translation se surcharge par le domain, pas par le bundle.

    Une translation se surcharge par le domain, pas par le bundle. Le nom du bundle dans le nom de file n'est que le nom du domain.

Application

À retenir en priorité

  2. Le nom d'un bundle dans un catalogue peut n'être qu'un nom de domain.
  3. Un controller-service relève de la décoration.
  4. Ne pas confondre cette approche avec la priorité de routes.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Template : templates/bundles/<NomDuBundle>/, même path relatif.
  • Étendre l'original : @!, sinon loop infinie.
  • Service : décoration ; supprimer une definition : compiler pass.
  • Form type : extension ; constraint : on ajoute, jamais on ne remplace.
  • Translation : même domain, dans translations/.
  • Route : ne pas l'importer ; controller-service : décoration.
  • Mapping : seulement via une mapped superclass.

Moyen mnémotechnique : « Une question par sous-système ».
