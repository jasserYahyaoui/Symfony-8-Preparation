Objectif

Le lecteur a consulté /blog/42 et choisit maintenant de s'inscrire. Supposons que cette branche utilise un bundle tiers fictif, AcmeUserBundle, qui fournit un écran de confirmation, des traductions et un form. Nous voulons adapter cet écran sans modifier les fichiers installés du bundle.

La difficulté est de choisir le bon mécanisme : un template se résout par priorité de chemin, un service peut être décoré et les contraintes de validation s'additionnent. Nous suivons ces différences avec Symfony 8.0 et Twig 3.22 ; le bundle fictif est un laboratoire, pas une dépendance imposée au blog.

L'essentiel

À comprendre

À retenir en priorité
  1. La surcharge suit le domain.
  2. Le nom d'un bundle dans un catalogue peut n'être qu'un nom de domain.

« Surcharger » signifie ici personnaliser une fonctionnalité fournie, pas appliquer une unique instruction du framework. Avant de modifier quoi que ce soit, identifions la ressource réellement consommée : nom Twig, identifiant de service, route, domain de traduction ou métadonnées de validation.

Pour la confirmation d'inscription, remplacer un bloc de template suffit si seul le texte change. Si l'action doit faire autre chose, changer le template ne modifiera pas son comportement. Et si l'on veut assouplir une validation, déclarer une contrainte moins stricte ne supprimera pas celle du bundle.

Cette analyse évite de copier tout un bundle ou de modifier vendor/. Elle prépare aussi les mises à jour : plus nous personnalisons un point public précis, moins nous dépendons des détails internes du fournisseur. Il faut néanmoins tester que le point d'extension existe toujours.

Le schéma

À retenir en priorité
  1. Un controller-service relève de la décoration.
  2. Ne pas confondre cette approche avec la priorité de routes.

Commençons par le cas le plus local : garder la structure d'une page du bundle et remplacer l'un de ses blocs. Le nom normal doit sélectionner notre surcharge ; le nom du parent doit au contraire atteindre l'original. Le schéma utilise les noms abrégés Acme et AcmeBundle :

Le premier choix privilégie le fichier applicatif. Si ce même fichier étendait encore @Acme/page.html.twig, le loader, responsable de trouver les templates, pourrait le sélectionner à nouveau : la recherche du parent reviendrait sur la surcharge elle-même. @!Acme/page.html.twig désigne l'original du namespace dans cette intégration.

Bleu : résolution ; orange : surcharge ; vert : page assemblée. Le ! ne désigne ni un autre bundle ni un ordre de priorité de route. Il permet seulement de choisir le bon parent Twig. Le résultat suppose encore que l'original expose les blocs que nous personnalisons.

L'exemple : étendre le template que l'on surcharge

Exemple concret

À retenir en priorité
  1. Le template de surcharge doit pouvoir retrouver l'original.
  2. Le préfixe @! évite de réétendre la surcharge elle-même.

Revenons à l'inscription. Le bundle fictif doit être activé, son intégration Twig chargée, et son template original doit exposer un bloc content. Nous plaçons le fichier suivant dans le chemin applicatif indiqué :

{# templates/bundles/AcmeUserBundle/registration/confirmed.html.twig #}
{% extends "@!AcmeUser/registration/confirmed.html.twig" %}

{% block content %}Bienvenue !{% endblock %}

Lorsque l'application rend @AcmeUser/registration/confirmed.html.twig, elle sélectionne cette surcharge. Son parent reste l'original grâce à @!AcmeUser. Résultat attendu : la structure de l'original demeure, tandis que son bloc content affiche Bienvenue !.

Le nom complet AcmeUserBundle sert au directory de surcharge ; le namespace Twig de cet exemple est AcmeUser, sans le suffixe Bundle. Il faut vérifier le namespace réellement fourni par un bundle, pas deviner tout nom à partir d'un filename. Cet exemple ne valide pas l'inscription, n'enregistre aucun utilisateur et ne crée pas une route de confirmation : il personnalise seulement le rendu une fois cette page appelée.

Vue d'ensemble

À retenir en priorité
  1. Une route externe n'entre pas automatiquement dans l'application.
  2. Contrôler l'import permet de choisir les routes exposées.

Le document officiel présente huit familles de personnalisation. Nous développons ici celles du périmètre retenu, sans réintroduire les intégrations de persistance exclues. Une même famille peut demander plusieurs décisions : les controllers ont deux cas, et les services distinguent décoration et manipulation de définitions.

Besoin dans la branche d'inscription Mécanisme à examiner
Garder la page avec un autre bloc Surcharge de template, parent @!
Ne pas exposer certaines routes du bundle Retirer leur import, ou importer une copie adaptée
Personnaliser un controller enregistré comme service Décoration du service et préservation de son contrat callable
Remplacer l'action d'un controller non enregistré comme service Route prioritaire vers une nouvelle action
Ajouter un comportement autour d'un autre service Décoration
Transformer ou supprimer des définitions après leur chargement Compiler pass adapté
Adapter un type de form existant Extension du form type
Ajouter des exigences de validation Contraintes supplémentaires ; groupes configurables pour choisir un autre ensemble
Changer un message traduit Même domain, même locale et même key dans les traductions applicatives

Une décoration enveloppe un service existant et délègue éventuellement à celui-ci. Un compiler pass travaille sur les définitions de services pendant la compilation du container, pas sur une inscription en cours. Une extension de form type adapte un type existant quand les forms sont construits ; elle n'est pas une copie de tous les forms du bundle.

Pour les routes, activer le bundle n'importe pas universellement ses ressources. L'import peut venir de notre configuration, du kernel ou d'une recette Flex. Si nous ne voulons pas les routes proposées, nous retirons l'import effectif. Si nous copions leur fichier pour le modifier, nous importons cette copie et suivons ensuite ses éventuelles divergences avec le fournisseur. Supprimer un import ne neutralise pas une autre source qui charge les mêmes routes.

Les templates

À retenir en priorité
  1. Le nom ordinaire peut résoudre vers la surcharge elle-même.
  2. @! désigne l'original et évite la récursion.

La correspondance de chemin est exacte : le template registration/confirmed.html.twig du bundle est remplacé par le même chemin relatif sous templates/bundles/AcmeUserBundle/. Un fichier voisin nommé confirmation.html.twig ne remplace pas automatiquement la ressource que le controller demande.

Nous pouvons remplacer tout le template, ou conserver son architecture avec extends et quelques blocs. Dans le second cas, @! évite la récursion vers notre propre surcharge. Déclarer un bloc inexistant ne suffit pas à modifier une zone que l'original n'affiche jamais. Le nom du bloc fait donc partie du contrat à inspecter.

Pour une confirmation plus explicite, le même fichier peut remplacer seulement le contenu du bloc par <p>Votre inscription est confirmée.</p>. L'entrée reste le nom Twig normal ; le résultat conserve le cadre de l'original et affiche ce paragraphe. Ce changement de vue ne prouve toujours pas qu'une inscription a effectivement réussi.

Si un template ajouté à un nouvel emplacement n'est pas détecté, le document recommande d'envisager de vider le cache même en debug, après avoir vérifié chemin, namespace et intégration. Avec Symfony Console 8.0 :

php bin/console cache:clear

Résultat attendu si la commande réussit : le cache de l'environment sélectionné est vidé puis réchauffé selon la configuration de la commande. Cela ne corrige pas un nom de bloc erroné et ne vise pas le cache du navigateur. Cette commande est documentaire, pas exécutée ici. La même technique de surcharge s'applique aux templates d'erreur de TwigBundle dans leur contexte de rendu approprié.

🌍 In Real Life

La situation : une fiche personnalisée remplace la fiche du fournisseur, mais doit consulter l'original pour conserver son cadre.

L’équivalent dans Symfony : fiche prioritaire → template applicatif ; original explicitement demandé → parent @! ; zone adaptée → bloc existant.

Retour à la réalité technique : étendre le nom normal peut revenir à la surcharge elle-même. Chemin, namespace et bloc doivent correspondre ; vider le cache ne répare pas un mauvais nom.

🧠 Comment le mémoriser : « Remplacer l'entrée, viser l'original comme parent. » Image mentale : deux fiches, une flèche sans boucle. Question-réflexe : vers quel fichier mon extends résout-il ?

⚠️ À ne pas confondre : personnalisation du rendu et changement de l'action.

Personnaliser un appartement meublé ne consiste pas à détruire les meubles : la surcharge utilise un emplacement prévu, sans modifier vendor/. @! permet de reprendre le meuble original sous la personnalisation.

Le controller a deux cas

Après le rendu, imaginons que le comportement de la confirmation doive changer. Il faut d'abord savoir comment le controller est obtenu. S'il est enregistré comme service, le document renvoie à la décoration : le container fournit le décorateur sous l'identité attendue. Celui-ci doit préserver le point d'entrée callable, c'est-à-dire invocable, et les contrats nécessaires ; entourer arbitrairement l'objet ne crée pas une action utilisable.

Dans la branche controller non-service, le document propose une nouvelle route de même path vers notre propre controller, chargée avant celle du bundle. Elle doit aussi correspondre aux autres conditions pertinentes, notamment la méthode HTTP et l'hôte. Le premier matching approprié sélectionne alors la nouvelle action.

Une route prioritaire peut également sélectionner un autre controller lorsque l'ancien est un service. Ce n'est simplement pas la même opération : elle ne remplace ni ne décore sa définition dans le container. Les controllers modernes de notre application étant généralement des services, distinguons donc « changer le fournisseur de l'objet » de « choisir une autre action pour cette URL ». La réponse d'examen suit la branche explicitement posée par le document.

🌍 In Real Life

La situation : on peut changer le poste auquel une demande est dirigée, ou entourer le poste habituel d'un intermédiaire.

L’équivalent dans Symfony : nouvelle destination → autre route/action ; intermédiaire → décoration du controller-service.

Retour à la réalité technique : le routage sélectionne un callable selon toutes ses conditions ; la décoration change l'objet fourni et doit préserver son contrat callable. Une route différente ne décore aucune définition.

🧠 Comment le mémoriser : « Autre destination ou autre fournisseur ? » Image mentale : flèche de direction face à un guichet ajouté. Question-réflexe : veut-on changer le matching ou l'objet obtenu ?

⚠️ À ne pas confondre : cas recommandé par le document et impossibilité technique d'une autre route vers un controller-service.

Les translations ne dépendent pas des bundles

La confirmation est maintenant personnalisée ; sa version espagnole doit encore employer notre formulation. Une traduction est recherchée par key, domain et locale. Le domain regroupe des messages ; ce n'est pas une référence obligatoire à un bundle.

Dans le laboratoire, le fournisseur utilise le domain AcmeUserBundle et la locale es. Avec les traductions applicatives chargées à leur emplacement standard, ce fichier remplace la valeur de la même key pour ce couple :

# translations/AcmeUserBundle.es.yaml
registration.confirmed: 'Tu inscripción está confirmada.'

Si le code demande registration.confirmed dans le domain AcmeUserBundle en espagnol, le résultat attendu est cette phrase. La key doit correspondre à celle réellement utilisée par le bundle ; ici elle fait partie de notre exemple fictif.

Mettre la même key dans messages.es.yaml ne remplace pas un appel qui demande explicitement AcmeUserBundle. De même, ce fichier ne sélectionne pas la langue du visiteur et ne traduit pas un texte codé directement dans le template. La résolution des messages et celle des templates restent deux mécanismes distincts.

La validation ne se surcharge pas

À retenir en priorité
  1. La configuration ajoute des constraints.
  2. Les groups permettent une sélection prévue par le modèle.

Le dernier besoin paraît similaire : adapter une règle du form d'inscription. Pourtant, la priorité de fichier utilisée par Twig ne s'applique pas ici. Le Validator combine les métadonnées de validation chargées ; déclarer une nouvelle contrainte sur une property ne retire pas l'ancienne.

Ce laboratoire porte sur la longueur d'un libellé, pas sur une recommandation de sécurité de mot de passe :

Bundle : longueur minimale 8 dans le groupe Default
Application : longueur minimale 4 ajoutée dans le même groupe
Validation Default : les deux règles s'appliquent ; 6 caractères restent invalides

Avec six caractères, la contrainte de longueur quatre est satisfaite, mais celle de longueur huit échoue encore. Ajouter une exigence peut renforcer la validation ; cela ne l'assouplit pas par remplacement. Le mot « surcharge » donnerait ici le mauvais modèle.

Un validation group sélectionne un ensemble de contraintes à exécuter. Pour choisir un contrat alternatif sans évaluer la règle d'origine, le bundle doit fournir le point de configuration adapté aux groupes. Déclarer nos contraintes dans un nouveau groupe ne suffit pas : le traitement du form doit effectivement sélectionner ce groupe plutôt que celui qui porte la règle initiale, sans réactiver celle-ci par une autre sélection.

Cette technique ne supprime pas les métadonnées d'origine. Sans point d'extension prévu, une simple déclaration supplémentaire ne peut pas promettre l'assouplissement souhaité. Nous devons vérifier les groupes réellement évalués, puis tester une valeur telle que nos six caractères pour observer le résultat.

🌍 In Real Life

La situation : ajouter un contrôle moins strict à un dossier n'efface pas le contrôle strict déjà obligatoire.

L’équivalent dans Symfony : contrôles cumulés → contraintes chargées ; liste des contrôles exécutés → groupes sélectionnés.

Retour à la réalité technique : minimum huit plus minimum quatre refusent toujours six caractères dans le même groupe. Un groupe alternatif doit être prévu puis effectivement sélectionné ; il ne supprime pas les métadonnées initiales.

🧠 Comment le mémoriser : « Ajouter n'est pas remplacer. » Image mentale : deux cases de contrôle restant cochables séparément. Question-réflexe : quelles contraintes sont réellement exécutées ?

⚠️ À ne pas confondre : cumul de validation et priorité de recherche des templates ou traductions.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Le nom normal peut revenir sur le fichier courant.

    Le nom normal peut revenir sur le fichier courant. Depuis la surcharge, étendre ce même nom crée la récursion ; @! vise l'original. Cela ne dispense pas de choisir le bloc réellement exposé par le parent.

  • Voir l’explication : Une deuxième contrainte ne remplace pas la première.

    Une deuxième contrainte ne remplace pas la première. Notre libellé de six caractères reste refusé par le minimum huit du même groupe. La sélection d'un autre groupe doit être prévue et réellement utilisée par le bundle ; elle ne supprime pas les métadonnées.

  • Voir l’explication : Un objet décoré n'est pas une définition compilée.

    Un objet décoré n'est pas une définition compilée. La décoration organise une délégation entre services ; le compiler pass transforme les définitions avant leur utilisation, notamment pour des manipulations avancées ou des suppressions. Il ne faut pas conclure que toute modification ordinaire de configuration exige un compiler pass.

  • Voir l’explication : Changer la route n'est pas remplacer le service controller.

    Changer la route n'est pas remplacer le service controller. La première opération choisit l'action d'une Request ; la seconde agit sur l'objet fourni par le container. Les deux peuvent concerner la même URL, mais la question d'examen précise le cas visé.

  • Voir l’explication : Le nom du fichier de traduction exprime un domain et une locale.

    Le nom du fichier de traduction exprime un domain et une locale. AcmeUserBundle.es.yaml est pertinent parce que l'appel demande ce domain et cette langue. L'activer comme bundle n'est pas un mécanisme de sélection des traductions ; la key doit aussi correspondre.

Fiche express

À mémoriser

La personnalisation de l'inscription se relit par responsabilité :

  1. Le template demandé correspond au même chemin relatif sous templates/bundles/<NomDuBundle>/.
  2. Son parent @! vise l'original ; le bloc existe et le cache de l'environment permet de détecter le nouvel emplacement.
  3. Le service décoré garde le contrat attendu ; une transformation avancée des définitions relève d'un compiler pass approprié.
  4. Le form type peut recevoir une extension, mais une contrainte ajoutée ne remplace pas une contrainte déjà chargée.
  5. Le groupe de validation alternatif doit être sélectionné au traitement, pas seulement nommé dans un fichier.
  6. La traduction reprend domain, locale et key réellement demandés.
  7. Les imports de routes contrôlent leur chargement ; sélectionner un autre controller par une route ne décore pas son ancien service.

Nous avons changé les points nécessaires sans copier tout le fournisseur. Le prochain contrôle consiste à rejouer la confirmation, sa traduction et les entrées valides ou invalides, pas seulement à vérifier que les nouveaux fichiers existent.
