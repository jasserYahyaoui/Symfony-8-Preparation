Objectif

GET /blog/42 consulte un article ; importer un fichier d'articles n'a pas besoin d'attendre un navigateur. Nous ouvrons une autre entrée de la même application : app:blog:import. Elle peut utiliser les mêmes services métier, mais reçoit des arguments CLI et rend un code de sortie, pas une Response. Le premier objectif est de rendre ce contrat utilisable par une personne comme par un automate.

L'essentiel

À comprendre

À retenir en priorité
  1. Le résultat du process est un int.
  2. L'output affiché ne remplace pas l'exit code.

Le composant Console donne à un programme PHP une interface en ligne de commande : arguments, options, aide, sortie et code de retour. Il fonctionne sans FrameworkBundle ; dans une application Symfony, bin/console fournit l'intégration au kernel et aux services.

Application choisit la commande et règle les entrées/sorties. La commande réalise le traitement et retourne un entier. Le texte explique le résultat à une personne ; le code de retour permet au script appelant de décider si l'étape a réussi. Le mode interactif décide séparément si les questions peuvent être posées.

Par exemple, articles.csv est une valeur d'entrée, « fichier introuvable » est un message de sortie, et 2 peut signaler une mauvaise utilisation. Ces trois informations ne se remplacent pas. Une ligne « terminé » affichée juste avant un code non nul n'annonce pas un succès au script appelant.

Le schéma

À retenir en priorité
  1. La préparation précède l'interaction.
  2. Le travail final produit l'exit code.

Une fois le nom app:blog:import résolu, Console lie les valeurs reçues à la définition des arguments/options. Il prépare la commande, permet de compléter les valeurs manquantes si l'interaction est autorisée, puis valide les arguments requis avant de lancer le travail :

Bleu : étapes exécutées ; ambre : condition ; vert : résultat. Le schéma commence après la résolution de la commande : il ne suppose pas qu'une nouvelle instance est toujours construite à ce moment. configure() appartient à la construction d'une commande classique, pas à ce cycle d'exécution. Les événements Console et les exceptions du traitement sont détaillés dans les cours correspondants.

Dans notre première version, file est obligatoire. Avec -n et sans fichier, aucune question ne peut réparer cette absence ; la validation interrompt le trajet avant le corps de la commande. -n n'équivaut donc pas à « exécuter même avec une entrée invalide ».

L'exemple : une command d'import

Exemple concret

À retenir en priorité
  1. Zéro indique le succès.
  2. Une erreur métier utilise un code non nul.

Voici la première étape, limitée au contrôle d'existence du fichier. Dans un projet Symfony 8.0/PHP 8.4, placer cette classe dans src/Command/ImportCommand.php, avec la découverte et l'autoconfiguration des services activées. Le retour de succès concerne ce contrôle, pas un import fictivement terminé :

<?php
namespace App\Command;

use Symfony\Component\Console\Attribute\Argument;
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Style\SymfonyStyle;

#[AsCommand(name: 'app:blog:import')]
final class ImportCommand
{
    public function __invoke(SymfonyStyle $io, #[Argument] string $file): int
    {
        if (!is_file($file)) {
            $io->error('Fichier introuvable');

            return Command::INVALID;   // exit code 2 : mauvaise utilisation
        }
        $io->success('Fichier accepté ; import non exécuté dans cet exemple.');

        return Command::SUCCESS;       // exit code 0
    }
}

Avec un chemin qui n'existe pas :

php bin/console app:blog:import /chemin/inexistant.csv -n
echo $?

Le bloc d'erreur affiche Fichier introuvable, puis echo affiche :

2

L'étape suivante sera un service d'import injecté, ou le dispatch explicite d'un ImportBlogFile. Dans ce second cas, un envoi accepté vers un transport asynchrone configuré ne prouvera pas que le worker a fini l'import.

Ce qu'il fait

À retenir en priorité
  1. Console est un component autonome.
  2. bin/console est l'entry point du framework.

🌍 In Real Life

La situation : le blog reçoit ses lecteurs en salle, mais son équipe prépare les imports au bureau administratif.

L’équivalent dans Symfony : entrée administrative → bin/console ; sélection d'une tâche nommée → Application ; tâche → commande ; outils communs → services métier.

Retour à la réalité technique : Console analyse une entrée CLI et produit sortie et code de retour. L'import n'a pas besoin de passer par le contrôleur de /blog/42, RouterListener ou un cycle Request/Response.

🧠 Comment le mémoriser : « Autre porte, mêmes outils métier. » Image mentale : salle et bureau reliés à la même réserve. Question-réflexe : quelle entrée déclenche le service ?

⚠️ À ne pas confondre : composant Console autonome et intégration FrameworkBundle.

La même définition de commande sert à analyser l'entrée et à générer l'aide : le chemin de fichier n'est pas lu manuellement dans $_SERVER['argv']. Console fournit également sortie colorée et code de sortie. symfony/console s'installe seul dans n'importe quel projet PHP. Dans une application Symfony, bin/console est l'entry point : une Application détient les commands, les résout par leur nom, et gère --help, --version, list et la verbosity.

Ne pas confondre les rôles : le script démarre l'application, Application sélectionne la commande, puis celle-ci appelle ses services métier. Dans l'intégration au framework, l'assemblage des services repose sur le conteneur préparé ; l'import ne rejoue pas les compiler passes à chaque ligne du fichier. Hors framework, le composant n'impose ni kernel HTTP ni conteneur.

Le code de retour

À retenir en priorité
  1. Distinguer traitement échoué et mauvaise utilisation.
  2. Les constantes rendent l'intention lisible.

🌍 In Real Life

La situation : après l'import du blog, un opérateur lit le rapport, tandis que l'automate attend un signal numérique.

L’équivalent dans Symfony : rapport → texte de sortie ; signal → code de retour ; automate → shell ou ordonnanceur.

Retour à la réalité technique : SUCCESS, FAILURE et INVALID valent 0, 1 et 2. Afficher « succès » ne retourne pas 0. Le code final dépend aussi d'Application, des exceptions et des listeners éventuels.

🧠 Comment le mémoriser : « Le texte parle, le code décide. » Image mentale : une feuille et un voyant séparés. Question-réflexe : que reçoit réellement l'appelant ?

⚠️ À ne pas confondre : code de sortie CLI et statut HTTP.

Un ordonnanceur doit décider s'il poursuit après notre contrôle. Les constantes expriment une intention ; les nombres constituent le contrat avec l'appelant. Le tableau suppose les réglages standards du composant, autoExit activé, et aucun listener qui remplace l'erreur ou le code :

La command… Exit code
retourne Command::SUCCESS / FAILURE / INVALID 0 / 1 / 2
retourne 300 255 — plafonné par Application::run()
lève une exception de code 3 3
lève une exception de code 0 ou négatif 1
l'invocable ne retourne rien (void) 255 si la TypeError reste non capturée et termine le process PHP

Un script de CI peut conserver et analyser l'output, mais le statut du process reste un signal distinct. INVALID signale une mauvaise utilisation — un argument aberrant —, FAILURE un traitement qui a échoué. Dans Application::run(), le bloc catch reçoit un Throwable, mais relance une erreur telle que TypeError si catchErrors reste faux. Les Exception sont converties en code par défaut ; ce comportement se configure et ne décrit pas tous les wrappers possibles.

Le plafond à 255 est appliqué dans la branche qui appelle exit(). Avec setAutoExit(false), run() peut retourner 300 à son appelant PHP. Ne pas confondre cette valeur interne, la sortie effective du process et le statut que voit le shell. Un code 2 n'est pas non plus un statut HTTP.

Le cycle d'exécution

À retenir en priorité
  1. configure() construit la définition.
  2. L'entrée du user arrive plus tard.

🌍 In Real Life

La situation : avant de classer les articles du blog, on prépare le poste, complète le bordereau puis commence le travail.

L’équivalent dans Symfony : préparation → initialize() ; questions permises → interact() ; travail → execute() ou invocable.

Retour à la réalité technique : l'interaction est optionnelle et peut être désactivée par -n. La validation des entrées intervient avant le travail. Dans le style classique, configure() appartient à la construction, pas à ce cycle métier.

🧠 Comment le mémoriser : « Compléter avant de traiter. » Image mentale : un bordereau rempli avant son classement. Question-réflexe : sans interlocuteur, les valeurs requises existent-elles ?

⚠️ À ne pas confondre : définir une entrée et fournir sa valeur à l'exécution.

Le fichier existe peut-être, mais une commande plus complète peut encore avoir besoin d'une confirmation. Placer chaque opération au bon moment évite de demander une valeur après la validation qui exigeait déjà sa présence :

Method Role Obligatoire
initialize() préparer, avant toute interaction non
interact() demander au user ce qui manque non
__invoke() — ou execute() faire le travail et retourner le code oui
  • configure() n'en fait pas partie : elle tourne pendant le constructor, et seulement dans le style classique (une class qui étend Command).
  • Une command invocable a des équivalents par attributes : #[Ask] sur un parameter de __invoke(), #[Interact] sur une method publique, appelée avant __invoke() et sautée comme interact().
  • interact() n'est appelée que si l'entrée est interactive : -n, -q ou --silent la rendent non interactive (Application::configureIO()). L'absence de terminal ne suffit pas : sous cron, sans -n, interact() peut tourner. Sur une entrée vide, une question peut utiliser son défaut ; sans valeur exploitable, elle peut lever MissingInputException. Définir le mode et le repli explicitement.

initialize() prépare une exécution, tandis que configure() définit la commande à sa construction. Ni l'une ni l'autre n'est la compilation du conteneur. Pour une invocable, InvokableCommand adapte l'appel PHP : il fournit les paramètres issus de la définition et vérifie que le résultat est un entier. La résolution des paramètres Console n'est pas l'ArgumentResolver du contrôleur HTTP.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'absence de terminal n'est pas le réglage interactif.
  2. Une tâche automatisée doit choisir son mode.
  • Voir l’explication : L'invocable doit retourner un int.

    L'invocable doit retourner un int. Un retour void échoue au contrôle de InvokableCommand. La TypeError n'est pas absorbée par les réglages standards de Application ; un traitement d'erreur personnalisé peut changer le résultat observé.

  • Voir l’explication : SUCCESS vaut 0

    SUCCESS vaut 0, comme la convention Unix ; la sortie automatique de Application::run() plafonne un code supérieur à 255. Un appel sans sortie automatique n'applique pas ce plafond.

  • Voir l’explication : Un cron n'est pas un mode non interactif

    Un cron n'est pas un mode non interactif : l'absence de terminal ne désactive pas à elle seule interact(). Le mode d'entrée effectif compte.

  • Voir l’explication : -q coupe aussi l'interaction

    -q coupe aussi l'interaction, pas seulement l'output.

Fiche express

À mémoriser

À retenir en priorité
  1. La verbosity peut influencer l'entrée.
  2. Ne pas attendre interact() en mode quiet.

Le contrôle du fichier a maintenant trois frontières lisibles : entrée CLI, travail de la commande et résultat du process. Garder ces frontières quand le contrôle deviendra un vrai import :

Si tu dois retenir seulement 6 choses :

  • Component autonome ; bin/console est l'entry point du framework.
  • La command retourne un int : SUCCESS 0, FAILURE 1, INVALID 2.
  • Sortie automatique de Application : plus de 255 → 255 ; exception convertie → son code positif, sinon 1 ; invocable void → erreur, fatale à 255 si non capturée.
  • Cycle : initialize(), interact(), __invoke() ; configure() dans le constructor.
  • interact() sautée avec -n, -q, --silent — pas faute de terminal.
  • Invocable : #[Ask] et #[Interact].

Moyen mnémotechnique : « Un int en sortie, une option pour se taire ».
