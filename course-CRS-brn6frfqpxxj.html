Objectif

Situer le component, et connaître le contrat d'une command — dont la return value, qui n'est pas facultative, et le moment où elle peut poser des questions.

L'essentiel

À comprendre

À retenir en priorité
  1. Le résultat du process est un int.
  2. L'output affiché ne remplace pas l'exit code.

Console donne à un programme PHP une interface en ligne de commande : arguments, options, aide, sortie et code de retour. Il fonctionne sans FrameworkBundle ; dans une application Symfony, bin/console fournit l'intégration au kernel et aux services.

Application choisit la commande et règle les entrées/sorties. La commande réalise le traitement et retourne un entier. Le texte explique le résultat à une personne ; le code de retour permet au script appelant de décider si l'étape a réussi. Le mode interactif décide séparément si les questions peuvent être posées.

Le schéma

À retenir en priorité
  1. La préparation précède l'interaction.
  2. Le travail final produit l'exit code.

Bleu : étapes exécutées ; ambre : condition ; vert : résultat. Le schéma commence après la résolution de la commande : il ne suppose pas qu'une nouvelle instance est toujours construite à ce moment. configure() appartient à la construction d'une commande classique, pas à ce cycle d'exécution. Les événements Console et les exceptions du traitement sont détaillés dans les cours correspondants.

L'exemple : une command d'import

Exemple concret

À retenir en priorité
  1. Zéro indique le succès.
  2. Une erreur métier utilise un code non nul.
#[AsCommand(name: 'app:import')]
class ImportCommand
{
    public function __invoke(SymfonyStyle $io, #[Argument] string $file): int
    {
        if (!is_file($file)) {
            $io->error('Fichier introuvable');

            return Command::INVALID;   // exit code 2 : mauvaise utilisation
        }
        // …
        return Command::SUCCESS;       // exit code 0
    }
}

Ce qu'il fait

À retenir en priorité
  1. Console est un component autonome.
  2. bin/console est l'entry point du framework.

Analyse des arguments, aide générée, sortie colorée, exit code. symfony/console s'installe seul dans n'importe quel projet PHP. Dans une application Symfony, bin/console est l'entry point : une Application détient les commands, les résout par leur nom, et gère --help, --version, list et la verbosity.

Le code de retour

À retenir en priorité
  1. Distinguer traitement échoué et mauvaise utilisation.
  2. Les constantes rendent l'intention lisible.
La command… Exit code
retourne Command::SUCCESS / FAILURE / INVALID 0 / 1 / 2
retourne 300 255 — plafonné par Application::run()
lève une exception de code 3 3
lève une exception de code 0 ou négatif 1
ne retourne rien (void) 255 — TypeError non capturée

Un cron ou une CI ne lit pas l'output, il lit le code. INVALID signale une mauvaise utilisation — un argument aberrant —, FAILURE un traitement qui a échoué. Une TypeError n'est pas rattrapée : Application n'attrape par défaut que les Exception.

Le cycle d'exécution

À retenir en priorité
  1. configure() construit la définition.
  2. L'entrée du user arrive plus tard.
Method Role Obligatoire
initialize() préparer, avant toute interaction non
interact() demander au user ce qui manque non
__invoke() — ou execute() faire le travail et retourner le code oui
  • configure() n'en fait pas partie : elle tourne pendant le constructor, et seulement dans le style classique (une class qui étend Command).
  • Une command invocable a des équivalents par attributes : #[Ask] sur un parameter de __invoke(), #[Interact] sur une method publique, appelée avant __invoke() et sautée comme interact().
  • interact() n'est appelée que si l'entrée est interactive : -n, -q ou --silent la rendent non interactive (Application::configureIO()). L'absence de terminal ne suffit pas : sous cron, sans -n, interact() peut tourner. Sur une entrée vide, une question peut utiliser son défaut ; sans valeur exploitable, elle peut lever MissingInputException. Définir le mode et le repli explicitement.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. L'absence de terminal n'est pas le réglage interactif.
  2. Une tâche automatisée doit choisir son mode.
  • Voir l’explication : La method d'exécution doit retourner un int.

    La method d'exécution doit retourner un int. Ne rien retourner lève une TypeError, que l'application ne rattrape pas.

  • Voir l’explication : SUCCESS vaut 0

    SUCCESS vaut 0, comme la convention Unix ; un code au-delà de 255 sort à 255.

  • Voir l’explication : Un cron n'est pas un mode non interactif

    Un cron n'est pas un mode non interactif : sans -n, interact() tourne.

  • Voir l’explication : -q coupe aussi l'interaction

    -q coupe aussi l'interaction, pas seulement l'output.

Fiche express

À mémoriser

À retenir en priorité
  1. La verbosity peut influencer l'entrée.
  2. Ne pas attendre interact() en mode quiet.

Si tu dois retenir seulement 6 choses :

  • Component autonome ; bin/console est l'entry point du framework.
  • La command retourne un int : SUCCESS 0, FAILURE 1, INVALID 2.
  • Plus de 255 → 255 ; exception → son code, ou 1 ; void → 255.
  • Cycle : initialize(), interact(), __invoke() ; configure() dans le constructor.
  • interact() sautée avec -n, -q, --silent — pas faute de terminal.
  • Invocable : #[Ask] et #[Interact].

Moyen mnémotechnique : « Un int en sortie, une option pour se taire ».
