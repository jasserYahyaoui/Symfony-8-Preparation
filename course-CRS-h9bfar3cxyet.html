Objectif

L'import peut réussir ou repartir en retry. Pour l'observer, faut-il recopier le même journal dans tous les handlers ? Un middleware permet d'intervenir sur le trajet du bus. Suivons ImportBlogFile, depuis le dispatch lié à l'administration du blog jusqu'à une réception par le worker, pour choisir où journaliser et ce que cette observation prouve réellement.

L'essentiel

À comprendre

À retenir en priorité
  1. Le passage au suivant est explicite.
  2. Sans lui la chaîne s'arrête.

Un middleware est un traitement composable : il reçoit l'Envelope et l'accès à la suite de la chaîne. Le bus ne recherche pas secrètement un handler après cette chaîne ; c'est HandleMessageMiddleware qui en est chargé. Ne pas déléguer peut donc empêcher l'import tout en retournant une Envelope sans exception.

La pile standard place les middleware applicatifs avant l'envoi et le traitement. Ceux qui sont atteints peuvent observer le dispatch initial puis la réception. Ce sont deux passages du bus, pas deux lectures de GET /blog/42, et pas une promesse que chaque middleware sera appelé exactement deux fois.

Le schéma

À retenir en priorité
  1. Le message n'arrive pas seul.
  2. Les stamps portent le contexte.

La pile est assemblée pendant la préparation de la configuration du bus. À chaque dispatch, le bus parcourt les services ainsi choisis ; il ne relance pas l'extension du bundle ni les compiler passes. Cette première vue décrit un dispatch initial sans exception et sans réception préalable :

Bleu : traversée ; ambre : choix ; vert : résultat. Vue du premier dispatch, avec la pile par défaut. Un message déjà reçu n'est pas réexpédié par send_message. « Sans erreur » signifie ici que le middleware retourne une Envelope sans lever ; cela ne signifie pas que le métier a réussi.

Un middleware maison s'insère donc avant l'envoi et le traitement : il peut empêcher l'un comme l'autre.

L'exemple

Exemple concret

À retenir en priorité
  1. with() rend une nouvelle Envelope.
  2. La transmettre conserve le stamp ajouté.

Nous voulons un journal technique de l'import, pas envoyer un deuxième message métier. Le service App\Middleware\AuditMiddleware doit être découvert par le container ; le logger doit être disponible pour son injection. Cette configuration du bus ne remplace pas l'enregistrement du service :

framework:
    messenger:
        buses:
            messenger.bus.default:
                middleware:
                    - 'App\Middleware\AuditMiddleware'
namespace App\Middleware;

use Psr\Log\LoggerInterface;
use Symfony\Component\Messenger\Envelope;
use Symfony\Component\Messenger\Middleware\MiddlewareInterface;
use Symfony\Component\Messenger\Middleware\StackInterface;
use Symfony\Component\Messenger\Stamp\ReceivedStamp;

final class AuditMiddleware implements MiddlewareInterface
{
    public function __construct(private LoggerInterface $logger) {}

    public function handle(Envelope $envelope, StackInterface $stack): Envelope
    {
        $side = $envelope->last(ReceivedStamp::class) ? 'received' : 'dispatched';
        $this->logger->info($side, ['class' => $envelope->getMessage()::class]);

        return $stack->next()->handle($envelope, $stack);
    }
}

Le champ class vaut ici App\Message\ImportBlogFile. Au dispatch initial, le message de journal vaut dispatched ; à une réception marquée, il vaut received. Aucune donnée personnelle du fichier n'est journalisée. Le retour de la suite est indispensable : le logger seul ne lance aucun handler.

Ce qu'un middleware voit

À retenir en priorité
  1. L'absence de continuation peut être silencieuse.
  2. Le middleware responsable du contrôle n'est pas exécuté.

🌍 In Real Life

La situation : au secrétariat du blog, viser une pochette ne suffit pas à la remettre au bureau suivant.

L’équivalent dans Symfony : annotation → stamp ; pochette enrichie → nouvelle Envelope ; remise effective → $stack->next()->handle(...).

Retour à la réalité technique : le middleware reçoit et retourne une Envelope. Ne pas appeler la suite peut arrêter le trajet normalement ; le bus n'appelle pas secrètement un handler ensuite.

🧠 Comment le mémoriser : « Annoter puis transmettre. » Image mentale : une pochette tamponnée restée sur place. Question-réflexe : la suite est-elle réellement appelée avec la bonne Envelope ?

⚠️ À ne pas confondre : obtenir next() et exécuter son handle().

L'Envelope réunit les données du travail et les stamps de son trajet. Cela permet d'ajouter un contexte transversal sans changer la classe ImportBlogFile. Mais l'enrichissement et la continuation restent deux opérations différentes :

  • Il reçoit l'Envelope — le message et ses stamps — et rend une Envelope.
  • $stack->next()->handle(...) appelle le suivant. Obtenir seulement $stack->next() ne l'exécute pas. Retourner directement l'Envelope arrête la suite : un HandleMessageMiddleware placé plus loin ne sera pas atteint et ne pourra pas lever NoHandlerForMessageException. Cela n'annule pas les effets déjà produits avant l'arrêt et ne masque pas une exception explicitement levée par le middleware lui-même.
  • Il peut modifier l'Envelope et agir avant et après la suite : un stamp ajouté par with() exige de transmettre la nouvelle Envelope. Rendre ensuite celle retournée par la suite conserve ses enrichissements, sauf si un autre middleware retire volontairement ce stamp.

Le middleware neutre suivant isole ce contrat, sans logger ni effet métier. L'enregistrer dans la pile est nécessaire pour qu'il soit appelé :

<?php
use Symfony\Component\Messenger\Envelope;
use Symfony\Component\Messenger\Middleware\MiddlewareInterface;
use Symfony\Component\Messenger\Middleware\StackInterface;

final class ForwardMessageMiddleware implements MiddlewareInterface
{
    public function handle(Envelope $envelope, StackInterface $stack): Envelope
    {
        return $stack->next()->handle($envelope, $stack);
    }
}

Le résultat est celui de la suite. Retourner l'Envelope d'entrée après avoir ignoré ce résultat peut perdre ses nouveaux stamps ; retourner sans appeler la suite supprime même l'opération attendue.

Deux passages en asynchrone

À retenir en priorité
  1. Deux traversées sont normales.
  2. ReceivedStamp distingue la réception.

Supposons l'import routé vers un transport réellement différé et consommé une fois, avec A et B atteints sur les deux passages. Le journal nominal est alors :

Moment Journal de deux middlewares A puis B
après dispatch() A:dispatched, B
après messenger:consume async --limit=1 … puis A:received, B, et le handler

Un compteur incrémenté à chaque passage compterait deux observations pour un même import. ReceivedStamp permet de viser la réception, pas de prouver le succès métier. Un retry ajoute des réceptions ; un arrêt anticipé peut empêcher d'atteindre B ou le handler.

De plus, sync:// ajoute aussi ReceivedStamp lors d'un redispatch immédiat : ce stamp ne prouve ni l'existence d'un worker ni une attente asynchrone. Définir si la métrique mesure les envois, les réceptions, les tentatives ou les réussites avant de choisir son point d'observation.

Où se place un middleware maison

À retenir en priorité
  1. Le code custom peut intervenir avant l'envoi.
  2. Il doit ensuite déléguer pour poursuivre.

🌍 In Real Life

La situation : un responsable du blog attend que son adjoint termine, lequel attend lui-même la fin du classement.

L’équivalent dans Symfony : délégations imbriquées → appels A puis B ; reprises après délégation → retour dans B puis A.

Retour à la réalité technique : le code après l'appel de la suite s'exécute au retour normal, en ordre inverse. Une exception peut sauter ce code si elle n'est pas traitée ; un finally a un autre contrat.

🧠 Comment le mémoriser : « Entrer A-B, sortir B-A. » Image mentale : deux chemises emboîtées. Question-réflexe : ce log est-il avant, après ou dans un finally ?

⚠️ À ne pas confondre : retour d'appel et deuxième dispatch lors de la consommation asynchrone.

Pour mesurer le temps passé dans la suite, il faut comprendre le retour des appels imbriqués. A n'est pas réinséré une seconde fois après B : son appel attend simplement le résultat de celui de B.

Cette seconde vue montre les appels réels, pas une seconde liste de services : pour chronométrer le traitement, mesurer avant l'appel puis à son retour. Utiliser finally si la mesure doit aussi être produite en cas d'exception. Dans l'exemple d'audit, injecter le logger et enregistrer le service ; un envoi asynchrone consommé une fois, sans interruption avant l'audit, produit dispatched, puis received. Une mesure autour de la suite mesure le trajet atteint : lors d'un envoi différé, elle ne mesure pas le handler qui tournera plus tard.

Les middlewares applicatifs sont placés avant send_message et handle_message dans la pile standard. send_message envoie aux transports sélectionnés, ou poursuit sans envoi ; handle_message appelle les handlers puis transmet au middleware suivant. Un middleware doit transmettre l'Envelope pour poursuivre la chaîne. Lorsque Lock est activé et sa factory disponible, deduplicate_middleware s'ajoute en fin de premier groupe. Cette présence conditionnelle ne fournit pas une garantie universelle d'exécution unique de tous les messages.

La pile par défaut

À retenir en priorité
  1. Une pile vide peut ne rien faire.
  2. Déclarer les middleware indispensables.

L'audit retourne correctement une Envelope, mais l'import ne tourne toujours pas ? Vérifier la pile avant de chercher une panne de handler. Le tableau suppose un dispatch sans sender, aucune interruption applicative et, pour la ligne false, une liste middleware: vide :

default_middleware Pile Sans handler Avec handler
(défaut) complète NoHandlerForMessageException traité
allow_no_handlers complète accepté, aucun HandledStamp traité
false vide accepté non traité, sans erreur
  • Avec default_middleware: false, la pile se limite à la liste middleware: : sans send_message ni handle_message, rien n'est fait.
  • allow_no_senders vaut true par défaut ; à false, un dispatch initial sans sender lève NoSenderForMessageException lorsque le middleware d'envoi est atteint, même s'il a des handlers.

allow_no_handlers assouplit un contrôle ; il ne supprime pas le middleware ni les handlers existants. default_middleware: false, au contraire, retire la pile fournie par le framework mais conserve les middleware explicitement listés. Aucun de ces réglages ne crée un transport implicite.

`DispatchAfterCurrentBusStamp`

À retenir en priorité
  1. Le traitement courant doit réussir.
  2. Le message différé ne part pas si ce traitement échoue.

🌍 In Real Life

La situation : le secrétariat retient l'annonce « import terminé » tant que le dossier courant n'a pas fini son circuit.

L’équivalent dans Symfony : annonce retenue → message marqué ; bac temporaire → gestion par DispatchAfterCurrentBusMiddleware ; libération → traitement après réussite du circuit courant.

Retour à la réalité technique : le stamp exige son middleware. Ce report dans le processus n'est ni une file durable ni une annulation des effets déjà réalisés ; l'échec du traitement courant peut empêcher la libération.

🧠 Comment le mémoriser : « Annoncer après le circuit. » Image mentale : une lettre retenue sous un presse-papier. Question-réflexe : quel middleware retient ce message et jusqu'à quel succès ?

⚠️ À ne pas confondre : différer dans le bus et exécuter dans un worker distant.

L'import souhaite annoncer sa fin, mais pourrait encore échouer après avoir préparé cette notification. La variante historique de confirmation d'abonnement illustre le même problème : un message déjà envoyé ne revient pas parce que le handler appelant lève ensuite.

Le fragment suivant suppose OrderConfirmationEmail disponible, un bus injecté et l'import de Symfony\Component\Messenger\Stamp\DispatchAfterCurrentBusStamp :

$this->bus->dispatch(new OrderConfirmationEmail($command->orderId), [new DispatchAfterCurrentBusStamp()]);

Avec dispatch_after_current_bus installé, un dispatch imbriqué portant ce stamp est retenu en mémoire jusqu'au retour réussi de la pile du dispatch racine. Le middleware conserve l'Envelope et la position de continuation ; après le succès, il reprend cette suite. Selon le routage de la notification, celle-ci peut alors être envoyée à un transport plutôt que traitée immédiatement.

Si une exception remonte de la pile courante, le middleware vide cette attente et relance l'exception : la notification retenue par cet essai ne part pas. Si un autre middleware absorbe l'exception, cette condition n'est plus la même. Un stamp sur un dispatch racine n'invente pas non plus une file durable : en l'absence de dispatch courant, le traitement continue.

Ce mécanisme ne remplace ni une transaction locale ni l'idempotence d'un effet externe. Lors de l'exécution des messages différés, le code 8.0.16 collecte les Exception rencontrées et peut lever une DelayedMessageHandlingException après les autres éléments déjà en attente ; il retire les nouveaux messages ajoutés par le traitement différé qui a échoué. Ne pas transformer ce comportement en rollback global.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. Le stamp décrit le trajet.
  2. Il évite d'appliquer deux fois une logique réservée à la réception.
  • Voir l’explication : Ne pas déléguer par next()->handle() arrête la suite

    Ne pas déléguer par next()->handle() arrête la suite, sans exception automatique si le middleware retourne normalement son Envelope.

  • Voir l’explication : Envoi et réception sont deux passages possibles

    Envoi et réception sont deux passages possibles, pas une borne du nombre d'appels. ReceivedStamp marque la réception, y compris via sync://.

  • Voir l’explication : Le middleware reçoit l'Envelope

    Le middleware reçoit l'Envelope, pas le message nu : les stamps sont lisibles.

  • Voir l’explication : La pile standard place les middleware maison avant send_message et handle_message

    La pile standard place les middleware maison avant send_message et handle_message ; leur code après délégation s'exécute au retour.

  • Voir l’explication : default_middleware: false retire aussi le traitement

    default_middleware: false retire aussi le traitement : il faut alors déclarer soi-même send_message et handle_message.

Fiche express

À mémoriser

À retenir en priorité
  1. L'option assouplit l'absence de handler.
  2. Elle ne vide pas la pile.

Le point à retenir pour l'import n'est pas seulement le nom des middleware : il faut savoir quelle suite est atteinte et quelle Envelope revient.

Si tu dois retenir seulement 7 choses :

  • Un middleware reçoit l'Envelope et rend une Envelope.
  • $stack->next()->handle() continue ; retourner directement arrête la suite.
  • Envoi puis réception : deux passages nominaux ; retries et interruptions changent ce compte. ReceivedStamp ne signifie pas uniquement worker.
  • Vos middlewares passent avant send_message et handle_message.
  • allow_no_handlers : pas d'erreur sans handler.
  • default_middleware: false : réinstaller explicitement les opérations souhaitées ; une liste vide n'envoie ni ne traite.
  • DispatchAfterCurrentBusStamp : reprise après succès de la pile courante ; attente abandonnée si son échec remonte au middleware.

Moyen mnémotechnique : « recevoir l'Envelope, passer la main, ou tout arrêter ».

défauts (stamps, redelivered, dispatch_after_current_bus, failed) > vos middlewares > send_message > handle_message ;
next()->handle() pour continuer ; envoi/réception nominaux ; allow_no_handlers et allow_no_senders assouplissent des contrôles ; false retire les défauts

Pour observer une étape sans confondre un listener avec cette chaîne de délégation, poursuivre avec les événements Messenger.
