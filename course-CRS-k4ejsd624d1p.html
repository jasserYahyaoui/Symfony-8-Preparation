Objectif

Modifier un type de field existant — y compris un type fourni par Symfony ou par un bundle tiers — sans le remplacer, et savoir jusqu'où la modification s'étend.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La propagation suit l'inheritance des form types.
  2. FormType n'est pas la racine des boutons.

Une form type extension greffe un comportement sur un type existant — TextType, FileType, un type de bundle — partout dans l'application, sans toucher un seul form. Un type crée un nouveau field ; une extension modifie ceux qui existent. Elle suit l'inheritance des types : elle atteint leurs descendants, pas leurs frères.

Le schéma

L'exemple : `help_icon`

▣ Exemple concret

À retenir en priorité
  1. La method est statique.
  2. Une liste vide est une erreur d'enregistrement.
class HelpIconExtension extends AbstractTypeExtension
{
    public static function getExtendedTypes(): iterable
    {
        return [TextType::class];
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefined('help_icon');
    }

    public function buildView(FormView $view, FormInterface $form, array $options): void
    {
        $view->vars['help_icon'] = $options['help_icon'] ?? null;
    }
}

Un IconTextType obligerait à remplacer TextType dans chaque form, et ne toucherait pas les forms des bundles.

Le principe

○ À comprendre

À retenir en priorité
  1. Une extension enrichit les types existants.
  2. Un nouveau type impose de le sélectionner aux call sites.

C'est quoi ?

Une form type extension ajoute ou ajuste le comportement de types existants sans demander de remplacer chaque utilisation par un nouveau type. Un type personnalisé exprime une variante nommée ; une extension exprime une règle transversale pour les types qu'elle cible et leurs descendants.

À quoi ça sert ?

Une extension convient pour une option commune ou une convention de présentation. Elle peut aussi affecter beaucoup de formulaires involontairement : la portée doit être choisie à partir de la hiérarchie des types, pas d'une ressemblance entre widgets HTML.

Où dans Symfony ?

La classe étend AbstractTypeExtension. Sa seule méthode obligatoire est public static function getExtendedTypes(): iterable. L'intégration la collecte via le tag form.type_extension, souvent ajouté par autoconfiguration. Hors framework, cette classe doit être fournie à la factory ; déclarer le fichier ne l'enregistre pas magiquement.

Comment, étape par étape ?

  1. Choisir le type le plus précis qui correspond à la règle.
  2. Le retourner dans getExtendedTypes() ; une liste vide n'étend rien et est refusée par l'intégration.
  3. Déclarer les options dans configureOptions(), puis les utiliser dans le point d'accroche approprié si nécessaire.
  4. Vérifier l'enregistrement avec debug:form et tester un type descendant ainsi qu'un type extérieur à la hiérarchie.

Exemple concret PHP

Service autoconfiguré sous App\Form, cette extension ajoute une aide par défaut aux champs EmailType et à leurs descendants. Un champ peut fournir sa propre option help.

<?php
namespace App\Form;

use Symfony\Component\Form\AbstractTypeExtension;
use Symfony\Component\Form\Extension\Core\Type\EmailType;
use Symfony\Component\OptionsResolver\OptionsResolver;

final class EmailHelpExtension extends AbstractTypeExtension
{
    public static function getExtendedTypes(): iterable
    {
        return [EmailType::class];
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['help' => 'Utilisez votre adresse de contact.']);
    }
}

Contre-exemple : cibler FormType pour ne changer que les emails. La règle touche une portée beaucoup plus large. Correction : cibler EmailType. Même FormType n'est pas universel : les boutons appartiennent à une autre racine de types. Pour ordonner plusieurs extensions, la priorité appartient au tag form.type_extension ; ne pas supposer qu'un mécanisme de priorité utilisé ailleurs est automatiquement lu ici.

Passage canonique conservé

Le principe

Une extension étend AbstractTypeExtension et s'applique à tous les fields des types qu'elle désigne. Elle redéfinit les mêmes points d'accroche qu'un type : buildForm(), configureOptions(), buildView(), finishView().

La seule method obligatoire

getExtendedTypes() est statique, retourne un itérable, et peut nommer plusieurs types. Un itérable vide est refusé à la compilation du container : FormPass lève une InvalidArgumentException, « The getExtendedTypes() method for service "e" does not return any extended types. ».

Qui est touché, et quand

○ À comprendre

C'est quoi ?

Une type extension enrichit un type Form existant et ses descendants dans la hiérarchie des types. Elle ne remplace pas chaque classe PHP correspondante. Le choix du type étendu détermine la portée réelle de ses options et de ses hooks de construction.

À quoi ça sert ?

Une option de présentation commune peut être ajoutée à une famille de champs sans créer un nouveau type pour chacun. La porter trop haut peut affecter plus de champs que prévu ; la porter trop bas laisse des types voisins sans cette option.

Où dans Symfony ?

Une extension de TextType atteint notamment EmailType, qui en dérive, mais pas IntegerType, dont le parent est FormType. Étendre FormType touche la lignée correspondante, pas les boutons dont la racine est ButtonType. Chaque extension intervient après le type qu'elle étend dans la résolution de la hiérarchie.

Comment, étape par étape ?

  1. Identifier l'ancêtre commun réel des champs concernés.
  2. Déclarer ce type dans getExtendedTypes, méthode statique retournant un itérable non vide.
  3. Déclarer et typer les nouvelles options avant de les utiliser.
  4. Vérifier l'enregistrement de l'extension et les types qui acceptent effectivement l'option ; une option inconnue doit rester une erreur explicite.

Exemple concret PHP

Extension enregistrée comme service form.type_extension par la configuration habituelle :

<?php
use Symfony\Component\Form\AbstractTypeExtension;
use Symfony\Component\Form\Extension\Core\Type\TextType;
use Symfony\Component\OptionsResolver\OptionsResolver;

final class TextHintExtension extends AbstractTypeExtension
{
    public static function getExtendedTypes(): iterable
    {
        return [TextType::class];
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefault('hint_code', null);
        $resolver->setAllowedTypes('hint_code', ['null', 'string']);
    }
}

L'exemple déclare l'option ; il ne l'affiche pas encore : une vue et un theme doivent l'utiliser si c'est le besoin. Contre-exemple : passer hint_code à IntegerType et attendre qu'il soit reconnu parce que les deux widgets ressemblent à un input. Correction : choisir FormType si cette portée est voulue, ou étendre explicitement les familles adaptées.

Passage canonique conservé

Qui est touché, et quand

Field Extension de TextType
TextType option acceptée
EmailType, enfant de TextType option acceptée
IntegerType, enfant de FormType UndefinedOptionsException : « The option "help_icon" does not exist »
  • Étendre FormType::class touche tous les fields, mais pas les boutons : ButtonType n'a pas de parent.
  • Ordre : chaque extension s'exécute juste après le type qu'elle étend. Pour un EmailType, l'extension de FormType passe avant celle de TextType.

Une coque annonce les modèles de téléphone compatibles ; getExtendedTypes() annonce les types concernés. Étendre FormType n'équipe pas tous les objets sans exception : les boutons appartiennent à une autre racine.

L'enregistrement

À retenir en priorité
  1. La priority la plus haute passe d'abord.
  2. debug:form permet de vérifier l'enregistrement.
  • Un service tagué form.type_extension, posé par l'autoconfiguration pour une class de src/.
  • Plusieurs extensions d'un même type s'ordonnent par l'attribute priority du tag : 0 par défaut, la plus haute d'abord.
  • Cette priority exige de déclarer le service explicitement : #[AsTaggedItem(priority: 10)] sur une extension autoconfigurée est ignoré par FormPass.
  • php bin/console debug:form vérifie l'enregistrement.

Pièges d'examen

△ Piège à éviter

  • Voir l’explication : Un type crée un field ; une extension modifie ceux qui existent.

    Un type crée un field ; une extension modifie ceux qui existent. Pour ajouter une option à un type fourni par Symfony, écrire un nouveau type ne sert à rien.

  • Voir l’explication : La method qui désigne les types étendus est statique

    La method qui désigne les types étendus est statique, retourne un itérable, et ne peut pas être vide.

  • Voir l’explication : Une extension atteint les types enfants

    Une extension atteint les types enfants, pas les types frères : étendre TextType touche EmailType, pas IntegerType.

  • Portée d’une extension du type racine

    Étendre le type racine touche tous les fields, pas les boutons.

  • Voir l’explication : La priority se règle sur le tag

    La priority se règle sur le tag, dans la configuration du service.

Application

À retenir en priorité
  1. La propagation suit l'inheritance des form types.
  2. FormType n'est pas la racine des boutons.
  3. La method est statique.
  4. Une liste vide est une erreur d'enregistrement.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 6 choses :

  • Un type crée un field ; une extension modifie ceux qui existent.
  • getExtendedTypes() : statique, itérable, jamais vide.
  • Elle atteint les descendants : TextType → EmailType, pas IntegerType.
  • Étendre FormType : tous les fields, pas les boutons.
  • Tag form.type_extension, autoconfiguré ; priority sur le tag, la plus haute d'abord.
  • #[AsTaggedItem] : ignoré par FormPass.

Moyen mnémotechnique : « Greffer, pas remplacer ».
