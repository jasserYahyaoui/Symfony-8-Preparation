Objectif

Changer le HTML produit par le rendu d'un form, au bon niveau de spécificité, et au bon endroit : partout, pour un template, ou sur place.

L'essentiel

○ À comprendre

À retenir en priorité
  1. block_prefix ajoute un niveau de personnalisation.
  2. Un préfixe _form_field cible un seul field.

Le rendu d'un form est fait de blocks Twig ; un theme en redéfinit quelques-uns. Pour chaque field, le rendu cherche le block du plus précis au plus vague le long de sa lignée de types, et parcourt les themes du dernier au premier. Tout se joue sur le bon nom de block, au bon endroit.

Le schéma

À retenir en priorité
  1. La recherche commence au préfixe le plus spécifique.
  2. Un email_widget existant peut empêcher d'atteindre text_widget.

L'exemple : le form `user`

▣ Exemple concret

name (TextType), contact (EmailType) et vip (TextType avec block_prefix: 'vip') :

name     ["form", "text", "_user_name"]
contact  ["form", "text", "email", "_user_contact"]
vip      ["form", "text", "vip", "_user_vip"]

Les parties d'un field

À retenir en priorité
  1. Le suffixe _widget cible la saisie.
  2. Le suffixe _row cible l'ensemble de la ligne.

Un nom de block = un préfixe + une partie : _row (le container complet), _label, _widget, _help, _errors. Exemples : email_widget, text_row, _user_contact_label. Le theme par défaut est form_div_layout.html.twig ; Bootstrap, Foundation et Tailwind sont livrés aussi.

La chaîne de recherche

À chaque niveau, tous les themes sont consultés avant de descendre. Le theme par défaut définit email_widget, et aucun theme livré ne définit text_widget : un text_widget personnalisé change les TextType, pas les EmailType.

Chercher une personne par son identité complète avant son service illustre la recherche de block : field précis, type précis, puis ancêtres. Un block général ne remplace pas un block plus spécifique déjà trouvé.

Repère — Trois exemples documentés qui échouent : No. That block is not supplied there; use a block that actually exists. Vérifier le block de base avant parent(). email_widget existe pour conserver le type email.

Cibler un field, ou plusieurs fields

○ À comprendre

C'est quoi ?

Un theme Form fournit des blocks Twig dont le nom combine un préfixe et une partie, par exemple email_widget. La recherche suit les préfixes du champ du plus spécifique vers le plus général. À un niveau donné, les themes disponibles sont examinés avant de descendre au niveau suivant.

À quoi ça sert ?

Une surcharge peut viser un champ précis, un type de champ ou une catégorie plus large. Comprendre cet ordre explique pourquoi un block text_widget peut modifier les champs TextType sans modifier un EmailType pourtant apparenté : un block email_widget plus spécifique existe déjà.

Où dans Symfony ?

La vue possède block_prefixes, qui comprend la lignée des types et un préfixe spécifique au champ. Pour un formulaire nommé user et un enfant contact, _user_contact_widget peut cibler uniquement ce widget. Les noms réels se vérifient dans la vue, notamment lorsqu'une option de préfixe les personnalise.

Comment, étape par étape ?

  1. Choisir la partie à personnaliser : row, label, widget, help ou errors.
  2. Identifier le préfixe correspondant à la portée souhaitée.
  3. Déclarer le block dans un theme appliqué au formulaire.
  4. Conserver les attributes essentiels du widget plutôt que recopier un input incomplet.

Exemple concret Twig

Theme form/contact.html.twig :

{% block _user_contact_widget %}
    <div class="contact-input">{{ block('email_widget') }}</div>
{% endblock %}

Template contenant la vue d'un formulaire nommé user, avec contact de type EmailType :

{% form_theme form 'form/contact.html.twig' %}
{{ form_row(form.contact) }}

Le block spécifique enveloppe le widget email existant. Contre-exemple : appeler _user_contact_widget depuis sa propre définition : cela se rappelle indéfiniment. Correction : déléguer au block moins spécifique, ici email_widget. De même, surcharger seulement text_widget n'est pas un moyen fiable de changer tous ses descendants, puisqu'un descendant peut posséder son propre block plus spécifique.

Passage canonique conservé

Cibler un field, ou plusieurs fields

  • Un seul field : _ + nom du form + nom du field — _user_contact_widget.
  • Plusieurs fields choisis, sans créer de type : l'option block_prefix insère un préfixe dans block_prefixes, et un block vip_widget ne vise que les fields qui le portent.

Où appliquer un theme

○ À comprendre

À retenir en priorité
  1. Un theme only doit fournir les blocks nécessaires.
  2. Importer les blocks de base permet un theme autonome.

C'est quoi ?

Un form theme, thème de formulaire, est un ensemble de blocks Twig qui définissent son HTML. Il ne change ni les données soumises ni les contraintes serveur. Le renderer cherche un nom de block combinant un préfixe et une partie : widget, row, label, help ou errors.

À quoi ça sert ?

Le thème centralise une présentation commune sans recopier la structure de chaque champ dans chaque page. Un block spécifique vise un champ ; un block de type vise une famille. Changer tous les widgets pour personnaliser un seul libellé serait une portée inutilement large.

Où dans Symfony ?

twig.form_themes applique des thèmes globalement. Le tag form_theme les complète pour une vue donnée ; only remplace la liste globale au lieu de la compléter. Parmi plusieurs thèmes, le dernier a priorité pour un même block. Cette priorité ne supprime pas la recherche du nom de block le plus spécifique.

Comment, étape par étape ?

  1. Identifier la partie à personnaliser : une ligne complète n'est pas un widget.
  2. Trouver le préfixe réellement présent dans la vue ; pour le champ contact du formulaire user, _user_contact_label cible son libellé.
  3. Écrire le block dans un fichier de thème dédié.
  4. Appliquer le thème localement si le besoin concerne une page, globalement si la convention concerne tout le site.
  5. Tester également les champs non redéfinis : ils doivent encore trouver les blocks de base.

Exemple concret Twig

Dans templates/form/contact.html.twig, le thème complète les thèmes habituels :

{% block _user_contact_label %}
    <label for="{{ id }}">Adresse de contact</label>
{% endblock %}

Puis, dans une page dont le contexte contient la vue du formulaire nommé user :

{% form_theme form 'form/contact.html.twig' %}
{{ form(form) }}

Seul ce libellé est remplacé ; les autres parties utilisent les thèmes existants. La variable id relie correctement le libellé à son champ. Contre-exemple : ajouter only à un thème ne contenant que ce block. Les autres blocks deviennent introuvables. Correction : conserver les thèmes globaux, ou importer les blocks de base avec {% use 'form_div_layout.html.twig' %} dans un thème réellement autonome. _self demande aussi de maîtriser l'héritage de la page pour éviter l'affichage direct des blocks de thème.

Passage canonique conservé

Où appliquer un theme

Portée Écriture À savoir
globale twig.form_themes le dernier listé gagne
un template {% form_theme form 'form/fields.html.twig' %} s'ajoute aux themes globaux
un template, seul {% form_theme form with [...] only %} remplace tout, theme par défaut compris
sur place {% form_theme form _self %} à une condition : le template étend un autre template
  • Avec only, un theme incomplet fait échouer le rendu : « Unable to render the form as none of the following blocks exist… ». Commencer par {% use 'form_div_layout.html.twig' %}.
  • _self sans extends : chaque block est aussi affiché là où il est écrit, et un appel à block('form_widget_simple') lève une RuntimeError.

Pièges d'examen

△ Piège à éviter

  • Priorité des thèmes de formulaire

    La liste des themes est parcourue de la fin vers le début.

  • Voir l’explication : text_widget n'existe dans aucun theme livré

    text_widget n'existe dans aucun theme livré ; email_widget, si.

  • Voir l’explication : Un field remonte sa propre lignée

    Un field remonte sa propre lignée : un block de type parent ne s'applique pas quand un block plus spécifique existe.

  • Prérequis de _self pour un thème de formulaire

    _self exige un template qui en étend un autre.

  • Distinguer personnalisation de row et widget

    Redéfinir _row quand on voulait _widget efface libellé, aide et erreurs.

  • Voir l’explication : form_theme … only écarte aussi le theme par défaut

    form_theme … only écarte aussi le theme par défaut : un theme incomplet fait échouer le rendu.

Application

À retenir en priorité
  1. La recherche commence au préfixe le plus spécifique.
  2. Un email_widget existant peut empêcher d'atteindre text_widget.
  3. Vérifier le block de base avant parent().
  4. email_widget existe pour conserver le type email.

Fiche express

◆ À mémoriser

Si tu dois retenir seulement 7 choses :

  • Block = préfixe + partie (_row, _label, _widget, _help, _errors).
  • Recherche du plus précis au plus vague : _form_field, type, parent, form.
  • email_widget existe ; text_widget n'existe dans aucun theme livré.
  • Un field : _user_contact_widget ; plusieurs : option block_prefix.
  • twig.form_themes : le dernier gagne.
  • only écarte aussi le theme par défaut.
  • _self exige un extends.

Moyen mnémotechnique : « Du plus précis au plus vague, du dernier au premier ».
