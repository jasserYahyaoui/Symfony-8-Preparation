Objectif

GET /blog/42 sait déjà afficher l'article fourni par notre ArticleCatalog en mémoire. Un autre travail apparaît : une commande d'import doit consulter deux services externes avant de préparer des données. Ce travail est une branche du projet, pas une étape obligatoire de chaque consultation du blog.

Ici, notre application devient cliente HTTP. Nous allons lancer les appels, attendre les données au bon moment et distinguer une absence annoncée par le serveur d'une connexion interrompue. Les laboratoires utilisent Symfony 8.0, PHP 8.4 et des réponses simulées ; ils ne changent pas le catalogue principal.

L'essentiel

À comprendre

À retenir en priorité
  1. request() rend une Response lazy.
  2. Lire immédiatement chaque Response rend la boucle séquentielle.

Si la commande attend intégralement le premier service avant d'appeler le second, leurs attentes s'additionnent. request() retourne une Response lazy, dont on diffère la lecture : nous conservons d'abord les deux objets, puis demandons leurs données. Le transport peut alors faire progresser plusieurs échanges pendant la même période.

Ce chevauchement n'est ni un nouveau processus PHP ni une garantie de durée. request() peut lui-même prendre du temps ou échouer ; les ressources du transport et ses limites de connexions comptent. Lire les headers ou le body attend les données nécessaires si elles ne sont pas encore disponibles.

Cette lecture est aussi un point de contrôle. Un statut 404, un JSON illisible et une panne de transport ne signifient pas la même chose pour l'import. Même une Response oubliée peut signaler son statut 3xx–5xx à sa destruction : ne pas lire n'est pas une politique de gestion des erreurs.

Le schéma

À retenir en priorité
  1. Une erreur HTTP dispose d'une Response.
  2. Une TransportExceptionInterface peut survenir sans Response.

La commande dispose des adresses A et B, indépendantes l'une de l'autre. Le premier dessin montre pourquoi nous conservons les deux Responses avant de demander le contenu de A. Il représente un chemin réussi, avec un transport permettant le chevauchement ; il ne promet pas que B finira après A.

Bleu : lancement ; orange : points d'attente possibles ; vert : résultat. Si B est déjà arrivée lorsque nous la lisons, cette lecture n'attend pas le réseau. À l'inverse, lire A avant d'appeler B supprime ce chevauchement. Conserver les Responses évite également leur destruction immédiate entre les deux lancements. Nous verrons ensuite comment stream() permet de traiter les morceaux disponibles sans imposer l'ordre de lecture A puis B.

Avant cela, il faut nommer les échecs possibles. Le deuxième dessin est une carte de contrats d'exceptions, et non la suite du chronomètre précédent.

Les pointillés orange indiquent exclusivement l'héritage d'interfaces. Une exception HTTP permet de retrouver la Response reçue ; une exception de transport n'offre pas cette garantie. En particulier, un timeout — un délai d'attente dépassé — peut survenir après le traitement distant. Pour une future publication par POST, le rejouer sans mécanisme de déduplication pourrait donc répéter l'effet. Recevoir une erreur localement ne prouve pas l'absence d'effet à distance.

L'exemple : des Requests en parallèle

Exemple concret

À retenir en priorité
  1. Lancer toutes les Requests avant de lire les Responses permet la concurrence.
  2. stream() observe ensuite les chunks ; isLast() indique la fin d'une Response.

Notre premier essai observe uniquement la fin de deux lectures, sans encore importer leurs données. Après chargement de l'autoloader du projet, cette préparation fournit $client et $urls au fragment suivant :

use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;

$client = new MockHttpClient([
    new MockResponse('{"id":42}'),
    new MockResponse('{"images":[]}'),
]);
$urls = [
    'https://example.test/articles/42',
    'https://example.test/articles/42/images',
];

MockHttpClient remplace le réseau par les deux Responses préparées. Les adresses désignent ici des ressources du fournisseur fictif, pas des routes ajoutées à notre blog. Nous conservons le schéma de lancement puis de lecture :

$responses = [];
foreach ($urls as $url) {
    $responses[] = $client->request('GET', $url);   // toutes lancées
}

foreach ($client->stream($responses) as $response => $chunk) {
    if ($chunk->isLast()) {
        // cette Response est complète
    }
}

Le fragment ne produit aucun affichage : pour ces deux réponses réussies, il atteint deux fois la branche isLast(). Un chunk est un morceau du flux ; le dernier marque la fin de la Response, pas la validation métier de son JSON. « Toutes lancées » signifie ici toutes confiées au client avant leur lecture, non toutes transmises physiquement au même instant.

Ce laboratoire vérifie la structure de consommation, pas un gain de temps réseau. Avec un transport réel, l'ordre d'arrivée dépend des services et des connexions. La version tolérante aux erreurs arrivera après l'explication des statuts : ce premier fragment suppose volontairement deux succès.

L'interface

À retenir en priorité
  1. HttpClientInterface expose request(), stream() et withOptions().
  2. withOptions() produit une nouvelle instance.

La commande doit pouvoir utiliser soit le réseau, soit une simulation sans réécrire sa logique. Elle reçoit donc Symfony\Contracts\HttpClient\HttpClientInterface, un contrat séparé des implémentations du component. Dans une application configurée pour cela, l'autowiring fournit le service correspondant ; déclarer le type ne crée pas magiquement un service dans n'importe quel programme PHP.

Les trois methods suivent notre besoin : request($method, $url, $options) démarre un échange ; stream($responses, $timeout) expose les Responses par morceaux ; withOptions($options) retourne une nouvelle instance avec d'autres options par défaut. Pour dériver un client d'import, il faut conserver ce retour. Appeler seulement withOptions() puis continuer avec l'ancien objet ne revient pas à utiliser le nouveau client.

Avant le lot de données, isolons un contrôle de disponibilité. Ce laboratoire indépendant utilise toujours l'autoloader du projet :

use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Contracts\HttpClient\HttpClientInterface;

function readStatus(HttpClientInterface $client): int
{
    return $client->request('GET', 'https://example.test/health')->getStatusCode();
}

$client = new MockHttpClient(new MockResponse('', ['http_code' => 204]));
echo readStatus($client), "\n";

Résultat attendu : 204. La fonction dépend de l'interface, pas du mock ; HttpClient::create() peut fournir une implémentation réelle adaptée aux transports disponibles. Cette substitution ne teste toutefois ni la connectivité ni la configuration TLS de production. Elle montre seulement que notre code sait lire le statut fourni.

Le point central : les Responses sont lazy

Le contrôle de disponibilité lit immédiatement son unique résultat : c'est cohérent pour un appel isolé. Copier cette forme dans la boucle des dix sources d'import aurait un autre effet. Chaque getContent() ou toArray() attendrait son body avant le lancement suivant : le programme fonctionnerait, mais les lectures seraient séquentielles.

Le fonctionnement asynchrone par défaut permet de séparer lancement et consommation. getStatusCode() attend les headers nécessaires ; getContent() attend le contenu complet ; toArray() attend ce contenu puis le décode. Ce sont des besoins différents, pas trois syntaxes équivalentes. Différer la lecture n'implique pas que le transfert ne commencera qu'à cette lecture.

Pour notre lot indépendant, nous gardons donc les objets de retour, puis les consommons. Pour une seconde URL calculée à partir du premier JSON, cette indépendance n'existe plus : il faut d'abord obtenir la donnée nécessaire. La certification attend cette distinction entre possibilité de concurrence et dépendance réelle du programme, pas la promesse « lazy = jamais bloquant ».

🌍 In Real Life

La situation : la commande d'approvisionnement contacte deux fournisseurs indépendants avant d'attendre leurs colis ; attendre le premier avant de contacter le second supprime ce chevauchement.

L’équivalent dans Symfony : demandes lancées → request() ; reçus conservés → Responses lazy ; attente du résultat nécessaire → lecture du statut ou du contenu.

Retour à la réalité technique : le transport et ses limites déterminent la concurrence possible. Lazy ne signifie ni jamais bloquant ni processus détaché. Une seconde URL dépendant du premier résultat doit attendre cette donnée.

La Response

À retenir en priorité
  1. false désactive les exceptions liées au status code.
  2. Un JSON invalide peut toujours lever DecodingExceptionInterface.

Le service distant répond maintenant 404 pour une référence à importer. L'objet reçu implémente Symfony\Contracts\HttpClient\ResponseInterface : ce n'est pas la HttpFoundation\Response que notre controller retournerait au navigateur. Le lire ne transmet aucune Response à l'utilisateur du blog.

getStatusCode() permet de choisir une branche sur 404 sans lever à cause de ce statut ; une erreur de transport reste possible. En revanche, getHeaders(), getContent() et toArray() lèvent par défaut sur les statuts 300 à 599 de la Response obtenue. Leur argument $throw = false désactive ce contrôle HTTP pour l'appel concerné, pas toutes les autres erreurs.

Nous voulons conserver le détail JSON de l'absence. Voici une simulation indépendante avec les mêmes prérequis que précédemment :

use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;

$client = new MockHttpClient(new MockResponse(
    '{"error":"missing"}',
    ['http_code' => 404],
));
$response = $client->request('GET', 'https://example.test/items/42');
$status = $response->getStatusCode();
$data = $response->toArray(false);
echo $status, ': ', $data['error'], "\n";

Résultat attendu : 404: missing. Le chemin historique /items/42 appartient à ce laboratoire distant ; il ne signifie pas que notre article local 42 a disparu. getContent(false) fournirait le texte JSON sans le décoder. toArray(false) peut encore lever une DecodingExceptionInterface : un body vide, un JSON invalide ou le JSON scalaire 42 ne satisfont pas son contrat de tableau. Même un tableau décodé doit ensuite respecter le format métier attendu par l'import ; le mock ci-dessus garantit seul la clé error.

La lecture ne corrige pas non plus une mauvaise configuration d'émission. Ces options se donnent à request() ou comme valeurs par défaut du client :

Option Sens
json encode la valeur et ajoute Content-Type: application/json si absent ; ne pas fournir aussi un body non vide
timeout délai d'inactivité, pas la durée totale
max_duration durée totale ; 0 = illimitée (défaut)
max_redirects 20 par défaut ; 0 = aucun redirect suivi

Pour l'import, timeout = 10 tolère dix secondes d'inactivité : un transfert qui continue à recevoir des données peut durer davantage. max_duration = 10 borne la durée totale de l'échange. Deux zéros ont donc des sens différents : max_duration = 0 n'impose pas de limite totale, tandis que max_redirects = 0 interdit de suivre une redirection. Un 3xx alors exposé reste soumis au contrôle HTTP des methods de lecture.

Enfin, l'option json concerne le body envoyé, alors que toArray() concerne le body reçu. Envoyer du JSON ne garantit pas que le fournisseur répondra avec un JSON valide. C'est précisément pour séparer ces situations que le client expose plusieurs familles d'exceptions.

La hiérarchie d'exceptions

Reprenons les trois résultats possibles d'une source d'import. Un 404 reçu puis lu avec le contrôle HTTP actif relève de ClientExceptionInterface ; un 503 relève de ServerExceptionInterface. Ces contrats HTTP, comme RedirectionExceptionInterface pour un 3xx exposé, héritent de HttpExceptionInterface, qui garantit getResponse(). Nous pouvons donc inspecter la Response associée, en choisissant explicitement si sa lecture doit à nouveau contrôler le statut.

À l'inverse, une connexion interrompue relève de TransportExceptionInterface. TimeoutExceptionInterface en est un sous-contrat. Il n'y a pas de garantie générale de getResponse() à ce niveau, ni de preuve que le serveur n'a rien reçu. La commande doit enregistrer un échec de transport, pas inventer un 404.

Enfin, recevoir un 200 contenant un JSON illisible est un échec de décodage, DecodingExceptionInterface, pas un échec HTTP 4xx. Ces trois branches rejoignent le contrat commun ExceptionInterface, mais les confondre ferait perdre la raison utile au diagnostic.

Le cas 3xx mérite une dernière précision : suivre une redirection peut conduire à un succès final. RedirectionExceptionInterface concerne le 3xx que rencontre une lecture avec contrôle HTTP, notamment lorsque le suivi est désactivé ou sa limite atteinte ; chaque redirection intermédiaire n'est pas nécessairement une exception remise à notre code.

🌍 In Real Life

La situation : le fournisseur peut répondre « indisponible », la liaison peut tomber, ou le document reçu peut être illisible.

L’équivalent dans Symfony : résultat HTTP contrôlé → HttpExceptionInterface ; liaison interrompue → TransportExceptionInterface ; contenu indécodable → DecodingExceptionInterface.

Retour à la réalité technique : seul le contrat HTTP présenté garantit getResponse(). $throw=false supprime le contrôle de statut pour la lecture, pas les erreurs de transport/décodage. Une panne de liaison ne prouve pas l'absence d'effet distant.

Une Response jamais lue lève quand même

À retenir en priorité
  1. Le destructor constitue un filet d'erreur.
  2. getInfo() ne remplace pas getStatusCode() pour ce contrôle.

Supposons que la commande lance une notification puis abandonne immédiatement l'objet retourné. Cela ne transforme pas l'appel en travail durable exécuté ailleurs. Le destructor, appelé à la destruction de l'objet, attend les headers et contrôle un statut non pris en charge. Un appel non assigné tel que $client->request('POST', $url); peut donc attendre et lever sur un 500 avant que la commande poursuive.

Pour maîtriser le point d'échec, nous conservons la Response et lisons explicitement son statut dans la zone de traitement prévue. getStatusCode() désarme ce contrôle HTTP automatique à la destruction ; cela n'empêche pas un appel ultérieur à getContent() ou toArray() de contrôler à nouveau le statut. getInfo('http_code') est une consultation d'information et ne remplace pas cette prise en charge.

Dans le laboratoire précédent, la branche 404 est donc connue avant de décoder le message. Si l'on ne veut plus du transfert, cancel() sert à l'annuler, non à annuler un éventuel effet déjà produit par le serveur. Le filet du destructor évite un oubli silencieux de statut ; il ne dispense pas de choisir une politique explicite de lecture, d'erreur ou d'annulation.

🌍 In Real Life

La situation : jeter un reçu de commande ne délègue pas son suivi à un employé ; un contrôle restant peut encore se déclencher au rangement.

L’équivalent dans Symfony : reçu abandonné → Response détruite ; contrôle restant → attente des headers et contrôle HTTP du destructor ; prise en charge explicite → getStatusCode().

Retour à la réalité technique : getInfo() ne désarme pas ce contrôle. Lire le statut n'empêche pas une lecture ultérieure de contrôler à nouveau le code. cancel() n'annule pas un effet déjà accompli au serveur.

🧠 Comment le mémoriser : « Oublier n'est pas détacher. » Image mentale : reçu non traité revenant au rangement. Question-réflexe : où ai-je explicitement décidé du statut ou de l'annulation ?

⚠️ À ne pas confondre : cycle de vie d'objet et tâche durable en arrière-plan.

Rejouer les échecs : RetryableHttpClient

À retenir en priorité
  1. Le statut et la method déterminent le retry.
  2. Trois retries signifient au plus quatre tentatives.

Une source peut répondre 503 puis redevenir disponible. Une retry est une nouvelle tentative, pas la reprise automatique d'une opération métier au point exact où elle s'était arrêtée. RetryableHttpClient décore un client : il ajoute une politique de décision et d'attente sans changer le contrat reçu par la commande. Dans une application Symfony configurée, retry_failed permet de régler cette fonction.

La table suivante décrit les décisions de GenericRetryStrategy par défaut, pas une règle imposée à toutes les stratégies personnalisées :

Échec Rejoué
423, 425, 429, 502, 503 pour toute method
500, 504, 507, 510 methods idempotentes de la stratégie seulement
erreur de transport examinée par la stratégie methods idempotentes de la stratégie seulement
autre statut, dont 404 jamais

Cette liste de methods est GET, HEAD, PUT, DELETE, OPTIONS, TRACE, QUERY. Elle ne doit pas être déduite d'un autre prédicat Symfony : Request::isMethodIdempotent() connaît aussi PURGE, absent de cette liste. Le décorateur possède en outre un cas distinct avant consultation de la stratégie : en cas d'erreur de transport avec primary_ip vide, il prévoit une nouvelle tentative dans le budget disponible, notamment pour l'échec de résolution DNS. « Toute erreur de transport exige une method idempotente » serait donc trop général pour décrire l'implémentation complète.

Le budget par défaut est de trois retries, donc quatre tentatives au plus, hors échanges supplémentaires liés aux redirections. Le délai de base est de 1 seconde, doublé à chaque retry ; le jitter, une variation aléatoire de 10 % par défaut, empêche d'annoncer exactement 1, 2 puis 4 secondes. Un Retry-After interprétable prend priorité sur le délai de la stratégie. Cet espacement évite de répéter immédiatement un appel vers un service déjà indisponible.

Pour observer la décision sans attendre ni contacter un serveur, ce laboratoire indépendant simule 503 puis 200 et autorise une seule retry :

use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Component\HttpClient\Retry\GenericRetryStrategy;
use Symfony\Component\HttpClient\RetryableHttpClient;

$mock = new MockHttpClient([
    new MockResponse('', ['http_code' => 503]),
    new MockResponse('{"ok":true}', ['http_code' => 200]),
]);
$client = new RetryableHttpClient($mock, new GenericRetryStrategy(delayMs: 0), 1);
$data = $client->request('GET', 'https://example.test/health')->toArray();
var_export($data['ok']);

Résultat attendu : true, après une nouvelle tentative. Le délai nul appartient au laboratoire, pas à une recommandation pour le service réel. Si le budget s'épuise, le décorateur laisse passer le dernier résultat : il ne transforme pas un 503 en succès, et toArray() peut alors lever l'exception HTTP. Un dernier échec de transport reste lui aussi un échec.

Le GET de lecture se prête à une nouvelle tentative ; pour un POST de publication, il faut examiner les effets métier. La politique par défaut rejoue POST sur 503, mais pas sur 500. Elle ne fournit pas à elle seule une garantie d'unicité de publication.

🌍 In Real Life

La situation : rappeler un fournisseur après un incident demande un budget d'essais et une attente ; cela ne prouve pas que la commande précédente n'a rien produit.

L’équivalent dans Symfony : rappels autorisés → budget de retries ; décision → stratégie et cas du décorateur ; espacement → délai, jitter ou Retry-After.

Retour à la réalité technique : la stratégie par défaut distingue POST en 503 et en 500 ; le cas de transport sans primary_ip se traite aussi dans le décorateur. Timeout d'inactivité et durée totale ne sont pas la même borne. Aucune retry n'assure l'unicité métier.

🧠 Comment le mémoriser : « Réessayer n'est pas reprendre sans doublon. » Image mentale : compteur d'essais à côté du bon initial. Question-réflexe : quel effet distant pourrait déjà exister ?

⚠️ À ne pas confondre : liste idempotente de la stratégie et prédicat Request incluant PURGE.

Un stream dont une Response échoue

À retenir en priorité
  1. Un échec de chunk ne doit pas abandonner les autres Responses.
  2. Lire le statut au premier chunk et traiter isTimeout().

Revenons aux sources indépendantes : A répond correctement, B échoue. Abandonner toute la boucle ferait perdre le résultat de A. Nous plaçons donc le try/catch autour de la lecture de chaque chunk, dans la boucle, afin d'enregistrer l'échec associé à sa Response puis de poursuivre les autres.

Trois signaux guident cette lecture. isTimeout() signale une attente de stream dépassée ; nous choisissons ici d'annuler la Response, plutôt que d'attendre à nouveau. isFirst() annonce les premiers headers : c'est le moment de lire getStatusCode() et d'appliquer notre politique HTTP. isLast() marque la fin. Les morceaux intermédiaires portent le contenu. Les methods du chunk peuvent lever une TransportExceptionInterface, y compris isTimeout() lorsqu'il s'agit d'une véritable erreur de transport.

Ce laboratoire indépendant reprend le cas A/B avec une erreur simulée :

use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Contracts\HttpClient\Exception\TransportExceptionInterface;

$client = new MockHttpClient([
    new MockResponse('OK'),
    new MockResponse('', ['error' => 'Connexion simulée indisponible']),
]);
$responses = [];
foreach (['a', 'b'] as $id) {
    $responses[] = $client->request('GET', 'https://example.test/'.$id, ['user_data' => $id]);
}

$results = [];
foreach ($client->stream($responses, 1.0) as $response => $chunk) {
    $id = $response->getInfo('user_data');
    try {
        if ($chunk->isTimeout()) {
            $response->cancel();
            $results[$id] = 'Délai dépassé';
        } elseif ($chunk->isFirst()) {
            $status = $response->getStatusCode();
            if (200 !== $status) {
                $response->cancel();
                $results[$id] = 'Statut inattendu : '.$status;
            }
        } elseif ($chunk->isLast()) {
            $results[$id] = 'Terminé';
        } else {
            $chunk->getContent();
        }
    } catch (TransportExceptionInterface $error) {
        $response->cancel();
        $results[$id] = 'Échec de transport : '.$error->getMessage();
    }
}
var_export($results);

Le tableau attendu associe a à Terminé et b à un message d'échec de transport, sans dépendre de l'ordre d'arrivée. user_data conserve notre identifiant local avec la Response. Le contenu OK est consommé puis ignoré : ce programme contrôle les fins de transfert, pas un import complet.

Deux limites protègent cette lecture. D'abord, exiger exactement 200 est la politique de ce laboratoire, pas une définition de tous les succès HTTP. Ensuite, un catch interne ne récupère pas magiquement toute erreur de l'itérateur : si nous négligeons le statut au premier chunk, le stream peut lui-même déclencher le contrôle HTTP en reprenant son exécution. Lire le statut dès isFirst() et traiter les chunks d'erreur évite de laisser ces contrôles implicites décider à notre place.

La commande peut maintenant rendre un bilan partiel fiable. Si elle doit ensuite importer des articles, il reste à décoder et valider les données réussies ; « transfert terminé » n'autorise pas encore leur publication.

🌍 In Real Life

La situation : plusieurs livraisons arrivent par morceaux ; un colis abîmé est associé à son fournisseur sans jeter automatiquement les colis corrects des autres.

L’équivalent dans Symfony : morceaux → chunks ; première information → isFirst() et lecture du statut ; fin → isLast() ; incident localisé → traitement de lecture dans la boucle.

Retour à la réalité technique : les méthodes du chunk peuvent lever. Le catch interne ne capture pas toute erreur de l'itérateur ; lire le statut au premier chunk évite un contrôle HTTP laissé implicite. Fin de transfert ne signifie pas données validées.

Pièges d'examen

Piège à éviter

  • Voir l’explication : Un JSON invalide n'est pas un statut 4xx.

    Un JSON invalide n'est pas un statut 4xx. Notre fournisseur peut répondre 200 avec un body invalide : toArray() lève alors une DecodingExceptionInterface, pas une ClientExceptionInterface. Passer false ne désactive que le contrôle HTTP, pas le décodage ni le transport. Même le JSON valide 42 ne devient pas un tableau accepté par cette method.

  • Voir l’explication : Une retry dépend de la politique, pas seulement du mot POST.

    Une retry dépend de la politique, pas seulement du mot POST. Avec la stratégie par défaut et un budget disponible, POST en 500 n'est pas rejoué, POST en 503 l'est. Le cas de résolution DNS traité par le décorateur ne se résume pas non plus à la table des statuts. Vérifier la décision technique ne prouve jamais à elle seule l'absence de doublon métier.

  • Voir l’explication : Une Response ignorée n'est pas une tâche détachée.

    Une Response ignorée n'est pas une tâche détachée. Son destructor peut attendre et lever ; getInfo() ne vaut pas prise en charge du statut. Conserver les Responses puis les consommer explicitement sert à la fois la concurrence et la maîtrise des points d'échec.

Fiche express

À mémoriser

Relisez le bilan de la commande d'import dans l'ordre de ses décisions :

  1. Recevoir HttpClientInterface permet de substituer un mock au réseau. Une Request sortante n'est pas la Request entrante de GET /blog/42.
  2. Conserver les Responses lazy, puis lire, permet le chevauchement des échanges indépendants si le transport le permet ; aucune durée n'est promise.
  3. Lire getStatusCode() permet de traiter 404 sans exception de statut. getHeaders(), getContent() et toArray() contrôlent les 3xx–5xx par défaut ; false ne supprime pas les erreurs de transport ou de décodage.
  4. Prendre en charge le statut évite de le laisser au destructor. getInfo() ne désarme pas ce contrôle ; abandonner l'objet n'est pas détacher un travail durable.
  5. Distinguer les exceptions conserve le diagnostic. Parmi les contrats présentés, HttpExceptionInterface garantit getResponse() ; un timeout ne prouve pas que le serveur n'a rien traité.
  6. Borner l'attente exige de distinguer timeout et max_duration. Le suivi autorise 20 redirections par défaut ; max_redirects = 0 le coupe. Les retries ont leur budget, leurs délais et leur politique : 503 et 500 ne sont pas interchangeables pour POST.
  7. Consommer le stream exige le statut au premier chunk et la gestion des erreurs de chunk dans la boucle. Un résultat partiel doit signaler les échecs, puis valider les données réussies avant leur utilisation.

« Lancer, conserver, lire, décider » résume cette branche. Le trajet principal du blog peut continuer à lire son catalogue en mémoire : ajouter HttpClient n'impose aucun appel distant à chaque affichage.
