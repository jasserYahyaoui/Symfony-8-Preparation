Objectif

Émettre une Request sortante avec HttpClientInterface et comprendre quand elle s'exécute réellement — c'est tout l'enjeu de cet item.

L'essentiel

○ À comprendre

À retenir en priorité
  1. request() rend une Response lazy.
  2. Lire immédiatement chaque Response rend la boucle séquentielle.

HttpClientInterface::request() rend la main tout de suite : la Request n'est attendue qu'au premier accès à la Response. On lance donc toutes les Requests, puis on les lit. Lire, c'est aussi décider des erreurs : un statut 3xx-5xx lève à la lecture — ou à la destruction si personne ne l'a lu.

Le schéma

À retenir en priorité
  1. Une erreur HTTP dispose d'une Response.
  2. Une TransportExceptionInterface peut survenir sans Response.

L'exemple : des Requests en parallèle

▣ Exemple concret

À retenir en priorité
  1. Lancer toutes les Requests avant de lire les Responses permet la concurrence.
  2. stream() observe ensuite les chunks ; isLast() indique la fin d'une Response.
$responses = [];
foreach ($urls as $url) {
    $responses[] = $client->request('GET', $url);   // toutes lancées
}

foreach ($client->stream($responses) as $response => $chunk) {
    if ($chunk->isLast()) {
        // cette Response est complète
    }
}

L'interface

À retenir en priorité
  1. HttpClientInterface expose request(), stream() et withOptions().
  2. withOptions() produit une nouvelle instance.

Trois methods, injectées par autowiring via HttpClientInterface : request($method, $url, $options), stream($responses, $timeout) et withOptions($options), qui rend une nouvelle instance du client.

Le point central : les Responses sont lazy

Revoir la règle : request() rend une Response lazy.

Le client est asynchrone par défaut : getStatusCode(), getContent() ou toArray() bloquent, pas request(). Lire chaque Response dans la loop qui l'émet rend l'ensemble séquentiel, sans erreur visible.

Envoyer une pile de courriers puis ouvrir les retours permet leur progression simultanée. Envoyer un courrier et attendre sa lecture avant le suivant transforme le même client lazy en usage séquentiel.

Repère de l’exemple : It creates all responses first, then consumes them with stream(). Lancer toutes les Requests avant de lire les Responses permet la concurrence. stream() observe ensuite les chunks ; isLast() indique la fin d'une Response.

La Response

À retenir en priorité
  1. false désactive les exceptions liées au status code.
  2. Un JSON invalide peut toujours lever DecodingExceptionInterface.

getHeaders(), getContent() et toArray() lèvent sur un statut 3xx-5xx, sauf avec $throw = false. getStatusCode() ne déclare qu'une TransportExceptionInterface : c'est l'appel qui inspecte un 404 sans rien attraper. toArray() décode et peut lever une DecodingExceptionInterface, même avec false.

Option Sens
json encode et pose Content-Type: application/json ; exclusif avec body
timeout délai d'inactivité, pas la durée totale
max_duration durée totale ; 0 = illimitée (défaut)
max_redirects 20 par défaut ; 0 = aucun redirect suivi

Deux zéros, deux sens : max_duration = 0 illimite, max_redirects = 0 interdit. En test, MockHttpClient et MockResponse remplacent le réseau.

La hiérarchie d'exceptions

Revoir la règle : Une erreur HTTP dispose d'une Response.

Seule HttpExceptionInterface expose getResponse(), parce qu'elle seule a une Response à montrer. TimeoutExceptionInterface hérite de TransportExceptionInterface. RedirectionExceptionInterface ne lève qu'une fois max_redirects atteint.

Une Response jamais lue lève quand même

À retenir en priorité
  1. Le destructor constitue un filet d'erreur.
  2. getInfo() ne remplace pas getStatusCode() pour ce contrôle.

Si rien n'a lu le statut, le destructor lève sur un 3xx-5xx : un $client->request('POST', $url); non assigné devient synchrone et lève sur un 500. getInfo('http_code') ne désarme pas ce filet.

Rejouer les échecs : RetryableHttpClient

À retenir en priorité
  1. Le statut et la method déterminent le retry.
  2. Trois retries signifient au plus quatre tentatives.
Échec Rejoué
423, 425, 429, 502, 503 pour toute method
500, 504, 507, 510, erreur de transport methods idempotentes seulement
autre statut, dont 404 jamais

Trois retries par défaut, donc quatre Requests au plus ; délai de 1 s doublé à chaque essai, Retry-After prioritaire. Épuisés, la dernière Response est rendue telle quelle. Dans une application : l'option retry_failed.

Un stream dont une Response échoue

À retenir en priorité
  1. Un échec de chunk ne doit pas abandonner les autres Responses.
  2. Lire le statut au premier chunk et traiter isTimeout().

L'échec d'une Response est levé par les methods de son chunk ; non attrapée, la TransportExceptionInterface termine la loop pour toutes : le try/catch va dans la loop. Le statut se lit au premier chunk (isFirst()), sinon un 404 lève au stream. Un timeout passé à stream() donne un chunk dont isTimeout() vaut true.

Pièges d'examen

△ Piège à éviter

Revoir la règle : false désactive les exceptions liées au status code.

toArray() n'est pas json_decode() : sur un body invalide, il lève une DecodingExceptionInterface, pas une ClientExceptionInterface.

Un POST en 500 n'est pas rejoué, un POST en 503 l'est.

Application

À retenir en priorité
  1. HttpClientInterface expose request(), stream() et withOptions().
  2. withOptions() produit une nouvelle instance.
  3. Le destructor constitue un filet d'erreur.
  4. getInfo() ne remplace pas getStatusCode() pour ce contrôle.
  • Flashcard : HttpClientInterface expose request(), stream() et withOptions(). withOptions() produit une nouvelle instance.
  • Flashcard : Le destructor constitue un filet d'erreur. getInfo() ne remplace pas getStatusCode() pour ce contrôle.

Fiche express

◆ À mémoriser

Revoir la règle : Un échec de chunk ne doit pas abandonner les autres Responses.

Si tu dois retenir seulement 7 choses :

  • request() ne bloque pas ; lancer tout, puis lire.
  • getStatusCode() ne lève pas sur un statut ; les autres, si.
  • Jamais lu : le destructor lève ; getInfo() ne désarme pas.
  • getResponse() seulement sur HttpExceptionInterface.
  • timeout = inactivité ; max_duration = total ; 20 redirects.
  • Retry : 503 pour tous, 500 pour les idempotentes ; 404 jamais.
  • stream() : try/catch dans la loop, statut au premier chunk.

Moyen mnémotechnique : « Lancer tout, lire après, attraper dedans ».
