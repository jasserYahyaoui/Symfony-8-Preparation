Objectif

Émettre une Request sortante avec HttpClientInterface et comprendre quand elle s'exécute réellement — c'est tout l'enjeu de cet item.

L'essentiel

À comprendre

À retenir en priorité
  1. request() rend une Response lazy.
  2. Lire immédiatement chaque Response rend la boucle séquentielle.

HttpClientInterface::request() fournit une Response lazy : conserver les Responses puis les lire permet le chevauchement si le transport le permet. Ce n'est pas une garantie universelle d'absence d'attente dans request() : le transport, ses ressources et ses limites de connexions comptent aussi. La lecture peut attendre les headers ou le body et lever une exception. Un statut 3xx–5xx non pris en charge peut aussi être signalé à la destruction.

Le schéma

À retenir en priorité
  1. Une erreur HTTP dispose d'une Response.
  2. Une TransportExceptionInterface peut survenir sans Response.

Bleu : lancement ; orange : points d'attente possibles ; vert : résultat. Chemin sans erreur et avec transport permettant le chevauchement. « Lazy » signifie que la lecture est différée, pas que request() ne peut jamais prendre de temps ni lever une erreur. Conserver les Responses évite leur destruction immédiate avant le lancement suivant.

Ici, les pointillés orange représentent exclusivement l'héritage d'interfaces, pas l'ordre de survenue des erreurs. Un timeout peut arriver après le traitement du serveur : rejouer un POST sans déduplication peut répéter son effet.

L'exemple : des Requests en parallèle

Exemple concret

À retenir en priorité
  1. Lancer toutes les Requests avant de lire les Responses permet la concurrence.
  2. stream() observe ensuite les chunks ; isLast() indique la fin d'une Response.
$responses = [];
foreach ($urls as $url) {
    $responses[] = $client->request('GET', $url);   // toutes lancées
}

foreach ($client->stream($responses) as $response => $chunk) {
    if ($chunk->isLast()) {
        // cette Response est complète
    }
}

L'interface

À comprendre

À retenir en priorité
  1. HttpClientInterface expose request(), stream() et withOptions().
  2. withOptions() produit une nouvelle instance.

C'est quoi ?

HttpClientInterface est le contrat Symfony pour effectuer des demandes HTTP sortantes. Il expose request() pour démarrer une demande, stream() pour consommer des réponses progressivement et withOptions() pour obtenir un client dérivé avec d'autres options par défaut.

À quoi ça sert ?

Dépendre de l'interface sépare le service métier du transport concret. Le même code peut utiliser un client réel dans l'application et un client simulé dans un test sans envoyer de requête réseau. L'interface n'est pas celle de la Request entrante d'HttpFoundation.

Où dans Symfony ?

Le contrat se trouve dans Symfony\Contracts\HttpClient, les implémentations dans le component HttpClient. Dans une application configurée, l'interface peut être injectée. HttpClient::create() choisit un transport disponible ; MockHttpClient fournit des réponses contrôlées. withOptions() retourne une nouvelle instance : conserver ce retour est nécessaire pour utiliser ses nouveaux défauts.

Comment, étape par étape ?

  1. Dépendre du contrat dans le service consommateur.
  2. Fournir l'implémentation au moment de construire ce service.
  3. Appeler request avec méthode, URL et options adaptées.
  4. Consommer et vérifier la réponse, en traitant aussi les erreurs différées.

Exemple concret PHP

Avec HttpClient 8.0 et ses contracts chargés, sans réseau :

<?php
use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Contracts\HttpClient\HttpClientInterface;
function readStatus(HttpClientInterface $client): int
{
    return $client->request('GET', 'https://example.test/health')->getStatusCode();
}
$client = new MockHttpClient(new MockResponse('', ['http_code' => 204]));
echo readStatus($client), "\n";

On attend 204 sans contacter example.test. Contre-exemple : construire systématiquement un client réel dans la fonction métier, rendant le test dépendant d'un serveur. Correction : recevoir l'interface puis fournir le mock en test. Une simulation vérifie le contrat et les branches du code, pas la connectivité réelle ni la configuration TLS de production.

Passage canonique conservé

Trois methods, injectées par autowiring via HttpClientInterface : request($method, $url, $options), stream($responses, $timeout) et withOptions($options), qui rend une nouvelle instance du client.

Le point central : les Responses sont lazy

Le client est asynchrone par défaut : getStatusCode(), getContent() ou toArray() attendent les données nécessaires si elles manquent. Lire chaque Response dans la loop qui l'émet rend l'ensemble séquentiel, sans erreur visible.

Envoyer une pile de courriers puis ouvrir les retours permet leur progression simultanée. Envoyer un courrier et attendre sa lecture avant le suivant transforme le même client lazy en usage séquentiel.

Repère de l’exemple : It creates all responses first, then consumes them with stream(). Lancer toutes les Requests avant de lire les Responses permet la concurrence. stream() observe ensuite les chunks ; isLast() indique la fin d'une Response.

La Response

À comprendre

À retenir en priorité
  1. false désactive les exceptions liées au status code.
  2. Un JSON invalide peut toujours lever DecodingExceptionInterface.

C'est quoi ?

La Response du client HTTP implémente Symfony\Contracts\HttpClient\ResponseInterface. Elle représente une réponse distante reçue, contrairement à la Response HttpFoundation que l'application construit pour envoyer son propre résultat.

À quoi ça sert ?

  • getStatusCode() lit le statut sans lever une exception simplement parce qu'il vaut 404 ou 500.
  • getHeaders() fournit des noms en minuscules associés à des listes de valeurs.
  • getContent() lit une chaîne ; toArray() décode un JSON qui doit produire un tableau PHP.
  • getInfo() expose des informations de transport disponibles à l'instant de l'appel, sans attendre la fin ; elles peuvent être incomplètes.
  • cancel() interrompt une réponse dont on ne veut plus poursuivre le transfert.

Où dans Symfony ?

Par défaut, getHeaders, getContent et toArray lèvent pour les statuts 300–599. Passer false désactive ce contrôle de statut pour cet appel, pas les erreurs réseau ni les erreurs de décodage. Un JSON scalaire valide, comme 42, n'est pas un tableau acceptable pour toArray.

Comment, étape par étape ?

  1. Lire le statut si le code veut gérer lui-même les réponses d'erreur.
  2. Choisir la lecture correspondant au format réellement attendu.
  3. Passer false seulement si cette gestion explicite remplace le contrôle automatique.
  4. Valider ensuite le schéma métier : un tableau décodé n'est pas nécessairement la structure attendue.

Exemple concret PHP

<?php
use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
$client = new MockHttpClient(new MockResponse('{"error":"missing"}', ['http_code' => 404]));
$response = $client->request('GET', 'https://example.test/items/42');
$status = $response->getStatusCode();
$data = $response->toArray(false);
echo $status, ': ', $data['error'], "\n";

On attend 404: missing. Contre-exemple : croire que toArray(false) ne peut jamais échouer ; un body HTML ou JSON scalaire échoue au décodage attendu. Correction : distinguer statut, transport, syntaxe JSON et structure métier, puis traiter chaque problème au bon niveau.

Passage canonique conservé

getHeaders(), getContent() et toArray() lèvent sur un statut 3xx-5xx, sauf avec $throw = false. getStatusCode() ne déclare qu'une TransportExceptionInterface : c'est l'appel qui inspecte un 404 sans rien attraper. toArray() décode et peut lever une DecodingExceptionInterface, même avec false.

Option Sens
json encode et pose Content-Type: application/json ; exclusif avec body
timeout délai d'inactivité, pas la durée totale
max_duration durée totale ; 0 = illimitée (défaut)
max_redirects 20 par défaut ; 0 = aucun redirect suivi

Deux zéros, deux sens : max_duration = 0 illimite, max_redirects = 0 interdit. En test, MockHttpClient et MockResponse remplacent le réseau.

La hiérarchie d'exceptions

Parmi ces contrats, HttpExceptionInterface garantit getResponse(). TimeoutExceptionInterface hérite de TransportExceptionInterface, laquelle ne garantit pas qu'aucune donnée n'a circulé. RedirectionExceptionInterface signale un statut 3xx non suivi lorsqu'une lecture avec contrôle HTTP le rencontre, notamment quand la limite de redirections est atteinte ou le suivi désactivé.

Une Response jamais lue lève quand même

À comprendre

À retenir en priorité
  1. Le destructor constitue un filet d'erreur.
  2. getInfo() ne remplace pas getStatusCode() pour ce contrôle.

C'est quoi ?

Le destructeur d'une réponse non traitée sert de filet de sécurité : il attend les headers et peut lever une exception HTTP pour un statut 300–599. Une demande lancée puis immédiatement oubliée n'est donc pas une opération garantie sans attente ni signalement d'erreur.

À quoi ça sert ?

Ce comportement évite de perdre silencieusement un échec simplement parce que le programme n'a jamais lu le résultat. En contrepartie, laisser le contrôle au destructeur rend le moment de l'échec moins explicite, notamment lorsque la dernière référence disparaît.

Où dans Symfony ?

Appeler getStatusCode() désactive ce contrôle automatique de statut au destructeur : le code est alors censé prendre la responsabilité de l'interprétation. Cela ne transforme pas les appels suivants à getContent ou toArray en lectures sans contrôle : leur argument throw reste vrai par défaut. Une erreur de transport peut aussi survenir pendant la lecture du statut.

Comment, étape par étape ?

  1. Conserver la Response tant que l'opération est en cours.
  2. Lire son statut dans le périmètre où les erreurs sont gérées.
  3. Traiter le statut et le contenu selon le contrat.
  4. Annuler explicitement le transfert si le résultat est abandonné, plutôt que compter sur la destruction.

Exemple concret PHP

<?php
use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
$client = new MockHttpClient(new MockResponse('', ['http_code' => 404]));
$response = $client->request('GET', 'https://example.test/items/42');
$status = $response->getStatusCode();
if (404 === $status) {
    echo "La ressource demandée est absente.\n";
} elseif (200 !== $status) {
    throw new RuntimeException('Statut inattendu : '.$status);
}

Le 404 est ici interprété volontairement. Contre-exemple : appeler getStatusCode uniquement pour empêcher l'exception puis ignorer sa valeur ; l'erreur redevient silencieuse. Correction : décider explicitement du résultat métier ou propager un échec. La destruction ne doit pas servir de mécanisme principal de synchronisation ou de gestion des erreurs de l'application.

Passage canonique conservé

Si rien n'a lu le statut, le destructor lève sur un 3xx-5xx : un $client->request('POST', $url); non assigné devient synchrone et lève sur un 500. getInfo('http_code') ne désarme pas ce filet.

Rejouer les échecs : RetryableHttpClient

À comprendre

À retenir en priorité
  1. Le statut et la method déterminent le retry.
  2. Trois retries signifient au plus quatre tentatives.

C'est quoi ?

Une retry est une nouvelle tentative après un échec. RetryableHttpClient décore un client pour appliquer une stratégie de décision et de délai. Une tentative supplémentaire peut résoudre une panne temporaire, mais peut aussi répéter un effet métier si la première demande avait déjà été appliquée.

À quoi ça sert ?

La stratégie générique 8.0 distingue les statuts rejouables pour toutes les méthodes (423, 425, 429, 502, 503) de ceux réservés à sa liste de méthodes idempotentes (500, 504, 507, 510, ainsi que les erreurs de transport). Cette liste est GET, HEAD, PUT, DELETE, OPTIONS, TRACE et QUERY ; ne pas la déduire aveuglément d'un autre helper Request, qui connaît aussi PURGE.

Où dans Symfony ?

Le comportement par défaut autorise trois nouvelles tentatives, donc jusqu'à quatre tentatives au total. GenericRetryStrategy part d'un délai de 1000 ms, le multiplie par deux et ajoute par défaut une variation aléatoire de 10 %, appelée jitter. Les délais ne sont donc pas exactement 1, 2 et 4 secondes à chaque exécution ; d'autres informations comme Retry-After peuvent aussi intervenir dans le décorateur.

Comment, étape par étape ?

  1. Classer l'échec et vérifier si la méthode est éligible.
  2. Vérifier que le budget de nouvelles tentatives n'est pas épuisé.
  3. Attendre selon la stratégie.
  4. Rejouer puis traiter le résultat final, sans masquer l'échec si toutes les tentatives échouent.

Exemple concret PHP

Simulation d'une erreur 503 puis d'un succès, avec délai nul uniquement pour ce laboratoire :

<?php
use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Component\HttpClient\Retry\GenericRetryStrategy;
use Symfony\Component\HttpClient\RetryableHttpClient;
$mock = new MockHttpClient([
    new MockResponse('', ['http_code' => 503]),
    new MockResponse('{"ok":true}', ['http_code' => 200]),
]);
$client = new RetryableHttpClient($mock, new GenericRetryStrategy(delayMs: 0), 1);
$data = $client->request('GET', 'https://example.test/health')->toArray();
var_export($data['ok']);

On attend true après au plus une nouvelle tentative. Contre-exemple : affirmer que POST n'est jamais rejoué : POST en 503 l'est par défaut, contrairement à POST en 500. Correction : vérifier la stratégie et les effets métier ; la capacité technique de rejouer ne garantit pas à elle seule l'absence de doublon applicatif.

Passage canonique conservé
Échec Rejoué
423, 425, 429, 502, 503 pour toute method
500, 504, 507, 510, erreur de transport methods idempotentes seulement
autre statut, dont 404 jamais

Trois retries par défaut, donc quatre Requests au plus ; délai de 1 s doublé à chaque essai, Retry-After prioritaire. Épuisés, la dernière Response est rendue telle quelle. Dans une application : l'option retry_failed. La comparaison GET/POST pour une erreur transport suppose une résolution DNS réussie : RetryableHttpClient rejoue spécialement les échecs DNS (primary_ip vide), indépendamment de la méthode. Le budget de retries reste applicable et l'erreur finale remonte.

Un stream dont une Response échoue

À comprendre

À retenir en priorité
  1. Un échec de chunk ne doit pas abandonner les autres Responses.
  2. Lire le statut au premier chunk et traiter isTimeout().

C'est quoi ?

Un stream est une consommation progressive par morceaux, appelés chunks. Le client peut suivre plusieurs réponses et fournir chaque morceau lorsqu'il arrive, au lieu d'attendre le contenu complet de chaque réponse dans l'ordre des demandes.

À quoi ça sert ?

Le traitement peut isoler l'échec d'une réponse sans abandonner toutes les autres. Il doit néanmoins distinguer un délai d'inactivité signalé par isTimeout(), l'arrivée des premiers headers par isFirst() et la fin par isLast(). Le statut se lit dès le premier morceau, avant de traiter le contenu comme un succès.

Où dans Symfony ?

$client->stream($responses, $timeout) fournit les couples réponse/morceau. Une erreur de transport peut être levée lors de la lecture du morceau ; le try/catch doit donc entourer ce traitement dans la boucle. Un timeout de stream peut être une occasion de décider d'attendre de nouveau ou d'annuler, pas nécessairement une preuve que le serveur ne répondra jamais.

Comment, étape par étape ?

  1. Identifier chaque réponse, par exemple avec user_data.
  2. Traiter les délais et lire le statut au premier morceau.
  3. Consommer les données ou constater la fin.
  4. En cas d'abandon, appeler cancel et conserver un résultat d'échec explicite.

Exemple concret PHP

Simulation de deux réponses, dont une échoue avant ses headers :

<?php
use Symfony\Component\HttpClient\MockHttpClient;
use Symfony\Component\HttpClient\Response\MockResponse;
use Symfony\Contracts\HttpClient\Exception\TransportExceptionInterface;
$client = new MockHttpClient([
    new MockResponse('OK'),
    new MockResponse('', ['error' => 'Connexion simulée indisponible']),
]);
$responses = [];
foreach (['a', 'b'] as $id) {
    $responses[] = $client->request('GET', 'https://example.test/'.$id, ['user_data' => $id]);
}
$results = [];
foreach ($client->stream($responses, 1.0) as $response => $chunk) {
    $id = $response->getInfo('user_data');
    try {
        if ($chunk->isTimeout()) {
            $response->cancel();
            $results[$id] = 'Délai dépassé';
        } elseif ($chunk->isFirst()) {
            $status = $response->getStatusCode();
            if (200 !== $status) {
                $response->cancel();
                $results[$id] = 'Statut inattendu : '.$status;
            }
        } elseif ($chunk->isLast()) {
            $results[$id] = 'Terminé';
        } else {
            $chunk->getContent();
        }
    } catch (TransportExceptionInterface $error) {
        $response->cancel();
        $results[$id] = 'Échec de transport : '.$error->getMessage();
    }
}
var_export($results);

Le contenu du succès est volontairement consommé puis ignoré dans ce laboratoire ; les résultats distinguent réussite et échec, indépendamment de leur ordre d'arrivée. Contre-exemple : laisser un catch vide puis annoncer que toutes les réponses ont réussi. Correction : enregistrer ou propager chaque échec selon le contrat appelant. Ce scénario simulé ne valide pas les conditions réseau d'une installation réelle.

Passage canonique conservé

L'échec d'une Response est levé par les methods de son chunk ; non attrapée, la TransportExceptionInterface termine la loop pour toutes : le try/catch va dans la loop. Le statut se lit au premier chunk (isFirst()), sinon un 404 lève au stream. Un timeout passé à stream() donne un chunk dont isTimeout() vaut true.

Pièges d'examen

Piège à éviter

  • Voir l’explication : toArray() n'est pas json_decode()

    toArray() n'est pas json_decode() : sur un body invalide, il lève une DecodingExceptionInterface, pas une ClientExceptionInterface.

  • Voir l’explication : Un POST en 500 n'est pas rejoué

    Un POST en 500 n'est pas rejoué, un POST en 503 l'est.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Responses lazy : conserver les appels lancés, puis lire ; l'attente dépend des données déjà disponibles et du transport.
  • getStatusCode() ne lève pas sur un statut ; les autres, si.
  • Jamais lu : le destructor lève ; getInfo() ne désarme pas.
  • getResponse() seulement sur HttpExceptionInterface.
  • timeout = inactivité ; max_duration = total ; 20 redirects.
  • Retry : 503 pour tous, 500 pour les idempotentes ; 404 jamais.
  • stream() : try/catch dans la loop, statut au premier chunk.

Moyen mnémotechnique : « Lancer tout, lire après, attraper dedans ».
