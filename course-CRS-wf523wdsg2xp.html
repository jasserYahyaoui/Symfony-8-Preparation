Objectif

Inspecter une valeur, et interroger l'application sur ce qu'elle a réellement compris de sa configuration.

L'essentiel

À comprendre

À retenir en priorité
  1. dd interrompt le programme.
  2. dump peut continuer le traitement.

dump() affiche une valeur et la rend ; dd() affiche puis arrête. Avec DebugBundle, le dump va dans la debug toolbar, pas dans la Response. Un dump() oublié en production ne casse rien de façon visible : il corrompt la Response. Et des commands disent ce que Symfony a retenu de sa configuration. Le profiler web relève d'un autre item.

Le schéma

À retenir en priorité
  1. Un octet ajouté peut invalider le JSON.
  2. Retirer les dumps du code publié.

Bleu : appels ; ambre : routage du dump ; vert : effet. Démarrer server:dump ne détourne pas magiquement tous les processus : leur handler doit cibler ce serveur. Le comportement de repli dépend de la configuration. Les buffers PHP peuvent retarder l'envoi des headers ; leur perte n'est pas systématique.

L'exemple

Exemple concret

À retenir en priorité
  1. dump n'est pas uniquement une écriture.
  2. Sa valeur de retour peut être utilisée mais ne justifie pas un oubli.
$total = dump($cart)->getTotal();                       // affiche, la chaîne continue
[$a, $b] = dump($cart->getItems(), $cart->getDiscount()); // plusieurs valeurs : un array
dd($total);                                               // affiche, puis arrête
php bin/console router:match /cart -v        # pourquoi cette URL répond 404
php bin/console debug:config framework        # la configuration après fusion

`dump()` plutôt que `var_dump()`

À retenir en priorité
  1. Le collecteur sépare diagnostic et contenu.
  2. Sans intégration la sortie peut revenir au body.
  • Une vue adaptée au type, en HTML ou colorée en terminal, et la détection des références : un object rencontré deux fois n'est pas réaffiché.
  • dump(5) rend 5 ; dump(1, 2) affiche les deux et rend [1, 2].
  • Avec DebugBundle, le dump va dans la debug toolbar. Si la barre ne peut pas s'afficher — dd(), die(), une erreur fatale —, il repart sur l'output normal.
  • php bin/console server:dump collecte les dumps à part : la parade pour une API JSON, où tout octet imprimé casse la Response.

Un `dump()` oublié en production

À retenir en priorité
  1. Le mode d'installation ne nettoie pas le code.
  2. Un dump oublié reste dangereux pour la Response.

La documentation installe VarDumper et DebugBundle avec --dev, mais FrameworkBundle exige symfony/error-handler, qui exige symfony/var-dumper en dependency ordinaire. Seul DebugBundle est absent. En prod :

Appel Résultat
function_exists('dump') true
route qui appelle dump() 200 ; le dump HTML part avant le contenu
headers de cette Response ceux de PHP : le Cache-Control de Symfony a disparu

Ce tableau décrit un scénario sans handler personnalisé et avec sortie déjà transmise. Selon le buffering, les headers peuvent encore être modifiés. Le risque durable est l'émission de données dans le corps ou hors du canal attendu : retirer les dumps, surtout ceux contenant des credentials ou données personnelles, plutôt que compter sur --no-dev.

Pas d'erreur fatale, donc, mais une Response corrompue — fatale pour une API JSON.

Interroger l'application

À comprendre

À retenir en priorité
  1. Lire le résultat et lire la référence sont deux besoins.
  2. Choisir la command adaptée.

C'est quoi ?

Déboguer consiste à confronter le comportement attendu à l'état réellement utilisé par l'application. Les commandes de diagnostic montrent les routes, services, listeners et valeurs fusionnées ; elles sont plus précises qu'une lecture d'un seul fichier source.

À quoi ça sert ?

Une configuration peut être importée, surchargée ou compilée. Observer son résultat permet d'expliquer pourquoi une route ou un service n'est pas celui imaginé, sans désactiver les contrôles qui signalent l'erreur.

Où dans Symfony ?

  • debug:container et debug:autowiring : services et types injectables.
  • debug:router puis router:match : routes déclarées et sélection effective.
  • debug:event-dispatcher : listeners et ordre.
  • debug:config : configuration résolue ; config:dump-reference : catalogue des options disponibles.
  • debug:twig : extensions et chemins connus de Twig.

Comment, étape par étape ?

  1. Formuler une question précise, comme « quelle route répond à ce chemin ? ».
  2. Choisir la commande et l'environment concernés.
  3. Comparer le résultat à la définition attendue.
  4. Si une inspection de valeur est nécessaire en développement, utiliser les outils de dump avec prudence, puis retirer le diagnostic temporaire du code livré.

Exemple concret en shell

php bin/console debug:router
php bin/console router:match /catalogue -v
php bin/console debug:config framework

La seconde commande peut expliquer les correspondances ou leur absence ; son chemin est un exemple de diagnostic, pas la promesse qu'une route existe ici.

dump() produit une représentation structurée et laisse normalement continuer ; dd() affiche puis arrête. Avec l'intégration de débogage, des dumps peuvent être dirigés vers la toolbar ou un serveur de dump. Sans cette intégration, une sortie peut se retrouver dans le corps HTTP et casser un document JSON.

Contre-exemple : conserver un dump puis compter sur --no-dev pour l'éliminer. Correction : retirer le code de diagnostic et vérifier la Response ; VarDumper peut rester une dependency indirecte ordinaire. Ne jamais dumper un mot de passe, un token ou une configuration complète contenant des secrets. Le serveur de dump est un outil de développement, pas une justification pour laisser ces données dans le code de production.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La résolution peut être examinée directement.
  2. La liste des routes seule ne suffit pas toujours.
  • Voir l’explication : dd() arrête l'exécution ; dump() non

    dd() arrête l'exécution ; dump() non, et dump() rend sa valeur.

  • Voir l’explication : dump() va dans la debug toolbar

    dump() va dans la debug toolbar quand DebugBundle est installé, pas dans la Response.

  • Voir l’explication : --no-dev ne supprime pas dump()

    --no-dev ne supprime pas dump() : VarDumper est requis par ErrorHandler. Une sortie directe peut corrompre le corps et empêcher l'envoi des headers.

  • Voir l’explication : debug:config montre la configuration fusionnée

    debug:config montre la configuration fusionnée, pas le contenu d'un file.

Fiche express

À mémoriser

À retenir en priorité
  1. L'event dispatcher possède son diagnostic.
  2. Il aide à comprendre une priority inattendue.

Si tu dois retenir seulement 7 choses :

  • dump() rend sa valeur (plusieurs → array) ; dd() arrête.
  • DebugBundle : la debug toolbar ; server:dump : à part.
  • En prod, dump() existe : Response corrompue.
  • router:match -v explique un 404.
  • debug:config : configuration fusionnée.
  • config:dump-reference : toutes les keys possibles.
  • debug:autowiring <mot> : quoi injecter.

Moyen mnémotechnique : « Voir, rendre, demander ».

dump() rend sa valeur, dd() arrête ; toolbar ou serveur selon configuration ; sortie directe : risque pour corps et headers ;
router:match -v (404), debug:config (fusionné), config:dump-reference (possible), debug:autowiring, debug:container
