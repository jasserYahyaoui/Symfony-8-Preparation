Objectif

GET /blog/42 réussit. Demandons maintenant /blog/999 : la route existe, mais le catalogue ne contient pas cet article. Ce cas attendu doit produire 404 ; une panne inattendue du traitement ne doit pas être maquillée en article absent. Le traitement d'erreur transforme l'échec en réponse tout en gardant un diagnostic privé.

L'essentiel

À comprendre

À retenir en priorité
  1. Le message ne détermine pas le status code.
  2. Le contrat de l'exception porte cette information.

Une exception non interceptée pendant le traitement HTTP peut être transformée en Response d'erreur par le kernel. Un avertissement PHP n'est converti que si le handler est configuré pour le lever. Son status code vient de la configuration, d'un attribute ou d'une interface — sinon normalement 500, quel que soit le message. Avec debug actif, on voit la page d'exception ; sans debug, une page d'erreur qu'on personnalise au niveau le plus bas qui suffit.

Un statut décrit le résultat HTTP ; un message d'exception décrit un diagnostic. Écrire « 404 » dans ce message ne donne pas un statut 404. De même, choisir une jolie page d'erreur ne corrige ni la cause ni le contrat HTTP.

Le schéma

À retenir en priorité
  1. Le détail sert au développement.
  2. Ne pas publier de trace aux utilisateurs.

Ce trajet concerne une exception capturée pendant le traitement HTTP. Un import Console ou un handler Messenger possède sa propre frontière de traitement : il ne traverse pas automatiquement kernel.exception.

Bleu : traitement ; ambre : décisions ; vert : sortie. Chemin standard avec exceptions capturées ; un listener peut fournir sa propre Response, et une terminaison brutale ne garantit aucun rendu. Les deprecations sont exclues de la conversion en exception par l'ErrorHandler Symfony.

L'exemple

Exemple concret

À retenir en priorité
  1. Créer une exception ne la lève pas.
  2. throw déclenche le traitement d'erreur.

Extrait de BlogController, qui étend AbstractController. On suppose les imports Symfony\Component\Routing\Attribute\Route et Symfony\Component\HttpFoundation\Response, le type applicatif ArticleCatalog importé, son service injecté et son contrat find(int $id) renvoyant l'article ou null. Le template reçoit un ArticleView en mémoire ; aucune persistance n'est impliquée :

#[Route('/blog/{id}', name: 'blog_show')]
public function show(int $id, ArticleCatalog $articles): Response
{
    $article = $articles->find($id)
        ?? throw $this->createNotFoundException('Article absent'); // 404
    // throw new \RuntimeException('Article absent'); // normalement 500

    return $this->render('blog/show.html.twig', ['article' => $article]);
}

Avec 42, le contrôleur rend la page normale ; avec 999, throw interrompt l'action avant le rendu et le chemin standard produit 404. Un chemin inconnu peut aussi aboutir à 404, mais avant tout appel à cette action. Ne pas attraper tout Throwable pour le convertir en 404 : une erreur de programmation ou une panne mérite son diagnostic distinct.

Tout est une exception

À retenir en priorité
  1. Un warning peut être journalisé sans interrompre.
  2. La configuration décide de la conversion.

Le titre est un raccourci à ne pas prendre au pied de la lettre. Retourner explicitement une réponse 404 n'exige pas de lever une exception, et une dépréciation observée n'est pas convertie par le handler Symfony.

Un 404 levé dans le controller emprunte le traitement des exceptions HTTP. Ne pas assimiler toute erreur fatale ou tout arrêt du processus à ce chemin. Une erreur PHP non fatale — un avertissement — ne devient une ErrorException que si framework.php_errors.throw est vraie, et sa default value est %kernel.debug% :

Le tableau suppose le handler standard actif, la politique par défaut et un contrôleur qui retourne normalement 200 s'il continue. Un warning ne choisit pas lui-même le statut :

Mode Key d'array absente
debug 500, ErrorException : Warning: Undefined array key
sans debug 200 : l'avertissement est journalisé, le code continue

Cette continuation ne prouve pas l'absence de défaut : vérifier les entrées du catalogue ou de l'import reste nécessaire. Si le handler ou le réglage de conversion change, le nom dev/prod ne suffit plus à prédire ce résultat.

Deux affichages, selon l'environment

À retenir en priorité
  1. La page debug masque la présentation normale.
  2. La prévisualisation permet de voir le template d'erreur.

Pendant le développement, nous cherchons la ligne fautive. Pour le lecteur du blog, nous voulons une explication sobre qui ne divulgue pas la trace :

Environment Ce que voit le user
debug actif (habituellement dev) la page d'exception : message, trace, journaux
debug désactivé (habituellement prod) une page d'erreur minimale

Avec debug actif, on ne voit donc pas sa propre page d'erreur : les routes /_error, chargées sous when@dev, la prévisualisent — /_error/404, /_error/404.json (route /{code}.{_format}).

Ces URLs supposent les routes d'aperçu chargées et le rendu du format demandé disponible. L'aperçu vérifie une présentation avec un code donné ; il ne prouve pas que /blog/999 choisit réellement 404 ni que le pipeline de sécurité de cette requête est identique. Garder aussi le test fonctionnel du trajet réel, et ne pas exposer les diagnostics en production.

Le status code

À retenir en priorité
  1. L'attribute ne domine pas toujours l'interface.
  2. La configuration explicite peut imposer le code.

🌍 In Real Life

La situation : au restaurant, écrire « plat introuvable » sur une note ne suffit pas à classer officiellement l'incident. La procédure utilise une catégorie définie.

L’équivalent dans Symfony : texte libre → message de l'exception ; catégorie officielle → contrat HTTP ou mapping configuré ; réponse au visiteur → statut produit pour /blog/999.

Retour à la réalité technique : une exception ordinaire reste un 500 dans le parcours standard sans mapping adapté. Le statut vient des mécanismes décrits ci-dessous, pas d'une recherche de mots dans le message ; construire une exception sans la lever n'emprunte pas ce trajet.

🧠 Comment le mémoriser : « Le statut suit le contrat, pas la phrase. » Image mentale : note libre à côté d'une case de classification. Question-réflexe : quel mécanisme fixe réellement le code HTTP ?

⚠️ À ne pas confondre : code de l'exception et statut HTTP.

Dans le chemin standard, ErrorListener applique d'abord la configuration ou l'attribut, puis la représentation FlattenException reprend les contrats HTTP. Une FlattenException est un objet de données décrivant l'exception pour le diagnostic/rendu, pas l'exception originale à relancer :

Source Exemple Statut
framework.exceptions, pour une class status_code: 418 418 — s'impose même à l'interface
#[WithHttpStatus] sur la class #[WithHttpStatus(404)] 404 — ignoré si l'interface est implémentée
HttpExceptionInterface::getStatusCode() NotFoundHttpException 404
RequestExceptionInterface BadRequestException 400
rien de tout cela RuntimeException 500

Le message n'est jamais lu. createNotFoundException(), dans AbstractController, rend une NotFoundHttpException — qu'il faut lever avec throw.

La recherche dans framework.exceptions suit l'ordre des classes configurées : le premier instanceof correspondant avec un status_code défini l'emporte. Une classe parente placée trop tôt peut donc masquer un réglage plus spécifique. Le listener enveloppe au besoin l'exception dans une exception HTTP, en conservant les en-têtes HTTP existants. Une simple configuration du niveau de journal ne fixe pas le statut.

Sans mapping de statut et sans HttpExceptionInterface, WithHttpStatus peut fournir code et headers. Ensuite, FlattenException lit l'interface HTTP, sinon RequestExceptionInterface pour 400, sinon retient normalement 500. Un listener personnalisé qui fournit sa réponse peut modifier le trajet : la table n'est pas une loi sur toute réponse créée dans l'application.

Quatre niveaux d'intervention

À retenir en priorité
  1. Choisir l'intervention minimale.
  2. La logique kernel.exception n'est pas nécessaire pour un simple style.

🌍 In Real Life

La situation : améliorer la carte d'excuses remise au restaurant ne demande pas de remplacer tout le protocole de traitement des incidents.

L’équivalent dans Symfony : présentation de la carte → template ; format du compte rendu → normalizer ; fabrication de la réponse → contrôleur d'erreur ; interception du traitement → listener kernel.exception.

Retour à la réalité technique : choisir le niveau minimal adapté au besoin et à l'intégration active. Personnaliser le rendu ne répare pas la cause et ne doit pas transformer un échec en succès HTTP ni divulguer une trace interne.

🧠 Comment le mémoriser : « Changer la carte sans refaire le protocole. » Image mentale : une carte remplacée dans une procédure intacte. Question-réflexe : dois-je changer le contenu, le format ou la décision ?

⚠️ À ne pas confondre : page d'erreur publique et diagnostic privé.

Le lecteur doit voir « page introuvable » et un lien de retour ; inutile de remplacer toute la gestion d'erreur pour cela. Pour /api/blog/999, le même échec peut demander une représentation JSON sobre :

Besoin Intervention
changer l'apparence de la page surcharger les templates d'erreur
changer un output non-HTML (JSON, XML) un normalizer de FlattenException
changer la logique de génération surcharger le controller d'erreur : framework.error_controller
maîtriser entièrement le traitement écouter kernel.exception

Prendre le niveau le plus bas qui suffit. Le normalizer concerne la représentation de FlattenException, avec Serializer et le rendu non-HTML configurés ; il ne choisit pas automatiquement le statut depuis un message.

L'exception HTTP minimale, à lever dans le trajet applicatif, reste :

use Symfony\Component\HttpKernel\Exception\NotFoundHttpException;

throw new NotFoundHttpException('Ressource introuvable.');

Le fragment ne fabrique pas lui-même une réponse hors du kernel. new RuntimeException('404') n'est pas son équivalent.

En interne, ErrorListener inscrit sa phase de mapping/journalisation à priorité 0, puis sa génération à -128. Cette seconde phase prépare une requête dupliquée en GET visant le contrôleur d'erreur et appelle le kernel en sous-requête, sans capture récursive à cet appel. Ce n'est ni un redirect du navigateur ni un nouveau boot de l'application. La réponse obtenue est placée dans l'événement.

Intervenir par kernel.exception signifie assumer plus de responsabilités : statut, en-têtes, représentation et journalisation. Sans réponse fournie par les listeners, HttpKernel relance l'exception. Ne pas convertir systématiquement tous les échecs en succès pour faire disparaître les tests rouges.

Surcharger un template

À retenir en priorité
  1. Le template par status code est prioritaire.
  2. Le générique sert de repli.

Avec le rendu d'erreur Twig configuré, garder cette page indépendante des services qui viennent potentiellement d'échouer :

  • Dans templates/bundles/TwigBundle/Exception/ : error404.html.twig pour ce code, sinon error.html.twig, sinon la page minimale par défaut.
  • En debug, les templates sont ignorés : c'est la page d'exception.
  • TwigErrorRenderer passe status_code, status_text et exception, une FlattenException — dont on ne montre jamais la trace à un user.
  • Une 404 de routage peut survenir avant l'initialisation du firewall : ne pas supposer que le user est disponible dans le template d'erreur. Une 404 levée plus tard dans un controller n'a pas nécessairement ce contexte.

Par exemple, dans templates/bundles/TwigBundle/Exception/error404.html.twig, un fragment volontairement statique suffit :

<h1>Page introuvable</h1>
<p>La page demandée n'est pas disponible.</p>
<a href="/blog/page/1">Revenir aux articles</a>

Le lien suppose la pagination du récit configurée. Le template ne lit ni le catalogue défaillant, ni la trace, ni un utilisateur obligatoire. Il change le corps public, pas à lui seul le statut de la réponse. Tester séparément le 404 de routage et l'article 999 absent conserve la nuance de contexte de sécurité.

À mémoriser

À retenir en priorité
  1. Ce niveau intervient dans la logique d'erreur.
  2. L'utiliser seulement si les options plus simples ne suffisent pas.

Pour l'article absent, vérifier 404 et une page publique sobre. Pour une défaillance inattendue, conserver le statut et le diagnostic appropriés. L'aperçu contrôle l'apparence ; le test de la vraie requête contrôle le comportement.

Si tu dois retenir seulement 7 choses :

  • Avertissement → exception selon php_errors.throw, hors deprecations.
  • Statut : une configuration explicite peut primer ; HttpExceptionInterface fournit son code. WithHttpStatus ne remplace pas le code d'une exception qui implémente cette interface. RequestExceptionInterface peut produire 400 ; sinon 500.
  • Le message n'est jamais lu.
  • Debug actif : page détaillée ; désactivé : page d'erreur.
  • error404.html.twig puis error.html.twig.
  • /_error/{code} pour prévisualiser, .json pour un autre format.
  • Template < normalizer < controller d'erreur < kernel.exception.

Moyen mnémotechnique : « Configuration et contrats, pas le message ».

warning → exception selon php_errors.throw (défaut lié au debug) ; kernel.exception ; statut selon configuration et contrats ;
WithHttpStatus ne remplace pas HttpExceptionInterface ; debug actif : détails ; sinon errorCODE puis error.html.twig ; /_error/{code}.{format}

Pour examiner la cause sans modifier le contrat public, passer au débogage du code.
