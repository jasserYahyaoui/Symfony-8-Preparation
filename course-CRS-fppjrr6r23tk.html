Objectif

Savoir ce que Symfony fait d'une erreur, et à quel niveau intervenir selon ce qu'on veut changer.

L'essentiel

À comprendre

À retenir en priorité
  1. Le message ne détermine pas le status code.
  2. Le contrat de l'exception porte cette information.

Une exception non interceptée pendant le traitement HTTP peut être transformée en Response d'erreur par le kernel. Un avertissement PHP n'est converti que si le handler est configuré pour le lever. Son status code vient de la configuration, d'un attribute ou d'une interface — sinon normalement 500, quel que soit le message. Avec debug actif, on voit la page d'exception ; sans debug, une page d'erreur qu'on personnalise au niveau le plus bas qui suffit.

Le schéma

À retenir en priorité
  1. Le détail sert au développement.
  2. Ne pas publier de trace aux utilisateurs.

Bleu : traitement ; ambre : décisions ; vert : sortie. Chemin standard avec exceptions capturées ; un listener peut fournir sa propre Response, et une terminaison brutale ne garantit aucun rendu. Les deprecations sont exclues de la conversion en exception par l'ErrorHandler Symfony.

L'exemple

Exemple concret

À retenir en priorité
  1. Créer une exception ne la lève pas.
  2. throw déclenche le traitement d'erreur.

Extrait PHP : contexte de class, method ou signature requis. Syntaxe vérifiée dans ce contexte ; ce fragment ne constitue pas un programme autonome.

#[Route('/product/{id}')]
public function show(int $id, ProductRepository $products): Response
{
    $product = $products->find($id)
        ?? throw $this->createNotFoundException('Produit absent'); // 404
    // throw new \RuntimeException('Produit absent');  // 500 : le message n'est pas lu

    return $this->render('product/show.html.twig', ['product' => $product]);
}

Tout est une exception

À retenir en priorité
  1. Un warning peut être journalisé sans interrompre.
  2. La configuration décide de la conversion.

Un 404 levé dans le controller emprunte le traitement des exceptions HTTP. Ne pas assimiler toute erreur fatale ou tout arrêt du processus à ce chemin. Une erreur PHP non fatale — un avertissement — ne devient une ErrorException que si framework.php_errors.throw est vraie, et sa default value est %kernel.debug% :

Mode Key d'array absente
debug 500, ErrorException : Warning: Undefined array key
sans debug 200 : l'avertissement est journalisé, le code continue

Deux affichages, selon l'environment

À retenir en priorité
  1. La page debug masque la présentation normale.
  2. La prévisualisation permet de voir le template d'erreur.
Environment Ce que voit le user
debug actif (habituellement dev) la page d'exception : message, trace, journaux
debug désactivé (habituellement prod) une page d'erreur minimale

Avec debug actif, on ne voit donc pas sa propre page d'erreur : les routes /_error, chargées sous when@dev, la prévisualisent — /_error/404, /_error/404.json (route /{code}.{_format}).

Le status code

À retenir en priorité
  1. L'attribute ne domine pas toujours l'interface.
  2. La configuration explicite peut imposer le code.

L'ordre, lu dans ErrorListener :

Source Exemple Statut
framework.exceptions, pour une class status_code: 418 418 — s'impose même à l'interface
#[WithHttpStatus] sur la class #[WithHttpStatus(404)] 404 — ignoré si l'interface est implémentée
HttpExceptionInterface::getStatusCode() NotFoundHttpException 404
RequestExceptionInterface BadRequestException 400
rien de tout cela RuntimeException 500

Le message n'est jamais lu. createNotFoundException(), dans AbstractController, rend une NotFoundHttpException — qu'il faut lever avec throw.

Quatre niveaux d'intervention

À comprendre

À retenir en priorité
  1. Choisir l'intervention minimale.
  2. La logique kernel.exception n'est pas nécessaire pour un simple style.

C'est quoi ?

Le traitement d'erreur transforme une exception en Response adaptée tout en conservant un diagnostic interne. Le statut HTTP exprime la nature de l'échec ; le corps public ne doit pas dévoiler une trace ou des données sensibles.

À quoi ça sert ?

On peut améliorer la présentation sans réécrire toute la gestion d'exception. Distinguer présentation et statut évite une page d'erreur élégante rendue involontairement avec 200.

Où dans Symfony ?

  • Pour l'apparence HTML : surcharger le template d'erreur.
  • Pour la représentation non HTML : adapter la normalisation de l'erreur.
  • Pour la logique de construction : personnaliser le controller d'erreur.
  • Pour une intervention sur le traitement lui-même : écouter kernel.exception.

Choisir le niveau le plus limité qui répond au besoin.

Comment, étape par étape ?

  1. Lever une exception appropriée ; la construire sans throw ne déclenche pas son traitement.
  2. Déterminer le statut depuis les contrats et la configuration, jamais depuis les mots du message. Une exception ordinaire conduit généralement à 500 ; HttpExceptionInterface fournit un statut HTTP.
  3. Tenir compte des surcharges : framework.exceptions peut imposer un statut ; un WithHttpStatus ne doit pas être supposé prioritaire sur toute autre information.
  4. Rendre une page publique sobre et conserver la journalisation utile. Le mode debug permet le détail de développement ; le nom de l'environment seul ne remplace pas la vérification d'APP_DEBUG.

Exemple concret PHP

Dans une application HttpKernel, cette exception porte explicitement un 404 :

<?php
use Symfony\Component\HttpKernel\Exception\NotFoundHttpException;

throw new NotFoundHttpException('Ressource introuvable.');

Il s'agit d'un fragment à exécuter dans le trajet applicatif, pas d'un script autonome produisant lui-même une Response HTTP. Contre-exemple : throw new RuntimeException('404') en pensant obtenir un 404. Correction : employer le contrat HTTP approprié, puis tester le statut réellement rendu.

Les pages de prévisualisation d'erreur en développement aident à examiner les templates de production ; elles ne justifient pas de rendre publiques les traces ou le profiler. Personnaliser une page ne doit ni supprimer l'erreur des journaux ni convertir systématiquement ses statuts en succès.

Pages d'erreur 8.0.

Passage canonique conservé
Besoin Intervention
changer l'apparence de la page surcharger les templates d'erreur
changer un output non-HTML (JSON, XML) un normalizer de FlattenException
changer la logique de génération surcharger le controller d'erreur : framework.error_controller
maîtriser entièrement le traitement écouter kernel.exception

Prendre le niveau le plus bas qui suffit.

Surcharger un template

À retenir en priorité
  1. Le template par status code est prioritaire.
  2. Le générique sert de repli.
  • Dans templates/bundles/TwigBundle/Exception/ : error404.html.twig pour ce code, sinon error.html.twig, sinon la page minimale par défaut.
  • En debug, les templates sont ignorés : c'est la page d'exception.
  • TwigErrorRenderer passe status_code, status_text et exception, une FlattenException — dont on ne montre jamais la trace à un user.
  • Une 404 de routage peut survenir avant l'initialisation du firewall : ne pas supposer que le user est disponible dans le template d'erreur. Une 404 levée plus tard dans un controller n'a pas nécessairement ce contexte.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. La trace peut exposer l'application.
  2. Le rendu public doit rester minimal.
  • Voir l’explication : Une exception ordinaire donne 500

    Une exception ordinaire donne 500, quel que soit son message. Ce qui change le statut : l'interface, l'attribute #[WithHttpStatus], la configuration framework.exceptions, ou une RequestExceptionInterface (400).

  • Voir l’explication : Un avertissement PHP n'est une exception qu'en debug

    Un avertissement PHP n'est une exception qu'en debug, par défaut.

  • Voir l’explication : Le mode debug pilote l'affichage détaillé

    Le mode debug pilote l'affichage détaillé, pas le nom d'environnement seul.

  • Voir l’explication : Avec debug actif, prévisualiser sa propre page d'erreur

    Avec debug actif, prévisualiser sa propre page d'erreur : utiliser les routes /_error.

  • Ordre de recherche des templates d’erreur

    error<code>.html.twig d'abord, error.html.twig ensuite.

  • Voir l’explication : 404 de routage et identité.

    404 de routage et identité. Une erreur de routage précoce peut précéder l'initialisation du contexte de sécurité ; prévoir une page sans utilisateur.

Fiche express

À mémoriser

À retenir en priorité
  1. Ce niveau intervient dans la logique d'erreur.
  2. L'utiliser seulement si les options plus simples ne suffisent pas.

Si tu dois retenir seulement 7 choses :

  • Avertissement → exception selon php_errors.throw, hors deprecations.
  • Statut : une configuration explicite peut primer ; HttpExceptionInterface fournit son code. WithHttpStatus ne remplace pas le code d'une exception qui implémente cette interface. RequestExceptionInterface peut produire 400 ; sinon 500.
  • Le message n'est jamais lu.
  • Debug actif : page détaillée ; désactivé : page d'erreur.
  • error404.html.twig puis error.html.twig.
  • /_error/{code} pour prévisualiser, .json pour un autre format.
  • Template < normalizer < controller d'erreur < kernel.exception.

Moyen mnémotechnique : « Configuration et contrats, pas le message ».

warning → exception selon php_errors.throw (défaut lié au debug) ; kernel.exception ; statut selon configuration et contrats ;
WithHttpStatus ne remplace pas HttpExceptionInterface ; debug actif : détails ; sinon errorCODE puis error.html.twig ; /_error/{code}.{format}
