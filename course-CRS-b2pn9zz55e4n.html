Objectif

Modifier un form pendant son cycle de vie : ajouter un field selon la donnée, assainir une valeur brute, réagir après la submission. C'est le mécanisme qui rend un form dynamique.

L'essentiel

À comprendre

À retenir en priorité
  1. PRE_SET_DATA concerne les données initiales.
  2. PRE_SUBMIT précède les transformations de submission.

buildForm() s'exécute une fois, sans connaître ni l'object ni la Request. Les cinq form events permettent d'intervenir plus tard : deux à la mise en place de la donnée initiale, trois à la submission. À chaque event, il faut savoir quelle donnée on reçoit et si l'on peut toujours ajouter un field.

Le schéma

À retenir en priorité
  1. L'enfant termine avant le SUBMIT du parent.
  2. Le parent peut ainsi traiter le field dépendant.

L'exemple : pays et région

Exemple concret

À retenir en priorité
  1. Le listener lit le pays transformé avec getForm()->getData().
  2. Il ajoute region au parent qui peut toujours intégrer ce field, pas à l'enfant déjà soumis.
$builder->add('country', ChoiceType::class, ['choices' => $countries]);

$builder->addEventListener(FormEvents::PRE_SET_DATA, function (FormEvent $event) {
    $address = $event->getData();                                 // l'object initial
    $this->addRegion($event->getForm(), $address?->country);
});

$builder->get('country')->addEventListener(FormEvents::POST_SUBMIT, function (FormEvent $event) {
    $country = $event->getForm()->getData();                      // le pays soumis
    $this->addRegion($event->getForm()->getParent(), $country);   // au parent
});

Deux moments, cinq events

Event Phase Usage
PRE_SET_DATA mise en place modifier la donnée initiale, ajouter ou retirer des fields selon elle
POST_SET_DATA mise en place décider en connaissant l'état complet (object neuf ou existant ?)
PRE_SUBMIT submission assainir la donnée brute, ajouter des fields selon ce qui est envoyé
SUBMIT submission modifier la norm data ; les enfants sont déjà soumis
POST_SUBMIT submission réagir après coup ; la validation s'exécute ici

Ce que porte chaque event

À comprendre

À retenir en priorité
  1. Distinguer event data et form data.
  2. Dans PRE_SET_DATA, lire les données sur l'event.

C'est quoi ?

Un event de formulaire expose la donnée de la phase où il est déclenché. getData sur l'event et getData sur le Form ne désignent donc pas toujours la même représentation ni le même instant. PRE_SUBMIT porte les données brutes soumises ; SUBMIT porte la donnée normalisée ; POST_SUBMIT expose la donnée de vue de l'event alors que le Form possède sa donnée modèle finale.

À quoi ça sert ?

Choisir la bonne phase évite de traiter une chaîne brute comme un objet métier déjà converti, ou de modifier une structure lorsque les enfants ont déjà été soumis. Le nom POST_SUBMIT ne garantit pas non plus que tous les autres listeners de cette phase ont déjà tourné.

Où dans Symfony ?

PRE_SET_DATA et POST_SET_DATA entourent l'installation initiale du modèle. Dans PRE_SET_DATA, lire event.getData évite une réentrée dans Form.getData alors que l'installation est en cours. Les enfants exécutent leur soumission avant SUBMIT du parent ; un POST_SUBMIT d'enfant peut encore agir sur le parent non soumis.

Comment, étape par étape ?

  1. Identifier la représentation dont l'opération a besoin.
  2. Choisir l'event qui la fournit.
  3. Utiliser event.setData seulement dans une phase où cette modification a un sens et est autorisée.
  4. Ne pas utiliser un event tardif pour corriger rétroactivement une étape de conversion déjà terminée.

Exemple concret PHP

Extrait de buildForm, pour normaliser uniquement une chaîne title dans un tableau brut soumis :

$builder->addEventListener(\Symfony\Component\Form\FormEvents::PRE_SUBMIT, static function (\Symfony\Component\Form\FormEvent $event): void {
    $data = $event->getData();
    if (is_array($data) && isset($data['title']) && is_string($data['title'])) {
        $data['title'] = trim($data['title']);
        $event->setData($data);
    }
});

Le code garde les entrées de type inattendu pour le traitement d'erreur normal, plutôt que les convertir arbitrairement. Contre-exemple : attendre POST_SUBMIT pour réécrire la saisie brute et penser que toute la chaîne recommencera. Correction : intervenir avant sa conversion, ou traiter une donnée modèle au moment approprié. Ajouter un enfant au SUBMIT du même form peut être accepté techniquement sans que cet enfant soit soumis ; cette tolérance n'en fait pas la bonne phase.

Passage canonique conservé

Ce que porte chaque event

Un field texte avec un model transformer entre l'int 5 et la string 'n:5', soumis avec 'n:7' :

Event $event->getData() $event->getForm()->getData()
PRE_SET_DATA 5 (modèle) interdit : RuntimeException
POST_SET_DATA 5 (modèle) 5
PRE_SUBMIT 'n:7' (brut : strings, arrays, UploadedFile) 5
SUBMIT 'n:7' (norm data) 5
POST_SUBMIT 'n:7' (view data) 7

Dans PRE_SET_DATA, $form->getData() lève « A cycle was detected. Listeners to the PRE_SET_DATA event must not call getData() if the form data has not already been set. » : lire $event->getData().

Ce que dit le code sur le verrouillage

À comprendre

À retenir en priorité
  1. L'ajout utile doit précéder la submission des enfants.
  2. Une opération acceptée n'implique pas le traitement attendu.

C'est quoi ?

Le verrouillage de structure dépend du Form concerné. Dans son SUBMIT, les enfants ont déjà été parcourus mais le marqueur submitted n'est pas posé ; dans son POST_SUBMIT, il l'est. Un enfant peut donc être soumis alors que son parent reste en cours de traitement.

À quoi ça sert ?

Une sélection convertie dans un enfant peut déterminer un autre champ du parent. L'ajout doit se faire au parent au bon moment ; l'ajouter à l'enfant déjà soumis est interdit, et attendre SUBMIT du parent serait trop tard pour sa soumission normale.

Où dans Symfony ?

Form::add refuse un Form marqué soumis. L'ajout pendant SUBMIT peut être techniquement accepté sans soumettre le nouveau champ. Avec l'extension Validator, le ValidationListener lance le contrôle depuis POST_SUBMIT de la racine ; POST_SUBMIT d'un enfant ne signifie pas que cette validation globale a déjà eu lieu. Des erreurs de transformation ou d'autres listeners peuvent néanmoins déjà exister.

Comment, étape par étape ?

  1. Pour des données brutes, privilégier PRE_SUBMIT du parent.
  2. Pour la donnée convertie d'un enfant, écouter son POST_SUBMIT.
  3. Ajouter le champ dépendant à son parent, toujours en traitement.
  4. Prévoir séparément la construction initiale si le même champ doit être présent avant soumission.

Exemple concret PHP

Démonstration de soumission avec Form chargé, sans rendu initial ni extension Validator :

<?php
use Symfony\Component\Form\Forms;
use Symfony\Component\Form\FormEvent;
use Symfony\Component\Form\FormEvents;
use Symfony\Component\Form\Extension\Core\Type\ChoiceType;
$builder = Forms::createFormFactory()->createBuilder();
$builder->add('delivery', ChoiceType::class, ['choices' => ['Retrait' => 'pickup']]);
$builder->get('delivery')->addEventListener(FormEvents::POST_SUBMIT, static function (FormEvent $event): void {
    $parent = $event->getForm()->getParent();
    if (null === $parent) { throw new \LogicException('Un parent est nécessaire.'); }
    if ('pickup' === $event->getForm()->getData()) {
        $parent->add('pickupPoint', ChoiceType::class, ['choices' => ['Centre' => 'center', 'Gare' => 'station']]);
    }
});
$form = $builder->getForm();
$form->submit(['delivery' => 'pickup', 'pickupPoint' => 'station']);
var_export($form->getData());

Le résultat contient delivery égal à pickup et pickupPoint égal à station. Contre-exemple : ajouter pickupPoint sur le Form de l'enfant dans ce listener : il est déjà soumis. Correction : cibler le parent. Pour l'affichage initial, reproduire la décision à partir du modèle dans une phase de mise en place adaptée ; ce script montre uniquement le parcours de soumission.

Passage canonique conservé

Ce que dit le code sur le verrouillage

Form::add() ne teste qu'une chose : le form est-il marqué soumis ? Form::submit() pose ce marqueur après SUBMIT et avant POST_SUBMIT. Un listener du form racine ajoute extra, la Request envoyant extra = 'sent' :

Event add() Le field ajouté
PRE_SET_DATA, POST_SET_DATA, PRE_SUBMIT accepté soumis, donnée 'sent'
SUBMIT accepté, sans erreur jamais soumis
POST_SUBMIT AlreadySubmittedException : « You cannot add children to a submitted form. » —

Repère — Comment s'abonner : During form building, before the dispatcher becomes immutable. Le builder accepte listeners et subscribers. Après construction, le dispatcher ne s'étend plus.

Les forms imbriqués

  • L'enfant est soumis en entier avant le SUBMIT du parent : un field dépendant s'ajoute au parent, depuis le POST_SUBMIT de l'enfant, et il est soumis avec la valeur de la Request.
  • La validation ne part que du form racine : ValidationListener écoute le POST_SUBMIT de chaque form mais n'agit que si isRoot(). Dans le POST_SUBMIT d'un enfant, aucune erreur de validation n'existe toujours.

Les points de contrôle d'un dossier enfant se terminent avant ceux du parent. Un POST_SUBMIT de l'enfant peut donc compléter le parent ; cela ne signifie pas qu'il peut modifier la structure de l'enfant déjà soumis.

Repère de l’exemple : To the parent form, not to the already-submitted country child. Le listener lit le pays transformé avec getForm()->getData(). Il ajoute region au parent qui peut toujours intégrer ce field, pas à l'enfant déjà soumis.

La table de décision

À comprendre

À retenir en priorité
  1. PRE_SUBMIT agit sur les données brutes.
  2. SUBMIT agit sur norm data.

C'est quoi ?

Un form event est une notification située à un moment précis de la construction ou de la soumission du formulaire. Un listener, traitement enregistré pour cet event, reçoit un objet contenant le formulaire et les données de cette étape. Il faut identifier ces données avant de les lire ou de les remplacer.

À quoi ça sert ?

Un formulaire dynamique doit parfois dépendre de l'objet initial, parfois de la saisie nouvelle. Ces besoins ne se résolvent pas au même moment. Modifier la structure trop tard peut laisser un champ non soumis ou provoquer une exception ; il ne suffit pas que la méthode add() soit accessible.

Où dans Symfony ?

Les cinq events principaux sont :

  • PRE_SET_DATA et POST_SET_DATA : mise en place des données modèle.
  • PRE_SUBMIT : données brutes soumises, avant les transformations.
  • SUBMIT : données normalisées, après la soumission des enfants.
  • POST_SUBMIT : fin de soumission ; la donnée de l'event est celle de vue, alors que getData() du formulaire expose le modèle. La validation intégrée intervient sur cette phase.

Comment, étape par étape ?

  1. Si la décision dépend de l'objet initial, utiliser PRE_SET_DATA et lire $event->getData(), sans déclencher une lecture récursive de données encore en cours d'installation.
  2. Si elle dépend d'un champ envoyé, utiliser PRE_SUBMIT sur le parent.
  3. Autre cas : le POST_SUBMIT d'un enfant peut modifier son parent encore en cours de soumission. Ne pas modifier le même enfant déjà soumis.
  4. Ne pas prendre SUBMIT comme phase normale d'ajout d'enfants : même si l'ajout est accepté par le code, la phase de soumission de ces enfants est déjà passée.

Exemple concret PHP

Dans buildForm(), $builder est le builder reçu. Le champ name doit déjà avoir été ajouté. Le listener normalise seulement une chaîne ; il ne transforme pas silencieusement un tableau inattendu en texte.

$builder->addEventListener(
    \Symfony\Component\Form\FormEvents::PRE_SUBMIT,
    static function (\Symfony\Component\Form\FormEvent $event): void {
        $data = $event->getData();
        if (is_array($data) && isset($data['name']) && is_string($data['name'])) {
            $data['name'] = trim($data['name']);
            $event->setData($data);
        }
    },
);

' Ada ' devient 'Ada' avant les conversions des enfants. Contre-exemple : lire un objet métier dans ce listener alors que l'event porte le tableau brut envoyé. Correction : utiliser la couche de données de l'event choisi, ou déplacer le traitement vers la phase correspondant à l'objet initial.

La table de décision

Besoin Event
modifier la donnée initiale ; adapter la structure à elle PRE_SET_DATA (ou POST_SET_DATA)
assainir la donnée brute soumise PRE_SUBMIT
ajouter des fields d'après la valeur soumise PRE_SUBMIT sur le parent, ou POST_SUBMIT sur l'enfant
modifier la norm data SUBMIT
réagir après coup, journaliser POST_SUBMIT

La question qui tranche : réagit-on à la donnée initiale (l'object) ou à la donnée soumise (la Request) ?

Comment s'abonner

À retenir en priorité
  1. Le builder accepte listeners et subscribers.
  2. Après construction, le dispatcher ne s'étend plus.

$builder->addEventListener(FormEvents::PRE_SET_DATA, $callable) pour un cas local, ou une class EventSubscriberInterface, réutilisable. Les listeners se déclarent pendant buildForm() : ensuite, le dispatcher est un ImmutableEventDispatcher, et addListener() lève une BadMethodCallException.

Pièges d'examen

Piège à éviter

Données, ajout de champs et validation selon l’événement du formulaire
  • PRE_SUBMIT reçoit la donnée brute : strings, arrays, files téléversés — pas d'object du modèle.
  • À SUBMIT, add() ne lève rien, mais le field ajouté n'est jamais soumis ; l'exception n'arrive qu'à POST_SUBMIT.
  • POST_SUBMIT porte la view data ; le modèle est sur le form.
  • Dans PRE_SET_DATA, $form->getData() lève une exception : lire $event->getData().
  • La validation s'exécute sur le POST_SUBMIT de la racine, pas avant.
  • Un field dépendant s'ajoute au parent.

Application

À retenir en priorité
  1. L'enfant termine avant le SUBMIT du parent.
  2. Le parent peut ainsi traiter le field dépendant.
  3. PRE_SET_DATA concerne les données initiales.
  4. PRE_SUBMIT précède les transformations de submission.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Cinq events : PRE_SET_DATA, POST_SET_DATA, PRE_SUBMIT, SUBMIT, POST_SUBMIT.
  • Données : modèle, modèle, Request, normalisée, vue.
  • PRE_SET_DATA : lire $event->getData() ; $form->getData() lève une exception.
  • add() : OK jusqu'à PRE_SUBMIT ; ignoré à SUBMIT ; exception à POST_SUBMIT.
  • L'enfant est soumis en entier avant le SUBMIT du parent.
  • Field dépendant : ajouté au parent depuis le POST_SUBMIT de l'enfant.
  • Validation : POST_SUBMIT de la racine ; dispatcher immuable après buildForm().

Moyen mnémotechnique : « Poser, compléter, recevoir, normaliser, conclure ».
