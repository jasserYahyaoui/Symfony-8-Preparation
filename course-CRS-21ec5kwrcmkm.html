Objectif

Savoir ce que la backward compatibility promise garantit au user de Symfony, et surtout ce qu'elle ne garantit pas.

L'essentiel

À comprendre

À retenir en priorité
  1. Utiliser une API n'est pas la même chose que l'étendre.
  2. Un nouveau membre Symfony peut entrer en collision avec un membre ajouté.

La promesse suit le semantic versioning : seule une version majeure peut casser la compatibilité ; une mineure ajoute et déprécie. Mais elle n'est pas globale : elle dépend de la manière dont on utilise le code — utiliser, implémenter, étendre — et trois zones en sont exclues. Le piège le plus visé : les named arguments.

Le schéma

À retenir en priorité
  1. Les named arguments ordinaires ne sont pas garantis.
  2. Les constructors d'attributes constituent l'exception.

L'exemple : un argument ajouté en mineure

Exemple concret

À retenir en priorité
  1. L'argument ajouté vient en dernière position.
  2. Le comportement antérieur reste le défaut effectif.
class Example03d5f51d
{
    public function say(string $text, /* bool $stripWhitespace = true */): void
    {
        $stripWhitespace = 2 <= \func_num_args() ? func_get_arg(1) : false;
    }

Le contexte de class, d’interface ou de builder est explicité pour la syntaxe ; les dependencies et données de l’application ne sont pas exécutées ici.

Utiliser, étendre, implémenter

À comprendre

C'est quoi ?

La compatibilité ascendante, souvent abrégée BC pour backward compatibility, est la promesse qu'un usage couvert continue de fonctionner lors d'une évolution compatible de Symfony. Utiliser une API publique, implémenter une interface et étendre une classe ne créent pas les mêmes risques.

À quoi ça sert ?

La promesse rend les mises à jour prévisibles, mais elle ne garantit pas tous les usages techniquement possibles. Une réflexion sur un détail privé ou une nouvelle méthode ajoutée dans une sous-classe peut dépendre d'un choix interne que Symfony conserve le droit de modifier.

Où dans Symfony ?

Sous réserve des exclusions documentées, les appels publics et l'implémentation des interfaces sont couverts. L'extension d'une classe l'est largement pour ses points publics et protégés. En revanche, ajouter une nouvelle méthode ou propriété dans une sous-classe expose à une collision avec un futur ajout du parent ; accéder au privé par réflexion n'est pas couvert.

Comment, étape par étape ?

  1. Identifier l'API et vérifier qu'elle n'est ni interne ni expérimentale.
  2. Classer l'usage : appel, implémentation ou extension.
  3. Pour une extension, vérifier si l'on surcharge un point prévu ou invente un nom susceptible de collision.
  4. Préférer composition et interface lorsque l'héritage n'apporte pas de contrat utile.

Exemple concret text

Version A du parent : aucune méthode normalize()
Application : sous-classe avec normalize(int): int
Version B du parent : ajout public normalize(string): string
Résultat : collision de signatures dans la sous-classe

Le nouvel appel public du parent peut être compatible pour ses utilisateurs ordinaires tout en cassant cette sous-classe. Contre-exemple : conclure « une mineure ne peut jamais casser mon héritage ». Correction : vérifier la catégorie d'usage et les exclusions ; encapsuler le service dans un objet applicatif lorsque l'on veut seulement lui ajouter une opération indépendante. Les garanties des traits ont leur propre grille : leur code importé devient partie de la classe utilisatrice, contrairement au privé d'un parent.

Passage canonique conservé

Utiliser, étendre, implémenter

Utiliser et implémenter une interface sont toujours couverts. Étendre l'est pour l'essentiel, mais la grille officielle répond non à quatre lignes : ajouter une property, ajouter une method, appeler une method privée ou lire une property privée par réflexion. Les deux premières vous concernent en code ordinaire : si Symfony ajoute le même nom en mineure, la collision est à votre charge.

Repère — Les traits, et leur asymétrie avec les classes : No. Trait members become part of the consuming class and receive broader protection, unless internal. Le trait est intégré dans la class consommatrice. Le privé d'une class Symfony n'a pas la même garantie.

Repère — Ajouter un argument : toujours en dernier : Last, documented without breaking the existing signature, and read through func_get_arg(). L'argument ajouté vient en dernière position. Le comportement antérieur reste le défaut effectif.

Les traits, et leur asymétrie avec les classes

À retenir en priorité
  1. Le trait est intégré dans la class consommatrice.
  2. Le privé d'une class Symfony n'a pas la même garantie.

La grille des traits ne répond jamais non : properties et methods, publiques, protégées ou privées, tout est garanti. Le privé d'une class ne l'est jamais, celui d'un trait toujours : un trait importé fait partie de votre class. Seule exception : @internal.

Ajouter un argument : toujours en dernier

Un argument ne s'ajoute à une method publique qu'en dernière position, en commentaire dans la signature, documenté en PHPDoc et lu par func_num_args() et func_get_arg(). Le défaut retenu préserve le comportement actuel — false ici, quand le commentaire annonce true.

Les trois exclusions

À comprendre

À retenir en priorité
  1. @internal exclut l'API du contrat de stabilité.
  2. Une fonctionnalité experimental possède une fenêtre limitée.

C'est quoi ?

Une exclusion de compatibilité désigne une surface que Symfony ne promet pas de stabiliser comme son API publique ordinaire. Le fait qu'une classe ou une chaîne soit accessible ne suffit pas à la rendre contractuelle.

À quoi ça sert ?

Les internes peuvent évoluer pour améliorer l'implémentation ; l'expérimental recueille des retours avant stabilisation ; les traductions internes peuvent être corrigées sans devenir une interface de programmation figée.

Où dans Symfony ?

  • @internal et les espaces de noms de tests désignent des éléments non destinés à l'usage applicatif public.
  • @experimental signale une fonctionnalité hors promesse pendant cette phase. La politique prévoit normalement une mineure, avec prolongation exceptionnelle d'une mineure, et pas d'introduction expérimentale dans une LTS.
  • Les traductions internes des messages de sécurité et de validation ne sont pas couvertes.

Une rupture peut également être tolérée lorsqu'elle est nécessaire pour corriger une faille de sécurité.

Comment, étape par étape ?

  1. Lire les annotations et la documentation de l'élément utilisé.
  2. Vérifier si la donnée est un contrat ou seulement un détail de présentation.
  3. Éviter de bâtir une décision métier sur un texte interne traduit.
  4. Prévoir des tests et une adaptation explicite si une fonctionnalité expérimentale est choisie.

Exemple concret text

Mauvais contrat : si le message traduit vaut exactement « valeur incorrecte », classer l'erreur X
Contrat préférable : utiliser le type ou le code d'erreur documenté, puis traduire pour l'affichage

Contre-exemple : refuser une mise à jour parce qu'une traduction interne a changé alors que le code analysait cette phrase. Correction : ne pas utiliser la phrase comme identifiant métier. « Stable » ne signifie pas que chaque octet affiché dans une erreur ou chaque classe de tests publique est gelé.

Passage canonique conservé

Les trois exclusions

  • ce qui porte @internal, et tout namespace *\Tests\ ;
  • les fonctionnalités @experimental : une seule mineure — prolongeable d'une au cas par cas —, jamais dans une LTS ;
  • les translations internes de sécurité et de validation.

Une rupture est aussi tolérée pour corriger une faille de sécurité.

Un contrat de location protège les pièces qui en font partie, pas les zones explicitement réservées au personnel. @internal marque pareillement une frontière : la visibilité PHP seule ne suffit pas à promettre la stabilité.

Le piège des named arguments

À comprendre

C'est quoi ?

Les arguments nommés PHP associent une valeur au nom du paramètre plutôt qu'à sa position. Ce nom devient donc une dépendance du code appelant. La promesse Symfony ne protège ces noms que pour les constructeurs des classes d'attributs.

À quoi ça sert ?

Cette limite explique comment un renommage de paramètre peut préserver les appels positionnels tout en cassant un appel nommé. Elle ne dit pas que PHP interdit les arguments nommés ailleurs ; elle distingue validité immédiate et stabilité promise lors des mises à jour.

Où dans Symfony ?

#[Route(path: '/blog')] utilise le constructeur d'un attribut : son nom path relève de l'exception protégée. Une méthode de service ordinaire ne bénéficie pas automatiquement de cette protection pour ses noms de paramètres.

Comment, étape par étape ?

  1. Vérifier si l'appel vise le constructeur d'une classe d'attribut.
  2. Sinon, distinguer la signature publique garantie du nom des paramètres non couvert.
  3. Choisir l'appel en connaissance de cette dépendance.
  4. Lors d'une mise à jour, tester les appels nommés concernés et lire les changements documentés.

Exemple concret PHP

Ce PHP autonome montre le mécanisme, sans prétendre reproduire une API Symfony réelle.

<?php
function formatLabel(string $text, bool $uppercase = false): string
{
    return $uppercase ? strtoupper($text) : $text;
}
echo formatLabel(text: 'demo', uppercase: true), "\n";

La sortie est DEMO. Si l'auteur renomme $uppercase en $capitalize sans garder ce nom, l'appel nommé uppercase: échoue alors qu'un appel positionnel avec true conserve sa position. Contre-exemple : déduire de la prise en charge PHP que tous les noms de paramètres Symfony sont garantis. Correction : appliquer la règle précise des constructeurs d'attributs et évaluer séparément les autres appels.

Passage canonique conservé

Le piège des named arguments

Les noms de parameters ne sont couverts que pour les constructors de classes d'attribute : #[Route(path: '/blog')] survit à une mineure, $service->method(timeout: 5) peut casser.

final et @final

À comprendre

À retenir en priorité
  1. final bloque techniquement l'extension.
  2. @final peut exclure l'extension de la promesse sans la bloquer.

C'est quoi ?

final est un mot-clé PHP qui interdit l'extension d'une classe ou la surcharge d'une méthode finale. @final est une indication documentaire : PHP ne l'impose pas, mais la politique de compatibilité peut exclure l'héritage de cet élément.

À quoi ça sert ?

Une bibliothèque peut annoncer que son objet est destiné à être utilisé plutôt qu'étendu. Cela réduit les engagements liés aux détails d'héritage. Le consommateur peut ajouter un comportement par composition sans supposer que la structure interne est un point d'extension.

Où dans Symfony ?

La documentation distingue @final sans date et @final since Symfony x.y, qui annonce une finalisation à la prochaine majeure. Cette dernière forme est un avis de migration : la classe n'est pas déjà considérée finale de la même manière pendant la période de transition.

Comment, étape par étape ?

  1. Vérifier le mot-clé et les annotations de la classe.
  2. Ne pas confondre « PHP accepte mon héritage » et « cet héritage est garanti ».
  3. Si la finalisation est annoncée, préparer le remplacement de l'héritage.
  4. Conserver un contrat public avec un objet enveloppant ou une interface adaptée.

Exemple concret PHP

<?php
final class BaseFormatter
{
    public function format(string $value): string { return trim($value); }
}
final class ApplicationFormatter
{
    public function __construct(private BaseFormatter $formatter) {}
    public function format(string $value): string
    {
        return '['.$this->formatter->format($value).']';
    }
}
echo (new ApplicationFormatter(new BaseFormatter()))->format(' demo '), "\n";

La sortie est [demo] ; aucune extension de la classe finale n'est nécessaire. Contre-exemple : retirer localement final dans vendor/ pour faire fonctionner une sous-classe. Correction : utiliser la composition ou un point d'extension public ; modifier une dépendance installée ne crée aucune garantie de maintenance.

Passage canonique conservé

final interdit l'extension. @final marque la même intention sans l'imposer : le code fonctionne, mais l'étendre sort de la promesse. @final since Symfony x.y annonce une class qui deviendra finale à la prochaine majeure : elle n'est pas toujours considérée finale.

Pièges d'examen

Piège à éviter

  • Voir l’explication : « Étendre est couvert » est vrai à quatre lignes près.

    « Étendre est couvert » est vrai à quatre lignes près. Ajouter une property ou une method à une class Symfony étendue n'est pas garanti : Symfony peut introduire le même nom en mineure. Les deux autres lignes visent le privé par réflexion, jamais garanti.

  • Voir l’explication : Les named arguments ne sont pas couverts

    Les named arguments ne sont pas couverts, sauf pour les constructors de classes d'attribute.

  • Voir l’explication : @final n'interdit rien techniquement.

    @final n'interdit rien techniquement. Le code qui étend une class @final fonctionne — il sort simplement de la promesse. Seul le mot-clé final empêche l'extension.

  • Voir l’explication : Privé d'un trait ≠ privé d'une class.

    Privé d'un trait ≠ privé d'une class. Le premier est garanti, le second jamais. Le trait devient votre code ; la class reste celle de Symfony.

  • Voir l’explication : Un argument ne s'ajoute qu'en dernière position.

    Un argument ne s'ajoute qu'en dernière position. Une signature Symfony qui porte un argument en commentaire n'est pas un oubli : c'est le procédé officiel.

Application

À retenir en priorité
  1. Le trait est intégré dans la class consommatrice.
  2. Le privé d'une class Symfony n'a pas la même garantie.
  3. Les named arguments ordinaires ne sont pas garantis.
  4. Les constructors d'attributes constituent l'exception.

Fiche express

À mémoriser

Si tu dois retenir seulement 7 choses :

  • Utiliser, implémenter : couverts ; étendre : sauf ajout de property ou de method.
  • Privé par réflexion : jamais ; privé d'un trait : toujours.
  • Named arguments : constructors d'attribute seulement.
  • Hors promesse : @internal, *\Tests\, @experimental, translations internes.
  • @experimental : une mineure, jamais en LTS.
  • Argument ajouté en dernier, défaut qui préserve le comportement.
  • @final marque l'intention ; final l'impose.

Moyen mnémotechnique : « Trois verbes, trois verdicts ».
