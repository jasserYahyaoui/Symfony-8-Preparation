Objectif

Comprendre qui collecte quoi, où c'est stocké, et par quels entry points on y accède — y compris quand la barre n'apparaît pas.

L'essentiel

○ À comprendre

À retenir en priorité
  1. La collecte précède le stockage.
  2. La barre est une vue du profil.

Trois pièces : les data collectors ramassent l'information, le profiler la stocke sous un token, la debug toolbar en affiche un résumé. La barre n'est qu'une vue : elle manque souvent (JSON, redirect), le profil existe toujours. Le tout s'installe en dependency de développement, jamais en production.

Le schéma

À retenir en priorité
  1. La présentation et la collecte sont distinctes.
  2. Examiner les headers de diagnostic lorsqu'ils sont présents.

L'exemple : un collector de hits

▣ Exemple concret

À retenir en priorité
  1. Le profil est sérialisé.
  2. Conserver des données plutôt que des ressources actives.
class HitCollector extends AbstractDataCollector implements LateDataCollectorInterface
{
    public function __construct(private HitCounter $counter) {}

    public function collect(Request $request, Response $response, ?\Throwable $exception = null): void
    {
        $this->data['hits'] = $this->counter->count();      // ramasse, ne mesure pas
    }

    public function lateCollect(): void
    {
        $this->data['late_hits'] = $this->counter->count(); // après la Response
    }
}

Trois pièces, trois roles

À retenir en priorité
  1. Le diagnostic est sensible.
  2. Ne pas confondre outil de développement et fonctionnalité publique.
Pièce Role
Data collectors ramassent l'information pendant la Request
Profiler stocke ces données sous un token, et les ressert
Debug toolbar affiche un résumé en bas de la page

composer require --dev symfony/profiler-pack. La documentation est catégorique : ne jamais l'activer en production, ce serait ouvrir des vulnérabilités majeures. Un controller qui reçoit le service profiler le type ?Profiler : il n'existe pas en production.

La barre n'apparaît pas toujours

À retenir en priorité
  1. Le lien peut exister sur une Response non HTML.
  2. Son absence ne se traite pas comme une erreur fonctionnelle.
Response Barre injectée X-Debug-Token-Link
HTML avec </body> oui présent
JSON, redirect 302, HTML demandé en XHR non présent
HTML sans tag </body> non présent

X-Debug-Token porte le token, X-Debug-Token-Link l'URL du profil, et /_profiler liste tous les profils. Les profils sont supprimés probabilistiquement après 2 jours : une écriture sur dix, la purge (FileProfilerStorage) retire les profils de plus de 2 * 86400 secondes.

Les collectors

À retenir en priorité
  1. La collecte tardive observe la fin du cycle.
  2. Les deux étapes ne sont pas interchangeables.
  • Un service qui implémente DataCollectorInterface — collect(), reset(), getName() — ou étend AbstractDataCollector, qui fournit $this->data.
  • collect() est appelée une seule fois, sur kernel.response : elle ramasse ce qu'un service a mesuré. lateCollect() (LateDataCollectorInterface) tourne sur kernel.terminate : ProfilerListener::onKernelTerminate() l'appelle, puis écrit le profil.
  • Les données sont sérialisées : une connexion, une closure ne passent pas.
  • php bin/console debug:container --tag=data_collector liste les collectors ; avec autoconfigure, rien à déclarer, sinon le tag data_collector.

Un collector de bout en bout

À retenir en priorité
  1. Les données doivent survivre au stockage.
  2. Une function active n'est pas une donnée de profil.
Étape Résultat
getName() non redéfini le FQCN de la class ; getTemplate() rend null
Profiler::collect() appelle collect(), range un clone dans le profil
saveProfile() lateCollect() sur ce clone, puis serialization
loadProfile($token)->getCollector($nom) une copie désérialisée ; nom inconnu : InvalidArgumentException
une Closure dans $this->data saveProfile() lève « Serialization of 'Closure' is not allowed »
reset() vide $this->data

Tagué à la main, le data_collector porte un id égal à getName(). En test, $client->getProfile()->getCollector('app.hit'), après enableProfiler() si collect vaut false.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. Le nom sert de key.
  2. Le tag et la récupération doivent rester cohérents.
  • Voir l’explication : La barre n'est injectée que dans du HTML qui a un </body>

    La barre n'est injectée que dans du HTML qui a un </body>, hors redirect et hors XHR ; sinon, X-Debug-Token-Link, toujours présent.

  • Voir l’explication : collect() est appelée une fois, sur kernel.response

    collect() est appelée une fois, sur kernel.response ; lateCollect() sur kernel.terminate.

  • Voir l’explication : Les profils disparaissent après environ 2 jours

    Les profils disparaissent après environ 2 jours — purge déclenchée une fois sur dix, à l'écriture d'un profil.

  • Voir l’explication : getName() est la key d'accès

    getName() est la key d'accès — par défaut le FQCN, avec AbstractDataCollector.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Un service peut être réutilisé.
  2. Le reset évite de mélanger plusieurs Requests.

Si tu dois retenir seulement 6 choses :

  • Collectors ramassent, profiler stocke, barre affiche.
  • --dev, jamais en production ; ?Profiler dans un controller.
  • Barre : HTML avec </body>, hors redirect et XHR ; sinon X-Debug-Token-Link ou /_profiler.
  • collect() sur kernel.response, une fois ; lateCollect() sur kernel.terminate.
  • Données sérialisées ; purge après 2 jours, une fois sur dix.
  • Nom par défaut : le FQCN ; tag data_collector avec id.

Moyen mnémotechnique : « Ramasser, stocker, montrer ».
