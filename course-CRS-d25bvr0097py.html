Objectif

Modifier le container pendant sa compilation : collecter des services tagués, supprimer une definition, réécrire un argument. Et surtout savoir quand une passe s'exécute, parce que l'étape choisie décide de ce qu'elle peut toujours voir.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le compiler pass modifie le plan.
  2. La création des instances reste ultérieure.

Une passe modifie le container pendant sa compilation : elle manipule des definitions, jamais des objects. Elle s'enregistre dans un bundle ou dans le kernel, à une étape et une priority — et l'étape décide de ce qu'elle voit toujours. Elle ne s'exécute qu'une fois, à la compilation.

Le schéma

À retenir en priorité
  1. Le cache chaud réutilise le résultat.
  2. Les passes ne font pas partie du traitement courant.

Le fil rouge : une chaîne de handlers

À retenir en priorité
  1. La passe déclare les appels.
  2. Elle ne doit pas instancier les handlers.
class HandlerPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has(HandlerChain::class)) {   // sinon : ServiceNotFoundException
            return;
        }
        $chain = $container->findDefinition(HandlerChain::class);
        foreach ($container->findTaggedServiceIds('app.handler') as $id => $tags) {
            $chain->addMethodCall('addHandler', [new Reference($id)]);
        }
    }
}

La passe ne construit aucun handler : elle décrit les appels que le container fera plus tard.

Ce qu'une passe est

○ À comprendre

À retenir en priorité
  1. findDefinition() suit les alias.
  2. getDefinition() ne les résout pas.

C'est quoi ?

Une passe de compilation est un objet dont process(ContainerBuilder) modifie les définitions du container pendant sa préparation. Elle travaille sur les instructions de construction, pas sur les objets métier déjà utilisés par les requêtes.

À quoi ça sert ?

Elle peut adapter une définition fournie par un bundle, collecter des services tagués ou vérifier un assemblage. Modifier seulement l'argument nécessaire préserve le reste de la définition, contrairement à sa redéclaration complète sous le même identifiant.

Où dans Symfony ?

La passe implémente CompilerPassInterface. getDefinition() exige un identifiant de définition ; findDefinition() suit les alias. findTaggedServiceIds() retourne les identifiants et attributs de tags, mais ne les trie pas automatiquement par priorité.

Comment, étape par étape ?

  1. Vérifier si la définition attendue doit obligatoirement exister.
  2. La récupérer, en suivant un alias si nécessaire.
  3. Modifier un argument ou ajouter un appel décrit par une Reference.
  4. Laisser le container construire les services plus tard ; éviter get() dans la passe pour exécuter leur logique.

Exemple concret PHP

Dans un bundle dont vendor.exporter doit exister et attend string $region :

<?php
use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\ContainerBuilder;
final class ExportRegionPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has('vendor.exporter')) {
            throw new LogicException('Le service vendor.exporter est requis.');
        }
        $container->findDefinition('vendor.exporter')
            ->setArgument('$region', 'eu');
    }
}

La passe change une instruction ; elle ne lance aucun export. Contre-exemple : appeler $container->get('vendor.exporter')->export() pour « configurer » ce service. Correction : manipuler sa définition. Si l'intégration est réellement facultative, un retour sans modification en cas d'absence peut être légitime ; ici l'absence viole explicitement le contrat et doit échouer.

Passage canonique conservé

Ce qu'une passe est

Une class CompilerPassInterface, une method process(ContainerBuilder). Dans une passe, getDefinition('priv') rend une Definition, et initialized('priv') vaut false.

Method Ce qu'elle fait
has($id) / hasDefinition($id) definition ou alias / definition seulement
getDefinition($id) la definition ; sur un alias, ServiceNotFoundException
findDefinition($id) la definition, en suivant les alias
findTaggedServiceIds($tag) id => liste d'attributes, dans l'ordre de déclaration, sans tri
removeDefinition($id) retire le service
$def->setArgument('$region', 'eu') fixe un argument, nommé ou par index
$def->replaceArgument() exige un argument existant, sinon OutOfBoundsException

Le tri par priority des services tagués se fait avec PriorityTaggedServiceTrait::findAndSortTaggedServices(). Un tag de bundle se préfixe : acme_mailer.transport.

Où l'enregistrer

○ À comprendre

À retenir en priorité
  1. Le kernel peut enregistrer une passe dédiée.
  2. Un bundle peut utiliser son build().

C'est quoi ?

Écrire une classe de passe ne suffit pas à l'exécuter : il faut la joindre à la liste des opérations de compilation. L'enregistrement indique au container quel objet appeler, dans quelle phase et avec quelle priorité.

À quoi ça sert ?

La passe appartient au cycle de préparation, pas au catalogue des services métier. La déclarer seulement comme un service découvert ne constitue pas un enregistrement de passe. Le point d'enregistrement rend aussi visible le propriétaire de la transformation : application ou bundle.

Où dans Symfony ?

Une application peut appeler addCompilerPass() dans Kernel::build(). Un bundle le fait dans son propre build(). Une extension implémentant CompilerPassInterface dispose du raccord prévu par le framework ; le kernel peut également implémenter directement l'interface. Ces raccourcis ont leur ordre propre et ne sont pas équivalents à une priorité arbitrairement choisie.

Comment, étape par étape ?

  1. Choisir le propriétaire de la passe.
  2. Enregistrer l'objet lors de la construction du container.
  3. Laisser la compilation appeler process().
  4. Lors d'un démarrage utilisant un cache valide, ne pas attendre une nouvelle exécution de la passe.

Exemple concret PHP

ExportRegionPass est la classe de passe déjà définie, placée dans le même espace de noms que ce bundle ou importée explicitement.

<?php
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\HttpKernel\Bundle\AbstractBundle;
final class ExportBundle extends AbstractBundle
{
    public function build(ContainerBuilder $container): void
    {
        $container->addCompilerPass(new ExportRegionPass());
    }
}

L'enregistrement utilise la phase et la priorité par défaut. Contre-exemple : appeler process() depuis une action de controller ; le container de l'application est déjà compilé et le moment n'est pas approprié. Correction : enregistrer la passe dans build() et reconstruire le cache quand ses règles changent. La passe n'est pas un listener HTTP.

Les cinq étapes

○ À comprendre

À retenir en priorité
  1. L'étape précède l'optimisation par défaut.
  2. Une priority haute agit plus tôt dans la même étape.

C'est quoi ?

Les phases de compilation sont des groupes ordonnés de passes. La phase choisit le moment global ; la priorité ordonne les passes à l'intérieur d'une même phase. Un grand nombre de priorité ne fait pas sortir une passe de sa phase.

À quoi ça sert ?

Le choix dépend de l'état du graphe nécessaire : définitions avant optimisation, références résolues, ou résultat final après retrait des inutilisés. La plupart des adaptations simples utilisent la phase par défaut, avant optimisation.

Où dans Symfony ?

PassConfig expose cet ordre :

  1. TYPE_BEFORE_OPTIMIZATION : avant optimisation.
  2. TYPE_OPTIMIZE : optimisation.
  3. TYPE_BEFORE_REMOVING : avant suppression.
  4. TYPE_REMOVE : suppression.
  5. TYPE_AFTER_REMOVING : après suppression.

Comment, étape par étape ?

  1. Classer les passes par phase selon la liste ci-dessus.
  2. Dans chaque phase, commencer par la priorité la plus élevée.
  3. Exécuter les transformations successives : chaque passe voit l'état laissé par les précédentes.
  4. Ne pas supposer qu'une donnée produite par une passe plus tardive existe déjà.

Exemple concret PHP

Cet extrait de méthode d'enregistrement reçoit un builder et deux passes existantes ; il n'appelle pas leur logique lui-même.

<?php
use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\Compiler\PassConfig;
use Symfony\Component\DependencyInjection\ContainerBuilder;
function registerPasses(ContainerBuilder $builder, CompilerPassInterface $first, CompilerPassInterface $second): void
{
    $builder->addCompilerPass($first, PassConfig::TYPE_BEFORE_OPTIMIZATION, 20);
    $builder->addCompilerPass($second, PassConfig::TYPE_BEFORE_OPTIMIZATION, 0);
}

$first est exécutée avant $second. Sans arguments supplémentaires, le défaut est TYPE_BEFORE_OPTIMIZATION, priorité 0. Contre-exemple : croire qu'une priorité 1000 en TYPE_AFTER_REMOVING passe avant une priorité 0 en TYPE_BEFORE_REMOVING. Correction : comparer d'abord la phase, puis la priorité.

Passage canonique conservé

Les cinq étapes

addCompilerPass($pass, $type, $priority) : le type par défaut est PassConfig::TYPE_BEFORE_OPTIMIZATION, la priority par défaut 0. À type égal, la priority la plus haute passe en premier.

Ce que l'étape rend visible

○ À comprendre

À retenir en priorité
  1. Référencer avant la suppression préserve le service.
  2. Une passe tardive ne restaure pas automatiquement la definition.

C'est quoi ?

La visibilité d'une définition pendant la compilation dépend des passes déjà exécutées. Un service privé inutilisé peut être retiré ; un tag issu de l'autoconfiguration peut ne pas être posé au tout début. La compilation est une transformation progressive, pas une photographie constante.

À quoi ça sert ?

Une passe qui rend un service nécessaire doit créer sa référence avant que la suppression des inutilisés ne décide de le retirer. Une passe qui consomme des métadonnées automatiques doit attendre qu'elles existent.

Où dans Symfony ?

TYPE_BEFORE_REMOVING offre une étape avant suppression. TYPE_AFTER_REMOVING convient pour examiner ou ajuster ce qui a survécu, pas pour garantir la récupération de définitions déjà disparues. Les priorités internes pertinentes doivent être vérifiées sur la version ciblée ; la règle utile est la dépendance entre transformations, pas « toujours le plus tôt possible ».

Comment, étape par étape ?

  1. Identifier ce que la passe doit lire et ce qu'elle va ajouter.
  2. Repérer le producteur des informations nécessaires.
  3. Placer la passe après ce producteur, mais avant la suppression des services qu'elle rend nécessaires.
  4. Vérifier le résultat compilé et le premier usage du consommateur.

Exemple concret PHP

Dans build(), on peut enregistrer une passe qui ajoute une référence vers un service privé avant les suppressions :

<?php
use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\Compiler\PassConfig;
use Symfony\Component\DependencyInjection\ContainerBuilder;
function registerCollector(ContainerBuilder $builder, CompilerPassInterface $collector): void
{
    $builder->addCompilerPass($collector, PassConfig::TYPE_BEFORE_REMOVING);
}

Contre-exemple : déplacer cette collecte après suppression puis ajouter une référence vers un privé déjà retiré. Le consommateur peut échouer lorsqu'il est construit. Correction : faire connaître la référence avant le retrait, et non rendre tous les services publics pour cacher l'erreur d'ordre. Une compilation qui termine sans erreur ne dispense pas de tester l'instanciation des services modifiés tardivement.

Passe ou configuration

○ À comprendre

À retenir en priorité
  1. Utiliser l'abstraction existante pour une collection.
  2. Réserver la passe aux modifications nécessaires.

C'est quoi ?

La configuration déclarative décrit le service souhaité. Une passe applique un algorithme de transformation au graphe de définitions. Les deux peuvent parfois produire le même résultat, mais n'ont pas le même coût de lecture, de maintenance et d'ordre d'exécution.

À quoi ça sert ?

Choisir l'outil le plus simple rend l'intention visible : un argument fixe relève normalement de arguments ou bind ; une collection de services tagués relève d'abord d'un iterator ou locator. Une passe devient utile pour une adaptation conditionnelle de définitions déjà fournies par un bundle.

Où dans Symfony ?

Redéclarer un identifiant existant remplace sa définition ; cela peut perdre des appels, tags ou options du bundle. Une passe qui modifie seulement un argument évite ce remplacement complet. Avant l'une ou l'autre solution, utiliser l'option publique de configuration du bundle si elle existe.

Comment, étape par étape ?

  1. Chercher une option publique répondant au besoin.
  2. Pour son propre service, utiliser une déclaration explicite.
  3. Pour une collection standard, utiliser l'injection taguée.
  4. Réserver la passe à la transformation réellement nécessaire et tester son ordre.

Exemple concret YAML

App\Exporter est un service applicatif dont le constructeur attend string $region.

services:
    App\Exporter:
        arguments:
            $region: eu

Cette déclaration suffit ; une passe de vingt lignes n'apporterait aucune information supplémentaire. Contre-exemple : recopier sous un même identifiant toute la définition interne d'un bundle pour ne changer qu'un argument. Une évolution du bundle peut rendre cette copie obsolète. Correction : utiliser son option publique ; à défaut, modifier précisément la définition dans une passe. Une passe reste couplée aux détails qu'elle manipule : elle n'annule pas le besoin de vérifier les montées de version.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. La collecte et le tri sont distincts.
  2. Ne pas supposer un ordre de priority.
Definitions, ordre et visibilité des compiler passes
  • Une passe manipule des definitions, jamais des instances.
  • Le type par défaut est TYPE_BEFORE_OPTIMIZATION, priority 0.
  • Câbler un service privé après TYPE_REMOVE échoue : il a déjà disparu — et l'erreur n'arrive qu'à l'exécution, pas à la compilation.
  • Priority haute = plus tôt, à type égal — au-delà de 100, avant l'autoconfiguration.
  • La passe du kernel tourne à -10000, après les passes de bundle de son étape.
  • Une passe s'exécute une fois, à la compilation — jamais par Request.
  • findTaggedServiceIds() retourne une liste d'attributes par service, pas un seul jeu.
  • findTaggedServiceIds() ne trie pas par priority : l'ordre est celui des declarations. Le tri se fait avec PriorityTaggedServiceTrait.
  • getDefinition() sur un alias lève ServiceNotFoundException ; findDefinition() suit l'alias.
  • La method load() d'une extension ne voit ni les services des autres bundles ni ceux de l'application ; une passe les voit tous.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. Les extensions chargent leur configuration.
  2. La passe intervient sur l'ensemble assemblé.

Si tu dois retenir seulement 7 choses :

  • Une passe manipule des definitions ; elle tourne une fois.
  • Défaut : TYPE_BEFORE_OPTIMIZATION, priority 0 ; plus haute = plus tôt.
  • Autoconfiguration à 100 ; kernel à -10000.
  • Référencer un privé avant TYPE_REMOVE, sinon erreur à l'instanciation.
  • getDefinition() ne suit pas les alias, findDefinition() oui.
  • findTaggedServiceIds() ne trie pas.
  • Configuration pour tes services, passe pour ceux des autres.

Moyen mnémotechnique : « Avant d'optimiser, avant de jeter ».
