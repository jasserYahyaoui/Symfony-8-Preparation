Objectif

Savoir ce que Symfony apporte par-dessus le protocole : un reverse proxy écrit en PHP, un attribute déclaratif, et une trace pour comprendre pourquoi une Response a été servie du cache ou non.

L'essentiel

○ À comprendre

À retenir en priorité
  1. Le proxy raisonne sur le protocole HTTP.
  2. La politique vient des headers de Response.

Par-dessus le protocole HTTP, Symfony apporte un reverse proxy écrit en PHP, activé par une option ; un attribute #[Cache] qui déclare la politique d'une action ; et une trace, X-Symfony-Cache, qui dit pourquoi une Response vient du cache ou non. Le cache ne vaut que pour les safe methods, et sa key est l'URI.

Le schéma

À retenir en priorité
  1. Une Response fraîche évite le serveur d'origine.
  2. Une Response périmée peut être revalidée.

Le reverse proxy de Symfony

À retenir en priorité
  1. L'intégration utilise un proxy PHP.
  2. L'application continue d'exprimer sa politique en HTTP.
  • framework.http_cache: true suffit : le kernel stocke les Responses et les ressert. Sous when@prod, parce qu'un cache masquerait les changements pendant le développement.
  • Ce n'est pas Varnish, ni aussi rapide qu'un proxy écrit en C ; mais l'application ne parle que HTTP, et passer à un autre proxy ne la change pas.
  • En debug, le header X-Symfony-Cache trace chaque décision (miss, store puis fresh) ; hors debug, trace_level vaut none. short, conçu pour les journaux du serveur, ne trace que la main Request ; full, tout ; trace_header renomme le header.

Déclarer plutôt que construire

À retenir en priorité
  1. L'attribute fournit une politique par défaut.
  2. Le controller peut la préciser.
  3. Les validators sont définis avant isNotModified().
  4. Un 304 réutilise la représentation déjà stockée.
  • #[Cache] pose une politique par défaut ; les headers posés dans le controller l'emportent : #[Cache(maxage: 60)] et setMaxAge(10) donnent max-age=10.
  • L'attribute écrit ses options en camelCase (maxage, smaxage, mustRevalidate, lastModified) ; $response->setCache([...]) les mêmes en snake_case (max_age, s_maxage, must_revalidate, etag).
  • $response->expire() marque la Response périmée ; $response->setNotModified() en fait un 304 sans contenu.

Après avoir défini l'ETag ou Last-Modified, le controller peut appeler $response->isNotModified($request). Si la condition de la Request est satisfaite, la Response devient 304 et son body est retiré ; retourner à ce moment évite de produire le contenu. Lorsque If-None-Match est présent, il prime sur If-Modified-Since dans la vérification conditionnelle. Un 304 n'est pas une nouvelle représentation vide à stocker comme contenu.

Ce que le cache ne fera pas

À retenir en priorité
  1. public autorise le partage.
  2. La personnalisation doit être prise en compte dans la politique.
  • La key de cache est l'URI, query string normalisée : ?b=2&a=1 et ?a=1&b=2 partagent leur entrée. Pour QUERY, le body entre aussi dans la key.
  • Une entrée public sert tout le monde : exécuté, Bob reçoit la page d'Alice. Sinon, une Request avec Cookie ou Authorization rend la Response private, jamais stockée.
  • Safe methods seulement : jamais PUT ou DELETE ; ne jamais modifier l'état sur un GET ou un HEAD. En 8.0, Request::isMethodCacheable() retient aussi QUERY. Exécuté, un POST à max-age=60 donne pass, invalidate à chaque fois.
  • L'invalidation à la demande n'est pas dans la spécification HTTP : avec l'expiration seule, il faut attendre l'échéance.

Pièges d'examen

△ Piège à éviter

À retenir en priorité
  1. 304 signifie réutiliser la représentation conservée.
  2. Le body ne doit pas être renvoyé.

framework.http_cache: true suffit à activer le proxy ; aucune class à écrire.

Le controller l'emporte sur #[Cache], pas l'inverse.

La key de cache est l'URI, pas la route ni ses parameters — corps compris pour QUERY.

Le cache HTTP ne s'applique qu'aux safe methods.

L'invalidation à la demande est hors spécification HTTP ; RFC 9111 §4.4 n'impose que celle qui suit une method non sûre réussie.

X-Symfony-Cache n'apparaît qu'en debug ou si trace_level le demande.

Fiche express

◆ À mémoriser

À retenir en priorité
  1. La trace explique hit, miss et stockage.
  2. Elle dépend des réglages de diagnostic.

Si tu dois retenir seulement 7 choses :

  • framework.http_cache: true : un reverse proxy en PHP, remplaçable.
  • X-Symfony-Cache en debug ; sinon trace_level (none, short, full), trace_header.
  • #[Cache] déclare ; le controller l'emporte.
  • Attribute en camelCase, setCache() en snake_case.
  • Key : l'URI, query normalisée ; body compris pour QUERY.
  • Safe methods seulement ; Cookie ou Authorization → private.
  • Invalidation à la demande : hors HTTP.

Moyen mnémotechnique : « Activer, déclarer, tracer ».
