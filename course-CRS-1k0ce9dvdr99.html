Objectif

Savoir ce que Symfony apporte par-dessus le protocole : un reverse proxy écrit en PHP, un attribute déclaratif, et une trace pour comprendre pourquoi une Response a été servie du cache ou non.

L'essentiel

À comprendre

À retenir en priorité
  1. Le proxy raisonne sur le protocole HTTP.
  2. La politique vient des headers de Response.

Un reverse proxy reçoit les requêtes avant l'application et peut réutiliser une réponse stockée. Une réponse encore fraîche et réutilisable évite d'exécuter à nouveau le controller. Une réponse périmée peut être revalidée : l'application confirme alors si sa représentation a changé.

Symfony fournit un proxy PHP (HttpCache), une configuration d'activation et l'attribute #[Cache] pour déclarer une politique. L'attribute ne crée pas un cache à lui seul : il règle les en-têtes HTTP. X-Symfony-Cache, lorsqu'il est activé, permet de suivre les décisions du proxy. Les mécanismes d'inclusion externes ne sont pas enseignés ici.

Pour ce proxy, le cache ne vaut que pour les méthodes sûres ; la clé principale est l'URI, et Vary distingue les variantes.

Le schéma

À retenir en priorité
  1. Une Response fraîche évite le serveur d'origine.
  2. Une Response périmée peut être revalidée.

Les losanges ambre sont des décisions, les rectangles bleus des traitements et les formes vertes des étapes d'entrée ou de sortie. pass signifie que le proxy délègue à l'application, pas que l'accès est autorisé par Security.

Cette seconde vue simplifie le parcours normal : elle suppose une variante compatible avec Vary et, pour une revalidation conditionnelle, un validateur tel qu'un ETag ou Last-Modified. Sans validateur utilisable, l'application doit fournir une nouvelle réponse. Les erreurs, verrous et politiques de réutilisation d'une réponse périmée ne sont pas représentés.

Exemple : une page publique a max-age=60 et l'ETag "v1". Une seconde lecture pendant sa fraîcheur peut être servie sans controller. Après expiration, une revalidation qui obtient 304 confirme le corps déjà stocké ; ce 304 entre application et proxy ne signifie pas que le visiteur reçoit nécessairement une page vide.

Le reverse proxy de Symfony

À retenir en priorité
  1. L'intégration utilise un proxy PHP.
  2. L'application continue d'exprimer sa politique en HTTP.
  • framework.http_cache: true suffit : le kernel stocke les Responses et les ressert. Sous when@prod, parce qu'un cache masquerait les changements pendant le développement.
  • Ce n'est pas Varnish, ni aussi rapide qu'un proxy écrit en C ; mais l'application ne parle que HTTP, et passer à un autre proxy ne la change pas.
  • En debug, le header X-Symfony-Cache trace chaque décision (miss, store puis fresh) ; hors debug, trace_level vaut none. short, conçu pour les journaux du serveur, ne trace que la main Request ; full, tout ; trace_header renomme le header.

Déclarer plutôt que construire

À comprendre

À retenir en priorité
  1. L'attribute fournit une politique par défaut.
  2. Le controller peut la préciser.
  3. Les validators sont définis avant isNotModified().
  4. Un 304 réutilise la représentation déjà stockée.

C'est quoi ?

Un reverse proxy reçoit les Requests avant l'application et peut réutiliser une Response stockée. L'expiration dit jusqu'à quand elle est fraîche ; la validation permet de demander si une représentation déjà conservée est encore valable.

À quoi ça sert ?

Une Response fraîche peut éviter le travail de l'origine. Une validation réussie permet un 304 sans renvoyer le contenu déjà connu. Ce sont deux mécanismes différents, pas deux manières de vider un cache applicatif.

Où dans Symfony ?

L'intégration framework.http_cache peut activer le proxy PHP de Symfony. La politique reste exprimée par HTTP : max-age pour la fraîcheur, s-maxage pour les caches partagés, ETag ou Last-Modified pour les validateurs. L'attribute #[Cache] fournit une politique par défaut ; les en-têtes explicitement posés par le controller peuvent la préciser.

Comment, étape par étape ?

  1. Décider si le contenu est réellement partageable. Une Response personnalisée ne doit pas être déclarée publique comme un catalogue identique pour tous.
  2. Définir les en-têtes de fraîcheur et/ou un validateur lié à la représentation.
  3. Après avoir fixé ETag ou Last-Modified, appeler isNotModified($request) pour examiner une Request conditionnelle.
  4. Si elle devient 304, la retourner sans produire son contenu. Le client réutilise sa représentation, il ne stocke pas un nouveau document vide.
  5. En diagnostic, les traces X-Symfony-Cache peuvent indiquer miss, stockage ou fraîcheur ; elles dépendent du mode et de la configuration de trace.

Exemple concret PHP

Fragment de controller pour un contenu public statique, avec $request fourni par HttpFoundation :

$response = new \Symfony\Component\HttpFoundation\Response();
$response->setPublic();
$response->setMaxAge(60);
$response->setEtag('catalogue-v1');
if ($response->isNotModified($request)) {
    return $response;
}
$response->setContent('Catalogue public version 1');
return $response;

L'ETag doit changer quand cette représentation change. Contre-exemple : conserver la même valeur pour une page personnalisée par user. Correction : ne pas partager ce contenu avec une politique publique et concevoir les variantes explicitement.

L'URI et les variantes HTTP appropriées participent à la sélection d'une représentation ; le proxy ne connaît pas les règles métier. Ne jamais modifier l'état par GET ou HEAD pour profiter du cache. Les méthodes mutantes ne deviennent pas cachables simplement parce qu'on ajoute max-age. Une purge applicative à la demande n'est pas une capacité universelle du protocole : elle dépend du proxy choisi. ESI reste hors de ce cours.

Cache HTTP 8.0.

Passage canonique conservé
  • #[Cache] pose une politique par défaut ; les headers posés dans le controller l'emportent : #[Cache(maxage: 60)] et setMaxAge(10) donnent max-age=10.
  • L'attribute écrit ses options en camelCase (maxage, smaxage, mustRevalidate, lastModified) ; $response->setCache([...]) les mêmes en snake_case (max_age, s_maxage, must_revalidate, etag).
  • $response->expire() marque la Response périmée ; $response->setNotModified() en fait un 304 sans contenu.

Après avoir défini l'ETag ou Last-Modified, le controller peut appeler $response->isNotModified($request). Si la condition de la Request est satisfaite, la Response devient 304 et son body est retiré ; retourner à ce moment évite de produire le contenu. Lorsque If-None-Match est présent, il prime sur If-Modified-Since dans la vérification conditionnelle. Un 304 n'est pas une nouvelle représentation vide à stocker comme contenu.

Documentation Symfony 8.0.

Ce que le cache ne fera pas

À retenir en priorité
  1. public autorise le partage.
  2. La personnalisation doit être prise en compte dans la politique.
  • La key de cache est l'URI, query string normalisée : ?b=2&a=1 et ?a=1&b=2 partagent leur entrée. Pour QUERY, le body entre aussi dans la key.
  • Une entrée public peut être réutilisée par un cache partagé : ne pas rendre publique une page personnalisée par utilisateur sans séparation adaptée. Sinon, une Request avec Cookie ou Authorization rend la Response private, jamais stockée.
  • Safe methods seulement : jamais PUT ou DELETE ; ne jamais modifier l'état sur un GET ou un HEAD. En 8.0, Request::isMethodCacheable() retient aussi QUERY. Exécuté, un POST à max-age=60 donne pass, invalidate à chaque fois.
  • L'invalidation à la demande n'est pas dans la spécification HTTP : avec l'expiration seule, il faut attendre l'échéance.

Pièges d'examen

Piège à éviter

À retenir en priorité
  1. 304 signifie réutiliser la représentation conservée.
  2. Le body ne doit pas être renvoyé.
  • Voir l’explication : framework.http_cache: true suffit

    framework.http_cache: true suffit à activer le proxy ; aucune class à écrire.

  • Voir l’explication : Le controller l'emporte sur #[Cache]

    Le controller l'emporte sur #[Cache], pas l'inverse.

  • Voir l’explication : La key de cache est l'URI

    La key de cache est l'URI, pas la route ni ses parameters — corps compris pour QUERY.

  • Méthodes sûres et cache HTTP

    Le cache HTTP ne s'applique qu'aux safe methods.

  • Voir l’explication : L'invalidation à la demande est hors spécification HTTP

    L'invalidation à la demande est hors spécification HTTP ; RFC 9111 §4.4 n'impose que celle qui suit une method non sûre réussie.

  • Voir l’explication : X-Symfony-Cache n'apparaît qu'en debug

    X-Symfony-Cache n'apparaît qu'en debug ou si trace_level le demande.

Fiche express

À mémoriser

À retenir en priorité
  1. La trace explique hit, miss et stockage.
  2. Elle dépend des réglages de diagnostic.

Si tu dois retenir seulement 7 choses :

  • framework.http_cache: true : un reverse proxy en PHP, remplaçable.
  • X-Symfony-Cache en debug ; sinon trace_level (none, short, full), trace_header.
  • #[Cache] déclare ; le controller l'emporte.
  • Attribute en camelCase, setCache() en snake_case.
  • Key : l'URI, query normalisée ; body compris pour QUERY.
  • Méthodes cachables seulement ; Cookie ou Authorization rendent la réponse privée dans ce proxy sauf déclaration publique explicite.
  • Invalidation à la demande : hors HTTP.
